## 01.前言介绍

### 1.1 为什么要深入执行上下文

每当JavaScript代码运行时，引擎都在幕后创建和管理一种数据结构——**执行上下文（Execution Context）**。理解它，就理解了：

- **变量为什么能提升**
- **闭包为什么能记住外层变量**
- **this为什么在不同场景指向不同**
- **作用域链是如何形成的**

这些不是孤立的知识点，它们都源于同一个底层机制。

### 1.2 ECMAScript规范中的定义

ECMAScript规范（ECMA-262）将执行上下文定义为：

> An execution context is a specification device that is used to track the runtime evaluation of code by an ECMAScript implementation.

执行上下文是一个**规范层面的抽象概念**，V8等引擎按照规范的语义实现它，但具体数据结构可能不同。理解规范定义有助于我们跳出具体引擎，把握本质。


## 02.执行上下文的本质

### 2.1 三种执行上下文

JavaScript中存在三种执行上下文：

**全局执行上下文（Global Execution Context）**：

```javascript
// 这段代码在全局执行上下文中运行
var globalVar = "I'm global";
console.log(this); // 浏览器中是window，Node中是global/{}
```

- 一个程序只有一个全局执行上下文
- 创建全局对象（浏览器中是`window`）
- 将`this`绑定到全局对象

**函数执行上下文（Function Execution Context）**：

```javascript
function greet(name) {
    // 每次调用greet都创建一个新的函数执行上下文
    var message = "Hello, " + name;
    return message;
}

greet("Alice");  // 创建EC1
greet("Bob");    // 创建EC2（与EC1独立）
```

- 每次函数**调用**都创建一个新的执行上下文
- 同一个函数被调用多次，每次都是不同的执行上下文

**Eval执行上下文**：

```javascript
eval("var x = 10");  // eval内的代码有自己的执行上下文（不推荐使用）
```

### 2.2 执行上下文栈（调用栈）

引擎通过**执行上下文栈（Execution Context Stack）**管理所有执行上下文：

```javascript
function first() {
    console.log("first");
    second();
    console.log("first end");
}

function second() {
    console.log("second");
    third();
    console.log("second end");
}

function third() {
    console.log("third");
}

first();
```

执行过程中栈的变化：

```
初始状态:
│ Global EC  │ ← 栈底

调用first():
│ first EC   │ ← 栈顶
│ Global EC  │

first中调用second():
│ second EC  │ ← 栈顶
│ first EC   │
│ Global EC  │

second中调用third():
│ third EC   │ ← 栈顶
│ second EC  │
│ first EC   │
│ Global EC  │

third执行完毕，弹出:
│ second EC  │ ← 栈顶
│ first EC   │
│ Global EC  │

second执行完毕，弹出:
│ first EC   │ ← 栈顶
│ Global EC  │

first执行完毕，弹出:
│ Global EC  │ ← 仅剩全局
```

**关键规则**：同一时刻只有一个执行上下文在运行（JavaScript是单线程的）。新的执行上下文压入栈顶，执行完毕后弹出。

### 2.3 疑惑：栈溢出是怎么发生的

```javascript
function infinite() {
    return infinite();  // 无限递归
}
infinite();  // RangeError: Maximum call stack size exceeded
```

**答疑**：每次函数调用都会在栈上分配一个执行上下文。栈的大小是有限的（V8中默认约984KB），当嵌套调用层数过深时，栈空间耗尽，引擎抛出`RangeError`。

**论证**：

```javascript
// 测试栈深度
let count = 0;
function countStack() {
    count++;
    countStack();
}
try {
    countStack();
} catch(e) {
    console.log(`栈深度: ${count}`);
    // Chrome约15000层，Firefox约26000层
    // 差异来自每个栈帧的大小和栈总大小不同
}
```

**结果**：栈溢出是物理限制，不是逻辑错误。解决方案包括：尾调用优化（TCO）、将递归改为迭代、使用trampoline模式。


## 03.执行上下文的生命周期

### 3.1 两个阶段

执行上下文有两个阶段：**创建阶段**和**执行阶段**。

```javascript
function example(a) {
    var b = 10;
    function inner() {}
    var c = function() {};
}

example(20);
```

**创建阶段（Creation Phase）**：

```
ExecutionContext = {
    // 1. 确定this绑定
    ThisBinding: <取决于调用方式>,

    // 2. 创建词法环境
    LexicalEnvironment: {
        EnvironmentRecord: {
            // let/const声明（未初始化）
            // 函数声明（已初始化为函数对象）
        },
        outer: <外部词法环境引用>
    },

    // 3. 创建变量环境
    VariableEnvironment: {
        EnvironmentRecord: {
            // var声明（初始化为undefined）
            b: undefined,
            c: undefined
        },
        outer: <外部词法环境引用>
    }
}
```

在创建阶段：
- `var`声明的变量被初始化为`undefined`（这就是变量提升）
- 函数声明被完整初始化为函数对象
- `let`/`const`声明被登记但**不初始化**（TDZ的根源）
- 确定`this`的绑定
- 建立作用域链

**执行阶段（Execution Phase）**：

```
ExecutionContext = {
    LexicalEnvironment: {
        EnvironmentRecord: {
            inner: <function object>   // 函数声明在创建阶段就初始化了
        }
    },
    VariableEnvironment: {
        EnvironmentRecord: {
            b: 10,                      // 赋值为10
            c: <function object>        // 赋值为函数表达式
        }
    }
}
```

### 3.2 用一个例子完整追踪

```javascript
var x = 10;

function foo(a) {
    var b = 20;
    return a + b + x;
}

foo(30);
```

**第一步：全局执行上下文的创建阶段**

```
GlobalEC.创建阶段 = {
    ThisBinding: window (浏览器),
    VariableEnvironment: {
        EnvironmentRecord: {
            x: undefined,        // var声明，初始化为undefined
            foo: <function>      // 函数声明，完整初始化
        },
        outer: null              // 全局没有外部环境
    }
}
```

**第二步：全局执行上下文的执行阶段**

```
执行 var x = 10;   → x被赋值为10
执行 foo(30);      → 创建foo的执行上下文
```

**第三步：foo执行上下文的创建阶段**

```
FooEC.创建阶段 = {
    ThisBinding: window (普通调用),
    VariableEnvironment: {
        EnvironmentRecord: {
            a: 30,           // 形参在创建阶段就绑定实参
            b: undefined     // var声明，初始化为undefined
        },
        outer: → GlobalEC.LexicalEnvironment
    }
}
```

**第四步：foo执行上下文的执行阶段**

```
执行 var b = 20;      → b被赋值为20
执行 return a + b + x;
  a → 在当前EnvironmentRecord找到，值30
  b → 在当前EnvironmentRecord找到，值20
  x → 当前没有，沿outer到GlobalEC，找到x=10
  返回 60
```


## 04.变量环境与词法环境

### 4.1 疑惑：为什么有两个环境

ES6之前只有一个变量对象（Variable Object）就够了。ES6引入了`let`/`const`的块级作用域，但要向后兼容`var`的函数作用域。

**答疑**：规范将环境拆分为两个——**词法环境（LexicalEnvironment）**处理`let`/`const`/`class`等块级声明，**变量环境（VariableEnvironment）**处理`var`和`function`声明。

### 4.2 两个环境如何协作

```javascript
function test() {
    var a = 1;
    let b = 2;
    
    {
        var c = 3;     // var穿透块级
        let d = 4;     // let局限于块级
        const e = 5;   // const局限于块级
    }
    
    console.log(a);  // 1
    console.log(b);  // 2
    console.log(c);  // 3   ← var穿透了块！
    console.log(d);  // ReferenceError
}
```

内部结构：

```
test执行上下文:
  VariableEnvironment: {        ← var的家
    a: 1,
    c: 3                       ← var c 穿透了块
  }
  LexicalEnvironment: {         ← let/const的家
    b: 2,
    // 进入块时，创建新的块级词法环境
    BlockLexicalEnvironment: {
      d: 4,
      e: 5,
      outer: → test的LexicalEnvironment
    }
    // 离开块时，BlockLexicalEnvironment被丢弃
  }
```

### 4.3 环境记录的类型

```
EnvironmentRecord（环境记录）
├── DeclarativeEnvironmentRecord（声明式）
│   ├── FunctionEnvironmentRecord（函数的）
│   │   - 有this绑定
│   │   - 有arguments对象
│   │   - 有super引用（如果在class method中）
│   └── ModuleEnvironmentRecord（模块的）
│       - 有import绑定（live binding）
├── ObjectEnvironmentRecord（对象式）
│   - with语句创建
│   - 全局对象的属性绑定
└── GlobalEnvironmentRecord（全局的）
    - DeclarativeRecord + ObjectRecord的组合
    - let/const在DeclarativeRecord中
    - var/function在ObjectRecord中（挂到全局对象上）
```

### 4.4 全局环境的特殊性

```javascript
var a = 1;      // 进入GlobalObjectRecord（window.a可访问）
let b = 2;      // 进入GlobalDeclarativeRecord（window.b不可访问）
const c = 3;    // 进入GlobalDeclarativeRecord

function foo() {} // 进入GlobalObjectRecord（window.foo可访问）

console.log(window.a);    // 1
console.log(window.b);    // undefined!
console.log(window.foo);  // function
```

这就解释了一个常见疑惑：为什么`var`声明的全局变量可以通过`window.xxx`访问，而`let`/`const`不行。


## 05.作用域与作用域链

### 5.1 词法作用域（静态作用域）

JavaScript使用**词法作用域（Lexical Scope）**——作用域在代码编写时（准确说是解析时）就确定了，和代码在哪里调用无关。

```javascript
var x = 10;

function foo() {
    console.log(x);  // 按词法作用域，这里的x是全局的x
}

function bar() {
    var x = 20;
    foo();  // 虽然在bar内调用foo，但foo看到的x仍是全局的10
}

bar();  // 输出 10，不是 20
```

**对比动态作用域**（JavaScript不使用，但bash等脚本语言使用）：

```bash
# bash使用动态作用域
x=10
foo() { echo $x; }
bar() { local x=20; foo; }
bar  # 输出 20（动态作用域：在调用处查找变量）
```

### 5.2 作用域链的形成

作用域链在函数**定义**时就确定了（不是调用时）：

```javascript
var x = "global";

function outer() {
    var x = "outer";
    
    function middle() {
        var x = "middle";
        
        function inner() {
            console.log(x);  // 沿作用域链查找
        }
        
        inner();
    }
    
    middle();
}

outer();  // 输出 "middle"
```

作用域链：

```
inner的作用域链:
  inner的环境 → middle的环境 → outer的环境 → 全局环境
  
查找x的过程:
  1. inner自身：没有x
  2. middle：找到x = "middle" ✓ 停止查找
```

### 5.3 [[Environment]]内部属性

每个函数对象都有一个`[[Environment]]`（在旧规范中叫`[[Scope]]`）内部属性，记录了函数**定义时**的词法环境：

```javascript
function createCounter() {
    let count = 0;
    
    // increment函数在此处定义
    // 它的[[Environment]]指向createCounter的词法环境
    function increment() {
        count++;
        return count;
    }
    
    return increment;
}

const counter = createCounter();
// createCounter执行完毕，但其词法环境没有被GC
// 因为increment的[[Environment]]还在引用它

counter();  // 1
counter();  // 2
```

### 5.4 作用域链的查找算法

```
ResolveBinding(name, env):
  1. 如果 env 为 null，抛出 ReferenceError
  2. 在 env.EnvironmentRecord 中查找 name
  3. 如果找到，返回该绑定
  4. 否则，递归调用 ResolveBinding(name, env.outer)
```

这是一个纯粹的链式查找，从内到外，找到第一个匹配就停止。这意味着**内层变量会遮蔽外层同名变量**：

```javascript
var x = 1;
function foo() {
    var x = 2;       // 遮蔽全局的x
    function bar() {
        var x = 3;   // 遮蔽foo的x
        console.log(x); // 3
    }
    bar();
}
foo();
```

### 5.5 块级作用域的实现

```javascript
function example() {
    let x = 1;
    
    {
        let x = 2;  // 新的块级词法环境中的x
        console.log(x);  // 2
    }
    
    console.log(x);  // 1（块级环境已销毁）
}
```

V8的实现：

```
进入函数:
  LexicalEnv_0 = { x: 1 }

进入块:
  LexicalEnv_1 = { x: 2, outer: → LexicalEnv_0 }
  当前环境切换到 LexicalEnv_1

离开块:
  当前环境恢复到 LexicalEnv_0
  LexicalEnv_1 如果没有闭包引用，可以被GC
```

### 5.6 for循环中的块级作用域

这是一个经典面试题：

```javascript
// var版本——经典bug
for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 100);
}
// 输出: 3, 3, 3（所有回调共享同一个i，循环结束后i=3）

// let版本——符合预期
for (let i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 100);
}
// 输出: 0, 1, 2
```

**let版本为什么有效**？规范规定：`for`循环的每次迭代都会创建一个新的词法环境，并将循环变量的当前值复制到新环境中：

```
迭代0:
  BlockEnv_0 = { i: 0 }  ← 回调0的闭包引用这个环境

迭代1:
  BlockEnv_1 = { i: 1 }  ← 回调1的闭包引用这个环境

迭代2:
  BlockEnv_2 = { i: 2 }  ← 回调2的闭包引用这个环境
```

每个回调捕获了不同的环境，所以看到不同的`i`值。


## 06.变量提升的底层原理

### 6.1 什么是变量提升

变量提升（Hoisting）是指变量和函数声明在代码执行前被"移动"到作用域顶部的行为：

```javascript
console.log(a);  // undefined（不是ReferenceError）
var a = 10;

foo();  // "hello"（函数声明可以在声明前调用）
function foo() { console.log("hello"); }
```

### 6.2 疑惑：代码真的被"移动"了吗

**答疑**：不，代码没有被物理移动。提升是执行上下文**创建阶段**的副作用。

**论证**：

在创建阶段，引擎扫描代码中的所有声明：

1. **`var`声明**：在变量环境中创建绑定，初始化为`undefined`
2. **函数声明**：在词法环境中创建绑定，初始化为**函数对象**
3. **`let`/`const`声明**：在词法环境中创建绑定，**不初始化**

```javascript
// 你写的代码
console.log(a);
var a = 10;

// 引擎"看到"的语义等价（但代码并没有真的被移动）
// 创建阶段：var a → a = undefined
// 执行阶段：console.log(a) → undefined
//           a = 10
```

### 6.3 函数提升优先于变量提升

```javascript
console.log(foo);  // [Function: foo]

var foo = 1;
function foo() {}

console.log(foo);  // 1
```

执行过程：

```
创建阶段:
  1. 扫描到 function foo() {} → 创建绑定 foo = <function>
  2. 扫描到 var foo = 1       → 发现foo已存在，忽略var声明（不覆盖）

执行阶段:
  1. console.log(foo)  → <function>
  2. foo = 1            → 赋值操作覆盖了函数
  3. console.log(foo)  → 1
```

### 6.4 函数表达式不会提升

```javascript
foo();  // TypeError: foo is not a function
var foo = function() { console.log("hello"); };

// 等价于
var foo;          // 创建阶段：foo = undefined
foo();            // 执行阶段：undefined不是函数 → TypeError
foo = function() { console.log("hello"); };
```

注意错误类型：不是`ReferenceError`（变量存在），而是`TypeError`（变量值不是函数）。

### 6.5 同名函数声明的覆盖

```javascript
foo();  // "second"

function foo() { console.log("first"); }
function foo() { console.log("second"); }
```

当有多个同名函数声明时，后面的覆盖前面的。在创建阶段，引擎按源码顺序处理函数声明，后处理的覆盖先处理的。

### 6.6 条件语句中的函数声明

```javascript
// 不同浏览器行为不一致！避免这样写
if (true) {
    function foo() { return 1; }
} else {
    function foo() { return 2; }
}
```

ES规范规定函数声明不应出现在块语句中（只应在函数顶层或程序顶层）。但为了Web兼容性，各引擎有不同的处理方式。**规则**：永远不要在条件语句中使用函数声明，改用函数表达式。


## 07.let/const与暂时性死区

### 7.1 暂时性死区（TDZ）

```javascript
console.log(x);  // ReferenceError: Cannot access 'x' before initialization
let x = 10;
```

TDZ（Temporal Dead Zone）是从块的开始到`let`/`const`声明语句之间的区域。在TDZ中访问变量会抛出`ReferenceError`。

### 7.2 TDZ的底层机制

**疑惑**：`let`/`const`也提升了吗？

**答疑**：是的，`let`/`const`的声明确实被提升了（引擎在创建阶段就知道有这个变量），但它们**没有被初始化**。

**论证**：

```javascript
let x = "outer";

{
    // 如果let没有提升，这里应该访问到外层的x = "outer"
    console.log(x);  // ReferenceError!
    // 但引擎知道块中有一个let x，所以不去外层查找
    // x存在但未初始化，在TDZ中
    let x = "inner";
}
```

**结果**：`let`/`const`的绑定在创建阶段被注册，但初始化被延迟到执行阶段遇到声明语句时。

```
var的生命周期:
  创建 → 初始化为undefined → 赋值

let/const的生命周期:
  创建 → [TDZ] → 初始化 → 赋值（let）/ 绑定（const）
```

### 7.3 TDZ的边界情况

```javascript
// 函数参数默认值中的TDZ
function foo(a = b, b = 1) {
    // 参数按从左到右的顺序初始化
    // a的默认值引用b时，b还在TDZ中
}
foo();  // ReferenceError

// typeof也不能豁免TDZ
typeof undeclared;  // "undefined"（未声明的变量，typeof不报错）
typeof x;           // ReferenceError（x在TDZ中）
let x;
```

### 7.4 const的不可变性

`const`声明的绑定不可变，但值本身可能可变：

```javascript
const obj = { x: 1 };
obj.x = 2;          // 允许！修改的是对象的属性
obj = { x: 3 };     // TypeError！不能重新绑定

// 真正的深冻结需要：
const frozen = Object.freeze({ x: 1, nested: { y: 2 } });
frozen.x = 99;           // 静默失败（严格模式下TypeError）
frozen.nested.y = 99;    // 成功！freeze只是浅冻结
```

### 7.5 var vs let vs const 底层对比

| 特性 | var | let | const |
|------|-----|-----|-------|
| 存储位置 | VariableEnvironment | LexicalEnvironment | LexicalEnvironment |
| 作用域 | 函数级 | 块级 | 块级 |
| 提升 | 声明 + 初始化为undefined | 声明（不初始化） | 声明（不初始化） |
| TDZ | 无 | 有 | 有 |
| 重复声明 | 允许 | SyntaxError | SyntaxError |
| 全局属性 | 是（window.x） | 否 | 否 |
| 可重新赋值 | 是 | 是 | 否 |


## 08.闭包的底层实现

### 8.1 什么是闭包

MDN的定义：**闭包是函数和其词法环境的组合。**

更精确地说：当一个函数访问了其外部作用域的变量，并且该函数在外部作用域之外被执行时，就形成了闭包。

```javascript
function createCounter() {
    let count = 0;  // 自由变量
    
    return function increment() {
        count++;    // 访问外部作用域的变量
        return count;
    };
}

const counter = createCounter();
// createCounter已经返回了，但count没有被GC
counter();  // 1
counter();  // 2
```

### 8.2 V8如何实现闭包

在V8内部，闭包的实现涉及**Context对象**：

```javascript
function outer() {
    let a = 1;   // 被inner引用
    let b = 2;   // 被inner引用
    let c = 3;   // 没有被引用
    
    function inner() {
        return a + b;
    }
    
    return inner;
}
```

V8的处理：

```
1. 编译outer时，V8进行作用域分析：
   - a被inner引用 → 标记为"需要Context分配"
   - b被inner引用 → 标记为"需要Context分配"
   - c没有被引用 → 分配在栈上

2. outer执行时：
   - 创建Context对象（堆上）：{ a: 1, b: 2 }
   - c分配在栈帧上：c = 3

3. inner函数对象的[[Environment]]指向这个Context

4. outer返回后：
   - 栈帧销毁（c被回收）
   - Context对象因为inner的引用而保留（a, b存活）
```

**关键洞察**：V8只会将**被闭包引用的变量**放入Context对象。未被引用的变量仍然在栈上，随函数返回而销毁。这是一种重要的优化。

### 8.3 闭包的内存影响

```javascript
function createHeavyClosure() {
    const hugeArray = new Array(1000000).fill('x');  // 大数组
    const name = "test";
    
    return function() {
        return name;  // 只引用了name
    };
}
```

**疑惑**：`hugeArray`没有被返回的函数引用，它会被GC吗？

**答疑**：在现代V8中，**会被GC**。V8在编译时做作用域分析，只有`name`被放入Context对象，`hugeArray`不会。

**但有例外**：

```javascript
function createHeavyClosure() {
    const hugeArray = new Array(1000000).fill('x');
    const name = "test";
    
    return function() {
        // eval可以访问所有外部变量
        // V8无法静态分析eval的内容
        // 所以必须保留整个作用域中的所有变量
        return eval('hugeArray.length');
    };
}
```

如果闭包内使用了`eval`，V8无法确定哪些变量会被访问，只能保守地保留所有变量——这就是`eval`的另一个危害。

### 8.4 共享闭包环境

同一个外部函数中创建的多个内部函数共享同一个Context：

```javascript
function createPair() {
    let shared = 0;
    
    function increment() { shared++; }
    function getCount() { return shared; }
    
    return { increment, getCount };
}

const pair = createPair();
pair.increment();
pair.increment();
pair.getCount();  // 2

// increment和getCount引用同一个Context对象中的shared
```

### 8.5 循环中的闭包

经典的闭包陷阱：

```javascript
// 问题代码
function createFunctions() {
    var funcs = [];
    for (var i = 0; i < 3; i++) {
        funcs.push(function() { return i; });
    }
    return funcs;
}

const [f0, f1, f2] = createFunctions();
f0();  // 3（不是0！）
f1();  // 3
f2();  // 3
// 三个函数共享同一个变量i，循环结束时i=3
```

解决方案对比：

```javascript
// 方案1：IIFE创建新作用域
for (var i = 0; i < 3; i++) {
    (function(j) {
        funcs.push(function() { return j; });
    })(i);  // 每次迭代传入当前i值
}

// 方案2：let的块级作用域
for (let i = 0; i < 3; i++) {
    funcs.push(function() { return i; });
}
// 每次迭代有独立的块级环境，每个闭包引用不同的i
```

### 8.6 闭包的典型应用

**模块模式**：

```javascript
const Module = (function() {
    let private_var = 0;
    
    function privateMethod() {
        private_var++;
    }
    
    return {
        publicMethod() {
            privateMethod();
            return private_var;
        }
    };
})();
```

**柯里化**：

```javascript
function curry(fn) {
    return function curried(...args) {
        if (args.length >= fn.length) {
            return fn.apply(this, args);
        }
        return function(...moreArgs) {
            return curried.apply(this, [...args, ...moreArgs]);
        };
    };
}

const add = curry((a, b, c) => a + b + c);
add(1)(2)(3);    // 6
add(1, 2)(3);    // 6
```

**防抖与节流**：

```javascript
function debounce(fn, delay) {
    let timer = null;  // 闭包保持timer引用
    return function(...args) {
        clearTimeout(timer);
        timer = setTimeout(() => fn.apply(this, args), delay);
    };
}
```


## 09.eval与with对作用域的破坏

### 9.1 eval的作用域影响

```javascript
function test() {
    let x = 1;
    eval('var y = 2');  // 在当前作用域中创建变量
    console.log(y);     // 2（非严格模式下）
}
```

`eval`在非严格模式下会**修改当前执行上下文的变量环境**。这破坏了词法作用域的静态性——引擎在编译时无法确定作用域中有哪些变量。

### 9.2 eval对引擎优化的影响

```javascript
function withEval(str) {
    let x = 1;
    eval(str);    // 可能修改x，可能创建新变量
    return x;     // 引擎不确定x是否被修改过
}

function withoutEval() {
    let x = 1;
    // 没有eval，引擎确定x是常量1
    return x;     // TurboFan可以直接内联为 return 1
}
```

使用`eval`会导致：
1. V8无法对变量做静态分析
2. 闭包必须保留所有变量（无法做死变量消除）
3. TurboFan的优化受到严重限制

### 9.3 严格模式下的eval

```javascript
"use strict";
function test() {
    eval('var x = 10');
    console.log(x);  // ReferenceError!
    // 严格模式下eval有自己独立的作用域
}
```

严格模式将eval的声明限制在eval自身的作用域中，不会泄漏到外部。

### 9.4 with语句的危害

```javascript
// with将对象的属性变成作用域中的变量
var obj = { x: 1, y: 2 };
with (obj) {
    console.log(x);  // 1
    console.log(y);  // 2
    z = 3;           // obj没有z属性，创建了全局变量z！
}
```

`with`创建了一个ObjectEnvironmentRecord，插入到作用域链中。引擎在编译时无法确定`with`块中的标识符是对象属性还是外部变量，严重阻碍优化。

严格模式下`with`被完全禁止。现代代码不应使用`with`。

### 9.5 替代方案

```javascript
// 替代eval
const fn = new Function('a', 'b', 'return a + b');
fn(1, 2);  // new Function有自己的作用域，不影响外部

// 替代with
const { x, y, z } = obj;  // 解构赋值
// 或
const x = obj.x;
const y = obj.y;
```


## 10.严格模式对执行上下文的影响

### 10.1 严格模式的作用域

```javascript
"use strict";  // 全局严格模式

function foo() {
    "use strict";  // 函数级严格模式
}
```

ES6模块自动启用严格模式，不需要`"use strict"`声明。

### 10.2 对this绑定的影响

```javascript
// 非严格模式
function foo() {
    console.log(this);  // window（全局对象）
}
foo();

// 严格模式
"use strict";
function foo() {
    console.log(this);  // undefined
}
foo();
```

严格模式下，普通函数调用不再将`this`默认绑定到全局对象，而是`undefined`。这避免了意外的全局对象污染。

### 10.3 对变量声明的影响

```javascript
"use strict";

x = 10;               // ReferenceError（必须先声明）
delete x;              // SyntaxError（不能删除变量）
var arguments = 1;     // SyntaxError（不能用保留字）
var eval = 1;          // SyntaxError
function foo(a, a) {}  // SyntaxError（不能重复参数名）
```

### 10.4 对arguments的影响

```javascript
// 非严格模式：arguments和参数共享引用
function foo(a) {
    arguments[0] = 99;
    console.log(a);  // 99（a被修改了！）
}
foo(1);

// 严格模式：arguments是参数的独立副本
"use strict";
function bar(a) {
    arguments[0] = 99;
    console.log(a);  // 1（a不受影响）
}
bar(1);
```


## 11.模块作用域

### 11.1 模块有独立的执行上下文

ES模块中的代码运行在独立的模块作用域中：

```javascript
// module-a.js
var x = 1;       // 不是全局变量！
let y = 2;       // 模块作用域
const z = 3;     // 模块作用域

// 模块顶层的this是undefined（不是window）
console.log(this);  // undefined
```

### 11.2 模块的环境记录

```
ModuleEnvironmentRecord {
    // import绑定——live binding
    importedVar: → 指向源模块的绑定（实时引用）
    
    // 模块自身的声明
    x: 1,
    y: 2,
    z: 3
}
```

**Live Binding**（实时绑定）是模块作用域的独特特性：

```javascript
// counter.js
export let count = 0;
export function increment() { count++; }

// main.js
import { count, increment } from './counter.js';
console.log(count);  // 0
increment();
console.log(count);  // 1（看到了最新值！）
// count不是值的拷贝，而是对counter.js中count的实时引用
```

### 11.3 与CommonJS的作用域差异

```javascript
// CommonJS——值的拷贝
// counter.js
let count = 0;
module.exports = { count, increment() { count++; } };

// main.js
const { count, increment } = require('./counter.js');
console.log(count);  // 0
increment();
console.log(count);  // 0（仍然是0！拿到的是拷贝）
```


## 12.实战：从引擎视角分析代码执行

### 12.1 综合示例分析

```javascript
var a = 1;
let b = 2;

function foo(x) {
    var c = 3;
    let d = 4;
    
    function bar(y) {
        let e = 5;
        console.log(a + b + c + d + e + x + y);
    }
    
    bar(6);
}

foo(7);
```

**完整执行流程**：

```
Step 1: 创建全局执行上下文
  GlobalEC = {
    VariableEnvironment: { a: undefined, foo: <function> },
    LexicalEnvironment: { b: <uninitialized> },
    ThisBinding: window
  }
  → 压入调用栈

Step 2: 执行全局代码
  a = 1, b = 2
  调用 foo(7)
  
Step 3: 创建foo执行上下文
  FooEC = {
    VariableEnvironment: { c: undefined },
    LexicalEnvironment: { d: <uninitialized>, bar: <function>, x: 7 },
    ThisBinding: window,
    outer: → GlobalEC.LexicalEnvironment
  }
  → 压入调用栈

Step 4: 执行foo代码
  c = 3, d = 4
  调用 bar(6)

Step 5: 创建bar执行上下文
  BarEC = {
    LexicalEnvironment: { e: <uninitialized>, y: 6 },
    ThisBinding: window,
    outer: → FooEC.LexicalEnvironment
  }
  → 压入调用栈

Step 6: 执行bar代码
  e = 5
  console.log(a + b + c + d + e + x + y)
  查找链: bar → foo → global
    y: 6 (bar自身)
    e: 5 (bar自身)
    x: 7 (foo)
    d: 4 (foo)
    c: 3 (foo)
    b: 2 (global, LexicalEnvironment)
    a: 1 (global, VariableEnvironment → ObjectEnvironmentRecord)
  输出: 1+2+3+4+5+7+6 = 28

Step 7: bar执行完毕
  弹出BarEC

Step 8: foo执行完毕
  弹出FooEC

Step 9: 全局代码执行完毕
  GlobalEC保留（直到页面关闭）
```

### 12.2 经典面试题分析

```javascript
var foo = function() {
    console.log(1);
};

function foo() {
    console.log(2);
}

foo();  // 输出什么？
```

分析：

```
创建阶段:
  1. 扫描函数声明: function foo() { console.log(2); }
     → foo = <function: log 2>
  2. 扫描var声明: var foo
     → foo已存在，跳过

执行阶段:
  1. foo = function() { console.log(1); }
     → 赋值覆盖：foo = <function: log 1>
  2. foo()
     → 输出 1
```

### 12.3 复杂闭包分析

```javascript
function create() {
    let fns = [];
    for (let i = 0; i < 3; i++) {
        fns.push(function() {
            for (let j = 0; j < 3; j++) {
                if (j === i) {
                    return j;
                }
            }
        });
    }
    return fns;
}

const [a, b, c] = create();
console.log(a());  // 0
console.log(b());  // 1
console.log(c());  // 2
```

每次for循环迭代，`let i`创建新的块级环境。每个推入的函数捕获了不同的`i`值（0, 1, 2）。这就是执行上下文和作用域链的完美协作。

### 12.4 函数参数的作用域

```javascript
var x = 1;

function foo(x, y = function() { x = 2; }) {
    var x = 3;
    y();
    console.log(x);  // 3（var x在函数体作用域）
}

foo();
console.log(x);      // 1（全局x未受影响）
```

当函数有默认参数时，ES规范创建一个**中间作用域**：

```
全局环境: { x: 1 }
    ↓
参数环境: { x: undefined, y: <function> }  ← y中的x指向这里
    ↓
函数体环境: { x: 3 }  ← var x在这里
```

`y()`修改的是参数环境中的`x`，而`console.log(x)`读取的是函数体环境中的`x`。三个`x`分别在三个不同的环境中。

### 12.5 总结：执行上下文的核心要点

1. **执行上下文有创建和执行两个阶段**——变量提升是创建阶段的产物
2. **词法环境和变量环境**——ES6块级作用域需要分离处理
3. **作用域在定义时确定**——词法作用域，不是动态作用域
4. **闭包 = 函数 + 词法环境**——V8只保留被引用的变量
5. **`[[Environment]]`**——每个函数对象都记住了它定义时的环境
6. **TDZ**——let/const提升了声明但没有初始化
7. **eval/with破坏静态分析**——严格模式限制了这种破坏
8. **模块有独立作用域**——Live Binding是ESM的独特机制
