## 01.前言介绍

### 1.1 为什么要理解引擎

很多开发者写了多年JavaScript，却从未思考过一个根本问题：**你写的代码是如何变成CPU能执行的指令的？**

理解引擎原理不是为了炫技，而是因为：

1. **性能调优需要方向**：不了解引擎如何优化代码，所谓的"性能优化"只是盲人摸象
2. **诡异行为有了解释**：`typeof null === 'object'`、`0.1 + 0.2 !== 0.3`，这些不是bug，而是底层实现的必然结果
3. **架构设计需要依据**：知道对象在内存中如何存储，才能写出对引擎友好的数据结构

### 1.2 主流JavaScript引擎

| 引擎 | 开发商 | 使用场景 |
|------|--------|---------|
| V8 | Google | Chrome、Node.js、Deno |
| SpiderMonkey | Mozilla | Firefox |
| JavaScriptCore (Nitro) | Apple | Safari、React Native |
| Chakra | Microsoft | 旧版Edge（已废弃） |
| Hermes | Meta | React Native |
| QuickJS | Fabrice Bellard | 嵌入式场景 |

V8是目前最流行的引擎，本文以V8为主线讲解，但核心原理对其他引擎同样适用。

### 1.3 疑惑：JavaScript不是解释型语言吗

很多教材将JavaScript归类为"解释型语言"，这在2008年之前基本正确。但V8从诞生之初就引入了编译技术。

**答疑**：现代JavaScript引擎采用的是**混合执行**策略——先解释执行，对热点代码再编译优化。这被称为**JIT（Just-In-Time）编译**。

**论证**：看一段代码在V8中的完整旅程：

```
源代码 → 词法分析 → 语法分析 → AST → 字节码(Ignition) → 解释执行
                                                ↓
                                         发现热点代码
                                                ↓
                                    机器码(TurboFan) → 直接执行
                                                ↓
                                         假设失败？
                                                ↓
                                    去优化(Deoptimization) → 回到字节码
```

**结果**：JavaScript既不是纯解释型，也不是纯编译型，而是一种**自适应编译**语言。引擎会根据代码的实际运行情况，动态选择最优的执行策略。


## 02.JavaScript引擎全景图

### 2.1 V8架构演进

V8的架构经历过重大变革：

**第一代架构（2008-2016）**：

```
源代码 → Full-Codegen(基线编译器) → 机器码
                                      ↓
                              Crankshaft(优化编译器) → 优化后的机器码
```

问题：直接编译成机器码，内存消耗巨大。一个大型Web应用的机器码可能占用数百MB。

**第二代架构（2016至今）**：

```
源代码 → Parser → AST → Ignition(解释器) → 字节码
                                              ↓
                                    TurboFan(优化编译器) → 机器码
```

引入字节码作为中间表示，内存占用降低了约60%。

### 2.2 完整的代码执行管线

一段JavaScript从文本到执行，要经过以下阶段：

```
┌──────────────────────────────────────────────────────────┐
│  1. 词法分析（Scanner/Lexer）                             │
│     "let x = 1 + 2;"  →  [let] [x] [=] [1] [+] [2] [;]  │
│                            ↓ Token流                       │
│  2. 语法分析（Parser）                                     │
│     Token流 → 抽象语法树（AST）                            │
│                            ↓                               │
│  3. 字节码生成（Ignition）                                 │
│     AST → 字节码指令序列                                   │
│                            ↓                               │
│  4. 解释执行                                               │
│     逐条执行字节码，同时收集类型反馈信息                    │
│                            ↓                               │
│  5. 优化编译（TurboFan）                                   │
│     热点字节码 + 类型反馈 → 优化后的机器码                  │
│                            ↓                               │
│  6. 去优化（Deoptimization）                               │
│     类型假设失败时，回退到字节码解释执行                    │
└──────────────────────────────────────────────────────────┘
```

### 2.3 懒解析策略

V8并不会一次性解析所有代码。它采用**懒解析（Lazy Parsing）**策略：

```javascript
// 顶层代码——立即完整解析
const config = { debug: true };

// 函数声明——先进行预解析（Pre-parsing）
function heavyComputation(data) {
    // 函数体只做语法检查，不生成AST
    // 直到第一次调用时才完整解析
    const result = data.map(x => x * 2);
    return result.reduce((a, b) => a + b, 0);
}

// 此时 heavyComputation 还没有被完整解析

heavyComputation([1, 2, 3]); // 第一次调用，触发完整解析
```

**预解析器（Pre-parser）做了什么**：

1. 验证语法正确性
2. 发现函数声明和变量声明（用于作用域分析）
3. **不**生成AST
4. **不**生成字节码

这个策略很关键。一个典型的Web页面可能加载1MB的JavaScript，但首次加载时只执行其中20-30%。懒解析节省了大量不必要的解析和编译时间。

### 2.4 IIFE的解析陷阱

```javascript
// 被预解析后又立即完整解析——双重解析
(function() {
    // ...
})();
```

V8遇到`function`关键字时会先预解析。但如果发现它是IIFE（被括号包裹且立即调用），就必须回头重新完整解析。这导致了**双重解析开销**。

V8通过启发式规则部分解决了这个问题：当检测到`(`前缀时，会直接进入完整解析模式。但不是所有情况都能检测到。

Webpack的一些插件（如`optimize-js`）会给需要立即执行的函数添加括号前缀，帮助引擎更好地做出解析决策。


## 03.源代码到AST：解析阶段

### 3.1 词法分析：从字符到Token

词法分析器（Scanner）逐字符扫描源代码，输出Token序列：

```javascript
// 源代码
let sum = a + 10;

// 词法分析输出的Token序列
[
  { type: 'Keyword',    value: 'let' },
  { type: 'Identifier', value: 'sum' },
  { type: 'Punctuator', value: '=' },
  { type: 'Identifier', value: 'a' },
  { type: 'Punctuator', value: '+' },
  { type: 'Numeric',    value: '10' },
  { type: 'Punctuator', value: ';' }
]
```

### 3.2 几个有趣的词法分析细节

**自动分号插入（ASI）**发生在词法分析阶段：

```javascript
// 源代码
return
42

// 词法分析器插入分号后
return;   // 返回 undefined！
42;
```

这就是为什么`return`后面不能换行的原因——ASI规则在解析器发现语法错误之前就把分号插入了。

**正则与除法的歧义**：

```javascript
// 这是正则还是除法？
let x = a / b / g;      // 两次除法
let y = /pattern/g;      // 正则表达式
```

词法分析器需要根据上下文判断`/`是除法运算符还是正则表达式的开始。它通过追踪前一个Token的类型来决定：如果前一个Token是标识符、数字或`)`，则`/`是除法；否则是正则。

### 3.3 语法分析：从Token到AST

语法分析器（Parser）将Token序列构建为抽象语法树（AST）：

```javascript
// 源代码
let sum = a + 10;

// AST结构（简化表示）
{
  type: "Program",
  body: [{
    type: "VariableDeclaration",
    kind: "let",
    declarations: [{
      type: "VariableDeclarator",
      id: { type: "Identifier", name: "sum" },
      init: {
        type: "BinaryExpression",
        operator: "+",
        left: { type: "Identifier", name: "a" },
        right: { type: "Literal", value: 10 }
      }
    }]
  }]
}
```

### 3.4 AST的实际应用

AST不仅是引擎内部使用的中间产物，它也是整个前端工具链的基石：

| 工具 | 用途 | AST操作 |
|------|------|---------|
| Babel | 语法转换 | 解析 → 转换AST → 生成代码 |
| ESLint | 代码检查 | 解析 → 遍历AST → 匹配规则 |
| Prettier | 代码格式化 | 解析 → 从AST重新生成代码 |
| Webpack | 模块打包 | 解析import/require → 构建依赖图 |
| TypeScript | 类型检查 | 解析 → 在AST上做类型推断 |

你可以通过 [AST Explorer](https://astexplorer.net/) 在线查看任意JavaScript代码的AST结构。

### 3.5 V8的Parser优化

V8的Parser有几项重要优化：

1. **流式解析**：不需要等待整个脚本下载完成才开始解析，可以边下载边解析
2. **后台解析**：解析可以在后台线程完成，不阻塞主线程
3. **字节码缓存**：解析和编译的结果可以被缓存（V8 Code Cache），下次加载同一脚本时直接使用

```
第一次加载:
  下载脚本 → 解析 → 编译 → 缓存字节码 → 执行

第二次加载:
  下载脚本 → 读取缓存 → 直接执行（跳过解析和编译！）
```

Chrome通过Service Worker和HTTP Cache配合V8 Code Cache，可以让第二次访问时的JavaScript启动时间减少40%以上。


## 04.AST到字节码：Ignition解释器

### 4.1 什么是字节码

字节码是介于AST和机器码之间的中间表示。它是一种**紧凑的指令集**，由V8的Ignition解释器执行。

```javascript
// 源代码
function add(a, b) {
    return a + b;
}
```

你可以通过Node.js查看V8生成的字节码：

```bash
node --print-bytecode --print-bytecode-filter=add script.js
```

输出类似：

```
[generated bytecode for function: add]
Parameter count 3        // this + 2个参数
Register count 0
Frame size 0
   0 : 25 02             Ldar a1         // 把参数a加载到累加器
   2 : 34 03 00          Add a0, [0]     // 累加器 += 参数b
   5 : aa                Return          // 返回累加器的值
```

### 4.2 字节码的设计哲学

**疑惑**：既然最终可能编译成机器码，为什么还要先生成字节码？直接编译不是更快？

**答疑**：V8的第一代架构确实是直接编译成机器码的（Full-Codegen），但这种方案有严重问题：

1. **编译时间长**：大型应用的启动时间很长
2. **内存消耗大**：机器码体积是字节码的3-5倍
3. **没有中间层**：优化编译器无法获得运行时的类型反馈信息

**论证**：通过数据对比：

```
同一段代码在不同表示下的大小：
源代码:    ~100 bytes
AST:       ~300 bytes  (约3倍)
字节码:    ~50 bytes   (约0.5倍，比源代码还小！)
机器码:    ~200 bytes  (约2倍)
```

**结果**：字节码方案达到了三个平衡——

- 启动快（生成字节码比生成机器码快得多）
- 内存省（字节码比机器码小很多）
- 可优化（字节码执行时收集的类型反馈是TurboFan的输入）

### 4.3 Ignition的寄存器机

Ignition是一个**寄存器机**（Register Machine），而不是栈机（Stack Machine）。

**栈机**（如Java的JVM）：

```
// a + b 在栈机上
push a     // 栈: [a]
push b     // 栈: [a, b]
add        // 栈: [a+b]
```

**寄存器机**（V8的Ignition）：

```
// a + b 在寄存器机上
Ldar a1    // 累加器 = a
Add a0     // 累加器 += b
```

寄存器机的优势是指令更少、执行路径更短。V8使用一个特殊的**累加器（Accumulator）**寄存器，大多数操作的结果都存在累加器中，减少了显式的数据移动指令。

### 4.4 类型反馈向量

Ignition在执行字节码时，会为每个操作点收集**类型反馈（Type Feedback）**：

```javascript
function add(a, b) {
    return a + b;  // 这个 + 操作会被监控
}

add(1, 2);       // 反馈: 整数 + 整数
add(3, 4);       // 反馈: 整数 + 整数（确认）
add("a", "b");   // 反馈: 字符串 + 字符串（类型变了！）
```

类型反馈信息存储在**FeedbackVector**中：

```
FeedbackVector for add:
  slot[0]: BinaryOp(+)
    - 之前: Smi + Smi      → Smi结果
    - 现在: 多态（Smi + Smi 或 String + String）
```

这些信息是TurboFan优化编译的核心输入。如果一个`+`操作在99%的情况下都是整数加法，TurboFan就会按整数加法来生成机器码，只在类型不符时做去优化回退。


## 05.热点代码优化：TurboFan编译器

### 5.1 什么是热点代码

V8通过计数器追踪每个函数的调用次数和循环迭代次数。当计数超过阈值时，该函数被标记为"热点"：

```javascript
// 这个函数只调用一次——不会被优化
function initApp() {
    // ...
}

// 这个函数被调用10000次——一定会被优化
function processItem(item) {
    return item.x * item.y + item.z;
}

for (let i = 0; i < 10000; i++) {
    processItem(items[i]);
}
```

### 5.2 TurboFan的优化流程

TurboFan接收字节码和类型反馈，生成优化后的机器码：

```
字节码 + 类型反馈
       ↓
Sea of Nodes（图IR）
       ↓
类型推断和范围分析
       ↓
内联展开（Inlining）
       ↓
逃逸分析（Escape Analysis）
       ↓
公共子表达式消除（CSE）
       ↓
死代码消除（DCE）
       ↓
指令选择和寄存器分配
       ↓
机器码
```

### 5.3 关键优化手段

**内联展开（Inlining）**：

```javascript
// 优化前
function square(x) { return x * x; }
function sumOfSquares(a, b) {
    return square(a) + square(b);
}

// TurboFan内联后（概念上）
function sumOfSquares(a, b) {
    return a * a + b * b;  // 消除了函数调用开销
}
```

**逃逸分析（Escape Analysis）**：

```javascript
function createPoint(x, y) {
    return { x, y };  // 对象可能不需要真正分配在堆上
}

function distance(x1, y1, x2, y2) {
    const p1 = createPoint(x1, y1);
    const p2 = createPoint(x2, y2);
    // p1和p2没有逃逸出这个函数
    return Math.sqrt((p1.x - p2.x) ** 2 + (p1.y - p2.y) ** 2);
}
```

逃逸分析发现`p1`和`p2`没有离开`distance`函数，于是将对象属性直接存储在栈上或寄存器中，避免了堆分配和后续的GC开销。

**类型特化（Type Specialization）**：

```javascript
function add(a, b) {
    return a + b;
}

// 类型反馈显示总是 number + number
// TurboFan生成的机器码（伪代码）：
function add_optimized(a, b) {
    if (typeof a !== 'number' || typeof b !== 'number') {
        // 去优化！回退到字节码
        deoptimize();
    }
    return machine_add_float64(a, b);  // 直接CPU浮点加法
}
```

### 5.4 去优化（Deoptimization）

当运行时遇到违反编译假设的情况，TurboFan编译的代码必须"去优化"：

```javascript
function process(obj) {
    return obj.x + obj.y;
}

// 前1000次调用：总是 {x: number, y: number}
for (let i = 0; i < 1000; i++) {
    process({ x: i, y: i + 1 });
}
// TurboFan已经按 "obj有x和y属性，都是number" 假设优化

// 第1001次：传入了不同结构的对象
process({ x: "hello", y: "world" }); // 触发去优化！
```

去优化的过程：

1. 暂停机器码执行
2. 从机器码栈帧重建字节码栈帧（On-Stack Replacement）
3. 回退到Ignition解释执行
4. 重新收集类型反馈
5. 可能再次触发TurboFan编译（但这次会用更保守的策略）

去优化是昂贵的。频繁的去优化比不优化更慢。


## 06.JIT编译的核心策略

### 6.1 分层编译策略

V8采用分层编译（Tiered Compilation）策略，平衡启动速度和峰值性能：

```
┌─────────────────────────────────────────────────┐
│  Tier 0: Ignition（解释器）                      │
│  - 最快启动                                      │
│  - 最低性能                                      │
│  - 收集类型反馈                                   │
│                                                   │
│  ↓ 热点检测                                      │
│                                                   │
│  Tier 1: Sparkplug（2021新增，基线编译器）         │

```

### 6.2 JIT与AOT的对比

| 方面 | JIT（V8） | AOT（如C++/Rust） |
|------|-----------|-------------------|
| 编译时机 | 运行时 | 运行前 |
| 类型信息 | 运行时收集 | 编译时已知 |
| 启动速度 | 快（先解释执行） | 慢（需完整编译） |
| 峰值性能 | 接近AOT | 最高 |
| 自适应 | 可根据实际运行调整 | 固定 |
| 内存开销 | 包含编译器本身 | 只有目标代码 |

JIT的独特优势是**Profile-Guided Optimization（PGO）**——它能根据实际运行数据做出AOT编译器无法做到的优化：

```javascript
// AOT编译器不知道这里通常传入什么类型
function process(x) {
    if (x > 0) {
        return x * 2;
    } else {
        return -x;
    }
}

// JIT编译器知道：99%的情况x是正整数
// 因此可以把 x > 0 分支放在更有利的位置（分支预测友好）
// 还可以假设x是Smi，直接用整数运算
```

### 6.3 On-Stack Replacement（OSR）

一个特殊的场景：一个函数内的循环非常热，但函数本身只调用了一次：

```javascript
function processAll() {
    for (let i = 0; i < 1000000; i++) {
        // 这个循环是热点，但processAll只调用一次
        doSomething(i);
    }
}

processAll();
```

OSR允许V8在**循环执行过程中**将解释执行切换到优化后的机器码，而不需要等到下次函数调用：

```
processAll() 开始执行（Ignition解释）
    循环第1次...
    循环第100次...
    —— 检测到热点循环 ——
    —— 编译循环体为机器码 ——
    —— 在栈上替换执行帧（OSR Entry）——
    循环第101次...（TurboFan机器码执行）
    循环第1000000次...
processAll() 结束
```


## 07.隐藏类与内联缓存

### 7.1 疑惑：JavaScript对象怎么能高效访问属性

JavaScript是动态类型语言，对象可以随时添加或删除属性。对比静态语言：

```c
// C语言：编译时就知道name在结构体偏移0位置，age在偏移8位置
struct Person { char* name; int age; };
// 访问 person.age 直接一条mov指令，offset固定
```

```javascript
// JavaScript：对象形状随时可变
let person = { name: "Alice" };
person.age = 25;        // 动态添加属性
delete person.name;     // 动态删除属性
// 访问 person.age 如何做到高效？
```

**答疑**：V8通过**隐藏类（Hidden Class）**将动态对象"静态化"。

### 7.2 隐藏类（Hidden Class / Map）

V8为每个对象维护一个隐藏类（内部称为Map），记录对象的形状——有哪些属性、每个属性在哪个偏移位置。

```javascript
let a = {};          // Hidden Class: HC0 {}
a.x = 1;             // Hidden Class: HC1 {x: offset 0}
a.y = 2;             // Hidden Class: HC2 {x: offset 0, y: offset 1}

let b = {};          // Hidden Class: HC0 {}
b.x = 10;            // Hidden Class: HC1 {x: offset 0}  ← 复用了HC1！
b.y = 20;            // Hidden Class: HC2 {x: offset 0, y: offset 1}  ← 复用了HC2！
```

关键洞察：**a和b以相同顺序添加相同名称的属性，它们共享同一系列隐藏类**。

隐藏类形成一个**转换链（Transition Chain）**：

```
HC0 {} —— 添加x → HC1 {x} —— 添加y → HC2 {x, y}
                   ↘ 添加y → HC3 {y}  ← 不同的路径产生不同的HC
```

### 7.3 为什么属性顺序很重要

```javascript
// 对象a和b属性相同但添加顺序不同
let a = {}; a.x = 1; a.y = 2;   // HC0 → HC1{x} → HC2{x,y}
let b = {}; b.y = 2; b.x = 1;   // HC0 → HC3{y} → HC4{y,x}

// a和b有不同的隐藏类！HC2 ≠ HC4
```

这意味着：

```javascript
function getX(obj) {
    return obj.x;   // 这个操作点期望统一的隐藏类
}

getX(a);  // 使用HC2，属性x在offset 0
getX(b);  // 使用HC4，属性x在offset 1（不同offset！）
// 变成多态（Polymorphic），性能下降
```

**编码建议**：对象的属性应该以固定的顺序初始化，最好在构造函数中一次性初始化所有属性。

### 7.4 内联缓存（Inline Cache, IC）

内联缓存是V8优化属性访问的核心机制。原理是**缓存上次属性查找的结果**：

```javascript
function getX(obj) {
    return obj.x;  // 这个位置有一个IC
}

// 第一次调用
getX({ x: 1, y: 2 });
// IC状态：未初始化(Uninitialized) → 单态(Monomorphic)
// 缓存：HC2 → offset 0

// 第二次调用（相同HC）
getX({ x: 10, y: 20 });
// IC命中！直接用offset 0读取，不需要查找
// 状态：保持单态(Monomorphic)

// 第三次调用（不同HC的对象）
getX({ x: 100, z: 200 });
// IC未命中，HC不同
// 状态：单态 → 多态(Polymorphic)
// 缓存：[HC2 → offset 0, HC5 → offset 0]
```

IC的四种状态：

```
Uninitialized → Monomorphic → Polymorphic → Megamorphic
  (未初始化)      (单态,最快)    (多态,较快)    (超态,最慢)
                   1个HC          2-4个HC         >4个HC
```

当IC退化到Megamorphic状态时，V8放弃缓存，改为通用的哈希表查找，性能显著下降。

### 7.5 IC对TurboFan的影响

TurboFan在优化编译时会读取IC的状态：

- **Monomorphic IC**：TurboFan直接内联属性访问，生成一条内存读取指令（最快）
- **Polymorphic IC**：生成一系列类型检查 + 对应的内联访问（稍慢）
- **Megamorphic IC**：调用通用的属性查找函数（最慢，等同于解释执行）

```javascript
// 最佳：所有对象形状一致
const points = [];
for (let i = 0; i < 10000; i++) {
    points.push({ x: i, y: i * 2 });  // 统一形状
}

function sumX(arr) {
    let sum = 0;
    for (const p of arr) {
        sum += p.x;  // Monomorphic IC，TurboFan可以完全优化
    }
    return sum;
}
```

```javascript
// 最差：对象形状混乱
const things = [
    { x: 1 },
    { x: 2, y: 3 },
    { a: 1, x: 4 },
    { x: 5, b: 6, c: 7 },
    // ... 更多不同形状
];

function sumX(arr) {
    let sum = 0;
    for (const t of arr) {
        sum += t.x;  // Megamorphic IC，每次都要查找
    }
    return sum;
}
```

### 8.2 调用栈的结构

每次函数调用都会创建一个**栈帧（Stack Frame）**：

```javascript
function outer(x) {
    let a = 10;
    return inner(a + x);
}

function inner(y) {
    let b = 20;
    return y + b;  // ← 当前执行到这里
}

outer(5);
```

此时的调用栈：

```
┌─────────────────────────┐  ← 栈顶（SP）
│  inner的栈帧              │
│  - b = 20                │
│  - y = 15                │
│  - 返回地址: outer+XX     │
├─────────────────────────┤
│  outer的栈帧              │
│  - a = 10                │
│  - x = 5                 │
│  - 返回地址: global+XX    │
├─────────────────────────┤
│  全局栈帧                 │
│  - 全局变量引用            │
└─────────────────────────┘  ← 栈底（BP）
```

### 8.3 栈溢出

调用栈大小有限（通常约1MB），递归调用太深会导致栈溢出：

```javascript
function factorial(n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}

factorial(100);     // 正常
factorial(100000);  // RangeError: Maximum call stack size exceeded
```

**尾调用优化（TCO）** 可以解决这个问题——如果函数的最后一步是调用另一个函数，引擎可以复用当前栈帧：

```javascript
// 尾调用形式
function factorial(n, acc = 1) {
    if (n <= 1) return acc;
    return factorial(n - 1, n * acc);  // 尾位置，可以优化
}
```

但实际上，只有Safari的JSC引擎完全实现了TCO。V8基于调试困难等原因，没有实现通用的TCO。

### 8.4 堆上的对象布局

```javascript
let obj = { x: 1, y: "hello", z: true };
```

在V8堆上的布局：

```
┌──────────────────────────┐
│  Map指针                  │  → 指向隐藏类HC，描述对象形状
├──────────────────────────┤
│  Properties指针           │  → 指向溢出属性存储（如果有的话）
├──────────────────────────┤
│  Elements指针             │  → 指向数组元素存储（如果有的话）
├──────────────────────────┤
│  x: Smi(1)               │  ← 内联存储（In-Object Property）
├──────────────────────────┤
│  y: 指针                  │  → 堆上的String对象 "hello"
├──────────────────────────┤
│  z: 指针                  │  → 堆上的Oddball对象 true
└──────────────────────────┘
```

注意：Smi（Small Integer）直接存储在字段中，不需要额外的堆分配。


## 09.数值表示的底层实现

### 9.1 疑惑：为什么 0.1 + 0.2 !== 0.3

这是JavaScript最经典的"坑"之一，但它其实不是JavaScript的bug，而是IEEE 754双精度浮点数的固有特性。

### 9.2 IEEE 754 双精度浮点数

JavaScript的`number`类型使用64位双精度浮点数：

```
 S  EEEEEEEEEEE  FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
[1]  [11 bits]                    [52 bits]
符号   指数                         尾数（mantissa/fraction）

值 = (-1)^S × 2^(E-1023) × 1.F
```

- 符号位：0正1负
- 指数：11位，偏移1023
- 尾数：52位，隐含前导1

**0.1在二进制中是无限循环小数**：

```
0.1 (十进制) = 0.0001100110011001100110011... (二进制，无限循环)
```

存储时只能截取52位，产生精度损失。0.2同理。两个有精度损失的数相加，误差叠加，导致结果不精确。

```javascript
0.1 + 0.2  // 0.30000000000000004
```

### 9.3 V8的Smi优化

**论证**：如果所有数字都用64位浮点数表示，那简单的整数运算（如数组索引）也要用浮点运算，非常浪费。

V8引入了**Smi（Small Integer）**优化：

```
V8中number的两种内部表示：
┌──────────────────┐
│  Smi              │  31位有符号整数（64位平台）
│  范围: -2^30 ~ 2^30-1  │  即 -1073741824 ~ 1073741823
│  直接存储在指针中   │  不需要堆分配
├──────────────────┤
│  HeapNumber        │  64位IEEE 754浮点数
│  分配在堆上         │  需要GC管理
└──────────────────┘
```

**结果**：

```javascript
let a = 42;          // Smi，直接存储在变量槽中，无堆分配
let b = 42.5;        // HeapNumber，分配在堆上
let c = 2147483648;  // 超出Smi范围，HeapNumber

// 数组索引通常是Smi，所以数组访问非常快
let arr = [1, 2, 3];
arr[0];  // 索引0是Smi，快速路径
```

### 9.4 BigInt

当需要超出`Number.MAX_SAFE_INTEGER`（2^53 - 1）的整数时，使用`BigInt`：

```javascript
const big = 9007199254740993n;  // BigInt字面量
typeof big;  // "bigint"

// 注意：BigInt和Number不能混合运算
big + 1;     // TypeError!
big + 1n;    // 9007199254740994n

// BigInt没有浮点数精度问题
0n + 0n === 0n;  // true
```

### 9.5 安全整数范围

```javascript
Number.MAX_SAFE_INTEGER;  // 9007199254740991 (2^53 - 1)
Number.MIN_SAFE_INTEGER;  // -9007199254740991

// 超出安全范围的计算不准确
9007199254740992 === 9007199254740993;  // true! 精度丢失

// 检查是否安全
Number.isSafeInteger(9007199254740991);  // true
Number.isSafeInteger(9007199254740992);  // false
```


## 10.字符串的内部存储

### 10.1 V8的字符串类型

V8内部有多种字符串表示，根据内容和使用方式自动选择：

```
String（V8内部类型体系）
├── SeqString（连续存储）
│   ├── SeqOneByteString    // Latin-1字符，每字符1字节
│   └── SeqTwoByteString    // UTF-16字符，每字符2字节
├── ConsString（拼接字符串）
│   // 不真正拼接，只存两个指针
│   // "hello" + "world" → ConsString(→"hello", →"world")
├── SlicedString（切片字符串）
│   // str.substring(2, 5) → SlicedString(→str, offset=2, length=3)
├── ThinString（去重后的引用）
│   // 指向内部化（internalized）字符串
└── ExternalString（外部字符串）
    // 内容存在V8堆外
```

### 10.2 ConsString的妙用

```javascript
let result = "";
for (let i = 0; i < 10000; i++) {
    result += "x";  // 每次拼接会创建ConsString
}
```

如果每次拼接都要复制整个字符串，复杂度是O(n²)。V8通过ConsString将拼接变成O(1)：

```
第1次: "x"
第2次: ConsString(→"x", →"x")
第3次: ConsString(→ConsString(→"x", →"x"), →"x")
...
```

ConsString形成一棵树，只在需要时（如输出、比较）才展平。展平时一次性完成，摊销后仍然高效。

### 10.3 字符串内部化（Internalization）

字符串字面量和属性名会被"内部化"——存入全局字符串表，相同内容的字符串共享同一份内存：

```javascript
let a = "hello";
let b = "hello";
// a 和 b 指向堆中同一个字符串对象（内部化后）

// 内部化字符串可以用指针比较代替字符比较
// 这就是为什么属性查找如此快——属性名是内部化的，比较是O(1)
```


## 11.对象存储模型

### 11.1 对象的属性分类

V8将对象的属性分为三类：

```javascript
let obj = {};
obj.name = "Alice";    // 命名属性（Named Property）
obj[0] = "first";      // 索引属性（Indexed Property / Element）
obj[Symbol.iterator] = function() {}; // Symbol属性
```

**索引属性和命名属性分别存储**：

```
obj的内存布局:
┌─────────────────┐
│  Map             │ → 隐藏类
├─────────────────┤
│  Properties      │ → 命名属性存储
├─────────────────┤
│  Elements        │ → 索引属性存储
├─────────────────┤
│  name: "Alice"   │ ← In-Object Property
└─────────────────┘
```

### 11.2 快属性与慢属性

命名属性有两种存储模式：

**快属性（Fast Properties）**：

```javascript
// 属性少于一定数量（通常10-20个），使用线性存储
let obj = { a: 1, b: 2, c: 3 };
// 属性存储在对象内部（In-Object）或Properties数组中
// 通过隐藏类记录的offset直接访问，O(1)
```

**慢属性（Dictionary Mode）**：

```javascript
// 以下操作会导致对象退化到字典模式
let obj = {};
for (let i = 0; i < 100; i++) {
    obj['prop' + i] = i;  // 大量动态属性
}

// 或者
delete obj.someProperty;  // delete操作通常触发字典模式

// 字典模式使用哈希表存储
// 查找变成O(1)平均但常数更大，且无法被TurboFan高效优化
```

### 11.3 数组的元素类型

V8根据数组内容选择不同的存储策略：

```javascript
// PACKED_SMI_ELEMENTS — 最高效
let a = [1, 2, 3, 4, 5];

// PACKED_DOUBLE_ELEMENTS — 高效
let b = [1.1, 2.2, 3.3];

// PACKED_ELEMENTS — 通用
let c = [1, "two", true];

// HOLEY_SMI_ELEMENTS — 有空洞的整数数组
let d = [1, , 3];  // 空洞！

// DICTIONARY_ELEMENTS — 稀疏数组
let e = [];
e[0] = 1;
e[10000] = 2;  // 巨大空洞，退化为字典模式
```

元素类型的**退化方向**（单向，不可逆）：

```
PACKED_SMI_ELEMENTS
      ↓ 加入浮点数
PACKED_DOUBLE_ELEMENTS
      ↓ 加入非数值
PACKED_ELEMENTS
      ↓ 出现空洞
HOLEY_ELEMENTS
```

一旦数组退化，不会自动恢复到更优的类型。

### 11.4 编码建议

```javascript
// 好：固定形状的对象
class Point {
    constructor(x, y) {
        this.x = x;  // 总是先x
        this.y = y;  // 再y
    }
}

// 好：紧凑的数组
const arr = new Array(1000);
for (let i = 0; i < 1000; i++) {
    arr[i] = i;  // 无空洞，纯整数
}

// 坏：删除属性
delete obj.prop;  // 触发字典模式

// 坏：稀疏数组
const sparse = [];
sparse[999999] = 1;  // 字典模式

// 坏：类型混合的数组
const mixed = [1, "two", 3];  // PACKED_ELEMENTS

// 替代delete
obj.prop = undefined;  // 不改变隐藏类
```


## 12.引擎优化的编码启示

### 12.1 让隐藏类保持稳定

```javascript
// ✅ 好：构造函数中初始化所有属性
class User {
    constructor(name, age) {
        this.name = name;
        this.age = age;
        this.email = null;  // 即使暂时没值也要初始化
    }
}

// ❌ 差：动态添加属性
function createUser(name, age) {
    const user = {};
    user.name = name;
    if (age) user.age = age;  // 条件性添加导致不同的HC
    return user;
}
```

### 12.2 让函数保持单态

```javascript
// ✅ 好：总是传入相同类型
function add(a, b) { return a + b; }
add(1, 2);     // number + number
add(3, 4);     // number + number（保持Monomorphic）

// ❌ 差：传入不同类型
add(1, 2);       // number + number
add("a", "b");   // string + string（变成Polymorphic）
add(1n, 2n);     // bigint + bigint（变成Megamorphic）
```

### 12.3 避免去优化

```javascript
// ❌ 会触发去优化的模式
function process(obj) {
    return obj.x + obj.y;
}

// 前1000次传入{x: number, y: number}
// TurboFan按此假设优化
// 然后突然：
process({ x: "hello", y: "world" });  // 去优化！

// ✅ 改进：始终保持类型一致
// 或者使用TypeScript在编译时保证类型
```

### 12.4 利用V8的数组优化

```javascript
// ✅ 预分配数组
const arr = new Array(1000);  // 预分配
for (let i = 0; i < 1000; i++) {
    arr[i] = i;
}

// ❌ 避免创建空洞
const arr2 = [1, 2, 3];
arr2[100] = 4;  // 创建了97个空洞

// ✅ 优先使用TypedArray处理数值
const floats = new Float64Array(1000);
// 固定类型，固定大小，没有类型退化问题
```

### 12.5 try-catch的性能影响

```javascript
// 旧版V8中，try-catch内的代码无法被TurboFan优化
// 现代V8已经大幅改善，但仍有一些注意事项

// ✅ 好：try-catch包裹最小范围
function process(data) {
    const prepared = prepareData(data);  // 热路径在try外
    try {
        return riskyOperation(prepared);
    } catch (e) {
        return fallback(prepared);
    }
}

// ❌ 差：整个函数包在try-catch里
function process(data) {
    try {
        // 大量计算...
        // 这里的代码在早期V8中无法被优化
    } catch (e) {
        // ...
    }
}
```

### 12.6 使用性能分析工具验证

不要靠猜测做优化，用工具验证：

```bash
# 查看V8的优化决策
node --trace-opt --trace-deopt script.js

# 查看内联缓存状态
node --trace-ic script.js

# 查看GC活动
node --trace-gc script.js

# Chrome DevTools
# Performance面板 → 录制 → 查看火焰图
# Memory面板 → 堆快照 → 分析对象分布
```

### 12.7 总结：引擎友好的编码原则

1. **对象形状稳定**：使用构造函数/class，按固定顺序初始化所有属性
2. **类型一致**：函数参数保持相同类型，避免IC退化
3. **数组紧凑**：避免空洞，避免类型混合，优先TypedArray
4. **热路径简洁**：热点函数保持短小，便于内联
5. **避免delete**：用赋值undefined代替
6. **善用工具**：用V8的trace选项和Chrome DevTools做Profile
7. **不要过早优化**：先写正确的代码，用工具发现瓶颈后再针对性优化
