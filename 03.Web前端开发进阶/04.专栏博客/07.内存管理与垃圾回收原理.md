## 01.前言介绍

### 1.1 为什么要关注内存

JavaScript开发者很少需要手动管理内存——GC（垃圾回收器）帮我们做了。但这不意味着可以忽视内存问题：

1. **性能**：GC运行时会暂停JavaScript执行（Stop-The-World），频繁GC会导致卡顿
2. **内存泄漏**：不正确的引用导致对象无法被回收，内存持续增长，最终OOM（Out of Memory）
3. **架构决策**：理解内存模型才能在Map vs Object、数组 vs TypedArray之间做出正确选择

### 1.2 疑惑：自动GC还需要我操心什么

**答疑**：GC只能回收**不可达**的对象。如果一个对象已经没用了，但仍然被某个变量或数据结构引用着，GC无法回收它——这就是内存泄漏。

```javascript
// 经典泄漏：全局数组无限增长
const cache = [];
function processRequest(data) {
    cache.push(data);  // 只进不出
    // cache永远不会被GC回收
}
```


## 02.JavaScript内存模型

### 2.1 栈内存与堆内存

```
┌──────────────────────────────────────────┐
│                栈内存（Stack）              │
│  - 原始类型的值                             │
│  - 函数调用帧                              │
│  - 变量引用（指针）                         │
│  - 大小固定，自动管理（LIFO）               │
│  - 访问速度极快                             │
├──────────────────────────────────────────┤
│                堆内存（Heap）               │
│  - 对象、数组、函数等引用类型                │
│  - 闭包中的变量                             │
│  - 大小动态，由GC管理                       │
│  - 访问速度较慢（需要指针间接寻址）           │
└──────────────────────────────────────────┘
```

### 2.2 值的存储方式

```javascript
// 原始类型：值直接存在栈上（或Smi编码在指针中）
let a = 42;       // 栈上：a → 42
let b = "hello";  // 栈上：b → 指针 → 堆上的字符串对象

// 引用类型：引用在栈上，对象在堆上
let obj = { x: 1, y: 2 };
// 栈上：obj → 指针
// 堆上：{ x: 1, y: 2 }

// 赋值的区别
let c = a;    // 复制值42到c
let d = obj;  // 复制指针到d（obj和d指向同一个堆对象）
```


## 03.V8的分代堆结构

### 3.1 分代假说

V8的GC基于一个关键观察——**分代假说（Generational Hypothesis）**：

> 大多数对象很快就会变得不可达（短命对象），而存活较长的对象往往会继续存活（长命对象）。

基于这个假说，V8将堆分为**新生代**和**老生代**，使用不同的GC策略。

### 3.2 堆内存布局

```
V8堆内存:
┌────────────────────────────────────────────────┐
│  新生代（Young Generation）                      │
│  ┌─────────────────┬─────────────────┐          │
│  │  Semi-Space A    │  Semi-Space B    │          │
│  │  (From/To)      │  (From/To)      │          │
│  │  各1-8 MB       │                 │          │
│  └─────────────────┴─────────────────┘          │
│  新对象分配在这里，GC频繁但快速                    │
├────────────────────────────────────────────────┤
│  老生代（Old Generation）                        │
│  ┌─────────────────────────────────────┐        │
│  │  Old Space（普通对象）                │        │
│  │  数百MB到数GB                        │        │
│  ├─────────────────────────────────────┤        │
│  │  Large Object Space（大对象）         │        │
│  │  单个对象超过某阈值直接分配在这里       │        │
│  ├─────────────────────────────────────┤        │
│  │  Code Space（编译后的代码）            │        │
│  ├─────────────────────────────────────┤        │
│  │  Map Space（隐藏类/Map对象）          │        │
│  └─────────────────────────────────────┘        │
│  存活久的对象在这里，GC不频繁但耗时              │
└────────────────────────────────────────────────┘
```

### 3.3 对象晋升

新生代中经过两次GC仍然存活的对象会被**晋升（Promote）**到老生代：

```
新对象 → 新生代Semi-Space A
          ↓ 第一次GC存活
        Semi-Space B
          ↓ 第二次GC仍存活
        老生代Old Space
```


## 04.新生代回收：Scavenge算法

### 4.1 Scavenge（Cheney算法）

新生代使用半空间复制算法：

```
GC前:
From空间: [A] [B] [C] [D] [E]     To空间: [空]
  A被root引用
  B被A引用
  C没有引用（垃圾）
  D被root引用
  E没有引用（垃圾）

GC过程:
1. 从root出发，标记可达对象：A, B, D
2. 将可达对象复制到To空间
3. 更新所有指针

GC后:
From空间: [空]（整体释放）    To空间: [A] [B] [D]
                              对象紧凑排列，无碎片

角色互换:
新的From = 原To     新的To = 原From
```

### 4.2 Scavenge的特点

- **速度快**：只需处理存活对象（新生代中大多数对象是短命的，存活率低）
- **空间浪费**：始终有一半空间是空的（空间换时间）
- **天然紧凑**：复制后对象连续排列，没有内存碎片

### 4.3 写屏障（Write Barrier）

如果老生代对象引用了新生代对象，GC怎么知道？

```javascript
// 老生代对象
const longLived = { data: null };  // 已晋升到老生代

// 新生代对象
const shortLived = { value: 42 };  // 在新生代

// 老生代引用新生代
longLived.data = shortLived;  // ← 触发写屏障！
```

V8使用**写屏障（Write Barrier）**：每当老生代对象写入一个新的引用时，将该引用记录在一个**记忆集（Remembered Set）**中。新生代GC时，除了root，还要检查记忆集中的引用。


## 05.老生代回收：Mark-Sweep与Mark-Compact

### 5.1 Mark-Sweep（标记清除）

```
Mark阶段:
  从root出发，递归遍历所有可达对象，标记为"活"
  
  root → A → B → D
              → E
  C和F没有被标记（垃圾）

Sweep阶段:
  遍历整个堆，回收未标记的对象空间

  [A] [空] [B] [空] [D] [E] [空]
       ↑ C被回收      ↑ F被回收
```

**问题**：Mark-Sweep后产生**内存碎片**——空闲空间不连续，可能无法分配大对象。

### 5.2 Mark-Compact（标记整理）

```
Compact阶段（在Mark-Sweep后）:
  将存活对象向一端移动，消除碎片

  Before: [A] [空] [B] [空] [D] [E] [空]
  After:  [A] [B] [D] [E] [空闲空间........]
```

Mark-Compact解决了碎片问题，但移动对象需要更新所有指针，代价更大。V8会根据碎片程度决定是否执行Compact。

### 5.3 三色标记法

V8使用**三色标记法（Tri-color Marking）**来实现增量标记：

```
白色：尚未访问（可能是垃圾）
灰色：已发现但子引用未完全处理
黑色：已完全处理（确定存活）

初始：所有对象为白色
      ┌─── root引用的对象变为灰色

标记过程：
  while (灰色集合非空) {
    取出一个灰色对象
    将它的所有白色子引用变为灰色
    将它自身变为黑色
  }

结束：白色对象都是垃圾
```

三色标记法的优势是可以**暂停和恢复**——灰色集合记录了中间状态。


## 06.增量标记与并发回收

### 6.1 疑惑：GC会不会造成页面卡顿

**答疑**：早期的V8 GC确实会暂停所有JavaScript执行（Stop-The-World），对于大型应用可能造成几十到几百毫秒的卡顿。

**论证**：V8团队为此开发了多种策略来减少暂停时间。

### 6.2 增量标记（Incremental Marking）

```
传统方式（全停顿）:
JS执行 ─────────│ GC（200ms）│────────── JS执行

增量标记（分片）:
JS ──│GC 5ms│── JS ──│GC 5ms│── JS ──│GC 5ms│── ... ──│完成│── JS
     每次只标记一部分对象，然后让出控制权
```

### 6.3 并发标记（Concurrent Marking）

```
主线程:  JS执行 ─────────────────────── JS执行
辅助线程: ────── 标记阶段 ──────────────

标记在后台线程完成，不暂停主线程JS执行
（但最后的原子暂停阶段仍然需要Stop-The-World）
```

### 6.4 并行清除（Parallel Sweeping）

```
主线程:  JS执行 ───────────────────
辅助线程1: ──── 清除区域A ────
辅助线程2: ──── 清除区域B ────
辅助线程3: ──── 清除区域C ────
```

### 6.5 V8 GC策略总结

| 代 | 算法 | 暂停时间 | 触发条件 |
|---|------|---------|---------|
| 新生代 | Scavenge（复制） | ~1-5ms | 半空间满 |
| 老生代（标记） | 增量 + 并发三色标记 | ~几ms | 老生代空间不足 |
| 老生代（清除） | 并行清除 | ~0ms（后台） | 标记完成后 |
| 老生代（整理） | Mark-Compact | ~10ms | 碎片严重时 |


## 07.内存泄漏的常见模式

### 7.1 意外的全局变量

```javascript
function foo() {
    // 非严格模式下，忘记var/let/const会创建全局变量
    leakedVar = "I'm global now!";
    
    // this指向window，也会创建全局属性
    this.anotherLeak = "oops";
}
foo();

// 修复：使用严格模式
"use strict";
function bar() {
    leakedVar = "error";  // ReferenceError!
}
```

### 7.2 遗忘的定时器

```javascript
// 泄漏：定时器引用了闭包中的大对象
function setup() {
    const hugeData = new Array(1000000).fill('x');
    
    setInterval(() => {
        // 即使这个回调不再需要hugeData
        // 只要定时器存在，hugeData就不会被GC
        doSomething();
    }, 1000);
}

// 修复：保存引用，适时清除
function setup() {
    const hugeData = new Array(1000000).fill('x');
    const timer = setInterval(() => {
        doSomething();
    }, 1000);
    
    return () => clearInterval(timer);  // 返回清理函数
}
const cleanup = setup();
// 不需要时
cleanup();
```

### 7.3 DOM引用泄漏

```javascript
// 泄漏：DOM元素被删除但JS仍持有引用
const elements = {};

function addButton() {
    const btn = document.createElement('button');
    btn.id = 'myBtn';
    document.body.appendChild(btn);
    elements.myBtn = btn;  // JS引用
}

function removeButton() {
    document.body.removeChild(document.getElementById('myBtn'));
    // DOM树中删除了，但elements.myBtn仍然引用着
    // 按钮及其关联的事件监听器都无法被GC
}

// 修复
function removeButton() {
    document.body.removeChild(document.getElementById('myBtn'));
    delete elements.myBtn;  // 清除JS引用
}
```

### 7.4 闭包泄漏

```javascript
// 泄漏：闭包无意中持有大对象
function outer() {
    const largeData = getSomeLargeData();
    const smallData = processData(largeData);
    
    return function inner() {
        // inner只用了smallData
        // 但V8可能将largeData也放入Context
        // （取决于是否有eval等动态访问）
        return smallData;
    };
}

// 更安全的写法
function outer() {
    const largeData = getSomeLargeData();
    const smallData = processData(largeData);
    // largeData不再被引用后，离开作用域即可被GC
    
    return createInner(smallData);
}

function createInner(data) {
    return function() { return data; };
}
```

### 7.5 事件监听器泄漏

```javascript
// 泄漏：组件销毁时未移除事件监听
class Component {
    constructor() {
        this.data = new Array(10000).fill('x');
        this.handleResize = () => {
            console.log(this.data.length);
        };
        window.addEventListener('resize', this.handleResize);
    }
    
    destroy() {
        // 必须移除，否则this（及this.data）永远不会被GC
        window.removeEventListener('resize', this.handleResize);
    }
}
```

### 7.6 Map/Set中的引用

```javascript
// 泄漏：Map的key是对象引用
const cache = new Map();

function processNode(node) {
    const result = heavyComputation(node);
    cache.set(node, result);  // 即使node从DOM中移除
    return result;             // cache仍然引用它
}

// 修复：使用WeakMap
const cache = new WeakMap();
function processNode(node) {
    if (cache.has(node)) return cache.get(node);
    const result = heavyComputation(node);
    cache.set(node, result);  // node被GC时，entry自动消失
    return result;
}
```


## 08.WeakRef与FinalizationRegistry

### 8.1 弱引用（WeakRef）

```javascript
// ES2021引入
let target = { data: "important" };
const weakRef = new WeakRef(target);

// 获取引用的对象
weakRef.deref();  // { data: "important" }

// 如果target被GC
target = null;
// 下一次GC后
weakRef.deref();  // undefined（对象已被回收）
```

### 8.2 使用场景：缓存

```javascript
class ImageCache {
    #cache = new Map();
    
    get(url) {
        const ref = this.#cache.get(url);
        if (ref) {
            const img = ref.deref();
            if (img) return img;  // 缓存命中
            this.#cache.delete(url);  // 已被GC，清理entry
        }
        return null;  // 缓存未命中
    }
    
    set(url, img) {
        this.#cache.set(url, new WeakRef(img));
    }
}
```

### 8.3 FinalizationRegistry

```javascript
// 对象被GC时收到通知
const registry = new FinalizationRegistry((heldValue) => {
    console.log(`Object with key "${heldValue}" was garbage collected`);
    // 可以在这里做清理工作
});

let obj = { data: "test" };
registry.register(obj, "my-key");  // 注册

obj = null;  // 不再引用
// 某次GC后，控制台输出：Object with key "my-key" was garbage collected
```

### 8.4 注意事项

```javascript
// ⚠️ WeakRef和FinalizationRegistry的回调时机不确定
// 不要依赖它们做关键逻辑

// ⚠️ deref()返回的引用会临时强引用对象
// 如果保存了这个引用，对象就不会被GC
const ref = new WeakRef(obj);
const strong = ref.deref();  // strong是强引用！
// 要及时让strong离开作用域
```


## 09.内存分析工具实战

### 9.1 Chrome DevTools Memory面板

```
三种分析方式:

1. Heap Snapshot（堆快照）
   - 拍摄当前堆的完整快照
   - 查看对象分布、对象间的引用关系
   - 对比两个快照找出泄漏

2. Allocation instrumentation on timeline（时间线分配）
   - 记录一段时间内的内存分配
   - 可以看到哪些对象被分配、哪些被GC

3. Allocation sampling（分配采样）
   - 低开销的采样方式
   - 适合在生产环境中使用
```

### 9.2 堆快照分析方法

```
查找内存泄漏的步骤:

1. 打开Chrome DevTools → Memory面板
2. 执行操作前拍摄快照A
3. 执行可能泄漏的操作（如打开/关闭弹窗）
4. 手动触发GC（点击垃圾桶图标）
5. 拍摄快照B
6. 选择快照B，对比模式选择"Objects allocated between snapshot A and B"
7. 查看哪些对象没有被回收

关键指标:
- Shallow Size：对象自身占用的内存
- Retained Size：对象及其引用链占用的总内存（如果该对象被GC，能释放多少）
```

```javascript
// 普通数组：每个元素可以是任何类型
const arr = [1, 2, 3];

```

## 11.大规模应用的内存优化策略

### 11.1 对象池模式

```javascript
class ObjectPool {
    constructor(createFn, resetFn, initialSize = 10) {
        this.createFn = createFn;
        this.resetFn = resetFn;
        this.pool = [];
        
        for (let i = 0; i < initialSize; i++) {
            this.pool.push(createFn());
        }
    }
    
    acquire() {
        return this.pool.length > 0 
            ? this.pool.pop() 
            : this.createFn();
    }
    
    release(obj) {
        this.resetFn(obj);
        this.pool.push(obj);
    }
}

// 使用
const particlePool = new ObjectPool(
    () => ({ x: 0, y: 0, vx: 0, vy: 0, active: false }),
    (p) => { p.x = 0; p.y = 0; p.vx = 0; p.vy = 0; p.active = false; }
);

const p = particlePool.acquire();
p.x = 100; p.y = 200; p.active = true;
// 使用完毕
particlePool.release(p);  // 回收复用，避免频繁GC
```

### 11.2 结构数组（Structure of Arrays）

```javascript
// 面向对象风格（Array of Structures）
// 每个粒子是一个对象，1000个粒子 = 1000个堆对象
const particles = [];
for (let i = 0; i < 1000; i++) {
    particles.push({ x: 0, y: 0, vx: 0, vy: 0 });
}

// 数据导向风格（Structure of Arrays）
// 4个TypedArray，0个额外堆对象
const particleData = {
    x:  new Float32Array(1000),
    y:  new Float32Array(1000),
    vx: new Float32Array(1000),
    vy: new Float32Array(1000)
};

// SoA对缓存更友好，GC压力为零
// 更新所有粒子的x坐标：
for (let i = 0; i < 1000; i++) {
    particleData.x[i] += particleData.vx[i];
}
```

### 11.3 字符串优化

```javascript
// 避免大量小字符串拼接
// 差：每次拼接可能创建新字符串
let result = "";
for (let i = 0; i < 10000; i++) {
    result += items[i] + ",";
}

// 好：用数组join
const parts = [];
for (let i = 0; i < 10000; i++) {
    parts.push(items[i]);
}
const result = parts.join(",");
```

### 11.4 定期清理策略

```javascript
// LRU缓存——有上限的缓存
class LRUCache {
    constructor(maxSize) {
        this.maxSize = maxSize;
        this.cache = new Map();
    }
    
    get(key) {
        if (!this.cache.has(key)) return undefined;
        const value = this.cache.get(key);
        // 移到最后（最近使用）
        this.cache.delete(key);
        this.cache.set(key, value);
        return value;
    }
    
    set(key, value) {
        if (this.cache.has(key)) this.cache.delete(key);
        this.cache.set(key, value);
        
        if (this.cache.size > this.maxSize) {
            // 删除最早的（第一个）
            const oldest = this.cache.keys().next().value;
            this.cache.delete(oldest);
        }
    }
}
```

### 12.3 流式处理避免内存爆炸


### 12.4 总结：内存管理的核心要点

1. **分代回收**：新生代Scavenge（快速复制），老生代Mark-Sweep/Compact
2. **增量+并发**：现代V8的GC暂停时间已经很短（几毫秒级）
3. **常见泄漏**：全局变量、遗忘的定时器/监听器、DOM引用、闭包
4. **WeakMap/WeakRef**：自动跟随GC的弱引用方案
5. **TypedArray**：零GC压力的数值存储
6. **对象池**：高频创建销毁场景的优化利器
7. **工具驱动**：用DevTools和heap snapshot定位问题
