## 1.线程异常由来

### 1.1 为何设计异常

线程异常机制的根本目的是**在非正常执行路径上安全地传递错误信息并恢复控制流**。

| 动机 | 说明 |
|------|------|
| **隔离错误传播** | 线程是独立执行单元，一个线程的异常不应默默地让整个进程崩溃或数据损坏 |
| **资源安全释放** | 异常发生时需保证锁、文件句柄、内存等资源被正确释放（栈展开/finally） |
| **错误可观测性** | 没有异常机制，错误只能通过返回值传递，容易被忽略 |
| **线程间错误传递** | 子线程的错误需要一种机制传回给父线程/调用方（`Future.get()` 抛异常、Go 的 `recover` 等） |
| **程序健壮性** | 避免未处理错误导致线程"静默死亡"，外部无法感知 |

### 1.2 异常设计哲学

**核心设计哲学**：线程异常 = **控制流转移** + **错误信息封装** + **资源清理保证**

## 2.异常如何引起

### 2.1 如何引起分析

线程异常如何引起的

```
┌─────────────────────────────────────────────────┐
│              线程异常触发源                        │
├──────────────┬──────────────────────────────────┤
│   硬件/OS层   │  CPU 除零、非法内存访问(SIGSEGV)、  │
│              │  栈溢出、硬件中断                    │
├──────────────┼──────────────────────────────────┤
│   运行时层    │  空指针解引用、数组越界、类型转换失败、│
│              │  OOM、断言失败、死锁检测              │
├──────────────┼──────────────────────────────────┤
│   应用层      │  业务逻辑 throw/raise、线程取消/     │
│              │  中断(interrupt)、超时               │
├──────────────┼──────────────────────────────────┤
│   线程交互层   │  线程池任务异常、Future 执行异常、   │
│              │  Channel 关闭、锁获取失败             │
└──────────────┴──────────────────────────────────┘
```

**关键区别**：

- **同步异常**：由当前指令直接触发（除零、空指针），可预测
- **异步异常**：由外部事件触发（线程中断 `Thread.interrupt()`、信号 `SIGTERM`），不可预测
- **线程特有问题**：未捕获异常导致线程静默终止，父线程无法感知（最危险的场景）
