## 1.多种引用背景

### 1.1 根本矛盾

程序的核心矛盾之一：**对象的"使用权"与"生命周期"的耦合问题**。

```
最朴素的模型：
  我持有一个指针 → 我能用这个对象 → 这个对象必须活着 → 谁来保证它活着？

三个不可能同时满足的需求：
  ① 自动内存管理（不想手动free）
  ② 灵活的对象共享（多处引用同一对象）
  ③ 及时的内存回收（不用的对象立刻释放）
```

只有一种引用类型时，②和③严重冲突。

**内存管理面临的核心矛盾：**

1. **可达性与生命周期的不匹配**：对象的逻辑生命周期与其在内存中的可达性并不总是一致
2. **循环引用的困境**：相互引用的对象群体可能永远无法被回收
3. **性能与安全的权衡**：安全的内存管理往往意味着性能开销

### 1.2 单一引用困境

**困境一：循环引用 → 内存泄漏**

```
A → B → A（引用计数永远≥1，永远不会回收）

真实场景：
  - 父子UI组件互相持有
  - 观察者模式中Subject持有Observer、Observer持有Subject
  - 缓存系统：缓存引用对象、对象反向查缓存
```

**困境二：缓存膨胀 → OOM**

```
缓存持有强引用 → 对象永远不会被GC → 内存无限增长

真实场景：
  - 图片缓存：加载过的图片全部保留在内存
  - DNS缓存：解析过的域名永不释放
  - 数据库连接池的元数据缓存
```

**困境三：观察者泄漏 → 隐式内存泄漏**

```
EventBus.register(listener)  // 强引用
// listener的拥有者已经销毁了
// 但EventBus还握着强引用 → listener无法回收

Android经典Bug：Activity注册监听后未反注册 → Activity泄漏（几十MB/个）
```

**困境四：临时关联 vs 所有权**

```
我想"知道"一个对象存不存在，但不想"拥有"它。单一引用模型下无法表达这种语义。
```

### 1.3 引用本质需求

需要一种机制让程序员能精确表达：**"我和这个对象的关系强度"**。

```
强关系：我拥有它，它必须活着      → 强引用
弱关系：我认识它，它死了我接受    → 弱引用
缓存关系：内存够就留着，不够就扔  → 软引用
纯通知：它被回收时告诉我一声      → 虚引用
```

## 2.设计引用哲学

### 2.1 分级表达

核心哲学：所有权语义的分级表达。类比现实世界的物品关系：

```
强引用 = 房产证    你拥有这栋房子，只要证在，房子不能拆
弱引用 = 知道地址  你知道那里有栋房子，但房子拆了你也没办法
软引用 = 租约      正常情况你能住，但房东急需资金时可以收回
虚引用 = 拆迁通知  你不能住（不能访问），但房子拆时你会收到通知
```

从理论角度看，引用类型可以被理解为一个连续的强度谱系，从最强的"必须保持"到最弱的"可有可无"：

**引用强度谱系：**

```
强引用 ───────→ 软引用 ───────→ 弱引用 ───────→ 虚引用
  ↑             ↑               ↑              ↑
阻止回收      内存压力时       不阻止回收        回收通知
必须存在       可以回收         可能消失        已经消失
```

### 2.2 设计原则

**原则一：默认安全，显式降级**

```
强引用是默认行为（最安全），弱化引用需要程序员显式声明。
→ 防止新手误用弱引用导致悬空访问
```

**原则二：GC可介入性**

```
引用强度 = 程序员告诉GC的"回收优先级"
强引用：GC绝不能碰
软引用：GC在OOM前可以碰
弱引用：GC任何时候都能碰
虚引用：GC已经碰了，只是通知你
```

**原则三：关注点分离**

```
"使用对象"和"管理对象生命周期"是两个独立关注点。
多种引用让程序员可以只参与使用，而将生命周期决策委托给运行时。
```

## 3.引用理论模型

### 3.1 可达性模型

GC判断对象是否存活的核心模型：

```
         GC Root
           │
      ┌────┴────┐
      │         │
   强引用     强引用
      │         │
   Obj A     Obj B ←─── 弱引用 ─── Obj C
      │
   软引用
      │
   Obj D ←─── 虚引用 ─── PhantomQueue
```

**可达性层次（Java定义，最经典）：**

```
Strongly Reachable  > Softly Reachable  > Weakly Reachable  > Phantom Reachable > Unreachable
    强可达                软可达              弱可达              虚可达            不可达
  │ 绝不回收 │         │ OOM前回收 │       │ 下次GC回收 │      │ 已终结待清理 │   │ 回收 │
```

**关键规则：对象的可达性 = 从GC Root到该对象的所有路径中，最强的那条路径决定。**

```
如果存在任何一条强引用路径 → 强可达（不回收）
所有路径都最多到软引用    → 软可达（OOM前可回收）
所有路径都最多到弱引用    → 弱可达（随时可回收）
只剩虚引用               → 虚可达（已在终结队列中）
```

### 3.2 偏序关系

引用强度的偏序关系

```
Strong > Soft > Weak > Phantom > None

这是一个全序关系，GC按此顺序做回收决策：
1. 标记所有强可达对象 → 保留
2. 内存不足？标记软可达对象 → 可回收
3. 标记弱可达对象 → 回收
4. 虚可达对象 → 加入ReferenceQueue，等待清理
5. 不可达 → 直接回收
```

### 3.3 引用计数

引用计数 vs 追踪式GC中的引用语义

```
引用计数模型（C++/OC/Swift/Python）：
  强引用 = refcount + 1
  弱引用 = weak_count + 1, 不增加refcount
  refcount == 0 → 释放对象
  weak_count == 0 → 释放控制块

追踪式GC模型（Java/C#/Go/JS）：
  强引用 = GC遍历时跟踪的边
  弱引用 = GC遍历时不跟踪的边
  不可达 → 回收
```

### 3.4 设计引用维度


```
维度一：所有权语义
  ├── 独占所有权（unique_ptr）
  ├── 共享所有权（shared_ptr / 强引用）
  └── 无所有权（weak_ptr / 弱引用 / 裸指针）

维度二：对GC的约束力
  ├── 禁止回收（强引用）
  ├── 条件回收（软引用：内存压力时）
  ├── 允许回收（弱引用：任意GC周期）
  └── 已回收通知（虚引用）

维度三：可访问性
  ├── 可直接访问对象（强/软/弱引用）
  └── 不可访问对象（虚引用：get()始终返回null）

维度四：回收通知
  ├── 无通知（强引用、普通弱引用）
  └── 有通知（虚引用 + ReferenceQueue、C++ weak_ptr::expired()）

维度五：内存回收时机
  ├── 确定性回收（C++：引用计数归零立即析构）
  └── 非确定性回收（Java/Go/JS：GC周期决定）

维度六：线程安全性
  ├── 原子引用计数（C++ shared_ptr 控制块原子操作）
  ├── GC安全点（Java：STW时处理引用）
  └── 无保证（裸指针）
```

## 4.强引用探索

强引用的设计基于"所有权"的概念。当一个对象被强引用指向时，垃圾回收器认为这个对象是"必需的"，不会对其进行回收。

这种设计确保了程序的基本正确性，避免了对象在使用过程中被意外回收。

### 4.1 强引用场景

```java
// Java中的强引用示例
public class StrongReferenceExample {

    private Object strongRef;  // 强引用字段
    public void demonstrateStrongReference() {
        Object obj = new Object();  // obj是强引用
        strongRef = obj;           // strongRef也是强引用
        // 只要存在任何一个强引用指向对象，对象就不会被回收
        obj = null;  // 即使obj被置空，strongRef仍然保持对象存活
        System.gc();  // 强制垃圾回收，但对象不会被回收
        // 只有当所有强引用都被清除时，对象才可能被回收
        strongRef = null;  // 现在对象可能被回收了
    }
}
```

**强引用的内存管理语义：**

- **生命周期绑定**：对象的生命周期与强引用的生命周期紧密绑定
- **传递性**：通过强引用可达的所有对象都不会被回收
- **确定性**：强引用的行为是完全可预测的

### 4.2 强引用设计


### 4.3 强引用原理

**在引用计数模型中（C++/OC/Swift）：**

```
创建强引用 → atomic_fetch_add(&refcount, 1)
销毁强引用 → atomic_fetch_sub(&refcount, 1)
              if (refcount == 0) → 析构对象 + 释放内存

// C++ shared_ptr 控制块结构
struct ControlBlock {
  std::atomic<int> strong_count;  // 强引用计数
  std::atomic<int> weak_count;    // 弱引用计数
  T* ptr;                         // 指向管理的对象
  Deleter deleter;                // 自定义删除器
};
```

**在追踪式GC中（Java/Go/JS）：**

```
强引用不需要特殊数据结构，就是普通的对象引用。
GC从Root出发做可达性分析，能到达的 = 强可达 = 不回收。

// 就是最普通的赋值
Object obj = new Object();  // obj就是强引用
```


### 4.4 强引用问题

```
问题：过于强势，导致"该死的对象死不了"

场景：
  Map<String, Object> cache = new HashMap<>();
  cache.put("big_image", loadImage());  // 强引用
  // 即使没有任何业务代码在用这张图，GC也不敢回收
  // 因为cache→"big_image"→Image 是一条强可达路径
```

## 5.软引用探索

软引用是一种"内存敏感"的引用类型，它在内存管理中扮演着缓存的角色。

它允许垃圾回收器在内存不足时回收被软引用指向的对象，但在内存充足时会尽量保持这些对象。这种设计特别适合实现内存敏感的缓存系统。

### 5.1 软引用场景

```java
// 图片缓存：内存够就缓存，不够就自动释放
Map<String, SoftReference<Bitmap>> imageCache = new HashMap<>();

Bitmap get(String key) {
  SoftReference<Bitmap> ref = imageCache.get(key);
  if (ref != null) {
    Bitmap bmp = ref.get();  // 可能返回null（已被GC回收）
    if (bmp != null) return bmp;
  }
  // cache miss，重新加载
  Bitmap bmp = loadFromDisk(key);
  imageCache.put(key, new SoftReference<>(bmp));
  return bmp;
}
```

### 5.2 软引用设计

软引用的回收策略，不同的垃圾回收器对软引用有不同的回收策略：

- **基于内存阈值**：当可用内存低于某个阈值时回收
- **基于时间戳**：结合对象的最后访问时间进行决策
- **基于回收压力**：在垃圾回收压力大时优先回收

为什么C++没有软引用？C++没有GC，引用计数是确定性回收。"内存压力"这个概念在用户态C++中没有标准的感知机制。要实现类似语义，需要自己写LRU缓存 + 内存监控 + 手动淘汰。

### 5.3 软引用原理

**GC决策逻辑：**

```
// JVM内部的软引用回收策略（HotSpot实现）
bool should_clear_soft_ref(SoftReference ref) {
  // 上次访问时间距现在的间隔
  long idle_time = now - ref.timestamp;
  // 剩余可用内存（MB） × 系数
  long threshold = free_heap_mb * SoftRefLRUPolicyMSPerMB;
  
  return idle_time > threshold;
  // 即：空闲堆内存越少，越积极地清除软引用
  // -XX:SoftRefLRUPolicyMSPerMB=1000 (默认)
  // 意味着每MB空闲内存保留1000ms的软引用
}
```

**量化示例：**

```
空闲堆 = 100MB, 系数 = 1000ms/MB
  → 100秒内未被访问的软引用才会被清除

空闲堆 = 10MB, 系数 = 1000ms/MB
  → 10秒内未被访问的就会被清除

空闲堆 ≈ 0MB（即将OOM）
  → 所有软引用全部清除
```

## 6.弱引用探索

### 6.1 弱引用场景

```cpp
// C++: 观察者模式，避免观察者泄漏
class EventBus {
  std::vector<std::weak_ptr<Observer>> observers_;
  
  void Notify() {
    for (auto it = observers_.begin(); it != observers_.end();) {
      if (auto sp = it->lock()) {
        sp->OnEvent();  // 还活着，通知
        ++it;
      } else {
        it = observers_.erase(it);  // 已死，清理
      }
    }
  }
};
```

```java
// Java: WeakHashMap，key被GC后自动移除entry
WeakHashMap<Object, String> map = new WeakHashMap<>();
Object key = new Object();
map.put(key, "value");
key = null;  // 断开强引用
System.gc();
// map.size() → 0，entry自动被清除
```

### 6.2 弱引用设计

解决循环引用

```
不用弱引用：
  Parent ──strong──→ Child
  Child  ──strong──→ Parent
  两者引用计数永远≥1，内存泄漏

用弱引用：
  Parent ──strong──→ Child
  Child  ──weak────→ Parent
  Parent无外部引用时 → strong_count=0 → 析构
  → Child的weak_ptr.lock()返回nullptr
  → Child也无外部引用 → 析构
  → 循环打破
```


**弱引用的内存语义：**

- **非拥有性**：不会延长对象的生命周期
- **即时性**：对象一旦不可达就可能被立即回收
- **不确定性**：无法保证对象在任何时刻都存在

### 6.3 弱引用原理


**引用计数模型（C++ weak_ptr）：**

```
// shared_ptr控制块中有两个计数
struct ControlBlock {
  atomic<int> strong_count;  // shared_ptr数量
  atomic<int> weak_count;    // weak_ptr数量 + (strong_count > 0 ? 1 : 0)
};

// weak_ptr不增加strong_count
weak_ptr<T> wp = sp;  // strong_count不变，weak_count + 1

// 使用前必须"升级"为shared_ptr
shared_ptr<T> sp2 = wp.lock();
if (sp2) {
  // 对象还活着，可以安全使用
} else {
  // 对象已被销毁
}

// 生命周期：
// strong_count → 0 : 析构对象（调用~T()），但控制块还在
// weak_count → 0   : 释放控制块内存
// 这就是为什么weak_ptr能"知道对象死了"——控制块比对象活得久
```

**追踪式GC模型（Java WeakReference）：**

```
// GC标记阶段：不沿弱引用追踪
void mark(Object obj) {
  if (obj.marked) return;
  obj.marked = true;
  for (Reference ref : obj.references) {
    if (ref.type == STRONG || ref.type == SOFT) {
      mark(ref.target);  // 追踪
    }
    // WEAK和PHANTOM：不追踪
  }
}

// 标记完成后：所有仅通过弱引用可达的对象 → 弱可达 → 清除引用
```

### 7.2 C++最精细

C++的引用/指针体系是所有语言中最丰富的：

```
┌───────────────────┬────────────────────────────┬──────────────────┐
│ 类型               │ 语义                        │ 开销              │
├───────────────────┼────────────────────────────┼──────────────────┤
│ T*（裸指针）        │ 无所有权，纯地址            │ 0（无管理）       │
│ T&（引用）          │ 别名，不可为空              │ 0                │
│ unique_ptr<T>     │ 独占所有权，不可拷贝         │ 0（零开销抽象）   │
│ shared_ptr<T>     │ 共享所有权，引用计数         │ 控制块+原子操作   │
│ weak_ptr<T>       │ 非拥有型观察，可检测失效     │ 控制块引用         │
└───────────────────┴────────────────────────────┴──────────────────┘

unique_ptr是C++独有的设计精华：
  → 编译期保证只有一个拥有者
  → 零运行时开销（和裸指针完全一样的机器码）
  → 转移所有权用std::move，语义清晰
```

**shared_ptr + weak_ptr 的内存布局：**

```
shared_ptr<T> sp          weak_ptr<T> wp
    │                          │
    ▼                          ▼
┌──────────────┐          ┌──────────────┐
│  ptr ────────┼────┐     │  ptr ─────┐  │
│  ctrl_block ─┼──┐ │     │  ctrl ──┐ │  │
└──────────────┘  │ │     └─────────┼─┼──┘
                  │ │               │ │
                  ▼ ▼               │ │
              ┌──────────────┐      │ │
              │ strong_cnt=1 │◄─────┘ │
              │ weak_cnt=2   │        │
              │ ptr ─────────┼────┐   │
              │ deleter      │    │   │
              └──────────────┘    │   │
                 控制块            ▼   ▼
                              ┌────────┐
                              │ T对象   │
                              └────────┘

strong_cnt归零 → T对象析构（调用deleter）
weak_cnt归零   → 控制块内存释放
两阶段回收，使weak_ptr能安全检测对象是否存活
```

**PhantomReference的独特价值：**

```java
// 虚引用：比finalize()更安全的资源清理机制
ReferenceQueue<Object> queue = new ReferenceQueue<>();
PhantomReference<HeavyResource> phantom = 
    new PhantomReference<>(resource, queue);

// 清理线程
while (true) {
  Reference<?> ref = queue.remove();  // 阻塞等待
  // 对象已被GC回收，此时安全地清理native资源
  cleanupNativeResource(ref);

// 1. finalize()在GC线程执行，可能导致对象"复活"（this逃逸）
```


## 8.多引用案例

### 8.1 C++案例

```cpp
int main() {
    // 1. 强引用 (shared_ptr) - 引用计数，计数归零时释放
    auto strong = std::make_shared<int>(42);
    // Strong: 42, use_count=1
    std::cout << "Strong: " << *strong << ", use_count=" << strong.use_count() << std::endl;

    // 2. 弱引用 (weak_ptr) - 不增加引用计数，不阻止释放
    std::weak_ptr<int> weak = strong;
    if (auto locked = weak.lock()) {
        // Weak locked: 42
        std::cout << "Weak locked: " << *locked << std::endl;
    }

    // 3. 独占引用 (unique_ptr) - 独占所有权，不可复制
    // 4. 裸指针 (raw pointer) - 无所有权语义，需手动管理
    // 5. weak_ptr 检测对象是否已释放
    return 0;
}
```


### 8.2 Java案例

Java提供了最完整的引用类型体系，这得益于其成熟的垃圾回收机制。

```java
// Java引用类型的完整实现
public class JavaReferenceSystem {
    
    // 1. 强引用 - 默认的引用类型。强引用 (Strong Reference) - 不会被GC回收
    public void strongReferenceDemo() {
        Object obj = new Object();  // 强引用
        List<String> list = new ArrayList<>();  // 强引用
        // 这些对象只有在引用被清除时才可能被回收
    }
    
    // 2. 软引用 - 软引用 (Soft Reference) - 内存不足时才回收
    public void softReferenceDemo() {
        Object obj = new Object();
        SoftReference<Object> softRef = new SoftReference<>(obj);
        obj = null;  // 清除强引用
        
        // 在内存不足时，softRef指向的对象可能被回收
        Object retrieved = softRef.get();  // 可能返回null
    }
    
    // 3. 弱引用 - 弱引用 (Weak Reference) - 随时可能会被回收
    public void weakReferenceDemo() {
        Object obj = new Object();
        WeakReference<Object> weakRef = new WeakReference<>(obj);
        obj = null;  // 清除强引用
        
        System.gc();  // 建议垃圾回收
        Object retrieved = weakRef.get();  // 很可能返回null
    }
    
    // 4. 虚引用 - 回收通知引用
    public void phantomReferenceDemo() {
        ReferenceQueue<Object> queue = new ReferenceQueue<>();
        Object obj = new Object();
        PhantomReference<Object> phantomRef = new PhantomReference<>(obj, queue);
        
        obj = null;  // 清除强引用
        System.gc();  // 触发垃圾回收
        
        // 检查回收通知
        Reference<?> ref = queue.poll();
        if (ref != null) {
            System.out.println("Object has been garbage collected");
        }
    }
}
```
