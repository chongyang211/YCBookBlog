## 1.多种引用背景

### 1.1 根本矛盾

程序的核心矛盾之一：**对象的"使用权"与"生命周期"的耦合问题**。

```
最朴素的模型：
  我持有一个指针 → 我能用这个对象 → 这个对象必须活着 → 谁来保证它活着？

三个不可能同时满足的需求：
  ① 自动内存管理（不想手动free）
  ② 灵活的对象共享（多处引用同一对象）
  ③ 及时的内存回收（不用的对象立刻释放）

只有一种引用类型时，②和③严重冲突。
```

### 1.2 单一引用困境

**困境一：循环引用 → 内存泄漏**

```
A → B → A（引用计数永远≥1，永远不会回收）

真实场景：
  - 父子UI组件互相持有
  - 观察者模式中Subject持有Observer、Observer持有Subject
  - 缓存系统：缓存引用对象、对象反向查缓存
```

**困境二：缓存膨胀 → OOM**

```
缓存持有强引用 → 对象永远不会被GC → 内存无限增长

真实场景：
  - 图片缓存：加载过的图片全部保留在内存
  - DNS缓存：解析过的域名永不释放
  - 数据库连接池的元数据缓存
```

**困境三：观察者泄漏 → 隐式内存泄漏**

```
EventBus.register(listener)  // 强引用
// listener的拥有者已经销毁了
// 但EventBus还握着强引用 → listener无法回收

Android经典Bug：Activity注册监听后未反注册 → Activity泄漏（几十MB/个）
```

**困境四：临时关联 vs 所有权**

```
我想"知道"一个对象存不存在，但不想"拥有"它。单一引用模型下无法表达这种语义。
```

### 1.3 引用本质需求

需要一种机制让程序员能精确表达：**"我和这个对象的关系强度"**。

```
强关系：我拥有它，它必须活着      → 强引用
弱关系：我认识它，它死了我接受    → 弱引用
缓存关系：内存够就留着，不够就扔  → 软引用
纯通知：它被回收时告诉我一声      → 虚引用
```

## 2.设计引用哲学

### 2.1 分级表达

核心哲学：所有权语义的分级表达。类比现实世界的物品关系：

```
强引用 = 房产证    你拥有这栋房子，只要证在，房子不能拆
弱引用 = 知道地址  你知道那里有栋房子，但房子拆了你也没办法
软引用 = 租约      正常情况你能住，但房东急需资金时可以收回
虚引用 = 拆迁通知  你不能住（不能访问），但房子拆时你会收到通知
```

### 2.2 设计原则

**原则一：默认安全，显式降级**

```
强引用是默认行为（最安全），弱化引用需要程序员显式声明。
→ 防止新手误用弱引用导致悬空访问
```

**原则二：GC可介入性**

```
引用强度 = 程序员告诉GC的"回收优先级"
强引用：GC绝不能碰
软引用：GC在OOM前可以碰
弱引用：GC任何时候都能碰
虚引用：GC已经碰了，只是通知你
```

**原则三：关注点分离**

```
"使用对象"和"管理对象生命周期"是两个独立关注点。
多种引用让程序员可以只参与使用，而将生命周期决策委托给运行时。
```

## 3.引用理论模型

### 3.1 可达性模型

GC判断对象是否存活的核心模型：

```
         GC Root
           │
      ┌────┴────┐
      │         │
   强引用     强引用
      │         │
   Obj A     Obj B ←─── 弱引用 ─── Obj C
      │
   软引用
      │
   Obj D ←─── 虚引用 ─── PhantomQueue
```

**可达性层次（Java定义，最经典）：**

```
Strongly Reachable  > Softly Reachable  > Weakly Reachable  > Phantom Reachable > Unreachable
    强可达                软可达              弱可达              虚可达            不可达
  │ 绝不回收 │         │ OOM前回收 │       │ 下次GC回收 │      │ 已终结待清理 │   │ 回收 │
```

**关键规则：对象的可达性 = 从GC Root到该对象的所有路径中，最强的那条路径决定。**

```
如果存在任何一条强引用路径 → 强可达（不回收）
所有路径都最多到软引用    → 软可达（OOM前可回收）
所有路径都最多到弱引用    → 弱可达（随时可回收）
只剩虚引用               → 虚可达（已在终结队列中）
```

### 3.2 偏序关系

引用强度的偏序关系

```
Strong > Soft > Weak > Phantom > None

这是一个全序关系，GC按此顺序做回收决策：
1. 标记所有强可达对象 → 保留
2. 内存不足？标记软可达对象 → 可回收
3. 标记弱可达对象 → 回收
4. 虚可达对象 → 加入ReferenceQueue，等待清理
5. 不可达 → 直接回收
```

### 3.3 引用计数

引用计数 vs 追踪式GC中的引用语义

```
引用计数模型（C++/OC/Swift/Python）：
  强引用 = refcount + 1
  弱引用 = weak_count + 1, 不增加refcount
  refcount == 0 → 释放对象
  weak_count == 0 → 释放控制块

追踪式GC模型（Java/C#/Go/JS）：
  强引用 = GC遍历时跟踪的边
  弱引用 = GC遍历时不跟踪的边
  不可达 → 回收
```

### 3.4 设计引用维度


```
维度一：所有权语义
  ├── 独占所有权（unique_ptr）
  ├── 共享所有权（shared_ptr / 强引用）
  └── 无所有权（weak_ptr / 弱引用 / 裸指针）

维度二：对GC的约束力
  ├── 禁止回收（强引用）
  ├── 条件回收（软引用：内存压力时）
  ├── 允许回收（弱引用：任意GC周期）
  └── 已回收通知（虚引用）

维度三：可访问性
  ├── 可直接访问对象（强/软/弱引用）
  └── 不可访问对象（虚引用：get()始终返回null）

维度四：回收通知
  ├── 无通知（强引用、普通弱引用）
  └── 有通知（虚引用 + ReferenceQueue、C++ weak_ptr::expired()）

维度五：内存回收时机
  ├── 确定性回收（C++：引用计数归零立即析构）
  └── 非确定性回收（Java/Go/JS：GC周期决定）

维度六：线程安全性
  ├── 原子引用计数（C++ shared_ptr 控制块原子操作）
  ├── GC安全点（Java：STW时处理引用）
  └── 无保证（裸指针）
```

### 4.3 强引用原理

**在引用计数模型中（C++/OC/Swift）：**

```
创建强引用 → atomic_fetch_add(&refcount, 1)
销毁强引用 → atomic_fetch_sub(&refcount, 1)
              if (refcount == 0) → 析构对象 + 释放内存

// C++ shared_ptr 控制块结构
struct ControlBlock {
  std::atomic<int> strong_count;  // 强引用计数
  std::atomic<int> weak_count;    // 弱引用计数
  T* ptr;                         // 指向管理的对象
  Deleter deleter;                // 自定义删除器
};
```

**在追踪式GC中（Java/Go/JS）：**

```
强引用不需要特殊数据结构，就是普通的对象引用。
GC从Root出发做可达性分析，能到达的 = 强可达 = 不回收。

// 就是最普通的赋值
Object obj = new Object();  // obj就是强引用
```


### 4.4 强引用问题

```
问题：过于强势，导致"该死的对象死不了"

场景：
  Map<String, Object> cache = new HashMap<>();
  cache.put("big_image", loadImage());  // 强引用
  // 即使没有任何业务代码在用这张图，GC也不敢回收
  // 因为cache→"big_image"→Image 是一条强可达路径
```

## 5.软引用原理

### 5.1 软引用场景


```java
// 图片缓存：内存够就缓存，不够就自动释放
Map<String, SoftReference<Bitmap>> imageCache = new HashMap<>();

Bitmap get(String key) {
  SoftReference<Bitmap> ref = imageCache.get(key);
  if (ref != null) {
    Bitmap bmp = ref.get();  // 可能返回null（已被GC回收）
    if (bmp != null) return bmp;
  }
  // cache miss，重新加载
  Bitmap bmp = loadFromDisk(key);
  imageCache.put(key, new SoftReference<>(bmp));
  return bmp;
}
```

### 5.3 软引用原理

**GC决策逻辑：**

```
// JVM内部的软引用回收策略（HotSpot实现）
bool should_clear_soft_ref(SoftReference ref) {
  // 上次访问时间距现在的间隔
  long idle_time = now - ref.timestamp;
  // 剩余可用内存（MB） × 系数
  long threshold = free_heap_mb * SoftRefLRUPolicyMSPerMB;
  
  return idle_time > threshold;
  // 即：空闲堆内存越少，越积极地清除软引用
  // -XX:SoftRefLRUPolicyMSPerMB=1000 (默认)
  // 意味着每MB空闲内存保留1000ms的软引用
}
```

**量化示例：**

```
空闲堆 = 100MB, 系数 = 1000ms/MB
  → 100秒内未被访问的软引用才会被清除

空闲堆 = 10MB, 系数 = 1000ms/MB
  → 10秒内未被访问的就会被清除

空闲堆 ≈ 0MB（即将OOM）
  → 所有软引用全部清除
```
