## 1.多种引用背景

### 1.1 根本矛盾

程序的核心矛盾之一：**对象的"使用权"与"生命周期"的耦合问题**。

```
最朴素的模型：
  我持有一个指针 → 我能用这个对象 → 这个对象必须活着 → 谁来保证它活着？

三个不可能同时满足的需求：
  ① 自动内存管理（不想手动free）
  ② 灵活的对象共享（多处引用同一对象）
  ③ 及时的内存回收（不用的对象立刻释放）

只有一种引用类型时，②和③严重冲突。
```

### 1.2 单一引用困境

**困境一：循环引用 → 内存泄漏**

```
A → B → A（引用计数永远≥1，永远不会回收）

真实场景：
  - 父子UI组件互相持有
  - 观察者模式中Subject持有Observer、Observer持有Subject
  - 缓存系统：缓存引用对象、对象反向查缓存
```

**困境二：缓存膨胀 → OOM**

```
缓存持有强引用 → 对象永远不会被GC → 内存无限增长

真实场景：
  - 图片缓存：加载过的图片全部保留在内存
  - DNS缓存：解析过的域名永不释放
  - 数据库连接池的元数据缓存
```

**困境三：观察者泄漏 → 隐式内存泄漏**

```
EventBus.register(listener)  // 强引用
// listener的拥有者已经销毁了
// 但EventBus还握着强引用 → listener无法回收

Android经典Bug：Activity注册监听后未反注册 → Activity泄漏（几十MB/个）
```

**困境四：临时关联 vs 所有权**

```
我想"知道"一个对象存不存在，但不想"拥有"它。单一引用模型下无法表达这种语义。
```
