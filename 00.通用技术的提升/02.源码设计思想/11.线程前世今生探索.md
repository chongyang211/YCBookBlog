## 1.线程背景说明

### 1.1 多道程序设计

**从单道批处理到多道程序**。早期计算机是**单道批处理**——CPU 一次只执行一个程序，I/O 时 CPU 完全空闲。

```
时间线：
[====CPU运算====][--------I/O等待--------][====CPU运算====]
                  ↑ CPU 在此完全空闲，利用率极低
```

**多道程序设计**引入了**进程（Process）**概念——操作系统可以同时加载多个程序，CPU 在一个进程等待 I/O 时切换到另一个进程。

### 1.2 进程的代价

进程解决了 CPU 利用率问题，但每个进程拥有**独立的地址空间**：

| 资源 | 开销 |
|------|------|
| 虚拟内存页表 | 每个进程独立，切换需刷新 TLB |
| 文件描述符表 | 独立副本 |
| 信号处理表 | 独立副本 |
| 堆、数据段 | 独立副本 |

进程间通信（IPC）需要经过内核态：管道、消息队列、共享内存、Socket……代价高昂。

**核心矛盾**：很多时候一个程序内部需要并发（如 Web 服务器同时处理多个请求），如果每个并发单元都是独立进程，创建/销毁/切换/通信的开销太大。

### 1.3 线程的诞生

**线程（Thread）= 轻量级进程**，核心思想：

> **共享进程的地址空间和资源，仅独立维护执行流所必需的最小状态。**

```
┌─────────────── 进程 ───────────────┐
│  代码段（共享）                      │
│  数据段/堆（共享）                   │
│  文件描述符（共享）                  │
│  信号处理（共享）                    │
│                                     │
│  ┌─Thread 1─┐  ┌─Thread 2─┐       │
│  │ 栈        │  │ 栈        │       │
│  │ PC寄存器  │  │ PC寄存器  │       │
│  │ 线程局部  │  │ 线程局部  │       │
│  │ 状态      │  │ 状态      │       │
│  └──────────┘  └──────────┘       │
└─────────────────────────────────────┘
```

**线程独有的最小状态**：

- **程序计数器（PC）**：当前执行到哪条指令
- **寄存器集合**：CPU 寄存器的快照
- **栈（Stack）**：函数调用链、局部变量
- **线程局部存储（TLS）**：线程私有数据

## 2.线程设计思想

### 2.1 关注点分离

将"资源容器"和"执行单元"**解耦**：

| 概念 | 职责 |
|------|------|
| **进程** | 资源分配的基本单位（内存、文件、信号等） |
| **线程** | CPU 调度的基本单位（执行流） |

这是一个经典的**正交分解**——资源管理和执行调度是两个独立的维度。

### 2.2 共享vs隔离

共享vs隔离的权衡

```
完全隔离（进程）◄──────────────────►完全共享（线程）
  安全性高                             效率高
  通信复杂                             通信简单
  开销大                               开销小
  故障隔离                             故障传播
```

线程选择了**偏向共享**的设计点：

- **优点**：创建快（Linux 下 `pthread_create` 比 `fork` 快 10~100 倍）、通信零拷贝（直接读写共享内存）、切换快（不需刷新页表）
- **代价**：引入了**并发安全**问题——数据竞争、死锁、可见性、有序性

### 2.3 抢占式调度

协作式 vs 抢占式

| 模式 | 原理 | 优缺点 |
|------|------|--------|
| **协作式**（Cooperative） | 线程主动让出 CPU（yield） | 无抢占开销，但一个线程不让出则所有线程饿死 |
| **抢占式**（Preemptive） | 操作系统通过时钟中断强制切换 | 公平，但需要处理并发安全 |

现代操作系统几乎全部采用**抢占式调度**，因为协作式在生产环境不可靠。

## 3.线程模型思想

线程的实现涉及**用户态**和**内核态**两个层面，由此产生三种经典模型：

### 3.1 内核级线程

1:1 模型（内核级线程）

```
用户线程:   T1    T2    T3    T4
             │     │     │     │       每个用户线程对应一个内核线程
内核线程:   KT1   KT2   KT3   KT4
             \     |     |     /
              \    |     |    /
               ───CPU调度器───
```

- **实现**：Linux `pthread`、Java HotSpot（Linux）、Windows Thread
- **优点**：真正的并行（多核利用）、一个线程阻塞不影响其他线程
- **缺点**：创建/切换需要内核态转换（syscall 开销约 1~10 μs）

### 3.2 用户级线程

N:1 模型（用户级线程）

```
用户线程:   T1  T2  T3  T4  T5  T6
             \   \   |   |   /   /     N个用户线程映射到1个内核线程
              \   \  |  |   /   /
内核线程:       ─── KT1 ───
                     │
                   CPU核
```

- **实现**：早期 Java Green Thread、Ruby 1.8、GNU Pth
- **优点**：创建/切换极快（纯用户态，~100 ns）
- **缺点**：无法利用多核、一个线程做阻塞系统调用会阻塞所有线程

### 3.3 混合线程

```
用户线程:   T1  T2  T3  T4  T5  T6
             \   |   |   |   |   /     M个用户线程映射到N个内核线程
              \  |   |   |   |  /
内核线程:    KT1    KT2    KT3
              \      |      /
               ──CPU调度器──
```

- **实现**：Go goroutine（GMP 模型）、Erlang process、Java 21 Virtual Thread
- **优点**：兼具用户级线程的轻量和内核级线程的并行能力
- **缺点**：调度器实现复杂

### 3.4 GMP模型

```
           ┌─── P (Processor，逻辑处理器) ───┐
           │  本地运行队列：[G1, G2, G3]      │
           │  当前运行的 G：G0                 │
           └──────────┬──────────────────────┘
                      │ 绑定
                      ▼
                M (Machine，OS 内核线程)
                      │
                    CPU 核

G = Goroutine（用户态协程，初始栈仅 2KB）
M = Machine（真实 OS 线程，栈 1~8MB）
P = Processor（调度上下文，数量 = GOMAXPROCS）

核心设计：
- Work Stealing：P 的本地队列空了，从其他 P 偷任务
- Hand Off：M 阻塞在 syscall 时，P 解绑并交给新 M
- Preemption：Go 1.14+ 基于信号的异步抢占
```

## 4.线程架构设计

### 4.1 操作系统层面

Linux 中线程和进程在内核中统一用 `task_struct` 表示：

```c
// 简化的 task_struct
struct task_struct {
    pid_t pid;                  // 线程 ID（每个线程唯一）
    pid_t tgid;                 // 线程组 ID（= 进程 PID，同进程的线程 tgid 相同）
    
    struct mm_struct *mm;       // 内存描述符 → 同进程的线程共享同一个 mm
    struct files_struct *files; // 文件描述符表 → 共享
    struct signal_struct *signal; // 信号处理 → 共享
    
    struct thread_struct thread; // CPU 寄存器状态 → 每线程独立
    void *stack;                 // 内核栈 → 每线程独立
    // ...
};
```

**`fork()` vs `clone()`**：

```
fork()  → 创建新进程：复制 mm、files、signal（写时复制）
clone() → 创建线程：共享 mm、files、signal（通过标志位控制）

clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD, ...)
       共享内存    共享文件系统  共享文件描述符  共享信号处理    同一线程组
```

### 4.2 线程上下文切换

```
线程 A 运行中
    │
    ▼ 时钟中断 / 系统调用 / 主动让出
┌──────────────────────────────┐
│ 1. 保存 A 的寄存器到 A 的 TCB │  (Thread Control Block)
│ 2. 切换内核栈指针              │
│ 3. 恢复 B 的寄存器从 B 的 TCB │
│ 4. 跳转到 B 的 PC 继续执行    │
└──────────────────────────────┘
    │
    ▼
线程 B 运行中
```

**同进程线程切换 vs 跨进程切换**：

| 操作 | 同进程线程切换 | 跨进程切换 |
|------|--------------|-----------|
| 保存/恢复寄存器 | 需要 | 需要 |
| 切换页表（CR3） | **不需要** | 需要 |
| 刷新 TLB | **不需要** | 需要（代价极大） |
| 典型耗时 | ~1-2 μs | ~3-5 μs |

### 4.3 线程栈架构

```
高地址 ┌──────────────┐
       │  Guard Page   │ ← 栈溢出保护（访问触发 SIGSEGV）
       ├──────────────┤
       │              │
       │  线程栈空间   │ ← 默认 1~8MB（Linux 默认 8MB）
       │  (向下增长)   │
       │              │
       │      ↓       │
       │    栈顶 SP   │ ← 当前栈指针
       │              │
       ├──────────────┤
       │     TLS      │ ← 线程局部存储
低地址 └──────────────┘
```

### 4.4 内存可见性架构

多核 CPU 的缓存层次导致线程间可见性问题：

```
  Thread 1 (Core 0)          Thread 2 (Core 1)
       │                          │
   ┌───┴───┐                  ┌───┴───┐
   │L1 Cache│                  │L1 Cache│  ← 每核私有，可能有过期数据
   └───┬───┘                  └───┬───┘
   ┌───┴───┐                  ┌───┴───┐
   │L2 Cache│                  │L2 Cache│
   └───┬───┘                  └───┬───┘
       └──────────┬───────────────┘
              ┌───┴───┐
              │L3 Cache│  ← 共享
              └───┬───┘
              ┌───┴───┐
              │ 主内存  │
              └───────┘
```

**解决方案**——内存屏障（Memory Barrier）/ 缓存一致性协议（MESI）：
- **Store Barrier**：确保写操作对其他核可见
- **Load Barrier**：确保读到最新值
- **Full Barrier**：两者兼具

各语言的关键字映射：

- Java: `volatile`、`synchronized`
- C/C++: `std::atomic`、`memory_order_*`
- Go: `sync/atomic`、channel
