






### 三、通信模型只有两大范式


#### 范式 1：共享内存（Shared Memory）

```
线程A ──写──→ [共享变量] ←──读── 线程B
```

- 多个线程直接访问同一块内存
- 问题：需要**同步机制**保证可见性和有序性
- 代表：mutex、atomic、condition_variable、读写锁、volatile
- C++/Java/C# 的主流模型

#### 范式 2：消息传递（Message Passing）

```
线程A ──send──→ [channel/queue/pipe] ──recv──→ 线程B
```

- 线程之间不共享状态，通过**发送/接收消息**通信
- 数据的所有权随消息**转移**，天然避免竞争
- 代表：Go channel、Erlang mailbox、pipe、消息队列
- Go 的哲学：_"Don't communicate by sharing memory; share memory by communicating."_

**但两者在底层是等价的**：消息传递的 channel 内部仍然是共享内存 + mutex + condition_variable。区别在于**抽象层级**——消息传递把同步细节封装了，程序员不直接接触共享状态。

### 四、同步的本质——建立 Happens-Before 关系

所有同步机制的**数学本质**是在线程的操作之间建立**偏序关系（Happens-Before）**：

```
操作A happens-before 操作B
⟹ A的所有内存效果对B可见
```

不同机制建立 happens-before 的方式：

| 机制 | Happens-Before 如何建立 |
|------|----------------------|
| mutex unlock → lock | 释放锁的线程的所有写 → 对获取锁的线程可见 |
| atomic release → acquire | store(release) 之前的写 → 对 load(acquire) 之后的读可见 |
| condition notify → wait返回 | 通知前的写 → 对被唤醒线程可见 |
| channel send → recv | 发送前的写 → 对接收后的读可见 |
| thread create / join | 父线程创建前的写 → 子线程可见；子线程的写 → join 后的父线程可见 |

**没有 happens-before 关系的并发访问 = 数据竞争 = 未定义行为。**

### 五、为什么需要这么多种机制？

本质原因是**性能和易用性的权衡**：

```
       简单/安全                                    高性能/复杂
  ←─────────────────────────────────────────────────────→
  
  channel    mutex    semaphore    atomic    CAS自旋    无锁数据结构
  (消息传递)  (粗粒度锁) (资源计数)   (细粒度)  (忙等待)   (极致性能)
  
  ■ 程序员心智负担低                    ■ 程序员心智负担高
  ■ 编译器/运行时帮你同步              ■ 手动管理内存序
  ■ 有额外开销（拷贝、调度）           ■ 几乎零开销
```

每种机制适用不同场景的本质是在这条光谱上找**最优平衡点**：

- **只需通知**（"事情做完了"）→ atomic flag / eventfd / signal（最轻量）
- **保护临界区**（"这段代码同时只能一个人执行"）→ mutex / 读写锁
- **等待条件成立**（"等数据准备好"）→ condition_variable / semaphore
- **传递数据所有权**（"把数据给你，我不再碰"）→ channel / 消息队列
- **多线程汇合**（"大家都到齐了再走"）→ barrier / latch
- **隔离数据**（"各管各的"）→ thread_local（根本不通信）

### 六、终极抽象——通信的三层模型

```
┌────────────────────────────────────────────────────────┐
│  语义层 (What)                                          │
│  程序员表达意图：等待、通知、传递数据、互斥访问            │
│  channel / mutex / barrier / future / async             │
├────────────────────────────────────────────────────────┤
│  同步层 (How)                                           │
│  建立 happens-before 关系，保证可见性和有序性              │
│  atomic + memory_order / lock-unlock 协议                │
├────────────────────────────────────────────────────────┤
│  硬件层 (Mechanism)                                     │
│  CAS 指令 + 内存屏障 + CPU 缓存一致性协议(MESI)          │
│  + OS 调度器 (futex / 上下文切换)                        │
└────────────────────────────────────────────────────────┘
```

### 核心结论

> **线程通信的本质是：在无序的并发执行中，人为地建立确定性的顺序关系（happens-before），使一个线程的内存修改对另一个线程可见。**
>
> 所有机制的区别，仅仅是在**哪一层**、以**多大粒度**、付出**多少性能代价**来建立这个顺序。越底层越快但越危险，越高层越安全但越慢。语言设计者的工作，就是在这条权衡曲线上，为不同场景提供最合适的抽象点。
