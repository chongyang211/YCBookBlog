## 三、根本驱动力

上下文切换不是为了"好玩"，它是被几个根本性矛盾**逼出来的**：

### 矛盾1：CPU速度 vs IO速度

CPU执行一条指令约0.3ns，磁盘IO约10ms——差了**3000万倍**。如果CPU傻等IO完成，浪费极其严重。上下文切换让CPU在等IO时去做别的事。

### 矛盾2：物理核心数 vs 并发任务数

现代服务器可能只有几十个核心，但要同时处理成千上万个请求。上下文切换让有限的核心通过时间片轮转服务大量任务。

### 矛盾3：交互性需求

用户无法接受"等前面的任务跑完才响应我的操作"。分时调度+上下文切换保证了每个任务都能在几毫秒内获得CPU时间，营造出"同时运行"的体验。

### 矛盾4：公平性与优先级

操作系统需要在多个任务之间**公平分配**CPU资源，同时让高优先级任务（实时音视频、中断处理）能**抢占**低优先级任务。这必然需要在任意时刻打断一个任务、切换到另一个任务。

## 四、两种触发模式的演进

### 协作式（Cooperative）——早期方式

任务**主动让出**CPU（调用yield或发起IO）。问题：一个任务如果不让出，其他任务全部饿死。Windows 3.1就是这种模式，一个程序死循环整个系统就卡死。

### 抢占式（Preemptive）——现代主流

操作系统通过**硬件时钟中断**强制切换。时间片到了不管你在干什么，一律打断保存上下文、切换到下一个任务。这是现代OS（Linux、Windows NT、macOS）的基础。

抢占式调度之所以能实现，依赖一个关键硬件机制：**可编程中断定时器（PIT/APIC Timer）**。OS设定一个时间片（通常1-10ms），定时器到期后触发中断，CPU自动陷入内核态，内核的中断处理程序检查是否需要调度，如果需要则执行上下文切换。

## 五、演进脉络总结

```
CPU独占（无切换）
  ↓ CPU利用率太低
多道程序（IO阻塞时切换）
  ↓ 交互性不够
分时系统（时间片 + 抢占式切换）
  ↓ 进程切换太重（TLB刷新）
多线程（共享地址空间，轻量切换）
  ↓ 内核线程数有限，切换仍需陷入内核
用户态协程/绿色线程（用户态切换，几百ns）
  ↓ 需要配合异步IO
M:N调度（Go goroutine / Java虚拟线程）
  ↓ 编译器深度参与
无栈协程 / 状态机（Rust async / JS async-await，趋近零开销）
```

**核心趋势**：保存的状态越来越少，切换越来越快，从微秒级到纳秒级。但本质不变——**在有限物理资源上通过状态保存/恢复实现逻辑并发**。
