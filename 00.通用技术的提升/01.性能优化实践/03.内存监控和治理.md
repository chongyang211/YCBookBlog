## 01.内存优化的概述

### 1.1 项目背景说明

内存优化就是对内存问题的一个预防和解决，做内存优化能让应用挂得少、活得好和活得久。

**挂得少**："挂"指的是Crash。导致应用Crash的原因有很多种，而做内存优化就能让应用避免由内存问题引起的Crash。内存问题导致Crash的具体表现就是内存溢出异常OOM，引起OOM的原因有多种。

**活得好**：指的是使用流畅。造成界面卡顿的原因有很多种，其中一种就是由内存问题引起的。内存问题之所以会影响到界面流畅度，是因为垃圾回收（GC，Garbage Collection），在GC时，所有线程都要停止（Stop The World），包括主线程，当GC和绘制界面的操作同时触发时，绘制的执行就会被搁置，导致掉帧，也就是界面卡顿。

**活得久**：指的是应用在后台运行时不会被干掉。系统会按照特定的机制清理进程，清理进程时优先会考虑清理后台进程。清理进程的机制就是低杀（Low Memory Killer）。

**疑惑**：为什么内存优化不是只做一次就够了？因为内存问题是随着代码迭代不断引入的。每次新增功能、引入第三方库、修改业务逻辑，都可能带来新的内存问题。因此内存优化必须建立持续的监控和治理机制，而不是一次性的工作。

### 1.2 遇到问题介绍

**问题描述**：OOM不知道是从哪里开始出现的，没办法确定具体引发OOM的地方。

**问题分析**：在OOM的时候如果去获取内存信息基本上是获取不到的。原因是已经内存不足了，无法再创建数据来记录当时的状态。

OOM 发生时的困境：

```
正常运行                                      OOM 时刻
───────────────────────────────────────────→  ────────────
堆内存: [██████████░░░░░░] 200MB/512MB         [████████████████] 512MB/512MB
                                                    │
                                        ┌───────────┴───────────┐
                                        │ 此时想 dump hprof?      │
                                        │ → 需要分配 byte[] 缓冲区 │
                                        │ → 内存不足，分配失败     │
                                        │ → 再次触发 OOM          │
                                        │ → 死循环！              │
                                        └─────────────────────────┘

正确做法：在 OOM 之前（如80%水位线）预防性采集
───────────────────────────────────────────→
堆内存: [████████████░░░░] 410MB/512MB (80%)
                     ↑
                 触发预警采集
                 → fork子进程dump hprof
                 → 不影响主进程
                 → 异步分析上报
```

**修改建议**：可以在临近OOM的时候提前获取一下内存的数据信息，来辅助问题定位。具体做法是设定内存水位线（如堆内存使用率超过80%时触发采集），在接近阈值时自动dump堆信息。

**疑惑**：为什么不能在OOM发生的瞬间进行数据采集？

**答疑**：因为OOM本身就意味着堆内存已经耗尽。此时JVM无法再分配内存来创建采集所需的对象（如byte数组、String对象等）。任何需要分配内存的操作都会再次触发OOM。因此必须在OOM发生之前就进行预防性采集。

**论证**：可以通过定时轮询`Runtime.getRuntime().totalMemory()`和`freeMemory()`来监测内存水位。当剩余内存低于阈值时，触发hprof dump，并通过独立进程进行分析，避免影响主进程的内存状态。

**业界方案对比**：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| KOOM(快手) | fork子进程+COW dump | 主进程暂停<100ms | 需要native层支持 |
| LeakCanary | WeakReference+GC触发 | 简单易用 | 只能检测已知生命周期对象 |
| Matrix(微信) | 定时采样+hprof裁剪 | 线上可用，开销小 | hprof文件需裁剪才能上传 |
| 美团Probe | 虚拟机层hook | 零延迟感知分配 | 侵入性强，适配成本高 |

### 1.4 核心设计目标

一期方案的目的在于分析线上OOM的问题根源，到底是什么原因产生的内存泄露，并且泄露的用户中占比有多大。

**线上问题分析**：

1. 建立内存数据等相关指标数据，对指标问题进行梳理和定义；建立端上内存数据采集SDK，统计相关数据
2. 分析线上数据，特别是Android 5.0～Android 7.0这个区间、Android 8.0以上的用户，对Ram大小信息进行分析归类

**线下问题分析**：

建立so内存监控能力，分析so占用大小问题；对各种内存泄露问题case进行编写测试，复现相关场景

对于以上问题，方案设计核心思路如下：

- 建立线下内存自动化分析工具，解决过多的人力投入
- 建立问题解决闭环机制，打通问题的发现、上报、处理、解决问题等多个链路，闭环解决问题
- 建立内存泄露度量体现，数据和结果度量内存质量问题

### 1.5 内存管理演进

**疑惑**：为什么内存管理机制在不断演进？最早的方案有什么问题？

**答疑**：早期的内存管理完全依赖开发者手动分配和释放（如C语言的malloc/free），这种方式极易出错。随着应用复杂度的提升，自动化的内存管理成为必然趋势。

**内存管理技术演变历程**：

```
手动管理(C/C++) → 引用计数(ObjC/Python) → 标记清除(Java/JS) → 分代收集(JVM G1) → 并发收集(ZGC/Shenandoah)
     ↓                    ↓                      ↓                    ↓                      ↓
  忘记释放=泄漏       循环引用=泄漏          STW停顿严重          停顿大幅降低           亚毫秒级停顿
```

- **手动管理时代**：C/C++时代，开发者通过malloc/free、new/delete管理内存，效率最高但最易出错
- **引用计数时代**：Objective-C的MRC/ARC、Python的引用计数，每个对象维护一个引用计数器，计数为0时回收，但无法处理循环引用
- **标记清除时代**：Java的GC、JavaScript的V8引擎，从GC Root开始标记所有可达对象，未被标记的对象被清除，解决了循环引用问题但STW停顿严重
- **分代收集时代**：JVM的CMS/G1收集器，将堆分为新生代和老年代，新生代用复制算法，老年代用标记整理，大幅降低GC停顿
- **并发收集时代**：ZGC、Shenandoah等，实现了几乎零停顿的垃圾回收，通过并发标记、并发整理实现亚毫秒级STW

**结果**：现代GC已经非常高效，但这并不意味着开发者可以完全不关心内存问题。GC只能回收"不可达"的对象，如果存在不合理的引用关系（内存泄漏），GC也无能为力。

## 02.内存基础属性解读

### 2.1 内存属性名词解释

在分析内存问题之前，首先需要理解内存管理中的核心概念：

- **堆内存（Heap）**：JVM管理的最大一块内存区域，用于存放对象实例。GC主要在堆内存上工作。
- **栈内存（Stack）**：线程私有，用于存放局部变量和方法调用栈帧，由系统自动管理。
- **方法区（Method Area）/元空间（Metaspace）**：存放类信息、常量、静态变量等。Java 8后由Metaspace替代永久代。
- **Native内存**：非JVM管理的内存，通过JNI调用C/C++代码分配，如Bitmap像素数据（Android 8.0+存储在Native层）。
- **共享内存**：多个进程共享的内存区域，如mmap映射的文件、Ashmem匿名共享内存。

**疑惑**：Java应用的内存只有堆内存吗？

**答疑**：不是。Java应用的内存构成非常复杂，包括Java Heap、Native Heap、Code（so/dex/oat）、Stack、Graphics（GPU缓冲区）等多个部分。OOM不一定只发生在Java Heap耗尽时，Native内存耗尽、虚拟地址空间耗尽、文件描述符耗尽等都可能触发OOM。

### 2.2 VSS/RSS/PSS/USS详解

这四个指标是理解进程内存占用的基础，从大到小排列：

1. **VSS（Virtual Set Size）**：虚拟耗用内存，包含共享库占用的内存。是进程的虚拟地址空间大小，包括了所有映射但不一定加载到物理内存的区域。
2. **RSS（Resident Set Size）**：实际使用物理内存，包含共享库占用的内存。是进程当前实际驻留在物理内存中的数据大小。
3. **PSS（Proportional Set Size）**：实际使用的物理内存，按比例分配共享库占用的内存。如果一个共享库被3个进程使用，每个进程的PSS只计算1/3。
4. **USS（Unique Set Size）**：进程独自占用的物理内存，不包含共享库占用的内存。这是进程被杀死后能真正释放的内存量。

**大小规律**：VSS >= RSS >= PSS >= USS

**疑惑**：为什么需要这么多内存指标？直接用一个不行吗？

**答疑**：因为现代操作系统中，进程之间大量共享内存（如系统库、共享so等）。如果用RSS来统计所有进程的内存总和，会远大于实际物理内存使用量（因为共享部分被重复计算了）。PSS通过按比例分摊的方式解决了这个问题，是衡量进程真实内存贡献的最佳指标。

```
进程A (RSS=100MB)          进程B (RSS=80MB)
├── 独占内存 60MB (USS)     ├── 独占内存 40MB (USS)
└── 共享库   40MB           └── 共享库   40MB  (同一份物理内存)
                                                
PSS(A) = 60 + 40/2 = 80MB    PSS(B) = 40 + 40/2 = 60MB
系统总PSS = 80 + 60 = 140MB   (实际物理内存 = 60 + 40 + 40 = 140MB ✓)
系统总RSS = 100 + 80 = 180MB  (大于实际物理内存 ✗)
```


例如，如下所示：


关键字段解释：

```
MemTotal      所有可用RAM大小
MemFree       LowFree与HighFree的总和，被系统留着未使用的内存
MemAvailable  系统估算的可用内存（包括可回收的cache），比MemFree更有参考价值
Buffers       用来给文件做缓冲大小
Cached        被高速缓冲存储器用的内存大小
Active        在活跃使用中的缓冲或高速缓冲存储器页面文件的大小
Inactive      在不经常使用中的缓冲或高速缓冲存储器页面文件的大小，可能被用于其他途径
```

**注意**：`MemAvailable`比`MemFree`更能反映系统实际可用内存。因为Linux会积极使用空闲内存作为文件缓存（Cached），这部分内存在需要时可以快速回收给应用使用。

### 2.4 获取Dalvik配置信息

adb指令查看Android虚拟机配置：

```shell
adb shell getprop|grep vm 
```

下面对关键字段进行解释：

```bash
dalvik.vm.heapstartsize       堆的起始大小，应用启动时分配的初始堆内存
dalvik.vm.heapsize            堆的最大大小，单个应用可使用的最大堆内存（通常256MB-512MB）
dalvik.vm.heapgrowthlimit     堆增长的限制，普通应用的堆内存上限（通常128MB-256MB）
dalvik.vm.heapminfree         堆的最小剩余空间
dalvik.vm.heapmaxfree         堆的最大剩余空间
dalvik.vm.heaptargetutilization  理想的堆内存利用率，取值0-1之间（通常0.75）
ro.config.low_ram             该设备是否是低内存设备
dalvik.vm.checkjni            是否要执行扩展的JNI检查
dalvik.vm.stack-trace-file    指定堆栈跟踪文件路径
```

**疑惑**：`heapsize`和`heapgrowthlimit`有什么区别？

**答疑**：`heapgrowthlimit`是普通应用的堆内存上限，而`heapsize`是设置了`android:largeHeap="true"`的应用的堆内存上限。`heapgrowthlimit`通常是`heapsize`的一半左右。不建议随意使用`largeHeap`，因为更大的堆意味着更长的GC停顿时间。

```shell
adb shell cat /proc/<pid>/status
```

关键字段：

```bash
VmPeak    进程虚拟内存的峰值大小（历史最大值）
VmSize    当前虚拟内存大小
VmRSS     实际使用的物理内存大小
VmData    数据段大小（堆内存等）
VmStk     栈大小
VmSwap    被交换到swap的内存大小
Threads   线程数量
```

### 2.7 获取对象内存大小

**疑惑**：什么时候需要知道对象的内存大小？

**答疑**：当设计缓存机制（如LruCache）时，需要精确控制缓存的内存上限；当排查内存问题时，需要知道哪些对象占用了大量内存。

Java基础数据类型所占内存大小：

```
数据类型    所占空间（byte）
byte         1
short        2
int          4
long         8
float        4
double       8
char         2
boolean      1
```

Java对象内存布局分两种：

- **一般非数组对象**：8字节对象头(mark) + 4/8字节对象指针 + 数据区 + padding内存对齐(按照8的倍数对齐)
- **数组对象**：8字节对象头(mark) + 4/8字节对象指针 + 4字节数组长度 + 数据区 + padding内存对齐(按照8的倍数对齐)

对象指针是4字节还是8字节取决于是否开启指针压缩。Oracle JDK从6 update 23开始在64位系统上默认开启压缩指针（-XX:+UseCompressedOops）。

以下面的类为例：

```java
private static class ObjectA {
    String str;   // 4 (引用指针)
    int i1;       // 4
    byte b1;      // 1
    byte b2;      // 1
    int i2;       // 4
    ObjectB obj;  // 4 (引用指针)
    byte b3;      // 1
}
```

由于HotSpot会对字段重排序（从长到短排列：long/double → int/float → short/char → byte/boolean → Reference），实际内存布局为：

```
Size(ObjectA) = 8(mark) + 4(oop指针) + 4(int i1) + 4(int i2) + 1(byte b1) + 1(byte b2) + 1(byte b3) + 1(padding) + 4(String str) + 4(ObjectB obj)
Size(ObjectA) = 32 字节
```

可以使用`Unsafe`来验证字段偏移：

```java
private final static Unsafe UNSAFE;
static {
    try {
        UNSAFE = (Unsafe) Unsafe.class.getDeclaredField("theUnsafe").get(null);
    } catch (Exception e) {
        throw new Error();
    }
}

Field[] fields = ObjectA.class.getDeclaredFields();
for (Field field : fields) {
    System.out.println(field.getName() + "---offSet:" + UNSAFE.objectFieldOffset(field));
}
// 输出: i1---offSet:12, i2---offSet:16, b1---offSet:20, b2---offSet:21, b3---offSet:22, str---offSet:24, obj---offSet:28
```



## 03.为何要内存治理

### 3.1 什么是内存泄漏

**泄露的原因**如果用一句话概括就是：引用了不再需要的内存信息。详细划分可以归为以下几种类别：

- **内部类和匿名内部类导致的内存泄露**：最常见也最容易忽略的问题，尤其在GUI编程中，存在大量的callback回调。非静态内部类会隐式持有外部类的引用。
- **多线程导致的内存泄露**：本质上是线程的生命周期太长了，页面销毁的时候线程有可能还在运行。
- **单例问题**：本质上也是生命周期太长导致的，单例的生命周期等于应用的生命周期。

**疑惑**：线上还是有内存泄露问题，工具不是应该都能检测到吗？

**答疑**：线上的真实使用环境比较复杂，有很多的场景不一定在线下完全覆盖到。虽然线下也有自动化工具上报问题，但很多人都忽略了内存泄露问题，不重视和不及时是掩埋线下问题的根本原因。

**内存泄漏的本质**：当一个对象已经不需要再使用本该被回收时，另外一个正在使用的对象持有它的引用从而导致它不能被回收，这导致本该被回收的对象不能被回收而停留在堆内存中，这就产生了内存泄漏。

**典型案例**：当Activity的onDestroy()方法被调用后，Activity以及它涉及到的View和相关的Bitmap都应该被回收。但如果有一个后台线程持有这个Activity的引用，那么该Activity所占用的内存就不能被回收，最终将会导致内存耗尽引发OOM而让应用crash。

### 3.2 内存泄漏后果

**内存泄漏的直接后果**：

- 可用内存逐步减少，GC频率增加，每次GC的时间也在增加，导致应用运行越来越卡顿
- 当泄漏的内存累积到一定程度时，堆内存不足，最终触发OOM（OutOfMemoryError），应用崩溃退出
- 在Android中，GC过程中所有线程会暂停（Stop The World），如果GC频繁发生，用户会感知到明显的卡顿和掉帧

**内存泄漏的间接后果**：

- 后台进程因占用内存过多被LMK（Low Memory Killer）优先回收，导致用户返回App时需要冷启动
- 系统整体内存紧张，影响其他应用的正常运行，在低端设备上尤为明显
- 长期运行的应用（如音乐播放器、导航类App）内存泄漏问题更加致命，因为它们的存活时间远超普通应用

**疑惑**：内存泄漏和内存溢出是一回事吗？

**答疑**：不是。内存泄漏是"该释放的没有释放"，内存溢出是"要分配的内存超过了可用空间"。内存泄漏是内存溢出的常见原因之一，但内存溢出也可能由于一次性申请过大内存（如加载超大图片）导致。

### 3.3 内存泄漏常见场景

**场景一：监听器未移除**

```java
// 问题代码：add了监听，但没有remove
tv.getViewTreeObserver().addOnWindowFocusChangeListener(this);

// 解决：注册和销毁必须成对出现
// 在onDestroy中：
tv.getViewTreeObserver().removeOnWindowFocusChangeListener(this);
```

**场景二：资源未关闭**

- BroadcastReceiver、ContentObserver、FileObserver、Cursor、Callback、动画等在Activity onDestroy或某类生命周期结束之后一定要unregister或close掉
- 关闭语句必须在finally中执行，否则有可能因为异常未关闭资源，致使Activity泄漏

**场景三：非静态内部类创建静态实例**

```java
// 问题代码
private static TestResource mResource = null;
@Override
protected void onCreate(Bundle savedInstanceState) {
    if(mResource == null){
        mResource = new TestResource();
    }
}
class TestResource {
    // 非静态内部类持有外部Activity的引用
    // mResource是静态变量，生命周期等于应用生命周期
    // 导致Activity无法被回收
}
```

**解决办法**：将该内部类设为静态内部类或将该内部类抽取出来封装成一个单例，如果需要使用Context，使用Application的Context。

**场景四：静态集合使用不当**

- 当把对象加入到static类型的集合容器后，如果不在合适的时机清除，GC就无法回收这些对象
- 解决：当不再需要某对象时，需要主动将之从集合中移除

### 3.4 什么是内存溢出

**内存溢出（Out Of Memory，简称OOM）**：指程序在申请内存时，没有足够的内存空间供其使用。通俗来说就是"要的太多，给的不够"。

在Java/Android中，当JVM的堆内存不足以分配新的对象时，会抛出`java.lang.OutOfMemoryError`。

**内存溢出和内存泄漏的关系**：

- 内存泄漏积累到一定程度就会导致内存溢出，但内存溢出不一定都是由内存泄漏引起的
- 例如，一次性加载一张8000x8000像素的图片到内存，即使没有内存泄漏也可能直接OOM

### 3.5 内存溢出后果

- **应用直接崩溃**：OOM是致命错误，一旦发生应用进程会被系统终止
- **数据丢失**：用户正在编辑的内容、未保存的状态都可能丢失
- **连锁反应**：在多进程架构下，一个进程OOM可能导致其他进程通过Binder通信超时，进而引发更大范围的异常

**OOM 崩溃与普通异常的本质区别**：

```
普通异常（NullPointerException等）：
  → try-catch 可以捕获 → 应用可以恢复 → 用户可能无感知

OOM（OutOfMemoryError）：
  → 虽然是 Error 也能 catch → 但 catch 之后：
     1. 内存仍然不足，后续操作大概率还会 OOM
     2. GC 已经尽最大努力回收了，仍然不够
     3. 应用处于"僵尸状态"：活着但无法正常工作
  → 正确做法：catch OOM 后记录现场信息，然后安全重启
```

**OOM 对用户体验的量化影响**：

| 影响维度 | 具体表现 | 业务损失 |
|---------|---------|---------|
| 稳定性 | 应用闪退 | 用户留存率下降5-10% |
| 数据完整性 | 编辑内容丢失 | 用户投诉增加 |
| 信任度 | 频繁崩溃 | 应用评分下降，卸载率上升 |
| 系统影响 | 触发LMK杀其他进程 | 影响设备整体体验 |

**iOS 的特殊情况**：iOS 没有 OOM Exception，系统通过 Jetsam 机制直接杀死内存占用过高的进程。应用不会收到任何回调，从用户角度看就是"应用突然消失了"。这使得 iOS 的 OOM 问题比 Android 更难定位和追踪。

### 3.6 内存溢出场景

常见的内存溢出场景：

- **Bitmap加载不当**：直接加载超大分辨率图片到内存，未经过采样压缩
- **数据库Cursor未关闭**：查询大量数据时未及时关闭游标，数据一直驻留在内存
- **无限递归**：方法调用栈溢出（StackOverflowError，严格来说是栈溢出）
- **WebView长期使用**：WebView会占用大量内存且难以完全释放，特别是加载复杂网页时
- **大量字符串拼接**：在循环中使用"+"进行字符串拼接，每次都产生新的String对象

**跨平台对比**：

- **iOS**：没有Java堆的概念，但也存在内存溢出问题，系统通过`didReceiveMemoryWarning`通知应用清理内存。iOS没有GC，使用ARC（自动引用计数），内存不足时系统直接杀死进程（Jetsam机制）
- **Web端**：通过浏览器的垃圾回收机制管理内存，但JavaScript闭包、DOM节点泄漏、事件监听器未移除等也会导致内存持续增长。浏览器会在Tab页内存过大时提示用户或自动回收



## 04.内存分析指标体系

### 4.1 内存衡量标准

App内存可以用工具查看总的消耗内存（如Java内存、Native内存），但衡量App内存是否健康需要建立一套衡量准则。

**核心衡量指标**：

| 指标 | 说明 | 健康阈值参考 |
|------|------|-------------|
| Java Heap | Java堆内存占用 | 不超过heapgrowthlimit的75% |
| Native Heap | Native层内存占用 | 持续增长需关注 |
| PSS Total | 按比例分配的总物理内存 | 因应用类型而异，一般<200MB |
| 内存泄漏次数 | 单位时间内检测到的泄漏数 | 0 |
| GC频率 | 单位时间内GC次数 | 非高频操作下不应频繁触发 |
| 内存抖动 | 短时间内内存快速分配和回收 | Memory Profiler中无锯齿波形 |

**线上监控指标体系**：

```
一级指标：OOM率 = OOM次数 / 总启动次数
二级指标：内存均值 = SUM(采样点PSS) / 采样次数
三级指标：内存峰值 = MAX(采样点PSS)
四级指标：GC次数/频率 = 单位时间GC次数
五级指标：内存泄漏检测数 = LeakCanary等工具检测到的泄漏次数
```

### 4.2 内存泄漏判断方法

**疑惑**：内存泄漏在堆内存中不可见，怎么判断？

**答疑**：通常我们可以借助以下方法和工具来检测：

**方法一：反复操作观察法**

- 反复进入退出某个页面，观察Memory Profiler的内存曲线
- 如果每次退出后内存不回到之前的水位线，说明存在泄漏
- 结合Heap Dump对比前后的对象实例数，找出只增不减的对象

**方法二：自动化检测**

- 集成LeakCanary，自动在Activity/Fragment的onDestroy后检测泄漏
- 自定义ObjectWatcher，监控任意对象的回收情况

**方法三：线上监控**

- 定时采集PSS/Java Heap指标，通过趋势分析发现缓慢泄漏
- 在内存水位超过阈值时自动dump hprof文件，上传后台分析

### 4.3 内存监控采集方案

**进程级内存统计**：

```shell
# 获取指定进程的内存信息
stats=$(ps -o pid,pcpu,pmem,rss,vsz -p "$pid" 2>/dev/null | tail -n1)
echo "$stats" | tr -s ' ' | awk '{print $2","$3","int($4/1024)","int($5/1024)}'
```

统计指标详解：

- **pmem (%)**：进程内存使用百分比 = (进程RSS / 系统总内存) × 100
- **rss (MB)**：实际物理内存占用，单位从KB转换为MB
- **vsz (MB)**：虚拟内存大小，包括共享库、堆栈等，单位从KB转换为MB

数据来源：`/proc/[pid]/stat` 和 `/proc/[pid]/status`

### 4.4 系统级内存统计

**核心原理——理解 Linux 内存管理的层次结构**

Linux 系统的内存管理分为物理内存和虚拟内存两个层次。应用进程看到的是虚拟地址空间，通过 MMU（内存管理单元）和页表映射到物理内存。理解这个机制对于正确解读内存指标至关重要。

```
Linux 内存管理全景图：

┌─────────────── 物理内存 (RAM) ────────────────┐
│                                               │
│  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────────┐  │
│  │内核   │  │进程A  │  │进程B  │  │ 页面缓存  │  │
│  │空间   │  │RSS    │  │RSS    │  │ (文件缓存)│  │
│  └──────┘  └──────┘  └──────┘  └──────────┘  │
│                                               │
│  total = used + free + buffers + cached        │
│  available = free + 可回收的cached              │
└───────────────────────────────────────────────┘
```

**关键内存指标解读**：

| 指标 | 含义 | 获取方式 | 注意事项 |
|------|------|---------|---------|
| MemTotal | 物理内存总量 | /proc/meminfo | 固定值 |
| MemFree | 完全空闲的内存 | /proc/meminfo | 不含缓存，通常很小 |
| MemAvailable | 可用内存(含可回收缓存) | /proc/meminfo | **最有参考价值** |
| Buffers | 块设备缓冲 | /proc/meminfo | 可回收 |
| Cached | 页面缓存 | /proc/meminfo | 可回收 |
| SwapTotal | 交换空间总量 | /proc/meminfo | Android默认无swap |

```shell
# 获取系统内存使用情况
mem_info=$(free -m | awk 'NR==2{print $3 * 100/$2","$3","$2}')
```

统计指标详解：

- **sys_mem_usage(%)**：系统内存使用率 = (已用内存 / 总内存) × 100
- **sys_mem_used(MB)**：系统已使用内存
- **sys_mem_total(MB)**：系统总内存

数据来源：`/proc/meminfo`（通过free命令解析）

**Android 的 LowMemoryKiller (LMK) 机制**：

当系统内存不足时，LMK 按照 `oom_adj` 值从高到低依次杀死进程：

```
oom_adj 值与进程类型对应关系：

oom_adj    进程类型              被杀优先级
  906      缓存进程(空进程)       最先被杀
  700      后台服务进程           较早被杀
  200      可感知进程             较晚被杀
  100      可见进程               晚被杀
    0      前台进程               最后被杀
 -800      系统进程               基本不杀
-1000      Native进程             不杀

查看方式：cat /proc/[pid]/oom_adj
```

**iOS 的 Jetsam 机制**：与 Android LMK 类似，iOS 通过 Jetsam 按内存占用和优先级杀进程。但 iOS 不发送任何通知就直接杀死进程，且 footprint 限制更严格（通常单应用不超过系统总内存的50%）。

**数据采集流程**：

```
进程PID → ps命令 → 解析RSS/VSZ → 单位转换(KB→MB) → 输出CSV字段
系统内存 → free命令 → 解析used/total → 计算使用率 → 输出CSV字段
```



## 05.内存监控核心设计

### 5.1 内存泄漏检测原理

**疑惑**：怎样才能自动发现一个对象是否泄漏了？

**答疑**：核心思想是利用Java的弱引用（WeakReference）和引用队列（ReferenceQueue）机制。当一个对象应该被销毁时（如Activity.onDestroy），用弱引用包装它并关联到ReferenceQueue。如果GC后弱引用没有出现在队列中，说明对象仍然存活——即发生了泄漏。

**论证**——引用队列机制：

```
1. 创建 WeakReference(target, referenceQueue)
2. 当target对象被GC回收时，WeakReference会被放入referenceQueue
3. 通过检查referenceQueue是否收到了该WeakReference，可以判断target是否被回收

如果触发GC后，referenceQueue中没有收到WeakReference → target对象未被回收 → 泄漏
```

**结果**：这个机制的优雅之处在于它完全依赖JVM自身的GC机制来判断对象的存活状态，不需要侵入式地修改业务代码。

### 5.2 GC Root与引用链

**GC Root是什么？**

GC Root是垃圾回收器判断对象是否可回收的起点。从GC Root开始，通过引用链遍历所有可达对象。不可达的对象即为垃圾，可以被回收。

**哪些对象可以作为GC Root**：

- 虚拟机栈中的局部变量引用的对象（方法正在执行时的局部变量）
- 方法区中静态变量引用的对象（static字段引用的对象）
- 方法区中常量引用的对象（如字符串常量池中的引用）
- Native方法栈中JNI引用的对象（JNI Global References）
- 活跃线程（Thread对象）
- 类加载器（ClassLoader）
- Monitor锁持有的对象

**引用链分析示例**：

```
GC Root (static field) → Singleton → Callback → Activity → View → Bitmap
                                                    ↑
                                              这就是泄漏的Activity
```

只要存在从任意GC Root到目标对象的引用路径，该对象就不会被回收。

### 5.3 WeakReference与ReferenceQueue

**WeakReference的工作机制**：

```java
// 弱引用的对象，在下次GC时就会被回收（不论内存是否充足）
WeakReference<Activity> weakRef = new WeakReference<>(activity);
activity = null; // 清除强引用
System.gc(); // 触发GC
weakRef.get(); // 返回null，说明对象已被回收
```

**ReferenceQueue的工作机制**：

```java
ReferenceQueue<Activity> queue = new ReferenceQueue<>();
WeakReference<Activity> weakRef = new WeakReference<>(activity, queue);
activity = null;
System.gc();

// 检查队列：如果weakRef出现在queue中，说明activity已被回收
Reference<? extends Activity> ref = queue.poll();
if (ref != null) {
    // 对象已被GC回收
} else {
    // 对象仍然存活，可能发生了泄漏
}
```

**疑惑**：为什么不直接用`weakRef.get()`来判断，而要用ReferenceQueue？

**答疑**：`weakRef.get()`返回null确实说明对象已被回收，但在批量监控场景中（如同时监控多个Activity），使用ReferenceQueue可以通过poll一次性获知哪些对象已被回收，效率更高。此外，ReferenceQueue是异步通知机制，可以在独立线程中处理，不会阻塞主线程。

### 5.4 LeakCanary核心原理

LeakCanary是Android上最主流的内存泄漏检测工具，其核心原理可以分为以下几个步骤：

**第一步：监听生命周期**

```java
// 通过Application.registerActivityLifecycleCallbacks监听所有Activity的生命周期
application.registerActivityLifecycleCallbacks(new ActivityLifecycleCallbacks() {
    @Override
    public void onActivityDestroyed(Activity activity) {
        // Activity销毁时开始监控
        objectWatcher.watch(activity, "Activity " + activity.getClass().getName());
    }
});
```

**第二步：弱引用 + ReferenceQueue监控**

```java
// 将Activity用WeakReference包装，关联到ReferenceQueue
WeakReference<Object> weakRef = new WeakReference<>(watchedObject, queue);
// 记录到Map中，key为唯一ID
watchedObjects.put(key, new KeyedWeakReference(weakRef, key, description));
```

**第三步：延迟检测**

```java
// 延迟5秒后检查（给GC足够的时间回收对象）
mainHandler.postDelayed(() -> {
    // 先触发GC
    Runtime.getRuntime().gc();
    // 再次检查ReferenceQueue
    removeWeaklyReachableObjects();
    if (!gone(key)) {
        // 对象仍未被回收，确认泄漏
        // dump hprof文件，分析引用链
    }
}, 5000);
```

**第四步：Hprof分析**

- 使用shark库解析hprof文件
- 从GC Root开始BFS（广度优先搜索），找到到泄漏对象的最短引用路径
- 将引用路径以通知的形式展示给开发者

### 5.5 内存泄漏引用链分析

**引用链的作用**：仅知道某个对象泄漏了是不够的，开发者还需要知道"谁持有了它"。通过dump堆内存（hprof文件），分析从GC Root到泄漏对象的最短引用路径，就能定位到具体的泄漏原因。

**引用链分析工具**：

- **MAT（Memory Analyzer Tool）**：Eclipse出品的堆分析工具，功能强大，适合深度分析。支持OQL查询、Dominator Tree、Leak Suspects等功能。
- **Android Studio Profiler**：集成在IDE中，可以直接dump堆并查看对象引用关系。支持按包名过滤、查看实例详情。
- **LeakCanary/Shark**：自动dump堆并分析引用链，以通知的形式展示给开发者。Shark是LeakCanary的分析引擎，可以独立使用。

**MAT使用示例**：

```
1. 在Android Studio中点击Dump Java Heap，导出hprof文件
2. 使用hprof-conv转换为标准格式：hprof-conv input.hprof output.hprof
3. 在MAT中打开hprof文件
4. 使用Leak Suspects Report自动识别可疑泄漏
5. 通过Dominator Tree查看内存占用最大的对象
6. 对可疑对象右键→Path to GC Roots→exclude weak/soft references
7. 即可看到完整的引用链，定位泄漏根因
```



## 06.常见内存泄漏案例治理

### 6.1 单例造成的内存泄漏

**造成泄漏原因分析**：

单例设计模式在开发中经常使用，单例经常需要持有Context对象。如果持有的Context对象的生命周期比单例更短时，就会导致Context无法被释放，造成内存泄漏。

**问题代码**：

```java
public class AppManager {
    private static AppManager instance;
    private Context context;
    
    private AppManager(Context context) {
        this.context = context; // 如果传入Activity的Context，Activity退出后无法回收
    }
    
    public static AppManager getInstance(Context context) {
        if (instance == null) {
            instance = new AppManager(context);
        }
        return instance;
    }
}
```

**解决办法**：

```java
private AppManager(Context context) {
    this.context = context.getApplicationContext(); // 使用Application的Context
}
```

**原理**：Application的Context的生命周期等于应用的生命周期，与单例的生命周期一致，不会导致任何组件被不当持有。

### 6.2 Handler造成的内存泄漏

**造成泄漏原因分析**：

通过内部类的方式创建mHandler对象，mHandler会隐式持有外部类（Activity）的引用。当执行postDelayed方法时，该方法会将Handler装入一个Message，并把Message推到MessageQueue中。MessageQueue是在Looper线程中不断轮询处理消息，当Activity退出时消息队列中还有未处理的消息或者正在处理消息，而Message持有Handler引用，Handler又持有Activity引用，导致Activity无法被回收。

**引用链**：

```
MessageQueue → Message → Handler(内部类) → Activity
```

**解决Handler内存泄露**：

```java
// 方案一：静态内部类 + WeakReference
private static class SafeHandler extends Handler {
    private final WeakReference<Activity> activityRef;
    
    SafeHandler(Activity activity) {
        this.activityRef = new WeakReference<>(activity);
    }
    
    @Override
    public void handleMessage(Message msg) {
        Activity activity = activityRef.get();
        if (activity != null && !activity.isFinishing()) {
            // 安全处理消息
        }
    }
}

// 方案二：在onDestroy中移除所有消息
@Override
protected void onDestroy() {
    super.onDestroy();
    mHandler.removeCallbacksAndMessages(null);
}
```

### 6.3 线程造成的内存泄漏

**线程内存泄漏场景**：

当开启一个子线程执行耗时操作后，如果发生配置变更（如横竖屏切换）导致Activity重新创建，旧Activity应交给GC回收。但如果线程是非静态内部类或匿名类，线程会保持对旧Activity的隐式引用。当线程的run()方法还没有执行结束时，线程不会被销毁，导致旧Activity也不会被回收。

**线程产生内存泄露的主要原因**：

1. 线程生命周期的不可控——Thread和AsyncTask不会因为Activity销毁而销毁，Thread会一直等到run()执行结束才会停止
2. 非静态的内部类和匿名类会隐式地持有外部类的引用

**解决方案**：

```java
// 方案一：静态内部类 + 弱引用
private static class MyTask extends Thread {
    private final WeakReference<Activity> activityRef;
    
    MyTask(Activity activity) {
        this.activityRef = new WeakReference<>(activity);
    }
    
    @Override
    public void run() {
        Activity activity = activityRef.get();
        if (activity != null && !activity.isFinishing()) {
            // 安全执行任务
        }
    }
}

// 方案二：在Activity退出后主动停止线程
@Override
protected void onDestroy() {
    super.onDestroy();
    if (myThread != null) {
        myThread.interrupt(); // 中断线程
    }
}
```

### 6.4 静态变量造成的内存泄漏

**问题描述**：在工具类中使用静态方法很方便，但创建的对象如果被全局化（加上static修饰），就可能导致内存泄漏。

**问题代码**：

```java
public class ShareUtil {
    private static Dialog sShareDialog; // 静态变量持有Dialog引用
    
    public static void showShareView(Activity activity) {
        sShareDialog = new Dialog(activity); // Dialog内部持有Activity的引用
        sShareDialog.show();
    }
}
// 当Activity销毁后，sShareDialog仍然持有Activity引用
// 导致Activity无法被回收
```

**解决办法**：

```java
public class ShareUtil {
    public static void showShareView(Activity activity) {
        Dialog shareDialog = new Dialog(activity); // 使用局部变量
        shareDialog.show();
        // 或者在Dialog dismiss时置空
        shareDialog.setOnDismissListener(d -> {
            // 释放引用
        });
    }
}
```

**原则**：静态方法中创建的对象或变量不要全局化，全局化后的变量或对象会导致内存泄漏。

### 6.5 资源未关闭造成的内存泄漏

**常见资源泄漏类型**：

| 资源类型 | 关闭方法 | 泄漏后果 |
|---------|---------|---------|
| Cursor | close() | 数据库连接不释放 |
| InputStream/OutputStream | close() | 文件句柄泄漏 |
| BroadcastReceiver | unregisterReceiver() | Activity被系统强引用 |
| ContentObserver | unregisterContentObserver() | 观察者无法释放 |
| TypedArray | recycle() | 内部数组无法回收 |
| Bitmap | recycle() | 大量像素数据无法释放 |
| 动画 | cancel() | 持有View引用 |

**最佳实践**：使用try-with-resources或try-finally确保资源关闭：

```java
// Java 7+ try-with-resources
try (Cursor cursor = db.query(...)) {
    while (cursor.moveToNext()) {
        // 处理数据
    }
} // 自动关闭

// Kotlin use扩展函数
db.query(...).use { cursor ->
    while (cursor.moveToNext()) {
        // 处理数据
    }
}
```

### 6.6 集合容器造成的内存泄漏

**问题描述**：往static类型的集合容器中不断添加对象，但从不清理，这些对象永远无法被GC回收。

**常见场景**：

```java
// 问题：全局缓存不断增长
public class EventBus {
    private static final Map<String, List<Observer>> observers = new HashMap<>();
    
    public static void register(String event, Observer observer) {
        observers.computeIfAbsent(event, k -> new ArrayList<>()).add(observer);
    }
    // 如果从不调用unregister，observer就永远不会被回收
}
```

**解决方案**：

1. 在合适的生命周期节点调用remove/clear
2. 使用WeakHashMap或WeakReference包装value
3. 对缓存设置上限，使用LruCache等淘汰策略



## 07.内存治理优化策略

### 7.1 内存优化整体思路

内存优化的整体策略可以分为三个层面：

- **减少内存分配**：从源头上减少不必要的对象创建和内存申请
- **及时释放内存**：确保不再使用的对象能够被GC正确回收，避免泄漏
- **合理使用内存**：充分利用缓存机制和对象复用技术，在性能和内存之间取得平衡

**具体实施方向**：

| 方向 | 具体措施 |
|------|---------|
| 图片优化 | 使用合适的采样率加载Bitmap，及时回收不需要的图片资源，使用Glide/Coil的缓存策略 |
| 数据结构优化 | Android中用SparseArray替代HashMap<Integer, Object>，避免自动装箱 |
| 布局优化 | 减少布局层级，避免过度绘制，使用ViewStub延迟加载 |
| 后台释放 | 重写onTrimMemory方法，根据不同级别释放缓存资源 |
| 对象复用 | 使用对象池（Message.obtain()、RecyclerView ViewHolder） |
| 大对象管理 | 大Bitmap放到独立进程，使用mmap映射大文件 |

### 7.2 避免内存抖动

**什么是内存抖动？**

内存抖动是由于短时间内有大量对象进出新生区导致的，它伴随着频繁的GC。GC会大量占用UI线程和CPU资源，导致App整体卡顿。在Memory Profiler中表现为锯齿状的内存曲线。

**避免内存抖动的建议**：

- 尽量避免在循环体内创建对象，应该把对象创建移到循环体外
- 注意自定义View的onDraw()方法会被频繁调用，不应该在里面创建对象
- 当需要大量使用Bitmap时，试着用数组或容器缓存实现复用
- 对于能够复用的对象，使用对象池进行缓存

**问题代码示例**：

```java
// 错误：在onDraw中创建对象，每帧都会分配内存
@Override
protected void onDraw(Canvas canvas) {
    Paint paint = new Paint(); // 每次绘制都创建新对象！
    Rect rect = new Rect();   // 每次绘制都创建新对象！
    paint.setColor(Color.RED);
    canvas.drawRect(rect, paint);
}

// 正确：在构造函数中创建，onDraw中复用
private final Paint mPaint = new Paint();
private final Rect mRect = new Rect();

@Override
protected void onDraw(Canvas canvas) {
    mPaint.setColor(Color.RED);
    canvas.drawRect(mRect, mPaint);
}
```

### 7.3 四种引用优化

Java中有四种引用类型，从强到弱排列：

| 引用类型 | GC回收条件 | 典型用途 |
|---------|-----------|---------|
| 强引用 | 不会回收，宁愿OOM | 普通对象引用 |
| 软引用（SoftReference） | 内存不足时回收 | 图片缓存、频率高且内存易吃紧的场景 |
| 弱引用（WeakReference） | 下次GC时回收 | Handler防泄漏、LeakCanary检测 |
| 虚引用（PhantomReference） | 随时回收 | 跟踪对象被GC回收的状态 |

**软引用VS弱引用选择**：

- 如果只是想避免OutOfMemory异常的发生，则可以使用软引用
- 如果对于应用的性能更在意，想尽快回收占用大内存的对象，则使用弱引用
- 如果该对象可能会经常使用，就尽量用软引用；如果不被使用的可能性更大，就用弱引用

**示例代码**：

```java
// 软引用缓存示例
public class ImageCache {
    private Map<String, SoftReference<Bitmap>> cache = new HashMap<>();
    
    public void put(String key, Bitmap bitmap) {
        cache.put(key, new SoftReference<>(bitmap));
    }
    
    public Bitmap get(String key) {
        SoftReference<Bitmap> ref = cache.get(key);
        return ref != null ? ref.get() : null; // 内存不足时可能返回null
    }
}

// 弱引用防止Handler泄漏
private static class SafeHandler extends Handler {
    private final WeakReference<Activity> activityRef;
    
    SafeHandler(Activity activity) {
        activityRef = new WeakReference<>(activity);
    }
}
```

### 7.4 合理使用对象池

**什么是对象池**：

对象池（Object Pool）是一种设计模式，预先创建一组对象放入池中，需要使用时从池中获取，使用完毕后归还到池中，而不是每次都new一个新对象。其核心目标是减少频繁创建和销毁对象带来的GC压力和性能开销。

**Android中的对象池实践**：

- **Message.obtain()**：Message类使用了对象池，通过一个链表维护回收的Message实例，下次获取Message时优先从池中复用

```java
// Message对象池源码核心
public static Message obtain() {
    synchronized (sPoolSync) {
        if (sPool != null) {
            Message m = sPool;
            sPool = m.next;
            m.next = null;
            m.flags = 0;
            sPoolSize--;
            return m; // 复用池中的Message
        }
    }
    return new Message(); // 池为空时创建新对象
}
```

- **Pools.SimplePool**：Android SDK提供的通用对象池

```java
private static final Pools.SimplePool<MyObject> sPool = new Pools.SimplePool<>(10);

public static MyObject obtain() {
    MyObject obj = sPool.acquire();
    return obj != null ? obj : new MyObject();
}

public void recycle() {
    reset(); // 重置对象状态
    sPool.release(this);
}
```

- **RecyclerView的ViewHolder**复用机制本质上也是对象池思想

**注意事项**：

- 对象池大小需要合理控制，过大占用过多内存，过小起不到复用效果
- 归还对象前必须重置对象状态，避免脏数据
- 对象池中的对象不应该持有外部引用

### 7.5 即时销毁与log优化

**即时销毁对象**：

在组件销毁的时候即时销毁对象，将对象设置为null，中断强引用与对象之间的关系，让GC能够回收这些对象的内存。

```java
@Override
protected void onDestroy() {
    super.onDestroy();
    if (mBitmap != null && !mBitmap.isRecycled()) {
        mBitmap.recycle();
        mBitmap = null;
    }
    if (mAdapter != null) {
        mAdapter = null;
    }
}
```

**log日志优化**：

log方法内存开销可能过大，应该在Release包中关闭日志：

```java
public static void d(Object object) {
    // 问题：即使不打印日志，字符串拼接操作也会执行，产生大量临时String对象
    // Log.d(TAG, " log : " + object);
    
    // 正确做法：Debug模式下才执行
    if (BuildConfig.DEBUG) {
        Log.d(TAG, " log : " + object);
    }
}
```

### 7.6 onTrimMemory响应

**onTrimMemory的设计目的**：

Android系统在内存紧张时会回调`onTrimMemory(int level)`方法，通知应用释放不必要的内存资源。通过响应不同级别的内存警告，可以有效降低被系统杀死的概率。

**关键级别说明**：

```java
@Override
public void onTrimMemory(int level) {
    switch (level) {
        case TRIM_MEMORY_UI_HIDDEN:
            // 应用UI不再可见，释放UI相关资源
            clearImageCache();
            break;
        case TRIM_MEMORY_RUNNING_LOW:
            // 系统内存较低，应用正在运行，清理不必要的缓存
            reduceCacheSize();
            break;
        case TRIM_MEMORY_RUNNING_CRITICAL:
            // 系统内存非常低，尽可能释放所有可释放的资源
            clearAllCaches();
            break;
        case TRIM_MEMORY_COMPLETE:
            // 应用在后台，且系统即将杀死该进程，释放所有可能的资源
            releaseEverything();
            break;
    }
}
```

**跨平台对比**：

- **iOS**：通过`didReceiveMemoryWarning`方法接收内存警告，原理类似
- **Web端**：暂无标准API，但可以通过`performance.memory`监控JS堆内存，在接近阈值时主动释放
- **Flutter**：通过`WidgetsBindingObserver.didHaveMemoryPressure()`接收内存警告



## 08.内存治理实战与效果验证

### 8.1 Bitmap内存治理实战

**Bitmap是移动端内存头号杀手**。一张 4000×3000 的照片，以 ARGB_8888 格式加载到内存，占用 4000 × 3000 × 4 = 48MB。如果列表页同时加载 10 张这样的图片，仅图片就占用 480MB，直接触发 OOM。

**治理原理——采样率降低分辨率**：

BitmapFactory 提供 `inSampleSize` 参数，按 2 的幂次降低图片分辨率。采样率为 4 时，宽高各缩小为 1/4，内存降为原来的 1/16。

```
原图 4000×3000 → inSampleSize=4 → 1000×750
内存: 48MB → 3MB (降低93.75%)
```

**治理做法一：按View尺寸精准加载**

```java
// 第一步：只读取图片宽高，不加载像素数据
BitmapFactory.Options options = new BitmapFactory.Options();
options.inJustDecodeBounds = true;
BitmapFactory.decodeResource(res, resId, options);
int imageWidth = options.outWidth;   // 4000
int imageHeight = options.outHeight; // 3000

// 第二步：计算最优采样率
int reqWidth = imageView.getWidth();   // 如 200dp
int reqHeight = imageView.getHeight(); // 如 150dp
int inSampleSize = 1;
while ((imageWidth / inSampleSize) > reqWidth * 2 
    && (imageHeight / inSampleSize) > reqHeight * 2) {
    inSampleSize *= 2;
}

// 第三步：按采样率加载
options.inJustDecodeBounds = false;
options.inSampleSize = inSampleSize;
Bitmap bitmap = BitmapFactory.decodeResource(res, resId, options);
```

**治理做法二：使用RGB_565替代ARGB_8888**

如果图片不需要透明通道（如纯照片），使用 RGB_565 格式，每像素从 4 字节降到 2 字节，内存直接减半。

```java
options.inPreferredConfig = Bitmap.Config.RGB_565;
// 同一张图: ARGB_8888 = 48MB → RGB_565 = 24MB
```

**治理做法三：Bitmap复用池（inBitmap）**

Android 3.0+ 支持 `inBitmap`，让新的 Bitmap 解码到已有 Bitmap 的内存空间，避免重复分配和 GC。

```java
// 维护一个可复用的Bitmap池
private final Set<SoftReference<Bitmap>> reusablePool = Collections.synchronizedSet(new HashSet<>());

// 解码时指定复用
options.inMutable = true;
options.inBitmap = findReusableBitmap(options); // 从池中查找大小匹配的Bitmap
Bitmap bitmap = BitmapFactory.decodeStream(inputStream, null, options);
```

**理论依据——内存分配与GC的关系**：

每次 `BitmapFactory.decodeXxx()` 都会在堆上分配一块连续内存。频繁分配大块内存会导致：(1) 堆碎片化，触发 GC Compact 整理内存；(2) 新生代迅速填满，频繁触发 Minor GC；(3) 大对象直接进入老年代，触发 Major GC（STW 时间更长）。通过 `inBitmap` 复用已有内存块，从根本上减少了分配/回收的次数。

**治理前后效果**：

| 指标 | 治理前 | 治理后 | 改善幅度 |
|------|--------|--------|---------|
| 图片列表页PSS | 380MB | 120MB | -68% |
| GC次数(每分钟) | 45次 | 8次 | -82% |
| 列表滑动帧率 | 42fps | 58fps | +38% |
| 图片页OOM率 | 2.3‰ | 0.1‰ | -95.6% |

### 8.2 页面泄漏专项治理

**泄漏治理不是修一个算一个，而是建立系统化的发现-修复-验证闭环**。

**治理流程**：

```
Step 1: 自动化扫描
────────────────────
Monkey测试 + LeakCanary → 自动收集泄漏引用链 → 写入本地日志

Step 2: 引用链分类
────────────────────
泄漏类型分类：
├── Handler消息未清理 ──── 35%
├── 匿名内部类持有Activity ── 25%
├── 单例持有Context ──── 20%
├── 注册监听未注销 ──── 12%
└── 其他 ──────────── 8%

Step 3: 批量修复
────────────────────
按占比从高到低逐项修复，每修复一类后验证

Step 4: 回归验证
────────────────────
重新执行相同的Monkey测试路径，对比泄漏数量
```

**治理做法一：Handler消息泄漏批量修复**

**问题根因**：Activity.onDestroy() 时 MessageQueue 中仍有未处理的 Message，Message → Handler → Activity 形成引用链。

```java
// 封装SafeHandler基类，所有业务Handler继承它
public abstract class SafeHandler<T extends Activity> extends Handler {
    private final WeakReference<T> hostRef;

    public SafeHandler(T host) {
        this.hostRef = new WeakReference<>(host);
    }

    @Override
    public final void handleMessage(Message msg) {
        T host = hostRef.get();
        if (host != null && !host.isFinishing() && !host.isDestroyed()) {
            handleMessageSafely(host, msg);
        }
    }

    protected abstract void handleMessageSafely(T host, Message msg);
}

// 统一在BaseActivity.onDestroy中清理
@Override
protected void onDestroy() {
    super.onDestroy();
    if (mHandler != null) {
        mHandler.removeCallbacksAndMessages(null);
    }
}
```

**治理做法三：注册/注销配对检查**

```java
// 在BaseActivity中统一管理注册与注销
public class BaseActivity extends AppCompatActivity {
    private final List<Runnable> cleanupTasks = new ArrayList<>();

    // 注册时记录对应的注销操作
    protected void registerWithCleanup(Runnable registerAction, Runnable unregisterAction) {
        registerAction.run();
        cleanupTasks.add(unregisterAction);
    }

    @Override
    protected void onDestroy() {
        super.onDestroy();
        for (Runnable task : cleanupTasks) {
            task.run();
        }
        cleanupTasks.clear();
    }
}

// 使用示例

    () -> sensorManager.registerListener(listener, sensor, rate),
    () -> sensorManager.unregisterListener(listener)
);
```

**理论依据——GC可达性分析**：

GC 通过从 GC Root 出发遍历引用图来判断对象是否存活。泄漏的本质是：对象的预期生命周期已结束，但从某个 GC Root 出发仍然可以到达它。治理的核心就是在对象生命周期结束时，切断从 GC Root 到该对象的所有引用路径。

```
治理前：GC Root → static Singleton → Callback → Activity (已onDestroy，但无法回收)
治理后：GC Root → static Singleton → Callback → WeakRef → null (Activity已被回收)
```

### 8.3 大对象与缓存治理

**疑惑**：缓存不是为了提高性能吗？为什么要治理缓存？

**答疑**：无上限的缓存等于内存泄漏。缓存治理不是删除缓存，而是给缓存加上合理的上限和淘汰策略，让缓存在"命中率"和"内存占用"之间取得平衡。

**治理做法一：LruCache合理设置上限**

```java
// 错误：拍脑袋设定缓存大小
LruCache<String, Bitmap> cache = new LruCache<>(100); // 100个？100KB？100MB？

// 正确：基于可用内存动态计算
int maxMemory = (int) (Runtime.getRuntime().maxMemory() / 1024); // KB
int cacheSize = maxMemory / 8; // 分配1/8给图片缓存

LruCache<String, Bitmap> cache = new LruCache<String, Bitmap>(cacheSize) {
    @Override
    protected int sizeOf(String key, Bitmap value) {
        return value.getByteCount() / 1024; // 以KB为单位
    }
    
    @Override
    protected void entryRemoved(boolean evicted, String key, Bitmap oldValue, Bitmap newValue) {
        if (evicted && oldValue != null && !oldValue.isRecycled()) {
            // 被淘汰的Bitmap加入复用池而不是直接回收
            reusablePool.add(new SoftReference<>(oldValue));
        }
    }
};
```

**理论依据——LRU淘汰的数学基础**：

LRU（Least Recently Used）基于"时间局部性原理"：最近被访问的数据在短期内再次被访问的概率更高。对于大多数用户行为（如浏览相册、刷新闻流），数据访问呈幂律分布——少量数据被频繁访问，大量数据很少被访问。

```
缓存命中率与缓存大小的关系（典型场景）：

缓存大小(占总数据%)   命中率
     5%               60%    ← 帕累托法则：5%的缓存覆盖60%的请求
    10%               75%
    20%               88%
    50%               95%
   100%              100%    ← 全量缓存，但内存不允许

结论：缓存大小到达某个拐点后，继续增大的边际收益急剧下降
```

**治理做法二：三级缓存架构**

```
请求图片
  ↓
[一级缓存] 内存LruCache (热数据，命中率~70%)
  ↓ 未命中
[二级缓存] 磁盘DiskLruCache (温数据，命中率~20%)
  ↓ 未命中
[三级缓存] 网络下载 (冷数据，~10%的请求才走网络)
  ↓
加载成功后回写到一级和二级缓存
```

**治理做法三：大对象独立进程管理**

对于 WebView、地图引擎等占用内存巨大且难以精确控制的组件，使用独立进程隔离：

```xml
<!-- AndroidManifest.xml -->
<activity
    android:name=".WebViewActivity"
    android:process=":webview" />
```

**优势**：WebView 进程 OOM 不会影响主进程；退出 WebView 页面后进程销毁，内存彻底释放。

**治理前后效果**：

| 指标 | 治理前 | 治理后 | 改善幅度 |
|------|--------|--------|---------|
| 图片缓存内存峰值 | 200MB(无上限) | 48MB(1/8 maxMemory) | -76% |
| WebView退出后内存残留 | 80-120MB | 0MB(进程销毁) | -100% |
| 缓存命中率 | 85%(冗余缓存) | 82%(LRU淘汰) | -3%(可接受) |
| 应用整体PSS峰值 | 450MB | 220MB | -51% |

**理论依据——虚拟内存与物理内存映射**：

so 库加载时通过 `mmap` 映射到虚拟地址空间。只有实际被访问的代码页才会加载到物理内存（Demand Paging）。但一旦加载，即使不再使用也不会被主动释放（除非系统内存紧张触发 page out）。懒加载的本质是延迟 mmap 的时机，减少物理内存的常驻占用。

### 8.5 线程与连接池治理

**疑惑**：线程也占内存？占多少？

**答疑**：每个线程在创建时都会分配独立的栈空间。Java 线程默认栈大小约 512KB~1MB，Native 线程默认 1MB（Android pthread 默认 1MB）。创建 100 个线程仅栈空间就占用 50-100MB，加上线程关联的对象（ThreadLocal、Runnable等），实际更多。

**治理做法一：线程池统一管理**

```java
// 治理前：业务代码中散落的线程创建
new Thread(() -> doSomething()).start();           // 无法复用
new Thread(() -> doAnotherThing()).start();         // 无上限创建
Executors.newCachedThreadPool();                    // 上限为Integer.MAX_VALUE

// 治理后：全局统一的线程池工厂
public class AppExecutors {
    // IO密集型：核心线程数 = CPU核数 * 2
    private static final ExecutorService IO = new ThreadPoolExecutor(
        4, Runtime.getRuntime().availableProcessors() * 2,
        30L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(128),
        new ThreadFactory() {
            private final AtomicInteger count = new AtomicInteger(0);
            @Override
            public Thread newThread(Runnable r) {
                Thread t = new Thread(r, "app-io-" + count.getAndIncrement());
                t.setPriority(Thread.NORM_PRIORITY - 1);
                return t;
            }
        },
        new ThreadPoolExecutor.CallerRunsPolicy() // 队列满时由调用线程执行
    );
    
    // CPU密集型：核心线程数 = CPU核数
    private static final ExecutorService COMPUTE = new ThreadPoolExecutor(
        Runtime.getRuntime().availableProcessors(),
        Runtime.getRuntime().availableProcessors(),
        0L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(64)
    );
    
    public static ExecutorService io() { return IO; }
    public static ExecutorService compute() { return COMPUTE; }
}
```

### 8.7 治理理论原理总结

将内存治理中涉及的理论原理进行系统化总结：

**原理一：对象生命周期对齐**

内存泄漏的根本原因是"引用关系的生命周期长于被引用对象的预期生命周期"。治理的第一原则是确保引用关系和对象生命周期对齐。

```
生命周期层次（从短到长）：

方法局部变量 < Activity/Fragment < Service < Application(单例) < 进程
     ↑                ↑               ↑            ↑
   方法结束回收      onDestroy回收   stopSelf回收   进程退出回收

规则：短生命周期的对象不应被长生命周期的对象强引用
违反时的解法：WeakReference / 手动置null / Lifecycle感知组件
```

**原理二：内存分配的空间-时间权衡**

所有的内存优化本质上都是在"空间"和"时间"之间做权衡：

| 策略 | 空间 | 时间 | 典型场景 |
|------|------|------|---------|
| 缓存 | 多用空间 | 换更快的访问 | LruCache、DiskLruCache |
| 压缩 | 少用空间 | 换额外的计算 | Bitmap采样、数据压缩 |
| 对象池 | 预留空间 | 减少分配开销 | Message.obtain()、ViewHolder |
| 懒加载 | 延迟分配 | 首次使用更慢 | so按需加载、ViewStub |
| 独立进程 | 多用系统资源 | 换隔离性和可释放性 | WebView进程 |

**原理三：GC效率与堆利用率的关系**

JVM 分代收集的效率与堆内存利用率密切相关。`heaptargetutilization`（默认0.75）控制 GC 后期望的堆利用率：

```
堆利用率过高（>85%）：
  → GC频率增加（堆几乎满了，很快就需要下一次GC）
  → 每次GC回收量少（大部分对象都是存活的）
  → STW停顿虽然短但次数多，累积影响大

堆利用率过低（<50%）：
  → 浪费内存（其他App可以用的内存被你"霸占"了）
  → 系统可能认为你的App占用过多，提高被LMK杀死的概率

最优区间：60%-80%
  → GC频率适中
  → 每次GC能回收足够的空间
  → 给临时对象留有分配余量，减少紧急GC
```

**原理四：内存碎片与分配器设计**

频繁分配和释放不同大小的对象会导致堆碎片化——虽然总空闲内存充足，但没有足够大的连续空间分配给大对象。

```
碎片化内存示例：
[████|░░|████|░|████|░░░|████|░░|████]
  已用 空闲 已用 空 已用 空闲 已用 空闲 已用

总空闲: 8个单位，但最大连续空闲只有3个单位
→ 如果要分配4个单位的大对象 → 分配失败 → 触发GC Compact（整理）→ STW

治理思路：
1. 使用对象池减少分配/释放频率
2. 同类型对象尽量相同大小（如inBitmap要求）
3. 大对象预分配，避免运行时动态创建
```

**原理五：缓存效率的数学模型**

缓存设计的核心参数是缓存大小和淘汰策略。根据工作集理论（Working Set Theory），应用在任意时间窗口内活跃访问的数据集合是有限的。缓存大小应该能覆盖"工作集"，但不需要覆盖全部数据。

| 淘汰策略 | 命中率 | 实现复杂度 | 适用场景 |
|---------|--------|-----------|---------|
| FIFO | 低 | 简单(队列) | 数据无明显时间局部性 |
| LRU | 高 | 中(HashMap+双向链表) | 大多数场景的默认选择 |
| LFU | 较高 | 高(最小堆+HashMap) | 热点数据明显的场景 |
| ARC | 最高 | 最高(两个LRU) | 对命中率要求极高 |
| Random | 中 | 最简单(随机) | 数据访问均匀分布 |

**治理方法论总结——PDCA循环**：

```
Plan(计划)：分析内存指标 → 识别瓶颈 → 确定治理目标
  ↓
Do(执行)：按优先级实施治理方案 → 先治大头(Bitmap/泄漏)再治细节
  ↓
Check(检查)：对比治理前后指标 → 验证治理效果 → 识别新问题
  ↓
Act(改进)：将有效方案固化为规范 → 集成到CI/CD → 持续监控防劣化
  ↓
回到 Plan（下一轮迭代）
```

```java
// 获取Java堆内存信息
Runtime runtime = Runtime.getRuntime();
long maxMemory = runtime.maxMemory();       // 最大可用堆内存
long totalMemory = runtime.totalMemory();   // 当前已分配的堆内存
long freeMemory = runtime.freeMemory();     // 当前空闲的堆内存
long usedMemory = totalMemory - freeMemory; // 当前已使用的堆内存
float usageRate = (float)usedMemory / maxMemory; // 使用率

// 获取Debug信息
Debug.MemoryInfo memInfo = new Debug.MemoryInfo();
Debug.getMemoryInfo(memInfo);
int totalPss = memInfo.getTotalPss(); // 总PSS
int nativePss = memInfo.nativePss;    // Native PSS
int dalvikPss = memInfo.dalvikPss;    // Dalvik PSS
```

**Native层内存监控**：

```cpp
// 通过mallinfo获取Native堆信息
#include <malloc.h>
struct mallinfo info = mallinfo();
long nativeHeapSize = info.usmblks;  // Native堆大小
long nativeHeapAlloc = info.uordblks; // Native堆已分配
long nativeHeapFree = info.fordblks;  // Native堆空闲
```

**内存泄漏自动检测**：

- 集成LeakCanary 2.x，零配置自动监控Activity、Fragment、ViewModel、Service的泄漏
- KOOM（快手开源）：针对线上场景优化，支持Java/Native内存泄漏检测，采用fork子进程dump hprof避免应用卡顿

### 9.2 iOS内存监控方案

**iOS内存管理机制**：

iOS使用ARC（Automatic Reference Counting）自动引用计数管理内存，不像Java有垃圾回收器。每个对象维护一个引用计数器，引用计数为0时对象被立即释放。

**内存监控方式**：

```objectivec
// 获取App内存使用信息
#import <mach/mach.h>

- (int64_t)getAppMemoryUsage {
    struct mach_task_basic_info info;
    mach_msg_type_number_t count = MACH_TASK_BASIC_INFO_COUNT;
    kern_return_t kr = task_info(mach_task_self(),
                                 MACH_TASK_BASIC_INFO,
                                 (task_info_t)&info,
                                 &count);
    if (kr == KERN_SUCCESS) {
        return info.resident_size; // 物理内存使用量
    }
    return -1;
}
```

**iOS循环引用检测**：

iOS最常见的内存泄漏是循环引用（Retain Cycle），因为ARC无法处理循环引用。

```swift
// 问题：闭包捕获self导致循环引用
class ViewController: UIViewController {
    var closure: (() -> Void)?
    
    override func viewDidLoad() {
        closure = {
            self.view.backgroundColor = .red // self被闭包强引用，闭包被self强引用
        }
    }
}

// 解决：使用[weak self]
closure = { [weak self] in
    self?.view.backgroundColor = .red
}
```

**iOS内存监控工具**：

- **MLeaksFinder**：腾讯开源，通过Method Swizzling hook ViewController的dealloc方法，延迟检查对象是否被释放
- **FBRetainCycleDetector**：Facebook开源，运行时检测循环引用
- **MetricKit**：iOS 13+提供的系统级性能监控框架，自动收集内存指标

### 9.3 Web端内存监控方案

**JavaScript内存管理**：

Web端使用V8引擎（Chrome）或JavaScriptCore（Safari）的垃圾回收器管理内存，采用分代收集策略。

**内存监控API**：

```javascript
// 方式一：performance.memory（Chrome专属）
const memInfo = performance.memory;
console.log('JS Heap Size Limit:', memInfo.jsHeapSizeLimit); // JS堆上限
console.log('Total JS Heap Size:', memInfo.totalJSHeapSize); // 已分配的JS堆大小
console.log('Used JS Heap Size:', memInfo.usedJSHeapSize);   // 已使用的JS堆大小

// 方式二：PerformanceObserver监控内存相关事件
const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
        console.log('Memory entry:', entry);
    }
});
observer.observe({ entryTypes: ['measure'] });

// 方式三：Heap Snapshot（Chrome DevTools）
// 在DevTools → Memory → Take Heap Snapshot
// 对比两次snapshot，找出只增不减的对象
```

**Web端常见内存泄漏场景**：

| 场景 | 原因 | 解决方案 |
|------|------|---------|
| 事件监听器未移除 | addEventListener后未removeEventListener | 组件卸载时清理 |
| 闭包引用 | 闭包意外持有大对象 | 及时解除引用 |
| 定时器未清理 | setInterval/setTimeout未clear | 组件卸载时clearInterval |
| DOM节点泄漏 | 移除DOM节点但JS仍持有引用 | 同步清理JS引用 |
| console.log | console中的对象不会被GC | 生产环境移除console |

### 9.4 Flutter内存监控方案

**Flutter内存模型**：

Flutter应用的内存分为三部分：Dart Heap、Native Heap、Graphics（Skia/Impeller渲染引擎占用）。

```dart
// 获取Dart堆内存信息
import 'dart:developer';

void checkMemory() {
    // 通过DevTools的Memory view查看
    // 或者使用vm_service获取
    
    // 监听内存压力
    WidgetsBinding.instance.addObserver(
        _MemoryObserver(),
    );
}

class _MemoryObserver with WidgetsBindingObserver {
    @override
    void didHaveMemoryPressure() {
        // 系统内存不足，清理缓存
        imageCache.clear();
        imageCache.clearLiveImages();
    }
}
```

**Flutter常见内存问题**：

- **大图加载**：使用`ResizeImage`控制解码后的图片大小
- **列表未复用**：ListView.builder自动复用Widget，避免使用Column包裹大量子Widget
- **Stream未关闭**：StreamController在dispose时必须close
- **全局状态持有页面引用**：避免在全局状态中持有Widget/State/BuildContext的引用

### 9.5 跨平台方案对比总结

| 维度 | Android | iOS | Web | Flutter |
|------|---------|-----|-----|---------|
| 内存管理 | GC（分代收集） | ARC（引用计数） | GC（V8分代） | GC（Dart VM） |
| 主要泄漏类型 | GC Root引用链 | 循环引用 | 闭包/DOM | Stream/全局状态 |
| 检测工具 | LeakCanary/KOOM | MLeaksFinder/Instruments | Chrome DevTools | Dart DevTools |
| 系统回调 | onTrimMemory | didReceiveMemoryWarning | 无标准API | didHaveMemoryPressure |
| OOM处理 | 抛出OOMError | Jetsam杀进程 | Tab崩溃 | 抛出OutOfMemoryError |
| Native内存 | 通过mallinfo/proc | 通过mach API | N/A | 通过FFI |

**共性原则**：

1. 无论哪个平台，内存泄漏的本质都是"长生命周期对象持有短生命周期对象的引用"
2. 所有平台都需要在组件销毁时清理资源（取消监听、关闭流、置空引用）
3. 缓存必须有上限和淘汰策略
4. 大对象（图片、文件）需要按需加载和及时释放



## 10.内存监控设计总结

### 10.1 技术演变历程

**疑惑**：内存监控技术是怎么一步步发展到今天的？

**答疑**：让我们回顾内存监控的技术演变过程：

```
阶段一：手动分析时代
├── 开发者手动使用adb shell dumpsys meminfo查看内存
├── 使用DDMS/MAT手动dump和分析hprof文件
└── 问题：效率极低，依赖人工经验，线上问题无法分析

    ↓

阶段二：自动检测时代
├── LeakCanary的出现（2015年），自动检测Activity/Fragment泄漏
├── 基于WeakReference+ReferenceQueue的检测机制
└── 问题：仅限线下调试，dump hprof会导致应用卡顿

    ↓

阶段三：线上监控时代
├── 内存水位线监控，定时采集内存指标上报
├── KOOM等工具实现fork子进程dump hprof，不卡主进程
├── 线上自动分析引用链，推送到开发者
└── 问题：采集频率和性能开销需要平衡

    ↓

阶段四：智能化治理时代
├── 基于大数据分析的内存异常自动识别
├── 结合机器学习的泄漏预测和根因分析
├── 自动化的内存优化建议推送
└── 发展方向：更低开销、更高覆盖、更快定位
```

### 10.2 设计原则与最佳实践

**内存监控系统设计原则**：

1. **低侵入性**：监控代码不应该影响业务代码的正常运行，不应该引入额外的内存泄漏
2. **低开销**：内存采集本身不应该造成明显的性能开销，避免频繁GC
3. **高覆盖**：不仅监控Java Heap，还要覆盖Native Heap、Graphics、Stack等
4. **快速定位**：不仅告诉开发者"发生了泄漏"，还要提供完整的引用链帮助快速定位
5. **闭环治理**：从发现→分析→修复→验证形成完整闭环

**最佳实践清单**：

| 阶段 | 实践 |
|------|------|
| 开发阶段 | 集成LeakCanary，开启StrictMode，使用Profiler实时监控 |
| 测试阶段 | 执行内存专项测试（反复进退页面、长时间运行、极端操作） |
| 发布阶段 | 集成线上内存监控SDK，设置OOM率告警阈值 |
| 运维阶段 | 建立内存指标看板，定期Review内存趋势，及时修复泄漏 |

### 10.3 内存监控伪代码示例

以下是一个跨平台通用的内存监控框架伪代码：

```
// 通用内存监控接口
interface IMemoryMonitor {
    fun start()                    // 启动监控
    fun stop()                     // 停止监控
    fun getMemoryInfo(): MemoryInfo // 获取当前内存信息
    fun setThreshold(threshold: Long) // 设置内存水位阈值
    fun setCallback(callback: MemoryCallback) // 设置回调
}

// 内存信息数据模型
data class MemoryInfo(
    val javaHeapUsed: Long,    // Java堆已使用
    val javaHeapMax: Long,     // Java堆上限
    val nativeHeapUsed: Long,  // Native堆已使用
    val totalPss: Long,        // 总PSS
    val timestamp: Long        // 采集时间戳
)

// Android实现
class AndroidMemoryMonitor : IMemoryMonitor {
    private val handler = Handler(Looper.getMainLooper())
    private var isRunning = false
    private var threshold = 0.8f // 默认80%水位线
    
    override fun start() {
        isRunning = true
        handler.postDelayed(collectTask, INTERVAL)
    }
    
    private val collectTask = Runnable {
        if (!isRunning) return
        
        // 1. 采集Java堆信息
        val runtime = Runtime.getRuntime()
        val used = runtime.totalMemory() - runtime.freeMemory()
        val max = runtime.maxMemory()
        
        // 2. 采集PSS信息
        val memInfo = Debug.MemoryInfo()
        Debug.getMemoryInfo(memInfo)
        
        // 3. 判断是否超过阈值
        val usageRate = used.toFloat() / max
        if (usageRate > threshold) {
            // 触发告警，可选择dump hprof
            callback?.onMemoryWarning(usageRate)
        }
        
        // 4. 上报数据
        reportMemoryData(MemoryInfo(used, max, ...))
        
        // 5. 继续下一次采集
        handler.postDelayed(collectTask, INTERVAL)
    }
}

// iOS实现（伪代码）
class IOSMemoryMonitor : IMemoryMonitor {
    override fun getMemoryInfo(): MemoryInfo {
        // 通过task_info获取物理内存
        val taskInfo = task_info(mach_task_self(), MACH_TASK_BASIC_INFO)
        return MemoryInfo(
            residentSize = taskInfo.resident_size,
            virtualSize = taskInfo.virtual_size
        )
    }
}

// Web实现（伪代码）
class WebMemoryMonitor : IMemoryMonitor {
    override fun getMemoryInfo(): MemoryInfo {
        val mem = performance.memory
        return MemoryInfo(
            jsHeapUsed = mem.usedJSHeapSize,
            jsHeapTotal = mem.totalJSHeapSize,
            jsHeapLimit = mem.jsHeapSizeLimit
        )
    }
}
```

**核心设计思想**：

1. 抽象统一接口，各平台差异化实现
2. 定时采集 + 阈值告警的双重机制
3. 采集数据标准化，便于跨平台对比分析
4. 告警分级处理（水位线告警 → dump hprof → 自动分析 → 推送开发者）
