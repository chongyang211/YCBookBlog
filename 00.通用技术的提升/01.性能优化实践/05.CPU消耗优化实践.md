## 01.CPU优化背景说明

### 1.1 项目背景介绍
- CPU是移动设备最核心的计算资源
    - CPU消耗直接影响应用的响应速度、流畅度和用户体验
    - 过高的CPU占用还会导致设备发热、电量快速消耗、甚至被系统强制降频
    - 在低端设备上，CPU性能本身就有限，不合理的CPU使用会导致更严重的性能问题
- CPU优化的必要性
    - 功耗问题：CPU是移动设备最大的耗电元件之一，持续高负载会显著缩短续航
    - 发热问题：高CPU占用导致设备升温，触发系统的热节流机制，进一步降低性能
    - 卡顿问题：CPU资源被后台任务大量占用时，主线程得不到足够的时间片，导致UI卡顿
    - 资源竞争：多个应用共享CPU资源，过度占用会影响其他应用和系统服务

### 1.2 CPU消耗的影响
- CPU过高消耗对用户的直接影响
    - 手机发烫：用户握持不适，长时间可能影响设备硬件寿命
    - 电量骤降：用户明显感知电量消耗加快，影响使用意愿
    - 界面卡顿：帧率下降，滑动不流畅，点击响应延迟
    - 功能异常：系统为了降温可能限制应用CPU使用，导致后台任务被延迟或取消
- CPU过高消耗的间接影响
    - 应用评分下降：发热和耗电是用户差评的常见原因
    - 被系统限制：Android 8.0+系统对后台CPU使用有严格限制，违规应用可能被限制
    - 被应用市场标记：部分应用市场会监控应用的资源消耗，异常应用可能被标记或下架

### 1.3 优化设计目标
- CPU优化的核心目标
    - 降低CPU平均占用率：应用在前台时CPU占用率控制在20%以下（单核）
    - 消除CPU尖刺：避免短时间内CPU使用率飙升到100%的情况
    - 减少后台CPU消耗：应用进入后台后CPU消耗趋近于0
    - 合理利用多核：将耗时任务分配到工作线程，避免单核过载

### 1.4 建设收益分析
- CPU优化的收益是多方面的
    - 用户体验：降低发热和耗电，提升应用流畅度
    - 业务指标：用户停留时长增加，DAU提升
    - 技术指标：帧率提升、启动速度加快、后台存活率提高


## 02.CPU如何收集

### 2.1 CPU占用率获取

CPU是系统非常重要的资源，在Android中/proc/stat

包含了所有CPU的相关详情信息，查看CPU使用情况，CPU不是一个瞬时态，而是一个过程态的体现，一般可以使用top命令和dump cpuinfo命令进行CPU占用率获取。

top命令获取方法，top是比较经典的CPU计算方法，总的cpu时间 = user + nice + system + idle + iowait + irq + softirq

例如：User 147 + Nice 11 + Sys 79 + Idle 408 + IOW 1 + IRQ 0 + SIRQ 6 = 652

而proc->delta_time是两次读取/proc/pid/stat相减得到，可见，top是一段时间内，计算process的cpu jiffies与总的cpu jiffies差值得到。

通过adb获取top：

```bash
adb shell top -m 100 -n 1 -s cpu | grep 包名
```

dump cpuinfo命令获取方法

Android特有的命令，dump cpuinfo命令的实现在androidm/frameworks/base/core/java/com/android/internal/os/ProcessCpuTracker.java类里面，方法是printCurrentState

进程的总Cpu时间processCpuTime = utime + stime + cutime + cstime，该值包括其所有线程的cpu时间。

通过adb获取dump：

```bash
adb shell dumpsys cpuinfo |grep 包名
```

### 2.2 CPU总使用率

指计算机中所有CPU核心的整体利用率。它表示了CPU在特定时间段内的工作负荷，即CPU用于处理各种任务的时间比例。

当CPU总使用率较高时，可能表示系统负荷较重，处理器资源被大量任务占用，可能会导致系统响应速度变慢或出现卡顿现象。监控和理解CPU总使用率对于评估系统性能、优化资源分配以及解决潜在问题都非常重要。

**在Android低版本设备中，可以通过读取 /proc/stat 文件实现**

/proc/stat 内容首行有8个数值，分别提供了所有CPU在 用户态(user)、用户态-低优先级(nice)、内核态(sys)、空闲态(idle)、io等待(iowait)、硬中断(irq)、软中断(softirq) 状态 下的时间总和，将这些值累加作为系统总的CPU时间(cpuTime)。

计算 iowait/cpuTime 为系统的CPU空闲率，1-cpu空闲率 及为cpu利用率 。注意这里的时间单位为 jiffies，通常一个jiffies 等于10ms。

总的cpu时间totalCpuTime = user + nice + system + idle + iowait + irq + softirq + stealstolen +guest

在Android 8.0以上版本，为了防止旁路攻击，普通应用程序已经无法访问/proc/stat 文件，所以无法通过/proc/stat 的方式计算系统cpu利用率。

部分线下性能监控相关的开源库 如Dokit 会在Android8.0以上的设备 通过执行shell 命令 top -n 1 来直接获取某个进程CPU使用率信息，不过这种方式在高版本设备上也是无法使用的，得到的CPU使用率总是为0。

如何计算cpu使用率：

- 1、采样两个足够短的时间间隔的Cpu快照，分别记作t1,t2，其中t1、t2的结构均为： (user、nice、system、idle、iowait、irq、softirq、stealstolen、guest)的9元组;
- 2、计算总的Cpu时间片totalCpuTime。a) 把第一次的所有cpu使用情况求和，得到s1；b) 把第二次的所有cpu使用情况求和，得到s2；c) s2 - s1得到这个时间间隔内的所有时间片，即totalCpuTime = s2 - s1 ;
- 3、计算空闲时间idle。idle对应第四列的数据，用第二次的idle - 第一次的idle即可 idle = idle2 - idle1
- 4、计算cpu使用率。CPU总使用率（%） = 100*((totalCputime2- totalCputime1)-(idle2-idle1))/(totalCputime2-totalCputime1)

### 2.3 程序CPU使用率

单个应用CPU监控：将选中应用的PID传入，读取/proc/PID/stat文件信息及可获取该PID对应程序的CPU信息。计算方法

- 1、首先获取应用的进程id： adb shell ps | grep com.package | awk '{print $2}' > tmp
- 2、根据进程id，通过proc获取CPU信息 while read line; do adb shell cat /proc/line/stat | awk '{print 14,15,16,$17}' >> appcpu0; done < tmp

以下只解释对我们计算Cpu使用率有用相关参数（14-17列） 参数解释

- utime 该任务在用户态运行的时间，单位为jiffies
- stime 该任务在核心态运行的时间，单位为jiffies
- cutime 所有已死线程在用户态运行的时间，单位为jiffies
- cstime 所有已死在核心态运行的时间，单位为jiffies

进程的总Cpu时间：processCpuTime = utime + stime + cutime + cstime，该值包括其所有线程的cpu时间。

App的CPU占用率，之后可以每1s获取一次CPU信息，分析获得app的CPU占用率等信息。

单个程序的CPU使用率（%） = 100*(processCpuTime2-processCpuTime1)/(totalCpuTime2-totalCpuTime1)


## 03.CPU排查分析
### 3.1 CPU损耗原因
- 对于线上系统突然产生的运行缓慢问题
    - 如果该问题导致线上系统不可用，那么首先需要做的就是，导出 jstack 和内存信息，然后重启系统，尽快保证系统的可用性。
- 这种情况可能的原因主要有两种：
    - 代码中某个位置读取数据量较大，导致系统内存耗尽，从而导致 Full GC 次数过多，系统缓慢。
    - 代码中有比较耗 CPU 的操作，导致 CPU 过高，系统运行缓慢。
- 另外有几种情况也会导致某个功能运行缓慢，但是不至于导致系统不可用：
    - 代码某个位置有阻塞性的操作，导致该功能调用整体比较耗时，但出现是比较随机的。
    - 某个线程由于某种原因而进入 WAITING 状态，此时该功能整体不可用，但是无法复现。
    - 由于锁使用不当，导致多个线程进入死锁状态，从而导致系统整体比较缓慢。

    - https://mp.weixin.qq.com/s/ixm14buRWvsNlV5WpVZCmQ


### 3.2 线上CPU异常排查
- 线上CPU异常排查流程
    - 第一步：通过APM平台发现CPU异常告警（CPU使用率持续高于阈值）
    - 第二步：关联分析异常的维度信息（版本、设备、场景、时间）
    - 第三步：获取CPU异常时的线程堆栈快照
    - 第四步：分析高消耗线程的调用链路，定位热点函数
    - 第五步：修复问题并验证
- 线上排查的关键数据
    - CPU使用率时间曲线：观察CPU使用率的变化趋势，区分持续高和间歇性高
    - 线程CPU分布：哪些线程消耗了最多的CPU时间
    - 调用堆栈：高消耗线程在做什么操作
    - 关联信息：当时用户在什么页面、进行什么操作

### 3.3 CPU热点函数定位
- 热点函数是指消耗CPU时间最多的函数
    - 使用Android Profiler的CPU Recording功能采集调用链路
    - 分析Flame Chart（火焰图），识别调用栈中耗时最长的函数
    - 关注Self Time（函数自身耗时）而非Total Time（包含子调用耗时）
- 常见的CPU热点场景
    - 频繁的JSON解析/序列化：大量数据的序列化和反序列化操作
    - 正则表达式匹配：复杂的正则在大文本上执行
    - 频繁的反射调用：反射的性能比直接调用差10-100倍
    - 频繁的文件IO：主线程上的文件读写操作
    - 复杂的布局计算：深层嵌套布局的measure/layout过程




## 04.CPU优化实践

### 4.1 使用线程池
- 线程池是CPU优化的基础手段
    - 避免频繁创建和销毁线程带来的CPU开销（线程创建涉及系统调用、内存分配等开销）
    - 控制并发线程数量，避免过多线程导致CPU频繁上下文切换
    - 线程池大小应根据任务类型设置：CPU密集型任务线程数 = CPU核心数+1，IO密集型任务线程数 = CPU核心数*2
- 线程池使用的注意事项
    - 避免使用Executors.newCachedThreadPool()，它可能创建无限多的线程
    - 设置合理的队列大小，防止内存溢出
    - 为不同优先级的任务使用不同的线程池

```java
// CPU密集型任务线程池
int cpuCount = Runtime.getRuntime().availableProcessors();
ExecutorService cpuExecutor = new ThreadPoolExecutor(
    cpuCount + 1, cpuCount + 1,  // 核心线程 = CPU核心数+1
    60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(128),
    new ThreadFactory() {
        private AtomicInteger count = new AtomicInteger(0);
        @Override
        public Thread newThread(Runnable r) {
            Thread t = new Thread(r, "cpu-worker-" + count.getAndIncrement());
            t.setPriority(Thread.NORM_PRIORITY - 1);  // 降低优先级
            return t;
        }
    }
);
```


### 4.2 减少CPU等待

如果某个线程或进程拥有 CPU 的时间片，但是 CPU 却在当前指令段停下来，长时间无法接着执行后面的代码指令的情况，都可以看做是 CPU 的等待。

此时，CPU 之所无法继续执行后面的代码，可能是因为代码陷入了空循环导致 CPU 空转，或者 CPU 被切走去执行其他线程了。

总的来说，有两种情况经常导致 CPU 等待，一是等待锁，二是等待 IO。

因为锁相关的内容非常庞大，所以这里主要介绍下锁优化方法:

1. 无锁比有锁好：除了不加锁，还有线程本地存储，偏向锁等方案，都属于无锁优化。 
2. 合理细化锁的粒度：比如将 Synchronize 锁住整个方法细化成只锁住方法内可能会产生线程安全的代码块。 
3. 避免在主线程或者渲染线程使用锁： 前面说到锁可能会阻塞线程，所以如果非要使用到锁，也应尽量避免在主线程或渲染线程上使用。


### 4.3 利用CPU闲置时刻
- CPU闲置时刻是指主线程处于空闲状态、没有用户操作的时间段
    - 将非紧急的计算任务延迟到CPU闲置时执行，避免与用户交互操作竞争CPU资源
    - Android可以使用IdleHandler在主线程消息队列空闲时执行任务
    - Web可以使用requestIdleCallback在浏览器空闲时执行任务

```java
// Android使用IdleHandler在CPU空闲时执行任务
public class IdleTaskScheduler {
    private final Queue<Runnable> pendingTasks = new LinkedList<>();
    
    public void addIdleTask(Runnable task) {
        pendingTasks.add(task);
        scheduleIdleExecution();
    }
    
    private void scheduleIdleExecution() {
        Looper.myQueue().addIdleHandler(() -> {
            Runnable task = pendingTasks.poll();
            if (task != null) {
                long startTime = SystemClock.uptimeMillis();
                task.run();
                long duration = SystemClock.uptimeMillis() - startTime;
                // 单个任务执行不超过5ms，避免影响下一帧
                if (duration > 5) {
                    Log.w("IdleTask", "Task took " + duration + "ms");
                }
            }
            // 返回true保持IdleHandler，false移除
            return !pendingTasks.isEmpty();
        });
    }
}
```

- 适合在CPU闲置时执行的任务
    - 预加载数据：提前加载下一页的数据
    - 预渲染：提前创建即将使用的View
    - 上报统计数据：埋点数据的批量上报
    - 缓存清理：过期缓存的清理操作

### 4.4 减少主线程负载

主线程负责 UI 渲染和用户交互，如果主线程负载过高，会导致应用卡顿。优化方法：

- 将耗时操作（如网络请求、数据库查询、文件IO）移到后台线程
- 使用 HandlerThread、ExecutorService 或 Coroutine 管理后台任务
- 避免在 onCreate()、onResume() 等生命周期方法中执行耗时操作
- 图片解码、JSON解析等CPU密集型操作必须在工作线程完成

主线程耗时操作的常见来源：
- SharedPreferences的getXxx()方法：首次调用会触发文件加载和解析
- ContentProvider的query操作：涉及跨进程通信和数据库查询
- 视图inflate操作：XML解析和反射创建View对象
- 大数据量的RecyclerView.Adapter.onBindViewHolder：数据处理应提前在后台完成

```java
// 使用Kotlin协程优化主线程负载
class DataViewModel : ViewModel() {
    fun loadData() {
        viewModelScope.launch {
            // 在IO线程执行耗时操作
            val result = withContext(Dispatchers.IO) {
                val data = repository.fetchData()    // 网络请求
                parseAndTransform(data)               // 数据处理
            }
            // 自动切回主线程更新UI
            _uiState.value = result
        }
    }
}
```

### 4.5 优化算法逻辑

低效的算法和数据结构会导致 CPU 使用率过高。优化方法：

- 使用更高效的算法（如快速排序代替冒泡排序）
- 选择合适的数据结构（如 HashMap O(1)查找 代替 ArrayList O(n)查找）
- 避免不必要的循环和递归
- 使用缓存避免重复计算

常见的算法优化案例：
- 列表搜索：对于有序列表使用二分查找（O(logN)）替代线性查找（O(N)）
- 字符串匹配：使用KMP算法替代暴力匹配
- 数据去重：使用HashSet替代双层循环遍历
- 数据排序：小规模用插入排序，大规模用快排或归并排序

```java
// 优化前：O(n^2) 暴力去重
List<String> removeDuplicates(List<String> list) {
    List<String> result = new ArrayList<>();
    for (String item : list) {
        if (!result.contains(item)) {  // contains是O(n)
            result.add(item);
        }
    }
    return result;
}

// 优化后：O(n) HashSet去重
List<String> removeDuplicates(List<String> list) {
    return new ArrayList<>(new LinkedHashSet<>(list));
}
```


### 4.6 减少锁竞争

多线程编程中，锁竞争会导致 CPU 资源浪费。优化方法：

- 使用无锁数据结构（如 ConcurrentHashMap）
- 减少锁的粒度，避免全局锁
- 使用 ReadWriteLock 或 StampedLock 提高并发性能
- 考虑使用CAS（Compare-And-Swap）操作替代加锁

锁竞争导致CPU浪费的原因分析：
- 线程在等待锁时会被挂起，唤醒时需要上下文切换（消耗CPU）
- 重度锁竞争下，大量线程反复加锁失败、挂起、唤醒，CPU时间浪费在调度上
- 自旋锁在争用时直接消耗CPU时间片空转
- synchronized在JDK 6+有偏向锁→轻量级锁→重量级锁的升级过程，但升级后的重量级锁仍有较大开销

```java
// 锁粒度优化示例
// 优化前：粗粒度锁，所有操作都互斥
public synchronized void processData(String key, Object data) {
    Object cached = cache.get(key);
    if (cached == null) {
        cached = expensiveCompute(data);
        cache.put(key, cached);
    }
    updateUI(cached);
}

// 优化后：细粒度锁，只锁必要的部分
private final ConcurrentHashMap<String, Object> cache = new ConcurrentHashMap<>();

public void processData(String key, Object data) {
    Object cached = cache.computeIfAbsent(key, k -> expensiveCompute(data));
    // updateUI不需要加锁
    updateUI(cached);
}
```

### 4.7 优化布局和渲染

复杂的布局和频繁的 UI 更新会导致 CPU 负载过高。优化方法：

- 使用 ConstraintLayout 减少布局层级（减少measure/layout递归深度）
- 避免过度绘制，使用 ViewStub 和 Merge 标签优化布局
- 使用 RecyclerView 代替 ListView，减少 UI 更新开销
- 减少requestLayout和invalidate的调用频率
- 使用DiffUtil进行列表差量更新，避免全量刷新

### 4.8 优化网络请求

频繁的网络请求会导致 CPU 和电量消耗过高。优化方法：

使用缓存减少重复请求。
使用 OkHttp 或 Retrofit 优化网络请求。
合并多个请求，减少请求次数。



### 4.9 CPU亲和性优化

**疑惑**：什么是CPU亲和性？为什么将线程绑定到特定CPU核心能提升性能？

**答疑**：CPU亲和性（CPU Affinity）是指将线程/进程绑定到特定的CPU核心上执行。当线程在不同CPU核心之间迁移时，之前核心上的L1/L2缓存数据会失效，新核心需要重新从内存加载数据。绑定核心可以避免这种缓存失效，提升性能。

**论证 — 在移动端的特殊性**：

移动设备普遍采用大小核架构（big.LITTLE），例如：
- 骁龙8系列：1个超大核（X核心）+ 3个大核（A7xx）+ 4个小核（A5xx）
- A系列芯片：2个性能核心（Firestorm）+ 4个能效核心（Icestorm）

大核的性能是小核的2-3倍，但功耗也高出3-5倍。合理地将任务分配到大核或小核，可以在性能和功耗之间取得平衡。

```java
// Android: 通过设置线程优先级间接影响CPU调度
// 高优先级任务 → 系统倾向于调度到大核
public void bindToBigCore(Thread thread) {
    // 设置为前台优先级，系统倾向调度到大核
    Process.setThreadPriority(thread.getId(), Process.THREAD_PRIORITY_FOREGROUND);
}

// 低优先级后台任务 → 系统倾向于调度到小核
public void bindToLittleCore(Thread thread) {
    Process.setThreadPriority(thread.getId(), Process.THREAD_PRIORITY_BACKGROUND);
}
```

```swift
// iOS: 使用QoS等级控制CPU调度策略
// 高性能任务 → 性能核心
DispatchQueue.global(qos: .userInteractive).async {
    // UI关键路径任务，系统优先调度到性能核心
    self.processUIUpdate()
}

// 低优先级任务 → 能效核心
DispatchQueue.global(qos: .background).async {
    // 后台维护任务，系统调度到能效核心
    self.cleanupCache()
}
```

**结果**：移动端不直接操作CPU亲和性（不像Linux服务器可以用sched_setaffinity），而是通过线程优先级和QoS等级间接控制。让系统调度器做出最优决策，同时确保关键路径获得足够的CPU资源。


## 05.CPU监控实践

### 5.1 CPU监控思路
- CPU监控是发现和定位CPU性能问题的基础
    - 定期采样应用的CPU使用率，建立CPU使用基线
    - 当CPU使用率超过阈值时采集线程堆栈信息
    - 将CPU数据与用户操作场景关联，定位问题发生的上下文
- CPU监控的数据采集方式
    - /proc/self/stat：获取当前进程的CPU时间片信息（utime + stime）
    - /proc/stat：获取系统总的CPU时间（Android 8.0以下可用）
    - Debug.threadCpuTimeNanos()：获取当前线程的CPU时间
    - 主动采样：定时（如每3秒）采集一次CPU数据

```java
// CPU使用率采集器
public class CpuSampler {
    private long lastProcessCpuTime = 0;
    private long lastSystemCpuTime = 0;
    
    /**
     * 获取当前进程的CPU使用率
     */
    public float getProcessCpuUsage() {
        try {
            // 读取/proc/self/stat
            String stat = readFile("/proc/self/stat");
            String[] fields = stat.split("\\s+");
            long utime = Long.parseLong(fields[13]);  // 用户态时间
            long stime = Long.parseLong(fields[14]);  // 内核态时间
            long currentProcessCpu = utime + stime;
            
            // 读取/proc/stat获取系统CPU时间
            long currentSystemCpu = getSystemCpuTime();
            
            float usage = 0;
            if (lastProcessCpuTime > 0 && lastSystemCpuTime > 0) {
                long processDelta = currentProcessCpu - lastProcessCpuTime;
                long systemDelta = currentSystemCpu - lastSystemCpuTime;
                if (systemDelta > 0) {
                    usage = (float) processDelta / systemDelta * 100f;
                }
            }
            
            lastProcessCpuTime = currentProcessCpu;
            lastSystemCpuTime = currentSystemCpu;
            return usage;
        } catch (Exception e) {
            return -1;
        }
    }
}
```

### 5.2 CPU监控指标设计
- 需要监控的核心CPU指标
    - 应用CPU使用率：当前应用占用的CPU百分比
    - 各线程CPU使用率：识别消耗CPU最多的线程
    - CPU温度：设备CPU温度，用于判断是否触发热节流
    - CPU频率：当前CPU运行频率，判断是否被降频

| 指标 | 采集频率 | 告警阈值 | 数据来源 |
|------|---------|---------|---------|
| 应用CPU使用率 | 3秒 | >30%持续10秒 | /proc/self/stat |
| 线程CPU Top5 | 5秒 | 单线程>80% | /proc/self/task/ |
| CPU温度 | 10秒 | >45°C | thermal_zone |
| 主线程CPU | 3秒 | >50% | Debug.threadCpuTimeNanos |

### 5.3 CPU异常告警方案
- CPU异常告警需要避免误报和漏报
    - 持续告警：CPU使用率持续超过阈值一定时间才触发，避免短暂波动导致误报
    - 差异告警：与同版本的历史基线对比，异常偏离时告警
    - 分场景告警：区分前台和后台的告警阈值（前台允许较高，后台应接近0）
- CPU异常的响应策略
    - 低优先级（P2）：后台CPU使用率偏高 → 下个版本优化
    - 中优先级（P1）：前台特定场景CPU持续过高 → 本迭代修复
    - 高优先级（P0）：大面积发热投诉或CPU导致ANR → 立即修复


## 06.CPU优化进阶实践

### 6.1 减少不必要的唤醒
- 不必要的CPU唤醒是后台耗电的主要原因
    - 频繁的AlarmManager唤醒：使用ELAPSED_REALTIME代替RTC_WAKEUP，减少唤醒次数
    - WakeLock持有时间过长：确保及时释放WakeLock，使用超时机制兜底
    - 不必要的后台轮询：用推送替代轮询，或使用JobScheduler/WorkManager进行批量化处理
    - 频繁的Sensor监听：不需要时及时取消传感器注册
- 批量化处理策略
    - 将多个独立的后台任务合并为一次执行，减少CPU唤醒次数
    - 使用JobScheduler/WorkManager设置条件约束（如充电中、WiFi连接时才执行）
    - iOS使用BGProcessingTask实现后台任务的智能调度


### 6.2 IO操作优化
- IO操作虽然不直接消耗CPU，但不当的IO操作会导致CPU等待和上下文切换
    - 同步IO阻塞线程：线程等待IO完成期间虽然不消耗CPU，但占用了线程资源
    - 频繁的小IO操作：频繁的系统调用（read/write）会导致用户态和内核态频繁切换
    - 主线程IO：主线程的IO操作会直接导致UI卡顿
- IO优化策略
    - 使用缓冲IO：BufferedInputStream/BufferedOutputStream减少系统调用次数
    - 批量写入：将多次小写入合并为一次大写入（如日志系统的mmap方案）
    - 异步IO：所有IO操作都应该在工作线程中执行
    - 减少SharedPreferences的commit调用：使用apply代替commit，批量修改一次提交

```java
// 日志写入优化：使用缓冲区合并写入
public class BufferedLogWriter {
    private final StringBuilder buffer = new StringBuilder(8192);
    private static final int FLUSH_THRESHOLD = 4096;
    
    public synchronized void write(String log) {
        buffer.append(log).append('\n');
        if (buffer.length() > FLUSH_THRESHOLD) {
            flush();
        }
    }
    
    public synchronized void flush() {
        if (buffer.length() > 0) {
            // 一次性写入文件，减少IO次数
            writeToFile(buffer.toString());
            buffer.setLength(0);
        }
    }
}
```


### 6.3 序列化和反序列化优化
- JSON序列化/反序列化是CPU消耗的常见热点
    - 常用JSON库性能对比：Gson < Jackson < Moshi < FastJSON
    - 对于大数据量的场景，流式解析（JsonReader）比整体解析（fromJson）更省CPU和内存
    - 考虑使用二进制序列化协议（Protocol Buffers/FlatBuffers）替代JSON
- 各序列化方案的对比

| 方案 | 解析速度 | 数据大小 | 易用性 | 适用场景 |
|------|---------|---------|-------|---------|
| JSON(Gson) | 慢 | 大 | 高 | 通用接口 |
| Protocol Buffers | 快 | 小 | 中 | 高性能接口 |
| FlatBuffers | 极快 | 小 | 低 | 游戏/高频数据 |
| MessagePack | 快 | 小 | 中 | 跨平台数据交换 |

### 6.4 编译器优化利用
- 现代编译器提供了很多优化选项，合理利用可以显著降低CPU消耗
    - R8/ProGuard：不仅能混淆代码，还能进行方法内联、无用代码消除、常量折叠等优化
    - LLVM（iOS）：支持多种优化级别（-O0到-Os），Release模式下默认开启优化
    - V8/JSC（Web/RN）：JIT编译器会对热点代码进行优化编译
- 代码层面帮助编译器优化
    - 使用final修饰不变的变量和方法，帮助编译器内联
    - 避免过深的调用链，减少方法调用开销
    - 使用基本类型代替包装类型，避免拆箱装箱的CPU开销
    - 循环中避免创建对象，将不变的计算提取到循环外

### 6.5 CPU缓存友好优化
- CPU缓存（L1/L2/L3 Cache）对性能有显著影响
    - 缓存命中时访问速度是内存的10-100倍，合理的数据访问模式可以显著提升性能
    - 数据局部性原则：顺序访问数组比随机访问效率高得多
    - 紧凑的数据结构：SparseArray比HashMap更缓存友好（数据连续存储）
- 缓存友好的编程建议
    - 优先使用数组和ArrayList，减少使用LinkedList（链表节点内存不连续）
    - 遍历二维数组时按行遍历（数据在内存中按行连续存储）
    - 结构体/对象的字段按访问频率排列，常用字段放在一起
    - 避免False Sharing：多线程频繁写入的变量应该在不同缓存行上


## 07.CPU优化设计总结

### 7.1 CPU优化核心原则

**原则一：做更少的事**

最有效的CPU优化是减少不必要的计算。在编码时应该思考：这个计算是否必要？能否通过缓存避免重复计算？能否延迟到真正需要时再计算？

**原则二：做更快的事**

当计算不可避免时，使用更高效的算法和数据结构：
- O(1)的HashMap查找优于O(n)的List遍历
- 位运算替代乘除法
- 使用Native代码加速计算密集型任务

**原则三：做更智能的事**

利用系统特性和硬件能力：
- 多核并行：将可并行的任务分配到多个CPU核心
- GPU加速：图形渲染、图像处理等交给GPU
- 延迟执行：非紧急任务延迟到CPU闲置时执行
- 批量处理：合并多个小任务为一次大任务

### 7.3 CPU优化方法论

CPU优化遵循"测量-分析-优化-验证"四阶段方法论：

**第一阶段：测量CPU现状**
1. 建立CPU使用率基线（各场景的CPU占用率）
2. 识别CPU消耗Top页面和Top操作
3. 采集CPU Profile数据（Systrace/Profiler）

**第二阶段：分析CPU热点**
1. 火焰图分析：识别调用链中的热点函数
2. 线程分析：哪些线程消耗了最多的CPU
3. 场景分析：哪些用户操作触发了高CPU消耗
4. 锁分析：是否存在锁争用导致的CPU浪费

**第三阶段：实施优化**
1. 异步化：将耗时操作移出主线程
2. 算法优化：使用更高效的算法和数据结构
3. 减少计算：缓存计算结果、延迟计算
4. 并行化：利用多核并行处理
5. 降频减速：降低不必要的更新频率（如动画帧率、传感器采样率）

**第四阶段：验证效果**
1. 优化前后CPU Profile对比
2. 性能回归测试
3. 线上灰度验证
4. 长期监控

### 7.4 CPU优化常见误区

**疑惑**：CPU优化中有哪些常见的认知误区？

**答疑**：以下误区会导致CPU优化效果不佳甚至适得其反。

**论证**：

**误区一：创建更多线程就能更好地利用CPU**

线程不是越多越好。过多的线程会导致频繁的上下文切换，反而降低CPU效率。线程切换需要保存和恢复寄存器状态，在Linux上一次上下文切换的开销约为1-10微秒。合理的线程数应该根据CPU核心数和任务类型来确定。

**误区二：后台服务不消耗CPU就不需要优化**

后台服务即使CPU消耗不高，也可能因为持有WakeLock导致CPU无法进入低功耗状态，从而大量消耗电量。需要关注应用对CPU睡眠的影响。

**误区三：只关注主线程CPU优化**

主线程CPU优化确实最重要（关乎UI流畅度），但工作线程的CPU消耗同样影响整体性能。过多的工作线程消耗CPU会导致主线程得不到足够的时间片，间接影响UI流畅度。

**误区四：用Native代码替代Java就能提升性能**

JNI调用本身有开销，对于简单的操作，JNI调用的开销可能超过性能收益。只有计算密集型的操作（如图像处理、音视频编解码）才适合放到Native层。此外Native代码更难调试和维护。

**误区五：CPU优化是一次性工作**

CPU优化需要持续进行。每次版本迭代都可能引入新的CPU消耗（新功能、新动画、新的后台任务），需要通过CI集成性能测试和线上监控来保证优化效果的可持续性。

**结果**：CPU优化的核心是在合适的时机、用合适的线程、做合适的计算。建立完善的CPU监控体系，持续关注CPU使用情况，才能保证应用的流畅和低功耗。


## 08.各端CPU采集伪代码

### 8.1 Android CPU采集

```java
public class AndroidCpuCollector {
    private long lastProcessTime = 0;
    private long lastTotalTime = 0;

    /**
     * 采集当前进程CPU使用率
     * 原理：读取/proc/self/stat获取进程CPU时间，
     *       读取/proc/stat获取系统总CPU时间，
     *       通过两次采样的增量计算使用率
     */
    public float collectCpuUsage() {
        try {
            // 进程CPU时间 = utime + stime
            String procStat = readFile("/proc/self/stat");
            String[] fields = procStat.split("\\s+");
            long utime = Long.parseLong(fields[13]);
            long stime = Long.parseLong(fields[14]);
            long processTime = utime + stime;

            // 系统总CPU时间
            String systemStat = readFirstLine("/proc/stat");
            String[] cpuFields = systemStat.split("\\s+");
            long totalTime = 0;
            for (int i = 1; i <= 7; i++) {
                totalTime += Long.parseLong(cpuFields[i]);
            }

            float usage = 0;
            if (lastProcessTime > 0) {
                long pDelta = processTime - lastProcessTime;
                long tDelta = totalTime - lastTotalTime;
                if (tDelta > 0) {
                    usage = (float) pDelta / tDelta * 100f
                            * Runtime.getRuntime().availableProcessors();
                }
            }
            lastProcessTime = processTime;
            lastTotalTime = totalTime;
            return usage;
        } catch (Exception e) {
            return -1;
        }
    }

    /**
     * 获取各线程CPU使用排名
     * 遍历/proc/self/task/下的所有线程目录
     */
    public List<ThreadCpuInfo> getTopThreads(int topN) {
        List<ThreadCpuInfo> threads = new ArrayList<>();
        File taskDir = new File("/proc/self/task");
        for (File tidDir : taskDir.listFiles()) {
            try {
                String stat = readFile(tidDir.getPath() + "/stat");
                String[] f = stat.split("\\s+");
                String name = f[1].replace("(", "").replace(")", "");
                long cpu = Long.parseLong(f[13]) + Long.parseLong(f[14]);
                threads.add(new ThreadCpuInfo(name, Integer.parseInt(f[0]), cpu));
            } catch (Exception ignored) {}
        }
        threads.sort((a, b) -> Long.compare(b.cpuTime, a.cpuTime));
        return threads.subList(0, Math.min(topN, threads.size()));
    }
}
```

```objectivec
/// 获取当前App的CPU使用率（所有线程累加）
/// 原理：通过Mach API获取进程内所有线程的cpu_usage字段
- (double)collectCpuUsage {
    thread_act_array_t threads;
    mach_msg_type_number_t threadCount = 0;
    
    kern_return_t kr = task_threads(mach_task_self(), &threads, &threadCount);
    if (kr != KERN_SUCCESS) return -1;
    
    double totalUsage = 0;
    for (mach_msg_type_number_t i = 0; i < threadCount; i++) {
        thread_basic_info_data_t info;
        mach_msg_type_number_t infoCount = THREAD_BASIC_INFO_COUNT;
        
        kr = thread_info(threads[i], THREAD_BASIC_INFO,
                        (thread_info_t)&info, &infoCount);
        if (kr == KERN_SUCCESS && !(info.flags & TH_FLAGS_IDLE)) {
            totalUsage += (double)info.cpu_usage / TH_USAGE_SCALE * 100.0;
        }
    }
    
    vm_deallocate(mach_task_self(),
                  (vm_address_t)threads,
                  threadCount * sizeof(thread_t));
    return totalUsage;
}
```

### 8.3 Web CPU采集

```javascript
class WebCpuCollector {
    constructor() {
        this.longTaskDurations = [];
        this._installLongTaskObserver();
    }

    /**
     * Web端无法直接获取CPU使用率
     * 通过以下间接方式评估CPU负载：
     * 1. Long Task API：检测>50ms的主线程阻塞
     * 2. requestAnimationFrame：通过帧间隔评估CPU压力
     * 3. performance.now()：测量代码执行耗时
     */
    _installLongTaskObserver() {
        if ('PerformanceObserver' in window) {
            new PerformanceObserver((list) => {
                for (const entry of list.getEntries()) {
                    this.longTaskDurations.push({
                        duration: entry.duration,
                        startTime: entry.startTime,
                        timestamp: Date.now()
                    });
                }
            }).observe({ type: 'longtask', buffered: true });
        }
    }

    /**
     * 通过rAF帧间隔评估CPU压力
     * 帧间隔越大，说明CPU越繁忙
     */
    measureCpuPressure(durationMs = 1000) {
        return new Promise((resolve) => {
            const intervals = [];
            let lastTime = performance.now();
            let count = 0;

            function tick(now) {
                intervals.push(now - lastTime);
                lastTime = now;
                count++;
                if (now - intervals[0] < durationMs) {
                    requestAnimationFrame(tick);
                } else {
                    const avgInterval = intervals.reduce((a, b) => a + b) / intervals.length;
                    const fps = 1000 / avgInterval;
                    // CPU压力评估：fps越低压力越大
                    resolve({
                        fps: Math.round(fps),
                        avgFrameTime: Math.round(avgInterval * 100) / 100,
                        pressure: fps < 30 ? 'high' : fps < 50 ? 'medium' : 'low',
                        longTaskCount: this.longTaskDurations.length
                    });
                }
            }
            requestAnimationFrame(tick);
        });
    }
}
```
