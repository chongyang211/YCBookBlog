## 01.整体概述说明
### 1.1 项目背景
- 现在几乎所有App都是网络强相关的
    - 客户端展示的很多东西都是通过接口从服务器上获取的，服务器也会接收大量从客户端上传的数据，这两端在进行双向通信的时候，就很容易被第三方截获，导致数据被盗取、接口被盗刷。
- Android项目常见的安全
    - 反编译代码。将jar文件转换成java代码 ，使用jd-gui工具打开classes-dex2jar.jar这个文件就能查看Java代码。
    - dos攻击。DoS 是一种常见的网络攻击，有人也称其为“洪水攻击”。最常见的表现是，利用大量机器发送请求，将目标网站的带宽或者其他资源耗尽，导致其无法响应正常用户的请求。
    - App被挂载。利用xposed攻击apk



### 1.2 思考问题
- 有哪些不安全案例
    - 代码线程安全，尤其多线程，如果不加锁，容易造成数据错误，引发其他问题
    - 业务安全，比如短信登录增加滑块校验，避免网络攻击
    - 代码不规范安全，比如异常日志不要打印重要信息
    - 传输数据安全，尤其是数据在客户端和服务端传输时，有的不序列化，还要保证有的数据不能被捕获。
- 逆向解析app案例
    - 使用xposed工具hook修改代码，反解析app也会造成安全问题，或者使用VA去挂载/双开app也会造成安全问题
- 网络安全问题
    - 密钥破解，导致本地加密数据被盗取；通信密钥破解，导致接口数据被盗取
    - 伪造接口数据上报；接口签名被破解，导致接口可以被重放攻击



### 1.3 常见方式
- 应用安全防御的常见方式可以从多个层面来归类
    - 代码层面：混淆、加固、防调试、防Hook
    - 传输层面：HTTPS、证书锁定（Certificate Pinning）、数据加密
    - 存储层面：敏感数据加密存储、KeyStore/KeyChain安全存储
    - 运行时层面：Root/越狱检测、模拟器检测、调试器检测、Hook框架检测
    - 业务层面：接口签名、防重放攻击、风控策略
- 不同平台的安全防御侧重点
    - Android：防反编译（ProGuard/R8混淆、DEX加固）、防Xposed/Frida Hook、Root检测、签名校验
    - iOS：防越狱、防动态调试（ptrace反调试）、代码签名验证、Keychain安全存储
    - Web：XSS防护、CSRF防护、CSP策略、SRI校验、防止JS注入
- 安全防御的分层思想
    - 安全防御不是单一手段能解决的，需要多层防御（Defense in Depth）。即使某一层被突破，其他层仍然能提供保护。
    - 第一层：传输安全（HTTPS + 证书锁定）
    - 第二层：数据安全（加密存储 + 加密传输）
    - 第三层：代码安全（混淆 + 加固 + 防调试）
    - 第四层：运行环境安全（Root检测 + Hook检测 + 模拟器检测）
    - 第五层：业务安全（接口签名 + 风控 + 行为分析）


### 1.4 设计目标
- 针对SDK安全要求
    - 数据加密：开发者应该采取适当的加密措施，确保敏感数据在储存过程中得到保护。
    - 安全传输：开发者需要规划安全的数据传输方式，如使用 HTTPS 协议来传输敏感数据，以及做好防止抓包或者攻击保护。
    - 数据处理：开发者应该严格控制数据的访问权限，只允许有必要权限的组件对数据进行处理。



### 1.5 收益分析
- 安全防御建设的收益体现在多个维度
    - 直接收益：减少因安全漏洞导致的数据泄露、资产损失、接口被盗刷等问题
    - 合规收益：满足等保要求、GDPR、个人信息保护法等法规要求
    - 品牌收益：减少因安全事故导致的负面舆论和用户信任损失
    - 运营收益：减少因被薅羊毛、刷量等行为导致的运营成本增加
- 安全投入的ROI评估
    - 安全防御的投入成本：开发人力 + 安全工具/服务费用 + 持续维护成本
    - 不投入安全的潜在损失：数据泄露赔偿 + 监管处罚 + 品牌损失 + 业务损失
    - 行业经验表明，安全事故的损失通常是安全投入的10-100倍




## 02.项目安全风险
### 2.1 移动安全有哪些
- App的移动安全主要包括下面几种：
    - 密钥破解，导致本地加密数据被盗取
    - 通信密钥破解，导致接口数据被盗取
    - 伪造接口数据上报
    - 接口签名被破解，导致接口可以被重放攻击
- 那么归结起来，实际上就是这样几种模式：
    - 代码反编译
    - so破解
    - 中间人攻击


### 2.2 反编译安全风险
- 反编译是Android面临的最直接的安全威胁
    - Android应用打包为APK文件，其中的DEX文件可以通过dex2jar等工具转换为Java源码，几乎可以完整还原原始代码逻辑
    - 相比之下，iOS编译为ARM二进制文件，逆向难度更高；Web应用虽然源码可见但通常只有压缩后的代码
    - 反编译后攻击者可以获取：业务逻辑、加密算法、接口地址、密钥信息等敏感内容



### 2.3 so库破解风险
- so库面临的安全威胁主要有以下几种
    - 静态分析：攻击者使用IDA Pro等工具对so文件进行反汇编分析，查看函数逻辑和字符串常量
    - 动态调试：使用GDB或LLDB附加到进程，动态跟踪so中函数的执行流程和参数
    - Hook攻击：通过Frida、Xposed等框架Hook so中的函数，修改参数和返回值
    - 内存Dump：在运行时直接从内存中提取解密后的数据
- so库中的核心风险点
    - 密钥硬编码：将加密密钥直接写在so中，通过strings命令即可提取
    - 算法暴露：加密/签名算法的实现逻辑可以被逆向分析
    - 符号表泄露：未strip的so文件会暴露函数名，降低逆向难度
    - JNI接口暴露：JNI_OnLoad和Java_xxx_xxx函数名暴露了调用关系


### 2.4 中间人攻击风险
- 中间人攻击，在客户端主要是防抓包
    - 通过一些黑科技手段，抓包app的数据。哪怕是https这种安全协议！
- 客户端抓包的突破口集中以下几点
    - 第一点：必须链接代理，且跟Charles要具有相同ip。**思路：客户端是否可以判断网络是否被代理了**。
    - 第二点：CA证书，这一块避免使用黑科技hook证书校验代码，或者拥有修改CA证书权限。**思路：集中在可以判断是否挂载**。
    - 第三点：冒充中间人CA证书，在客户端client和服务端server之间篡改拦截数据。**思路：可以做CA证书校验**。
    - 第四点：为了可以在7.0上抓包，App往往配置清单文件networkSecurityConfig。**思路：线上环境去掉该配置**。



### 2.5 代码安全风险
- 代码安全风险涵盖开发过程中可能引入的安全隐患
    - 日志泄露：Release包中残留Debug日志，输出敏感信息（token、密码、用户数据）
    - 调试接口未关闭：开发环境的调试入口（如WebView的setWebContentsDebuggingEnabled）在生产环境仍然开启
    - 不安全的数据存储：将敏感数据明文存储在SharedPreferences、SQLite或文件中
    - 组件暴露：Activity、Service、BroadcastReceiver、ContentProvider的exported属性配置不当
    - 不安全的WebView：WebView未禁用JavaScript接口注入、file协议访问等风险功能
- 常见的代码安全漏洞类型
    - SQL注入：拼接用户输入构造SQL语句，导致数据泄露或篡改
    - 路径遍历：未校验文件路径，导致攻击者可以读写任意文件
    - 不安全的随机数：使用java.util.Random而非SecureRandom生成安全相关的随机值
    - Intent劫持：隐式Intent可能被恶意应用拦截，导致数据泄露



## 03.一些安全防御实践
### 3.1 本地加密
- 密钥的安全问题
    - 第一种：最低级的，密钥被直接放在Java代码中。
    - 第二种：放在Java代码中，会把密钥拆成几个部分，然后通过一定算法计算合成完整的密钥。
    - 第三种：把密钥和加解密放so中
    - 第四种：so再做下签名校验
- 秘钥及敏感信息
    - 此类配置应当妥善存放，不要在类中硬编码敏感信息，可以使用JNI将敏感信息写到Native层。





### 3.2 proguard混淆
- proguard混淆让代码增加阅读难度
    - 最简单的加密，成本最低，令 APK 难以被逆向工程，增加反编译的成本。而且可以比较有效的扼杀一些在破解边缘徘徊的初级破解者。




### 3.3 接口签名
- 接口上的安全，最基本的保证就是Https，同时对SSL协议的域名进行校验（关键词：X509TrustManager、hostnameVerifier）
    - 在此之上，请求的接口上，我们一般会带上一个签名，或者叫token，这个加密的密钥串，就是我们身份的象征。
    - 一般来说，这个签名也就是通过前面我们千辛万苦要藏好的本地密钥来进行生成的，通常也就是那几个参数，例如时间戳、UserID、IMEI、Mac地址等等进行拼装，然后通过DES、3DES、AES、hmacSHA1等方式进行加密后，再经过Base64进行编码生成的，这些加密过程就不赘述了。



### 3.4 TCP协议安全攻击
- TCP协议层面常见的安全攻击类型
    - SYN Flood攻击：攻击者发送大量SYN包但不完成三次握手，耗尽服务端的半连接队列资源
    - TCP会话劫持：攻击者通过嗅探获取TCP序列号，插入伪造的数据包劫持会话
    - RST攻击：攻击者发送伪造的RST包强制断开TCP连接
    - DNS劫持：通过篡改DNS解析结果，将用户请求重定向到恶意服务器
- 客户端层面的TCP安全防护
    - 使用TLS/SSL加密TCP连接，防止数据被窃听和篡改
    - 实现心跳机制检测连接异常断开
    - 对长连接实施Token认证，防止连接被劫持
    - 配合HTTPDNS绕过运营商DNS劫持
- 防止DoS攻击对客户端的影响
    - 客户端请求增加指数退避重试策略，避免在服务端压力大时雪上加霜
    - 实施请求限频，防止客户端被利用发起DDoS攻击
    - 设置合理的连接超时和读取超时时间



### 3.5 防抓包安全
- 客户端抓包的突破口集中以下几点
    - 第一点：必须链接代理，且跟Charles要具有相同ip。**思路：客户端是否可以判断网络是否被代理了**。
    - 第二点：CA证书，这一块避免使用黑科技hook证书校验代码，或者拥有修改CA证书权限。**思路：集中在可以判断是否挂载**。
    - 第三点：冒充中间人CA证书，在客户端client和服务端server之间篡改拦截数据。**思路：可以做CA证书校验**。
    - 第四点：为了可以在7.0上抓包，App往往配置清单文件networkSecurityConfig。**思路：线上环境去掉该配置**。
- SDK网络安全实践操作
    - 第一种，sdk网络请求默认设置关闭代理【厂商这边也可以通过配置打开支持代理】，避免代理抓包
    - 第二种，设置配置文件，配置networkSecurityConfig清单文件的system和user权限去掉，只有这样才不会信任用户证书。不信任证书，自然增加抓包难度！
    - 第三种，数据加解密，可以保证接口请求安全性！
    - 第四种，sign签名，即使别人拿到token，通过对请求参数md5 + 时间戳，即可最大程度保证安全！该方案，需要跟服务端一起做，待定！
    - 第五种，CA证书校验，可以有效防止抓包，保证数据安全



### 3.6 so库加固检测
- 先说一下so库的风险点
    - So文件为APK中包含的动态链接库文件，Android利用NDK技术将C/C++语言实现的核心代码编译为So库文件供Java层调用。
    - So文件被破解可能导致应用的核心功能代码和算法泄露。攻击者利用核心功能与算法可轻易抓取到客户端的敏感数据，并对其解密，导致用户的隐私泄露或直接财产损失。
- 解决方案
    - 由于release签名的唯一性，可以考虑在native层进行签名的校验。如果签名不正确，直接让App crash。https://juejin.cn/post/6844903609197395976?searchId=20231030192753CFCCAB7732D5AC0A58BB#heading-3
    - 对so文件进行安全加固、可以使用第三方的安全平台so加固方案。



### 3.7 截屏录屏
- 先说一下截屏攻击风险
    - 截屏攻击是指在APP运行过程中，界面被监控并且截屏或者录屏。截屏攻击主要发生在APP登录、身份认证、资金操作等界面。
    - Android5.0中增加了一个MediaProjection接口，它提供截屏或者录屏的服务，准许APP拥有截取屏幕或者记录系统音频的能力。
    - 同时系统允许其他消息窗口覆盖在系统的录制提示上，从而在用户无感知的情况下启动录屏或者截屏工具。
- 解决方案
    - 在Activity的create()方法中调用：getWindow().setFlags(LayoutParams.FLAG_SECURE, LayoutParams.FLAG_SECURE)；
    - 或者getWindow().addFlags(WindowManager.LayoutParams.FLAG_SECURE);来达到防止截屏攻击的目的。




## 04.代码安全例子
### 4.1 条件判断代码
- 首先，我们一起来看一段不起眼的条件判断代码，这里可能有什么问题吗？你可能会纳闷，这是再常见不过的一个条件判断了，能有什么安全隐患？
    ```
    // a, b, c 都是 int 类型的数值
    if (a + b < c) {
        // …
    }
    ```
    - 这里的隐患是数值类型需要防范溢出，否则这不仅仅可能会带来逻辑错误，在特定情况下可能导致严重的安全漏洞。
    - 从语言特性来说，Java 和 JVM 提供了很多基础性的改进，相比于传统的 C、C++等语言，对于数组越界等处理要完善的多，原生的避免了缓冲区溢出等攻击方式，提高了软件的安全性。但这并不代表完全杜绝了问题，Java 程序可能调用本地代码，也就是JNI 技术，错误的数值可能导致 C/C++ 层面的数据越界等问题，这是很危险的。
- 所以，上面的条件判断，需要判断其数值范围，例如，写成类似下面结构。
    ```
    if (a < c – b)
    ```


### 4.2 异常不要携带重要信息
- 再来看一个例子，请看下面的一段异常处理代码：
    ```
    try {
        // 业务代码
    } catch (Exception e) {
        throw new RuntimeException(hostname + port + “ doesn’t response”);
    }
    ```
    - 这段代码将敏感信息包含在异常消息中，试想，如果是一个应用，异常也没有良好的包装起来，很有可能就把内部信息暴露给终端客户。
    - 对于安全标准特别高的系统，甚至可能要求敏感信息被使用后，要立即明确在内存中销毁，以免被探测；或者避免在发生 core dump 时，意外暴露。



### 4.3 序列化安全问题
- Java 提供了序列化等创新的特性，广泛使用在远程调用等方面，但也带来了复杂的安全问题。直到今天，序列化仍然是个安全问题频发的场景，通常建议：
    - 敏感信息不要被序列化！在编码中，建议使用 transient 关键字将其保护起来。
    - 反序列化中，建议在 readObject 中实现与对象构件过程相同的安全检查和数据检查。
- 另外，在 JDK 9 中，Java引入了过滤器机制，以保证反序列化过程中数据都要经过基本验证才可以使用。
    - 其原理是通过黑名单和白名单，限定安全或者不安全的类型，并且你可以进行定制，然后通过环境变量灵活进行配置，会更加具体的使用你可以参考 ObjectInputFilter。



### 4.4 三方库lib中类安全
- 看到很多第三方库，比如gson，rxJava等库，几乎大多数类都是用finial修饰的。这个是为什么呢？
- 当用final修饰一个类时，表明这个类不能被继承。也就是说，如果一个类你永远不会让他被继承，就可以用final进行修饰。final类中的成员变量可以根据需要设为final，但是要注意final类中的所有成员方法都会被隐式地指定为final方法。
- 很多类，不想被开发者继承，为了内部安全。同时也避免反射攻击，所以就用finial修饰。这也是一种保证类安全的有效做法。


### 4.6 扫描漏洞安全
- Activity 组件对外暴露风险
    - Activity 组件对外暴露，且未做权限控制，可能会造成信息泄露、劫持利用、拒绝服务等风险。
- 漏洞位置
    ```
    <activity android:name="com.yc.library.web.WebViewActivity"
        android:exported="true"/>
    ```
- 修复建议
    - 如果应用的 Activity 组件不必要对外，或者组件配置了intent filter标签，建议显示设置组件的'android:exported'属性为'false'；
    - 如果组件必须要提供给外部应用使用，建议对组件进行权限控制。
    - android:exported 是Android中的四大组件 Activity，Service，Provider，Receiver 四大组件中都会有的一个属性。总体来说它的主要作用是：是否支持其它应用调用当前组件。
- 如果 android:exported="true" 无法修改，那么可以增加权限处理
    ```
    <uses-permission android:name="${applicationId}.permission.WEB_ACTIVITY" />
    
    <activity android:name="com.yc.library.web.WebViewActivity"
        android:permission="${applicationId}.permission.WEB_ACTIVITY"
        android:exported="true"/>
    ```
- 公共组件安全风险提示说明
    - Activity、Service、Provider、Receiver四大组件若配置为android:exported =”true”，将可以被外部应用调用，这样存在安全隐患的风险。
- 解决方案
    - 在应用的AndroidManifest.xml文件中，设置组件的android:exported 属性为false或者通过设置自定义权限来限制对这些组件的访问。
    - 值得一提的是，若部分功能使用前提是配置必须使用exported为true，这种情况开发者应该根据实际情况来进行集成。



### 4.7 硬编码安全
- 1、密钥直接明文存在SharedPreferences文件中，这是最不安全的。
- 2、密钥直接硬编码在Java代码中，这很不安全，dex文件很容易被逆向成java代码。
- 3、将密钥分成不同的几段，有的存储在文件中、有的存储在代码中，最后将他们拼接起来，可以将整个操作写的很复杂，这因为还是在java层，逆向者只要花点时间，也很容易被逆向。
- 4、用ndk开发，将密钥放在so文件，加密解密操作都在so文件里，这从一定程度上提高了的安全性，挡住了一些逆向者，但是有经验的逆向者还是会使用IDA破解的。
- 5、在so文件中不存储密钥，so文件中对密钥进行加解密操作，将密钥加密后的密钥命名为其他普通文件，存放在assets目录下或者其他目录下，接着在so文件里面添加无关代码（花指令），虽然可以增加静态分析难度，但是可以使用动态调式的方法，追踪加密解密函数，也可以查找到密钥内容。
- https://juejin.cn/post/6844903432499773448?searchId=20231030192753CFCCAB7732D5AC0A58BB




### 4.9 作弊器攻击问题
- 作弊器攻击是指通过外部工具修改App的运行行为
    - 游戏修改器：如GameGuardian，通过内存搜索和修改来篡改游戏数值
    - 自动化脚本：如Auto.js、按键精灵，模拟用户操作实现自动刷量、抢购等
    - 虚拟定位：修改GPS定位信息，影响基于地理位置的业务（如打卡、外卖、出行）
    - 改机工具：篡改设备信息（IMEI、MAC地址、设备型号等），绕过设备维度的风控策略
- 作弊器的检测思路
    - 内存检测：检测是否有外部进程在读写当前App的内存空间
    - 辅助服务检测：检测是否有可疑的AccessibilityService在运行
    - 位置校验：GPS定位与基站定位、WiFi定位交叉验证，检测虚拟定位
    - 设备指纹：采集多维度设备特征生成唯一指纹，检测改机行为
    - 行为分析：通过用户操作的时间间隔、触摸轨迹等特征识别非人类操作

```java
// 虚拟定位检测示例
public class MockLocationDetector {
    
    public static boolean isMockLocationEnabled(Context context, Location location) {
        // 方法1：检查Location对象的mock标志（Android 18+）
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.JELLY_BEAN_MR2) {
            if (location.isFromMockProvider()) {
                return true;
            }
        }
        
        // 方法2：检查是否开启了模拟位置权限
        if (Build.VERSION.SDK_INT < Build.VERSION_CODES.M) {
            String mockLocation = Settings.Secure.getString(
                context.getContentResolver(),
                Settings.Secure.ALLOW_MOCK_LOCATION);
            return "1".equals(mockLocation);
        }
        
        // 方法3：检测已知的虚拟定位App
        return checkMockLocationApps(context);
    }
    
    private static boolean checkMockLocationApps(Context context) {
        PackageManager pm = context.getPackageManager();
        List<ApplicationInfo> apps = pm.getInstalledApplications(0);
        for (ApplicationInfo app : apps) {
            try {
                if (pm.checkPermission(
                    "android.permission.ACCESS_MOCK_LOCATION",
                    app.packageName) == PackageManager.PERMISSION_GRANTED) {
                    return true;
                }
            } catch (Exception ignored) {}
        }
        return false;
    }
}
```



## 05.安全防御进阶实践
### 5.1 数据传输安全
- 数据传输安全是应用安全的核心环节
    - 所有网络通信必须使用HTTPS，禁止任何明文HTTP传输
    - 仅仅使用HTTPS是不够的，还需要实施证书锁定（Certificate Pinning）防止中间人攻击
    - 对于高度敏感的数据（如支付信息），在HTTPS基础上还需要应用层加密
- 证书锁定的实现方式

```java
// OkHttp证书锁定实现
OkHttpClient client = new OkHttpClient.Builder()
    .certificatePinner(new CertificatePinner.Builder()
        .add("api.example.com", 
             "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
        .add("api.example.com", 
             "sha256/BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB=")
        .build())
    .build();
```

- 应用层数据加密策略
    - 对称加密（AES-256-GCM）用于大数据量的加密传输
    - 非对称加密（RSA-2048/ECDH）用于密钥协商
    - 混合加密模式：用RSA加密AES密钥，用AES加密业务数据
    - 密钥轮换机制：定期更换加密密钥，降低密钥泄露的影响范围


### 5.2 本地存储安全
- 本地存储安全是防止数据在设备端被窃取的关键
    - SharedPreferences中的敏感数据必须加密存储
    - SQLite数据库可使用SQLCipher进行整库加密
    - 文件存储使用EncryptedFile（Jetpack Security库）
    - iOS端使用Keychain存储敏感凭证
- Android Keystore和iOS Keychain的使用

```java
// Android使用EncryptedSharedPreferences存储敏感数据
public class SecureStorage {
    private SharedPreferences securePrefs;
    
    public SecureStorage(Context context) throws Exception {
        MasterKey masterKey = new MasterKey.Builder(context)
            .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
            .build();
            
        securePrefs = EncryptedSharedPreferences.create(
            context,
            "secure_prefs",
            masterKey,
            EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
            EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
        );
    }
    
    public void saveToken(String token) {
        securePrefs.edit().putString("auth_token", token).apply();
    }
    
    public String getToken() {
        return securePrefs.getString("auth_token", null);
    }
}
```

- 不安全存储的常见问题
    - 明文存储密码和token
    - 将敏感信息写入日志文件
    - 备份文件中包含敏感数据（android:allowBackup="true"）
    - 临时文件未及时删除


### 5.3 运行环境检测
- 运行环境检测用于识别不安全的运行环境
    - Root/越狱检测：在Root/越狱环境下，应用的沙箱保护机制被破坏
    - 模拟器检测：模拟器环境通常用于自动化攻击和批量注册
    - Hook框架检测：Xposed/Frida等Hook框架可以修改应用运行时行为
    - 多开/分身检测：VirtualApp等分身应用可以绕过设备唯一性限制

```java
// Root检测综合方案
public class RootDetector {
    
    public static boolean isDeviceRooted() {
        return checkRootFiles() || checkSuBinary() || checkRootProperties();
    }
    
    // 检查常见的Root文件
    private static boolean checkRootFiles() {
        String[] rootPaths = {
            "/system/app/Superuser.apk",
            "/system/xbin/su",
            "/system/bin/su",
            "/sbin/su",
            "/data/local/xbin/su",
            "/data/local/bin/su"
        };
        for (String path : rootPaths) {
            if (new File(path).exists()) return true;
        }
        return false;
    }
    
    // 检查su命令是否可执行
    private static boolean checkSuBinary() {
        try {
            Process process = Runtime.getRuntime().exec(new String[]{"which", "su"});
            BufferedReader reader = new BufferedReader(
                new InputStreamReader(process.getInputStream()));
            return reader.readLine() != null;
        } catch (Exception e) {
            return false;
        }
    }
    
    // 检查系统属性
    private static boolean checkRootProperties() {
        try {
            String buildTags = Build.TAGS;
            return buildTags != null && buildTags.contains("test-keys");
        } catch (Exception e) {
            return false;
        }
    }
}
```

- Frida检测方案
    - 端口检测：检查Frida默认端口（27042）是否被监听
    - 进程检测：检查是否存在frida-server进程
    - 内存特征检测：扫描内存中是否存在Frida特征字符串
    - 注意：检测和反检测是一个持续对抗的过程，没有一劳永逸的方案


### 5.4 代码完整性校验
- 代码完整性校验用于防止应用被篡改和重打包
    - 签名校验：在运行时验证APK/IPA的签名是否合法
    - DEX文件校验：计算DEX文件的哈希值并与预设值比对
    - so文件校验：验证关键so库的完整性
    - 资源文件校验：防止资源被替换（如广告劫持替换资源文件）

```java
// APK签名校验
public class SignatureVerifier {
    private static final String EXPECTED_SIGNATURE = "预期的签名哈希值";
    
    public static boolean verifySignature(Context context) {
        try {
            PackageInfo packageInfo = context.getPackageManager()
                .getPackageInfo(context.getPackageName(), 
                    PackageManager.GET_SIGNATURES);
            Signature[] signatures = packageInfo.signatures;
            
            MessageDigest md = MessageDigest.getInstance("SHA-256");
            md.update(signatures[0].toByteArray());
            String currentSignature = Base64.encodeToString(
                md.digest(), Base64.NO_WRAP);
            
            return EXPECTED_SIGNATURE.equals(currentSignature);
        } catch (Exception e) {
            return false;
        }
    }
}
```


### 5.5 动态防护策略
- 静态防护容易被绕过，动态防护增加对抗强度
    - 代码动态化：将关键算法通过服务端下发执行，避免被静态分析
    - 运行时自检：应用运行过程中定期检查自身完整性和运行环境
    - 蜜罐机制：设置虚假的敏感数据，当这些数据被访问时触发告警
    - 行为混淆：关键函数的控制流混淆，增加动态调试难度
- 安全响应机制
    - 当检测到安全威胁时的响应策略需要根据威胁等级来决定：
    - 低威胁（模拟器、Root）：记录并上报，根据业务需求决定是否限制功能
    - 中威胁（Hook检测、签名异常）：限制敏感功能（支付、账号操作），强制重新认证
    - 高威胁（确认被篡改）：退出应用，清除本地敏感数据，上报安全事件





## 08.安全防御设计总结

### 8.1 安全防御核心原则

**原则一：纵深防御（Defense in Depth）**

不依赖单一安全措施，在多个层面建立安全防线。传输层（HTTPS+证书锁定）、存储层（加密存储）、代码层（混淆+加固）、运行时层（环境检测）、业务层（签名+风控），任何一层被突破不会导致全面失守。

**原则二：最小权限原则**

应用只请求必要的权限，组件只暴露必要的接口。减少攻击面是最有效的安全策略：
- 组件默认exported=false，仅在必要时开放
- 权限按需申请，拒绝一次性申请全部权限
- 数据按需获取，不过度收集用户信息

**原则三：安全左移**

将安全工作前置到开发阶段，而不是上线后亡羊补牢：
- 需求阶段：安全评审，识别敏感数据和风险场景
- 开发阶段：安全编码规范，代码审计工具集成
- 测试阶段：安全测试（渗透测试、漏洞扫描）
- 发布阶段：安全签名、加固处理

**原则四：持续对抗**

安全是攻防对抗的过程，没有一劳永逸的方案。需要持续关注新的攻击手法和漏洞，及时更新防御策略。

### 8.2 跨平台安全对比

**疑惑**：不同平台在安全防御上有什么差异？移动端、Web端、后端分别面临怎样的安全挑战？

**答疑**：各平台由于技术架构不同，面临的安全威胁和可用的防御手段存在明显差异。

**论证**：

| 维度 | Android | iOS | Web |
|------|---------|-----|-----|
| 代码保护 | ProGuard/R8混淆+加固 | LLVM混淆+Bitcode | 代码压缩+混淆 |
| 沙箱安全 | Root可突破 | 越狱可突破 | 同源策略保护 |
| 存储安全 | Keystore+加密SP | Keychain | localStorage(不安全) |
| 逆向难度 | 较低(Java字节码) | 中等(ARM二进制) | 极低(源码可见) |
| Hook风险 | Xposed/Frida | Cydia Substrate | 浏览器DevTools |
| 主要威胁 | 反编译/重打包 | 越狱+动态调试 | XSS/CSRF/注入 |
| 发布审核 | 无强制审核 | AppStore严格审核 | 无审核 |

**iOS安全防御特点**：

import Security

class KeychainHelper {
    static func save(key: String, data: Data) -> Bool {
        let query: [String: Any] = [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrAccount as String: key,
            kSecValueData as String: data,
            kSecAttrAccessible as String: 
                kSecAttrAccessibleWhenUnlockedThisDeviceOnly
        ]
        SecItemDelete(query as CFDictionary)
        let status = SecItemAdd(query as CFDictionary, nil)
        return status == errSecSuccess
    }
    
    // 越狱检测
    static func isJailbroken() -> Bool {
        // 检查越狱文件
        let jailbreakPaths = [
            "/Applications/Cydia.app",
            "/Library/MobileSubstrate/MobileSubstrate.dylib",
            "/usr/sbin/sshd",
            "/etc/apt",
            "/private/var/lib/apt/"
        ]
        for path in jailbreakPaths {
            if FileManager.default.fileExists(atPath: path) {
                return true
            }
        }
        // 检查是否能写入系统目录
        let testPath = "/private/jailbreak_test.txt"
        do {
            try "test".write(toFile: testPath, atomically: true, 
                           encoding: .utf8)
            try FileManager.default.removeItem(atPath: testPath)
            return true
        } catch {
            return false
        }
    }
}

### 8.3 安全防御方法论

安全防御建设遵循"评估-防护-检测-响应"四阶段方法论：

**第一阶段：安全评估**
1. 资产梳理：识别应用中的敏感数据和关键功能
2. 威胁建模：分析可能的攻击场景和攻击路径
3. 风险评级：根据威胁影响和发生概率评估风险等级
4. 基线制定：确定各安全维度的最低要求

**第二阶段：安全防护**
1. 代码安全：混淆、加固、安全编码规范
2. 传输安全：HTTPS、证书锁定、应用层加密
3. 存储安全：加密存储、敏感数据保护
4. 运行安全：环境检测、防调试、完整性校验

**第三阶段：安全检测**
1. 静态扫描：CI集成安全扫描工具
2. 动态测试：定期渗透测试
3. 运行监控：安全事件实时上报
4. 漏洞跟踪：关注CVE和安全公告

**第四阶段：安全响应**
1. 事件分级：根据影响范围和严重程度分级
2. 快速修复：安全漏洞优先修复
3. 通报机制：安全事件及时通报利益相关方
4. 经验沉淀：安全事件归档和复盘

### 8.4 安全防御常见误区

**疑惑**：应用安全防御中有哪些常见的误区？

**答疑**：安全防御实践中，很多团队容易陷入以下误区。

**论证**：

**误区一：HTTPS就等于安全**

HTTPS只是保证传输通道的安全（防窃听、防篡改），但无法防止中间人攻击（如用户安装了恶意根证书）。需要配合证书锁定（Certificate Pinning）才能有效防止中间人攻击。同时HTTPS不能解决应用层的安全问题，如接口参数被伪造。

**误区二：代码混淆就能防止逆向**

混淆只是增加了逆向的成本和难度，并不能完全阻止逆向。有经验的逆向工程师可以通过动态调试、Hook等手段绕过混淆。混淆应该作为多层防御中的一层，而不是唯一的代码保护手段。

**误区三：将密钥硬编码在代码中**

无论是放在Java代码中还是so文件中，硬编码的密钥都可能被提取。正确的做法是使用平台提供的安全存储（Android Keystore/iOS Keychain），或者通过密钥协商协议动态获取密钥。

**误区四：安全检测做得越多越好**

过多的安全检测会影响应用性能和用户体验。例如在Root手机上直接禁止使用应用会影响开发者和技术用户的体验。安全策略应该与业务场景匹配：金融类应用可以严格限制，工具类应用可以适当放宽。

**误区五：忽略第三方SDK的安全风险**

很多应用引入了大量第三方SDK，但对SDK的安全性缺乏评估。SDK可能会收集过多的用户数据、包含已知漏洞、或者在后台执行不当操作。建议建立SDK准入评审机制，定期审计已接入SDK的安全性。

**结果**：安全防御需要在安全性和用户体验之间寻找平衡。过度安全会影响用户体验和开发效率，安全不足又会面临被攻击的风险。根据应用的业务特点和安全等级要求，制定合适的安全策略是关键。


## 07.跨平台安全防御对比

### 7.1 各平台安全机制

| 安全维度 | Android | iOS | Web |
|---------|---------|-----|-----|
| 代码保护 | ProGuard/R8混淆+so加固 | Bitcode+Swift编译优化 | 代码混淆+Source Map分离 |
| 数据存储 | Android Keystore+加密SP | Keychain+Data Protection | Crypto API+HttpOnly Cookie |
| 网络安全 | Certificate Pinning+TLS1.3 | ATS(App Transport Security) | HSTS+CSP+SRI |
| 运行时保护 | Root检测+完整性校验 | 越狱检测+代码签名 | XSS防御+CSRF Token |
| 权限管理 | 运行时权限+Scoped Storage | Privacy框架+Photo Picker | Permission API+沙箱 |
| 反调试 | ptrace检测+isDebuggerConnected | sysctl检测+ptrace deny | DevTools检测(有限) |
| 安全通信 | 接口签名+请求防重放 | 接口签名+Certificate Pinning | JWT+CORS+HTTPS |

### 7.2 安全防御技术演进

| 阶段 | 时期 | 核心防御 | 攻击手段演进 |
|------|------|---------|-------------|
| 基础防御 | 2012前 | HTTPS+混淆 | 静态反编译+抓包 |
| 加固时代 | 2012-2016 | 壳加固+SO加密 | 动态调试+Hook |
| 主动防御 | 2016-2020 | 运行时检测+行为分析 | Frida/Xposed框架 |
| 智能防御 | 2020至今 | AI风控+设备指纹+端安全 | AI辅助逆向+自动化攻击 |
