## 01.程序卡顿概念

### 1.1 卡顿的概念
- 卡顿是指应用程序在运行过程中出现的响应延迟或画面不流畅现象
    - 从用户感知角度：点击按钮后没有立即响应、列表滑动不流畅、页面切换动画卡顿、输入文字后延迟显示
    - 从技术角度：主线程被耗时操作阻塞，无法在规定时间内完成一帧的渲染或事件的处理
    - 卡顿的本质是主线程的消息处理速度跟不上消息产生的速度，导致消息队列积压
- 卡顿与ANR的关系
    - 卡顿是一个广泛的概念，包括轻微的掉帧（几十毫秒的延迟）到严重的冻帧（几百毫秒甚至几秒的无响应）
    - ANR（Application Not Responding）是Android系统对卡顿的一种极端处理机制
    - 当主线程在规定时间内没有完成特定操作时，系统会弹出ANR对话框
    - ANR的触发阈值：输入事件5秒、广播接收器10秒、Service前台20秒/后台200秒
    - 卡顿是ANR的前兆，治理卡顿可以有效预防ANR

### 1.2 为什么会卡顿
- 卡顿的根本原因是主线程被阻塞或负载过重
    - Android/iOS的UI框架都采用单线程模型：所有UI操作必须在主线程执行
    - 任何在主线程上执行时间过长的操作都会导致UI更新被延迟
    - 16ms是60fps屏幕的帧预算，超过这个时间就会掉帧
- 常见的卡顿原因分类
    - CPU密集型操作：复杂的计算、JSON解析、图片处理、大量对象创建
    - IO操作：文件读写、SharedPreferences操作、数据库查询、网络请求
    - 锁竞争：主线程等待子线程持有的锁、死锁、synchronized过度使用
    - 布局渲染：布局层级过深导致Measure/Layout耗时长、过度绘制、频繁触发requestLayout
    - 内存问题：频繁GC（垃圾回收）导致Stop-the-world暂停、内存不足导致内存回收
    - 系统资源竞争：CPU被其他进程/线程抢占、IO带宽不足、低电量模式下CPU降频
- 卡顿原因的排查思路
    - 首先确认卡顿发生在哪个线程：是主线程耗时还是主线程等待
    - 如果是主线程耗时：通过堆栈采样定位耗时方法
    - 如果是主线程等待：检查锁竞争、Binder调用、IO阻塞等情况
    - 如果是系统原因：检查CPU调度、内存压力、温控降频等外部因素

### 1.3 卡顿的分类
- 按照卡顿的严重程度分类

| 等级 | 名称 | 耗时范围 | 用户感知 | 处理优先级 |
|------|------|---------|---------|-----------|
| Level 1 | 轻微掉帧 | 17ms-50ms | 几乎无感知 | 低 |
| Level 2 | 明显卡顿 | 50ms-200ms | 能感觉到卡顿 | 中 |
| Level 3 | 严重卡顿 | 200ms-700ms | 明显卡住 | 高 |
| Level 4 | 冻帧 | >700ms | 界面冻结感 | 紧急 |
| Level 5 | ANR | >5s(输入事件) | 系统弹框 | 最高 |

- 按照卡顿的发生场景分类
    - 启动卡顿：应用冷启动、温启动时的白屏或黑屏时间过长
    - 滑动卡顿：列表滑动、页面滚动时的掉帧
    - 切换卡顿：页面切换、Tab切换时的动画不流畅
    - 交互卡顿：点击、长按、输入等用户操作后的响应延迟
    - 后台返回卡顿：从后台切回前台时的恢复延迟
- 按照卡顿的触发条件分类
    - 必现卡顿：每次操作都会触发，通常是逻辑问题，容易排查
    - 概率性卡顿：受设备性能、系统负载、数据量等因素影响，需要大量数据分析
    - 积累性卡顿：随使用时间增长逐渐恶化（内存泄漏、缓存增长），需要长时间监控

### 1.4 卡顿对用户的影响
- 卡顿是用户流失的重要原因之一
    - Google研究表明：53%的用户会放弃加载时间超过3秒的应用
    - Android Vitals数据显示：卡顿率高的应用，用户卸载率是正常应用的2-3倍
    - 应用商店评分：卡顿相关的差评占所有性能类差评的40%以上
- 卡顿对不同类型应用的影响差异
    - 电商应用：商品列表滑动卡顿直接影响浏览效率，降低转化率
    - 社交应用：聊天列表和朋友圈滑动卡顿影响用户粘性
    - 视频应用：视频列表滑动卡顿和播放控制延迟影响观看体验
    - 游戏应用：操作响应延迟直接影响游戏体验和竞技公平性

### 1.5 卡顿治理目标
- 卡顿治理的量化目标

| 指标 | 目标值 | 说明 |
|------|-------|------|
| 帧率(FPS) | ≥55fps | 核心页面的滑动帧率 |
| 掉帧率 | <5% | 掉帧帧数/总帧数 |
| 冻帧率 | <0.1% | >700ms帧占比 |
| ANR率 | <0.05% | ANR次数/UV |
| P95帧时间 | <20ms | 95%的帧在20ms内完成 |
| 卡顿率 | <3% | 存在明显卡顿的会话占比 |

- 卡顿治理的分阶段策略
    - 第一阶段（止血）：治理ANR和冻帧，消除最严重的卡顿问题
    - 第二阶段（优化）：降低掉帧率，提升核心页面的帧率
    - 第三阶段（防劣化）：建立卡顿监控体系，防止新代码引入卡顿
    - 第四阶段（精细化）：针对不同机型、场景、用户群体进行差异化优化


## 02.卡顿监听方案

### 2.1 帧率监控
- 帧率监控是最直观的卡顿检测方式
    - 通过Choreographer.FrameCallback获取每帧回调的时间戳
    - 计算相邻帧之间的时间差（帧时间），统计帧率
    - 帧时间超过16.67ms（60Hz）表示发生了掉帧
- 帧率监控的优缺点
    - 优点：实现简单，性能开销小，能反映渲染流畅度
    - 优点：可以精确计算帧率和掉帧次数
    - 缺点：只能检测到渲染阶段的卡顿，无法检测非渲染阶段的主线程卡顿
    - 缺点：无法直接获取卡顿的堆栈信息，需要配合堆栈采样
    - 缺点：帧回调本身有一定的精度限制（依赖VSync信号的精度）
- 帧率监控适用的场景
    - 列表滑动场景的流畅度评估
    - 动画执行过程的帧率监控
    - 页面渲染性能的持续跟踪
    - 不适合检测非渲染场景的卡顿（如点击响应延迟）

### 2.2 事件循环监控
- 事件循环监控利用Android消息机制的特性来检测卡顿
    - Android的主线程运行在一个Looper消息循环中
    - 每个Message的dispatch前后，Looper会通过Printer打印日志
    - 通过设置Looper.setMessageLogging()可以截获这些日志
    - 计算dispatch前后的时间差，即可得到单个Message的处理时间
- 事件循环监控的原理
    - Looper.loop()的核心代码中，在msg.target.dispatchMessage(msg)前后会调用Printer
    - dispatch前打印 `>>>>> Dispatching to Handler ...`
    - dispatch后打印 `<<<<< Finished to Handler ...`
    - 通过这两行日志的时间差即可获得Message处理耗时
- 事件循环监控的优缺点
    - 优点：可以检测所有在主线程消息循环中执行的耗时操作
    - 优点：不仅限于渲染卡顿，还能检测IO、计算等导致的卡顿
    - 优点：可以获取到具体的Handler和Message类型信息
    - 缺点：Printer.println()调用本身有性能开销（字符串拼接）
    - 缺点：系统Looper的Printer可能被其他组件覆盖
    - 缺点：对于通过反射或其他非标准方式执行的主线程操作无法检测

### 2.3 执行耗时监控
- 执行耗时监控通过函数插桩（AOP）来检测耗时方法
    - 在编译期通过ASM/AspectJ在目标方法的入口和出口插入计时代码
    - 运行时记录每个方法的执行时间
    - 超过阈值的方法触发告警
- 执行耗时监控的方案
    - 编译期插桩：使用Gradle Plugin + ASM，在字节码层面插入计时代码
    - 运行时插桩：使用Debug.startMethodTracing()进行方法级别的追踪
    - Systrace标记：在关键方法中添加Trace.beginSection()/endSection()标记
- 执行耗时监控的优缺点
    - 优点：可以精确定位到具体的耗时方法
    - 优点：不依赖消息循环，可以检测任何线程上的耗时操作
    - 缺点：编译期插桩会增大包体积（每个方法增加若干字节码指令）
    - 缺点：方法级别的计时有精度问题（System.nanoTime()的开销）
    - 缺点：全量插桩的性能开销不可忽视，通常需要配置白名单/黑名单

### 2.4 渲染性能监控
- 渲染性能监控专注于渲染流水线各阶段的耗时
    - FrameMetrics API（Android 7.0+）可以获取每帧各阶段的精确耗时
    - 包括：UNKNOWN_DELAY、INPUT_HANDLING、ANIMATION、LAYOUT_MEASURE、DRAW、SYNC、COMMAND_ISSUE、SWAP_BUFFERS、TOTAL_DURATION
    - 可以精确判断卡顿发生在渲染的哪个阶段
- 渲染性能监控的优缺点
    - 优点：可以精确到渲染流水线的每个阶段
    - 优点：是系统原生API，数据准确可靠
    - 优点：对应用性能的影响极小
    - 缺点：只支持Android 7.0+
    - 缺点：只能监控渲染相关的卡顿，非渲染卡顿无法检测
    - 缺点：无法获取卡顿时的方法堆栈信息

### 2.5 监听方案对比
- 四种监控方案的综合对比

| 维度 | 帧率监控 | 事件循环监控 | 执行耗时监控 | 渲染性能监控 |
|------|---------|------------|------------|------------|
| 监控范围 | 渲染卡顿 | 主线程所有操作 | 指定方法 | 渲染流水线 |
| 实现复杂度 | 低 | 低 | 高 | 低 |
| 性能开销 | 很低 | 低-中 | 中-高 | 很低 |
| 定位精度 | 帧级别 | 消息级别 | 方法级别 | 阶段级别 |
| 堆栈信息 | 需配合采样 | 需配合采样 | 自带 | 无 |
| 最低API | 16 | 1 | 编译期 | 24 |
| 适用场景 | 滑动/动画 | 通用 | 精确定位 | 渲染分析 |

- 推荐的组合方案
    - 线上环境：帧率监控 + 事件循环监控 + 异步堆栈采样
    - 线下环境：全部四种方案配合使用，获取最完整的卡顿信息
    - 帧率监控作为核心指标，事件循环监控作为卡顿捕获手段，堆栈采样提供定位能力


## 03.卡顿监听实践

### 3.1 方案敲定和选择
- 选择卡顿监控方案需要考虑的因素
    - 目标场景：是否只关注渲染卡顿，还是需要覆盖所有主线程卡顿
    - 性能预算：监控本身的CPU/内存开销不能影响应用性能
    - 线上/线下：线上环境对性能开销更敏感，线下可以使用更重的工具
    - 堆栈需求：是否需要获取卡顿时的方法堆栈用于问题定位
    - 兼容性：需要支持的最低Android API版本
- 推荐的线上卡顿监控架构
    - 核心层：基于事件循环监控（Looper Printer）检测卡顿
    - 帧率层：基于Choreographer帧回调统计帧率指标
    - 采样层：独立线程定期采样主线程堆栈
    - 上报层：卡顿数据聚合、采样、上报

### 3.2 监控帧率实践
- 基于Choreographer的帧率监控实现

```java
/**
 * 帧率监控器
 * 基于Choreographer.FrameCallback实现
 */
public class FPSMonitor implements Choreographer.FrameCallback {
    private static final long ONE_SECOND_NS = 1_000_000_000L;
    private static final long FRAME_INTERVAL_NS = 16_666_667L; // 16.67ms
    
    private long lastFrameTimeNanos = 0;
    private int frameCount = 0;
    private long periodStartNanos = 0;
    private boolean isRunning = false;
    
    // 帧率回调接口
    public interface FPSCallback {
        void onFPSUpdate(float fps, int droppedFrames);
    }
    
    private FPSCallback callback;
    
    public FPSMonitor(FPSCallback callback) {
        this.callback = callback;
    }
    
    public void start() {
        if (isRunning) return;
        isRunning = true;
        lastFrameTimeNanos = System.nanoTime();
        periodStartNanos = lastFrameTimeNanos;
        frameCount = 0;
        Choreographer.getInstance().postFrameCallback(this);
    }
    
    public void stop() {
        isRunning = false;
    }
    
    @Override
    public void doFrame(long frameTimeNanos) {
        if (!isRunning) return;
        
        // 计算帧间隔
        long frameDuration = frameTimeNanos - lastFrameTimeNanos;
        frameCount++;
        
        // 检测掉帧（超过2帧间隔认为掉帧）
        if (frameDuration > FRAME_INTERVAL_NS * 2) {
            int droppedFrames = (int) (frameDuration / FRAME_INTERVAL_NS) - 1;
            onFrameDropped(droppedFrames, frameDuration);
        }
        
        // 每秒计算一次帧率
        long elapsed = frameTimeNanos - periodStartNanos;
        if (elapsed >= ONE_SECOND_NS) {
            float fps = frameCount * 1e9f / elapsed;
            if (callback != null) {
                callback.onFPSUpdate(fps, 0);
            }
            frameCount = 0;
            periodStartNanos = frameTimeNanos;
        }
        
        lastFrameTimeNanos = frameTimeNanos;
        Choreographer.getInstance().postFrameCallback(this);
    }
    
    private void onFrameDropped(int droppedFrames, long durationNanos) {
        float durationMs = durationNanos / 1e6f;
        // 根据掉帧程度分级处理
        if (durationMs > 700) {
            // 冻帧级别：需要紧急处理
            reportFreezeFrame(droppedFrames, durationMs);
        } else if (durationMs > 200) {
            // 严重卡顿：需要高优处理
            reportSevereJank(droppedFrames, durationMs);
        } else if (durationMs > 50) {
            // 明显卡顿：需要记录
            reportJank(droppedFrames, durationMs);
        }
    }
}
```

### 3.3 监控事件循环实践
- 基于Looper Printer的事件循环监控实现

```java
/**
 * 事件循环卡顿监控器
 * 通过Hook Looper的Printer来检测消息处理耗时
 */
public class LooperMonitor {
    private static final long JANK_THRESHOLD_MS = 100; // 卡顿阈值
    private static final long FREEZE_THRESHOLD_MS = 700; // 冻帧阈值
    
    private long dispatchStartTime = 0;
    private boolean isDispatching = false;
    private StackSampler stackSampler;
    
    public void start() {
        stackSampler = new StackSampler();
        
        Looper.getMainLooper().setMessageLogging(new Printer() {
            @Override
            public void println(String log) {
                if (log.startsWith(">>>>> Dispatching")) {
                    // 消息开始处理
                    dispatchStartTime = System.currentTimeMillis();
                    isDispatching = true;
                    // 开始堆栈采样
                    stackSampler.startSampling();
                } else if (log.startsWith("<<<<< Finished")) {
                    // 消息处理完成
                    isDispatching = false;
                    long duration = System.currentTimeMillis() - dispatchStartTime;
                    stackSampler.stopSampling();
                    
                    if (duration >= JANK_THRESHOLD_MS) {
                        // 获取采样到的堆栈
                        String stackTrace = stackSampler.getSampledStack();
                        reportJank(duration, stackTrace, log);
                    }
                }
            }
        });
    }
    
    private void reportJank(long duration, String stackTrace, String msgInfo) {
        JankInfo jankInfo = new JankInfo();
        jankInfo.duration = duration;
        jankInfo.stackTrace = stackTrace;
        jankInfo.messageInfo = msgInfo;
        jankInfo.timestamp = System.currentTimeMillis();
        jankInfo.scene = getCurrentScene();
        
        if (duration >= FREEZE_THRESHOLD_MS) {
            jankInfo.level = JankLevel.FREEZE;
        } else if (duration >= 200) {
            jankInfo.level = JankLevel.SEVERE;
        } else {
            jankInfo.level = JankLevel.NORMAL;
        }
        
        // 上报卡顿信息
        JankReporter.report(jankInfo);
    }
}
```

### 3.4 监控执行耗时实践

```java
/**
 * 方法耗时监控（被插桩后的效果）
 * 编译期通过Gradle Plugin + ASM在目标方法入口/出口插入计时代码
 */
public class MethodTracer {
    // 线程局部变量，记录方法调用栈的时间戳
    private static final ThreadLocal<long[]> sTimestampStack = 
        ThreadLocal.withInitial(() -> new long[128]);
    private static final ThreadLocal<Integer> sStackDepth = 
        ThreadLocal.withInitial(() -> 0);
    
    // 方法入口（由ASM插桩插入）
    public static void onMethodEnter(int methodId) {
        int depth = sStackDepth.get();
        long[] stack = sTimestampStack.get();
        if (depth < stack.length) {
            stack[depth] = System.nanoTime();
            sStackDepth.set(depth + 1);
        }
    }
    
    // 方法出口（由ASM插桩插入）
    public static void onMethodExit(int methodId) {
        int depth = sStackDepth.get() - 1;
        if (depth < 0) return;
        sStackDepth.set(depth);
        
        long[] stack = sTimestampStack.get();
        long startTime = stack[depth];
        long duration = System.nanoTime() - startTime;
        long durationMs = duration / 1_000_000;
        
        // 超过阈值记录
        if (durationMs > 16 && isMainThread()) {
            recordSlowMethod(methodId, durationMs);
        }
    }
    
    private static boolean isMainThread() {
        return Looper.getMainLooper().getThread() == Thread.currentThread();
    }
}
```

### 3.5 卡顿信息采集
- 卡顿发生时需要采集的关键信息
    - 基础信息：卡顿时长、发生时间、当前页面/场景、用户操作序列
    - 堆栈信息：主线程调用栈（最关键的定位信息）
    - 系统信息：CPU使用率、可用内存、IO状态、电量状态
    - 应用信息：线程数量、FD数量、GC频率、当前任务队列状态
    - 设备信息：设备型号、系统版本、可用存储空间、屏幕分辨率
- 堆栈采样是卡顿定位的核心

```java
/**
 * 主线程堆栈采样器
 * 在独立线程中定期获取主线程的调用栈
 */
public class StackSampler {
    private static final long SAMPLE_INTERVAL_MS = 50; // 采样间隔50ms
    private Thread mainThread;
    private HandlerThread samplerThread;
    private Handler samplerHandler;
    private volatile boolean isSampling = false;
    private List<String> sampledStacks = new ArrayList<>();
    
    public StackSampler() {
        mainThread = Looper.getMainLooper().getThread();
        samplerThread = new HandlerThread("stack-sampler");
        samplerThread.start();
        samplerHandler = new Handler(samplerThread.getLooper());
    }
    
    public void startSampling() {
        isSampling = true;
        sampledStacks.clear();
        samplerHandler.postDelayed(sampleRunnable, SAMPLE_INTERVAL_MS);
    }
    
    public void stopSampling() {
        isSampling = false;
        samplerHandler.removeCallbacks(sampleRunnable);
    }
    
    private final Runnable sampleRunnable = new Runnable() {
        @Override
        public void run() {
            if (!isSampling) return;
            
            // 获取主线程堆栈
            StackTraceElement[] stackTrace = mainThread.getStackTrace();
            StringBuilder sb = new StringBuilder();
            for (StackTraceElement element : stackTrace) {
                sb.append(element.toString()).append("\n");
            }
            sampledStacks.add(sb.toString());
            
            // 继续采样
            samplerHandler.postDelayed(this, SAMPLE_INTERVAL_MS);
        }
    };
    
    /**
     * 获取出现频率最高的堆栈（即卡顿的热点位置）
     */
    public String getSampledStack() {
        if (sampledStacks.isEmpty()) return "";
        // 统计堆栈频率，返回出现最多的堆栈
        Map<String, Integer> stackFrequency = new HashMap<>();
        for (String stack : sampledStacks) {
            stackFrequency.merge(stack, 1, Integer::sum);
        }
        return stackFrequency.entrySet().stream()
            .max(Map.Entry.comparingByValue())
            .map(Map.Entry::getKey)
            .orElse("");
    }
}
```

- 堆栈采样的优化策略
    - 采样间隔的选择：太短（<10ms）会增加性能开销，太长（>100ms）会丢失短时间的卡顿堆栈
    - 推荐采样间隔：线上50ms，线下20ms
    - 采样去重：连续相同的堆栈只记录一次，减少存储开销
    - 堆栈裁剪：过滤掉系统框架层的堆栈帧，只保留应用代码部分

### 4.2 卡顿堆栈采样
- 堆栈采样是卡顿定位的关键能力
    - 当检测到卡顿开始时，启动堆栈采样
    - 采样线程以固定间隔获取主线程的调用栈
    - 卡顿结束后，分析采样到的堆栈，找出出现频率最高的调用路径
    - 高频堆栈即为卡顿的真正原因
- 堆栈采样的精度优化
    - 基础方案：使用Thread.getStackTrace()获取Java层堆栈
    - 进阶方案：使用libunwind获取Native层堆栈（可以看到JNI调用链）
    - 高精度方案：使用Simpleperf进行CPU Profiling，获取函数级别的耗时分布
    - 堆栈聚合算法：将多次采样的堆栈进行聚合，生成调用火焰图

### 4.3 动态阈值调整
- 不同机型、场景的卡顿阈值应该不同
    - 高端机（如旗舰手机）：卡顿阈值设为50ms，对流畅度要求更高
    - 低端机（如入门手机）：卡顿阈值设为150ms，避免过多的误报
    - 高刷屏（90/120Hz）：帧预算更短，卡顿阈值应相应降低
    - 后台场景：不需要渲染的场景可以提高阈值或暂停监控
- 动态阈值的实现
    - 通过配置下发实现动态调整，无需发版
    - 根据设备性能评分自动选择阈值等级
    - 设备性能评分可根据CPU核心数、频率、内存大小、GPU型号等综合计算
    - 支持按页面/场景配置不同的阈值

### 4.4 多级警报系统
- 卡顿警报需要分级处理，避免告警疲劳
    - P0（紧急）：冻帧(>700ms)或ANR，需要立即处理
    - P1（高优）：严重卡顿(200-700ms)，当日内处理
    - P2（中优）：明显卡顿(50-200ms)，版本内处理
    - P3（低优）：轻微掉帧(17-50ms)，持续优化
- 警报的触发条件
    - 单次阈值触发：单次卡顿超过设定阈值
    - 频率触发：一段时间内卡顿次数超过设定值
    - 趋势触发：卡顿率较前一版本显著上升
    - 比较触发：某页面的卡顿率显著高于同类页面

### 4.5 卡顿聚合分析
- 线上采集到的卡顿数据需要聚合分析才有意义
    - 堆栈聚合：将相同调用路径的卡顿聚合为一个Issue
    - 维度聚合：按页面、设备型号、系统版本、网络状态等维度聚合
    - 趋势分析：跟踪每个Issue的卡顿次数随版本的变化趋势
    - Top N分析：找出影响范围最大的Top 10卡顿问题
- 聚合分析的技术要点
    - 堆栈去框架：去掉系统框架层的调用帧，只根据应用代码部分进行聚合
    - 堆栈签名：对堆栈计算Hash作为唯一标识，相同Hash的堆栈归为同一Issue
    - 影响面评估：每个Issue的影响面 = 受影响UV / 总UV，用于优先级排序
    - 自动归因：通过堆栈分析自动标记卡顿类型（IO类、锁竞争类、布局类等）

## 06.帧率监控原理

### 6.1 帧率监控核心
- 帧率监控的核心是利用VSync信号的规律性
    - Android的Choreographer在每个VSync信号到来时回调FrameCallback
    - 通过记录每次回调的时间戳，可以计算帧间隔和帧率
    - 帧率 = 帧数 / 统计时间窗口
    - 掉帧数 = (帧间隔 / 标准帧间隔) - 1
- Choreographer的工作原理
    - Choreographer内部维护了一个按时间排序的回调队列
    - 回调分为四种类型：CALLBACK_INPUT → CALLBACK_ANIMATION → CALLBACK_INSETS_ANIMATION → CALLBACK_TRAVERSAL
    - 每次VSync信号到来时，Choreographer按顺序执行队列中到期的回调
    - 如果某个回调执行时间过长，会导致后续回调延迟，从而产生掉帧
- FrameCallback的注册和执行流程
    - 调用Choreographer.postFrameCallback()注册回调
    - 系统在下一个VSync信号到来时调用doFrame(long frameTimeNanos)
    - frameTimeNanos是VSync信号的精确时间戳（纳秒级别）
    - 需要在doFrame中再次调用postFrameCallback以保持持续监控

### 6.2 frame本质
- 帧（Frame）的本质是屏幕上一次完整的画面更新
    - 从软件角度：一帧对应一次完整的UI线程处理（Input→Animation→Measure→Layout→Draw）加RenderThread渲染
    - 从硬件角度：一帧对应显示器一次完整的像素刷新（从左上角扫描到右下角）
    - 两者通过VSync信号同步：软件在VSync信号到来时开始渲染新一帧，硬件在下一个VSync信号到来时显示渲染好的帧
- 帧的生命周期
    - 创建：VSync信号到来，Choreographer开始调度回调
    - 处理：UI线程执行Input→Animation→Measure→Layout→Draw
    - 渲染：RenderThread将DisplayList提交给GPU渲染
    - 合成：SurfaceFlinger将多个Surface的帧合成为最终画面
    - 显示：VSync信号到来时，交换缓冲区，画面更新到屏幕
- DisplayList与帧的关系
    - DisplayList是View树绘制命令的序列化表示
    - 每次View.draw()调用会更新对应View的DisplayList
    - RenderThread遍历所有DisplayList生成GPU渲染指令
    - 只有DisplayList发生变化的View才需要重新record，未变化的可以复用

### 6.3 帧率一般是多少
- 不同设备和场景下的帧率标准
    - 大多数Android设备：60Hz屏幕刷新率，对应60fps
    - 高刷新率设备：90Hz(如OnePlus 7 Pro)、120Hz(如三星Galaxy S系列)、144Hz(游戏手机)
    - 低功耗模式：部分设备在低电量时降至30Hz/48Hz以节省电量
    - 视频播放：通常为24fps/30fps/60fps，取决于视频源
- 帧率与体验的关系
    - <24fps：明显的画面跳帧感，类似幻灯片
    - 24-30fps：基本流畅，但快速运动场景会感觉不够平滑
    - 30-45fps：一般流畅，偶尔会感觉到轻微卡顿
    - 45-60fps：流畅，满足大多数场景的需求
    - 60fps：标准流畅，人眼难以分辨更高帧率带来的差异
    - 90-120fps：极致流畅，在快速滑动等场景能感受到细微提升
- 帧率并非越高越好
    - 更高的帧率意味着更高的CPU/GPU负载和更多的电量消耗
    - 自适应帧率（如Android 12的可变刷新率）是更好的选择
    - 根据场景动态调整帧率：静态页面降至30fps，滑动时恢复60fps

### 6.4 帧率影响因素
- 影响帧率的因素是多维度的
    - 硬件因素：CPU性能（核心数/频率）、GPU性能、内存带宽、存储IO速度
    - 软件因素：布局复杂度、绘制复杂度、主线程任务负载、线程竞争
    - 系统因素：后台进程数量、内存压力、温控降频、省电模式
    - 内容因素：页面元素数量、图片数量和尺寸、动画复杂度
- 帧率波动的常见原因
    - GC（垃圾回收）：GC暂停（Stop-the-world）直接导致帧渲染停止
    - JIT编译：ART的JIT编译器在运行时编译热点代码，会占用CPU资源
    - 系统服务调用：Binder调用、ContentProvider查询等跨进程操作
    - IO操作：文件系统IO、数据库IO、网络IO在主线程执行
    - CPU降频：温度过高时CPU降频，渲染速度下降

### 6.5 掉帧判定标准
- 掉帧的判定需要明确的标准
    - 标准定义：当一帧的实际渲染时间超过一个VSync周期时，发生掉帧
    - 60Hz屏幕：帧时间>16.67ms即掉帧
    - 90Hz屏幕：帧时间>11.11ms即掉帧
    - 120Hz屏幕：帧时间>8.33ms即掉帧
- Google推荐的掉帧分级标准（Android Vitals）
    - Slow rendering：帧时间超过16ms的帧占比
    - Frozen frames：帧时间超过700ms的帧
    - 应用在Google Play Console中会显示这两个指标
    - Slow rendering >50%或Frozen frames >0.1%会被标记为需要优化
- 实际项目中的掉帧判定建议
    - 不要将所有超过16ms的帧都视为掉帧，17-20ms的帧用户几乎无法感知
    - 建议以2倍帧间隔（33ms）作为掉帧的实际判定阈值
    - 连续掉帧比单次掉帧的体验影响更大，需要单独统计
    - 在高刷屏设备上，掉帧判定阈值应相应调低


## 07.事件监控原理

### 7.1 消息循环机制
- Android主线程的核心是Handler-Looper-MessageQueue消息循环
    - Looper.loop()是一个无限循环，不断从MessageQueue中取出Message
    - 每个Message通过msg.target.dispatchMessage(msg)分发处理
    - 所有的UI操作（View更新、动画、输入事件处理）都是通过Message在主线程执行的
- 消息循环的关键代码

```java
// Looper.loop() 简化版核心逻辑
public static void loop() {
    final Looper me = myLooper();
    final MessageQueue queue = me.mQueue;
    
    for (;;) {
        Message msg = queue.next(); // 阻塞获取消息
        if (msg == null) return;
        
        // 关键：dispatch前后的Printer回调
        final Printer logging = me.mLogging;
        if (logging != null) {
            logging.println(">>>>> Dispatching to " + msg.target 
                + " " + msg.callback + ": " + msg.what);
        }
        
        msg.target.dispatchMessage(msg); // 消息处理（可能耗时）
        
        if (logging != null) {
            logging.println("<<<<< Finished to " + msg.target 
                + " " + msg.callback);
        }
        
        msg.recycleUnchecked();
    }
}
```

### 7.2 Printer监控原理
- 利用Looper的Printer机制是最经典的卡顿监控方案
    - 在dispatch前后各打印一条日志，通过计算两条日志的时间差获得消息处理耗时
    - 这个方案被BlockCanary、Matrix等知名开源项目广泛使用
- Printer监控的实现细节
    - 通过Looper.getMainLooper().setMessageLogging(printer)设置自定义Printer
    - 需要注意：setMessageLogging会覆盖之前设置的Printer
    - 为了兼容性，可以先保存原有的Printer，在自定义Printer中转发
    - Printer的println方法在主线程调用，实现要尽可能轻量
- Printer方案的性能影响
    - 每次Message处理前后都会触发Printer.println()
    - println参数的字符串拼接会产生临时String对象
    - 在高频消息场景（如触摸事件连续分发）中，性能开销不可忽视
    - 优化方式：使用反射Hook而非Printer来减少字符串拼接开销

### 7.3 消息耗时检测
- 消息耗时检测的进阶方案
    - 基础方案：通过Printer获取dispatch前后的时间差
    - 进阶方案：Hook Handler.dispatchMessage()方法，在调用前后插入计时逻辑
    - 高精度方案：使用Native层的epoll机制监控消息循环的空闲和忙碌状态
- 消息分类统计
    - 输入事件消息：touch、key等用户输入，处理时间直接影响操作响应速度
    - UI刷新消息：invalidate、requestLayout触发的Traversal消息
    - 动画消息：Choreographer的动画回调
    - 业务消息：应用业务逻辑产生的Handler消息
    - 不同类型的消息有不同的耗时预期和阈值标准

### 7.4 ANR与卡顿的关系
- ANR是卡顿的极端表现形式
    - ANR = 主线程在规定时间内未完成特定操作
    - 卡顿 = 主线程处理某个消息的时间超过预期
    - 治理卡顿就是在预防ANR
- ANR的触发机制
    - 输入事件ANR：InputDispatcher发现之前的输入事件在5秒内未处理完
    - 广播ANR：BroadcastQueue发现广播接收器在规定时间内未处理完
    - Service ANR：ActiveServices发现Service在规定时间内未完成启动或超时
    - ContentProvider ANR：ContentProvider在发布超时时间内未完成
- 卡顿监控对ANR治理的帮助
    - 通过卡顿监控发现耗时>1秒的主线程操作，这些就是潜在的ANR风险点
    - 卡顿堆栈可以帮助定位ANR的根因（很多ANR的traces.txt堆栈不准确）
    - 建立卡顿趋势，当某个场景的卡顿率上升时提前预警，避免ANR率飙升

### 7.5 性能分析优化
- 卡顿监控本身的性能优化
    - 监控代码的CPU开销应控制在1%以内，不能因为监控导致卡顿
    - 堆栈采样的线程优先级应设为最低，避免与业务线程竞争CPU
    - 采样数据使用环形缓冲区存储，控制内存占用
    - 上报数据先在本地聚合，定时批量上报，减少IO频率
- 监控的采样策略
    - 全量监控性能开销大，线上环境建议采样10%-20%用户
    - 可以对新版本的前几天全量监控，确认无明显退化后降低采样率
    - 高端机可以适当提高采样率（因为监控开销对它们影响更小）
    - 出现线上问题时可以动态提高指定版本/机型的采样率
- 卡顿数据的存储和上报优化
    - 卡顿数据先写入本地DB，避免丢失
    - 使用Protobuf或自定义二进制格式序列化，比JSON省50%以上流量
    - 上报时机选择在WiFi环境或应用退到后台时
    - 对于冻帧级别的严重卡顿，立即上报（不等待批量上报周期）


## 08.跨平台卡顿监控

### 8.1 各平台卡顿特点
- 不同平台的卡顿原因和监控方式存在差异

| 维度 | Android | iOS | Web |
|------|---------|-----|-----|
| UI线程模型 | Looper消息循环 | RunLoop | Event Loop |
| 卡顿根因 | 主线程耗时操作 | 主线程耗时操作 | 主线程耗时操作 |
| 帧率标准 | 60/90/120fps | 60/120fps(ProMotion) | 60fps |

| 主要工具 | Systrace/Perfetto | Instruments | Chrome DevTools |

### 8.2 iOS卡顿监控
- iOS的卡顿监控基于RunLoop机制

```swift
/// iOS卡顿监控器
/// 基于RunLoop Observer检测主线程卡顿
class JankMonitor {
    private var runLoopObserver: CFRunLoopObserver?
    private var runLoopActivity: CFRunLoopActivity = .entry
    private var semaphore: DispatchSemaphore = DispatchSemaphore(value: 0)
    private var monitorThread: Thread?
    
    // 卡顿阈值（毫秒）
    private let jankThreshold: TimeInterval = 0.1 // 100ms
    
    func start() {
        // 创建RunLoop Observer
        let observer = CFRunLoopObserverCreateWithHandler(
            kCFAllocatorDefault, 
            CFRunLoopActivity.allActivities.rawValue, 
            true, 0
        ) { [weak self] _, activity in
            self?.runLoopActivity = activity
            self?.semaphore.signal()
        }
        
        CFRunLoopAddObserver(CFRunLoopGetMain(), observer, .commonModes)
        runLoopObserver = observer
        
        // 监控线程
        monitorThread = Thread {
            while true {
                // 等待RunLoop状态变化
                let result = self.semaphore.wait(
                    timeout: .now() + self.jankThreshold
                )
                
                if result == .timedOut {
                    // 超时说明主线程卡住了
                    let activity = self.runLoopActivity
                    if activity == .beforeSources || activity == .afterWaiting {
                        // 获取主线程堆栈
                        let stack = Thread.callStackSymbols.joined(separator: "\n")
                        self.reportJank(stack: stack)
                    }
                }
            }
        }
        monitorThread?.start()
    }
    
    private func reportJank(stack: String) {
        print("[JankMonitor] 检测到卡顿:\n\(stack)")
    }
}
```

- iOS卡顿监控的注意事项
    - RunLoop Observer的方案无法精确获取卡顿时长，只能判断是否超过阈值
    - 需要配合CADisplayLink来统计帧率数据
    - iOS 15+可以使用MetricKit框架获取系统级的卡顿数据
    - Xcode的Hang Detection工具可以自动检测超过250ms的主线程卡顿

### 8.3 Web卡顿监控
- Web平台的卡顿监控基于Event Loop和requestAnimationFrame

```javascript
/**
 * Web卡顿监控器
 * 基于requestAnimationFrame和Long Task API
 */
class WebJankMonitor {
    constructor(options = {}) {
        this.jankThreshold = options.jankThreshold || 50; // 50ms
        this.lastFrameTime = 0;
        this.frameCount = 0;
        this.isRunning = false;
    }
    
    start() {
        this.isRunning = true;
        this.lastFrameTime = performance.now();
        
        // 方案1：基于requestAnimationFrame的帧率监控
        this._monitorFPS();
        
        // 方案2：基于Long Task API的卡顿监控
        this._monitorLongTasks();
        
        // 方案3：基于PerformanceObserver的帧时间监控
        this._monitorFrameTiming();
    }
    
    _monitorFPS() {
        const loop = (timestamp) => {
            if (!this.isRunning) return;
            
            const frameDuration = timestamp - this.lastFrameTime;
            this.frameCount++;
            
            // 检测掉帧
            if (frameDuration > this.jankThreshold) {
                this._reportJank({
                    type: 'frame_drop',
                    duration: frameDuration,
                    timestamp: Date.now()
                });
            }
            
            this.lastFrameTime = timestamp;
            requestAnimationFrame(loop);
        };
        requestAnimationFrame(loop);
    }
    
    _monitorLongTasks() {
        // Long Task API：检测超过50ms的任务
        if ('PerformanceObserver' in window) {
            const observer = new PerformanceObserver((list) => {
                for (const entry of list.getEntries()) {
                    this._reportJank({
                        type: 'long_task',
                        duration: entry.duration,
                        startTime: entry.startTime,
                        name: entry.name
                    });
                }
            });
            observer.observe({ type: 'longtask', buffered: true });
        }
    }
    
    _monitorFrameTiming() {
        // 使用PerformanceObserver监控帧时间
        if ('PerformanceObserver' in window) {
            try {
                const observer = new PerformanceObserver((list) => {
                    for (const entry of list.getEntries()) {
                        if (entry.duration > 16.67) {
                            this._reportJank({
                                type: 'slow_frame',
                                duration: entry.duration,
                                startTime: entry.startTime
                            });
                        }
                    }
                });
                observer.observe({ type: 'frame', buffered: true });
            } catch (e) {
                // frame type可能不被支持
            }
        }
    }
    
    _reportJank(data) {
        console.warn('[JankMonitor]', data);
        // 上报到监控平台
    }
    
    stop() {
        this.isRunning = false;
    }
}

// 使用示例
const monitor = new WebJankMonitor({ jankThreshold: 50 });
monitor.start();
```

- Web卡顿监控的特殊考虑
    - Long Task API是W3C标准，检测超过50ms的JS执行任务
    - Web Worker中的卡顿不影响主线程渲染，不需要监控
    - Service Worker中的卡顿可能影响网络请求响应，需要单独监控
    - React/Vue等框架可以通过Performance API检测组件渲染耗时


## 09.卡顿监控设计总结

### 9.1 核心设计原则

**原则一：监控不能造成卡顿**

卡顿监控代码运行在主线程或与主线程交互频繁，如果监控本身有性能问题，就会成为卡顿的制造者。监控代码的CPU开销应控制在1%以内，内存开销应控制在5MB以内。

**原则二：多维度交叉验证**

单一的监控方案无法覆盖所有卡顿场景。帧率监控检测渲染卡顿，事件循环监控检测消息处理卡顿，两者结合才能全面覆盖。堆栈采样提供定位能力，渲染分析提供阶段划分能力。

**原则三：分级治理**

不是所有的卡顿都值得治理。轻微掉帧（17-50ms）用户几乎无感知，可以低优处理；冻帧（>700ms）严重影响用户体验，需要紧急处理。根据卡顿的严重程度和影响范围确定治理优先级。

**原则四：持续防劣化**

卡顿治理不是一次性的工作。新代码的引入可能带来新的卡顿问题。需要建立持续的监控和告警机制，在卡顿率上升时及时发现和处理。CI/CD中集成帧率测试，防止卡顿退化。

**原则五：数据驱动决策**

卡顿治理的优先级应基于数据决定，而非主观感受。通过线上监控数据确定影响面最大的卡顿问题，集中资源治理Top问题，获得最大的优化收益。

### 9.2 卡顿治理方法论

**第一阶段：建立监控**
1. 搭建帧率监控体系，覆盖核心页面
2. 部署事件循环监控，配合堆栈采样
3. 确定各级别卡顿的阈值标准
4. 建立卡顿数据的采集、存储、分析链路

**第二阶段：摸清家底**
1. 统计各页面/场景的帧率基线
2. 识别Top 10卡顿问题
3. 按卡顿类型分类（IO类、计算类、锁竞争类、布局类）
4. 评估每个问题的影响面和治理成本

**第三阶段：专项治理**
1. 主线程IO治理：将文件IO、SP操作、数据库操作迁移到子线程
2. 布局优化：使用ConstraintLayout扁平化、ViewStub延迟加载、异步inflate
3. 锁竞争优化：减少主线程等待锁的场景，使用无锁数据结构
4. 计算优化：耗时计算移到子线程，结果通过Handler/LiveData回调到主线程

**第四阶段：防劣化**
1. CI/CD集成帧率测试，每次构建自动验证核心页面帧率
2. 线上卡顿率监控，版本对比异常时告警
3. 建立卡顿问题的Review机制，新代码引入的卡顿问题需要限期修复
4. 定期回顾卡顿数据，持续优化

### 9.3 常见误区分析

**疑惑**：卡顿监控和治理中有哪些常见的误区？

**答疑**：以下五个误区在实际工作中经常出现，需要特别警惕。

**论证**：

**误区一：只关注ANR忽略卡顿**

很多团队只在ANR率上升时才开始治理，忽略了卡顿是ANR的前兆。一个200ms的卡顿虽然不会触发ANR，但在低端机或系统负载高时可能变成5秒的ANR。治理卡顿是预防ANR最有效的手段。

**误区二：帧率高就代表不卡**

平均帧率55fps的应用可能存在严重的局部卡顿。如果95%的帧在8ms内完成，但有5%的帧超过200ms，用户体验仍然很差。需要关注帧时间的P95/P99和掉帧分布，而不仅是平均帧率。

**误区三：把所有耗时操作都移到子线程**

将操作移到子线程不一定能解决卡顿。如果子线程完成后需要大量UI更新，主线程仍然会卡顿。如果子线程持有主线程需要的锁，反而会造成主线程等待。正确的做法是减少主线程的总工作量，而非简单地转移。

**误区四：线下没问题就放心了**

开发和测试用的设备通常是中高端机型，线下测试的数据量和使用时长也有限。线上环境中，低端机、大数据量、长时间使用等因素可能暴露出线下未发现的卡顿问题。线上监控是不可或缺的。

**误区五：一次优化后就不管了**

卡顿治理是一个持续的过程。随着业务迭代，新功能的加入可能引入新的卡顿问题。没有防劣化机制的卡顿治理，效果会随着时间逐渐衰减，最终回到治理前的水平。

**结果**：卡顿监控和治理是一个系统工程，需要从监控方案搭建、问题发现、精准定位、专项治理到持续防劣化形成完整闭环。通过帧率监控+事件循环监控+堆栈采样的组合方案覆盖各类卡顿场景，结合线上数据驱动治理优先级，才能持续保证应用的流畅度。


## 10.跨平台卡顿治理对比

### 10.1 各平台卡顿检测机制

| 维度 | Android | iOS | Web |
|------|---------|-----|-----|
| 帧率监控 | Choreographer.FrameCallback | CADisplayLink | requestAnimationFrame |
| 主线程监控 | Looper.Printer/BlockCanary | RunLoop Observer | Long Task API |
| 堆栈采集 | Thread.getStackTrace() | backtrace/NSThread | Error.stack(有限) |
| 系统卡顿 | ANR(5s阈值) | Watchdog Timeout | 无(浏览器管理) |
| 性能工具 | Systrace/Perfetto/GPU渲染 | Instruments/Time Profiler | Chrome Performance |
| 关键指标 | 帧率/掉帧率/ANR率 | 帧率/掉帧率/卡死率 | INP/FID/Long Task |

### 10.2 卡顿治理核心指标

- **帧率(FPS)**：页面交互时的实时帧率，目标60fps以上
- **掉帧率**：帧间隔>16.67ms的帧占比，目标<5%
- **严重卡顿率**：帧间隔>700ms的帧占比，目标<0.1%
- **ANR率(Android)**：ANR次数/活跃会话数，目标<0.01%
- **INP(Web)**：Interaction to Next Paint，目标<200ms(P75)
