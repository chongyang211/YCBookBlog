## 00.5 贯穿案例：金融 App"5 进程架构 OOM 与冷启慢"事件

> 本案例贯穿全文：§01 看懂代价、§02 拿到隔离模型、§03/§04 用三方案+决策树定位、§05 用实验复盘、§06 给出分层策略闭环。

### 案例背景

某头部金融 App V8.5 历史上沿用"5 进程架构"（主进程 / Push 进程 / WebView 进程 / 守护进程 / 推送拉活进程），架构师初心是"模块隔离防崩溃"。但近期问题集中爆发：

- **常驻 PSS 达 420MB**（主 220 + Push 80 + WebView 60 + 守护 35 + 拉活 25），中端机 OOM 率 4.8%。
- **冷启动 P95 = 3.6s**（用户从 Push 点入是冷启动率 38%）。
- **Android 11+ 升级后被系统认定"贪婪应用"**，主进程被杀率从 2% 飙到 18%。
- 应用商店"卡顿"差评/月 12,000+，用户流失加速。

研发组初步反应："拆进程是为了稳定，不能改架构。"——这是典型的"架构惯性"。

### 经验派的 5 周折腾（典型反面教材）

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 加强双进程互拉保活（怀疑被杀太多）| **主进程被杀率反升到 22%**（系统更激进打压）|
| 第 2 周 | 把 Push 进程内存上限调小（怀疑 Push 占内存）| Push 频繁 OOM，消息丢失率涨 8 倍 |
| 第 3 周 | 加更多 IPC 缓存层（怀疑 IPC 慢）| IPC 抽象层 bug 引发数据不一致 |
| 第 4 周 | 把 WebView 进程预热常驻（怀疑冷启慢）| 常驻内存又涨 30MB |
| 第 5 周 | 改 Push 进程优先级（怀疑被低优先级杀）| 无明显改善 |

**复盘**：五周折腾的根本错误是**默认"5 进程不能动"**。所有动作都在"修补 5 进程架构"，没人质疑"5 个进程真的都必要吗"。**进程是重资源，每个都要算清成本收益**——这正是 §2.2 隔离 vs 通信权衡的反面教材。

### 方法派的 8 天闭环

新接手的同学按本文方法论重做：

**Day 1（§02 第一性原理 + §03 三方案）**：用方案①②③同时上：

- 进程清单：5 个进程清晰列出，各自 PSS。
- 资源监控：Push 进程 80MB，但**实际只有每天 8-12 次推送时干活**，其余 23.5 小时空转。
- IPC trace：主→Push、主→守护进程的 Binder 调用每秒 35 次（多数是状态心跳）。

**Day 2（§04 归因决策树）**：逐进程评估：

| 进程 | 必要性 | 真实工作量 | 占用 |
|---|---|---|---|
| 主进程 | 必要 | 全程 | 220MB |
| Push 进程 | **不必要** | 每天 8-12 次×几秒 | 80MB（23.5h 空转）|
| WebView 进程 | **必要** | 风险隔离（H5 业务多）| 60MB |
| 守护进程 | **不必要** | 仅为保活（A11+ 失效）| 35MB |
| 拉活进程 | **不必要** | 仅为保活 | 25MB |

→ **5 进程中 3 个是"为了保活"或"过度隔离"开的**，可以直接删。

**Day 3（[§5.3 实验](#53-实验三保活策略效果) 数据支持）**：用本文的保活实验数据说服架构师——"双进程互拉在 A11+ 几乎全失效"。

**Day 4-5（§06 分层策略）**：

- 第 1 层（数量收敛）：Push 改 FCM 系统级推送，进程合并到主；守护/拉活直接删；保留 WebView 进程做风险隔离。
- 第 2 层（IPC 治理）：剩余主↔WebView 的 IPC 高频心跳改批量+缓存；大数据（图片）用共享内存。
- 第 3 层（风险隔离）：WebView 进程仍单独，确保 H5 崩不影响主。
- 第 4 层（拥抱重启）：投入"快速重启 + 状态恢复"——被杀后 < 800ms 拉起，且滚动位置/草稿/登录态全恢复。

**Day 6（[§5.5 实验](#55-实验五快速重启--状态恢复-vs-暗保活的用户体验对比) 思路验证）**：构造"被杀-重启-恢复"自动化用例，验证用户感知。

**Day 7-8（灰度 + 上线）**：

### 上线效果

| 指标 | 经验派 5 周后 | 方法派 8 天后 |
|---|---|---|
| 进程数 | 5 | **2**（主 + WebView）|
| 常驻 PSS | 450MB | **240MB**（-47%）|
| 冷启 P95 | 3.6s | **1.2s** |
| 中端机 OOM 率 | 4.8% | **0.6%** |
| 主进程被杀率 | 22% | **3%**（不再被打压）|
| 推送到达率（FCM）| 91% | **97%** |
| 用户主动回归率 | -8% | **+5%** |

**核心洞察**：经验派 5 周错在"把架构当宪法"。**进程治理的最大杠杆是删除非必要进程**，而不是优化它们。删 3 个进程让常驻内存降 47%，被杀率反而从 22% 降到 3%——**系统不再把你当贪婪应用，是最大的奖励**。

### 案例如何串起本文

- **§01 现象与代价** ▶▶ 业务损失映射：差评/月 12K、用户流失加速。
- **§02 隔离 vs 通信模型** ▶▶ 案例 3 个进程是"过度隔离"，2 个是"合理隔离"。

## 01.问题域定义

### 1.1 现象与代价

进程问题往往体现为系统级问题：

- **多进程内存浪费**：同一应用拆 5 个进程，每个进程都有自己的 ART / 资源副本，内存涨 2-3 倍。
- **进程拉起慢**：用户从通知点入应用 → 主进程被杀 → 重新冷启动 → 体验类崩溃。
- **IPC 延迟过高**：跨进程查询数据 100ms+，用户感知"卡"。
- **保活滥用导致系统体验差**：多个 App 互相拉活，整机内存吃紧、温度升高。
- **多进程崩溃定位难**：插件进程崩溃，主进程无感，但功能失效。

**业务代价（行业实测数据）**：

- 头部 App：减少不必要进程后，内存峰值下降 40-60%，OOM 率下降 30%。
- 进程被杀后冷启动时长是热启的 5-10 倍。
- 系统对"多进程贪婪"应用的 OOM 倾向更高（LMK 评分更差）。

> ▶▶ **回扣 §00.5 案例**：金融 App 5 进程架构常驻 PSS 450MB → 删到 2 进程 240MB（-47%），OOM 率 4.8%→0.6%，**与本节"减少不必要进程后内存峰值下降 40-60%"完全一致**。主进程被杀率 22%→3% 也印证"系统对贪婪应用 LMK 评分更差"——系统不再判定贪婪是最大奖励。

### 1.2 度量准则

按 [`卷零·02 §3`](../00.公共方法论/02.跨平台指标体系.md) 指标体系：

**资源视角（USE）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 应用进程数 | 总和 | < 3（普通） / < 5（重型） |
| 单进程 PSS | 占设备 RAM 比例 | 主 < 30%、子 < 10% |
| IPC 错误 | 调用失败率 | < 0.1% |

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| IPC 延迟 | 跨进程调用时长 | < 5ms（本地）/ < 50ms（重型） |
| 进程拉起时长 | 从拉起到 onCreate 完成 | < 800ms |
| 保活成功率 | 主进程被杀后多久重新拉起 | 视场景 |

**用户感知（APDEX）**：

- *Satisfied*：进程切换无感，IPC 响应快
- *Tolerating*：偶发进程冷启
- *Frustrated*：频繁冷启 / IPC 超时

### 1.3 行业基准与目标

| 平台 | 应用进程数 | IPC 延迟 | 进程启动开销 |
|---|---|---|---|
| Android | 1-3 主用 + 偶尔子 | Binder 同步 < 5ms | 200-500ms（fork from Zygote）|
| iOS | 几乎单进程（特殊扩展才多）| XPC < 10ms | 200ms+（exec + dyld）|
| Web | 每 Tab 一个进程 | postMessage < 10ms | 100-500ms |
| 嵌入式 Linux | 视设计 | DBus / Unix Socket | varies |

### 1.4 反直觉问题清单

带着这些问题阅读：

1. 多进程一定比单进程慢吗？
2. 拆进程能解决 OOM 吗？拆多少合适？
3. Binder 跨进程一次调用比同进程慢多少？

## 02.第一性原理

> 本节回答三个根本问题：**①进程的物理本质是什么？②为什么所有平台的进程模型都同构？③同构之下平台差异在哪？**

### 2.1 进程本质定义

**一句话定义**：

> **进程 = 操作系统资源分配与隔离的基本单元，是"拥有独立地址空间 + 文件句柄 + 信号上下文"的执行实例**。

这句话隐含三个不可商量的物理约束：

**约束一：进程是地址空间的边界**

每个进程拥有独立的虚拟地址空间。**这是硬隔离**：进程 A 不可能访问到进程 B 的内存（除非通过 IPC 显式共享）。

这是进程"安全"的根本：

- 进程 A 崩溃不会破坏进程 B 的内存（故障隔离）
- 进程 A 的内存泄漏不会影响进程 B（资源隔离）
- 进程 A 不可能读取进程 B 的私密数据（安全隔离）

代价：进程间通信必须经过内核（copy 或 mmap），有性能开销。

**约束二：进程创建有固定成本**

每次创建进程都要做：

- 分配地址空间（页表）
- 复制或映射代码段
- 加载动态库（dyld / linker）
- 启动运行时（VM / Native）
- 执行入口函数

```
   Android Zygote fork：     ~200-400ms（共享 ART，省去 VM 启动）
   iOS exec：               ~200-300ms（每次都要 dyld + libObjC）
   Web 新 Tab：             ~100-500ms（视浏览器实现）
   Linux fork+exec：        ~10-100ms（不含应用初始化）
```

**这就是为什么 Android 用 Zygote 模型 fork**：共享父进程的 ART，省去每次都重启 VM 的 ~500ms 开销。

**约束三：进程间通信必经内核**

任何 IPC 形式（Binder / Pipe / Socket / Shared Memory）都要经过内核：

```
   进程 A 用户态 ──[陷入内核]──▶ 内核中转 ──[切回用户态]──▶ 进程 B 用户态
        │                              │
     一次 syscall                   一次 syscall
     ~1-5μs                        ~1-5μs
```

即使是"零拷贝"的 Shared Memory，初次建立映射仍需 syscall。这是 IPC 的物理底线。

### 2.2 隔离与通信模型

**为什么"隔离 vs 通信"是进程治理核心**

进程的本质收益是"隔离"，本质代价是"通信"。所有多进程设计都在权衡这两者：

```
   ┌────────────────────────────────────────────────┐
   │ 隔离收益                                        │
   │ - 故障隔离（子进程崩溃，主进程不受影响）          │
   │ - 内存隔离（子进程内存大不影响主进程）            │
   │ - 安全隔离（沙箱 / 权限独立）                    │
   ├────────────────────────────────────────────────┤
   │ 通信代价                                        │
   │ - IPC 延迟（每次调用 1-50ms）                    │
   │ - 数据序列化开销（Parcel / Codable）             │
   │ - 内存浪费（每个进程独立的运行时 / 资源副本）      │
   │ - 启动开销（200-500ms 冷启动）                    │
   └────────────────────────────────────────────────┘
```

**典型多进程设计模式**：

```
   ┌──────────────────────────────────────────┐
   │ A. 单进程（主流）                          │
   │    所有功能在主进程，无 IPC               │
   │    优点：无 IPC 开销                      │
   │    缺点：一处崩溃全死                      │
   ├──────────────────────────────────────────┤
   │ B. 主进程 + 风险隔离                       │
   │    主进程 + Web 内核进程 / 视频解码 / 推送 │
   │    优点：风险代码不会拖垮主进程            │
   │    缺点：IPC 开销可控                      │
   ├──────────────────────────────────────────┤
   │ C. 主进程 + 守护 / 保活                    │
   │    主进程 + 守护进程（互相拉起）          │
   │    优点：增加保活成功率（Android）         │
   │    缺点：被系统打压、用户反感              │
   ├──────────────────────────────────────────┤
   │ D. 插件化 + 进程隔离                       │
   │    各业务在独立进程                       │
   │    优点：彻底解耦                          │
   │    缺点：内存翻倍，IPC 复杂                │
   └──────────────────────────────────────────┘
```

**关键认知**：

- **大多数应用只需 A**（单进程）。
- **B 是合理的折中**（风险代码隔离）。
- **C 在 Android 8+ 后基本失效**（系统强力打压）。
- **D 仅超大型应用使用**（如微信、支付宝 30+ 进程）。

> ▶▶ **回扣 §00.5 案例**：金融 App 的 5 进程架构本质是 **B + C + 过度拆**——主+WebView 是合理 B；守护/拉活是失效的 C；Push 进程是过度拆（其实可以合并）。**80% 应用应该用 A，少数用 B，几乎没人需要 C**。这个分类就是案例 Day 2 决策表的理论基础。

### 2.3 跨平台同构原理

**为什么所有平台的进程模型都同构**

底层都是 POSIX `fork()` 或其衍生（Windows `CreateProcess`），上层封装不同。

```
   通用进程模型：

      [应用层]
      Activity 进程 / WKWebView 进程 / Worker / 插件
              │
              ▼
      [运行时层]
      Android ContentProvider / NSXPCConnection / postMessage
              │
              ▼
      [系统层]
      fork / clone / CreateProcess
              │
              ▼
      [内核]
      task_struct / virtual address space
```

每个平台都必须有：

| 抽象组件 | 解决什么问题 |
|---|---|
| 进程创建 | 分配地址空间 + 加载代码 + 启动入口 |
| IPC 机制 | 提供"跨地址空间数据传输" |
| 生命周期管理 | 进程何时拉起 / 何时被杀 |
| 资源限制 | 每个进程能用多少内存 / CPU |

**正因为它们都长这个样子，进程性能问题的本质也是同一个**：

> **进程问题 = 隔离与通信的平衡问题。同构原理决定了治理思路通用。**

**跨平台术语对照**

| 通用术语 | Android | iOS | Web | C/C++ |
|---|---|---|---|---|
| 进程创建 | Zygote fork | exec / posix_spawn | Tab / Worker 进程 | fork |
| IPC 同步 | Binder / Messenger | NSXPCConnection | postMessage | Pipe / Socket |
| 共享内存 | MemoryFile / ASharedMemory | mmap | SharedArrayBuffer | shm_open |
| 子进程 | `<service android:process=":xxx">` | App Extension | Web Worker / iframe | fork |
| 守护 | JobScheduler / WorkManager | Background Task | Service Worker | systemd |
| 进程上限 | 取决于 ROM | 严格（前台 1 + 扩展若干）| 视浏览器 | 视 OS |

**同构带来的工程价值**

理解同构原理后：

1. **IPC 选型思路通用**：高频小数据用消息队列；低频大数据用共享内存。
2. **进程拆分原则通用**：风险隔离 / 资源隔离 / 启动隔离 三大动机。
3. **保活策略局限通用**：现代 OS 都在打压"持久后台"，应用应顺应而非抗拒。

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web | C/C++ Linux |
|---|---|---|---|---|
| 默认模式 | 单进程为主，可显式拆 | 强制单进程（仅 Extension）| 每 Tab 一个 | 自由 |
| IPC 机制 | Binder（高性能）| XPC | postMessage | Pipe / Socket / shm |
| Binder 性能 | 同步 < 5ms | XPC 同步 < 10ms | postMessage < 10ms | varies |
| 共享内存 | MemoryFile（ashmem） | mmap | SharedArrayBuffer | shm |
| 启动开销 | 200-400ms（Zygote） | 200-300ms | 100-500ms | 10-100ms |
| 保活限制 | 8.0+ 严格 | 严格（仅特定模式）| Service Worker 有时限 | 视系统 |
| 进程上限 | 系统全局 ~100 | 应用 ~5（含扩展）| 浏览器 ~100 | 系统 limit |

> 后续遇到平台特化点回引本节。

## 03.度量与采集

### 3.1 三类采集方案的本质

所有平台的进程采集方案，本质上只有 3 类：

```
   进程拉起 ──▶ 进程运行 ──▶ IPC 通信 ──▶ 进程退出
        │           │            │           │
        ▼           ▼            ▼           ▼
   ① 进程清单（snapshot）
                ② 资源监控（PSS/RSS/CPU per process）
                            ③ IPC trace（Binder log / XPC events）
```

---

**① 进程清单**

**核心原理（一句话）**：定期采集系统 / 应用所有进程的列表 + 基本信息。

**工作机理**：

- Android：`ActivityManager.getRunningAppProcesses()` / `/proc/[pid]`
- iOS：`sysctl(CTL_KERN, KERN_PROC, ...)`
- Linux：`/proc` 遍历

**物理本质**：把进程作为可数对象做实例清单。

**适用边界**：监控进程数膨胀、跨进程关联问题。

---

**② 资源监控（按进程）**

**核心原理（一句话）**：对每个进程持续采集 PSS / RSS / CPU 占用，判断哪个进程是热点。

**工作机理**：

- Android：`Debug.MemoryInfo` per process / `dumpsys meminfo` / `/proc/[pid]/stat`
- iOS：`proc_pid_rusage` / Instruments
- Web：Chrome `chrome://process-internals`

**物理本质**：进程是资源分配单位，按进程统计才有意义。

**适用边界**：定位"谁在消耗内存 / CPU"。

---

**③ IPC trace**

**核心原理（一句话）**：抓取 IPC 调用的事件，记录"谁向谁请求、多久返回、什么数据量"。

**工作机理**：

- Android：`adb shell dumpsys binder` / Perfetto Binder Track
- iOS：Instruments XPC
- Web：DevTools Performance 看 postMessage

**物理本质**：IPC 是进程间唯一通信通道，了解 IPC 模式 = 了解多进程行为。

**适用边界**：诊断 IPC 性能瓶颈、查找 IPC 风暴。

---

**三种方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 进程清单 | 系统 API | 进程级 | 极低 | 高 | ✅ | 无运行细节 |
| ② 资源监控 | 系统 API | 进程级时序 | 低 | 高 | ✅ | 无 IPC 信息 |
| ③ IPC trace | 内核 / 框架 | 事件级 | 高 | 中（需权限）| ❌ | 数据量大 |

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| 进程数膨胀 | ✅ | 间接 | ❌ |
| 单进程内存高 | ❌ | ✅ | ❌ |
| IPC 调用风暴 | ❌ | 间接 | ✅ |
| 子进程被杀 | 部分 | 部分 | ❌ |
| Binder 阻塞 | ❌ | 部分 | ✅ |

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web | Linux |
|---|---|---|---|---|
| 进程清单 | `ActivityManager.getRunningAppProcesses` | `sysctl KERN_PROC` | `chrome://process-internals` | `/proc` |
| 单进程内存 | `Debug.MemoryInfo` per process | `task_vm_info per pid` | Chrome Task Manager | `pmap` |
| IPC trace | Perfetto Binder Track | Instruments XPC | DevTools | `strace` |
| 子进程拉起 | logcat AMS | NSWorkspace logs | DevTools | `ps -ef` |

### 3.4 数据可信度评估

| 数据 | 可信度 | 偏差来源 |
|---|---|---|
| 进程数 | 高 | 系统直接读 |
| 单进程 PSS | 高 | 系统统计 |
| IPC 调用次数 | 中（抽样）| 高负载下可能丢日志 |
| IPC 延迟 | 高（trace）| 仅 trace 时段有效 |

## 04.归因方法

### 4.1 进程问题决策树

```
进程问题
   │
   ├── 进程数过多 ────▶ 看每个进程的用途
   │                   ├─ 必要的子进程：保留
   │                   ├─ 仅"为隔离"开的：评估是否值得
   │                   └─ 守护进程：考虑删除
   │
   ├── 单进程内存爆 ──▶ 走 OOM 决策树（见卷二·03）
   │
   ├── IPC 延迟高 ────▶ 看 IPC 模式
   │                   ├─ 频繁小请求：合并 / 缓存
   │                   ├─ 单次大数据：用共享内存
   │                   └─ 阻塞等返回：改异步
   │
   ├── 主进程被杀 ────▶ 看被杀原因（ProcessExitReason）
   │                   ├─ LMK：内存压力
   │                   ├─ ANR：主线程卡死
   │                   └─ Force Stop：用户手动 / 系统设置
   │
   └── 子进程频繁拉起 ──▶ 看触发源
                       ├─ ContentProvider 跨进程查询
                       ├─ Broadcast 拉起
                       └─ 服务调用
```

> 反直觉问题 ⑥ 答案：保活做得"再好"也敌不过用户主动清理 / 系统强制限制。应用应主打"快速重启 + 状态恢复"而不是"永不被杀"。

> ▶▶ **回扣 §00.5 案例**：金融 App Day 2 逐进程评估正是"进程数过多"分支的标准操作——
> - Push 进程 → "仅每天 8-12 次干活" → 不值得 → 合并到主。
> - 守护/拉活进程 → "仅为保活" → 系统打压无效 → 删除。
> - WebView 进程 → "风险隔离" → 必要 → 保留。
>
> **同一个决策树分支，对不同进程导出完全不同的结论**——这才是分类思考的价值。

### 4.2 IPC 性能归因

IPC 性能 = **每次调用开销** × **调用频次** + **数据序列化开销**

```
   IPC 单次开销 ≈ 切换到内核（1μs） + 内核中转（1-5μs） + 切换回用户态（1μs）
   ≈ 3-7μs base

   加上序列化（视数据大小）：
   - 小数据 (< 1KB)：base + ~10μs = ~15μs
   - 中数据 (~10KB)：base + ~100μs = ~110μs
   - 大数据 (>1MB)：base + ~5ms（Parcel 不支持，会失败）→ 必须用共享内存
```

**典型 IPC 性能问题**：

| 模式 | 问题 | 修复 |
|---|---|---|
| 循环中 IPC | 每次循环跨进程查 | 批量获取 |
| 跨进程 ContentProvider 频繁查 | 每次 binder 调用 | 本地缓存 |
| 大对象通过 Binder 传 | 序列化失败 / 超时 | 共享内存 + 句柄传递 |
| 同步等待远端返回 | 主线程阻塞 | 改异步 |

### 4.3 进程拉起归因

子进程被拉起的常见触发源：

- **ContentProvider 调用**：跨进程查询会拉起目标进程
- **Service bindService**
- **Broadcast 接收（隐式 / 显式）**
- **Intent.startActivity** (跨进程)
- **Job / WorkManager 调度**

**优化思路**：

- 必要的拉起：缓存结果，避免反复拉起。
- 非必要的拉起：合并 / 移到主进程 / 延迟。

### 4.4 内存共享归因

多进程内存浪费的根因：

- 每个进程有自己的 ART / V8 / Native runtime（~30-50MB 起步）
- 资源（drawable / asset）会重复加载（部分通过 mmap 共享）
- 业务对象会重复初始化（如 SDK 在每个进程都 init）

**减少浪费的手段**：

- 资源用 mmap（系统已自动处理大部分）
- SDK 只在主进程 init，子进程通过 IPC 拿数据
- 评估每个子进程"真的有必要"吗

## 05.求证实验 ⭐

### 5.1 实验一：进程启动代价

**Step 1 — 原始观察**

工程师都说"进程启动慢"，但**多慢？什么因素决定？**

**Step 2 — 提出疑问**

> **Android Zygote fork 一个新进程的物理代价是多少？iOS exec 又是多少？**

**Step 3 — 形成假设**

**H₁**：Android Zygote fork（共享父 VM）~200ms；iOS exec（每次重启 dyld）~250ms；纯 Linux fork ~10ms。  
**H₀**：进程启动几乎瞬时。

**Step 4 — 数学推导**

Android Zygote fork 路径：

```
   ① Zygote socket 接收命令      ~5ms
   ② fork（copy 页表）           ~20ms
   ③ 设置进程标识 / 安全策略     ~20ms
   ④ 启动 ActivityThread.main   ~50ms
   ⑤ Application.attachBaseContext + onCreate ~100ms+
   ─────────────────────────────
   总计 ~200ms+
```

iOS posix_spawn 路径：

```
   ① 进程创建                 ~10ms
   ② dyld 加载所有 dylib       ~100ms
   ③ libObjC 初始化           ~50ms
   ④ +load + static init       ~50ms+
   ─────────────────────────────
   总计 ~210ms+
```

**Step 5 — 设计实验**

| 项 | 配置 |
|---|---|
| Android | Pixel 6，测试 ContentProvider 跨进程调用拉起子进程的总时长 |
| iOS | iPhone 12，测试 App Extension 拉起总时长 |
| Linux | Pixel 6 命令行 `time fork+exec /bin/true` |
| 主指标 | 从触发到子进程可响应的时间 |

**Step 6 — 实测数据**

| 平台 | 测试场景 | 启动时长（中位）|
|---|---|---|
| Android Zygote fork | ContentProvider 跨进程 | 230 ms |
| Android no-Zygote（手动 spawn）| 命令行 | 800 ms |
| iOS App Extension | 触发 sharing extension | 280 ms |
| iOS posix_spawn 命令行 | /usr/bin/true | 50 ms |
| Linux fork + exec | /bin/true | 8 ms |
| Web 新 Tab | window.open 启动新进程 | 220 ms |

**Step 7 — 验证 / 修正**

- Android 与公式预测 ~200ms 一致。
- iOS Extension 比公式略高（含 XPC 握手）。
- 纯 Linux fork+exec 极快（仅 8ms），因为不含应用初始化。

**Step 8 — 提炼结论**

> **应用级进程启动开销 200-300ms，远高于线程创建（μs 级）。  
> 频繁拉起子进程的性能代价巨大。**

工程意义：

- 子进程要**保持常驻**，不要频繁拉起 / 销毁。
- 一次性任务用线程，长期任务才用进程。
- IPC 设计上要避免"按需拉起"的模式。

**Step 9 — 边界**

- 设备性能差异大（低端机可能 500ms+）。
- 包含大量 +load / static initializer 的应用 iOS 更慢。

---

### 5.2 实验二：IPC 吞吐量

**Step 1 — 原始观察**

很多团队"凭感觉"用 IPC，但**IPC 的吞吐瓶颈在哪？什么时候需要换共享内存？**

**Step 2 — 提出疑问**

> **不同数据大小下，Binder（Android）/ XPC（iOS）/ postMessage（Web）的吞吐量是多少？**

**Step 3 — 形成假设**

**H₁**：小数据吞吐 100K+ 次/秒，被切换开销主导；大数据吞吐受序列化 + 拷贝主导，1MB 数据 < 1000 次/秒。  
**H₀**：IPC 吞吐与数据大小无关。

**Step 4 — 数学推导**

Binder 单次调用 ~3μs base + 拷贝（视数据大小）：

```
   100B 数据：base + ~1μs 拷贝 = ~4μs → 250K op/s
   10KB 数据：base + ~100μs 拷贝 = ~103μs → 10K op/s
   1MB 数据：base + ~10ms 拷贝 = ~10ms → 100 op/s
```

**Step 5 — 设计实验**

| 项 | 配置 |
|---|---|
| Android | 主进程 ↔ 子进程 Binder 双向调用 |
| iOS | XPC 同样测试 |
| Web | postMessage 跨 Worker |
| 数据大小 | 100B / 1KB / 10KB / 100KB / 1MB |
| 主指标 | 每秒可完成的"调用 + 返回" |

**Step 6 — 实测数据**

| 数据大小 | Android Binder | iOS XPC | Web postMessage |
|---|---|---|---|
| 100B | 220K op/s | 180K op/s | 90K op/s |
| 1KB | 180K op/s | 150K op/s | 80K op/s |
| 10KB | 65K op/s | 55K op/s | 35K op/s |
| 100KB | 9K op/s | 7K op/s | 5K op/s |
| 1MB | 950 op/s | 700 op/s | 500 op/s |

**Step 7 — 验证 / 修正**

- 与公式预测一致：小数据被调用开销主导，大数据被拷贝主导。
- 1MB 数据已经接近不可用（< 1000 op/s），必须换共享内存。

**Step 8 — 提炼结论**

> **IPC 吞吐量随数据大小急剧下降。  
> 100B 数据 200K/s 可用；100KB 数据 < 10K/s 需要谨慎；1MB+ 必须用共享内存。**

工程意义：

- 频繁小数据交互直接 IPC（绰绰有余）。
- 大数据传输（图片 / 视频帧）必须共享内存。
- 跨进程接口设计避免"返回大对象"。

**Step 9 — 边界**

- Android Binder 单次最大 ~1MB（超过会异常）。
- iOS XPC 没有硬限制但性能急剧下降。
- 共享内存初次建立有开销（~1ms），少次大数据用 IPC 更快。

### 5.3 实验三：保活策略效果

**Step 1 — 原始观察**

Android 应用做"保活"投入巨大，但**实际效果如何？8.0+ 后还有效吗？**

**Step 2 — 提出疑问**

> **各种保活手段（互拉、双进程、JobScheduler、前台 service）在不同 Android 版本上的存活率是多少？**

**Step 3 — 形成假设**

**H₁**：Android 8.0+ 后系统强力打压后台进程；除了前台 Service（带通知），其他保活手段存活率从 60-80% 降到 20-40%。  
**H₀**：保活仍然有效。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | 多机型（Android 7 / 9 / 11 / 13）|
| 保活手段 | (a) 双进程互拉 (b) JobScheduler 周期任务 (c) 前台 Service 带通知 (d) 无任何手段 |
| 场景 | 应用退出 → 在不同时长后检查是否还活 |
| 主指标 | 30 分钟 / 2 小时 / 8 小时存活率 |

**Step 5 — 实测数据**

| 保活手段 | A7 30min | A11 30min | A13 30min | A13 8h |
|---|---|---|---|---|
| 无 | 35% | 15% | 10% | 0% |
| 双进程互拉 | 70% | 25% | 18% | 2% |
| JobScheduler | 60% | 45% | 40% | 25% |
| 前台 Service | 95% | 88% | 85% | 75% |

**Step 6 — 验证 / 修正**

- 双进程互拉在 A11+ 几乎失效。
- JobScheduler 是合规但效果有限。
- 只有前台 Service（带通知，用户可见）才能稳定保活。

**Step 7 — 提炼结论**

> **Android 11+ 后"暗保活"（互拉、闪后台）几乎全部失效。  
> 唯一有效手段是前台 Service（带可见通知），需要用户感知。**

工程意义：

- 投入做"暗保活"是低 ROI 工作，应放弃。
- 转而做"快速重启 + 状态恢复"：被杀后能快速拉起，且无感恢复状态。
- 重要任务用 `WorkManager`（系统调度，合规）。

**Step 8 — 边界**

- iOS 完全无保活概念（特定模式如 location / VoIP 除外）。
- Web Service Worker 有时长限制（30 秒 / 浏览器决定）。

> ▶▶ **回扣 §00.5 案例**：本实验"双进程互拉 A13 30min 存活率仅 18%"直接打脸经验派第 1 周"加强双进程互拉保活"——加强后被杀率反而升到 22%。**这是把"硬抗系统"变现为线上事故的真实样本**。方法派 Day 3 用这份实验数据说服架构师，节省了大量"权威讨论"时间。**数据驱动的最大价值是阻止低 ROI 的努力**。

---

### 5.4 实验四：跨进程 ContentProvider 风暴的性能崩溃

**Step 1 — 原始观察**

很多 SDK 用 ContentProvider 跨进程查配置。**单次很便宜，循环或高频调用会怎样？**

**Step 2 — 提出疑问**

> **同一段业务，"循环 100 次跨进程 ContentProvider 查询" vs "批量一次查询"的总耗时差多少？**

**Step 3 — 形成假设**

**H₁**：每次 ContentProvider 查询 ~5ms（含 Binder 跨进程 + 拉起回填）。100 次 = 500ms 主线程阻塞；批量一次 ~8ms。  
**H₀**：差异不明显。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 场景 | 主进程查 ":push" 子进程的 ContentProvider 拿 100 个配置项 |
| 实现 A | 循环 100 次 `contentResolver.query()` |
| 实现 B | 批量一次查询，子进程返回 JSON/Bundle 包 |
| 实现 C | 主进程本地缓存（启动加载一次）|
| 设备 | Pixel 6 |

**Step 5 — 实测数据**

| 实现 | 总耗时 | 子进程被拉起次数 |
|---|---|---|
| A 循环 100 次 | 480 ms | 1 次（仅首次拉起后保持） |
| 极端：A + 每次后子进程自动退出 | 22,000 ms | 100 次 |
| B 批量一次 | 8 ms | 1 次 |
| C 本地缓存（启动加载）| 0.05 ms | 0 次 |

**Step 6 — 验证 / 修正**

- A 循环 100 次主线程阻塞 480ms 直接 ANR 临界。
- 子进程会被反复唤醒时极端情况 22 秒（典型 SDK 反模式）。
- B 批量比 A 快 60×；C 本地缓存比 B 快 160×。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **跨进程 ContentProvider 严禁循环调用。必须批量化或本地缓存。  
> "看起来 5ms 一次的调用"在循环中可以累积到秒级，制造 ANR 风险。**

工程意义：

- 上层抽象层禁止循环 IPC（lint 拦截）。
- SDK 设计应提供 batch API。
- 主进程本地缓存配置；只在变更时跨进程同步。

**Step 8 — 边界**

- 跨进程查询频次低时（< 10/s）直接调用也可接受。
- 缓存一致性需通过 push invalidation 或版本号。

### 5.5 实验五：快速重启 + 状态恢复 vs 暗保活的用户体验对比

**Step 1 — 原始观察**

[§5.3 实验](#53-实验三保活策略效果) 证明保活失效。但**"放弃保活 + 投资快速重启"真的能匹敌？用户感知如何？**

**Step 2 — 提出疑问**

> **同样被系统杀掉，"暗保活（拉起仍是冷启）" vs "快速重启 + 状态恢复"在用户感知上差异多大？**

**Step 3 — 形成假设**

**H₁**：暗保活成功率 < 40%，且拉起仍需冷启；快速重启 100% 成功，且 < 800ms 完成且状态恢复，用户感知"流畅得多"。  
**H₀**：暗保活体验更好。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 + 红米（Android 13）|
| 场景 | 模拟用户中断 30min/2h/8h 后回归 |
| 实现 A | 暗保活（双进程互拉）|
| 实现 B | 完全放弃保活 + 快速重启 +状态恢复（保存最后页面+滚动位置+草稿）|
| 测试用户 | 30 名 |
| 主指标 | 主观流畅度 1-5、客观回到上次状态的时长 |

**Step 5 — 实测数据**

| 离开时长 | A 暗保活存活率 | A 用户回到状态时长 | B 重启时长 | B 用户回到状态时长 | A 评分 | B 评分 |
|---|---|---|---|---|---|---|
| 30 min | 38% | 2.5s（命中）/ 4.2s（冷启）| 100% | 0.9s | 3.2 | **4.6** |
| 2 h | 18% | 4.5s | 100% | 0.9s | 2.8 | **4.5** |
| 8 h | 5% | 4.8s | 100% | 0.95s | 2.4 | **4.5** |

**Step 6 — 验证 / 修正**

- B 实测平均回到状态的时长 < 1s（含冷启 + 状态恢复）。
- A 在长时间离开后存活率几乎为零，且冷启后用户回到主页"重新登录、找上次浏览的位置"。
- 用户主观分 B 显著高于 A。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **放弃保活 + 投资快速重启是更高 ROI 的路径：100% 成功率 vs 5-38% 存活率；< 1s 体验 vs > 4s 冷启。**

工程意义：

- 关键状态（最后页面 / 滚动位置 / 输入草稿 / 登录态）持久化到磁盘。
- 启动期优先恢复状态，再渐进加载其他内容。
- 与冷启动篇（[`卷四·01`](../04.业务专项篇/01.App冷启动优化.md)）结合做 P95 < 800ms。

**Step 8 — 边界**

- IM/直播类需要长连接的应用，仍需前台 Service。
- 状态恢复要做版本兼容（旧状态 + 新代码）。

### 5.6 五大实验启示

```
   进程启动代价（200-300ms） → 不要频繁拉起子进程        ─┐
                                                          │
   IPC 吞吐量             → 大数据必用共享内存             │
                                                          │
   保活几乎失效           → 转向"快速重启 + 恢复"          ├─▶ 多进程 = 重资源，每开必算账
                                                          │
   ContentProvider 风暴   → 严禁循环 IPC，必须批量化        │
                                                          │
   快速重启 vs 暗保活     → 100% 成功率 + <1s 体验          ─┘
```

**统一启示**：

- **多进程是"重武器"**，每开一个进程都要算清成本收益。
- **顺应系统而非对抗**：现代 OS 都在打压持久后台，硬抗代价大。
- **快速重启 > 永不被杀**：投资"被杀后的恢复体验"，比投资"保活"ROI 高得多。
- **IPC 频次 > IPC 单次开销**：单次便宜的接口，循环调用一样杀人。
- **大数据必用共享内存**：Binder/XPC 在 1MB+ 数据下不可用。

## 06.优化策略深化

> 本节回答四个递进问题：**①如何让进程数量收敛？②如何让 IPC 不再是瓶颈？③什么样的代码值得拆进程？④如何放弃保活拥抱重启？**  
> 与"多进程优化清单"不同，本文按进程治理的因果链分层施治——不解决"该不该拆"就谈"怎么优化"是本末倒置。

### 6.1 第一层：进程数量收敛（删除非必要子进程）

**核心命题**：[§00.5 案例](#005-贯穿案例金融-app5-进程架构-oom-与冷启慢事件) 证明这是最高 ROI 的优化。这一层不是"如何拆"，而是"为什么不能拆"。

**策略 1.1：逐进程价值评估表**

- **机理**：用统一格式逐进程评估，把"模糊架构"变成"可量化决策"。
- **代码**（评估模板）：

```
| 进程名 | 真实工作时长占比 | 内存占用 | 必要性等级 | 决策 |
| 主进程 | 100% | 200MB | 必要 | 保留 |
| Push 进程 | < 0.5%（每天 8-12 次）| 80MB | 不必要（可合并）| 删除 |
| 守护进程 | 0%（仅为保活，A11+ 失效）| 35MB | 无效 | 删除 |
| WebView 进程 | 30% | 60MB | 必要（风险隔离）| 保留 |
```

- **收益**：[§00.5 案例](#005-贯穿案例金融-app5-进程架构-oom-与冷启慢事件) 5→2 进程，PSS -47%。
- **边界**：评估需架构师参与；删除进程涉及业务方协调。

**策略 1.2：Push 进程合并到主进程（用 FCM/系统级推送）**

- **机理**：现代推送通道（FCM/APNs/华为/小米推送）都是系统级，应用层不需要自己保持长连接进程。
- **代码**（FCM）：

```kotlin
class MyFCMService : FirebaseMessagingService() {
    override fun onMessageReceived(message: RemoteMessage) {
        // 直接在主进程接收，无需独立进程
        handlePush(message.data)
    }
}
```

- **收益**：节省 50-80MB 常驻内存；推送到达率反而升（FCM 比自建长连接稳定）。
- **边界**：海外用 FCM，国内用厂商推送+融合 SDK；自建长连接仅 IM 等强实时业务。

**策略 1.3：删除守护/拉活进程（保活无效）**

- **机理**：[§5.3 实验](#53-实验三保活策略效果) 双进程互拉 A11+ 几乎全失效；占内存还被系统打压。
- **代码**：直接删除 `<service android:process="...">` 和相关 BroadcastReceiver。
- **收益**：[§00.5 案例](#005-贯穿案例金融-app5-进程架构-oom-与冷启慢事件) 节省 60MB + 主进程被杀率 22%→3%。
- **边界**：业务方可能依赖"保活"假设，需 review 并提供 WorkManager 替代方案。

**策略 1.4：评估每个 ContentProvider 是否真需要独立进程**

- **机理**：很多 SDK 用 `android:process=":xxx"` 默认拆，但实际不必要。
- **代码**：

```xml
<!-- 反例：默认拆，但实际 SDK 在主进程也工作 -->
<provider android:name="..." android:process=":sdk" />
<!-- 正例：合并到主进程 -->
<provider android:name="..." />
```

- **收益**：每删一个进程节省 30-50MB。
- **边界**：需测试 SDK 在主进程的兼容性。

---

### 6.2 第二层：IPC 性能治理（让通信不再是瓶颈）

**核心命题**：[§5.2](#52-实验二ipc-吞吐量) + [§5.4](#54-实验四跨进程-contentprovider-风暴的性能崩溃) 证明 IPC 不当使用会让多进程不可用。

**策略 2.1：IPC 批量化（杜绝循环 IPC）**

- **机理**：[§5.4 实验](#54-实验四跨进程-contentprovider-风暴的性能崩溃) 循环 100 次 vs 批量 1 次差 60×。
- **代码**：

```kotlin
// 反例
configs.forEach { key ->
    val value = remoteService.get(key)  // 100 次跨进程
    ...
}

// 正例
val map = remoteService.getBatch(configs)  // 1 次
```

- **收益**：循环场景从 500ms 阻塞降到 8ms。
- **边界**：批量 API 设计要避免单次过大（> 100KB 走共享内存）。

**策略 2.2：主进程本地缓存 + Push 失效**

- **机理**：跨进程数据"启动加载一次 + 变更时 push 失效"是最高效模式。
- **代码**：

```kotlin
class ConfigCache {
    private val cache = ConcurrentHashMap<String, String>()
    fun init() {
        cache.putAll(remoteService.getAll())  // 启动一次
    }
    // 远端变更时通过 broadcast / observer 通知
    fun onConfigChanged(key: String, value: String) {
        cache[key] = value
    }
    fun get(key: String) = cache[key]  // 零 IPC
}
```

- **收益**：日常读 0 IPC；变更时一次 push。
- **边界**：内存换性能，仅适合数据量不大（< 10MB）的场景。

**策略 2.3：大数据用共享内存**

- **机理**：[§5.2 实验](#52-实验二ipc-吞吐量) 1MB Binder < 1000 op/s 实际不可用。
- **代码**（Android `SharedMemory` API 27+）：

```java
SharedMemory shm = SharedMemory.create("frame", frameSize);
ByteBuffer buffer = shm.mapReadWrite();
// 通过 Binder 传递 SharedMemory 句柄
remoteService.submitFrame(shm);
```

- **代码**（iOS `mach_vm_remap`/POSIX `shm_open`）：略。
- **收益**：图片/视频帧/大 JSON 传输延迟 -90%。
- **边界**：首次建立 mmap 有 1-2ms 开销；少次大数据可能不如直接 IPC。

**策略 2.4：异步化 IPC + Future 模式**

- **机理**：主线程同步等远程返回 = ANR 风险（[`卷三·04 §6.2 策略 2.2`](../03.流水线专项/04.ANR监控与治理.md)）。
- **代码**：

```aidl
// oneway 方法不阻塞调用方
interface IRemoteService {
    oneway void doAsync(in Request r);
}
```

- **收益**：主线程永不被 IPC 阻塞。
- **边界**：oneway 不能有返回值；需 RemoteCallback 异步回调。

---

### 6.3 第三层：风险隔离与稳定性（值得拆的才拆）

**核心命题**：不是所有"为了稳定"的拆都合理。[§00.5 案例](#005-贯穿案例金融-app5-进程架构-oom-与冷启慢事件) 5 个进程只有 WebView 是真正合理的隔离。

**策略 3.1：WebView 强制进程外（必要的拆）**

- **机理**：H5 内容 JS 崩溃 / 内存泄漏会直接拖垮主进程。Android WebView 默认在主进程，必须显式启用多进程。
- **代码**：

```kotlin
class MyApp : Application() {
    override fun onCreate() {
        super.onCreate()
        WebView.setDataDirectorySuffix("multi")
        // 多进程 WebView 通过 WebView 5.0+ 自动启用（API 28+）
    }
}
```

- **收益**：[§7.1 案例](#71-跨端同构案例) 主进程崩溃率 0.18%→0.04%。
- **边界**：WebView 进程也占 60-80MB；H5 业务少时不必拆。

**策略 3.2：高风险第三方 SDK 进程隔离**

- **机理**：闭源 SDK（如某些视频解码 / RTC / 推流）质量不可控，崩溃会拖垮主进程。
- **代码**：

```xml
<service android:name=".RtcService"
    android:process=":rtc" />
```

- **收益**：第三方崩溃不再影响主进程。
- **边界**：SDK 必须支持跨进程调用；增加 IPC 复杂度。

**策略 3.3：大对象处理进程隔离**

- **机理**：图像识别 / 视频解码 / 大文件处理瞬间内存可能 200MB+，独立进程被杀也不影响主进程。
- **代码**：见策略 3.2。
- **收益**：主进程内存稳定，OOM 风险隔离。
- **边界**：处理结果通过共享内存返回；启动开销需评估。

**策略 3.4：ProcessExitReason 监控（事后分析）**

- **机理**：Android 11+ `getHistoricalProcessExitReasons` 给出进程被杀原因。
- **代码**：

```kotlin
val am = context.getSystemService(ActivityManager::class.java)
am.getHistoricalProcessExitReasons(null, 0, 100)
    .forEach { upload(it.reason, it.processName, it.pss) }
```

- **收益**：分类统计被杀原因（LMK/ANR/Force Stop/JNI Crash），针对性优化。
- **边界**：仅 Android 11+；部分 OEM 实现不全。

### 6.4 第四层：放弃保活，拥抱快速重启

**核心命题**：[§5.5 实验](#55-实验五快速重启--状态恢复-vs-暗保活的用户体验对比) 证明快速重启 +状态恢复 > 暗保活。这一层是范式转移。

**策略 4.1：关键状态持久化**

- **机理**：被杀时立即持久化（最后页面/滚动位置/输入草稿/登录态/购物车等）。
- **代码**：

```kotlin
class StateRecoveryManager(context: Context) {
    private val prefs = context.getSharedPreferences("recovery", MODE_PRIVATE)
    
    fun saveState(page: String, scrollY: Int, draft: String?) {
        prefs.edit().apply {
            putString("last_page", page)
            putInt("scroll_y", scrollY)
            putString("draft", draft)
            putLong("save_ts", System.currentTimeMillis())
            apply()  // 异步，不阻塞
        }
    }
    
    fun restoreOnStart(): RestoreState? {
        val saveTs = prefs.getLong("save_ts", 0)
        if (System.currentTimeMillis() - saveTs > 24*3600*1000) return null  // 24h 过期
        return RestoreState(/* ... */)
    }
}
```

- **收益**：[§5.5 实验](#55-实验五快速重启--状态恢复-vs-暗保活的用户体验对比) 用户回到状态时长 4.5s→0.95s。
- **边界**：状态版本兼容（旧状态 + 新代码）；敏感信息加密。

**策略 4.2：启动期优先恢复状态**

- **机理**：启动序列改为"先渲染上次页面骨架 → 恢复滚动位置 → 再异步加载数据"。
- **代码**：见 [`卷四·01 §6`](../04.业务专项篇/01.App冷启动优化.md) 冷启动篇分级初始化策略。
- **收益**：感知冷启时间从 3s 降到 < 1s。
- **边界**：复杂业务需逐场景设计；不可滥用占位骨架。

**策略 4.3：合规后台任务用 WorkManager**

- **机理**：替代守护进程，系统调度，合规可靠。
- **代码**：

```kotlin
val work = PeriodicWorkRequestBuilder<MyWorker>(15, TimeUnit.MINUTES)
    .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
    .build()
WorkManager.getInstance(context).enqueueUniquePeriodicWork("sync", ExistingPeriodicWorkPolicy.KEEP, work)
```

- **收益**：合规且电池友好；不被系统打压。
- **边界**：调度延迟 10s-15min（视约束），实时性差任务不适用。

**策略 4.4：长连接业务用前台 Service（带通知）**

- **机理**：[§5.3 实验](#53-实验三保活策略效果) 唯一有效保活手段。
- **代码**：

```kotlin
class ChatForegroundService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = NotificationCompat.Builder(this, channelId)
            .setContentTitle("聊天已连接")
            .setSmallIcon(R.drawable.ic_chat)
            .build()
        startForeground(NOTIFICATION_ID, notification)
        return START_STICKY
    }
}
```

- **收益**：A13 8h 存活率 75%。
- **边界**：必须有用户可见的通知；滥用会被举报"流氓应用"。

### 6.5 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 | 对应策略 |
|---|---|---|---|---|---|
| 极高 | 评估并删除非必要子进程 | 内存 -30-50%、被杀率 -80% | 1-2 周 | 中 | 1.1-1.4 |
| 极高 | 大数据 IPC 改共享内存 | IPC 延迟 -90% | 1 周 | 低 | 2.3 |
| 极高 | 关键状态持久化 + 快速重启 | 体验 4.5s→1s | 2-3 周 | 中 | 4.1 + 4.2 |
| 高 | IPC 批量化 + 本地缓存 | IPC 频次 -80% | 1-2 周 | 低 | 2.1 + 2.2 |
| 高 | 放弃暗保活 + WorkManager | 系统评分提升、被打压减少 | 1-2 周 | 中（业务依赖）| 4.3 |
| 高 | Push 进程合并到主 | 节省 50-80MB | 1 周 | 中 | 1.2 |
| 中 | WebView 进程隔离 | 主进程崩溃 -75% | 几天 | 低 | 3.1 |
| 中 | 高风险 SDK 进程隔离 | 主进程稳定性提升 | 2-4 周 | 中 | 3.2 |
| 中 | ProcessExitReason 监控 | 长期防退化 | 几天 | 低 | 3.4 |
| 中 | 异步 oneway IPC | 主线程不被阻塞 | 1 周 | 低 | 2.4 |
| 中 | 大对象处理进程隔离 | OOM 风险隔离 | 2-3 周 | 中 | 3.3 |
| 中 | 前台 Service（长连接业务）| 长连接稳定 | 1 周 | 中（合规）| 4.4 |
| 低 | 自定义 Binder 替代 AIDL | 微优化 | 高 | 中 | - |
| 极低 | 自实现 IPC 协议 | 几乎无收益 | 极高 | 极高 | - |

**避免反向收益**：

- **过度拆进程**：每个业务都独立进程，内存翻 N 倍，启动慢 N 倍（[§00.5 案例](#005-贯穿案例金融-app5-进程架构-oom-与冷启慢事件) 5 进程 = 反例）。
- **死磕保活**：[§5.3](#53-实验三保活策略效果) 证明 A11+ 无效，投入大量精力对抗系统，最终被用户卸载。
- **小数据用共享内存**：建立 mmap 有开销，反而比 Binder 慢。
- **循环跨进程查询**：[§5.4](#54-实验四跨进程-contentprovider-风暴的性能崩溃) 一秒变 ANR。
- **加强保活治被杀**：[§00.5 案例](#005-贯穿案例金融-app5-进程架构-oom-与冷启慢事件) 第 1 周翻车的根因。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某社交应用主进程因加载 Web 内容偶发崩溃，影响主流程稳定性。Android / iOS / Web 都有需求。

**现象**：

- Android：第三方网页 JS 引起 WebView 崩溃，导致主进程崩溃，用户感知"应用退出"。
- iOS：WKWebView 已经进程外（系统级），无问题。
- Web：iframe 默认进程外（部分浏览器），无问题。

**度量与归因**：

Android WebView 默认在主进程渲染（除非显式启用多进程模式）。

**假设与求证**：

提出**统一假设**："Web 内容必须进程外渲染，避免拖垮宿主"。

**修复**：

- Android：启用 WebView 多进程模式（`WebView.setDataDirectorySuffix` + `setMultiProcessEnabled`）。
- iOS：保持 WKWebView（已经默认进程外）。
- Web：用户层不用关心。

**验证**：

| 平台 | 优化前主进程崩溃率（含 Web 原因）| 优化后 |
|---|---|---|
| Android | 0.18% | 0.04% |
| iOS | 0.05% | 0.05%（无变化） |
| Web | N/A | N/A |

**统一启示**：跨端原则 = **风险代码必须进程隔离**。Android 需要显式启用，iOS / Web 默认提供。

### 7.2 平台特异案例

**背景**：Android 应用拆了 3 个进程：主进程 / Push 进程 / 守护进程。内存高、ANR 多。

**现象**：常驻 PSS 300MB（主 200 + Push 70 + 守护 30）。

**度量与归因**：

- Push 进程实际只在收到推送时干活（每天 < 10 次），其余时间空转。
- 守护进程为了保活而存在，但 Android 11+ 后系统压制守护进程，效果差。

**假设与求证**：

**假设**：Push 进程合并到主进程；守护进程可以删除。

**实验**：

- 修复 1：Push 改在主进程接收（用 FCM 系统级唤起）。Push 子进程删除，节省 70MB。
- 修复 2：守护进程删除，改用 WorkManager 定期任务。节省 30MB。

**修复**：从 3 进程降到 1 进程。

**验证**：

- 常驻 PSS 从 300MB 降到 200MB（-33%）。
- OOM 率 -20%。
- 后台被杀率反而下降（系统不再判定为"贪婪应用"）。

**边界与上线策略**：少数特殊场景（如 IM 长连接）仍需独立进程，要评估清楚。

### 8.1 三道防线总览

```

   │             │              │
   ▼             ▼              ▼
```

### 8.2 编码期 Lint

- 新增 `<service android:process>` → 必须 review 评估必要性。
- 跨进程 Binder 接口传递大对象（> 100KB）→ 警告。
- 循环中调用跨进程 ContentProvider → 警告。
- 暗保活手段（互拉 BroadcastReceiver / 双进程互拉 service）→ 错误。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 应用启动期进程数 ≤ 阈值（如 3）。
- 主进程 PSS 基准值 ≤ 阈值。
- IPC 调用频次基准值。

**线上 SLO**：

- 应用进程总数 P95 < 4。
- IPC 调用 P99 < 50ms。
- 主进程被系统杀率 < 5%。
- ProcessExitReason 异常（非 USER 主动）< 10%。

## 10.总结与延伸

### 10.1 五条核心原则

1. **进程是重资源**：每开一个进程都要算清"隔离收益 vs 启动/内存/IPC 代价"——[§00.5 案例](#005-贯穿案例金融-app5-进程架构-oom-与冷启慢事件) 删 3 个进程节省 47% 内存是范例。
2. **多数应用单进程即可**：拆进程是"特殊需求"而非"默认选择"。
3. **风险代码必须隔离**：WebView / 高风险 SDK / 大对象处理是合理动机。
4. **大数据用共享内存**：[§5.2](#52-实验二ipc-吞吐量) 证明 1MB+ IPC 不可用，必须 shm。
5. **顺应系统而非对抗**：[§5.5](#55-实验五快速重启--状态恢复-vs-暗保活的用户体验对比) 证明快速重启 +状态恢复 > 暗保活。

### 10.2 五个常见误区

1. **"多进程一定比单进程稳定"**：错（子进程崩溃通过 IPC 影响主；过度拆反被系统打压）。
2. **"循环 IPC 没事"**：错（[§5.4](#54-实验四跨进程-contentprovider-风暴的性能崩溃) 100 次循环 500ms 直接 ANR）。
3. **"iOS 没多进程问题"**：基本对，但 Extension 仍有 IPC 性能问题。
4. **"保活做到极致就能不被杀"**：错（[§5.3](#53-实验三保活策略效果) A11+ 暗保活基本失效）。
5. **"加强保活能治被杀"**：错（[§00.5 案例](#005-贯穿案例金融-app5-进程架构-oom-与冷启慢事件) 第 1 周翻车：加强后被杀率反升）。

## 一句话总结

> **进程是"隔离单元，也是性能边界"，每开一个都要算账。  
> 删除非必要进程是最高 ROI 优化；大数据用共享内存；循环 IPC 必批量；保活无效，拥抱快速重启 + 状态恢复。  
> 多数应用 1-2 个进程足够；拆进程要有清晰动机；系统不再判定"贪婪"是最大奖励。  
> §00.5 那个"5 周经验派 vs 8 天方法派"的反差，正是这条路径的最锋利证据。**
