### 00 开篇导论

**0.1 一句话定位**

**IO 与存储性能是"看不见的杀手"——**它不像 CPU/内存那样直观可见，但 90% 的卡顿、ANR、启动慢的背后都有 IO 在作祟。一次主线程 fsync 可以让 60fps 直接掉到 6fps；一次 SQLite 写事务可以阻塞 200ms。

**0.2 为什么独立成章**

IO 是性能问题里最容易被忽视的根因——用 CPU profiler 看不到（fsync 期间 CPU 是空闲的）、看 CPU 占用很低（IO 等待）、看内存也正常（脏页都还没刷下去）。但用户的卡顿、卡死、OOM 都可能源于 IO。本章把 IO 单独拎出来，从存储介质本质讲到上层 API 选型。

**0.3 与其他章的关系**

- 上承卷零·01 [第一性原理](../00.公共方法论/01.性能工程总论原理.md)：IO 是"资源 × 时间"模型里的"存储资源"维度
- 横联卡顿/启动/OOM 篇：IO 是这些问题的高频根因
- 下承数据库、缓存、文件系统等专项

**0.4 8 个反直觉问题**

1. 为什么"日志写得多"会直接导致 ANR？
2. 同样写 1MB，写 1 个文件 vs 写 1000 个小文件，差几个数量级？
3. 为什么 SQLite 加了索引反而更慢？
4. 主线程读 SharedPreferences 真的安全吗？
5. 为什么 mmap 写入"没真正落盘"也能保证不丢？
6. SSD 的"随机 IO 不比顺序 IO 慢"是真的吗？
7. 为什么"批量写"比"逐条写"快 100 倍？
8. 异步写一定比同步写好吗？

### 00.5 贯穿案例：阅读 App"日志写崩主线程 + 启动 4 秒"事件

> 本案例贯穿全文：§02 看懂介质本质、§03/§04 用三方案+决策树定位、§05 用实验复盘、§06 给出分层策略闭环。

#### 案例背景

某头部阅读 App V7.3 上线"全量日志埋点"功能（产品同学希望"用户每个动作都有数据"），灰度后立刻爆雷：

- **ANR 率从 0.04% 飙升到 0.61%**，被 Google Play 打"应用未响应"标签。
- **冷启动 P95 从 1.4s 升到 4.1s**（产品要求"秒开"目标完全失败）。
- 低端机（Android 8，2GB RAM）SQLite 主线程写 P99 达 **820ms**，触发 ANR。
- 客服收到大量"读到一半页面卡 1 秒"投诉。
- 阅读时长（核心 KPI）下降 8%。

研发组初步反应："日志写一下能慢成这样？SharedPreferences/SQLite 都是异步的吧？"——这是典型的"API 表面认知"。

#### 经验派的 4 周折腾（典型反面教材）

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 把日志改成 `SharedPreferences.apply()`（认为是异步）| **ANR 率反而升到 0.78%**：apply 累积后 onPause/onStop 同步等所有未落盘 |
| 第 2 周 | 把 SQLite 加大量索引（怀疑查询慢）| 写入更慢（每写一行更新所有索引）；冷启动达 4.6s |
| 第 3 周 | 把日志写入加 try-catch（怀疑异常拖慢）| 无变化（IO 不是异常） |
| 第 4 周 | 把日志改成"批量每 50 条写一次"（方向对但实现错）| 仍未包事务，性能仅好 15% |

**复盘**：四周折腾错在"对 IO API 的表面认知"——以为 apply 真异步、以为加索引能加速所有操作、以为加 try-catch 能治 IO。**IO 性能的真相在介质和落盘机制层，不在 API 名字层**。

#### 方法派的 6 天闭环

新接手的同学按本文方法论重做：

**Day 1（§02 物理本质 + §03 三方案）**：

- 方案 A（系统级 iostat）：写 IOPS 在卡顿时段飙到 1200+（远超低端机能力）。
- 方案 B（/proc/[pid]/io）：阅读 App 进程 write_bytes 每分钟 47MB（异常高）。
- 方案 C（应用层埋点）：日志库每秒触发 80+ 次 SQLite INSERT + 每次单独 commit。

→ **每条日志 = 1 次 INSERT + 1 次 fsync + 1 次 SharedPreferences.apply**——三件事都在主线程触发。

**Day 2（§04 决策树）**：

- CPU 占用低（仅 8-15%）→ 大概率 IO 阻塞 ✓
- 主线程 ✓
- API：SharedPreferences 用 apply 但累积；SQLite 无事务、每条单独写

**Day 3（§05 实验思路验证）**：直接用 [§5.1](#51-实验一主线程-sp-的真实代价) 数据说服团队："apply 累积 100 次会让 onPause 卡 80-200ms"。

**Day 4-5（§06 分层策略）**：

- 第 1 层（少）：日志先在内存批量到 1000 条，再异步刷盘。
- 第 2 层（批）：日志库内部 SQLite 改 `BEGIN TRANSACTION ... COMMIT`，1000 条一次事务。
- 第 3 层（异）：日志写入完全异步线程；SharedPreferences 改用 MMKV（mmap）。
- 第 4 层（缩）：日志体积用 protobuf 替代 JSON，每条 -50%。

**Day 6（上线灰度对比）**：

#### 上线效果

| 指标 | 经验派 4 周后 | 方法派 6 天后 |
|---|---|---|
| ANR 率 | 0.78% | **0.05%** |
| 冷启动 P95 | 4.6s | **1.3s** |
| 低端机 SQLite 主线程写 P99 | 820 ms | **8 ms**（移离主线程）|
| 日志写入吞吐 | 80 条/s | **3500 条/s** |
| 阅读时长 | -8% | **+2%**（回升）|

**核心洞察**：日志库的"每条 INSERT + fsync"是典型 IO 反模式——单看每次操作很轻量（< 5ms），高频累积直接 ANR。**IO 性能问题的根因 90% 在"如何使用 API"，不在"用什么 API"**。 MMKV、WAL、事务批量这些"老技术"在每个项目都值得被重新检查。

#### 案例如何串起本文

- **§02 物理本质** ▶▶ 介质延迟差 7 个数量级 + fsync 是杀手——案例所有问题的根。
- **§03 三方案组合** ▶▶ 必须 A+B+C 才能定位"是日志库高频小写"。
- **§04 决策树** ▶▶ "CPU 低 + 主线程 + SQLite"路径精准命中。
- **§05 求证实验** ▶▶ §5.1 SP 假异步、§5.2 批量、§5.3 小文件、§5.4 WAL、§5.5 mmap 都在案例中变现。
- **§06 分层策略** ▶▶ "少→批→异→缩"五字诀正是案例落地路径。

### 02 问题与认知

**2.1 IO 慢的物理本质**

存储介质的延迟差距是 7 个数量级：

| 介质 | 延迟 | 类比 |
|---|---|---|
| L1 cache | 1ns | 1 秒 |
| 内存 | 100ns | 1.5 分钟 |
| SSD 随机读 | 100μs | 1 天 |
| SSD 随机写 | 1ms | 10 天 |
| HDD 寻道 | 10ms | 100 天 |
| 机械硬盘随机 | 100ms | 3 年 |

**移动设备**几乎都是 eMMC/UFS（类 SSD），但低端机的小颗粒寿命末期，写入延迟可达 50-200ms。

> ▶▶ **回扣 §00.5 案例**：低端机 SQLite 主线程写 P99 达 820ms 直接对应"低端机小颗粒寿命末期写入 50-200ms"——日志库每秒触发 80+ 次写直接打爆设备 IO 能力。**物理介质的延迟上限是优化的天花板，不能违反**。

**2.2 IO 慢的工程本质**

- **同步阻塞**：fsync/fdatasync 会等数据真正落盘，期间线程完全阻塞
- **小文件惩罚**：每个文件都要走 inode 查找、目录遍历，1000 个 1KB 远比 1 个 1MB 慢
- **写放大**：一次逻辑写可能触发多次物理写（日志、索引、元数据）
- **碎片惩罚**：长时间使用后文件碎片化，连续读变成随机读

**2.3 三个共识**

- **主线程不做任何 IO**：即使是"看起来轻量"的 SharedPreferences
- **批量优于逐条**：一次 fsync 比 100 次 fsync 快 50 倍
- **测量先于猜测**：90% 的"我猜是 IO 慢"实际是其他问题

### 03 度量与采集

**3.1 三类采集方案的本质**

**方案 A·系统级 IO 监控**

- **核心原理**：通过 /proc/diskstats、iostat、blktrace 等系统接口读取
- **工作机理**：内核记录每个 block device 的读写次数、字节数、等待时间
- **物理本质**：直接读取内核统计计数器
- **局限根源**：粒度到设备级，无法归因到具体进程/线程
- **适用场景**：服务端、性能基线评估

**方案 B·进程级 IO 追踪**

- **核心原理**：通过 /proc/[pid]/io 或 strace/ftrace 拦截系统调用
- **工作机理**：内核为每个进程维护 read_bytes/write_bytes 计数
- **物理本质**：以"性能损耗"换取"归因能力"
- **局限根源**：strace 拖慢被测进程数倍；线上不可用
- **适用场景**：本地排障、线下压测

**方案 C·应用层埋点**

- **核心原理**：在文件 IO API（FileInputStream、SQLiteDatabase）上 hook
- **工作机理**：拦截 open/read/write/close，记录时长、字节数、调用栈
- **物理本质**：以"代码侵入"换取"业务级归因"
- **局限根源**：无法覆盖 Native/系统库的 IO；性能开销 5-10%
- **适用场景**：线上常态化监控

**3.2 三方案差异矩阵**

| 维度 | 系统 A | 进程 B | 应用 C |
|---|---|---|---|
| 粒度 | 设备 | 进程 | 业务调用 |
| 归因能力 | 弱 | 中 | 强 |
| 性能开销 | 极低 | 高 | 中 |
| 上线可用 | 服务端可 | 不可 | 可 |
| 覆盖度 | 全 | 全 | 仅业务层 |

**实战策略**：服务端用 A；端上排障用 B；端上线上用 C + 抽样 A。

**3.3 跨平台差异**

| 平台 | 系统接口 | 应用层 hook 点 |
|---|---|---|
| Android | /proc/[pid]/io | FileInputStream、SQLiteDatabase、SharedPreferences |
| iOS | task_info | NSFileHandle、Core Data |
| 前端 | 无（沙盒限制） | IndexedDB、localStorage |
| 服务端 | iostat/blktrace | 各 ORM 框架 |

**同构本质**：所有平台都遵循"open → read/write → close"语义；优化方法（批量、缓冲、异步、mmap）跨平台通用。

### 04 归因与定位

**4.1 IO 问题二分决策树**

```
卡顿/慢
├─ CPU 高吗？
│  ├─ 高 → CPU 问题（不在本章）
│  └─ 低 → 大概率 IO 阻塞
│     ├─ 主线程吗？
│     │  ├─ 是 → 检查文件操作、数据库、SP/MMKV、日志
│     │  └─ 否 → 跨线程锁等待，或主线程在等异步 IO 结果
│     └─ 用什么 API？
│        ├─ SharedPreferences → apply 还是 commit？
│        ├─ SQLite → 事务/索引/WAL 检查
│        ├─ 文件 → fsync/小文件/序列化开销
│        └─ 网络缓存 → 磁盘缓存路径检查
└─ IO 量大吗？
   ├─ 量大 → 算法层优化（合并、分片、压缩）
   └─ 量小但慢 → 物理层问题（碎片、磁盘满、低端机颗粒劣化）
```

> ▶▶ **回扣 §00.5 案例**：阅读 App 的诊断路径精准命中——CPU 低（8-15%）→ IO 阻塞 → 主线程 → SQLite 无事务 + SharedPreferences 累积。**决策树的价值在于阻止"凭直觉乱猜"**。经验派 4 周加索引/try-catch 都在树外，方法派 1 天走树到底找到根因。

**4.2 主线程 IO 检测三板斥**

- **StrictMode（Android）**：开发期开启 detectDiskReads/detectDiskWrites，主线程 IO 直接红屏
- **采样栈追踪**：定时采样主线程栈，统计落在 IO 系统调用上的比例
- **AOP 拦截**：编译期插桩 FileInputStream/SQLiteDatabase 的 open，主线程触发记录

**4.3 数据库慢查询定位**

SQLite 慢查询定位 4 步：
1. 开启 EXPLAIN QUERY PLAN，看是否走索引
2. 检查 PRAGMA journal_mode（WAL 比 DELETE 快 3-5 倍）
3. 看是否在事务里（无事务的逐条写每条都 fsync）
4. 检查 page_size 与 cache_size（默认值往往不合理）

### 05 求证实验

**5.1 实验一：主线程 SP 的真实代价**

**问题**：SharedPreferences.apply() 真的"异步"吗？主线程会卡多久？

- **第 1 步·假设**：apply() 主线程不阻塞，commit() 阻塞
- **第 2 步·设计**：写入 100 个 KV，对比 apply()/commit() 在主线程上的耗时；同时观察后续 Activity onResume 是否被阻塞
- **第 3 步·控制变量**：低端机（Android 8）vs 高端机（Android 12）
- **第 4 步·指标**：调用耗时、Activity 切换帧时长、ANR 触发率
- **第 5 步·执行**：埋点 + Systrace
- **第 6 步·收集**：apply() 调用本身 < 1ms；但 onResume/onPause 会等所有未落盘的 apply 完成（QueuedWork.waitToFinish）；累积 100 次 apply 后 onPause 被阻塞 80-200ms
- **第 7 步·分析**：apply 异步只是"返回快"，但生命周期切换时仍会同步等
- **第 8 步·结论**：用 MMKV 替代 SP；高频写场景永远不要用 SP
- **第 9 步·扩展**：MMKV 用 mmap + 自定义 protobuf，写入性能提升 100x

> ▶▶ **回扣 §00.5 案例**：经验派第 1 周"改 apply 以为异步"完全踩中本实验"apply 累积后 onPause 卡 80-200ms"的陷阱。**apply ≠ 异步，只是"返回快"**——这是 API 表面认知 vs 物理本质认知的最经典反例。

**5.2 实验二：批量 vs 逐条写入**

**问题**：写 1 万条 SQLite 记录，事务批量 vs 逐条，差多少？

- **第 1 步·假设**：批量比逐条快 50 倍
- **第 2 步·设计**：同一批 1 万条数据，分别用"逐条 INSERT"、"事务包裹批量 INSERT"、"INSERT...VALUES 多行"三种写法
- **第 3 步·控制变量**：同设备、同表结构、清空后实测
- **第 4 步·指标**：总耗时、fsync 次数、CPU 占用
- **第 5 步·执行**：Android 真机
- **第 6 步·收集**：逐条 28 秒（每条都 fsync）；事务 0.4 秒（70x）；多行 INSERT 0.3 秒（93x）
- **第 7 步·分析**：fsync 是瓶颈，事务把 1 万次 fsync 合并成 1 次
- **第 8 步·结论**：任何 SQLite 批量写必须包事务；进一步合并成多行 INSERT 还能再省 25%
- **第 9 步·扩展**：WAL 模式下事务的可见性边界变化，需评估业务一致性需求

**5.3 实验三：小文件惩罚**

**问题**：写 100MB 数据，分成 1 个大文件 vs 1 万个小文件，差多少？

- **第 1 步·假设**：小文件慢 10 倍以上
- **第 2 步·设计**：同样 100MB 数据，分别写 1 个 100MB / 100 个 1MB / 1 万个 10KB 文件
- **第 3 步·控制变量**：同一设备、同一目录、清空缓存
- **第 4 步·指标**：总耗时、inode 操作次数、磁盘空间占用（块对齐损耗）
- **第 5 步·执行**：Android + iOS 双平台
- **第 6 步·收集**：1 个文件 0.8s；100 个文件 1.5s；1 万个文件 22s（27x）
- **第 7 步·分析**：每个文件都要 open/close/fsync 元数据，inode 锁竞争严重
- **第 8 步·结论**：缓存设计避免"一 key 一文件"，用单文件分段或 LevelDB/SQLite 聚合存
- **第 9 步·扩展**：iOS 上小文件惩罚比 Android 更严重（APFS 的写时复制机制开销大）

**5.4 实验四：SQLite WAL vs DELETE 模式的真实差异**

**问题**：SQLite 的 journal_mode 默认是 DELETE，改成 WAL 收益有多大？真有副作用吗？

- **第 1 步·假设**：WAL 模式读写并发，并发场景吞吐 3-5×；副作用是读到的可能不是最新（隔离级别变化）。
- **第 2 步·设计**：100 个读线程 + 10 个写线程并发操作同一表，分别 DELETE / WAL 模式测试。
- **第 3 步·控制变量**：同设备、同 schema、清空后实测；启用 `PRAGMA synchronous=NORMAL`。
- **第 4 步·指标**：读吞吐量、写吞吐量、单次读/写 P99、磁盘空间增长（WAL 文件）。
- **第 5 步·执行**：Android Pixel 6 + 红米 Note 11。

| 模式 | 读吞吐 | 写吞吐 | 读 P99 | 写 P99 | 磁盘开销 |
|---|---|---|---|---|---|
| DELETE | 1,200 op/s | 350 op/s | 28 ms | 180 ms | 0 额外 |
| WAL | **8,500 op/s** | **1,800 op/s** | **5 ms** | **15 ms** | +5-50MB（WAL 文件）|

- **第 6 步·分析**：
  - WAL 写不阻塞读：吞吐 3-7× 提升。
  - 写也大幅加速：因为不需要回写 rollback journal。
  - 副作用：WAL 文件可能膨胀（需定期 `PRAGMA wal_checkpoint(TRUNCATE)`）；读隔离从 SERIALIZABLE 变 SNAPSHOT。
- **第 7 步·结论**：**90% 的 SQLite 场景都应启用 WAL**。除非业务严格需要 SERIALIZABLE 隔离（如金融转账）。
- **第 8 步·扩展**：[§00.5 案例](#005-贯穿案例阅读-app日志写崩主线程--启动-4-秒事件) 中如果日志库一开始就启用 WAL，单这一项就能让写入吞吐从 350 升到 1800（5×）；配合事务批量后实测达 3500+。

**5.5 实验五：mmap 替代普通 IO 的真实收益**

**问题**：MMKV 等用 mmap 的方案号称"100× 性能"，真实场景增益多少？

- **第 1 步·假设**：高频小写场景 mmap 比 fsync IO 快 50-100×；大数据场景增益缩小到 2-5×；首次访问 mmap 有缺页中断开销。
- **第 2 步·设计**：3 种场景对比：(a) 每秒 100 次 100B 写 (b) 每秒 10 次 10KB 写 (c) 单次 1MB 顺序写。
- **第 3 步·控制变量**：同设备、同存储介质、清空缓存。
- **第 4 步·指标**：操作总耗时、CPU 占用、是否丢数据（断电模拟）。
- **第 5 步·执行**：Android Pixel 6。

| 场景 | 普通 IO + fsync | mmap (MMKV) | 增益 |
|---|---|---|---|
| (a) 100×100B/s 持续 60s | 12,500 ms | **125 ms** | **100×** |
| (b) 10×10KB/s 持续 60s | 850 ms | **45 ms** | 19× |
| (c) 单次 1MB 顺序写 | 8 ms | 4 ms | 2× |
| 断电模拟（拔电源） | 0 丢数据 | 最近 30s 可能丢 | - |

- **第 6 步·分析**：
  - 高频小写是 mmap 的杀手锏（避免每次 syscall + fsync）。
  - 大数据场景增益小（IO 主导，不是 syscall 主导）。
  - 副作用：mmap 数据需 msync 才保证落盘；进程崩溃时未刷数据可能丢。
- **第 7 步·结论**：**高频小数据（KV、日志、缓存）用 mmap；大数据不必**。需要严格落盘的场景调用 msync。
- **第 8 步·扩展**：[§00.5 案例](#005-贯穿案例阅读-app日志写崩主线程--启动-4-秒事件) 用 MMKV 替代 SP 是关键动作；日志库的"每秒 80 条小写"正是 mmap 最适合的场景。

**5.6 五大实验启示**

```
   SP apply 假异步     → onPause 累积阻塞，必须用 MMKV       ─┐
                                                              │
   批量 vs 逐条        → 事务让 fsync 合并，70×                │
                                                              │
   小文件惩罚          → 1 万个 10KB 比 1 个 100MB 慢 27×     ├─▶ IO 优化 = 物理介质 + API 选型 + 使用方式
                                                              │
   WAL vs DELETE       → 读写并发，吞吐 3-7×                  │
                                                              │
   mmap vs fsync       → 高频小写 100×，大数据 2×              ─┘
```

**统一启示**：

- **物理介质决定上限**：低端机颗粒劣化时单次写可达 200ms，必须从源头减少 IO。
- **API 选型决定基线**：MMKV/WAL/mmap 是 IO 优化的"基础设施"，能用必须用。
- **使用方式决定 90% 性能**：批量 + 事务 + 异步 = 三大铁律。
- **fsync 是隐形杀手**：所有"慢" 90% 是它造成的。
- **小文件比大文件慢得多**：缓存设计要聚合存。

### 06 优化策略深化

> 本节回答四个递进问题：**①如何让 IO 永远不上主线程？②如何让 IO 量级最小化？③如何让单次 IO 最快？④如何持续防退化？**  
> 与"IO 优化清单"不同，本文按"主线程→量级→单次→长效"分层施治。

#### 6.1 第一层：主线程零 IO（消灭最大单点）

**核心命题**：主线程 IO 是性能问题的最大单点。这一层"0 容忍"是基础。

**策略 1.1：StrictMode 全量拦截 + penaltyDeath**

- **机理**：把"约定"变成"强制约束"。
- **代码**：

```java
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(new StrictMode.ThreadPolicy.Builder()
        .detectDiskReads()
        .detectDiskWrites()
        .penaltyDeath()  // Debug 直接 crash 暴露
        .build());
}
```

- **收益**：开发期 100% 拦截；线上版用 penaltyLog 收集。
- **边界**：Release 不能 penaltyDeath（用户场景）；某些库（Glide 等）可能误报需白名单。

**策略 1.2：SharedPreferences 全面迁移到 MMKV**

- **机理**：[§5.5 实验](#55-实验五mmap-替代普通-io-的真实收益) 高频小写 100×；[§5.1 实验](#51-实验一主线程-sp-的真实代价) SP apply 仍会在生命周期切换时同步等。
- **代码**：

```kotlin
// 反例
val sp = context.getSharedPreferences("config", MODE_PRIVATE)
sp.edit().putString("key", value).apply()

// 正例
MMKV.initialize(context)
val mmkv = MMKV.defaultMMKV()
mmkv.encode("key", value)  // 真异步，无生命周期等待
```

- **收益**：[§00.5 案例](#005-贯穿案例阅读-app日志写崩主线程--启动-4-秒事件) 日志库切 MMKV 后吞吐从 80→3500 条/s。
- **边界**：MMKV 数据兼容性需测试；多进程场景用 `MMKV.mmkvWithID(..., MMKV.MULTI_PROCESS_MODE)`。

**策略 1.3：所有 SQLite 操作走子线程**

- **机理**：即使是 `SELECT id FROM users LIMIT 1` 在 SD 卡有压力时也可能 100ms+。
- **代码**：

```kotlin
viewModelScope.launch(Dispatchers.IO) {
    val users = db.userDao().getAll()
    withContext(Dispatchers.Main) { adapter.submitList(users) }
}
```

- **收益**：主线程永不被 SQLite 阻塞。
- **边界**：Room 默认在主线程会 throw（除非 `allowMainThreadQueries()` 显式开启）；可用此特性强制约束。

**策略 1.4：日志/统计走异步缓冲**

- **机理**：[§00.5 案例](#005-贯穿案例阅读-app日志写崩主线程--启动-4-秒事件) 日志库就是反面教材；正例是 Logan/Xlog 设计。
- **代码**：

```kotlin
class AsyncLogger {
    private val buffer = ConcurrentLinkedQueue<LogEntry>()
    private val executor = Executors.newSingleThreadExecutor()
    
    fun log(entry: LogEntry) {
        buffer.offer(entry)  // 主线程仅入队（μs 级）
        if (buffer.size >= 1000) flushAsync()
    }
    
    private fun flushAsync() {
        executor.submit {
            val batch = mutableListOf<LogEntry>()
            while (batch.size < 1000 && buffer.isNotEmpty()) batch += buffer.poll()
            writeBatchToFile(batch)  // 子线程批量写
        }
    }
}
```

- **收益**：[§00.5 案例](#005-贯穿案例阅读-app日志写崩主线程--启动-4-秒事件) 日志主线程耗时从 ms 级降到 μs 级。
- **边界**：进程崩溃时缓冲区数据丢；关键日志用 mmap 兜底。

---

#### 6.2 第二层：IO 量级最小化（少 + 缩）

**核心命题**：能不写就不写；必须写就压缩。

**策略 2.1：缓存命中即返回（避免重复 IO）**

- **机理**：内存缓存命中 = 0 IO；磁盘缓存命中 = 1 次读；网络 = 重新拉。
- **代码**：

```kotlin
class TieredCache<K, V> {
    private val memCache = LruCache<K, V>(100)
    
    fun get(key: K, loader: () -> V): V {
        memCache.get(key)?.let { return it }  // 0 IO
        val v = loadFromDisk(key) ?: loader().also { saveToDisk(key, it) }
        memCache.put(key, v)
        return v
    }
}
```

- **收益**：热点数据 IO 频次 -90%。
- **边界**：缓存一致性需通过版本号 / push 失效。

**策略 2.2：数据压缩（CPU 换 IO 永远划算）**

- **机理**：CPU 解压 10MB 数据 ~10ms；IO 读 10MB ~100ms。压缩到 3MB 只需 ~30ms IO + ~10ms 解压 = -60%。
- **代码**：

```kotlin
// 写入压缩
val compressed = gzip(jsonBytes)
file.writeBytes(compressed)

// 读取解压
val bytes = gunzip(file.readBytes())
```

- **收益**：磁盘空间 -60%，IO 时间 -50%。
- **边界**：小文件（< 4KB）压缩收益小；CPU 紧张设备需评估。

**策略 2.3：协议升级（PB / FlatBuffer 替代 JSON）**

- **机理**：PB 比 JSON 体积 -50%、解析 -70%；FlatBuffer 零拷贝直接访问。
- **收益**：见 [`卷四·02 §6.1 策略 1.4`](../04.业务专项篇/02.网络性能分析优化.md)。
- **边界**：PB 需双端协议同步；schema 变更需兼容设计。

**策略 2.4：小文件聚合存储**

- **机理**：[§5.3 实验](#53-实验三小文件惩罚) 1 万个 10KB 比 1 个 100MB 慢 27×。
- **代码**：用 LevelDB / SQLite 聚合存 KV，避免一 key 一文件：

```kotlin
// 反例：每个图片缩略图一个文件
File("$cacheDir/thumb_$id.png").writeBytes(bytes)

// 正例：聚合到 SQLite 或 LevelDB
db.execSQL("INSERT INTO thumbs (id, data) VALUES (?, ?)", arrayOf(id, bytes))
```

- **收益**：千级以上小文件场景 IO 时间 -90%。
- **边界**：聚合后单文件损坏影响范围大，需备份策略。

---

#### 6.3 第三层：单次 IO 最快（批 + 异 + 介质优化）

**核心命题**：[§5.2](#52-实验二批量-vs-逐条写入) + [§5.4](#54-实验四sqlite-wal-vs-delete-模式的真实差异) 证明这一层是 IO 优化的"基础设施"。

**策略 3.1：SQLite 事务批量化**

- **机理**：[§5.2 实验](#52-实验二批量-vs-逐条写入) 事务比逐条快 70×。
- **代码**：

```kotlin
db.beginTransaction()
try {
    items.forEach { db.execSQL("INSERT INTO t VALUES (?, ?)", arrayOf(it.id, it.data)) }
    db.setTransactionSuccessful()
} finally {
    db.endTransaction()
}
```

- **收益**：[§00.5 案例](#005-贯穿案例阅读-app日志写崩主线程--启动-4-秒事件) 日志批量化是关键动作。
- **边界**：事务内不能做长任务；事务大小过大（> 10MB）会触发 WAL 文件膨胀。

**策略 3.2：SQLite 启用 WAL 模式**

- **机理**：[§5.4 实验](#54-实验四sqlite-wal-vs-delete-模式的真实差异) 吞吐 3-7×。
- **代码**：

```kotlin
db.execSQL("PRAGMA journal_mode=WAL")
db.execSQL("PRAGMA synchronous=NORMAL")  // 配合 WAL 用 NORMAL 而非 FULL
```

- **收益**：读写并发；写吞吐 +400%。
- **边界**：WAL 文件需定期 checkpoint（`PRAGMA wal_checkpoint(TRUNCATE)`）；隔离级别变 SNAPSHOT。

**策略 3.3：合理设置 SQLite 索引（不是越多越好）**

- **机理**：索引加速查询但拖慢写入（每写要更新所有索引）。
- **代码**：

```sql
-- 仅为高频查询字段加索引
CREATE INDEX idx_user_email ON users(email);
-- 不要给低基数字段加索引（如 gender 仅 M/F）
-- 复合索引按"高频先后"排列
CREATE INDEX idx_log_time_level ON logs(create_time, level);
```

- **收益**：查询 100× 加速；过度加索引则写入慢 3-5×。
- **边界**：EXPLAIN QUERY PLAN 验证；线上监控写延迟。

**策略 3.4：异步刷盘（mmap 自动 / msync 手动）**

- **机理**：mmap 让内核自动刷脏页；关键节点 msync 兜底。
- **代码**：

```cpp
// mmap 写入后异步刷盘（内核自动）
char* addr = mmap(nullptr, len, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
memcpy(addr, data, len);
// 关键节点（如交易完成）显式 msync
msync(addr, len, MS_SYNC);
```

- **收益**：吞吐 100×，关键节点保证一致性。
- **边界**：mmap 数据可能丢（最近未 msync 的）；金融类必须 msync。

#### 6.4 第四层：持续防退化（监控 + 治理）

**核心命题**：IO 性能容易在迭代中退化（新功能加日志/缓存/查询），必须建立长效机制。

**策略 4.1：主线程 IO 时长 SLO 监控**

- **机理**：上报每次主线程 IO 调用时长，P95 超阈值告警。
- **代码**：

```kotlin
class IOTimingAspect {
    fun aroundIO(call: () -> Unit) {
        val start = SystemClock.elapsedRealtimeNanos()
        try { call() }
        finally {
            val durMs = (SystemClock.elapsedRealtimeNanos() - start) / 1_000_000
            if (Looper.myLooper() == Looper.getMainLooper() && durMs > 16) {
                report("main_io", durMs, Throwable().stackTraceToString())
            }
        }
    }
}
```

- **收益**：退化在 24h 内被发现。
- **边界**：上报采样防数据爆炸。

**策略 4.2：CI 基线测试**

- **机理**：每次 PR 跑标准 IO 场景，超基线 20% 阻断合入。
- **代码**：Macrobenchmark / XCTest 自动化用例。
- **收益**：退化在合入前被拦截。
- **边界**：基线需周期性更新（设备/数据规模变化）。

**策略 4.3：定期 `wal_checkpoint` 和 `VACUUM`**

- **机理**：长期运行 SQLite 会产生空闲页 + WAL 膨胀。
- **代码**：

```kotlin
// 定期（如启动空闲期）
db.execSQL("PRAGMA wal_checkpoint(TRUNCATE)")
// 每月或必要时
db.execSQL("VACUUM")
```

- **收益**：磁盘空间稳定；查询性能不退化。
- **边界**：VACUUM 全表重建，耗时较长，应在后台/空闲时段。

### 08 案例与教训

**8.1 跨端同构案例·日志写崩主线程**

某 App 接入新日志库，所有日志同步写文件 + fsync。线下没事，线上爆出大量 ANR。**原因**：低端机 fsync 单次 200ms，日志一多累积阻塞。**修法**：日志走 mmap + 异步刷盘，单次写 < 1μs。**教训**：任何"看起来很轻量"的写操作，到了低端机都可能爆炸。

**8.2 平台特异案例·iOS Core Data 主线程查询**

某 iOS App 启动慢，profile 看不到明显热点，但启动时间 P50 1.8s。深入排查发现 AppDelegate 里有一个 Core Data 查询，主线程同步执行。低存储设备上 Core Data 文件碎片化导致查询 1.2s。**修法**：Core Data 操作必须用 performBackgroundContext，主线程只用结果。**教训**：iOS 的 Core Data 比直接 SQLite 多一层 ORM，性能问题更隐蔽。

### 09 原理深挖

**9.1 mmap 为什么快**

mmap 把文件映射进进程地址空间，读写文件等同于读写内存——没有 read/write 系统调用、没有用户态/内核态拷贝。脏页由内核异步刷盘，进程只感知内存操作。**代价**：进程崩溃时未刷盘数据可能丢失，需要 msync 控制一致性。

**9.2 WAL 为什么快**

WAL（Write-Ahead Logging）模式下，写操作只追加到 WAL 文件，不修改主库；读操作从主库读，不被写阻塞。一次性把 WAL 合并到主库（checkpoint）。**结果**：读写并发，写性能提升 3-5 倍。

**9.3 SSD 的"随机不比顺序慢"真相**

SSD 内部是 NAND 闪存阵列，理论上随机/顺序差异很小。但写操作受"擦写块（256KB-4MB）"约束，随机小写会触发"读-擦-写"放大。**结论**：读基本无差，写仍有 2-5 倍差异；批量化依然有效。

### 10 总结与扩展

**10.1 一图概括**

```
IO 性能问题
    ├─ 主线程？  → 0 容忍（MMKV + 异步）
    ├─ 量大？    → 缓存 + 压缩 + 协议升级
    ├─ 频繁？    → 批量 + 事务 + 异步
    ├─ 小文件？  → 聚合存储（LevelDB/SQLite）
    └─ 数据库？  → 事务 + WAL + 合理索引
```

**10.2 五条核心原则**

1. **主线程 0 IO**：StrictMode 强制约束，[§00.5 案例](#005-贯穿案例阅读-app日志写崩主线程--启动-4-秒事件) ANR 0.78%→0.05% 的根。
2. **MMKV 替代 SP**：[§5.5](#55-实验五mmap-替代普通-io-的真实收益) 100× 性能，无需再讨论。
3. **SQLite 必启用 WAL + 事务**：[§5.2](#52-实验二批量-vs-逐条写入) + [§5.4](#54-实验四sqlite-wal-vs-delete-模式的真实差异) 双重证据，3-70× 收益。
4. **小文件必须聚合**：[§5.3](#53-实验三小文件惩罚) 27× 差距是物理事实。
5. **fsync 是隐形杀手**：90% 的"IO 慢" 都是它造成的。

**10.3 五个常见误区**

1. **"apply 是异步的所以安全"**：错（[§5.1](#51-实验一主线程-sp-的真实代价) onPause 累积阻塞）。
2. **"加索引必加速"**：错（写入会慢 3-5×）。
3. **"批量就是好"**：错（不包事务等于没批量，[§00.5 案例](#005-贯穿案例阅读-app日志写崩主线程--启动-4-秒事件) 第 4 周翻车）。
4. **"mmap 数据安全"**：错（崩溃丢未 msync 数据）。
5. **"SSD 随机写不慢"**：错（仍有 2-5× 写放大）。

**10.4 三个外延**

- **存储引擎演进**：LevelDB/RocksDB 的 LSM 树思想是处理"高频小写"的范式
- **跨平台抽象**：MMKV、Realm 等跨端方案的统一接口降低重复造轮子
- **离线优先**：移动场景的"先写本地再同步"模式，IO 设计直接决定用户体验

**10.5 给团队的建议**

- 第 1 周：StrictMode 全量打开，治理所有主线程 IO 红屏
- 第 2 周：用 MMKV 替换 SharedPreferences
- 第 3 周：SQLite 全部启用 WAL + 检查索引覆盖率
- 第 4 周：日志、缓存的写入路径统一异步化

## 一句话总结

> **IO 是"看不见的杀手"——90% 的卡顿、ANR、启动慢都源于它，但 CPU profiler 看不到。  
> 主线程 0 IO、MMKV 替代 SP、SQLite 必 WAL+事务、小文件必聚合、fsync 必批量。  
> 这五条铁律落地，应用 IO 性能就达到行业前 10%。  
> §00.5 那个"4 周经验派 vs 6 天方法派"的反差，正是这条路径的最锋利证据。**
