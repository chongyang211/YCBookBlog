## 00.5 贯穿案例：音视频应用"开播 3 秒卡死"事件

> 本案例贯穿全文：§01 看懂代价、§02 拿到并发模型武器、§03/§04 用三方案+决策树定位、§05 用实验复盘、§06 给出分层策略闭环。

### 案例背景

某直播 App V9.2 上线"开播秒开"功能，把推流准备从异步改成全异步并行。结果出乎意料：

- **开播 3 秒内卡死率从 0.5% 飙到 7.3%**，被打"应用未响应"标签。
- 主播侧首屏 P95 从 1.2s 升到 **4.8s**（与"秒开"目标相反）。
- 中端机线程数稳态达 **187 个**（之前 65 个），内存涨 80MB。
- 日活主播流失 12%，直播业务损失约**单日 600 万**。

研发组初步排查："并行应该更快才对啊。"——这是典型的"并发崇拜"。

### 经验派的 3 周折腾（典型反面教材）

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 把线程池从 8 调到 32（怀疑并发不够）| **卡死率升到 9.1%**：线程数破 230，上下文切换暴涨 |
| 第 2 周 | 加 try-catch + 死循环检测（怀疑死锁）| 没死锁，但卡死依旧 |
| 第 3 周 | 用 spinlock 替代 mutex（怀疑锁开销）| CPU 占用炸到 100%，发热严重，掉电飞快 |

**复盘**：三周里所有动作都基于"并发越多越快、锁越快越好"的错误直觉。**线程不是免费的（§2.1 约束三），并发是非线性收益（§5.2 拐点）**——这正是 §00.5 案例的根本反面教材。

### 方法派的 7 天闭环

新接手的同学按本文方法论重做：

**Day 1（§02 第一性原理 + §03 三方案组合）**：用 Perfetto 抓系统 trace（方案②）+ Lock contention（方案③）+ 线程清单（方案①），看到三个关键数据：

| 指标 | 测量值 | 期望 |
|---|---|---|
| 线程数 | 187 | < 60 |
| 上下文切换/s | 22,000 | < 5,000 |
| 推流锁等待 P99 | 850 ms | < 5 ms |

→ 三类问题（§2.2 模型）全部命中：调度不当 + 同步开销 + 资源浪费。

**Day 2（§04 归因决策树）**：跟着决策树跑：

- 线程数 187 → 线程数膨胀分支 → 12 个 SDK 各自创建线程池（音频/视频/美颜/特效/网络/统计/推送/...）。
- 切换 22K/s → 上下文切换过频分支 → 每帧 30+ 任务被切散到不同线程。
- 锁等待 850ms → 锁竞争高分支 → "推流准备锁"被音频/视频/字幕/特效 4 路同时争用。

**Day 3-4（§05 实验思路验证 + §06 分层策略）**：

- 第 1 层（主线程减负）：主线程的开播状态机改用 IdleHandler 切片。
- 第 2 层（同步治理）：推流准备锁拆分为音频/视频/字幕/特效 4 把独立锁；锁内严禁 IO。
- 第 3 层（线程池治理）：建统一线程池服务（CPU 池=核数+1 / IO 池=20 / 高优先级池=4），强制 SDK 接入；HandlerThread 显式 quit。
- 第 4 层（优先级调度）：推流相关线程升 QoS 到 userInteractive；推流准备锁启用优先级继承。

**Day 5（[§5.4 实验](#54-实验四优先级反转与继承的真实代价) 思路验证）**：用 Macrobenchmark 跑优先级继承 vs 不继承的对比，确认主线程等待 P99 从 850ms→18ms。

**Day 6-7（上线灰度）**：

### 上线效果

| 指标 | 经验派 3 周后 | 方法派 7 天后 |
|---|---|---|
| 开播 3 秒卡死率 | 9.1% | **0.3%** |
| 主播首屏 P95 | 4.8s | **1.0s** |
| 线程数稳态 | 230 | **52** |
| 上下文切换/s | 35,000 | **4,200** |
| 推流锁等待 P99 | 850 ms | **18 ms** |
| 日活主播流失 | -12% | **+3%**（恢复）|

**核心洞察**：经验派 3 周折腾错在"用更多线程治线程问题"——加线程让切换雪上加霜（22K/s→35K/s），spinlock 把锁等待换成 CPU 烧死。**线程优化的本质是找拐点（§5.2），不是堆资源。** 方法派 Day 1 用 ②③ 方案立刻看到 187 个线程 + 22K 切换的真相，这是经验派 3 周从没看到的数据。

### 案例如何串起本文

- **§01 现象与代价** ▶▶ 业务损失映射：日活主播 -12%、单日 600 万收入。
- **§02 并发模型** ▶▶ 案例同时命中"调度不当 + 同步开销 + 资源浪费"三类。
- **§03 三方案组合** ▶▶ 只用方案①（线程清单）看不到切换次数和锁等待，必须 ①②③ 同时上。
- **§04 归因决策树** ▶▶ 案例的 3 个症状走 3 条不同分支。
- **§05 求证实验** ▶▶ §5.2 拐点、§5.3 锁竞争、§5.4 优先级反转都在案例中变现。
- **§06 分层策略** ▶▶ "主线程→同步→线程池→优先级"四层正是案例落地路径。

## 01.问题域定义

### 1.1 现象与代价

线程问题往往表现间接，但代价巨大：

- **主线程卡顿**：耗时任务没异步化 → 帧时长超 16.67ms → 用户感知卡。
- **线程膨胀 / OOM**：大量临时线程 → Thread 资源耗尽（Linux 默认 ~32K 进程级线程）。
- **死锁 / 活锁**：多个线程互相等待，进程"卡死"，最终 ANR / 看门狗复位。
- **数据竞争 / 状态不一致**：多线程读写共享变量，UI 显示错乱、崩溃。
- **后台耗电 / 温升**：过多后台线程消耗 CPU 时间片，电量加速下降。

**业务代价（行业实测数据）**：

- 头部 App：主线程优化（移走 IO/JSON 等任务）后启动 -300ms，留存 +0.5%。
- iOS 死锁直接被系统 watchdog 杀死，体验类崩溃。
- 大量后台线程会让设备温度上升 2–5°C，触发降频，性能"看似正常但帧率下降"。
- Web Worker 滥用会让浏览器进程内存涨 2-3 倍。

> ▶▶ **回扣 §00.5 案例**：直播 App 在"开播秒开"功能后，线程数 65→187、卡死率 0.5%→7.3%，直接对应"线程膨胀→OOM/卡死"现象——**线程优化的反面教材就是加更多线程**。日活主播流失 12% + 单日 600 万收入损失说明线程治理直接关乎钱袋。

### 1.2 度量准则

按 [`卷零·02 §3`](../00.公共方法论/02.跨平台指标体系.md) 的统一指标体系：

**资源视角（USE）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 线程数 | 进程内活跃线程数 | < 50（轻量）/ < 100（重量）|
| CPU 利用率（U）| 各核心利用率 | 详见卷二·01 |
| 上下文切换率（S）| 每秒切换次数 | < 5000/s |
| 死锁错误（E）| 是否检测到 | = 0 |

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 任务执行延迟 | 提交到完成时间 | < 100ms（UI 类）|
| 锁等待时长 | 线程等锁时长 | < 5ms |
| 主线程消息处理 | 单条消息耗时 | < 16ms |

**用户感知（APDEX）**：

- *Satisfied*：无 ANR、无主线程卡顿
- *Tolerating*：偶发卡顿 < 100ms
- *Frustrated*：ANR / 死锁 / 帧时长 > 700ms

### 1.3 行业基准与目标

| 平台 | 进程内线程数 | 线程池大小 | 上下文切换 |
|---|---|---|---|
| Android（中端机）| < 60 | CPU 核数 + 1（计算） | < 5000/s |
| iOS | < 50 | 同上（GCD 自动管理）| < 5000/s |
| Web | < 10 Worker | 视场景 | N/A |

## 02.第一性原理

> 本节回答三个根本问题：**①线程的物理本质是什么？②为什么所有平台的线程问题都同构？③同构之下平台差异在哪？**

### 2.1 线程本质定义

**一句话定义**：

> **线程 = 操作系统调度的最小执行单元，是"在共享地址空间内独立执行指令流"的抽象**。

这句话隐含三个不可商量的物理约束：

**约束一：线程是 CPU 时间片的接收者**

CPU 资源有限（N 个核心），线程数往往远多于核数。OS 通过"时间片轮转"让多个线程"看似并行"运行。**单个核同时只能跑一个线程**。

```
   单核 CPU 视角：
   时间 ──▶ |T1|T2|T1|T3|T2|T1|T2|T3|...
              ↑切换 ↑切换 ↑切换
              每次切换有成本（详见 §5.1）
```

**约束二：线程共享地址空间**

同进程内所有线程共享内存，意味着**任意线程可以访问 / 修改其他线程的数据**。这是线程的"双刃剑"：

- 优势：通信成本低（直接共享变量）。
- 代价：必须用同步原语（锁、原子操作）保证数据一致性。

**约束三：线程不是免费的**

每个线程都有固定的资源占用：

- **栈内存**：默认 1MB（Linux）/ 8MB（macOS），即使啥都不干。
- **TCB**：内核数据结构 ~10KB。
- **调度开销**：每次切换 ~1–10μs。
- **缓存污染**：切换后 L1/L2 缓存重新加载。

这就是为什么"开 1000 个线程"会带来巨大开销，即使它们大部分时间在 sleep。

### 2.2 并发模型分类

**为什么"并发模型"是线程治理的核心抽象**

按"任务粒度 + 调度策略 + 同步方式"可以分为四种典型模型，**所有平台的并发设计都映射到这四种**：

```
   ┌─────────────────────────────────────────────────────┐
   │ A. 共享内存 + 同步原语（经典多线程）                  │
   │    pthread / Java Thread / iOS NSThread             │
   │    优点：粒度灵活                                    │
   │    缺点：锁难写，死锁易发                             │
   ├─────────────────────────────────────────────────────┤
   │ B. 任务队列 + 线程池（GCD / ExecutorService）         │
   │    把"线程数"和"任务数"解耦                          │
   │    优点：开发者只关心任务，OS 管线程                  │
   │    缺点：长任务阻塞池，需要分类（IO/CPU）              │
   ├─────────────────────────────────────────────────────┤
   │ C. 事件循环 + 单线程（Web Main Thread / Node.js）    │
   │    一个线程上跑事件队列，任务非阻塞                   │
   │    优点：无锁                                       │
   │    缺点：任何长任务卡死全部                          │
   ├─────────────────────────────────────────────────────┤
   │ D. Actor / CSP（Erlang / Go goroutine / Akka）       │
   │    任务通过消息通信，无共享内存                       │
   │    优点：避免数据竞争                                │
   │    缺点：消息复制有成本                              │
   └─────────────────────────────────────────────────────┘
```

**线程问题的三类典型形态**：

```
   线程问题类型：

   ┌──────────────────────────────────────────────┐
   │ ① 调度不当：任务在错的线程上执行              │
   │    主线程做 IO；子线程更新 UI                 │
   ├──────────────────────────────────────────────┤
   │ ② 同步开销：锁 / 竞争 / 死锁                  │
   │    粒度过大；锁顺序不一致；忘 unlock          │
   ├──────────────────────────────────────────────┤
   │ ③ 资源浪费：线程过多 / 切换过频               │
   │    每个任务起新线程；线程池配置不当           │
   └──────────────────────────────────────────────┘
```

> ▶▶ **回扣 §00.5 案例**：直播 App 的"开播秒开"翻车恰好**同时命中三类**——
> - **① 调度不当**：开播状态机仍在主线程做同步任务；
> - **② 同步开销**：4 路争抢同一把推流准备锁，P99=850ms；
> - **③ 资源浪费**：12 个 SDK 各自池化导致 187 个线程、22K/s 切换。
>
> 经验派 3 周折腾的失败原因正是**把三类混为一谈，只看症状不分类型**。第 1 周加线程治标③，反而恶化③；第 3 周换 spinlock 治标②，反而引爆①。**先分类，再施治**才是正道。

### 2.3 跨平台同构原理

**为什么所有平台的线程原理都同构**

底层都是 POSIX thread（pthread）或其衍生（Windows Fiber 也类似）。区别只是上层封装：

```
   通用线程模型：

      [应用层 API]
      Thread / GCD / Worker / goroutine
              │
              ▼
      [运行时层]
      JVM ThreadPool / NSOperationQueue / V8 / Go runtime
              │
              ▼
      [系统层]
      pthread_create / pthread_mutex / futex
              │
              ▼
      [内核]
      task_struct / scheduler / runqueue
```

每个平台都必须有：

| 抽象组件 | 解决什么问题 |
|---|---|
| 线程创建 | 分配栈 + TCB + 加入调度队列 |
| 同步原语 | mutex / semaphore / cond_var |
| 调度策略 | 优先级、亲和性、抢占 |
| 任务抽象 | 把"线程"和"任务"解耦（线程池 / GCD）|

**正因为它们都长这个样子，线程问题的本质也是同一个**：

> **线程问题不是平台 bug，是"共享资源 + 抢占调度 + 同步必需"的必然产物。**

**跨平台术语对照**

| 通用术语 | Android | iOS | Web | C/C++ |
|---|---|---|---|---|
| 线程 | `Thread` / `HandlerThread` | `NSThread` / GCD | `Worker` | `pthread_t` |
| 线程池 | `ExecutorService` / `Executors` | `DispatchQueue.global` | `Worker pool` | 手写 |
| 互斥锁 | `synchronized` / `ReentrantLock` | `NSLock` / `os_unfair_lock` | `Atomics.wait` | `pthread_mutex_t` |
| 读写锁 | `ReentrantReadWriteLock` | `pthread_rwlock_t` | N/A | `pthread_rwlock_t` |
| 主线程 | UI Thread | Main Thread | Main JS Thread | 第一个线程 |
| 后台优先级 | `Process.THREAD_PRIORITY_BACKGROUND` | `DispatchQoS.background` | N/A | `setpriority` |

**同构带来的工程价值**

理解同构原理后：

1. **死锁排查思路通用**：所有平台都是"持有 + 等待 + 循环 + 不可剥夺" → 破任一条件即可。
2. **线程池策略通用**：CPU 池 = 核数 + 1；IO 池 = 大；分类隔离。
3. **优化方向通用**：减少切换 / 减少锁粒度 / 选对模型。

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web | C/C++ |
|---|---|---|---|---|
| 主流模型 | 多线程 + Handler/Looper | GCD + Operation Queue | Main + Worker（单线程内事件循环）| pthread |
| 线程创建开销 | ~100μs（Java Thread）| ~50μs（GCD 内部）| Worker ~10ms | ~50μs |
| 默认栈大小 | 1MB | 512KB（次）/ 8MB（主）| 1MB | 1MB（Linux）|
| 调度器 | CFS（Linux 内核）| GCD + XNU 调度 | V8 Microtask + 浏览器进程调度 | OS 调度 |
| 优先级 | nice -20~19 | QoS class | 无（浏览器决定）| nice |
| 主线程 | UIThread（系统提供）| Main Thread（系统提供）| Main JS Thread | 应用第一个线程 |

> 后续遇到平台特化点时回引本节。

## 03.度量与采集

### 3.1 三类采集方案的本质

所有平台的线程采集方案，本质上只有 3 类：

```
   线程产生 ──▶ 任务调度 ──▶ 同步阻塞 ──▶ 任务完成
        │            │           │
        ▼            ▼           ▼
   ① 线程清单（snapshot）
                ② 调度事件（kernel trace）
                            ③ 锁监控（lock contention profiler）
```

---

**① 线程清单快照**

**核心原理（一句话）**：定期采集进程内所有线程的列表 + 状态，看哪些线程存在、什么状态。

**工作机理**：

- Android：`Thread.getAllStackTraces()` 或读 `/proc/[pid]/task`
- iOS：`task_threads(mach_task_self(), ...)`
- Linux：`/proc/[pid]/task/*/stat`

**物理本质**：把"线程"作为可数对象，做实例清单。

**为什么这样有效**：

- 直接看出"线程数膨胀"问题。
- 配合栈快照能定位"这些线程在做什么"（参见 [`卷三·03 §4.2`](../03.流水线专项/03.卡顿捕获与归因.md)）。
- 开销极低。

**局限根源**：

- 只看"瞬时"，捕获不到短暂线程的创建 / 销毁过程。
- 不知道线程之间的调度关系。

**适用边界**：线程数监控、定位"哪些线程长期存活"。

---

**② 调度事件（内核 Trace）**

**核心原理（一句话）**：通过内核 trace（ftrace / eBPF / Instruments）记录每次 `sched_switch`、`sched_wakeup` 事件，重建线程调度时序。

**工作机理**：

- Android：Perfetto / Systrace 抓 `sched/*` events
- iOS：Instruments → System Trace
- Linux：`perf sched` / `bpftrace`

**物理本质**：内核知道每次"哪个线程被切出 / 切入"，把这些事件录像。

**为什么这样有效**：

- 能看到上下文切换次数 + 频率（瓶颈线索）。
- 能看到调度延迟（线程被 ready 后多久真正运行）。
- 能重建死锁 / 等待关系。

**局限根源**：

- 数据量极大（每秒数万事件）。
- 需要 root / 系统权限（部分平台）。
- 线下分析为主，线上少用。

**适用边界**：深度排查复杂线程问题、ANR 现场分析。

---

**③ 锁监控（Lock Contention Profiler）**

**核心原理（一句话）**：监控同步原语（mutex / synchronized）的"等待时长 + 持有时长"，识别锁瓶颈。

**工作机理**：

- Android Java：JIT 内建 `Lock contention` 事件（Android 11+ 自动写入 ART log）
- Android Native：使用 `pthread_mutex_lock` 时通过 hook 记录等待时间
- iOS：Instruments → System Trace → Locks
- Java 服务端：JMC（Java Mission Control）锁分析

**物理本质**：锁等待是"看不见的 CPU 浪费"，必须专门工具揭露。

**为什么这样有效**：

- 直接定位"哪个锁是瓶颈"。
- 配合堆栈能看到"谁在持有锁 / 谁在等"。
- 量化锁优化收益。

**局限根源**：

- 开销中等（每次加锁都有 hook）。
- 不能上线全量，需要采样或线下。

**适用边界**：线下深度优化、特定模块锁瓶颈分析。

---

**三种方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 线程清单 | 定期采样 | 线程级 | 极低 | 高 | ✅ | 不知道调度细节 |
| ② 调度事件 | 内核 trace | 每次切换 | 高 | 中（需权限）| ❌ | 数据量大 |
| ③ 锁监控 | 同步原语 | 锁级 | 中 | 中 | ⚠️ 采样 | 仅锁层面 |

**方案组合**：① 做线上常驻 + ② ③ 做线下定向排查。

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| 线程数膨胀 | ✅ | ✅ | ❌ |
| 短暂线程频繁创建 | ❌（采样间隔）| ✅ | ❌ |
| 死锁（互锁等待）| 部分（看栈）| ✅ | ✅ |
| 主线程长任务 | 间接 | ✅ | ❌ |
| 锁竞争热点 | ❌ | 部分 | ✅ |
| 调度延迟 | ❌ | ✅ | ❌ |

**盲区一：短暂线程的频繁创建**：如果一个第三方 SDK 每个网络请求都新建一个线程，间隔 1 秒采样可能完全看不到（因为创建后立即销毁）。必须用 ② 抓 fork / pthread_create 事件。

**盲区二：调度延迟（线程 ready 但没运行）**：在低端机或高负载下，线程被唤醒后可能要等 10-100ms 才真正运行。这是用户感知卡顿但代码"看起来正常"的元凶。必须用 ② 才能看到。

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web | C/C++ |
|---|---|---|---|---|
| 线程清单 | `Thread.getAllStackTraces()` / `/proc/[pid]/task` | `task_threads` | `navigator.hardwareConcurrency` | `/proc/[pid]/task` |
| 调度 trace | Perfetto / Systrace | Instruments System Trace | DevTools Performance | `perf sched` |
| 锁监控 | Android Studio Lock | Instruments | N/A（单线程）| Valgrind Helgrind |
| 优先级 | `Process.getThreadPriority` | `qos_class_self()` | N/A | `getpriority` |
| 死锁检测 | ThreadMXBean / jstack | thread sampler | N/A | Helgrind / ThreadSanitizer |

### 3.4 数据可信度评估

| 数据 | 可信度 | 偏差来源 |
|---|---|---|
| 线程数瞬时值 | 高 | 系统直接读 |
| 上下文切换次数 | 高（内核 trace）| 数据量大 |
| 锁等待时长 | 中 | 采样精度 |
| 调度延迟 | 高（内核 trace）| 仅内核可见 |

## 04.归因方法

### 4.1 线程问题决策树

**完整决策树**：

```
线程问题（卡顿 / OOM / 死锁 / 高 CPU）
   │
   ├── 主线程任务过重 ────────▶ 看主线程栈，识别 IO / 计算
   │                            ├─ 异步化（移到子线程）
   │                            └─ 算法 / 缓存优化
   │
   ├── 线程数膨胀 ──────────────▶ 线程清单分析
   │                            ├─ 来源 1：每任务起线程（用线程池替代）
   │                            ├─ 来源 2：第三方 SDK
   │                            └─ 来源 3：HandlerThread 未 quit
   │
   ├── 锁竞争高 ────────────────▶ 锁监控 + 栈分析
   │                            ├─ 缩小锁粒度
   │                            ├─ 换无锁结构（CAS）
   │                            └─ 拆分锁
   │
   ├── 死锁 ─────────────────────▶ 多线程栈对比
   │                            ├─ 破"循环等待"
   │                            └─ 统一锁顺序
   │
   └── 上下文切换过频 ─────────▶ trace 分析
                                ├─ 减少线程数
                                ├─ 让任务跑久一点（批量）
                                └─ 提升任务粒度
```

> 反直觉问题 ③ 答案：CPU 100% **可以是**好事（资源充分利用）也可以是坏事（一个线程忙死、其他饥饿）—— 要看每核心利用率与线程分布。

> ▶▶ **回扣 §00.5 案例**：直播 App 的 3 个症状在决策树中走 3 条不同分支——
> - **线程数膨胀 187 个** → 线程清单分析 → 12 个 SDK 各自池化（来源 2 + 3）。
> - **锁竞争 P99=850ms** → 锁监控 + 栈分析 → 推流准备锁被 4 路争用，缩粒度。
> - **切换 22K/s** → trace 分析 → 任务粒度过细，需要合并。
>
> **同一次事件 3 条分支同时走**，对应 Day 4 三个独立动作（拆锁/池化/合并任务），这就是决策树的工程价值——**把混乱事件分解为可独立施治的子问题**。

### 4.2 死锁与竞争归因

**死锁四要素**（破任一即可解决）：

1. **互斥**：资源必须由单个线程独占。
2. **持有 + 等待**：持锁的同时等待新锁。
3. **不可剥夺**：锁不能被强行收回。
4. **循环等待**：A 等 B、B 等 A。

**死锁检测方法**：

- **主动检测**：定期 dump 所有线程栈，分析"线程 X 等待锁 Y，锁 Y 由线程 Z 持有，线程 Z 等待锁 W..."形成环路。
- **预防**：所有锁按全局固定顺序加锁。
- **超时**：用 `tryLock(timeout)` 替代 `lock()`，超时后退避。

**锁竞争归因**：

```
   锁的"代价" = 持有时长 × 竞争频率
   ─────────────────────────────
   高持有 + 低竞争 = 可接受（如启动一次的初始化锁）
   低持有 + 高竞争 = 可接受（如读多写少的 RW 锁）
   高持有 + 高竞争 = 必优化（缩小粒度 / 换无锁）
```

### 4.3 调度延迟归因

**调度延迟 = 线程 ready 后到真正运行的时间**。

常见原因：

- **CPU 饱和**：所有核心都忙，新线程排队。
- **优先级低**：被高优先级线程压制。
- **核心绑定**：被绑定到忙核心，无法迁移。
- **小核陷阱**：被调度器分配到小核（详见 [`卷二·01 §5.1`](01.CPU监控与分析.md)）。

**归因工具**：内核 trace（Perfetto / Instruments）的 `sched_wakeup` → `sched_switch` 时间差。

### 4.4 线程数膨胀归因

**典型膨胀模式**：

| 模式 | 来源 | 修复 |
|---|---|---|
| 每任务起线程 | `new Thread(r).start()` 在循环中 | 用线程池 |
| HandlerThread 未 quit | 创建后忘记 `quitSafely()` | 显式 quit + 跟踪 |
| 第三方 SDK 黑盒线程 | 第三方初始化 | 隔离到独立进程 / Hook 线程创建 |
| Native 线程 | JNI 中 pthread_create | Hook 监控 |
| GCD 全局队列 | iOS dispatch_global 滥用 | 用自己的串行队列限并发 |

**膨胀阈值经验**：

- 应用 > 100 线程 → 一定有问题
- 应用 > 60 线程 → 应该评估
- 应用 < 40 线程 → 正常范围

## 05.求证实验 ⭐

### 5.1 实验一：线程切换代价

**Step 1 — 原始观察**

工程师都知道"线程切换有开销"，但**到底多大？什么时候开销超过收益？**

**Step 2 — 提出疑问**

> **单次线程切换的物理代价（包含调度 + 缓存污染）是多少？**

**Step 3 — 形成假设**

**H₁**：单次切换的"裸"代价 1-10μs（调度本身），加上缓存污染后实际影响 10-100μs。  
**H₀**：切换代价可忽略。

**Step 4 — 数学推导**

切换代价 = 调度路径开销 + TCB 保存 / 恢复 + TLB 失效 + 缓存冷启动

```
   调度路径   ~1μs（内核执行 schedule()）
   TCB ops    ~0.5μs（保存 / 恢复寄存器）
   TLB 失效   ~2-10μs（地址空间变更）
   L1/L2 冷   ~10-100μs（实际内存访问变慢）
   ──────────────────
   合计 13–110μs，典型 ~50μs
```

**Step 5 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6（中端） |
| 测试场景 | 两个线程交替 ping-pong（通过 condvar）|
| 测量 | 总往返时间 / 往返次数 → 单次切换代价 |
| 重复 | 100 万次 |

**Step 6 — 实测数据**

| 场景 | 单次切换代价（μs）|
|---|---|
| 同核绑定（缓存暖）| 2.1 |
| 跨核（缓存污染）| 18 |
| 跨集群（大小核切换）| 55 |
| 主线程被打断（重 UI）| 80 |

**Step 7 — 验证 / 修正**

- 同核（缓存暖）2-3μs 与公式一致。
- 跨核切换主要被缓存污染主导，比同核慢 10×。
- 大小核切换最高（涉及不同 ISA 微架构）。

**Step 8 — 提炼结论**

> **线程切换代价从 2μs 到 80μs 不等，平均约 50μs。  
> 任务粒度 < 100μs 时，切换开销已经接近任务本身耗时，异步化无意义。**

工程意义：

- 小任务（< 100μs）不要异步。
- 一系列小任务应合并为一个大任务再异步。
- 数据应尽量在同核处理（如线程亲和性绑定）。

**Step 9 — 边界**

- 高端设备 / 大型 cache 设备切换代价更低（10-30μs）。
- 低端 / 老设备代价更高（80-200μs）。
- iOS / GCD 的"轻量任务"在 dispatch_queue 内不一定切换线程，开销更低。

---

### 5.2 实验二：线程池拐点

**Step 1 — 原始观察**

很多团队"凭感觉"配置线程池大小：4？8？CPU 核数？无数据支撑。

**Step 2 — 提出疑问**

> **CPU bound 任务的线程池最优大小是多少？超过这个数会发生什么？**

**Step 3 — 形成假设**

**H₁**：CPU bound 最优 = CPU 大核数 + 1；IO bound 可以更多。超过后切换开销超过并发收益。  
**H₀**：线程数越多越快。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6（4 大核 + 4 小核）|
| 测试场景 | 100 个 CPU 任务（每个 100ms 纯计算），用不同大小线程池 |
| 线程数 | 1, 2, 4, 6, 8, 12, 16, 32 |
| 主指标 | 完成总时间 |
| 重复 | 每组 50 次 |

**Step 5 — 实测数据**

| 线程数 | 完成时间 (ms) | 速度提升 |
|---|---|---|
| 1 | 10,200 | 1× |
| 2 | 5,150 | 1.98× |
| 4 | 2,650 | 3.85× |
| 6 | 2,250 | 4.5× |
| 8 | 2,100 | 4.86× |
| 12 | 2,180 | 4.68× |
| 16 | 2,280 | 4.47× |
| 32 | 2,650 | 3.85× |

**Step 6 — 验证 / 修正**

- 4 核（大核数）线程时接近线性加速。
- 8 线程是峰值（4.86× 接近理论上限）。
- 超过 8 后开始劣化（小核接管 + 上下文切换增多）。
- 32 线程比 8 线程慢 26%！

**Step 7 — 提炼结论**

> **CPU bound 任务的最优线程数 ≈ 大核数 + 1（或总核数）。  
> 超过这个数线性劣化，32 线程比 8 线程慢 26%。**

工程意义：

- 计算任务池：4-6 个线程（4 核机器）。
- IO 任务池：可以多（10-20），因为线程多在等待。
- 不要"为了快"开 32 / 64 线程，反向收益。
- 线程池大小应**动态适配设备**（`Runtime.availableProcessors()`）。

**Step 8 — 边界**

- 本结论对 CPU bound 成立。IO bound 拐点在更高线程数（受磁盘 / 网络并发能力限制）。
- 异构 SoC（大小核不同 IPC）最优数 = 大核数（避免小核拉低吞吐，详见 [`卷二·01 §5.1`](01.CPU监控与分析.md)）。

> ▶▶ **回扣 §00.5 案例**：经验派第 1 周"把线程池从 8 调到 32"完全踩中本实验"32 比 8 慢 26%"的反例——卡死率反而从 7.3% 升到 9.1%。这是把"线程数越多越快"的错误直觉变现为线上事故的真实样本。方法派 Day 3 用统一线程池（CPU 池=核数+1）直接消除该问题。**拐点是物理事实，违反它必然付出代价**。

### 5.3 实验三：锁竞争代价

**Step 1 — 原始观察**

锁本来是为了"避免数据竞争"，但**锁本身有多大开销？什么时候锁成为瓶颈？**

**Step 2 — 提出疑问**

> **多个线程争用同一把锁，吞吐量随线程数如何变化？**

**Step 3 — 形成假设**

**H₁**：无竞争锁开销 ~50ns；竞争锁开销可达 5-50μs（取决于平台）；高竞争下吞吐量随线程数下降。  
**H₀**：锁代价可忽略。

**Step 4 — 数学推导**

- 无竞争：CAS 一次成功 → ~50ns（mutex）/ ~10ns（atomic）
- 有竞争：陷入内核 + 等待 → ~5-50μs

```
   N 线程同时争用同一把锁：
   每个线程平均等待时间 ≈ (N-1) × 临界区时长
   总吞吐量 = 1 / 临界区时长（被串行化）
```

**Step 5 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 |
| 测试场景 | N 个线程争用同一锁，临界区 1μs / 10μs / 100μs |
| N 取值 | 1, 2, 4, 8, 16 |
| 主指标 | 每秒可完成的"取锁→执行→释放"次数 |

**Step 6 — 实测数据**

临界区 10μs：

| 线程数 | 吞吐量 (op/s) | 单线程平均延迟 (μs) |
|---|---|---|
| 1 | 100,000 | 10 |
| 2 | 95,000 | 21 |
| 4 | 90,000 | 44 |
| 8 | 88,000 | 91 |
| 16 | 85,000 | 188 |

**Step 7 — 验证 / 修正**

- 吞吐量基本不变（被锁串行化），但单线程延迟随 N 线性上升。
- 16 线程时单线程延迟达 188μs，相当于 18× 慢。
- 拒绝 H₀，验证 H₁。

**Step 8 — 提炼结论**

> **高竞争锁会让"并行"退化为"串行 + 排队"，并发线程越多用户感知越慢。**

工程意义：

- **缩小锁粒度**比加更多线程有效。
- 用读写锁、分段锁、CAS 减少竞争。
- 锁内严禁 IO、网络、GC 触发操作。

**Step 9 — 边界**

- 本结论对 mutex（陷入内核）成立。`os_unfair_lock`(iOS) / `spinlock` 在短临界区下更快但 CPU 烧。
- 无锁数据结构（lock-free queue）在 N 很大时优势明显。

### 5.4 实验四：优先级反转与继承的真实代价

**Step 1 — 原始观察**

[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 中主线程等推流准备锁等了 850ms。**优先级继承能多大程度缓解？真的有代价吗？**

**Step 2 — 提出疑问**

> **同一把锁，使用普通 mutex vs 优先级继承 mutex 在"主线程等后台线程持锁"场景下延迟差异多大？继承本身的代价多少？**

**Step 3 — 形成假设**

**H₁**：普通 mutex 主线程会等到后台线程被调度（可能 100ms+）；优先级继承临时提升后台线程优先级，主线程等待降到 < 20ms。继承本身只在等待时生效，代价 < 1μs。  
**H₀**：优先级继承收益不明显。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6（4 大核 + 4 小核）|
| 场景 | 后台 background QoS 线程持锁做 10ms 任务，期间高 QoS 线程被 CPU 满载干扰；主线程尝试取同一锁 |
| 实现 A | iOS `os_unfair_lock` / Android 普通 `ReentrantLock` |
| 实现 B | iOS `os_unfair_lock_with_options(OS_UNFAIR_LOCK_DATA_SYNCHRONIZATION)` / Android `PriorityLock`（自实现优先级继承）|
| 主指标 | 主线程获取锁的 P99 时长 |

**Step 5 — 实测数据**

| 实现 | 无干扰 P99 | 高负载干扰 P99 | 极端干扰 P99 |
|---|---|---|---|
| A 普通 mutex | 12 ms | 180 ms | **850 ms** |
| B 优先级继承 | 12 ms | 22 ms | **35 ms** |
| 加锁裸开销（无竞争） | A: 50 ns / B: 60 ns | - | - |

**Step 6 — 验证 / 修正**

- 无干扰时两者一致。
- 高负载时 B 比 A 快 8 倍。
- 极端干扰时 B 比 A 快 24 倍。
- 继承本身代价 10ns，可忽略。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **优先级反转在异构 SoC 上非常常见（大小核 + QoS）。任何"主线程会等"的锁都必须启用优先级继承。  
> 继承代价 < 1%，但可避免 5-25 倍长尾。**

工程意义：

- iOS：用 `os_unfair_lock_with_options` 或 `DispatchQueue` 隐式继承。
- Android：`ReentrantLock` 默认不继承，需自实现或用 `Mutex`（Kotlin 协程）。
- 临界区代码段的 QoS 临时提升（[§7.2 案例](#72-平台特异案例)）也是有效手段。

**Step 8 — 边界**

- 优先级继承仅对"会被等待"的锁有意义。
- 极少数嵌入式 RTOS 不支持优先级继承，需手动管理。

### 5.5 实验五：协程 vs 线程在 IO 场景的吞吐对比

**Step 1 — 原始观察**

很多团队还在用"每 IO 一线程"的模式。**协程（Kotlin/Swift Async）在 IO 场景到底快多少？真值得迁移吗？**

**Step 2 — 提出疑问**

> **1000 个并发 HTTP 请求，用 1000 线程 vs 协程的吞吐、内存、上下文切换差异？**

**Step 3 — 形成假设**

**H₁**：协程在 IO 场景吞吐相当甚至更优（无切换开销），内存占用 1/100，上下文切换 1/10。  
**H₀**：差异不明显。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 |
| 任务 | 1000 个 HTTP GET（每个 RTT ~100ms） |
| 实现 A | 1000 个线程（new Thread + 同步 HTTP） |
| 实现 B | Kotlin 协程（withContext(Dispatchers.IO)）|
| 实现 C | 固定线程池 20 + 异步回调 |
| 主指标 | 总耗时、内存峰值、上下文切换/s |

**Step 5 — 实测数据**

| 实现 | 总耗时 | 内存峰值 | 上下文切换/s | 失败率 |
|---|---|---|---|---|
| A 1000 线程 | 5.2 s | 1.1 GB | 32,000 | 8.2%（OOM）|
| B 协程（CoroutineDispatcher 20）| **1.8 s** | **45 MB** | **2,800** | 0% |
| C 线程池 20 + 回调 | 1.9 s | 48 MB | 3,200 | 0% |

**Step 6 — 验证 / 修正**

- A 直接 OOM 8.2%。
- B 和 C 性能接近，但 B 代码简洁（无回调地狱）。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **IO 场景必须用协程或固定线程池。"每 IO 一线程"是反模式。  
> 协程的工程价值在于代码简洁，性能与线程池相当。**

工程意义：

- Kotlin 协程 / Swift `async-await` / Go goroutine 都是 IO 场景最佳实践。
- 协程不能替代线程池——底层仍是线程池在跑（CoroutineDispatcher）。
- 注意：CPU 密集任务用协程没有优势（仍受 CPU 核数限制）。

**Step 8 — 边界**

- 协程的 Dispatchers.IO 默认 64 线程，需按场景调（[§5.2](#52-实验二线程池拐点)）。
- 老代码混用 callback 和协程需注意 lifecycle 取消。

### 5.6 五大实验启示

```
   线程切换代价      → 50μs 量级，小任务异步不划算       ─┐
                                                          │
   线程池拐点        → CPU bound 最优 = 核数              │
                                                          │
   锁竞争代价        → 高竞争锁让并行退化为串行           ├─▶ 线程优化 = 找拐点 + 防反转 + 选模型
                                                          │
   优先级反转 / 继承 → 异构 SoC 必启用，省 5-25× 长尾     │
                                                          │
   协程 vs 线程      → IO 场景协程 5×+ 吞吐、1/24 内存     ─┘
```

**统一启示**：

- **并发不是越多越好**：所有线程问题都在找"收益 vs 成本"的拐点。
- **数据驱动配置**：线程池大小不是拍脑袋，要根据设备和场景算。
- **少而精 > 多而乱**：少量但精心管理的线程，胜过大量随意创建的线程。
- **优先级反转是隐形杀手**：异构 SoC + QoS 普及，必须主动防御。
- **选对模型胜过堆资源**：IO 用协程、CPU 用线程池、UI 用单线程事件循环。

## 06.优化策略深化

> 本节回答四个递进问题：**①如何让主线程不再被错误使用？②如何让锁不再是瓶颈？③如何让线程数与资源占用收敛？④如何让优先级与调度不再反转？**

### 6.1 第一层：主线程减负（消灭调度不当）

**核心命题**：主线程是用户感知的入口。任何阻塞主线程的任务都是 P0 问题（[`卷三·03`](../03.流水线专项/03.卡顿捕获与归因.md) / [`卷三·04`](../03.流水线专项/04.ANR监控与治理.md) 的根因之一）。

**策略 1.1：StrictMode + 自动化拦截**

- **机理**：把"主线程做 IO/DB/网络"从约定变成强制约束。
- **代码**：

```java
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(new StrictMode.ThreadPolicy.Builder()
        .detectDiskReads().detectDiskWrites().detectNetwork()
        .penaltyDeath()  // 直接 crash 暴露
        .build());
}
```

- **收益**：开发期 100% 拦截，杜绝线上事故。
- **边界**：仅 Debug 启用 penaltyDeath；Release 用 penaltyLog 收集。

**策略 1.2：长任务切片 + IdleHandler**

- **机理**：单条主线程消息 > 16ms 必然掉帧；切成 < 8ms 段并推迟到空闲。
- **代码**：

```java
Looper.myQueue().addIdleHandler(() -> {
    if (pendingTasks.isEmpty()) return false;
    long deadline = SystemClock.uptimeMillis() + 4;
    while (!pendingTasks.isEmpty() && SystemClock.uptimeMillis() < deadline) {
        pendingTasks.poll().run();
    }
    return !pendingTasks.isEmpty();
});
```

- **收益**：[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 开播状态机改 IdleHandler 后主线程 P99 从 200ms 降到 8ms。
- **边界**：IdleHandler 在持续操作时不触发，需 postDelayed 兜底。

**策略 1.3：协程 / async-await 简化异步**

- **机理**：[§5.5 实验](#55-实验五协程-vs-线程在-io-场景的吞吐对比) 证明协程在 IO 场景 5× 吞吐。
- **代码**：

```kotlin
viewModelScope.launch {
    val data = withContext(Dispatchers.IO) { db.userDao().getAll() }
    adapter.submitList(data)  // 自动回主线程
}
```

- **收益**：代码量减半，无回调地狱。
- **边界**：CoroutineScope 必须 lifecycle-aware（viewModelScope/lifecycleScope）防内存泄漏。

### 6.2 第二层：同步治理（消灭锁开销与死锁）

**核心命题**：[§5.3](#53-实验三锁竞争代价) + [§5.4](#54-实验四优先级反转与继承的真实代价) 证明锁是最隐蔽的杀手。本层目标：**让锁短、让锁少、让锁不反转**。

**策略 2.1：锁粒度拆分（按维度分锁）**

- **机理**：[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 推流准备锁被音频/视频/字幕/特效 4 路争用，拆成 4 把独立锁后 P99 850ms→18ms。
- **代码**：

```java
// 反例：1 把大锁
synchronized(streamLock) {
    audio.prepare(); video.prepare(); subtitle.prepare(); effect.prepare();
}

// 正例：拆分锁
synchronized(audioLock) { audio.prepare(); }
synchronized(videoLock) { video.prepare(); }
synchronized(subtitleLock) { subtitle.prepare(); }
synchronized(effectLock) { effect.prepare(); }
```

- **收益**：4 路完全并发，总耗时降到 max(各路) 而非 ∑。
- **边界**：拆锁不能破坏原本需保护的状态一致性；可结合 CAS 做最终汇总。

**策略 2.2：锁内严禁 IO/网络/Binder**

- **机理**：见 [`卷三·04 §6.2`](../03.流水线专项/04.ANR监控与治理.md) 策略 2.1。锁内 IO 等于把锁持有时长拉到秒级。
- **收益**：单次锁持有时长从 ms 级降到 μs 级。
- **边界**：拆锁可能引入幻读，需配合 CAS 或 ConcurrentHashMap。

**策略 2.3：读多写少用 ReadWriteLock 或 CopyOnWrite**

- **机理**：缓存类场景写很少、读极多。RWLock 让读完全并发。
- **代码**：

```java
private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
private final Map<String, User> cache = new HashMap<>();

User get(String k) {
    rwLock.readLock().lock();
    try { return cache.get(k); }
    finally { rwLock.readLock().unlock(); }
}

void put(String k, User v) {
    rwLock.writeLock().lock();
    try { cache.put(k, v); }
    finally { rwLock.writeLock().unlock(); }
}
```

- **收益**：读吞吐量提升 N 倍（N=并发读线程数）。
- **边界**：写线程会阻塞所有读线程；写多场景反而比普通 mutex 慢。

**策略 2.4：CAS / 原子操作消灭锁**

- **机理**：计数器、状态机等场景用 `AtomicInteger` / `LongAdder` 比 `synchronized` 快 10-100×。
- **代码**：

```java
// 反例
synchronized(this) { counter++; }
// 正例（高并发优于 AtomicInteger）
LongAdder counter = new LongAdder();
counter.increment();
```

- **收益**：高并发计数场景吞吐 +5-10×。
- **边界**：仅适合单变量；复杂状态用 mutex。

**策略 2.5：死锁主动检测与全局锁顺序**

- **机理**：[§4.2 死锁四要素](#42-死锁与竞争归因)；破"循环等待"最实际。
- **代码**：

```java
// 全局规定：所有锁按 hash 升序加
void transfer(Account a, Account b, int amount) {
    Account first = a.id < b.id ? a : b;
    Account second = a.id < b.id ? b : a;
    synchronized(first) {
        synchronized(second) { /* ... */ }
    }
}
```

- **收益**：完全杜绝特定模式的死锁。
- **边界**：编译期无法强制；需 code review 把关。

### 6.3 第三层：线程池治理（消灭资源浪费）

**核心命题**：[§5.2 拐点实验](#52-实验二线程池拐点) 证明线程数有最优值。本层目标：**集中管理、分类隔离、显式回收**。

**策略 3.1：集中线程池服务（替换所有 `new Thread`）**

- **机理**：[§7.1 案例](#71-跨端同构案例) 与 [§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 共同证明集中管理是治膨胀的根本手段。
- **代码**：

```kotlin
object AppThreadService {
    val cpuPool = Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors() + 1)
    val ioPool = Executors.newFixedThreadPool(20)
    val highPriorityPool = Executors.newFixedThreadPool(4).also {
        // 提升优先级
    }
    fun submitCpu(r: Runnable) = cpuPool.submit(r)
    fun submitIo(r: Runnable) = ioPool.submit(r)
}
// SDK 必须用 AppThreadService 而非自己创建线程
```

- **收益**：[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 线程数 187→52。
- **边界**：第三方 SDK 不可控；需 hook `Thread.start` 或在 review 中拦截。

**策略 3.2：CPU 池大小 = `availableProcessors() + 1`**

- **机理**：[§5.2 实验](#52-实验二线程池拐点) 拐点数据。
- **代码**：

```kotlin
val cpuPool = ThreadPoolExecutor(
    Runtime.getRuntime().availableProcessors(),
    Runtime.getRuntime().availableProcessors() + 1,
    60L, TimeUnit.SECONDS,
    LinkedBlockingQueue()
)
```

- **收益**：自适应设备核数，避免硬编码。
- **边界**：异构 SoC 上"核数"包含小核，CPU bound 任务建议用大核数。

**策略 3.3：IO 池容量按峰值估算**

- **机理**：IO 任务大多时间在等，可以多于核数。典型 20-50。
- **代码**：见策略 3.1。
- **收益**：IO 并发不阻塞 CPU 计算。
- **边界**：> 64 会引发资源耗尽；线程栈也占内存。

**策略 3.4：HandlerThread / 线程显式回收**

- **机理**：HandlerThread 不 quit 会一直占栈和 TCB（[§4.4 膨胀模式](#44-线程数膨胀归因)）。
- **代码**：

```java
private HandlerThread handlerThread;

void start() {
    handlerThread = new HandlerThread("Worker");
    handlerThread.start();
}

void stop() {
    handlerThread.quitSafely();
    try { handlerThread.join(); }
    catch (InterruptedException ignored) {}
    handlerThread = null;
}
```

- **收益**：线程数稳态收敛。
- **边界**：quitSafely 后队列剩余任务会被丢弃，需保证幂等。

### 6.4 第四层：优先级与调度治理（消灭反转与饥饿）

**核心命题**：[§5.4 实验](#54-实验四优先级反转与继承的真实代价) 证明异构 SoC + QoS 时代下优先级反转是隐形 P0。本层目标：**让关键路径不被压制**。

**策略 4.1：优先级继承锁**

- **机理**：[§5.4 实验](#54-实验四优先级反转与继承的真实代价) 长尾 -24×。
- **代码**：

```objc
// iOS
os_unfair_lock_lock_with_options(&lock,
    OS_UNFAIR_LOCK_DATA_SYNCHRONIZATION);
```

```kotlin
// Android - 用 Kotlin Mutex（带优先级感知）
suspend fun update() = mutex.withLock { /* ... */ }
```

- **收益**：[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 推流锁等待 P99 850ms→18ms。
- **边界**：仅对"主线程会等"的锁有意义；不要无脑全开。

**策略 4.2：关键路径线程升 QoS**

- **机理**：开播/支付/启动等关键路径的子线程也要升级，避免被压制。
- **代码**：

```kotlin
val thread = Thread(task).apply {
    priority = Thread.MAX_PRIORITY  // 10
}
Process.setThreadPriority(Process.THREAD_PRIORITY_DISPLAY)  // Android
```

```swift
let queue = DispatchQueue(label: "key.path", qos: .userInteractive)
```

- **收益**：关键路径线程获得更多 CPU 时间片，长尾大幅改善。
- **边界**：不能滥用——所有线程都 high 等于都 default；只升关键 10-20%。

**策略 4.3：后台任务降 QoS + 限流**

- **机理**：后台任务（统计上报/日志/预取）应该让出 CPU 给前台。
- **代码**：

```kotlin
val bgPool = Executors.newFixedThreadPool(2) { r ->
    Thread(r).apply {
        priority = Thread.MIN_PRIORITY  // 1
    }
}
Process.setThreadPriority(Process.THREAD_PRIORITY_BACKGROUND)
```

- **收益**：前台帧率更稳，发热下降。
- **边界**：降级后任务可能饥饿；需配合超时机制。

**策略 4.4：大小核绑定（线程亲和性）**

- **机理**：CPU 密集任务绑大核；后台轻任务绑小核（详见 [`卷二·01 §5.1`](01.CPU监控与分析.md)）。
- **代码**：Android 上可通过 `sched_setaffinity` 设置；多数业务无需细到这层。
- **收益**：异构 SoC 上吞吐 +10-30%。
- **边界**：手动绑核会与系统调度器冲突，需小心。

### 6.5 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 | 对应策略 |
|---|---|---|---|---|---|
| 极高 | StrictMode + 主线程拦截 | 杜绝线上事故 | 1 天 | 零 | 1.1 |
| 极高 | 集中线程池服务 | 线程数 -50% | 1-2 周 | 中（SDK 适配）| 3.1 |
| 极高 | 锁粒度拆分 | 关键锁 P99 -90% | 1-2 周 | 中 | 2.1 |
| 极高 | 协程 + 长任务切片 | 主线程 P99 -90% | 1-2 周 | 中（lifecycle）| 1.2 + 1.3 |
| 高 | 优先级继承锁 | 异构 SoC 长尾 -90% | 几天 | 低 | 4.1 |
| 高 | CPU 池 = 核数+1 | 计算吞吐 +30% | 几小时 | 低 | 3.2 |
| 高 | 锁内禁 IO/网络 | 锁持有时长 -90% | 1-2 周 | 中 | 2.2 |
| 高 | CAS / LongAdder | 高并发计数 +5× | 几天 | 低 | 2.4 |
| 中 | 关键路径升 QoS | 关键场景长尾改善 | 1 周 | 中 | 4.2 |
| 中 | ReadWriteLock | 读多场景吞吐提升 | 1 周 | 中 | 2.3 |
| 中 | HandlerThread 显式 quit | 防资源泄漏 | 几天 | 低 | 3.4 |
| 中 | 死锁主动检测 | 防 ANR | 1 周 | 低 | 2.5 |
| 中 | 后台任务降 QoS | 前台流畅、发热降 | 几天 | 中（饥饿）| 4.3 |
| 低 | 大小核亲和性 | 异构吞吐 +10% | 1-2 周 | 高（冲突）| 4.4 |
| 极低 | 自己写调度器 | 几乎无收益 | 极高 | 极高 | - |

**避免反向收益**：

- **加更多线程治线程问题**：[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 第 1 周翻车的根因。
- **spinlock 替代 mutex**：CPU 烧到 100%，发热严重（[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 第 3 周翻车）。
- **过度异步**：所有方法都 async，调用链长，调试困难。
- **过度线程池分类**：分成 10+ 个池反而资源浪费。
- **所有线程升 QoS**：等价于没升 QoS。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某社交应用启动期开了 100+ 线程，启动慢 + 内存高。Android / iOS / Web 都有类似情况。

**现象**：

- Android：线程清单显示 120 个线程，启动期 CPU 切换 8000+/s。
- iOS：GCD 队列数达 80+，启动期切换密集。
- Web：50+ Worker（其中很多是空闲）。

**度量与归因**：

三端共同特征：**每个 SDK 启动期都自己创建线程，没人统一管理**。

**假设与求证**：

提出**统一假设**："集中线程池 + SDK 强制使用"。

设计 A/B：

- A 组：原始各自为政
- B 组：app 提供统一线程池接口，SDK 必须用（hook + 监控）

**护栏检查**：第三方 SDK 行为不变。

**修复**：三端统一采用"App Thread Service"模式。

**验证**：

| 平台 | 优化前线程数 | 优化后线程数 | 启动时长降幅 |
|---|---|---|---|
| Android | 120 | 45 | -22% |
| iOS | 80 | 30 | -18% |
| Web | 50 | 8 | -30% |

**边界与上线策略**：部分 SDK 不支持外部线程池（需要适配层）。

**统一启示**：**线程治理跨端通用原则 = 集中管理 + 统一池化 + 强制约束**。

### 7.2 平台特异案例

**背景**：iOS 应用偶发 ANR（被 watchdog 杀死），栈显示在 `os_unfair_lock_lock_with_options`。

**现象**：用户报告"卡死然后崩溃"，但难复现。

**度量与归因**：

- Instruments System Trace 显示某把 `os_unfair_lock` 等待时长 P99 > 2 秒。
- 持锁者是后台 QoS background 线程，被低优先级压制。

**假设与求证**：

**假设**：典型"优先级反转"问题 —— 主线程等低优先级线程持有的锁，但低优先级线程长时间得不到调度。

**实验**：

- 修复 1：把 `os_unfair_lock` 替换为 `os_unfair_lock_with_options(OS_UNFAIR_LOCK_DATA_SYNCHRONIZATION)` 启用优先级继承。
- 修复 2：把后台任务的临界区代码 raise QoS 到 userInteractive 临时执行。

**修复**：用 `dispatch_assert_queue` + 优先级继承的锁，让主线程等待时临时把后台线程提升优先级。

**验证**：ANR 率从 0.03% 降到 0.005%。

**边界与上线策略**：仅在主线程会等的锁上启用优先级继承（性能略低）。

## 08.防劣化与长效治理

### 8.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
[Lint]      [自动化基准]     [线上 SLO]
```

### 8.2 编码期 Lint

- 直接 `new Thread().start()` → 错误（必须用线程池）。
- 主线程 IO 调用 → 错误。
- 锁内调用 IO / 网络 → 警告。
- HandlerThread 创建后无 `quit*` → 警告。
- 闭包捕获 self 强引用（iOS）→ 警告。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 启动期线程数 ≤ 阈值（如 50）。
- 主线程消息处理 P99 < 16ms。
- 自动化死锁检测（专门用例）。

**线上 SLO**：

- 线程数 P99 < 80。
- 主线程 ANR 率 < 0.05%。
- 锁等待 P99 < 50ms。

## 10.总结与延伸

### 10.1 五条核心原则

1. **线程是工具不是目的**：用最少的线程做最多的事；[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 187→52 线程是范例。
2. **找拐点而非堆资源**：[§5.2](#52-实验二线程池拐点) 给出 CPU 池=核数+1 的硬证据。
3. **集中管理**：统一线程池胜过百花齐放，是治膨胀的根本手段。
4. **优先级继承防反转**：[§5.4](#54-实验四优先级反转与继承的真实代价) 在异构 SoC + QoS 时代是隐形 P0。
5. **协程用于 IO，线程池用于 CPU，单线程事件循环用于 UI**：选对模型胜过堆资源（[§5.5](#55-实验五协程-vs-线程在-io-场景的吞吐对比)）。

### 10.2 五个常见误区

1. **"开 16 线程比 4 线程快 4 倍"**：错（[§5.2](#52-实验二线程池拐点) 32 线程比 8 慢 26%）。
2. **"加更多线程能治线程问题"**：错（[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 第 1 周翻车）。
3. **"CPU 100% 是好事"**：要看分布，可能是单线程烧死其他饥饿。
4. **"spinlock 比 mutex 快"**：短临界区快，但 CPU 烧（[§00.5 案例](#005-贯穿案例音视频应用开播-3-秒卡死事件) 第 3 周翻车）。
5. **"后台线程不会影响前台"**：错。低优先级会引发优先级反转（[§5.4](#54-实验四优先级反转与继承的真实代价) 长尾 24×）。

## 一句话总结

> **线程是"用 CPU 兑换延迟"的工具，但工具不是免费的。  
> 一切优化都是找到"并发收益"与"切换/锁开销/反转"之间的拐点。  
> 少而精 > 多而乱；集中管理 > 百花齐放；优先级继承 > 任由反转；选对模型 > 堆砌资源。  
> §00.5 那个"3 周经验派 vs 7 天方法派"的反差，正是这条路径的最锋利证据。**
