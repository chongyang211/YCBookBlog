## 01.专栏世界观

### 1.1 我们要解决什么问题

性能优化领域的常见痛点：

- **平台割裂**：Android / iOS / Web / 嵌入式 各讲各的，原理相同的问题被讲成了"四套知识"。
- **经验主义**：充斥"建议这样做""通常那样会快"，缺乏可证伪的求证。
- **碎片化**：今天讲一个 GC、明天讲一个火焰图，缺少统一的方法论坐标系。
- **不持久**：辛苦优化一轮，三个版本被业务功能堆回去。

本专栏的目标：**用一套方法论 + 一套指标语言 + 一套分卷体系，把上述痛点系统性解决**。

### 1.2 跨平台抽象的必要性

**核心命题**：性能问题的"原理"是跨平台同构的，"实现"才是平台特异的。

```
原理（跨平台共性）：    资源 × 时间 × 流水线
                          │
                          ▼
实现（平台特异）：   ART / V8 / OC Runtime / RTOS
```

学懂任意一端的原理，迁移到其他端只需要换 API 名称。本专栏的所有文章都遵循"**先讲跨平台原理，再讲平台特化实现**"的结构。

详见 → [`00.公共方法论/01.性能工程总论与第一性原理`](./00.公共方法论/01.性能工程总论与第一性原理.md)

### 1.3 科学求证的写作范式

每篇文章必须满足：

- 所有结论**可证伪**（带前置条件、设备、数据集）。
- 所有数字**有出处**（带样本量、置信区间、P50/P95/P99）。
- 所有建议**有边界**（什么场景成立，什么场景不成立）。
- 所有案例**走完闭环**（现象 → 度量 → 归因 → 求证 → 防御）。

详见 → [`00.公共方法论/03.性能求证实验方法论`](./00.公共方法论/03.性能求证实验方法论.md)


## 02.分卷设计原则

### 2.1 分卷的三个维度

把内容拆成"卷"，需要在三个正交维度上找到一个一致的切分：

| 维度 | 含义 | 是否作为分卷依据 |
|---|---|---|
| **抽象层级** | L1 系统 / L2 运行时 / L3 应用 / L4 体感 | ✅ 主维度 |
| **问题视角** | 资源（USE）/ 请求（RED）/ 体感（APDEX） | ✅ 辅维度 |
| **技术维度** | 监控 / 优化 / 防御 | ❌ 不作为分卷（每篇内部都包含三者） |

**最终采用的分卷主线**：

```
方法论（卷零） → 体系建设（卷一） → 资源（卷二） → 流水线（卷三） → 业务（卷四） → 交付防御（卷五）
   ↑              ↑                    ↑               ↑                ↑                ↑
   宪法           地基                  L1              L2               L3               L4 边界
```

### 2.2 卷与卷的衔接关系

```
                        ┌─────────────────────┐
                        │    卷零：方法论       │  ← 提供：模型、指标、求证、归因
                        └──────────┬──────────┘
                                   │ 被所有卷引用
                                   ▼
                        ┌─────────────────────┐
                        │  卷一：体系建设      │  ← 提供：APM、稳定性、SLO 守护
                        └──────────┬──────────┘
                                   │ 提供基础设施
            ┌──────────────────────┼──────────────────────┐
            ▼                      ▼                      ▼
   ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
   │  卷二：资源篇   │  │  卷三：流水线   │  │  卷四：业务篇   │
   │  CPU/MEM/线程   │  │  渲染/卡顿/UI   │  │  启动/网络/图片 │
   └────────┬────────┘  └────────┬────────┘  └────────┬────────┘
            └─────────┬──────────┴─────────┬──────────┘
                      │                    │
                      ▼                    ▼
                ┌─────────────────────────────┐
                │     卷五：交付与防御        │  ← 收口：崩溃、包体、安全
                └─────────────────────────────┘
```

**关键约定**：

- **卷零是基础设施**：定义术语、模型、方法论。其他卷必须引用而非重复。
- **卷一是工具地基**：APM 与稳定性体系，是后续卷内"如何度量"的支撑。
- **卷二/三/四并列展开**：分别从资源、流水线、业务三种视角看性能问题。它们之间会**互相引用**（如启动优化要引用 CPU/IO/线程章节）。
- **卷五是边界与收口**：崩溃、包体、安全 —— 这些是"性能 / 体验"的边界条件，不属于性能本体但与性能强耦合。

### 2.3 卷内文章的统一骨架

每篇文章遵循 [`README.md`](./README.md) 中定义的"科学求证 11 章骨架"：

```
00.阅读说明 → 01.问题域 → 02.第一性原理 → 03.度量与采集 → 04.归因方法
→ 05.求证实验 ⭐ → 06.优化策略 → 07.实战案例 → 08.防劣化 → 09.跨平台对照 → 10.总结
```

## 05.卷一：体系建设（可观测性与稳定性）

### 卷定位
> **基础设施层**。在你做任何具体的资源 / 流水线 / 业务优化之前，必须先有"看得见、防得住"的能力。

### 卷目标
- 提供线上线下统一的可观测能力（**怎么看见性能问题**）。
- 建立稳定性兜底体系（**性能问题不演变为崩溃**）。
- 治理性能数据本身（**数据可信、可对比、可决策**）。

### 卷文章

| 序号 | 文章 | 核心命题 | 来源 |
|---|---|---|---|
| 01 | 应用 APM 的设计 | 可观测性是性能工程的地基 | 已有：`01.应用Apm的设计.md` |
| 02 | 稳定性专项建设 | 稳定性是性能的边界条件 | 已有：`18.应用稳定性专项.md` |
| 03 | 性能监控数据治理 ★ | 监控数据本身的可信度 / 一致性 / 可决策性 | **新增** |

### 为什么新增"03.性能监控数据治理"
现有 APM 文档解决"采什么、怎么采"，但缺一篇专门讲：

- 跨端口径对齐（Android/iOS/Web 同名指标含义不同）
- 数据质量评估（采样偏差、生存偏差、设备偏差）
- 数据血缘与追溯（指标定义变更如何不影响历史数据）
- 数据-决策衔接（看板、告警、错误预算的落地）

这是 APM 与"线上 SLO 守护"之间缺失的一环。

| 05 | 进程模型与多进程优化 | 进程是隔离单元，也是性能边界 | 已有：`13.进程优化设计实践.md` |

### 为什么新增"06.IO 与存储性能"
现有文章中 IO 散落在 CPU、卡顿、网络、图片等多个章节里，缺乏系统化的论述。但 IO 实际上是：

- off-CPU 等待的最大来源（详见卷零·05 归因方法论）。
- SharedPreferences、SQLite、文件读写、mmap 等所有存储原语的统一抽象层。
- 跨平台同构性极强（Linux / Darwin / 浏览器 IndexedDB / RTOS Flash）。

需要一篇专门系统化论述。

### 为什么新增"04.列表与滚动性能"
列表是几乎所有 App 的核心场景：

- 同时考验 渲染 / 内存 / 图片 / 网络 / 复用机制。
- 在卷三"渲染"和卷四"图片"中都有零散提及，但缺少综合性的"场景化"文章。
- 跨平台同构性极强（RecyclerView / UICollectionView / VirtualList / LVGL List）。

### 为什么新增"05.功耗与电量优化"

- 移动 / 嵌入式领域，"性能"必须放在功耗约束下讨论。
- "用更少电做同样事"和"用同样电做更多事"是同一个命题的两面。
- 涉及 频率调度、唤醒锁、定位 / 传感器、网络聚合等独立知识体系。

> 说明：嵌入式开发者会发现这一卷与你日常关注的 RTOS、MCU 性能问题强相关。


## 09.卷五：交付与防御（崩溃包体安全）

### 卷定位
> **L4 体感边界**。这些主题不是"性能本体"，但与性能强耦合 —— 它们决定**性能成果能否安全交付到用户手里**。

### 卷目标
- 性能成果的"防御层"：崩溃保护、包体约束、安全权衡、极端环境兜底。
- 帮助理解性能优化的"上下文边界"。

### 卷文章

| 序号 | 文章 | 核心命题 | 来源 |
|---|---|---|---|
| 01 | 崩溃捕获设计实践 | 崩溃是性能体系的最后一道防线 | 已有：`14.崩溃捕获设计实践.md` |
| 02 | 包体积与资源治理 | 包体积是冷启动 / 安装转化的瓶颈 | 已有：`19.App资源和反编译.md` |
| 03 | 应用安全与性能权衡 | 安全是性能 / 稳定性的隐形成本 | 已有：`16.应用安全的防御.md` |
| 04 | 弱网与极端环境治理 ★ | 弱网 / 低端机 / 高温降频是真实的常态 | **新增** |

### 为什么新增"04.弱网与极端环境治理"

- 实验室环境的性能数据 ≠ 真实用户环境。
- 弱网（地铁 / 电梯）、低端机（千元机 / 老机型）、高温降频是性能"反例"的主要来源。
- 需要专门的策略：弱网检测、降级方案、低端机分发策略、温度感知调度等。
- 当前文档完全没有覆盖这部分，是体系最大缺口之一。
