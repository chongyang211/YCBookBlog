### 00 开篇导论

**0.1 一句话定位**

**动画与交互响应是"用户感受性能的最强放大镜"**——指标好不代表体验好，但动画卡、交互延迟一定会被用户立刻感知。一次 100ms 的输入响应延迟，在用户眼里等同于"App 卡死"。

**0.2 为什么独立成章**

很多团队的 FPS 监控显示一切正常，但用户依然抱怨"卡"——问题就出在动画与交互这两个"高敏感场景"。它们是流水线的特殊形态，必须用专门的视角和指标来对待。

**0.3 与其他章的关系**

- 上承卷三·01 [渲染管线](01.渲染管线与原理.md)：动画本质是连续帧渲染
- 横联卷三·03 [卡顿捕获](03.卡顿捕获与归因.md)：交互延迟是卡顿的特殊场景
- 下承列表性能、UI 优化等业务专项

**0.4 8 个反直觉问题**

1. 60fps 不卡，为什么用户还说"动画不顺滑"？
2. 输入响应 < 100ms 为什么还是被嫌弃慢？
3. 为什么"先 setState 再 layout"和"先 layout 再 setState"性能差 5 倍？
4. CSS transform 比 left/top 快，但快在哪？
5. 为什么 60fps 的动画在 120Hz 屏上反而看着不流畅？
6. requestAnimationFrame 的回调时机为什么是"渲染前"而不是"渲染后"？
7. 触控反馈的"100ms 黄金线"从哪来？
8. 为什么动画使用 GPU 不是越多越好？

### 02 问题与认知

**2.1 用户感知的物理基线**

| 时间 | 用户感受 |
|---|---|
| < 16ms | 即时（一帧） |
| 16-100ms | 流畅 |
| 100-300ms | 可感知延迟 |
| 300ms-1s | 明显卡顿 |
| > 1s | 中断感（Doherty 阈值） |

动画的核心目标：**所有交互反馈 ≤ 100ms，所有动画连续帧 ≤ 16.67ms（60fps）**。

**2.2 动画卡顿的三种形态**

- **抖动**：FPS 平均够，但帧间方差大（一会 60、一会 30）→ 比纯 30fps 更刺眼
- **撕裂**：CPU 提交速度跟不上 GPU 合成 → 半屏新帧半屏旧帧
- **延迟**：动画总时长超过预期 → 比如 300ms 的过场实际跑了 600ms

**2.3 三个共识**

- **平均 FPS 没用**：用户感受的是"最差那帧"，监控必须看 P99
- **120Hz 不是简单 2 倍 60fps**：每帧时间预算 8.3ms，对 CPU/GPU 是降维打击
- **GPU 不是免费的**：开太多硬件加速层反而触发"层爆炸"，性能更差

### 03 度量与采集

**3.1 三类采集方案的本质**

**方案 A·帧绘制时间序列**

- **核心原理**：记录每一帧的提交、合成、上屏时间戳
- **工作机理**：Choreographer.FrameCallback / requestAnimationFrame / CADisplayLink
- **物理本质**：直接利用平台帧回调机制
- **局限根源**：只能看到"提交"时间，看不到 GPU 端真实合成耗时
- **适用场景**：常态化 FPS 监控

**方案 B·输入到首帧延迟**

- **核心原理**：记录用户事件触发到屏幕首次出现反馈的时间
- **工作机理**：MotionEvent → ViewRootImpl → Choreographer 链路打点
- **物理本质**：完整覆盖"输入 → 计算 → 渲染 → 上屏"全链路
- **局限根源**：需要平台底层 hook，工程难度较大
- **适用场景**：交互响应度量、关键场景 SLO

**方案 C·人眼级视频对比**

- **核心原理**：用 240fps 高速摄像录制屏幕，逐帧分析
- **工作机理**：人工或 OpenCV 自动比对帧差
- **物理本质**：以"人力 + 设备成本"换取"地面真值"
- **局限根源**：不可线上化、不可常态化；只用于关键评估
- **适用场景**：动画体验评测、双盲对比

**3.2 三方案差异矩阵**

| 维度 | A 帧时序 | B 输入延迟 | C 视频对比 |
|---|---|---|---|
| 粒度 | 单帧 | 全链路 | 物理像素 |
| 覆盖度 | 高 | 中 | 局部 |
| 工程成本 | 低 | 中 | 高 |
| 上线可用 | 是 | 是 | 否 |
| 真值精度 | 中 | 高 | 最高 |

**3.3 跨平台同构与差异**

| 平台 | 帧回调 | 输入回调 | 高速摄像 |
|---|---|---|---|
| Android | Choreographer | MotionEvent | 通用 |
| iOS | CADisplayLink | UIEvent | 通用 |
| 前端 | rAF | PointerEvent | 通用 |
| 小程序 | 平台限制 | 受限 | 通用 |

**同构本质**：所有平台都暴露"帧回调"和"输入事件"两套 API，只是名字不同。优化方法（合成器加速、避免主线程阻塞、layer 化）跨平台通用。

### 04 归因与定位

**4.1 动画卡顿二分决策树**

```
动画不顺滑
├─ 平均 FPS 达标吗？
│  ├─ 否 → 整体性能问题（参考渲染篇 §04）
│  └─ 是 → 帧间方差大（抖动问题）
│     ├─ 主线程被偶发任务打断（GC、IO、Layout）
│     └─ GPU 提交不稳定（层频繁 invalidate）
└─ 是动画本身慢还是输入响应慢？
   ├─ 动画 → 检查 transform/opacity 是否走合成器
   └─ 输入 → 检查事件分发链路、首帧绘制
```

**4.2 交互延迟分段归因**

任何用户操作的延迟都可拆为 4 段：

```
T_input → T_dispatch → T_layout → T_compose → T_display
   ↑          ↑           ↑          ↑           ↑
  事件      分发到目标    布局重算    GPU 合成    屏幕显示
```

每一段都可独立度量：

- T_input → T_dispatch：事件队列拥堵（主线程被阻塞）
- T_dispatch → T_layout：业务逻辑过重（setState 链/同步网络）
- T_layout → T_compose：layout/paint 抖动（强制同步布局、过度重绘）
- T_compose → T_display：GPU 合成压力（层数太多、图层尺寸大）

**4.3 强制同步布局检测**

JS 引擎/Android View 层都有"强制同步布局"陷阱：写完属性立刻读属性。**检测方法**：Chrome DevTools Performance 里的紫色块、Android Systrace 里 `measure/layout` 高频出现。**修法**：分离读写，批量化。

### 05 求证实验

**5.1 实验一：transform vs left/top**

**问题**：CSS 动画用 transform 比 left/top 快多少？

- **第 1 步·假设**：transform 走 GPU 合成器，比 left/top 快 5 倍
- **第 2 步·设计**：100 个元素同时做 200px 位移动画，分别用 left/top 与 transform: translate
- **第 3 步·控制变量**：同浏览器、同设备、关闭其他动画
- **第 4 步·指标**：FPS 平均/P99、主线程 CPU 占用、GPU 内存
- **第 5 步·执行**：Chrome Performance 录制
- **第 6 步·收集**：left/top 平均 32fps、主线程 95%；transform 稳定 60fps、主线程 12%
- **第 7 步·分析**：left/top 触发 layout（影响兄弟节点） + paint（重新光栅化）；transform 仅触发 composite（直接 GPU 矩阵变换）
- **第 8 步·结论**：所有位移/缩放/旋转动画一律用 transform，opacity 同理
- **第 9 步·扩展**：will-change: transform 提前晋升合成层，但开太多会爆显存

**5.2 实验二：rAF 时机决定卡顿率**

**问题**：用 setTimeout(16) 模拟 60fps，和 rAF 比有什么差别？

- **第 1 步·假设**：rAF 卡顿率明显低于 setTimeout
- **第 2 步·设计**：同一动画分别用 setTimeout(16) 与 rAF 驱动 30 秒
- **第 3 步·控制变量**：同设备、同负载
- **第 4 步·指标**：丢帧率、连续两帧时差方差
- **第 5 步·执行**：浏览器实测
- **第 6 步·收集**：setTimeout 丢帧率 18%（与 vsync 不对齐导致漂移）；rAF 丢帧率 2%
- **第 7 步·分析**：setTimeout 是不可靠定时器（timer coalescing），实际间隔 15-20ms 抖动；rAF 严格对齐 vsync
- **第 8 步·结论**：所有动画必须用 rAF 驱动；定时器只用于业务逻辑
- **第 9 步·扩展**：iOS 上 CADisplayLink 是同等机制；Android Choreographer.postFrameCallback

**5.3 实验三：100ms 黄金线**

**问题**：输入响应延迟从 50ms 增加到 200ms，用户体验下降多少？

- **第 1 步·假设**：< 100ms 用户无感，> 100ms 急剧下降
- **第 2 步·设计**：构造按钮点击场景，人为加入 50/100/150/200ms 延迟，用户主观打分（1-5）
- **第 3 步·控制变量**：双盲、随机顺序、20 个用户
- **第 4 步·指标**：主观分、复购意愿、感知到的"卡"次数
- **第 5 步·执行**：标准可用性测试
- **第 6 步·收集**：50ms→4.7、100ms→4.3、150ms→3.2、200ms→2.1
- **第 7 步·分析**：100-150ms 是用户感知断崖；这一区间每 10ms 都有显著差异
- **第 8 步·结论**：输入响应 SLO 必须 ≤ 100ms（P95），不要设 200ms
- **第 9 步·扩展**：Doherty 阈值（< 400ms）是"思维不中断"，但只是底线，不是优秀

### 06 治理与原则

**6.1 动画三原则**

- **能合成器就合成器**：transform、opacity、filter 是首选
- **能不重排就不重排**：避免触发 layout
- **能批量就批量**：rAF 内合并所有 DOM 写

**6.2 交互三原则**

- **首帧 100ms 内出现反馈**：哪怕只是按钮按下态
- **长任务必须分片**：> 50ms 的任务必须 yield 给主线程
- **关键路径优先**：用户当前看到/操作的内容优先级最高

**6.3 反模式清单**

- ❌ 一次 setState 触发整页重排
- ❌ 用 setTimeout 做动画
- ❌ 用 left/top 做位移
- ❌ 输入框 onChange 直接触发网络请求（无 debounce）
- ❌ 滚动监听里做布局计算
- ❌ will-change 全局开（层爆炸）

### 07 防劣化体系

**7.1 三道防线**

- **第一道·开发期**：Chrome DevTools / Android GPU Profiler 强制使用
- **第二道·CI**：关键动画自动跑分，FPS P99 < 55 阻断
- **第三道·线上**：交互延迟 P95 实时监控，超阈值告警

**7.2 SLO 示例**

- 动画 FPS P95 ≥ 55（60Hz 屏）/ ≥ 110（120Hz 屏）
- 输入响应延迟 P95 ≤ 100ms
- 页面切换动画完成时间偏差 ≤ 10%
- 强制同步布局每帧 ≤ 0 次

### 08 案例与教训

**8.1 跨端同构案例·列表滚动卡顿**

某 App 列表页滑动卡顿，FPS 降到 25。排查发现 onScroll 回调里做了 measureText 计算（强制同步布局）。**修法**：把测量移到滚动结束后；中间状态用预估值。**教训**：滚动监听里只做读、不做写、不做计算。

**8.2 平台特异案例·iOS 转场动画掉帧**

某 iOS App 自定义转场动画在低端机掉帧严重。Instruments 看到 Core Animation 提交栈每次都触发 layoutIfNeeded。**修法**：动画前预先调用 layoutIfNeeded 强制完成布局，再启动 CABasicAnimation。**教训**：UIKit 的隐式布局会污染动画路径，动画前必须确保布局已稳定。

### 09 原理深挖

**9.1 为什么 transform 走合成器**

合成器（compositor）独立于主线程运行，掌握 GPU 上的 layer 纹理。transform 只改变 layer 的变换矩阵，不需要重新光栅化纹理。**结果**：主线程完全不参与，丝滑 60fps 是物理决定的。

**9.2 vsync 对齐的本质**

屏幕刷新是固定频率（60Hz/120Hz），如果 CPU 提交不对齐 vsync 边界，就会出现"提交了但显示不到下次刷新"的浪费帧。rAF/Choreographer 把回调严格调度到 vsync 前几毫秒，给 CPU 留出准备时间。

**9.3 120Hz 的工程挑战**

120Hz 把每帧预算从 16.67ms 砍到 8.3ms。任何超过 8ms 的任务都会掉帧。**应对**：分片更细（5ms 一片）、避免不必要的合成层、优先级调度（react-scheduler 类似）。

### 10 总结与扩展

**10.1 一图概括**

```
动画与交互
    ├─ 动画 → 合成器优先 + rAF + 不重排
    ├─ 输入 → 100ms 黄金线 + 长任务分片
    ├─ 监控 → P95/P99 + 输入延迟全链路
    └─ 防御 → CI 自动化 + 用户主观评测
```

**10.2 三个外延**

- **动效设计语言**：iOS Spring/Material Motion 等系统级动画规范，工程实现要遵守
- **可访问性（a11y）**：prefers-reduced-motion 等用户偏好必须尊重
- **AI 辅助评测**：自动化分析视频帧，未来可替代人工感知打分

**10.3 给团队的建议**

- 第 1 周：审计所有动画，把 left/top 改成 transform
- 第 2 周：上线输入响应延迟监控，SLO 设 100ms
- 第 3 周：滚动 / 列表场景做强制同步布局清零
- 第 4 周：120Hz 设备适配，关键动画做专项调优

动画与交互是"性能给用户的最直接答卷"——指标都达标了，但用户还说卡，那一定是这一章没做好。
