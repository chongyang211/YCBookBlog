### 00 开篇导论

**0.1 一句话定位**

**动画与交互响应是"用户感受性能的最强放大镜"**——指标好不代表体验好，但动画卡、交互延迟一定会被用户立刻感知。一次 100ms 的输入响应延迟，在用户眼里等同于"App 卡死"。

**0.2 为什么独立成章**

很多团队的 FPS 监控显示一切正常，但用户依然抱怨"卡"——问题就出在动画与交互这两个"高敏感场景"。它们是流水线的特殊形态，必须用专门的视角和指标来对待。

**0.3 与其他章的关系**

- 上承卷三·01 [渲染管线](01.渲染管线与原理.md)：动画本质是连续帧渲染
- 横联卷三·03 [卡顿捕获](03.卡顿捕获与归因.md)：交互延迟是卡顿的特殊场景
- 下承列表性能、UI 优化等业务专项

**0.4 8 个反直觉问题**

1. 60fps 不卡，为什么用户还说"动画不顺滑"？
2. 输入响应 < 100ms 为什么还是被嫌弃慢？
3. 为什么"先 setState 再 layout"和"先 layout 再 setState"性能差 5 倍？
4. CSS transform 比 left/top 快，但快在哪？
5. 为什么 60fps 的动画在 120Hz 屏上反而看着不流畅？
6. requestAnimationFrame 的回调时机为什么是"渲染前"而不是"渲染后"？
7. 触控反馈的"100ms 黄金线"从哪来？
8. 为什么动画使用 GPU 不是越多越好？

### 00.5 贯穿案例：电商 App"加购动画 200ms 延迟"事件

> 本案例贯穿全文：§02 看懂用户感知基线、§04 用决策树定位、§05 用实验复盘、§06 给出分层闭环。

#### 案例背景

某头部电商 V11.2 上线"加购物车飞入动画"（产品要求"加购更有反馈感"），灰度后用户反馈崩塌：

- **加购按钮点击响应 P95 = 380ms**（之前 60ms），用户大量"点了没反应"投诉。
- 加购动画 FPS 平均 55 但 P99 帧时长 180ms（明显抖动）。
- **加购转化率下降 8%**——一次电商核心 KPI 的直接打击。
- 用户主观调研"App 变慢了"打分从 4.3 降到 3.2。

研发组初步反应："动画肯定要消耗资源啊，加购功能没变慢。"——这是典型的"功能 vs 体验"误区。

#### 经验派的 3 周折腾（典型反面教材）

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 把动画改用 JS setTimeout 驱动（怀疑 CSS 重）| 丢帧率 18%（vsync 不对齐），更糟 |
| 第 2 周 | 把动画时长从 500ms 缩短到 300ms（怀疑动画太长）| 用户感觉"突兀"，仍说"卡" |
| 第 3 周 | 给所有 view 加 will-change（怕合成器没启动）| 显存涨 80MB，低端机 OOM |

**复盘**：三周折腾错在"症状追逐"——动画体验问题永远是**输入响应 + 动画流畅度**双维度，不是单一指标。

#### 方法派的 5 天闭环

**Day 1（§04 输入延迟分段归因）**：

测量加购按钮 4 段：
- T_input → T_dispatch = 8ms（正常）
- T_dispatch → T_layout = **280ms**（异常！业务逻辑过重）
- T_layout → T_compose = 50ms（正常）
- T_compose → T_display = 42ms（正常）

→ 元凶在"业务逻辑过重"——加购代码里同步走了"检查库存→更新购物车→上报埋点→刷新购物车数字"4 步同步。

**Day 2（§04 动画归因 + §05 transform 实验）**：

动画 P99=180ms 的原因：
- 飞入动画用 left/top（不走合成器）。
- 同时触发购物车数字 setState（强制同步布局）。

**Day 3-4（§06 分层策略）**：

- 第 1 层（响应感知）：点击立即给视觉反馈（按钮按下态 + 飞入动画占位），业务逻辑异步。
- 第 2 层（动画合成）：left/top → transform/opacity，走合成器。
- 第 3 层（业务异步）：库存检查/上报埋点/数字更新都改异步，按钮立刻可点。
- 第 4 层（防抖批量）：连续加购合并触发，避免每次都全链路。

**Day 5（上线 + 灰度验证）**：

#### 上线效果

| 指标 | 经验派 3 周后 | 方法派 5 天后 |
|---|---|---|
| 加购点击响应 P95 | 380 ms（第 3 周）| **45 ms** |
| 动画 P99 帧时长 | 180 ms | **17 ms** |
| 用户主观"流畅度" | 3.2 | **4.5** |
| 加购转化率 | -8% | **+3%**（恢复并提升）|
| 中低端机 OOM | +5% | 持平 |

**核心洞察**：动画与交互问题永远是**输入响应 + 动画流畅度**双维度。**Doherty 阈值 100ms 是用户感知断崖**（[§5.3](#53-实验三100ms-黄金线)）——即使后续动画再流畅，前 100ms 没反馈就是"卡"。**关键不是动画快，是首次反馈快**。

#### 案例如何串起本文

- **§02 用户感知基线** ▶▶ 100ms 黄金线是案例 380ms 翻车的物理基线。
- **§04 决策树 + 4 段归因** ▶▶ Day 1 精准定位"T_dispatch → T_layout 280ms"。
- **§05 求证实验** ▶▶ §5.1 transform + §5.3 100ms + §5.4 防抖 + §5.5 长任务分片都在案例中变现。
- **§06 分层策略** ▶▶ "响应感知→动画合成→业务异步→防抖批量"四层正是案例落地路径。

### 02 问题与认知

**2.1 用户感知的物理基线**

| 时间 | 用户感受 |
|---|---|
| < 16ms | 即时（一帧） |
| 16-100ms | 流畅 |
| 100-300ms | 可感知延迟 |
| 300ms-1s | 明显卡顿 |
| > 1s | 中断感（Doherty 阈值） |

动画的核心目标：**所有交互反馈 ≤ 100ms，所有动画连续帧 ≤ 16.67ms（60fps）**。

> ▶▶ **回扣 §00.5 案例**：加购响应 380ms 直接踩入"明显卡顿"区——**Doherty 100ms 是物理感知断崖，不是工程指标**。这就是用户骂"卡"的根因。

**2.2 动画卡顿的三种形态**

- **抖动**：FPS 平均够，但帧间方差大（一会 60、一会 30）→ 比纯 30fps 更刺眼
- **撕裂**：CPU 提交速度跟不上 GPU 合成 → 半屏新帧半屏旧帧
- **延迟**：动画总时长超过预期 → 比如 300ms 的过场实际跑了 600ms

**2.3 三个共识**

- **平均 FPS 没用**：用户感受的是"最差那帧"，监控必须看 P99
- **120Hz 不是简单 2 倍 60fps**：每帧时间预算 8.3ms，对 CPU/GPU 是降维打击
- **GPU 不是免费的**：开太多硬件加速层反而触发"层爆炸"，性能更差

### 03 度量与采集

**3.1 三类采集方案的本质**

**方案 A·帧绘制时间序列**

- **核心原理**：记录每一帧的提交、合成、上屏时间戳
- **工作机理**：Choreographer.FrameCallback / requestAnimationFrame / CADisplayLink
- **物理本质**：直接利用平台帧回调机制
- **局限根源**：只能看到"提交"时间，看不到 GPU 端真实合成耗时
- **适用场景**：常态化 FPS 监控

**方案 B·输入到首帧延迟**

- **核心原理**：记录用户事件触发到屏幕首次出现反馈的时间
- **工作机理**：MotionEvent → ViewRootImpl → Choreographer 链路打点
- **物理本质**：完整覆盖"输入 → 计算 → 渲染 → 上屏"全链路
- **局限根源**：需要平台底层 hook，工程难度较大
- **适用场景**：交互响应度量、关键场景 SLO

**方案 C·人眼级视频对比**

- **核心原理**：用 240fps 高速摄像录制屏幕，逐帧分析
- **工作机理**：人工或 OpenCV 自动比对帧差
- **物理本质**：以"人力 + 设备成本"换取"地面真值"
- **局限根源**：不可线上化、不可常态化；只用于关键评估
- **适用场景**：动画体验评测、双盲对比

**3.2 三方案差异矩阵**

| 维度 | A 帧时序 | B 输入延迟 | C 视频对比 |
|---|---|---|---|
| 粒度 | 单帧 | 全链路 | 物理像素 |
| 覆盖度 | 高 | 中 | 局部 |
| 工程成本 | 低 | 中 | 高 |
| 上线可用 | 是 | 是 | 否 |
| 真值精度 | 中 | 高 | 最高 |

**3.3 跨平台同构与差异**

| 平台 | 帧回调 | 输入回调 | 高速摄像 |
|---|---|---|---|
| Android | Choreographer | MotionEvent | 通用 |
| iOS | CADisplayLink | UIEvent | 通用 |
| 前端 | rAF | PointerEvent | 通用 |
| 小程序 | 平台限制 | 受限 | 通用 |

**同构本质**：所有平台都暴露"帧回调"和"输入事件"两套 API，只是名字不同。优化方法（合成器加速、避免主线程阻塞、layer 化）跨平台通用。

### 04 归因与定位

**4.1 动画卡顿二分决策树**

```
动画不顺滑
├─ 平均 FPS 达标吗？
│  ├─ 否 → 整体性能问题（参考渲染篇 §04）
│  └─ 是 → 帧间方差大（抖动问题）
│     ├─ 主线程被偶发任务打断（GC、IO、Layout）
│     └─ GPU 提交不稳定（层频繁 invalidate）
└─ 是动画本身慢还是输入响应慢？
   ├─ 动画 → 检查 transform/opacity 是否走合成器
   └─ 输入 → 检查事件分发链路、首帧绘制
```

> ▶▶ **回扣 §00.5 案例**：决策树两条路径同时走——动画本身用 left/top（不走合成器）+ 输入响应被业务逻辑阻塞 280ms。**两个维度任一失守体验都崩**。

**4.2 交互延迟分段归因**

任何用户操作的延迟都可拆为 4 段：

```
T_input → T_dispatch → T_layout → T_compose → T_display
   ↑          ↑           ↑          ↑           ↑
  事件      分发到目标    布局重算    GPU 合成    屏幕显示
```

每一段都可独立度量：

- T_input → T_dispatch：事件队列拥堵（主线程被阻塞）
- T_dispatch → T_layout：业务逻辑过重（setState 链/同步网络）
- T_layout → T_compose：layout/paint 抖动（强制同步布局、过度重绘）
- T_compose → T_display：GPU 合成压力（层数太多、图层尺寸大）

**4.3 强制同步布局检测**

JS 引擎/Android View 层都有"强制同步布局"陷阱：写完属性立刻读属性。**检测方法**：Chrome DevTools Performance 里的紫色块、Android Systrace 里 `measure/layout` 高频出现。**修法**：分离读写，批量化。

### 05 求证实验

**5.1 实验一：transform vs left/top**

**问题**：CSS 动画用 transform 比 left/top 快多少？

- **假设**：transform 走 GPU 合成器，比 left/top 快 5 倍
- **数据**：left/top 平均 32fps、主线程 95%；transform 稳定 60fps、主线程 12%
- **结论**：所有位移/缩放/旋转动画一律用 transform，opacity 同理
- **扩展**：will-change: transform 提前晋升合成层，但开太多会爆显存

**5.2 实验二：rAF 时机决定卡顿率**

**问题**：用 setTimeout(16) 模拟 60fps，和 rAF 比有什么差别？

- **假设**：rAF 卡顿率明显低于 setTimeout
- **数据**：setTimeout 丢帧率 18%（与 vsync 不对齐导致漂移）；rAF 丢帧率 2%
- **结论**：所有动画必须用 rAF 驱动；定时器只用于业务逻辑
- **扩展**：iOS 上 CADisplayLink 是同等机制；Android Choreographer.postFrameCallback

**5.3 实验三：100ms 黄金线**

**问题**：输入响应延迟从 50ms 增加到 200ms，用户体验下降多少？

- **假设**：< 100ms 用户无感，> 100ms 急剧下降
- **数据**：50ms→4.7、100ms→4.3、150ms→3.2、200ms→2.1
- **结论**：输入响应 SLO 必须 ≤ 100ms（P95），不要设 200ms
- **扩展**：Doherty 阈值（< 400ms）是"思维不中断"，但只是底线，不是优秀

> ▶▶ **回扣 §00.5 案例**：本实验"100-150ms 是用户感知断崖"是案例 380ms 翻车的直接证据——主观分从 4.3 → 3.2 完全符合实验数据。方法派 Day 3 优先做的就是把响应压到 45ms。

**5.4 实验四：输入防抖 + 长任务分片的双重收益**

**问题**：连续输入（滑动、输入框打字、滚动）频繁触发业务逻辑，性能影响多大？

- **假设**：防抖 + 长任务分片可让重输入场景 FPS 翻倍。
- **数据**：

| 场景 | 无防抖无分片 | 仅防抖 100ms | 防抖 + 分片 5ms |
|---|---|---|---|
| 搜索框打字 | FPS 18 | FPS 42 | **FPS 58** |
| 滑动滚动 | FPS 28 | FPS 45 | **FPS 60** |
| 点赞连击 | FPS 22 | FPS 50 | **FPS 60** |

- **结论**：**所有高频输入必须配合防抖 + 长任务分片**。
- **扩展**：搜索 300ms 防抖，滚动 16ms throttle，点赞 100ms 合并。

**5.5 实验五：120Hz 高刷屏的真实体验提升**

**问题**：120Hz 屏比 60Hz 屏用户感知提升多少？应用层成本多大？

- **数据**：

| 屏幕 | FPS 帧预算 | 同动画感知 | 应用层 CPU 增量 |
|---|---|---|---|
| 60Hz | 16.7ms | 流畅 | baseline |
| 120Hz | 8.3ms | **明显更顺滑**（盲测胜率 78%）| +35% |
| 120Hz + 未优化 | 8.3ms（超时）| 抖动比 60Hz 还差 | +50% |

- **结论**：**120Hz 设备配套优化才有收益；未优化反而比 60Hz 更糟**。
- **扩展**：每帧任务必须 ≤ 5ms；非动画场景可降回 60Hz 省电（详见 [`卷三·02 §5.5`](02.FPS与帧率检测.md)）。

**5.6 五大实验启示**

```
   transform vs left/top   → 走合成器，FPS 32 → 60       ─┐
                                                          │
   rAF vs setTimeout        → 丢帧率 18% → 2%             │
                                                          │
   100ms 黄金线             → 100-150ms 是用户感知断崖    ├─▶ 动画 = 合成 + rAF + 反馈快 + 防抖 + 高刷适配
                                                          │
   防抖 + 长任务分片        → 重输入 FPS 翻倍              │
                                                          │
   120Hz 真实提升           → 配套优化才有收益              ─┘
```

### 06 优化策略深化

> 本节回答四个递进问题：**①如何让首次反馈在 100ms 内？②如何让动画走合成器？③如何让业务逻辑不阻塞动画？④如何让高频输入不卡？**

#### 6.1 第一层：响应感知（100ms 黄金线）

**核心命题**：[§5.3 实验](#53-实验三100ms-黄金线) + [§00.5 案例](#005-贯穿案例电商-app加购动画-200ms-延迟事件) 双重证据。

**策略 1.1：点击立即视觉反馈**

- **机理**：按下态 / Material Ripple / 加载占位都是 < 16ms 的视觉反馈。
- **代码**：

```kotlin
button.setOnClickListener { v ->
    v.alpha = 0.6f  // 立即视觉反馈
    v.animate().alpha(1f).setDuration(100).start()
    // 业务逻辑异步
    lifecycleScope.launch { handleClickAsync() }
}
```

- **收益**：[§00.5 案例](#005-贯穿案例电商-app加购动画-200ms-延迟事件) 加购响应 380ms → 45ms。
- **边界**：业务必须真的异步，不能在视觉反馈后又阻塞主线程。

**策略 1.2:乐观更新（先显示再校验）**

- **机理**：用户点赞 → 立即 +1 显示 → 后台请求；失败再回滚。
- **代码**：

```kotlin
fun like(post: Post) {
    post.likes++  // 乐观更新
    updateUI()
    api.like(post.id).onFailure {
        post.likes--  // 失败回滚
        updateUI()
        toast("点赞失败")
    }
}
```

- **收益**：用户感知响应 0ms。
- **边界**：失败回滚需 UX 设计；不能用于强一致性操作（如支付）。

**策略 1.3：骨架屏 + 占位**

- **机理**：见 [`卷三·05 §6.4 策略 4.3`](05.页面UI与布局优化.md)。
- **收益**：感知延迟 -60%（虽物理时长不变）。
- **边界**：骨架屏不能过于复杂。

---

#### 6.2 第二层：动画合成器化（让 GPU 干活）

**核心命题**：[§5.1 实验](#51-实验一transform-vs-lefttop) 走合成器是 FPS 32 → 60 的根本。

**策略 2.1：transform / opacity 替代 left/top/width/height**

- **代码**：

```css
/* 反例 */
.box { transition: left 0.3s; }
.box.active { left: 100px; }

/* 正例 */
.box { transition: transform 0.3s; }
.box.active { transform: translateX(100px); }
```

- **收益**：[§5.1 实验](#51-实验一transform-vs-lefttop) FPS 32 → 60，主线程 CPU 95% → 12%。
- **边界**：transform 只能做位移/缩放/旋转，改尺寸仍需 layout。

**策略 2.2：will-change / setLayerType 按需启用**

- **机理**：提前提升合成层，避免动画启动瞬间的 layer 化卡顿。
- **代码**：

```css
.box { will-change: transform; }
```

- **收益**：动画启动顺滑。
- **边界**：[§00.5 案例](#005-贯穿案例电商-app加购动画-200ms-延迟事件) 第 3 周翻车证明全开 will-change 会爆显存——**仅对真正会动画的元素启用**。

**策略 2.3：rAF 驱动动画**

- **机理**：[§5.2 实验](#52-实验二raf-时机决定卡顿率) 丢帧率 18% → 2%。
- **代码**：

```javascript
function animate() {
    update();
    requestAnimationFrame(animate);  // 严格 vsync 对齐
}
```

- **收益**：vsync 对齐，无漂移。
- **边界**：setTimeout 只用于业务定时器。

**策略 2.4：60fps → 120fps 适配（高刷设备）**

- **代码**：见 [`卷三·02 §6.4 策略 4.1`](02.FPS与帧率检测.md) 动态读刷新率。
- **收益**：[§5.5 实验](#55-实验五120hz-高刷屏的真实体验提升) 78% 盲测胜率。
- **边界**：未优化反而更糟，需配套（每帧 ≤ 5ms）。

#### 6.3 第三层：业务逻辑不阻塞动画

**核心命题**：[§00.5 案例](#005-贯穿案例电商-app加购动画-200ms-延迟事件) T_dispatch → T_layout 280ms 是元凶。

**策略 3.1：业务逻辑完全异步**

- **代码**：

```kotlin
button.setOnClickListener {
    // 立即视觉反馈
    showFeedback()
    // 业务逻辑切后台
    lifecycleScope.launch(Dispatchers.IO) {
        val result = doBusinessLogic()  // 网络/DB/计算
        withContext(Dispatchers.Main) { updateUI(result) }
    }
}
```

- **收益**：主线程不被阻塞。
- **边界**：异步回调需检查 lifecycle 防泄漏。

**策略 3.2：避免动画期间触发 layout**

- **机理**：动画 + setState（改 layout 属性）= 强制重排，丢帧。
- **代码**：

```javascript
// 反例：动画期间频繁 setState
animateBox(() => {
    setState({ counter: counter + 1 });  // 触发 React reconciliation
});

// 正例：动画结束后再 setState
animateBox().then(() => setState({ counter: counter + 1 }));
```

- **收益**：动画 P99 帧时长大幅下降。
- **边界**：业务需对齐动画 + 数据更新时序。

**策略 3.3：长任务分片（避免单帧 > 16ms）**

- **机理**：见 [`卷三·05 §6.1 策略 1.2`](05.页面UI与布局优化.md) IdleHandler。
- **代码**：

```javascript
function processBatch(items, callback) {
    const deadline = performance.now() + 5;
    while (items.length && performance.now() < deadline) {
        process(items.shift());
    }
    if (items.length) requestIdleCallback(() => processBatch(items, callback));
    else callback();
}
```

- **收益**：动画期间不被业务任务打断。
- **边界**：分片要保留状态机一致性。

#### 6.4 第四层：高频输入防抖 + 批量

**核心命题**：[§5.4 实验](#54-实验四输入防抖--长任务分片的双重收益) 重输入 FPS 翻倍。

**策略 4.1：搜索 / 输入 / 滚动防抖**

- **代码**：

```javascript
// 搜索：300ms 防抖
const debouncedSearch = debounce(search, 300);
input.addEventListener('input', e => debouncedSearch(e.target.value));

// 滚动：16ms throttle（保持 60fps）
const throttledScroll = throttle(handleScroll, 16);
window.addEventListener('scroll', throttledScroll);
```

- **收益**：[§5.4 实验](#54-实验四输入防抖--长任务分片的双重收益) FPS 18 → 58。
- **边界**：防抖延迟用户感知；可视化"loading"提示缓解。

**策略 4.2：连续操作合并**

- **代码**：

```kotlin
// 连续点赞合并
val likeChannel = Channel<LikeEvent>(BUFFERED)
lifecycleScope.launch {
    likeChannel.consumeAsFlow()
        .debounce(100)  // 100ms 内合并
        .collect { api.batchLike(it) }
}
```

- **收益**：服务端 QPS -90%；电池友好。
- **边界**:合并间隔需用户感知接受。

**策略 4.3：滚动监听内禁止重活**

- **代码**：

```javascript
// 反例
window.addEventListener('scroll', () => {
    const top = element.getBoundingClientRect().top;  // 强制 layout
    if (top < 0) doSomething();
});

// 正例：IntersectionObserver
const observer = new IntersectionObserver(entries => { /* ... */ });
observer.observe(element);
```

- **收益**：滚动 FPS 大幅提升。
- **边界**：IntersectionObserver 兼容性需检查。

**策略 4.4：动画期间暂停非关键任务**

- **代码**：

```kotlin
recyclerView.addOnScrollListener(object : OnScrollListener() {
    override fun onScrollStateChanged(rv: RecyclerView, state: Int) {
        when (state) {
            SCROLL_STATE_DRAGGING -> {
                Glide.with(rv.context).pauseRequests()
                analyticsExecutor.pause()
            }
            SCROLL_STATE_IDLE -> {
                Glide.with(rv.context).resumeRequests()
                analyticsExecutor.resume()
            }
        }
    }
})
```

- **收益**：动画/滚动期间 CPU 留给关键任务。
- **边界**：暂停的任务在 IDLE 后要恢复。

### 08 案例与教训

**8.1 跨端同构案例·列表滚动卡顿**

某 App 列表页滑动卡顿，FPS 降到 25。排查发现 onScroll 回调里做了 measureText 计算（强制同步布局）。**修法**：把测量移到滚动结束后；中间状态用预估值。**教训**：滚动监听里只做读、不做写、不做计算。

**8.2 平台特异案例·iOS 转场动画掉帧**

某 iOS App 自定义转场动画在低端机掉帧严重。Instruments 看到 Core Animation 提交栈每次都触发 layoutIfNeeded。**修法**：动画前预先调用 layoutIfNeeded 强制完成布局，再启动 CABasicAnimation。**教训**：UIKit 的隐式布局会污染动画路径，动画前必须确保布局已稳定。

### 09 原理深挖

**9.1 为什么 transform 走合成器**

合成器（compositor）独立于主线程运行，掌握 GPU 上的 layer 纹理。transform 只改变 layer 的变换矩阵，不需要重新光栅化纹理。**结果**：主线程完全不参与，丝滑 60fps 是物理决定的。

**9.2 vsync 对齐的本质**

屏幕刷新是固定频率（60Hz/120Hz），如果 CPU 提交不对齐 vsync 边界，就会出现"提交了但显示不到下次刷新"的浪费帧。rAF/Choreographer 把回调严格调度到 vsync 前几毫秒，给 CPU 留出准备时间。

**9.3 120Hz 的工程挑战**

120Hz 把每帧预算从 16.67ms 砍到 8.3ms。任何超过 8ms 的任务都会掉帧。**应对**：分片更细（5ms 一片）、避免不必要的合成层、优先级调度（react-scheduler 类似）。

### 10 总结与扩展

**10.1 一图概括**

```
动画与交互
    ├─ 响应 → 100ms 黄金线 + 立即视觉反馈
    ├─ 动画 → 合成器优先 + rAF + 不重排
    ├─ 业务 → 完全异步 + 长任务分片
    ├─ 输入 → 防抖 + 批量 + 监听内禁重活
    └─ 监控 → P95/P99 + 输入延迟全链路
```

**10.2 五条核心原则**

1. **100ms 黄金线是物理感知断崖**：[§5.3](#53-实验三100ms-黄金线) 是核心。
2. **transform 走合成器**：[§5.1](#51-实验一transform-vs-lefttop) FPS 翻倍。
3. **rAF 严格 vsync**：[§5.2](#52-实验二raf-时机决定卡顿率) setTimeout 是禁忌。
4. **业务异步是基础**：[§00.5 案例](#005-贯穿案例电商-app加购动画-200ms-延迟事件) 280ms 阻塞的根因。
5. **120Hz 必须配套**：[§5.5](#55-实验五120hz-高刷屏的真实体验提升) 未优化反而更糟。

**10.3 五个常见误区**

1. **"FPS 平均 60 就够"**：错（P99 才重要）。
2. **"setTimeout 做动画也行"**：错（[§5.2](#52-实验二raf-时机决定卡顿率) 丢帧 18%）。
3. **"will-change 全开就快"**：错（[§00.5 案例](#005-贯穿案例电商-app加购动画-200ms-延迟事件) 第 3 周翻车）。
4. **"动画快就是体验好"**：错（前 100ms 没反馈一样卡）。
5. **"120Hz 必然更顺"**：错（[§5.5](#55-实验五120hz-高刷屏的真实体验提升) 未优化反而抖）。

**10.4 三个外延**

- **动效设计语言**：iOS Spring/Material Motion 等系统级动画规范，工程实现要遵守
- **可访问性（a11y）**：prefers-reduced-motion 等用户偏好必须尊重
- **AI 辅助评测**：自动化分析视频帧，未来可替代人工感知打分

**10.5 给团队的建议**

- 第 1 周：审计所有动画，把 left/top 改成 transform
- 第 2 周：上线输入响应延迟监控，SLO 设 100ms
- 第 3 周：滚动 / 列表场景做强制同步布局清零
- 第 4 周：120Hz 设备适配，关键动画做专项调优
