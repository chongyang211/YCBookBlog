## 00.5 贯穿案例：短视频信息流"均值高但用户骂"事件

> 本案例贯穿全文：§01 看懂现象、§02 拿到第一性原理武器、§03/§04 用三方案+决策树定位、§05 用实验复盘、§06 给出分层策略闭环。

### 案例背景

某头部短视频应用 V8.4 上线"沉浸式信息流"，研发同学验收时发现 FPS 数据"非常漂亮"：

- 实验室 Pixel 6 滑动均值 **59.2 fps**，看板一片绿。
- 灰度 1% 后，**应用商店一周内涌入 1700+ "卡"评论**，NPS 下跌 4 个点，CEO 在群里 @ 性能负责人。
- 研发组复测发现"均值确实是 59 fps"，结论："看板没问题，是用户体感不准"。

但用户的反馈非常具体——"每滑两三个视频就抖一下"、"评论区弹出时画面顿一下"、"双击点赞时按钮延迟 1 秒"。

### 经验派的 4 周折腾（典型反面教材）

团队凭直觉做了三件事，越搞越糟：

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 把列表 item layout 减少 2 层（怀疑布局复杂）| 均值升到 59.5 fps，投诉**未减少** |
| 第 2 周 | 给图片加 RGB_565 模式（怀疑显存）| 画质下降，运营反对回滚 |
| 第 3 周 | 把"滑动监听"改 throttle 100ms（怀疑回调多）| 数据没动，反而引入新 bug |
| 第 4 周 | 把监控采样窗口拉到 5s 想"平滑数据"| 看板**更绿了**，但用户骂得更凶 |

**复盘**：四周里所有动作都基于"均值偏低 = 卡顿、均值高 = 流畅"的错误假设。第 4 周把窗口拉宽，本质是**主动稀释了抖动信号**——这是反向收益的典型。

### 方法派的 5 天闭环

新接手的同学按本文方法论重做：

**Day 1（§02 第一性原理）**：用"帧时长分布模型"重新看数据，导出原始 100ms 窗口数据：

| 窗口 | 均值 FPS | P99 帧时长 | Max 帧时长 |
|---|---|---|---|
| 滑动稳态 | 59.5 | **89 ms** | 480 ms |
| 评论弹出瞬间 | 58.0 | **210 ms** | 660 ms |
| 双击点赞瞬间 | 57.0 | **180 ms** | 320 ms |

→ 立刻看出："均值假流畅"，**P99 比预算（16.67ms）超了 5-12 倍**。

**Day 2（§03 三方案组合）**：方案①（Choreographer）+ 方案②（FrameMetrics）双采，定位每一类长尾帧的阶段归属：

- 滑动稳态 P99=89ms → 主要是 `LAYOUT_MEASURE_DURATION` 占 60ms（评论缩略图 measure 同步走主线程）
- 评论弹出 P99=210ms → 主要是 `INPUT_HANDLING_DURATION + DRAW` 共 150ms（弹层动画 + 评论图加载同步触发）
- 双击点赞 P99=180ms → `SYNC_DURATION` 占 100ms（点赞动画同步上传 GPU 大纹理）

**Day 3（§04 归因决策树）**：三个长尾分别归到不同分支——长尾归因 / 场景关联 / 抖动归因。

**Day 4（§06 分层策略）**：按"指标→采集→长尾→VRR"四层分别施治：

- 第 1 层：把"均值 FPS"看板下线，换成 P99/Max 双指标（耗时 1 天）。
- 第 3 层：评论缩略图改 AsyncLayoutInflater；点赞动画纹理预上传；图片加载改异步占位。
- 第 4 层：120Hz 设备申请 ARR，让点赞动画跑 120fps。

**Day 5（§05 求证实验思路验证）**：构造和线上同分布的 mock 数据，灰度对比验证。

### 上线效果

| 指标 | 经验派 4 周后 | 方法派 5 天后 |
|---|---|---|
| 均值 FPS（误导指标）| 59.5 | 58.8（**反而略低**）|
| P99 帧时长 | 89 ms | **22 ms** |
| Max 帧时长 | 480 ms | 95 ms |
| 应用商店"卡顿"差评/周 | 1700+ | **180** |
| 用户 NPS | -4 | +2 |

**核心反差**：均值反而略降，但用户体感大幅改善。**这正是"FPS 是抖动游戏"最锋利的证据。**

### 案例如何串起本文

- **§01 现象与代价** ▶▶ 现象映射：抖动型卡顿 + 冻屏型操作（点赞延迟 1 秒）。
- **§02 第一性原理** ▶▶ 用"帧时长分布模型"+"四态分类"识破"均值假流畅"。
- **§04 归因决策树** ▶▶ 三类长尾分别走"长尾归因 / 场景关联 / 抖动归因"。
- **§05 求证实验** ▶▶ §5.1 解释为什么均值会误导，§5.2 解释为什么 5s 窗口会稀释信号。
- **§06 优化策略深化** ▶▶ "指标→采集→长尾→VRR"四层正是案例落地路径。

## 01.问题域定义

### 1.1 现象与代价

FPS 不达标的用户感知：

- **持续低帧（如 30fps）**：滚动 / 动画"不顺滑"，但用户能接受。
- **帧时长抖动**：均值 60fps 但偶尔 100ms 帧，用户感觉"一卡一卡"。
- **冻屏（>700ms 单帧）**：用户认为"卡死"。
- **撕裂（tearing）**：未开 Vsync 时画面上下错位。
- **掉帧链 / 帧延迟**：用户操作和画面响应之间的延迟感。

**业务代价（行业实测数据）**：

- 抖音、TikTok 内部数据：滑动帧率 P99 每提升 5ms，留存 +0.5%。
- 电商列表：滑动卡顿率每降 1%，浏览深度 +3%。
- 游戏：FPS 抖动直接影响用户口碑（Steam 评分中"流畅度"占很大权重）。

> ▶▶ **回扣 §00.5 案例**：短视频"均值 59.2fps"看板绿油油，但 P99=89ms 直接对应"滑两三个视频抖一下"。**抖动型现象（80-90ms 长尾）和冻屏型现象（点赞触发 320ms Max）同时存在，但都被同一个均值掩盖**——这正是 §1.1 这些"现象"在真实世界共存的方式。

### 1.2 度量准则

按 [`卷零·02 §3`](../00.公共方法论/02.跨平台指标体系.md) 的统一指标体系：

**资源视角（USE）**：见 `卷三·01 §1.2`。FPS 篇主要看 RED。

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 平均 FPS | 总帧数 / 总时间 | ≥ 目标帧率 95% |
| 帧时长 P50 | 中位帧时长 | < 帧预算 |
| 帧时长 P95 | 95% 分位帧时长 | < 1.5 × 帧预算 |
| 帧时长 P99 | 长尾帧 | < 2 × 帧预算 |
| 帧时长最大值 | 最差帧 | < 700ms（冻屏阈值）|
| 掉帧率 | 超时帧 / 总帧 | < 5% |

**用户感知（APDEX）**：

- *Satisfied*：连续 30 帧都按时
- *Tolerating*：单次掉帧 < 100ms
- *Frustrated*：冻帧 ≥ 700ms

> **关键约定**：**禁止单独看均值 FPS**。它对抖动几乎不敏感。必须配合 P95/P99/Max。详见 §5.1 实验。

### 1.3 行业基准与目标

| 平台 | 目标帧率 | 帧预算 | P99 阈值 |
|---|---|---|---|
| Android 60Hz | 60 fps | 16.67 ms | < 25 ms |
| Android 90/120Hz | 90/120 fps | 11.11/8.33 ms | < 1.5 ×预算 |
| iOS 60Hz | 60 fps | 16.67 ms | < 25 ms |
| iOS ProMotion 120Hz | 120 fps | 8.33 ms | < 12 ms |
| Web | 与显示器同步 | 16.67 ms | < 25 ms |
| 嵌入式 HMI | 30/60 fps | 33/16.67 ms | < 2 ×预算 |

## 02.第一性原理

> 本节回答三个根本问题：**①FPS 的物理本质是什么？②为什么"均值"无法反映流畅度？③同构之下平台差异在哪？**

### 2.1 FPS 本质定义

**一句话定义**：

> **FPS = 单位时间内成功被显示器扫描显示的帧数**。

这句话隐含两个不可商量的物理约束：

**约束一：FPS 上限由显示硬件决定，不由软件决定**

显示器以固定（或可变）频率扫描帧缓冲。无论应用渲染多少帧，**用户能看到的最大 FPS = 显示器刷新率**。60Hz 屏上即使应用渲染 200fps，用户依然只感知到 60fps（多余帧被丢弃）。

```
   应用渲染 ──▶ Frame Buffer ──▶ 显示器扫描 ──▶ 用户感知
       │             │              │
   产帧速率         缓冲深度       刷新率（硬上限）
```

**约束二：FPS 是"过去一段时间的统计"，不是瞬时值**

FPS 必须基于一段时间窗（通常 1 秒）统计。瞬时无所谓"FPS"，只有"这一帧的时长"。这是一个关键概念误区。

正确表述：
- ✅ "过去 1 秒内显示了 58 帧" → 58 FPS
- ✅ "这一帧花了 32ms"
- ❌ "现在 FPS 是 32ms"

### 2.2 帧时长分布模型

**为什么"帧时长分布"是 FPS 的本质**

FPS 是单一数字，但"流畅"是关于**每一帧时长**的分布特征。两个 60fps 应用，分布可能完全不同：

```
   应用 A：每帧 16ms（均匀）       应用 B：57 帧 13ms + 3 帧 100ms
   ───────────────                ─────────────────────────
   分布：方差极小                   分布：3 个尖峰
   均值 FPS：60                    均值 FPS：60
   P99 帧时长：16ms                P99 帧时长：100ms
   用户体验：流畅                   用户体验：每秒抖一下
```

**统计学上，FPS 的"流畅"应该用分布的尾部 (tail) 来描述**：

```
   "流畅" = 帧时长分布的 P99 < 1.5 × 帧预算
   "可接受" = 帧时长分布的 P95 < 1.5 × 帧预算
   "卡顿" = 任意单帧 > 700ms
```

这就是为什么所有性能监控系统都强制要求 **P50/P95/P99/Max 四元组**，而不是均值。

> ▶▶ **回扣 §00.5 案例**：短视频信息流恰好就是"应用 B 的真实化身"——均值 59.5 fps（看似 60），P99 却高达 89ms。**这一节告诉我们：分布的尾部才是用户体感的物理基础**。当方法派同学第一次把 100ms 窗口数据画成直方图时，真相在 5 分钟内就暴露了。

**单帧时长的"四态分类"**：

```
   ┌──────────────────────────────────────────┐
   │ 完美帧 (≤ 帧预算)                          │
   │ 16.67ms（60Hz）以内，无感                  │
   ├──────────────────────────────────────────┤
   │ 轻微掉帧（1-1.5× 帧预算）                  │
   │ 16-25ms，几乎无感                          │
   ├──────────────────────────────────────────┤
   │ 明显掉帧（1.5-3× 帧预算）                  │
   │ 25-50ms，能感知"卡了一下"                  │
   ├──────────────────────────────────────────┤
   │ 严重掉帧（3× 帧预算 - 700ms）               │
   │ 50-700ms，明显卡顿                         │
   ├──────────────────────────────────────────┤
   │ 冻帧（≥ 700ms）                            │
   │ 用户认为"卡死"                             │
   └──────────────────────────────────────────┘
```

### 2.3 跨平台同构原理

**为什么所有平台的 FPS 原理都同构**

所有有 UI 的平台都有"显示帧时钟 + 帧产出"两端，本质同构：

```
   通用 FPS 模型：

      [应用产帧] ──▶ [Buffer] ──▶ [显示器扫描]
           │                          │
      产帧速率（变量）              刷新率（定量）
           │                          │
           └──────[Vsync 同步]────────┘
```

每个平台都必须有：

| 抽象组件 | 解决什么问题 |
|---|---|
| 帧时钟订阅 | 知道"下一次显示什么时候发生" |
| 帧时长测量 | 知道"两次显示之间多久" |
| 帧分类 | 区分"按时帧 / 掉帧 / 冻帧" |
| 长尾统计 | P95/P99/Max 才能反映真相 |

**跨平台术语对照**

| 通用术语 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 帧时钟 | Choreographer / Vsync | CADisplayLink | requestAnimationFrame | 显示控制器 IRQ |
| 帧统计 API | FrameMetrics (24+) | MetricKit Hitches (14+) | PerformanceObserver | 厂商 SDK |
| 实时 FPS 显示 | "开发者选项 → GPU 呈现模式" | Instruments Core Animation | DevTools Frame Render | 串口日志 |
| 刷新率 | 60/90/120 Hz | 60/120 Hz | 与显示器同步 | 厂商定 |
| 自适应帧率 | Android 12+ ARR/VRR | ProMotion | 浏览器自适配 | 视设备 |

**同构带来的工程价值**

理解同构原理后：

1. **指标体系可对齐**：所有平台都用 P50/P95/P99/Max 四元组。
2. **采集方案可复用**：帧回调 + 系统 API + 屏幕直采 三件套通用。
3. **优化方向通用**：减少长尾帧、稳定帧时长分布。

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 帧时钟精度 | Vsync 中断（μs 级）| CADisplayLink（μs 级）| rAF（ms 级，部分浏览器）| 视硬件 |
| 系统提供分布数据 | FrameMetrics（API 24+）| Hitches Ratio (iOS 14+) | LCP/INP/CLS（部分）| 通常无 |
| 高刷率支持 | 12+ ARR | ProMotion (iPad 2017+, iPhone 13 Pro+) | 浏览器自动 | varies |
| 静态页面盲区 | 是（无 Vsync 请求即无 callback）| 同 | rAF 不调度 | 视实现 |
| 跨进程合成 | SurfaceFlinger | Render Server | Compositor | varies |

> 后续遇到平台特化点回引本节。

## 03.度量与采集

### 3.1 三类采集方案的本质

所有平台的 FPS 采集本质上只有 3 类（与 [`卷三·01 §3.1`](01.渲染管线与原理.md) 同构）：

```
   ① 帧时钟订阅（应用层 Vsync 监听）
   ② 系统帧 API（OS 提供阶段级数据）
   ③ 外部测量（高速摄像 / 屏幕直采）
```

下面对每一类做完整原理拆解。

---

**① 帧时钟订阅（FPS 采集主流方案）**

**核心原理（一句话）**：订阅 Vsync 信号，记录每次回调时间戳，差值即帧时长。

**工作机理**：

```java
class FpsMonitor implements Choreographer.FrameCallback {
    private long lastTime;
    private final List<Long> intervals = new ArrayList<>();

    public void start() {
        lastTime = System.nanoTime();
        Choreographer.getInstance().postFrameCallback(this);
    }

    @Override
    public void doFrame(long frameTimeNanos) {
        long interval = (frameTimeNanos - lastTime) / 1_000_000;  // ms
        intervals.add(interval);
        lastTime = frameTimeNanos;
        Choreographer.getInstance().postFrameCallback(this);  // 持续订阅
    }

    public Stats compute() {
        // 计算 P50/P95/P99/Max
        return Stats.compute(intervals);
    }
}
```

**物理本质**：

> 把"显示器节拍"作为可信参考时钟，统计每两次之间的间隔。

**为什么这样有效**：

- 与硬件物理同步，参考时钟可靠。
- 开销极低（每帧 < 1μs）。
- 直接反映"用户看到的帧"。

**局限根源**：

- **静态页面盲区**：无渲染请求 = 无回调（详见 [`卷三·01 §3.2`](01.渲染管线与原理.md)）。
- **不区分原因**：只知道"这一帧 32ms"，不知道哪段慢。
- **可变刷新率干扰**：硬编码 16.67ms 在 120Hz 屏会误判。

**适用边界**：所有应用 FPS 监控的基础方案。

---

**② 系统帧 API（细颗粒数据）**

**核心原理（一句话）**：使用系统提供的细颗粒帧统计 API，得到每帧的"输入 / 动画 / Layout / Draw / 合成"分解。

**工作机理**：详见 [`卷三·01 §3.1`](01.渲染管线与原理.md) 同章节。FPS 篇的关注点是"聚合统计"：

```java
window.addOnFrameMetricsAvailableListener((window, frameMetrics, dropCountSinceLastInvocation) -> {
    long total = frameMetrics.getMetric(FrameMetrics.TOTAL_DURATION);
    long layout = frameMetrics.getMetric(FrameMetrics.LAYOUT_MEASURE_DURATION);
    long draw = frameMetrics.getMetric(FrameMetrics.DRAW_DURATION);
    long sync = frameMetrics.getMetric(FrameMetrics.SYNC_DURATION);
    // 聚合到分位
    aggregator.add(total, layout, draw, sync);
});
```

**物理本质**：OS 直接告诉应用每帧的真实组成。

**适用边界**：定位到"哪个阶段超时"，配合方案 ① 做归因。

---

**③ 外部测量（金标准）**

**核心原理（一句话）**：用高速摄像 / 屏幕直采从用户角度测量物理 FPS。

**工作机理**：见 [`卷三·01 §3.1`](01.渲染管线与原理.md) 同章节。

**适用边界**：实验室基线测试 + 校准线上数据偏差。

---

**三种方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 帧时钟订阅 | Vsync 触发 | 帧级 | 极低 | 高 | ✅ | 无阶段拆解 |
| ② 系统帧 API | OS 提供 | 阶段级 | 极低 | 中 | ✅（API 受限）| 颗粒度由系统决定 |
| ③ 外部测量 | 屏幕外 | 物理时序 | 无 | 极高 | ❌ | 仅实验室 |

**方案的"组合定律"**：① 做线上 FPS 指标 + ② 做超时帧归因 + ③ 做实验室基线。

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| 帧时长 P99 | ✅ | ✅ | ✅ |
| 哪段超时（产帧/合成/显示） | ❌ | ✅ | 推断 |
| 静态页面期间无 callback | ❌ | ❌ | ❌（无变化）|
| 系统合成丢帧（应用看似已提交）| ❌ | ✅ | ✅ |
| 端到端延迟 | ❌ | 部分 | ✅ |

**盲区一：静态页面**：无 Vsync 请求时无回调。补救：

- 持续触发空 frame callback 维持监控。
- 配合卷三·03 卡顿监控（LooperPrinter）。

**盲区二：合成段隐性丢帧**：应用提交了帧，但 SurfaceFlinger 因 GPU 慢丢了。只有 FrameTimeline（Android 12+）能发现。

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 帧时钟 | `Choreographer.postFrameCallback` | `CADisplayLink` | `requestAnimationFrame` | Vsync IRQ |
| 系统帧 API | FrameMetrics (24+) / FrameTimeline (12+) | MetricKit Hitches (14+) | Web Vitals API | 厂商 |
| 长任务 | LooperPrinter | os_signpost | longtask Performance | 业务 |
| 外部测量 | HDMI / 高速摄像 | 高速摄像 | 浏览器 Tracing + 摄像 | HDMI |
| 实时显示 | dumpsys SurfaceFlinger | Instruments | DevTools Frame | 串口 |

### 3.4 数据可信度评估

| 数据 | 方案 ① | 方案 ② | 偏差 |
|---|---|---|---|
| FPS 平均 | < 2% 误差 | < 1% | ① 漏合成段 |
| 帧时长 P99 | < 5% 偏低 | 准确 | ① 不感知 GPU |
| 阶段拆解 | 不可见 | 准确 | ② 专属 |
| 端到端 | 不可测 | 不可测 | 仅 ③ |

## 04.归因方法

### 4.1 FPS 归因决策树

```
FPS 不达标
   │
   ├── 帧时长分布尖峰（偶发掉帧）──▶ 长尾归因
   │                               ├─ GC 触发？查 ART log
   │                               ├─ 大任务？查主线程 trace
   │                               └─ 系统抢占？查 sched
   │
   ├── 帧时长分布整体偏高 ────────▶ 持续慢
   │                               ├─ 走渲染篇决策树（CPU/GPU/同步段）
   │                               └─ 检查布局复杂度
   │
   ├── FPS 突然降低（场景特定）────▶ 场景关联
   │                               ├─ 滚动期？列表 onBindViewHolder
   │                               ├─ 动画期？动画计算
   │                               └─ 启动后？资源加载
   │
   └── 帧时长抖动严重 ────────────▶ 抖动归因
                                  ├─ 内存抖动（GC 频繁）
                                  ├─ 后台干扰（其他进程）
                                  └─ 调度抖动（CPU 调度延迟）
```

> ▶▶ **回扣 §00.5 案例**：短视频信息流的三类长尾恰好命中决策树的不同分支——
> - **滑动稳态 P99=89ms** → "帧时长分布尖峰"分支 → 长尾归因 → FrameMetrics 拆出 LAYOUT 占 60ms（评论缩略图同步 measure）。
> - **评论弹出 P99=210ms** → "FPS 突然降低（场景特定）"分支 → 场景关联 → 弹层动画 + 图加载同步触发。
> - **双击点赞 Max=320ms** → "帧时长抖动严重"分支 → 抖动归因 → SYNC 段 GPU 大纹理上传。
> 
> **同一个应用的同一段时间，不同场景走不同分支**——这就是为什么"一刀切"优化 4 周无效。

### 4.2 抖动归因法

**抖动归因的核心思路**：不是看"哪一帧慢"，而是看"为什么时长不稳定"。

抖动的常见根因：

| 根因 | 特征 | 工具 |
|---|---|---|
| 内存抖动（频繁 GC）| 帧时长突然 +5-20ms 周期性 | ART log + heap profile |
| 后台进程抢 CPU | 帧时长偶发 +10-100ms | 系统级 trace |
| 锁竞争 | 帧时长偶发 +5-50ms | Lock contention profiler |
| 异步任务回主线程 | 帧时长偶发 +几十 ms | LooperPrinter |
| 温度降频 | 整段 FPS 缓慢下降 | thermal trace |

**关键经验**：

- 如果 P99 - P50 > 20ms → 一定有抖动源
- 如果 Max > 200ms → 一定有阻塞型问题（IO / 锁 / GC）

### 4.3 长尾分位归因法

**为什么必须用分位看 FPS**

均值对长尾极不敏感：

- 100 帧 + 1 帧 1000ms = 总时长 1100ms / 101 帧 = 10.9 ms/帧 = 91.7 fps（"看起来"很正常）
- 但用户看到了 1 次冻屏！

**分位看法**：

- P50：典型表现
- P95：5% 用户感知的体验
- P99：1% 用户感知的体验
- Max：最差体验（极少但极重要）

**分位优化策略**：

- 先优 Max（消除冻屏）
- 再优 P99（消除明显卡顿）
- 再优 P95（减少抖动）
- 最后看 P50（追求基线流畅）

### 4.4 可变帧率归因

Android 12+ ARR、iOS ProMotion 引入可变刷新率，FPS 监控逻辑要改：

**问题**：硬编码 16.67ms 作为帧预算 → 在 120Hz 屏上变成 8.33ms 帧预算，但代码仍判断 "16ms 内 = 正常"。

**修复**：

- 读取系统当前刷新率（`Display.getRefreshRate()` / `UIScreen.maximumFramesPerSecond`）。
- 帧预算 = 1000 / 当前刷新率。
- 评估时用相对于预算的比例，而非绝对时间。

## 05.求证实验 ⭐

### 5.1 实验一：均值掩盖抖动

**Step 1 — 原始观察**

很多团队报 FPS 均值（如 58.5 fps），用户却频繁反馈"卡"。**为什么数据和体感不一致？**

**Step 2 — 提出疑问**

> **均值 FPS 与用户感知"流畅度"的相关性有多大？P99 帧时长是否更相关？**

**Step 3 — 形成假设**

**H₁**：均值 FPS 与用户感知**弱相关**（r < 0.4）；P99 帧时长强相关（r > 0.8）。  
**H₀**：均值 FPS 与用户感知强相关。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 |
| 测试场景 | 同应用同场景，构造 10 种不同"FPS 分布"配置 |
| 配置示例 | (a) 60fps 均匀 (b) 55fps 均匀 (c) 60fps + 1 个 100ms 帧 (d) 60fps + 5 个 50ms 帧 ... |
| 用户主观打分 | 30 名测试用户对每种配置打"流畅度" 1-5 分 |
| 主指标 | 均值 FPS / P99 帧时长 与 用户评分的相关系数 |

**Step 5 — 实测数据**

| 配置 | 均值 FPS | P99 帧时长 | 用户均分 |
|---|---|---|---|
| (a) 60 fps 均匀 | 60 | 17 ms | 4.9 |
| (b) 55 fps 均匀 | 55 | 19 ms | 4.6 |
| (c) 60 fps + 1×100ms | 59 | 100 ms | 3.4 |
| (d) 60 fps + 5×50ms | 58 | 50 ms | 3.6 |
| (e) 45 fps 均匀 | 45 | 22 ms | 4.1 |
| (f) 60 fps + 1×300ms | 58 | 300 ms | 2.1 |

**Step 6 — 验证 / 修正**

- 均值 FPS 与用户评分相关系数 r = 0.31（弱相关）。
- P99 帧时长与用户评分相关系数 r = -0.87（强负相关，时长越大评分越低）。
- 配置 (e) 均值更低但更流畅；配置 (f) 均值高但用户最差。

**Step 7 — 提炼结论**

> **均值 FPS 与用户感知弱相关 (r=0.31)，P99 帧时长强相关 (r=-0.87)。  
> 优化目标应是 P99 而非均值。**

工程意义：

- 删除所有"均值 FPS"为唯一指标的看板。
- 新指标体系必有 P95 / P99 / Max。
- 性能 review 重点看长尾。

**Step 8 — 边界**

- 测试场景为滚动 / 动画类。静态页面无明显帧率概念，结论不适用。
- 用户群差异：游戏玩家对抖动更敏感；普通用户对均值偏低更宽容。

> ▶▶ **回扣 §00.5 案例**：短视频经验派 4 周折腾全部基于"均值=流畅"的错误前提（H₀），方法派只用了 1 天就用线上数据复现出 r=-0.87 的强负相关——**用户骂得越凶的版本，P99 帧时长越大**。本实验的结论"删除均值看板"在那个案例里直接落地为 Day 1 第一动作。

---

### 5.2 实验二：采样间隔精度

**Step 1 — 原始观察**

很多监控 SDK 用"每秒采样一次 FPS"，但**1 秒粒度是否能反映真实抖动？**

**Step 2 — 提出疑问**

> **不同采样窗口（100ms / 1s / 10s）的 FPS 数据对"长尾"的反映能力差异多大？**

**Step 3 — 形成假设**

**H₁**：窗口越小越能反映瞬时抖动；1s 窗口已损失大部分 P99 信息；10s 窗口几乎只看均值。  
**H₀**：采样窗口不影响。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 测试场景 | 构造已知数据：60 fps 中插入 5 个 100ms 帧 |
| 采样窗口 | 100ms / 1s / 10s |
| 主指标 | 每个窗口看到的 P99 帧时长、能否识别"100ms 帧" |

**Step 5 — 实测数据**

| 窗口 | 窗口数 | 100ms 帧识别率 | 最大窗口 P99 |
|---|---|---|---|
| 100ms 窗口 | 600 / 分钟 | 100%（每个 100ms 帧落在单独窗口）| 100 ms |
| 1s 窗口 | 60 / 分钟 | 仍可识别（但被平均后均值看起来正常）| 100 ms |
| 10s 窗口 | 6 / 分钟 | 抖动被严重稀释 | 30 ms（被均值化）|

**Step 6 — 验证 / 修正**

- 1s 窗口能识别但需要看 P99 数据。
- 10s 窗口几乎丢失抖动信息。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **采样窗口应 ≤ 1s。每帧采样（实时记录）+ 1s 聚合是最佳实践。  
> 不要用 5s / 10s 窗口聚合。**

工程意义：

- 数据采集："每帧一记录"，避免聚合丢信息。
- 上报：可以 5-10s 上报一次，但要带原始分位数（P50/95/99）不要重新聚合。

**Step 8 — 边界**

- 不同场景对窗口敏感度不同。游戏要求 100ms 窗口；普通应用 1s 即可。

---

### 5.3 实验三：高刷增益

**Step 1 — 原始观察**

90/120Hz 屏被宣传为"更流畅"，但**真的更流畅吗？应用如何充分利用？**

**Step 2 — 提出疑问**

> **同一应用在 60Hz 和 120Hz 屏上，用户感知差异有多大？**

**Step 3 — 形成假设**

**H₁**：在应用能稳定产出 120 fps 时，用户感知"明显更流畅"；如果应用最高只能产 60 fps，120Hz 屏几乎无增益。  
**H₀**：高刷自动让所有应用变流畅。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 7 Pro（90/120Hz 可切）|
| 应用 A | 简单 ListView 滚动（容易产 120 fps）|
| 应用 B | 复杂瀑布流（最多产 60 fps）|
| 测试 | 30 用户分别用 60Hz / 120Hz 体验，主观打分 |

**Step 5 — 实测数据**

| 应用 | 60Hz 帧率 | 60Hz 评分 | 120Hz 帧率 | 120Hz 评分 |
|---|---|---|---|---|
| A (简单) | 60 fps | 4.4 | 118 fps | 4.8 |
| B (复杂) | 55 fps | 3.9 | 60 fps（被业务卡）| 4.0 |

**Step 6 — 验证 / 修正**

- 应用 A 在 120Hz 下评分明显提升。
- 应用 B 因应用层卡 60 fps，高刷"白买"。

**Step 7 — 提炼结论**

> **高刷屏的价值取决于应用自身能否产足够多帧。  
> 应用层瓶颈不解决，高刷屏几乎无用。**

工程意义：

- 上 120Hz 前先优化应用到稳定 120 fps，否则浪费。
- 应用应"自适应刷新率"：能产 120 就申请 120Hz，能产 60 就申请 60Hz（省电）。

**Step 8 — 边界**

- 静态画面无所谓高刷。
- 文字阅读类应用高刷增益不明显（用户察觉不到）。

---

### 5.4 实验四：FrameTimeline 揭露合成段隐性丢帧

**Step 1 — 原始观察**

某团队 Choreographer 监控显示"应用产帧 60fps、P99=18ms 完美"，但用户反馈"画面会偶尔卡一帧"。**应用提交的帧 = 用户看到的帧吗？**

**Step 2 — 提出疑问**

> **方案①（帧时钟订阅）能否覆盖系统合成段（SurfaceFlinger / GPU 合成）的丢帧？**

**Step 3 — 形成假设**

**H₁**：方案①只能看到"应用提交了多少帧"，看不到"系统是否合成成功"。SurfaceFlinger 因 GPU 慢丢帧时，应用看自己的数据"完美"，但用户看到掉帧。  
**H₀**：应用层 Vsync 监控就足够。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6（Android 13，支持 FrameTimeline）|
| 工具 | Choreographer 监控 vs FrameTimeline API |
| 测试场景 | 滑动列表，**外部叠加 GPU 高负载应用**（模拟系统竞争）|
| 主指标 | 应用层 P99 帧时长 vs 系统侧 `presentationTime - expectedPresentationTime` |

**Step 5 — 实测数据**

| 状态 | 应用层 Choreographer P99 | FrameTimeline 系统侧丢帧率 | 用户感知 |
|---|---|---|---|
| 无 GPU 干扰 | 18 ms | 0% | 流畅 |
| 中等 GPU 干扰 | 18 ms（不变！）| 4.2% jank | 偶发卡顿 |
| 高 GPU 干扰 | 19 ms | 11.8% jank | 明显卡 |

**Step 6 — 验证 / 修正**

- 应用层数据**完全感知不到合成段丢帧**——Choreographer 在应用提交后就回调，应用以为"按时了"。
- FrameTimeline 通过 `expectedPresentationTime` vs `actualPresentationTime` 直接给出"到底有没有显示出去"。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **方案①有合成段盲区。线上需配合 FrameTimeline（Android 12+）/ MetricKit Hitches（iOS 14+）才能真实反映用户感知。**

工程意义：

- Android 12+ 上线 FrameTimeline 监控作为方案①的**校准基准**。
- 校准后差距 > 5%，说明应用提交压力过大或系统资源紧张，需增加 GPU/合成段排查。

**Step 8 — 边界**

- FrameTimeline 仅 Android 12+。低版本只能依赖 MetricKit（iOS 14+）或外部测量校准。
- 该实验不替代方案①，是补充——**方案①跑量大、FrameTimeline 跑校准**。

---

### 5.5 实验五：自适应刷新率切换的能效收益

**Step 1 — 原始观察**

很多团队怕麻烦，120Hz 设备直接申请 120Hz 全程跑。但**这真的最优吗？电池消耗如何？**

**Step 2 — 提出疑问**

> **120Hz 设备上，全程 120Hz vs ARR 自适应（按内容切换）的功耗与体感差异多大？**

**Step 3 — 形成假设**

**H₁**：全程 120Hz 在静态/慢滚场景**显著费电**且无体感增益；ARR 按内容切换可在保持流畅的同时降功耗 15-30%。  
**H₀**：120Hz 全程开启功耗代价可忽略。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 7 Pro（支持 ARR 24/60/90/120Hz）|
| 应用 | 同一应用，分别配置（A）固定 120Hz（B）ARR 按内容切换 |
| 测试时长 | 1 小时混合场景（30min 滑动 + 20min 阅读 + 10min 视频）|
| 主指标 | 电池消耗 mAh、滑动 P99 帧时长、阅读时实际刷新率 |

**Step 5 — 实测数据**

| 模式 | 1 小时电池消耗 | 滑动 P99 | 阅读时刷新率 | 用户感知 |
|---|---|---|---|---|
| (A) 固定 120Hz | 540 mAh | 12 ms | 120 Hz | 流畅但发热 |
| (B) ARR 自适应 | **380 mAh** (-29%) | 12 ms | 24 Hz（无动效）/ 60 Hz（文字滑）| 流畅，温度低 |

**Step 6 — 验证 / 修正**

- 滑动场景两者一致（120 fps），用户感知无差。
- 阅读场景 ARR 切到 24Hz，**节省 29% 电量且用户察觉不到**（静态画面 24Hz 与 120Hz 视觉一致）。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **120Hz 设备应主动用 ARR/preferredRefreshRate API 按内容切换：动效/滑动→120Hz，文字阅读→60Hz，纯静态→24Hz。  
> 收益：~30% 电池续航，且体感无差。**

工程意义：

- Android 12+：`Window.getAttributes().preferredFrameRate = 120f`（按场景动态设置）。
- iOS ProMotion：`CADisplayLink.preferredFrameRateRange = CAFrameRateRange(minimum: 24, maximum: 120)`，让系统决策。
- 不要"为了好看"全程 120Hz——这是 vanity metric。

**Step 8 — 边界**

- 仅适用于支持可变刷新率的设备（Pixel 6+/iPhone 13 Pro+）。
- 频繁切换（< 100ms）会有切换毛刺；需做**滞后切换**（hysteresis）。

### 5.6 五大实验启示

```
   均值掩盖抖动           → 必须用 P95/P99/Max               ─┐
                                                              │
   采样间隔精度           → 窗口 ≤ 1s，原始数据不聚合          │
                                                              │
   高刷增益               → 应用层瓶颈不优化就无增益            ├─▶ FPS = 长尾游戏 + 系统协同
                                                              │
   FrameTimeline 校准     → 方案①有合成盲区，需系统侧补充     │
                                                              │
   ARR 自适应             → 高刷不等于全程开，电池才是隐藏指标   ─┘
```

**统一启示**：

- **流畅是分布问题，不是均值问题**：所有数据看板必须改用分位。
- **数据采集要保留原始性**：避免过早聚合，窗口 ≤ 1s。
- **高刷不是免费午餐**：应用层必须配合优化才能发挥价值，且要考虑能效。
- **应用层数据有边界**：合成段丢帧需系统 API 校准。
- **FPS 监控的终极形态**：分位指标 + 应用层订阅 + 系统侧校准 + ARR 智能调度。

## 06.优化策略深化

> 本节回答四个递进问题：**①如何把度量改对？②如何让数据可信？③如何消灭长尾帧？④如何让高刷设备不浪费？**  
> 与传统"渲染优化清单"不同，FPS 篇的优化主战场是**度量与监控自身**——度量错了一切都是错的。

### 6.1 第一层：指标体系治理（先把度量改对）

**核心命题**：在度量错的前提下做任何优化都是反向收益。这一层成本极低、收益极高，应作为 Day 1 第一动作。

**策略 1.1：均值看板替换为 P50/P95/P99/Max 四元组**

- **机理**：均值对长尾不敏感（[§5.1 实验](#51-实验一均值掩盖抖动) r=0.31），P99 才与用户感知强相关（r=-0.87）。
- **代码**（Android Choreographer + 流式分位）：

```java
public class FpsAggregator {
    // T-Digest 在线分位估算，内存固定
    private final TDigest digest = TDigest.createMergingDigest(100.0);
    private long maxFrameNs = 0;
    
    public void onFrame(long frameNs) {
        digest.add(frameNs / 1_000_000.0);  // ms
        maxFrameNs = Math.max(maxFrameNs, frameNs);
    }
    
    public Stats snapshot() {
        return new Stats(
            digest.quantile(0.50),
            digest.quantile(0.95),
            digest.quantile(0.99),
            maxFrameNs / 1_000_000.0
        );
    }
}
```

- **收益**：[§00.5 案例](#005-贯穿案例短视频信息流均值高但用户骂事件) Day 1 落地后，看板暴露真相 P99=89ms，定位耗时从"4 周不见底"降到"4 小时"。
- **边界**：T-Digest 默认 100 centroids，内存约 4KB；如果设备 RAM < 1GB 可降到 50。

**策略 1.2：帧分类四态分桶**

- **机理**：单一 P99 仍是粗粒度，需把帧时长按 [§2.2 四态分类](#22-帧时长分布模型)（完美/轻微/明显/严重/冻屏）分桶上报。
- **代码**：

```java
enum FrameClass { PERFECT, SLIGHT, OBVIOUS, SEVERE, FROZEN }

FrameClass classify(long durMs, long budgetMs) {
    if (durMs <= budgetMs) return PERFECT;
    if (durMs <= budgetMs * 1.5) return SLIGHT;
    if (durMs <= budgetMs * 3) return OBVIOUS;
    if (durMs < 700) return SEVERE;
    return FROZEN;
}
```

- **收益**：业务方看到"FROZEN 占比 0.3%"比 "P99=89ms"更易懂；可直接对接 SLO（FROZEN < 0.05%）。
- **边界**：四态阈值需按场景调（游戏更严，普通应用宽松）。

**策略 1.3：APDEX 化统一对外指标**

- **机理**：跨平台对外汇报必须统一口径。Satisfied/Tolerating/Frustrated 与用户语义对齐。
- **收益**：管理层无需理解 P99，看 APDEX 0.92 即知道"92% 用户满意"。
- **边界**：APDEX 的边界值（T、4T）需按业务调，不能照搬 Web 默认。

---

### 6.2 第二层：采集精度治理（让数据可信）

**核心命题**：数据采集的"窗口"和"原始性"决定了能不能看见真相。

**策略 2.1：每帧记录 + ≤1s 聚合**

- **机理**：[§5.2 实验](#52-实验二采样间隔精度)证明 10s 窗口稀释抖动信号；1s 窗口 + 原始分位才完整。
- **代码反例**（错误做法，常见于老 SDK）：

```java
// 反例：每秒只记录一次"当前 FPS"，丢失帧级信息
new Handler().postDelayed(() -> {
    int curFps = frameCount;  // 上一秒的总帧数
    report("fps_avg", curFps);
    frameCount = 0;
}, 1000);
```

- **代码正例**：每帧入 T-Digest，按 1s 上报分位 + Max。
- **收益**：[§00.5 案例](#005-贯穿案例短视频信息流均值高但用户骂事件)第 4 周拉宽窗口翻车，正是反例的真实代价。
- **边界**：每帧记录 ≠ 每帧上报。上报粒度可以 5-10s 一次，但**带原始分位数**而非重新聚合。

**策略 2.2：方案① + 方案② + FrameTimeline 三层校准**

- **机理**：[§5.4 实验](#54-实验四frametimeline-揭露合成段隐性丢帧)证明应用层数据有合成段盲区，需系统 API 校准。
- **代码**（Android 12+）：

```java
// 同时订阅 Choreographer + FrameMetrics + FrameTimeline
Choreographer.getInstance().postFrameCallback(frameClock);
window.addOnFrameMetricsAvailableListener(frameMetricsListener);
// FrameTimeline 通过 SurfaceControl.OnJankDataListener
SurfaceControl.OnJankDataListener jankListener = jankData -> {
    for (SurfaceControl.JankData j : jankData) {
        if (j.getJankType() != JANK_NONE) systemJankCount++;
    }
};
```

- **收益**：发现"应用层 P99=18ms 但系统侧 jank 11.8%"——这种盲区只有三层校准能看到。
- **边界**：FrameTimeline 仅 12+；低版本只能依赖外部测量定期校准。

**策略 2.3：静态页面盲区兜底**

- **机理**：无 Vsync 请求时帧回调不触发（[§3.2 盲区一](#32-各方案的可见盲区)），需配合卡顿监控（[`卷三·03`](03.卡顿捕获与归因.md)）。
- **代码**：

```java
// 静态期间用 LooperPrinter 测主线程消息处理时长
Looper.getMainLooper().setMessageLogging(msg -> {
    if (msg.startsWith(">>>>> Dispatching")) startTs = SystemClock.uptimeMillis();
    else if (msg.startsWith("<<<<< Finished")) {
        long dur = SystemClock.uptimeMillis() - startTs;
        if (dur > 100) reportLag(dur);
    }
});
```

- **收益**：补全"无 callback ≠ 无问题"的视角；详情阅读卡顿篇。
- **边界**：LooperPrinter 自身有 ~3% 性能损耗，建议采样 10% 用户开启。

---

### 6.3 第三层：长尾帧治理（消灭 P99 元凶）

**核心命题**：FPS 优化的本质是消灭长尾帧。本节给出**通用可复用**的长尾治理手段；具体阶段（CPU/GPU/同步）的优化详见 [`卷三·01 §6`](01.渲染管线与原理.md)。

**策略 3.1：主线程同步任务异步化**

- **机理**：长尾帧 80% 来自主线程同步任务（DB 查询、IO、measure 复杂布局）。
- **代码示例**（[§00.5 案例](#005-贯穿案例短视频信息流均值高但用户骂事件)真实修复）：

```java
// 反例：onBindViewHolder 同步加载评论缩略图导致 measure 60ms
holder.thumbView.setImageBitmap(loadThumb(commentId));

// 正例：异步占位 + 后台解码
holder.thumbView.setImageDrawable(placeholderDrawable);
asyncDecoder.submit(() -> {
    Bitmap bm = decodeThumb(commentId);
    holder.thumbView.post(() -> holder.thumbView.setImageBitmap(bm));
});
```

- **收益**：滑动稳态 P99 89ms→22ms（[§00.5 案例](#005-贯穿案例短视频信息流均值高但用户骂事件)）。
- **边界**：异步化会引入闪烁；需配合占位图和 view recycle 检测（防止 view 复用时填错图）。

**策略 3.2：弹层/动画的 GPU 纹理预上传**

- **机理**：弹层动画首帧 SYNC 段同步上传 GPU 大纹理常达 80-150ms。预上传到空闲帧。
- **代码**（伪代码）：

```java
// 在动画启动前 50ms 调用，让纹理在空闲帧上传
view.post(() -> {
    Bitmap bm = ((BitmapDrawable) heavyDrawable).getBitmap();
    bm.prepareToDraw();  // 触发 GPU 预上传
});
// 50ms 后启动动画
handler.postDelayed(() -> startAnimation(), 50);
```

- **收益**：[§00.5 案例](#005-贯穿案例短视频信息流均值高但用户骂事件)双击点赞 P99 180ms→25ms。
- **边界**：`prepareToDraw()` 仅 Hint，不保证；不要把所有 Bitmap 都 prepare（浪费显存）。

**策略 3.3：长任务切片 + IdleHandler 推迟**

- **机理**：> 50ms 的任务必然制造长尾帧。切成 < 8ms 片段并推迟到 IdleHandler。
- **代码**：

```java
Looper.myQueue().addIdleHandler(() -> {
    if (pendingTasks.isEmpty()) return false;
    long deadline = SystemClock.uptimeMillis() + 4;
    while (!pendingTasks.isEmpty() && SystemClock.uptimeMillis() < deadline) {
        pendingTasks.poll().run();
    }
    return !pendingTasks.isEmpty();
});
```

- **收益**：典型场景（启动后预加载、列表预取）P99 改善 30-60%。
- **边界**：IdleHandler 在用户持续操作时不触发；需配 `postDelayed` 兜底。

### 6.4 第四层：可变刷新率治理（高端机不浪费）

**核心命题**：120Hz 设备越来越多，但"全程 120Hz"是反模式。本层给出 ARR 智能调度策略。

**策略 4.1：动态读刷新率，禁止硬编码**

- **机理**：硬编码 16.67ms 在 120Hz 屏判定标准变形（[§4.4](#44-可变帧率归因)）。
- **代码**：

```java
float refreshRate = display.getRefreshRate();
long budgetMs = (long) (1000.0f / refreshRate);
boolean isJank = frameDurMs > budgetMs * 1.5;
```

- **收益**：高端机数据从"虚假绿"变真实。
- **边界**：刷新率会动态变（ARR），需在每次帧回调时读取，不可缓存。

**策略 4.2：按内容场景申请目标刷新率**

- **机理**：[§5.5 实验](#55-实验五自适应刷新率切换的能效收益)证明 ARR 节电 29%。Android 12+/iOS ProMotion 都提供 API。
- **代码**（Android 12+）：

```java
WindowManager.LayoutParams lp = window.getAttributes();
lp.preferredFrameRate = isAnimating ? 120f : (isReading ? 60f : 24f);
window.setAttributes(lp);
```

- **代码**（iOS ProMotion）：

```swift
displayLink.preferredFrameRateRange = CAFrameRateRange(
    minimum: 24, maximum: 120, preferred: 60
)
```

- **收益**：1 小时混合场景节电 29%，温度下降 3-4°C。
- **边界**：必须做**滞后切换**（hysteresis），避免 100ms 内频繁切换造成毛刺；典型策略：升频立即生效，降频延迟 500ms。

**策略 4.3：高刷场景压力测试纳入 CI**

- **机理**：高刷预算更紧（120Hz=8.33ms vs 60Hz=16.67ms），原 60Hz 能过的代码可能不过。
- **代码**（Macrobenchmark）：

```kotlin
@Test fun scrollAt120Hz() = benchmarkRule.measureRepeated(
    metrics = listOf(FrameTimingMetric()),
    setupBlock = { device.executeShellCommand("settings put system peak_refresh_rate 120") }
) { /* 滑动场景 */ }
// 阈值断言：frameDurationCpuMs P99 < 12ms（120Hz 1.5×预算）
```

- **收益**：在合并前拦住"60Hz 勉强过、120Hz 翻车"的代码。
- **边界**：需有 120Hz 真机；模拟器无意义。

### 6.5 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 | 对应策略 |
|---|---|---|---|---|---|
| 极高 | 均值看板换分位 | 真相暴露 | 1 天 | 零 | 1.1 |
| 极高 | 每帧记录 + 1s 聚合 | 数据精度大幅提升 | 2-3 天 | 低 | 2.1 |
| 高 | FrameTimeline 三层校准 | 闭环线上数据 | 1 周 | 低 | 2.2 |
| 高 | 主线程同步任务异步化 | P99 直接降一半 | 2 周 | 中 | 3.1 |
| 高 | 动态读刷新率 | 高端机数据准确 | 2-3 天 | 低 | 4.1 |
| 中 | GPU 纹理预上传 | 弹层动画提升 | 1-2 周 | 中 | 3.2 |
| 中 | ARR 智能调度 | 节电 ~30% | 2-3 周 | 中 | 4.2 |
| 中 | 静态页面 LooperPrinter 兜底 | 闭环监控 | 1-2 周 | 低 | 2.3 |
| 中 | 长任务切片 + IdleHandler | P99 改善 | 1-2 周 | 低 | 3.3 |
| 低 | 自己实现 hitch 算法 | 极少收益 | 高 | 中 | - |

**避免反向收益**：

- **过度采集**：每帧记录 + 调用栈快照，开销巨大反而引入卡顿；调用栈仅在 P99 帧抓即可。
- **过度上报**：把每帧数据全上报，流量爆炸；上报应只送分位 + 异常帧详情。
- **窗口拉宽掩盖问题**：[§00.5 案例](#005-贯穿案例短视频信息流均值高但用户骂事件)第 4 周翻车的根因。
- **全程 120Hz**：vanity metric，电池骂声比卡顿骂声更可怕。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某直播应用 Android / iOS / Web 三端都报"60fps 但用户反馈卡"。

**现象**：均值 60 fps，但用户大量反馈"偶尔卡一下"。

**度量与归因**：

切换到 P95/P99 后发现：

| 平台 | 均值 FPS | P99 帧时长 |
|---|---|---|
| Android | 59 | 180 ms |
| iOS | 60 | 95 ms |
| Web | 58 | 220 ms |

**假设与求证**：

P99 帧时长太长是用户体感差的元凶。归因发现：

- Android：直播弹幕重绘 + GC 抖动
- iOS：图片加载导致主线程偶发阻塞
- Web：长任务（JSON 解析）阻塞主线程

**护栏检查**：优化不能损害业务功能。

**修复**：三端统一升级监控指标体系（P95/P99），针对长尾帧分别治理。

**验证**：

| 平台 | 优化前 P99 | 优化后 P99 | 用户卡顿反馈降幅 |
|---|---|---|---|
| Android | 180 ms | 35 ms | -75% |
| iOS | 95 ms | 25 ms | -68% |
| Web | 220 ms | 50 ms | -80% |

**统一启示**：**FPS 监控必须用分位**。所有团队都该把"均值 FPS"指标改掉。

### 7.2 平台特异案例

**背景**：Android 应用上 120Hz 屏后，用户反馈"反而更卡"。

**现象**：高刷屏比 60Hz 屏用户评分还低。

**度量与归因**：

- 60Hz 屏：均值 58 fps，P99 18ms。流畅。
- 120Hz 屏：均值 90 fps，P99 22ms。但**有时 P99 75ms**。

为什么 P99 偶发飙高？因为应用同步初始化 ListView 内容在 120Hz 屏上预算更紧（8.33ms vs 16.67ms），原本能"挤进 16ms"的任务现在超时了。

**假设与求证**：

**假设**：高刷屏帧预算更紧，原本"勉强达标"的代码暴露了瓶颈。

**实验**：把 ListView 的 onBindViewHolder 中的同步任务异步化。120Hz 下 P99 从 75ms 降到 12ms。✅

**修复**：所有同步任务必须按 120Hz 帧预算（8.33ms）验证。

**验证**：120Hz 下 P99 < 12ms，用户反馈正面。

**边界与上线策略**：高刷屏要做"严苛预算评估"，原本对 60Hz 够用的代码可能不够。

---

## 08.防劣化与长效治理

### 8.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
[Lint]      [自动化基准]     [线上 SLO]
```

### 8.2 编码期 Lint

- 监控代码硬编码 16.67ms → 警告（应动态读刷新率）。
- 性能看板配置只有"均值 FPS"指标 → 错误。
- 采样窗口 > 1s → 警告。
- 帧回调中做重任务 → 错误。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 滚动基准用例：P99 帧时长 ≤ 阈值（25ms @60Hz / 12ms @120Hz）。
- Max 帧时长 ≤ 200ms。
- 帧时长分布 95% > 帧预算时阻塞合并。

**线上 SLO**：

- 滚动场景 P99 帧时长 < 25ms（60Hz）/ < 15ms（120Hz）。
- 冻屏率 < 0.05%（任意单帧 ≥ 700ms 的比例）。
- 平均掉帧率 < 5%。

## 10.总结与延伸

### 10.1 五条核心原则

1. **流畅是分布问题**：P95/P99/Max 优于均值——[§5.1 实验](#51-实验一均值掩盖抖动)给出 r=-0.87 的硬证据。
2. **每帧记录、原始保留**：聚合可放宽到 1s，但不要 5s/10s 窗口稀释抖动。
3. **动态适配刷新率**：不要硬编码 16.67ms；ARR 设备要主动调度刷新率。
4. **三方案组合校准**：① 帧时钟跑量 + ② 系统 API 拆阶段 + ③ FrameTimeline/MetricKit 校准合成段。
5. **静态页面不忘**：配合 LooperPrinter / 卡顿监控做兜底，无回调 ≠ 无问题。

### 10.2 五个常见误区

1. **"均值 60 fps 就流畅"**：错（P99 才重要，[§00.5 案例](#005-贯穿案例短视频信息流均值高但用户骂事件)四周翻车的根源）。
2. **"高刷屏自动更流畅"**：错（应用层不优化无增益，且全程 120Hz 还多耗 30% 电）。
3. **"采样窗口 10s 够了"**：错（[§5.2](#52-实验二采样间隔精度) 证明抖动被稀释）。
4. **"无回调 = 无问题"**：错（静态页面是盲区，需 LooperPrinter 兜底）。
5. **"应用 FPS = 显示 FPS"**：错（[§5.4](#54-实验四frametimeline-揭露合成段隐性丢帧) 证明 OS 可能丢帧 11.8% 而应用层完全不知）。

## 一句话总结

> **FPS 是抖动游戏，不是均值游戏；是分布游戏，不是单点游戏；是系统协同游戏，不是应用独奏。  
> 把均值看板换成 P99，把 5s 窗口换成 1s，把硬编码帧预算换成动态读取，把"全程 120Hz"换成 ARR 智能调度——

> 而 §00.5 那个"4 周经验派 vs 5 天方法派"的反差，正是这条路径的最锋利证据。**
