## 00.5 贯穿案例：新闻 App"详情页打开 1.8 秒 + 评论列表 22fps"事件

> 本案例贯穿全文：§01 看懂代价、§02 拿到三阶段成本模型、§03/§04 用三方案+决策树定位、§05 用实验复盘、§06 给出分层策略闭环。

### 案例背景

某新闻 App V6.8 重构详情页（产品要求"功能更丰富"），上线后用户体验崩盘：

- **详情页打开 P95 = 1.8s**（之前 0.6s），用户大量"白屏"投诉。
- **评论列表滑动 FPS 仅 22**（之前 56），P99 帧时长 110ms。
- 详情页 cell 总创建时间长达 580ms（10 个 cell）。
- DAU 流失 6%、文章阅读完成率 -15%。
- 公司高层强力施压"必须立刻恢复"。

研发组初步反应："功能加多了肯定慢点，是产品需求。"——这是典型的"功能 vs 性能"误区。

### 经验派的 4 周折腾（典型反面教材）

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 把 LinearLayout 都改 ConstraintLayout（认为扁平就快）| 简单 cell 反而**慢 10%**（CL 自身 overhead），详情页快 5% |
| 第 2 周 | 全量异步 Inflate（认为异步就好）| 简单 cell 也异步，**Attach 闪烁 + 总耗时反增** |
| 第 3 周 | 用 setLayerType(LAYER_TYPE_HARDWARE) 加速所有 View | GPU 内存涨 80MB，低端机 OOM 率升 5× |
| 第 4 周 | 把列表 cell 高度固定（怀疑动态高度）| FPS 升到 26，但内容显示不全 |

**复盘**：四周折腾错在"听经验，没数据"。**ConstraintLayout 不是万能（简单场景反而慢）；异步 Inflate 不是万能（简单 cell 没收益还闪烁）；setLayerType 不是万能（吃显存）；固定高度不是万能（牺牲业务）**。每个所谓"经验"都需场景化验证——这正是 §00.5 案例反面教材的核心。

### 方法派的 6 天闭环

新接手的同学按本文方法论重做：

**Day 1（§02 三阶段成本模型 + §03 三方案）**：

- 方案②（FrameMetrics）：详情页首帧 INPUT=8ms / ANIM=12ms / LAYOUT=520ms / DRAW=80ms / SWAP=8ms。
- 方案①（自定义基类计时）：详情页 setContentView 耗时 380ms（XML 层级达 9 层）；评论 cell 层级 6 层。
- 方案③（FPS）：列表稳态 P99=110ms，远超 16.67ms 帧预算 6.6×。

→ **三阶段都有问题**：Inflate（380ms）+ Layout 每帧（45ms）+ Draw 每帧（22ms）。

**Day 2（§04 决策树 + 分类）**：

- 首屏慢 → Inflate 分支 → 9 层深 + 大量未必要 View（社交/评论/相关推荐都同步 inflate）。
- 滚动卡 → Layout 分支 → 6 层 cell + RelativeLayout 双测量 + 动态高度。
- 局部卡 → Draw 分支 → 评论头像 + 表情用 SVG 实时解析。

**Day 3-4（§06 分层策略）**：

- 第 1 层（节点收敛）：详情页根布局扁平化（9 层→4 层）；评论 cell ConstraintLayout（6 层→2 层）；相关推荐改 ViewStub 延迟。
- 第 2 层（Inflate 时机）：评论/广告/相关推荐改 AsyncLayoutInflater；详情页主体保持同步（用户感知）。
- 第 3 层（重绘）：固定背景区域 setLayerType；SVG 改 WebP；只对动画区域 invalidate(Rect)。
- 第 4 层（列表）：onBindViewHolder 减负（图加载/格式化全异步）；prefetchDataSource 提前测量。

**Day 5（§05 实验思路验证）**：构造 mock 数据用 Macrobenchmark 跑前后对比。

**Day 6（上线灰度）**：

### 上线效果

| 指标 | 经验派 4 周后 | 方法派 6 天后 |
|---|---|---|
| 详情页打开 P95 | 1.7s | **0.55s** |
| 评论列表稳态 FPS | 26 | **58** |
| 列表 P99 帧时长 | 100 ms | **18 ms** |
| 单 cell 创建时间 | 50 ms | **8 ms** |
| 内存峰值 | 380 MB | **220 MB**（setLayerType 滥用解除）|
| 详情页 DAU 流失 | -6% | **+1%**（恢复）|
| 文章阅读完成率 | -15% | **+3%** |

**核心洞察**：UI 优化不存在"银弹"——每个"经验招"都有场景边界。**方法派的胜利不是用了什么神奇技术，而是用数据驱动按场景选择**：复杂层级才扁平化，复杂页面才异步 Inflate，动画区才用 setLayerType。**经验招 + 错误场景 = 反向收益**。

### 案例如何串起本文

- **§01 现象与代价** ▶▶ 业务损失映射：DAU -6%、阅读完成率 -15%。
- **§02 三阶段模型** ▶▶ 案例 Inflate/Layout/Draw 三阶段同时有问题，正是模型存在的理由。
- **§03 三方案组合** ▶▶ 单一方案看不到全貌，必须 ①②③ 配合。
- **§04 决策树** ▶▶ 三个症状走三条不同分支，对应三种治法。
- **§05 求证实验** ▶▶ §5.1 扁平化（场景边界）+ §5.2 异步 Inflate（场景边界）+ §5.4 列表复用 + §5.5 声明式 UI 都在案例中变现。
- **§06 分层策略** ▶▶ "节点→Inflate→重绘→列表"四层正是案例落地路径。

## 01.问题域定义

### 1.1 现象与代价

UI 性能问题的用户感知很直接：

- **页面打开慢**：点击后白屏 / 等待，启动期 Inflate 慢。
- **滚动不流畅**：列表滑动卡顿，每个 cell 创建 / 测量耗时长。
- **切换迟钝**：Activity / ViewController 之间切换有卡顿。
- **键盘弹出卡顿**：弹键盘时整个布局重新测量。
- **旋转 / 折叠后慢**：屏幕配置变化触发整树重新 Layout。

**业务代价（行业实测数据）**：

- 头部 App：列表 P99 帧时长降 20ms，滑动留存 +1%。
- 启动期 inflate 优化能让首屏可见时间 -200-500ms。
- UI 卡顿是用户主观投诉最直接的来源（"卡"占投诉 30%+）。

> ▶▶ **回扣 §00.5 案例**：新闻 App 详情页 P95 1.8s + 列表 22fps 直接导致 DAU -6% + 阅读完成率 -15%——**UI 性能 = 业务 KPI 不是夸张说法**。10 个 cell 创建 580ms 也精准对应"启动期 inflate 优化能让首屏 -200-500ms"的行业基准。

### 1.2 度量准则

按 [`卷零·02 §3`](../00.公共方法论/02.跨平台指标体系.md) 指标体系：

**资源视角（USE）**：与渲染篇同。

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 首屏 inflate 时长 | 从 setContentView 到 measure 完成 | < 100ms |
| 单 cell 创建耗时 | onCreateViewHolder | < 5ms |
| 单 cell 绑定耗时 | onBindViewHolder | < 8ms |
| Layout 单次耗时 | measure + layout | < 帧预算 60% |
| Draw 单次耗时 | onDraw | < 帧预算 30% |

**用户感知（APDEX）**：与渲染篇同。

### 1.3 行业基准与目标

| 平台 | 首屏 inflate | 单 cell 创建 | Layout 复杂度 |
|---|---|---|---|
| Android | < 100ms | < 5ms | 树深 ≤ 8 |
| iOS | < 80ms | < 5ms | 嵌套 ≤ 10 |
| Web | < 200ms（含 CSS）| < 5ms | DOM 节点 ≤ 1500 |
| 嵌入式 | 视设备 | varies | 严格规划 |

### 1.4 反直觉问题清单

带着这些问题阅读：

1. 减少 View 层级一定能让渲染更快吗？
2. ConstraintLayout 一定比 LinearLayout 嵌套快吗？
3. 异步 inflate 是不是总比同步快？
4. wrap_content 真的慢吗？
5. RelativeLayout 真的会"测量两次"吗？
6. View 复用一定能加速滚动吗？
7. 软件渲染（disable hardware acceleration）什么时候比 GPU 快？
8. 页面层级 5 vs 10 实测差多少？

## 02.第一性原理

### 2.1 UI 优化本质

**一句话定义**：

> **UI 优化 = 减少"主线程产出一帧"所需的工作量，把 Layout / Draw / Inflate 三大开销压到帧预算之内**。

这句话隐含三个不可商量的物理约束：

**约束一：UI 工作量与"节点数"直接相关**

无论 View / UIView / DOM / LVGL Object，UI 都是一棵树。Measure / Layout / Draw / Compose 都是树形递归算法。**节点数越多，单帧成本越高**（详见 [`卷三·01 §5.1`](01.渲染管线与原理.md) 实验）。

**约束二：UI 工作分摊在三个时间窗口**

```
   ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
   │ ① Inflate 阶段  │    │ ② 帧产出阶段    │    │ ③ 重绘阶段      │
   │ 仅创建时一次    │    │ 每帧执行       │    │ 局部触发        │
   │ 影响首屏时长   │    │ 影响 FPS       │    │ 影响交互流畅     │
   └────────────────┘    └────────────────┘    └────────────────┘
```

**这三个阶段的优化手段完全不同**，不能混为一谈：

- Inflate 慢 → 异步 inflate / 缓存 / ViewStub
- 帧产出慢 → 减少层级 / 简化 onDraw
- 重绘慢 → 局部 invalidate / 合理的更新粒度

**约束三：UI 工作在主线程上执行**

UI 操作必须在主线程（详见 [`卷三·01 §2.1`](01.渲染管线与原理.md)）。这意味着：

- UI 优化的每一毫秒都在和"帧预算"赛跑。
- 无法靠增加 CPU 核数加速。
- 必须通过"减"或"延"，而不是"并"。

### 2.2 三阶段成本模型

```
   单帧主线程总成本 = Inflate（首次） + Layout × N + Draw × M
   
   N = 当前帧需要重测量的节点数
   M = 当前帧需要重绘的节点数
```

**关键洞察**：

- **Inflate 是一次性成本**（创建时一次），但成本最高（每个节点要解析 XML / 反射 / 创建对象）。
- **Layout 是每帧成本**，与树深度指数相关（详见渲染篇 §5.1）。
- **Draw 是每帧成本**，与重绘范围 + Shader 复杂度相关。

**优化优先级**（按"成本 × 频次"）：

```
   优先级 = 单次成本 × 触发频次

   ① Layout per 帧：成本 5-50ms × 60 帧/秒 = 300-3000 ms/秒（最高）
   ② Draw per 帧：成本 1-20ms × 60 帧/秒 = 60-1200 ms/秒
   ③ Inflate：成本 50-500ms × 1 次 = 50-500 ms（一次性，但首屏关键）
```

**三类问题的物理来源**：

```
   ┌────────────────────────────────────────────┐
   │ A. 层级过深：树形递归成本指数级               │
   │    根因：嵌套布局 / RelativeLayout 误用       │
   ├────────────────────────────────────────────┤
   │ B. 重绘范围过大：onDraw 被调用太多 / 太大     │
   │    根因：父布局 invalidate 全量；Shader 复杂  │
   ├────────────────────────────────────────────┤
   │ C. Inflate 慢：XML 解析 / 反射 / 资源加载    │
   │    根因：层级深 + 复杂控件 + 大量资源          │
   └────────────────────────────────────────────┘
```

> ▶▶ **回扣 §00.5 案例**：新闻 App 同时命中三类——A（详情页 9 层 + 评论 6 层 RelativeLayout）+ B（SVG 实时解析 + 大背景 invalidate）+ C（首屏全量同步 inflate）。**经验派的失败正是因为不分类——只治一类问题不可能解决三类共存的真实场景**。三阶段模型存在的价值正是"分而治之"。

### 2.3 跨平台同构原理

所有平台的 UI 都是"声明式 / 命令式 + 树 + 渲染管线"：

```
   通用 UI 模型：

      [声明 UI 树]   →   [Inflate 创建实例]   →   [Layout]   →   [Draw]   →   [Compose]
       声明文件             实例化对象               位置确定        画到 canvas    上屏
       XML/JSX/SwiftUI    Java 对象/JS DOM/UIView   Measure+Layout  onDraw         GPU 合成
```

每个平台都必须解决：

| 抽象问题 | 解决什么问题 |
|---|---|
| 树构造 | 把声明转为运行时对象 |
| 测量 | 计算每个节点尺寸 |
| 布局 | 确定每个节点位置 |
| 绘制 | 生成像素 |
| 重绘 | 局部更新机制 |

**跨平台术语对照**

| 通用术语 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 树根 | View | UIView | DOM | LVGL Obj |
| 节点 | View / ViewGroup | UIView / Layer | Element | Obj |
| 测量 | onMeasure | sizeThatFits / layoutSubviews | reflow | 自定义 |
| 布局 | onLayout | layoutSubviews | reflow | 自定义 |
| 绘制 | onDraw | drawRect / Layer.draw | paint | 自定义 |
| 重绘 | invalidate | setNeedsDisplay | requestAnimationFrame + DOM 修改 | invalidate |
| 异步实例化 | AsyncLayoutInflater | dispatchqueue 创建 | Web Worker | 不常见 |

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 声明方式 | XML / Compose | XIB / Storyboard / SwiftUI | HTML / CSS / JSX | C 代码 / LVGL |
| 实例化成本 | 高（XML 解析 + 反射） | 中（XIB 高，代码低）| 中（DOM 创建）| 低 |
| 树深限制 | 经验 ≤ 8 | 经验 ≤ 10 | 浏览器有上限（巨深会卡）| 严格 |
| 重绘粒度 | View 级 | Layer 级 | Element 级 | Obj 级 |
| 异步 inflate | AsyncLayoutInflater | 不常用 | 自动（浏览器） | 罕见 |
| 主流模式 | RecyclerView 复用 | UITableView 复用 | 虚拟滚动 | 列表组件 |

> 后续遇到平台特化点回引本节。

## 03.度量与采集

### 3.1 三类采集方案的本质

所有平台的 UI 性能采集方案，本质上只有 3 类：

```
   ① 节点级采集（每个 View 的测量 / 布局耗时）
                ② 阶段级采集（FrameMetrics / DevTools 阶段拆解）
                            ③ 全局级采集（FPS、INP 等用户感知）
```

---

**① 节点级采集（精细到单个 View）**

**核心原理（一句话）**：在 onMeasure / onLayout / onDraw 等关键回调上插桩，记录每个节点的耗时。

**工作机理**：

```java
// 自定义 View 基类做计时
public class TimedView extends View {
    @Override
    protected void onMeasure(int wMs, int hMs) {
        long t = System.nanoTime();
        super.onMeasure(wMs, hMs);
        Tracer.record("Measure", getClass().getSimpleName(), System.nanoTime() - t);
    }
}
```

或者 ASM / Aspect 编译期注入。

**物理本质**：把"哪个 View 慢"做到颗粒级追踪。

**为什么这样有效**：直接定位"罪魁祸首 View"。

**局限根源**：开销大；侵入式（要求所有 View 用基类或插桩）；线下用为主。

**适用边界**：性能分析阶段、定向排查特定页面。

---

**② 阶段级采集**

**核心原理（一句话）**：使用系统提供的"阶段级"数据，看 Layout / Draw / Sync 各阶段耗时（详见 [`卷三·01 §3.1`](01.渲染管线与原理.md)）。

**适用边界**：所有应用线上监控的核心方案。

---

**③ 全局级采集**

**核心原理（一句话）**：用 FPS / INP / TTI 等用户感知指标。

**适用边界**：监控仪表盘、SLO 跟踪。

---

**三种方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 节点级 | View 回调 | 单 View | 高 | 中（需基类）| ❌（线下） | 侵入式 |
| ② 阶段级 | OS 提供 | 阶段 | 极低 | 中（API 不同）| ✅ | 颗粒度由系统决定 |
| ③ 全局级 | 帧时钟 / 用户事件 | 帧 / 操作 | 极低 | 高 | ✅ | 不能定位单一 View |

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| 哪个 View 慢 | ✅ | ❌ | ❌ |
| 哪个阶段慢 | 部分 | ✅ | ❌ |
| 用户感知 | ❌ | 间接 | ✅ |
| Inflate 时长 | ✅ | 部分 | 间接 |

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web |
|---|---|---|---|
| 节点级 | 自定义基类 / Lithium / Choreographer 触发 | UIViewSubclass + signpost | DevTools Performance + Chrome trace |
| 阶段级 | FrameMetrics | os_signpost intervals | Performance.timing |
| 全局级 | FPS + Vitals | MetricKit Hitches | Web Vitals |
| Layout 检视 | Layout Inspector | View Debugger | DevTools Elements |
| Inflate 时长 | LayoutInflater 打点 | UIView creation 打点 | Performance Mark |

### 3.4 数据可信度评估

| 数据 | 可信度 | 偏差来源 |
|---|---|---|
| 单 View 耗时 | 高（< 1%）| 插桩开销 |
| 阶段时长 | 高 | OS 直接暴露 |
| FPS / INP | 高 | 帧/事件级 |
| Inflate 耗时 | 中 | 启动期受调度抖动影响大 |

## 04.归因方法

### 4.1 UI 问题决策树

```
UI 性能问题
   │
   ├── 首屏慢（Inflate）──▶ 减少节点 / 异步化 / 缓存
   │
   ├── 滚动卡（每帧 Layout）──▶ 减层级 / 复用 / 预计算
   │
   ├── 局部交互卡（Draw）──▶ 局部 invalidate / Shader 优化
   │
   └── 切换 / 旋转后慢 ──▶ 重新构建成本（少触发 / 缓存中间状态）
```

> ▶▶ **回扣 §00.5 案例**：新闻 App 的三个症状精准走三条决策树分支——
> - **详情页打开 1.8s** → Inflate 分支 → 减节点 + ViewStub + 异步 inflate（仅复杂部分）。
> - **列表滑动 22fps** → 滚动每帧 Layout 分支 → cell 扁平化 + RelativeLayout 改 ConstraintLayout + 固定高度。
> - **评论局部卡** → Draw 分支 → SVG 改 WebP + 固定背景 setLayerType。
>
> **同一个事件 3 个症状 3 条路径**——决策树的价值是阻止"一招治万病"。

### 4.2 布局复杂度归因

布局成本主要由三个因素决定：

```
   布局成本 = 节点数 × 单节点测量成本 × 重测量次数
```

**每个因素的优化手段**：

- **节点数**：用 `<merge>` / 扁平化 / ConstraintLayout / SwiftUI 等。
- **单节点测量成本**：避免复杂的 onMeasure 逻辑；用简单 LayoutManager。
- **重测量次数**：避免触发整树重测量（如不要在 onMeasure 中改 child 的 LayoutParams）。

**典型反模式**：

| 反模式 | 影响 | 修复 |
|---|---|---|
| 嵌套 LinearLayout 5 层以上 | 测量指数增长 | 用 ConstraintLayout 扁平化 |
| 嵌套 RelativeLayout | 双次测量 | 用 ConstraintLayout |
| wrap_content + match_parent 混用 | 多次测量 | 明确尺寸 |
| 在 onMeasure 中调用 setLayoutParams | 触发祖先重新测量 | 改用 onSizeChanged |

### 4.3 重绘范围归因

**关键观察**：`invalidate()` 调用一个 View 会让从该 View 到 GPU 之间的所有层都重绘。如果调用根 View，等于全屏重绘。

**优化思路**：

- 用最小粒度的 invalidate（带 Rect 参数）。
- 把"经常变化"的 View 与"静态"的 View 分到不同 layer。
- 用 setLayerType 把静态部分 cache 起来。

**Web 同等概念**：避免 layout thrash。CSS 中 `will-change: transform` 把元素提升到独立 layer。

### 4.4 Inflate 性能归因

Inflate 慢的根因：

| 根因 | 占比 | 修复 |
|---|---|---|
| XML 节点多 | 主要 | 扁平化 / 拆 ViewStub |
| 反射创建 View | 次要 | 用代码直接 new（牺牲灵活性）|
| 资源加载（drawable / 字符串） | 次要 | 异步预加载 |
| 自定义 View 的 init 重 | 视情况 | 简化 init |

**异步 Inflate 的代价**：

- AsyncLayoutInflater 限制：Inflate 后的 View 不能含 Handler / Looper（部分场景受限）。
- 异步 Inflate 也要付出"创建对象的总时间"，只是把它移出主线程；如果用户已经看到 UI 才完成，反而引入闪烁。

## 05.求证实验 ⭐

### 5.1 实验一：扁平化收益

**Step 1 — 原始观察**

工程经验都说"扁平化布局快"，但**到底快多少？什么时候必须扁平化？**

**Step 2 — 提出疑问**

> **同一组 UI 用 5 层嵌套 LinearLayout 实现 vs 用 ConstraintLayout 单层实现，性能差异多大？**

**Step 3 — 形成假设**

**H₁**：扁平化 ConstraintLayout 单帧测量耗时是嵌套 LinearLayout 的 30-50%。  
**H₀**：差异可忽略。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 |
| UI 内容 | 同一卡片：头像 + 标题 + 副标题 + 3 按钮 |
| 实现 A | 5 层嵌套 LinearLayout（共 12 View）|
| 实现 B | 1 层 ConstraintLayout（共 8 View）|
| 主指标 | 单卡片测量 + 布局耗时 |
| 重复 | 1000 次 |

**Step 5 — 实测数据**

| 实现 | View 数 | 测量耗时（μs）| 布局耗时（μs）| 总耗时（μs）|
|---|---|---|---|---|
| A 嵌套 LinearLayout | 12 | 380 | 280 | 660 |
| B ConstraintLayout | 8 | 220 | 165 | 385 |

**Step 6 — 验证 / 修正**

- 扁平化耗时是嵌套的 58%，节省 42%。
- 验证 H₁。

**Step 7 — 提炼结论**

> **扁平化布局（ConstraintLayout）相比 5 层嵌套 LinearLayout 节省 ~40% 测量布局耗时。**

工程意义：

- 复杂 cell 应用 ConstraintLayout。
- 简单单层 cell 用 LinearLayout 更快（ConstraintLayout 测量算法本身有 overhead）。
- 不要"为了扁平而扁平"，单层 LinearLayout 已经最快。

**Step 8 — 边界**

- 简单布局（< 5 节点）ConstraintLayout 反而比 LinearLayout 慢。
- iOS 用 SwiftUI vs UIKit Auto Layout 对应同样规律。
- Web 用 Grid / Flexbox 替代深嵌套 div。

> ▶▶ **回扣 §00.5 案例**：经验派第 1 周"把所有 LinearLayout 改 ConstraintLayout" 完全踩中本实验"简单布局 ConstraintLayout 反而慢"的反例——简单 cell 反而慢 10%。**这是把"经验招"硬套到所有场景的典型反面教材**。方法派 Day 3 只对复杂层级（详情页 9 层、cell 6 层）扁平化，简单部分保留 LinearLayout，体现了"按场景选择"的工程素养。

---

### 5.2 实验二：异步 inflate 收益

**Step 1 — 原始观察**

异步 Inflate 听起来"明显有用"，但**实际效果如何？什么时候不该用？**

**Step 2 — 提出疑问**

> **AsyncLayoutInflater 在不同复杂度页面上的实际启动收益是多少？**

**Step 3 — 形成假设**

**H₁**：复杂页面（节点 > 50）异步 inflate 能减少首屏可见时间 30-50%；简单页面（节点 < 20）几乎无收益。  
**H₀**：异步 inflate 总是有收益。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 测试场景 | 三种页面：简单（10 节点）、中等（30 节点）、复杂（80 节点）|
| 实现 A | 同步 LayoutInflater |
| 实现 B | AsyncLayoutInflater |
| 主指标 | TTID（首帧可见时间）|

**Step 5 — 实测数据**

| 页面复杂度 | 同步 (ms) | 异步 (ms) | 节省 |
|---|---|---|---|
| 简单（10 节点）| 25 | 22 | 12% |
| 中等（30 节点）| 80 | 55 | 31% |
| 复杂（80 节点）| 220 | 130 | 41% |

**Step 6 — 验证 / 修正**

- 复杂页面收益显著（30-40%）。
- 简单页面收益小（10%），可能不值得引入异步复杂度。
- 验证 H₁。

**Step 7 — 提炼结论**

> **异步 Inflate 在复杂页面（节点 > 30）有显著收益（30-40%）。  
> 简单页面收益不大，不必为了异步而异步。**

工程意义：

- 首屏复杂页面值得引入。
- 列表 cell 等高频小节点不要用异步（复用机制已经够快）。
- 异步 inflate 完成后再 attach 到 ViewGroup，如果用户已经看到 UI 会闪烁。

**Step 8 — 边界**

- AsyncLayoutInflater 不支持含 Handler 的自定义 View。
- 复杂的 onCreateView 中如果有 IO 仍会卡子线程，不能完全替代"减少初始化"。

---

### 5.3 实验三：局部重绘收益

**Step 1 — 原始观察**

工程师都用 `view.invalidate()` 触发重绘，但**有 `invalidate(Rect)` 的局部重绘版本，实际收益多大？**

**Step 2 — 提出疑问**

> **同一场景下，全量 invalidate 与局部 invalidate 的 GPU 帧时长差异多大？**

**Step 3 — 形成假设**

**H₁**：局部 invalidate 在大屏复杂场景下能节省 30-70% GPU 帧时长。  
**H₀**：差异可忽略（GPU 都在硬件加速）。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 1080P |
| 场景 | 大背景 + 中央小动画区域 |
| 实现 A | 整 View invalidate |
| 实现 B | 仅动画区域 invalidate(Rect) |
| 主指标 | GPU 帧时长（FrameMetrics SWAP_BUFFERS_DURATION）|

**Step 5 — 实测数据**

| 实现 | GPU 时长（ms）| 总帧时长 |
|---|---|---|
| A 全量 | 6.2 | 14.8 |
| B 局部（动画区 200×200）| 1.8 | 9.5 |

**Step 6 — 验证 / 修正**

- 局部 invalidate GPU 时长降到 30%，整帧时长降 36%。
- 验证 H₁。

**Step 7 — 提炼结论**

> **局部 invalidate 能让 GPU 工作量从 100% 屏幕降到指定区域，节省 50-70% GPU 时间。**

工程意义：

- 自定义动画 View 必须用 invalidate(Rect)。
- 用 clipRect 限制 onDraw 的绘制范围。
- Web 用 transform 或 will-change 让浏览器只重绘受影响层。

**Step 8 — 边界**

- 如果父 View 已经触发 invalidate，子 View 的局部 invalidate 无效（被父 View 整体重绘覆盖）。
- 在已经"足够流畅"的小屏上收益不明显。

---

### 5.4 实验四：列表复用与 onBindViewHolder 异步预测算

**Step 1 — 原始观察**

[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 中评论列表 22fps，单 cell 创建 50ms。**复用机制 + onBindViewHolder 异步能改善多少？**

**Step 2 — 提出疑问**

> **同一列表场景，"无复用 + 同步 bind" vs "复用 + 同步 bind" vs "复用 + 异步预测算 bind"的滑动 FPS 差异？**

**Step 3 — 形成假设**

**H₁**：复用比无复用 FPS +30-50%；异步预测算再 +20-30%，可让中端机稳定 60fps。  
**H₀**：复用够了，异步预测算无必要。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 + 红米 Note 11 |
| 场景 | 100 个 cell 快速滑动 |
| 实现 A | 无复用（每次 new ViewHolder）|
| 实现 B | RecyclerView 默认复用 |
| 实现 C | B + onBindViewHolder 中所有 IO/格式化 异步 |
| 主指标 | 稳态 FPS、P99 帧时长 |

**Step 5 — 实测数据**

| 实现 | Pixel 6 FPS | Pixel 6 P99 | 红米 FPS | 红米 P99 |
|---|---|---|---|---|
| A 无复用 | 35 | 95 ms | 18 | 220 ms |
| B 复用 | 52 | 28 ms | 38 | 65 ms |
| C 复用 + 异步预测算 | **58** | **18 ms** | **56** | **20 ms** |

**Step 6 — 验证 / 修正**

- B 比 A 提升显著（复用是基础设施）。
- C 比 B 再提升 30-50%，中端机从 38→56 fps，达到流畅。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **复用是列表性能的基础；onBindViewHolder 异步预测算是中低端机稳定 60fps 的关键。  
> 高端机两者差距小，中端机差距巨大。**

工程意义：

- 任何高频列表（> 20 cell）必须复用。
- onBindViewHolder 中的图加载、文本格式化、时间转换等都应异步预测算。
- iOS UICollectionView 的 `prefetchDataSource` 是等价机制。

**Step 8 — 边界**

- 复用要求 cell 类型有限（< 10 种）；类型过多复用率下降。
- 异步预测算要在 ViewHolder lifecycle 内完成，避免泄漏。

### 5.5 实验五：声明式 UI（Compose/SwiftUI）vs 命令式 UI 的真实性能

**Step 1 — 原始观察**

Compose / SwiftUI 被宣传"性能更好"，但**实测真比 XML/UIKit 快吗？什么场景？**

**Step 2 — 提出疑问**

> **同一复杂页面（30 节点）用 XML/UIKit vs Compose/SwiftUI 实现，首屏时长、内存、滑动 FPS 差异？**

**Step 3 — 形成假设**

**H₁**：Compose/SwiftUI 首屏略慢（运行时构建），稳态性能相当或略优（重组粒度细）；内存略高（diff 算法）。  
**H₀**：声明式 UI 全面更好。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 |
| 页面 | 列表 + 详情卡片（30 节点）|
| 实现 A | XML + RecyclerView（Android）/ UIKit + UITableView（iOS） |
| 实现 B | Compose LazyColumn（Android）/ SwiftUI List（iOS） |
| 主指标 | 首屏 TTI、滑动 FPS、内存峰值 |

**Step 5 — 实测数据**（Android）

| 实现 | 首屏 TTI | 滑动 FPS | 内存峰值 |
|---|---|---|---|
| A XML + RecyclerView | 380 ms | 58 | 110 MB |
| B Compose LazyColumn | 480 ms | 58 | 135 MB |
| B + Baseline Profiles | 320 ms | 60 | 135 MB |

**Step 6 — 验证 / 修正**

- Compose 默认首屏略慢（运行时构建）。
- 启用 Baseline Profiles 后首屏反而比 XML 快 16%。
- 内存略高 23%（diff 算法 + 重组开销）。
- 部分拒绝 H₀（不是"全面更好"，需要配套）。

**Step 7 — 提炼结论**

> **声明式 UI 不是默认性能更好，但配合 Baseline Profiles 后可超越命令式 UI。  
> 内存代价 +20% 是普遍现象，低端机需评估。**

工程意义：

- 新项目优先用声明式 + Baseline Profiles。
- 老项目混合架构（重要页面声明式，性能敏感页面保留命令式）。
- 内存敏感场景慎用。

**Step 8 — 边界**

- Compose 跨 View 系统互操作有开销。
- SwiftUI 在 iOS 14 性能较差（建议 iOS 15+）。
- 复杂动画 SwiftUI 不如 UIKit 灵活。

### 5.6 五大实验启示

```
   扁平化收益          → 复杂布局 -40%（简单反而慢）       ─┐
                                                            │
   异步 Inflate        → 复杂页面 -30-40% TTID（简单无益） │
                                                            │
   局部重绘            → -50-70% GPU 时长                   ├─▶ UI 优化 = 减节点 + 拆首屏 + 限重绘 + 复用 + 选对范式
                                                            │
   列表复用 + 异步     → 中端机 FPS 38→56                  │
                                                            │
   声明式 vs 命令式 UI → 配 Baseline Profiles 可超越          ─┘
```

**统一启示**：

- **五大维度都有量化收益**：层级、Inflate、重绘范围、复用、UI 范式。
- **没有银弹**：每个优化都有场景边界，简单场景上"经验招"可能反向收益。
- **数据驱动**：每个优化必须有 A/B 验证。
- **复用是高频场景基础设施**：列表必须用。
- **声明式 UI 是未来**：但需配套基础设施（Baseline Profiles）。

## 06.优化策略深化

> 本节回答四个递进问题：**①如何让节点数收敛？②如何让 Inflate 不卡首屏？③如何让重绘范围最小？④如何让列表稳定 60fps？**  
> 与传统 UI 优化清单不同，本文按"治根 → 治首屏 → 治帧率 → 治长尾"分层施治，每一层都是上一层的延伸。

### 6.1 第一层：节点数收敛（治根）

**核心命题**：[§2.2 三阶段成本模型](#22-三阶段成本模型) 证明节点数决定所有阶段的物理上限。这一层不解决，所有上层优化都是补丁。

**策略 1.1：复杂层级用 ConstraintLayout / SwiftUI**

- **机理**：[§5.1 实验](#51-实验一扁平化收益) 证明 5 层嵌套节省 42%。
- **代码**：

```xml
<!-- 反例：5 层嵌套 LinearLayout -->
<LinearLayout orientation="vertical">
    <LinearLayout orientation="horizontal">
        <ImageView .../>
        <LinearLayout orientation="vertical">
            <TextView .../>
            <LinearLayout orientation="horizontal">
                <TextView .../>
                <Button .../>
            </LinearLayout>
        </LinearLayout>
    </LinearLayout>
</LinearLayout>

<!-- 正例：ConstraintLayout 单层 -->
<androidx.constraintlayout.widget.ConstraintLayout>
    <ImageView app:layout_constraintStart_toStartOf="parent"/>
    <TextView app:layout_constraintStart_toEndOf="@id/avatar"/>
    ...
</androidx.constraintlayout.widget.ConstraintLayout>
```

- **收益**：[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 详情页 9 层→4 层、cell 6 层→2 层。
- **边界**：简单布局（< 5 节点）ConstraintLayout 自身 overhead 反而拖累，**只对复杂场景用**——这是 [§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--evening-列表-22fps事件) 经验派第 1 周翻车的关键教训。

**策略 1.2：`<merge>` 消除冗余根节点**

- **机理**：自定义 ViewGroup 内 include 时，根节点容易冗余。`<merge>` 让 inflate 直接挂到 parent。
- **代码**：

```xml
<!-- 自定义 view 内部 -->
<merge xmlns:android="...">
    <ImageView .../>
    <TextView .../>
</merge>
```

- **收益**：单 cell 减少 1-2 个冗余层。
- **边界**：仅适用于"父布局已确定"的场景。

**策略 1.3：ViewStub 延迟加载稀有视图**

- **机理**：错误页/空态页/高级菜单等场景大多数时间不显示，ViewStub 把 inflate 推迟到真正需要时。
- **代码**：

```xml
<ViewStub
    android:id="@+id/error_stub"
    android:layout="@layout/error_layout"
    android:inflatedId="@+id/error_view"/>
```

```kotlin
// 仅在错误时 inflate
if (hasError) findViewById<ViewStub>(R.id.error_stub).inflate()
```

- **收益**：首屏节点 -20-30%。
- **边界**：ViewStub 自身极轻量，但 inflate 时仍卡主线程，复杂错误页应配合异步。

**策略 1.4：声明式 UI（Compose/SwiftUI）**

- **机理**：[§5.5 实验](#55-实验五声明式-uicomposeswiftuivs-命令式-ui-的真实性能) 声明式 + Baseline Profiles 可超越命令式。
- **代码**：

```kotlin
@Composable
fun ArticleCard(article: Article) {
    Card { Column {
        AsyncImage(model = article.cover)
        Text(article.title)
    }}
}
```

- **收益**：首屏 -16%（启用 Baseline Profiles），代码简洁。
- **边界**：内存 +20%；老项目混合架构需评估。

### 6.2 第二层：Inflate 时机优化（治首屏）

**核心命题**：[§2.2](#22-三阶段成本模型) 中 Inflate 是一次性但成本最高的开销。这一层目标：**让首屏只 Inflate 关键内容**。

**策略 2.1：异步 Inflate 复杂页面**

- **机理**：[§5.2 实验](#52-实验二异步-inflate-收益) 复杂页面 -30-40% TTID。
- **代码**：

```kotlin
val inflater = AsyncLayoutInflater(this)
inflater.inflate(R.layout.complex_page, null) { view, _, _ ->
    parent.addView(view)
}
```

- **收益**：[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 评论/广告/相关推荐区异步 Inflate，详情页首屏 -300ms。
- **边界**：简单页面（< 20 节点）异步反而引入闪烁——[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--evening-列表-22fps事件) 经验派第 2 周翻车正是因为对所有 cell 都异步。

**策略 2.2：分级 Inflate（首屏只渲染可见部分）**

- **机理**：用户首屏只看到屏幕第一屏，下方内容可推迟。
- **代码**：

```kotlin
// 首屏只 inflate 标题区
val titleView = inflater.inflate(R.layout.article_title, parent)
// 滚动到可见时 inflate 正文
recyclerView.setOnScrollListener {
    if (becomesVisible(commentArea)) commentInflater.inflateAsync()
}
```

- **收益**：首屏 Inflate 时间 -50%。
- **边界**：滚到时的 inflate 可能引入卡顿，需配合占位骨架。

**策略 2.3：预 Inflate 池（高频复用场景）**

- **机理**：把常用 cell 提前 inflate 到池，使用时直接取。
- **代码**：

```kotlin
object ViewPool {
    private val pool = mutableListOf<View>()
    fun preInflate(count: Int) {
        repeat(count) {
            executor.submit {
                val v = AsyncLayoutInflater(context).inflate(R.layout.cell, null)
                synchronized(pool) { pool += v }
            }
        }
    }
    fun acquire(): View? = synchronized(pool) { pool.removeFirstOrNull() }
}
```

- **收益**：首次使用近 0 inflate 耗时。
- **边界**：内存占用增加；要做容量上限。

**策略 2.4：用代码替代 XML（极致场景）**

- **机理**：XML 反射 + 解析占 Inflate 时间 60%+；代码直接 new 跳过解析。
- **代码**：

```kotlin
class FastCellView(context: Context) : LinearLayout(context) {
    init {
        addView(ImageView(context).apply { /* setup */ })
        addView(TextView(context).apply { /* setup */ })
    }
}
```

- **收益**：单 cell Inflate 时间 -50%。
- **边界**：牺牲布局可视化预览；不适合频繁变化的 UI。

### 6.3 第三层：重绘范围限制（治帧率）

**核心命题**：[§5.3 实验](#53-实验三局部重绘收益) 证明局部 invalidate 可省 50-70% GPU。这一层关键是**让重绘范围 = 真正变化的范围**。

**策略 3.1：用 invalidate(Rect) 替代 invalidate()**

- **机理**：[§5.3 实验](#53-实验三局部重绘收益) 数据。
- **代码**：

```java
// 反例：全 View 重绘
view.invalidate();

// 正例：仅动画区域
view.invalidate(animRect);
```

- **收益**：自定义动画 View GPU 时长 -70%。
- **边界**：父 View 触发整体 invalidate 时子 View 局部失效。

**策略 3.2：setLayerType 缓存静态部分（按场景使用）**

- **机理**：把"不变的复杂背景"提升为独立 layer，避免每帧重绘。
- **代码**：

```java
// 复杂静态背景
staticBgView.setLayerType(View.LAYER_TYPE_HARDWARE, null);
// 动画结束后恢复
staticBgView.setLayerType(View.LAYER_TYPE_NONE, null);
```

- **收益**：滚动场景 GPU 时长 -40%。
- **边界**：每层吃 GPU 内存（屏幕宽 × 高 × 4B）——[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 经验派第 3 周给所有 View 都 setLayerType 导致 OOM。

**策略 3.3:复杂 onDraw 优化**

- **机理**：onDraw 中避免 new 对象、避免复杂计算；用 Paint/Path 缓存。
- **代码**：

```java
// 反例
@Override protected void onDraw(Canvas canvas) {
    Paint p = new Paint();  // 每帧 new！
    canvas.drawCircle(x, y, r, p);
}

// 正例
private final Paint paint = new Paint();  // init 时创建
@Override protected void onDraw(Canvas canvas) {
    canvas.drawCircle(x, y, r, paint);
}
```

- **收益**：60fps 场景节省大量 GC。
- **边界**：onDraw 中的状态需注意线程安全。

**策略 3.4：SVG 改预渲染 WebP（针对低端机）**

- **机理**：SVG 解析在低端机 CPU 上慢；预渲染 WebP 解码硬件加速。
- **收益**：[§7.2 案例](#72-平台特异案例) 单 cell 创建 50ms→12ms。
- **边界**：失去矢量缩放优势；多分辨率需多份资产。

### 6.4 第四层：列表与高频场景治理（治长尾）

**核心命题**：列表是 UI 性能问题最集中的场景。[§5.4](#54-实验四列表复用与-onbindviewholder-异步预测算) 证明复用 + 异步预测算可让中端机稳定 60fps。

**策略 4.1：RecyclerView/UITableView 强制复用**

- **机理**：每 cell 创建 5-50ms，复用接近 0。
- **代码**（Android Room+RecyclerView）：

```kotlin
class ArticleAdapter : ListAdapter<Article, ArticleVH>(DIFF_CALLBACK) {
    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): ArticleVH {
        val view = LayoutInflater.from(parent.context).inflate(R.layout.cell, parent, false)
        return ArticleVH(view)
    }
    override fun onBindViewHolder(holder: ArticleVH, position: Int) {
        holder.bind(getItem(position))  // 轻量 bind
    }
}
```

- **收益**：列表必备项。
- **边界**：cell 类型过多（> 10）复用率下降。

**策略 4.2：onBindViewHolder 异步预测算**

- **机理**：[§5.4 实验](#54-实验四列表复用与-onbindviewholder-异步预测算) 中端机 FPS 38→56。
- **代码**：

```kotlin
override fun onBindViewHolder(holder: VH, position: Int) {
    val item = items[position]
    // 主线程仅 setText/setImage（轻量）
    holder.titleTv.text = item.title
    holder.imageIv.setImageDrawable(placeholder)
    // 重活异步
    asyncExecutor.submit {
        val formatted = formatTime(item.timestamp)  // 复杂格式化
        val bm = decodeImage(item.imageUrl)  // 图解码
        holder.itemView.post {
            if (holder.bindingAdapterPosition == position) {  // 检查 view 未被复用
                holder.timeTv.text = formatted
                holder.imageIv.setImageBitmap(bm)
            }
        }
    }
}
```

- **收益**：[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 列表 FPS 22→58。
- **边界**：异步回调需检查 position 防止填错。

**策略 4.3：固定 ViewType 高度（避免动态测量）**

- **机理**：动态高度需多次测量；固定高度可直接跳过。
- **代码**：

```kotlin
override fun onBindViewHolder(holder: VH, position: Int) {
    holder.itemView.layoutParams.height = FIXED_HEIGHT  // 类型确定时
}
```

- **收益**：滚动测量耗时 -30%。
- **边界**：内容必须能适配固定高度；否则牺牲业务。

**策略 4.4：prefetchDataSource / Prefetcher**

- **机理**：在 cell 即将出现前提前测量 + 加载。
- **代码**（Android RecyclerView）：

```kotlin
recyclerView.setItemViewCacheSize(20)  // 增加 cache
val layoutManager = LinearLayoutManager(context).apply {
    initialPrefetchItemCount = 4  // 提前 inflate 4 个
}
```

- **代码**（iOS）：

```swift
class MyVC: UIViewController, UICollectionViewDataSourcePrefetching {
    func collectionView(_ cv: UICollectionView, prefetchItemsAt indexPaths: [IndexPath]) {
        // 提前测量、加载
    }
}
```

- **收益**：快速滑动场景白屏率 -80%。
- **边界**：prefetch 范围过大反而抢资源。

### 6.5 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 | 对应策略 |
|---|---|---|---|---|---|
| 极高 | 复杂布局扁平化（按场景）| 单帧 -30-50% | 1-2 周 | 中（动画行为）| 1.1 |
| 极高 | 列表复用 + onBindViewHolder 异步 | 中端机 60fps | 1-2 周 | 中 | 4.1 + 4.2 |
| 极高 | 复杂页面异步 Inflate | TTID -30-40% | 1 周 | 中（特殊 View）| 2.1 |
| 高 | 局部 invalidate(Rect) | 动画类 GPU -50% | 几天 | 低 | 3.1 |
| 高 | ViewStub 延迟加载 | 首屏 -20-50ms | 几天 | 低 | 1.3 |
| 高 | 分级 Inflate（首屏可见）| 首屏 -50% | 1-2 周 | 中（占位骨架）| 2.2 |
| 高 | prefetchDataSource | 白屏率 -80% | 1 周 | 低 | 4.4 |
| 中 | setLayerType 静态部分 | 滚动 GPU -40% | 1 周 | 中（OOM）| 3.2 |
| 中 | onDraw 对象缓存 | GC 减少 | 几天 | 低 | 3.3 |
| 中 | SVG 改 WebP | 低端机 cell 创建 -75% | 1-2 周 | 低 | 3.4 |
| 中 | `<merge>` + 复用 layout | 单 cell -1-2 层 | 几天 | 低 | 1.2 |
| 中 | 声明式 UI + Baseline Profiles | 首屏 -16% | 2-4 周 | 中（内存）| 1.4 |
| 中 | 预 Inflate 池 | 高频场景近 0 inflate | 1-2 周 | 中（内存）| 2.3 |
| 中 | 固定 ViewType 高度 | 滚动测量 -30% | 1 周 | 中（业务）| 4.3 |
| 低 | 代码替代 XML | 单 cell -50% | 高 | 高（维护）| 2.4 |
| 极低 | 软件渲染替代硬件 | 几乎无收益 | 高 | 极高 | - |

**避免反向收益**：

- **简单布局用 ConstraintLayout**：[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 第 1 周翻车，简单场景反而慢 10%。
- **所有 cell 异步 Inflate**：[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 第 2 周翻车，引入闪烁。
- **全 View setLayerType**：[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 第 3 周翻车，GPU 内存 +80MB 导致 OOM。
- **固定高度牺牲业务**：[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 第 4 周翻车，内容显示不全。
- **过度扁平化**：用 ConstraintLayout 装单一 View，自身 overhead > 收益。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某电商列表 P99 帧时长 80ms（60Hz 屏），用户感知"滑动卡"。Android / iOS / Web 都有问题。

**现象**：

- Android：Trace 显示 Measure / Layout 占 60ms，cell 层级深。
- iOS：layoutSubviews 50ms。
- Web：reflow 45ms。

**度量与归因**：

三平台 cell 都有 5 层嵌套（D=11，按渲染篇 §5.1 公式总耗时指数级）。

**假设与求证**：

提出**统一假设**："cell 扁平化 + onBindViewHolder 异步预算"。

设计 A/B：

- A 组：原始嵌套
- B 组：扁平化（D=4） + 部分数据异步加载

**修复**：三端统一扁平化设计。

**验证**：

| 平台 | 优化前 P99 | 优化后 P99 | 降幅 |
|---|---|---|---|
| Android | 80 ms | 22 ms | 72% |
| iOS | 75 ms | 18 ms | 76% |
| Web | 70 ms | 25 ms | 64% |

**统一启示**：UI 优化跨端通用法则 = **扁平化 + 复用 + 异步**。

### 7.2 平台特异案例

**背景**：Android 应用在某低端机上 cell 创建慢（每个 cell 50ms），导致首屏空白时间长。

**现象**：列表前 10 个 cell 总创建时间 500ms，远高于行业基准。

**度量与归因**：

Profiler 显示 cell 中的 3 个 ImageView 都用了 SVG drawable，运行时反复 parse SVG。

**假设与求证**：

**假设**：SVG drawable 在低端机 CPU 上慢，应改为预渲染的 PNG / WebP。

**实验**：替换 SVG 为 WebP，单 cell 创建时间从 50ms 降到 12ms。

**修复**：低端机白名单 + 改图片格式 + 缓存。

**验证**：首屏可见时间从 800ms 降到 350ms。

**边界与上线策略**：高端机上 SVG 可接受（无差异），但代码维护两套图片资产。可考虑 SVG → 矢量绘制运行时缓存。

## 08.防劣化与长效治理

### 8.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
[Lint]      [自动化基准]     [线上 SLO]
```

### 8.2 编码期 Lint

- 嵌套布局深度 > 5 层 → 警告。
- onDraw 中 new 对象 → 错误。
- onMeasure / onLayout 中调用 setLayoutParams → 错误（会触发整树重测）。
- 复杂 cell 不用复用 → 警告。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 首屏 inflate 时长 ≤ 阈值。
- 列表滚动 P99 帧时长 ≤ 阈值（25ms @60Hz）。
- 单 cell 创建 + bind 时间 ≤ 13ms。

**线上 SLO**：

- 首屏 TTID < 1.5s。
- 滚动帧 P99 < 25ms（60Hz）。
- Inflate 失败率 < 0.01%。

## 10.总结与延伸

### 10.1 五条核心原则

1. **节点数决定 Layout 成本**：层级越深成本指数级上升，**复杂场景才扁平化**。
2. **三阶段差异化优化**：Inflate / Layout / Draw 用不同手段——[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 三阶段同时治才有效。
3. **复用胜过创建**：[§5.4](#54-实验四列表复用与-onbindviewholder-异步预测算) 中端机 FPS 38→56 的关键。
4. **局部胜过全量**：invalidate / 重绘 / inflate 都尽量局部，[§5.3](#53-实验三局部重绘收益) 给出 -50% GPU 的证据。
5. **数据驱动 + 按场景选择**：每个"经验招"都有场景边界，简单场景上经验招可能反向收益（[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 经验派 4 周翻车的根因）。

### 10.2 五个常见误区

1. **"减少层级总是好"**：错（简单 LinearLayout 比 ConstraintLayout 快，[§5.1](#51-实验一扁平化收益)）。
2. **"异步 Inflate 总有收益"**：错（简单页面收益小且引入闪烁，[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 第 2 周翻车）。
3. **"setLayerType 全开就加速"**：错（[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 第 3 周翻车，GPU 内存 +80MB 引发 OOM）。
4. **"声明式 UI 默认更快"**：错（[§5.5](#55-实验五声明式-uicomposeswiftuivs-命令式-ui-的真实性能) 需配 Baseline Profiles 才超越命令式）。
5. **"固定 cell 高度万能"**：错（[§00.5 案例](#005-贯穿案例新闻-app详情页打开-18-秒--评论列表-22fps事件) 第 4 周翻车，内容显示不全）。

## 一句话总结

> **UI 优化 = 减少主线程产帧成本，分四层施治：节点收敛→Inflate 时机→重绘范围→列表治理。  
> 没有银弹——每个"经验招"都有场景边界，简单场景上经验招可能反向收益。  
> 数据驱动 + 按场景选择 是 UI 优化的最高纪律。  
> §00.5 那个"4 周经验派 vs 6 天方法派"的反差，正是这条路径的最锋利证据。**
