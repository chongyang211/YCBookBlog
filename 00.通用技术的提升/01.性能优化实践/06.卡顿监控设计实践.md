## 01.卡顿整体概述

### 1.1 项目背景介绍

- App中卡顿让用户使用体验不佳
  - 在复杂的项目环境中，由于历史代码庞大，业务复杂，包含各种第三方库，所以在出现了卡顿的时候，很难定位到底是哪里出现了问题。
  - 即便知道是哪一个Activity/Fragment，也仍然需要进去里面一行一行看，动辄数千行的类再加上跳来跳去调来调去的，结果就是不了了之随它去了，实在不行了再优化吧。
- 卡顿可能引发未知问题
  - 卡顿还可能会引发一些未知的问题，比如卡顿会造成掉帧，会造成抖动，甚至还会造成ANR，对用户来说体验特别不好。简单来说，就是APP用起来有点卡……
- 排查卡顿问题非常费劲
  - 很多情况下卡顿不是必现的，它们可能与机型、环境、操作等有关，存在偶然性，即使发生了，再去查那如山般的logcat，也不一定能找到卡顿的原因，是我们自己的应用导致的还是其他应用抢占资源导致的？是哪些方法导致的？很难去回溯。


### 1.2 卡顿简单介绍

- 什么是卡顿
  - 界面呈现是指从应用生成帧并将其显示在屏幕上的动作。我们要确保用户能够流畅地与应用互动，应用呈现每帧的时间不应超过16ms，以达到每秒60帧的呈现速度。
  - 如果应用存在界面呈现缓慢的问题，系统会不得不跳过一些帧，这会导致用户感觉应用不流畅。我们将这种情况称为卡顿。
- UI线程执行时间
  - 在Android中，UI线程负责执行UI视图的布局、渲染等工作，UI在更新期间，如果UI线程执行时间超过了16ms，则就会产生丢帧的现象，大量的丢帧，就会造成卡顿，影响用户体验。
  - Android中规定，每秒可以执行60次屏幕刷新，当APP能够达到60帧/秒时，这种体验是优秀的，当帧率降低到40帧以下，甚至30帧以下，用户就可以感知到卡顿了。
- 时间计算公式
  - 公式（1秒刷新60次，那么每次刷新耗时16毫秒）：1000毫秒 / 60帧 = 16ms，关于帧率怎么查看呢？可以通过fps查看。


### 1.3 卡顿分类说明

- CPU紧张
  - 系统CPU资源紧张，分配给APP主线程（UI线程）的CPU时间片减少。
  - UI线程中执行了大量的耗时任务，导致了UI线程视图刷新工作的阻塞。
- 频繁GC
  - Android虚拟机频繁执行GC操作导致的卡顿。由于GC会占用大量的系统资源，同时GC过程中会产生UI线程停顿，从而产生卡顿。
- 过度绘制
  - 过度绘制产生卡顿。过度绘制会导致GPU执行时间变长，从而产生丢帧现象。


### 1.4 卡顿例子

- 卡顿其实分为直观的和微观两个方向的，举个例子
  - 比如用户点击了登录，预期是得到登录成功/失败的反馈，可现在没有页面刷新，实际的刷新耗时超出了预期，这就是直观的卡顿。
  - 比如用户在看股票，正常60秒刷新一次，可到了60秒，触发了刷新但是刷新处理逻辑耗时较长，导致新的数据在下一个60秒之前的第59秒才回来，用户基本无感知，主要说的是内部耗时的问题，这种情况可以粗略的理解为微观卡顿。


### 1.5 设计目标

- 设计目标要求
  - 对主线程操作进行了完全透明的监控，并能输出有效的信息，帮助开发分析、定位到问题所在，迅速优化应用。
  - 要求接入方便，外部开发者调用简单，非侵入式，简单的两行就打开监控，不需要到处打点，破坏代码优雅性。
  - 精准，输出的信息可以帮助定位到问题所在（精确到行），不需要像Logcat一样，慢慢去找。
- 卡顿优化点分析
  - 如果没能在16ms内完成这个过程，就会使屏幕重复显示上一帧的内容，即造成了卡顿。在这16ms内，需要完成视图树的所有测量、布局、绘制渲染及合成。而我们的优化工作主要就是针对这个过程的。



## 02.卡顿技术要点说明

### 2.1 UI卡顿产生原因

- UI卡顿通常产生的原因如下：
  - 系统CPU资源紧张，分配给APP主线程（UI线程）的CPU时间片减少。
  - UI线程中执行了大量的耗时任务，导致了UI线程视图刷新工作的阻塞。
  - Android虚拟机频繁执行GC操作导致的卡顿。由于GC会占用大量的系统资源，同时GC过程中会产生UI线程停顿，从而产生卡顿。
  - 过度绘制产生卡顿。过度绘制会导致GPU执行时间变长，从而产生丢帧现象。
- 举一些案例说明
  - 比如滑动列表时，如果在onBindViewHolder中执行了IO操作或复杂计算，就会导致滑动卡顿。
  - 比如在Activity启动时，如果在onCreate中执行了大量的初始化操作（如读取数据库、解析大型JSON），就会导致页面打开时卡顿。
  - 比如在自定义View的onDraw方法中创建了新的Paint或Path对象，每帧都会触发GC，导致绘制卡顿。
  - 比如WebView加载复杂网页时，JS执行和DOM渲染会占用主线程时间，导致整个页面响应变慢。
- 疑惑：为什么16ms是一个关键数值？
  - 答疑：人眼对动画的流畅感知阈值大约在60fps，即每秒60帧。1000ms/60 ≈ 16.67ms，所以每帧的渲染必须在约16ms内完成。
  - 论证：实际上在VSYNC信号驱动下，系统每16.6ms发出一次垂直同步信号，如果当前帧没有在这个时间窗口内完成渲染，就必须等到下一个VSYNC信号，这就造成了掉帧。
  - 结果：用户感知到的就是画面不流畅、滑动顿挫感、动画跳帧等现象。研究表明，连续掉帧超过3帧（约50ms延迟），用户就能明显感知到卡顿。



### 2.2 卡顿和ANR的关系

- 卡顿与ANR的关系
  - 产生卡顿的根本原因是UI线程不能够及时的进行渲染，导致UI的反馈不能按照用户的预期，连续、一致的呈现。
  - 产生卡顿的原因多种多样，很难一一列举，而ANR是Google人为规定的概念，产生ANR的原因最多也只有四个。
- 两者相关但不同维度
  - 事实上，长时间的UI卡顿是导致ANR最常见的原因；但另一方面，从原理上来看，两者既不充分也不必要，是两个维度的概念。
- 卡顿监控ANR准确吗
  - 一些卡顿监控工具，经常被拿来监控ANR（卡顿阈值设置为5秒），这其实很不严谨。
  - 首先，5秒只是发生ANR的其中一种原因（Touch事件5秒未被及时消费）的阈值，而其他原因发生ANR的阈值并不是5秒；
  - 另外，就算是主线程卡顿了5秒，如果用户没有输入任何的Touch事件，同样是不会发生ANR的，更何况还有后台ANR等情况。



### 2.3 什么是FPS流畅度

- 流畅度，是页面在滑动、渲染等过程中的体验。FPS（Frames Per Second）即每秒帧数，是衡量界面流畅度的核心指标。
  - Android系统要求每一帧都要在16ms内绘制完成，平滑的完成一帧意味着任何特殊的帧需要执行所有的渲染代码（包括framework发送给GPU和CPU绘制到缓冲区的命令）都要在16ms内完成，保持流畅的体验。
  - 如果没有在期间完成渲染就会发生掉帧。掉帧是用户体验中一个非常核心的问题。丢弃了当前帧，并且之后不能够延续之前的帧率，这种不连续的间隔会容易引起用户的注意，也就是常说的卡顿、不流畅。
- 那么是不是1s只要绘制了60帧就是流畅的呢？
  - 也不一定，如果发生抖动的情况，那么肯定会有其中几帧是有问题的。其中肯定会有最大绘制帧和最小绘制帧的情况，所以平均值、最大值、最小值都是我们需要知道的。



### 2.4 一帧显示的步骤

- 一帧的显示要经历如下步骤：
  - cpu计算画多大，画在哪里，画什么，然后gpu渲染计算结果存到buffer，显示器每隔一段时间从buffer取帧。若没有取到帧，只能继续显示上一帧。
- 16ms内都需要完成什么？
  - VSync调度、doFrame消息调度、input输入处理、动画、测量/布局、绘制、同步和上传、命令问题、交换缓冲区。也就是我们常用的GPU严格模式。
- 理解双缓冲和三缓冲机制
  - 双缓冲（Double Buffering）：系统使用两个buffer交替工作，一个用于显示（Front Buffer），一个用于绘制（Back Buffer）。绘制完成后交换两个buffer。
  - 三缓冲（Triple Buffering）：在双缓冲基础上增加一个buffer。当CPU/GPU的处理速度跟不上显示器的刷新速度时，三缓冲可以让CPU/GPU不必等待显示器释放buffer，从而提高流水线的并行度。
  - Android 4.1引入了Project Butter（黄油计划），核心改进就是：VSYNC同步信号驱动 + 三缓冲机制 + Choreographer调度框架，大幅提升了渲染流畅度。


### 2.5 卡顿根本原因

- 视图刷新原理：
  - View的requestLayout和ViewRootImpl的setView最终都会调用ViewRootImpl的requestLayout方法，然后通过scheduleTraversals方法向Choreographer提交一个绘制任务，然后再通过DisplayEventReceiver向底层请求vsync垂直同步信号，当vsync信号来的时候，会通过JNI回调回来，通过Handler往消息队列post一个异步任务，最终是ViewRootImpl去执行绘制任务，调用performTraversals方法，完成绘制。
- 卡顿的根本原因：
  - 从刷新原理来看卡顿的根本原理是有两个地方会造成掉帧：
  - 一个是主线程有其它耗时操作，导致doFrame没有机会在vsync信号发出之后16毫秒内调用；
  - 还有一个就是当前doFrame方法耗时，绘制太久，下一个vsync信号来的时候这一帧还没画完，造成掉帧。
  - 从更底层的角度看，卡顿可以归结为三类：CPU瓶颈（主线程任务过重、线程调度延迟）、GPU瓶颈（过度绘制、复杂纹理）和IO瓶颈（主线程磁盘读写、网络请求）。
- 疑惑：为什么有时候CPU和GPU都不忙，但还是会卡顿？
  - 答疑：这种情况通常是由于主线程被锁等待（如synchronized竞争）、Binder调用阻塞（如跨进程通信超时）或者系统调度延迟（如低优先级线程得不到CPU时间片）导致的。这类卡顿从CPU/GPU负载角度看并不明显，需要通过Systrace的CPU调度信息来定位。



## 03.卡顿问题排查思路

### 3.1 卡顿排查总思路

- 卡顿排查的整体流程
  - 第一步：发现卡顿。通过线上监控（FPS监控、卡顿日志上报）或线下工具（Systrace、Profiler）发现卡顿问题。
  - 第二步：定位卡顿。拿到卡顿时的堆栈信息，结合CPU使用率、内存状态、IO情况等辅助信息，定位卡顿发生的位置。
  - 第三步：分析原因。根据堆栈信息和上下文，分析是主线程耗时操作、布局问题、内存问题还是其他原因导致。
  - 第四步：修复验证。修改代码后，通过AB测试或灰度发布验证修复效果，对比修复前后的卡顿率指标。
- 线下排查卡顿工具
  - Systrace：系统级trace工具，能看到整个系统的运行状态，包括CPU调度、渲染流水线、锁等待等信息。
  - Android Studio Profiler：集成在IDE中，可以实时查看CPU、内存、网络等性能数据，方便定位具体方法的耗时。
  - Layout Inspector：用于查看当前Activity的布局层级结构，帮助发现过度嵌套的布局。
  - GPU呈现模式分析：开发者选项中开启，以条形图形式展示每帧的渲染耗时，超过绿线的部分表示掉帧。
- 线上监控卡顿方案
  - LooperPrinter方案：替换主线程Looper的Printer，监控每个消息的处理耗时。
  - WatchDog方案：定时向主线程发送消息，检测消息是否被及时处理。
  - Choreographer.FrameCallback方案：通过帧回调计算帧率和掉帧情况。



## 04.卡顿监控思路

### 4.1 卡顿监控核心思路

- 可以监控卡顿，从而可以对卡顿优化做到极致。我们可以从下面四个方面来监控应用程序卡顿：
  - 基于Looper的Printer分发消息的时间差值来判断是否卡顿。
  - 基于Choreographer回调函数postFrameCallback来监控。
  - 基于开源框架BlockCanary来监控。
  - 基于开源框架rabbit-client来监控。



### 4.2 LooperPrinter

- 卡顿监控不优雅的处理
  - 直接创建一个基类放在项目代码中，所有需要Handler的地方都对此进行继承，然后在基类中添加日志监控。
  - 不好，这样对项目改造的成本太高了，而且也监控不到系统中的消息，也监控不到第三方SDK中的消息执行时间！
- 卡顿监控优雅的处理
  - 分析Looper中的loop方法可知，处理消息前后有日志打印，看到有个Printer日志输出管理的类，并且暴露setMessageLogging方法。这个可以自己定义实现。
- 使用LooperPrinter监控
  - 替换主线程Looper的Printer，从而监控dispatchMessage的执行时间。甚至，在Android源码中，主线程Looper也会根据执行dispatchMessage的时间来判断是否有卡顿，有则会打印一些日志。
  - 在Printer中判断start和end，来获取主线程dispatch该message的开始和结束时间，并判定该时间超过阈值(如2000毫秒)为主线程卡慢发生，并dump出各种信息，提供开发者分析性能瓶颈。
  - 卡顿之后收集相关dump信息，主要包含一些基本信息、耗时信息、CPU信息还有堆栈信息等等。可以直接参考LeakCanary即可。
- 优缺点分析
  - 优点：不会随机漏报，无需轮询，一劳永逸；缺点：某些类型的卡顿无法被监控到。




### 4.3 WatchDog

#### 4.3.1 WatchDog卡顿监控

- 如何监控UI卡顿
  - 启动一个卡顿检测线程，该线程定期的向UI线程发送一条延迟消息，执行一个标志位加1的操作，如果规定时间内，标志位没有变化，则表示产生了卡顿。如果发生了变化，则代表没有长时间卡顿，我们重新执行延迟消息即可。
- 具体的原理说明
  - 不断向UI线程发送Message，每隔一段时间检查一次刚刚发送的Message是否被处理，如果没有被处理，则说明这段时间主线程被卡住了。


#### 4.3.2 WatchDog的优缺点

- 优缺点
  - 优点：简单，稳定，结果论，可以监控到各种类型的卡顿
  - 缺点：轮询不优雅，不环保，有不确定性，随机漏报
- 间隔时间设置
  - 这种方法的轮询的时间间隔选择很重要，又让人左右为难，轮询的时间间隔越小，对性能的负面影响就越大，而时间间隔选择的越大，漏报的可能性也就越大。
- 如何理解性能负面影响
  - UI线程要不断处理我们发送的Message，必然会影响性能和功耗。


#### 4.3.3 如何理解漏报数据

- 时间间隔选择了4秒
  - 事实上，之前是想要通过这种方案来监控ANR，当然，这并不严谨。来分析一下
- 举一个例子
  - 每隔4秒，向主线程发送一个消息。下面是轮训的过程
  - 0秒 ---- 4秒 ---- 8秒 ---- 12秒 ---- 16秒
  - 现在有一个5秒的卡顿发生在第2秒，结束在第7秒，这种情况无论是在0-4秒的周期内，还是4-8秒的周期内，都有一段时间是不卡顿的，消息都可以被处理掉，这种情况自然就无法被监控到。
- 计算监控成功率
  - 计算公式：p = x/a - 1 ；注意条件（a<= x <= 2a）
  - 上面案例计算 ： p = 5/4 - 1 = 0.25 ; 如果轮询间隔设置为4秒，发现一个5秒的卡顿的概率仅为25%。
- 修改轮训间隔时间
  - 默认轮询间隔为5秒，如果有一个8秒的卡顿（8秒已经很容易产生ANR），被发现的概率也只有8/5-1=60%
  - 从这个概率公式还可以发现，对于一个固定的轮询间隔，只有卡顿时间大于两倍的轮询间隔，才能百分之百被监控到。
- 思考把间隔时间缩短
  - 每隔2秒，向主线程发送一个消息。下面是轮训的过程
  - 0秒 -- 2秒 -- 4秒 -- 6秒 -- 8秒 -- 10秒 -- 12秒
  - 现在有一个6秒的卡顿发生在第1秒，结束在第7秒，那么这个在2-4和4-6区间可以捕获到。

## 05.卡顿原理探索

### 5.1 Handler机制说一下

- 想要监控线上用户UI线程的卡顿，也就是要把UI线程中的耗时逻辑找出来，然后进行优化开发。那么我们如何做呢？
  - Android中的应用程序是消息驱动的，也就是UI线程执行的所有操作，通常都会经过消息机制来进行传递（也就是Handler通信机制）。
  - Handler的handleMessage负责在UI线程中处理UI相关逻辑，如果我们能在handleMessage执行之前和handleMessage执行之后，分别插入一段日志代码，不就可以实现UI任务执行时间的监控了吗？



### 5.2 UI卡顿检测实现

- 来看Looper的loop方法，loop方法中有一个Printer类型的logging，它会在消息执行之前和消息执行之后，输出一行日志，用于标记消息执行的开始和结束。
  - 只要记录开始日志和结束日志的时间差，就可以计算出该任务在UI线程的执行时间了，如果执行时间很长，则必然产生了卡顿。
  ```java
  public static void loop() {
      for (;;) {
          Message msg = queue.next(); // might block
          if (msg == null) {
              return;
          }
          final Printer logging = me.mLogging;
          //这个是开始
          if (logging != null) {
              logging.println(">>>>> Dispatching to " + msg.target + " " +
                      msg.callback + ": " + msg.what);
          }
          //消息处理相关逻辑
          msg.target.dispatchMessage(msg);
          //这个是结束
          if (logging != null) {
              logging.println("<<<<< Finished to " + msg.target + " " + msg.callback);
          }
      }
  }
  ```
- 如何监控这个Printer类型的日志呢？
  - 发现mLogging这个对象可以通过一个public方法进行设置！可以通过setMessageLogging方法设置我们自己的Printer对象就可以实现卡顿的监控了！
  ```java
  private Printer mLogging;
  public void setMessageLogging(@Nullable Printer printer) {
      mLogging = printer;
  }
  ```
- 为何说可以监测大部分卡顿
  - 通过计算执行dispatchMessage方法之后和之前打印字符串的时间的差值，就可以拿到dispatchMessage方法执行的时间。
  - 即整个应用的主线程，只有这一个looper，不管有多少handler，最后都会回到这里。而大部分的主线程的操作最终都会执行到这个dispatchMessage方法中。
- 具体怎么判断卡顿呢？
  - 在Printer中判断start和end，来获取主线程dispatch该message的开始和结束时间，并判定该时间超过阈值(如2000毫秒)为主线程卡慢发生，并dump出各种信息，提供开发者分析性能瓶颈。
- 卡顿之后收集相关dump信息【参考LeakCanary】
  - 基本信息：安装包标示、机型、api等级、uid、CPU内核数、进程名、内存、版本号等
  - 耗时信息：实际耗时、主线程时钟耗时、卡顿开始时间和结束时间
  - CPU信息：时间段内CPU是否忙，时间段内的系统CPU/应用CPU占比，I/O占CPU使用率
  - 堆栈信息：发生卡慢前的最近堆栈，可以用来帮助定位卡慢发生的地方和重现路径
- 存在的问题有：
  - 如果queue.next()卡住了，那么就无法往下执行了。这个时候无法检测到卡顿。



### 5.3 那些卡顿无法监控

- 看到上面的queue.next()，这里给了注释：might block
  - 代码直接跟你说这里是可能会卡住的，这时候再计算dispatchMessage方法的耗时显然就没有意义了。
  - 有人可能会想，那改成计算相邻两次dispatchMessage执行之前打印字符串的时间差值不就好了？这样就可以把next方法的耗时也计算在内。
  - 不幸的是，主线程空闲时，也会阻塞在MessageQueue的next方法中，我们很难区分究竟是发生了卡顿还是主线程空闲。
- 分析一下MessageQueue的next方法
  - 是什么原因会卡在MessageQueue的next方法中呢？下面是next方法简化过后的源码：
  ```java
  for (;;) {
      if (nextPollTimeoutMillis != 0) {
          Binder.flushPendingCommands();
      }
      nativePollOnce(ptr, nextPollTimeoutMillis);
      for (int i = 0; i < pendingIdleHandlerCount; i++) {
          final IdleHandler idler = mPendingIdleHandlers[i];
          mPendingIdleHandlers[i] = null;
          boolean keep = false;
          try {
              keep = idler.queueIdle();
          } catch (Throwable t) {
          }
          if (!keep) {
              synchronized (this) {
                  mIdleHandlers.remove(idler);
              }
          }
      }
  }
  ```
- 有这么几类无法监控到
  - View的TouchEvent中的卡顿这种方案是无法监控的
  - IdleHandler的queueIdle()回调方法也是无法被监控的
  - SyncBarrier（同步屏障）的泄漏同样无法被监控到

#### 5.3.1 View的TouchEvent卡顿

- 在MessageQueue的next方法中
  - 除了主线程空闲时阻塞在nativePollOnce之外，非常重要的是，应用的Touch事件也是在这里被处理的。
  - 这就意味着，View的TouchEvent中的卡顿这种方案是无法监控的。
- 那么TouchEvent造成卡顿场景有哪些呢？
  - 在onTouchEvent方法中执行了耗时操作，如复杂的计算、IO操作等。
  - 在自定义View的onTouchEvent中频繁调用invalidate()导致过度重绘。
  - 在GestureDetector的回调方法中执行了大量数据处理逻辑。
  - 嵌套滑动场景下，事件分发链路过长，每一层都需要计算是否拦截，累积耗时导致卡顿。


#### 5.3.2 IdleHandler的queueIdle()

- IdleHandler的queueIdle()回调方法也是无法被监控的
  - 这个方法会在主线程空闲的时候被调用。然而实际上，很多开发同学都先入为主的认为这个时候反正主线程空闲，做一些耗时操作也没所谓。
  - 其实主线程MessageQueue的queueIdle默认当然也是执行在主线程中，所以这里的耗时操作其实是很容易引起卡顿和ANR的。
- 那么queueIdle()造成卡顿场景有哪些呢？
  - 例如App之前就使用IdleHandler在进入主界面后，做一些读写文件的IO操作，就造成了一些卡顿和ANR问题。


#### 5.3.3 SyncBarrier（同步屏障）的泄漏

- SyncBarrier（同步屏障）的泄漏同样无法被监控到
  - 当我们每次通过invalidate来刷新UI时，最终都会调用到ViewRootImpl中的scheduleTraversals方法，会向主线程的Looper中post一个SyncBarrier，其目的是为了在刷新UI时，主线程的同步消息都被跳过，此时渲染UI的异步消息就可以得到优先处理。
  - 但是注意到这个方法是线程不安全的，如果在非主线程中调用到了这里，就有可能会同时post多个SyncBarrier，但只能remove掉最后一个，从而有一个SyncBarrier就永远无法被remove，就导致了主线程Looper无法处理同步消息（Message默认就是同步消息），导致卡死
- ViewRootImpl源码如下所示
  ```java
  void scheduleTraversals() {
      if (!mTraversalScheduled) {
          mTraversalScheduled = true;
          mTraversalBarrier = mHandler.getLooper().getQueue().postSyncBarrier();
          mChoreographer.postCallback(
                  Choreographer.CALLBACK_TRAVERSAL, mTraversalRunnable, null);
          notifyRendererOfFramePending();
          pokeDrawLockIfNeeded();
      }
  }
  
  void unscheduleTraversals() {
      if (mTraversalScheduled) {
          mTraversalScheduled = false;
          mHandler.getLooper().getQueue().removeSyncBarrier(mTraversalBarrier);
          mChoreographer.removeCallbacks(
                  Choreographer.CALLBACK_TRAVERSAL, mTraversalRunnable, null);
      }
  }
  ```



### 5.4 监控IdleHandler卡顿

- 首先从简单的下手，对于IdleHandler的queueIdle回调方法的监控。
  - 我们惊喜的发现MessageQueue中的mIdleHandlers是可以被反射的，这个变量保存了所有将要执行的IdleHandler，我们只需要把ArrayList类型的mIdleHandlers，通过反射，替换为MyArrayList，在自定义的MyArrayList中重写add方法，再将自定义的MyIdleHandler添加到MyArrayList中，就完成了"偷天换日"。
  - 从此之后MessageQueue每次执行queueIdle回调方法，都会执行到我们的MyIdleHandler中的queueIdle方法，就可以在这里监控queueIdle的执行时间了。
- 代码如下所示
  ```java
  private static void detectIdleHandler() {
      try {
          MessageQueue mainQueue = Looper.getMainLooper().getQueue();
          Field field = MessageQueue.class.getDeclaredField("mIdleHandlers");
          field.setAccessible(true);
          MyArrayList<MessageQueue.IdleHandler> myIdleHandlerArrayList = new MyArrayList<>();
          field.set(mainQueue, myIdleHandlerArrayList);
      } catch (Throwable t) {
          t.printStackTrace();
      }
  }
  
  static class MyArrayList<T> extends ArrayList {
      Map<MessageQueue.IdleHandler, MyIdleHandler> map = new HashMap<>();
  
      @Override
      public boolean add(Object o) {
          if (o instanceof MessageQueue.IdleHandler) {
              MyIdleHandler myIdleHandler = new MyIdleHandler((MessageQueue.IdleHandler) o);
              map.put((MessageQueue.IdleHandler) o, myIdleHandler);
              return super.add(myIdleHandler);
          }
          return super.add(o);
      }
  
      @Override
      public boolean remove(@Nullable Object o) {
          if (o instanceof MyIdleHandler) {
              MessageQueue.IdleHandler idleHandler = ((MyIdleHandler) o).idleHandler;
              map.remove(idleHandler);
              return super.remove(o);
          } else {
              MyIdleHandler myIdleHandler = map.remove(o);
              if (myIdleHandler != null) {
                  return super.remove(myIdleHandler);
              }
              return super.remove(o);
          }
      }
  }
  ```

### 5.5 监控TouchEvent卡顿

- 那么TouchEvent我们有什么办法监控吗？
  - 首先想到的可能是反射View的mListenerInfo，然后进一步替换其中的mTouchListener，但是这需要枚举所有需要被监控的View，全部反射替换一遍，这完全是不可行的做法。
- 那有没有更加根本，全局性的方法呢？
  - 方案一：Hook InputChannel。Touch事件通过InputChannel从InputDispatcher传递到应用进程，可以通过反射替换InputChannel的fd（文件描述符），在数据到来时先由我们的代码处理，然后再转发给原始的InputChannel。但这种方式比较hack，兼容性风险高。
  - 方案二：Hook Choreographer的FrameCallback。在doFrame回调中记录每帧的Input阶段耗时，当超过阈值时dump堆栈。这种方式可以间接监控到Touch处理的耗时。
  - 方案三：在Application级别设置ViewGroup.OnHierarchyChangeListener监听，为所有添加到视图树的View设置AccessibilityDelegate，通过AccessibilityDelegate可以间接获取到Touch事件的回调时机。
  - 目前业界比较成熟的方案是结合Choreographer和消息队列监控，通过间接方式覆盖Touch事件的耗时监控。


### 5.6 监控SyncBarrier泄漏

- SyncBarrier泄漏监控的核心思路
  - 通过反射获取MessageQueue中的mMessages字段，遍历消息队列中的Message链表。
  - SyncBarrier消息的特征是其target字段为null（正常的Message都有一个非null的target Handler）。
  - 定期检查消息队列，如果发现某个SyncBarrier存在时间超过阈值（如1秒），则认为发生了SyncBarrier泄漏。
- 监控代码核心思路如下
  ```java
  private static void detectSyncBarrierLeak() {
      // 定时检查主线程MessageQueue
      // 反射获取mMessages字段
      // 遍历消息链表，检查target为null的消息（SyncBarrier）
      // 如果SyncBarrier存在超过阈值时间，上报泄漏信息
      // 包括：SyncBarrier的when时间、已存在时长、当前消息队列状态等
  }
  ```
- SyncBarrier泄漏的解决方案
  - 根本原因通常是在非UI线程调用了View的invalidate等方法，触发了scheduleTraversals。
  - 通过StrictMode或自定义Lint规则检查非UI线程调用View方法的情况。
  - 在代码层面确保View操作都在主线程进行，使用View.post()或Handler.post()将操作切到主线程。



## 06.治理卡顿的流程

### 6.1 排查卡顿流程

- 优化卡顿的步骤
  - 监控卡顿的发生 ---> 准确定位到哪个模块(甚至哪个方法导致了卡) ---> 分析代码并解决卡顿
- 监控卡顿的发生
  - 主要使用工具监控
- 定位到卡顿的点
  - 拿到卡顿堆栈后，需要分析堆栈中的关键信息：
  - 堆栈顶部的方法通常就是造成卡顿的直接原因，比如某个数据库查询、文件IO、复杂计算等。
  - 结合CPU使用率信息，判断是当前App占用CPU过多，还是系统整体CPU负载过高导致的。
  - 结合内存信息，判断是否存在频繁GC（内存抖动）导致主线程被暂停。
  - 结合IO信息，判断是否存在主线程上的IO阻塞。
- 分析代码并解决卡顿
  - UI卡顿：优化布局层级、减少过度绘制、使用ViewStub延迟加载、异步inflate布局。
  - 线程卡顿：将耗时操作移到子线程、优化锁竞争、合理设置线程优先级。
  - 过度绘制卡顿：移除多余的背景色、使用clipRect减少绘制区域、合理使用Canvas.save/restore。
  - 内存抖动卡顿：避免在循环和高频方法中创建对象、使用对象池复用对象、优化数据结构。



### 6.2 排查卡顿工具

- 卡顿排查工具
  - Systrace方法
  - Android CPU Profiler工具分析卡顿
  - 线上性能监控方法
  - FPS帧率检测


### 6.3 制定卡顿指标

- FPS：帧率；取vsync到来的时间为起点，doFrame执行完成的时间为终点，作为每帧的渲染耗时
  - 同时利用渲染耗时/刷新率可以得出每次渲染的丢帧数。平均FPS = 一段时间内渲染帧的个数 * 60 / (渲染帧个数 + 丢帧个数)
- 卡顿指标说明
  - stall_video_ui_rate：总卡顿率；（UI卡顿时长 + 流卡顿时长）/ 采集时长
  - stall_ui_rate：UI卡顿率；【> 3帧】UI卡顿时长 / 采集时长
  - stall_video_rate：流卡顿率；流卡顿时长 / 采集时长
  - stall_ui_slight_rate：轻微卡顿率；【3 - 6】帧丢帧时长 / 采集时长
  - stall_ui_moderate_rate：中等卡顿率；【7 - 13】帧丢帧时长 / 采集时长
  - stall_ui_serious_rate：严重卡顿率；【> 14】帧丢帧时长 / 采集时长
- 疑惑：卡顿率和FPS有什么区别？用哪个指标更好？
  - 答疑：FPS是一个平均值指标，可能掩盖掉短暂的严重卡顿。例如，一秒内前900ms都是60fps，但最后100ms掉帧到10fps，平均FPS可能还是55fps，看起来不错，但用户已经明显感知到了卡顿。
  - 论证：卡顿率是一个事件型指标，记录的是"发生了多少次卡顿"以及"卡顿的严重程度"，更能反映用户的真实体验。
  - 结果：业界的最佳实践是同时关注FPS和卡顿率，FPS用于全局趋势监控，卡顿率（按严重程度分级）用于具体问题定位和治理。
  - 补充说明：除了上述指标，还可以关注"冻帧率"（Frozen Frame Rate），即单帧耗时超过700ms的帧占比。Google Play Console也将冻帧率作为应用质量的重要衡量指标。

### 6.4 建立卡顿治理闭环

- 完整的卡顿治理闭环流程
  - 采集：线上通过多种方案（LooperPrinter+WatchDog+Choreographer）采集卡顿数据。
  - 聚合：将采集到的卡顿堆栈进行去重和聚合，按照TOP N排序。
  - 分派：根据堆栈信息自动识别所属的业务模块，分派给对应的开发人员。
  - 修复：开发人员根据堆栈和辅助信息定位问题，修复卡顿。
  - 验证：修复后通过灰度发布验证效果，对比修复前后的卡顿率变化。
  - 防劣化：在CI流程中加入卡顿检测，防止新代码引入新的卡顿问题。
- 卡顿治理的度量指标
  - 整体卡顿率：所有用户中发生卡顿的占比。
  - 人均卡顿次数：每个用户平均遇到的卡顿次数。
  - TOP N卡顿Issue的修复率：排名前N的卡顿问题的修复完成情况。
  - 卡顿率环比变化：本周/本月的卡顿率相比上一周期的变化。



## 07.卡顿的成因分析

### 7.1 渲染机制中卡顿点

- View渲染的一生。可以理解为在16.6ms做了那些事情。
- 卡顿的点有哪些呢
  - 渲染机制中的任何流转过程发生异常，均会造成卡顿。逐个分析，看看都会有哪些原因可能造成卡顿。
- 渲染流程中的卡顿分析
  - **Vsync调度**：这个是起始点，但是调度的过程会经过线程切换以及一些委派的逻辑，有可能造成卡顿，但一般可能性比较小，我们也基本无法介入；
  - **消息调度**：主要是doFrame Message的调度，这就是一个普通的Handler调度，如果这个调度被其他的Message阻塞产生了时延，会直接导致后续的所有流程不会被触发。可以通过优化消息调度达到插帧的效果；
  - **input处理**：input是一次Vsync调度最先执行的逻辑，主要处理input事件。如果有大量的事件堆积或者在事件分发逻辑中加入大量耗时业务逻辑，会造成当前帧的时长被拉大；
  - **动画处理**：主要是animator动画的更新，动画数量过多或者动画的更新中有比较耗时的逻辑，也会造成当前帧的渲染卡顿；
  - **view处理**：主要是接下来的三大流程，过度绘制、频繁刷新、复杂的视图效果都是此处造成卡顿的主要原因；
  - **measure/layout/draw**：view渲染的三大流程，因为涉及到遍历和高频执行，所以这里涉及到的耗时问题均会被放大；
  - **DisplayList更新**：这里主要是canvas和displaylist的映射，一般不会存在卡顿问题；
  - **OpenGL指令转换**：将canvas的命令转换为OpenGL的指令，一般不存在问题；
  - **buffer交换**：主要指OpenGL指令集交换给GPU，和指令的复杂度有关；
  - **GPU处理**：耗时主要和任务量和纹理复杂度有关，这也就是降低GPU负载有助于降低卡顿的原因；
  - **layer合成**：主要是layer的compose工作，一般接触不到；
  - **Buffer切换**：主要是屏幕的显示，buffer的数量也会影响帧的整体延迟，不过是系统行为，不能干预。
- 视频流中的卡顿分析
  - 渲染卡顿：主要是TextureView渲染，TextureView跟随window共用一个surface，每一帧均需要一起协同渲染并相互影响；
  - 解码：解码主要是将数据流解码为surface可消费的buffer数据，是除了网络外最重要的耗时点；
  - OpenGL处理：有时会对解码完成的数据做二次处理，如果比较耗时会直接导致渲染卡顿；
  - 网络：包括DNS节点优选、CDN服务、GOP配置等。
- 系统负载
  - 内存：内存的吃紧会直接导致GC的增加甚至ANR，是造成卡顿的一个不可忽视的因素；
  - CPU：CPU对卡顿的影响主要在于线程调度慢、任务执行的慢和资源竞争，比如降频会直接导致应用卡顿；
  - GPU：GPU的影响见渲染流程，但还会间接影响到功耗和发热；
  - 功耗/发热：高功耗会引起高发热，进而会引起系统保护，比如降频、热缓解等，间接导致卡顿。



### 7.2 卡顿的分类

- 在一定程度上，我们遇到的所有卡顿问题，均能在渲染流程中找到理论依据，这也是指导我们优化卡顿问题的理论支撑。
- 从影响范围分类
  - 全局性卡顿：影响整个应用的卡顿，如内存不足导致的频繁GC、CPU被其他进程抢占等。
  - 局部性卡顿：只影响特定页面或操作的卡顿，如某个列表页的滑动卡顿、某个动画的掉帧等。
  - 偶发性卡顿：不确定出现的卡顿，通常与设备状态、网络环境等外部因素有关。



### 7.3 核心关注的卡顿

- 从用户感知维度划分核心卡顿
  - 滑动卡顿：用户在列表（RecyclerView/UITableView/ScrollView）滑动时感知到的卡顿，是最直观也最影响体验的卡顿类型。
  - 页面切换卡顿：Activity/Fragment切换时的卡顿，表现为转场动画不流畅或黑屏白屏。
  - 点击响应延迟：用户点击按钮后，反馈延迟超过200ms，用户就会感知到卡顿。
  - 动画卡顿：属性动画、帧动画在执行过程中的掉帧，视觉上非常明显。
- 从技术实现维度划分核心卡顿
  - 主线程耗时操作：IO操作、复杂计算、数据库查询等放在了主线程执行。最常见的卡顿原因，也是最容易修复的。
  - 布局层级过深：多层嵌套的布局导致measure/layout过程耗时过长，使用Layout Inspector工具可以直观看到布局层级。
  - 过度绘制：同一像素区域被多次绘制，GPU负载增大。通过开发者选项中的"调试GPU过度绘制"可以直接查看。
  - 内存抖动导致的频繁GC：短时间内大量创建临时对象，触发频繁GC，导致主线程被暂停。
  - 线程竞争：多个线程争抢CPU资源或锁资源，导致主线程得不到及时调度。
- 跨平台卡顿对比
  - iOS端：主要关注CADisplayLink回调耗时、AutoLayout约束计算耗时、离屏渲染等问题。iOS的UIKit不允许非主线程操作UI，避免了部分线程安全问题。
  - Web端：主要关注JavaScript长任务（Long Task）、CSS重排重绘、DOM操作过于频繁等问题。可以通过Performance API和PerformanceObserver监控Long Task。
  - Flutter端：关注Build/Layout/Paint阶段耗时、Widget重建次数、Skia渲染性能等。



## 08.卡顿优化实战策略

### 8.1 View卡顿点分析

- 产生卡顿原因有很多，主要有以下几点：
  - 布局Layout过于复杂，无法在16ms内完成渲染。
  - 同一时间动画执行的次数过多，导致CPU和GPU负载过重。
  - View过度绘制，导致某些像素在同一帧时间内被绘制多次。
  - 在UI线程中做了稍微耗时的操作。
  - GC回收时暂停时间过长或者频繁的GC产生大量的暂停时间。


### 8.2 UI卡顿优化八板斧

- 对于UI卡顿来说，手握卡顿优化的8板大斧子，所向披靡：
  - **下线代码**：直接移除不必要的逻辑，最彻底的优化方式。
  - **减少执行次数**：通过缓存、防抖等手段减少方法的调用频率。
  - **异步**：将耗时操作移到子线程，如IO、复杂计算、网络请求等。
  - **打散**：将大任务拆分成多个小任务，分散到多帧中执行，避免单帧耗时过长。
  - **预热**：提前执行一些初始化操作，将耗时操作前置到用户感知不到的时机。
  - **复用**：使用对象池、缓存等机制复用已有资源，避免重复创建。
  - **方案优化**：从算法和数据结构层面优化，如使用更高效的排序算法、更合适的数据结构。
  - **硬件加速**：利用GPU加速渲染，开启硬件加速Layer等。


### 8.3 UI线程阻塞分析

- 如果UI线程受到阻塞，显而易见的是，Traversal过程也将受阻塞，画面卡顿妥妥发生。这就是为什么一直强调不要在UI线程做耗时操作的原因。通常UI线程的阻塞和以下原因脱不了关系：
  - 在UI线程中进行IO读写数据的操作。这是一个很费时的过程，把IO操作统统放到子线程中去。
  - 在UI线程中进行复杂的运算操作。运算本身是一个耗时的操作，对于十分复杂的运算，对时间的消耗是十分可观的。
  - 在UI线程中进行复杂的数据处理。比如数据的加密、解密、编码等等。这些操作都需要进行复杂运算，特别是在数据比较复杂的时候。
  - 频繁的发生GC，导致UI线程被频繁中断。在Java中，发生GC意味着Stop-The-World，其它线程全部会被暂停。频繁GC的罪魁祸首是内存抖动——短时间内频繁的创建大量对象，导致达到GC的阈值，然后GC就发生了。
- 疑惑：为什么StrictMode能检测到主线程IO但很多人不用？
  - 答疑：StrictMode是Android提供的一个开发工具，可以在检测到主线程IO、网络操作时输出警告甚至崩溃。但它有以下局限：
  - 1.只能在Debug模式下使用，不能带到线上。
  - 2.它只能检测到标准的IO API调用，对于一些底层或第三方库的IO操作无法检测。
  - 3.它会降低应用性能，不适合长期开启。
  - 因此，StrictMode适合在开发阶段作为辅助工具使用，但不能替代线上的卡顿监控系统。



### 8.4 内存抖动与卡顿

- 什么是内存抖动？
  - 是由于短时间内有大量对象进出Young Generation区导致的，它伴随着频繁的GC。在Java内存管理机制中内存抖动会引起频繁的GC，从而使UI线程被频繁阻塞，导致画面卡顿。
- 避免发生内存抖动的几点建议：
  - 尽量避免在循环体内创建对象，应该把对象创建移到循环体外。
  - 注意自定义View的onDraw()方法会被频繁调用，所以在这里面不应该频繁的创建对象。
  - 当需要大量使用Bitmap的时候，试着把它们缓存在数组中实现复用。
  - 对于能够复用的对象，同理可以使用对象池将它们缓存起来。
- 如何定位内存抖动
  - 使用Android Studio的Memory Profiler，观察内存曲线是否呈现锯齿状波动。锯齿状说明内存在频繁分配和回收。
  - 点击Record allocations按钮，记录一段时间内的对象分配情况，然后查看哪些类被频繁创建。
  - 结合堆栈信息定位到具体的代码位置，通常是循环体内、高频回调方法内（如onDraw、onBindViewHolder）创建了临时对象。
- 内存抖动的解决方案
  - 对象池模式：预先创建一组对象，使用时取出，用完归还，避免频繁创建销毁。Android SDK中的Message.obtain()就是典型案例。
  - 局部变量提升为成员变量：将方法内频繁创建的对象提升为类的成员变量，在初始化时创建一次，后续复用。
  - 使用StringBuilder替代字符串拼接：在循环中使用"+"拼接字符串会产生大量中间String对象，改用StringBuilder可以避免。


### 8.5 复杂视图树优化

- 如果视图树复杂，会使整个Traversal过程变长。
  - 因此，在开发过程中要控制视图树的复杂程度。减少不必要的层级嵌套。比如使用RelativeLayout/ConstraintLayout可以减少复杂布局的嵌套。
- 频繁触发requestLayout()
  - 可能会导致在一帧的周期内，频繁的发生布局计算，这也会导致整个Traversal过程变长。
  - 有的ViewGroup类型的控件，比如RelativeLayout，在一帧的周期内会通过两次layout()操作来计算确认子View的位置，这种少量的操作并不会引起能够被注意到的性能问题。
  - 但是如果在一帧的周期内频繁的发生layout()计算，就会导致严重的性能问题，每次计算都是要消耗时间的！
  - requestLayout()操作，会向ViewRootImpl中一个名为mLayoutRequesters的List集合里添加需要重新Layout的View，这些View将在下一帧中全部重新layout()一遍。通常在一个控件加载之后，如果没什么变化的话，它不会在每次的刷新中都重新layout()一次。
  - 需要注意，setLayoutParams()最终也会调用requestLayout()，所以也不能滥用！


### 8.6 自定义View优化策略

- 对于频繁调用的方法，需要尽量减少不必要的代码。先从onDraw开始，需要特别注意不应该在这里做内存分配的事情，因为它会导致GC，从而导致卡顿。在初始化或者动画间隙期间做分配内存的动作。
- 还需要尽可能的减少onDraw被调用的次数，大多数时候导致onDraw都是因为调用了invalidate()。因此请尽量减少调用invalidate()的次数。如果可能的话，尽量调用含有4个参数的invalidate()方法而不是没有参数的invalidate()。没有参数的invalidate会强制重绘整个view。
- 另外一个非常耗时的操作是请求layout。任何时候执行requestLayout()，会使得Android UI系统去遍历整个View的层级来计算出每一个view的大小。如果找到有冲突的值，它会需要重新计算好几次。另外需要尽量保持View的层级是扁平化的。
- onDraw中的性能陷阱总结
  - 不要在onDraw中new对象（Paint、Rect、Path等），应该在构造函数或onSizeChanged中初始化。
  - 不要在onDraw中调用Log.d等日志方法，因为字符串拼接会创建临时对象。
  - 避免在onDraw中进行Bitmap的decode操作。
  - 使用Canvas.clipRect()限制绘制区域，减少不必要的绘制。
  - 如果View只有局部更新，使用invalidate(Rect)而不是invalidate()，只重绘变化的区域。
  - 对于复杂的绘制，考虑使用硬件加速或RenderScript来提升渲染性能。
  - 使用Canvas.saveLayer()时要谨慎，它会创建离屏buffer，内存开销较大。尽量使用View的setLayerType代替。



## 09.卡顿监控设计总结

### 9.1 卡顿监控方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| LooperPrinter | 替换主线程Looper的Printer | 精准、无轮询开销 | 无法监控Touch、IdleHandler等 | 线上监控 |
| WatchDog | 定时向主线程发送消息 | 能监控各类卡顿 | 有漏报概率、有轮询开销 | 线上ANR预警 |
| Choreographer | 利用帧回调计算帧率 | 可以直接得到FPS | 只能得到帧率，无法定位原因 | FPS监控 |
| Systrace | 系统级trace | 信息最全面、最准确 | 只能线下使用、学习成本高 | 线下深度分析 |
| CPU Profiler | 采样/插桩方法耗时 | 可以精确到方法级别 | 对性能有一定影响 | 线下定向分析 |

### 9.2 核心设计原则

- 低开销原则
  - 监控本身不能成为新的性能问题。线上监控应尽量使用低开销的方案，如LooperPrinter方案几乎零开销。
  - 堆栈采集是最昂贵的操作，应该只在检测到卡顿时才进行，而不是每帧都采集。
  - 日志上报应该进行采样和聚合，避免大量日志对网络和存储的压力。

- 准确性原则
  - 单一方案很难覆盖所有卡顿类型，建议组合使用多种方案。
  - LooperPrinter覆盖消息处理阶段的卡顿，WatchDog兜底覆盖其他类型的卡顿。
  - 对于Touch事件和IdleHandler等特殊场景，需要额外的Hook方案来补充监控。

- 可分析原则
  - 仅有卡顿报警是不够的，必须输出足够的信息帮助开发者定位问题。
  - 必备信息：卡顿堆栈、卡顿耗时、CPU使用率、内存状态、当前Activity/Fragment。
  - 增强信息：IO等待时间、锁等待信息、GC次数和耗时、线程数量等。

### 9.3 卡顿优化最佳实践

- 建立卡顿基线
  - 在优化之前，先建立当前应用的卡顿基线数据，包括：平均FPS、卡顿率、严重卡顿率等。
  - 每次优化后与基线对比，量化优化效果。没有数据支撑的优化是盲目的。

- 分级治理策略
  - P0级（严重卡顿，>700ms）：必须立即修复，通常是主线程执行了IO或网络操作。
  - P1级（中等卡顿，250ms-700ms）：计划修复，通常是复杂的布局计算或大量数据处理。
  - P2级（轻微卡顿，100ms-250ms）：持续优化，通常是可以通过微调改善的问题。

- 防劣化机制
  - 在CI/CD流程中加入自动化性能测试，每次提交代码后自动检测是否引入了新的卡顿问题。
  - 建立卡顿告警机制，当线上卡顿率超过阈值时自动通知相关开发人员。
  - 在代码Review中关注可能引起卡顿的代码模式，如主线程IO、大循环中创建对象等。

### 9.4 跨平台卡顿监控对比

- **Android**
  - 核心机制：基于Looper消息循环和Choreographer帧回调。
  - 特有问题：多厂商ROM差异、后台进程对前台的影响、Doze模式等。
  - 成熟方案：BlockCanary、Matrix的TracePlugin、ANRWatchDog等。

- **iOS**
  - 核心机制：基于RunLoop的Observer回调和CADisplayLink帧率检测。
  - 特有问题：离屏渲染、AutoLayout约束计算、Core Animation提交事务耗时。
  - 成熟方案：利用RunLoop Observer在kCFRunLoopBeforeSources和kCFRunLoopAfterWaiting之间计算耗时。

- **Web**
  - 核心机制：基于requestAnimationFrame帧率检测和PerformanceObserver的Long Task监控。
  - 特有问题：JavaScript单线程模型、DOM操作开销、CSS重排重绘、第三方脚本影响。
  - 成熟方案：Lighthouse性能审计、Web Vitals指标（FID、INP、CLS等）。

- **Flutter**
  - 核心机制：基于SchedulerBinding.addPersistentFrameCallback监控每帧耗时。
  - 特有问题：Widget树rebuild过深、Skia渲染层性能、Platform Channel通信延迟。
  - 成熟方案：Flutter DevTools的Performance面板、自定义WidgetsBinding监控。

### 10.1 Android卡顿监控

```java
// Android卡顿监控（LooperPrinter + 堆栈采样）
public class AndroidJankMonitor {
    
    private static final long JANK_THRESHOLD_MS = 100;
    private HandlerThread sampleThread;
    private Handler sampleHandler;
    
    public void start() {
        sampleThread = new HandlerThread("JankSampler");
        sampleThread.start();
        sampleHandler = new Handler(sampleThread.getLooper());
        
        Looper.getMainLooper().setMessageLogging(new Printer() {
            private long startTime;
            private ScheduledFuture<?> samplerFuture;
            private List<String> stackSamples = new ArrayList<>();
            
            @Override
            public void println(String x) {
                if (x.startsWith(">>>>> Dispatching")) {
                    startTime = SystemClock.elapsedRealtime();
                    stackSamples.clear();
                    // 延迟JANK_THRESHOLD_MS后开始采样
                    sampleHandler.postDelayed(sampler, JANK_THRESHOLD_MS);
                } else if (x.startsWith("<<<<< Finished")) {
                    sampleHandler.removeCallbacks(sampler);
                    long duration = SystemClock.elapsedRealtime() - startTime;
                    
                    if (duration > JANK_THRESHOLD_MS) {
                        reportJank(duration, stackSamples);
                    }
                }
            }
            
            Runnable sampler = new Runnable() {
                @Override
                public void run() {
                    // 采集主线程堆栈
                    StackTraceElement[] stack = Looper.getMainLooper().getThread()
                        .getStackTrace();
                    stackSamples.add(formatStack(stack));
                    // 每50ms采样一次
                    sampleHandler.postDelayed(this, 50);
                }
            };
        });
    }
}
```

### 10.2 iOS卡顿监控

```objectivec

@implementation IOSJankMonitor {
    CFRunLoopObserverRef _observer;
    dispatch_semaphore_t _semaphore;
    CFRunLoopActivity _currentActivity;
}

- (void)startMonitoring {
    _semaphore = dispatch_semaphore_create(0);
    
    // RunLoop Observer
    CFRunLoopObserverContext context = {0, (__bridge void *)self, NULL, NULL, NULL};
    _observer = CFRunLoopObserverCreate(kCFAllocatorDefault,
        kCFRunLoopAllActivities, YES, 0, &runLoopObserverCallback, &context);
    CFRunLoopAddObserver(CFRunLoopGetMain(), _observer, kCFRunLoopCommonModes);
    
    // 子线程检测
    dispatch_async(dispatch_get_global_queue(0, 0), ^{
        while (YES) {
            // 等待信号量，超时时间为卡顿阈值
            long result = dispatch_semaphore_wait(self->_semaphore, 
                dispatch_time(DISPATCH_TIME_NOW, 88 * NSEC_PER_MSEC));
            
            if (result != 0) {
                // 超时，主线程可能卡顿
                if (self->_currentActivity == kCFRunLoopBeforeSources ||
                    self->_currentActivity == kCFRunLoopAfterWaiting) {
                    // 采集主线程堆栈
                    NSArray *stack = [NSThread callStackSymbols];
                    [self reportJank:stack];
                }
            }
        }
    });
}

static void runLoopObserverCallback(CFRunLoopObserverRef observer, 
    CFRunLoopActivity activity, void *info) {
    IOSJankMonitor *monitor = (__bridge IOSJankMonitor *)info;
    monitor->_currentActivity = activity;
    dispatch_semaphore_signal(monitor->_semaphore);
}

@end
```

### 10.3 Web卡顿监控

```javascript
// Web卡顿监控（Long Task + rAF帧率检测）
class WebJankMonitor {
    startMonitoring() {
        // Long Task API
        if (typeof PerformanceObserver !== 'undefined') {
            new PerformanceObserver((list) => {
                for (const entry of list.getEntries()) {
                    if (entry.duration > 100) {
                        this.reportJank({
                            type: 'long_task',
                            duration: entry.duration,
                            timestamp: Date.now()
                        });
                    }
                }
            }).observe({ entryTypes: ['longtask'] });
        }
        
        // rAF帧率监控
        let lastTime = performance.now();
        let frameCount = 0;
        const checkFPS = (now) => {
            frameCount++;
            if (now - lastTime >= 1000) {
                const fps = Math.round(frameCount * 1000 / (now - lastTime));
                if (fps < 50) {
                    this.reportLowFPS(fps);
                }
                frameCount = 0;
                lastTime = now;
            }
            requestAnimationFrame(checkFPS);
        };
        requestAnimationFrame(checkFPS);
    }
}
```
