## 01.问题域定义

### 1.1 现象与代价

**用户感知**：

- 点击按钮后没有立即响应（交互延迟）
- 列表滑动顿挫、画面掉帧（渲染延迟）
- 页面切换 / 转场动画不流畅
- 输入框输入文字延迟显示
- 极端情况：界面"冻住"几秒（冻帧 / ANR）

**业务代价（行业数据）**：

| 指标 | 影响 | 来源 |
|---|---|---|
| 卡顿率高的应用，卸载率提升 2–3× | 用户流失 | Google Android Vitals |
| 53% 的用户会放弃加载 > 3s 的应用 | 转化下降 | Google Research |
| 卡顿差评占性能类差评的 40%+ | 评分下滑 | App Store / Play Store 公开数据 |
| 输入延迟每增加 100ms，电商转化率下降 ~1% | GMV 损失 | Akamai 行业研究 |

### 1.2 度量准则

参考 [`卷零·02 跨平台性能模型与指标体系`](../00.公共方法论/02.跨平台性能模型与指标体系.md)，本文从三个视角组合度量：

| 视角 | 模型 | 关键指标 | 含义 |
|---|---|---|---|
| 用户感知 | APDEX / Vitals | 大卡顿率、INP、Tap Latency | 用户能否感觉到 |
| 请求级 | RED-D | 帧时长 P50/P90/P95/P99 | 单帧产出时长分布 |
| 资源级 | USE-S | 主线程 off-CPU 时长占比 | 流水线被"等待"占用比例 |

> ⚠️ **不要使用平均 FPS 作为唯一指标**。详见 [`卷三·02`](./02.FPS与帧率检测.md) 与本文 §1.4 反直觉问题。

### 1.3 行业基准与目标值

业界共识的卡顿分级（综合 Google Android Vitals / Apple HIG / Web Vitals）：

| 等级 | 单帧时长 | 用户感知 | 处理优先级 |
|---|---|---|---|
| Level 1 轻微掉帧 | 17–50 ms | 几乎无感知 | 低 |
| Level 2 明显卡顿 | 50–200 ms | 能感觉 | 中 |
| Level 3 严重卡顿 | 200–700 ms | 明显卡住 | 高 |
| Level 4 冻帧 | > 700 ms | 界面冻结 | 紧急 |
| Level 5 ANR / Hang | > 5 s（输入）/ > 250 ms（iOS Hang） | 系统介入 | 最高 |

**典型 SLO 目标**（中端机基线，需按机型分档）：

| 指标 | 目标值 |
|---|---|
| 帧时长 P95 | < 20 ms |
| 帧时长 P99 | < 33 ms |
| 大卡顿率（> 700 ms 帧 / 总帧） | < 0.1% |
| 卡顿会话率（含明显卡顿的会话占比） | < 3% |
| ANR / Hang 率 | < 0.05% |

## 02.第一性原理

### 2.1 一句话定义卡顿

> **卡顿 = 主线程未能在帧时钟规定的截止时间内完成应有的工作**

注意三个关键词：

- **主线程**：所有平台的 UI 框架都采用单线程模型（Android UI Thread / iOS Main Thread / Web Main JS Thread / 嵌入式 UI Task）。
- **帧时钟**：固定截止时间（60Hz=16.67ms / 90Hz=11.11ms / 120Hz=8.33ms）。
- **应有的工作**：处理输入、跑动画、Layout、Draw、Composite，以及业务消息。

### 2.2 用"流水线阻塞"模型解释

回到 [`卷零·01 第一性原理`](../00.公共方法论/01.性能工程总论与第一性原理.md) 中的"资源 × 时间 × 流水线"模型：

```
卡顿的物理来源 = 主线程在 16.67ms 预算内被迫等待 / 多算 / 算错

  ┌────────────────────────────────┐
  │  A. on-CPU 类卡顿（在烧 CPU）   │  ──→ 算法/数据/解码/解析等
  │     特征：CPU 100%，热点函数明显  │
  ├────────────────────────────────┤
  │  B. off-CPU 类卡顿（在等）      │  ──→ IO / 锁 / Binder / GC 暂停
  │     特征：CPU 不高，但帧没产出     │
  ├────────────────────────────────┤
  │  C. 系统级阻塞                  │  ──→ 调度延迟 / 高温降频 / 后台抢占
  │     特征：跨进程、跨线程         │
  └────────────────────────────────┘
```

> **关键认知**：很多团队只盯 A 类（因为 Profiler 一眼能看到），却忽略 B 类（用户更常遇到）和 C 类（最难复现）。

### 2.3 跨平台同构原理

不同平台的"卡顿"原理完全同构，只是叫法不同：

```
通用流水线模型：
  输入采样 ──▶ 主线程任务队列 ──▶ Run Loop / Looper ──▶ 帧产出 ──▶ 合成 ──▶ 显示
                  ▲                      ▲
                  │                      │
              业务任务                 帧时钟驱动的渲染任务
              （耗时操作在这里阻塞）   （超时即丢帧）
```

| 通用术语 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 主线程 | UI Thread | Main Thread | Main JS Thread | UI Task |
| 任务队列 | MessageQueue | Main RunLoop sources | Task Queue / Microtask | OS Queue |
| 帧时钟 | Choreographer / Vsync | CADisplayLink | requestAnimationFrame | 显示控制器 IRQ |
| 渲染流水线 | Measure→Layout→Draw→Composite | Layout→Display→Composite | Style→Layout→Paint→Composite | 自定义 |
| 系统兜底 | ANR（5s）| Watchdog Hang（~250ms 警告） | 浏览器自处理 | 看门狗复位 |

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| GC 影响 | ART STW + 并发 GC | 无 GC（ARC） | V8 GC（增量+并发） | 通常无 |
| 跨进程代价 | Binder（中等） | XPC / Mach（轻） | 跨域受限 | 较少 |
| 触摸事件路径 | InputDispatcher → MessageQueue | Main RunLoop EventTracking mode | DOM Event Loop | 直驱 |
| 系统兜底差异 | **有 ANR 弹框**，最严厉 | 无弹框，但**会被 watchdog 杀进程** | 浏览器接管 | 看门狗触发复位 |
| 高刷适配 | 多刷新率（60/90/120） | ProMotion 自适应 | 浏览器自适应 | 固定 |

> 反直觉问题 ⑦ 答案：**iOS 没 ANR 弹框反而更严厉** —— 用户看不到提示就直接进程被杀，体验更差。  
> 反直觉问题 ⑧ 答案：**Web Long Task 50ms 是 W3C 选定的"用户能感知交互延迟的最低阈值"**，并非渲染帧阈值；渲染帧由 rAF 单独度量。


## 03.度量与采集

### 3.1 五种采集方案的物理本质

所有平台的卡顿采集方案，本质上只有 5 类，区别在于"在流水线的哪一段下钩子"：

```
   输入采样 ──▶ MessageQueue ──▶ dispatchMessage ──▶ 渲染 ──▶ 合成 ──▶ 显示
                                       │              │
                       ┌───────────────┘              │
                       ▼                              ▼
              ① Looper Printer 钩子        ③ 帧回调钩子（Choreographer / CADisplayLink / rAF）
              （消息开始/结束）           （帧间隔统计）

              ② WatchDog 心跳：             ④ FrameMetrics / FrameTiming：
                "主线程能不能定期回我话"     系统提供帧各阶段耗时

              ⑤ 编译期函数插桩：在所有方法入口/出口插计时（精确但开销大）
```

| 方案 | 原理 | 输出粒度 | 性能开销 | 线上可用 |
|---|---|---|---|---|
| ① Looper Printer / RunLoop Observer | 消息分发前后埋点 | 消息级 | 低 | ✅ |
| ② WatchDog（心跳） | 子线程定期 ping 主线程 | 阈值级 | 中 | ✅ |
| ③ 帧回调（Choreographer / CADisplayLink / rAF） | 帧间隔统计 | 帧级 | 极低 | ✅ |
| ④ 系统帧 API（FrameMetrics / FrameTiming） | 系统直出帧各阶段耗时 | 阶段级 | 极低 | ✅（API 受限）|
| ⑤ 函数插桩（ASM / SwiftSyntax / Babel） | 编译期/运行期方法计时 | 方法级 | 中–高 | ⚠️ 需采样 |

### 3.2 各方案的可见盲区

**任何单一方案都有盲区**。以最常用的 Android `Looper Printer` 为例：

```
Looper.loop() 简化逻辑：
  for (;;) {
    Message msg = queue.next();   ← ❶ IdleHandler 在 next() 内执行，Printer 看不到！
                                    ❷ TouchEvent 在 nativePollOnce 内分发，Printer 也看不到！
    printer.println(">>>>> Dispatching");
    msg.target.dispatchMessage(msg);  ← Printer 仅能观测这段
    printer.println("<<<<< Finished");
  }
```

**Looper Printer 的三大盲区**：

| 盲区 | 原因 | 用户感知 |
|---|---|---|
| TouchEvent 卡顿 | 在 `next()` 的 `nativePollOnce` 内被分发 | 点击 / 滑动延迟 |
| IdleHandler.queueIdle() 卡顿 | 在 `next()` 内执行，不经 dispatch | 空闲时被插入的耗时任务 |
| SyncBarrier 泄漏 | 同步屏障未被移除，导致同步消息全卡死 | 整个主线程"假死" |

> 反直觉问题 ⑤ 答案：**LooperPrinter 无法监控 100% 卡顿**。这是后面 §4.4 的"不可见卡顿归因"专门要解决的问题。

iOS / Web 的对应方案也各有盲区：

| 平台 | 主方案 | 主要盲区 |
|---|---|---|
| iOS | RunLoop Observer | 无法精确测时长，只知"是否超阈值" |
| Web | Long Task API（>50ms） | 无法看到 < 50ms 的轻微卡顿；Layout 抖动需要 LTI |
| 嵌入式 | OS Tick / Watchdog | 中断处理内的卡顿不可见 |

### 3.3 跨平台采集对照表

| 信号 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 帧间隔 | `Choreographer.FrameCallback` | `CADisplayLink` | `requestAnimationFrame` | 显示 IRQ + 时间戳 |
| 帧各阶段耗时 | `Window.addOnFrameMetricsAvailableListener` (24+) | `MetricKit MXAppLaunchMetric` / `os_signpost` | `PerformanceObserver(type:'frame')` (实验) | 自定义埋点 |
| 主线程消息耗时 | `Looper.setMessageLogging` | `CFRunLoopObserverCreate` | `PerformanceObserver(type:'longtask')` | OS Hook |
| 主线程心跳 | 子线程 + Handler ping | 子线程 + dispatch_async ping | Web Worker + postMessage ping | 任务监视器 |
| 主线程堆栈 | `Thread.getStackTrace` / `unwind` | `backtrace` / `Thread.callStackSymbols` | `Error().stack`（受限） | `libunwind` |
| 系统级 trace | Perfetto / Systrace | Instruments Time Profiler | Chrome DevTools Performance | ftrace / lttng |

### 3.4 数据可信度评估

参考 [`卷零·04 采集与可观测性原理`](../00.公共方法论/04.采集与可观测性原理.md) §05，卡顿数据的常见误差来源：

| 误差来源 | 描述 | 应对 |
|---|---|---|
| 时钟选择 | 用 `System.currentTimeMillis()` 测耗时（NTP 调时会出错） | 必须用单调时钟（`nanoTime`/`mach_absolute_time`/`performance.now`） |
| Printer 字符串拼接 | 自身耗时 ~50–200μs/次，高频时影响 | 反射 hook 而非用 Printer，或限频 |
| WatchDog 漏报 | 阈值 vs 卡顿时长的概率关系 | 详见 §5.1 求证实验 |
| 堆栈采样错过 | 间隔过大，错过短卡顿 | 详见 §5.2 求证实验 |
| 采样偏差 | 仅采集前台用户、仅采集成功用户 | 多维切片 + A/A 校验 |
| 设备温度 | 高温降频导致测出"假慢" | 测试前检查温度（< 35℃）|

> **数据上报必须附带置信区间和采样口径**，否则不可作为决策依据。详见 [`卷零·02 §5.3`](../00.公共方法论/02.跨平台性能模型与指标体系.md)。


## 04.归因方法

### 4.1 卡顿归因决策树

引自 [`卷零·05 §5.1`](../00.公共方法论/05.归因方法论与火焰图解读.md)，针对单帧 > 16.67ms 的归因路径：

```
单帧 > 16.67ms
   │
   ├── on-CPU 占主导？──── Yes ──► 火焰图找平顶
   │                              │
   │                              ├─ 业务计算 → 算法 / 异步化
   │                              ├─ 渲染计算 → 减少视图层级 / 减少重绘
   │                              ├─ 内存分配密集 → 对象池 / 复用
   │                              └─ 解码 / 解析 → 异步 / 缓存
   │
   └── off-CPU 占主导？─── Yes ──► off-CPU 火焰图 + wakeup 链
                                  │
                                  ├─ IO Wait → 异步 / 缓存
                                  ├─ 锁等待 → 减少临界区 / 无锁
                                  ├─ Binder/IPC → 批量 / 缓存远端
                                  ├─ GC 停顿 → 减少分配 / 降低内存压力
                                  └─ Page Fault → mmap 预热 / 减少冷数据
```

> 反直觉问题 ② 答案：**CPU / 内存都不忙仍卡顿** —— 几乎一定是 off-CPU 类（锁、Binder、IO Wait）。

### 4.2 堆栈采样的归因价值

只知道"卡了 300ms"是无用的，必须把这 300ms 还原为**调用栈**。这就是堆栈采样的价值：

```
卡顿区间 [t0, t0+300ms]
   │
   │  ① 子线程定期采样主线程栈（间隔 50ms）
   │  ② 区间内得到 ~6 个栈快照
   │  ③ 聚合：相同栈 +1，得到"频率分布"
   │  ④ 频率最高的栈 = 卡顿热点
   ▼
归因结果：72% 时间在 SQLite.query → 主线程数据库查询
```

**采样方案的工程要点**：

```java
// 主线程栈采样器（Android 示意；iOS 用 backtrace、Web 用 Error().stack）
public class StackSampler {
    private final Thread mainThread = Looper.getMainLooper().getThread();
    private final Handler sampler;          // 独立 HandlerThread
    private final int interval;             // 采样间隔
    private final Map<String, Integer> bucket = new HashMap<>();

    public void start() {
        sampler.post(this::sample);
    }

    private void sample() {
        StackTraceElement[] st = mainThread.getStackTrace();
        String key = StackHasher.hash(st);   // 去掉行号 / 系统栈帧后的归一化签名
        bucket.merge(key, 1, Integer::sum);
        sampler.postDelayed(this::sample, interval);
    }
}
```

> ⚠️ 关键约定：上报数据时**只上报"栈签名 + 频次"**，不要上报每次原始栈，否则流量爆炸且不利于服务端聚合。

### 4.3 on-CPU vs off-CPU 卡顿

这是工程师最容易混淆的两类卡顿，必须**先分清再归因**：

| 维度 | on-CPU 卡顿 | off-CPU 卡顿 |
|---|---|---|
| 现象 | CPU% 高、热点函数明显 | CPU% 不高，但帧没产出 |
| 工具 | Time Profiler / 火焰图 | sched_switch / wakeup 链 / off-CPU 火焰图 |
| 典型根因 | JSON 解析、布局测量、解码 | IO、锁、Binder、GC |
| 归因难度 | 低 | 高（需要看"等待者 + 唤醒者"） |
| 用户感知占比（经验数据） | ~40–60% | ~40–60%（被低估） |

**off-CPU 卡顿的识别方法**：

1. 看主线程 trace：是否存在大段"灰色"区间（线程被切出 CPU）。
2. 看伴生现象：IO 增高 / GC 暂停 / Binder 调用 / 锁竞争。
3. 必要时启用 eBPF / dtrace 抓 sched_switch + wakeup 因果链。

### 4.4 不可见卡顿的归因

§3.2 提到 LooperPrinter 的三大盲区。下面给出可工程化的补救方案：

#### A. IdleHandler 卡顿的捕获

**思路**：用反射把 `MessageQueue.mIdleHandlers` 从 `ArrayList` 替换为代理列表，每次 add 时包装成代理 IdleHandler，在代理的 `queueIdle()` 前后埋点。

```java
// 简化伪代码（完整实现见原项目）
Field f = MessageQueue.class.getDeclaredField("mIdleHandlers");
f.setAccessible(true);
ArrayList<IdleHandler> proxy = new IdleHandlerProxyList();
f.set(Looper.getMainLooper().getQueue(), proxy);
```

#### B. TouchEvent 卡顿的捕获

直接 hook InputChannel 兼容性差，工程上更稳妥的两种方式：

- **方案 a**（推荐）：结合 `Choreographer.doFrame` 的 `INPUT_HANDLING` 阶段耗时（见 FrameMetrics API）。
- **方案 b**：通过 `View.dispatchTouchEvent` 的统一切面（编译期插桩在 Activity / 顶层 ViewGroup）。

#### C. SyncBarrier 泄漏的捕获

**思路**：定时反射读 `MessageQueue.mMessages` 链表，找到 `target == null`（即 SyncBarrier）且 `when` 已过期 > 阈值（如 1s）的节点，即为泄漏。

```java
// 检查逻辑（每 N 秒在子线程跑一次，避免影响主线程）
Object queue = Looper.getMainLooper().getQueue();
Field msgsField = MessageQueue.class.getDeclaredField("mMessages");
msgsField.setAccessible(true);
Message head = (Message) msgsField.get(queue);
long now = SystemClock.uptimeMillis();
for (Message m = head; m != null; m = MessageNext.get(m)) {
    if (m.getTarget() == null && now - m.getWhen() > 1000) {
        report("SyncBarrier leak", m);
        break;
    }
}
```

> **根因预防**：SyncBarrier 泄漏的根因几乎都是**在非 UI 线程调用了 `View.invalidate()` / `View.requestLayout()`**。可用 StrictMode + 自定义 Lint 在编码期阻断。


## 05.求证实验 ⭐

> 本章是"科学家求证"风格的核心。所有关键结论必须有实验数据支撑。  
> 实验设计方法参见 [`卷零·03 性能求证实验方法论`](../00.公共方法论/03.性能求证实验方法论.md)。

### 5.1 实验一：WatchDog 阈值与漏报率的定量关系

#### 命题

**H₁**：WatchDog 心跳间隔 `T` 与卡顿时长 `X` 之间存在确定的捕获概率关系；当 `X < 2T` 时存在漏报。  
**H₀**：WatchDog 阈值无关漏报率。

#### 数学推导

设 WatchDog 每 `T` 秒向主线程 ping 一次。一个时长 `X` 的卡顿，要被发现，必须在卡顿区间内有完整的一个 `T` 间隔被覆盖。

```
T  ─┼──────┼──────┼──────┼──────┼─→
        │■■■■■■■■■■■■■■■■■■│ 卡顿区间，时长 X
        ↑                  ↑
        卡顿开始           卡顿结束

  捕获概率 P(X, T) =
      X < T:  0
      T ≤ X < 2T:  (X - T) / T = X/T - 1
      X ≥ 2T:  1
```

#### 验证实验

**实验设计**：

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6（中端 Android） |
| 编译 | Release |
| 卡顿模拟 | 在主线程 `view.post` 中执行不同时长的 `Thread.sleep` |
| 重复次数 | 每个 (T, X) 组合 100 次 |
| 控制 | T ∈ {1s, 2s, 3s, 5s}, X ∈ {0.5T, T, 1.25T, 1.5T, 1.75T, 2T, 3T} |

**预期结果对比**：

| T | X | 公式预测 | 实测捕获率 | 误差 |
|---|---|---|---|---|
| 5s | 4s | 0% | 0% | 0% |
| 5s | 6.25s | 25% | 23% | 2% |
| 5s | 7.5s | 50% | 51% | 1% |
| 5s | 8.75s | 75% | 76% | 1% |
| 5s | 10s | 100% | 100% | 0% |
| 2s | 2.5s | 25% | 24% | 1% |
| 2s | 4s | 100% | 100% | 0% |

> 实验数据为示例，实际数值需在你自己的设备上复刻。  
> 但**结论是稳健的**：T 越大，对短卡顿越漏；T 越小，监控自身开销越大。

#### 结论与边界

- **结论**：WatchDog 漏报率 = 1 − P(X, T)，仅当 X ≥ 2T 时漏报率为 0。
- **工程取舍**：
  - 若 SLO 关注 ≥ 5s 的 ANR：T = 2.5s 可 100% 捕获。
  - 若 SLO 关注 ≥ 1s 的严重卡顿：T = 0.5s，但要评估自身开销（详见 §5.3）。
- **建议**：WatchDog 仅用作"长卡顿兜底"，配合 LooperPrinter 实现"短卡顿主线"。

### 5.2 实验二：堆栈采样间隔与归因准确率的权衡

#### 命题

**H₁**：堆栈采样间隔 `I` 越小，定位卡顿热点的命中率越高，但 CPU 开销线性增加；存在"性价比拐点"。  
**H₀**：采样间隔与命中率无关。

#### 实验设计

| 项 | 配置 |
|---|---|
| 卡顿场景 | 主线程执行 200ms 的 SQL 查询 |
| 采样间隔 I | {10ms, 20ms, 50ms, 100ms, 200ms} |
| 评估指标 | （a）命中率：采到至少一个含 SQLiteDatabase.query 栈的概率；（b）热点准确度：top1 栈是否正是 query；（c）采样自身 CPU 开销 |
| 重复 | 每组 200 次 |

#### 实测数据示意

| I | 命中率 | top1 准确度 | CPU 开销（采样线程） |
|---|---|---|---|
| 10ms | 99% | 95% | 4.2% |
| 20ms | 98% | 92% | 2.1% |
| 50ms | 92% | 85% | 0.9% |
| 100ms | 76% | 70% | 0.5% |
| 200ms | 41% | 38% | 0.2% |

#### 结论与边界

- **拐点**：50ms 是性价比最优点 —— 命中率 92%，开销 < 1%。
- **线上推荐**：50ms。
- **线下深度分析**：20ms。
- **不要使用 200ms 及更大间隔**：会漏掉大量短卡顿。

> 这就是为什么很多开源框架（BlockCanary、Matrix）默认采样间隔在 30–50ms 区间。

### 5.3 实验三：LooperPrinter 自身开销的量化

#### 命题

**H₁**：`Looper.setMessageLogging` 在高频消息场景下因字符串拼接产生显著开销，影响主线程性能。  
**H₀**：开销可忽略。

#### 实验设计

| 项 | 配置 |
|---|---|
| 场景 | 列表快速滚动 60s（高频 Touch + 重绘消息） |
| 对照组 | 不开启 LooperPrinter |
| 实验组 A | 开启原生 Printer（带字符串拼接） |
| 实验组 B | 开启反射 hook 版本（仅记录时间戳，不拼接） |

#### 实测数据示意

| 组 | 滚动 P99 帧时长 | 主线程 CPU% | 大卡顿次数 |
|---|---|---|---|
| 对照组 | 18.2ms | 38% | 0 |
| 实验组 A | 21.7ms (+19%) | 44% | 2 |
| 实验组 B | 18.6ms (+2%) | 39% | 0 |

#### 结论

- 原生 Printer 在高频消息下**自身就会引入卡顿**（+19% P99）。
- 反射 hook 方案显著优于 Printer 方案（开销可忽略）。
- **生产环境建议**：直接 hook `Looper.mLogging` 字段而非用 `setMessageLogging`，避免字符串拼接。

> 这是为什么"知名开源 APM"几乎都用反射 hook，而不是直接用 Printer。


## 06.优化策略

### 6.1 通用治理矩阵

按"流水线阻塞"模型分类，所有平台通用：

| 阻塞来源 | 通用治理思路 | 适用平台 |
|---|---|---|
| 主线程 IO | 异步化 / 内存缓存 / mmap 预热 | All |
| 主线程网络 | 全部异步 + 超时降级 | All |
| 锁竞争 | 缩小临界区 / 无锁数据结构 / CopyOnWrite | All |
| Binder / IPC | 批量调用 / 缓存远端结果 / 异步 IPC | Android（Binder）/ iOS（XPC）/ 嵌入式（共享内存） |
| GC 停顿 | 减少分配 / 对象池 / 避免 onDraw 内 new | Android（ART）/ Web（V8）/ 大多数 GC 平台 |
| 布局过深 | 扁平化 / 异步 inflate / ViewStub | Android / iOS / Web |
| 过度绘制 | 移除冗余背景 / clipRect / 半透明优化 | All |
| 大图解码 | 异步预解码 + 内存缓存 + 采样降尺寸 | All（参考卷四·03 图片优化） |
| 反射 / 动态加载 | 启动期前置 / 缓存反射结果 | All |

> 反直觉问题 ③ 答案：**简单"挪到子线程"不一定解决问题**：
> - 子线程结果回主线程时若需大量 UI 更新，主线程仍会卡。
> - 子线程持有主线程在等的锁，反而更糟。
> 正确路径：**减少主线程总工作量**，而非简单转移。

### 6.2 平台特化策略

| 平台 | 特化点 |
|---|---|
| Android | RenderThread / `Trace.beginSection` / Compose 异步 measure / R8 内联 |
| iOS | Core Animation 隐式动画 / `dispatch_async` 主队列分片 / Auto Layout 简化 |
| Web | `requestIdleCallback` 拆任务 / Web Worker 卸载计算 / `content-visibility:auto` |
| 嵌入式 | 双缓冲 / 局部刷新 / 硬件图层 / 中断分级 |

### 6.3 优先级判定（ROI）

参考 [`卷零·01 §4.3`](../00.公共方法论/01.性能工程总论与第一性原理.md)，按 ROI 排序：

```
ROI = (卡顿帧改善幅度 × 影响用户比例) / (开发成本 × 风险系数)
```

**推荐顺序**：

1. P0：消除冻帧（> 700ms）—— 极少用户但极差体验，必须先治理。
2. P1：压缩 P99 帧时长 —— 大量用户感受到的"明显卡顿"。
3. P2：减少 P95 帧时长 —— 持续优化项。
4. P3：把均值再往下压 —— 用户几乎无感知，性价比低。


## 07.实战案例

### 7.1 跨端同构案例：列表 onBindViewHolder 主线程 IO

#### 现象
- Android：`RecyclerView` 滚动 P99 = 48ms，平均 FPS 42。
- iOS：`UICollectionView` 同列表 P99 = 38ms。
- Web：`react-window` 同列表 P99 = 55ms。
- 三端皆有卡顿，但程度不同。

#### 度量与归因（按 §4.1 决策树）

1. RED-D：滚动单帧时长 P99 异常。
2. USE-S：CPU 中等（50–70%），不饱和。
3. on-CPU vs off-CPU：on-CPU 占 70–85%。
4. 火焰图：三端共同热点 —— `Bitmap.decode / UIImage init / Image decode`。

#### 假设与求证

**H₁**：将图片解码从主线程移至 IO 线程（IO 线程预解码），首屏 P99 帧时长 P99 降低 ≥ 30%。

| 平台 | 对照（主线程解码） | 实验（预解码） | 改善 |
|---|---|---|---|
| Android | 48ms | 17ms | -65% |
| iOS | 38ms | 14ms | -63% |
| Web | 55ms | 20ms | -64% |

**护栏检查**：

| 指标 | 对照 | 实验 | 是否可接受 |
|---|---|---|---|
| 首屏内存峰值 | 86MB | 112MB (+30%) | ⚠️ 中端机及以上 OK |
| 首屏崩溃率 | 0.02% | 0.04% | ⚠️ 需排查 OOM 风险 |

#### 边界与上线策略

- ✅ 在 ≥ 4GB 内存设备上稳定成立。
- ⚠️ 在 2GB 机型上反向劣化（GC 增加）。
- ❌ 在 1GB 机型上可能 OOM。
- 上线策略：按 `Build.MODEL` / `navigator.deviceMemory` 分档启用。

### 7.2 平台特异案例：Android SyncBarrier 泄漏

#### 现象
- 某 Android 8.0 用户报"App 整个 UI 卡死"，但 Looper Printer 没有任何超时事件。
- 表象：主线程任务队列堆积，但消息没在被分发。

#### 归因（按 §4.4 不可见卡顿）

排查顺序：

1. LooperPrinter 无异常 → 排除 dispatchMessage 阶段问题。
2. WatchDog 触发，且子线程发现 `mMessages` 头部存在 `target == null` 的消息持续 > 5s → SyncBarrier 泄漏。
3. Trace 回溯：发现一个第三方库在工作线程调用了 `view.invalidate()`。

#### 修复

- 将工作线程的 UI 操作改为 `view.post { ... }`。
- 加 Lint 规则：禁止非 UI 线程调用 View 系列方法。
- 上线 SyncBarrier 泄漏监控（§4.4 C 方案），作为兜底。

#### 验证

- 灰度 7 天后，相关用户的"主线程长时间无响应"率从 0.18% 降至 0.001%。

### 三道防线

```
开发期 ──► 编译期/CI ──► 上线期/运行期
   │              │              │
   ▼              ▼              ▼
[Lint]      [自动化基准]     [线上 SLO]
```

#### 编码期 Lint
- 主线程同步 IO 调用 → 警告
- 非 UI 线程访问 View → 错误

- 列表滚动基准用例：滚动 60s，P99 帧时长 ≤ 阈值。

#### 线上 SLO
- 大卡顿率 < 0.1%（中端机切片）。
- 卡顿会话率 < 3%。
- 错误预算耗尽 → 冻结新功能。

## 10.总结与延伸

### 10.1 五条核心原则

1. **卡顿是流水线阻塞的投影**。捕获 = 观测超时事件，归因 = 把超时区间还原为调用栈。
2. **均值是性能领域的谎言**。卡顿必须看 P95 / P99 + 大卡顿率，而非平均 FPS。
3. **任何单一方案都有盲区**。线上推荐"帧回调 + LooperPrinter（或等价）+ WatchDog 兜底 + 堆栈采样"四件套。
4. **on-CPU 与 off-CPU 卡顿要分清**。前者看火焰图找平顶；后者看 sched_switch + wakeup 链。
5. **求证 > 经验**。每个治理结论都要带"前后数据 + 置信区间 + 适用边界"。

### 10.2 五个常见误区

- ❌ 只看均值 FPS（见 §1.4 / §1.2）。
- ❌ 把所有耗时挪子线程（见 §6.1）。
- ❌ WatchDog 阈值 5s 设了就放心（见 §5.1）。
- ❌ 线下没复现就放过（机型 / 数据量 / 弱网会暴露）。
- ❌ 一次治理后就不管（必须建立防劣化）。
