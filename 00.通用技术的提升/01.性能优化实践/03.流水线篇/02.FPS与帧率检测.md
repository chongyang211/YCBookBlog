## 01.问题域定义

### 1.1 现象与代价

FPS 不达标的用户感知：

- **持续低帧（如 30fps）**：滚动 / 动画"不顺滑"，但用户能接受。
- **帧时长抖动**：均值 60fps 但偶尔 100ms 帧，用户感觉"一卡一卡"。
- **冻屏（>700ms 单帧）**：用户认为"卡死"。
- **撕裂（tearing）**：未开 Vsync 时画面上下错位。
- **掉帧链 / 帧延迟**：用户操作和画面响应之间的延迟感。

**业务代价（行业实测数据）**：

- 抖音、TikTok 内部数据：滑动帧率 P99 每提升 5ms，留存 +0.5%。
- 电商列表：滑动卡顿率每降 1%，浏览深度 +3%。
- 游戏：FPS 抖动直接影响用户口碑（Steam 评分中"流畅度"占很大权重）。

### 1.2 度量准则

按 [`卷零·02 §3`](../00.公共方法论/02.跨平台性能模型与指标体系.md) 的统一指标体系：

**资源视角（USE）**：见 `卷三·01 §1.2`。FPS 篇主要看 RED。

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 平均 FPS | 总帧数 / 总时间 | ≥ 目标帧率 95% |
| 帧时长 P50 | 中位帧时长 | < 帧预算 |
| 帧时长 P95 | 95% 分位帧时长 | < 1.5 × 帧预算 |
| 帧时长 P99 | 长尾帧 | < 2 × 帧预算 |
| 帧时长最大值 | 最差帧 | < 700ms（冻屏阈值）|
| 掉帧率 | 超时帧 / 总帧 | < 5% |

**用户感知（APDEX）**：

- *Satisfied*：连续 30 帧都按时
- *Tolerating*：单次掉帧 < 100ms
- *Frustrated*：冻帧 ≥ 700ms

> **关键约定**：**禁止单独看均值 FPS**。它对抖动几乎不敏感。必须配合 P95/P99/Max。详见 §5.1 实验。

### 1.3 行业基准与目标

| 平台 | 目标帧率 | 帧预算 | P99 阈值 |
|---|---|---|---|
| Android 60Hz | 60 fps | 16.67 ms | < 25 ms |
| Android 90/120Hz | 90/120 fps | 11.11/8.33 ms | < 1.5 ×预算 |
| iOS 60Hz | 60 fps | 16.67 ms | < 25 ms |
| iOS ProMotion 120Hz | 120 fps | 8.33 ms | < 12 ms |
| Web | 与显示器同步 | 16.67 ms | < 25 ms |
| 嵌入式 HMI | 30/60 fps | 33/16.67 ms | < 2 ×预算 |

带着这些问题阅读：

2. 为什么 P99 比均值有用得多？

## 02.第一性原理

> 本节回答三个根本问题：**①FPS 的物理本质是什么？②为什么"均值"无法反映流畅度？③同构之下平台差异在哪？**

### 2.1 FPS 本质定义

**一句话定义**：

> **FPS = 单位时间内成功被显示器扫描显示的帧数**。

这句话隐含两个不可商量的物理约束：

**约束一：FPS 上限由显示硬件决定，不由软件决定**

显示器以固定（或可变）频率扫描帧缓冲。无论应用渲染多少帧，**用户能看到的最大 FPS = 显示器刷新率**。60Hz 屏上即使应用渲染 200fps，用户依然只感知到 60fps（多余帧被丢弃）。

```
   应用渲染 ──▶ Frame Buffer ──▶ 显示器扫描 ──▶ 用户感知
       │             │              │
   产帧速率         缓冲深度       刷新率（硬上限）
```

**约束二：FPS 是"过去一段时间的统计"，不是瞬时值**

FPS 必须基于一段时间窗（通常 1 秒）统计。瞬时无所谓"FPS"，只有"这一帧的时长"。这是一个关键概念误区。

正确表述：
- ✅ "过去 1 秒内显示了 58 帧" → 58 FPS
- ✅ "这一帧花了 32ms"
- ❌ "现在 FPS 是 32ms"

### 2.2 帧时长分布模型

**为什么"帧时长分布"是 FPS 的本质**

FPS 是单一数字，但"流畅"是关于**每一帧时长**的分布特征。两个 60fps 应用，分布可能完全不同：

```
   应用 A：每帧 16ms（均匀）       应用 B：57 帧 13ms + 3 帧 100ms
   ───────────────                ─────────────────────────
   分布：方差极小                   分布：3 个尖峰
   均值 FPS：60                    均值 FPS：60
   P99 帧时长：16ms                P99 帧时长：100ms
   用户体验：流畅                   用户体验：每秒抖一下
```

**统计学上，FPS 的"流畅"应该用分布的尾部 (tail) 来描述**：

```
   "流畅" = 帧时长分布的 P99 < 1.5 × 帧预算
   "可接受" = 帧时长分布的 P95 < 1.5 × 帧预算
   "卡顿" = 任意单帧 > 700ms
```

这就是为什么所有性能监控系统都强制要求 **P50/P95/P99/Max 四元组**，而不是均值。

**单帧时长的"四态分类"**：

```
   ┌──────────────────────────────────────────┐
   │ 完美帧 (≤ 帧预算)                          │
   │ 16.67ms（60Hz）以内，无感                  │
   ├──────────────────────────────────────────┤
   │ 轻微掉帧（1-1.5× 帧预算）                  │
   │ 16-25ms，几乎无感                          │
   ├──────────────────────────────────────────┤
   │ 明显掉帧（1.5-3× 帧预算）                  │
   │ 25-50ms，能感知"卡了一下"                  │
   ├──────────────────────────────────────────┤
   │ 严重掉帧（3× 帧预算 - 700ms）               │
   │ 50-700ms，明显卡顿                         │
   ├──────────────────────────────────────────┤
   │ 冻帧（≥ 700ms）                            │
   │ 用户认为"卡死"                             │
   └──────────────────────────────────────────┘
```

### 2.3 跨平台同构原理

**为什么所有平台的 FPS 原理都同构**

所有有 UI 的平台都有"显示帧时钟 + 帧产出"两端，本质同构：

```
   通用 FPS 模型：

      [应用产帧] ──▶ [Buffer] ──▶ [显示器扫描]
           │                          │
      产帧速率（变量）              刷新率（定量）
           │                          │
           └──────[Vsync 同步]────────┘
```

每个平台都必须有：

| 抽象组件 | 解决什么问题 |
|---|---|
| 帧时钟订阅 | 知道"下一次显示什么时候发生" |
| 帧时长测量 | 知道"两次显示之间多久" |
| 帧分类 | 区分"按时帧 / 掉帧 / 冻帧" |
| 长尾统计 | P95/P99/Max 才能反映真相 |

**跨平台术语对照**

| 通用术语 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 帧时钟 | Choreographer / Vsync | CADisplayLink | requestAnimationFrame | 显示控制器 IRQ |
| 帧统计 API | FrameMetrics (24+) | MetricKit Hitches (14+) | PerformanceObserver | 厂商 SDK |
| 实时 FPS 显示 | "开发者选项 → GPU 呈现模式" | Instruments Core Animation | DevTools Frame Render | 串口日志 |
| 刷新率 | 60/90/120 Hz | 60/120 Hz | 与显示器同步 | 厂商定 |
| 自适应帧率 | Android 12+ ARR/VRR | ProMotion | 浏览器自适配 | 视设备 |

**同构带来的工程价值**

理解同构原理后：

1. **指标体系可对齐**：所有平台都用 P50/P95/P99/Max 四元组。
2. **采集方案可复用**：帧回调 + 系统 API + 屏幕直采 三件套通用。
3. **优化方向通用**：减少长尾帧、稳定帧时长分布。

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 帧时钟精度 | Vsync 中断（μs 级）| CADisplayLink（μs 级）| rAF（ms 级，部分浏览器）| 视硬件 |
| 系统提供分布数据 | FrameMetrics（API 24+）| Hitches Ratio (iOS 14+) | LCP/INP/CLS（部分）| 通常无 |
| 高刷率支持 | 12+ ARR | ProMotion (iPad 2017+, iPhone 13 Pro+) | 浏览器自动 | varies |
| 静态页面盲区 | 是（无 Vsync 请求即无 callback）| 同 | rAF 不调度 | 视实现 |
| 跨进程合成 | SurfaceFlinger | Render Server | Compositor | varies |

> 后续遇到平台特化点回引本节。

## 03.度量与采集

### 3.1 三类采集方案的本质

所有平台的 FPS 采集本质上只有 3 类（与 [`卷三·01 §3.1`](01.渲染管线与原理.md) 同构）：

```
   ① 帧时钟订阅（应用层 Vsync 监听）
   ② 系统帧 API（OS 提供阶段级数据）
   ③ 外部测量（高速摄像 / 屏幕直采）
```

下面对每一类做完整原理拆解。

---

**① 帧时钟订阅（FPS 采集主流方案）**

**核心原理（一句话）**：订阅 Vsync 信号，记录每次回调时间戳，差值即帧时长。

**工作机理**：

```java
class FpsMonitor implements Choreographer.FrameCallback {
    private long lastTime;
    private final List<Long> intervals = new ArrayList<>();

    public void start() {
        lastTime = System.nanoTime();
        Choreographer.getInstance().postFrameCallback(this);
    }

    @Override
    public void doFrame(long frameTimeNanos) {
        long interval = (frameTimeNanos - lastTime) / 1_000_000;  // ms
        intervals.add(interval);
        lastTime = frameTimeNanos;
        Choreographer.getInstance().postFrameCallback(this);  // 持续订阅
    }

    public Stats compute() {
        // 计算 P50/P95/P99/Max
        return Stats.compute(intervals);
    }
}
```

**物理本质**：

> 把"显示器节拍"作为可信参考时钟，统计每两次之间的间隔。

**为什么这样有效**：

- 与硬件物理同步，参考时钟可靠。
- 开销极低（每帧 < 1μs）。
- 直接反映"用户看到的帧"。

**局限根源**：

- **静态页面盲区**：无渲染请求 = 无回调（详见 [`卷三·01 §3.2`](01.渲染管线与原理.md)）。
- **不区分原因**：只知道"这一帧 32ms"，不知道哪段慢。
- **可变刷新率干扰**：硬编码 16.67ms 在 120Hz 屏会误判。

**适用边界**：所有应用 FPS 监控的基础方案。

---

**② 系统帧 API（细颗粒数据）**

**核心原理（一句话）**：使用系统提供的细颗粒帧统计 API，得到每帧的"输入 / 动画 / Layout / Draw / 合成"分解。

**工作机理**：详见 [`卷三·01 §3.1`](01.渲染管线与原理.md) 同章节。FPS 篇的关注点是"聚合统计"：

```java
window.addOnFrameMetricsAvailableListener((window, frameMetrics, dropCountSinceLastInvocation) -> {
    long total = frameMetrics.getMetric(FrameMetrics.TOTAL_DURATION);
    long layout = frameMetrics.getMetric(FrameMetrics.LAYOUT_MEASURE_DURATION);
    long draw = frameMetrics.getMetric(FrameMetrics.DRAW_DURATION);
    long sync = frameMetrics.getMetric(FrameMetrics.SYNC_DURATION);
    // 聚合到分位
    aggregator.add(total, layout, draw, sync);
});
```

**物理本质**：OS 直接告诉应用每帧的真实组成。

**适用边界**：定位到"哪个阶段超时"，配合方案 ① 做归因。

---

**③ 外部测量（金标准）**

**核心原理（一句话）**：用高速摄像 / 屏幕直采从用户角度测量物理 FPS。

**工作机理**：见 [`卷三·01 §3.1`](01.渲染管线与原理.md) 同章节。

**适用边界**：实验室基线测试 + 校准线上数据偏差。

---

**三种方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 帧时钟订阅 | Vsync 触发 | 帧级 | 极低 | 高 | ✅ | 无阶段拆解 |
| ② 系统帧 API | OS 提供 | 阶段级 | 极低 | 中 | ✅（API 受限）| 颗粒度由系统决定 |
| ③ 外部测量 | 屏幕外 | 物理时序 | 无 | 极高 | ❌ | 仅实验室 |

**方案的"组合定律"**：① 做线上 FPS 指标 + ② 做超时帧归因 + ③ 做实验室基线。

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| 帧时长 P99 | ✅ | ✅ | ✅ |
| 哪段超时（产帧/合成/显示） | ❌ | ✅ | 推断 |
| 静态页面期间无 callback | ❌ | ❌ | ❌（无变化）|
| 系统合成丢帧（应用看似已提交）| ❌ | ✅ | ✅ |
| 端到端延迟 | ❌ | 部分 | ✅ |

**盲区一：静态页面**：无 Vsync 请求时无回调。补救：

- 持续触发空 frame callback 维持监控。
- 配合卷三·03 卡顿监控（LooperPrinter）。

**盲区二：合成段隐性丢帧**：应用提交了帧，但 SurfaceFlinger 因 GPU 慢丢了。只有 FrameTimeline（Android 12+）能发现。

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 帧时钟 | `Choreographer.postFrameCallback` | `CADisplayLink` | `requestAnimationFrame` | Vsync IRQ |
| 系统帧 API | FrameMetrics (24+) / FrameTimeline (12+) | MetricKit Hitches (14+) | Web Vitals API | 厂商 |
| 长任务 | LooperPrinter | os_signpost | longtask Performance | 业务 |
| 外部测量 | HDMI / 高速摄像 | 高速摄像 | 浏览器 Tracing + 摄像 | HDMI |
| 实时显示 | dumpsys SurfaceFlinger | Instruments | DevTools Frame | 串口 |

### 3.4 数据可信度评估

| 数据 | 方案 ① | 方案 ② | 偏差 |
|---|---|---|---|
| FPS 平均 | < 2% 误差 | < 1% | ① 漏合成段 |
| 帧时长 P99 | < 5% 偏低 | 准确 | ① 不感知 GPU |
| 阶段拆解 | 不可见 | 准确 | ② 专属 |
| 端到端 | 不可测 | 不可测 | 仅 ③ |

## 04.归因方法

### 4.1 FPS 归因决策树

```
FPS 不达标
   │
   ├── 帧时长分布尖峰（偶发掉帧）──▶ 长尾归因
   │                               ├─ GC 触发？查 ART log
   │                               ├─ 大任务？查主线程 trace
   │                               └─ 系统抢占？查 sched
   │
   ├── 帧时长分布整体偏高 ────────▶ 持续慢
   │                               ├─ 走渲染篇决策树（CPU/GPU/同步段）
   │                               └─ 检查布局复杂度
   │
   ├── FPS 突然降低（场景特定）────▶ 场景关联
   │                               ├─ 滚动期？列表 onBindViewHolder
   │                               ├─ 动画期？动画计算
   │                               └─ 启动后？资源加载
   │
   └── 帧时长抖动严重 ────────────▶ 抖动归因
                                  ├─ 内存抖动（GC 频繁）
                                  ├─ 后台干扰（其他进程）
                                  └─ 调度抖动（CPU 调度延迟）
```

### 4.2 抖动归因法

**抖动归因的核心思路**：不是看"哪一帧慢"，而是看"为什么时长不稳定"。

抖动的常见根因：

| 根因 | 特征 | 工具 |
|---|---|---|
| 内存抖动（频繁 GC）| 帧时长突然 +5-20ms 周期性 | ART log + heap profile |
| 后台进程抢 CPU | 帧时长偶发 +10-100ms | 系统级 trace |
| 锁竞争 | 帧时长偶发 +5-50ms | Lock contention profiler |
| 异步任务回主线程 | 帧时长偶发 +几十 ms | LooperPrinter |
| 温度降频 | 整段 FPS 缓慢下降 | thermal trace |

**关键经验**：

- 如果 P99 - P50 > 20ms → 一定有抖动源
- 如果 Max > 200ms → 一定有阻塞型问题（IO / 锁 / GC）

### 4.3 长尾分位归因法

**为什么必须用分位看 FPS**

均值对长尾极不敏感：

- 100 帧 + 1 帧 1000ms = 总时长 1100ms / 101 帧 = 10.9 ms/帧 = 91.7 fps（"看起来"很正常）
- 但用户看到了 1 次冻屏！

**分位看法**：

- P50：典型表现
- P95：5% 用户感知的体验
- P99：1% 用户感知的体验
- Max：最差体验（极少但极重要）

**分位优化策略**：

- 先优 Max（消除冻屏）
- 再优 P99（消除明显卡顿）
- 再优 P95（减少抖动）
- 最后看 P50（追求基线流畅）

### 4.4 可变帧率归因

Android 12+ ARR、iOS ProMotion 引入可变刷新率，FPS 监控逻辑要改：

**问题**：硬编码 16.67ms 作为帧预算 → 在 120Hz 屏上变成 8.33ms 帧预算，但代码仍判断 "16ms 内 = 正常"。

**修复**：

- 读取系统当前刷新率（`Display.getRefreshRate()` / `UIScreen.maximumFramesPerSecond`）。
- 帧预算 = 1000 / 当前刷新率。
- 评估时用相对于预算的比例，而非绝对时间。

## 05.求证实验 ⭐

### 5.1 实验一：均值掩盖抖动

**Step 1 — 原始观察**

很多团队报 FPS 均值（如 58.5 fps），用户却频繁反馈"卡"。**为什么数据和体感不一致？**

**Step 2 — 提出疑问**

> **均值 FPS 与用户感知"流畅度"的相关性有多大？P99 帧时长是否更相关？**

**Step 3 — 形成假设**

**H₁**：均值 FPS 与用户感知**弱相关**（r < 0.4）；P99 帧时长强相关（r > 0.8）。  
**H₀**：均值 FPS 与用户感知强相关。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 |
| 测试场景 | 同应用同场景，构造 10 种不同"FPS 分布"配置 |
| 配置示例 | (a) 60fps 均匀 (b) 55fps 均匀 (c) 60fps + 1 个 100ms 帧 (d) 60fps + 5 个 50ms 帧 ... |
| 用户主观打分 | 30 名测试用户对每种配置打"流畅度" 1-5 分 |
| 主指标 | 均值 FPS / P99 帧时长 与 用户评分的相关系数 |

**Step 5 — 实测数据**

| 配置 | 均值 FPS | P99 帧时长 | 用户均分 |
|---|---|---|---|
| (a) 60 fps 均匀 | 60 | 17 ms | 4.9 |
| (b) 55 fps 均匀 | 55 | 19 ms | 4.6 |
| (c) 60 fps + 1×100ms | 59 | 100 ms | 3.4 |
| (d) 60 fps + 5×50ms | 58 | 50 ms | 3.6 |
| (e) 45 fps 均匀 | 45 | 22 ms | 4.1 |
| (f) 60 fps + 1×300ms | 58 | 300 ms | 2.1 |

**Step 6 — 验证 / 修正**

- 均值 FPS 与用户评分相关系数 r = 0.31（弱相关）。
- P99 帧时长与用户评分相关系数 r = -0.87（强负相关，时长越大评分越低）。
- 配置 (e) 均值更低但更流畅；配置 (f) 均值高但用户最差。

**Step 7 — 提炼结论**

> **均值 FPS 与用户感知弱相关 (r=0.31)，P99 帧时长强相关 (r=-0.87)。  
> 优化目标应是 P99 而非均值。**

工程意义：

- 删除所有"均值 FPS"为唯一指标的看板。
- 新指标体系必有 P95 / P99 / Max。
- 性能 review 重点看长尾。

**Step 8 — 边界**

- 测试场景为滚动 / 动画类。静态页面无明显帧率概念，结论不适用。
- 用户群差异：游戏玩家对抖动更敏感；普通用户对均值偏低更宽容。

---

### 5.2 实验二：采样间隔精度

**Step 1 — 原始观察**

很多监控 SDK 用"每秒采样一次 FPS"，但**1 秒粒度是否能反映真实抖动？**

**Step 2 — 提出疑问**

> **不同采样窗口（100ms / 1s / 10s）的 FPS 数据对"长尾"的反映能力差异多大？**

**Step 3 — 形成假设**

**H₁**：窗口越小越能反映瞬时抖动；1s 窗口已损失大部分 P99 信息；10s 窗口几乎只看均值。  
**H₀**：采样窗口不影响。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 测试场景 | 构造已知数据：60 fps 中插入 5 个 100ms 帧 |
| 采样窗口 | 100ms / 1s / 10s |
| 主指标 | 每个窗口看到的 P99 帧时长、能否识别"100ms 帧" |

**Step 5 — 实测数据**

| 窗口 | 窗口数 | 100ms 帧识别率 | 最大窗口 P99 |
|---|---|---|---|
| 100ms 窗口 | 600 / 分钟 | 100%（每个 100ms 帧落在单独窗口）| 100 ms |
| 1s 窗口 | 60 / 分钟 | 仍可识别（但被平均后均值看起来正常）| 100 ms |
| 10s 窗口 | 6 / 分钟 | 抖动被严重稀释 | 30 ms（被均值化）|

**Step 6 — 验证 / 修正**

- 1s 窗口能识别但需要看 P99 数据。
- 10s 窗口几乎丢失抖动信息。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **采样窗口应 ≤ 1s。每帧采样（实时记录）+ 1s 聚合是最佳实践。  
> 不要用 5s / 10s 窗口聚合。**

工程意义：

- 数据采集："每帧一记录"，避免聚合丢信息。
- 上报：可以 5-10s 上报一次，但要带原始分位数（P50/95/99）不要重新聚合。

**Step 8 — 边界**

- 不同场景对窗口敏感度不同。游戏要求 100ms 窗口；普通应用 1s 即可。

---

### 5.3 实验三：高刷增益

**Step 1 — 原始观察**

90/120Hz 屏被宣传为"更流畅"，但**真的更流畅吗？应用如何充分利用？**

**Step 2 — 提出疑问**

> **同一应用在 60Hz 和 120Hz 屏上，用户感知差异有多大？**

**Step 3 — 形成假设**

**H₁**：在应用能稳定产出 120 fps 时，用户感知"明显更流畅"；如果应用最高只能产 60 fps，120Hz 屏几乎无增益。  
**H₀**：高刷自动让所有应用变流畅。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 7 Pro（90/120Hz 可切）|
| 应用 A | 简单 ListView 滚动（容易产 120 fps）|
| 应用 B | 复杂瀑布流（最多产 60 fps）|
| 测试 | 30 用户分别用 60Hz / 120Hz 体验，主观打分 |

**Step 5 — 实测数据**

| 应用 | 60Hz 帧率 | 60Hz 评分 | 120Hz 帧率 | 120Hz 评分 |
|---|---|---|---|---|
| A (简单) | 60 fps | 4.4 | 118 fps | 4.8 |
| B (复杂) | 55 fps | 3.9 | 60 fps（被业务卡）| 4.0 |

**Step 6 — 验证 / 修正**

- 应用 A 在 120Hz 下评分明显提升。
- 应用 B 因应用层卡 60 fps，高刷"白买"。

**Step 7 — 提炼结论**

> **高刷屏的价值取决于应用自身能否产足够多帧。  
> 应用层瓶颈不解决，高刷屏几乎无用。**

工程意义：

- 上 120Hz 前先优化应用到稳定 120 fps，否则浪费。
- 应用应"自适应刷新率"：能产 120 就申请 120Hz，能产 60 就申请 60Hz（省电）。

**Step 8 — 边界**

- 静态画面无所谓高刷。
- 文字阅读类应用高刷增益不明显（用户察觉不到）。

---

### 5.4 三大实验启示

```
   均值掩盖抖动     → 必须用 P95/P99/Max          ─┐
                                                    │
   采样间隔精度     → 窗口 ≤ 1s，原始数据不聚合     ├─▶ FPS = 长尾游戏
                                                    │
   高刷增益         → 应用层瓶颈不优化就无增益       ─┘
```

**统一启示**：

- **流畅是分布问题，不是均值问题**。所有数据看板必须改用分位。
- **数据采集要保留原始性**，避免过早聚合。
- **高刷不是免费午餐**，应用层必须配合优化才能发挥价值。

## 06.优化策略

### 6.1 通用治理矩阵

FPS 优化大部分来自渲染篇（[`卷三·01`](01.渲染管线与原理.md)）和卡顿篇（[`卷三·03`](03.卡顿捕获与归因.md)）。本节聚焦"采集与监控"层面的优化：

| 维度 | 治理方向 | 通用手段 |
|---|---|---|
| 指标体系 | 用分位代替均值 | P50/P95/P99/Max 四元组 |
| 采集精度 | 每帧记录 | 窗口 ≤ 1s 聚合 |
| 数据可信度 | 多方案校准 | 线上 ① + 实验室 ③ |
| 适配可变帧率 | 动态读刷新率 | 不硬编码 16.67 |
| 静态页面盲区 | 配合卡顿监控 | LooperPrinter 兜底 |

### 6.2 平台特化策略

**Android 特化**：

- 主用 Choreographer.postFrameCallback 持续订阅。
- API 24+ 补充 FrameMetrics 阶段数据。
- API 31+ 用 FrameTimeline 识别合成段隐性丢帧。
- 用 `Display.getRefreshRate()` 动态获取帧预算。

**iOS 特化**：

- CADisplayLink + MetricKit Hitches 组合。
- 用 `UIScreen.maximumFramesPerSecond` 适配 ProMotion。
- Hitch Time Ratio < 5ms/s 是苹果推荐目标。

**Web 特化**：

- requestAnimationFrame + PerformanceObserver `longtask`。
- 用 Web Vitals 的 INP（响应延迟）补充。
- 大于 50ms 的任务都算 long task。

**嵌入式特化**：

- 显示控制器 IRQ 计数 + 时间戳。
- 自定义"帧时长直方图"输出到串口。

### 6.3 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 |
|---|---|---|---|---|
| 极高 | 把"均值 FPS"看板替换为 P95/P99 | 性能问题被正确识别 | 1 天 | 零 |
| 极高 | 每帧记录 + 1s 聚合 | 数据精度大幅提升 | 几天 | 低 |
| 高 | 适配可变刷新率 | 高端机数据准确 | 1 周 | 低 |
| 高 | FrameMetrics 阶段化 | 归因能力提升 | 1 周 | 低 |
| 中 | 静态页面卡顿兜底 | 闭环监控 | 1-2 周 | 低 |
| 中 | 实验室基线校准 | 数据可信度高 | 一次性 | 低 |
| 低 | 自己实现 hitch 算法 | 极少收益 | 高 | 中 |

**避免反向收益**：

- 过度采集：每帧记录 + 调用栈快照，开销巨大反而引入卡顿。
- 过度上报：把每帧数据全上报，流量爆炸。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某直播应用 Android / iOS / Web 三端都报"60fps 但用户反馈卡"。

**现象**：均值 60 fps，但用户大量反馈"偶尔卡一下"。

**度量与归因**：

切换到 P95/P99 后发现：

| 平台 | 均值 FPS | P99 帧时长 |
|---|---|---|
| Android | 59 | 180 ms |
| iOS | 60 | 95 ms |
| Web | 58 | 220 ms |

**假设与求证**：

P99 帧时长太长是用户体感差的元凶。归因发现：

- Android：直播弹幕重绘 + GC 抖动
- iOS：图片加载导致主线程偶发阻塞
- Web：长任务（JSON 解析）阻塞主线程

**护栏检查**：优化不能损害业务功能。

**修复**：三端统一升级监控指标体系（P95/P99），针对长尾帧分别治理。

**验证**：

| 平台 | 优化前 P99 | 优化后 P99 | 用户卡顿反馈降幅 |
|---|---|---|---|
| Android | 180 ms | 35 ms | -75% |
| iOS | 95 ms | 25 ms | -68% |
| Web | 220 ms | 50 ms | -80% |

**统一启示**：**FPS 监控必须用分位**。所有团队都该把"均值 FPS"指标改掉。

### 7.2 平台特异案例

**背景**：Android 应用上 120Hz 屏后，用户反馈"反而更卡"。

**现象**：高刷屏比 60Hz 屏用户评分还低。

**度量与归因**：

- 60Hz 屏：均值 58 fps，P99 18ms。流畅。
- 120Hz 屏：均值 90 fps，P99 22ms。但**有时 P99 75ms**。

为什么 P99 偶发飙高？因为应用同步初始化 ListView 内容在 120Hz 屏上预算更紧（8.33ms vs 16.67ms），原本能"挤进 16ms"的任务现在超时了。

**假设与求证**：

**假设**：高刷屏帧预算更紧，原本"勉强达标"的代码暴露了瓶颈。

**实验**：把 ListView 的 onBindViewHolder 中的同步任务异步化。120Hz 下 P99 从 75ms 降到 12ms。✅

**修复**：所有同步任务必须按 120Hz 帧预算（8.33ms）验证。

**验证**：120Hz 下 P99 < 12ms，用户反馈正面。

**边界与上线策略**：高刷屏要做"严苛预算评估"，原本对 60Hz 够用的代码可能不够。

## 08.防劣化与长效治理

### 8.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
[Lint]      [自动化基准]     [线上 SLO]
```

### 8.2 编码期 Lint

- 监控代码硬编码 16.67ms → 警告（应动态读刷新率）。
- 性能看板配置只有"均值 FPS"指标 → 错误。
- 采样窗口 > 1s → 警告。
- 帧回调中做重任务 → 错误。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 滚动基准用例：P99 帧时长 ≤ 阈值（25ms @60Hz / 12ms @120Hz）。
- Max 帧时长 ≤ 200ms。
- 帧时长分布 95% > 帧预算时阻塞合并。

**线上 SLO**：

- 滚动场景 P99 帧时长 < 25ms（60Hz）/ < 15ms（120Hz）。
- 冻屏率 < 0.05%（任意单帧 ≥ 700ms 的比例）。
- 平均掉帧率 < 5%。

## 10.总结与延伸

### 10.1 五条核心原则

1. **流畅是分布问题**：P95/P99/Max 优于均值。
2. **每帧记录**：原始数据采集要细，聚合可放宽。
3. **动态适配刷新率**：不要硬编码 16.67ms。
4. **三方案组合**：① 帧时钟 + ② 系统 API + ③ 外部测量。
5. **静态页面不忘**：配合卡顿监控做兜底。

### 10.2 五个常见误区

1. **"均值 60 fps 就流畅"**：错（P99 才重要）。
2. **"高刷屏自动更流畅"**：错（应用层不优化无增益）。
3. **"采样窗口 10s 够了"**：错（抖动信息被稀释）。
4. **"无回调 = 无问题"**：错（静态页面是盲区）。
5. **"应用 FPS = 显示 FPS"**：错（OS 可能丢帧）。

### 10.3 延伸阅读

- Android Vitals：*Frame Rendering Performance*
- WWDC 2020: *Eliminate Hitches with the Render Loop*
- Web Vitals：*Cumulative Layout Shift* / *Interaction to Next Paint*
- Brendan Gregg：*Systems Performance* Chapter 2（USE/RED）
- 论文：*Statistically Rigorous Java Performance Evaluation*（Georges 2007）

## 一句话总结

> **FPS 是抖动游戏，不是均值游戏。  
> 60fps 均值 + P99 = 200ms 远不如 45fps 均值 + 帧时长稳定。  
> 一切优化要看 P95/P99/Max，而不是均值。**
