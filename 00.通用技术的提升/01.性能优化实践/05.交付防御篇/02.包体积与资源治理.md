## 01.问题域定义

### 1.1 现象与代价

包体积过大的影响链：

- **应用商店警告**：Google Play 在 APK 超 150MB 时建议拆分。
- **下载放弃率**：每多 10MB，安装转化下降 1-3%。
- **流量浪费**：用户用流量下载大包体验差。
- **冷启动慢**：包大 → DEX 加载慢 / dyld 慢（详见 [`卷四·01`](../04.业务专项篇/01.App冷启动优化.md)）。
- **存储占用**：长期占用用户设备空间。

**业务代价（行业实测数据）**：

- Google 数据：APK 每减 6MB，安装转化 +1%（中位）。
- 印度、东南亚等地区对包体积更敏感（设备存储小、流量贵）。
- 大包应用更容易被用户"卸载腾空间"。

### 1.2 度量准则

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 包体积（下载）| APK / IPA / Web Bundle | Android < 30MB / iOS < 60MB / Web < 200KB Gz |
| 安装后体积 | 解压 + 资源缓存 | < 100MB 中等 |
| 单文件最大 | 资产中最大单文件 | 图片 < 200KB / so < 5MB |
| 体积增长 | 每个版本增量 | < 5% |

### 1.3 行业基准与目标

| 平台 | 安装包 | 安装后 | 单图 |
|---|---|---|---|
| Android（轻量）| < 20MB | < 60MB | < 200KB |
| Android（重型）| < 80MB | < 300MB | < 500KB |
| iOS（含资源）| 通常更大 | < 200MB | < 500KB |
| Web | < 200KB（首屏 Gz） | < 5MB（全量） | < 100KB |

### 1.4 反直觉问题清单

带着这些问题阅读：

1. 包体积每多 1MB 转化率掉多少？
2. ProGuard / R8 真的能减少 30% 吗？
3. 多 ABI 包 vs 单 ABI 体积差多少？
4. 动态分发（App Bundle）能减多少？
5. WebP 替代 PNG 能省多少？
6. AAB 上传后用户实际下载多大？
7. iOS Bitcode 影响体积吗？
8. 代码混淆能减小多少？

## 02.第一性原理

### 2.1 包体积本质

**一句话定义**：

> **包体积 = 应用安装包中所有"代码 + 资源 + 元数据"的总和**。

包体积既是"用户下载时的数据量"，也是"应用运行时的硬盘占用"。前者影响安装转化，后者影响用户长期保留。

### 2.2 三部分组成模型

```
   总包体积 = 代码 + 资源 + 元数据 / 配置

   ┌──────────────────────────────────────┐
   │ ① 代码（30-60%）                       │
   │ - DEX / Java / Kotlin（Android）       │
   │ - Mach-O 可执行 / dylib（iOS）         │
   │ - JS Bundle（Web）                     │
   │ - .so / .a Native 库                   │
   ├──────────────────────────────────────┤
   │ ② 资源（30-60%）                       │
   │ - 图片（最大头）                       │
   │ - 字符串 / 配置                        │
   │ - 字体 / 音频 / 视频                   │
   │ - HTML / CSS                          │
   ├──────────────────────────────────────┤
   │ ③ 元数据 / 配置（5-10%）               │
   │ - Manifest / Info.plist                │
   │ - 签名 / 加固元数据                    │
   │ - 调试信息                             │
   └──────────────────────────────────────┘
```

**关键认知**：

- 优化前必须**先做组成分析**，不知道大头就不知道往哪优化。
- 不同应用大头不同：游戏 > 资源；工具 > 代码；图像 > 图片资源。

### 2.3 跨平台同构原理

所有平台的包构成都是"可执行 + 资源 + 元数据"：

```
   通用包模型：

      [可执行]   +   [资源]   +   [元数据]
       compiled     assets       meta
       Android: DEX  Android: res  Android: AndroidManifest
       iOS: Mach-O   iOS: assets   iOS: Info.plist
       Web: JS       Web: HTML/CSS/img Web: HTTP headers
```

每个平台都必须有：

| 抽象组件 | 解决什么问题 |
|---|---|
| 编译压缩 | 优化代码体积 |
| 资源优化 | 选择合适格式 / 压缩级别 |
| 多分发 | 按设备特性分包 |
| 动态加载 | 按需下载非首屏内容 |

**跨平台术语对照**

| 通用术语 | Android | iOS | Web |
|---|---|---|---|
| 包格式 | APK / AAB | IPA | 静态资源 |
| 代码压缩 | R8 / ProGuard | LLVM strip | Terser / esbuild |
| 资源压缩 | aapt2 | Asset Catalog | 服务端压缩 / brotli |
| 动态分发 | App Bundle Dynamic | App Thinning | Code Splitting / Dynamic Import |
| ABI 拆分 | abiFilters | App Thinning（Bitcode 转译）| 浏览器解析 |

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web |
|---|---|---|---|
| 上限警告 | Play 150MB+ 警告 | App Store 200MB+ 蜂窝下载 | LCP < 2.5s |
| 代码混淆 | R8 全方位优化 | LLVM 优化 | minify / Terser |
| 多 ABI | 默认含 arm64 + armv7（部分仍含 x86） | 自动 thin | 浏览器自动 |
| 资源优化 | WebP / 9-patch / drawable-density | Asset Catalog / vector | WebP / AVIF |
| 动态分发 | App Bundle 自动按需 | App Thinning（按设备） | Service Worker 缓存 |
| 安装大小 | 解压后通常 2-3× 包大小 | 同 | N/A |

> 后续遇到平台特化点回引本节。

## 03.度量与采集

### 3.1 三类采集方案的本质

```
   ① 包大小总量（构建产物）
                ② 内部组成分析（apkanalyzer / Bundle Analyzer）
                            ③ 用户实际下载（Play Console / App Store Connect）
```

---

**① 包大小总量**

**核心原理（一句话）**：每次构建后记录最终包大小，跟踪版本间变化。

**适用边界**：CI 必备的最简监控。

---

**② 内部组成分析**

**核心原理（一句话）**：用工具分析包内每个文件 / 每个类的体积，找到大头。

**工作机理**：

| 平台 | 工具 |
|---|---|
| Android | `apkanalyzer` / Android Studio APK Analyzer |
| iOS | Xcode App Thinning Size Report |
| Web | webpack-bundle-analyzer / source-map-explorer |

**适用边界**：定向优化必备。

---

**③ 用户实际下载量**

**核心原理（一句话）**：渠道数据反映用户最终下载体积（与构建产物可能不同，因为分发会按设备 thin）。

**适用边界**：评估实际用户感知。

---

**三类方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 主要局限 |
|---|---|---|---|---|---|
| ① 总量 | 构建产物 | 文件级 | 极低 | 高 | 不知组成 |
| ② 组成 | 内部分析 | 类 / 资源级 | 极低 | 高 | 工具差异 |
| ③ 实际下载 | 渠道数据 | 用户级 | 渠道提供 | 中 | 数据滞后 |

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| 包总大小 | ✅ | ✅ | ✅（实际下载）|
| 哪个资源大 | ❌ | ✅ | ❌ |
| 哪个类大 | ❌ | ✅ | ❌ |
| 用户实际下载 | ❌ | ❌ | ✅ |
| 多 ABI 实际占比 | ❌ | 部分 | ✅ |

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web |
|---|---|---|---|
| 总量 | apk / aab 文件大小 | ipa 文件大小 | dist 文件夹大小 |
| 组成 | apkanalyzer / AS APK Analyzer | App Thinning Size Report | bundle-analyzer |
| 实际下载 | Play Console "Download size" | App Store Connect | CDN 日志 |
| 增量分析 | apkanalyzer compare | 自定义 | 自定义 diff |

### 3.4 数据可信度评估

| 数据 | 可信度 | 偏差来源 |
|---|---|---|
| 构建产物大小 | 高 | 文件系统精确 |
| 各资源占比 | 高 | 工具直接分析 |
| 实际下载（Play 数据）| 高 | Google 直接统计 |
| 安装后大小 | 中 | 解压 + 缓存 + dex2oat 等差异 |

## 04.归因方法

### 4.1 包体积决策树

```
包体积过大
   │
   ├── 代码占比 > 50% ──▶ 代码优化
   │                     ├─ 启用 R8 / Terser 全量
   │                     ├─ 删除未使用的库
   │                     └─ 评估 Native .so 大小
   │
   ├── 资源占比 > 50% ──▶ 资源优化
   │                     ├─ 图片格式（WebP / AVIF）
   │                     ├─ 大资源动态分发
   │                     └─ 压缩级别（aapt2 / Asset Catalog）
   │
   ├── ABI 占比 ──────────▶ ABI 优化
   │                     ├─ 删除 x86 / armv7（如已不支持）
   │                     └─ 用 App Bundle 自动按需
   │
   └── 元数据 / 调试 ───▶ 元数据优化
                       ├─ 删除调试符号（release）
                       └─ 删除未用 manifest 配置
```

### 4.2 资源占比归因

资源中典型分布：

| 类型 | 典型占比 | 优化方向 |
|---|---|---|
| 图片 | 40-60% | 现代格式、下采样、按需分发 |
| 字体 | 5-15% | 子集化、按需加载 |
| 音频 / 视频 | 视应用 | 低码率、按需下载 |
| 字符串 | 5-10% | 多语言按需加载 |
| 其他 | 视情况 | 评估必要性 |

### 4.3 代码占比归因

代码中典型分布：

| 类型 | 占比 | 优化 |
|---|---|---|
| 业务代码 | 视项目 | R8 / Terser 移除未用 |
| 第三方库 | 通常大头 | 评估必要性 / 替换轻量库 |
| Native .so | 视项目 | strip / 分 ABI |
| 编译产物 | 视编译选项 | release 编译 |

### 4.4 ABI 与多分包归因

Android 多 ABI 的典型情况：

```
   只含 armv7：             ~10-30 MB
   armv7 + arm64：           ~20-60 MB
   armv7 + arm64 + x86 + x86_64： ~40-120 MB
```

**App Bundle 后用户实际下载只含设备 ABI，节省 50%+**。

## 05.求证实验 ⭐

### 5.1 实验一：体积与转化率

**Step 1 — 原始观察**

工程师都听过"包小转化高"，但**到底相关性多大？**

**Step 2 — 提出疑问**

> **包大小每减少 X MB，安装转化率提升多少？是线性还是有阈值？**

**Step 3 — 设计实验**

某 App 在 6 个月内做了多次包优化，对应转化率变化（已脱敏）：

| 版本 | 包大小 (MB) | 安装转化率 |
|---|---|---|
| v1.0 | 65 | 38% |
| v1.5 | 50 | 41% |
| v2.0 | 35 | 45% |
| v2.5 | 25 | 47% |
| v3.0 | 20 | 48% |

**Step 4 — 实测数据**

- 65 → 35 MB：转化率 +7%（每减 10MB +2.3%）。
- 35 → 20 MB：转化率 +3%（每减 10MB +2%）。
- 20 → 15 MB：边际收益递减。

**Step 5 — 提炼结论**

> **包大小 65 → 35 MB 区间内，每减 10MB 转化率 +2-2.5%。  
> 20 MB 以下边际收益递减。**

工程意义：

- 重点优化 30-50MB 区间应用。
- 已经 20MB 以下不必狂减，把精力投到其他地方。
- 不同地区 / 用户群差异：印度 / 东南亚比北美 / 欧洲更敏感。

**Step 6 — 边界**

- 重型应用（如游戏）有不同曲线（用户预期就是大）。
- 一线品牌应用（用户已认知品牌）不那么敏感。

---

### 5.2 实验二：R8 收益

**Step 1 — 原始观察**

R8 是 Android 默认混淆压缩工具，**实际收益多少？**

**Step 2 — 提出疑问**

> **R8 各项功能（缩减 / 优化 / 混淆）分别贡献多少包减小？**

**Step 3 — 设计实验**

| 配置 | 描述 |
|---|---|
| A | R8 完全关闭 |
| B | 仅混淆（minifyEnabled, 不 shrink） |
| C | minify + shrinkResources |
| D | 全量（含 R8 fullMode） |

**Step 4 — 实测数据**

| 配置 | DEX 大小 | 资源大小 | 总包 | 减小 |
|---|---|---|---|---|
| A 关闭 | 18 MB | 15 MB | 38 MB | - |
| B 仅混淆 | 14 MB | 15 MB | 33 MB | -13% |
| C +shrinkRes | 14 MB | 11 MB | 28 MB | -26% |
| D 全量 | 11 MB | 10 MB | 25 MB | -34% |

**Step 5 — 提炼结论**

> **R8 全量启用能让 Android 包减 30-35%。  
> 不启用 R8 是巨大的浪费。**

工程意义：

- 必须启用 R8（Android Studio 默认）。
- 必须 shrinkResources（删除未用资源）。
- R8 fullMode 需要测试兼容性。

**Step 6 — 边界**

- R8 可能与某些反射 / 动态加载库冲突，需配 keep 规则。
- iOS 类似工具是 LLVM 优化（自动）。
- Web 用 Terser / esbuild 类似收益。

---

### 5.3 实验三：动态分发收益

**Step 1 — 原始观察**

App Bundle 上传后用户实际下载多大？相比传统 APK 节省多少？

**Step 2 — 提出疑问**

> **App Bundle 按设备 / 屏幕 / 语言分发，相比"含全部"的 APK 节省多少？**

**Step 3 — 设计实验**

某 App 同一版本：

- A 传统 APK（含全部 ABI / 屏幕密度 / 语言）
- B App Bundle（用户按设备下载）

**Step 4 — 实测数据**

| 设备 | A APK | B AAB 下载 | 节省 |
|---|---|---|---|
| arm64 + 1080P + 简中 | 80 MB | 38 MB | 53% |
| armv7 + 720P + 英文 | 80 MB | 32 MB | 60% |
| 平均 | 80 MB | 36 MB | 55% |

**Step 5 — 提炼结论**

> **App Bundle 平均节省 50%+ 用户下载量，是巨大的"白送"收益。**

工程意义：

- 必须用 App Bundle 上架（Google Play 已强制）。
- iOS 的 App Thinning 类似（自动）。
- Web 用 Code Splitting 实现"按需加载"。

**Step 6 — 边界**

- 部分非 Play 渠道仍需 APK，需要单独打包（变体管理）。
- 国内市场仍以 APK 为主，需要自己设计动态分发。

---

### 5.4 三大实验启示

```
   体积 vs 转化   → 30-50MB 区间每减 10MB +2% ─┐
                                                │
   R8 收益        → -30-35% 包大小             ├─▶ 包优化 = 工具用足 + 动态分发 + 关注用户分布
                                                │
   动态分发       → -50% 用户实际下载          ─┘
```

**统一启示**：

- **R8 + App Bundle 是必做基线**：能减 50%+ 不开就是浪费。
- **关注用户分布**：不同地区对包体积敏感度不同。
- **数据驱动 ROI**：每个优化都要量化转化率收益。

## 06.优化策略

### 6.1 通用治理矩阵

| 维度 | 治理方向 | 通用手段 |
|---|---|---|
| 代码 | 移除未用 | R8 / Terser / Tree Shaking |
| 代码 | 压缩混淆 | minify / mangle |
| 代码 | 替换重型库 | 评估每个三方库收益 |
| 代码 | Native strip | release 编译去调试符号 |
| 资源 | 现代格式 | WebP / AVIF / HEIC |
| 资源 | 下采样 | 按目标尺寸 |
| 资源 | 删除未用 | shrinkResources / Asset Catalog |
| 配置 | 多 ABI | abiFilters / App Bundle |
| 配置 | 多语言 | 按需下载 |
| 配置 | 调试信息 | release 去除 |
| 分发 | 动态分发 | App Bundle / Code Splitting |
| 分发 | 按需下载 | Dynamic Feature / Lazy Load |

### 6.2 平台特化策略

**Android 特化**：

- R8 全量开启 + fullMode。
- 上架 App Bundle（Play 必须）。
- Dynamic Feature 把次要模块独立。
- abiFilters 删除已无设备的 ABI（如 armv7 / x86）。
- 资源 build.gradle resConfigs 限制语言。

**iOS 特化**：

- App Thinning 系统自动（无需配置）。
- 启用 Bitcode 让 Apple 后期优化（已废弃于 iOS 17 SDK）。
- Asset Catalog 集中管理资源。
- LLVM 已自动 strip dead code。
- On-Demand Resources 按需下载。

**Web 特化**：

- Tree Shaking + Terser / esbuild。
- Code Splitting 按路由 / 按需。
- 资源 brotli 压缩（替代 gzip）。
- WebP / AVIF + `<picture>` fallback。
- Service Worker 长缓存。

**嵌入式特化**：

- 静态规划资源大小。
- 只编译必要功能（编译期 #define 控制）。
- OTA 包做差分（相对上一版本只发增量）。

### 6.3 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 |
|---|---|---|---|---|
| 极高 | 启用 R8 全量 | -30-35% Android | 1 天（含调试 keep）| 中 |
| 极高 | 上 App Bundle | -50% 用户下载 | 1 周 | 低 |
| 极高 | WebP 替代 PNG / JPEG | -30% 资源 | 1-2 周 | 低 |
| 高 | 删除无用 ABI | -20-40% | 几天 | 中 |
| 高 | Dynamic Feature 拆分 | -30-50%（首次安装）| 1 月 | 中 |
| 中 | 删除未用三方库 | -5-15% | 1-2 周 | 中（依赖）|
| 中 | 资源下采样 | -10-20% 资源 | 1 周 | 低 |
| 低 | 自实现资源压缩 | 极少 | 高 | 高 |

**避免反向收益**：

- 过度 R8：与反射 / 动态调用冲突，运行期崩溃。
- 过度 Dynamic Feature：用户首次使用需要联网下载，体验差。
- 过度 ABI 裁剪：用户用老设备打不开应用。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某应用 Android 80MB / iOS 120MB，希望大幅减小。

**度量与归因**：

- Android：apkanalyzer 显示资源 50MB（含多 ABI / 多语言）。
- iOS：Xcode size report 显示资源 70MB / 代码 50MB。

**假设与求证**：

提出**统一假设**："上动态分发 + 现代图片格式 + 移除未用"。

**修复**：

- Android：上 App Bundle + 资源 WebP + 删除 x86 ABI。
- iOS：Asset Catalog 集中 + ODR 按需下载 + LLVM 优化。

**验证**：

| 平台 | 优化前 | 优化后用户下载 | 降幅 |
|---|---|---|---|
| Android | 80 MB | 32 MB | -60% |
| iOS | 120 MB | 70 MB | -42% |

**统一启示**：包优化跨端通用法则 = **现代格式 + 动态分发 + 移除未用**。

### 7.2 平台特异案例

**背景**：Android 应用启用 R8 后偶发 Class Not Found 崩溃。

**现象**：上线后 0.05% 设备崩溃，本地测试无问题。

**度量与归因**：

崩溃栈显示 `com.app.AClass not found`。AClass 是动态反射调用的类，被 R8 误删。

**修复**：

- 添加 ProGuard keep 规则保留反射类。
- 长期：减少反射使用，改为编译期注解处理。

**验证**：崩溃消失。

**边界**：每次启用新 R8 优化时必须测试反射 / 动态加载场景。

## 08.防劣化与长效治理

### 8.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
[Lint+预算]  [自动化基准]    [转化监控]
```

### 8.2 编码期 Lint

- 引入 > 1MB 第三方库 → 警告。
- 资产中含未压缩 PNG / 大图 → 警告。
- 启用 Bitcode（iOS 已废弃）→ 警告。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 包大小基准对比上一版本，增长 > 5% 阻塞。
- 单文件 > 阈值（图片 200KB / so 5MB）阻塞。
- App Bundle / Asset Catalog 必须启用。

**线上 SLO**：

- 总包大小 ≤ 阈值（按业务定）。
- 用户实际下载（Play Console）≤ 阈值。
- 安装转化率 ≥ 阈值。

## 10.总结与延伸

### 10.1 五条核心原则

1. **三组成分析**：代码 / 资源 / 配置 各自治理。
2. **工具用足**：R8 / App Bundle / Tree Shaking 必开。
3. **现代格式默认**：WebP / 矢量图 / brotli。
4. **动态分发**：用户只下载需要的。
5. **持续监控**：CI 跟踪每个版本增量。

### 10.2 五个常见误区

1. **"删几张图就够了"**：错（不是大头）。
2. **"R8 容易出 bug 不开"**：错（默认开 + 配 keep 即可）。
3. **"App Bundle 麻烦不用"**：错（上传一次自动分发）。
4. **"包小到极致才好"**：错（< 20MB 边际收益小）。
5. **"用户不在乎包大小"**：错（数据证明转化率敏感）。

## 一句话总结

> **包体积是冷启动 + 安装转化的瓶颈，每多 1MB 都让用户漏斗多损失。  
> R8 + App Bundle + 现代格式 是 Android 必做基线，能减 50%+。  
> 数据驱动，关注用户实际下载而非构建产物大小。**
