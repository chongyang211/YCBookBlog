### 00 开篇导论

**0.1 一句话定位**

**弱网与极端环境治理是性能体系的"压力测试"——**实验室里完美的产品，在地铁、电梯、信号断点的真实场景下经常崩溃。把"95% 用户的良好"做到"99.9% 用户在极端环境下不崩溃"，是高品质 App 与普通 App 的分水岭。

**0.2 为什么独立成章**

弱网/极端环境问题有独特特性：①复现困难（线下网很好）；②长尾分布（仅影响 1-3% 用户但投诉强烈）；③需要专门的工程范式（重试、超时、降级、缓存）。普通的"性能监控"难以覆盖。

### 02 问题与认知

**2.1 弱网的三种典型形态**

| 形态 | 特征 | 典型场景 |
|---|---|---|
| 慢速 | 带宽低、延迟高 | 地铁 2G/3G |
| 抖动 | 时通时断 | 高铁/电梯 |
| 切换 | WiFi ↔ 4G 切换 | 进出门、换基站 |

每种形态需要不同的应对策略——"慢速"需要降级，"抖动"需要重试，"切换"需要连接重建。

**2.2 弱网的物理本质**

- **慢速**：信号弱 → 误码率高 → TCP 频繁重传 → 实际带宽急剧下降
- **抖动**：基站切换/拥塞 → 数据包丢失或延迟 → 应用层超时
- **切换**：物理链路变更 → 旧连接断开但应用未感知 → 大量 socket 半死态

**2.3 三个共识**

- **超时不是越长越好**：5 秒等不到的 99% 是 50 秒也等不到
- **重试不是越多越好**：盲目重试在弱网中会雪崩
- **离线优先才是终极方案**：把"在线"当作锦上添花，不是必需

### 03 度量与采集

**3.1 三类采集方案的本质**

**方案 A·客户端 RUM**

- **核心原理**：埋点记录每次请求的全链路时间和成功率
- **工作机理**：DNS、TCP、TLS、首字节、下载各阶段打点
- **物理本质**：用户真实体验
- **局限根源**：只能事后分析，无法主动探测
- **适用场景**：日常 SLO 监控

**方案 B·主动探测**

- **核心原理**：定期主动发起测速、ping、连通性检查
- **工作机理**：固定周期或事件触发，记录探测结果
- **物理本质**：以"额外流量/功耗"换取"基线 baseline"
- **局限根源**：探测时机不一定能命中真实问题
- **适用场景**：网络环境感知

**方案 C·弱网模拟**

- **核心原理**：开发期通过工具模拟弱网条件
- **工作机理**：Charles/Network Link Conditioner/tc
- **物理本质**：可控制的人造环境
- **局限根源**：真实弱网千变万化，模拟只是子集
- **适用场景**：开发期验证 + CI

**3.2 三方案差异矩阵**

| 维度 | A RUM | B 探测 | C 模拟 |
|---|---|---|---|
| 真实度 | 极高 | 中 | 低 |
| 主动性 | 被动 | 主动 | 主动 |
| 上线可用 | 是 | 是（成本） | 否 |
| 复现能力 | 弱 | 中 | 强 |

**3.3 跨平台同构**

| 平台 | RUM 工具 | 弱网模拟 |
|---|---|---|
| Android | OkHttp Interceptor | Network Link Conditioner（系统）/Charles |
| iOS | URLSession Metric | NLC（Xcode）/Charles |
| 前端 | PerformanceObserver | Chrome DevTools Throttling |
| 服务端 | tcpdump | tc/netem |

**同构本质**：所有平台都遵循"DNS → 连接 → 传输 → 应用"分阶段度量；优化方法跨平台通用。

### 04 归因与定位

**4.1 弱网问题二分决策树**

```
请求慢/失败
├─ 哪个阶段慢？
│  ├─ DNS → DNS 解析问题（HTTPDNS/缓存）
│  ├─ TCP 握手 → 连接复用 / Connection: keep-alive
│  ├─ TLS → 证书优化 / TLS 1.3 / 0-RTT
│  ├─ 首字节 → 服务端性能（不在客户端范畴）
│  └─ 下载 → 带宽不足 / 包大小过大
└─ 是单点失败还是连锁失败？
   ├─ 单点 → 重试 / fallback
   └─ 连锁 → 已经雪崩，需要熔断 + 降级
```

**4.2 弱网识别三方法**

- **延迟方法**：连续 N 次请求 RTT > 阈值则判弱网
- **吞吐方法**：实测下载速度 < 阈值则判弱网
- **失败率方法**：滑动窗口失败率 > 阈值则判弱网

线上常用三者组合判定，避免单一指标误判。

**4.3 重试雪崩的归因**

某请求因弱网失败 → 客户端重试 → 后端压力倍增 → 更多请求超时 → 更多客户端重试 → 雪崩。**判定**：服务端 QPS 短时倍增 + 失败率不降反升 = 重试雪崩。

### 05 求证实验

**5.1 实验一：超时时长的最优值**

**问题**：HTTP 请求超时设多少秒最合适？

- **第 1 步·假设**：5-8 秒是最优区间，再长收益递减
- **第 2 步·设计**：用 NLC 模拟 4G/3G/弱网，分别设 3/5/8/15/30 秒超时，统计成功率和用户感知耗时
- **第 3 步·控制变量**：同接口（首页 API）、同模拟环境
- **第 4 步·指标**：成功率、用户感知耗时（成功 = 实际，失败 = 超时值）
- **第 5 步·执行**：1000 次/档
- **第 6 步·收集**：3s → 成功率 78% 平均耗时 4.2s；5s → 86% 5.5s；8s → 91% 6.8s；15s → 92% 9.2s；30s → 92% 11s
- **第 7 步·分析**：8 秒后边际收益接近 0；继续延长只是让用户白等
- **第 8 步·结论**：默认 8 秒；关键 API（登录）放到 12 秒；非关键 API 5 秒
- **第 9 步·扩展**：连接超时和读超时分开设——连接 3s（快速 fallback），读 8s（容忍服务端慢）

**5.2 实验二：重试退避算法**

**问题**：固定间隔 vs 指数退避，弱网下成功率差多少？

- **第 1 步·假设**：指数退避成功率高 20%+
- **第 2 步·设计**：失败后分别用"立即重试 3 次"vs"指数退避 1s/2s/4s"两种策略，模拟抖动型弱网
- **第 3 步·控制变量**：同请求、同弱网环境
- **第 4 步·指标**：最终成功率、累计耗时
- **第 5 步·执行**：500 次模拟
- **第 6 步·收集**：固定间隔 → 65% 成功 平均 3.2s；指数退避 → 87% 成功 平均 4.5s
- **第 7 步·分析**：弱网"抖动"特性是阵发性，固定间隔三次都打在抖动期；指数退避恰好跨越短抖动
- **第 8 步·结论**：所有重试用指数退避；首次延迟 1-2 秒；上限 16 秒；最多 3 次
- **第 9 步·扩展**：加入随机抖动（jitter）避免"惊群"——多客户端同时重试加剧服务端压力

**5.3 实验三：长连接 vs 短连接的弱网表现**

**问题**：弱网下长连接和短连接哪个更可靠？

- **第 1 步·假设**：长连接在抖动场景更不可靠（半死连接难感知）
- **第 2 步·设计**：同样 100 次请求，分别用长连接（HTTP/2 keep-alive）和短连接，模拟周期性断网 1 秒
- **第 3 步·控制变量**：同 API、同断网模式
- **第 4 步·指标**：成功率、平均延迟
- **第 5 步·执行**：CI 测试
- **第 6 步·收集**：长连接 → 56% 成功 失败者平均 12s 才感知；短连接 → 78% 成功 失败者平均 5s 感知
- **第 7 步·分析**：长连接的 TCP 半死状态需要 keepalive 探测才能发现，默认 keepalive 间隔很长
- **第 8 步·结论**：弱网/移动场景必须配合应用层心跳 + 连接健康检查；不能依赖 TCP 自身机制
- **第 9 步·扩展**：QUIC（HTTP/3）的连接迁移特性在切网场景比 TCP 优秀很多

### 06 治理与原则

**6.1 弱网设计五原则**

- **快速失败**：不要让用户等不可能成功的请求
- **指数退避**：所有重试都退避 + 加 jitter
- **优雅降级**：弱网下展示缓存 + 降级提示
- **离线优先**：核心功能必须能离线工作
- **可见进度**：长加载必须有进度提示

**6.2 弱网降级矩阵**

| 弱网级别 | 体验降级 |
|---|---|
| 正常 | 全功能 |
| 一般弱网 | 关闭预加载、降低图片质量 |
| 严重弱网 | 仅核心功能、文字优先、图片占位 |
| 离线 | 缓存数据 + 离线提示 + 重连按钮 |

**6.3 反模式清单**

- ❌ 默认超时 60 秒（用户早等不了）
- ❌ 失败立即重试 3 次
- ❌ 无 jitter 的同步重试（惊群）
- ❌ 长连接不做应用层心跳
- ❌ 无离线缓存
- ❌ 无失败 fallback UI

### 07 防劣化体系

**7.1 三道防线**

- **第一道·开发期**：所有功能必须过弱网/断网测试
- **第二道·CI**：自动化弱网模拟，关键流程不达标阻断
- **第三道·线上**：弱网用户成功率 SLO 监控

**7.2 SLO 示例**

- 一般弱网下核心 API 成功率 ≥ 95%
- 严重弱网下首屏可降级展示 ≥ 99%
- 离线下核心功能可用 = 100%
- 弱网下用户感知耗时 P95 ≤ 8s

### 08 案例与教训

**8.1 跨端同构案例·地铁场景的失败重试**

某 App 在地铁内频繁失败，用户进站后即使信号恢复，App 仍持续显示"加载失败"。原因：失败后停止重试，且未监听网络恢复事件。**修法**：失败后保留"待重试队列"，监听网络变化，恢复后自动重试。**教训**：弱网场景必须区分"暂时失败"和"永久失败"。

**8.2 平台特异案例·iOS 切网时连接半死**

某 iOS App 用户从 WiFi 进电梯切到 4G 后，已有连接进入半死状态，请求 hang 住直到默认 60 秒超时。**修法**：监听 `NWPathMonitor` 的网络变化事件，主动断开重建连接。**教训**：iOS 上必须用新的 Network framework，老的 Reachability 不可靠。

### 09 原理深挖

**9.1 TCP 在弱网下的劣势**

TCP 重传机制是为"可靠数据流"设计的，但在频繁丢包/抖动的移动网络下：①重传定时器很慢；②慢启动后窗口反复重置；③一个分段丢失阻塞整个数据流。这是 QUIC 出现的根本动机。

**9.2 QUIC/HTTP/3 的弱网优势**

- **0-RTT 握手**：减少建连耗时
- **连接迁移**：换网不断连接（基于 ConnectionID 而非 IP）
- **多路复用无队头阻塞**：单个分段丢失不影响其他流
- **快速恢复**：改进的拥塞控制算法

弱网/移动场景，HTTP/3 是未来。

**9.3 离线优先架构**

理想架构：本地数据库是单一数据源，UI 永远从本地读；后台异步同步到服务端。这样弱网/断网下应用完全可用，恢复后静默同步。代表：Notion、Linear、Figma。

### 10 总结与扩展

**10.1 一图概括**

```
弱网治理
    ├─ 识别 → 延迟 + 吞吐 + 失败率三合一
    ├─ 超时 → 8 秒为主，分级别
    ├─ 重试 → 指数退避 + jitter
    ├─ 降级 → 弱网级别 → 体验级别映射
    ├─ 离线 → 核心功能离线优先
    └─ 监控 → 弱网用户单独 SLO
```

**10.2 三个外延**

- **HTTP/3 普及**：QUIC 已被各大 App 采用，移动场景效果显著
- **CRDT 数据结构**：解决离线协作的冲突合并
- **AI 网络感知**：基于历史预测当前网络状况，提前降级

**10.3 给团队的建议**

- 第 1 周：审计所有 API 超时配置，统一到 8 秒
- 第 2 周：所有重试改为指数退避 + jitter
- 第 3 周：核心功能加离线缓存
- 第 4 周：上线弱网用户细分 SLO

弱网与极端环境是 App 的"诚信考验"——做好了，用户在地铁里也夸你；做不好，那 1% 的差体验会被放大成 100% 的差口碑。
