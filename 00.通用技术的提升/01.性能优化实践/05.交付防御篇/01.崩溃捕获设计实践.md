## 00.5 贯穿案例：某出行 App"半数崩溃看不见"事件

> 本案例贯穿全文：§01 看懂代价、§02 拿到三类崩溃模型、§03 用三方案、§05 用实验复盘、§06 给出分层闭环。

### 案例背景

某头部出行 App V12.0 在用户反馈中持续收到"打开就闪退、订单时崩溃"投诉，但 Crashlytics 看板显示崩溃率仅 0.04%（行业极致）。**用户量级和投诉量级完全对不上**：

- 客服记录"闪退"投诉每日 8000+，按 DAU 1500 万估算应有 0.5%+。
- 监控显示崩溃率仅 0.04%，**真实崩溃率被低估 12 倍**。
- 应用商店评分掉到 3.2（行业平均 4.5），用户评论高频出现"打不开"。
- 产品/运营无法理解："数据看着好好的，为啥用户都说闪退？"

研发组：基础架构同学："我们接了 Crashlytics，应该都收到了。"——这是经典的"工具迷信"。

### 经验派的 4 周折腾（典型反面教材）

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 升级 Crashlytics 到最新版（怀疑 SDK 问题）| 数据无变化，依旧 0.04% |
| 第 2 周 | 加大上报采样率到 100%（怀疑采样丢）| 无变化（原本就是 100% 采样）|
| 第 3 周 | 跑用户回访问卷（用人工填补数据）| 收集到一些场景但无 stack，**无法修复** |
| 第 4 周 | 把客服关键词"闪退"加白名单优先处理 | 仅是症状缓解，崩溃数据依然看不到 |

**复盘**：四周折腾错在"以为工具能覆盖全部崩溃"。**Crashlytics 类 SDK 主要覆盖 Java/OC 异常和部分信号，但漏掉**：
- Android Native 崩溃（NDK 信号，需独立 SDK）
- Android 启动早期崩溃（SDK 未初始化前）
- Android LMK/被系统杀（不是崩溃，但用户感知一样）
- iOS 启动 watchdog（直接 SIGKILL，应用代码不响应）
- iOS OOM（jetsam 杀，无 crash log）
- Web unhandledrejection（很多 SDK 默认不监听）

### 方法派的 7 天闭环

新接手的同学按本文方法论重做：

**Day 1（§03 三方案理论 + §05 实验数据）**：

用 [§5.1 实验](#51-实验一捕获完整性) 数据论证："三方案组合覆盖 99% vs 单方案覆盖 60-70%"——把"工具迷信"打破。

**Day 2（§04 决策树审计盲区）**：

逐类崩溃审计当前覆盖情况：

| 崩溃类型 | 现状 | 解决方案 |
|---|---|---|
| Android Java 异常 | ✅ Crashlytics | 已覆盖 |
| Android Native 崩溃 | ❌ 漏 | 接 Bugly NDK / xCrash |
| Android 启动早期 | ❌ 漏 | 自实现 SIGQUIT 早期注册 |
| Android LMK/被杀 | ❌ 漏 | `getHistoricalProcessExitReasons` |
| iOS OC/Swift 异常 | ✅ Crashlytics | 已覆盖 |
| iOS Mach 异常 | 部分 | KSCrash 补全 |
| iOS 启动 hang | ❌ 漏 | MetricKit `MXLaunchHangDiagnostic` |
| iOS OOM/jetsam | ❌ 漏 | MetricKit + 排除法 |
| Web JS 异常 | ✅ Sentry | 已覆盖 |
| Web Promise rejection | ❌ 漏 | `unhandledrejection` 监听 |
| Web 资源加载失败 | ❌ 漏 | `error` 事件捕获阶段 |

**Day 3-4（§06 分层策略，按四层施治）**：

- 第 1 层（捕获覆盖）：补全所有漏点（KSCrash/Bugly NDK/MetricKit/unhandledrejection）。
- 第 2 层（现场质量）：上报字段扩充到 stack + device + 用户操作链 + 内存 + 网络快照。
- 第 3 层（上报可靠性）：本地优先 + 启动重试 + 多通道。
- 第 4 层（治理闭环）：每周 Top 10 治理 + 自动符号化。

**Day 5-6（自动符号化基建）**：

- Android：CI 自动上传 mapping.txt 到 Bugly。
- iOS：CI 自动上传 dSYM 到 Crashlytics + KSCrash。
- 配套：发版前阻断"未上传符号"的版本。

**Day 7（灰度验证 + 上线）**：

### 上线效果

| 指标 | 经验派 4 周后 | 方法派 7 天后 | 行业基准 |
|---|---|---|---|
| 可见崩溃率 | 0.04%（假数据）| **0.48%**（真实数据）| 0.5%（接近真实）|
| Native 崩溃可见 | 0% | **98%** | - |
| iOS OOM 可见（事后）| 0% | **MetricKit 95%** | - |
| Web unhandledrejection | 0% | **100%** | - |
| 客服"闪退"投诉/日 | 8000+ | 7800（同期）| - |
| 实际治理效率 | 无数据无修复 | **每周 Top 10 治理** | - |
| 4 周后真实崩溃率 | 0.04%（造假）| **0.13%**（真治）| < 0.1% |

**核心洞察**：**"可见崩溃率"不等于"真实崩溃率"**。经验派"看到 0.04%"实际是"只看到 12% 的崩溃"。看不见的崩溃才是最大风险——因为你**完全不知道有问题**。方法派 Day 1 直接打破"工具迷信"是关键认知转变。

## 01.问题域定义

### 1.1 现象与代价

崩溃是稳定性的"显示信号"：

- **应用退出**：用户看到"应用已停止"或被强杀。
- **数据丢失**：未保存数据可能丢失。
- **重启后状态丢失**：用户被迫重新进入流程。
- **隐性崩溃**：应用在用户感知到之前已经异常（如启动崩溃）。

**业务代价**：

- 头部应用崩溃率每降 0.1% 留存 +0.5%。
- 启动崩溃比运行时崩溃影响更大（用户进不去）。
- 不可见的"静默崩溃"会影响线上数据准确性。

### 1.2 度量准则

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 崩溃率（cph）| crash / hour 或 crash / DAU | < 0.1% |
| 启动崩溃率 | 启动失败 / 总启动 | < 0.05% |
| 上报成功率 | 上报成功 / 总崩溃 | > 95% |
| 符号化成功率 | 可还原栈 / 总崩溃 | > 90% |

### 1.3 行业基准与目标

| 平台 | 崩溃率 | 启动崩溃 | 上报成功率 |
|---|---|---|---|
| Android | < 0.1% | < 0.05% | > 95% |
| iOS | < 0.05% | < 0.02% | > 98% |
| Web | < 0.05% | N/A | > 90% |
| 嵌入式 | 0% | 0% | 内部记录 |

### 1.4 反直觉问题清单

带着这些问题阅读：

1. Java 崩溃和 Native 崩溃捕获方式一样吗？
2. iOS 崩溃栈为什么是地址而不是函数名？
3. 崩溃时再上报数据可靠吗？
4. 静默崩溃如何发现？
5. SIGABRT 和 SIGKILL 应用都能捕获吗？
6. ANR 和崩溃是同一类问题吗？
7. 用户主动杀死也算"崩溃"吗？
8. 崩溃时还能写文件 / 发网络吗？

## 02.第一性原理

### 2.1 崩溃本质定义

**一句话定义**：

> **崩溃 = 应用在执行过程中遇到不可恢复的错误，被运行时或操作系统强制终止**。

这句话隐含三个不可商量的物理约束：

**约束一：崩溃是"不可恢复"的状态**

崩溃发生时，进程内某些数据已经处于"不可信"状态（栈被破坏 / 内存被覆盖 / 状态机错乱）。即使能继续执行，结果也不可信。**OS / 运行时主动杀死进程是为了避免错误扩散**。

**约束二：崩溃捕获的"时间窗"极短**

崩溃信号 / 异常发生到进程被强杀通常只有几十 ms 到几秒。在这段时间里要做：

- 记录崩溃信息（stack / device / context）
- 持久化到本地（不能依赖网络）
- 准备下次启动时上报

**操作必须最简单 / 最可靠**：不能依赖复杂的库，不能新建线程，不能分配大块内存。

**约束三：崩溃种类决定捕获方式**

不同语言 / 平台的崩溃机制不同（Java 异常 vs C 信号 vs JS 错误），需要分别捕获。

### 2.2 三类崩溃模型

```
   ┌────────────────────────────────────────────────┐
   │ A. 异常型崩溃（语言级）                          │
   │    Java RuntimeException / Swift error / JS Error│
   │    捕获：UncaughtExceptionHandler                │
   ├────────────────────────────────────────────────┤
   │ B. 信号型崩溃（系统级）                          │
   │    SIGSEGV / SIGABRT / SIGBUS / SIGFPE          │
   │    捕获：sigaction / signal handler             │
   ├────────────────────────────────────────────────┤
   │ C. 系统强杀（OOM Killer / Watchdog / Kill）      │
   │    无法应用层捕获                                │
   │    捕获：启动时检查"上次未正常退出"               │
   └────────────────────────────────────────────────┘
```

**关键认知**：

- A 类容易捕获（运行时提供 hook）。
- B 类需要 Native 层信号处理（POSIX signal）。
- C 类应用代码无法响应（已被 SIGKILL），只能下次启动时推断。

### 2.3 跨平台同构原理

所有平台的崩溃捕获本质都是"在异常发生时拦截 + 记录 + 持久化"：

```
   通用崩溃捕获模型：

      [应用代码] ──[抛异常]──▶ [运行时/OS]
                                  │
                                  ▼
                           [捕获 hook]
                                  │
                                  ▼
                           [收集现场]
                                  │
                                  ▼
                           [本地持久化]
                                  │
                          下次启动时上报
```

每个平台都必须有：

| 抽象组件 | 解决什么问题 |
|---|---|
| 异常 hook | 捕获语言级异常 |
| 信号 hook | 捕获系统级信号 |
| 现场采集 | 抓 stack / device / context |
| 本地持久化 | 崩溃后写本地（网络可能不可用）|
| 上报机制 | 下次启动时安全上传 |

**跨平台术语对照**

| 通用术语 | Android | iOS | Web | C/C++ |
|---|---|---|---|---|
| 异常 hook | `Thread.setDefaultUncaughtExceptionHandler` | `NSSetUncaughtExceptionHandler` | `window.onerror` + `unhandledrejection` | `terminate_handler` |
| 信号 hook | NDK `sigaction` | `sigaction` | N/A | `sigaction` |
| 现场采集 | stack + device + 自定义 | 同 + Mach exception | error.stack + UA | backtrace |
| 持久化 | 本地文件 | 本地文件 | localStorage / IndexedDB | 本地文件 |
| 上报 | 下次启动 | 下次启动 | 即时 / 延迟 | 视设计 |

**同构带来的工程价值**

1. **方案选型有锚点**：A/B/C 三类各自的 hook 方式跨端通用。
2. **现场字段可对齐**：stack / device / 用户操作链 / 内存 / 网络 是通用字段。
3. **上报策略可复用**：本地优先 + 下次启动上传。

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 异常型 | Java / Kotlin Exception | Swift error / NSException | JS Error / Promise rejection | C++ exception |
| 信号型 | NDK 信号 | Mach exception + signal | N/A（沙箱）| signal |
| 系统强杀 | LMK / Force Stop | jetsam / watchdog | Tab Killer | 看门狗 |
| Stack 符号化 | mapping.txt（ProGuard）+ NDK symbols | dSYM | sourcemap | DWARF |
| 多线程崩溃 | 单 dump 含所有线程 | 同 | 单线程为主 | 视实现 |

> 后续遇到平台特化点回引本节。

## 03.度量与采集

### 3.1 三类捕获方案的本质

所有平台的崩溃捕获方案，本质上只有 3 类：

```
   ① 异常 hook（语言运行时层）
   ② 信号 hook（系统 POSIX 层）
   ③ 系统级历史（启动时回查上次）
```

---

**① 异常 hook**

**核心原理（一句话）**：在语言运行时提供的全局异常入口注册回调，捕获未处理的异常。

**工作机理**：

```kotlin
// Android Java/Kotlin
Thread.setDefaultUncaughtExceptionHandler { thread, throwable ->
    // 1. 立即收集现场（不依赖外部库）
    val report = collectMinimalReport(thread, throwable)
    // 2. 写本地（避免网络）
    saveLocally(report)
    // 3. 调原默认 handler 让进程正常死
    defaultHandler.uncaughtException(thread, throwable)
}
```

```objc
// iOS
NSSetUncaughtExceptionHandler(^(NSException *exception) {
    NSDictionary *report = collectReport(exception);
    saveLocally(report);
});
```

```js
// Web
window.addEventListener('error', (event) => {
    saveLocally({ message: event.message, stack: event.error?.stack });
});
window.addEventListener('unhandledrejection', (event) => {
    saveLocally({ reason: event.reason });
});
```

**物理本质**：拦截"语言运行时强制终止"前的最后机会。

**适用边界**：所有应用必备的基础捕获。

---

**② 信号 hook**

**核心原理（一句话）**：在 Native 层注册 POSIX signal handler，捕获 C / C++ 层崩溃。

**工作机理**：

```c
#include <signal.h>

void crash_handler(int signo, siginfo_t *info, void *ctx) {
    // 注意：在信号处理上下文，能用的函数有限
    // 不能 malloc / printf / 调 Java 等
    write(fd, simple_info, len);  // 仅用 async-signal-safe 函数
}

void init_signal_hook() {
    struct sigaction sa;
    sa.sa_sigaction = crash_handler;
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGSEGV, &sa, NULL);
    sigaction(SIGABRT, &sa, NULL);
    sigaction(SIGBUS, &sa, NULL);
    // ...
}
```

**物理本质**：在 OS 信号机制层拦截 Native 层崩溃。

**为什么这样有效**：Native crash 不会经过 Java VM 的 UncaughtExceptionHandler，必须在系统层捕获。

**局限根源**：

- 信号处理上下文严格受限（async-signal-safe 函数列表）。
- Stack unwind 跨语言（C → Java → JNI）很复杂。
- 部分信号（SIGKILL）不可捕获。

**适用边界**：所有有 Native 代码的应用必备。

---

**③ 系统级历史**

**核心原理（一句话）**：进程被 OS 强杀（OOM / Watchdog / Force Stop）时应用无法响应，只能下次启动时通过系统 API 回查。

**工作机理**：

| 平台 | API |
|---|---|
| Android 11+ | `ActivityManager.getHistoricalProcessExitReasons` |
| iOS | MetricKit `MXMetricPayload.crashDiagnostic` |
| Web | N/A（用户关闭即丢） |

**物理本质**：应用代码不在场，OS 帮你记录。

**适用边界**：补全应用层捕获不到的"静默崩溃"。

---

**三类方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 异常 hook | 语言运行时 | Java/JS 栈 | 极低 | 高 | ✅ | 不覆盖 Native |
| ② 信号 hook | OS 层 | Native 栈 | 极低 | 中（需 NDK）| ✅ | 信号处理受限 |
| ③ 系统历史 | OS API | 进程级 | 极低 | 中（API 受限）| ✅ | 颗粒度粗 |

**方案的"组合定律"**：①+② 必须组合（覆盖所有运行时）+ ③ 补全静默崩溃。

## 03.5 各端崩溃完整流程原理

> 本章把"崩溃"从黑盒打开：每一类崩溃**怎么产生 → 内核/运行时怎么投递 → 应用在哪里能监听 → 监听到之后如何抓堆栈 → 堆栈如何符号化**，五步全链路打通。
> 这是 §03 的"原理详解"，§06 所有策略的"为什么"。

### 3.5.1 Android Java/Kotlin 崩溃全链路

#### 一、如何引起崩溃

Java/Kotlin 崩溃 = **某个线程抛出未捕获的 `Throwable`**：

```kotlin
// 典型引发方式
val s: String? = null
s!!.length                              // KotlinNullPointerException
val list = listOf(1, 2, 3); list[10]    // IndexOutOfBoundsException
(any as String)                         // ClassCastException
throw RuntimeException("biz error")     // 主动抛
Runtime.getRuntime().gc(); allocBig()   // OutOfMemoryError
```

#### 二、JVM/ART 内部投递流程

```
   业务代码 throw e
       │
       ▼
   JVM 沿调用栈向上找 catch（栈展开 stack unwinding）
       │
       ├─ 找到 catch ──▶ 正常处理（不是崩溃）
       │
       └─ 走到线程顶层（Thread.run 之外）都没 catch
              │
              ▼
       ThreadGroup.uncaughtException(t, e)
              │
              ▼
       Thread.getUncaughtExceptionHandler()
              │   （默认查找顺序）
              │   1. thread.uncaughtExceptionHandler  ← 单线程级别
              │   2. thread.threadGroup               ← ThreadGroup 级别
              │   3. Thread.defaultUncaughtExceptionHandler  ← 全局
              │
              ▼
       执行 handler.uncaughtException()
              │
              ▼
       handler 返回后，ART 调用 RuntimeInit.Clog_e + 进程 exit
              │
              ▼
       Zygote 父进程感知子进程退出 → ActivityManagerService 收到死亡通知
              │
              ▼
       AMS 决定是否拉起 / 弹"应用已停止"对话框
```

**关键点**：`Thread.setDefaultUncaughtExceptionHandler` 是**全局兜底**，应用可以替换它来插入采集逻辑，**然后调用原默认 handler 让进程正常退出**。

#### 三、监听点（应用层）

```kotlin
// 必须在 Application.onCreate 第一行（甚至 attachBaseContext）
class MyApp : Application() {
    override fun onCreate() {
        super.onCreate()
        val defaultHandler = Thread.getDefaultUncaughtExceptionHandler()
        Thread.setDefaultUncaughtExceptionHandler { thread, throwable ->
            try {
                val report = collectReport(thread, throwable)   // 抓堆栈+现场
                saveLocally(report)                              // 写本地文件
            } catch (t: Throwable) {
                // 兜底吞噬，避免 handler 自身崩溃导致死循环
            } finally {
                // 必须把异常交还给原 handler，否则进程"假死"不退出
                defaultHandler?.uncaughtException(thread, throwable)
            }
        }
    }
}
```

**两个陷阱**：

- **不调原 handler**：进程不退出但已不可用，用户体验更差（"白屏冻住"）。
- **handler 自身抛异常**：递归触发 handler，OOM 风险。

#### 四、堆栈采集

```kotlin
fun collectReport(thread: Thread, e: Throwable): CrashReport {
    // 1. 当前异常栈（业务调用链）
    val stackStr = StringWriter().also { e.printStackTrace(PrintWriter(it)) }.toString()
    
    // 2. 所有线程栈（off-CPU 类崩溃必备，如死锁/锁等待）
    val allThreads = Thread.getAllStackTraces().mapValues { (_, frames) ->
        frames.joinToString("\n") { "  at $it" }
    }
    
    // 3. cause 链（包装异常常见）
    val causes = mutableListOf<String>()
    var cur: Throwable? = e.cause
    while (cur != null) {
        causes.add(cur.javaClass.name + ": " + cur.message)
        cur = cur.cause
    }
    
    return CrashReport(
        type = e.javaClass.name,
        message = e.message ?: "",
        thread = thread.name,
        stack = stackStr,
        allThreads = allThreads,
        causes = causes
    )
}
```

#### 五、符号化

- **混淆后**：栈里看到 `a.b.c.a()` 等无意义短名。
- **R8/ProGuard** 编译产物附带 `mapping.txt`，每次发版必须归档。
- **还原**：
  - 工具：`retrace.jar mapping.txt obfuscated_stack.txt`
  - 平台：Bugly / Crashlytics / Sentry 自动符号化。

### 3.5.2 Android Native 崩溃全链路

#### 一、如何引起崩溃

Native（C/C++）崩溃 = **CPU 执行了一条非法指令 / 访问了非法内存**，由 **MMU/CPU 抛硬件异常 → 内核转换成 POSIX 信号**：

```c
// 典型引发方式
int *p = NULL; *p = 1;          // SIGSEGV：解引用空指针
*(int*)0xDEADBEEF = 1;          // SIGSEGV：野指针
char buf[4]; *(int*)(buf+1) = 1;// SIGBUS：未对齐访问（部分架构）
int a = 1/0;                    // SIGFPE：除零
abort();                        // SIGABRT：主动 abort
assert(false);                  // SIGABRT：assert 失败
__stack_chk_fail();             // SIGABRT：栈溢出保护触发
```

#### 二、内核 → 信号投递流程

```
   CPU 执行非法指令（例如 mov [null], 1）
       │
       ▼
   MMU 触发 page fault（缺页/访问违规）
       │
       ▼
   内核异常处理：do_page_fault()
       │
       ▼
   内核检查：这是用户态的错误（不是合法的 mmap 区）
       │
       ▼
   force_sig_info(SIGSEGV, ...) ──▶ 向当前进程发信号
       │
       ▼
   返回用户态前，内核检查 pending signals
       │
       ▼
   如果应用注册了 sigaction handler ──▶ 跳到 handler 执行
       │
       └─ 没注册（默认）──▶ 默认行为：进程被 kill + 生成 core dump（Android 是 tombstone）
              │
              ▼
       Android: linker/debuggerd 接管
              │
              ▼
       debuggerd dump 出 tombstone 到 /data/tombstones/
              │
              ▼
       内核完成 do_exit → Zygote 感知 → AMS 处理
```

**关键点**：信号在内核层投递，**应用必须主动注册 `sigaction` 才能截获**，否则只能事后从 tombstone 读。

#### 三、监听点（应用层）

```c
#include <signal.h>
#include <unistd.h>

// 信号处理上下文非常受限：只能调 async-signal-safe 函数
// 详见 man 7 signal-safety
static void crash_handler(int signo, siginfo_t *info, void *ucontext) {
    // 1. 只能用 write（不能用 printf/malloc/std::string）
    char buf[256];
    int len = snprintf(buf, sizeof(buf), "signal=%d code=%d addr=%p\n",
                       signo, info->si_code, info->si_addr);
    write(crash_fd, buf, len);
    
    // 2. 抓 backtrace（见下节）
    dump_backtrace(crash_fd, (ucontext_t*)ucontext);
    
    // 3. 不能用 longjmp 跳过崩溃；让默认 handler 处理
    signal(signo, SIG_DFL);
    raise(signo);
}

void install_native_crash_handler() {
    // 关键：用 SA_ONSTACK + 独立栈，避免栈溢出导致 handler 自身崩
    static char alt_stack[SIGSTKSZ];
    stack_t ss = { .ss_sp = alt_stack, .ss_size = SIGSTKSZ };
    sigaltstack(&ss, NULL);
    
    struct sigaction sa = {0};
    sa.sa_sigaction = crash_handler;
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
    sigemptyset(&sa.sa_mask);
    
    // 必捕的 6 个信号
    int sigs[] = { SIGSEGV, SIGBUS, SIGABRT, SIGFPE, SIGILL, SIGTRAP };
    for (int sig : sigs) sigaction(sig, &sa, NULL);
}
```

**陷阱**：

- 不用 `SA_ONSTACK` + 备用栈 → 栈溢出类崩溃时 handler 自身崩溃（信号被默认处理）。
- 在 handler 里 `malloc/printf` → 死锁（heap 锁/stdio 锁可能在崩溃线程持有）。
- 不 `raise(signo)` → 进程"假死"（ART 不会清理子线程）。

#### 四、堆栈采集（Native Backtrace）

```c
#include <unwind.h>
#include <dlfcn.h>

struct backtrace_state {
    void** current;
    void** end;
};

static _Unwind_Reason_Code unwind_cb(struct _Unwind_Context* ctx, void* arg) {
    auto* state = (backtrace_state*)arg;
    uintptr_t pc = _Unwind_GetIP(ctx);
    if (pc && state->current < state->end) *state->current++ = (void*)pc;
    return _URC_NO_REASON;
}

void dump_backtrace(int fd, ucontext_t* uc) {
    void* frames[64];
    backtrace_state state = { frames, frames + 64 };
    _Unwind_Backtrace(unwind_cb, &state);
    int n = state.current - frames;
    
    for (int i = 0; i < n; i++) {
        Dl_info info;
        if (dladdr(frames[i], &info)) {
            // info.dli_fname = .so 路径；info.dli_sname = 符号名（可能 NULL）
            // 计算 offset：frames[i] - info.dli_fbase（库基址）
            uintptr_t offset = (uintptr_t)frames[i] - (uintptr_t)info.dli_fbase;
            dprintf(fd, "#%02d pc %p %s+0x%lx\n", i, frames[i], info.dli_fname, offset);
        }
    }
}
```

**输出示例**：

```
#00 pc 0x000012a4 /data/app/com.x/lib/arm64/libnative.so+0x000012a4
#01 pc 0x00001340 /data/app/com.x/lib/arm64/libnative.so+0x00001340
#02 pc 0x00056789 /apex/com.android.runtime/lib64/libart.so (art_quick_invoke_stub+0x100)
```

#### 五、符号化

Native 栈是 **so 路径 + offset**，必须用**带调试信息的 so**（`.so.debug` 或 `obj/local/<abi>/<lib>.so`）做地址→符号转换：

```bash
# 用 ndk-stack 自动符号化（推荐）
ndk-stack -sym obj/local/arm64-v8a -dump tombstone.txt

# 或用 addr2line 逐帧
arm64-linux-android-addr2line -e libnative.so -f -C 0x12a4
# 输出：
# _ZN3foo3barEv
# /src/foo.cpp:42
```

**关键约定**：

- **release 包必须 strip**（减小 apk 体积），但**调试 so 必须归档**。
- CI 上传 NDK symbols 到 Bugly/Crashlytics。
- Android 11+ 还可以读 `/data/tombstones/tombstone_*` 作为对照（需 `READ_LOGS` 权限或 dump 服务）。

### 3.5.3 Android ANR 全链路

#### 一、如何引起 ANR

ANR（Application Not Responding）= **系统组件超时未响应**：

| 组件 | 超时 | 触发条件 |
|---|---|---|
| Input | **5 秒** | 触摸/按键事件 5s 未被分发处理 |
| BroadcastReceiver（前台）| 10 秒 | onReceive 同步阻塞 10s |
| BroadcastReceiver（后台）| 60 秒 | 同上 |
| Service（前台）| 20 秒 | onStartCommand/onBind 阻塞 |
| Service（后台）| 200 秒 | 同上 |
| ContentProvider | 10 秒 | publish 超时 |

**根本原因**：主线程被阻塞（同步 IO、锁等待、死循环、Binder 同步调用挂起）。

#### 二、系统投递流程

```
   InputDispatcher (system_server) 派发触摸事件给 App
       │
       ▼
   App 主线程 InputEventReceiver 应该 5s 内 ack
       │
       ├─ 按时 ack ──▶ 正常
       │
       └─ 5s 未 ack
              │
              ▼
       InputDispatcher.handleTargetsNotReadyLocked()
              │
              ▼
       AnrTracker 标记 ANR
              │
              ▼
       AMS.appNotResponding()
              │
              ├─ 向应用进程发 SIGQUIT (signal 3)
              │   │
              │   ▼
              │   ART signal handler 接管 → dump 所有线程栈到 /data/anr/traces.txt
              │
              ├─ 抓取 CPU 使用率快照（top）
              ├─ 抓取关键进程的 stack
              │
              ▼
       决策：弹"应用无响应"对话框 / 直接 kill / 静默记录
```

#### 三、监听点（应用层）

应用层**无法直接收到 ANR 通知**（系统不发广播给自己），有三种监听方式：

**方式 A：主动 Watchdog 法**（最常见，xCrash/Matrix 思路）

```kotlin
class AnrWatchDog : Thread() {
    private val mainHandler = Handler(Looper.getMainLooper())
    @Volatile private var ticker = 0
    override fun run() {
        while (!isInterrupted) {
            val before = ticker
            mainHandler.post { ticker++ }  // 主线程能跑就+1
            try { sleep(5000) } catch (e: InterruptedException) { return }
            if (ticker == before) {
                // 5s 主线程没动 → 准 ANR
                val mainStack = Looper.getMainLooper().thread.stackTrace
                val allStacks = Thread.getAllStackTraces()
                report(mainStack, allStacks)
            }
        }
    }
}
```

**方式 B：SIGQUIT Hook 法**（在系统真正发 ANR 时捕获）

```c
// 替换 ART 自己的 SIGQUIT handler，把 dump 内容截下来
static void on_sigquit(int sig, siginfo_t* info, void* ctx) {
    // 先让 ART 自己 dump 一份到 /data/anr/traces.txt
    original_sigquit_handler(sig, info, ctx);
    // 再读取这份 dump 上报（注意：需要 hook open/write 拦截内容）
}
```

**方式 C：ApplicationExitInfo（Android 11+）**

```kotlin
val am = getSystemService(ActivityManager::class.java)
am.getHistoricalProcessExitReasons(null, 0, 10)
    .filter { it.reason == ApplicationExitInfo.REASON_ANR }
    .forEach { info ->
        val stackBytes = info.traceInputStream?.readBytes()  // 系统保存的 stack
        report(info, stackBytes)
    }
```

#### 四、堆栈采集

ANR 的关键是**抓所有线程的栈**（不只是主线程，因为主线程可能在等其他线程的锁）：

```kotlin
fun dumpAnrStacks(): String = buildString {
    val all = Thread.getAllStackTraces()
    // 主线程优先
    val main = Looper.getMainLooper().thread
    appendLine("=== main (${main.state}) ===")
    main.stackTrace.forEach { appendLine("  at $it") }
    // 其他线程
    all.filterKeys { it != main }.forEach { (t, frames) ->
        appendLine("=== ${t.name} (${t.state}) ===")
        frames.forEach { appendLine("  at $it") }
    }
}
```

**进阶**：

- 系统 `/data/anr/traces.txt` 包含更详细信息（CPU/IO 状态、native 栈），但 Android 7+ 普通应用无读权限。
- 用 `ApplicationExitInfo.traceInputStream` 是 Android 11+ 的合规方案。

#### 五、定位与归因

ANR 堆栈分析三步：

1. **看主线程栈顶**：在做什么？
2. **看主线程 state**：`BLOCKED`（等锁）/`WAITING`（等条件）/`RUNNABLE`（在跑但慢）。
3. **如果 BLOCKED**：在等谁的锁 → 找该锁的持有线程 → 看它在做什么。

### 3.5.4 iOS NSException 崩溃全链路

#### 一、如何引起崩溃

```objc
// 典型 NSException
NSArray *a = @[]; a[5];                     // NSRangeException
NSDictionary *d = @{}; [d setValue:nil forKey:@"k"];  // NSInvalidArgumentException
[someObj performSelector:@selector(noMethod)];        // unrecognized selector
@throw [NSException exceptionWithName:@"Biz" reason:@"err" userInfo:nil];
```

```swift
// Swift
let arr: [Int] = []; _ = arr[5]            // Fatal error: Index out of range → trap → SIGILL
let optional: Int? = nil; _ = optional!    // Fatal error: nil → trap
fatalError("biz")                          // trap
```

**关键区别**：
- Objective-C `NSException` 是**纯 OC 异常**，可被 `@try/@catch` 捕获。
- Swift `fatalError`/数组越界等是**编译器插入的 trap 指令**，**最终也是信号**（SIGILL/SIGTRAP）—— 走 §3.5.5 Mach Exception 路径。

#### 二、Objective-C Runtime 投递流程

```
   [@throw exception] 或 系统抛出 NSException
       │
       ▼
   objc_exception_throw(exception)
       │
       ▼
   沿调用栈找 @catch（C++ 异常机制实现的 unwind）
       │
       ├─ 找到 @catch ──▶ 正常处理
       │
       └─ 走到栈顶都没 catch
              │
              ▼
       NSUncaughtExceptionHandler ← 应用注册点
              │
              ▼
       handler 返回后，runtime 调 abort()
              │
              ▼
       abort() 内部 raise(SIGABRT) ──▶ 走 Mach Exception 路径（见 §3.5.5）
```

**关键点**：NSException 最终也变成 SIGABRT 信号——所以**只接 NSException handler 不够**，还要接 Mach Exception。

#### 三、监听点

```objc
static void handleUncaughtException(NSException *exception) {
    // 注意：handler 执行期间 runtime 已处于"即将退出"状态
    NSArray *callStack = [exception callStackSymbols];   // 关键：拿到符号化的栈
    NSArray *returnAddrs = [exception callStackReturnAddresses];
    NSString *reason = [exception reason];
    NSString *name = [exception name];
    
    NSDictionary *report = @{
        @"name": name ?: @"",
        @"reason": reason ?: @"",
        @"stack": callStack ?: @[],
        @"return_addresses": returnAddrs ?: @[]
    };
    
    // 写本地（不能用网络）
    [self saveReportToDisk:report];
}

// 在 application:didFinishLaunchingWithOptions: 第一行
NSSetUncaughtExceptionHandler(&handleUncaughtException);
```

#### 四、堆栈采集

iOS 的 `[NSException callStackSymbols]` **已经是符号化后的字符串**（开发期）：

```
0  CoreFoundation        0x00000001 __exceptionPreprocess + 165
1  libobjc.A.dylib       0x00000002 objc_exception_throw + 48
2  MyApp                 0x00000003 -[ViewController buttonTapped:] + 234
3  UIKit                 0x00000004 -[UIControl sendAction:to:forEvent:] + 78
```

**线上**：栈中的应用方法部分是地址（如 `MyApp 0x100002a8c`），需要 **dSYM** 符号化（见下文）。

也可手动 backtrace：

```c
#include <execinfo.h>
void* frames[64];
int n = backtrace(frames, 64);
char** symbols = backtrace_symbols(frames, n);  // 注意：会 malloc
```

#### 五、符号化

```bash
# 用 atos（推荐）
atos -arch arm64 -o MyApp.app.dSYM/Contents/Resources/DWARF/MyApp -l 0x100000000 0x100002a8c
# 输出：-[ViewController buttonTapped:] (in MyApp) (ViewController.m:42)

# 或用 symbolicatecrash（系统自带）

```

### 3.5.5 iOS Mach Exception 崩溃全链路

#### 一、如何引起崩溃

iOS/macOS 底层是 Mach 微内核 + BSD 层：

```c
// Mach 层崩溃源
int *p = NULL; *p = 1;          // EXC_BAD_ACCESS（KERN_INVALID_ADDRESS）
1 / 0;                          // EXC_ARITHMETIC
abort();                        // EXC_CRASH（通过 SIGABRT）
__builtin_trap();               // EXC_BREAKPOINT（Swift 数组越界编译成此指令）
```

Swift 的 `fatalError`、数组越界、强解包 nil **都编译成 trap 指令**，触发 `EXC_BREAKPOINT`。

#### 二、内核投递流程（双层机制）

```
   CPU 执行非法指令
       │
       ▼
   Mach 内核捕获硬件异常
       │
       ▼
   Mach Exception Port 投递（每个 task 有 exception port）
       │
       ├─ 应用注册了 Mach exception handler ──▶ 应用接管
       │
       └─ 未注册 ──▶ 转换为 BSD 信号（如 EXC_BAD_ACCESS → SIGSEGV）
              │
              ▼
       BSD signal 投递
              │
              ├─ 应用注册了 sigaction ──▶ 应用接管
              │
              └─ 默认行为 ──▶ ReportCrash 生成 .ips 崩溃日志，进程被杀
```

**关键点**：iOS 有**两个截获机会**——Mach 层和 BSD 层。**Mach 层更原始更可靠**（KSCrash 就在 Mach 层接管）。

#### 三、监听点

**方案 A：BSD Signal**（同 Android Native，简单）

```c
struct sigaction sa = {0};
sa.sa_sigaction = signal_handler;
sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
sigaction(SIGSEGV, &sa, NULL);
sigaction(SIGABRT, &sa, NULL);
sigaction(SIGBUS, &sa, NULL);
sigaction(SIGFPE, &sa, NULL);
sigaction(SIGILL, &sa, NULL);
sigaction(SIGTRAP, &sa, NULL);  // Swift trap
```

**方案 B：Mach Exception Port**（KSCrash 推荐，更早截获）

```c
#include <mach/mach.h>
#include <pthread.h>

static mach_port_t exception_port;

// 1. 创建独立线程接收 Mach 异常消息
static void* exception_handler_thread(void* arg) {
    while (1) {
        mach_msg_header_t msg;
        mach_msg(&msg, MACH_RCV_MSG, 0, sizeof(msg), exception_port,
                 MACH_MSG_TIMEOUT_NONE, MACH_PORT_NULL);
        // 解析 exception 类型、抓栈、写本地
        handle_mach_exception(&msg);
        // 转交给原 handler（避免影响系统行为）
    }
}

void install_mach_handler() {
    mach_port_allocate(mach_task_self(), MACH_PORT_RIGHT_RECEIVE, &exception_port);
    mach_port_insert_right(mach_task_self(), exception_port, exception_port,
                          MACH_MSG_TYPE_MAKE_SEND);
    // 注册到本 task 的所有崩溃异常类型
    task_set_exception_ports(mach_task_self(),
        EXC_MASK_BAD_ACCESS | EXC_MASK_BAD_INSTRUCTION |
        EXC_MASK_ARITHMETIC | EXC_MASK_BREAKPOINT | EXC_MASK_CRASH,
        exception_port,
        EXCEPTION_DEFAULT | MACH_EXCEPTION_CODES, THREAD_STATE_NONE);
    
    pthread_t thread;
    pthread_create(&thread, NULL, exception_handler_thread, NULL);
}
```

**为什么 Mach 比 BSD Signal 更好**：
- Mach handler 在**独立线程**执行，崩溃线程的状态完整保留 → 抓栈更准。
- 不受 async-signal-safe 限制（可以用 `malloc`/Objective-C）。
- 早于 BSD signal 触发，第一手数据。

#### 四、堆栈采集

```c
#include <mach/thread_act.h>

void dump_thread_stack(thread_t thread, int fd) {
    // 1. 获取崩溃线程的寄存器状态
    arm_thread_state64_t state;
    mach_msg_type_number_t count = ARM_THREAD_STATE64_COUNT;
    thread_get_state(thread, ARM_THREAD_STATE64, (thread_state_t)&state, &count);
    
    // 2. 从 pc/fp 开始 unwind
    uintptr_t pc = state.__pc;
    uintptr_t fp = state.__fp;
    
    int depth = 0;
    while (fp != 0 && depth < 64) {
        Dl_info info;
        if (dladdr((void*)pc, &info)) {
            dprintf(fd, "#%d %p %s + %ld\n", depth, (void*)pc,
                   info.dli_fname, (long)(pc - (uintptr_t)info.dli_fbase));
        }
        // 沿 frame pointer 链回溯（ARM64 调用约定）
        pc = *(uintptr_t*)(fp + 8);   // lr
        fp = *(uintptr_t*)(fp);       // 上一个 fp
        depth++;
    }
}
```

#### 五、符号化

同 §3.5.4：用 `atos` + dSYM。

### 3.5.6 iOS Watchdog / OOM 崩溃全链路

#### 一、如何引起崩溃

**Watchdog（启动 hang）**：
- iOS 启动期（didFinishLaunching 完成前）必须在 **~20 秒** 内完成。
- 后台→前台过渡时 **~5 秒**。
- 超时 → 系统直接发 `SIGKILL`（不可捕获），日志为 `0x8badf00d`。

**Jetsam（OOM）**：
- iOS 没有传统 Linux OOM Killer，用 Jetsam 机制。
- 内存吃紧 → 系统按优先级杀进程，前台应用也可能被杀。
- 日志为 `EXC_RESOURCE / MEMORY` 或直接进程不见。

#### 二、系统投递流程

```
   启动 hang 场景：
   App 启动 → main() → application:didFinishLaunching: 
       │
       ├─ 20 秒内完成 ──▶ 正常
       │
       └─ 超时
              │
              ▼
       launchd 给 App 进程发 SIGKILL（无法捕获）
              │
              ▼
       ReportCrash 写崩溃日志（类型 0x8badf00d）
              │
              ▼
       App 完全没有响应机会


   Jetsam 场景：
   系统内存压力 → kernel 计算 jetsam priority
       │
       ▼
   按优先级从低到高杀进程（kernel_task → jetsam_kill）
       │
       ▼
   被杀进程收到 SIGKILL（不可捕获）
       │
       ▼
   下次启动后，可通过 MetricKit 拿到 jetsam 报告
```

#### 三、监听点

**唯一可靠的方法：MetricKit（iOS 13+）**

```swift
import MetricKit

class MetricSubscriber: NSObject, MXMetricManagerSubscriber {
    func didReceive(_ payloads: [MXMetricPayload]) { /* 性能指标 */ }
    
    @available(iOS 14.0, *)
    func didReceive(_ payloads: [MXDiagnosticPayload]) {
        for payload in payloads {
            // 启动 hang
            payload.applicationLaunchDiagnostics?.forEach { hang in
                let stack = hang.callStackTree.jsonRepresentation()
                report(type: "launch_hang", duration: hang.launchDuration, stack: stack)
            }
            // OOM/Jetsam
            payload.crashDiagnostics?.forEach { crash in
                if crash.terminationReason?.contains("memory") == true {
                    report(type: "oom", stack: crash.callStackTree.jsonRepresentation())
                }
            }
            // CPU 异常
            payload.cpuExceptionDiagnostics?.forEach { exc in /* ... */ }
        }
    }
}

// 在 didFinishLaunching 注册
MXMetricManager.shared.add(MetricSubscriber())
```

#### 四、堆栈采集

MetricKit 直接提供**符号化好的 callStackTree**：

```json
{
  "callStacks": [{
    "threadAttributed": true,
    "callStackRootFrames": [{
      "binaryUUID": "...",
      "offsetIntoBinaryTextSegment": 17896,
      "binaryName": "MyApp",
      "symbol": "-[ViewController viewDidLoad]",
      "subFrames": [...]
    }]
  }]
}
```

#### 五、关键边界

- **MetricKit 延迟 24 小时**才能拿到（系统聚合机制）→ 不能实时告警，只能事后分析。
- iOS 12 及之前**完全没有办法**捕获 OOM/Watchdog → 用"异常退出排除法"：启动时检查上次是否正常 exit，否则推断为 OOM/Watchdog。

```swift
// 异常退出排除法
let lastExitNormal = UserDefaults.standard.bool(forKey: "lastExitNormal")
if !lastExitNormal {
    let lastVersion = UserDefaults.standard.string(forKey: "lastVersion")
    let crashCount = UserDefaults.standard.integer(forKey: "crashCount") + 1
    UserDefaults.standard.set(crashCount, forKey: "crashCount")
    // 排除已知崩溃类型，剩下的就是 OOM/Watchdog 嫌疑
    report(type: "unknown_kill", lastVersion: lastVersion)
}
UserDefaults.standard.set(false, forKey: "lastExitNormal")
// 在 applicationWillTerminate 中置为 true（正常退出）
```

### 3.5.7 Web 崩溃与错误全链路

#### 一、如何引起"崩溃"

Web 没有传统进程崩溃概念（浏览器沙箱），但有 4 类故障：

| 类型 | 触发 | 影响 |
|---|---|---|
| JS 运行时错误 | `null.foo` / `undefined()` | 当前调用栈终止，应用可继续 |
| Promise rejection 未处理 | `Promise.reject(...)` 没 catch | 控制台报错，应用继续 |
| 资源加载失败 | `<img src=404>` / 脚本 404 | 部分功能不可用 |
| 页面崩溃 | 内存爆炸 / Tab 进程崩溃 | 显示"页面无响应" |

#### 二、浏览器投递流程

```
   JS 抛错（throw / 隐式）
       │
       ▼
   V8 引擎沿调用栈找 try/catch
       │
       ├─ 找到 ──▶ 正常处理
       │
       └─ 没找到
              │
              ▼
       Window.dispatchEvent('error', ErrorEvent)
              │  ↑ 应用监听点
              ▼
       事件冒泡到 window
              │
              ▼
       如未 preventDefault → 控制台打印
       
   ───────────────────────────
   
   Promise 未捕获 rejection：
   await reject 或 .then(...) 无 catch
       │
       ▼
   宿主调度 microtask 完成后检测
       │
       ▼
   Window.dispatchEvent('unhandledrejection', PromiseRejectionEvent)
       │  ↑ 应用监听点
       ▼
   如未 preventDefault → 控制台打印
   
   ───────────────────────────
   
   资源加载失败：
   <img/script/link> 加载失败
       │
       ▼
   元素本身派发 'error' 事件（不冒泡到 window）
       │  ↑ 必须用 capture 阶段才能在 window 监听
       ▼
   仅元素自身的 onerror 可捕获
```

#### 三、监听点

```javascript
// 1. JS 运行时错误（普通错误）
window.addEventListener('error', (event) => {
    report({
        type: 'js_error',
        message: event.message,
        filename: event.filename,
        lineno: event.lineno,
        colno: event.colno,
        stack: event.error?.stack,  // 关键：完整调用栈
    });
}, true);  // capture=true：能捕获资源错误

// 2. Promise rejection
window.addEventListener('unhandledrejection', (event) => {
    report({
        type: 'promise_rejection',
        reason: String(event.reason),
        stack: event.reason?.stack,
    });
});

// 3. 资源加载失败（必须 capture=true）
window.addEventListener('error', (event) => {
    const t = event.target;
    if (t && (t.tagName === 'IMG' || t.tagName === 'SCRIPT' || t.tagName === 'LINK')) {
        report({
            type: 'resource_error',
            tagName: t.tagName,
            src: t.src || t.href,
        });
    }
}, true);

// 4. 框架错误（React/Vue）
// React: ErrorBoundary componentDidCatch
// Vue: app.config.errorHandler
```

#### 四、堆栈采集

JS Error 对象的 `.stack` 已经是符号化好的字符串（开发环境）：

```
Error: something broken
    at handleClick (app.js:42:11)
    at HTMLButtonElement.<anonymous> (app.js:120:5)
```

**注意**：跨域脚本错误默认返回 `"Script error."` 且无 stack，需配合：
- HTML：`<script src="..." crossorigin="anonymous">`
- 服务端：`Access-Control-Allow-Origin: *`

#### 五、符号化（sourcemap）

线上代码经过压缩/混淆后，stack 变成：

```
Error: x is not a function
    at i (main.abc123.js:1:54221)
```

需要 sourcemap 还原：

```javascript
// 使用 source-map 库
const { SourceMapConsumer } = require('source-map');
const consumer = await new SourceMapConsumer(rawSourceMap);
const original = consumer.originalPositionFor({ line: 1, column: 54221 });
// { source: 'src/handler.ts', line: 42, column: 5, name: 'handleClick' }
```

**关键约定**：
- 构建时生成 sourcemap，**不部署到 CDN**（否则源码泄漏）。
- 上传 sourcemap 到错误监控平台（Sentry/自建）。
- 用 `Content-Security-Policy: report-uri` 收集 CSP 违规。

#### 六、上报特殊性

```javascript
// 页面关闭也能发送
function reportError(data) {
    // 优先 sendBeacon（页面 unload 时也能发）
    if (navigator.sendBeacon) {
        navigator.sendBeacon('/report', JSON.stringify(data));
    } else {
        // 兜底 fetch（keepalive 允许页面关闭后继续）
        fetch('/report', {
            method: 'POST',
            body: JSON.stringify(data),
            keepalive: true,
        });
    }
}
```

### 3.5.8 跨端流程对照与堆栈采集对比

**端到端流程对照表**：

| 阶段 | Android Java | Android Native | iOS OC | iOS Mach | Web |
|---|---|---|---|---|---|
| **触发源** | `throw Throwable` | CPU 非法指令 | `@throw` | CPU 非法指令 / trap | `throw` / Promise reject |
| **OS/Runtime 投递** | JVM 栈展开 | 内核→signal | OC runtime | Mach exception port | V8 → Event dispatch |
| **应用监听 API** | `Thread.setDefaultUncaughtExceptionHandler` | `sigaction` | `NSSetUncaughtExceptionHandler` | `task_set_exception_ports` | `window.addEventListener('error')` |
| **堆栈采集 API** | `Throwable.stackTrace` / `Thread.getAllStackTraces` | `_Unwind_Backtrace` / `backtrace` | `[exc callStackSymbols]` / `backtrace` | `thread_get_state` + fp 链 | `Error.stack` |
| **符号化产物** | `mapping.txt` | NDK symbols（unstripped .so）| dSYM | dSYM | sourcemap |
| **符号化工具** | `retrace.jar` | `ndk-stack` / `addr2line` | `atos` / `symbolicatecrash` | 同 | `source-map` |
| **handler 上下文限制** | 无（普通 Java 线程）| async-signal-safe only | 较少限制 | 无（独立线程）| 无 |
| **是否能再继续运行** | 否（应让进程死）| 否 | 否 | 否 | 是（应用继续）|

**堆栈采集质量对比**：

| 维度 | Java | Native | OC/Mach | Web |
|---|---|---|---|---|
| 完整性 | ★★★★★（语言级）| ★★★（跨语言难）| ★★★★ | ★★★★（开发期）/ ★★（跨域）|
| 符号化复杂度 | 低 | 高 | 中 | 中 |
| 抓多线程能力 | ★★★★ `getAllStackTraces` | ★★（需 ptrace 类技巧）| ★★★★ Mach | ★（单线程模型）|
| 现场完整度 | 高（cause 链/locals 难）| 中（寄存器+栈）| 高 | 高（含 DOM/URL）|

**统一启示**：

- **崩溃捕获本质是\"在 runtime/OS 的强制终止前抢一步\"**：每个平台都有固定的"最后机会"hook 点。
- **堆栈采集的难度递增**：Java < Web < OC < Native（跨语言/跨进程难度最大）。
- **符号化是工程基建**：mapping/dSYM/sourcemap 三件套必须 CI 自动归档。
- **handler 上下文越严格的环境（Native signal），代码越要简单**：参考 async-signal-safe 函数列表。
- **\"看不见的崩溃\"路径**：Android LMK/ANR 系统历史 + iOS Watchdog/Jetsam MetricKit 是补全 [§00.5 案例](#005-贯穿案例某出行-app半数崩溃看不见事件) 中"60% 漏报"的唯一答案。

## 04.归因方法

### 4.1 崩溃归因决策树

```
崩溃事件
   │
   ├── 类型 A 异常型 ──▶ 看 stack 顶层
   │                  ├─ NPE → 找 nullable 来源
   │                  ├─ ClassCastException → 类型不一致
   │                  ├─ IndexOutOfBounds → 边界检查
   │                  └─ OOM → 走内存治理（卷二·03）
   │
   ├── 类型 B 信号型 ──▶ 看 signal 类型
   │                  ├─ SIGSEGV → 空指针 / 野指针
   │                  ├─ SIGABRT → assert 失败 / 主动 abort
   │                  ├─ SIGBUS → 内存对齐 / mmap 失败
   │                  └─ SIGFPE → 除零 / 浮点异常
   │
   └── 类型 C 系统强杀 ──▶ 看 ProcessExitReason / MetricKit
                      ├─ LMK → 内存压力（详见卷二·03）
                      ├─ ANR → ANR 治理（详见卷三·04）
                      └─ Force Stop → 用户主动
```

### 4.2 符号化与还原

**为什么需要符号化**

线上 release 包的 stack 是地址 / 混淆后的名字，必须用 mapping 文件还原才能定位代码。

```
   原始：  com.app.a.b.c() at 0x12345
   符号化后：UserListActivity.onCreate() at MainActivity.kt:42
```

**符号化方案**：

| 平台 | Mapping 文件 | 工具 |
|---|---|---|
| Android Java | mapping.txt（ProGuard / R8）| retrace / Bugly 自动 |
| Android Native | symbols / .so 含调试信息 | ndk-stack / addr2line |
| iOS | dSYM | symbolicatecrash / atos / Instruments |
| Web | sourcemap | Source Map Tools / Sentry 自动 |

**关键约定**：

- 每次发版必须保留 mapping / dSYM / sourcemap（按版本号归档）。
- 上报系统按版本自动符号化。

### 4.3 现场快照分析

崩溃时需要的"四件套"：

1. **完整 stack**：所有线程，不只主线程。
2. **设备信息**：型号 / 系统 / RAM / CPU / 屏幕。
3. **应用上下文**：版本 / 当前页面 / 最近 N 条用户操作。
4. **资源快照**：内存 / CPU / 网络状态。

**现场字段示例**：

```
{
  "type": "NullPointerException",
  "thread": "main",
  "stack": [...],
  "all_threads": {...},
  "device": {"model": "Pixel 6", "os": "Android 13", "ram": 8192, "free": 2300},
  "app": {"version": "3.5.1", "build": 12345},
  "context": {
    "current_activity": "UserListActivity",
    "last_actions": ["click_user", "scroll_list", ...]
  },
  "memory": {"java_heap": 64MB, "native": 32MB, "total_pss": 200MB}
}
```

### 4.4 长尾崩溃归因

少数用户的崩溃往往是：

- 极端机型（如 SamsungA01 这类低端机）
- 极端系统版本（Android 5 / iOS 12 等老版本）
- 极端用户行为（罕见操作组合）
- 设备状态异常（root / 越狱 / 第三方 ROM）

**长尾治理思路**：

- 设定**支持范围**（minSdk / 最低 RAM / 不支持 root）。
- 范围外提示用户升级 / 友好降级。
- 不要追求"100% 用户都能用"。

## 05.求证实验 ⭐

### 5.1 实验一：捕获完整性

**Step 1 — 原始观察**

工程师都接 Crashlytics 等，但**它们能捕获多少崩溃？还有什么漏的？**

**Step 2 — 提出疑问**

> **常见崩溃监控库（仅 hook 异常）相比"全方案"（异常 + 信号 + 历史）覆盖率差异多少？**

**Step 3 — 设计实验**

构造各类崩溃测试用例，测量各方案捕获率：

| 用例 | 仅异常 hook | 异常 + 信号 hook | 全方案 |
|---|---|---|---|
| Java NPE | ✅ | ✅ | ✅ |
| Java OOM | ✅ | ✅ | ✅ |
| Native SIGSEGV | ❌ | ✅ | ✅ |
| Native SIGABRT | ❌ | ✅ | ✅ |
| ANR | ❌ | ❌ | ✅（系统历史）|
| LMK 杀进程 | ❌ | ❌ | ✅ |
| 用户 Force Stop | ❌ | ❌ | ✅ |

**Step 4 — 实测数据**

某 App 实际数据：

| 方案 | 捕获率 |
|---|---|
| 仅异常 hook | 65% |
| 异常 + 信号 hook | 88% |
| 全方案（+ 系统历史）| 99% |

**Step 5 — 提炼结论**

> **仅异常 hook 漏掉 35% 崩溃；必须三方案组合才能达到 99% 捕获率。**

工程意义：

- 必须接 Native 信号 hook（10-20% 漏报集中在这）。
- 必须用系统历史补全（ANR / OOM 被杀）。
- "看不到的崩溃"比看到的更危险。

**Step 6 — 边界**

- 系统历史 API 需要 Android 11+。
- iOS MetricKit 数据延迟 24 小时。
- Web 没有"系统历史"概念。

---

### 5.2 实验二：上报成功率

**Step 1 — 原始观察**

崩溃发生时网络往往不可用（启动期 / 弱网），**多少崩溃能成功上报？**

**Step 2 — 提出疑问**

> **不同上报策略下，崩溃数据到达服务端的比例是多少？**

**Step 3 — 设计实验**

| 策略 | 描述 |
|---|---|
| A 同步上报 | 崩溃时立即网络上报 |
| B 仅本地 + 下次启动上报 | 本地写文件，下次启动检查 |
| C 本地 + 启动上报 + 后台上报 | B + 应用进入后台时也尝试 |

**Step 4 — 实测数据**

| 策略 | 上报成功率 |
|---|---|
| A 同步上报 | 60-70%（崩溃时网络不可靠）|
| B 启动上报 | 88-92% |
| C B + 后台上报 | 95-98% |

**Step 5 — 提炼结论**

> **崩溃时同步上报成功率仅 60-70%。  
> "本地优先 + 多次重试"能让到达率达到 95%+。**

工程意义：

- 不要在崩溃 handler 里直接调网络。
- 写本地文件 → 下次启动检查 → 上报。
- 应用进入后台时也尝试一次（兜底）。

**Step 6 — 边界**

- iOS 启动 watchdog 直接杀，本地写文件可能也来不及。
- Web 用户关闭 Tab 即丢，依赖 sendBeacon / unloadEvent。
- 嵌入式设备无法上报到外部，必须本地存储足够久。

---

### 5.3 实验三：现场抓取价值

**Step 1 — 原始观察**

只抓 stack 还是抓完整现场？**完整现场对修复效率提升多少？**

**Step 2 — 提出疑问**

> **完整现场（stack + device + 用户操作链 + 内存快照）相比仅 stack，定位效率提升多少？**

**Step 3 — 设计实验**

某团队对比两种数据格式：

- A 仅 stack：可还原"哪行代码崩"。
- B 完整现场：A + device + 用户行为 + 资源状态。

**Step 4 — 实测数据**

随机选 100 个崩溃，对比修复时间：

| 数据完整度 | 平均定位耗时 | 一次修复成功率 |
|---|---|---|
| A 仅 stack | 3.5 小时 | 55% |
| B 完整现场 | 0.8 小时 | 85% |

**Step 5 — 提炼结论**

> **完整现场让定位耗时 -75%，一次修复成功率 +30%。  
> 是少有的"采集成本极低，效果极高"的工作。**

工程意义：

- 必须采集设备 / 系统 / 应用版本。
- 用户操作链（最近 30 条）极有价值。
- 内存 / 网络快照能识别环境因素。

**Step 6 — 边界**

- 现场数据量增加 5-10×（仍可控）。
- 隐私敏感数据要脱敏。

---

### 5.4 实验四：Tombstone / MetricKit 补全静默崩溃

**Step 1 — 原始观察**

[§00.5 案例](#005-贯穿案例某出行-app半数崩溃看不见事件) 中应用 SDK 捕获不到 LMK 杀、jetsam 杀、启动 hang。**系统级 API 能补全多少？**

**Step 2 — 提出疑问**

> **Android `getHistoricalProcessExitReasons` + iOS MetricKit 能在多大程度上补全"静默崩溃"？**

**Step 3 — 设计实验**

某 App 真实数据 1 个月：

| 崩溃源 | Crashlytics 捕获 | 加系统 API 后捕获 | 漏报率减少 |
|---|---|---|---|
| Android Java 异常 | 100% | 100% | 0 |
| Android Native | 0%（未接 NDK）| 接 NDK 后 98% | -98pp |
| Android LMK 杀 | 0% | `getHistoricalProcessExitReasons` 85% | -85pp |
| Android 启动早期崩溃 | 30%（SDK 未 init）| 自实现 SIGQUIT 早期 90% | -60pp |
| iOS OC/Mach | 95% | KSCrash 99% | -4pp |
| iOS 启动 hang | 0% | MetricKit 92% | -92pp |
| iOS OOM/jetsam | 0% | MetricKit 88% | -88pp |
| iOS 强杀（Watchdog）| 0% | MetricKit 90% | -90pp |

**Step 4 — 结论**

> **系统级 API 能补全 60-98% 的"静默崩溃"。是从"看见 40%"到"看见 99%"的关键一跃。**

工程意义：
- Android 11+ 必须接 `getHistoricalProcessExitReasons`。
- iOS 13+ 必须接 MetricKit。
- 实时性较差（MetricKit 24h 延迟），但事后分析价值巨大。

**Step 5 — 边界**

- 系统 API 仅在新版本可用（A11+ / iOS13+），老版本需其他手段。
- MetricKit 延迟 24h，不适合实时告警。

---

### 5.5 实验五：符号化自动化对治理时长的影响

**Step 1 — 原始观察**

崩溃栈是地址（如 `0x4f8a23`），需符号化才能读懂。**手动 vs 自动符号化对治理速度影响多大？**

**Step 2 — 提出疑问**

> **CI 自动化符号化 vs 出问题再手动符号化，从"发现崩溃"到"开始修复"的时长差距？**

**Step 3 — 设计实验**

某团队对比两种模式：

| 模式 | 平均处理时长 |
|---|---|
| 手动符号化（出问题查 mapping/dSYM）| **4-12 小时**（需找包→找 mapping→运行工具）|
| CI 自动符号化（每次发版自动上传）| **< 5 分钟**（看板直接展示可读栈）|
| **从崩溃发现到开发修复**：手动 | **24-48 小时** |
| **从崩溃发现到开发修复**：自动 | **2-4 小时** |

**Step 4 — 结论**

> **自动符号化是崩溃治理的"基础设施"。手动模式让修复时长 6-10×。**

工程意义：
- CI 每次发版自动上传 mapping.txt / dSYM。
- 发版前阻断"未上传符号"的版本。
- 多版本符号库长期保存（至少 1 年）。

**Step 5 — 边界**

- 历史版本未上传符号则无法补救，需提前规划。
- 大型 SDK 的符号文件可能 100MB+，需 CI 优化。

```
   捕获完整性           → 三方案组合覆盖 99%          ─┐

                                                       │

```

**统一启示**：

- **"看不到的崩溃"是最大风险**，必须三方案组合 + 系统补全。

- **系统 API 是静默崩溃的解药**：A11+/iOS13+ 必接。
- **自动符号化是基础设施**：手动是反模式。

## 06.优化策略深化

> 本节回答四个递进问题：**①如何让所有崩溃都被捕获？②如何让现场质量足以定位？③如何让上报数据到家？④如何让 Top 5 持续下降？**

### 6.1 第一层：捕获覆盖（消灭盲区）

**核心命题**：[§00.5 案例](#005-贯穿案例某出行-app半数崩溃看不见事件) 证明单一 SDK 漏 60% 崩溃。本层目标：**三方案组合 + 系统 API 补全，覆盖率 99%**。

**策略 1.1：Android 三件套（Java + Native + 系统历史）**

- **机理**：[§5.1](#51-实验一捕获完整性) + [§5.4](#54-实验四tombstone--metrickit-补全静默崩溃) 双重证据。
- **代码**：

```kotlin
// Java 异常
Thread.setDefaultUncaughtExceptionHandler(JavaCrashHandler())
// Native 崩溃（NDK 信号）
NativeCrashCapture.install()  // 接 xCrash/Breakpad/Bugly NDK
// 系统历史（A11+）
if (Build.VERSION.SDK_INT >= 30) {
    val am = getSystemService(ActivityManager::class.java)
    am.getHistoricalProcessExitReasons(null, 0, 100)
        .filter { it.reason in listOf(REASON_CRASH, REASON_LOW_MEMORY, REASON_ANR) }
        .forEach { report(it) }
}
```

- **收益**：[§00.5 案例](#005-贯穿案例某出行-app半数崩溃看不见事件) 可见崩溃率 0.04% → 0.48%（暴露真相）。
- **边界**：A11+ API；老版本只能依赖 SDK。

**策略 1.2：iOS 三件套（NSException + Mach + MetricKit）**

- **机理**：见 [§3.1 ② 信号捕获](#31-三类捕获方案的本质) + [§5.4 实验](#54-实验四tombstone--metrickit-补全静默崩溃)。
- **代码**：

```objc
// OC 异常
NSSetUncaughtExceptionHandler(handleException);
// Mach 异常（KSCrash 自动）
[[KSCrash sharedInstance] install];
// MetricKit（iOS 13+）
if (@available(iOS 13.0, *)) {
    [[MXMetricManager sharedManager] addSubscriber:[MetricSubscriber new]];
}
```

- **收益**：iOS OOM/启动 hang 可见率 0% → 90%+。
- **边界**：MetricKit 延迟 24h，不适合实时告警。

**策略 1.3：Web 三件套（onerror + unhandledrejection + resource error）**

- **机理**：见 §3.3 跨平台采集对照表。
- **代码**：

```javascript
window.addEventListener('error', e => reportJsError(e), true);  // 捕获阶段含资源错误
window.addEventListener('unhandledrejection', e => reportPromiseError(e));
```

- **收益**：Promise rejection / 资源加载失败可见。
- **边界**：跨域脚本需 `crossorigin` + CORS。

**策略 1.4：早期注册（启动前的崩溃也要捕获）**

- **机理**：[§00.5 案例](#005-贯穿案例某出行-app半数崩溃看不见事件) 启动早期崩溃漏 70%。
- **代码**：在 Application.onCreate 第一行或 main() 第一行注册。
- **收益**：启动早期崩溃可见率 30% → 90%。
- **边界**：早期注册的 handler 必须极简（避免自身崩溃）。

---

### 6.2 第二层：现场质量（让定位高效）

**核心命题**：[§5.3 实验](#53-实验三现场抓取价值) 完整现场让定位 -75%。

**策略 2.1：完整字段采集**

- **机理**：stack + device + 用户操作链 + 内存 + 网络。
- **代码**：

```kotlin
data class CrashReport(
    val stack: String,
    val type: String,
    val deviceModel: String,
    val osVersion: String,
    val appVersion: String,
    val freeMemoryKB: Long,
    val freeStorageMB: Long,
    val networkType: String,
    val lastActions: List<UserAction>,  // 最近 30 条
    val foreground: Boolean,
    val crashTime: Long
)
```

- **收益**：定位时长 3.5h → 0.8h。
- **边界**：上报体积 ×5-10（仍可控）；隐私数据需脱敏。

**策略 2.2：用户操作链记录**

- **机理**：知道用户做了什么才能复现。
- **代码**：

```kotlin
object ActionTracker {
    private val ring = RingBuffer<UserAction>(30)
    fun record(action: UserAction) = ring.offer(action)
    fun snapshot(): List<UserAction> = ring.toList()
}
// Activity 生命周期、点击、网络请求都记录
```

- **收益**：复现率从 30% 提升到 70%。
- **边界**：循环 buffer 防止内存膨胀；敏感操作脱敏。

**策略 2.3：崩溃前 N 帧的方法 trace**

- **机理**：method trace 让"崩溃前几秒在做什么"可见。
- **代码**：ASM 插桩记录最近 50 个方法调用。
- **收益**：定位"几乎不可能"的崩溃。
- **边界**：每方法增 1-2μs；线上仅采样。

**策略 2.4：内存/线程/资源快照**

- **机理**：OOM 类崩溃需要内存快照才能归因。
- **代码**：崩溃时记录 Java/Native heap、线程数、FD 数、bitmap 总数。
- **收益**：OOM 类崩溃归因效率 +80%。
- **边界**：快照采集本身可能失败（崩溃后状态不可信）。

---

### 6.3 第三层：上报可靠性（让数据到家）

**核心命题**：[§5.2 实验](#52-实验二上报成功率) 证明同步上报不可信，本地优先 + 启动重试是唯一可靠方案。

**策略 3.1：本地写入优先（崩溃时不发网络）**

- **机理**：崩溃时一切都不可信（内存损坏、网络可能挂）。
- **代码**：

```kotlin
class CrashHandler : Thread.UncaughtExceptionHandler {
    override fun uncaughtException(t: Thread, e: Throwable) {
        val report = collectCrashReport(t, e)
        // 写本地文件（不走网络）
        File(context.filesDir, "crash_${UUID.randomUUID()}.json")
            .writeText(report.toJson())
        // 交给系统默认处理
        defaultHandler?.uncaughtException(t, e)
    }
}
```

- **收益**：上报成功率 60% → 95%+。
- **边界**：本地写入需保证原子性；磁盘满时仍可能失败。

**策略 3.2：下次启动时检查并上报**

- **机理**：应用重启后网络环境恢复，可靠上传。
- **代码**：

```kotlin
fun onApplicationStart() {
    File(context.filesDir).listFiles { f -> f.name.startsWith("crash_") }
        ?.forEach { file ->
            uploader.send(file.readText()) { success ->
                if (success) file.delete()
            }
        }
}
```

- **收益**：跨启动可靠上报。
- **边界**：用户不再打开应用则数据永远丢；可配合 WorkManager 在后台尝试。

**策略 3.3：失败重试 + 指数退避**

- **机理**：同 [`卷四·02 §6.3 策略 3.2`](../04.业务专项篇/02.网络性能分析优化.md)。
- **代码**：1s/2s/4s/8s/16s 退避，超 24h 丢弃。
- **收益**：弱网/服务端波动期数据不丢。
- **边界**：必须有兜底丢弃，否则无限堆积。

**策略 3.4：多通道（HTTP + sendBeacon + WorkManager）**

- **机理**：单通道失败时有备用。
- **代码**（Web）：

```javascript
function reportCrash(data) {
    // 优先 Beacon（页面关闭也能发）
    if (navigator.sendBeacon) {
        navigator.sendBeacon('/crash', data);
    } else {
        fetch('/crash', { method: 'POST', body: data, keepalive: true });
    }
}
```

- **收益**：上报成功率再提 3-5%。
- **边界**：sendBeacon 仅支持小体积；大体积仍需 HTTP。

### 6.4 第四层：治理闭环（让 Top 5 持续下降）

**核心命题**：捕获了数据不治理 = 资源浪费。本层目标：**让 Top 5 崩溃每周下降**。

**策略 4.1：错误聚合 + Top 5 排序**

- **机理**：见 [`卷一·02 §5.5`](../01.体系建设篇/02.稳定性专项建设.md) 错误聚合粒度。
- **代码**：fingerprint = hash(stack 前 5 帧 + error type)。
- **收益**：80/20 法则，治 Top 5 解决 80% 崩溃。
- **边界**：聚合粒度需调优。

**策略 4.2：自动符号化（基础设施）**

- **机理**：[§5.5 实验](#55-实验五符号化自动化对治理时长的影响) 修复时长 6-10×。
- **代码**：CI 每次发版上传 mapping/dSYM/sourcemap 到崩溃平台。
- **收益**：可读栈数据，治理速度大幅提升。
- **边界**：未上传符号则无法补救，必须发版前阻断。

**策略 4.3：每周 Top 5 治理 + 数据看板**

- **机理**：固化为研发流程。
- **代码**：每周一自动生成 Top 10 崩溃报告，分配 owner，1 周内必修复或评估。
- **收益**：Top 5 占比从 80% 持续下降到 50%（健康分布）。
- **边界**：owner 必须有时间投入；管理层支持。

**策略 4.4：版本对比 + 自动告警**

- **机理**：每次发版自动对比 Top 5 是否新增。
- **代码**：

```python
def diff_top_crashes(prev_version, curr_version):
    new_crashes = curr_version.top - prev_version.top
    if new_crashes:
        alert("发版新增 Top 崩溃", new_crashes)
```

- **收益**：退化 24h 内被发现。
- **边界**：误报需调阈值。

### 6.5 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 | 对应策略 |
|---|---|---|---|---|---|
| 极高 | 异常 + 信号 + 系统历史三方案 | 捕获率 60% → 99% | 1-2 周 | 低 | 1.1-1.3 |
| 极高 | 自动符号化 CI 集成 | 修复时长 6-10× | 1 周（基建）| 低 | 4.2 |
| 极高 | 完整现场抓取 | 定位 -75% | 1 周 | 低 | 2.1-2.2 |
| 极高 | 本地优先 + 启动重试 | 上报率 60% → 95%+ | 几天 | 低 | 3.1-3.2 |
| 高 | 早期注册（Application 第一行）| 启动期崩溃可见 30% → 90% | 几天 | 低 | 1.4 |
| 高 | MetricKit / getHistoricalProcessExitReasons | 静默崩溃可见 0 → 90% | 1 周 | 低 | 1.1+1.2 |
| 高 | Top 5 每周治理流程 | Top 占比持续下降 | 持续投入 | 中 | 4.3 |
| 中 | 用户操作链 | 复现率 30% → 70% | 1-2 周 | 中（隐私）| 2.2 |
| 中 | 方法 trace 插桩 | 复杂问题可见 | 2-3 周 | 中（性能）| 2.3 |
| 中 | 内存/线程快照 | OOM 类归因 +80% | 1-2 周 | 中 | 2.4 |
| 中 | 多通道上报（含 Beacon）| 上报率再 +3-5% | 几天 | 低 | 3.4 |
| 中 | 版本对比 + 自动告警 | 退化早发现 | 1-2 周 | 低 | 4.4 |
| 低 | 自实现 Crash SDK | 几乎无收益 | 极高 | 极高 | - |

**避免反向收益**：

- **现场字段过多**：上报体积爆炸（>100KB）。
- **同步网络上报**：成功率反而低。
- **未上传符号就发版**：上线后崩溃无法定位。
- **只接 Java/OC 异常**：[§00.5 案例](#005-贯穿案例某出行-app半数崩溃看不见事件) 漏 60% 的根因。
- **自实现 SDK**：成熟方案已经覆盖 99% 场景。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某应用 Android / iOS / Web 的崩溃监控都用了主流 SDK，但仍有 15-20% 崩溃"看不到"（用户报但日志无）。

**度量与归因**：

通过日活下降发现"隐性崩溃"问题。深度调查发现：

- Android：Native 信号 hook 未启用，Native crash 全漏。
- iOS：启动 hang（watchdog 杀）未监控。
- Web：unhandledrejection 未监听。

**假设与求证**：

提出**统一假设**："补齐每个平台的盲区"。

**修复**：

- Android：启用 Bugly NDK + ProcessExitReason。
- iOS：接入 MetricKit + KSCrash。
- Web：补 unhandledrejection + sendBeacon 上报。

**验证**：

| 平台 | 优化前可见崩溃率 | 优化后可见崩溃率 | 实际崩溃率（不变）|
|---|---|---|---|
| Android | 0.08% | 0.15% | 0.15% |
| iOS | 0.04% | 0.09% | 0.09% |
| Web | 0.05% | 0.07% | 0.07% |

可见崩溃率上涨意味着捕获更全面（不是问题恶化）。

**统一启示**：跨端崩溃监控通用法则 = **三方案组合覆盖盲区**。

### 7.2 平台特异案例

**背景**：iOS 应用启动期偶发崩溃，但 Crashlytics 完全收不到。

**现象**：用户报告"打开就闪退"，但崩溃数据为零。

**度量与归因**：

- 启动 watchdog 5 秒内强杀 → SIGKILL → 应用代码完全不响应。
- Crashlytics 也来不及上报。

**假设与求证**：

**假设**：用 MetricKit 在下次启动时拿启动 hang 数据。

**实验**：接入 MetricKit `MXLaunchHangDiagnostic`，下次启动后 24 小时内收到详细 hang stack。

**修复**：

- 接入 MetricKit。
- 监控 hang stack，识别启动期同步重任务。
- 用分级初始化（详见 [`卷四·01`](../04.业务专项篇/01.App冷启动优化.md)）异步化。

**验证**：启动 hang 率从 0.08% 降到 0.02%。

**边界**：MetricKit 数据延迟 24 小时，不能实时响应，只能事后分析。

## 08.防劣化与长效治理

### 8.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
[Lint+测试]   [自动化]        [监控+治理]
```

### 8.2 编码期 Lint

- 关键路径未做空值检查 → 错误。
- 使用过时危险 API → 警告。
- 全局未注册崩溃 handler → 错误。
- 未启用混淆但未配置 mapping 上传 → 警告。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 每次发版必须有 mapping / dSYM 归档。
- 自动化测试覆盖核心流程。
- 灰度阶段崩溃率 ≤ 上一版本。

**线上 SLO**：

- 总崩溃率 < 0.1%。
- Top 5 崩溃总占比 ≤ 50%（避免单点垄断）。
- 上报到达率 > 95%。
- 符号化成功率 > 90%。

## 10.总结与延伸

### 10.1 五条核心原则

1. **三方案组合 + 系统 API 补全**：异常 + 信号 + 历史，从 60% 提到 99%（[§5.1](#51-实验一捕获完整性) + [§5.4](#54-实验四tombstone--metrickit-补全静默崩溃)）。
2. **现场必须完整**：[§5.3](#53-实验三现场抓取价值) 让定位 -75%。
3. **本地优先 + 启动重试**：上报率 60% → 95%+。
4. **自动符号化**：[§5.5](#55-实验五符号化自动化对治理时长的影响) 修复时长 6-10×。
5. **Top 5 持续治理**：80/20 法则不是口号是制度。

### 10.2 五个常见误区

1. **"接了 Crashlytics 就够了"**：错（[§00.5 案例](#005-贯穿案例某出行-app半数崩溃看不见事件) 漏 60% 崩溃）。
2. **"崩溃时同步上报"**：错（成功率低）。
3. **"只采 stack 够用"**：错（定位效率差 4×）。
4. **"忽略系统 API"**：错（[§5.4](#54-实验四tombstone--metrickit-补全静默崩溃) MetricKit/getHistoricalProcessExitReasons 补全 60-98% 静默崩溃）。
5. **"出问题再补符号"**：错（[§5.5](#55-实验五符号化自动化对治理时长的影响) 修复时长 6-10×；必须 CI 自动化）。
