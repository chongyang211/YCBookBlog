## 01.问题域定义

### 1.1 现象与代价

安全措施的性能影响：

- **加密 / 解密 CPU 消耗**：每次 API 请求加密、本地数据加密。
- **加固包体积膨胀**：Android 加固通常增加 5-15MB。
- **校验启动慢**：签名校验 / 完整性校验耗时。
- **防调试影响调试体验**：开发期效率受损。
- **沙箱隔离 IPC 开销**：iOS WKWebView 进程外渲染需要 IPC。

**业务代价**：

- 加密用错算法（如 RSA 解大数据）会让 API 响应慢 100ms+。
- 加固让冷启动慢 100-500ms。
- 安全检查未做合理可能导致严重事故（数据泄露 / 反编译破解）。

### 1.2 度量准则

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 单次加密耗时 | 单次操作 | < 1ms（小数据）/ < 10ms（大数据）|
| 启动安全开销 | 校验占启动期 | < 100ms |
| 加固包增加 | 包体积增量 | < 15% |
| 安全告警率 | 风险事件 / 请求 | < 0.1% |

### 1.3 行业基准与目标

| 维度 | 良好 | 合格 |
|---|---|---|
| HTTPS 全启用 | 是 | 必须 |
| 关键数据加密 | AES + 密钥安全存储 | 必须 |
| 包加固 | 中端机启动 +< 100ms | 视场景 |
| 反调试 / 防 hook | release 启用 | 视风险 |

### 1.4 反直觉问题清单

带着这些问题阅读：

1. AES 是不是越长 key 越安全越慢？
2. RSA 真的能加密大数据吗？
3. 加固一定让启动慢吗？
4. 防 root / 防越狱真有用吗？
5. WhiteBox 加密能完全防破解吗？
6. 国密算法比 AES 慢多少？
7. HTTPS 必须双向认证吗？
8. 防 hook 是不是只对国内有用？

## 02.第一性原理

### 2.1 安全本质定义

**一句话定义**：

> **安全 = 通过加密 / 校验 / 隔离 / 混淆等手段，让"非授权方获取或篡改数据"的成本远高于其潜在收益**。

这句话隐含三个不可商量的物理约束：

**约束一：安全是"成本对抗"，不是"绝对防护"**

任何安全措施都可以被破解，只是需要的时间 / 资金 / 能力。设计目标是让**攻击成本 > 收益**。

**约束二：所有安全措施都有性能代价**

```
   加密 = CPU 时间
   加固 = 包体积 + 启动时长
   校验 = 启动时长 + IO
   防调试 = 运行时检测开销
   隔离 = IPC 开销
```

工程的目标不是"无限提升安全"，而是"匹配业务风险等级"。

**约束三：安全不能"部分做"**

链条上最弱一环决定整体安全。**一个不加密的 API 让全应用 HTTPS 失去意义**。

### 2.2 安全与性能权衡模型

```
   ┌──────────────────────────────────────┐
   │ 必须做（关乎用户隐私 / 金钱）             │
   │ - HTTPS 全站                           │
   │ - 用户密码 hash + salt                  │
   │ - 关键 API 签名                          │
   │ - 敏感数据本地加密存储                    │
   ├──────────────────────────────────────┤
   │ 视风险做（防破解 / 反作弊）              │
   │ - 代码混淆                              │
   │ - 加固                                  │
   │ - 反调试                                │
   │ - 完整性校验                            │
   ├──────────────────────────────────────┤
   │ 一般不做（成本 > 收益）                  │
   │ - WhiteBox 加密                         │
   │ - 完全自定义协议                         │
   │ - 极致防 hook                           │
   └──────────────────────────────────────┘
```

**关键认知**：

- 第一类是基线（不做就是事故）。
- 第二类按业务（金融 / 游戏 必做，工具 视情况）。
- 第三类大多数应用不必做。

### 2.3 跨平台同构原理

所有平台的安全 + 性能权衡都基于同一对抗模型：

```
   通用安全模型：

      [攻击方]                  [防御方]
       破解能力                  保护强度
          │                          │
          ▼                          ▼
       破解时间 ─── < ──── 防御过期时间 → 不安全
                  > ──── 防御过期时间 → 安全
```

每个平台都必须做：

| 抽象组件 | 解决什么问题 |
|---|---|
| 传输加密 | 防止网络嗅探 |
| 存储加密 | 防止本地数据窃取 |
| 代码保护 | 防止逆向 / 篡改 |
| 完整性校验 | 防止包被修改 |
| 运行时防御 | 防止动态 hook / 调试 |

**跨平台术语对照**

| 通用术语 | Android | iOS | Web |
|---|---|---|---|
| 传输加密 | HTTPS / TLS | 同 | 同 |
| 存储加密 | EncryptedSharedPreferences / Keystore | Keychain | localStorage 加密 / IndexedDB |
| 代码混淆 | R8 / ProGuard | LLVM 优化 | Terser / WebAssembly |
| 加固 | 360 加固 / 腾讯乐固 | iOS 系统签名 | N/A |
| 防 hook | Frida 检测 / 自实现 | 同 | N/A |
| 完整性 | APK 签名 / SafetyNet | App Attest | SRI（Subresource Integrity） |

**同构带来的工程价值**

1. **威胁模型通用**：传输 / 存储 / 代码 / 运行时 四类威胁跨端一致。
2. **技术选型有锚点**：HTTPS / AES / hash 是所有平台共识。
3. **代价评估通用**：CPU / 体积 / 启动时长 / 开发体验。

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web |
|---|---|---|---|
| 系统级保护 | SELinux / 沙箱 | 沙箱 + 严格审核 | 浏览器同源 / CSP |
| 反编译难度 | 低（dex 易反编译）| 高（Mach-O 优化）| 极低（明文 JS）|
| 加固生态 | 成熟（多家加固服务）| 不需要（系统签名）| WebAssembly 部分 |
| 平台审核 | Play 自动化扫描 | App Store 人工审核 | 浏览器扩展审核 |
| 用户改包风险 | 高 | 低（须越狱）| 浏览器扩展 / proxy |

> 后续遇到平台特化点回引本节。

## 03.度量与采集

### 3.1 三类采集方案的本质

```
   ① 性能开销监控（加密 / 校验耗时）
                ② 安全告警（异常行为 / 风险事件）
                            ③ 攻击模拟（线下渗透测试）
```

---

**① 性能开销监控**

**核心原理（一句话）**：在加密 / 校验等关键操作处埋点，监控各操作的实际耗时与失败率。

**适用边界**：所有应用必备的常驻监控。

---

**② 安全告警**

**核心原理（一句话）**：监控运行时风险事件（root 检测、hook 检测、签名校验失败、异常解密失败）。

**适用边界**：金融 / 游戏 / 高安全应用必备。

---

**③ 攻击模拟**

**核心原理（一句话）**：线下用攻击者视角扫描应用漏洞。

**工作机理**：

- 反编译看代码暴露程度。
- Frida hook 试探防御。
- HTTPS 抓包试探（自签名根证书）。
- 改包测签名校验。

**适用边界**：发版前必跑的安全 audit。

---

**三类方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 主要局限 |
|---|---|---|---|---|---|
| ① 性能监控 | 代码内 | 操作级 | 极低 | 高 | 不知风险 |
| ② 安全告警 | 运行时 | 事件级 | 低 | 高 | 误报 / 漏报 |
| ③ 攻击模拟 | 线下 | 黑盒 | 无（线下）| 高 | 一次性 |

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| 加密太慢 | ✅ | ❌ | ❌ |
| 被动态 hook | ❌ | 部分 | ✅ |
| 被反编译破解 | ❌ | ❌ | ✅ |
| 异常解密失败 | 部分 | ✅ | ❌ |

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web |
|---|---|---|---|
| 加密耗时 | Cipher.doFinal 计时 | CryptoKit signpost | crypto.subtle 计时 |
| Root 检测 | RootBeer / 自实现 | 越狱检测库 | N/A（沙箱足够）|
| Hook 检测 | Frida 检测 / Xposed 特征 | 同 | N/A |
| 签名校验 | PackageInfo + cert 比对 | 系统级 | SRI |
| 抓包检测 | 检测代理 / VPN | 同 | N/A |

### 3.4 数据可信度评估

| 数据 | 可信度 | 偏差来源 |
|---|---|---|
| 加密耗时 | 高 | 直接计时 |
| Root / 越狱检测 | 中 | 检测可被绕过 |
| Hook 检测 | 中 | 攻击者升级对抗 |
| 攻击模拟 | 高（线下）| 仅一次性 |

## 04.归因方法

### 4.1 安全性能决策树

```
安全相关性能问题
   │
   ├── 加密太慢 ──▶ 算法选择
   │            ├─ 大数据用对称加密（AES）
   │            ├─ 小数据 / 密钥协商用非对称（RSA / ECC）
   │            ├─ 哈希用 SHA-256
   │            └─ 国密视场景
   │
   ├── 加固让启动慢 ──▶ 加固方案
   │              ├─ DEX 加密 → 启动时解密
   │              ├─ Native 加固 → 启动时初始化
   │              └─ 评估必要性
   │
   ├── HTTPS 慢 ──▶ 传输优化
   │            ├─ 长连接（卷四·02）
   │            ├─ TLS 1.3
   │            └─ 0-RTT
   │
   └── 防 hook 影响调试 ──▶ Debug 配置
                       ├─ release 启用 / debug 关闭
                       └─ 灰度环境配置
```

### 4.2 加密代价归因

**算法选择决定一半性能**：

| 场景 | 推荐 | 不推荐 |
|---|---|---|
| 大数据本地加密 | AES-256-GCM | RSA（不能加密大数据） |
| 密钥协商 | ECDH | RSA-2048（慢）|
| 数据签名 | ECDSA / Ed25519 | RSA-4096 |
| 哈希 | SHA-256 / Blake2 | MD5（不安全）/ SHA-1（已弱）|

**典型耗时（Pixel 6）**：

| 算法 | 1KB 耗时 | 1MB 耗时 |
|---|---|---|
| AES-256-GCM | 50μs | 8ms |
| AES-128 | 30μs | 5ms |
| RSA-2048 加密 | 500μs | 不适用 |
| RSA-2048 签名 | 5ms | 5ms（恒定）|
| ECDSA P-256 | 1ms | 1ms |
| SHA-256 | 5μs | 4ms |

### 4.3 加固代价归因

加固的性能代价：

- **包体积 +5-15MB**：加固 SDK + 加密 DEX。
- **启动 +100-500ms**：解密 DEX / 初始化加固运行时。
- **JIT 失效**：加固代码 JIT 编译可能失效，运行时性能下降。

**归因方法**：

- 启动 trace 中识别加固 SDK 耗时。
- 对比加固前后冷启动时长。

### 4.4 网络安全代价

HTTPS 的代价主要是握手（详见 [`卷四·02 §5.1`](../04.业务专项篇/02.网络性能分析优化.md)）。

**减少代价手段**：

- 长连接 + keepalive。
- TLS 1.3（1-RTT 握手 + 0-RTT 重连）。
- HTTP/2 / HTTP/3。

## 05.求证实验 ⭐

### 5.1 实验一：加密算法选择

**Step 1 — 原始观察**

工程师常用 RSA 加密大数据（错误用法），导致 API 慢。**对比正确做法（AES + RSA 协商）能省多少？**

**Step 2 — 提出疑问**

> **不同加密方案对 1MB 数据的总耗时差异多大？**

**Step 3 — 设计实验**

| 方案 | 描述 |
|---|---|
| A | 直接 RSA-2048 加密 1MB（错误，分块）|
| B | RSA-2048 加密 AES key（32B），AES 加密 1MB |
| C | 全 AES（密钥已经协商好）|

**Step 4 — 实测数据**

| 方案 | 总耗时 |
|---|---|
| A 全 RSA | 不可用（RSA 不支持大数据，需分块且慢到不可接受 ~5s）|
| B RSA + AES | 8.5 ms（RSA 0.5 + AES 8）|
| C 纯 AES | 8 ms |

**Step 5 — 提炼结论**

> **大数据必须用 AES，密钥用 RSA / ECDH 协商。  
> 一次会话内多次加密用同一 AES key（已协商）。**

工程意义：

- 千万不要用 RSA 加密业务数据。
- 关键场景用混合方案（RSA 协商 + AES 传输）。
- 长会话用一次性协商的 AES key。

**Step 6 — 边界**

- 国密 SM2（非对称）和 SM4（对称）规律相同。
- 量子加密目前性能差，但未来必趋势。

---

### 5.2 实验二：加固方案对比

**Step 1 — 原始观察**

Android 加固服务很多家（360 / 乐固 / 几维 等），**对启动性能影响差异多大？**

**Step 2 — 设计实验**

某 App 同样代码用 3 家加固对比：

| 厂商 | 加固方式 | 包体积增加 | 启动时长 +/- |
|---|---|---|---|
| A 厂 | DEX 加密 + Java 反射 | +12 MB | +180ms |
| B 厂 | Native 加固 + DEX 抽取 | +6 MB | +90ms |
| C 厂 | VMP 虚拟机保护 | +20 MB | +400ms |

**Step 3 — 提炼结论**

> **加固方案差异巨大：包体积可差 3 倍、启动时长可差 4 倍。  
> 选型必须实测，不能只看防护强度宣传。**

工程意义：

- 加固选型必须做完整 benchmark。
- 防护强度 + 性能代价同时考虑。
- 不要盲目追求最强防护。

**Step 4 — 边界**

- 不同业务（金融 / 游戏 / 工具）需要的防护级别不同。
- 加固后必须充分测试兼容性（一些设备可能崩溃）。

---

### 5.3 实验三：HTTPS 长连接

**Step 1 — 原始观察**

HTTPS 公认"慢"，但配合长连接到底慢多少？

**Step 2 — 设计实验**

测试同一接口：

| 配置 | 描述 |
|---|---|
| A | HTTP / 短连接 |
| B | HTTPS / 短连接 |
| C | HTTPS / 长连接（keepalive）|

**Step 3 — 实测数据**

| 配置 | 第一次 | 后续平均 |
|---|---|---|
| A HTTP 短连 | 50ms | 50ms（每次新建）|
| B HTTPS 短连 | 220ms | 220ms |
| C HTTPS 长连 | 220ms（首次） | 38ms |

**Step 4 — 提炼结论**

> **HTTPS 长连接后续请求几乎和 HTTP 一样快（< 10ms 差异）。  
> "HTTPS 慢"是没用长连接的误会。**

工程意义：

- 必用 HTTPS（详见 [`卷四·02 §5.1`](../04.业务专项篇/02.网络性能分析优化.md)）。
- 必用长连接（OkHttp / URLSession 默认开）。
- TLS 1.3 + HTTP/2 进一步优化首次。

---

### 5.4 三大实验启示

```
   加密算法选择   → AES + RSA 协商 vs 单 RSA 差几个量级 ─┐
                                                          │
   加固方案对比   → 不同厂商启动差 4×                    ├─▶ 安全 = 选对方案 + 配合优化 + 实测代价
                                                          │
   HTTPS 长连接   → 后续请求几乎无开销                   ─┘
```

**统一启示**：

- **算法 / 方案选错代价巨大**：必须按业务匹配。
- **数据驱动**：每个方案上线前必须实测。
- **安全和性能不矛盾**：选对方案能同时达成。

## 06.优化策略

### 6.1 通用治理矩阵

| 维度 | 治理方向 | 通用手段 |
|---|---|---|
| 传输 | 加密 | HTTPS 全启用 + TLS 1.3 |
| 传输 | 完整性 | API 签名 / 时间戳防重放 |
| 存储 | 加密 | AES + 安全密钥库 |
| 存储 | 隔离 | Sandbox / Keychain / Keystore |
| 代码 | 混淆 | R8 / Terser |
| 代码 | 加固 | 视风险选服务 |
| 运行时 | 校验 | 签名 / 完整性 |
| 运行时 | 检测 | Root / 越狱 / Hook |
| 性能 | 算法选对 | AES 大数据 + RSA 协商 |
| 性能 | 长连接 | 减少握手次数 |

### 6.2 平台特化策略

**Android 特化**：

- 用 EncryptedSharedPreferences / AndroidKeyStore（系统级密钥保护）。
- HTTPS 用 NetworkSecurityConfig 严格配置。
- 加固选型实测启动开销 + 防护强度。
- Root 检测用 RootBeer + 自定义。
- 关键 API 双向认证（mTLS）。

**iOS 特化**：

- 用 Keychain 存储敏感数据（系统级保护）。
- ATS 强制 HTTPS（默认开）。
- App Attest（iOS 14+）做 device 完整性校验。
- 越狱检测：libfishhook / 自实现。
- 不需要"加固"（系统签名足够）。

**Web 特化**：

- HTTPS 全站 + HSTS。
- CSP 防 XSS。
- SRI（Subresource Integrity）防 CDN 被改。
- 敏感操作用 SameSite Cookie + CSRF Token。
- WebAssembly 替代关键算法（部分混淆作用）。

**嵌入式特化**：

- 安全启动（Secure Boot）。
- 硬件密钥库（HSM / TPM）。
- OTA 包必须签名校验。

### 6.3 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 |
|---|---|---|---|---|
| 极高 | HTTPS 全启用 + 长连接 | 安全基线 + 几乎无性能代价 | 1 周 | 低 |
| 极高 | 敏感数据 AES + 系统密钥库 | 防数据泄露 | 1-2 周 | 低 |
| 高 | API 签名防重放 | 防业务风险 | 1 周 | 低 |
| 中 | Android 加固（金融 / 游戏）| 防破解 | 实测 + 接入 | 中（兼容性）|
| 中 | Root / 越狱检测 | 风险用户识别 | 1 周 | 低 |
| 低 | WhiteBox 加密 | 极少收益 | 高 | 高 |
| 极低 | 自实现加密算法 | 几乎无收益 | 极高 | 极高（必出错） |

**避免反向收益**：

- 用错算法（RSA 加密大数据）。
- 过度加固（启动慢用户流失）。
- 自己设计协议（必有漏洞）。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某金融应用希望"全面升级安全"但担心性能变差。

**度量与归因**：

- HTTPS 已经全启用，但部分老接口未用长连接。
- 本地数据存 SharedPreferences 明文。
- API 没有签名 / 时间戳。

**假设与求证**：

提出**统一假设**："必做基线 + 关键场景加强"。

**修复**：

- 全平台启用 HTTPS 长连接。
- 敏感数据迁移到 EncryptedSP / Keychain。
- API 全部加签名 + 时间戳。

**验证**：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 安全 audit 通过率 | 60% | 95% |
| API 平均响应 | 280ms | 270ms（HTTPS 长连接基本无代价）|
| 启动时长 | 1.5s | 1.5s（无变化）|

**统一启示**：**做对方案，安全和性能不矛盾**。

### 7.2 平台特异案例

**背景**：Android 应用接入加固后冷启动慢 400ms，用户流失。

**现象**：加固前 1.2s，加固后 1.6s。

**度量与归因**：

加固方案：VMP（虚拟机保护，最强防护但代价大）。

**假设与求证**：

**假设**：业务不需要 VMP 级别防护，DEX 加密 + Native 加固已经足够。

**实验**：换轻量加固方案，启动恢复到 1.3s（仅 +100ms 代价）。

**修复**：换轻量方案 + 内部代码混淆补强。

**验证**：启动时长达标 + 防护强度仍可接受。

**边界**：金融 / 游戏等高安全需求保留 VMP。

## 08.防劣化与长效治理

### 8.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
[Lint]       [安全 audit]    [监控 + 告警]
```

### 8.2 编码期 Lint

- HTTP（非 HTTPS）API 调用 → 错误。
- 用 RSA 加密大数据 → 错误。
- 用 MD5 / SHA-1 做安全哈希 → 警告。
- 敏感数据存 SharedPreferences 明文 → 警告。
- 密钥硬编码在代码里 → 错误。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 静态扫描（敏感字符串 / 弱算法）。
- 加密接口性能基准。
- 加固后包大小 / 启动 baseline。

**线上 SLO**：

- HTTPS 失败率 < 0.1%。
- 加密耗时 P99 < 阈值。
- 安全告警率（root / hook 检测）合理范围。

## 10.总结与延伸

### 10.1 五条核心原则

1. **安全是成本对抗**：让攻击成本 > 收益。
2. **必做基线先做满**：HTTPS / AES / 密钥库 / 签名是地板。
3. **算法选对省 90% 性能**：RSA 协商 + AES 传输。
4. **加固方案实测**：不同厂商差异巨大。
5. **链条最弱环决定整体**：不能"部分做"。

### 10.2 五个常见误区

1. **"安全必牺牲性能"**：错（选对方案不冲突）。
2. **"AES 越长越安全越慢"**：AES-128 vs AES-256 性能差很小，安全已经够。
3. **"加固越强越好"**：错（性能代价大，部分攻击用不上）。
4. **"WhiteBox 加密无敌"**：错（仍可破解，性能差）。
5. **"自实现算法更安全"**：错（必有漏洞）。

### 10.3 延伸阅读

- OWASP Mobile Top 10
- *Cryptography Engineering*（Ferguson 等）
- WWDC: *Core Data Security*
- Google: *Android Application Security*
- *Real-World Cryptography*（David Wong）

## 一句话总结

> **安全是性能的隐形成本，但选对方案两者并不矛盾。  
> HTTPS 长连接、AES + RSA 混合、系统密钥库 是无代价的"必做基线"。  
> 加固和重型防护要按业务风险匹配，实测代价。**
