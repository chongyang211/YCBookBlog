## 01.问题域定义

### 1.1 现象与代价

崩溃是稳定性的"显示信号"：

- **应用退出**：用户看到"应用已停止"或被强杀。
- **数据丢失**：未保存数据可能丢失。
- **重启后状态丢失**：用户被迫重新进入流程。
- **隐性崩溃**：应用在用户感知到之前已经异常（如启动崩溃）。

**业务代价**：

- 头部应用崩溃率每降 0.1% 留存 +0.5%。
- 启动崩溃比运行时崩溃影响更大（用户进不去）。
- 不可见的"静默崩溃"会影响线上数据准确性。

### 1.2 度量准则

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 崩溃率（cph）| crash / hour 或 crash / DAU | < 0.1% |
| 启动崩溃率 | 启动失败 / 总启动 | < 0.05% |
| 上报成功率 | 上报成功 / 总崩溃 | > 95% |
| 符号化成功率 | 可还原栈 / 总崩溃 | > 90% |

### 1.3 行业基准与目标

| 平台 | 崩溃率 | 启动崩溃 | 上报成功率 |
|---|---|---|---|
| Android | < 0.1% | < 0.05% | > 95% |
| iOS | < 0.05% | < 0.02% | > 98% |
| Web | < 0.05% | N/A | > 90% |
| 嵌入式 | 0% | 0% | 内部记录 |

### 1.4 反直觉问题清单

带着这些问题阅读：

1. Java 崩溃和 Native 崩溃捕获方式一样吗？
2. iOS 崩溃栈为什么是地址而不是函数名？
3. 崩溃时再上报数据可靠吗？
4. 静默崩溃如何发现？
5. SIGABRT 和 SIGKILL 应用都能捕获吗？
6. ANR 和崩溃是同一类问题吗？
7. 用户主动杀死也算"崩溃"吗？
8. 崩溃时还能写文件 / 发网络吗？

## 02.第一性原理

### 2.1 崩溃本质定义

**一句话定义**：

> **崩溃 = 应用在执行过程中遇到不可恢复的错误，被运行时或操作系统强制终止**。

这句话隐含三个不可商量的物理约束：

**约束一：崩溃是"不可恢复"的状态**

崩溃发生时，进程内某些数据已经处于"不可信"状态（栈被破坏 / 内存被覆盖 / 状态机错乱）。即使能继续执行，结果也不可信。**OS / 运行时主动杀死进程是为了避免错误扩散**。

**约束二：崩溃捕获的"时间窗"极短**

崩溃信号 / 异常发生到进程被强杀通常只有几十 ms 到几秒。在这段时间里要做：

- 记录崩溃信息（stack / device / context）
- 持久化到本地（不能依赖网络）
- 准备下次启动时上报

**操作必须最简单 / 最可靠**：不能依赖复杂的库，不能新建线程，不能分配大块内存。

**约束三：崩溃种类决定捕获方式**

不同语言 / 平台的崩溃机制不同（Java 异常 vs C 信号 vs JS 错误），需要分别捕获。

### 2.2 三类崩溃模型

```
   ┌────────────────────────────────────────────────┐
   │ A. 异常型崩溃（语言级）                          │
   │    Java RuntimeException / Swift error / JS Error│
   │    捕获：UncaughtExceptionHandler                │
   ├────────────────────────────────────────────────┤
   │ B. 信号型崩溃（系统级）                          │
   │    SIGSEGV / SIGABRT / SIGBUS / SIGFPE          │
   │    捕获：sigaction / signal handler             │
   ├────────────────────────────────────────────────┤
   │ C. 系统强杀（OOM Killer / Watchdog / Kill）      │
   │    无法应用层捕获                                │
   │    捕获：启动时检查"上次未正常退出"               │
   └────────────────────────────────────────────────┘
```

**关键认知**：

- A 类容易捕获（运行时提供 hook）。
- B 类需要 Native 层信号处理（POSIX signal）。
- C 类应用代码无法响应（已被 SIGKILL），只能下次启动时推断。

### 2.3 跨平台同构原理

所有平台的崩溃捕获本质都是"在异常发生时拦截 + 记录 + 持久化"：

```
   通用崩溃捕获模型：

      [应用代码] ──[抛异常]──▶ [运行时/OS]
                                  │
                                  ▼
                           [捕获 hook]
                                  │
                                  ▼
                           [收集现场]
                                  │
                                  ▼
                           [本地持久化]
                                  │
                          下次启动时上报
```

每个平台都必须有：

| 抽象组件 | 解决什么问题 |
|---|---|
| 异常 hook | 捕获语言级异常 |
| 信号 hook | 捕获系统级信号 |
| 现场采集 | 抓 stack / device / context |
| 本地持久化 | 崩溃后写本地（网络可能不可用）|
| 上报机制 | 下次启动时安全上传 |

**跨平台术语对照**

| 通用术语 | Android | iOS | Web | C/C++ |
|---|---|---|---|---|
| 异常 hook | `Thread.setDefaultUncaughtExceptionHandler` | `NSSetUncaughtExceptionHandler` | `window.onerror` + `unhandledrejection` | `terminate_handler` |
| 信号 hook | NDK `sigaction` | `sigaction` | N/A | `sigaction` |
| 现场采集 | stack + device + 自定义 | 同 + Mach exception | error.stack + UA | backtrace |
| 持久化 | 本地文件 | 本地文件 | localStorage / IndexedDB | 本地文件 |
| 上报 | 下次启动 | 下次启动 | 即时 / 延迟 | 视设计 |

**同构带来的工程价值**

1. **方案选型有锚点**：A/B/C 三类各自的 hook 方式跨端通用。
2. **现场字段可对齐**：stack / device / 用户操作链 / 内存 / 网络 是通用字段。
3. **上报策略可复用**：本地优先 + 下次启动上传。

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 异常型 | Java / Kotlin Exception | Swift error / NSException | JS Error / Promise rejection | C++ exception |
| 信号型 | NDK 信号 | Mach exception + signal | N/A（沙箱）| signal |
| 系统强杀 | LMK / Force Stop | jetsam / watchdog | Tab Killer | 看门狗 |
| Stack 符号化 | mapping.txt（ProGuard）+ NDK symbols | dSYM | sourcemap | DWARF |
| 多线程崩溃 | 单 dump 含所有线程 | 同 | 单线程为主 | 视实现 |

> 后续遇到平台特化点回引本节。

## 03.度量与采集

### 3.1 三类捕获方案的本质

所有平台的崩溃捕获方案，本质上只有 3 类：

```
   ① 异常 hook（语言运行时层）
   ② 信号 hook（系统 POSIX 层）
   ③ 系统级历史（启动时回查上次）
```

---

**① 异常 hook**

**核心原理（一句话）**：在语言运行时提供的全局异常入口注册回调，捕获未处理的异常。

**工作机理**：

```kotlin
// Android Java/Kotlin
Thread.setDefaultUncaughtExceptionHandler { thread, throwable ->
    // 1. 立即收集现场（不依赖外部库）
    val report = collectMinimalReport(thread, throwable)
    // 2. 写本地（避免网络）
    saveLocally(report)
    // 3. 调原默认 handler 让进程正常死
    defaultHandler.uncaughtException(thread, throwable)
}
```

```objc
// iOS
NSSetUncaughtExceptionHandler(^(NSException *exception) {
    NSDictionary *report = collectReport(exception);
    saveLocally(report);
});
```

```js
// Web
window.addEventListener('error', (event) => {
    saveLocally({ message: event.message, stack: event.error?.stack });
});
window.addEventListener('unhandledrejection', (event) => {
    saveLocally({ reason: event.reason });
});
```

**物理本质**：拦截"语言运行时强制终止"前的最后机会。

**适用边界**：所有应用必备的基础捕获。

---

**② 信号 hook**

**核心原理（一句话）**：在 Native 层注册 POSIX signal handler，捕获 C / C++ 层崩溃。

**工作机理**：

```c
#include <signal.h>

void crash_handler(int signo, siginfo_t *info, void *ctx) {
    // 注意：在信号处理上下文，能用的函数有限
    // 不能 malloc / printf / 调 Java 等
    write(fd, simple_info, len);  // 仅用 async-signal-safe 函数
}

void init_signal_hook() {
    struct sigaction sa;
    sa.sa_sigaction = crash_handler;
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGSEGV, &sa, NULL);
    sigaction(SIGABRT, &sa, NULL);
    sigaction(SIGBUS, &sa, NULL);
    // ...
}
```

**物理本质**：在 OS 信号机制层拦截 Native 层崩溃。

**为什么这样有效**：Native crash 不会经过 Java VM 的 UncaughtExceptionHandler，必须在系统层捕获。

**局限根源**：

- 信号处理上下文严格受限（async-signal-safe 函数列表）。
- Stack unwind 跨语言（C → Java → JNI）很复杂。
- 部分信号（SIGKILL）不可捕获。

**适用边界**：所有有 Native 代码的应用必备。

---

**③ 系统级历史**

**核心原理（一句话）**：进程被 OS 强杀（OOM / Watchdog / Force Stop）时应用无法响应，只能下次启动时通过系统 API 回查。

**工作机理**：

| 平台 | API |
|---|---|
| Android 11+ | `ActivityManager.getHistoricalProcessExitReasons` |
| iOS | MetricKit `MXMetricPayload.crashDiagnostic` |
| Web | N/A（用户关闭即丢） |

**物理本质**：应用代码不在场，OS 帮你记录。

**适用边界**：补全应用层捕获不到的"静默崩溃"。

---

**三类方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 异常 hook | 语言运行时 | Java/JS 栈 | 极低 | 高 | ✅ | 不覆盖 Native |
| ② 信号 hook | OS 层 | Native 栈 | 极低 | 中（需 NDK）| ✅ | 信号处理受限 |
| ③ 系统历史 | OS API | 进程级 | 极低 | 中（API 受限）| ✅ | 颗粒度粗 |

**方案的"组合定律"**：①+② 必须组合（覆盖所有运行时）+ ③ 补全静默崩溃。

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| Java / Swift 异常 | ✅ | ❌ | ❌ |
| Native crash (SIGSEGV) | ❌ | ✅ | 部分 |
| ANR | ❌ | ❌ | ✅ |
| OOM 被杀 | ❌ | ❌ | ✅ |
| SIGKILL（用户强杀）| ❌ | ❌ | ✅ |
| 静默退出 | ❌ | ❌ | ✅ |

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web | C/C++ |
|---|---|---|---|---|
| 异常 | Bugly / Crashlytics / 自实现 | Crashlytics / Sentry | Sentry / window.onerror | terminate_handler |
| 信号 | Bugly NDK / Breakpad | KSCrash / Crashlytics | N/A | google-breakpad / crashpad |
| 系统历史 | `getHistoricalProcessExitReasons` | MetricKit | N/A | dmesg / journal |

### 3.4 数据可信度评估

| 数据 | 可信度 | 偏差来源 |
|---|---|---|
| 异常 stack | 高 | 直接 throwable |
| Native stack | 中 | 符号化失败导致部分缺失 |
| 用户操作链 | 中 | 缓冲区可能丢失最近事件 |
| 系统历史 | 高 | OS 直接记录 |
| 上报到达 | < 100% | 网络失败 / 应用未启动 |

## 04.归因方法

### 4.1 崩溃归因决策树

```
崩溃事件
   │
   ├── 类型 A 异常型 ──▶ 看 stack 顶层
   │                  ├─ NPE → 找 nullable 来源
   │                  ├─ ClassCastException → 类型不一致
   │                  ├─ IndexOutOfBounds → 边界检查
   │                  └─ OOM → 走内存治理（卷二·03）
   │
   ├── 类型 B 信号型 ──▶ 看 signal 类型
   │                  ├─ SIGSEGV → 空指针 / 野指针
   │                  ├─ SIGABRT → assert 失败 / 主动 abort
   │                  ├─ SIGBUS → 内存对齐 / mmap 失败
   │                  └─ SIGFPE → 除零 / 浮点异常
   │
   └── 类型 C 系统强杀 ──▶ 看 ProcessExitReason / MetricKit
                      ├─ LMK → 内存压力（详见卷二·03）
                      ├─ ANR → ANR 治理（详见卷三·04）
                      └─ Force Stop → 用户主动
```

### 4.2 符号化与还原

**为什么需要符号化**

线上 release 包的 stack 是地址 / 混淆后的名字，必须用 mapping 文件还原才能定位代码。

```
   原始：  com.app.a.b.c() at 0x12345
   符号化后：UserListActivity.onCreate() at MainActivity.kt:42
```

**符号化方案**：

| 平台 | Mapping 文件 | 工具 |
|---|---|---|
| Android Java | mapping.txt（ProGuard / R8）| retrace / Bugly 自动 |
| Android Native | symbols / .so 含调试信息 | ndk-stack / addr2line |
| iOS | dSYM | symbolicatecrash / atos / Instruments |
| Web | sourcemap | Source Map Tools / Sentry 自动 |

**关键约定**：

- 每次发版必须保留 mapping / dSYM / sourcemap（按版本号归档）。
- 上报系统按版本自动符号化。

### 4.3 现场快照分析

崩溃时需要的"四件套"：

1. **完整 stack**：所有线程，不只主线程。
2. **设备信息**：型号 / 系统 / RAM / CPU / 屏幕。
3. **应用上下文**：版本 / 当前页面 / 最近 N 条用户操作。
4. **资源快照**：内存 / CPU / 网络状态。

**现场字段示例**：

```
{
  "type": "NullPointerException",
  "thread": "main",
  "stack": [...],
  "all_threads": {...},
  "device": {"model": "Pixel 6", "os": "Android 13", "ram": 8192, "free": 2300},
  "app": {"version": "3.5.1", "build": 12345},
  "context": {
    "current_activity": "UserListActivity",
    "last_actions": ["click_user", "scroll_list", ...]
  },
  "memory": {"java_heap": 64MB, "native": 32MB, "total_pss": 200MB}
}
```

### 4.4 长尾崩溃归因

少数用户的崩溃往往是：

- 极端机型（如 SamsungA01 这类低端机）
- 极端系统版本（Android 5 / iOS 12 等老版本）
- 极端用户行为（罕见操作组合）
- 设备状态异常（root / 越狱 / 第三方 ROM）

**长尾治理思路**：

- 设定**支持范围**（minSdk / 最低 RAM / 不支持 root）。
- 范围外提示用户升级 / 友好降级。
- 不要追求"100% 用户都能用"。

## 05.求证实验 ⭐

### 5.1 实验一：捕获完整性

**Step 1 — 原始观察**

工程师都接 Crashlytics 等，但**它们能捕获多少崩溃？还有什么漏的？**

**Step 2 — 提出疑问**

> **常见崩溃监控库（仅 hook 异常）相比"全方案"（异常 + 信号 + 历史）覆盖率差异多少？**

**Step 3 — 设计实验**

构造各类崩溃测试用例，测量各方案捕获率：

| 用例 | 仅异常 hook | 异常 + 信号 hook | 全方案 |
|---|---|---|---|
| Java NPE | ✅ | ✅ | ✅ |
| Java OOM | ✅ | ✅ | ✅ |
| Native SIGSEGV | ❌ | ✅ | ✅ |
| Native SIGABRT | ❌ | ✅ | ✅ |
| ANR | ❌ | ❌ | ✅（系统历史）|
| LMK 杀进程 | ❌ | ❌ | ✅ |
| 用户 Force Stop | ❌ | ❌ | ✅ |

**Step 4 — 实测数据**

某 App 实际数据：

| 方案 | 捕获率 |
|---|---|
| 仅异常 hook | 65% |
| 异常 + 信号 hook | 88% |
| 全方案（+ 系统历史）| 99% |

**Step 5 — 提炼结论**

> **仅异常 hook 漏掉 35% 崩溃；必须三方案组合才能达到 99% 捕获率。**

工程意义：

- 必须接 Native 信号 hook（10-20% 漏报集中在这）。
- 必须用系统历史补全（ANR / OOM 被杀）。
- "看不到的崩溃"比看到的更危险。

**Step 6 — 边界**

- 系统历史 API 需要 Android 11+。
- iOS MetricKit 数据延迟 24 小时。
- Web 没有"系统历史"概念。

---

### 5.2 实验二：上报成功率

**Step 1 — 原始观察**

崩溃发生时网络往往不可用（启动期 / 弱网），**多少崩溃能成功上报？**

**Step 2 — 提出疑问**

> **不同上报策略下，崩溃数据到达服务端的比例是多少？**

**Step 3 — 设计实验**

| 策略 | 描述 |
|---|---|
| A 同步上报 | 崩溃时立即网络上报 |
| B 仅本地 + 下次启动上报 | 本地写文件，下次启动检查 |
| C 本地 + 启动上报 + 后台上报 | B + 应用进入后台时也尝试 |

**Step 4 — 实测数据**

| 策略 | 上报成功率 |
|---|---|
| A 同步上报 | 60-70%（崩溃时网络不可靠）|
| B 启动上报 | 88-92% |
| C B + 后台上报 | 95-98% |

**Step 5 — 提炼结论**

> **崩溃时同步上报成功率仅 60-70%。  
> "本地优先 + 多次重试"能让到达率达到 95%+。**

工程意义：

- 不要在崩溃 handler 里直接调网络。
- 写本地文件 → 下次启动检查 → 上报。
- 应用进入后台时也尝试一次（兜底）。

**Step 6 — 边界**

- iOS 启动 watchdog 直接杀，本地写文件可能也来不及。
- Web 用户关闭 Tab 即丢，依赖 sendBeacon / unloadEvent。
- 嵌入式设备无法上报到外部，必须本地存储足够久。

---

### 5.3 实验三：现场抓取价值

**Step 1 — 原始观察**

只抓 stack 还是抓完整现场？**完整现场对修复效率提升多少？**

**Step 2 — 提出疑问**

> **完整现场（stack + device + 用户操作链 + 内存快照）相比仅 stack，定位效率提升多少？**

**Step 3 — 设计实验**

某团队对比两种数据格式：

- A 仅 stack：可还原"哪行代码崩"。
- B 完整现场：A + device + 用户行为 + 资源状态。

**Step 4 — 实测数据**

随机选 100 个崩溃，对比修复时间：

| 数据完整度 | 平均定位耗时 | 一次修复成功率 |
|---|---|---|
| A 仅 stack | 3.5 小时 | 55% |
| B 完整现场 | 0.8 小时 | 85% |

**Step 5 — 提炼结论**

> **完整现场让定位耗时 -75%，一次修复成功率 +30%。  
> 是少有的"采集成本极低，效果极高"的工作。**

工程意义：

- 必须采集设备 / 系统 / 应用版本。
- 用户操作链（最近 30 条）极有价值。
- 内存 / 网络快照能识别环境因素。

**Step 6 — 边界**

- 现场数据量增加 5-10×（仍可控）。
- 隐私敏感数据要脱敏。

---

### 5.4 三大实验启示

```
   捕获完整性   → 三方案组合覆盖 99%      ─┐
                                            │
   上报成功率   → 本地优先 + 启动重试 95%+ ├─▶ 崩溃 = 多手段 + 高可靠 + 全现场
                                            │
   现场抓取     → 完整现场让定位 -75%      ─┘
```

**统一启示**：

- **"看不到的崩溃"是最大风险**，必须三方案组合。
- **崩溃时一切都不可信**，本地优先 + 下次上报。
- **现场数据决定修复速度**，性价比极高。

## 06.优化策略

### 6.1 通用治理矩阵

| 维度 | 治理方向 | 通用手段 |
|---|---|---|
| 捕获 | 三方案组合 | 异常 hook + 信号 hook + 系统历史 |
| 现场 | 完整字段 | stack + device + 用户操作 + 内存 |
| 上报 | 高可靠 | 本地优先 + 多次重试 |
| 符号化 | 自动化 | 每次发版保留 mapping / dSYM |
| 治理 | Top 5 优先 | 80/20 法则 |
| 防退化 | CI 卡口 | 自动化测试 + 灰度对比 |

### 6.2 平台特化策略

**Android 特化**：

- Bugly / Firebase Crashlytics（生态主流）。
- NDK Native crash 接 Bugly NDK 或 google-breakpad。
- Android 11+ 用 `getHistoricalProcessExitReasons` 补全 LMK / ANR。
- 注意：UncaughtExceptionHandler 链式调用要保留原 handler。

**iOS 特化**：

- Crashlytics + KSCrash（更强大）。
- 启动 watchdog 必须用 MetricKit `MXLaunchHangDiagnostic`。
- dSYM 必须上传所有发版的（包括 hotfix）。
- App Store 审核时崩溃会被立即拒绝。

**Web 特化**：

- Sentry / Bugsnag。
- Source Map 必须自动化处理。
- 用户关闭 Tab 时 `navigator.sendBeacon` 上报。
- Service Worker 失败也要上报。

**嵌入式特化**：

- 内核 panic 写入 NVRAM。
- 看门狗 dump 进系统日志。
- 通过串口 / OTA 上传分析。

### 6.3 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 |
|---|---|---|---|---|
| 极高 | 异常 + 信号 + 系统历史三方案 | 捕获率 99% | 1-2 周 | 低 |
| 极高 | 完整现场抓取 | 修复效率 +75% | 1 周 | 低 |
| 极高 | 自动符号化 | 可读栈数据 | 1 周（基建）| 低 |
| 高 | 本地优先 + 启动上报 | 上报率 95%+ | 几天 | 低 |
| 高 | Top 5 集中治理 | 崩溃率快速下降 | 持续 | 中 |
| 中 | 内存快照 + 用户行为 | 长尾归因能力 | 1 周 | 低 |
| 低 | 自实现 Crash SDK | 几乎无收益 | 极高 | 极高 |

**避免反向收益**：

- 现场字段过多：上报体积爆炸。
- 同步网络上报：成功率反而低。
- 自实现 SDK：成熟方案已经覆盖 99% 场景。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某应用 Android / iOS / Web 的崩溃监控都用了主流 SDK，但仍有 15-20% 崩溃"看不到"（用户报但日志无）。

**度量与归因**：

通过日活下降发现"隐性崩溃"问题。深度调查发现：

- Android：Native 信号 hook 未启用，Native crash 全漏。
- iOS：启动 hang（watchdog 杀）未监控。
- Web：unhandledrejection 未监听。

**假设与求证**：

提出**统一假设**："补齐每个平台的盲区"。

**修复**：

- Android：启用 Bugly NDK + ProcessExitReason。
- iOS：接入 MetricKit + KSCrash。
- Web：补 unhandledrejection + sendBeacon 上报。

**验证**：

| 平台 | 优化前可见崩溃率 | 优化后可见崩溃率 | 实际崩溃率（不变）|
|---|---|---|---|
| Android | 0.08% | 0.15% | 0.15% |
| iOS | 0.04% | 0.09% | 0.09% |
| Web | 0.05% | 0.07% | 0.07% |

可见崩溃率上涨意味着捕获更全面（不是问题恶化）。

**统一启示**：跨端崩溃监控通用法则 = **三方案组合覆盖盲区**。

### 7.2 平台特异案例

**背景**：iOS 应用启动期偶发崩溃，但 Crashlytics 完全收不到。

**现象**：用户报告"打开就闪退"，但崩溃数据为零。

**度量与归因**：

- 启动 watchdog 5 秒内强杀 → SIGKILL → 应用代码完全不响应。
- Crashlytics 也来不及上报。

**假设与求证**：

**假设**：用 MetricKit 在下次启动时拿启动 hang 数据。

**实验**：接入 MetricKit `MXLaunchHangDiagnostic`，下次启动后 24 小时内收到详细 hang stack。

**修复**：

- 接入 MetricKit。
- 监控 hang stack，识别启动期同步重任务。
- 用分级初始化（详见 [`卷四·01`](../04.业务篇/01.App启动优化.md)）异步化。

**验证**：启动 hang 率从 0.08% 降到 0.02%。

**边界**：MetricKit 数据延迟 24 小时，不能实时响应，只能事后分析。

## 08.防劣化与长效治理

### 8.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
```

### 8.2 编码期 Lint

- 关键路径未做空值检查 → 错误。
- 使用过时危险 API → 警告。
- 全局未注册崩溃 handler → 错误。
- 未启用混淆但未配置 mapping 上传 → 警告。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 每次发版必须有 mapping / dSYM 归档。
- 自动化测试覆盖核心流程。
- 灰度阶段崩溃率 ≤ 上一版本。

**线上 SLO**：

- 总崩溃率 < 0.1%。
- Top 5 崩溃总占比 ≤ 50%（避免单点垄断）。
- 上报到达率 > 95%。
- 符号化成功率 > 90%。

## 10.总结与延伸

### 10.1 五条核心原则

1. **三方案组合**：异常 + 信号 + 系统历史，缺一不可。
2. **现场必须完整**：stack + device + context + 资源。
3. **本地优先**：上报失败比无数据好。
4. **符号化自动化**：每次发版保留 mapping。
5. **80/20 治理**：Top 5 优先。

### 10.2 五个常见误区

1. **"接了 Crashlytics 就够了"**：错（Native + 系统强杀漏报）。
2. **"崩溃时同步上报"**：错（成功率低）。
3. **"只采 stack 够用"**：错（定位效率差 4×）。
4. **"忽略 ANR 不算崩溃"**：错（用户感知同样差）。
5. **"自实现 SDK 更可靠"**：错（成熟方案久经考验）。

- Google: *Stability and crashes*（Android Vitals）

- Sentry / Bugsnag SDK 源码
