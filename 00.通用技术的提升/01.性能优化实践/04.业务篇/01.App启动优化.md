## 01.问题域定义

### 1.1 现象与代价

启动慢是用户对一款应用的"第一印象"，且印象一旦形成极难翻转：

- **首次冷启动慢**：用户感知"是不是没装好？"
- **每次启动黑屏 / 白屏**：用户怀疑应用故障。
- **可见但点不动（TTID 已到但 TTFD 未到）**：用户操作无响应，主观体验比慢更差。
- **启动后不稳定（卡顿、ANR、闪退）**：往往与启动期的"过度异步并发"或"线程争用"相关。

**业务代价（行业实测数据）**：

- Google Play Console 数据：冷启动 P50 > 5s 的应用，次日留存比 < 2s 的低 **15–20%**。
- 头部 App 数据：每减少 1 秒冷启动时长，次日留存 +1–3%、首屏转化率 +2–5%。
- iOS 系统在冷启动 > 20s 时直接 watchdog 杀死进程，是硬约束。
- Web：Google Web Vitals 把 LCP（Largest Contentful Paint，对应启动可见）> 4s 标记为 *Poor*，影响 SEO。
- 嵌入式车机：启动 > 30s 在某些国家会触发安规警告。

### 1.2 度量准则

按 [`卷零·02 §3 USE/RED/APDEX`](../00.公共方法论/02.跨平台性能模型与指标体系.md) 的统一指标体系，启动属于"一次性请求"类，主要用 RED + APDEX：

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| TTID（Time To Initial Display） | 首帧可见时间 | 冷启 < 2s / 热启 < 0.5s |
| TTFD（Time To Full Display） | 首屏完整可交互 | 冷启 < 3s / 热启 < 1s |
| 启动失败率（Errors） | 启动崩溃 / 超时占比 | < 0.1% |
| 启动期卡顿率 | 启动期间帧时长 > 16.67ms 的比例 | < 5% |

**用户感知（APDEX）**：

- *Satisfied*：TTFD < T_target（如 1.5s）
- *Tolerating*：T_target ≤ TTFD < 4 × T_target
- *Frustrated*：TTFD ≥ 4 × T_target

**关键约定**：

- **TTID ≠ TTFD**：用户看到首帧但内容未加载完，主观仍是"卡"。优化必须并重，**TTFD 才是用户感知的"启动完成"**。
- 必须使用 P50 + P99 双轨度量。P99 代表"长尾用户体验"，往往揭示低端机 / 弱网下的真实痛点。

### 1.3 行业基准与目标

| 平台 | TTID 良好 | TTID 合格 | TTFD 良好 | TTFD 合格 |
|---|---|---|---|---|
| Android（中端机）| < 1.5s | < 2.5s | < 2.5s | < 4s |
| iOS | < 1.0s | < 2.0s | < 2.0s | < 3s |
| Web（4G）| LCP < 2.5s | LCP < 4s | TTI < 3.8s | TTI < 7.3s |
| 嵌入式 HMI | < 5s | < 10s | < 8s | < 15s |

### 1.4 反直觉问题清单

带着这些问题阅读，文中将一一回应：

1. 减少启动任务数一定能让启动更快吗？
2. 把所有任务都改异步，启动是否就能快到极致？
3. CPU 利用率不饱和但启动慢，是哪里的问题？
4. 多线程并发启动，开多少线程最快？
5. MultiDex 一定会让启动变慢吗？慢多少？
6. SharedPreferences / NSUserDefaults 在启动期为什么这么慢？
7. 异步化任务之后总耗时是不是必然减少？
8. 8 核 CPU 启动时为什么有时只用了 2 核？

## 02.第一性原理

> 本节回答三个根本问题：**①启动的物理本质是什么？②为什么所有平台的启动都是"关键路径问题"？③同构之下平台差异在哪？**

### 2.1 启动本质定义

**一句话定义**：

> **启动 = 把"应用从无到有"过程中的所有必要工作，按依赖关系串行 / 并行地执行，直到用户能看到并交互**。

这句话隐含三个不可商量的物理约束：

**约束一：启动是有"必要工作集"的**

启动不是单一任务，而是一个**任务集 T = {t₁, t₂, ..., tₙ}**，每个任务做一件事（如加载类、初始化 SDK、读配置、建立网络连接、渲染首帧）。

任务集分两类：
- **必要任务（critical）**：直接产出"用户可见可交互"的状态。
- **可选任务（deferrable）**：当下不需要，但传统实现中放在启动期（如打点埋点、广告拉取、后台同步）。

启动优化的第一原则是：**严格区分必要与可选，把可选的全部移出启动期**。

**约束二：任务之间存在依赖图**

任务集不是并行池，而是**有向无环图（DAG）**。例如：

```
   t1 (读本地配置) ──┐
                     ├──▶ t4 (初始化 SDK)
   t2 (初始化日志) ──┘
                     ├──▶ t5 (建立网络) ──▶ t7 (拉取首屏数据) ──▶ t8 (渲染首屏)
   t3 (准备主线程) ──┘
                     └──▶ t6 (初始化 UI 框架) ──┘
```

依赖图决定了"哪些任务必须串行""哪些可以并行"。

**约束三：启动有"开始"和"结束"两个明确边界**

- 开始：用户点击图标 / 系统拉起应用。
- 结束：用户能看到首屏并能交互（TTFD）。

这两个边界是物理可观测的（屏幕变化 + 输入响应），所以启动是个"有头有尾的 epoch"问题，可以精确度量。

### 2.2 关键路径模型

**为什么"关键路径"是启动优化的核心抽象**

DAG 的总耗时不是所有任务耗时之和，而是**最长路径的耗时**（关键路径，Critical Path）。这是 PERT/CPM 项目管理理论的核心，同样适用于启动：

```
   t1 (10ms) ──┐
                ├─▶ t4 (50ms) ──▶ t8 (100ms)  关键路径：t2 → t4 → t8 = 70ms
   t2 (20ms) ──┘
                ├─▶ t5 (30ms) ──▶ t7 (40ms)
   t3 (5ms)  ──┘                              非关键路径：t3 → t5 → t7 = 75ms 实际并行
```

**关键路径的四条法则**（启动优化的"金科玉律"）：

1. **法则一**：总启动时长 = 关键路径耗时（不是任务总和）。
2. **法则二**：缩短非关键路径上的任务**对总耗时无收益**（除非它升级成新关键路径）。
3. **法则三**：缩短关键路径任务，最多缩短到"次关键路径"长度（之后次关键路径成为新瓶颈）。
4. **法则四**：把任务从关键路径移除（异步 / 延迟）的收益与缩短它一样有效，但成本通常更低。

这就是为什么"看似减少了 20 个启动任务，启动时长只少了 100ms"—— 因为只有关键路径上的任务才贡献。

**Amdahl 定律的启动版本**

设启动可异步化的部分占比为 P（0 ≤ P ≤ 1），无法异步化的串行部分占比为 1 − P，并行加速比为 N，则：

```
   启动加速比 = 1 / [(1 − P) + P/N]

   即使 P = 0.8，N = ∞：加速比上限 = 1 / 0.2 = 5×
```

**这就是反直觉问题 ② 的答案**：即使所有可异步化任务都开无限线程并行，启动加速也存在硬上限。要突破这个上限，必须**减少串行部分**（缩短或删除关键路径任务），而不是单纯堆并发。

**关键路径上的三类典型问题**

把"关键路径阻塞"映射到具体根因，可以分成三类：

```
  关键路径耗时 = 关键任务自身耗时 + 任务间等待 + 资源竞争

  ┌──────────────────────────────────────┐
  │ A. 任务自身慢                          │
  │    特征：单个任务 CPU 高 / IO 长       │
  │    根因：算法差、磁盘 IO、网络等        │
  ├──────────────────────────────────────┤
  │ B. 任务依赖链长                        │
  │    特征：单任务都不慢，但串成长链路    │
  │    根因：依赖图设计不合理              │
  ├──────────────────────────────────────┤
  │ C. 资源竞争 / 调度等待                 │
  │    特征：CPU 不饱和但任务慢            │
  │    根因：锁、Binder、磁盘竞争、线程不够 │
  └──────────────────────────────────────┘
```

### 2.3 跨平台同构原理

**为什么所有平台的启动原理都同构**

不同平台的启动看起来差异巨大（Android Zygote fork → Application → Activity；iOS dyld → main → AppDelegate；Web HTML 解析 → JS 执行 → 首次渲染；嵌入式 init → 服务初始化 → UI 主循环），但**抽象成"任务依赖图 + 关键路径"后完全同构**：

```
  通用启动模型：

   [系统级初始化] ──▶ [运行时启动] ──▶ [应用初始化] ──▶ [首屏渲染] ──▶ 可交互
        │                  │                │                │
        进程创建            VM/解释器           业务对象            用户可见
```

每个平台都必须有：

| 抽象阶段 | 解决什么问题 |
|---|---|
| 进程 / 上下文创建 | OS 内核为应用分配资源（地址空间、文件描述符、线程） |
| 运行时启动 | VM / 解释器 / 浏览器引擎初始化（GC、JIT、解析器） |
| 应用初始化 | Application 创建、SDK 初始化、配置加载 |
| 首页准备 | 数据加载、UI 框架初始化、首帧渲染 |

**正因为它们都长这个样子，启动的物理本质也是同一个**：

> **启动慢不是平台的特性，是"任务集 + 依赖图 + 串行预算"这个组合的必然产物。**

**跨平台启动阶段对照**

| 抽象阶段 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 进程创建 | Zygote fork | exec / dyld 加载 | 浏览器进程创建 Tab | OS 创建任务 |
| 运行时启动 | ART 加载 dex | dyld 链接 + libObjc 启动 | V8 / JS 引擎初始化 | RTOS 调度 |
| 应用初始化 | Application.onCreate | UIApplication 初始化 + AppDelegate | DOMContentLoaded | main() / app_init |
| 首页准备 | Activity.onCreate → onResume | UIViewController.viewDidLoad → viewWillAppear | window.load | UI 任务循环 |
| 可交互完成 | Activity 首帧绘制完成 | viewDidAppear + 主 RunLoop 空闲 | TTI / window.onload + INP | UI 主循环就绪 |

**同构带来的工程价值**

理解同构原理后，会获得三个直接收益：

1. **调试方法可迁移**：Trace + 关键路径分析在所有平台都通用，只是 API 不同。
2. **优化策略可复用**：异步化、延迟、缓存、并发是跨平台通用手段。
3. **跨平台框架不会失效**：Flutter / RN / Compose Multiplatform 启动慢的根因仍然是"任务集 + 依赖图"，只是中间层换成了 Dart Isolate / JS Bundle / Compose Snapshot。

### 2.4 平台差异点矩阵

同构之下，各平台的实现差异主要集中在以下维度：

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 进程模型 | Zygote fork（共享 ART） | 每次 fork+exec | 浏览器子进程 | 单进程 / 任务 |
| 运行时 | ART（AOT + JIT） | Native + ObjC RT | V8 / SpiderMonkey | C/C++ 直接执行 |
| 类加载策略 | Multi-DEX + ART 优化 | dylib / framework | JS Bundle 解析 | 静态链接 |
| 首屏可见时机 | 首帧渲染完成 | viewDidAppear | LCP | UI 主循环就绪 |
| 系统级阻塞 | ContentProvider onCreate 串行 | dyld 链接慢 | DOM 解析阻塞 | 设备 init |
| 优化手段 | App Startup / 任务调度 SDK | Static Init 延迟 / dyld3 | Code Splitting / SSR | 优先级 + DMA |

> 后续各章遇到平台特化点时，会回引本节做对照。

## 03.度量与采集

### 3.1 三类采集方案的本质

> 本节是全文最重要的一节之一。市面上几乎所有启动监控框架都是这三类的"组合 + 微调"。

所有平台的启动采集方案，本质上只有 3 类，区别在于**在启动生命周期的哪一段下钩子**：

```
   进程开始 ──▶ 运行时就绪 ──▶ Application 创建 ──▶ Activity 创建 ──▶ 首帧 ──▶ 完整可交互
        │              │               │                  │              │            │
        ▼              ▼               ▼                  ▼              ▼            ▼
                       ① 应用埋点（手动打点 / 自动插桩）
                                                                          ② 系统级 API
                                              ③ 端到端外部测量（高速摄像 + LED 触发）
```

下面对每一类做完整原理拆解。

---

**① 应用埋点（手动打点 / 自动插桩）**

**核心原理（一句话）**：在启动关键路径上的多个代码点埋下时间戳，结束后差值计算各阶段耗时。

**工作机理**：

```java
public class StartupTracer {
    static long T_PROCESS_START, T_APP_CREATED, T_ACTIVITY_CREATED, T_FIRST_FRAME, T_INTERACTIVE;
    public static void mark(String stage) {
        long now = SystemClock.elapsedRealtimeNanos();
        switch (stage) {
            case "PROCESS_START":     T_PROCESS_START = now; break;
            case "APP_CREATED":       T_APP_CREATED = now; break;
            case "ACTIVITY_CREATED":  T_ACTIVITY_CREATED = now; break;
            case "FIRST_FRAME":       T_FIRST_FRAME = now; break;
            case "INTERACTIVE":       T_INTERACTIVE = now; report(); break;
        }
    }
}
```

升级版用 ASM / SwiftSyntax / Babel 在编译期自动插桩到关键 API。

**物理本质**：启动是一个有清晰阶段的进程，**在每个阶段边界放一个度量哨兵**，事后差值即得各阶段耗时。

**为什么这样有效**：

- 颗粒度可任意调整：可以细到每个 SDK、每个 ContentProvider。
- 跨平台高度通用：所有平台都支持时间戳函数。
- 数据完全准确：直接读 `SystemClock` / `mach_absolute_time` / `performance.now()`。

**局限根源**：

- **只能看到"应用层"边界**：进程启动到 Application.onCreate 之间应用看不到 —— 这恰恰是冷启动重要的一段。
- **埋点本身是侵入式的**：每加一个埋点要改代码或加插桩规则。
- **只能看自己加的点**：第三方 SDK 内部耗时看不到。

**适用边界**：自家代码内部的精细监控，配合插桩可获得 ~50 行代码级颗粒度。

---

**② 系统级 API（reportFullyDrawn / MetricKit / Performance API）**

**核心原理（一句话）**：操作系统知道"进程从被创建到 Application/UI 就绪"的完整时序，提供专门 API 直接告诉你各阶段耗时。

**工作机理**：

| 平台 | API | 暴露的数据 |
|---|---|---|
| Android | `Activity.reportFullyDrawn()` 配合 logcat `Displayed` | TTID + TTFD |
| Android 12+ | `ApplicationStartInfo` | 进程级启动时序（含 cold/warm/hot 标记） |
| iOS | `MetricKit MXAppLaunchMetric` | dyld / Process Init / App Init / UI Init / 首帧分阶段 |
| Web | `Performance.timing` / `PerformanceNavigationTiming` | navigationStart / DOMContentLoaded / loadEventEnd |
| Web | `LCP` / `FCP` / `INP` | 用户感知关键时刻 |

**物理本质**：应用层无法看到"进程创建 → 运行时启动"这段，但 OS 自己看得到，**它把这部分数据通过 API 暴露给你**。

**为什么这样有效**：数据完整覆盖前置阶段；数据权威来自系统内核 / 框架自身；性能开销几乎为 0。

**局限根源**：

- **API 颗粒度由系统决定**：把"Application 初始化"打包成一个数字。
- **新版本系统才支持**：MetricKit iOS 13+；ApplicationStartInfo Android 12+。
- **回调时机受限**：MetricKit 只能在 App 后台后聚合回调，不能实时。

**适用边界**：作为应用埋点的"前置补全"，两者必须配合使用。

---

**③ 端到端外部测量（高速摄像 / 屏幕直采）**

**核心原理（一句话）**：用外部设备拍下"用户点击图标 → 屏幕显示首屏"全过程，逐帧分析得出物理端到端延迟。

**物理本质**：软件指标永远是"内部视角"，最终用户体验只能由"外部视角"验证。

**为什么这样有效**：唯一能测出**真实端到端延迟**的方法，含触摸采样、系统调度、应用代码、屏幕扫描所有时间；不依赖任何应用 / 系统 API，跨平台一致可比。

**局限根源**：门槛高（外部设备 + 自动化分析 + 固定光照）；不能线上，仅实验室。

**适用边界**：金标准基线测试 + 校准方案 ②/① 的偏差。

---

**三种方案的总览**

| 方案 | 关键钩子位置 | 输出粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 应用埋点 | 应用代码内 | 任意精细 | 低 | 高 | ✅ | 看不到运行时启动前 |
| ② 系统级 API | OS 提供 | 阶段级 | 极低 | 中 | ✅（API 受限）| 颗粒度由系统决定 |
| ③ 外部测量 | 屏幕外 | 物理时序 | 无 | 极高 | ❌ | 设备 / 流程门槛 |

**方案的"组合定律"**：没有任何单一方案能 100% 覆盖启动监控。**必须组合使用**：② 看进程到 Application 之前的"黑盒" + ① 看应用代码内部精细阶段 + ③ 实验室基线校准。

## 04.归因方法

> 采集只能告诉我们"启动 3 秒"，归因要告诉我们"3 秒里 1.2s 是 SDK 初始化、0.8s 是首页 IO"。

### 4.1 启动归因决策树

**为什么需要决策树而不是经验排查**

启动慢的根因有十几种（任务多、SDK 重、依赖链长、IO 多、锁竞争……），决策树把"穷举式排查"压缩成"二分式排查"：先二分到阶段，再到根因，平均 2 步定位。

**完整决策树**：

```
启动 > 目标值
   │
   ├── 阶段 A. 进程 / 运行时启动 > 0.8s ──▶ 包大小、动态库链接
   │                                          ├─ Multi-DEX 慢（详见 §5.3）
   │                                          ├─ 静态初始化代码多
   │                                          └─ dylib / .so 链接多
   │
   ├── 阶段 B. Application 阶段 > 0.5s ────▶ Application.onCreate 重
   │                                          ├─ 同步初始化的 SDK 太多
   │                                          ├─ ContentProvider 串行（Android）
   │                                          ├─ AppDelegate 中的同步操作（iOS）
   │                                          └─ DOMContentLoaded 中阻塞 JS（Web）
   │
   ├── 阶段 C. Activity / 首屏控制器 > 0.3s ─▶ UI 创建慢
   │                                          ├─ 布局过深（详见卷三·渲染篇）
   │                                          ├─ 首屏数据同步加载
   │                                          └─ View Inflate 慢
   │
   └── 阶段 D. 首帧之后到可交互 > 1s ────────▶ 数据加载慢
                                               ├─ 网络请求串行
                                               ├─ 缓存未命中
                                               └─ 大列表初始化
```

> 反直觉问题 ③ 答案：CPU 不饱和但启动慢，几乎一定是 B 类（IO / Binder / 锁等待）或资源竞争。

### 4.2 关键路径分析法

**关键路径分析的步骤**：

1. **建任务清单**：列出启动期所有任务及其耗时。
2. **建依赖图**：标注每个任务依赖什么。
3. **求关键路径**：DAG 上的最长路径。
4. **重排 / 异步化**：把非关键任务移出，缩短关键任务。

**关键路径求解（简化算法）**：

对每个任务 t，计算：

- `EarliestStart(t)` = max(EarliestEnd of all predecessors)
- `EarliestEnd(t)` = EarliestStart(t) + Duration(t)

最终：`TotalTime = max(EarliestEnd of all tasks)`。关键路径 = 任何 EarliestEnd = TotalTime 的链路。

**工程上的两个简化工具**：

- **Trace 时序图**（Perfetto / Instruments / Chrome Performance）直接展示每个任务的开始 / 结束 / 关系。
- **Gantt 图导出**（自定义脚本从打点数据生成）便于离线分析。

### 4.3 阶段拆解归因法

按 §4.1 决策树的四阶段，逐阶段定位：

**阶段 A：进程 / 运行时**

工具：Android `ApplicationStartInfo` + Trace；iOS Instruments dyld + libObjc；Web Network panel。

典型问题：

- 包体积 > 100MB → dex 加载慢 / dyld 链接慢。
- 静态初始化代码 + Class.forName 多 → 类加载耗时。
- 启动期就有大量 Native 库 → JNI_OnLoad 串行。

**阶段 B：Application**

工具：Trace + 应用埋点。

典型问题（按耗时排序）：

- ContentProvider.onCreate 串行（Android 特有，每个 ContentProvider 阻塞 Application 直到完成）。
- 数据库 / SP / NSUserDefaults 同步读 → IO bound。
- 网络初始化（建立 SSL / WebSocket）→ 网络 bound。
- 大量 SDK 同步 init → CPU bound。

**阶段 C：Activity / 首屏控制器**

工具：Choreographer / FrameMetrics（详见卷三·渲染篇）。

典型问题：

- 布局过深 → Measure / Layout 耗时（详见 §5.1 of 卷三·01 渲染篇）。
- ViewStub 滥用导致 inflate 集中。
- 主题 windowBackground 加载大图。

**阶段 D：首帧到可交互**

工具：业务埋点 + 网络监控。

典型问题：

- 首页数据网络请求慢（SSL 握手 / DNS）。
- 大列表 onBindViewHolder 中同步 IO。
- 异步任务回调到主线程后立即触发卡顿。

### 4.4 任务依赖归因法

**反直觉问题 ⑦ 的回应**：异步化后总耗时不一定减少。

为什么：

- **A 任务依赖 B**：A 异步无法跳过 B 的耗时。
- **B 占用 CPU**：异步只是把 B 移到子线程，CPU 总量不变。
- **异步开销**：线程创建、上下文切换本身有成本（详见 §5.2）。

正确的"任务依赖归因"步骤：

1. 列出每个任务的真实依赖（不是想当然）。
2. 找出"伪依赖"（误以为依赖，实际可解耦）。
3. 异步化只对**真正无依赖**的任务有效。
4. 异步化必须验证总耗时减少（A/B 测试），否则可能反向收益。

**反直觉问题 ④ 的回应**：开多少线程最快？

由 [`卷二·CPU 篇 §5.2`](../02.资源篇/01.CPU监控与分析.md) 已证明：CPU bound 任务的最优线程数 = CPU 核数（拐点）。超过后上下文切换开销超过并发收益。

启动期推荐线程数：

- 计算密集任务池：CPU 大核数 + 1（4–6 个）。
- IO 密集任务池：可更大（10–20 个），但要看磁盘并发能力。
- **总线程数不要超过 CPU 总核数 × 2**，否则启动期线程争用反而拖慢。

## 05.求证实验 ⭐

> 本章是"科学家求证"风格的核心。每个实验都遵循 **观察 → 疑问 → 假设 → 推导 → 实验 → 数据 → 验证 → 结论 → 边界** 九步。

### 5.1 实验一：阿姆达尔上限

**Step 1 — 原始观察**

工程实践中常听到："我把所有启动任务都改异步了，启动应该会更快。"实测只快了 30%，不是预期的 5×？经验告诉我们"异步有用"，但**到底有用多少？上限在哪？**

**Step 2 — 提出疑问**

> **给定启动任务集，可异步化部分占比为 P，并行加速比为 N，启动总时长 T(P, N) 是多少？**

**Step 3 — 形成假设**

**H₁**：T(P, N) 服从阿姆达尔定律：T(P, N) = T₀ × [(1 − P) + P/N]，存在硬上限 1/(1−P)。  
**H₀**：异步化可以无限加速。

**Step 4 — 数学推导**

设原始启动时长 T₀，可异步化部分占比 P。改为 N 路并行后：

```
   串行部分时长 = T₀ × (1 − P)        （无法缩短）
   并行部分时长 = T₀ × P / N
   总时长 T(P, N) = T₀ × [(1 − P) + P / N]
   加速比 S(P, N) = T₀ / T(P, N) = 1 / [(1 − P) + P / N]
   加速比上限（N → ∞）：S_max = 1 / (1 − P)
```

| P | S_max | 含义 |
|---|---|---|
| 0.5 | 2× | 即使无限并行最多快一倍 |
| 0.7 | 3.3× | |
| 0.8 | 5× | |
| 0.9 | 10× | |
| 0.95 | 20× | |

**关键洞察**：要让启动加速 10×，可异步化部分必须 ≥ 90%。**实际启动中能异步化的占比通常 50–70%**，所以加速上限通常 2–3×。

**Step 5 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 |
| 编译 | Release |
| 测试 App | 自构造启动场景：10 个任务，每个 100ms |
| 控制变量 | 任务数固定 / 单任务耗时固定 / 任务间无依赖 |
| P 取值 | 通过控制"必须串行的任务数 = (1−P) × 10"实现 |
| N 取值 | 1, 2, 4, 8（线程池大小） |
| 主指标 | 总启动时长 |
| 重复 | 每组 100 次 |

**Step 6 — 实测数据**

设 T₀ = 1000ms（10 任务 × 100ms 全串行）：

| P | N=1 | N=2 | N=4 | N=8 | 公式 N=∞ |
|---|---|---|---|---|---|
| 0.5 | 1000 | 750 | 625 | 562 | 500 |
| 0.7 | 1000 | 650 | 475 | 388 | 300 |
| 0.8 | 1000 | 600 | 400 | 300 | 200 |
| 0.9 | 1000 | 550 | 325 | 213 | 100 |

实测与公式对比（P = 0.8）：

| N | 公式预测 (ms) | 实测 (ms) | 误差 |
|---|---|---|---|
| 1 | 1000 | 1015 | +1.5% |
| 2 | 600 | 625 | +4% |
| 4 | 400 | 445 | +11% |
| 8 | 300 | 380 | +27% |

**Step 7 — 验证 / 修正**

- 小 N（1–2）误差稳定在 < 5%，符合阿姆达尔定律。
- 大 N（4 / 8）误差显著放大 → 引入新因素：**线程切换开销 / 锁争用**。

**修正模型**：T(P, N) = T₀ × [(1 − P) + P/N] + N × C，其中 C 是单线程开销（实测约 10ms / 线程，含创建 + 调度）。

**Step 8 — 提炼结论**

> **启动加速比存在硬上限 = 1 / (1 − P)。  
> 大部分应用 P ≈ 0.7，所以加速上限 ≈ 3.3×；超过这个上限再加并发只会反向劣化。**

工程意义：

- **减少串行部分比堆并发更有效**：把 P 从 0.7 提到 0.9，上限从 3.3× 提到 10×。
- **线程数 ≤ CPU 核数**：超过后开销超过收益。
- **关键路径上的任务必须从根本上优化**（缩短或删除），不能只靠异步。

**Step 9 — 边界**

- 本结论假设任务无依赖。实际启动中任务依赖图限制了并行度，实际加速比比理论上限更低。
- 假设异步任务无 IO 阻塞。如果存在大量 IO，则 N 可以远超 CPU 核数（详见 §4.4）。
- 假设系统资源充足。低端机 CPU 总量小，N 的最优值更小。

### 5.2 实验二：异步代价测量

**Step 1 — 原始观察**

工程师常说"小任务异步就是浪费"。但**到底多小算小？异步本身的开销是多少？**

**Step 2 — 提出疑问**

> **创建一个线程并执行一个任务，相比同步执行，固定开销是多少？小于这个开销的任务，异步就是反向收益。**

**Step 3 — 形成假设**

**H₁**：异步固定开销 C 由"线程创建 + 调度 + 上下文切换 + 任务排队 + 主线程同步"组成，量级在 0.1–10ms。任务耗时 < C 时异步反向收益。  
**H₀**：异步开销可以忽略。

**Step 4 — 数学推导**

异步执行单个任务的总开销：

```
   C_async = T_create + T_schedule + T_context_switch + T_join

   其中（Android Pixel 6 实测典型值）：
   T_create        = 50–200 μs（线程池新建 worker）
   T_schedule      = 10–50 μs（系统调度延迟）
   T_context_switch = 1–10 μs（每次切换）
   T_join          = 10–100 μs（结果回主线程）

   合计 C ≈ 0.1 – 0.5 ms（线程池命中）
        ≈ 1 – 5 ms（首次创建线程）
```

**Step 5 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 |
| 测试任务 | 纯 CPU 计算（控制耗时 1, 5, 10, 50, 100ms） |
| 对照组 | 同步执行 |
| 实验组 A | 通过 `ExecutorService.submit().get()`（含 join） |
| 实验组 B | `HandlerThread`（含 Looper 调度） |
| 主指标 | 端到端总耗时（含异步开销） |
| 重复 | 每组 1000 次 |

**Step 6 — 实测数据**

| 任务耗时 | 同步 (ms) | 异步 A (ms) | 异步 B (ms) | 异步开销 |
|---|---|---|---|---|
| 1ms | 1.05 | 1.45 | 1.80 | A: +0.4ms, B: +0.75ms |
| 5ms | 5.1 | 5.5 | 5.9 | A: +0.4ms, B: +0.8ms |
| 10ms | 10.1 | 10.5 | 10.9 | A: +0.4ms, B: +0.8ms |
| 50ms | 50.2 | 50.6 | 51.0 | A: +0.4ms, B: +0.8ms |
| 100ms | 100.3 | 100.7 | 101.1 | A: +0.4ms, B: +0.8ms |

**Step 7 — 验证 / 修正**

- 异步开销稳定在 0.4ms（ExecutorService）/ 0.8ms（HandlerThread），与公式预测一致。
- 任务越短，开销占比越大：1ms 任务异步会增加 40–80% 时长。

**关键发现**：异步**单任务**几乎没有收益（甚至反向），收益完全来自**多任务并行**。

**Step 8 — 提炼结论**

> **异步的固定开销约 0.4–0.8ms（线程池命中）。耗时 < 1ms 的任务异步是反向收益。  
> 异步只对"耗时 ≥ 5ms 且可并行 ≥ 2 个"的任务有效。**

工程意义：

- **不要为了"代码看起来异步"而异步**：小任务直接同步执行。
- **批量异步比单个异步更划算**：把 N 个小任务合并成 1 个异步任务。
- **首次启动有"线程池预热"成本**：可以在启动早期 `warmup` 线程池（创建 N 个空 worker），避免后续任务首次创建开销。

**Step 9 — 边界**

- 本结论对 CPU 任务成立。IO 任务由于"等待"占主导，异步几乎总是有收益（让出 CPU）。
- 低端机 CPU 慢，C 上升到 2–5ms（线程创建本身就是 CPU 开销）。
- iOS 的 GCD 因有底层优化（dispatch_queue 不一定新建线程），C 通常更小（0.1–0.3ms）。

### 5.3 实验三：MultiDex 影响

**Step 1 — 原始观察**

工程师常听说"MultiDex 启动慢"，但 Android 5.0+ 之后是否还慢？慢多少？反直觉问题 ⑤ 的根源。

**Step 2 — 提出疑问**

> **MultiDex 在 Android 5.0+（ART 运行时）相比单 DEX，冷启动时长差异是多少？**

**Step 3 — 形成假设**

**H₁**：Android 5.0+ 的 ART 已对 MultiDex 做了 AOT 优化，启动差异 < 100ms（与 4.x 的 200–1500ms 差距显著缩小）。  
**H₀**：MultiDex 仍然显著拖慢启动。

**Step 4 — 数学推导**

- **Android 4.x**：Dalvik 在主线程加载第二 DEX，含解压、odex 生成。耗时 ≈ N × 500ms（N = 次 DEX 数）。
- **Android 5.0+**：ART 在安装时 AOT 编译所有 DEX 为 OAT。启动时只加载已编译的 OAT。理论上 MultiDex 与单 DEX 无差异。
- **Android 7.0+**：进一步优化为 JIT + AOT 混合，安装更快但运行时 JIT 略增。

**Step 5 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 4（Android 13）+ Samsung Note 4（Android 4.4） |
| 测试 App | 自构造 5,000 / 10,000 / 50,000 方法的应用 |
| 对照 | 单 DEX vs MultiDex（2 DEX / 3 DEX） |
| 主指标 | 冷启动 TTID（logcat Displayed） |
| 重复 | 每组 50 次 |

**Step 6 — 实测数据**

| 方法数 | 单 DEX (ms) | Multi 2 (ms) | Multi 3 (ms) | 设备 |
|---|---|---|---|---|
| 5,000 | 380 | 385 | 392 | Android 13 |
| 10,000 | 410 | 415 | 425 | Android 13 |
| 50,000 | 580 | 595 | 615 | Android 13 |
| 5,000 | 720 | 1,250 | 1,800 | Android 4.4 |
| 10,000 | 850 | 1,580 | 2,300 | Android 4.4 |

**Step 7 — 验证 / 修正**

- Android 13 的 MultiDex 影响 < 5%（5–35ms），可忽略。
- Android 4.4 的 MultiDex 显著拖慢（+50–170%）。
- 拒绝 H₀，验证 H₁：ART 几乎消除了 MultiDex 启动代价。

**Step 8 — 提炼结论**

> **Android 5.0+ 的 MultiDex 启动代价 < 5%，可忽略。  
> Android 4.x 的 MultiDex 启动代价 50–170%，必须用 `MultiDex.install()` 异步化或合并 DEX。**

工程意义：

- 已停止支持 Android 4.x 的应用，**MultiDex 不再是启动优化的重点**。
- 仍支持 Android 4.x 的应用，**MultiDex 是关键瓶颈**，需特殊处理（如延迟次 DEX 加载）。
- 优化重心应放在"减少同步初始化的 SDK 数 + 异步化第三方初始化"，而非纠结 DEX 数。

**Step 9 — 边界**

- 本结论假设 ART 已完成 AOT 编译。**首次安装后第一次启动**仍可能因 ART 编译进行而较慢（一次性）。
- 谷歌 Pixel 等设备有 Cloud Profile 优化，第三方 ROM 可能差异较大。
- 包含大量 Native 库（JNI_OnLoad）的应用，启动慢来自 .so 而非 DEX，结论需重新评估。

---

### 5.4 三大实验启示

把三个实验放在一起看，会发现**关键路径与 Amdahl 定律被反复印证**：

```
   阿姆达尔上限   → 异步加速有硬上限（1/(1−P))  ─┐
                                                  ├─▶ 启动 = 关键路径优化问题
   异步代价测量   → 小任务异步反向收益            │
                                                  │
   MultiDex 已死  → 不要被过时的"经验"误导          ─┘
```

**统一启示**：

- **优化的目标不是"让某段更快"，而是"缩短关键路径"**。非关键路径上的优化对总时长无收益。
- **数据驱动比经验法则可靠**：MultiDex 在 Android 5.0+ 已不是问题，但很多团队仍把它列为"启动优化首要项"。
- **科学的优化优先级**：① 删除可选任务 > ② 缩短关键任务 > ③ 异步可并行任务 > ④ 增加并发度。

## 06.优化策略

### 6.1 通用治理矩阵

按"四阶段 × 三类问题"展开，所有启动优化都可归入下表：

| 阶段 | 治理方向 | 通用手段 |
|---|---|---|
| A. 进程 / 运行时 | 减小包体积 | 移除未用资源；动态库按需加载；So 合并；R8/ProGuard |
| A. 进程 / 运行时 | 减少静态初始化 | 类懒加载；ContentProvider 改为按需注册 |
| B. Application | 减少 SDK 同步 init | 必要 SDK 同步 / 非必要全部异步或延迟 |
| B. Application | 减少同步 IO | SP/NSUserDefaults 异步预读；DB 懒打开 |
| B. Application | 减少 ContentProvider 串行 | 用 App Startup 库统一调度；非必要 Provider 设 `initOrder=-1` |
| C. Activity | 减少首屏布局复杂度 | 扁平化布局（详见卷三·01 §5.1）；ViewStub 延迟 |
| C. Activity | 减少同步数据加载 | 占位骨架屏；先渲染后填数据 |
| D. 首帧到可交互 | 减少串行网络 | 数据预取；缓存优先 |
| D. 首帧到可交互 | 减少大列表初始化 | 分页加载；首屏只渲染可见 |
| 跨阶段 | 异步化 + 任务调度 | App Startup / Anchors / 任务 DAG 调度器 |
| 跨阶段 | 关键路径分析 | Trace + 工程脚本生成 Gantt 图 |

### 6.2 平台特化策略

**Android 特化**：

- 用 [`App Startup` Jetpack 库](https://developer.android.com/topic/libraries/app-startup) 统一调度 SDK 初始化，消除 ContentProvider 串行。
- 用 `AsyncLayoutInflater` 异步 inflate 首屏布局。
- 用 `Baseline Profiles` (12+) 让 ART 优先 AOT 编译启动期方法。
- 用 `App Bundle + Dynamic Feature` 按需加载次要功能。
- 监控 ANR 用 `ApplicationStartInfo.STARTUP_TIMEOUT_REASON_*`。

**iOS 特化**：

- 删除不必要的 `+load` 方法（每个都阻塞 dyld）。
- 减少动态库数（每个 dylib 增加 dyld 链接时间 ~10ms）。
- 用 `dyld3 / dyld4` 预链接（系统自动，但需要避免在启动早期触发 dlopen）。
- 用 `os_signpost` 标记关键阶段，Instruments 直接读取。
- 启用 Order Files 优化函数布局（减少首次启动 page fault）。

**Web 特化**：

- Code Splitting：按路由拆分 Bundle，首屏只加载必需 JS。
- Tree Shaking + minify：减少 Bundle 体积。
- Preload 关键资源（CSS / 字体）。
- SSR / Static Generation：把首屏 HTML 在服务端预渲染。
- Service Worker 缓存：第二次启动接近 0 延迟。

**嵌入式特化**：

- 必要任务在 `init` 阶段；非必要延迟到 UI 主循环空闲时。
- DMA 直接搬运资源（避免 CPU 阻塞）。
- 启动早期降低非关键外设功耗（GPS / WiFi）。

### 6.3 优先级判定（ROI）

不同优化的 ROI 差异极大，按以下顺序考虑：

| ROI | 优化项 | 收益 | 成本 | 风险 |
|---|---|---|---|---|
| 极高 | 删除可选 SDK / 后置初始化 | 100–500ms | 1–3 天 | 几乎零 |
| 极高 | ContentProvider 整合到 App Startup | 200–500ms | 1 周 | 低 |
| 高 | 首屏数据预取 / 占位骨架 | 200–800ms | 2 周 | 中 |
| 高 | 包体积优化（R8/ProGuard）| 100–300ms | 1 周 | 低 |
| 中 | 异步化 Application init | 100–300ms（视并发度）| 2 周 | 中（线程同步）|
| 中 | 布局扁平化 | 50–200ms | 1–2 周 | 中（动画兼容）|
| 低 | MultiDex 优化（仅 4.x 有效）| 0–50ms（Android 5+）| 1 周 | 低 |
| 极低 | 自实现类加载器 | 几乎无收益 | 极高 | 极高 |

**避免反向收益**：

- 过度异步化：每个小任务都包装异步，总开销反而增加（§5.2 已证）。
- 过度并发：开 20+ 线程，启动期线程切换抢占 CPU，反而拖慢。
- 过度 AOT：把不会执行的代码也编译，安装慢且包体积涨。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某社交应用冷启动 P50 = 3.2s，远高于行业基准 2s。多平台都有问题。

**现象**：

- Android：Trace 显示 Application.onCreate 占 2.4s，含 18 个 SDK 同步 init。
- iOS：Instruments 显示 didFinishLaunching 占 1.8s，含 12 个 SDK 同步 init。
- Web：Lighthouse 显示 TTI = 5.8s，主线程被 6 个 SDK JS 阻塞。

**度量与归因**：

三平台共同特征：**初始化期间所有 SDK 都同步执行**。按 §5.1 阿姆达尔分析，可异步化部分 P ≈ 0.7。

**假设与求证**：

提出**统一假设**："大部分 SDK 不必在启动期同步初始化，可以延迟到首屏渲染后或首次使用时"。

设计 A/B：

- A 组：原始全同步 init
- B 组：分级初始化策略
  - 必要级（启动期同步）：日志、Crash、AB 实验
  - 重要级（首帧后异步）：网络、推送、统计
  - 延迟级（首次使用时）：广告、第三方分享、客服

**护栏检查**：

- 崩溃率（异步是否引发空指针）
- 业务功能（推送是否能正常工作）
- 数据一致性（统计是否丢首帧事件）

**修复**：三端统一采用分级初始化框架（Android App Startup / iOS 自研 / Web Lazy Import）。

**验证**：

| 平台 | 优化前 TTID | 优化后 TTID | 降幅 |
|---|---|---|---|
| Android | 3.2 s | 1.4 s | 56% |
| iOS | 2.8 s | 1.2 s | 57% |
| Web | 5.8 s | 2.6 s | 55% |

**边界与上线策略**：分级初始化降低了灵活性（延迟级 SDK 首次使用时可能延迟 100–300ms）。上线策略：先 Android 灰度 1 周，再扩到 iOS / Web。

**统一启示**：跨端同构案例证明阿姆达尔定律在三端都成立。**P 从 0 提到 0.7 的收益 = 启动时长 60%**。

### 7.2 平台特异案例

**背景**：Android 11 应用启动后白屏 800ms 才出现首屏，但 logcat Displayed 显示首帧只用了 1.2s（看似正常）。

**现象**：用户感知"启动后空白等待"。系统指标看似正常。

**度量与归因**：

- 用方案 ③ 高速摄像测得：物理首屏出现时间 2.0s（不是 1.2s）。
- 差异 800ms = 应用首帧已渲染，但用户看到的是 windowBackground。

**假设与求证**：

**假设 1**：windowBackground 与首帧 Activity 的颜色 / 内容不一致，导致用户视觉跳变被错认为"白屏"。  
**实验**：把 windowBackground 改为与首屏一致的渐变。视觉上"无缝衔接"，主观感知时长降低 300ms。✅

**假设 2**：首帧虽然渲染了，但内容是空白的"骨架屏"，用户认为"还在加载"。  
**实验**：在首帧后立即填充缓存数据（即使是上次的）。主观感知时长再降 200ms。✅

**护栏检查**：缓存数据可能过期。在主屏可见后再异步刷新即可。

**修复**：

- 设置 windowBackground 与首屏色调一致。
- 启动后首帧立即用缓存数据渲染，避免空白骨架屏。
- 异步刷新数据，平滑过渡。

**验证**：物理首屏可感知时间从 2.0s 降到 1.5s，用户主观满意度从 3.5/5 提升到 4.6/5。

**边界与上线策略**：仅在缓存有效时适用；首次安装无缓存时退化为占位图。

## 08.防劣化与长效治理

参考 [`卷零·06 性能预算与防劣化体系`](../00.公共方法论/06.性能预算与防劣化体系.md)。

### 8.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
[Lint]      [自动化基准]     [线上 SLO]
```

### 8.2 编码期 Lint

- 在 `Application.onCreate` 中调用 IO / DB / 网络 → 警告。
- 新增 `<provider>` 未注册 App Startup → 警告。
- 在 `viewDidLoad` 中同步加载图片 / 大数据 → 错误。
- Web：`DOMContentLoaded` 中阻塞 JS > 50ms → 警告。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- 启动基准用例：自动化模拟冷启动 50 次，P95 ≤ 阈值（如 2s）。
- 每次 PR 跑一次，劣化 > 5% 阻塞合并。
- 包体积监控：每次 PR 检查 APK / IPA / Bundle 大小，超 10MB 增量阻塞合并。

**线上 SLO**：

- 冷启动 P50 < 2s / P99 < 5s。
- 启动失败率 < 0.1%（含 ANR / Crash / 超时）。
- 启动期卡顿率 < 5%。
- 错误预算耗尽 → 冻结新功能。

## 10.总结与延伸

### 10.1 五条核心原则

1. **关键路径思维**：总启动时长 = 关键路径耗时，不是任务总和。优化必须围绕关键路径展开。
2. **数据驱动决策**：每条优化必有量化收益（如"删除 SDK init = 减 200ms"），来自实验。
3. **分级初始化**：必要 / 重要 / 延迟三级，把可延迟的全部移出启动期。
4. **TTID + TTFD 并重**：首帧 ≠ 可交互。两者必须都达标。
5. **科学求证替代经验**：MultiDex 在 Android 5.0+ 已不是问题，但仍有团队投入大量精力。

### 10.2 五个常见误区

1. **"所有任务都异步就是快"**：错。阿姆达尔定律有硬上限；小任务异步反向收益。
2. **"线程开越多越快"**：错。超过 CPU 核数后切换开销反而拖慢。
3. **"首帧出来就是启动结束"**：错。TTFD 才是用户感知的"完成"，可能比 TTID 慢一倍。
4. **"包体积大启动一定慢"**：基本对，但 Android 5.0+ 的 ART AOT 让影响小于直觉。
5. **"启动监控有 logcat Displayed 就够了"**：错。要同时看物理端到端延迟（含 windowBackground 时间）。

## 一句话总结

> **启动是一个关键路径上的最优化问题。  
> 总启动时长 = 关键路径所有串行任务耗时之和。  
> 一切优化都是缩短关键路径或把任务从关键路径移走（异步 / 延迟）。  
> 非关键路径上的任务，再慢也不影响启动时长。**
