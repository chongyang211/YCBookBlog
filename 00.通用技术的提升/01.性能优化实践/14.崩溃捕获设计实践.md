## 01.整体介绍概述
### 1.1 项目背景介绍
- `Android`的稳定性是`Android`性能的一个重要指标，它也是App质量构建体系中最基本和最关键的一环。
    - 如果应用经常崩溃率，或者关键功能不可用，那显然会对我们的留存产生重大影响。


### 1.2 遇到问题
- `Crash`率多少算优秀呢？
    - 在明确了目标之后，我们才能正确认识我们的工作到底有什么作用。降低崩溃率到我们的指标……
- 崩溃率如何衡量
    - 崩溃率 UV = 发生崩溃的UV / 启动UV
    - 衡量标准：崩溃率小于3/1000为正常，3/10000为优秀
- 崩溃治理面临的核心挑战
    ```
    崩溃治理四大核心挑战：
    
    1.复现难 ──→ 用户环境多样（机型×系统版本×网络×操作路径）
      │          线上崩溃往往无法在开发环境复现
      │
    2.定位难 ──→ 混淆后堆栈不可读
      │          Native崩溃缺少符号表
      │          多线程并发导致的随机崩溃
      │
    3.归因难 ──→ 崩溃堆栈≠根因（OOM的堆栈只是最后一根稻草）
      │          跨版本对比困难
      │
    4.防劣化难 ─→ 修一个引入一个
                  三方SDK升级引入新崩溃
                  灰度验证不充分
    ```
- 不同类型崩溃的捕获难度对比
    | 崩溃类型 | 捕获难度 | 信息完整度 | 典型案例 |
    |---------|---------|-----------|---------|
    | Java Crash | 低 | 高（完整堆栈） | NullPointerException |
    | Native Crash | 中 | 中（需符号化） | 空指针解引用SIGSEGV |
    | ANR | 中 | 中（需traces.txt） | 主线程死锁 |
    | OOM | 高 | 低（堆栈非根因） | Bitmap内存不足 |
    | 系统杀进程 | 极高 | 极低（无回调） | LMK杀死进程 |


### 1.3 Crash指标和治理原则
- 计算Crash率，首先应该明白稳定性优化的一些关键指标
    - UV Crash率：针对用户使用量的统计，统计一段时间内所有用户发生崩溃的占比，用于评估Crash率的影响范围。
    - PV Crash率：针对用户使用次数的统计，评估相关Crash影响的严重程度。
    - Java与Native的总崩溃率必须在千分之二以下，Crash率万分位为优秀。
- Crash治理的核心原则
    - 由点到面：一个Crash发生了，不能只针对这个Crash去解决，而要去考虑这一类Crash怎么去解决和预防。
    - 异常不能随便吃掉：随意的使用try-catch，只会增加业务的分支和隐蔽真正的问题。catch的分支，更要根据业务场景去兜底，保证后续的流程正常。
    - 先止损再根治：当Crash发生的时候，损失已经造成了。尽可能的提前预防Crash的发生，可以将Crash消灭在萌芽阶段。
    - 事后复现和总结：尽量去找到复现问题的链路，方便排查问题，修改后是否再次出现。
- 崩溃治理成熟度模型
    ```
    Level 1 - 被动响应：用户反馈才知道崩溃 → 崩溃率 > 1%
    Level 2 - 基础监控：接入Bugly/Firebase → 崩溃率 0.3-1%
    Level 3 - 主动治理：专项治理+归因分析 → 崩溃率 0.1-0.3%
    Level 4 - 体系化：自动归因+防劣化+灰度验证 → 崩溃率 < 0.1%
    Level 5 - 智能化：AI辅助根因定位+自动修复 → 崩溃率 < 0.03%
    ```


### 1.4 基础概念介绍
- 崩溃现场是"第一案发现场"，它保留着很多有价值的线索。
    - 接下来具体来看看在崩溃现场，确认重点，内存&线程需特别注意，很多崩溃都是由于它们使用不当造成的。如何去分析日志
- 确认严重程度
    - 如果一时半会解决不了，那么能否先止损，采用降级策略。延期修复，如果是非要解决，那么解决完后即通过灰度测试发版，及时跟进问题。
- 崩溃基本信息
    - Java 崩溃（比如 `NullPPointerException` 是空指针，`OutOfMemoryError` 是资源不足）
    - Native 崩溃（比较常见的是有 SIGSEGV 和 SIGABRT）
    - ANR（先看看主线程的堆栈，是否是因为锁等待导致。接着看看 ANR 日志中 iowait、CPU、GC、system server 等信息，进一步确定是 I/O 问题，或是 CPU 竞争问题，还是由于大量 GC 导致卡死）
- Logcat日志
    - 从 `Logcat` 中我们可以看到当时系统的一些行为跟手机的状态，当从一条崩溃日志中无法看出问题的原因，或者得不到有用信息时，不要放弃，建议查看相同崩溃点下的更多崩溃日志。
- 查找共性（机型、系统、ROM、厂商、ABI）
    - 机型、系统、ROM、厂商、ABI，这些采集到的系统信息都可以作为维度聚合，共性问题例如是不是因为安装了 Xposed，是不是只出现在 x86 的手机，是不是只有三星这款机型，是不是只在 Android 8.0 的系统上。
- 复现问题
    - 尽量去找到复现问题的链路，方便排查问题。有些bug如果找不到，那么思考能否上传info日志，通过技术埋点去排查崩溃链路问题。



### 1.5 设计目标
- 能够准确将崩溃日志写到本地文件
    - 能够捕获到崩溃日志，然后把它通过io流写入到file文件中。写入的崩溃信息，带有完整的异常堆栈链信息，还有一些基础的手机和App属性。
- 能够有效计算相同崩溃的次数
    - 比如针对同一段代码的类型转化异常`java.lang.NumberFormatException: For input string: "12.3"`，如果出现多次，需要统计到具体的次数。
- 能够可视化展示崩溃日志信息
    - 这一块，主要是能够读到崩溃日志路径，拿到所有的文件。然后通过可视化界面展示出来，方便查看！
- 能够将崩溃信息文件转发分享
    - 能够将崩溃file文件分享到微信，QQ或者钉钉这类社交App，方便测试童鞋转发给开发。[MonitorFileLib](https://github.com/yangchong211/YCAndroidTool/tree/master/MonitorFileLib)



## 02.App崩溃流程
### 2.1 为何崩溃推出App
- 线程中抛出异常以后的处理逻辑
    - 一旦线程出现抛出异常，并且在没有捕捉的情况下，`JVM`将调用`Thread`中的`dispatchUncaughtException`方法把异常传递给线程的未捕获异常处理器。
- 找到Android源码中处理异常捕获入口
    - 既然`Android`遇到异常会发生崩溃，然后找一些哪里用到设置`setDefaultUncaughtExceptionHandler`，即可定位到`RuntimeInit`类。
    - 即在这个里面设置异常捕获`KillApplicationHandler`，发生异常之后，会调用`handleApplicationCrash`打印输出崩溃`crash`信息，最后会杀死应用`app`。



### 2.2 处理崩溃流程
**崩溃的大概流程**
- 然后看一下`RuntimeInit`类，由于是java代码，所以首先找`main`方法入口。代码如下所示
    ``` java
    public static final void main(String[] argv) {
        commonInit();
    }
    ```
- 然后再来看一下`commonInit()`方法，看看里面做了什么操作？
    - 可以发现这里调用了`setDefaultUncaughtExceptionHandler`方法，设置了自定义的`Handler`类
    ``` java
    protected static final void commonInit() {
        Thread.setDefaultUncaughtExceptionHandler(new KillApplicationHandler(loggingHandler));
    }
    ```
- 接着看一下`KillApplicationHandler`类，可以发现该类实现了`Thread.UncaughtExceptionHandler`接口
    - 这个就是杀死app逻辑具体的代码。可以看到当出现异常的时候，在finally中会退出进程操作。
    ``` java
    private static class KillApplicationHandler implements Thread.UncaughtExceptionHandler {
        @Override
        public void uncaughtException(Thread t, Throwable e) {
            try {
                ActivityManager.getService().handleApplicationCrash(
                        mApplicationObject, new ApplicationErrorReport.ParcelableCrashInfo(e));
            } finally {
                Process.killProcess(Process.myPid());
                System.exit(10);
            }
        }
    }
    ```
- 得出结论如下所示
    - 其实在`fork`出`app`进程的时候，系统已经为`app`设置了一个异常处理，并且最终崩溃后会直接导致执行该`handler`的`finally`方法最后杀死app直接退出app。
- 如何自己捕获App异常
    - 如果你要自己处理，你可以自己实现`Thread.UncaughtExceptionHandler`。而调用`setDefaultUncaughtExceptionHandler`多次，最后一次会覆盖之前的。



**2.2.2 崩溃日志的记录**
- 在`KillApplicationHandler`类中的`uncaughtException`方法
    - 可以看到`ActivityManager.getService().handleApplicationCrash`被调用，那么这个是用来做什么的呢？
    - ActivityManager.getService().handleApplicationCrash-->ActivityManagerService.handleApplicationCrash-->handleApplicationCrashInner方法
- 从下面可以看出,若传入`app`为`null`时,`processName`就设置为`system_server`
    ``` java
    public void handleApplicationCrash(IBinder app, ApplicationErrorReport.ParcelableCrashInfo crashInfo) {
        ProcessRecord r = findAppProcess(app, "Crash");
        final String processName = app == null ? "system_server" : (r == null ? "unknown" : r.processName);
        handleApplicationCrashInner("crash", r, processName, crashInfo);
    }
    ```
- 然后接着看一下`handleApplicationCrashInner`方法做了什么。调用`addErrorToDropBox`将应用`crash`，进行封装输出
    ``` java
    void handleApplicationCrashInner(String eventType, ProcessRecord r, String processName,
            ApplicationErrorReport.CrashInfo crashInfo) {
        addErrorToDropBox(eventType, r, processName, null, null, null, null, null, crashInfo);
        mAppErrors.crashApplication(r, crashInfo);
    }
    ```
- 崩溃日志封装流程如下所示
    > ActivityManagerService#handleApplicationCrash()，在这个方法里处理崩溃日志信息
    > ActivityManagerService#findAppProcess()，这个是根据binder去找对应的crash的ProcessRecord对象
    > ActivityManagerService#handleApplicationCrashInner()，这个方法很关键
    > ActivityManagerService#addErrorToDropBox()，这个就是将crash，anr，装到盒子里。这个主要在下面会说到
    > ActivityManagerService#appendDropBoxProcessHeaders，这个方法是拼接app的进程，pid，package包名等等




### 2.3 Native崩溃流程
- Native崩溃监控入口流程
    > SystemServer#main()，在fork出system_server进程后执行main方法，然后创建该对象并且执行run方法做初始化各种服务逻辑
    > SystemServer#run()，在这个线程run方法中，调用startOtherServices开启各种服务逻辑
    > SystemServer#startOtherServices()，在这个方法里，是系统system_server进程开启众多服务，比如IMS输入事件服务，NMS通知栏服务等
    > ActivityManagerService#startObservingNativeCrashes()，在这个类中创建NativeCrashListener去监控native崩溃
- `native_crash`，顾名思义，就是`native`层发生的`crash`。其实他是通过一个`NativeCrashListener`线程去监控的。
    ``` java
    final class NativeCrashListener extends Thread {
        @Override
        public void run() {
            try {
                //1.一直循环地读peerFd文件,若发生存在,则进入consumeNativeCrashData
                while (true) {
                    try {
                        if (peerFd != null) {
                            //2.进入native crash数据处理流程
                            consumeNativeCrashData(peerFd);
                        }
                    } 
                }
            }
        }

        void consumeNativeCrashData(FileDescriptor fd) {
            try {
                    //3.启动NativeCrashReporter作为上报错误的新线程
                    final String reportString = new String(os.toByteArray(), "UTF-8");
                    (new NativeCrashReporter(pr, signal, reportString)).start();
            } catch (Exception e) {
            }
        }
    }
    ```
- 上报`native_crash`的线程-->NativeCrashReporter:
    ``` java
    class NativeCrashReporter extends Thread {
        @Override
        public void run() {
            try {
    ```

### 2.5 最后推出App
- 推出App的方式常见的有哪些？思考一下，系统是采用那种方式推出App，为什么？
    - 第一种：在根页面，调用`finish`直接推出App的首页，`Activity`会调用`onDestroy`。这种情况进程其实是未杀死的情况，

- App常见友好的推出方式
    - 杀死进程：先回退到桌面，然后`finish`掉所有`activity`页面，然后在杀死进程和推出程序。可以避免闪一下……

## 03.崩溃处理入口
### 3.1 Java处理异常入口
- `UncaughtExceptionHandler`接口，官方介绍为：
    ``` java
    @FunctionalInterface
    public interface UncaughtExceptionHandler {
        void uncaughtException(Thread t, Throwable e);
    }
    ```
    - Interface for handlers invoked when a Thread abruptly terminates due to an uncaught exception.
    - When a thread is about to terminate due to an uncaught exception the Java Virtual Machine will query the thread for its UncaughtExceptionHandler using getUncaughtExceptionHandler() and will invoke the handler's uncaughtException method, passing the thread and the exception as arguments. If a thread has not had its UncaughtExceptionHandler explicitly set, then its ThreadGroup object acts as its UncaughtExceptionHandler. If the ThreadGroup object has no special requirements for dealing with the exception, it can forward the invocation to the default uncaught exception handler.
- 翻译后大概的意思是
    - `UncaughtExceptionHandler`接口用于处理因为一个未捕获的异常而导致一个线程突然终止问题。
    - 当一个线程因为一个未捕获的异常即将终止时，Java虚拟机将通过调用`getUncaughtExceptionHandler() `函数去查询该线程的`UncaughtExceptionHandler`并调用处理器的`uncaughtException`方法将线程及异常信息通过参数的形式传递进去。如果一个线程没有明确设置一个UncaughtExceptionHandler，那么ThreadGroup对象将会代替UncaughtExceptionHandler完成该行为。如果ThreadGroup没有明确指定处理该异常，ThreadGroup将转发给默认的处理未捕获的异常的处理器。
- 线程出现未捕获异常后，JVM将调用`Thread`中的`dispatchUncaughtException`方法把异常传递给线程的未捕获异常处理器。
    ``` java
    public final void dispatchUncaughtException(Throwable e) {
        getUncaughtExceptionHandler().uncaughtException(this, e);
    }
    public UncaughtExceptionHandler getUncaughtExceptionHandler() {
        return uncaughtExceptionHandler != null ? uncaughtExceptionHandler : group;
    }
    ```


### 3.2 异常处理常用api
**设置uncaughtExceptionPreHandler**
- `Thread`中存在两个`UncaughtExceptionHandler`。
    - 一个是静态的`defaultUncaughtExceptionHandler`，另一个是非静态`uncaughtExceptionHandler`。
    ``` java
    private volatile UncaughtExceptionHandler uncaughtExceptionHandler;
    private static volatile UncaughtExceptionHandler defaultUncaughtExceptionHandler;
    ```
- `defaultUncaughtExceptionHandler`:设置一个静态的默认的`UncaughtExceptionHandler`。
    - 来自所有线程中的`Exception`在抛出并且未捕获的情况下，都会从此路过。进程`fork`的时候设置的就是这个静态的`defaultUncaughtExceptionHandler`，管辖范围为整个进程。
    ``` java
    Thread.setDefaultUncaughtExceptionHandler(new Thread.UncaughtExceptionHandler() {
        @Override
        public void uncaughtException(Thread t, Throwable e) {
            System.out.println("所有线程异常都会被捕获，捕获所有线程："+t.toString() + " throwable : " + e.getMessage());
        }
    });
    ```
- `uncaughtExceptionHandler`:为单个线程设置一个属于线程自己的`uncaughtExceptionHandler`，辖范围比较小。
    ``` java
    //为单个线程设置一个属于线程自己的uncaughtExceptionHandler，捕获单个线程异常。设置后，线程可以完全控制它对未捕获到的异常作出响应的处理。
    thread.setUncaughtExceptionHandler(new Thread.UncaughtExceptionHandler() {
        @Override
        public void uncaughtException(Thread t, Throwable e) {
            System.out.println("捕获单个线程："+t.toString() + " throwable : " + e.getMessage());
        }
    });
    ```


**没有设置uncaughtExceptionPreHandler**
- 没有设置`uncaughtExceptionHandler`怎么办？
    - 如果没有设置`uncaughtExceptionHandler`，将使用线程所在的线程组来处理这个未捕获异常。
    - 线程组`ThreadGroup`实现了`UncaughtExceptionHandler`，所以可以用来处理未捕获异常。ThreadGroup类定义：
    ``` java
    private ThreadGroup group;
    //可以发现ThreadGroup类是集成Thread.UncaughtExceptionHandler接口的
    class ThreadGroup implements Thread.UncaughtExceptionHandler{}
    ```
- 然后看一下`ThreadGroup`中实现`uncaughtException(Thread t, Throwable e)`方法，代码如下
    - 默认情况下，线程组处理未捕获异常的逻辑是，首先将异常消息通知给父线程组，然后尝试利用一个默认的`defaultUncaughtExceptionHandler`来处理异常，
    - 如果没有默认的异常处理器则将错误信息输出到`System.err`。也就是JVM提供给我们设置每个线程的具体的未捕获异常处理器，也提供了设置默认异常处理器的方法。
    ``` java
    public void uncaughtException(Thread t, Throwable e) {
        if (parent != null) {
            parent.uncaughtException(t, e);
        } else {
            //返回线程由于未捕获到异常而突然终止时调用的默认处理程序。如果返回值为 null，则没有默认处理程序。
            Thread.UncaughtExceptionHandler ueh = Thread.getDefaultUncaughtExceptionHandler();
            if (ueh != null) {
                ueh.uncaughtException(t, e);
            } 
        }
    }
    ```



### 3.3 注意事项说明
- 难道要为每一个线程创建`UncaughtExceptionHandler`吗？
    - 应用程序通常都会创建很多线程，如果为每一个线程都设置一次 `UncaughtExceptionHandler` 未免太过麻烦。
    - 既然出现未处理异常后 JVM 最终都会调 getDefaultUncaughtExceptionHandler()，那么我们可以在应用启动时设置一个默认的未捕获异常处理器。
    - 即调用`Thread.setDefaultUncaughtExceptionHandler(handler)`就可以。
- `setDefaultUncaughtExceptionHandler`被调用多次如何理解？
    - `Thread.setDefaultUncaughtExceptionHandler(handler)`方法如果被多次调用的话，会以最后一次传递的 handler 为准。
    - 所以如果用了第三方的统计模块，可能会出现失灵的情况。
    - 对于这种情况，在设置默认 `handler` 之前，可以先通过 `getDefaultUncaughtExceptionHandler()` 方法获取并保留旧的`handler`，然后在默认`handler`的`uncaughtException`方法中调用其他`handler`的`uncaughtException`方法，保证都会收到异常信息。

### 3.6 JVM如何实现异常
- 那么思考一下，`jvm`是如何构造`Throwable`异常的呢？
- 异常实例的构造十分昂贵
    - 由于在构造异常实例时，JVM 需要生成该异常的栈轨迹，该操作逐一访问当前线程的 Java 栈桢，并且记录下各种调试信息，包括栈桢所指向方法的名字、方法所在的类名以及方法在源代码中的位置等信息。
- JVM 捕获异常需要异常表
    - 每个方法都有一个异常表，异常表中的每一个条目都代表一个异常处理器，并且由 from、to、target 指针及其异常类型所构成。form-to 其实就是 try 块，而 target 就是 catch 的起始位置。
    - 当程序触发异常时，JVM 会检测触发异常的字节码的索引值落到哪个异常表的 from-to 范围内，然后再判断异常类型是否匹配，匹配就开始执行 target 处字节码处理该异常。
- 最后是finally代码块的编译
    - finally 代码块一定会运行的（除非虚拟机退出了）。那么它是如何实现的呢？其实是一个比较笨的办法，当前 JVM 的做法是，复制 finally 代码块的内容，分别放在所有可能的执行路径的出口中。
- 如何理解Java函数调用栈桢呢
    - 操作系统给每个线程分配了一块独立的内存空间，这块内存被组织成"栈"这种结构, 用来存储函数调用时的临时变量。每进入一个函数，就会将临时变量作为一个栈帧入栈，当被调用函数执行完成，返回之后，将这个函数对应的栈帧出栈。
    ```
    int main() {
       int a = 1; 
       int ret = 0;
       int res = 0;
       ret = add(3, 5);
       res = a + ret;
       printf("%d", res);
       reuturn 0;
    }
    
    int add(int x, int y) {
       int sum = 0;
       sum = x + y;
       return sum;
    }
    ```
    - 从代码中我们可以看出，main() 函数调用了 add() 函数，获取计算结果，并且与临时变量 a 相加，最后打印 res 的值。

### 4.3 实现相同异常次数统计
- 大概的思路如下所示
    - 每一次发生崩溃时，拿到异常Throwable，然后获取它的堆栈信息，转化为字符串后再md5一下得到一个key。
    - 每一次存储的时候，获取之前的【如果之前没有则是0】次数加一
- 注意问题点：关键是怎么判断两个崩溃是同一个？
    - 举一个例子：Integer.parseInt("12.3") 和 Integer.parseInt("12.4") 它们都是 NumberFormatException 异常，但却是不同的。获取堆栈再md5一下即可保证key唯一
- 崩溃聚合的工业级设计方案
    ```
    崩溃聚合算法的三种策略及适用场景：
    
    策略1: 堆栈完全MD5（当前方案）
    ├─ 原理: 完整堆栈字符串 → MD5 → 作为唯一标识
    ├─ 优点: 实现简单
    └─ 缺点: 行号变化（版本更新）会导致同一问题被识别为不同崩溃
    
    策略2: Top-N帧聚合（推荐）
    ├─ 原理: 取堆栈顶部3-5帧的类名+方法名（忽略行号）→ MD5
    ├─ 优点: 跨版本聚合能力强
    └─ 实现: hash(ExceptionType + frame[0].class + frame[0].method + ... + frame[N])
    
    策略3: 智能归类（高级）
    ├─ 原理: 过滤系统帧，只保留业务帧进行聚合
    ├─ 优点: 不同调用路径触发的同一Bug可合并
    └─ 实现: 配置业务包名前缀白名单，仅对白名单内的帧参与hash
    ```
- 统计存储的实现要点
    ```java
    // 崩溃指纹提取（Top-3帧聚合策略）
    private String generateCrashFingerprint(Throwable e) {
        StringBuilder sb = new StringBuilder();
        sb.append(e.getClass().getName()); // 异常类型
        StackTraceElement[] stack = e.getStackTrace();
        int depth = Math.min(3, stack.length); // 取顶部3帧
        for (int i = 0; i < depth; i++) {
            sb.append(stack[i].getClassName())
              .append(stack[i].getMethodName());
            // 注意：不包含行号，保证跨版本聚合
        }
        return md5(sb.toString());
    }
    ```



### 4.4 崩溃日志收集
**收集崩溃信息**
- 从崩溃的基本信息，可以对崩溃有初步的判断。
    - 进程名、线程名。崩溃的进程是前台进程还是后台进程，崩溃是不是发生在 UI 线程。
    - 崩溃堆栈和类型。崩溃是属于 Java 崩溃、Native 崩溃，还是 ANR，对于不同类型的崩溃我们关注的点也不太一样。特别需要看崩溃堆栈的栈顶，看具体崩溃在系统的代码，还是我们自己的代码里面。
- 收集崩溃时的系统信息
    - 机型、系统、厂商、CPU、ABI、Linux 版本等。（寻找共性）
    - `Logcat`。（包括应用、系统的运行日志，其中会记录 App 运行的一些基本情况）
    - 设备状态：是否 root、是否是模拟器。一些问题是由 Xposed 或多开软件造成，对这部分问题我们要区别对待。
- 收集崩溃时的内存信息（OOM、ANR、虚拟内存耗尽等，很多崩溃都跟内存有直接关系）
    - 系统剩余内存。（系统可用内存很小 – 低于 MemTotal 的 10%时，OOM、大量 GC、系统频繁自杀拉起等问题都非常容易出现）
    - 虚拟内存（但是很多类似OOM、tgkill 等问题都是虚拟内存不足导致的）
    - 应用使用内存（得出应用本身内存的占用大小和分布）
- 资源信息
    - 有的时候我们会发现应用堆内存和设备内存都非常充足，还是会出现内存分配失败的情况，这跟资源泄漏可能有比较大的关系。
    - 文件句柄 `fd`。一般单个进程允许打开的最大文件句柄个数为 1024。但是如果文件句柄超过 800 个就比较危险，需要将所有的 fd 以及对应的文件名输出到日志中，进一步排查是否出现了有文件或者线程的泄漏
    - 线程数。一个线程可能就占 2MB 的虚拟内存，过多的线程会对虚拟内存和文件句柄带来压力。根据我的经验来说，如果线程数超过 400 个就比较危险。需要将所有的线程 id 以及对应的线程名输出到日志中，进一步排查是否出现了线程相关的问题。
- 收集崩溃时的应用信息
    - 崩溃场景（崩溃发生在哪个 Activity 或 Fragment，发生在哪个业务中）
    - 关键操作路径（记录关键的用户操作路径，这对我们复现崩溃会有比较大的帮助）
    - 其他自定义信息（不同应用关心的重点不一样。例如运行时间、是否加载了补丁、是否是全新安装或升级等）

## 05.Native异常捕获
### 5.1 Native崩溃日志组成
- 设备指纹
    - 用于记录设备相关信息
- Revision
    - Revision 指的是硬件，而不是软件。通常情况下不使用 revision，但使用 revision 有助于您自动忽略由不良硬件导致的已知错误
- ABI
    - ABI 是 arm、arm64、mips、mips64、x86 或 x86-64 之一，记录该值主要用于后续对信息分析时区分使用什么工具链
- 进程相关信息
    - 包括进程号、进程名称
- 错误信号
    - 接收的信号 (这里是SIGABRT) 以及有关如何接收该信号的更多信息 (这里是SI_TKILL)
- 中断消息
    - 并非所有崩溃问题都会有中止消息行，但发生中止时，会出现该消息行。这是从此 pid/tid 的最后一行严重 logcat 输出中自动收集而来的，而在有意中止的情况下，这可以解释该程序自行终止的原因
- 寄存器信息
    - 展示所有寄存器中的内容，这些内容的有用程度取决于确切的崩溃问题
- 调用栈
    - crash函数调用栈


### 5.2 捕获native异常
- Linux信号机制如何处理崩溃
    - 所有的崩溃都是编程错误或者硬件错误相关的，系统遇到不可恢复的错误时会触发崩溃机制让程序退出，如除零、段地址错误等。
    - 异常发生时，CPU通过异常中断的方式，触发异常处理流程，不同的处理器有不同的异常中断类型和中断处理方式。
    - Linux把这些中断处理统一为信号量，可以注册信号量向量进行处理。
    - 既然 Android 系统也是基于 Linux 的，那么我们可以利用 Linux 的信号机制进行异常捕获。
- 在Linux系统中，当发生异常时，内核会以信号机制通知进程，收到信号后，进程可以有以下三种处理方案：
    - 忽略信号。对该信号不做任何处理，就像未发生过一样；
    - 使用系统默认操作。这种缺省操作对大部分的信号是使进程终止；
    - 指定处理函数处理。类似中断的处理程序，对于需要处理的信号，进程可以指定处理函数；
- 那么以什么方处理native异常
    - 需要自己指定信号处理函数捕捉信号




### 5.3 注册信号处理函数
- 如何使用指定的信号处理函数
    - 进程通过 sigaction() 函数来指定对某个信号的处理行为。
    ```
    #include <signal.h>
    int sigaction(int sig, const struct sigaction* new_action, struct sigaction* old_action);
    ```




### 5.4 获取native异常信息

- 获取native异常信息的核心流程
  - 在信号处理函数中，可以通过`siginfo_t`结构体获取到信号编号（si_signo）、错误码（si_errno）、发送信号的进程ID（si_pid）等基本信息。
  - 通过`ucontext_t`上下文结构体，可以获取到崩溃时的寄存器状态（如PC指针、SP指针等），这些信息对于定位崩溃位置至关重要。
- 获取native调用栈
  - 使用`libunwind`库或`_Unwind_Backtrace`函数来遍历调用栈帧，获取每一层函数的返回地址。
  - 通过`dladdr`函数将返回地址转换为对应的共享库名称和符号偏移量，从而得到可读的调用栈信息。
  - Google的Breakpad采用了更安全的方式：在信号处理函数中fork子进程，由子进程通过ptrace读取父进程的内存和寄存器来构建调用栈。


### 5.5 写native异常到文件

- 在信号处理函数中写文件的注意事项
  - 信号处理函数中只能调用"异步信号安全"（async-signal-safe）的函数。常见的如`open`、`write`、`close`等系统调用是安全的，但`malloc`、`printf`、`fopen`等则不安全。
  - 为了确保能够成功写入文件，应该预先打开文件句柄（fd），在信号处理函数中直接使用该fd写入数据。
- 写入的信息内容
  - 崩溃信号信息（信号类型、错误码等）
  - 寄存器快照（所有通用寄存器的值）
  - 调用栈信息（每一帧的地址、库名、偏移量）
  - 线程信息（崩溃线程ID、所有线程列表）
  - 内存映射信息（/proc/self/maps的内容，用于后续符号化）

### 5.6 异常抛到Java层

- 为什么要将native异常抛到Java层
  - Java层有更完善的日志上报体系和网络上传能力，将native异常信息传递到Java层可以复用已有的崩溃上报通道。
- 实现方式
  - 在信号处理函数中，通过JNI调用Java层的方法。但需要注意，崩溃时JNI环境可能已经不稳定，因此通常的做法是：
  - 1.在信号处理函数中将崩溃信息写入文件
  - 2.在应用下次启动时，检查是否存在未上报的native崩溃日志文件
  - 3.如果存在，读取文件内容通过Java层的上报通道上传到服务端
  - 这种"延迟上报"的方式更加可靠，避免了在崩溃现场调用JNI的风险。


### 5.7 Native信号机制
- 当native 层发生异常的时候，往往是通过信号的方式发送，给相对应的信号处理器处理
  - 发生异常----->发送signal信号----->主进程
- 可以从signal.h看到，大概已经定义的信号有
  - signal1，signal2，signal3，signal4，signal5，signal6，……，signal31
- 常见的崩溃信号及其含义
  - SIGSEGV（11）：段错误，访问了无效的内存地址，是最常见的native崩溃信号。常见原因包括空指针解引用、数组越界、使用已释放的内存。
  - SIGABRT（6）：程序主动调用abort()函数触发，通常由assert失败、调用了C++的纯虚函数、double free等情况引起。
  - SIGBUS（7）：总线错误，通常由于内存对齐问题或访问了不存在的物理地址引起。
  - SIGFPE（8）：浮点异常，如除以零操作。
  - SIGILL（4）：非法指令，CPU尝试执行了一条无法识别的指令。
  - SIGPIPE（13）：管道破裂，向一个已关闭的Socket写入数据时触发。
- 疑惑：为什么不直接用try-catch来捕获native异常？
  - 答疑：C/C++的异常机制（try-catch）只能捕获C++层面的异常（如throw），无法捕获操作系统级别的信号。段错误、非法指令等是由CPU硬件检测并通过中断机制通知操作系统的，操作系统再以信号的形式传递给进程，因此必须使用信号处理机制来捕获。





## 06.崩溃信息收集
### 6.1 Native崩溃入口
- 在java环境中，如果程序出现了不可预期的crash（即没有捕获），就会往上抛出给最终的线程UncaughtExceptionHandler
- native 层的crash大多数是"不可恢复"的，比如某个内存方面的错误，这些往往是不可处理的，需要中断当前进程。
- 对比Java层和Native层的异常处理差异
  - Java层异常有完善的try-catch机制和UncaughtExceptionHandler兜底，可以获取完整的堆栈信息。
  - Native层异常通过信号机制传递，获取调用栈需要借助libunwind等工具，且在崩溃现场操作受到async-signal-safe的限制。



### 6.2 跨平台崩溃监听

- 跨平台崩溃监听对比
  - iOS中使用NSSetUncaughtExceptionHandler设置OC层异常处理器，使用signal注册信号处理函数捕获Mach异常和Unix信号。
  - Web端使用window.onerror和window.addEventListener('unhandledrejection')捕获未处理的异常和Promise rejection。



### 6.3 Native捕获难点
- 最核心的是怎么样保证客户端在各种极端情况下依然可以生成崩溃日志。
  - 因为在崩溃时，程序会处于一个不安全的状态，如果处理不当，非常容易发生二次崩溃。那么，生成崩溃日志时会有哪些比较棘手的情况呢？
- 情况一：文件句柄泄漏，导致创建日志文件失败，怎么办？
  - 应对方式：我们需要提前申请文件句柄 fd 预留，防止出现这种情况。
- 情况二：因为栈溢出了，导致日志生成失败，怎么办？
  - 应对方式：为了防止栈溢出导致进程没有空间创建调用栈执行处理函数，我们通常会使用常见的 signalstack。在一些特殊情况，我们可能还需要直接替换当前栈，所以这里也需要在堆中预留部分空间。
- 情况三：整个堆的内存都耗尽了，导致日志生成失败，怎么办？
  - 应对方式：这个时候我们无法安全地分配内存，也不敢使用 stl 或者 libc 的函数，因为它们内部实现会分配堆内存。这个时候如果继续分配内存，会导致出现堆破坏或者二次崩溃的情况。Breakpad 做的比较彻底，重新封装了Linux Syscall Support，来避免直接调用 libc。
- 情况四：堆破坏或二次崩溃导致日志生成失败，怎么办？
  - 应对方式：Breakpad 会从原进程 fork 出子进程去收集崩溃现场，此外涉及与 Java 相关的，一般也会用子进程去操作。这样即使出现二次崩溃，只是这部分的信息丢失，我们的父进程后面还可以继续获取其他的信息。在一些特殊的情况，我们还可能需要从子进程 fork 出孙进程。




### 6.4 完整的流程
- 完整的 Native 崩溃从捕获到解析的流程：
  - 编译端。编译 C/C++ 代码时，需要将带符号信息的文件保留下来
  - 客户端。捕获到崩溃时候，将收集到尽可能多的有用信息写入日志文件，然后选择合适的时机上传到服务器。
  - 服务端。读取客户端上报的日志文件，寻找适合的符号文件，生成可读的 C/C++ 调用栈。
- Native崩溃处理完整流程图
    ```
    ┌─ 编译端 ─────────────────────────────────────────────┐
    │  gcc -g → ELF(带DWARF调试信息)                        │
    │     │                                                  │
    │     ├─ strip → .so (发布版，去除符号)                   │
    │     └─ 保留 → .so.sym (符号文件，用于还原堆栈)         │
    │                                                        │
    │  NDK编译时：                                           │
    │  obj/local/<abi>/ 下有未strip的.so → 务必保留!         │
    └────────────────────────────────────────────────────────┘
                          │
                          ▼
    ┌─ 客户端 ─────────────────────────────────────────────┐
    │  1. 信号处理函数被触发（SIGSEGV等）                     │
    │  2. fork子进程（避免主进程不安全操作）                   │
    │  3. 子进程中收集信息：                                  │
    │     ├─ 寄存器状态（ucontext_t）                        │
    │     ├─ 调用栈回溯（unwind）                            │
    │     ├─ 内存映射（/proc/self/maps）                     │
    │     ├─ 线程列表和各线程栈                              │
    │     └─ logcat最近日志                                  │
    │  4. 写入minidump文件                                   │
    │  5. 下次启动时上传（崩溃时不上传，不安全）              │
    └────────────────────────────────────────────────────────┘
                          │
                          ▼
    ┌─ 服务端 ─────────────────────────────────────────────┐
    │  1. 接收minidump + 匹配符号文件（通过Build ID）        │
    │  2. addr2line / ndk-stack 符号化                       │
    │     0x7f8a2b3c → libapp.so!CrashFunction(main.cpp:42)│
    │  3. 堆栈聚合 → 生成Issue                              │
    │  4. 告警 → 分发 → 修复                                │
    └────────────────────────────────────────────────────────┘
    ```
- 符号化是整个链路的关键环节：每次发版都必须保留对应版本的符号文件，否则线上崩溃将无法还原为可读的源码位置。建议在CI/CD流程中自动上传符号文件到崩溃分析平台





## 07.崩溃捕获设计哲学

### 7.1 分层防御的设计思想
- 崩溃捕获系统的设计遵循分层防御的思想
  - 第一层：Java层UncaughtExceptionHandler，捕获所有未处理的Java异常，这是最基础也是最可靠的防线。
  - 第二层：Native层信号处理函数，捕获C/C++代码中的崩溃信号，如段错误、非法指令等。
  - 第三层：ANR监控，通过FileObserver监听/data/anr/traces.txt的变化，或通过Looper消息处理超时来检测ANR。
  - 每一层都独立工作，互不干扰，确保任何类型的异常都不会遗漏。

### 7.2 崩溃日志的完整性保障
- 在极端条件下保证日志可用
  - 预分配资源：预先申请文件句柄和内存缓冲区，避免崩溃时无法申请新资源。
  - 子进程收集：fork子进程进行数据收集，即使子进程二次崩溃也不影响主进程日志写入。
  - 最小化依赖：崩溃处理代码不依赖第三方库，不调用可能分配堆内存的函数，只使用async-signal-safe的系统调用。
  - 延迟上报：崩溃现场只负责写入文件，上报逻辑在下次启动时执行，确保网络IO不会阻塞崩溃处理流程。

### 7.3 崩溃捕获的信号安全问题

**疑惑**：为什么Native崩溃处理函数不能调用malloc、printf等常见函数？

**答疑**：信号处理函数运行在被中断线程的上下文中，此时进程可能处于不一致状态。如果被中断的线程正在执行malloc（持有堆锁），信号处理函数再调用malloc会导致死锁。

**论证**：

POSIX标准定义了一组async-signal-safe函数，只有这些函数可以在信号处理函数中安全调用：

```
// async-signal-safe的函数（部分列举）
write()          // 可以安全写入文件
open() / close() // 可以安全操作文件描述符
fork()           // 可以安全创建子进程
_exit()          // 可以安全退出进程
signal()         // 可以安全修改信号处理
getpid()         // 可以安全获取进程ID

// 不安全的函数（绝对不能在信号处理中调用）
malloc() / free()   // 可能死锁（堆锁）
printf() / fprintf()// 内部使用malloc和锁
new / delete        // C++内存分配
pthread_mutex_lock()// 可能死锁
```

最佳实践是在信号处理函数中只做最小化的工作——写入预分配的缓冲区，然后通过管道通知子进程进行详细的信息收集：

```c
// 崩溃处理的信号安全实现伪代码
static int g_crash_pipe[2];            // 预分配的管道
static char g_buffer[4096];            // 预分配的缓冲区
static struct crash_info g_crash_data; // 预分配的崩溃信息结构

void signal_handler(int sig, siginfo_t *info, void *context) {
    // 1. 只使用async-signal-safe函数
    g_crash_data.signal = sig;
    g_crash_data.fault_addr = info->si_addr;
    g_crash_data.tid = gettid();
    
    // 2. 通过预分配的管道通知子进程
    write(g_crash_pipe[1], &g_crash_data, sizeof(g_crash_data));
    
    // 3. 等待子进程完成收集（带超时）
    // 使用预分配缓冲区读取确认
    read(g_crash_pipe[0], g_buffer, 1);
    
    // 4. 恢复默认信号处理并重新触发
    signal(sig, SIG_DFL);
    raise(sig);
}
```

**结果**：崩溃处理函数必须严格遵循信号安全约束。违反此约束可能导致崩溃处理本身死锁，用户将看到应用卡死而非正常的崩溃退出，同时丢失宝贵的崩溃日志。


## 08.跨平台崩溃捕获实践

### 8.1 iOS崩溃捕获方案

iOS的崩溃捕获需要覆盖三个层面：OC异常、Mach异常、Unix信号。

**疑惑**：iOS为什么需要同时捕获Mach异常和Unix信号？只捕获一种不够吗？

**答疑**：Mach异常是macOS/iOS内核级别的异常机制，Unix信号是POSIX层面的。某些崩溃（如EXC_GUARD）只能通过Mach异常捕获，而某些信号（如SIGABRT）在Mach层不易直接拦截。双重覆盖才能确保不遗漏。

**论证**：

```
iOS崩溃传递链路：
硬件异常 → Mach异常（内核态） → Unix信号（用户态） → 进程终止

┌──────────────┐
│  硬件/内核异常  │  例如：访问非法地址、除零
└──────┬───────┘
       ▼
┌──────────────┐
│  Mach Exception │  内核通过exception port发送消息
│  EXC_BAD_ACCESS  │  最早可以拦截的层级
└──────┬───────┘
       ▼
┌──────────────┐
│  Unix Signal    │  内核将Mach异常转换为对应信号
│  SIGSEGV/SIGBUS │  用户态信号处理函数
└──────┬───────┘
       ▼
┌──────────────┐
│  进程终止       │  默认行为：产生Core Dump并退出
└──────────────┘
```

iOS崩溃捕获完整伪代码：

```objectivec
// iOS崩溃捕获管理器
@interface IOSCrashMonitor : NSObject
@property (nonatomic, strong) NSString *crashLogPath;
@end

@implementation IOSCrashMonitor

- (void)startMonitoring {
    // 第一层：OC未捕获异常
    NSSetUncaughtExceptionHandler(&handleOCException);
    
    // 第二层：Unix信号捕获
    struct sigaction action;
    action.sa_sigaction = handleSignal;
    action.sa_flags = SA_SIGINFO | SA_ONSTACK;
    sigemptyset(&action.sa_mask);
    
    // 注册需要捕获的信号
    sigaction(SIGABRT, &action, NULL);  // abort调用
    sigaction(SIGSEGV, &action, NULL);  // 段错误
    sigaction(SIGBUS,  &action, NULL);  // 总线错误
    sigaction(SIGFPE,  &action, NULL);  // 浮点异常
    sigaction(SIGILL,  &action, NULL);  // 非法指令
    sigaction(SIGTRAP, &action, NULL);  // 断点陷阱
    sigaction(SIGPIPE, &action, NULL);  // 管道破裂
    
    // 第三层：Mach异常捕获（需要独立线程）
    [self setupMachExceptionHandler];
}

// OC异常处理函数
static void handleOCException(NSException *exception) {
    // 获取异常信息
    NSString *name = exception.name;
    NSString *reason = exception.reason;
    NSArray *callStack = exception.callStackSymbols;
    
    // 收集设备信息
    NSMutableDictionary *crashInfo = [NSMutableDictionary dictionary];
    crashInfo[@"type"] = @"OC_Exception";
    crashInfo[@"name"] = name;
    crashInfo[@"reason"] = reason;
    crashInfo[@"callStack"] = callStack;
    crashInfo[@"timestamp"] = @([[NSDate date] timeIntervalSince1970]);
    
    // 写入文件（使用C函数确保安全）
    NSData *data = [NSJSONSerialization dataWithJSONObject:crashInfo 
                                                   options:0 error:nil];
    [data writeToFile:getCrashLogPath() atomically:YES];
}

// Unix信号处理函数
static void handleSignal(int signal, siginfo_t *info, void *context) {
    // 获取崩溃上下文
    ucontext_t *ucontext = (ucontext_t *)context;
    
    // 收集寄存器信息（ARM64架构）
    // ucontext->uc_mcontext->__ss.__pc  程序计数器
    // ucontext->uc_mcontext->__ss.__lr  链接寄存器
    // ucontext->uc_mcontext->__ss.__fp  帧指针
    
    // 收集调用栈（使用backtrace，注意：不完全signal-safe）
    void *frames[128];
    int frameCount = backtrace(frames, 128);
    
    // 将崩溃信息写入预分配的缓冲区
    // ... 写入信号编号、故障地址、寄存器、调用栈
    
    // 恢复默认处理并重新触发
    signal(signal, SIG_DFL);
    raise(signal);
}

// Mach异常处理（独立线程监听exception port）
- (void)setupMachExceptionHandler {
    dispatch_async(dispatch_get_global_queue(DISPATCH_QUEUE_PRIORITY_HIGH, 0), ^{
        mach_port_t exceptionPort;
        // 分配异常端口
        mach_port_allocate(mach_task_self(), MACH_PORT_RIGHT_RECEIVE, &exceptionPort);
        mach_port_insert_right(mach_task_self(), exceptionPort, exceptionPort, 
                              MACH_MSG_TYPE_MAKE_SEND);
        
        // 设置异常端口
        task_set_exception_ports(mach_task_self(),
            EXC_MASK_BAD_ACCESS | EXC_MASK_BAD_INSTRUCTION | EXC_MASK_ARITHMETIC,
            exceptionPort,
            EXCEPTION_DEFAULT | MACH_EXCEPTION_CODES,
            THREAD_STATE_NONE);
        
        // 循环等待异常消息
        while (YES) {
            // mach_msg接收异常消息
            // 解析异常类型和线程信息
            // 收集崩溃日志
            // 转发给之前的异常处理器
        }
    });
}

@end
```

### 8.2 iOS OOM检测方案

**疑惑**：iOS的OOM不会产生崩溃日志，如何检测它？

**答疑**：iOS OOM检测使用"排除法"——如果上次退出不是正常退出、不是崩溃、不是系统强杀，那就是OOM。

**论证**：

```objectivec
// iOS OOM排除法检测伪代码
@interface OOMDetector : NSObject
@end

@implementation OOMDetector

// 启动时检查上次退出原因
- (void)checkLastExitReason {
    BOOL lastTimeDidCrash = [self didCrashLastTime];        // 有崩溃日志？
    BOOL lastTimeWasUpgrade = [self wasAppUpgraded];         // 版本升级了？
    BOOL lastTimeWasTerminated = [self wasTerminatedBySystem]; // 系统终止？
    BOOL lastTimeDidExit = [self didExitNormally];           // 正常退出？
    
    if (!lastTimeDidCrash && !lastTimeWasUpgrade && 
        !lastTimeWasTerminated && !lastTimeDidExit) {
        // 排除所有已知退出原因后，判定为OOM
        BOOL wasForeground = [self wasForegroundLastTime];
        if (wasForeground) {
            [self reportForegroundOOM];  // 前台OOM（FOOM）
        } else {
            [self reportBackgroundOOM];  // 后台OOM（BOOM）
        }
    }
}

// 通过内存水位辅助判断
- (void)startMemoryMonitoring {
    // 定期记录内存水位
    [NSTimer scheduledTimerWithTimeInterval:1.0 repeats:YES block:^(NSTimer *timer) {
        task_vm_info_data_t vmInfo;
        mach_msg_type_number_t count = TASK_VM_INFO_COUNT;
        task_info(mach_task_self(), TASK_VM_INFO, (task_info_t)&vmInfo, &count);
        
        uint64_t usedMemory = vmInfo.phys_footprint;  // 物理内存占用
        uint64_t memoryLimit = os_proc_available_memory();  // 可用内存（iOS 13+）
        
        // 记录到本地，崩溃后用于分析
        [self recordMemoryWatermark:usedMemory limit:memoryLimit];
        
        // 内存接近阈值时触发紧急dump
        if (memoryLimit < 50 * 1024 * 1024) {  // 可用内存低于50MB
            [self emergencyMemoryDump];
        }
    }];
}

@end
```

### 8.3 Web端崩溃捕获方案

Web端的"崩溃"与Native端有本质区别——JavaScript是解释执行的，不存在段错误等硬件异常。Web端需要捕获的是：JS运行时错误、Promise未处理拒绝、资源加载失败、页面崩溃（如内存溢出导致标签页崩溃）。

```javascript
// Web端崩溃监控完整方案
class WebCrashMonitor {
    constructor() {
        this.crashLog = [];
        this.heartbeatTimer = null;
    }
    
    startMonitoring() {
        this.setupJSErrorCapture();
        this.setupPromiseCapture();
        this.setupResourceErrorCapture();
        this.setupPageCrashDetection();
        this.setupPerformanceMonitoring();
    }
    
    // 1. 全局JS错误捕获
    setupJSErrorCapture() {
        window.onerror = (message, source, lineno, colno, error) => {
            const crashInfo = {
                type: 'js_error',
                message: message,
                source: source,
                line: lineno,
                column: colno,
                stack: error ? error.stack : 'N/A',
                timestamp: Date.now(),
                url: location.href,
                userAgent: navigator.userAgent
            };
            this.reportCrash(crashInfo);
            return false;  // 不阻止默认错误处理
        };
    }
    
    // 2. Promise未处理拒绝捕获
    setupPromiseCapture() {
        window.addEventListener('unhandledrejection', (event) => {
            const crashInfo = {
                type: 'unhandled_promise',
                reason: event.reason instanceof Error 
                    ? event.reason.stack 
                    : String(event.reason),
                timestamp: Date.now(),
                url: location.href
            };
            this.reportCrash(crashInfo);
        });
    }
    
    // 3. 资源加载失败捕获
    setupResourceErrorCapture() {
        window.addEventListener('error', (event) => {
            if (event.target && (event.target.src || event.target.href)) {
                const crashInfo = {
                    type: 'resource_error',
                    tagName: event.target.tagName,
                    resourceUrl: event.target.src || event.target.href,
                    timestamp: Date.now()
                };
                this.reportCrash(crashInfo);
            }
        }, true);  // 注意：必须使用捕获阶段
    }
    
    // 4. 页面崩溃检测（基于Service Worker心跳）
    setupPageCrashDetection() {
        // 方案一：Service Worker心跳检测
        if ('serviceWorker' in navigator) {
            // 页面定期向SW发送心跳
            this.heartbeatTimer = setInterval(() => {
                navigator.serviceWorker.controller?.postMessage({
                    type: 'heartbeat',
                    timestamp: Date.now()
                });
            }, 5000);
            
            // 页面正常卸载时通知SW
            window.addEventListener('beforeunload', () => {
                navigator.serviceWorker.controller?.postMessage({
                    type: 'page_unload'
                });
            });
        }
        
        // 方案二：基于sessionStorage的崩溃检测
        // 页面加载时检查上次是否正常退出
        const lastState = sessionStorage.getItem('page_state');
        if (lastState === 'active') {
            // 上次没有正常卸载，可能是崩溃
            this.reportCrash({
                type: 'page_crash',
                message: '上次页面异常退出（可能是崩溃或内存溢出）',
                timestamp: Date.now()
            });
        }
        sessionStorage.setItem('page_state', 'active');
        
        window.addEventListener('beforeunload', () => {
            sessionStorage.setItem('page_state', 'closed');
        });
    }
    
    // 5. 性能相关崩溃监控
    setupPerformanceMonitoring() {
        // 监控长任务（可能导致页面无响应）
        if (typeof PerformanceObserver !== 'undefined') {
            const observer = new PerformanceObserver((list) => {
                for (const entry of list.getEntries()) {
                    if (entry.duration > 5000) {  // 超过5秒的长任务
                        this.reportCrash({
                            type: 'long_task_warning',
                            duration: entry.duration,
                            timestamp: Date.now()
                        });
                    }
                }
            });
            observer.observe({ entryTypes: ['longtask'] });
        }
        
        // 监控内存使用（仅Chrome）
        if (performance.memory) {
            setInterval(() => {
                const memInfo = performance.memory;
                const usage = memInfo.usedJSHeapSize / memInfo.jsHeapSizeLimit;
                if (usage > 0.9) {  // 内存使用超过90%
                    this.reportCrash({
                        type: 'memory_warning',
                        usedHeap: memInfo.usedJSHeapSize,
                        heapLimit: memInfo.jsHeapSizeLimit,
                        usageRatio: usage,
                        timestamp: Date.now()
                    });
                }
            }, 10000);
        }
    }
    
    reportCrash(crashInfo) {
        // 添加公共信息
        crashInfo.sessionId = this.getSessionId();
        crashInfo.pageLoadTime = performance.timing.loadEventEnd - 
                                 performance.timing.navigationStart;
        
        // 使用Beacon API发送（页面关闭时也能发送成功）
        if (navigator.sendBeacon) {
            navigator.sendBeacon('/api/crash-report', JSON.stringify(crashInfo));
        } else {
            // 降级方案：同步XHR（仅在页面卸载时使用）
            const xhr = new XMLHttpRequest();
            xhr.open('POST', '/api/crash-report', false);
            xhr.send(JSON.stringify(crashInfo));
        }
    }
}
```

## 09.崩溃捕获设计总结

### 9.1 跨平台崩溃捕获对比

| 维度 | Android | iOS | Web |
|------|---------|-----|-----|
| Java/OC层 | UncaughtExceptionHandler | NSSetUncaughtExceptionHandler | window.onerror |
| Native层 | sigaction信号处理 | sigaction + Mach异常端口 | 不适用 |
| ANR/卡死 | FileObserver/Looper监控 | Watchdog线程 | Long Task API |
| OOM检测 | 内存水位监控+hprof dump | 排除法检测 | performance.memory |
| 符号化 | R8/ProGuard mapping + addr2line | dSYM符号表 + atos | SourceMap |
| 崩溃上报 | 下次启动上报 | 下次启动上报 | Beacon API即时上报 |
| 开源方案 | xCrash/Bugly | KSCrash/PLCrashReporter | Sentry/TraceKit |

### 9.2 崩溃捕获的核心原则

- **完整性**：覆盖所有崩溃类型，不留盲区。Java/OC异常、Native崩溃、ANR/卡死、OOM每一种都需要专门的捕获手段。
- **可靠性**：崩溃处理代码本身不能崩溃。预分配资源、信号安全函数、子进程隔离是三大保障手段。
- **低侵入**：崩溃监控不应影响正常业务性能。信号处理函数只做最少工作，详细收集放在子进程。
- **可分析**：崩溃日志要包含足够的上下文——线程堆栈、寄存器状态、内存信息、设备环境，才能支撑高效的问题定位。




## 10.崩溃分析三部曲
### 10.1 确定重点
- 确认和分析重点，关键在于在日志中找到重要的信息，对问题有一个大致判断。
    - 1.确认严重程度。解决崩溃也要看性价比，我们优先解决 Top 崩溃或者对业务有重大影响，例如启动、支付过程的崩溃。
    - 2.崩溃基本信息。确定崩溃的类型以及异常描述，对崩溃有大致的判断。
    - 3.各个资源情况。结合崩溃的基本信息，接着看看是不是跟 "内存信息" 有关，是不是跟"资源信息"有关。比如是物理内存不足、虚拟内存不足，还是文件句柄 fd 泄漏了。


### 10.2 查找共性
- 如果使用了上面的方法还是不能有效定位问题，我们可以尝试查找这类崩溃有没有什么共性。
    - 机型、系统、ROM、厂商、ABI，这些采集到的系统信息都可以作为维度聚合，找到了共性，可以对你下一步复现问题有更明确的指引。
- 崩溃堆栈的聚合策略
    - 相同崩溃的聚合是崩溃分析平台的核心能力。聚合的关键在于如何定义"相同"：通常以崩溃类型+顶部N帧堆栈（去除混淆影响后）作为聚合key。
    - 聚合后的崩溃需要展示：影响的UV数、PV数、首次出现时间、最后出现时间、影响的版本分布、设备分布等信息。


### 10.3 尝试复现
- "只要能本地复现，我就能解"，相信这是很多开发跟测试说过的话。
    - 有这样的底气主要是因为在稳定的复现路径上面，可以采用增加日志或使用 Debugger、GDB 等各种各样的手段或工具做进一步分析。
- 崩溃信息采集的完整性
    - 一份完整的崩溃信息应该包含：崩溃堆栈（包括Java堆栈和Native堆栈）、设备信息（型号、系统版本、CPU架构）、App信息（版本号、渠道、构建时间）、内存信息（堆内存使用情况、可用物理内存）、磁盘信息（可用存储空间）、网络信息（网络类型、是否联网）、用户操作路径（崩溃前的页面跳转和操作记录）、线程信息（所有线程的堆栈信息）。
    - 越完整的崩溃信息，越有利于问题定位。很多时候崩溃堆栈本身不能说明问题（如OOM的堆栈通常不是真正的泄漏点），需要借助上下文信息来分析。



## 11.Crash常见治理
### 11.1 常见Crash分类
- 常规Crash发生的原因主要是由于开发人员编写代码不小心导致的。
    - 解决这类Crash需要由点到面，根据Crash引发的原因和业务本身，统一集中解决。
- 常见的Crash类型包括：
    - 空节点、角标越界、类型转换异常、实体对象没有序列化、数字转换异常、Activity或Service找不到等。
    - 这类Crash是App中最为常见的Crash，也是最容易反复出现的。在获取Crash堆栈信息后，解决这类Crash一般比较简单，**更多考虑的应该是如何避免**。


### 11.2 空指针崩溃问题
- NullPointerException是遇到最频繁的，造成这种Crash一般有两种情况：
    - 对象本身没有进行初始化就进行操作；对象已经初始化过，但是被回收或者手动置为null，然后对其进行操作。
- 针对第一种情况导致的原因有很多，可能是开发人员的失误、API返回数据解析异常、进程被杀死后静态变量没初始化导致，我们可以做的有：
    - 对可能为空的对象做判空处理；养成使用@NonNull和@Nullable注解的习惯；如果是kotlin避免使用!!；尽量不使用静态变量存储跨页面数据。
- 针对第二种情况大部分是由于Activity/Fragment销毁或被移除后，在Message、Runnable、网络等回调中执行了一些代码导致的，可以做的有：
    - 1.Message、Runnable回调时，判断Activity/Fragment是否销毁或被移除；加try-catch保护；Activity/Fragment销毁时移除所有已发送的Runnable。
    - 2.封装LifecycleMessage/Runnable基础组件，并自定义Lint检查，提示使用封装好的基础组件。在BaseActivity、BaseFragment的onDestroy()里把当前Activity所发的所有请求取消掉。
    - 3.针对Fragment中onActivityResult回调，处理data偶发空指针(原因是activity异常生命周期导致data可能为空)，增加非空判断。


### 11.3 索引越界异常
- 这类Crash常见于对RecyclerView的操作和多线程下对容器的操作。
    - 针对RecyclerView中造成的IndexOutOfBoundsException，经常是因为外部也持有了Adapter里数据的引用(如在Adapter的构造函数里直接赋值)，这时如果外部引用对数据更改了，但没有及时调用notifyDataSetChanged()，则有可能造成Crash。
    - 对此我们封装了一个BaseAdapter，数据统一由Adapter自己维护通知，这两类Crash目前得到了统一的解决。
- 注意有些容器是线程不安全的
    - 所以如果在多线程下对其操作就容易引发IndexOutOfBoundsException。常用的如JDK里的ArrayList和Android里的SparseArray、ArrayMap，同时也要注意有一些类的内部实现也是用的线程不安全的容器，如Bundle里用的就是ArrayMap。
- 线程安全容器的选择
    - 如果需要线程安全的List，使用CopyOnWriteArrayList替代ArrayList。它在写操作时复制整个数组，适合读多写少的场景。
    - 如果需要线程安全的Map，使用ConcurrentHashMap替代HashMap或Collections.synchronizedMap。
    - 如果需要线程安全的Set，使用ConcurrentHashMap.newKeySet()或CopyOnWriteArraySet。
- ConcurrentModificationException也是常见的崩溃
    - 在遍历集合的同时修改集合（增删元素）会抛出此异常。常见于在for-each循环中remove元素。
    - 解决方案：使用Iterator的remove方法、使用CopyOnWriteArrayList、先收集待删除的元素再统一删除、使用removeIf方法（Java 8+）。
    ``` java
    // 错误写法：遍历时直接删除
    for (String item : list) {
        if (condition) list.remove(item); // ConcurrentModificationException
    }
    // 正确写法1：使用Iterator
    Iterator<String> it = list.iterator();
    while (it.hasNext()) {
        if (condition) it.remove();
    }
    // 正确写法2：使用removeIf（Java 8+）
    list.removeIf(item -> condition);
    ```


### 11.4 核心catch上报
- 核心try-catch建议增加APM异常上报
    - 对于一些特殊情况，比如说，开发过程当中或代码中出现了一些catch代码块，捕获住了异常，让程序不崩溃，这其实是不合理的，程序虽然没有崩溃，当时程序的功能已经变得不可用。
    - 所以，这些被catch的异常我们也需要上报上来，这样我们才能知道用户到底出现了什么问题而导致的异常。
- 异常捕获准则
    - catch 时请分清稳定代码和非稳定代码。对于非稳定代码的 catch 尽可能进行区分异常类型，再做对应的异常处理。
    - 不要在 finally 块中使用 return。finally 块中的 return 返回后方法结束执行，返回值被 finally 的返回值覆盖。
    - catch 只处理应用能处理的异常，不要捕获 Throwable。Throwable 是所有 Exceptions 和 Errors 的父类，捕获它会同时捕获不应由应用处理的 Error。



## 12.系统级别Crash
### 12.1 排查解决思路
- eg举个例子，看下下面这个崩溃:
    ``` java
    java.util.concurrent.TimeoutException:
             android.os.BinderProxy.finalize() timed out after 10 seconds
    at android.os.BinderProxy.destroy(Native Method)
    at android.os.BinderProxy.finalize(Binder.java:459)
    ```
- Android的机型众多，碎片化严重，各个硬件厂商可能会定制自己的ROM，更改系统方法，导致特定机型的崩溃。常见的解决思路：
    - 查找可能的原因（通过操作路径和日志，找到一些怀疑的点）
    - 尝试规避（查看可疑的代码调用，是否使用了不恰当的 API，是否可以更换其他的实现方式规避）
    - Hook 解决（Java Hook 和 Native Hook）。Java Hook主要靠反射或者动态代理来更改相应API的行为；Native Hook原理上是用更改后方法把旧方法在内存地址上进行替换。
    - 如果前两种方式都无法解决，尝试反编译ROM，寻找解决的办法。


### 12.2 解决Toast崩溃
- 举一个比较实际的案例
    ``` java
    android.view.WindowManager$BadTokenException:
        at android.view.ViewRootImpl.setView(ViewRootImpl.java)
        at android.view.WindowManagerGlobal.addView(WindowManagerGlobal.java)
        at android.view.WindowManagerImpl.addView(WindowManagerImpl.java4)
        at android.widget.Toast$TN.handleShow(Toast.java)
    ```
- 为什么 Android 8.0 的系统不会有这个问题？在查看 Android 8.0 的源码后我们发现有以下修改：
    ``` java
    try {
      mWM.addView(mView, mParams);
      trySendAccessibilityEvent();
    } catch (WindowManager.BadTokenException e) {
      /* ignore */
    }
    ```
    - 考虑再三，决定参考 Android 8.0 的做法，直接 catch 住这个异常。Toast 里面有一个变量叫 mTN，它的类型为 handler，我们只需要代理它就可以实现捕获。


### 12.3 排查so库异常
- so库崩溃的常见类型
    - SIGSEGV（Signal 11）：最常见的Native崩溃，通常是空指针解引用、访问已释放内存或数组越界。
    - SIGABRT（Signal 6）：程序主动调用abort()终止，通常是检测到不可恢复的错误。
    - SIGBUS（Signal 7）：非法地址访问，通常是内存对齐问题。
- so库崩溃的排查步骤
    - 第一步：获取崩溃堆栈。使用Breakpad或自建的Native Crash捕获组件获取minidump文件，使用addr2line或ndk-stack工具将地址转换为源码行号。
    - 第二步：确认so库版本。检查崩溃时加载的so库版本是否与当前调试符号文件匹配。
    - 第三步：使用addr2line定位代码。
    ``` bash
    # 使用addr2line将地址转换为文件名和行号
    arm-linux-androideabi-addr2line -C -f -e libxxx.so 0x12345
    # 使用ndk-stack直接分析tombstone文件
    ndk-stack -sym obj/local/armeabi-v7a -dump tombstone_00
    ```
    - 第四步：分析内存状态。如果是内存相关的崩溃，需要检查是否有内存越界写入、double-free、use-after-free等问题。可以使用ASan（AddressSanitizer）进行检测。
- so库崩溃的预防措施
    - 使用ASan（AddressSanitizer）：Google提供的内存错误检测工具，可以检测缓冲区溢出、使用已释放的内存等问题。
    - 代码审查重点：指针使用前必须判空，数组访问必须检查边界，动态分配内存必须检查返回值，JNI中的局部引用必须及时释放。
    - 编译选项：开启编译器的安全检查选项（如-fstack-protector-all），启用FORTIFY_SOURCE宏来检测缓冲区溢出。


### 12.4 反编译ROM解决
- 举一个定制系统ROM导致Crash的例子，根据Crash平台统计数据发现该Crash只发生在vivo V3Max这类机型上，Crash堆栈如下：
    ```
    java.lang.RuntimeException: An error occured while executing doInBackground()
      at android.os.AsyncTask$3.done(AsyncTask.java:304)
      ...
    Caused by: java.lang.NullPointerException: Attempt to invoke interface method 'int java.util.List.size()' on a null object reference
      at android.widget.AbsListView$UpdateBottomFlagTask.isSuperFloatViewServiceRunning(AbsListView.java:7689)
      at android.widget.AbsListView$UpdateBottomFlagTask.doInBackground(AbsListView.java:7665)
    ```
- 发现原生系统上对应系统版本的AbsListView里并没有UpdateBottomFlagTask类，因此可以断定是vivo该版本定制的ROM修改了系统的实现。通过反射添加try-catch解决。
    ``` java
    public static void setFinalStatic(Field field, Object newValue) throws Exception {
        field.setAccessible(true);
        Field artField = Field.class.getDeclaredField("artField");
        artField.setAccessible(true);
        Object artFieldValue = artField.get(field);
        Field accessFlagsFiled = artFieldValue.getClass().getDeclaredField("accessFlags");
        accessFlagsFiled.setAccessible(true);
        accessFlagsFiled.setInt(artFieldValue, field.getModifiers() & ~Modifier.FINAL);
        field.set(null, newValue);
    }
    ```



## 13.OOM导致Crash
### 13.1 OOM崩溃概述
- OOM是OutOfMemoryError的简称，在常见的Crash疑难排行榜上，OOM绝对可以名列前茅并且经久不衰。
    - 因为它发生时的Crash堆栈信息往往不是导致问题的根本原因，而只是压死骆驼的最后一根稻草。
- 导致OOM的原因大部分如下：
    - 第一是内存泄漏，大量无用对象没有被及时回收导致后续申请内存失败；
    - 第二是大内存对象过多，最常见的大对象就是Bitmap，几个大图同时加载很容易触发OOM。


### 13.2 内存泄漏问题
- 内存泄漏指系统未能及时释放已经不再使用的内存对象，一般是由错误的程序代码逻辑引起的。
    - 在Android平台上，最常见也是最严重的内存泄漏就是Activity对象泄漏。
- 常见的可能会造成Activity泄漏的原因有：
    - 匿名内部类实现Handler处理消息，可能导致隐式持有的Activity对象无法回收。
    - Activity和Context对象被混淆和滥用，在只需要Application Context的地方使用了Activity对象。
    - View对象处理不当，使用Activity的LayoutInflater创建的View自身持有的Context对象其实就是Activity。
- 对于Activity泄漏，目前已经有了一个非常好用的检测工具：
    - LeakCanary，它可以自动检测到所有Activity的泄漏情况，并且在发生泄漏时给出十分友好的界面提示。


### 13.3 大对象和Bitmap优化
- 在Android平台上，占用内存最多的对象大都是Bitmap对象。
- 对于图片内存优化，我们有几个常用的思路：
    - 尽量使用成熟的图片库，比如Glide，图片库会提供很多通用方面的保障。
    - 根据实际需要，也就是View尺寸来加载图片，可以在分辨率较低的机型上尽可能少地占用内存。
    - 服务端进行图片缩放处理，从而减轻客户端的内存压力。
- Bitmap内存占用的精确计算
    ```
    Bitmap 内存计算公式：
    内存 = 宽 × 高 × 每像素字节数 × (设备dpi / 资源目录dpi)²
    
    常见像素格式内存对比：
    ┌──────────────┬────────┬──────────────────┐
    │ 格式          │ 字节数 │ 适用场景           │
    ├──────────────┼────────┼──────────────────┤
    │ ARGB_8888    │ 4B     │ 默认格式,质量最高   │
    │ RGB_565      │ 2B     │ 不需要透明的场景    │
    │ ALPHA_8      │ 1B     │ 只有透明度信息      │
    │ HARDWARE     │ 0B*    │ Android 8.0+,GPU内存│
    └──────────────┴────────┴──────────────────┘
    * HARDWARE格式图片存储在GPU内存中，不计入Java堆
    ```


### 13.4 OOM崩溃的排查方法论
- OOM排查的系统方法
    - 第一步：确认OOM类型。Android中OOM主要有两种：Java堆内存OOM和Native内存OOM（通常表现为pthread_create failed）。
    - 第二步：获取内存快照。在OOM发生时dump Java Heap（hprof文件），使用MAT或Android Studio的Memory Profiler分析。
    - 第三步：分析Retained Size。找出Retained Size最大的对象，顺着引用链追踪是什么对象持有了它。
    - 第四步：定位根因。内存泄漏导致的OOM需要找到泄漏的根引用；大对象导致的OOM需要优化对象的大小或数量。
- OOM自动dump方案
    ``` java
    // 监控内存使用率，接近阈值时自动dump
    Runtime runtime = Runtime.getRuntime();
    long maxMemory = runtime.maxMemory();
    long usedMemory = runtime.totalMemory() - runtime.freeMemory();
    float memoryUsage = (float) usedMemory / maxMemory;
    if (memoryUsage > 0.85f) {
        // 内存使用超过85%，触发dump
        Debug.dumpHprofData(dumpFilePath);
    }
    ```
- 线程数OOM的排查
    - pthread_create failed表示创建线程失败，通常是因为线程数过多或虚拟内存不足。
    - 解决方案：统一线程池管理、减少不必要的线程创建、裁剪线程栈大小。
- FD（文件描述符）泄漏导致的崩溃
    - Linux系统对每个进程的FD数量有限制（通常为1024），超出后任何需要打开文件、Socket、数据库连接的操作都会失败。
    - 常见原因：Cursor没有关闭、InputStream/OutputStream没有关闭、Socket连接泄漏、Handler Message泄漏（持有Binder fd）。



## 14.三方库导致Crash
### 14.1 三方库崩溃排查方法
- App经常会依赖很多AAR，每个AAR可能有多个版本，互相依赖的AAR中不兼容的版本会造成NoClassDefFoundError、NoSuchFieldError、NoSuchMethodError等异常。
- 排查步骤
    - 第一步：确认崩溃是否来自三方库。通过崩溃堆栈中的包名判断。
    - 第二步：检查版本兼容性。使用`./gradlew app:dependencies`命令查看完整的依赖树，检查是否存在版本冲突。
    - 第三步：尝试升级或降级三方库版本。在三方库的Release Notes或Issue中搜索是否有类似问题的修复。
    - 第四步：如果无法修改三方库，考虑以下方案：
        - 通过反射修改三方库内部的行为。
        - 通过字节码插桩在编译时修改三方库的代码。
        - 通过AOP在运行时拦截三方库的异常方法调用。
        - 下载三方库源码，本地修改后上传到私有Maven仓库。
- 依赖版本冲突的检测
    ``` groovy
    configurations.all {
        resolutionStrategy {
            force 'com.google.code.gson:gson:2.8.9'
            force 'com.squareup.okhttp3:okhttp:4.9.3'
            // 或者直接在编译时检测版本冲突
            // failOnVersionConflict()
        }
    }
    ```



## 15.AOP增强辅助
### 15.1 AOP崩溃防护原理
- AOP是面向切面编程的简称，在Android的Gradle插件1.5.0中新增了Transform API之后，编译时修改字节码来实现AOP变得非常方便。
- AOP的核心思想是在不修改原始代码的前提下，通过编译时字节码修改，将安全保护代码插入到目标方法中。
    - 在Android中，AOP通常通过ASM、AspectJ或Javassist等字节码操作框架，配合Gradle Transform API实现。
    - 执行时机：在编译阶段的class文件生成后、打包成dex文件之前，对class字节码进行修改。
- 在一些特定情况下，可以通过AOP的方式自动处理未捕获的异常：
    - 抛异常的方法非常明确，调用方式比较固定；异常处理方式比较统一。
    - 和业务逻辑无关，即自动处理异常后不会影响正常的业务逻辑。
- AOP可以处理的常见崩溃场景
    - SharedPreferences操作：getString/getInt等方法在数据类型不匹配时会抛出ClassCastException。
    - JSON解析：JSONObject/JSONArray的get方法在key不存在时会抛出JSONException。
    - Color解析：Color.parseColor()在传入非法颜色字符串时会抛出IllegalArgumentException。
    - Window操作：WindowManager.addView()和removeView()在特定生命周期状态下会抛出异常。
    - Dialog显示：Dialog.show()在Activity已经finish时会抛出BadTokenException。


### 15.2 处理Intent异常
- 读取Intent Extras的问题在于常用方法 Intent#getStringExtra 在代码逻辑出错或者恶意攻击的情况下可能会抛出ClassNotFoundException异常。
- 我们专门制作了一个Gradle插件，只需要配置一下参数就可以将某个特定方法的调用替换成另一个方法：
    ```
    WaimaiBytecodeManipulator {
         replacements(
             "android/content/Intent.getIntExtra(Ljava/lang/String;I)I=com/waimai/IntentUtil.getInt(Landroid/content/Intent;Ljava/lang/String;I)I",
             "android/content/Intent.getStringExtra(Ljava/lang/String;)Ljava/lang/String;=com/waimai/IntentUtil.getString(Landroid/content/Intent;Ljava/lang/String;)Ljava/lang/String;",
             ...)
        }
    }
    ```
- 上面的配置就可以将App代码（包括第三方库）里所有的Intent.getXXXExtra调用替换成IntentUtil类中的安全版实现。
    - 在IntentUtil中会对App的运行环境做判断，Debug下会将异常直接抛出，Release环境下则在捕获到异常时返回对应的默认值然后将异常上报到服务器。



## 16.Crash的预防实践
### 16.1 工程架构对Crash率的影响
- 在治理Crash的实践中，往往忽略了工程架构对Crash率的影响。
    - Crash的发生大部分原因是源于程序员的不合理的代码，而程序员工作中最直接接触的就是工程架构。
    - 对于一个层级混乱的架构，是更加容易写出引起Crash的代码。相反，一个层级清晰、边界明确的架构，能够大大减少Crash发生的概率。
- 业务模块的划分
    - App的业务模块化后，每个业务都有唯一包名和对应的负责人。当某个模块发生了Crash，可以根据包名提交问题给这个模块的负责人，让他第一时间进行处理。
- 页面跳转路由统一处理
    - 将页面的跳转，都通过封装的scheme路由去分发。所有业务解耦，同时只需要在scheme路由里一处加上ActivityNotFoundException异常捕获即可解决这种类型的Crash。
- 网络层统一处理API脏数据
    - 客户端的很大一部分的Crash是因为API返回的脏数据。比如当API返回空值、空数组或返回不是约定类型的数据，App收到这些数据，就极有可能发生空指针、数组越界和类型转换错误等Crash。
    - 如果存在脏数据的话，在网络层就会发现问题，不会影响到UI层，返回给UI层的都是校验成功的数据。


### 16.2 大图监控
- 大对象是导致OOM的主要原因之一，Bitmap是App里最常见的大对象类型。
- 用AOP方式Hook了三种常见图片库的加载图片回调方法，同时监控图片库加载图片时的两个维度：
    - 加载图片使用的URL。除了限定CDN域名之外还要求所有图片加载时都要添加对应的动态缩放参数。
    - 最终加载出的图片结果（也就是Bitmap对象）。要求显示在ImageView中的Bitmap分辨率不允许超过View自身的尺寸。
- 开发过程中，在App里检测到不合规的图片时会立即高亮出错的ImageView所在的位置并弹出对话框提示相关信息，辅助开发同学定位并解决问题。


### 16.3 Lint检查
- 发现线上的很多Crash其实可以在开发过程中通过Lint检查来避免。
    - Lint是Google提供的Android静态代码检查工具，可以扫描并发现代码中潜在的问题。
- 通过自定义Lint规则已经实现了Crash预防、Bug预防、提升性能/安全和代码规范检查这些功能。
- 常见的自定义Lint规则示例
    - 禁止在onDraw中创建对象：检测到View.onDraw方法中调用了new操作符时报错。
    - 禁止直接使用new Thread：检测到直接创建Thread对象时警告，建议使用线程池。
    - 检查Parcelable完整性：检测Parcelable实现类的writeToParcel和构造函数中读写顺序是否一致。
    - 检查Handler内存泄漏：检测非静态内部类Handler的使用，建议改为静态内部类+WeakReference。
    - 检查资源关闭：检测Cursor、InputStream等Closeable对象是否在finally块中关闭。


### 16.4 Crash长效治理
- 开发阶段
    - 统一编码规范、增强编码功底、技术评审、增强CodeReview机制；架构优化，能力收敛，统一容错。
- 测试阶段
    - 除了常规测试流程之外，还需要针对特殊场景、机型等边界进行测试。
    - Monkey测试：使用adb shell monkey命令对App进行随机操作压力测试，建议每次版本发布前执行至少10万次Monkey事件。
    - 弱网测试：模拟2G/3G等弱网环境，测试网络请求超时、数据不完整等异常场景。
    - 低内存测试：使用开发者选项中的"后台进程限制"，模拟系统内存紧张时的行为。
    - 快速操作测试：快速连续点击按钮、快速切换页面，测试是否有并发问题或状态不一致。
- 合码阶段
    - 功能开发完毕，即将合并到主分支时，首先进行编译检测、静态扫描，先进行预编译流程，流程通过后再合入主分支。
- 发布阶段
    - 进行多轮灰度，灰度量级应逐渐由小变大，用最小的代价提前暴露问题。可以针对特别的版本，机型等进行专门的灰度。
- 运维阶段
    - 上线之后，稳定性问题同样需要关注，特别依赖于APM的灵敏监控，发现问题及时报警。如果出现了异常情况，也需要根据情况进行回滚或者降级策略。



## 17.Looper拦截崩溃
### 17.1 能否用Looper拦截崩溃
- 能否基于Handler和Looper拦截全局崩溃（主线程），避免 APP 退出。
    - APP的启动方法是在ActivityThread中，在main方法中创建了主线程的Looper。在main方法的最后调用了 Looper.loop()，一旦执行完这个方法就意味着APP被退出了。
    - 如果我们要避免APP被退出，就必须让APP持续执行Looper.loop()。

### 17.2 拦截主线程崩溃
- 如果主线程发生了异常，就会退出循环，意味着APP崩溃，所以我们需要进行try-catch。我们可以在主线程再启动一个 Looper.loop() 去执行主线程任务：
    ``` java
    public class MyApplication extends Application {
        @Override
        protected void attachBaseContext(Context base) {
            super.attachBaseContext(base);
            new Handler(getMainLooper()).post(new Runnable() {
                @Override
                public void run() {
                    while (true) {
                        try {
                            Looper.loop();
                        } catch (Throwable e) {
                            e.printStackTrace();
                            if (e.getMessage() != null && e.getMessage().startsWith("Unable to start activity")) {
                                android.os.Process.killProcess(android.os.Process.myPid());
                                break;
                            }
                        }
                    }
                }
            });
        }
    }
    ```

### 17.3 拦截子线程崩溃
- 子线程抛出异常需要通过setDefaultUncaughtExceptionHandler处理：
    ``` java
    Thread.setDefaultUncaughtExceptionHandler(new Thread.UncaughtExceptionHandler() {
        @Override
        public void uncaughtException(Thread t, Throwable e) {
            e.printStackTrace();
            // 需要手动上报错误到异常管理平台
        }
    });
    ```

### 17.4 Looper拦截的总结建议
- 虽然说looper可以拦截主线程、子线程崩溃，还有ANR。但是有一个最大的问题是，让本该出现异常的地方触发后没有反应，可能会导致后续出现大问题。
- Looper拦截方案的适用场景
    - 适合场景：对于某些系统ROM导致的不可控崩溃（如Toast的BadTokenException），Looper拦截可以作为最后的安全网。
    - 不适合场景：业务逻辑错误导致的崩溃不应该被Looper拦截，否则会掩盖真正的问题。
    - 建议策略：Looper拦截应该配合白名单使用，只拦截已知的、无法通过常规手段修复的系统级崩溃。
- 疑惑：Looper拦截会不会导致App处于"半死不活"的状态？
    - 答疑：确实会。如果Activity.onCreate崩溃被拦截了，界面可能显示为黑屏。这比直接崩溃重启后重新进入的体验更差。
    - 结果：Looper拦截必须配合异常类型判断。对于Activity生命周期中的崩溃，应该杀死进程让App重启，而不是简单拦截。



## 18.Crash监控和止损
### 18.1 Crash的监控
- 建立如下监控流程，来保证异常发生时能够及时得到反馈并处理。
    - 首先是灰度监控，灰度阶段是增量Crash最容易暴露的阶段。可以在灰度期间制定灰度策略去提高Crash的暴露，例如分渠道灰度、分城市灰度、分业务场景灰度、新装用户的灰度等。
    - 灰度结束之后便开始全量，在全量的过程中还需要日常Crash监控和Crash率的异常报警来防止突发情况的发生。
- Crash监控的关键指标
    - 实时崩溃率：每5分钟计算一次的崩溃率，用于快速发现突发问题。
    - 版本崩溃率趋势：对比当前版本与上一版本的崩溃率曲线，发现版本引入的问题。
    - Top崩溃排行：按崩溃次数排序的Top10/Top20崩溃列表，优先处理影响最大的崩溃。
    - 新增崩溃：当前版本新出现的崩溃类型，通常是由新代码引入的。
    - 启动崩溃率：单独统计启动阶段的崩溃率，启动崩溃对用户体验影响最大。
- Crash报警策略
    - 阈值报警：崩溃率超过千分之二时触发P1级报警，超过百分之一时触发P0级报警。
    - 环比报警：崩溃率相比前一天同时段上升超过50%时触发报警。
    - 突增报警：5分钟内某类崩溃次数突然增加10倍以上时触发报警。
    - 启动崩溃报警：启动崩溃率超过千分之一时立即触发P0级报警。


### 18.2 Crash的止损
- Crash还是无法避免的，如果出现问题就需要考虑如何止损。
- 止损手段的优先级
    - 第一优先：服务端配置开关。如果崩溃与某个服务端下发的配置有关，直接在服务端关闭开关即可止损。
    - 第二优先：热修复。使用Tinker/Sophix等热修复框架，在不发版的情况下修复客户端代码。热修复的覆盖速度通常在24小时内可达90%以上。
    - 第三优先：业务降级。关闭出问题的功能模块，使用兜底方案替代。如WebView崩溃时降级使用系统浏览器打开。
    - 第四优先：紧急发版。在以上方案都不可行时，紧急发版并强制升级。
- 热修复的使用注意事项
    - 热修复包需要经过严格测试，避免修复一个问题引入新问题。
    - 需要建立热修复包的回滚机制，出问题时可以撤回。
    - 热修复包的下发应支持灰度，先灰度验证再全量推送。


### 18.3 Crash的自我修复
- 实际情况中有一些技术方案在兼容性和稳定性上做了一定妥协的场景，往往是因为考虑到性能或扩展性等方面的优势。App里也可以实现备用的降级方案，然后设置特定条件的触发策略，从而达到自动修复Crash的目的。
- 一些可以做自动降级的场景：
    - 部分使用JNI实现的模块，在SO加载失败或者运行时发生异常则可以降级为Java版实现。
    - RenderScript实现的图片模糊效果，也可以在失败后降级为普通的Java版高斯模糊算法。
    - 在使用Retrofit网络库时发现OkHttp3或者HttpURLConnection网络通道失败率高，可以主动切换到另一种通道。
    - Android 3.0中引入了硬件加速机制，在某些机型上会有Crash的情况，可以主动选择是否开启硬件加速。


### 18.4 Crash日志回捞
- 线上某些怪异的Crash发生后，除了分析Crash堆栈信息之外，还可以使用离线日志回捞、下发动态日志等工具来还原Crash发生时的场景。
    - 离线日志的内容都是预先记录好的，有时候可能会漏掉一些关键信息。
    - 动态日志存在的问题是每次下发只能针对已知UUID的一个用户的一台设备，对于大量线上Crash的情况并不合适。
- 可以改造动态日志使其支持批量甚至全量下发，记录的日志等到发生特定类型的Crash时才上报，这样可以减少日志服务器压力，同时极大提高定位问题的效率。



## 19.崩溃治理设计总结
### 19.1 崩溃治理的核心哲学
- 崩溃治理的本质
    - 崩溃治理不是单纯的"修bug"，而是一套系统工程。它涵盖了预防、检测、响应、修复和复盘五个环节，形成一个完整的闭环。
    - 优秀的崩溃治理体系应该是"预防为主，治理为辅"。80%的精力应该放在预防（编码规范、Lint检查、架构设计）上，20%放在治理（修复、止损）上。
- 崩溃治理的分级策略
    - P0级（阻断性崩溃）：启动崩溃、支付流程崩溃、核心功能崩溃。要求：1小时内响应，4小时内修复。
    - P1级（高频崩溃）：影响大量用户的崩溃，UV崩溃率超过万分之五。要求：4小时内响应，当天修复。
    - P2级（低频崩溃）：影响少量用户的崩溃，通常与特定机型或ROM相关。要求：24小时内响应，下一个版本修复。
    - P3级（极低频崩溃）：偶发性崩溃，难以复现。要求：记录并持续观察，如有共性再集中处理。


### 19.2 崩溃治理的长效机制
- 技术债务管理
    - 定期（如每月）对崩溃Top10进行专项治理，分配专人负责。
    - 将崩溃率纳入团队的技术KPI，让每个开发者都有崩溃治理的意识。
    - 建立崩溃知识库，记录每次崩溃的原因、解决方案和预防措施，避免重复犯错。
- 工具链建设
    - 崩溃捕获SDK：支持Java/Kotlin异常和Native崩溃的完整捕获。
    - 崩溃分析平台：支持崩溃的自动聚合、趋势分析、版本对比、机型分布等多维度分析。
    - 日志回捞系统：支持对特定用户或特定崩溃类型的日志定向回捞。
    - 热修复能力：在不发版的情况下修复线上崩溃。
    - 灰度发布系统：支持分渠道、分人群、分比例的精细化灰度。
- 流程规范
    - 代码提交前：Lint检查通过、单元测试通过、CR审核通过。
    - 合入主分支前：预编译成功、自动化测试通过、无新增Lint警告。
    - 版本发布前：回归测试通过、核心流程覆盖测试通过、崩溃率无异常。
    - 版本发布后：灰度期间重点监控崩溃率，全量后持续监控48小时。


### 19.3 崩溃治理的常见误区
- 误区一：只关注崩溃堆栈，忽略上下文
    - 崩溃堆栈只是结果，不是原因。需要结合用户操作路径、设备状态、内存情况等上下文信息才能找到根因。
- 误区二：用try-catch掩盖问题
    - try-catch只应该用在确实需要容错的地方，不应该用来掩盖逻辑错误。过多的try-catch会让问题更难被发现。
- 误区三：只修复Top崩溃，忽略长尾
    - Top崩溃固然重要，但长尾崩溃可能包含了严重的架构问题。需要定期分析长尾崩溃的共性，从架构层面解决问题。
- 误区四：过度依赖热修复
    - 热修复是应急手段，不是常规手段。过度依赖热修复会降低对代码质量的要求，积累技术债务。
- 误区五：崩溃率低就不需要治理
    - 崩溃率低不等于没有问题。可能是崩溃被吞掉了（try-catch），可能是统计口径有问题，也可能是用户流失了。
    - 需要同时关注崩溃率和崩溃用户的留存率，如果崩溃用户的次日留存明显低于非崩溃用户，说明崩溃对用户体验的影响比数据表面看起来更严重。


### 19.4 崩溃治理核心指标
- **崩溃率**：崩溃UV / 活跃UV × 100%（目标 < 0.1%）
- **启动崩溃率**：启动崩溃UV / 启动UV × 100%（目标 < 0.01%）
- **崩溃MTTR**：Mean Time To Repair，从崩溃发生到修复上线的平均时间
- **崩溃MTTD**：Mean Time To Detect，从崩溃发生到被发现的平均时间
- **崩溃用户留存**：崩溃用户的次日/7日留存率与整体用户的对比
