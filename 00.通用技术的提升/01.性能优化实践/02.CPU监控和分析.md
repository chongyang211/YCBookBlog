## 01.CPU基础概念

### 1.1 思考一下问题

思考一些问题

1. CPU优化中，主要是涉及到那些点的优化？如何进行优化和衡量标准？
2. CPU主要是跟线程有关吗？如何理解CPU？如何搞懂CPU架构？
3. 为什么同一段代码在不同设备上CPU消耗差异巨大？CPU架构（ARM big.LITTLE）如何影响性能？
4. 如何区分"有效CPU利用"和"CPU浪费"？一个CPU使用率50%的App到底算不算有性能问题？
5. 多线程真的能加速程序吗？什么时候多线程反而会拖慢CPU效率？

一些核心概念：CPU，这里也可以叫做CPU寄存器。一般计算器是多核的，有多个CPU，主要是为了提高计算效率！

**理解CPU优化的本质**：CPU优化的本质不是"降低CPU使用率"，而是**提高CPU的有效利用率**。有效利用是指每一个CPU周期都在做对用户有价值的计算，无效消耗包括：忙等待(spin lock)、频繁GC、不必要的对象创建/销毁、低效算法、过多的上下文切换等。

```
CPU优化的四个核心维度：

┌──────────────────────────────────────────────────────────┐
│                  CPU 优化全景图                           │
├──────────┬──────────┬──────────────┬─────────────────────┤
│ 减少计算量 │ 提升效率  │  合理调度     │  硬件感知           │
│          │          │              │                     │
│ · 缓存结果 │ · 高效算法 │ · 线程池管理  │ · 缓存友好布局      │
│ · 懒计算  │ · 批量处理 │ · 优先级调度  │ · SIMD/NEON指令     │
│ · 避免重绘 │ · 减少拷贝 │ · 大小核绑定  │ · 分支预测友好      │
│ · 移除冗余 │ · JIT预热 │ · 后台限制    │ · 内存对齐          │
└──────────┴──────────┴──────────────┴─────────────────────┘
```

### 1.2 CPU内存架构

**CPU的内存架构 — 理解性能的硬件基础**

![CPU内存架构](https://img-blog.csdnimg.cn/574aa76843b14f83b6ec938288840119.png)

现在的计算机，基本都是多个CPU，并且有些CPU还是多核的，因此你的程序中，**每个CUP执行一个线程**。并且俩个或者**俩个以上的CPU在同时执行任务，这种情况就是我么所说的：并发**。

**移动端 CPU 架构的特殊性 — ARM big.LITTLE**：

与桌面CPU不同，移动端CPU采用异构多核架构（big.LITTLE / DynamIQ），不同核心的性能差异巨大：

```
典型移动CPU架构（以骁龙8 Gen3为例）：

┌───────────────────────────────────────────────┐
│                  CPU 集群                      │
├───────────┬──────────────┬────────────────────┤
│ 超大核 ×1  │  大核 ×3     │  小核 ×4           │
│ Cortex-X4 │ Cortex-A720  │  Cortex-A520       │
│ 3.3 GHz   │ 2.3 GHz      │  1.9 GHz          │
│ 性能最强   │ 性能均衡      │  功耗最低          │
│           │              │                    │
│ 适合：     │ 适合：        │ 适合：             │
│ UI渲染     │ 图片解码      │ 后台同步           │
│ 动画计算   │ 网络处理      │ 日志写入           │
│ 复杂计算   │ JSON解析      │ 心跳保活           │
└───────────┴──────────────┴────────────────────┘
```

**这对性能优化的启示**：
1. **同一段代码在大核和小核上执行速度可能差3-4倍**——不能用单一基准衡量性能
2. **线程优先级影响核心调度**：Android 的 `nice` 值和 `cgroup` 决定线程被调度到哪个核心
3. **热感知调度**：CPU温度升高后系统会将任务从大核迁移到小核，即使你的线程优先级很高
4. **频率动态调节（DVFS）**：CPU频率根据负载动态调整，空载时可能只有最高频率的1/3

**缓存一致性协议（MESI）**：

多核CPU面临的核心挑战是缓存一致性。当两个核心同时缓存了同一块内存数据，一个核心修改后如何通知另一个核心？这就是MESI协议要解决的问题：

| 状态 | 含义 | 场景 |
|------|------|------|
| Modified | 已修改，与主内存不一致 | 当前核心写入了新值 |
| Exclusive | 独占，与主内存一致 | 只有当前核心缓存了此数据 |
| Shared | 共享，多核缓存了相同数据 | 多个核心读取了同一数据 |
| Invalid | 无效，需要重新从内存加载 | 其他核心修改了此数据 |

**伪共享（False Sharing）陷阱**：两个线程分别修改两个不同的变量，但这两个变量恰好在同一个缓存行（64字节）中，会导致缓存行在两个核心之间反复失效和加载，性能急剧下降。这是多线程编程中最隐蔽的性能杀手之一。

### 1.3 CPU核心工作原理

CPU的工作本质是一个不断"取指令-解码-执行"的循环过程。理解这个过程对优化CPU使用至关重要。

**CPU指令执行流水线**：

现代CPU采用流水线（Pipeline）架构来提高执行效率。一条指令的执行通常分为以下阶段：

1. **取指（Fetch）**：从内存中读取下一条要执行的指令
2. **解码（Decode）**：将机器码翻译成CPU内部的微操作
3. **执行（Execute）**：ALU（算术逻辑单元）执行运算操作
4. **访存（Memory Access）**：读写内存数据
5. **回写（Write Back）**：将结果写回寄存器

流水线让CPU可以同时处理多条指令的不同阶段，极大提高了吞吐量。但分支预测失败、缓存缺失等情况会导致流水线停顿（Pipeline Stall），降低效率。

**CPU缓存层次**：

```
CPU核心 → L1 Cache (32-64KB, ~1ns)
        → L2 Cache (256KB-1MB, ~3-10ns)  
        → L3 Cache (2-32MB, ~10-40ns, 多核共享)
        → 主内存 RAM (~50-100ns)
        → 磁盘/SSD (~100us-10ms)
```

数据在缓存中命中（Cache Hit）的速度远快于从主内存读取。因此，程序的内存访问模式对CPU性能影响巨大。顺序访问数组比随机访问链表快得多，原因就在于缓存友好性。

**CPU调度与上下文切换**：

操作系统通过调度器（Scheduler）管理CPU资源的分配。每个线程获得一个时间片（Time Slice），时间片用完后被挂起，切换到下一个线程执行。上下文切换的开销包括：
- 保存/恢复CPU寄存器状态
- 刷新TLB（Translation Lookaside Buffer）
- 切换内存映射
- 缓存失效

频繁的上下文切换是CPU性能的大敌。一次上下文切换大约耗时1-10微秒，看似很短，但如果每秒发生数万次，开销就相当可观了。

### 1.4 CPU与性能的关系

**疑惑**：CPU使用率高一定意味着程序性能好吗？CPU使用率低是否说明程序没有性能问题？

**答疑**：CPU使用率与程序性能之间并非简单的正相关关系。高CPU使用率可能意味着程序在做有效工作，也可能意味着程序在做无用功（如死循环、频繁GC）。低CPU使用率可能意味着程序在等待IO、等待锁、或被其他进程抢占。

**论证**：

1. **CPU高+性能好**：计算密集型任务（如图像处理、加密解密）充分利用CPU是正常现象
2. **CPU高+性能差**：死循环、频繁的短生命周期对象创建导致GC、低效算法
3. **CPU低+性能好**：IO密集型应用在等待IO时CPU自然空闲
4. **CPU低+性能差**：锁等待、Binder调用阻塞、被其他高优先级进程抢占

**结果**：判断性能需要综合分析CPU使用率、CPU使用的有效性、以及用户感知的响应时间。单看CPU使用率容易得出错误结论。

## 02.CPU使用率

### 2.1 理解CPU使用率

**CPU使用率的本质——时间片的分配统计**

在Linux系统下CPU分为：CPU利用率分为用户态、系统态、空闲态，分别表示CPU处于用户态执行的时间，系统内核执行的时间，和空闲系统进程执行的时间。

平时所说的CPU利用率是指：CPU执行非系统空闲进程的时间 / CPU总的执行时间。

```
CPU 时间组成的完整分解：

/proc/stat 输出示例：
cpu  10132153 290696 3084719 46828483 16683 0 25195 0 0 0

各字段含义：
┌──────────┬──────────┬─────────────────────────────────────┐
│ 字段      │ 值        │ 含义                                │
├──────────┼──────────┼─────────────────────────────────────┤
│ user     │ 10132153 │ 用户态时间（应用代码执行）              │
│ nice     │ 290696   │ 低优先级用户态时间                     │
│ system   │ 3084719  │ 内核态时间（系统调用）                  │
│ idle     │ 46828483 │ 空闲时间                              │
│ iowait   │ 16683    │ IO等待时间（磁盘/网络）                 │
│ irq      │ 0        │ 硬中断处理时间                         │
│ softirq  │ 25195    │ 软中断处理时间                         │
│ steal    │ 0        │ 虚拟化环境被宿主机占用的时间             │
└──────────┴──────────┴─────────────────────────────────────┘

CPU使用率 = 1 - idle / (user + nice + system + idle + iowait + irq + softirq)
```

**关键区分——CPU使用率 vs CPU负载（Load Average）**：

这两个概念经常被混淆，但含义截然不同：

| 指标 | CPU使用率 | CPU负载(Load Average) |
|------|---------|---------------------|
| 定义 | CPU忙碌时间的占比 | 运行队列中等待+正在执行的进程数 |
| 范围 | 0%-100%(每个核心) | 0到无穷大 |
| 健康值 | <70% | <核心数(如8核<8) |
| 高值含义 | CPU在忙碌计算 | 很多进程在排队等CPU |
| 典型场景 | CPU使用率低但负载高→大量IO等待 | CPU使用率高但负载适中→计算密集 |

先介绍几个和Linux时间有关的名词：HZ、tick与jiffies。

- HZ：Linux 核心每隔固定周期会发出timer interrupt (IRQ 0)，HZ是用来定义每一秒有几次timer interrupts。例如HZ为1000，就代表每秒有1000次timer interrupts。
- Tick ：Tick是HZ的倒数，Tick = 1/HZ 。即timer interrupt每发生一次中断的时间。如HZ为250时，tick为4毫秒(millisecond)。
- Jiffies ：在Linux的内核中，有一个全局变量：Jiffies。 Jiffies代表时间。它的单位随硬件平台的不同而不同。jiffies的单位就是 1/HZ。Intel平台jiffies的单位是1/100秒，这就是系统所能分辨的最小时间间隔了。每个CPU时间片，Jiffies都要加1。 CPU的利用率就是用执行用户态+系统态的Jiffies除以总的Jifffies来表示。

CPU利用率计算公式也就是： CPU使用率＝（用户态Jiffies＋系统态Jiffies）／总Jiffies

**Android 中计算CPU使用率的实际代码**：

```java
/**
 * 读取 /proc/stat 计算整体CPU使用率
 * 需要两次采样，计算时间差值
 */
public double calculateCpuUsage(long[] prevCpuTime, long[] currCpuTime) {
    // prevCpuTime/currCpuTime: [user, nice, system, idle, iowait, irq, softirq]
    long prevTotal = 0, currTotal = 0;
    for (int i = 0; i < 7; i++) {
        prevTotal += prevCpuTime[i];
        currTotal += currCpuTime[i];
    }
    long totalDelta = currTotal - prevTotal;
    long idleDelta = (currCpuTime[3] + currCpuTime[4]) - (prevCpuTime[3] + prevCpuTime[4]);
    
    if (totalDelta == 0) return 0;
    return (1.0 - (double) idleDelta / totalDelta) * 100.0;
}
```

### 2.2 CPU使用率分类

在 终端应用（Android应用，iOS应用，嵌入式应用APP等） 中，CPU 使用率可以分为：

1. 应用 CPU 使用率：应用占用的 CPU 资源。
2. 系统 CPU 使用率：系统进程占用的 CPU 资源。

更细粒度地，Linux系统将CPU时间划分为以下几类：

| 类型 | 含义 | 典型场景 |
|------|------|---------|
| user | 用户态CPU时间 | 应用代码执行 |
| nice | 低优先级用户态时间 | nice值调整后的进程 |
| system | 内核态CPU时间 | 系统调用、驱动 |
| idle | 空闲时间 | CPU无任务 |
| iowait | IO等待时间 | 等待磁盘/网络IO |
| irq | 硬中断时间 | 硬件中断处理 |
| softirq | 软中断时间 | 网络包处理等 |
| steal | 虚拟机被抢占时间 | 虚拟化环境 |

### 2.3 CPU使用率异常表现

CPU使用率异常通常有以下几种表现形式：

**1. CPU使用率持续过高（>80%）**

表现：设备发热、界面卡顿、响应迟缓、电量消耗快

常见原因：
- 死循环或低效循环
- 频繁的GC（垃圾回收）
- 复杂的UI布局计算
- 后台线程抢占CPU资源
- 加密/解密、图像处理等计算密集操作

**2. CPU使用率频繁波动**

表现：应用时快时慢，体验不稳定

常见原因：
- 定时器触发的周期性任务
- 不合理的轮询机制
- 网络请求回调处理不当

**3. CPU iowait过高**

表现：CPU使用率不高但应用感觉很慢

常见原因：
- 主线程读写大文件
- 频繁的数据库查询
- SharedPreferences的apply/commit
- 日志写入过于频繁

### 2.4 CPU负载与使用率区别

**疑惑**：CPU负载（Load Average）和CPU使用率有什么区别？为什么有时候CPU使用率不高但系统很慢？

**答疑**：CPU负载表示的是等待CPU执行的任务队列长度（包含正在执行和等待执行的），而CPU使用率只表示CPU正在被使用的时间比例。

**论证**：

打个比方，CPU是一个收银台：
- CPU使用率 = 收银员实际工作时间 / 总时间（收银员忙不忙）
- CPU负载 = 排队等待结账的人数（队伍有多长）

可能的场景：
- 使用率低+负载低：系统空闲
- 使用率高+负载低：CPU在做计算密集型工作，没有排队现象
- 使用率低+负载高：大量线程在等IO，CPU虽空闲但任务堆积
- 使用率高+负载高：CPU满负载且有任务排队，系统严重繁忙

Linux中通过`/proc/loadavg`获取负载值，它给出1分钟、5分钟和15分钟的平均值：

```shell
$ cat /proc/loadavg
2.50 3.10 2.80 4/256 12345
# 1分钟: 2.50, 5分钟: 3.10, 15分钟: 2.80
# 4个running线程/256个总线程, 最近pid: 12345
```

**结果**：对于4核CPU，负载值4.0意味着CPU刚好满负载。负载值超过核心数则意味着有任务在排队等待。日常监控中应同时关注CPU使用率和负载值，两者结合才能准确判断系统状态。

## 03.CPU监控核心原理

**CPU监控**：基于`/proc/stat`和`/proc/[pid]/stat`计算使用率

### 3.1 监控原理与数据源

CPU使用率计算基于`/proc/stat`和`/proc/[pid]/stat`：

- 总CPU时间 = user + nice + system + idle + iowait + irq + softirq
- 进程CPU时间 = utime + stime
- CPU使用率 = (进程CPU时间增量 / 总CPU时间增量) * 100%

计算CPU使用率需要在两个时间点分别采样，然后通过增量计算得出。单次读取的值只是累计值，没有实际意义。

**计算方法详解**：

1. 采样两个足够短的时间间隔的CPU快照，分别记作t1、t2
2. 计算总的CPU时间片totalCpuTime = s2 - s1
3. 计算空闲时间 idle = idle2 - idle1
4. CPU总使用率（%）= 100 * ((totalCpuTime2 - totalCpuTime1) - (idle2 - idle1)) / (totalCpuTime2 - totalCpuTime1)

**单个程序CPU使用率**：进程的总CPU时间 processCpuTime = utime + stime + cutime + cstime（该值包括其所有线程的cpu时间），单个程序的CPU使用率（%）= 100 * (processCpuTime2 - processCpuTime1) / (totalCpuTime2 - totalCpuTime1)

```java
// Android中计算CPU使用率的示例
public class CpuMonitor {
    private long previousTotalCpu = 0;
    private long previousProcessCpu = 0;
    
    /**
     * 计算进程CPU使用率
     * @return CPU使用率百分比
     */
    public float getProcessCpuUsage() {
        long[] totalCpu = readTotalCpuTime();      // 从/proc/stat读取
        long[] processCpu = readProcessCpuTime();   // 从/proc/[pid]/stat读取
        
        long totalDelta = totalCpu[0] - previousTotalCpu;
        long processDelta = processCpu[0] - previousProcessCpu;
        
        previousTotalCpu = totalCpu[0];
        previousProcessCpu = processCpu[0];
        
        if (totalDelta == 0) return 0;
        return (float) processDelta / totalDelta * 100;
    }
    
    private long[] readTotalCpuTime() {
        try {
            BufferedReader reader = new BufferedReader(
                new FileReader("/proc/stat"));
            String line = reader.readLine();  // 第一行是总CPU时间
            reader.close();
            
            String[] parts = line.split("\\s+");
            long total = 0;
            for (int i = 1; i < parts.length; i++) {
                total += Long.parseLong(parts[i]);
            }
            return new long[]{total};
        } catch (Exception e) {
            return new long[]{0};
        }
    }
    
    private long[] readProcessCpuTime() {
        try {
            int pid = android.os.Process.myPid();
            BufferedReader reader = new BufferedReader(
                new FileReader("/proc/" + pid + "/stat"));
            String line = reader.readLine();
            reader.close();
            
            String[] parts = line.split("\\s+");
            // 第14列: utime, 第15列: stime
            long utime = Long.parseLong(parts[13]);
            long stime = Long.parseLong(parts[14]);
            return new long[]{utime + stime};
        } catch (Exception e) {
            return new long[]{0};
        }
    }
}
```

### 3.2 proc文件系统详解

Linux的`/proc`虚拟文件系统是CPU监控的基础数据源。以下是几个关键文件：

**`/proc/stat`** - 系统整体CPU统计

```
cpu  10132153 290696 3084719 46828483 16683 0 25195 0 0 0
cpu0 1393280  32966  572056  13343292 6130  0 17875 0 0 0
cpu1 ...
```

各列含义：user, nice, system, idle, iowait, irq, softirq, steal, guest, guest_nice

**`/proc/[pid]/stat`** - 进程CPU统计

该文件包含进程的详细状态信息，关键字段：
- 第14列（utime）：进程在用户态的CPU时间（时钟节拍数）
- 第15列（stime）：进程在内核态的CPU时间
- 第16列（cutime）：已终止子进程的用户态CPU时间
- 第17列（cstime）：已终止子进程的内核态CPU时间

**`/proc/[pid]/status`** - 进程状态信息（可读格式）

```
Name:   com.example.app
State:  S (sleeping)
Threads: 45
VmRSS:  120456 kB
voluntary_ctxt_switches:    15234
nonvoluntary_ctxt_switches: 3456
```

其中`voluntary_ctxt_switches`和`nonvoluntary_ctxt_switches`分别表示主动和被动上下文切换次数，是分析CPU调度问题的重要指标。

**`/proc/[pid]/task/`** - 进程内的线程信息

每个线程都有一个以线程ID命名的子目录，结构与`/proc/[pid]/`类似。通过遍历该目录可以获取每个线程的CPU使用情况。

### 3.3 CPU数据获取方式

**top命令获取**：

top是比较经典的CPU计算方法，总的cpu时间 = user + nice + system + idle + iowait + irq + softirq。proc->delta_time是两次读取/proc/pid/stat相减得到，可见top是一段时间内，计算process的cpu jiffies与总的cpu jiffies差值得到。

```bash
adb shell top -m 100 -n 1 -s cpu | grep 包名
```

**dump cpuinfo命令获取**：

Android特有的命令，dump cpuinfo命令的实现在`ProcessCpuTracker.java`类中。进程的总CPU时间processCpuTime = utime + stime + cutime + cstime，该值包括其所有线程的cpu时间。

```bash
adb shell dumpsys cpuinfo |grep 包名
```

**Android高版本限制**：在Android 8.0以上版本，为了防止旁路攻击，普通应用程序已经无法访问`/proc/stat`文件。部分开源库如DoKit会通过执行 `top -n 1` 来获取CPU使用率，但在高版本设备上可能无法使用。

### 3.4 监控数据采集策略

CPU监控数据的采集需要考虑以下关键因素：

**采样频率的选择**：

| 场景 | 推荐采样频率 | 原因 |
|------|-------------|------|
| 开发调试 | 100ms-500ms | 需要精细数据 |
| 线上监控 | 1s-5s | 平衡精度和开销 |
| 长时间压测 | 5s-10s | 减少数据量 |
| 异常检测 | 动态调整 | 正常时低频，异常时高频 |

**采集的性能开销**：

读取`/proc`文件系统本身也会消耗CPU。在嵌入式设备或低端手机上，需要控制采样频率以避免监控行为影响被监控的对象。一般建议监控自身的CPU开销不超过总CPU的1%。

```java
// 动态调整采样频率的策略
public class AdaptiveCpuSampler {
    private static final long NORMAL_INTERVAL = 2000;   // 正常2秒
    private static final long HIGH_FREQ_INTERVAL = 200;  // 高频200ms
    private static final float CPU_THRESHOLD = 70.0f;
    
    private long currentInterval = NORMAL_INTERVAL;
    
    public void onCpuUsageUpdate(float cpuUsage) {
        if (cpuUsage > CPU_THRESHOLD && currentInterval == NORMAL_INTERVAL) {
            // CPU使用率超过阈值，切换到高频采样
            currentInterval = HIGH_FREQ_INTERVAL;
            restartSampling(currentInterval);
        } else if (cpuUsage < CPU_THRESHOLD * 0.8f && currentInterval == HIGH_FREQ_INTERVAL) {
            // CPU使用率恢复，切回正常频率
            currentInterval = NORMAL_INTERVAL;
            restartSampling(currentInterval);
        }
    }
}
```

## 04.CPU监控方案设计

### 4.1 监控方案原则

**系统资源监控专用设计，体现了系统监控的核心理念**：

1. 轻量化原则：使用BusyBox兼容的shell命令，避免依赖复杂工具
2. 实时性要求：0.1秒采样间隔，满足实时系统的精确监控需求
3. 资源约束意识：考虑到嵌入式系统的存储和计算限制

**分层监控架构，脚本采用了三层监控架构**：

1. 应用层监控：目标进程(yt-palm)的CPU、内存占用
2. 系统层监控：整体系统负载、内存使用率、温度
3. 数据持久化层：CSV格式的结构化日志存储

### 4.2 监控指标与告警

需要监控的核心CPU指标：

| 指标 | 采集频率 | 告警阈值 | 数据来源 |
|------|---------|---------|---------|
| 应用CPU使用率 | 3秒 | >30%持续10秒 | /proc/self/stat |
| 线程CPU Top5 | 5秒 | 单线程>80% | /proc/self/task/ |
| CPU温度 | 10秒 | >45°C | thermal_zone |
| 主线程CPU | 3秒 | >50% | Debug.threadCpuTimeNanos |
| CPU频率 | 10秒 | 持续降频 | cpufreq |

**分级告警策略**：

根据CPU使用率的严重程度设置分级告警，避免误报和漏报：
- **正常（<50%）**：记录日志
- **警告（50%-70%）**：增加采样频率，收集更多上下文
- **严重（70%-90%）**：触发告警，自动收集线程堆栈
- **危急（>90%）**：紧急告警，准备降级方案

告警设计要点：
- 持续告警：CPU使用率持续超过阈值一定时间才触发，避免短暂波动导致误报
- 差异告警：与同版本的历史基线对比，异常偏离时告警
- 分场景告警：区分前台和后台的告警阈值（前台允许较高，后台应接近0）

```java
// CPU使用率采集器
public class CpuSampler {
    private long lastProcessCpuTime = 0;
    private long lastSystemCpuTime = 0;
    
    public float getProcessCpuUsage() {
        try {
            String stat = readFile("/proc/self/stat");
            String[] fields = stat.split("\\s+");
            long utime = Long.parseLong(fields[13]);
            long stime = Long.parseLong(fields[14]);
            long currentProcessCpu = utime + stime;
            
            long currentSystemCpu = getSystemCpuTime();
            
            float usage = 0;
            if (lastProcessCpuTime > 0 && lastSystemCpuTime > 0) {
                long processDelta = currentProcessCpu - lastProcessCpuTime;
                long systemDelta = currentSystemCpu - lastSystemCpuTime;
                if (systemDelta > 0) {
                    usage = (float) processDelta / systemDelta * 100f;
                }
            }
            
            lastProcessCpuTime = currentProcessCpu;
            lastSystemCpuTime = currentSystemCpu;
            return usage;
        } catch (Exception e) {
            return -1;
        }
    }
}
```

## 05.CPU优化方法论

### 5.1 CPU优化思路

UI界面渲染，行为交互，功能运算等等操作最终都会转换成为一条条机器指令，而这些机器指令是要依靠CPU去执行的。所以在面对同一功能时，如何让CPU以最短的时间去完成功能就是我们的首要目标。

当我们想要提升某些场景（如启动、打开页面、渲染动画等）的速度时，本质上就是降低 CPU 执行完这些场景指令的时间，这个时间简称为 CPU 时间。

程序所消耗 CPU 时间的计算公式：CPU 时间 ＝ 程序执行所需的时钟周期数 * 时钟周期时间，其中的 程序执行所需的时钟周期数 = 程序指令数 * 每条指令的平均时钟周期"

1. 程序执行所需的时钟周期数：CPU的所有操作都是以时钟周期为基础来计算的，每个时钟周期都会执行一个指令或完成一个操作。
2. 时钟周期时间：指CPU完成一次执行所需的时间，即：一个时钟周期的时间，它通常以纳秒（ns）或皮秒（ps）为单位来表示，时钟周期时间越短，CPU的运行速度就越快。
3. 程序指令数：程序代码编译成机器码指令后的指令数量。
4. 每条指令的平均时钟周期：指令执行完毕所消耗的平均时间周期，指令不同所需的时钟周期数也不同。

只要对上述的任何一项因子进行优化都可以达到目的，所以我们的优化方法论就是：①.减少程序指令数、②.降低每条指令的平均时钟周期、③.降低时钟周期的时间、④.其他优化方案

### 5.2 减少程序指令数

减少程序指令数是CPU优化最直观的手段。以下是几种常见的优化方法：

**1. 算法优化**

选择合适的算法可以极大减少指令数。例如排序操作：

```java
// O(n²) 的冒泡排序 - 大量比较和交换指令
for (int i = 0; i < n; i++) {
    for (int j = 0; j < n - 1; j++) {
        if (arr[j] > arr[j + 1]) {
            swap(arr, j, j + 1);
        }
    }
}

// O(n log n) 的归并排序 - 指令数显著减少
// 对于10000个元素：冒泡约需100,000,000次比较，归并约需133,000次
Arrays.sort(arr);  // Java内部使用TimSort
```

**2. 减少方法调用深度**

每次方法调用都涉及栈帧的创建和销毁，这需要多条CPU指令。减少不必要的方法调用和调用深度可以减少开销：

```java
// 优化前：多层抽象封装，每一层都有方法调用开销
public String getDisplayName(User user) {
    return formatName(getFirstName(user), getLastName(user));
}

// 优化后：关键路径减少调用层级（热点代码适用）
public String getDisplayName(User user) {
    return user.firstName + " " + user.lastName;
}
```

**3. 循环优化**

```java
// 优化前：每次循环都调用size()方法
for (int i = 0; i < list.size(); i++) {
    process(list.get(i));
}

// 优化后：提取循环不变量
int size = list.size();
for (int i = 0; i < size; i++) {
    process(list.get(i));
}

// 更优：使用增强for循环（编译器会优化迭代器创建）
for (Item item : list) {
    process(item);
}
```

**4. 避免不必要的对象创建**

对象创建涉及内存分配、构造函数调用、GC压力等多方面CPU开销：

```java
// 优化前：循环内频繁创建StringBuilder
for (int i = 0; i < 1000; i++) {
    String result = "prefix_" + items[i] + "_suffix";  // 每次创建新StringBuilder
    process(result);
}

// 优化后：复用StringBuilder
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 1000; i++) {
    sb.setLength(0);  // 重置但不释放内存
    sb.append("prefix_").append(items[i]).append("_suffix");
    process(sb.toString());
}
```

### 5.3 降低指令时钟周期

降低每条指令的平均时钟周期，核心在于提高CPU缓存命中率和减少内存访问延迟。

**1. 数据局部性优化**

CPU缓存按照缓存行（Cache Line，通常64字节）为单位加载数据。连续访问内存中相邻的数据可以极大提高缓存命中率：

```java
// 缓存不友好：按列遍历二维数组
int[][] matrix = new int[1000][1000];
long sum = 0;
for (int j = 0; j < 1000; j++) {     // 外层遍历列
    for (int i = 0; i < 1000; i++) {   // 内层遍历行
        sum += matrix[i][j];           // 每次跳1000个int，缓存频繁失效
    }
}

// 缓存友好：按行遍历二维数组
for (int i = 0; i < 1000; i++) {     // 外层遍历行
    for (int j = 0; j < 1000; j++) {   // 内层遍历列
        sum += matrix[i][j];           // 连续内存访问，缓存命中率高
    }
}
```

按行遍历的速度通常比按列遍历快3-10倍，原因就是缓存行的预加载机制。

**2. 选择缓存友好的数据结构**

```java
// ArrayList（内部是数组）比LinkedList缓存友好
// 数组元素在内存中连续存储，一次缓存行加载可以获取多个元素
ArrayList<Integer> arrayList = new ArrayList<>();  // 推荐

// LinkedList每个节点在内存中随机分布
// 遍历时每访问一个节点都可能导致缓存失效
LinkedList<Integer> linkedList = new LinkedList<>();  // 不推荐用于遍历
```

**3. 减少分支预测失败**

现代CPU通过分支预测器来预测if/else的走向。预测失败需要清空流水线，代价约10-20个时钟周期：

```java
// 分支不可预测的情况（数据随机）
for (int value : randomData) {
    if (value > threshold) {  // 约50%概率，分支预测器难以预测
        sum += value;
    }
}

// 优化：先排序，让分支变得可预测
Arrays.sort(randomData);  // 排序后，前半部分全部不满足，后半部分全部满足
for (int value : randomData) {
    if (value > threshold) {  // 分支预测器可以很好地预测
        sum += value;
    }
}
```

### 5.4 线程与CPU调度优化

线程是CPU调度的基本单位。合理的线程管理直接影响CPU利用效率。

**线程优先级**：

Android/Linux中线程优先级通过nice值（-20到19）和调度策略来控制。nice值越低，优先级越高。

```java
// Android中设置线程优先级
// 主线程默认nice值为-10（较高优先级）
// 后台线程应设置较低优先级
Thread backgroundThread = new Thread(() -> {
    Process.setThreadPriority(Process.THREAD_PRIORITY_BACKGROUND); // nice=10
    doHeavyWork();
});
backgroundThread.start();

// 线程优先级常量
// THREAD_PRIORITY_FOREGROUND = -2   前台线程
// THREAD_PRIORITY_DEFAULT = 0       默认优先级
// THREAD_PRIORITY_BACKGROUND = 10   后台线程
// THREAD_PRIORITY_LOWEST = 19       最低优先级
```

**CPU亲和性（CPU Affinity）**：

移动设备普遍采用大小核架构（big.LITTLE），大核的性能是小核的2-3倍，但功耗也高出3-5倍。在多核系统中，可以将线程绑定到特定的CPU核心，减少缓存失效和上下文切换开销：

```c
// Linux C中设置CPU亲和性
#include <sched.h>

cpu_set_t cpuset;
CPU_ZERO(&cpuset);
CPU_SET(0, &cpuset);  // 绑定到CPU 0
sched_setaffinity(0, sizeof(cpuset), &cpuset);
```

移动端不直接操作CPU亲和性，而是通过线程优先级和QoS等级间接控制：

```java
// Android: 通过设置线程优先级间接影响CPU调度
Process.setThreadPriority(threadId, Process.THREAD_PRIORITY_FOREGROUND);  // 绑定大核
Process.setThreadPriority(threadId, Process.THREAD_PRIORITY_BACKGROUND);  // 绑定小核
```

```swift
// iOS: 使用QoS等级控制CPU调度策略
DispatchQueue.global(qos: .userInteractive).async { self.processUIUpdate() }
DispatchQueue.global(qos: .background).async { self.cleanupCache() }
```

### 5.5 CPU缓存友好优化

CPU缓存（L1/L2/L3 Cache）对性能有显著影响。缓存友好的编程建议：
- 优先使用数组和ArrayList，减少使用LinkedList
- 遍历二维数组时按行遍历（数据在内存中按行连续存储）
- 结构体/对象的字段按访问频率排列，常用字段放在一起
- 避免False Sharing：多线程频繁写入的变量应该在不同缓存行上

**编译器优化利用**：

现代编译器提供了很多优化选项：
- R8/ProGuard：方法内联、无用代码消除、常量折叠等优化
- LLVM（iOS）：支持多种优化级别（-O0到-Os）
- V8/JSC（Web/RN）：JIT编译器对热点代码进行优化编译

代码层面帮助编译器优化：使用final修饰不变的变量和方法、避免过深的调用链、使用基本类型代替包装类型、循环中避免创建对象。

### 6.1 减少主线程负载

主线程负责 UI 渲染和用户交互，如果主线程负载过高会导致卡顿。主线程耗时操作的常见来源：

### 6.2 使用线程池

线程池是CPU优化的基础手段。避免频繁创建和销毁线程带来的CPU开销，控制并发线程数量。线程池大小应根据任务类型设置：CPU密集型任务线程数 = CPU核心数+1，IO密集型任务线程数 = CPU核心数*2。

```java

    cpuCount + 1, cpuCount + 1,

    new LinkedBlockingQueue<>(128),

        return t;
    }
);
```

### 6.3 减少锁竞争与CPU等待

锁竞争导致CPU浪费的原因：线程在等待锁时被挂起，唤醒时需要上下文切换；自旋锁在争用时直接消耗CPU时间片空转。

**锁优化方法**：
1. 无锁比有锁好：线程本地存储、偏向锁等方案都属于无锁优化
2. 合理细化锁的粒度：将Synchronize锁住整个方法细化成只锁住线程安全相关的代码块
3. 避免在主线程或渲染线程使用锁

```java
// 优化前：粗粒度锁
public synchronized void processData(String key, Object data) {
    Object cached = cache.get(key);
    if (cached == null) {
        cached = expensiveCompute(data);
        cache.put(key, cached);
    }
    updateUI(cached);
}

// 优化后：细粒度锁 + ConcurrentHashMap
private final ConcurrentHashMap<String, Object> cache = new ConcurrentHashMap<>();
public void processData(String key, Object data) {
    Object cached = cache.computeIfAbsent(key, k -> expensiveCompute(data));
    updateUI(cached);
}
```

### 6.4 利用CPU闲置时刻

CPU闲置时刻是指主线程处于空闲状态、没有用户操作的时间段。适合在CPU闲置时执行的任务：预加载数据、预渲染、上报统计数据、缓存清理。

```java
// Android使用IdleHandler在CPU空闲时执行任务
Looper.myQueue().addIdleHandler(() -> {
    Runnable task = pendingTasks.poll();
    if (task != null) task.run();

});
```

### 6.5 IO与序列化优化

**IO优化策略**：使用缓冲IO减少系统调用次数、批量写入合并小IO、异步IO避免主线程阻塞、使用apply代替commit。

不必要的CPU唤醒是后台耗电的主要原因：

## 07.CPU异常排查

### 7.1 CPU使用率过高排查

当发现应用CPU使用率异常偏高时，可以按照以下步骤进行排查：

**步骤一：确认CPU使用率数据**


### 7.2 CPU温度异常排查

CPU温度过高会触发系统的热节流（Thermal Throttling），导致CPU降频，严重影响性能。

**获取CPU温度**：

```shell
# 读取CPU温度（单位：毫摄氏度）
adb shell cat /sys/class/thermal/thermal_zone0/temp
# 输出: 45000 (即45°C)

# 查看热策略状态
adb shell dumpsys thermalservice
```

**温度阈值参考**：

| 温度范围 | 状态 | 系统行为 |
|---------|------|---------|
| <40°C | 正常 | 无限制 |
| 40-50°C | 温热 | 可能降低亮度 |
| 50-60°C | 热 | CPU降频，限制后台任务 |
| >60°C | 过热 | 大幅降频，可能关机 |

**温度过高的常见原因**：
1. 持续高CPU负载（如游戏、视频编解码）
2. 后台线程频繁唤醒（WakeLock滥用）
3. GPS/相机等硬件长时间使用
4. 网络请求过于频繁
5. 环境温度过高

### 7.3 常见CPU异常场景

**场景一：后台线程过多抢占CPU**

```java
// 问题：创建了大量线程执行任务
for (int i = 0; i < 100; i++) {
    new Thread(() -> doWork()).start();
}

// 解决：使用线程池控制并发数
ExecutorService executor = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors());
for (int i = 0; i < 100; i++) {
    executor.submit(() -> doWork());
}
```

**场景二：定时器泄漏持续消耗CPU**

```java
// 问题：Timer/Handler没有在页面销毁时取消
Timer timer = new Timer();
timer.scheduleAtFixedRate(new TimerTask() {
    @Override
    public void run() {
        refreshData();  // 即使页面关闭也在持续执行
    }
}, 0, 1000);

// 解决：在onDestroy中取消
@Override
protected void onDestroy() {
    super.onDestroy();
    if (timer != null) {
        timer.cancel();
        timer = null;
    }
}
```

**场景三：死循环或无限递归**

```java
// 问题：条件判断错误导致死循环

    process(list.get(0));
    // 忘记remove，永远循环
}

// 解决：确保循环有正确的终止条件
while (!list.isEmpty()) {
    Item item = list.remove(0);
    process(item);
}
```


### 7.4 线上CPU异常排查

对于线上系统突然产生的运行缓慢问题，首先需要导出jstack和内存信息，然后重启系统保证可用性。可能的原因包括：内存耗尽导致Full GC次数过多、耗CPU操作导致CPU过高、阻塞性操作、线程死锁等。

**CPU热点函数定位**：

热点函数是指消耗CPU时间最多的函数：
- 使用Android Profiler的CPU Recording功能采集调用链路
- 分析Flame Chart（火焰图），关注Self Time（函数自身耗时）而非Total Time
- 常见热点：频繁JSON解析、复杂正则匹配、频繁反射调用、主线程文件IO、深层布局计算

**线上排查流程**：
1. 通过APM平台发现CPU异常告警
2. 关联分析异常维度信息（版本、设备、场景、时间）
3. 获取CPU异常时的线程堆栈快照
4. 分析高消耗线程的调用链路，定位热点函数
5. 修复问题并验证

**CPU异常响应策略**：
- P2（低优先级）：后台CPU使用率偏高 → 下个版本优化
- P1（中优先级）：前台特定场景CPU持续过高 → 本迭代修复
- P0（高优先级）：大面积发热投诉或CPU导致ANR → 立即修复


## 08.跨平台CPU采集伪代码

### 8.1 Android CPU采集

```java
public class AndroidCpuCollector {
    private long lastProcessTime = 0;
    private long lastTotalTime = 0;

    /**
     * 采集当前进程CPU使用率
     * 原理：读取/proc/self/stat获取进程CPU时间，
     *       读取/proc/stat获取系统总CPU时间，
     *       通过两次采样的增量计算使用率
     */
    public float collectCpuUsage() {
        try {
            String procStat = readFile("/proc/self/stat");
            String[] fields = procStat.split("\\s+");
            long utime = Long.parseLong(fields[13]);
            long stime = Long.parseLong(fields[14]);
            long processTime = utime + stime;

            String systemStat = readFirstLine("/proc/stat");
            String[] cpuFields = systemStat.split("\\s+");
            long totalTime = 0;
            for (int i = 1; i <= 7; i++) {
                totalTime += Long.parseLong(cpuFields[i]);
            }

            float usage = 0;
            if (lastProcessTime > 0) {
                long pDelta = processTime - lastProcessTime;
                long tDelta = totalTime - lastTotalTime;
                if (tDelta > 0) {
                    usage = (float) pDelta / tDelta * 100f
                            * Runtime.getRuntime().availableProcessors();
                }
            }
            lastProcessTime = processTime;
            lastTotalTime = totalTime;
            return usage;
        } catch (Exception e) {
            return -1;
        }
    }

    /**
     * 获取各线程CPU使用排名
     * 遍历/proc/self/task/下的所有线程目录
     */
    public List<ThreadCpuInfo> getTopThreads(int topN) {
        List<ThreadCpuInfo> threads = new ArrayList<>();
        File taskDir = new File("/proc/self/task");
        for (File tidDir : taskDir.listFiles()) {
            try {
                String stat = readFile(tidDir.getPath() + "/stat");
                String[] f = stat.split("\\s+");
                String name = f[1].replace("(", "").replace(")", "");
                long cpu = Long.parseLong(f[13]) + Long.parseLong(f[14]);
                threads.add(new ThreadCpuInfo(name, Integer.parseInt(f[0]), cpu));
            } catch (Exception ignored) {}
        }
        threads.sort((a, b) -> Long.compare(b.cpuTime, a.cpuTime));
        return threads.subList(0, Math.min(topN, threads.size()));
    }
}
```

### 8.2 iOS CPU采集

```objectivec
@implementation iOSCpuCollector

/// 获取当前App的CPU使用率（所有线程累加）
/// 原理：通过Mach API获取进程内所有线程的cpu_usage字段
- (double)collectCpuUsage {
    thread_act_array_t threads;
    mach_msg_type_number_t threadCount = 0;
    
    kern_return_t kr = task_threads(mach_task_self(), &threads, &threadCount);
    if (kr != KERN_SUCCESS) return -1;
    
    double totalUsage = 0;
    for (mach_msg_type_number_t i = 0; i < threadCount; i++) {
        thread_basic_info_data_t info;
        mach_msg_type_number_t infoCount = THREAD_BASIC_INFO_COUNT;
        
        kr = thread_info(threads[i], THREAD_BASIC_INFO,
                        (thread_info_t)&info, &infoCount);
        if (kr == KERN_SUCCESS && !(info.flags & TH_FLAGS_IDLE)) {
            totalUsage += (double)info.cpu_usage / TH_USAGE_SCALE * 100.0;
        }
    }
    
    vm_deallocate(mach_task_self(),
                  (vm_address_t)threads,
                  threadCount * sizeof(thread_t));
    return totalUsage;
}

/// 获取CPU使用率Top N线程
- (NSArray<NSDictionary *> *)topThreads:(NSInteger)topN {
    NSMutableArray *result = [NSMutableArray array];
    thread_act_array_t threads;
    mach_msg_type_number_t threadCount = 0;
    
    if (task_threads(mach_task_self(), &threads, &threadCount) != KERN_SUCCESS) {
        return result;
    }
    
    for (mach_msg_type_number_t i = 0; i < threadCount; i++) {
        thread_basic_info_data_t info;
        mach_msg_type_number_t infoCount = THREAD_BASIC_INFO_COUNT;
        
        thread_info(threads[i], THREAD_BASIC_INFO, (thread_info_t)&info, &infoCount);
        
        if (!(info.flags & TH_FLAGS_IDLE)) {
            double usage = (double)info.cpu_usage / TH_USAGE_SCALE * 100.0;
            char name[256] = {0};
            pthread_getname_np(pthread_from_mach_thread_np(threads[i]), name, sizeof(name));
            [result addObject:@{
                @"name": [NSString stringWithUTF8String:name],
                @"usage": @(usage)
            }];
        }
    }
    
    [result sortUsingComparator:^NSComparisonResult(NSDictionary *a, NSDictionary *b) {
        return [b[@"usage"] compare:a[@"usage"]];
    }];
    
    vm_deallocate(mach_task_self(), (vm_address_t)threads,
                  threadCount * sizeof(thread_t));
    return [result subarrayWithRange:NSMakeRange(0, MIN(topN, result.count))];
}
```

### 8.3 Web CPU采集

```javascript
class WebCpuCollector {
    constructor() {
        this.longTaskDurations = [];
        this._installLongTaskObserver();
    }

    /**
     * Web端无法直接获取CPU使用率
     * 通过以下间接方式评估CPU负载：
     * 1. Long Task API：检测>50ms的主线程阻塞
     * 2. requestAnimationFrame：通过帧间隔评估CPU压力
     */
    _installLongTaskObserver() {
        if ('PerformanceObserver' in window) {
            new PerformanceObserver((list) => {
                for (const entry of list.getEntries()) {
                    this.longTaskDurations.push({
                        duration: entry.duration,
                        startTime: entry.startTime,
                        timestamp: Date.now()
                    });
                }
            }).observe({ type: 'longtask', buffered: true });
        }
    }

    /**
     * 通过rAF帧间隔评估CPU压力
     */
    measureCpuPressure(durationMs = 1000) {
        return new Promise((resolve) => {
            const intervals = [];
            let lastTime = performance.now();

            function tick(now) {
                intervals.push(now - lastTime);
                lastTime = now;
                if (now - intervals[0] < durationMs) {
                    requestAnimationFrame(tick);
                } else {
                    const avgInterval = intervals.reduce((a, b) => a + b) / intervals.length;
                    const fps = 1000 / avgInterval;
                    resolve({
                        fps: Math.round(fps),
                        avgFrameTime: Math.round(avgInterval * 100) / 100,
                        pressure: fps < 30 ? 'high' : fps < 50 ? 'medium' : 'low',
                        longTaskCount: this.longTaskDurations.length
                    });
                }
            }
            requestAnimationFrame(tick);
        });
    }
}
```


## 09.CPU监控设计总结

### 9.1 CPU监控核心原则

**原则一：数据驱动，量化一切**。任何CPU优化都应该基于精确的数据，而非凭感觉。"过早优化是万恶之源"——Donald Knuth。先通过监控发现热点，再有针对性地优化。实践中，开发者凭直觉定位的性能瓶颈只有30%是准确的，70%的真正瓶颈隐藏在意想不到的地方。

**原则二：最小侵入，监控不能成为负担**。CPU监控系统本身不应该成为性能负担。监控代码的CPU开销应控制在被监控应用的1%以内。具体策略：
- 采样而非全量：线上使用采样率（如10%用户采样），避免所有用户都开启全量监控
- 分级采集：正常状态低频采样（5s），异常状态高频采样（500ms）
- 异步上报：监控数据写入本地缓冲区，空闲时批量上报，避免干扰主线程

**原则三：全栈可观测，多维度交叉分析**。需要综合关注：CPU使用率、CPU负载、上下文切换次数、缓存命中率、线程状态分布、调度延迟等多维度数据。

```
CPU 监控的数据关联分析模型：

                CPU使用率高
                    │
        ┌───────────┼───────────┐
        │           │           │
    user态高     system态高    iowait高
        │           │           │
   业务代码低效   系统调用频繁   磁盘IO瓶颈
        │           │           │
   ┌────┴────┐  ┌───┴───┐  ┌───┴───┐
   算法问题  GC频繁  锁竞争  Binder  数据库  文件IO
```

**原则四：闭环治理，从监控到优化形成完整闭环**：

| 阶段 | 动作 | 工具/方法 |
|------|------|---------|
| 发现 | 线上监控发现CPU异常 | APM平台告警 |
| 定位 | 线下复现，定位热点函数 | Profiler/Systrace/Perfetto |
| 优化 | 针对性优化代码 | 算法优化/缓存/异步 |
| 验证 | 回归测试，确认优化效果 | 对比前后P50/P90数据 |
| 防劣化 | CI集成性能基准测试 | 性能卡口，新代码不允许劣化超过5% |

### 9.3 CPU优化核心原则

CPU优化遵循"发现-分析-优化-验证"的循环方法论：

**做更少的事**：最有效的CPU优化是减少不必要的计算。能否通过缓存避免重复计算？能否延迟到真正需要时再计算？

**做更快的事**：当计算不可避免时，使用更高效的算法和数据结构。O(1)的HashMap查找优于O(n)的List遍历。

**做更智能的事**：利用系统特性和硬件能力——多核并行、GPU加速、延迟执行、批量处理。

CPU优化的核心目标：
- 降低CPU平均占用率：应用在前台时CPU占用率控制在20%以下（单核）
- 消除CPU尖刺：避免短时间内CPU使用率飙升到100%
- 减少后台CPU消耗：应用进入后台后CPU消耗趋近于0
- 合理利用多核：将耗时任务分配到工作线程，避免单核过载

### 9.4 CPU监控常见误区

**疑惑**：CPU监控和优化中有哪些常见的认知误区？

**答疑**：CPU相关的误区很多，主要源于对CPU工作原理的不充分理解。

**论证**：

**误区一：CPU使用率越低越好**。低CPU使用率不一定是好事。如果应用本应做计算密集型工作，CPU使用率低可能意味着程序在等待IO或被调度不合理。

**误区二：多线程一定能提升CPU利用率**。线程数远超CPU核心数时，大量上下文切换反而降低效率。最佳线程数：CPU核心数 × (1 + IO等待时间/CPU计算时间)。

**误区三：只关注Java层CPU消耗**。Native层的CPU消耗同样重要。图片解码（Skia）、网络处理（OkHttp底层）、数据库操作（SQLite引擎）等大量工作在Native层完成。

**误区四：采样越频繁监控越准确**。过高的采样频率不仅增加CPU开销，还可能因海森堡效应导致数据失真。线上监控1-5秒的采样间隔通常足够。

**误区五：CPU优化是一次性工作**。CPU性能会随功能迭代、数据量增长而变化。需要建立长效的CPU监控机制，通过CI集成性能测试持续跟踪。

**结果**：CPU监控和优化是一门系统性工程，需要理解硬件原理、操作系统调度、编程语言运行时等多层次知识。建立科学的监控和优化体系，才能持续保持应用的高性能。
