### 00 开篇导论

**0.1 一句话定位**

**列表是几乎每个 App 最高频的场景**——Feed、聊天、购物、订单都是列表。列表性能差，全 App 体验差；列表性能好，App 整体观感"快"。这是性能投入产出比最高的专项。

**0.2 为什么独立成章**

列表性能问题集中在三个特殊点：①数据量大（成千上万条）；②滚动连续触发（每秒 60 次帧渲染机会）；③视图复用（错位、抖动、重渲染）。这些问题与"普通页面"完全不同，不能用通用 UI 优化方法解决。

**0.3 与其他章的关系**

- 上承卷三·05 [UI 与布局优化](../03.流水线专项/05.页面UI与布局优化.md)：本章是 UI 优化在"列表场景"的特化
- 横联卷四·03 [图片性能](03.图片性能解码优化.md)：列表性能瓶颈常在图片解码
- 下承动画与交互响应：滚动是最敏感的交互场景

**0.4 8 个反直觉问题**

1. 为什么"分页加载"比"虚拟列表"更慢？
2. RecyclerView 的 ViewHolder 真的复用了吗？
3. 为什么"item 长得一样"反而比"长得不一样"卡？
4. 滚动时图片"先模糊后清晰"是体验更好还是更差？
5. 预加载越多越流畅吗？
6. 为什么"惯性滚动"在弱机上经常变成"匀速滚动"？
7. 滚动停止时的"重渲染"为什么必须有？
8. 为什么 iOS 列表性能普遍比 Android 好？

### 02 问题与认知

**2.1 列表性能的三个核心矛盾**

- **大量数据 vs 内存预算**：1 万条记录 ≠ 1 万个 View
- **滚动连续 vs 帧时间**：每帧只有 16ms，必须能在帧内完成 inflate + bind
- **视图复用 vs 状态正确**：复用降低开销，但错位、闪烁是常见 bug

**2.2 列表的本质是"流水线"**

```
数据源 → 数据 diff → ViewHolder 复用 → 绑定 → measure → layout → draw
```

任何一环慢，整体就掉帧。**核心是把每一环的耗时控制在 1-3ms 以内**。

**2.3 三个共识**

- **必须用虚拟列表**：长列表不虚拟化等于自残
- **复用是底线，不是优化**：没有复用就没有列表性能可言
- **图片是最大头**：列表性能优化 70% 的功夫在图片

### 03 度量与采集

**3.1 三类采集方案的本质**

**方案 A·滚动 FPS**

- **核心原理**：在滚动期间持续采样帧时长
- **工作机理**：监听 onScroll + Choreographer
- **物理本质**：FPS 是用户最直接感受
- **局限根源**：FPS 平均掩盖了"个别长帧"的痛点
- **适用场景**：常态化监控

**方案 B·绑定耗时分布**

- **核心原理**：埋点测量 onBindViewHolder/cellForRowAt 耗时
- **工作机理**：每次 bind 前后打点
- **物理本质**：归因到具体 ItemType 和数据
- **局限根源**：只覆盖业务层，不含图片解码等异步耗时
- **适用场景**：精细归因

**方案 C·首屏到稳定耗时**

- **核心原理**：测量从"打开列表"到"所有可见项稳定"的时间
- **工作机理**：监听首帧 + 所有图片加载完成事件
- **物理本质**：直接对应用户感受的"列表加载完了"
- **局限根源**：需要业务侧定义"稳定"
- **适用场景**：关键场景 SLO

**3.2 三方案差异矩阵**

| 维度 | A FPS | B 绑定 | C 首屏 |
|---|---|---|---|
| 粒度 | 帧 | 单 item | 整页 |
| 归因 | 弱 | 强 | 中 |
| 上线可用 | 是 | 是 | 是 |
| 体验关联 | 强 | 弱 | 极强 |

**3.3 跨平台同构**

| 平台 | 列表组件 | 复用机制 |
|---|---|---|
| Android | RecyclerView | ViewHolder + Pool |
| iOS | UICollectionView | reuseIdentifier |
| 前端 | react-virtualized | overscan + 节点回收 |
| 小程序 | recycle-view | 同前端思路 |

**同构本质**：所有平台都是"窗口可见 + 节点回收 + 数据 diff"三件套。

### 04 归因与定位

**4.1 列表卡顿二分决策树**

```
列表滚动卡顿
├─ 是 bind 慢还是图片慢？
│  ├─ 关闭图片显示再测
│  │  ├─ 还卡 → bind 慢，进入 §4.2
│  │  └─ 不卡 → 图片解码慢（参考图片篇）
│  └─ 选择性测
└─ 是首次进入慢还是滚动中慢？
   ├─ 首次进入 → 数据加载或首帧布局
   └─ 滚动中 → 复用机制失效或局部高耗任务
```

**4.2 bind 慢三大原因**

- **布局复杂**：嵌套层级深、约束布局频繁、自定义绘制重
- **业务计算**：每次 bind 里做格式化、正则、JSON 解析
- **图片同步加载**：bind 里走完整解码路径（应该交给异步加载库）

**4.3 复用失效的检测**

RecyclerView：开启 `setHasFixedSize(true)`、检查 ViewHolder Pool 大小、observe `onCreateViewHolder` 调用频率（高于复用率说明复用没启动）。UICollectionView：检查 reuseIdentifier 是否唯一对应一种 cell 类型。

### 05 求证实验

**5.1 实验一：虚拟化的极限收益**

**问题**：1 万条数据，全量渲染 vs 虚拟列表，性能差多少？

- **第 1 步·假设**：虚拟列表内存降 100x、首帧降 50x
- **第 2 步·设计**：构造 1 万条数据，分别用普通 ScrollView/RecyclerView，对比内存占用、首帧时间、滚动 FPS
- **第 3 步·控制变量**：同设备、同数据
- **第 4 步·指标**：内存峰值、首帧耗时、FPS P95
- **第 5 步·执行**：Android 真机
- **第 6 步·收集**：全量 ScrollView 内存 350MB（崩溃边缘）首帧 4.2s；RecyclerView 内存 18MB 首帧 80ms FPS 稳定 58
- **第 7 步·分析**：全量持有 1 万个 View 树，每个 View 平均 35KB；虚拟化只持有可见 + 缓存约 30 个
- **第 8 步·结论**：> 100 条的列表必须虚拟化，没有讨论余地
- **第 9 步·扩展**：前端虚拟列表注意 overscan 数量，太少滚动空白、太多失去优化意义

**5.2 实验二：异构列表的复用陷阱**

**问题**：同一列表里有 5 种 item 类型，复用率会降多少？

- **第 1 步·假设**：5 种类型，复用率从 95% 降到 50%
- **第 2 步·设计**：构造 5 种 ItemType（图文/纯文/视频/广告/分隔）随机交替，统计 onCreateViewHolder/onBindViewHolder 调用次数
- **第 3 步·控制变量**：滚动 1000 条
- **第 4 步·指标**：onCreate 次数（理想 ≈ ItemType × 屏幕容量）
- **第 5 步·执行**：Android RecyclerView
- **第 6 步·收集**：单类型 onCreate 18 次（屏幕容量 ≈ 6×3 缓冲）；5 类型 onCreate 90 次（5x）；FPS P95 从 60 降到 47
- **第 7 步·分析**：每种 ItemType 独立维护一个 Pool，类型越多 Pool 越分散
- **第 8 步·结论**：合并相似 ItemType；用一种"通用 layout + 数据驱动差异"代替多种独立 layout
- **第 9 步·扩展**：可手动调大 setRecycledViewPool 容量，但治标不治本

**5.3 实验三：图片解码对滚动的影响**

**问题**：列表里图片解码是不是滚动卡顿主因？

- **第 1 步·假设**：图片解码占滚动主线程时间 60%+
- **第 2 步·设计**：同一列表，分别用：①全图片占位 ②延迟解码（滚动停止后）③解码线程池 ，对比 FPS
- **第 3 步·控制变量**：同图片源、同设备
- **第 4 步·指标**：滚动期 FPS P95、滚动停止后图片就绪时间
- **第 5 步·执行**：Android + Glide
- **第 6 步·收集**：同步解码 FPS 28；延迟解码 FPS 58、停止后 80ms 图片就绪；线程池 FPS 56、就绪 50ms
- **第 7 步·分析**：图片解码 CPU 重，主线程做必然丢帧；延迟到滚动停止后是体验最佳折衷
- **第 8 步·结论**：滚动期暂停图片解码，停止后批量加载；用 RequestOptions/Kingfisher 等都支持
- **第 9 步·扩展**：iOS 上 ImageIO 默认在主线程，必须自行切换到后台 queue

### 06 治理与原则

**6.1 列表四要素**

- **虚拟化**：> 50 条必须用虚拟列表
- **复用化**：尽量减少 ItemType 数量
- **轻量化**：bind 里不做格式化、不做计算
- **异步化**：图片、视频、复杂动画都异步

**6.2 选型决策树**

```
列表场景
├─ < 50 条且简单 → 直接 ScrollView/普通列表
├─ < 1000 条标准 → RecyclerView/UICollectionView
├─ > 1000 条复杂 → 虚拟列表 + 高级复用
├─ 瀑布流 → StaggeredGridLayoutManager / 自定义
└─ 极致性能 → 自绘列表（Flutter Sliver / Compose LazyColumn）
```

**6.3 反模式清单**

- ❌ ScrollView 装大列表
- ❌ bind 里 new 对象
- ❌ 每个 item 一种 layout
- ❌ 图片同步解码
- ❌ notifyDataSetChanged 全刷
- ❌ 滚动监听里频繁 setState

**7.1 三道防线**

- **第一道·开发期**：检查 ItemType 数量上限、bind 耗时单测
- **第二道·CI**：模拟滚动跑分，FPS P95 < 55 阻断

- 列表滚动 FPS P95 ≥ 55
- 单次 bind 耗时 P95 ≤ 8ms
- 列表首屏到稳定 P95 ≤ 1s

### 08 案例与教训

**8.1 跨端同构案例·瀑布流图片错位**

某 App 瀑布流列表偶发图片错位。原因：异步加载完成时，ViewHolder 已被复用，url 不再匹配。**修法**：bind 时给 ImageView 设 tag = url，加载回调里校验 tag 一致才显示。**教训**：异步 + 复用 = 必须做"绑定校验"。

**8.2 平台特异案例·iOS UITableView 复用失效**

某 iOS App 切换 tab 后回到列表，所有 cell 重建。原因：reuseIdentifier 写成动态字符串（含 indexPath），失去了复用前提。**修法**：reuseIdentifier 必须是 ItemType 唯一对应的常量。**教训**：reuseIdentifier 是复用机制的钥匙，绝不能动态。

### 09 原理深挖

**9.1 RecyclerView 的多级缓存**

- **Scrap 缓存**：屏幕上即将移出的 View，直接复用
- **Cache 缓存**：刚移出屏幕的 View，2 个，原位 bind 不需要重新绑定
- **ViewCacheExtension**：开发者自定义
- **RecycledViewPool**：按 ItemType 分类，共享池

理解这个层级才能精准调优——比如把 setItemViewCacheSize 调大到 10 可以减少快滑时的 onBind。

**9.2 DiffUtil 的本质**

DiffUtil 用 Eugene Myers 算法计算两个列表最小编辑距离，时间复杂度 O((N+M)D)，远比全刷高效。**关键**：必须实现 areItemsTheSame（按 id 判断）和 areContentsTheSame（按内容判断），二者不同 → 触发 onChange 而非 onMove。

**9.3 Compose LazyColumn 的优化哲学**

LazyColumn 不是 RecyclerView 包装，而是基于 Layout 的"按需测量"——可见区域才进入测量阶段，看不见的 item 完全不参与 measure。这从根本上避免了"复用机制 + 状态保持"的复杂性。

### 10 总结与扩展

**10.1 一图概括**

```
列表性能
    ├─ 数据 → 虚拟化（> 100 条）
    ├─ 复用 → ItemType 收敛
    ├─ bind → 1ms 极简原则
    ├─ 图片 → 异步 + 滚动停止后加载
    └─ 监控 → FPS P95 + 复用率
```

**10.2 三个外延**

- **声明式 UI 趋势**：Compose/SwiftUI 的 Lazy 列表是新范式
- **服务端预渲染**：Feed 服务端先做布局计算，端只渲染
- **预测式预加载**：根据滚动速度智能预加载下 N 屏

**10.3 给团队的建议**

- 第 1 周：审计所有列表，超 50 条全部虚拟化
- 第 2 周：合并 ItemType，做到主流列表 ≤ 3 种
- 第 3 周：图片库统一接入滚动暂停机制
- 第 4 周：上线 FPS + 复用率监控

列表是一个 App 的"性能门面"——这一关过不去，再好的其他场景也救不回用户的"卡"印象。
