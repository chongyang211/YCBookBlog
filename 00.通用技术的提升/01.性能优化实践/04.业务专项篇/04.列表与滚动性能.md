### 00 开篇导论

**0.1 一句话定位**

**列表是几乎每个 App 最高频的场景**——Feed、聊天、购物、订单都是列表。列表性能差，全 App 体验差；列表性能好，App 整体观感"快"。这是性能投入产出比最高的专项。

**0.2 为什么独立成章**

列表性能问题集中在三个特殊点：①数据量大（成千上万条）；②滚动连续触发（每秒 60 次帧渲染机会）；③视图复用（错位、抖动、重渲染）。这些问题与"普通页面"完全不同，不能用通用 UI 优化方法解决。

**0.3 与其他章的关系**

- 上承卷三·05 [UI 与布局优化](../03.流水线专项/05.页面UI与布局优化.md)：本章是 UI 优化在"列表场景"的特化
- 横联卷四·03 [图片性能](03.图片性能解码优化.md)：列表性能瓶颈常在图片解码
- 下承动画与交互响应：滚动是最敏感的交互场景

**0.4 8 个反直觉问题**

1. 为什么"分页加载"比"虚拟列表"更慢？
2. RecyclerView 的 ViewHolder 真的复用了吗？
3. 为什么"item 长得一样"反而比"长得不一样"卡？
4. 滚动时图片"先模糊后清晰"是体验更好还是更差？
5. 预加载越多越流畅吗？
6. 为什么"惯性滚动"在弱机上经常变成"匀速滚动"？
7. 滚动停止时的"重渲染"为什么必须有？
8. 为什么 iOS 列表性能普遍比 Android 好？

### 00.5 贯穿案例：社交 App"信息流 12fps 滑动卡死"事件

> 本案例贯穿全文：§02 看懂矛盾、§03/§04 用方案+决策树定位、§05 用实验复盘、§06 给出分层闭环。

#### 案例背景

某头部社交 App V9.5 重构信息流列表（产品要求"支持图文/视频/直播预览/广告/推荐位/卡片 6 种 item 类型"），上线后用户反馈崩塌：

- **列表稳态 FPS 仅 12-18**（之前 56），用户大量"滑不动"投诉。
- **首屏到稳定耗时 P95 = 5.8s**（之前 1.2s）。
- **OOM 率从 0.2% 飙到 4.5%**（中低端机）。
- **客服收到"App 越用越卡"的差评每天 6000+**。
- DAU 1500 万的产品，活跃时长下降 22%。

研发组初步反应："新功能多，肯定慢点，是数据量大。"——这是典型的"功能背锅"。

#### 经验派的 3 周折腾（典型反面教材）

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 把分页改为"加载更多"按钮（怕全部加载）| 用户反感按钮，但**滑动 FPS 还是 12-18**（虚拟化问题没解决）|
| 第 2 周 | 加大 RecycledViewPool 容量到 50（怕复用不够）| 内存涨 60MB，FPS 微涨到 22 |
| 第 3 周 | 把图片质量统一降低（怕解码慢）| 视觉降级，运营投诉，FPS 无明显变化 |

**复盘**：三周折腾错在"症状疗法 + 不分析根因"。**列表性能问题永远是三个维度**：虚拟化、复用率、单 bind 耗时。**经验派碰这碰那但从未直接攻击这三个维度的核心**。

#### 方法派的 6 天闭环

**Day 1（§03/§04 系统分析）**：

- 方案 A（FPS）：稳态 12-18，长尾帧达 250ms。
- 方案 B（bind 耗时）：单 bind P99 = 180ms（标准 < 8ms 的 22 倍）。
- 方案 C（首屏到稳定）：P95 = 5.8s。

→ 三个数据全爆，**典型三维度全失守**。

**Day 2（深度归因）**：

- 测试虚拟化：开启 `setHasFixedSize(true)` 后 FPS 升到 28 → **虚拟化部分失效**。
- 测试复用率：onCreateViewHolder 在 1000 滚动中调用 380 次（应 ≈ 屏幕容量 × ItemType 数 ≈ 30）→ **6 种 ItemType 让 Pool 极度分散**。
- 测试 bind 内容：bind 里同步格式化时间、解析 JSON、加载图片 → **三件重活全在主线程**。

**Day 3-5（§06 分层策略落地）**：

- 第 1 层（虚拟化）：补全 RecyclerView 配置，确认 LinearLayoutManager 正确使用。
- 第 2 层（复用率治理）：6 种 ItemType 合并为 3 种通用 layout + 数据驱动差异 → onCreate 调用 380 → 35 次。
- 第 3 层（bind 减负）：时间格式化预计算入数据模型；图片改 Glide 异步 + 滚动暂停；JSON 解析放数据层。
- 第 4 层（图片治理）：滚动期暂停解码（[`卷四·03 §6.4 策略 4.1`](03.图片性能解码优化.md)），停止后批量加载。

**Day 6（上线 + 灰度验证）**：

#### 上线效果

| 指标 | 经验派 3 周后 | 方法派 6 天后 |
|---|---|---|
| 稳态 FPS | 22 | **58** |
| 长尾帧 P99 | 200 ms | **18 ms** |
| 单 bind P99 | 150 ms | **6 ms** |
| 首屏到稳定 P95 | 5.5s | **1.0s** |
| OOM 率 | 4.0% | **0.3%** |
| onCreateViewHolder 频次 | 380/千滚动 | **35**（复用率 91%）|
| 活跃时长 | -22% | **+5%** |

**核心洞察**：列表性能问题**永远在三个维度上找拐点**：虚拟化（数据→视图比例）、复用率（ItemType 收敛）、bind 耗时（单帧预算）。**经验派 3 周折腾的所有动作都是症状疗法**，方法派 6 天直击三维度根因。

#### 案例如何串起本文

- **§02 三核心矛盾** ▶▶ 案例三维度全失守是反面教材。
- **§03 方案组合** ▶▶ 必须 A+B+C 才能定位。
- **§04 决策树** ▶▶ 三个分支（bind 慢 / 图片慢 / 首屏慢）同时走。
- **§05 求证实验** ▶▶ §5.1 + §5.2 + §5.3 + §5.4 + §5.5 都在案例中变现。
- **§06 分层策略** ▶▶ "虚拟化→复用→bind→图片"四层正是案例落地路径。

### 02 问题与认知

**2.1 列表性能的三个核心矛盾**

- **大量数据 vs 内存预算**：1 万条记录 ≠ 1 万个 View
- **滚动连续 vs 帧时间**：每帧只有 16ms，必须能在帧内完成 inflate + bind
- **视图复用 vs 状态正确**：复用降低开销，但错位、闪烁是常见 bug

> ▶▶ **回扣 §00.5 案例**：信息流三维度全失守正是本节"三核心矛盾"全部命中——大量数据未虚拟化、滚动期 bind 180ms 远超 16ms 帧预算、6 种 ItemType 让复用机制失效。**三个矛盾任一失守都会让 FPS 跌到 < 30**。

**2.2 列表的本质是"流水线"**

```
数据源 → 数据 diff → ViewHolder 复用 → 绑定 → measure → layout → draw
```

任何一环慢，整体就掉帧。**核心是把每一环的耗时控制在 1-3ms 以内**。

**2.3 三个共识**

- **必须用虚拟列表**：长列表不虚拟化等于自残
- **复用是底线，不是优化**：没有复用就没有列表性能可言
- **图片是最大头**：列表性能优化 70% 的功夫在图片

### 03 度量与采集

**3.1 三类采集方案的本质**

**方案 A·滚动 FPS**

- **核心原理**：在滚动期间持续采样帧时长
- **工作机理**：监听 onScroll + Choreographer
- **物理本质**：FPS 是用户最直接感受
- **局限根源**：FPS 平均掩盖了"个别长帧"的痛点
- **适用场景**：常态化监控

**方案 B·绑定耗时分布**

- **核心原理**：埋点测量 onBindViewHolder/cellForRowAt 耗时
- **工作机理**：每次 bind 前后打点
- **物理本质**：归因到具体 ItemType 和数据
- **局限根源**：只覆盖业务层，不含图片解码等异步耗时
- **适用场景**：精细归因

**方案 C·首屏到稳定耗时**

- **核心原理**：测量从"打开列表"到"所有可见项稳定"的时间
- **工作机理**：监听首帧 + 所有图片加载完成事件
- **物理本质**：直接对应用户感受的"列表加载完了"
- **局限根源**：需要业务侧定义"稳定"
- **适用场景**：关键场景 SLO

**3.2 三方案差异矩阵**

| 维度 | A FPS | B 绑定 | C 首屏 |
|---|---|---|---|
| 粒度 | 帧 | 单 item | 整页 |
| 归因 | 弱 | 强 | 中 |
| 上线可用 | 是 | 是 | 是 |
| 体验关联 | 强 | 弱 | 极强 |

**3.3 跨平台同构**

| 平台 | 列表组件 | 复用机制 |
|---|---|---|
| Android | RecyclerView | ViewHolder + Pool |
| iOS | UICollectionView | reuseIdentifier |
| 前端 | react-virtualized | overscan + 节点回收 |
| 小程序 | recycle-view | 同前端思路 |

**同构本质**：所有平台都是"窗口可见 + 节点回收 + 数据 diff"三件套。

### 04 归因与定位

**4.1 列表卡顿二分决策树**

```
列表滚动卡顿
├─ 是 bind 慢还是图片慢？
│  ├─ 关闭图片显示再测
│  │  ├─ 还卡 → bind 慢，进入 §4.2
│  │  └─ 不卡 → 图片解码慢（参考图片篇）
│  └─ 选择性测
└─ 是首次进入慢还是滚动中慢？
   ├─ 首次进入 → 数据加载或首帧布局
   └─ 滚动中 → 复用机制失效或局部高耗任务
```

> ▶▶ **回扣 §00.5 案例**：决策树两条路径同时走——bind 慢（180ms 主线程同步格式化）+ 图片慢（同步解码）。**经验派从未走过这个决策树，所以三周方向全错**。

**4.2 bind 慢三大原因**

- **布局复杂**：嵌套层级深、约束布局频繁、自定义绘制重
- **业务计算**：每次 bind 里做格式化、正则、JSON 解析
- **图片同步加载**：bind 里走完整解码路径（应该交给异步加载库）

**4.3 复用失效的检测**

RecyclerView：开启 `setHasFixedSize(true)`、检查 ViewHolder Pool 大小、observe `onCreateViewHolder` 调用频率（高于复用率说明复用没启动）。UICollectionView：检查 reuseIdentifier 是否唯一对应一种 cell 类型。

### 05 求证实验

**5.1 实验一：虚拟化的极限收益**

**问题**：1 万条数据，全量渲染 vs 虚拟列表，性能差多少？

- **假设**：虚拟列表内存降 100x、首帧降 50x
- **设计**：构造 1 万条数据，分别用普通 ScrollView/RecyclerView，对比内存占用、首帧时间、滚动 FPS
- **数据**：全量 ScrollView 内存 350MB（崩溃边缘）首帧 4.2s；RecyclerView 内存 18MB 首帧 80ms FPS 稳定 58
- **结论**：> 100 条的列表必须虚拟化，没有讨论余地
- **扩展**：前端虚拟列表注意 overscan 数量，太少滚动空白、太多失去优化意义

**5.2 实验二：异构列表的复用陷阱**

**问题**：同一列表里有 5 种 item 类型，复用率会降多少？

- **假设**：5 种类型，复用率从 95% 降到 50%
- **设计**：构造 5 种 ItemType（图文/纯文/视频/广告/分隔）随机交替，统计 onCreateViewHolder/onBindViewHolder 调用次数
- **数据**：单类型 onCreate 18 次（屏幕容量 ≈ 6×3 缓冲）；5 类型 onCreate 90 次（5x）；FPS P95 从 60 降到 47
- **结论**：合并相似 ItemType；用一种"通用 layout + 数据驱动差异"代替多种独立 layout

> ▶▶ **回扣 §00.5 案例**：信息流 6 种 ItemType 导致 onCreate 380 次（标准 30 的 12 倍）——本实验"5 类型让 onCreate 5×"的真实化身。方法派 Day 3 合并到 3 种通用 layout 后 onCreate 降到 35 次。**ItemType 数量是列表性能的隐形杀手**。

**5.3 实验三：图片解码对滚动的影响**

**问题**：列表里图片解码是不是滚动卡顿主因？

- **假设**：图片解码占滚动主线程时间 60%+
- **数据**：同步解码 FPS 28；延迟解码（滚动停止后）FPS 58、停止后 80ms 图片就绪；线程池 FPS 56、就绪 50ms
- **结论**：滚动期暂停图片解码，停止后批量加载

**5.4 实验四：DiffUtil 比 notifyDataSetChanged 的真实收益**

**问题**：列表数据变更，用 `notifyDataSetChanged()` 全刷 vs `DiffUtil` 局部刷，性能差多少？

- **假设**：DiffUtil 在小更新（< 10% 变更）场景下显著优于全刷。
- **设计**：1000 条列表，新增 1 条 / 修改 1 条 / 删除 1 条 三种场景。
- **数据**：

| 场景 | notifyDataSetChanged | DiffUtil |
|---|---|---|
| 新增 1 条 | 重建所有 ViewHolder ≈ 250ms | 仅 1 个 onBind 8ms |
| 修改 1 条内容 | 同上 | 触发 onBindPayload 5ms |
| 删除 1 条 | 同上 | 1 个 remove 动画 + 平移 |
| 1000 条增量 update | 250ms | 50ms（diff 算法 + 增量更新）|

- **结论**：**90% 的列表更新场景应用 DiffUtil + ListAdapter**。
- **扩展**：必须正确实现 areItemsTheSame（按 id）+ areContentsTheSame（按内容）。

**5.5 实验五：声明式 Lazy 列表 vs 命令式 RecyclerView 的真实性能**

**问题**：Compose LazyColumn / SwiftUI List 相比 RecyclerView / UITableView 性能如何？

- **假设**：Compose 首帧略慢，稳态相当；启用 Baseline Profiles 后超越。
- **数据**：

| 实现 | 首帧 TTI | 滚动 FPS | 内存 |
|---|---|---|---|
| RecyclerView | 380ms | 58 | 110MB |
| Compose LazyColumn | 480ms | 58 | 135MB |
| Compose + Baseline Profiles | **320ms** | **60** | 135MB |

- **结论**：声明式 Lazy 列表配 Baseline Profiles 是新一代列表的最佳实践。
- **扩展**：见 [`卷三·05 §5.5`](../03.流水线专项/05.页面UI与布局优化.md)。

**5.6 五大实验启示**

```
   虚拟化           → 内存 -95%、首帧 -50×                ─┐
                                                          │
   异构 ItemType    → 类型每多 1 种，onCreate 翻倍         │
                                                          │
   图片同步解码     → FPS 28 → 58（暂停 + 异步）          ├─▶ 列表 = 虚拟化 + 复用 + bind 减负 + 图片治理 + 声明式范式
                                                          │
   DiffUtil vs 全刷  → 增量场景 5× 提速                    │
                                                          │
   Compose Lazy 列表 → 配 Baseline Profiles 超越命令式     ─┘
```

### 06 优化策略深化

> 本节回答四个递进问题：**①如何保证虚拟化生效？②如何让复用率最大化？③如何让 bind 极简？④如何让图片不卡滚动？**

#### 6.1 第一层：虚拟化（数据 vs 视图的比例约束）

**核心命题**：[§5.1 实验](#05-求证实验) 证明虚拟化是列表性能的物理底线。

**策略 1.1：> 50 条数据必须虚拟化**

- **代码**：RecyclerView / UICollectionView / react-virtualized / Compose LazyColumn 都是虚拟化容器。
- **反例**：ScrollView + ForEach 装大列表是禁忌。
- **收益**：内存 350MB → 18MB；首帧 4.2s → 80ms。
- **边界**：< 50 条且简单可用普通 ScrollView。

**策略 1.2：固定高度 + setHasFixedSize**

- **机理**：固定高度避免动态测量，setHasFixedSize 跳过部分重新计算。
- **代码**：

```kotlin
recyclerView.setHasFixedSize(true)
// XML 里 RecyclerView 高度用 match_parent 而非 wrap_content
```

- **收益**：滚动测量耗时 -30%。
- **边界**：动态高度场景不适用（如瀑布流）。

**策略 1.3：前端虚拟列表 overscan 调优**

- **机理**：可见区域外预留几个 item，避免快速滚动空白。
- **代码**（react-window）：

```jsx
<FixedSizeList overscanCount={3} ... />
```

- **收益**：滚动流畅度提升；空白率下降。
- **边界**：overscan 太多失去虚拟化意义；典型 2-5。

---

#### 6.2 第二层：复用率最大化（ItemType 收敛）

**核心命题**：[§5.2 实验](#52-实验二异构列表的复用陷阱) + [§00.5 案例](#005-贯穿案例社交-app信息流-12fps-滑动卡死事件) 证明 ItemType 数量是隐形杀手。

**策略 2.1：合并相似 ItemType（通用 layout + 数据驱动差异）**

- **机理**：把 6 种类型合并为 2-3 种通用模板，差异由数据控制。
- **代码**：

```kotlin
// 反例：6 种类型
override fun getItemViewType(position: Int) = when (items[position].type) {
    "image" -> 0; "text" -> 1; "video" -> 2; "live" -> 3; "ad" -> 4; "rec" -> 5
}

// 正例：3 种通用类型
override fun getItemViewType(position: Int) = when {
    items[position].hasMedia -> TYPE_MEDIA  // 包含 image/video/live
    items[position].isAd -> TYPE_AD
    else -> TYPE_TEXT  // 包含 text/rec
}
```

- **收益**：[§00.5 案例](#005-贯穿案例社交-app信息流-12fps-滑动卡死事件) onCreate 380 → 35（复用率 91%）。
- **边界**：通用模板可能 layout 略复杂，需权衡。

**策略 2.2：reuseIdentifier 必须是常量（iOS）**

- **机理**：[§8.2 案例](#08-案例与教训) 反面教材。
- **代码**：

```swift
// 反例
let id = "Cell_\(indexPath.row)"  // 动态，失去复用

// 正例
static let cellId = "MyCell"  // 常量
```

- **收益**：复用机制正常运行。
- **边界**：必须按 type 而非 index。

**策略 2.3：RecycledViewPool 跨列表共享**

- **机理**：多个相似列表共享 ViewHolder 池。
- **代码**：

```kotlin
val sharedPool = RecyclerView.RecycledViewPool()
listA.setRecycledViewPool(sharedPool)
listB.setRecycledViewPool(sharedPool)
```

- **收益**：列表切换零开销。
- **边界**：ItemType 必须严格对应。

---

#### 6.3 第三层：bind 减负（每次 < 8ms）

**核心命题**：[§5.3 实验](#53-实验三图片解码对滚动的影响) 证明 bind 重活是 FPS 杀手。

**策略 3.1：bind 内禁止格式化/JSON 解析**

- **机理**：预计算入数据模型。
- **代码**：

```kotlin
// 反例
holder.timeTv.text = SimpleDateFormat("yyyy-MM-dd HH:mm").format(Date(item.ts))

// 正例：数据模型预格式化
data class Item(val ts: Long) {
    val formattedTime: String by lazy { /* 预格式化 */ }
}
holder.timeTv.text = item.formattedTime  // 仅赋值
```

- **收益**：bind P99 180ms → 6ms。
- **边界**：lazy 计算首次仍有开销，需在后台预热。

**策略 3.2：bind 内异步图片加载**

- **机理**：[`卷四·03 §6.2 策略 2.2`](03.图片性能解码优化.md)。
- **代码**：Glide / Coil / SDWebImage / Kingfisher 都默认异步。
- **收益**：主线程 bind 时间不含图片解码。
- **边界**：异步回调需校验 view 未被复用（用 tag 校验）。

**策略 3.3：onBindPayload 增量更新**

- **机理**：DiffUtil 计算出"哪部分变了"，只更新变化部分。
- **代码**：

```kotlin
override fun onBindViewHolder(holder: VH, position: Int, payloads: List<Any>) {
    if (payloads.isEmpty()) {
        // 全量 bind
        bindFull(holder, items[position])
    } else {
        // 增量 bind（如只更新点赞数）
        bindPartial(holder, payloads)
    }
}
```

- **收益**：增量场景 bind 时间 -90%。
- **边界**：需正确实现 DiffUtil getChangePayload。

**策略 3.4：onBindViewHolder 异步预测算**

- **机理**：见 [`卷三·05 §6.4 策略 4.2`](../03.流水线专项/05.页面UI与布局优化.md)。
- **收益**：中端机 FPS 38 → 56。
- **边界**：异步回调需校验 position。

---

#### 6.4 第四层：图片治理（70% 列表性能瓶颈）

**核心命题**：[§5.3 实验](#53-实验三图片解码对滚动的影响) + [§2.3](#02-问题与认知) 三个共识第 3 条。

**策略 4.1：滚动期暂停图片解码**

- **机理**：[§5.3 实验](#53-实验三图片解码对滚动的影响) FPS 28 → 58。
- **代码**：

```kotlin
recyclerView.addOnScrollListener(object : OnScrollListener() {
    override fun onScrollStateChanged(rv: RecyclerView, state: Int) {
        when (state) {
            SCROLL_STATE_DRAGGING -> Glide.with(rv.context).pauseRequests()
            SCROLL_STATE_IDLE -> Glide.with(rv.context).resumeRequests()
        }
    }
})
```

- **收益**：滚动 FPS 大幅提升。
- **边界**：用户停止后会有 50-80ms"图片加载延迟"。

**策略 4.2：按 ImageView 尺寸下采样**

- **机理**：[`卷四·03 §6.2 策略 2.1`](03.图片性能解码优化.md)。
- **收益**：内存 -90%、解码 -80%。
- **边界**：见图片篇。

**策略 4.3：滚出屏幕的 view 立即取消图片加载**

- **机理**：[`卷四·03 §6.4 策略 4.1`](03.图片性能解码优化.md)。
- **代码**：

```kotlin
override fun onViewRecycled(holder: VH) {
    Glide.with(holder.itemView.context).clear(holder.imageView)
}
```

- **收益**：快速滑动 CPU -30%。
- **边界**：用户回滑需重新加载（命中内存缓存仍快）。

**策略 4.4：异步绑定校验防错位**

- **机理**：[§8.1 案例](#08-案例与教训)。
- **代码**：

```kotlin
holder.imageView.tag = item.imageUrl
asyncLoad(item.imageUrl) { bm ->
    if (holder.imageView.tag == item.imageUrl) {  // 校验未被复用
        holder.imageView.setImageBitmap(bm)
    }
}
```

- **收益**：图片错位 bug 清零。
- **边界**：tag key 不能与业务冲突。

### 08 案例与教训

**8.1 跨端同构案例·瀑布流图片错位**

某 App 瀑布流列表偶发图片错位。原因：异步加载完成时，ViewHolder 已被复用，url 不再匹配。**修法**：bind 时给 ImageView 设 tag = url，加载回调里校验 tag 一致才显示。**教训**：异步 + 复用 = 必须做"绑定校验"。

**8.2 平台特异案例·iOS UITableView 复用失效**

某 iOS App 切换 tab 后回到列表，所有 cell 重建。原因：reuseIdentifier 写成动态字符串（含 indexPath），失去了复用前提。**修法**：reuseIdentifier 必须是 ItemType 唯一对应的常量。**教训**：reuseIdentifier 是复用机制的钥匙，绝不能动态。

### 09 原理深挖

**9.1 RecyclerView 的多级缓存**

- **Scrap 缓存**：屏幕上即将移出的 View，直接复用
- **Cache 缓存**：刚移出屏幕的 View，2 个，原位 bind 不需要重新绑定
- **ViewCacheExtension**：开发者自定义
- **RecycledViewPool**：按 ItemType 分类，共享池

理解这个层级才能精准调优——比如把 setItemViewCacheSize 调大到 10 可以减少快滑时的 onBind。

**9.2 DiffUtil 的本质**

DiffUtil 用 Eugene Myers 算法计算两个列表最小编辑距离，时间复杂度 O((N+M)D)，远比全刷高效。**关键**：必须实现 areItemsTheSame（按 id 判断）和 areContentsTheSame（按内容判断），二者不同 → 触发 onChange 而非 onMove。

**9.3 Compose LazyColumn 的优化哲学**

LazyColumn 不是 RecyclerView 包装，而是基于 Layout 的"按需测量"——可见区域才进入测量阶段，看不见的 item 完全不参与 measure。这从根本上避免了"复用机制 + 状态保持"的复杂性。

### 10 总结与扩展

**10.1 一图概括**

```
列表性能
    ├─ 数据 → 虚拟化（> 50 条）
    ├─ 复用 → ItemType 收敛（≤ 3 种）
    ├─ bind → 1-8ms 极简原则
    ├─ 图片 → 异步 + 滚动停止后加载
    └─ 监控 → FPS P95 + 复用率
```

**10.2 五条核心原则**

1. **虚拟化是底线**：[§5.1](#05-求证实验) > 50 条必须。
2. **ItemType 收敛**：[§5.2](#52-实验二异构列表的复用陷阱) 6 → 3 让 onCreate -90%。
3. **bind 1-8ms**：[§00.5 案例](#005-贯穿案例社交-app信息流-12fps-滑动卡死事件) 180ms → 6ms 是关键。
4. **图片占 70% 瓶颈**：滚动暂停 + 下采样 + clear 是组合拳。
5. **数据驱动**：[§5.5](#55-实验五声明式-lazy-列表-vs-命令式-recyclerview-的真实性能) 选型必须看数据。

**10.3 五个常见误区**

1. **"加大 Pool 治复用"**：错（治标）。
2. **"降图片质量治卡顿"**：错（视觉牺牲）。
3. **"notifyDataSetChanged 简单就用"**：错（5× 慢）。
4. **"声明式 UI 默认更快"**：错（需 Baseline Profiles）。
5. **"ItemType 多没关系"**：错（隐形杀手，[§00.5 案例](#005-贯穿案例社交-app信息流-12fps-滑动卡死事件)）。

**10.4 三个外延**

- **声明式 UI 趋势**：Compose/SwiftUI 的 Lazy 列表是新范式
- **服务端预渲染**：Feed 服务端先做布局计算，端只渲染
- **预测式预加载**：根据滚动速度智能预加载下 N 屏

**10.5 给团队的建议**

- 第 1 周：审计所有列表，超 50 条全部虚拟化
- 第 2 周：合并 ItemType，做到主流列表 ≤ 3 种
- 第 3 周：图片库统一接入滚动暂停机制
- 第 4 周：上线 FPS + 复用率监控
