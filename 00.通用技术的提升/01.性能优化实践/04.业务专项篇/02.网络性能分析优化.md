- **本文卷归属**：卷四 · 业务篇 · 第 2 篇
- **本文目标层级**：L2 进阶 → L3 专家
- **适用平台**：Android / iOS / Web / 嵌入式（联网设备）
- **前置阅读**：
  - [`卷零·02 跨平台性能模型与指标体系`](../00.公共方法论/02.跨平台指标体系.md)
- **本文核心命题**：
  > **网络性能 = 协议层效率 × 业务层调度**。  
  > 协议层（DNS / TCP / TLS / HTTP）决定每次请求的最小代价；业务层（请求合并 / 缓存 / 并发 / 弱网容错）决定如何最少地用网络。  
  > 一切优化都是在这两个维度上"减少请求数 × 减少每次请求开销"。

## 00.5 贯穿案例：跨境电商东南亚弱网"首屏 8 秒"事件

> 本案例贯穿全文：§01 看懂代价、§02 拿到协议层模型、§03/§04 用三方案+决策树定位、§05 用实验复盘、§06 给出分层策略闭环。

### 案例背景

某跨境电商 V5.2 出海东南亚（印尼/越南/菲律宾），首屏体验在国内一片好评，到了东南亚却问题暴露：

- 印尼 4G 用户首屏 P50 = **3.8s**，P95 = **8.2s**。
- 失败率从国内 0.3% 飙到 **6.7%**。
- 应用商店一周内涌入大量"打不开"差评，下载转化率掉 18%。
- BD 团队压力极大：**每天损失约 80 万 GMV**。

研发组初步排查："是当地网络差，没办法。"——这是典型的"环境无解论"。

### 经验派的 3 周折腾（典型反面教材）

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 把超时从 10s 改 60s（怀疑超时太短）| **失败率反而升到 8.1%**：用户等不及自己关了页面 |
| 第 2 周 | 加 5 次激进重试（怀疑偶发失败）| 服务端被打到限流，部分用户彻底打不开 |
| 第 3 周 | 把首屏 6 个 API 改成全并发（怀疑串行慢）| 弱网下连接数过多，TCP 全部握手失败 |

**复盘**：三周里所有动作都基于"加大-加多-加快"的直觉，本质是把强网思维硬套到弱网。**弱网不是"网慢点的强网"，是物理特性完全不同的环境**。

### 方法派的 7 天闭环

新接手的同学按本文方法论重做：

**Day 1（§02 第一性原理）**：用"距离 × 带宽"模型重新理解。中国服务端 → 印尼 RTT = 80ms（光速近极限），但当地运营商 4G 平均丢包 8%、RTT 抖动 50-300ms。**这是"高 RTT + 高丢包"的典型 C 类问题（[§2.2 协议层效率模型](#22-协议层效率模型)）**。

**Day 2（§03 三方案组合）**：方案①+②+③同时上：

- 方案①：OkHttp Interceptor 上报每次请求的总耗时和错误码。
- 方案②：EventListener 拆 DNS / TCP / TLS / TTFB / 传输 5 阶段。
- 方案③：mitmproxy 抓包看真实数据包行为。

抓到的关键数据（弱网首屏 6 个 API）：

| 阶段 | 平均耗时 | 占比 |
|---|---|---|
| DNS（系统）| 850 ms | 22% |
| TCP 握手 | 240 ms | 6% |
| TLS 握手 | 620 ms（带丢包重传）| 16% |
| TTFB | 380 ms | 10% |
| 传输 | 1700 ms（响应体大 + 丢包重传）| 45% |
| **总单次** | ≈ **3.8s** | 100% |

→ **DNS 慢 + TLS 重传 + 响应体太大**三大头部问题，与第 4.1 决策树对应。

**Day 3（§04 归因决策树）**：4 类问题分别走不同路径：

- DNS 慢 → 阶段 A（DNS 优化）→ 用 HttpDns + IP 池 fallback。
- TLS 慢 → 阶段 B（连接优化）→ HTTP/3 0-RTT + TLS 1.3 + Session Resumption。
- 响应体大 → 阶段 D（数据优化）→ Protobuf + brotli + 字段裁剪。
- 弱网放大 → 弱网容错分支 → 智能超时 + 指数退避 + 服务端边缘部署。

**Day 4（§06 分层策略，按四层施治）**：

- 第 1 层（协议层）：HttpDns + HTTP/3 + TLS 1.3 + 边缘 CDN（雅加达节点）。
- 第 2 层（业务层）：6 API 合并为 2 个聚合 API；首屏关键资源 inline 到 HTML。
- 第 3 层（弱网容错）：超时按弱网识别动态调整（强网 5s / 弱网 15s）；指数退避重试 1s/3s/9s；最多 2 次。
- 第 4 层（监控）：地区维度看板，按"国家×网络类型"细分。

**Day 5-6（§05 求证实验思路验证）**：构造印尼 4G 流量回放，灰度对比验证。

**Day 7（上线复盘）**：

### 上线效果

| 指标 | 经验派 3 周后 | 方法派 7 天后 |
|---|---|---|
| 印尼首屏 P50 | 3.8s | **1.1s** |
| 印尼首屏 P95 | 8.2s | **2.4s** |
| 失败率 | 8.1% | **0.6%** |
| GMV/日 | -80 万（损失）| **+45 万**（同比涨）|
| 应用商店评分 | 3.4 | 4.6 |

**核心洞察**：弱网治理 ≠ 强网思维 + 超时拉长。**HTTP/3 的 0-RTT 在丢包场景下让首屏 TLS 阶段从 620ms→0ms（复用 Session），是单次最大收益**。这正是 [§5.1 实验](#51-实验一握手开销) 工程意义"首次连接慢可用 HTTP/3 0-RTT 缓解"的真实落地。

### 案例如何串起本文

- **§01 现象与代价** ▶▶ 业务损失映射：每天 80 万 GMV。
- **§02 协议层效率模型** ▶▶ 印尼场景是 C 类（弱网放大）+ A 类（连接开销）的混合。
- **§03 三方案组合** ▶▶ 必须 ①+②+③ 才能定位"DNS 慢 + TLS 重传 + 响应体大"三段。
- **§04 归因决策树** ▶▶ 4 个根因走 4 条路径，正是决策树设计目的。
- **§05 求证实验** ▶▶ §5.1 握手开销、§5.2 弱网超时、§5.4 HTTP/3 增益都在案例中变现。
- **§06 分层策略** ▶▶ "协议→业务→弱网→监控"四层正是案例落地路径。

## 01.问题域定义

### 1.1 现象与代价

网络性能问题的用户感知：

- **首屏加载慢**：API 慢 → 页面白屏 / 骨架屏停留过久。
- **图片加载慢 / 闪烁**：图片下载慢 / 失败重试。
- **操作无响应**：点击后等待 API 返回，无 loading 反馈。
- **离线 / 弱网"假死"**：弱网下请求长时间不返回又不超时。
- **流量浪费**：重复请求、压缩不充分、协议头冗余。

**业务代价**：

- 头部应用：API P99 每降 100ms，留存 +0.5%、转化率 +1%。
- 弱网下用户操作放弃率比强网高 5-10 倍。
- 流量过度消耗会让用户主动停用应用（特别是预付费 / 国际场景）。

> ▶▶ **回扣 §00.5 案例**：跨境电商东南亚弱网首屏 P50=3.8s 直接对应"放弃率比强网高 5-10 倍"的真实样本——失败率从国内 0.3% 飙到 6.7%，**每天 80 万 GMV 流失**。这就是"业务代价"的钱袋打击：网络性能不是工程美学，而是直接 ROI 杠杆。

### 1.2 度量准则

按 [`卷零·02 §3`](../00.公共方法论/02.跨平台指标体系.md) 指标体系：

**资源视角（USE）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 带宽利用率 | 实际下载速率 / 链路上限 | > 60%（理想情况）|
| 连接数饱和 | 同时活跃 TCP 连接 | < 10 |
| 失败率 | 请求失败 / 总请求 | < 1% |

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| API P50 | 中位响应时长 | < 200ms |
| API P95 | 95% 分位 | < 800ms |
| API P99 | 长尾 | < 2s |
| API 失败率（Errors）| | < 0.5% |
| 弱网超时率 | 仅弱网下 | < 5% |

**用户感知（APDEX）**：

- *Satisfied*：API < 1s
- *Tolerating*：1-3s
- *Frustrated*：> 3s 或失败

### 1.3 行业基准与目标

| 平台 | API P50 | API P99 | 失败率 |
|---|---|---|---|
| Android / iOS（4G）| 200ms | < 1s | < 0.5% |
| Web（4G） | LCP < 2.5s | TTI < 5s | < 1% |
| 弱网（< 100Kbps）| 1s | < 5s | < 5% |

### 1.4 反直觉问题清单

带着这些问题阅读：

1. HTTPS 比 HTTP 慢多少？是不是必须用 HTTPS？
2. HTTP/2 一定比 HTTP/1.1 快吗？

## 02.第一性原理

### 2.1 网络性能本质

**一句话定义**：

> **网络性能 = 单位时间能完成多少有效数据传输 + 平均每次传输的延迟**。

这句话隐含三个不可商量的物理约束：

**约束一：网络是"距离 × 带宽"的硬约束**

物理光速决定了最小 RTT（Round Trip Time）：

```
   北京 → 美西：~150ms RTT（光速理论下限 ~100ms + 路由延迟）
   北京 → 上海：~30ms RTT
   北京 → 北京：~5-20ms RTT
```

**这是物理硬约束**：任何"加速"都不能让数据包跑得比光快。优化只能是"减少往返次数"。

**约束二：网络协议有固定开销**

每次连接都要：

```
   DNS 查询    50-500ms（视缓存）
   TCP 握手    1 RTT（~30-150ms）
   TLS 握手    1-2 RTT（HTTPS）
   HTTP 请求   1 RTT（请求 + 响应）
   ─────────────────────────────────
   首次请求    3-5 RTT = 100-700ms（仅协议开销）
```

这就是为什么"连接复用"如此重要：复用连接省去 DNS + TCP + TLS 三次握手。

**约束三：弱网会指数级放大问题**

弱网（高 RTT + 高丢包）下，TCP 重传 + TLS 握手丢包都会让单次请求时间从 100ms 涨到几秒甚至超时。**弱网治理是网络优化的最大变量**。

### 2.2 协议层效率模型

**为什么"协议层效率"是网络治理的核心**

每个协议都在做"功能 vs 性能"的取舍：

```
   ┌──────────────────────────────────────────────┐
   │ HTTP/1.1                                     │
   │ - 每请求一连接 / 队头阻塞                       │
   │ - keepalive 部分缓解                          │
   ├──────────────────────────────────────────────┤
   │ HTTP/2                                       │
   │ - 多路复用（一连接多请求）                      │
   │ - 头部压缩（HPACK）                            │
   │ - 仍受 TCP 队头阻塞影响                        │
   ├──────────────────────────────────────────────┤
   │ HTTP/3 (QUIC)                                │
   │ - 基于 UDP，无 TCP 队头阻塞                    │
   │ - 0-RTT 重连                                  │
   │ - 弱网表现优于 H2                              │
   ├──────────────────────────────────────────────┤
   │ WebSocket / 长连接                            │
   │ - 一次握手长期通信                              │
   │ - 适合实时双向                                 │
   │ - 需要心跳保活                                 │
   └──────────────────────────────────────────────┘
```

**网络问题的三类典型形态**：

```
   ┌────────────────────────────────────────────────┐
   │ A. 连接开销主导：每请求都重连                     │
   │    根因：未启用 keepalive / 长连接               │
   ├────────────────────────────────────────────────┤
   │ B. 串行依赖：请求互相等                          │
   │    根因：A 完成才能发 B / 同步阻塞               │
   ├────────────────────────────────────────────────┤
   │ C. 弱网放大：高 RTT 高丢包                       │
   │    根因：未做弱网容错 / 超时策略不当              │
   └────────────────────────────────────────────────┘
```

> ▶▶ **回扣 §00.5 案例**：东南亚弱网场景**同时命中 A + B + C 三类**——
> - **A 类**：响应体大触发了 TCP 慢启动 + 多次 RTT；
> - **B 类**：首屏 6 个 API 串行依赖，被打成 6×3.8s 的累积；
> - **C 类**：8% 丢包率让 TLS 握手频繁重传到 620ms。
>
> 经验派 3 周折腾的失败原因正是把三类混为一谈，用强网思维一刀切——**第 1 周拉超时治不了 C，第 3 周改全并发治不了 B（依赖关系还在），且把 A 恶化（连接数过多握手失败）**。这正是 §2.2 模型分类的工程意义：**先识形态，再选武器**。

### 2.3 跨平台同构原理

所有平台的网络栈都基于 TCP/IP，应用层都是 HTTP / WebSocket / 自定义协议：

```
   通用网络模型：

      [应用 API]   →   [HTTP 客户端]   →   [TLS]   →   [TCP/UDP]   →   [网卡]
       业务请求          OkHttp / URLSession   SSL/TLS    内核网络栈   硬件
```

每个平台都必须有：

| 抽象组件 | 解决什么问题 |
|---|---|
| HTTP 客户端 | 封装 HTTP 协议细节 |
| 连接池 | 复用 TCP / TLS 连接 |
| DNS 缓存 | 减少 DNS 查询 |
| 重试策略 | 弱网容错 |
| 超时控制 | 防止永久阻塞 |

**跨平台术语对照**

| 通用术语 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| HTTP 客户端 | OkHttp / Retrofit | URLSession / Alamofire | fetch / axios | libcurl |
| 连接池 | OkHttp ConnectionPool | URLSession 自动 | 浏览器自动 | 自实现 |
| 长连接 | OkHttp WebSocket | URLSessionWebSocketTask | WebSocket API | 自实现 |
| HTTP/2 | OkHttp 自动 | URLSession 自动 | 浏览器自动 | 视库 |

**同构带来的工程价值**

1. **协议优化思路通用**：复用、合并、压缩、缓存 跨端通用。
2. **弱网治理通用**：超时控制、重试策略、降级逻辑。
3. **指标体系通用**：API 延迟分位 + 失败率 + 弱网占比。

## 03.度量与采集

### 3.1 三类采集方案的本质

```
   请求发起 ──▶ DNS / TCP / TLS ──▶ HTTP 传输 ──▶ 响应解析 ──▶ 业务回调
       │                                                            │
       ▼                                                            ▼
   ① 客户端打点（每请求埋点）
                ② 阶段拆解（系统提供的 timing API）
                            ③ 抓包分析（Charles / Wireshark / 自定义）
```

---

**① 客户端打点**

**核心原理（一句话）**：HTTP 客户端拦截器记录每个请求的开始 / 结束 / 错误，统计延迟与失败率。

**工作机理**：

```kotlin
// OkHttp 拦截器
class TimingInterceptor : Interceptor {
    override fun intercept(chain: Chain): Response {
        val start = System.nanoTime()
        val req = chain.request()
        try {
            val resp = chain.proceed(req)
            report(req.url, "ok", (System.nanoTime() - start) / 1_000_000)
            return resp
        } catch (e: Exception) {
            report(req.url, "fail:${e.javaClass.simpleName}", (System.nanoTime() - start) / 1_000_000)
            throw e
        }
    }
}
```

**物理本质**：从应用视角记录每个请求生命周期。

**为什么这样有效**：直接对应业务关心的"用户感知到的网络延迟"；开销极低。

**局限根源**：看不到协议细节（哪一阶段慢）。

**适用边界**：所有应用的核心监控方案。

---

**② 阶段拆解（Timing API）**

**核心原理（一句话）**：使用系统提供的 timing API 分解出 DNS / TCP / TLS / 等待 / 响应 / 解析 各阶段耗时。

**工作机理**：

| 平台 | API |
|---|---|
| Android OkHttp | EventListener（dnsStart/dnsEnd/connectStart...）|
| iOS URLSession | URLSessionTaskTransactionMetrics |
| Web | PerformanceResourceTiming（resource start / domainLookup / connect / requestStart / responseEnd）|

**物理本质**：协议栈各阶段对应用不透明，必须借助系统 API。

**适用边界**：归因每次"为什么慢"。

---

**③ 抓包分析（线下深度）**

**核心原理（一句话）**：在网络层抓取所有数据包，离线分析协议级行为。

**工作机理**：

- Charles / Wireshark / Fiddler：HTTPS 需安装根证书。
- mitmproxy：脚本化抓包。
- adb tcpdump：Android 命令行抓包。

**物理本质**：在数据包级别看真相。

**适用边界**：线下排查协议问题、抓"看不到的"行为。

---

**三种方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 客户端打点 | 应用 HTTP 库 | 请求级 | 极低 | 高 | ✅ | 不知协议细节 |
| ② 阶段拆解 | 系统 API | 阶段级 | 极低 | 中 | ✅ | API 不一致 |
| ③ 抓包 | 网络层 | 包级 | 低 | 极高 | ❌ | 需配置 |

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| API 总耗时 | ✅ | ✅ | ✅ |
| 哪阶段慢（DNS/TCP/TLS）| ❌ | ✅ | ✅ |
| 重传 / 丢包 | ❌ | 部分 | ✅ |
| 加密包内容 | ❌ | ❌ | ✅（带证书）|
| HTTP/2 多路复用细节 | ❌ | 部分 | ✅ |

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web |
|---|---|---|---|
| 客户端打点 | OkHttp Interceptor / EventListener | URLProtocol | fetch wrapper / Performance Resource API |
| 阶段拆解 | EventListener.dnsStart/connectStart... | URLSessionTaskTransactionMetrics | PerformanceResourceTiming |
| 弱网模拟 | adb / 第三方 / Charles | Network Link Conditioner | DevTools Network Throttling |
| 抓包 | Charles + 系统 CA | Charles + iOS CA | DevTools Network |

### 3.4 数据可信度评估

| 数据 | 可信度 | 偏差来源 |
|---|---|---|
| API 总耗时 | 高（< 1%）| 客户端时钟 |
| 阶段拆解 | 高 | 系统 API 准确 |
| 弱网识别 | 中 | 网络类型不准确（4G 可能很慢）|
| 失败原因 | 中 | 错误码合并损失信息 |

## 04.归因方法

### 4.1 网络问题决策树

```
网络问题
   │
   ├── 阶段 A. DNS 慢（> 200ms）──▶ DNS 优化
   │                              ├─ HttpDns 替代系统 DNS
   │                              └─ DNS 缓存 + 预解析
   │
   ├── 阶段 B. TCP / TLS 慢（> 500ms）──▶ 连接优化
   │                              ├─ 连接复用（keepalive）
   │                              ├─ HTTP/2 多路复用
   │                              └─ HTTP/3 (QUIC) 0-RTT
   │
   ├── 阶段 C. 服务端处理慢（TTFB > 300ms）──▶ 服务端优化
   │                              ├─ CDN / 边缘
   │                              └─ 后端逻辑优化
   │
   ├── 阶段 D. 响应传输慢（大体积）──▶ 数据优化
   │                              ├─ 压缩（gzip / brotli）
   │                              ├─ 协议升级（PB / FlatBuffer）
   │                              └─ 减少返回字段
   │
   └── 弱网放大 ──────────────────▶ 弱网容错
                                  ├─ 合理超时
                                  ├─ 降级 / 缓存
                                  └─ 重试策略
```

> ▶▶ **回扣 §00.5 案例**：东南亚首屏 6 API 的阶段拆解恰好命中 4 条分支——DNS 850ms 走阶段 A；TLS 620ms 走阶段 B；响应体 1700ms 走阶段 D；同时整体走"弱网放大"分支。**经验派只盯一条分支必然失败**，方法派 7 天闭环对 4 条分支同时施治才取得首屏 3.8s→1.1s 的成果。决策树的工程价值就是**"分而治之，按图索骥"**。

### 4.2 阶段拆解归因

**典型阶段时长占比**：

```
   首次请求（无连接复用）：
   DNS         50-200ms    20%
   TCP         30-150ms    15%
   TLS         60-300ms    30%
   等待 TTFB   50-300ms    25%
   传输        视体积       10%
   
   连接复用后：
   等待 TTFB   50-300ms    70-90%
   传输                    剩余
```

**归因思路**：先看哪一阶段最长，再针对性优化。

### 4.3 弱网模式归因

**弱网的物理特征**：

- 高 RTT（300ms+）
- 高丢包率（> 5%）
- 低带宽（< 100Kbps）
- 不稳定（速度波动大）

**弱网下的典型问题**：

- TCP 重传指数级增长（一个丢包导致整个 window 重传）。
- TLS 握手丢包让加密失败。
- 长任务超时（默认 60s 太长）。
- 用户已经放弃但请求仍在等待。

**弱网识别方法**：

- 系统 API：Android `NetworkCapabilities` / iOS Reachability。
- 主动探测：定期请求小固定大小数据，测量延迟。
- 业务感知：连续 N 次请求慢即判弱网。

### 4.4 失败重试归因

**重试是双刃剑**：

- 善用重试：偶发失败一次重试解决问题。
- 滥用重试：本来就慢的网络被重试雪上加霜。

**正确的重试策略**：

- **指数退避**（Exponential Backoff）：1s, 2s, 4s, 8s。
- **最大重试次数**（3-5 次）。
- **特定错误码才重试**（5xx 重试 / 4xx 不重试）。
- **幂等性检查**：POST 谨慎重试（可能重复创建）。

## 05.求证实验 ⭐

### 5.1 实验一：握手开销

**Step 1 — 原始观察**

工程师都知道 HTTPS 比 HTTP 慢，但**慢多少？连接复用后还慢吗？**

**Step 2 — 提出疑问**

> **HTTP / HTTPS / HTTP/2 在首次和连接复用情况下的延迟差异多大？**

**Step 3 — 形成假设**

**H₁**：首次连接 HTTPS 比 HTTP 慢 100-300ms（多 1-2 RTT TLS 握手）；连接复用后两者几乎相同。HTTP/2 在连接复用后并发请求显著快。  
**H₀**：HTTPS 永远慢。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 测试服务器 | 部署同一服务支持 HTTP / HTTPS / HTTP2 |
| 网络 | Wi-Fi 50Mbps |
| 请求 | 单独 GET 1KB JSON |
| 场景 | 首次请求 / 连接复用第 2-10 次 |

**Step 5 — 实测数据**

| 协议 | 首次 (ms) | 复用第 2 次 (ms) |
|---|---|---|
| HTTP/1.1 | 50 | 35 |
| HTTPS（HTTP/1.1 + TLS）| 220 | 38 |
| HTTP/2（HTTPS）| 230 | 38 |

并发 10 请求：

| 协议 | 串行总时长 | 并发总时长 |
|---|---|---|
| HTTP/1.1 keepalive | 350 ms | 220 ms（最多 6 条 TCP）|
| HTTP/2 | 380 ms | 80 ms（多路复用）|

**Step 6 — 验证 / 修正**

- 首次 HTTPS 比 HTTP 慢 170ms（TLS 握手）。
- 连接复用后 HTTPS 与 HTTP 几乎相同（38ms vs 35ms）。
- HTTP/2 在并发时显著优于 HTTP/1.1（80ms vs 220ms）。
- 验证 H₁。

**Step 7 — 提炼结论**

> **HTTPS 的"慢"主要在首次连接（多 1-2 RTT TLS 握手）。  
> 连接复用后开销可忽略。HTTP/2 在多请求并发场景下显著优于 HTTP/1.1。**

工程意义：

- 必用 HTTPS（安全 + 复用后无开销）。
- 必用连接复用（keepalive / 连接池）。
- 多请求场景必用 HTTP/2 / HTTP/3。
- 首次连接慢可用 HTTP/3 0-RTT 缓解。

**Step 8 — 边界**

- 实验数据基于良好网络。弱网下 TLS 握手时间会更长。
- 服务端 SSL 配置不当会增加延迟。
- HTTP/3 在弱网下优势更明显（无 TCP 队头阻塞）。

---

### 5.2 实验二：弱网超时策略

**Step 1 — 原始观察**

弱网下默认超时 30-60 秒，用户根本等不了那么久；但太短又会"明明能成功"被截断。**最优超时是多少？**

**Step 2 — 提出疑问**

> **不同超时配置（5s / 10s / 30s / 60s）下，弱网请求的成功率与"用户实际等待时间"如何变化？**

**Step 3 — 形成假设**

**H₁**：超时太短会牺牲成功率；太长会浪费用户时间。最优值在 10-15s 区间。  
**H₀**：超时设大点更好。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 弱网模拟 | RTT 500ms / 丢包 10% / 带宽 50Kbps |
| 超时配置 | 5s / 10s / 15s / 30s / 60s |
| 主指标 | (a) 请求成功率 (b) 用户平均等待时间 |
| 重复 | 每场景 200 次 |

**Step 5 — 实测数据**

| 超时 | 成功率 | 失败时用户等待（s）| 加权用户体验 |
|---|---|---|---|
| 5s | 78% | 5 | 中 |
| 10s | 92% | 10 | 较好 |
| 15s | 95% | 15 | 较好 |
| 30s | 96% | 30 | 较差 |
| 60s | 97% | 60 | 差 |

**Step 6 — 验证 / 修正**

- 5s 太短，成功率明显下降。
- 10-15s 是甜蜜点。
- 30s+ 边际收益极低（多 1% 成功率 vs 多 15s 等待）。
- 验证 H₁。

**Step 7 — 提炼结论**

> **弱网超时建议 10-15 秒。短于 5s 牺牲成功率，长于 30s 浪费用户时间。**

工程意义：

- 不要用默认 60s 超时。
- 关键场景（首屏 / 关键操作）可用 10s + 重试。
- 非关键（统计 / 上报）可用 5s 超时即放弃。

**Step 8 — 边界**

- 不同业务对成功率敏感度不同。
- 大数据传输需要更长超时。
- 弱网识别后可动态调整超时。

> ▶▶ **回扣 §00.5 案例**：经验派第 1 周"拉到 60s"是把本实验"超时长成功率高"误读为"超时越长越好"，**忽略了实验数据中 30s+ 边际收益极低、用户体验大幅下降的明确警告**。方法派 Day 4 的"强网 5s/弱网 15s 动态切换"才是本实验工程意义的正确实现。这告诉我们：**超时不是常量，是函数（网络状态）**。

---

### 5.3 实验三：连接复用收益

**Step 1 — 原始观察**

工程师都用连接池，但**连接池大小、空闲时长怎么配？什么时候应该断开？**

**Step 2 — 提出疑问**

> **连接池大小 N 与请求平均延迟的关系是什么？空闲连接保留多久最优？**

**Step 3 — 形成假设**

**H₁**：连接池大小 N 应等于"并发峰值"；空闲保留 5-10 分钟（与服务端 keepalive 对齐）。  
**H₀**：连接池越大越好。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 测试场景 | 模拟用户行为：每 5 秒发 3-5 请求 |
| 连接池大小 | 1 / 5 / 10 / 20 |
| 空闲保留 | 1min / 5min / 10min |
| 主指标 | 平均请求延迟 / 连接重建率 |

**Step 5 — 实测数据**

| 连接池大小 | 空闲 5min | 平均延迟（ms）| 重建率 |
|---|---|---|---|
| 1 | 5min | 80（队头阻塞）| 5% |
| 5 | 5min | 30 | 5% |
| 10 | 5min | 28 | 4% |
| 20 | 5min | 28 | 4% |

| 空闲保留 | 池 5 | 平均延迟 | 重建率 |
|---|---|---|---|
| 1min | 5 | 60（频繁重建）| 30% |
| 5min | 5 | 30 | 5% |
| 10min | 5 | 28 | 3% |

**Step 6 — 验证 / 修正**

- 池 5 已经覆盖大部分场景。再大无收益。
- 空闲保留 5min 是甜蜜点。

**Step 7 — 提炼结论**

> **连接池大小 = 并发峰值（典型 5）；空闲保留 5 分钟。  
> 超过这两者收益递减。**

工程意义：

- OkHttp 默认 5 / 5 分钟基本够用。
- 大并发应用可调到 10。
- 不要为"快"开 50+，吃不消还可能被服务端限。

**Step 8 — 边界**

- 服务端 keepalive 时长决定空闲上限。
- 移动应用切网络（Wi-Fi → 4G）时连接池要清空。

### 5.4 实验四：HTTP/3 在弱网下的相对增益

**Step 1 — 原始观察**

HTTP/3 (QUIC) 被宣传为"弱网神器"，但**强网下与 HTTP/2 几乎一致。它的真实价值边界在哪？**

**Step 2 — 提出疑问**

> **HTTP/2 和 HTTP/3 在不同网络条件（强网 / 弱网 / 移动切换）下的延迟差异多大？**

**Step 3 — 形成假设**

**H₁**：强网下两者几乎一致；弱网（高丢包）下 HTTP/3 显著优于 HTTP/2（无 TCP 队头阻塞）；网络切换时（4G→Wi-Fi）HTTP/3 连接迁移让 0-RTT 重连 vs HTTP/2 完整重新握手。  
**H₀**：HTTP/3 永远更好。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 服务端 | Cronet/nginx 同时支持 HTTP/2 和 HTTP/3 |
| 网络场景 | (a) Wi-Fi 100Mbps RTT 30ms 0% 丢包 (b) 4G RTT 80ms 1% 丢包 (c) 弱网 RTT 300ms 8% 丢包 (d) 4G→Wi-Fi 切换 |
| 请求 | 首屏 6 API（每个 1KB） |
| 主指标 | 总耗时、连接迁移失败率 |

**Step 5 — 实测数据**

| 场景 | HTTP/2 | HTTP/3 | 增益 |
|---|---|---|---|
| (a) Wi-Fi 强网 | 280 ms | 270 ms | -3% |
| (b) 4G 普通 | 520 ms | 460 ms | -12% |
| (c) 弱网（8% 丢包）| 4200 ms | **2100 ms** | **-50%** |
| (d) 4G→Wi-Fi 切换 | 重新握手 380ms | **连接迁移 < 50ms** | -86% |

**Step 6 — 验证 / 修正**

- 强网下两者无明显差。
- 弱网下 HTTP/3 因无 TCP 队头阻塞，单丢包不影响其他流，延迟降低 50%。
- 网络切换是 HTTP/3 的"独门绝技"。
- 拒绝 H₀（HTTP/3 不是永远更好，但在弱网/切换场景压倒性优势）。

**Step 7 — 提炼结论**

> **HTTP/3 真实价值在"弱网 + 移动切换"场景。强网用户感知不到，但弱网用户和移动切换用户体验提升 50% 以上。**

工程意义：

- 出海应用、新兴市场应用必上 HTTP/3。
- 强网为主的内网/办公应用不必着急。
- 配合 Cronet（Android）/ iOS 15+ URLSession（自动）落地。
- 服务端启用 0-RTT 是关键（节省首次 TLS 握手）。

**Step 8 — 边界**

- 服务端必须支持 QUIC（nginx 1.25+/Caddy/Cloudflare）。
- 部分企业网/校园网防火墙拦截 UDP，需 fallback 到 HTTP/2。
- 0-RTT 数据有重放攻击风险，敏感请求（POST 转账）需禁用。

### 5.5 实验五：请求合并与批处理的吞吐增益

**Step 1 — 原始观察**

很多业务首屏 6-10 个 API 串行/并发各有问题。**合并到 1-2 个聚合 API 收益有多大？**

**Step 2 — 提出疑问**

> **6 个独立 API vs 1 个聚合 API（服务端聚合）vs BFF 模式的延迟与代码成本差异？**

**Step 3 — 形成假设**

**H₁**：合并 API 在弱网下有 2-3 倍提升（节省 N-1 次 RTT）；强网下提升 30-50%。BFF 模式还能节省客户端业务逻辑。  
**H₀**：合并不重要。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 场景 | 首屏 6 API（用户、商品、推荐、活动、广告、配置）|
| 方案 A | 6 个独立 API 客户端并发 |
| 方案 B | 服务端聚合为 1 个 batch API |
| 方案 C | BFF 网关聚合（GraphQL）|
| 网络 | 强网 / 弱网 |
| 主指标 | 总耗时、移动端 CPU 占用、流量大小 |

**Step 5 — 实测数据**

| 方案 | 强网总耗时 | 弱网总耗时 | 流量 | 客户端代码复杂度 |
|---|---|---|---|---|
| A 6 独立并发 | 480 ms | 4200 ms | 12 KB（多次头部）| 高（6 处错误处理）|
| B 服务端聚合 | 220 ms | **1500 ms** | 8 KB | **低**（1 处）|
| C BFF GraphQL | 250 ms | 1600 ms | 7 KB（按需字段）| 低 |

**Step 6 — 验证 / 修正**

- 弱网下合并 API 延迟降低 64%（4200→1500）。
- 流量降低 33%（去重 HTTP 头部）。
- 客户端代码量降低 70%。
- 拒绝 H₀。

**Step 7 — 提炼结论**

> **首屏类多 API 必须合并：弱网延迟降低 60%+，流量节省 30%+，客户端代码大幅简化。BFF 模式适合微服务架构。**

工程意义：

- 首屏不超过 2 个 API（必要时用 BFF）。
- 服务端聚合优于客户端聚合（节省 N-1 RTT）。
- GraphQL 适合复杂场景；REST + batch endpoint 适合简单场景。
- 注意：聚合 API 的失败处理要"部分成功也返回"（不能因为推荐失败让首屏全空）。

**Step 8 — 边界**

- 服务端聚合增加后端复杂度和耦合。
- 不同 API 缓存策略不同时（如商品 1h、广告 5min）合并后受限于最严格的策略。
- 流式场景（视频/直播）不适合合并。

### 5.6 五大实验启示

```
   握手开销         → HTTPS 首次慢 100-300ms，复用后无差异      ─┐
                                                                 │
   弱网超时         → 10-15s 是甜蜜点，超过 30s 边际为零         │
                                                                 │
   连接复用         → 池 5 / 5min 是默认最优                     ├─▶ 网络优化 = 减请求 + 减开销 + 防弱网 + 适配场景
                                                                 │
   HTTP/3 弱网增益   → 弱网/切换场景 50%+ 提升                    │
                                                                 │
   请求合并         → 弱网延迟 -64%、流量 -33%、代码 -70%        ─┘
```

**统一启示**：

- **HTTPS 不是"慢"的元凶**：连接复用后开销可忽略。
- **超时不是越长越好**：用户体验 vs 成功率有甜蜜点。
- **数据驱动配置**：连接池等参数都有最优值。
- **协议升级要看场景**：HTTP/3 在弱网 50% 增益，强网无差。
- **请求合并是首屏类最大杠杆**：弱网下省 N-1 个 RTT。

## 06.优化策略深化

> 本节回答四个递进问题：**①如何让每次请求最小化代价？②如何让请求更少更聪明？③如何在弱网保住底盘？④如何让问题先于用户被发现？**

### 6.1 第一层：协议层效率优化（每次请求最小化代价）

**核心命题**：协议层的"每请求开销"是网络性能的物理下限。这一层的优化是**单次请求的天花板**。

**策略 1.1：DNS 优化（HttpDns + 预解析 + IP 池）**

- **机理**：[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) 印尼 DNS 850ms（22% 占比），系统 DNS 在新兴市场极不稳定。HttpDns 走 HTTP 直连权威服务器，且不被劫持。
- **代码**：

```kotlin
class HttpDnsResolver : Dns {
    private val cache = mutableMapOf<String, Pair<List<InetAddress>, Long>>()
    override fun lookup(hostname: String): List<InetAddress> {
        cache[hostname]?.let { (ips, expireAt) ->
            if (System.currentTimeMillis() < expireAt) return ips
        }
        val ips = httpDnsClient.resolve(hostname)
        cache[hostname] = ips to (System.currentTimeMillis() + 600_000)  // 10min TTL
        return if (ips.isNotEmpty()) ips else Dns.SYSTEM.lookup(hostname)  // fallback
    }
}
OkHttpClient.Builder().dns(HttpDnsResolver()).build()
```

- **收益**：[§7.2 案例](#72-平台特异案例) 失败率 5%→0.3%；[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) DNS 阶段 850ms→<50ms。
- **边界**：HttpDns 服务本身的可用性需保障；必须有 IP 池 fallback 防服务挂掉。

**策略 1.2：HTTP/3 + TLS 1.3 + 0-RTT**

- **机理**：[§5.4 实验](#54-实验四http3-在弱网下的相对增益) 证明弱网/切换场景 50% 提升；TLS 1.3 把握手从 2 RTT 降到 1 RTT；0-RTT 复用 Session 几乎零延迟。
- **代码**（Cronet）：

```kotlin
val cronetEngine = CronetEngine.Builder(context)
    .enableQuic(true)
    .addQuicHint("api.example.com", 443, 443)
    .enableHttp2(true)
    .build()
```

- **收益**：[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) TLS 阶段 620ms→0ms（0-RTT 复用），单次首屏 -2s。
- **边界**：服务端必须支持 QUIC；防火墙偶发拦截 UDP 需 fallback；敏感 POST 禁用 0-RTT 防重放。

**策略 1.3：连接复用（连接池 + keepalive）**

- **机理**：[§5.3 实验](#53-实验三连接复用收益) 池 5 + 5min 是甜蜜点。
- **代码**：

```java
ConnectionPool pool = new ConnectionPool(5, 5, TimeUnit.MINUTES);
OkHttpClient client = new OkHttpClient.Builder().connectionPool(pool).build();
```

- **收益**：复用后单请求 35-38ms vs 首次 220ms（[§5.1](#51-实验一握手开销)）。
- **边界**：网络切换（Wi-Fi→4G）必须清空连接池；服务端 keepalive 时长决定上限。

**策略 1.4：数据压缩与协议升级**

- **机理**：响应体积 = 单次主要耗时（弱网下传输占 45%）。
- **代码**：

```kotlin
OkHttpClient.Builder()
    .addInterceptor { chain ->
        val req = chain.request().newBuilder()
            .header("Accept-Encoding", "br, gzip")
            .build()
        chain.proceed(req)
    }
val pbResponse = MyProto.parseFrom(response.body!!.bytes())
```

- **收益**：JSON+gzip → PB+brotli 体积通常 -60%；[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) 响应体阶段 1700ms→700ms。
- **边界**：PB 需双端协议同步；brotli CPU 编码成本略高于 gzip。

### 6.2 第二层：业务层调度治理（让请求更少更聪明）

**核心命题**：协议层是"每次开销"，业务层是"如何最少地用网络"。这一层有时收益更大。

**策略 2.1：请求合并与 BFF 聚合**

- **机理**：[§5.5 实验](#55-实验五请求合并与批处理的吞吐增益) 弱网延迟 -64%。
- **代码**（GraphQL）：

```graphql
query HomePage {
  user { id name avatar }
  feed(limit: 10) { id title cover }
  recommendations(limit: 5) { id title }
}
```

- **收益**：[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) Day 4 第 2 层落地——6 API 合 2 个，强网 480→220ms，弱网 4200→1500ms。
- **边界**：聚合 API 失败处理要"部分成功也返回"；不同缓存策略的字段需拆开。

**策略 2.2：依赖图分析与并发化**

- **机理**：[§7.1 案例](#71-跨端同构案例) 6 API 中只 2 个真依赖，其余可并发——拓扑分析后总耗时降到 max(C+F, D+E) + A + B。
- **代码**（协程）：

```kotlin
val a = async { getA() }
val b = async { getB() }
val c = async { val ab = awaitAll(a, b); getC(ab) }
val d = async { val ab = awaitAll(a, b); getD(ab) }
val (cR, dR) = awaitAll(c, d)
```

- **收益**：典型首屏 -50%。
- **边界**：并发数过高（> 6）反而触发 HTTP/2 流限制；服务端要能扛突发并发。

**策略 2.3：缓存策略（HTTP + 业务双层）**

- **机理**：HTTP Cache-Control / ETag 解决"内容未变不下载"；业务层缓存解决"快速展示再后台刷新"。
- **代码**：

```kotlin
val cached = cache.get(key)
if (cached != null) showImmediately(cached)
viewModelScope.launch {
    val fresh = api.getData()
    if (fresh != cached) {
        cache.put(key, fresh)
        showRefreshed(fresh)
    }
}
```

- **收益**：首屏感知延迟接近 0（先用缓存）。
- **边界**：缓存一致性需通过 ETag/版本号或 push 失效。

**策略 2.4：预取与预测**

- **机理**：用户行为可预测（点了商品列表 80% 会进详情页）。空闲时间预取下一步资源。
- **代码**：

```kotlin
listScrollListener.onIdle { firstVisible ->
    if (firstVisible >= 5) prefetch(items[firstVisible].detailUrl)
}
```

- **收益**：详情页打开延迟 -70%（命中预取）。
- **边界**：流量浪费风险（预测错 = 浪费）；需限制预取并发数和数据量。

### 6.3 第三层：弱网容错治理（保住底盘）

**核心命题**：[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) 第 1 周拉超时翻车的根因——弱网治理不是"加大加多"，而是"识别+适配+优雅降级"。

**策略 3.1：弱网识别 + 动态超时**

- **机理**：连续 N 次请求慢即判弱网；按弱网等级动态调整超时（[§5.2 实验](#52-实验二弱网超时策略)）。
- **代码**：

```kotlin
class NetworkQualityDetector {
    private val recentLatencies = ArrayDeque<Long>(10)
    fun report(latencyMs: Long) {
        if (recentLatencies.size >= 10) recentLatencies.poll()
        recentLatencies.offer(latencyMs)
    }
    fun quality(): Quality {
        val avg = recentLatencies.average()
        return when {
            avg < 500 -> Quality.STRONG
            avg < 2000 -> Quality.MEDIUM
            else -> Quality.WEAK
        }
    }
}
val timeout = when (quality()) {
    Quality.STRONG -> 5_000L
    Quality.MEDIUM -> 10_000L
    Quality.WEAK -> 15_000L
}
```

- **收益**：[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) Day 4 落地后失败率 8.1%→0.6%。
- **边界**：弱网识别需 10 个样本才稳定；冷启动期可用网络类型粗判。

**策略 3.2：指数退避重试 + 错误码白名单**

- **机理**：[§4.4 失败重试归因](#44-失败重试归因)；不是所有错误都重试。
- **代码**：

```kotlin
suspend fun <T> retryWithBackoff(maxAttempts: Int = 3, block: suspend () -> T): T {
    var lastError: Throwable? = null
    repeat(maxAttempts) { attempt ->
        try { return block() }
        catch (e: HttpException) {
            if (e.code() in 400..499 && e.code() != 408 && e.code() != 429) throw e
            lastError = e
            delay((1000L * (1L shl attempt)) + Random.nextLong(500))  // 1s/2s/4s + 抖动
        }
    }
    throw lastError!!
}
```

- **收益**：偶发失败由重试解决，恶意/不可恢复错误不浪费。
- **边界**：POST 必须保证幂等性（用 Idempotency-Key）；总重试预算不超过 3 次防雪崩。

**策略 3.3：降级链路与离线 fallback**

- **机理**：极端弱网/无网用本地缓存或简化版数据保住主流程。
- **代码**：

```kotlin
val data = try {
    api.getHomePage()
} catch (e: IOException) {
    cache.getStale() ?: defaultData()
}
```

- **收益**：失败率体感降到 0（用户看到内容而非错误页）。
- **边界**：降级数据要打 stale 标识，避免用户基于过期数据做决策。

**策略 3.4：CDN 与边缘部署**

- **机理**：物理距离决定 RTT 下限。出海/广域用户必须就近接入。
- **收益**：[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) 雅加达节点让印尼 RTT 从 80ms→<10ms。
- **边界**：边缘节点的缓存一致性策略要设计（如 push invalidation）。

### 6.4 第四层：监控与可观测（让问题先于用户被发现）

**核心命题**：网络问题在不同地区/网络类型差异巨大，必须细粒度监控。

**策略 4.1：阶段拆解监控（DNS/TCP/TLS/TTFB/传输）**

- **机理**：[§3.1 方案②](#31-三类采集方案的本质) EventListener 直接给出每阶段时长。
- **代码**：

```kotlin
class TimingEventListener : EventListener() {
    private val timings = mutableMapOf<String, Long>()
    override fun dnsStart(call: Call, hostname: String) { timings["dns_start"] = now() }
    override fun dnsEnd(call: Call, hostname: String, ips: List<InetAddress>) {
        timings["dns"] = now() - timings["dns_start"]!!
    }
    override fun callEnd(call: Call) { report(call.request().url, timings) }
}
```

- **收益**：[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) Day 2 直接定位"DNS 慢 + TLS 重传 + 响应体大"三段。
- **边界**：阶段拆解仅在客户端打点，无法看到服务端内部分解。

**策略 4.2：地区 × 网络类型维度看板**

- **机理**：均值掩盖地区差异。必须按"国家×运营商×网络类型"细分。
- **收益**：[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) 是因为这种细分才发现"全球均值正常但印尼极差"。
- **边界**：地区维度数据量大，需采样上报。

**策略 4.3：弱网占比与失败码分类**

- **机理**：失败率 = ∑(各错误码占比 × 业务损失权重)。SocketTimeout 与 SSLException 治理路径完全不同。
- **代码**：上报字段加 `error_code` / `network_type` / `quality`。
- **收益**：归因从"5% 失败"细化到"3% 是 DNS 失败、1% 是 TLS、1% 是 SocketTimeout"。
- **边界**：错误码合并要保留原始 OS error。

- **强网思维硬套弱网**：必须按场景区分，不是"一套配置打天下"。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某社交应用首屏 6 个 API 串行（依赖关系）总耗时 2.5s，希望优化。Android / iOS / Web 都有同样问题。

**度量与归因**：

仔细分析依赖关系：实际只有 2 个 API 真正依赖前置结果，其余 4 个可以并行。

**假设与求证**：

提出**统一假设**："拆分依赖图，把可并行的并发执行"。

修复设计：

```
   原始（串行）：
   A → B → C → D → E → F  总耗时 = ΣTi

   优化（并发）：
   A → B → ┬─→ D ─→ E
           └─→ C ─→ F
   总耗时 = max(D+E, C+F) + A + B
```

**验证**：

| 平台 | 优化前 | 优化后 | 降幅 |
|---|---|---|---|
| Android | 2.5s | 1.2s | 52% |
| iOS | 2.4s | 1.1s | 54% |
| Web | 2.6s | 1.3s | 50% |

**统一启示**：网络优化跨端通用法则 = **依赖图分析 + 并发化**。

### 7.2 平台特异案例

**背景**：Android 应用在某些地区 DNS 失败率 5%，iOS 同地区 < 0.5%。

**现象**：Android 用户报告"打不开"，iOS 没问题。

**度量与归因**：

抓包发现：Android 用 InetAddress.getByName 查系统 DNS，部分运营商 DNS 不稳定。iOS 系统 DNS 自带 fallback。

**假设与求证**：

**假设**：用 HttpDns 服务（如阿里 / 腾讯）替代系统 DNS。

**实验**：HttpDns 失败率 < 0.1%，且不被运营商劫持。

**修复**：Android 接入 HttpDns + 系统 DNS fallback。

**验证**：失败率从 5% 降到 0.3%。

**边界与上线策略**：HttpDns 需要 IP 白名单（先用本地 IP 列表 fallback）。

## 10.总结与延伸

### 10.1 五条核心原则

1. **协议优化 + 业务优化 + 弱网容错 + 监控四层缺一不可**：[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) 是只治一层 3 周失败的真实证据。
2. **复用最有效**：HTTPS / HTTP/2 / HTTP/3 / 连接池都基于复用，[§5.1](#51-实验一握手开销) 给出硬证据。
3. **弱网容错是必修课**：识别 + 动态超时 + 指数退避 + 降级链路，**不是拉长超时和无脑重试**。
4. **数据驱动**：每次请求都有阶段拆解 + 长尾分析 + 地区维度细分。
5. **请求合并 + 预取**：[§5.5](#55-实验五请求合并与批处理的吞吐增益) 弱网 -64%，是首屏类最大杠杆。

### 10.2 五个常见误区

1. **"HTTPS 总是慢"**：错（复用后无差异，[§5.1](#51-实验一握手开销)）。
2. **"超时设大点稳"**：错（[§5.2](#52-实验二弱网超时策略) 30s+ 边际为零；[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) 第 1 周翻车）。
3. **"重试越多越稳"**：错（弱网下雪上加霜，[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) 第 2 周打挂服务端）。
4. **"HTTP/3 永远更快"**：错（[§5.4](#54-实验四http3-在弱网下的相对增益) 强网无差，价值在弱网/切换）。
5. **"全部并发更快"**：错（[§00.5 案例](#005-贯穿案例跨境电商东南亚弱网首屏-8-秒事件) 第 3 周翻车，弱网下并发数过多反而握手失败）。

## 一句话总结

> **网络性能 = 协议层效率 × 业务层调度 × 弱网容错 × 监控可观测；四层缺一不可。  
> 连接复用最基础，HTTPS 不是"慢"的元凶，HTTP/3 在弱网/切换场景 50% 提升，请求合并是首屏类最大杠杆。  
> 弱网治理 ≠ 拉长超时 + 无脑重试，而是"识别+适配+优雅降级"。  
> §00.5 那个"3 周经验派 vs 7 天方法派"的反差，正是这条路径的最锋利证据。**
