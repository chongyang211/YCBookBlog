- **本文卷归属**：卷四 · 业务篇 · 第 2 篇
- **本文目标层级**：L2 进阶 → L3 专家
- **适用平台**：Android / iOS / Web / 嵌入式（联网设备）
- **前置阅读**：
  - [`卷零·02 跨平台性能模型与指标体系`](../00.公共方法论/02.跨平台指标体系.md)
- **本文核心命题**：
  > **网络性能 = 协议层效率 × 业务层调度**。  
  > 协议层（DNS / TCP / TLS / HTTP）决定每次请求的最小代价；业务层（请求合并 / 缓存 / 并发 / 弱网容错）决定如何最少地用网络。  
  > 一切优化都是在这两个维度上"减少请求数 × 减少每次请求开销"。

## 01.问题域定义

### 1.1 现象与代价

网络性能问题的用户感知：

- **首屏加载慢**：API 慢 → 页面白屏 / 骨架屏停留过久。
- **图片加载慢 / 闪烁**：图片下载慢 / 失败重试。
- **操作无响应**：点击后等待 API 返回，无 loading 反馈。
- **离线 / 弱网"假死"**：弱网下请求长时间不返回又不超时。
- **流量浪费**：重复请求、压缩不充分、协议头冗余。

**业务代价**：

- 头部应用：API P99 每降 100ms，留存 +0.5%、转化率 +1%。
- 弱网下用户操作放弃率比强网高 5-10 倍。
- 流量过度消耗会让用户主动停用应用（特别是预付费 / 国际场景）。

### 1.2 度量准则

按 [`卷零·02 §3`](../00.公共方法论/02.跨平台指标体系.md) 指标体系：

**资源视角（USE）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| 带宽利用率 | 实际下载速率 / 链路上限 | > 60%（理想情况）|
| 连接数饱和 | 同时活跃 TCP 连接 | < 10 |
| 失败率 | 请求失败 / 总请求 | < 1% |

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| API P50 | 中位响应时长 | < 200ms |
| API P95 | 95% 分位 | < 800ms |
| API P99 | 长尾 | < 2s |
| API 失败率（Errors）| | < 0.5% |
| 弱网超时率 | 仅弱网下 | < 5% |

**用户感知（APDEX）**：

- *Satisfied*：API < 1s
- *Tolerating*：1-3s
- *Frustrated*：> 3s 或失败

### 1.3 行业基准与目标

| 平台 | API P50 | API P99 | 失败率 |
|---|---|---|---|
| Android / iOS（4G）| 200ms | < 1s | < 0.5% |
| Web（4G） | LCP < 2.5s | TTI < 5s | < 1% |
| 弱网（< 100Kbps）| 1s | < 5s | < 5% |

### 1.4 反直觉问题清单

带着这些问题阅读：

1. HTTPS 比 HTTP 慢多少？是不是必须用 HTTPS？
2. HTTP/2 一定比 HTTP/1.1 快吗？
3. 多请求并发是不是越多越快？
4. 连接复用真的能省那么多吗？
5. 弱网下重试会让情况变好还是变坏？
6. CDN 加速真的有用吗？
7. WebSocket 比 HTTP 长轮询快多少？
8. DNS 查询为什么有时几百毫秒？

## 02.第一性原理

### 2.1 网络性能本质

**一句话定义**：

> **网络性能 = 单位时间能完成多少有效数据传输 + 平均每次传输的延迟**。

这句话隐含三个不可商量的物理约束：

**约束一：网络是"距离 × 带宽"的硬约束**

物理光速决定了最小 RTT（Round Trip Time）：

```
   北京 → 美西：~150ms RTT（光速理论下限 ~100ms + 路由延迟）
   北京 → 上海：~30ms RTT
   北京 → 北京：~5-20ms RTT
```

**这是物理硬约束**：任何"加速"都不能让数据包跑得比光快。优化只能是"减少往返次数"。

**约束二：网络协议有固定开销**

每次连接都要：

```
   DNS 查询    50-500ms（视缓存）
   TCP 握手    1 RTT（~30-150ms）
   TLS 握手    1-2 RTT（HTTPS）
   HTTP 请求   1 RTT（请求 + 响应）
   ─────────────────────────────────
   首次请求    3-5 RTT = 100-700ms（仅协议开销）
```

这就是为什么"连接复用"如此重要：复用连接省去 DNS + TCP + TLS 三次握手。

**约束三：弱网会指数级放大问题**

弱网（高 RTT + 高丢包）下，TCP 重传 + TLS 握手丢包都会让单次请求时间从 100ms 涨到几秒甚至超时。**弱网治理是网络优化的最大变量**。

### 2.2 协议层效率模型

**为什么"协议层效率"是网络治理的核心**

每个协议都在做"功能 vs 性能"的取舍：

```
   ┌──────────────────────────────────────────────┐
   │ HTTP/1.1                                     │
   │ - 每请求一连接 / 队头阻塞                       │
   │ - keepalive 部分缓解                          │
   ├──────────────────────────────────────────────┤
   │ HTTP/2                                       │
   │ - 多路复用（一连接多请求）                      │
   │ - 头部压缩（HPACK）                            │
   │ - 仍受 TCP 队头阻塞影响                        │
   ├──────────────────────────────────────────────┤
   │ HTTP/3 (QUIC)                                │
   │ - 基于 UDP，无 TCP 队头阻塞                    │
   │ - 0-RTT 重连                                  │
   │ - 弱网表现优于 H2                              │
   ├──────────────────────────────────────────────┤
   │ WebSocket / 长连接                            │
   │ - 一次握手长期通信                              │
   │ - 适合实时双向                                 │
   │ - 需要心跳保活                                 │
   └──────────────────────────────────────────────┘
```

**网络问题的三类典型形态**：

```
   ┌────────────────────────────────────────────────┐
   │ A. 连接开销主导：每请求都重连                     │
   │    根因：未启用 keepalive / 长连接               │
   ├────────────────────────────────────────────────┤
   │ B. 串行依赖：请求互相等                          │
   │    根因：A 完成才能发 B / 同步阻塞               │
   ├────────────────────────────────────────────────┤
   │ C. 弱网放大：高 RTT 高丢包                       │
   │    根因：未做弱网容错 / 超时策略不当              │
   └────────────────────────────────────────────────┘
```

### 2.3 跨平台同构原理

所有平台的网络栈都基于 TCP/IP，应用层都是 HTTP / WebSocket / 自定义协议：

```
   通用网络模型：

      [应用 API]   →   [HTTP 客户端]   →   [TLS]   →   [TCP/UDP]   →   [网卡]
       业务请求          OkHttp / URLSession   SSL/TLS    内核网络栈   硬件
```

每个平台都必须有：

| 抽象组件 | 解决什么问题 |
|---|---|
| HTTP 客户端 | 封装 HTTP 协议细节 |
| 连接池 | 复用 TCP / TLS 连接 |
| DNS 缓存 | 减少 DNS 查询 |
| 重试策略 | 弱网容错 |
| 超时控制 | 防止永久阻塞 |

**跨平台术语对照**

| 通用术语 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| HTTP 客户端 | OkHttp / Retrofit | URLSession / Alamofire | fetch / axios | libcurl |
| 连接池 | OkHttp ConnectionPool | URLSession 自动 | 浏览器自动 | 自实现 |
| 长连接 | OkHttp WebSocket | URLSessionWebSocketTask | WebSocket API | 自实现 |
| HTTP/2 | OkHttp 自动 | URLSession 自动 | 浏览器自动 | 视库 |
| QUIC / HTTP/3 | Cronet | URLSession iOS 15+ | 部分浏览器 | 视库 |

**同构带来的工程价值**

1. **协议优化思路通用**：复用、合并、压缩、缓存 跨端通用。
2. **弱网治理通用**：超时控制、重试策略、降级逻辑。
3. **指标体系通用**：API 延迟分位 + 失败率 + 弱网占比。

### 2.4 平台差异点矩阵

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 默认 HTTP 客户端 | OkHttp（生态主流）| URLSession（系统）| fetch（浏览器内置）| libcurl / 厂商 |
| HTTP/2 支持 | OkHttp 自动 | iOS 9+ | 浏览器自动 | 视库 |
| HTTP/3 / QUIC | Cronet（Google）/ OkHttp 实验 | iOS 15+ | Chrome / Edge | 视库 |
| 弱网模拟 | adb / 第三方 | Charles / Network Link Conditioner | DevTools throttling | 自定义 |
| 网络权限 | NetworkSecurityConfig | ATS（强制 HTTPS）| HTTPS / Service Worker | 自由 |
| DNS 优化 | HttpDns / 系统 | URLSession 自动 | 浏览器自动 | 自实现 |

> 后续遇到平台特化点回引本节。

## 03.度量与采集

### 3.1 三类采集方案的本质

```
   请求发起 ──▶ DNS / TCP / TLS ──▶ HTTP 传输 ──▶ 响应解析 ──▶ 业务回调
       │                                                            │
       ▼                                                            ▼
   ① 客户端打点（每请求埋点）
                ② 阶段拆解（系统提供的 timing API）
                            ③ 抓包分析（Charles / Wireshark / 自定义）
```

---

**① 客户端打点**

**核心原理（一句话）**：HTTP 客户端拦截器记录每个请求的开始 / 结束 / 错误，统计延迟与失败率。

**工作机理**：

```kotlin
// OkHttp 拦截器
class TimingInterceptor : Interceptor {
    override fun intercept(chain: Chain): Response {
        val start = System.nanoTime()
        val req = chain.request()
        try {
            val resp = chain.proceed(req)
            report(req.url, "ok", (System.nanoTime() - start) / 1_000_000)
            return resp
        } catch (e: Exception) {
            report(req.url, "fail:${e.javaClass.simpleName}", (System.nanoTime() - start) / 1_000_000)
            throw e
        }
    }
}
```

**物理本质**：从应用视角记录每个请求生命周期。

**为什么这样有效**：直接对应业务关心的"用户感知到的网络延迟"；开销极低。

**局限根源**：看不到协议细节（哪一阶段慢）。

**适用边界**：所有应用的核心监控方案。

---

**② 阶段拆解（Timing API）**

**核心原理（一句话）**：使用系统提供的 timing API 分解出 DNS / TCP / TLS / 等待 / 响应 / 解析 各阶段耗时。

**工作机理**：

| 平台 | API |
|---|---|
| Android OkHttp | EventListener（dnsStart/dnsEnd/connectStart...）|
| iOS URLSession | URLSessionTaskTransactionMetrics |
| Web | PerformanceResourceTiming（resource start / domainLookup / connect / requestStart / responseEnd）|

**物理本质**：协议栈各阶段对应用不透明，必须借助系统 API。

**适用边界**：归因每次"为什么慢"。

---

**③ 抓包分析（线下深度）**

**核心原理（一句话）**：在网络层抓取所有数据包，离线分析协议级行为。

**工作机理**：

- Charles / Wireshark / Fiddler：HTTPS 需安装根证书。
- mitmproxy：脚本化抓包。
- adb tcpdump：Android 命令行抓包。

**物理本质**：在数据包级别看真相。

**适用边界**：线下排查协议问题、抓"看不到的"行为。

---

**三种方案的总览**

| 方案 | 钩子位置 | 数据粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 客户端打点 | 应用 HTTP 库 | 请求级 | 极低 | 高 | ✅ | 不知协议细节 |
| ② 阶段拆解 | 系统 API | 阶段级 | 极低 | 中 | ✅ | API 不一致 |
| ③ 抓包 | 网络层 | 包级 | 低 | 极高 | ❌ | 需配置 |

### 3.2 各方案的可见盲区

| 现象 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| API 总耗时 | ✅ | ✅ | ✅ |
| 哪阶段慢（DNS/TCP/TLS）| ❌ | ✅ | ✅ |
| 重传 / 丢包 | ❌ | 部分 | ✅ |
| 加密包内容 | ❌ | ❌ | ✅（带证书）|
| HTTP/2 多路复用细节 | ❌ | 部分 | ✅ |

### 3.3 跨平台采集对照表

| 维度 | Android | iOS | Web |
|---|---|---|---|
| 客户端打点 | OkHttp Interceptor / EventListener | URLProtocol | fetch wrapper / Performance Resource API |
| 阶段拆解 | EventListener.dnsStart/connectStart... | URLSessionTaskTransactionMetrics | PerformanceResourceTiming |
| 弱网模拟 | adb / 第三方 / Charles | Network Link Conditioner | DevTools Network Throttling |
| 抓包 | Charles + 系统 CA | Charles + iOS CA | DevTools Network |

### 3.4 数据可信度评估

| 数据 | 可信度 | 偏差来源 |
|---|---|---|
| API 总耗时 | 高（< 1%）| 客户端时钟 |
| 阶段拆解 | 高 | 系统 API 准确 |
| 弱网识别 | 中 | 网络类型不准确（4G 可能很慢）|
| 失败原因 | 中 | 错误码合并损失信息 |

## 04.归因方法

### 4.1 网络问题决策树

```
网络问题
   │
   ├── 阶段 A. DNS 慢（> 200ms）──▶ DNS 优化
   │                              ├─ HttpDns 替代系统 DNS
   │                              └─ DNS 缓存 + 预解析
   │
   ├── 阶段 B. TCP / TLS 慢（> 500ms）──▶ 连接优化
   │                              ├─ 连接复用（keepalive）
   │                              ├─ HTTP/2 多路复用
   │                              └─ HTTP/3 (QUIC) 0-RTT
   │
   ├── 阶段 C. 服务端处理慢（TTFB > 300ms）──▶ 服务端优化
   │                              ├─ CDN / 边缘
   │                              └─ 后端逻辑优化
   │
   ├── 阶段 D. 响应传输慢（大体积）──▶ 数据优化
   │                              ├─ 压缩（gzip / brotli）
   │                              ├─ 协议升级（PB / FlatBuffer）
   │                              └─ 减少返回字段
   │
   └── 弱网放大 ──────────────────▶ 弱网容错
                                  ├─ 合理超时
                                  ├─ 降级 / 缓存
                                  └─ 重试策略
```

### 4.2 阶段拆解归因

**典型阶段时长占比**：

```
   首次请求（无连接复用）：
   DNS         50-200ms    20%
   TCP         30-150ms    15%
   TLS         60-300ms    30%
   等待 TTFB   50-300ms    25%
   传输        视体积       10%
   
   连接复用后：
   等待 TTFB   50-300ms    70-90%
   传输                    剩余
```

**归因思路**：先看哪一阶段最长，再针对性优化。

### 4.3 弱网模式归因

**弱网的物理特征**：

- 高 RTT（300ms+）
- 高丢包率（> 5%）
- 低带宽（< 100Kbps）
- 不稳定（速度波动大）

**弱网下的典型问题**：

- TCP 重传指数级增长（一个丢包导致整个 window 重传）。
- TLS 握手丢包让加密失败。
- 长任务超时（默认 60s 太长）。
- 用户已经放弃但请求仍在等待。

**弱网识别方法**：

- 系统 API：Android `NetworkCapabilities` / iOS Reachability。
- 主动探测：定期请求小固定大小数据，测量延迟。
- 业务感知：连续 N 次请求慢即判弱网。

### 4.4 失败重试归因

**重试是双刃剑**：

- 善用重试：偶发失败一次重试解决问题。
- 滥用重试：本来就慢的网络被重试雪上加霜。

**正确的重试策略**：

- **指数退避**（Exponential Backoff）：1s, 2s, 4s, 8s。
- **最大重试次数**（3-5 次）。
- **特定错误码才重试**（5xx 重试 / 4xx 不重试）。
- **幂等性检查**：POST 谨慎重试（可能重复创建）。

## 05.求证实验 ⭐

### 5.1 实验一：握手开销

**Step 1 — 原始观察**

工程师都知道 HTTPS 比 HTTP 慢，但**慢多少？连接复用后还慢吗？**

**Step 2 — 提出疑问**

> **HTTP / HTTPS / HTTP/2 在首次和连接复用情况下的延迟差异多大？**

**Step 3 — 形成假设**

**H₁**：首次连接 HTTPS 比 HTTP 慢 100-300ms（多 1-2 RTT TLS 握手）；连接复用后两者几乎相同。HTTP/2 在连接复用后并发请求显著快。  
**H₀**：HTTPS 永远慢。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 测试服务器 | 部署同一服务支持 HTTP / HTTPS / HTTP2 |
| 网络 | Wi-Fi 50Mbps |
| 请求 | 单独 GET 1KB JSON |
| 场景 | 首次请求 / 连接复用第 2-10 次 |

**Step 5 — 实测数据**

| 协议 | 首次 (ms) | 复用第 2 次 (ms) |
|---|---|---|
| HTTP/1.1 | 50 | 35 |
| HTTPS（HTTP/1.1 + TLS）| 220 | 38 |
| HTTP/2（HTTPS）| 230 | 38 |

并发 10 请求：

| 协议 | 串行总时长 | 并发总时长 |
|---|---|---|
| HTTP/1.1 keepalive | 350 ms | 220 ms（最多 6 条 TCP）|
| HTTP/2 | 380 ms | 80 ms（多路复用）|

**Step 6 — 验证 / 修正**

- 首次 HTTPS 比 HTTP 慢 170ms（TLS 握手）。
- 连接复用后 HTTPS 与 HTTP 几乎相同（38ms vs 35ms）。
- HTTP/2 在并发时显著优于 HTTP/1.1（80ms vs 220ms）。
- 验证 H₁。

**Step 7 — 提炼结论**

> **HTTPS 的"慢"主要在首次连接（多 1-2 RTT TLS 握手）。  
> 连接复用后开销可忽略。HTTP/2 在多请求并发场景下显著优于 HTTP/1.1。**

工程意义：

- 必用 HTTPS（安全 + 复用后无开销）。
- 必用连接复用（keepalive / 连接池）。
- 多请求场景必用 HTTP/2 / HTTP/3。
- 首次连接慢可用 HTTP/3 0-RTT 缓解。

**Step 8 — 边界**

- 实验数据基于良好网络。弱网下 TLS 握手时间会更长。
- 服务端 SSL 配置不当会增加延迟。
- HTTP/3 在弱网下优势更明显（无 TCP 队头阻塞）。

---

### 5.2 实验二：弱网超时策略

**Step 1 — 原始观察**

弱网下默认超时 30-60 秒，用户根本等不了那么久；但太短又会"明明能成功"被截断。**最优超时是多少？**

**Step 2 — 提出疑问**

> **不同超时配置（5s / 10s / 30s / 60s）下，弱网请求的成功率与"用户实际等待时间"如何变化？**

**Step 3 — 形成假设**

**H₁**：超时太短会牺牲成功率；太长会浪费用户时间。最优值在 10-15s 区间。  
**H₀**：超时设大点更好。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 弱网模拟 | RTT 500ms / 丢包 10% / 带宽 50Kbps |
| 超时配置 | 5s / 10s / 15s / 30s / 60s |
| 主指标 | (a) 请求成功率 (b) 用户平均等待时间 |
| 重复 | 每场景 200 次 |

**Step 5 — 实测数据**

| 超时 | 成功率 | 失败时用户等待（s）| 加权用户体验 |
|---|---|---|---|
| 5s | 78% | 5 | 中 |
| 10s | 92% | 10 | 较好 |
| 15s | 95% | 15 | 较好 |
| 30s | 96% | 30 | 较差 |
| 60s | 97% | 60 | 差 |

**Step 6 — 验证 / 修正**

- 5s 太短，成功率明显下降。
- 10-15s 是甜蜜点。
- 30s+ 边际收益极低（多 1% 成功率 vs 多 15s 等待）。
- 验证 H₁。

**Step 7 — 提炼结论**

> **弱网超时建议 10-15 秒。短于 5s 牺牲成功率，长于 30s 浪费用户时间。**

工程意义：

- 不要用默认 60s 超时。
- 关键场景（首屏 / 关键操作）可用 10s + 重试。
- 非关键（统计 / 上报）可用 5s 超时即放弃。

**Step 8 — 边界**

- 不同业务对成功率敏感度不同。
- 大数据传输需要更长超时。
- 弱网识别后可动态调整超时。

---

### 5.3 实验三：连接复用收益

**Step 1 — 原始观察**

工程师都用连接池，但**连接池大小、空闲时长怎么配？什么时候应该断开？**

**Step 2 — 提出疑问**

> **连接池大小 N 与请求平均延迟的关系是什么？空闲连接保留多久最优？**

**Step 3 — 形成假设**

**H₁**：连接池大小 N 应等于"并发峰值"；空闲保留 5-10 分钟（与服务端 keepalive 对齐）。  
**H₀**：连接池越大越好。

**Step 4 — 设计实验**

| 项 | 配置 |
|---|---|
| 测试场景 | 模拟用户行为：每 5 秒发 3-5 请求 |
| 连接池大小 | 1 / 5 / 10 / 20 |
| 空闲保留 | 1min / 5min / 10min |
| 主指标 | 平均请求延迟 / 连接重建率 |

**Step 5 — 实测数据**

| 连接池大小 | 空闲 5min | 平均延迟（ms）| 重建率 |
|---|---|---|---|
| 1 | 5min | 80（队头阻塞）| 5% |
| 5 | 5min | 30 | 5% |
| 10 | 5min | 28 | 4% |
| 20 | 5min | 28 | 4% |

| 空闲保留 | 池 5 | 平均延迟 | 重建率 |
|---|---|---|---|
| 1min | 5 | 60（频繁重建）| 30% |
| 5min | 5 | 30 | 5% |
| 10min | 5 | 28 | 3% |

**Step 6 — 验证 / 修正**

- 池 5 已经覆盖大部分场景。再大无收益。
- 空闲保留 5min 是甜蜜点。

**Step 7 — 提炼结论**

> **连接池大小 = 并发峰值（典型 5）；空闲保留 5 分钟。  
> 超过这两者收益递减。**

工程意义：

- OkHttp 默认 5 / 5 分钟基本够用。
- 大并发应用可调到 10。
- 不要为"快"开 50+，吃不消还可能被服务端限。

**Step 8 — 边界**

- 服务端 keepalive 时长决定空闲上限。
- 移动应用切网络（Wi-Fi → 4G）时连接池要清空。

---

### 5.4 三大实验启示

```
   握手开销     → HTTPS 首次慢 100-300ms，复用后无差异 ─┐
                                                         │
   弱网超时     → 10-15s 是甜蜜点                       ├─▶ 网络优化 = 减请求 + 减开销 + 防弱网
                                                         │
   连接复用     → 池 5 / 5min 是默认最优                ─┘
```

**统一启示**：

- **HTTPS 不是"慢"的元凶**：连接复用后开销可忽略。
- **超时不是越长越好**：用户体验 vs 成功率有甜蜜点。
- **数据驱动配置**：连接池等参数都有最优值。

## 06.优化策略

### 6.1 通用治理矩阵

按"协议层 × 业务层"展开：

| 维度 | 治理方向 | 通用手段 |
|---|---|---|
| 协议层 | 减少握手 | HTTPS 连接复用 / HTTP/2 / HTTP/3 |
| 协议层 | 减少 DNS | HttpDns / 缓存 / 预解析 |
| 协议层 | 减少传输量 | gzip / brotli / Protocol Buffer |
| 协议层 | 减少 TLS 开销 | TLS 1.3 / Session Resumption |
| 业务层 | 减少请求数 | 批量 API / 合并 / GraphQL |
| 业务层 | 缓存 | HTTP 缓存（ETag / Cache-Control）/ 业务层缓存 |
| 业务层 | 并发 | 关键资源并发拉取 |
| 业务层 | 弱网容错 | 合理超时 / 重试 / 降级 |
| 业务层 | 预取 | 预测用户行为提前加载 |
| 业务层 | 离线 | Service Worker / 本地缓存 |

### 6.2 平台特化策略

**Android 特化**：

- 用 OkHttp（行业标准），开启 ConnectionPool。
- 启用 HTTP/2（默认）和 HTTP/3 / QUIC（Cronet）。
- HttpDns 替代系统 DNS（避免运营商劫持）。
- 大数据用 OkHttp + 流式处理（避免一次性加载到内存）。
- 网络变化时清空连接池。

**iOS 特化**：

- 优先使用 URLSession（系统级）。
- 配置 `URLSessionConfiguration` 的连接池。
- iOS 15+ 支持 HTTP/3（自动）。
- ATS 强制 HTTPS。
- WatchOS / iPadOS 同样 API。

**Web 特化**：

- HTTP/2 / HTTP/3 自动协商（浏览器决定）。
- Service Worker 缓存（PWA）。
- 资源预加载（`<link rel="preload">`）。
- DNS 预解析（`<link rel="dns-prefetch">`）。
- 关键 CSS 内联，非关键资源延迟。

**嵌入式特化**：

- 用 libcurl / mbedtls 等成熟库。
- 严格控制并发数（资源有限）。
- 实现自己的连接池。

### 6.3 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 |
|---|---|---|---|---|
| 极高 | 全站 HTTPS + 连接复用 | API 复用后延迟 -50-70% | 1-2 周 | 中 |
| 极高 | 弱网超时优化 (10-15s) | 弱网体验大幅改善 | 几天 | 低 |
| 高 | HTTP/2 全启用 | 多请求场景 -50% | 1 周 | 低 |
| 高 | HttpDns 替代系统 DNS | DNS 慢减少、防劫持 | 1 周 | 中 |
| 高 | 数据压缩（gzip/PB）| 流量 -50%、延迟 -30% | 1-2 周 | 低 |
| 中 | HTTP/3 (QUIC) | 弱网优势 | 2-4 周 | 中 |
| 中 | 缓存策略优化 | 重复请求减少 | 1-2 周 | 中（一致性） |
| 低 | 自实现协议 | 极少收益 | 极高 | 极高 |

**避免反向收益**：

- 过度并发：服务端限流，重试反而拥塞。
- 过度缓存：数据不一致问题。
- 过度重试：弱网雪上加霜。

## 07.实战案例

### 7.1 跨端同构案例

**背景**：某社交应用首屏 6 个 API 串行（依赖关系）总耗时 2.5s，希望优化。Android / iOS / Web 都有同样问题。

**度量与归因**：

仔细分析依赖关系：实际只有 2 个 API 真正依赖前置结果，其余 4 个可以并行。

**假设与求证**：

提出**统一假设**："拆分依赖图，把可并行的并发执行"。

修复设计：

```
   原始（串行）：
   A → B → C → D → E → F  总耗时 = ΣTi

   优化（并发）：
   A → B → ┬─→ D ─→ E
           └─→ C ─→ F
   总耗时 = max(D+E, C+F) + A + B
```

**验证**：

| 平台 | 优化前 | 优化后 | 降幅 |
|---|---|---|---|
| Android | 2.5s | 1.2s | 52% |
| iOS | 2.4s | 1.1s | 54% |
| Web | 2.6s | 1.3s | 50% |

**统一启示**：网络优化跨端通用法则 = **依赖图分析 + 并发化**。

### 7.2 平台特异案例

**背景**：Android 应用在某些地区 DNS 失败率 5%，iOS 同地区 < 0.5%。

**现象**：Android 用户报告"打不开"，iOS 没问题。

**度量与归因**：

抓包发现：Android 用 InetAddress.getByName 查系统 DNS，部分运营商 DNS 不稳定。iOS 系统 DNS 自带 fallback。

**假设与求证**：

**假设**：用 HttpDns 服务（如阿里 / 腾讯）替代系统 DNS。

**实验**：HttpDns 失败率 < 0.1%，且不被运营商劫持。

**修复**：Android 接入 HttpDns + 系统 DNS fallback。

**验证**：失败率从 5% 降到 0.3%。

**边界与上线策略**：HttpDns 需要 IP 白名单（先用本地 IP 列表 fallback）。

### 8.2 编码期 Lint

- 关键 API 调用未设超时 → 错误。

- 主线程同步网络调用 → 错误。

### 8.3 CI 卡口与线上 SLO

**CI 卡口**：

- API 关键场景 P95 延迟基准。
- 弱网模拟用例：成功率 ≥ 阈值。
- 流量监控：每次发版流量增长 < 5%。

**线上 SLO**：

- API P50 < 200ms / P99 < 2s。
- 失败率 < 0.5%。
- 弱网超时率 < 5%。

## 10.总结与延伸

### 10.1 五条核心原则

1. **协议优化 + 业务优化**：两者缺一不可。
2. **复用最有效**：HTTPS / HTTP/2 / 连接池都基于复用。
3. **弱网容错是必修课**：合理超时 + 智能重试 + 降级链路。
4. **数据驱动**：每次请求都有阶段拆解 + 长尾分析。
5. **预取胜过实时**：用预测换响应。

### 10.2 五个常见误区

1. **"HTTPS 总是慢"**：错（复用后无差异）。
2. **"超时设大点稳"**：错（用户体验差）。
3. **"重试越多越稳"**：错（弱网雪上加霜）。
4. **"HTTP/2 自动加速"**：要服务端配合。
5. **"WebSocket 总比 HTTP 快"**：长连接有保活成本。

### 10.3 延伸阅读

- IETF RFC 9114 (HTTP/3)
- Google Web Fundamentals: *Networking*
- WWDC: *Modern Network Performance*

> **网络性能 = 协议层效率 × 业务层调度。  
> 连接复用最有效，HTTPS 不是"慢"的元凶，弱网容错是必修课。  
> 数据驱动，每次请求都看分位 + 阶段。**
