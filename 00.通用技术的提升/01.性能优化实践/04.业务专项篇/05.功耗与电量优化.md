### 00 开篇导论

**0.1 一句话定位**

**功耗是性能领域的"长尾杀手"**——单次开销很小，但累积放大后会让用户的电池一天少撑 2 小时。一个后台 30 秒一次的心跳、一个屏幕亮着的 5 分钟动画、一个频繁 GPS 定位的服务，都是"流量级"投诉的源头。

**0.2 为什么独立成章**

性能优化通常追求"快"，但功耗优化追求"省"——这两个目标经常冲突。比如多线程加速可能更耗电，预加载可能浪费流量和功耗。需要单独建立一套度量、归因、决策框架。

**0.3 与其他章的关系**

- 上承卷零·01 [第一性原理](../00.公共方法论/01.性能工程总论原理.md)：功耗是"资源"维度的长期消耗
- 横联 CPU/网络/IO 各章：功耗是这些资源使用的最终代价
- 下承网络优化、定位优化、唤醒治理等专项

**0.4 8 个反直觉问题**

1. 为什么 App 在前台用得多反而比后台耗电少（按比例）？
2. 屏幕亮 1 秒和 CPU 跑 1 秒，哪个更耗电？
3. WiFi 和 4G 哪个更省电？
4. 为什么"心跳间隔越长越省电"不一定成立？
5. AlarmManager 的"精确"和"不精确"差几十倍功耗？
6. 后台定位为什么是电量黑洞？
7. 为什么 push 推送比 App 自轮询省电？
8. 暗黑模式真的能省电吗？

### 02 问题与认知

**2.1 功耗的物理本质**

手机功耗主要由四部分组成：

| 模块 | 占比 | 关键 |
|---|---|---|
| 屏幕 | 30-50% | 亮度、刷新率、色深 |
| CPU/SoC | 20-30% | 频率、核数、任务密度 |
| 通信 | 15-25% | WiFi/4G/GPS 唤醒 |
| 其他 | 10% | 传感器、振动、扬声器 |

**关键认知**：屏幕和通信是最大头，CPU 反而不是。这与"性能优化主战场是 CPU"形成鲜明对比。

**2.2 通信的"高耗能尾巴"**

通信芯片有"工作 → 高功耗保持（tail time）→ 休眠"三态。一次小数据包发送会触发完整的 tail time（约 5-10 秒）。**因此**：100 个包 1 秒发完，比 100 个包分散 100 秒发，省电 90%。

**2.3 三个共识**

- **省电 = 让硬件多睡觉**：CPU 降频、屏幕灭、网卡休眠
- **批量是省电的元方法**：批量请求、批量传感器、批量定位
- **后台越简单越好**：后台任务每多一个，电池就少一段

### 03 度量与采集

**3.1 三类采集方案的本质**

**方案 A·系统电量统计**

- **核心原理**：读取 batterystats（Android）或 IOPMrootDomain（iOS）系统级耗电统计
- **工作机理**：系统按"唤醒时长 × 模块功率"估算每个 App 耗电
- **物理本质**：基于硬件功耗模型计算
- **局限根源**：只是估算（误差 10-30%），不是真实测量
- **适用场景**：相对对比、长期趋势

**方案 B·物理功耗台**

- **核心原理**：直接接入电池电流监测设备（Monsoon/Power Profiler）
- **工作机理**：硬件级测量电流，毫安级精度
- **物理本质**：地面真值
- **局限根源**：实验室设备，不可线上化
- **适用场景**：性能基线、功耗实验

**方案 C·业务事件归因**

- **核心原理**：埋点记录所有"高耗能事件"（CPU 高、网络发送、屏幕唤醒）
- **工作机理**：每次唤醒/发送/定位带时长 + 调用栈
- **物理本质**：以"工程归因"换取"线上可观测"
- **局限根源**：只能归因到事件，不能直接换算电量
- **适用场景**：线上根因分析

**3.2 三方案差异矩阵**

| 维度 | A 系统统计 | B 物理台 | C 事件归因 |
|---|---|---|---|
| 精度 | 中 | 极高 | 间接 |
| 上线可用 | 是 | 否 | 是 |
| 归因能力 | 弱 | 强 | 强 |
| 成本 | 0 | 高 | 中 |

**3.3 跨平台同构**

| 平台 | 系统统计 | 物理台 | 事件归因 |
|---|---|---|---|
| Android | dumpsys batterystats | Monsoon | WakeLock/JobScheduler 埋点 |
| iOS | MetricKit | 同上 | BackgroundTask 埋点 |
| 服务端 | 不适用 | 机柜级 PUE | 无直接对应 |

**同构本质**：所有移动平台都遵循"硬件功耗模型 + 唤醒时长 × 功率"框架。

### 04 归因与定位

**4.1 功耗问题二分决策树**

```
耗电高
├─ 前台还是后台？
│  ├─ 前台 → 屏幕/CPU/网络密集（看哪类）
│  └─ 后台 → 唤醒次数过多（最常见）
│     ├─ 网络心跳？
│     ├─ 定位服务？
│     ├─ Job/Alarm 频繁触发？
│     └─ 第三方 SDK？
└─ 是个别用户还是全量？
   ├─ 个别 → 设备 / 网络环境特异
   └─ 全量 → 通用问题，深入排查 §4.2
```

**4.2 后台耗电四大元凶**

- **WakeLock 滥用**：长时间持有 PARTIAL_WAKE_LOCK 防止 CPU 休眠
- **网络心跳过频**：< 10 分钟一次的网络请求基本浪费
- **定位精度过高**：后台用 GPS 高精度定位
- **AlarmManager 精确触发**：setExact 的精确时机让 CPU 无法批量唤醒

**4.3 唤醒次数 vs 唤醒时长**

后台耗电核心指标：

- **唤醒次数（次/小时）**：影响通信 tail time，每次唤醒成本 ≈ 5-10 秒
- **唤醒时长占比（%）**：影响 CPU 高频时段
- **联合指标**：tail time 总占比 = 唤醒次数 × 5s / 总时间

### 05 求证实验

**5.1 实验一：心跳间隔的甜区**

**问题**：长连接心跳间隔多长最省电又能保活？

- **第 1 步·假设**：30 秒和 5 分钟的功耗差距很大；5 分钟之后边际收益递减
- **第 2 步·设计**：分别用 30s/1min/3min/5min/10min/30min 间隔做心跳，物理台测一小时耗电
- **第 3 步·控制变量**：同设备、同网络（WiFi）、屏幕灭
- **第 4 步·指标**：累计耗电（mAh）
- **第 5 步·执行**：Monsoon
- **第 6 步·收集**：30s → 28mAh、1min → 18、3min → 12、5min → 10、10min → 9.5、30min → 9
- **第 7 步·分析**：每次心跳 + tail time ≈ 7 秒，30s 间隔的"工作时间占比"巨大；5 分钟后 tail time 已可忽略
- **第 8 步·结论**：心跳间隔 ≥ 5 分钟，再长边际收益小但失去保活意义；最佳甜区 5-10 分钟
- **第 9 步·扩展**：智能心跳（NAT 探测）可动态调整，进一步节电

**5.2 实验二：定位精度的代价**

**问题**：高精度 GPS、网络定位、被动定位耗电差几倍？

- **第 1 步·假设**：GPS > 网络 > 被动，差 10x 以上
- **第 2 步·设计**：分别用 GPS_PROVIDER（高精度）/NETWORK_PROVIDER/PASSIVE_PROVIDER 持续定位 30 分钟
- **第 3 步·控制变量**：同位置（户外）、同设备
- **第 4 步·指标**：耗电（mAh）、定位精度（米）
- **第 5 步·执行**：Monsoon + 系统 API
- **第 6 步·收集**：GPS → 35mAh 精度 5m；网络 → 8mAh 精度 50m；被动 → 0.5mAh 精度依赖其他 App
- **第 7 步·分析**：GPS 需要持续唤醒卫星接收器；网络定位用基站 + WiFi MAC，开销小很多
- **第 8 步·结论**：除非业务必须，绝不用 GPS 后台持续定位；优先被动 → 网络 → GPS
- **第 9 步·扩展**：iOS Significant Location Change 是更省电的"位置变化触发"模式

**5.3 实验三：批量唤醒的收益**

**问题**：100 次小请求逐次发 vs 批量打包一次发，省电多少？

- **第 1 步·假设**：批量省 80% 以上电
- **第 2 步·设计**：100 个 1KB 请求，分别"5 秒 1 次共 500 秒"和"全部打包 1 次"两种模式
- **第 3 步·控制变量**：同 4G 环境、同设备
- **第 4 步·指标**：累计耗电
- **第 5 步·执行**：Monsoon
- **第 6 步·收集**：逐次 → 56mAh；批量 → 7mAh（8x 差距）
- **第 7 步·分析**：每次小请求触发完整 tail time（5-10 秒）；批量只触发一次
- **第 8 步·结论**：所有非紧急请求必须用 JobScheduler 批量调度；紧急请求合并 1-2 秒窗口
- **第 9 步·扩展**：Doze 模式下系统会强制批量，符合系统期望反而双赢

### 06 治理与原则

**6.1 功耗五字诀**

- **少**：能不做就不做（后台必要性审查）
- **批**：能批量就批量（网络、定位、传感器）
- **让**：让系统决定时机（JobScheduler、WorkManager）
- **延**：能延迟就延迟（非紧急任务等待充电/WiFi）
- **轻**：能轻量就轻量（WiFi 比 4G 省电、被动比 GPS 省电）

**6.2 选型决策树**

```
要做什么后台任务？
├─ 紧急通知 → push（FCM/APNs），不要自轮询
├─ 数据同步 → WorkManager + Constraint(WiFi+充电)
├─ 位置追踪 → 被动定位 / 系统位置变化通知
├─ 心跳保活 → 5-10 分钟，智能调整
└─ 定时任务 → AlarmManager.setInexact / 系统 Job
```

**6.3 反模式清单**

- ❌ PARTIAL_WAKE_LOCK 长期持有
- ❌ 后台 30 秒一次心跳
- ❌ 后台高精度 GPS 定位
- ❌ AlarmManager.setExact 用于非紧急任务
- ❌ 每个事件都立刻发请求
- ❌ 暗黑模式只改色不关注 OLED 像素

### 07 防劣化体系

**7.1 三道防线**

- **第一道·开发期**：Battery Historian / Energy Log 必查
- **第二道·CI**：物理台基线测试，新版功耗 > 基线 10% 阻断
- **第三道·线上**：MetricKit / batterystats 抽样上报

**7.2 SLO 示例**

- 后台每小时耗电 ≤ 0.5%（低端机）
- 唤醒次数 ≤ 6 次/小时
- 后台 CPU 时长占比 ≤ 1%
- WakeLock 累计时长 ≤ 30 秒/小时

### 08 案例与教训

**8.1 跨端同构案例·心跳风暴**

某 App 长连接断线后重连策略是"每 5 秒重试"。一旦遇到弱网长时间不通，连续重试 1 小时，耗电飙升 5x。**修法**：指数退避 5s/10s/30s/1min/5min；上限 5 分钟。**教训**：所有重试都必须有指数退避 + 上限。

**8.2 平台特异案例·iOS Background Fetch 滥用**

某 iOS App 把数据同步全放 Background Fetch，结果系统智能调度后频繁唤醒，电池被吃光。**修法**：核心同步用 push 触发，非核心用 BGProcessingTask 设置 requiresExternalPower = true。**教训**：iOS 的后台 API 越精细，误用代价越大。

### 09 原理深挖

**9.1 Doze 模式的工程意图**

Android 6+ 引入 Doze：屏幕灭、不充电、静止 1 小时后进入 Doze，所有网络/Job/Alarm 暂停，只在维护窗口短暂放行。这强制 App 批量化，是系统级省电的范式。**App 应主动配合**：不要试图绕过 Doze（那只会被系统降权）。

**9.2 OLED 暗黑模式的真省电**

OLED 像素不亮 = 不耗电。纯黑像素比白色省 60% 屏幕功耗。但**LCD 屏暗黑模式不省电**（背光始终全亮）。判断设备屏幕类型再做差异化。

**9.3 5G 的功耗陷阱**

5G 通信芯片功耗比 4G 高 30-50%；非 5G 高速场景下，5G 反而是负担。系统通常自动切换，但应用应该避免长期占用 5G 通道做小数据传输。

### 10 总结与扩展

**10.1 一图概括**

```
功耗优化
    ├─ 屏幕 → 暗黑模式 + 亮度自动 + 灭屏快
    ├─ CPU → 任务批量 + 让系统调度
    ├─ 通信 → 心跳 5+ 分钟 + 批量打包
    ├─ 定位 → 被动 > 网络 > GPS
    └─ 监控 → 唤醒次数 + WakeLock 时长
```

**10.2 三个外延**

- **碳排追踪**：手机功耗最终对应碳排放，是 ESG 的端侧指标
- **设备老化**：电池循环 500+ 次后容量衰减，App 应自适应低电量行为
- **AI 调度**：未来 OS 可能用 ML 预测 App 唤醒时机，进一步省电

**10.3 给团队的建议**

- 第 1 周：审计所有后台任务，无必要的全部砍掉
- 第 2 周：心跳间隔统一调到 5 分钟以上
- 第 3 周：定位精度全面降级（除非业务必须）
- 第 4 周：上线 batterystats 抽样，建电量大盘

功耗是"看不见的承诺"——用户不会因为电池长 1 小时来夸你，但一定会因为电池短 1 小时骂你。
