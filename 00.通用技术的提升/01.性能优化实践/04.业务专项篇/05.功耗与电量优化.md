### 00 开篇导论

**0.1 一句话定位**

**功耗是性能领域的"长尾杀手"**——单次开销很小，但累积放大后会让用户的电池一天少撑 2 小时。一个后台 30 秒一次的心跳、一个屏幕亮着的 5 分钟动画、一个频繁 GPS 定位的服务，都是"流量级"投诉的源头。

**0.2 为什么独立成章**

性能优化通常追求"快"，但功耗优化追求"省"——这两个目标经常冲突。比如多线程加速可能更耗电，预加载可能浪费流量和功耗。需要单独建立一套度量、归因、决策框架。

**0.3 与其他章的关系**

- 上承卷零·01 [第一性原理](../00.公共方法论/01.性能工程总论原理.md)：功耗是"资源"维度的长期消耗
- 横联 CPU/网络/IO 各章：功耗是这些资源使用的最终代价
- 下承网络优化、定位优化、唤醒治理等专项

**0.4 8 个反直觉问题**

1. 为什么 App 在前台用得多反而比后台耗电少（按比例）？
2. 屏幕亮 1 秒和 CPU 跑 1 秒，哪个更耗电？
3. WiFi 和 4G 哪个更省电？
4. 为什么"心跳间隔越长越省电"不一定成立？
5. AlarmManager 的"精确"和"不精确"差几十倍功耗？
6. 后台定位为什么是电量黑洞？
7. 为什么 push 推送比 App 自轮询省电？
8. 暗黑模式真的能省电吗？

### 00.5 贯穿案例：导航 App"用 1 小时手机没电"事件

> 本案例贯穿全文：§02 看懂功耗物理本质、§04 用决策树定位、§05 用实验复盘、§06 给出分层闭环。

#### 案例背景

某出行类导航 App V6.0 上线"全程实时车辆追踪"功能（产品要求"用户开车 1 小时也能稳定定位"），用户反馈崩塌：

- **用 1 小时手机耗电 35%**（之前 8%）。
- **手机持续发烫**，部分机型触发降频，定位精度反而下降。
- 应用商店一星差评激增："开个导航手机就废了"。
- 100 万 DAU 中投诉 12,000+/日。
- 与百度地图/高德对比测试：竞品同场景 1 小时耗电 10-12%，**功耗 3 倍**。

研发组初步反应："导航本来就费电，这是物理限制。"——这是典型的"物理背锅"。

#### 经验派的 3 周折腾（典型反面教材）

| 周次 | 动作 | 结果 |
|---|---|---|
| 第 1 周 | 把屏幕亮度降低到自动（怕屏幕耗电）| 用户看不清，体验差；耗电降到 32% |
| 第 2 周 | 关闭语音播报（怕扬声器耗电）| 用户怒了：导航不语音播报？耗电 30% |
| 第 3 周 | 降低地图刷新率到 30fps（怕 GPU 耗电）| 地图卡顿，耗电 28%（仅微降）|

**复盘**：三周折腾错在"四处找耗电源"，但没碰到真正根因——**GPS 高精度定位 + 网络心跳 + 后台多任务**才是 80% 的耗电源。**屏幕和 GPU 都不是主战场**。

#### 方法派的 5 天闭环

**Day 1（§03 物理台 + 系统统计联合诊断）**：

- Monsoon 物理台测试：发现 GPS 持续高精度占电 38%、网络心跳 22%、屏幕 25%、其他 15%。
- batterystats：定位服务 1 小时唤醒 7200 次（2s 一次）。

→ **GPS 高频高精度是元凶**，竞品大多用"传感器融合 + 低频 GPS"。

**Day 2（§04 决策树）**：

- 前台运行 → 看哪类密集 → 定位（38%）→ §6.2 定位策略。
- 后台同步 → 心跳过频 → 5s 重试 → §6.1 心跳策略。

**Day 3-4（§06 分层策略）**：

- 第 1 层（少）：评估每个后台任务必要性，砍掉 60% 非核心。
- 第 2 层（批）：定位从 2s/次 改为 5s/次 + 加速度传感器融合（移动慢时延长到 10s）。
- 第 3 层（让）：把"地图预加载"改用 WorkManager 在 WiFi + 充电时执行。
- 第 4 层（轻）：定位策略升级——直行时低频 GPS、转弯时高频，省 50%。

**Day 5（上线 + 灰度验证）**：

#### 上线效果

| 指标 | 经验派 3 周后 | 方法派 5 天后 | 竞品 |
|---|---|---|---|
| 1 小时导航耗电 | 28% | **11%** | 10-12% |
| GPS 唤醒次数/h | 7200 | **720** | - |
| 后台 CPU 占比 | 8% | **1.2%** | - |
| 应用商店"耗电"差评 | 持续 | **下降 90%** | - |
| 定位精度（直行场景）| 5m | **8m**（无感知差）| 6m |

**核心洞察**：功耗优化**80% 收益来自定位 + 网络两个模块**，屏幕和 GPU 是小头。**经验派错在没分清主次**——一开始就该用物理台精确归因。**功耗治理 = 让硬件多睡觉，不是降低单次质量**。

#### 案例如何串起本文

- **§02 功耗物理本质** ▶▶ 通信和屏幕是大头，但定位是"通信 + 传感器"双高耗。
- **§04 决策树** ▶▶ 前台分支精准命中定位高耗。
- **§05 求证实验** ▶▶ §5.2 定位精度 + §5.3 批量唤醒都在案例中变现。
- **§06 分层策略** ▶▶ "少→批→让→轻"四层正是案例落地路径。

### 02 问题与认知

**2.1 功耗的物理本质**

手机功耗主要由四部分组成：

| 模块 | 占比 | 关键 |
|---|---|---|
| 屏幕 | 30-50% | 亮度、刷新率、色深 |
| CPU/SoC | 20-30% | 频率、核数、任务密度 |
| 通信 | 15-25% | WiFi/4G/GPS 唤醒 |
| 其他 | 10% | 传感器、振动、扬声器 |

**关键认知**：屏幕和通信是最大头，CPU 反而不是。这与"性能优化主战场是 CPU"形成鲜明对比。

> ▶▶ **回扣 §00.5 案例**：导航场景下"屏幕 25% + GPS 38% + 网络心跳 22%"——**定位类应用是反常态**：通信+定位 60%+，远超普通 App。**功耗优化必须按场景分析占比，不能套通用模型**。

**2.2 通信的"高耗能尾巴"**

通信芯片有"工作 → 高功耗保持（tail time）→ 休眠"三态。一次小数据包发送会触发完整的 tail time（约 5-10 秒）。**因此**：100 个包 1 秒发完，比 100 个包分散 100 秒发，省电 90%。

**2.3 三个共识**

- **省电 = 让硬件多睡觉**：CPU 降频、屏幕灭、网卡休眠
- **批量是省电的元方法**：批量请求、批量传感器、批量定位
- **后台越简单越好**：后台任务每多一个，电池就少一段

### 03 度量与采集

**3.1 三类采集方案的本质**

**方案 A·系统电量统计**

- **核心原理**：读取 batterystats（Android）或 IOPMrootDomain（iOS）系统级耗电统计
- **工作机理**：系统按"唤醒时长 × 模块功率"估算每个 App 耗电
- **物理本质**：基于硬件功耗模型计算
- **局限根源**：只是估算（误差 10-30%），不是真实测量
- **适用场景**：相对对比、长期趋势

**方案 B·物理功耗台**

- **核心原理**：直接接入电池电流监测设备（Monsoon/Power Profiler）
- **工作机理**：硬件级测量电流，毫安级精度
- **物理本质**：地面真值
- **局限根源**：实验室设备，不可线上化
- **适用场景**：性能基线、功耗实验

**方案 C·业务事件归因**

- **核心原理**：埋点记录所有"高耗能事件"（CPU 高、网络发送、屏幕唤醒）
- **工作机理**：每次唤醒/发送/定位带时长 + 调用栈
- **物理本质**：以"工程归因"换取"线上可观测"
- **局限根源**：只能归因到事件，不能直接换算电量
- **适用场景**：线上根因分析

**3.2 三方案差异矩阵**

| 维度 | A 系统统计 | B 物理台 | C 事件归因 |
|---|---|---|---|
| 精度 | 中 | 极高 | 间接 |
| 上线可用 | 是 | 否 | 是 |
| 归因能力 | 弱 | 强 | 强 |
| 成本 | 0 | 高 | 中 |

**3.3 跨平台同构**

| 平台 | 系统统计 | 物理台 | 事件归因 |
|---|---|---|---|
| Android | dumpsys batterystats | Monsoon | WakeLock/JobScheduler 埋点 |
| iOS | MetricKit | 同上 | BackgroundTask 埋点 |
| 服务端 | 不适用 | 机柜级 PUE | 无直接对应 |

**同构本质**：所有移动平台都遵循"硬件功耗模型 + 唤醒时长 × 功率"框架。

### 04 归因与定位

**4.1 功耗问题二分决策树**

```
耗电高
├─ 前台还是后台？
│  ├─ 前台 → 屏幕/CPU/网络密集（看哪类）
│  └─ 后台 → 唤醒次数过多（最常见）
│     ├─ 网络心跳？
│     ├─ 定位服务？
│     ├─ Job/Alarm 频繁触发？
│     └─ 第三方 SDK？
└─ 是个别用户还是全量？
   ├─ 个别 → 设备 / 网络环境特异
   └─ 全量 → 通用问题，深入排查 §4.2
```

> ▶▶ **回扣 §00.5 案例**：导航 App 走"前台 + 全量"分支，进一步定位"定位服务"分支。**经验派 3 周折腾错在没走决策树**，凭直觉找屏幕/GPU/扬声器，全部偏离主战场。

**4.2 后台耗电四大元凶**

- **WakeLock 滥用**：长时间持有 PARTIAL_WAKE_LOCK 防止 CPU 休眠
- **网络心跳过频**：< 10 分钟一次的网络请求基本浪费
- **定位精度过高**：后台用 GPS 高精度定位
- **AlarmManager 精确触发**：setExact 的精确时机让 CPU 无法批量唤醒

**4.3 唤醒次数 vs 唤醒时长**

后台耗电核心指标：

- **唤醒次数（次/小时）**：影响通信 tail time，每次唤醒成本 ≈ 5-10 秒
- **唤醒时长占比（%）**：影响 CPU 高频时段
- **联合指标**：tail time 总占比 = 唤醒次数 × 5s / 总时间

### 05 求证实验

**5.1 实验一：心跳间隔的甜区**

**问题**：长连接心跳间隔多长最省电又能保活？

- **假设**：30 秒和 5 分钟的功耗差距很大；5 分钟之后边际收益递减
- **数据**：30s → 28mAh、1min → 18、3min → 12、5min → 10、10min → 9.5、30min → 9
- **结论**：心跳间隔 ≥ 5 分钟，再长边际收益小但失去保活意义；最佳甜区 5-10 分钟
- **扩展**：智能心跳（NAT 探测）可动态调整，进一步节电

**5.2 实验二：定位精度的代价**

**问题**：高精度 GPS、网络定位、被动定位耗电差几倍？

- **假设**：GPS > 网络 > 被动，差 10x 以上
- **数据**：GPS → 35mAh 精度 5m；网络 → 8mAh 精度 50m；被动 → 0.5mAh 精度依赖其他 App
- **结论**：除非业务必须，绝不用 GPS 后台持续定位；优先被动 → 网络 → GPS
- **扩展**：iOS Significant Location Change 是更省电的"位置变化触发"模式

> ▶▶ **回扣 §00.5 案例**：本实验"GPS 35mAh vs 网络 8mAh"是导航 App 38% 耗电源的物理证据。方法派 Day 4 用"传感器融合 + 低频 GPS"省电 50%，正是本实验工程意义的扩展应用。

**5.3 实验三：批量唤醒的收益**

**问题**：100 次小请求逐次发 vs 批量打包一次发，省电多少？

- **假设**：批量省 80% 以上电
- **数据**：逐次 → 56mAh；批量 → 7mAh（8x 差距）
- **结论**：所有非紧急请求必须用 JobScheduler 批量调度；紧急请求合并 1-2 秒窗口
- **扩展**：Doze 模式下系统会强制批量，符合系统期望反而双赢

**5.4 实验四：屏幕亮度 + OLED 暗黑模式的真实功耗**

**问题**：调暗屏幕 / 暗黑模式 / 自动亮度，省电效果如何？

- **数据**：

| 模式 | OLED 屏 1h 耗电 | LCD 屏 1h 耗电 |
|---|---|---|
| 100% 亮度 + 白色背景 | 12% | 13% |
| 50% 亮度 + 白色 | 7% | 8% |
| 100% 亮度 + 暗黑（OLED 像素不亮）| **5%** | 12%（LCD 背光仍全亮）|
| 自动亮度（户外低亮度）| 6% | 7% |

- **结论**：**OLED 设备暗黑模式真省电（-58%）；LCD 设备暗黑模式无效**。
- **扩展**：判断设备屏幕类型后做差异化推荐。

**5.5 实验五：5G vs 4G vs WiFi 的功耗对比**

**问题**：5G 通信芯片功耗高，什么场景下应主动用 4G/WiFi？

- **数据**：

| 网络 | 待机 | 100KB 下载 | 10MB 下载 |
|---|---|---|---|
| WiFi | 5mA | 10mA | 60mA |
| 4G | 15mA | 25mA | 80mA |
| 5G | **25mA** | **40mA** | 90mA |

- **结论**：**小数据用 4G/WiFi 反而省电；5G 仅适合大数据传输**。
- **扩展**：应用应"按需切换"——非视频/下载场景主动用 4G（部分系统 API 支持）。

**5.6 五大实验启示**

```
   心跳间隔        → 5-10 分钟甜区，30s 耗电 3×            ─┐
                                                            │
   定位精度        → GPS vs 网络 4×、vs 被动 70×            │
                                                            │
   批量唤醒        → 100 次 vs 1 次省 88%                   ├─▶ 功耗 = 少 + 批 + 让 + 延 + 轻
                                                            │
   屏幕 + 暗黑     → OLED 暗黑省 58%、LCD 无效              │
                                                            │
   5G 功耗陷阱      → 小数据用 5G 反而费电                   ─┘
```

### 06 优化策略深化

> 本节回答四个递进问题：**①如何减少必要任务？②如何让任务批量？③如何让系统决策时机？④如何选低功耗硬件路径？**

#### 6.1 第一层：少（后台任务必要性审查）

**核心命题**：[§00.5 案例](#005-贯穿案例导航-app用-1-小时手机没电事件) 砍掉 60% 非核心任务是第一大杠杆。

**策略 1.1：后台任务清单审查**

- **代码**：列出所有后台 Service / Job / Worker / BroadcastReceiver，逐条评估必要性。
- **收益**：典型可砍 40-60%。
- **边界**：业务方可能反对，需用功耗数据说服。

**策略 1.2：用 push 替代轮询**

- **代码**：FCM / APNs / 厂商推送替代自建长连接轮询。
- **收益**：心跳消耗清零；推送到达率反而升。
- **边界**：海外用 FCM，国内用厂商推送融合 SDK。

**策略 1.3：WakeLock 强制超时**

- **代码**：

```java
wakeLock.acquire(timeout)  // 必须带 timeout
```

- **收益**：防"持有忘释放"长期持锁。
- **边界**：业务方需理解 timeout 后任务可能被打断。

---

#### 6.2 第二层：批（批量化所有可批量任务）

**核心命题**：[§5.3 实验](#05-求证实验) 批量省 88%。

**策略 2.1：网络请求批量化**

- **代码**：JobScheduler / WorkManager 调度，非紧急请求等待批量窗口。
- **收益**：通信 tail time 大幅下降。
- **边界**：紧急请求要单独通道。

**策略 2.2：定位 + 传感器融合**

- **代码**：

```kotlin
// 直行用低频 GPS（10s/次），转弯/高速时用高频
val locationRequest = LocationRequest.create()
    .setPriority(if (isFastMoving) PRIORITY_HIGH_ACCURACY else PRIORITY_BALANCED_POWER_ACCURACY)
    .setInterval(if (isFastMoving) 2000L else 10000L)
```

- **收益**：[§00.5 案例](#005-贯穿案例导航-app用-1-小时手机没电事件) 定位耗电 -50%。
- **边界**：需用加速度传感器判断"是否在移动"。

**策略 2.3：AlarmManager.setInexactRepeating**

- **代码**：

```kotlin
alarmManager.setInexactRepeating(AlarmManager.RTC, triggerTime, INTERVAL_HOUR, pi)
```

- **收益**：系统可批量唤醒多个 App 的 Alarm，省电。
- **边界**：精确时间任务（如倒计时）仍需 setExact。

---

#### 6.3 第三层：让（让系统决策最佳时机）

**核心命题**：系统知道全局资源状态，让它决策比应用自决策更优。

**策略 3.1：WorkManager + Constraints**

- **代码**：

```kotlin
val work = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(Constraints.Builder()
        .setRequiredNetworkType(NetworkType.UNMETERED)  // 仅 WiFi
        .setRequiresCharging(true)                       // 仅充电
        .build())
    .build()
```

- **收益**：在最经济时段执行任务。
- **边界**：调度延迟可能 10s-小时，实时性差任务不适用。

**策略 3.2：Doze 模式配合**

- **代码**：不要试图绕过 Doze；用 WorkManager 让系统在维护窗口批量执行。
- **收益**：系统级省电的范式。
- **边界**：被发现绕过的应用会被系统降权。

**策略 3.3：iOS BGProcessingTask + requiresExternalPower**

- **代码**：

```swift
let request = BGProcessingTaskRequest(identifier: "sync")
request.requiresExternalPower = true  // 仅充电时
BGTaskScheduler.shared.submit(request)
```

- **收益**：避免后台 fetch 频繁唤醒（[§8.2 案例](#08-案例与教训)）。
- **边界**：iOS 后台 API 越精细，误用代价越大。

---

#### 6.4 第四层：轻（选低功耗硬件路径）

**核心命题**：[§5.2](#52-实验二定位精度的代价) + [§5.4](#54-实验四屏幕亮度--oled-暗黑模式的真实功耗) + [§5.5](#55-实验五5g-vs-4g-vs-wifi-的功耗对比) 证明选硬件路径有 3-10× 差距。

**策略 4.1：定位优先级（被动 > 网络 > GPS）**

- **收益**：[§5.2 实验](#52-实验二定位精度的代价) 4-70× 差距。
- **边界**：业务必须的高精度场景仍需 GPS。

**策略 4.2：暗黑模式（OLED 设备）**

- **代码**：

```kotlin
val isOled = isOledDevice(deviceModel)
if (isOled) suggestDarkMode()  // 仅 OLED 推荐
```

- **收益**：[§5.4 实验](#54-实验四屏幕亮度--oled-暗黑模式的真实功耗) OLED 设备 -58%。
- **边界**：LCD 无效，不要误导用户。

**策略 4.3：网络选择（小数据 4G/WiFi、大数据 5G）**

- **机理**：[§5.5 实验](#55-实验五5g-vs-4g-vs-wifi-的功耗对比)。
- **收益**：日常小请求功耗下降。
- **边界**：网络选择 API 部分系统不支持。

**策略 4.4：低电量模式自适应**

- **代码**：

```kotlin
val powerManager = context.getSystemService(PowerManager::class.java)
if (powerManager.isPowerSaveMode) {
    reduceAnimations()
    disablePrefetch()
    increaseHeartbeatInterval()
}
```

- **收益**：低电量场景体验保护 + 省电。
- **边界**：需业务方对齐降级策略。

### 07 防劣化体系

**7.1 三道防线**

- **第一道·开发期**：Battery Historian / Energy Log 必查
- **第二道·CI**：物理台基线测试，新版功耗 > 基线 10% 阻断
- **第三道·线上**：MetricKit / batterystats 抽样上报

**7.2 SLO 示例**

- 后台每小时耗电 ≤ 0.5%（低端机）
- 唤醒次数 ≤ 6 次/小时
- 后台 CPU 时长占比 ≤ 1%
- WakeLock 累计时长 ≤ 30 秒/小时

### 08 案例与教训

**8.1 跨端同构案例·心跳风暴**

某 App 长连接断线后重连策略是"每 5 秒重试"。一旦遇到弱网长时间不通，连续重试 1 小时，耗电飙升 5x。**修法**：指数退避 5s/10s/30s/1min/5min；上限 5 分钟。**教训**：所有重试都必须有指数退避 + 上限。

**8.2 平台特异案例·iOS Background Fetch 滥用**

某 iOS App 把数据同步全放 Background Fetch，结果系统智能调度后频繁唤醒，电池被吃光。**修法**：核心同步用 push 触发，非核心用 BGProcessingTask 设置 requiresExternalPower = true。**教训**：iOS 的后台 API 越精细，误用代价越大。

### 09 原理深挖

**9.1 Doze 模式的工程意图**

Android 6+ 引入 Doze：屏幕灭、不充电、静止 1 小时后进入 Doze，所有网络/Job/Alarm 暂停，只在维护窗口短暂放行。这强制 App 批量化，是系统级省电的范式。**App 应主动配合**：不要试图绕过 Doze（那只会被系统降权）。

**9.2 OLED 暗黑模式的真省电**

OLED 像素不亮 = 不耗电。纯黑像素比白色省 60% 屏幕功耗。但**LCD 屏暗黑模式不省电**（背光始终全亮）。判断设备屏幕类型再做差异化。

**9.3 5G 的功耗陷阱**

5G 通信芯片功耗比 4G 高 30-50%；非 5G 高速场景下，5G 反而是负担。系统通常自动切换，但应用应该避免长期占用 5G 通道做小数据传输。

### 10 总结与扩展

**10.1 一图概括**

```
功耗优化
    ├─ 屏幕 → OLED 暗黑 + 亮度自动 + 灭屏快
    ├─ CPU → 任务批量 + 让系统调度
    ├─ 通信 → 心跳 5+ 分钟 + 批量打包
    ├─ 定位 → 被动 > 网络 > GPS + 传感器融合
    └─ 监控 → 唤醒次数 + WakeLock 时长
```

**10.2 五条核心原则**

1. **让硬件多睡觉**：CPU 降频、屏幕灭、网卡休眠是终极手段。
2. **批量 > 频繁**：[§5.3](#05-求证实验) 批量省 88%。
3. **被动 > 主动**：[§5.2](#52-实验二定位精度的代价) 定位 GPS vs 被动 70× 差。
4. **让系统决策**：WorkManager + Constraints 是最佳实践。
5. **按硬件适配**：[§5.4](#54-实验四屏幕亮度--oled-暗黑模式的真实功耗) OLED/LCD 差异化。

**10.3 五个常见误区**

1. **"降亮度治耗电"**：错（[§00.5 案例](#005-贯穿案例导航-app用-1-小时手机没电事件) 屏幕不是主战场）。
2. **"心跳越长越省电"**：错（10 分钟后边际为零，失去保活）。
3. **"GPS 精度高就好"**：错（[§5.2](#52-实验二定位精度的代价) 70× 功耗差）。
4. **"5G 永远更好"**：错（[§5.5](#55-实验五5g-vs-4g-vs-wifi-的功耗对比) 小数据反而费电）。
5. **"绕过 Doze 能省"**：错（被系统降权）。

**10.4 三个外延**

- **碳排追踪**：手机功耗最终对应碳排放，是 ESG 的端侧指标
- **设备老化**：电池循环 500+ 次后容量衰减，App 应自适应低电量行为
- **AI 调度**：未来 OS 可能用 ML 预测 App 唤醒时机，进一步省电

**10.5 给团队的建议**

- 第 1 周：审计所有后台任务，无必要的全部砍掉
- 第 2 周：心跳间隔统一调到 5 分钟以上
- 第 3 周：定位精度全面降级（除非业务必须）
- 第 4 周：上线 batterystats 抽样，建电量大盘

---

## 一句话总结

> **功耗是"看不见的承诺"——用户不会因为电池长 1 小时来夸你，但一定会因为电池短 1 小时骂你。  
> 让硬件多睡觉 = 少 + 批 + 让 + 轻四字诀；定位 + 通信 + 屏幕是三大主战场。  
> §00.5 那个"3 周经验派 28% 耗电 vs 5 天方法派 11% 耗电"的反差，正是这条路径的最锋利证据。**
