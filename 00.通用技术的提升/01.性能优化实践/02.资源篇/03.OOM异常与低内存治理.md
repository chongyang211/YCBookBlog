## 01.常见OOM分类说明
### 1.1 OOM简单分类
- Java堆内存超限
    - 堆内存单次分配过大。例如一次性加载超大图片或超大文件到内存
    - 多次分配累计过大【StringBuilder，Array等】。例如循环拼接超长字符串
    - 堆内存积累分配触顶。这是最常见的场景，内存泄漏导致可用内存逐渐减少
- 文件描述符（fd）数目超限
    - Linux对每个进程的FD数量有上限（默认1024），超过后任何需要FD的操作都会失败
    - 常见的FD消耗：文件操作、Socket连接、数据库Cursor、管道通信等
    - FD泄漏通常是由于资源打开后未正确关闭导致
- pthread_create
    - 线程数超限。Linux对每个进程可创建的线程数有限制（/proc/sys/kernel/threads-max）
    - 虚拟内存空间不足。每个线程需要分配栈内存（默认约1MB），大量线程消耗虚拟地址空间
    - 在32位系统上这个问题更加突出，因为虚拟地址空间只有约4GB



### 1.2 OOM各种占比
- pthread_create 问题占到了总比例大约在百分之 50，Java 堆内存超限为百分之 40 多，剩下是少量的 fd 数量超限。其中 pthread_create 和 fd 数量不足均为 native 内存限制导致的 Java 层崩溃，对这部分的内存问题也做了针对性优化，主要包括：
    - 线程收敛、监控
    - 线程栈泄漏自动修复
    - FD 泄漏监控
    - 虚拟内存监控、优化
- 虚拟机抛出异常
    - Android 虚拟机最终抛出OutOfMemoryError的代码位于/art/runtime/thread.cc



### 1.3 OOM泄漏场景
- OOM错误可以分为以下几种类型：
    - Java堆内存溢出（Java Heap Space）：这是最常见的OOM错误类型。当应用程序在Java堆中分配的对象超过了堆的容量限制时，就会发生堆内存溢出。这通常是由于内存泄漏、大对象的创建或者堆设置不合理导致的。
    - Native堆内存溢出（Native Heap Space）：除了Java堆，Android应用还可以使用Native堆来分配内存，例如通过JNI调用C/C++代码。如果Native堆中分配的内存超过了堆的容量限制，就会发生Native堆内存溢出。
    - 图片内存溢出（Bitmap Out of Memory）：在Android中，加载大型图片时容易发生内存溢出。由于图片占用的内存较大，如果同时加载多张大图或者没有正确释放图片资源，就会导致图片内存溢出。
    - 视图层级过深（View Hierarchy）：Android应用中的视图层级（View Hierarchy）是由多个嵌套的视图组成的。如果视图层级过深，即嵌套层级过多，会导致内存消耗过大，从而引发OOM错误。
    - 内存泄漏（Memory Leaks）：内存泄漏是指应用程序中的对象在不再使用时没有被正确释放，导致内存占用不断增加。如果内存泄漏问题严重，最终会导致内存耗尽，引发OOM错误。
- 说一下在实际开发中避免内存泄漏的场景:
    - 资源型对象未关闭: Cursor,File
    - 注册对象未销毁: 广播，回调监听
    - 类的静态变量持有大数据对象
    - 非静态内部类的静态实例
    - Handler 临时性内存泄漏: 使用静态 + 弱引用，退出即销毁
    - 容器中的对象没清理造成的内存泄漏
    - WebView: 使用单独进程



### 1.4 如何避免OOM
- 可以从如下几个方面去展开说明:
    - AutoBoxing(自动装箱): 能用小的坚决不用大的。
    - 内存复用，适用对象池
    - 使用最优的数据类型
    - 枚举类型: 使用注解枚举限制替换 Enum
    - 图片内存优化（这里可以从 Glide 等开源框架去说下它们是怎么设计的）
    - 选择合适的位图格式bitmap 内存复用，压缩图片的多级缓存
    - 基本数据类型如果不用修改的建议全部写成 static final,因为 它不需要进行初始化工作，直接打包到 dex 就可以直接使用，并不会在 类 中进行申请内存
    - 字符串拼接别用 +=，使用 StringBuffer 或 StringBuilder
    - 不要在 onMeuse, onLayout, onDraw 中去刷新 UI




## 02.OOM治理思路
### 2.1 堆内存治理思路
- 从 Java 堆内存超限的分类来看，主要有两类问题：
- 1.堆内存单次分配过大多次分配累计过大。
    - 触发这类问题的原因有数据异常导致单次内存分配过大超限，也有一些是 StringBuilder 拼接累计大小过大导致等等。这类问题的解决思路比较简单，问题就在当前的堆栈。
- 2.堆内存累积分配触顶。
    - 这类问题的问题堆栈会比较分散，在任何内存分配的场景上都有可能会被触发，那些高频的内存分配节点发生的概率会更高，比如 Bitmap 分配内存。
    - 这类 OOM 的根本原因是内存累积占用过多，而当前的堆栈只是压死骆驼的最后一根稻草，并不是问题的根本所在。所以这类问题我们需要分析整体的内存分配情况，从中找到不合理的内存使用（比如内存泄露、大对象、过多小对象、大图等）。


### 2.2 FD超限治理思路
- 文件描述符（File Descriptor）超限是导致OOM的隐性原因之一
    - Linux系统对每个进程的FD数量有上限限制，通常为1024（可通过ulimit查看）
    - Android应用中常见的FD泄漏场景：未关闭的文件流、数据库连接、Socket连接、Cursor等
    - FD泄漏的表现不像内存泄漏那样直观，往往在FD耗尽时才以OOM或各种异常形式暴露
- FD超限的治理步骤
    - 第一步：监控FD数量。定期读取 /proc/self/fd 目录下的文件数量，统计FD使用情况
    - 第二步：分析FD类型。对泄漏的FD进行分类（socket、pipe、file、anon_inode等），定位泄漏源
    - 第三步：修复泄漏。确保所有资源在使用完毕后正确关闭，推荐使用try-with-resources

```java
// FD数量监控
public class FDMonitor {
    public static int getFDCount() {
        File fdDir = new File("/proc/self/fd");
        File[] files = fdDir.listFiles();
        return files != null ? files.length : 0;
    }
    
    public static Map<String, Integer> getFDDistribution() {
        Map<String, Integer> distribution = new HashMap<>();
        File fdDir = new File("/proc/self/fd");
        File[] files = fdDir.listFiles();
        if (files == null) return distribution;
        
        for (File file : files) {
            try {
                String link = Os.readlink(file.getAbsolutePath());
                String type = classifyFD(link);
                distribution.merge(type, 1, Integer::sum);
            } catch (Exception ignored) {}
        }
        return distribution;
    }
    
    private static String classifyFD(String link) {
        if (link.startsWith("socket:")) return "socket";
        if (link.startsWith("pipe:")) return "pipe";
        if (link.startsWith("/dev/")) return "device";
        if (link.contains(".db")) return "database";
        return "file";
    }
}
```


### 2.3 线程OOM治理思路
- 线程创建失败导致的OOM是另一个常见场景
    - 每个线程创建都需要分配栈内存（默认1MB左右），大量线程创建会快速消耗虚拟内存空间
    - 在32位系统上虚拟内存空间有限（约4GB，用户空间约3GB），更容易触发线程OOM
    - 常见的线程泄漏场景：未正确关闭的线程池、频繁创建临时线程、定时器泄漏等
- 线程OOM的治理策略
    - 线程收敛：统一使用全局线程池，禁止随意创建独立线程
    - 线程监控：定期统计应用的线程数量，超过阈值告警
    - 线程栈优化：适当减小线程栈大小（如从1MB降到512KB或256KB）
    - 线程命名：强制所有线程命名，便于排查泄漏

```java
// 线程监控和收敛
public class ThreadMonitor {
    private static final int THREAD_WARNING_THRESHOLD = 200;
    
    public static int getThreadCount() {
        File taskDir = new File("/proc/self/task");
        File[] tasks = taskDir.listFiles();
        return tasks != null ? tasks.length : 0;
    }
    
    public static void checkThreadCount() {
        int count = getThreadCount();
        if (count > THREAD_WARNING_THRESHOLD) {
            // 上报告警
            reportThreadWarning(count, dumpThreadInfo());
        }
    }
    
    public static List<String> dumpThreadInfo() {
        List<String> threadInfos = new ArrayList<>();
        Map<Thread, StackTraceElement[]> allThreads = Thread.getAllStackTraces();
        for (Map.Entry<Thread, StackTraceElement[]> entry : allThreads.entrySet()) {
            Thread thread = entry.getKey();
            threadInfos.add(String.format("%s [%s] - %s",
                thread.getName(), thread.getState(),
                entry.getValue().length > 0 ? entry.getValue()[0] : ""));
        }
        return threadInfos;
    }
}
```


## 03.使用那些分析工具
### 3.1 分析工具介绍
- 在研发和测试的时候能够提前发现内存泄漏问题。
    - 业界的主流工具也是这个思路，比如 Android Studio Memory Profiler、LeakCanary、Memory Analyzer (MAT)。
- Android Studio Memory Profiler
    - 优势：与IDE深度集成，可以实时查看内存分配和回收情况，支持HPROF导出和分析
    - 功能：实时内存曲线、内存分配追踪、HPROF分析、GC触发、内存分类统计（Java/Native/Graphics/Stack/Code/Others）
    - 适用场景：开发阶段的内存问题定位和验证
- LeakCanary
    - 优势：集成简单（只需添加依赖即可），自动检测Activity/Fragment泄漏，自动分析泄漏链
    - 原理：监听Activity/Fragment的onDestroy，通过WeakReference+ReferenceQueue判断对象是否被回收
    - 适用场景：开发和测试阶段的自动化内存泄漏检测
- Memory Analyzer (MAT)
    - 优势：功能最强大的HPROF分析工具，支持OQL查询、支配树分析、泄漏怀疑报告
    - 核心功能：Retained Size计算、GC Root路径分析、对象直方图、线程分析
    - 适用场景：深入分析复杂的内存问题，线上HPROF文件的离线分析
- 其他工具
    - StrictMode：检测Activity实例泄漏（Android 11+）
    - dumpsys meminfo：查看应用内存占用详情
    - Allocation Tracker：跟踪对象分配的堆栈（适合分析短时间内的大量分配）


### 3.2 工具优势和弊端
- 检测出来的内存泄漏过多，并且也没有比较好的优先级排序，研发消费不过来，历史问题就一直堆积。另外也很难和业务研发沟通问题解决的收益，大家针对解决线下的内存泄漏问题的 ROI（投入产出比）比较难对齐。
- 线下场景能跑到的场景有限，很难把所有用户场景穷尽。经常遇到一些线上的OOM激增问题，因为缺少线上数据而无从查起。
- Android 端的 HPORF 的获取依赖原生的 Debug.dumpHporf，dump 过程会挂起主线程导致明显卡顿，线下使用体验较差，经常会有研发反馈影响测试。
- LeakCanary 基于 Shark 分析引擎分析，分析速度较慢，通常在 5 分钟以上才能分析完成，分析过程会影响进程内存占用。
- 分析结果较为单一，仅仅只能分析出 Fragment、Activity 内存泄露，像大对象、过多小对象问题导致的内存 OOM 无法分析。


### 3.3 线上内存分析方案
- 线下工具无法覆盖线上所有场景，需要建立线上内存分析能力
    - 传统方案（Debug.dumpHporf）的问题：dump HPROF会挂起所有Java线程，导致明显卡顿甚至ANR，不适合线上使用
    - 优化方案：在子线程中进行dump操作，通过Copy-on-Write机制（fork子进程）避免阻塞主线程
    - HPROF裁剪：线上的HPROF文件需要裁剪（去除bitmap像素数据等），将文件大小从几百MB降低到几十MB，便于上传
- 线上内存分析的触发时机
    - 被动触发：OOM发生时自动采集（但此时内存已经极度紧张，采集可能失败）
    - 主动触发：当内存使用率超过阈值（如80%的maxMemory）时主动采集
    - 采样触发：对一定比例的用户定期采样分析，发现潜在的内存问题
- 线上采集的数据分析流程
    - HPROF文件上传到服务端
    - 使用Shark/MAT等工具自动分析
    - 生成泄漏链路报告和大对象列表
    - 按影响面和严重程度排序
    - 派发给对应业务方处理



## 04.常见OOM出现场景
### 4.1 堆内存分配失败
- 系统源码文件：/art/runtime/gc/heap.cc
    ```
    void Heap::ThrowOutOfMemoryError(Thread* self, size_t byte_count, AllocatorType allocator_type)
    抛出时的错误信息：
        oss << "Failed to allocate a " << byte_count << " byte allocation with " << total_bytes_free  << " free bytes and " << PrettySize(GetFreeMemoryUntilOOME()) << " until OOM";
    ```
- 这是在进行堆内存分配时抛出的OOM错误，这里也可以细分成两种不同的类型：
    - 为对象分配内存时达到进程的内存上限。由Runtime.getRuntime.MaxMemory()可以得到Android中每个进程被系统分配的内存上限，当进程占用内存达到这个上限时就会发生OOM，这也是Android中最常见的OOM类型。
    - 没有足够大小的连续地址空间。这种情况一般是进程中存在大量的内存碎片导致的，其堆栈信息会比第一种OOM堆栈多出一段信息：failed due to fragmentation (required continguous free "<< required_bytes << " bytes for a new buffer where largest contiguous free " <<  largest_continuous_free_pages << " bytes)"; 其详细代码在art/runtime/gc/allocator/rosalloc.cc中，这里不作详述。



### 4.2 创建线程失败
- 系统源码文件：/art/runtime/thread.cc
    ```
    void Thread::CreateNativeThread(JNIEnv* env, jobject java_peer, size_t stack_size, bool is_daemon)
        抛出时的错误信息：
            "Could not allocate JNI Env"
          或者
            StringPrintf("pthread_create (%s stack) failed: %s", PrettySize(stack_size).c_str(), strerror(pthread_create_result)));
    ```
- 这是创建线程时抛出的OOM错误，且有多种错误信息。源码这里不展开详述了，下面是根据源码整理的Android中创建线程的步骤，其中两个关键节点是创建JNIEnv结构体和创建线程，而这两步均有可能抛出OOM。
    - ![image](https://img-blog.csdnimg.cn/20210129171220785.png)
- 创建线程也可以归纳为两个步骤：
    - 调用mmap分配栈内存。这里mmap flag中指定了MAP_ANONYMOUS，即匿名内存映射。这是在Linux中分配大块内存的常用方式。其分配的是虚拟内存，对应页的物理内存并不会立即分配，而是在用到的时候触发内核的缺页中断，然后中断处理函数再分配物理内存
    - 调用clone方法进行线程创建。
- 第一步分配栈内存失败是由于进程的虚拟内存不足，抛出错误信息如下：
    ```
    W/libc: pthread_create failed: couldn't allocate 1073152-bytes mapped space: Out of memory
    W/tch.crowdsourc: Throwing OutOfMemoryError with VmSize  4191668 kB "pthread_create (1040KB stack) failed: Try again"
    java.lang.OutOfMemoryError: pthread_create (1040KB stack) failed: Try again
            at java.lang.Thread.nativeCreate(Native Method)
            at java.lang.Thread.start(Thread.java:753)
    ```
- 第二步clone方法失败是因为线程数超出了限制，抛出错误信息如下：
    ```
    W/libc: pthread_create failed: clone failed: Out of memory
    W/art: Throwing OutOfMemoryError "pthread_create (1040KB stack) failed: Out of memory"
    java.lang.OutOfMemoryError: pthread_create (1040KB stack) failed: Out of memory
      at java.lang.Thread.nativeCreate(Native Method)
      at java.lang.Thread.start(Thread.java:1078)
    ```


### 4.3 FD数量超限
- FD（File Descriptor）数量超限是第三类常见的OOM场景
    - Android进程默认的FD上限通常为1024，当应用打开的文件描述符超过此限制时就会触发异常
    - FD超限的错误信息通常为：java.lang.RuntimeException: Could not read input channel file descriptors from parcel
    - 或者：android.os.ParcelFileDescriptor: Too many open files
- FD超限的排查方法
    - 通过adb命令查看当前FD数量：`adb shell ls -la /proc/<pid>/fd | wc -l`
    - 通过adb查看FD上限：`adb shell cat /proc/<pid>/limits | grep "Max open files"`
    - 在代码中周期性读取/proc/self/fd进行监控
- 常见FD泄漏修复方案
    - 使用try-with-resources确保流资源被关闭
    - 确保Cursor在使用后及时close

## 05.OOM如何监听
### 5.1 OOM如何监听设计
- OOM监听的核心目标是在OOM发生前后采集足够的信息用于定位问题
    - 设置UncaughtExceptionHandler捕获OOM异常
    - 在OOM回调中采集内存快照、线程信息、FD信息等
    - 注意OOM发生时内存已经紧张，采集操作要尽量轻量
- OOM监听的实现思路

```java
// OOM监听基础框架
public class OOMMonitor {
    
    public static void init() {
        Thread.UncaughtExceptionHandler defaultHandler =
            Thread.getDefaultUncaughtExceptionHandler();
            
        Thread.setDefaultUncaughtExceptionHandler((thread, throwable) -> {
            if (throwable instanceof OutOfMemoryError) {
                handleOOM(throwable);
            }
            if (defaultHandler != null) {
                defaultHandler.uncaughtException(thread, throwable);
            }
        });
    }
    
    private static void handleOOM(Throwable oom) {
        // 采集关键信息（此时内存紧张，操作要轻量）
        String memoryInfo = collectMemoryInfo();
        String threadInfo = collectThreadInfo();
        int fdCount = collectFDCount();
        
        // 写入本地文件，下次启动时上报
        saveOOMReport(memoryInfo, threadInfo, fdCount, oom);
    }
    
    private static String collectMemoryInfo() {
        Runtime runtime = Runtime.getRuntime();
        long maxMemory = runtime.maxMemory();
        long totalMemory = runtime.totalMemory();
        long freeMemory = runtime.freeMemory();
        long usedMemory = totalMemory - freeMemory;
        
        return String.format("max=%dMB, total=%dMB, used=%dMB, free=%dMB",
            maxMemory / 1024 / 1024,
            totalMemory / 1024 / 1024,
            usedMemory / 1024 / 1024,
            freeMemory / 1024 / 1024);
    }
}
```

### 5.2 OOM需要收集什么
- OOM发生时需要采集的关键信息
    - 内存信息：Java堆内存使用量、Native内存使用量、系统可用内存
    - 线程信息：当前线程数量、各线程名称和状态
    - FD信息：当前FD数量、FD分布情况
    - 堆栈信息：OOM发生时的调用堆栈
    - 设备信息：设备型号、系统版本、可用存储空间
    - 业务信息：当前页面、用户操作路径
- 理想情况下还需要采集HPROF文件
    - HPROF文件包含了完整的Java堆内存快照，是分析内存问题的最有力工具
    - 但在OOM发生时dump HPROF可能因为内存不足而失败
    - 更好的策略是在内存水位接近上限时提前dump


### 5.3 内存水位监控
- 内存水位监控是OOM预防的核心手段
    - 不等到OOM发生才采集数据，而是在内存使用率达到一定阈值时就开始监控和采集
    - 通过定期采样内存使用率，建立内存变化趋势曲线
    - 当内存持续上涨并突破阈值时触发预警和数据采集
- 内存水位等级设计

| 水位等级 | 内存使用率 | 响应策略 |
|---------|-----------|---------|
| 安全 | < 60% | 正常运行，不做特殊处理 |
| 关注 | 60%-75% | 开始记录内存分配热点 |
| 警告 | 75%-85% | 主动释放非必要缓存（图片缓存、页面缓存） |
| 危险 | 85%-95% | dump HPROF、上报告警、降级非核心功能 |
| 临界 | > 95% | 清理所有可清理的内存、准备OOM采集 |

### 6.2 针对小对象优化
- 如何小对象优化
    - 小对象优化我们集中在字段优化、业务优化、缓存优化三个纬度，不同的纬度有不同的优化策略。
- 通用类优化
    - 在业务中，视频是最核心且通用的 Model，抖音业务层的数据存储分散在各个业务维护了各自视频的 Model，Model 本身由于聚合了各个业务需要的属性很多导致单个实例内存占用就不低，随着用户使用过程实例增长内存占用越来越大。对 Model 本身我们可以从属性优化和拆分这两种思路来优化。
    - 字段优化：针对一次性的属性字段，在使用完之后即使清理掉缓存，比如在视频 Model 内部存在一个 Json 对象，在反序列完成之后 Json 对象就没有使用价值了，可以及时清理。
    - 类拆分：针对通用 Model 冗杂过多的业务属性，尝试对 Model 本身进行治理，将各个业务线需要用到的属性进行梳理，将 Model 拆分成多个业务 Model 和一个通用 Model，采用组合的方式让各个业务线最小化依赖自己的业务 Model，减少大杂烩 Model 不必要的内存浪费。
- 业务优化
    - 内存缓存限制或清理：首页推荐列表的每一次 Loadmore 操作，都不会清理之前缓存起来的视频对象，导致用户长时间停留在推荐 Feed 时，缓存起来的视频对象过多会导致内存方面的压力。在通过实验验证不会对业务产生负面影响情况下对首页的缓存进行了一定数量的限制来减小内存压力。
- 缓存优化
    - 使用 Manager 来管理通用的视频实例。Manager 使用 HashMap 存储了所有的视频对象，最初的方案里面没有对内存大小进行限制且没有清除逻辑，随着使用时间的增加而不断膨胀，最终出现 OOM 异常。
    - ![image](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/7aa778a2fded4816914a8f93d57366d3~tplv-k3u1fbpfcp-watermark.image)
    - 使用 LRU 缓存机制来缓存视频对象。在内存中缓存最近使用的 100 个视频对象，当视频对象从内存缓存中移除时，将其缓存至磁盘中。在获取视频对象时，首先从内存中获取，若内存中没有缓存该对象，则从磁盘缓存中获取。在退出 App 时，清除 Manager 的磁盘缓存，避免磁盘空间占用不断增长。
- 减小对象的内存占用
    - `使用更加轻量级的数据结构`：
        - 例如，我们可以考虑使用`ArrayMap`/`SparseArray`而不是`HashMap`等传统数据结构，相比起Android系统专门为移动操作系统编写的`ArrayMap`容器，在大多数情况下，`HashMap`都显示效率低下，更占内存。另外，`SparseArray`更加高效在于，**避免了对key与value的自动装箱，并且避免了装箱后的解箱**。这个使用场景，比如封装viewholder时，使用SparseArray存储id，详细可以参考我的封装库：https://github.com/yangchong211/YCBaseAdapter
    - `避免使用Enum`：
        - 在Android中应该尽量使用`int`来代替`Enum`，因为使用`Enum`会导致编译后的dex文件大小增大，并且使用`Enum`时，其运行时还会产生额外的内存占用。

    - `inBitmap`：如果设置了这个字段，Bitmap在加载数据时可以复用这个字段所指向的bitmap的内存空间。**但是，内存能够复用也是有条件的。比如，在`Android 4.4(API level 19)`之前，只有新旧两个Bitmap的尺寸一样才能复用内存空间。`Android 4.4`开始只要旧 Bitmap 的尺寸大于等于新的 Bitmap 就可以复用了**。

### 6.5 手机低内存优化
- 综合考虑设备内存阈值与其他因素设计合适的缓存大小
- `onLowMemory()`：
    - Android系统提供了一些回调来通知当前应用的内存使用情况，通常来说，当所有的background应用都被kill掉的时候，forground应用会收到onLowMemory()的回调。在这种情况下，需要尽快释放当前应用的非必须的内存资源，从而确保系统能够继续稳定运行。
- `onTrimMemory()`：
    - Android系统从4.0开始还提供了onTrimMemory()的回调，当系统内存达到某些条件的时候，所有正在运行的应用都会收到这个回调，同时在这个回调里面会传递以下的参数，代表不同的内存使用情况，收到onTrimMemory()回调的时候，需要根据传递的参数类型进行判断，合理的选择释放自身的一些内存占用，一方面可以提高系统的整体运行流畅度，另外也可以避免自己被系统判断为优先需要杀掉的应用
    - TRIM_MEMORY_UI_HIDDEN：应用进入后台，可以释放UI相关的资源
    - TRIM_MEMORY_RUNNING_MODERATE：设备内存偏低，应用正在运行
    - TRIM_MEMORY_RUNNING_LOW：设备内存不足，应该释放不需要的资源
    - TRIM_MEMORY_RUNNING_CRITICAL：设备内存极低，尽量释放所有非必要资源
    - TRIM_MEMORY_BACKGROUND：应用进入后台且在LRU列表中，释放容易恢复的资源
    - TRIM_MEMORY_MODERATE：应用在LRU列表中间位置，有被回收的风险
    - TRIM_MEMORY_COMPLETE：应用在LRU列表尾部，即将被回收，释放所有可释放的资源
- 资源文件需要选择合适的文件夹进行存放：
    - 例如我们只在`hdpi`的目录下放置了一张100100的图片，那么根据换算关系，`xxhdpi`的手机去引用那张图片就会被拉伸到200200。需要注意到在这种情况下，内存占用是会显著提高的。**对于不希望被拉伸的图片，需要放到assets或者nodpi的目录下**。
- 其他建议
    - 谨慎使用static对象
    - 优化布局层次，减少内存消耗
    - 使用FlatBuffer等工具序列化数据
    - 谨慎使用依赖注入框架
    - 使用ProGuard来剔除不需要的代码


### 6.11 OOM可以被try…catch吗
- 正确认识Error和OOM
    - 这里 catch 的是一个 Error，原则上，触发了Error时，它的执行状态已经无法恢复了，此时需要终止线程甚至是终止虚拟机。这是一种不应该被我们应用层去捕获的异常。
- catch OOM 的先决条件
    - 想通过 try-catch 避免 OOM，你需要两个先决条件：
        - 触发 OOM 的代码是开发者可控的。
        - 在 try 块中，申明对象并会申请了大段内存，导致触发 OOM。
    - 只有满足这两个条件，你才可以说，你对 OOM 有控制权，能够将其 catch 住。但是这通常不是合适的做法。
- 是否建议catch住OOM
    - 不应该去主动 catch OOM。哪怕在此处catch住了，可App当前的状态也已经处于“濒危”状态。如果不采取措施，此时不崩，换一个地方也会崩。
- 总结一下
    - OOM 能不能被 catch 住？在某些条件下可以。仅在我们可控的代码，并且在 try 块中存在申请大量内存的情况下，此时触发的 OOM，才是可以被 catch 住的。
    - 当我们 catch 住 OOM 的时候，我们应该主动释放一些我们可控的内存，做好内存管理，避免在后续的操作中，立即又会触发 OOM，导致崩溃。



## 07.OOM治理进阶实践
### 7.1 内存泄漏检测原理
- 内存泄漏的本质是对象已经不再被使用，但仍然被GC Root可达的引用链持有，导致GC无法回收
    - 典型的GC Root包括：静态变量、活跃线程、JNI引用、系统Class等
    - 内存泄漏检测的核心原理是判断特定对象（如Activity、Fragment）在其生命周期结束后是否被正确回收
- LeakCanary的检测原理
    - 监听Activity的onDestroy回调（通过Application.ActivityLifecycleCallbacks）
    - 将销毁的Activity用WeakReference包装，同时关联一个ReferenceQueue
    - 等待5秒后检查ReferenceQueue中是否收到该WeakReference
    - 如果未收到，说明Activity未被回收，主动触发GC后再次检查
    - 如果仍未被回收，则认为发生了内存泄漏，dump HPROF进行泄漏链分析

```java
// 内存泄漏检测核心原理示意
public class LeakDetector {
    private final Map<String, WeakReference<Object>> watchedObjects = new HashMap<>();
    private final ReferenceQueue<Object> referenceQueue = new ReferenceQueue<>();
    
    public void watch(Object object, String description) {
        String key = UUID.randomUUID().toString();
        WeakReference<Object> ref = new WeakReference<>(object, referenceQueue);
        watchedObjects.put(key, ref);
        
        // 延迟5秒检查
        handler.postDelayed(() -> checkRetained(key), 5000);
    }
    
    private void checkRetained(String key) {
        // 清理已回收的引用
        removeWeaklyReachableObjects();
        
        if (watchedObjects.containsKey(key)) {
            // 主动触发GC
            Runtime.getRuntime().gc();
            
            // 再次清理
            removeWeaklyReachableObjects();
            
            if (watchedObjects.containsKey(key)) {
                // 确认泄漏，分析泄漏链
                analyzeLeakChain(key);
            }
        }
    }
    
    private void removeWeaklyReachableObjects() {
        Reference<?> ref;
        while ((ref = referenceQueue.poll()) != null) {
            watchedObjects.values().remove(ref);
        }
    }
}
```


### 7.2 大对象监控方案
- 大对象是导致OOM的重要因素，需要建立有效的监控手段
    - 运行时监控：通过字节码插桩Hook对象分配，对超过指定阈值的分配进行记录
    - HPROF分析：定期或触发式dump HPROF，分析Retained Size排名靠前的对象
    - Bitmap监控：Hook Bitmap.createBitmap等方法，监控大图分配
- 大对象的判定标准
    - 单个对象占用内存超过1MB可视为大对象
    - 对于Bitmap，宽高超过View尺寸2倍以上可视为不合理的大图
    - 对于集合类，元素数量超过10000或内存占用超过5MB需要关注
- 大对象治理策略
    - Bitmap降采样：根据ImageView的实际尺寸对图片进行降采样加载
    - 对象池复用：对频繁创建的大对象使用对象池机制
    - 及时释放：在页面销毁或不可见时及时释放大对象引用
    - 延迟加载：非必要的大对象延迟到真正需要时才创建


### 7.3 Native内存治理
- Native内存不受Java堆大小限制，但同样会导致OOM
    - Native内存泄漏不会被LeakCanary等Java层工具检测到
    - Native内存的申请和释放由开发者手动管理（malloc/free），容易出错
    - Android中常见的Native内存消耗大户：Bitmap（Android 8.0+）、WebView、音视频编解码、OpenGL
- Native内存监控手段
    - /proc/self/status中的VmRSS字段反映实际物理内存占用
    - malloc_debug和Address Sanitizer用于检测Native内存错误
    - 通过PLT Hook拦截malloc/free调用，统计Native内存分配
- Native内存治理方案
    - 图片：Android 8.0以后Bitmap像素数据存储在Native堆，需要关注Native内存水位
    - WebView：WebView的内存占用不可控且较大，建议使用独立进程加载
    - JNI：确保JNI层分配的内存在不使用时及时释放
    - 第三方库：关注使用了Native实现的第三方库的内存行为


### 7.4 线程泄漏治理
- 线程泄漏是一种特殊的资源泄漏，最终会导致线程创建失败的OOM
    - 每个线程默认占用约1MB的栈内存，100个泄漏的线程就会额外消耗约100MB虚拟内存
    - 在32位系统上虚拟地址空间有限，线程泄漏更容易触发OOM
- 常见的线程泄漏场景
    - 未关闭的HandlerThread：创建了HandlerThread但在组件销毁时未调用quit()或quitSafely()
    - 无限循环的子线程：while(true)的工作线程在组件销毁后仍在运行
    - Timer/TimerTask泄漏：Timer未调用cancel()导致后台线程持续运行
    - ExecutorService未shutdown：线程池的核心线程不会自动销毁
    - AsyncTask泄漏：持有Activity引用的AsyncTask在后台运行
- 线程收敛策略
    - 统一线程池：全局共享线程池，禁止业务方自行创建线程
    - 线程命名规范：所有线程必须有业务标识的名称，便于排查
    - 生命周期绑定：线程的生命周期与组件（Activity/Fragment）绑定，组件销毁时自动取消任务
    - 线程数监控：定期统计线程数，超过阈值告警并上报线程列表


## 08.OOM优化设计总结

### 8.1 OOM治理核心原则

**原则一：分类治理**

OOM不是单一问题，需要按类型（堆内存、线程、FD）分别治理。不同类型的OOM有不同的根因和解决方案，统一方案无法覆盖所有场景。

**原则二：预防优于治理**

建立内存水位监控，在OOM发生前就发现并解决问题。线上的HPROF采集能力是发现问题的关键，但更重要的是在开发和测试阶段通过工具（LeakCanary、StrictMode等）提前发现内存问题。

**原则三：全链路监控**

从开发（线下检测）→ 测试（内存基线）→ 灰度（内存指标观测）→ 全量（线上监控告警）建立完整的内存治理链路。

**原则四：持续治理**

内存治理不是一次性工作。每次版本迭代都可能引入新的内存问题，需要通过自动化工具（CI集成内存检测、线上持续监控）来保证治理效果的可持续性。

### 8.2 跨平台OOM对比

**疑惑**：不同平台面临的内存问题有什么差异？

**答疑**：各平台由于内存管理模型不同，OOM的表现和治理方式存在差异。

**论证**：

| 维度 | Android | iOS | Web |
|------|---------|-----|-----|
| 内存管理 | Java GC + Native手动管理 | ARC自动引用计数 | JS GC自动管理 |
| OOM表现 | 抛出OutOfMemoryError | 被系统Jetsam机制kill | 页面卡死/标签页crash |
| 内存上限 | 堆大小受限(256-512MB) | 无明确上限但受系统管控 | 受浏览器限制(通常1-4GB) |
| 常见原因 | Bitmap/泄漏/线程 | 图片/循环引用/大数据 | DOM过多/闭包泄漏 |
| 检测工具 | LeakCanary/MAT/Profiler | Instruments/Allocations | Chrome DevTools/Heap Snapshot |
| 热点问题 | Native内存/FD泄漏 | 循环引用/Autorelease Pool | 闭包/事件监听器泄漏 |

**iOS内存治理示例**：

```swift
// iOS使用Instruments检测内存泄漏
// 循环引用检测和处理
class ViewController: UIViewController {
    var completionHandler: (() -> Void)?
    
    func setupHandler() {
        // 错误：循环引用 - self持有closure，closure持有self
        // completionHandler = { self.doSomething() }
        
        // 正确：使用weak self打破循环引用
        completionHandler = { [weak self] in
            guard let self = self else { return }
            self.doSomething()
        }
    }
    
    // 大图处理 - 使用autoreleasepool控制内存峰值
    func processLargeImages(_ urls: [URL]) {
        for url in urls {
            autoreleasepool {
                guard let data = try? Data(contentsOf: url),
                      let image = UIImage(data: data) else { return }
                processImage(image)
                // 出了autoreleasepool，image会被释放
            }
        }
    }
}
```

**Web内存治理示例**：

```javascript
// Web端内存泄漏的典型场景和修复
// 场景1：事件监听器泄漏
class Component {
    constructor() {
        this.handler = this.onResize.bind(this);
        window.addEventListener('resize', this.handler);
    }
    
    // 必须在组件销毁时移除监听器
    destroy() {
        window.removeEventListener('resize', this.handler);
    }
}

// 场景2：使用WeakRef避免内存泄漏（ES2021）
class Cache {
    constructor() {
        this.cache = new Map();
    }
    
    set(key, value) {
        this.cache.set(key, new WeakRef(value));
    }
    
    get(key) {
        const ref = this.cache.get(key);
        if (ref) {
            const value = ref.deref();
            if (value) return value;
            this.cache.delete(key);  // 清理已被GC的条目
        }
        return undefined;
    }
}
```

**结果**：各平台的内存管理模型不同，但治理思路相通：监控→发现→分析→修复→验证。关键是建立适合各平台特性的监控和检测能力。

### 8.3 OOM治理方法论

OOM治理遵循"监控-分析-治理-验证"四阶段方法论：

**第一阶段：建立监控体系**
1. 线上OOM率统计和分类
2. 内存水位监控和预警
3. 线程/FD数量监控
4. 线上HPROF自动采集能力

**第二阶段：问题分析归因**
1. HPROF分析：泄漏链路、大对象、对象统计
2. OOM堆栈聚合和分类
3. 与版本、设备、场景的关联分析
4. 按影响面和严重程度排优先级

**第三阶段：专项治理**
1. 内存泄漏修复：按泄漏链逐一修复
2. 大对象优化：降采样、延迟加载、缓存管理
3. 线程收敛：统一线程池、生命周期绑定
4. FD治理：资源关闭规范、泄漏检测
5. Native内存：独立进程隔离、内存限制

**第四阶段：效果验证和持续保障**
1. OOM率指标回归对比
2. 内存基线建立和版本对比
3. CI集成内存检测
4. 持续监控和告警

### 8.4 OOM治理常见误区

**疑惑**：OOM治理中有哪些常见的认知误区？

**答疑**：OOM治理涉及多个层面，以下误区会导致治理效果不佳。

**论证**：

**误区一：OOM一定是内存泄漏导致的**

OOM有三类根因：堆内存超限、线程创建失败、FD超限。其中线程和FD导致的OOM占比约50%，但很多团队只关注Java堆内存泄漏。需要先对OOM进行分类，再针对性治理。

**误区二：增大堆内存就能解决OOM**

增大堆内存只是治标不治本。如果存在内存泄漏，更大的堆只是延缓了OOM的发生时间，并且会导致GC暂停时间更长。正确做法是找到并修复内存问题的根因。

**误区三：LeakCanary报告的都要修复**

LeakCanary可能报告系统SDK内部的泄漏，或者某些设计上就是全局持有的对象。需要区分真正影响内存水位的泄漏和无害的泄漏，优先修复影响最大的问题。

**误区四：线下没问题线上就不会有OOM**

线下测试场景有限，无法覆盖所有用户的使用模式。例如用户长时间使用不退出应用、快速切换页面、低端设备内存紧张等场景，都可能在线下环境中被忽略。线上监控是不可或缺的。

**误区五：Native内存不需要关注**

Android 8.0以后Bitmap像素数据存储在Native堆，Native内存的增长不会反映在Java堆的统计中。只关注Java堆可能忽略大量的Native内存消耗。需要同时监控Java堆和Native内存。

**结果**：OOM治理需要全面的视角，不能只关注Java堆泄漏。建立覆盖堆内存、线程、FD、Native内存的全方位监控体系，结合线上线下数据进行持续治理，才能有效降低OOM率。

### 9.1 Android OOM监控

```java
// Android OOM全方位监控器
public class AndroidOOMMonitor {
    
    private static final long CHECK_INTERVAL = 5000;  // 5秒检查一次
    private Handler handler;
    
    // 启动OOM监控
    public void startMonitoring(Context context) {
        handler = new Handler(Looper.getMainLooper());
        handler.postDelayed(new Runnable() {
            @Override
            public void run() {
                checkJavaHeap();
                checkNativeHeap();
                checkThreadCount();
                checkFDCount();
                handler.postDelayed(this, CHECK_INTERVAL);
            }
        }, CHECK_INTERVAL);
    }
    
    // 1. Java堆内存监控
    private void checkJavaHeap() {
        Runtime runtime = Runtime.getRuntime();
        long maxMemory = runtime.maxMemory();          // 最大堆内存
        long totalMemory = runtime.totalMemory();      // 已分配堆内存
        long freeMemory = runtime.freeMemory();        // 空闲堆内存
        long usedMemory = totalMemory - freeMemory;    // 已使用堆内存
        
        float usageRatio = (float) usedMemory / maxMemory;
        
        if (usageRatio > 0.85f) {
            // 内存使用超过85%，触发告警
            reportMemoryWarning("JavaHeap", usedMemory, maxMemory, usageRatio);
            
            if (usageRatio > 0.95f) {
                // 内存使用超过95%，紧急dump hprof
                triggerHeapDump();
            }
        }
    }
    
    // 2. Native堆监控（Android 8.0+重要，Bitmap存储在Native堆）
    private void checkNativeHeap() {
        long nativeHeapSize = Debug.getNativeHeapSize();
        long nativeHeapFree = Debug.getNativeHeapFreeSize();
        long nativeHeapUsed = nativeHeapSize - nativeHeapFree;
        
        // Native堆没有明确上限，但超过500MB通常有问题
        if (nativeHeapUsed > 500 * 1024 * 1024) {
            reportMemoryWarning("NativeHeap", nativeHeapUsed, nativeHeapSize, 
                (float) nativeHeapUsed / nativeHeapSize);
        }
    }
    
    // 3. 线程数监控
    private void checkThreadCount() {
        // 读取/proc/self/status获取线程数
        try {
            BufferedReader reader = new BufferedReader(
                new FileReader("/proc/self/status"));
            String line;
            while ((line = reader.readLine()) != null) {
                if (line.startsWith("Threads:")) {
                    int threadCount = Integer.parseInt(line.split("\\s+")[1]);
                    
                    // Android默认线程上限约为500-2000（取决于设备）
                    if (threadCount > 400) {
                        reportThreadWarning(threadCount);
                        dumpThreadInfo();
                    }
                    break;
                }
            }
            reader.close();
        } catch (Exception e) {
            // ignore
        }
    }
    
    // 4. FD数量监控
    private void checkFDCount() {
        File fdDir = new File("/proc/self/fd");
        String[] fdList = fdDir.list();
        int fdCount = fdList != null ? fdList.length : 0;
        
        // Linux默认FD上限1024
        if (fdCount > 800) {
            reportFDWarning(fdCount);
            
            // dump所有FD的符号链接，定位泄漏源
            if (fdCount > 900) {
                dumpFDInfo(fdDir);
            }
        }
    }
    
    // 内存泄漏检测（基于弱引用的简化版LeakCanary原理）
    public void watchObject(Object watchedObject, String description) {
        String key = UUID.randomUUID().toString();
        ReferenceQueue<Object> queue = new ReferenceQueue<>();
        WeakReference<Object> weakRef = new WeakReference<>(watchedObject, queue);
        
        // 延迟5秒检查对象是否被GC
        handler.postDelayed(() -> {
            // 先触发GC
            Runtime.getRuntime().gc();
            
            handler.postDelayed(() -> {
                if (queue.poll() == null && weakRef.get() != null) {
                    // 对象未被GC，可能存在泄漏
                    reportPossibleLeak(description, weakRef.get().getClass().getName());
                }
            }, 1000);
        }, 5000);
    }
    
    // 紧急堆dump（线上使用需要注意性能影响）
    private void triggerHeapDump() {
        try {
            String path = context.getCacheDir() + "/oom_dump_" + 
                System.currentTimeMillis() + ".hprof";
            Debug.dumpHprofData(path);
            
            // 裁剪hprof文件（移除Bitmap像素等大块数据，减小文件体积）
            // 只保留对象引用关系图
            trimHprof(path);
            
            // 异步上传
            uploadHprofAsync(path);
        } catch (IOException e) {
            // dump失败，可能是磁盘空间不足
        }
    }
}
```

### 9.2 iOS OOM监控

```objectivec
// iOS OOM监控器
@interface IOSOOMMonitor : NSObject

@property (nonatomic, assign) uint64_t lastPhysFootprint;
@property (nonatomic, strong) NSTimer *memoryTimer;

@end

@implementation IOSOOMMonitor

- (void)startMonitoring {
    // 1. 内存警告监听
    [[NSNotificationCenter defaultCenter] addObserver:self 
        selector:@selector(handleMemoryWarning:) 
        name:UIApplicationDidReceiveMemoryWarningNotification 
        object:nil];
    
    // 2. 定时检查内存水位
    self.memoryTimer = [NSTimer scheduledTimerWithTimeInterval:3.0 
        repeats:YES block:^(NSTimer *timer) {
        [self checkMemoryStatus];
    }];
    
    // 3. 启动时检查上次是否OOM（排除法）
    [self checkLastExitReason];
}

// 获取进程物理内存占用（Jetsam的判断依据）
- (uint64_t)getPhysicalFootprint {
    task_vm_info_data_t vmInfo;
    mach_msg_type_number_t count = TASK_VM_INFO_COUNT;
    kern_return_t result = task_info(mach_task_self(), TASK_VM_INFO, 
                                     (task_info_t)&vmInfo, &count);
    if (result == KERN_SUCCESS) {
        return vmInfo.phys_footprint;
    }
    return 0;
}

// 定时检查内存状态
- (void)checkMemoryStatus {
    uint64_t footprint = [self getPhysicalFootprint];
    uint64_t footprintMB = footprint / 1024 / 1024;
    
    // iOS 13+可以获取可用内存
    uint64_t availableMemory = 0;
    if (@available(iOS 13.0, *)) {
        availableMemory = os_proc_available_memory() / 1024 / 1024;
    }
    
    // 记录内存水位（用于崩溃分析）
    NSUserDefaults *defaults = [NSUserDefaults standardUserDefaults];
    [defaults setInteger:footprintMB forKey:@"last_memory_footprint"];
    [defaults synchronize];
    
    // 内存增长速度异常检测
    if (self.lastPhysFootprint > 0) {
        int64_t delta = footprint - self.lastPhysFootprint;
        int64_t deltaMB = delta / 1024 / 1024;
        
        // 3秒内内存增长超过50MB，可能存在内存激增
        if (deltaMB > 50) {
            [self reportMemorySurge:deltaMB currentMB:footprintMB];
        }
    }
    self.lastPhysFootprint = footprint;
    
    // Jetsam阈值警告
    // 不同设备的Jetsam阈值不同：
    // iPhone 6s (2GB RAM): ~约600-700MB
    // iPhone 11 (4GB RAM): ~约1200-1400MB
    // iPhone 13 Pro (6GB RAM): ~约1800-2000MB
    if (availableMemory > 0 && availableMemory < 100) {
        [self reportJetsamWarning:footprintMB available:availableMemory];
        [self emergencyMemoryRelease];
    }
}

// 紧急内存释放
- (void)emergencyMemoryRelease {
    // 清理图片缓存
    [[SDImageCache sharedImageCache] clearMemory];
    
    // 清理URL缓存
    [[NSURLCache sharedURLCache] removeAllCachedResponses];
    
    // 通知业务层释放非关键资源
    [[NSNotificationCenter defaultCenter] 
        postNotificationName:@"EmergencyMemoryRelease" object:nil];
}

// OOM排除法检测
- (void)checkLastExitReason {
    NSUserDefaults *defaults = [NSUserDefaults standardUserDefaults];
    
    BOOL lastTimeCrashed = [defaults boolForKey:@"did_crash"];
    BOOL isAppUpgrade = [self isAppUpgraded];
    BOOL wasBackground = [defaults boolForKey:@"was_background"];
    BOOL normalExit = [defaults boolForKey:@"normal_exit"];
    
    // 重置标记
    [defaults setBool:NO forKey:@"did_crash"];
    [defaults setBool:NO forKey:@"normal_exit"];
    [defaults synchronize];
    
    if (!lastTimeCrashed && !isAppUpgrade && !normalExit) {
        // 排除已知原因后，判定为异常退出
        uint64_t lastFootprint = [defaults integerForKey:@"last_memory_footprint"];
        
        if (wasBackground) {
            [self reportBackgroundOOM:lastFootprint];
        } else {
            [self reportForegroundOOM:lastFootprint];
        }
    }
}

@end
```

### 9.3 Web OOM监控

```javascript
// Web端内存溢出监控
class WebOOMMonitor {
    constructor() {
        this.memoryHistory = [];
        this.maxHistorySize = 60;  // 保留最近60次采样
    }
    
    startMonitoring() {
        this.monitorJSHeap();
        this.monitorDOMSize();
        this.monitorDetachedDOM();
        this.setupCrashRecovery();
    }
    
    // 1. JS堆内存监控（仅Chrome系浏览器）
    monitorJSHeap() {
        if (!performance.memory) {
            console.log('performance.memory不可用，使用降级方案');
            this.monitorWithCrossOriginIsolation();
            return;
        }
        
        setInterval(() => {
            const memory = performance.memory;
            const sample = {
                timestamp: Date.now(),
                usedJSHeapSize: memory.usedJSHeapSize,
                totalJSHeapSize: memory.totalJSHeapSize,
                jsHeapSizeLimit: memory.jsHeapSizeLimit,
                usageRatio: memory.usedJSHeapSize / memory.jsHeapSizeLimit
            };
            
            this.memoryHistory.push(sample);
            if (this.memoryHistory.length > this.maxHistorySize) {
                this.memoryHistory.shift();
            }
            
            // 检测内存泄漏趋势（连续增长）
            if (this.memoryHistory.length >= 10) {
                this.detectMemoryLeakTrend();
            }
            
            // 内存使用率告警
            if (sample.usageRatio > 0.9) {
                this.reportOOMWarning(sample);
            }
        }, 5000);
    }
    
    // 2. DOM节点数监控（DOM泄漏是Web最常见的内存问题）
    monitorDOMSize() {
        setInterval(() => {
            const allNodes = document.querySelectorAll('*').length;
            
            // 正常页面通常不超过1500个DOM节点
            // 超过5000个节点说明可能存在DOM泄漏
            if (allNodes > 5000) {
                this.reportDOMWarning(allNodes);
            }
        }, 10000);
    }
    
    // 3. Detached DOM检测（已从DOM树移除但仍被JS引用的节点）
    monitorDetachedDOM() {
        // Chrome DevTools Protocol中有getHeapObjectId
        // 线上可以通过FinalizationRegistry间接检测（ES2021）
        if (typeof FinalizationRegistry !== 'undefined') {
            const registry = new FinalizationRegistry((heldValue) => {
                // 对象被GC回收时的回调
                console.log(`对象 ${heldValue} 已被GC回收`);
            });
            
            // 监控关键DOM元素的生命周期
            // 示例：监控动态创建的列表项
            this._finalizationRegistry = registry;
        }
    }
    
    // 4. 内存泄漏趋势检测
    detectMemoryLeakTrend() {
        const recent = this.memoryHistory.slice(-10);
        let increasingCount = 0;
        
        for (let i = 1; i < recent.length; i++) {
            if (recent[i].usedJSHeapSize > recent[i-1].usedJSHeapSize) {
                increasingCount++;
            }
        }
        
        // 连续8次以上内存增长，高度怀疑内存泄漏
        if (increasingCount >= 8) {
            const firstSample = recent[0];
            const lastSample = recent[recent.length - 1];
            const growthMB = (lastSample.usedJSHeapSize - firstSample.usedJSHeapSize) 
                / 1024 / 1024;
            
            this.reportMemoryLeakSuspected({
                growthMB: growthMB.toFixed(2),
                duration: (lastSample.timestamp - firstSample.timestamp) / 1000,
                currentUsage: (lastSample.usedJSHeapSize / 1024 / 1024).toFixed(2)
            });
        }
    }
    
    // 5. 崩溃恢复机制
    setupCrashRecovery() {
        // 标记页面为活跃状态
        sessionStorage.setItem('page_alive', 'true');
        sessionStorage.setItem('last_active', Date.now().toString());
        
        // 定期更新心跳
        setInterval(() => {
            sessionStorage.setItem('last_active', Date.now().toString());
        }, 3000);
        
        // 正常卸载时清除标记
        window.addEventListener('beforeunload', () => {
            sessionStorage.removeItem('page_alive');
        });
        
        // 页面加载时检查上次是否正常退出
        const wasAlive = sessionStorage.getItem('page_alive');
        if (wasAlive === 'true') {
            const lastActive = parseInt(sessionStorage.getItem('last_active') || '0');
            const timeSinceLastActive = Date.now() - lastActive;
            
            // 上次没有正常卸载，且心跳停止超过10秒
            if (timeSinceLastActive > 10000) {
                this.reportPageCrash({
                    type: 'possible_oom',
                    lastActiveTime: new Date(lastActive).toISOString(),
                    timeSinceLastActive: timeSinceLastActive
                });
            }
        }
    }
}
```
