## 01.程序卡顿概念

### 1.1 卡顿的概念
- 卡顿是指应用程序在运行过程中出现的响应延迟或画面不流畅现象
    - 从用户感知角度：点击按钮后没有立即响应、列表滑动不流畅、页面切换动画卡顿、输入文字后延迟显示
    - 从技术角度：主线程被耗时操作阻塞，无法在规定时间内完成一帧的渲染或事件的处理
    - 卡顿的本质是主线程的消息处理速度跟不上消息产生的速度，导致消息队列积压
- 卡顿与ANR的关系
    - 卡顿是一个广泛的概念，包括轻微的掉帧（几十毫秒的延迟）到严重的冻帧（几百毫秒甚至几秒的无响应）
    - ANR（Application Not Responding）是Android系统对卡顿的一种极端处理机制
    - 当主线程在规定时间内没有完成特定操作时，系统会弹出ANR对话框
    - ANR的触发阈值：输入事件5秒、广播接收器10秒、Service前台20秒/后台200秒
    - 卡顿是ANR的前兆，治理卡顿可以有效预防ANR

### 1.2 为什么会卡顿
- 卡顿的根本原因是主线程被阻塞或负载过重
    - Android/iOS的UI框架都采用单线程模型：所有UI操作必须在主线程执行
    - 任何在主线程上执行时间过长的操作都会导致UI更新被延迟
    - 16ms是60fps屏幕的帧预算，超过这个时间就会掉帧
- 常见的卡顿原因分类
    - CPU密集型操作：复杂的计算、JSON解析、图片处理、大量对象创建
    - IO操作：文件读写、SharedPreferences操作、数据库查询、网络请求
    - 锁竞争：主线程等待子线程持有的锁、死锁、synchronized过度使用
    - 布局渲染：布局层级过深导致Measure/Layout耗时长、过度绘制、频繁触发requestLayout
    - 内存问题：频繁GC（垃圾回收）导致Stop-the-world暂停、内存不足导致内存回收
    - 系统资源竞争：CPU被其他进程/线程抢占、IO带宽不足、低电量模式下CPU降频
- 卡顿原因的排查思路
    - 首先确认卡顿发生在哪个线程：是主线程耗时还是主线程等待
    - 如果是主线程耗时：通过堆栈采样定位耗时方法
    - 如果是主线程等待：检查锁竞争、Binder调用、IO阻塞等情况
    - 如果是系统原因：检查CPU调度、内存压力、温控降频等外部因素

### 1.3 卡顿的分类
- 按照卡顿的严重程度分类

| 等级 | 名称 | 耗时范围 | 用户感知 | 处理优先级 |
|------|------|---------|---------|-----------|
| Level 1 | 轻微掉帧 | 17ms-50ms | 几乎无感知 | 低 |
| Level 2 | 明显卡顿 | 50ms-200ms | 能感觉到卡顿 | 中 |
| Level 3 | 严重卡顿 | 200ms-700ms | 明显卡住 | 高 |
| Level 4 | 冻帧 | >700ms | 界面冻结感 | 紧急 |
| Level 5 | ANR | >5s(输入事件) | 系统弹框 | 最高 |

- 按照卡顿的发生场景分类
    - 启动卡顿：应用冷启动、温启动时的白屏或黑屏时间过长
    - 滑动卡顿：列表滑动、页面滚动时的掉帧
    - 切换卡顿：页面切换、Tab切换时的动画不流畅
    - 交互卡顿：点击、长按、输入等用户操作后的响应延迟
    - 后台返回卡顿：从后台切回前台时的恢复延迟
- 按照卡顿的触发条件分类
    - 必现卡顿：每次操作都会触发，通常是逻辑问题，容易排查
    - 概率性卡顿：受设备性能、系统负载、数据量等因素影响，需要大量数据分析
    - 积累性卡顿：随使用时间增长逐渐恶化（内存泄漏、缓存增长），需要长时间监控

### 1.4 卡顿对用户的影响
- 卡顿是用户流失的重要原因之一
    - Google研究表明：53%的用户会放弃加载时间超过3秒的应用
    - Android Vitals数据显示：卡顿率高的应用，用户卸载率是正常应用的2-3倍
    - 应用商店评分：卡顿相关的差评占所有性能类差评的40%以上
- 卡顿对不同类型应用的影响差异
    - 电商应用：商品列表滑动卡顿直接影响浏览效率，降低转化率
    - 社交应用：聊天列表和朋友圈滑动卡顿影响用户粘性
    - 视频应用：视频列表滑动卡顿和播放控制延迟影响观看体验
    - 游戏应用：操作响应延迟直接影响游戏体验和竞技公平性

### 1.5 卡顿治理目标
- 卡顿治理的量化目标

| 指标 | 目标值 | 说明 |
|------|-------|------|
| 帧率(FPS) | ≥55fps | 核心页面的滑动帧率 |
| 掉帧率 | <5% | 掉帧帧数/总帧数 |
| 冻帧率 | <0.1% | >700ms帧占比 |
| ANR率 | <0.05% | ANR次数/UV |
| P95帧时间 | <20ms | 95%的帧在20ms内完成 |
| 卡顿率 | <3% | 存在明显卡顿的会话占比 |

- 卡顿治理的分阶段策略
    - 第一阶段（止血）：治理ANR和冻帧，消除最严重的卡顿问题
    - 第二阶段（优化）：降低掉帧率，提升核心页面的帧率
    - 第三阶段（防劣化）：建立卡顿监控体系，防止新代码引入卡顿
    - 第四阶段（精细化）：针对不同机型、场景、用户群体进行差异化优化


## 02.卡顿监听方案

### 2.1 帧率监控
- 帧率监控是最直观的卡顿检测方式
    - 通过Choreographer.FrameCallback获取每帧回调的时间戳
    - 计算相邻帧之间的时间差（帧时间），统计帧率
    - 帧时间超过16.67ms（60Hz）表示发生了掉帧
- 帧率监控的优缺点
    - 优点：实现简单，性能开销小，能反映渲染流畅度
    - 优点：可以精确计算帧率和掉帧次数
    - 缺点：只能检测到渲染阶段的卡顿，无法检测非渲染阶段的主线程卡顿
    - 缺点：无法直接获取卡顿的堆栈信息，需要配合堆栈采样
    - 缺点：帧回调本身有一定的精度限制（依赖VSync信号的精度）
- 帧率监控适用的场景
    - 列表滑动场景的流畅度评估
    - 动画执行过程的帧率监控
    - 页面渲染性能的持续跟踪
    - 不适合检测非渲染场景的卡顿（如点击响应延迟）

### 2.2 事件循环监控
- 事件循环监控利用Android消息机制的特性来检测卡顿
    - Android的主线程运行在一个Looper消息循环中
    - 每个Message的dispatch前后，Looper会通过Printer打印日志
    - 通过设置Looper.setMessageLogging()可以截获这些日志
    - 计算dispatch前后的时间差，即可得到单个Message的处理时间
- 事件循环监控的原理
    - Looper.loop()的核心代码中，在msg.target.dispatchMessage(msg)前后会调用Printer
    - dispatch前打印 `>>>>> Dispatching to Handler ...`
    - dispatch后打印 `<<<<< Finished to Handler ...`
    - 通过这两行日志的时间差即可获得Message处理耗时
- 事件循环监控的优缺点
    - 优点：可以检测所有在主线程消息循环中执行的耗时操作
    - 优点：不仅限于渲染卡顿，还能检测IO、计算等导致的卡顿
    - 优点：可以获取到具体的Handler和Message类型信息
    - 缺点：Printer.println()调用本身有性能开销（字符串拼接）
    - 缺点：系统Looper的Printer可能被其他组件覆盖
    - 缺点：对于通过反射或其他非标准方式执行的主线程操作无法检测

### 2.3 执行耗时监控
- 执行耗时监控通过函数插桩（AOP）来检测耗时方法
    - 在编译期通过ASM/AspectJ在目标方法的入口和出口插入计时代码
    - 运行时记录每个方法的执行时间
    - 超过阈值的方法触发告警
- 执行耗时监控的方案
    - 编译期插桩：使用Gradle Plugin + ASM，在字节码层面插入计时代码
    - 运行时插桩：使用Debug.startMethodTracing()进行方法级别的追踪
    - Systrace标记：在关键方法中添加Trace.beginSection()/endSection()标记
- 执行耗时监控的优缺点
    - 优点：可以精确定位到具体的耗时方法
    - 优点：不依赖消息循环，可以检测任何线程上的耗时操作
    - 缺点：编译期插桩会增大包体积（每个方法增加若干字节码指令）
    - 缺点：方法级别的计时有精度问题（System.nanoTime()的开销）
    - 缺点：全量插桩的性能开销不可忽视，通常需要配置白名单/黑名单

### 2.4 渲染性能监控
- 渲染性能监控专注于渲染流水线各阶段的耗时
    - FrameMetrics API（Android 7.0+）可以获取每帧各阶段的精确耗时
    - 包括：UNKNOWN_DELAY、INPUT_HANDLING、ANIMATION、LAYOUT_MEASURE、DRAW、SYNC、COMMAND_ISSUE、SWAP_BUFFERS、TOTAL_DURATION
    - 可以精确判断卡顿发生在渲染的哪个阶段
- 渲染性能监控的优缺点
    - 优点：可以精确到渲染流水线的每个阶段
    - 优点：是系统原生API，数据准确可靠
    - 优点：对应用性能的影响极小
    - 缺点：只支持Android 7.0+
    - 缺点：只能监控渲染相关的卡顿，非渲染卡顿无法检测
    - 缺点：无法获取卡顿时的方法堆栈信息

### 2.5 监听方案对比
- 四种监控方案的综合对比

| 维度 | 帧率监控 | 事件循环监控 | 执行耗时监控 | 渲染性能监控 |
|------|---------|------------|------------|------------|
| 监控范围 | 渲染卡顿 | 主线程所有操作 | 指定方法 | 渲染流水线 |
| 实现复杂度 | 低 | 低 | 高 | 低 |
| 性能开销 | 很低 | 低-中 | 中-高 | 很低 |
| 定位精度 | 帧级别 | 消息级别 | 方法级别 | 阶段级别 |
| 堆栈信息 | 需配合采样 | 需配合采样 | 自带 | 无 |
| 最低API | 16 | 1 | 编译期 | 24 |
| 适用场景 | 滑动/动画 | 通用 | 精确定位 | 渲染分析 |

- 推荐的组合方案
    - 线上环境：帧率监控 + 事件循环监控 + 异步堆栈采样
    - 线下环境：全部四种方案配合使用，获取最完整的卡顿信息
    - 帧率监控作为核心指标，事件循环监控作为卡顿捕获手段，堆栈采样提供定位能力


## 03.卡顿监听实践

### 3.1 方案敲定和选择
- 选择卡顿监控方案需要考虑的因素
    - 目标场景：是否只关注渲染卡顿，还是需要覆盖所有主线程卡顿
    - 性能预算：监控本身的CPU/内存开销不能影响应用性能
    - 线上/线下：线上环境对性能开销更敏感，线下可以使用更重的工具
    - 堆栈需求：是否需要获取卡顿时的方法堆栈用于问题定位
    - 兼容性：需要支持的最低Android API版本
- 推荐的线上卡顿监控架构
    - 核心层：基于事件循环监控（Looper Printer）检测卡顿

### 3.2 监控帧率实践
- 基于Choreographer的帧率监控实现

```java
/**
 * 帧率监控器
 * 基于Choreographer.FrameCallback实现
 */
public class FPSMonitor implements Choreographer.FrameCallback {
    private static final long ONE_SECOND_NS = 1_000_000_000L;
    private static final long FRAME_INTERVAL_NS = 16_666_667L; // 16.67ms
    
    private long lastFrameTimeNanos = 0;
    private int frameCount = 0;
    private long periodStartNanos = 0;
    private boolean isRunning = false;
    
    // 帧率回调接口
    public interface FPSCallback {
        void onFPSUpdate(float fps, int droppedFrames);
    }
    
    private FPSCallback callback;
    
    public FPSMonitor(FPSCallback callback) {
        this.callback = callback;
    }
    
    public void start() {
        if (isRunning) return;
        isRunning = true;
        lastFrameTimeNanos = System.nanoTime();
        periodStartNanos = lastFrameTimeNanos;
        frameCount = 0;
        Choreographer.getInstance().postFrameCallback(this);
    }
    
    public void stop() {
        isRunning = false;
    }
    
    @Override
    public void doFrame(long frameTimeNanos) {
        if (!isRunning) return;
        
        // 计算帧间隔
        long frameDuration = frameTimeNanos - lastFrameTimeNanos;
        frameCount++;
        
        // 检测掉帧（超过2帧间隔认为掉帧）
        if (frameDuration > FRAME_INTERVAL_NS * 2) {
            int droppedFrames = (int) (frameDuration / FRAME_INTERVAL_NS) - 1;
            onFrameDropped(droppedFrames, frameDuration);
        }
        
        // 每秒计算一次帧率
        long elapsed = frameTimeNanos - periodStartNanos;
        if (elapsed >= ONE_SECOND_NS) {
            float fps = frameCount * 1e9f / elapsed;
            if (callback != null) {
                callback.onFPSUpdate(fps, 0);
            }
            frameCount = 0;
            periodStartNanos = frameTimeNanos;
        }
        
        lastFrameTimeNanos = frameTimeNanos;
        Choreographer.getInstance().postFrameCallback(this);
    }
    
    private void onFrameDropped(int droppedFrames, long durationNanos) {
        float durationMs = durationNanos / 1e6f;
        // 根据掉帧程度分级处理
        if (durationMs > 700) {
            // 冻帧级别：需要紧急处理
            reportFreezeFrame(droppedFrames, durationMs);
        } else if (durationMs > 200) {
            // 严重卡顿：需要高优处理
            reportSevereJank(droppedFrames, durationMs);
        } else if (durationMs > 50) {
            // 明显卡顿：需要记录
            reportJank(droppedFrames, durationMs);
        }
    }
}
```

    private static final long FREEZE_THRESHOLD_MS = 700; // 冻帧阈值
    
    private long dispatchStartTime = 0;
    private boolean isDispatching = false;
    private StackSampler stackSampler;

        stackSampler = new StackSampler();
        
        Looper.getMainLooper().setMessageLogging(new Printer() {
            @Override
            public void println(String log) {
                if (log.startsWith(">>>>> Dispatching")) {
                    // 消息开始处理
                    dispatchStartTime = System.currentTimeMillis();
                    isDispatching = true;
                    // 开始堆栈采样
                    stackSampler.startSampling();
                } else if (log.startsWith("<<<<< Finished")) {
                    // 消息处理完成
                    isDispatching = false;
                    long duration = System.currentTimeMillis() - dispatchStartTime;
                    stackSampler.stopSampling();
                    
                    if (duration >= JANK_THRESHOLD_MS) {
                        // 获取采样到的堆栈
                        String stackTrace = stackSampler.getSampledStack();
                        reportJank(duration, stackTrace, log);
                    }
                }
            }
        });
    }
    
    private void reportJank(long duration, String stackTrace, String msgInfo) {
        JankInfo jankInfo = new JankInfo();
        jankInfo.duration = duration;
        jankInfo.stackTrace = stackTrace;
        jankInfo.messageInfo = msgInfo;
        jankInfo.timestamp = System.currentTimeMillis();
        jankInfo.scene = getCurrentScene();
        
        if (duration >= FREEZE_THRESHOLD_MS) {
            jankInfo.level = JankLevel.FREEZE;
        } else if (duration >= 200) {
            jankInfo.level = JankLevel.SEVERE;
        } else {
            jankInfo.level = JankLevel.NORMAL;
        }

/**
 * 方法耗时监控（被插桩后的效果）
 * 编译期通过Gradle Plugin + ASM在目标方法入口/出口插入计时代码
 */
public class MethodTracer {
    // 线程局部变量，记录方法调用栈的时间戳
    private static final ThreadLocal<long[]> sTimestampStack = 
        ThreadLocal.withInitial(() -> new long[128]);
    private static final ThreadLocal<Integer> sStackDepth = 
        ThreadLocal.withInitial(() -> 0);
    
    // 方法入口（由ASM插桩插入）
    public static void onMethodEnter(int methodId) {
        int depth = sStackDepth.get();
        long[] stack = sTimestampStack.get();
        if (depth < stack.length) {
            stack[depth] = System.nanoTime();
            sStackDepth.set(depth + 1);
        }
    }
    
    // 方法出口（由ASM插桩插入）
    public static void onMethodExit(int methodId) {
        int depth = sStackDepth.get() - 1;
        if (depth < 0) return;
        sStackDepth.set(depth);
        
        long[] stack = sTimestampStack.get();
        long startTime = stack[depth];
        long duration = System.nanoTime() - startTime;
        long durationMs = duration / 1_000_000;
        
        // 超过阈值记录
        if (durationMs > 16 && isMainThread()) {
            recordSlowMethod(methodId, durationMs);
        }
    }
    
    private static boolean isMainThread() {
        return Looper.getMainLooper().getThread() == Thread.currentThread();
    }
}

### 3.5 卡顿信息采集
- 卡顿发生时需要采集的关键信息
    - 基础信息：卡顿时长、发生时间、当前页面/场景、用户操作序列
    - 堆栈信息：主线程调用栈（最关键的定位信息）
    - 系统信息：CPU使用率、可用内存、IO状态、电量状态
    - 应用信息：线程数量、FD数量、GC频率、当前任务队列状态
    - 设备信息：设备型号、系统版本、可用存储空间、屏幕分辨率
- 堆栈采样是卡顿定位的核心

```java
/**
 * 主线程堆栈采样器
 * 在独立线程中定期获取主线程的调用栈
 */
public class StackSampler {
    private static final long SAMPLE_INTERVAL_MS = 50; // 采样间隔50ms
    private Thread mainThread;
    private HandlerThread samplerThread;
    private Handler samplerHandler;
    private volatile boolean isSampling = false;
    private List<String> sampledStacks = new ArrayList<>();
    
    public StackSampler() {
        mainThread = Looper.getMainLooper().getThread();
        samplerThread = new HandlerThread("stack-sampler");
        samplerThread.start();
        samplerHandler = new Handler(samplerThread.getLooper());
    }
    
    public void startSampling() {
        isSampling = true;
        sampledStacks.clear();
        samplerHandler.postDelayed(sampleRunnable, SAMPLE_INTERVAL_MS);
    }
    
    public void stopSampling() {
        isSampling = false;
        samplerHandler.removeCallbacks(sampleRunnable);
    }
    
    private final Runnable sampleRunnable = new Runnable() {
        @Override
        public void run() {
            if (!isSampling) return;
            
            // 获取主线程堆栈
            StackTraceElement[] stackTrace = mainThread.getStackTrace();
            StringBuilder sb = new StringBuilder();
            for (StackTraceElement element : stackTrace) {
                sb.append(element.toString()).append("\n");
            }
            sampledStacks.add(sb.toString());
            
            // 继续采样
            samplerHandler.postDelayed(this, SAMPLE_INTERVAL_MS);
        }
    };
    
    /**
     * 获取出现频率最高的堆栈（即卡顿的热点位置）
     */
    public String getSampledStack() {
        if (sampledStacks.isEmpty()) return "";
        // 统计堆栈频率，返回出现最多的堆栈
        Map<String, Integer> stackFrequency = new HashMap<>();
        for (String stack : sampledStacks) {
            stackFrequency.merge(stack, 1, Integer::sum);
        }
        return stackFrequency.entrySet().stream()
            .max(Map.Entry.comparingByValue())
            .map(Map.Entry::getKey)
            .orElse("");
    }
}
```

- 堆栈采样的优化策略
    - 采样间隔的选择：太短（<10ms）会增加性能开销，太长（>100ms）会丢失短时间的卡顿堆栈
    - 推荐采样间隔：线上50ms，线下20ms
    - 采样去重：连续相同的堆栈只记录一次，减少存储开销
    - 堆栈裁剪：过滤掉系统框架层的堆栈帧，只保留应用代码部分

### 4.1 帧率监控页面
- 开发阶段可以在应用内显示实时帧率悬浮窗
    - 显示当前帧率数值、帧率趋势曲线、掉帧次数统计
    - 使用不同颜色标示帧率状态：绿色(≥55fps)、黄色(40-55fps)、红色(<40fps)
    - 支持点击展开查看详细的帧时间分布

    - 使用WindowManager添加TYPE_APPLICATION_OVERLAY类型的悬浮窗
    - 悬浮窗本身的渲染不能影响帧率数据的准确性
    - 帧率数据的刷新频率控制在每秒1次，避免频繁刷新悬浮窗内容
    - 提供拖拽功能，不遮挡关键UI区域

### 4.2 卡顿堆栈采样
- 堆栈采样是卡顿定位的关键能力
    - 当检测到卡顿开始时，启动堆栈采样
    - 采样线程以固定间隔获取主线程的调用栈
    - 卡顿结束后，分析采样到的堆栈，找出出现频率最高的调用路径
    - 高频堆栈即为卡顿的真正原因
- 堆栈采样的精度优化
    - 基础方案：使用Thread.getStackTrace()获取Java层堆栈
    - 进阶方案：使用libunwind获取Native层堆栈（可以看到JNI调用链）
    - 高精度方案：使用Simpleperf进行CPU Profiling，获取函数级别的耗时分布
    - 堆栈聚合算法：将多次采样的堆栈进行聚合，生成调用火焰图

### 4.3 动态阈值调整
- 不同机型、场景的卡顿阈值应该不同
    - 高端机（如旗舰手机）：卡顿阈值设为50ms，对流畅度要求更高
    - 低端机（如入门手机）：卡顿阈值设为150ms，避免过多的误报
    - 高刷屏（90/120Hz）：帧预算更短，卡顿阈值应相应降低
    - 后台场景：不需要渲染的场景可以提高阈值或暂停监控
- 动态阈值的实现
    - 通过配置下发实现动态调整，无需发版
    - 根据设备性能评分自动选择阈值等级
    - 设备性能评分可根据CPU核心数、频率、内存大小、GPU型号等综合计算
    - 支持按页面/场景配置不同的阈值

### 4.4 多级警报系统
- 卡顿警报需要分级处理，避免告警疲劳
    - P0（紧急）：冻帧(>700ms)或ANR，需要立即处理
    - P1（高优）：严重卡顿(200-700ms)，当日内处理
    - P2（中优）：明显卡顿(50-200ms)，版本内处理
    - P3（低优）：轻微掉帧(17-50ms)，持续优化
- 警报的触发条件
    - 单次阈值触发：单次卡顿超过设定阈值
    - 频率触发：一段时间内卡顿次数超过设定值
    - 趋势触发：卡顿率较前一版本显著上升
    - 比较触发：某页面的卡顿率显著高于同类页面

### 4.5 卡顿聚合分析
- 线上采集到的卡顿数据需要聚合分析才有意义
    - 堆栈聚合：将相同调用路径的卡顿聚合为一个Issue
    - 维度聚合：按页面、设备型号、系统版本、网络状态等维度聚合
    - 趋势分析：跟踪每个Issue的卡顿次数随版本的变化趋势
    - Top N分析：找出影响范围最大的Top 10卡顿问题
- 聚合分析的技术要点
    - 堆栈去框架：去掉系统框架层的调用帧，只根据应用代码部分进行聚合
    - 堆栈签名：对堆栈计算Hash作为唯一标识，相同Hash的堆栈归为同一Issue
    - 影响面评估：每个Issue的影响面 = 受影响UV / 总UV，用于优先级排序
    - 自动归因：通过堆栈分析自动标记卡顿类型（IO类、锁竞争类、布局类等）

## 06.帧率监控原理

### 6.1 帧率监控核心
- 帧率监控的核心是利用VSync信号的规律性
    - Android的Choreographer在每个VSync信号到来时回调FrameCallback
    - 通过记录每次回调的时间戳，可以计算帧间隔和帧率
    - 帧率 = 帧数 / 统计时间窗口
    - 掉帧数 = (帧间隔 / 标准帧间隔) - 1
- Choreographer的工作原理
    - Choreographer内部维护了一个按时间排序的回调队列
    - 回调分为四种类型：CALLBACK_INPUT → CALLBACK_ANIMATION → CALLBACK_INSETS_ANIMATION → CALLBACK_TRAVERSAL
    - 每次VSync信号到来时，Choreographer按顺序执行队列中到期的回调
    - 如果某个回调执行时间过长，会导致后续回调延迟，从而产生掉帧
- FrameCallback的注册和执行流程
    - 调用Choreographer.postFrameCallback()注册回调
    - 系统在下一个VSync信号到来时调用doFrame(long frameTimeNanos)
    - frameTimeNanos是VSync信号的精确时间戳（纳秒级别）
    - 需要在doFrame中再次调用postFrameCallback以保持持续监控

### 6.2 frame本质
- 帧（Frame）的本质是屏幕上一次完整的画面更新
    - 从软件角度：一帧对应一次完整的UI线程处理（Input→Animation→Measure→Layout→Draw）加RenderThread渲染
    - 从硬件角度：一帧对应显示器一次完整的像素刷新（从左上角扫描到右下角）
    - 两者通过VSync信号同步：软件在VSync信号到来时开始渲染新一帧，硬件在下一个VSync信号到来时显示渲染好的帧
- 帧的生命周期
    - 创建：VSync信号到来，Choreographer开始调度回调
    - 处理：UI线程执行Input→Animation→Measure→Layout→Draw
    - 渲染：RenderThread将DisplayList提交给GPU渲染
    - 合成：SurfaceFlinger将多个Surface的帧合成为最终画面
    - 显示：VSync信号到来时，交换缓冲区，画面更新到屏幕
- DisplayList与帧的关系
    - DisplayList是View树绘制命令的序列化表示
    - 每次View.draw()调用会更新对应View的DisplayList
    - RenderThread遍历所有DisplayList生成GPU渲染指令
    - 只有DisplayList发生变化的View才需要重新record，未变化的可以复用

### 6.3 帧率一般是多少
- 不同设备和场景下的帧率标准
    - 大多数Android设备：60Hz屏幕刷新率，对应60fps
    - 高刷新率设备：90Hz(如OnePlus 7 Pro)、120Hz(如三星Galaxy S系列)、144Hz(游戏手机)
    - 低功耗模式：部分设备在低电量时降至30Hz/48Hz以节省电量
    - 视频播放：通常为24fps/30fps/60fps，取决于视频源
- 帧率与体验的关系
    - <24fps：明显的画面跳帧感，类似幻灯片
    - 24-30fps：基本流畅，但快速运动场景会感觉不够平滑
    - 30-45fps：一般流畅，偶尔会感觉到轻微卡顿
    - 45-60fps：流畅，满足大多数场景的需求
    - 60fps：标准流畅，人眼难以分辨更高帧率带来的差异
    - 90-120fps：极致流畅，在快速滑动等场景能感受到细微提升
- 帧率并非越高越好
    - 更高的帧率意味着更高的CPU/GPU负载和更多的电量消耗
    - 自适应帧率（如Android 12的可变刷新率）是更好的选择
    - 根据场景动态调整帧率：静态页面降至30fps，滑动时恢复60fps

### 6.4 帧率影响因素
- 影响帧率的因素是多维度的
    - 硬件因素：CPU性能（核心数/频率）、GPU性能、内存带宽、存储IO速度
    - 软件因素：布局复杂度、绘制复杂度、主线程任务负载、线程竞争
    - 系统因素：后台进程数量、内存压力、温控降频、省电模式
    - 内容因素：页面元素数量、图片数量和尺寸、动画复杂度
- 帧率波动的常见原因
    - GC（垃圾回收）：GC暂停（Stop-the-world）直接导致帧渲染停止
    - JIT编译：ART的JIT编译器在运行时编译热点代码，会占用CPU资源
    - 系统服务调用：Binder调用、ContentProvider查询等跨进程操作
    - IO操作：文件系统IO、数据库IO、网络IO在主线程执行
    - CPU降频：温度过高时CPU降频，渲染速度下降

### 6.5 掉帧判定标准
- 掉帧的判定需要明确的标准
    - 标准定义：当一帧的实际渲染时间超过一个VSync周期时，发生掉帧
    - 60Hz屏幕：帧时间>16.67ms即掉帧
    - 90Hz屏幕：帧时间>11.11ms即掉帧
    - 120Hz屏幕：帧时间>8.33ms即掉帧
- Google推荐的掉帧分级标准（Android Vitals）
    - Slow rendering：帧时间超过16ms的帧占比
    - Frozen frames：帧时间超过700ms的帧
    - 应用在Google Play Console中会显示这两个指标
    - Slow rendering >50%或Frozen frames >0.1%会被标记为需要优化
- 实际项目中的掉帧判定建议
    - 不要将所有超过16ms的帧都视为掉帧，17-20ms的帧用户几乎无法感知
    - 建议以2倍帧间隔（33ms）作为掉帧的实际判定阈值
    - 连续掉帧比单次掉帧的体验影响更大，需要单独统计
    - 在高刷屏设备上，掉帧判定阈值应相应调低


## 07.事件监控原理

### 7.1 消息循环机制
- Android主线程的核心是Handler-Looper-MessageQueue消息循环
    - Looper.loop()是一个无限循环，不断从MessageQueue中取出Message
    - 每个Message通过msg.target.dispatchMessage(msg)分发处理
    - 所有的UI操作（View更新、动画、输入事件处理）都是通过Message在主线程执行的
- 消息循环的关键代码

```java
// Looper.loop() 简化版核心逻辑
public static void loop() {
    final Looper me = myLooper();
    final MessageQueue queue = me.mQueue;
    
    for (;;) {
        Message msg = queue.next(); // 阻塞获取消息
        if (msg == null) return;
        
        // 关键：dispatch前后的Printer回调
        final Printer logging = me.mLogging;
        if (logging != null) {
            logging.println(">>>>> Dispatching to " + msg.target 
                + " " + msg.callback + ": " + msg.what);
        }
        
        msg.target.dispatchMessage(msg); // 消息处理（可能耗时）
        
        if (logging != null) {
            logging.println("<<<<< Finished to " + msg.target 
                + " " + msg.callback);
        }
        
        msg.recycleUnchecked();
    }
}
```

### 7.2 Printer监控原理
- 利用Looper的Printer机制是最经典的卡顿监控方案
    - 在dispatch前后各打印一条日志，通过计算两条日志的时间差获得消息处理耗时
    - 这个方案被BlockCanary、Matrix等知名开源项目广泛使用
- Printer监控的实现细节
    - 通过Looper.getMainLooper().setMessageLogging(printer)设置自定义Printer
    - 需要注意：setMessageLogging会覆盖之前设置的Printer
    - 为了兼容性，可以先保存原有的Printer，在自定义Printer中转发
    - Printer的println方法在主线程调用，实现要尽可能轻量
- Printer方案的性能影响
    - 每次Message处理前后都会触发Printer.println()
    - println参数的字符串拼接会产生临时String对象
    - 在高频消息场景（如触摸事件连续分发）中，性能开销不可忽视
    - 优化方式：使用反射Hook而非Printer来减少字符串拼接开销

### 7.3 消息耗时检测
- 消息耗时检测的进阶方案
    - 基础方案：通过Printer获取dispatch前后的时间差
    - 进阶方案：Hook Handler.dispatchMessage()方法，在调用前后插入计时逻辑
    - 高精度方案：使用Native层的epoll机制监控消息循环的空闲和忙碌状态
- 消息分类统计
    - 输入事件消息：touch、key等用户输入，处理时间直接影响操作响应速度
    - UI刷新消息：invalidate、requestLayout触发的Traversal消息
    - 动画消息：Choreographer的动画回调
    - 业务消息：应用业务逻辑产生的Handler消息
    - 不同类型的消息有不同的耗时预期和阈值标准

### 7.4 ANR与卡顿的关系
- ANR是卡顿的极端表现形式
    - ANR = 主线程在规定时间内未完成特定操作
    - 卡顿 = 主线程处理某个消息的时间超过预期
    - 治理卡顿就是在预防ANR
- ANR的触发机制
    - 输入事件ANR：InputDispatcher发现之前的输入事件在5秒内未处理完
    - 广播ANR：BroadcastQueue发现广播接收器在规定时间内未处理完
    - Service ANR：ActiveServices发现Service在规定时间内未完成启动或超时
    - ContentProvider ANR：ContentProvider在发布超时时间内未完成
- 卡顿监控对ANR治理的帮助
    - 通过卡顿监控发现耗时>1秒的主线程操作，这些就是潜在的ANR风险点
    - 卡顿堆栈可以帮助定位ANR的根因（很多ANR的traces.txt堆栈不准确）
    - 建立卡顿趋势，当某个场景的卡顿率上升时提前预警，避免ANR率飙升

### 7.5 性能分析优化
- 卡顿监控本身的性能优化
    - 监控代码的CPU开销应控制在1%以内，不能因为监控导致卡顿
    - 堆栈采样的线程优先级应设为最低，避免与业务线程竞争CPU
    - 采样数据使用环形缓冲区存储，控制内存占用
    - 上报数据先在本地聚合，定时批量上报，减少IO频率
- 监控的采样策略
    - 全量监控性能开销大，线上环境建议采样10%-20%用户
    - 可以对新版本的前几天全量监控，确认无明显退化后降低采样率
    - 高端机可以适当提高采样率（因为监控开销对它们影响更小）
    - 出现线上问题时可以动态提高指定版本/机型的采样率
- 卡顿数据的存储和上报优化
    - 卡顿数据先写入本地DB，避免丢失
    - 使用Protobuf或自定义二进制格式序列化，比JSON省50%以上流量
    - 上报时机选择在WiFi环境或应用退到后台时
    - 对于冻帧级别的严重卡顿，立即上报（不等待批量上报周期）


## 08.跨平台卡顿监控

### 8.1 各平台卡顿特点
- 不同平台的卡顿原因和监控方式存在差异

| 维度 | Android | iOS | Web |
|------|---------|-----|-----|
| UI线程模型 | Looper消息循环 | RunLoop | Event Loop |
| 卡顿根因 | 主线程耗时操作 | 主线程耗时操作 | 主线程耗时操作 |
| 帧率标准 | 60/90/120fps | 60/120fps(ProMotion) | 60fps |
| 监控入口 | Choreographer/Printer | CADisplayLink/RunLoop | requestAnimationFrame |

| 主要工具 | Systrace/Perfetto | Instruments | Chrome DevTools |

### 8.2 iOS卡顿监控
- iOS的卡顿监控基于RunLoop机制

```swift
/// iOS卡顿监控器
/// 基于RunLoop Observer检测主线程卡顿
class JankMonitor {
    private var runLoopObserver: CFRunLoopObserver?
    private var runLoopActivity: CFRunLoopActivity = .entry
    private var semaphore: DispatchSemaphore = DispatchSemaphore(value: 0)
    private var monitorThread: Thread?
    
    // 卡顿阈值（毫秒）
    private let jankThreshold: TimeInterval = 0.1 // 100ms
    
    func start() {
        // 创建RunLoop Observer
        let observer = CFRunLoopObserverCreateWithHandler(
            kCFAllocatorDefault, 
            CFRunLoopActivity.allActivities.rawValue, 
            true, 0
        ) { [weak self] _, activity in
            self?.runLoopActivity = activity
            self?.semaphore.signal()
        }
        
        CFRunLoopAddObserver(CFRunLoopGetMain(), observer, .commonModes)
        runLoopObserver = observer
        
        // 监控线程
        monitorThread = Thread {
            while true {
                // 等待RunLoop状态变化
                let result = self.semaphore.wait(
                    timeout: .now() + self.jankThreshold
                )
                
                if result == .timedOut {
                    // 超时说明主线程卡住了
                    let activity = self.runLoopActivity
                    if activity == .beforeSources || activity == .afterWaiting {
                        // 获取主线程堆栈
                        let stack = Thread.callStackSymbols.joined(separator: "\n")
                        self.reportJank(stack: stack)
                    }
                }
            }
        }
        monitorThread?.start()
    }
    
    private func reportJank(stack: String) {
        print("[JankMonitor] 检测到卡顿:\n\(stack)")
    }
}
```

- iOS卡顿监控的注意事项
    - RunLoop Observer的方案无法精确获取卡顿时长，只能判断是否超过阈值
    - 需要配合CADisplayLink来统计帧率数据
    - iOS 15+可以使用MetricKit框架获取系统级的卡顿数据
    - Xcode的Hang Detection工具可以自动检测超过250ms的主线程卡顿

### 8.3 Web卡顿监控
- Web平台的卡顿监控基于Event Loop和requestAnimationFrame

```javascript
/**
 * Web卡顿监控器
 * 基于requestAnimationFrame和Long Task API
 */
class WebJankMonitor {
    constructor(options = {}) {
        this.jankThreshold = options.jankThreshold || 50; // 50ms
        this.lastFrameTime = 0;
        this.frameCount = 0;
        this.isRunning = false;
    }
    
    start() {
        this.isRunning = true;
        this.lastFrameTime = performance.now();
        
        // 方案1：基于requestAnimationFrame的帧率监控
        this._monitorFPS();
        
        // 方案2：基于Long Task API的卡顿监控
        this._monitorLongTasks();
        
        // 方案3：基于PerformanceObserver的帧时间监控
        this._monitorFrameTiming();
    }
    
    _monitorFPS() {
        const loop = (timestamp) => {
            if (!this.isRunning) return;
            
            const frameDuration = timestamp - this.lastFrameTime;
            this.frameCount++;
            
            // 检测掉帧
            if (frameDuration > this.jankThreshold) {
                this._reportJank({
                    type: 'frame_drop',
                    duration: frameDuration,
                    timestamp: Date.now()
                });
            }
            
            this.lastFrameTime = timestamp;
            requestAnimationFrame(loop);
        };
        requestAnimationFrame(loop);
    }
    
    _monitorLongTasks() {
        // Long Task API：检测超过50ms的任务
        if ('PerformanceObserver' in window) {
            const observer = new PerformanceObserver((list) => {
                for (const entry of list.getEntries()) {
                    this._reportJank({
                        type: 'long_task',
                        duration: entry.duration,
                        startTime: entry.startTime,
                        name: entry.name
                    });
                }
            });
            observer.observe({ type: 'longtask', buffered: true });
        }
    }
    
    _monitorFrameTiming() {
        // 使用PerformanceObserver监控帧时间
        if ('PerformanceObserver' in window) {
            try {
                const observer = new PerformanceObserver((list) => {
                    for (const entry of list.getEntries()) {
                        if (entry.duration > 16.67) {
                            this._reportJank({
                                type: 'slow_frame',
                                duration: entry.duration,
                                startTime: entry.startTime
                            });
                        }
                    }
                });
                observer.observe({ type: 'frame', buffered: true });
            } catch (e) {
                // frame type可能不被支持
            }
        }
    }
    
    _reportJank(data) {
        console.warn('[JankMonitor]', data);
        // 上报到监控平台
    }
    
    stop() {
        this.isRunning = false;
    }
}

// 使用示例
const monitor = new WebJankMonitor({ jankThreshold: 50 });
monitor.start();
```

- Web卡顿监控的特殊考虑
    - Long Task API是W3C标准，检测超过50ms的JS执行任务
    - Web Worker中的卡顿不影响主线程渲染，不需要监控
    - Service Worker中的卡顿可能影响网络请求响应，需要单独监控
    - React/Vue等框架可以通过Performance API检测组件渲染耗时


## 09.卡顿监控设计总结

### 9.1 核心设计原则

**原则一：监控不能造成卡顿**

卡顿监控代码运行在主线程或与主线程交互频繁，如果监控本身有性能问题，就会成为卡顿的制造者。监控代码的CPU开销应控制在1%以内，内存开销应控制在5MB以内。

**原则二：多维度交叉验证**

单一的监控方案无法覆盖所有卡顿场景。帧率监控检测渲染卡顿，事件循环监控检测消息处理卡顿，两者结合才能全面覆盖。堆栈采样提供定位能力，渲染分析提供阶段划分能力。

**原则三：分级治理**

不是所有的卡顿都值得治理。轻微掉帧（17-50ms）用户几乎无感知，可以低优处理；冻帧（>700ms）严重影响用户体验，需要紧急处理。根据卡顿的严重程度和影响范围确定治理优先级。

**原则四：持续防劣化**

卡顿治理不是一次性的工作。新代码的引入可能带来新的卡顿问题。需要建立持续的监控和告警机制，在卡顿率上升时及时发现和处理。CI/CD中集成帧率测试，防止卡顿退化。

**原则五：数据驱动决策**

卡顿治理的优先级应基于数据决定，而非主观感受。通过线上监控数据确定影响面最大的卡顿问题，集中资源治理Top问题，获得最大的优化收益。

### 9.2 卡顿治理方法论

**第一阶段：建立监控**
1. 搭建帧率监控体系，覆盖核心页面
2. 部署事件循环监控，配合堆栈采样
3. 确定各级别卡顿的阈值标准
4. 建立卡顿数据的采集、存储、分析链路

**第二阶段：摸清家底**
1. 统计各页面/场景的帧率基线
2. 识别Top 10卡顿问题
3. 按卡顿类型分类（IO类、计算类、锁竞争类、布局类）
4. 评估每个问题的影响面和治理成本

**第三阶段：专项治理**
1. 主线程IO治理：将文件IO、SP操作、数据库操作迁移到子线程
2. 布局优化：使用ConstraintLayout扁平化、ViewStub延迟加载、异步inflate
3. 锁竞争优化：减少主线程等待锁的场景，使用无锁数据结构
4. 计算优化：耗时计算移到子线程，结果通过Handler/LiveData回调到主线程

**第四阶段：防劣化**
1. CI/CD集成帧率测试，每次构建自动验证核心页面帧率
2. 线上卡顿率监控，版本对比异常时告警
3. 建立卡顿问题的Review机制，新代码引入的卡顿问题需要限期修复
4. 定期回顾卡顿数据，持续优化

### 9.3 常见误区分析

**疑惑**：卡顿监控和治理中有哪些常见的误区？

**答疑**：以下五个误区在实际工作中经常出现，需要特别警惕。

**论证**：

**误区一：只关注ANR忽略卡顿**

很多团队只在ANR率上升时才开始治理，忽略了卡顿是ANR的前兆。一个200ms的卡顿虽然不会触发ANR，但在低端机或系统负载高时可能变成5秒的ANR。治理卡顿是预防ANR最有效的手段。

**误区二：帧率高就代表不卡**

平均帧率55fps的应用可能存在严重的局部卡顿。如果95%的帧在8ms内完成，但有5%的帧超过200ms，用户体验仍然很差。需要关注帧时间的P95/P99和掉帧分布，而不仅是平均帧率。

**误区三：把所有耗时操作都移到子线程**

将操作移到子线程不一定能解决卡顿。如果子线程完成后需要大量UI更新，主线程仍然会卡顿。如果子线程持有主线程需要的锁，反而会造成主线程等待。正确的做法是减少主线程的总工作量，而非简单地转移。

**误区四：线下没问题就放心了**

开发和测试用的设备通常是中高端机型，线下测试的数据量和使用时长也有限。线上环境中，低端机、大数据量、长时间使用等因素可能暴露出线下未发现的卡顿问题。线上监控是不可或缺的。

**误区五：一次优化后就不管了**

卡顿治理是一个持续的过程。随着业务迭代，新功能的加入可能引入新的卡顿问题。没有防劣化机制的卡顿治理，效果会随着时间逐渐衰减，最终回到治理前的水平。

**结果**：卡顿监控和治理是一个系统工程，需要从监控方案搭建、问题发现、精准定位、专项治理到持续防劣化形成完整闭环。通过帧率监控+事件循环监控+堆栈采样的组合方案覆盖各类卡顿场景，结合线上数据驱动治理优先级，才能持续保证应用的流畅度。


## 10.跨平台卡顿治理对比

### 10.1 各平台卡顿检测机制

| 维度 | Android | iOS | Web |
|------|---------|-----|-----|
| 帧率监控 | Choreographer.FrameCallback | CADisplayLink | requestAnimationFrame |
| 主线程监控 | Looper.Printer/BlockCanary | RunLoop Observer | Long Task API |
| 堆栈采集 | Thread.getStackTrace() | backtrace/NSThread | Error.stack(有限) |
| 系统卡顿 | ANR(5s阈值) | Watchdog Timeout | 无(浏览器管理) |
| 性能工具 | Systrace/Perfetto/GPU渲染 | Instruments/Time Profiler | Chrome Performance |
| 关键指标 | 帧率/掉帧率/ANR率 | 帧率/掉帧率/卡死率 | INP/FID/Long Task |

### 10.2 卡顿治理核心指标

**卡顿指标体系的设计原理**

卡顿治理需要建立一套完整的指标体系，从用户感知层、系统层、代码层三个维度衡量应用的流畅度。不同指标反映不同层面的问题，需要交叉分析才能全面诊断。

```
卡顿指标金字塔：

              ┌──────────────┐
              │  用户体验指标  │ ← 最终目标
              │  (用户可感知)  │
              ├──────────────┤
              │ 系统性能指标   │ ← 技术度量
              │ (帧级别度量)  │
              ├──────────────┤
              │ 代码质量指标   │ ← 根因定位
              │ (方法级别)    │
              └──────────────┘
```

| 指标 | 定义 | 目标值 | 计算方式 | 适用场景 |
|------|------|--------|---------|---------|
| **帧率(FPS)** | 页面交互时的实时帧率 | ≥60fps | Choreographer帧间隔统计 | 滑动/动画场景 |
| **掉帧率** | 帧间隔>16.67ms的帧占比 | <5% | 超时帧数/总帧数 | 综合评估 |
| **严重卡顿率** | 帧间隔>700ms的帧占比 | <0.1% | 冻帧数/总帧数 | 用户可感知卡顿 |
| **ANR率(Android)** | ANR次数/活跃会话数 | <0.01% | ANR信号捕获统计 | 严重阻塞场景 |
| **INP(Web)** | Interaction to Next Paint | <200ms(P75) | PerformanceObserver | Web交互响应 |
| **滑动流畅度** | 滑动过程中的平均帧率 | ≥55fps | 滑动状态下单独统计 | 列表页体验 |
| **页面渲染耗时** | 首帧渲染完成时间 | <300ms | Activity创建到首帧 | 页面打开体验 |

**指标之间的关联分析**：
- FPS<50 + 掉帧率>20% → 持续性卡顿，通常是布局/渲染问题
- FPS正常 + 偶发冻帧 → 间歇性卡顿，通常是主线程IO/锁等待
- ANR率高 + 冻帧率高 → 严重阻塞，可能是死锁/Binder超时


## 11.卡顿项目背景说明

### 11.1 项目背景介绍

- App中卡顿让用户使用体验不佳
  - 在复杂的项目环境中，由于历史代码庞大，业务复杂，包含各种第三方库，所以在出现了卡顿的时候，很难定位到底是哪里出现了问题。
  - 即便知道是哪一个Activity/Fragment，也仍然需要进去里面一行一行看，动辄数千行的类再加上跳来跳去调来调去的，结果就是不了了之随它去了，实在不行了再优化吧。
- 卡顿可能引发未知问题
  - 卡顿还可能会引发一些未知的问题，比如卡顿会造成掉帧，会造成抖动，甚至还会造成ANR，对用户来说体验特别不好。简单来说，就是APP用起来有点卡……
- 排查卡顿问题非常费劲
  - 很多情况下卡顿不是必现的，它们可能与机型、环境、操作等有关，存在偶然性，即使发生了，再去查那如山般的logcat，也不一定能找到卡顿的原因，是我们自己的应用导致的还是其他应用抢占资源导致的？是哪些方法导致的？很难去回溯。

### 11.2 卡顿例子说明

- 卡顿其实分为直观的和微观两个方向的，举个例子
  - 比如用户点击了登录，预期是得到登录成功/失败的反馈，可现在没有页面刷新，实际的刷新耗时超出了预期，这就是直观的卡顿。
  - 比如用户在看股票，正常60秒刷新一次，可到了60秒，触发了刷新但是刷新处理逻辑耗时较长，导致新的数据在下一个60秒之前的第59秒才回来，用户基本无感知，主要说的是内部耗时的问题，这种情况可以粗略的理解为微观卡顿。

**卡顿分类的完整体系**：

| 卡顿类型 | 用户感知 | 持续时间 | 典型场景 | 严重程度 |
|---------|---------|---------|---------|---------|
| 掉帧卡顿 | 画面不流畅 | 17-100ms | 列表滑动、动画 | 低 |
| 交互卡顿 | 点击无响应 | 100-500ms | 按钮点击、页面跳转 | 中 |
| 冻帧卡顿 | 界面冻住 | 500ms-5s | 大图加载、复杂计算 | 高 |
| ANR卡顿 | 弹出对话框 | >5s | 主线程死锁/IO/网络 | 极高 |
| 微观卡顿 | 用户无感知 | 内部耗时异常 | 后台数据处理延迟 | 隐患 |

**真实案例分析**：

```
案例一：RecyclerView 滑动卡顿
  现象：快速滑动商品列表时明显掉帧
  抓取堆栈：onBindViewHolder → ImageLoader.load → DiskCache.get → FileInputStream.read
  根因：图片磁盘缓存命中但读取在主线程执行
  修复：图片加载切到IO线程，占位图先显示
  效果：滑动FPS从42→58

案例二：页面打开冻帧
  现象：从首页跳转到详情页，白屏1.5秒
  抓取堆栈：onCreate → initView → inflateLayout (800ms) → loadData → DB.query (400ms)
  根因：XML布局层级过深(18层) + 主线程数据库查询
  修复：ConstraintLayout扁平化(5层) + 异步加载数据
  效果：打开耗时从1500ms→280ms
```

### 11.3 监控设计目标

- 设计目标要求
  - 对主线程操作进行了完全透明的监控，并能输出有效的信息，帮助开发分析、定位到问题所在，迅速优化应用。
  - 要求接入方便，外部开发者调用简单，非侵入式，简单的两行就打开监控，不需要到处打点，破坏代码优雅性。
  - 精准，输出的信息可以帮助定位到问题所在（精确到行），不需要像Logcat一样，慢慢去找。
- 卡顿优化点分析
  - 如果没能在16ms内完成这个过程，就会使屏幕重复显示上一帧的内容，即造成了卡顿。在这16ms内，需要完成视图树的所有测量、布局、绘制渲染及合成。而我们的优化工作主要就是针对这个过程的。


## 12.卡顿技术要点补充

### 12.1 一帧显示的步骤

- 一帧的显示要经历如下步骤：
  - cpu计算画多大，画在哪里，画什么，然后gpu渲染计算结果存到buffer，显示器每隔一段时间从buffer取帧。若没有取到帧，只能继续显示上一帧。
- 16ms内都需要完成什么？
  - VSync调度、doFrame消息调度、input输入处理、动画、测量/布局、绘制、同步和上传、命令问题、交换缓冲区。也就是我们常用的GPU严格模式。
- 理解双缓冲和三缓冲机制
  - 双缓冲（Double Buffering）：系统使用两个buffer交替工作，一个用于显示（Front Buffer），一个用于绘制（Back Buffer）。绘制完成后交换两个buffer。
  - 三缓冲（Triple Buffering）：在双缓冲基础上增加一个buffer。当CPU/GPU的处理速度跟不上显示器的刷新速度时，三缓冲可以让CPU/GPU不必等待显示器释放buffer，从而提高流水线的并行度。
  - Android 4.1引入了Project Butter（黄油计划），核心改进就是：VSYNC同步信号驱动 + 三缓冲机制 + Choreographer调度框架，大幅提升了渲染流畅度。

### 12.2 卡顿根本原因

- 视图刷新原理：
  - View的requestLayout和ViewRootImpl的setView最终都会调用ViewRootImpl的requestLayout方法，然后通过scheduleTraversals方法向Choreographer提交一个绘制任务，然后再通过DisplayEventReceiver向底层请求vsync垂直同步信号，当vsync信号来的时候，会通过JNI回调回来，通过Handler往消息队列post一个异步任务，最终是ViewRootImpl去执行绘制任务，调用performTraversals方法，完成绘制。
- 卡顿的根本原因：
  - 从刷新原理来看卡顿的根本原理是有两个地方会造成掉帧：
  - 一个是主线程有其它耗时操作，导致doFrame没有机会在vsync信号发出之后16毫秒内调用；
  - 还有一个就是当前doFrame方法耗时，绘制太久，下一个vsync信号来的时候这一帧还没画完，造成掉帧。
  - 从更底层的角度看，卡顿可以归结为三类：CPU瓶颈（主线程任务过重、线程调度延迟）、GPU瓶颈（过度绘制、复杂纹理）和IO瓶颈（主线程磁盘读写、网络请求）。
- 疑惑：为什么有时候CPU和GPU都不忙，但还是会卡顿？
  - 答疑：这种情况通常是由于主线程被锁等待（如synchronized竞争）、Binder调用阻塞（如跨进程通信超时）或者系统调度延迟（如低优先级线程得不到CPU时间片）导致的。这类卡顿从CPU/GPU负载角度看并不明显，需要通过Systrace的CPU调度信息来定位。


## 13.WatchDog卡顿监控

### 13.1 WatchDog监控原理

**核心设计思想——基于"心跳检测"的卡顿感知**

WatchDog（看门狗）方案借鉴了硬件看门狗的设计思想：硬件看门狗要求 CPU 定期"喂狗"（写入特定寄存器），如果超时未喂狗则判定系统挂死并触发重启。软件 WatchDog 同理：

```
WatchDog 工作原理时序图：

监控线程(子线程)                    主线程(UI线程)
    │                                  │
    ├── tick = 0                        │
    ├── post(tick++) ──────────→       │
    │                                  ├── 收到消息, tick = 1
    │← sleep(阈值时间, 如5秒) →│       │
    ├── 检查: tick == 1?               │
    │   是 → 主线程正常                  │
    │                                  │
    ├── tick = 1                        │
    ├── post(tick++) ──────────→       │
    │                                  ├── 主线程卡住!!! 
    │← sleep(5秒) ──────────→│       │   消息无法处理
    ├── 检查: tick == 1?               │   tick 未变化
    │   是(未变化) → 主线程卡顿!!!       │
    ├── 采集主线程堆栈                   │
    └── 上报卡顿信息                     │
```

- 如何监控UI卡顿
  - 启动一个卡顿检测线程，该线程定期的向UI线程发送一条延迟消息，执行一个标志位加1的操作，如果规定时间内，标志位没有变化，则表示产生了卡顿。如果发生了变化，则代表没有长时间卡顿，我们重新执行延迟消息即可。
- 具体的原理说明
  - 不断向UI线程发送Message，每隔一段时间检查一次刚刚发送的Message是否被处理，如果没有被处理，则说明这段时间主线程被卡住了。

### 13.2 WatchDog的优缺点

- 优缺点
  - 优点：简单，稳定，结果论，可以监控到各种类型的卡顿
  - 缺点：轮询不优雅，不环保，有不确定性，随机漏报
- 间隔时间设置
  - 这种方法的轮询的时间间隔选择很重要，又让人左右为难，轮询的时间间隔越小，对性能的负面影响就越大，而时间间隔选择的越大，漏报的可能性也就越大。
- 如何理解性能负面影响
  - UI线程要不断处理我们发送的Message，必然会影响性能和功耗。

### 13.3 如何理解漏报数据

- 时间间隔选择了4秒
  - 事实上，之前是想要通过这种方案来监控ANR，当然，这并不严谨。来分析一下
- 举一个例子
  - 每隔4秒，向主线程发送一个消息。下面是轮训的过程
  - 0秒 ---- 4秒 ---- 8秒 ---- 12秒 ---- 16秒
  - 现在有一个5秒的卡顿发生在第2秒，结束在第7秒，这种情况无论是在0-4秒的周期内，还是4-8秒的周期内，都有一段时间是不卡顿的，消息都可以被处理掉，这种情况自然就无法被监控到。
- 计算监控成功率
  - 计算公式：p = x/a - 1 ；注意条件（a<= x <= 2a）
  - 上面案例计算 ： p = 5/4 - 1 = 0.25 ; 如果轮询间隔设置为4秒，发现一个5秒的卡顿的概率仅为25%。
- 修改轮训间隔时间
  - 默认轮询间隔为5秒，如果有一个8秒的卡顿（8秒已经很容易产生ANR），被发现的概率也只有8/5-1=60%
  - 从这个概率公式还可以发现，对于一个固定的轮询间隔，只有卡顿时间大于两倍的轮询间隔，才能百分之百被监控到。
- 思考把间隔时间缩短
  - 每隔2秒，向主线程发送一个消息。下面是轮训的过程
  - 0秒 -- 2秒 -- 4秒 -- 6秒 -- 8秒 -- 10秒 -- 12秒
  - 现在有一个6秒的卡顿发生在第1秒，结束在第7秒，那么这个在2-4和4-6区间可以捕获到。


## 14.无法监控的卡顿

### 14.1 哪些卡顿无法监控

- 看到queue.next()，这里给了注释：might block
  - 代码直接跟你说这里是可能会卡住的，这时候再计算dispatchMessage方法的耗时显然就没有意义了。
  - 有人可能会想，那改成计算相邻两次dispatchMessage执行之前打印字符串的时间差值不就好了？这样就可以把next方法的耗时也计算在内。
  - 不幸的是，主线程空闲时，也会阻塞在MessageQueue的next方法中，我们很难区分究竟是发生了卡顿还是主线程空闲。
- 分析一下MessageQueue的next方法
  - 是什么原因会卡在MessageQueue的next方法中呢？下面是next方法简化过后的源码：
  ```java
  for (;;) {
      if (nextPollTimeoutMillis != 0) {
          Binder.flushPendingCommands();
      }
      nativePollOnce(ptr, nextPollTimeoutMillis);
      for (int i = 0; i < pendingIdleHandlerCount; i++) {
          final IdleHandler idler = mPendingIdleHandlers[i];
          mPendingIdleHandlers[i] = null;
          boolean keep = false;
          try {
              keep = idler.queueIdle();
          } catch (Throwable t) {
          }
          if (!keep) {
              synchronized (this) {
                  mIdleHandlers.remove(idler);
              }
          }
      }
  }
  ```
- 有这么几类无法监控到
  - View的TouchEvent中的卡顿这种方案是无法监控的
  - IdleHandler的queueIdle()回调方法也是无法被监控的
  - SyncBarrier（同步屏障）的泄漏同样无法被监控到

### 14.2 View的TouchEvent卡顿

- 在MessageQueue的next方法中
  - 除了主线程空闲时阻塞在nativePollOnce之外，非常重要的是，应用的Touch事件也是在这里被处理的。
  - 这就意味着，View的TouchEvent中的卡顿这种方案是无法监控的。
- 那么TouchEvent造成卡顿场景有哪些呢？
  - 在onTouchEvent方法中执行了耗时操作，如复杂的计算、IO操作等。
  - 在自定义View的onTouchEvent中频繁调用invalidate()导致过度重绘。
  - 在GestureDetector的回调方法中执行了大量数据处理逻辑。
  - 嵌套滑动场景下，事件分发链路过长，每一层都需要计算是否拦截，累积耗时导致卡顿。

### 14.3 IdleHandler的queueIdle()

**核心原理——IdleHandler 的执行时机与陷阱**

```
MessageQueue 消息处理流程：

    ┌───── MessageQueue.next() ─────┐
    │                                │
    │  1. 检查消息队列               │
    │     ├── 有到期消息 → 返回执行   │
    │     └── 无到期消息 ↓           │
    │                                │
    │  2. 执行 IdleHandler          │
    │     ├── 遍历 mIdleHandlers    │
    │     ├── 依次调用 queueIdle()  │ ← 在主线程执行！
    │     └── 如果返回false则移除    │
    │                                │
    │  3. nativePollOnce(timeout)    │ ← 阻塞等待新消息
    └────────────────────────────────┘

关键点：queueIdle() 在主线程执行！
        它只是"主线程空闲"时调用，不是"在后台线程"调用！
```

- IdleHandler的queueIdle()回调方法也是无法被监控的（指LooperPrinter方案）
  - 这个方法会在主线程空闲的时候被调用。然而实际上，很多开发同学都先入为主的认为这个时候反正主线程空闲，做一些耗时操作也没所谓。
  - 其实主线程MessageQueue的queueIdle默认当然也是执行在主线程中，所以这里的耗时操作其实是很容易引起卡顿和ANR的。
- 那么queueIdle()造成卡顿场景有哪些呢？
  - 例如App之前就使用IdleHandler在进入主界面后，做一些读写文件的IO操作，就造成了一些卡顿和ANR问题。

**为什么 LooperPrinter 无法监控 IdleHandler**：

LooperPrinter 只在 `Looper.loop()` 中 `msg.target.dispatchMessage()` 前后打印日志。而 IdleHandler 的执行发生在 `MessageQueue.next()` 内部，即"取消息"阶段，不经过 `dispatchMessage()`，自然不会触发 Printer 的回调。

```java
// Looper.loop() 简化流程
for (;;) {
    Message msg = queue.next(); // IdleHandler在这里面执行，Printer看不到！
    printer.println(">>>>> Dispatching");
    msg.target.dispatchMessage(msg);  // Printer只能看到这里
    printer.println("<<<<< Finished");
}
```

### 14.4 SyncBarrier泄漏

- SyncBarrier（同步屏障）的泄漏同样无法被监控到
  - 当我们每次通过invalidate来刷新UI时，最终都会调用到ViewRootImpl中的scheduleTraversals方法，会向主线程的Looper中post一个SyncBarrier，其目的是为了在刷新UI时，主线程的同步消息都被跳过，此时渲染UI的异步消息就可以得到优先处理。
  - 但是注意到这个方法是线程不安全的，如果在非主线程中调用到了这里，就有可能会同时post多个SyncBarrier，但只能remove掉最后一个，从而有一个SyncBarrier就永远无法被remove，就导致了主线程Looper无法处理同步消息（Message默认就是同步消息），导致卡死
- ViewRootImpl源码如下所示
  ```java
  void scheduleTraversals() {
      if (!mTraversalScheduled) {
          mTraversalScheduled = true;
          mTraversalBarrier = mHandler.getLooper().getQueue().postSyncBarrier();
          mChoreographer.postCallback(
                  Choreographer.CALLBACK_TRAVERSAL, mTraversalRunnable, null);
          notifyRendererOfFramePending();
          pokeDrawLockIfNeeded();
      }
  }
  
  void unscheduleTraversals() {
      if (mTraversalScheduled) {
          mTraversalScheduled = false;
          mHandler.getLooper().getQueue().removeSyncBarrier(mTraversalBarrier);
          mChoreographer.removeCallbacks(
                  Choreographer.CALLBACK_TRAVERSAL, mTraversalRunnable, null);
      }
  }
  ```


## 15.监控特殊卡顿场景

### 15.1 监控IdleHandler卡顿

- 首先从简单的下手，对于IdleHandler的queueIdle回调方法的监控。
  - 我们惊喜的发现MessageQueue中的mIdleHandlers是可以被反射的，这个变量保存了所有将要执行的IdleHandler，我们只需要把ArrayList类型的mIdleHandlers，通过反射，替换为MyArrayList，在自定义的MyArrayList中重写add方法，再将自定义的MyIdleHandler添加到MyArrayList中，就完成了"偷天换日"。
  - 从此之后MessageQueue每次执行queueIdle回调方法，都会执行到我们的MyIdleHandler中的queueIdle方法，就可以在这里监控queueIdle的执行时间了。
- 代码如下所示
  ```java
  private static void detectIdleHandler() {
      try {
          MessageQueue mainQueue = Looper.getMainLooper().getQueue();
          Field field = MessageQueue.class.getDeclaredField("mIdleHandlers");
          field.setAccessible(true);
          MyArrayList<MessageQueue.IdleHandler> myIdleHandlerArrayList = new MyArrayList<>();
          field.set(mainQueue, myIdleHandlerArrayList);
      } catch (Throwable t) {
          t.printStackTrace();
      }
  }
  
  static class MyArrayList<T> extends ArrayList {
      Map<MessageQueue.IdleHandler, MyIdleHandler> map = new HashMap<>();
  
      @Override
      public boolean add(Object o) {
          if (o instanceof MessageQueue.IdleHandler) {
              MyIdleHandler myIdleHandler = new MyIdleHandler((MessageQueue.IdleHandler) o);
              map.put((MessageQueue.IdleHandler) o, myIdleHandler);
              return super.add(myIdleHandler);
          }
          return super.add(o);
      }
  
      @Override
      public boolean remove(@Nullable Object o) {
          if (o instanceof MyIdleHandler) {
              MessageQueue.IdleHandler idleHandler = ((MyIdleHandler) o).idleHandler;
              map.remove(idleHandler);
              return super.remove(o);
          } else {
              MyIdleHandler myIdleHandler = map.remove(o);
              if (myIdleHandler != null) {
                  return super.remove(myIdleHandler);
              }
              return super.remove(o);
          }
      }
  }
  ```

### 15.2 监控TouchEvent卡顿

- 那么TouchEvent我们有什么办法监控吗？
  - 首先想到的可能是反射View的mListenerInfo，然后进一步替换其中的mTouchListener，但是这需要枚举所有需要被监控的View，全部反射替换一遍，这完全是不可行的做法。
- 那有没有更加根本，全局性的方法呢？
  - 方案一：Hook InputChannel。Touch事件通过InputChannel从InputDispatcher传递到应用进程，可以通过反射替换InputChannel的fd（文件描述符），在数据到来时先由我们的代码处理，然后再转发给原始的InputChannel。但这种方式比较hack，兼容性风险高。
  - 方案二：Hook Choreographer的FrameCallback。在doFrame回调中记录每帧的Input阶段耗时，当超过阈值时dump堆栈。这种方式可以间接监控到Touch处理的耗时。
  - 方案三：在Application级别设置ViewGroup.OnHierarchyChangeListener监听，为所有添加到视图树的View设置AccessibilityDelegate，通过AccessibilityDelegate可以间接获取到Touch事件的回调时机。
  - 目前业界比较成熟的方案是结合Choreographer和消息队列监控，通过间接方式覆盖Touch事件的耗时监控。

### 15.3 监控SyncBarrier泄漏

- SyncBarrier泄漏监控的核心思路
  - 通过反射获取MessageQueue中的mMessages字段，遍历消息队列中的Message链表。
  - SyncBarrier消息的特征是其target字段为null（正常的Message都有一个非null的target Handler）。
  - 定期检查消息队列，如果发现某个SyncBarrier存在时间超过阈值（如1秒），则认为发生了SyncBarrier泄漏。
- 监控代码核心思路如下
  ```java
  private static void detectSyncBarrierLeak() {
      // 定时检查主线程MessageQueue
      // 反射获取mMessages字段
      // 遍历消息链表，检查target为null的消息（SyncBarrier）
      // 如果SyncBarrier存在超过阈值时间，上报泄漏信息
      // 包括：SyncBarrier的when时间、已存在时长、当前消息队列状态等
  }
  ```
- SyncBarrier泄漏的解决方案
  - 根本原因通常是在非UI线程调用了View的invalidate等方法，触发了scheduleTraversals。
  - 通过StrictMode或自定义Lint规则检查非UI线程调用View方法的情况。
  - 在代码层面确保View操作都在主线程进行，使用View.post()或Handler.post()将操作切到主线程。


## 16.渲染机制卡顿分析

### 16.1 渲染流程中的卡顿点

- View渲染的一生。可以理解为在16.6ms做了那些事情。
- 卡顿的点有哪些呢
  - 渲染机制中的任何流转过程发生异常，均会造成卡顿。逐个分析，看看都会有哪些原因可能造成卡顿。
- 渲染流程中的卡顿分析
  - **Vsync调度**：这个是起始点，但是调度的过程会经过线程切换以及一些委派的逻辑，有可能造成卡顿，但一般可能性比较小，我们也基本无法介入；
  - **消息调度**：主要是doFrame Message的调度，这就是一个普通的Handler调度，如果这个调度被其他的Message阻塞产生了时延，会直接导致后续的所有流程不会被触发。可以通过优化消息调度达到插帧的效果；
  - **input处理**：input是一次Vsync调度最先执行的逻辑，主要处理input事件。如果有大量的事件堆积或者在事件分发逻辑中加入大量耗时业务逻辑，会造成当前帧的时长被拉大；
  - **动画处理**：主要是animator动画的更新，动画数量过多或者动画的更新中有比较耗时的逻辑，也会造成当前帧的渲染卡顿；
  - **view处理**：主要是接下来的三大流程，过度绘制、频繁刷新、复杂的视图效果都是此处造成卡顿的主要原因；
  - **measure/layout/draw**：view渲染的三大流程，因为涉及到遍历和高频执行，所以这里涉及到的耗时问题均会被放大；
  - **DisplayList更新**：这里主要是canvas和displaylist的映射，一般不会存在卡顿问题；
  - **OpenGL指令转换**：将canvas的命令转换为OpenGL的指令，一般不存在问题；
  - **buffer交换**：主要指OpenGL指令集交换给GPU，和指令的复杂度有关；
  - **GPU处理**：耗时主要和任务量和纹理复杂度有关，这也就是降低GPU负载有助于降低卡顿的原因；
  - **layer合成**：主要是layer的compose工作，一般接触不到；
  - **Buffer切换**：主要是屏幕的显示，buffer的数量也会影响帧的整体延迟，不过是系统行为，不能干预。

### 16.2 视频流中的卡顿分析

- 视频流中的卡顿分析
  - 渲染卡顿：主要是TextureView渲染，TextureView跟随window共用一个surface，每一帧均需要一起协同渲染并相互影响；
  - 解码：解码主要是将数据流解码为surface可消费的buffer数据，是除了网络外最重要的耗时点；
  - OpenGL处理：有时会对解码完成的数据做二次处理，如果比较耗时会直接导致渲染卡顿；
  - 网络：包括DNS节点优选、CDN服务、GOP配置等。
- 系统负载
  - 内存：内存的吃紧会直接导致GC的增加甚至ANR，是造成卡顿的一个不可忽视的因素；
  - CPU：CPU对卡顿的影响主要在于线程调度慢、任务执行的慢和资源竞争，比如降频会直接导致应用卡顿；
  - GPU：GPU的影响见渲染流程，但还会间接影响到功耗和发热；
  - 功耗/发热：高功耗会引起高发热，进而会引起系统保护，比如降频、热缓解等，间接导致卡顿。


## 17.卡顿治理流程

### 17.1 排查卡顿流程

- 优化卡顿的步骤
  - 监控卡顿的发生 ---> 准确定位到哪个模块(甚至哪个方法导致了卡) ---> 分析代码并解决卡顿
- 定位到卡顿的点
  - 拿到卡顿堆栈后，需要分析堆栈中的关键信息：
  - 堆栈顶部的方法通常就是造成卡顿的直接原因，比如某个数据库查询、文件IO、复杂计算等。
  - 结合CPU使用率信息，判断是当前App占用CPU过多，还是系统整体CPU负载过高导致的。
  - 结合内存信息，判断是否存在频繁GC（内存抖动）导致主线程被暂停。
  - 结合IO信息，判断是否存在主线程上的IO阻塞。
- 分析代码并解决卡顿
  - UI卡顿：优化布局层级、减少过度绘制、使用ViewStub延迟加载、异步inflate布局。
  - 线程卡顿：将耗时操作移到子线程、优化锁竞争、合理设置线程优先级。
  - 过度绘制卡顿：移除多余的背景色、使用clipRect减少绘制区域、合理使用Canvas.save/restore。
  - 内存抖动卡顿：避免在循环和高频方法中创建对象、使用对象池复用对象、优化数据结构。

### 17.2 制定卡顿指标

- FPS：帧率；取vsync到来的时间为起点，doFrame执行完成的时间为终点，作为每帧的渲染耗时
  - 同时利用渲染耗时/刷新率可以得出每次渲染的丢帧数。平均FPS = 一段时间内渲染帧的个数 * 60 / (渲染帧个数 + 丢帧个数)
- 卡顿指标说明
  - stall_video_ui_rate：总卡顿率；（UI卡顿时长 + 流卡顿时长）/ 采集时长
  - stall_ui_rate：UI卡顿率；【> 3帧】UI卡顿时长 / 采集时长
  - stall_video_rate：流卡顿率；流卡顿时长 / 采集时长
  - stall_ui_slight_rate：轻微卡顿率；【3 - 6】帧丢帧时长 / 采集时长
  - stall_ui_moderate_rate：中等卡顿率；【7 - 13】帧丢帧时长 / 采集时长
  - stall_ui_serious_rate：严重卡顿率；【> 14】帧丢帧时长 / 采集时长
- 疑惑：卡顿率和FPS有什么区别？用哪个指标更好？
  - 答疑：FPS是一个平均值指标，可能掩盖掉短暂的严重卡顿。例如，一秒内前900ms都是60fps，但最后100ms掉帧到10fps，平均FPS可能还是55fps，看起来不错，但用户已经明显感知到了卡顿。
  - 论证：卡顿率是一个事件型指标，记录的是"发生了多少次卡顿"以及"卡顿的严重程度"，更能反映用户的真实体验。
  - 结果：业界的最佳实践是同时关注FPS和卡顿率，FPS用于全局趋势监控，卡顿率（按严重程度分级）用于具体问题定位和治理。
  - 补充说明：除了上述指标，还可以关注"冻帧率"（Frozen Frame Rate），即单帧耗时超过700ms的帧占比。Google Play Console也将冻帧率作为应用质量的重要衡量指标。

### 17.3 建立卡顿治理闭环

- 完整的卡顿治理闭环流程
  - 采集：线上通过多种方案（LooperPrinter+WatchDog+Choreographer）采集卡顿数据。
  - 聚合：将采集到的卡顿堆栈进行去重和聚合，按照TOP N排序。
  - 分派：根据堆栈信息自动识别所属的业务模块，分派给对应的开发人员。
  - 修复：开发人员根据堆栈和辅助信息定位问题，修复卡顿。
  - 验证：修复后通过灰度发布验证效果，对比修复前后的卡顿率变化。
  - 防劣化：在CI流程中加入卡顿检测，防止新代码引入新的卡顿问题。
- 卡顿治理的度量指标
  - 整体卡顿率：所有用户中发生卡顿的占比。
  - 人均卡顿次数：每个用户平均遇到的卡顿次数。
  - TOP N卡顿Issue的修复率：排名前N的卡顿问题的修复完成情况。
  - 卡顿率环比变化：本周/本月的卡顿率相比上一周期的变化。


## 18.卡顿优化实战策略

### 18.1 UI卡顿优化八板斧

- 对于UI卡顿来说，手握卡顿优化的8板大斧子，所向披靡：
  - **下线代码**：直接移除不必要的逻辑，最彻底的优化方式。
  - **减少执行次数**：通过缓存、防抖等手段减少方法的调用频率。
  - **异步**：将耗时操作移到子线程，如IO、复杂计算、网络请求等。
  - **打散**：将大任务拆分成多个小任务，分散到多帧中执行，避免单帧耗时过长。
  - **预热**：提前执行一些初始化操作，将耗时操作前置到用户感知不到的时机。
  - **复用**：使用对象池、缓存等机制复用已有资源，避免重复创建。
  - **方案优化**：从算法和数据结构层面优化，如使用更高效的排序算法、更合适的数据结构。
  - **硬件加速**：利用GPU加速渲染，开启硬件加速Layer等。

### 18.2 UI线程阻塞分析

- 如果UI线程受到阻塞，显而易见的是，Traversal过程也将受阻塞，画面卡顿妥妥发生。这就是为什么一直强调不要在UI线程做耗时操作的原因。通常UI线程的阻塞和以下原因脱不了关系：
  - 在UI线程中进行IO读写数据的操作。这是一个很费时的过程，把IO操作统统放到子线程中去。
  - 在UI线程中进行复杂的运算操作。运算本身是一个耗时的操作，对于十分复杂的运算，对时间的消耗是十分可观的。
  - 在UI线程中进行复杂的数据处理。比如数据的加密、解密、编码等等。这些操作都需要进行复杂运算，特别是在数据比较复杂的时候。
  - 频繁的发生GC，导致UI线程被频繁中断。在Java中，发生GC意味着Stop-The-World，其它线程全部会被暂停。频繁GC的罪魁祸首是内存抖动——短时间内频繁的创建大量对象，导致达到GC的阈值，然后GC就发生了。
- 疑惑：为什么StrictMode能检测到主线程IO但很多人不用？
  - 答疑：StrictMode是Android提供的一个开发工具，可以在检测到主线程IO、网络操作时输出警告甚至崩溃。但它有以下局限：
  - 1.只能在Debug模式下使用，不能带到线上。
  - 2.它只能检测到标准的IO API调用，对于一些底层或第三方库的IO操作无法检测。
  - 3.它会降低应用性能，不适合长期开启。
  - 因此，StrictMode适合在开发阶段作为辅助工具使用，但不能替代线上的卡顿监控系统。

### 18.3 内存抖动与卡顿

- 什么是内存抖动？
  - 是由于短时间内有大量对象进出Young Generation区导致的，它伴随着频繁的GC。在Java内存管理机制中内存抖动会引起频繁的GC，从而使UI线程被频繁阻塞，导致画面卡顿。
- 避免发生内存抖动的几点建议：
  - 尽量避免在循环体内创建对象，应该把对象创建移到循环体外。
  - 注意自定义View的onDraw()方法会被频繁调用，所以在这里面不应该频繁的创建对象。
  - 当需要大量使用Bitmap的时候，试着把它们缓存在数组中实现复用。
  - 对于能够复用的对象，同理可以使用对象池将它们缓存起来。
- 如何定位内存抖动
  - 使用Android Studio的Memory Profiler，观察内存曲线是否呈现锯齿状波动。锯齿状说明内存在频繁分配和回收。
  - 点击Record allocations按钮，记录一段时间内的对象分配情况，然后查看哪些类被频繁创建。
  - 结合堆栈信息定位到具体的代码位置，通常是循环体内、高频回调方法内（如onDraw、onBindViewHolder）创建了临时对象。
- 内存抖动的解决方案
  - 对象池模式：预先创建一组对象，使用时取出，用完归还，避免频繁创建销毁。Android SDK中的Message.obtain()就是典型案例。
  - 局部变量提升为成员变量：将方法内频繁创建的对象提升为类的成员变量，在初始化时创建一次，后续复用。
  - 使用StringBuilder替代字符串拼接：在循环中使用"+"拼接字符串会产生大量中间String对象，改用StringBuilder可以避免。

### 18.4 复杂视图树优化

- 如果视图树复杂，会使整个Traversal过程变长。
  - 因此，在开发过程中要控制视图树的复杂程度。减少不必要的层级嵌套。比如使用RelativeLayout/ConstraintLayout可以减少复杂布局的嵌套。
- 频繁触发requestLayout()
  - 可能会导致在一帧的周期内，频繁的发生布局计算，这也会导致整个Traversal过程变长。
  - 有的ViewGroup类型的控件，比如RelativeLayout，在一帧的周期内会通过两次layout()操作来计算确认子View的位置，这种少量的操作并不会引起能够被注意到的性能问题。
  - 但是如果在一帧的周期内频繁的发生layout()计算，就会导致严重的性能问题，每次计算都是要消耗时间的！
  - requestLayout()操作，会向ViewRootImpl中一个名为mLayoutRequesters的List集合里添加需要重新Layout的View，这些View将在下一帧中全部重新layout()一遍。通常在一个控件加载之后，如果没什么变化的话，它不会在每次的刷新中都重新layout()一次。
  - 需要注意，setLayoutParams()最终也会调用requestLayout()，所以也不能滥用！

### 18.5 自定义View优化策略

- 对于频繁调用的方法，需要尽量减少不必要的代码。先从onDraw开始，需要特别注意不应该在这里做内存分配的事情，因为它会导致GC，从而导致卡顿。在初始化或者动画间隙期间做分配内存的动作。
- 还需要尽可能的减少onDraw被调用的次数，大多数时候导致onDraw都是因为调用了invalidate()。因此请尽量减少调用invalidate()的次数。如果可能的话，尽量调用含有4个参数的invalidate()方法而不是没有参数的invalidate()。没有参数的invalidate会强制重绘整个view。
- 另外一个非常耗时的操作是请求layout。任何时候执行requestLayout()，会使得Android UI系统去遍历整个View的层级来计算出每一个view的大小。如果找到有冲突的值，它会需要重新计算好几次。另外需要尽量保持View的层级是扁平化的。
- onDraw中的性能陷阱总结
  - 不要在onDraw中new对象（Paint、Rect、Path等），应该在构造函数或onSizeChanged中初始化。
  - 不要在onDraw中调用Log.d等日志方法，因为字符串拼接会创建临时对象。
  - 避免在onDraw中进行Bitmap的decode操作。
  - 使用Canvas.clipRect()限制绘制区域，减少不必要的绘制。
  - 如果View只有局部更新，使用invalidate(Rect)而不是invalidate()，只重绘变化的区域。
  - 对于复杂的绘制，考虑使用硬件加速或RenderScript来提升渲染性能。
  - 使用Canvas.saveLayer()时要谨慎，它会创建离屏buffer，内存开销较大。尽量使用View的setLayerType代替。


## 19.卡顿监控方案对比

### 19.1 监控方案综合对比

**各方案在卡顿监控维度上的能力矩阵**：

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| LooperPrinter | 替换主线程Looper的Printer | 精准、无轮询开销 | 无法监控Touch、IdleHandler等 | 线上监控 |
| WatchDog | 定时向主线程发送消息 | 能监控各类卡顿 | 有漏报概率、有轮询开销 | 线上ANR预警 |
| Choreographer | 利用帧回调计算帧率 | 可以直接得到FPS | 只能得到帧率，无法定位原因 | FPS监控 |
| Systrace | 系统级trace | 信息最全面、最准确 | 只能线下使用、学习成本高 | 线下深度分析 |
| CPU Profiler | 采样/插桩方法耗时 | 可以精确到方法级别 | 对性能有一定影响 | 线下定向分析 |

**监控能力覆盖范围对比**：

```
                    Looper  Watch  Choreo  Systrace  Profiler
                    Printer  Dog   grapher
                    
Message耗时           ✓       ✓      ✗        ✓         ✓
帧率统计              ✗       ✗      ✓        ✓         ✗
Touch事件卡顿          ✗       ✓      △        ✓         ✓
IdleHandler卡顿        ✗       ✓      ✗        ✓         ✓
SyncBarrier泄漏        ✗       ✗      ✗        ✓         ✗
精确到方法级           △       ✗      ✗        ✓         ✓
线上可用               ✓       ✓      ✓        ✗         ✗
性能开销               低      中      低       高        高
```

**最佳实践：组合方案**

单一方案都有盲区，业界最佳实践是多方案组合：

```
推荐的线上卡顿监控组合：

┌────────────────────────────────────────┐
│          线上卡顿监控体系               │
├──────────────┬─────────────────────────┤
│ 第一层：帧率  │ Choreographer           │
│ 感知掉帧     │ → 统计FPS/掉帧率         │
├──────────────┼─────────────────────────┤
│ 第二层：定位  │ LooperPrinter           │
│ Message耗时  │ → 定位慢消息             │
├──────────────┼─────────────────────────┤
│ 第三层：兜底  │ WatchDog                │
│ 严重卡顿     │ → 捕获Touch/Idle等盲区   │
├──────────────┼─────────────────────────┤
│ 第四层：堆栈  │ 高频采样+聚合           │
│ 精确归因     │ → 定位到具体方法和行号    │
└──────────────┴─────────────────────────┘
```

### 19.2 卡顿优化最佳实践

- 建立卡顿基线
  - 在优化之前，先建立当前应用的卡顿基线数据，包括：平均FPS、卡顿率、严重卡顿率等。
  - 每次优化后与基线对比，量化优化效果。没有数据支撑的优化是盲目的。

- 分级治理策略
  - P0级（严重卡顿，>700ms）：必须立即修复，通常是主线程执行了IO或网络操作。
  - P1级（中等卡顿，250ms-700ms）：计划修复，通常是复杂的布局计算或大量数据处理。
  - P2级（轻微卡顿，100ms-250ms）：持续优化，通常是可以通过微调改善的问题。

- 防劣化机制
  - 在CI/CD流程中加入自动化性能测试，每次提交代码后自动检测是否引入了新的卡顿问题。
  - 建立卡顿告警机制，当线上卡顿率超过阈值时自动通知相关开发人员。
  - 在代码Review中关注可能引起卡顿的代码模式，如主线程IO、大循环中创建对象等。

### 19.3 卡顿监控技术演进
