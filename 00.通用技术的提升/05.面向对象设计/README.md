## 01.面向对象设计思想

- 2.1 面向过程思想：相信大家都被问过这样一个问题: 把大象装入冰箱需要几步？第一步：打开冰箱；第二步：把大象塞进去；第三步：关上冰箱。
- 2.2 面向过程演变：当需求单一，或者简单时，面向过程还比较好实现！可随着需求的更改，功能的增多，发现需要面对每一个步骤很麻烦了。
- 2.3 面向对象思想：我们可以把大象看作一个对象，冰箱看作一个对象。冰箱的一些功能：开门、装物体、关门。
- 2.4 面向对象思想特点：是一种更符合我们思想习惯的思想，可以将复杂的事情简单化。
- 3.1 面向对象编程，基础概念：有两个非常重要、非常基础的概念，那就是 **类（class）和对象（object）**。
- 3.2 编程语言划分：面向对象按照最简单方式来理解，就是将**对象或类**作为代码组织的基本单元，来进行编程的一种编程范式或者编程风格。
- 3.3 面向对象分析和设计：面向对象分析就是要搞清楚做什么，面向对象设计就是要搞清楚怎么做，面向对象编程就是将分析和设计的的结果翻译成代码的过程。
- 3.4 UML介绍说明：常用它来画图表达面向对象或设计模式的设计思路！
- 4.1 面向对象和过程背景介绍：用面向对象编程语言，编写面向过程风格的代码而已，是否有发挥面向对象编程的优势。
- 4.3 面向过程编程：以过程（可以为理解方法、函数、操作）作为组织代码的基本单元，通过拼接一组顺序执行的方法来操作数据完成一项功能。
- 4.4 面向过程局限性：面向过程的编程范式在小型、简单的项目中可能是高效的，但在面对复杂系统时，其局限性会显现出来。


## 02.面向对象的特性

- **3.什么是封装**：封装也叫作信息隐藏或者数据访问保护。类通过暴露有限的访问接口，授权外部仅能通过类提供的方式（或者叫函数）来访问内部信息或者数据。
- 封装的案例：通过封装一个钱包（包含钱包id，创建时间，余额，存钱时间等属性），隐藏一些属性访问，对外暴露一些api来访问钱包数据，这个就是叫做封装。
- 封装的语法机制是什么：1.要有访问权限控制，比如java中public，private；2.要支持隐藏属性，只能类本身访问，类之外不能直接访问；3.提供公开api暴露获取指定的信息。
- 如果不封装会怎么样：对类中属性的访问不做限制，那任何代码都可以访问、修改类中的属性，过度灵活也意味着不可控。
- 封装的设计意义是什么：封装的设计意义是将实现细节隐藏起来，提供简洁的接口，以提高代码的可维护性、重用性和安全性。
- **4.什么是抽象**：抽象讲的是如何隐藏方法的具体实现，让调用者只需要关心方法提供了哪些功能，并不需要知道这些功能是如何实现的。
- 抽象特性的实现：抽象这个特性是非常容易实现的，并不需要非得依靠接口类或者抽象类这些特殊语法机制来支持。
- 如何理解抽象的机制：开发者可以定义抽象类、接口、函数、模块等，以提供更高级别的抽象。这些抽象可以隐藏底层的复杂性，使代码更易于理解、维护和重用。
- 抽象的意义是什么：抽象的意义是通过隐藏细节和提供概念上的简化，使复杂问题更易理解和处理。
- **5.什么是面向对象之继承**：继承是一种is-a关系，指的是一个类（称为子类、子接口）继承另外的一个类（称为父类、父接口）的功能，并可以增加它自己的新功能的能力。
- 继承设计有什么意义：继承最大的一个好处就是代码复用。不过过度使用继承，继承层次过深过复杂，就会导致代码可读性、可维护性变差。

- **8.什么是面向对象和过程**：
- 面向对象编程是指什么：一种编程范式或编程风格。它以类或对象作为组织代码的基本单元，并将封装、抽象、继承、多态四个特性，作为代码设计和实现的基石 。
- 面向对象编程语言：支持类或对象的语法机制，并有现成的语法机制，能方便地实现面向对象编程四大特性（封装、抽象、继承、多态）的编程语言。
- 什么是面向过程编程：以过程（可以为理解方法、函数、操作）作为组织代码的基本单元，以数据（可以理解为成员变量、属性）与方法相分离为最主要的特点。通过拼接一组顺序执行的方法来操作数据完成一项功能。
- 面向过程的场景：整个程序的处理流程只有一条主线，很容易被划分成顺序执行的几个步骤，然后逐句翻译成代码，这就非常适合采用面向过程这种面条式的编程风格来实现。
- 复杂的程序用面向过程为何吃力：整个程序的处理流程错综复杂，并非只有一条主线，可能是一个网状结构。用面向过程编程这种流程化、线性的思维方式，去翻译这个网状结构，去思考如何把程序拆解为一组顺序执行的方法，就会比较吃力。
- 面向对象编程相比起面向过程编程的优势主要有三个：1.面向对象编程比起面向过程编程，更能应对这种复杂类型的程序开发；2.具有更加丰富的特性；3.更加人性化、更加高级。


## 03.接口vs抽象类比较

- 一些问题的思考：“接口和抽象类的区别是什么？什么时候用接口？什么时候用抽象类？抽象类和接口存在的意义是什么？
- 如何理解抽象的思想：将事物或概念从具体的、特定的细节中抽离出来，关注其普遍性、共性和本质特征的思维方式。
- 什么是抽象类：抽象类用于定义一组抽象方法和可能的具体方法，以提供一种通用的接口和行为，供其子类实现和继承。
- 抽象类案例的理解：提供了一种抽象的概念，用于定义一组相关的类的共同行为和属性。它可以作为一种模板或基类，为子类提供一致的接口和行为，实现代码的复用和多态性。
- 什么是接口：接口是一种抽象的概念，用于定义一组方法的契约，而不涉及具体的实现。接口定义了类应该具有的方法和行为，以提供一种通用的接口，供类来实现。
- 抽象类和接口语法上区别：比如抽象类中可以定义属性、方法的实现，而接口中不能定义属性，方法也不能包含代码实现等等。
- 抽象类和接口设计上区别：抽象类实际上就是类，只不过是一种特殊的类，这种类不能被实例化为对象，只能被子类继承。对于接口，有一个更加形象的叫法，那就是协议（contract）。
- 抽象类主要解决什么问题：是为代码复用而生的。多个子类可以继承抽象类中定义的属性和方法，避免在子类中，重复编写相同的代码。
- 接口主要解决什么问题：接口是对行为的一种抽象，相当于一组协议或者契约，调用者只需要关注抽象的接口，不需要了解具体的实现，具体的实现代码对调用者透明。
- 判断用抽象类和接口的场景：表示一种 is-a 的关系，并且是为了解决代码复用的问题，就用抽象类；表示一种 has-a 关系，并且是为了解决抽象而非代码复用的问题，那就可以使用接口。

## 04.接口而非实现编程

- **什么是基于接口而非实现编程**：代码应该依赖于抽象的概念和契约，而不是具体的实现细节。通过定义接口或抽象类，将具体的实现细节隐藏起来，可扩展和可维护。
- 定义接口主要是解决什么问题：通过定义接口或抽象类，将具体的实现细节隐藏起来，使得代码更加灵活、可扩展和可维护。
- 如何如何理解接口：可以理解为编程语言中的接口或者抽象类。可以将接口和实现相分离，封装不稳定的实现，暴露稳定的接口。
- 设计接口的时候要注意什么：接口的定义只表明做什么，而不是怎么做。要多思考一下，是否能够做到在替换具体的接口实现的时候，不需要任何接口定义的改动。
- 定义接口的场景有哪些：比如数据访问层定义抽象接口可以方便不同数据存储方式；比如依赖注入通过定义接口，可以将依赖关系从具体的实现中解耦出来。
- **定义接口原则是什么**：设计初衷是将接口和实现相分离，封装不稳定的实现，暴露稳定的接口。
- 举一例子知道接口原则重要性：开发一个支付程序，多个支付提供商，例如支付宝、微信支付等，希望能够轻松地切换和添加新的支付提供商，需要用接口编程思想！

## 05.多用组合和少继承

- 1.1 组合优于继承思考：组合优于继承，多用组合少用继承。为什么不推荐使用继承？组合相比继承有哪些优势？如何判断该用组合还是继承？
- 为什么说继承有一些争议：继承有诸多作用，但继承层次过深、过复杂，也会影响到代码的可维护性。所以，对于是否应该在项目中使用继承，网上有很多争议。
- 继承的问题暴露有哪些：继承层次过深、继承关系过于复杂会影响到代码的可读性和可维护性。
- 组合这种思想有什么问题：继承改写成组合意味着要做更细粒度的类的拆分。这也就意味着，我们要定义更多的类和接口。类和接口的增多也就或多或少地增加代码的复杂程度和维护成本。
- 组合替代继承有什么优势：组合替代继承的优势在于提供更大的灵活性和代码重用性，从而实现更灵活的对象关系和更容易的代码重用。





# 封装的设计与实现原理


### 封装解决的三个根本问题

**（1）不变量保护——防止非法状态**

对象内部有些约束必须始终成立，一旦被外部代码破坏，系统进入不可预测状态：

```
栈（Stack）的不变量：
  - top 指向最后入栈元素
  - size >= 0 且 size <= capacity
  - 只能从栈顶操作

没有封装：
  stack.top = -5;        // 不变量被破坏
  stack.data[999] = 42;  // 越界写入
  stack.size = 0;        // 数据还在但size归零 → 数据丢失

有封装：
  stack.push(42);  // 内部检查容量、更新top、维护size
  stack.pop();     // 内部检查非空、返回元素、更新top
  // 所有操作都经过守卫逻辑，不变量永远成立
```

**（2）变更隔离——内部修改不波及外部**

```
版本1: 用数组实现
  class List {
      private int[] data;
      public void add(int x) { data[size++] = x; }
  }

版本2: 改用链表实现
  class List {
      private Node head;
      public void add(int x) { head = new Node(x, head); }
  }

调用方代码：list.add(42);  // 完全不用改

如果 data 是 public → 外部直接操作 data[i]
→ 改成链表时所有外部代码全部崩溃
```

**（3）认知降负——降低使用者的心智负担**

```
HashMap 内部：
  - 桶数组、链表/红黑树转换、哈希扰动函数、负载因子、
    扩容rehash、并发修改检测、序列化兼容……

使用者只需要知道：
  put(key, value)
  get(key)
  remove(key)
  
几千行实现细节被封装成3个方法
```

## 核心原理：信息隐藏（Information Hiding）

David Parnas 在 1972 年提出的**信息隐藏原则**，是封装的理论基础：

> 模块的设计决策应该对其他模块隐藏。每个模块只通过定义良好的接口与外界交互。

**关键区分**：封装 ≠ 访问控制

```
封装（Encapsulation）:
  将数据和操作数据的方法捆绑为一个单元（类/模块/包）
  → 组织结构上的概念

信息隐藏（Information Hiding）:
  隐藏设计决策（数据表示、算法选择、实现策略）
  → 知识管理上的概念

访问控制（Access Control）:
  public/private/protected 等关键字
  → 实现信息隐藏的语法工具

三者关系：
  封装是容器 → 信息隐藏是原则 → 访问控制是工具
```

### 封装的层次

封装不仅存在于类级别，而是一个**多层次的概念**：

```
┌────────────────────────────────────────────────┐
│ 系统层：微服务之间通过 API 交互，内部实现互不可见  │
├────────────────────────────────────────────────┤
│ 模块层：Java module / Go package / C++ namespace│
│         对外导出有限接口，内部类型不可见           │
├────────────────────────────────────────────────┤
│ 类层：private 字段 + public 方法                 │
│       对象的数据表示对外不可见                     │
├────────────────────────────────────────────────┤
│ 函数层：局部变量对外部不可见                       │
│         函数签名是接口，函数体是实现               │
└────────────────────────────────────────────────┘
```

每一层的原理都是相同的：**隐藏实现，暴露接口，降低耦合**。

## 封装与其他面向对象特性的关系

```
封装 → 创造独立单元（有边界的模块）
继承 → 在封装单元之间建立层次关系
多态 → 在封装单元之间建立统一的交互协议

封装是基础，没有封装：
  - 继承无意义（没有"内部"可以复用）
  - 多态无意义（没有"接口"和"实现"的区分）
```

## 技术实现原理

### 1. C++：编译期内存布局 + 名称查找规则

**类的封装在编译期由两个机制实现**：

**（a）内存布局——数据捆绑**

```cpp
class Account {
 private:
    double balance_;
    std::string owner_;
 public:
    void Deposit(double amount);
    double GetBalance() const;
};
```

编译器把字段连续排列在内存中：

```
Account 对象内存布局:
┌──────────────────┐ offset 0
│ balance_ (8字节)  │
├──────────────────┤ offset 8
│ owner_   (32字节) │  ← std::string 的大小（实现相关）
└──────────────────┘

方法不存储在对象中，而是普通函数 + 隐式 this 指针：

Account::Deposit(double amount)
  → 编译为：Deposit(Account* this, double amount)
  → this->balance_ → *(this + 0)  // 直接偏移量访问
```

数据和方法在源码层面是"绑定"的，但在二进制层面，方法就是普通函数，数据就是一块内存。**封装是源码级的组织，不是运行时的机制**。

**（b）访问控制——名称查找规则**

```cpp
Account acc;
acc.balance_;  // 编译错误

// 编译器的处理流程：
// 1. 名称查找：在 Account 类中找到 balance_
// 2. 访问检查：balance_ 是 private，当前上下文不在 Account 类内部
// 3. 拒绝访问 → 编译错误

// 但在二进制层面，balance_ 只是 offset 0 处的8字节
// 用指针算术完全可以访问（未定义行为）：
double* p = reinterpret_cast<double*>(&acc);
*p = 999.0;  // "突破"封装

// → C++ 的封装是编译期君子协定，不是运行时铁笼
```

**头文件的封装缺陷——C++ 独有的问题**：

```cpp
// account.h（公开头文件）
class Account {
 public:
    void Deposit(double amount);
 private:
    double balance_;      // 调用方能"看到"私有成员
    std::string owner_;   // 虽然不能访问，但知道内部结构
};

// 问题：修改 private 字段 → 头文件变了 → 所有 #include 的文件都要重编译
// → 私有实现的变更泄漏到了编译依赖中

// 解决方案：Pimpl（Pointer to Implementation）惯用法
// account.h
class Account {
 public:
    Account();
    ~Account();
    void Deposit(double amount);
 private:
    struct Impl;           // 前向声明，不暴露任何细节
    std::unique_ptr<Impl> impl_;
};

// account.cpp
struct Account::Impl {
    double balance;        // 真正的数据，只在 .cpp 中可见
    std::string owner;
};

// 修改 Impl 内部 → 只重编译 account.cpp → 调用方无需重编译
// → 编译期的信息隐藏达到真正的物理隔离
```

### 2. Java：字节码 access_flags + 反射控制

**编译期**：javac 检查访问权限，与 C++ 类似。

**运行时**：封装信息保留在字节码中，JVM 持续执行检查：

```
.class 文件中每个字段/方法的结构：
field_info {
    u2 access_flags;    // ACC_PRIVATE=0x0002, ACC_PUBLIC=0x0001 ...
    u2 name_index;
    u2 descriptor_index;
    ...
}

JVM 在以下时机检查 access_flags：
1. 类链接（linking）时：验证字段/方法引用的合法性
2. 反射调用时：Field.get() / Method.invoke()
3. 模块访问时：跨模块是否 exports

// 反射可以"打破"封装：
Field f = Account.class.getDeclaredField("balance");
f.setAccessible(true);   // 关闭访问检查
f.getDouble(account);    // 成功读取私有字段

// Java 9+ 模块系统可以阻止 setAccessible：
// 如果模块没有 opens 给反射调用方 → setAccessible 抛异常
// → 模块系统让封装从"可绕过"变为"不可绕过"
```

**与 C++ 的关键区别**：

```
C++: 封装信息在编译后完全丢失，二进制中无任何访问控制
Java: 封装信息保留在字节码中，运行时持续检查

→ Java 的封装更强，但有运行时开销
→ C++ 的封装零开销，但无法防止二进制层面的越界访问
```

### 3. JavaScript：从约定到语言级隔离

**ES5 时代——闭包封装（唯一可靠手段）**：

```javascript
function createAccount(initial) {
    let balance = initial;  // 闭包变量，外部完全不可达

    return {
        deposit(amount) { balance += amount; },
        getBalance() { return balance; }
    };
}

const acc = createAccount(100);
acc.deposit(50);
acc.getBalance();    // 150
acc.balance;         // undefined，根本不存在这个属性
```

**实现原理**：

```
createAccount 执行时创建一个"闭包环境"（Closure Environment）:

环境记录（存在堆上，不在栈上）:
┌─────────────────┐
│ balance: 100    │
└─────────────────┘
       ↑
deposit 函数 ──引用──┘  （函数对象内部持有环境指针）
getBalance 函数 ──引用──┘

外部代码没有任何途径获取这个环境记录的引用
→ balance 是真正的私有，不是约定私有
→ 不可反射、不可遍历、不可访问

这是 JS 中最强的封装，比 class 的 # 字段更早出现
```

**ES2022 `#` 私有字段**：

```javascript
class Account {
    #balance;
    constructor(initial) { this.#balance = initial; }
    deposit(amount) { this.#balance += amount; }
}

const acc = new Account(100);
acc.#balance;  // SyntaxError（不是运行时错误，是语法错误）
```

**实现原理（V8 引擎）**：

```
#balance 不是字符串属性名 "balance"
引擎为每个类的每个 # 字段生成一个唯一的内部 Symbol:

class Account 的 #balance → Symbol("Account.#balance", internal=true)

这个 Symbol:
1. 不可枚举（Object.keys 看不到）
2. 不可被外部代码构造（不是 Symbol('balance')，是引擎内部ID）
3. 只有类定义的词法作用域内的代码知道它的存在

→ 封装通过"信息不对称"实现：你不知道钥匙长什么样，自然打不开锁
```

### 4. Go：包级封装——大小写控制导出

```go
package account

type account struct {      // 小写：包外不可见
    balance float64        // 小写：包外不可见
    Owner   string         // 大写：包外可见
}

func New(owner string) *account {   // 工厂函数
    return &account{Owner: owner}
}

func (a *account) Deposit(amount float64) {  // 大写：包外可见
    a.balance += amount
}
```

**实现原理**：

```
Go 编译器在编译时检查标识符首字母大小写：
  大写开头 → 导出（exported），其他包可访问
  小写开头 → 未导出（unexported），仅当前包可访问

这不是运行时检查，是编译器的符号可见性规则
链接器（linker）中，unexported 的符号不会出现在包的导出表中
→ 其他包的代码在编译时根本找不到这些标识符

Go 没有 class 级别的 private，只有包级别
→ 同一个包内的所有文件互相完全可见
→ 封装的粒度是"包"而不是"类"
```

### 5. Python：名称改写——最弱的封装

```python
class Account:
    def __init__(self):
        self._hint = "convention"    # 单下划线：约定私有
        self.__secret = "mangled"    # 双下划线：名称改写

# Python 解释器在编译字节码时：
# self.__secret → self._Account__secret

acc = Account()
acc._hint           # 能访问（纯约定，无强制）
acc.__secret        # AttributeError（名字不对）
acc._Account__secret  # 能访问（知道规则就行）
```

**为什么 Python 选择不强制封装**：

```
Python 哲学："We are all consenting adults here"
→ 信任开发者的自律，不靠编译器强制

实际原因：
1. Python 是动态语言，属性可以运行时动态添加/删除
2. 强制封装在动态语言中代价极高（每次属性访问都要检查权限）
3. 双下划线的设计目的不是"私有"，而是防止子类意外覆盖同名属性
```

## 封装的代价

| 代价 | 说明 |
|------|------|
| 间接调用开销 | 通过方法访问数据比直接访问多一层函数调用（编译器常可内联消除） |
| 过度封装 | getter/setter 满天飞，增加代码量却没有真正保护不变量 |
| 调试困难 | 过深的封装层次让问题定位变难 |
| Pimpl 代价 | C++ 的编译隔离需要额外堆分配 + 指针间接访问 |

### 好封装 vs 坏封装

```
坏封装（无意义的getter/setter）:
  private int x;
  public int getX() { return x; }
  public void setX(int x) { this.x = x; }
  → 等于没封装，只是多了两层函数调用

好封装（保护不变量 + 隐藏决策）:
  private List<Item> items;
  public void addItem(Item item) {
      if (items.size() >= MAX) throw ...;    // 守卫不变量
      items.add(item);
      totalPrice += item.price();            // 维护派生状态
      notifyObservers();                     // 触发副作用
  }
  → addItem 背后有逻辑，不是简单的赋值
```
