### 1.2 国际化要做什么

- 1、必须要进行资源文件的国际化。这些资源主要是指：文字资源，字体资源【使用默认】，图片资源
- 2、针对特殊的翻译，需要做做适配。语言翻译，可以获取系统local自动配置相关语言。如果app中有语音播放，则音频文件也需要处理
- 3、接口需要做国际化，需要在接口参数中增加字段。看看接口是否需要添加字段用来区分不同的区域。注意：下发数据对应的资源
- 4、组件UI兼容适配。针对一些组件，可能需要做兼容，比如在中文下内容长度合适，但是在其他语言情况下，长度超出，那么可能得做适配。
- 5、国际化时间，时区，根据时区转化时间，时间校验方案

### 1.3 需求分析

功能需求

- **多语言文本支持**：支持中文、英文、日文等多种语言的UI文本显示
- **Key-Value映射**：通过键值对方式管理多语言文本资源
- **默认回退机制**：当指定语言不可用时，自动回退到英文
- **动态语言切换**：运行时可以动态切换语言环境
- **配置持久化**：语言设置可以保存并在重启后恢复

非功能需求

- **扩展性**：支持新增语言，无需修改核心代码
- **可维护性**：配置文件格式简单，易于翻译和维护
- **兼容性**：支持UTF-8编码，兼容各种字符集

### 3.2 语言备选方案

| 格式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| JSON | 结构化，支持嵌套 | 不支持注释，格式严格 | 复杂数据结构 |
| XML | 功能强大，支持验证 | 冗余度高，解析复杂 | 企业级应用 |
| YAML | 可读性好，支持注释 | 解析库依赖，格式敏感 | 配置管理 |
| **Key-Value** | **简单高效，易维护** | **功能有限** | **简单文本资源** |

#### JSON语言配置

**格式示例**：

```json
{
  "activation": {
    "title": "设备激活",
    "scan_prompt": "扫码激活",
    "errors": {
      "network": "网络错误"
    }
  }
}
```

**优点**： 1.结构化数据，支持嵌套；3.广泛支持，标准格式；3.解析必须用成熟的解析库

**缺点**： 1.不支持注释；2.格式严格，容易出错；3.翻译人员不友好

**适用场景**： 1.复杂的数据结构；2.Web应用开发

#### XML语言配置

**格式示例**：

```xml
<resources>
  <string name="activation_title">设备激活</string>
  <string name="scan_to_activate">扫码激活</string>
  <string name="network_error">网络错误</string>
</resources>
```

**优点**：1.功能强大，支持属性和命名空间；2.支持格式验证（XSD）；3.支持注释；4.企业级应用广泛使用

**缺点**：1.冗余度高，文件体积大；2.解析复杂，性能较低；3.需要XML解析库

**适用场景**：1.企业级应用；2.需要严格格式验证的场景；3.Android应用开发


#### YAML语言配置

**格式示例**：

```yaml
# 中文配置
activation:
  title: 设备激活
  scan_prompt: 扫码激活
  errors:
    network: 网络错误
```

**优点**：1.可读性好，支持注释；2.支持复杂数据结构；3.格式相对简洁

**缺点**：1.对缩进敏感，容易出错；2.需要YAML解析库；3.解析性能一般

**适用场景**：1.配置管理；2.DevOps工具；3.复杂配置场景

#### Key-Value语言配置

配置文件格式：Key-Value文本文件

**选择理由**：1.格式简单，易于人工编辑和维护；2.支持注释，便于翻译人员理解上下文；3解析效率高，启动速度快；4版本控制友好

```text
# 中文语言配置文件

scan_to_activate=扫码激活
network_error=网络错误
```

**优点**：1.格式简单，易于理解和编辑；2.支持注释，便于翻译人员理解上下文；3.解析速度快，内存占用小；4.无需额外依赖库

**缺点**：1.不支持嵌套结构；2.不支持数组和复杂数据类型；3.缺乏格式验证机制

**适用场景**：1.简单的文本资源管理；2.嵌入式设备资源受限环境；3.iOS应用语言就是用这种key-value形式。


**Key-Value文本格式，选择理由**：1. 最适合嵌入式设备的资源限制；2.翻译人员友好，维护成本低；3解析性能优异，启动速度快

**LanguageManager 职责**：1.管理当前语言设置；2.加载和缓存语言配置文件；3.提供文本查询接口；4.处理语言切换逻辑

**接口设计**：

```cpp
private:
```

### 3.5 配置文件解析

```cpp
bool LanguageManager::LoadLanguageConfig(const std::string& language_code) {
    std::string config_path = "res/lang/lang_" + language_code + ".txt";
    std::ifstream file(config_path);
    if (!file.is_open()) {
        return false;
    }
    
    text_map_.clear();
    std::string line;
    
    while (std::getline(file, line)) {
        // 跳过注释和空行
        if (line.empty() || line[0] == '#') {
            continue;
        }
        
        // 解析key=value格式
        size_t pos = line.find('=');
        if (pos != std::string::npos) {
            std::string key = line.substr(0, pos);
            std::string value = line.substr(pos + 1);
            
            // 去除首尾空格
            key = Trim(key);
            value = Trim(value);
            
            text_map_[key] = value;
        }
    }
    
    return true;
}
```

### 3.6 文本查询算法

```cpp
std::string LanguageManager::GetText(const std::string& key) const {
    // 1. 在当前语言映射中查找
    auto it = text_map_.find(key);
    if (it != text_map_.end()) {
        return it->second;
    }
    
    // 2. 回退到英文
    if (current_language_ != "en") {
        // 临时加载英文配置进行查找
        auto english_map = LoadEnglishFallback();
        auto en_it = english_map.find(key);
        if (en_it != english_map.end()) {
            return en_it->second;
        }
    }
    
    // 3. 返回键名作为最后回退
    LOG_W("Text not found for key: {}", key);
    return key;
}
```


## 5.国际化时间校验

### 5.1 时区概念介绍

对于时区来说，有着不同标准，比如：GMT和UTC

- 先说结论：在编程领域，我们可以认为两者完全相同。GMT+8 也就是 UTC+8。
- 各地的标态追强准时间为格林威治时间（G.M.T）加上 (+) 或减去 (-) 时区中所标的小时和分钟数时差。

时区（Timezone）是如何理解？

- 大家都知道北京是东八区，可以记作 UTC+8；而美国阿拉斯加是西九区，记作UTC-9。
- UTC 是指“协调世界时”，是一个基准时间。后面跟着的“+n”可以理解为“快了n 个小时“。“-n”同理。所以北京时间比阿拉斯加快了17个小时。
- 一天有 24 小时，所以分为 24 个时区：西十一区到东十二区（UTC-11 到 UTC+12）。


### 5.2 如何获取时区

格式1：GMT+08:00

TimeZone.getDefault().getDisplayName(false, TimeZone.SHORT)

这种是获取GMT时区的方式，但是会存在返回“PST”、“WIB”等别名的时区，这会导致返回格式不统一，解析起来会存在问题。

格式2：+0800

SimpleDateFormat("Z").format(Calendar.getInstance(TimeZone.getTimeZone("GMT"),Locale.getDefault()).time)
- 其实这种格式已经是比较通用，业务上可以直接使用这种方式统一时区格式。

Locale 就是某一个地域内的人们的语言习惯和文化传统和生活习惯。

一个地区的locale就是根据这几大类的习惯定义的。其中暂时只关注这几点：语言、数字、时间、货币、距离。locale有什么属性

- languageTag   普通语言标签
- language      语言
- country       地区
- script        脚本
- variant       变体。变体子标签用于指示附加的、公认的方言，定义一种不被其他子标签代表的语言。比如
- 还有其他属性    其他

```text
获取系统locale的属性 : zh_CN_#Hans
获取系统locale的tag : zh-Hans-CN
获取系统locale的language : zh
获取系统locale的country : CN
获取系统locale的script : Hans
获取系统locale的variant : 

获取系统locale的displayLanguage : 中文
获取系统locale的ISO3Language : zho

```

**获取系统Locale**。系统语言的设置在手机设置页面的语言中选中即可。在应用中如果想要获取到系统当前语言Locale，可以用该方法。

```java
public static Locale getSysLocale() {
    Locale locale;
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.N) {
        locale = Resources.getSystem().getConfiguration().getLocales().get(0);
    } else {
        locale = Resources.getSystem().getConfiguration().locale;
    }
    return locale;
}
```

**应用设置Locale**：是通过context的resource更新的，用`configuration.setLocale`设置，而Application的resource和所有Activity的resource是不同的两个资源对象。

**应用更新Locale**：在获取Locale时，无法保证使用Application的context还是Activity的context，所以需要我们在更新Locale时，将两种context都更新。

```java
public static void updateLocale(Context context, Locale newLocale){
    Configuration configuration = context.getResources().getConfiguration();
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.N){
        configuration.setLocales(new LocaleList(newLocale));
    } else {
        configuration.setLocale(newLocale);
    }
    context.getResources().updateConfiguration(configuration,null);
}
```

假如我们使用Application的context更新Locale时，Activity的context不会同步更新，这就会导致我们在后续使用Activity的context.getString()时，使用的Locale还是之前的Locale，造成错误，反之也是一样。

```java
updateLocale(context,locale)
updateLocale(context.applicationContext,locale)
```

**应用获取Locale**：通过context拿到的Locale应该就是更新后的Locale了。

```java
public static Locale getAppLocale(Context context){
    Locale locale;
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.N) {
        locale = context.getResources().getConfiguration().getLocales().get(0);
    } else {
        locale = context.getResources().getConfiguration().locale;
    }
    return locale;
}
```
