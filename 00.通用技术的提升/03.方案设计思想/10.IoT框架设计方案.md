# IoT 设备管理平台 — 整体设计方案

---

## 一、项目背景

**业务场景**：微信支付线下智能硬件（刷掌支付设备），需要一套完整的 IoT 能力来管理分布在全国/全球各个商户场所的终端设备。

**核心痛点**：
- 设备分散在各地，无法现场维护，需要**远程管理**
- 设备配置需要**云端统一下发**，也需要**本地可修改并同步**
- 设备软件需要**远程升级**（OTA），支持灰度、静默、增量
- 需要感知设备**在线状态、位置、运行健康度**
- 需要向设备**下发指令**（如封禁、重启、恢复出厂）
- 支持**多平台**（Android O1 / Linux O2）、**多地域**（国内/海外）

## 二、整体思路

```
┌──────────────────────────── 云端管控平台 ────────────────────────────┐
│                                                                       │
│   属性管理    OTA管理    指令下发    设备监控    配置管理    数据上报      │
│                                                                       │
└────────┬────────────┬───────────┬──────────┬──────────┬──────────────┘
         │            │           │          │          │
         │       HTTPS/Protobuf + MQTT 推送 + iLink 长连接
         │            │           │          │          │
┌────────▼────────────▼───────────▼──────────▼──────────▼──────────────┐
│                        设备端 IoT Service                              │
│                                                                       │
│  ┌─────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌──────┐ ┌────────┐  │
│  │ Shadow  │ │  OTA   │ │  CMD   │ │ Device │ │ Env  │ │Activate│  │
│  │属性同步  │ │远程升级 │ │指令执行 │ │设备管理 │ │环境上报│ │设备激活 │  │
│  └─────────┘ └────────┘ └────────┘ └────────┘ └──────┘ └────────┘  │
│                                                                       │
│                       IoT SDK（IPC 接口层）                            │
└────────────────────────────┬──────────────────────────────────────────┘
                             │ AIDL / Binder / Protobuf
┌────────────────────────────▼──────────────────────────────────────────┐
│                        业务应用层                                       │
│                                                                       │
│   ┌────────────────┐    ┌──────────────────┐    ┌─────────────────┐  │
│   │  palm-wepay    │    │ palm_activation  │    │  其他业务 App    │  │
│   │ H5设置/刷掌UI  │    │  扫码激活流程     │    │                  │  │
│   └────────────────┘    └──────────────────┘    └─────────────────┘  │
└───────────────────────────────────────────────────────────────────────┘
```

**设计原则**：
1. **服务与业务分离** — IoT Service 作为独立进程运行，业务 App 通过 SDK 接入
2. **模块化** — 按职责拆分独立模块，通过 Proxy 模式解耦
3. **双向属性同步（Shadow）** — 设备属性上报云端 + 云端配置下发设备，解决"远程改配置"核心需求
4. **多通道冗余** — iLink 长连接（国内）+ HTTPS REST（海外）+ MQTT 推送，保证指令可达
5. **安全优先** — SE 安全芯片 + 国密 SM2/SM3 签名 + 设备认证，防伪防篡改

## 三、核心能力模块

| 能力模块 | 解决什么问题 | 关键机制 |
|---------|-------------|---------|
| **Shadow（设备影子）** | 设备与云端属性双向同步 | 版本号冲突检测、批量+实时双模式上报、差分拉取、MQTT 推送+HTTP 轮询兜底 |
| **OTA（远程升级）** | 设备软件远程更新 | 全量/增量升级、灰度发布、静默/弹窗安装、多类型（APK/固件/ROM/插件）|
| **CMD（指令下发）** | 云端远程控制设备 | 双通道拉取（iLink/HTTP）、执行状态上报、指令生命周期管理 |
| **Device（设备管理）** | 设备配置、状态、封禁 | 多属性统一管理、刷掌保护机制、ADB 权限控制、语言/时区同步 |
| **Activate（设备激活）** | 设备首次开机入网 | 扫码激活、SE 密钥交换、业务 App 拉取安装、国内/海外双流程 |
| **Env（环境上报）** | 设备健康监控 | 硬件/位置/运行状态/已装应用定期采集上报 |
| **Recovery（故障恢复）** | 远程修复设备故障 | 远程重启、恢复出厂、日志上传、崩溃监控 |

## 四、Shadow（设备影子）— 核心机制详解

Shadow 是整个 IoT 系统的**灵魂**，理解它就理解了一半系统。

### 4.1 什么是 Shadow

Shadow 是设备在云端的**数字镜像**。无论设备在线还是离线，云端始终维护一份设备的"期望状态"。

```
              ┌─────────────┐
              │   云端 Shadow │ ← 产品经理在管控台修改配置
              │   (期望状态)  │
              └──────┬──────┘
                     │ 下发
              ┌──────▼──────┐
              │  设备端缓存   │ ← 设备本地也有一份
              │  (实际状态)   │
              └─────────────┘
```

### 4.2 两个方向

| 方向 | 术语 | 场景举例 |
|------|------|---------|
| **设备 → 云** | DeviceSideProperty | 设备上报电池电量、软件版本、当前配置 |
| **云 → 设备** | CloudSideProperty | 管控台下发语言切换、ADB 开关、设备封禁 |

### 4.3 属性标识

每个属性由 **三元组** 唯一确定：
- `identifier`：属性名（如 `palm_behavior`、`device_behavior`）
- `scopeType`：作用域（`APP` 级别 / `GLOBAL` 全局）
- `scopeValue`：作用域值（如 `global`、`com.xxx.app`）

### 4.4 同步策略

| 模式 | 时机 | 适用场景 |
|------|------|---------|
| **批量上报** | 每 5 分钟合并上报 | 非紧急属性（版本号、环境信息） |
| **实时上报** | 属性变更立即发送 | 用户操作的配置变更（开关、模式切换） |
| **MQTT 推送** | 云端变更实时推送 | 管控台下发配置 |
| **HTTP 轮询** | 每 60 秒检查差异 | 兜底机制，防止推送丢失 |

## 五、设备生命周期

```
出厂 → 激活 → 正常运行 → 配置变更 → OTA升级 → 故障恢复 → 退役
  │      │        │           │          │          │
  │      │        │           │          │          └→ 恢复出厂/封禁
  │      │        │           │          └→ 静默/弹窗安装
  │      │        │           └→ Shadow 双向同步
  │      │        └→ 心跳保活 + 环境上报
  │      └→ SE密钥交换 + 业务App安装
  └→ ROM预装IoTService + 激活App
```

## 六、多平台支持

| 平台 | 代号 | 技术栈 | 运行环境 |
|------|------|--------|---------|
| Android | O1 | Kotlin/Java + C++ (JNI) | Android 5.0+ |
| Linux | O2 | C++ + D-Bus + Boost | 嵌入式 Linux |

两个平台共享：
- 相同的云端 API（Shadow Server、OTA Server、CMD Server）
- 相同的 Protobuf 协议定义
- 相同的属性模型（`palm_behavior`、`device_behavior` 等）
- 相同的 PaasShadow C++ 核心实现（Android 通过 JNI 桥接）

## 七、安全体系

| 层面 | 机制 | 说明 |
|------|------|------|
| 硬件安全 | SE 安全芯片 | 设备私钥存储在硬件中，不可提取 |
| 设备认证 | SM2 签名 + 设备证书 | 每次请求云端都验证设备身份 |
| 通信安全 | HTTPS + Protobuf | 全链路加密 |
| 应用安全 | priv-app 特权 + 签名校验 | IoTService 预装为系统应用 |
| 防篡改 | 图灵盾 + 设备特征 | 检测设备是否被非法改装 |

## 八、快速落地指引

如果要搭建一个类似的 IoT 设备管理项目，核心工作优先级：

| 优先级 | 工作项 | 交付物 |
|--------|--------|--------|
| P0 | 定义 Shadow 属性模型 | 属性列表 + 三元组 + JSON Schema |
| P0 | 搭建 Shadow Server | 云端属性存储 + 上报/下发 API |
| P0 | 实现设备端 Shadow Client | 属性缓存 + 上报 + 拉取 + 监听 |
| P1 | 设备激活流程 | 扫码激活 + 密钥交换 + 身份绑定 |
| P1 | OTA 升级系统 | 版本管理 + 灰度 + 下载安装 |
| P1 | 设备管控台 | Web 管理后台，查看/修改设备属性 |
| P2 | 指令下发 | CMD 通道 + 执行状态追踪 |
| P2 | 环境上报 | 设备健康度数据采集 |
| P3 | 故障恢复 | 远程重启/恢复出厂/日志抓取 |

## 九、一句话总结

> **IoT Service 是运行在智能硬件上的"设备大脑"，通过 Shadow（数字孪生）实现设备与云端的属性双向同步，通过 OTA 实现远程升级，通过 CMD 实现远程控制，通过 SDK 为业务 App 提供统一接入能力，支撑了微信支付刷掌设备从出厂激活到日常运营的全生命周期管理。**
