# Map 实际应用与设计原理

> 本篇深入剖析 Map 家族中核心实现——HashMap、LinkedHashMap、TreeMap、ConcurrentHashMap、Hashtable 的设计思想、核心原理及实际应用场景，带你由浅入深理解每种 Map 背后的工程取舍。


## 01. 从需求出发：为什么需要多种 Map？

### 1.1 不同场景，不同需求

```
场景A：用户ID → 用户信息 → 快速查找，不关心顺序 → HashMap
场景B：LRU缓存 → 需要按访问顺序排列 → LinkedHashMap
场景C：字典/排行榜 → 需要按key排序 → TreeMap
场景D：高并发计数器 → 多线程安全读写 → ConcurrentHashMap
```

### 1.2 Map 家族全景图

```
                      «interface»
                         Map
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   AbstractMap        SortedMap         Hashtable
        │              «interface»         │
  ┌─────┼─────┐           │           Properties
  │     │     │        NavigableMap
  │     │     │        «interface»
  │     │     │           │
HashMap │  WeakHashMap  TreeMap
  │     │
  │  IdentityHashMap
  │
LinkedHashMap

                ConcurrentHashMap（java.util.concurrent）
```

**核心实现的定位**：

| 实现 | 底层结构 | 有序性 | 线程安全 | Null key/value | 典型场景 |
|------|---------|--------|---------|----------------|---------|
| HashMap | 数组+链表+红黑树 | 无序 | 否 | 允许 | 通用键值存储 |
| LinkedHashMap | HashMap+双向链表 | 插入/访问序 | 否 | 允许 | LRU缓存 |
| TreeMap | 红黑树 | Key自然序 | 否 | 不允许null key | 有序字典 |
| ConcurrentHashMap | 数组+链表+红黑树 | 无序 | 是 | 不允许 | 高并发场景 |
| Hashtable | 数组+链表 | 无序 | 是（synchronized） | 不允许 | 已废弃 |


## 02. HashMap：最核心的 Map 实现

### 2.1 三层架构设计

```
HashMap 的数据结构 = 数组 + 链表 + 红黑树

              0     1     2     3     4     5     6     7
table:    [null] [Node] [null] [Node] [null] [null] [Node] [null]
                  │             │                    │
                 Node          Node                 Node
                  │             │                    │
                 Node          null                TreeNode
                  │                                 / \
                 null                         TreeNode TreeNode

桶为空 → null
冲突少 → 链表（≤8个节点）
冲突多 → 红黑树（>8个节点时转换）
```

### 2.2 核心字段

```java
public class HashMap<K,V> extends AbstractMap<K,V> implements Map<K,V> {
    
    static final int DEFAULT_INITIAL_CAPACITY = 1 << 4;   // 默认容量 16
    static final float DEFAULT_LOAD_FACTOR = 0.75f;        // 默认负载因子
    static final int TREEIFY_THRESHOLD = 8;                // 链表→红黑树阈值
    static final int UNTREEIFY_THRESHOLD = 6;              // 红黑树→链表阈值
    static final int MIN_TREEIFY_CAPACITY = 64;            // 树化的最小表容量
    
    transient Node<K,V>[] table;       // 哈希桶数组
    transient int size;                // 键值对数量
    int threshold;                     // 扩容阈值 = capacity × loadFactor
    final float loadFactor;            // 负载因子
}
```

### 2.3 哈希扰动函数

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

**为什么要将高 16 位异或到低 16 位？**

```
假设 table 大小为 16（常见场景），定位桶用的是：
  index = (n - 1) & hash = 0x0000000F & hash

只有 hash 的低 4 位参与运算！高 28 位完全被忽略。

扰动前：两个 hashCode 只有高位不同的 key 会被映射到同一个桶
  key1.hashCode() = 0xAAAA0001  → index = 1
  key2.hashCode() = 0xBBBB0001  → index = 1  碰撞！

扰动后：高 16 位被混入低 16 位
  h ^ (h >>> 16) 让高位信息参与到低位运算中
  key1: 0xAAAA0001 ^ 0x0000AAAA = 0xAAAAAAAA → index 不同
  key2: 0xBBBB0001 ^ 0x0000BBBB = 0xBBBBBBBA → index 不同

一次异或操作，零成本地将碰撞率大幅降低。
```

### 2.4 put 操作的完整流程

```java
public V put(K key, V value) {
    return putVal(hash(key), key, value, false, true);
}
```

```
put(key, value) 的完整分支：

Step 1: hash = hash(key)  扰动计算
Step 2: index = (n-1) & hash  定位桶

if table[index] == null:
    ➊ 桶为空 → 直接放入新 Node

else if 桶的第一个节点.key == key:
    ➋ 首节点命中 → 更新 value

else if 首节点 instanceof TreeNode:
    ➌ 已经是红黑树 → 红黑树的 putTreeVal

else:  // 链表
    遍历链表：
        ➍ 找到相同 key → 更新 value
        ➎ 未找到 → 尾插法追加新节点
           if 链表长度 >= 8:
              ➏ 链表转红黑树（treeifyBin）

最后：
    if ++size > threshold:
        resize()  // 扩容
```

### 2.5 扩容：容量翻倍 + 链表拆分

```java
// 扩容后每个节点要么在原位置，要么在 原位置+旧容量 的位置
// 只需要看 hash 值的一个 bit 即可判断！

Node<K,V> loHead = null, loTail = null;  // 低位链表（留在原位）
Node<K,V> hiHead = null, hiTail = null;  // 高位链表（移到新位）

do {
    if ((e.hash & oldCap) == 0) {
        // hash 的第 N 位为 0 → 留在原桶
        if (loTail == null) loHead = e; else loTail.next = e;
        loTail = e;
    } else {
        // hash 的第 N 位为 1 → 移到 原桶+oldCap 位置
        if (hiTail == null) hiHead = e; else hiTail.next = e;
        hiTail = e;
    }
} while ((e = next) != null);
```

```
为什么这么巧？因为容量是 2 的幂！

旧容量 16: index = hash & 0b01111 (低4位)
新容量 32: index = hash & 0b11111 (低5位)

唯一的区别就是多看了 hash 的第 5 位（即 oldCap 那一位）。
  第5位 = 0 → 新index = 旧index（留在原位）
  第5位 = 1 → 新index = 旧index + 16（移到新位）

不需要重新计算 hash，一次位运算搞定。
```

### 2.6 实际应用

```java
// 场景1：用户信息缓存
Map<Long, User> userCache = new HashMap<>(1024);  // 预估1000用户，设初始容量

// 场景2：词频统计
Map<String, Integer> wordCount = new HashMap<>();
for (String word : words) {
    wordCount.merge(word, 1, Integer::sum);  // JDK 8 优雅写法
}

// 场景3：分组
Map<String, List<Order>> ordersByCity = orders.stream()
    .collect(Collectors.groupingBy(Order::getCity));
```


## 03. LinkedHashMap：有序的 HashMap

### 3.1 在 HashMap 基础上加"有序链"

LinkedHashMap 继承自 HashMap，在每个 Entry 上额外维护了 `before` 和 `after` 指针：

```java
static class Entry<K,V> extends HashMap.Node<K,V> {
    Entry<K,V> before, after;  // 双向链表指针
    Entry(int hash, K key, V value, Node<K,V> next) {
        super(hash, key, value, next);
    }
}
```

```
HashMap 的视角：
  table[0] → Node → Node → null
  table[3] → Node → null

LinkedHashMap 额外的双向链表（按插入顺序）：
  head ⇄ [Entry A] ⇄ [Entry B] ⇄ [Entry C] ⇄ [Entry D] ⇄ tail
  
  即使 A、B、C、D 散落在不同的桶中，双向链表把它们按插入顺序串起来。
```

### 3.2 两种排序模式

```java
// 模式1：按插入顺序（默认）
Map<String, Integer> insertOrder = new LinkedHashMap<>();
insertOrder.put("banana", 2);
insertOrder.put("apple", 1);
insertOrder.put("cherry", 3);
// 遍历顺序：banana → apple → cherry（插入顺序）

// 模式2：按访问顺序（accessOrder=true）
Map<String, Integer> accessOrder = new LinkedHashMap<>(16, 0.75f, true);
accessOrder.put("banana", 2);
accessOrder.put("apple", 1);
accessOrder.put("cherry", 3);
accessOrder.get("banana");  // 访问 banana，移到尾部
// 遍历顺序：apple → cherry → banana（最近访问的在尾部）
```

### 3.3 用 LinkedHashMap 实现 LRU 缓存

```java
public class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxSize;
    
    public LRUCache(int maxSize) {
        super(maxSize, 0.75f, true);  // accessOrder = true
        this.maxSize = maxSize;
    }
    
    // 核心：当 put 后，HashMap 会回调这个方法问"要不要删除最老的元素"
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize;  // 超过容量就删除最久未访问的
    }
}

// 使用：
LRUCache<String, String> cache = new LRUCache<>(3);
cache.put("a", "1");
cache.put("b", "2");
cache.put("c", "3");
cache.get("a");           // 访问a，a移到尾部
cache.put("d", "4");      // 容量满，淘汰最久未访问的b
// 结果：{c=3, a=1, d=4}
```

**为什么这个实现如此优雅？**

```
LinkedHashMap 已经维护了访问顺序的双向链表。
每次 get/put → 自动将节点移到尾部（最近访问）。
链表头部永远是"最久未访问"的元素。
removeEldestEntry 在 put 后被调用，只需一行判断。

整个 LRU 缓存 = 5 行代码。O(1) get + O(1) put。
```

### 3.4 实际应用

```java
// 场景1：保持配置项顺序（JSON/YAML解析常用）
Map<String, Object> config = new LinkedHashMap<>();
// 保证序列化输出的字段顺序与插入顺序一致

// 场景2：最近浏览记录
LinkedHashMap<String, Long> recentViewed = new LinkedHashMap<>(16, 0.75f, true) {
    protected boolean removeEldestEntry(Map.Entry eldest) {
        return size() > 50;  // 最多保留50条
    }
};

// 场景3：去重且保持顺序
List<String> uniqueOrdered = new ArrayList<>(new LinkedHashSet<>(listWithDuplicates));
```


## 04. TreeMap：红黑树的有序 Map

### 4.1 核心设计

TreeMap 底层是一棵红黑树，所有节点按 key 的自然顺序（或自定义 Comparator）排列：

```java
public class TreeMap<K,V> extends AbstractMap<K,V>
        implements NavigableMap<K,V>, Cloneable, java.io.Serializable {
    
    private final Comparator<? super K> comparator;  // 自定义比较器（可选）
    private transient Entry<K,V> root;                // 红黑树根节点
    private transient int size = 0;
    
    static final class Entry<K,V> implements Map.Entry<K,V> {
        K key;
        V value;
        Entry<K,V> left;
        Entry<K,V> right;
        Entry<K,V> parent;
        boolean color = BLACK;  // 红黑树颜色
    }
}
```

### 4.2 操作复杂度

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| get(key) | O(log N) | 红黑树查找 |
| put(key, value) | O(log N) | 查找 + 插入 + 修复 |
| remove(key) | O(log N) | 查找 + 删除 + 修复 |
| firstKey/lastKey | O(log N) | 沿左/右子树到底 |
| floorKey/ceilingKey | O(log N) | 查找最近的 ≤/≥ 给定key的节点 |

**核心优势**：HashMap 不支持的**范围查询和有序操作**：

```java
TreeMap<Integer, String> scores = new TreeMap<>();
scores.put(95, "Alice");
scores.put(87, "Bob");
scores.put(92, "Charlie");
scores.put(78, "David");
scores.put(99, "Eve");

// HashMap 做不到的操作：
scores.firstKey();                    // 78（最小key）
scores.lastKey();                     // 99（最大key）
scores.subMap(85, 96);                // {87=Bob, 92=Charlie, 95=Alice}
scores.headMap(90);                   // {78=David, 87=Bob}
scores.tailMap(90);                   // {92=Charlie, 95=Alice, 99=Eve}
scores.floorEntry(90);               // 87=Bob（≤90的最大key）
scores.ceilingEntry(90);             // 92=Charlie（≥90的最小key）
scores.descendingMap();               // 逆序视图
```

### 4.3 TreeMap vs HashMap 选型

```
何时用 TreeMap：
  ✅ 需要按 key 排序遍历
  ✅ 需要范围查询（subMap、headMap、tailMap）
  ✅ 需要最近邻查询（floorKey、ceilingKey）
  ✅ 需要第一个/最后一个元素

何时用 HashMap：
  ✅ 只需要 get/put/remove
  ✅ 对顺序没有要求
  ✅ 追求极致性能（O(1) vs O(log N)）
```

### 4.4 实际应用

```java
// 场景1：排行榜（按分数排序）
TreeMap<Integer, List<String>> leaderboard = new TreeMap<>(Comparator.reverseOrder());
leaderboard.computeIfAbsent(95, k -> new ArrayList<>()).add("Alice");

// 场景2：区间查找（如价格区间筛选）
TreeMap<Double, Product> priceIndex = new TreeMap<>();
// 查找 100~500 价格区间的商品
Map<Double, Product> range = priceIndex.subMap(100.0, 500.0);

// 场景3：时间线（按时间排序的事件）
TreeMap<LocalDateTime, Event> timeline = new TreeMap<>();
// 查找某个时间点之后的所有事件
Map<LocalDateTime, Event> future = timeline.tailMap(LocalDateTime.now());

// 场景4：IP 路由表（查找最匹配的路由规则）
TreeMap<Long, String> routeTable = new TreeMap<>();
// floorEntry 找到 ≤ 给定IP 的最大网段
```


## 05. ConcurrentHashMap：高并发的工业级 Map

### 5.1 为什么需要 ConcurrentHashMap？

```java
// HashMap 在多线程下的致命问题（JDK 7）：
// 两个线程同时 put 触发扩容 → 链表形成环 → get 操作死循环 → CPU 100%

// 简单加锁的方案：
Map<K,V> syncMap = Collections.synchronizedMap(new HashMap<>());
// 问题：所有读写操作共用一把大锁，完全串行化
// 100个线程读，也要排队 → 性能灾难
```

### 5.2 JDK 7：分段锁设计

```
JDK 7 的 ConcurrentHashMap 结构：

ConcurrentHashMap
  └── Segment[0..15]     （16个段，每段一把锁）
        ├── Segment[0] → HashEntry[] table
        │     lock
        ├── Segment[1] → HashEntry[] table
        │     lock
        └── ...

并发度 = Segment 数量（默认16）
线程A写Segment[3]，线程B写Segment[7] → 互不影响
线程A写Segment[3]，线程C读Segment[3] → 读无锁（volatile）
线程A写Segment[3]，线程D写Segment[3] → 竞争同一把锁
```

### 5.3 JDK 8：CAS + synchronized 细粒度锁

JDK 8 完全重构了 ConcurrentHashMap，放弃分段锁，改用更细粒度的锁：

```java
// JDK 8 的核心思路：锁的粒度从 Segment（段）缩小到 Node（桶）

// put 操作（简化版）：
final V putVal(K key, V value, boolean onlyIfAbsent) {
    int hash = spread(key.hashCode());
    
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();                     // CAS 初始化
            
        else if ((f = tabAt(tab, i = (n-1) & hash)) == null) {
            // 桶为空：CAS 放入新节点（无锁！）
            if (casTabAt(tab, i, null, new Node<>(hash, key, value, null)))
                break;
        }
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);            // 协助扩容
            
        else {
            // 桶不为空：锁住这个桶的头节点
            synchronized (f) {                     // 只锁一个桶！
                if (tabAt(tab, i) == f) {          // 双重检查
                    // 链表或红黑树的插入逻辑
                }
            }
        }
    }
    addCount(1L, binCount);
    return null;
}
```

**JDK 7 vs JDK 8 对比**：

| 维度 | JDK 7 分段锁 | JDK 8 CAS+synchronized |
|------|-------------|----------------------|
| 锁粒度 | Segment（含多个桶） | 单个桶（Node） |
| 最大并发度 | 16（固定） | 等于桶数量（动态增长） |
| 读操作 | volatile 无锁 | volatile 无锁 |
| 空桶写入 | 需要获取段锁 | CAS 无锁 |
| 非空桶写入 | 段锁 | synchronized 桶头节点 |
| 内存 | 16个Segment对象 | 无额外对象 |

### 5.4 size() 的精巧实现

```java
// 问题：在高并发下准确统计 size 非常困难
// 如果用 AtomicLong，所有线程竞争一个变量 → 性能瓶颈

// JDK 8 方案：借鉴 LongAdder 的分散计数
// baseCount + CounterCell[] 分散统计
private transient volatile long baseCount;
private transient volatile CounterCell[] counterCells;

// 低竞争：直接 CAS 更新 baseCount
// 高竞争：每个线程更新自己的 CounterCell，最后求和
public int size() {
    long n = sumCount();  // baseCount + Σ counterCells[i].value
    return ((n < 0L) ? 0 : (n > Integer.MAX_VALUE) ? Integer.MAX_VALUE : (int)n);
}
```

### 5.5 实际应用

```java
// 场景1：高并发计数器
ConcurrentHashMap<String, LongAdder> metrics = new ConcurrentHashMap<>();
// 多线程安全地递增
metrics.computeIfAbsent("api.calls", k -> new LongAdder()).increment();

// 场景2：缓存（带原子性计算）
ConcurrentHashMap<String, User> cache = new ConcurrentHashMap<>();
User user = cache.computeIfAbsent(userId, id -> loadFromDB(id));
// computeIfAbsent 保证原子性：只会调用一次 loadFromDB

// 场景3：线程安全的 Set
Set<String> concurrentSet = ConcurrentHashMap.newKeySet();
concurrentSet.add("item1");

// 场景4：批量并行操作（JDK 8+）
cache.forEach(4, (key, value) -> {  // 并行度=4
    process(key, value);
});
long count = cache.reduceValuesToLong(4, User::getAge, 0L, Long::sum);
```


## 06. Hashtable：历史遗留，了解即可

### 6.1 与 HashMap 的核心差异

```java
// Hashtable 的特点：
// 1. 方法级 synchronized（和 Vector 一样的问题）
public synchronized V put(K key, V value) {
    if (value == null) throw new NullPointerException();  // 不允许null值
    // ...
}

// 2. 不允许 null key 和 null value
// 3. 初始容量 11，扩容 2N+1（不是2的幂）
// 4. hash 计算直接用 hashCode()，不做扰动
```

| 对比 | HashMap | Hashtable |
|------|---------|-----------|
| 线程安全 | 否 | 是（synchronized） |
| null key | 允许1个 | 不允许 |
| null value | 允许 | 不允许 |
| 初始容量 | 16 | 11 |
| 扩容 | 2倍 | 2N+1 |
| 哈希计算 | 扰动函数 | 直接 hashCode |
| 推荐 | ✅ | ❌ 已废弃 |

**一句话总结**：Hashtable 之于 ConcurrentHashMap，就像 Vector 之于 ArrayList——历史遗留，请勿使用。


## 07. 特殊用途 Map

### 7.1 WeakHashMap：自动清理的缓存

```java
// WeakHashMap 的 key 是弱引用，当 key 没有其他强引用时，GC 会自动回收
WeakHashMap<Object, String> cache = new WeakHashMap<>();

Object key1 = new Object();
cache.put(key1, "data1");
System.out.println(cache.size());  // 1

key1 = null;  // 去掉强引用
System.gc();   // 触发 GC
System.out.println(cache.size());  // 0（key 被回收，entry 也被清除）
```

**适用场景**：类元数据缓存、ClassLoader 关联数据、ThreadLocal 的底层实现。

### 7.2 IdentityHashMap：用 == 代替 equals

```java
// 普通 HashMap：用 equals() 判断 key 相等
// IdentityHashMap：用 == （引用相等）判断 key 相等

IdentityHashMap<String, Integer> map = new IdentityHashMap<>();
String s1 = new String("hello");
String s2 = new String("hello");

map.put(s1, 1);
map.put(s2, 2);
System.out.println(map.size());  // 2！（普通 HashMap 会是1）
// 因为 s1 != s2（不同对象），虽然 s1.equals(s2)
```

**适用场景**：序列化框架中追踪对象引用、拓扑排序中标记已访问节点。

### 7.3 EnumMap：枚举专用极致性能

```java
// EnumMap 内部用数组实现，下标就是 enum.ordinal()
EnumMap<DayOfWeek, String> schedule = new EnumMap<>(DayOfWeek.class);
schedule.put(DayOfWeek.MONDAY, "会议");
schedule.put(DayOfWeek.FRIDAY, "周报");

// 内部实现极其简单高效：
// Object[] vals = new Object[keyUniverse.length];
// put: vals[key.ordinal()] = value;   → O(1)，无哈希计算
// get: return vals[key.ordinal()];    → O(1)，无哈希计算
```


## 08. 全面对比与选型指南

### 8.1 性能对比

| 操作 | HashMap | LinkedHashMap | TreeMap | ConcurrentHashMap |
|------|---------|---------------|---------|-------------------|
| get | O(1) | O(1) | O(log N) | O(1) |
| put | O(1) | O(1) | O(log N) | O(1) |
| remove | O(1) | O(1) | O(log N) | O(1) |
| 有序遍历 | ❌ | 插入/访问序 | Key排序 | ❌ |
| 范围查询 | ❌ | ❌ | ✅ | ❌ |
| 并发安全 | ❌ | ❌ | ❌ | ✅ |

### 8.2 选型决策树

```
你的需求是什么？
  │
  ├── 需要按 key 排序 / 范围查询？
  │     └── 是 → TreeMap
  │
  ├── 需要保持插入顺序？
  │     └── 是 → LinkedHashMap
  │
  ├── 需要 LRU 缓存？
  │     └── 是 → LinkedHashMap(accessOrder=true) + removeEldestEntry
  │
  ├── 需要线程安全？
  │     ├── 高并发 → ConcurrentHashMap ✅
  │     └── 简单场景 → Collections.synchronizedMap
  │
  ├── key 是枚举类型？
  │     └── 是 → EnumMap（极致性能）
  │
  └── 通用场景
        └── HashMap ✅
```

### 8.3 跨语言对比

| 语言 | 无序Map | 有序Map | 并发Map | 特殊Map |
|------|---------|---------|---------|--------|
| Java | HashMap | TreeMap / LinkedHashMap | ConcurrentHashMap | WeakHashMap, EnumMap |
| Go | map | 无内置（需 btree 库） | sync.Map | 无 |
| Python | dict (3.7+有序) | 无内置（SortedDict） | 无内置 | WeakValueDictionary |
| Rust | HashMap | BTreeMap | DashMap (第三方) | 无 |
| C++ | unordered_map | map (红黑树) | concurrent_unordered_map (TBB) | 无 |
| Swift | Dictionary | 无内置 | 无内置（需加锁） | NSMapTable |

**Go 的独特设计**：Go 的 map 迭代顺序是**故意随机化**的，每次运行都不一样。这是为了防止开发者依赖迭代顺序。


## 思考题

> 以下问题由浅入深，建议先独立思考再查阅资料。

**1. 基础理解**：HashMap 允许 null key（最多一个），TreeMap 不允许 null key。请从底层实现原理解释为什么——HashMap 如何处理 null key 的哈希值？TreeMap 为什么无法处理？

**2. 设计分析**：LinkedHashMap 的 `removeEldestEntry` 方法在每次 `put` 之后被调用。如果一次性 `putAll` 100 个元素，这个方法会被调用多少次？如果 maxSize=10，最终 Map 中有多少个元素？

**3. 并发深入**：ConcurrentHashMap 的 `computeIfAbsent` 是原子操作，但以下代码仍然有并发问题，为什么？
```java
if (!map.containsKey(key)) {
    map.put(key, computeValue(key));
}
```
如何用 `computeIfAbsent` 解决？它的原子性是如何实现的？

**4. 性能陷阱**：在一个有 1000 万条数据的 HashMap 中，如果所有 key 的 `hashCode()` 都返回相同的值，get 操作的时间复杂度是多少？JDK 8 之前和之后有什么区别？如何防御这种 HashDoS 攻击？

**5. 架构思考**：设计一个支持"过期时间"的 Map（类似 Redis 的 EXPIRE）：`put(key, value, ttl)` 存入数据并设置过期时间，`get(key)` 读取时自动清除过期数据。请设计数据结构，分析惰性删除和定时删除两种清理策略的优缺点。
