# List 实际应用与设计原理

> 本篇深入剖析 List 家族中四大核心实现——ArrayList、Vector、LinkedList、CopyOnWriteArrayList 的设计思想、核心原理及实际应用场景，带你由浅入深理解每种实现背后的工程取舍。


## 01. 从需求出发：为什么需要多种 List？

### 1.1 一个问题引出所有矛盾

假设你正在开发一个系统，有以下四个不同的场景：

```
场景A：商品列表展示 → 频繁读取，偶尔追加，极少删除
场景B：多线程计数器 → 多线程同时往列表中追加数据
场景C：消息队列双端操作 → 需要头部插入、尾部删除
场景D：配置中心热更新 → 读远多于写，写的时候不能阻塞读
```

**一种 List 能搞定所有场景吗？** 不能。每种场景对性能、线程安全、内存的侧重点完全不同。这就是 Java 集合框架设计多种 List 实现的根本原因——**没有银弹，只有针对特定场景的最优解**。

### 1.2 List 家族全景图

```
                         «interface»
                           List
                            │
           ┌────────────────┼────────────────┐
           │                │                │
      AbstractList    AbstractSequentialList   │
           │                │                │
     ┌─────┼─────┐         │                │
     │     │     │     LinkedList            │
ArrayList  │   Vector                        │
           │     │                           │
           │  Stack(已废弃)     CopyOnWriteArrayList
           │
    SubList(内部类)
```

**四大核心实现的定位**：

| 实现 | 底层结构 | 线程安全 | 核心优势 | 典型场景 |
|------|---------|---------|---------|---------|
| ArrayList | 动态数组 | 否 | 随机访问 O(1) | 单线程读多写少 |
| Vector | 动态数组 | 是（synchronized） | 方法级同步 | 已废弃，历史遗留 |
| LinkedList | 双向链表 | 否 | 头尾操作 O(1) | 队列/双端队列 |
| CopyOnWriteArrayList | 不可变数组快照 | 是（COW） | 读无锁 O(1) | 读多写极少 |


## 02. ArrayList：动态数组的工业级实现

### 2.1 核心设计思想

ArrayList 的设计哲学可以用一句话概括：**用连续内存换取 O(1) 随机访问，用均摊策略消化扩容成本**。

```java
public class ArrayList<E> extends AbstractList<E>
        implements List<E>, RandomAccess, Cloneable, java.io.Serializable {
    
    // 核心：底层就是一个 Object 数组
    transient Object[] elementData;
    
    // 实际元素个数（不是数组长度！）
    private int size;
}
```

**两个关键区分**：
- `elementData.length`：数组容量（capacity），是已分配的内存空间
- `size`：实际元素数量，`size <= elementData.length`

### 2.2 延迟初始化：不用不分配

```java
// JDK 8+ 的空数组常量
private static final Object[] DEFAULTCAPACITY_EMPTY_ELEMENTDATA = {};

// 无参构造器 —— 并不会立即分配大小为10的数组！
public ArrayList() {
    this.elementData = DEFAULTCAPACITY_EMPTY_ELEMENTDATA;
}
```

**为什么要延迟初始化？**

```
场景：代码中有 100 个 ArrayList 字段，但运行时只有 20 个会被使用。

JDK 7：new ArrayList() → 立即分配 10 个位置的数组 → 80个白白浪费内存
JDK 8+：new ArrayList() → 空数组 → 第一次 add 时才分配 → 80个零成本

在 Android 这样内存敏感的环境中，这个优化效果尤为显著。
```

### 2.3 扩容机制：1.5 倍增长的数学之美

```java
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    // 核心公式：新容量 = 旧容量 + 旧容量/2 = 1.5倍
    int newCapacity = oldCapacity + (oldCapacity >> 1);
    if (newCapacity - minCapacity < 0)
        newCapacity = minCapacity;
    if (newCapacity - MAX_ARRAY_SIZE > 0)
        newCapacity = hugeCapacity(minCapacity);
    elementData = Arrays.copyOf(elementData, newCapacity);
}
```

**为什么是 1.5 倍而不是 2 倍？**

这不是拍脑袋决定的，背后有严谨的数学分析：

```
假设初始容量为 C，2 倍增长：
  C → 2C → 4C → 8C → 16C
  
当从 8C 扩容到 16C 时，之前释放的内存总量：
  C + 2C + 4C + 8C = 15C < 16C
  
问题：新数组永远无法复用之前释放的内存块！
因为之前所有释放的内存加起来 < 新需要的内存。

1.5 倍增长：
  C → 1.5C → 2.25C → 3.375C → 5.0625C → 7.59C
  
当从 5.06C 扩容到 7.59C 时，之前释放的内存总量：
  C + 1.5C + 2.25C + 3.375C + 5.0625C = 13.1875C > 7.59C ✓
  
几轮之后，新数组可以复用之前释放的内存，对内存分配器更友好。
```

**均摊复杂度证明**（记账法）：

```
给每个 add 操作"预收"3个单位的工作量：
  - 1个单位：执行当前的插入操作
  - 2个单位：存入"银行"，用于将来扩容时的复制

当容量从 N 扩到 1.5N 时，需要复制 N 个元素。
这 N 个元素的扩容费用，由它们之前积累的"银行存款"支付。
从上次扩容以来新增了 N/2 个元素，每个存了2个单位 = N单位。
正好覆盖 N 次复制的成本。

因此，每次 add 的均摊成本 = 3 = O(1) ✓
```

### 2.4 增删改查的完整流程

**添加元素（尾部追加）**：

```java
public boolean add(E e) {
    ensureCapacityInternal(size + 1);  // 检查容量，必要时扩容
    elementData[size++] = e;           // 放入元素，size+1
    return true;
}
// 时间复杂度：均摊 O(1)
```

**添加元素（指定位置插入）**：

```java
public void add(int index, E element) {
    rangeCheckForAdd(index);                           // 边界检查
    ensureCapacityInternal(size + 1);                  // 容量检查
    System.arraycopy(elementData, index,               // 核心：后移元素
                     elementData, index + 1, size - index);
    elementData[index] = element;                      // 插入新元素
    size++;
}
// 时间复杂度：O(N)，因为需要移动 size-index 个元素
```

```
插入前：[A, B, C, D, E, _, _]   size=5, 在 index=2 插入 X
                                 
Step 1 arraycopy：[A, B, C, C, D, E, _]  把 index=2 开始的元素后移1位
Step 2 赋值：     [A, B, X, C, D, E, _]  在 index=2 放入 X
Step 3 size++：   size=6
```

**删除元素**：

```java
public E remove(int index) {
    rangeCheck(index);
    modCount++;                                        // fail-fast 计数
    E oldValue = elementData(index);
    int numMoved = size - index - 1;
    if (numMoved > 0)
        System.arraycopy(elementData, index + 1,       // 前移元素
                         elementData, index, numMoved);
    elementData[--size] = null;  // 关键：置null，让GC回收！
    return oldValue;
}
```

**为什么要显式置 null？**

```java
// 如果不置 null：
elementData = [A, B, C, D, E]  删除 index=2 (C)
→ elementData = [A, B, D, E, E]  size=4
// 最后一个 E 虽然逻辑上不存在了，但数组仍然持有它的引用
// 垃圾回收器无法回收这个对象 → 内存泄漏！

// 置 null 后：
→ elementData = [A, B, D, E, null]  size=4
// null 引用，GC 可以正常回收 ✓
```

### 2.5 RandomAccess 标记接口的工程智慧

```java
public class ArrayList<E> implements RandomAccess { ... }
```

`RandomAccess` 是一个空接口（标记接口），没有任何方法。它的作用是给算法一个"提示"：

```java
// Collections.binarySearch 的实现
public static <T> int binarySearch(List<? extends Comparable<? super T>> list, T key) {
    if (list instanceof RandomAccess || list.size() < BINARYSEARCH_THRESHOLD)
        return Collections.indexedBinarySearch(list, key);   // 用 get(i) 随机访问
    else
        return Collections.iteratorBinarySearch(list, key);  // 用迭代器顺序访问
}
```

**为什么需要这个标记？**

```
ArrayList.get(i)   → O(1)  → 二分查找总共 O(log N)
LinkedList.get(i)  → O(N)  → 二分查找退化为 O(N log N) ！

有了 RandomAccess 标记，算法可以自动选择最优策略。
这是"策略模式"在集合框架中的巧妙应用。
```

### 2.6 实际应用场景

```java
// 场景1：数据展示列表（最常见）
List<Product> products = new ArrayList<>();
products.add(new Product("iPhone", 9999));
Product p = products.get(0);  // O(1) 随机访问

// 场景2：预知大小时设置初始容量
List<String> lines = new ArrayList<>(10000);  // 避免多次扩容

// 场景3：批量数据处理
list.forEach(item -> process(item));  // 顺序遍历，缓存友好

// 场景4：排序（数组的缓存局部性使排序极快）
Collections.sort(products, Comparator.comparing(Product::getPrice));
```


## 03. Vector：同步 List 的历史遗产

### 3.1 Vector 的诞生与定位

Vector 是 JDK 1.0 就存在的类，比 ArrayList（JDK 1.2）早了两个版本。它的设计目标很简单：**一个线程安全的动态数组**。

```java
public class Vector<E> extends AbstractList<E>
        implements List<E>, RandomAccess, Cloneable, java.io.Serializable {
    
    protected Object[] elementData;  // 与 ArrayList 一样的底层数组
    protected int elementCount;       // 相当于 ArrayList 的 size
    protected int capacityIncrement;  // 扩容增量（ArrayList 没有）
}
```

### 3.2 与 ArrayList 的核心差异

**差异一：方法级 synchronized**

```java
// Vector 的 add 方法
public synchronized boolean add(E e) {   // ← 注意 synchronized
    modCount++;
    ensureCapacityHelper(elementCount + 1);
    elementData[elementCount++] = e;
    return true;
}

// ArrayList 的 add 方法
public boolean add(E e) {                 // ← 没有 synchronized
    ensureCapacityInternal(size + 1);
    elementData[size++] = e;
    return true;
}
```

**差异二：扩容策略不同**

```java
// Vector 的扩容：默认 2 倍（或自定义增量）
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + 
        ((capacityIncrement > 0) ? capacityIncrement : oldCapacity);  // 2倍！
    // ...
}

// ArrayList：1.5 倍
int newCapacity = oldCapacity + (oldCapacity >> 1);  // 1.5倍
```

**对比总结**：

| 对比维度 | ArrayList | Vector |
|---------|-----------|--------|
| 线程安全 | 否 | 是（synchronized） |
| 扩容倍数 | 1.5倍 | 2倍（或自定义增量） |
| 性能 | 高 | 低（锁开销） |
| 迭代器 | fail-fast | fail-fast |
| 引入版本 | JDK 1.2 | JDK 1.0 |
| 推荐使用 | ✅ | ❌ 已过时 |

### 3.3 为什么 Vector 被废弃？

**问题一：粗粒度锁导致性能差**

```java
// Vector 的每个方法都加了 synchronized
// 即使是"先读后写"这样的复合操作，也需要在外部额外加锁

// 这段代码 NOT 线程安全！
if (!vector.contains(element)) {  // 读操作加锁释放
    vector.add(element);          // 写操作加锁释放
}                                 // 两个操作之间锁被释放了！

// 正确做法：外部加锁
synchronized (vector) {
    if (!vector.contains(element)) {
        vector.add(element);
    }
}
// 既然还要外部加锁，Vector 内部的 synchronized 就是白白浪费性能
```

**问题二：全部方法加锁 = 读写互斥**

```
线程A: get(0)  加锁 → 读取 → 释放锁
线程B: get(1)  等待A释放锁 → 加锁 → 读取 → 释放锁

两个纯读操作居然也互斥了！这在读多写少场景下完全不可接受。
```

**问题三：Stack 继承自 Vector，设计有缺陷**

```java
public class Stack<E> extends Vector<E> {
    public E push(E item) { ... }
    public E pop() { ... }
    public E peek() { ... }
}
// 问题：Stack 继承了 Vector 的所有方法
// 你可以对 Stack 调用 add(0, elem)、remove(2) 等破坏栈语义的操作！
// 这违反了"里氏替换原则"——子类不应该暴露父类不该有的行为
```

### 3.4 现代替代方案

```java
// 替代方案1：Collections.synchronizedList（简单包装）
List<String> syncList = Collections.synchronizedList(new ArrayList<>());
// 本质：在 ArrayList 外面包一层 synchronized 代理

// 替代方案2：CopyOnWriteArrayList（读多写少）
List<String> cowList = new CopyOnWriteArrayList<>();
// 本质：写时复制，读无锁

// 替代方案3：并发容器（高性能场景）
// 如果需要的是 queue 语义，用 ConcurrentLinkedQueue
// 如果需要的是 set 语义，用 ConcurrentHashMap.newKeySet()
```


## 04. LinkedList：双向链表的多面手

### 4.1 核心结构

LinkedList 实现了 `List` 和 `Deque` 两个接口，既是列表又是双端队列：

```java
public class LinkedList<E> extends AbstractSequentialList<E>
        implements List<E>, Deque<E>, Cloneable, java.io.Serializable {
    
    transient int size = 0;
    transient Node<E> first;  // 头指针
    transient Node<E> last;   // 尾指针
    
    // 双向链表节点
    private static class Node<E> {
        E item;
        Node<E> next;
        Node<E> prev;
        
        Node(Node<E> prev, E element, Node<E> next) {
            this.item = element;
            this.next = next;
            this.prev = prev;
        }
    }
}
```

```
内存布局：

[first] ⇄ [Node A] ⇄ [Node B] ⇄ [Node C] ⇄ [Node D] [last]
  │         item: "a"   item: "b"   item: "c"   item: "d"  │
  └─────────→ prev=null                     next=null ←─────┘

每个 Node 独立分配内存，不要求连续。
每个 Node 占用：item引用(8B) + next引用(8B) + prev引用(8B) + 对象头(16B) = 40B
```

### 4.2 核心操作分析

**头部插入 O(1)**：

```java
private void linkFirst(E e) {
    final Node<E> f = first;
    final Node<E> newNode = new Node<>(null, e, f);  // prev=null, next=旧first
    first = newNode;
    if (f == null)
        last = newNode;       // 链表为空时，first=last=新节点
    else
        f.prev = newNode;     // 旧 first 的 prev 指向新节点
    size++;
    modCount++;
}
// 只修改了 2-3 个指针，无需移动任何元素 → O(1)
```

**按下标访问 O(N)**：

```java
Node<E> node(int index) {
    // 优化：判断 index 在前半段还是后半段
    if (index < (size >> 1)) {
        Node<E> x = first;
        for (int i = 0; i < index; i++)  // 从头找
            x = x.next;
        return x;
    } else {
        Node<E> x = last;
        for (int i = size - 1; i > index; i--)  // 从尾找
            x = x.prev;
        return x;
    }
}
// 最好情况 O(1)（index=0 或 size-1）
// 最坏情况 O(N/2) → 仍然是 O(N)
```

**中间插入的"隐藏成本"**：

很多人说"链表插入是 O(1)"，这是不完整的。

```
链表在已知节点处插入确实是 O(1)——只需修改几个指针。
但 list.add(index, element) 需要先找到 index 位置的节点！

真实复杂度 = 查找 O(N) + 插入 O(1) = O(N)

vs ArrayList：查找 O(1) + 移动 O(N) = O(N)

两者都是 O(N)！但 ArrayList 的"移动"是连续内存的 System.arraycopy，
走的是 CPU 缓存行，实际速度远快于 LinkedList 的指针跳跃。
```

### 4.3 作为 Deque 的应用

```java
LinkedList<String> deque = new LinkedList<>();

// 当队列使用
deque.offer("task1");      // 尾部入队 → linkLast → O(1)
deque.offer("task2");
String task = deque.poll(); // 头部出队 → unlinkFirst → O(1)

// 当栈使用
deque.push("page1");       // 头部入栈 → linkFirst → O(1)
deque.push("page2");
String page = deque.pop(); // 头部出栈 → unlinkFirst → O(1)

// 当双端队列使用
deque.offerFirst("urgent"); // 头部插入
deque.offerLast("normal");  // 尾部插入
deque.pollFirst();           // 头部删除
deque.pollLast();            // 尾部删除
```

### 4.4 LinkedList 的性能真相

**理论 vs 实际的巨大鸿沟**：

```
测试：1000万次 get(随机下标)
  ArrayList: ~50ms     → 地址计算，直接访问
  LinkedList: ~超时     → 每次都要从头/尾遍历

测试：100万次头部 add(0, x)
  ArrayList: ~2500ms   → 每次移动所有元素（但 arraycopy 很快）
  LinkedList: ~150ms   → 修改指针 O(1)，LinkedList 胜出

测试：100万次尾部 add(x)
  ArrayList: ~30ms     → 直接写入末尾，缓存友好
  LinkedList: ~200ms   → 每次 new Node + 修改指针，有GC压力

测试：顺序遍历 1000万元素
  ArrayList: ~15ms     → 连续内存，CPU 预取机制完美命中
  LinkedList: ~80ms    → 节点散布在堆中，每次访问都可能 cache miss
```

**结论**：除了"头部频繁插入/删除"这一个场景，ArrayList 几乎全面碾压 LinkedList。

### 4.5 为什么很少推荐 LinkedList？

```
1. 内存开销大：每个元素需要额外 32 字节（prev + next + 对象头）
2. 缓存不友好：节点散落在堆内存各处，CPU 缓存命中率低
3. GC 压力大：大量独立小对象给垃圾回收带来负担
4. get(i) 是 O(N)：随机访问性能灾难
5. 实际场景中"已知节点的 O(1) 插入"很少出现

推荐替代：
  需要 Queue → ArrayDeque（数组实现的双端队列，比 LinkedList 快）
  需要 Deque → ArrayDeque
  需要 List → ArrayList
  需要 LRU → 自己写 HashMap + 双向链表（需要直接操作节点）
```


## 05. CopyOnWriteArrayList：写时复制的精巧设计

### 5.1 设计理念

CopyOnWriteArrayList（以下简称 COWList）的核心思想极为简洁：**读操作不加锁，写操作复制整个数组**。

```java
public class CopyOnWriteArrayList<E> implements List<E>, RandomAccess {
    
    // 关键：volatile 保证可见性，指向不可变数组
    private transient volatile Object[] array;
    
    // 写操作的独占锁
    final transient ReentrantLock lock = new ReentrantLock();
}
```

### 5.2 读操作：零成本

```java
// get 操作：直接读，没有任何同步开销
public E get(int index) {
    return get(getArray(), index);  // getArray() 就是 return array;
}

private E get(Object[] a, int index) {
    return (E) a[index];
}

// 读操作的秘密：
// 1. array 被 volatile 修饰 → 读总能看到最新的数组引用
// 2. 数组内容不可变 → 不存在"读到一半被修改"的问题
// 3. 无锁 → 性能与普通 ArrayList 一样
```

### 5.3 写操作：复制 + 修改 + 替换

```java
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();  // 写操作加锁，保证只有一个线程在写
    try {
        Object[] elements = getArray();
        int len = elements.length;
        // 核心：复制出一个新数组（长度+1）
        Object[] newElements = Arrays.copyOf(elements, len + 1);
        newElements[len] = e;
        // 原子替换：将 array 引用指向新数组
        setArray(newElements);
        return true;
    } finally {
        lock.unlock();
    }
}
```

**写时复制的过程**：

```
初始状态：
  array ──→ [A, B, C]         （所有读线程看到这个数组）

线程W执行 add("D")：
  Step 1: 加锁
  Step 2: newElements = copy [A, B, C] → [A, B, C, _]  （新数组）
  Step 3: newElements[3] = "D" → [A, B, C, D]
  Step 4: array = newElements  （volatile 写，原子切换）
  Step 5: 释放锁

  旧数组 [A, B, C] 仍然存在于内存中（正在读的线程还在用它）
  新数组 [A, B, C, D] 是新的引用
  
读线程R（在 Step 4 之前开始读）：
  看到的仍然是 [A, B, C]  → 不受影响，读取一致的快照
  
读线程R'（在 Step 4 之后开始读）：
  看到的是 [A, B, C, D]   → 读到最新数据
```

### 5.4 快照迭代器：弱一致性

```java
public Iterator<E> iterator() {
    return new COWIterator<E>(getArray(), 0);
}

static final class COWIterator<E> implements ListIterator<E> {
    private final Object[] snapshot;  // 创建时的数组快照
    private int cursor;
    
    COWIterator(Object[] elements, int initialCursor) {
        cursor = initialCursor;
        snapshot = elements;  // 直接引用当时的数组
    }
    
    // 不支持修改操作
    public void remove() { throw new UnsupportedOperationException(); }
    public void add(E e) { throw new UnsupportedOperationException(); }
}
```

**快照语义**：

```
Thread-A: Iterator it = cowList.iterator();  // 拿到 [A, B, C] 的快照
Thread-B: cowList.add("D");                  // 创建新数组 [A, B, C, D]
Thread-A: it.next() → A, B, C               // 遍历的仍然是旧快照

这就是"弱一致性"：迭代器不会抛出 ConcurrentModificationException，
但也不会看到迭代开始后的修改。
```

### 5.5 COW 的代价与适用场景

**代价分析**：

| 维度 | 代价 |
|------|------|
| 内存 | 每次写操作复制整个数组，瞬时内存翻倍 |
| 写性能 | O(N) 复制 + 锁竞争 |
| 一致性 | 读到的可能是旧数据（弱一致性） |
| GC 压力 | 频繁写入产生大量废弃数组 |

**适用场景判断**：

```
✅ 适合：
  - 配置列表（启动时写入，运行时只读）
  - 监听器/观察者列表（注册少，通知多）
  - 黑白名单（定期全量更新，实时查询）
  - 缓存（写入少，读取多）

❌ 不适合：
  - 频繁写入（每次写都要复制整个数组）
  - 大数据量（复制成本与数据量成正比）
  - 需要强一致性的场景
```

### 5.6 实际应用案例

```java
// 案例1：事件监听器列表
public class EventBus {
    private final CopyOnWriteArrayList<EventListener> listeners = new CopyOnWriteArrayList<>();
    
    // 注册（写操作，很少发生）
    public void register(EventListener listener) {
        listeners.add(listener);
    }
    
    // 发布事件（读操作，频繁发生）
    public void publish(Event event) {
        for (EventListener listener : listeners) {  // 快照迭代，无锁
            listener.onEvent(event);
        }
    }
}

// 案例2：配置热更新
public class ConfigCenter {
    private final CopyOnWriteArrayList<String> whitelist = new CopyOnWriteArrayList<>();
    
    // 定时任务：每5分钟从数据库拉取最新白名单（写，低频）
    @Scheduled(fixedRate = 300000)
    public void refreshWhitelist() {
        List<String> newList = db.queryWhitelist();
        whitelist.clear();       // 写
        whitelist.addAll(newList); // 写
    }
    
    // 每个请求都要检查（读，高频）
    public boolean isAllowed(String userId) {
        return whitelist.contains(userId);  // 无锁读
    }
}
```


## 06. 四大 List 全面对比

### 6.1 操作复杂度对比

| 操作 | ArrayList | Vector | LinkedList | CopyOnWriteArrayList |
|------|-----------|--------|------------|---------------------|
| get(i) | **O(1)** | **O(1)** | O(N) | **O(1)** |
| add(末尾) | **均摊 O(1)** | **均摊 O(1)** | **O(1)** | O(N) 复制 |
| add(i) | O(N) | O(N) | O(N) | O(N) 复制 |
| remove(i) | O(N) | O(N) | O(N) | O(N) 复制 |
| contains | O(N) | O(N) | O(N) | O(N) |
| 迭代 | **快（缓存友好）** | 快 | 慢（指针跳跃） | **快（数组快照）** |

### 6.2 线程安全对比

| 维度 | ArrayList | Vector | LinkedList | COWList |
|------|-----------|--------|------------|---------|
| 线程安全 | ❌ | ✅ | ❌ | ✅ |
| 锁策略 | 无 | synchronized | 无 | ReentrantLock + COW |
| 读并发 | - | 互斥 | - | **无锁** |
| 写并发 | - | 互斥 | - | 互斥 |
| 迭代安全 | fail-fast | fail-fast | fail-fast | **快照（弱一致）** |

### 6.3 内存占用对比

```
存储 100 万个 Integer 对象：

ArrayList:
  数组引用: 100万 × 8B(引用) = 7.6MB
  + 数组对象头 + 空闲位（~10%冗余）≈ 8.4MB

Vector:
  与 ArrayList 类似，但 2 倍扩容可能有更多空闲 ≈ 12MB

LinkedList:
  每个 Node: item(8B) + next(8B) + prev(8B) + 对象头(16B) = 40B
  100万 × 40B = 38MB  → ArrayList 的 4.5 倍！

CopyOnWriteArrayList:
  正常情况与 ArrayList 类似 ≈ 8.4MB
  写入瞬间：旧数组 + 新数组 ≈ 16.8MB（瞬时翻倍）
```

### 6.4 选型决策树

```
你的场景是什么？
  │
  ├── 单线程 / 外部已保证线程安全
  │     ├── 需要随机访问（get/set 频繁）→ ArrayList ✅
  │     ├── 需要头尾操作（队列/栈语义）→ ArrayDeque ✅（不是 LinkedList！）
  │     └── 需要在已知位置频繁插入删除 → LinkedList（极少见）
  │
  ├── 多线程
  │     ├── 读远多于写（99%读 1%写）→ CopyOnWriteArrayList ✅
  │     ├── 读写均衡 → Collections.synchronizedList(new ArrayList<>())
  │     └── 高并发场景 → 考虑 ConcurrentLinkedQueue 或其他并发容器
  │
  └── 绝对不要用
        └── Vector / Stack → 历史遗留，性能差，设计有缺陷
```

### 6.5 跨语言对比

| 语言 | 动态数组 | 链表 | 线程安全List | COW方案 |
|------|---------|------|------------|--------|
| Java | ArrayList | LinkedList | CopyOnWriteArrayList | ✅ 内置 |
| Go | slice | container/list | sync.Mutex + slice | 需自己实现 |
| Python | list | 无内置 | queue.Queue | 无内置 |
| Rust | Vec | LinkedList | Arc<RwLock<Vec>> | 有 im 库 |
| C++ | vector | list/forward_list | 无内置 | 需自己实现 |
| Swift | Array | 无内置 | DispatchQueue + Array | 值语义自带COW |
| Kotlin | ArrayList | LinkedList | CopyOnWriteArrayList | 同 Java |

**Swift 的独特设计**：Swift 的 Array 是值类型，内置了 COW 优化——赋值时不会立即复制，只有在修改时才复制。这是语言级别的 COW 支持。

```swift
var a = [1, 2, 3]
var b = a          // b 和 a 共享底层存储（不复制）
b.append(4)        // 此时 b 才真正复制一份（COW触发）
// a = [1, 2, 3]   不受影响
// b = [1, 2, 3, 4]
```


## 07. 高级话题：不常见但重要的 List 变体

### 7.1 Collections.unmodifiableList — 不可变包装

```java
List<String> mutable = new ArrayList<>(Arrays.asList("a", "b", "c"));
List<String> immutable = Collections.unmodifiableList(mutable);

immutable.add("d");  // 抛出 UnsupportedOperationException

// 陷阱：底层列表仍然可以被修改！
mutable.add("d");
System.out.println(immutable);  // [a, b, c, d] ← 不可变列表的内容也变了！

// JDK 9+ 的真正不可变列表
List<String> trueImmutable = List.of("a", "b", "c");
// 底层有专门的不可变实现，无法通过任何方式修改
```

### 7.2 Collections.synchronizedList — 同步包装

```java
List<String> syncList = Collections.synchronizedList(new ArrayList<>());

// 内部实现：
static class SynchronizedList<E> extends SynchronizedCollection<E> implements List<E> {
    final List<E> list;
    final Object mutex;  // 锁对象
    
    public E get(int index) {
        synchronized (mutex) { return list.get(index); }
    }
    public void add(int index, E element) {
        synchronized (mutex) { list.add(index, element); }
    }
}

// 注意：迭代时必须手动加锁！
synchronized (syncList) {
    for (String s : syncList) {
        // ...
    }
}
```

### 7.3 SubList — 视图而非副本

```java
List<Integer> original = new ArrayList<>(Arrays.asList(1, 2, 3, 4, 5));
List<Integer> sub = original.subList(1, 4);  // [2, 3, 4]

// subList 是原列表的视图，不是副本！
sub.set(0, 99);
System.out.println(original);  // [1, 99, 3, 4, 5]  ← 原列表也变了！

// 修改原列表会导致 SubList 的迭代器失效
original.add(6);
sub.get(0);  // 抛出 ConcurrentModificationException
```


## 思考题

> 以下问题由浅入深，建议先独立思考再查阅资料。

**1. 基础理解**：在 ArrayList 的 `add(int index, E element)` 中，`System.arraycopy` 将 index 之后的元素后移一位。如果 index=0 且 size=100万，这次 arraycopy 需要移动 100 万个元素。但实际测试发现耗时只有几毫秒——比 100 万次单独赋值快得多。为什么 `System.arraycopy` 这么快？（提示：它是 native 方法，底层使用了什么 CPU 指令？）

**2. 设计反思**：LinkedList 同时实现了 List 和 Deque 接口，导致它有大量冗余方法（如 `remove()` vs `removeFirst()`、`add()` vs `offer()`）。如果让你重新设计 Java 集合框架，你会如何处理"链表既能当列表用又能当队列用"的需求？拆成两个类？还是有其他方案？

**3. COW 优化**：CopyOnWriteArrayList 的 `set(int index, E element)` 也需要复制整个数组。请思考：能否优化为"只在数组引用发生变化时才复制"（即如果 set 的值和原来一样就不复制）？JDK 源码中是怎么做的？这个优化有什么意义？

**4. 性能对决**：设计一个基准测试，比较 ArrayList、LinkedList、ArrayDeque 在"10 万次头部插入 + 10 万次头部删除"场景下的性能。预测结果，然后编码验证。实际结果和你的预测一致吗？

**5. 架构思考**：CopyOnWriteArrayList 的"弱一致性"在某些场景下是个问题：写入后，已经创建的迭代器看不到新数据。如果你的业务要求"写入立即可见 + 读无锁 + 迭代安全"，你会怎么设计？（提示：参考 MVCC 多版本并发控制的思路）
