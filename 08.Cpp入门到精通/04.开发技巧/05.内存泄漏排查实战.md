## 01. 先说清楚：什么才是"内存泄漏"

内存泄漏在工程里有两种定义，区分不清会把排查方向带偏。

**定义 A（狭义，语言层面）**：程序里有一块内存，已经不可能再被任何指针到达，但也没被 `free`/`delete`。这和 Java 的 GC 视角一致，LSan、Valgrind 走的是这套语义。

**定义 B（广义，运维层面）**：进程的 RSS 随时间单调上涨，最终触发 OOM。只要表现是"不停上涨"，哪怕每块内存都有指针指着，也算"泄漏"。

两者区别在哪？举几个典型差异：

- **缓存没有淘汰策略**：每一条记录都有指针指着（活的），但数量一直涨 → A 认为不泄漏，B 认为泄漏。
- **线程局部缓冲**：每新开一个线程 TLS 就分配一次、线程退出才释放。短生命线程大量创建销毁正常，但线程池里线程永不退出 → A 认为不泄漏，B 觉得可能是泄漏。
- **glibc ptmalloc 的 per-thread arena**：glibc 为每个线程预留一个 arena，线程退出后 arena 不会返还给 OS，而是挂在一个"待重用列表"里，表现为 RSS 永不下降 → A 否，B 是。
- **内存碎片**：分配器手里有大把小块空闲内存拼不出一块连续 1MB，不得不继续向 OS 要新页 → A 否，B 是。
- **大页（huge page）预留**：进程启动时一次性预留 1GB 大页，实际用了 100MB，剩下 900MB 看起来"浪费"了 → 都不算，属于设计选择。

**这也是为什么工具不能万能**：LSan 和 Valgrind 走的是定义 A，它们找不到"缓存未淘汰"这类问题；tcmalloc heap profile、jemalloc `prof.dump` 走的是定义 B，能告诉你"哪个调用栈分配的内存还没释放"，但不保证那就是 Bug。

本章会两种语义都覆盖，但在心里先把它们分清楚。

## 02. 现场诊断：五条命令先过一遍

发现服务 RSS 在涨。**别急着挂工具**——先用下面五条命令分清是什么现象。

### 2.1 `/proc/<pid>/status`：看总览

```bash
grep -E 'VmRSS|VmSize|VmData|VmPeak|VmSwap' /proc/$(pidof myservice)/status
```

关键指标：
- **VmRSS**：实际占用物理内存（和 `top` 看到的 RES 一致）
- **VmSize**：虚拟内存总量（含未驻留的）
- **VmData**：数据段 + 堆大小
- **VmPeak**：启动以来 VmSize 峰值
- **VmSwap**：被交换出去的部分

**经验判断**：
- VmSize 涨、VmRSS 不涨 → 疑似 mmap 了大块内存但没真正写入（例如映射了文件）；
- VmRSS 涨、VmData 不涨 → 可能是共享库或 mmap 文件读入导致 page cache，不是堆泄漏；
- VmData 持续涨 → 真堆增长，值得深挖。

### 2.2 `/proc/<pid>/maps`：看地址空间布局

```bash
cat /proc/$(pidof myservice)/maps | head -40
```

看看有没有大量 `[anon]` 段、或者反复出现的同名匿名映射。如果你发现有几百个 2MB 的匿名段并排着，基本可以锁定是 glibc 的 arena 或 mmap allocator。

### 2.3 `/proc/<pid>/smaps`：按段看详情

```bash
pmap -x $(pidof myservice) | sort -k3 -n -r | head -20
```

这会按 RSS 倒序排出占用最大的几段。如果排在前面的是 `[heap]` 和若干匿名段，基本锁定堆内分配。如果前排是某个 `.so` 或文件映射，重点就在文件读入/缓存而非堆分配。

### 2.4 `top`/`htop` 的 trend 视角

- 观察 RSS **涨的速度**：每小时 10MB vs 每小时 1GB，前者是慢性泄漏、后者是急性泄漏，调查策略完全不同。
- 观察是否有**上涨平台**（RSS 涨到某点稳定）：典型的缓存预热，不是泄漏；
- 观察 **RSS vs 请求量** 的相关性：相关 → 每请求都有残留；不相关 → 可能是定时任务或后台线程累积。

### 2.5 `malloc_stats()`（glibc）与 `MALLOC_TRACE`

glibc 提供了内建钩子：

```cpp
#include <malloc.h>
malloc_stats();    // 向 stderr 打印各 arena 的统计
```

能看到每个 arena 的 "system bytes"、"in use bytes"，差值就是"空闲但没还给 OS 的碎片"。如果这个值很大（几百 MB+），问题可能在**碎片**而非**真泄漏**。

此外 `MALLOC_TRACE=/tmp/trace ./prog` 可以让 glibc 把每次 malloc/free 都写到文件（受 `mtrace()` 控制），再用 `mtrace` 工具分析。老派但直接。

**经验规则**：
1. 单测、开发阶段 → **ASan（自带 LSan）**；
2. 已知可复现的单机问题 → **Valgrind**（慢但最准）；
3. 生产只涨不崩、靠采样定位调用栈 → **tcmalloc/jemalloc heap profile**；
4. 现场诊断、不能重启 → **pmap + smaps + malloc_stats**。

## 04. LSan / ASan 实战（单测阶段的"首选")

### 4.1 编译与运行

```bash
clang++ -O1 -g -fsanitize=address -fno-omit-frame-pointer prog.cpp
ASAN_OPTIONS="detect_leaks=1:print_stacktrace=1" ./a.out
```

退出时，LSan 会以 mark-sweep 算法扫描所有堆块，打出"不可达块"的分配栈：

```
=================================================================
==12345==ERROR: LeakSanitizer: detected memory leaks

Direct leak of 40 byte(s) in 1 object(s) allocated from:
    #0 0x4a8c9f in operator new(unsigned long)
    #1 0x4b4d12 in main prog.cpp:5:15

Indirect leak of 8 byte(s) in 1 object(s) allocated from:
    #0 0x4a8c9f in operator new(unsigned long)
    #1 0x4b4d40 in main prog.cpp:6:15

SUMMARY: AddressSanitizer: 48 byte(s) leaked in 2 allocation(s).
```

"direct leak" 指直接不可达；"indirect leak" 指被 direct leak 间接持有——修直接泄漏通常就能连带消掉间接泄漏。

### 4.2 主动触发

长跑进程里不想等退出才检测？用 `__lsan_do_recoverable_leak_check()`：

```cpp
#include <sanitizer/lsan_interface.h>

// 某个周期性钩子
if (tick % 3600 == 0) {
    __lsan_do_recoverable_leak_check();  // 打印但不退出
}
```

配合 `__lsan_ignore_object(ptr)` 可以告诉 LSan "这块我故意留着，不要当泄漏"，适用于单例、全局缓存等。

### 4.3 LSan 原理再梳理

LSan 退出时做的事情和 GC 的 mark-sweep 极像：

1. **Stop the world**：所有线程 freeze。
2. **根集合**：
   - 所有 **全局变量区**（`.bss`、`.data`）；
   - 所有 **线程栈**（`/proc/self/maps` 里的 `[stack:*]` 段）；
   - 所有 **寄存器值**（通过 signal handler 保存）；
   - 所有 **TLS**（thread-local storage）。
3. **遍历根**：把根集合当作字节流，每遇到一个 8 字节对齐的疑似指针（值恰好落在已知堆块范围内），就把那个堆块标记为"活的"，并把它的内容也加入待扫描队列。
4. **传递闭包**：直到没有新块被标记。
5. **sweep**：所有未标记的堆块报成 direct leak（被 direct leak 持有但自身没直接被根指向的则是 indirect leak）。

这种"扫描字节流找疑似指针"的办法**有假阴性**：如果一个整数恰好数值上等于某堆块地址，它会被错判成指针，导致 LSan 以为那块"活着"，实际是泄漏。这就是为什么 LSan 不能 100% 替代 review。

## 05. Valgrind memcheck（单机疑难杂症的核武器）

Valgrind 不需要重编代码：

```bash
valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./a.out
```

原理是**动态二进制翻译**（DBT）：Valgrind 拦截整个进程的每条机器指令，转译成带检查的 IR，再 JIT 回 native 执行。每一字节真实内存都有 9 bit 影子信息（1 addressable + 8 defined）。这就是为什么开销飙到 20-50x。

优势是**完全不改代码、什么语言都支持、能抓 MSan 抓得到的未初始化读**。劣势是慢。工业实践一般是"平时不开，问题定位时单机拉一份 core 场景跑一次"。

Valgrind 的报告有四类泄漏：

- **definitely lost**：狭义泄漏，最严重。
- **indirectly lost**：被 definitely lost 持有。
- **possibly lost**：valgrind 只能扫到指针指向**块中间**而非起点（可能是多继承指针偏移或自定义数据结构），保守报"可能"。
- **still reachable**：退出时仍可达（全局缓存、单例）。一般不算 bug。

重点盯前两类。

## 06. tcmalloc / jemalloc heap profile（线上长跑唯一选项）

这是**工业生产环境**最常用的办法，因为 ASan/Valgrind 那 2-50x 开销不可能开在线上。

### 6.1 tcmalloc heap profile

把 tcmalloc 的 `.so` 作为依赖（或用 `LD_PRELOAD` 注入）：

```bash
env HEAPPROFILE=/tmp/myprog.heap \
    LD_PRELOAD=/usr/lib/libtcmalloc.so \
    ./myprog
```

tcmalloc 会按配置的频率（环境变量 `HEAP_PROFILE_ALLOCATION_INTERVAL`、默认每分配 1GB 采样一次）往 `/tmp/myprog.heap.XXXX.heap` 写入快照。快照格式是压缩的调用栈 → 字节数映射。

分析：

```bash
pprof --text ./myprog /tmp/myprog.heap.0001.heap
pprof --web  ./myprog /tmp/myprog.heap.0001.heap   # SVG 火焰图
```

**定位泄漏的套路是"两份快照相减"**：

```bash
pprof --base=/tmp/myprog.heap.0001.heap \
      --text ./myprog /tmp/myprog.heap.0100.heap
```

这样得到的是"这 99 分钟里新增了多少内存，各自由哪些调用栈分配"。**新增的就是最可疑的**——因为服务稳态运行应该净分配 ≈ 0。排序一看哪条栈净分配最大，基本就锁定嫌疑犯。

### 6.2 jemalloc prof

jemalloc 是 Facebook/Firefox 主力分配器，profile 能力类似：

```bash
env MALLOC_CONF="prof:true,prof_prefix:/tmp/myprog.jeprof" \
    LD_PRELOAD=/usr/lib/libjemalloc.so \
    ./myprog
```

运行时主动 dump：

```cpp
#include <jemalloc/jemalloc.h>
mallctl("prof.dump", NULL, NULL, NULL, 0);
```

用 `jeprof` 解析，和 pprof 类似。

### 6.3 采样而非全量：为什么开销只有 5%

核心技巧是**泊松采样**：平均每分配 N 字节（默认 512KB）才记录一次调用栈。短期 workload 这种采样会漏，但长跑中"泄漏大户"的累计分配量巨大，采样率再低也一定会被命中。

采样点记录的是 `backtrace()` 的栈，这步用 libunwind / `.eh_frame` 解析调用链。生成 profile 时是用链表把所有采样堆块串起来，dump 时只需遍历一次——**这正是 heap profile 只慢 5% 的原因**。

## 07. 原理深挖：为什么"已 free 却 RSS 不降"

工程师经常遇到这个魔幻现象：代码明明 `free` 了，`top` 看 RSS 不降反涨。这不是 bug，是操作系统 + 分配器的合作后果。让我们拆成两层看。

### 7.1 glibc ptmalloc2 的"不归还"策略

ptmalloc2 的 heap 扩张通过两个 syscall：

- 小于 128KB（`M_MMAP_THRESHOLD`）的分配 → 从 heap 里切（`brk` 扩展数据段）；
- 大于等于 128KB → 独立 `mmap` 一块匿名映射。

**`free` 发生时**：
- mmap 块：直接 `munmap`，RSS 立刻下降；
- heap 内的小块：**只是挂回 free list**，真实物理页不返还。只有当 heap 顶部有大片连续空闲时才会 `sbrk` 缩回，且 glibc 默认的 trim 阈值是 128KB（`M_TRIM_THRESHOLD`）。

这意味着：一个应用分配了 1 亿个 32 字节小对象然后全部 free，RSS 依然高居不下。解决方案有三：

- 主动调用 `malloc_trim(0)`；
- 换用 jemalloc / tcmalloc（它们的归还策略更激进）；
- 不要短时间大量分配小对象——用对象池。

### 7.2 Per-thread arena 的阴影

glibc 为减少多线程竞争，为每个线程分配独立 arena（上限是 CPU 数 × 8）。每个 arena 各自管理自己的空闲链。线程退出时，**arena 不归还**，只是挂到复用列表。多次大量创建/销毁线程会导致每线程 arena 都胀到最大然后留在那里。

`MALLOC_ARENA_MAX=2` 是常见的"省内存"魔法环境变量，强制最多 2 个 arena。代价是多线程分配锁竞争变激烈。

### 7.3 内存碎片的真相

假设你有 1GB heap、里面散布着 1 亿个 32 字节空洞、总空闲 3GB，但现在申请一块 1MB 连续内存——可能失败。这就是**碎片**。碎片在 ptmalloc 上比较严重；jemalloc/tcmalloc 做了 size class 对齐（把相近大小归并到同一个 pool），碎片显著改善。

这也解释了为什么长跑后换 jemalloc/tcmalloc 通常能立即看到 RSS 下降 10-30%。

## 08. 特殊场景：智能指针时代的"新泄漏模式"

C++11 之后 `shared_ptr` 普及，传统 `new/delete` 型泄漏大幅减少。但引入了两类新模式。

### 8.1 循环引用

```cpp
struct Node {
    std::shared_ptr<Node> next;
};
auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->next = a;   // 循环！
```

`a` 和 `b` 互相持有对方的 shared_ptr，引用计数永远 > 0，谁都不会被销毁。工具侧：
- LSan **查不出来**——因为两个块"互相可达"，不算不可达；
- Valgrind definitely-lost 也查不出来——同样可达；
- 只能靠 heap profile 看到"有两类块累积不降"然后自己 review。

防御办法：双向引用场景一律用 `weak_ptr` 打破环。

### 8.2 Lambda 捕获 shared_ptr 后注册到长生命对象

```cpp
auto res = std::make_shared<Resource>();
long_lived_dispatcher.subscribe([res](Event e) {
    res->handle(e);
});
// 忘了 unsubscribe，lambda 一直活着，res 一直活着
```

lambda 按值捕获 `shared_ptr` → lambda 持有 res 的引用计数。只要 dispatcher 不销毁该订阅者，res 就不会释放。这种"**通过回调/事件/信号槽形成的隐形持有**"是现代 C++ 最常见的泄漏形态之一。

防御：能用 `weak_ptr` 捕获的就用 weak；必须有生命周期管理的回调要配套 unsubscribe；或使用 `std::enable_shared_from_this` + weak promote 模式。

## 09. 疑难杂症调查方法论

下面是几个行之有效的调查套路，来自真实线上案例。

### 9.1 "一周才复现，没法本地复现" 怎么办

1. **先用 tcmalloc heap profile 在线上采样**——隔天 dump 一份，和启动时基准比差值；
2. 找到 top N 可疑栈后，**构造定向压测**："只打这条接口的 workload"；
3. 本地跑压测 + ASan，通常几分钟就能定位。

### 9.2 "压测不泄漏、生产泄漏" 怎么办

1. 先猜差异：**压测 workload 单一、生产 workload 多样**。某些只在特定请求路径上才进入的 cleanup 逻辑可能出错；
2. 用 bpftrace 写个 uprobe 监控 malloc/free 比率按接口维度分档；
3. 找到 free/malloc 比显著偏低的接口，定向复现。

### 9.3 "RSS 周期性高峰、低谷，但每个周期比上个高一点" 怎么办

1. 这是**渐进式泄漏**的典型特征，每个请求周期都有少量残留；
2. 用 pprof base diff 对比两个"低谷"时刻的 heap profile；
3. 差值不为零的栈就是嫌疑栈。

### 9.4 "只有某个容器化部署才泄漏，物理机不泄漏" 怎么办

1. **检查 cgroup memory limit** 是否导致 glibc 分配策略变化；
2. 检查 `MALLOC_ARENA_MAX`、`MALLOC_MMAP_THRESHOLD_` 在容器里的默认值；
3. 检查容器 OS 的 glibc 版本是否和物理机一致；
4. glibc 某些旧版本在受限环境里有已知碎片化问题。

## 10. 小结：排查矩阵与三条准则

### 10.1 排查流程图（文字版）

```
发现 RSS 上涨
    ├─ 是否真泄漏？(pmap + malloc_stats 看是不是碎片/arena)
    │       ├─ 否 → 调参数 / 换 jemalloc
    │       └─ 是 ↓
    ├─ 能否本地复现？
    │       ├─ 能 → ASan/Valgrind
    │       └─ 不能 ↓
    └─ 线上采样（tcmalloc heap profile or jemalloc prof）
             └─ 定位 top 栈 → 构造定向压测 → 本地 ASan 一击必中
```

### 10.2 三条准则

1. **先定性、再定位**——别拿到一个 RSS 曲线就挂工具，先用 smaps 看是不是真泄漏、是哪一段在涨。挂错工具浪费一天是常事。
2. **线上采样、线下精查**——生产环境上 heap profile 的角色是"给出候选栈"；最终的定位和修复应该在线下完成，这样才能跑 ASan 验证修复。
3. **工具不是万能**——LSan 查不出循环引用，Valgrind 查不出缓存未淘汰，heap profile 查不出"合理增长"。工具只是提醒，判断"这算不算 bug"最终靠人。

## 11. 思考题

1. 你的服务启动后前 30 分钟 RSS 从 100MB 涨到 2GB，之后稳定在 2GB 不再变化。这是泄漏吗？该怎么诊断？
2. LSan 为什么对"循环引用"束手无策？你能设计一种工具来发现循环引用吗（提示：对比强弱引用计数）？
3. 一个程序退出前把所有 `new` 出的对象都塞进一个全局 vector 不释放。LSan、Valgrind、tcmalloc heap profile 各自会如何报告？
4. `malloc_trim(0)` 有没有副作用？什么时候**不该**调用它？
5. 用 `LD_PRELOAD` 注入 tcmalloc，与静态链接 tcmalloc，二者在内存占用与性能上有区别吗？
6. 为什么生产环境上 ASan 几乎不被使用？假设你非要在线上定位偶发 UAF，有什么权衡方案？
