## 01.变更与故障

### 1.1 90% 事故源头

Google SRE 数据：**70% 的线上故障由人为变更引起**。其中：

- 代码变更：40%
- 配置变更：20%
- 数据库变更：10%
- 基础设施变更：10%
- 外部依赖变化：10%
- 自然增长 / 容量：5%
- 真硬件故障：5%

工程结论：**对变更的控制力，决定了系统的稳定性上限**。再好的架构、再多的监控，每次变更都全量推，事故只是时间问题。

### 1.2 灰度的本质

灰度（gradual rollout）的核心思想：

```
新版本上线
   │
   ├─ 阶段 1：1% 流量验证（影响半径最小）
   ├─ 阶段 2：10%
   ├─ 阶段 3：50%
   └─ 阶段 4：100%

每个阶段：观察指标 → 没问题 → 进下一阶段
                 → 有问题 → 立即回滚（影响仅限当前阶段）
```

数学上：把"事故概率"乘以"影响范围"——前者改不了，后者可以乘 0.01。

### 1.3 适用与不适用

| 适用 | 不适用 / 弱适用 |
|------|-----------------|
| 无状态服务（Web、API） | 强一致的存储变更（schema 变更） |
| 多实例部署 | 单实例服务（无法并存） |
| 流量可路由 | 内核/驱动级变更 |
| 改动可独立验证 | 多服务联动且必须同步上 |

数据库 schema 变更要专门方案：**先做向后兼容的扩展（加字段）→ 灰度新代码 → 等老代码下线 → 再清理**。直接 ALTER 不可灰度。


## 02.发布策略图谱

### 2.1 全量发布

```
[v1] [v1] [v1] [v1]   →   [v2] [v2] [v2] [v2]
```

最简单也最危险。**仅限内部工具、灰度环境本身**。

### 2.2 滚动发布

```
[v1][v1][v1][v1]
   ↓ 一台一台升
[v2][v1][v1][v1]
[v2][v2][v1][v1]
[v2][v2][v2][v1]
[v2][v2][v2][v2]
```

K8s `RollingUpdate` 默认。优点：节省资源、平滑。缺点：

- 升级期间新旧版本并存（要求**接口兼容**）
- 一个实例有 bug，其他实例已更新——回滚要重走流程
- 影响半径 = 1/N，但每台都会经过

### 2.3 蓝绿部署

```
[蓝 v1][蓝 v1][蓝 v1]   ← 当前接流量
[绿 v2][绿 v2][绿 v2]   ← 完全独立，跑预热

负载均衡切换流量：蓝 → 绿
有问题立即切回蓝
```

优点：**回滚 < 1 秒**（切流量即可）。缺点：双倍机器成本。

适合：金融、支付等对回滚速度极敏感的服务。

### 2.4 金丝雀发布

```
[v1][v1][v1][v1][v1][v1][v1][v1][v1][v2]   ← 一只金丝雀
                                       ↑ 只它接 1% 流量

观察 10 分钟 → 无异常 → 增加金丝雀数量
              有异常 → 撤掉它
```

最安全的灰度模式。"金丝雀"是矿工带下井探测毒气的鸟——**一只死了大家撤**。

### 2.5 影子流量

```
请求来 → 复制一份 → 发给 v2（结果丢弃）
              ↓
              v1（真实响应）
```

v2 只接收**复制的流量**，不返回响应给用户。用于：

- 性能对比（v2 资源占用 vs v1）
- 兼容性验证（v2 解析新协议是否报错）
- 大改造的预演

C++ 高性能场景常用——重写一个核心模块，先用影子跑 1 个月。


## 03.灰度维度

### 3.1 按比例放量

最简单：在网关 / sidecar 用 random 抽样：

```cpp
if (rand_unit() < 0.01) route_to_v2();   // 1%
else                    route_to_v1();
```

注意：用 hash(user_id) 而不是真随机——**同一用户每次落到同一版本**，避免一会儿新一会儿旧的体验差。

```cpp
uint32_t h = hash(user_id);
if (h % 10000 < 100) route_to_v2();   // 1% 用户群体稳定切到 v2
```

### 3.2 按用户分群

| 群体 | 用法 |
|------|------|
| 内部员工 | 0.01% 切到 v2，员工先用，发现问题最快 |
| 灰度白名单 | 邀请 100 个早期用户 |
| 高价值用户 | **避免**，影响最大 |
| 风险用户 | 测兼容性问题（老设备、低端网络） |

### 3.3 按地域机房

```
Shanghai 机房 → v2
Beijing  机房 → v1
```

适合：

- 服务有明显地域聚集（用户主要在某区）
- 一旦出问题，单机房影响小
- 便于"跟着太阳走"——同一时刻只在低峰区放量

### 3.4 按设备版本

针对客户端协议变更：

```
iOS App ≥ 5.0 → 后端 v2（新协议）
iOS App < 5.0 → 后端 v1（兼容老协议）
```

服务端通过 User-Agent 路由。**这种灰度可能持续半年**——直到老版本客户端低于 1%，才能下线 v1。


## 04.C++ 服务特殊性

### 4.1 二进制兼容

C++ 灰度比 Java/Go 更复杂，因为**它有 ABI 概念**：

| 兼容层级 | 含义 | 灰度影响 |
|----------|------|----------|
| 源码兼容 | 重编译能用 | 无 |
| 二进制兼容（ABI） | 不重编译能用 | 影响 .so 升级 |
| 协议兼容 | 跨进程网络协议 | 影响微服务灰度 |

C++ 修改一个虚函数表（加虚函数、改基类、改成员顺序）就破坏 ABI——**老代码加载新 .so 直接 crash**。Itanium ABI 详见卷三第 22 章。

实战纪律：

- 公共库版本号（SONAME）按 ABI 兼容性升
- 灰度部署期间禁止修改公共 .so 中的类内部结构
- 新增字段要"加在末尾"且不影响现有 layout

### 4.2 状态迁移

C++ 服务常常持有大量内存状态（缓存、连接、定时器）。新旧实例并存时：

```
[v1 实例]  内存里有 1000 万 active 会话
   │
   优雅退出：
   1) 摘掉服务发现注册（不再接新流量）
   2) 等待存量请求处理完（drain）
   3) 持久化必要状态
   4) 退出

[v2 实例]  启动 → 加载状态 → 注册 → 接流量
```

C++ 服务没有 GC，**对象生命周期错乱常发生在退出阶段**——很多服务在 normal 运行没问题，shutdown 时各种崩溃。要专门测试退出路径。

### 4.3 长连接处理

HTTP/1.1 keepalive、WebSocket、gRPC 都是长连接。灰度时：

```
v1 实例下线 → 切断 1 万条长连接 → 客户端重连
                                    ↓
                              到 v2 实例
                                    ↓
                              v2 接受连接、协议是否兼容？
```

陷阱：

- 如果协议不向后兼容，老客户端连到 v2 直接断
- 短时间大量重连可能压垮 v2（"reconnect storm"）

解决：

1. 协议层面保证向后兼容（gRPC reflection）
2. 客户端加随机退避重连（jitter）
3. 服务端有连接限速（rate limit）


## 05.特性开关

### 5.1 feature flag

代码与发布解耦的杀器：

```cpp
if (FeatureFlag::IsEnabled("new_pricing", user_id)) {
    return new_pricing_logic(req);
} else {
    return old_pricing_logic(req);
}
```

特性：

- **代码可以提前合入主干**，但不立即生效
- 上线后"翻开关"放量，**不需要重启**
- 出问题"翻回"瞬间生效

### 5.2 配置中心模式

```
[配置中心 server]   ← 后台改配置
   │
   ├─ 实例 A（订阅）──→ 收到 push，本地缓存更新
   ├─ 实例 B
   └─ 实例 C
```

C++ 实现要点：

- 用 atomic / RCU 让配置切换无锁
- 单个 key 读取必须 < 100 ns（高频路径不能锁）
- 配置 schema 校验在 server 端，**避免下发 bad config 让所有实例炸**

```cpp
// RCU 模式示例
std::atomic<std::shared_ptr<Config>> g_config;

const Config& get_config() {
    return *g_config.load(std::memory_order_acquire);
}

void on_config_update(std::shared_ptr<Config> new_cfg) {
    g_config.store(new_cfg, std::memory_order_release);
    // 老配置由 shared_ptr 自动释放，安全
}
```

### 5.3 与发布解耦

```
[周一] 代码合入主干（包了 flag 防护，flag 默认 off）
[周二] 部署到生产（行为不变，flag off）
[周三] 内部员工开 flag（0.01% 流量）
[周四] 1% 用户开 flag
[下周] 100% 开
[下下周] 删除 flag 和老代码
```

好处：

- **部署变得无趣**：每天部署也不会出事
- 开关验证比代码验证轻得多
- 出事 30 秒回退（关 flag）

代价：

- 代码里到处是 if(flag)，要维护
- 必须有"flag 清理"的纪律，否则积成屎山


## 06.熔断与降级

灰度本身不能预防所有故障，运行期还要有自愈机制。

### 6.1 熔断器状态机

```
        失败率超阈值
[CLOSED] ───────────────→ [OPEN]
   ↑                          │
   │ 探测成功                 │ 等待 N 秒
   │                          ↓
   └────── [HALF_OPEN] ←──────┘
              │
              失败 → [OPEN]
              成功 → [CLOSED]
```

| 状态 | 行为 |
|------|------|
| CLOSED | 正常调用 |
| OPEN | 直接返回 fail，不调下游 |
| HALF_OPEN | 放少量请求探测下游恢复了吗 |

C++ 实现常用 [Hystrix-cpp](https://github.com/Netflix/Hystrix) 风格的库，或自己实现（约 200 行）。

### 6.2 限流算法

| 算法 | 特点 | 适合 |
|------|------|------|
| 计数器 | 简单，时间窗口边界突刺 | 粗略限流 |
| 滑动窗口 | 平滑边界 | API 网关 |
| 漏桶 | 输出速率恒定 | 后端保护 |
| 令牌桶 | 允许突发 | 用户友好型限流 |

C++ 高性能限流要**避免锁**。token bucket 用原子操作：

```cpp
class TokenBucket {
    std::atomic<int64_t> tokens_{capacity_};
    std::atomic<int64_t> last_refill_{now_ns()};
    
public:
    bool try_acquire() {
        refill();
        int64_t cur = tokens_.load(std::memory_order_acquire);
        while (cur > 0) {
            if (tokens_.compare_exchange_weak(cur, cur - 1)) return true;
        }
        return false;
    }
};
```

### 6.3 降级策略

服务无法保证完整功能时，主动减功能保命：

| 等级 | 牺牲 | 例子 |
|------|------|------|
| L1 软降 | 部分非核心功能 | 关掉个性化推荐，返回热门列表 |
| L2 半降 | 部分用户 | 非 VIP 限流 50% |
| L3 硬降 | 全功能但保读 | 写入直接拒绝，只支持读 |
| L4 紧急 | 服务静态化 | 返回 CDN 缓存的固定页面 |

降级开关应该**事先准备好、定期演练**——不能等出事才写降级代码。


## 07.回滚机制

### 7.1 三种回滚速度

| 类型 | 时间 | 实现 |
|------|------|------|
| 配置回滚 | 秒级 | feature flag / 配置中心 |
| 流量切换回滚 | 30 秒 | 网关 / 蓝绿 |
| 镜像/二进制回滚 | 5-15 分钟 | K8s rollback / docker tag 切换 |

**纪律**：能用配置回滚的不用流量切换，能用流量切换的不用镜像回滚。**回滚速度直接决定故障止损时间**。

### 7.2 数据库变更不可回滚

```
v1 → v2 加了字段 user_email
此后写入会带 email
回滚到 v1 → v1 不知道 email 字段，但数据库里已经有了
```

如果 v1 严格 schema 校验，回滚就崩。**所有 DB 变更应分两步**：

1. 先改 schema（v1 兼容）
2. 再改代码用新字段
3. 多天观察后才能反向操作（先回代码再改 schema）

### 7.3 回滚演练

回滚预案不演练等于没有。**每个团队季度至少演练 1 次**：

- 选低峰期（周末凌晨）
- 模拟"刚发布了 v2，触发指标异常"
- 真实点回滚按钮
- 测算 MTTR（mean time to recovery）

演练发现的问题往往是：

- 回滚按钮放错地方了，oncall 找了 5 分钟
- 镜像 v1 已被清理，回不去
- 状态迁移代码不向后兼容
- 监控大盘连"是否回滚成功"都看不出


## 08.稳定性体系

灰度只是工具，**稳定性是体系**：

```
[设计层]  无状态、幂等、重试、超时、限流
[发布层]  灰度、特性开关、蓝绿、影子
[运行层]  熔断、降级、自愈、限流
[监控层]  RED + USE + SLO 告警
[应急层]  Runbook、Oncall、演练
[复盘层]  blameless postmortem
```

任何一层缺失都会让整体质量塌方。本卷其他章节分别覆盖各层：

- 第 16 章：监控
- 第 18 章：复盘
- 卷三《并发与内存序》：并发设计层
- 卷二《工程卷》：CMake/CI 等部署层

C++ 服务还有自己的特殊议题：

- 内存稳定性（卷四第 5/6 章）
- 崩溃恢复（卷四第 1/2 章）
- 性能稳定性（卷四第 10/11/12 章）

读完整卷四，应该能把这些拼成一张图。
