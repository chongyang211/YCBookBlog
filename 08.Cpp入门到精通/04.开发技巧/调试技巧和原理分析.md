## 01.调试的基本思想

### 1.1 调试的本质

调试（Debugging）的本质是**缩小问题范围的过程**。从一个可观察的错误现象出发，通过系统性的方法逐步定位到导致错误的代码行。

```
调试的思维模型：

症状（可观察）        →  原因（不可见）
─────────────         ─────────────
崩溃/段错误           空指针解引用
输出结果错误           逻辑错误/边界条件
性能低下              算法复杂度/缓存未命中
死锁/卡住             锁顺序错误/竞争条件
内存持续增长           内存泄漏
```

### 1.2 调试的基本流程

```
1. 复现（Reproduce）
   │ 稳定复现是调试的前提
   │ 如果不能稳定复现，收集环境信息、增加日志
   ↓
2. 隔离（Isolate）
   │ 缩小问题范围：哪个模块？哪个函数？哪行代码？
   │ 方法：二分法注释代码、最小化测试用例
   ↓
3. 定位（Locate）
   │ 使用调试器、日志、断言精确定位
   │ 理解代码的预期行为 vs 实际行为
   ↓
4. 修复（Fix）
   │ 修改代码，确保修复不引入新问题
   ↓
5. 验证（Verify）
   │ 运行原来的复现步骤，确认问题解决
   │ 运行回归测试，确保没有副作用
   ↓
6. 预防（Prevent）
   添加测试用例、断言、文档
```

### 1.3 常见的调试工具

| 工具 | 用途 | 场景 |
|------|------|------|
| GDB/LLDB | 交互式调试 | 逻辑错误、崩溃分析 |
| AddressSanitizer | 内存错误检测 | 越界、Use-After-Free、泄漏 |
| ThreadSanitizer | 线程安全检测 | 数据竞争、死锁 |
| UBSanitizer | 未定义行为检测 | 整数溢出、空指针 |
| Valgrind | 内存检测与分析 | 泄漏、未初始化读取 |
| perf | 性能分析 | CPU热点、缓存未命中 |
| strace | 系统调用追踪 | IO问题、权限问题 |
| ltrace | 库调用追踪 | 库函数调用序列 |
| objdump/nm | 二进制分析 | 符号表、反汇编 |


## 02.GDB调试核心技巧

### 2.1 基本操作

```bash
# 编译时必须加-g保留调试信息
g++ -g -O0 -o myapp main.cpp

# 启动GDB
gdb ./myapp

# GDB核心命令
(gdb) run [args]        # 运行程序
(gdb) run < input.txt   # 重定向输入
(gdb) continue (c)      # 继续执行
(gdb) next (n)          # 单步执行（跳过函数调用）
(gdb) step (s)          # 单步执行（进入函数调用）
(gdb) finish            # 执行到当前函数返回
(gdb) until 100         # 执行到第100行
(gdb) return [value]    # 强制从当前函数返回
(gdb) quit (q)          # 退出GDB
```

### 2.2 断点管理

```bash
# 设置断点
(gdb) break main.cpp:42       # 在文件第42行设断点
(gdb) break processData       # 在函数入口设断点
(gdb) break MyClass::method   # 在类方法上设断点

# 条件断点（只在条件满足时中断）
(gdb) break main.cpp:42 if count > 100
(gdb) break processData if ptr == 0x0

# 临时断点（只触发一次）
(gdb) tbreak main.cpp:42

# 管理断点
(gdb) info breakpoints      # 列出所有断点
(gdb) delete 3              # 删除编号3的断点
(gdb) disable 2             # 禁用编号2的断点
(gdb) enable 2              # 启用编号2的断点

# 监视点（变量值变化时中断）
(gdb) watch counter          # counter被修改时中断
(gdb) rwatch *0x7fff1234     # 内存地址被读取时中断
(gdb) awatch data->size      # 被读或写时中断

# 捕获点
(gdb) catch throw            # C++异常抛出时中断
(gdb) catch catch            # C++异常捕获时中断
(gdb) catch syscall write    # write系统调用时中断
```

### 2.3 变量和内存检查

```bash
# 打印变量
(gdb) print counter          # 打印变量值
(gdb) print *ptr             # 解引用指针
(gdb) print arr[0]@10        # 打印数组前10个元素
(gdb) print/x value          # 十六进制格式
(gdb) print/t value          # 二进制格式
(gdb) print sizeof(MyStruct) # 打印类型大小

# 显示表达式（每次停下来都自动打印）
(gdb) display counter
(gdb) display/x *ptr
(gdb) undisplay 1            # 取消显示

# 检查内存
(gdb) x/10wx 0x7fff1234     # 从地址开始打印10个32位字（hex格式）
(gdb) x/20bx ptr            # 从ptr开始打印20个字节
(gdb) x/5i $rip             # 从当前指令开始反汇编5条指令
(gdb) x/s str_ptr           # 以字符串格式打印

# x命令格式: x/[数量][格式][单位] 地址
# 格式: x(hex) d(decimal) u(unsigned) o(octal) t(binary) s(string) i(instruction)
# 单位: b(byte) h(halfword,2B) w(word,4B) g(giant,8B)

# 类型信息
(gdb) ptype myObject         # 打印对象的类型定义
(gdb) info locals            # 打印所有局部变量
(gdb) info args              # 打印函数参数
```

### 2.4 多线程调试

```bash
# 查看线程
(gdb) info threads           # 列出所有线程
  Id   Target Id         Frame
* 1    Thread 0x7f... "main"     at main.cpp:42
  2    Thread 0x7f... "worker1"  at worker.cpp:100
  3    Thread 0x7f... "worker2"  at worker.cpp:87

# 切换线程
(gdb) thread 2               # 切换到线程2

# 对所有线程执行命令
(gdb) thread apply all bt    # 打印所有线程的栈回溯
(gdb) thread apply 2 3 bt    # 打印线程2和3的栈回溯

# 线程调度控制
(gdb) set scheduler-locking on    # 只运行当前线程（其他线程冻结）
(gdb) set scheduler-locking step  # 单步时只运行当前线程
(gdb) set scheduler-locking off   # 所有线程自由运行（默认）

# 在特定线程上设断点
(gdb) break worker.cpp:100 thread 2
```


## 03.内存调试工具

### 3.1 AddressSanitizer

```bash
# 编译时启用（GCC/Clang都支持）
g++ -fsanitize=address -g -O1 -o myapp main.cpp

# ASan能检测的问题：
# - 堆缓冲区溢出（Heap Buffer Overflow）
# - 栈缓冲区溢出（Stack Buffer Overflow）
# - 全局缓冲区溢出（Global Buffer Overflow）
# - Use-After-Free
# - Use-After-Return（使用-fsanitize-address-use-after-return=always）
# - Double-Free
# - 内存泄漏（配合-fsanitize=leak）
```

```cpp
// ASan会自动检测并报告这些问题
void heap_buffer_overflow() {
    int* arr = new int[10];
    arr[10] = 42;  // ASan报告：heap-buffer-overflow
    delete[] arr;
}

void use_after_free() {
    int* p = new int(42);
    delete p;
    *p = 100;  // ASan报告：heap-use-after-free
}

void stack_buffer_overflow() {
    int arr[10];
    arr[10] = 42;  // ASan报告：stack-buffer-overflow
}
```

**ASan的底层原理**：

```
ASan使用影子内存（Shadow Memory）追踪内存状态：

应用内存                     影子内存
┌───────────────┐           ┌────────┐
│  8 bytes      │  ──映射──→ │ 1 byte │
│               │           │        │
└───────────────┘           └────────┘

影子字节的含义：
0x00: 全部8字节可访问
0x01-0x07: 前1-7个字节可访问
0x80+: 各种不可访问状态
  0xfa: 堆缓冲区右侧的红区
  0xfd: 已释放的内存
  0xf1: 栈缓冲区左侧的红区
  0xf3: 栈缓冲区右侧的红区

每次内存访问前，编译器插入检查代码：
  shadow_value = shadow_mem[addr >> 3]
  if (shadow_value != 0 && (shadow_value < (addr & 7) + size))
      report_error()  // 非法访问！

性能开销：约2x慢，内存约2-3x
```

### 3.2 Valgrind

```bash
# 运行Memcheck（默认工具）
valgrind --leak-check=full --show-leak-kinds=all ./myapp

# 常见输出解读
==1234== Invalid read of size 4          # 读取非法内存
==1234==    at 0x401234: func (main.cpp:42)
==1234==  Address 0x5a2c040 is 0 bytes after a block of size 40 alloc'd
==1234==    at 0x4C2BE45: operator new[](unsigned long) (vg_replace_malloc.c)
# → 堆缓冲区溢出：访问了紧随40字节分配块之后的内存

==1234== Use of uninitialised value      # 使用未初始化的值
==1234== Conditional jump depends on uninitialised value(s)
# → 分支条件依赖于未初始化的变量

==1234== LEAK SUMMARY:
==1234==    definitely lost: 72 bytes in 3 blocks    # 确定泄漏
==1234==    indirectly lost: 1,024 bytes in 1 blocks # 间接泄漏
==1234==    possibly lost: 0 bytes in 0 blocks       # 可能泄漏
==1234==    still reachable: 256 bytes in 2 blocks   # 程序结束时仍可达
```

**Valgrind的底层原理**：

```
Valgrind是一个动态二进制翻译框架：
1. 不修改源程序，运行时翻译机器码
2. 将每条x86指令翻译为Valgrind的中间表示（VEX IR）
3. 在VEX IR上插入检测代码
4. 将带检测的IR编译回机器码执行

优点：不需要重新编译
缺点：运行速度约为正常的10-30倍
```

### 3.3 ThreadSanitizer

```bash
# 编译时启用
g++ -fsanitize=thread -g -O1 -o myapp main.cpp

# TSan检测的问题：
# - 数据竞争（Data Race）
# - 死锁（Deadlock，使用-fsanitize=thread配合锁检测）
```

```cpp
// TSan会报告数据竞争
int counter = 0;

void thread_func() {
    counter++;  // TSan报告：data race on 'counter'
}

int main() {
    std::thread t1(thread_func);
    std::thread t2(thread_func);
    t1.join();
    t2.join();
}
```

```
TSan输出示例：
WARNING: ThreadSanitizer: data race (pid=1234)
  Write of size 4 at 0x7f1234 by thread T1:
    #0 thread_func() main.cpp:4
  Previous write of size 4 at 0x7f1234 by thread T2:
    #0 thread_func() main.cpp:4
  Location is global 'counter' of size 4
```


## 04.编译器辅助调试

### 4.1 警告选项

```bash
# 推荐的警告组合
g++ -Wall -Wextra -Wpedantic -Werror main.cpp

# 各选项的含义
-Wall       # 开启大部分警告（但不是"全部"）
-Wextra     # 额外的警告（如未使用的参数）
-Wpedantic  # 严格ISO C++合规检查
-Werror     # 将警告视为错误
-Wshadow    # 变量遮蔽警告
-Wnon-virtual-dtor  # 没有虚析构函数的多态基类
-Wold-style-cast    # C风格强制转换
-Wconversion        # 隐式类型转换可能丢失精度
-Wsign-conversion   # 有符号/无符号转换
-Wnull-dereference  # 可能的空指针解引用
-Wformat=2          # printf格式字符串检查
```

### 4.2 静态分析

```bash
# Clang静态分析器
scan-build g++ -o myapp main.cpp
# 生成HTML报告，展示可能的bug

# Cppcheck
cppcheck --enable=all --std=c++17 main.cpp

# Clang-Tidy
clang-tidy main.cpp -- -std=c++17
# 检查编码规范、可能的bug、性能问题、可读性
```


## 05.性能调试与分析

### 5.1 perf工具

```bash
# CPU性能分析
perf stat ./myapp                    # 统计信息（指令数、缓存命中率等）
perf record -g ./myapp               # 采样记录
perf report                          # 查看报告

# 常见的性能指标
perf stat -e cache-misses,cache-references,instructions,cycles ./myapp
# cache-misses / cache-references → 缓存命中率
# instructions / cycles → IPC（每周期指令数）

# 函数级热点
perf record -g --call-graph dwarf ./myapp
perf report --sort=dso,symbol
```

### 5.2 火焰图

```bash
# 使用Brendan Gregg的FlameGraph工具
perf record -g -F 99 ./myapp
perf script > out.perf
./stackcollapse-perf.pl out.perf > out.folded
./flamegraph.pl out.folded > flamegraph.svg

# X轴：栈帧宽度 = 该函数在采样中的占比（不是时间顺序）
# Y轴：调用栈深度
# 宽的函数 = CPU热点，优化重点
```


## 06.调试的底层原理

### 6.1 ptrace系统调用

GDB等调试器的核心依赖于`ptrace`系统调用：

```c
#include <sys/ptrace.h>

// ptrace是Linux调试的基础设施
long ptrace(enum __ptrace_request request, pid_t pid, void *addr, void *data);

// 常用请求：
PTRACE_ATTACH    // 附加到目标进程
PTRACE_DETACH    // 分离
PTRACE_PEEKTEXT  // 读取目标进程的代码/数据
PTRACE_POKETEXT  // 修改目标进程的代码/数据
PTRACE_GETREGS   // 读取寄存器
PTRACE_SETREGS   // 设置寄存器
PTRACE_SINGLESTEP // 单步执行一条指令
PTRACE_CONT      // 继续执行
PTRACE_SYSCALL   // 在系统调用入口/出口停下

// ptrace的工作模式：
// 1. 调试器通过ptrace附加到目标进程
// 2. 目标进程变为"被追踪"状态
// 3. 目标进程遇到信号或断点时，暂停并通知调试器
// 4. 调试器通过ptrace检查/修改目标进程状态
// 5. 调试器通过ptrace让目标进程继续执行
```

### 6.2 断点的实现原理

**软件断点**（最常用）：

```
原理：用INT3指令（0xCC）替换目标地址的原始指令

设置断点：
1. 调试器保存目标地址的原始字节
2. 用PTRACE_POKETEXT将该字节替换为0xCC (INT3)

触发断点：
1. CPU执行到0xCC，产生#BP异常
2. 内核向目标进程发送SIGTRAP
3. 进程暂停，调试器收到通知

恢复执行：
1. 调试器恢复原始字节（PTRACE_POKETEXT）
2. 将RIP寄存器回退1（指向被替换的指令）
3. 单步执行原始指令
4. 重新设置断点（再次替换为0xCC）
5. 继续执行

示例：
原始代码:  0x401234: 48 89 e5    mov rbp, rsp
设断点后:  0x401234: CC 89 e5    int3 + 垃圾
```

### 6.3 单步执行的原理

```
x86 CPU的EFLAGS寄存器中有一个TF（Trap Flag）位：
  TF=1: CPU执行每条指令后产生#DB（Debug Exception）
  TF=0: 正常执行

单步执行流程：
1. 调试器通过PTRACE_SINGLESTEP请求单步
2. 内核设置目标进程的EFLAGS.TF = 1
3. 恢复目标进程执行
4. CPU执行一条指令后触发#DB
5. 内核自动清除TF位，向进程发送SIGTRAP
6. 进程暂停，调试器检查新状态
```

### 6.4 监视点的原理

```
硬件监视点利用CPU的调试寄存器（DR0-DR7）：

DR0-DR3: 4个地址寄存器（监视的内存地址）
DR6:     状态寄存器（哪个监视点被触发）
DR7:     控制寄存器（监视类型和长度）

设置监视点：
1. 调试器将目标地址写入DR0-DR3之一
2. 在DR7中配置监视类型：
   00 = 仅执行断点
   01 = 数据写入
   10 = I/O读写（通常不用）
   11 = 数据读取或写入
3. 配置监视长度：1/2/4/8字节

触发：
1. CPU在执行每条指令时检查内存访问是否命中DR0-DR3
2. 命中时触发#DB异常
3. 内核向进程发送SIGTRAP

限制：
- 只有4个硬件监视点
- 如果需要更多，GDB会退化为软件实现（非常慢）
```

**总结**：调试是C++开发中最重要的实践技能之一。理解调试器的底层原理（ptrace、断点实现、单步执行），掌握内存检测工具（ASan、Valgrind、TSan），善用编译器警告和静态分析，才能在复杂的C++项目中快速定位和解决问题。
