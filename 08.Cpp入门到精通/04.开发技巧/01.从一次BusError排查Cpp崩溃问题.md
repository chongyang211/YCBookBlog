## 01.前言：一次令人意外的崩溃

### 1.1 复现现场

事情的起因来自一段非常普通的命令行输出：

```bash
CHONGYYANG-MB1:worker yangchong$ g++ Worker.cpp Boss.cpp Manager.cpp Employee.cpp WorkerManager.cpp
CHONGYYANG-MB1:worker yangchong$ ./a.out
ID: 1, Name: c, Did: 1
Bus error: 10
```

这是一个用 C++ 写的"职工管理系统"，按 [02.综合案例/03.职工管理系统](../02.综合案例/03.职工管理系统.md) 中的设计，系统包含一个抽象基类 `Employee` 和三个派生类 `Worker`、`Manager`、`Boss`，由 `WorkerManager` 统一管理。

程序启动后做了两件事：

1. 从文件中读取一个职工的信息并打印
2. 紧接着崩了，提示 `Bus error: 10`

最让人疑惑的是：**第一行明明已经成功打印了，意味着相关对象至少已经被创建并能正常访问**。

### 1.2 看似毫无头绪

如果只看错误现象，新人通常会问出三类问题：

- 是不是 `g++` 编译命令写错了？
- 是不是文件路径有问题？
- 是不是某个 `.cpp` 文件里某个函数写错了？

但这些都是"症状层面"的猜测。真正的调试要回答的是：**程序在崩溃的那一瞬间，到底访问了什么不该访问的内存？**

### 1.3 本文要解决的问题

本文以这次 `Bus error: 10` 为真实主线，由浅入深地走过一个完整的崩溃调试流程：

| 阶段 | 目标 |
|------|------|
| 读懂信号 | 弄清 `Bus error` 是哪个信号、为什么会发 |
| 经验排查 | 用最快的方式锁定可疑点 |
| 工具加持 | lldb / ASan / 编译告警的正确用法 |
| 定位根因 | 不止"修好了"，要能解释"为什么坏了" |
| 修复论证 | 用三种修复方案 + 多种验证手段闭环 |

读完本文，你不仅能解决这个具体 BUG，更能掌握一类 C++ 崩溃问题的通用排查框架。


## 02.读懂错误信号本身

### 2.1 Bus error 究竟是什么

`Bus error` 是操作系统通过 **`SIGBUS`** 信号告知应用："你访问了一个物理上无法被 CPU 处理的内存地址"。

| 维度 | 说明 |
|------|------|
| 信号名 | SIGBUS（编号在 macOS / Linux 上略有差异） |
| 触发者 | 内核 / 硬件 |
| 默认动作 | 终止进程（core dump） |
| 典型成因 | 未对齐访问、文件映射越界、写入只读段、野指针落到不合法地址 |

直觉上可以这样理解：**SIGBUS 是"硬件层面 / 物理地址层面" 不允许访问，SIGSEGV 是"页表 / 权限层面"不允许访问**。但在用户态代码里，二者经常表现得相似，且不同平台对它们的划分并不严格。

### 2.2 SIGBUS 与 SIGSEGV 的区别

```
        访问无效虚拟地址           对齐错误 / mmap 越界 / 物理总线错误
           ↓                                    ↓
        SIGSEGV (11)                        SIGBUS (10)
       Segmentation fault                  Bus error
```

实际工作中，可以把它们视为"同源不同名"的崩溃，处理流程几乎一致：**先看调用栈，再看访问的是哪个地址。**

### 2.3 macOS 上的特殊性

macOS（Darwin）继承了 BSD 的信号实现，对未对齐访问、被截断的 mmap 文件、空指针解引用等都更倾向于发 `SIGBUS`，而 Linux 同样的代码可能更常见 `SIGSEGV`。

这也是为什么本案例在 macOS 上看到 `Bus error: 10`，但同样的代码在某些 Linux 上可能直接是 `Segmentation fault`。

### 2.4 错误码 10 的含义

那个 `10` 不是 errno，而是 **macOS 上 SIGBUS 的信号编号**。可以通过 `kill -l` 查看：

```bash
$ kill -l | tr ' ' '\n' | grep -n BUS
10) BUS
```

所以 `Bus error: 10` 翻译成人话就是：**"进程收到了 10 号信号 SIGBUS，已被强制终止。"**


## 03.从经验出发的初步排查

### 3.1 先列出可疑点清单

在不打开调试器之前，先用经验快速过一遍代码可疑点。结合本案例的代码（多态、多文件、读文件、动态分配），可疑点优先级如下：

| 优先级 | 可疑模式 | 在职工管理系统中的可能位置 |
|--------|----------|-----------------------------|
| ★★★★★ | 野指针 / 未初始化指针 | `Employee** m_EmpArray` 是否被全初始化 |
| ★★★★☆ | 数组越界 | 文件中职工人数与实际数组容量是否一致 |
| ★★★★☆ | 释放后再使用 | 析构后还在循环里访问 |
| ★★★☆☆ | 空指针解引用 | 文件不存在分支返回的指针 |
| ★★★☆☆ | 虚函数表破坏 | 派生类对象通过 `Employee*` 操作时类型错误 |
| ★★☆☆☆ | 对齐错误 | 极少见，本案例几乎不可能 |

### 3.2 简单复盘代码逻辑

输出 `ID: 1, Name: c, Did: 1` 说明程序能成功读到第一条记录。但紧接着崩溃，意味着循环里第一次成功，第二次（或循环结束之后）失败。

这种"第一次成功、第二次失败"的模式，**99% 是数组越界或指针未初始化**。可以重点关注这种代码：

```cpp
// 高度疑似的写法
for (int i = 0; i < this->m_EmpNum; i++) {
    cout << "ID: " << this->m_EmpArray[i]->m_Id
         << ", Name: " << this->m_EmpArray[i]->m_Name
         << ", Did: " << this->m_EmpArray[i]->m_DeptId
         << endl;
}
```

如果 `m_EmpNum` 比实际填充进数组的元素多，越界访问的 `m_EmpArray[i]` 就是一个未初始化的指针，对它解引用，恭喜你——`Bus error` 或 `Segmentation fault` 二选一。

### 3.3 三种最常见的崩溃模式

```
模式 A：未初始化指针
    Employee** arr = new Employee*[10];   // 10 个槽位都是垃圾值
    cout << arr[0]->m_Id;                 // 直接崩

模式 B：数组越界
    arr[0] = new Worker(...);             // 只填了一个
    for (int i = 0; i < 10; ++i) ...      // 但循环了十次

模式 C：use-after-free
    delete arr[0];
    cout << arr[0]->m_Id;                 // 再次访问已释放的对象
```

本案例最像 **A + B 的组合体**：数组按"文件中记录的职工数"分配，但因为某个分支没把每个槽都赋值，循环到没赋值的位置就崩了。


## 04.正确开启调试模式

### 4.1 添加调试符号编译

最初的命令行没带 `-g`，导致 lldb 看到的栈是裸地址。重新编译：

```bash
g++ -g -O0 -Wall -Wextra \
    Worker.cpp Boss.cpp Manager.cpp Employee.cpp WorkerManager.cpp \
    -o worker
```

参数解释：

| 参数 | 作用 |
|------|------|
| `-g` | 生成调试符号，让调试器看到行号 / 变量名 |
| `-O0` | 关闭优化，避免变量被优化掉看不见 |
| `-Wall -Wextra` | 打开常用警告，编译期就能筛掉一批问题 |
| `-o worker` | 输出名为 `worker`，比默认的 `a.out` 更直观 |

### 4.2 打开警告与未定义行为检测

进一步加上：

```bash
g++ -g -O1 -Wall -Wextra \
    -fsanitize=address,undefined -fno-omit-frame-pointer \
    *.cpp -o worker_asan
```

`-fsanitize=address,undefined` 会在运行期检测：

- 越界读写（堆 / 栈 / 全局）
- Use-After-Free
- 未初始化的指针访问
- 整数溢出 / 错误强转 / 空指针解引用

代价是程序大概慢 2-5 倍，但调试期间是**最值得的投入**。

### 4.3 用 ulimit 打开 core dump

如果程序在生产或者 CI 上崩溃，能拿到 core dump 是后期排查的救命稻草：

```bash
ulimit -c unlimited
./worker
# 崩溃后会产生 core 文件，使用 lldb 加载：
lldb worker -c /cores/core.<pid>
```

macOS 默认会把 core 写到 `/cores/`，记得检查目录是否存在并有写权限。

### 4.4 给可执行文件命名

最初输入的命令是：

```bash
g++ Worker.cpp Boss.cpp Manager.cpp Employee.cpp WorkerManager.cpp
./a.out
```

下意识就用了默认的 `a.out`。这个习惯有两个隐患：

1. 多个项目都生成同名 `a.out`，调试时容易调错
2. core dump 文件名往往是 `core.a.out.<pid>`，过几天自己都不认识

所以**给可执行文件起个有意义的名字**是很小但很有效的工程纪律。


## 05.使用 lldb 精确定位崩溃点

### 5.1 启动调试器

macOS 默认装的是 lldb（不是 gdb）。命令几乎和 gdb 一一对应：

```bash
lldb ./worker
```

进入交互界面：

```
(lldb) target create "./worker"
Current executable set to './worker' (x86_64).
(lldb)
```

### 5.2 运行并复现崩溃

直接运行：

```
(lldb) run
Process 12345 launched: './worker' (x86_64)
ID: 1, Name: c, Did: 1
Process 12345 stopped
* thread #1, queue = 'com.apple.main-thread',
  stop reason = EXC_BAD_ACCESS (code=1, address=0x0)
    frame #0: 0x0000000100002a4f worker`WorkerManager::Show_Emp() at WorkerManager.cpp:75:24
```

注意几个关键信息：

- **stop reason**：`EXC_BAD_ACCESS`，正是 SIGBUS / SIGSEGV 的底层异常
- **address=0x0**：访问的是空地址（如果是 `0xc4...` 那种诡异值，就是野指针）
- **frame #0**：崩溃发生的精确文件 + 行号

### 5.3 查看调用栈

```
(lldb) bt
* thread #1
  * frame #0: 0x...  worker`WorkerManager::Show_Emp(this=0x7fff...) at WorkerManager.cpp:75:24
    frame #1: 0x...  worker`main + 64 at WorkerManager.cpp:142:9
    frame #2: 0x... libdyld.dylib`start + 1
```

`bt` 把整条调用链打了出来。崩溃发生在 `Show_Emp()` 第 75 行——这就是显示职工信息的循环。

### 5.4 检查崩溃帧的局部变量

```
(lldb) frame variable
(WorkerManager *) this = 0x00007fff5fbff828
(int) i = 1
```

- `i = 1` 说明已经成功显示了第 0 个元素，**正在尝试访问第 1 个元素时崩了**
- 而原始输出 `ID: 1, Name: c, Did: 1` 也只看到了一行

继续看 `m_EmpArray` 的内容：

```
(lldb) p this->m_EmpNum
(int) $0 = 2

(lldb) p this->m_EmpArray[0]
(Employee *) $1 = 0x0000000100600000

(lldb) p this->m_EmpArray[1]
(Employee *) $2 = 0x00007ffeefbff5a8   ← 看起来像是栈地址或随机值
```

至此真相已经显现：`m_EmpNum` 是 2，但 `m_EmpArray` 只有第 0 个槽是合法对象指针，**第 1 个槽是未初始化的垃圾值**。

### 5.5 切换帧定位真正的元凶

崩溃点是 `Show_Emp`，但**真正的 BUG 在更早的地方**——是谁让 `m_EmpNum=2` 而 `m_EmpArray[1]` 没有被赋值？

```
(lldb) frame select 1
(lldb) list
```

往上回溯到 `WorkerManager` 的构造函数，发现是 `init_Emp()` 里的循环条件写错了，导致只填充了 `m_EmpNum-1` 个元素。

> **调试金句**：*The crash site is rarely the bug site.*  
> 崩溃发生的位置，往往不是 BUG 本身的位置。它只是"症状暴露之处"。


## 06.锁定问题：野指针的来源

### 6.1 输出第一行的玄机

为什么程序能成功打印 `ID: 1, Name: c, Did: 1`？因为：

- `m_EmpArray[0]` 确实是合法的 `Worker*`
- 它的字段读取没有任何问题
- 流刷新到了 stdout

但循环 `i=1` 时进入了未初始化的内存，直接踩雷。

### 6.2 数组只填了一个元素

定位到 `init_Emp()`：

```cpp
// 假想还原后的有问题代码
void WorkerManager::init_Emp() {
    ifstream ifs(FILENAME, ios::in);
    int id, dId;
    string name;

    int index = 0;
    while (ifs >> id && ifs >> name && ifs >> dId) {
        // 错误一：只在第一行读了一次就 break
        m_EmpArray[index] = new Worker(id, name, dId);
        break;       // ← 万恶之源
        index++;
    }
    // m_EmpNum 在 get_EmpNum() 里被算成了文件实际行数
    ifs.close();
}
```

或者更隐晦的版本：

```cpp
// m_EmpNum 提前在 get_EmpNum() 算出来的行数 = 2
// 但 init_Emp 里没把第二行写进数组（被 if 误过滤）
```

无论是哪种，本质都是 **"数组容量声称的"和"实际填充的"对不上**。

### 6.3 m_EmpNum 与数组容量的错位

代码里有两个独立维护的状态：

```cpp
int m_EmpNum;          // 职工总数（从文件统计来）
Employee** m_EmpArray; // 实际存放的对象数组
```

只要这两者的"含义"和"实际"不一致，就一定崩。**这种"双源真相"是 C++ 老 BUG 之王**。

### 6.4 未初始化指针的危害

C++ 中 `new T*[n]` 不会把指针清零（除非加 `()`）：

```cpp
Employee** arr = new Employee*[10];     // 内容是垃圾
Employee** arr = new Employee*[10]();   // 全部置 nullptr
```

第一种写法下，未填充的槽位会是任意值。**任意值意味着任意行为**：

- 落到不可访问区域 → SIGBUS / SIGSEGV
- 落到一段恰好可读的内存 → 读出乱码字符串
- 落到看起来合法的对象 → 程序静默错误，最危险


## 07.Sanitizer 一键揪出根因

### 7.1 AddressSanitizer 的使用

如果不想自己一步步在 lldb 里点，**ASan 可以一句话告诉你哪里有问题**：

```bash
g++ -g -O1 -fsanitize=address -fno-omit-frame-pointer \
    *.cpp -o worker_asan
./worker_asan
```

### 7.2 实际的 ASan 报告解析

ASan 会输出类似下面的报告：

```
==45623==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x60200000eff8
READ of size 8 at 0x60200000eff8 thread T0
    #0 0x10... in WorkerManager::Show_Emp() WorkerManager.cpp:75
    #1 0x10... in main WorkerManager.cpp:142

0x60200000eff8 is located 0 bytes to the right of 8-byte region
[0x60200000eff0,0x60200000eff8) allocated by thread T0 here:
    #0 0x10... in operator new[](unsigned long)
    #1 0x10... in WorkerManager::WorkerManager() WorkerManager.cpp:23
```

直接告诉你三件事：

1. 错误类型：**heap-buffer-overflow**（堆缓冲区越界）
2. 越界访问发生在：`WorkerManager.cpp:75`
3. 那块内存是在 `WorkerManager.cpp:23` 申请的，且大小只有 8 字节（`sizeof(Employee*)`）

**8 字节 = 1 个指针**，但 `Show_Emp` 试图读第 2 个指针，立刻穿帮。

### 7.3 为什么 ASan 比 lldb 更高效

| 维度 | lldb | AddressSanitizer |
|------|------|------------------|
| 信息粒度 | 崩溃那一刻的栈 + 变量 | 越界 / UAF / 泄漏 / 未初始化 |
| 是否需要复现 | 需要稳定崩溃 | 不崩也能查出潜在越界 |
| 学习曲线 | 命令较多 | 编译选项 + 看报告 |
| 性能开销 | 仅调试时启动 | 运行慢 2-5 倍 |
| 推荐用法 | 在线深入分析 | CI / 日常开发默认开启 |

**实战建议**：日常开发期默认开 ASan；线上抓回的 core dump 用 lldb 分析。


## 08.修复方案与代码改造

### 8.1 修复一：保证数组容量与计数一致

最小改动版本——把 `init_Emp` 里漏写的 `index++` 补上、保证读到一行就填一格：

```cpp
void WorkerManager::init_Emp() {
    ifstream ifs(FILENAME, ios::in);
    int id, dId;
    string name;
    int index = 0;

    while (ifs >> id >> name >> dId) {
        Employee* worker = nullptr;
        if (dId == 1) {
            worker = new Worker(id, name, dId);
        } else if (dId == 2) {
            worker = new Manager(id, name, dId);
        } else {
            worker = new Boss(id, name, dId);
        }
        m_EmpArray[index] = worker;
        index++;
    }
    ifs.close();

    // 防御：确保循环结束后 index == m_EmpNum
    assert(index == m_EmpNum);
}
```

并把 `new Employee*[m_EmpNum]` 改为 `new Employee*[m_EmpNum]()` 给所有指针默认 `nullptr`，这样即使再出错，也是 `nullptr` 解引用 + `assert` 触发，而不是野指针。

### 8.2 修复二：使用智能指针管理对象

更进一步，使用 `unique_ptr` 让生命周期自动管理：

```cpp
#include <memory>
#include <vector>

class WorkerManager {
public:
    std::vector<std::unique_ptr<Employee>> m_Emps;
    // ...
};

void WorkerManager::init_Emp() {
    ifstream ifs(FILENAME, ios::in);
    int id, dId;
    string name;

    while (ifs >> id >> name >> dId) {
        if (dId == 1)      m_Emps.emplace_back(std::make_unique<Worker>(id, name, dId));
        else if (dId == 2) m_Emps.emplace_back(std::make_unique<Manager>(id, name, dId));
        else               m_Emps.emplace_back(std::make_unique<Boss>(id, name, dId));
    }
}
```

不再需要：

- 单独维护 `m_EmpNum`
- 在析构函数里 `for (int i = 0; i < m_EmpNum; ++i) delete m_EmpArray[i];`
- 担心 `delete` 漏写造成内存泄漏

### 8.3 修复三：用 vector 替代裸数组

哪怕暂时不上 `unique_ptr`，至少把 `Employee**` 换成 `std::vector<Employee*>`：

```cpp
std::vector<Employee*> m_EmpArray;

// Show_Emp() 直接：
for (size_t i = 0; i < m_EmpArray.size(); ++i) {
    m_EmpArray[i]->showInfo();
}
```

**`size()` 永远等于真实元素数**，就再也不会出现"声称 2 个、实际 1 个"的错位。

### 8.4 修复四：构造函数初始化所有成员

`WorkerManager` 的构造函数应明确初始化每一个成员：

```cpp
WorkerManager::WorkerManager()
    : m_EmpNum(0)
    , m_EmpArray(nullptr)
    , m_FileIsEmpty(true)
{
    // 再根据文件存在与否补充初始化
}
```

这能避免另一类同样会触发 `Bus error` 的潜伏 BUG：**构造函数没走完文件分支，导致成员是垃圾**。


## 09.论证修复的有效性

### 9.1 重跑原始复现路径

最重要的一步——回到最初的命令行，用同样的输入复现一次：

```bash
./worker
ID: 1, Name: c, Did: 1
ID: 2, Name: 张三, Did: 2
程序正常退出。
```

**没有崩溃 ≠ BUG 修好了**，但**和原来路径走完同样的步骤还能崩 = 修复一定无效**。所以这一步是必要不充分条件。

### 9.2 边界条件回归测试

构造一组覆盖边界的测试输入：

| 用例 | 输入 | 期望行为 |
|------|------|----------|
| 空文件 | 0 行 | `m_FileIsEmpty=true`，提示无数据 |
| 1 条记录 | 1 行 | 正常显示 |
| 2 条记录 | 2 行 | 正常显示两行 |
| 100 条记录 | 100 行 | 正常显示 |
| 文件不存在 | 删除 | 创建空管理器，无崩溃 |
| 文件中部分行格式错 | 中间一行残缺 | 优雅跳过或报错，不崩 |

每条都跑一遍。这才是"论证修复"的核心。

### 9.3 使用 ASan 二次验证

用 ASan 编译版本再跑一次：

```bash
g++ -g -O1 -fsanitize=address *.cpp -o worker_asan
./worker_asan
```

如果输出全部正常、ASan 没有任何报错，可以基本确信：

- 没有越界
- 没有 UAF
- 没有内存泄漏（ASan 在退出时会顺便检查泄漏）

### 9.4 压力测试与稳定性观察

写一个简单的循环压力脚本：

```bash
for i in $(seq 1 1000); do
    ./worker_asan < scripted_input.txt > /dev/null || echo "fail at $i"
done
```

跑 1000 次都不崩、ASan 没报错，那这个修复就算闭环了。


## 10.常见 Bus error 的其他场景

虽然本案例的根因是数组越界，但 SIGBUS 还有几种你迟早会遇到的"花式触发法"，提前混个脸熟。

### 10.1 内存映射文件被截断

```cpp
int fd = open("data.bin", O_RDONLY);
char* p = (char*)mmap(nullptr, 4096, PROT_READ, MAP_PRIVATE, fd, 0);
// 假如 data.bin 实际只有 100 字节
char c = p[200];   // ← SIGBUS：访问了文件实际不存在的部分
```

`mmap` 返回的虚拟地址区间可能比文件实际长度大，访问超出文件长度的页面会触发 SIGBUS。

### 10.2 栈溢出

无限递归或者超大栈数组都会让 SP 跑出栈页，进而触发 SIGBUS / SIGSEGV：

```cpp
void f() { char buf[16 * 1024 * 1024]; f(); }   // 一次开 16MB 栈
```

### 10.3 对齐访问错误

部分 ARM 平台上：

```cpp
char buffer[16];
int* p = reinterpret_cast<int*>(buffer + 1);   // 偏移 1
*p = 0x12345678;                               // ← SIGBUS：未对齐
```

x86 / x86_64 对未对齐相对宽容（性能下降但不崩），ARM / RISC-V 的某些模式下直接崩。

### 10.4 写入只读段

```cpp
char* s = "hello";    // 字面量在只读段
s[0] = 'H';           // ← 可能 SIGBUS / SIGSEGV
```

C++ 中字符串字面量类型其实是 `const char*`，强行写入是 UB。开 `-Wwrite-strings` 编译期就能告警。


## 11.建立你自己的调试方法论

### 11.1 三层防御：编译、运行、回归

```
┌────────────────────────────────────────────────┐
│ 编译期：-Wall -Wextra -Werror -Wpedantic       │
│         clang-tidy / cppcheck 静态分析         │
├────────────────────────────────────────────────┤
│ 运行期：-fsanitize=address,undefined           │
│         valgrind（替代或补充）                 │
│         lldb / gdb（深入分析）                 │
├────────────────────────────────────────────────┤
│ 回归期：单元测试覆盖核心流程                   │
│         CI 上默认开 ASan + 整套用例            │
└────────────────────────────────────────────────┘
```

三层任意一层挡住了，问题都不会到用户那里。

### 11.2 调试黄金五步法

借用 [03.专栏博客/调试技巧和原理分析](调试技巧和原理分析.md) 中的总结，并结合本案例落实：

| 步骤 | 本案例怎么做 |
|------|--------------|
| 复现 | `./a.out` 必崩，复现 100% |
| 隔离 | 输出第一行后崩，问题在 `Show_Emp` 的循环 |
| 定位 | lldb / ASan 锁定 `m_EmpArray[1]` 越界 |
| 修复 | 用 vector + unique_ptr 重构 |
| 验证 | 多用例 + ASan + 压力测试 |

不要跳步，尤其是不要跳过"复现"和"验证"。

### 11.3 推荐的工具组合

| 阶段 | 一线工具 | 二线工具 |
|------|----------|----------|
| 编译期 | gcc/clang `-Wall -Wextra` | clang-tidy、cppcheck |
| 运行期检测 | AddressSanitizer | UBSan、TSan、Valgrind |
| 交互调试 | lldb（macOS）/ gdb（Linux） | rr（时光倒流调试） |

| 静态扫描 | clangd | SonarQube |


## 12.总结与思考

回头看这次 `Bus error: 10` 的排查：

- **表象**：第一行能输出，第二行立刻崩
- **症状**：`SIGBUS`，`EXC_BAD_ACCESS`
- **直接原因**：`Show_Emp` 越界访问 `m_EmpArray[1]`
- **根因**：`m_EmpNum` 与实际填充的对象数对不上
- **更深层根因**：用裸指针数组 + 双源真相维护容器，违背了"单一事实来源"原则

修复手段从"打补丁式 assert"到"用 vector + unique_ptr 重构"，对应的是**"修这个 BUG"**和 **"消灭这一类 BUG"**两种格局。
