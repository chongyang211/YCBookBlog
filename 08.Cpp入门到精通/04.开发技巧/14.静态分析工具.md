## 01.静态分析全景

### 1.1 三个层次的检查

按"分析深度"由浅到深：

```
[词法层]   token 级模式匹配  →  cpplint, 简单的 grep 规则
[语法层]   AST 模式匹配       →  clang-tidy 大部分规则
[语义层]   控制流/数据流/路径  →  Clang Static Analyzer, Coverity
```

层次越深：

- 能发现的问题越复杂（空指针 deref、资源泄漏链）
- 误报越多
- 速度越慢
- 配置/抑制工作越重

工程上**应该按层次叠加**：编译器告警 → clang-tidy → cppcheck → CSA → 商用方案，由浅入深，每层只放剩余的。

### 1.2 工具家族对照

| 工具 | 分析深度 | 误报率 | 速度 | 主要价值 |
|------|----------|--------|------|----------|
| 编译器 `-Wall -Wextra` | 语法 + 简单数据流 | 低 | 极快 | 必开 |
| `clang-tidy` | AST 模式 + 部分语义 | 中 | 快 | 风格 + 现代化 + 常见 bug |
| `cppcheck` | 简单流分析 | 中 | 快 | 资源管理、空检查 |
| Clang Static Analyzer | 路径敏感符号执行 | 中-高 | 慢 | 真正的 bug 寻找 |
| Coverity / PVS-Studio | 全程序、跨模块 | 中 | 很慢 | 商业最强 |
| `iwyu` | include 关系 | 低 | 中 | 头文件治理 |

### 1.3 共同的能力边界

所有静态分析都跨不过这三道墙：

1. **不可判定问题**：图灵停机问题决定了"任意完整代码是否会某种行为"无法严格判定。所有工具都是**近似**。
2. **跨模块/跨进程数据流**：跨 RPC、跨线程的数据流分析能做但代价指数级。
3. **运行时多态**：`Base*` 实际是哪个派生类，静态分析常常推不出来。

知道了边界，才能**理性看待"工具没报"≠"代码没问题"**。Sanitizer/fuzz 的角色无法被静态分析替代。


## 02.编译器告警

### 2.1 必开告警清单

最低限度的"全员开关"：

```bash
-Wall -Wextra -Wpedantic
-Wshadow                    # 局部变量遮蔽外层
-Wnon-virtual-dtor          # 多态基类的析构没 virtual
-Wold-style-cast            # C 风格 cast
-Wcast-align                # 对齐降级 cast
-Wunused                    # 未用变量/函数
-Woverloaded-virtual        # 派生类无意覆盖
-Wconversion                # 隐式窄化转换
-Wsign-conversion           # 有符号 ↔ 无符号
-Wformat=2                  # printf 格式严格
-Wformat-security           # 格式串非常量警告
-Wnull-dereference          # 显然的空 deref
-Wdouble-promotion          # float 隐式升 double
-Wimplicit-fallthrough      # switch 漏 break
```

GCC 还推荐 `-Wlogical-op -Wduplicated-cond -Wduplicated-branches`（这些 Clang 没有对应项）。

### 2.2 警告升级为错误

CI 里加一条：

```bash
-Werror              # 任何 warning 变 error
-Wno-error=deprecated-declarations  # 个别豁免
```

为什么要这样：**警告堆积是慢性病，越多人越习以为常。一旦升级 error 就强制清零，永远保持 0 warning 状态**。

### 2.3 告警背后的语义

很多人见到告警直接 `-Wno-` 关掉，这是反模式。每个告警都对应一类已知的"工程教训"，例如：

| 告警 | 背后的真实 bug |
|------|----------------|
| `-Wuninitialized` | 直接读未初始化值，行为未定义 |
| `-Wmaybe-uninitialized` | 在某条路径未初始化（控制流敏感） |
| `-Wsign-compare` | `i < container.size()` 当 i 是 int → 比较失真 |
| `-Wreturn-type` | 缺 return → UB |
| `-Wstrict-aliasing` | reinterpret_cast 违反严格别名 → UB |
| `-Wdangling-else` | else 绑错 if |

**遇到告警的正确流程**：搞懂它指的语义问题 → 真改代码而不是关告警。


## 03.clang-tidy 详解

### 3.1 检查器分类

clang-tidy 自带 600+ 检查器，按前缀组织：

| 前缀 | 含义 | 推荐度 |
|------|------|--------|
| `bugprone-*` | 容易出 bug 的写法 | ★★★★★ |
| `cert-*` | CERT 安全规范 | ★★★★ |
| `cppcoreguidelines-*` | ISO C++ Core Guidelines | ★★★★★ |
| `modernize-*` | 升级到现代 C++ | ★★★★ |
| `performance-*` | 性能反模式 | ★★★★ |
| `readability-*` | 可读性 | ★★★ |
| `clang-analyzer-*` | 集成 CSA | ★★★★ |
| `misc-*` | 杂项 | ★★ |
| `google-*` `llvm-*` `mpi-*` | 特定项目规范 | 视情况 |

### 3.2 配置文件实战

项目根放 `.clang-tidy`：

```yaml
Checks: >
  -*,
  bugprone-*,
  -bugprone-easily-swappable-parameters,
  cert-*,
  cppcoreguidelines-*,
  -cppcoreguidelines-pro-bounds-pointer-arithmetic,
  modernize-*,
  -modernize-use-trailing-return-type,
  performance-*,
  readability-*,
  -readability-magic-numbers,
  -readability-identifier-length

WarningsAsErrors: 'bugprone-*,cert-*'

HeaderFilterRegex: '^(src|include)/.*'

CheckOptions:
  - key: readability-function-cognitive-complexity.Threshold
    value: 25
  - key: cppcoreguidelines-special-member-functions.AllowSoleDefaultDtor
    value: true
```

要点：

- 用 `-*` 起步白名单式管理，比黑名单稳
- 把 `bugprone-*`、`cert-*` 升级为 error，**只对真错误零容忍**
- `HeaderFilterRegex` 限定只检查自家头文件，别给三方库发 100 万条建议
- 阈值类规则要根据项目实际定（cognitive-complexity 默认 25 比较合理）

### 3.3 自动 fix 与 review

clang-tidy 的杀手锏是 `-fix`：

```bash
clang-tidy -p build/ --fix --fix-errors src/foo.cpp
```

它能自动改 `NULL → nullptr`、`typedef → using`、`for(int i=0;i<v.size();++i) → for(auto& x:v)`、`push_back(T(...)) → emplace_back(...)`、`final` 标记等等。

但有两条**纪律**：

1. **fix 完一定要人工 review**：自动改的代码偶尔语义不等价（比如 emplace_back 触发不同重载）
2. **批量 fix 单独 PR**：和功能改动混在一起会让 review 失焦

工程实践：每月做一次 "lint-only PR"，统一 modernize/readability 的改动，单独评审单独合入。


## 04.cppcheck 互补

### 4.1 流程敏感分析

cppcheck 不基于 Clang AST，而是自己写的简单流分析。它能抓一些 clang-tidy 抓不到的：

```cpp
int* p = malloc(n);
if (!p) return;
*p = 1;
free(p);
*p = 2;       // ← cppcheck: Use after free
```

```cpp
void f(int x) {
    if (x > 0 && x < 10) { ... }
    else if (x > 5)      { ... }   // ← cppcheck: Logically dead branch
}
```

特长：**资源管理路径、空指针路径、不可达分支**。

### 4.2 与 clang-tidy 取舍

| 维度 | clang-tidy | cppcheck |
|------|------------|----------|
| 解析模型 | Clang AST，完全准确 | 自实现 lexer，偶有误判 |
| 检查丰富度 | 600+ | 200+ |
| 流程分析 | 弱 | 强 |
| 风格/现代化 | 强 | 弱 |
| 速度 | 中 | 快 |
| 误报率 | 较低 | 较高（要花时间抑制） |

**工程建议**：clang-tidy 主力 + cppcheck 跑流分析子集 + CSA 跑深路径分析，三者并存。


## 05.Clang Static Analyzer

### 5.1 路径敏感分析

CSA 是真正的"按可能执行路径分析"的工具。它会枚举：

```cpp
int* f(int x) {
    int* p = nullptr;
    if (x > 0) p = new int(x);
    return p;            // 路径 1: x>0 → p 非空
                         // 路径 2: x≤0 → p 为空
}
void g() {
    int* q = f(-1);
    *q = 5;              // CSA: 路径 2 下 q 为空，UB
}
```

clang-tidy 的 `-checks=clang-analyzer-*` 就是把 CSA 集成进来。也可以独立跑：

```bash
scan-build -o reports cmake --build build/
```

会生成 HTML 报告，每条问题附"路径标注图"——一步步告诉你"它假设的执行路径是什么"。

### 5.2 符号执行原理

CSA 的核心算法是**符号执行**：

- 把变量看作符号（`x = α`），约束随分支累积（`x > 0 ∧ x < 10`）
- 在每个语句更新符号状态
- 到 bug 检测点（deref、divide）时，求解约束是否允许触发

代价是路径数指数爆炸——每个分支都要分两路，10 个分支就是 1024 路径。CSA 用启发式剪枝（限制路径长度、合并状态、抛弃低概率路径），但代价是漏报：**深层路径的 bug 可能被剪掉**。

### 5.3 误报源与抑制

CSA 主要误报来源：

1. **跨函数无法看到约束**：A 函数检查了 `if(p) ... else throw`，但 CSA 在调用 A 后不知道 throw 已退出
2. **第三方库语义不知**：`assert(p)` 之后还报"可能为空"
3. **位运算丢精度**：`x & 0xff` 后 CSA 可能不知道结果范围

抑制方式（按推荐度）：

```cpp
// 1) 在源码里加 assert，对工具和 reader 都是文档
assert(p && "should be ensured by precondition");

// 2) 注解抑制（局部，明确）
// NOLINTNEXTLINE(clang-analyzer-core.NullDereference)
*p = 1;

// 3) 配置文件里全局禁用（最差，会掩盖真问题）
```


## 06.IWYU 与头文件

### 6.1 包含什么用什么

IWYU（Include What You Use）的口号："每个文件应该直接包含它用到的头，不多不少"：

```cpp
// foo.h
#include <vector>      // foo.h 用 vector
struct Foo { std::vector<int> v; };

// foo.cpp
#include "foo.h"
#include <iostream>    // ← 我用了 cout，必须自己 include，不能依赖 foo.h 间接给我
int main() { Foo f; std::cout << f.v.size(); }
```

不这样做的代价：依赖 foo.h 间接给的 `<iostream>`，哪天 foo.h 内部把 cout 拿掉了，cpp 编译失败。

```bash
iwyu_tool.py -p build/ src/foo.cpp
```

会打印"应增加 include 哪些、应删除 include 哪些"。

### 6.2 编译时间的副作用

C++ 编译慢，**80% 的时间在反复解析头文件**。IWYU 治理可以：

- 砍掉无用 include → 减少传染性 include
- 用前向声明替代 include → 缩小翻译单元
- 把"用一次"的 include 从 .h 移到 .cpp → 不污染下游

加上 PCH（precompiled header）和 modules（C++20），可以再减 30%-70% 编译时间。


## 07.工程接入

### 7.1 compile_commands

clang-tidy / CSA / iwyu 都要用 `compile_commands.json`。CMake 一键开启：

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```

或 `cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON`。Bazel 用 `bazel-compdb`，build2 自带，xmake `-y`。

### 7.2 增量分析策略

全量跑 clang-tidy 一个中等项目要 30 分钟+，**只看变更文件**：

```bash
# 取得 PR 改动的 cpp/h 文件
changed=$(git diff --name-only origin/main HEAD -- '*.cpp' '*.h')
clang-tidy -p build/ $changed
```

或用 `clang-tidy-diff.py`：

```bash
git diff -U0 origin/main | clang-tidy-diff.py -p1 -path build/
```

只在改动的"行"上跑，速度从 30 分钟降到 30 秒。

### 7.3 IDE 实时反馈

让开发者**写代码时就看见警告**比 PR 时收到 100 条要好得多：

- VSCode：`clangd` 扩展，自动读 `.clang-tidy`
- CLion：内置 clang-tidy 支持
- Vim/Emacs：通过 `clangd` LSP

`clangd` 还自带 CSA 简化版（部分 path-sensitive）。

### 7.4 PR gate 闭环

```yaml
# GitHub Actions 节选
- name: clang-tidy diff
  run: |
    git fetch origin main
    git diff -U0 origin/main HEAD | \
      clang-tidy-diff.py -p1 -path build/ \
        -extra-arg=-Wno-unknown-warning-option | tee tidy.log
    [ -s tidy.log ] && exit 1 || exit 0
```

要点：

- 不在 PR 检查中跑全量（太慢，且历史问题不归这个 PR 修）
- 只看 PR 引入的新告警
- 失败时把日志贴到 PR 评论里


## 08.规则建设

工具是壳，规则是肉。一个团队的规则演进通常这样：

```
第 1 阶段：开 -Wall -Wextra -Werror，零容忍
第 2 阶段：加 cppcoreguidelines + bugprone 子集
第 3 阶段：加项目特定规则（如禁用 std::auto_ptr、统一 logger 接口）
第 4 阶段：写自定义 clang-tidy 检查器（matcher AST，30-100 行）
```

第 4 阶段是真正的"工程纪律落地"——比如"所有 RPC 接口的 timeout 参数必须 >0 且 <60s"这类业务规则，没有现成检查器，需要自己写。基于 Clang ASTMatchers 不难，1-2 周能从零到产出。

每条规则都应该有：

| 字段 | 内容 |
|------|------|
| 编号 | TEAM-001 |
| 标题 | 禁止 std::shared_ptr 默认参数 |
| 动机 | 隐式拷贝构造昂贵，引发引用计数原子争抢 |
| 反例 / 正例 | 各 1-2 段 |
| 自动检测 | clang-tidy 检查器名 / 自实现 |
| 例外 | 哪些场景豁免 |


## 09.思考题

1. clang-tidy 报 `bugprone-use-after-move`，但这段代码运行多年没崩——可能的解释是什么？
2. 为什么 CSA 几乎不能跨函数分析空指针？要让它跨函数有什么代价？
3. `-Wshadow` 和 `-Wshadow-field-in-constructor`、`-Wshadow-local` 有什么区别？为什么要分这么细？
4. 同一个 bug，clang-tidy 没报、CSA 没报、cppcheck 报了——你应不应该信 cppcheck？
5. 把 clang-tidy 集成到 PR gate 后，如何避免"为了过 lint 而写难懂的代码"？
