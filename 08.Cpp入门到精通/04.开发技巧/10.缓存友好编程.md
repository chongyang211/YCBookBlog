## 01.内存墙时代

### 1.1 速度的鸿沟

CPU 主频 30 年涨了 1000×，DRAM 延迟只下降了 5×。这就是著名的"内存墙"（Memory Wall）：

```
时间维度：       1990            2020
CPU 主频：       33 MHz    →    4 GHz   （×120）
DRAM 延迟：      80 ns     →    50 ns   （×1.6）
相对差距：       2.6 cycles →   200 cycles
```

也就是说：**今天一次未命中 cache 的访问，相当于 200 条加法指令的时间**。性能优化的"主战场"早就从"减少计算"转向了"减少访存"。

### 1.2 cache 层级模型

现代 x86_64 典型层级（以 Intel Skylake 为例）：

| 层级 | 容量 | 访问延迟 | 共享范围 |
|------|------|----------|----------|
| L1d / L1i | 32 KB / core | 4 cycle | 单核私有 |
| L2 | 256 KB - 1 MB / core | 12 cycle | 单核私有 |
| L3 (LLC) | 8 MB - 64 MB | 30-40 cycle | 全 socket 共享 |
| DRAM | GB 级 | 200+ cycle | 全机 |
| NVMe SSD | TB 级 | 100,000 cycle | 全机 |

这是一个"上一层比下一层小 8-32×、慢 3-10×"的金字塔。**一切优化的核心**：让数据尽可能停留在更高层。

### 1.3 一次访问的代价

直观感受：

```
L1 命中:        1 ns       像伸手拿桌上的水杯
L2 命中:        3 ns       从抽屉里拿
L3 命中:        12 ns      去隔壁工位拿
DRAM:           60-100 ns  下楼到便利店
SSD:            100 μs     从城市另一头
机房间:         1 ms       从另一个城市
```

把 L1 命中当 1 秒，DRAM 访问就是 1 分钟，SSD 是 1 天。**这种比例感是性能编程的"母语"**。


## 02.cache line 原理

### 2.1 64 字节的世界

绝大多数 x86_64/ARM 系统的 cache line 是 **64 字节**。这意味着：

- CPU 从 DRAM 一次至少读 64 字节
- 你访问 `arr[0]` 一个 byte，硬件实际加载了 64 个 byte 进 L1
- 紧跟着访问 `arr[1]..arr[63]` 都是免费的（已经在 L1 了）

**所以"按顺序读"和"跳跃读"性能差距常常是 10×**。

```cpp
// A：顺序读 1 GB
for (size_t i = 0; i < N; ++i) sum += arr[i];

// B：跨 cache line 读（每次跳 64 字节）
for (size_t i = 0; i < N; i += 16) sum += arr[i];
// 看起来只读 1/16 数据，时间却几乎一样——因为每次都触发一次 cache miss
```

### 2.2 组相联与替换

cache 不是一个大平面，而是被划成 **set × way**：

- 每个内存地址通过 `(addr / 64) mod num_sets` 定位到唯一一个 set
- 每个 set 有 N 个 way（slot），新数据来了如果 set 满，按 LRU 替换最旧的

L1d 典型 8-way 组相联：64 KB / 64 B / 8-way = 128 sets。  
**陷阱**：如果你的数据恰好都映射到同一个 set，再大的 cache 也只有 8 个 slot 可用——这叫 **conflict miss**。

经典坑：步长为 4096 的循环（恰好是 page size 倍数）会让所有访问落入同一个 set：

```cpp
double matrix[1024][1024];
for (int j = 0; j < 1024; ++j)
    for (int i = 0; i < 1024; ++i)
        sum += matrix[i][j];   // 每次跳 8KB，全是 conflict miss
```

### 2.3 cache 一致性协议

多核共享内存，每个核有自己的 L1/L2，怎么保证一致？答：**MESI 协议**。

每个 cache line 在每个核里有一种状态：

| 状态 | 含义 |
|------|------|
| **M**odified | 我有，且只有我有，且我改过 |
| **E**xclusive | 我有，且只有我有，没改 |
| **S**hared | 我和别人都有，没改 |
| **I**nvalid | 我没有 |

转换规则的核心：**任何核要写一个 line，必须把其他核的副本变成 I**——这要发广播消息（RFO，Read For Ownership），延迟 30-100 ns。

这个机制是后面"伪共享"的物理基础。


## 03.局部性两原则

### 3.1 时间局部性

"刚访问过的，很可能再次访问"。优化方向：**让热数据反复进出同一个 cache 槽位**。

工程做法：循环展开 / 数据复用 / 共用基址：

```cpp
// 差：每次循环都从对象里 load count
for (int i = 0; i < obj.count; ++i) ...
// 好：先 load 一次到寄存器
const int n = obj.count;
for (int i = 0; i < n; ++i) ...
```

### 3.2 空间局部性

"刚访问的旁边，很可能也被访问"。优化方向：**让相关数据在内存上紧挨着**。

矩阵乘法是经典案例：

```cpp
// 行主序：A[i][k] B[k][j] —— 访问 B 时跨行（坏）
for (i) for (j) for (k) C[i][j] += A[i][k] * B[k][j];

// ikj 顺序：让 B 顺序读
for (i) for (k) for (j) C[i][j] += A[i][k] * B[k][j];
```

仅仅交换循环顺序就能从 GFLOPS 个位数提到几十——**算法没变，cache miss 减少了**。

### 3.3 失效的常见模式

| 模式 | 现象 | 改造方向 |
|------|------|----------|
| 链表遍历 | 节点散布堆中，每节点 miss | 改 vector / boost::intrusive |
| 指针密集 hash 表 | 桶内每节点都 miss | 开放寻址 / robin-hood |
| 大对象 + 多字段，只用一个字段 | 每次拉整个对象 | SoA 拆分（见下节） |
| 多线程写同 line 不同字节 | 伪共享（见 05 节） | padding |
| 间接调用（虚函数） | 跳进未预取的代码段 | 减少间接调用 / sealed class |


## 04.AoS 与 SoA

### 4.1 数据布局对比

**AoS（Array of Structures）**：

```cpp
struct Particle { float x, y, z, vx, vy, vz, mass; };  // 28 字节
std::vector<Particle> ps;
for (auto& p : ps) p.x += p.vx * dt;   // 只用 x、vx
```

每次访问取整个 28 字节，但只用了 8 字节——**cache 利用率 28%**。

**SoA（Structure of Arrays）**：

```cpp
struct Particles {
    std::vector<float> x, y, z, vx, vy, vz, mass;
};
for (size_t i = 0; i < n; ++i) ps.x[i] += ps.vx[i] * dt;
```

只读 x、vx 两个数组，每个 cache line 拉 16 个 float，全部用得上——**利用率 100%**。

更大的好处是 **SIMD 友好**：`x[i..i+8]` 是连续的，可以一条 AVX 指令同时处理 8 个 float。

### 4.2 选择的原则

| 场景 | 推荐 |
|------|------|
| 一次访问对象的多数字段（如 OOP 业务对象） | AoS |
| 一次只用一两个字段，但要遍历海量对象（粒子/ECS/数据库列） | SoA |
| 字段数量很多，访问模式按"字段"分批 | SoA |
| 需要按对象增删（vector::erase 频繁） | AoS（SoA 维护多数组同步麻烦） |

游戏引擎的 ECS（Entity Component System）本质就是 SoA + 组件分离，这也是它高性能的根本原因。

### 4.3 PGO 视角验证

是否要 SoA 化，**不能拍脑袋**。用 perf 看实际 cache miss：

```bash
perf stat -e L1-dcache-load-misses,L1-dcache-loads ./bench
# miss rate > 5% 才考虑 SoA 化
# < 1% 说明数据布局不是瓶颈，去找别的
```


## 05.伪共享避坑

### 5.1 现象与代价

```cpp
struct Counter {
    std::atomic<int> a;   // 4 字节
    std::atomic<int> b;   // 4 字节
};
Counter c;

// 线程 1 写 c.a，线程 2 写 c.b
```

a 和 b 同在 64 字节的 cache line。线程 1 写 a 让线程 2 的 line 变 I 态，线程 2 又要 RFO 拉回——**两个无关字段被强制串行化**。这就是 **false sharing**。

测得开销：**两个线程写不同字段比写同字段还慢 2-5×**（写同字段用 ALU 即可，写不同字段额外加 RFO 广播）。

### 5.2 padding 与对齐

```cpp
struct Counter {
    alignas(64) std::atomic<int> a;
    char pad[60];
    alignas(64) std::atomic<int> b;
};
```

或更优雅地：

```cpp
struct alignas(64) Slot {
    std::atomic<int> v;
};
std::array<Slot, N> slots;   // 每个 slot 独占一行
```

**代价**：内存翻 16×。所以**只在多线程高频写的字段上做**，不要全量加 padding。

### 5.3 hardware_destructive_interference

C++17 标准化了这个常量：

```cpp
#include <new>
struct alignas(std::hardware_destructive_interference_size) Slot {
    std::atomic<int> v;
};
```

它在不同 CPU 上有不同值（x86 是 64，部分 ARM 是 128，Apple M1 是 128），用它而不是硬编码 64 更可移植。

**反向用法**：`hardware_constructive_interference_size`——希望两个字段共享 line（局部性）时按它对齐打包。


## 06.预取与流水

### 6.1 硬件预取器

现代 CPU 自带预取器，能识别两种模式：

1. **Stream prefetcher**：连续递增/递减地址（顺序遍历数组）
2. **Stride prefetcher**：固定步长（如每隔 8 个 int 访问一次）

只要你的访问模式落在这两种里，**硬件会自动提前把后续 line 拉进 L2/L1**，让你感觉不到 miss。

但它**抓不住**：

- 链表遍历（地址依赖前一次 load）
- 间接索引（`a[b[i]]`）
- 树/图遍历

### 6.2 软件预取指令

抓不住时手工预取：

```cpp
for (size_t i = 0; i < n; ++i) {
    if (i + 16 < n)
        __builtin_prefetch(&arr[indices[i + 16]], 0, 0);
    sum += arr[indices[i]];
}
```

`__builtin_prefetch(addr, rw, locality)`：

- rw：0 读 / 1 写
- locality：0-3，3 表示"高复用，进 L1"，0 表示"用一次就丢"

预取距离要**比内存延迟乘以一次循环时间略长**，太近无效，太远反被驱逐。一般是 8-16 次循环之外。

### 6.3 链式数据的痛

链表的根本问题是**指针有依赖**：必须 load 完 next 才知道下一个要 prefetch 谁。一些缓解手段：

| 手段 | 思路 |
|------|------|
| 节点池 + 同段分配 | 节点物理紧邻，硬件预取部分起作用 |
| 把 next 在节点头几字节 | 跟数据共享 line，至少省一次 miss |
| 改用 vector / deque | 真正解决问题 |
| skip-list / btree | 一次决策多个候选，部分隐藏延迟 |


## 07.SIMD 入门

### 7.1 SIMD 三种姿势

| 方式 | 控制力 | 可读性 | 跨平台 |
|------|--------|--------|--------|
| 自动向量化（编译器） | 低 | 高 | 高 |
| Intrinsic（_mm_add_ps 等） | 高 | 中 | 低（绑定 ISA） |
| `std::experimental::simd` / `std::simd`（C++26） | 中 | 高 | 高 |

工程顺序应该是：**先靠自动向量化 → 不行用 std::simd → 极端热点再上 intrinsic**。

### 7.2 自动向量化条件

GCC/Clang 自动向量化要求：

1. 循环边界编译期可推断（或不可变）
2. 无数据依赖（`a[i] = a[i-1] + 1` 不行）
3. 内存访问连续或固定步长
4. 无函数调用（除非 inline）
5. 数据对齐（不强制，但对齐性能更好）

加 `-Rpass=loop-vectorize -Rpass-missed=loop-vectorize`（Clang）或 `-fopt-info-vec`（GCC）能看到编译器为什么没向量化。

### 7.3 intrinsic 实战

```cpp
#include <immintrin.h>
void add(const float* a, const float* b, float* c, size_t n) {
    size_t i = 0;
    for (; i + 8 <= n; i += 8) {
        __m256 va = _mm256_loadu_ps(a + i);
        __m256 vb = _mm256_loadu_ps(b + i);
        _mm256_storeu_ps(c + i, _mm256_add_ps(va, vb));
    }
    for (; i < n; ++i) c[i] = a[i] + b[i];   // 尾部
}
```

8 个 float 一条指令搞定，理论 8× 加速。但实际性能受**内存带宽**限制：如果数据来不及从 DRAM 拉到 L1，再快的 SIMD 也是空转。这就回到第一节的"内存墙"——**SIMD 加速的前提是数据已经在 cache 里**。


## 08.度量与验证

### 8.1 perf cache miss

```bash
perf stat -e cache-references,cache-misses,L1-dcache-load-misses,LLC-load-misses ./bin
```

观察重点：

| 指标 | 健康值 | 异常含义 |
|------|--------|----------|
| L1 miss rate | < 5% | 高：数据布局/访问模式问题 |
| LLC miss rate | < 50% / L1 misses | 高：工作集超 LLC |
| LLC miss / IPC | < 0.05 | 高：内存墙，考虑 prefetch |

### 8.2 toplev 自顶向下

Intel 的 [pmu-tools/toplev](https://github.com/andikleen/pmu-tools) 把 CPU 流水线分成四类瓶颈：

```
Frontend Bound      ← 取指/解码 不够快（icache miss、分支）
Bad Speculation     ← 分支预测错
Backend Bound       ← 执行/访存 不够快
   ├── Memory Bound  ← 访存（cache miss、bandwidth）
   └── Core Bound    ← 计算（端口竞争、依赖链）
Retiring            ← 真正在干活（理想 100%）
```

```bash
toplev.py -l1 ./bin
# Memory Bound: 65%   ← 锁定内存瓶颈
# 然后 -l2 看是 L1/L2/L3/DRAM 哪一级
```

**这是工业级缓存优化的标准入口**——它告诉你"问题在哪一层"，本章讲的所有技巧才有的放矢。
