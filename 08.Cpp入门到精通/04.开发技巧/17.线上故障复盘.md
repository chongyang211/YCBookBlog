## 01.案例背景

> 本章使用的是一个虚构但**贴近真实**的案例，集合了笔者经历过的多次故障的典型特征——任何相似纯属"线上事故的母题就那几种"。

### 1.1 服务架构

某 IM（即时通讯）后端的"消息存储"服务（C++ 编写）：

```
用户客户端
    │
    ▼ HTTP/gRPC
[gateway] (80 实例)
    │
    ▼ gRPC
[msg-store]  ← 本章主角，60 实例，C++17
    │
    ├──→ Redis 集群（消息热缓存）
    └──→ MySQL 分库分表（持久化）
```

`msg-store` 职责：

- 写入消息到 Redis + MySQL（双写，eventual consistency）
- 读取最近 N 条消息（先 Redis 后 MySQL）
- QPS：写 5 万 / 秒，读 30 万 / 秒
- 单实例约 8 GB RES，主要是连接池 + 内存缓存

### 1.2 流量与 SLO

| 项 | 值 |
|----|----|
| 月活用户 | 5000 万 |
| SLO | 99.95% 成功率，P99 < 200ms |
| 错误预算 | 0.05% × 50e8 请求/月 = 2.5e6 次失败可接受 |
| 单次故障预算 | < 1 小时 P0、< 4 小时 P1 |

### 1.3 故障一句话概述

> **2024-XX-XX 14:32 起，msg-store 服务 P99 延迟从 50ms 飙升至 4500ms，错误率从 0.01% 升至 8%，持续 48 分钟。**

## 03.现象层分析

### 3.1 关键指标曲线

```
QPS：       平稳无变化（流量不是触发因素）
错误率：    14:32 0.01% → 14:40 8% → 15:20 0.01%
P99 延迟：  14:32 50ms → 14:40 4500ms → 15:20 50ms
CPU：       14:32 30% → 14:40 60% → 15:20 30%（轻度上升）
内存：      14:32 8GB → 14:40 11GB → 15:20 8GB（明显增长）
线程数：    14:32 200 → 14:40 1500 → 15:20 200（暴涨！）
```

**异常最显著的是线程数暴涨**——这通常意味着**有很多线程被阻塞**，调用方持续创建新线程。

### 3.2 日志特征

```
14:33:01 [WARN] tx 23 wait_for(5s) timed out, retrying
14:33:02 [WARN] tx 24 wait_for(5s) timed out, retrying
14:33:05 [ERROR] tx 23 abandoned after 3 retries
14:33:10 [WARN] new connection rejected: thread pool full
14:34:00 [ERROR] mutex acquire deadline exceeded in MsgStore::Save
14:35:11 [WARN] gRPC handler hijacked, queue depth 1024
```

**关键证据**：`wait_for(5s) timed out` 和 `mutex acquire deadline exceeded`——这就是线程在等锁等到超时，引发上层重试，重试又创建新连接……雪崩链条形成。

### 3.3 链路追踪

trace 数据对比：

```
正常时：
 gateway (1ms) → msg-store (8ms)
                     ├ redis_get (1ms)
                     └ mysql_insert (5ms)

故障时：
 gateway (4500ms) → msg-store (4500ms)
                       └ <span 仅 1 个：waiting_for_lock 4500ms>
```

trace 直接告诉我们：**msg-store 内部的某把锁等了 4.5 秒**——既不是 Redis 也不是 MySQL 的问题。范围确定在 msg-store 进程内。


## 04.排查思路全过程

复盘的价值之一是**重现"当时的思路"**——包括走过的弯路。

### 4.1 第一假设：依赖问题

最常见的故障是"依赖服务慢/挂"。先验证：

| 检查项 | 结论 |
|--------|------|
| Redis QPS / 延迟 | 正常 |
| MySQL QPS / 延迟 | 正常 |
| 网络（机房间 ping） | 正常 |
| DNS 解析 | 正常 |

**结论**：依赖正常，问题在 msg-store 内部。**第一假设排除**。

### 4.2 第二假设：流量异常

"突发流量打挂服务"也很常见：

| 检查项 | 结论 |
|--------|------|
| QPS 曲线 | 14:00-14:32 平稳，无突增 |
| 上游 gateway 重试率 | 正常 |
| 用户分布 | 无异常聚集 |
| 异常 query / DDoS | 没有 |

**结论**：流量没异常，问题不在外部。**第二假设排除**。

### 4.3 第三假设：变更触发

时间高度可疑——14:00 发布、14:32 故障，间隔 32 分钟。

| 检查项 | 结论 |
|--------|------|
| 发布时间 | 14:00 |
| 故障时间 | 14:32 |
| 滚动发布是否完成 | 14:30 完成全量 |
| 配置是否变更 | 否 |
| 依赖版本是否变 | 否 |

**结论**：高度怀疑 v2.3.1 引入问题。**进入代码审查**。

### 4.4 决定性证据

回滚后故障平息，**强支持"是 v2.3.1 引入"**。但还要复现根因：

```bash
# 在沙箱环境用 v2.3.1 跑生产流量回放
# 5 分钟后 P99 飙升、线程数暴涨，故障重现 ✓
```

接下来用 GDB attach 到一个卡死的实例：

```
(gdb) thread apply all bt
# 看到 800+ 线程都阻塞在 MsgStore::Save 的同一行
(gdb) frame 5
(gdb) info locals
# 看到 std::lock_guard<std::mutex> lock_a(mu_a_) 在等
# 而其他线程持有 mu_a_ 在等 mu_b_

# 经典死锁图
```

**死锁** ✓。


## 05.根因深析

### 5.1 直接原因

v2.3.0：

```cpp
class MsgStore {
    std::mutex mu_;
    std::unordered_map<UserId, MsgList> cache_;
public:
    void Save(UserId u, Msg m) {
        std::lock_guard lk(mu_);
        cache_[u].push_back(std::move(m));
        async_persist(u, m);   // 异步写
    }
};
```

v2.3.1（修复"内存泄漏"，引入死锁）：

```cpp
class MsgStore {
    std::mutex mu_a_, mu_b_;
    std::unordered_map<UserId, MsgList> cache_;
    LRU<UserId> hot_users_;
public:
    void Save(UserId u, Msg m) {
        std::lock_guard la(mu_a_);
        cache_[u].push_back(std::move(m));
        std::lock_guard lb(mu_b_);   // ← Save 顺序：a → b
        hot_users_.touch(u);
    }
    void Evict() {
        std::lock_guard lb(mu_b_);
        std::lock_guard la(mu_a_);   // ← Evict 顺序：b → a！
        auto victim = hot_users_.pop_lru();
        cache_.erase(victim);
    }
};
```

**死锁**：Save 走 a→b，Evict 走 b→a。两个线程并发就锁死。

### 5.2 触发条件

为什么开发期没发现？

| 条件 | 解释 |
|------|------|
| `Evict` 是后台线程偶尔运行 | 单线程测试根本不调 |
| 单元测试没并发跑两条 | 测试覆盖不到 |
| Code review 漏看 | 锁顺序问题需要全局视角 |
| 内存够用时 Evict 不触发 | 开发环境内存小但流量也小，Evict 频率与生产不同 |
| 发布后 32 分钟才爆 | 因为 cache 长到一定大才开始 Evict |

### 5.3 系统弱点

每次故障都暴露**多个系统弱点**：

1. **代码层**：缺锁顺序静态检查（Helgrind/TSan 没在 CI 跑）
2. **测试层**：没有"长时间稳定性测试"（24h+）
3. **发布层**：滚动发布全量铺开太快，1% 灰度 30 分钟就能发现
4. **监控层**：线程数/锁争抢指标没单独告警
5. **应急层**：oncall 第一次见这种症状，runbook 没"线程数暴涨"分类

任何一层加固都能阻断这条故障链。

### 5.4 五个为什么

[Five Whys](https://en.wikipedia.org/wiki/Five_whys) 是丰田生产体系传下来的根因分析法：

```
为什么用户发不出消息？
   → 因为 msg-store 服务延迟暴涨

为什么延迟暴涨？
   → 因为 800+ 线程都在等锁

为什么会大量线程等锁？
   → 因为 Save 和 Evict 之间死锁

为什么会死锁？
   → 因为锁顺序不一致（a→b vs b→a）

为什么锁顺序不一致没被发现？
   → 因为没有锁顺序检测工具入 CI、code review 时没建立"锁顺序文档"
```

**五个为什么的关键**：每问一层都从"具体现象"走向"系统机制"。最后一个 why 才是真正可改进的根因——而且**它通常是流程/工具层面的**。


## 06.修复方案

### 6.1 应急止损

- **回滚 v2.3.1 → v2.3.0**：14:55 开始，15:20 完成

### 6.2 短期修复

代码修复（v2.3.2）：

```cpp
class MsgStore {
    std::mutex mu_;     // 单锁
    // 或者保持双锁但定义全局顺序
    std::mutex mu_a_, mu_b_;
public:
    void Save(UserId u, Msg m) {
        std::scoped_lock lk(mu_a_, mu_b_);  // C++17 死锁安全
        ...
    }
    void Evict() {
        std::scoped_lock lk(mu_a_, mu_b_);  // 同样顺序
        ...
    }
};
```

`std::scoped_lock` 内部用 [Hierarchical try-lock](https://en.cppreference.com/w/cpp/thread/lock) 算法，**保证多锁顺序一致且无死锁**——这就是 C++17 引入它的原因。

### 6.3 长期改进

| 序号 | 改进项 | Owner | DDL | 验收 |
|------|--------|-------|-----|------|
| 1 | TSan 入 CI 跑核心模块 | 工程效能 | 1 周 | TSan job 在 PR 触发 |
| 2 | 24 小时稳定性测试入 CD | QA | 2 周 | 每次 release 前必跑 |
| 3 | 灰度从 30 分钟全量改为 4 小时阶梯 | 平台 | 1 周 | 灰度规则文档更新 |
| 4 | 监控加 mutex 等待时间分布 | SRE | 2 周 | 大盘看到 P99 等锁时间 |
| 5 | 写一份"锁顺序文档"，code review 必看 | 团队 X | 1 周 | 文档 + review checklist |
| 6 | runbook 新增"线程数暴涨"分类 | oncall | 3 天 | runbook 已发布 |
| 7 | 用 `scoped_lock` 替换所有多锁场景 | 团队 X | 1 月 | grep `lock_guard` 检查 |

**纪律**：每条改进项都要有 Owner、DDL、验收标准。否则改进项会沉到 Jira 海底。


## 07.复盘方法论

### 7.1 blameless 文化

复盘的第一原则：**不针对个人，针对系统**。

为什么？

- 责怪个人 → 大家在事故中藏报告 → 后续故障不再透明
- 责怪个人 → 工程师怕担责拒绝高风险变更 → 整体进步停滞
- 复盘的目标是让**一个新人在同样情境下也不会重蹈覆辙**——这只能靠改系统

具体表达：

| 不要说 | 应该说 |
|--------|--------|
| "Alice 写了 bug 导致死锁" | "代码评审流程未识别多锁顺序不一致，CI 没有 TSan 检测" |
| "oncall 反应慢" | "告警内容不够明确，runbook 缺少这类症状的分类" |
| "发布把控不严" | "灰度速度过快，未给指标暴露异常的窗口" |

### 7.2 复盘文档结构

推荐结构（本章已基本按此组织）：

```
1. 摘要（一句话）
2. 时间线
3. 影响范围（用户数 / 业务损失 / SLO 消耗）
4. 现象层（指标、日志、trace）
5. 排查过程（含走过的弯路）
6. 根因（含五个为什么）
7. 修复方案（应急 / 短期 / 长期）
8. 改进项（含 Owner / DDL）
9. 经验教训
```

文档应**永久存档**且**对全团队公开**。每一份文档都是组织的"系统记忆"。

### 7.3 改进项跟踪

改进项最常见的失败模式：写完没人跟。建议机制：

- 每条改进项进 Jira 并打 `from-postmortem-XYZ` 标签
- 月度回顾未关闭的改进项
- 季度评估"复盘改进项关闭率"作为团队指标
- 改进项关闭率 < 70% → 团队要被问责（不是个人）

### 7.4 故障分级

不是所有事故都要正式复盘。建议分级：

| 级别 | 判定 | 复盘要求 |
|------|------|----------|
| P0 | 全站不可用 / SLO 月预算耗尽 | 全员复盘 + 高管参会 + 文档对外（如果是公司级） |
| P1 | 核心功能受损 > 30 分钟 | 团队复盘 + 文档全公司可见 |
| P2 | 局部影响 / 低峰期 | 团队复盘 + 文档存档 |
| P3 | 内部抖动，用户无感知 | 简要总结 + 改进项即可 |

故障级别决定**复盘深度**。但即使 P3，**改进项不能跳过**——很多 P0 都是 P3 没改进的累积。


## 08.对全卷的回望

回到本章开头说的：本章是全卷的实战缩影。让我们把"复盘案例"和"全卷工具/原理"对应起来：

| 案例环节 | 用到的章节 |
|----------|------------|
| 监控告警 → 14:33 触发 | 第 16 章《日志监控告警》 |
| GDB attach 看堆栈 | 第 4 章《GDB 与 LLDB 实战》 |
| trace 看到 4500ms 等锁 | 第 16 章 trace 体系 |
| 怀疑死锁 → TSan/Helgrind 验证 | 第 6 章《Sanitizer 实战》/ 第 7 章《Valgrind 深度》 |
| 决定回滚 | 第 17 章《灰度发布稳定》 |
| 修复时用 `std::scoped_lock` | 卷三第 16 章《并发与内存序》 |
| code review 加锁顺序检查 | 第 15 章《代码规范评审》 |
| 改进 CI 跑 TSan | 第 14 章《静态分析工具》 + 第 6 章 |
| 加监控大盘 | 第 16 章 |
| 改灰度策略 | 第 17 章 |

**这就是工程能力的样子**：每个工具单独学没用，要在真实事故中**像神经网络一样自动激活其中需要的模块**。

而真正的高级工程师与初级的差距，不在"知道这些工具"——大家都能 google 出来。差距在：

1. **故障发生时第一反应**做什么（不是慌、不是猜）
2. **假设空间**多大（前面 4.1-4.4 那种思路）
3. **决断**（什么时候止损、什么时候等证据）
4. **沉淀**（每次事故都让系统变强一分）
5. **传播**（让团队所有人都从你的事故中学到）

希望读完整卷四，这五种能力你都能比开始时多一格。
