## 01.规范与评审定位

### 1.1 规范的三个层级

```
[格式]   缩进、空格、换行、大括号位置  ← clang-format
[命名]   类名、变量名、文件名、宏       ← clang-tidy + 人工
[设计]   架构、接口、抽象、依赖          ← 人工 review
```

**层级越往上，机器越无能为力**。一个团队的精力分配应该是反过来的：80% 投入在设计层评审，命名层 15%，格式层 5%（且全自动）。

如果你看到的 review 评论 80% 都是"这里少个空格""这括号位置不对"——**这是工具没接好，不是评审到位**。

### 1.2 评审解决什么

| 价值类型 | 实例 |
|----------|------|
| **抓 bug** | 边界条件、错误处理、并发竞争、资源泄漏 |
| **传播知识** | "这个模块为什么这样设计"，让 reader 理解上下文 |
| **建立标准** | 新人通过看大量 review 形成"我们这里怎么写代码"的直觉 |
| **共享所有权** | 多人看过的代码出 bug 时不是单点责任 |
| **挑战决策** | "为什么不用现有的 X？"——让作者多想一遍 |

研究表明（Microsoft、Google、SmartBear 的论文）：

- code review 找 bug 的效率是单元测试的 1.5-3×
- 但找 bug 只是表面，**真正的高价值在"知识传播"和"标准建立"**——这些在大规模团队中决定长期速度

### 1.3 不应解决什么

评审**不是**：

- 风格喜好的战场（用 lint 自动化）
- 重写代码的机会（在不影响功能时尊重原作者风格）
- 拷问能力的舞台（所有评论应针对代码不针对人）
- 单元测试的替代（很多 bug 在 review 看不出来）
- 设计决策的"事后否决会"（架构应在编码前评审）


## 02.主流规范对比

### 2.1 Google C++ Style

特点：**保守、易学、强约束**。

| 立场 | 规则 |
|------|------|
| 异常 | 不用（继承遗产，新项目可考虑改） |
| RTTI | 谨慎用 |
| 模板元 | 复杂的不写 |
| 智能指针 | 默认 unique_ptr，shared_ptr 谨慎 |
| 引用 vs 指针 | 输出参数用指针（区分意图） |
| 命名 | 类 PascalCase，函数 PascalCase（非成员是 ALL_CAPS） |
| 头文件 | `#pragma once` 或 include guard，要求严格 |

**优点**：可预测，新人上手 1 周。**缺点**：保守到限制现代 C++ 表达力（如禁止异常）。

### 2.2 ISO Core Guidelines

由 Bjarne Stroustrup 和 Herb Sutter 主持的"C++ 之父级"规范。强调：

- **类型与资源安全**：用类型/RAII 而不是注释保证不变式
- **零成本抽象**：高层表达不付运行时代价
- **现代特性优先**：智能指针、`std::span`、Concepts、`std::expected`

举几条核心：

```
F.16: 输入参数小或廉价复制 → 按值传；其余按 const&
F.51: 默认参数优于函数重载（仅用于一处差异时）
ES.5: 作用域尽量小
ES.20: 总是初始化对象
ES.46: 避免窄化转换
R.20: 用 unique_ptr/shared_ptr 而不是 new/delete
T.20: 避免 SFINAE，用 Concepts（C++20）
```

**优点**：技术上最先进，覆盖 C++11-23 全部新特性。**缺点**：文档巨大，新人要学习曲线。

### 2.3 LLVM/Mozilla 风格

适合编译器、浏览器这类长期运行、性能敏感、跨平台的项目：

- 强调零依赖、避免 STL 重 IO
- 自定义容器（`SmallVector` 替代 `std::vector` 在小规模时）
- 严格的内存自管理纪律

普通业务项目不需要这么严苛。

### 2.4 自家项目的取舍

**不要从零造**。推荐做法：

1. 选 Google 或 Core Guidelines 之一作基线
2. 写一份 5-10 页的"项目差异表"：哪些条款豁免、哪些条款增强
3. 用 `.clang-format` + `.clang-tidy` 自动化能自动化的部分

差异表必须有"动机"。比如："禁止异常"是因为本项目嵌入到不支持异常的宿主中——把动机写下来，未来 reviewer 才能判断"这条规则是否还适用"。


## 03.格式规范自动化

### 3.1 clang-format 入门

```bash
clang-format -i src/foo.cpp        # 直接改文件
clang-format --dry-run -Werror src/foo.cpp   # CI 检查模式
```

放一个 `.clang-format` 在仓库根。所有 IDE / pre-commit hook / CI 都按这个走，**永远不再有"格式 PR 评论"**。

### 3.2 配置实战

基于 Google 风格微调示例：

```yaml
BasedOnStyle: Google
IndentWidth: 4
TabWidth: 4
UseTab: Never
ColumnLimit: 100
PointerAlignment: Left            # int* p 而不是 int *p
ReferenceAlignment: Left
AccessModifierOffset: -4          # public: 缩进减 4
AllowShortFunctionsOnASingleLine: Inline
SpacesBeforeTrailingComments: 2
SortIncludes: CaseInsensitive
IncludeBlocks: Regroup
IncludeCategories:
  - Regex: '^"[^/]+"'             # "foo.h" 同目录
    Priority: 1
  - Regex: '^".*"'                # "sub/foo.h"
    Priority: 2
  - Regex: '^<[^/]+\.h>'          # <stdio.h>
    Priority: 3
  - Regex: '^<.+>'                # <vector>
    Priority: 4
```

### 3.3 格式与 review 解耦

工程纪律：

1. **pre-commit hook**：本地提交时自动 clang-format
2. **CI gate**：PR 跑 `clang-format --dry-run -Werror`，不一致直接拒
3. **不可修改 区域用注释包围**：`// clang-format off ... // clang-format on`（极少用）

效果：reviewer 永远只看到"格式正确的差异"，**注意力 100% 在逻辑上**。


## 04.命名与风格

### 4.1 命名的三原则

| 原则 | 说明 |
|------|------|
| **意图清晰** | `int d;`（差） vs `int days_since_modification;`（好） |
| **作用域适配** | 局部循环可 `i`，全局变量名要长 |
| **避免误导** | `accountList` 实际是 set？不要 |

经典反例：

```cpp
int n;                  // 太短，啥都可能是
int the_total_user_count_in_the_system_now;  // 太长，readers 走神
int activeUsers;        // 刚好
bool flag;              // flag 啥？isActive / isReady / isDirty 才对
```

### 4.2 类与函数边界

```cpp
class OrderService {
public:
    Order create(const CreateOrderRequest&);
    void cancel(OrderId);
    OrderList list(const Filter&);

private:
    OrderRepository* repo_;     // 后缀下划线区分成员
    Logger* logger_;
};
```

要点：

- **公有接口要稳**，私有实现可常变
- 一个类**做一件事**，超过 7 个公有方法考虑拆分
- 函数 **20 行警戒，50 行拆分**——超过往往说明做了多件事
- **入参 ≤4 个**：超过用结构体打包

### 4.3 头文件纪律

C++ 头文件设计有四条铁律：

1. **`#pragma once`**（或对应 include guard）
2. **不在头文件 `using namespace`**
3. **能前向声明就别 include**
4. **包含什么用什么**（IWYU 原则）

反例：

```cpp
// foo.h
using namespace std;        // ← 污染所有 include 我的人
#include <bits/stdc++.h>    // ← 编译器告别快速编译
class Foo { vector<int> v; };
```

正例：

```cpp
// foo.h
#pragma once
#include <vector>           // 我直接用了 vector
namespace mylib {
class Foo {
public:
    Foo();
    void add(int);
private:
    std::vector<int> v_;
};
}
```


## 05.C++ 特有规则

### 5.1 RAII 优先

| 反模式 | 正模式 |
|--------|--------|
| `new T; ... delete t;` | `auto t = std::make_unique<T>();` |
| `lock(); ... unlock();` | `std::scoped_lock lk(m);` |
| `fopen(); ... fclose();` | `std::ifstream f(...);` 或 `unique_ptr<FILE, decltype(&fclose)>` |
| `if (err) goto cleanup;` | 析构函数自动清理 |

**评审纪律**：见到裸 `new`/`delete`/`malloc`/`free`/手工 `unlock` 就要标黄，要求作者解释"为什么不能 RAII"。

### 5.2 const 与 noexcept

```cpp
class Foo {
public:
    int size() const noexcept;           // 显然
    int& at(size_t) noexcept = delete;   // 不抛？看实现
    void swap(Foo&) noexcept;            // 标准容器需要的契约
};
```

`const`：**所有不修改对象状态的函数都必须标**——既是文档，也让 const 对象能调用。  
`noexcept`：**正确使用能让 `std::vector<T>` 在扩容时用 move 而不是 copy**，性能差异巨大。

但 `noexcept` 是契约：违反会直接 `std::terminate`。**非 100% 把握不抛的不要标**。

### 5.3 智能指针选择

决策树：

```
有所有权吗？
├─ 否，仅观察 → 裸指针 / 引用 / std::span
└─ 是
   ├─ 唯一所有权 → unique_ptr（默认选这个）
   ├─ 共享所有权
   │  ├─ 简单共享 → shared_ptr
   │  └─ 有循环引用风险 → shared_ptr + weak_ptr
   └─ 数组所有权 → unique_ptr<T[]> 或 vector<T>
```

review 看到 `shared_ptr` 要追问："为什么必须共享？"——80% 时候改成 `unique_ptr` + 借引用即可。`shared_ptr` 的引用计数是真实开销（原子操作 + 缓存抖动）。

### 5.4 模板与重载

什么时候模板：

- 行为对所有类型一致（容器、算法）
- 编译期能确定（避免运行时多态开销）

什么时候不模板：

- 行为只对几个固定类型有效（用重载更清楚）
- 模板会让头文件巨大、编译慢
- 错误信息会变成 200 行模板地狱

C++20 加 Concepts 后，**复杂 SFINAE 几乎都该改成 Concepts**：

```cpp
// 旧：SFINAE 地狱
template <typename T,
          std::enable_if_t<std::is_integral_v<T>, int> = 0>
T add(T a, T b) { return a + b; }

// 新：Concepts，错误信息友好
template <std::integral T>
T add(T a, T b) { return a + b; }
```


## 06.Review checklist

### 6.1 正确性维度

- [ ] 边界条件：空容器、最大值、负数、零
- [ ] 错误路径：每个 fail 点是否有合理处理？是否泄漏资源？
- [ ] 并发安全：共享数据有同步？锁顺序一致？
- [ ] 生命周期：所有指针/引用的所有权清晰？无悬挂？
- [ ] 异常安全：throw 之后状态是否一致？至少 basic guarantee？
- [ ] 整数溢出：所有"长度类"计算前是否检查上限？
- [ ] 接口契约：前置/后置条件是否在文档中明示？

### 6.2 可维护性维度

- [ ] 命名是否表意清晰？
- [ ] 函数 < 50 行？类 < 500 行？
- [ ] 缩进层级 ≤ 4？
- [ ] 重复代码是否提炼？
- [ ] 注释解释 **why** 而不是 **what**？
- [ ] 公共 API 是否有 doxygen？
- [ ] 单元测试覆盖关键分支？
- [ ] commit message 描述清楚改动动机？

### 6.3 性能维度

- [ ] 热路径上有无不必要的拷贝（特别是 string/vector）？
- [ ] 容器选择合理？vector 比 list 快几乎所有场景
- [ ] 是否过早优化？没有 profile 数据的优化是空想
- [ ] 是否影响了内存布局/cache 友好性？
- [ ] 锁粒度是否合理？锁范围最小化？

### 6.4 安全维度

- [ ] 用户输入是否做了 validation？
- [ ] 是否有格式化字符串注入风险？
- [ ] 整数算术是否检查溢出？
- [ ] 序列化反序列化是否限制 size 上限？
- [ ] 是否泄漏了敏感信息（错误消息、日志）？
- [ ] 加密用法正确吗？算法、随机数、密钥来源？


## 07.评审的工程化

### 7.1 评审节奏

| 项 | 推荐 |
|----|------|
| PR 大小 | < 400 行变更（研究表明超过缺陷发现率骤降） |
| 单次评审时长 | < 60 分钟，超时安排第二轮 |
| PR 等待时间 | < 24 小时收到第一轮反馈 |
| 单 PR 来回轮次 | < 3 轮，超过往往是 PR 太大 |
| 每周评审时间 | 每个工程师 5-10 小时是合理上限 |

### 7.2 评审者数量

- **1 人 review**：日常 PR，已批就合
- **2 人 review**：重要模块、新人 PR、跨模块
- **架构组 review**：公共库、核心抽象、breaking change

不要无脑 N 人 review，"责任稀释"会让大家都不深入看。

### 7.3 评论的态度

经验之谈，按重要度排序：

```
[blocker]   不修不能合：bug、安全、契约违反
[require]   要修但可后续：风格违反、缺测试
[suggest]   建议但作者可拒：更优写法、个人偏好
[nit]       小事吐槽，作者完全可忽略：typo、空格
[praise]    正向反馈：好设计、好测试
```

**写评论的措辞**：

- 差："This is wrong."
- 好："I don't think this handles X case—line 42, what if `n == 0`?"

不带情绪、给具体行号、说出推理过程。

### 7.4 评审者职责

reviewer 不是"挑错警察"。真正的角色：

| 角色 | 行为 |
|------|------|
| **质疑设计** | "为什么用 X 而不是 Y？" |
| **验证假设** | "如果并发 100 个线程进入这里会怎样？" |
| **请教问题** | "我没看懂这里的目的，能解释下吗？" |
| **提供选择** | "有个写法是 Z，可以参考下，但你这种也行" |
| **认可优秀** | "这个抽象很漂亮，记一下" |

reviewer 也是学习者。看别人代码 1 小时，比自己写 3 小时学到的东西多。


## 08.度量与改进

可量化的健康指标：

| 指标 | 健康值 | 说明 |
|------|--------|------|
| 平均 PR review 时长 | < 24h | 太长说明评审者过载或文化问题 |
| 平均 PR 大小 | < 400 行 | 大 PR 是 review 质量杀手 |
| 自动化拦截率 | 工具拦的问题 / 总问题 ≥ 70% | 否则评审者在做机器活 |
| 缺陷漏出率 | 上线 bug 数 / 评审 PR 数 | 趋势看 |
| 评审反馈延迟 | < 4h（首轮） | 阻塞越长越伤士气 |
| 评审参与广度 | top 20% reviewer 不超 50% 评审量 | 否则知识集中风险 |

每季度回顾这些指标，**用数据驱动改进**：是工具不够、文化不到、还是流程卡点。


## 09.思考题

1. 一个 1000 行的 PR，你作为 reviewer 该怎么处理？
2. 团队对"是否用异常"分歧严重，应该怎么决议？
3. clang-tidy 已经能拦下 80% 的格式/命名问题，剩 20% 是哪些？需要人来 review 哪些？
4. 评审中发现一个潜在 bug 但作者坚持"我测过没问题"，你怎么应对？
5. 设计一份"新人 1 个月入组评审作业清单"，让他在 1 个月内通过 review 别人代码学习项目。
