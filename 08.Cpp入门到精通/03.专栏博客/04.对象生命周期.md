> **案例引入｜"先析构 base 还是 derived？" 一次面试现场的翻车**
>
> 面试题：下面这段代码输出什么？
>
> ```cpp
> struct Base { ~Base() { std::cout << "~Base\n"; } };
> struct Derived : Base { ~Derived() { std::cout << "~Derived\n"; } };
> int main() {
>     Base* p = new Derived();
>     delete p;                 // 问：输出几行？
> }
> ```
>
> 候选人答："`~Derived → ~Base`，两行。" **错**——只有一行 `~Base`，而且大概率内存泄漏。面试官追问："那为什么说是未定义行为？" 候选人又说："我知道要把 `~Base()` 声明成 `virtual`——但为什么基类没 virtual 就会变成 UB？底层到底发生了什么？"
>
> 这就是典型的"**对对象生命周期缺少完整图像**"导致的掉坑。构造和析构、拷贝和移动、临时对象、RVO、异常展开——这些都是同一个主题的不同切片：**C++ 对象的"一生"由谁负责、在什么时机被调用、能不能省略**。

## 1. 引言

C++ 对象的一生——从**出生**（构造）到**死亡**（析构）——被语言标准规定得极其精确：调用时机、调用顺序、哪些可以被省略、谁负责调用、异常时如何回滚……全部有章可循。但这套规则**细节极多**，也正因为细节多，才有了这么多"看上去对、跑起来崩"的代码。

### 1.1 对象生命周期的五大阶段

```mermaid
stateDiagram-v2
    [*] --> 分配内存: new / 栈分配 / 容器扩容
    分配内存 --> 构造: 调用构造函数
    构造 --> 活动: 进入成员函数调用 / 参与运算
    活动 --> 析构: 作用域结束 / delete / 容器缩容
    析构 --> 释放内存: 归还给分配器
    释放内存 --> [*]

    活动 --> 移动后: std::move(obj) 被消费
    移动后 --> 析构: 源对象仍需析构（"已掏空但未销毁"）
```

**关键观察**：**移动** 不是一个独立阶段，它发生在"活动"里——被移动过的对象**仍要析构**，这是 `std::unique_ptr` 等 RAII 类正确性的基石。

## 2. 构造函数详解

### 2.1 构造函数的种类

```cpp
#include <iostream>
#include <string>

class Widget {
    int id_;
    std::string name_;
    int* data_;
    
public:
    // 1. 默认构造函数
    Widget() : id_(0), name_("default"), data_(new int(0)) {
        std::cout << "Default ctor: " << id_ << std::endl;
    }
    
    // 2. 参数化构造函数
    Widget(int id, const std::string& name) 
        : id_(id), name_(name), data_(new int(id)) {
        std::cout << "Parameterized ctor: " << id_ << std::endl;
    }
    
    // 3. 拷贝构造函数
    Widget(const Widget& other) 
        : id_(other.id_), name_(other.name_), data_(new int(*other.data_)) {
        std::cout << "Copy ctor: " << id_ << std::endl;
    }
    
    // 4. 移动构造函数
    Widget(Widget&& other) noexcept
        : id_(other.id_), name_(std::move(other.name_)), data_(other.data_) {
        other.data_ = nullptr;
        other.id_ = 0;
        std::cout << "Move ctor: " << id_ << std::endl;
    }
    
    // 5. 转换构造函数
    explicit Widget(int id) : id_(id), name_("unnamed"), data_(new int(id)) {
        std::cout << "Converting ctor: " << id_ << std::endl;
    }
    
    // 6. 委托构造函数(C++11)
    Widget(const std::string& name) : Widget(0, name) {
        std::cout << "Delegating ctor\n";
    }
    
    // 拷贝赋值
    Widget& operator=(const Widget& other) {
        std::cout << "Copy assign: " << other.id_ << std::endl;
        if (this != &other) {
            id_ = other.id_;
            name_ = other.name_;
            delete data_;
            data_ = new int(*other.data_);
        }
        return *this;
    }
    
    // 移动赋值
    Widget& operator=(Widget&& other) noexcept {
        std::cout << "Move assign: " << other.id_ << std::endl;
        if (this != &other) {
            delete data_;
            id_ = other.id_;
            name_ = std::move(other.name_);
            data_ = other.data_;
            other.data_ = nullptr;
            other.id_ = 0;
        }
        return *this;
    }
    
    ~Widget() {
        std::cout << "Destructor: " << id_ << std::endl;
        delete data_;
    }
};
```

### 2.2 初始化列表 vs 函数体内赋值

**疑惑**：初始化列表和在构造函数体内赋值效果一样吗？

```cpp
class CompareInit {
    std::string name_;
    int value_;
    const int id_;
    int& ref_;
    
public:
    // 方式1：初始化列表（推荐）
    CompareInit(const std::string& name, int val, int id, int& r)
        : name_(name),   // 直接构造，调用string的拷贝构造函数
          value_(val),    // 直接初始化
          id_(id),        // const成员必须在初始化列表中初始化
          ref_(r)         // 引用成员必须在初始化列表中初始化
    {}
    
    // 方式2：函数体内赋值（效率低）
    // CompareInit(const std::string& name, int val, int id, int& r)
    //     : id_(id), ref_(r)  // 这两个必须在初始化列表
    // {
    //     name_ = name;   // 先默认构造string，再赋值 → 两步操作
    //     value_ = val;   // 先默认初始化，再赋值
    // }
};
```

**答疑**：

```
初始化列表 vs 函数体赋值的区别：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

初始化列表：
  name_(name)  →  string拷贝构造函数（1次调用）

函数体赋值：
  先：name_()   →  string默认构造函数（1次调用）
  后：name_ = name  →  string赋值运算符（1次调用）
  总共2次调用，且默认构造的结果被浪费了

特殊情况（必须用初始化列表）：
├── const成员
├── 引用成员
├── 没有默认构造函数的成员
└── 基类构造函数
```

### 2.3 成员初始化顺序

```cpp
class OrderDemo {
    int a_;
    int b_;
    int c_;
public:
    // 注意：成员的初始化顺序由声明顺序决定，不是初始化列表的顺序！
    OrderDemo() : c_(3), a_(1), b_(a_ + 1) {
        // 实际初始化顺序：a_(1) → b_(a_+1=2) → c_(3)
        // 因为声明顺序是 a_, b_, c_
    }
    
    // 危险：如果依赖错误的顺序
    // OrderDemo() : c_(3), b_(c_ + 1), a_(1) {}
    // 实际顺序：a_(1) → b_(c_+1) → c_(3)
    // b_使用了未初始化的c_！→ UB
};

// GCC警告：-Wreorder 可以检测这个问题
```

### 2.4 委托构造函数

```cpp
class Connection {
    std::string host_;
    int port_;
    bool ssl_;
    int timeout_;
    
public:
```

## 3. 析构函数

### 3.1 析构顺序

```cpp
class Inner {
public:
    std::string name;
    Inner(const std::string& n) : name(n) { std::cout << "  Inner(" << name << ")\n"; }
    ~Inner() { std::cout << "  ~Inner(" << name << ")\n"; }
};

class Outer {
    Inner first_;
    Inner second_;
    Inner third_;
public:
    Outer() : first_("1st"), second_("2nd"), third_("3rd") {
        std::cout << "  Outer constructed\n";
    }
    ~Outer() {
        std::cout << "  ~Outer starting\n";
        // 析构函数体执行后，成员按声明的逆序析构
    }
};

// 构造顺序：first → second → third → Outer体
// 析构顺序：~Outer体 → ~third → ~second → ~first
// 析构顺序与构造顺序严格相反
```

### 3.2 继承中的构造和析构顺序

```cpp
class Base {
public:
    Base()  { std::cout << "Base()\n"; }
    virtual ~Base() { std::cout << "~Base()\n"; }
};

class Middle : public Base {
    Inner member_{"Middle::member"};
public:
    Middle() { std::cout << "Middle()\n"; }
    ~Middle() { std::cout << "~Middle()\n"; }
};

class Top : public Middle {
    Inner member_{"Top::member"};
public:
    Top() { std::cout << "Top()\n"; }
    ~Top() { std::cout << "~Top()\n"; }
};

void construction_order() {
    Top t;
    // 构造顺序：
    // 1. Base()                    基类
    // 2. Inner("Middle::member")   Middle的成员
    // 3. Middle()                  Middle函数体
    // 4. Inner("Top::member")      Top的成员
    // 5. Top()                     Top函数体
    
    // 析构顺序（严格相反）：
    // 5. ~Top()
    // 4. ~Inner("Top::member")
    // 3. ~Middle()
    // 2. ~Inner("Middle::member")
    // 1. ~Base()
}
```

### 3.3 析构函数中的注意事项

```cpp
class Resource {
    FILE* file_;
    int* buffer_;
public:
    Resource() : file_(fopen("test.txt", "w")), buffer_(new int[100]) {}
    
    ~Resource() noexcept {
        // 规则1：析构函数不应该抛出异常
        // 如果析构中抛出异常且已有异常在传播，程序会调用std::terminate
        
        try {
            if (file_) fclose(file_);
        } catch (...) {
            // 吞掉异常
        }
        
        delete[] buffer_;
        
        // 规则2：析构函数不要调用虚函数
        // 在析构过程中，对象的动态类型会"退化"
        // Base析构中调用虚函数，调用的是Base版本，不是Derived版本
    }
};

// 演示析构中虚函数的行为
class VBase {
public:
    virtual void identify() { std::cout << "VBase\n"; }
    virtual ~VBase() {
        identify();  // 调用VBase::identify，不是Derived版本！
    }
};

class VDerived : public VBase {
public:
    void identify() override { std::cout << "VDerived\n"; }
    ~VDerived() {
        identify();  // 调用VDerived::identify
    }
};

void destructor_virtual() {
    VBase* p = new VDerived();
    delete p;
    // 输出：
    // VDerived    (VDerived析构中)
    // VBase       (VBase析构中，不是VDerived!)
}
```

## 4. 对象的各种创建方式

### 4.1 栈对象

```cpp
void stack_objects() {
    // 直接初始化
    Widget w1(1, "direct");
    
    // 拷贝初始化
    Widget w2 = Widget(2, "copy-init");

    Widget w4;  // 调用默认构造函数
    
    // 值初始化
    Widget w5{};  // 调用默认构造函数

    int y;        // 默认初始化（未初始化，值不确定）
    
    // 作用域结束时，逆序析构：w5, w4, w3, w2, w1
}
```

### 4.2 堆对象

```cpp
void heap_objects() {
    // 原始new
    Widget* p1 = new Widget(1, "heap");
    delete p1;
    
    // 数组new
    Widget* p2 = new Widget[3];  // 调用3次默认构造
    delete[] p2;                 // 调用3次析构，逆序
    
    // placement new
    alignas(Widget) char buffer[sizeof(Widget)];
    Widget* p3 = new (buffer) Widget(3, "placement");
    p3->~Widget();  // 手动调用析构函数
    // 不能delete p3!
    
    // nothrow new
    Widget* p4 = new (std::nothrow) Widget(4, "nothrow");
    if (p4) delete p4;
    
    // 智能指针（推荐）
    auto p5 = std::make_unique<Widget>(5, "unique");
    auto p6 = std::make_shared<Widget>(6, "shared");
    // 自动管理生命周期
}
```

### 4.3 全局和静态对象

```cpp
// 全局对象：main之前构造，main之后析构
Widget global_widget(0, "global");

void static_objects() {
    // 静态局部对象：第一次执行时构造，程序结束时析构
    static Widget static_widget(1, "static");
    // 线程安全（C++11保证）
    // 如果构造函数抛异常，下次进入时会再次尝试构造

Widget& getGlobalWidget() {
    static Widget instance(0, "safe_global");
    return instance;  // 保证在首次使用时初始化
}
```

## 5. 拷贝和移动

### 5.1 拷贝语义

```cpp
class DeepCopy {
    int* data_;
    size_t size_;
public:
    DeepCopy(size_t n) : size_(n), data_(new int[n]) {
        std::fill(data_, data_ + n, 0);
    }
    
    // 深拷贝
    DeepCopy(const DeepCopy& other) : size_(other.size_), data_(new int[other.size_]) {
        std::copy(other.data_, other.data_ + size_, data_);
        std::cout << "Deep copy: " << size_ << " elements\n";
    }
    
    DeepCopy& operator=(const DeepCopy& other) {
        if (this != &other) {
            // Copy-and-swap idiom
            DeepCopy temp(other);
            std::swap(data_, temp.data_);
            std::swap(size_, temp.size_);
        }
        return *this;
    }
    
    ~DeepCopy() { delete[] data_; }
};

// 什么时候调用拷贝构造？
void copy_scenarios() {
    DeepCopy a(100);
    
    // 1. 用已有对象初始化新对象
    DeepCopy b = a;       // 拷贝构造
    DeepCopy c(a);        // 拷贝构造
    
    // 2. 函数参数传值
    auto by_value = [](DeepCopy obj) {};
    by_value(a);           // 拷贝构造
    
    // 3. 函数返回值（可能被消除）
    auto factory = []() { DeepCopy d(50); return d; };
    DeepCopy e = factory();  // NRVO可能消除拷贝
    
    // 4. 赋值
    DeepCopy f(200);
    f = a;                 // 拷贝赋值运算符
}
```

### 5.2 移动语义

```cpp
class MoveDemo {
    int* data_;
    size_t size_;
    std::string name_;
public:
    MoveDemo(size_t n, const std::string& name) 
        : size_(n), data_(new int[n]), name_(name) {
        std::cout << "Construct " << name_ << "\n";
    }
    
    // 移动构造：窃取资源
    MoveDemo(MoveDemo&& other) noexcept
        : data_(other.data_), size_(other.size_), name_(std::move(other.name_)) {
        other.data_ = nullptr;
        other.size_ = 0;
        std::cout << "Move construct " << name_ << "\n";
    }
    
    // 移动赋值
    MoveDemo& operator=(MoveDemo&& other) noexcept {
        if (this != &other) {
            delete[] data_;
            data_ = other.data_;
            size_ = other.size_;
            name_ = std::move(other.name_);
            other.data_ = nullptr;
            other.size_ = 0;
        }
        std::cout << "Move assign " << name_ << "\n";
        return *this;
    }
    
    ~MoveDemo() { delete[] data_; }
};

void move_scenarios() {
    MoveDemo a(1000000, "big_object");
    
    // 移动：转移所有权而不是拷贝数据
    MoveDemo b = std::move(a);  // 移动构造
    // a现在处于"有效但不确定"的状态
    // 不能假设a的任何特定值，但可以安全地析构或重新赋值
    
    // 从函数返回（通常被消除，但概念上是移动）
    auto factory = []() -> MoveDemo {
        MoveDemo temp(500, "temp");
        return temp;  // 移动（如果没有NRVO）
    };
    MoveDemo c = factory();
}
```

### 5.3 noexcept与移动

```cpp
// noexcept对移动操作极其重要
class SafeMove {
public:
    SafeMove(SafeMove&&) noexcept;  // 标记为noexcept
};

class UnsafeMove {
public:
    UnsafeMove(UnsafeMove&&);  // 未标记noexcept
};

// STL容器（如vector）在扩容时：
// - 如果元素的移动构造是noexcept → 使用移动
// - 如果不是noexcept → 使用拷贝（保证强异常安全）
// 原因：如果移动一半时抛异常，已移动的元素无法恢复

#include <vector>
void noexcept_importance() {
    std::vector<SafeMove> v1;
    // v1扩容时使用移动 → 高效

    std::vector<UnsafeMove> v2;
    // v2扩容时使用拷贝 → 低效但安全
    
    // 所以：移动构造/赋值应该标记noexcept
    // 除非真的可能抛出异常
}
```

## 6. 拷贝消除（Copy Elision）

### 6.1 RVO和NRVO

```cpp
class Tracer {
public:
    Tracer()                    { std::cout << "Default ctor\n"; }
    Tracer(const Tracer&)       { std::cout << "Copy ctor\n"; }
    Tracer(Tracer&&)            { std::cout << "Move ctor\n"; }
    Tracer& operator=(const Tracer&) { std::cout << "Copy assign\n"; return *this; }
    ~Tracer()                   { std::cout << "Destructor\n"; }
};

// RVO (Return Value Optimization) - 返回临时对象
Tracer make_rvo() {
    return Tracer();  // 直接在调用者的空间中构造
}

// NRVO (Named Return Value Optimization) - 返回具名对象
Tracer make_nrvo() {
    Tracer t;
    // ... 使用t
    return t;  // 编译器可能消除拷贝/移动
}

void copy_elision_demo() {
    std::cout << "--- RVO ---\n";
    Tracer a = make_rvo();
    // C++17前：可能输出 "Default ctor" + "Move ctor"
    // C++17后：保证只输出 "Default ctor"（强制拷贝消除）
    
    std::cout << "--- NRVO ---\n";
    Tracer b = make_nrvo();
    // NRVO不是强制的，但大多数编译器都会做
    // 通常只输出 "Default ctor"
}
```

### 7.1 临时对象的生命周期

### 7.2 减少临时对象的技巧

```cpp
#include <string>
#include <vector>

void minimize_temporaries() {
    std::vector<std::string> vec;
    std::string name = "long_string_that_wont_fit_in_SSO";
    
    // 低效：创建临时对象再拷贝
    vec.push_back(name);          // 拷贝
    vec.push_back(std::string("temp"));  // 构造临时 + 移动
    
    // 高效：原地构造
    vec.emplace_back(name);       // 拷贝（但避免了额外的移动）
    vec.emplace_back("temp");     // 直接在vector中构造string
    
    // 字符串拼接避免临时对象
    // 低效：
    std::string result = std::string("Hello") + " " + "World" + "!";
    // 每次+都创建临时string
    
    // 高效：
    std::string result2;
    result2.reserve(20);
    result2.append("Hello").append(" ").append("World").append("!");
    
    // 或使用string_view避免拷贝(C++17)
    std::string_view sv = "This is a view, no allocation";
}
```

## 8. 异常安全与对象生命周期

### 8.1 构造中的异常

```cpp
class ExceptionInCtor {
    int* a_;
    int* b_;
    int* c_;
public:
    ExceptionInCtor() {
        a_ = new int(1);
        b_ = new int(2);  // 如果这里抛异常...
        c_ = new int(3);  // ...这里不会执行
        // 问题：a_已分配但不会被析构（因为对象未完全构造）
        // → 内存泄漏！
    }
    ~ExceptionInCtor() {
        delete c_;
        delete b_;
        delete a_;
    }
};

// 解决方案：使用智能指针
class SafeConstruction {
    std::unique_ptr<int> a_;
    std::unique_ptr<int> b_;
    std::unique_ptr<int> c_;
public:
    SafeConstruction()
        : a_(std::make_unique<int>(1))
        , b_(std::make_unique<int>(2))   // 如果抛异常...
        , c_(std::make_unique<int>(3))
    {
        // 初始化列表中抛异常时：
        // 已构造的成员（a_）会被正确析构
        // 因为已构造的成员会被逆序析构
    }
};
```

### 8.2 异常安全的三个级别

```cpp
class Container {
    int* data_;
    size_t size_;
public:
    // 基本保证(Basic Guarantee)：
    // 异常后对象处于有效状态，但可能改变了值
    void basic_guarantee_push(int val) {
        int* new_data = new int[size_ + 1];  // 可能抛异常
        std::copy(data_, data_ + size_, new_data);
        new_data[size_] = val;
        delete[] data_;
        data_ = new_data;
        size_++;
        // 如果new抛异常，data_和size_未改变 → 基本保证
    }
    
    // 强保证(Strong Guarantee)：
    // 异常后对象状态完全不变（事务语义）
    void strong_guarantee_push(int val) {
        // Copy-and-swap idiom
        int* new_data = new int[size_ + 1];  // 可能抛异常
        std::copy(data_, data_ + size_, new_data);
        new_data[size_] = val;
        // 到此处都安全，如果抛异常则new_data泄漏？不会，因为我们还没改变对象状态
        // 但实际上需要更仔细的处理...
        
        // 只有在所有可能抛异常的操作完成后，才修改对象状态
        delete[] data_;  // noexcept
        data_ = new_data;
        size_++;
    }
    
    // 不抛保证(Nothrow Guarantee)：
    // 操作永远不会抛出异常
    size_t getSize() const noexcept {
        return size_;
    }
    
    void swap(Container& other) noexcept {
        std::swap(data_, other.data_);
        std::swap(size_, other.size_);
    }
};
```

### 8.3 RAII与异常安全

```cpp
// RAII (Resource Acquisition Is Initialization)
// 资源的获取在构造函数中完成，释放在析构函数中完成
// 异常发生时，已构造对象的析构函数保证被调用

class FileGuard {
    FILE* file_;
public:
    FileGuard(const char* path, const char* mode)
        : file_(fopen(path, mode)) {
        if (!file_) throw std::runtime_error("Cannot open file");
    }
    ~FileGuard() {
        if (file_) fclose(file_);
    }
    FILE* get() { return file_; }
    
    FileGuard(const FileGuard&) = delete;
    FileGuard& operator=(const FileGuard&) = delete;
};

void raii_exception_safety() {
    try {
        FileGuard f1("file1.txt", "r");
        FileGuard f2("file2.txt", "r");  // 如果这里抛异常
        // f1的析构函数保证被调用（栈展开）
        
        // 处理文件...
        
    } catch (const std::exception& e) {
        // f1和f2（如果已构造）都被正确清理
        std::cout << "Error: " << e.what() << std::endl;
    }
}
```

## 10. Rule of Zero/Three/Five

### 10.1 规则说明

```cpp
// Rule of Zero：如果不需要自定义资源管理，不要声明任何特殊成员函数
class RuleOfZero {
    std::string name_;
    std::vector<int> data_;
    std::unique_ptr<Widget> widget_;
    // 编译器生成的默认构造、拷贝、移动、析构全部正确
};

// Rule of Three（C++98）：如果需要自定义析构函数、拷贝构造或拷贝赋值中的任一个，
// 通常三个都需要自定义
class RuleOfThree {
    int* data_;
    size_t size_;
public:
    RuleOfThree(size_t n) : size_(n), data_(new int[n]) {}
    ~RuleOfThree() { delete[] data_; }
    RuleOfThree(const RuleOfThree& other)
        : size_(other.size_), data_(new int[other.size_]) {
        std::copy(other.data_, other.data_ + size_, data_);
    }
    RuleOfThree& operator=(const RuleOfThree& other) {
        if (this != &other) {
            delete[] data_;
            size_ = other.size_;
            data_ = new int[size_];
            std::copy(other.data_, other.data_ + size_, data_);
        }
        return *this;
    }
};

// Rule of Five（C++11）：在Rule of Three基础上加上移动构造和移动赋值
class RuleOfFive : public RuleOfThree {
public:
    using RuleOfThree::RuleOfThree;
    
    RuleOfFive(RuleOfFive&& other) noexcept
        : RuleOfThree(std::move(other)) {}
    
    RuleOfFive& operator=(RuleOfFive&& other) noexcept {
        RuleOfThree::operator=(std::move(other));
        return *this;
    }
};
```

## 十二、深挖：对象生命周期机制拾遗

### 12.1 为什么 C++ 要区分"构造"和"初始化"

其他语言（Java、Python）里"创建对象"是一个动作；C++ 把它切成了**构造（给对象一个合法的初始状态）**和**初始化（写入具体值）**两件事。这种区分看似多余，但在几个场景里是不可替代的：

- **成员初始化列表**：`A(): x(1), y(2) {}` 比 `A() { x = 1; y = 2; }` 更高效，因为前者是"构造 x 时就写入 1"，后者是"先默认构造再赋值"。对基础类型无所谓，但对 `std::string` 这种成员，差别就是一次 `malloc`。
- **常量成员 / 引用成员**：只能在初始化列表里赋值，因为一旦"构造完成"，它们就不可再改。
- **placement new**：分配和构造可以分两步，让内存池、环形缓冲区成为可能。

这也是为什么 C++ 的构造函数不能被"继承"（你必须显式委托或用 C++11 的 `using Base::Base;`）——构造是高度定制的步骤，每个类的初始逻辑可能完全不同。

### 12.2 析构顺序为什么是"反向构造顺序"

规则是：**对象按声明的反序析构，函数内的局部对象按创建的反序析构**。这不是"约定"，而是**保证正确性的唯一选择**。

想象一个简单场景：对象 A 持有对 B 的引用，B 先于 A 构造。如果析构时 B 先析构，A 在自己的析构函数里访问 B 就是 UB。反向析构保证**依赖关系始终满足**：后构造的一定先析构，它可能依赖的那些"先存在的东西"在自己析构时仍然活着。

这也是为什么 C++ 里经常出现"有问题的全局变量析构"——不同编译单元（.cpp）里的全局变量构造顺序未定义，析构顺序同样混乱，跨 .cpp 的依赖可能在析构期崩溃。解决方法是 **Meyers Singleton**（函数内 static 对象）——标准保证它的构造线程安全、析构在 `main` 返回时按反序进行。

### 12.3 拷贝构造和移动构造何时被"生成"

编译器会自动生成五个特殊成员函数：默认构造、拷贝构造、拷贝赋值、移动构造、移动赋值、析构。规则复杂但有一致性：

- 你**定义**任何一个，编译器就**不生成**对应类别的那些（如定义析构 → 不生成移动）；
- 你**显式 delete** 一个，编译器就**明确禁止**它被调用；
- 你**显式 default** 一个，就强制使用编译器生成的版本。

这就是 "Rule of Five / Zero"：
- **Rule of Zero**：不定义任何一个，让编译器全部生成（用智能指针管理资源的现代 C++ 推荐做法）。
- **Rule of Five**：定义了其中一个，就定义全部五个，避免意外的 delete/生成组合。

### 12.4 为什么"析构虚函数"是基类必备

如果 `Base` 没有虚析构，`delete static_cast<Base*>(new Derived)` 是 UB——它只调用 `Base::~Base`，`Derived` 的资源（包括成员的析构）都泄漏。

虚析构的实现：和普通虚函数一样，通过 vtable 查找实际析构函数。代价是：
- 基类必须有 vtable（多 8 字节的 vptr）；
- 析构调用多一次间接寻址。

所以"什么时候不加虚析构"也有明确答案：**类不打算被继承使用**（用 `final` 或设计上就是值类型）。`std::string`、`std::vector` 都没有虚析构——它们是"值"不是"基类"。

### 12.5 委托构造函数的一个非显然规则

C++11 允许构造函数调用同类的另一个构造函数：

```cpp
class A {
  A() : A(42) {}        // 委托到 A(int)
  A(int x) : val(x) {}
};
```

但**委托构造执行期间，对象处于"部分构造"状态**——如果被委托的构造函数抛异常，**析构函数不会被调用**（因为对象还未构造完成）。这个微妙规则导致了一个经典 bug：在委托构造里 `new` 资源，然后依赖析构释放。正确做法是用成员初始化列表 + RAII 成员（`std::unique_ptr`），让资源自己管资源。

### 12.6 临时对象的生命周期：一行语句的终点

`std::string("hello")` 这种临时对象的生命周期是**产生它的完整表达式结束**——通常是一行语句末尾的分号。所以：

```cpp
const char* p = std::string("hello").c_str();  // UB！
// 临时 string 在分号处销毁，p 成为悬空指针
```

但 C++ 有个"延长规则"：**const 引用或右值引用绑定到临时对象时，临时对象的生命周期会延长到引用的生命周期**。

```cpp
const std::string& r = std::string("hello");   // OK，临时 string 活到 r 离开作用域
```

这个规则帮你避免了大量 UB，但它有一个陷阱：**只对直接绑定生效**，不对间接绑定生效。`auto&& r = foo().get_ref();` 这种从返回值取引用再绑定，临时对象**不会延长寿命**。

理解这些细节，就能在遇到"看起来没问题但运行时崩溃"的代码时，准确指出 C++ 生命周期规则被违反的那一行。
