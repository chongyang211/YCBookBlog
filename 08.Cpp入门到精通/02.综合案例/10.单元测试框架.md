## 01.需求说明

### 1.1 为什么要写测试框架

翻完前 9 个案例你会发现一个问题：我们一直在**手动验证代码**——输入数据、眼看输出、判断对错。这在 300 行的小项目里还可以，到了 1500 行的机房预约系统就很难维持。工程师需要一种**自动化、可重复、可量化**的验证手段——这就是**单元测试（Unit Test）**。

C++ 社区成熟的测试框架包括 Google Test、Catch2、doctest。它们功能强大，但源码也都在万行以上，不适合初学者直接啃。本案例的目标是：**用 400 行写出一个够用的精简版**，让你彻底看懂"宏 + 模板 + 异常"这三件套是怎么变魔术的。

### 1.2 参考对象：Catch2 最小骨架

我们仿照 Catch2 的 API 风格（不是代码）：

```cpp
// test_sum.cpp  ← 用户只需写这一个文件
#include "mini_test.hpp"

int sum(int a, int b) { return a + b; }

TEST_CASE("sum of two ints") {
    REQUIRE(sum(1, 2) == 3);
    CHECK(sum(-1, 1) == 0);
    CHECK(sum(100, 200) == 300);
}

TEST_CASE("sum overflow") {
    REQUIRE(sum(INT_MAX, 1) != INT_MIN);  // 这行会挂，说明整数溢出是 UB
}
```

编译：`g++ -std=c++17 test_sum.cpp mini_test.cpp -o run_tests && ./run_tests`

期望输出：

```
[  PASS  ] sum of two ints
[  FAIL  ] sum overflow
  at test_sum.cpp:10
  REQUIRE(sum(INT_MAX, 1) != INT_MIN)
  with expansion: -2147483648 != -2147483648 → false

Results: 1 passed, 1 failed (2 total)
```

### 1.3 功能清单

| 编号 | 功能 | 对应宏 / API |
|------|------|--------------|
| F1 | 注册测试用例 | `TEST_CASE("name")` |
| F2 | 强断言（失败则终止当前用例） | `REQUIRE(expr)` |

| F6 | 彩色终端输出 | 内部 ANSI 转义 |
| F7 | 最终统计报告 | 自动 |

## 02.核心数据结构

### 2.1 测试用例与注册表

每个 `TEST_CASE` 被展开成一个 `TestCase` 对象，保存在全局 `vector` 中。

```cpp
// mini_test.hpp
#pragma once
#include <string>
#include <vector>
#include <functional>

namespace mt {

struct TestCase {
    std::string name;                    // 用户给的名字
    std::string file;                    // 所在源文件
    int line;                            // 所在行
    std::function<void()> body;          // 测试体
};

class Registry {
public:
    static Registry& instance();         // 单例

    // 注册一个测试用例（被宏在全局静态初始化阶段调用）
    void add(TestCase tc);

    // 跑完所有用例，返回 "失败数"
    int runAll();

private:
    std::vector<TestCase> cases_;
};

} // namespace mt
```

> **关键点**：`Registry` 用单例，保证跨翻译单元（`.cpp` 文件）能共享同一个列表。

### 2.2 断言失败异常

`REQUIRE` 失败必须**跳出当前测试用例但不能终止整个测试程序**——抛异常是 C++ 里最干净的方案。

```cpp
class AssertionFailure : public std::exception {
public:
    AssertionFailure(std::string msg) : msg_(std::move(msg)) {}
    const char* what() const noexcept override { return msg_.c_str(); }
private:
    std::string msg_;
};
```

> **为什么是异常而不是 `return`？** `REQUIRE` 展开后是一行语句，处在用户函数体的任意深度（可能在 `for` 里、可能在嵌套 Lambda 里），`return` 无法把你"送回"到 `runAll()`。异常是 C++ 里**唯一能跨越任意调用栈深度的控制流**，正好匹配这个需求。

### 2.3 全局汇总器

```cpp
struct Stats {
    int passed = 0;
    int failed = 0;
    int checks_failed = 0;   // CHECK 失败计数（不中止用例）
};
```

## 03.注册宏的设计

### 3.1 `TEST_CASE` 宏展开

目标：让用户只写 `TEST_CASE("name") { ... }` 就能自动注册。

```cpp
#define TEST_CASE(name)                                                   \
    static void MT_CONCAT(mt_test_, __COUNTER__)();                       \
    namespace {                                                           \
        struct MT_CONCAT(mt_reg_, __COUNTER__) {                          \
            MT_CONCAT(mt_reg_, __COUNTER__)() {                           \
                ::mt::Registry::instance().add(                           \
                    {name, __FILE__, __LINE__,                            \
                     &MT_CONCAT(mt_test_, __COUNTER__)});                 \
            }                                                             \
        } MT_CONCAT(mt_reg_instance_, __COUNTER__);                       \
    }                                                                     \
    static void MT_CONCAT(mt_test_, __COUNTER__)()
```

这段展开**故意保留**，让读者去体会"为什么 Catch2 的宏看起来像天书"。

### 3.2 匿名类与静态注册

简化版（便于教学，不考虑重复注册）：

```cpp
#define TEST_CASE(name)                                                       \
    static void mt_test_body_##__LINE__();                                    \
    static const bool mt_reg_##__LINE__ = [] {                                \
        ::mt::Registry::instance().add({name, __FILE__, __LINE__,             \
                                        &mt_test_body_##__LINE__});           \
        return true;                                                          \
    }();                                                                      \
    static void mt_test_body_##__LINE__()
```

**展开原理**：
1. 声明一个 `mt_test_body_42()` 函数（假设 `TEST_CASE` 在第 42 行）。
2. 定义一个**静态全局变量** `mt_reg_42 = [](){...; return true;}()`——C++ 保证**静态对象在 `main` 前初始化**，这就是"自动注册"的秘密。
3. 最后保留 `static void mt_test_body_42()`，让用户后面的 `{ ... }` 成为这个函数的函数体。

### 3.3 `__COUNTER__` 避免重名

`__LINE__` 在**同一文件、不同行**才唯一；跨文件合并可能冲突。`__COUNTER__`（编译器扩展，GCC/Clang/MSVC 都支持）在**全编译单元内单调递增**，是更稳妥的选择。

```cpp
#define MT_CONCAT_IMPL(a, b) a##b
#define MT_CONCAT(a, b) MT_CONCAT_IMPL(a, b)
```

> **为什么需要两层 CONCAT？** 因为 `##` 阻止宏展开，必须再套一层让 `__COUNTER__` 先展开再拼接。这是宏编程里最著名的"脚坑 #1"。

## 04.断言宏的设计

### 4.1 `REQUIRE` vs `CHECK`

```cpp
#define REQUIRE(expr)                                                         \
    do {                                                                      \
        if (!(expr)) {                                                        \
            throw ::mt::AssertionFailure(                                     \
                std::string(__FILE__) + ":" + std::to_string(__LINE__) +      \
                "\n  REQUIRE(" #expr ")  → false");                           \
        }                                                                     \
    } while (0)

#define CHECK(expr)                                                           \
    do {                                                                      \
        if (!(expr)) {                                                        \
            ::mt::Registry::instance().reportCheckFail(                       \
                std::string(__FILE__) + ":" + std::to_string(__LINE__) +      \
                "\n  CHECK(" #expr ")  → false");                             \
        }                                                                     \
    } while (0)
```

关键区别：`REQUIRE` 抛异常，异常被 `runAll()` 在单次用例外层捕获，当前用例标记失败并进入下一个；`CHECK` 只记录，继续跑完后续断言。

### 4.2 `#` 字符串化技巧

`#expr` 在预处理阶段把 `expr` 的**文本**变成字符串字面量：

```
REQUIRE(sum(1,2) == 3)
↓ 预处理展开
throw AssertionFailure(... "REQUIRE(sum(1,2) == 3) → false" ...);
```

这让错误信息带上**用户代码的原貌**，是测试框架输出可读性的关键。

### 4.3 `do { ... } while(0)` 包裹

为什么要多套一层 `do-while(0)`？因为：

```cpp
if (cond) REQUIRE(x);  // 如果 REQUIRE 不是单语句，这里就会出意外
else other();
```

`do { ... } while(0)` 让多行宏展开成"单语句"，在 if 后面、结尾需要分号等各种场景下都能保持语法正确。**这是 C++ 宏编程的不成文约定**。

## 05.浮点比较 APPROX

### 5.1 直接比较的陷阱

```cpp
REQUIRE(0.1 + 0.2 == 0.3);   // 失败！浮点不是数学实数
```

`0.1 + 0.2` 的 IEEE 754 结果是 `0.30000000000000004`。

### 5.2 相对误差 + 绝对误差

正确的比较应该是：

$$|a - b| < \max(\epsilon_{abs},\ \epsilon_{rel} \times \max(|a|, |b|))$$

代码：

```cpp
class Approx {
public:
    explicit Approx(double val, double eps = 1e-9)
        : value_(val), eps_(eps) {}

    friend bool operator==(double lhs, const Approx& rhs) {
        double tol = std::max(rhs.eps_,
                              rhs.eps_ * std::max(std::abs(lhs), std::abs(rhs.value_)));
        return std::abs(lhs - rhs.value_) < tol;
    }
    friend bool operator==(const Approx& lhs, double rhs) { return rhs == lhs; }

    friend std::ostream& operator<<(std::ostream& os, const Approx& a) {
        return os << "Approx(" << a.value_ << " ± " << a.eps_ << ")";
    }

private:
    double value_;
    double eps_;
};
```

用户侧：

```cpp
REQUIRE(0.1 + 0.2 == Approx(0.3));           // PASS，默认 1e-9
REQUIRE(pi_approx == Approx(3.14159).eps(1e-4));  // 可链式调整误差
```

### 5.3 运算符重载

`operator==` 双向重载（`double == Approx` 与 `Approx == double`）是卷一第 4 章运算符重载的典型应用。**友元函数是必要的**——因为左侧是 `double`，不可能是 `Approx` 的成员。

## 06.泛型断言

### 6.1 `REQUIRE_EQ` 模板实现

```cpp
template <typename A, typename B>
void requireEq(const A& a, const B& b,
               const char* a_str, const char* b_str,
               const char* file, int line) {
    if (!(a == b)) {
        std::ostringstream oss;
        oss << file << ":" << line << "\n"
            << "  REQUIRE_EQ(" << a_str << ", " << b_str << ")\n"
            << "  with expansion: " << a << " == " << b << " → false";
        throw AssertionFailure(oss.str());
    }
}

#define REQUIRE_EQ(a, b) \
    ::mt::requireEq((a), (b), #a, #b, __FILE__, __LINE__)
```

### 6.2 类型无关的错误消息

模板参数 `A`/`B` 让 `a == b` 支持任意可比类型；`oss << a` 要求**类型可流式输出**。

### 6.3 `operator<<` 的退化技巧

如果 `A` 没重载 `operator<<`（比如自定义类），上面代码会编译失败。现代做法（C++17）：

```cpp
template <typename T, typename = void>
struct is_streamable : std::false_type {};

template <typename T>
struct is_streamable<T, std::void_t<decltype(std::declval<std::ostream&>() << std::declval<T>())>>
    : std::true_type {};

template <typename T>
void safePrint(std::ostream& os, const T& v) {
    if constexpr (is_streamable<T>::value) {
        os << v;
    } else {
        os << "<unprintable: " << typeid(T).name() << ">";
    }
}
```

`if constexpr` 在**编译期**选择分支，`is_streamable<T>` 用 SFINAE 探测类型能力——这是**卷一第 18 章特性图谱**里多次出现的模式。

## 07.测试驱动器 main

### 7.1 扫描注册表

```cpp
int Registry::runAll() {
    Stats s;
    for (const auto& tc : cases_) {
        std::cout << "[  RUN   ] " << tc.name << "\n";
        try {
            tc.body();
            std::cout << "[  PASS  ] " << tc.name << "\n";
            ++s.passed;
        } catch (const AssertionFailure& e) {
            std::cout << "[  FAIL  ] " << tc.name << "\n"
                      << "  " << e.what() << "\n";
            ++s.failed;
        } catch (const std::exception& e) {
            std::cout << "[ ERROR  ] " << tc.name << " (uncaught std::exception: "
                      << e.what() << ")\n";
            ++s.failed;
        } catch (...) {
            std::cout << "[ ERROR  ] " << tc.name << " (uncaught unknown exception)\n";
            ++s.failed;
        }
    }
    std::cout << "\nResults: " << s.passed << " passed, "
              << s.failed << " failed (" << cases_.size() << " total)\n";
    return s.failed;
}
```

### 7.2 异常捕获

三级 catch：
1. `AssertionFailure`：预期内的测试失败；
2. `std::exception`：被测代码抛出的其他标准异常（通常是代码 bug）；
3. `...`：来路不明的异常（例如 `throw 42`），全部标记为 ERROR 而不是 FAIL。

这是**卷一第 14 章"异常层次"**的经典实践。

### 7.3 彩色输出

```cpp
constexpr const char* GREEN = "\033[32m";
constexpr const char* RED   = "\033[31m";
constexpr const char* RESET = "\033[0m";

std::cout << GREEN << "[  PASS  ] " << RESET << tc.name << "\n";
```

> Windows 10+ 的 `cmd` / Windows Terminal 已原生支持 ANSI 转义。如果在老版 `cmd` 中乱码，用 `#ifdef _WIN32` 条件编译关闭颜色即可——顺带练习**卷一第 17 章条件编译**。

### 7.4 主入口

```cpp
// mini_test.cpp
int main() {
    return ::mt::Registry::instance().runAll();
}
```

用户的 `test_xxx.cpp` 只 `#include "mini_test.hpp"`，链接 `mini_test.cpp`，就自动得到一个能跑的测试程序——**零样板代码**。

## 08.示例使用

### 8.1 测试一个纯函数

```cpp
#include "mini_test.hpp"

int factorial(int n) {
    if (n < 0) throw std::invalid_argument("n must be >= 0");
    return n <= 1 ? 1 : n * factorial(n - 1);
}

TEST_CASE("factorial basic") {
    REQUIRE(factorial(0) == 1);
    REQUIRE(factorial(1) == 1);
    REQUIRE(factorial(5) == 120);
}

TEST_CASE("factorial throws on negative") {
    REQUIRE_THROWS_AS(factorial(-1), std::invalid_argument);
}
```

### 8.2 测试一个类

```cpp
TEST_CASE("Account deposit/withdraw") {
    Account a("001", "test", 100.0);
    a.deposit(50);
    REQUIRE_EQ(a.getBalance(), 150.0);
    a.withdraw(80);
    REQUIRE_EQ(a.getBalance(), 70.0);
}

TEST_CASE("Account withdraw overdraft fails silently") {
    Account a("002", "test", 100.0);
    a.withdraw(200);
    CHECK_EQ(a.getBalance(), 100.0);  // 余额应该不变
}
```

### 8.3 异常断言 `REQUIRE_THROWS`

```cpp
#define REQUIRE_THROWS_AS(expr, ExceptionT)                                   \
    do {                                                                      \
        bool caught = false;                                                  \
        try { (void)(expr); }                                                 \
        catch (const ExceptionT&) { caught = true; }                          \
        catch (...) { /* wrong type */ }                                      \
        if (!caught) {                                                        \
            throw ::mt::AssertionFailure(                                     \
                std::string(__FILE__) + ":" + std::to_string(__LINE__) +      \
                "\n  REQUIRE_THROWS_AS(" #expr ", " #ExceptionT ")"           \
                "\n  but no exception of that type was thrown");              \
        }                                                                     \
    } while (0)
```

### 8.4 完整闭环测试

把 8.1～8.3 的所有用例汇总到一个 `test_demo.cpp`，**故意混进 1 个失败用例**，验证框架"通过/失败"两条路径都正确：

```cpp
// test_demo.cpp
#include "mini_test.hpp"
#include <stdexcept>

int factorial(int n) {
    if (n < 0) throw std::invalid_argument("n must be >= 0");
    return n <= 1 ? 1 : n * factorial(n - 1);
}

TEST_CASE("factorial basic") {
    REQUIRE(factorial(0) == 1);
    REQUIRE(factorial(1) == 1);
    REQUIRE(factorial(5) == 120);
}

TEST_CASE("factorial throws on negative") {
    REQUIRE_THROWS_AS(factorial(-1), std::invalid_argument);
}

TEST_CASE("approx float compare") {
    REQUIRE(0.1 + 0.2 == mt::Approx(0.3));   // 通过
}

TEST_CASE("intentional failure") {
    REQUIRE(1 + 1 == 3);                      // 故意挂掉
}
```

编译 + 运行：

```bash
g++ -std=c++17 mini_test.cpp test_demo.cpp -o run_tests
./run_tests
```

预期打印（颜色省略）：

```text

[  PASS  ] factorial basic
[  RUN   ] factorial throws on negative
[  PASS  ] factorial throws on negative
[  RUN   ] approx float compare
[  PASS  ] approx float compare
[  RUN   ] intentional failure
[  FAIL  ] intentional failure
  test_demo.cpp:24
  REQUIRE(1 + 1 == 3)  → false

Results: 3 passed, 1 failed (4 total)
```

`exit code` 等于失败用例数（这里是 1）——CI 系统拿到非零退出码会**自动把这次构建标红**。最关键的细节：**4 个 TEST_CASE 全部被自动收集执行**，用户从没写过"register"代码——这就是 3.1 静态注册宏的价值兑现。

> 🧠 **`exit code = 失败数` 是测试驱动器的行业惯例**：不仅 mini_test 这样设计，Catch2 / Google Test / pytest / JUnit 全部如此。CI 脚本里 `./run_tests && deploy.sh` 这一行就够了——失败时短路阻止部署、成功时继续。如果你的测试程序总是 `return 0`，CI 会**永远把红测试当成绿色通过**，这是新手最容易在 CI 流程上踩的坑。

> 💡 **跑一次 + 看错误信息 = 测试框架的全部价值**：上面 `intentional failure` 那条打印"REQUIRE(1 + 1 == 3) → false"——把**用户写的表达式原样回显**是借助 4.2 的 `#expr` 字符串化技巧实现的。换成 Google Test，错误信息会更详细（连两侧值也展开），但本质都是宏在干活。

### 9.2 核心原理复盘

| 机制 | 作用 | 对应卷一章 |
|------|------|-----------|
| 全局静态对象初始化先于 main | 实现 `TEST_CASE` 自动注册 | 第 11 章 内存模型（静态存储期） |

| 运算符重载 | `0.1+0.2 == Approx(0.3)` | 第 4 章 运算符 |

### 9.3 优缺点与对比 Catch2

**优点**：
- 零依赖、400 行、编译 < 1s
- API 保持与 Catch2 一致，替换只需修改 `#include`
- 每个机制都能在卷一某一章找到出处

**缺点**：
- 不支持参数化测试（Catch2 的 `GENERATE`）
- 不支持测试分节（`SECTION`）
- 不支持 BDD 风格（`SCENARIO`/`GIVEN`/`WHEN`/`THEN`）
- 输出无 JUnit XML，无法直接对接 CI

这也是 Catch2 万行代码的价值所在——上面每个缺点都对应一套复杂机制。**本案例的目的不是替代 Catch2，而是让你看懂 Catch2**。

## 10.技术思考

### 10.1 为什么 `TEST_CASE` 能"自动被发现"？

C++ 标准保证：**命名空间作用域的静态存储期对象，在 main 之前被初始化**（同一翻译单元内按声明顺序）。我们利用这条规则——`static const bool mt_reg_... = []{ register(); return true; }()` 把"注册动作"挂载到静态对象的初始化上。main 启动时，注册表已经被 N 个测试用例填满。

> **注意**：跨翻译单元的静态对象初始化顺序是**未定义**的。这就是为什么 `Registry` 必须是 **Meyers 单例**（函数内 `static` 局部变量），而不是全局对象——函数内 `static` 在**首次调用**时初始化，保证被访问前一定构造完成。

### 10.2 异常为什么是测试框架的正确选择？

`REQUIRE` 可能在如下位置被调用：

```cpp
TEST_CASE("deep") {
    for (int i = 0; i < 100; ++i) {
        runSomething([i]() {
            doMore([i]() {
                REQUIRE(i >= 0);   // ← 如何"一键跳出"到用例外？
            });
        });
    }
}
```

`return` 只能回到**当前函数**；`goto` 无法跨函数；**只有异常能跨越任意调用栈深度**。加上"异常在未被捕获时自然终止线程"这条性质，`runAll` 外层一个 `try/catch` 就能兜住所有 `REQUIRE` 失败，不论它发生在嵌套多深。

### 10.3 宏 vs `constexpr if`：什么时候必须用宏？

模板和 `if constexpr` 几乎能替代宏的所有编译期逻辑，但**有两件事仍离不开宏**：

1. **拿到源代码文本**：`#expr` 把表达式原样字符串化，用于错误信息。模板做不到。
2. **拿到源代码位置**：`__FILE__`/`__LINE__`/`__func__` 是预处理器特性。C++20 起有 `std::source_location` 可以替代，但需要作为参数默认值传递，侵入接口。

这就是为什么 Catch2 / Google Test 到今天仍然是**宏 + 模板**的混合架构。

### 11.2 与下一案例的递进

### 11.3 三个延伸挑战

**A（基础）· `SECTION` 分节**：模仿 Catch2，让一个 `TEST_CASE` 内部能写：
```cpp
TEST_CASE("Account") {
    Account a("001", "x", 100);
    SECTION("deposit") { a.deposit(50); REQUIRE_EQ(a.getBalance(), 150); }
    SECTION("withdraw") { a.withdraw(30); REQUIRE_EQ(a.getBalance(), 70); }
}
```
每个 `SECTION` 都重新执行一次外层 `TEST_CASE` 初始化代码——这是 Catch2 最核心的"**基于分支路径的树形执行**"。实现难度：需要在 `TEST_CASE` 里维护一棵执行树。

**B（进阶）· 参数化测试**：实现 `GENERATE` 让同一 `TEST_CASE` 对一组数据重复运行：
```cpp
TEST_CASE("abs") {
    int x = GENERATE(-3, 0, 3, -100, 100);
    REQUIRE(std::abs(x) >= 0);
}
```

**C（挑战）· JUnit XML 输出**：加一个 `--reporter=junit` 命令行开关，把结果写成 Jenkins / GitLab CI 能识别的 XML 格式。这一步做完，你的小框架就能接进真实的 CI 流水线——**玩具变成工具**。
