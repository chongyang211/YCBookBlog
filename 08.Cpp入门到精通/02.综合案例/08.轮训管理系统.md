# 第八章：C++ 轮询管理系统

> 本章是**策略模式 + 命令模式**的工程化练习——"轮询器"的核心问题只有一个："下次间隔多久"。这个行为被抽成 `IPollingStrategy` 接口，内置三种实现（固定间隔 / 指数退避 / 随机抖动），用户也可以自己写一个。相比 [07.票务](./07.票务购买系统.md) 偏重"多线程并发"，本案例把重点放在 **`std::function` + 抽象接口 + `std::chrono` + `std::async/future`** 四件套的组合拳上——这是写"基础设施级"框架代码最常见的思维方式。
>
> 跟着本章一步步写完，你会得到一个**生产级轮询调度框架的雏形**：可启停、可暂停继续、可热切换策略、可超时打断、可异常隔离、可统计回看。

## 01.轮询管理系统

### 1.1 产品需求

我们要做一个"通用轮询调度器"——任何"周期性地干一件事"的场景都能用，比如：每 30 秒拉取一次接口、每 5 分钟检查一次磁盘、每天凌晨跑一次任务。它的功能边界如下：

1. **可灵活设置轮询的时间**——不只是固定间隔，还要支持指数退避、随机抖动等动态策略
2. **暴露一个 `doAction` 接口**——用户传入 `std::function<TaskResult()>` 即是要周期执行的任务
3. **支持启动 / 停止 / 暂停 / 继续**——四个生命周期方法都要线程安全
4. **支持任务执行超时监控**——任务卡住了不能拖死轮询线程
5. **支持任务执行结果的回调或记录**——成功/失败/超时各算各的，可统计回看
6. **支持多线程**——轮询在一个线程，任务执行可以在另一个线程或线程池
7. **异常处理**——任务函数抛异常不能让进程崩溃，要被框架兜住

### 1.2 设计核心思路

我们将设计一个 `Poller` 类，它包含以下主要部分：

- **配置**：轮询间隔（用 `IPollingStrategy` 抽象，可固定可动态）、任务超时时间等
- **状态**：运行状态（运行 / 暂停 / 停止），用 `std::atomic<bool> running_` + `bool paused_` 双标志位维护
- **线程**：一个 `std::thread worker_thread_` 跑轮询主循环
- **任务执行**：用 `std::async + std::future::wait_for` 跑用户任务并提供超时能力
- **同步原语**：`std::mutex` 保护共享状态、`std::condition_variable` 让暂停/停止能够"立即响应"而不是死等

> 🧠 **为什么用 `condition_variable` 而不是 `sleep_for`？**——如果用 `sleep_for(1000ms)` 硬睡，那么暂停或停止操作要等当前 sleep 结束才生效，最坏要等一整个间隔。改用 `cond_.wait_until(lock, wake_time)` 后，外部一调 `cond_.notify_all()` 立即唤醒，**响应延迟从"间隔"降到"微秒级"**。这是工程化轮询器和"玩具版 sleep 循环"的本质区别。

### 1.3 开发的步骤

按依赖顺序自底向上：

1. 先写 `TimeUnit` 枚举 + `TimeConverter` 工具类（最底层、零依赖）
2. 写 `IPollingStrategy` 纯虚接口（依赖 `TimeUnit`）
3. 写三种具体策略：`FixedIntervalStrategy` / `ExponentialBackoffStrategy` / `RandomIntervalStrategy`（依赖接口）
4. 写 `TaskResult` 结构 + `TaskStatistics` 统计类
5. 写 `Poller` 调度引擎（聚合上述所有）
6. 写 `LooperTest.cpp` 端到端测试 main

> 💡 **为什么要按这个顺序？**——让"被依赖的人先存在"。先有 `TimeUnit`，`TimeConverter` 才有意义；先有 `IPollingStrategy`，三种策略才能实现；先有所有策略和统计，`Poller` 才能拿来用。这个顺序也是你**自顶向下设计、自底向上实现**思维方式的最朴素体现。

### 1.4 技术栈说明

| 组件 | C++ 标准库工具 | 作用 |
|------|---------------|------|
| 时间表达 | `std::chrono::steady_clock`、`std::chrono::nanoseconds` | 单调时钟（不会被系统调时影响），ns 精度 |
| 任务对象 | `std::function<TaskResult()>` | 把 lambda / 函数指针 / 仿函数统一抽象为"可调用对象" |
| 多态接口 | `virtual` 纯虚函数 + `unique_ptr<IPollingStrategy>` | 运行时切换策略 |
| 启停同步 | `std::atomic<bool>` + `std::mutex` + `std::condition_variable` | 三件套实现"可中断的等待" |
| 超时控制 | `std::async(std::launch::async, ...)` + `std::future::wait_for` | 任务级超时打断（实际是"放弃等待"） |
| 异常隔离 | `try/catch (...)` | 用户任务抛异常被兜住、转成 `TaskResult{success=false}` |
| 资源管理 | `std::unique_ptr` 自动析构 | 切换策略时旧策略自动释放，零内存泄漏 |

### 1.5 核心组件说明

类名：`Poller`，成员构成：

- 配置：`std::unique_ptr<IPollingStrategy> strategy_`（可热替换的间隔策略）
- 任务：`ActionFunc action_`（即 `std::function<TaskResult()>`）
- 状态：`std::atomic<bool> running_` + `bool paused_`
- 同步：`std::mutex mutex_` + `std::condition_variable cond_`
- 线程：`std::thread worker_thread_`
- 超时：`long task_timeout_ns_`（0 表示不开启超时控制）
- 统计：`TaskStatistics stats_`（用 deque 存最近 100 条结果）

> 🧠 **为什么 `running_` 用 `std::atomic` 而 `paused_` 是普通 `bool`？**——`running_` 在多个地方被无锁读取（包括 `run()` 主循环里 `while (running_)`），必须原子化保证内存可见性；`paused_` 只在持锁后修改/读取，普通 `bool` 即可。**根据"是否在锁外被访问"区分原子性需求**——这是并发编程最朴素也最容易踩坑的点。

#### 关于"是否使用线程池"的取舍

由于需要超时控制，C++ 标准没有提供"中断线程"的方法。我们最终的妥协方案是：

- 用 `std::async(std::launch::async, action_)` 启一个临时线程跑任务
- 主线程用 `future.wait_for(timeout)` 等结果；超时则记录"timed out"但**任务实际仍在后台跑完**（我们只是放弃等待）
- 如果任务很重而轮询间隔很短，就会出现"任务排队"——本案例的简化是：**只允许一次只跑一个任务，下一次轮询会等上一个 future 走完**（因为 `executeAction()` 是同步调用）

> ⚠️ **这是个工程妥协**：超时不能真正"杀死"任务（C++ 没有 `pthread_cancel` 的安全跨平台等价物）。如果你的任务可能永远卡住、且你不能等它自然结束，需要在任务函数内部自己埋"协作式取消点"（比如检查一个 `std::atomic<bool> cancel_token`）。

### 1.6 功能丰富

1. **轮询间隔策略**：固定间隔、指数退避、随机抖动——也可以自己写新策略，**不需要改 `Poller` 一行代码**（开闭原则）
2. **任务执行**：传入 `std::function<TaskResult()>`，框架负责调度/计时/异常隔离
3. **统计信息**：成功/失败计数 + 最近 100 条结果环形缓冲，便于排错回溯

### 1.7 轮询工作流程

```text
┌─────────────────────────────────────────────────────────────┐
│                    Poller::run() 主循环                       │
└─────────────────────────────────────────────────────────────┘
       │
       ▼
   running_ ?  ──── false ──→ 退出循环
       │ true
       ▼
  [加锁] strategy_->getNextInterval()  → next_interval (ns)
       │
       ▼
  cond_.wait_until(wake_time)  ◄── 期间任何 notify_all 都会唤醒
       │
       ▼
   paused_ ? ──── true ──→ cond_.wait(直到 !paused_ || !running_) → 重来
       │ false
       ▼
   running_ ? ──── false ──→ break
       │ true
       ▼[解锁]
   executeAction()
       │
       ├── try: result = action_()  (或 future.wait_for 超时控制)
       ├── catch: 把异常转成 TaskResult(false, "Exception: ...")
       │
       ▼
   [加锁] result.success ? recordSuccess() : recordFailure()
       │
       ▼
   回到循环开头
```

**6 个关键节点串起来一句话**：策略说"睡多久" → 条件变量睡（可被打断） → 醒了检查暂停/停止 → 跑任务（带超时和异常隔离） → 用结果回喂策略 → 再回头问策略。

> 🧠 **为什么"用结果回喂策略"很重要？**——这是**指数退避**的关键。任务失败时，下一次 `getNextInterval()` 返回的间隔会自动翻倍（在 `ExponentialBackoff` 内部实现）；任务成功时调 `reset()` 把间隔拉回初始值。**调用方只管 `recordSuccess/recordFailure`，不需要关心策略内部状态机**——又是一个策略模式的红利。

## 03.时间单位与工具

目标：定义时间单位枚举、写时间换算工具——所有内部时间统一存储为**纳秒（ns）**，对外接口允许多种单位输入。

### 3.1 时间单位定义

`TimeUnit.h`：

```cpp
#ifndef TIMEUNIT_H
#define TIMEUNIT_H

// 限定作用域枚举：枚举值的作用域被限定在 TimeUnit 内部
// 使用方式：TimeUnit::SECONDS（必须加类型前缀）
enum class TimeUnit {
    NANOSECONDS,
    MICROSECONDS,
    MILLISECONDS,
    SECONDS,
    MINUTES
};

#endif //TIMEUNIT_H
```

> 🧠 **为什么用 `enum class` 而不是传统 `enum`？**——传统 `enum`（"非限定作用域枚举"）会把枚举值**直接放到全局命名空间**，容易和别处冲突。比如：
>
> ```cpp
> enum TimeUnitOnly { SECONDS, MINUTES };  // 老式 enum
> enum DurationKind  { SECONDS };          // 编译报错：SECONDS 重定义！
> ```
>
> 而 `enum class`（C++11 引入）把枚举值**限定在类型内部**：
>
> ```cpp
> enum class TimeUnit  { SECONDS };
> enum class Duration  { SECONDS };  // OK！互不冲突
> TimeUnit u = TimeUnit::SECONDS;    // 必须加前缀
> ```
>
> **`enum class` 还禁止隐式转 int**——`int x = TimeUnit::SECONDS;` 直接编译错（必须 `static_cast<int>` 显式转换），从语法层面避免了"枚举当数字用"的脏写法。**写新代码一律 `enum class`，不要再用裸 `enum`**。

### 3.2 时间转换工具类

先定义好`TimeConverter.h`（声明）：

```cpp
#ifndef TIMECONVERTER_H
#define TIMECONVERTER_H
#include <string>
#include "TimeUnit.h"

class TimeConverter {
public:
    static long toNanoseconds(long duration, TimeUnit unit);
    static std::string unitToString(TimeUnit unit);
};

#endif //TIMECONVERTER_H
```

然后做具体`TimeConverter.cpp`（实现）：

```cpp
#include "TimeConverter.h"
#include <stdexcept>

long TimeConverter::toNanoseconds(long duration, TimeUnit unit) {
    switch (unit) {
        case TimeUnit::NANOSECONDS:  return duration;
        case TimeUnit::MICROSECONDS: return duration * 1000L;
        case TimeUnit::MILLISECONDS: return duration * 1000000L;
        case TimeUnit::SECONDS:      return duration * 1000000000L;
        case TimeUnit::MINUTES:      return duration * 60000000000L;
        default: throw std::invalid_argument("Invalid time unit");
    }
}
```

> ⚠️ **数字字面量后缀 `L` 必须要加**——`60 * 1000000000` 在 32 位 `int` 下会**溢出**（`6e10 > 2^31`）。写成 `60000000000L` 强制 `long` 类型才安全。这是**整数溢出**最常见的隐藏 bug，写时间/字节/计数类代码必须警觉。

> 💡 **为什么 `static`？**——这两个函数纯粹是"输入→输出"的换算，不依赖任何对象状态。设为 `static` 后可直接 `TimeConverter::toNanoseconds(1, TimeUnit::SECONDS)` 调用，无需 new 实例。**纯工具类一律静态成员**。

### 3.3 获取时间单位

## 04.轮询策略接口设计

### 4.1 策略接口分析

轮询器最核心的设计决策是："**下次什么时候唤醒**"。它有无数种可能的实现：

- **固定间隔**：每 1 秒一次，雷打不动（监控类任务最常用）
- **指数退避**：失败后间隔翻倍——1s → 2s → 4s → 8s（网络重试场景，保护被调方）
- **随机抖动**：在 [500ms, 2s] 之间随机取一个值（防止"惊群效应"——大量客户端同时定时拉取）
- ……还可以有"线性退避""按时间段调整"等等

如果把这些逻辑硬编码在 `Poller` 内部，每加一种就要改 `Poller`、还可能不小心动到其他策略——这就是"代码僵化"的源头。

**策略模式的核心动作**：把"易变的部分（间隔计算逻辑）"抽成一个接口，让 `Poller` 只依赖接口而不依赖具体实现。

我们要的接口长这样——四个职责：

1. `IPollingStrategy`（基类，纯虚）
2. `FixedIntervalStrategy`（固定间隔）
3. `ExponentialBackoffStrategy`（指数退避）
4. `RandomIntervalStrategy`（随机间隔）

### 4.2 轮询策略接口

`IPollingStrategy.h`：

```cpp
#ifndef IPOLLINGSTRATEGY_H
#define IPOLLINGSTRATEGY_H
#include <string>

class IPollingStrategy {
public:
    // 虚析构函数：通过基类指针 delete 派生类对象时，能正确析构
    virtual ~IPollingStrategy() {}

    // 获取下一次轮询的时间间隔（单位 ns）
    virtual long getNextInterval() = 0;

    // 重置策略内部状态（例如把指数退避的当前间隔拉回初始值）
    virtual void reset() = 0;

    // 上一次任务成功 → 让策略调整内部状态
    virtual void recordSuccess() = 0;

    // 上一次任务失败 → 让策略调整内部状态
    virtual void recordFailure() = 0;

    // 返回策略配置的可读字符串（日志用）
    virtual std::string getConfigInfo() const = 0;
};

#endif //IPOLLINGSTRATEGY_H
```

接口的五个方法各自的职责：

| 方法 | 职责 | 可变性 |
|------|------|--------|
| `getNextInterval()` | 计算下一次唤醒间隔 | 每次调用可能返回不同值（指数退避/随机） |
| `reset()` | 重置内部状态 | 切换策略后由 `Poller` 主动调用 |
| `recordSuccess()` | 接收"任务成功"信号 | 让策略据此调整下次间隔 |
| `recordFailure()` | 接收"任务失败"信号 | 同上 |
| `getConfigInfo()` | 返回可读配置信息 | 只读、用于日志 |

> 🧠 **`virtual ~IPollingStrategy() {}` 这个空虚析构非常重要**——`Poller` 持有 `std::unique_ptr<IPollingStrategy>`，析构时会通过基类指针 delete 派生类对象。**如果析构函数不是 virtual，派生类的析构函数不会被调用，会发生资源泄漏**。这是 C++ 多态最经典的陷阱，写任何打算"被继承的基类"都必须把析构标 `virtual`。

> 💡 **`= 0` 是什么意思？**——它把这个虚函数标记为"纯虚函数"。**只要类里有任何一个纯虚函数，这个类就是抽象类**——不能直接实例化（`IPollingStrategy s;` 编译报错），只能被继承并实现所有纯虚函数后才能用。这就是 C++ 表达"接口"的方式。

### 4.3 改进建议（可选项）

实战中可以根据需求扩展接口能力：

1. **线程安全**：如果某个策略内部状态被多线程同时读写（比如统计型策略），可以在其内部加 `std::mutex`
2. **更多配置**：`recordFailure()` 可以加参数 `(const std::exception& e)` 让策略根据异常类型决定退避力度
3. **日志钩子**：让策略上报"我现在为什么决定睡 X 秒"，方便排错

本案例为简化只暴露最小接口——**先把最小可用版本跑起来，再按需求加接口**，这是优秀框架演进的常态。

### 5.1 固定间隔策略

最简单的实现——构造时记下间隔（统一转 ns），每次返回同一个值：

```cpp
/**
 * @brief 固定间隔轮询策略：每次返回构造时设定的间隔，雷打不动
 */
class FixedIntervalStrategy : public IPollingStrategy {
public:
    FixedIntervalStrategy(long interval, TimeUnit unit)
        : interval_ns(TimeConverter::toNanoseconds(interval, unit)) {}

    virtual long getNextInterval() override { return interval_ns; }
    virtual void reset() override {}
    virtual void recordSuccess() override {}
    virtual void recordFailure() override {}

    virtual std::string getConfigInfo() const override {
        std::ostringstream oss;
        oss << "FixedInterval: " << interval_ns << " ns";
        return oss.str();
    }

private:
    const long interval_ns;
};
```

单元自测（写完每个策略都建议跑一下）

在 `LooperTest.cpp` 里临时加几行：

```cpp
int main() {
    FixedIntervalStrategy strategy(1000, TimeUnit::MILLISECONDS);
    std::cout << "Config: " << strategy.getConfigInfo() << std::endl;
    std::cout << "Next interval: " << strategy.getNextInterval() << " ns" << std::endl;
    std::cout << "Next interval: " << strategy.getNextInterval() << " ns" << std::endl;
    return 0;
}
```

预期输出：

```text
Config: FixedInterval: 1000000000 ns
Next interval: 1000000000 ns
Next interval: 1000000000 ns
```

`1000 ms` 被 `TimeConverter::toNanoseconds` 转成 `1_000_000_000 ns`——**所有内部时间统一存储为 ns**，对外接口才允许多种时间单位。这是"接口友好 + 内部统一"的经典做法：调用方用 `MILLISECONDS` 写得舒服，框架内部走纳秒级运算保证精度。

> 🧠 **`getNextInterval` 多次调用永远返回同一个数**：因为这是"固定间隔"策略——这正是策略模式可替换性的最低要求。下一节 `ExponentialBackoffStrategy` 每次返回的值会**翻倍**，但接口签名 `long getNextInterval()` 完全不变。**调用方代码 `int ns = strategy_->getNextInterval()` 一行不用改**就能切换策略，这就是策略模式的核心价值。

> 💡 **`override` 关键字别漏写**——如果你把基类纯虚函数签名写错（比如 `getnextInterval` 大小写写错），编译器会以为你在派生类里"新增了一个普通成员函数"而不是"重写虚函数"，结果运行时调到的还是空实现导致 bug。**加上 `override` 后编译器会校验"必须能找到对应的虚函数"，写错就编译报错**——这是 C++11 防止"重写失败"的最简单工具。

### 5.2 指数退避策略

`ExponentialBackoffStrategy` 用于"重试场景"：每次失败后间隔翻倍，直到达到 `max_ns` 上限；每次成功就重置回 `initial_ns`。

```cpp
/**
 * @brief 指数退避策略：失败时间隔翻倍、成功时重置
 */
class ExponentialBackoffStrategy : public IPollingStrategy {
public:
    ExponentialBackoffStrategy(long initial, long max, TimeUnit unit)
        : initial_ns(TimeConverter::toNanoseconds(initial, unit)),
          max_ns(TimeConverter::toNanoseconds(max, unit)),
          current_ns(initial_ns) {}

    virtual long getNextInterval() override {
        long result = current_ns;
        // 翻倍但不超过 max_ns
        current_ns = std::min(current_ns * 2, max_ns);
        return result;
    }

    virtual void reset() override { current_ns = initial_ns; }
    virtual void recordSuccess() override { reset(); }
    virtual void recordFailure() override {
        // 失败时不主动改 current_ns，因为 getNextInterval 里下一次自动翻倍
    }

    virtual std::string getConfigInfo() const override {
        std::ostringstream oss;
        oss << "ExponentialBackoff: Initial=" << initial_ns
            << "ns, Max=" << max_ns << "ns";
        return oss.str();
    }

private:
    const long initial_ns;
    const long max_ns;
    long current_ns;
};
```

行为推演（重要）

设 `initial=500ms`、`max=4000ms`，连续调用 `getNextInterval()`：

| 调用次序 | 返回值（即"本次"间隔） | `current_ns` 翻倍后变为 |
|---------|----------------------|----------------------|
| 第 1 次 | 500ms                | 1000ms |
| 第 2 次 | 1000ms               | 2000ms |
| 第 3 次 | 2000ms               | 4000ms |
| 第 4 次 | 4000ms               | 4000ms（封顶不再增长）|
| ……     | 4000ms               | 4000ms |
| 任务成功后 `recordSuccess()` 调用 | —— | 拉回 500ms |
| 第 N 次（成功后） | 500ms          | 1000ms |

> ⚠️ **`current_ns * 2` 也要警惕溢出**——如果用户传入 `max = LONG_MAX`，`current_ns * 2` 会越过 `long` 上限变成负数。生产代码里应当先判断 `if (current_ns > max_ns / 2) current_ns = max_ns; else current_ns *= 2;` 来安全防溢出。本案例因 `max_ns` 一般也就几秒级，所以省略了这层判断。

可选改进：

- (1) **线程安全**：如果策略在多线程被多个 `Poller` 共享（少见但可能），`current_ns` 写入需加锁
- (2) **更友好的配置信息**：`getConfigInfo` 中可以返回 "Initial=0.5s, Max=4s" 而不是裸 ns
- (3) **退避因子**：把 `* 2` 提取为构造参数 `factor`，允许 `* 1.5` 这种温和退避
- (4) **失败计数器**：连续失败 N 次时触发额外动作（比如告警）

### 5.3 随机间隔策略

`RandomIntervalStrategy` 用于"防止惊群"——多个客户端如果都用固定间隔轮询，请求会在每秒同一时刻挤到一起；加随机抖动后请求会被自然摊平。

```cpp
/**
 * @brief 随机间隔策略：每次在 [min, max] 区间内随机取一个间隔
 */
class RandomIntervalStrategy : public IPollingStrategy {
public:
    RandomIntervalStrategy(long min, long max, TimeUnit unit)
        : min_ns(TimeConverter::toNanoseconds(min, unit)),
          max_ns(TimeConverter::toNanoseconds(max, unit)),
          engine(std::random_device()()) {}  // 用真随机种子

    virtual long getNextInterval() override {
        std::uniform_int_distribution<long> dist(min_ns, max_ns);
        return dist(engine);
    }

    virtual void reset() override {}
    virtual void recordSuccess() override {}
    virtual void recordFailure() override {}

    virtual std::string getConfigInfo() const override {
        std::ostringstream oss;
        oss << "RandomInterval: Min=" << min_ns
            << "ns, Max=" << max_ns << "ns";
        return oss.str();
    }

private:
    const long min_ns;
    const long max_ns;
    std::default_random_engine engine;
};
```

> 🧠 **`std::random_device()()` 两层括号是什么？**——第一层 `std::random_device()` 创建一个临时 `random_device` 对象（**它是真随机源**，通常读取 OS 提供的 `/dev/urandom` 等熵源）；第二层 `()` 调用它的 `operator()` 拿出一个真随机数，作为 `default_random_engine` 的种子。
>
> **新手常见错误**：写成 `engine(time(0))` 这种"用秒级时间戳做种子"——同一秒内启动的多个进程会得到同样的随机序列。`std::random_device` 是 C++11 推荐的标准做法。

> 💡 **`std::uniform_int_distribution` 是干嘛的？**——`engine` 输出的原始整数是 `[0, 2^32)` 的均匀整数；`uniform_int_distribution<long>(min, max)` 把它压缩到 `[min, max]` 闭区间且仍保持均匀分布。**直接用 `engine() % (max-min) + min` 是不均匀的**（高位偏多），所以一定要用分布器，不要自己取模。

### 5.4 三种策略的对比

| 策略 | 何时间隔变化 | 典型场景 |
|------|------------|---------|
| `FixedInterval` | 永远不变 | 心跳/监控/简单定时任务 |
| `ExponentialBackoff` | 每次失败翻倍、成功重置 | 网络重试、保护被调方 |
| `RandomInterval` | 每次都不一样 | 多实例去抖、避免惊群 |

> 📌 **三种策略都遵守同一个 `IPollingStrategy` 接口契约**——这意味着 `Poller::updateStrategy()` 可以**在运行时把任意一种换成任意一种**，不需要重启进程、不需要 `Poller` 内部 if/else 大堆判断。这就是策略模式的杀手特性："**运行时多态地切换算法**"。

## 06.任务结果与统计

目标：定义"任务执行后的标准回执"，以及一个滚动统计的小组件——把最近 N 条结果留在内存里方便排错。

### 6.1 任务结果结构

`TaskStatistics.h` 顶部先定义 `TaskResult`——它是用户任务的统一返回值。无论你的任务实际做了什么，**最后都得给框架一个 `TaskResult` 让它知道是成功还是失败**：

```cpp
// TaskStatistics.h
#ifndef TASKSTATISTICS_H
#define TASKSTATISTICS_H
#include <chrono>
#include <deque>
#include <string>

struct TaskResult {
    bool success;                                       // 成功 / 失败
    std::string message;                                // 描述信息（失败原因 / 成功摘要）
    std::chrono::steady_clock::time_point timestamp;    // 任务完成时刻

    TaskResult(bool s, const std::string& m,
               std::chrono::steady_clock::time_point t)
        : success(s), message(m), timestamp(t) {}
};
```

> 🧠 **为什么用 `steady_clock` 而不是 `system_clock`？**——`system_clock` 是"墙钟时间"，能被用户/NTP 调整，可能突然往回跳，导致 `t2 - t1 < 0` 这种诡异结果；`steady_clock` 是"单调时钟"，永远只增不减，**只要是测"经过了多久"的场景一律用 `steady_clock`**，永远不会出错。

### 6.2 任务统计系统

继续在 `TaskStatistics.h` 里写统计类的声明：

```cpp
class TaskStatistics {
public:
    TaskStatistics() : total(0), success(0), failure(0) {}

    void recordResult(const TaskResult& result);   // 记录一条结果
    void printSummary() const;                     // 打印统计摘要

private:
    int total;
    int success;
    int failure;
    std::deque<TaskResult> recentResults;          // 最近 100 条（环形缓冲）
    std::string formatTime(const std::chrono::steady_clock::time_point& tp) const;
};

#endif //TASKSTATISTICS_H
```

> 💡 **为什么用 `std::deque` 而不是 `std::vector`？**——我们要在头部"丢老的"、尾部"加新的"。`vector::erase(begin())` 是 `O(N)`（要把所有元素往前挪一格）；`deque::pop_front()` 是 `O(1)`（双端队列的天然能力）。**滚动窗口/环形缓冲的标准选择是 `deque` 或 `boost::circular_buffer`**。

### 6.3 记录任务结果

`TaskStatistics.cpp` 实现 `recordResult`：

```cpp
// TaskStatistics.cpp
#include "TaskStatistics.h"
#include <iomanip>
#include <iostream>
#include <sstream>

void TaskStatistics::recordResult(const TaskResult& result) {
    total++;
    if (result.success) {
        success++;
    } else {
        failure++;
    }
    // 保留最近 100 条结果（环形缓冲）
    recentResults.push_back(result);
    if (recentResults.size() > 100) {
        recentResults.pop_front();
    }
}
```

> 🧠 **为什么是固定 100 条？**——既限制了内存占用（避免长期跑积累十万条结果撑爆内存），又留了足够近期信息便于"刚出问题立刻看一眼"。**这种"最近 N 条"的环形缓冲在监控系统、日志收集器、分布式追踪里无处不在**。生产代码里 100 一般会做成可配置参数。

### 6.4 打印统计摘要

```cpp
void TaskStatistics::printSummary() const {
    std::cout << "=== Task Statistics ===" << std::endl;
    std::cout << "Total runs: " << total << std::endl;
    std::cout << "Success: " << success << " ("
              << (total ? (success * 100.0 / total) : 0.0) << "%)" << std::endl;
    std::cout << "Failure: " << failure << " ("
              << (total ? (failure * 100.0 / total) : 0.0) << "%)" << std::endl;

    if (!recentResults.empty()) {
        std::cout << "\nRecent results (last "
                  << recentResults.size() << "):" << std::endl;
        for (const auto& res : recentResults) {
            auto timeStr = formatTime(res.timestamp);
            std::cout << "[" << timeStr << "] "
                      << (res.success ? "SUCCESS" : "FAILURE")
                      << ": " << res.message << std::endl;
        }
    }
}
```

> ⚠️ **`(total ? ... : 0.0)` 这层判断很重要**——如果 `total == 0` 时直接 `success * 100.0 / total` 就是除零、得到 `inf`/`nan`。**一切除法之前都要先判断分母非零**，这是数值代码最容易踩的坑之一。

### 6.5 格式化时间戳

`steady_clock::time_point` 默认无法直接 `<<` 输出。我们把它格式化成 `HH:MM:SS.mmm` 这种可读形式：

```cpp
std::string TaskStatistics::formatTime(
    const std::chrono::steady_clock::time_point& tp) const {
    // 注意：steady_clock 的 epoch 没有"现实意义"，
    // 这里仅展示相对时间结构（取模 24h 后只是个相对计数）
    auto duration = tp.time_since_epoch();
    auto hours = std::chrono::duration_cast<std::chrono::hours>(duration);
    auto minutes = std::chrono::duration_cast<std::chrono::minutes>(
        duration % std::chrono::hours(1));
    auto seconds = std::chrono::duration_cast<std::chrono::seconds>(
        duration % std::chrono::minutes(1));
    auto milliseconds = std::chrono::duration_cast<std::chrono::milliseconds>(
        duration % std::chrono::seconds(1));

    std::stringstream ss;
    ss << std::setfill('0')
       << std::setw(2) << hours.count() % 24 << ":"
       << std::setw(2) << minutes.count() << ":"
       << std::setw(2) << seconds.count() << "."
       << std::setw(3) << milliseconds.count();
    return ss.str();
}
```

> 🧠 **`steady_clock` 的 `time_since_epoch()` 没有现实意义**——它的 epoch 是"程序启动时（实现定义）"，不是"1970-01-01"。所以本函数输出的 "12:34:56.789" 只是一个**相对结构**，不是真正的时间。如果你要打印"墙钟时间"用于和外部日志对比，应当用 `std::chrono::system_clock` 然后转 `std::time_t` + `std::localtime` + `strftime`——属于 11.3 节的延伸挑战 C 范畴。

## 07.轮询器核心实现

`Poller` 是整个框架的"调度引擎"——它把"策略"和"任务"在时间轴上编排起来。

大家都是"想清楚一个能力 → 给类加一个成员/方法 → 实现 → 编译跑通 → 再加下一个"。这一节就是带你**模拟"工程师的真实思考节奏"**。

### 7.1 最小骨架start/stop

需求倒推：先抛掉策略、抛掉任务、抛掉暂停超时——一个轮询器最最最核心的两件事是 **"启动一个后台线程"** 和 **"能让它停下来"**。

只要四个成员变量就能撑起这个最小版本：

| 成员 | 类型 | 作用 |
|------|------|------|
| `running_` | `std::atomic<bool>` | 标志主循环是否要继续跑 |
| `worker_thread_` | `std::thread` | 后台轮询线程 |
| `mutex_` | `std::mutex` | 保护后续要加的共享状态（先占位） |
| `cond_` | `std::condition_variable` | 后续可中断等待用（先占位） |

**`Poller.h` v1（最小骨架）**：

```cpp
// Poller.h —— v1 最小骨架
#ifndef POLLER_H
#define POLLER_H

#include <atomic>
#include <condition_variable>
#include <mutex>
#include <thread>

class Poller {
public:
    Poller() : running_(false) {}
    ~Poller();

    void start();
    void stop();

private:
    void run();   // 后台线程主循环

    std::atomic<bool> running_;
    std::thread worker_thread_;
    std::mutex mutex_;
    std::condition_variable cond_;
};

#endif //POLLER_H
```

然后在具体实现一下，**`Poller.cpp` v1**：

```cpp
// Poller.cpp —— v1
#include "Poller.h"
#include <iostream>

Poller::~Poller() {
    stop();   // RAII：保证线程一定被 join
}

void Poller::start() {
    if (running_) return;     // 重复 start 防御
    running_ = true;
    worker_thread_ = std::thread(&Poller::run, this);
}

void Poller::stop() {
    if (!running_) return;    // 重复 stop 防御
    running_ = false;
    if (worker_thread_.joinable()) {
        worker_thread_.join();
    }
    std::cout << "Poller stopped." << std::endl;
}

void Poller::run() {
    while (running_) {
        std::cout << "[tick]" << std::endl;
        std::this_thread::sleep_for(std::chrono::milliseconds(500));
    }
}
```

然后我们调试一下代码：

```cpp
int main() {
    Poller poller;
    poller.start();
    std::this_thread::sleep_for(std::chrono::seconds(2));
    poller.stop();
    return 0;
}
```

打印结果如下所示：

```
[tick]
[tick]
[tick]
[tick]
Poller stopped.
```

到这一步，**最小骨架已经能跑了**。下一节给它接上策略和任务。

> ⚠️ **析构函数 `~Poller() { stop(); }` 是 RAII 硬性要求**——`std::thread` 析构时如果既没 `join` 也没 `detach`，C++ 标准规定**直接调 `std::terminate()` abort 进程**。所以析构必须把线程收掉。`stop()` 里那个 `if (!running_) return;` 防御就是为这一刻准备的——防止用户已经手动调过 `stop()`、析构再调一次时重复 join。

> 🧠 **`running_` 为什么用 `std::atomic<bool>`？**——主线程在 `stop()` 里写它、worker 线程在 `run()` 里读它。普通 `bool` 在多核 CPU 上**可能因 cache 不一致而看不到对方的写入**——worker 线程会一直死循环！原子类型保证了"任何一次写都对其他线程立即可见"。这是并发编程最朴素也最容易踩的坑。

> 💡 **`stop()` 里的 `running_ = false` 后还有个 `sleep_for(500ms)` 要走完才退出**——这是"硬 sleep 循环"的硬伤：**最坏要等一整个间隔才响应 stop**。我们 7.3 节会用 `condition_variable::wait_until` 解决它。

### 7.2 接上策略和任务

现在 `Poller` 还在打印傻 tick，是时候让它干真活了。我们需要给它**两件东西**：

1. **一个策略对象**——告诉它"下次睡多久"
2. **一个任务函数**——告诉它"醒来干啥"

#### 给 `Poller.h` 增量加成员

```diff
  #include <atomic>
  #include <condition_variable>
+ #include <functional>
+ #include <memory>
  #include <mutex>
  #include <thread>
+
+ #include "IPollingStrategy.h"
+ #include "TaskStatistics.h"   // 为了用 TaskResult

  class Poller {
  public:
+     typedef std::function<TaskResult()> ActionFunc;
+
-     Poller() : running_(false) {}
+     Poller(std::unique_ptr<IPollingStrategy> strategy, ActionFunc action)
+         : strategy_(std::move(strategy)),
+           action_(action),
+           running_(false) {}
      ~Poller();

      void start();
      void stop();

  private:
      void run();

+     std::unique_ptr<IPollingStrategy> strategy_;
+     ActionFunc action_;
      std::atomic<bool> running_;
      std::thread worker_thread_;
      std::mutex mutex_;
      std::condition_variable cond_;
  };
```

> 🧠 **构造函数为什么用 `std::move(strategy)`？**——`std::unique_ptr` 不可拷贝（设计哲学：一份所有权只能有一个持有者），只能"转移所有权"。`std::move` 把传入的左值变量"标记成可移动"，让初始化列表 `strategy_(std::move(strategy))` 触发 `unique_ptr` 的移动构造而不是被禁用的拷贝构造。**任何持有 `unique_ptr` 的成员，构造时都得 `std::move`，否则编译错**。

> 💡 **`ActionFunc = std::function<TaskResult()>`**——这是命令模式的体现。无论用户传 lambda、普通函数指针、还是仿函数，只要"无参 + 返回 TaskResult"，都能被 `std::function` 统一接住。**框架对外暴露 `function` 类型而非具体函数签名，是写"接受用户回调"的库的标准做法**。

#### 升级 run()——真的去跑用户任务

```cpp
void Poller::run() {
    while (running_) {
        // ① 问策略要下次间隔
        long next_interval_ns = strategy_->getNextInterval();

        // ② 朴素 sleep（下一节升级为条件变量等待）
        std::this_thread::sleep_for(std::chrono::nanoseconds(next_interval_ns));
        if (!running_) break;

        // ③ 跑用户任务（先不带超时、不带异常隔离）
        TaskResult result = action_();

        // ④ 用结果回喂策略
        if (result.success) {
            strategy_->recordSuccess();
        } else {
            strategy_->recordFailure();
        }

        std::cout << "Action: "
                  << (result.success ? "SUCCESS" : "FAILURE")
                  << " - " << result.message << std::endl;
    }
}
```

#### 升级 start()——打印一行启动日志

```cpp
void Poller::start() {
    if (running_) return;
    running_ = true;
    worker_thread_ = std::thread(&Poller::run, this);
    std::cout << "Poller started with strategy: "
              << strategy_->getConfigInfo() << std::endl;
}
```

> 🧠 **`std::thread(&Poller::run, this)` 怎么理解？**——成员函数指针 `&Poller::run` 调用时需要"对象 this"作为隐藏的第 0 个参数；`std::thread` 的可变参数构造把 `this` 作为第 2 个参数自动绑过去。等价于"在新线程里调 `this->run()`"。**任何要让成员函数跑在新线程的代码都是这个套路**。

#### 试跑一下

```cpp
auto action = []() -> TaskResult {
    return TaskResult(true, "hello", std::chrono::steady_clock::now());
};
Poller p(std::unique_ptr<IPollingStrategy>(
```

应该能看到 4 次 `Action: SUCCESS - hello`。**到这里"轮询"二字已经名副其实了**——但 stop 还要等 sleep 自然结束，最坏延迟 500ms，下一节解决。

### 7.3 用条件变量替代 sleep——让 stop 立即响应

`std::this_thread::sleep_for` 是"无脑硬睡"——一旦睡下，外部什么调用都打扰不了它。我们换成 `std::condition_variable::wait_until`：它和 sleep 一样能睡到指定时刻，但**任何 `notify` 都能立即把它叫醒**。

#### 升级 run()

```cpp
void Poller::run() {
    while (running_) {
        long next_interval_ns = 0;
        {
            std::unique_lock<std::mutex> lock(mutex_);
            next_interval_ns = strategy_->getNextInterval();
            auto wake_time = std::chrono::steady_clock::now()
                           + std::chrono::nanoseconds(next_interval_ns);
            // 等到 wake_time 或被 notify 唤醒
            cond_.wait_until(lock, wake_time);
            if (!running_) break;
        }   // ← 解锁再去执行任务，避免长时间持锁

        TaskResult result = action_();
        if (result.success) strategy_->recordSuccess();
        else                strategy_->recordFailure();

        std::cout << "Action: "
                  << (result.success ? "SUCCESS" : "FAILURE")
                  << " - " << result.message << std::endl;
    }
}
```

#### 升级 stop()——加 notify 唤醒等待中的主循环

```cpp
void Poller::stop() {
    if (!running_) return;
    {
        std::lock_guard<std::mutex> lock(mutex_);
        running_ = false;
    }
    cond_.notify_all();   // 立刻把还在 wait_until 的主循环叫醒
    if (worker_thread_.joinable()) {
        worker_thread_.join();
    }
    std::cout << "Poller stopped." << std::endl;
}
```

> 🧠 **为什么先解锁再 notify？**——被唤醒的线程会立即尝试拿锁；如果 notify 时主调线程还持锁，被唤醒线程拿不到、又得睡回去。**先放锁再 notify**，可以让被唤醒线程一次拿锁成功——这是教科书级的微优化。这里我们用 `{ ... }` 块的 RAII 析构自动解锁，再 notify，效果等价。

> 💡 **`worker_thread_.joinable()` 必须先判**——如果 `start()` 没调用过、`worker_thread_` 是默认构造（不持有线程），那么 `join()` 会抛 `std::system_error`。

#### 试跑

把 7.2 的测试代码原封不动跑一遍，stop 几乎瞬时返回。**这就是"可中断的等待"**——是工程化轮询器和"玩具版 sleep 循环"的本质区别。

### 7.4 加 pause/resume——可暂停继续

需求：用户希望临时让轮询器"歇一下"，不停止线程、不丢失策略状态，过会儿能"接着干"。这需要一个新的标志位 `paused_`。

#### 给 `Poller.h` 增量加成员和方法

```diff
  void start();
  void stop();
+ void pause();
+ void resume();

  private:
  ...
  std::atomic<bool> running_;
+ bool paused_;            // 注意：不是 atomic
  std::thread worker_thread_;
```

构造函数初始化列表里加 `paused_(false),`。

> 🧠 **为什么 `running_` 用 `atomic` 而 `paused_` 是普通 `bool`？**——`running_` 在 worker 线程的 `while (running_)` 处**无锁读**（不持 mutex_），必须原子化保证内存可见性；`paused_` 永远只在持有 `mutex_` 时被读写，普通 `bool` 即可。**根据"是否会在锁外被访问"区分原子性需求**——不要无脑全用 atomic，普通 bool 更省也更明确。

#### 实现 pause/resume

```cpp
void Poller::pause() {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        paused_ = true;
    }
    cond_.notify_all();   // 唤醒主循环让它再走一次状态检查
    std::cout << "Poller paused." << std::endl;
}

void Poller::resume() {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        paused_ = false;
    }
    cond_.notify_all();   // 唤醒"暂停 wait"
    std::cout << "Poller resumed." << std::endl;
}
```

#### 升级 run()——支持暂停分支

```cpp
void Poller::run() {
    while (running_) {
        {
            std::unique_lock<std::mutex> lock(mutex_);
            long next_interval_ns = strategy_->getNextInterval();
            auto wake_time = std::chrono::steady_clock::now()
                           + std::chrono::nanoseconds(next_interval_ns);
            cond_.wait_until(lock, wake_time);

            // 暂停时再睡一觉，直到 resume 或 stop
            if (paused_) {
                cond_.wait(lock, [this] { return !paused_ || !running_; });
                continue;     // ← 重新算下次间隔，不要复用旧 wake_time
            }
            if (!running_) break;
        }
        TaskResult result = action_();
        if (result.success) strategy_->recordSuccess();
        else                strategy_->recordFailure();
        // ... 输出日志省略
    }
}
```

> ⚠️ **暂停后必须 `continue` 重新算间隔，不能直接 `executeAction()`**——否则用户在 pause 状态下睡了 10 分钟，resume 那一瞬间会立刻执行任务，相当于丢了 10 分钟的间隔约束。`continue` 让循环回头重新调 `getNextInterval()`、重新算 `wake_time`，符合用户直觉。

> 🧠 **`cond_.wait(lock, predicate)` 的两参数版本**：等价于 `while (!predicate()) cond_.wait(lock);`——内置防虚假唤醒。**只要你能用一个 lambda 表达"等到什么条件成立才走"，就用两参数版本，比手写 while 更清晰**。

### 7.5 主循环完全体——绝对时刻 + 虚假唤醒防护

7.4 版本的 `run()` 还有一个**没有暴露但隐藏的 bug**：`cond_.wait_until` 可能因"虚假唤醒"提前返回——OS 实现细节、信号中断都可能让 wait 没等到时刻就醒。如果不重新检查时刻，就会变成"提前 N 毫秒就跑任务"。

#### 完全体 run()

```cpp
void Poller::run() {
    while (running_) {
        {
            std::unique_lock<std::mutex> lock(mutex_);
            // ① 锁内问策略要下次间隔（updateStrategy 也会改 strategy_，必须互斥）
            long next_interval_ns = strategy_->getNextInterval();

            // ② 计算"绝对唤醒时刻"
            auto now = std::chrono::steady_clock::now();
            auto wake_time = now + std::chrono::nanoseconds(next_interval_ns);

            // ③ 用 while 防虚假唤醒：只要还没到时刻、还在跑、没暂停，就继续等
            while (running_
                   && std::chrono::steady_clock::now() < wake_time
                   && !paused_) {
                cond_.wait_until(lock, wake_time);
            }

            // ④ 暂停分支：再睡一觉，直到 resume / stop
            if (paused_) {
                cond_.wait(lock, [this] { return !paused_ || !running_; });
                continue;
            }
            // ⑤ 停止分支
            if (!running_) break;
        }   // ← 解锁，避免 executeAction 长时间持锁
        // ⑥ 执行用户任务（下一节抽成 executeAction）
        TaskResult result = action_();
        std::lock_guard<std::mutex> lock(mutex_);
        if (result.success) strategy_->recordSuccess();
        else                strategy_->recordFailure();
    }
}
```

六个关键节点的设计意图（一张表收齐）：

| 编号 | 行为 | 为什么这么写 |
|------|------|-------------|
| ① | `getNextInterval()` 在锁内调 | `updateStrategy` 也要写 `strategy_`，必须互斥 |
| ② | 用绝对时刻 `wake_time = now + interval` | 比"相对时长"更稳——虚假唤醒时不会被错算成"再睡一整轮" |
| ③ | `while (... < wake_time && !paused_) wait_until` | 防**虚假唤醒**——`wait_until` 可能提前返回，必须重新检查 |
| ④ | 暂停时再 `wait` 一次 + `continue` | 暂停后必须重新算间隔，不复用旧 wake_time |
| ⑤ | 停止则 break | 让 `running_` 这个原子标志承担退出职责 |
| ⑥ | 跑任务时**不持锁** | 任务可能跑很久，持锁会卡住 `pause/stop/updateStrategy` |

> 🧠 **"虚假唤醒"是什么？**——`std::condition_variable::wait/wait_until` 可能在没有任何 `notify` 的情况下自己醒来——这是 POSIX/Windows 系统调用层的实现细节（信号中断、内核抢占等）。所以 **C++ 标准明确规定：所有 `wait` 都必须放在 `while (条件不满足)` 循环里**。这是 C++ 并发圣经里 100% 必背的规则，没有例外。

> 💡 **为什么 `executeAction` 后还要再加锁去 `recordSuccess/Failure`？**——因为 `strategy_` 可能在执行任务期间被 `updateStrategy` 替换了。锁内访问保证我们调到的总是"当前策略"。

### 7.6 updateStrategy——运行时热切换策略

策略模式最有价值的红利：**运行时换算法不用重启进程、不用改 Poller 一行代码**。

#### `Poller.h` 增量

```diff
  void pause();
  void resume();
+ void updateStrategy(std::unique_ptr<IPollingStrategy> new_strategy);
```

#### 实现

```cpp
void Poller::updateStrategy(std::unique_ptr<IPollingStrategy> new_strategy) {
    std::lock_guard<std::mutex> lock(mutex_);
    strategy_ = std::move(new_strategy);   // 旧策略被 unique_ptr 自动析构释放
    strategy_->reset();
    std::cout << "Strategy updated: "
              << strategy_->getConfigInfo() << std::endl;
}
```

> 🧠 **`strategy_ = std::move(new_strategy)` 这一行做了三件事**：① 旧 `FixedIntervalStrategy` 被 `unique_ptr` 析构释放（赋值时 `unique_ptr` 会先 delete 当前持有的对象，再接管新对象）；② 新策略接管所有权；③ 紧接着调 `reset()` 重置内部状态。**如果用裸指针 `IPollingStrategy* strategy_`，开发者必须手写 `delete strategy_;` 否则就是内存泄漏**——这是 RAII 让"运行时换零件"安全无忧的典型场景。

> ⚠️ **不要忘记 `reset()`**——比如旧策略是指数退避、当前 `current_ns` 已经膨胀到 4 秒了；新策略接管后如果不 reset，第一次取到的间隔可能就是新策略构造时的值（看具体实现）。统一 `reset()` 一下，调用方语义最清晰。

### 7.7 抽出 executeAction——异常隔离 v1

7.5 的 `run()` 里直接调 `action_()`——**用户任务一旦抛异常，整个 worker 线程就崩了**，进程触发 `std::terminate`。框架代码必须把"用户任务调用"包成一个独立函数，统一兜底。

#### `Poller.h` 增量

```diff
  private:
      void run();
+     void executeAction();
```

#### 实现 v1（先只做异常隔离，超时下一节加）

```cpp
void Poller::executeAction() {
    auto start_time = std::chrono::steady_clock::now();
    TaskResult result(false, "Unknown result",
                      std::chrono::steady_clock::now());
    try {
        result = action_();
    } catch (const std::exception& e) {
        result = TaskResult(false,
                            std::string("Exception: ") + e.what(),
                            std::chrono::steady_clock::now());
    } catch (...) {
        result = TaskResult(false, "Unknown exception",
                            std::chrono::steady_clock::now());
    }
    auto duration_ms = std::chrono::duration_cast<std::chrono::milliseconds>(
        std::chrono::steady_clock::now() - start_time).count();

    {
        std::lock_guard<std::mutex> lock(mutex_);
        if (result.success) strategy_->recordSuccess();
        else                strategy_->recordFailure();
    }
    std::cout << "Action executed in " << duration_ms << "ms. Result: "
              << (result.success ? "SUCCESS" : "FAILURE")
              << " - " << result.message << std::endl;
}
```

#### run() 调用点替换

把 7.5 中"⑥ 执行用户任务"那一段改成：

```cpp
        }   // ← 解锁
        executeAction();   // 替代原来的 action_() + 加锁回喂策略
```

> 💡 **`catch (...)` 一定要兜底**——`catch (const std::exception& e)` 只接派生自 `std::exception` 的；如果用户任务抛了 `int 42` 或自定义类型，会冒泡到线程顶部触发 `std::terminate`。**框架代码必须 `catch (...)` 兜底**，把任何形态的异常都转成"任务失败"的 `TaskResult`。

> 🧠 **为什么时间统计用 `start_time`/`duration_ms`？**——一来日志好读，二来"任务耗时"是排查"任务卡了"的关键指标。生产代码里这个值一般还会上报到监控系统里做 P99 分析。

### 7.8 给 executeAction 加超时控制 v2

需求：用户传进来的任务**可能永远卡住**（网络死锁、外部服务挂了……）。我们不能让一个任务把整个轮询线程拖死。

C++ 没有"中断线程"的安全 API，最务实的方案是：**用 `std::async` 起一个临时线程跑任务，主循环用 `future.wait_for` 设硬上限**——超时就记 "Task timed out" 但**任务实际还在后台跑完**（我们只是不等它）。

#### `Poller.h` 增量

```diff
  void updateStrategy(std::unique_ptr<IPollingStrategy> new_strategy);
+ void setTaskTimeout(long timeout, TimeUnit unit);

  private:
      ...
+     long task_timeout_ns_;       // 0 表示不开启超时
```

`Poller.cpp` 顶部 includes 加：

```cpp
#include <future>
#include "TimeConverter.h"
```

构造函数初始化列表里加 `task_timeout_ns_(0),`。

#### setTaskTimeout 实现

```cpp
void Poller::setTaskTimeout(long timeout, TimeUnit unit) {
    std::lock_guard<std::mutex> lock(mutex_);
    task_timeout_ns_ = TimeConverter::toNanoseconds(timeout, unit);
    std::cout << "Task timeout set to: "
              << task_timeout_ns_ << " ns" << std::endl;
}
```

#### executeAction v2——加上 try 的"超时分支"

把 7.7 中的 `result = action_();` 这一行替换为下面 if/else：

```cpp
    try {
        if (task_timeout_ns_ > 0) {
            // 带超时：开 async 任务 + wait_for
            std::future<TaskResult> fut = std::async(std::launch::async, action_);
            auto status = fut.wait_for(std::chrono::nanoseconds(task_timeout_ns_));
            if (status == std::future_status::ready) {
                result = fut.get();
            } else {
                result = TaskResult(false, "Task timed out",
                                    std::chrono::steady_clock::now());
                // ⚠️ 此处 fut 离开 try 块时其析构会等任务跑完——
                //   "超时"只是"我们不等了"，不是"杀掉任务"
            }
        } else {
            // 不带超时：同步直接调
            result = action_();
        }
    } catch (...) { /* 同 v1 */ }
```

> ⚠️ **`std::async + future.wait_for` 的"超时"是假超时**——只是主线程不等了，async 任务还在后台跑；`future` 析构时**会阻塞等待任务自然结束**（`std::launch::async` 创建的 future 析构语义就是 join）。**真正的"中断任务"在 C++ 标准里不存在**——只能任务函数内部主动检查取消标志（"协作式取消"）。

> 💡 **`task_timeout_ns_ == 0` 表示不开启超时**——这种"零值代表特殊语义"的写法，比起加一个 `bool enable_timeout_` 更精炼。但要在文档/注释里写明白，否则维护者会困惑。

### 7.9 收尾——triggerNow + printStatistics + Poller.h 终态

最后两个小方法和一个完整的 `Poller.h`。

#### triggerNow——手动让等待提前结束

```cpp
void Poller::triggerNow() {
    cond_.notify_all();   // 让主循环 wait_until 立刻醒来
}
```

> ⚠️ **当前实现并不是"立即额外执行一次"，只是"让本次等待提前结束"**——主循环醒来后还会按部就班检查 `running_/paused_`，只是"原本要睡 10 秒，现在 0 秒就跑任务"。如果你想要**真正的"另起一线程立即跑一次"语义**，应当直接 `std::async(action_)` 而不去打扰主循环——这是 10.3 节延伸挑战 B 的方向。

#### printStatistics——打印统计摘要

需要先给 `Poller.h` 加上 `TaskStatistics stats_;` 成员，并把 `mutex_` 标 `mutable`：

```diff
- std::mutex mutex_;
+ mutable std::mutex mutex_;
+ TaskStatistics stats_;
```

实现：

```cpp
void Poller::printStatistics() const {
    std::lock_guard<std::mutex> lock(mutex_);
    stats_.printSummary();
}
```

> 💡 **`mutable std::mutex mutex_` 的 `mutable` 是干嘛的？**——`mutable` 让这个成员**即使在 `const` 成员函数里也能被修改**。`printStatistics() const` 标了 const、但内部要 `lock_guard<mutex>` 加锁——加锁会修改 mutex 内部状态，没 `mutable` 编译报错。**任何"逻辑只读但需要内部加锁"的类，互斥量都得标 `mutable`**。

> 📌 **配套源码里这个函数当前是空实现**——因为示例代码里 `stats_` 还没接入 `executeAction` 的结果回填（`stats_.recordResult(result)` 这一行被略过了）。完整功能版需要在 `executeAction` 末尾加上这一行——这是 10.3 节延伸挑战 A 的内容。

#### Poller.h 终态——所有增量收齐

把 7.1～7.9 所有 `Poller.h` 增量合在一起就是最终版：

```cpp

#define POLLER_H

#include <memory>

public:
    typedef std::function<TaskResult()> ActionFunc;

        : strategy_(std::move(strategy)),
          action_(action),
          running_(false),
```

## 08.示例使用场景

### 8.1 示例任务函数

新建 `LooperTest.cpp`，先写一个"30% 失败率"的模拟任务函数（用静态计数器制造不确定性）：

```cpp
// LooperTest.cpp
#include <iostream>
#include <thread>
#include <chrono>

#include "Looper.h"             // 三种策略（FixedInterval / ExponentialBackoff / RandomInterval）
#include "IPollingStrategy.h"
#include "Poller.h"
#include "TaskStatistics.h"
#include "TimeConverter.h"
#include "TimeUnit.h"

int main(int argc, char* argv[]) {
    // 示例任务函数：模拟"30% 失败 + 不同耗时"
    auto sampleAction = []() -> TaskResult {
        static int counter = 0;
        counter++;

        if (counter % 10 < 3) {
            // 失败分支：sleep 150ms 模拟"慢失败"
            std::this_thread::sleep_for(std::chrono::milliseconds(150));
            return TaskResult(false,
                              "Simulated failure #" + std::to_string(counter),
                              std::chrono::steady_clock::now());
        }
        // 成功分支：sleep 50ms 模拟"快成功"
        std::this_thread::sleep_for(std::chrono::milliseconds(50));
        return TaskResult(true,
                          "Operation succeeded #" + std::to_string(counter),
                          std::chrono::steady_clock::now());
    };
```

> 🧠 **`auto sampleAction = []() -> TaskResult { ... };` 三个关键点**：
> 1. `auto`：让编译器推断 lambda 的类型（lambda 类型每个都不同、写不出来）
> 2. `[]`：空捕获列表，因为我们没用到外部变量
> 3. `-> TaskResult`：显式声明返回类型，让编译器把它转成 `std::function<TaskResult()>` 时不发生歧义

### 8.2 创建轮询器

```cpp
    // 创建轮询器：初始用固定间隔策略 1000ms
    Poller poller(
        std::unique_ptr<IPollingStrategy>(
            new FixedIntervalStrategy(1000, TimeUnit::MILLISECONDS)),
        sampleAction
    );

    // 设置任务超时：100ms
    // 因为我们的失败任务 sleep 150ms，所以失败任务都会被判超时
    poller.setTaskTimeout(100, TimeUnit::MILLISECONDS);
```

> 💡 **`std::unique_ptr<IPollingStrategy>(new FixedIntervalStrategy(...))` 是 C++11 写法**——C++14 起推荐 `std::make_unique<FixedIntervalStrategy>(1000, TimeUnit::MILLISECONDS)`，更短、更安全（避免 new 和 unique_ptr 之间出现异常时的内存泄漏）。本案例为兼容 `-std=c++11` 而用旧写法。

### 8.3 启动轮询器

```cpp
    poller.start();
```

启动后 `Poller` 内部 `worker_thread_` 立即开始干活：① 询问 `strategy_->getNextInterval()` 拿到 1s；② 在条件变量上等 1s（可被打断）；③ 调 `sampleAction()` 跑任务；④ 拿任务结果调 `recordSuccess` / `recordFailure`；⑤ 回到步骤①。**这就是"轮询"的本质——策略告诉它"下次什么时候醒"，任务函数告诉它"醒了干啥"，两者完全解耦**。

### 8.4 完整闭环测试

把 8.1～8.3 拼装成一个端到端的 main，**完整覆盖 7 大功能**——启动 / 暂停 / 继续 / 切换策略 / 手动触发 / 停止 / 统计：

```cpp
    // 8.4.1 跑 5 秒固定间隔
    std::this_thread::sleep_for(std::chrono::seconds(5));

    // 8.4.2 暂停 2 秒
    poller.pause();
    std::this_thread::sleep_for(std::chrono::seconds(2));

    // 8.4.3 继续 → 再跑 3 秒
    poller.resume();
    std::this_thread::sleep_for(std::chrono::seconds(3));

    // 8.4.4 切换到指数退避策略
    poller.updateStrategy(
        std::unique_ptr<IPollingStrategy>(
            new ExponentialBackoffStrategy(500, 5000, TimeUnit::MILLISECONDS)));

    // 8.4.5 再跑 8 秒，观察"失败 → 翻倍 → 成功 → 重置"过程

    // 8.4.6 手动立即触发一次
    std::cout << "Manually triggering task..." << std::endl;
    poller.triggerNow();
    std::this_thread::sleep_for(std::chrono::seconds(2));

    // 8.4.7 停止 + 打印统计
    poller.stop();
    poller.printStatistics();

    return 0;
}
```

#### 关键观察点（建议跟着输出对比代码理解）

1. **第 3、6、9 次任务必失败**——`counter % 10 < 3` 决定（counter 1-based，所以 #3 #13 #23... 失败；这里因为有效计数变化，实际可能是 #3、#6、#9 失败）
2. **失败任务的 `Action executed in` 总是 ≈ 100ms**——被 `task_timeout_ns_=100ms` 准时打断
3. **成功任务的 `Action executed in` 总是 ≈ 51ms**——`sleep_for(50ms)` + 函数调用开销
4. **暂停期间无任何 `Action executed` 输出**——`worker_thread_` 卡在 `cond_.wait` 上
5. **切换到指数退避后**：连续成功间隔仍是 500ms（`recordSuccess` 重置）；一遇失败下次翻倍到 1000ms
6. **`triggerNow` 之后会立即出现一次 `Action executed`**——被打断的等待提前结束

> 🧠 **`updateStrategy` 配合 `unique_ptr` 自动析构旧策略**：`strategy_ = std::move(new_strategy)` 这一行实际上做了三件事——① 旧的 `FixedIntervalStrategy` 被 unique_ptr 析构释放；② 新的 `ExponentialBackoffStrategy` 接管；③ 调用 `reset()` 重置内部状态。**这是 RAII 让"运行时换策略"变得安全的典型场景**。如果用裸指针 `IPollingStrategy* strategy_`，开发者必须手动 `delete` 旧的、否则就是内存泄漏。

> ⚠️ **`pause + resume` 期间任务执行计数不会清零**：`sampleAction` 里的 `static int counter` 是函数级静态变量，活到程序结束。所以 resume 后任务编号是 6、7、8 而不是从 1 重启——这其实是合理的：用户的"任务计数"应当和"策略生命周期"解耦。**如果你想让计数随策略重置，应当用一个外部的 `std::atomic<int>` 而非 `static`**。

## 09.核心组件说明

> 📌 本节是对全章的"知识地图"回顾——每个组件背后的设计原则比代码本身更值得记住。

### 9.1 时间系统

支持多种时间单位（纳秒到分钟）、精确的时间转换工具类——所有内部存储统一为纳秒，对外接口暴露 `TimeUnit` 枚举供调用方按业务需要选择。**这种"内部统一 + 接口多元"的模式，是写工具库的通用做法**：调用方写得舒服（用 `MILLISECONDS` 表达意图），框架内部算得准（ns 精度无截断）。

设计要点回顾：

- `enum class TimeUnit` 限定作用域、禁止隐式转 int
- `TimeConverter` 全静态成员（纯函数库）
- 数字字面量 `60000000000L` 加 `L` 后缀防溢出

### 9.2 轮询策略系统

抽象基类 `IPollingStrategy` + 三种内置实现（`FixedInterval` / `ExponentialBackoff` / `RandomInterval`）。**新增策略只需继承重写 5 个虚函数，无需改动 `Poller` 一行代码**——这就是开闭原则（OCP，Open-Closed Principle）的教科书示范："**对扩展开放，对修改封闭**"。

设计要点回顾：

- 虚析构函数 `virtual ~IPollingStrategy() {}` 防多态析构泄漏
- `= 0` 把虚函数变纯虚、把类变抽象类
- `override` 关键字防"重写失败"

### 9.3 任务统计系统

`TaskStatistics` 用 `std::deque<TaskResult>` 滚动存最近 100 条结果（`push_back + pop_front`），**既限制了内存占用、又保留了足够的近期信息**。这种"环形缓冲"思维在监控系统、日志收集器、分布式追踪里无处不在。

设计要点回顾：

- `steady_clock` 用于时间差计算、`system_clock` 用于墙钟显示
- 除法之前先判断分母非零防 `nan/inf`
- `std::deque` 是头尾 O(1) 的滚动窗口首选

### 9.4 核心轮询器功能

`Poller` 类封装了完整的生命周期：start / stop / pause / resume / updateStrategy / triggerNow / setTaskTimeout。每个公开方法都用 `std::lock_guard<std::mutex>` 保护共享状态——这是 [07 票务案例](./07.票务购买系统.md) 并发训练的延续。

设计要点回顾：

- `std::atomic<bool> running_` 无锁读、`bool paused_` 持锁读写——按访问模式区分
- `condition_variable + while-wait` 防虚假唤醒
- 析构 `~Poller() { stop(); }` 是 RAII 硬性要求

### 9.5 高级特性

- **任务超时监控**：`std::async + std::future::wait_for` 给每个任务设硬上限。注意这是"放弃等待"不是"杀死任务"
- **策略热切换**：运行时调 `updateStrategy` 即可换间隔策略，配合 `unique_ptr` 自动释放旧策略
- **手动触发**：`triggerNow` 通过 `cond_.notify_all()` 强制唤醒等待中的轮询线程，实现"立即结束等待"
- **异常隔离**：任务函数抛出的任何异常被 `try/catch (...)` 兜住，不会传到轮询线程导致进程崩溃

> 💡 **本案例已经具备生产级框架的雏形**：把它和 [09.简易的线程池](./09.简易的线程池.md) 组合，就是一个"定时任务调度器"——很多公司监控系统的内核就是这样搭出来的。

### 10.3 三个延伸挑战

**A（基础）· 接通统计 + 再写一种策略**

任务一：把 `Poller::executeAction` 末尾加一行 `stats_.recordResult(result);`、把 `printStatistics()` 里的注释取消，让最后的统计真正打出来。

任务二：实现一个 `LinearBackoffStrategy`——间隔从 `initial` 线性增长，每失败一次加 `step`，直到达到 `max` 后封顶。只需继承 `IPollingStrategy` 重写 5 个虚函数，整个框架不用改一行。**这就是开闭原则的威力**。

```cpp
class LinearBackoffStrategy : public IPollingStrategy {
public:
    LinearBackoffStrategy(long initial, long step, long max, TimeUnit unit);
    long getNextInterval() override {
        long result = current_ns;
        current_ns = std::min(current_ns + step_ns, max_ns);
        return result;
    }
    void recordSuccess() override { reset(); }
    // ... reset / recordFailure / getConfigInfo
private:
    const long initial_ns, step_ns, max_ns;
    long current_ns;
};
```

**B（进阶）· 并发多任务 + 真正的"立即触发"**

当前一个 `Poller` 只管一个任务、`triggerNow()` 也只是"提前结束等待"而不是"额外执行一次"。扩展为：

1. `Poller` 内部管 N 个独立任务，每个任务有自己的策略和开关：

   ```cpp
   struct Task {
       std::string name;
       std::function<TaskResult()> fn;
       std::unique_ptr<IPollingStrategy> strategy;
       std::atomic<bool> enabled;
   };
   ```

2. `triggerNow(taskName)` 直接 `std::async(task.fn)` 在另一个线程里跑一次，不打扰主循环
3. 用一个 `std::unordered_map<std::string, Task>` 索引任务，`addTask / removeTask / triggerNow(name)` 全部线程安全

**C（挑战）· C++20 现代化**

如果你的编译器支持 C++20：

- 把 `formatTime` 里"手写时间戳转字符串"替换为 `std::format("{:%H:%M:%S}", tp)`（配合 `<chrono>` + `<format>`）
- 把 `using ActionFunc = std::function<TaskResult()>` 加上 `concept` 约束：

  ```cpp
  template <typename F>
  concept ActionLike = std::invocable<F> &&
                       std::same_as<std::invoke_result_t<F>, TaskResult>;
  ```

- 用 `std::jthread` 替代 `std::thread`——`jthread` 析构会自动 `request_stop` + `join`，析构函数里那一行 `stop()` 都可以省掉

这是**现代 C++ 时间处理 + 类型约束 + 协作式取消的终极写法**。
