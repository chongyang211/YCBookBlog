# MiniNet 迷你网络栈 · 设计方案（Go 从 0 到 1 徒手造一台"会讲协议"的机器）

> **一句话定位**：从一个 `socketpair` 字节流开始，**15 个阶段 · 共 58 个 Step**，徒手造一台既是客户端又是服务端的迷你网络栈。把《网络协议原理》18 篇专栏的每一个知识点都在自己代码里落一遍：ARP → IP → TCP 状态机 → TLS → HTTP → 反代/缓存 → WebSocket → QUIC → 全链路可视化诊断。
>
> **本篇是顶层设计方案**（≈ 建筑总图纸）。所有阶段都展开到 **"写一点 → 编译 → 看输出 → 再写下一点"** 的 Step 粒度。具体一行行代码怎么敲，去 7 篇施工现场文档（§13 列表）。

## 00.从这里开始：这个案例值不值得做？

┌─ 👀 三分钟自检 ─────────────────────────────────────────┐
│ ① 你读完《网络协议原理》18 篇，仍然觉得"知道了"但"用不上"？ │
│ ② 你能画出 TCP 三次握手，但说不清"丢一个 SYN-ACK 系统到底发生什么"？ │
│ ③ 你能背 HTTPS 握手步骤，但没亲眼看过 ClientHello 的字节分布？ │
│ ④ 你会用 `wrk`/`curl`，但没自己写过 TCP 状态机，没亲手让一个包"丢"过？ │
└──────────────────────────────────────────────────────────┘

只要有一个 ✅，本案例就是给你的。学完之后你能：

- 拿到任何一次 curl 请求，说出它在 5 层协议栈里走了几跳
- 手写 `mnet-ping` / `mnet-dig` / `mnet-curl`，看着它们一个字节一个字节地离开自己的栈
- 亲手拉过 7 个"造 BUG"闸门（大小端反、子网掩码写反、丢包不重传、EPOLLET 漏读、缓存击穿、WS 心跳缺失、QUIC 迁移失败）

**⚠️ 请务必接受一件事**：这不是"照抄代码就完事"的项目。每一个阶段都有**必看的失败现场**——SYN 发出去没人回打脸状态机、TLS 版本不匹配、HPACK 动态表错位、QUIC 迁移因 NAT rebinding 失败。**跳过失败现场 = 白学**。

**每个 Step 必须做的三件事**：

> 1. **看 🎯 Step 目标**：明确这一小步做什么、不做什么、验收标准
> 2. **写一小段代码就 `make build` 一次**（Go 增量编译只需 1-2 秒）
> 3. **看到预期输出再进下一个 Step**（**绝不一口气抄完整段代码**）

**每个阶段的结构模板**（你在正文里会反复看到）：

```text
┌─ 🎯 阶段目标 ────────────────┐  ← 阶段开头：明确做什么/不做什么
│  完成什么、不做什么、验收标准    │
└─────────────────────────────┘

   灵魂三问（动手前先想清楚：为什么是这样的技术选型？）

   Step X.1：先写最小可编译版（10-30 行）
   Step X.2：make build && make test → 看到预期输出 ✅
   Step X.3：再加一个小功能（10-50 行）
   Step X.4：make build → >>> dump 看到新输出 ✅
   ...

┌─ 🧪 阶段运行验证 ───────────┐  ← 阶段结尾：完整命令 + 预期输出 + 排错
│  编译命令 / 预期输出 / 排错指南  │
└───────────────────────────────┘

┌─ 📌 阶段小结 ───────────────┐  ← 阶段结尾：今天学到了什么
│  ✅ 已掌握 / 🎁 新增文件 / 🔜 下一阶段 │
└──────────────────────────────┘
```

**⚠ 关于"造 BUG 高峰"**（本案例 7 处）：每处都严格遵循**五步法**，**绝不要跳过"先写有 bug 的版本"**：

> 1. **写一个有 bug 的最小可编译版**（故意的！）
> 2. **跑起来亲眼看到崩溃 / 慢速 / 错误输出**（Wireshark/pcap/日志里）
> 3. **用一句话说清为什么会这样**
> 4. **写修复版**
> 5. **benchmark 修复前后对比**（钉死数值）

跳过失败现场 = 白学。你以为"我看懂了"，但不走一遍"亲眼看到坏结果 → 修复 → 对比"的流程，三个月后面试被问就是答不出来。

### 一条命令跑起来（零权限）

```bash
cd mini_net
make build                        # 编译所有二进制(1-2 秒)
./bin/mnet                        # 交互式 REPL

>>> peer up                       # 启动一个"对端" mnet 进程

```

## 03.为什么这样选技术栈（选型论证）

### 3.1 为什么选 Go 而不是 C++/Rust？

| 维度 | Go | C++20 | Rust |
|------|----|-------|------|
| 跨 macOS/Linux | ✅ 一次编译 | ⚠️ 需条件编译 epoll/kqueue | ✅ |
| 协程 vs 多路复用 | ✅ 原生 goroutine | 需自己写 reactor | 需 async-std/tokio |
| 调试体验 | ✅ `dlv` + `pprof` | ✅ gdb + `perf` | ⚠️ `rust-gdb` 周边弱 |
| 网络库 | ✅ 标准库 `net` + `x/net` | ⚠️ asio/libuv 是重依赖 | ✅ tokio |
| 编译速度 | ✅ 1-2 秒增量 | ❌ 10-30 秒 | ⚠️ 5-15 秒 |
| 学习曲线 | ✅ 1 天上手 | ⚠️ 模板/所有权陡 | ⚠️ 借用检查陡 |
| 本案例代码量 | ~6000 行 | ~9000 行 | ~7500 行 |

**结论**：Go 的"**改一行代码 → 2 秒看到结果**"的闭环效率，是"**写一点编译一次**"节奏的决定性保障。缺点是 GC 偶尔会让 benchmark 略有噪声，§07/§15 的性能对比里用 `runtime.LockOSThread()` + 多次取中位数规避。

### 3.2 为什么要"双模运行"（可运行调试的核心设计）

**问题**：用户态 TCP 栈必须有一个"网卡接口"收发帧，但有三条路：

| 方案 | 优点 | 致命缺点 |
|------|------|----------|
| 真接管物理网卡 (`AF_PACKET`) | 最真实 | 必须 Linux + root + 可能把自己网络搞断 |
| tap/tun 虚拟网卡 (`utun`/`tap0`) | 真实感 90%，可 ping 外网 | **需 sudo**；macOS 要装 `tuntaposx` |
| **socketpair/pipe 回环对打** | **零权限、跨平台、CI 友好** | 不是"真"网络，但协议栈代码**一字不差** |

**本案例选"双模"**：

```text
┌─────────────────────────────────────────────────────────┐
│  mnet-A (goroutine)  ◄──── unix socketpair ────►  mnet-B│   ← loopback 模式（默认，0 权限）
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│  mnet (goroutine)    ◄──── tap/utun ────►  内核 TCP/IP   │   ← tap 模式（可选，sudo）
└─────────────────────────────────────────────────────────┘
```

关键是：**上层所有代码（IP/TCP/TLS/HTTP）零修改**。只有最底层 `pkg/link/` 换一个驱动。这个解耦让我们在 CI 里也能跑完整集成测试。**没有这个设计，就不存在"开箱即跑"**。

### 3.3 什么自己造 / 什么复用（教学 vs 工程取舍）

**自己造（教学核心，占 ~4500 行）**：

- 以太帧 / ARP / IPv4 / ICMP / UDP / TCP 的**完整编解码 + 状态机**
- TCP 握手挥手 11 态、滑动窗口、慢启动、快速重传、Nagle、SACK（简化版）
- DNS 递归解析器（根域名服务器 `a.root-servers.net` 可用公网真机测试）
- Reactor + epoll/kqueue（三种 IO 模型 benchmark 对比）
- HTTP/1.1 解析器 + 服务端 + 客户端
- 反向代理 + LRU 缓存 + 连接池
- WebSocket 帧解析 + 心跳 + 重连
- QUIC 多流 vs TCP 单流 的队头阻塞对比 demo

**复用（避免分心，占 ~1500 行胶水代码）**：

- `crypto/tls`：实际的 TLS 握手由标准库完成，**我们自己写 ClientHello/ServerHello 解析器**
- `quic-go`：实际 QUIC 由库完成，**我们自己写 StreamMux 对比演示**
- `encoding/binary`：大小端编解码
- `golang.org/x/sys/unix`：syscall 封装

**原则**：**与协议原理直接相关的代码一律自己写**，**纯胶水（密码学/平台 syscall）复用标准库**。你要学的是"TCP 怎么握手"，不是"RSA-OAEP 的位运算"。

## 04.可运行可调试：工程化五件套

**没有这五件套，就不叫"可运行可调试"的综合案例**。每一件都在 §10 的 Step 清单里会反复出现。

### 4.1 件 1：REPL + 单步执行

```text
>>> step on                       # 开启单步模式
>>> ping 10.0.0.2
[trace] L2 → tx eth frame type=0x0806 (ARP who-has 10.0.0.2)   [press enter]
[trace] L2 ← rx eth frame type=0x0806 (ARP is-at aa:bb:cc:...)  [press enter]
[trace] L3 → tx ip pkt proto=1 (ICMP echo-req id=1 seq=1)       [press enter]
[trace] L3 ← rx ip pkt proto=1 (ICMP echo-rep id=1 seq=1)
reply from 10.0.0.2: time=0.42ms
```

每个包的"离开"和"进入"都有 trace，`step on` 之后变成"**按一次 Enter 走一个事件**"——跟 gdb `next` 一样，但观察的是网络事件而不是 CPU 指令。

### 4.2 件 2：pcap 导出 + Wireshark 对照

每一帧流经 `pkg/link/` 时都会被 `pkg/pcap/writer.go` **原样复制一份**到环形缓冲，`>>> dump cap /tmp/x.pcap` 一键落盘：

```bash
wireshark /tmp/x.pcap             # 你写的 TCP 栈产生的流量,Wireshark 看
tshark -r /tmp/x.pcap -V          # 或者命令行
```

**教学意义**：Wireshark 的 `[TCP Retransmission]` 红色告警、`[TCP Dup ACK]` 黄色告警、Expert Info 的 Warning，会**无情地审判**你栈写得对不对。阶段 ⑦（TCP 滑窗）的 🔥BUG-3 就是靠 Wireshark 的红色标记来暴露的——比你自己打日志猜 bug 可靠 10 倍。

### 4.3 件 3：dlv 单步 + 配套 VSCode launch.json

`docs/vscode/launch.json`：

```json
{
  "configurations": [
    { "name": "mnet (loopback)",  "type": "go", "request": "launch",
      "program": "${workspaceFolder}/cmd/mnet", "args": ["--mode", "loopback"] },
    { "name": "mnet (tap, sudo)", "type": "go", "request": "launch",
      "program": "${workspaceFolder}/cmd/mnet",
      "args": ["--mode", "tap", "--tap", "utun7"],
      "asRoot": true },
    { "name": "test tcp state",   "type": "go", "request": "launch",
      "mode": "test", "program": "${workspaceFolder}/pkg/transport" }
  ]
}
```

命令行：

```bash
dlv debug ./cmd/mnet -- --mode loopback
(dlv) b pkg/transport/tcp_state.go:handleSyn
(dlv) c
# 对端 SYN 到达时触发断点, bt 看调用栈
```

### 4.4 件 4：结构化日志按五元组染色

```text
[t=12.345ms][L4][conn=10.0.0.1:5000→10.0.0.2:8080][state=SYN_SENT]
  TX SYN seq=0 win=65535
[t=12.890ms][L4][conn=10.0.0.1:5000→10.0.0.2:8080][state=SYN_SENT]
  RX SYN+ACK seq=0 ack=1 win=65535
[t=12.891ms][L4][conn=10.0.0.1:5000→10.0.0.2:8080][state=ESTABLISHED]
  TX ACK seq=1 ack=1
```

同一条连接自动染同一色（终端 ANSI），多条连接并发时眼睛不会花。阶段 ⑧（epoll 多连接）必备。

### 4.5 件 5：Makefile 一条命令都不用记

```makefile

make demo-ws     # 跑 demo 06: WebSocket 聊天室
make demo-shop   # 跑 demo 07: shop.html 端到端
```

## 09.七次"造 BUG → 修复"高峰全览

| # | 阶段 | 造什么 BUG | 打脸现场 | 修复方案 |
|---|------|----------|--------|--------|
| 1 | ③ 报文 | 用小端打包 IP 头 `total_len` | Wireshark 把 20 字节解析成 `0x1400=5120` | `BeU16` 封装 + 校验和自动跑 |
| 2 | ⑤ IP | 子网掩码写成 `/24`，路由当 `/16` | ping 同网段也走网关、RTT 翻倍 | 最长前缀匹配 + `route show` 命令 |
| 3 | ⑦ TCP | 关掉重传定时器 | 丢一个包就卡死，`cwnd` 永远不恢复，Wireshark 大片红 | RTO = `SRTT + 4·RTTVAR` + 快速重传 |
| 4 | ⑧ epoll | ET 模式只 `read` 一次 | 高并发时随机"消息吞一半"，表现为 HTTP 响应被截断 | 循环 read 到 `EAGAIN` |
| 5 | ⑬ 缓存 | 1000 个 key 同一秒过期 | 源站 QPS 瞬间 1000×，`bench/cache_bench_test.go` 把它钉死 | TTL 抖动 + singleflight |
| 6 | ⑭ WS | 不发 ping | 云厂 LB 60s 空闲就 RST，用户感知"消息收不到" | 30s 心跳 + 客户端指数退避重连 |

### 阶段 ⑮ QUIC 多流 vs TCP 队头阻塞 🔥 造 BUG 高峰 7（专栏 18）

┌─ 🎯 阶段 ⑮ 目标 ─────────────────────────────────────┐
│ 完成什么：quic-go demo + 自写 StreamMux（多 stream 跑同一 UDP conn）vs TCP 单连接多 request 对比 │
│ 造 BUG：QUIC client 换 wifi (5-tuple 变) 不做 conn_id 迁移 → 断流 │
│ 修复：path validation + conn_id 迁移                     │
│ 验收标准：`bench/quic_bench_test.go` 1% 丢包时 HTTP/3 vs HTTP/1.1 吞吐比 2× |
│ 预计耗时：1.5h · 4 Step                                │
└──────────────────────────────────────────────────────┘

**灵魂三问**：

❓ QUIC 为什么走 UDP？—— TCP 是内核态，演进慢；UDP 走用户态，QUIC 协议本身在应用层快速迭代。

❓ 什么叫"队头阻塞"？—— TCP 字节流有序，前面丢一个包，后面即使到了也不能上送（等重传）；QUIC 多 stream 彼此独立。

❓ Connection ID 和 5-tuple 的差别？—— 5-tuple = (srcIP,srcPort,dstIP,dstPort,proto)，一变就新连接；QUIC 用 conn_id 不依赖 5-tuple，手机 wifi→4G 不断线。

**Step 清单**：

| Step | 做什么 | 验收输出 |
|------|-------|---------|
| 15.1 | `pkg/quic/demo.go` 用 quic-go 做 echo server + 0-RTT | 复用票据第 2 次连接 0-RTT 成功 |
| 15.2 | 自写 StreamMux（3 stream in 1 UDP conn） vs TCP 3-request pipeline | 丢 1% 包时 QUIC 吞吐是 TCP 的 2×（因为 TCP 队头阻塞） |
| 15.3 | 🔥 BUG-7：模拟 NAT rebinding，源端口变 | QUIC 本该不断却断了 |
| 15.4 | 修复：path validation + conn_id 迁移 | 切换源端口后流继续，没有丢包 |

## 11.第一次编译失败速查（新手必读）

写代码过程中最容易卡住的 10 个坑，提前列出来：

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| 1 | `cannot find package "github.com/you/mini_net/pkg/common"` | `go.mod` 的 module 名和你 import 的不一致 | `cat go.mod` 第一行,import 必须和 module 对齐 |
| 2 | `undefined: syscall.EpollCreate1` 在 macOS 编译失败 | 没加 build tag | 文件名改成 `epoll_linux.go`,顶部 `//go:build linux` |
| 3 | `imported and not used` | Go 不允许未使用的 import | 删掉；或改用 `_` 空导入 |
| 4 | ARP 发出后对方收不到 | Loopback driver 两端 MAC 互填错 | 阶段 ④ Step 4.1 启动时 A 端用 MAC-A，B 端用 MAC-B |
| 5 | TCP 握手卡在 SYN_SENT | 对面没监听 / Loopback 字节丢了 | `>>> tcp show` 看状态；pcap 看 SYN 是否真出去 |
| 6 | Wireshark 报 `[Malformed Packet]` | 大小端错 / 长度字段错 | 回阶段 ③ 用 hexdump 对比正确样本 |
| 7 | `panic: concurrent map writes` | goroutine 共享 map 没加锁 | 用 `sync.Map` 或 `sync.RWMutex` |
| 8 | `make test` 过了但 demo 卡住 | 真实环境端口被占 | `lsof -i:8080` 看占用 |
| 9 | `dlv debug` 启动很慢 | Go 1.22 优化问题 | 加 `-gcflags="all=-N -l"` 禁优化 |
| 10 | pcap 用 Wireshark 打开说"文件损坏" | pcap 文件头没写对 | 阶段 ⑯ Step 16.4 参考 pcap_samples/ 下预录文件 |

**调试三招**（每个阶段都能用）：

- **招 1**：`--log=trace` 看所有层的 TRACE 日志
- **招 2**：`>>> dump` 看任意时刻的协议栈内部状态
- **招 3**：`dump cap` 导出 pcap 用 Wireshark 对照
