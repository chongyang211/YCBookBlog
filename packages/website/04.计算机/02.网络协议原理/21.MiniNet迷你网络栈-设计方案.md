# MiniNet 迷你网络栈 · 设计方案（Go 从 0 到 1 徒手造一台"会讲协议"的机器）

> **一句话定位**：从一个 `socketpair` 字节流开始，**15 个阶段**徒手造一台**既是客户端又是服务端**的迷你网络栈。把《网络协议原理》18 篇专栏的每一个知识点都在自己代码里落一遍：ARP → IP → TCP 状态机 → TLS → HTTP → 反代/缓存 → WebSocket → QUIC → 全链路可视化诊断。
>
> **本篇不是施工现场**，而是**顶层设计方案**：会说清楚技术选型、15 阶段拆解、7 次造 BUG 高峰、目录结构、代码规模预算、7 次会话切分、以及**可运行可调试**的工程化支撑。等你拍板之后，具体一行行怎么敲进去，去 `22.迷你Web栈mnet设计.md`（施工现场文档）。

## 00.从这里开始：这个案例值不值得做？

┌─ 👀 三分钟自检 ─────────────────────────────────────────┐
│ ① 你读完《网络协议原理》18 篇，仍然觉得"知道了"但"用不上"？ │
│ ② 你能画出 TCP 三次握手，但说不清"丢一个 SYN-ACK 系统到底发生什么"？ │
│ ③ 你能背 HTTPS 握手步骤，但没亲眼看过 ClientHello 的字节分布？ │
│ ④ 你会用 `wrk`/`curl`，但没自己写过 TCP 状态机，没亲手让一个包"丢"过？ │
└──────────────────────────────────────────────────────────┘

只要有一个 ✅，本案例就是给你的。学完之后你能：

- 拿到任何一次 curl 请求，说出它在 5 层协议栈里走了几跳（DNS → ARP → TCP SYN → TLS CH → HTTP → 响应 → 渲染）
- 手写 `mnet-ping` / `mnet-dig` / `mnet-curl`，看着它们一个字节一个字节地离开自己的栈
- 亲手拉过 7 个"造 BUG"闸门（大小端反、子网掩码写反、丢包不重传、EPOLLET 漏读、缓存击穿、WS 心跳缺失、QUIC 迁移失败），真正理解每一层**为什么长这样**

**⚠️ 请务必接受一件事**：这不是"照抄代码就完事"的项目。每一个阶段都有**必看的失败现场**——SYN 发出去没人回打脸状态机、`ioctl(TUNSETIFF)` 权限错误、TLS 版本不匹配、HPACK 动态表错位、QUIC 连接迁移因 NAT rebinding 失败。**跳过失败现场 = 白学**。

### 一条命令跑起来（零权限）

```bash
cd mini_net
make build                        # 编译所有二进制
./bin/mnet                        # 交互式 REPL

>>> mode loopback                 # 默认就是 loopback,无需 sudo
>>> peer up                       # 启动一个"对端" mnet 进程
>>> arp whois 10.0.0.2
>>> ping 10.0.0.2
>>> tcp connect 10.0.0.2:8080
>>> http get http://peer/index.html
>>> dump cap /tmp/mnet.pcap       # 导出 pcap, 用 Wireshark 打开
>>> quit
```

进阶（需要 sudo，用 tap 模式接管真实网卡）：

```bash
sudo ./bin/mnet --mode tap --tap utun7
>>> ping 8.8.8.8                  # 真实网络, 走你自己的 TCP/IP 栈
```

## 02.为什么这样选技术栈（选型论证）

### 2.1 为什么选 Go 而不是 C++/Rust？

| 维度 | Go | C++20 | Rust |
|------|----|-------|------|
| 跨 macOS/Linux | ✅ 一次编译 | ⚠️ 需处理 epoll/kqueue 条件编译 | ✅ |
| 协程 vs 多路复用 | ✅ 原生 goroutine | 需自己写 reactor | 需 async-std/tokio |
| 调试体验 | ✅ `dlv` + `pprof` | ✅ gdb + `perf` | ⚠️ `rust-gdb` 周边弱 |
| 网络库 | ✅ 标准库 `net` + `x/net` | ⚠️ asio/libuv 都是重依赖 | ✅ tokio |
| 学习曲线 | ✅ 1 天上手 | ⚠️ 模板/所有权/编译慢 | ⚠️ 借用检查陡 |
| 本案例代码量 | ~6000 行 | ~9000 行 | ~7500 行 |

**结论**：Go **开发/调试效率碾压**，网络原理的学习不会因语言本身"抢戏"。缺点是垃圾回收偶尔会让"精确计时的 benchmark"略有噪声，我们在 §07/§15 的性能对比里用 `runtime.LockOSThread()` + 多次取中位数规避。

### 2.2 为什么要"双模运行"（这是本案例可运行调试的核心设计）

**问题**：用户态 TCP 栈必须有一个"网卡接口"收发帧，但有三条路：

| 方案 | 优点 | 致命缺点 |
|------|------|----------|
| 真接管物理网卡 (`AF_PACKET`) | 最真实 | 必须 Linux + root + 可能把自己网络搞断 |
| tap/tun 虚拟网卡 (`utun`/`tap0`) | 真实感 90%，可 ping 外网 | **需 sudo**；macOS 还要额外安装 `tuntaposx` |
| **socketpair/pipe 回环对打** | **零权限、跨平台、CI 友好** | 不是"真"网络，但协议栈代码**一字不差** |

**本案例选"双模"**：

```text
┌─────────────────────────────────────────────────────────┐
│  mnet-A (goroutine)  ◄──── unix socketpair ────►  mnet-B│   ← loopback 模式（默认，0 权限）
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│  mnet (goroutine)    ◄──── tap/utun ────►  内核 TCP/IP   │   ← tap 模式（可选，sudo）
└─────────────────────────────────────────────────────────┘
```

关键是：**上层所有代码（IP/TCP/TLS/HTTP）零修改**。只有最底层 `pkg/link/` 换一个驱动。这解耦让我们在 CI 里也能跑完整集成测试。

### 2.3 什么自己造 / 什么复用

**自己造（教学核心）**：

- 以太帧 / ARP / IPv4 / ICMP / UDP / TCP 的**完整编解码 + 状态机**
- TCP 握手挥手 11 态、滑动窗口、慢启动、快速重传、Nagle、SACK（简化版）
- DNS 递归解析器（根域名服务器 `a.root-servers.net` 可用公网真机测试）
- Reactor + epoll/kqueue 多路复用（三种 IO 模型 benchmark 对比）
- HTTP/1.1 解析器 + 服务端 + 客户端
- 反向代理 + LRU 缓存 + 连接池
- WebSocket 帧解析 + 心跳 + 重连
- QUIC 多流 vs TCP 单流 的队头阻塞对比 demo

**复用（避免 1000 行密码学分心）**：

- `crypto/tls`：实际的 TLS 握手由标准库完成，**我们自己写 ClientHello/ServerHello 解析器**，教学可见
- `quic-go`：实际的 QUIC 连接由库完成，**我们自己写 StreamMux 对比演示**
- `encoding/binary`：大小端编解码
- `golang.org/x/sys/unix`：syscall 封装

## 03.可运行可调试：工程化三件套

### 3.1 组件 1：REPL + 单步

```text
>>> step on                       # 开启单步模式
>>> ping 10.0.0.2
[trace] L2 → tx eth frame type=0x0806 (ARP who-has 10.0.0.2)   [press enter]
[trace] L2 ← rx eth frame type=0x0806 (ARP is-at aa:bb:cc:...)  [press enter]
[trace] L3 → tx ip pkt proto=1 (ICMP echo-req id=1 seq=1)       [press enter]
[trace] L3 ← rx ip pkt proto=1 (ICMP echo-rep id=1 seq=1)
reply from 10.0.0.2: time=0.42ms
```

每一个包的"离开"和"进入"都有 trace，`step on` 之后变成"按一次 Enter 走一个事件"——跟 gdb `next` 一样，但观察的是网络事件而不是 CPU 指令。

### 3.2 组件 2：pcap 导出

每一帧流经 `pkg/link/` 时都会被 `pkg/pcap/writer.go` **原样复制一份**到环形缓冲，`>>> dump cap /tmp/x.pcap` 一键落盘。

```bash
# 你写的 TCP 栈产生的流量, 用 Wireshark 看
wireshark /tmp/x.pcap
# 或者命令行
tshark -r /tmp/x.pcap -V
```

这件事的**教学意义**：Wireshark 的红色/绿色/黄色染色、Expert Info 的"Retransmission"告警，会**无情地审判**你栈写得对不对。阶段 ⑦（TCP 滑窗）的造 BUG 就是靠 Wireshark 的 `[TCP Retransmission]` 标记来暴露的。

### 3.3 组件 3：dlv 单步 + 配套 launch.json

`docs/vscode/launch.json`：

```json
{
  "configurations": [
    { "name": "mnet (loopback)",  "type": "go", "request": "launch",
      "program": "${workspaceFolder}/cmd/mnet", "args": ["--mode", "loopback"] },
    { "name": "mnet (tap, sudo)", "type": "go", "request": "launch",
      "program": "${workspaceFolder}/cmd/mnet",
      "args": ["--mode", "tap", "--tap", "utun7"],
      "asRoot": true }
  ]
}
```

命令行：

```bash
dlv debug ./cmd/mnet -- --mode loopback
(dlv) b pkg/transport/tcp_state.go:handleSyn
(dlv) c
# 对端 SYN 到达时触发断点
```

### 3.4 组件 4：结构化日志按五元组染色

```text
[t=12.345ms][L4][conn=10.0.0.1:5000→10.0.0.2:8080][state=SYN_SENT]
  TX SYN seq=0 win=65535
[t=12.890ms][L4][conn=10.0.0.1:5000→10.0.0.2:8080][state=SYN_SENT]
  RX SYN+ACK seq=0 ack=1 win=65535
[t=12.891ms][L4][conn=10.0.0.1:5000→10.0.0.2:8080][state=ESTABLISHED]
  TX ACK seq=1 ack=1
```

同一条连接自动染同一色（终端 ANSI），多条连接并发时眼睛不会花。

### 3.5 组件 5：make targets 一条命令都不用记

```makefile
make build       # 编译所有二进制 → bin/
make test        # 跑单元测试
make demo-ping   # 跑 demo 01: ARP + ICMP
make demo-tcp    # 跑 demo 02: TCP 握手挥手, 自动生成 pcap
make demo-http   # 跑 demo 03: HTTP GET 全链路
make demo-tls    # 跑 demo 04: TLS 握手可视化
make demo-ws     # 跑 demo 06: WebSocket 聊天室
make demo-shop   # 跑 demo 07: shop.html 端到端
make bench       # 跑所有 benchmark (缓存命中/epoll vs 阻塞 等)
make trace       # 开 TRACE 日志跑 shop demo, 输出到 /tmp/mnet-trace.log
make pcap        # 跑所有 demo, 把 pcap 落到 /tmp/mnet-*.pcap
make clean
```

## 07.七次"造 BUG → 修复"高峰全览

| # | 阶段 | 造什么 BUG | 打脸现场 | 修复方案 |
|---|------|----------|--------|--------|
| 1 | ③ 报文 | 用小端打包 IP 头的 `total_len` | Wireshark 把 20 字节解析成 `0x1400=5120` | `BeU16` 封装 + 校验和自动跑 |
| 2 | ⑤ IP | 子网掩码写成 `/24`,路由当 `/16` | ping 同网段也走网关、RTT 翻倍 | 最长前缀匹配 + `route show` 命令 |
| 3 | ⑦ TCP | 关掉重传定时器 | 丢一个包就卡死，`cwnd` 永远不恢复，Wireshark 大片红 | RTO = `SRTT + 4·RTTVAR` + 快速重传 |
| 4 | ⑧ epoll | ET 模式只 `read` 一次 | 高并发时随机"消息吞一半"，表现为 HTTP 响应被截断 | 循环 read 到 `EAGAIN` |
| 5 | ⑬ 缓存 | 1000 个 key 同一秒过期 | 源站 QPS 瞬间 1000×，`bench/cache_bench_test.go` 把它钉死 | TTL 抖动 + singleflight |
| 6 | ⑭ WS | 不发 ping | 云厂 LB 60s 空闲就 RST，用户感知"消息收不到" | 30s 心跳 + 客户端指数退避重连 |
| 7 | ⑮ QUIC | 换 wifi 5-tuple 变了 | TCP 必断（4 层连接定义变了），QUIC 本该不断 | `conn_id` 迁移 + 路径验证 |

> 每个高峰都严格遵循 **"先写有 bug 的最小可编译版 → 亲眼看到崩溃/慢速 → 一句话解释 → 写修复版 → benchmark 打脸对比"** 五步法。

3. **不实现 QUIC 核心**——阶段 ⑮ 用 `quic-go`，但自写 StreamMux 对比
4. **tap 模式仅在 Linux/macOS 测试**，Windows 需要 WSL
5. **性能不是目标**——goroutine 调度 + GC 导致 QPS 比 Nginx 低一个数量级，教学项目不追
6. **不实现 TCP SACK 的完整版**——只做简化版 (3 个重复 ACK 快速重传)
7. **DNS 不实现 DNSSEC / DoH / DoT**——只做明文 UDP:53
