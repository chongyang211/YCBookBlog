## 13.综合案例电商引擎

本篇是「面向对象设计」专栏的**毕业设计案例**：从一段 250 行、17 处坏味道、3 个真实 bug 的双 11 屎山出发，经过 **8 个版本（V0→V7）** 的演化，把它救成一个 **5 上下文 + 领域事件 + 面向接口** 的 DDD 工程。**从零到一亲手做完全部版本，49 个测试全绿**，把整个专栏 12 篇的内功变成肌肉记忆。

**学习方式**：本案例**篇幅较长**（约 16-20 小时），建议**分 5 次会话**，每次 1.5-2 小时，每次会话独立可验收。**绝不要一口气看完**——每一版都是上一版的"自然演化"，跳读会漏掉最关键的"为什么要改"。如果说前 12 篇是"过单元考试"，本篇就是"毕业答辩"：它检验你能不能把封装、多态、组合、SOLID、重构、可测试性、DDD **协同**起来，而不只是会用单点。

> 配套代码：`code/Programming/PaySystem`（纯 JDK 17，无 Maven，一键 `./build.sh && ./run.sh v0..v7`）。
>
> 全程仿照 [《C++ 迷你 KV 存储引擎》](/pages/97f31a/) 的"**5 次会话 + 灵魂三问 + 造 BUG 修复**"教学骨架：先看见病，再开药方，每一步都有可运行的验收。

⚠️ **本案例的五处"造 BUG → 修复"高峰**（亲手制造、亲眼看见、亲手修好）：

> - **会话 1**：V0 屎山原景重现——250 行里数出 17 处坏味道、3 个真实 bug（满减顺序 / 重复打折 / 时间不可控）；
> - **会话 2 · V1 前**：`balance -= pay` 直写全局变量 → 余额扣成负数，账不平；
> - **会话 2 · V3 前**：`VirtualCourse extends PhysicalProduct` → 被迫实现无意义的 `ship()`（企鹅会飞）；
> - **会话 4 · V6 前**：`new Date().getHours()` 判秒杀 → 测试只能等到晚上 8 点跑；
> - **会话 5 · V7 前**：结算方法里 `new SmsClient().send()` → 加"发票"需求就得改结算代码。
>
> 五次"踩坑→修复"，让你真正记住**封装 / 组合 / 依赖注入 / 领域事件**为什么存在。

## PayFlow 技术全景

### 技术栈分层详解

| 技术层级 | 对应专栏知识点 | 在 PayFlow 中的具体实现 |
|---------|-------------|---------------------|
| **语言特性层** | 封装、多态、继承 | Wallet 聚合、VipPolicy 多态族、值对象 |
| **结构层** | 接口 vs 抽象类、面向接口 | BillingNotifier 双层范式、PaymentChannel + 装饰器 |
| **组合层** | 组合优于继承 | Product 能力接口 + Builder 装配 |
| **原则层** | SOLID 五原则 | SettlementEngine + PromotionStep SPI（9 步链） |
| **重构层** | 坏味道、重构十二式 | 特征化测试锁定 V0、挖出 3 个 bug |
| **可测层** | 可测试性设计 | Clock 抽象注入、秒杀测试 26ms |
| **架构层** | DDD 战术建模 | Order 聚合根、领域事件、EventBus、五上下文 |

### 为什么是毕业设计

1. **完整性**：12 篇博客的 50+ 个知识点全部落地，无一处"为凑覆盖而覆盖"——订单结算这个业务**天然需要它们全部**；
2. **首尾闭环**：第 01 篇凌晨 1 点告警的"重复打折 bug"，在本篇 V5 特征化测试里被亲手挖出，同一段代码走完全专栏；
3. **递进性**：V0→V7 每版只解决一类问题，每 30 秒可跑、可验收；
4. **可回收**：12 篇留下的 11 段半成品代码（`OrderUtil.calc` / `Account.transfer` / `MyLogger` / `OSSClient` / `Dragon` / `OrderManager` 上帝类……）在 PayFlow 里各得其所、继续演化（见 §12 映射表）；
5. **工程化**：含异常体系、审计轨迹、事件总线、自建测试工具等工程必备要素。

### 项目目录结构

本案例**直接采用工程级多包结构**，一个版本一个包、层层递进。这样做的好处有三：

1. **版本—包名一一对应**：你按会话读到哪，就打开对应的包跟着写，不会迷路；
2. **职责单一、依赖单向**：`v7 → v6/v4 → shared`，高层版本复用低层版本的产物，从上到下层次清晰；
3. **随时对照**：想看"屎山长什么样"，打开 `v0shipan`；想看"终局长什么样"，打开 `v7ddd`——**两个包可以在 IDE 里并排打开对比**，这是本案例最推荐的学习姿势。

### 一条命令编译运行

```bash
cd code/Programming/PaySystem
./build.sh           # 编译全部 76 个源文件 → build/
./run.sh v0          # 屎山演示
./run.sh v1 .. v7    # 任意版本 demo + 测试
./run.sh test-all    # 49 个测试全量回归
```

⚠️ **`build.sh` 用了 `--release 17`**：保证即使你装了 JDK 21 也能按 17 的语义编译。如果你本机 JDK < 17，`java --version` 先确认。

## 01.需求说明：为什么是订单结算

### 1.1 业务场景

电商订单结算是后端世界最经典的"规则叠加"场景：

- 商品有小计、阶梯满减、限时秒杀、优惠券、会员折扣、运费、跨境税、积分抵扣……**每一层单看都不复杂，叠加就是雪崩**；
- 结算完还要扣钱包、发通知、开发票、发积分、对账——**一个动作触发一串下游**；
- 营销规则**每周都在加**：今天生日礼金、明天直播间折扣、后天黑五直降——**变化是常态**。

这恰好是面向对象设计的主场：**封装**守住钱、**多态**消灭分支、**组合**装配能力、**SOLID** 预留扩展点、**重构**救活屎山、**可测试性**让秒杀不再等半夜、**DDD** 让代码跟业务说同一种话。

> 我们不是为了"凑覆盖"才做订单，而是订单结算这个题目**天然需要这 12 篇的全部技术**，做一遍刚好把它们用对位置。

### 1.2 订单闭环与九层结算规则

订单闭环：**下单 → 结算 → 扣款 → 通知 → 事件下发（发票/积分/风控/对账）**。

**九层结算规则**（V0 里全部糊在一个函数，V4 拆成 9 个 Step）：

```text
Step 1: 小计       = Σ(单价 × 数量)
Step 2: 满减       - 阶梯满减（满 1000 减 250 / 满 500 减 100 / 满 300 减 50）
Step 3: 秒杀折扣   × 20:00-22:00 打 8 折     ← Clock 硬刚需
Step 4: 优惠券     - 券面值（有门槛：C10 满100 / C30 满300 / C50 满500）
Step 5: 会员折扣   × 铂金 85% / 黄金 90% / 白银 95%
Step 6: 运费       + 满 99 包邮，否则 12~15 元
Step 7: 跨境税     + 11.9%
Step 8: 积分抵扣   - 100 积分 = 1 元（不能抵成负数）
Step 9: 最低兜底   ≥ 0.01
```

**V0 就是把九层规则 + 扣款 + 短信 + 小票，全部塞进一个 `calculate()` 静态方法**——第 01 篇"复杂度持续叠加"的现场标本。

### 灵魂三问：地基两件套

❓ **既然教学场景可以 `double` 算钱，为什么要先写 Money？**

来看反例：

```java
// ❌ 反例：double 算钱
double total = 0;
for (double p : prices) total += p * 0.85;   // 0.1 + 0.2 != 0.3
System.out.println(total);                    // 382.49999999999994
```

**问题**：
1. 二进制浮点**无法精确表示** 0.1、0.85 这类十进制小数，误差随运算链累积；
2. 双 11 少收几百万的事故，元凶之一就是它；
3. `double` 没有业务语义——`99.5` 是元？是折后价？还是运费？编译器不知道，只有写注释的人知道，而注释会过时。

✅ **正确做法**：**以"分"为单位用 `long` 存储**的不可变值对象。整数运算无精度问题，类型本身携带语义（`Money` 就知道自己是钱）。

❓ **不用 JUnit，自己写测试工具不是重复造轮子吗？**

教学场景有三个考量：
1. **零依赖**：下载 jar 包、配 classpath 会把注意力从"面向对象"转移到"工程配置"；
2. **testkit 本身就是教材**：`Assert.throwsException` 里藏着"可测试性设计"的思想（异常即断言素材），写一遍胜过用百遍；
3. **API 完全对齐 JUnit 风格**（`assertEquals` → `Assert.equals`），你以后切到 JUnit 零成本。

❓ **Money 的构造器为什么是 private，却提供两个静态工厂？**

```java
private Money(long cents) { ... }               // 私有构造
public static Money ofYuan(double yuan) { ... }  // 从"元"创建（内部转分）
public static Money ofCents(long cents) { ... }  // 从"分"创建（直接用）
```

**工厂的意义是表达意图**：调用方写 `Money.ofYuan(99.9)` 一眼可知单位是元；如果只有一个 `new Money(9990)`，鬼知道 9990 是分还是元。**构造器只能表达类型，工厂能表达语义**——这是第 02 篇"意图方法"思想在创建场景的应用。

### Step 0.1 Money 值对象

> 📁 **归属文件**：`src/com/yc/payflow/shared/Money.java`

```java
public final class Money implements Comparable<Money> {
    public static final Money ZERO = new Money(0);

    private final long cents; // 以"分"为最小单位

    private Money(long cents) { this.cents = cents; }

    public static Money ofYuan(double yuan) {
        return new Money(Math.round(yuan * 100));   // 四舍五入到分
    }

    public static Money ofCents(long cents) {
        return new Money(cents);
    }

    // ---- 业务意义的运算（不是裸的加减乘除） ----
    public Money plus(Money other)      { return new Money(this.cents + other.cents); }
    public Money minus(Money other)     { return new Money(this.cents - other.cents); }
    public Money multiply(double factor){ return new Money(Math.round(this.cents * factor)); }

    /** 按比例打折。例如 percentOff(15) 表示打 85 折。 */
    public Money percentOff(double percent) { return this.multiply(1.0 - percent / 100.0); }

    /** 取两者较大。用于最低消费兜底。 */
    public Money max(Money other) { return this.cents >= other.cents ? this : other; }
    /** 取两者较小。用于优惠抵扣兜底（抵扣不能超过金额）。 */
    public Money min(Money other) { return this.cents <= other.cents ? this : other; }

    // ---- 谓词 ----
    public boolean isNegative()          { return cents < 0; }
    public boolean isPositive()          { return cents > 0; }
    public boolean isZero()              { return cents == 0; }
    public boolean greaterThan(Money o)  { return this.cents > o.cents; }
    public boolean greaterOrEqual(Money o){ return this.cents >= o.cents; }

    public long cents()    { return cents; }
    public double toYuan() { return cents / 100.0; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money)) return false;
        return cents == ((Money) o).cents;          // 相等基于内容
    }
    @Override
    public int hashCode() { return Objects.hash(cents); }

    @Override
    public String toString() { return String.format("¥%.2f", cents / 100.0); }
}
```

**五个设计要点**（对照第 11 篇"值对象"四特征）：

1. **不可变**：`final class` + `final` 字段 + 无 setter——所有运算返回新对象，多线程随便共享；
2. **相等基于内容**：`equals/hashCode` 基于 `cents`，`Money.ofYuan(1)` 和 `Money.ofCents(100)` 相等；
3. **单位升维**：`long cents` 从根上消灭浮点误差；
4. **业务方法**：`percentOff(15)`（打 85 折）、`max/min`（兜底）——调用方读的是**业务语言**，不是数学语言；
5. **`max/min` 为何重要**：第 09 篇"积分为 0 抵扣"规则在 V4 的 `PointsStep` 里一行 `total.min(deduction)` 就实现了兜底。

> ⚠️ **V0 故意不用 Money**：`v0shipan` 包里保留 `double`——**事故现场要原汁原味**，否则 V5 的对比测试就没有"精度陷阱"可挖了。

### Step 0.2 testkit 三件套

> 📁 **归属文件**：`src/com/yc/payflow/shared/testkit/`

**① Executable——测试体**（函数式接口，一个方法 3 行）：

```java
@FunctionalInterface
public interface Executable {
    void execute() throws Throwable;
}
```

**② Assert——5 种断言**：

```java
public final class Assert {
    private Assert() {}

    public static void equals(Object expected, Object actual, String hint) {
        if (!Objects.equals(expected, actual)) {
            throw new AssertionError(
                "断言失败：" + hint + " | 期望=" + expected + " | 实际=" + actual);
        }
    }

    public static void trueThat(boolean condition, String hint) {
        if (!condition) throw new AssertionError("断言失败：" + hint);
    }

    public static void notNull(Object obj, String hint) { /* 同理 */ }

    /** 异常断言：期望动作抛出指定异常，并返回该异常供进一步检查 */
    public static <E extends Throwable> E throwsException(Class<E> expected, Executable action) {
        try {
            action.execute();
        } catch (Throwable t) {
            if (expected.isInstance(t)) return expected.cast(t);
            throw new AssertionError("断言失败：期望抛 " + expected.getSimpleName()
                + " 实际抛 " + t.getClass().getSimpleName() + " : " + t.getMessage());
        }
        throw new AssertionError("断言失败：期望抛 " + expected.getSimpleName() + "，但未抛出任何异常");
    }
}
```

📚 **`throwsException` 是可测试性的灵魂**：第 02 篇说过"**守卫的最好测试就是看它拒绝什么**"。V1 的"超额扣款抛异常且余额不变"用例，全靠这个断言。

**③ TestRunner——套件运行器**：

```java
public final class TestRunner {
    private final String suiteName;
    private final List<Case> cases = new ArrayList<>();

    public TestRunner(String suiteName) { this.suiteName = suiteName; }

    public TestRunner test(String name, Executable body) {
        cases.add(new Case(name, body));
        return this;                                   // 链式注册
    }

    public void run() {
        System.out.println("[TEST SUITE] " + suiteName);
        int pass = 0, fail = 0;
        long start = System.currentTimeMillis();
        for (Case c : cases) {
            try {
                c.body.execute();
                System.out.println("  ✓ " + c.name);
                pass++;
            } catch (Throwable t) {                    // 一个用例挂了不影响后面的
                System.out.println("  ✗ " + c.name);
                System.out.println("      " + t.getMessage());
                fail++;
            }
        }
        System.out.println(String.format("[结果] %d 通过 / %d 失败 / %dms",
            pass, fail, System.currentTimeMillis() - start));
        if (fail > 0) System.exit(1);                  // 退出码供 CI 判定
    }
}
```

### 灵魂三问：V0 屎山现场

❓ **为什么金额不能用 `double`？**

试算 `0.1 + 0.2` 你就明白——结果是 `0.30000000000000004`。V0 用 double 是双 11 少收几百万的元凶之一；V1 起统一换 `Money`（以分为单位存储）。**但 V0 我们故意保留 double**——事故现场要原汁原味，V5 的对比测试才有东西可挖。

❓ **`static WALLET_BALANCE` 有什么问题？**

三点：
1. **不可测**：上一个测试改了余额，下一个测试就被污染——测试之间必须知道彼此的存在，这叫"隐式耦合"；
2. **并发不安全**：两个线程同时 `-= amount`，一个覆盖另一个，钱就这么没了；
3. **不变量无人守**：任何代码都能写 `WALLET_BALANCE = -999`，扣成负数没有任何人拦。

V1 会用 `Wallet` 类的 `withdraw()` 意图方法把这三点一起治好。

❓ **`if (city.equals("北京"))` 为什么是坏味道？**

**基本类型偏执 + 散弹式修改**：城市是个概念，却被降级成字符串；新增"天津配送 13 元"要找出所有出现城市判断的地方逐个改——改漏一处就是 bug。多态族 + 数据驱动的注册表（V1 的 `VipPolicies`）就是这类问题的通解。

### 灵魂三问：V1 封装 + 多态

❓ **`balance -= amount` 直接写在调用方为什么错？**

因为**不变量无人守**。"余额不能为负"是钱包的天然约束，但写在调用方意味着**每个调用点都要自己记得校验**——写漏一处就扣成负数。封装的本质是：**不变量跟数据住在一起**，谁也别想绕过。

❓ **五个字段全 public 的类是 OOP 吗？**

**伪 OOP**。它只是"披着类外衣的结构体"：有类型名，没有行为；有字段，没有约束。判断标准很简单——**删掉所有方法，这个类还能正常工作吗？** 能，说明方法都是摆设。

❓ **消灭 switch 的关键动作是什么？**

**让"是什么"自己回答"怎么办"**。`vipLevel == 3` 是在问"你是什么"，然后调用方替它决定"打 85 折"；多态的做法是把"打几折"挪进每个等级自己的类里——调用方只说 `policy.applyDiscount(money)`，**问都不问你是谁**。以后加"钻石会员"，调用方一行不改。

### Step 2.1 先造 BUG：直写余额

按本案例的教学传统，先亲手踩坑。看这段"看起来没问题"的代码：

```java
// ❌ 反例：V0 的扣款方式

// 某个业务方法里：
```

**三个灾难**：
1. **不变量失守**：余额 `¥100` 扣 `¥150`，得到 `-50`——账不平，财务对账炸锅；
2. **测试互相污染**：上个测试把全局余额扣到 30，下个测试期望 100——**单测通过与否取决于执行顺序**；
3. **并发覆盖**：两个请求同时读 `100`、各扣 80，写回时后写的覆盖先写的——20 元凭空蒸发。

✅ 这个 BUG 不需要单独的复现工程——它就是 V0 的 `WALLET_BALANCE = WALLET_BALANCE - total`（第 156 行）。**下一小节的 Wallet 就是它的修复**。

### Step 2.2 Wallet 四动作：真封装的分水岭

> 📁 **归属文件**：`src/com/yc/payflow/v1feature/Wallet.java`

```java
public class Wallet {
    private Money balance;                          // ① 字段私有

    public Wallet(Money initial) {                  // ② 构造时校验
        if (initial == null || initial.isNegative()) {
            throw new IllegalArgumentException("初始余额不能为负: " + initial);
        }
        this.balance = initial;
    }

    /**
     * 扣款——业务意图方法（不是步骤方法）。
     * 【不变量守卫】金额为正 + 余额充足
     * 【原子性】判断 + 修改在同一方法内完成，不给调用方可乘之机
     */
    public void withdraw(Money amount) {
        if (amount == null || !amount.isPositive()) {
            throw new IllegalArgumentException("扣款金额必须为正: " + amount);
        }
        if (amount.greaterThan(balance)) {
            throw new InsufficientFundsException(
                "余额不足：需要 " + amount + "，当前 " + balance);
        }
        this.balance = balance.minus(amount);
    }

    public void refund(Money amount)  { /* 校验为正 → balance.plus */ }
    public void deposit(Money amount) { /* 校验为正 → balance.plus */ }

    public Money balance() { return balance; }      // 只读访问器（无 setter！）
}
```

**四个动作**（第 02 篇"真封装"的定义，逐条对上）：

| 动作 | 代码位置 | 治好 V0 的什么 |
|---|---|---|
| ① 字段私有 | `private Money balance` | 坏味道 15（直改全局） |
| ② 构造校验 | `if (initial.isNegative()) throw` | 非法状态从门口拒之 |
| ③ 意图方法 | `withdraw/refund/deposit` 而非 `setBalance` | 调用方读的是业务语言 |
| ④ 不变量强守 | `amount.greaterThan(balance)` → 抛异常 | 余额永不为负 |

📚 **意图方法 vs 步骤方法**（第 02 篇核心概念）：

> - `setBalance(newBalance)` 是**步骤方法**——暴露"怎么改"，调用方自己负责算出正确的新值；
> - `withdraw(amount)` 是**意图方法**——表达"干什么"，怎么保证不出错是类自己的事。
>
> **判断标准：方法名是动词短语（业务动作）还是 setXxx（技术操作）**。

💡 **为什么用自定义异常而不是 RuntimeException**：`InsufficientFundsException` 这个名字本身就是文档——调用方 catch 它的时候，不需要读注释就知道发生了什么。第 07 篇的"异常体系"原则：**用类型说话**。

### Step 2.4 VipPolicies 注册表：数据驱动

```java
        REGISTRY.put(0, new NormalVipPolicy());
        REGISTRY.put(1, new SilverVipPolicy());
```

### 灵魂三问：V2 双层范式

❓ **通知（短信/推送/邮件）用继承还是接口？**

先问"通道之间的关系是什么"——它们**互不替代**（短信不替换推送），但**共享流程**（校验→黑名单→拼文案→发送→记日志）。答案立即清晰：
- **is-a（可替换）**→ 接口；
- **共享流程骨架**→ 抽象类模板方法。
**两个都要，各干各的**——这就是"双层范式"。

❓ **只用接口 + default 方法为什么不行？**

接口不能有实例字段。**黑名单 `Set<String>` 存哪？** default 方法是无状态的，要么每个实现类自己抄一份黑名单（三处重复代码），要么用外部 Map（又回到全局状态）。**"需要共享状态 + 共享流程"的场景，抽象类无可替代**——这是第 03 篇对"接口 vs 抽象类"的终极答案。

❓ **重试为什么不能塞进 PaymentChannel 接口？**

重试是**横切关注**（cross-cutting concern），跟"支付"这个业务概念无关：
1. 塞进接口 → 每个渠道实现都要复制重试代码（微信一份、支付宝一份、银联一份……）；
2. 想要"微信带重试、支付宝不带"？做不到，接口方法焊死了；
3. 装饰器方案：`new RetryableChannel(new WechatChannel(), 3)`——**重试像胶带一样，想贴谁贴谁，还能叠着贴**。

### Step 3.1 BillingNotifier 接口

> 📁 **归属文件**：`src/com/yc/payflow/v2structure/notifier/BillingNotifier.java`


### Step 3.2 AbstractBillingNotifier 骨架：模板方法

> 📁 **归属文件**：`src/com/yc/payflow/v2structure/notifier/AbstractBillingNotifier.java`

```java
public abstract class AbstractBillingNotifier implements BillingNotifier {

    private final Set<String> blacklist = new HashSet<>();   // ← 接口存不了，只能存这里

    /** 模板方法：final 锁住流程，子类只填 doSend */
    @Override
    public final void notify(String recipient, String orderNo, String amount) {
        if (recipient == null || recipient.isEmpty()) {
            throw new IllegalArgumentException("接收方不能为空");
        }
        if (blacklist.contains(recipient)) {
            System.out.println("[" + channelName() + "] 命中黑名单，跳过: " + recipient);
            return;
        }
        String body = renderTemplate(orderNo, amount);       // 公共文案
        doSend(recipient, body);                             // ← 子类填空
        onSent(recipient, orderNo);                          // ← 钩子，子类可覆盖
    }

    /** 子类必须实现：真正的发送动作 */
    protected abstract void doSend(String recipient, String body);

    /** 钩子方法：默认打日志，子类按需覆盖 */
    protected void onSent(String recipient, String orderNo) {
        System.out.println("[" + channelName() + "] 已发送 " + orderNo + " 至 " + recipient);
    }

    /** 公共文案——三通道共用 */
    protected String renderTemplate(String orderNo, String amount) {
        return "尊敬的会员，您的订单 " + orderNo + " 已支付 " + amount + "，感谢惠顾。";
    }

    /** 骨架层附带能力：黑名单管理 */
    public void addBlacklist(String recipient) { blacklist.add(recipient); }
}
```

**三个设计细节**：

1. **`notify` 是 `final` 的**：流程顺序（校验→黑名单→渲染→发送→回调）是业务约定，**子类不许重排**。模板方法的"锁"就是 final；
2. **`doSend` 是 `protected abstract`**：子类**必须**实现（填空题），但外界看不见（封装）；
3. **`onSent` 是钩子**：给了默认实现，子类**可选**覆盖——这是模板方法模式的标准三件套：`final 模板 + abstract 填空 + default 钩子`。

📚 **这套范式你在用的框架里天天见**：

> - Spring：`BeanFactory`（接口）+ `AbstractApplicationContext`（骨架）
> - Netty：`ChannelHandler`（接口）+ `ChannelInboundHandlerAdapter`（骨架）
> - MyBatis：`Executor`（接口）+ `BaseExecutor`（骨架）
> - Servlet：`Servlet`（接口）+ `HttpServlet`（骨架，`service()` 就是 final 模板）
>
> 第 03 篇的结论：**框架 = 接口定契约 + 抽象类定骨架 + 你的类填空**。

### Step 3.5 RetryableChannel 装饰器：指数退避

> 📁 **归属文件**：`src/com/yc/payflow/v2structure/payment/RetryableChannel.java`

```java
public class RetryableChannel implements PaymentChannel {

    private final PaymentChannel delegate;      // ← 持有同接口的委托对象
    private final int maxAttempts;

    public RetryableChannel(PaymentChannel delegate, int maxAttempts) {
        this.delegate = delegate;
        this.maxAttempts = maxAttempts;
    }

    @Override
    public String pay(String orderNo, Money amount) {
        long backoffMs = 100;
        PaymentException lastError = null;
        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            try {
                return delegate.pay(orderNo, amount);
            } catch (PaymentException e) {
                lastError = e;
                if (attempt < maxAttempts) {
                    System.out.println("  [重试] 第 " + attempt + " 次失败，"
                        + backoffMs + "ms 后重试");
                    sleep(backoffMs);
                    backoffMs *= 2;             // ← 指数退避：100 → 200 → 400 → 800
                }
            }
        }
        throw new PaymentException("支付重试 " + maxAttempts + " 次后仍失败", lastError);
    }

    @Override
    public String channelName() {
        return "RETRY(" + delegate.channelName() + ")";   // 名字也"包"一层
    }
}
```

**为什么指数退避而不是固定间隔**：下游已经在过载（所以你才失败），固定间隔重试等于继续压；指数退避给下游**指数级增长的喘息时间**。生产常见序列：`2s → 4s → 8s → 16s → 32s → 60s → 120s → 300s` 封顶（本教学场景用 100ms 起步，保证测试快）。

**装饰器的可组合性**（这是它完胜继承的地方）：

```java
// 微信 + 重试

// 微信 + 重试 + 监控（将来再写个 MetricChannel 装饰器）
PaymentChannel ch2 = new MetricChannel(new RetryableChannel(new WechatChannel()));

// 重试套重试（测试里真这么干了）
PaymentChannel ch3 = new RetryableChannel(new RetryableChannel(new FlakyChannel(3), 2), 2);
```

继承方案要 3 × 2 = 6 个类排列组合，装饰器**零新增类**。V2 测试的最后一用例"装饰器可嵌套（重试套重试）"验证的就是这一点。

### 灵魂三问：V3 组合

❓ **虚拟课程 `extends PhysicalProduct` 会发生什么？**

**企鹅会飞**（第 05 篇的经典寓言）：`PhysicalProduct` 有 `ship()`，于是虚拟课程被迫实现一个"永远抛 UnsupportedOperationException"的 `ship()`——继承逼你说谎。更糟的是：`ColdChainProduct extends PhysicalProduct`、`CrossBorderProduct extends PhysicalProduct`……**组合爆炸**。

❓ **能力该继承还是持有？**

问自己一句话：**"疫苗是冷链，还是有冷链能力？"** ——"是"的关系用继承（is-a），"有"的关系用持有（has-a）。商品的各种附加属性全是 **has-a**：有配送能力、有冷链需求、有跨境税……

❓ **组合的三步动作是什么？**

① 能力抽成接口（`Shippable` 等）→ ② 每种能力独立实现（`StandardShipping` 等）→ ③ Builder 把能力装配进 `Product`。**装配发生在运行时，类图在编译期保持扁平**。

### Step 4.1 反面教材：继承的笛卡尔积爆炸

先看不用组合的下场。5 种能力：配送 / 冷链 / 跨境 / 可退 /（虚拟）：

```java
// ❌ 反例：继承派的类图
class Product                          { }
class PhysicalProduct extends Product  { void ship(); }
```

```java
    public Optional<Shippable> shipping()          { return Optional.ofNullable(shipping); }
    public Optional<ColdChainable> coldChain()     { return Optional.ofNullable(coldChain); }
    public Optional<CrossBorderable> crossBorder() { return Optional.ofNullable(crossBorder); }
    public Optional<Refundable> refundable()       { return Optional.ofNullable(refundable); }

        return new Builder(sku, name, priceCents);
    }

        // ... withShipping / withColdChain / withCrossBorder / withRefundable

    }

```

**两个易错点**：

1. **为什么能力查询返回 `Optional` 而不是直接给字段**：调用方必须先回答"它有没有这个能力"（`isPresent()`），才拿得到能力对象——**"虚拟课程没有配送"从运行时异常变成编译期显式分支**。对比继承方案：`instanceof` 判断散落各处，漏判就炸；
2. **`Optional` 的正确打开方式**：它只该出现在**返回值**（表示"可能没有"），不该做字段（`Optional` 不可序列化）——所以字段是裸引用、返回时包一层，这是 Java 社区的标准实践。

## 07.会话 3：V4 SOLID 五马分尸（第 06/07 篇）

```
┌─ 🎯 V4 目标 ─────────── 本案例的 OCP 高峰 ⭐ ────────────┐
│ 完成什么：SettlementEngine + 9 个 PromotionStep SPI        │
│           核心承诺：加"新营销规则"永远不改 Engine 一行代码    │
│ 不做什么：秒杀时间仍用系统时钟（V6 治）；金额审计做简化版      │
│ 验收标准：SettlementEngine 10 通过（含"扩展点验收"用例）      │
│ 预计耗时：120 min · 6 Step                                  │
└───────────────────────────────────────────────────────────┘
```

💡 **先想清楚再动手**：V0 的 `calculate()` 为什么改不动？因为它把**九层规则 + 编排顺序**焊在一起——加一个规则要在 250 行里找正确的插入点，改一个阈值要通读全函数。V4 的手术刀只有一把：**把"规则"和"编排"分离**。

### 灵魂三问：V4 SOLID

❓ **拆函数的第一刀怎么下？**

**找变化轴**。问产品经理一句话："这段逻辑里，什么最常变？"——营销规则（每周加新的）。那就按规则切：**每个变化方向一个类**。运费逻辑三个月不动，也照样切成 Step 吗？**是**——切它不是因为它会变，而是因为"统一的扩展点"比"个别的灵活"更值钱（这正是第 06 篇对 OCP 的深层解读）。

❓ **SPI 与 API 的区别？**

**谁调谁**：API 是"你调库"（`List.sort()` 你来调）；SPI 是"库调你"（`PromotionStep.apply()` 引擎来调）。面向 API 设计时你想的是"用户要什么功能"；面向 SPI 设计时你想的是"**我要给扩展者留什么缝**"。`PromotionStep` 的 4 个方法就是这条缝。

❓ **SOLID 五条哪条最重要？**

**DIP 是地基**。Engine 不依赖 9 个具体 Step，只依赖 `PromotionStep` 抽象——有了这条，OCP（加 Step 不改 Engine）、LSP（任意 Step 可换位置）、ISP（接口只有 4 个方法）才有意义。SRP 管拆分粒度，DIP 管依赖方向，**一个管刀法、一个管刀向**。

> 1. **调试**：断点停在 Step 里，`ctx.currentTotal` 直接可看——链式写法得追上一步的返回值；
> 2. **审计**：`auditTrail` 天然挂在 Context 上，订单算完连明细一起带走。

### Step 5.3 PromotionStep SPI

> 📁 **归属文件**：`src/com/yc/payflow/v4solid/PromotionStep.java`

```java
public interface PromotionStep {
    /** 执行顺序权重，小的先跑 */
    int order();

    /** 步骤名，用于审计 */
    String name();

    /** 是否适用于此上下文；不适用则跳过 */
    default boolean applies(SettlementContext ctx) { return true; }

    /** 执行步骤，可修改 ctx.currentTotal */
    void apply(SettlementContext ctx);
}
```

**4 个方法各自的存在理由**（对照 ISP：没有一个是凑数的）：

| 方法 | 回答的问题 | 例 |
|---|---|---|
| `order()` | 我排在链条哪 | 满减=20，秒杀=30，最低兜底=90 |
| `name()` | 审计日志怎么叫我 | `"FullReduction"` |
| `applies()` | 这个订单轮得到我吗 | `CrossBorderTaxStep`：无跨境商品就返回 false |
| `apply()` | 我做什么 | 满减命中阶梯就减钱 |

`applies()` 是**散弹式修改的克星**：V0 里"是否秒杀/是否有券/是否跨境"的判断散落在主流程；V4 里**每个 Step 自己回答适不适用**——Engine 一个 if 都不用写。

**FullReductionStep 全文**——注意它怎么修 BUG 1：

```java
public class FullReductionStep implements PromotionStep {

    /** 阶梯定义：满 X 减 Y（按阈值降序） */
    private static final long[][] LADDERS = {
        {100000, 25000},  // 满 1000 减 250
        {50000,  10000},  // 满  500 减 100
        {30000,  5000}    // 满  300 减  50
    };

    @Override public int order() { return 20; }
    @Override public String name() { return "FullReduction"; }

    @Override
    public void apply(SettlementContext ctx) {
        Money total = ctx.currentTotal();
        for (long[] rung : LADDERS) {                 // ← 从高到低，命中即停
            Money threshold = Money.ofCents(rung[0]);
            Money discount = Money.ofCents(rung[1]);
            if (total.greaterOrEqual(threshold)) {
                Money after = total.minus(discount);
                ctx.setCurrentTotal(after);
                ctx.audit(name(), discount, after);
                return;
            }
        }
    }
}
```

**BUG 1 的两种死法对比**：

```java
// V0（bug）：升序判断，>= 300 拦截一切
if (total >= 300)      fullReductionAmount = 50;      // 500 元订单在这就命中了
else if (total >= 500) fullReductionAmount = 100;     // 永远进不来

// V4（修复）：降序阶梯，命中即 return
{100000, 25000}, {50000, 10000}, {30000, 5000}        // 1000→250, 500→100, 300→50
```

**降序 + 命中即停**在数学上保证了"最大命中"——同样的写法还能直接处理"数据化阶梯"：运营想加"满 2000 减 600"？**改 LADDERS 一行数据，逻辑零改动**。魔法数从代码降级为数据。

💡 **VipDiscountStep 的彩蛋**：它内部直接 `VipPolicies.of(ctx.vipLevel())`——**V1 的多态族原封不动搬进 V4 的 Step 链**。这就是"版本演化"的含义：新版本不是推翻旧版本，而是**把旧版本的零件装进新版本的骨架**。

### Step 5.5 SettlementEngine：只做编排

> 📁 **归属文件**：`src/com/yc/payflow/v4solid/SettlementEngine.java`

```java
public class SettlementEngine {

    private final List<PromotionStep> steps;

    public SettlementEngine(List<PromotionStep> steps) {
        List<PromotionStep> sorted = new ArrayList<>(steps);       // 防御性拷贝
        sorted.sort(Comparator.comparingInt(PromotionStep::order)); // 按 order 排
        this.steps = List.copyOf(sorted);                          // 不可变
    }

    public SettlementResult settle(SettlementContext ctx) {
        for (PromotionStep step : steps) {
            if (step.applies(ctx)) {
                step.apply(ctx);
            } else {
                ctx.audit(step.name() + "(不适用)", Money.ZERO, ctx.currentTotal());
            }
        }
        return new SettlementResult(ctx.orderNo(), ctx.currentTotal(), ctx.auditTrail());
    }

    /** 便捷工厂：默认全套 9 个 Step */
    public static SettlementEngine defaults() { /* new 九个 Step */ }
}
```

**核心方法就一个 for 循环**。三个细节值得停留：

1. **构造器排序 + 拷贝**：调用方乱序传入也不怕（`order()` 是唯一真相）；`List.copyOf` 之后调用方手里的原 List 怎么改都影响不到 Engine——**不可变防御**；
2. **不适用也留痕**：`applies() == false` 的 Step 会写一条"(不适用)"审计——**对账时能解释"为什么这单没收跨境税"**，这是 V0 永远给不了的东西；
3. **Engine 不知道任何具体规则**：删掉 `steps/` 目录里任意一个类，Engine 照常编译——DIP 的直接证据。

### 灵魂三问：V5 特征化测试

❓ **没有测试的屎山怎么重构？**

**先写特征化测试**（characterization test）。它的断言不是"应该等于多少"（TDD 问的是应然），而是"**现在等于多少就锁多少**"——哪怕锁住的是 bug。先给行为拍 X 光片，再动手术；每动一刀，跑一遍片子对比。

❓ **特征化测试和 TDD 是一回事吗？**

**不是，方向相反**：

| | TDD | 特征化测试 |
|---|---|---|
| 断言来源 | 需求/设计（应然） | 现有行为（实然） |
| 时机 | 写实现**之前** | 重构**之前** |
| 测试挂了说明 | 实现错 | **行为变了**——重构出问题 |
| bug 的处理 | 防止产生 | **先锁住，修 bug = 有意识地改断言** |

❓ **"不改外部行为"到底指什么？**

**对相同输入产生相同输出**——**包括 bug 也一起算"行为"**。V5 的教学张力就在这：V4 是修复版，它和 V0 的行为**本来就该不同**（bug 被修了）。所以本套测试不是"验收重构"，而是**"量化差异"**：把 V0/V4 的不一致一条条列出来，证明"每个差异背后都是一个 bug"。

### Step 6.1 特征化测试 vs TDD

> 📁 **归属文件**：`src/com/yc/payflow/v5refactor/CharacterizationTest.java`

先解决一个工程障碍：V0 的 `calculate()` 里全是 `System.out.println`（坏味道 17 的另一面——测试它就得先忍它刷屏）。harness 用**输出流重定向**静默它：

```java
private static double calcV0(OrderInput in) {

    java.io.PrintStream originalOut = System.out;
    System.setOut(new java.io.PrintStream(java.io.OutputStream.nullOutputStream()));
    try {
        return OrderUtil.calculate(in);
    } finally {
        System.setOut(originalOut);              // 无论成败都还原
    }
}
```

> ⚠️ **这是教学妥协，不是最佳实践**：`System.setOut` 是全局开关，并发测试会互相干扰。正确姿势是 V2 的依赖注入（Notifier 作为参数传进来）。**这里保留它，恰恰让你体会"副作用不分离有多难测"**——第 10 篇的伏笔又回收一次。

另一个坑：V0 用 `static WALLET_BALANCE`，**用例之间会互相污染**——所以每个 case 构造输入时都要重置：

```java

    in.orderNo = "CT";
    in.prices = new double[]{price};
    in.counts = new int[]{1};
    ...
```


### 灵魂三问：V6 Clock 注入

❓ **为什么秒杀 Step 不能 `new Date()` / `LocalTime.now()`？**

因为**时间是你控制不了的外部输入**。`now()` 读的是 JVM 时钟，测试时它指向几点，取决于你什么时候跑测试——**输入不可控，输出就不可断言**。白天跑测试，秒杀分支永远进不去；凌晨跑测试，又测不了"非秒杀时段"。

❓ **生产环境用什么 Clock？**

`Clock.system()`——内部就是 `LocalDateTime.now()`，走 JVM 时钟。**生产代码和 V4 没有任何行为差异**，这是重构的安全底线。

❓ **测试环境用什么？**

`Clock.fixed(LocalDateTime.of(2024, 11, 11, 21, 30))`——**想拨到几点拨到几点**。测 20:00、21:30、22:00 边界、19:59 边界，四个用例四种时间，瞬间跑完。

### Step 7.1 Clock 抽象接口

> 📁 **归属文件**：`src/com/yc/payflow/v6testable/Clock.java`

```java
public interface Clock {
    /** 返回当前时间。 */
    LocalDateTime now();

    /** 便捷方法：当前时刻。 */
    default LocalTime nowTime() { return now().toLocalTime(); }

    /** 生产：走 JVM 系统时钟。 */
    static Clock system() { return () -> LocalDateTime.now(); }

    /** 测试：固定在某时刻。 */
    static Clock fixed(LocalDateTime at) { return () -> at; }
}
```

**这个接口浓缩了第 10 篇的三个可测试性特性**：

1. **可观测**：`now()` 是纯函数，输入输出一目了然；
2. **可控制**：`fixed()` 让测试当"时间的主人"；
3. **可隔离**：生产 `system()` / 测试 `fixed()`，同一份业务代码两种命运。

💡 **两个静态工厂都是 lambda**：`() -> LocalDateTime.now()` 就是 `Clock` 函数式接口的实现——**接口只有一个抽象方法时，工厂返回 lambda 比写匿名类优雅十倍**。

> 📚 JDK 自己就有 `java.time.Clock`，Spring 生态也推荐注入它。本案例**自己造一个**是为了让你看清它为什么存在——毕竟，亲手写 10 行胜过 import 一万次。

### Step 7.2 FlashSaleStepV6：只改一行

> 📁 **归属文件**：`src/com/yc/payflow/v6testable/FlashSaleStepV6.java`

```java
public class FlashSaleStepV6 implements PromotionStep {

    private static final int START_HOUR = 20;
    private static final int END_HOUR = 22;

    private final Clock clock;                        // ← 显式依赖，构造注入

    public FlashSaleStepV6(Clock clock) {
        this.clock = clock;
    }

    @Override public int order() { return 30; }
    @Override public String name() { return "FlashSaleV6"; }

    @Override
    public boolean applies(SettlementContext ctx) {
        for (OrderItem it : ctx.items()) {
            if (it.isFlashSale()) return true;
        }
        return false;
    }

    @Override
    public void apply(SettlementContext ctx) {
        int hour = clock.nowTime().getHour();         // ← V4 是 LocalTime.now()，
                                                      //    整个 V6 就改这一行
        if (hour < START_HOUR || hour >= END_HOUR) {
            ctx.audit(name() + "(不在秒杀时段," + hour + "时)",
                Money.ZERO, ctx.currentTotal());
            return;
        }
        Money before = ctx.currentTotal();
        Money after = before.percentOff(20);
        ctx.setCurrentTotal(after);
        ctx.audit(name() + "(-20%," + hour + "时)", before.minus(after), after);
    }
}
```

**对比 V4 版本的全部差异**：

```java
// V4：隐式依赖 JVM 时钟
int hour = LocalTime.now().getHour();

// V6：显式依赖注入的 Clock
int hour = clock.nowTime().getHour();
```

**业务规则一行没改**——这就是"可测试性重构"的理想形态：**改动最小化，收益最大化**。`[20, 22)` 半开区间的语义（20:00 含、22:00 不含）原样保留，只是从此**时间成了测试的提线木偶**。

### 灵魂三问：V7 DDD

❓ **"会员"在营销/账户/风控三处是同一个类吗？**

**不是，也不该是**。营销上下文的会员 = "折扣等级"；账户上下文的会员 = "钱包余额"；风控上下文的会员 = "风险画像"。**强行共享一个 Member 类，它会长成所有人都不认识的上帝类**（第 08 篇的上帝类病根就在这）。DDD 的答案：**限界上下文各自建模，同名词不同义是常态**。

❓ **聚合根的一致性边界画在哪？**

**找"同生共死"的对象**：OrderLine 离开 Order 没有意义（订单删了行也得删）、订单的状态转换（草稿→已结算）跨行有效——**一致性边界画在 Order 上**，Order 是聚合根，OrderLine 是内部实体，外部只能通过 Order 的意图方法触碰 OrderLine。

❓ **结算后要触发库存/发票/积分/通知/风控，怎么办？**

**发领域事件**。结算方法只管"结算发生了"这个事实，`bus.publish(new OrderSettled(...))`；谁想响应谁订阅——**结算代码永远不知道下游有谁**。将来加"风控订阅方"，连结算方法的注释都不用改。

### Step 8.3 Order 聚合根：状态机不变量

> 📁 **归属文件**：`src/com/yc/payflow/v7ddd/domain/Order.java`

```java
public class Order {

    public enum Status { DRAFT, SETTLED, SHIPPED, CANCELLED }

    private final OrderId id;
    private final String buyerId;
    private final String contactEmail;
    private final String contactPhone;
    private final List<OrderLine> lines = new ArrayList<>();
    private Status status = Status.DRAFT;
    private Money finalAmount;

    public void addLine(OrderLine line) {
        if (status != Status.DRAFT) {
            throw new IllegalStateException("只有草稿订单才能加行: 当前状态=" + status);
        }
        lines.add(line);
    }

    /** 结算——聚合根的核心意图方法。成功后发布 OrderSettled。 */
    public void settle(Money finalAmount, EventBus bus) {
        if (status != Status.DRAFT) {
            throw new IllegalStateException("订单已经结算或取消: " + status);
        }
        if (lines.isEmpty()) {
            throw new IllegalStateException("空订单不能结算");
        }
        if (finalAmount == null || !finalAmount.isPositive()) {
            throw new IllegalArgumentException("结算金额必须为正: " + finalAmount);
        }
        this.finalAmount = finalAmount;
        this.status = Status.SETTLED;

        // 发布领域事件：结算只宣布事实，不关心谁在听
        bus.publish(new OrderSettled(
            id.value(), buyerId, finalAmount, contactEmail, contactPhone));
    }

    public void cancel() {
        if (status == Status.SHIPPED) {
            throw new IllegalStateException("已发货订单不可取消");
        }
        this.status = Status.CANCELLED;
    }

    public List<OrderLine> lines() { return Collections.unmodifiableList(lines); } // 只读！
}
```

**五个要点**：

1. **状态机是 DRAFT → SETTLED → SHIPPED / CANCELLED**，每个意图方法开头都是 `if (status != ...)` 守卫——**非法状态转换在聚合门口被拒**，不是靠下游代码自觉；
2. **`lines()` 返回不可变视图**：外部拿到 List 也改不了聚合内部——**封装从"字段私有"升级为"边界守卫"**（对比 V0：`OrderInput` 的数组随便改）；
3. **`settle()` 的三重校验**（状态/非空/金额为正）就是 V1 Wallet"不变量四动作"在聚合维度的重演——**封装思想一以贯之**；
4. **EventBus 作为参数传入**而不是 Order 自己 new——依赖注入（V6 的 Clock 同款手法），聚合保持纯粹；
5. **发布事件放在状态变更之后**：先改状态再广播，保证订阅方看到的事件一定是"已生效的事实"。

### Step 8.4 DomainEvent + EventBus

> 📁 **归属文件**：`src/com/yc/payflow/v7ddd/event/{DomainEvent, OrderSettled, EventSubscriber, EventBus}.java`

```java
/** 领域事件基类：不可变的事实快照 */
public abstract class DomainEvent {
    private final LocalDateTime occurredAt;
    protected DomainEvent() { this.occurredAt = LocalDateTime.now(); }
    public LocalDateTime occurredAt() { return occurredAt; }
}

/** 订阅方接口：声明自己关心哪类事件 */
public interface EventSubscriber<T extends DomainEvent> {
    Class<T> subscribedTo();
    void handle(T event);
}

/** 事件总线：按事件类型路由到订阅方 */
public class EventBus {
    private final Map<Class<?>, List<EventSubscriber<?>>> registry = new HashMap<>();

    public <T extends DomainEvent> void subscribe(EventSubscriber<T> subscriber) {
        registry.computeIfAbsent(subscriber.subscribedTo(), k -> new ArrayList<>())
                .add(subscriber);
    }

    public void publish(DomainEvent event) {
        List<EventSubscriber<?>> subs = registry.getOrDefault(event.getClass(), List.of());
        for (EventSubscriber sub : subs) {
            try {
                sub.handle(event);
            } catch (Throwable t) {
                // 教学场景简化；生产建议：死信队列 + 告警
                System.err.println("[EventBus] 订阅方处理失败 "
                    + sub.getClass().getSimpleName() + ": " + t.getMessage());
            }
        }
    }
}
```

**三个设计决策**：

1. **事件是过去式名词**（OrderSettled 不是 OrderSettling）——领域事件记录"已发生的事实"，所以天然不可变；
2. **一个订阅方抛异常不影响其他订阅方**（catch Throwable 继续 for）——**下游故障不能反向击穿核心域**。这是六边形架构"出站端口"的容错语义，生产上对应 MQ 的重试/死信；
3. **同步 in-process 实现**：教学场景够用；换 Kafka 时**Order 聚合的代码一行不改**——因为 `bus.publish(...)` 签名没变，换的只是 EventBus 实现。**又一次面向接口**。

## 11.造 BUG → 修复清单：五处详解

参照 KV 案例"高峰造 BUG"设计，本案例五处"亲手制造、亲眼看见、亲手修好"。**每个 BUG 都在配套代码里可复现**——这是"以错为师"学习法的核心：

### BUG 1：满减顺序写反（V0 埋 / V4 修）

```java
// 造：
if (total >= 300)      fullReductionAmount = 50;    // 500 元订单在这命中
else if (total >= 500) fullReductionAmount = 100;   // 死代码

// 看见：./run.sh v0 → 订单 2 少收 ¥50；./run.sh v5 → 20/24 不一致
// 修复：V4 FullReductionStep 降序阶梯 {1000→250, 500→100, 300→50}，命中即 return
```

**教训**：逻辑正确 ≠ 顺序正确。if-else 的隐含语义是"先到先得"，**阶梯类判断必须从高到低**（或改用数据表 + 最大命中）。

### BUG 2：GOLD 重复打折（V0 埋 / V4 修）

```java
// 造：
if (input.vipLevel == 3) {
    total = total * 0.85;
    total = total - fullReductionAmount;   // 满减金额被再减一次
}

// 看见：./run.sh v0 → 期望 ¥382.5 实际 ¥332.5；./run.sh v4 → ¥340.00 正确
// 修复：V4 里满减和会员折扣是两个独立 Step，各算各的 Δ，互不干扰
```

**教训**：**一个变量被多条规则反复读写，就是 bug 温床**（V0 的 `total` 被读写 17 次）。Step 化之后每个 Step 只声明自己的 Δ，审计轨迹可查证。

### BUG 3：直写全局余额（V0 埋 / V1 修）

```java
// 造：
public static double WALLET_BALANCE = 100.0;
WALLET_BALANCE = WALLET_BALANCE - 150;     // → -50.0，账不平

// 看见：V1 会话 2.1 的反例演示；测试互相污染见 V5 harness 的"每 case 重置"
// 修复：V1 Wallet.withdraw() 不变量守卫——超额抛 InsufficientFundsException
```

**教训**：**不变量跟数据住在一起**。余额非负这个约束写在调用方，等于每个调用点都是潜在漏洞。

### BUG 4：企鹅会飞——继承逼你说谎（V3 前造 / V3 修）

```java
// 造：
class VirtualProduct extends PhysicalProduct {
    @Override void ship() {
        throw new UnsupportedOperationException();   // 被迫实现无意义的方法
    }
}

// 看见：调用 virtualCourse.ship() 当场抛异常
// 修复：V3 能力组合——virtualCourse 根本没有 shipping 字段，
//       course.shipping() 返回 Optional.empty()，编译期就无法误用
```

**教训**：is-a 关系不成立时硬用继承，**子类会用"永远抛异常的方法"向你说谎**。组合（has-a）让"没有这个能力"成为一等公民。

### BUG 5：隐式时间让测试等半夜（V4 埋 / V6 修）

```java
// 造（V4 的 FlashSaleStep）：
int hour = LocalTime.now().getHour();     // 输入不可控 → 输出不可断言

// 看见：./run.sh v0 → "当前 12 点，未进入秒杀时段，折扣未生效"
// 修复：V6 Clock 注入——Clock.fixed(21:30) 想测几点测几点，6 用例 26ms
```

**教训**：**你控制不了的输入（时间/随机数/网络）都必须显式注入**。同一个思想在 V2 的 FlakyChannel（可控故障）、V7 的 EventBus（参数传入）里反复出现——**依赖注入是可测试性的万能钥匙**。

| 特征化测试 | V5 | `CharacterizationTest` | 锁现状，量化差异 |
| 依赖注入 | V6 | `Clock` | 不可控输入显式化 |
| 聚合根 | V7 | `Order` | 一致性边界 + 状态机 |
| 领域事件 | V7 | `OrderSettled` / `EventBus` | 事实广播，星型解耦 |

### 13.3 设计决策树

```text
遇到一个设计问题，按这棵树走：

新增一种"同类行为的变体"（会员等级/支付渠道）？
    └── 抽接口 + 每变体一个类 + 注册表查找        → V1/V2

多个实现共享"流程骨架"？
    └── 接口定契约 + 抽象类定模板（final）+ 子类填空 → V2 双层范式

某能力只有部分对象具备（虚拟商品不配送）？
    └── 能力抽接口 + 字段持有 + Optional 暴露      → V3 组合

一个流程的"步骤"会持续增加？
    └── 每步一个类 + order() 排序 + 编排器 for 循环 → V4 SPI

旧代码没测试但必须改？
    └── 先特征化测试锁现状 → 小步搬 → 每步对比    → V5

逻辑依赖时间/随机数/环境？
    └── 抽象 + 构造注入 + 生产/测试双实现          → V6 Clock

一个动作要触发多个下游动作？
    └── 聚合根发领域事件 + EventBus 星型分发       → V7
```

### 13.4 距生产电商的差距

诚实面对：PayFlow 是教学工程，距生产还差这些（也是延伸方向）：

| 维度 | PayFlow 现状 | 生产要求 |
|------|-------------|---------|
| 持久化 | 内存对象 | 仓库模式 + 数据库事务（聚合根一个事务一个聚合）|
| 事件投递 | 同步 in-process | MQ 异步、至少一次投递、幂等消费、死信队列 |
| 并发 | 单线程演示 | 乐观锁（version 字段）防并发改同一聚合 |
| 金额精度 | long cents ✅ | 还需多币种（Currency 值对象）、汇率 |
| 配置 | 魔法数进常量 | 规则引擎/配置中心热更新（阶梯数据本来就已数据化）|
| 可观测 | println 审计 | 结构化日志 + 链路追踪（auditTrail 的结构化版本）|

> 注意一个细节：**这些差距大多在"基础设施"而非"领域模型"**——Order 聚合、Step 链、事件定义换到生产工程里几乎原样可用。这正是 DDD"领域与基础设施分离"的价值：**教学工程和生产工程的距离，比想象中近**。

## 14.项目技术思考

### 14.1 为什么金额必须是值对象

```java
// 三种写法的差距：
double a = 0.1 + 0.2;                    // 0.30000000000000004，且 a 是"数"不是"钱"
BigDecimal b = BigDecimal.valueOf(0.3);  // 精确，但 b.multiply(x) 到处裸运算，无业务语义
Money c = Money.ofYuan(0.3);              // 精确 + percentOff/max/min 是业务语言
```

`Money` 比 `BigDecimal` 多的那一层，就是**领域语言**：`total.min(deduction)`（积分抵扣不能超过总额）读出来就是业务规则本身。第 11 篇说"值对象是最便宜的 DDD 投资"——**写一个 Money 类 100 行，换来的是全工程永不出现的精度 bug 和自解释的金额运算**。

### 14.2 接口 vs 抽象类：本案例的三个现场答案

| 现场 | 选择 | 为什么 |
|------|------|--------|
| VipPolicy | 接口 | 等级之间是"可替换变体"，无共享流程 |
| BillingNotifier | 接口+抽象类 | 有共享流程（校验/黑名单/文案）**和共享状态**（blacklist Set）|
| PromotionStep | 接口 | Step 之间互不知晓，且需要 default 方法（applies）|

**判据**：要共享**状态**（字段）→ 抽象类必须出场；只共享**契约**或**默认行为** → 接口足够。第 03 篇的结论在三个现场全部兑现。

### 14.3 装饰器为什么优于继承

把"重试"给支付渠道加上的三种方案对比：

```java
// 方案 A：塞进接口 → 每个渠道实现都要抄重试代码，还不想要重试的渠道也被迫带上
// 方案 B：RetryableWechatChannel extends WechatChannel → 微信×支付宝×银联×是否重试 = 组合爆炸
// 方案 C：装饰器
new RetryableChannel(new WechatChannel(), 3);                    // 微信+重试
new MetricChannel(new RetryableChannel(new WechatChannel()));    // 还能再包一层监控
new RetryableChannel(new RetryableChannel(ch, 2), 2);            // 甚至套娃（V2 测试真的测了）
```

**装饰器 = 运行时组装的"单一职责小类"**。它的代价是层级深了调试要一层层 `delegate` 点进去——**收益是组合自由，代价是阅读跳转**，第 04 篇的权衡在 RetryableChannel 上看得清清楚楚。

### 14.4 领域事件 vs 直接调用：一笔账

结算后要通知发票/积分/短信，V7 前后的对比：

```java
// 直接调用（V0 风格的结局）：
void settle(...) {
    invoiceService.issue(...);      // 结算 import 发票
    pointsService.grant(...);       // 结算 import 积分
    smsService.send(...);           // 结算 import 短信
    // 新增财务对账？→ 改这里，重新测试结算，重新发布结算服务
}

// 领域事件（V7）：
void settle(Money amount, EventBus bus) {
    ...;
    bus.publish(new OrderSettled(...));   // 结算只认识事件
    // 新增财务对账？→ 写个 Handler + 注册一行，结算服务不动
}
```

**这笔账的本质**：直接调用的依赖数 = 下游个数（随业务**线性增长**）；事件发布的依赖数 = **永远 1**（只依赖 EventBus）。当"结算后要触发 XX"的需求清单从 3 条涨到 13 条，你才真正体会第 11 篇为什么说**"事件的本质是把'谁知道谁'倒置成'谁关心我'"**。

## 15.衔接与延伸

### 15.1 与图片框架案例（第 12 篇）的差异

| 维度 | 第 12 篇图片框架 | 本篇 PayFlow |
|------|----------------|--------------|
| 领域复杂度 | 低（技术管道为主）| 高（九层规则 + 多下游联动）|
| 演化主轴 | 架构分层（V0 单体 → V5 分层）| 质量属性（封装→结构→原则→可测→领域）|
| 高光模式 | 策略 + 工厂 | SPI + 装饰器 + 聚合 + 事件 |
| 教学重心 | "怎么分层" | "怎么从屎山长出架构" |

两篇方法论同构（**先看见病 → 小步演化 → 每步验收**），但视角互补：图片框架是"绿地项目怎么设计好"，PayFlow 是"遗产项目怎么救活"。**工作中后者占 80%**。

### 15.2 三个延伸挑战

**挑战 A（基础）· 给 EventBus 加异步分发**

把 `publish` 里的同步 for 循环改成线程池并发分发，注意两个坑：① 订阅方的异常处理从"打印"升级为"收集 + 死信列表"；② 想想 demo 输出顺序为什么变得不确定了——这正好复习《并发》专栏的坑。

**挑战 B（进阶）· 实现仓库模式 + 内存持久化**

写 `OrderRepository` 接口（`save / findById`），用 `Map<OrderId, Order>` 做内存实现。注意聚合根的 `lines` 是可变 List——**save 时深拷贝，findById 时返回副本**，否则外部拿到引用就绕过了聚合边界（这道题会让你真正理解"聚合边界"四个字）。

**挑战 C（冲刺）· 规则配置化**

把 `FullReductionStep` 的 LADDERS 从硬编码常量改成"构造注入 + JSON 加载"，让运营改阶梯**不发版**。做完后自问：为什么 V4 的架构这一步几乎零成本？（提示：阶梯早已数据化，这就是 SPI + 数据驱动的红利。）

### 15.3 学习路线建议

1. **第一遍（跟做）**：按 5 次会话顺序，每 Step 亲手敲、每验收亲眼见——约 20 小时；
2. **第二遍（盲做）**：只看 V0 和本文档的"版本演进路线"图，**不看中间版本代码**，自己从屎山推到 DDD，卡住再偷看对应版本——这是把"看会了"变"会写了"的唯一路径；
3. **第三遍（讲授）**：挑一个版本（推荐 V4 或 V7），给同事讲 30 分钟——讲不清的地方就是你还没真懂的地方（费曼学习法）。
