# 01.Agent 全景认知 —— LLM 如何从"聊天"走向"干活"

> 本文是《Agent 开发原理与体系化实战》专栏的第 1 篇。我们先不写框架代码，只做一件事：把「什么是 Agent」这件事讲透。读完你能获得三样东西 —— 一套判断"什么系统才算 Agent"的标准、一张辨识 Agent / RAG / Workflow / Chatbot 的坐标图，以及一段可运行的手写 ReAct 循环源码。
>
> 全文约 1.1 万字，建议阅读时长 25 分钟。

## 写在前面

2023 年，我们在用 LLM 写文案、总结文档、翻译。
2024 年，我们开始用 LLM 做 RAG，让它能"看资料回答"。
2025 年往后，越来越多的团队在做同一件事 —— **让 LLM 自己去干活**：查数据库、发邮件、执行代码、调用支付接口、操作浏览器下单。

从"回答问题"到"完成任务"，中间那个被塞满想象力的词，就叫 **Agent（智能体）**。

但只要你翻过几十篇公众号文章、看过几场大会分享，就会发现 Agent 这个词已经被玩坏了 —— 有人把「LLM + 一个搜索接口」叫 Agent，有人把「n8n 工作流」叫 Agent，甚至有人把「ChatGPT 网页版」也叫 Agent。

所以这一篇，我们不聊代码框架，先把三件事讲清楚：

1. **Agent 到底是什么**：一个能落到工程判断的定义。
2. **Agent 和它的邻居们有什么区别**：RAG、Workflow、Chatbot 到底差在哪。
3. **Agent 最小心智模型是什么**：不依赖任何框架，用 80 行代码手写一个 ReAct 循环，把黑盒变白盒。

## 一、概念篇：Agent 的定义与坐标系

### 1.1 一句话定义 Agent

社区里流传最广的一个公式，来自 Lilian Weng（OpenAI 前应用研究负责人）2023 年那篇著名的博客 *LLM Powered Autonomous Agents*：

$$
\text{Agent} = \text{LLM} + \text{Planning} + \text{Memory} + \text{Tools}
$$

这个公式简洁到近乎粗暴，但它道出了 Agent 与"普通 LLM 应用"的核心区别：**LLM 只是 Agent 的大脑，Agent 还需要眼睛（工具）、笔记本（记忆）、和会拆解任务的思维（规划）**。

如果你觉得这个定义还是太抽象，我们换个更工程化的说法：

> **Agent 是一个以 LLM 为决策核心、能在没有人类逐步指令的情况下、通过循环调用工具与环境交互、直到完成用户目标的软件系统。**

关键词有四个：

- **LLM 为决策核心** —— 每一步做什么，不是硬编码的 `if-else`，而是 LLM 现场判断的。
- **无需人类逐步指令** —— 用户只说"帮我调研三家竞品"，Agent 自己拆成"搜索 → 提取 → 对比 → 汇总"。
- **循环调用工具** —— 一次 LLM 调用不算 Agent，多次调用工具形成"决策 → 行动 → 观察"闭环才算。
- **目标驱动** —— 有明确的终止条件（拿到答案 / 达到最大步数 / 用户中断）。

把这四点当尺子，我们后面看任何一个系统是不是 Agent，就有得判了。

### 1.2 Agent 的四个组件详解

我们把 Lilian Weng 的公式拆开，看看每个组件到底承担什么职责。

#### 组件一：LLM（决策核心）

LLM 在 Agent 里扮演的不是"回答者"，而是"决策者"。

它的输出不再是"给用户的答案"，而是**"下一步该做什么"**：

- "我需要调用 `search` 工具查一下这个信息"
- "工具返回的结果不够，我要再查一次"
- "信息够了，可以生成最终答案了"

这就要求 LLM 具备两种能力：

1. **推理（Reasoning）**：能从当前信息推导出下一步。
2. **函数调用（Function Calling / Tool Use）**：能输出结构化的工具调用指令。

GPT-4、Claude 3.5+、Gemini 1.5+、DeepSeek-V3、Qwen2.5 这些模型都原生支持 tool calling，是构建 Agent 的一线选择。

#### 组件二：Planning（规划）

Planning 解决的是**"任务如何分解"**的问题。

面对"帮我写一篇 Vue 3 组合式 API 的技术文章"这样的任务，Agent 需要在心里（或显式地）做这样的拆解：

```
目标：写一篇 Vue 3 组合式 API 文章
├─ 子任务 1：调研 Vue 3 组合式 API 的核心概念
├─ 子任务 2：找 3-5 个典型代码示例
├─ 子任务 3：梳理与 Options API 的对比
├─ 子任务 4：撰写正文
└─ 子任务 5：审阅与润色
```

按规划的时机和粒度，Planning 分成几大流派：

| 流派 | 特点 | 代表 |
|------|------|------|
| **无显式规划** | LLM 每一步临场决策 | ReAct |
| **先规划后执行** | 先出完整计划再逐步执行 | Plan-and-Execute |
| **规划推理解耦** | 计划一次生成，执行时不再调 LLM | ReWOO |
| **反思式规划** | 执行后自我审查再修正计划 | Reflexion |

第 6 篇会专门深入对比这几种规划策略，本文只需要记住：**Planning 不是可选项，是 Agent 之所以为 Agent 的核心特征**。

#### 组件三：Memory（记忆）

LLM 本身是无状态的 —— 每次 API 调用都是"失忆"的。要让 Agent 有连贯的行为，就必须外挂记忆。

Agent 的记忆通常分三层：

- **短期记忆（Working Context）**：当前会话的消息列表，塞进 `messages` 里传给 LLM。
- **工作记忆（Working Memory）**：一次任务执行过程中的中间状态（比如已经调用过哪些工具、拿到了什么结果）。
- **长期记忆（Long-term Memory）**：跨会话的知识沉淀，通常用向量数据库存储。

第 3 篇会有完整的记忆系统实战，这里先埋个种子。

#### 组件四：Tools（工具）

Tools 是 Agent 的"手脚"。没有工具的 LLM 只能靠训练时的静态知识说话；有了工具，它就能：

- **感知世界**：搜索引擎、数据库查询、API 调用
- **改变世界**：发邮件、写文件、部署代码
- **辅助推理**：调用 Python 解释器算数学、调用 SQL 引擎跑查询

Tools 是让 Agent 从"聊天机器人"跃升为"数字员工"的关键。

### 1.3 Agent vs RAG vs Workflow vs Chatbot：一张坐标图

这是被问得最多的问题。我们用两个维度画一张坐标图：

- **横轴 —— 自主性**：从"完全按脚本走"到"完全自主决策"
- **纵轴 —— 外部交互**：从"只靠模型自身知识"到"深度调用外部世界"

```
外部交互
  ↑
高 │              RAG          Agent
  │            (查资料)      (查+做)
  │
  │
低 │            Chatbot       Workflow
  │           (纯聊天)      (按流程)
  │
  └─────────────────────────────→ 自主性
          低                    高
```

**Chatbot（左下）**：低自主性、低外部交互。用户问 → 模型答，一问一答，靠模型自身记忆的知识回答。典型例子：早期 ChatGPT、大部分客服机器人的话术树。

**Workflow（右下）**：高自主性错觉、低外部交互。看起来能"干活"，但每一步做什么、按什么顺序都是**人预先编排好的**。LLM 只是在某几个节点扮演"节点函数"。典型例子：n8n / Dify / Coze 的"工作流"模式。

**RAG（左上）**：低自主性、高外部交互。会去外部知识库（向量库）取资料，但取多少次、要不要多轮迭代、要不要写代码验证 —— 这些都不是它自主决定的。典型例子：企业知识问答系统。

**Agent（右上）**：高自主性、高外部交互。**这一步用什么工具、要不要再调一次、什么时候停下来 —— 都是 LLM 现场判断的**。这才是 Agent 的核心特征。

一个更细节的对比表：

| 维度 | Chatbot | RAG | Workflow | Agent |
|------|---------|-----|----------|-------|
| **决策者** | 无决策 | 检索器（固定策略） | 人（预编排） | LLM（运行时） |
| **步骤数** | 1 | 通常 1 | 固定 N | 动态 |
| **能否循环** | ❌ | ❌（通常） | 有限循环 | ✅ 循环直到完成 |
| **工具调用** | ❌ | 只读检索 | 预定义 | LLM 现场选 |
| **能否失败重试** | ❌ | ❌ | 有限重试 | ✅ 自主重试 |
| **失控风险** | 极低 | 低 | 低 | ⚠️ 需要防护 |

**判断口诀**：如果一个系统的"下一步做什么"是由 **LLM 在运行时决定的**，并且这个决策会形成 **循环**，那它就是 Agent。反之，无论包装得多花哨，都不是。

### 1.4 为什么 2025 是 Agent 元年

如果说 2023 年是 LLM 元年、2024 年是 RAG 元年，那么 2025 有几个信号让我相信这一年是 Agent 元年：

**信号一：模型能力越过阈值**
Tool Calling 的准确率、长上下文的稳定性、多步推理的一致性 —— GPT-4、Claude 3.7、Gemini 2.0 这一代模型在这三项能力上都跨过了"能商用"的门槛。

**信号二：协议开始统一**
Anthropic 主推的 **MCP（Model Context Protocol）** 让工具接入从"每家一套"走向"USB 化"，Google 提出的 **A2A** 让 Agent 之间通信有了标准。协议一旦统一，生态就会爆发（这是我们做过 Web、做过 App、做过区块链的人都验证过的规律）。

**信号三：从 Copilot 到 Autopilot 的范式转移**
2024 年是 Copilot 时代 —— 用户主导，AI 辅助（GitHub Copilot、Cursor 补全）。
2025 年往后是 Autopilot 时代 —— AI 主导，用户监督（Devin、Manus、Claude Code 一次搞定完整任务）。

**信号四：应用侧的爆款验证**
Devin（自主编程）、Manus（通用任务）、Claude Code（终端 Agent）、Cursor Composer（多文件重构）—— 这些明星产品都不是 Chatbot，都是 Agent。资本和用户已经用真金白银投票了。

### 1.5 Agent 的三种主流架构

进入实战之前，我们再看一层更工程的视角 —— Agent 系统的三种典型架构：

#### 架构 A：Router Agent（路由型）

```
        ┌─── Tool A
用户 → LLM ─┼─── Tool B
        └─── Tool C
```

最简单的形态：LLM 根据用户输入选一个工具执行，一次就结束。严格来说，这是"半 Agent" —— 没有循环，只有单次路由。

**典型场景**：ChatGPT 的插件系统早期形态、简单的意图分类系统。

#### 架构 B：Tool-Use Agent（工具循环型）

```
用户 → LLM → 工具 → LLM → 工具 → ... → LLM → 最终答案
        ↑         ↓
        └─── 循环 ─┘
```

**这才是最经典的 Agent 形态**。LLM 决定调什么工具、拿到结果后再决定下一步，直到判断"可以给用户答案了"才结束。

**典型场景**：ReAct、大部分单体 Agent、Cursor Composer、Claude Code。

**本文实战篇要手写的，就是这个架构。**

#### 架构 C：Multi-Agent（多 Agent 协作型）

```
                 Manager Agent
                /      |      \
      Researcher   Writer   Reviewer
```

多个专职 Agent 协作完成复杂任务，通常有一个 Manager 负责调度。

**典型场景**：内容创作、复杂调研、软件工程（MetaGPT）。第 8 篇会深入。

**新手建议**：先把架构 B 吃透，再看架构 C，不要一上来就上 CrewAI / AutoGen —— 那些框架把黑盒又加了一层壳。

## 二、实战篇：80 行代码手写 ReAct 循环

理论讲得再漂亮，都不如自己跑通一次。这一节我们**不依赖任何 Agent 框架**（不用 LangChain、不用 LangGraph、不用 CrewAI），只用 `openai` SDK，从零手写一个能"边想边做"的 Agent。

跑通这段代码，你会对 Agent 的运作机制建立永久的、去神秘化的认知。

### 2.1 我们要做什么

任务示例：

> "帮我查一下上海今天的天气，然后计算一下如果气温再高 12 度会是多少度。"

这个任务不能靠 LLM 一次生成答案，因为：

1. 天气数据不在 LLM 训练集里 —— 需要调用**天气工具**。
2. 数学计算 LLM 容易算错 —— 需要调用**计算器工具**。
3. 两个工具的调用有先后顺序 —— 需要**多轮循环**。

正是 Agent 的用武之地。

### 2.3 定义工具

工具就是普通的 Python 函数。我们先写两个玩具工具。

```python
# tools.py
def get_weather(city: str) -> str:
    """模拟天气查询。生产环境请接入和风天气 / OpenWeather 等真实 API。"""
    fake_data = {
        "上海": "晴，气温 22℃，湿度 65%",
        "北京": "多云，气温 18℃，湿度 40%",
        "深圳": "小雨，气温 26℃,湿度 80%",
    }
    return fake_data.get(city, f"暂无 {city} 的天气数据")


def calculate(expression: str) -> str:
    """安全的数学表达式计算器。仅支持数字与四则运算，防止代码注入。"""
    import re
    # 白名单：只允许数字、小数点、四则运算符、括号、空格
    if not re.fullmatch(r"[\d\.\+\-\*\/\(\)\s]+", expression):
        return "错误：表达式包含非法字符"
    try:
        # 显式给 eval 传空的全局/本地命名空间，杜绝调用任意函数
        result = eval(expression, {"__builtins__": {}}, {})
        return str(result)
    except Exception as e:
        return f"计算错误：{e}"
```

::: warning 安全提醒
生产环境**永远不要**把 LLM 生成的字符串直接扔给 `eval` / `exec` / `os.system`。上面 `calculate` 加了正则白名单，只允许数字与四则运算符，防止 RCE。第 4 篇会专门讲 Agent 工具的沙箱与权限设计。
:::

### 2.4 描述工具给 LLM

Tool Calling 的关键是让 LLM"看懂"每个工具能干什么、参数是什么。这份描述叫 **Tool Schema**，遵循 JSON Schema 规范。

```python
# schemas.py
TOOLS_SCHEMA = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的实时天气。当用户询问天气、气温、湿度等信息时调用。",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "城市中文名，例如 '上海'、'北京'"
                    }
                },
                "required": ["city"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "calculate",
            "description": "执行数学表达式计算。当用户需要进行加减乘除等数学运算时调用。",
            "parameters": {
                "type": "object",
                "properties": {
                    "expression": {
                        "type": "string",
                        "description": "标准数学表达式，例如 '22 + 12'、'(3 + 5) * 2'"
                    }
                },
                "required": ["expression"]
            }
        }
    }
]
```

::: tip Tool Schema 的写作艺术
- **description 要写给 LLM 看**：想象你在给一个刚入职的实习生写"这个函数什么时候用"。写得越准，Agent 调用越准。
- **参数命名要语义化**：`city` 比 `c` 好，`expression` 比 `e` 好。
- **required 一定要标**：不然 LLM 可能漏传关键参数。

第 2 篇会专门讲 Tool Schema 设计的进阶技巧，比如枚举值、条件必填、复合参数。
:::

### 2.5 手写 ReAct 循环

核心来了。**Agent 之所以是 Agent，就在于这个循环。**

```python
# agent.py
import json
import os
from dotenv import load_dotenv
from openai import OpenAI
from tools import get_weather, calculate
from schemas import TOOLS_SCHEMA

load_dotenv()

client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL"),
)

# 工具注册表：把工具名字映射到实际的 Python 函数
TOOL_REGISTRY = {
    "get_weather": get_weather,
    "calculate": calculate,
}


def run_agent(user_query: str, max_steps: int = 8) -> str:
    """一个最小可用的 ReAct 循环 Agent。"""
    messages = [
        {
            "role": "system",
            "content": (
                "你是一个能使用工具解决问题的智能助手。"
                "遇到需要查天气或做数学运算的问题时，主动调用对应的工具。"
                "拿到工具结果后继续推理，直到给出最终答案。"
            )
        },
        {"role": "user", "content": user_query},
    ]

    for step in range(max_steps):
        print(f"\n────────── 第 {step + 1} 轮 ──────────")

        # 1. Thought：让 LLM 决定下一步
        response = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            tools=TOOLS_SCHEMA,
            tool_choice="auto",
        )
        msg = response.choices[0].message

        # 2. 判断循环出口：如果 LLM 不再调工具，说明它准备给答案了
        if not msg.tool_calls:
            print(f"[最终答案] {msg.content}")
            return msg.content

        # 3. 把 assistant 的这条消息（含 tool_calls）先追加进上下文
        messages.append(msg)

        # 4. Action + Observation：逐个执行工具调用
        for tool_call in msg.tool_calls:
            tool_name = tool_call.function.name
            tool_args = json.loads(tool_call.function.arguments)

            print(f"[Action] 调用 {tool_name}({tool_args})")

            if tool_name in TOOL_REGISTRY:
                try:
                    tool_result = TOOL_REGISTRY[tool_name](**tool_args)
                except Exception as e:
                    tool_result = f"工具执行异常：{e}"
            else:
                tool_result = f"未知工具：{tool_name}"

            print(f"[Observation] {tool_result}")

            # 把工具结果作为 tool 角色消息回传给 LLM
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": tool_result,
            })

    return "已达到最大步数上限，未能得出最终答案。"


if __name__ == "__main__":
    query = "帮我查一下上海今天的天气，然后计算一下如果气温再高 12 度会是多少度。"
    print(f"[用户] {query}")
    run_agent(query)
```


一次真实运行的输出：

```
[用户] 帮我查一下上海今天的天气，然后计算一下如果气温再高 12 度会是多少度。

────────── 第 1 轮 ──────────
[Action] 调用 get_weather({'city': '上海'})
[Observation] 晴，气温 22℃，湿度 65%

────────── 第 2 轮 ──────────
[Action] 调用 calculate({'expression': '22 + 12'})
[Observation] 34

────────── 第 3 轮 ──────────
[最终答案] 上海今天天气晴，气温 22℃，湿度 65%。
如果气温再高 12 度，会是 34℃。
```

**注意看这三轮里发生了什么：**

- **第 1 轮**：LLM 判断需要查天气，主动调用 `get_weather`，拿到 `22℃`。
- **第 2 轮**：LLM 拿到天气结果后**自主决定**下一步要算 `22 + 12`，调用 `calculate`，拿到 `34`。
- **第 3 轮**：LLM 判断"信息够了，可以答了"，输出最终答案，循环终止。

**关键观察**：整个过程中没有任何一段代码写着「先查天气，再算加法」。这个执行顺序是 **LLM 在运行时决定的**。这就是 Agent 与 Workflow 的本质区别 —— **决策权在运行时，而不是编译时**。

### 2.7 ReAct 循环拆解图

回头看这段代码，其实就是把下面这张 ReAct 论文（Yao et al., 2022）里的经典循环图翻译成了 Python：

```
   ┌─────────────────────────────────────┐
   │  Thought：我该做什么？               │
   │  （LLM 生成决策，含 tool_calls）      │
   └──────────────┬──────────────────────┘
                  │
                  ▼
   ┌─────────────────────────────────────┐
   │  Action：执行工具调用                 │
   │  （Python 侧真实调用函数）             │
   └──────────────┬──────────────────────┘
                  │
                  ▼
   ┌─────────────────────────────────────┐
   │  Observation：拿到工具结果            │
   │  （追加到 messages 里）               │
   └──────────────┬──────────────────────┘
                  │
        ┌─────────┴─────────┐
        │                   │
   还需要工具？          可以给答案？
        │                   │
        └───→ 回到 Thought   └───→ 输出 Final Answer
```

**记住这张图。以后你看任何 Agent 框架的源码 —— LangGraph 的 `create_react_agent`、LangChain 的 `AgentExecutor`、CrewAI 的 `Task.execute` —— 剥到最底层，都是这个循环。**

## 三、思考篇：Agent 不是银弹

写到这里，Agent 的样子应该已经清晰了。但作为一个工程师而不是布道者，我们还得聊聊 Agent 的**代价与边界**。

### 3.1 什么时候该用 Agent，什么时候不该

Agent 是把双刃剑。它带来了自主性，但也带来了**不确定性**。下面是我的判断标准：

**该用 Agent 的场景**：

- **任务链条长、路径不固定**：调研、报告生成、代码修复
- **需要跟外部系统深度交互**：数据库查询、API 编排、浏览器操作
- **用户输入意图模糊**：需要 LLM 边做边判断"用户到底想要什么"

**不该用 Agent 的场景**：

- **流程固定、路径已知**：请假审批、订单查询 → 用 Workflow 更稳
- **只需要一次问答**：FAQ、翻译、摘要 → 用 Chatbot 就够了
- **对准确率要求 100%**：财务对账、医疗诊断的关键决策 → Agent 的幻觉率不允许，得人在环中
- **响应时间敏感**：Agent 循环通常 10-30 秒起步，做实时接口会被投诉

**一个粗略的决策树**：

```
用户任务
   │
   ├─ 单步就能完成？   ── 是 ──→ Chatbot / Chain
   │
   ├─ 步骤固定？        ── 是 ──→ Workflow（Dify / n8n）
   │
   ├─ 需要检索资料？    ── 是 且 ── 不需要动态决策 ──→ RAG
   │                                      │
   │                                需要动态决策 ─── Agentic RAG
   │
   └─ 步骤动态、多轮工具 ─────────→ Agent（本专栏）
```

### 3.2 Agent 开发的三大挑战

Agent 好玩，但**上线不易**。真正把 Agent 做进生产系统，你会撞上三面墙。

#### 挑战一：幻觉放大（Hallucination Amplification）

单次 LLM 调用出错的概率如果是 5%，那 10 轮循环下来，全对的概率是 $0.95^{10} \approx 60\%$。也就是说，链条越长，累计出错率越高。

**典型翻车案例**：
- 工具参数瞎编（把 `city="上海"` 写成 `city="Shang Hai City"`）
- 工具结果解读错误（返回 `温度：22℃`，LLM 理解成"22 华氏度"）
- 死循环（工具报错但 LLM 一直重试同一种错误调用）

**应对手段**：Schema 严格校验、工具结果格式化、最大步数上限、关键节点人工审核（Human-in-the-loop）。第 10 篇会专门讲评测和可观测性。

#### 挑战二：成本爆炸（Token Explosion）

Agent 每一轮循环都要把**完整历史**（含所有 tool_calls 和 tool_results）传给 LLM。10 轮下来，一次任务可能消耗几万到几十万 Token。

**一个真实数据**：跑一个 15 步的调研任务，用 GPT-4，单次成本可能到 **$1-3**。如果一天跑 1000 次，一个月账单就是 3-9 万美金。

**应对手段**：
- 记忆压缩（第 3 篇）
- 便宜模型跑辅助任务（用 GPT-4o-mini 判决策、用 GPT-4o 出答案）
- ReWOO 类"规划推理解耦"（第 6 篇）
- 缓存重复的工具调用

#### 挑战三：可控性下降

Workflow 时代，程序做什么、什么时候做，程序员心里门清。到了 Agent 时代，你只能"祈祷" LLM 别乱来 —— 别删了不该删的库、别发出不该发的邮件、别把公司秘密写进 Prompt 又搜出来。

**应对手段**：
- **权限最小化**：给 Agent 的每个工具都做权限收敛（只读 vs 读写、白名单目录）
- **危险操作二次确认**：删除文件、发送邮件、执行付款前必须人工点确认
- **Prompt Injection 防护**：用户输入不能直接拼进 System Prompt
- **审计日志**：每一步 Thought / Action / Observation 落库，可回溯

::: warning 一条铁律
**永远不要给一个还没经过充分测试的 Agent 授予"生产环境的写权限"。** 先只读、再受控写、最后放开写 —— 这个顺序不能反。
:::

### 3.3 一个反直觉的建议

聊了这么多 Agent 的好，最后给一条反直觉的建议：

> **能不用 Agent 就不用 Agent。**

优先级从高到低：**Chain > Workflow > RAG > Agent**。

原因很简单：**Agent 的能力上限来自 LLM，Agent 的坑也来自 LLM**。一个能用 3 行 `if-else` 解决的问题，硬要套上 Agent 框架，只会得到"更慢、更贵、更容易翻车"的版本。

真正好的 Agent 工程师，不是逢事就上 Agent 的人，而是**能精准判断"这个需求配得上 Agent 吗"的人**。

## 四、本文小结

**核心记忆点**：

1. **Agent 的判断标准**：LLM 在运行时决定下一步做什么，并且这个决策形成循环 —— 这才是 Agent，其他都是伪 Agent。
2. **Agent 的四组件**：LLM（决策）+ Planning（规划）+ Memory（记忆）+ Tools（工具）。
3. **Agent 和邻居的区别**：自主性 × 外部交互 两个维度看清 Chatbot / RAG / Workflow / Agent 的坐标。
4. **ReAct 循环是所有 Agent 的最小公倍数**：Thought → Action → Observation → 循环 → Final Answer。剥掉所有框架，本质都在这。
5. **Agent 有代价**：幻觉放大、成本爆炸、可控性下降 —— 上生产前必须直面这三面墙。
