## 01.工作案例引入

### 1.1 案例引入

**场景**：凌晨 2:13，值班的后端工程师小林收到告警——登录接口 `POST /api/login` P99 延迟飙升，响应超过 5 秒。

**第一步：确认现象**。`curl` 请求登录接口，返回 `504 Gateway Timeout`——说明上游应用没在 Nginx 超时时间内响应。是应用挂了还是网络断了？

**第二步：测试连通性**。`ping api-server-1`——丢包 0%、延迟 3ms，网络通、服务器没死。但 `telnet api-server-1 8080` 返回 `Connection refused`——端口被拒，Tomcat 可能挂了。

**第三步：检查进程**。SSH 上去，`ps aux | grep tomcat` 进程还在，但 `netstat -ant | grep 8080` 没有 LISTEN。`tail -f catalina.out` 看到 `OutOfMemoryError: Java heap space`——应用没退出，但卡在 GC 循环，已无法处理请求。

**第四步：找根因**。重启 Tomcat 恢复后，`grep "OutOfMemory" catalina.out` 发现一小时内 OOM 了 3 次。再查 Nginx 日志，发现一个爬虫 IP 在疯狂请求 `GET /api/products/export?size=100000`——每次导出 10 万条数据，在堆里建了巨大 ArrayList。

**第五步：源头阻断**。Nginx 加 `limit_req_zone` 限流、把爬虫 IP 拉黑、给 `/export` 接口加 `slow-query-threshold` 监控。

**疑惑链条**：

- "504 和 502 有什么区别？" → 504=上游超时未响应，502=上游返回了无效响应 → 不同的排查方向
- "ping 通了为什么 telnet 不通？" → ping 走 ICMP（网络层），telnet 走 TCP（传输层）→ 网络通不意味着端口通 → 不同层的问题要用不同层的工具排查
- "进程在为什么不监听端口？" → 进程在 GC 停滞，主线程卡住，还没来得及 `bind()` 端口 → `netstat` 看不到 LISTEN
- "怎么找到是哪个请求导致的 OOM？" → Nginx 日志按 URL 聚合排序 → 找出请求量/数据传输量最大的接口

小林这一串排查，本质是在问：**网络出问题时，从哪一层开始查？每层用什么工具？工具的输入和输出怎么解读？**——这正是"如何去排查网络故障"要回答的。

### 1.2 知识图谱

**小林排查路径在 OSI 模型中的映射**：

```text
应用层：  curl → 504 → 问题在上游              [第5章]
传输层：  telnet → Connection refused         [第6章]
        netstat → 无 LISTEN → 进程异常       [第4章]
网络层：  ping → 0% 丢包 → 网络正常           [第2章]
        traceroute → 路径可达                [第7章]
链路层：  arp → MAC 正常                      [第8章]
```

**排查方法论：自顶向下 or 自底向上？**

| | 自顶向下（小林） | 自底向上 |
|---|---|---|
| 顺序 | 应用 → 传输 → 网络 → 链路 | 链路 → 网络 → 传输 → 应用 |
| 优点 | 从用户视角快速定位 | 先排除底层、避免误判 |
| 适用 | 用户报"功能不可用" | 基础设施变更后验证 |

**本章主线**：沿 OSI 模型从应用到链路，掌握 ping / telnet / netstat / traceroute / tcpdump / curl 六大工具，知道什么场景先拿哪个、什么时候换下一个，最终形成"分层排查"的系统思维。

### 1.5 核心原理

网络故障排查的最高效方法是**自底向上按OSI模型逐层排查**。为什么是自底向上？因为下层故障会导致上层全部失败，但上层故障不影响下层。检查顺序：物理层（网线插了吗？灯亮吗？）→ 链路层（ARP能解析MAC吗？）→ 网络层（`ping`能通吗？TTL正常吗？）→ 传输层（`telnet IP port`端口通吗？）→ 应用层（`curl -v`能拿到响应吗？）。90%的网络故障在传输层以下，而你最可能一开始就跳到了应用层检查——浪费大量时间。记住这条铁律：**先ping再telnet最后curl**。

## 02.学会使用Ping工具

### 2.1 Ping工具是什么

Ping工具是一种网络诊断工具，通过发送ICMP（Internet Control Message Protocol）回显请求消息到目标主机，并等待返回ICMP回显应答来测量往返时间（RTT）和丢包率。

### 2.2 Ping工具的用途

Ping 的三个核心用途，每个背后都对应它的原理：

1. **测试连通性**：发出 ICMP 回显请求，收到回显应答就说明源到目标「去 + 回」两条路都通；收不到则说明某一段链路断了或目标不可达。
2. **测量延迟（RTT）**：从发出请求到收到应答的时间差就是往返时间 RTT，由物理距离、路由跳数、链路拥塞共同决定——RTT 越小，说明链路越「近」越通畅。
3. **检测丢包**：发出但没收到应答的请求就算丢包，丢包率直接反映链路质量——0% 健康，持续 >1% 就要警惕拥塞、带宽不足或硬件问题。

### 2.3 Ping工具使用

```text
yangchong@CHONGYYANG-MC2 ~ % ping www.baidu.com  
PING www.a.shifen.com (183.2.172.177): 56 data bytes
64 bytes from 183.2.172.177: icmp_seq=0 ttl=64 time=29.305 ms
64 bytes from 183.2.172.177: icmp_seq=1 ttl=64 time=38.341 ms
64 bytes from 183.2.172.177: icmp_seq=2 ttl=64 time=27.886 ms
64 bytes from 183.2.172.177: icmp_seq=3 ttl=64 time=28.842 ms
64 bytes from 183.2.172.177: icmp_seq=4 ttl=64 time=28.104 ms
64 bytes from 183.2.172.177: icmp_seq=5 ttl=64 time=39.136 ms
64 bytes from 183.2.172.177: icmp_seq=6 ttl=64 time=29.360 ms
64 bytes from 183.2.172.177: icmp_seq=7 ttl=64 time=28.035 ms
64 bytes from 183.2.172.177: icmp_seq=8 ttl=64 time=44.451 ms
^C
--- www.a.shifen.com ping statistics ---
9 packets transmitted, 9 packets received, 0.0% packet loss
round-trip min/avg/max/stddev = 27.886/32.607/44.451/5.915 ms
```

让我们逐行解读

```
PING www.a.shifen.com (183.2.172.177): 56 data bytes    // 你 ping 的是 www.baidu.com，DNS 解析到真实服务域名 www.a.shifen.com（百度 CDN），IP 是 183.2.172.177
64 bytes from 183.2.172.177: icmp_seq=0 ttl=64 time=29.305 ms    // 每次回显应答：返回 64 字节、序列号 0、TTL=64、往返耗时 29.3ms（后面 8 行同理，仅 seq 和 time 不同）
^C    // 手动 Ctrl+C 中断 ping
9 packets transmitted, 9 packets received, 0.0% packet loss    // 发 9 收 9，丢包率 0%
round-trip min/avg/max/stddev = 27.886/32.607/44.451/5.915 ms    // RTT 最小 27.9 / 平均 32.6 / 最大 44.5 / 标准差 5.9ms，波动小、链路稳定
```

### 2.4 Ping诊断结果分析

**先看当前这段结果**：网络访问百度正常，无丢包，平均延迟约 32ms，延迟波动不大，整体网络状态良好。

```
网络连通：正常
DNS 解析：正常
访问百度：正常
延迟：约 30ms
丢包：目前看没有丢包
稳定性：较稳定
```

**再看 ping 结果要重点关注的 4 个指标**：

| 指标 | 怎么看 | 健康标准 |
|------|--------|---------|
| 目标 IP | DNS 解析出的地址，判断域名是否解析正确 | 解析到预期的真实服务 IP |
| RTT（延迟） | 单次往返耗时，越低越好 | 内网 <1ms，同城 <10ms，跨省 <50ms |
| 丢包率 | 未收到应答的比例 | 0% 健康，持续 >1% 需排查 |
| min/max/avg | 延迟的最小/最大/平均值，看波动 | max 与 min 差距小 = 链路稳定 |

**判读口诀**：先看丢包（0% 才继续看延迟）→ 再看 avg（越低越好）→ 最后看 max-min 波动（波动大说明拥塞或抖动）。

### 2.5 Ping常见案例

**案例 1：连接超时（Request timeout）**

```text
ping 10.0.0.99
PING 10.0.0.99 (10.0.0.99): 56 data bytes
Request timeout for icmp_seq 0
Request timeout for icmp_seq 1
Request timeout for icmp_seq 2
^C
--- 10.0.0.99 ping statistics ---
3 packets transmitted, 0 packets received, 100.0% packet loss
```

**分析结论**：100% 丢包，一个包都没回来。三个可能原因：① 目标主机不存在或已关机；② 中间没有回程路由；③ 防火墙/安全组屏蔽了 ICMP。排查顺序：先 `ping` 网关确认本机链路正常 → 再 `ping` 同网段其他主机 → 最后确认目标是否放行 ICMP。

**案例 2：高延迟**

```text
ping www.baidu.com
64 bytes from 183.2.172.177: icmp_seq=0 ttl=64 time=180.5 ms
64 bytes from 183.2.172.177: icmp_seq=1 ttl=64 time=210.3 ms
64 bytes from 183.2.172.177: icmp_seq=2 ttl=64 time=195.8 ms
--- www.a.shifen.com ping statistics ---
round-trip min/avg/max/stddev = 175.2/198.6/220.4/12.3 ms
```

**分析结论**：无丢包但平均延迟高达 198ms（正常跨省才 <50ms），说明链路「绕远路」了。三个可能原因：① 路由走了境外或绕行节点；② 带宽被打满导致排队；③ 目标服务器负载过高。排查方向：用 `traceroute` 看每一跳的延迟，定位是从哪一跳开始变慢。

**案例 3：部分丢包**

```text
ping 192.168.1.100
64 bytes from 192.168.1.100: icmp_seq=0 ttl=64 time=3.2 ms
Request timeout for icmp_seq 1
64 bytes from 192.168.1.100: icmp_seq=2 ttl=64 time=3.5 ms
Request timeout for icmp_seq 3
64 bytes from 192.168.1.100: icmp_seq=4 ttl=64 time=2.8 ms
--- 192.168.1.100 ping statistics ---
10 packets transmitted, 6 packets received, 40.0% packet loss
```

**分析结论**：40% 丢包，时好时坏（能通但间歇性失败）。三个可能原因：① 链路质量问题（网线老化、无线信号弱）；② 网络拥塞导致缓冲溢出丢包；③ 网卡或交换机硬件故障。排查方向：换网线/换端口测试，`ifconfig` 查看网卡 error、drop 计数是否持续增长。

### 2.6 Ping基础的原理

ping 基于 ICMP 协议（不是 TCP 也不是 UDP）。ICMP 在 IP 报文后加入了类型（ping请求=8，应答=0）、代码、校验和、标识符、序列号等字段。

**这是小林排查中的关键认知**：ping 通了只说明 IP 层可达，不说明 TCP 端口开放。所以 ping 通但 telnet 不通是完全合理的情况。

## 03.用ifconfig查询网络

### 3.1 ifconfig 是什么

ifconfig 用于配置和显示网络接口信息：IP地址、子网掩码、MAC地址、MTU等。

常用命令：`ifconfig`（显示所有接口）、`ifconfig eth0`（特定接口）、`ifconfig eth0 up/down`（启用/禁用）、`ifconfig eth0 mtu 1500`（设置MTU）。


## 04.netstat和lsof

### 4.1 netstat和lsof是什么

`netstat` 用于显示网络连接、路由表和网络接口统计信息。

```bash
netstat -ant  # 所有TCP连接
netstat -u    # UDP连接
netstat -p    # 显示关联进程
```

`lsof` 用于列出当前系统中打开的文件和网络连接。

```bash
lsof -i       # 所有网络连接
lsof -i :80   # 使用端口80的连接
lsof -p <PID> # 特定进程的连接
```

**回到小林的排查**：`netstat -ant | grep 8080` 没有 LISTEN 状态，说明 Tomcat 没有成功绑定端口。配合 `ps aux` 发现进程在但端口不存在，指向了 OOM → GC 停滞的方向。


## 05.HTTP应用排查工具

### 5.1 应用层排查工具

Chrome DevTools（F12）是最常用的应用层排查工具。

### 5.2 找有问题服务端IP

Network → 点击请求 → Headers → Remote address 查看当前连接的 IP。这在排查 CDN/多节点问题时非常有用——不同用户可能连到不同的节点。

### 5.3 辅助排查网页慢问题

Network → Timeline 查看各资源耗时，定位耗时最高的 HTTP 资源对象。

### 5.4 解决失效Cookie

Application → Storage → Cookie → 清除对应条目。

### 5.5 查看证书的信息

Security 菜单查看 TLS 信息，包括协议版本、密钥交换算法、证书有效期等。更详细的 TLS 握手细节需要用 tcpdump + Wireshark。


## 06.传输层排查工具

### 6.1 路径可达性测试

```bash
telnet www.baidu.com 443    # 测试TCP端口可达性
nc -w 2 -zv www.baidu.com 443  # nc 测试连通性
```

**回到小林的排查**：`telnet api-server-1 8080` 返回 `Connection refused`，说明 TCP 握手被拒绝——网络通但端口未监听。

### 6.2 查看当前连接状况

```bash
netstat -ant  # 查看所有TCP连接及状态
```

关注输出中的 ESTABLISHED、TIME_WAIT、CLOSE_WAIT 等状态。

### 6.3 查看连接传输速率

`iftop`（需安装）可以显示不同连接的实时传输速率，定位带宽占用。

### 6.4 查看丢包和乱序等

**tcpdump + Wireshark** 是最强大的传输层排查组合：

```bash
# 抓取特定端口数据包
sudo tcpdump -i eth0 tcp port 80 -w capture.pcap
# 只抓TCP SYN包（排查连接建立问题）
sudo tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0' -w syn.pcap
```

Wireshark 过滤器：
```
tcp.analysis.retransmission     # TCP重传
tcp.analysis.out_of_order       # 乱序包
tcp.analysis.duplicate_ack      # 重复ACK
tcp.analysis.zero_window        # 零窗口（接收缓冲区满）
```

**查看 TCP 统计**：`netstat -s | grep -i retransmit` 查看重传次数。


## 07.网络层排查工具

### 7.1 查看网络路径状况

**traceroute** 逐跳显示数据包经过的路由器：

```bash
traceroute www.baidu.com
# 如果UDP被屏蔽，用 -I 切换为ICMP探测
traceroute www.baidu.com -I
```

**mtr** 是 traceroute 的超集，能连续多次探测并显示每跳丢包率：

```bash
mtr www.baidu.com -r -c 10  # 发送10个包，报告模式
```

重点关注每跳的 Loss% 列——哪一跳丢包率高，问题就在哪一跳。

### 7.2 查看路由信息

```bash
route -n       # 查看路由表
netstat -r     # netstat查看路由
ip route       # 新命令查看路由
```


## 08.数据链路层排查

### 8.1 ARP相关排查

```bash
arp -a              # 查看ARP缓存表
sudo arp -d <IP>    # 清除指定IP的ARP缓存
cat /proc/net/arp   # Linux上查看ARP表
```

关注：ARP缓存是否过期、是否有ARP欺骗（同一IP对应多个MAC）。

### 8.2 查看网卡信息

```bash
ethtool eth0           # 查看网卡速率、双工模式、链路状态
ethtool -S eth0 | grep -i error  # 查看网卡错误统计
ifconfig en0           # macOS查看网卡状态
```

如果 `rx_errors` 或 `tx_errors` 异常高，可能是网线质量问题或交换机端口故障。

### 8.3 抓取链路层数据

```bash
sudo tcpdump -i eth0 -e -c 5        # 显示MAC地址
sudo tcpdump -i eth0 arp -c 10      # 抓ARP包
sudo tcpdump -i eth0 ether host aa:bb:cc:dd:ee:ff  # 特定MAC流量
```


## 09.CURL网络请求工具

### 9.1 CURL工具介绍

CURL 是命令行 HTTP 客户端，支持多种协议，常用于测试 API、下载文件、调试网络请求。功能强大到可以完全取代 Postman。

### 9.2-9.7 CURL基本用法

```bash
curl http://www.baidu.com              # GET请求
curl -d 'key=value' -X POST URL       # POST表单
curl -H "Content-Type: application/json" -X POST -d '{"a":1}' URL  # JSON POST
curl -F "file=@photo.jpg" URL          # 文件上传
curl -o filename URL                   # 下载文件
curl -H 'Authorization: bearer xxx' URL # 自定义头
```

### 9.8 CURL通信过程

`curl -v` 显示完整通信过程——DNS解析→TCP连接→TLS握手→HTTP请求→响应，是排查应用层问题的首选。

```bash
curl -v https://www.wanandroid.com/banner/json
# 输出：DNS解析 → TCP握手 → TLS协商 → HTTP请求行/头 → 响应状态行/头 → 响应体
```

### 9.9 CURL其他的实践

```bash
curl --connect-timeout 5 --max-time 30 URL   # 超时控制
curl -L URL                                    # 跟随重定向
curl -x http://proxy:8080 URL                  # 使用代理
curl -k https://self-signed.example.com        # 忽略SSL证书
curl -A "User-Agent" -e "Referer" URL          # 模拟浏览器
# 查看各阶段耗时（DNS/TCP/TLS/TTFB/总耗时）
curl -o /dev/null -s -w "DNS:%{time_namelookup}s TCP:%{time_connect}s TLS:%{time_appconnect}s TTFB:%{time_starttransfer}s Total:%{time_total}s\n" URL
```


## 10.综合案例

本章用**一个贯穿全文的实战案例**——模拟一个从用户投诉到根因定位的完整排查过程。我们会从应用层开始，沿着 OSI 模型逐层下沉，每层使用对应的工具，直到找到根因。**读完这一节，你应该能形成"遇到任何网络问题都能按层次、用工具、找线索"的排查能力**。

### 10.1 案例背景与目标

**场景设定**：运维接到用户投诉——"网站打不开了"。作为值班工程师，你需要独立完成排查。系统的部署架构如下：

```
用户浏览器 → CDN → Nginx(反向代理) → Tomcat集群 → MySQL
```

没有已知线索，需要从零开始一步步排查。

### 10.2 用户侧验证

**目标**：确认问题是"完全打不开"还是"慢"还是"部分功能不可用"。

```bash
# 1. 用 curl 模拟用户请求，看返回什么
curl -I https://www.company.com
# HTTP/1.1 200 OK → 主站正常
# 或 HTTP/1.1 502 Bad Gateway → 后端有问题
# 或 curl: (7) Failed to connect → 网络不通
# 或 curl: (28) Connection timed out → 超时
```

**情况A：返回 502/504**
→ 问题在上游（Nginx 连不上 Tomcat），进入第二层

**情况B：返回超时**
→ 网络不通或服务器没响应，跳过传输层查网络层

**情况C：返回 200 但用户说打不开**
→ 可能是 CDN 缓存了旧内容、DNS 解析到了错误 IP

```bash
# 2. 查看请求耗时明细
curl -o /dev/null -s -w \
  "DNS:%{time_namelookup}s TCP:%{time_connect}s TLS:%{time_appconnect}s TTFB:%{time_starttransfer}s Total:%{time_total}s\n" \
  https://www.company.com
# 如果 DNS > 1s → DNS问题
# 如果 TCP > 100ms → 网络延迟高
# 如果 TTFB > 5s → 服务端处理慢
```

### 10.3 应用层排查

**目标**：确定 HTTP 层面的具体错误。

```bash
# 直接绕过CDN，请求Nginx
curl -v -H "Host: www.company.com" http://10.0.0.1/
# → HTTP/1.1 502 Bad Gateway
# 说明 Nginx 活着，但连不上 Tomcat

# 查看 Nginx 错误日志
tail -100 /var/log/nginx/error.log
# → upstream timed out (110: Connection timed out) while connecting to upstream
# Nginx连接Tomcat超时

# 查看 Nginx upstream 状态
curl http://127.0.0.1/nginx_status  # 如果配置了stub_status
```

**确定问题**：Nginx 正常，连接不到 Tomcat。

### 10.4 传输层排查

**目标**：确定 TCP 层面的连通性。

```bash
# 1. ping 测试（网络层）
ping 10.0.0.101  # Tomcat-1 的IP
# 64 bytes from 10.0.0.101: icmp_seq=0 ttl=64 time=0.5ms
# ✅ 网络层可达

# 2. telnet 测试端口（传输层）
telnet 10.0.0.101 8080
# Trying 10.0.0.101...
# telnet: connect to address 10.0.0.101: Connection refused
# ❌ TCP端口不监听！

# 3. SSH登录服务器，检查进程
ssh 10.0.0.101
ps aux | grep tomcat
# tomcat  12345  0.1  85.2 5123456 4096000 ?  Sl   02:00  0:30 java ...
# 进程在！内存占用85%

# 4. 检查端口监听
netstat -ant | grep 8080
# 空！没有LISTEN状态
# 进程在但不监听端口 → 进程异常（可能卡在GC或其他阻塞操作）

# 5. 查看应用日志
tail -200 /var/log/tomcat/catalina.out
# java.lang.OutOfMemoryError: Java heap space
# Dumping heap to java_pid12345.hprof ...
# ❌ OOM！应用在Full GC循环中，无法响应任何请求
```

**确定根因**：Tomcat OOM，应用卡在 GC，无法监听端口。Nginx 连接超时 → 返回 502。

### 10.5 网络层排查

**如果第三步 ping 不通**，排查方向转到网络层：

```bash
# 1. traceroute看路径
traceroute 10.0.0.101 -n
# 1  10.0.0.1  0.5ms  ← 到了网关
# 2  * * *           ← 之后全是星号
# 说明：出了网关就断了 → 路由问题或交换机/防火墙问题

# 2. 检查路由表
ip route | grep 10.0.0
# 如果没有到10.0.0.0/24的路由 → 路由缺失

# 3. 检查防火墙
sudo iptables -L -n | grep 10.0.0.101
# 如果有DROP规则 → 防火墙阻断了

# 4. 用mtr持续探测
mtr 10.0.0.101 -r -c 20
# 可以精确定位丢包发生在哪一跳
```

### 10.6 链路层排查

**如果以上都正常，但问题仍然存在**，排查方向转到链路层：

```bash
# 1. 检查网卡状态
ethtool eth0 | grep -E "Speed|Duplex|Link"
# Speed: 1000Mb/s  ✅
# Duplex: Full      ✅
# Link detected: yes ✅

# 2. 检查网卡错误计数
ethtool -S eth0 | grep -i error
# rx_errors: 12547  ← 接收错误很多！
# → 可能是网线质量问题或交换机端口故障

# 3. 检查ARP
arp -a | grep 10.0.0.101
# 如果IP对应的MAC是(incomplete) → ARP解析失败
# 可能是同一网段有IP冲突
```

### 10.7 排查全景总结

```text
小林完成排查后整理的问题分析：

问题现象：    网站打不开，返回502
直接原因：    Tomcat OOM，进程卡在GC无法响应
根本原因：    爬虫疯狂请求导出接口，每次创建大对象导致堆溢出
触发条件：    凌晨爬虫集中扫描 + 导出接口没有做限制
解决方案：    Nginx限流 + 爬虫IP黑名单 + 导出接口异步化 + JVM参数优化

排查路径回顾（自顶向下）：
  L7 应用层： curl → 502 → 问题在上游
  L4 传输层： telnet → Connection refused → 端口不监听
             netstat → 无LISTEN → 进程异常
             SSH → 日志 → OOM
  L3 网络层： ping → 正常（本次排查中网络层没问题）
  L2 链路层： 无需排查

排查工具箱：
  应用层   → curl, Chrome DevTools
  传输层   → telnet, nc, netstat, tcpdump, Wireshark
  网络层   → ping, traceroute, mtr, ip route
  链路层   → arp, ethtool, tcpdump -e
```

```text
"遇到网络问题第一件事做什么？"

不是敲命令，而是先做一件事：缩小范围。

1. 是自己打不开还是所有人都打不开？
   → curl/cron监控 → 所有人打不开 = 服务端问题

2. 是哪个服务/接口出问题？
   → 日志+curl逐个接口测试 → 定位到具体接口

3. 是整个服务都慢，还是特定操作慢？
   → 接口粒度 → 定位到具体操作

4. 是什么时候开始出的问题？
   → 日志时间+版本发布时间 → 关联到变更

范围缩小后，再按OSI模型自顶向下逐层使用工具排查。
```

**最终的方法论沉淀**——排查网络故障时，都应该问自己三个问题：

1. **范围缩小了吗？**（是全局还是局部？哪个接口？什么时间开始的？→ 不盲目排查）
2. **层次清楚了吗？**（应用层→传输层→网络层→链路层，各用各的工具 → 不混用工具）

## 11.思考题与作业

### 11.1 基础思考题

1. **Ping vs Telnet**：`ping 10.0.0.1` 能通但 `telnet 10.0.0.1 80` 不通，可能的原因有哪些？（至少列举3种）

2. **502 vs 504**：Nginx 返回 502 和 504 分别代表什么？排查方向有什么不同？

3. **traceroute 星号之谜**：`traceroute` 输出中从某跳开始全是 `* * *`，说明什么？加 `-I` 参数又正常了，说明什么？

4. **工具分层**：将以下工具填入正确的 OSI 层次：`ping`、`telnet`、`curl`、`tcpdump`、`arp`、`traceroute`、`ethtool`。

### 11.2 进阶思考题

1. **CLOSE_WAIT 堆积排查**：`netstat -ant | grep CLOSE_WAIT | wc -l` 返回 500+。这是什么问题？如何找到是哪个服务没有正确关闭连接？和之前哪篇文章的知识点关联？

2. **TIME_WAIT 的排查思路**：`netstat -ant | grep TIME_WAIT | wc -l` 返回 30000+。这是正常的还是不正常的？如何判断是否需要优化？优化手段有哪些？

3. **TCP重传的定量分析**：`netstat -s` 显示 1000 万次重传。如何判断这个数值是否正常？如何用 tcpdump 抓包并精确定位是哪个连接在重传？重传的主要原因有哪些？

4. **跨层排查的陷阱**：为什么网络工程师经常说"ping通了不代表网络就没问题"？请举出一个 ping 通但应用层出问题的具体例子（不是防火墙屏蔽端口），并给出排查方法。
