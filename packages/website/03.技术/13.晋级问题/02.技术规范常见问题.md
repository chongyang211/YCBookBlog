# 1.代码与协作规范

### 代码规范怎么定才能落地不走形式？

答：一句话，**风格靠工具强制，质量靠流程闭环，永远不要靠口头约定**。

先分层：代码规范分「风格规范」和「质量规范」两种，落地方式完全不同。风格类（缩进、命名、格式）交给 lint 工具自动执行，提交时格式化卡点，机器能拦的绝不靠人；质量类（逻辑、设计、测试）走 Code Review 流程。

CR 不走形式的三个关键：

1. **MR 控制粒度**：小批量提交，一次评审二百行以内，太大了没人看得细；
2. **明确评审标准**：清单化（正确性、测试、命名、边界），没有标准就没有判断依据；
3. **要有反馈机制**：定期抽查评审质量，评审意见被采纳的情况反过来考核评审人。

我踩过的坑：早期团队定了规范文档发群里，三个月后没人记得内容。后来全部工具化，规范从「文档」变成「流水线的卡点」，才算真正落地。

总结：**能写成工具的不要写成流程，能写成流程的不要写成口头约定**。

> 面试官追问点：CR 效率低、团队抱怨评审等太久怎么办？应答思路：小 MR、评审 SLA（24 小时内响应）、评审人轮值分担。

### 分支模型怎么选？发布流程怎么管？

答：分支模型一句话：**小团队主干开发，多团队并行用 GitFlow**，没有银弹只有适配。

发布流程我守三条铁律：

1. **提交信息规范化**：feat/fix/refactor 前缀，保证历史可追溯，出问题能按类型回查；
2. **发布必走预发环境**：预发通过才上生产，杜绝「本地跑通直接上线」；
3. **发布必须有回滚预案**：上线前先验证回滚路径通不通，回不了的发布不许发。

最核心的一条红线：**禁止任何人不走流程直接改线上**。这条规矩必须由 Leader 亲自守住，我带团队时见过资深工程师图快直接改线上配置导致故障，处理那次事件之后这条红线才真正立起来。

总结：**发布流程的每一道关卡，都是历史上某次事故换来的**。

> 面试官追问点：紧急修复也要走完整流程吗？应答思路：紧急通道可以有但更严格（双人复核加事后复盘），简化审批不等于跳过验证。

### 团队的命名规范应该怎么治理？

答：命名的治理原则：**建立团队术语表，新代码立即执行，老代码随改随修**。

命名看着是小事，实际是代码可读性的根基。我的做法分三步：

1. **建术语表**：把业务域的核心概念统一命名（订单到底叫 order 还是 trade，用户叫 user 还是 member），一个概念一个词，全库统一；
2. **分层约定**：项目名、模块名、类名、函数名各定规则，见名知意优先于简洁；
3. **渐进治理**：中英文混用和拼音命名的存量代码，改到哪个模块顺手修哪个，不搞专项运动。

治理的关键认知：**命名不一致的代价比想象中大**，同一个概念三个名字，新人和跨模块协作的人每次都要做心智翻译。

总结：**术语表是团队沟通的协议，协议不统一，协作成本永远降不下来**。

> 面试官追问点：团队有人就是不遵守命名约定怎么办？应答思路：CR 卡点拦截，同时反思约定本身是否合理（过于苛刻的规则该修订）。

### 第三方库的引入应该怎么管理？

答：核心机制是**引入评审 + 版本锁定 + 禁止私改源码**，三条缺一不可。

我踩过的真实教训：团队成员随手引了个不再维护的三方库，两年后爆出安全漏洞，全站被迫紧急排查替换。从那以后我们建了引入评审机制：

1. **评审三看**：看维护活跃度（多久没更新了）、看许可证（商用合规）、看体积和依赖树（别引个小功能带进来一串传递依赖）；
2. **版本锁定与升级窗口**：版本锁死在配置文件，升级集中做（统一窗口评估破坏性变更），不允许悄悄升版本；
3. **禁止私拉 fork 和拷贝源码**：改了源码的依赖等于失联资产，安全补丁进不来，自己还不知道改过什么。

总结：**依赖是资产也是负债，引入的那一刻就要想好退出成本**。

> 面试官追问点：评审流程会不会拖慢开发效率？应答思路：轻量评审（半天内出结论）加白名单机制（成熟库免审），平衡效率与风险。

# 2.文档与接口规范

### 哪些文档必须写？写多少才合适？

答：四类必写：**架构设计、接口定义、事故复盘、新人上手指南**；原则是够用就好，**避免文档的形式主义**。

为什么是这四类：架构设计防止系统演进失控，接口定义是跨团队协作的契约，事故复盘是组织的记忆，上手指南决定新人产能爬坡速度。这四类缺失的代价都是真金白银。

写多少合适的判断标准：**文档的维护成本要低于没有它的沟通成本**。我在早期犯过形式主义的错误：要求每个需求都写详细设计文档，结果文档应付了事没人看。后来改成按需求风险分级，核心链路全量文档、一般需求评审纪要、小改动代码即文档，团队负担小了文档反而更准。

保持更新的机制：**把文档检查绑定进流程**，发布前检查接口文档是否同步、复盘会后文档必须归档。

总结：**文档不是写得越多越专业，是写得越准越有价值**。

> 面试官追问点：怎么发现文档已经过期了？应答思路：定期抽查加流程卡点（发布时核对），过期文档比没有文档更害人。

### 接口规范应该怎么定义和维护？

答：接口规范的核心是**版本管理遵守兼容原则：只增不改不删**，这是跨团队协作的生命线。

具体约定四个方面：

1. **风格约定**：RESTful 与 RPC 各自的规范（资源命名、错误码、分页格式），团队内统一，不混搭；
2. **版本兼容**：字段只允许新增、不允许修改语义、不允许删除，废弃字段先标记 deprecated 给迁移期；
3. **错误码统一**：全局错误码表集中管理，每个码有唯一含义，不能各家自定义各家的；
4. **文档与 mock 同步**：接口文档和 mock 服务同源维护，调用方联调不等后端进度。

我对接口兼容性有个深刻记忆：一次上游悄悄改了字段含义，下游没感知，数据静默错误了两周才被发现。那次之后「只增不改不删」成了不可谈判的红线。

总结：**接口是团队之间的合同，改合同可以，单方面撕毁不行**。

> 面试官追问点：真的必须做破坏性变更怎么办？应答思路：提前通知、双版本并行过渡、给明确的下线时间表。

### 接口上线前要评审哪些内容？

答：我有一份**评审清单六问**：命名、幂等、分页、超时、限流、降级，一项一项过。

1. **命名**：符合团队约定，语义清晰无歧义；
2. **幂等**：写接口必须明确幂等策略，重试会不会造成重复数据；
3. **分页**：列表接口必须有分页和上限，防止全量查询拖垮服务；
4. **超时**：调用方超时怎么设，你的接口最坏耗时多少，要匹配；
5. **限流**：接口的容量预估和限流阈值，防突发流量；
6. **降级**：依赖的下游挂了，这个接口返回什么，兜底策略是什么。

评审的产出物：**破坏性变更必须通报所有调用方并留迁移期**，不能让调用方踩坑后才发现。

总结：**接口评审评的不是代码写得好不好，是这个接口放到生产环境后坏不坏得起**。

> 面试官追问点：评审会变成走过场怎么办？应答思路：清单化评审（勾选式）降低评审成本，高危接口（资金、核心链路）升级为专项评审。

# 3.数据与安全规范

### 数据库规范应该怎么落地执行？

答：四个抓手：**建表规范、变更流程、慢查询治理、索引审查**，靠工具和流程双重把关。

1. **建表规范**：命名统一、必有字段（创建时间、更新时间、软删除标记），这些约定进建表模板，从源头统一；
2. **大表变更走流程**：DDL 评审加低峰执行，线上大表的 ALTER 可能锁表几小时，必须评审影响范围、分批执行；
3. **慢查询治理定目标**：慢查询监控开着，每周治理清零，不设目标的规范等于没有规范；
4. **索引规范审查与工具并行**：人工评审看设计合理性，工具扫描（如未走索引的 SQL）兜底。

我的一个体感：数据库规范是所有规范里**最值得花力气落地的**，因为数据库出问题的影响面和恢复难度都是最高的。

总结：**代码写错了可以回滚，数据搞坏了可能救不回来，数据库规范要按最坏情况设防**。

> 面试官追问点：开发抱怨 DDL 评审太慢耽误进度怎么办？应答思路：评审时效承诺（当天出结论）加自动化预检查（工具先筛掉低风险变更）。

### 敏感数据应该怎么分级管理？

答：敏感数据管理三个关键词：**分级、脱敏、留痕**。

1. **分级**：数据按敏感度分公开、内部、机密三级，不同级别不同管控强度，不分级的管控要么过严要么漏放；
2. **脱敏**：测试环境禁止用生产真实数据，必须有脱敏方案（手机号、身份证、姓名打码或伪造），导出数据默认脱敏；
3. **留痕**：敏感数据的查询和导出走审批加记录，谁在什么时候查了什么，事后可审计。

一个底线认知：**数据泄露和代码事故不一样，代码事故损失一次，数据泄露摧毁信任**。用户把数据交给你是基于信任，这个信任的维护成本必须付。

总结：**敏感数据的管控不是效率问题，是能不能活下去的问题**。

> 面试官追问点：脱敏会不会影响测试有效性？应答思路：脱敏保格式保逻辑（保留数据特征和分布），只换真实值，测试有效性不受影响。

### 安全规范至少要包含哪些内容？

答：安全规范的底线四件套：**密钥管理、权限最小化、数据脱敏、上线前扫描**。

1. **密钥管理**：密钥放环境变量或密钥平台，**禁止硬编码进代码和配置仓库**，这是最常见也最低级的安全事故来源；
2. **权限最小化**：每个人、每个服务只拥有完成工作所需的最小权限，宁可麻烦一点，不留冗余授权；
3. **敏感数据脱敏**：日志和报错信息里的敏感字段自动脱敏，防止密钥和用户数据被打进日志；
4. **上线前安全扫描**：SAST 静态扫描加 DAST 动态扫描进流水线，高危漏洞卡点拦截。

我对安全的核心认知：**安全不是概率问题，是必然问题**，你不设防，被打只是时间问题。

总结：**安全规范的每一分钟投入，都是在为「不存在的安全事故」付费，这笔钱不能省**。

> 面试官追问点：安全规范和开发效率冲突时怎么选？应答思路：安全红线不可妥协，但可以用工具（自动扫描）降低人的遵守成本。

# 4.线上纪律

### 值班和线上纪律应该怎么定？

答：四个机制：**变更窗口、oncall 轮值、报警 SLA、事故分级升级**，目标是让线上问题「有人管、按时管、按级管」。

1. **变更窗口**：约定什么时段允许变更（避开业务高峰），封网期（大促前后）冻结一切非紧急变更；
2. **oncall 轮值**：值班表排班到人、替补明确，值班的人保持响应能力（不安排出差和重要会议）；
3. **报警响应 SLA**：多严重的告警必须多快响应，写清楚超时升级路径；
4. **事故分级**：P0 到 P3 各级的响应流程和通报范围，别所有问题都靠喊。

要坚决杜绝的一种文化：**「改一下就上线」**。哪怕改一行配置也要走验证，因为线上没有小改动。

总结：**线上纪律的本质是把「应对线上问题」从英雄行为变成流程行为**。

> 面试官追问点：值班的人消极怠工、报警不响应怎么办？应答思路：值班响应进考核，升级机制自动兜底（超时自动升级到上级）。

### 线上变更的三板斧机制是什么？

答：变更三板斧：**可灰度、可监控、可回滚**，任何线上变更必须能回答这三个问题，答不出就不许执行。

1. **可灰度**：变更先放小流量，验证无异常再逐步放大，控制爆炸半径；
2. **可监控**：变更后核心指标盯三十分钟才许离场，出了问题第一时间能发现是这次变更引起的；
3. **可回滚**：上线前先验证回滚路径，回滚方案和上线方案同时准备。

为什么变更这么重要：**80% 的线上故障来自变更**，系统不会自己坏，是人把它改坏的。管住了变更就管住了大部分故障来源。

我们落地的方式：变更单里强制填三个问题（灰度计划、监控指标、回滚步骤），填不全的变更单直接打回。

总结：**三板斧不是形式，是用三个问题把拍脑袋式发布拦在门外**。

> 面试官追问点：数据库变更这种没法灰度的怎么办？应答思路：影子验证（先在备份库跑）、双写过渡、分批执行，等效于灰度。

### 生产环境的权限应该怎么治理？

答：权限治理原则：**最小化、可审批、可追溯**，高危操作双重确认。

1. **最小化**：日常不给生产写权限，需要时临时申请（有审批、有时效），用完自动回收；
2. **双人复核**：删表、清缓存、强制重启这类高危操作，必须第二个人确认才能执行，一个人说了不算；
3. **操作留痕**：所有生产操作走跳板机或操作平台，命令级留档，事后可审计。

我坚持这条的底气来自一个观察：**很多大事故不是黑客干的，是自己的工程师在深夜一个人操作数据库删错了表**。双人复核麻烦，但它拦住的是最贵的那类事故。

总结：**权限治理的本质是让「想犯错」变成「犯不了错」，而不是寄希望于「没人想犯错」**。

> 面试官追问点：紧急故障处理时走审批来不及怎么办？应答思路：紧急通道（break glass）机制，先放行但事后强制复盘留档，权限审计看的是异常率不是流程完备率。

# 5.规范落地方法论

### 规范为什么难落地？怎么破局？

答：规范难落地的根因：**规范是反人性的约束，靠自觉必然失败**。破局靠四层递进：**工具自动化、流程卡点、人工审查、口头约定**，越靠前越可靠。

落地方法论：

1. **能工具化的全部工具化**：lint、扫描、流水线卡点，机器执行没有折扣；
2. **工具管不了的用流程卡点**：评审、审批节点卡在关键路径上，绕不过去；
3. **流程覆盖不到的靠人工审查**：定期抽查、复盘纠偏；
4. **口头约定只作为补充**：文化宣导辅助，绝不作为主要手段。

推行新规范的节奏：**先试点再推广**，找一个小组跑两个月，把问题暴露完、把方案打磨顺，再全量铺开，配套迁移方案和时间表。

我见过最多失败的案例：Leader 在群里发个规范文档宣布下周一执行，没有工具没有过渡，一个月后名存实亡。

总结：**规范的执行力等于工具化程度，写给人看的规范不如写给机器执行的规则**。

> 面试官追问点：试点小组不听劝、试点失败怎么办？应答思路：试点失败是低成本试错，复盘修订规范本身（可能是规范不合理不是人不配合）。

### 规范松紧的度应该怎么把握？

答：我的分层原则：**底线规范强约束，风格规范弱引导**。

1. **底线规范零容忍**：安全红线、变更三板斧、权限治理这些关乎生存的规则，违反必究，没有例外；
2. **风格规范靠工具引导**：代码风格、命名偏好这类，lint 自动处理或 CR 建议即可，不值得上纲上线。

判断一个规范该松该紧的标准：**违反它的代价是不是团队和个人能承受的**。删库和缩进不一致，显然不是一个量级的事。

过度规范的代价我亲身体会过：一个团队流程卡点多到改一行代码要过五道审批，最后大家学会了「绕过流程」的野路子，规范没管住人，反而管丢了信任。

总结：**规范的目的是降低系统风险，不是展示管理权威，管得越多不代表管得越好**。

> 面试官追问点：怎么判断一条规范已经过时该废除了？应答思路：看违反它的实际代价是否还在（环境变了代价可能消失），定期评审废止。

### 规范要不要定期修订演进？

答：必须修订，**规范不是刻在石头上的法律，是随系统演化的活文档**。

我的机制三条：

1. **每季度评审**：过一遍现有规范，废止过时条款（技术栈换了、团队规模变了，老规范可能已经不适用）；
2. **任何人可提修订建议**：一线开发者最有体感，他们的痛点就是规范的盲区，但修订必须走评审，避免规范变成个人偏好；
3. **修订留痕**：为什么改、什么时候改的，记录在案，后来的新人才能理解规则背后的原因。

一个反常识的认知：**没人违反的规范不一定是好规范，可能是它已经没人看了**。定期修订就是让规范保持「被需要」的状态。

总结：**好规范是被反复使用和修订的规范，一次定终身的规范很快会变成墙上的装饰品**。

> 面试官追问点：修订太频繁导致团队无所适从怎么办？应答思路：区分条款稳定性（底线条款不动、操作条款可调），修订有公示期和生效缓冲期。
