# 1.疑难问题排查

- **问：线上出问题，你的排查框架是什么？**
  答：先止血再定位——回滚/降级/扩容优先；再用监控与日志缩小范围（分层定位：网络→应用→数据库→依赖）；最后根因分析，避免「哪里痛医哪里」。

- **问：偶现的低概率问题怎么查？**
  答：先补全日志与链路追踪、保存现场 dump；再想办法提高复现概率——流量回放、压力放大、场景穷举；不能复现的问题靠增加观测逼近。

- **问：出问题才发现日志不够，怎么办？**
  答：事前布好关键路径日志清单——入口、外部调用、状态变更、异常分支；日志等级与脱敏平衡，出问题时日志要能回答「发生了什么」。

- **问：你的排查工具箱有什么？**
  答：Arthas 在线诊断、tcpdump/Wireshark 抓包、perf/火焰图找热点、线程与内存 dump 分析；关键是知道什么问题用什么工具。

# 2.性能与高并发

- **问：性能优化的方法论是什么？**
  答：先测量再优化（profile 找瓶颈），避免直觉优化；手段按优先级——缓存、异步、批处理、索引、算法优化、资源池化；优化后用基准测试与线上对比验证效果。

- **问：秒杀/抢购系统怎么设计？**
  答：削峰（MQ 排队）、限流（网关+服务层双层）、库存预扣（Redis 预扣防超卖）、热点隔离（独立部署防拖垮主站）；再加缓存三大问题（穿透/击穿/雪崩）的对策与分布式锁选型。

- **问：全链路压测怎么做？**
  答：流量染色标记压测请求、影子库隔离数据风险；从压测数据推算容量（安全水位、扩容阈值）；大促保障出 checklist，逐项演练核对。

# 3.数据与存储

- **问：分布式事务方案怎么选？**
  答：对比 2PC/TCC/本地消息表/最终一致——强一致用 2PC（性能差）、高并发用 TCC（侵入强）、一般场景用本地消息表+最终一致；配合幂等性保障与对账机制兜底。

- **问：慢查询治理的标准动作是什么？**
  答：慢日志找 SQL → 执行计划分析 → 索引优化；大表考虑分库分表（分片键选择、跨片查询方案、数据迁移）；冷热分离与归档降低在线表规模。

- **问：不停机数据迁移怎么做？**
  答：双写（新旧同步写）→ 灰度切读（逐步把读切到新库）→ 数据校验（全量比对+增量比对+抽样核对）→ 停写旧库；每一步都要有回滚设计。

# 4.重构与迁移

- **问：大规模重构的策略是什么？**
  答：用绞杀者模式渐进替换而非推倒重来——新功能走新系统、旧功能逐步迁移；数据迁移用双写与回滚设计；老系统平滑下线分步骤执行。

- **问：接手一个没文档没人懂的老系统怎么办？**
  答：先补监控再动代码（看得见才敢改）；画依赖图理清边界；找还懂的老人做访谈；改动前用测试兜底，小步提交。

- **问：框架/语言大版本升级怎么搞？**
  答：先评估收益值不值；做兼容层降低切换成本；灰度迁移+新旧双跑验证；升级期间业务并行靠流量切换保障，随时可回退。

# 5.攻坚组织与复盘

- **问：遇到难题怎么组织攻坚？**
  答：组建小队突击、设定时间盒、每日站会同步进展；向管理层同步风险与进展要坦诚；设止损点，攻不下来及时换方案而不是无限投入。

- **问：事故复盘怎么开才有效？**
  答：原则对事不对人、不追责只求改进；模板覆盖时间线、影响面、根因、改进项；改进项必须闭环——有负责人、有截止时间、有回头看检查。

- **问：一个故障修完，怎么避免同类问题再发？**
  答：举一反三——从单点扫描到面（同类风险批量治理）；沉淀安全基线并文档化；把故障变成案例库与演练素材，让每次故障的价值最大化。

- **问：怎么从「救火」走向「防火」？**
  答：事后救火转向事前预防——变更管控、故障注入演练、人因风险四道防线；用故障次数与恢复时长的趋势数据向管理层证明防火投入的产出。
