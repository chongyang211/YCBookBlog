# 1.疑难问题排查

### 线上出问题的排查框架是什么？

答：我的框架六个字：**先止血，再定位**。

止血的动作优先级：最近有变更先回滚（变更覆盖了八成故障来源）、能降级先降级、容量不够先扩容。**业务恢复永远优先于找根因，用户不关心 root cause，只关心服务什么时候恢复**。

定位阶段用分层法：看监控大盘确定影响面，顺着链路追踪从入口往下钻，按「网络、应用、数据库、依赖」的层次缩小范围，避免「哪里痛医哪里」的局部视角。

最后是根因确认和复盘：确认了根因不算完，还要回答两个问题：**为什么监控没有更早发现、为什么变更流程没有拦住**，把堵点补上才算闭环。

一个经验之谈：排查最忌讳的是全员扑上去「查问题」却没人拍板「先回滚」。

总结：**止血是命令，定位是推理，复盘是升华，三步的节奏感比技术细节更考验人**。

> 面试官追问点：怎么判断该止血还是该继续定位？应答思路：影响面和恢复成本的对比，影响大且止血代价小（回滚）就先止血，止血代价大（数据已脏）才边定位边处理。

### 偶现的低概率问题怎么排查？

答：偶现问题的思路：**提高复现概率加全观测逼近，不能等它自己出现**。

具体三招：

1. **补全观测**：日志埋点加密（关键路径全覆盖）、链路追踪开着、出问题时的现场自动保存（线程 dump、内存快照），先保证下次出现时能抓到证据；
2. **提高复现概率**：流量回放（把生产流量放大打到测试环境）、压力放大（并发数拉高让低概率事件高频化）、场景穷举（把所有条件组合列出来逐一验证）；
3. **条件假设验证**：根据仅有的线索列假设（并发？时序？特定数据特征？），写针对性的验证用例逐个排除。

我处理过一个经典案例：万分之一概率的超时，最后发现是连接池耗尽时偶发的获取超时，靠的是全量日志加长时间压测才复现。

一个心态提醒：偶现问题最消耗团队士气，**要给排查设定时间盒**，超时就转「加强观测等下次」，不能无底洞投入。

总结：**偶现问题的本质是信息不足，破解思路就是「让它再发生一次，且这次留下证据」**。

> 面试官追问点：一直无法复现的问题怎么收尾？应答思路：观测加固加防御性修复（可疑点都加上保护），带着监控上线，诚实同步风险。

### 线上 CPU 飙高怎么排查定位？

答：CPU 飙高的排查有标准四步：**找进程、找线程、找代码、找原因**。

1. **找进程**：top 看是哪个进程吃 CPU，先确认是不是我们的服务（也可能是宿主机上别的进程或系统进程）；
2. **找线程**：top -Hp [pid] 看进程内哪个线程飙高，拿到线程号；Java 服务用 jstack 前先 top -Hp 转十六进制线程号；
3. **找代码**：把线程号转十六进制后去 jstack 输出里 grep，直接定位到正在执行的代码行；非 JVM 服务用 perf top 看热点函数；
4. **找原因**：根据代码场景判断，常见三类：**死循环或循环退出条件错了、频繁 GC（GC 线程占用 CPU，要配合 jstat 看 GC 频率）、正则回溯或序列化这类 CPU 密集操作**。

加一层判断力：**us 高是业务代码问题，sy 高是系统调用频繁（锁竞争、线程切换），wa 高是 IO 等待**，三种高的解法完全不同。

我处理过的真实案例：CPU 100%，jstack 定位到一个正则表达式，特定输入触灾难性回溯，修复正则后恢复。

总结：**CPU 飙高排查的本质是把「进程级现象」逐级下钻到「代码行级原因」，工具链是固定的，难在下钻的方向判断**。

> 面试官追问点：CPU 飙高但服务还能响应，要不要马上重启？应答思路：先抓现场（dump 和 top 数据）再处置，重启会让证据消失，下次还得从头查。

### 内存泄漏应该怎么定位解决？

答：内存泄漏定位的核心逻辑：**用两份快照的差集，找出「只进不出」的对象**。

定位步骤：

1. **确认是泄漏不是流量**：内存持续上涨且流量没有对应增长、GC 后不回落，才是泄漏；流量涨内存涨是正常的；
2. **抓两份快照**：间隔一段业务时间（比如一小时）抓两次堆 dump（jmap 或 arthas heapdump）；
3. **差集分析**：用 MAT 或 JProfiler 对比两份快照，找**数量持续增长且 GC 后仍存活**的对象类型；
4. **追溯引用链**：MAT 的 Leak Suspects 或引用树，看是谁持有这些对象（哪个静态集合、哪个缓存、哪个 ThreadLocal）。

常见泄漏源清单：**静态集合只加不减、ThreadLocal 没 remove（线程池场景必漏）、监听器和回调没注销、本地缓存无淘汰策略、类加载器泄漏**。

修复原则：找到持有点，改成有界（加上限加淘汰）或及时释放（finally 里清理）。

总结：**内存泄漏的排查就是「证明确实泄漏、找到泄漏对象、定位持有点」三段论，工具是次要的，持有链的分析能力是主要的**。

> 面试官追问点：堆 dump 会导致服务停顿，生产环境怎么抓？应答思路：摘掉一台流量再 dump，或用低暂停的采样方式（arthas 的异步采集）。

### 出问题时才发现日志不够怎么办？

答：事后的补救加事前的补课，两手都要做。

当下的补救：**能加的日志立刻加版本上**（下次出现就能抓到）、从别的信息源拼现场（监控指标、链路追踪、变更记录、用户反馈的时间点）、用流量回放在测试环境复现。

事前的补课是根本，我有一份**关键路径日志埋点清单**：

1. **入口**：请求进来记什么接口、什么参数（脱敏后）；
2. **外部调用**：调下游前后的入参出参、耗时、成功失败；
3. **状态变更**：关键业务状态翻转的上下文；
4. **异常分支**：catch 块里必须留档，吞异常是排查的大敌。

日志的度：**等级和脱敏要平衡**，info 记主干、debug 记细节（生产默认关）、error 记需要人处理的，敏感字段一律脱敏（这也是安全规范的要求）。

总结：**日志是排查的燃料，出事时才想起加油已经晚了，埋点清单要长在开发流程里**。

> 面试官追问点：日志加太多影响性能怎么办？应答思路：异步日志加采样策略（高频日志抽样），核心路径不省，边缘路径可采。

### 你的疑难排查工具箱有什么？

答：我的工具箱按「问题类型」组织，**关键是知道什么问题用什么工具，而不是工具本身多全**。

1. **CPU 类**：top（找进程线程）、jstack（线程栈）、perf（火焰图看热点）；
2. **内存类**：jmap（堆快照）、MAT（泄漏分析）、arthas（在线诊断，不断服务）；
3. **网络类**：tcpdump/Wireshark（抓包看协议层）、ss/netstat（连接状态）、telnet/curl（连通性验证）；
4. **链路类**：分布式追踪系统（全链路耗时分布）、日志平台（多机日志聚合检索）；
5. **系统类**：iostat/vmstat（IO 和内存换页）、pidstat（进程级资源）、dmesg（系统层异常，比如 OOM 被杀）。

工具箱之上是**使用顺序的方法论**：先无损的（监控、日志、追踪在线看），再有损的（dump、抓包有性能代价），最后才是侵入的（重启、下线）。**先看后动，证据优先**。

总结：**工具人人会搜，排查老手的差距在于「什么信号指向什么工具」的映射速度**。

> 面试官追问点：arthas 和 jstack 比优势在哪？应答思路：在线诊断不重启、实时 watch 方法出入参、热更新排查逻辑，适合不能停的生产服务。

# 2.性能与高并发

### 性能优化的方法论是什么？

答：方法论一句话：**先测量再优化，找到瓶颈再动手，用数据验证效果**，直觉优化是性能工作最大的浪费。

标准流程四步：

1. **建立基线**：优化前的耗时分布（P50/P99）、吞吐量、资源占用，没有基线就无法证明优化有效；
2. **定位瓶颈**：profile 找热点（CPU 火焰图、慢 SQL 榜单、IO 等待分布），二八法则，八成耗时集中在两成代码；
3. **按优先级下药**：手段按性价比排序：**缓存**（命中率高的读）、**异步**（不阻塞主流程的）、**批处理**（N 次变 1 次）、**索引**（数据库的第一反应）、**算法优化**（数量级改善）、**资源池化**（复用贵的资源）；
4. **对比验证**：优化后同口径压测，基准对比，确认收益且无副作用。

一个真实教训：我早年凭直觉优化了一个「看起来慢」的循环，费了两天效果甚微，后来 profile 发现 95% 耗时在数据库往返。**直觉会说谎，火焰图不会**。

总结：**性能优化是数据驱动的工程，不是灵感驱动的手艺**。

> 面试官追问点：优化到什么程度算够？应答思路：看目标（SLO 达标就停）和边际收益（下一档优化成本翻倍收益减半就停），过度优化是浪费。

### 秒杀抢购系统怎么设计？

答：秒杀设计的核心思想：**层层设防把流量漏斗化，让数据库永远只见到它扛得住的量**。

四层防线：

1. **前端与网关削峰**：按钮防抖、答题或验证码错峰、静态资源 CDN 化，页面能挡掉的请求最便宜；
2. **限流分层**：网关限流（总量控制）加服务限流（单机保护），超出容量的请求快速失败返回「已抢完」，**排队九秒失败，好过全体卡死三十秒**；
3. **库存预扣**：库存放 Redis 预扣（decr 原子操作防超卖），扣完直接拒绝，请求根本不碰数据库；
4. **热点隔离**：秒杀服务独立部署，挂了不连累主站；下单走 MQ 异步削峰，数据库按自己的节奏消费。

再加缓存三大问题的对策：**穿透用空值缓存、击穿用互斥锁重建、雪崩用过期时间加随机**。

配套的分布式锁注意点：锁要带超时和续期，防止死锁加业务校验防误删。

总结：**秒杀的本质是「用层层过滤换数据库的苟活」，每一层都在问：这个请求能不能在更便宜的地方被拒掉**。

> 面试官追问点：Redis 扣库存和数据库最终一致性怎么保证？应答思路：Redis 预扣成功发 MQ，数据库消费扣减，失败进补偿队列人工或自动对账。

### 全链路压测应该怎么做？

答：全链路压测四个关键动作：**流量染色、数据隔离、容量推算、风险预案**。

1. **流量染色**：压测请求打上标记，全链路透传，下游据此识别（日志隔离、不触达真实外部依赖如短信支付）；
2. **数据隔离**：影子表或影子库存压测数据，压测流量写影子存储，**绝不能污染生产数据**；
3. **容量推算**：从压测数据摸水位线（安全水位、扩容水位、红线水位），大促容量等于预估峰值乘以冗余系数（一般 1.5），反推要扩容多少台；
4. **风险预案**：压测本身有风险（把生产压挂了），压测前要有熔断条件（错误率超阈值自动停）、回滚预案和应急值班表。

落地节奏：先单接口压测摸单点容量，再链路级压测找瓶颈传导，最后大促前的全链路演练。

压测的价值不止于容量数字：**很多隐性瓶颈（连接池配置小、慢 SQL 被放大）都是压测暴露的，比线上大促当天发现便宜太多**。

总结：**全链路压测是把「大促当天的不确定性」换成「压测当天的可控性」，是花小钱买确定性**。

> 面试官追问点：压测和生产流量互相影响怎么办？应答思路：低峰期压测、压测流量限上限、染色隔离，实时盯生产指标异常即停。

# 3.数据与存储

### 分布式事务的方案怎么选？

答：选型原则一句话：**按一致性要求和并发量选，能最终一致就别上强一致**。

方案对比：

1. **2PC/XA**：强一致但性能差（同步阻塞、协调者单点），传统数据库间事务，互联网高并发场景基本不用；
2. **TCC**：业务层面的两阶段（Try 预留资源、Confirm 确认、Cancel 释放），性能好但侵入强（每个参与方要写三个接口），适合资金类核心链路；
3. **本地消息表**：业务操作和消息记录在同一个本地事务，异步投递保证最终一致，实现简单可靠，**多数场景的首选**；
4. **事务消息**（RocketMQ）：等价于本地消息表但中间件代劳，少写表但依赖 MQ 的可靠性。

无论选哪个，两个配套不能少：**幂等性**（重试必达的设计，没有幂等一切重试都是灾难）和**对账机制**（兜底扫描，不一致的自动修复或人工介入）。

我的实战倾向：**生活缴费、积分这类允许秒级延迟的，本地消息表加对账；账户扣款这种强一致要求的，TCC 加幂等**。

总结：**分布式事务没有免费午餐，一致性和可用性总要牺牲一头，选型就是认清自己业务能牺牲哪头**。

> 面试官追问点：本地消息表的消息投递失败怎么办？应答思路：定时任务扫描重投加指数退避，投递有幂等去重，末端对账兜底。

### 慢查询治理的标准动作是什么？

答：慢查询治理五步标准动作：**开慢日志、看执行计划、加索引、改写法、治大表**。

1. **开慢日志**：long_query_time 设阈值（比如 500 毫秒），监控大盘周维度看趋势，治理先有度量；
2. **看执行计划**：EXPLAIN 是基本功，重点看 type（ALL 全表扫要警惕）、rows（扫描行数）、key（走没走索引）；
3. **加索引**：按查询条件建联合索引，注意最左前缀原则；索引不是越多越好（写放大），冗余索引要清理；
4. **改写法**：索引救不了的改 SQL（子查询改 join、大 IN 改批量、select 指定字段）；应用层加缓存挡读压力；
5. **治大表**：单表几千万行后索引也救不了全部，分库分表（分片键选择要覆盖主流查询）、冷热分离（历史数据归档）、读写分离分流。

治理的组织方式：**每周慢查询清零机制**，本周新增的慢 SQL 必须有处理结论（修复、豁免说明或排期），不清零下周复盘。

总结：**慢查询治理不是一次性运动，是「发现、修复、防复发」的常态化循环，度量闭环是关键**。

> 面试官追问点：分库分表的分片键怎么选？应答思路：最高频的查询维度（比如用户 ID），跨片查询用冗余表或异构索引解决，避免为了一个低频查询广播全片。

### 不停机的数据迁移怎么做？

答：不停机迁移的套路四步：**双写、灰度切读、数据校验、停写收尾**，每步都要有回滚预案。

1. **双写阶段**：新旧库同时写，以旧库为准，新库写入失败只记日志不阻断业务；双写期间新库数据在追平；
2. **灰度切读**：读流量按比例从旧库切到新库（1% 到 10% 到 50% 到 100%），每一步观察对比（同请求双读比对结果），有问题立刻切回；
3. **数据校验**：全量比对（分批扫两库做 diff）加增量校验（迁移期间的变更对账）加抽样核对（业务层人工抽查），三层验证数据一致；
4. **停写收尾**：确认稳定后，选低峰期停旧库写（或切主），新库独立承担，观察一个完整业务周期后下线旧库。

回滚设计贯穿全程：**每个阶段都能退回上一步**，双写阶段可停双写，切读阶段可切回旧库，这是「不停机」承诺的底气。

我踩过的坑：切读后才发现新库的时区配置不对，时间字段差八小时。所以**校验不能只比条数，要抽样比对字段内容**。

总结：**不停机迁移的本质是「让新库在旧库的监护下逐步接班」，监护期越长越稳，但成本越高，节奏是艺术**。

> 面试官追问点：双写期间两库数据不一致怎么发现和修复？应答思路：对账程序定时 diff，不一致的按旧库为准修复新库，并查双写失败的日志找根因。

# 4.重构与迁移

### 大规模重构的策略是什么？

答：大规模重构首选**绞杀者模式：渐进替换，绝不推倒重来**。

推倒重写（Big Bang）的三个致命问题：周期内新旧并行成本翻倍、业务需求还在往老系统上加（重写永远追不上）、三年后上线的「新系统」已经又过时了。

绞杀者的打法：

1. **新功能全部走新系统**，老功能按「变更频率乘风险」排序，热点模块先迁；
2. **按接口逐步迁移**：老系统前面加一层路由（网关或适配层），把指定接口的流量切到新实现，灰度验证、可回切；
3. **数据迁移用双写加灰度切读**（参考前面那题的套路）；
4. **老系统平滑下线**：迁完一块下一块，最后老系统零流量再停机。

重构的前提保护：**迁移之前先给老系统补测试**（没有测试保护的迁移是蒙眼开车），测试是重构的安全网。

总结：**绞杀者的智慧是承认「一次性换心手术」风险太大，选择让新系统像器官移植一样逐步接管**。

> 面试官追问点：渐进迁移要多久，业务等得起吗？应答思路：给业务可见的节奏（每月迁移 N 个模块），让新系统尽早承接新需求产生价值，业务看到增量收益就愿意等。

### 接手没人懂的老系统怎么办？

答：接手老系统四步：**先监控、再摸底、后小改、留缓冲**。

1. **先补监控**：接手第一件事是给核心链路加监控和告警，**看得见才敢动**，黑盒系统里做任何修改都是赌博；
2. **摸底三件事**：画依赖图（谁调用它、它调用谁）、找还懂的老人做访谈（趁他们还在）、梳理核心业务逻辑入文档；
3. **改动小步走**：每次改动前先加测试兜底（针对要改的行为写测试再改）、提交粒度小、灰度发布，**老系统里大改动等于闭眼跳崖**；
4. **留缓冲**：老系统的排期要打富余，它的坑（隐含依赖、未知定时任务）会不断吃掉时间。

一个心态调整：**接手老系统不是接手烂摊子，是接手别人的历史决策**，那些「愚蠢的设计」往往有当时的历史背景，先理解再判断。

总结：**老系统的改造原则是「先透明化、再手术」，监控和测试是麻醉和消毒，跳过这两步直接开刀必出事故**。

> 面试官追问点：老板要求快速给老系统加新功能怎么办？应答思路：向老系统加功能可以但走「外挂模式」（新逻辑独立服务，老系统调它），不在老代码里深改。

### 框架的大版本升级怎么搞？

答：大版本升级四步：**评估收益、兼容层过渡、灰度迁移、双跑验证**。

1. **评估收益值不值**：新版本解决的是不是我们的实际痛点（性能？安全漏洞？新特性要用？），**为了升级而升级是纯成本**，列收益清单先说服自己；
2. **建兼容层**：把框架依赖收敛到中间层（我们自己的封装包），升级时只改兼容层不改业务代码，把升级成本从「改全站」降到「改一层」；
3. **灰度迁移**：按服务或模块分批升（边缘服务先升当炮灰），每批观察稳定期再推进下一批；
4. **双跑验证**：关键路径新旧版本并行跑（影子流量或按比例分流），对比行为一致性，确认无差异才全量切。

升级期间的**业务并行保障**：功能开发不停，但约定「升级窗口内的新功能必须兼容双版本」，避免升级和业务互相阻塞。

我经历的一次教训：跳了两个大版本直接升，中间版本的破坏性变更没吃透，踩了一周的坑。**跨版本升级要拆步**，一次一个版本。

总结：**大版本升级是「收益驱动的项目管理」而不是技术炫技，兼容层是护城河，灰度是安全绳**。

> 面试官追问点：升级过程中踩到框架 bug 怎么办？应答思路：定位是否阻塞性（阻塞则回退该批次并提 issue），非阻塞记入已知问题清单继续，升级节奏不因单点问题停摆。

# 5.攻坚组织与复盘

### 遇到难题怎么组织技术攻坚？

答：攻坚组织三件套：**小队突击、时间盒管理、止损点设置**。

1. **组建小队**：三到五人小队（一两个最懂这块的加一两个新鲜视角），**小队要专职**，兼职攻坚等于没有攻坚；授权要充分，日常事务为他们让路；
2. **时间盒管理**：攻坚设每日站会同步进展（只讲进展、卡点、需要的支持），短周期迭代（每两三天要有阶段性结论，证明在收敛）；
3. **止损点设置**：预设止损条件（超过一周没有任何收敛迹象就换路线），**攻不下来及时止损换方案，比死磕到底更需要勇气**。

对上的沟通：向管理层同步要坦诚，**进展和风险一起报**，「遇到困难但有三条备选路线」永远好过「一切正常」然后突然爆雷。

攻坚结束后：沉淀复盘（方案文档加经验教训），把攻坚的成果变成团队资产而不是个人荣誉。

总结：**攻坚管理的核心是「聚焦、透明、有退路」，小队专职是聚焦，每日站会是透明，止损点是退路**。

> 面试官追问点：攻坚成员怎么选？应答思路：领域熟手保深度加跨领域新手保视角，全是熟手容易思维定势，全是新手在基础知识上浪费攻坚时间。

### 事故复盘怎么开才有效？

答：有效复盘三原则：**对事不对人、改进项可执行、闭环追踪**。

会前准备：**时间线还原**（几点几分发生什么、谁做了什么操作、系统什么反应）先由当事人梳理成文，会上一分钟一分钟过，事实先于观点。

会中把控三条：

1. **只谈事实与时间线**：禁止「都怪谁」的句式，主持人把「为什么没做好」引导成「哪个环节的机制缺了」；
2. **改进项必须可执行**：每条有负责人、有截止时间，「大家以后小心点」这种不算改进项；
3. **根因挖到机制层**：连问几个为什么，从「人误操作」挖到「为什么误操作能生效」（权限、防呆、流程缺了什么），**人的失误背后都是系统的漏洞**。

会后闭环：**下次复盘先查上次的改进项**，没完成的当场解释，改进项不闭环的复盘会一次，团队就不信了。

一个立文化的动作：**从不处罚主动暴露问题的人，只处理隐瞒问题的人**，第一次有人因诚实复盘被惩罚，复盘文化就死了。

总结：**复盘的产出不是追责报告，是「让同类事故不可能再发生」的机制清单**。

> 面试官追问点：复盘会不会流于形式走个过场？应答思路：改进项的完成率是复盘质量的度量，Leader 亲自盯闭环，把复盘的案例用于新人培训让它产生复利。

### 一个故障修完怎么避免再发？

答：一题三解：**从单点扫描到面、基线文档化、故障资产化**，让一次故障的价值榨干。

1. **单点扫描到面**：这个故障的模式（比如「配置变更无审核」「缓存无过期」）在其他系统还有多少同类风险，一次性批量排查治理，**修一个漏十个不如修一批**；
2. **沉淀安全基线**：把教训变成可执行的检查项（发布 checklist 加一条、监控模板加一个指标），规则化让它长在流程里而不是人的记忆里；
3. **故障资产化**：案例库归档（脱敏后的时间线加根因），新人的第一课就是复盘真实故障，演练的剧本也从这里来。

我有个量化习惯：**复盘时算「杠杆率」，修这一个问题总共消灭了多少同类风险**。杠杆率高的故障值得开大会深挖，杠杆率低的快速处理，精力分配也讲性价比。

总结：**故障是付过学费的老师，学费既然交了，就要把课听全，只修单点等于交了学费只听了半节课**。

> 面试官追问点：批量治理会不会战线太长烂尾？应答思路：按风险分级排期，高危先治（两周内），中低危进常态治理池，设完成率度量防烂尾。

### 怎么从救火式走向防火式？

答：防火体系四道防线：**变更管控、故障注入演练、人因防线、趋势度量**，转化公式是**把应急动作固化成预防机制**。

1. **变更管控**：防火第一优先级，因为八成故障来自变更（变更三板斧：可灰度、可监控、可回滚），管住变更就掐灭了最大火源；
2. **故障注入演练**：定期主动制造可控故障，验证系统免疫力和告警有效性，**疫苗比治疗便宜**；
3. **人因风险四道防线**：流程防呆、双人复核、权限最小化、演练教育，把「人会犯错」当设计前提；
4. **趋势度量**：故障次数和恢复时长（MTTR）的季度趋势，是向管理层证明防火投入产出的唯一语言。

救火到防火的转化心法：**每次救火后问一句「什么机制能让这个火根本烧不起来」**，答案沉淀进上面的四道防线，救火经验才有复利。

向管理层争取防火资源的话术：**用故障成本换算**，一次 P0 的资损加人力加信任成本，对比防火投入，账一算就清楚。

总结：**救火型团队永远在还昨天的债，防火型团队才有资格谈明天的规划，防火是投入，更是解锁**。

> 面试官追问点：防火做到什么程度算够？应答思路：没有绝对够，按故障成本和业务阶段匹配，高资损业务多投入，验证期业务快速粗糙反而合理。
