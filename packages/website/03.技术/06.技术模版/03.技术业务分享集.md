## 03.技术业务分享模版

> **文档定位**：用于组内或跨团队的技术业务分享，把"我做过的事"讲成"别人能接住的知识"。
> **篇幅**：30-60 分钟。10 分钟以内的快速分享见 04.十分钟分享模版。
> **怎么用**：复制第 08 章骨架填写，写完用 7.2 自检清单打勾，分享前 24 小时把稿子发出来让听众先读。

### 使用说明

**适用范围**

1. 新业务、新模块上线后，向团队介绍
2. 跨团队对齐，让协作方理解你的业务和接口边界
3. 攻克技术难题后，把排查过程沉淀成经验
4. 新技术栈、新实践的推广

**分享的黄金结构**

开场用 SCQA 一句话点题（见 1.1），主体按"背景 → 演示 → 实现 → 难点"推进，思考这条线要贯穿始终：听众不光要听你做了什么，更要听你当时为什么这么选。

**时间分配（45 分钟场次）**

| 段 | 内容 | 时长 |
|---|---|---|
| 开场 | 一句话点题，听众带走什么 | 2 min |
| 01 背景 | 为什么做、解决了什么问题 | 8 min |
| 02 演示 | 长什么样、怎么用 | 8 min |
| 03 方案 | 架构、关键设计、代码 | 15 min |
| 04 难点 | 踩了什么、怎么解决 | 8 min |
| 05 沉淀 | 可复用经验、建议、Q&A | 4 min |

### 01.业务背景

#### 1.1 一句话开场（SCQA）

分享的第一句话不要铺垫，用 SCQA 在 30 秒内说清"今天讲什么、听众能带走什么"。SCQA 是麦肯锡金字塔原理的经典四要素：

```
S - Situation (情境)     大家共识的背景
C - Complication (冲突)  但是发生了什么问题
Q - Question (问题)      所以我们要回答什么
A - Answer (答案)        我的建议 / 今天的安排
```

```
❌ 铺垫式: "关于这次支付模块, 我想先讲一下背景, 老系统是 5 年前搭的..."（听众 10 秒走神）

✅ SCQA 式:
   S: 我们要接入聚合支付, 支持 5 个渠道
   C: 但现在每接一个渠道要改 6 个服务, 耗时 2 人月
   Q: 所以今天讲: 怎么用一套网关把接入成本降到 3 人天
   A: 下面 40 分钟, 我从背景、方案到踩坑完整过一遍
```

#### 1.2 产品业务背景

讲清楚这个需求从哪来、解决什么业务问题。假设听众没参加过需求评审，从产品视角把来龙去脉讲明白。

```
产品背景示例:
  来源: 海外业务扩张, Q3 需新增 3 个本地支付渠道
  痛点: 现有模式每接一个渠道要改 6 个服务, 渠道排队接不进
  价值: 接入周期从 2 人月降到 3 人天, 支撑海外 GMV
```

#### 1.3 技术背景与现状

讲清楚接手时的技术现状、已有包袱和痛点。这节决定了后面"为什么这么设计"能不能讲通，不能省。

要点：当前架构长什么样、历史债务有哪些、哪些坑是前人的、这次要不要动。

#### 1.4 本次目标与收益

对齐方案模版的 1.4，讲清这次分享对应的目标与可验收收益，让听众知道"好"的判定标准。

```
目标与收益示例:
  [业务] 渠道扩展至 5 个, 新渠道接入 ≤ 3 人天
  [技术] P99 ≤ 300ms, 渠道故障 30s 自动切换
  [质量] 核心链路单测覆盖率 ≥ 80%
```

### 02.功能演示

对实现的功能做完整的交互和视觉演示，帮助其他人理解产品需求与使用场景。可以用截图或现场演示，复杂动画要专门说明。

#### 2.1 演示路径

提前规划一条能覆盖核心场景的演示路径，从入口到关键结果走通一遍。不要临时发挥，临时发挥最容易在线上翻车。

#### 2.2 关键交互与视觉

重点演示容易被人忽略的交互细节：空状态、加载态、异常态、降级态。这些是评审和 QA 最关心、也最容易在分享里被漏掉的。

#### 2.3 演示注意事项

1. 提前录屏兜底：现场网络、环境、数据不稳时，录屏能救场
2. 准备降级方案：演示环境挂了，至少能放截图或录屏
3. 不要现场敲代码：演示是给人体感，不是现场改 bug
4. 复杂动画单独放一段：说明触发条件和实现思路，不要一笔带过

### 03.技术实现方案

从整体角度介绍实现方案，通过设计框图体现：流程图、时序图、框架图等。较复杂的项目要输出完整技术文档。

#### 3.1 整体架构与流程

一张图说清分层和模块关系，再讲主流程怎么走。不要一上来就贴代码，先建立全局认知。

#### 3.2 关键设计点

挑 3-5 个最能体现你思考的设计点展开，每个讲清"为什么这么选"：

```
关键设计点示例:
  1. 渠道适配用 SPI 而非 if-else: 新增渠道只写插件, 不动主干
  2. 回调用对账兜底而非信任渠道: 以主动查询为准, 防渠道丢回调
  3. 路由层独立: 故障渠道秒级摘流, 不影响其他渠道
```

#### 3.3 数据与接口

与服务端的数据通信流程、请求 API 返回的数据结构。讲清楚谁调用、传什么、返回什么、错误码大类。

#### 3.4 异常与降级

网络异常、状态同步异常、降级的处理。这节和 5.x 难点对应——能在这里讲清楚的，复盘时就不用在事故里补。

### 04.代码 Review

体现核心代码结构与框架，不要全量贴代码。UML 图、核心片段、关键代码点说明即可。

#### 4.1 核心代码结构

用一张包结构图或类图，说明代码怎么组织的、主干在哪、扩展点在哪里。听众能照着找到代码。

#### 4.2 关键代码解读

只贴最核心的 1-3 段代码，每段配一段说明：它在流程里的位置、为什么这么写、有没有更好的写法。控制篇幅，一屏最多一段。

#### 4.3 值得借鉴与待改进

诚实列出：这段代码哪里设计得好（可复用）、哪里是妥协（已知债）。这样既展示思考，也邀请听众帮你挑刺。

### 05.难点与解决方案

把遇到的问题和思考讲具体：交互难点、技术难点、兼容性难点，落到例子上。提供可行方案：怎么排查、怎么解决，并输出有效文档链接。

#### 5.1 难点清单

| 难点 | 类型 | 排查过程 | 解决方案 | 沉淀文档 |
|---|---|---|---|---|
| 渠道回调丢失 | 技术 | 抓包发现 3% 回调未送达 | 主动查询 + 对账兜底 | 对账设计文档 |
| 低版本白屏 | 兼容 | 机型矩阵复现 |  SDK 版本对齐 + 降级 | 兼容测试清单 |

#### 5.2 排查方法论

比"解决了什么"更重要的是"怎么查出来的"。把你的排查套路讲出来，听众能复用的是方法不是结论：

```
排查套路示例:
  1. 先复现: 固定输入, 找到最小复现路径
  2. 再分层: 客户端 / 网关 / 渠道, 逐层打点定位
  3. 看数据: 监控 + 日志 + 抓包三件套, 不靠猜
  4. 验假设: 每次只改一个变量, 验证后固化
```

#### 5.3 还没解决的坑

诚实列出现有未决问题，这本身就是很好的 Q&A 引子，也避免分享看起来"完美无缺"失去可信度。

### 06.沉淀与建议

#### 6.1 可复用的经验

把这次能复用的东西提炼出来：一个组件、一套排查流程、一份踩坑清单。让听众下次遇到类似问题能直接拿来用。

#### 6.2 现有问题与改进建议

原"吐槽与建议"升级：说现有业务/代码结构的不足点，但要有建设性——每条问题带一个改进建议，而不是只吐槽。

```
改进建议示例:
  ❌ "老代码太乱了"
  ✅ "支付与路由耦合过重, 建议抽独立路由层, 参考本次 SPI 方案, 预计能减少 40% 改动"
```

#### 6.3 后续规划

这次做到的边界在哪、下期做什么。让分享不只是"回顾"，也是"对齐下一步"。

### 07.分享技巧与自检

#### 7.1 讲好一场分享的五要点

1. **结论先行**：用 1.1 的 SCQA 开场，不铺垫
2. **事实与判断分离**：先给事实（"每层多一次转发"），再下判断（"所以延迟高"），不要混成"这个设计不优雅"
3. **一页一观点**：一页 PPT 只讲一件事，不要塞五个点
4. **讲为什么不讲是什么**：代码贴出来大家自己看，重点讲当时为什么这么选
5. **留 Q&A 时间**：最后 10% 留给提问，不要讲到最后一秒

#### 7.2 写完自检清单

```
开场与背景（3 条）
□ 1. 开场用了 SCQA, 一句话说清"讲什么、听众带走什么"
□ 2. 业务背景讲清了"为什么做、解决什么问题"
□ 3. 技术现状与痛点讲清了, 非本技术栈的人能听懂

演示与实现（5 条）
□ 4. 有可演示路径, 或录屏兜底
□ 5. 空/加载/异常/降级态都有提及
□ 6. 有整体架构图或流程图
□ 7. 关键设计点 3-5 个, 每个讲清"为什么这么选"
□ 8. 异常与降级方案有说明

代码与难点（3 条）
□ 9. 只贴核心代码, 不念全文
□ 10. 代码对应到设计点, 不孤立展示
□ 11. 难点有"排查过程 + 解决 + 沉淀文档"

沉淀（1 条）
□ 12. 有可复用经验或可落地的改进建议, 并留了 Q&A 时间
```

#### 7.3 分享反模式

| # | 反模式 | 现象 | 危害 | 对法 |
|:--:|---|---|---|---|
| 1 | 念代码 | 把代码贴满屏逐行念 | 听众自己能看，听你念纯浪费 | 只贴核心段，讲为什么 |
| 2 | 只有实现没有思考 | 讲"做了什么"，不讲"为什么这么选" | 听众学不到决策方法 | 每个设计点讲取舍 |
| 3 | 无演示 | 纯 PPT 讲功能 | 听众没体感，记不住 | 录屏 + 四态演示 |
| 4 | 前松后紧 | 背景讲 20 分钟，难点 2 分钟 | 最有价值的部分草草带过 | 按时间分配表卡点 |
| 5 | 没有结论 | 讲完大家不知道带走什么 | 分享没有沉淀 | 6.1 提炼可复用经验 |
| 6 | 自嗨 | 术语堆砌，非本栈的人听不懂 | 一半听众掉线 | 技术名词后紧跟业务价值 |
