## 04.业务串讲模版

> **文档定位**：开发中或开发完成后，对本次需求的业务和代码做一次完整串讲。把业务讲清楚、把实现讲清楚，核心代码还要讲透实现细节和底层原理。听众是同组开发、评审人、后续接手者。
> **篇幅**：45-90 分钟，按代码量与难点定。
> **怎么用**：复制第 08 章骨架，按"业务 → 概览 → 逐模块深挖 → 边界"走，写完用 7.2 自检清单打勾。

### 使用说明

**适用范围**

1. 需求开发完成、提测或 review 前，团队对齐实现
2. 核心模块新写/重构了大量代码，需要讲透原理
3. 技术评审，把"为什么这么写"讲给评审人听
4. 新人接手模块，老手把设计与坑口述一遍

**和 03 技术业务分享的区别**

| 维度 | 03 技术业务分享 | 04 业务串讲（本文） |
|---|---|---|
| 目的 | 对外展示、知识传播 | 对内对齐、code review、接手 |
| 听众 | 组内 + 跨团队 | 同组开发、评审人 |
| 演示 | 有功能演示 | 无演示，直接对代码讲 |
| 重点 | 我做过什么、思考线 | 代码怎么写、原理是什么 |
| 代码 | 只贴核心段 | 逐模块讲，核心代码讲透原理 |

**时间分配（60 分钟场次）**

| 段 | 内容 | 时长 |
|---|---|---|
| 01 业务 | 需求、边界、业务规则 | 10 min |
| 02 概览 | 整体设计、模块划分、数据流 | 10 min |
| 03 实现 | 逐模块讲业务意图 + 代码落点 | 25 min |
| 04 原理 | 核心代码深挖实现细节与原理 | 10 min |
| 05 边界 | 异常、测试、踩坑 | 5 min |

### 01.需求与业务背景

#### 1.1 需求来源与要解决的问题

讲清楚这次需求从哪来、解决什么业务问题。假设听众没参加过需求评审，从产品和业务视角把来龙去脉讲明白。

```
需求背景示例（消息推送去重模块）:
  来源: 运营反馈用户被同一条活动消息重复触达多次, 投诉骚扰
  问题: 现有推送没有去重和限流, 重试 + 多渠道导致同一用户收到 5+ 次
  目标: 同一用户同一消息 7 天内只推 1 次, 每分钟最多 5 条
```

#### 1.2 业务边界与不做的事

明确范围：哪些算本次需求、哪些明确不做。边界讲不清，评审和接手者就会对改动预期不一致。

```
边界示例:
  做: 去重、限流、失败重试退避
  不做: 推送内容个性化、跨端去重（下期）
```

#### 1.3 关键业务规则

把业务规则讲具体，尤其是状态、流程、口径这些容易理解错的地方。串讲里 80% 的疑问都出在业务规则没对齐。

```
业务规则示例:
  - 去重口径: 以 (userId + msgId) 为唯一键, 7 天窗口
  - 限流口径: 同一 userId 1 分钟滑动窗口 ≤ 5 条
  - 状态机: 待推送 → 推送中 → 成功/失败 → 失败重试(≤3)
```

#### 1.4 本次改动范围

点明动了哪些模块、新增还是改动。让听众先有全局改动地图，再进入细节。

```
改动范围示例:
  [新增] dedup 去重服务, rate_limit 限流组件
  [改动] push-scheduler 接入去重判断
  [不动] 推送通道 SDK
```

### 02.整体设计与模块划分

#### 2.1 架构与分层

一张图说清分层和模块关系，再讲主流程怎么走。先建立全局认知，再进入代码。

#### 2.2 模块划分与职责

讲清楚模块怎么切的、每个类/文件/方法负责什么、为什么这么切。切分理由本身就是设计思考的一部分。

```
模块划分示例:
  DedupService   去重判断 + 记录, 无状态, 依赖 Redis
  RateLimiter    滑动窗口限流, 可复用组件
  PushScheduler  编排: 先去重 → 再限流 → 才推送
  切分理由: 去重与限流正交, 拆开各自可单测、可复用
```

#### 2.3 核心数据流

讲清楚一条请求从进来到落地的完整路径：经过哪些模块、数据怎么流转、最终落到哪。

### 03.逐模块实现讲解

每个模块按"业务意图 → 代码落点 → 关键片段"三步走。**业务意图先行，代码随后**——听众先懂为什么，再看怎么写。

```
模块讲解三步法示例（DedupService）:
  1. 业务意图: 判断这条推送是否已被推过
  2. 代码落点: DedupService.judge(userId, msgId)
  3. 关键片段: 见 4.x, 核心在 Redis 唯一键 + 原子判断
```

普通模块一笔带过，难点的模块在 04 章深挖。不要平均用力，串讲最怕"每个都讲一点、重点淹没"。

### 04.核心代码实现细节与原理（重点）

这是本文和 03 最大的区别：**核心代码要讲透实现细节和底层原理**，不是贴一段代码念完。

#### 4.1 挑哪些核心代码

挑选标准（1-3 处足够）：体现难点、体现关键设计、容易踩坑的代码。不要全量讲。

#### 4.2 实现细节

贴核心段（控制在 30 行内），逐行/逐段讲：这段在流程里的位置、变量含义、分支逻辑。

#### 4.3 底层原理

讲清"为什么这么写"，从算法、数据结构、并发模型、设计模式、框架机制里找依据。这是接手者最该带走的。

```
核心原理示例 1: 去重为什么用"唯一键 + 数据库唯一索引"而非"先查后写"
  先查后写: 并发下两个请求都查到"不存在", 都插入 → 重复
  唯一索引: 插入时数据库原子校验, 第二个直接抛 DuplicateKey
  结论: 用唯一索引做最后兜底, 不要相信应用层的"查了没有"
```

```
核心原理示例 2: 限流为什么用 Redis ZSet 滑动窗口, 而非计数器
  计数器(固定窗口): 第 59s 和第 0s 各来 5 条, 实际 1 秒集群了 10 条
  滑动窗口(ZSet): 以当前时间戳为界, 统计窗口内数量, 边界平滑
  实现: member 用时间戳, score 也用时间戳; 先 ZREMRANGEBYSCORE 清旧, 再 ZCARD 计数
  注意大 key: 窗口内请求少时 ZSet 也小, 但高频用户要定期清理, 避免内存膨胀
```

#### 4.4 性能与复杂度

核心代码要说明时间/空间复杂度、并发安全、热点。评审最关心这块。

```
复杂度示例:
  去重: Redis GET + SETNX, O(1); 唯一索引兜底 O(1) 写入
  限流: ZSet 每次 ZADD + ZREMRANGEBYSCORE + ZCARD, O(logN)
  并发: 两者都依赖 Redis 单线程原子性, 无需应用层加锁
```

### 05.边界、异常与测试

#### 5.1 异常与降级

网络异常、下游超时、Redis 挂了怎么办。讲清楚降级策略，不要说"应该没问题"。

```
降级示例:
  Redis 不可用 → 去重降级为"不拦截"(宁可重复不可阻断业务), 打监控告警
```

#### 5.2 边界条件

把边界列出来：空值、超长、并发、幂等、时钟回拨。这些是 bug 高发区。

```
边界示例:
  - userId 为空: 跳过限流, 不报错
  - 时钟回拨: ZSet 时间戳用 Redis 时间而非本地时间
  - 幂等: 同一 msgId 重复投递, 去重拦截
```

#### 5.3 测试覆盖

讲清单测/场景覆盖了什么、没覆盖什么。诚实列未覆盖项，比"已充分测试"可信。

### 06.踩坑与接手注意事项

#### 6.1 开发中遇到的坑

把开发时踩的坑讲出来，这是最有价值的实战经验。

#### 6.2 给接手者的注意事项

画一张"雷区地图"：哪些地方易错、哪些配置不能乱动、哪些依赖要留意。

```
接手提醒示例:
  - 去重窗口 7 天是写死在配置中心的, 改了要同步清 Redis 旧键
  - RateLimiter 的 key 必须用 userId, 用 msgId 会限不住
```

### 07.串讲技巧与自检

#### 7.1 讲透代码的五要点

1. **按业务流讲，不按文件顺序**：按请求路径走，听众能跟上
2. **业务意图先行**：每段代码先说"为什业务上要这个"，再贴代码
3. **核心代码讲原理**：普通代码一笔带过，难点代码讲透算法/并发/框架机制
4. **挑难点讲透**：1-3 处够，不要 2000 行全过一遍
5. **给接手者留雷区地图**：明确易错点和不能乱动的配置

#### 7.2 写完自检清单

```
业务与范围（3 条）
□ 1. 需求背景讲清了"为什么做、解决什么问题"
□ 2. 业务边界讲清了(做/不做), 业务规则(状态/口径)对齐了
□ 3. 改动范围点明了(哪些模块新增/改动/不动)

概览与实现（4 条）
□ 4. 有整体架构图/模块划分, 讲清切分理由
□ 5. 核心数据流讲清了(从进来到落地)
□ 6. 每个模块按"业务意图→代码落点"讲, 非平均用力
□ 7. 普通模块一笔带过, 难点模块在 04 深挖

核心原理（3 条）
□ 8. 挑了 1-3 处核心代码(体现难点/设计/易错)
□ 9. 核心代码讲了实现细节, 不是念一遍
□ 10. 底层原理讲清了(算法/并发/框架机制/为什么这么写)

边界与沉淀（2 条）
□ 11. 异常/边界/幂等有覆盖, 测试覆盖讲清(含未覆盖项)
□ 12. 给接手者留了踩坑与雷区地图
```

#### 7.3 串讲反模式

| # | 反模式 | 现象 | 危害 | 对法 |
|:--:|---|---|---|---|
| 1 | 跳着讲 | 不按业务流，按文件顺序念 | 听众跟不上上下文 | 按请求路径走 |
| 2 | 只念代码 | 贴一屏代码逐行念，不解释 | 听完不知道为什么 | 业务意图先行 |
| 3 | 不讲原理 | 只说"用了 Redis"，不讲怎么保证安全 | 接手者踩同样的坑 | 4.3 讲底层原理 |
| 4 | 边界一笔带过 | "应该没问题" | 并发/幂等翻车 | 5.2 列边界 |
| 5 | 没有改动范围 | 不先说动了哪 | 评审预期错乱 | 1.4 点明范围 |
| 6 | 追求全覆盖 | 2000 行全讲完 | 重点淹没 | 只深挖 1-3 处核心 |
