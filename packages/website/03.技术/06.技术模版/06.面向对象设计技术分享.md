# 面向对象设计 → 技术分享

> 一句话价值: 用 4 个真实线上事故，把"面向对象"从语法名词讲成"责任边界的设计哲学"；听众带走一张"何时用接口 / 抽象类 / 直接 new"的决策卡
> 档位: 20 分钟（可按 10 / 30 裁剪，每节标了时长）

## 1. 开场（SCQA）  [2min · 口语三句，不寒暄]

S: 我们天天写 Java、写 class，但线上大事故大多不是算法错，是"对象没设计对"。
C: 双11 订单雪崩、余额对账差 1273 元、日志器被改 47 次、云迁移 6 万行——这四类事故根因惊人一致。
Q: 所以今天讲：面向对象设计的边界到底怎么划。
A: 下面 20 分钟，用 4 个事故串起，最后给一张决策卡。

## 2. 问题（对象没设计对，事故就来了）  [6min · 先给现象再给根因]

- 痛点（四个真实事故）:
  - 双11 订单雪崩：CPU 100%、错误率 23%，`OrderUtil.calculate` 从 47 行长到 1284 行，17 个 `if (activityType==...)`
  - 余额对账差 ¥1273.45：转账直接改 `balance` 字段，不变量"余额≥0、流水必同步"没人守
  - 日志器被改 47 次：加能力全靠 `if(type=="kafka")` 堆在工具类里
  - 云迁移 6 万行：代码里散落 62873 个 `OSSClient` 字符串，换云要改天
- 怎么发生的: 数据和行为不绑一起、责任边界不划清，一次改动就到处漏
- 根因: 不是语法不会用，是"责任边界没划清"——这正是 OOP 要解决的

## 3. 方案与数据（边界怎么划）  [8min · 讲为什么不讲是什么]

- 关键做法（主线三招）:
  1. **封装是地基**：`balance` 变 private，校验写进 `increase/decrease`，不变量强制守卫
  2. **接口还是抽象类**：is-a 用抽象类、can-do 用接口，主流用"接口 + 抽象类"双层
  3. **依赖接口而非实现**：抽 `ImageStore`，切换云只在构造时换一行

```java
// 双层：接口写给调用方看（能打什么交道），抽象类写给实现者看（填什么空）
public interface PaymentGateway { PayResult pay(Order o); }
public abstract class AbstractGateway implements PaymentGateway {
    public final PayResult pay(Order o) { validate(); rateLimit(); doPay(); record(); }
    protected abstract PayResult doPay(Order o);   // 唯一可插拔点
}
```

```java
// 依赖接口：调用方永远只看到 ImageStore，切换实现只在构造时换一行
public interface ImageStore { String upload(Image i, String bucket); Image download(String url); }
public class ImageJob { private final ImageStore store;
    public void process(Image i){ store.upload(i, "ai_images"); } }
```

- 为什么选它（对比）:
  - 过程式问"怎么做" → 复杂度摊给每个调用方；对象式问"谁来做" → 复杂度切片进对象内部
  - 直接 new 三方 SDK → 散弹修改 62873 处；依赖接口 → 加一种实现只加一个类（OCP）
- 前后数据:
  - 日志器：3 年加 3 个能力却被改 47 次 → 拆接口后稳定
  - `OSSClient` 62873 处 → `ImageStore` 1 处
  - 支付网关：纯接口 600 行 → 抽象类骨架 250 行

## 4. 总结与 Q&A  [4min · 给带走的东西]

- 可复用经验（决策卡）:

  ```
  ┌─ 这组类未来会被替换吗？ ──────────────┐
  │  否（脚本 / 工具类 / 业务实体）→ 直接 new │
  │  is-a + 有公共骨架      → 抽象类    │
  │  can-do / 需多重能力     → 接口      │
  │  既要契约又要骨架       → 接口 + 抽象类 │
  └───────────────────────────────────────┘
  ```

  > 一句话带走：**OOP 不是"用类组织代码"，是"用类划清责任边界"。封装是边界，抽象是边界的语义，继承是边界的层级，多态是边界外的统一视角。**

- 适用边界: 一次性脚本、工具类、不会变的业务实体，不用硬抽接口——接口有类爆炸、间接调用、过度设计代价
- 备问:
  - Q1 小项目也要上接口吗？ → 看"未来会不会被替换"，工具类不用
  - Q2 接口和抽象类到底选谁？ → is-a 用抽象类，can-do 用接口
  - Q3 继承不是被说别用吗？ → 强耦合代价，能用组合（策略注入）就用组合
  - Q4 接口越多类爆炸？ → 只有一种实现且不会变，就不抽
