# 面向对象设计 → 技术分享

> 一句话价值: 用 4 个真实线上事故，把"面向对象"从语法名词讲成"责任边界的设计哲学"；听众带走一张"何时用接口 / 抽象类 / 直接 new"的决策卡
> 档位: 20 分钟（可按 10 / 30 裁剪，每节标了时长）   受众: 组内 + 跨团队，初/中/高级都听得懂

## 1. 开场（SCQA）  [2-3min · 口语三句，不寒暄]

S: 我们天天写 Java、写 class，但线上大事故大多不是算法错，是"对象没设计对"。
C: 双11 订单雪崩、余额对账差 1273 元、日志器被改 47 次、云迁移 6 万行——这四类事故根因惊人一致。
Q: 所以今天讲：面向对象设计的边界到底怎么划。
A: 下面 20 分钟，用 4 个事故串起四个知识点，最后给一张决策卡，照着填就不会错。

## 2. 背景与问题  [6-8min · 先现象后根因]

- 痛点（四个真实事故，带数字）:
  - 双11 订单雪崩：CPU 100%、错误率 23%，`OrderUtil.calculate` 从 47 行长到 1284 行，17 个 `if (activityType==...)`
  - 余额对账差 ¥1273.45：一段 `transfer` 直接改 `from.balance`/`to.balance` 字段，不变量没人守
  - 日志器被改 47 次：加能力全靠 `if(type=="kafka")` 堆在工具类
  - 云迁移 6 万行：代码里散落 62873 个 `OSSClient` 字符串，换云要改天
- 为什么重要: 对象设计错，改动成本不是加法是**乘法**——一处边界没划清，所有调用方跟着改；新人也不敢动老代码
- 根因: 不是语法不会用，是"责任边界没划清"——数据行为不绑、抽象没选对、调用方依赖实现
- 常见误区（引出正解）:
  - 误区1：getter/setter 一堆就是"封装"（其实只是字段访问器，不变量没守）
  - 误区2：面向接口 = 到处抽接口（类爆炸、过度设计）
  - 误区3：能复用就继承（强耦合，改父类崩子类）

## 3. 核心内容  [主体 · 每个子主题讲透]

### 3.1 为什么用对象：数据和行为要绑一起

- 概念: 对象把"数据"和"操作数据的行为"绑在一个责任体里，问"谁来做"而非"怎么做"
- 为什么（对比）: 过程式把复杂度摊给每个调用方（新增折扣要改调用端 + 工具类）；对象式把复杂度切片进对象内部（新增折扣只加一个 `DiscountPolicy` 类）
- 案例/代码（演示）:

  ```java
  // 过程式：数据是裸数组，行为是漂浮的函数
  double total = subtotal * discount + shipFee + subtotal * taxRate;

  // 对象式：Order 自己知道怎么算
  class Order {
      public Money total() {
          return discount.apply(subtotal).add(shipping.fee(this)).add(tax.of(afterDisc));
      }
  }
  ```

- 数据: `OrderUtil.calculate` 47 行 → 1284 行（过程式腐烂的速度）

### 3.2 四大特性划边界：封装是地基

- 概念: 封装/抽象/继承/多态各治一类复杂度——封装守不变量、抽象藏实现、继承去重、多态消 if-else
- 为什么（案例）: 余额事故根因是 `balance` 是 public 字段，客服能绕过流水直接改；把 `balance` 变 private、校验写进 `increase/decrease`，不变量被强制守卫，调用方再无法绕过
- 案例/代码（演示）:

  ```java
  class Wallet {
      private Money balance;
      void increase(Money m){ checkNonNegative(m); this.balance = this.balance.add(m); record(); }
      void decrease(Money m){ require(this.balance.compareTo(m) >= 0); this.balance = this.balance.sub(m); record(); }
  }
  ```

- 数据: 对账差 ¥1273.45（不变量失守的代价）
- 讲法: 抽象/继承/多态都建在封装之上，没有封装的抽象是空中楼阁

### 3.3 接口还是抽象类：is-a 用抽象类，can-do 用接口

- 概念: 接口是"能力契约"（can-do），抽象类是"有公共骨架的本质类型"（is-a）
- 为什么（案例）: 日志器 `MyLogger` 3 年只加 3 个能力却被改 47 次，根因是把所有类型堆在一个工具类里用 `if(type==...)`；拆成"接口 + 抽象类"双层后稳定
- 案例/代码（演示，双层）:

  ```java
  public interface PaymentGateway { PayResult pay(Order o); }      // 能力契约：调用方只看这个
  public abstract class AbstractGateway implements PaymentGateway {
      public final PayResult pay(Order o) { validate(); rateLimit(); doPay(); record(); } // 骨架
      protected abstract PayResult doPay(Order o);                 // 唯一可插拔点
  }
  ```

  File/Kafka/ES 各自 `extends AbstractGateway` 只填 `doPay`；接口写给调用方看（能打什么交道），抽象类写给实现者看（填什么空）
- 数据: 47 次改动 vs 拆接口后稳定
- 决策树（一句话）: is-a + 有公共代码 → 抽象类；can-do 或需多重能力 → 接口

### 3.4 依赖接口而非实现：调用方只看接口

- 概念: 高层模块依赖抽象（接口），不依赖具体实现类
- 为什么（案例）: 云迁移阿里云 OSS → 腾讯云 COS，代码里 62873 个 `OSSClient` 字符串，调用方锁死在类名/方法名/流程，切换实现代价乘法爆炸
- 案例/代码（演示，三步重构）:

  ```java
  public interface ImageStore { String upload(Image i, String bucket); Image download(String url); }
  public class ImageJob { private final ImageStore store;   // 永远只看到接口
      public void process(Image i){ store.upload(i, "ai_images"); } }
  ```

  三步：① 命名抽象（`uploadToAliyun` → `upload`）② 流程封装（token 生成封进实现内部）③ 抽接口；改完后切换云只在构造时换一行
- 数据: `OSSClient` 62873 处 → `ImageStore` 1 处
- 延伸: 背后是 DIP（高层低层都依赖抽象）+ OCP（加 PayPal 只加类、不改 `CheckoutService`）；副产品**可测性**——没有接口就没有 Mock，单测无需真实 SDK

## 5. 总结与决策  [3-4min]

- 决策卡（照着填）:

  ```
  ┌─ 这组类未来会被替换吗？ ──────────────┐
  │  否（脚本 / 工具类 / 业务实体）→ 直接 new │
  │  is-a + 有公共骨架      → 抽象类    │
  │  can-do / 需多重能力     → 接口      │
  │  既要契约又要骨架       → 接口 + 抽象类 │
  └───────────────────────────────────────┘
  ```

- 一句话带走: **OOP 不是"用类组织代码"，是"用类划清责任边界"。封装是边界，抽象是边界的语义，继承是边界的层级，多态是边界外的统一视角。**
- 适用边界: 一次性脚本、工具类、不会变的业务实体，不用硬抽接口
- 反模式（最易被用错的方式）:
  - 为接口而接口：只有一种实现且不会变还抽 → 类爆炸、间接调用
  - getter/setter 当封装：字段公开 + 手动校验 → 不变量仍失守
  - 用继承做复用：父子强耦合，改父类崩子类 → 能用组合（策略注入）就用组合

## 6. Q&A  [留 10% 时间]

- Q1 小项目也要上接口吗？ → 看"未来会不会被替换"，工具类/一次性脚本不用
- Q2 接口和抽象类到底选谁？ → is-a 用抽象类，can-do 用接口
- Q3 继承不是被说别用吗？ → 强耦合代价，能用组合（策略注入）就用组合
- Q4 接口越多类爆炸？ → 只有一种实现且不会变，就不抽
- Q5 那我怎么判断该不该抽？ → 问"未来会不会被替换"：会 → 抽接口，不会 → 直接 new
