## 引子 · 手滑毁掉三天工作的那个夜晚

小李接到了一个紧急需求——加班三天，赶完了一个复杂的登录页面。周五晚上十点，他终于要 commit 了：

```bash
git status
# 显示：一堆修改，还有一些临时调试代码没删
```

他手忙脚乱地想「清理干净再提交」，于是敲下：

```bash
git reset --hard
```

**几秒钟后，他脸色发白**——工作区所有未提交的修改**全没了**。三天的心血，随着一条命令，化为乌有。

他给我打电话时，声音都在抖：「哥，我完了……」

我问他一句：「你刚才 commit 过没？」他说没有。

我沉默了三秒——如果真的一次 commit 都没有，那**任何工具都救不了他**，Git 也不例外。

**这就是本章的第一课**：Git 是后悔药最多的工具，但它救得了「已经 commit 过的你」，救不了「从未 commit 过的你」。

**养成频繁 commit 的习惯——是所有 Git 修行的第一戒律**。

## 二、三区五态：一切命令的舞台

上一章已经画过图，本章要做的是**让你脑子里的图变成肌肉记忆**。

```
   ┌──────────────┐   git add    ┌──────────────┐   git commit   ┌──────────────┐
   │   工作区     │ ───────────▶ │   暂存区     │ ─────────────▶ │   版本库     │
   │              │              │              │                │              │
   │              │ ◀─────────── │              │ ◀───────────── │              │
   └──────────────┘  git restore └──────────────┘   git reset    └──────────────┘
```

**你每一天的所有 Git 操作，都是在这张图上搬运数据**。有了这张图当坐标，任何命令都不会迷路。

**五态对照**：

| 状态 | 位置 | 意思 | 常见触发 |
|---|---|---|---|
| Untracked | 工作区 | Git 完全不认识 | 新建文件 |
| Unmodified | 三区一致 | 跟版本库一样 | commit 后无改动 |
| Modified | 工作区 | 改了但没 add | 修改文件 |
| Staged | 暂存区 | add 之后 | `git add` |
| Committed | 版本库 | commit 之后 | `git commit` |

## 三、日常七件事

一个人的 Git 工作流，永远是同样的七件事。看熟了下面这张表，你的手指自然会知道该敲什么。

### 3.1 初始化仓库：`git init` / `git clone`

```bash
git init                              # 在当前目录变成 Git 仓库（新建 .git/）
git init --initial-branch=main        # 一步到位用 main 而不是 master

git clone <URL>                       # 从远程克隆
git clone <URL> --depth=1             # 只克隆最近一个 commit（大仓库救命）
git clone <URL> my-name               # 克隆到指定目录名
```

**⚡ 小心机**：`git init` 之后立刻做一次「零号 commit」——建个空 README 就行。**永远让仓库处于「有历史」的状态**，后续所有 `reset` / `reflog` 才有意义。

### 3.2 查看现状：`git status` / `git diff`

```bash
git status                       # 完整现状（初学者友好）
git status -s                    # 简洁模式（老手最爱）
                                 # 前一位：暂存区状态；后一位：工作区状态

git diff                         # 工作区 vs 暂存区（还没 add 的改动）
git diff --staged                # 暂存区 vs 版本库（已 add 但未 commit）
git diff HEAD                    # 工作区 vs 版本库（所有未提交改动）
git diff <commit1> <commit2>     # 任意两次提交之间的差异
git diff --stat                  # 只看统计，不看细节
```

**记忆口诀**：**「不带参数看未 add，带 `--staged` 看已 add」**。

### 3.3 提交历史：`git add` / `git commit`

```bash
# 基础
git add file.txt                 # 把某个文件加入暂存区
git add .                        # 把当前目录所有变化加入暂存区
git add -A                       # 加入所有（包括删除）

# 精细化
git add -p                       # 交互式选择——每一段 diff 都问你要不要 add
                                 # 这是老手的秘密武器：让 commit 保持原子性

git commit -m "message"          # 一句话提交
git commit                       # 打开编辑器写详细 message（生产环境推荐）
git commit -am "message"         # 跳过 add，直接把所有已跟踪文件的修改提交
git commit --amend               # 修改上一次 commit（改 message 或补充文件）
                                 # ⚠️ 已推送的 commit 不要 amend！
```

> **⚡ 一句话**  
> **`git add -p` 是把「一次乱糟糟的修改」拆成「多个原子 commit」的神器**。老手花 5 分钟 `-p` 拆干净，胜过菜鸟花 5 天 revert。

### 3.4 撤销修改：`git restore` 家族

`git restore` 是 Git 2.23（2019 年）引入的现代命令，专门用来撤销修改。**它比老命令 `git checkout` 更清晰**：

```bash
git restore file.txt             # 撤销工作区的修改（恢复到最近一次 add 或 commit）
                                 # ⚠️ 未 add 的改动会永久丢失！

git restore --staged file.txt    # 把暂存区的改动退回工作区（撤销 add）

git restore --source=HEAD~1 file.txt   # 从上一个 commit 恢复某个文件
```

**旧命令对照**（了解即可，别用）：
- `git checkout -- file.txt` → 现在写 `git restore file.txt`
- `git reset HEAD file.txt` → 现在写 `git restore --staged file.txt`

### 3.5 回退版本：`git reset` 的三张脸

`git reset` 是 Git 里**最强大也最危险**的命令。它有三个参数，长得很像，杀伤力完全不同：

```bash
git reset --soft HEAD~1          # 撤销上一个 commit
                                 # 变更留在暂存区、工作区（最温和）

git reset --mixed HEAD~1         # 撤销上一个 commit（默认）
                                 # 变更留在工作区，暂存区清空

git reset --hard HEAD~1          # 撤销上一个 commit
                                 # ⚠️ 工作区、暂存区全部清空——变更永久丢失！
```

**一张对照表帮你永远不再搞混**：

| 参数 | 版本库指针 | 暂存区 | 工作区 | 用途 |
|---|---|---|---|---|
| `--soft` | 后退 | 保留 | 保留 | 「我 commit 分错了，重新组织」 |
| `--mixed`（默认） | 后退 | 清空 | 保留 | 「我 commit 里包含了不该有的文件」 |
| `--hard` | 后退 | 清空 | **清空** | 「这个功能不要了，全部废弃」 |

**⚡ 一句话记忆**：
- **soft** → **s**taged 保留（只动版本库）
- **mixed** → **m**iddle 中间（版本库 + 暂存区都动）
- **hard** → **h**arsh 狠（三个区都动，无情清空）

⚠️ **`--hard` 是全书最危险的命令**——但**只要你 commit 过一次**，`git reflog` 就能救回你。见 3.6 节。

### 3.6 时光倒流：`git log` / `git reflog`

```bash
# git log —— 看的是 commit 的历史
git log                          # 完整日志
git log --oneline                # 每个 commit 一行
git log --graph --oneline --all  # 带图，全分支（老手最爱）
git log -n 5                     # 只看最近 5 条
git log --author="小李"          # 按作者过滤
git log --since="2 weeks ago"    # 按时间过滤
git log -p                       # 显示每次 commit 的具体 diff
git log --stat                   # 显示每次 commit 的文件统计
git log -- <file>                # 只看某个文件的历史

# git reflog —— 看的是「HEAD 移动的历史」
git reflog                       # 显示所有 HEAD 变化
```

**这两个命令的区别决定了你能不能救回来**：

| 命令 | 记录了什么 | 找得回什么 |
|---|---|---|
| `git log` | commit 之间的父子链 | 只能看到当前分支「往回连得上」的 commit |
| `git reflog` | HEAD 每一次移动 | **可以看到所有历史操作**——包括 `reset --hard` 之后「表面上消失」的 commit |

**救命场景**：

```bash
# 场景：手滑 reset --hard，代码没了
git reflog
# 输出：
# abc123 HEAD@{0}: reset: moving to HEAD~1     ← 就是这条毁了我
# def456 HEAD@{1}: commit: my precious work    ← 我要救的 commit！
# ...

# 一步救回来：
git reset --hard def456
# 或者：
git reset --hard HEAD@{1}
```

**记住**：**只要你 commit 过，reflog 就保你 30 天**——这是 Git 给独行者最厚重的护身符。

### 3.7 忽略清单：`.gitignore` 的正确姿势

`.gitignore` 是每个仓库的第一件正事——**决定了哪些文件永远不入版本控制**。

```gitignore
# 依赖目录
node_modules/
vendor/
.venv/

# 构建产物
dist/
build/
*.class
*.o

# IDE 与系统
.vscode/
.idea/
.DS_Store
Thumbs.db

# 敏感信息（这一段是重中之重！）
.env
.env.local
*.pem
*.key
secrets/
config/production.yaml

# 日志与临时
*.log
tmp/
*.swp
*.swo
```

**⚡ 三条铁律**：

1. **在 `git init` 后立刻建 `.gitignore`**——比什么都重要。一旦敏感文件（`.env`、密钥）被 commit，即使删除、即使 push 后再删除，**历史里也永远存在**。
2. **不要写 `git add .` 之前不先 `git status` 一眼**——好习惯胜过好工具。
3. **官方模板站**：<https://github.com/github/gitignore>——按语言/框架下载，比你手写强百倍。

**万一敏感文件已经提交了怎么办？** 见第 08 章「故障排除之手册」。

## 四、心智模型剖析：`reset` 的三张脸

第 3.5 节讲了 `reset` 的三个参数。但**你要真正看懂它，需要把三区图叠加上「HEAD 指针」**：

```
                     ┌────────────┐
      HEAD ─指向─▶   │  分支引用   │  ─指向─▶  commit（某个版本）
                     └────────────┘
                          │
                          ▼
                      版本库快照
                          │
                          ▼
                        暂存区
                          │
                          ▼
                        工作区
```

**`git reset` 的三个参数，就是「往回退几层」**：

- `--soft`：**只退版本库指针**（HEAD 与分支后移）。暂存区、工作区**原封不动**。
- `--mixed`（默认）：退版本库指针 + **清空暂存区**（重新填成 HEAD 的状态）。工作区不动。
- `--hard`：三层全退——**版本库指针后移 + 暂存区 = HEAD + 工作区 = HEAD**。所有未 commit 的改动全部消失。

**一句话**：**`--hard` 之所以危险，是因为它连工作区都覆盖了**。而工作区一旦被覆盖，**没 commit 过的东西 reflog 也救不回来**——因为 reflog 记录的是 HEAD 移动，不是工作区变更。

## 五、深入 index：暂存区在磁盘上到底长什么样

大多数 Git 用户从来没打开过 `.git/index` 文件。但**这个文件是理解「暂存区」的钥匙**——它就是暂存区本身。

**index 是一个二进制文件**，格式在 `Documentation/technical/index-format.txt` 里有完整定义。它的结构大致如下：

```
┌────────────────────────────────────────────────┐
│  Header (12 字节)                              │
│  ├── 4 字节  签名 "DIRC"（DIR-C, dir cache）   │
│  ├── 4 字节  版本号（2/3/4）                    │
│  └── 4 字节  index 条目数                       │
├────────────────────────────────────────────────┤
│  Entry 1                                       │
│  ├── ctime（创建时间）                          │
│  ├── mtime（修改时间）                          │
│  ├── dev / ino（设备号 / inode）                │
│  ├── mode（文件权限：100644 / 100755 / 120000） │
│  ├── uid / gid（所有者）                        │
│  ├── file size（文件大小）                      │
│  ├── SHA-1（对应 blob 的 SHA-1）                │
│  ├── flags（合并冲突阶段等）                     │
│  └── path（文件路径）                           │
├────────────────────────────────────────────────┤
│  Entry 2                                       │
│  ...                                           │
├────────────────────────────────────────────────┤
│  Extensions（可选：TREE / REUC / link ...）    │
├────────────────────────────────────────────────┤
│  SHA-1 of the entire file（校验）              │
└────────────────────────────────────────────────┘
```

**几个关键洞察**：

1. **index 记录的是「文件 → blob SHA-1」的映射**——它是一份**清单**，不存文件内容。真正的内容永远在 `.git/objects/` 里。
2. **`git add` 干了什么**？——两件事：**把文件内容写成 blob（存进 `.git/objects/`）+ 在 index 里更新对应条目**。
3. **`git commit` 干了什么**？——**把 index 打包成一个 tree 对象，然后造一个 commit 指向它**。所以 commit 时不再看工作区——只看 index。
4. **index 缓存了 stat 信息**（ctime、mtime、size）——这是 `git status` 能秒回的关键。它先比 stat，只有 stat 变了才真去比 blob 内容。

**动手看一下**：

```bash
# 查看 index 里的所有条目
git ls-files -s
# 输出：100644 8ab686e... 0    README.md
#      100644 a1b2c3d... 0    src/index.js
#      100755 def456... 0    build.sh          ← 100755 = 可执行

# 查看 index 的详细状态（含 stat 信息）
git ls-files --debug

# 手动读 index（会看到二进制乱码，但能看到路径）
xxd .git/index | head -30
```

> **⚡ 冷知识**  
> index 之所以叫「index」而不是「staging area」，是因为它最早的功能是**给合并操作提供快速索引**——「暂存区」是它后来才被赋予的用户视角。**同一个东西，机器视角叫 index，人视角叫 staging area**。

## 六、restore / switch：Git 2.23 的命令拆分革命

如果你的 Git 版本 ≥ 2.23（2019 年 8 月发布），你会拥有两个之前没有的命令：`git switch` 和 `git restore`。**它们是 Git 团队近十年最大的可用性改进**——理解它们的动机，你会更深刻地理解 Git。

**为什么要拆分？** 因为老命令 `git checkout` 太万能，是一个**臭名昭著的「上下文敏感」命令**：

```bash
# 场景 1：切换分支
git checkout main

# 场景 2：创建并切换分支
git checkout -b feature

# 场景 3：恢复文件（危险！和场景 1 只差一个「.」和一个「--」）
git checkout -- file.txt
git checkout HEAD file.txt

# 场景 4：进入 detached HEAD（新手噩梦）
git checkout abc123

# 场景 5：从某个 commit 恢复某个文件到工作区
git checkout abc123 -- file.txt
```

**五种截然不同的操作，长得都像 `git checkout xxx`**——很多新手因为多打了或少打了一个 `--`，导致代码丢失。

**Git 2.23 的解法：拆成两个专用命令**：

| 老命令 | 新命令 | 干什么 |
|---|---|---|
| `git checkout <branch>` | **`git switch <branch>`** | 切换分支 |
| `git checkout -b <branch>` | **`git switch -c <branch>`** | 创建并切换分支 |
| `git checkout --detach <commit>` | **`git switch --detach <commit>`** | 进入 detached HEAD |
| `git checkout -- <file>` | **`git restore <file>`** | 恢复工作区文件 |
| `git checkout <commit> -- <file>` | **`git restore --source=<commit> <file>`** | 从某 commit 恢复文件 |
| `git reset HEAD <file>` | **`git restore --staged <file>`** | 取消 staging |

**新命令的三个优势**：

1. **一个命令做一件事**——`switch` 只管分支，`restore` 只管文件，不会误用。
2. **语义更清晰**——参数名（`--staged` / `--source` / `-c`）都是自解释的。
3. **老命令继续可用**——`checkout` 不会删除，只是**不再推荐给新人**。

**⚡ 一句话记忆**：

- **切分支** → `switch`（意思是 switch to another line of work）
- **改文件** → `restore`（意思是 restore state of files）
- **不再推荐** → `checkout`（保留兼容，但新代码用上面两个）

**为什么这个改进这么重要**？因为 Git 20 年来第一次**承认「命令行 UX 有问题」并且真的动手改**。这是一个成熟软件的成熟表现——**不是所有决定都要一辈子扛着，用户不好用就该改**。

## 七、reflog 深度剖析：三十天的时空胶囊

前面第 3.6 节讲过 `reflog` 是「30 天的救命日志」，但**它到底存在哪、怎么过期、能不能配置**？这一节我们把它拆到底。

**reflog 存在哪**？

```
.git/logs/
├── HEAD                       # HEAD 指针的所有移动
└── refs/
    ├── heads/
    │   ├── main               # main 分支的所有移动
    │   └── feature/xyz
    └── remotes/
        └── origin/
            └── main           # 远程跟踪分支的移动
```

**每一行的格式**（打开 `.git/logs/HEAD` 看）：

```
0000000... abc123... 杨充 <ycpeimai@163.com> 1745000000 +0800  commit (initial): first commit
abc123... def456... 杨充 <ycpeimai@163.com> 1745000060 +0800  commit: add feature
def456... 000000... 杨充 <ycpeimai@163.com> 1745000120 +0800  reset: moving to HEAD~1
```

**每一行 = 一次 HEAD 变化**，记录了：
- **before SHA-1**（`0000000...` 表示初次）
- **after SHA-1**
- **谁**（作者名 + 邮箱）
- **什么时候**（Unix 时间戳 + 时区）
- **什么操作**（commit / reset / merge / rebase / checkout ...）

**reflog 的过期策略**（默认）：

- **可达对象**（能从 branch/tag 回溯到的）——保留 **90 天**（`gc.reflogExpire`）
- **不可达对象**（比如被 `reset --hard` 抹掉的）——保留 **30 天**（`gc.reflogExpireUnreachable`）

**过期后**：`git gc` 会清理 reflog 中过期条目 + 清理没有任何引用的对象（dangling objects）。

**你可以自定义**（比如个人重要项目改成 1 年）：

```bash
git config gc.reflogExpire "1 year"
git config gc.reflogExpireUnreachable "6 months"
```

**几个救命场景**：

```bash
# 场景 1：手滑 reset --hard，找回来
git reflog
git reset --hard HEAD@{1}      # 回到「reset 之前」

# 场景 2：branch 被误删（哭爹喊娘的场景）
git reflog                     # 找到那个 branch 最后指向的 SHA
git branch feature-recovered <SHA>

# 场景 3：rebase 搞砸了，想回到 rebase 前
git reflog                     # 看到「rebase (start)」之前的 SHA
git reset --hard <SHA>

# 场景 4：查一个具体分支的 reflog（不是全局 HEAD）
git reflog show main

# 场景 5：按时间查
git reflog --date=iso          # 显示 ISO 格式的时间
git show HEAD@{"2 days ago"}   # 看两天前 HEAD 指向的 commit
git show HEAD@{yesterday}
```

**⚡ reflog 的局限**（这是很多人不知道的坑）：

1. **reflog 是本地的**——不会 push、不会 clone。**换台电脑就没了**。
2. **reflog 只记 HEAD/引用的移动**——不记录**未 add** 的工作区改动。工作区丢了 reflog 也救不了。
3. **reflog 会被 `git gc --aggressive` 清理**——手动 gc 前请三思。
4. **`git reflog delete` 或 `git reflog expire --expire=now --all` 会立刻清空**——这是不可逆操作，谨慎使用。

> **⚡ 一句话**  
> **reflog 是 Git 送给独行者的最厚礼物**——但它救不了「没 commit 过的你」。所以本章第一句话就说：**养成频繁 commit 的习惯**。

## 八、Commit Message 的书写之道

一个人写代码，也要好好写 commit message。因为**六个月后的你，就是别人**。

**推荐规范：Conventional Commits**（<https://www.conventionalcommits.org/zh-hans/>）

```
<type>(<scope>): <subject>

<body>

<footer>
```

**type 常用值**：

| type | 含义 | 场景 |
|---|---|---|
| `feat` | 新功能 | 「加了个登录页」 |
| `fix` | 修 bug | 「修复了空指针崩溃」 |
| `docs` | 文档 | 「更新 README」 |
| `style` | 格式（不影响功能） | 「统一缩进、加分号」 |
| `refactor` | 重构（不改功能） | 「拆分 login.js 成三个模块」 |
| `perf` | 性能优化 | 「首屏加载从 3s 优化到 1s」 |
| `test` | 测试 | 「加了 login 的单测」 |
| `chore` | 构建/工具 | 「升级 webpack 到 v5」 |
| `revert` | 回滚 | 「回滚上一个 commit」 |

**好例子**：

```
feat(login): add SMS verification

Support China Mobile / Unicom / Telecom.
Add 60s countdown after sending code.
Use Ant Design's Input.OTP for the UI.

Closes #123
```

**坏例子**（请引以为戒）：

```
- 提交
- update
- fix bug
- 改了下代码
- 111
- ...................
```

**⚡ 一句话**：**commit message 是给六个月后的自己写的情书**——写得温柔一点。

## 九、Git Hooks：让 Git 自动化你的规范

`.gitignore` 让你忽略文件，**hooks 让你注入行为**——在特定时机自动运行脚本。一个成熟开发者的 Git 仓库，一定有几个精心配置的钩子。

**hooks 存在哪**：`.git/hooks/` 目录，每个钩子是一个可执行文件（shell / Python / Node 都行）。**新建仓库时里面有一堆 `.sample` 文件**——去掉 `.sample` 后缀就生效。

**hooks 全景**（客户端 + 服务端）：

| 阶段 | Hook 名 | 触发时机 | 常见用途 |
|---|---|---|---|
| **提交前** | `pre-commit` | `git commit` 前 | 跑 lint、跑单测、检查禁用词 |
| | `prepare-commit-msg` | 打开 commit message 编辑器前 | 自动填 template |
| | `commit-msg` | 输入完 message 后 | 校验 message 格式（Conventional Commits） |
| **提交后** | `post-commit` | commit 之后 | 通知、发消息 |
| **合并** | `pre-merge-commit` | merge commit 前 | 阻止某些合并 |
| | `post-merge` | merge 之后 | 自动重装依赖（`npm install`） |
| **切换** | `post-checkout` | 切分支后 | 提示环境变化 |
| **变基** | `pre-rebase` | rebase 开始前 | 阻止 rebase 主分支 |
| **推送** | `pre-push` | push 前 | 跑集成测试、检查大文件 |
| **接收（服务端）** | `pre-receive` / `update` / `post-receive` | 服务端接收推送 | CI 触发、权限检查、Webhook |

**最实用的三个客户端钩子**：

**① `pre-commit`：提交前跑 lint**

```bash
#!/bin/bash
# .git/hooks/pre-commit
# 只 lint 已 staged 的 JS/TS 文件

FILES=$(git diff --cached --name-only --diff-filter=ACMR | grep -E '\.(js|ts|jsx|tsx)$')
if [ -z "$FILES" ]; then exit 0; fi

npx eslint $FILES
if [ $? -ne 0 ]; then
  echo "❌ ESLint 检查失败，请修复后再提交"
  exit 1
fi
```

**② `commit-msg`：校验 message 格式**

```bash
#!/bin/bash
# .git/hooks/commit-msg
# 强制 Conventional Commits

PATTERN='^(feat|fix|docs|style|refactor|perf|test|chore|revert)(\(.+\))?: .{1,80}$'
if ! grep -qE "$PATTERN" "$1"; then
  echo "❌ commit message 必须符合 Conventional Commits"
  echo "示例：feat(login): add SMS verification"
  exit 1
fi
```

**③ `pre-push`：推送前跑单测**

```bash
#!/bin/bash
# .git/hooks/pre-push
npm test
if [ $? -ne 0 ]; then
  echo "❌ 单元测试失败，禁止 push"
  exit 1
fi
```

**hooks 的痛点：hooks 不入版本控制**——`.git/` 是被 gitignore 的。团队协作时怎么共享？两个方案：

- **`husky`（前端主流）**：`.husky/` 目录里的脚本可以入版本控制，团队 clone 后 `npm install` 自动装。
- **`pre-commit`（Python 主流）**：<https://pre-commit.com>，配置文件 `.pre-commit-config.yaml`。
- **Git 2.9+ 内置**：`git config core.hooksPath .githooks`——把仓库里的 `.githooks/` 目录作为钩子目录。

> **⚡ 一句话**  
> hooks 是**「让规范自动生效」的杠杆**——比开会宣讲十遍规范，都不如一个 3 行的 `commit-msg` hook。

## 十、换行符与编码：跨平台协作的隐形炸弹

如果你的团队里有 Mac、Linux、Windows 三种系统混用——**恭喜你，你迟早会遇到换行符问题**。这可能是 Git 用户最头疼的隐形炸弹之一。

**背景**：
- **Unix / Linux / Mac**：一行结尾用 **LF**（`\n`，`0x0A`）
- **Windows**：一行结尾用 **CRLF**（`\r\n`，`0x0D 0x0A`）
- **老 Mac（Mac OS 9 及之前）**：单独 **CR**（几乎绝迹）

**如果不处理换行符**，会出现这些惨案：
- Windows 用户克隆下来后，`git diff` 显示「整个文件都变了」——但其实一行代码都没改。
- 跨平台协作时不停地互相 revert 换行符。
- 某些工具（shell 脚本、Makefile）在 Windows 换行符下**根本跑不起来**。

**Git 的解法：`core.autocrlf` 配置**

| 值 | 行为 |
|---|---|
| `true`（Windows 推荐） | 提交时 CRLF → LF，检出时 LF → CRLF |
| `input`（Mac/Linux 推荐） | 提交时 CRLF → LF，检出时不转换 |
| `false` | 完全不转换（保持原样） |

```bash
# Windows 用户
git config --global core.autocrlf true

# Mac / Linux 用户
git config --global core.autocrlf input
```

**更精细的方案：`.gitattributes`**

`.gitattributes` 是一个**放在仓库根目录、入版本控制**的配置文件——它比 `core.autocrlf` 更精细，能对不同文件类型指定不同规则：

```gitattributes
# 默认：所有文件用 LF
* text=auto eol=lf

# 特殊：shell 脚本永远 LF
*.sh text eol=lf

# 特殊：Windows 批处理永远 CRLF
*.bat text eol=crlf

# 二进制文件：不做任何转换
*.png binary
*.pdf binary
*.zip binary

# 特殊 diff 规则
*.md diff=markdown
*.go diff=golang

# 合并策略
package-lock.json merge=binary
```

**⚡ 一次终结换行符战争**：

```bash
# 1. 在仓库根目录建 .gitattributes（内容如上）
# 2. 让 Git 重新规范所有已跟踪文件
git add --renormalize .
git commit -m "chore: normalize line endings"

# 之后所有人 pull 下来都是干净的 LF
```

**编码问题**：中文用户还会遇到 GBK / UTF-8 混合的问题。**标准答案**：

```bash
# 全局设置为 UTF-8
git config --global i18n.commitEncoding utf-8
git config --global i18n.logOutputEncoding utf-8

# Windows PowerShell 也要设置
$env:LESSCHARSET = "utf-8"

# .gitattributes 里声明
*.md text eol=lf encoding=UTF-8
```

> **⚡ 一句话**  
> `.gitattributes` **是每个正经仓库的第二件正事**——第一件是 `.gitignore`，第二件是它。

## 十一、`git diff` 到底做了什么：diff 算法一览

`git diff` 每天要跑几十次，但它背后的算法很少有人关心。**一个懂 diff 算法的开发者，能看懂为什么某些改动 diff 出来「特别丑」——并且能修好它**。

**Git 支持四种 diff 算法**（通过 `--diff-algorithm=` 或配置 `diff.algorithm` 选择）：

| 算法 | 时间 | 优势 | 场景 |
|---|---|---|---|
| **myers** | 默认 | 最快，Eugene Myers 1986 论文 | 通用 |
| **minimal** | 慢一些 | 找最小的 diff | 追求最小改动 |
| **patience** | 中等 | 让 diff 更「有意义」（找唯一行做锚点） | 结构化代码（有函数签名的） |
| **histogram** | 最新 | patience 的改良版，更快 | Git 2.x 推荐 |

**配置成默认用 histogram**（大多数场景更优）：

```bash
git config --global diff.algorithm histogram
```

**举个例子**——同一份改动，`myers` 可能给出这样的 diff：

```diff
- }
- 
- func Bar() {
+ func Bar() {
+ }
+ 
+ func Baz() {
```

而 `histogram` 会给出：

```diff
+ func Baz() {
+ }
+ 
  func Bar() {
```

——**histogram 保留了函数边界，diff 更符合人类直觉**。

**几个进阶用法**：

```bash
# 按词 diff（不是按行）——改文档时超有用
git diff --word-diff
git diff --word-diff-regex='[A-Za-z_][A-Za-z0-9_]*'   # 只把标识符当词

# 忽略空白
git diff -w                    # 忽略所有空白差异
git diff -b                    # 忽略行尾空白

# 移动检测（Git 2.15+）
git diff --color-moved         # 高亮「只是移动」的代码块

# 只看统计
git diff --stat
git diff --shortstat

# 只看文件名
git diff --name-only

# 只看某种改动
git diff --diff-filter=AM      # 只看新增(A)和修改(M)，忽略删除(D)

# 结构化对比（比如 JSON）
git diff --no-index a.json b.json   # 不需要在仓库里，任意两个文件
```

**给自己配一个 diff 神器**：

```bash
# 安装 delta（更漂亮的 diff）
brew install git-delta          # Mac
sudo apt install git-delta      # Ubuntu

# 配置 Git 用 delta
git config --global core.pager delta
git config --global interactive.diffFilter "delta --color-only"
git config --global delta.navigate true
git config --global delta.side-by-side true
```

**从此你的 `git diff` 会变成一屏彩色的、并排的、语法高亮的对比**——生产力翻倍。

> **⚡ 冷知识**  
> `patience diff` 算法是 Bram Cohen（BitTorrent 作者）为 Bazaar 发明的，后来被移植到 Git。名字来源于「Patience 单人纸牌游戏」——它把 diff 问题转化为纸牌游戏的最长递增子序列问题。**软件工程与游戏理论的一次浪漫相遇**。

## 十二、动手实战：一次完整的独行者工作流

打开终端，跟着敲下面这段——你会走完一位独行者的**典型一天**：

```bash
# 上午 9:00 · 新建项目
mkdir my-blog && cd my-blog
git init --initial-branch=main

# 建 .gitignore（第一件事）
cat > .gitignore <<EOF
node_modules/
.env
.DS_Store
dist/
*.log
EOF

# 零号 commit
echo "# My Blog" > README.md
git add .
git commit -m "chore: initial commit"

# 上午 10:00 · 写点代码
cat > index.js <<EOF
console.log('Hello Blog')
EOF

git status                        # 看到 Untracked
git add index.js
git status                        # 看到 Staged
git commit -m "feat: add entry point"

# 上午 11:00 · 加个功能，但写乱了
cat >> index.js <<EOF
// 一堆没组织好的代码
function foo() {}
function bar() {}
console.log('debug')
EOF

# 意识到写乱了，先看看
git diff

# 决定用 add -p 拆成两个原子 commit
git add -p                        # 交互式选择：只 add foo
git commit -m "feat: add foo"

git add -p                        # 只 add bar
git commit -m "feat: add bar"

git restore index.js              # 剩下的 debug 代码丢弃

# 下午 2:00 · 手滑：写错了 commit message
git commit --allow-empty -m "fx: wrong typo"
git commit --amend -m "fix: correct typo"

# 下午 3:00 · 灾难：手滑 reset --hard
echo "critical work" >> index.js
git add . && git commit -m "feat: critical work"
git reset --hard HEAD~3           # 😱 三个 commit 全没了！

# 冷静：reflog 救命
git reflog                        # 看到所有历史
git reset --hard HEAD@{1}         # 找回来

# 下午 5:00 · 查看今日战果
git log --oneline --graph
git log --stat
```

**这段脚本浓缩了一个独行者的完整流程**：**初始化 → 写代码 → 原子 commit → 修 message → 灾难 → 救回**。练熟这段，你在单机上就再也翻不了船。

## 十三、单机十诫

结束本章前，把这十条心法**贴在你显示器上方**：

1. **`git init` 后立刻建 `.gitignore`**。
2. **每次 `git add .` 之前，先 `git status`**。
3. **一个 commit 只做一件事**（用 `git add -p` 帮忙）。
4. **commit message 写给六个月后的自己**（Conventional Commits）。
5. **已推送的 commit 不要 `amend`，不要 `reset`**。
6. **`--hard` 是重炮，先想再打**。
7. **手滑了不要慌，先 `git reflog`**。
8. **敏感信息永远不 commit**——一次误操作，历史里永远洗不掉。
9. **每天至少一次 commit**——哪怕是 WIP，也是护身符。
10. **每周 `git gc`** ——清理垃圾对象，保持仓库健康。

## 下一章预告

到此为止，我们的世界还只有**一条时间线**。但真实开发不是这样——你会同时在做**主功能 + 热修 + 实验 + 重构**——四条线并行。

Git 用一个叫「**分支**」的东西解决了这个问题。它是 Git 之所以成为 Git 的**灵魂**——

- 分支为什么可以毫秒级创建？
- `merge` 和 `rebase` 到底选哪个？
- 冲突到底是怎么产生的？

**第 04 章 · 分支之灵魂所在**——每一个真正会用 Git 的开发者，都是分支的舞者。

> 「一条线只是记录，多条线才是创造。」
