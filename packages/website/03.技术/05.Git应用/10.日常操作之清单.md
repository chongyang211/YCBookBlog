## 引子 · 三个月练成 Git 老兵

小李当年学 Git，看了三本书、五个视频，还是每次要打开搜索引擎。直到有一天，一位老兵告诉他：

> 「你不缺知识，缺的是**手感**。」

老兵给他布置了三个月的训练计划：

- **第 1 个月**：每天故意用 `git reflog` 至少一次——熟悉「找回失踪 commit」。
- **第 2 个月**：每天 `git add -p` 至少一次——熟悉「原子 commit」。
- **第 3 个月**：每天 `git rebase -i` 至少一次——熟悉「重写私有历史」。

三个月后，小李在团队里开始成为「大家有事都找的那个人」。

**这就是本章的目标——** 把书里的知识变成手下的反射。

## 二、每日必练的十套组合拳

每套组合拳都是「3~5 条命令 + 1 句心法」，练到不需要看笔记为止。

---

**组合拳 1 · 开工同步三连**

```bash
git switch main
git fetch origin
git rebase origin/main
```

**心法**：**每天早上第一件事**——同步。手上永远拿着最新的 main。

---

**组合拳 2 · 建分支写代码**

```bash
git switch -c feat/task-123
# ... 写代码 ...
git add -p
git commit -m "feat(task): concise message"
```

**心法**：**分支要短命，commit 要原子**——两条铁律。

---

**组合拳 3 · 提交前自 review**

```bash
git status -s
git diff --staged
git log --oneline -n 5
```

**心法**：**push 之前先自审**——省下一半 review 意见。

---

**组合拳 4 · rebase 保持干净**

```bash
git fetch origin
git rebase origin/main
# 有冲突：解决 → git add → git rebase --continue
git push --force-with-lease           # 私有分支才能强推
```

**心法**：**push PR 前先 rebase main**——PR 变成漂亮的 fast-forward。

---

**组合拳 5 · 交互式整理 commit**

```bash
git rebase -i HEAD~5
# 编辑：pick / reword / squash / fixup / drop
git push --force-with-lease
```

**心法**：**push 前把碎 commit 整理成 1~3 个漂亮的**——reviewer 会爱你。

---

**组合拳 6 · 临时救火**

```bash
git stash push -u -m "wip"
git switch hotfix
# ... 救火 ...
git switch -
git stash pop
```

**心法**：**用 `-u` 记得**——不然新建的文件不会被 stash。

---

**组合拳 7 · 找回失踪的 commit**

```bash
git reflog
git switch -c rescue HEAD@{N}     # 或者 git reset --hard HEAD@{N}
```

**心法**：**只要 commit 过就有救**——reflog 是 30 天后悔药。

---

**组合拳 8 · 摘一颗别处的樱桃**

```bash
git switch target-branch
git cherry-pick <commit-id>
# 冲突：解决 → git add → git cherry-pick --continue
```

**心法**：**cherry-pick 一次一颗**——多了就 merge。

---

**组合拳 9 · 找 bug 引入者**

```bash
git bisect start
git bisect bad
git bisect good v1.0.0
# 反复：测试 → git bisect good/bad
git bisect reset
```

**心法**：**200 步 → 8 步**——二分查找的力量。

---

**组合拳 10 · 收尾归档**

```bash
git switch main
git pull
git branch -d feat/task-123
git push origin --delete feat/task-123
```

**心法**：**合并后立刻删分支**——公共仓库不留野草。

---

**十套组合拳，覆盖 90% 的日常**。**每套练 100 次**，你的手就再也不用问脑子。

## 三、一次完整的交付：从 0 到上线

**把上面十套组合拳串联起来**——这是一次「典型交付」的完整节奏。假设任务：**给博客加暗黑模式**。

```bash
# ────── 第 1 步 · 拿到任务 ──────
# 从 Jira / GitHub Issue 拿到任务号：#234

# ────── 第 2 步 · 开工同步 ──────
git switch main
git fetch origin
git rebase origin/main

# ────── 第 3 步 · 建分支 ──────
git switch -c feat/234-dark-mode

# ────── 第 4 步 · 上午：加基础主题 ──────
# ... 写主题 CSS 变量 ...
git add -p
git commit -m "feat(theme): add CSS variables"

# ... 写 useTheme hook ...
git add -p
git commit -m "feat(theme): add useTheme hook"

# ────── 第 5 步 · 中午：救火中断 ──────
# 收到消息：线上有个空指针崩溃
git stash push -u -m "wip: dark mode"
git switch main
git switch -c hotfix/npe

# ... 修 bug ...
git commit -am "fix: prevent NPE in login"
git push -u origin hotfix/npe
gh pr create --title "fix: prevent NPE in login" --body "..."

# 回来
git switch feat/234-dark-mode
git stash pop

# ────── 第 6 步 · 下午：加 toggle 组件 + 测试 ──────
# ... 写 ThemeToggle 组件 ...
git add -p
git commit -m "feat(theme): add toggle component"

# ... 写单测 ...
git add -p
git commit -m "test(theme): add theme tests"

# ────── 第 7 步 · 提 PR 前：自 review ──────
git status -s
git diff origin/main..HEAD
git log --oneline

# ────── 第 8 步 · rebase 保持 PR 干净 ──────
git fetch origin
git rebase origin/main

# 若冲突：解决 → git add → git rebase --continue

# ────── 第 9 步 · 整理 commit ──────
git rebase -i origin/main
# 把 4 个 commit 整理成 2 个：
# - feat(theme): support dark mode
# - test(theme): add coverage

# ────── 第 10 步 · 推送 + PR ──────
git push -u origin feat/234-dark-mode
gh pr create --title "feat(theme): support dark mode" \
             --body "Closes #234\n\n- 支持系统偏好\n- 支持手动切换\n- 附完整单测"

# ────── 第 11 步 · Review 后修改 ──────
# ... 根据 reviewer 意见改 ...
git commit -am "fix: address review comments"
git push

# 或者压回原 commit：
git rebase -i origin/main
git push --force-with-lease

# ────── 第 12 步 · 合并后收尾 ──────
# PR 被 merge 之后：
git switch main
git fetch origin
git rebase origin/main
git branch -d feat/234-dark-mode
git push origin --delete feat/234-dark-mode

# ────── 第 13 步 · 打 tag 发布（如果这次交付是版本发布点） ──────
git tag -a v1.5.0 -m "Release 1.5.0: dark mode support"
git push origin v1.5.0
# 或者用 semantic-release 全自动化
```

**这套 13 步流水线**——是一位资深开发者的「一次完整交付」。**从「有需求」到「上线归档」，涵盖了本书前九章的每一个知识点**。

**把这套流水线复现 20 次，你就是资深开发者**。

## 四、老兵的私房 alias

把下面这份配置粘贴到 `~/.gitconfig`——**你的 Git 手速会翻倍**：

```ini
[alias]
    # 基础缩写
    st = status -s
    co = checkout
    sw = switch
    br = branch
    cm = commit -m
    ca = commit --amend --no-edit
    caa = commit --amend
    unstage = restore --staged

    # 日志三兄弟
    lg = log --oneline --graph --all --decorate
    lgs = log --oneline --graph --all --decorate --stat
    last = log -1 HEAD --stat

    # 同步四件套
    sync = "!git fetch origin && git rebase origin/main"
    up = "!git fetch origin && git rebase origin/$(git branch --show-current)"

    # 分支管理
    brm = branch --merged
    brn = branch --no-merged
    clean-branches = "!git branch --merged main | grep -v main | xargs -n 1 git branch -d"

    # 撤销
    undo = reset --soft HEAD~1
    redo = reset HEAD@{1}

    # PR 三兄弟（配合 GitHub CLI）
    pr = "!gh pr create"
    prs = "!gh pr list"
    prv = "!gh pr view --web"

    # 特种兵
    hide = stash push -u -m
    unhide = stash pop
    hides = stash list

    # 排查
    who = blame -w
    when = log --follow -p

[color]
    ui = auto

[core]
    editor = code --wait
    autocrlf = input        # macOS/Linux
    excludesfile = ~/.gitignore_global

[pull]
    ff = only               # 拉取只允许 fast-forward

[push]
    autoSetupRemote = true  # 首次 push 自动 -u
    default = simple

[rebase]
    autoStash = true        # rebase 前自动 stash，完事自动 pop

[merge]
    conflictstyle = diff3   # 冲突显示三方 diff（更清楚）

[diff]
    algorithm = histogram   # 更聪明的 diff 算法

[init]
    defaultBranch = main

[user]
    name = 你的名字
    email = your@email.com
```

**配好之后**，日常用起来是这样：

```bash
git st                # git status -s
git lg                # 漂亮的图形化日志
git sync              # 同步 main
git up                # 同步当前分支
git undo              # 撤销上一个 commit
git hide "wip"        # stash
git unhide            # stash pop
git clean-branches    # 清理已合并分支
```

## 五、老兵的私房配置

**除了 alias，还有一些「隐性提速」配置**：

### 5.1 全局 gitignore

```bash
# 建立全局 gitignore
cat > ~/.gitignore_global <<EOF
# macOS
.DS_Store
.AppleDouble
.LSOverride

# Windows
Thumbs.db
Desktop.ini

# Linux
*~
.fuse_hidden*

# IDE
.vscode/
.idea/
*.swp
*.swo

# 环境变量
.env.local
EOF

git config --global core.excludesfile ~/.gitignore_global
```

**效果**：**再也不用给每个项目单独忽略 `.DS_Store`**。

### 5.2 让 diff 更好看

```bash
# 安装 diff-so-fancy 或 delta
brew install git-delta                # macOS
```

在 `~/.gitconfig`：

```ini
[core]
    pager = delta

[interactive]
    diffFilter = delta --color-only

[delta]
    navigate = true
    line-numbers = true
    side-by-side = true
```

**效果**：`git diff` 从灰扑扑的文本，变成 IDE 般的高亮体验。

### 5.3 自动填 SSH passphrase

```bash
# macOS
# 在 ~/.ssh/config
Host *
  AddKeysToAgent yes
  UseKeychain yes
  IdentityFile ~/.ssh/id_ed25519

# Linux（用 keyring）
ssh-add ~/.ssh/id_ed25519
```

**效果**：**每天开机敲一次 passphrase，一整天不再问**。

## 六、七大高频快捷键

如果你用 Terminal + Vim，下面这几个组合是 Git 操作的高频加速：

| 快捷键 | 场景 | 说明 |
|---|---|---|
| `!!` | 上一条命令 | `sudo !!` 用管理员权限重跑 |
| `!git` | 最近的 git 命令 | 快速重复 |
| `Ctrl+R` | 搜索历史 | 输入片段找历史命令 |
| `Alt+.` | 上一条命令的最后一个参数 | `git commit -m` 之后 `git tag Alt+.` |
| `Ctrl+W` | 删除前一个词 | 打错命令快速修正 |
| `Ctrl+U` | 清空当前行 | 一秒重来 |
| `Ctrl+A/E` | 光标到行首/行尾 | 修改长命令必备 |

**用一个月，你的键盘输入速度会翻倍**。

## 八、成长路径：从入门到大师的五重境界

技术成长不是线性的，而是**分阶段跃迁**的。Git 也一样——从新手到大师，可以清晰地划分为五个境界。**看看你在哪一重**，也就知道下一步该往哪走。

### 8.1 五重境界详解

| 境界 | 特征 | 代表能力 | 大约用时 |
|---|---|---|---|
| 🥉 **入门（Novice）** | 靠搜索引擎和 GUI 生存 | 会 clone / pull / commit / push 四条命令 | 1 周 |
| 🥈 **熟练（Practitioner）** | 命令行独立工作，能解基本冲突 | branch、merge、rebase、stash 都会用 | 3 个月 |
| 🥇 **进阶（Advanced）** | 理解对象模型，能优雅处理复杂场景 | reflog 救命、rebase -i 整理、cherry-pick、bisect | 1 年 |
| 💎 **专家（Expert）** | 能设计团队工作流，能急救复杂事故 | 制定 branching strategy、写 hooks、hooks CI 集成 | 3 年 |
| 🏆 **大师（Master）** | Git 内化为呼吸，能贡献 Git 本身或工具生态 | 读 Git 源码、造轮子、给团队/社区做导师 | 5+ 年 |

### 8.2 每一重的「毕业标准」

**入门 → 熟练**（毕业作业）：

- ✅ 能不看笔记完成本章的「十套组合拳」
- ✅ 能独立解决 add/commit/pull/push 的日常需求
- ✅ 能给一个 GitHub 项目提 PR

**熟练 → 进阶**：

- ✅ 会用 `rebase -i` 整理 commit
- ✅ 会用 `reflog` 救回失踪 commit
- ✅ 能给自己项目配 `.gitattributes` + hooks + CI
- ✅ 能在冲突时看懂 `<<<<<<< ======= >>>>>>>` 三段内容并合理决策

**进阶 → 专家**：

- ✅ 读过一遍 `.git/` 目录，能画出 object model 图
- ✅ 能在团队里当 Git 顾问，帮别人急救
- ✅ 能推动一次「工作流升级」（如从 Git Flow → Trunk-Based）
- ✅ 至少给一次开源仓库贡献代码（不是 typo 修正）

**专家 → 大师**：

- ✅ 读过一部分 Git 官方源码
- ✅ 写过至少一个 Git 工具或插件
- ✅ 在公司/社区内是「Git 之神」，别人有事找你
- ✅ 能从 first principles 讨论 VCS 未来（如 Sapling、Jujutsu、Pijul）

### 8.3 加速跃迁的三个策略

**策略 1 · 输出倒逼输入**

- 每个月写 1 篇 Git 相关技术博客
- 每季度给团队做 1 次内部分享
- **你能讲清楚的，才是你真的懂的**

**策略 2 · 教学倒逼系统化**

- 找一位新人，做他的 Git mentor 3 个月
- 你会发现——**新人的每个「简单问题」，都在挑战你的知识边界**

**策略 3 · 开源倒逼实战**

- 找一个中等规模的开源项目，长期贡献
- 一次 rebase 20 个 commit、一次跨 3 个 fork 的 cherry-pick、一次给上游 upstream 大 PR——**这些经验，在自己公司项目里遇不到**

**⚡ 一句话总结**：**境界不是靠年限熬出来的，是靠有意识地训练磨出来的**。

## 九、开源贡献指南：把 Git 用到真实世界里

一切 Git 技能，最终都要**在真实的开源项目中验证**。这是最好的练兵场——因为你要面对**陌生的代码风格、异步的沟通节奏、严格的 review 标准**。

### 9.1 找一个「刚刚好」的项目

**不要选**：

- ❌ Linux Kernel、Kubernetes 这类超巨型项目（门槛太高）
- ❌ 一个人维护的小工具（缺少协作练习价值）
- ❌ 完全不熟悉的领域（技术门槛消耗光协作精力）

**推荐选**：

- ✅ 100~10000 星、活跃维护（近 3 月有 commit）
- ✅ 有 `good-first-issue` / `help-wanted` 标签
- ✅ 有 CONTRIBUTING.md 说明贡献流程
- ✅ 你**日常在用、遇到过 bug 或痒点**的项目

**从哪找**：

- 🔍 <https://goodfirstissue.dev/>
- 🔍 <https://firstcontributions.github.io/>
- 🔍 <https://github.com/topics/good-first-issue>
- 🔍 GitHub 高级搜索：`is:issue is:open label:"good first issue" language:python`

### 9.2 一次标准的开源贡献流程

```bash
# ────── 阶段 1 · 准备 ──────
# 1) fork 到自己账号
gh repo fork owner/project --clone

# 2) 加 upstream 用于同步
cd project
git remote add upstream https://github.com/owner/project.git
git fetch upstream

# 3) 读 CONTRIBUTING.md、CODE_OF_CONDUCT.md、issue 模板
cat CONTRIBUTING.md

# ────── 阶段 2 · 开工 ──────
# 4) 从最新的 main 开新分支
git switch main
git rebase upstream/main
git switch -c fix/issue-123-typo

# 5) 写代码 + 遵守项目的 lint / test / commit 规范
npm run lint
npm test

# ────── 阶段 3 · 提交 ──────
# 6) 原子 commit + Conventional Commits 风格
git add -p
git commit -m "fix(auth): handle empty username edge case

Closes #123

Signed-off-by: Your Name <you@email>"

# 7) 同步 upstream 再 rebase 一次
git fetch upstream
git rebase upstream/main

# 8) push 到自己的 fork
git push -u origin fix/issue-123-typo

# ────── 阶段 4 · PR ──────
# 9) 提 PR（引用 issue、写清楚 why + how + test）
gh pr create --title "fix(auth): handle empty username" \
             --body-file .github/PULL_REQUEST_TEMPLATE.md

# ────── 阶段 5 · Review 循环 ──────
# 10) 有反馈？改代码 → 补 commit（或 fixup）→ push
git commit --fixup=<原 commit sha>
git push

# 11) 合并前如果 reviewer 要求「squash」，用 autosquash
git rebase -i --autosquash upstream/main
git push --force-with-lease

# ────── 阶段 6 · 合并后 ──────
# 12) 更新自己的 main
git switch main
git rebase upstream/main
git push origin main

# 13) 删掉本地和 fork 的分支
git branch -d fix/issue-123-typo
git push origin --delete fix/issue-123-typo
```

### 9.3 开源礼仪 Top 10

1. **先看有没有类似 PR/issue**——不要重复劳动。
2. **先在 issue 里讨论方案再动手**——避免写完被拒。
3. **PR 要小要专注**——一个 PR 只做一件事。
4. **commit message 讲清楚 why**——不是 what。
5. **测试要跟上**——没测试的 PR 优先级极低。
6. **代码风格 100% 遵循项目**——不要用你的偏好挑战别人的规范。
7. **文档 + Changelog 都要更**——别让 reviewer 提醒。
8. **回复 review 意见要礼貌 + 及时**——沉默一周相当于放弃。
9. **合并后写感谢帖**——@ 感谢 reviewer 和维护者。
10. **持续贡献同一项目**——单次贡献是打卡，持续贡献才是成长。

### 9.4 开源作为「简历」

**HR / 面试官眼中的开源画像**：

| 阶段 | 特征 | 简历价值 |
|---|---|---|
| 💡 提过 1~3 个 PR | 有基本贡献经历 | 加分项 |
| 🔥 长期贡献某项目 | 熟悉一个中大型项目内部 | 亮眼 |
| 🚀 自己维护有一定用户的项目 | 有开源作品 | 面试直通车 |
| 🌟 是某项目的 committer / maintainer | 已经在世界舞台上 | offer 抢着给 |

**⚡ 一句话总结**：**开源是最公平的舞台**——不看学历、不看背景，只看你 commit。

## 十、Git 面试高频题：能答上来说明你真的懂了

按频率整理的 **20 道高频面试题**——每题给出「一句话答案 + 深入回答」。如果你能全部答上来，你的 Git 就到了**熟练偏进阶**的水平。

### 🟢 基础层（新手常问）

**Q1 · git pull 和 git fetch 的区别？**

- **一句话**：fetch 只拉不合，pull = fetch + merge。
- **深入**：老手基本不用 pull，用 `fetch + merge/rebase` 分两步，明确性大于自动化。

**Q2 · git merge 和 git rebase 的区别？**

- **一句话**：merge 保留分叉历史，rebase 让历史变直线。
- **深入**：merge 更真实、可追溯；rebase 更整洁、便于 review。公共分支必用 merge，私有分支推荐 rebase。

**Q3 · git reset 三种模式的区别？**

- **一句话**：soft 只动 HEAD、mixed 动 HEAD+index、hard 动 HEAD+index+worktree。
- **深入**：hard 是最危险的——但只要 commit 过，reflog 30 天可救。

**Q4 · git revert 和 git reset 的区别？**

- **一句话**：reset 改历史，revert 加新 commit 反做。
- **深入**：公共分支只能 revert；私有分支两者都行。

**Q5 · `.git/` 目录里有什么？**

- **一句话**：objects（数据）+ refs（指针）+ HEAD（当前指针）+ index（暂存区）+ config + hooks + logs。
- **深入**：objects 分 loose 和 pack；refs 又分 heads / tags / remotes；HEAD 内容通常是 `ref: refs/heads/main`。

### 🟡 进阶层（有几年经验会问）

**Q6 · Git 的存储模型是「差量」还是「快照」？**

- **一句话**：**快照**——每次 commit 保存完整的树，未变的文件复用旧对象。
- **深入**：只有在 packfile 中才用 delta 压缩，那是**存储优化**，不是**逻辑模型**。区分「逻辑快照」与「物理 delta」是关键。

**Q7 · SHA-1 会碰撞吗？Git 未来会用什么？**

- **一句话**：2017 年 Google 已证明 SHA-1 可碰撞（SHAttered），Git 正在迁移到 SHA-256。
- **深入**：Git 2.29 起支持 SHA-256 仓库，但生态兼容仍在推进；平台侧（GitHub/GitLab）已经加了 collision detection 补丁。

**Q8 · 什么是 detached HEAD？**

- **一句话**：HEAD 直接指向 commit 而不是 branch 时，进入 detached 状态。
- **深入**：这时的 commit **不属于任何分支**，一旦切走就会被 gc；救命方法：`git switch -c rescue`。

**Q9 · git stash 底层是什么？**

- **一句话**：**是三个 commit**——工作区、暂存区、（可选）untracked，存在 `refs/stash` 引用上。
- **深入**：所以 stash 也是可以救回的，只要它没被 gc。

**Q10 · reflog 保留多久？在哪配置？**

- **一句话**：默认 90 天（HEAD）/ 30 天（不可达对象），`gc.reflogExpire` 配置。
- **深入**：reflog 是**本地**的，push 不同步；所以「别人误操作我救不了」。

**Q11 · rebase -i 里的 pick / reword / squash / fixup / drop 区别？**

- **一句话**：pick 保留、reword 改 message、squash 合并且合 message、fixup 合并且丢弃 message、drop 删除。
- **深入**：配合 `commit --fixup=<sha>` + `rebase --autosquash` 可全自动整理 commit。

**Q12 · fast-forward merge 和 three-way merge 的区别？**

- **一句话**：ff = 分支只是「往前挪指针」，3-way = 需要造新 commit 融合两条分支。
- **深入**：`git merge --no-ff` 强制产生 merge commit，保留分支边界，便于回滚整个特性。

**Q13 · cherry-pick 和 rebase 有什么关系？**

- **一句话**：rebase 本质上是**批量的 cherry-pick + reset**。
- **深入**：这也是为什么 rebase 会「重新计算 SHA」——因为它相当于「重新提交」一遍。

### 🔴 高级层（老兵才会问）

**Q14 · `git push --force` 和 `--force-with-lease` 的区别？**

- **一句话**：force 无脑覆盖，force-with-lease 会检查远端有没有别人新 commit。
- **深入**：--force-with-lease **仍然不安全**（依赖本地 refs 是否最新），最安全的做法是先 `fetch` 再 push。

**Q15 · pack 文件是什么？为什么需要它？**

- **一句话**：把大量 loose object 压缩成一个大文件 + delta 编码，节省磁盘和网络传输。
- **深入**：`git gc` 会触发打包；`git verify-pack -v` 可以看内部结构。GitHub 有 midx 优化多 pack 场景。

**Q16 · 什么是 shallow clone？副作用？**

- **一句话**：`clone --depth 1` 只拉最新一个 commit，节省空间，但不能 push、bisect 也受限。
- **深入**：适合 CI 场景，不适合本地长期开发。可以后续 `git fetch --unshallow` 补齐。

**Q17 · submodule 和 subtree 怎么选？**

- **一句话**：submodule 是「指针 + 独立仓库」，subtree 是「代码合进主仓库」。
- **深入**：submodule 使用者痛苦（要 `--recursive`）、维护者简单；subtree 使用者简单、维护者复杂。多数情况推荐 subtree 或 monorepo 工具。

**Q18 · 什么是 packed-refs？**

- **一句话**：把 `refs/heads/xxx`、`refs/tags/xxx` 打包进单一文件 `packed-refs`，避免 inode 爆炸。
- **深入**：`git pack-refs` 手动触发；查找 ref 时优先 loose，再 fallback 到 packed。

**Q19 · git 传输协议有哪些？各有什么特点？**

- **一句话**：Smart HTTP（主流，443）、SSH（22，需要 key）、Dumb HTTP（老，纯静态）、git://（9418，明文无鉴权，几乎废弃）。
- **深入**：企业内网 SSH，穿越防火墙用 HTTPS。所有 pack 传输都会经过 negotiation 决定发送哪些 object。

**Q20 · Monorepo 的挑战？**

- **一句话**：仓库爆炸 → 需要 partial clone、sparse checkout、增量构建、并行 CI、代码所有权划分。
- **深入**：Google 用自研 Piper，Meta 转向 Sapling，微软用 VFS for Git / Scalar。中小团队用 Nx / Turborepo / Bazel 也能撑到千人规模。

**⚡ 一句话总结**：这 20 题**不是靠背，是靠悟**——真正用过、栽过跟头的人，答起来就像呼吸。

## 十二、把 Git 内化为呼吸

到这里，本书的所有知识、章法、命令、实战，都已经交到你手上了。剩下的只有一件事——**把它用到你每天的开发里**。

**Git 之道有三重境界**：

**第一重 · 会用**——记住命令，能应付日常。90% 的开发者停在这里。

**第二重 · 看透**——知道每条命令背后在改什么对象、什么指针、什么图。剩下 9% 到这里。

**第三重 · 忘我**——手指先动，脑子后到。你不再想「我应该用哪个命令」——你只想「我要做什么」，手就自动敲出正确的组合。**最后的 1%**。

**这本书**，是为了让你从第一重跨到第二重、从第二重跨到第三重。

**能不能到第三重，取决于你**——不取决于书。
