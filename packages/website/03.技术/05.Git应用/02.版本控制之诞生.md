## 本章位置

上一章我们画出了 Git 的**心智地图**——三区五态、DAG、SHA-1、四种对象、三种指针。你可能会问：**为什么 Git 要这样设计？**

本章回答两个「为什么」——

1. **为什么会有 Git？**（历史与需求）
2. **为什么 Git 长这个样子？**（设计原则）

理解这两个「为什么」，你后面学的每一条命令都会自然而然地站到正确的位置上。

## 引子 · 2005 年的那个夏天

那是 2005 年 4 月。

Linux 内核开发团队——地球上最大的开源协作项目——正在使用一个叫 **BitKeeper** 的商业版本控制工具。它是私有的、不开源的，但**免费给 Linux 内核用**。这是当时唯一能满足 Linux 内核规模需求的分布式版本控制系统。

然后，一场戏剧性的争端爆发了：Linux 阵营的一位开发者尝试**逆向工程 BitKeeper 的协议**。BitMover 公司愤怒地宣布——**从此收回免费授权**。

Linux 内核陷入了前所未有的危机——**几百万行代码、数千名贡献者，突然没有了协作工具**。

Linus Torvalds 面临三个选项：

1. 屈服，付钱给 BitMover；
2. 换用当时的开源工具——但没有一个能满足 Linux 内核的性能要求；
3. **自己写一个**。

**他选了第三条**。

- 4 月 3 日，Linus 开始写 Git 的第一行代码。
- 4 月 7 日，Git 的第一个版本已经能自举——Linus 用 Git 管理 Git 自己的源代码。
- 4 月 18 日，Linux 内核开始迁移到 Git。
- 6 月 16 日，Linux 2.6.12 正式发布——用 Git 管理。

**从零到管理世界上最大的开源项目，Linus 只用了两个月**。前 5 天，甚至只用了他一个人。

这个故事的意义远不止「Linus 很牛」——它揭示了一个深刻的事实：**当你把需求理解到极致，工具就会像水一样自然流出**。

## 二、没有版本控制的黑暗年代

### 2.1 手动备份的原始时代

在版本控制诞生之前，程序员靠什么保存历史？——**复制文件夹**。

```
├── my-project/
├── my-project-backup/
├── my-project-backup-final/
├── my-project-backup-final-v2/
├── my-project-backup-final-真的最终版/
└── my-project-backup-final-真的最终版-改完就交/
```

看到这，你一定笑了——因为这样的目录，至今还躺在你或你同事的电脑上。这就是**没有版本控制的痛**。

### 2.2 三大痛点：找不回、合不上、协不了

**痛点一：找不回。**「上周的那版是哪一个？」——只能靠文件名的自然语言约定，人一走神就废。

**痛点二：合不上。**两个人各改了同一个项目的不同部分，最后怎么合？——手动 diff、手动 copy，一个下午一晃就没了。

**痛点三：协不了。**三个人同时改？——大家在群里喊：「谁在改 login.js，不要动！」

版本控制的历史，就是逐一解决这三个痛点的历史：

| 年代 | 代表工具 | 解决了 |
|---|---|---|
| 1972 | **SCCS**（贝尔实验室） | 「找不回」——第一次支持文件版本回溯 |
| 1982 | **RCS** | 「找不回」——差量存储，节省空间 |
| 1986 | **CVS** | 「合不上」——支持多人协作合并 |
| 2000 | **Subversion（SVN）** | 「协不了」——原子提交、目录级版本 |
| 2005 | **Git** | 「离线也能协作 + 分支自由」 |
| 2008 | **GitHub** | 「协作的社交化」 |

**版本控制的进化史，本质是「让人越来越少地关心历史」的进化史**。

### 2.3 版本控制的四个世代

如果把上面这份年表再抽象一层，版本控制的历史可以清晰地分为**四个世代**——每一代都因为**上一代的天花板**而诞生：

**第一代 · 本地版本控制（1970s-1980s）**  
代表：**SCCS**（1972）、**RCS**（1982）。特点：把一个文件的多个版本压缩存到本地的 `,v` 文件里，用「差量存储」节省空间（这个思路影响了后来几乎所有 VCS）。**天花板**：只管一个文件、只在一台电脑上、无法多人协作。

- **有趣一点**：RCS 的差量存储采用「反向差量」——最新版本存全文，历史版本存 diff——这样看最新版最快。这个思路后来被 SVN 继承。

**第二代 · 集中式版本控制（1986-2010）**  
代表：**CVS**（1986）、**Subversion / SVN**（2000）、**Perforce**（1995）。特点：一个中央服务器保存全部历史，多个客户端 checkout 出来协作。**解决了**：多人协作、跨机器同步。**天花板**：网络断了就干不了活；中央服务器一挂全公司瘫痪；分支慢到不敢用。

- **有趣一点**：CVS 是从 RCS 的 Shell 脚本进化来的——它其实**只是给 RCS 加了一层网络协议**。这也解释了为什么 CVS 的很多设计缺陷（比如无法原子提交）是继承自 RCS 的历史包袱。

**第三代 · 分布式版本控制（2005-）**  
代表：**BitKeeper**（1998，先驱）、**Git**（2005）、**Mercurial / hg**（2005）、**Bazaar**（2005）、**Darcs**（2003）、**Fossil**（2007）。特点：每一个 clone 都是完整仓库；协作靠「推 / 拉 / 抓」而不是「借 / 还」。**解决了**：离线可用、无单点故障、分支便宜。

- **戏剧性时间点**：2005 年 4 月，一个月之内，Git、Mercurial、Bazaar 三大分布式 VCS 几乎同时诞生——因为大家都发现了同一个问题（SVN 不够用），也都看到了同一个解法（分布式）。**这是软件史上「时机成熟」的经典案例**——不是一个天才憋出来的，而是整个行业的集体觉醒。

**第四代 · 平台化协作（2008-）**  
代表：**GitHub**（2008）、**GitLab**（2011）、**Bitbucket**（2008）、**Gitea/Gitee**。特点：把 Git 包装成 SaaS，加上 PR / Issue / CI / Wiki / Actions……让 Git 从「工具」升级为「协作生态」。**解决了**：社交化协作、开源治理、DevOps 集成。**天花板**：中心化再度回归（GitHub 一挂，全球都急）——但和 SVN 时代不同，**技术层依然是分布式的**，任何一个 clone 都能顶上去。

> **⚡ 关键洞察**  
> 版本控制的进化，是一条**从「个人」→「团队」→「全球分布式」→「生态平台」**的清晰路线。每一代都不是推翻上一代，而是**站在上一代的肩膀上突破天花板**。理解了这四代，你就明白为什么 Git 是必然、GitHub 是必然。

## 三、集中式：SVN 的黄金十年

在 Git 出现之前，Subversion 是绝对的王者。它统治了 2000 到 2010 的十年——几乎所有大公司都在用它。

### 3.1 SVN 的核心心智

```
                    ┌───────────────────────┐
                    │   中央服务器（SVN）    │
                    │   ┌───────────────┐   │
                    │   │  所有历史      │   │
                    │   │  所有分支      │   │
                    │   └───────────────┘   │
                    └───────┬───────┬───────┘
                            │       │
                    ┌───────┘       └───────┐
                    ▼                       ▼
              ┌──────────┐            ┌──────────┐
              │ 开发者 A │            │ 开发者 B │
              │ 只有一份 │            │ 只有一份 │
              │ 工作副本 │            │ 工作副本 │
              └──────────┘            └──────────┘
```

**SVN 的世界观**：
- **唯一真相源**：中央服务器是唯一保存完整历史的地方。
- **开发者只是「借书人」**：本地只有当前版本的工作副本。
- **提交必须联网**：所有 `svn commit` 都要与中央服务器通信。

这个设计非常优雅——**中央权威、便于审计、简单直观**。它服务了整个软件行业整整十年。

### 3.2 SVN 的三大死结

但是随着开源项目的兴起，SVN 遇到了三个**结构性死结**——它们不是 bug，是**设计上的必然**：

**死结一：分支慢，慢到不敢用。**
- SVN 的分支是「服务器上的目录复制」。
- 一个大项目建分支要几分钟，删分支要几分钟，合并要几十分钟。
- **结果**：大家都怕建分支，都在 `trunk`（主线）上直接开发。

**死结二：离线什么也干不了。**
- 出差、坐飞机、断网——**你连 `svn log` 都跑不了**。
- 每一次 commit 都要等服务器响应，网络抖动就失败。
- **结果**：开发者的效率被网络绑架。

**死结三：中央服务器一挂，全公司瘫痪。**
- SVN 服务器崩了，整个团队集体停工。
- 磁盘损坏没备份？——**十年历史一朝清零**。
- **结果**：SVN 服务器成了单点故障，运维如履薄冰。

Linus 在 2005 年那个夏天看到了这三个死结——**他决定把整个模型倒过来**。

### 3.3 CVS → SVN 的进化启示

CVS 和 SVN 都是集中式，为什么 SVN 能取代 CVS 十年？答案很简单：**SVN 修好了 CVS 三个致命缺陷**——

**缺陷一：CVS 没有原子提交。**  
CVS 一次 commit 涉及多个文件时，是**逐个文件依次提交**——一旦中间网络断掉，就出现「一半文件提了、一半没提」的地狱状态。SVN 引入了「事务型提交」——**要么全部成功，要么全部回滚**。这一条改进，就让 SVN 从 CVS 手里抢走了大半市场。

**缺陷二：CVS 无法版本化目录。**  
在 CVS 里，「重命名一个目录」不是一个操作——你得删除旧目录、新建新目录、把每个文件挪进去，中间的历史全断了。SVN 把「目录」也当成一等公民版本化，`svn mv` 一条命令搞定。

**缺陷三：CVS 只能存文本文件，二进制处理差。**  
CVS 用「文本行 diff」思维处理一切，二进制文件的差量算法糟糕。SVN 内置了对二进制的「二进制 diff」（xdelta 算法），存储效率翻倍。

**这段历史给我们的启示是**：**下一代工具，永远是通过修复上一代的具体痛点而胜出**。Git 之于 SVN，也是同样的路径——只是它修的痛点更狠，直接把「集中式」这个前提都翻了。

**⚡ 冷知识**  
- SVN 的作者 Karl Fogel 后来写了本书叫《Producing Open Source Software》，是开源治理的经典。
- SVN 的核心贡献者 Ben Collins-Sussman 后来加入 Google，成了 Chromium 项目早期的技术骨干——**从「集中式教父」到「Git 用户」的身份转变，正是行业变迁的缩影**。

## 四、Git 的登场：两周颠覆一个时代

### 4.1 BitKeeper 事件的完整时间线

前文引子里已经速写了那两个月的高潮，这里把**完整的时间线**摆出来——因为它是软件史上少有的「危机催生传奇」案例：

| 日期 | 事件 |
|---|---|
| 2002 · 2 月 | Linux 内核开始使用 **BitKeeper**（商业闭源工具，免费给开源用）。此前 Linux 用一个叫「patch + tarball」的原始工作流，2.2/2.4 都靠邮件补丁维护。 |
| 2002-2005 · | Linus 用 BitKeeper 三年，深度体验了「分布式」的巨大好处。他心里已经有了「分布式 VCS 应该长什么样」的完整轮廓。 |
| 2005 · 4 月 3 日 | Andrew Tridgell（Samba 作者）逆向 BitKeeper 协议——BitMover CEO Larry McVoy 愤怒宣布**收回免费授权**。 |
| 2005 · 4 月 6 日 | Linus 在邮件列表宣布：「**我要自己写一个 SCM**。」——这就是 Git 的第一次公开亮相。 |
| 2005 · 4 月 7 日 | Git 第一个原型完成。**当天**，Linus 就用 Git 提交了 Git 自己的第一个 commit——**Git 开始自举**。 |
| 2005 · 4 月 18 日 | Git 第一次 merge 成功。这一天是 Git 真正「可用」的分水岭。 |
| 2005 · 4 月 29 日 | Git 的性能测试：**打包 Linux 内核历史的速度已达每秒 6.7 MB**。 |
| 2005 · 6 月 16 日 | Linux 2.6.12 用 Git 发布——**Git 正式成为 Linux 内核的官方 SCM**。 |
| 2005 · 7 月 26 日 | Linus 把 Git 的维护权移交给 Junio C Hamano——**Linus 只想造工具，不想天天当版本工具的维护者**。Junio 至今仍是 Git 的首席维护者（已 20 年）。 |
| 2005 · 12 月 | Git 1.0 发布。 |

**几个值得咀嚼的细节**：

- **Linus 只当了 3 个月 Git 项目的领导人**。他造完就跑了——把维护权交给了 Junio。这个决定后来被证明**极其明智**：Linus 是天才架构师但不喜欢日常运维；Junio 是耐心细致的工程师但缺少破坏性创新——**两人的接力，恰好符合每一段的需要**。
- **Andrew Tridgell 的「逆向工程」到底做了什么**？他其实只是用 telnet 连到 BitKeeper 端口，敲了几行命令看看协议——一个再普通不过的探测行为。但这在 McVoy 眼里越过了红线。**一个几分钟的动作，间接催生了统治世界的工具**。
- **BitKeeper 后来的命运**：2016 年 5 月，BitMover 宣布 BitKeeper **开源**——用的是 Apache 2.0 许可证。但**为时已晚**——Git 已经统治了世界。这是「开源就是护城河」的活教材。

### 4.2 Linus 的四条设计原则

Linus 在 Git 的第一封邮件（2005 年 4 月）中，写下了四条**永远不能违反的原则**：

**原则一：速度。**
- 一切操作必须是**毫秒级**。
- 分支创建、切换、diff、log——全都不能等。
- **背后的技术**：内容寻址 + 本地对象数据库。

**原则二：分布式。**
- 每个开发者的电脑，都是一个**完整的仓库副本**。
- 没有「中央服务器」这种特权节点——任何一台机器崩了都不会丢历史。
- **背后的技术**：DAG + SHA-1 全局唯一 ID。

**原则三：完整性。**
- 任何数据**一 bit** 的损坏都能被立刻发现。
- 依靠 SHA-1 哈希——**内容变了，哈希就变了**。
- **背后的技术**：Merkle 树 + 内容寻址。

**原则四：非线性开发的强大支持。**
- 分支必须像换衣服一样容易——建、切、合、删都要毫秒级。
- **背后的技术**：分支只是「40 字节的文件」（指向 commit 的引用）。

**四条原则，四把利刃，正好戳向 SVN 的四个死穴。**

### 4.3 Git 是如何解开 SVN 三大死结的

| SVN 的死结 | Git 的破法 | 底层技术 |
|---|---|---|
| **分支慢** | 分支只是一个 40 字节的文本文件 | `refs/heads/*` |
| **离线不能干活** | 每个 clone 都是完整仓库 | 本地 `.git/objects/` |
| **中央服务器单点故障** | 任何一个 clone 都可以成为「中央」 | 分布式 DAG |

**顺带解决的赠品**：
- **原子提交**：不再有「提了一半」的中间态。
- **数据完整性**：SHA-1 校验每一 bit。
- **可自证的历史**：改任何一个字节，后续所有 SHA-1 全变——**篡改历史是数学上不可能的**。

> **⚡ 关键洞察**  
> Git 的每一个设计选择，都是**逆着 SVN 的某个痛点**做出来的。
> 理解了 SVN 的痛，你就理解了 Git 的每一个「反常识」的设计——为什么本地要存所有历史、为什么分支这么便宜、为什么 commit ID 不是自增的数字。

### 4.4 「Git」这个名字的由来

「Git」这个名字，是 Linus 自己起的。它在英式英语里是一句**骂人话**——大致相当于「混蛋、蠢货、讨厌鬼」（an unpleasant person，尤其是自负而讨人嫌的那种）。

Linus 在 Git 的官方 man page 里写了三种「官方解释」，一本正经地胡说八道：

> **"Git" can mean anything, depending on your mood.**
>
> - random three-letter combination that is pronounceable, and not actually used by any common UNIX command.
> - stupid. contemptible and despicable. simple. Take your pick from the dictionary of slang.
> - "global information tracker"（全球信息追踪器）: you're in a good mood, and it actually works for you.
> - "goddamn idiotic truckload of sh\*t"（该死的愚蠢的一大堆屎）: when it breaks.

翻译过来是：**「Git 可以表示任何东西，取决于你此刻的心情」**——从「全球信息追踪器」到「该死的一大堆屎」都行。这是 Linus 一贯的自嘲式幽默——他在给自己的项目取名时，特意**留了个骂自己的接口**。

**Linus 有一个梗**：他喜欢用自己的名字命名重大项目：**Linux** = Linus + Unix，**Git** = Linus 说自己是 git（对 Linux 内核社区一位曾用「BitKeeper 不该被逆向」立场的人）。他曾开玩笑：「我把所有工具都用『我』命名——因为我懒得为它们想名字。」

### 4.5 Linus 早期邮件摘译：从零到自举的两周

Git 的诞生过程有大量原始邮件保留在 LKML（Linux Kernel Mailing List）里，是研究「顶级工程师如何思考问题」的绝佳素材。这里摘译几段——

**2005 年 4 月 6 日，宣战邮件（LKML）**：

> "我不是在开玩笑。我要写一个新的 SCM，它必须满足几个铁律——**速度、简单、支持非线性开发、完全分布式、能高效处理像 Linux 内核这么大的项目**。它绝对不会是 CVS，也不会是 SVN——那两个我都受够了。"

**2005 年 4 月 7 日，第一个自举 commit 的 message**：

> "**Initial revision of "git", the information manager from hell.**"（"git"——地狱来的信息管理器——的第一版）

——**Linus 用他标志性的自嘲，给 Git 打了一个「地狱来的」标签**，一并留在 Git 项目自身的历史里。这个 commit 至今可以在 Git 的源代码仓库里找到：`git log --reverse` 到底就是。

**2005 年 4 月 8 日，关于「快」的邮件**：

> "如果你觉得 SCM 应该慢，那你就没有真正用过一个快的 SCM。**任何超过一秒的操作都是不可接受的**——因为它会打断我的思路。人一分心，代码就废了。所以 Git 的所有操作，必须在**眨眼之间**完成。"

——这段话后来被广泛引用，是「工具影响思维」这一命题的经典表述。

**2005 年 4 月 11 日，关于「分布式」的邮件**：

> "**每一个 clone 都是一个完整的仓库**，这不是可选的，这是必须的。因为我不相信任何一台服务器不会坏、任何一个人不会走。**唯一可靠的备份策略，是让每一个开发者都成为一个备份**。"

——这段话后来被 GitLab 引用在其官方博客里，用来解释「为什么去中心化的 Git 反而比中心化的 SVN 更抗风险」。

> **⚡ 一句话**  
> 读 Linus 2005 年的邮件，你会发现——**Git 的每一个设计，都是有明确目标的**。它不是天才的灵光一现，而是**对痛点极度清醒之后的系统性回答**。这才是「优秀设计」的真正样子。

## 五、心智模型剖析：Git 的三块基石

现在，我们要打开 Git 的引擎盖。**Git 的整个世界，只由三种基础对象搭建起来**——blob、tree、commit。

### 5.1 内容寻址：blob 对象

**blob（Binary Large Object）** 是最底层的对象——它存储**一个文件的内容**。

**关键点**：
- blob **不存文件名**——它只存内容。
- blob 的 ID = **SHA-1(内容)**——**内容相同，ID 就相同**。
- 两个不同路径的文件，只要内容一样，就只存一份 blob。

```
文件 A：  README.md    "Hello Git"
文件 B：  copy.md      "Hello Git"

     ▼                        ▼
   ┌──────────────────────────────┐
   │  blob: a1b2c3...             │
   │  content: "Hello Git"        │
   └──────────────────────────────┘
                （只存一份！）
```

**这就是「内容寻址」——用内容本身生成地址，天然去重**。GitHub 上任何两个仓库里，只要有一段代码内容相同，理论上底层都指向同一个 blob。

### 5.2 目录快照：tree 对象

**tree** 记录一个目录里都有什么——**它是文件名的守护者**。

```
tree（根目录）
├── blob a1b2c3... "Hello Git"           README.md
├── blob d4e5f6... "console.log('hi')"   src/main.js
└── tree 789abc...（子目录 src）
    └── blob d4e5f6... "console.log('hi')"   main.js
```

**关键点**：
- 每一条记录 = **模式 + 类型 + SHA-1 + 名称**。
- tree 自己的 ID 也是 SHA-1（对整个清单做哈希）。
- 目录不变 → tree 不变 → 复用。

这就是 Git **快照式**存储的秘密——它不像 SVN 那样存 diff，它**直接快照整棵目录树**。因为有内容寻址，快照并不占用多少额外空间——**没变的部分共享同一个 blob/tree**。

### 5.3 时间机器：commit 对象

**commit** 是快照的封面——它把 tree 变成「一次可回溯的历史事件」。

一个 commit 对象包含：

```
tree     b8c3a1... （指向根目录的 tree）
parent   4e5f6a... （上一个 commit 的 SHA-1，可能有 0~N 个）
author   xxx <email> 2025-06-23 10:00:00 +0800
committer xxx <email> 2025-06-23 10:00:00 +0800

feat: add login page
```

**关键点**：
- **每个 commit 记住自己的父提交**——这就是 DAG 有向无环图的边。
- commit 自己也是 SHA-1——**它的 ID 由它的整个 tree + parents + 元数据共同哈希**。
- **改任何一个字节，SHA-1 就会变，后续所有 commit 的 SHA-1 全部级联变化**——这就是 Git 的**防篡改**基础。

### 5.4 三块基石的化学反应

三种对象一叠加，Git 的所有魔法就浮现了：

```
                 commit（v3）
                     │
                     ▼
                   tree（根）
                  /    \
              blob     tree（子目录）
                        │
                        ▼
                       blob
```

**每一次 commit 都是一次完整的目录快照**——但因为内容寻址，**没变的 blob/tree 直接复用**——所以既有「快照的简单」，又有「差量的节省」。

这就是 Git 的**魔法配方**：

```
   内容寻址（blob）
        +
    目录快照（tree）
        +
    父子链条（commit）
        =
    可回溯、可校验、可分布式的时间机器
```

### 5.5 对象在磁盘上真正长什么样

前面讲的都是「概念」，但**对象在磁盘上到底存成什么样**？让我们打开 `.git/objects/` 看看真相。

**Loose Object（松散对象）**——每个对象一个文件：

```
.git/objects/
├── 8a/
│   └── b686eafeb1f44702738c8b0f24f2567c36da6d   # 前 2 位是目录，后 38 位是文件名
├── e6/
│   └── 9de29bb2d1d6434b8b29ae775ad8c2e48c5391
└── ...
```

**每个文件的内容格式**（zlib 压缩前）：

```
<type> <size>\0<content>
```

举例：一个内容为 `Hello Git\n` 的 blob，未压缩时是：

```
blob 10\0Hello Git\n
```

- `blob`：对象类型（blob / tree / commit / tag）
- `10`：内容字节数
- `\0`：分隔符（一个 NUL 字节）
- `Hello Git\n`：真正的文件内容

然后**用 zlib 压缩**后存到磁盘上。**SHA-1 是对整个未压缩内容（`blob 10\0Hello Git\n`）算的**——所以类型和长度也参与哈希，这就杜绝了「不同类型对象碰撞出相同哈希」的可能。

**Packed Object（打包对象）**——当仓库变大后，Git 会执行 `git gc`，把大量松散对象压进一个 pack 文件：

```
.git/objects/pack/
├── pack-abc123.pack   # 打包后的对象内容（可能几 GB）
└── pack-abc123.idx    # 索引文件（能快速根据 SHA-1 找到对象在 pack 中的位置）
```

Pack 文件里的对象采用**差量压缩**（delta compression）——**注意：这不违反「Git 是快照」这个说法**。快照是**逻辑模型**（每次 commit 是完整快照），差量压缩是**物理存储优化**（磁盘上聪明地省空间）。这两层的分离，是 Git 设计的一大精妙——**逻辑简单，物理高效**。

**动手看一下**：

```bash
# 看仓库中所有松散对象
find .git/objects -type f -not -path "*/pack/*" | head

# 看 pack 文件的统计
git count-objects -v
# 输出：
# count: 12         ← 松散对象数
# size: 48          ← 松散对象总大小（KB）
# in-pack: 1234     ← 打包对象数
# packs: 1          ← pack 文件数
# size-pack: 5678   ← 打包对象总大小

# 查看某个对象的类型 / 大小 / 内容
git cat-file -t <SHA>   # 类型
git cat-file -s <SHA>   # 大小
git cat-file -p <SHA>   # 内容（漂亮打印）
```

> **⚡ 一句话**  
> Git 的存储是**「先快照、后差量」**——逻辑上快照，物理上差量。这就是它既容易理解、又足够高效的秘密。

## 六、SHA-1 危机与 SHA-256 迁移

Git 的整个体系建立在 SHA-1 之上。但**SHA-1 从 2005 年就已经被证明理论上不安全**——那 Git 为什么还敢用？后来又发生了什么？这是每个 Git 深度用户都该知道的一段历史。

**2005 · SHA-1 的理论警报**  
王小云教授（中国科学院院士）在 Crypto 2005 会议上发表论文，证明 SHA-1 的碰撞复杂度远低于设计目标——从 2⁸⁰ 降到 2⁶⁹ 左右。**这个警报，比 Git 诞生只晚了几个月**。

**2005-2017 · 十二年的「不慌」**  
在此期间，Linus 多次公开表态：「**Git 用 SHA-1 不是为了密码学安全，而是为了完整性校验**——防止硬件错误或无意错误，不是防止恶意攻击。就算 SHA-1 被攻破，Git 也不会立刻崩，因为攻击者还需要匹配文件长度、类型等元信息。」这段时间，SHA-1 破解的算力成本仍然让攻击者望而却步。

**2017 · SHAttered 攻击（震撼弹）**  
2017 年 2 月 23 日，Google 与 CWI Amsterdam 联合宣布——**他们成功造出了两个不同的 PDF 文件，具有完全相同的 SHA-1**。这是史上第一次**实际发生的 SHA-1 碰撞**。攻击代号「SHAttered」，用了约 6500 CPU-年 + 100 GPU-年的算力，成本约 11 万美元。

- **对 Git 的直接影响**：理论上，攻击者可以造出两个不同的 commit 或 blob，SHA-1 相同——从而在 push 时替换对方仓库的内容。
- **实际风险**：非常低。Git 仓库有多重防线（对象大小、类型标记、tree 结构），构造一个「实用的」碰撞对比 PDF 要难得多。
- **Git 团队的紧急响应**：立刻发布 `git 2.13.1`，加入 SHAttered 攻击的检测逻辑——Git 现在会主动识别 SHAttered 特征并拒绝该对象。

**2018-至今 · SHA-256 迁移**  
Git 从 2.29 版本（2020 年 10 月）开始，实验性支持 **SHA-256**。你可以在 `git init` 时指定：

```bash
git init --object-format=sha256 my-new-repo
```

- 新仓库的哈希会是 **64 位十六进制**（256 / 4）。
- 与 SHA-1 仓库**目前不能互操作**（GitHub 至 2025 年仍以 SHA-1 为主）。
- **完整迁移路径**（interop layer）还在讨论中——预计还要几年才能全生态跟上。

**Git 团队公开的迁移路线**：
1. **阶段一**（已完成）：SHA-256 单独可用。
2. **阶段二**（进行中）：SHA-1 ↔ SHA-256 双写、可互相引用。
3. **阶段三**（未来）：默认 SHA-256。
4. **阶段四**（长期）：完全废弃 SHA-1。

**几点你需要知道的**：

- **今天你用 Git 依然 100% 安全**——SHAttered 需要 11 万美元造一次碰撞，还只能碰撞两个特定构造的文件。日常开发无需担心。
- **如果你在做安全关键领域**（金融、军事、加密货币）——建议开启 SHA-256 或使用 GPG 签名（`git commit -S`）。
- **未来 5-10 年**，Git 生态将逐步迁移到 SHA-256——**你现在学的 Git，将会平滑过渡**。

> **⚡ 冷思考**  
> Linus 当年选 SHA-1，不是因为它「完美」，而是因为「够用而且快」。这就是**工程决策**——**在时代的约束下，做最合时宜的选择**。今天我们能在 20 年后从容迁移到 SHA-256，恰恰证明了这个决策的正确——**它给了我们足够长的窗口**。

## 七、动手实战：亲手复现 Git 的诞生

现在，我们要做一件疯狂的事——**不用 `git add`、不用 `git commit`，直接用底层命令造出一个 commit**。这段实战会让你**真正看清 Git 的骨骼**。

```bash
# 1. 建一个空仓库
mkdir git-genesis && cd git-genesis
git init

# 2. 手动造一个 blob（不用 git add）
echo "Hello Git" | git hash-object -w --stdin
# 输出：8ab686eafeb1f44702738c8b0f24f2567c36da6d（你的 SHA-1 会一样，因为内容相同）

# 3. 造第二个 blob
echo "Universe" | git hash-object -w --stdin
# 输出：另一个 40 位 SHA-1

# 4. 把两个 blob 组装成一个 tree
git update-index --add --cacheinfo 100644 \
  8ab686eafeb1f44702738c8b0f24f2567c36da6d README.md

git write-tree
# 输出：tree 的 SHA-1，比如 abc123...

# 5. 用 tree 造出第一个 commit（无父提交）
TREE=$(git write-tree)
echo "chapter 02 · genesis" | git commit-tree $TREE
# 输出：commit 的 SHA-1，比如 def456...

# 6. 把 HEAD 指向这个 commit（这一步等价于 git commit 的最后一步）
COMMIT=def456...
git update-ref refs/heads/main $COMMIT

# 7. 看看结果
git log --oneline
# 显示：def456 chapter 02 · genesis

# 8. 底层探索三种对象
git cat-file -t 8ab686e   # 输出：blob
git cat-file -t $TREE     # 输出：tree
git cat-file -t $COMMIT   # 输出：commit

git cat-file -p $COMMIT   # 看到 tree + author + message
git cat-file -p $TREE     # 看到 blob 的清单
git cat-file -p 8ab686e   # 看到内容：Hello Git
```

**你刚才做的事情，等价于 `git add + git commit` 的全部工作**——只是把它拆成了七步。

以后，你每敲一次 `git commit`，就知道 Git 在**底层实际做了什么**：

1. 把每个变化的文件写成 blob → `.git/objects/`
2. 把当前目录快照写成 tree → `.git/objects/`
3. 把 tree + 父提交 + 元数据 写成 commit → `.git/objects/`
4. 把当前分支的引用指向这个新 commit → `.git/refs/heads/*`

**四步，一步不多，一步不少**。

## 八、Git 20 年演进大事记

Git 从 2005 到 2025，走过了整整 20 年。这条时间线上有许多值得记忆的里程碑——你今天用的每一个「习以为常」的功能，都是某一天某一版本引入的：

| 时间 | 版本 | 里程碑 |
|---|---|---|

- **2008 · GitHub 上线**——Git 的杀手级应用。GitHub 不是 Git，但**它让 Git 成为「协作事实标准」**。没有 GitHub，Git 可能只是极客圈的玩具。
- **2019 · switch/restore**——这是 Git 团队近十年最大的可用性改进。承认「`checkout` 太万能了，用户学不会」，勇敢地拆成两个命令。**这一步过去，Git 才真正变得对新人友好**。
- **2020 · main 替代 master**——技术圈响应社会讨论的一次典型事件。GitHub 主导、Git 官方跟进——从此新仓库默认 `main` 分支。老仓库不强制迁移。
- **2020 · SHA-256**——为未来 10 年的 Git 铺路。

> **⚡ 一句话**  
> Git 20 年 = 前 5 年造出来 + 后 15 年不断打磨。**一个好的软件不是「一次做对」，而是「持续变对」**。

## 十、思考题

1. **如果两个开发者在两台断网的电脑上，都对同一份初始代码做了不同的修改，然后各自 commit——他们的 commit ID 会一样吗？** 为什么？
2. **SVN 的 revision 是自增数字（r1、r2、r3……），Git 的 commit 是 SHA-1**。分别有什么优缺点？
3. **假设你在 GitHub 上有一个 100MB 的仓库**——如果你把整个 `src/` 目录复制一份成 `src-backup/`，仓库会不会变成 200MB？为什么？
4. **一个 Git 仓库被恶意篡改了某个历史 commit 的内容**——普通用户能不能发现？依靠什么机制？
5. **假设 SHA-1 未来被彻底攻破**（能人为构造哈希碰撞）——Git 会遇到什么问题？（提示：Git 已经在 2018 年逐步支持 SHA-256）
