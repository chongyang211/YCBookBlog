## 1. 案例引入

### 1.1 照做被骂

上一篇里糖果充的对账系统 V2 上线成功，李姐日活起来了。三个月过去，某天早上李姐路过糖果充工位：

```
李姐:   "小杨, 你这个系统能不能加个导出 PDF 的功能?"
糖果充: "行, 简单, 我下周就加。"
李姐:   "好呀好呀, 加油!"
```

糖果充这次学乖了——照用户说的做嘛。两周后 PDF 导出功能上线，糖果充还特意告诉李姐："李姐，PDF 功能加好了！"

李姐："哦好的，谢谢。"

**又过了三个月**，糖果充在部门季度总结上顺手看了下 PDF 功能的使用数据：

```
月度导出 PDF 次数:   3 次
其中 2 次是糖果充自己测试的
李姐真实使用:        1 次
```

糖果充懵了。同一时期正好在电梯里遇到李姐，李姐说："**小杨啊，你那个 PDF 用不了，我还是自己复制到 Word 里的**。"

糖果充：**"我不是照你说的做了吗?!"**

回工位后，糖果充翻了 V2 的需求记录本，发现自己居然有 12 条这种需求：

```
需求 1:  加个 PDF 导出       实际用: 1 次
需求 2:  加个批量操作         实际用: 0 次
需求 3:  加个搜索框           实际用: 4 次
需求 4:  加个夜间模式         实际用: 0 次
需求 5:  加个数据备份         实际用: 2 次
需求 6:  加个自动定时提醒     实际用: 0 次
需求 7:  加个多语言支持       实际用: 0 次
需求 8:  加个操作日志         实际用: 0 次
需求 9:  加个用户权限         实际用: 0 次
需求 10: 加个自定义模板       实际用: 0 次
需求 11: 加个数据校验规则     实际用: 3 次
需求 12: 加个 API 对接        实际用: 0 次
```

**12 个需求全部照做，10 个 0 次使用**。糖果充花了 3 个月做了一堆没用的东西。

### 1.2 顺藤摸根因

带着这条线往下挖：

- **假设 1**：李姐在骗糖果充？——不是，李姐没有恶意，她是真的觉得"如果有会更好"
- **假设 2**：糖果充实现质量不行？——不是，PDF 导出功能技术上完美，UI 也参考了业内标准
- **假设 3**：李姐说的时候不专心？——不是，她当时正好在整理季度报表，是有真实场景的
- **假设 4**：那到底哪里错了？——**糖果充把"李姐说的话"当成了"李姐真正要的东西"**
- **假设 5**：这两者差在哪？——李姐说"加个 PDF 导出"是**手段**，她真正的**目的**是"给主管发一份不会被改乱格式的月度对账明细"
- **假设 6**：糖果充有没有可能一开始就问对？——有，只要多问一句"你打算拿这个 PDF 干嘛？"
- **假设 7**：这套"多问一句"有系统方法吗？——有，本篇的主线

仔细分析这次翻车的根因：

```
表象                              真实问题
──────────────────────────────────────────────────────
"用户说要 A, 我就做 A"          → 把手段当目的
"用户说的时候听着都合理"         → 用户嘴里全是"手段", 目的藏在后面
"12 个需求 10 个没用"            → 需求真伪不分, 全都照做
"实现质量没问题"                 → 需求方向错了, 质量再好也白搭
"李姐没投诉"                    → 中国式礼貌反馈, 没投诉 ≠ 在用
```

**根因**：糖果充**没有需求分析能力**。**只会当"需求翻译机"（用户说 A → 做 A），不会当"需求侦探"（用户说 A → 追问为什么要 A → 找到真正的价值 B）**。

这一段里至少藏着 8 个原理点：

```
① 用户嘴里的需求为什么不可信? 又不能不听?          → 第 2 章
② 从"用户说的"到"真正要的", 中间隔了几层?         → 第 3 章
③ 5Why 具体怎么问? 问过头会怎样?                  → 第 4 章
④ JTBD 是什么? 跟需求有什么不一样?                 → 第 5 章
⑤ 需求怎么分类? 真需求、伪需求、反需求、隐需求?     → 第 6 章
⑥ 12 个需求怎么筛出真正该做的 2 个?                → 第 6 章
⑦ 需求分析常见反模式?                              → 第 7 章
⑧ 硬件/算法/运维/传统行业的需求分析有什么变形?      → 第 8 章
```

### 1.3 要回答什么

这个事故就是本篇的**主线案例**。带着上面 8 个问号往下走。本篇路线：

```
需求分析四步 (第 2 章)
   ↓
剥洋葱四层 (第 3 章) ─→ 解开"用户嘴上说的和真要的差几层"
   ↓
5Why 追问法 (第 4 章) ─→ 解开"怎么问才能挖到根"
   ↓
JTBD 框架 (第 5 章) ─→ 解开"用户不是买产品, 是雇佣你去完成 Job"
   ↓
真伪反隐四类 (第 6 章) ─→ 解开"12 个需求哪 2 个真的该做"
   ↓
反模式 (第 7 章) + 跨岗位 (第 8 章)
   ↓
综合案例 (第 9 章) ─→ 糖果充重做 PDF 需求
```

📌 **本篇定位**：这是继"用户视角"之后的**具体方法**。第 1 篇教你"承认自己不是用户"，本篇教你"**怎么从用户身上挖出他自己都没意识到的真需求**"。读完本篇后再听需求，你会自然多问几句："为什么？你拿它干嘛？如果没有你怎么办？"

## 2. 分析全景图

### 2.1 分析四步

一次完整的需求分析，包含四步。少一步都会翻车：

```
┌───────────────────────────────────────────────────────────┐
│                    需求分析四步                             │
├───────────────────────────────────────────────────────────┤
│  ① 记录 (Record)        原样记下用户嘴里说的话              │
│  ② 追问 (Probe)         5Why / JTBD 追到深层动机            │
│  ③ 归类 (Classify)      真需求 / 伪需求 / 反需求 / 隐需求    │
│  ④ 决策 (Decide)        做 / 不做 / 转化 / 存档              │
└───────────────────────────────────────────────────────────┘
```

四步属性速查：

| 步 | 输入 | 输出 | 糖果充 V1 翻车点 |
|---|---|---|---|
| 记录 | 用户原话 | 完整语境的原话 | ✅ 做了 (但只记了话, 没记场景) |
| 追问 | 记录 | 深层动机 | ❌ 完全跳过 |
| 归类 | 深层动机 | 四类中的一类 | ❌ 全部当"真需求"处理 |
| 决策 | 归类结果 | 做/不做/转化 | ❌ 全部选"做" |

### 2.2 为什么这么切

需求分析不就是"用户说什么就记什么然后做出来"吗？为什么要切成四步？

**论证**：

**1.没记录就没原始证据**——三个月后你想复盘"当初为什么做 PDF"，只能靠回忆，回忆是不可靠的。**记录的价值 = 让需求可复盘**。糖果充 V1 有做（但只记原话，缺场景）。

**2.没追问就是需求翻译机**——用户嘴里的话有 90% 是**手段**，10% 是**目的**。不追问，你就是照抄手段的翻译机。**追问 = 从翻译机升级为侦探**。

**3.没归类就是需求垃圾场**——12 个需求同等对待，等于把真金和沙子搅一起。归类之后你会发现，12 个里可能只有 2 个是真需求，3 个是伪需求（可以否），5 个是反需求（做了反而害用户），2 个是隐需求（用户没说但真正想要的）。**归类 = 需求的分诊台**。

**4.没决策就是无脑照做**——分析完不落地在"做/不做"上，前三步白做。**决策的关键是敢说"不做"**——12 个里砍 10 个才是需求分析真正的价值。

反向验证：**没这四步会怎样**？答案就是第 1 章，糖果充照 12 个需求全做完，10 个没人用。

**结论**：四步的本质是把"接需求"这个**被动动作**升级为"**分析决策**"这个**主动过程**。少一步都漏风。

## 3. 剥洋葱四层

### 3.1 第一层表象

用户嘴里说的第一句话，几乎永远是**表象**：

```
❌ 表象:  "我要一个 PDF 导出"
❌ 表象:  "我要一匹更快的马"
❌ 表象:  "我要一个更亮的手电筒"  
❌ 表象:  "我要一个自动化流水线"
❌ 表象:  "我要一个 AI 助手"
```

**表象的特征**：
- 是一个**具体的方案**（PDF、马、手电筒、AI）
- 用户听过、见过、类比过来的
- 通常来自**旧世界的经验**（用户想不到新方案）

**处理规则**：**记下来，但绝不当行动指南**。

### 3.2 第二层手段

追问一次，你会进入**手段层**：

```
用户: "我要一个 PDF 导出"
糖果充: "你打算用这个 PDF 干嘛?"
用户: "打印出来交给主管审阅"
```

**PDF 是手段，"给主管审阅"才是手段的目的**。到这里你会发现，如果主管的诉求是"能看到就行"，那手段可以是 PDF、可以是 Word、可以是钉钉截图、可以是直接屏幕分享。**方案空间从 1 个扩到 5 个**。

**手段层的特征**：
- 用户回答"我拿它做什么"
- 通常是**一个动作**（打印、发送、分享、备份）
- 揭示了**用户的工作流**

### 3.3 第三层目的

再追问一次，你会进入**目的层**：

```
糖果充: "为什么要给主管审阅?"
用户: "月底主管要在总监月度会上汇报, 我这份是他的原始数据"
```

**"打印给主管"是手段，"帮主管在月度会上汇报"才是目的**。这时候你会意识到：

- 主管在会上不会拿一张 A4 PDF 念
- 主管会做一个 PPT，从原始数据里挑几个亮点
- 你如果直接给他一份 **PPT 素材**（3 张关键图 + 3 句话结论），比 PDF 强 10 倍

**目的层的特征**：
- 用户回答"我为什么要做这个动作"
- 揭示了**上下游的场景**（下游是主管、总监）
- 通常隐含着**KPI 或组织目标**

### 3.4 第四层动机

再追问一次，你会进入**动机层**（最深）：

```
糖果充: "帮主管汇报, 对你来说重要在哪?"
李姐: "……主管月度会讲得好, 我这个季度的绩效才好。 
      我们财务组 5 个人, KPI 一半看主管的评价。"
```

**"帮主管汇报"是目的，"提升自己的绩效"才是动机**。到这里你会发现：

- 李姐真正的痛点不是"没 PDF"，是"我做的事情主管看不到、不重视"
- 你如果做一个 **"月度亮点自动生成"** 功能（帮李姐每月自动生成 3 条"我这个月发现了什么问题、避免了什么损失"给主管看），价值 100 倍于 PDF

**动机层的特征**：
- 用户回答"这对我意味着什么"
- 通常涉及**个人利益、职业发展、情感需求**
- 是产品**真正的价值锚点**

**四层对照总表**：

| 层 | 用户说什么 | 追问句 | 例子（李姐） |
|---|---|---|---|
| 表象 | 具体方案 | (记下) | "加个 PDF" |
| 手段 | 我拿它干嘛 | "你打算用这个 XX 做什么?" | "打印给主管" |
| 目的 | 为什么要做这个动作 | "为什么要 XX?" | "帮主管汇报" |
| 动机 | 这对你意味着什么 | "XX 对你重要在哪?" | "关系到我的绩效" |

**结论**：**追到动机层，你才真正拿到需求的钻石**。表象层交付给用户的是玻璃，动机层交付的是钻石。

## 4. 5Why 追问法

### 4.1 五层递进

丰田的 5Why 法，用在需求分析上就是**连续问 5 次"为什么"**：

```
需求原话:   "系统能不能加个 PDF 导出?"

Why 1: 你打算用 PDF 做什么?
       → "打印出来给主管"

Why 2: 为什么要打印给主管?
       → "月度会上主管要汇报"

Why 3: 为什么主管要在月度会上汇报?
       → "总监每月要看财务组的月度总结"

Why 4: 为什么这个总结对你有影响?
       → "总监说好, 我们组这个季度绩效才好"

Why 5: 为什么绩效对你这么重要?
       → "我 44 岁了, 换工作难, 这份工作要稳"
```

**5 个 Why 之后，你才看到全貌**：李姐要的不是 PDF，是"**帮主管在总监面前有排面 → 提升整个组绩效 → 稳住自己的工作**"。

**方案空间的爆炸**：

```
Why 0 层方案:  加 PDF 导出 (1 个方案)
Why 2 层方案:  PDF / Word / 邮件截图 / 钉钉发送 (4 个方案)
Why 3 层方案:  + 直接生成主管的汇报 PPT (5 个方案)  
Why 4 层方案:  + 帮主管发现"月度亮点", 让总监觉得组里有洞察 (6 个方案)
Why 5 层方案:  + 帮李姐个人建立"专业形象", 每月一份亮点报告署名给她 (7 个方案)
```

从 Why 0 到 Why 5，方案从 1 个变成 7 个。**你不追问，永远做不出最优解**。

### 4.2 六个禁忌

追问不是逼供。5Why 用不好会**把用户问烦**。六个禁忌：

| 禁忌 | 错误示例 | 修复 |
|------|---------|------|
| 咄咄逼人 | "为什么? 为什么? 到底为什么?" | 变换句式："我想理解一下…"、"能不能多讲讲…" |
| 引导性问题 | "是不是因为老板催你?" | 开放式："这背后是什么让你想到的?" |
| 过早给方案 | "我知道了, 你就是想 A 对吧" | 忍住, 继续问："除了这个还有其他考虑吗?" |
| 只问一次就走 | 问了 Why 1 就急着写代码 | 至少问到 Why 3 才有点洞察 |
| 问过头惹人烦 | 无止境地追问 | 5 次为界, 或者对方开始不耐烦立即停 |
| 忽略非语言信息 | 只听文字 | 观察对方的表情、停顿、犹豫 —— 那才是真需求 |

**追问的姿态**：**不是审讯，是好奇**。真正好的追问，用户会觉得"这个工程师是想真心帮我"。

### 4.3 PDF 需求练习

拿糖果充的真实场景练一遍，看看糖果充如果当时会追问，剧本会怎么改：

```
❌ V1 实际发生的 (0 次追问, 直接照做):

李姐:   "小杨, 你这个系统能不能加个导出 PDF 的功能?"
糖果充: "行, 简单, 我下周就加。"

结果:   两周后 PDF 上线, 三个月使用 1 次, 用户还骂"用不了"


✅ 如果糖果充追问 (5 次 Why):

李姐:   "小杨, 你这个系统能不能加个导出 PDF 的功能?"

糖果充: "行, 我可以做, 不过先问你几个问题, 免得做出来不是你要的。
        (Why 1) 你打算用这个 PDF 做什么?"
李姐:   "打印出来交给主管审阅。"

糖果充: "(Why 2) 主管一般会怎么处理这份 PDF?"
李姐:   "月底总监要开月度会, 她要把关键数据放到她的 PPT 里。"

糖果充: "(Why 3) 主管做 PPT 的时候, 打印的 PDF 好用吗?"
李姐:   "……说实话, 她还是要在 PDF 上一个一个数字抄到 PPT 里。 
        有一次抄错了一个数字, 她还骂了我一顿, 说我给她的数据不够清晰。"

糖果充: (听到关键点了) "(Why 4) 那如果我直接给你和主管一份月度关键数据摘要, 
                     可以复制粘贴到 PPT 里, 会不会更好用?"
李姐:   "那简直好死了! 主管肯定夸我。"

糖果充: "(Why 5) 主管夸你, 对你有什么好处?"
李姐:   "我们组季度绩效评价, 主管的话很关键。而且我 44 岁了, 
        这份工作我很想稳住, 主管觉得我专业, 我就安全。"

结果:   糖果充没做 PDF, 做了一个"月度数据摘要"功能, 
        自动生成 3 张关键图 + 3 句结论, 一键复制到 PPT。
        李姐月度使用 100%, 还推荐给了 3 位隔壁部门的同事。
```

**代价对比**：

```
V1 (照做):       开发 2 周 PDF, 上线后 3 个月使用 1 次, 收益 ≈ 0
如果追问 5Why:   多花 15 分钟对话, 开发 2 周摘要功能, 
                月度使用 100%, 用户主动传播, 收益 ≈ 50 倍
```

**15 分钟追问 = 50 倍产出**。这就是需求分析的杠杆率。

## 5. JTBD 框架

### 5.1 用户在雇你

哈佛商学院 Christensen 教授的 **Jobs-to-be-Done** 框架（简称 JTBD），核心洞察：

> **用户不是购买你的产品，而是"雇佣"你的产品去完成某个特定情境下的任务（Job）。**

经典案例：**麦当劳奶昔**。

麦当劳想提高奶昔销量，请咨询公司做了 6 个月用户调研，得出的方案是"加水果、加更甜、加健康"。做完销量没变。

Christensen 团队接手，只问一个问题：**"这个奶昔，你是雇它来做什么？"**

数据揭示了两个完全不同的"雇佣场景"：

```
场景 A: 早上 8 点通勤路上买奶昔的司机
  Job: 一手开车, 一手能吃, 不想开车前吃完 (通勤 40 分钟, 需要慢慢吸)
  竞品: 香蕉 (吃太快)、甜甜圈 (会掉屑)、咖啡 (不能填肚子)
  改进: 更粘稠, 让他能吸 40 分钟

场景 B: 下午 5 点带孩子回家路上, 家长顺便买给孩子哄开心
  Job: 让孩子安静 10 分钟不闹
  竞品: 玩具、糖果
  改进: 更小杯, 让孩子 10 分钟能喝完 (太粘家长嫌孩子喝不完)
```

**结论**：同一个产品（奶昔），在两个 Job 里的最优改进方向**完全相反**（一个要更粘、一个要更稀）。**不知道 Job，你不知道产品往哪改**。

### 5.2 一句话模板

JTBD 的标准表达法（黄金一句话模板）：

```
当  [情境]  时,
我想要  [动机]  ,
以便  [结果]  。
```

**拿李姐练手**：

```
❌ 传统需求描述:  "李姐要一个 PDF 导出"

✅ JTBD 描述:    当 [月底主管要在总监月度会上汇报] 时,
                我想要 [快速给主管一份能直接放进 PPT 的关键数据] ,
                以便 [主管在会上讲得好, 让总监觉得我们组专业] 。
```

**JTBD 描述的三个价值**：

```
① 情境明确:      产品什么时候被想起, 一目了然
② 动机具体:      不是"要 PDF", 而是"要能放进 PPT 的数据"
③ 结果可验收:    产品做完能不能达成"总监觉得组里专业", 可衡量
```

**结论**：**JTBD 一句话 = 让工程师、产品、设计对齐到同一个 Job 上**。

### 5.3 功能情感社交

Christensen 把 Job 分为三种：

```
┌──────────────────────────────────────────────┐
│                Job 三分类                     │
├──────────────────────────────────────────────┤
│ ① 功能 Job    要完成什么任务                   │
│               例: 快速对账、生成报表、通勤     │
│ ② 情感 Job    要感受到什么                     │
│               例: 我很专业、我很安全、我很酷   │
│ ③ 社交 Job    要在别人眼中看起来怎样            │
│               例: 主管觉得我细心、朋友觉得我有品│
└──────────────────────────────────────────────┘
```

**关键洞察**：**同一个产品往往同时承担三种 Job**，好的产品要三个都命中。

拿李姐练手：

```
功能 Job:   "帮我快速生成主管要的月度数据"
情感 Job:   "让我在月底那 2 天不慌、不出错"
社交 Job:   "让主管和总监觉得我们组专业, 让我在同事眼里有排面"
```

V1 的 PDF 导出只碰到了 "功能 Job" 的一小角（打印这个动作），完全没碰情感和社交。V2 的"月度亮点摘要"三个都碰到了——难怪李姐**主动推荐给同事**（社交 Job 被满足才会传播）。

**产品的口碑，来自社交 Job 的成功**。

## 6. 真伪反隐

### 6.1 四类定义

用户提的每个需求，做完 5Why + JTBD 之后，归入四类：

```
┌───────────────────────────────────────────────────────────┐
│                    需求四分类                               │
├───────────────────────────────────────────────────────────┤
│ ① 真需求  用户嘴上说要, 追问后确实是深层动机, 做了会用       │
│ ② 伪需求  用户嘴上说要, 追问后动机站不住, 做了不会用         │
│ ③ 反需求  用户嘴上说要, 做了反而害了用户 (副作用大于收益)    │
│ ④ 隐需求  用户没说, 但追问出来才是真正的痛点                 │
└───────────────────────────────────────────────────────────┘
```

**四类举例**（拿李姐的 12 个需求练手）：

| 需求 | 追问结果 | 类型 |
|------|---------|------|
| 加 PDF 导出 | 真正要的是"给主管 PPT 素材" | **伪** → 转化为"月度摘要" |
| 加批量操作 | 从没用过, 只是"看别的系统有" | **伪** |
| 加搜索框 | 每月找历史账目要翻半天 | **真** |
| 加夜间模式 | 只是听说别人都有 | **伪** |
| 加数据备份 | 怕数据丢, 怕背锅 | **真** |
| 加自动定时提醒 | 她自己有手机日历 | **伪** |
| 加多语言支持 | 她们公司没外国人 | **伪** |
| 加操作日志 | 追责用, 但可能反被追责 | **反** |
| 加用户权限 | 财务组就 3 个人 | **伪** |
| 加自定义模板 | 她其实只用一个模板 | **伪** |
| 加数据校验规则 | 想拦下明显错误 | **真** |
| 加 API 对接 | 只是听 IT 说过 API | **伪** |
| （追问出）月度亮点摘要 | 帮主管在月度会上加分 | **隐** ✨ |
| （追问出）供应商晚到发票补录 | 27 号最痛的场景 | **隐** ✨ |

**结果**：12 个显性需求里，只有 3 个真需求（搜索、备份、校验），2 个隐需求需要主动挖掘（月度摘要、发票补录）。**真正该做的是 5 个，不是 12 个**。

### 6.2 识别方法

四类怎么识别？用**追问后回答的稳定性**来判断：

```
真需求识别:
  Why 1-5 层层递进, 深层动机清晰, 用户举出真实场景至少 2 次
  → 例: "加搜索" → 她能立刻说"上周我找 3 月的账翻了半小时"

伪需求识别:
  Why 1 就答不上来, 或者答"别的系统都有"
  → 例: "加夜间模式" → "为什么要这个?" → "……听说都有嘛"

反需求识别:
  做了之后有明显副作用 (法律、责任、心理)
  → 例: "加操作日志" → 追问发现李姐怕日志反被审计, 
        做了她反而不敢用系统了

隐需求识别:
  用户没主动说, 但 Why 3-5 层浮现出来的深层痛点
  → 例: 5Why 追到"主管做 PPT 要抄数字" → 隐需求"月度摘要"
```

**技巧**：**用户越会举具体例子的需求，越可能是真需求**。用户举不出例子、只能说"感觉""大家都""据说"的，几乎都是伪需求。

### 6.3 处理策略

四类需求的处理策略：

```
┌────────────────────────────────────────────────────────────┐
│                    四类处理策略                              │
├────────────────────────────────────────────────────────────┤
│ 真需求  →  做, 排优先级 (进第 3 篇《优先级排序》流程)         │
│ 伪需求  →  不做, 但给用户一个"体面的答复" (见下)              │
│ 反需求  →  不做, 主动跟用户沟通副作用, 引导到真需求           │
│ 隐需求  →  做 (优先级往往最高), 主动向用户展示"我猜你要的"    │
└────────────────────────────────────────────────────────────┘
```

**"体面拒绝"的三段话术**（用于伪需求）：

```
段 1 - 承认价值:   "你说的 XX 我理解, 确实有很多系统在做"
段 2 - 摆出数据:   "我调研了一下, 我们组用这个功能大概是 3 个月 0 次, 
                    数据不太支持做"  
段 3 - 引到真需求: "但我发现你真正想要的是 YY, 这个我可以做, 你觉得?"

示例:
"李姐, 加夜间模式我理解 (段 1), 但我看后台数据,
 我们所有用户都是白天 9-18 点在用, 夜间几乎无访问 (段 2)。
 不过你上次说过对账时眼睛累, 我可以做一个'当前行高亮'功能,
 帮你聚焦当前操作行, 你觉得呢? (段 3)"
```

**关键**：**拒绝需求 ≠ 拒绝用户**。段 3 一定要有，把用户从伪需求带到真需求上。

## 7. 反模式清单

工程师做需求分析最容易犯的 8 个反模式：

| 反模式 | 症状 | 危害 | 修复 |
|--------|------|------|------|
| 需求翻译机 | 用户说 A 就做 A | 90% 时间做无用功 | 至少追问到 Why 3 |
| 会议纪要式记录 | 只记结论不记原话 | 三个月后没法复盘 | 记原话 + 场景 + 用户情绪 |
| 只问一次 Why | 问了一次就急着写代码 | 停在手段层, 达不到目的 | 至少 3 次, 最好 5 次 |
| 用引导性问题 | "你是不是想要 A 对吧?" | 用户附和你, 拿到假答案 | 开放式提问 |
| 不看用户表情 | 只记文字答案 | 忽略犹豫/回避的真信号 | 观察 + 追问犹豫点 |
| 需求同等对待 | 12 个需求同排优先级 | 真金和沙子一起做 | 先四分类, 再排优先级 |
| 从不敢拒绝 | 全接单, 做不完就加班 | 团队被稀释, 真需求做不完 | 学"体面拒绝"三段话术 |
| 忽略隐需求 | 只处理用户说出来的 | 错失最有价值的需求 | 5Why 到动机层, 主动挖掘 |

**结论**：这 8 条反模式覆盖了工程师做需求分析 95% 的翻车场景。做完需求分析后自检一遍，能砍掉大部分坑。

## 8. 给不同岗位的话

**如果你是做硬件的**：硬件的需求分析比软件难 10 倍——**硬件一旦造出来改不了**。5Why 一定要问到位，尤其是 **"你在什么场景下会用到这个硬件?"** 硬件的隐需求经常在**用户的其他工具上下文**里（比如你做一个智能音箱，用户真正的隐需求可能是"我做家务时手上湿的没法碰手机"）。硬件的 JTBD 情境描述要**精确到分钟粒度**——早上 7:30 起床、洗漱、吃早餐这三个动作里，每个动作 30 秒就换场景。

**如果你是做算法的**：算法工程师最容易掉进"精度需求陷阱"——业务方说"精度要 95%"，你以为这是真需求，其实是伪需求。5Why 追下去，通常真需求是"**错了之后人工兜底要多久**"或"**错了谁负责**"。**算法的隐需求几乎永远是"可解释性"**——不是精度不够，是**用户不敢信精度**。JTBD 描述要重点写"错误发生时用户要做什么"，这比"正常时怎么用"重要 10 倍。

**如果你是做运维 / SRE 的**：运维平台的用户是研发同事，他们的需求嘴上说的和真要的差距最大。研发说"我要一个更快的 CI"，5Why 追下去往往是"**上线出错我不想担责**"。你做的 CI 再快，如果不能帮他们规避责任，他们不会真用。**隐需求**：一键回滚、一键预演、一键"这次上线会影响什么"。运维产品的核心 JTBD 是"**帮研发在半夜三点不用被叫起来**"。

**如果你在传统行业（银行、制造、政企、医疗）**：传统行业需求分析最大的陷阱是"**合规需求 = 真需求？**" 不一定。有些"合规要求"是**过度解读**，有些是**过时政策**。5Why 追下去经常发现"**监管其实没要求这个，是我们内部风控部门保险起见加的**"。区分真合规和伪合规，能砍掉 30% 的需求。**隐需求**：**责任归属清晰**。传统行业里"谁的锅"比"效率提升"重要 10 倍——一个能让员工"确认过、盖过章、免责"的功能，比任何酷炫的功能都受欢迎。

## 9. 综合案例

### 9.1 重做 PDF 需求

回到糖果充。他从系统数据里翻出 12 个 0-1 次使用的功能，决定重来一次。这次他做了三件事：

**第一件事：翻旧账 + 补追问**

他把 12 个需求逐个找李姐重新聊，每个至少问到 Why 3。原本 2 周不到就做完的"需求收集"，这次花了 3 天。

**第二件事：JTBD 重写每一个需求**

按 "当 [情境] 时，我想要 [动机]，以便 [结果]" 重写：

```
需求 1 (原): "加 PDF 导出"
JTBD 重写: 当 [月底主管做月度总结 PPT] 时,
          我想要 [3 分钟拿到 3 张关键图 + 3 句结论] ,
          以便 [主管讲得好, 让总监觉得我们组专业] 。

需求 3 (原): "加搜索框"
JTBD 重写: 当 [每月被主管问'去年 3 月的 XX 供应商付款是多少'] 时,
          我想要 [10 秒内找到] ,
          以便 [不让主管等我翻半小时] 。

需求 8 (原): "加操作日志"
JTBD 重写: 当 [账目出错被审计] 时,
          我想要 [证明是别人误操作, 不是我的责任] ,
          以便 [不背锅] 。
          → 但追问发现: 日志反而可能证明是李姐操作错误
          → 归为反需求, 不做
```

**第三件事：四分类 + 决策**

12 个需求 + 追问挖出的 2 个隐需求，做四分类：

```
真需求 (做):        搜索、数据备份、数据校验规则、月度摘要 (隐)、发票补录 (隐) = 5 个
伪需求 (拒):        PDF、批量操作、夜间模式、自动提醒、多语言、用户权限、自定义模板、API = 8 个
反需求 (拒 + 沟通): 操作日志 = 1 个

原本计划: 做 12 个 (0 隐需求)  
新计划:  做 5 个 (含 2 个隐需求, 8 个伪需求拒掉, 1 个反需求沟通)
```

**这次糖果充连着做了 4 件事**：
1. 5 个真需求逐个 JTBD 描述
2. 8 个伪需求按"体面拒绝三段话术"沟通
3. 1 个反需求主动跟李姐说明副作用，李姐一听就懂了，说"那真的不做"
4. 2 个隐需求做完后主动跟李姐说："我猜你其实想要 XX，这是我做的初版你看看"

### 9.2 分析回望

三个月后再看数据：

```
V1 (照做 12 个): 
  开发人月:  6 人月
  使用率:   平均 10%  
  用户满意度: "还行, 有几个用不了"

V2 (追问后做 5 个):
  开发人月:  4 人月  (省了 2 人月)
  使用率:   平均 85%
  用户满意度: "简直是我的救星, 已经推荐给 5 个人"
```

**"少做 60% 的功能，用户满意度反而翻倍"**——这就是需求分析的杠杆。

**需求分析能力的五级**：

```
初级:  用户说 A → 做 A                        (需求翻译机)
中级:  用户说 A → 追问 1 次 → 做 A'           (半个侦探)
高级:  用户说 A → 5Why 追到动机 → 做 B         (完整侦探)
资深:  用户说 A → JTBD 描述 → 挖出隐需求 C → 做 C  (需求猎人)
大师:  用户还没说, 你就能预判他即将说什么      (业务直觉)
```

**需求分析的四个心法**：

```
① 用户嘴里的话是谜面, 不是答案
② 手段和目的隔着 3 层洋葱, 不追问永远看不到
③ 12 个需求里, 值得做的通常只有 3-5 个
④ 最有价值的需求, 是用户没说出来的
```

### 9.3 速查与练习

**需求分析自检卡**（听完每个需求后逐条问自己）：

```
□ 1. 我记下的是原话 + 场景, 还是只有一句话摘要?
□ 2. 我至少追问了 3 次 Why 吗?
□ 3. 我能用 JTBD 一句话写出 "当____, 我想要____, 以便____" 吗?
□ 4. 我识别出了功能 Job / 情感 Job / 社交 Job 各是什么吗?
□ 5. 我把这个需求归入了真/伪/反/隐 四类吗?
□ 6. 如果是伪需求, 我准备好三段话术拒绝了吗?
□ 7. 如果是反需求, 我跟用户沟通过副作用了吗?
□ 8. 我在追问过程中, 有没有挖出至少 1 个用户没主动说的隐需求?
```

**需求分析速查表**：

| 场景 | 动作 |
|---|---|
| 用户提了个具体功能 | 记原话 + 追问"你打算用它做什么" |
| 用户说"别人都有" | 大概率是伪需求, 追问真实场景 |
| 用户说不出具体例子 | 大概率是伪需求 |
| 用户举出 2 次以上真实场景 | 大概率是真需求 |
| 追问时用户开始犹豫 | 那就是关键点, 继续追 |
| 追问到用户情绪激动 | 触到动机层了, 记下来 |
| 想拒绝一个需求 | 三段话术: 承认 + 数据 + 引到真需求 |
| 感觉有隐需求 | 用 "我猜你其实想 XX" 试探 |

**JTBD 一句话模板**（贴工位）：

```
当 [_______________________] 时,
我想要 [_____________________] ,
以便 [_______________________] 。
```

**30 天需求分析练习**：

```
Week 1 (记录 + 追问):
  找到 5 个真实用户 (同事、家人、客户), 
  每人聊一次他们对某产品的抱怨, 至少追问 3 次 Why
  写下: 原话 → Why1 → Why2 → Why3 → 真正动机

Week 2 (JTBD 描述):
  拿你负责的产品的 5 个现有功能, 逐个反推 JTBD:
  当 [_____] 时, 我想要 [_____] , 以便 [_____] 。
  如果有 1 个写不出来, 说明这个功能可能是伪需求

Week 3 (四分类):
  拿你手上正在处理的需求池 (至少 10 个需求),
  逐个归入真/伪/反/隐 四类
  你会发现真需求可能只有 30%

Week 4 (体面拒绝):
  找出你归为"伪需求"的 3 个,
  用三段话术写出拒绝话术, 实际发给需求方
  记录: 对方接受率 (目标 > 70%)
```
