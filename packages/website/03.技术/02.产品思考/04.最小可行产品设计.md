## 1. 案例引入

### 1.1 六件套只用一件

上一篇糖果充搞定了优先级三方评审会，Q3 排期锁定。团队开始做 RICE 分数最高的 **"发票批量识别"**。糖果充信心满满，脑子里的规划是：

> "既然做，就做完整。业内标杆都是六件套。"

**发票识别六件套**（糖果充的初版规划）：

```
① 标准 A4 增值税发票识别      (核心)
② 异形票据识别 (小票/收据)     (增强)
③ 多币种支持 (美元/欧元/港币)  (增强)
④ AI 智能字段提取             (亮点)
⑤ 自动分类归档                (亮点)
⑥ 批量校验规则引擎             (亮点)
```

**开发投入**：3 人 × 2 个月 = 6 人月。上线当天糖果充在小群里发了截图："**发票六件套上线！**"

**两周后统计使用情况**：

```
① 标准 A4 增值税发票识别    月度识别 4200 次     ← 99% 使用集中在这
② 异形票据识别            月度识别 12 次       (0.3%)
③ 多币种支持              月度使用 0 次        (0%)
④ AI 智能字段提取         月度触发 89 次       (2%, 且 60% 结果被人工改)
⑤ 自动分类归档            月度使用 24 次       (0.6%)
⑥ 批量校验规则引擎         月度使用 7 次        (0.2%)

合计: 
  用户实际使用集中在 ① (标准 A4)
  ②③④⑤⑥ 合计使用占比 3%
  但开发投入占了 60% (3.6 人月)
```

**糖果充算了一下**：**60% 的开发投入换来 3% 的使用**。

去问李姐使用体验：

```
糖果充: "李姐, 发票识别用得怎么样?"
李姐:   "第一个 (A4 识别) 特别好, 简直救命。"
糖果充: "其他五个呢? 异形、多币种、AI 提取、自动归档、批量校验?"
李姐:   "……啊, 有这些功能吗? 我没注意。"
糖果充: (痛苦)
```

**更痛苦的是**：因为要做完六件套，功能上线晚了整整 5 周。李姐这 5 周多加了 20 小时班。

```
如果早 5 周只上 ① (A4 识别):
  李姐可以省 20 小时加班
  用户获得价值早 5 周
  团队多出 3.6 人月做其他需求

现实版:
  李姐加班了 20 小时
  用户价值晚 5 周到达
  3.6 人月投在了没人用的功能上
```

糖果充把这个数据摊给带过他的产品前辈老周看。老周只问了一句：

```
老周: "你上线前, 用什么方式验证过这六件套的必要性?"
糖果充: (愣) "……业内标杆都有, 我看了三个竞品都有。"
老周: "所以你验证的是'竞品有', 不是'用户要'。这是两件事。"
```

### 1.2 顺藤摸根因

带着这条线往下挖：

- **假设 1**：糖果充做的六件套不好用？——不是，六件套技术上都实现得挺好
- **假设 2**：用户不知道有这些功能？——部分是，但即使知道也不用（因为没场景）
- **假设 3**：糖果充需求分析没做到位？——不是，前面 5Why 挖到李姐月底加班的痛点了
- **假设 4**：糖果充优先级排错了？——**部分是**，"发票识别"整体排 RICE 960 没错，**但"发票识别里面的子功能"没有再排一次优先级**
- **假设 5**：这属于什么问题？——**MVP 认知缺失**。糖果充把"发票识别"当成一个不可分的整体，没有意识到里面还能再拆
- **假设 6**：什么是真正的 MVP？——**"能让用户真正用起来的最小完整闭环"**，不是"缩水版完整产品"
- **假设 7**：怎么砍功能才不砍错？——四刀法：按时间/角色/场景/权限砍
- **假设 8**：上线之后怎么持续迭代？——Build-Measure-Learn 循环

仔细分析这次翻车的根因：

```
表象                                真实问题
────────────────────────────────────────────────
"业内标杆都有六件套"              → 参照竞品做规划, 不是参照用户做规划
"既然做就做完整"                   → 工程师完美主义, 把 MVP 当成 "1.0 完整版"
"多做几个也不费事"                 → 忽略了机会成本 (那 3.6 人月本可以做别的)
"上线晚 5 周问题不大"              → 忽略了用户等待成本 (李姐 20 小时加班)
"上线后再看数据"                   → 没有 Build-Measure-Learn 意识, 
                                    验证太晚, 沉没成本已锁死
```

**根因**：糖果充**只会造完整产品, 不会造 MVP**。他脑子里的产品长什么样是**"六件套齐全那种"**，不是**"能验证核心假设的最小版本"**。工程师本能是"造成品"，但产品的本能应该是"**造实验**"。

这一段里至少藏着 8 个原理点：

```
① MVP 到底是什么? 常见的三种误解?                    → 第 2 章
② MVP 有几种形态? 什么时候用哪种?                    → 第 3 章
③ 怎么把大功能砍成 MVP? 有什么系统方法?              → 第 5 章
④ Build-Measure-Learn 循环怎么落地?                → 第 4 章
⑤ 上线后什么时候该迭代什么时候该重做?                → 第 6 章
⑥ MVP 常见反模式?                                    → 第 7 章
⑦ 不同岗位 MVP 变形?                                → 第 8 章
⑧ 糖果充要重做, 从哪一刀砍?                          → 第 9 章
```

### 1.3 要回答什么

这个事故就是本篇的**主线案例**。带着上面 8 个问号往下走。本篇路线：

```
MVP 全景 + 三个错觉 (第 2 章)
   ↓
MVP 三种形态 (第 3 章) ─→ 解开"MVP 长什么样"
   ↓
Build-Measure-Learn (第 4 章) ─→ 解开"MVP 之后怎么办"
   ↓
砍功能四刀法 (第 5 章) ─→ 解开"具体怎么砍"
   ↓
重做 vs 迭代 (第 6 章) ─→ 解开"沉没成本怎么处理"
   ↓
反模式 (第 7 章) + 跨岗位 (第 8 章)
   ↓
综合案例 (第 9 章) ─→ 糖果充重做发票识别 MVP
```

📌 **本篇定位**：这是"产品思考"系列的**执行力升级**。前三篇讲"看到用户、挖到真需求、排好优先级"，本篇讲"**决定做了之后，做多大才算对**"。MVP 认知是工程师转产品最难的一关——**违背工程师"造完整"的本能**。读完这篇你会明白：**先活下来才能长大，一开始就想造完美的产品往往什么都活不下来**。

## 2. MVP 全景图

### 2.1 MVP 三个错觉

MVP（Minimum Viable Product，最小可行产品）这个词被讲滥了，大多数工程师**理解是错的**。三个最常见的错觉：

**错觉一：MVP = 完整版的缩水**

```
❌ 错误理解: 
   完整版有 100 个功能, 缩水到 20 个就是 MVP
   
问题: 
   20 个里可能一个用户核心闭环都没走通, 用户根本用不起来
   典型症状: "登录都有了, 但用户登录后没功能可用"
```

**错觉二：MVP = 粗糙的原型**

```
❌ 错误理解:
   UI 丑一点、性能差一点、bug 多一点, 反正是 MVP
   
问题:
   MVP 不是"质量差", 是"范围小"
   范围小的部分, 质量应该反而更高 (因为你只做这么点东西)
   典型症状: "第一版做得像 demo, 用户一用就走了"
```

**错觉三：MVP = 内部版本**

```
❌ 错误理解:
   MVP 是给内部测试的, 用户版应该做完整
   
问题:
   MVP 就是给真实用户用的, 内部测试不叫 MVP 叫"内测"
   MVP 的价值在于"用真实用户来验证假设"
   典型症状: "MVP 只发给公司同事看, 得到的反馈全是假的"
```

糖果充的"六件套发票识别"同时踩了三个错觉——**他做的不是 MVP，是一个完整产品**。

### 2.2 MVP 真定义

MVP 之父 Eric Ries 在《精益创业》里给的定义：

> **MVP = 能让你以最小代价，用真实用户验证核心假设的最小完整闭环。**

拆解四个关键词：

```
① 最小代价:      不是"缩水"是"聚焦", 尽可能少的开发投入
② 真实用户:      不是内部测试, 是付费/日活的目标用户
③ 核心假设:      每个 MVP 只验证 1 个假设 (最多不超过 3 个)
④ 完整闭环:      用户能从"想用"到"用完得到结果"的全程走通
```

**四个关键词映射到糖果充的例子**：

```
糖果充造六件套 vs 真正的 MVP:

维度         糖果充做法          真正 MVP 做法
────────────────────────────────────────────────
最小代价    3 人 × 2 月 = 6 人月  1 人 × 3 周 = 0.75 人月
真实用户    李姐等 5 位财务       同样 5 位 (但只上一个功能)
核心假设    ??? (没有明确假设)     "AI 识别 A4 发票能否让李姐月底
                                    加班从 20 小时降到 <5 小时"
完整闭环    六件套齐全 (才叫完整)  上传 A4 图片 → 识别文字 → 
                                   李姐确认 → 一键填入 Excel
                                   (闭环走通, 就叫完整)
```

**关键洞察**：**MVP 的"完整"是"闭环完整", 不是"功能完整"**。上传能上传但识别不了，那不叫 MVP；识别能识别但填不回 Excel，那也不叫 MVP。**闭环走不通 = 不是 MVP**。

**六件套的问题**：闭环 ①（A4 识别）走通了，但 ②③④⑤⑥ 是**额外的独立闭环**，不是"完整"的一部分。糖果充把"锦上添花的独立闭环"当成"必须有的完整闭环"，导致投入爆炸、上线延迟。

## 3. MVP 三种形态

MVP 不一定是软件产品。经典的 **三种形态**，按投入从低到高：

### 3.1 人肉服务型

**定义**：用人工代替产品，一对一给用户提供服务。**没有代码、没有产品，先用人跑业务**。

**经典案例**：Airbnb 早期。创始人在自家客厅拍照片、手工放上简易网站、亲自接待每个客人。三个月人肉服务，才写了正式的产品代码。

**拿糖果充的案例练手**：

```
糖果充 MVP 版本 - Concierge:

流程:
① 李姐月底把一叠发票拍照发微信给糖果充
② 糖果充打开某在线 OCR (免费的百度/腾讯 API) 
③ 手动跑一遍 OCR
④ 复制结果, 手动整理成 Excel 发回李姐

投入:
- 开发工作: 0
- 糖果充每月投入: 4 小时
- 时间到位: 立刻

验证:
- 假设: "AI 识别 A4 发票能救李姐"
- 结果: 4 小时后李姐反馈"这个太救命了, 你能不能自动化?"
- 数据: 一次验证胜过 100 页 PRD
```

**Concierge 的适用场景**：
- 目标用户 ≤ 10 个
- 单次服务成本可控（糖果充每月 4 小时可以接受）
- 想验证"用户是否真的需要这个功能"（0 代码就能验证）

**Concierge 的价值**：**用人力换代码**——你不知道该做什么之前，不写代码。

### 3.2 奥兹魔法师

**定义**：**用户看到的是自动化产品，实际背后是人工在跑**。前端是产品，后端是人肉。

**经典案例**：Zappos 早期卖鞋。创始人建了一个电商网站，用户下单后他跑到街边鞋店买鞋再寄给用户。没有库存、没有物流、没有 ERP，先验证"人们会在网上买鞋吗"。

**拿糖果充的案例练手**：

```
糖果充 MVP 版本 - Wizard-of-Oz:

用户看到:
- 一个漂亮的上传界面, "拖入发票, 30 秒自动识别"

实际后台:
- 上传后进入队列
- 糖果充在办公室后台看到新任务, 手动跑 OCR + 校验
- 30 秒后系统"自动"返回结果给用户

投入:
- 前端页面: 1 周
- 后台 API: 1 周 (只有上传/回传, 没有真正的识别引擎)
- 糖果充每月人肉: 4 小时
- 时间到位: 2 周

验证:
- 假设 1: "李姐愿意上传发票到系统" (前端体验)
- 假设 2: "30 秒返回的识别结果她会信任" (交互心理)
- 假设 3: "识别错误率 < 5% 时她愿意继续用" (质量阈值)
- 结果: 三个假设都得到验证, 
        再决定投资 1 人月做真正的自动 OCR
```

**Wizard-of-Oz 的适用场景**：
- 目标用户 10-100 个（人肉还能跑得动）
- 想验证"用户交互体验"（比如"李姐愿不愿意上传"）
- 后端技术复杂/成本高（先用人肉延后技术投入）

**Wizard-of-Oz 的价值**：**用用户体验的真实性换后端的真实性**——用户不知道背后是人，但反馈是真的。

### 3.3 落地页型

**定义**：**做一个宣传页，还没造产品就先测市场需求**。

**经典案例**：Buffer（社交媒体调度工具）。创始人第一版只做了一个宣传页，写着"我们要做一个社交媒体调度工具"，页面上有个"感兴趣就留邮箱"按钮。**先看有没有人留邮箱，再决定做不做产品**。

**拿糖果充的案例练手**：

```
糖果充 MVP 版本 - Landing Page:

产物:
- 一个内部宣传页 (钉钉/飞书页面即可)
- 标题: "发票识别功能即将上线, 帮你月底不加班"
- 内容: 一段 30 秒视频演示 + 一个"报名试用"按钮

投入:
- 视频拍摄: 半天
- 页面制作: 半天
- 总计: 1 人天

验证:
- 假设: "财务部/其他部门里有多少人对这个功能感兴趣"
- 数据: 页面 PV 200, 报名 43 人
- 结论: 潜在用户超过预期, 从"只做财务"扩展到"财务+采购+行政"
         或者相反: 报名 3 人, 说明这个功能不值得投入 6 人月
```

**Landing Page 的适用场景**：
- 完全新方向，不确定市场需求
- 想估算真实用户规模（辅助 RICE 打分的 Reach）
- 投入极低（1 人天）就能得到用户意愿数据

**Landing Page 的价值**：**用一个页面换需求验证**——花 1 天知道该不该投 6 人月。

**三种形态对照表**：

| 形态 | 投入 | 验证的假设 | 用户规模 | 适用阶段 |
|------|------|-----------|---------|---------|
| Concierge | 极低 (0 代码) | "用户是否需要" | ≤ 10 | 探索早期 |
| Wizard-of-Oz | 中 (前端为主) | "用户体验能否成立" | 10-100 | 验证中期 |
| Landing Page | 极低 (1 人天) | "有多少人感兴趣" | 无限 | 需求预估 |

**结论**：**MVP 不一定要写全套代码**。三种形态里选最匹配你要验证的假设的那种。糖果充做发票识别，最合适的其实是 **Wizard-of-Oz**——2 周做前端 + 人肉 OCR 跑 1 个月，就能验证六件套哪几件真的有人用。

## 4. BML 循环

### 4.1 三步循环

MVP 不是"上线就完了"，是**一个持续学习的循环**。Eric Ries 的核心方法：

```
     Ideas (假设)
       │
       ▼
    ┌──────┐
    │ Build│    ← 造最小 MVP 验证假设
    └──┬───┘
       │
       ▼
    Product (产品)
       │
       ▼
    ┌──────┐
    │Measure│   ← 用数据测量用户行为
    └──┬───┘
       │
       ▼
     Data (数据)
       │
       ▼
    ┌──────┐
    │ Learn│    ← 从数据学到什么, 修正下一个假设
    └──┬───┘
       │
       └─────────→ 回到 Ideas
```

**三步节奏**：

```
Build  阶段: 把假设变成能验证的产品 (最小)
Measure 阶段: 用数据 (不是感觉) 测量结果
Learn  阶段: 从数据里得到"下一个假设"
```

**关键**：**循环的速度就是学习的速度**。每次循环 1 周 vs 每次循环 6 个月，学习速度差 25 倍。

### 4.2 假设卡模板

每次 Build 之前，先填一张**假设卡**：

```
┌─────────────────────────────────────────────────┐
│              MVP 假设卡                          │
├─────────────────────────────────────────────────┤
│ 核心假设:                                        │
│   我们相信 [用户] 会 [做什么行为],                │
│   因为 [什么理由]。                              │
│                                                  │
│ 验证方式:                                        │
│   我们做 [什么 MVP], 让 [多少用户] 用 [多长时间]. │
│                                                  │
│ 成功指标:                                        │
│   如果看到 [什么数据], 假设成立。                 │
│                                                  │
│ 止损线:                                          │
│   如果 [什么情况], 假设失败, 立即停手/转向。       │
│                                                  │
│ 学习问题:                                        │
│   无论成败, 我们都想学到 [什么]。                  │
└─────────────────────────────────────────────────┘
```

**拿糖果充的发票识别练手**：

```
核心假设:
  我们相信 [李姐等 5 位财务] 会 [每月上传发票并使用识别结果],
  因为 [她们月底加班 20 小时, 手动录发票是主要耗时]。

验证方式:
  我们做 [A4 识别 MVP], 让 [5 位财务] 用 [1 个月].

成功指标:
  如果看到 [月度识别 > 500 次 且 李姐加班从 20 小时降到 <10 小时], 
  假设成立。

止损线:
  如果 [月度识别 < 100 次 或 李姐加班时间不变], 
  假设失败, 说明手动录不是她的核心痛点, 或者用户不信任 AI 识别。
  立即停手, 重新访谈找真痛点。

学习问题:
  无论成败, 我们都想学到:
  ① 用户对识别错误的容忍度是多少?
  ② 用户会不会自动传播给同事? (社交 Job)
  ③ 除了 A4, 用户还有哪些"没提但会用"的隐性场景?
```

**关键**：**止损线必须写**。写止损线的价值不是"允许失败"，是**"事先约定失败标准"**——避免上线后"数据不好但舍不得砍"的沉没成本陷阱。

### 4.3 速度即学习

**循环速度对比**：

```
慢循环 (糖果充 V1):
  Build:   6 人月造六件套
  Measure: 上线 2 周才有第一批数据
  Learn:   3 个月后才看到"5 件套没人用"
  总: 一次循环 ~ 8 个月

快循环 (MVP 方式):
  Build:   2 周做 Wizard-of-Oz 版 A4 识别
  Measure: 上线后每周一份数据报告
  Learn:   1 个月后就能决定"要不要投入做异形/AI/自动归档"
  总: 一次循环 ~ 5 周

差距: 6 倍学习速度
```

**这就是 MVP 的核心价值——不是"少做功能"，是"快速迭代"**。

**迭代节奏推荐**：

```
探索期 (前 1-3 个月):    每 2 周一次循环
成长期 (3-12 个月):      每 1 个月一次循环
成熟期 (12 个月+):      每季度一次循环
```

## 5. 砍功能四刀法

Build 阶段最难的是**"砍"**。工程师本能是"多做点，多留几个功能"，产品本能应该是"再砍一刀"。四刀法帮你系统性地砍：

### 5.1 按时间砍

**问题**：这个功能是**上线第一天就用**，还是**上线一个月后才用**？

**拿六件套练手**：

| 功能 | 上线第一天用吗？ | 判决 |
|------|:---:|:---:|
| ① A4 识别 | ✓ | V1 |
| ② 异形票据 | 一月后碰到 | V2 |
| ③ 多币种 | 半年后可能碰到 | V2+ |
| ④ AI 智能提取 | 一月后碰到 | V2 |
| ⑤ 自动分类 | 用满 3 个月后才有归档需求 | V3 |
| ⑥ 批量校验 | 用满 3 个月且数据量大才有 | V3 |

**结论**：**只有 ① 是 V1 必须的**。②–⑥ 全部砍到后续版本。

### 5.2 按角色砍

**问题**：这个功能是**80% 用户都用**，还是**20% 用户才用**？

**拿六件套练手**：

| 功能 | 80% 用户会用吗？ | 判决 |
|------|:---:|:---:|
| ① A4 识别 | 财务/采购/行政都会用 | V1 |
| ② 异形票据 | 只有采购报销偶尔碰 | V2 |
| ③ 多币种 | 只有外贸财务 | V2+ |
| ④ AI 智能提取 | 只有大量数据的高级用户 | V2 |
| ⑤ 自动分类 | 只有会计岗位有归档需求 | V3 |
| ⑥ 批量校验 | 只有审计岗位 | V3 |

**结论**：**只有 ① 覆盖 80% 用户**。其他都是长尾。

### 5.3 按场景砍

**问题**：这个功能是**核心场景必须**，还是**边缘场景锦上添花**？

**拿六件套练手**：

| 功能 | 核心场景（月底对账）必须？ | 判决 |
|------|:---:|:---:|
| ① A4 识别 | ✓ (每月 4000+ 张 A4 发票要录) | V1 |
| ② 异形票据 | 月底 12 张小票, 手动录也 5 分钟 | V2 |
| ③ 多币种 | 公司无外币业务 | 砍 |
| ④ AI 智能提取 | A4 识别已能提取字段, 是 ① 的锦上添花 | 砍 |
| ⑤ 自动分类 | 归档是月末动作, 手动分类只需 10 分钟 | V3 |
| ⑥ 批量校验 | 现有校验规则手写 5 条就够 | V3 |

**结论**：**只有 ① 是核心场景不可或缺**。③ 甚至可以直接砍。

### 5.4 按权限砍

**问题**：这个功能是**普通用户能用**，还是**需要特殊权限（管理员/合规审计）才能用**？

**拿六件套练手**：

| 功能 | 权限层级 | 判决 |
|------|:---:|:---:|
| ① A4 识别 | 所有人 | V1 |
| ② 异形票据 | 所有人 | V2 |
| ③ 多币种 | 所有人 | V2+ |
| ④ AI 智能提取 | 所有人 | V2 |
| ⑤ 自动分类 | 会计权限 | V3 |
| ⑥ 批量校验 | 审计权限 | V3 |

**结论**：**权限越少的功能, V1 越应该覆盖**。权限复杂的功能天然是后置的。

**四刀合击**：

```
四刀合击表:

功能    时间   角色   场景   权限   总分   判决
──────────────────────────────────────────────
① A4 识别  V1    V1    V1    V1    4/4    ★ V1 必做
② 异形     V2    V2    V2    V1    1/4    V2
③ 多币种   V2+   V2+   砍   V1    0/4    砍
④ AI 提取  V2    V2    砍   V1    0/4    砍/合并到①
⑤ 自动分类 V3    V3    V3    V3    0/4    V3
⑥ 批量校验 V3    V3    V3    V3    0/4    V3
```

**结论**：**只有 ① 通过四刀合击的 4/4**——**这就是真正的 MVP**。其他五件全部砍到 V2/V3 甚至完全砍掉。

**开发工作量**：

```
糖果充 V1 (六件套):  6 人月
真 MVP (只做 ①):    1.5 人月

节省:  4.5 人月, 相当于团队 3 人多出 1.5 个月做其他 3 个 Must Have
上线时间:  从 8 周缩短到 3 周, 李姐早 5 周解脱
```

## 6. 重做还是迭代

MVP 上线后拿到数据，两条路：**继续迭代**（在现有 MVP 上加功能）还是**推倒重做**（承认方向错了从头来）。

### 6.1 沉没成本识别

工程师最难克服的心理障碍是**沉没成本**——"我已经做了 6 人月了，怎么能砍掉？"

**沉没成本陷阱识别**：

```
症状 1: "都做这么多了砍了太可惜" 
       → 这就是沉没成本 sunk cost 的心理话术
       
症状 2: "再优化一下就好了" 
       → 已经优化过 3 次以上还没起色, 大概率是方向错了
       
症状 3: "用户没反馈说不好用" 
       → 沉默用户 ≠ 满意用户, 看数据不看嘴
       
症状 4: "老板一定不同意重做" 
       → 你没有把数据和成本讲清楚, 老板不是不同意重做, 
         是没看到重做的必要性
```

**沉没成本决策原则**：

> **过去投入的所有成本，都与今天的决策无关。今天的决策只看：从此刻开始的投入 vs 从此刻开始的收益。**

**拿糖果充的六件套练手**：

```
已投入: 6 人月 (沉没, 不再纳入决策)

选项 A - 继续在六件套上优化:
  预计再投入 2 人月修复用户反馈
  预期收益: 使用率从 3% 提升到 5% (还是没人用)
  
选项 B - 保留 ① (A4 识别), 砍掉 ②③④⑤⑥, 集中做别的 Must Have:
  投入 0 (①已在跑)
  释放 3.6 人月, 可以做客户对账门户
  
选项 C - 彻底重做整个方向:
  投入 4 人月 (从头做一个不同思路的方案)
  预期收益: 未知
  
决策: 选 B, 因为 ROI 最高, 且 ① 已经证明价值
```

**沉没成本被 6 人月绑架的人**：会选 A，把已经错的方向再错下去
**跳出沉没成本的人**：直接选 B，砍掉未用功能，把精力投在别处

### 6.2 三条止损线

在 Learn 阶段，如果触发以下**任一止损线**，必须停手重估：

**止损线 1: 使用率止损**

```
指标: 目标功能上线 4 周后, 核心场景使用率 < 20%
触发后: 立即停止在该功能上加投入, 反向做用户访谈找原因
```

**止损线 2: 留存止损**

```
指标: 上线 8 周后, 第 1 周用户到第 8 周的留存 < 30%
触发后: 说明产品没有长期价值, 重新审视核心假设
```

**止损线 3: 时间止损**

```
指标: 单次 MVP 迭代周期超过 8 周, 还没拿到有效数据
触发后: 迭代节奏太慢, 学习速度不够, 强制拆更小的 MVP
```

**糖果充的六件套评估**：

```
① A4 识别:      使用率 99% (远超 20%) ✓ 通过
② 异形票据:     使用率 0.3% (低于 20%) ✗ 触发止损
③ 多币种:      使用率 0% (远低于 20%) ✗ 触发止损
④ AI 智能提取:  使用率 2% ✗ 触发止损
⑤ 自动分类:    使用率 0.6% ✗ 触发止损
⑥ 批量校验:    使用率 0.2% ✗ 触发止损

止损行动: 
- ② 到 ⑥ 全部停止后续投入
- 保留代码 (不下线, 万一有人用)
- 团队精力立即转向下一个 Must Have (客户对账门户)
```

**止损文化的建立**：**团队应该把"止损"当成正常事件, 不是失败**。谁触发止损了就集体复盘, 学到什么, 下次不再犯——**这才是学习型团队**。

## 7. MVP 反模式

工程师做 MVP 最容易犯的 8 个反模式：

| 反模式 | 症状 | 危害 | 修复 |
|--------|------|------|------|
| MVP = 完整版缩水 | 从完整版砍到 30% 叫 MVP | 闭环走不通, 用户用不起来 | 从 0 开始想"最小闭环", 不是"砍功能" |
| 六件套心态 | 竞品有 6 个功能, 我也要 6 个 | 60% 投入换 3% 使用 | 四刀砍到 1 个功能, V2 再加 |
| 不写止损线 | 上线后没有失败标准 | 触发沉没成本陷阱 | 上线前写假设卡 + 止损线 |
| MVP 只写代码 | 忘了 Concierge/Wizard-of-Oz | 该 1 天验证的用 2 个月 | 先想"这个假设最小怎么验证" |
| 数据观测太晚 | 上线 3 个月才看数据 | 学习速度太慢 | 每周固定看数据, 拉一次曲线 |
| 沉没成本焦虑 | "都做这么多了砍不了" | 错误方向越走越远 | 只看未来 ROI, 过去投入清零 |
| Learn 阶段没了 | 上线就结束 | 只有 Build-Measure 没 Learn | 每次 MVP 后固定 1 天做 Learn 复盘 |
| MVP 只对内测 | 只给同事看 | 反馈全是假的 (礼貌反馈) | 至少 3 位真实付费/日活用户 |

**结论**：这 8 条覆盖了工程师做 MVP 95% 的翻车场景。上线前逐条自检。

## 8. 给不同岗位的话

**如果你是做硬件的**：硬件做 MVP 最难——**造出来就不好改**。三种形态里 **Wizard-of-Oz 尤其重要**：用 3D 打印做外壳，用现成模块拼电路，用 Arduino 跑一个"假装是最终产品"的版本。硬件的 Build-Measure-Learn 循环也更长（每次实体打样 1-2 周），所以**假设卡必须写更严格**，止损线要更早触发。**硬件 MVP 铁律**：**能不上模就不上模, 3D 打印跑通 5 个假设再考虑开模**。

**如果你是做算法的**：算法工程师最容易做"六件套"——**"识别 + 分类 + 推荐 + 排序 + 召回 + 兜底"** 全套上线。真正的算法 MVP 是**先跑通一个核心闭环**：一个模型 + 一个场景 + 一个数据源。**Concierge 在算法里的变形**：**用规则代替模型**——先用 30 条 if-else 上线，看看用户反馈，再决定要不要投入 3 个月做深度学习。**算法 MVP 铁律**：**先规则再模型, 先简单模型再复杂模型, 每次只加一个模型**。

**如果你是做运维 / SRE 的**：运维平台最容易踩"完整平台"陷阱——**监控 + 告警 + CI/CD + 日志 + tracing + 权限 + 审计**七件套齐发。真正的运维 MVP 是**先解决一个最痛的场景**：比如"上线后半夜三点回滚 5 分钟能做完"。**Wizard-of-Oz 在运维的变形**：**先手动 SOP + 值班群机器人**，跑通流程再自动化。**运维 MVP 铁律**：**先能救火再能防火, 先能回滚再能上线, 一个功能能救 3 点被叫起来的人就值得做**。

**如果你在传统行业（银行、制造、政企、医疗）**：传统行业做 MVP 最难的是**合规和试错空间**——上线前必须过审、试错代价高、用户容错率低。**Concierge 在传统行业尤其重要**：**先用人肉服务跑 3 个月**（一个客户经理带 5 个 VIP 客户），验证流程再上系统。**传统行业 MVP 铁律**：**MVP 不是给全体用户，是给 5 个 VIP 试点**——**Beta 用户圈子越小越好，反馈频率越高越好**。

## 9. 综合案例

### 9.1 发票识别 V2

回到糖果充。六件套翻车后，他做了三件事重建：

**第一件事：承认沉没成本，让六件套里的 ②–⑥"冻结"**

```
糖果充跟团队开了 1 小时会:
"六件套里的 ②③④⑤⑥ 使用率都在止损线以下, 
 我们不下线 (万一有人用), 但也不再投入优化。
 从今天起团队精力转向下一个 Must Have — 客户对账门户 MVP。"

团队反应: "但我们花了 3.6 人月做的功能不管了?"
糖果充: "不是不管, 是不再优化。过去的 3.6 人月已经沉没,
        今天的决策只看未来 ROI。"
```

**第二件事：给客户对账门户做真正的 MVP 假设卡**

```
核心假设:
  我们相信 [5 家大客户] 会 [每月登录门户查看对账明细],
  因为 [他们签合同时提出过'客户自助对账'的要求, 
       且传统方式是每月等我们邮件, 效率低]。

验证方式:
  我们做 [最小闭环: 登录 + 查对账 + 明细导出], 
  让 [5 家大客户各 1 位对接人] 用 [1 个月].

成功指标:
  月度登录 ≥ 15 次 (5 家 × 3 次) 
  且 3 家以上主动查过明细 
  且 无一次被投诉体验差

止损线:
  月度登录 < 5 次 → 说明合同要求是伪需求, 
  实际客户不用, 立即降级为"邮件发送对账单"

学习问题:
  ① 客户查对账的高频时点是什么? (影响未来告警设计)
  ② 客户会不会主动分享给他们的其他同事? (影响权限设计)
  ③ 5 家客户对"体验"的分歧点在哪? (影响后续版本)
```

**第三件事：四刀砍功能, 定 V1 范围**

```
客户对账门户完整版 (合同要求):
  ① 登录 + 查对账
  ② 明细导出 (PDF/Excel)
  ③ 异常上报 (客户发现错误提交回来)
  ④ 支付账单
  ⑤ 客户资料自维护
  ⑥ 多用户/多权限
  ⑦ 客户内部审批流

四刀合击后:
  ① ★ V1 必做
  ② V1 必做 (合同显性提及)
  ③ V1 必做 (核心闭环: 查 → 发现问题 → 上报)
  ④ V2 (Q4)
  ⑤ V2 (Q4)
  ⑥ V3 (客户超过 20 家再考虑)
  ⑦ V3 (客户强需求出现再考虑)

V1 范围: 3 个功能, 预计 2 人月
上线: 从 6 人月的完整版缩到 2 人月的 MVP
```

**上线 1 个月后数据**：

```
月度登录:  27 次 (超止损线 5.4 倍) ✓
主动查明细客户数: 4 家 (超止损线) ✓
投诉数: 0 ✓
主动分享给同事的客户: 2 家 (超预期) ✓

Learn 阶段收获:
- 客户高频查询时点集中在每月 5 号 (对账周期开始)
  → V2 加"月初对账提醒推送"
- 客户希望能一次导出多月对账
  → V2 加"批量导出"
- 3 家客户提到"能不能给我们的老板加只读权限"
  → V3 的多用户/多权限提前到 V2
- 0 家客户主动问"支付账单"
  → V2 的支付功能可以延后
```

**对比**：

```
V1 完整版 (糖果充最初的规划):
  6 人月 → 上线晚 5 周 → 未验证的功能 4 个

V1 MVP 版 (四刀 + 假设卡):
  2 人月 → 上线快 4 周 → 每个功能都验证过
  + 通过 Learn 得到 V2 的清晰方向
```

**这次糖果充彻底跨过了 MVP 这一关**——**先做小、快验证、真上线、看数据、再迭代**。他跟老周汇报时说：

```
糖果充: "老周, 我以前造产品都是'一次做到位', 现在明白了,
        没有'一次做到位', 只有'一次比一次学到位'。"
        
老周:   "你这就毕业了。"
```

### 9.2 MVP 能力回望

回望糖果充这次翻车 + 重建的全过程，**MVP 能力**的本质是：

```
初级:  一次做完整版, 上线看结果        (工程师完美主义)
中级:  砍到 30% 上线, 但没有假设       (缩水版)
高级:  写假设卡, 做最小闭环, 有止损线    (真 MVP)
资深:  三种形态灵活运用, 有 Concierge 也有 Wizard-of-Oz  (MVP 老手)
大师:  Build-Measure-Learn 循环成为日常, 每周都在学习    (精益文化)
```

**MVP 的四个心法**：

```
① 最小 ≠ 缩水, 最小 = 闭环完整
② 竞品有几件 ≠ 你要做几件, 用户要几件才是几件
③ 沉没成本清零, 只看未来 ROI
④ 学习速度 = 循环速度, 每周都要有 Learn
```

**MVP 的哲学**：**先活下来才能长大**。工程师本能是"造完美的一次到位"，产品本能应该是"**做实验、快验证、边学边造**"。**做产品不是雕塑（雕完就永远立在那里），是植物（先活下来才能长成任何形状）**。

### 9.3 速查与练习

**MVP 自检卡**（每个功能上线前逐条问自己）：

```
□ 1. 我写了 MVP 假设卡吗? 核心假设、成功指标、止损线都写了吗?
□ 2. 我判断过用 Concierge / Wizard-of-Oz / Landing Page 哪种形态吗?
□ 3. 我用四刀 (时间/角色/场景/权限) 砍过功能吗?
□ 4. 我的 MVP 是"最小闭环"还是"完整产品缩水"?
□ 5. 我的 MVP 上线后, 第 1/4/8 周的数据观测点定了吗?
□ 6. 触发止损线时我会立即停手, 还是"再优化一下"?
□ 7. 我对"过去投入"的敏感度有降到 0 吗? 只看未来 ROI 吗?
□ 8. Build-Measure-Learn 循环每次多长? 有没有 8 周超时?
```

**MVP 速查表**：

| 场景 | 动作 |
|---|---|
| 想做一个大功能 | 先写假设卡, 再砍四刀 |
| 老板说"做完整版" | 亮出 MVP + 假设卡 + 三种形态选项 |
| 团队争论要不要做 X | 用假设卡逼团队写止损线 |
| 上线后使用率低 | 对照止损线, 触发就停手 |
| "都做这么多了砍了太可惜" | 沉没成本陷阱, 清零重算 |
| 想加新功能 | 先跑 Landing Page 或 Concierge 验证需求 |
| 迭代太慢学不到东西 | 强制拆更小 MVP, 缩短循环到 2 周 |
| MVP 上线了没动静 | 检查是否闭环完整, 常见问题是走不通 |

**MVP 速查模板**（复制到你的项目文档）：

```markdown
# [功能名] MVP 假设卡

## 核心假设
我们相信 [用户群体] 会 [做什么行为],
因为 [什么理由/证据]。

## 形态选择
- [ ] Concierge (人肉服务)
- [ ] Wizard-of-Oz (前端真, 后端假)
- [ ] Landing Page (先测需求)
- [ ] 完整 MVP (前后端都真, 最小闭环)

## 四刀砍功能
| 子功能 | 时间刀 | 角色刀 | 场景刀 | 权限刀 | 总分 | V1/V2/砍 |
|-------|:---:|:---:|:---:|:---:|:---:|:---:|
|       |     |     |     |     |     |         |

## 验证方式
我们做 [MVP], 让 [用户 N 人] 用 [时长].

## 成功指标 (至少 1 个)
- 指标 1: ______ ≥ ______
- 指标 2: ______ ≥ ______

## 止损线 (至少 1 条)
- 如果 [情况], 停手/转向

## 数据观测点
- Week 1: ______
- Week 4: ______
- Week 8: ______

## Learn 阶段问题
- 我们想学到 ______
- 我们想学到 ______
```

**30 天 MVP 练习**：

```
Week 1 (假设卡训练):
  拿你手上 3 个正在做的功能, 每个补写一张假设卡
  重点: 每张卡必须有"止损线", 且是具体可测量的数字
  你会发现: 至少 1 个功能其实没想清楚假设

Week 2 (四刀砍功能):
  拿你正在做的一个"大功能", 列出所有子功能
  用四刀 (时间/角色/场景/权限) 逐个砍
  目标: 砍到不超过 30% 的原范围
  和团队一起过一遍, 争论过程本身就是学习

Week 3 (三种形态尝试):
  找一个新方向, 不写代码, 用 Concierge 或 Landing Page 验证
  Concierge: 人肉服务 3 位用户 1 周
  Landing Page: 花半天做个宣传页, 测点击率
  记录: 需求真伪 + 数据

Week 4 (Build-Measure-Learn 完整跑一次):
  选一个 MVP, 从假设卡到上线到 Learn 全流程跑一次
  上线后固定周一看数据 (Measure), 周五做复盘 (Learn)
  4 周结束后写一份 Learn 报告, 至少 3 条学到的东西
```

**练完 30 天你会得到什么**：
- 一种反射：**做功能前先想"这是要验证什么假设"**
- 一种自律：**看到"六件套"就想砍到"一件套"**
- 一种自信：**敢在老板面前说"这个先做 MVP, 数据不好我们及时止损"**
- 一种文化：**团队开始把"止损"当成学习, 不是失败**
