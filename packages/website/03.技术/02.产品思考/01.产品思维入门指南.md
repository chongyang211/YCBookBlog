## 1. 案例引入

### 1.1 日活为零

先看一段真实故事。糖果充，32 岁，工龄 8 年，最近从后端负责人被调去带一个新方向：**帮公司做一套内部对账系统**，替换财务姐姐用了 7 年的 Excel。

糖果充干得很兴奋。技术选型漂亮：Spring Boot + Postgres + Redis + Kafka，前端 Vue3，支持多币种、支持自动匹配、支持异常预警。2 个月开发完毕，架构评审拿了 A，Leader 在周会上表扬了他。

上线当天，糖果充给财务部三位姐姐做了一场培训，PPT 40 页，讲得口干舌燥。三位姐姐点头如捣蒜，说"很厉害"。

**三个月后统计后台数据**：

```
日活用户:        0
月活用户:        0
财务姐姐还在用:  她们的 Excel
糖果充的系统:    每天 2 次自动同步跑得很稳
```

糖果充崩溃了。他去找财务小李（三位姐姐里最年轻的那位）问：

```
糖果充: "李姐, 系统是不是有 bug? 我看你们都没用。"
李姐:   "没 bug 呀, 你做得挺好。"
糖果充: "那为什么不用?"
李姐:   "……你这个系统, 每次要打开浏览器、登录、选月份、点导入。
        我 Excel 拖一下鼠标就出来了。而且我做了 7 年, 
        闭着眼都知道哪个格子是哪个。"
糖果充: "但我这个自动匹配, 能省你 3 小时啊!"
李姐:   "……我一个月对账才 2 天, 3 小时对我不算啥。而且你这个系统万一算错,
        出问题算谁的? 我用 Excel 出问题, 至少我知道错在哪一格。"
```

糖果充回工位坐了 10 分钟没说话。

### 1.2 顺藤摸根因

带着这条线往下挖：

- **假设 1**：糖果充技术不好？——不是，架构评审拿 A，代码同事们都夸干净
- **假设 2**：需求没搞清楚？——好像也搞清楚了，"帮财务对账"这个需求是老板亲口交代的
- **假设 3**：培训没做到位？——PPT 40 页讲了 2 小时，姐姐们当场都说会用
- **假设 4**：那到底是什么？——**他把"帮财务对账"当成了技术任务，没当成"帮李姐替换她用了 7 年的 Excel"这件事**
- **假设 5**："帮李姐替换 Excel"意味着什么？——**要理解李姐的旧方案有多好用、迁移成本有多高、她真正的痛点在哪**
- **假设 6**：糖果充做的这些考虑过吗？——**零**。他从头到尾在解决"技术上怎么对账"，李姐要解决的是"月底那两天怎么应付过去"
- **假设 7**：这个错误有没有名字？有没有可复用的框架能避免？——**产品思维缺失**，本篇的主线

翻车根因清单：

```
表象                           真实问题
────────────────────────────────────────────────
"系统技术上完美"              → 只看了"我造得多好", 没看"用户旧方案多好"
"自动匹配省 3 小时"           → 用了"我的价值观", 没用"李姐的价值观"  
"培训了 2 小时都会用了"        → 会用 ≠ 愿意用, 忽略了迁移成本
"每天 2 次自动同步很稳"        → 系统在自嗨, 用户在另一个宇宙
"李姐说做得挺好"              → 中国人礼貌性夸奖被当真, 没做用户观察
```

**根因**：糖果充把"产品"当成了"技术项目"。**只关心"我造了什么"，不关心"用户凭什么用它"**。

这一段里至少藏着 8 个原理点：

```
① 用户视角到底是什么? 缺了会怎样?                → 第 2 章
② 用户凭什么用你的产品? 用什么公式衡量?           → 第 3 章
③ 什么是痛点/痒点/爽点? 工程师容易搞错哪个?       → 第 4 章
④ "谁在用、何时用、为何用" 怎么问?               → 第 5 章
⑤ 用户嘴里的需求和真实价值差多远?                → 第 6 章
⑥ 不同岗位 (硬件/算法/运维/传统行业) 有变形吗?    → 第 7 章
⑦ 糖果充要重做, 从哪一步开始?                    → 第 8 章
⑧ 每天怎么练用户视角?                            → 第 8 章
```

### 1.3 要回答什么

这个事故就是本篇的**主线案例**。带着上面 8 个问号往下走，每讲完一段方法就解开一两个；最后在第 8 章把糖果充的对账系统彻底重做，并给出可复用速查卡。

本篇路线：

```
用户视角四层 (第 2 章)
   ↓
用户价值公式 (第 3 章) ─→ 解开"用户凭什么用"
   ↓
痛点痒点爽点 (第 4 章) ─→ 解开"你以为的痛不是痛"
   ↓
场景三问法 (第 5 章) ─→ 解开"用户到底在什么场景下会想到你"
   ↓
需求到价值的翻译 (第 6 章) ─→ 解开"用户嘴上说的是需求, 手上要的是价值"
   ↓
跨岗位适配 (第 7 章)
   ↓
综合案例 (第 8 章) ─→ 糖果充的对账系统彻底重做
```

📌 **本篇定位**：这是"产品思考"系列的**开篇**。用户视角是所有产品能力的**起点**。没有这一步，后面所有的需求分析、优先级、MVP、指标、竞品分析都没有根。读完本篇后再做产品，你会自然回答一个问题："**这个东西凭什么让用户放下他的 Excel**"。

## 2. 视角全景图

### 2.1 视角四层

"用户视角"这四个字被讲烂了，但真正落到工程师身上是什么？拆成四层：

```
┌───────────────────────────────────────────────────────────┐
│                    用户视角四层                             │
├───────────────────────────────────────────────────────────┤
│  ① 谁 (Who)          用户是具体的一个人, 不是"用户群体"      │
│  ② 何时 (When)       在什么触发下, 才会想到你的产品          │
│  ③ 为何 (Why)        真实动机是什么, 不是嘴上说的            │
│  ④ 凭什么 (Value)    价值 = 新体验 - 旧体验 - 迁移成本       │
└───────────────────────────────────────────────────────────┘
```

四层属性速查：

| 层 | 输入 | 输出 | 糖果充 V1 翻车点 |
|---|---|---|---|
| 谁 | 用户画像 | 一个具体的人 + 她的日常 | 只说"财务", 没具体到李姐 |
| 何时 | 场景观察 | 触发点清单 | 没观察, 假设用户"随时用" |
| 为何 | 深度访谈 | 真实动机 | 假设"用户要提效" |
| 凭什么 | 价值公式 | 三项差值 | 只算了"新体验", 没减旧体验和迁移成本 |

### 2.2 为什么这么切

用户视角不就是"多站在用户角度想"吗？为什么要切成四层？想到哪写到哪不行吗？

**1.没有"谁"就没有对话对象**——"用户"是一个抽象名词，抽象名词不会用产品。真正会用的是"李姐，44 岁，做了 7 年财务，每天早上 8:50 到工位，第一件事是开 Excel"。**具体到人，才有产品**。

**2.没有"何时"就没有触发点**——你的产品不是 24 小时被想起的。李姐一个月只在**月末对账那两天**才需要对账工具，其他 28 天她想都不想。**不知道何时被想起，就不会被想起**。

**3.没有"为何"就抓错关键点**——李姐的真实动机不是"提效 3 小时"，是"月底那两天别出错、别让老板骂"。**动机错了，功能全废**。

**4.没有"凭什么"就是一厢情愿**——你觉得自动匹配值 10 分，李姐觉得"能出错的自动匹配 = 负分"。**价值不是你说了算，是用户按公式算出来的**。

反向验证：**没这四层会怎样**？答案就是第 1 章，糖果充造了个漂亮系统，李姐动都不动。

**结论**：四层的本质是把"用户视角"这个玄学**变成工程可操作的四个问句**。谁、何时、为何、凭什么——每次做功能前先答一遍。答不出来就先别写代码。

## 3. 用户价值公式

### 3.1 三项相减

俞军讲过一个公式，我做完那套没人用的对账系统之后，才真正读懂：

$$
\text{用户价值} = \text{新体验} - \text{旧体验} - \text{迁移成本}
$$

看着简单，用起来极反直觉。工程师的本能是：**只要新体验够高，用户就该来用**。公式里有两个减号，很多人视而不见。

**三项定义**：

```
新体验:      用户用你的产品获得的收益 (省时间、省钱、少犯错、更爽)
旧体验:      用户不用你, 而是用当前替代方案获得的收益  
迁移成本:    从旧方案切换到新方案需要付出的代价
```

**关键洞察**：**旧体验不是零**。李姐的 Excel 不是"落后工具"，是**她 7 年打磨的操作肌肉记忆**。不认真看这个数字，永远算不清账。

### 3.2 迁移成本四项

**迁移成本**是工程师最容易低估的一项。它至少包含四小项：

```
┌──────────────────────────────────────────────┐
│                迁移成本四小项                  │
├──────────────────────────────────────────────┤
│ C1 学习成本      记住新界面、新流程、新术语     │
│ C2 习惯成本      改变已经形成的工作习惯         │
│ C3 试错成本      新工具万一出错谁负责           │
│ C4 数据迁移成本  历史数据搬过来的代价           │
└──────────────────────────────────────────────┘
```

糖果充 V1 只想到 C1（我培训过了呀），完全没考虑 C2/C3/C4：

```
C1 学习成本:   培训 2 小时 (糖果充有做) → 但李姐记不住第 3 个菜单在哪
C2 习惯成本:   李姐 7 年养成的 Excel 肌肉 → 系统里点 5 下才能完成
C3 试错成本:   自动匹配错了算谁的? → 李姐宁可自己错也不背这个锅
C4 数据迁移:   过去 3 年的历史账目在 Excel 里 → 系统只支持从上线日起对账
```

**结论**：**迁移成本 = C1 + C2 + C3 + C4**。工程师看到 C1 就觉得"我算过了"，其实只算了 25%。

### 3.3 公式复盘

拿糖果充的对账系统代入公式，10 分制打分：

**新体验**：
- 自动匹配（+3）
- 异常预警（+2）
- 多币种支持（+2）
- 报表一键导出（+1）
- 小计：**+8**

**旧体验**（李姐的 Excel）：
- 7 年操作肌肉，闭眼操作（+4）
- 每一格错在哪一目了然（+3）
- 出错自己扛，可控（+2）
- 一个月只用 2 天，够用（+1）
- 小计：**+10**

**迁移成本**：
- C1 学习成本：40 页 PPT，5 个菜单要记（-2）
- C2 习惯成本：Excel 拖鼠标 → 系统点 5 下（-3）
- C3 试错成本：自动匹配出错责任归属不明（-4）
- C4 数据迁移成本：3 年历史账目无法导入（-2）
- 小计：**-11**

**用户价值** = 8 − 10 − 11 = **−13**

一个大负数。李姐不用是**极度理性**的选择。

**反问**：那糖果充要做到多高的"新体验"才能翻盘？答：至少 +21 分（覆盖旧体验 10 + 迁移成本 11）。现有 +8 分距离 +21 分差 13 分——**再堆功能是没用的**，必须**降低迁移成本**（比如支持历史数据一键导入、比如让自动匹配可预览可修改、比如让 UI 学 Excel 的操作方式）。

**结论**：**公式的价值不是算出精确的分数，是逼你诚实地看那两个减号**。

## 4. 痛点痒点爽点

### 4.1 三点定义

产品圈流传的"痛痒爽"三点法：

```
痛点 (Pain)        用户遇到的真实困扰, 不解决会产生负面情绪
                   例: 财务姐姐月底加班到 11 点

痒点 (Itch)        用户觉得"如果有会更好"的锦上添花
                   例: 有个自动汇总的按钮

爽点 (Delight)     用户瞬间被打动、超出预期的体验
                   例: 系统自动帮她挑出 3 笔可疑账, 老板夸她细心
```

**三点关系**：

```
痛点 → 用户会付钱/付时间去解决 (刚需)
痒点 → 用户看到会点赞, 但没了也无所谓 (次要)
爽点 → 用户会主动推荐给别人 (口碑引擎)
```

### 4.2 工程师偏见

**核心洞察**：**工程师 90% 的时间在做痒点，以为自己在解痛点**。

原因是工程师的痛点和用户的痛点完全不重合：

```
工程师眼里的痛:          用户眼里的痛:
─────────────────────────────────────────
代码不优雅              月底加班到 11 点
系统扩展性不好           出错被老板骂
接口设计不 REST          客户催了 5 次还没做完
CI/CD 不自动化           工资涨不上去
故障率 0.5%              系统换了要重学
```

**两个宇宙**。糖果充做对账系统时，脑子里的痛是"财务用 Excel 太原始"，李姐的痛是"月底那两天出错怎么办"。这两个痛的解法**完全不同**：

- 解"太原始" → 做一套酷炫系统（糖果充做的）
- 解"出错怎么办" → 做一个"复核工具"，帮李姐在她的 Excel 上多加一层校验（应该做的）

### 4.3 识别练习

拿到一个需求，先做**三点识别**：

```
需求: 财务想要一个自动对账工具

三点识别:
□ 痛点是什么?     月底 2 天加班到 11 点 + 出错扣工资
□ 痒点是什么?     报表自动生成、多币种支持
□ 爽点是什么?     系统能帮李姐"发现她自己没发现的错"

工程师版 V1 做了什么:
✓ 痒点覆盖: 报表、多币种、自动同步 (全做了)
✗ 痛点覆盖: 出错怎么办? (没解决, 反而加了新的 C3 试错成本)
✗ 爽点覆盖: 零

产品版 V2 应该做什么:
✓ 痛点: 让李姐月底那 2 天更省心 (核心)
✓ 爽点: 帮她主动发现 Excel 里她没注意到的可疑数据 (口碑引擎)
✗ 痒点: 报表/多币种/自动同步 (V2 都可以砍掉)
```

**结论**：**痛点是刚需，痒点是加分，爽点是传播**。三者优先级严格排序：**痛 > 爽 > 痒**。

**反例**：市面上 80% 的 to B 系统翻车都是同一个模式——**痒点做满，痛点没碰，爽点为零**。

## 5. 场景三问法

### 5.1 谁在用

"用户是财务"这不算答案。**具体到一个真人**才算：

```
❌ 抽象答: "用户是财务部的人"

✅ 具体答:
姓名: 李姐 (44 岁, 财务专员)
职级: 中层, 上有主管下有 2 个实习生
一天:  8:50 到工位, 9:00 打开 Excel, 中午 1 小时休息, 
      18:00 准时下班 (家里有孩子接送)
月度: 只有 25 号-30 号 (对账周) 会加班到 11 点
KPI:  账目零错误 (错一次扣 500 块)
性格: 谨慎、怕承担责任、不喜欢新东西
```

**核心问句**：**如果你做出来的产品要变成李姐每天工作流里的一部分，她要怎么用？**糖果充 V1 从头到尾没答过这个问句。

### 5.2 何时用

用户不是 24 小时想着你的产品。**触发点**才关键：

```
❌ 抽象答: "用户随时可以用"

✅ 具体答:
李姐一个月使用对账工具的时刻:
- 25 号 09:00   核对本月银行流水 (2 小时)  ← 高频高压
- 26 号 14:00   核对客户回款 (3 小时)      ← 高频高压
- 27 号 09:00   核对供应商付款 (2 小时)    ← 高频高压
- 28 号 10:00   出对账报表给主管 (1 小时)  ← 高频中压
- 30 号 18:00   月度归档 (30 分钟)         ← 低频
```

**结论**：**李姐一个月只在 6 个时点上会想到"对账"这件事**。这 6 个时点的体验决定一切，其他 720 小时你的系统在她的世界里**不存在**。

**做产品的启示**：不是"做一个 24 小时可用的系统"，是**做那 6 个时点的最佳伴侣**。

### 5.3 为何用

**动机 ≠ 需求**。李姐嘴里的"我需要对账工具"，翻译成动机是：

```
表层需求:    "我需要一个对账工具"
中层动机:    "月底那 2 天让我别出错"
深层动机:    "让老板月度总结会上表扬我而不是骂我"
本质动机:    "我 44 岁了, 换工作难, 这份工作必须稳"
```

**从表层需求到本质动机的翻译，是产品思维的核心**。

**做产品的启示**：只解表层，你会做一个"对账工具"；解到深层，你会做一个"月底那 2 天让李姐 confidently 交差的助手"；解到本质，你甚至会在系统里加一个"月度亮点自动生成"功能——帮李姐在总结会上有话讲。**这就是从"造代码"到"造产品"的分水岭**。

## 6. 需求到价值

### 6.1 需求与价值

工程师最容易犯的错：**把用户嘴里的"需求"当成"要做的功能"**。对照关系：

```
用户嘴里的需求         用户手上真正要的价值
────────────────────────────────────────────
"我要一匹更快的马"    → "让我更快到达目的地"
"我要一个对账工具"    → "让我月底不出错、被老板表扬"
"我要一个更亮的手电筒" → "让我在黑夜里更有安全感"
"我要一个报表"        → "让我在周会上有说服力"
"我要一个 API"        → "让我的功能上线不用等后端一周"
```

**翻译规则**：**需求是手段，价值是目的**。工程师要用"5Why"把手段追问回目的（详见下一篇《用户需求分析方法》）。

### 6.2 三段翻译

给出一个可复用的三段翻译模板：

```
用户嘴里的需求: __________________ (原样记录)

追问 1 (为什么想要这个): ______________ (手段的目的)

追问 2 (为什么这个目的重要): _____________ (深层动机)

翻译后的价值: __________________ (给用户真正的东西)
```

**示例**（拿李姐练手）：

```
用户嘴里的需求: "我要一个对账工具"

追问 1 (为什么想要这个): "月底对账太慢, 加班到 11 点"

追问 2 (为什么这个目的重要): "老公要接孩子, 我加班家里就没人管娃"

翻译后的价值: "让李姐月底那 2 天准时下班 (18:00 前)"
```

**看，"对账工具"这个需求，翻译后的价值居然是"准时下班"**。这时候你会发现：

- 自动匹配（+3 小时）：**匹配价值**（帮她省时间）
- 多币种支持：**不匹配**（她们公司没外币业务）
- 异常预警：**匹配**（省她复核时间）
- 报表导出：**不匹配**（她根本不做报表，主管做）

**V2 版本自然砍掉了两个"痒点功能"**。这不是靠工程师的直觉，是靠**翻译**得出的结论。

### 6.3 反模式清单

工程师最容易犯的 6 个视角错误：

| 反模式 | 症状 | 危害 | 修复 |
|--------|------|------|------|
| 以自己为用户 | "我是用户我觉得这样好用" | 你的画像是"32 岁工程师", 用户可能是 44 岁财务 | 场景三问, 具体到人 |
| 只算新体验 | "我加了 10 个功能" | 忽略旧体验 + 迁移成本, 负价值 | 用价值公式三项相减 |
| 痛痒不分 | 花 80% 时间做痒点 | 用户觉得"好玩但不必须" | 三点识别, 痛 > 爽 > 痒 |
| 24 小时假设 | "用户随时会用" | 忽略触发点, 产品在用户宇宙里不存在 | 列出真实触发时点 |
| 相信礼貌反馈 | "用户当面说很好" | 中国人礼貌 ≠ 会真的用 | 看行为数据, 不看嘴上评价 |
| 需求当功能 | 用户说 A 就做 A | 需求是手段, 不是目的 | 三段翻译, 追问到价值 |

**结论**：**这 6 条反模式覆盖了工程师做产品 90% 的翻车场景**。做完功能前逐条自检一遍，能砍掉大部分不必要的坑。

## 7. 给不同岗位的话

**如果你是做硬件的**：用户视角的"迁移成本"里，C4（数据迁移）会变成 C4'（**硬件替换成本**）——用户已经有的设备扔不扔？扔了亏钱、不扔占位置。硬件产品的旧体验里还多一项：**已有的实体资产**。价值公式对硬件更残酷，很多"技术上完美"的硬件产品败给"用户舍不得扔家里那台老的"。

**如果你是做算法的**：算法工程师最容易掉进"痒点陷阱"——精度提升 3%，用户完全无感。真正的痛点是"错一次要人工兜底多久"。**算法价值 = 新精度 − 旧精度 − 部署迁移成本 − 可解释性成本**。可解释性成本对 B 端算法尤其重要，一个"我不知道为什么错的高精度模型" 不如 "我完全能解释的低精度模型"。

**如果你是做运维 / SRE 的**：你的用户是同事（研发、测试、产品）。他们的"旧体验"是**已经形成的工作流**（手动上线也好、jenkins 也好），你造的 DevOps 平台再漂亮，他们只在**发布那一刻**才会用你。抓住那一刻，其他都是次要。**运维平台的爽点**：帮他们**发现他们自己没意识到的问题**（比如帮研发同学发现"你这次发布的服务和 A 服务有依赖冲突"）。

**如果你在传统行业（银行、制造、政企、医疗）**：用户的旧体验通常极其顽固——李姐的 Excel 只是入门级，银行柜员的 AS400 绿屏字符终端才是终极难题。传统行业做产品的核心不是"新体验多好"，是**"把迁移成本降到零"**——让他们**不用改工作习惯就能享受新价值**。这就是为什么"抬头看这一眼就完成对账"的方案，永远比"打开一个新系统"的方案更受欢迎。

## 8. 综合案例

### 8.1 第二次做对账

回到糖果充。系统被李姐晾了 3 个月后，他找了产品同学老周喝咖啡。老周没听他讲技术，先问：

```
老周: "你造这个东西之前, 有没有花一个下午坐李姐边上, 看她怎么对账?"
糖果充: "......没有, 我看了她的 Excel 模板。"
老周: "模板和真人操作是两回事。你知道她 25 号那天几点开始吗? 
       她开的第一件事是什么? 中间有没有被打断? 打断后怎么找回上下文?"
糖果充: (被问懵) "都不知道。"

老周: "你现在的对账系统解决的是'如何对账', 
       李姐要的是'如何在月底那 2 天准时下班'。
       这两件事看着像一件事, 差着一整套产品。"

糖果充: (愣住)
```

第二天糖果充搬了张凳子坐在李姐工位边上，观察她整个 25 号的对账过程。8 小时观察 + 3 次访谈 + 4 次追问，糖果充手里有了 3 页笔记。

**关键发现**（他之前完全不知道的）：

```
发现 1: 李姐 90% 的时间不是"匹配", 是"复核"
        她怕自动匹配出错, 每一笔都要人眼再看一遍
        她在乎的不是"省时间", 是"我扫过一眼确认过了, 出错不背锅"

发现 2: 李姐真正的痛点在 27 号下午
        供应商发票经常晚到, 她要在 Excel 里手动补录
        每次补录都要重新算合计, 特别容易错

发现 3: 李姐从不看糖果充的"报表"功能
        她的老板要的报表是 Word 版本, Word 版本主管自己写
        糖果充做的"一键导出 Excel 报表"是给谁的? 没有用户
```

糖果充按新的用户视角重做了 V2：

```
V1 (被抛弃)                   V2 (被拥抱)
────────────────────────────────────────────────
一套独立系统, 让李姐弃用 Excel   Excel 插件, 李姐还是用她的 Excel
自动匹配 (李姐不敢用)           匹配预览 (李姐点"接受"才生效, 责任归她)
一键报表 (老板不看)             全砍
多币种支持 (公司不用)           全砍
异常预警 (弹窗)                 Excel 单元格变红 (在她原本的界面里)
新增: 供应商发票晚到智能补录     ← V1 完全没做的痛点
新增: "月度亮点" 自动摘要        ← 帮李姐在总结会上有话讲 (爽点)
```

V2 上线两周后：

```
李姐日活:            月底 6 天 100% 使用, 其他时间 0
月度加班时长:        从 20 小时降到 4 小时
李姐给糖果充发消息:  "小杨, 这次的东西比上次那个真好用, 我推荐给了隔壁部门"
```

**注意最后一句**——李姐主动推荐给隔壁部门。这就是"爽点"引发的口碑。V1 三个月零日活，V2 两周就出现了自发传播。

### 8.2 视角回望

回望糖果充这次翻车 + 重做的全过程，**用户视角**并**不是模糊的态度**，而是**四层可操作动作**：

```
初级视角:     "我做的东西挺好用"                   (自我视角)
中级视角:     "用户应该喜欢我做的东西"             (假设视角)
高级视角:     "我坐在用户边上看她怎么用"           (观察视角)
资深视角:     "我用价值公式算过, 用户真的会用"     (量化视角)
大师视角:     "用户主动推荐给别人"                 (口碑视角)
```

**用户视角的四个心法**：

```
① "我造了什么" 不重要, "用户凭什么用" 才重要
② 旧体验从来不是零, 迁移成本从来不是四分之一
③ 用户嘴上说的是需求, 手上要的是价值
④ 会用 ≠ 愿意用, 说好用 ≠ 真在用
```

**产品思维的第一课，就是承认自己不是用户**。

### 8.3 速查与练习

**用户视角自检卡**（做完每个功能前逐条问自己）：

```
□ 1. 我能说出至少 1 个具体用户的姓名和一天的时间安排吗?
□ 2. 我知道这个用户一周会在几个时点触发使用我的产品吗?
□ 3. 我用价值公式算过用户价值 = 新体验 - 旧体验 - 迁移成本吗?
□ 4. 我把迁移成本拆成 C1/C2/C3/C4 四小项算过吗?
□ 5. 我识别过这个功能属于痛点/痒点/爽点吗?
□ 6. 我确认这不是我自己想要的痒点吗?
□ 7. 我把用户嘴里的需求做过三段翻译, 找到了真正的价值吗?
□ 8. 我至少花过 1 小时坐在真实用户边上看他工作吗?
```

**用户视角速查表**：

| 场景 | 动作 |
|---|---|
| 想做一个新功能 | 先答"谁在用/何时用/为何用" |
| 感觉需求"很酷" | 警惕, 大概率是痒点 |
| 用户当面说好 | 别信, 看数据 |
| 用户提了个具体需求 | 三段翻译, 找价值 |
| 觉得自动化能救用户 | 先算 C3 试错成本 |
| 系统上线后没人用 | 复盘价值公式, 大概率新体验没盖过迁移成本 |

**30 天用户视角练习**：

```
Week 1 (自我校准):
  每天记录 1 次"作为用户, 我被某个产品激怒/取悦"的瞬间
  写下: 具体触发时点 + 我的真实动机 + 迁移成本考量

Week 2 (身边观察):
  找到 1 位真实用户 (同事、家人、朋友), 
  观察他使用某个产品的完整过程 (至少 30 分钟)
  写下 5 个"我没预料到的操作"

Week 3 (公式演练):
  拿你负责的一个功能, 用价值公式打分:
  新体验 = ? 旧体验 = ? 迁移成本 (C1+C2+C3+C4) = ?
  加总看是不是负数

Week 4 (三段翻译):
  收集 3 个用户提过的需求, 每个做三段翻译:
  嘴里的需求 → 追问 1 → 追问 2 → 真正的价值
  对比翻译前和翻译后, 应该做的功能变了没?
```

**练完 30 天你会得到什么**：
- 一份属于你的"用户宇宙笔记"
- 一种条件反射：**做功能前先想公式**
- 一种能力：**区分你自己的偏好和用户的动机**
