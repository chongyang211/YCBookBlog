# 技术影响力建设法

> 开源贡献、社区运营、内部布道——让你的价值被看见

## 一、为什么你的技术能力不被看见

很多工程师都有一个困惑：我技术不差，为什么升职加薪的不是我？

```text
两个能力相同的工程师，3 年后：

工程师 A：
  → 代码写了就合，从不写文档，从不分享
  → 只和他直属 leader 知道他能做什么
  → 跳槽时简历上写的都是"参与 XX 项目"

工程师 B：
  → 把踩坑经验写成团队 wiki，帮后面 5 个人省了时间
  → 在团队内做了一次技术分享，隔壁组的 TL 记住了他
  → Git 上维护了一个小工具库，300+ star
  → 跳槽时面试官说"我读过你的博客"
```

**技术能力 × 影响力 = 职业价值。影响力不是让你去搞关系——是让你的技术能力在工作之外的地方也被看到。**

## 二、内部影响力——让你的价值在团队内外可见

### 2.1 从"做完了"到"写下来"

```text
你做了一件事 → 只有你知道你做了
你写下来了 → 所有当时和以后需要这件事的人都知道
```

内部影响力最小的起步动作：

```text
□ 你排查了一个线上问题 → 写一篇 oncall 记录发到群里
□ 你做了一个技术选型 → 把对比分析写到 wiki
□ 你优化了一个接口 → 写 3 句话 + 一张对比图，发到团队频道
□ 你发现了一个公共组件的 bug → 修了之后在公共频道说一下
```

**每一次"写下来"都在积累你的技术信用。** 半年后，团队里遇到类似问题就会想起"上次 XX 写过"，你成为了那个方向的"默认回答者"。

### 2.2 技术分享——最低成本的个人品牌

很多工程师对做分享的心理门槛："我不是专家，讲错了怎么办。"

但实际上，内部技术分享不需要你成为专家：

```text
第一档：项目复盘
  "我们做订单系统重构的 3 个坑"
  → 你讲的就是你刚做的，不可能出错。价值：让其他组下次类似需求时少踩坑。

第二档：技术调研
  "5 个消息队列的对比——Kafka/RocketMQ/Pulsar/RabbitMQ/Redis Stream"
  → 你做了技术选型，顺便做个分享。价值：帮其他人省调研时间。

第三档：外部学习复盘
  "我去参加了 XX 技术大会，这 3 个 talk 最有收获"
  → 你没讲新东西，你做了信息搬运+翻译。价值：帮没法参会的同事获取信息。
```

**先做第一档。** 你能讲好自己做过的事。讲完第一次后，你会发现"做分享没那么可怕"。

### 2.3 跨团队协作——让你的影响力越过组间墙

```text
你发现隔壁组的 API 设计有一个扩展性问题，你有两个选择：

选择 A：不管。反正是他们组的事。
  → 只在本组有影响力

选择 B：提一个友好的 issue/PR comment，附上改进建议和理由。
  → 隔壁组 TL 注意到了你，下次遇到类似问题可能直接来找你讨论
  → 年终 review，你的 leader 可能会听到"你们组 XX 帮我们解决了一个问题"
```

**跨团队的影响力不用刻意经营——就是多走一步：不只自己组的事做好，碰到其他组的问题时你也愿意伸手。**

## 三、外部影响力——开源和社区

### 3.1 开源不是"写了一个框架才叫开源"

很多工程师觉得"开源"的门槛太高——必须是 Vue/React 这种级别的东西才算。但实际上：

```text
开源贡献的四个阶梯：

L1：提 issue（0 成本）
  → 用某个开源项目时发现了 bug/不足 → 友好地提一个 issue，描述场景和复现步骤
  → 你帮维护者发现了盲区——这就是贡献

L2：文档贡献（1-2 小时）
  → 看到一个开源库的文档有错误/缺例子/缺中文翻译 → 提一个 PR 修正
  → 维护者最头疼的就是文档——你帮他修了，他的感激度可能比你想象的更高
  
L3：修小 bug（2-4 小时）
  → 遇到一个 bug，顺着源码找到根因，提一个 fix PR
  → 从此你的名字出现在这个项目的 Contributors 里

L4：自己维护一个项目
  → 把你工作中反复用到的一个工具函数、一个脚本、一个小工具——整理出来开源
  → 不需要多复杂。一个 200 行的命令行工具只要解决了真实问题，就能有 star
```

**从 L1 开始。** 今天就去你常用的一个开源项目的 GitHub 页面上，找一个 issue 并写一条有建设性的评论。

### 3.2 写技术博客——外部影响力的复利

技术博客是外部影响力最稳定的杠杆：

```text
你写了一篇文章 → 被 100 个人看到 → 其中 3 个人关注了你
→ 3 个月后又写了第二篇 → 这 3 个人帮你转发了 → 300 人看到
→ 第 5 篇 → "在 XX 方向问题上，你是默认答案"的神奇拐点到来
```

**持续输出比单篇爆款重要 10 倍。** 写 20 篇普通文章的人，远比特意打磨一篇"大作"后不再写的人有影响力。

### 3.3 外部技术分享

```text
从内部分享到外部分享的路径：

1. 内部讲 3 次 → 内容打磨成型
2. 把内容改写成博客 → 外部验证是否有人感兴趣
3. 报名公司内部的技术开放日 / 跨公司交流
4. 投稿技术大会的 CFP（议题征集）
5. 被选中 → 你的 talk 被录下来 → 线上的传播周期可能长达 2-3 年
```

**第一外部分享去小场子，不去大会。** 小场子（50 人以内）压力小，互动好，主办方对讲者的要求也更友好。

## 四、社交——不是搞关系，是建立信任网络

### 4.1 什么是有效的技术社交

```text
❌ 广撒网式社交：
  加 500 个微信好友，从不互动，需要帮忙时群发"在吗？"
  → 没人回复。这 500 个"联系人"和你没有任何关系。

✅ 价值交换式社交：
  你在 GitHub 上给某人的项目提了一个高质量的 PR
  → 你们在讨论中建立了技术层面的互相认可
  → 一年后你找工作时，他刚好在你想去的公司——你多了一个内推渠道
```

**有效社交不是你认识谁——是谁在什么问题上会想到你。**

### 4.2 最低成本的社交方式

```text
1. 给开源项目提 PR → 不要提了就走，PR 被合并后在 issue 下面说声谢谢
2. 看到一篇好博客 → 不是点收藏——是留一条有内容的评论
   "你提到的第三点我们也遇到了，我们的解法是 XX，效果也不错。"
   作者大概率会回复你——对话开始了。
3. 技术大会茶歇 → 问演讲者一个问题，不要泛泛的"讲得很好"——
   "你在 XX 部分提到的方案，在高并发下会不会遇到 YY 问题？"
```

## 五、个人品牌——别人搜你名字时看到什么

### 5.1 你的"搜索名片"

```text
当你去面试、去认识新同事、去认识合作方——对方大概率会在见你之前搜索你的名字。

你现在可以去搜一下自己的名字：
  □ 搜出来的是什么？博客？GitHub？还是无关结果？
  □ 展示的技术方向是什么？是你想让人记住的方向吗？
```

你的个人品牌 = 别人搜你名字时看到的前 5 条结果。

### 5.2 三步建立一个简单但有效的技术品牌

```text
第一步：锁定一个标签
  → 不是"全栈工程师"——是"Android 性能优化"或"支付系统架构"
  → 说一个别人能在 3 秒理解的技术方向

第二步：围绕这个标签持续输出
  → 博客、分享、开源项目——每一条都强化同一个标签
  → 写 5 篇"Android 启动优化"系列 > 写 5 篇互不相关的文章

第三步：让别人帮你传播
  → 你的文章被转发、你的工具被推荐、你的分享被写进别人的博客——这才是影响力真正的杠杆
```

**标签不能太宽，也不能太窄。** "后端工程师"太宽，没人记得。"17 世纪法国酒馆管理系统专家"太窄——没需求。

## 六、影响力度量与反馈——看不见的就不是影响力

### 6.1 影响力不是"你觉得自己有"，是你走了之后还在运转的东西

| 测量维度 | 怎么验证 |
|---|---|
| 文档影响力 | 你 3 个月前写的文档，今天还有人引用吗？ |
| 工具影响力 | 你写的工具/脚本，团队里还有人在用吗？ |
| 决策影响力 | 你做过的技术决策，在没有你的维护下还在运转吗？ |
| 方法论影响力 | 你提出的方案/规范/流程，被其他团队采纳了吗？ |
| 人才影响力 | 你带过的人，离开你的团队后能独立成长吗？ |

### 6.2 一个季度一次"影响力自检"

```
□ 最近 3 个月，有没有一个技术决策是因为我写的文档/方案才做对的？
□ 最近 3 个月，有没有一个同事主动来找我请教某个领域的问题？
□ 最近 3 个月，有没有一个我的技术观点被团队之外的人引用？
□ 最近 3 个月，我给团队带来了什么"如果不是我就不会发生"的变化？
```

如果四个问题都是否——你的影响力在衰退。


## 七、公司内部晋升的影响力策略

### 7.1 晋升不是"跟 Leader 搞好关系"——是"让评审委员会看到证据"

晋升答辩的本质是：一群不认识你的人，在 30 分钟内决定你的级别。他们看什么？

| 证据类型 | 权重 | 你在答辩前需要准备 |
|---|---|---|
| 业务结果 | 40% | 你做的事，对业务产生了什么可量化的影响 |
| 技术深度 | 30% | 你解决的技术难题有多难、为什么你做到了别人做不到 |
| 影响力 | 20% | 你做的事，影响了团队/公司/行业中的多少人 |
| 潜力 | 10% | 你下一步能做什么 |

### 7.2 晋升准备的"三个月前置法"

```
答辩前 3 个月: 和 Leader 对齐晋升标准——"我还差什么"
答辩前 2 个月: 开始整理你的"证据文档"——不是写述职，是整理碎片
答辩前 1 个月: 写完第一版述职，找 2 个晋升过的人预审
答辩前 1 周: 准备 20 个可能被问的问题，找人 mock 一次
```

**最常见错误**：答辩前一周才开始准备——那时你发现少了关键证据，补都来不及。


## 八、新媒体的技术品牌建设

博客之外，越来越多工程师通过短视频/直播/B站建立了技术影响力。新媒体的规则和文字不同：

| | 文字（博客） | 视频 |
|---|---|---|
| 最佳时长 | 5-10 分钟读完 | 8-15 分钟 |
| 核心要素 | 标题 + 结构 | 标题 + 封面 + 前 30 秒 |
| 适合内容 | 深度分析、方案对比、踩坑经验 | 原理讲解、live coding、行业评论 |
| 起步门槛 | 用 Github Issue 就能开始 | 需要录屏/剪辑，但手机也能拍 |
| 受众 | 精准的技术读者 | 更广的技术爱好者 |

**选择原则**：先做一种做到 80 分，再扩展到另一种。不要同时开始两个方向——精力会分散到什么都做不好。


## 九、长案例：糖果充从"沉默码农"到"公司技术大使"的三年

这是本系列最长的一个故事——**因为影响力建设本来就是一个漫长的过程**。糖果充从 P6 开始建设影响力，到 P7 末年成为"公司技术大使"（内部半正式头衔），一共 3 年 36 个月。**我们逐季度拆解他的动作和结果。**

### 9.1 起点：Y0 Q4 —— 完全沉默的糖果充

**当时状态**：
- P6 高级工程师，工作 3 年
- **零外部影响力**：没博客、没 GitHub、没演讲
- **内部影响力也弱**：**除了本组同事，别的组不认识他**
- **原因**：**"我技术还不够，等再厉害点再写"**——**典型的完美主义**

**转折点**：一次跨部门评审，他的方案被隔壁组一个 P5 挑战——**因为对方"看起来更懂"**。糖果充事后打听——**那个 P5 有个技术博客，写了 20 多篇 Kafka 相关的文章**。**部门里所有人都以为他是 Kafka 专家**。

**糖果充的顿悟**：**"影响力不是等你厉害了自然有——是你要主动建设的"**。

### 9.2 Y1 Q1：从内部文档开始

**目标**：**从最容易的开始——不外露也不受挫**。

**动作**：
1. **每次踩坑都写一份 wiki 记录**（3 个月内累积 15 篇）
2. **主动补文档**：把组内一份"新人前 30 天指南"从 3 页扩到 15 页
3. **每周分享一次"我这周学到什么"**（组内 15 分钟）

**成果**：
- **新入职的两个新同事说"糖果充哥的 wiki 救了我"**
- **组内 code review 越来越多找他**
- **TL 在季度评价里第一次写了"知识分享意识强"**

**数据**：**Wiki 文档累积 15 篇，阅读量总计 200+，评论 20+**

**教训**：**内部影响力的门票 = 你的产出别人在你不在场时依然被使用**。

### 9.3 Y1 Q2：跨组的第一步

**契机**：糖果充踩了一个"MySQL 索引下推"的坑，花了 2 天定位——**这个坑其他组也在踩**。

**动作**：
1. **写了篇 3000 字的内网博客《MySQL 索引下推的三个陷阱》**
2. **主动发到公司技术分享群**（第一次公开发东西——**手抖发送**）
3. **一周内约了 3 个提问的人 1v1 交流**

**成果**：
- **阅读量 800+**（部门大概 200 人，说明传出部门了）
- **收到 5 位跨组同事的私信**——**其中 2 位后来成为长期合作伙伴**
- **一位 P8 架构师在群里 @ 他说"写得清楚"**——**这条 @ 是糖果充影响力的第一次\"社交货币\"事件**

**数据**：**博客第一篇，阅读 800+，跨组新联系人 5 人**

**教训**：**第一次"露头"是最难的——但一次成功后成本会指数级下降**。

### 9.4 Y1 Q3：主动申请一次分享

**契机**：部门季度技术分享公开征集选题——**大多数人不敢报，糖果充报了**。

**动作**：
1. **提交选题《微服务熔断实践》** — 部门通过
2. **准备 3 周**（第 02 篇提到的翻车实录就是这次，但补了几个月的迭代之后）
3. **现场分享 30 分钟 + Q&A 10 分钟**

**成果**：
- **200 人到场，30 人 Q&A**
- **分享后录像内部下载 500+**
- **原本部门内不认识的一位技术总监会后加了他微信**

**数据**：**部门知名度阶跃——从"本组同事认识"到"部门里 200 人以上认得"**

**教训**：**一次好的公开分享 = 3 个月博客写作的效果**——**因为演讲的\"人味\"传播性远超文字**。

### 9.5 Y1 Q4：外部博客试水

**契机**：内部博客写多了，糖果充想试试外部——**但害怕"数据难看"**。

**动作**：
1. **注册掘金账号，用 nickname**（怕数据难看有心理负担）
2. **把内网博客脱敏后重发**（3 篇）
3. **在技术社区回答了 5 个问题**（Stack Overflow / V2EX）

**成果**：
- **3 篇博客总阅读 3000+**（比预期低）
- **1 篇被"掘金前端专栏"收录**（意外之喜）
- **收到 2 个猎头联系**——**这是外部影响力的第一次"经济价值"证据**

**数据**：**外部数据 3000+ 阅读，2 位猎头**

**教训**：**外部影响力初期数据差是正常的**——**关键是"有 1-2 个真信号"**（比如猎头联系）。

### 9.6 Y2 Q1-Q2：开源项目的意外收获

**契机**：糖果充写熔断代码时，把生产代码抽象成了一个小的开源库——**只是自用**。

**动作**：
1. **在 Github 开源了一个熔断工具库**（500 行代码）
2. **写了详细的 README + 一个 example**
3. **发到几个技术群**——**没敢期待**

**Q1 末**：**Star 30，Fork 5**——他很满意了。

**Q2 中**：**一个知名博主转发了这个项目**——**一个月内 Star 涨到 500**。**糖果充懵了**。

**Q2 末**：**Star 1200，2 位外部贡献者，被一家中型公司真实上线**。**Star 数 = 猎头轰炸的门票**——**Q2 内收到 15 个猎头**。

**教训**：**开源的爆发是随机的**——**你能做的是"持续产出高质量代码 + 好的 README"**。**运气会自己来找**。

### 9.7 Y2 Q3：第一次外部演讲

**契机**：一个技术 meetup 主办方看到他的开源项目，主动邀请他做 30 分钟分享。

**动作**：
1. **接受邀请**（虽然紧张——**从没在陌生人面前讲过**）
2. **准备 4 周**——**用了两次内部预演**
3. **现场 80 人到场**

**成果**：
- **现场反馈良好**（Q&A 12 个问题）
- **录像上传 B 站 6 个月观看 5000+**
- **两位听众后来成为工作合作伙伴**——**其中一位 3 年后引荐了糖果充到下家公司**

**教训**：**外部演讲的"长尾价值"远大于"现场价值"**——**录像 + 传播 + 人脉沉淀**都是复利。

### 9.8 Y2 Q4：写"系列文章"取代散文

**转折点**：糖果充读了一位技术大 V 的博客——**发现大 V 都在写"系列"**（比如"Kafka 系列 10 篇""Kubernetes 源码解读 20 篇"）。

**他的观察**：
- **散文式博客**：读者读一篇就走
- **系列博客**：读者读第一篇会**期待第二篇**——**关注**——**订阅**——**长期粉丝**

**动作**：**开启"熔断与降级系列 12 篇"**，每两周一篇。

**成果**（Q4 末，写了 4 篇）：
- **每篇阅读 5000+**（对比之前散文 500-1000）
- **微信公众号涨了 500 粉丝**（之前是零）
- **一个技术出版社约他"考虑出书吗"**（后来真的成书）

**教训**：**同样的时间**，**"系列"的复利效应是"散文"的 5-10 倍**。**因为系列自带"锚定"和"期待"**。

### 9.9 Y3 Q1-Q2：内部影响力的放大

**转折点**：糖果充的外部影响力开始"倒灌"到公司内部——**同事在外网看到他的博客**，**在公司里对他刮目相看**。

**动作**：
1. **主动申请了公司级技术分享**（不只是部门级）
2. **主导了一个跨 5 部门的技术委员会**（关于服务治理规范）
3. **开始在公司内部专栏"发榜首"**

**成果**：
- **全公司 5000 人有 30% 认识他的名字**
- **公司 CTO 在一次全员会上点名表扬**
- **P7 晋升答辩\"一次通过\"**

**教训**：**内外部影响力互相放大**——**外部数据是内部信任的加速器**。**同事看到你在外面被认可，会更愿意在内部相信你**。

### 9.10 Y3 Q3-Q4：从"知名"到"大使"

**契机**：公司市场部要做技术品牌宣传，需要"内部技术代言人"——**糖果充是首选**。

**动作**（Q3-Q4）：

**成果**：
- **公司市场部把糖果充作为"技术品牌 icon"**（半正式头衔"公司技术大使"）

## 十一、影响力反模式相册（深化版）

第 10 章的速查卡里给了 6 个反模式的表格版，这一节做**详细展开 + 真实案例**。

### 11.1 反模式一：刷数据式

**症状**：**用小号点赞、买阅读、Star 互刷**——**制造"虚假繁荣"**。

**真实案例**：糖果充见过一位同行，博客阅读全靠"技术互推群"互刷——**看起来阅读几万，但评论区从来没人真讨论内容**。**3 个月后被识破，业内笑话**。

**危害**：
- **一次翻车信誉归零**——**技术圈很小**
- **自我欺骗**——**你以为你在做影响力，其实在做手工艺**
- **反噬**：**当有人真读你的东西发现质量不匹配，落差感极大**

**修复**：**盯真实指标**——**评论质量、私信问题深度、转发是否带具体观点**。**这些才是影响力**。

### 11.2 反模式二：蹭热点式

**症状**：**追每一个新技术、每一个新框架发文**——**从 ChatGPT 到 Bun.js 到 WebLLM**。

**真实案例**：糖果充见过一位博主，2023 一年发了 80 篇文章——**每篇都追热点，每篇都浅**。**一年下来涨了 3k 粉——但没人记得他"精通什么"**。

**危害**：
- **没有沉淀**——**热点过去你就消失**
- **没有标签**——**别人搜"XX 领域的专家"想不到你**
- **陷入焦虑循环**——**每天都在追新的东西**

**修复**：**选定 1-2 个主领域，热点只在你的主领域里追**——**其他新东西自己学但不发文**。

### 11.3 反模式三：水会议式

**症状**：**什么 CFP 都投——大会/小会/线上/线下——只求"我讲过"**。

**真实案例**：糖果充有个前同事，一年讲了 15 场——**但每场分享内容 80% 重复**。**主办方之间会打听——"这个人不能再邀请了"**。

**危害**：
- **名字被记住的方式是"讲得一般"**——**比不讲还糟**
- **准备不足**——**每场都是重复+一点新内容**——**观众感觉被敷衍**
- **消耗人品**——**主办方之间会互相分享"黑名单"**

**修复**：**一年精讲 3-4 场**——**每场都要有 30% 以上的新内容**。**宁缺毋滥**。

### 11.4 反模式四：伪开源式

**症状**：**GitHub 一堆废弃项目**——**Readme 只写了标题、无 example、无 doc**。

**真实案例**：糖果充招人时看到简历上"开源项目 20+"，一看 GitHub——**19 个项目都是 6 个月没提交的死项目**。**打了负分**——**因为暴露了"喜欢开始不喜欢完成"的性格**。

**危害**：
- **潜在雇主查了失分**（**技术总监会去看你 GitHub**）
- **稀释真正好项目的曝光**——**5 个精品比 20 个半成品好**
- **暴露性格问题**——**"我喜欢新东西但没耐心"**

**修复**：**每 6 月清理一次废弃项目**——**归档或删除**。**在 pinned 里只留 3-5 个精品**。**质量远胜数量**。

### 11.5 反模式五：自嗨式

**症状**：**只讲技术、不见人**——**博客通篇代码，PPT 通篇架构图，从不讲"你的思考过程"**。

**真实案例**：糖果充见过一位技术大牛，代码功底极强——**但外部影响力永远做不起来**。**因为他的博客像"官方文档"**，**没有个人温度**。

**危害**：
- **传不出去**——**读者只关心"和我有什么关系"**
- **没有情感连接**——**读者记不住你**
- **同类内容太多**——**你被淹没**

**修复**：**每篇技术内容必须至少有一段"我"**——**你为什么关心这个问题、你踩了什么坑、你现在怎么看**。**技术之外的"人味"是差异化的核心**。

### 11.6 反模式六：挂靠式

**症状**：**天天转发大 V 内容**——**自己 0 原创**。

**真实案例**：糖果充见过某个博主，2 年转发了 5000 条大 V 微博——**自己写的原创不到 50 条**。**别人只当"XX 大 V 的粉丝团团长"**。

**危害**：
- **没有原创 = 没有影响力**——**你只是别人影响力的"扬声器"**
- **主动权在别人手里**——**大 V 不发你就没内容**
- **被识别为"跟风者"**——**很难被平等对待**

**修复**：**每转发一条大 V 内容 = 你至少要有 1 条自己的评论/思考**。**转发不写评论 = 无意义的动作**。

### 11.7 反模式七：过度暴露式

**症状**：**每天发朋友圈**——**技术+生活+情感全都发**——**信息过载**。

**真实案例**：糖果充见过一位工程师，每天发 5-8 条朋友圈——**同事都屏蔽了**。**他还以为"我在做个人品牌"**——**实际是"人人都嫌"**。

**危害**：
- **同事屏蔽**——**你以为传播，实则消音**
- **稀释专业形象**——**如果你既讲 K8s 又讲宝宝辅食，别人不知道你是什么专家**
- **过度消耗人际关系**

**修复**：**朋友圈"技术 : 生活 = 3 : 1"**——**技术为主，生活穿插**。**每天最多 1-2 条**。**留白 = 神秘感 = 期待感**。

### 11.8 反模式八：等风来式

**症状**：**"等我技术再强一点就写"**——**"等我做出大项目就分享"**。

**真实案例**：这就是 Y0 Q4 的糖果充自己——**"技术还不够"**。**如果他 3 年前就开始写，今天可能是全国知名而不只是公司知名**。

**危害**：
- **永远等不到"够强"的那一天**——**这是完美主义的陷阱**
- **错过复利期**——**影响力最大的收益来自"起步的头两年"**
- **失去先发优势**——**同龄人可能已经跑出去了**

**修复**：**从"你比 3 个月前的自己强"开始写**——**你 3 个月前不会的事今天会了，就有资格写给"3 个月前的自己"看**。**读者不需要你"世界顶级"——只需要你"比他早半步"**。

- **Day 8**：把最近一次技术决策写成 300 字总结，发团队频道

- **Day 27**：投一次线下 meetup 或线上直播
- **Day 28**：做一次影响力自检——**过去 30 天有人在你不在场提到你吗**
- **Day 29**：整理这个月的"作品集"——所有产出集中一页
- **Day 30**：写第二篇博客——**开启下个 30 天**

| **外部广度** | 0 外部 | 千级粉丝 | 万级粉丝 |
| **内容沉淀** | 0 篇博客 | 10-30 篇 | 系列/书 |

| **商业变现** | 0 | 偶尔咨询 | 稳定副业收入 |

**建议每半年重画一次**，**盯自己最低的一维在下半年做提升**。

### 14.2 内容矩阵（一年内容日历骨架）

### 14.3 影响力在晋升中的权重（大厂典型）

| 晋升档 | 技术能力 | 业务价值 | 影响力 | 组织协作 |
|:---:|:---:|:---:|:---:|:---:|
| **P5 → P6** | 40% | 30% | **10%** | 20% |
| **P6 → P7** | 30% | 30% | **20%** | 20% |
| **P7 → P8** | 20% | 30% | **30%** | 20% |
| **P8 → P9** | 15% | 25% | **40%** | 20% |
| **P9+** | 10% | 20% | **50%** | 20% |

**结论**：
- **P5-P6 阶段**：影响力只是加分项——**先把技术基本功打扎实**
- **P6-P7 阶段**：影响力开始成为**分水岭**
- **P7 以上**：影响力权重**超过技术能力本身**——**做不出\"名字被记住的成就\"就上不去**

**别再问\"要不要做影响力\"——问\"我在哪个阶段、要做到什么程度\"**。
