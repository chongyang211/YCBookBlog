# 技术写作之道指南

> 文档结构设计、技术博客、方案撰写套路——写清楚比写得多重要

## 一、技术写作不是"写作文"，是"降低理解成本"

大多数工程师写文档时的心态：

```text
"我懂了就行，随便写写。反正没人看。"
```

然后你的设计文档被后来的同事打开，读了 10 分钟还是不知道你在说什么——他只能跑来打断你，问 20 分钟。你为了省 20 分钟写文档的时间，未来要花 200 分钟回答问题。

技术写作的核心目标就一个：**让读者用最短时间理解你想表达的东西。**

```text
❌ 写给自己看的 → 只有你自己能看懂，3 个月后你自己也看不懂
✅ 写给读者看的 → 任何有基本上下文的人都能看懂，不需要追问
```

---

## 二、技术文档的结构——两个铁律

### 2.1 TL;DR 前置

TL;DR（Too Long; Didn't Read）不是给懒人看的——是给**需要你的文档但不需要全部细节**的人看的。

```text
技术方案文档的标准结构：

# 标题
> TL;DR：用 3 句话说明——要做什么、为什么现在做、核心方案是什么

## 1. 背景与问题        ← 不关心的人看完 TL;DR 就不用往下翻了
## 2. 方案对比
## 3. 详细设计
## 4. 风险与应对
## 5. 排期与分工
```

**TL;DR 公式**：

```text
[做什么]，以解决 [什么问题]。
核心方案是 [一句话描述]，预计 [完成时间]。
关键决策：[最重要的技术选型/取舍]。
```

### 2.2 先说结论，再说过程

程序员最容易犯的写作错误：**按时间顺序写，而不是按重要程度写。**

```text
❌ 按你的思考过程写：
"我们最开始想用 Redis 做缓存，但是发现内存不够，然后调研了 Memcached，
发现也不合适，后来看到一篇博客说可以用本地缓存 + 分布式锁……"
→ 读者在这段废话里找你到底用了什么方案。

✅ 按重要性写：
"最终方案：Caffeine 本地缓存 + Redis 分布式锁。
为什么不用纯 Redis：内存成本估算每月 ¥8000，不可接受。
备选方案对比表见下文。"
→ 读者第一句就知道结论了。
```

**原则**：任何段落的第一句话都应该能独立回答"这一段在说什么"。如果读者只读每段第一句，他应该能理解文档的 80%。

## 三、技术博客——你为什么要写

### 3.1 博客不是工作汇报

```text
❌ "我们项目这周做了 A、B、C 三个功能。" ← 没人关心你的项目周报
✅ "做 A 功能时遇到一个死锁问题，排查过程是这样的……" ← 别人能学到东西
```

博客的读者不是你同事——他们不知道你的项目背景。你要给你的文章一个**独立存在的意义**：读者读完能带走什么？

三种有传播力的技术博客：

| 类型 | 例子 | 适合写的人 |
|---|---|---|
| **踩坑记录** | "MySQL 8.0 升级后 time_zone 表导致连接失败的排查" | 所有人 |
| **原理深挖** | "从 epoll 到 io_uring——Linux IO 模型的演进" | 对底层感兴趣的人 |
| **对比评测** | "React Query vs SWR vs RTK Query——数据请求库选型" | 做过技术选型的人 |

### 3.2 博客结构公式：STAR + Insight

```text
S - Situation（背景）：我在什么项目/场景下遇到这个问题
T - Task（问题）：具体是什么问题，现象是什么
A - Action（过程）：怎么排查的，试过哪些方案
R - Result（结果）：最终怎么解决的，效果怎样
+ Insight（洞察）：做完之后有什么收获，能不能抽象成通用规律
```

**STAR 让文章有骨架，Insight 让文章有价值。** 没有 Insight 的踩坑记录就是流水账。

### 3.3 代码是最费读者的东西——省着用

```text
❌ 贴一整段 50 行的代码，然后写："核心逻辑如上。"
→ 读者不知道重点在哪行。

✅ 贴 5-8 行关键代码，用注释标注关键行：
```java
// 关键：这里用了 CompletableFuture 的 thenCombine，
// 将两个独立的远程调用并行化，总耗时从 A+B 降到 max(A, B)
CompletableFuture<User> userFuture = userService.getUserAsync(userId);
CompletableFuture<Order> orderFuture = orderService.getOrderAsync(orderId);
userFuture.thenCombine(orderFuture, (user, order) -> {
    return new UserOrderResult(user, order);
});
```
```

代码片段旁边必须有注释解释**为什么这么写**——代码本身只能说明"怎么做的"，不能说明"为什么这么做"。

## 四、技术方案——让评审人快速说"同意"

### 4.1 方案评审的本质是"消除担心"

评审人看你的方案，不是在找亮点——是在找风险。你越快让他确认"没有坑"，他越快说同意。

一份好方案应该主动回答评审人脑子里的四个问题：

```text
问题 1：为什么要做？（有没有数据？还是拍脑袋？）
  → 回答：一张图/一个链接/一句引用。不要"我觉得"。

问题 2：为什么选这个方案？（对比过其他方案吗？）
  → 回答：一个对比表。3 列：方案名、优点、为什么不选。

问题 3：影响有多大？（下游谁会被影响到？）
  → 回答：一句话 + 一个影响清单。如果只改你自己的服务，直接说明。

问题 4：失败了怎么办？（有回滚方案吗？）
  → 回答：回滚步骤（能一行命令就别写一段话）+ 监控验证方法。
```

### 4.2 方案对比表——用一分钟取代一小时讨论

```text
| 维度 | 方案 A：MQ 异步 | 方案 B：线程池 | 方案 C：不处理 |
|---|---|---|---|
| 可靠性 | 高（消息持久化） | 中（重启丢失） | N/A |
| 延迟 | +50ms（网络开销） | +5ms | 0 |
| 复杂度 | 引入新组件 | 纯代码 | 无 |
| 开发成本 | 2 天 | 0.5 天 | 0 |
| **结论** | **推荐** | 备选 | 不可接受 |

理由：当前 QPS 不高，但后续计划上大促，MQ 的削峰能力未来会需要。
一次性引入，避免 3 个月后再重构。
```

这个表把"我推荐方案 A"变成了客观结果——评审人不用听你解释，自己看表就能判断。

### 4.3 灰度发布计划——这是评审人最想看到的

任何有风险的技术变更，如果你在方案里主动写了灰度计划，评审通过率大幅提升：

```text
灰度三步走：
Step 1：单机灰度（1 台机器，观察 1 小时）→ 监控：错误率、P99 延迟
Step 2：10% 流量（观察 1 天）→ 监控：同上 + 业务指标
Step 3：全量发布
回滚条件：Step 1/2 任意阶段错误率 > 基线 × 2，立刻回滚
回滚方式：切回 feature flag / 重新部署上一版本（预计 5 分钟）
```

**灰度计划的价值不只是安全——是让评审人感受到"你想过失败了怎么办"。**

## 五、常见技术文档的极简模板

### 5.1 Bug 报告

```text
## 现象
[一句话描述：用户在什么操作下看到了什么]

## 复现步骤
1. [步骤1]
2. [步骤2]
3. [看到的不符合预期的结果]

## 预期行为
[应该是什么样的]

## 环境
App版本: v2.3.1 / 设备: iPhone 14 iOS 18 / 网络: WiFi

## 日志/截图
[贴关键错误日志，不要贴全部]
```

### 5.2 接口文档（给调用方看）

```text
## POST /api/order/cancel

取消一个待支付的订单。

### 请求
| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| order_id | string | 是 | 订单ID |
| reason | string | 否 | 取消原因，最长 200 字 |

### 响应
```json
{ "code": 0, "message": "success" }
```

### 错误码
| code | 说明 |
|---|---|
| 1001 | 订单不存在 |
| 1002 | 订单已发货，不可取消 |
| 1003 | 重复取消 |

### 调用示例
```bash
curl -X POST https://api.example.com/order/cancel \
  -H "Authorization: Bearer xxx" \
  -d '{"order_id": "12345", "reason": "不想要了"}'
```
```

### 5.3 Oncall 记录

```text
## [告警] 支付回调处理延迟 > 3s
时间：2024-01-15 14:30 - 14:55
影响：约 200 个订单的回调处理延迟，用户收到支付成功通知晚了 5-15 分钟

### 根因
第三方支付回调的签名验证逻辑中，公钥获取接口超时（上游 CA 服务故障）

### 临时修复
降级方案：使用本地缓存的公钥（有效期 24h），跳过实时获取

### 长期修复
□ 公钥获取加入本地缓存 + 被动刷新机制
□ 回调处理增加异步化，签名验证失败不影响通知下发
```

## 六、长案例：糖果充的方案被打回 7 次

这是一个真实故事。糖果充 P5 转 P6 的关键一年，写了他人生第一份"跨部门技术方案"——**订单系统降级方案**。从初稿到最终评审通过，前后 3 周，被打回 7 次。这 7 次评审意见，几乎覆盖了工程师写作的所有典型问题。

### 6.1 背景

- **业务**：电商大促前，订单系统需要一份"极端流量下的降级方案"
- **协作方**：产品、SRE、支付、履约、客服五个团队
- **评审人**：直属 TL、部门架构师、SRE Team Lead
- **糖果充的自我认知**：技术方案我熟啊——不就是写清楚怎么改吗？

**结果**：他花了 2 天写了 18 页 PPT-style 文档，标题叫《订单系统降级技术方案 v0.1》，兴致勃勃发了评审邀请。**当天晚上就收到 TL 的第一条评论：**"这份文档我读不下去，明早聊。"

### 6.2 第一次打回：读者是谁

**TL 的批注**（凌晨 1:17）：

> "第一页写了'背景介绍'，我读了 3 分钟不知道你到底要干什么。这份文档 5 个团队要看——你想让他们各自带走什么？架构师看设计、SRE 看止损、产品看降级用户感知、支付看金额一致性、客服看话术。**你的第一页应该有一张\"读者向导\"**，让不同人跳到自己该看的段落。"

**修改前**（原第一页）：
```
背景介绍
━━━━━━━━━━━━
本次大促预计流量 3× 日常，订单系统面临巨大压力。
为保障核心链路稳定，特制定本降级方案……（后续 500 字都是背景铺垫）
```

**修改后**：
```
TL;DR
━━━━━━━━━━━━
问题：大促 3× 流量下订单系统可能雪崩
方案：三级降级（限流 → 异步化 → 只读兜底）
代价：极端情况下 5% 用户下单延迟 30s，无数据丢失
决策点：需要产品确认降级文案，SRE 确认止损阈值

读者向导：
- 架构师：跳到 §3 详细设计
- SRE：跳到 §5 止损与回滚
- 产品：跳到 §4 用户感知
- 支付：跳到 §6 金额一致性
- 客服：跳到 §7 客诉话术
```

**教训一**：**技术方案的第一页不是给你自己的记录本——是给读者的地图。**

### 6.3 第二次打回：为什么不是别的方案

**架构师的批注**：

> "你说要用限流，但你没写为什么不用扩容/为什么不用队列/为什么不用降级中间件。**没有对比的方案不是方案，是一厢情愿。**"

糖果充这才意识到——他跳过了"候选方案对比"。他补了一张表：

| 候选方案 | 成本 | 可控性 | 用户感知 | 决策 |
|---|:---:|:---:|:---:|:---:|
| 临时扩容 3× | 高（¥ 80w） | 中 | 无 | 否（成本超预算） |
| 加消息队列 | 中 | 高 | 有延迟 | 否（改造窗口不够） |
| 三级降级 | 低 | 高 | 部分延迟 | **✓ 选用** |
| 熔断中间件 | 中 | 低 | 硬失败 | 否（用户流失） |

**教训二**：**你选的方案必须是"击败了其他方案"才有说服力——不是"我想到了这个"。**

### 6.4 第三次打回：数据在哪里

**SRE Lead 的批注**：

> "你写'限流到 5000 QPS'——为什么是 5000 不是 3000 或 8000？**数字必须有出处**。"

糖果充回去翻了监控，加了一段：

```
QPS 阈值推导：
- 日常峰值：约 1200 QPS
- 单机压测极限：约 800 QPS（p99 < 200ms）
- 大促目标：3× 日常 = 3600 QPS
- 集群 8 台，冗余按 30% 计：8 × 800 × 70% ≈ 4480 QPS
- 向上取整并留 10% 缓冲：**5000 QPS**
```

**教训三**：**每一个关键数字都要能倒推出来。写"5000"和写"5000（推导见 §附录 A）"是天壤之别。**

### 6.5 第四次打回：风险不是列表，是场景

**TL 的第二次批注**：

> "你的\"风险\"章节列了 8 条，全是\"XX 可能出问题\"。**这不是风险分析——这是免责声明。**每一条风险要回答：什么条件下发生？影响面多大？我怎么止损？"

修改前：
```
风险：
- 限流可能误杀正常用户
- 异步化可能导致数据不一致
- 兜底方案可能被绕过
```

修改后（节选）：
```
风险 R1：限流误杀正常用户
- 触发条件：用户短时间多次点击\"提交订单\"
- 影响：预估 <0.3% 用户看到\"稍后再试\"
- 止损：用户侧展示友好文案 + 15 秒后自动重试
- 监控：观察 429 状态码占比，>1% 触发人工介入
- 回滚：熔断标记位 downgrade_enabled 秒级关闭
```

**教训四**：**风险 = 触发条件 + 影响 + 止损 + 监控 + 回滚，五要素缺一不可。**

### 6.6 第五次打回：谁做什么

**产品同学的批注**：

> "看完了，我还是不知道我需要做什么。什么时候做？给谁做？做完给谁验收？"

糖果充这才把"排期与分工"从半页扩到一页：

| 时间 | 负责人 | 任务 | 验收人 | 交付物 |
|---|---|---|---|---|
| T-14 | 糖果充 | 限流中间件接入 | 架构师 | 联调通过截图 |
| T-10 | 张同学（产品）| 降级文案定稿 | 客服 | 文案 doc |
| T-7  | SRE 王工 | 演练脚本 + 演练 | TL | 演练报告 |
| T-3  | 支付李姐 | 一致性回补脚本 | 支付 TL | 脚本 + 演练 |
| T-1  | 全体 | 最终 review | TL + 架构师 | Go/No-Go 决策 |
| T+7  | 糖果充 | 复盘文档 | 全体 | 复盘 doc |

**教训五**：**"排期"没有负责人和验收人 = 没有排期。**

### 6.7 第六次打回：缩短一半

**架构师的批注**（读到 v0.6）：

> "现在信息完整了，但太长了——**从 18 页压到 10 页**。评审人的注意力是有限资源。"

糖果充做了三件事：
- 把 4 页的"技术背景介绍"压到半页 TL;DR
- 把详细代码从正文移到附录（附录可以长，正文必须短）
- 把重复出现的架构图合并为一张总图 + 三张局部图

**教训六**：**好方案的第二稿一定比第一稿短。厚不代表深——厚代表你没想清楚哪些可以砍。**

### 6.8 第七次打回：一次性可读

**TL 的最终批注**：

> "让我们的实习生（完全不懂订单系统）读一遍——他看完前两页能否复述你的方案？"

实习生读完两页后，糖果充问他："这个方案在做什么？"

实习生答：**"好像是……减压？限流？我不太确定。"**

糖果充意识到——他的 TL;DR 里堆了太多术语（"限流""异步化""只读兜底"），非该领域的人根本读不懂。他改成了大白话：

```
一句话：大促期间，如果订单系统压力超过承受能力，
我们会有序地让一部分用户\"稍等一下\"，
而不是让所有人\"打不开页面\"。

三句话：
1. 用限流拦住突发的洪水（保护后端）
2. 把非核心的动作推迟（保住主流程）
3. 万一还是撑不住，就切到\"只读\"模式让用户能查订单
   但暂停下单（保数据安全）
```

**教训七（最关键）**：**一份好的技术方案，非技术人也能读懂前两页——如果读不懂，说明你没真正想清楚。**

### 6.9 复盘：7 次打回对应的 7 条黄金律

| # | 批注核心 | 一句话原则 |
|:---:|---|---|
| 1 | 读者是谁 | 首页必须有读者向导 |
| 2 | 为什么是这个方案 | 无对比不方案 |
| 3 | 数字从哪来 | 关键数字必须能倒推 |
| 4 | 风险是什么 | 风险 = 触发+影响+止损+监控+回滚 |
| 5 | 谁做什么 | 排期必须有负责人和验收人 |
| 6 | 太长了 | 好方案的第二稿一定更短 |
| 7 | 一次可读 | 前两页非技术人也要能懂 |

**这 7 条不是"糖果充的教训"——是所有工程师写第一份大方案都会踩的坑。**你现在拿到这份清单，可以少踩 7 次坑。


## 七、常见写作反模式（相册）

### 7.1 反模式一：把方案写成流水账

**症状**：按时间顺序写——"首先我调研了 X，发现不行→然后试了 Y，也有问题→最后决定用 Z"。

**危害**：评审人被迫跟着你的思考过程走，读完第三页才知道结论。实际评审中没人读完——他们直接跳到最后一页。

**修复**：结论先行的本质是**把时间顺序改为重要程度顺序**。最重要的事（结论）放在第一段。

### 7.2 反模式二：技术博客变成工作汇报

**症状**：标题"XX 系统优化实践"，内容="我们把 A 换成 B，性能提升了 30%"。

**危害**：读者不关心你的系统叫什么——他们关心"我也遇到同样的问题，我能怎么解决"。

**修复**：标题改成"降低 30% 数据库查询的三种方法"，读者一眼就知道和他有关。

### 7.3 反模式三：过度解释

**症状**：一个接口文档写了 5 页背景介绍，调用方式只有半页。

**危害**：读者需要的信息被埋在背景噪音里。他最需要的是：怎么调、参数是什么、返回什么。

**修复**：把所有文档想象成电梯——每多写一行，就多一个读者从电梯里走出去。

### 7.4 反模式四：总结里出现新论点

**症状**：小结章节突然冒出正文没提过的观点或数据。

**危害**：读者会怀疑"是不是我漏读了"，或者更糟——**觉得你逻辑不严谨**。

**修复**：小结只做两件事：**收拢正文的关键结论 + 给出下一步动作**。任何"新观点"要么提到正文，要么删掉。

### 7.5 反模式五：图表和正文各说各话

**症状**：正文说"性能提升了 30%"，图里画的是"延迟从 200ms 降到 140ms"（其实是 30%，但读者要自己算）。

**危害**：**每一次算数就是一次流失读者的机会**。

**修复**：图 = 一句话结论 + 一个证据点。图题写成完整句子（"改造后 p99 从 200ms → 140ms，降幅 30%"），不要写"图 3-1 性能曲线"这种废标题。

### 7.6 反模式六：把设计过程当成结论

**症状**：花了 5 页写"我们讨论了 A、B、C 三种方案"——最后没说选哪个。

**危害**：评审人不是来当法官的——他要的是"你的建议是什么"。

**修复**：**方案对比表里必须有一列叫"决策"**，用 ✓ 明确标出选择。理由紧跟在表下面，一段话说清。

### 7.7 反模式七：伪装成技术的甩锅

**症状**：事故复盘写"由于第三方接口不稳定导致……"——通篇找外因。

**危害**：**读者读完一头雾水**——那我们下次能改进什么？

**修复**：复盘必须至少有一条"**我们自己**能做的改进"（哪怕是"下次先做熔断"这样的小事）。**没有 self-action 的复盘不叫复盘，叫报告。**

### 7.8 反模式八：显然、众所周知、简单地

**症状**：文档里高频出现"显然""众所周知""简单地"。

**危害**：这些词是**知识诅咒**的标志——**对你显然，对读者不显然**。而且带有轻蔑意味。

**修复**：全文搜索这三个词，逐一改写成具体解释。**如果真的显然，就删掉这句话；如果需要解释，就好好解释。**


## 八、文档评审——让文档质量持续在线

### 8.1 为什么需要文档评审

代码有 Code Review，文档却经常"写完就发、没人看过"。一份没人审过的文档和一个没人审过的 PR 一样危险——错误的信息比没信息更糟糕。

### 8.2 文档评审的轻量流程

| 步骤 | 谁 | 做什么 | 耗时 |
|---|---|---|---|
| ① 作者自检 | 你 | 按本文的 TL;DR 和三原则自检 | 5 min |
| ② 找一人预读 | 同事 | "假装你是完全不懂的新人，能看懂前两段就通过" | 5 min |
| ③ 对标模板 | 你 | 检查你是否遗漏了模板里的必填项 | 2 min |
| ④ 发布+通知 | 你 | 发到频道并 @ 最可能需要这文档的人 | 1 min |


## 九、写作速查卡

一张 A4 打印贴在显示器旁，写不下去时抬头看一眼。

### 8.1 结构速查

| 文档类型 | 首段公式 | 核心章节 | 收尾必备 |
|---|---|---|---|
| 技术方案 | TL;DR: 问题+方案+代价 | 背景/目标/方案/对比/风险/计划 | 灰度与回滚 |
| 事故复盘 | 一句话结论+损失 | 时间线/根因/复盘/改进 | 可验证的 Action |
| 技术博客 | 场景钩子+我踩了什么坑 | Situation/Task/Action/Result | 一句话总结+扩展阅读 |
| 周报月报 | 本周关键成果 3 句 | 进展/风险/下周计划 | 需要老板决策的一件事 |
| PR/Commit | 动词+对象+影响面 | 改动点/测试/兼容性 | 关联 issue |

### 8.2 三条黄金问句

写完之前问自己：

1. **读者读第一段就走**——他能带走什么？
2. **读者读到一半**——他还愿意继续读吗？
3. **读者读完**——他知道下一步该干什么吗？

三个都答得上，再点发布。

### 8.3 十项质检表

```text
□ 标题一眼看出主题（不是"关于XX的一些思考"）
□ 首段 5 句话内说清"是什么/为什么/怎么办"
□ 二级标题连起来能独立成大纲
□ 每张图表都有说明文字，且被正文引用
□ 方案至少有 2 个候选并给出对比
□ 有"风险与不做什么"章节
□ 代码块不超过 30 行，多的放附录
□ 没有"显然/众所周知/简单地"这类词
□ 关键结论前后不矛盾
□ 存在可执行的 Next Step 或验收标准
```

十项过 8 项及格，过 10 项优秀。


## 十、小结

技术写作的核心能力不是文笔——是**换位思考**。每次写完问自己：如果我是读者，我能用最快的速度找到我要的信息吗？

```text
写作三原则：

1. 结论先行   → 读者不需要跟着你的思考过程走一遍
2. 对比择优   → 你的方案为什么好？是什么逻辑推理——是对比出来的
3. 处处为读者省时间 → TL;DR、表格、代码注释、灰度计划——每多一处少问一个问题
```

**行动清单**：

- [ ] 下一次写方案文档，先用 TL;DR 公式写第一段
- [ ] wiki/知识库里找一个旧文档，按"结论先行"原则改一遍
- [ ] 今天踩了一个坑？花 30 分钟写一个 STAR 格式的博客初稿
- [ ] 下一次写完文档，找一位同事花 5 分钟预读——你的文档第一次被别人读会发现很多"你以为清楚了但实际没有"的地方


## 十一、30 天写作练习

不必按天卡死，允许挪动，但**每周至少完成 5 天**。

### 第 1 周 · 结构训练（每天 15-30 分钟）

- **Day 1**：找出你最近写的一份最长的文档，用 TL;DR 公式重写首段
- **Day 2**：把该文档的所有二级标题抄出来，检查是否连起来能独立成大纲
- **Day 3**：给该文档补一个"风险与不做什么"章节
- **Day 4**：给该文档补一个方案对比表（至少 2 个候选）
- **Day 5**：用《8.3 十项质检表》给自己打分并逐条修正
- **Day 6**：找一位同事花 5 分钟预读，收集 3 条改进意见
- **Day 7**：休息，或读一份公司内你觉得写得好的文档，抄它的结构

### 第 2 周 · 复盘写作（每天 20-40 分钟）

- **Day 8-9**：挑一次最近的事故/踩坑，写事故时间线（精确到分钟）
- **Day 10-11**：把时间线转成"5 Whys"追问，找到根因
- **Day 12**：写"改进 Action"，每一条必须包含"负责人+截止日+验证方式"
- **Day 13**：把整个复盘按事故复盘模板整合
- **Day 14**：在组内做一次 10 分钟复盘分享

### 第 3 周 · 技术博客（每天 30-60 分钟）

- **Day 15**：列出最近半年你解决过的 3 个"起初以为简单结果不简单"的问题
- **Day 16**：选定其中 1 个，按 STAR 结构写 Situation
- **Day 17**：写 Task 和 Action（**过程比结果值钱**）
- **Day 18**：写 Result 和一句话总结
- **Day 19**：加代码块、图、扩展阅读
- **Day 20**：改标题——用"场景钩子+我踩了什么坑"公式
- **Day 21**：发布到内网或个人博客

### 第 4 周 · 方案文档（每天 30-60 分钟）

- **Day 22**：挑一个近期要做的技术项目
- **Day 23**：写背景/目标/非目标（**非目标是防边界扩大的锚**）
- **Day 24**：写至少 2 个候选方案 + 对比表
- **Day 25**：写风险与回滚
- **Day 26**：写灰度计划与验收标准
- **Day 27**：加 TL;DR
- **Day 28**：约 1-2 位同事 review，用《7. 文档评审》流程走一遍
- **Day 29**：根据评审意见修改
- **Day 30**：发布，同时把这份文档存进你的"作品集"

### 交付物清单

30 天后你应该有：

- ✅ 一份被同事称赞"结构清晰"的旧文档改写版
- ✅ 一份可作为团队复盘模板的事故复盘
- ✅ 一篇能拿去投稿的技术博客
- ✅ 一份评审通过的技术方案

**这四份就是你写作能力的 offer 附件。**
