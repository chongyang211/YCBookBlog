# 10.综合案例订单锻造厂（OrderForge）

本篇是「常见设计原则」专栏的**毕业设计案例**：**从 0 亲手写一个"能跑的烂订单系统"**——一个六职责的上帝类、12 处坏味道、3 个真实 bug；然后**用六大原则做六次手术**，每治一种病做一次验收；最后**用度量报告证明"治好了"**（圈复杂度 14 → 2，坏味道 4 → 0，加新需求从"改中心代码"变成"加一个文件"）。

> 配套代码：`code/Programming/OrderForge`（纯 JDK 17，无 Maven，一键 `./build.sh && ./run.sh v0..v4|metrics|report|test-all`）。
>
> 代号 **OrderForge（订单锻造厂）**：V0 是生铁，每一次手术是一次锻打，终局是锻件。

**学习方式**：本案例 16-18 小时，分 **7 次会话**，每次独立可验收。**绝不要一口气做完**——每次手术只治一种病，跳读会漏掉"为什么要这么改"的因果链。如果说前 8 篇是"过单元考试"，本篇就是"毕业答辩"：它检验你能不能把 SRP / OCP / LSP / ISP / DIP / LOD / 重构度量**协同**起来，而不只是背得出六句口诀。

## 📚 渐进学习节奏

先读这段，再开始敲代码！本案例 16 个章节，**严格按"7 次会话"切分**，每次会话独立可验收。

🎯 **每次会话开始前必读**：

> 1. **打开上一版的代码**，先跑一遍 `./run.sh v?` 确认验收点还在；
> 2. **每个 Step 写完一小段就编译运行**（`./build.sh` 只要几秒）；
> 3. **看到该节末尾的 ✅ 验收命令出现预期输出，再进入下一节**。

⚠️ **本案例独有的"先写烂、再治好"策略**：会话 1 你会**亲手写出**一个上帝类并埋下 3 个真实 bug——这不是练习题的错误示范，而是**02 篇"详情页上帝类诞生记"的亲身体验版**。每一周的需求单看都合理，叠起来成灾难；不亲手走一遍这条心路，你不会对"类边界"产生敬畏。会话 2 先给病拍 X 光片（度量），会话 3-6 才动手术，会话 7 用数字证明疗效。

⚠️ **本案例的三处"造 BUG → 修复"高峰**（亲手埋、亲眼见、亲手治）：

> - **会话 1**：亲手写出 3 个 bug——多收 125 元（顺序错误）/ 库存凭空消失（失败无补偿）/ 已扣款通知 NPE（穿透 + 空值）；
> - **会话 5**：故意保留一个 LSP 违约标本（`BrokenCreditCardPayment`），契约测试当场抓获"契约外异常 + 前置加强"双连违反；
> - **会话 6**：四层火车残骸 + 空地址，游客订单支付成功后通知崩溃——07 篇"31 个文件事故"的微缩版。
>
> 三次"踩坑→修复"，让你真正记住**SRP / LSP / LOD 各自在防什么**——不亲眼看 bug 炸一次，原则就只是口诀。

### 为什么是订单履约闭环：选型记

设计综合案例时评估过四个候选，这里浓缩记录选型过程（也是 08 篇"合适优于先进"的一次实践）：

| 评估维度 | **A 履约闭环** ✅ | B 折扣引擎 | C 详情页 | D 后台多角色 |
|---|---|---|---|---|
| SRP 现场强度 | ★★★★★ 上帝类六职责 | ★★★★ | ★★★★★ | ★★★ |
| OCP 现场强度 | ★★★★ 促销史 | ★★★★★ | ★★★ | ★★ |
| LSP 现场强度 | ★★★★★ 支付限额 | ★★ 硬造 | ★★★★ | ★★ |
| ISP 现场强度 | ★★★★★ 胖订单接口 | ★★ 硬造 | ★★★★ | ★★★★★ |
| DIP 现场强度 | ★★★★★ 通知+仓储换实现 | ★★★ | ★★★★ | ★★★ |
| LOD 现场强度 | ★★★★★ 火车残骸+门面 | ★ 几乎无处安放 | ★★★ | ★★★★ |
| 08 篇度量贯穿 | ★★★★★ 全程+终局报告 | ★★★★ | ★★★★ | ★★★ |
| 从 0 到 1 顺滑度 | ★★★★★ 先造屎山再治 | ★★★★★ | ★★★（控制台模拟 UI 别扭） | ★★★ |
| 专栏案例回收率 | **6/8 篇** | 2/8 | 5/8 | 2/8 |
| **结论** | **胜出** | ❌ 与 PayFlow 撞车 | ❌ 仿真度差 | ❌ 三原则偏弱 |

三条决定性理由：

1. **专栏自己"长出"了订单案例**：9 篇里有 6 篇的工作案例本来就是订单域——促销 if-else V1→V5（03）、`CreditCardPayment` 支付限额（04）、`UserOperations` 胖接口（05）、消息三通道（06）、`order.getUser().getAddress().getCity()` 火车残骸（07）、`calcPrice` 圈复杂度 8（08）。综合案例的使命是把这些半成品**接回一个工程**，而不是硬凑覆盖；
2. **六原则全部天然**：没有任何一条需要"造场景"，每条原则都有"不做手术就疼"的现场；
3. **"从 0 到 1 写烂再治好"的叙事独一无二**：先亲手造屎山（理解它怎么长出来的）、再亲手度量（22 坏味道 + 圈复杂度）、再六次手术、最后用报告证明治好——这是 08 篇"tab 4 改 5 花 4 天"的教学放大版。

B/C/D 的可取素材已吸收进对应会话：C 的链式调用素材并入 LOD 会话，D 的买家/客服/运营三角色并入 ISP 会话。

### 与 PayFlow 案例的差异化声明

同一工作区已有《01.面向对象设计》专栏的 PayFlow（订单**结算**引擎）。两个订单案例并存时的分工：

| 维度 | PayFlow（01 专栏） | OrderForge（本案例） |
|---|---|---|
| 订单切片 | **结算**：九层优惠规则叠加计算 | **履约**：下单→库存→支付→通知→对账闭环 |
| 主轴 | 封装/多态/组合/装饰器 → SPI → DDD 领域事件 | **六大原则逐条手术 + 重构度量方法论** |
| 起点 | V0 事故代码"原景重现"（给定代码） | **从 0 亲手写出** V0（每步都是学习者敲的） |
| 驱动方式 | 版本演化叙事 | **度量驱动**（圈复杂度/坏味道数/改动半径） |
| 终局产物 | DDD：聚合根 + 领域事件 + 4 订阅方 | **重构评估报告**：前后度量对比 + 三改实验 |
| 折扣桥段 | 做到九层 SPI 编排 | **刻意做浅**（一层策略链即止，见 §13.3） |

> 一句话：**PayFlow 教你"把新系统设计好"，OrderForge 教你"把烂系统治好并证明治好了"**——工作中后者占 80%。

### 灵魂三问：开工准备

❓ **为什么金额用 `long cents` 而不是 `double`？**

试算 `0.1 + 0.2`——结果是 `0.30000000000000004`。订单系统里 1 分钱的误差乘以千万订单就是事故。以"分"为单位存 `long`，整数运算从根上消灭浮点误差；再把"钱"包成类型（`Money`），它就携带了业务语义——`percentOff(10)` 读出来就是"打 9 折"，而不是一行需要注释解释的 `* 0.9`。

❓ **不用 JUnit 自己写 testkit，不是重复造轮子吗？**

三个理由：① 零依赖，注意力全在原则上，不在工程配置上；② **`Assert.throwsException` 本身就是教材**——"守卫的最好测试是看它拒绝什么"，写一遍胜过用百遍；③ API 对齐 JUnit 风格（`Assert.equals` / `TestRunner.test`），以后切到真 JUnit 零成本。

❓ **domain 包为什么单独建、而不塞进 v0god？**

因为**领域模型是跨版本共享的**——V0 用它埋 bug，V1~V4 用它做手术。`Order` 上有一个方法值得提前留意：`getShippingCityName()`（注释标着"V4 LOD 手术新增"）——它在会话 6 才被真正用起来，V0/V1 用的都是火车残骸写法。**同一个模型、两种访问姿势的对照，正是 LOD 会话的活教材**。

### Step 0.1 Money 值对象

> 📁 **归属文件**：`src/com/yc/orderforge/shared/Money.java`

```java
public final class Money {
    public static final Money ZERO = new Money(0);

    private final long cents;                          // 以"分"为最小单位

    private Money(long cents) { this.cents = cents; }

    public static Money ofYuan(double yuan) { return new Money(Math.round(yuan * 100)); }
    public static Money ofCents(long cents) { return new Money(cents); }

    public Money plus(Money o)  { return new Money(cents + o.cents); }
    public Money minus(Money o) { return new Money(cents - o.cents); }
    public Money multiply(double f) { return new Money(Math.round(cents * f)); }

    /** 按比例打折。percentOff(10) 表示打 9 折。 */
    public Money percentOff(double percent) { return multiply(1.0 - percent / 100.0); }

    /** 取较小者。用途：优惠券抵扣兜底（券面值即上限）。 */
    public Money min(Money o) { return cents <= o.cents ? this : o; }

    public boolean isPositive()            { return cents > 0; }
    public boolean isNegative()            { return cents < 0; }
    public boolean greaterThan(Money o)    { return cents > o.cents; }
    public boolean greaterOrEqual(Money o) { return cents >= o.cents; }

    public long cents()    { return cents; }
    public double toYuan() { return cents / 100.0; }

    @Override public boolean equals(Object o) {
        return o instanceof Money && ((Money) o).cents == cents;   // 相等基于内容
    }
    @Override public String toString() { return String.format("¥%.2f", cents / 100.0); }
}
```

**四个设计要点**：

1. **`private` 构造器 + 两个语义工厂**：`Money.ofYuan(99.9)` 一眼可知单位是元；如果只有 `new Money(9990)`，鬼知道 9990 是分还是元。**构造器只能表达类型，工厂能表达语义**；
2. **不可变**：`final class` + `final` 字段 + 无 setter，所有运算返回新对象——多线程随便共享；
3. **`min` 是业务方法**：V2 的 `CouponDiscount` 靠它一行实现"券不能把单抵成负数"；
4. **`isNegative` 会话 4 才用上**（策略兜底），先备好。

> ⚠️ **易错点**：`multiply` 里必须 `Math.round`——`9990 × 0.9 = 8991.0` 精确，但 `3990 × 0.85 = 3391.5` 不进位就会丢半分钱。

### Step 0.2 testkit 三件套

> 📁 **归属文件**：`src/com/yc/orderforge/shared/testkit/`

**① Executable——测试体**（函数式接口，3 行）：

```java
@FunctionalInterface
public interface Executable {
    void execute() throws Throwable;
}
```

**② Assert——4 种断言**（重点看 `throwsException`）：

```java
public final class Assert {
    private Assert() {}

    public static void equals(Object expected, Object actual, String hint) {
        if (!Objects.equals(expected, actual)) {
            throw new AssertionError(
                "断言失败：" + hint + " | 期望=" + expected + " | 实际=" + actual);
        }
    }

    public static void trueThat(boolean condition, String hint) {
        if (!condition) throw new AssertionError("断言失败：" + hint);
    }

    public static void falseThat(boolean condition, String hint) {
        if (condition) throw new AssertionError("断言失败：" + hint);
    }

    /** 异常断言：期望动作抛出指定异常，并返回该异常供进一步检查 */
    public static <E extends Throwable> E throwsException(Class<E> expected, Executable action) {
        try {
            action.execute();
        } catch (Throwable t) {
            if (expected.isInstance(t)) return expected.cast(t);
            throw new AssertionError("断言失败：期望抛 " + expected.getSimpleName()
                + "，实际抛 " + t.getClass().getSimpleName() + ": " + t.getMessage());
        }
        throw new AssertionError("断言失败：期望抛 " + expected.getSimpleName() + "，但未抛出任何异常");
    }
}
```

📚 **`throwsException` 是可测试性的灵魂**：02 篇说过"守卫的最好测试就是看它拒绝什么"。V1 的"支付失败库存自动回滚"、V3 的"超限抛统一异常"，全靠这个断言。

**③ TestRunner——套件运行器**：

```java
public final class TestRunner {
    private final String suiteName;
    private final List<Case> cases = new ArrayList<>();

    public TestRunner(String suiteName) { this.suiteName = suiteName; }

    public TestRunner test(String name, Executable body) {
        cases.add(new Case(name, body));
        return this;                                   // 链式注册
    }

    public void run() {
        System.out.println("[TEST SUITE] " + suiteName);
        int pass = 0, fail = 0;
        long start = System.currentTimeMillis();
        for (Case c : cases) {
            try {
                c.body.execute();
                System.out.println("  ✓ " + c.name);
                pass++;
            } catch (Throwable t) {                    // 一个用例挂了不影响后面的
                System.out.println("  ✗ " + c.name);
                System.out.println("      " + t.getMessage());
                fail++;
            }
        }
        System.out.println(String.format("[结果] %d 通过 / %d 失败 / %dms",
            pass, fail, System.currentTimeMillis() - start));
        if (fail > 0) System.exit(1);                  // 退出码供 CI 判定
    }
}
```

### 灵魂三问：V0 上帝类

❓ **为什么订单系统特别容易长出上帝类？**

因为履约链路是**一条线**：下单→库存→计价→支付→运费→通知→对账。线性流程最容易写成"一个方法从头干到尾"——每加一环就往方法里塞一段。**打破的关键是问：每一段的"变化原因"相同吗？** 库存跟着仓储策略变、计价跟着营销变、通知跟着渠道变——七个变化原因挤一个方法，这就是 SRP 违反的本质（02 篇：看变化来源，不看功能数量）。

❓ **bug 为什么埋在"规则的组合"而不是某一行？**

BUG 1（多收 125 元）单独看每一行都对：`×0.9` 对、`-250` 对——错的是**顺序**。逻辑正确但顺序错误，编译器不报错、单测不覆盖就上线。这正是 03 篇 V5 事故（"顺序写反，全量用户多扣钱"）的复刻：**if-else 的隐含语义是"先到先得"，顺序即业务，但代码把它藏起来了**。

❓ **为什么 BUG 2（库存消失）比 BUG 1 更危险？**

BUG 1 少收/多收钱，对账能发现；BUG 2 是**中途抛异常、库存已扣、无人回滚**——用户没买到东西、库存却少了，属于"系统状态被破坏"，每次发生都要人工修数。它示范了 SRP 的深层价值：**职责拆开后，"失败补偿"才有地方放**（V1 的库存回滚就是拆分的直接产物）。

```java
        if (order == null || order.getLines().isEmpty()) {
            throw new IllegalArgumentException("订单不能为空");
        }
        for (Order.OrderLine l : order.getLines()) {
            if (l.getQty() <= 0) {
```

### 灵魂三问：度量诊断

❓ **"感觉烂"和"量出来烂"差在哪？**

08 篇的答案：**"感觉烂"说服不了 PM，"量出来烂"可以**。"改 tab 花 4 天"的复盘之所以有力，是因为拿出了"硬编码 17 处"的数字。重构前建立度量基准，重构后同一把尺子再量一遍——**疗效才有证据**。

❓ **圈复杂度怎么算？**

```
圈复杂度 = 判断节点数 + 1
每个 if / else if / for / while / case / catch / && / || 各算一个判断节点
```

分级（08 篇体温计）：1~10 低 / 11~20 中（考虑简化）/ 21~50 高（必须重构）/ >50 极高（不可维护）。

❓ **为什么扫描器要自己写？**

两个理由：① SonarQube 在教学工程里是黑盒，**自己写一遍（源码文本解析 + 正则坏味道匹配，~140 行）才知道度量到底是什么**；② 自建扫描器让"重构效果对比"内建于工程——终局报告直接调用它，**前后数字出自同一把尺子**（§13.1 会回到这一点）。

### 灵魂三问：SRP 手术

❓ **第一刀从哪里下？**

**找变化原因**（02 篇的认知拐点：看角色，不看功能数量）。六件事背后是六个变化驱动者：仓储运营改库存规则、营销改折扣、支付组改渠道、物流改运费、增长改通知、财务改对账。**六个角色 = 六个类**，谁提需求改谁的类，互不打架。

❓ **拆完谁来串流程？**

`OrderService`——但它**只做编排不做实事**（对照 02 篇拆完的 DetailController：只剩"协调几位朋友"）。判据：协调者自己不应有任何一行"业务计算"。

❓ **"支付失败回滚库存"为什么在 V1 才可能，V0 不行？**

V0 里库存和支付是同一个方法的两行代码，**失败补偿没有天然的放置点**。拆分后 `InventoryService.restock()` 是库存服务的自然能力，协调者 try-catch 一接——**结构拆分释放了修复的可能性**。这是 SRP 的深层收益：不只是"好读"，而是"变更被限制在一个类里"。

```java
public class InventoryService {
```

### Step 3.3 OrderService 协调者 + 失败补偿（BUG 2 止血）

> 📁 **归属文件**：`src/com/yc/orderforge/v1srp/OrderService.java`

```java
/**
 * 只做编排，不做任何具体的事。
 * placeOrder 圈复杂度从 V0 的 14 降到 4。
 *
 * ⚠️ 留给 V4 的坏味道：构造器里 new 全部依赖（DIP 违反）——
 *    V1 先保证职责单一，"谁来提供依赖"是 DIP 手术的活。
 */
public class OrderService {

    private final InventoryService inventory = new InventoryService();      // ← V4 的手术靶子
    private final PricingService pricing = new PricingService();
    private final PaymentService payment = new PaymentService();
    private final ShippingService shipping = new ShippingService();
    private final NotificationService notification = new NotificationService();
    private final ReconciliationService reconciliation = new ReconciliationService();

    public String placeOrder(Order order) {
        if (order == null || order.getLines().isEmpty()) {
            throw new IllegalArgumentException("订单不能为空");
        }
        if (!inventory.tryDeduct(order)) {
            throw new IllegalStateException("库存不足");
        }

        Money total;
        try {
            total = pricing.price(order);
            payment.charge(order.getPayType(), total);
        } catch (RuntimeException e) {
            inventory.restock(order);        // ← V1 核心修复：失败补偿，库存不再凭空消失
            throw e;
        }

        total = total.plus(shipping.fee(order));
        notification.notifyPaid(order, total);   // BUG 3 仍在（V4 修）
        reconciliation.record(order.getOrderNo(), total);
        return order.getOrderNo();
    }
}
```

**三个要点**：

1. **try-catch-restock 三行就是 BUG 2 的止血**——它治的是"后遗症"（库存消失），还没治"病根"（限额为什么中途才知道？病根在 V3 的契约）；
2. **构造器 new 六个依赖是故意留的 DIP 坏味道**——注意它与"上帝类"的区别：职责已经单一，只是"依赖的来源"不对。V4 的刀会落在这里；
3. **placeOrder 只剩 4 个判断**：空单 / 库存 / try-catch / 无——从 14 降到 4，**复杂度没有消失，是被分摊到了六个各司其职的类里**。

## 06.会话 4：V2 OCP 手术（折扣变策略链）

```
┌─ 🎯 V2 目标 ─────────── 本案例 OCP 高峰 ⭐ ─────────────┐
│ 完成什么：DiscountStrategy SPI + 折扣链，修复 BUG 1       │
│ 核心承诺：加营销规则 = 加策略类 + 注册一行，核心 0 修改     │
│ 验收标准：V2OcpTest 6 通过（含"零改动"用例）               │
│ 预计耗时：90 min · 4 Step                                  │
└───────────────────────────────────────────────────────────┘
```

### 灵魂三问：OCP 手术

❓ **为什么 V1 的时候不抽策略、V2 才抽？**

**Rule of Three**（03 篇）：只有满减 1 种规则时不抽象；会员、券、新人立减出现到第 3、4 种时，"每次加规则都要改 `PricingService`"的疼痛已经真实发生——抽象的时机才到。提前抽象是过度设计（YAGNI），滞后抽象是债务，**三次是经验分界线**。

❓ **"对修改关闭"到底关闭的是什么？**

03 篇 §12.2 的精确辨析：**"加文件"是 OCP 鼓励的扩展，"改主流程代码"才是 OCP 要消灭的修改**。判据三问：动没动被复用的核心类？要不要重跑原有回归？会不会拖别的调用方下水？——V2 之后加折扣，`StrategyPricingService` 和 `DiscountChain` 的 diff 永远为空。

❓ **策略链怎么顺带修好 BUG 1？**

V0 的顺序错误藏在 if-else 的**书写顺序**里；策略化后，顺序变成 `DiscountChain` 的**注册顺序**——`满减 → 券 → 会员 → 新人`显式写在 `defaults()` 工厂里，评审一眼可见。**顺序从"实现细节"升级为"显式配置"**。

### Step 4.1 DiscountStrategy SPI

> 📁 **归属文件**：`src/com/yc/orderforge/v2ocp/DiscountStrategy.java`

```java
/**
 * 折扣策略 SPI（03 篇 DiscountStrategy 的落地）。
 *
 * OCP 三要素（03 篇 §6.2）：
 *   稳定点：本接口（3 个方法，再也不改）
 *   接入点：DiscountChain.register()（注册即生效）
 *   变化点：每种折扣一个实现类（加文件，不改文件）
 *
 * Rule of Three：V0 时只有 1 种规则不抽象；满减/会员/券出现第 3 种时才抽——
 * 现在已有 4 种，抽象的时机到了。
 */
public interface DiscountStrategy {

    /** 策略名（审计用） */
    String name();

    /** 是否适用于本单 */
    default boolean applies(DiscountContext ctx) { return true; }

    /** 在当前金额上应用本策略，返回新金额 */
    Money apply(Money current, DiscountContext ctx);
}
```

**三个方法各自的存在理由**（对照 ISP：没有一个是凑数的）：`name()` 供审计、`applies()` 让"这单轮不轮得到我"由策略自己回答（散弹式修改的克星）、`apply()` 是正事。

### Step 4.2 四个策略类（含一个易错点）

> 📁 **归属文件**：`v2ocp/` 下四个类，每个 20~35 行

**① FullReductionDiscount——阶梯数据化，BUG 1 修复的第一刀**：

```java
/**
 * 阶梯满减（V2 修复 BUG 1 的第一刀：满减优先，从高到低命中即停）。
 *
 * 对照 V0/V1 的写法，策略化的意义：
 *   - 顺序从"代码里碰巧的书写顺序"变成"注册顺序"，显式可查
 *   - 阶梯数据化（LADDERS），运营加档位改数据不改逻辑
 */
public class FullReductionDiscount implements DiscountStrategy {

    /** 阶梯：满 X 元减 Y 元（阈值降序，命中即停） */
    private static final double[][] LADDERS = {
        {1000, 250},   // 满 1000 减 250
        {500,  100},   // 满  500 减 100
        {300,  50}     // 满  300 减  50
    };

    @Override public String name() { return "阶梯满减"; }

    @Override
    public Money apply(Money current, DiscountContext ctx) {
        for (double[] rung : LADDERS) {
            if (current.greaterOrEqual(Money.ofYuan(rung[0]))) {
                return current.minus(Money.ofYuan(rung[1]));   // 命中即停
            }
        }
        return current;
    }
}
```

**②③④ 券 / 会员 / 新人**——重点看新人立减里的**易错点**：

```java
public class CouponDiscount implements DiscountStrategy {
    @Override public boolean applies(DiscountContext ctx) {
        return ctx.getOrder().getCoupon() != null;
    }
    @Override
    public Money apply(Money current, DiscountContext ctx) {
        return current.min(ctx.getOrder().getCoupon());   // 券面值即上限（min 兜底）
    }
}

public class VipDiscount implements DiscountStrategy {
    @Override public boolean applies(DiscountContext ctx) { return ctx.getOrder().isVip(); }
    @Override public Money apply(Money current, DiscountContext ctx) {
        return current.multiply(0.9);
    }
}

public class NewUserDiscount implements DiscountStrategy {
    @Override public boolean applies(DiscountContext ctx) { return ctx.getOrder().isNewUser(); }
    @Override
    public Money apply(Money current, DiscountContext ctx) {
        Money after = current.minus(Money.ofYuan(30));
        return after.isNegative() ? Money.ZERO : after;   // 立减不能把金额减成负数
    }
}
```

> ⚠️ **易错点：`min` 和 `minus` 不是一回事**（本工程开发时真踩过）：
>
> ```java
> // ❌ 错误写法：min(30) 的语义是"最多剩 30"，不是"减 30"
> return current.min(Money.ofYuan(30));        // 100 元单 → 30 元？！少收 70
>
> // ✅ 正确写法：先减，再兜底负数
> Money after = current.minus(Money.ofYuan(30));
> return after.isNegative() ? Money.ZERO : after;   // 100-30=70；20-30→0
> ```
>
> `min` 只适合**券**（"券面值即抵扣上限"，30 元单用 100 元券付 0 元——券没有找零）；**立减**是减法，需要的是负数兜底。**同名语义陷阱，靠单测逮住**——V2OcpTest 的"新人立减与券可叠加"用例当时就红了。

### Step 4.3 DiscountChain 注册表：顺序即业务

> 📁 **归属文件**：`src/com/yc/orderforge/v2ocp/DiscountChain.java`

```java
/**
 * 折扣链（注册表）：注册顺序 = 执行顺序，顺序从此显式可查。
 *
 * 【OCP 验收点】新增一种折扣 = 新写一个 Strategy 类 + 这里 register 一行。
 * 03 篇 §12.2 的辨析：register 一行属于"组装"，不属于"修改核心逻辑"——
 * 它在组合根（组装代码）里，不在任何被复用的业务类里。
 */
public class DiscountChain {

    private final List<DiscountStrategy> strategies = new ArrayList<>();

    public DiscountChain register(DiscountStrategy strategy) {
        strategies.add(strategy);
        return this;
    }

    public Money apply(Order order) {
        DiscountContext ctx = new DiscountContext(order, order.subtotal());
        Money current = order.subtotal();
        for (DiscountStrategy s : strategies) {
            if (s.applies(ctx)) {
                current = s.apply(current, ctx);
            }
        }
        return current;
    }

    /** 默认链条：满减 → 优惠券 → 会员 → 新人（顺序即业务规则，修复 BUG 1） */
    public static DiscountChain defaults() {
        return new DiscountChain()
            .register(new FullReductionDiscount())
            .register(new CouponDiscount())
            .register(new VipDiscount())
            .register(new NewUserDiscount());
    }
}
```

策略版计价服务从此**与营销规则彻底解耦**：

```java
public class StrategyPricingService {
    private final DiscountChain chain;
    public StrategyPricingService() { this(DiscountChain.defaults()); }
    public StrategyPricingService(DiscountChain chain) { this.chain = chain; }
    public Money price(Order order) { return chain.apply(order); }
}
```

### 灵魂三问：LSP+ISP 手术

❓ **04 篇的"多态"和"里氏替换"到底差在哪？**

**多态是语法，LSP 是契约**。`CreditCardPayment implements PaymentMethod` 编译秒过——但它在 `pay()` 里抛 `IllegalArgumentException`（契约外类型）、限额 5000 却不声明（前置条件被暗中加强），上游按契约统一 catch 时它就漏网炸穿。**语法允许 ≠ 契约允许**。

❓ **契约怎么"可执行"？**

写**契约测试**：一套用例循环体检所有实现——"正数金额要么成功要么抛统一异常""失败不得改变内部余额"。新写一个支付实现，加进 IMPLS 数组，契约测试立刻告诉你违没违约。**04 篇的检查清单（五行表格）变成代码**，这是 LSP 落地的关键一步。

❓ **限额怎么修才不违反 LSP？**

两条路：① 收窄父类契约（所有支付方式都声明限额，默认不限）；② 不继承。这里选 ①——`singleLimit()` 成为接口方法，信用卡如实声明 5000。于是"限额"从**实现内部的暗坑**变成**契约的一部分**——`PaymentRouter` 拿着它在**扣库存之前**拦截，BUG 2 从"事后炸"变成"事前挡"。

### Step 5.1 PaymentMethod 契约

> 📁 **归属文件**：`src/com/yc/orderforge/v3lspisp/PaymentMethod.java`

```java
/**
 * 支付方式契约（04 篇 DbC 契约式设计的落地）。
 *
 * 【本接口的契约】（每个实现者必须遵守，调用方可以放心依赖）：
 *
 *   前置条件：amount 必须为正；amount 不得超过 singleLimit()
 *   后置条件：pay() 正常返回 = 扣款成功并返回非空流水号；
 *             任何失败都抛 PaymentRejectedException（且不扣款）
 *   不变式  ：失败调用前后，实现内部余额不变
 *
 * 对照 04 篇 CreditCardPayment 案例：
 *   V0 的写法（金额>5000 抛 IllegalStateException）= 前置条件被加强 +
 *   抛契约外异常 —— 两连违反。
 */
public interface PaymentMethod {

    /** 发起支付：成功返回流水号，失败抛 PaymentRejectedException 且不扣款 */
    String pay(Money amount);

    /** 渠道名 */
    String name();

    /** 单笔限额（契约的一部分，默认不限额；调用方须在下单前检查） */
    default Money singleLimit() {
        return Money.ofCents(Long.MAX_VALUE);
    }
}
```

**契约写在接口的 Javadoc 里**——这不是"注释随便写写"，而是**实现者和调用方共同的依据**；契约测试（Step 5.2）逐条把它变成断言。

### Step 5.2 违约标本当场被抓

```java
/**
 * ⚠️ LSP 违反标本（04 篇 CreditCardPayment 原案，故意保留供契约测试抓获）：
 *
 *   1. singleLimit() 没有覆写 → 契约上"不限额"

    @Override
    public String pay(Money amount) {
```

### Step 5.3 修复版：限额入契约（BUG 2 结构性消灭）

```java
/**
 * 信用卡支付（V3 修复版）：限额成为契约的一部分。
 * V0 的 BUG 2 在这里被结构性消灭：singleLimit() 公开限额，
 * 调用方（PaymentRouter）在下单前拦截，库存再也不会白扣。
 */
public class CreditCardPayment implements PaymentMethod {

    private final Money limit;

    public CreditCardPayment(Money limit) { this.limit = limit; }

    @Override
    public String pay(Money amount) {
        if (amount == null || !amount.isPositive()) {
            throw new PaymentRejectedException("支付金额必须为正: " + amount);
        }
        if (amount.greaterThan(limit)) {
            throw new PaymentRejectedException(
                name() + "单笔限额 " + limit + "，当前 " + amount + "，请拆单或换渠道");
        }
        return "CARD-" + TX_SEQ.incrementAndGet();
    }

    @Override public String name() { return "信用卡"; }

    @Override public Money singleLimit() { return limit; }    // ← 限额公开可查
}

/**
 * 支付路由器：依赖"限额是契约的一部分"这件事，把失败提前到扣库存之前。
 */
public class PaymentRouter {

    public String pay(PaymentMethod method, Money amount) {
        if (amount.greaterThan(method.singleLimit())) {
            throw new PaymentRejectedException(
                "[" + method.name() + "] 单笔限额 " + method.singleLimit()
                + "，当前 " + amount + " —— 下单前拦截，未扣库存");
        }
        return method.pay(amount);
    }
}
```

### 灵魂三问：DIP+LOD 手术

❓ **V1 留下的 `new InventoryService()` 为什么是病？**

06 篇 380 处换库惨剧的微缩版：协调者**既用**依赖又**造**依赖。想测试 OrderService？对不起，它内部 new 了真短信服务；想换邮件通知？对不起，改 NotificationService 源码。**依赖注入的本质：把"造什么"从类里搬到组装根（main）**——业务类只声明"我需要什么类型"。

❓ **为什么接口要由高层定义？**

06 篇"倒置"的精髓：`MessageSender` 只有 `send(to, message)` 两个方法——这是**通知业务**需要的语义，不是短信 SDK 的 API 翻版。低层的 SmsSender/EmailSender 反过来适配高层接口："不是业务求着渠道，而是渠道适配业务"。**谁定义抽象，谁掌握语义控制权**。

❓ **`getShippingCityName` 和 07 篇的"中间人膨胀"怎么平衡？**

```java
        this.inventory = inventory;         this.pricing = pricing;
        this.shipping = shipping;           this.paymentRouter = paymentRouter;
        this.paymentMethod = paymentMethod; this.notification = notification;
        this.repository = repository;
    }

    /** 客户端唯一入口：一个方法完成履约全链路 */
    public String placeOrder(Order order) {
        if (order == null || order.getLines().isEmpty()) {
            throw new IllegalArgumentException("订单不能为空");
        }
        // ① 计价（V2 策略链，BUG 1 已修）
        Money total = pricing.price(order);
        // ② 运费
        total = total.plus(shipping.fee(order));
        // ③ 支付（V3 契约路由：超限/余额不足在扣库存之前失败，BUG 2 已修）
        String txId = paymentRouter.pay(paymentMethod, total);
        // ④ 扣库存（走到这里支付已成功，才会动库存；失败自动补偿）
        if (!inventory.tryDeduct(order)) {
            throw new IllegalStateException("库存不足（支付已成功，需人工退款 " + total + "）");
        }
        // ⑤ 通知（V4 LOD：空地址安全，BUG 3 已修）
        notification.notifyPaid(order, total);
        // ⑥ 仓储（对账）
        repository.save(order.getOrderNo(), total);
        return order.getOrderNo() + " / 流水 " + txId;
    }
}
```

📌 **注意 ③④ 的顺序被调换了**：V0/V1 是"先扣库存再支付"，V4 门面是"**先支付再扣库存**"——支付（可能失败的外部交互）放前面，库存（内部状态变更）放后面，失败面最小化。这是契约化带来的**流程重排自由**：限额可预知（singleLimit），支付才有资格先行。

## 10.造 BUG → 修复清单：三处详解

参照 KV 案例"高峰造 BUG"设计，三处"亲手埋、亲眼见、亲手治"：

### BUG 1：折扣顺序写反，多收 125 元（V0 埋 / V2 修）

```java
// 造：会员折扣先于满减（每一行都对，顺序错了）
if (order.isVip()) total = total.multiply(0.9);
if (total >= 1000) total -= 250;   // 1000×0.9=900，只命中"满500减100"

// 看见：./run.sh v0 → 订单 2 期望 ¥675 实收 ¥800
// 修复（V2）：DiscountChain.defaults() 注册顺序 = 满减 → 券 → 会员 → 新人
```

**教训**：if-else 的隐含语义是"先到先得"，**顺序即业务，必须显式化**。策略链把顺序从实现细节升级为配置——评审时一眼可见。

### BUG 2：信用卡限额中途炸，库存凭空消失（V0 埋 / V1 止血 / V3 根治）

```java
// 造：扣库存之后才检查限额
STOCK_SKU_A -= order.totalQty();
if (payType == 1 && total > 5000) throw new IllegalStateException(...);  // 库存没人还

// 看见：./run.sh v0 → 库存 96 → 94，订单失败
// V1 止血：catch 后 inventory.restock()（结构拆分释放的能力）
// V3 根治：singleLimit() 入契约 + PaymentRouter 扣库存前拦截
```

**教训**：这是 **LSP 违反 + 副作用时序**的复合事故——限额是"契约外的暗坑"，调用方无从预判。契约化之后，"事前挡"取代"事后补"；门面更是把"先支付后扣库存"变成可能。

### BUG 3：火车残骸 + 空地址，已扣款通知 NPE（V0 埋 / V4 修）

```java
// 造：四层 getter 链，穿透 Customer→Address→City
String city = order.getCustomer().getAddress().getCity().getName();  // address=null → NPE

// 看见：./run.sh v0 → 钱包已扣 70，通知崩了，订单卡死
// 修复（V4）：order.getShippingCityName() —— 一层调用 + "未知城市"兜底
```

**教训**：07 篇 31 文件事故的微缩版——**调用者了解得越多，崩得越随机**。LOD 不只是"链短好看"，而是把空值判断收敛到一个方法里（31 处兜底 → 1 处）。

## 13.项目技术思考

### 13.1 度量为什么必须"同一把尺子"

终局报告直接调用会话 2 的 CodeMetrics 扫描终局代码——**前后数字出自同一把尺子**，对比才有意义。这对应 08 篇"重构前建立度量基准"的告诫：如果手术前用 SonarQube、手术后用自己的脚本，数字再好看也是自欺。**教学工程自建度量的深层理由：让"疗效证明"内建于工程，而不是外挂一个谁也没跑过的工具**。

### 13.2 "诚实保留 bug"的教学价值

V1 的源码注释里写着"BUG 1 有意保留，V2 修"——这在真实工程里是荒谬的（发现 bug 立刻修），但在教学工程里是关键设计：**它强制展示"每次手术只治一种病"的纪律**，并且让每个 bug 在"它对应的原则会话"里被亲手修掉——修 BUG 1 时你正在学 OCP，修 BUG 3 时你正在学 LOD。**病与药在同一张处方上**。

### 13.3 与 PayFlow 案例的对照：折扣桥段的克制

同一工作区的 PayFlow 把折扣叠加做到了九层规则 + SPI 编排；OrderForge 的折扣**故意止步于一层策略链**——因为两个案例的教学目标不同：前者练"复杂规则的编排架构"，后者练"原则手术 + 度量证明"。看到同一个业务问题有两种深度的解法，本身就是一课：**抽象深度跟着教学目标（工程目标）走，不存在"标准答案级"的抽象**。

### 13.4 门面 vs 中间人：LOD 的平衡木

07 篇讲过"中间人膨胀"的反面案例（为了避残骸给 Order 加 12 个纯转发方法）。OrderFacade 给出的平衡姿势：**门面转发的是"用例级动作"（placeOrder 一个入口），不是"字段级数据"**——`facade.placeOrder(order)` 是完整业务动作，而 `facade.getCustomerAddressCityName()` 那种数据拼图才是中间人坏味道。判据一句话：**调用方要的是"做事"还是"取数"——做事给门面，取数给直接朋友**。

| 主轴 | 封装/多态/组合/装饰器 → DDD | **六大原则手术 + 重构度量** |
| 驱动 | 版本演化叙事 | **度量驱动**（前后对比） |
| 终局 | 聚合根 + 领域事件 | **重构评估报告** |

两篇方法论同构（先看见病 → 小步演化 → 每步验收），但视角互补：**PayFlow 是"绿地怎么设计好"，OrderForge 是"遗产怎么治好"——工作中后者占 80%**。

### 14.2 三个延伸挑战

**挑战 A（基础）· 给契约测试加"语义"检查**
LSP 第 4 条规则（不改变语义）最难测。尝试给 `PaymentMethod` 加一个 `audit()` 输出，契约测试断言每个实现的审计行都包含"渠道名 + 金额"——体会"语义契约"如何半形式化。

**挑战 B（进阶）· 用 DiscountChain 实现"互斥规则"**
业务新需求：新人立减与优惠券互斥。在不修改任何已有策略类的前提下实现（提示：新写一个 `MutexGuardStrategy` 或者给 Chain 加"跳过标记"——哪条路更 OCP？哪条更 KISS？做完你会对 03 篇的权衡公式有切身体会）。

**挑战 C（冲刺）· 度量工具升级为"提交门禁"**
把 MetricsReport 改造成：扫描全工程，任何方法 CC>10 就 `System.exit(1)`——然后在 V0 上跑一次看它拦截自己。这是"把原则变成 CI 流水线"的最小实验。

### 14.3 学习路线建议

1. **第一遍（跟做）**：7 次会话顺序敲完，每个验收亲眼见（~18 小时）；
2. **第二遍（盲做）**：只看 V0 和本文"渐进学习节奏"图，自己拆到门面，卡住再对照（把"看会"变"会写"）；
3. **第三遍（讲授）**：挑一次手术（推荐 V2 或 V3）讲给同事 30 分钟——讲不清的就是没真懂（费曼学习法）。

## 15.快速总结与尾声

> **OrderForge 干的事就一件**：把六大原则和重构方法论装进一个"先写烂、再治好、最后用数字证明治好了"的完整闭环——V0 上帝类（CC=14，3 个真实 bug）→ 度量诊断 → 六次手术 → 终局报告（CC=2，坏味道 0，加需求 = 加文件）。

> **与 PayFlow 的分工**：那边教你把新系统设计好，这边教你把烂系统治好——**工作中后者占 80%**。
