## 01.前言：为什么是"合体"，为什么是订单

12 篇博客走完，读者手上其实攥着 11 段"半成品代码"：
`OrderUtil.calculate()` 的 1284 行、`Account.transfer()` 的余额对不上、`MyLogger` 被改了 47 次的双层范式、62873 个 `OSSClient` 的支付渠道、`Dragon` 的能力组合、`OrderManager` 的 8194 行上帝类、`RiskCheckProcessor` 的 SOLID 现场……**它们本来就是同一个订单系统的 11 次片段演化**。

但没有一个能 `./build.sh` 跑起来。

**PayFlow 干的事就一件**：把这 11 段半成品接回去，让它在**一个真实可跑的工程里**继续演化到 DDD 终局——过程中：
- ✅ 每一版对应 1-2 篇博客的知识点，旧代码在新语境里"再一次"发挥作用；
- ✅ 每一版 30 秒可跑，`./run.sh v0..v7` 立刻看到；
- ✅ V0 埋 3 个真实 bug，V5 用特征化测试挖出来（伏笔从第 01 篇埋到第 14 篇回收）；
- ✅ 全程仿照 [《C++ 迷你 KV 存储引擎》](/pages/40e8e2/) 的"5 次会话 + 灵魂三问 + 造 BUG 修复"教学骨架。

**四方案评估**（详见博客 §1 的完整对比）：网约车 / 会员订阅 / 图片框架续篇都能覆盖大部分知识点，但只有电商订单能做到**"回收 00-11 篇留下的代码 + 全专栏首尾闭环"**，方案 A 胜出。

## 03.业务全景与九层结算规则

订单闭环：**下单 → 结算 → 扣款 → 通知 → 事件下发（发票/积分/风控）**。

**九层结算规则**（V0 里全部糊在一个函数，V4 拆成 9 个 Step）：

```
Step 1: 小计       = Σ(单价 × 数量)
Step 2: 满减       - 阶梯满减（满 1000 减 250 / 满 500 减 100 / 满 300 减 50）
Step 3: 秒杀折扣   × 20:00-22:00 打 8 折     ← Clock 硬刚需
Step 4: 优惠券     - 券面值（有门槛）
Step 5: 会员折扣   × 铂金 85% / 黄金 90% / 白银 95%
Step 6: 运费       + 满 99 包邮，否则 12 元
Step 7: 跨境税     + 11.9%
Step 8: 积分抵扣   - 100 积分 = 1 元
Step 9: 最低兜底   ≥ 0.01
```

**每一层单看都不复杂，叠加就是雪崩**——这就是第 01 篇"复杂度持续叠加"的现场标本。

## 05.会话 1：V0 屎山现场（诊断病）

**目标**：先看见病，才能开药。**不动 V0 的一行代码**——先用词汇给它命名。

### 5.1 灵魂三问（动手前先想清楚）

> ① **为什么金额不能用 `double`？**
> 试算 `0.1 + 0.2` 你就明白。V0 用 double 是双 11 少收几百万的元凶之一；V1 会引入 `Money` 值对象（以分为单位存储）。
>
> ② **`static WALLET_BALANCE` 有什么问题？**
> 三点：不可测（测试之间相互污染）、并发不安全（多线程扣款覆盖）、不变量无人守（可扣成负数）。V1 会用 `Wallet` 类的 `withdraw()` 意图方法守住。
>
> ③ **`if (city.equals("北京"))` 为什么是坏味道？**
> 基本类型偏执 + 散弹式修改：新增一个城市要改 N 个 if 分支。V1 之后会用多态族 + 数据驱动的注册表消除。

### 6.1 V1：封装 + 多态（第 02 篇）

**灵魂三问**：
> ① `balance -= amount` 直接写在调用方为什么错？→ **不变量无人守**
> ② 五个字段全 public 的类是 OOP 吗？→ **伪 OOP**
> ③ 消灭 switch 的关键动作是什么？→ **让"是什么"回答"怎么办"**

**Step 1：Wallet 聚合守住不变量**（`v1feature/Wallet.java`）

```java
public class Wallet {
    private Money balance;                          // ① 字段私有

    public Wallet(Money initial) {                  // ② 构造时校验
        if (initial == null || initial.isNegative()) throw ...;
        this.balance = initial;
    }

    public void withdraw(Money amount) {            // ③ 意图方法 vs 步骤方法
        if (amount == null || !amount.isPositive()) throw ...;
        if (amount.greaterThan(balance))            // ④ 不变量守卫
            throw new InsufficientFundsException(...);
        this.balance = balance.minus(amount);
    }
}
```

**四个动作**（对应 02 篇"真封装"定义）：字段私有 → 构造校验 → 意图方法 → 不变量强守。

**Step 2：VipPolicy 消灭 switch**

```java
public interface VipPolicy {
    Money applyDiscount(Money original);
    String levelName();
}
public class GoldVipPolicy implements VipPolicy {
    public Money applyDiscount(Money o) { return o.percentOff(10); }
    public String levelName() { return "GOLD"; }
}
// 主流程：VipPolicies.of(level).applyDiscount(money);
// ↑ 新增等级只加一个类，主流程零修改
```

### 6.2 V2：接口 vs 抽象类 + 面向接口（第 03/04 篇）

**灵魂三问**：
> ① 通知（短信/推送/邮件）用继承还是接口？→ **`can-do` 是接口**
> ② 只用接口 + default 方法为什么不行？→ **接口不能有实例字段**（黑名单 Set 存哪？）
> ③ 重试为什么不能塞进 PaymentChannel 接口？→ **横切关注要用装饰器**

**Step 1：BillingNotifier 双层范式**（模板方法）

```java
public interface BillingNotifier { void notify(recipient, orderNo, amount); }

public abstract class AbstractBillingNotifier implements BillingNotifier {
    private final Set<String> blacklist = new HashSet<>();   // ← 只能存这里

    public final void notify(String recipient, ...) {         // 模板方法 final 锁定流程
        if (recipient == null) throw ...;
        if (blacklist.contains(recipient)) return;
        doSend(recipient, renderTemplate(orderNo, amount));   // ← 子类填空
        onSent(...);
    }
    protected abstract void doSend(String recipient, String body);
}

public class SmsNotifier extends AbstractBillingNotifier {
    protected void doSend(String r, String body) { /* 调运营商 SDK */ }
    public String channelName() { return "SMS"; }
}
```

**这就是 Spring `BeanFactory + AbstractApplicationContext`、Netty `ChannelHandler + ChannelInboundHandlerAdapter`、MyBatis `Executor + BaseExecutor` 的同款范式**。

**Step 2：PaymentChannel 面向接口 + Retry 装饰器**

```java
public interface PaymentChannel {
    String pay(String orderNo, Money amount);
    String channelName();
}

// 装饰器：横切关注不塞进业务接口
public class RetryableChannel implements PaymentChannel {
    private final PaymentChannel delegate;
    private final int maxAttempts;
    public String pay(...) {
        long backoffMs = 100;
        for (int i = 1; i <= maxAttempts; i++) {
            try { return delegate.pay(...); }
            catch (PaymentException e) { sleep(backoffMs); backoffMs *= 2; }
        }
        throw ...;
    }
}
```

**指数退避序列**：100 → 200 → 400 → 800 ms（生产环境常见的 2s → 4s → 8s → 16s → 32s → 60s → 120s → 300s 封顶，本教学场景用 100ms 起步保证测试快）。

装饰器**可组合**：`new MetricChannel(new RetryableChannel(new WechatChannel()))`。

### 6.3 V3：组合优于继承（第 05 篇）

**灵魂三问**：
> ① 虚拟课程 `extends PhysicalProduct` 会发生什么？→ **企鹅会飞**（被迫实现 `ship()`）
> ② 能力该继承还是持有？→ **has-a 而非 is-a**
> ③ 组合的三步动作是什么？→ 能力抽接口 → 独立实现类 → Builder 装配

**Step 1：能力接口族**（`v3composition/ability/`）

```java
public interface Shippable    { long shippingFeeCents(String city, long subtotalCents); }
public interface ColdChainable { long coldChainSurchargeCents(); }
public interface CrossBorderable { double taxRate(); }
public interface Refundable   { int refundWindowDays(); }
```

**Step 2：Product 用 Builder 装配能力**

```java
Product virtualCourse = Product.builder("SKU-COURSE", "视频课程", 29900)
    .withRefundable(new StandardRefundable(7))
    // ↑ 没有 withShipping()！
    .build();

Product importedVaccine = Product.builder("SKU-VAX", "进口疫苗", 39900)
    .withShipping(new StandardShipping())
    .withColdChain(new ColdChainSurcharge())
    .withCrossBorder(new CrossBorderTax())
    .build();
// 三种能力叠加，无需任何继承
```

**继承 vs 组合的算术**：5 种能力任意组合，**继承需要 2^5 = 32 个子类**，组合只需 5 个能力类 + 1 个 Product。

**验收命令**：


## 07.会话 3：V4 SOLID 五马分尸（第 06/07 篇）

**目标**：把 V0 的 200 行 `calculate()` 拆成 `SettlementEngine + 9 个 PromotionStep`。**加"新营销规则"以后永远不改 Engine 一行代码**——这就是 OCP。

### 7.1 灵魂三问

> ① 拆函数的第一刀怎么下？→ **找变化轴**（每 2 周新增的规则就是变化轴）
> ② SPI 与 API 的区别？→ **谁调谁**：API 供人调，SPI 供人扩
> ③ SOLID 五条哪条最重要？→ **DIP 是地基**，其它四条都建立在"依赖抽象"上

### 7.2 SettlementContext + PromotionStep SPI

```java
public interface PromotionStep {
    int order();                                    // 执行权重，小的先跑
    String name();
    default boolean applies(SettlementContext ctx) { return true; }
    void apply(SettlementContext ctx);
}
```

九个 Step（`v4solid/steps/`）：`Subtotal → FullReduction → FlashSale → Coupon → VipDiscount → Shipping → CrossBorderTax → Points → MinimumCharge`。

**每个 Step 只干一件事**（SRP）：`FullReductionStep` 就 20 行，`CouponStep` 就 30 行，不复用不共享——从"改 200 行 1 个类"变成"改 20 行 9 个类"。

### 7.3 SettlementEngine：只做编排

```java
public class SettlementEngine {
    private final List<PromotionStep> steps;
    public SettlementEngine(List<PromotionStep> steps) {
        this.steps = steps.sorted(by::order);
    }
    public SettlementResult settle(SettlementContext ctx) {
        for (PromotionStep step : steps) {
            if (step.applies(ctx)) step.apply(ctx);
        }
        return new SettlementResult(ctx.orderNo(), ctx.currentTotal(), ctx.auditTrail());
    }
}
```

**Engine 本身不到 20 行**，就是一个 for 循环。**从今以后加规则不改 Engine**——毕设第一验收点。

### 7.4 SOLID 自检（用第 07 篇的 30 秒五步法）

| 原则 | V0 | V4 |
|---|---|---|
| **S**RP | 一个方法 6 职责 | 每个 Step 1 职责，Engine 只负责编排 |
| **O**CP | 加规则要改 calc | 加 Step 类，Engine 零修改 |
| **L**SP | N/A | 任意 Step 可替换现有位置 |
| **I**SP | 参数塞 10 个 | PromotionStep 只有 4 个方法 |
| **D**IP | 全部具体依赖 | Engine 依赖 PromotionStep 抽象 |

### 8.2 V6：Clock 注入让秒杀测试从"等半夜"到 10ms

**灵魂三问**：
> ① 为什么秒杀 Step 不能 `new Date()`？→ **不可控 → 不可测**
> ② 生产环境用什么 Clock？→ `Clock.system()` 走 JVM 时钟
> ③ 测试环境用什么？→ `Clock.fixed(LocalDateTime.of(2024, 11, 11, 21, 30))`

**Step 1：Clock 抽象接口**

```java
public interface Clock {
    LocalDateTime now();
    default LocalTime nowTime() { return now().toLocalTime(); }
    static Clock system() { return () -> LocalDateTime.now(); }
    static Clock fixed(LocalDateTime at) { return () -> at; }
}
```

**Step 2：FlashSaleStepV6 显式依赖 Clock**

```java
public class FlashSaleStepV6 implements PromotionStep {
    private final Clock clock;
    public FlashSaleStepV6(Clock clock) { this.clock = clock; }
    public void apply(SettlementContext ctx) {
        int hour = clock.nowTime().getHour();  // ← 从 LocalTime.now() 改这一行
        if (hour < 20 || hour >= 22) return;
        ctx.setCurrentTotal(ctx.currentTotal().percentOff(20));
    }
}
```

## 09.会话 5：V7 DDD 终局（第 11/12 篇）

**目标**：把 V4-V6 的技术性代码组织成**业务对齐**的架构——用限界上下文分门别类，用领域事件解耦上下文之间的依赖。

### 9.1 灵魂三问

> ① "会员"在营销/账户/风控三处是同一个类吗？→ **不是**（限界上下文各自建模）
> ② 聚合根的一致性边界画在哪？→ **同生共死** 的对象合成一个聚合
> ③ 结算后要触发库存/发票/积分/通知/风控，怎么办？→ **发领域事件**，谁想响应谁订阅

### 9.2 Order 聚合根

```java
public class Order {
    public enum Status { DRAFT, SETTLED, SHIPPED, CANCELLED }

    private final OrderId id;
    private final List<OrderLine> lines = new ArrayList<>();
    private Status status = Status.DRAFT;
    private Money finalAmount;

    public void addLine(OrderLine line) {
        if (status != Status.DRAFT)
            throw new IllegalStateException("只有草稿订单才能加行");
        lines.add(line);
    }

    public void settle(Money finalAmount, EventBus bus) {
        if (status != Status.DRAFT) throw ...;
        if (lines.isEmpty()) throw ...;
        this.finalAmount = finalAmount;
        this.status = Status.SETTLED;
        bus.publish(new OrderSettled(id.value(), buyerId, finalAmount, email, phone));
    }
}
```

**一致性边界**：`Order` 与 `OrderLine` 是同生共死，状态转换（DRAFT→SETTLED）跨行有效——一致性画在 `Order` 上。

**通过意图方法**（`addLine/settle/cancel`）暴露能力，外部不能直接改字段——不变量守卫。

### 9.3 领域事件 + 订阅方

```java
public class OrderSettled extends DomainEvent {
    private final String orderNo, buyerId;
    private final Money finalAmount;
    // ...
}

public class InvoiceIssuedHandler implements EventSubscriber<OrderSettled> {
```
