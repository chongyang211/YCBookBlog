# 第 7 卷｜编译与链接之道

> **核心命题**：从你按下 `保存` 到操作系统把 `main` 抬进 CPU，这中间**几十道工序**里，究竟发生了什么？为什么 C/C++ 交给链接器、Java 交给类加载器、Go 全部静态打包、JS 干脆不编译？这一整段路，是所有语言运行时的"上游"，也是本专栏第 2 卷「运行时模型」的地基。

---

## 一、这一卷要回答什么

在第 2 卷《运行时模型》里，我们从 `new` 那一刻开始，讲了类加载、栈帧、字节码、JIT——**但那已经是"程序在跑"了**。往前追一步：

- `printf("hello")` 里的 `printf`，是**谁**在**什么时候**告诉 CPU"跳到 libc 的这个地址"的？
- 为什么把一个 C 头文件多 `include` 一次会报 `multiple definition`，而 Java 里几乎不会？
- 为什么 Go 编译出来的 20MB 单文件能直接扔到服务器就跑，而一个 Java 项目要拖着一堆 jar？
- Rust 编译半小时，JavaScript 几乎不编译，Java 有 `javac + JIT`——**同一件"翻译"的事，为什么代价差这么多？**

这些问题的答案都藏在**编译 + 链接 + 加载**这条流水线里，本卷把它一次讲透。

---

## 二、学完你能回答

- 一份 `.c` 文件到 `a.out`，中间为什么要**预处理 → 编译 → 汇编 → 链接**四步，能不能少一步？
- 什么是"符号"？函数调用凭什么能"跨文件找到对方"？重定位到底重定位了什么？
- 静态库 `.a` 和动态库 `.so/.dll/.dylib` 的**根本差别**是什么？为什么大厂的服务喜欢静态、桌面/移动喜欢动态？
- 什么是 ABI？为什么 C++ 换个编译器就"链接不上"，而 C 从来不会？为什么 Rust 只对 C ABI 保证稳定？
- 编译型（C/C++/Rust）、VM 型（Java/Kotlin/C#/Go¹）、解释型（Python/JavaScript）**这三条路线**在"什么时候翻译、翻译到什么形式、由谁负责链接"三件事上，各自做了什么取舍？

> ¹ Go 严格说是 AOT 编译型，但因为带自研 runtime + GC + goroutine 调度器，工程属性更接近 VM 型，本卷第 5 篇会正面对比。

## 六、贯穿这一卷的三对矛盾

| 矛盾 | 一端 | 另一端 | 谁在做取舍 |
|------|------|--------|-----------|
| **翻译时刻** | 越早翻译（AOT）→ 启动快、可预测 | 越晚翻译（JIT/解释）→ 灵活、跨平台 | Rust ↔ Python 两个极端 |
| **拼装方式** | 静态链接：体积大、发布简单 | 动态链接：体积小、可热更、易 DLL Hell | Go ↔ 传统 Linux 生态 |
| **契约稳定性** | ABI 稳定：可跨语言 FFI、可长期兼容 | ABI 灵活：语言演进快、优化空间大 | C ↔ C++/Rust |

看清这三对矛盾，本卷就不用背了——**任何新语言、新工具链的选择，都是在这三对天平上重新称重**。

## 八、一句话总结

> **"编译"决定你写的东西 CPU 能不能懂；"链接"决定你写的东西能不能跟别人的东西拼在一起；"加载"决定这一切什么时候真正发生。**
> 这三件事，就是所有语言运行时的"上游"——**看懂它，你才能真正回答"程序是怎么跑起来的"**。
