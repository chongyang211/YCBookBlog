## 🎬 全卷综合案例："YC 商城"性能专项

### 背景设定（虚构但数字真实合理）

**YC 商城**：一家中型电商，DAU 800 万，年 GMV 200 亿。大促（双 11）前 3 个月，技术负责人发起"**百日性能专项**"。

| H5 / 小程序 | React | 日活 100 万 |
| API 网关 | Java / Spring Cloud Gateway | 峰值 12 万 QPS |
| 订单服务 | Go | 峰值 8 万 QPS |
| 商品/BFF | Java / Node | — |
| 中间件 | MySQL · Redis · Kafka | — |

### 大促体检发现的 9 个痛点（→ 10 篇 = 10 个战役）

| # | 痛点（现象） | 所属篇 | 治理后 |
|---|---|---|---|

| 2 | 网关大促预演 CPU 95%，扩容 3 倍无效（CPU 还是 95%） | 8.2 | 哈希碰撞修复，CPU 95% → 32%，缩容回原规模 |

### 案例使用规则（写作时遵守）

- **每篇开头**：从 YC 商城对应痛点的"事故现场"切入（值班群聊天记录 / 大盘截图 / 用户差评），立刻有代入感；
- **每篇主线**：用 YC 商城的**排查全过程**串起"分类 → 识图 → 工具 → 治理"，每个阶段都有当时的真实数据；
- **跨平台展开**：同一个痛点在 YC 商城的其他端"长什么样"（如 8.3 的 OOM：Android 8.3% / iOS 内存告警 3.1% / Web 页面崩溃 0.8% / 服务端 OOM 重启 2 次/周）——**这是跨平台节的天然素材**；
- **每篇结尾**：本战役战报（修复前后数字）+ "与下一战役的钩子"（如 8.2 修完 CPU 发现 QPS 还是上不去 → 引出 8.4 锁竞争）；
- **8.10 收束**：百日专项复盘大会——把 9 个战役的教训沉淀为制度，全卷故事闭环。

## 8.1 性能优化方法论与度量——建立性能的"看见能力"

> 🎯 **核心矛盾**：**不被度量的东西不能被优化**；90% 的性能"玄学"是因为没有共同的"看见"语言。
> 📌 **综合案例投影（战役 1）**：YC 商城大促前，下单接口 p99 1.8s、大盘平均 RT 210ms 全绿，GMV 悄悄掉 7% 却无人告警——专项第一战不是修问题，而是**换掉度量体系**。
> 🌐 **跨平台覆盖**：服务端（Prometheus/Grafana）· Android（Firebase/Matrix）· iOS（MetricKit）· Web（Web Vitals/RUM）· 全链路（OpenTelemetry）
> 🧠 **一句话心法**：**平均值是最大的骗子，分位数才是真话**。

### 01.开篇灵魂拷问
- 1.1 "我们的服务很快" vs "p99 怎么样"——平均之惑（YC 商城大盘全绿的教训）
- 1.2 "监控全绿为什么还崩"——指标选错之惑
- 1.3 "优化上线后 3 个月回到原点"——不守之惑

- 2.2 "三态"抽象：资源 → 响应 → 体验
- 2.3 为什么大多数团队只盯第一维（资源利用率）
- 2.4 面试锚点：**"你怎么理解性能？"**（四维答法）

### 03.现象到病因的映射
- 3.1 "QPS 下跌"的 5 种真实根因

### 04.度量心智三件套
- 4.1 **USE**（Utilization / Saturation / Errors）——资源视角
- 4.2 **RED**（Rate / Errors / Duration）——服务视角

- 4.5 分位数与直方图——打破"平均之骗"
  - p50 / p95 / p99 / p999 / 1% low 的工程含义

  - 🔬 深潜：Prometheus `histogram_quantile` 的插值误差
- 4.6 面试锚点：**"你们监控体系怎么设计的？"**

### 05.跨平台对照——同一个"慢"，四个端长得不一样
| 端 | 用户感知"慢" | 核心指标 | 采集方式 | 典型工具 |
|---|---|---|---|---|
| 服务端 | 下单转圈 | RT p99 / 错误率 / QPS | Metrics + Trace | Prometheus · Grafana · SkyWalking |

- 5.1 为什么四端的"四黄金信号"长得不一样（离用户的距离决定度量口径）

## 8.2 CPU 监控与分析优化——找到那 20% 吃掉 80% 的热点

> 🎯 **核心矛盾**：**高 CPU ≠ 慢，低 CPU 也不一定快**。真正要回答的是——**CPU 时间花在哪、哪个函数吃掉它、它是不是在真的"算"**。
> 📌 **综合案例投影（战役 2）**：YC 商城大促预演，网关 CPU 95% 告警，扩容 3 倍无效（CPU 还是 95%）。top 看 user 99%——Async Profiler 定位 `ConcurrentHashMap.get` 占 65%，根因是**促销价目表的 key 没重写 hashCode，哈希碰撞链表化**（修 1 行，CPU 95% → 32%，缩容回原规模，省 3 倍机器）。
> 🌐 **跨平台覆盖**：服务端 JVM（Async Profiler/JFR/perf）· Go（pprof）· Node（--prof/V8）· Android（Perfetto/simpleperf）· iOS（Instruments）
> 🧠 **一句话心法**：**CPU 100% 不是答案，是开始**。

### 01.开篇灵魂拷问
- 1.1 "CPU 100% 就是算得多吗？"——真伪算力之惑（YC 网关扩容无效的教训）
- 1.2 "火焰图最宽的函数就是瓶颈吗？"——采样偏差之惑
- 1.3 "多加机器为什么不解决？"——锁与同步之惑

### 02.CPU 的真实视角
- 2.1 user / sys / iowait / steal / softirq 各自是什么
- 2.2 CPU 占用率是如何采样出来的（/proc/stat）
- 2.3 Load Average ≠ CPU 使用率——Linux 的特殊语义
- 2.4 容器下的 CPU 幻觉：cfs_quota / cpu limit 隐形限流
- 2.5 面试锚点：**"top 的 %us 和 %sy 分别代表什么？什么时候 sy 高？"**

### 03.CPU 热点的"三类根因"
```
┌──────────────────────────────────────────────┐
│ ① 真算（Compute-bound）：算法复杂度 / 大循环   │
│ ② 伪算（Memory-bound）：Cache Miss / 伪共享    │
│ ③ 假算（Sync-bound）：锁自旋 / 空转等待          │
└──────────────────────────────────────────────┘
```
- 3.1 三类根因的采样特征差异（IPC / cache-miss / context-switch）
- 3.2 识图：perf stat 一眼分辨"真算 vs 伪算 vs 假算"
- 3.3 典型例子对照：JSON 解析 / 遍历大数组 / `synchronized`
- 3.4 面试锚点：**"CPU 100% 怎么判断是算得多还是锁竞争？"**

### 04.采样 vs instrumentation 与火焰图
- 4.1 两种原理的根本差异
- 4.2 采样的误差来源：时间偏差、**安全点偏差**（Safepoint Bias）
- 4.3 instrumentation 的开销：方法入口/出口埋点的字节码膨胀
- 4.4 火焰图的读法与误读（"宽度=耗时"的三个前提假设）
- 4.5 On-CPU vs Off-CPU 火焰图的本质区别
- 4.6 **差分火焰图**：定位版本间劣化的神器
- 4.7 🔬 深潜：火焰图颜色编码的工程含义

### 05.跨平台对照——同一个 CPU 热点，五个运行时的长相
| 平台 | 运行时 | 主战工具 | 采样机制 | 特有坑 |
|---|---|---|---|---|
| 服务端 JVM | JIT（C2） | Async Profiler · JFR · arthas | SIGPROF / **AGCT** | Safepoint Bias |
| Go | AOT | pprof（CPU） | SIGPROF | runtime 函数干扰读图 |
| Node | V8 JIT | `--prof` · Chrome DevTools | V8 Sampling Profiler | GC 线程单列 |
| Android | ART JIT+AOT 混合 | Perfetto · simpleprof · Studio Profiler | perf_events | 省电模式降频干扰 |
| iOS | AOT（LLVM） | Instruments Time Profiler | kdebug/mach_msg | 符号化要 dSYM |

- 5.1 **JIT vs AOT 的热点差异**：解释执行的热点 ≠ 机器码热点——为什么 Java 优化前要先"预热"
- 5.2 同一业务逻辑五端对照：**JSON 解析**在 JVM（JIT 去虚化）/ Go（AOT 直接机器码）/ Node（V8 内置）/ Android（ART + native）/ iOS（Codable/第三方）的热点长相
- 5.3 **YC 商城实战**：网关（JVM）、订单（Go）、BFF（Node）三个服务同一晚各跑一次火焰图的对照解读
- 5.4 移动端特有：**CPU 降频与小核调度**——为什么手机上"同一段代码"时快时慢（big.LITTLE）
- 5.5 🔬 深潜：eBPF profile 为什么是未来（跨语言统一、内核级、零侵入）
- 5.6 面试锚点：**"Java 的火焰图和 Go 的有什么区别？"**

### 06.CPU 监控体系（四类采集）
| 方案 | 原理 | 开销 | 适用 |
|---|---|---|---|
| ① 周期采样（perf/pprof） | 定时信号打断取栈 | 1-5% | 生产常驻 |
| ② 事件采样（PMU/硬件） | CPU 性能计数器 | <1% | 底层分析 |
| ③ 全埋点（Instrumentation） | 字节码插桩 | 30-200% | 线下深排 |
| ④ 跟踪（Tracing/eBPF） | 内核钩子 | 2-10% | 系统级 |

- 6.1 四类方案的能力矩阵对比（为什么只有四类——穷举完的理由）
- 6.2 🔬 深潜：PMU 硬件事件（IPC / cache-miss / branch-miss）

### 07.分层治理（按 ROI）

## 8.3 内存监控与治理——从"看不见"到"看得见、守得住"

> 🎯 **核心矛盾**：**GC ≠ 没内存问题**，而且现代内存问题比 malloc/free 时代**更隐蔽**——分配风暴、驻留集爆、缓存失控、堆外泄漏、LRU 失守。
> 📌 **综合案例投影（战役 3）**：YC 商城 Android 端低端机 OOM 率 8.3%（2GB 机型差评重灾区）；服务端订单 JVM "每天凌晨 1 点 OOM 重启"。双线排查：端上 LeakCanary + KOOM 治理泄漏/抖动/溢出；服务端 Heap Dump 找不到泄漏对象——真相是 **Netty Direct Buffer 没 release**，堆内平稳、RSS 一路涨。端云两线收官：**端上 OOM 8.3% → 0.4%，服务端 RSS 8GB → 3GB 稳定**。
> 🌐 **跨平台覆盖**：服务端 JVM（MAT/JFR/NMT）· Go（pprof heap）· Node（heap snapshot）· Android（LeakCanary/KOOM）· iOS（ARC/Instruments/MLeaksFinder）
> 🧠 **一句话心法**：**堆看着没问题，RSS 可能已经爆了**。

## 8.4 线程调度与并发性能优化——锁竞争才是慢的真正源头

> 🎯 **核心矛盾**：**线程多 ≠ 快，CPU 不高也可能很慢**——真正的敌人是锁竞争、线程泄漏、上下文切换、优先级倒置。
> 📌 **综合案例投影（战役 4）**：YC 商城下单链路压测 QPS 卡死 1200，网关 CPU 只有 40%、内存正常——"资源全绿却上不去"。jstack 抓 3 次快照：90% 工作线程 BLOCKED 在**库存服务的全局库存表锁**（`synchronized` 保护整个 HashMap）。分段锁 + 本地预扣 + 读写分离改造后 **QPS 1200 → 8500（7×，不加一台机器）**。
> 🌐 **跨平台覆盖**：Java（jstack/JFR/Async Profiler）· Kotlin 协程 · Go（GMP/pprof block·mutex）· Node（事件循环/clinic）· Swift（actor/Instruments）· Android（Perfetto）
> 🧠 **一句话心法**：**线程池慌，不如锁改良**。

## 8.5 I/O 与存储性能优化——存储延迟跨 7 个数量级

> 🎯 **核心矛盾**：从寄存器 1ns 到 HDD 10ms，**存储延迟跨 7 个数量级**；但代码里的 `read` 看上去都一样——不懂物理的优化都是蒙的。
> 📌 **综合案例投影（战役 5）**：YC 商城大促预演 2 小时后，订单库写 TPS 从 50 万跌到 5 万，CPU/网络正常——iostat 看到 `await` 2ms → 80ms，blktrace 定位到**审计日志每次 write 都 fsync**（新上的合规需求）。攒批 fsync + 慢查询治理后 **TPS 恢复 48 万并 +30%**。移动端侧同步治理：配置读取从 SharedPreferences 全量写迁移 MMKV。
> 🌐 **跨平台覆盖**：Linux 服务端（iostat/blktrace/eBPF）· Android（SharedPreferences/MMKV/Perfetto）· iOS（APFS/Core Data/Instruments）· Web（缓存/IndexedDB）· DB（MySQL/PG/SQLite）
> 🧠 **一句话心法**：**所有 I/O 优化 = 更少 syscall + 更顺序访问 + 更合适缓冲 + 更批量刷盘**。

## 8.7 网络传输性能优化——首屏 2.3s 中 2.2s 是网络

> 🎯 **核心矛盾**：**延迟 ≠ 带宽**——一次首屏 800ms 里，真正"算"的时间可能只有 50ms，剩下 750ms 都在 DNS / TCP / TLS / RTT / 排队 / 重传。
> 📌 **综合案例投影（战役 7）**：YC 商城首屏 2.3s，服务端 RT 只占 80ms——瀑布图：DNS 400ms（运营商劫持 + 未用 HTTPDNS）+ TCP 200ms + TLS 300ms + **串行 3 个接口** 1.2s。预连接 + HTTPDNS + 合并请求 + 离线包四板斧 → **首屏 2.3s → 600ms，转化 +18%**。弱网专项：电梯/地铁场景超时率 15% → 2%（重试退避 + 优雅降级）。

## 8.9 包体与资源优化——冗余的四根源

> 🎯 **核心矛盾**：**冗余四根源**——代码冗余、资源冗余、依赖冗余、元数据冗余；但 90% 的"减包大会"只盯着资源，错过真正的大头。
> 📌 **综合案例投影（战役 9）**：YC 商城 APK 80MB，渠道下载转化连续 3 个月下滑。常规减图减到 72MB 就停滞——换方法：**R8 全量混淆 + 依赖替换（3 个全家桶 → 自实现）+ 字体子集化（10MB → 200KB）+ ABI 拆分 + Dynamic Feature（营销插件按需下发）**，一月降到 **55MB（下载转化 +23%，低端机崩溃 -40%）**。H5 同步：主 bundle 2.3MB → 480KB。
> 🌐 **跨平台覆盖**：Android（R8/APK Analyzer/App Bundle）· iOS（App Thinning/Bitcode）· Web（Tree Shaking/代码分割）· Flutter（--analyze-size）· RN（Hermes 字节码）

5. **跨平台钩子**：每篇至少 1 个跨平台面试题（Q13/Q14）+ 1 个跨平台答题模板

### B. 每篇必备的"面试通道"
- **开篇灵魂拷问**（3 问破直觉，从 YC 商城现象切入）
- **每节末面试锚点**（简短 Q&A 嵌入章节内）
- **面试高频追问**（11-14 个，含跨平台对比题）
- **模拟面试模板**（5 个背诵级答题：90 秒电梯 + STAR + 决策树 + 跨平台答法）

### C. 每篇必备的"原理深潜"（🔬）
- 2-6 个 🔬 标记小节，给**资深向**读者看"为什么能这么做"
- 深潜不干扰主线，初读可跳过，二读深读

### D. 卷首共享的"三对矛盾"
贯穿每一篇：
- **度量精度 vs 开销**（全采样精确但扰动大 ↔ 低频采样低开销但有盲区）
- **延迟 vs 吞吐**（p99 砍到 50ms ↔ QPS 翻倍）
- **一次性优化 vs 持续守住**（冲数据漂亮 ↔ CI 卡口永不回退）

### E. 跨篇互链规则
- 每篇末尾"**与下篇承接**"段 + YC 商城故事的连续钩子
- 遇到跨篇话题（如 8.3 内存 ↔ 4.5 GC；8.6 渲染 ↔ 5.3 渲染管线；8.8 启动 ↔ 7.1 编译）必须用相对链接 + 一句话差异说明（**本卷讲工程，彼卷讲原理**）
