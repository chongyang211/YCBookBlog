### 1.1 一份真实的性能报告

**旅程坐标**：本篇站在请求旅程的**并发同步站**。前几篇把单线程路径上的税都砍掉了（过界税、访存税、分配税），现在多线程并行工作，真正的新敌人登场：**同步**。线程们要共享缓存、共享计数器、共享连接池——每一处共享都是潜在的串行点。用户可感的症状是本篇最有辨识度的一种：**核没满、吞吐却上不去，且流量一涨 P99 非线性恶化**。

案例回到老朋友网关（02/05 篇的同款），第三轮体检——这次是业务量涨了 2 倍之后暴露的问题：

```text
QPS 目标    : 15,000       ← 大促扩容后的新指标
QPS 实测    : 7,400        ← 05 篇优化后到这里就顶死了
CPU user    : 41%          ← ⚠ 核只用了四成
CPU idle    : 47%          ← ⚠ 一半算力在睡觉，吞吐却上不去
P99         : 8.2 ms       ← ⚠ 05 篇优化后明明是 1.9ms，流量涨了 30% 就恶化 4 倍
futex 调用  : 11.2 万次/秒  ← ⚠ strace 里 futex 一家独大（02 篇埋的伏笔）
```

对应的处理代码骨架（问题藏在"看似正常"的共享设计里）：

```cpp
// gateway.cpp —— 路由缓存：所有 worker 线程都要查的共享表
static std::mutex cache_mtx;                              // ← 【嫌疑点 1】全表一把锁
static std::unordered_map<std::string, Route> route_cache;

Route lookup(const std::string& key) {
    std::lock_guard<std::mutex> g(cache_mtx);            //    32 线程全部过同一道闸
    auto it = route_cache.find(key);
    if (it != route_cache.end()) return it->second;      //    命中（99.9%）：纯只读，也互斥
    Route r = compute(key);                               // ← 【嫌疑点 2】miss 时 70μs 重活在锁内
    route_cache.emplace(key, r);
    return r;                                            // ← 【嫌疑点 3】读多写少，没有读优化
}

// 热路径监控埋点：每个 worker 都要加一下
static std::atomic<uint64_t> qps_counter{0};
qps_counter.fetch_add(1, std::memory_order_relaxed);      // ← 【嫌疑点 4】32 核对同一行 RMW
```

### 1.2 顺藤摸到根因

带着"核不满 + P99 非线性恶化 + futex 爆表"三条线索，立四个假设（本篇归因主线，第 5 章逐条验证）：

- **假设 1**：全表一把锁——**32 个线程的并行度被压缩成 1**，这正是"核不满吞吐却上不去"的物理原因。→ 引出 **Amdahl 定律与串行化账本**。
- **假设 2**：`compute()` 70μs 的重活发生在锁内——**临界区长度决定排队队伍的服务速率**，一个 miss 就把后面所有线程堵 70μs。→ 引出**排队论与临界区设计**。
- **假设 3**：99.9% 的命中是纯只读，却付了全量互斥的钱——**读多写少的结构没做读路径分层**。→ 引出**读写分离与双缓冲**。
- **假设 4**：`qps_counter` 一行数据被 32 个核同时 RMW——**原子操作不便宜，真共享的乒乓与 [03 篇](/pages/c75b18/)的伪共享同价**。→ 引出**原子操作的正确打开方式**。

## 2. 资源镜头：串行化经济学

### 2.1 并发的天花板：Amdahl 定律的账本

**通俗理解**：把程序分成"能并行的部分"和"必须串行的部分"（比如过同一把锁），加速比的天花板由**串行部分**死死焊住——**串行占比 5%，无论 8 核还是 800 核，最多快 20 倍**。

$$
S(N) = \frac{1}{s + \dfrac{1-s}{N}}
\qquad \text{（s = 串行占比，N = 核数）}
$$

```
串行 5%  →  N=8:  9.1x   N=32: 14.6x   N=∞: 20x   ← 天花板 20 倍
串行 1%  →  N=32: 24x    N=∞: 100x                 ← 天花板 100 倍
```

案例的直译：**一把全局锁把 route_cache 的访问变成 100% 串行段**——CPU 只用 41% 却加不动，因为 47% 的 idle 里大半是"拿着号在窗口前排队"的等待（02 篇：等待不占 CPU，但占时间）。

**疑惑**：排队等待真的是 idle 吗？P99 为什么**非线性**恶化？

**论证**（排队论直觉，本案例 P99 恶化的元凶）：
1. 把锁想成只有 1 个窗口的银行，线程是随机到达的顾客——**平均等待时间随利用率非线性暴涨**；
2. 粗略量级：窗口利用率 50% 时顾客几乎不等；**80% 时等待 ≈ 服务时长；90% 以上等待数倍于服务时长、且方差爆炸**；
3. 这解释了案例症状：流量 5700 时 P99=1.9ms（利用率低），流量涨 30% 后利用率逼近 90%——**P99 恶化 4 倍**，而均值只涨了一点；
4. 结论：**锁优化的本质是"压低串行段的利用率"**——缩短临界区（分母变小）、或拆分串行段（窗口变多）。

### 2.2 一次加锁的成本清单

用「资源×流水线」模型给 `pthread_mutex_lock` 记账（glibc，x86_64 典型量级，口径声明同前几篇）：

| 路径 | 触发条件 | 成本 | 发生了什么 |
|---|---|---|---|
| **快路径** | 无争用 | **~10-20ns** | 用户态 CAS 一条指令（见 3.1），零过界 |
| 自旋探测 | 有争用但很快释放 | ~100ns 级 | adaptive 锁先自旋几十次再决定 |
| **慢路径** | 争用持久 | **~1-3μs + 唤醒延迟** | futex 系统调用进内核睡眠（02 篇的入口费 + 切换税） |
| 唤醒后 | 前任刚释放 | 额外排队 | 新到者可能"插队"成功——又一场 RMW 争用 |

两个推论：
1. **无争用的锁几乎免费**（~15ns ≈ 一次 L2 访存）——所以"少用锁"的正确表述是"**少用被争用的锁**"；
2. **有争用的锁按"过界+切换"计价**（[02 篇](/pages/2f9a64/)成本表直接套用）——且成本大头不是锁本身，是**后面排队浪费的并行度**（Amdahl）。

### 2.3 等待藏在哪里：自旋、睡眠与阻塞的三角

**通俗理解**：等待有三种藏法，各有代价——**自旋**（站在窗口前空转喊号，烧 CPU 但拿得快）、**睡眠**（回座位等叫号，省 CPU 但付切换税 + 唤醒延迟）、**阻塞**（不占核也不进内核的第三态，Go runtime 的 sema 队列在用户态再排一层）。

```
自旋锁   响应最快      烧核；线程>核数时雪崩（持有者被抢占，自旋者替它烧钱）
互斥锁   省核、稳      睡眠/唤醒 ~1-3μs + 内核往返；短临界区时反而更慢
自适应   先自旋后睡眠   glibc PTHREAD_MUTEX_ADAPTIVE_NP 的默认哲学
```

这个三角是 3.2 节选型的全部依据。记住一条主线：**等待策略的本质是"押注临界区有多长"**——押对了免单，押错了双倍罚。

## 3. 同步机制

### 3.1 futex：快路径不过界的秘密

[02 篇](/pages/2f9a64/)留了个伏笔："争锁失败进 futex 睡眠——去第 07 篇报到"。现在兑现：**futex（fast userspace mutex）是 Linux 锁体系的基石**，它的天才之处是把锁拆成"用户态快路径 + 内核慢路径"：

```
加锁流程（pthread_mutex_lock 的真实路径）：

第一步（用户态）：CAS 把锁字 0 → 1
   ├─ 成功 → 拿锁走人，零系统调用（~15ns）← 99% 的加锁止步于此 ✔
   └─ 失败 → 有竞争，进入第二步

第二步（用户态）：adaptive 自旋几十次
   ├─ 期间拿到 → 省了一次系统调用                      ← 押注"临界区很短"
   └─ 还没拿到 → 进入第三步

第三步（过界）：futex(FUTEX_WAIT) 系统调用
   内核把本线程挂到"以锁地址哈希索引"的等待队列 → 睡眠（02 篇的自愿切换）

解锁：CAS 1 → 0；若锁字记录了等待者 → futex(FUTEX_WAKE) 唤醒一个
```

三条机制性认知：
1. **无争用不过界**——与 vDSO（02 篇免税通道）同构：**把最常见的情况做成最便宜的路径**，futex 只是内核替你扛"最坏情况"；
2. **等待队列按锁地址哈希**——内核不认识你的 mutex 对象，只认地址；所以锁字必须在你 munmap 之前释放完，否则唤醒丢失（use-after-free 的并发版，ASan 都难抓）；
3. **案例里 futex 11.2 万/秒的直译**：32 线程 × 每秒几百次慢路径加锁——**每一次都是一次"过界 + 睡眠 + 唤醒"的全价票**，这正是 sys 时间和 P99 同时恶化的账单。

### 3.2 mutex 与 spinlock 的分水岭

| 场景 | 选型 | 理由 |
|---|---|---|
| 临界区 ~百 ns 级（改个链表头、更新状态）且 线程数 ≤ 核数 | **spinlock** | 睡眠的切换税（1-3μs）比自旋等待本身还贵 |
| 临界区 μs 级以上 | **mutex** | 自旋烧核的时间已超过睡眠成本 |
| 可能睡眠/做 IO/调用未知代码 | **必须 mutex** | 自旋者会陪着持有者一起睡死 |
| 线程数 > 核数 | **mutex（禁区：spin）** | 见下面"雪崩机制" |

**spinlock 的雪崩机制**（面试高频，务必讲得出机制）：线程 A 持锁跑到一半被调度器换下台（时间片到期），自旋等待的线程 B 在另一个核上**替 A 烧 CPU**——B 的整个时间片都空转，A 永远拿不回 CPU 去释放锁。线程数越超核数越惨烈，这就是分水岭表最后一行的"禁区"。内核态 spinlock 之所以能安全自旋，是因为它**顺手关了抢占**（持有者保证不被换下台）——用户态锁没有这个特权。

### 3.3 读写锁与双缓冲：读路径的分层设计

**通俗理解**： mutex 对"读"和"写"一视同仁地互斥——但 99.9% 命中的纯读查询，逻辑上**根本不冲突**。读路径分层的四个段位：

```
段位 1  std::mutex             读写互斥——最低段位（案例现状）
段位 2  std::shared_mutex      读共享、写独占——读并行了，但每次读仍有 RMW 计数开销
段位 3  seqlock（顺序锁）      读完全无锁（读前后比对版本号，写者递增）——写短读快适用
段位 4  双缓冲 / RCU           读路径就是一次原子 load，写者另建副本后原子切换
```

段位 4 的双缓冲是"读多写少 + 读极致敏感"场景的终局方案（6.3 节完整展开）；RCU（Read-Copy-Update）是 Linux 内核的招牌——读者完全不感知锁，写者复制修改后**延迟回收**旧版本（等所有读者离开临界区）。用户态可借用思想（`shared_ptr` 换指针 + 智能指针自动延迟释放），完整 RCU 语义用 liburcu。

**注意段位 2 的坑**：读写锁在读极多时**写者饥饿**（一直有新读者插进来），且每次 reader_lock 也是一次同一行的 RMW——**高并发读本身也会在这一行上乒乓**。所以"读路径零锁"（段位 3/4）才是高频读的归宿。

### 3.4 原子操作：真共享的乒乓

案例【嫌疑点 4】：32 个核对同一个 `qps_counter` 做 `fetch_add`。这是 [03 篇](/pages/c75b18/)伪共享的孪生兄弟，两者账单同源，病因相反：

| | 伪共享（03 篇） | 真共享（本篇） |
|---|---|---|
| 现象 | 多核写**不同变量**、同行 | 多核写**同一变量** |
| 病根 | 变量恰好挤在同一缓存行 | 变量本身就是共享点 |
| 解法 | 对齐/填充，把变量分开 | 分片，把写点分开（6.4 节） |
| 硬件本质 | MESI 按整行广播，无辜者陪绑 | RMW 必须独占整行，天然串行化 |

RMW（read-modify-write）的硬件代价：`fetch_add` 要把缓存行置为独占态（其他核副本全失效）→ 修改 → 视情况写回——**无争用时 ~10-20ns，32 核争用时每次几百 ns 起跳**（一行在核间轮流独占，乒乓税与伪共享同价）。

**memory order 注脚**（面试常考，一句话版）：`relaxed` 只保证原子性不保证顺序（计数器够用、最快）；`acquire/release` 建立同步关系（锁的基石）；默认 `seq_cst` 全局全序（最保守最慢）。**计数器写 `relaxed`、读的时候自然能看到最终值**——案例代码这一步是对的，但再"对"也架不住一行 32 核 RMW。

## 4. 临界区：锁的暗税

### 4.1 锁内干重活：排队雪崩

**通俗理解**：临界区是**串行段**——里面每多待 1μs，队伍里每个人都多等 1μs。锁内 70μs 的 `compute()` 意味着：一个 miss 请求可以把其他 31 个线程全部堵 70μs（31 × 70μs ≈ 2.2ms 的并行度蒸发）——P99 的直接来源。

**锁内禁做清单**（违反一条都是事故候补）：

```text
锁内禁做： IO 与远程调用（毫秒级持锁 = 全员冻结）
          sleep / 等条件变量（应改用条件变量，锁只护数据）
          大计算（compute 应搬到锁外，见 6.1）
          再拿别的锁（锁的嵌套是死锁候补，[死锁四条件]见 11 章高频题）
          内存分配（[05 篇]分配器自身有锁——锁中锁，放大争用）
```

**护航效应（convoy）**——比长度更隐蔽的坑：持锁线程被调度器换下台后，**整条队伍既不前进也不能睡**（队列头在等一个不在线的持有者）。高负载下这会造成 P99 与均值脱钩的长尾—— mitigation 是减小临界区 + 优先级不做花活（实时线程持锁被普通线程堵死的"优先级反转"，Linux 用 PI futex 修复，一句话带过）。

### 4.2 一把大锁的排队现场

把案例抽象成单窗口银行：

```
32 线程 ──┐
          ├──► [ 一把全局锁 ] ──► route_cache（共享表）
          │      唯一窗口，服务速率 = 1/临界区长度
          └── 到达率（QPS × 锁访问次数）逼近窗口速率
               → 利用率 > 90% → 等待时间非线性爆炸（2.1 节的 P99 恶化）

修复后的形态（6.2 节）：
32 线程 ──┬──► 锁0 → shard0（key 哈希分 16 片）
          ├──► 锁1 → shard1     16 个窗口，利用率摊薄到 6%
          └──► ...              即使单窗口速率不变，等待时间数量级下降
```

粒度优化的光谱：**全表一把锁 → 分段锁（16 片）→ per-key 锁 → 无锁（读路径零 RMW）**——光谱右端不是免费午餐（7.3 节误区三），但每右移一格，串行段就拆小一分。

### 4.3 动手实验：争用阶梯眼见为实

**实验 A：争用阶梯**——同一份工作，一把锁 vs 各写各的（10 分钟可复现）：

```c
// ladder.c —— N 线程抢一把 mutex vs 各自独立计数
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
enum { LOOPS = 2 * 1000 * 1000 };
static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
static long shared_v;
static void* work_shared(void* _) {
    for (int i = 0; i < LOOPS; i++) {           // 一把锁：串行段
        pthread_mutex_lock(&mtx); shared_v++; pthread_mutex_unlock(&mtx);
    } return NULL;
}
static void* work_local(void* arg) {
    long v = 0;
    for (int i = 0; i < LOOPS; i++) v++;        // 各写各的：无串行段
    return (void*)v; (void)arg;
}
static double run(void* (*fn)(void*), int n) {
    pthread_t t[32]; struct timespec a, b;
    clock_gettime(CLOCK_MONOTONIC, &a);
    for (int i = 0; i < n; i++) pthread_create(&t[i], 0, fn, 0);
    for (int i = 0; i < n; i++) pthread_join(t[i], 0);
    clock_gettime(CLOCK_MONOTONIC, &b);
    return b.tv_sec - a.tv_sec + (b.tv_nsec - a.tv_nsec) / 1e9;
}
int main(void) {
    for (int n = 1; n <= 16; n *= 2)
        printf("线程 %2d：抢锁 %.2fs   独立 %.2fs   （同样的活，差 %.1f 倍）\n",
               n, run(work_shared, n), run(work_local, n),
               run(work_shared, n) / run(work_local, n));
    return 0;
}
```

```bash
gcc -O2 ladder.c -o ladder -pthread && ./ladder
# 典型形态：
# 线程  1：抢锁 0.01s   独立 0.005s    （单线程差距不大——快路径本来就便宜）
# 线程  8：抢锁 0.19s  独立 0.006s    （差 30 倍：串行段焊死了并行度）
# 线程 16：抢锁 0.40s  独立 0.006s    （线程翻倍只换来时间翻倍——纯排队）
# ↑ 抢锁列"不随核数加速"就是 Amdahl 定律的活体展示

# 顺手观测争用的 futex 显影（对比 1 线程与 16 线程）
strace -f -c ./ladder 2>&1 | grep futex     # 多线程档 futex 调用数万次
```

### 4.4 度量第二刀：off-CPU 等待归因

CPU 视角的工具（perf top）只看得见"在烧核的自旋"——**睡眠等待根本不出现在火焰图上**。等待要换一套工具：

```bash
# 锁级统计（依赖内核 lockdep 事件，开销 2-10 倍——开发环境专用）
perf lock record -p $(pidof gateway) -- sleep 10 && perf lock report
#   输出每把锁的 contended 次数与等待总时长——锁的"病历本"

# futex 等待直方图（bpftrace 一行流，eBPF 嗅探）
bpftrace -e 'tracepoint:syscalls:sys_enter_futex /args->op==0/ { @ts[tid]=nsecs; }
  tracepoint:syscalls:sys_exit_futex /@ts[tid]/ {
    @wait_us = hist((nsecs - @ts[tid]) / 1000); delete(@ts[tid]); }'
#   @wait_us 直方图：等待时长的分布形态——中位数微秒级、长尾毫秒级
#   即"锁等待在偷 P99"的实证（直方图读法：[256, 512) 那一列越高越危险）

# 02 篇的第四刀在此复用：perf sched latency 看线程"睡了多久才被叫醒"
perf sched record -p $(pidof gateway) -- sleep 10 && perf sched latency --sort max
```

**off-CPU 三件套的分工**：`perf lock` 看锁的病历、`bpftrace` 看等待的分布、`perf sched` 看调度的账本——三者合围，把"核不满但慢"的隐形等待全部显影。

## 6. 优化策略

### 6.1 策略一：缩小与外移——锁内只做必须的事

**通俗理解**：锁只护"会互相踩的数据操作"，其余一切搬出闸口——**先算后锁再核对**（compute-then-lock-then-recheck）：

```cpp
// ❌ 修复前：70μs 重活在锁内，31 个线程陪着
std::lock_guard<std::mutex> g(cache_mtx);
auto it = cache.find(key);
if (it != cache.end()) return it->second;
Route r = compute(key);              // ← 闸口里干重活
cache.emplace(key, r);

// ✅ 修复后：重活搬到锁外，锁内只做"登记"（微秒级）
Route r = compute(key);               // ① 锁外重活（并行度保留）
{   std::lock_guard<std::mutex> g(cache_mtx);
    auto [it, inserted] = cache.try_emplace(key, r);  // ② 锁内只写表
    return inserted ? r : it->second;                   // ③ 别人抢先算了？用现成的
}
// 这就是"先算后锁再核对"——经典模式，DCLP 的无坑版本
```

### 6.2 策略二：分片——N 把小锁代替一把大锁

```cpp
// ✅ 16 片分段锁：key 哈希到固定片，不同片天然并行
struct Shard { std::mutex mtx; std::unordered_map<std::string, Route> map; };
static std::array<Shard, 16> shards;              // 片数 = 2 的幂（掩码取片）

Shard& s = shards[std::hash<std::string>{}(key) & 15];
std::lock_guard<std::mutex> g(s.mtx);             // 32 线程 → 平均每片 2 个竞争者
auto it = s.map.find(key);                        // 银行从 1 窗口变 16 窗口（4.2 节现场图）
```

三条工程分寸：
1. **片数不是越大越好**——超过"并发线程数"后再加片只涨内存不降争用；经验起点 = 核数的 2-4 倍；
2. **跨片操作是分片的死穴**——需要"遍历全表/原子迁移"的逻辑要用两阶段（先在各片内快照，锁外合并）；
3. 分片与 [03 篇](/pages/c75b18/)联动：每片独立后，**片与片不在同一缓存行**（`alignas(64)` 垫一下），避免"锁乒乓"与"伪共享"叠加。

### 6.3 策略三：双缓冲——读路径零锁

**通俗理解**：读多写少的共享表，最狠的招是**让读者根本不知道锁的存在**——表有新旧两份，读者永远读"当前指针"（一次原子 load，~几 ns），写者改完**整体换指针**：

```cpp
// ✅ shared_ptr 快照：读 = 一次原子 load；写 = 构建新表 + 原子换指针
static std::shared_ptr<const RouteTable> g_table;   // 智能指针，读者拿的是"快照"

Route lookup(const std::string& key) {
    auto snap = std::atomic_load(&g_table);         // ① 读者：锁不可见，拿到整表快照
    return snap->at(key);                           // ② 读快照——哪怕写者正在换表也不怕
}
void rebuild() {                                     // 写者：后台定时/配置变更时
    auto fresh = std::make_shared<RouteTable>(build_new_map()); // ③ 锁外建新表
    std::atomic_store(&g_table, fresh);             // ④ 一次原子换指针，读者瞬间"换频道"
}   // 旧表由最后一个读者用完自动析构（shared_ptr = 天然延迟回收，RCU 的穷人版）
```

效果：**读路径零锁零 RMW**（连 3.3 节读写锁的 reader 计数开销都省了）；代价：写要整表重建（内存双份瞬时峰值，[05 篇](/pages/5a2f87/)的账要算清）。适用判据：**读：写 ≥ 1000:1、表可整体重建**——案例（路由表几小时才变一次）完美命中。C++20 可直接用 `std::atomic<std::shared_ptr<T>>`，旧标准用 `std::atomic_load/store` 自由函数。

### 6.4 策略四：计数分片——让原子操作各写各的

```cpp
// ❌ 修复前：32 核对同一行 RMW（3.4 节真共享乒乓）
qps_counter.fetch_add(1, std::memory_order_relaxed);

// ✅ 修复后：thread_local 各写各的，读取时合并（03 篇 Counters 案例的正式答案）
static thread_local uint64_t tl_hits = 0;      // 每线程私有的行（无争用）
++tl_hits;                                     // 热路径：普通 ++，连原子指令都没有

uint64_t total_hits() {                        // 低频读取（每秒一次）才合并：
    // 遍历各线程的 slot 求和（注册表机制：线程启动时登记自己的 slot 指针）
    for (void** p : registry) sum += *(uint64_t*)p;
    return sum;
}
```

分寸与边界：**写极热、读极冷**（监控埋点、统计计数）是它的主场；反过来"读也热"的场景（限流器每次请求都要读精确值）不能这么存——那是 [10 篇]限流算法的领地。顺带兑现 [05 篇](/pages/5a2f87/)的伏笔：CAS 无锁栈在**高争用**下会互相"挤掉"对方的 CAS（活锁），解法是退避（backoff，抢失败就 sleep 一小段随机时间）——低争用无锁是银弹，高争用无锁需要排队（如 MCS 锁），工程上通常"分片 + 各写各的"更简单可靠。

### 6.5 并发度 sizing：Little 定律的供给账本

线程池开多大？给一个可背诵的公式（**Little 定律**，排队论皇冠上的明珠）：

$$
L = \lambda \times W \qquad \text{（并发度 = 到达率 × 单件耗时）}
$$

| 场景 | 计算 | 结论 |
|---|---|---|
| 纯 CPU 计算（120μs/请求） | 15000 QPS × 0.00012s = **1.8** | 8 核开 8 线程绰绰有余 |
| 含 1ms 下游 IO | 15000 × 0.001 = **15** | 8 线程不够，需 16-24（IO 等待靠线程填） |
| 混合负载 | 按阻塞系数分池：CPU 池 + IO 池 | 各算各的 L，别一锅炖 |

三条纪律：
1. **并发度是"需求"（L），线程数是"供给"**——供给略大于需求即可，超配的部分只交切换税（[02 篇](/pages/2f9a64/)误区二在此闭环）；
2. **W 用 P99 而不是均值估**——供给按均值配，长尾请求一来就积压；
3. **事件循环模型（epoll）把"IO 等待的线程"换成了"复用"**——少量线程 + 高效复用 = 既填满 W 又不交切换税，这就是 [09 篇](/pages/f82b04/)C10K 解法的排队论本质。

| __lll_lock_wait CPU | 28% | **<1%** | 热点整体消失 |
| CPU idle | 47% | **18%** | 排队的人去干活了 |
| 长尾（4-8K μs 等待列） | 412 次/10s | **0** | 护航效应消失（分布图验收） |

读数要点：**idle 从 47% 降到 18% 不是坏消息**——原来那 29% 是"排队空闲"，现在是"干活的忙"；这也再次验证 02 篇的教训：**CPU 利用率会骗人，吞吐和分布才不会**。

## 7. 常见误区清单

### 7.1 误区一：粗锁省心又够快

**现场**："加一把大锁最安全，性能不行再优化"——结果大锁进了核心路径，劣化时没人敢动它。

**破除**：
1. 大锁的**非线性排队**（2.1 节）让"够快"的结论随流量失效——昨天没事，今天大促就 P99 爆炸；
2. 正确姿势：**按数据分片定义锁的边界**（6.2 节），从第一天就让 key 哈希决定谁等谁；
3. 锁设计是"先想清楚谁会争"，而不是"先锁上再说"——争用地图（哪条路径高频过哪把锁）比锁本身重要。

### 7.2 误区二：自旋锁总是更快

**现场**：听说 mutex 要进内核，把所有锁换成 spinlock，压测反而更慢。

**破除**：
1. 无争用时两者都在用户态、都 ~15ns（3.1/3.2 节）——换型收益为零；
2. 有争用时 spinlock 的雪崩机制（持有者被抢占、等待者替烧 CPU，3.2 节）只有在**线程 ≤ 核且临界区极短**才不触发；
3. 判据背下来：**临界区 < 2 × 上下文切换成本 且 线程 ≤ 核数**——两个条件都满足才考虑 spin，其余一律 mutex。

### 7.3 误区三：无锁编程是银弹

**现场**：把分片计数改成无锁链表，benchmark 涨了 5%，两周后排查一个诡异的偶发丢数据。

**破除**：
1. 无锁结构的正确性门槛远高于锁：**ABA 问题**（指针被改走又改回，CAS 误判没变过）、memory order 选错导致的撕裂读、回收难题（谁敢删节点？）——每一项都是"平时没事、压测偶现"的生产事故候补；
2. 性能上高争用无锁会退化（05 篇伏笔的活锁），**很多"无锁更快"的对比，其实是"无争用 vs 有争用"的对比**——先分片把争用降下来，锁和无锁的差距就消失了；
3. 决策顺序：**先消争用（分片/双缓冲）→ 再看是否还需要无锁**——大多数场景走到第二步就停了。

### 7.4 误区四：原子操作是免费的

**现场**：把 `mutex + counter` 换成 `atomic counter` 就宣布"无锁优化完成"。

**破除**：
1. RMW 原子不是免费的——**无争用 ~10-20ns，32 核争用几百 ns 起**（3.4 节），比锁的快路径贵不了多少时也一样会成瓶颈；
2. `atomic` 只是消了"锁的语义"，没消"共享的物理"——一行还是那一行，乒乓照打；
3. 真正的答案还是**分片**（6.4 节）：`thread_local` 普通自增 + 低频合并——连原子指令都省了。**无锁的最高境界是"无共享"**，不是"无锁字"。

### 9.1 一次请求的同步足迹

```
修复前（查一次路由表）：
  lock(全局锁) ──► 命中？find 返回 ──► unlock ──► 计数器 RMW（32 核同行）
        │
        └─ miss 时：锁内 compute 70μs → 31 线程排队 → futex 睡眠 → 唤醒 → 再抢
修复后：
  atomic_load(表快照) ──► 纯读零锁 ──► tl_hits++（各写各的，无原子）
        │
        └─ miss 时：锁外 compute → 16 片之一 try_emplace（平均竞争者 2 个）
```

### 9.2 设计哲学回扣

**哲学 1：串行化是并发的头号敌人——一切账都从串行段长度算起**

Amdahl 焊天花板（2.1 节）、排队非线性引爆 P99、锁内禁做清单（4.1 节）——三个视角一条主线：**锁优化的 KPI 是"串行段利用率"**，不是"锁快不快"。评估任何同步设计，先问两个问题：临界区多长？有多少人排队？

**哲学 2：快路径不过界——futex 与 vDSO 是同一个思想**

[02 篇](/pages/2f9a64/)哲学二的第三次登场：vDSO 把最常问的答案放进用户态、[05 篇](/pages/5a2f87/)把最常用的块放进线程缓存、futex 把最常见的加锁做成一条 CAS——**"最常见的事最便宜"是系统设计的普适律**。识别一个设计的优劣，就看它的快路径覆盖了多少比例。

**哲学 3：结构消灭锁——最好的锁是不存在的锁**

分片让"不同 key 天然不冲突"（6.2）、双缓冲让"读永远无锁"（6.3）、thread_local 让"写各写各的"（6.4）——**同步成本是被数据组织方式决定的**，这与 [03 篇](/pages/c75b18/)"布局决定性能"同构：物理层（缓存行/MESI）只是执行者，胜负在设计层就定了。

### 9.3 速查表

**成本速记**（数量级，口径同前几篇）：

## 10. 跨语言对照

### 10.1 C++ / Rust / Go 三栏速查

| 关注点 | C++ | Rust | Go |
|---|---|---|---|
| 互斥锁 | std::mutex | parking_lot::Mutex / std::sync::Mutex | sync.Mutex |
| 读写锁 | std::shared_mutex | parking_lot::RwLock | sync.RWMutex |
| 自旋锁 | std::atomic_flag | std::sync::spin_lock（实验性）/ spin crate | 无（runtime 不鼓励） |
| 原子类型 | std::atomic | core::sync::atomic | sync/atomic |
| 双缓冲 | atomic\<shared_ptr\> | arc-swap crate（工业标配） | atomic.Value |
| 无锁队列 | folly / boost::lockfree | crossbeam（有 GC 语义的 epoch 回收） | 无标准（channel 替代） |
| 尺寸语义 | 一把锁一个计数（64 位） | poisoning 检测死锁痕迹 | sema 结构（内含计数+等待队列） |
| 底层等待 | futex | futex（parking_lot 直接用） | runtime sema → futex（Linux） |

三栏一个共同点：**三家的"锁"在 Linux 上殊途同归落到 futex**——语言层锁只是语义包装（Rust 的 poisoning、Go 的 sema 结构），物理层是同一套机制。

### 10.2 Go 的 channel 哲学

**通俗理解**：Go 的口号是"**不要通过共享内存来通信，而要通过通信来共享内存**"（CSP）——channel 看似消除了锁，实际是把"锁+队列+数据拷贝"打包成了一个原语：

1. **channel 底层不是魔法**：`sync.Mutex` + 环形缓冲 + goroutine 等待队列（runtime 的 sema），无缓冲 channel 就是一把"拷贝式的锁"——单次操作代价 = 锁 + 一份拷贝；
2. **它消灭的是"锁的误用"而不是锁**：把"谁该持有数据"从竞态问题变成"队列里流动的消息"问题——语义上的胜利（正确性），物理上竞争仍然存在（性能）；
3. 工程含义：channel 适合**数据所有权流转**（生产者→消费者）；**高频计数、读多写少的表**，Go 还是要回到 `sync.RWMutex` / `atomic.Value`——本篇的四策略在 Go 里一条不少（`atomic.Value` 就是 6.3 双缓冲的标准库版）。

### 11.2 两道满分答案示范

**示范一：「讲讲 mutex 的底层原理」**：

> "现代 Linux 上的 mutex 核心是 **futex**——fast userspace mutex（定义）。加锁分两层：**快路径在纯用户态做一次 CAS**，把锁字从 0 换成 1，成功就直接拿锁，大约 10-20 纳秒，完全不进内核——因为绝大多数加锁其实没有竞争，这条路径覆盖了 99% 的场景（物理路径+数字）。CAS 失败才走**慢路径**：glibc 的 adaptive 锁会先自旋几十次，赌持有者马上释放；赌输了才调 `futex(FUTEX_WAIT)` 系统调用，内核把这个线程挂到按锁地址哈希的等待队列上睡眠；解锁时如果发现有等待者，再 `futex(FUTEX_WAKE)` 唤醒（机制展开）。所以**锁的成本取决于争用**：无争用 ~15ns，有争用就是一次过界加一次切换，微秒级起步。我们网关踩过一个坑：一把全局路由锁在流量涨 30% 后 P99 从 1.9ms 恶化到 8.2ms，strace 里 futex 占了 79% 的系统调用——后来用双缓冲把读路径的锁整个消掉了（亲历闭环）。"

**示范二：「自旋锁和互斥锁怎么选？」**：

> "判据一句话：**临界区长度乘上争用概率，和一次上下文切换成本比大小**（定义直给）。自旋的代价是烧 CPU 等待，睡眠的代价是切换税 1-3μs 加唤醒延迟——临界区只有百纳秒级、线程数不超过核数时，睡眠的成本远大于等待本身，自旋赢；临界区到微秒级以上就反过来（方案边界一）。但自旋有个**雪崩机制**要单独讲：如果线程数超过核数，持有者可能被调度器换下台，自旋者会在别的核上替它烧 CPU，等到自己时间片用完还没等到——多超一个核就惨烈一分，所以**线程数大于核数时自旋锁是禁区**（方案边界二）。glibc 的 adaptive mutex 就是这个权衡的工程化：先自旋几十次，不行再睡。我做过阶梯实验：16 线程抢一把 mutex 对比各写各的计数，差 60 倍——同样的活，串行段把并行度焊死了（数字+实验）。所以我的默认选择是 mutex，只在'临界区极短 + 线程受控 ≤ 核数'的热点位置上自旋，而且必须带实验数据再上（分寸）。"

### 11.3 反向提问与加分项

**反向提问**：

- "团队的锁设计有'争用地图'或锁评审流程吗？热路径加锁要走什么评审？"
- "线上有 futex 或锁等待的监控吗？P99 恶化时第一反应查什么？"

**加分项清单**：

1. **讲得出非线性**：排队等待在利用率 90% 后暴涨——把"P99 与均值脱钩"归因到排队论，而不是背"锁慢"；
