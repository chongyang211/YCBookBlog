# Linux 性能优化实践

> 性能不是优化出来的，是体系守护出来的——本专栏共 10 篇，面向 **Linux 应用开发者**（用户态视角），把「资源×时间×流水线」模型翻译成系统调用、cache line、futex、page cache 的物理机制，配上 perf、火焰图、eBPF 工具链与实战代码。

## 一、专栏总览

```text
┌─ Linux 性能优化实践（10 篇）────────────────────────┐
│  按一次请求的物理旅程推进：                        │
│                                                    │
│  请求到达 ──► 系统调用与调度 ──► CPU 执行           │
│      │                                             │
│      ▼                                             │
│  编译产物 ──► 内存分配 ──► 页与NUMA                 │
│      │                                             │
│      ▼                                             │
│  并发同步 ──► 文件IO ──► 网络与零拷贝               │
│      │                                             │
│      ▼                                             │
│  底线守护 ─► 尾延迟与防劣化                         │
│                                                    │
│  篇篇带「现象→度量→归因→优化→防劣化」闭环           │
└─────────────────────────────────────────────────────┘
```

**专栏定位**：用户态应用开发者视角（C/C++ 服务端/系统程序）——讲"应用如何与内核高效协作"，不讲内核调优、驱动与运维巡检。

## 二、设计原则：三线融合

10 篇在三个粒度上各用一条组织线索，而非简单拼盘：

- **旅程线定排序**：从"请求到达"到"尾延迟守护"，篇目顺序即一次请求的物理路径；
- **资源线定内核**：每篇用「资源×流水线」模型给出物理归因框架（资源镜头）；
- **闭环线定结构**：每篇按「现象→度量→归因→优化→防劣化」五步展开，篇篇独立可查。

**每篇统一体例（四件套）**：

```text
┌─ ① 旅程坐标 ── 本篇在请求旅程哪一站？可感症状是什么？
├─ ② 资源镜头 ── 「资源×流水线」物理模型，分【应用层 / 内核与硬件层】双栏
├─ ③ 五步闭环 ── 现象→度量→归因→优化→防劣化，每步配 perf/strace/eBPF 实操
└─ ④ 跨语言对照 ── C++ / Rust / Go 三栏速查（同一机制的语言层封装差异）
```

**Linux 卷独有设计**：

- **双层归因**：应用慢，可能是你的代码、也可能是"内核替你做的事"（调度、页回收、futex 等待）——每篇资源镜头分两栏，先分清"该改代码还是该改用法"；
- **工具前置**：Linux 没有 GUI 一体化工具，perf/火焰图/eBPF 是一切归因的起点——第 1 篇工具箱权重比 iOS/Web 卷更重；
- **抖动源清单**：服务端最痛的 P99 抖动有专属排查手册（收官篇）。

## 四、选题说明

**10 篇构成**：总览 1 篇（作战地图）+ CPU 链路 3 篇（系统调用/缓存/编译）+ 内存链路 2 篇（分配器/页表 NUMA）+ 同步 1 篇（锁）+ IO 链路 2 篇（文件/网络）+ 收官 1 篇（尾延迟防劣化），覆盖 Linux 应用性能的全部主干考点。

**三个特色选题的理由**：

| 选题 | 为什么值得独立成篇 |
|---|---|
| 编译与链接优化 | "不改一行代码的提速"——-O2 与 -O3、LTO/PGO 的差距常超 20%，且与源码优化（第 3 篇）是两条独立路径 |
| 页表与 NUMA | 多核服务器的隐形性能税：跨 NUMA 访问延迟差 1.5-2 倍、TLB miss 让内存访问慢一个量级——多数教程缺席 |
| 尾延迟与防劣化 | 服务端 SLO 看 P99 不看均值；抖动源（THP 抖动/页回收/IRQ/调度迁移）是 Linux 独有的"隐性成本清单" |

## 五、篇间分界（防内容重叠）

四处容易写重的边界，明确分工：

| 主题 | 本篇负责 | 邻篇负责 |
|---|---|---|
| **CPU 微架构 vs 编译期** | 缓存篇管"运行时的数据布局与访问模式" | 编译篇管"编译期产物怎么变快"（两者叠加但路径独立） |
| **分配器 vs 页表** | 分配器篇管"用户态堆的组织"（brk/mmap 只是系统调用接口） | 页表篇管"内核的页管理"（缺页/TLB/NUMA），分配器篇的缺页成本由它兜底解释 |
| **文件 IO vs 网络** | 文件篇管"存储路径"（page cache/fsync） | 网络篇管"网络路径"（协议栈/零拷贝）；io_uring 作为现代提交模型在两篇各讲各的场景用法 |
| **专项防劣化 vs 体系防劣化** | 各篇的防劣化小节只管本专项（如大页抖动） | 尾延迟篇统一收口"线上观测与 CI 基准"的体系化方案 |

## 八、写作排期（非目录顺序）

**先立三根柱子验证体例**，再批量推进：

| 阶段 | 篇目 | 目的 |
|---|---|---|
| 柱子篇 | 1（地图）→ 3（缓存）→ 5（分配器） | 分别代表"总览型/微架构型/资源型"三种最难体例，打磨"双层归因"模板 |
| 批量篇 | 2、4、6、7、8、9 | 模板定型后按请求旅程顺序推进 |
| 收官篇 | 10 | 体系向内容最后收（尾延迟与防劣化闭环） |

每篇建议体量：正文 700-1000 行；四件套约占 15%（坐标/镜头/对照），五步闭环主体占 85%，其中"归因"与"防劣化"两步不低于一半篇幅——这是与市面"参数罗列式"文章的核心差异。
