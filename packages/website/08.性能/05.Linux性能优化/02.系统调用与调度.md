### 1.1 一份真实的压测报告

**旅程坐标**：本篇站在请求旅程的**第二站**——请求已经到达进程，接下来每一行代码都要在"用户态干活"还是"找内核办事"之间做选择。用户可感的症状是：**吞吐上不去、延迟抖动、CPU 明明没跑满但就是快不了**。

先看一份从真实服务裁剪出来的压测报告。这是一个转发代理服务（8 核容器，压测工具 wrk，业务逻辑只是"收包 → 查表 → 转发"）：

```text
QPS         : 812          ← 预期至少 5000
P50 latency : 1.8 ms
P99 latency : 11 ms        ← 抖动明显
CPU user    : 32%
CPU sys     : 58%          ← ⚠ 内核态占了 58%！
CPU idle    : 10%
```

业务逻辑简单到"查表转发"，QPS 却只有八百。**CPU 的 sys 占 58%**——内核在干什么？我们的代码明明只跑在 user 里。

对应的处理代码骨架（C 风格，问题就藏在里面）：

```c
// proxy_worker.c —— 每个连接一个线程，循环处理
void* handle_conn(void* arg) {
    int fd = *(int*)arg;
    char buf[1];                          // ← 【嫌疑点 1】1 字节的缓冲区
    while (1) {
        int n = read(fd, buf, 1);         // ← 【嫌疑点 2】每次只读 1 字节
        if (n <= 0) break;
        if (buf[0] == '\n') {
            struct timespec ts;
            clock_gettime(CLOCK_REALTIME, &ts);   // ← 【嫌疑点 3】每条消息取时间
            char* peer = get_peer_name(fd);        // ← 【嫌疑点 4】内部又调 getsockname
            forward(buf_line, ts, peer);
        }
    }
    return NULL;
}

// 每来一个连接就新建一个线程
pthread_t tid;
pthread_create(&tid, NULL, handle_conn, &connfd);  // ← 【嫌疑点 5】每连接一线程
```

### 1.2 顺藤摸到根因

带着"CPU sys 58%"这个线索往下挖，先立四个假设（本篇的归因主线，第 5 章逐条验证）：

- **假设 1**：`read(fd, buf, 1)` 每次只读 1 字节——转发 1KB 的消息要**过 1024 次海关**（系统调用），海关手续费比货还贵。→ 引出**系统调用成本模型**。
- **假设 2**：每条消息都 `clock_gettime` + `getsockname`——同样的信息反复问内核，**内核明明给了"免税通道"和"可以缓存的答案"**。→ 引出 **vDSO** 与**缓存策略**。
- **假设 3**：每连接一个线程——1000 个连接 = 1000 个线程在 8 个核上排队，调度器忙着"换人上台"，**上下文切换率爆表**。→ 引出**调度与切换成本**。
- **假设 4**：`CPU idle 10%` 却只有 812 QPS——**不是核不够，是每次干活之前都在排队/过海关**。→ 引出"CPU 时间是唯一硬通货"的资源观。

## 2. 资源镜头：边界经济学

### 2.1 用户态与内核态：为什么要有边界

**通俗理解**：CPU 上跑着两种代码——你的应用（用户态）和内核（内核态），就像一座城市里的"平民区"和"政府区"。平民区想用港口、铁路、国库（磁盘、网卡、内存页表这些全局资源），不能自己闯进去拿，必须到政府窗口（系统调用）排队申请。**边界的存在不是为了收费，是为了防止平民搞坏全局资源**。

x86 CPU 用特权级（ring）实现这道边界：

```
┌─────────────────────────────────────────────┐
│  Ring 3（用户态）                            │
│  你的代码：main、printf、std::vector ...      │
│  权限：只能访问自己的地址空间                   │
├──────────── 系统调用 = 唯一合法通道 ────────────┤
│  Ring 0（内核态）                            │
│  内核代码：read → VFS → 页缓存 → 磁盘驱动      │
│  权限：可访问一切硬件与所有进程的内存            │
└─────────────────────────────────────────────┘
```

**疑惑**：为什么要分两个态？全在 Ring 0 跑不就省了切换费？

**论证**：
1. 若任何代码都能直接操作磁盘控制器、页表，一个 bug 就能摧毁整机——多进程隔离直接失效；
2. 浏览器、数据库、你自己写的测试代码同处一台机器，**没有边界就没有"互相不信任"**，容器与云主机的安全模型全部坍塌；
3. 边界是**安全与隔离的地基**，性能税是它的副作用；
4. 真正的工程问题是**别为小事频繁过界**，而不是废除边界。

**结论**：边界不可废除，成本可以管理——本篇的一切优化手段，本质都是"**减少过界次数、或把过界变成不过界**"。

### 2.2 一次系统调用的成本清单

用「资源×流水线」模型给一次 `read(fd, buf, 1)` 记账：

| 成本项 | 量级 | 说明 |
|---|---|---|
| **入口开销** | ~100-300ns | `syscall` 指令：陷入内核、保存寄存器、查系统调用表 |
| **内核执行** | 视操作而定 | `read` 命中 page cache 约 0.5-1μs；真读磁盘是毫秒级 |
| **间接成本** | **可达数 μs** | 内核代码挤掉你的用户态缓存/TLB——回来后 cache 一片冰冷（第 3.2 节展开） |

**感性参照**：一次普通函数调用 ~1-2ns，一次空系统调用 ~100-300ns——**差两个数量级**。所以"把函数调用当系统调用随便使"是用户态程序最常见的性能失误。

**成本的历史注脚（为什么你的测量和别人不一样）**：2018 年 Spectre/Meltdown 漏洞披露后，内核默认开启 **KPTI（内核页表隔离）**——每次进出内核都要额外切换一次页表基址寄存器（CR3），系统调用与中断的固定开销在部分 CPU 上接近翻倍；较新的 CPU 用 PCID（进程上下文标识）把这笔税打了折扣。所以：

- 老文献里 "syscall ~50ns" 的数字，在你的机器上测出 200ns **不奇怪**；
- 反过来，云上共享宿主机的噪声、容器 cgroup 限流，也会让同一份代码测出不同数字；
- **本篇与全系列的数字口径**：均为"典型 x86_64 服务器、教学示意量级"，用于拍脑袋决策；精确值请在目标环境用第 3.4 节的实验自测——这也是上卷《指标与求证》"先测基线再谈优化"的落地。

### 2.3 调度的物理本质：CPU 时间片是唯一硬通货

**通俗理解**：一台 8 核机器就是一个只有 8 个窗口的银行。1000 个线程都要办业务（得到 CPU 才能跑），银行经理（调度器）必须不停地喊"下一位"（上下文切换）。**你感觉卡，不一定是窗口少（核不够），更可能是"叫号太频繁"（切换太狠）或者"每笔业务大量时间花在填表过户上"（系统调用）**。

把本篇案例翻译成资源语言：

```
总 CPU 时间（8核 × 100%） = 真正干业务的时间
                           + 过海关的时间（sys 入口+内核执行）
                           + 叫号换人的时间（上下文切换）
                           + 排队等待的时间（runqueue 等待，体现为 idle≠0 却不吞吐）
```

案例里 58% 的 sys + 每秒几十万次切换，意味着**真正干业务的时间不到三分之一**——QPS 低是必然。

## 3. 系统调用机制

### 3.1 一条 syscall 指令的旅程

以 `read(fd, buf, 1)` 为例，从 libc 到内核再回来的完整路径：

```
用户态                                内核态
──────                                ──────
read()  ← libc 包装
  │  把 fd/buf/count 放进 rdi/rsi/rdx 寄存器
  │  把系统调用号放进 rax（read = 0）
  ▼
syscall 指令 ──────── 陷入（trap）────────►  entry_SYSCALL_64
                                            │  切换到内核栈、保存用户寄存器
                                            │  （KPTI 开启时：CR3 切换内核页表）
                                            ▼
                                          sys_read（查表分发到 VFS 层）
                                            │  ... 真正干活（页缓存拷贝等）
                                            ▼
                                          返回值放 rax，恢复寄存器
  ◄──────── sysret 返回用户态 ──────────────  （KPTI：CR3 切回用户页表）
  │
  ▼
继续执行你的下一行代码
```

注意四个事实：
1. **寄存器是唯一的传参通道**——参数再多也是塞寄存器（多了压栈），这就是系统调用没法做成"变长参数随便传"的物理原因；
2. **每次过界要换栈**——用户栈和内核栈是两套，切换本身就有固定开销；
3. **内核干活的时间不可控**——`read` 命中 page cache 是亚微秒，落盘就是毫秒，所以成本清单要"入口费 + 业务费"分开算；
4. **指令本身也换过代**——32 位时代用 `int 0x80`（软中断，慢），后来 `sysenter/systr`，64 位统一为 `syscall` 指令（硬件专门优化的快路径）。老代码直接 `int 0x80` 会比 `syscall` 慢好几倍——这是"系统调用号与指令平台绑定"的历史包袱。

### 3.2 真正的大头：间接成本

**通俗理解**：过海关的直接成本（填表 100ns）还只是小钱；**过完海关回到自己办公室，发现桌上资料全被收走了（缓存全被内核代码挤掉），要花好几分钟重新找资料**——这才是大损失。

```
你的工作集（热数据）在 L1/L2 里放得好好的
        ↓ 一次深度系统调用（如 read 未命中、fsync）
内核驱动/文件系统代码大量执行，把 L1/L2/TLB 全换成内核的数据
        ↓ sysret 返回
你的下一次内存访问：cache miss → 走内存（几十 ns）
严重时：TLB miss → 多级页表遍历（几百 ns）
```

三层存储被"洗劫"的具体账单：

| 被洗的对象 | 平时命中成本 | 被洗后成本 | 恢复方式 |
|---|---|---|---|
| L1/L2 数据缓存 | ~1-4 个周期（<1ns） | 走内存 ~100 个周期 | 重新访问逐步回填 |
| 指令缓存 I-cache | 同上 | 同上 | 热循环重新预热 |
| TLB（地址翻译缓存） | 0 额外成本 | miss 后 4 级页表遍历 ~几百 ns | 随访问逐步回填；跨进程切换时可能整表作废（见 4.2） |

**实验感性数据**：微基准上，频繁系统调用的程序，**用户态 IPC（每周期指令数）会明显下降**——不是你的代码变慢了，是它的"工作环境"每次都被洗劫。这就是为什么第 06 篇（NUMA/大页）和本篇会互相引用：缓存污染的系统级治理，就是那边的主题。

**推理链条的收口**：直接成本 × 次数 = 可计算的显性税；间接成本 = 每次几十到几百纳秒、但叠加在**每一次后续内存访问**上的隐性税。所以"小 syscall 巨多"的代码，实测劣化经常**超过**直接成本推算——别只按次数 × 100ns 估账。

### 3.3 vDSO：gettimeofday 的免税通道

**通俗理解**：有些"问内核"的问题，答案其实内核早就写在了门口的公告栏上——比如现在几点（内核维护的时钟页）。**站在公告栏前看一眼（纯用户态读内存）就能拿到答案，根本不用进城**。这块"公告栏"就是 vDSO（virtual Dynamic Shared Object）。

```bash
# 看看你的进程是否映射了 vDSO
cat /proc/$$/maps | grep -E "vvar|vdso"
# 输出形如：
# 7f3e8c000000-7f3e8c002000 r--p 00000000 00:00 0  [vvar]   ← 内核单方面写的"数据页"
# 7f3e8c002000-7f3e8c004000 r-xp 00000000 00:00 0  [vdso]   ← 用户态执行的"读取代码"
```

它的机制拆开看：

```
内核侧（开机时）：选定时钟源（如 TSC）→ 按 TSC 频率换算公式写进 vvar 页
                              │
                              │  内核持续把最新时基参数维护在这页共享内存里
                              ▼
用户侧（clock_gettime 调用）：libc 直接跳进 vdso 页里的代码
                              → 读 vvar 数据 + TSC 寄存器 → 纯用户态算出时间
                              → 全程零陷入、零切页表、零缓存洗劫
```

**疑惑一**：为什么 `gettimeofday` 能"免税"，`read` 却不能？

**论证**：
1. 时间数据是**内核单方面维护、用户只读**的——没有竞态，共享内存就是安全的答案载体；
2. `read` 要**操作具体设备、可能阻塞、有私有状态（文件偏移）**——必须进内核处理；
3. 所以免税通道只适用于"**只读、无状态、不阻塞**"的查询类调用：gettimeofday/clock_gettime、gettid 等；
4. 现代内核里 `clock_gettime` 从一次真 syscall（微秒级）降到 **20-30ns**，提速几十倍。

**疑惑二**：免税通道会不会悄悄失效？

**论证**（这是很多资料不讲的坑）：
1. vDSO 加速的前提是**时钟源能被用户态直接读**——x86 的 TSC 可以；
2. 但如果时钟源是 `xen`、`acpi_pm` 或某些虚拟化环境下的 `kvm-clock` 不支持 vDSO 读取，`clock_gettime` 会**退化回真系统调用**——代码没变，性能差几十倍；
3. 验证方法一：`cat /sys/devices/system/clocksource/clocksource0/current_clocksource` 看时钟源；
4. 验证方法二（最直接）：`strace -c ./你的程序` 里**看不到 clock_gettime 才说明走了 vDSO**——strace 拦截的是真系统调用，vDSO 根本不过界，天然"隐身"。

**结论**：**用对时钟 API 就自动享受 vDSO**——`clock_gettime(CLOCK_MONOTONIC)` 走 vDSO，而某些封装（如老代码直接 `syscall(SYS_gettimeofday)`）会把它打回真系统调用。案例里的【嫌疑点 3】表面看没问题，真正的问题在"每条消息都取一次"——第 6.2 节讲怎么缓存。

### 3.4 动手实验：亲眼看见批处理的差距

原理讲了三节，不如亲手测一次。下面这个实验 10 分钟可复现，**强烈建议跟着做**——它同时演示"入口费"与"批处理"两个概念：

```bash
# 实验 A：用 dd 从 page cache 读 512MB
#   bs=1    → 512,000,000 次系统调用（每次 1 字节）
#   bs=64k  → 8,000 次系统调用（每次 64KB）
#   of=/dev/null 只读不写，iflag 只走内存缓存
dd if=/dev/zero of=/tmp/ddtest bs=1M count=512 2>/dev/null   # 准备一个 512MB 文件

echo "== bs=1（每次过海关搬 1 字节）==="
dd if=/tmp/ddtest of=/dev/null bs=1 count=100000000 2>&1 | tail -1
# 实测形态：100000000 bytes transferred in 25~40s → 约 3~4 MB/s

echo "== bs=64k（一次过海关搬 64KB）==="
dd if=/tmp/ddtest of=/dev/null bs=64k 2>&1 | tail -1
# 实测形态：512MB transferred in 0.2~0.5s → 约 1~3 GB/s

rm -f /tmp/ddtest
```

**读数与解读**：

| 版本 | 数据搬运量 | syscall 次数 | 吞吐差 |
|---|---|---|---|
| bs=1 | 同为 100MB~512MB | 1 亿次 vs 1.6 千次 | **约 3 个数量级** |

同一个内核、同一个 page cache、同一块内存——差的只是**过海关的次数**。这就是案例里【嫌疑点 1/2】的罪证形态：`read(fd, buf, 1)` 转发 1KB 消息要过 1024 次海关。这正是本卷第 08 篇（文件 IO）的入场券实验。

再补一个"空系统调用"的入口费测量（C 版）：

```c
// syscall_cost.c —— 测一次"什么都不干"的系统调用的固定开销
#include <sys/syscall.h>
#include <stdio.h>
#include <time.h>
int main() {
    struct timespec a, b;
    const int N = 10 * 1000 * 1000;
    clock_gettime(CLOCK_MONOTONIC, &a);          // 注意它本身走 vDSO，不污染被测对象
    for (int i = 0; i < N; i++)
        syscall(SYS_gettid);                      // gettid：几乎无副作用的"最轻"syscall
    clock_gettime(CLOCK_MONOTONIC, &b);
    double ns = (b.tv_sec - a.tv_sec) * 1e9 + (b.tv_nsec - a.tv_nsec);
    printf("每次 syscall 平均 %.0f ns\n", ns / N);   // 常见读数：100~300ns
    return 0;
}
```

```bash
gcc -O2 syscall_cost.c -o syscall_cost && ./syscall_cost
# gcc -O2：不开优化循环可能被测成"循环本身的开销"——基准测试永远注明编译参数
```

```bash
strace -c -p $(pidof proxy_worker)
```

典型输出（本篇案例的真实数据形态）：

```text

------ ----------- ----------- --------- --------- ----------------
 42.31    0.412000           2    206000           read          ← 每秒 20 万次！
 18.72    0.182000           8     22800           clock_gettime
 12.15    0.118000           9     12400           getsockname
  9.03    0.088000          20      4400           futex         ← 去第 07 篇报到
```

读表三件事：**calls 列**看有没有异常多的调用（绝对频率）；**usecs/call 列**看单个调用贵不贵（read 才 2μs，说明数据都在 page cache，慢不在"读"本身）；**errors 列**——非零错误率经常是 bug 信号（比如 fd 重复关闭后 read 一直 EBADF）。

**疑惑**：这个数字能直接用来当基准吗？

**论证**（strace 的三重陷阱）：
1. **strace 用 ptrace 实现**——每个系统调用要让目标进程停两次（进入、返回），被跟踪进程慢 **10-100 倍**。上面的数字是"相对结构"（哪个多哪个少）可用，绝对值不可用；
2. **压测时挂 strace = 自欺欺人**——测出来的是 strace 的开销不是程序的；
3. 生产环境短时间采样（几秒）可以，长挂会让服务超时。

**结论**：`strace -c` 的正确用法是**结构诊断**——看"哪个 syscall 异常多"，而不是"总共多快"。绝对性能用 `perf` 与 `/proc` 计数器。这个区分是 Linux 性能新手的第一个分水岭。

## 4. 上下文切换与调度

### 4.1 CFS：食堂排队模型

**通俗理解**：CFS（完全公平调度器）像一个按"打饭耗时"自动排序的食堂窗口——每个线程手里的餐盘上写着 vruntime（虚拟运行时间，吃得多排得越靠后），调度器永远叫"vruntime 最小的那个"上台。**没有任何人能一直霸占窗口，也没有人会永远饿着**。

关键规则（够用版，细节不展开）：

| 概念 | 含义 | 性能含义 |
|---|---|---|
| vruntime | 按 nice 值加权后的"已运行时间" | 公平的尺子，与优先级挂钩 |
| 调度周期（sched_latency） | 让所有可运行线程都跑一轮的目标时长（默认 ~6ms 量级） | 周期内每人分到的时间片 = 周期 / 线程数 |
| 最小粒度（min_granularity） | 单个时间片的下限（默认 ~0.75-3ms） | 线程多到"周期/线程数"小于下限时，一轮跑不完——**排队开始恶化** |
| 唤醒抢占 | 刚被唤醒的线程若 vruntime 落后，可立刻打断在跑的线程 | 睡醒的线程"插队"是设计特性——IO 型服务靠它保延迟 |

**对案例的影响**：1000 个活跃线程平分 8 核——每人每次只分到几毫秒，然后就被叫下去换人。**线程不是越多并行度越高，超过核数之后，加一个线程就多一份切换税**。

三个进阶注脚（面试与实战都会遇到）：

1. **参数是 sysctl 可调的**：`/proc/sys/kernel/sched_latency_ns`、`sched_min_granularity_ns`、`sched_wakeup_granularity_ns`——但**调它们是最后手段**，先修线程模型；
2. **EEVDF 是未来**：内核 6.6 起用 EEVDF 取代 CFS（更精确的延迟敏感模型），`sched_latency` 等参数在新内核已不存在——**学模型别死记参数**，本篇给的是"排队-时间片-抢占"的通用心智；
3. **容器里还有一层**：cgroup 的 cpu.shares/cpu.max 在 CFS 之上再切一刀（组间公平再组内公平）——容器"CPU 没满却慢"，先看 cgroup 配额是不是先到顶了（`/sys/fs/cgroup/.../cpu.stat`），这是第 10 篇尾延迟篇的领地。

### 4.2 切换一次到底多贵

切换成本取决于"换的是什么"——同进程线程、跨进程、带不带地址空间更换，税单完全不同：

| 切换类型 | 直接成本 | 典型场景 | TLB 命运 |
|---|---|---|---|
| 同进程线程切换 | ~1-2μs | 线程池内换任务 | TLB 保留（地址空间没变） |
| 跨进程切换 | ~2-5μs（KPTI 下更贵） | 进程间调度 | 老机制：TLB 全表作废；PCID 硬件：打标签部分保留 |

| 成本构成 | 说明 |
|---|---|
| 调度决策 | 挑下一个线程（红黑树/队列操作） |
| 寄存器/栈切换 | 保存旧线程寄存器、加载新线程的（含浮点状态惰性保存） |
| 地址空间切换 | 跨进程才有：CR3 重装 + KPTI 时代还要额外切页表 |
| **间接成本（大头）** | 新线程工作集把旧的挤掉，双方回来都要"重新热身"——常见 10μs 级 |

**感性换算**：8 核每秒理论可用时间 8s（CPU 秒）。若每秒 5 万次切换 × 3μs 直接成本 = **0.15s/秒 = 1.5% 的核白白烧掉**——直接成本尚可忍；但加上双方缓存互相洗劫的间接成本，**实际损失常见 5%-15%**。切换率是健康度指标，不是可以忽略的小钱。

### 4.3 两种切换：自愿与非自愿

```bash
# /proc 里内核替你记好了账（内核事实源，第 01 篇哲学）
grep -E "ctxt" /proc/$(pidof proxy_worker)/status
```

```text
voluntary_ctxt_switches   : 180234     ← 自愿：主动让出（read 阻塞、futex 等待、sleep）
nonvoluntary_ctxt_switches : 6412      ← 非自愿：被抢占（时间片用完/高优先级插队）
```

两种切换的性能含义完全不同：

| 类型 | 原因 | 健康度 |
|---|---|---|
| **自愿切换多** | 在等 IO/锁/睡眠——"没活干才让位" | 通常健康（该等的等），但**疯狂 futex 等待是锁竞争**（第 07 篇） |
| **非自愿切换多** | 线程数 > 核数，被迫轮转 | **不健康**——纯切换税，应减线程或调亲和 |

**一个隐蔽的判读技巧**：`voluntary / nonvoluntary` 的比值本身就是信号——IO 密集型服务的比值通常在 10:1 以上；比值逼近 1:1 说明"能跑的时间刚够被抢走"，线程数大概率超载。案例里 1000 线程 / 8 核，**nonvoluntary 必然爆炸**——这是【嫌疑点 5】的罪证形态。

## 6. 优化策略

### 6.1 策略一：批处理——把 N 次过海关变成 1 次

**通俗理解**：与其提着 1024 个 1 克的小包裹各过一次海关，不如**打成一个 1KG 的大箱一次通关**——入境费按"次"收，不按"重量"收。

```c
// ❌ 修复前：1 字节缓冲，1024 次海关
char buf[1];
while (read(fd, buf, 1) == 1) { ... }

// ✅ 修复后：大缓冲一次读够，在用户态慢慢解析
char buf[64 * 1024];
int n;
while ((n = read(fd, buf, sizeof(buf))) > 0) {
    for (int i = 0; i < n; i++) { /* 状态机解析行，不再过界 */ }
}
```

`read` 是这个道理，`write`、`sendto` 全都同理（Nagle/小包合并是第 09 篇网络篇的主场）。**批处理是系统调用优化的第一原则**：凡是"循环里逐条调用"的形态，先问能不能攒一批。

**适用边界**（什么时候不能批）：
1. **交互延迟敏感的字节流**（如 SSH 终端）：攒批会引入"等凑满"的延迟——批大小要按延迟预算定，不是越大越好；
2. **必须逐个响应的请求-回复协议**：回包不能攒（对端在等）——能批的只有"读入侧"；
3. **数据无边界时注意粘包处理**：批读后要自己维护"解析进度指针"，代码复杂度上升——这正是 JSON/KV 解析器案例里游标模型的用武之地。

### 6.2 策略二：缓存——把海关的答案记在本子上

**通俗理解**：对端地址（getsockname 结果）在一次连接的生命周期里**根本不会变**——第一次问过海关，就把答案抄在办公桌的便签上，此后纯用户态读便签。

```c
// ❌ 修复前：每条消息问一次内核
char* get_peer_name(int fd) {
    static char host[64];
    struct sockaddr_in sa; socklen_t len = sizeof(sa);
    getpeername(fd, (struct sockaddr*)&sa, &len);   // 每次 ~1-2μs 的真 syscall
    inet_ntop(AF_INET, &sa.sin_addr, host, sizeof(host));
    return host;
}

// ✅ 修复后：连接建立时问一次，随连接对象缓存
typedef struct {
    int   fd;
    char  peer[64];
    struct timespec connected_at;      // 时钟也缓存：连接级取一次足够
} conn_t;

conn_t* conn_new(int fd) {
    conn_t* c = malloc(sizeof(conn_t));
    /* getpeername 一次 + clock_gettime 一次，此后全是内存读取 */
    return c;
}
```

缓存的适用边界——三类问题三种答案：

| 问题类型 | 例子 | 策略 |
|---|---|---|
| 问一次后答案不变 | 对端地址、CPU 核数、页大小 | **永久缓存**（连接级/进程级） |
| 变但不需要每次都新鲜 | 时钟（日志时间戳容忍毫秒误差） | **周期缓存** |
| 变且必须新鲜 | 读 socket 数据、`epoll_wait` | **不能缓存**，走批处理 |

**周期缓存的工业级实现**（时间轮的简化版，很多日志库都这么干）：

```c
// 全局时间缓存：后台线程每 10ms 刷一次，业务线程纯内存读取
// 效果：QPS 10 万的服务，时钟 syscall 从 10万/s 降到 100/s
static _Atomic struct timespec g_now;      // C11 原子：读写不互斥
void* time_refresher(void* _) {
    while (1) {
        struct timespec ts;
        clock_gettime(CLOCK_REALTIME, &ts);   // 唯一过界点（vDSO，本已便宜）
        atomic_store(&g_now, ts);              // 发布给所有业务线程
        usleep(10 * 1000);                    // 刷新周期 = 可接受的时钟误差
    }
}
// 业务热路径：now = atomic_load(&g_now); —— 纳秒级，零 syscall
```

**注意分寸**：10ms 的误差对"日志时间戳、超时计算的粗判"够用；但**锁的超时、定时器触发必须用精确时钟**——缓存时钟只服务"展示与粗粒度判断"。

### 6.3 策略三：线程模型——切换率是设计出来的

**通俗理解**：把"每个客人配一个专属服务员"（每连接一线程）改成"8 个服务员的店"（小固定线程池 + 事件循环）——服务员不再轮流回家，切换税从"结构里"消失。

案例的改造：**每连接一线程 → 固定 8 线程 + epoll 事件循环**。epoll 本身就是"批处理"思想在事件上的应用：一次 `epoll_wait` 拿一批就绪 fd。切换率从 4.8 万/s 直落到千级——不是调优出来的，是**模型换掉的**。

线程数怎么定，给一个够用的决策表：

| 场景 | 推荐线程数 | 依据 |
|---|---|---|
| 纯 CPU 计算 | 核数（或核数-1，留一个给系统） | 没有阻塞点，多了只有切换税 |
| 混合负载（少量 IO + 计算） | 核数 × (1 + 阻塞系数) | 阻塞系数 = 阻塞时间占比，压测校准 |
| 大量慢 IO（如每连接一线程的老模型） | **别用线程数硬扛**——换事件循环 | 阻塞系数 > 0.5 后，线程模型的切换税失控 |

具体的事件循环与 epoll 深水区是第 09 篇的主场，本篇只需记住结论：**盲目加线程是给调度器加税**。

### 6.4 策略四：亲和性与优先级——让关键线程少排队

```bash
# 把关键 worker 钉在固定核上，减少迁移带来的缓存重建
taskset -pc 2-3 $(pidof proxy_worker)

# 降噪：后台统计线程降低优先级，别和收包线程抢窗口
nice -n 10 ./stats_collector
```

代码版（程序内设置，比命令行更可控）：

```c
#define _GNU_SOURCE
#include <sched.h>

cpu_set_t mask;
CPU_ZERO(&mask);
CPU_SET(2, &mask);                       // 只用 2 号核
pthread_setaffinity_np(worker_tid, sizeof(mask), &mask);
// 效果：worker 只在 2 号核排队——它的热数据在 2 号核的 L1/L2 里
//       不会被别的线程"搬家式"地挤掉（缓存常热的红利，第 03 篇展开）
```

| 手段 | 命令/API | 适用场景 | 过犹不及 |
|---|---|---|---|
| CPU 亲和 | `taskset` / `pthread_setaffinity_np` | 收包/渲染等关键线程，希望缓存常热 | 全部线程都钉死 = 失去负载均衡，一个核过载其他核看戏 |
| nice 优先级 | `nice` / `setpriority` | 后台任务让路前台 | 影响的是 CFS 加权，不是硬实时 |
| SCHED_FIFO 实时类 | `chrt` | 硬实时场景才用 | 饿死普通进程，容器里常被禁 |

### 6.5 优化前后对比

| 指标 | 修复前 | 修复后 | 手段 |
|---|---|---|---|
| QPS | 812 | **6,900** | 四策略合力 |
| P99 | 11 ms | **2.3 ms** | 切换率下降 + 批处理削峰 |
| CPU sys | 58% | **18%** | read 批处理 + 缓存 |
| 切换率（含非自愿） | 4.8 万（8500 非自愿） | **~2 千（非自愿 < 50）** | 线程模型重构 |
| syscall 总数 | 25.8 万/s | **~3.5 万/s** | 批处理 + 缓存 |

注意 **sys 不是降到 0 才好**——正常服务总有 IO。优化的目标是"**每次过界都货真价实**"，而不是"不过界"。另一个常被忽略的读数：**P99 的改善（11→2.3ms）大于 P50 的改善**——尾部的调度延迟税被砍掉，正是"切换率是 P99 之敌"的实证（第 10 篇会系统化这个命题）。

## 7. 常见误区清单

### 7.1 误区一：把系统调用当函数调用随手用

**现场**：代码评审看到循环里裸调 `getpid()`/`gettimeofday()`/`getcwd()`，作者理直气壮"这不是很轻吗"。

**破除**：
1. "轻"是相对的——`getpid` 现在也走 vDSO 了（几 ns），但 `getcwd`/`getsockopt` 是真过界（几百 ns + 间接成本）；
2. 量变引发质变——单次 200ns 不痛，**热路径每秒百万次就是 0.2 秒/秒 = 20% 的一核**；
3. 判据不是"这个调用贵不贵"，而是"**这个调用 × 它的频率**贵不贵"。

### 7.2 误区二：加线程提速

**现场**："压测上不去，把线程池从 8 调到 64 再到 256……怎么越调越慢？"

**破除**：
1. 线程数超过核数后，每加一个线程 = 多一份排队 + 一份切换税（第 4.1 节的最小粒度模型）；
2. 检验方法很简单：**线程数加倍的瞬间，看 nvcswch/s（pidstat -w）**——若同步翻倍，加的全是税；
3. 正确姿势：先找到"慢在哪"（是阻塞在 IO？还是在锁上排队？），IO 阻塞换事件循环，锁排队减少临界区——**两种病都不是"加线程"能治的**。

### 7.3 误区三：strace 挂在压测环境

**现场**：压测环境"顺路"挂着 strace 排查问题，然后拿着这份压测报告开会。

**破除**：strace 让被跟踪者慢 10-100 倍（第 3.5 节三重陷阱）——**挂着它的环境给出的任何数字都作废**。诊断用独立环境或短时采样，压测环境永远保持"无探针"。

### 7.4 误区四：taskset 当万能药

**现场**："听说绑核能提速"，于是把整个服务的所有线程都钉死在几个核上。

**破除**：
1. 绑核的本质收益是"**缓存常热**"（少迁移），对访存密集的特定线程有效；
2. 全员钉死 = 手动制造单核过载——CFS 本来会做的负载均衡被废掉了；
3. 正确姿势：**只绑少数关键线程**（收包、渲染），其余放养；绑完用 `pidstat -wt` 验证迁移率（cpu-migrations）真的降了、吞吐真的升了——**没有度量的绑核是玄学**。

## 8. 防劣化

### 8.1 CI 卡口：给 syscall 计数上锁

优化做完，怎么防止它悄悄劣化回来？给 CI 加两道卡口：

```bash
#!/usr/bin/env bash
# perf_gate.sh —— CI 性能卡口（简化骨架）
set -euo pipefail
BENCH="./benchmark --requests 100000"       # 固定负载，输出确定
BASELINE_SYSCALL=5000000                     # 基线×1.2，先跑三次取中位数定出来
BASELINE_CSW=8000                            # 同上

# 卡口 1：固定负载下 syscall 总数不超预算
strace -c -f -o /tmp/trace.txt $BENCH || true
total=$(awk '/^100\.\.\./{print $NF}' /tmp/trace.txt | tail -1)
[ "$total" -lt "$BASELINE_SYSCALL" ] || { echo "❌ syscall 预算超标: $total"; exit 1; }

# 卡口 2：压测窗口内切换率不超标（perf 精确计数）
csw=$(perf stat -e context-switches -x, -o /tmp/perf.txt $BENCH 2>/dev/null; \
      awk -F, '{print $1}' /tmp/perf.txt | tail -1)
[ "$csw" -lt "$BASELINE_CSW" ] || { echo "❌ 上下文切换超标: $csw"; exit 1; }

echo "✅ 性能卡口通过: syscall=$total csw=$csw"
```

**预算怎么定**：先跑三次取中位数当基线，预算 = 基线 × 1.2。数字本身不重要，**重要的是"每条 PR 都过一遍这个门槛"——劣化的本质是没人看着的渐变**。

### 8.2 线上监控与告警

```text
采集：pidstat -w 1 → 上报 cswch/s、nvcswch/s（进程级）
     /sys/fs/cgroup/.../cpu.stat → 容器被限流次数（nr_throttled，第 10 篇展开）
告警：非自愿切换 > 核数 × 500/s 持续 5 分钟 → 疑似线程模型劣化/下游变慢拖高并发
```

切换率是**滞后但忠实的哨兵**：业务代码没人改，但依赖变慢、流量上涨、线程池悄悄扩容，都会先在这里现形。

### 8.3 常见劣化模式清单

| 模式 | 信号 | 病根 |
|---|---|---|
| 循环逐条小 IO | strace 里 read/write 巨多 | 新人代码不批处理 |
| 热路径新增 getsockopt/getsockname | 单条消息 syscall 数上涨 | "顺手查一下"没意识成本 |
| 日志库每条打点取时钟 | clock_gettime 巨多（vDSO 也架不住量） | 没用时间缓存 |
| 线程池配置改大 | nvcswch/s 飙升 | "加线程提速"的迷信（误区二） |
| 容器超卖邻居干扰 | vmstat r 高但本进程切换也高 | 属第 10 篇尾延迟的领地 |
| 依赖 SDK 里藏了新 syscall | strace 结构突变但没人改代码 | 三方库升级的隐性成本——**卡口 1 的存在意义** |

## 9. 综合串讲

### 9.1 一次请求的一生

把案例修复前后的差别，画成"一次请求的一生"知识树：

```
修复前（每条 1KB 消息）：
  过海关 ×1024（read 1B） ──► 过海关 ×1（clock_gettime）
        ──► 过海关 ×1（getsockname） ──► 排队等待叫号（非自愿切换税）
                                        └─ perf sched：Max delay 8.3ms（P99 元凶）
修复后：
  过海关 ×1（read 64KB） ──► 读便签（缓存的 peer/时钟，纯用户态）
        ──► 留在自己的窗口继续干活（epoll 少线程，几乎不换人）
```

### 9.2 设计哲学回扣

**哲学 1：入口费思维——系统调用按"次"收费，与"量"无关**

评估任何一个热路径 API 前，先问三个问题：这是不是系统调用？一次的固定费是多少？**我们能不能把 N 次并成 1 次**？——批处理与缓存都是这条哲学的展开。但注意适用边界（6.1/6.2 节），**为批而批引入延迟、为缓存而缓存弄脏数据，都是过犹不及**。

**哲学 2：内核事实源——能问 /proc 就别瞎猜，能读共享页就别过界**

vDSO 与 `/proc/<pid>/status` 是同一思想的两种形态：**内核已经维护好的事实，用户态要么直接读（vDSO），要么低成本查（/proc），绝不用启发式重算**。判读 voluntary/nonvoluntary 比值（4.3 节）就是这条哲学的日常工作流。

**哲学 3：切换率是设计属性，不是调优属性**

线程模型定了，切换率的大盘就定了。事后 taskset 只能修修补补——**把切换税消灭在设计阶段（固定线程 + 事件循环），而不是运行阶段**。P99 的敌人是排队，排队的敌人是超载的线程数。

### 9.3 速查表

**成本速记**（数量级，供拍脑袋决策用；精确值用 3.4 节实验自测）：

| 操作 | 量级 |
|---|---|
| 普通函数调用 | ~1-2 ns |
| vDSO clock_gettime | ~20-30 ns |
| 空系统调用（入口费，含 KPTI 时代浮动） | ~100-300 ns |
| 命中 page cache 的 read | ~0.5-1 μs |
| 同进程线程切换（直接） | ~1-2 μs |
| 跨进程切换（直接，含地址空间） | ~2-5 μs |
| 切换后的缓存/TLB 重建（间接） | 可达 10 μs 级 |
| 磁盘真读（SSD） | ~100 μs+ |

**60 秒诊断命令清单**：

```bash
strace -c -p $PID                 # syscall 结构（别在压测时挂）
vmstat 1                          # 全局切换率 cs、r 队列
pidstat -w -p $PID 1              # 进程级自愿/非自愿切换
pidstat -wt -p $PID 1             # 线程级定位"谁在切换"
grep ctxt /proc/$PID/status       # 累计切换账本（内核事实源）
perf stat -e context-switches,cpu-migrations -p $PID -- sleep 10
perf top -g                       # 内核态热点现场
perf sched record -- sleep 10 && perf sched latency --sort max   # 排队时长分布
cat /proc/$PID/maps | grep vdso   # 确认 vDSO 在位
cat /sys/devices/system/clocksource/clocksource0/current_clocksource  # 时钟源
```

**归因决策树**（从症状到病根）：

```
CPU sys 高 ──► strace -c ──► read/write 巨多 ──► 小 IO 不批处理 ──► §6.1
                        └─► 查询类巨多 ────► 可缓存未缓存 ────► §6.2
切换率高   ──► pidstat -w ─► 非自愿为主 ──► 线程超载 ────────► §6.3
                        └─► 自愿为主 ───► 等锁/等IO（去第07/09篇）
P99 抖     ──► perf sched ─► Max delay 集中 ─► 排队税 ──────► §6.3 + 第10篇
```

## 10. 跨语言对照

### 10.1 C++ / Rust / Go 三栏速查

| 关注点 | C++ | Rust | Go |
|---|---|---|---|
| 读时钟 | `std::chrono::steady_clock::now()`（vDSO） | `std::time::Instant::now()`（vDSO） | `time.Now()`（vDSO） |
| 系统调用封装 | 裸 syscall / `syscall(2)` | `std::fs`（薄封装） | `syscall` 包 + runtime 内置 |
| 线程模型 | std::thread / pthread，线程=内核线程 | std::thread，同 C++ | **GMP：M 个内核线程跑 G 个任务，syscall 时 M 自动扩容** |
| 批读文件 | `read` 大缓冲 / `readv` | `Read::read_to_end`（内部分块） | `io.ReadAll` |
| 亲和性设置 | `pthread_setaffinity_np` | 同 C++（libc 绑定） | runtime 锁 M 在 P 上，应用层少直接控制 |

### 10.2 Go 为什么"感觉"不怕系统调用

**通俗理解**：Go 的 runtime 像一家自带报关行的贸易公司——你只管把货单（goroutine）递进去，报关行（runtime 的 M/G 调度）自己决定哪个报关员（内核线程 M）去过海关，而且**海关排队时会自动增派报关员**。

要点（不展开，属于第 07/09 篇的深水区预告）：
1. goroutine 切换是**用户态切换**（~100ns 级），不走内核——所以 Go 程序敢开几十万 goroutine，但 C++ 开几千线程就开始交切换税；
2. 阻塞 syscall 时 runtime 会**新开一个 M 顶班**，不把整个内核线程挂死；
3. 但**海关本身的入口费 Go 也免不了**——`read(fd, buf, 1)` 写在 Go 里照样是 1024 次 syscall。**本篇的批处理/缓存哲学跨语言通用**，语言只改变"切换税"，不改变"过界税"。
