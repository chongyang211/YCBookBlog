### 1.1 一份真实的内存事故报告

**旅程坐标**：本篇站在请求旅程的**第四站**——[第 02 篇](/pages/2f9a64/)把系统调用与切换税砍掉之后，服务跑得飞快，但新的问题浮出水面：**堆**。每处理一个请求，代码都在 `new/delete` 之间穿梭——对象在堆上生生死死，而堆是**应用与内核共管的战场**：应用层管"怎么分"，内核层管"从哪进货"。用户可感的症状是：**RSS 持续上涨、P99 毛刺、极端时 OOM 被杀**。

案例沿用 02 篇的同款网关（8 核容器）——修完 syscall 税之后的第二轮体检报告：

```text
QPS         : 6900         ← 02 篇优化后的战果，保持住了
P99 latency : 2.3 ms       ← 但出现了新的抖动尖刺
RSS         : 810 MB → 2.9 GB（7 天缓慢上涨后趋稳）   ← ⚠ 趋稳说明不是纯泄漏
oom_score   : 服务排到宿主机第 2 位                    ← ⚠ 再涨就要被 OOM killer 点名
内存毛刺    : P99.9 = 18 ms，毛刺时刻伴随大分配         ← ⚠ 尾部有暗税
```

对应的处理代码骨架（问题藏在内存维度）：

```cpp
// gateway.cpp —— 每请求的处理路径
void handle_request(Request& req) {
    auto ctx    = new RequestContext();          // ← 【嫌疑点 1】每请求 new 一堆小对象
    auto header = new HeaderMap();                //    解析一行头就 new 一个 map 节点
    auto body   = new std::string(64 * 1024);     // ← 【嫌疑点 2】64KB"大分配"踩 mmap 阈值
    parse(req, ctx, header, body);
    route(*ctx);
    delete ctx; delete header; delete body;      //    立刻归还——看似"很干净"
}
// 32 个 worker 线程并发调用，多线程共享 glibc 默认堆
```

### 1.2 顺藤摸到根因

带着"RSS 涨到 2.9GB 后趋稳"与"P99.9 毛刺"两条线索，立四个假设（本篇归因主线，第 5 章逐条验证）：

- **假设 1**：每请求 `new` 三件套 + 解析中的隐式分配——**分配次数本身是热路径税**，且多线程在同一块堆上"抢收银台"（arena 锁）。→ 引出**分配器成本模型**。
- **假设 2**：`new std::string(64KB)` 超过 mmap 阈值——**每次都真系统调用进货、每次 free 都退货给内核**，毛刺与系统调用税双双上身。→ 引出**brk/mmap 进货机制**。
- **假设 3**：RSS 涨到 2.9GB 趋稳不降——不是泄漏，是**碎片**：打散释放的空闲块"嵌"在仓库中间，分配器既用不上也还不回去。→ 引出**碎片经济学**。
- **假设 4**：修完这些，`oom_score` 能不能真正降下来——防劣化要看**稳态 RSS**，不是峰值。→ 引出**监控与卡口**。

## 2. 资源镜头：堆的批发经济学

### 2.1 malloc 的本质：应用与内核之间的批发商

**通俗理解**：`malloc` 不是"问内核要内存"，它是你进程里链接的一个**用户态函数库**（glibc 的一部分）——一个**批发商**。它从内核批发大块内存（brk/mmap），切成小块零售给你的代码。你每一次 `new` 64 字节，根本不惊动内核——**那是从批发商的货架上拿的**。

```
你的代码：new 64B      ──►  malloc(64)         用户态：查货架（bin/tcache）
                              │ 货架有货 → 直接返回（~20-50ns，零过界）✔
                              │ 货架空了 → 找批发仓库（arena）
                              │   仓库空了 → 向内核进货：
你的代码：malloc(1MB)  ──►  超 128KB 阈值 ──►    mmap() 真系统调用 → 内核直接划一块
                              │                    （以后每次 free 这块 → munmap 退货）
                              ▼
                          brk() 给主仓库扩容（真系统调用，很少发生）
```

**疑惑**：为什么不让内核直接管每一次分配，省掉批发商这层？

**论证**：
1. 一次 mmap 系统调用 ~1μs，若每次 64B 分配都过界，百万次分配就是一整秒——批发商把 N 次零售合并成少量批发，正是[第 02 篇](/pages/2f9a64/)"批处理哲学"的库级落地；
2. **释放比分配更麻烦**——内核的页是 4KB 粒度，用户对象是 16B 粒度，若内核直管，free 时还要做"页内是否全空"的合并判断；
3. 批发商在用户态做**分拣**（按尺寸归类、相邻合并），把复杂度从"每次系统调用"摊薄成"内存里的链表操作"；
4. 代价是**中间商赚差价**——碎片（第 4 章）与内存开销（元数据、锁），这就是本篇要治理的税。

**结论**：分配器的一切设计，都是"**批发减少过界、零售加速获取、分拣防止浪费**"的三角平衡。

### 2.2 一次 malloc 的成本清单

用「资源×流水线」模型给 `malloc(n)` 记账（glibc ptmalloc，64 位典型值）：

| 路径 | 触发条件 | 成本 | 说明 |
|---|---|---|---|
| **tcache 快路径** | ≤1KB 且线程缓存有存货 | **~20-50ns** | 纯用户态、无锁、单链表 pop |
| bins 慢路径 | tcache 空了 | ~100-300ns | 查 fastbin/smallbin/unsorted，可能竞争 arena 锁 |
| 锁等待路径 | 多线程争同一 arena | **不可控（毛刺源）** | 争锁失败进 futex 睡眠（去[第 07 篇](/pages/9d4e72/)） |
| mmap 路径 | 单笔 >128KB（默认阈值，动态可调） | ~1-5μs | 真系统调用进货 + 后续缺页 |
| **隐含的缺页税** | 拿到的内存**首次写入**时 | ~1-2μs/页 | 内核现场分配物理页（[第 06 篇](/pages/b16830/)兜底解释） |

三个常被忽略的事实：
1. **malloc 本身不产生缺页**——批发来的地址只是"记账"，第一次写每个 4KB 页才真给物理内存（zero page 惰性分配）。所以"分配慢"和"首次访问慢"是两笔账，很多微基准测错就是因为混了它们；
2. **mmap 阈值是动态的**——glibc 会根据历史调整（被释放的 mmap 块太大时自动上调阈值），所以"64KB 到底走不走 mmap"在长跑服务里可能变化，用 strace 实测最靠谱（3.5 节）；
3. **锁是毛刺之母**——均摊成本 50ns 的分配，在争锁时可以到微秒级；32 线程挤 8 个 arena（默认 arena 数上限 = 8×核数，但实际按需创建），抢锁概率不可忽视。

### 2.3 物理本质：RSS 是账本，缺页是提货

**通俗理解**：进程看内存有三个口径，像一个人看自己的钱：**虚拟地址空间 = 信用卡额度**（看起来很大随便刷）、**RSS = 账本余额**（真花掉的部分）、**物理页 = 现金**（机器里真实的钞票，多进程分抢）。

```
malloc 100GB  → 虚拟地址 +100GB（记账而已，内核只是登记了"他有额度"）
memset 1GB    → RSS +1GB（每写一页，缺页中断让内核真发 1 页现金）
free 且 munmap → 账本销账（现金回到内核金库）
free 未 munmap → 账本还在（现金压在批发商仓库里——碎片税的来源）
```

四条推论（后面章节全部围绕它们展开）：
1. **top 看 VIRT 没意义，看 RES**——VIRT 只是额度，jvm/大分配服务 VIRT 轻松几百 GB；
2. **RSS 涨不一定泄漏**——批发商压货（碎片）也涨账本（第 4 章展开，这也是误区一的病根）；
3. **OOM killer 看的是账本+现金水位**——宿主机现金不足时按 oom_score 杀最大的账本，`/proc/<pid>/oom_score` 提前知道自己的死刑排名；
4. **优化内存 = 优化"稳态账本水位"**——不是压低峰值的一瞬间，而是让批发商少压货、热路径少进货。

## 3. 分配器机制

### 3.1 ptmalloc：bins 分拣与 arena 分仓

**通俗理解**：ptmalloc（glibc 自带，Linux 默认）像一个总仓 + 分仓的连锁仓储：**主线程用 brk 扩容的"总仓"（main arena）**，**其他线程按需开设 mmap 的"分仓"（arena）**；每个仓内按货物尺寸分拣到不同货架（bins），拿货先看最近的私人小抽屉（tcache）。

进货与分拣的四级结构（分配时自上而下找货）：

```
第 1 级 tcache      每线程一个"私屉"，缓存 ≤1KB 的小块（glibc 2.26+）
                   同尺寸最多 7 个，单链表 LIFO——快路径无锁就在这
第 2 级 fastbin     ≤128B 的超小货，arena 内全局链表（单尺寸一条）
第 3 级 small/large/unsorted bin
                   smallbin 按 16B 阶梯分格；unsorted bin 是"回收站"——
                   free 的块先进这里，等下次 malloc 顺手分拣归类
第 4 级 top chunk  仓里的"待切割整料"——不够了就 brk/mmap 进货扩仓
```

三个性能关键点：
1. **arena 上限 = 8 × 核数**（64 位默认 `M_ARENA_MAX`）——32 线程 8 核，最多 8 个 arena，必然有多个线程共享一个 arena，共享就有锁；
2. **free 进 unsorted bin 的"顺手分拣"**是 ptmalloc 的灵魂设计——释放的相邻块在此时**合并**（coalesce），对抗外碎片；但也因此 free 并不总快，且合并依赖"物理相邻"，打散释放就合并不动（第 4 章）；
3. **单笔 > mmap 阈值（默认 128KB）绕过 arena 直购**——mmap 一块独立内存，free 时 munmap 整块退货。对大而短命的对象反而高效（无碎片）；对**反复分配释放的大对象**，等于每次都"进货-退货"，把 02 篇的系统调用税又交了一遍——【嫌疑点 2】的病根。

### 3.2 tcmalloc：线程私货柜台

**通俗理解**：ptmalloc 的痛点是"分仓有限、锁在仓上"。tcmalloc（Google）把思路反过来：**每个线程发一个私货柜台（thread cache）**，小分配全部在自己的柜台完成——无锁、无争用、无跨线程；柜台缺货才去中央仓库（central free list）补货，一次补一批。

```
thread cache（每线程，无锁）        ← 90%+ 的小分配在这里结束
        │ 柜台缺货 → 每尺寸类一把锁的 central freelist（补一批）
                │ 中央也缺 → page heap（按 span 批发页）
                        │ 页不够 → mmap/sbrk 进货
```

两个核心设计：
1. **尺寸类（size class）**：把请求尺寸归到 ~88 个"档位"（如 96B、112B、128B…），每档一个自由链表——分拣比 ptmalloc 的 bins 更细更规整，代价是**内碎片**（要 100B 给 112B 档，浪费 12B）；
2. **Go runtime 的直系血亲**：Go 的 `mcache → mcentral → mheap` 三层就是 tcmalloc 的翻版（第 10 章展开）。

### 3.3 jemalloc：按核分片与碎片治理

**通俗理解**：jemalloc（Facebook/Firefox 系）在"线程本地"与"锁分片"之外，把**碎片治理**做成了第一等公民——它对"仓库利用率"的执念，让它在长跑大内存服务里 RSS 更稳。

三个招牌设计：
1. **arena 分片**：默认 `4 × 核数` 个 arena，线程首次分配时绑定到某个 arena——锁的分片比 ptmalloc 更彻底（8 核 = 32 个 arena，32 线程几乎人人有专属仓）；
2. **extent 与 dirty page 归还**：jemalloc 精确追踪每个页区间的状态（allocated/dirty/muzzy/retained），空闲页**主动分批归还内核**（madvise），且可配置保留水位（`dirty_decay_ms`）——这是它"RSS 只涨不降"问题远轻于 glibc 的原因（4.2 节展开）；
3. **统计内建**：`MALLOC_CONF=stats_print:true` 退出时打印完整碎片报告——本篇归因的主力工具之一。

**疑惑**：既然 tcmalloc/jemalloc 全面占优，为什么 glibc 还是默认？

**论证**：
1. glibc 随系统分发、零依赖、零配置——对"不缺内存"的程序，ptmalloc 的 tcache 快路径已经足够快；
2. tcmalloc/jemalloc 各自**多吃了 5-10% 的常驻内存**（尺寸类档位浪费、更积极的页预留）——内存极度紧张的小进程反而吃亏；
3. 工程选型从来不是"谁最快"，是"**这个病的边际收益**"——第 6.1 节给决策表。

### 3.4 三家对比与选型

| 维度 | ptmalloc（glibc） | tcmalloc | jemalloc |
|---|---|---|---|
| 线程本地缓存 | tcache（≤1KB，2.26+） | thread cache（全尺寸） | tcache（全尺寸） |
| 锁分片度 | arena ≤ 8×核 | central 按尺寸类 | arena 默认 4×核 |
| 碎片治理 | 合并靠相邻、归还保守 | 中等 | **最激进可配** |
| RSS 稳定性 | 长跑易涨（4.2 节） | 中 | **好** |
| 元数据开销 | 小 | 中（档位多） | 中 |
| 典型适用 | 通用/内存敏感小进程 | 多线程吞吐型、Google 系 | 长跑大内存、Rust/Facebook 系 |
| 获取方式 | 系统自带 | 依赖库 + LD_PRELOAD | 依赖库 + LD_PRELOAD |

选型一句话决策（细节在 6.1 节的适用边界）：**多线程吞吐优先试 tcmalloc；长跑 RSS 胖、碎片疑虑重试 jemalloc；两者都救不动时，病在你的分配模式（第 6.2-6.4 节），不在分配器**。

补充第四位选手：**mimalloc**（微软）——短命小对象场景（解析器、游戏帧循环）实测常有惊喜，原理是"各代 free list 分层"，可作为以上两家都不理想时的第三选项。

## 4. 碎片：内存的暗税

### 4.1 内碎片与外碎片

**通俗理解**：碎片的两种形态，像仓库的两种浪费——**内碎片 = 货架空隙**（要 100B 的货只能放进 112B 的格子，格子里的 12B 永远卖不掉）；**外碎片 = 库房隔断**（库里明明有 1GB 空闲，但都是散落的小空位，拼不出一块连续 100MB——新的大货进不来）。

```
内碎片（分配器主动造成的）：
  请求 100B → 尺寸档位/对齐规则 → 实占 112B → 12B 静默浪费
  典型源头：tcmalloc 档位化、16B 对齐、chunk 元数据头（ptmalloc 每块 ~8-16B 头）

外碎片（分配与释放的"时序"造成的）：
  t0: [A活][B活][C活][D活][E活]     全在用，无碎片
  t1: free(A); free(C); free(E)     [空][B][空][D][空] —— 释放打散了！
  t2: 想分配"连续 3 格"的大对象 → 分不出来（B/D 卡在中间）
       —— 空闲总量足够，空闲"形状"不对——外碎片
```

**疑惑**：外碎片听起来只影响"大对象"，小服务为什么也要怕？

**论证**：
1. 内核对**批发商的归还**同样要求"连续空闲到仓顶"（4.2 节）——打散的空位还不了内核，**RSS 虚高**；
2. 分配器为拼大块会**触发更多进货**（arena 里拼不出 → 再 mmap 一块），VIRT/RSS 双涨；
3. 更隐蔽的是**缓存足迹**：活对象被空隙拉开距离，cache line 里混入大量空洞，[第 03 篇](/pages/c75b18/)的空间局部性被碎片破坏——碎片不只是内存税，还是缓存税。

### 4.2 为什么 RSS 只涨不降

**通俗理解**：批发商的仓库管理哲学是"**赚来的货压在仓库里，等下一波行情**"——free 掉的货回到货架（bins），但**只有仓顶连续空闲超过阈值才向内核退货**（glibc 默认 trim 阈值 128KB）。打散释放 = 空位卡在中间 = 永远凑不齐仓顶的一整块。

glibc 的三个保守参数（长跑服务的"RSS 只涨不降"三件套）：

| 参数 | 默认 | 含义 | 后果 |
|---|---|---|---|
| `M_TRIM_THRESHOLD` | 128KB | 仓顶连续空闲多少才退货 | 中间的空位永远不退 |
| `M_TOP_PAD` | 128KB | 仓顶预留缓冲 | 故意多留，防频繁进货 |
| `M_MMAP_THRESHOLD` | 128KB（动态） | 超过则绕过 arena 直购 | 64KB 边缘对象行为不稳定 |

**动手实验：肉眼看见碎片**（10 分钟可复现，建议跟做）：

```c
// fragment.c —— 展示"释放了一半内存，RSS 几乎不降"
#include <malloc.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static long rss_mb() {                       /* 读 /proc/self/statm 第二列 = RSS 页数 */
    FILE* f = fopen("/proc/self/statm", "r");
    long total, resident; fscanf(f, "%ld %ld", &total, &resident);
    fclose(f); return resident * 4 / 1024;   /* 页 4KB → MB */
}

#define N 30000
#define SZ (32 * 1024)                        /* 32KB：低于 mmap 阈值，走 arena */
int main() {
    void* p[N];
    for (int i = 0; i < N; i++) { p[i] = malloc(SZ); memset(p[i], 1, SZ); }
    printf("持有全部 %d MB 时 RSS=%ld MB\n", N*SZ/1024/1024, rss_mb());
    for (int i = 0; i < N; i += 2) free(p[i]);   /* 隔一个放一个：释放一半且打散 */
    printf("释放一半(打散)  RSS=%ld MB   ← 预期：几乎不降！\n", rss_mb());
    malloc_trim(0);                              /* 手动要求 glibc 归还空闲页 */
    printf("malloc_trim 后   RSS=%ld MB   ← 降一部分，中间空洞仍还不干净\n", rss_mb());
    return 0;
}
```

```bash
gcc -O2 fragment.c -o fragment && ./fragment
# 典型读数形态：960 → 940（释放一半只掉 2%）→ trim 后 ~500
# 第一行到第二行的差值，就是"碎片税"的直观展示
```

jemalloc 为什么轻得多：它不赌"仓顶连续"，而是按**页区间（extent）精确记账**，空闲页攒到水位就 `madvise` 部分归还（默认 `dirty_decay_ms=10s`）——空隙中间的页也能还。这就是 6.1 节"换分配器立降 RSS"的机制根源。

### 4.3 长尾毛刺：大分配的连带账单

一次 `malloc(64KB)` 踩过 mmap 阈值时，账单远不止一次系统调用：

```
mmap 进货（~1μs，02 篇的入口费模型）
   → 后续每次写这 64KB 触发 16 次缺页（~1-2μs/页，[第 06 篇]兜底）
      → 缺页若赶上内核内存紧张：页回收、甚至直接压缩（CPU 尖刺）
         → 若 THP 开启：内核可能现场拼接 2MB 大页（[第 10 篇]的抖动源清单）
free 时 munmap：页表拆除 + TLB 全核失效（又一个隐藏税）
```

所以"偶发的大分配"在压测里的形态是：**P50 毫无变化，P99.9 突然刺到 10ms+**——均值统计完全看不见，只有尾延迟观测能抓到。这是 [第 10 篇](/pages/7e53d6/)"毛刺源清单"的第一页，本篇负责把它归到"分配模式"病根下。

### 4.4 度量第二刀：把碎片率拍在桌面上

```bash
# 碎片率的金标准定义：1 - (活跃字节 / 堆实占字节)
# 活跃字节 = 应用真的在用的；堆实占 = 账本 RSS 里的堆部分

# glibc：malloc_info 的 XML 里，每个 arena 的 <size> 里 fast/small/large 空闲量
#        减去 <system ... type="current" size="..."/> 就是碎片水位
python3 - <<'EOF'   # 简化示意：从 malloc_stats 输出人工读
#   "system bytes = 2.9G, in use bytes = 1.1G"
#   → 碎片率 ≈ 1 - 1.1/2.9 = 62%  （本案例的实测形态）
EOF

# jemalloc：一条命令，直接给答案
MALLOC_CONF=stats_print:true ./gateway    # 退出时打印
#   输出找这两行：
#   "allocated: 1120000000"        ← 活跃
#   "mapped:   2900000000"        ← 实占
#   ratio = allocated/mapped 就是仓库利用率

# 进程级佐证：smaps 看堆段的 Private_Dirty
grep -A1 "\[heap\]" /proc/$(pidof gateway)/smaps
# Private_Dirty 高 + malloc 账本说大半空闲 → 碎片实锤（而非泄漏）
```

判读口诀：**"活跃小、实高大、脏页多 = 碎片；活跃与实高同步涨 = 泄漏"**——这一句话就是第 5 章归因的分水岭。

### 5.1 案例归因复盘

## 6. 优化策略

### 6.1 策略一：换分配器——三行配置的进货改革

**通俗理解**：分配模式一行不改，先把"批发商"换成管理更精细的——jemalloc 治碎片、tcmalloc 治锁争。LD_PRELOAD 让动态链接的所有 malloc 调用改道新分配器，**三行配置**：

```bash
# Ubuntu/Debian 为例
apt install libjemalloc2
export LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2
export MALLOC_CONF=stats_print:true,dirty_decay_ms:5000,lg_tcache_max:13
./gateway

# 验证确实挂上了（最容易被忽略的一步）
lsof -p $(pidof gateway) | grep jemalloc    # 有输出才生效
cat /proc/$(pidof gateway)/maps | grep jemalloc
```

本案例的实测效果：**碎片率 62% → 17%，稳态 RSS 2.9G → 1.35G**——没改一行业务代码。

**适用边界**（换分配器不是万能的第一步）：
1. **先量化再换**——`malloc_info` 显示碎片率低（<15%）却 RSS 高，多半是活跃内存真有那么大或泄漏，换 jemalloc 无效；
2. **小内存进程可能反向劣化**——jemalloc/tcmalloc 的元数据与档位浪费会多吃 5-10% 常驻，百 MB 级以下进程先测再上；
3. **静态链接/容器镜像体积**：LD_PRELOAD 依赖目标机器有库——容器场景直接在镜像里装，或改用编译期链接（`-ljemalloc`）更可控；
4. **换分配器治标，分配模式治本**——6.2-6.4 不做，三个月后碎片又回来了（误区四的现实形态）。

### 6.2 策略二：池化——把分配挪出热路径

**通俗理解**：**最优的 malloc 是没有 malloc**。请求里的对象生生死死都是同一批"形状"，何必每次找批发商进货、每次退货？——**对象池 = 自己开个私货仓库，出库入库只是指针翻转（~2ns），彻底绕过分配器**。

```cpp
// 简版 RequestContext 池：free-list + 原子栈
template <typename T>
class ObjectPool {
    std::vector<T*>   stock_;            // 预热批量 new 好的存货
    std::atomic<T*>   free_head_{nullptr};
public:
    explicit ObjectPool(size_t preheat) {
        stock_.reserve(preheat);
        for (size_t i = 0; i < preheat; ++i) stock_.push_back(new T);
        for (T* p : stock_) { p->next_ = free_head_.load(); free_head_ = p; }
    }
    T* acquire() {                        // ~2ns：CAS 弹栈顶
        T* p = free_head_.load(std::memory_order_acquire);
        while (p && !free_head_.compare_exchange_weak(p, p->next_)) {}
        return p ? p : new T;              // 池空兜底：宁可慢不能错
    }
    void release(T* p) {                   // ~2ns：CAS 压栈
        p->next_ = free_head_.load();
        while (!free_head_.compare_exchange_weak(p->next_, p)) {}
    }
};

// 用法：handle_request 里 new/delete 全换成 acquire/release
void handle_request(Request& req) {
    auto* ctx = pool_ctx.acquire();
    ...
    pool_ctx.release(ctx);                 // 真正的"复用"，不是"销毁重建"
}
```

池化削掉的三笔税：**分配器路径税**（40ns→2ns）、**arena 锁争用**（池无锁化）、**构造/析构税**（placement new 只初始化字段，不做分配）。配合[第 07 篇](/pages/9d4e72/)的语法：CAS 无锁栈在高争用下的退避，本例先用"池空兜底 new"保证正确性。

**适用边界**：
1. **先测后池**——heaptrack 显示该类型占比 <10% 就别池化，工程复杂度不划算；
2. **对象大小/类型固定才好池**——尺寸千变万化的（如变长 string）池化会退化成"自己写分配器"；
3. **注意生存期纪律**——池对象 release 后禁止再碰（use-after-free 的池版），或用 handle 间接访问；
4. **Go 有 sync.Pool、C++17 有 pmr**——别手写轮子（第 10 章跨语言表）。

### 6.3 策略三：reserve 与栈优先——少分配、不搬移

两处最容易被忽视的"分配税"，两行代码的解法：

```cpp
// 税 1：vector/map 扩容的"搬家"——push_back 到容量边界时
//       整块 2 倍重分配 + 逐个搬移（还可能退化拷贝构造）
std::vector<int> v;
v.reserve(count);          // ✅ 一次到位：分配 1 次，搬移 0 次

// 税 2：64KB string 的"反复进货退货"——本案例【嫌疑点 2】
// ✅ 方案 A：按最大尺寸 reserve 的复用缓冲（线程局部）
thread_local std::string body_buf;
body_buf.clear();                  // 容量保留，size 归零——零分配
body_buf.resize(req.body_size);    // 容量够时纯 memset，零进货

// ✅ 方案 B：能上栈就上栈——栈分配 = 移动一个栈指针（~1ns）
char body[64 * 1024];              // 64KB 在线程栈（默认 8MB）内绰绰有余
//    生命周期随作用域，连 free 都省了——"最优分配器是栈"的由来
```

`clear()` 不丢容量是 std::string/vector 的关键语义（capacity 保持），**"clear-resize 复用"是热路径缓冲的标准姿势**；C++17 的 `pmr::monotonic_buffer_resource`（一块栈内存 bump 分配、整体回收）是 arena 技巧的标准库落地——适合"请求内一次性分配、请求结束统一释放"的模式，正是网关/解析类服务的形状。

### 6.4 策略四：消灭隐式分配

heaptrack 里占比最高的往往不是显式 new，而是**库隐式分配**——三大惯犯：

```cpp
// 惯犯 1：map/unordered_map 的节点分配——一行头 new 一个 32B 节点
HeaderMap h;
h["content-type"] = ...;        // ← 每次插入隐式 operator new

// ✅ 固定小键集 → 用编译期数组/flat_map（连续内存，零节点分配）
static constexpr std::pair<std::string_view, Header*> kHeaders[] = { ... };

// 惯犯 2：string 拼接的临时对象——每次 + 产生一个新堆块
std::string url = host + ":" + port + path;    // ← 3 个临时对象

// ✅ reserve 后 append，或 format 库（fmt::format 单次分配）
std::string url; url.reserve(128);
url += host; url += ':'; url += port; url += path;

// 惯犯 3：按值传参/返回大对象（拷贝即新块）
// ✅ 移动语义 + (N)RVO：返回值直接在调用方内存上构造，零拷贝
std::string make_body();        // RVO：不发生任何"返回时的拷贝"
```

这一节与[第 04 篇（编译与链接优化）](/pages/e40d93/)的边界：本篇管"**源码层的分配模式**"，04 篇管"**编译器能帮你省掉哪些**"（RVO/move 生成、内联消除临时对象）——但方向是同一条：**热路径上的每个隐式 new 都是税**。

### 6.5 优化前后对比

| 指标 | 优化前 | 优化后 | 手段 |
|---|---|---|---|
| 稳态 RSS | 2.9 GB | **1.32 GB** | jemalloc（碎片 62%→17%）+ 池化 |
| 每请求分配次数 | ~180 | **~12** | 池化 + 消灭隐式分配 + reserve |
| P99 | 2.3 ms | **1.9 ms** | 锁争用消失 + 小分配税减少 |
| P99.9（毛刺） | 18 ms | **3.1 ms** | 64KB 大分配改复用缓冲 |
| QPS | 6900 | **7400** | 上述合力（瓶颈已转移） |
| oom_score 排名 | 第 2 | **第 11** | 稳态水位砍半的直接红利 |

读数要点：**QPS 只涨 7%**——因为 02 篇之后瓶颈已不在内存；但 **P99.9 从 18ms 到 3.1ms 与 oom_score 的改善**才是本篇真正的战场成果。内存优化的价值经常不在吞吐，而在**稳定性与密度**（同机可部署的副本数翻倍）。

## 7. 常见误区清单

### 7.1 误区一：RSS 涨就是泄漏

**现场**："RSS 一周涨了 2GB，肯定有泄漏！"——全组翻代码找 `new` 没配 `delete`，一周无果。

**破除**：
1. 先看**曲线形态**：泄漏是**线性不回头**，碎片是**先涨后趋稳**（压货饱和）——本案例的曲线趋稳就是第一线索；
2. 再看**账本**：`malloc_info`/`stats_print` 显示"in-use 只有 1.1G 而 system 2.9G"——**大半空闲却占着**，泄漏的账本长不出这个形态；
3. 最后用 **LSan/heaptrack 定检**——两小时内就能排除或坐实泄漏，比通读代码快一百倍；
4. 反向坑也存在：**碎片严重时"泄漏检测工具说没泄漏"但 RSS 就是高**——这正是 4.4 节碎片率测量的意义。

### 7.2 误区二：malloc 是系统调用

**现场**：优化清单第一条写"减少系统调用"，然后把 `malloc` 列为待消除对象。

**破除**：
1. malloc 是**用户态库函数**（第 2.1 节批发商模型）——小分配命中率 99%+ 时零过界；
2. 但这个误区**半对**：大分配（>128KB）、arena 扩容、tcache 补货**确实**产生 brk/mmap 系统调用——`strace -e brk,mmap,munmap` 量化的就是"批发频次"；
3. 正确姿势：不是"消灭 malloc"，是**消灭"过界的 malloc"**（反复大分配）与"过多次的 malloc"（热路径小分配×百万）——两个维度 strace 和 heaptrack 各测各的。

### 7.3 误区三：对象池万能

**现场**："性能不行？上对象池！"——把十几个类型全池化，代码复杂度暴涨，压测收益 2%。

**破除**：
1. 池化的前提是**该类型在 heaptrack 里占比显著**（本案例 RequestContext + Header 节点占 68%，池化才回本）；
2. 池化引入三类新成本：生存期纪律（池版 UAF 更难查）、并发正确性（无锁栈的 ABA/争用）、**大小假设**（变长对象池化=重新发明分配器）；
3. 池化之前先试**两个更便宜的**：`reserve` 复用缓冲（6.3）与消灭隐式分配（6.4）——很多"需要池"的场景，改完这两条就不需要了。

### 7.4 误区四：换了分配器就高枕无忧

**现场**：换 jemalloc 后 RSS 立降 50%，庆功。三个月后 RSS 又涨回来——因为流量涨了 3 倍，每请求 180 次分配一个没少。

**破除**：
1. 换分配器**降的是碎片常数**，**降不了分配次数**——次数税（40ns × 4 亿次/天）照交；
2. 分配模式的病（6.2-6.4）不做，碎片随流量重新堆积，jemalloc 只是推迟了拐点；
3. 防劣化的正确姿势是**把"每请求分配次数"和"稳态 RSS 水位"变成卡口**（第 8 章）——常数性优化必须配增量性防线，否则都是"借来的性能"。

## 8. 防劣化

### 8.1 CI 卡口：给分配次数与 RSS 上锁

```bash
#!/usr/bin/env bash
# mem_gate.sh —— CI 内存卡口（骨架）
set -euo pipefail
BENCH="./gateway_bench --requests 1000000"     # 固定负载

# 卡口 1：每请求分配次数（heaptrack 太慢，CI 用 ltrace 或自建 hook 计数）
ALLOC_PER_REQ=$(./alloc_counter $BENCH)        # LD_PRELOAD 计数器输出
[ "$ALLOC_PER_REQ" -lt 30 ] || { echo "❌ 每请求分配 $ALLOC_PER_REQ 次（预算 30）"; exit 1; }

# 卡口 2：稳态 RSS（跑 10 分钟后的水位，不是峰值）
RSS_MB=$(./bench_runner --warmup 300s --steady 300s --report rss)
[ "$RSS_MB" -lt 1600 ] || { echo "❌ 稳态 RSS ${RSS_MB}MB 超预算 1600MB"; exit 1; }

# 卡口 3：压测窗口内 mmap/munmap 对数（大分配反复进货的哨兵）
MMAP_PAIRS=$(strace -f -c -e trace=mmap,munmap $BENCH 2>&1 | awk '/munmap/{print $NF}' | tail -1)
[ "$MMAP_PAIRS" -lt 5000 ] || { echo "❌ 大分配进货退货 ${MMAP_PAIRS} 对"; exit 1; }

echo "✅ 内存卡口通过：alloc/req=$ALLOC_PER_REQ rss=${RSS_MB}MB mmap=$MMAP_PAIRS"
```

**预算怎么定**：与 02 篇同一纪律——先跑三轮取中位数为基线，预算 = 基线 × 1.2。内存卡口最容易被"临时大改"击穿，**每次超预算的合入必须带着归因报告**（是业务合理增长还是劣化），这条流程比数字本身重要。

### 8.2 线上监控与告警

```text
采集：RSS 曲线（带稳态/峰值双口径）          → 容器 memory.current（cgroup v2）
     oom_score 排名                          → /proc/<pid>/oom_score，每日巡检
     glibc arena 数与 mmap 对                → malloc_info 节选字段（自建 exporter）
     容器 OOM 事件                           → cgroup memory.events 的 oom 计数
告警规则：
  RSS 斜率   ：连续 3 天日涨 > 3% 且无发版     → 疑似泄漏/碎片劣化，开 4.4 节流程
  稳态水位   ：> 卡口预算 1.2 倍持续 1h        → 页面 + 自动抓 malloc_info 快照
  OOM 排名   ：进入宿主机前 3                 → 立刻复盘部署密度（10 篇容量话题）
```

内存的劣化是**所有资源里最沉默的**——CPU 高会立刻卡顿，内存高却常常"什么都没发生，直到 OOM 一刀毙命"。哨兵的价值在杀身之祸前的一周。

### 8.3 常见劣化模式清单

| 模式 | 信号 | 病根 |
|---|---|---|
| 每请求分配次数缓慢上涨 | CI 卡口 1 亮红 | 新代码引入隐式分配（map 节点/拼接临时） |
| 稳态 RSS 爬坡 | 斜率告警 | 版本引入长寿命缓存无上限（去 10 篇谈容量） |
| P99.9 尖刺复发 | 尾延迟告警 | 新增"偶发大分配"踩 mmap 阈值（4.3 节） |
| 升级 glibc 后 RSS 变化 | 同代码不同发行版表现不同 | tcache 引入/参数默认值变化——环境也要进基线 |
| arena 数暴涨 | malloc_info 里 arena 行多 | 线程数增长带动分仓——检查 02 篇的线程模型是否又劣化了 |
| 换了分配器后偶发崩 | ABI/初始化时序问题 | LD_PRELOAD 与静态初始化的加载顺序——预留启动期验证步骤 |

## 9. 综合串讲

### 9.1 一次请求的分配足迹

把案例修复前后的差别，画成"一次请求的分配足迹"知识树：

```
修复前（每请求 ~180 次分配）：
  new RequestContext ──► HeaderMap 逐节点 new ×140
        ──► string 拼接临时对象 ×30 ──► 64KB body（mmap 进货+16 次缺页）
        ──► free 全部（munmap 退货）──→ 下一个请求从零再来一遍
修复后（每请求 ~12 次分配）：
  pool.acquire（2ns 指针翻转）──► flat 头表（连续内存）
        ──► 复用缓冲 clear-resize（0 分配）──► pmr arena 内 bump 分配
        ──► 请求结束：arena 整体回收 ──→ 下一请求复用同一批仓库
```

### 9.2 设计哲学回扣

**哲学 1：批发思维——堆不是系统给的，是自己仓库里批发的**

`malloc` 慢不慢，先问"这批货是不是又要过界进货"（strace 数 mmap 对），再问"零售次数是不是太多"（heaptrack 数次数）。分配器优化的全部空间，就在"**批发次数 × 零售次数 × 压货量**"这三个变量里——它们分别对应 02 篇的批处理、本篇的池化、第 4 章的碎片治理。

**哲学 2：本地性优先——无锁快路径是一切现代分配器的共同答案**

tcache/thread cache/tcmalloc 柜台/jemalloc 分片，名字各异、内核同构：**把"最常见的事"做到线程本地无锁**。这与 [第 02 篇](/pages/2f9a64/)的 vDSO（把最常问的答案放进共享页）、[第 07 篇](/pages/9d4e72/)的 thread_local 计数是同一条哲学在三个战场的落地——**先消争用，再谈算法**。

**哲学 3：复用优先于分配——最优的 malloc 是没有 malloc**

栈 > 复用缓冲 > 对象池 > 分配器快路径 > 分配器慢路径——这是"每字节的获取成本阶梯"，设计时永远往阶梯上方走。本案例的 180→12 不是靠更快的分配器，是靠**大部分请求根本不发生分配**。内存密度（每 GB 部署的副本数）是服务端内存优化的最终商业指标，而密度只服从这一条哲学。

### 9.3 速查表

**成本速记**（数量级，供拍脑袋决策；精确值在目标环境自测——口径声明同 02 篇）：

| 操作 | 量级 |
|---|---|
| 栈分配 | ~1ns（移动栈指针） |
| 池 acquire/release（CAS 栈） | ~2-5ns |
| malloc 快路径（tcache 命中） | ~20-50ns |
| malloc 慢路径（bins + 锁） | ~100-300ns，争锁时 μs 级 |
| brk/mmap 进货（真系统调用） | ~1μs（02 篇入口费模型） |
| 首次触页（缺页，06 篇主战场） | ~1-2μs/页 |
| munmap 退货 + TLB 失效 | μs 级 + 后续访存变慢 |

**60 秒诊断命令清单**：

```bash
grep -E "VmRSS|VmData" /proc/$PID/status        # 账本水位
pmap -x $PID | sort -k3 -n | tail                # 堆段与 mmap 段分布
grep -A1 "\[heap\]" /proc/$PID/smaps             # 堆的 Private_Dirty
strace -f -c -e trace=brk,mmap,munmap -p $PID    # 进货频次（勿挂压测）
malloc_info / malloc_stats（代码内）或 jemalloc stats_print   # 碎片率金标准
heaptrack ./bin                                  # 分配形状（开发环境）
perf record -g -p $PID -- sleep 10               # 锁排队热点（__lll_lock_wait）
cat /proc/$PID/oom_score                         # 死刑排名
MALLOC_ARENA_MAX / mallopt                        # glibc 紧急止血阀
```

**归因决策树**（从症状到病根）：

```
RSS 高且线性涨 ──► LSan/heaptrack 定检 ──► 有未释放且可达 ──► 泄漏（修代码）
RSS 高先涨后稳 ──► malloc_info 账本 ────► in-use 小 system 大 ─► 碎片（§6.1 换分配器）
P99.9 尖刺   ──► strace 数 mmap 对 ────► 大分配反复进货 ────► §6.3 复用缓冲
CPU 热点在锁 ──► perf 栈底 __lll_lock_wait ← _int_malloc ────► §6.1 换分片 / §6.2 池化
oom 频发    ──► 稳态水位 vs 容器限额 ────► 密度超卖 ──────────► §8.2 + 第 10 篇容量
```

## 10. 跨语言对照

### 10.1 C++ / Rust / Go 三栏速查

| 关注点 | C++ | Rust | Go |
|---|---|---|---|
| 默认分配器 | glibc ptmalloc | 系统分配器（1.32+ 起默认；早期 jemalloc） | **内置 tcmalloc 血统（mcache/mcentral/mheap）** |
| 换分配器 | LD_PRELOAD / `-ljemalloc` | Cargo feature（如 jemalloc crate） | 不可换（runtime 一体），可调 `GOGC/GOMEMLIMIT` |
| 栈分配倾向 | 手动值语义 | **编译器强制（所有权→生命周期明确）** | **逃逸分析自动判定** |
| 池化 | 手写 / pmr（C++17） | 手写 / bumpalo | **sync.Pool（标准库）** |
| 剖析工具 | heaptrack/massif | heaptrack / cargo-flamegraph | **pprof heap（内置，alloc_space 口径）** |
| 错误检测 | ASan/Valgrind | Miri / ASan | race detector（无内存错误检测——GC 免除） |
| 内存上限 | cgroup 限额 | cgroup 限额 | **GOMEMLIMIT（1.19+，软上限）** |

### 10.2 Go 为什么感觉不怕堆分配

**通俗理解**：Go 像一家"统一配送"的公司——你写 `&User{}` 从不关心它住哪，编译器的**逃逸分析**替你做本篇 6.3 节的决策：**能栈则栈，逃逸才堆**；堆上的垃圾有 GC 打扫，看似"分配免费"。

但本篇的账单 Go 一分都免不了，三点认知差：
1. **分配本身仍是税**——Go 的 mcache 快路径 ~30ns 级别，但每请求几十万个对象照样压垮 P99（pprof 的 `alloc_space`/`alloc_objects` 就是 heaptrack 的 Go 版，按累计口径抓"分配大户"）；
2. **GC 是延迟的账单**——分配免费、回收集中：GC 的 STW/mark 协助让**分配速率直接决定毛刺频率**（`GOGC` 调低省 CPU 但涨 RSS，`GOMEMLIMIT` 反之——本质是"碎片税"换了收法）；
3. **心智模型的迁移**——Go 程序员做本篇优化的姿势：`sync.Pool` 复用（6.2）、预分配 slice（6.3 的 `make(n)` 带 cap）、`strings.Builder`（6.4 的拼接税）——与 C++ 完全同构，只是工具名换了。

一句话收束全篇：**分配器的语言可以不同，批发-零售-压货的经济学从不变**——看懂本篇的账本，任何语言的内存告警你都能归因。
