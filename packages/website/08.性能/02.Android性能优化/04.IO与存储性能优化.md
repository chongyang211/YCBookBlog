## 01.开篇灵魂拷问

读文章前，先问自己三个问题。答得上来，说明你已理解；答不上来，就是本文的学习目标。

### 1.1 异步之惑

**Q：`SharedPreferences.apply()` 不是官方声明"异步落盘不阻塞"吗？为什么把 commit 改成 apply 后 ANR 率反而从 0.61% 升到 0.78%？**

**🤔 疑惑**：API 文档明明白白写"apply 是异步的"，怎么还会阻塞主线程？

**💡 解答**：**apply() 的"异步"是半真半假**——它只保证"**调用方立即返回**"，但生命周期关键点（onPause/onStop/onDestroy）会**强制同步等待所有未落盘的 apply 完成**（AOSP 源码 `QueuedWork.waitToFinish()`）。日志狂写导致队列堆积，用户按 Home 瞬间触发 onStop，所有积压 apply 全在主线程同步刷盘 → 一次性 ANR。

> **心法**：**异步 API 从来不是"不阻塞"的承诺，是"**延迟阻塞**"的承诺**——阻塞被挪到了你看不见的时刻（生命周期切换/App 退后台），症状更隐蔽更致命。

### 1.2 CPU之惑

**Q：Perfetto / Android Studio Profiler 显示 CPU 占用只有 8-15%，看板一片绿——但用户卡到骂娘。CPU 空闲还能卡？**

**🤔 疑惑**：所有性能工具都告诉我"健康"，但线上投诉还在涨，到底是工具坏了还是用户矫情？

**💡 解答**：**IO 是 CPU profiler 的盲区**。线程在 fsync/read 等系统调用里等待时处于 **"D 状态"（Uninterruptible Sleep）**——不消耗 CPU 时间，但完全阻塞不能被抢占。CPU 占用低恰恰是 IO bound 的典型特征——**"CPU 不忙但卡"= 大概率 IO 阻塞**。

> **心法**：好工程师要会"**看缺席的数据**"——CPU profiler 上的"一片绿"不是"健康"的证明，而是"**问题在工具的盲区**"的信号。**测量工具的盲区就是优化的盲区**。

### 1.3 批量之惑

**Q：日志从"80 条/s + 每条独立 commit"改成"1000 条批量 + 一次 commit"后，吞吐从 80 条/s 飙到 3500 条/s（43×）。为什么就是"把多次写合并成一次"而已，收益能到两个数量级？**

**🤔 疑惑**：直觉上，总共要写的数据没变，为什么合批后速度能快两个数量级？

**💡 解答**：**fsync 的开销不随写入量线性**——它是"**固定仪式成本**"。单次 fsync 的开销 = 介质 ACK + 元数据刷新 + 页对齐开销 ≈ **1-200ms**，与写 1 字节还是写 100KB 几乎无关。1000 次独立 fsync vs 1 次合并 fsync，总开销差 **1000 倍级**。这就是"**聚合效应**"——把 N 次仪式成本摊销到 1 次。

> **心法**：**IO 优化的黄金等式**：`N × 固定成本 >> 1 × (固定成本 + N × 增量成本)`。所以"合批"是 IO 优化的"**第一板斧**"——任何高频 IO 操作，先问"**能不能合批**"，再谈其他。

## 02.探索问题本质

### 2.1 现象分类

IO 问题的工程症状可以归为**四类现象**，不同现象对应不同根因：

| 现象 | 典型表现 | 底层根因 | 对应章节 |
|---|---|---|---|
| **主线程卡顿** | FPS 掉、点击延迟 | 主线程调用了 fsync/read/SQLite | §3.1 §5.3 |
| **ANR** | 5s 无响应被系统杀 | 累积 IO + 生命周期切换 | §3.1 §5.3 |
| **启动慢** | 冷启 1.5s → 4s | 启动期 IO 量 > 5MB | §5.1 §5.4 |
| **耗电/发热** | 后台 IO 频繁 | writeback 唤醒 CPU | §5.5 §10 |

**反直觉结论**：**同一类现象可能来自完全不同的根因**。例如"卡顿"可能是：fsync 阻塞（直接）、apply 累积（延迟）、Core Data 查询（隐式）、writeback 抢 IO 带宽（间接）——这就是为什么**决策树**（§3.1）比"直觉经验"更可靠。

> ▶▶ **回扣贯穿案例**：阅读 App 同时命中前三类——日志每条 fsync（卡顿）+ apply 累积（ANR）+ 启动期日志回放（启动慢）。看似三个问题，根因都是"每条日志 = 1 次 INSERT + 1 次 fsync + 1 次 apply"。

### 2.2 黄金公式

把 IO 耗时拆成三个独立维度，所有优化都是针对其中之一：

```
   T_io = T_syscall × N_syscall + T_fsync × N_fsync + Bytes / Bandwidth
          ┬────────────────────   ┬─────────────────   ┬───────────────
          │                       │                   │
   ① 系统调用成本（μs 级）     ② 落盘仪式成本（ms 级）  ③ 数据带宽成本
   
   典型值（低端机）：
     T_syscall ≈ 10μs
     T_fsync   ≈ 1-200ms（主导项！）
     Bandwidth ≈ 50 MB/s（eMMC）/ 500 MB/s（UFS 3.0）
```

**三条推论**：

1. **fsync 是"杀手项"**：量级比 syscall 大 3 个数量级——高频 IO 场景 90% 的时间都花在 fsync 上；
2. **带宽项通常不是瓶颈**：移动端 IO 很少打满带宽（除非大文件连续读写），单条小写几乎不受带宽影响；
3. **syscall 项仅在"百万级小调用"时显现**：BufferedOutputStream 优化的是这一项，但收益远不如治 fsync。

> **心法**：**优化 IO 先治 fsync，次治 syscall，再治带宽**——顺序错了就是白干。

**▶▶ 公式实例化**（贯穿案例）：

```
   原始日志：80 条/s × (1 INSERT fsync + 1 apply fsync) = 160 次 fsync/s
          = 160 × 50ms（低端机均值）= 8000ms/s（800% CPU 等价）
          必然 ANR
   
   方法派改造后：1000 条/批 × 1 fsync = 1 次 fsync/批 = 20ms/批
          批频率 3.5 批/s → 70ms/s（7% 等价）
          完全在预算内
```

### 2.3 落盘三级语义

**IO 可靠性的"三道闸门"**决定数据到底写到了哪：

```
   应用调用          到达层级                    崩溃丢失边界            耗时
   ─────────────────────────────────────────────────────────────────────
   write()      ───▶ 用户态 buffer 或 page cache  进程崩溃就丢          ~10μs
   fflush()     ───▶ 刷到 page cache              断电就丢              ~10μs  
   fsync()      ───▶ 强制落盘 + 等硬件 ACK        仅硬件损坏才丢        1-200ms
   fdatasync()  ───▶ 仅刷数据不刷元数据           同 fsync（文件大小滞后）  比 fsync 快 10-30%
   mmap+msync   ───▶ 内核托管刷脏页               崩溃丢未 msync 的 30s   异步
```

**工程选型三原则**：

| 场景 | 选哪个 | 原因 |
|---|---|---|
| **临时文件/缓存** | write 即可 | 丢了无所谓，追求速度 |
| **日志/统计** | mmap + msync 兜底 | 大批量，断点可容忍 |
| **订单/支付/关键配置** | fsync 每次 | 零丢失，牺牲速度 |
| **数据库事务** | fsync（WAL commit 自带） | 完整性优先 |

**反直觉事实**：**write 快不代表"数据已保存"**——很多工程师直觉以为 write 完成了就"落地了"，实际上在 page cache 里，断电秒丢。关键数据必须显式 fsync，哪怕慢。

### 2.4 介质差异矩阵

**存储介质的延迟差距横跨 7 个数量级**（这是 IO 性能理解的物理基石）：

```
   L1 cache:        1 ns       （类比：1 秒）
   内存:            100 ns     （类比：1.5 分钟）
   SSD 随机读:      100 μs     （类比：1 天）
   SSD 随机写:      1 ms       （类比：10 天）
   eMMC 顺序写:     20 ms      （类比：200 天）
   低端 eMMC 末期:  50-200 ms  （类比：2-5 年）
   HDD 寻道:        10 ms      （类比：100 天）
```

**移动设备介质现状**：

| 设备档位 | 介质 | 顺序写 | 随机写 | 寿命末期恶化 |
|---|---|---|---|---|
| 旗舰（UFS 3.1） | UFS | 1500 MB/s | ~1ms | +50% |
| 中端（UFS 2.1） | UFS | 500 MB/s | ~2ms | +100% |
| 低端（eMMC 5.1） | eMMC | 150 MB/s | ~5ms | +300% |
| 极端低端（eMMC 老化） | eMMC | 50 MB/s | **50-200ms** | +1000% |

**关键洞察**：**同一 App 在高端机 50ms 完成的 IO，在低端机末期可能需要 2000ms**——40 倍差异。这就是为什么**"性能优化本质是给低端机让出预算"**。

> ▶▶ **回扣贯穿案例**：低端机 SQLite 主线程写 P99 达 820ms——"每条 INSERT + fsync 耗时 50-200ms × 累积多条"的典型表现。高端机根本看不出来，灰度到低端机瞬间爆雷。

### 2.5 面试锚点

**Q：讲一下 IO 性能和 CPU/内存性能本质上有什么不同？为什么 IO 问题这么难查？**

**答题模板**（三约束 + 工具盲区）：

> IO 的本质决定了它和 CPU/内存**完全不同**：
>
> **① 延迟差距 7 个数量级**：内存 100ns、SSD 1ms、低端 eMMC 末期 200ms——一个 fsync 相当于 2000 万次内存访问。CPU/内存的性能差异在"倍数"级，IO 在"数量级"级。
>
> **② fsync 是硬同步阻塞**：write 只到 page cache（μs 级，不等落盘），fsync 才真正强制刷盘（ms 到百 ms 级）。工程里"数据可靠"和"性能"是零和博弈，不像 CPU 可以用"异步"绕过去。
>
> **③ 小文件惩罚**：1000 个 1KB 文件比 1 个 1MB 文件慢 27 倍（§5.0 实验三）——因为每个文件都要走 inode 查找、目录遍历、元数据更新。CPU/内存不存在"数量放大效应"。
>
> **难查的本质**：**IO 阻塞时 CPU 占用是 0**——CPU profiler 上一片绿、Android Vitals 看不出异常，但用户卡到骂娘。线程卡在"**D 状态**"（Uninterruptible Sleep），不消耗 CPU 时间但完全阻塞。所有基于"CPU 占用"的监控工具都看不见 IO 问题。
>
> **一句话总结**：**CPU/内存问题看"忙在哪"，IO 问题看"**等在哪**"**——换一套工具链（iostat/strace/StrictMode），换一套思维（IO bound 时 CPU 低才正常）。

## 03.排查归因方法

### 3.1 归因决策树

IO 问题的归因是**结构化的**——不像业务 Bug 千变万化，IO 问题的根因可以用一棵决策树穷举：

```
   卡顿 / ANR / 启动慢
      │
      ├─ 【第一问】CPU 占用高吗？
      │     ├─ 高（> 60%）→ CPU bound 问题（见 §01 CPU 篇）
      │     └─ 低（< 30%）→ ★ 大概率是 IO 阻塞
      │              │
      │              ├─ 【第二问】主线程吗？
      │              │     ├─ 是 → ★ 主线程 IO，必治
      │              │     └─ 否 → 跨线程锁等待 or 主线程在等异步 IO
      │              │
      │              └─ 【第三问】什么 API？
      │                    ├─ SharedPreferences → apply 累积？commit 同步？
      │                    ├─ SQLite → 事务？WAL？索引？
      │                    ├─ 文件读写 → fsync？小文件？未缓冲？
      │                    ├─ 日志库 → 批量？异步？
      │                    └─ 网络缓存 → 落盘路径？
      │
      └─ 【第四问】IO 量大吗？
            ├─ 量大（> 10MB/s）→ 算法层优化（合并/分片/压缩）
            └─ 量小但慢 → 物理层问题（碎片/磁盘满/低端机颗粒劣化）
```

**关键原则**：**三问必走，不能跳步**——跳过"CPU 高吗？"就可能把 CPU 瓶颈误诊成 IO；跳过"主线程吗？"就可能把子线程 IO（通常无害）当成主要矛盾。

> ▶▶ **回扣贯穿案例**：方法派 Day 2 严格走决策树——① CPU 低（8-15%）→ IO 问题 ✓ ② 主线程 ✓ ③ API：SharedPreferences 用 apply 但累积、SQLite 无事务、每条单独写 ✓。3 分钟定位，没有一步猜。

### 3.2 IO 四象限

把"**IO 位置**（主线程 / 子线程）× **IO 量级**（高频小量 / 低频大量）"交叉，得到四象限：

| 位置 \ 量级 | **高频小量**（> 100 次/s） | **低频大量**（单次 > 1MB） |
|---|---|---|
| **主线程** | ★★★★ **火山区**（ANR/卡顿必爆）<br>日志、埋点、apply 滥用 | ★★★★ **冰山区**（启动慢/卡顿）<br>启动期大 JSON 读、Core Data 查询 |
| **子线程** | ★★ **预警区**（内存压力/带宽占用）<br>后台日志、缓存写 | ★★ **常规区**（通常无害）<br>图片下载、备份 |

**治理优先级**：先治"**火山区**"（主线程高频小量，§5.3 异之路）→ 再治"**冰山区**"（主线程低频大量，§5.1 少之路+§5.4 缩之路）→ 再治"预警区"（子线程高频，§5.2 批之路）→ "常规区"通常不需要治。

**▶▶ 四象限的工程意义**：

1. **火山区**占 IO 事故的 **70%**——所有 ANR/卡顿类 IO 问题几乎都在这里；
2. **冰山区**占 IO 事故的 **20%**——启动慢的主要来源；
3. **预警区**占 **8%**——通常是"偶发"（电量/发热反馈）；
4. **常规区**占 **2%**——除非真的量级极大（> 100MB），否则不用管。

### 3.3 StrictMode 识图

**StrictMode 是 Android 平台的"IO X 光片"**——开发期一开，所有主线程 IO 立刻红屏暴露：

```kotlin
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(
        StrictMode.ThreadPolicy.Builder()
            .detectDiskReads()
            .detectDiskWrites()
            .detectNetwork()
            .penaltyLog()
            .penaltyDeath()  // Debug 版直接 crash 暴露
            .build()
    )
}
```

**StrictMode 识图三要点**：

| 看什么 | 含义 | 典型根因 |
|---|---|---|
| **DiskReadViolation 栈顶** | 主线程读哪里 | SP 初次 load / 大文件读 / SQLite query |
| **DiskWriteViolation 栈顶** | 主线程写哪里 | log 库 / commit 同步 / 自写文件 |
| **栈深度 20+ 且含 getSharedPreferences** | SP 首次加载同步阻塞 | 应用启动期误用 SP 加载大 KV |

**跨平台等价工具**：

| 平台 | 工具 | 使用方式 |
|---|---|---|
| Android | StrictMode | 一行代码 |
| iOS | 自实现 Hook NSFileHandle + runtime check | 更复杂 |
| Web | Chrome DevTools Performance → Main Thread IO | 自动标记 |
| Linux | strace -e trace=file -p pid | 命令行 |

### 3.4 案例归因

**贯穿案例的归因全过程**：

**Step 1：现象 → 决策树第一问**

- 现象：ANR 率飙升到 0.61%、冷启动 P95 4.1s
- CPU 占用：8-15%（低！）→ 大概率 IO

**Step 2：定位主线程**

- StrictMode 开启：扫出 `DiskWriteViolation` 栈顶 `SharedPreferences$EditorImpl.commitToMemory → QueuedWork.waitToFinish`
- 确认：日志库大量 `apply()` 在主线程调用

**Step 3：API 分析**

- 日志库代码：每条日志 → `SQLite INSERT + apply`
- 问题：
  - SQLite 无事务，每条 INSERT 触发一次 fsync
  - apply 看似异步，但 lifecycle 切换时同步等待
  - 低端机 fsync 单次 50-200ms × 累积 → ANR

**Step 4：量级分析**

- /proc/[pid]/io 显示：write_bytes 47MB/分钟（异常高）
- iostat：写 IOPS 1200+（远超低端机能力）
- 结论：**量级 + 位置 + API 三维度全部命中火山区**

**Step 5：方案映射**

| 维度 | 根因 | 对应治理 |
|---|---|---|
| 位置 | 主线程 | §5.3 异之路：日志完全异步线程 |
| 量级 | 高频小写 | §5.2 批之路：1000 条/批 + 事务 |
| API | apply/SQLite 无事务 | §5.8 KV 深度治理（MMKV 替代）+ §5.7 数据库深度治理（WAL） |
| 介质放大 | 低端机颗粒 | §5.4 缩之路：protobuf 替代 JSON |

**Step 6：验证**

- 实测收益：ANR 0.78%→0.05%、冷启 4.6s→1.3s、吞吐 80→3500 条/s
- 预测误差 < 15%，闭环验证成功

### 3.5 面试锚点

**Q：遇到用户反馈"我这里卡"，但 Perfetto 看 CPU 一片绿，你怎么定位是不是 IO 问题？**

**答题模板**（三问 + 工具链 + 兜底）：

> CPU 低但卡的典型信号就是**IO 阻塞**。我会按**三问法**定位：
>
> **① CPU 占用 vs iowait 比值**：先看 `/proc/[pid]/stat` 的 CPU 占用，再看 `/proc/[pid]/io` 的 wait/等待时长。如果 CPU 占用低但 **blockio\_delay 高**，100% 是 IO bound。
>
> **② StrictMode 定位主线程 IO**：开发期一键开启，重现用户路径，看哪一行 Java 代码触发了 DiskReadViolation/DiskWriteViolation。线上版用 penaltyLog 收集栈。
>
> **③ 应用层 AOP 埋点**：hook FileInputStream/SQLiteDatabase/MMKV，记录调用方 + 耗时。线上 1% 用户采样，> 16ms 的调用上报栈。
>
> **兜底手段**：如果用户设备拿不到，让用户抓 Perfetto trace（Android 10+），本地分析 **sched_switch 事件中线程停留在 D 状态的时长**——这是 IO 阻塞的"地面真相"。
>
> **一句话总结**：**CPU profiler 看不见 IO，必须换工具链**——StrictMode/iostat/trace 三件套配合，没有 IO 问题躲得掉。

## 04.IO监控体系

### 4.1 采集三层

IO 监控的核心矛盾是"**粒度 vs 开销**"——想要调用栈必须 hook，一 hook 就拖慢被测物（Heisenberg 原理的工程版本）。所以永远**三层组合**：

```
   ┌──────────────────────────────────┐
   │ ① 系统级（iostat / /proc/diskstats）│  设备视图  极低开销  无归因
   ├──────────────────────────────────┤
   │ ② 进程级（/proc/[pid]/io）         │  进程视图  低开销    无栈
   ├──────────────────────────────────┤
   │ ③ 应用层（AOP hook + 埋点）        │  业务视图  5-10% 开销 有栈
   └──────────────────────────────────┘
```

**① 系统级 IO 监控**

```bash
# Android
adb shell iostat 1       # 每秒刷新
adb shell cat /proc/diskstats

# 关键列：rkB/s, wkB/s, await (IO 等待时间 ms), %util (设备利用率)
```

**适用场景**：服务端 CI 基准测试；端上抽样诊断。

**② 进程级 IO 追踪**

```bash
# Android
adb shell cat /proc/$(pidof com.example.app)/io

# 输出字段：
#   rchar: 读字节总数（含 cache 命中）
#   wchar: 写字节总数
#   read_bytes: 实际从介质读
#   write_bytes: 实际写入介质（含 writeback）
#   syscr/syscw: 系统调用次数
```

**适用场景**：线上 1% 用户采样，无开销定位进程异常。

**③ 应用层 AOP 埋点**

```kotlin
class IOTimingAspect {
    inline fun <T> timed(tag: String, call: () -> T): T {
        val start = SystemClock.elapsedRealtimeNanos()
        try { return call() }
        finally {
            val durMs = (SystemClock.elapsedRealtimeNanos() - start) / 1_000_000
            if (Looper.myLooper() == Looper.getMainLooper() && durMs > 16) {
                report(tag, durMs, Throwable().stackTraceToString())
            }
        }
    }
}
```

**适用场景**：业务级归因，必有调用栈 + 耗时 + 业务 tag。

### 4.2 IO 三大骗局

**骗局一：apply 是异步的**

- **表面认知**：API 文档写"异步"，调用返回快，所以不阻塞主线程。
- **物理真相**：apply 把 commit 排入 QueuedWork 队列，调用确实立即返回；但 **Activity.onPause/Service.onStart 等生命周期关键点，系统强制调用 `QueuedWork.waitToFinish()` 同步等所有未落盘 commit 完成**。累积 100 次 apply，onPause 直接卡 80-200ms（低端机）。
- **破骗要点**：apply ≠ 不阻塞，是"**延迟阻塞**"——用 MMKV 替代，MMKV 走 mmap 真异步。

**骗局二：CPU 占用低 = 性能健康**

- **表面认知**：Perfetto/Android Studio Profiler 显示 CPU 20%，看板全绿。
- **物理真相**：IO 阻塞时线程在"**D 状态**"（Uninterruptible Sleep），**不消耗 CPU 时间**。所有基于"CPU 占用率"的工具都看不见 IO。
- **破骗要点**：对比 CPU 占用 vs iowait，看 `/proc/[pid]/stat` 中的 **blocked_io_delay** 字段。

**骗局三：日志每条 < 5ms，不会出事**

- **表面认知**：StrictMode 测单次 log 调用 2-5ms，看起来人畜无害。
- **物理真相**：**IO 开销不是线性累积**——100 次 × 5ms ≠ 500ms，而是**累积阻塞 + 生命周期触发同步刷盘 + GC + Writeback 竞争 → 可能一次性 800-2000ms ANR**。
- **破骗要点**：IO 事故永远不看单次，看"**最差百分位 + 累积场景**"（P99 + onPause 累积测试）。

### 4.3 健康基准

**线上 IO 性能的"及格线"**：

| 指标 | 目标值 | 告警阈值 | 测量方式 |
|---|---|---|---|
| **主线程单次 IO 耗时 P95** | ≤ 16ms | > 50ms | AOP hook |
| **主线程总 IO 时长占比** | ≤ 5% | > 15% | 采样统计 |
| **数据库主线程查询 P99** | ≤ 50ms | > 200ms | AOP hook |
| **启动期 IO 总量** | ≤ 5MB | > 10MB | /proc/io 快照 |
| **ANR 中 IO 类占比** | < 10% | > 30% | ANR 栈分析 |
| **主线程 IO 频次** | ≤ 10 次/s | > 50 次/s | AOP hook |

**各档位设备的差异化基准**：

| 档位 | 单次 IO P95 | fsync P99 | 启动 IO |
|---|---|---|---|
| 旗舰（UFS 3.1） | ≤ 10ms | ≤ 20ms | ≤ 8MB |
| 中端（UFS 2.1） | ≤ 16ms | ≤ 50ms | ≤ 5MB |
| 低端（eMMC） | ≤ 30ms | ≤ 150ms | ≤ 3MB |

> **心法**：**IO 基准必须按设备档位分开定**，不能用旗舰机的基准卡低端机——那是治标不治本。

### 4.4 测量七坑

| # | 坑 | 症状 | 规避 |
|---|---|---|---|
| 1 | **page cache 作弊** | 第二次读相同文件秒出，误以为"优化生效" | 测前 `echo 3 > /proc/sys/vm/drop_caches` 清缓存 |
| 2 | **写入未落盘就测完** | write 返回快，但数据在 page cache，fsync 才是真实耗时 | 测写入必须包 fsync |
| 3 | **只测单次** | 单次 fsync 5ms 看着没事，100 次累积 500ms 爆雷 | 测百分位分布（P50/P95/P99/Max） |
| 4 | **只测高端机** | 旗舰机 UFS 3.1 看不出来，低端机 eMMC 爆雷 | 必测低端机覆盖 90% 用户 |
| 5 | **忽略 writeback 影响** | 测时 writeback 正在刷别的 app 的脏页，带宽被抢 | 测前 sync 一下，等 writeback 完成 |
| 6 | **AOP hook 自己也拖慢** | 加了 hook 后测的是 "IO + hook" 的总耗时 | hook 开销独立测，减去 |
| 7 | **StrictMode 自身的误报** | Glide/EasyPermissions 等库会误报，淹没真正问题 | 配置白名单 |

### 4.5 工具速查

**跨平台 IO 工具对照**：

| 平台 | 系统级 | 进程级 | 调用栈 | 可视化 |
|---|---|---|---|---|
| Android | iostat / `/proc/diskstats` | `/proc/[pid]/io` | StrictMode / Perfetto fsync 事件 | Android Studio Profiler |
| iOS | `task_info` | `task_info` | Instruments File Activity | Instruments Time Profiler |
| Web | （沙盒无） | （沙盒无） | DevTools Performance | DevTools Network/IO |
| Linux | iostat / blktrace | `/proc/[pid]/io` | strace / perf trace | Flame Graph |

**关键 API 速查**：

| 操作 | Android | iOS | Web |
|---|---|---|---|
| 主线程 IO 拦截 | StrictMode | 自实现 Hook | （无原生）|
| 高性能 KV | MMKV | MMKV/UserDefaults | IndexedDB |

### 4.6 面试锚点

**Q：线上 IO 监控怎么做？用户反馈卡但你拿不到设备，怎么复现定位？**

**答题模板**（三方案组合 + 线上降级 + 远程诊断）：

> 线上 IO 监控的核心是"**既要抓到问题，又不能拖慢应用**"：
>
> **① 分层采集**：
> - 系统级 iostat（设备视图，服务端跑 CI 基准）；
> - 进程级 /proc/io（线上 1% 用户抽样，无开销）；
> - 应用层 AOP hook（线上 1% 采样 + 16ms 阈值过滤，10% 开销可接受）。
>
> **② 线上降级策略**（可动态调开关）：
> - **常态**：方案③ 1% 采样 + 16ms 阈值；
> - **异常时**：10% 采样 + 完整栈上报；
> - **熔断**：全部采集关闭（避免采集本身加剧问题）。
>
> **③ 远程诊断**：拿不到设备就引导用户抓 Perfetto trace（Android 10+ 一键），trace 中看 `sched_switch` 事件里**线程在 D 状态的停留时长**——这就是 IO 阻塞的"地面真相"，比任何采样都准确。
>
> **破三大骗局**：apply 不是异步（看 QueuedWork.waitToFinish）、CPU 低不是健康（看 iowait）、单次快不是没事（看累积百分位）——面试里能说出这三条，就是方法派。
>
> **一句话总结**：**IO 监控是"分层采集 + 阈值过滤 + 远程兜底"的组合拳**——没有银弹，只有多工具协同。

## 05.分层治理优化

### 5.0 五组量化实验

**本节是治理的"**求证基石**"**。每个治理动作都对应一组实验数据，没有数据的优化等于凭直觉乱改。

**实验一：主线程 SP 的真实代价**（破"apply 异步"骗局）

| 设备 | 100 次 apply 本身耗时 | onPause 阻塞时长 |
|---|---|---|
| 高端机（Pixel 6） | < 5ms | 30-50ms |
| 中端机 | 6ms | 50-100ms |
| 低端机（Android 8） | 8ms | **80-200ms** |

**启示**：apply 返回快 ≠ 不阻塞——生命周期切换时同步等待。**用 MMKV 替代，高频写 100× 加速**。

**实验二：批量 vs 逐条写入**（证明批量是圣杯）

| 实现 | 1 万条耗时 | fsync 次数 |
|---|---|---|
| 逐条 INSERT（无事务） | **28 秒** | 10000 |
| 事务包裹批量 INSERT | **0.4 秒**（**70×**） | 1 |
| 多行 INSERT | 0.3 秒（93×） | 1 |

**启示**：**fsync 是瓶颈**，事务把 1 万次 fsync 合并成 1 次。

**实验三：小文件惩罚**（证明聚合存储的必要性）

| 实现 | 总耗时 |
|---|---|
| 1 个 100MB 文件 | 0.8s |
| 100 个 1MB 文件 | 1.5s |
| 1 万个 10KB 文件 | **22s（27×）** |

**启示**：每个文件都要 open/close/fsync 元数据，inode 锁竞争严重。缓存设计避免"一 key 一文件"，用 LevelDB/SQLite 聚合。

**实验四：WAL vs DELETE**（SQLite 性能的"开关")

| 模式 | 读吞吐 | 写吞吐 | 读 P99 | 写 P99 | 磁盘开销 |
|---|---|---|---|---|---|
| DELETE | 1,200 op/s | 350 op/s | 28 ms | 180 ms | 0 额外 |
| WAL | **8,500 op/s** | **1,800 op/s** | **5 ms** | **15 ms** | +5-50MB |

**启示**：WAL 写不阻塞读，吞吐 3-7×。**90% 的 SQLite 场景都应启用 WAL**。

**实验五：mmap vs fsync**（高频小写的终极武器）

| 场景 | 普通 IO + fsync | mmap (MMKV) | 增益 |
|---|---|---|---|
| 100×100B/s 持续 60s | 12,500 ms | **125 ms** | **100×** |
| 10×10KB/s 持续 60s | 850 ms | **45 ms** | 19× |
| 单次 1MB 顺序写 | 8 ms | 4 ms | 2× |

**启示**：**高频小写是 mmap 的杀手锏**；大数据场景增益收窄（IO 主导，不是 syscall 主导）。

**五大实验启示合集**：

```
   SP apply 假异步     → onPause 累积阻塞，必须用 MMKV       ─┐
   批量 vs 逐条        → 事务让 fsync 合并，70×              │
   小文件惩罚          → 1 万个 10KB 比 1 个 100MB 慢 27×   ├─▶ IO 优化 = 物理介质 × API 选型 × 使用方式
   WAL vs DELETE       → 读写并发，吞吐 3-7×                │
   mmap vs fsync       → 高频小写 100×，大数据 2×           ─┘
```

> **心法**：**没有实验就是经验派；有实验+定律才是方法派**。接下来的治理（§5.1-§5.8）每个动作都对应其中一组实验的物理机理。

### 5.1 少之路：量级最小化

**核心命题**：**能不写就不写；必须写就压缩**。

**5.1.1 缓存命中即返回**

```kotlin
class TieredCache<K, V> {
    private val memCache = LruCache<K, V>(100)
    
    fun get(key: K, loader: () -> V): V {
        memCache.get(key)?.let { return it }  // 0 IO
        val v = loadFromDisk(key) ?: loader().also { saveToDisk(key, it) }
        memCache.put(key, v)
        return v
    }
}
```

**收益**：热点数据 IO 频次 -90%。**边界**：缓存一致性需通过版本号 / push 失效。

**5.1.2 启动期 IO 延迟到首屏后**

- 启动期任何 IO 都直接拖慢冷启动，必须延迟。
- 原则：**首帧前零 IO**；用户看到首屏后再异步 warm up 缓存/日志。

```kotlin
// Application.onCreate 不写 IO
// 把配置读取延迟到首屏完成后
view.doOnPreDraw { 
    lifecycleScope.launch(Dispatchers.IO) { prepareCache() }
}
```

**5.1.3 小文件聚合存储**

```kotlin
// 反例：每个图片缩略图一个文件
File("$cacheDir/thumb_$id.png").writeBytes(bytes)

// 正例：聚合到 SQLite 或 LevelDB
db.execSQL("INSERT INTO thumbs (id, data) VALUES (?, ?)", arrayOf(id, bytes))
```

**收益**：千级以上小文件场景 IO 时间 -90%（§5.0 实验三）。

> **心法**：**优化顺序：先想能不能不做，再想能不能少做**。少一次 IO 永远比快一次 IO 收益大。

### 5.2 批之路：事务合并

**核心命题**：**N 次仪式 >> 1 次合批**——这是 §1.3 批量之惑的根本解。

**5.2.1 SQLite 事务批量化**

```kotlin
// ❌ 反例：10000 次 fsync
items.forEach { db.execSQL("INSERT...", it) }

// ✅ 正例：1 次 fsync（70×）
db.beginTransaction()
try {
    items.forEach { db.execSQL("INSERT...", it) }
    db.setTransactionSuccessful()
} finally {
    db.endTransaction()
}
```

**边界**：事务内不能做长任务；事务过大（> 10MB）会触发 WAL 膨胀。

**5.2.2 异步缓冲 + 定时批刷**

```kotlin
class AsyncLogger {
    private val buffer = ConcurrentLinkedQueue<LogEntry>()
    private val executor = Executors.newSingleThreadExecutor()
    
    fun log(entry: LogEntry) {
        buffer.offer(entry)                        // 主线程 μs 级
        if (buffer.size >= 1000) flushAsync()      // 达阈值批刷
    }
    
    init {
        // 定时兜底：避免数据长期停留在缓冲
        scheduledExecutor.scheduleAtFixedRate({ flushAsync() }, 5, 5, SECONDS)
    }
}
```

**5.2.3 文件 IO 缓冲**

```kotlin
BufferedOutputStream(FileOutputStream(file), 64 * 1024).use { out ->
    data.forEach { out.write(it.toByteArray()) }
}  // close 时 flush 一次 → syscall 次数 -100×
```

> **心法**：**批量 ≠ 多次调用**，批量 = **一次事务里多次操作**——这是贯穿案例第 4 周翻车的根因。

### 5.3 异之路：主线程零 IO

**核心命题**：主线程 IO 是性能问题的最大单点，这一层"**0 容忍**"是基础。

**5.3.1 StrictMode 全量拦截 + penaltyDeath**

见 §3.3 代码。开发期 100% 拦截；Release 版用 penaltyLog 收集。

**5.3.2 SharedPreferences 全面迁移到 MMKV**

```kotlin
// ❌ 反例
val sp = context.getSharedPreferences("config", MODE_PRIVATE)
sp.edit().putString("key", value).apply()

// ✅ 正例
MMKV.initialize(context)
val mmkv = MMKV.defaultMMKV()
mmkv.encode("key", value)  // 真异步，无生命周期等待
```

**5.3.3 所有 SQLite 操作走子线程**

```kotlin
viewModelScope.launch(Dispatchers.IO) {
    val users = db.userDao().getAll()
    withContext(Dispatchers.Main) { adapter.submitList(users) }
}
```

**边界**：Room 默认在主线程会 throw（除非 `allowMainThreadQueries()` 显式开启）——可用此特性强制约束。

**5.3.4 日志/统计走异步缓冲**

见 §5.2.2 代码。关键原则：**主线程仅入队，刷盘在子线程**。

> **心法**：**异步优先的思维要刻进肌肉记忆**——每次写 `prefs.edit().apply()` 前，先问"这能异步吗？"。

### 5.4 缩之路：压缩+二进制

**核心命题**：**CPU 换 IO 永远划算**——CPU 是 ns 级、IO 是 ms 级，6 个数量级差距。

**5.4.1 数据压缩**

```kotlin
// 写入压缩
val compressed = gzip(jsonBytes)
file.writeBytes(compressed)

// 读取解压
val bytes = gunzip(file.readBytes())
```

**收益**：磁盘空间 -60%，IO 时间 -50%。**边界**：小文件（< 4KB）压缩收益小；CPU 紧张设备需评估。

**5.4.2 协议升级（PB / FlatBuffer 替代 JSON）**

| 格式 | 体积 | 解析速度 | 易用 |
|---|---|---|---|
| JSON | 100% | 1× | 高 |
| Protobuf | 50% | 3× | 中 |
| FlatBuffer | 50% | 10×（零拷贝） | 低 |

**边界**：PB 需双端协议同步；schema 变更需兼容设计。

**5.4.3 列式存储（大批量场景）**

- 行式存储：每条记录完整存，适合"按主键查整条"；
- 列式存储：按列存，适合"统计/分析场景"，压缩率 +30%、读吞吐 +50%。
- 移动端很少用列式，但大型日志分析可考虑 Parquet。

> ▶▶ **回扣贯穿案例**：Day 5 日志体积用 protobuf 替代 JSON，每条 -50%——直接让磁盘空间和 IO 时间同步缩减。

### 5.5 IO 兜底四招

当"少/批/异/缩"都做了还是出问题时的兜底：

**兜底一：mmap + 内核托管刷盘**

```cpp
char* addr = mmap(nullptr, len, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
memcpy(addr, data, len);
// 关键节点（如交易完成）显式 msync
msync(addr, len, MS_SYNC);
```

**适用**：日志、KV、高频小写。

**兜底二：WriteBuffer + 周期刷盘**

- 内存里累积写请求；
- 周期（1s/10s）或阈值（1000 条）触发批刷；
- 崩溃丢最近一轮，可接受。

**兜底三：双 Buffer 轮转**

- Buffer A 接收写入；
- Buffer B 后台刷盘；
- 轮转，永不卡写方。

**兜底四：Fallback 到内存**

- IO 失败/慢 → 优雅降级到内存模式；
- 下次启动时重试落盘；
- 适用于"可丢但不能卡"的场景。

### 5.7 数据库深度治理

**7.1 启用 WAL 模式**

```sql

PRAGMA synchronous=NORMAL;  -- 配合 WAL 用 NORMAL 而非 FULL
```

**收益**：读写并发；写吞吐 +400%（§5.0 实验四）。
**边界**：WAL 文件需定期 checkpoint（`PRAGMA wal_checkpoint(TRUNCATE)`）；隔离级别变 SNAPSHOT。

**7.2 索引优化三原则**

```sql
-- ✅ 仅为高频查询字段加索引
CREATE INDEX idx_user_email ON users(email);

-- ❌ 不要给低基数字段加索引（如 gender 仅 M/F）

-- ✅ 复合索引按"高频先后"排列
CREATE INDEX idx_log_time_level ON logs(create_time, level);
```

**索引三反模式**：
- **过度索引**：每字段一个索引，写入慢 3-5×；
- **低基数索引**：性别/状态字段加索引，无加速反而占空间；
- **复合索引顺序错**：高基数字段应放前面。

**用 EXPLAIN QUERY PLAN 验证**：

```kotlin
db.rawQuery("EXPLAIN QUERY PLAN SELECT * FROM users WHERE email=?", arrayOf(email))
    .use { cursor ->
        // 看是否命中索引：SEARCH TABLE users USING INDEX idx_user_email
    }
```

**7.3 定期维护**

```kotlin

db.execSQL("PRAGMA wal_checkpoint(TRUNCATE)")

// 每月或必要时：清理空闲页
db.execSQL("VACUUM")
```

### 5.8 KV 深度治理

**8.1 MMKV 为什么快**（深度剖析）

```
   SharedPreferences:
      JSON/XML 全量序列化 → write + apply
          ↓
      QueuedWork 队列
          ↓
      生命周期切换时同步等
   
   MMKV:
      Protobuf 增量追加 → mmap 内存
          ↓
      内核 writeback 自动刷
          ↓
      零生命周期依赖
```

**MMKV 的三大优化点**：

1. **mmap 代替 syscall**：写入直接 memcpy 到映射内存，μs 级；
2. **Protobuf 代替 XML**：序列化成本降 90%；
3. **增量追加代替全量重写**：改一个 key 不用重写整个文件。

**8.2 MMKV 使用注意**

```kotlin

// ✅ 多进程

// ✅ 加密

// ⚠️ 边界：mmap 数据可能丢（崩溃时最近未 msync 的 30s 内数据）
// 金融场景手动 msync 兜底：
mmkv.sync()
```

## 06.IO 原理深潜

> 本章是面向资深工程师的"**知其所以然**"——理解了原理，才能应对任何陌生 IO 问题。

### 6.1 Page Cache 机制

Page Cache 是内核的"**写入缓冲层**"——所有普通 write() 都先落到这里，再异步刷到介质：

```
   应用 write(buf, len)
          ↓
   VFS → ext4/F2FS
          ↓
   拷贝到 Page Cache（内核内存，4KB 对齐页）
          ↓                    ↓
   用户态返回（μs 级）     内核 writeback 线程异步刷
                              ↓
                         Block IO 调度器
                              ↓
                         NAND Flash
```

**关键认知**：
- **读也经过 Page Cache**：第二次读相同文件秒出（缓存命中）；
- **"热"文件常驻 Cache**：高频访问的小文件（配置/索引）几乎不碰介质；
- **Cache 大小动态**：内存紧张时内核回收（LRU）；OOM 时首当其冲。

**工程启示**：
- 测试写性能必须 drop_caches，否则测的是"写到内存"；
- 启动期 IO 可预热（pre-read）让关键文件进 cache；
- 低内存设备 Page Cache 小，IO 实际开销比理论值高。

### 6.2 Writeback 内核线程

**Writeback = 内核把 Page Cache 的脏页刷到介质**：

```
   Page Cache
      │
      │ dirty_background_ratio（10%）  → 后台线程缓慢刷
      │ dirty_ratio（20%）             → 应用 write 开始阻塞
      │ dirty_expire_centisecs（30s）  → 老化脏页强制刷
      ↓
   Block Layer
```

**三条触发规则**：

1. **后台线程周期触发**：每 5s 扫一次，刷"过期"脏页；
2. **阈值触发**：脏页占内存 20% 时，应用 write 被阻塞（反压）；
3. **显式触发**：应用调 fsync/sync 时主动刷。

**工程坑**：
- 日志狂写 → 快速堆满 20% 脏页 → 应用莫名卡顿（writeback 反压）；
- 低端机内存小 → 20% 阈值更小 → 更容易触发反压；
- 后台应用写 IO 时触发 writeback → 抢占前台 IO 带宽。

### 6.3 ext4 vs F2FS vs APFS

**Android 设备文件系统演进**：

| FS | 典型设备 | 适合场景 | 性能特征 |
|---|---|---|---|
| ext4 | Android 4-9 老设备 | 通用 | 顺序写快，随机 OK |
| F2FS | Android 10+ 新设备 | Flash 优化 | 随机写 +30%，寿命 +50% |
| APFS | iOS 10.3+ | 写时复制 | 快照快，大文件写慢 |
| exFAT/FAT32 | SD 卡 | 跨平台 | 小文件慢，大文件 OK |

**F2FS 的 Flash 友好设计**：
- Log-Structured（日志结构）：所有写都追加，不原地改；
- Section/Zone 对齐：减少 Flash GC；
- NAT（Node Address Table）：加速元数据查询。

**APFS 的写时复制**：
- 修改文件时拷贝新块，不覆盖原块；
- 优点：快照/克隆 O(1)；
- 缺点：小文件频繁改 → 空间放大。

### 6.4 SQLite WAL 原理

**传统 DELETE 模式的问题**：

```
   BEGIN;
   UPDATE t SET x=1 WHERE id=1;
   ↓
   旧值写到 rollback journal（fsync 1）
   ↓
   新值写到主库文件（fsync 2）
   COMMIT;
   ↓
   删除 journal（fsync 3）
   
   = 每事务 3 次 fsync
```

**WAL 模式的优化**：

```
   BEGIN;
   UPDATE t SET x=1 WHERE id=1;
   ↓
   新值追加到 WAL 文件（fsync 1，顺序写极快）
   COMMIT;
   
   读请求：先读 WAL，没找到再读主库（读不阻塞写）
   
   定期 checkpoint：把 WAL 内容合并到主库
```

**WAL 收益**：
- 写只需 1 次 fsync（而非 3 次）；
- 读写并发（读不加锁，写追加）；
- 顺序写比随机写快（Flash 特性）。

**WAL 代价**：
- WAL 文件膨胀：需定期 checkpoint；
- 读隔离级别从 SERIALIZABLE 降到 SNAPSHOT；
- 极端场景（文件系统损坏）恢复稍复杂。

### 6.5 B-tree 索引结构

**SQLite 索引走 B+Tree**：

```
          [50]            ← 根节点
        /      \
     [20]      [80]        ← 中间节点
    /   \     /   \
   [10][30][60][90]       ← 叶子节点，含数据指针
```

**查询复杂度**：
- 无索引：O(N) 全表扫；
- B-tree 索引：O(log N) 树查找；
- 1 亿行查询：无索引 1 亿次比较 vs 索引 27 次比较。

**索引写入代价**：
- 每次 INSERT/UPDATE：
  - 主数据写入 1 次；
  - 每个索引更新 1 次（B-tree 可能分裂/合并）；
- 3 个索引 = 4 次写入 + B-tree 平衡成本。

**结论**：**索引是"读 vs 写"的典型零和博弈**——加 1 个索引，查询 100× 快，但写入慢 50%。

### 6.6 mmap 全栈

**mmap 把文件映射到进程虚拟地址空间**：

```
   应用 mmap(fd, size)
          ↓
   内核分配 VMA（Virtual Memory Area）
          ↓
   应用 memcpy(addr, data, len)
          ↓
   触发 Page Fault
          ↓
   内核把文件对应页加载到物理内存，建立 PTE 映射
          ↓
   返回用户态
          ↓
   后续访问：直接读/写内存地址（无 syscall）
          ↓
   内核 writeback 自动刷脏页到文件
```

**mmap 四大性能特点**：

1. **零 syscall**：读写就是 memcpy，无用户态/内核态切换；
2. **零拷贝**：数据只在 Page Cache 中一份，不复制到用户 buffer；
3. **按需加载**：Page Fault 懒加载，大文件不占全部内存；
4. **异步刷盘**：writeback 内核托管，不阻塞应用。

**mmap 的陷阱**：

- **崩溃丢数据**：未 msync 的脏页，进程 kill 时丢；
- **大文件地址空间**：32-bit 设备地址空间 4GB，大 mmap 可能失败；
- **信号安全问题**：Page Fault 时信号处理复杂；
- **文件扩展需 ftruncate**：mmap 不能自动扩展文件。

### 6.7 Direct IO vs Buffered IO

**两种 IO 模式对比**：

| 模式 | 路径 | 带宽 | 延迟 | 适用场景 |
|---|---|---|---|---|
| **Buffered IO**（默认） | 应用 → page cache → 介质 | 低（受 cache 限制） | 低（命中快） | 常规应用 |
| **Direct IO**（O_DIRECT） | 应用 → 介质（绕 cache） | 高（直通） | 高（无缓存） | 数据库、大文件备份 |

**Direct IO 要求**：
- Buffer 必须按介质块大小对齐（通常 512B）；
- 大小必须是块大小的倍数；
- 用户管理缓存。

**工程选择**：
- 移动端 99% 用 Buffered IO；
- 大数据顺序读写（视频文件处理）考虑 Direct IO；
- SQLite 默认 Buffered，可配置为 Direct。

### 6.8 Flash 磨损均衡

**NAND Flash 的物理限制**：
- 每个 cell 只能擦写有限次（MLC 3000-10000，TLC 500-3000，QLC < 1000）；
- 必须"**磨损均衡**"（Wear Leveling）：让所有 cell 均匀磨损，否则热点 cell 先坏。

**磨损均衡的开销**：
- 内部数据搬迁（garbage collection）；
- 搬迁时应用 IO 可能变慢（GC 抢带宽）；
- 低端机 Flash 控制器弱，GC 影响更大。

**工程启示**：
- **写放大**：应用写 1KB 可能实际写 100KB（因为块对齐 + GC）；
- **寿命**：高频写的应用（日志）加速 Flash 老化；
- **低端机末期**：GC 频繁 + cell 老化 → IO 延迟指数增加（50-200ms）。

### 6.9 TRIM 与垃圾回收

**TRIM 命令**：OS 告诉 Flash "这些块不用了，可以回收"：

```
   应用删文件 → VFS 标记为空闲 → OS 发 TRIM 命令 → Flash 控制器后台 GC
```

**没有 TRIM 的后果**：
- Flash 不知道哪些块空闲，必须保守对待；
- 写新数据时现场擦写（慢）；
- Android 4.3+ / iOS 全系默认支持 TRIM。

**应用层无需关心 TRIM，但要知道**：
- 存储空间满 90% 以上时 IO 性能骤降（GC 没空间腾挪）；
- 定期清理无用缓存文件，让 TRIM 有机会工作。

### 6.10 journaling 文件系统日志

**ext4/F2FS 都是 journaling FS**：所有元数据变更先写 journal，再更新实际元数据——保证断电一致性。

**三种 journaling 模式**：

| 模式 | 日志内容 | 性能 | 安全 |
|---|---|---|---|
| **writeback** | 仅元数据 | 快 | 低（数据可能乱序） |
| **ordered**（默认） | 元数据 + 数据顺序 | 中 | 中（元数据后数据） |
| **journal** | 元数据 + 数据 | 慢 | 高（全日志） |

**工程启示**：
- 普通应用用默认 ordered 即可；
- 数据库自己有 WAL，不需要 FS 层的 journal data；
- 可通过 mount 选项调整，但移动端无 root 权限。

## 07.面试高频追问

### Q1 apply 为什么还会阻塞

**问**：SharedPreferences.apply() 不是异步的吗？为什么会阻塞主线程？

**答**：apply() 的"异步"只保证**调用方立即返回**，但 AOSP 源码 `QueuedWork.waitToFinish()` 会在生命周期关键点（Activity.onPause/Service.onStart/BroadcastReceiver.onReceive 等）**同步等待所有未落盘的 apply 完成**。日志狂写导致队列堆积 → 用户按 Home 瞬间 onStop → 一次性阻塞 80-200ms（低端机），触发 ANR。**治法**：MMKV 替代 SP（走 mmap + 内核托管，无 QueuedWork 等待）。

### Q2 为什么 CPU 低也会卡

**问**：Perfetto 看 CPU 20%，为什么用户还是卡？

**答**：IO 阻塞时线程在**D 状态（Uninterruptible Sleep）**，不消耗 CPU 时间但完全阻塞不能被抢占。CPU profiler 看不见。**定位**：看 `/proc/[pid]/stat` 的 `delayacct_blkio_ticks`、或 Perfetto `sched_switch` 事件中线程停留在 D 状态的时长。CPU 低 + 卡 ≈ **大概率 IO bound**。

### Q3 加索引为什么反而慢

**问**：SQLite 加了几个索引，为什么写入反而慢 3-5 倍？

**答**：**索引是"读 vs 写"的零和博弈**。每次 INSERT/UPDATE：主数据写 1 次，每个索引更新 1 次（B-tree 可能分裂/合并）。3 个索引 = 4 次写 + 平衡成本。**治法**：只给**高频查询 + 高基数**字段加索引；复合索引按"高基数先"排列；用 EXPLAIN QUERY PLAN 验证是否命中。

### Q4 MMKV 一定比 SP 快吗

**问**：MMKV 真的全场景都比 SharedPreferences 快？

**答**：**高频小写场景快 100×**（§5.0 实验五），但**低频大 value 场景优势缩小到 2-3×**。另外 MMKV 的缺点：
- 崩溃可能丢最近 30s 数据（无 fsync 兜底）；
- 跨进程需显式开 MULTI_PROCESS_MODE，开销增加；
- 多端数据同步需额外设计。
**结论**：99% 场景用 MMKV，金融场景手动 `mmkv.sync()` 兜底。

### Q5 mmap 数据会丢吗

**问**：mmap 写数据后进程崩溃，数据丢吗？

**答**：**可能丢**——mmap 写的是 Page Cache，内核异步刷盘（30s 内）。进程崩溃不丢（内核仍会刷），但**断电会丢**。要确保落盘：显式 `msync(addr, len, MS_SYNC)`。**选型原则**：
- 日志/缓存：mmap 够用；
- 支付/订单：mmap + 关键节点 msync；
- 极端可靠：直接 write + fsync。

### Q6 SSD 随机写真的不慢吗

**问**：都说 SSD 随机 IO 不比顺序 IO 慢，是真的吗？

**答**：**部分真**。SSD 没有 HDD 的寻道开销，随机读几乎等同顺序读。但**随机写有写放大**：

```
   逻辑写 1KB
      ↓
   物理写 4KB（块对齐）+ WAL 8KB + 索引 4KB
      = 16KB（16× 放大）
```

加上 Flash 的 **GC 开销**，低端机末期 SSD 随机写延迟可达 50-200ms。所以：**SSD 随机写 ≠ 零成本**，仍要批量 + 顺序优先。

### Q7 WAL 什么时候不能用

**问**：WAL 性能这么好，什么场景不能用？

**答**：
- **严格 SERIALIZABLE 隔离**：WAL 把隔离级别降到 SNAPSHOT——金融转账等场景不能用；
- **只读居多**：WAL 的 checkpoint 开销反而拖慢；
- **跨网络文件系统**：WAL 要求 shared memory，NFS 不支持；
- **单次写极大（> 100MB）**：WAL 文件膨胀严重，不如直接写。
**90% 的 Android App 场景都应启用 WAL**（§5.0 实验四）。

### Q8 异步 IO 一定更好吗

**问**：所有 IO 都放到异步线程不就完事了？

**答**：**不完全对**。异步 IO 的坑：
- **主线程等结果**：异步变同步，白搭；
- **线程池耗尽**：IO 密集场景线程池满，新任务排队；
- **顺序依赖**：读 A 再写 B，异步化反而更慢（线程切换）；
- **可观测性下降**：异步调用栈难追踪；
- **耗电**：异步线程唤醒 CPU，功耗增加。
**正解**：异步 + 批量 + 缓冲三件套，而不是"傻异步"。

### Q9 Room 会救主线程吗

**问**：用了 Room 是不是就不用担心主线程 IO？

**答**：**部分救**。Room 默认在主线程 throw：

```kotlin
@Dao
interface UserDao {
    @Query("SELECT * FROM users")
    fun getAll(): List<User>  // 主线程调用 → IllegalStateException
}
```

但 **Room 不管底层的 SQLite 实现细节**——事务未开 WAL、索引设计差、查询慢，Room 一样慢。**Room 救的是"位置"，不救"效率"**。

### Q10 小文件为什么慢 27 倍

**问**：1 万个 10KB 文件比 1 个 100MB 文件慢 27 倍，差距为什么这么大？

**答**：每个文件都要走：
- **inode 查找**（目录遍历，B-tree 查找）；
- **元数据更新**（atime/mtime，fsync 落盘）；
- **数据块分配**（block allocator 竞争）；
- **可能的锁竞争**（inode lock、directory lock）；
- **fsync 开销**：每个文件 close 时内核可能同步元数据。

1 万次这些开销累积 = 27× 的差距（§5.0 实验三）。**治法**：聚合存储（SQLite/LevelDB）。

### Q11 journal\_mode 该怎么选

**问**：SQLite 有 DELETE/TRUNCATE/PERSIST/WAL 几种 journal_mode，怎么选？

**答**：

| 模式 | 性能 | 兼容 | 场景 |
|---|---|---|---|
| DELETE（默认） | 慢 | 最佳 | 兼容性要求 |
| TRUNCATE | 中 | 好 | ext4 优化 |
| PERSIST | 中 | 好 | journal 固定大小 |
| **WAL** | 快 3-7× | Android 2.3+ | **90% 场景推荐** |
| MEMORY | 极快 | 不可靠 | 测试/临时表 |
| OFF | 极快 | 极不可靠 | 不要用 |

**现代 Android App 用 WAL + synchronous=NORMAL** 几乎是无脑最优解。

### Q12 为什么批量不包事务等于没批量

**问**：我把 10000 条 INSERT 用循环连续写，是不是就是"批量"了？

**答**：**不是**——每条 INSERT **默认自动 commit**（Autocommit），仍然是 10000 次 fsync。贯穿案例第 4 周翻车就是这个坑：

```kotlin
// ❌ 以为批量，实际 10000 次 fsync
items.forEach { db.execSQL("INSERT...", it) }
// 性能仅提升 15%

// ✅ 真正批量（1 次 fsync）
db.beginTransaction()
try {
    items.forEach { db.execSQL("INSERT...", it) }
    db.setTransactionSuccessful()
} finally {
    db.endTransaction()
}
// 性能提升 70×
```

**"批量" = 一次事务里多次操作**，而不是"连续多次调用"。

### Q13 低端机 IO 为什么比高端机慢 10 倍

**问**：同一份代码，为什么低端机 IO 比高端机慢得多？

**答**：三重放大：
- **介质差距**：UFS 3.1（旗舰）vs eMMC 5.1（低端），顺序写 10× 差距；
- **Flash GC 开销**：低端 Flash 控制器弱，GC 时 IO 延迟增 300-1000%；
- **Page Cache 小**：低端机内存小，Cache 回收频繁，命中率低；
- **CPU 弱**：fsync 时 CPU 也要配合（元数据计算），CPU 慢 → fsync 慢。
**治理启示**：**性能优化本质是给低端机让出预算**——旗舰机用户感知不到优化，但低端机用户从"卡死"到"流畅"，这就是 GMV 的来源。

## 08.模拟面试模板

### 8.1 IO 优化理解

**问**：谈谈你对 IO 性能优化的整体理解？

**答**：

> IO 优化的本质是**穿透 API 看物理介质**——90% 的 IO 问题根因不在"用什么 API"，而在"**如何使用 API**"。我的理解框架是"**三公式四字诀**"：
>
> **三公式**：
> - `T_io = N × T_fsync + ...`（fsync 是杀手项，1-200ms）；
> - `write ≠ 落盘`（三级落盘语义：write/fflush/fsync）；
> - 介质差距 7 个数量级（内存 100ns → eMMC 末期 200ms）。
>
> **四字诀**（治理顺序）：
> - **少**：缓存命中、启动延迟、小文件聚合；
> - **批**：事务合并、异步缓冲、文件缓冲；
> - **异**：主线程零 IO、SP 换 MMKV、SQLite 走子线程；
> - **缩**：压缩、PB 替代 JSON、列式存储。
>
> **治理顺序**是关键：先治主线程（§5.3 异之路），再治量级（§5.1 少之路），再治高频（§5.2 批之路），最后治体积（§5.4 缩之路）。顺序倒过来就是贯穿案例"4 周翻车"的典型。

### 8.2 线上 IO 监控方案

**问**：线上 IO 怎么监控？

**答**：

> 分**三层采集 + 三阈值过滤**：
>
> **三层采集**：
> - 系统级：iostat 跑 CI 基准（设备视图）；
> - 进程级：/proc/[pid]/io 1% 用户抽样（进程视图，零开销）；
> - 应用层：AOP hook FileIO/SQLiteDatabase/MMKV，1% 采样 + 栈（业务视图）。
>
> **三阈值过滤**（控数据量）：
> - 时长阈值：单次 > 16ms 才上报；
> - 位置阈值：仅主线程调用上报；
> - 频次阈值：同一调用栈 10 分钟内只报 1 次。
>
> **线上降级**（可动态调）：常态 1% / 异常 10% / 熔断关闭。
>
> **SLO 告警**：主线程 IO P95 > 50ms 持续 5 分钟触发 P1；ANR 中 IO 类占比 > 30% 触发 P0。
>
> **远程诊断兜底**：拿不到设备就引导用户抓 Perfetto trace，看 `sched_switch` 事件中线程停留 D 状态的时长。

### 8.3 ANR 和 IO 的关系

**问**：ANR 为什么大多数都和 IO 相关？

**答**：

> **ANR 的本质 = 主线程 5s 内未响应**。主线程卡 5s 的原因：
> - **CPU 爆满**：罕见，只有死循环或密集计算；
> - **锁等待**：中等概率，常见于 synchronized 竞争；
> - **IO 阻塞**：**最高概率**，占 ANR 的 60-70%。
>
> **IO 导致 ANR 的四种路径**：
> - **fsync 累积**：日志狂写，每次 fsync 50-200ms，累积超 5s；
> - **apply 生命周期触发**：QueuedWork.waitToFinish 在 onPause 同步等；
> - **SQLite 慢查询**：主线程查询遇到大表无索引，单次 > 5s；
> - **启动期大文件读**：Core Data/缓存反序列化。
>
> **治理**：StrictMode 开发期拦截 + MMKV 替代 SP + 事务批量 + 全部走子线程——四招下来 ANR 中 IO 类占比可从 60% 降到 10% 以下。

### 8.4 MMKV 为什么快

**问**：MMKV 为什么比 SharedPreferences 快 100 倍？

**答**：

> **三重优化**：
>
> **① 用 mmap 代替 syscall**：SP 用普通文件 write + apply，每次写入要陷入内核、拷贝到 page cache；MMKV 把文件映射到进程地址空间，写入就是 memcpy，μs 级，无 syscall。
>
> **② 用 Protobuf 代替 XML**：SP 每次改一个 key 要全量序列化整个 XML 文件；MMKV 用 PB 二进制 + 增量追加，改一个 key 只追加几十字节。
>
> **③ 无 QueuedWork 等待**：SP 的 apply 看似异步，但 onPause 会同步等 QueuedWork 完成；MMKV 走内核 writeback，零生命周期依赖。
>
> **性能对比**（§5.0 实验五）：高频 100×100B/s 场景 100×（12500ms → 125ms）；大数据场景优势缩小到 2-5×。
>
> **代价**：崩溃可能丢最近 30s 未 msync 数据——金融场景需手动 `mmkv.sync()` 兜底。

### 8.5 优化故事线

**问**：讲一个你亲手做过的完整 IO 优化案例？

**答**：

> **背景**：某阅读 App V7.3 上线"全量日志埋点"，ANR 率从 0.04% 飙到 0.61%，冷启动 P95 从 1.4s 升到 4.1s，低端机日志狂写导致主线程 fsync P99 820ms，阅读时长 -8%。4 周经验派优化（apply 替换、加索引、try-catch）全无效甚至反向（第 1 周 ANR 升到 0.78%）。
>
> **归因**（1 天）：
> - CPU 占用 8-15%（低！）→ IO bound；
> - StrictMode 扫到日志库大量 apply/commit 在主线程；
> - `/proc/[pid]/io` 显示写字节 47MB/分钟；
> - iostat 显示写 IOPS 1200+，远超低端机能力。
>
> **方案**（5 天）：按"**少批异缩**"四字诀：
> - **异**：日志入队 → 子线程批刷；SP 全面迁移 MMKV；SQLite 全走子线程；
> - **批**：SQLite 加 `BEGIN TRANSACTION … COMMIT`，1000 条/批 + WAL；
> - **缩**：日志体积 protobuf 替代 JSON，-50%；
> - **少**：启动期日志延迟到首屏后 warm up。
>
> **防劣化**：加 Lint 规则（禁用 SP 直接调用）+ CI 卡口（主线程 IO P99 > 50ms 阻断 PR）+ 线上 SLO（ANR IO 占比 > 30% 告警）。
>
> **结果**：ANR 0.78% → **0.05%**（-93%），冷启动 4.6s → **1.3s**（-72%），日志吞吐 80 → **3500 条/s（43×）**，阅读时长 -8% → **+2%**。灰度 14 天无新异常全量上线。
>
> **复盘**：**经验派不是不努力，是归因错方向**——4 周全花在"API 名字"上（apply/索引/try-catch），根本没看到物理层的 fsync 累积。方法派按决策树归因 + 五大实验回推，第一刀就砍对位置。
