# App 冷启动优化

> **本文核心命题**：启动是**关键路径上的最优化问题**——从用户点击图标到"可交互"，所有环节串成一条关键路径，任何一段超标都直接累加到总时长。**启动优化的本质不是"把事情做快"，而是"决定哪些事情不做、晚做、别做在主线程上"**。

## 02.贯穿案例

> 本案例贯穿全文：§03 用它定义冷启动阶段、§04 用它画关键路径、§05/§06 用它演示度量与归因、§07-§11 对应每一段全链路、§13-§16 给出分层策略闭环、§17 用实验复盘。

### 2.1 案例背景

某电商 App 在大促版本（V7.8）上线后，冷启动指标恶化：

- **冷启动 P95 从 2.1s 恶化到 4.2s**（线上埋点：进程创建 → 首页可交互）。
- 应用商店"启动慢"差评环比 +230%；新用户次日留存 -1.8pp。
- 大促前两周紧急插入 60+ 个业务需求，其中 **23 个 SDK / 组件带初始化代码**，全部塞进了 `Application.onCreate()`。
- 初步排查（经验派）："手机太卡了""用户网络差"——3 周无进展。

### 2.2 方法派的 10 天闭环

| 天 | 动作 | 工具 | 发现 |
|---|---|---|---|
| D1 | 分阶段打点：进程创建 → Application.attach → onCreate 结束 → 首帧 → 可交互 | 自研埋点 + `am start -W` | Application.onCreate 占 1.9s（其中主线程 1.6s） |
| D2 | Perfetto 抓启动 trace，按线程泳道分析 | Perfetto | 主线程 41% 时间在等锁（等子线程初始化返回） |
| D3 | 锁等待归因 | Trace + 锁日志 | 17 个 SDK 初始化互相依赖，形成"伪异步"串行链 |
| D4-D5 | 任务分级重构：DAG 启动器，非关键任务全部延迟 | 自研启动器 | 主线程 SDK 工作从 1.6s 压到 0.5s |
| D6 | 首帧优化：首页骨架屏 + 非首屏模块延迟 inflate | Trace | 首帧提前 0.4s |
| D7 | 数据预取：点击图标即发首页接口（无网时缓存兜底） | 接口聚合 | 可交互再提前 0.5s |
| D8 | Baseline Profile 接入 | jetpack ProfileInstaller | 类加载与 JIT 开销 -35% |
| D9-D10 | A/B 对照 + 灰度放量 + 启动预算卡口 | CI | P95 = **1.9s**，达标上线 |

### 2.3 上线效果

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 冷启动 P95（中端机） | 4.2s | 1.9s | **-55%** |
| Application 主线程耗时 | 1.6s | 0.5s | -69% |
| 首帧时间 P95 | 2.6s | 1.2s | -54% |
| 商店"启动慢"差评 | 基线 | -81% | — |

- **[§03 启动本质](#03启动本质定义)**：先定义"冷启动到底从哪一刻开始、到哪一刻结束"。
- **[§04 关键路径](#04关键路径原理)**：为什么"23 个 SDK 异步初始化"反而变慢——伪异步串行链。
- **[§05-§06 度量归因](#05度量与采集)**：分阶段打点是定位的先决条件。

## 03.启动本质定义

### 3.1 冷 / 温 / 热启动物理定义

| 类型 | 进程 | Application | Activity | 用户感知 |
|---|---|---|---|---|
| **冷启动** | 不存在 | 完整走 | 完整走 | 白屏 / 品牌页 → 首页 |
| **温启动** | 存在（后台） | 不重走 | 重建或新开 | 短暂等待 |
| **热启动** | 存在且前台 | 不走 | 不走 | 切换动画 |

> **工程含义**：三个类型优化的对象完全不同——冷启动优化进程+Application+首帧全链路；温启动主要是 Activity 重建与状态恢复；热启动基本无可优化空间。**本文聚焦冷启动**（代价最大、劣化最隐蔽）。

### 3.2 冷启动五阶段模型

```text
T0 点击图标
 ├─ ① 进程创建：Launcher → AMS → Zygote fork → 新进程 attach
 ├─ ② Application：attachBaseContext → ContentProvider.onCreate → onCreate
 ├─ ③ Activity 创建：ActivityThread → onCreate → onStart → onResume
 ├─ ④ 首帧渲染：measure → layout → draw → GPU 合成 → 上屏（TTID）
 └─ ⑤ 可交互：首页核心数据到位、核心交互可响应（TTFD）
T5 可交互
```

**度量准则**：

| 指标 | 口径 | 行业基准（Android 中端机，P95） | 来源 |
|---|---|---|---|
| TTID（首帧） | 进程创建 → 首帧上屏 | ≤ 1.5s | Google Vital 建议冷启动 ≤ 5s 为底线，优秀应用 ≤ 2s |
| TTFD（完全展示） | 进程创建 → 全部数据到位 | ≤ 3s | Google 建议用 `reportFullyDrawn()` 上报 |
| 可交互 | 进程创建 → 首页核心点击可响应 | ≤ 2.5s | 业务自定 |

> **反直觉问题清单**：
> ① "启动时间从点击图标算起"——错，**用户感知从点击前 100ms 的心理预期就开始**，但工程口径必须统一从进程 fork（或 `am start` 时间戳）算起。
> ② "Application.onCreate 是启动大头"——不一定，**进程创建 + 类加载可能占 30%+**（低端机更甚）。
> ③ "异步化就能解决启动慢"——错，**伪异步（异步任务被主线程锁串行化）是启动慢的头号隐形原因**（本篇贯穿案例即如此）。
> ④ "首帧越早越好"——对，但**只提前首帧而数据晚到，用户感知是"白屏变骨架屏"**，TTID 好看、TTFD 没变。

## 04.关键路径原理

### 4.1 关键路径模型（Critical Path）

```text
串行链：  A(300ms) → B(500ms) → C(200ms)          总计 1000ms
并行化：  A(300ms) ┐
          B(500ms) ├→ C(200ms)                     总计 700ms（取决于最长支路）
          D(100ms) ┘
```

**三条推论**：

1. **非关键路径耗时对总时长无贡献**——把非关键任务优化到极致是零收益；找到关键路径才有靶子。
2. **并行化的上限 = 最长支路**——支路内有锁、有主线程回调、有同一线程池排队，"并行"就退化为串行（**伪异步**）。
3. **关键路径会漂移**——删掉当前关键段后，次关键段成为新的关键段；优化必须**每轮重新度量**，而不是一次规划到底。

### 4.2 启动的资源×流水线视角

| 资源 | 启动期特征 | 典型病灶 |
|---|---|---|
| CPU | 冷启动期 IO 密集 + JIT 解释执行，CPU 频率爬升慢 | 类加载、JSON 解析占满单核 |
| IO | 首次读写 SP / 数据库 / SO 解压 | 主线程 SharedPreferences 首次加载全量文件 |
| 内存 | 进程刚创建，页错误（缺页）密集 | APK 未对齐 / 未用 Baseline Profile，大量 cold page fault |
| IPC | AMS / PMS / WMS 往返 | `getInstalledPackages` 等重 IPC 在启动路径上 |

### 4.3 平台差异点矩阵

| 环节 | Android | iOS | Web |
|---|---|---|---|
| 进程创建 | Zygote fork（共享 COW 页） | posix_spawn + dyld | 无进程概念（Tab 冷启动 ≈ 渲染进程创建） |
| 类/符号加载 | ART 类加载 + JIT/AOT | dyld 动态库绑定（Order Files / Prewarming） | JS 解析 + 字节码缓存 |
| 首帧 | Vsync 流水线首帧 | CATransaction 提交 | FCP / LCP |
| 官方工具 | `am start -W` / Perfetto | XCTest Metrics / MetricKit | Lighthouse / web-vitals |

## 05.度量与采集

### 5.1 三类采集方案

**方案①：实验室 adb（开发期）**

```bash
# 输出 ThisTime / TotalTime / WaitTime（TotalTime 为准）
adb shell am start -W -n com.demo.app/.MainActivity
# 简单的完整展示回调（Android 4.4+，logcat 关键字）
adb logcat -s ActivityTaskManager:I | grep Displayed
```

- 优点：零成本、可重复。缺点：不含"可交互"，无法定位段内耗时。

**方案②：Perfetto / Systrace（定位期）**

```bash
adb shell perfetto -o /data/misc/perfetto-traces/launch.pftrace -t 10s \
  sched freq idle am wm view input binder driver
```

- 用 `Trace.beginSection` / `android.os.Trace` 打标业务段；看主线程泳道 + binder 泳道 + 锁等待（`futex`）。

**方案③：线上埋点（监控期）**

| 埋点 | 打点位置 | 说明 |
|---|---|---|
| 进程创建 | `Application.attachBaseContext` 首行 | 与 `am start` 时间戳求差可得 fork 前排队时长 |
| CP 阶段 | 首个 `ContentProvider.onCreate` 前后 | 暴露"SDK 偷启动" |
| Application 阶段 | `onCreate` 首尾 | 拆 SDK 粒度 |
| 首帧 | 首个 `View.onDraw` / `reportFullyDrawn()` | TTID |
| 可交互 | 首页核心接口渲染完成 | TTFD |

> **坑位提醒**：进程冷启动时间戳要**持久化到磁盘再在下次启动读取**（进程内静态变量在进程被杀重启时丢失"上一次启动"信息）。

### 5.2 数据可信度

- 分位数看 **P90 / P95 / P99**，均值会被启动快的设备拉低。
- 分机型分层：旗舰 / 中端 / 低端分别出数（低端机问题占启动差评的 60%+）。
- 剔除异常：进程因崩溃重启的启动（崩溃启动不是体验问题而是稳定性问题，归篇11）。

## 06.归因决策树

```text
启动慢（TTID 或 TTFD 超标）
├─ ① fork 排队久（点击→attachBaseContext 间隔大）
│    └─ 系统负载 / 内存压力（LMK 前兆）→ 看篇02/03；应用侧可预热（见 §15）
├─ ② Application 阶段长
│    ├─ 主线程 SDK 初始化多 → §13 分级调度
│    ├─ 伪异步（异步任务等主线程锁/结果）→ Perfetto 看锁泳道 → §13 解依赖
│    ├─ ContentProvider 偷启动 → §14 延迟 / App Startup 迁移
│    └─ 主线程 IO（SP 首次加载 / DB 建表）→ §13 异步化
├─ ③ Activity / 首帧阶段长
│    ├─ 布局层级深 / 首页一次 inflate 全部 → §15
│    ├─ 主题 windowBackground 缺失（白屏感知）→ §15 骨架屏
│    └─ 类加载密集（冷 JIT）→ §14 Baseline Profile
├─ ④ 数据阶段长（TTFD 与 TTID 差距大）
│    ├─ 接口串行请求 → §14 预取 + 聚合
│    └─ 首屏图片解码阻塞 → 篇09 图片篇
└─ ⑤ 跨端容器初始化（Flutter/RN/WebView 引擎）→ §11 / §14 预创建
```

## 07.进程创建全链路 ⭐

### 7.1 链路拆解

```text
点击图标 → Launcher startactivity → Binder → AMS（校验/栈管理）
  → Zygote fork（写时复制 COW，继承已初始化的 ART 与系统库）
  → 新进程 Runtime init → ActivityThread.main → attachApplication → AMS
  → 应用进程首次执行业务代码（attachBaseContext）
```

| 段 | 典型耗时（中端机） | 应用可控性 |
|---|---|---|
| AMS 调度 + fork | 100-300ms | 低（系统侧） |
| Runtime init + attach | 100-200ms | 低 |
| attachBaseContext → CP 之前 | 50-150ms | **高**（最早执行的业务代码） |

### 7.2 工程要点

- **fork 的 COW 红利**：Zygote 已预加载的类与资源共享物理页——**避免在 attachBaseContext 之前触碰大量未预加载的类**（否则触发缺页 + 校验）。
- **多进程代价**：每个额外进程都要完整走一遍 Runtime init（篇03 §28）。启动期避免"顺手"拉起非必要进程。
- **Provider 偷启动**：manifest 中所有 `ContentProvider` 在 Application 之前自动初始化——第三方 SDK 常埋此钩子，用工具（如 `App Startup` 的 Profiler 输出或启动埋点）盘点。

## 08.Application 全链路 ⭐

### 8.1 链路拆解与病灶

```text
attachBaseContext（无网络/无UI能力，最早）
  → ContentProvider.onCreate × N（SDK 偷启动高发区）
  → Application.onCreate（SDK 初始化主战场）
```

| 病灶 | 典型特征 | 物理原因 |
|---|---|---|
| SDK 串行初始化 | `sdkA.init(sdkB.getResult())` | 依赖链把并行变串行 |
| 伪异步 | `new Thread(){ sdkC.init() }` 但主线程随后 `sdkC.await()` | 锁把异步变回串行 + 额外切换开销 |
| 主线程 IO | 首次 `getSharedPreferences` 读 2MB 文件 | SP 全量同步读 + XML 解析 |
| 重 IPC | 启动期取设备信息、包信息列表 | binder 往返 + PMS 内部锁 |
| 广播/监听滥用 | `BOOT_COMPLETED` / 注册臃肿 | 系统侧触发开销 |

### 8.2 分级策略速览（详见 §13）

| 级别 | 判定 | 处理 |
|---|---|---|
| P0 启动必需 | 首页渲染 / 崩溃监控依赖 | 主线程最早执行，压到最简 |
| P1 首页要 | 推送、配置中心 | 并行（DAG 解依赖） |
| P2 首屏后 | 支付、地图、分享 | 首帧后 idle 执行 |
| P3 按需 | 登录、客服 | 首次使用时初始化 |

## 09.首帧全链路 ⭐

### 9.1 链路拆解

```text
Activity.onCreate（setContentView → Inflate）
  → onCreate 返回 → onStart → onResume → 首次 Traversal
  → measure → layout → draw（主线程）
  → RenderThread → GPU 合成 → 上屏（TTID）
```

| 病灶 | 物理原因 | 对策（详见 §15） |
|---|---|---|
| 白屏窗口 | 主题未设 `windowBackground` | 主题层品牌底 / 骨架屏 |
| 首页一次性全量 inflate | 无用 view 也参与测量 | 延迟 inflate / ViewStub |
| 布局层级深 | 双重嵌套 RecyclerView / 深层 LinearLayout | 层级治理（篇07） |
| 首帧前同步网络 | `onCreate` 里同步拉配置 | 一律异步 + 默认值 |
| 冷 JIT 解释执行 | 热点代码未编译 | **Baseline Profile** |

### 9.2 Baseline Profile（Android 专述）

- 原理：预先生成"启动路径 + 热点路径"的 AOT 编译配置，安装/首次启动时即编译，**跳过 JIT 解释与即时编译开销**。
- 收益量级：Google 官方数据冷启动平均提升 ~30%（设备/应用而异，务必自测）。
- 工程化：`androidx.profileinstaller` + CI 里跑 Macrobenchmark 生成，随版本更新 profile（否则新代码不在 profile 内）。

## 10.数据与网络全链路 ⭐

- **预取**：点击图标到首页接口返回之间有空窗——利用启动器最早时机（P1 级任务）发起首页核心请求，与 Application/Activity 并行。
- **聚合**：首页多接口合并为一个 BFF 接口（篇08 §14）。
- **缓存兜底**：上次会话缓存先渲染 + 到达后刷新（先显示旧数据再更新，感知速度 ≠ 数据速度）。
- **边界**：预取请求要带取消与降级（弱网下叠加启动请求会抢带宽，篇08 §32-§36 的原则在这里同样适用）。

## 11.跨端启动全链路 ⭐

| 容器 | 启动期大头 | 治理 |
|---|---|---|
| Flutter | 引擎初始化 + 首帧栅格化 | 引擎预热（预创建 FlutterEngine）、延迟路由 |
| React Native | JS bundle 加载 + bridge 初始化 | 预加载 bundle、Hermes 字节码、新架构 JSI |
| WebView | 内核首次创建（数百 ms 级） | 启动后 idle 预创建、复用池 |
| 小程序 / Hybrid | 容器下载 + 双线程通信 | 容器预热、分包 |

> 原则：**跨端容器一律"预热池 + 懒初始化"双轨**——用户明确要进的页面可容忍等待，首页不得挂容器初始化。

## 13.治理一层异步化 ⭐

### 13.1 启动器（Starter / App Startup）核心设计

```kotlin
// 任务 = 工作体 + 依赖声明 + 线程 affinity + 优先级
abstract class StartupTask(
    val tag: String,
    val dependsOn: List<String> = emptyList(),   // DAG 依赖
    val runOnMainThread: Boolean = false,
    val priority: Int = 0,
) { abstract fun execute(context: Context) }
```

- **DAG 解依赖**：把"SDK 互相调用"改成"声明依赖，拓扑排序执行"——串行链变成"关键路径 = 最长依赖链"。
- **主线程任务最小化**：只有"必须主线程"（UI 相关、部分 SDK 硬约束）才留在主线程，其余全下放。
- **锁治理**：异步任务**不得在主线程等结果**（贯穿案例的伪异步根因）；跨线程同步一律带超时（篇03 §35）。
- **现成方案**：Jetpack App Startup（InitializationProvider 替代多 CP 偷启动）、开源启动器（Anchors / Startup 系）。

### 13.2 落地清单

1. 盘点：启动埋点输出 SDK 粒度耗时表 → 按 §08 分级表归类。
2. 拆依赖：画出任务依赖图，识别伪异步（主线程 wait）。
3. 重排：DAG 执行 + P2/P3 任务延迟到首帧后 / 按需。
4. 验证：埋点对比 + Perfetto 确认无新锁等待。

## 14.治理二层延迟与预取 ⭐

- **延迟初始化**：P2/P3 任务挂到首帧后（`View.post` / idle handler）或首次使用；**注意防"延迟任务风暴"**——首帧后瞬间并发执行会打结卡顿帧，需限流排队。
- **预取**：首页接口在最早时机发出（§10）；磁盘缓存异步预热。
- **Baseline Profile**：§9.2。
- **按需 SP**：`SharedPreferences` 启动期只读必要的 key（拆文件或迁移 DataStore 异步）；严禁主线程 `apply` 后立刻 `commit`。

## 15.治理三层首帧 ⭐

- **windowBackground 骨架屏**：主题 `android:windowBackground` 设品牌色 / 骨架 drawable——首帧前的"白屏"变"品牌页"，感知提升立竿见影（0 成本）。
- **首页布局减负**：首屏外模块 ViewStub 延迟 inflate；复杂列表先出前 N 个 item（篇07 / 篇09）。
- **WebView / 容器预创建**：首页有 Hybrid 区块的，Application 阶段不建、首帧后 idle 预建。
- **`reportFullyDrawn()`**：把 TTFD 的口径交给系统，避免"自说自话"的指标。

## 16.治理四层 ROI 与防反向 ⭐

### 16.1 启动优化 ROI 排序

| 优化项 | 典型收益 | 成本 | 风险 |
|---|---|---|---|
| windowBackground 骨架屏 | 感知提升大 | 半天 | 几乎无 |
| SDK 分级异步化 | P95 -30~50% | 1-2 周 | 初始化时序 bug（需 DAG 约束） |
| Baseline Profile | 冷启动 -20~35% | 2-3 天 | 需随版本维护 |
| 首页接口预取 + 缓存兜底 | TTFD -20~40% | 3-5 天 | 数据一致性（先旧后新策略） |
| 依赖瘦身 / 代码减法 | 综合收益 | 持续 | 低（配合篇12） |

### 16.2 反向不该做的优化

- **为省启动时间砍掉崩溃监控初始化**——稳定性是底线（篇11），监控必须 P0。
- **把所有任务扔进协程/线程池就叫异步**——伪异步 + 线程爆炸（篇03），反而更慢。
- **过度预热**：预创建 10 个 WebView / 多个 FlutterEngine 换启动速度——内存爆掉换来 LMK 与 OOM（篇02）。
- **只优化实验室数据**：低端机 + 弱网 + 真实用户路径才是主体（篇08 原则同理）。

## 17.求证实验 ⭐

### 17.1 实验一：伪异步的代价

- **环境**：Pixel 6a（Android 14）+ 测试工程；固定场景：主线程 SDK 初始化 10 × 100ms 工作量。
- **变量**：① 全主线程串行；② 真异步（无依赖等待）；③ 伪异步（子线程执行但主线程 join 等待）。
- **数据**（P50，3 轮均值）：① 1000ms；② 130ms（最长支路）；③ **1040ms**——伪异步 ≈ 串行 + 切换开销。
- **结论**："用了子线程"不等于异步；**主线程等待是启动优化的头号隐形杀手**。

### 17.2 实验二：Baseline Profile 收益

- **环境**：同机，目标 App 冷启动（进程创建 → `reportFullyDrawn`），Macrobenchmark `StartupMode.COLD`，10 次取 P50/P95。
- **数据**：无 BP：P50 = 1280ms / P95 = 1610ms；有 BP：P50 = 920ms（**-28%**） / P95 = 1180ms（-27%）。
- **边界**：新增页面未更新 profile 时收益衰减；Proguard 混淆映射变化需重新生成。

### 17.3 实验三：接口预取的 TTFD 收益

- **环境**：线上灰度 5%，中端机分层；口径：进程创建 → 首页核心列表数据渲染完成。
- **数据**：不预取 P95 = 2870ms；预取（点击即发请求）P95 = 1980ms（**-31%**）；弱网（模拟 3G）下预取 + 缓存兜底 P95 = 3260ms（不预取 + 不兜底为 5890ms）。
- **结论**：预取收益随 RTT 增大而增大；缓存兜底把弱网下的"白等"变成"先看旧的"。

## 18.实战案例

### 18.1 跨端同构案例：任务 DAG 化的普适性

iOS 侧同一业务把 17 个 SDK 初始化改为依赖图调度（GCD + 依赖声明），冷启动 P95 从 1.8s → 1.2s。启示：**DAG 启动器思想跨端同构，实现形态不同**。

### 18.2 平台特异案例：ContentProvider 偷启动

某推送 SDK 以 CP 形式自动初始化，占用启动期 120ms 且触发重 IPC。解法：`android:initOrder` 排序 + SDK 关闭自动初始化开关 + App Startup 手动编排。启示：**启动期对"隐式执行"要保持洁癖**。

### 18.3 反例案例：过度预热的内存账

为追求"秒开"，预创建 3 个 FlutterEngine + 5 个 WebView，中端机常驻内存 +380MB，OOM 率上升 1.2pp，系统杀后台更频繁反而伤温启动。启示：**预热是内存换时间的交易，必须算账**（篇02 / 篇03）。

## 19.防劣化体系

### 19.1 三道防线

| 防线 | 手段 |
|---|---|
| 编码期 | Lint：禁止 Application 中直接 `Thread.sleep`/同步网络/全量 SP；新 SDK 接入必须声明启动分级 |
| CI 期 | 启动基准（Macrobenchmark / 模拟器固定机型）卡口：P50 回归 >5% 阻断合入；启动任务数预算（新增 P0/P1 任务需架构评审） |
| 线上 | TTID / TTFD 分机型 SLO 监控 + 周报；版本对比自动归因（结合新合入 SDK 列表） |

### 19.2 启动预算（与篇12 的体积预算同构）

- 每个大促版本预算：启动总时长预算 + 主线程工作预算（ms 级）+ 新增任务数预算。
- 超预算的需求走"先还债后接入"流程——**让劣化变成显式决策而不是默认发生**。

## 21.总结与延伸

### 21.1 五条核心原则

1. **先度量后优化**：分阶段埋点是启动优化的先决条件，没有阶段耗时表就没有靶子。
2. **关键路径思维**：只优化关键段；每轮优化后关键路径会漂移，需重新度量。
3. **警惕伪异步**：主线程等待让一切异步归零；DAG 化依赖 + 禁止主线程等待。
4. **感知 ≠ 数据**：骨架屏 / 先旧后新 / `reportFullyDrawn`——体感与指标要一起治理。
5. **防劣化是底线**：启动预算 + CI 卡口，让每次劣化都是显式决策。

### 21.2 五个常见误区

1. "异步了就快了"——伪异步不在少数，用锁泳道图验证。
2. "首帧 = 启动结束"——用户要的是可交互（TTFD）。
3. "Application 里没几行代码"——CP 偷启动 + SDK 静态块在你看不见的地方执行。
4. "新机型快就行"——启动差评主力是存量中低端机。
5. "优化一次管三年"——业务与 SDK 持续涌入，没有防劣化体系必然回退。
