## 01、开篇拷问

读文章前，先问自己三个问题。答得上来，说明你已理解；答不上来，就是本文的学习目标。

### 1.1 满载之惑

**Q：CPU 100% 一定是 CPU 瓶颈吗？**

- **直觉答案**："利用率都打满了，当然是 CPU 不够用。"
- **真实答案**：**利用率只回答"忙不忙"，不回答"忙得有没有效率"**。

CPU 在"跑指令"和"等内存"时都在计时——利用率无法区分这两者。判据是 **IPC**（每周期指令数）：

| IPC | 判定 | 正确动作 |
|---|---|---|
| > 2 | 健康计算，真的忙 | 优化指令数 |
| 1-2 | 正常 | 优化指令数 |
| **< 1** | **内存瓶颈**（大量周期在等数据） | 改数据布局，**砍指令数是白费** |

一次 cache miss ≈ 200 个时钟周期，CPU 在"等"的这段时间照常计入利用率。所以利用率 100% + IPC 0.7 的 App，病灶根本不在指令多少。

> **第一个心法：先问 IPC，再谈优化。**

### 1.2 低载之惑

**Q：利用率不高（< 30%），用户为什么还是卡？**

- **直觉答案**："CPU 没满，说明算力够，卡是别的原因……那是什么原因？"
- **真实答案**：**卡顿 = 主线程没在正确的时间做完事，而"没做完"不一定是"算不动"，更多是"在等"**。

主线程在等什么：

```
等锁     → 子线程持锁不放（最常见）
等 IO    → 主线程同步读磁盘 /SharedPreferences 首次加载
等 IPC   → 同步 Binder 调用远端服务，远端慢它就慢
等配额   → 后台被 cgroup 限流，分到的 CPU 时间不够
等调度   → 被高优先级线程抢占，或被按到小核上
```

这五种"等"发生时，CPU 利用率都是**低**的——线程根本没在跑。这就是 off-CPU 问题：**病灶不在计算，在等待**。

> **第二个心法：CPU 低但卡，不要看 CPU，看队列和等待。**

### 1.3 并行之惑

**Q：多线程一定加速吗？核越多开越多线程是不是越快？**

- **直觉答案**："8 个核开 16 个线程，并行度翻倍。"
- **真实答案**：**线程超过某个临界点后，加速变减速**。三笔账：

1. **切换税**：每次上下文切换 1-10μs，直接成本不高，但**间接成本**（cache 变冷 + TLB 刷新）是大头。每秒数万次切换可吃掉 10-30% CPU——纯浪费；
2. **伪共享**：两个线程各自改的变量挤在同一个 64 字节缓存行里，多核之间互相踢皮球。实测 8 线程争抢同一缓存行，并行度从 8 退化到 **1.3**（详见 §6.5）；
3. **Amdahl 定律**：串行部分不可并行，加速比上限 = 1 / (串行占比)。串行 10% 的程序，无限加线程上限也只有 10 倍。

> **第三个心法：线程不是越多越好——先算切换税和缓存账，再决定加人。**

> 带着这三个心法，我们进入正文。

## 02、问题本质

### 2.1 现象分类

**🤔 疑惑**：卡顿、ANR、发热、耗电、被杀——这些现象差异巨大，难道都是"CPU"的问题？

**💡 解答**：表现不同，但病因可以归到三类共性问题：

| 用户感知 | 真实病因 | 病因归类 |
|---|---|---|
| 列表滚动卡顿 | 主线程 on-CPU 占满，帧预算超支 | **算力型**（on-CPU） |
| ANR | 主线程被阻塞（算不动 **或** 在等待） | 算力型 / **等待型**（off-CPU） |
| 发烫、掉电快 | 高频驻留 + 大核占用 | **频率型**（能耗 ≈ 频率³） |
| 应用被杀 | 后台 CPU 超配额触发系统清理 | 频率型（配额） |

**三类病因 = 黄金公式的三项**，这是全文的总纲：

```
┌──────────────────────────────────────────────────┐
│ ① 算力型：指令数太多 → CPU 干的活太多              │
│    特征：on-CPU 高 + IPC 正常                      │
│    典型：主线程解码、复杂布局、JSON 解析            │
├──────────────────────────────────────────────────┤
│ ② 等待型：CPU 在等（内存/锁/IO/IPC/配额）          │
│    特征：利用率低但卡，或利用率高但 IPC < 1         │
│    典型：锁竞争、cache miss、同步 Binder            │
├──────────────────────────────────────────────────┤
│ ③ 频率型：单位时间的时钟数不够                     │
│    特征：同代码不同设备差几倍、发热后突然变慢        │
│    典型：小核执行、热降频、DVFS 低频驻留            │
└──────────────────────────────────────────────────┘
```

### 2.2 黄金公式

进一步抽象，所有 CPU 优化统一到一个公式：

```
程序耗时 = 指令数 × CPI × 时钟周期
        = 指令数 / IPC / 频率

┌─────────────────────────────────────────────┐
│ ① 指令数 ↓   算法 / 数据结构 / 缓存 / 去冗余  │ ← 业界 90% 的优化在这里
│ ② IPC ↑     缓存友好 / 少分支 / SIMD / 局部性 │ ← 最被忽视，常常收益更大
│ ③ 频率 ↑    绑大核 / 提优先级 / 防热降频      │ ← 移动端独有的大杠杆
└─────────────────────────────────────────────┘
```

**为什么这个抽象有价值**：

- **穷举性**：耗时被三个因子完全分解，任何优化的收益必然落在其中一项，不存在"第四条路"；
- **指导归因**：遇到慢，先测三个因子，缺哪个补哪个，避免"凭感觉改代码"；
- **指导排期**：三个因子的优化成本差异巨大（指令数改代码、IPC 改数据布局、频率调调度），ROI 排序有依据。

**为什么 ② 常比 ① 收益大**——看缓存层级的代价（详见 §6.4）：

```text
  寄存器      ~1 cycle (0.3ns)
  L1 Cache   32-64KB     4 cycles (~1ns)
  L2 Cache   256KB-1MB  12 cycles (~3ns)
  L3 Cache   2-32MB     40 cycles (~12ns)  共享
  主内存               200 cycles (~60ns)   ← 比 L1 慢 200 倍！
  Flash                       1M+ cycles    ← 慢 100 万倍
```

**一次 cache miss 浪费的时间 ≈ 跑 200 条普通指令**。所以"指令数少"不一定快，"内存访问少 / 局部性好"才重要——这就是数组顺序遍历远快于链表跳跃访问的物理原因。

**▶▶ 案例回扣**：礼物墙经验派 3 周只做了"指令数"维度的优化（减对象、池化、换协议），完全没碰 IPC 和频率——但实测数据显示 **IPC 相关的三项优化贡献了总收益的 60%**。这就是"90% 的教程只讲 1/3"的代价。

### 2.3 大小核

移动 CPU 不是"8 个一样的核"：

```text
   超大核 ×1            大核 ×3             小核 ×4
   Cortex-X4 3.3GHz    Cortex-A720 2.3GHz  Cortex-A520 1.9GHz
   IPC ~3.5            IPC ~2.5            IPC ~1.5
   适合：UI渲染/复杂计算   图片解码/网络        后台同步/心跳
```

**为什么异构设计反而高效**：能耗 ≈ 频率³。小核跑同样指令的能耗只有大核的 1/5-1/10。把后台任务按到小核、关键路径放超大核，是**性能和续航的唯一双赢解**。

对优化的颠覆性影响：

1. **同一段代码大小核耗时差 3-4 倍**——测试结论必须标注在哪个核上测的；
2. **不能拿旗舰大核的成绩代表低端机**——小核可能是 4 倍慢；
3. **线程优先级影响调度核**（nice + cgroup）——优先级低可能被按到小核上；
4. **热降频陷阱**：温度一高，即使你的线程优先级最高也会被迁到小核；
5. **DVFS**：空载时频率可能只有最高频的 1/3——**测耗时前先暖机**，否则数据全偏。

### 2.4 面试锚点

**Q："你怎么理解 CPU 优化？"**

**30 秒电梯答案**：

> CPU 优化有一个黄金公式：程序耗时 = 指令数 / IPC / 频率。所有优化只能落在这三项上：
> - **砍指令数**——算法降阶、异步化、缓存反射和正则，这是 90% 优化所在；
> - **提 IPC**——数据布局（SoA）、缓存友好、伪共享治理、分支可预测，这是最被忽视的 2/3；
> - **提频率**——关键路径绑大核、防热降频、race-to-idle 省电。
>
> 排查时用一棵决策树：利用率高先看 IPC（< 1 是内存瓶颈），利用率低但卡要看 off-CPU 等待。目标是让每一条优化都可归因、可量化、可守住。

**3 分钟展开版**：电梯答案 + 三类病因（算力/等待/频率）+ 礼物墙案例（三类并存、IPC 贡献 60% 收益）。

## 03、排查归因

### 3.1 归因决策树

**🤔 疑惑**：线上报"卡"，你只有一条 CPU 曲线，怎么下手？

**💡 解答**：和内存篇的 OOM 四分类一样，第一步永远是**先分类**。CPU 问题一棵决策树走天下：

```text
CPU 异常
  │
  ├─ 利用率持续 > 80%？─── Yes ──► 路径 A：CPU bound（§3.1-A）
  │
  ├─ 利用率不高但卡顿？─── Yes ──► 路径 B：off-CPU bound（§3.1-B）
  │
  └─ 上下文切换 > 10K/s？── Yes ──► 路径 C：调度问题
```

**为什么只分三类**：CPU 状态在任一时刻只有三种——在跑用户代码（user）、在跑内核代码（system）、没在跑（idle/等待）。三种状态对应三条归因路径，穷举完了。

**路径 A 细分**（利用率高，继续往下钻）：

```text
利用率 > 80%
  ├─ IPC < 1？ ──────────── 是 ──► 内存瓶颈！先做这个（别砍指令数）
  ├─ user 时间占比高？ ───── 是 ──► A1：业务代码热点
  │    └─ simpleperf 采 30s → 火焰图找平顶 → 改代码
  └─ system 时间占比 > 30%？─ 是 ──► A2：系统调用密集
       └─ strace / Perfetto 看 syscall 频次 → 批量化
  └─ involuntary 切换多？ ── 是 ──► A3：线程数超核 / 优先级被压
       └─ 线程池缩容 / 提优先级
```

**A1 高频热点清单**（先对照这张表，80% 的命中率）：

| 热点 | 治理方向 |
|---|---|
| `JSON.parse / Gson.fromJson` | 流式解析 / Protobuf |
| `Bitmap.decodeStream` | 异步预解码 + 缓存 |
| `Pattern.compile` 重复调用 | 正则预编译 |
| `getDeclaredMethod` 反射 | 反射缓存 |
| `String.format` / 拼接 | StringBuilder / 缓存 |

**A2 系统调用密集的典型形态**：频繁小 `read/write`、频繁 `mmap/munmap`、重复 `clock_gettime`、`futex` 风暴（锁竞争）、`binder_transact` 风暴（IPC 密集）。治理思路统一：**批量化、缓存、合并请求**。

**路径 B 细分**（利用率低却卡，最容易漏诊）：

```text
CPU% < 30% 但用户报卡
  ├─ Run Queue 高 + iowait 高？ → IO 瓶颈，看磁盘/网络
  ├─ Run Queue 高 + iowait 低？ → 锁竞争，看 sched_switch / 等待链
  └─ Run Queue 低？            → 被高优先级抢占 / cgroup 限流 / 被按到小核
```

**为什么 off-CPU 最容易漏诊**：所有主流工具（top、Profiler、simpleperf）**默认只看 on-CPU**。线程在等锁、等 IO 时完全不采样——它在监控里是"隐形"的。这就是反直觉问题"利用率不高为什么卡"的答案：被等的东西不在 CPU 视野里。

> **口诀：CPU 低但卡，不要看 CPU，看队列和等待。** 走错这条路的优化 = 礼物墙经验派的前两周。

#### 🔬 深潜：Linux 线程五态与 CPU 可见性

off-CPU 为什么"隐形"？要从 Linux 内核对线程状态的分类说起。`/proc/[pid]/stat` 的 state 字段只有五个合法值：

| 状态 | 字符 | 含义 | 利用率可见？ | 典型场景 |
|---|---|---|---|---|
| **Running** | R | 在 CPU 上跑 或 在 Run Queue 排队 | ✅ 计入 user/system | 执行指令 |
| **Interruptible Sleep** | S | 可被信号唤醒的睡眠 | ❌ **完全不计** | 等锁、等 Binder、`sleep()` |
| **Uninterruptible Sleep** | D | 不可中断睡眠 | ❌ **完全不计**（但计入 loadavg） | 磁盘 IO、kernel 关键段 |
| **Stopped** | T | 被 `SIGSTOP` 停住 | ❌ | 调试器挂起 |
| **Zombie** | Z | 已死但未被父进程回收 | ❌ | fork 后父进程未 wait |

**三个工程推论**：

1. **CPU 利用率只看到 R 态**：S / D 状态的线程 100% 不占 CPU 时间片，所以利用率一定低。这就是"低载之惑"的内核根源——**主线程卡在 S 态等 Binder，top 看一切正常**；

2. **D 态是 ANR 的隐形元凶**：D 态不响应任何信号（连 `SIGKILL` 都杀不掉），只能等 IO 完成。主线程若进入 D 态哪怕几百 ms 也会直接触发 ANR——而 CPU 曲线会告诉你"系统闲着"；

3. **loadavg 包含 D 态**：这是 Linux 独有的设计（其他 Unix 只统计 R）。意味着 loadavg 可能很高而 CPU 很空——"磁盘 IO 风暴时的高负载"就是这么来的。

**诊断工具的差异**：

```
top / /proc/stat    → 只统计 R 态 → 看"忙不忙"
loadavg             → R + D 态 → 看"排队 + IO 阻塞"
Perfetto 线程泳道   → 五态全可见 → 唯一能"看见 S 态"的工具
```

**▶▶ 案例回扣**：礼物墙经验派前两周之所以无效，就是只盯着 `/proc/stat` 的 R 态数据——而真正的病灶 22% 在图片主线程**同步**解码期间线程状态是 R（CPU 热），但调度抢占和主线程等待子线程完成的那部分是 S（看不见）。Perfetto 泳道里的 S 段是最终定位的关键证据。

### 3.2 利用率四象限

**收银台比喻**：利用率 = 收银员忙不忙；负载（Run Queue）= 排队人数。

| 利用率 | 负载 | 含义 | 应对 |
|---|---|---|---|
| 低 | 低 | 空闲 | 无需处理 |
| 高 | 低 | 计算密集、无排队 | **健康** |
| **低** | **高** | 大量线程在等 IO/锁，CPU 闲但任务堆积 | **off-CPU 问题，别优化 CPU** |
| 高 | 高 | 满载 + 排队 | 系统性繁忙，砍工作总量 |

**为什么需要两个指标才能定位**：利用率是强度，负载是存量。只看强度会漏掉"大量线程在排队但收银员闲着"的第三象限——而那恰恰是"利用率低却卡"的真相。

#### 🔬 深潜：loadavg 的 EMA 算法与读法

`/proc/loadavg` 的输出看起来很神秘：

```bash
$ cat /proc/loadavg
2.73 2.15 1.98 3/892 12346
└─1min─┘ 5min 15min  R/total  last_pid
```

**三个数字的本质**：**可运行线程数**（R + D 态）的**指数加权移动平均**（EMA）。公式：

```
每 5 秒内核采样一次 当前 Run Queue 长度 n
    ↓
load_1min  = load_1min  × e^(-5/60)   + n × (1 - e^(-5/60))
load_5min  = load_5min  × e^(-5/300)  + n × (1 - e^(-5/300))
load_15min = load_15min × e^(-5/900)  + n × (1 - e^(-5/900))
```

**三窗口的工程含义**：

| 窗口 | 响应速度 | 用途 |
|---|---|---|
| 1 min | 快速（1 分钟内变化显著） | 看**瞬时**压力峰值 |
| 5 min | 中等 | 看**持续**负载趋势 |
| 15 min | 慢（抗抖动强） | 看**长期**健康度 |

**趋势判读**：

```
load_1 > load_5 > load_15  →  负载在爬升，警惕
load_1 < load_5 < load_15  →  负载在下降，正在缓解
load_1 ≈ load_5 ≈ load_15  →  稳态（好或坏取决于绝对值）
```

**为什么 Android 不建议直接看 loadavg**：

1. **粒度太粗**：5 秒采样一次，捕捉不到百 ms 级的卡顿尖刺；
2. **包含 D 态**：IO 风暴会把 loadavg 推高，但 CPU 本身没问题；
3. **跨进程聚合**：是全系统指标，看不出是自己 App 还是别家应用在跑；
4. **大小核加权复杂**：异构 CPU 上"负载为 4"不等于"4 个核都满"——可能是 1 个大核满 + 3 个小核排队。

Android 更推荐看 **Run Queue Depth**（Perfetto 的 CPU 利用率视图）：直接给每个核的运行队列深度曲线，粒度到毫秒级，还能按核分开看。

### 3.3 火焰图识图

**原理**：采样监控每 10ms 抓一次调用栈，"函数耗时占比 ≈ 该函数出现在栈里的频次占比"——统计学的重要性采样。

**读火焰图找"平顶"**：横轴越宽 = 该函数占用越多。四类典型平顶：

| 平顶形态 | 诊断 | 治理 |
|---|---|---|
| 宽大的叶子函数 | 单一热点 | 直接优化它 |
| 宽大的中段（调用多样） | 公共路径 | 缓存 / 降频调用 |
| 又宽又深的塔 | 抽象层滥用 / 递归 | 拍平调用链 |
| 大量细碎小函数 | 内联不足 / 调用粒度太细 | 合并 / 内联 |

**为什么"平顶"是关键**：火焰图横向是时间占比。没有平顶 = 耗时均匀分散 = 没有单一热点，优化无从下手；宽平顶 = 少数函数吃掉大头 = 优化目标明确。

**采样监控的致命局限**：**默认只看 on-CPU**。线程在等锁、等 IO 时完全不采样——off-CPU 问题要用 Perfetto 的线程状态泳道补（`sched_switch`）。

#### 🔬 深潜：simpleperf 的采样原理

火焰图背后是 `simpleperf` 的采样机制，核心是 Linux 的 **`perf_event_open`** 系统调用——理解这一步能回答"采样到底怎么不干扰业务"。

**采样的触发源**：

```
① 定时中断触发（CPU-CLOCK）         → 每 N ms 中断一次
② PMU 硬件事件触发（CYCLES）        → CPU 跑够 N 个周期中断一次（更准）
③ 其他 PMU 事件（CACHE-MISSES 等）   → 事件计数到阈值触发
```

**完整采样链路**：

```
业务线程跑在 CPU 上
    ↓
PMU 计数到 1,000,000 cycles（约 1ms @ 1GHz）
    ↓
硬件触发 PMI (Performance Monitoring Interrupt)
    ↓
内核 ISR 保存当前寄存器 → 回溯调用栈 → 写入 ring buffer
    ↓
simpleperf 用户进程 mmap 读 ring buffer → 写 perf.data
    ↓
业务线程继续跑（整个中断约 10-50μs）
```

**栈回溯的三种方法**（simpleperf -g 的实现）：

| 方法 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **FP (Frame Pointer)** | 跟着 x29（AArch64）寄存器链 | 快（纳秒级） | 需编译保留 FP，Release 包常被优化掉 |
| **DWARF (CFI unwinder)** | 查 `.eh_frame` 元数据表翻译栈 | 不依赖 FP，Release 可用 | 慢（微秒级）、吃内存 |
| **LBR (Last Branch Record)** | ARM 的 BRBE 硬件记录最后 N 条分支 | 零软件开销 | 深度有限（通常 32 层） |

simpleperf 默认用 **DWARF**，这就是为什么要带 `-g` 并有符号表的 so——没有 `.eh_frame` 的 so 栈会断掉只剩叶子函数。

**采样频率的权衡**：

```
采样频率 F × 栈回溯耗时 T = 观察者开销
  99 Hz × 20μs ≈ 0.2% 开销    （线上安全）
 999 Hz × 20μs ≈ 2%   开销    （线下定位）
4999 Hz × 20μs ≈ 10%  开销    （精细分析，但误差加大）
```

**为什么是 99 Hz 不是 100 Hz**：避免与常见周期（60Hz 帧同步、100ms 定时器、1kHz 系统 tick）产生**相位锁定**——如果采样恰好永远落在"空闲间隙"或永远落在"热点段"，统计会严重失真。质数频率打破共振，是性能分析界的隐藏共识（Brendan Gregg 的建议）。

**局限：被抢占后看不见**：

```
场景：主线程被高优先级中断（如触屏 IRQ）抢走 2ms
实际：主线程状态 R → 被抢占后 S → IRQ 完 R
采样：这 2ms 落在 IRQ handler 的栈上，不在主线程栈里
    ↓
火焰图看不到"主线程被抢了 2ms"，只看到"主线程空了 2ms"
```

**正解**：on-CPU 问题看 simpleperf，调度抢占问题看 Perfetto 的 `sched_switch` 泳道——两个工具解决两类问题，无法互替。

### 3.4 案例归因

**第 1 阶段：经验派的 3 周失败**

## 04、监控体系

### 4.1 采集三层

**🤔 疑惑**：Profiler 看函数耗时很爽，为什么线上不能用？

**💡 解答**：Profiler 全量抓栈开销太大。线上必须用低开销方案，于是形成**三层采集体系**——每层回答不同的问题：

| 层 | 方案 | 回答的问题 | 粒度 | 开销 | 线上可用 |
|---|---|---|---|---|---|
| ① | OS 时间片统计 | 忙不忙 | 进程/线程级 | 极低 | ✅ |
| ② | Profiler 采样 | 谁在忙 | 函数级 | 1-3% | ⚠️ 降频采样 |
| ③ | PMU 硬件计数器 | 忙得有没有效率 | 事件级 | 极低 | ❌ 多受限 |

**第一层：OS 时间片累加器（线上主力）**

原理：内核每个时钟中断（HZ，常见 100/250/1000）给当前线程的 utime/stime 计数 +1，通过 `/proc` 暴露。**应用只是读现成数据，开销极低。**

```bash
# /proc/stat 系统级：user nice system idle iowait irq softirq
cpu  10132153 290696 3084719 46828483 16683 0 25195

# /proc/[pid]/stat 第 14、15 列 = utime / stime（累计值）
```

**计算利用率必须两次采样取差**（单次值无意义）：

```
Δproc = (utime + stime)₂ - (utime + stime)₁
CPU%  = Δproc / Δtotal
```

Android 上的可用封装：

```kotlin
// 进程级：免 /proc 权限（Android 8+ 普通应用读不了 /proc/stat）
val cpuMs = Process.getElapsedCpuTime()          // 单调递增，两次取差
// 线程级：/proc/self/task/<tid>/stat 仍可读（自己的线程）
```

局限：HZ=100 时精度下限 10ms——**看不了瞬时尖刺**，只适合宏观趋势。

**第二层：Profiler 采样（定位热点主力）**

```bash
adb shell simpleperf record -p <pid> -g --duration 30 -o perf.data
adb shell simpleperf report -i perf.data            # 直接看热点
```

局限：**只看 on-CPU**（见 §3.3），off-CPU 用 Perfetto 线程状态泳道补。

**第三层：PMU 硬件计数器（深挖 IPC）**

```bash
adb shell simpleperf stat -p <pid> --duration 10
# 关键输出：
#   instructions / cycles          → IPC（>2 优秀，<1 内存瓶颈嫌疑）
#   cache-misses / cache-references → miss rate
```

IPC 三段判读：

| IPC | 判定 | 动作 |
|---|---|---|
| > 2 | 健康计算 | 优化指令数 |
| 1-2 | 正常 | 优化指令数 |
| **< 1** | **内存瓶颈** | 改数据布局；别浪费时间砍指令数 |

局限：手机上通常需要 root / 特殊权限，**线下分析专用**。

**🔑 组合定律**：

> **线上**：① 做常态监控 + 越限时触发 ② 抓栈留证。**线下**：① + ② + ③ 组合，才能区分"指令多 / IPC 低 / 频率慢"三类原因——正好对应黄金公式三条路。

#### 🔬 深潜：为什么利用率计算必须两次采样取差

`/proc/[pid]/stat` 里的 utime/stime 是**开机以来的累计值**，不是瞬时值。单次读到 "utime = 5000" 毫无意义——你不知道这 5000 个 tick 是什么时候花的。

正确算法是差分：

```
CPU% = (本次累计 - 上次累计) / (本次时刻 - 上次时刻) 的总时间
```

**隐藏的精度陷阱**：HZ=100 时，每个 tick 10ms。一个线程在 1s 采样窗口内真实跑了 8ms，可能被记 0 个 tick（四舍五入到 0）或 1 个 tick——**小于 10ms 的占用是不可见的**。这就是"低载之惑"在监控层面的放大器：真正的尖刺可能根本没被记到。

#### 🔬 深潜：PMU 为什么是"地面真相"

软件测量（时间片、采样）都有系统误差：

- 时间片统计受 HZ 粒度限制（见上）；
- 采样监控自身吃 CPU（观察者效应）；
- 墙钟受 DVFS 影响大。

PMU（Performance Monitoring Unit）是 CPU 内部的**硬件电路**，直接数事件：cycles、instructions、cache-miss、branch-miss。它不占软件资源、不受采样间隔影响、不依赖操作系统配合——所以叫"地面真相"。

**工程约束**：ARM 上 PMU 访问需要 EL1 权限，普通 App 拿不到，所以 `simpleperf stat` 在非 root 设备只能测自己的进程（且部分 OEM 关闭了接口）。这是它"线下专用"的根本原因。

### 4.2 利用率三骗局

拿到利用率数字后，三个最常见的误读：

| 骗局 | 反例 | 真相 |
|---|---|---|
| 低 = 没问题 | 进程 5%，但 user 时间集中在主线程某 200ms 窗口 → 卡 | **均值掩盖峰值**，要看分线程分窗口 |
| 高 = 有问题 | 视频编码 80% 是健康的有效计算 | 利用率高且 IPC 高 = 在干正事 |
| iowait 高 = CPU 慢 | iowait 高 = CPU 闲着等 IO | 瓶颈在磁盘/网络，**优化 CPU 是白费** |

**共同根源**：利用率是一个**失去所有维度的聚合数字**——时间维度（均值 vs 峰值）、空间维度（整机 vs 进程 vs 线程）、性质维度（干活 vs 等待）全部被平均掉了。

**user / system / iowait 的正确读法**：

| 类型 | 含义 | 你该关心的场景 |
|---|---|---|
| **user** | 用户态代码 | 业务热点（走火焰图） |
| **system** | 内核态 | 系统调用密集（走决策树 A2） |
| **iowait** | 闲着等 IO | ⚠️ 瓶颈在磁盘/网络，**不在 CPU** |
| irq / softirq | 中断处理 | 网络风暴 / 触屏洪流 |
| steal | 被宿主抢占 | 云主机 / 容器 |

### 4.3 健康基准

| 等级 | 进程 CPU% | 体感 |
|---|---|---|
| 健康 | < 30% | 流畅、不发热 |
| 注意 | 30-60% | 偶有抖动、温热 |
| 警告 | 60-85% | 明显发热 |
| 危险 | > 85% | 卡顿明显、可能降频 |
| 严重 | 持续 100% | 热保护 / ANR |

**典型 SLO**（中端机基线，需按机型分档——大小核差异决定了不能一刀切）：

| 指标 | 目标值 |
|---|---|
| 主线程 on-CPU% P95 | < 60% |
| 进程 CPU 均值 | < 25%（前台）/ < 5%（后台） |
| 上下文切换率 | < 5000 次/秒（单线程） |
| Run Queue P95 | < 核心数 |
| IPC（典型业务，ARM A 系） | > 1.5 |

**线上监控体系四步**：

```text
采集：每 1-5s 读一次进程/线程 CPU（两次采样取差）
聚合：按机型分档（大小核差异），按前台/后台分场景，出 P95 而非均值
告警：主线程 on-CPU P95 > 60% 持续 5min / 后台均值 > 5% / 降频会话 > 1%
留证：指标越限时触发一次 30s 采样抓栈，把"发生了什么"带回来
```

**▶▶ 案例回扣**：礼物墙的 SLO 就是这么定的——"IPC ≥ 1.4 / FPS ≥ 50，CI 不达标阻断合入"，优化成果才没有在后续迭代中被悄悄吃掉。

#### 🔬 深潜：为什么 P95 完胜均值

SLO 一律用 P95 不用均值，背后是用户体验的**非线性感知**。

**均值的三宗罪**：

**① 掩盖长尾**：

```
场景 A：100 帧全部 16ms  → 均值 16ms，用户感知"丝滑"
场景 B：95 帧 10ms + 5 帧 150ms → 均值 17ms，用户感知"每秒都卡一下"
```

均值几乎一样，用户体验天差地别。问题的本质：用户感知的不是"平均流畅度"，而是**最差那几帧**。

**② Weber 定律放大主观感知**：

人对卡顿的感知遵循 Weber 定律——**同样的绝对差异，在流畅背景下更刺眼**：

```
从 16ms 跳到 50ms（+ 34ms）→ 感知"明显卡"
从 100ms 跳到 134ms（+ 34ms）→ 感知"没什么变化"（本来就卡）
```

均值把这种"跳变"抹平了，监控上看着没变化，用户却在集中反馈卡顿。

**③ Google Android Vitals 的实证数据**：

| 指标 | 低阈值 | 高阈值 | 对标数据 |
|---|---|---|---|
| Slow rendering（50ms+ 帧） | > 25% | > 50% | **P95 帧时长** |
| Frozen frames（700ms+ 帧） | > 0.1% | > 0.5% | **P99/P99.9 帧时长** |
| ANR 率 | > 0.47% | > 1.09% | **长尾事件** |

Google Play 的曝光降权算法用的全是"长尾比例"而不是均值——**均值达标不等于用户满意，长尾达标才是**。

**P95 / P99 / P99.9 的选择**：

```
P95   → 日常监控（覆盖 95% 用户的体验底线）
P99   → 严重卡顿追踪（1% 用户已经不满但还没流失）
P99.9 → 崩溃级（流失边界，必须拉警报）
```

**工程实现：如何采集 P95**：

```kotlin
// ❌ 均值统计（无法还原 P95）
val sum = AtomicLong(); val count = AtomicLong()

// ✅ 直方图统计（T-Digest 或分桶）
val histogram = ArrayList<Int>(1024)
// 1024 条样本 → 排序取 index 972 → 即为 P95
val p95 = histogram.sorted()[(histogram.size * 0.95).toInt()]
```

对大数据量场景用 **T-Digest 算法**（空间复杂度 O(log n) × 常数，百万样本只占几 KB，精度 > 99%）。

### 4.4 测量七坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 用墙钟测耗时 | NTP 调时数据跳变 | 用单调时钟（`nanoTime`） |
| 单次采样 | 拿到无意义的累计值 | 两次采样取差 |
| HZ 精度 | <10ms 的占用看不见 | 短任务用 PMU / ftrace |
| DVFS 变频 | 同指令数耗时不同 | 测前暖机 / 固频 |
| 温度降频 | 耗时突然变长 | 测前查温度（<35℃） |
| 跨核迁移 | 时钟不同步 | 绑核测试 |
| 采样器自扰 | 采样本身吃 CPU | 限 <99Hz |

**为什么这一节最重要**：所有"优化无效""数据复现不了"的挫败感，一半来自测量错误而不是优化错误。**上报数据必须附机型 / 核 / 温度 / 采样口径，否则不可作为决策依据。**

#### 🔬 深潜：Big.LITTLE 的时钟不同步

"跨核迁移时钟不同步"这个坑在异构 CPU 上特别严重。要搞清楚，得看 ARM 的时间源设计。

**ARM 的时钟寄存器层次**：

```
AArch64 时钟源
├─ CNTVCT_EL0  → 虚拟计数器（System.nanoTime 底层）
├─ CNTFRQ_EL0  → 频率寄存器（全核统一，常为 19.2 MHz）
└─ PMCCNTR_EL0 → PMU 周期计数器（每核独立，随 DVFS 变频）
```

**问题的核心**：

- **CNTVCT_EL0**：ARMv8 规范要求全核同步，但**实现由厂商决定**。部分 SoC（骁龙 6xx 系列、低端联发科）在大小核之间存在 几十到几百 ns 的漂移；
- **PMCCNTR_EL0**：每核独立，而且**频率跟着 DVFS 走**——同一个 cycle 计数在不同频率下代表的物理时间完全不同。

**实际场景的失败案例**：

```kotlin
val t1 = System.nanoTime()      // 跑在大核，CNTVCT_EL0 = X
heavyWork()                     // 中间被迁到小核
val t2 = System.nanoTime()      // 跑在小核，CNTVCT_EL0 可能 = X - 200ns
val duration = t2 - t1          // ⚠️ 可能为负数或虚假的小值！
```

真实项目遇到过 `t2 - t1 < 0` 导致 NPE 崩溃的线上事故——根因就是跨核迁移时钟倒流。

**三道防线**：

```kotlin
// ① 绑核测试（防迁移）
Process.setThreadAffinityMask(1 shl bigCoreId)

// ② 用 CLOCK_MONOTONIC_RAW（防 NTP + 不受 DVFS 影响）
val t = SystemClock.elapsedRealtimeNanos()  // 单调递增 + 不随核迁移跳变

// ③ 防御式判断（兜底）
val duration = max(0, t2 - t1)
```

**延伸：PMU 跨核采样的陷阱**：

`simpleperf stat` 在大小核异构机型上，若线程中途迁移，`cycles` 计数可能**不连续**（切核时 PMU 寄存器重置或快照不同步）。对策：

- 短任务测量：`taskset` 绑核；
- 长任务测量：忽略单次极值，用 P50 / P95 过滤异常。

**工程启示**：**测时间用 CNTVCT，测耗能用 cycles，两者不可互相替代**；跨核场景下用 `SystemClock.elapsedRealtimeNanos()` 比 `System.nanoTime()` 更稳。

#### 🔬 深潜：Perfetto 的 trace 事件模型

Perfetto 是 Android 10+ 的标准 trace 工具，取代了 systrace。为什么它比 simpleperf 更"全景"？因为采样源完全不同——**simpleperf 问"谁在跑"，Perfetto 问"系统发生了什么"**。

**Perfetto 的三类数据源**：

```
┌──────────────────────────────────────────┐
│ 用户态 trace (atrace / Trace.beginSection) │
│    ├─ Framework 预埋点（onDraw/measure/...）│
│    └─ 业务自埋点                           │
├──────────────────────────────────────────┤
│ 内核态 ftrace                              │
│    ├─ sched_switch   线程切换事件          │
│    ├─ sched_wakeup   唤醒事件              │
│    ├─ irq_handler    中断处理              │
│    ├─ cpu_frequency  频率变化              │
│    └─ binder_transaction  跨进程调用       │
├──────────────────────────────────────────┤
│ 轮询数据源                                 │
│    ├─ /proc/stat 周期采样                  │
│    ├─ /proc/meminfo                        │
│    └─ 温度传感器                           │
└──────────────────────────────────────────┘
```

**对比 simpleperf**：

| 维度 | simpleperf | Perfetto |
|---|---|---|
| 核心机制 | 采样（Sampling） | 事件（Event-based） |
| 粒度 | 函数级（10ms 一次栈） | 事件级（纳秒级精确） |
| 覆盖 | 只 on-CPU | **五态全覆盖**（R/S/D/T/Z） |
| 回答 | "谁在跑" | "系统发生了什么" |
| 开销 | 1-3%（99Hz） | 0.5-2%（事件稀疏时） |
| 文件 | perf.data 二进制 | Protobuf 格式 trace |

**sched_switch 事件的威力**：

内核每次切换线程都发一个事件，记录：

```protobuf
sched_switch {
    prev_pid: 12345      // 被切出的线程
    prev_state: S        // 切出时的状态（R/S/D...）
    next_pid: 23456      // 切入的线程
    cpu: 2               // 哪个核
    timestamp: 1234567890
}
```

有了这个流，可以**完整重建每条线程的生命周期**：

```
主线程时间轴（基于 sched_switch 重建）
──[R 跑 8ms]──[S 等 Binder 50ms]──[R 跑 2ms]──[S 等锁 20ms]──
                 ↑                            ↑
         这段 top 完全看不见    simpleperf 也看不见
         但 Perfetto 一眼就能看到
```

**延伸：Perfetto trace 的三阶段**：

```
① 配置阶段：trace_config.pbtxt 声明要采集哪些数据源
② 采集阶段：各数据源往 ring buffer 写事件（kernel + userspace）
③ 落盘阶段：traced_probes 把 ring buffer 序列化成 Protobuf trace
```

**工程启示**：

- **卡顿/ANR 分析首选 Perfetto**：唯一能看到 S/D 态和 Binder 等待的工具；
- **CPU 热点分析首选 simpleperf**：函数级火焰图比 Perfetto 的粗粒度更精准；
- **IPC/cache 深挖首选 simpleperf stat**：PMU 事件只有它能拿到。

### 4.6 面试锚点

**Q："你们线上 CPU 监控怎么做？"**

**90 秒标准答案**：

> 三层组合，各司其职：
>
> **第一层：常态采集**。每 1-5 秒读一次 `/proc/self/task/<tid>/stat`（线程级）和 `Process.getElapsedCpuTime()`（进程级），两次采样取差算利用率。按机型分档、前后台分场景聚合，出 P95 不出均值。
>
> **第二层：越限留证**。主线程 on-CPU P95 > 60% 持续 5 分钟触发告警，同时触发一次 30 秒的低频采样抓栈（simpleperf 限 99Hz 以下），把"谁在忙"带回来。
>
> **第三层：线下深挖**。simpleperf stat 看 IPC——低于 1 走数据布局优化，高于 1 走指令数优化；off-CPU 问题用 Perfetto 的 sched_switch 泳道看等待链。
>
> SLO 按机型分档：主线程 P95 < 60%、后台均值 < 5%、上下文切换 < 5000/秒，CI 卡口不达标阻断合入。

## 05、分层治理

> 治理按黄金公式分三条路，严格按 ROI 顺序执行。先看实验数据建立直觉，再讲每条路怎么走。

### 5.0 五组量化实验

**🤔 疑惑**：为什么"减少指令数"之外的优化总被忽视？因为没见过数据。

以下数据来自可控微基准（千元机骁龙 695 / Android 12 / 30 次取 P50），**量级比绝对值重要**：

| # | 实验 | 结论 | 量级 |
|---|---|---|---|
| ① | 大小核耗时差异 | 同代码大核比小核快，**SLO 必须按机型分档** | 4× |
| ② | 上下文切换代价 | 线程数远超核数反而拖慢，**线程池要科学算** | 反向劣化 |
| ③ | 缓存友好布局 | 顺序数组 vs 链表跳跃访问，**布局影响巨大** | 5-15× |
| ④ | 伪共享 | 8 线程争抢同缓存行，并行度从 8 退化到 1.3，**对齐是必修课** | 5.7× |
| ⑤ | 分支预测 | 数据有序 vs 无序，IPC 0.6 → 3.2，**喂给 CPU 可预测的数据** | 5× |

**统一到黄金公式**：

```
程序耗时 = 指令数 / IPC / 频率
            │        │       └─ 实验①：频率差 4×
            │        └─ 实验③④⑤：缓存×一致性×预测共影响 IPC 30×
            └─ §5.1（业界 90% 教程只讲这里）
```

> **隐藏地图：指令数只占 1/3，IPC 是被忽略的另外 2/3**——这就是礼物墙经验派失败的本质。

### 5.1 指令数之路

**① 算法降阶（O(n²) → O(n)）**

```kotlin
// ❌ O(n²)
for (gift in newGifts)
    for (existing in giftWall)
        if (existing.id == gift.id) merge(existing, gift)

// ✅ O(n)：哈希索引
val index = giftWall.associateBy { it.id }
for (gift in newGifts) index[gift.id]?.let { merge(it, gift) }
```

边界：n < 100 时常数因子主导，可能反而慢。

**② 异步化（不是降总量，是把总量挪出关键路径）**

```kotlin
// ❌ 主线程同步解码 30ms
override fun onBindViewHolder(h: VH, p: Int) {
    h.icon.setImageBitmap(BitmapFactory.decodeStream(...))
}
// ✅ 异步 + 占位
override fun onBindViewHolder(h: VH, p: Int) {
    h.icon.setImageResource(R.drawable.placeholder)
    decodePool.execute { val b = decode(...); h.icon.post { h.icon.setImageBitmap(b) } }
}
```

判定：任务 > 5ms 且不影响首帧 → 异步；< 1ms 异步反而亏（切换成本 0.4-0.8ms）。

**③ 序列化协议升级（JSON → Protobuf）**：JSON 每字段 200-500 指令（字符串扫描+反射），Protobuf 30-80（二进制 tag-value）。礼物墙反序列化 8μs → 1.5μs。边界：需要 Schema 管理与服务端配合。

**④ 反射 / 正则缓存**：`Pattern.compile`、`Class.forName` 每次百微秒级，重复调用 99% 是浪费。一行改动，高频场景 50-100× 收益——**性价比之王**。

```kotlin
// ❌ 每次编译   // ✅ 类加载时一次
fun isMobile(s: String) =
    Pattern.compile("^1\\d{10}$").matcher(s).matches()
private val MOBILE = Pattern.compile("^1\\d{10}$")
```

> 🔬 **深潜：ART 的四态编译模式与 Baseline Profile——同样的代码能差 5-10×**
>
> §5.1 讲的所有"减指令数"套路都有一个隐含前提：**代码已经被 AOT 编译成机器码**。可你写的 Kotlin 到底什么时候变成机器指令？答案不唯一——ART 把一个方法的执行形态切成**四种状态**，状态不同，指令数能差一个数量级。
>
> **四态模型（Android 7.0+）**：
>
> | 状态 | 触发条件 | 执行方式 | 相对速度 |
> |---|---|---|---|
> | ① Interpreted | 方法首次执行 | 解释 dex 字节码 | 1×（基准） |
> | ② JIT Compiled | 方法热度超阈值 | 运行时翻译为机器码 | 3-5× |
> | ③ AOT (speed-profile) | 空闲时后台 dex2oat | 按热点档案预编译 | 5-10× |
> | ④ AOT (speed) | 安装时全量预编译 | 所有方法编译 | 5-10×（odex 大 3-5×） |
>
> **关键信号链**：方法执行时，ART 的 `ProfileSaver` 持续把"热点方法 + 调用上下文（类初始化、虚调用目标）"写入 `/data/misc/profiles/cur/0/<pkg>/primary.prof`；设备空闲充电时 `BackgroundDexOptService` 读这份档案，调 `dex2oat` 把热点编译进 `/data/app/<pkg>/oat/arm64/base.odex`。**"App 用几天变流畅了"的真相不是玄学，是 AOT 补齐了。**
>
> **冷启动三连杀**：刚下载的 App profile 是空的，热点方法全部走解释执行或 JIT——首启比稳态慢 2-3× 的根因就在这。
>
> **Baseline Profile 的解法**：编译期预写一份 profile 打进 APK，首启直接从 AOT 态起跑：
>
> ```
> 开发期（Macrobenchmark 跑关键路径）──► baseline-prof.txt ──► 打进 APK
>                                                              │
> 运行期：PackageManager 安装时读取 ──► dex2oat 预编译 ──► 首启即 AOT 态
> ```
>
> **收益数据**（Google I/O 2022 + 国内大厂复现）：
>
> | 指标 | 无 BLP | 有 BLP | 收益 |
> |---|---|---|---|
> | 冷启动 P50 | 850ms | 620ms | -27% |
> | 首次滑动 jank 率 | 12% | 7% | -42% |
> | 稳态性能 | 基准 | 基准 | 持平（稳态都是 AOT） |
> | APK 增大 | — | +50-200KB | 可忽略 |
>
> **实操**：用 Jetpack `BaselineProfileRule` 跑一遍"冷启动 + 列表滑动 + 核心交互"自动生成 `baseline-prof.txt`。行首前缀是编译 hint：`H`=Hot（必 AOT）、`S`=Startup（启动必经）、`P`=Post-startup、`L`=类加载。
>
> **三条工程推论**：
>
> 1. **Day 0 性能必须单独测**——线下 benchmark 多次执行后已进稳态 AOT，看不见真实用户首启的卡顿；必须用 Macrobenchmark 的 `CompilationMode.None()` 复现。
> 2. **CI 要把 BLP 生成纳入流水线**——代码重构后方法签名变化，旧 profile 立即失效；发版前自动 regenerate，别让它烂尾。
> 3. **只写 80% 用户必经路径**——profile 越大 dex2oat 越慢、odex 越大，冷路径写进去是负收益。

### 5.2 IPC 之路

**① 数据布局 AoS → SoA**

```text
AoS：[id|name|cnt|ts][id|name|cnt|ts]...   ← 只用 cnt 却整块拉进 cache
SoA：[id,id,..][name,..][cnt,cnt,..][ts,..] ← 只拉 cnt 一段，命中率拉满
```

```kotlin
// ✅ 分析型计算用 SoA
class GiftColumn(val ids: LongArray, val counts: IntArray, ...)
giftColumn.counts.sum()   // 只拉 4 字节 × N
```

礼物墙此项单独贡献 IPC 0.7 → 1.4。边界：随机单条访问场景 SoA 反而慢。

**② SIMD / NEON 向量化**

```cpp
// ❌ 标量   // ✅ NEON 一次 4 个 float
for (i…) c[i]=a[i]+b[i];
for (int i = 0; i < n; i += 4)
    vst1q_f32(c+i, vaddq_f32(vld1q_f32(a+i), vld1q_f32(b+i)));
```

飘字矩阵变换 NEON 化后 -65% CPU。边界：编译器自动向量化已覆盖简单循环，只有确认的热点才手写。

> 🔬 **深潜：编译器自动向量化的"触发条件"与四大失效现场——为什么你不用手写 NEON 它也在跑**
>
> "边界：编译器自动向量化已覆盖简单循环"这句话值得展开——Clang/LLVM（NDK 底层）默认开启 `-O2` 时就会尝试把循环转成 NEON 指令（`vaddq_f32` 这类一次算 4 个 float 的 SIMD 指令）。**你写的很多 for 循环，其实早就被编译器"偷偷 NEON 化"了**——所以手写 NEON 的真实收益，只存在于自动向量化**失败**的地方。
>
> **自动向量化的四个触发前提**：
>
> 1. 循环体内**无跨迭代数据依赖**（`a[i] = a[i-1] + x[i]` 有依赖，不可并行）；
> 2. 循环次数**编译期可知或可分块处理**（先处理 `n/4*4` 个、剩余标量收尾）；
> 3. **无别名风险**——两个指针可能指向同一块内存时，重排会出错，编译器只能保守放弃；
> 4. 循环体内是**可映射为向量指令的简单操作**（算术、比较、饱和、shuffle），复杂控制流不可映射。
>
> **四大常见失效现场（对号入座）**：
>
> | # | 写法 | 为什么失效 | 解法 |
> |---|---|---|---|
> | ① | 循环内有 `if` 分支 | 向量指令没有"逐 lane 分支" | 分支改 `mask` 位运算（`vbslq`），或分支拆两个循环 |
> | ② | 循环次数是 `size()` 运行期才知道 | 可分块+标量收尾，但函数无法内联时编译器拿不到次数 | `@inline` / 移到头文件 / `restrict` 修饰指针 |
> | ③ | `float* a, float* b` 两指针参数 | 编译器怀疑 `a==b`（别名），必须保守 | 加 `restrict` 关键字声明"不重叠" |
> | ④ | 浮点累加顺序敏感 `sum += x[i]` | 向量化改变结合顺序，违反 IEEE 严格语义 | 开 `-ffast-math`（牺牲可复现性） |
>
> **验证三件套（不要靠感觉）**：
>
> ```bash
> # ① 让编译器"自首"——输出向量化报告
> # NDK 构建，CMakeLists.txt 加：
> set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -Rpass=loop-vectorize -Rpass-missed=loop-vectorize")
> # 日志会明说：哪些循环被向量化、哪些没被、为什么
>
> # ② 反汇编直接看指令（APK 的 .so 提出来后）
> llvm-objdump -d libnative.so | grep -A2 "vld1q\|vaddq"
> # 有 vld1q/vaddq → 真向量化了
> ```
>
> ```
> ③ 真机 microbenchmark 回归对比（simpleperf stat 看 IPC 变化）
> ```
>
> **三条工程推论**：
>
> 1. **优化"可向量化性"比手写 NEON 更便宜**——加一个 `restrict`、拆掉一个 if，编译器就替你写好了；手写 intrinsics 代码又难维护又绑死指令集。
> 2. **复杂控制流热点手写才划算**——飘字矩阵（固定 4x4 变换、无分支）是典型；有脏分支的业务循环先重构再谈 SIMD。
> 3. **fast-math 是双刃剑**——快，但破坏 IEEE 浮点可复现性；涉及钱、加密、坐标对齐的代码禁用。

**③ 减少分支（branch-less）**：分支预测失败罚 13-20 周期（原理见 §6.6）。把热点循环里的 if 改算术（`coerceIn`、位运算取绝对值），或**先排序让数据走向可预测**（实验⑤）。

**④ 伪共享治理（缓存行对齐）**（原理见 §6.5）

```java
// ❌ 两个计数器挤在同一 cache line，多核互相踢
class Counters { long countA; long countB; }
// ✅ JDK8+ 自动 64 字节隔离；高并发计数直接用分段设计
@sun.misc.Contended long countA;  @sun.misc.Contended long countB;
// ✅✅ 或直接 LongAdder（内部分段，比 AtomicLong 快 5-10×）
```

### 5.3 频率调度之路

**① 关键路径绑大核**

```kotlin
Process.setThreadPriority(Process.THREAD_PRIORITY_DISPLAY)  // 提优先级影响选核
```

礼物墙关键路径绑大核后单帧 -28%。边界：耗电 +2-5%，**只在关键期用，结束恢复**；注意热降频会没收你的大核（§6.3）。

**② race-to-idle**：能耗 ≈ 频率³，"3GHz 跑 100ms + 睡 900ms" 比 "1GHz 跑 1000ms" 省电 35%。后台任务**集中跑完让 CPU 睡**，别摊在一小时里。

**③ 线程池科学化**（实验②的落地）：

```kotlin
// ❌ 无界池 Executors.newCachedThreadPool()
// ✅ CPU 密集 = 物理核数；IO 密集 = 核数 × (1 + 等待/CPU)
val cpuPool = Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors())
// ✅✅ 协程（用户态调度，切换开销 ~1/100）
launch(Dispatchers.Default) { /* CPU 密集 */ }
```

> 🔬 **深潜：协程切换为什么比线程切换快 ~100×——一次切换的完整账单**
>
> "协程（用户态调度，切换开销 ~1/100）"这个注释里的 1/100 从哪来？把两种切换的**完整成本链**拆开算一遍就明白了。
>
> **线程切换的账单**（触发条件：时间片耗尽 / 主动 yield / 阻塞唤醒，全部要**陷入内核态**）：
>
> | 成本项 | 量级 | 说明 |
> |---|---|---|
> | 陷入内核 + 切换内核栈 | ~100ns | 特权级切换，固定开销 |
> | 保存/恢复全部寄存器 | ~200-500ns | 含 32 个 NEON/FP 寄存器，一个不能少 |
> | 调度器选下一个线程 | ~100-300ns | CFS 红黑树遍历、锁、负载均衡 |
> | 刷新 TLB | 0-数 μs | 换地址空间才刷（线程不换，跨进程才付） |
> | **L1/L2 cache 变冷** | **数 μs - 数十 μs** | **真正的大头**：新线程的工作集不在 cache，前几百次访存全 miss |
> | 写 processor queue + loadavg 统计 | ~100ns | 内核簿记 |
>
> **直接开销 1-5μs，算上 cache 变冷 20-50μs**——这就是 §6.2 账单的展开版。注意大头不是切换本身，是 **cache 污染**：切换越频繁，有效 cache 越小。
>
> **协程切换的账单**（触发条件：`suspend` 挂起，**全程不进内核**）：
>
> | 成本项 | 量级 | 说明 |
> |---|---|---|
> | 保存 continuation（标签 + 少量引用） | ~10-20ns | 只存"执行到哪个状态机节点"，不存寄存器现场 |
> | 调度器（队列）取下一个任务 | ~20-50ns | 用户态环形队列，无锁操作为主 |
> | **无 cache 变冷** | 0 | 还在同一个线程上跑，工作集全在 |
> | 合计 | **~50-200ns** | ≈ 一次函数调用的几倍 |
>
> **20μs vs 0.2μs，就是 ~100× 的来源**（保守说 25-100×，取决于线程切换是否伴随 cache 重建）。
>
> **为什么协程能这么轻？——CPS 变换的本质**：编译器把 `suspend fun` 改写成**状态机**，每个挂起点是一个 `state` 标签：
>
> ```kotlin
> // 你写的                                 // 编译器改写后（伪码）
> suspend fun load(): Data {                fun load(cont: Continuation): Any? {
>     val user = api.user()   // 挂起点①       when (cont.label) {
>     val feeds = api.feed()  // 挂起点②         0 -> api.user(cont.mark(1))  // 恢复时从 case 1 继续
>     return merge(user, feeds)                  1 -> api.feed(cont.mark(2))
> }                                            2 -> merge(...)
>                                            }
>                                          }
> ```
>
> "挂起"= 调一个普通函数把 continuation 存起来就返回；"恢复"= 跳回状态机的下一个 case。**没有寄存器现场要保存，因为状态机的"现场"就是那个 int 标签。**
>
> **三条工程推论**：
>
> 1. **百万级轻量并发只有协程能做**——100 万线程 = 调度自杀；100 万协程 = 100 万个小对象，切换成本趋近于零。IO 多路复用场景（网络库、批量下载）选协程是结构性优势，不是语法糖。
> 2. **协程不能加速 CPU 密集任务**——它只省"切换"，不省计算本身；CPU 密集任务总耗时 = 指令数/IPC/频率，协程一个都改不了，`Dispatchers.Default` 也只有 CPU 核数个线程。
> 3. **阻塞调用会饿死调度线程**——`Dispatchers.Default` 里的线程一旦执行阻塞 syscall（磁盘 IO、`Thread.sleep`），这个"工人"就被内核扣住了，排队协程全部陪等。阻塞操作必须 `Dispatchers.IO`（线程多）或非阻塞 API（OkIO 这类），这是协程工程化的第一铁律。

**④ 锁 → 原子 → 无锁**：锁竞争 = 上下文切换 + cache invalidation（§6.2）。计数用 `LongAdder`，队列用 `ConcurrentLinkedQueue`。边界：CAS 高竞争下自旋退化，极重竞争反而不如锁。

### 5.4 CPU 兜底四招

> §5.1-5.3 三条路做到位，稳态 CPU 问题基本能治——但**极端场景**（低端机、高温、重负载并行、后台被 cgroup 限流）仍会掉链。第四层承认"CPU 永远可能跑不赢业务"，建立兜底，对标内存篇 §5.4 OOM 兜底四招。

**① 温度分级降级**（最重要的兜底，对标内存 `onTrimMemory`）

Android 从未暴露"官方温度回调"，但 Android 10+ 的 `PowerManager.ThermalService` 提供 5 级信号，必须接：

```kotlin
val pm = getSystemService(POWER_SERVICE) as PowerManager
pm.addThermalStatusListener(mainExecutor) { status ->
    when (status) {
        PowerManager.THERMAL_STATUS_LIGHT     -> degrade(level = 1)  // 关粒子特效
        PowerManager.THERMAL_STATUS_MODERATE  -> degrade(level = 2)  // 降帧 60→30
        PowerManager.THERMAL_STATUS_SEVERE    -> degrade(level = 3)  // 关动画 + 预加载
        PowerManager.THERMAL_STATUS_CRITICAL  -> degrade(level = 4)  // 砍后台任务
        PowerManager.THERMAL_STATUS_EMERGENCY -> degrade(level = 5)  // 保核心路径
    }
}
```

**为什么必须接**：热降频一旦发生，大核频率可能从 3.0GHz 砍到 1.5GHz（§6.3），绑核策略全部失效；主动降级比"坐等 EAS 把你调去小核"**早 2-5 秒**，用户体感差距巨大。

**② 动态线程池**（根据核数、负载、温度自适应）

```kotlin
class AdaptiveThreadPool {
    private val maxCpuPool = Runtime.getRuntime().availableProcessors()
    fun recomputePoolSize(): Int {
        val load = loadavg1Min()                          // /proc/loadavg
        val thermal = thermalService.currentStatus        // 0-5
        return when {
            thermal >= 3 -> 2                             // 高温锁小池
            load > maxCpuPool * 0.8 -> maxCpuPool / 2     // 系统已满载，不加油
            else -> maxCpuPool                            // 正常
        }
    }
}
```

**实测收益**（礼物墙）：直播 30 分钟后设备温度 44°C，固定 8 线程池仍在拉满 → 卡顿帧 18%；改动态线程池后 → 卡顿帧 7%。

**③ 关键帧抢占（QoS 分层）**

主线程/Choreographer 相关线程全局最高优先级，后台任务永远低优先级，避免"后台 compile 挤掉主线程"：

```kotlin
// 主线程相关
Process.setThreadPriority(Process.THREAD_PRIORITY_URGENT_DISPLAY)  // -8
// 预加载 / 日志上传
Process.setThreadPriority(Process.THREAD_PRIORITY_BACKGROUND)     // 10
// cgroup v2 分组（Android 12+）
File("/dev/cpuctl/background/tasks").appendText("$tid\n")
```

**对比数据**：礼物墙高峰期不分层 → 后台 Protobuf 预编译占大核 15%；分层后 → cgroup `background` 组被限 CFS quota，主线程 P95 帧时长 -22%。

**④ 后台任务窗口化**（race-to-idle 的工程落地）

把分散的小任务**合并到少数几个时间窗口**集中跑完，让 CPU 深睡时间最大化：

```kotlin
// ❌ 每隔 5 分钟上报一次日志
scheduler.scheduleAtFixedRate(uploadLog, 0, 5, TimeUnit.MINUTES)

// ✅ 用 WorkManager 合并到系统的空闲窗口
WorkManager.getInstance(ctx).enqueueUniquePeriodicWork(
    "log-upload", KEEP,
    PeriodicWorkRequestBuilder<LogUploadWorker>(1, TimeUnit.HOURS)
        .setConstraints(Constraints.Builder()
            .setRequiredNetworkType(UNMETERED)
            .setRequiresDeviceIdle(true)      // 关键：空闲才跑
            .setRequiresCharging(true)        // 更关键：充电才跑
            .build())
        .build()
)
```

**原理依据**（§5.3 ②）：频率-能耗三次方关系 + 深睡静态功耗趋近 0。礼物墙后台任务窗口化后，整机功耗 -11%（JobScheduler 口径）。

**🧠 心法**：**降级比优化重要**——给 CPU 一个"喘息按钮"，比让它永远满血运行更稳定。1 秒主动降帧 >> 10 秒不可控卡顿。

> 🔬 **深潜：热降频的两级信号与"降级悬崖"问题**
>
> §5.4 ① 的 Thermal API 看似简单，但有一个工程陷阱——**降级悬崖**：
>
> ```
> 温度曲线：   38°C ──────► 42°C ─► 44°C ─► 46°C ──────►
>                           │       │       │
> ThermalStatus:  NONE     LIGHT  MODERATE SEVERE  (离散跳变)
> 用户体感：     流畅 ──────► 突然掉帧 60→30 ──────► 卡
> ```
>
> **问题**：Thermal API 是离散的 5 级，一旦从 `LIGHT` 跳到 `MODERATE`，你的降级代码从"关特效"直接跨到"降帧率"，用户体感是**悬崖式劣化**。
>
> **解法：两级信号融合**。
>
> 1. **粗粒度**：`ThermalStatus` 决定"降级档位"（骨架结构）；
> 2. **细粒度**：主动读 `/sys/class/thermal/thermal_zone*/temp` 做**平滑插值**——例如温度在 LIGHT 到 MODERATE 之间时，粒子效果密度从 100% 线性降到 30%。
>
> ```kotlin
> fun readSocTemperature(): Float {
>     // thermal_zone0 通常是 SoC 温度（厂商实现不同需探测）
>     return File("/sys/class/thermal/thermal_zone0/temp")
>         .readText().trim().toFloat() / 1000f  // milli-°C → °C
> }
>
> fun particleDensity(): Float {
>     val t = readSocTemperature()
>     return when {
>         t < 38f -> 1.0f
>         t > 46f -> 0.1f
>         else -> 1.0f - (t - 38f) / 8f * 0.9f  // 38-46°C 线性插值
>     }
> }
> ```
>
> **三条工程推论**：
>
> 1. **离散降级给结构、连续降级给细节**——粒子密度、动画速度、预加载距离这类"连续可调"参数走温度插值；UI 布局模式、帧率上限这类"离散状态"才走 ThermalStatus。
> 2. **降级必须滞回**——温度在阈值边缘抖动时，降级-恢复反复切换比不降级还糟。设置温度上下 ±2°C 的滞回带（Schmitt 触发器思路）。
> 3. **低端机 thermal_zone 不可信**——部分芯片温度传感器精度 ±5°C、刷新 500ms，别指望做高频插值；Pixel/三星旗舰可信度高。

> 🔬 **深潜：cgroup v2 的 CFS 配额——Android 12+ 后台限流的真实上限**
>
> §5.4 ③ 把 tid 写进 `/dev/cpuctl/background/tasks`，到底发生了什么？
>
> **cgroup v2 的三道闸门**（Linux 内核 CFS 调度器）：
>
> | 控制项 | 单位 | 作用 |
> |---|---|---|
> | `cpu.weight` | 1-10000（默认 100） | **按权重分 CPU**——background 组 20，foreground 100，饥饿时 1:5 分配 |
> | `cpu.max` | `quota period`（μs） | **硬上限**——例如 `20000 100000` = 每 100ms 最多跑 20ms（20% CPU） |
> | `cpu.max.burst` | μs | **允许短时超支**——避免 10ms 内每次都卡在限额上 |
>
> **Android 的默认配置**（AOSP `cpuctl.rc`）：
>
> ```
> foreground: cpu.weight = 1024, cpu.max = max  (不限)
> background: cpu.weight = 52,   cpu.max = 10000 100000  (10% 上限)
> system-background: cpu.weight = 128
> ```
>
> **关键推论**：
>
> 1. **background 组被限 10% CPU**——你的日志上报进程"看起来空闲"却跑不动，不是代码慢，是**内核在扣**；
> 2. **主动写 cgroup 要符号链接**——Android 10+ 后 `/dev/cpuctl/*` 已改为 `/sys/fs/cgroup/*`，适配要兼容；
> 3. **ANR 的隐形元凶**——如果主线程正好调了一个被扔到 background 组的 Binder 服务端，服务端被限流 → 主线程等 Binder 应答 → 卡 → ANR。off-CPU 排查（§4.1）必须覆盖 cgroup 状态。

### 5.5 Native 盲区

**🤔 疑惑**：为什么 Android Studio Profiler 的 CPU 曲线显示正常，但真机 FPS 持续抖？

**💡 解答**：Profiler 的 Java 采样器**看不见 Native 代码的 CPU 开销**。礼物墙里 25% 的 CPU 时间消耗在 `libart.so`（JIT 编译、GC 并发标记）、`libhwui.so`（UI 栅格化）、业务 `.so`（图片解码、音视频），Java 栈那层只能看到一个 `nativeDoFrame()` 的占位符。

**三类 Native 盲区**：

| 盲区 | 典型占比 | 代价表现 |
|---|---|---|
| ART 运行时（JIT/GC/dex2oat） | 5-15% | 稳态看不见，冷启动尖刺 |
| 系统图形栈（libhwui / Skia） | 10-20% | 滚动帧 Choreographer 后半段隐藏 |
| 业务 .so（解码/音视频/游戏引擎） | 10-30% | JNI 边界割裂栈，看起来像"主线程空转" |

**三件套破盲**：

```bash
# ① simpleperf 必须开 Native 栈回溯（-g dwarf）
adb shell simpleperf record -p <pid> -g --call-graph dwarf \
    --duration 10 -o /data/local/tmp/perf.data
# -g dwarf：按 DWARF 调试信息回栈，JNI 边界也能展开

# ② 符号化（线上 .so strip 过，必须本地还原）
adb pull /data/local/tmp/perf.data .
simpleperf report --symfs /path/to/unstripped_libs/ -g

# ③ 看 Native 分组（libart.so / libhwui.so / libYourApp.so）
simpleperf report --sort dso
```

**JNI 边界的两类成本**（面试加分）：

```cpp
// ❌ 高频 JNI 调用——每次 ~500ns-2μs 的边界税
for (int i = 0; i < n; i++) env->CallIntMethod(obj, mid, i);

// ✅ 批量化——一次 JNI 过去，Native 内循环
jintArray result = env->NewIntArray(n);
jint* buf = env->GetIntArrayElements(result, nullptr);
for (int i = 0; i < n; i++) buf[i] = compute(i);
env->ReleaseIntArrayElements(result, buf, 0);
```

**代价拆解**：JNI 调用 = 线程状态切换（Runnable → Native）+ 参数 marshal + 异常检查 + 返回时 GC checkpoint。单次 500ns-2μs，n = 10000 时 5-20ms，直接吃掉一帧。

> 🔬 **深潜：libart.so 里藏着多少 CPU——GC/JIT/dex2oat 的 CPU 账单**
>
> 用户经常问"GC 为什么卡？"——答案在 CPU 账单，不在内存。拆开 ART 稳态的三类 Native CPU 消费：
>
> | 消费项 | 稳态占比 | 冷启动占比 | 诊断信号 |
> |---|---|---|---|
> | **Concurrent GC**（并发标记 + CC 复制） | 1-3% | 5-10% | logcat `GC_FOR_ALLOC`、`Concurrent copying GC freed` |
> | **JIT 编译器线程** | 0.5-2% | 15-30% | `Jit thread pool worker` 线程 CPU 高 |
> | **dex2oat 后台编译** | 0%（只在空闲触发） | — | `BackgroundDexOptService` + 系统 CPU 突然 50% |
> | **类加载与 verification** | — | 10-20% | `ClassLinker::VerifyClass` 调用栈 |
>
> **三条高价值推论**：
>
> 1. **冷启动 CPU 60-70% 都在 libart.so**——这是 Baseline Profile 为什么能把冷启动降 27% 的根因（见 §5.1 深潜）。它消除的不是你的代码时间，是 **JIT 和类加载的 CPU**。
> 2. **GC 占用高 ≠ 代码分配多**——Android 11+ 分代 CC 把 Young GC 做到 < 2ms STW，但**后台并发线程**仍在扫整堆。真正的"GC CPU 开销"要看 `GcThread` 的 CPU 时间，不是看 STW。
> 3. **dex2oat 后台触发撞主线程**——用户插上充电、锁屏，`BackgroundDexOptService` 立即开火，大核吃满。如果你的后台 Service 也在跑（比如同步、推送 keep-alive），**两个 background 任务挤同一个 CPU budget**，第二天开 App 冷启动反而更慢。应对：核心场景 BLP 覆盖充分，让 dex2oat 本就无事可做。

### 5.6 ROI 排序

> 🔬 **深潜：Amdahl 定律——ROI 表为什么把"大头"永远排在 P0**
>
> 下面的 ROI 表把"主线程 IO 异步化"排在 P0，把 SIMD 排在 P3，这不是经验主义，是**一条数学定律的直接推论**。
>
> **Amdahl 定律**：整体加速比由"可优化部分占比 P"和"该部分加速倍数 S"共同决定：
>
> ```
> 整体加速比 = 1 / ( (1-P) + P/S )
>              ↑串行不可优化     ↑优化后变慢的部分
> ```
>
> **代入三组数据找手感**：
>
> | 场景 | P（占总耗时） | S（局部加速） | 整体加速比 | 整体耗时变化 |
> |---|---|---|---|---|
> | 异步化最大平顶 | 40% | ∞（挪出关键路径） | **1.67×** | -40% |
> | 优化中等热点 | 20% | 10× | 1.22× | -18% |
> | 疯狂优化小热点 | 5% | **100×** | 1.05× | -4.7% |
>
> **读表两个致命发现**：
>
> 1. **占比 5% 的代码，优化 100 倍，整体只快 5%**——P95 根本看不见（回忆 §4.3：用户可感知阈值 ~10%）。这就是"把角落代码抠到极致感动自己"的数学判决。
> 2. **"挪出关键路径"（S→∞）的收益上限就是 P 本身**——所以占比 40% 的主线程 IO 异步化，收益上限 -40%，稳居 P0；而局部加速 10× 的算法优化只能拿 -18%。**宽度的胜利 > 深度的胜利。**
>
> **火焰图上的对应操作**：Amdahl 说的 P 就是**火焰图上最宽的那个平顶的宽度占比**——"先削最宽的平顶"这条经验法则的数学本质就是 Amdahl 定律。
>
> **回扣 §5.0 的隐藏地图**：为什么说"指令数只占 1/3，IPC 是另外 2/3"？设热点代码中 1/3 时间花在执行指令（指令数可控），2/3 花在等内存/等分支预测/等伪共享（IPC 相关）。只砍指令数一半 → 整体只快 1/(2/3+1/6)=1.2 倍；把 IPC 翻倍 → 整体快 1/(1/3+1/3)=1.5 倍。**单点优化受 Amdahl 封顶，多维优化乘法生效**——三条路各砍一刀，收益是乘积不是加和。
>
> **Gustafson 反转（补个边界）**：Amdahl 的悲观假设是"总工作量固定"。当工作量可伸缩（数据量随机器变强而变大），串行部分占比会被稀释，加速比上限大幅放宽——这是"低端机降级策略"（降分辨率、减动画帧数）的理论依据：不追求把代码跑快，而是把 P 缩小。

```
ROI = (P95 改善 × 影响用户比例) / (开发成本 × 风险 × 可读性损失)
```

| 优先级 | 操作 | 收益区间 | 成本 |
|---|---|---|---|
| **P0** | 主线程 IO 异步化 | 50-200% | 低 |
| **P0** | 反射/正则缓存 | 50-100× | 一行 |
| **P1** | 算法降阶 | 10-100× | 中 |
| **P1** | 数据布局（SoA/对齐） | 2-15× | 中 |
| P2 | JSON → Protobuf | 3-10× | 高（需协同） |
| P2 | 线程池 / 协程化 | 1.5-3× | 低 |
| P3 | SIMD / branch-less | 2-5× | 高 |
| P3 | 绑核 / QoS | 1.5-4× | 低但耗电 |

> **铁律：P0/P1 没做完之前，P2/P3 是过度优化。**

**▶▶ 案例回扣：礼物墙的实际执行栈**（按 ROI 顺序）：

| 阶段 | 操作 | 单步收益 | 累计 FPS |
|---|---|---|---|
| 起点 | — | — | 12 |
| Day1 | 图片解码异步化 | -22% 主线程 | 22 |

**答题模板**（STAR + 三条路 + 兜底）：

## 06、原理深潜

> 本章为"知其所以然"而写。前面讲"怎么做"，这里讲"为什么能这么做"。

### 6.1 流水线访存墙

**问题起点**：CPU 物理上只做一件事——**不停"取指 → 解码 → 执行 → 访存 → 回写"**：

```text
  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
  │Fetch │→│Decode│→│Execute│→│ Mem  │→│Write │
  │ ~1ns │  │ ~1ns │  │1-3ns │  │1-100ns│ │ ~1ns │
  └──────┘  ┌──────┘  └──────┘  └──────┘  └──────┘
```

现代 CPU 是**流水线**执行：像工厂流水线一样，第 1 条指令在访存时，第 2 条已在执行、第 3 条在解码——理想情况下每周期完成 1 条指令（IPC = 1 的物理下限来源）。

**访存墙**：流水线各级的耗时严重不均——执行 1-3ns，访存 1-100ns。一旦流水线走到访存级而数据不在缓存，**整条流水线停摆等待**。这就是"访存是短板"的物理含义：

- 顺序访问：数据已在 L1，流水线不停 → IPC 高；
- 随机访问（链表/哈希冲突）：每跳一次可能 miss 一次 → 流水线反复停摆 → IPC 0.5-0.7。

**两个关键推论**：

1. **CPU 永远在跑**——"空闲"只是跑 idle 指令（`wfi`/`hlt`）。问题从来不是"CPU 没干活"，而是"干的活有没有价值"；
2. **超流水 + 乱序执行**让 IPC 理论上限超过 1（现代大核 3-5），但**前提是数据供给不断流**——IPC 低的本质是"流水线断流"。

### 6.2 上下文切换账单

**问题起点**：切换一次 1-10μs 听起来不大，为什么每秒几万次切换会吃掉 10-30% CPU？

**直接成本**（可控可测）：

- 保存/恢复寄存器组（ARM 约 30 个寄存器）：~0.1-0.5μs；
- 内核调度决策（选下一个线程）：~0.5-2μs；
- 切换页表（跨进程时）：TLB 刷新。

**间接成本**（大头，常被忽略）：

- **cache 变冷**：新线程的工作集不在 L1/L2，前几千条指令都在 miss。按 L1 命中 1ns、miss 60ns 算，重新"暖"一个 32KB 工作集需要数十微秒；
- **TLB 失效**：地址翻译缓存清空，前几次访存要多走页表遍历；
- **分支预测器污染**：预测历史被新线程覆盖，老线程回来后预测准确率暂时下降。

**账单结论**：直接成本 ~1-2μs，间接成本 ~5-20μs——**间接是直接的 5-10 倍**。每秒 28000 次切换（礼物墙优化前）≈ 每秒烧掉 150-500ms 的等效 CPU 时间。这就是"线程不是越多越好"的完整物理账单。

**voluntary vs involuntary 的诊断价值**：

| 类型 | 含义 | 高说明什么 |
|---|---|---|
| voluntary | 主动让出（等锁/等 IO/sleep） | 锁竞争或 IO 等待多（off-CPU 问题） |
| involuntary | 时间片用完被内核强制切 | 线程数超核数，CPU 真的不够分（调度问题） |

### 6.3 DVFS 热降频

**问题起点**：为什么同一段代码，同一台手机，上午测 100ms、下午测 400ms？

**DVFS（动态电压频率调节）机制**：

```
负载监测 → 调频 governor 决策 → 调整频率/电压 → 温度反馈再修正
   ↑                                    │
   └────────────── 持续循环 ◄────────────┘
```

- **升频条件**：调度器检测到 runnable 任务堆积；
- **降频条件**：负载下降，或**温度超过阈值**（热保护优先级最高）；
- **响应延迟**：governor 升频不是瞬时的，通常有 10-100ms 滞后——短任务的"测速"经常在低频段完成。

**热降频的三级阶梯**（典型安卓机）：

| 温度 | 行为 | 工程含义 |
|---|---|---|
| < 35℃ | 全核满频 | 基准测试的理想窗口 |
| 35-42℃ | 大核降频 / 小核接管 | 性能悄悄降 30-50%，无任何通知 |
| > 42℃ | 强制限频，甚至锁小核 | "发热后突然变卡"的元凶 |

**工程规则**：

- **测耗时前先暖机**（跑 1-2s 让频率拉起来），否则数据全偏；
- **关键路径绑大核不是保险箱**——热保护会没收大核，长时高负载任务必须按"降频后的性能"做预算；
- **race-to-idle 的物理依据**：能耗 ≈ 频率³，快跑 + 深睡的总能耗低于慢跑 + 长时间温热（温热本身也增加漏电流功耗）。

### 6.4 缓存层级局部性

**问题起点**：为什么"换个数据结构"能带来 5-15 倍提升，比算法降阶还猛？

**缓存层级与访问代价**（重复 §2.2 的表，补充工程含义）：

```text
  层级         容量         延迟          工程含义
  寄存器       ~32×8B       0 cycle      编译器分配，不可控
  L1 Cache    32-64KB      ~1ns (4c)    每核私有，工作集放这里最快
  L2 Cache    256KB-1MB    ~3ns (12c)   每核私有
  L3 Cache    2-32MB       ~12ns (40c)  共享，多核争抢
  主内存       GB 级        ~60ns (200c) ← 每次 miss 罚 200 周期
  Flash       GB 级         1M+ cycles   慢 100 万倍
```

**为什么缓存能生效**：程序的访存模式存在**局部性**——

- **时间局部性**：刚访问过的数据很快会再访问（循环变量、热对象）；
- **空间局部性**：访问某地址后，附近地址大概率被访问（数组顺序遍历）。

**缓存行的意义**：缓存以 **64 字节**为单位加载。访问 `array[0]` 时，`array[0..15]`（int 数组）全部进缓存——所以顺序遍历数组的 miss 率接近 0，而链表每个节点都可能 miss（节点在堆上不连续）。

**SoA 快的本质**：AoS 布局里"只用 cnt 字段"也要把整条 32 字节记录拉进缓存行，有效数据占比 12.5%；SoA 把 cnt 连续存放，一个缓存行装 16 个 cnt，有效占比 100%。**同样的 miss 预算，搬运的有效数据多 8 倍**。

**工程法则**：

- 热路径数据结构按**访问模式**排布字段（一起访问的放一起）；
- 大数组遍历用连续内存（数组 > 链表 > 哈希表跳转）；
- 常用小对象尽量内联（避免指针跳转带来的强制 miss）。

### 6.5 伪共享缓存行

**问题起点**：实验④——8 个线程各自改"自己的"计数器，理论上 8 倍加速，实测只有 1.3 倍。谁偷走了 6.7 倍？

**缓存一致性协议（MESI）**：每个核心的 L1 缓存要和其他核保持一致。规则：

```
核心 A 想改自己缓存里的一个缓存行
    → 必须先让其他核心的同一缓存行全部失效（Invalidate）
    → 其他核下次访问时，从 A 的缓存（或内存）重新拿
```

**伪共享（False Sharing）**：两个变量逻辑上无关，但物理上挤在**同一个 64 字节缓存行**：

```text
countA（线程 A 改）  countB（线程 B 改）
└────── 同一个 64B 缓存行 ──────┘

A 改 countA → 缓存行在 A 核变成 Modified → B 核的缓存行失效
B 改 countB → 又让 A 核失效 → A 再改 → B 再失效……
→ 缓存行在两个核之间来回"踢皮球"（乒乓），每次传递 ~40-100ns
```

**为什么"各自改各自的"也会打架**：一致性协议工作在**缓存行粒度**（64B），不理解"变量"。它只知道"这一行有人改了，别人都作废"。

**治理**：

- `@sun.misc.Contended`（JDK8+）：字段间自动填充对齐到独立缓存行；
- 手动 padding：变量间插 7 个 long（56 字节）凑满 64B；
- **LongAdder**：干脆分成多个 Cell 各自累加，读时求和——用"读时聚合"换"写时无争抢"，比 AtomicLong 快 5-10×。

**诊断**：Perfetto / perf c2c 可直接定位伪共享；简单判断法——多线程扩展性远低于核数 + 该热点附近有相邻的小字段写入。

### 6.6 分支预测器

**问题起点**：实验⑤——同样一段循环求和，数据有序时 IPC 3.2，无序时 IPC 0.6，差 5 倍。指令数一模一样，差在哪？

**流水线与分支的矛盾**：流水线要"提前开工"才高效，但遇到 `if` 分支，CPU 不知道该走哪条——**等条件算出来再开工，流水线就要空转 13-20 个周期**（分支预测失败惩罚）。

**分支预测器**：CPU 用历史统计"赌"分支走向：

```
记录每个分支的历史走向（ Taken / Not-Taken 的模式 ）
    ↓
下次遇到同一分支 → 按历史模式预测 → 猜对零成本，猜错罚 13-20 周期
```

- **可预测的分支**（数据有序、模式固定）：预测准确率 > 99%，几乎零惩罚；
- **不可预测的分支**（数据随机，如无序数组 `if (a[i] > 0)`）：预测接近抛硬币，准确率 ~50%，**每个分支平均罚 7-10 周期**。

**这就是"先排序再处理反而更快"的物理原因**：排序成本 n·log(n)，但换来了循环内分支 100% 可预测，总体反而赚（实验⑤：IPC 0.6 → 3.2）。

**工程手段**：

- 热点循环里**消灭不可预测分支**：`if` 改算术（`abs(x) = (x ^ (x >> 31)) - (x >> 31)`、`coerceIn`）；
- 数据预处理排序，让分支走向规律化；
- 概率差异大的分支：把高概率分支放前（也帮助编译器和预取）。

### 6.7 cgroup 限流

**问题起点**：为什么后台线程明明没饱和，任务却跑得特别慢？

**机制**：Android 用 cgroup 把线程分组，每组分配 CPU 配额：

```text
后台组（cpuset / cpu.cfs_quota_us）
    ↓
配额：每 100ms 周期，只允许使用 X ms 的 CPU 时间
    ↓
用完配额 → 本周期内剩余时间全部被 throttle（强制等待）
```

**前台/后台的典型配额差异**：

| 分组 | 配额 | 切后台后果 |
|---|---|---|
| 顶层（foreground） | 全部核 | 无影响 |
| 后台（background） | 1-2 个小核 或 5-20% 配额 | 同样的任务慢 5-20× |

**为什么"切后台后任务变慢"经常被误诊**：开发者看利用率——后台 CPU 才 10%，"没满啊"。真相是：**不是没跑满，是配额用完了被 throttle**。利用率低恰恰是限流的结果（等待时间不计入利用率）。

**诊断**：Perfetto 里看线程状态泳道，出现规律的 `S`（睡眠）且与 cgroup 周期对齐 → 限流；`/proc/[pid]/cgroup` 查线程所属组。

**治理**：后台任务合并批处理（减少配额碎片）、关键任务走前台 Service 提升分组、适配 Doze/App Standby 的窗口期调度。

### 6.8 EAS 调度器

**问题起点**：`setThreadPriority` 为什么能影响"跑在哪个核上"？谁在决策？

**EAS（Energy Aware Scheduling）**：Android 7+ 的默认调度器，核心思想是**在满足性能的前提下选能耗最低的核**：

```
任务放置决策 = f(任务负载预估, 各核当前容量, 能耗模型)

  小任务 → 塞给小核（能耗最低，性能够用）
  大任务 → 塞给大核（小核跑不动反而更耗能）
  关键任务（优先级高）→ 直接上大核 + 提频
```

**决策依据**：

- **任务负载追踪（Pelt/Walt）**：调度器持续估计每个线程的"需求容量"（0-1024）；
- **优先级映射**：`nice` 值和 cgroup 影响任务的需求容量估计和放置优先级；
- **能耗模型**：厂商为每颗核提供频率-能耗曲线，EAS 按曲线选"每瓦性能"最优解。

**为什么"提优先级"能变快**：两层机制——

1. **选核偏好**：高优先级任务的预估容量上调，EAS 更倾向把它放大小核放不下的核；
2. **抢占权重**：同核竞争时，优先级高的先跑、时间片更长。

**工程边界**：

- EAS 的负载估计有滞后（几百 ms 窗口），**突发短任务**经常被错误地按到小核上——这就是为什么关键路径要主动 `setThreadPriority`；
- 厂商可以替换调度策略（部分 OEM 用自家调度），同代码跨品牌表现可能不同；
- 温度保护在 EAS 之上，**热降频可以推翻一切调度决策**（§6.3）。

### 6.9 NUMA 与调度域

**问题起点**：为什么高通骁龙 8 Gen 2 的 1+4+3 架构，比上一代 1+3+4 性能提升不仅来自频率？

**NUMA（Non-Uniform Memory Access）在 ARM 的"类 NUMA"体现**：移动端 SoC 严格说不是 NUMA（不同 socket 不同内存控制器），但大小核之间**共享 L3 的拓扑与访问延迟差异**让 Linux 调度器把它建模为**调度域（sched domain）层级**：

```
sched_domain 层级（骁龙 8 Gen 2 为例）
┌─────────────────────────────────────┐
│ Level 2 (DIE)   8 核共享 L3/内存控制器 │  跨级迁移成本：缓存全冷
├─────────────────────────────────────┤
│ Level 1 (MC)   同簇共享 L2             │  同级迁移成本：L2 保留
│   ├ Prime 簇  1 × X3 @ 3.2GHz          │
│   ├ Gold  簇  4 × A715/A710 @ 2.8GHz   │
│   └ Silver 簇 3 × A510 @ 2.0GHz        │
├─────────────────────────────────────┤
│ Level 0 (SMT/CORE)  单核                │  不迁移
└─────────────────────────────────────┘
```

**调度域规则**：Linux CFS 做负载均衡时，**优先在低层级内迁移**（同簇迁移不丢 L2），不得已才跨级迁移（跨簇全冷 L1/L2 开销 20-50μs，§5.3 深潜已拆账）。

**三条工程推论**：

1. **大小核不对称是"穷人的 NUMA"**——相同的"数据亲和性"直觉适用：**长生命周期的 worker 线程绑簇**（而不是绑单核），既避免热降频后无核可用，又享受 L2 保留；
2. **CFS 的"wake affine"启发式会反直觉**——线程 A 唤醒线程 B 时，CFS 倾向把 B 放在**和 A 同一簇**（share L2 cache）；但如果 A 在小核、B 是重 CPU 任务，这个"亲和"反而害 B。应对：重任务显式 `setThreadPriority` 或用 `taskset` 绑簇。
3. **原子操作在跨簇时慢 10×**——`AtomicLong.incrementAndGet()` 同簇 L2 ping-pong 30-50ns，跨簇到 L3/DRAM ping-pong 200-500ns。多核并发计数器（§5.3 ④）在大小核混跑时翻车，必须 `LongAdder` 分段。

### 6.10 ARM 向量扩展演进

**问题起点**：NEON 是 2005 年的指令集，现代旗舰机的 CPU 还在用它吗？

**ARMv8-A 向量扩展演进路线**：

| 扩展 | 位宽 | 代表平台 | Android 可用性 |
|---|---|---|---|
| **NEON (ASIMD)** | 128 位固定 | ARMv7 起全部 | 100%，NDK 默认 |
| **SVE (Scalable Vector Extension)** | 128-2048 位**可变** | 服务器 Neoverse / 苹果 M4 | Android 旗舰 ARMv9（骁龙 8 Gen 3+）起 |
| **SVE2** | 同 SVE + 整数 SIMD + 加密 | ARMv9-A 全部 | 骁龙 8 Gen 1+、天玑 9000+ |
| **SME (Scalable Matrix Extension)** | 矩阵 tile（为 AI 设计） | ARMv9.2-A（2024+） | 2026 起旗舰 |

**SVE 相对 NEON 的三个范式转变**：

1. **"向量长度无关"编程（VLA）**——同一份代码在 128/256/512 位硬件上**自适应运行**，不用写三份：

```cpp
// NEON：绑死 128 位
for (int i = 0; i < n; i += 4)
    vst1q_f32(c+i, vaddq_f32(vld1q_f32(a+i), vld1q_f32(b+i)));

// SVE：向量长度运行期决定
svbool_t pg = svwhilelt_b32(i, n);           // 生成"活跃通道"掩码
while (svptest_first(svptrue_b32(), pg)) {
    svfloat32_t va = svld1(pg, a + i);
    svfloat32_t vb = svld1(pg, b + i);
    svst1(pg, c + i, svadd_x(pg, va, vb));
    i += svcntw();                           // CPU 告诉你当前向量宽度
    pg = svwhilelt_b32(i, n);
}
```

2. **Predicate（谓词）寄存器**——让"分支"变成"掩码"，彻底消除向量化的最大敌人（见 §5.2 NEON 深潜）；

3. **Gather/Scatter 内置**——SVE 原生支持"间接访存"，让链表/哈希这类 §6.1 "访存墙"场景也能向量化。

**工程现状与建议**：

- **2026 年主流机型**：天玑 9400 / 骁龙 8 Gen 3+ 都支持 SVE2，但 **NDK 默认不启用**，必须 `-march=armv9-a+sve2` 显式开启；
- **ANDROID_ABI 没变**：APK 还是 `arm64-v8a`，SVE 代码必须**运行期检测 `getauxval(AT_HWCAP2) & HWCAP2_SVE`** 做分支分发；
- **投入 ROI 判断**：业务侧**先把 NEON 自动向量化 + Baseline Profile + onTrimMemory 都做了再考虑 SVE**——SVE 收益主要在矩阵/深度学习（AI 推理框架用），普通业务代码 NEON 已够。

**一句话定位**：**NEON 是现在的基本功，SVE 是未来 3 年的尖端武器**，SME 之于端侧 AI 相当于 NEON 之于音视频。

## 07、高频追问

> **面试官最爱问**的 13 个"陷阱题"。每题按"问题 → 直觉答案 → 为什么错 → 正确答案 → 延伸追问"展开。

### Q1 利用率 50% 算问题吗

- **直觉**：才一半，很健康。
- **错在哪**：均值掩盖了三个维度。
- **正解**：50% 可能是"全时段均匀 50%"（健康），也可能是"99% 时间 0% + 峰值 100%"（主线程周期性尖刺，必卡）。要看**分线程、分窗口的 P95**，还要结合 IPC——50% + IPC 0.6 说明这 50% 全在低效空转。
- **追问**：采样窗口取多大？→ 监控粒度 1-5s 聚合，帧级问题要看 Systrace/Perfetto 的每帧时长，两者不可互相替代。

### Q2 iowait 高能优化 CPU 吗

- **直觉**：CPU 指标高就是要优化 CPU。
- **错在哪**：iowait 的定义是"**CPU 空闲但有待完成的 IO**"——它计入 CPU 时间线，但 CPU 此刻在歇着。
- **正解**：iowait 高 = 瓶颈在磁盘/网络。优化 CPU（降指令、绑大核）对它**完全无效**。正确方向：IO 异步化、批量读写、换存储介质。
- **追问**：iowait 高但磁盘也不忙？→ 可能是网络 IO 或同步 Binder，用 Perfetto 的 ftrace 看等待链。

### Q3 CPU 100% 一定是 CPU 瓶颈吗

- **直觉**：都满了，加机器/砍代码。
- **错在哪**：利用率不区分"跑指令"和"等内存"。
- **正解**：先测 IPC。IPC < 1 → 内存瓶颈（cache miss 高），砍指令数收益极小，要改数据布局（SoA、连续内存）。IPC > 2 才是真算力不足，砍指令数。
- **追问**：IPC 在哪看？→ `simpleperf stat`（PMU 计数），线下专用；线上只能靠"优化前后对比"间接推断。

### Q4 多线程一定加速吗

- **直觉**：8 核开 16 线程，并行度翻倍。
- **错在哪**：忽略了切换税、伪共享、Amdahl 上限。
- **正解**：三笔账——①切换的间接成本（cache/TLB 变冷）是直接的 5-10 倍；②伪共享可把 8 线程拖成 1.3 倍；③串行部分决定加速上限。**实测曲线：线程数过临界点后加速变减速**。
- **追问**：临界点怎么定？→ CPU 密集 = 物理核数；IO 密集 = 核数 × (1 + 等待/CPU 比)；压测找拐点最靠谱。

### Q5 绑大核一定快吗

- **直觉**：大核 3.3GHz 比 1.9GHz 快，绑上去准没错。
- **错在哪**：三个前提可能不成立。
- **正解**：①热降频会没收大核——手机烫了之后大核照样降频甚至锁核；②能耗 ≈ 频率³，非关键路径绑大核纯烧电；③EAS 可能把你的"大核任务"迁走（负载估计滞后）。正确姿势：**关键期绑定 + 结束恢复 + 长任务按降频性能做预算**。
- **追问**：怎么知道被降频了？→ 读 `/sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq`，Perfetto 有频率泳道。

### Q6 线程池核数怎么算

- **直觉**：网上公式背一个就行。
- **错在哪**：公式的前提（任务类型、等待比）没搞清。
- **正解**：CPU 密集 = 物理核数（超了纯交切换税）；IO 密集 = 核数 × (1 + 等待时间/CPU 时间)。但**更实用的是压测找拐点**——线程数从 1 加到 N，吞吐量峰值就是答案。
- **追问**：为什么协程更好？→ 用户态调度，切换不用进内核（无寄存器组保存恢复/TLB 刷新），开销 ~1/100；且挂起点让"等待"不再占用线程。

### Q7 race-to-idle 为什么省电

- **直觉**：3GHz 比 1GHz 费电，慢慢跑省电。
- **错在哪**：只算了频率的账，没算时间的账和静态功耗。
- **正解**：能耗 ≈ 频率³（电压随频率上升），但有**时间因子**和**深睡收益**：快跑 100ms + 深睡 900ms（功耗趋近 0），比 1GHz 慢跑 1000ms（整机持续温热、漏电流升高）总能耗低 ~35%。**慢跑的隐性成本是"一直不睡"**。
- **追问**：什么时候 race-to-idle 不成立？→ 快跑导致热降频、或任务能被摊到本来就要醒的时间窗口（如随屏刷新跑）。

### Q8 同代码为什么设备间差几倍

- **直觉**：旗舰机贵所以快，认了。
- **错在哪**：把"硬件差异"当黑盒，没拆解到可行动的层面。
- **正解**：差距来自四个可分别应对的因子——①大小核（4×）：低端机只有小核在跑，SLO 必须分档；②DVFS（1-3×）：低端机调度保守，暖机策略不同；③内存带宽（2-3×）：IPC 敏感型代码在低端机放大；④温控策略：低端机阈值更低更激进。应对：低端机降级（减动效、降精度）而不是全量优化。
- **追问**：低端机用户占比？→ 海外市场低端机常 >50%，Facebook "Building for Billions" 就是为此而写。

### Q9 采样监控会不会影响线上性能

- **直觉**：采个样能有多大开销。
- **错在哪**：观察者效应有累积和放大的场景。
- **正解**：99Hz 采样开销约 1-3%，单看可接受；但要注意三点——①采样在主线程密集期恰好落点会加重卡顿帧；②抓栈本身有锁和内存分配；③高频 + 多进程同时采会叠加。对策：限 ≤99Hz、错峰采样、越限触发制（平时不采）。
- **追问**：为什么是 99Hz 不是 100Hz？→ 避免与常见任务周期（60Hz 帧同步、100ms 定时器）产生共振导致永远采到同相位。

### Q10 为什么伪共享把 8 线程拖成 1.3 倍

- **直觉**：各自改各自的变量，井水不犯河水。
- **错在哪**：一致性协议工作在 64B 缓存行粒度，不理解"变量"。
- **正解**：两个变量同缓存行 → 一核写入使另一核的缓存行失效 → 缓存行在核间乒乓（每次 ~40-100ns）。8 线程 = 7 份失效广播，并行度退化到 1.3。治理：`@Contended` 对齐、手动 padding、LongAdder 分段。
- **追问**：怎么发现？→ 表现是"加线程不加速 + perf c2c 能定位"；快速判断：热点附近有相邻小字段的高频写入。

### Q11 频率翻倍为什么耗时没减半

- **直觉**：频率 1.5GHz → 3.0GHz，耗时应该砍半。
- **错在哪**：黄金公式里耗时 = 指令数 / IPC / 频率，频率只是三项之一。
- **正解**：**只有 CPU-bound 代码**（IPC 高、少 miss）频率翻倍才能近似耗时减半。现实中大部分业务代码是 **memory-bound**——cache miss 时 CPU 空等 DRAM，内存频率/带宽没变，耗时下降幅度可能只有 10-20%。更残酷的是：**提频通常伴随热降频风险**，持续满频几秒后反而比低频更慢。
- **追问**：怎么判断 CPU-bound vs memory-bound？→ 简单实验：`cpufreq` 从 1.5GHz 到 3.0GHz，耗时下降 ≥ 40% 为 CPU-bound，< 20% 为 memory-bound；配合 `simpleperf stat` 看 cache-miss 率佐证。

### Q12 协程为什么还需要线程池

- **直觉**：既然协程"切换 1/100"，开百万协程不就够了？
- **错在哪**：协程不执行计算，底层仍需要线程去跑用户代码。
- **正解**：协程是**调度单位**，线程是**执行单位**。`Dispatchers.Default` 底层是 N=核数的 ForkJoinPool，所有 CPU 密集协程**仍然在这几根线程里排队**。协程省掉的是"等待时的线程占用"（挂起不占线程），不是执行计算的 CPU。所以：IO 密集任务开百万协程合理（99% 时间在等），CPU 密集开再多也不加速。
- **追问**：那为什么 Server 端 Netty 这种能承载百万并发？→ Netty 走的是"事件驱动 + 少量 EventLoop 线程"模型，和协程本质同构——都是用"空闲时让出线程"换高并发。移动端同理，但受限于单设备算力，意义有限。

### Q13 Baseline Profile 稳态为什么没收益

- **直觉**：既然 BLP 让方法变 AOT，稳态应该也更快。
- **错在哪**：稳态下所有热点早已被 JIT→AOT 覆盖，BLP 的"预编译"没有净增量。
- **正解**：BLP 的收益**只在"从冷到热"的过渡期**：首次启动、安装后第一周、新页面首次打开——这些时刻方法还没进 AOT，BLP 让它直接起跑。稳态（App 用一周后）运行 10 分钟的性能，BLP 和无 BLP 基本一致，这是正常的，不是 BLP 没用。
- **追问**：怎么证明 BLP 真的在起作用？→ Macrobenchmark 用三种 `CompilationMode` 对比：`None()`（纯解释）、`Partial(baselineProfile = true)`（走 BLP）、`Full()`（全 AOT）；三个数据在冷启动场景应形成明显梯度，否则说明 BLP 覆盖不全。

## 附录：面试模板

> 5 个最高频面试题的**标准回答模板**。

### A1 CPU 优化理解

**90 秒版**：

> CPU 优化有且只有三条路，来自黄金公式：程序耗时 = 指令数 / IPC / 频率。
>
> **指令数**是 90% 优化所在：算法降阶、异步化、反射正则缓存、序列化协议升级。
> **IPC** 是最被忽视的 2/3：数据布局（SoA）、伪共享治理、分支可预测化、SIMD。一次 cache miss 罚 200 周期，"少访问内存"常常比"少执行指令"收益更大。
> **频率**是移动端特有杠杆：绑大核、防热降频、race-to-idle。
>
> 排查靠一棵决策树：利用率高先看 IPC（< 1 是内存瓶颈），利用率低但卡看 off-CPU 等待（锁/IO/IPC/cgroup）。我做过的礼物墙案例：四平顶 + IPC 0.7 双病灶，3 天 FPS 12 → 56，其中 IPC 相关优化贡献 60% 收益。

### A2 线上 CPU 监控方案

**STAR 模板**：

> **采集**：每 1-5 秒读线程级 `/proc/self/task/<tid>/stat`（两次采样取差）+ 进程级 `Process.getElapsedCpuTime()`，开销极低。按机型分档（大小核差 4 倍，不能一刀切）、前后台分场景、出 P95 不出均值。
>
> **告警**：主线程 on-CPU P95 > 60% 持续 5 分钟；后台均值 > 5%；上下文切换 > 5000/秒。
>
> **留证**：指标越限时触发一次 30 秒低频采样（simpleperf ≤99Hz），把火焰图带回来，回答"谁在忙"。
>
> **深挖**：线下用 PMU 看 IPC 区分"指令多 vs IPC 低"，用 Perfetto 线程状态泳道看 off-CPU 等待链。
>
> **防劣化**：CI 卡口跑核心场景基准（我们定的 IPC ≥ 1.4 / FPS ≥ 50），不达标阻断合入。

### A3 火焰图怎么读

> **原理**：采样监控每 10ms 抓一次栈，函数在栈里出现的频次 ≈ 它的耗时占比。
>
> **核心动作：找平顶**。横轴越宽 = 占用越多，四类平顶四种诊断：
> 1. 宽大叶子函数 → 单一热点，直接优化；
> 2. 宽大中段（下面调用多样）→ 公共路径（序列化、日志），做缓存降频；
> 3. 又宽又深的塔 → 抽象滥用/递归，拍平调用链；
> 4. 大量细碎小函数 → 调用粒度太细，合并内联。
>
> **关键局限**：默认只看 on-CPU。线程等锁/等 IO 时不采栈，是"隐形"的——off-CPU 问题用 Perfetto 的 sched_switch 泳道，看线程状态和等待链。
>
> 礼物墙案例里，火焰图四平顶（layout 28% / 解码 22% / 飘字 17% / 反序列化 15%）直接给出了治理清单。

### A4 ANR 和 CPU 的关系

> ANR = 主线程 5 秒内没处理完输入/广播。主线程"没做完"两种可能：
>
> **① on-CPU 占满**：主线程在真算——同步解码、复杂布局、大量序列化。CPU 利用率高、火焰图有平顶。治理：把活挪走（异步化）、把活变少（算法/缓存）。
>
> **② off-CPU 阻塞**（更常见，约 70%）：主线程在等——等锁、同步 Binder、主线程 IO、cgroup 限流。此时 CPU 利用率**很低**，top 看一切正常。诊断必须用 Perfetto 看主线程状态：S（睡眠）→ 查等谁（futex/Binder driver），D（不可中断）→ IO。
>
> **排查口诀**：先看利用率分流——高走火焰图，低走等待链。只盯 CPU 曲线找 ANR，会漏掉 70% 的真相。

### A5 优化故事线

**背景**：直播大促礼物墙，高峰期 FPS 58 → 12，千元机反馈占 73%，送礼 GMV -28%。此前团队 3 周 3 次发版（减对象、换协议、池化列表）无效。

**归因**：先重定义问题——"礼物墙卡" → "主线程 P95 帧时长 80ms、on-CPU 持续 >95%、IPC 0.7"。决策树走路径 A，simpleperf 火焰图四个平顶（layout 28% / 主线程解码 22% / 飘字矩阵 17% / 反序列化 15%），PMU 补刀发现 IPC 0.7 + cache-miss 27%——**指令数和 IPC 双病灶并存**，经验派只治了前者。

**治理**（3 天，按 ROI）：
- Day1：解码异步化（-22% 主线程）+ LongAdder 治伪共享（-8% CPU）；
- Day2：GiftItem AoS → SoA（IPC 0.7 → 1.4）+ JSON → Protobuf（-15% CPU）；
- Day3：关键路径绑大核（-28% 单帧）+ 飘字 NEON 化（-65%）。

**结果**：
- FPS 平均：12.4 → **56.8**；FPS P5：4.2 → 51.3；
- 主线程 P95 帧时长：80ms → 18ms；IPC：0.7 → 1.6；
- L1 cache miss：27% → 4.1%；上下文切换：28000 → 9500/秒；
- 送礼成功率：71.2% → **99.4%**。

**沉淀**：A/B 归因发现影响 IPC 的三项优化贡献了总收益的 **60%**——恰好是凭直觉完全找不到的维度。教训：**CPU 优化的地图上，指令数只是 1/3，IPC 是被忽略的另外 2/3**。
