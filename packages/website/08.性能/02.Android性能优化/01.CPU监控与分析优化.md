# CPU 监控与分析

> **本文主线**：CPU 是什么 → 为什么重要 → 监控什么 → 如何获取数据 → 如何分析 → 如何优化 → 如何防劣化。
> **📊 学习成本预估** ｜ 难度：⭐⭐⭐⭐（4/5）｜ 阅读：约 40 分钟 ｜ 实操：top / simpleperf / Perfetto 各一次 + 一个微基准实验
> **🔗 前置阅读**：篇03 线程与进程模型优化, 篇13 App 冷启动优化（规划中）　｜　**➡️ 后续延伸**：篇04 IO 与存储性能优化

**一句话总纲**：

```text
   CPU 是什么：一个按时间片计费的指令执行器
   为什么重要：卡顿 / ANR / 耗电 / 发热，最终都在这里算账
   监控什么：  利用率 × 负载 × 上下文切换 × IPC（四件套，缺一必误判）
   如何获取：  OS 时间片（线上）→ Profiler 采样（定位）→ PMU 计数器（深挖）
   如何分析：  一棵决策树三分支：CPU bound / off-CPU bound / 调度问题
   如何优化：  黄金公式三条路——指令数↓ / IPC↑ / 频率↑，按 ROI 排序执行
```

## 00.贯穿案例：直播礼物墙卡顿

> 全文用这个真实案例串起来。先看"经验派"怎么失败，再看"方法论派"怎么 3 天解决。

### 0.1 问题背景

- **业务场景**：直播大促活动现场，"礼物墙"3 列网格、每秒新增 5-8 条记录、单条带礼物图标 + 头像 + 飘字动画。
- **现象**：高峰期（2000+ 在线）**FPS 从 58 跌到 12**，大量用户投诉"礼物送不出去"。
- **机型分布**：千元机反馈占 73%，旗舰机偶发。
- **业务损失**：高峰期送礼 GMV 同比 -28%。

### 0.2 经验派的 3 周失败

| 假设 | 措施 | 结果 |
|---|---|---|
| 内存不够 | 加大缓存、减少对象创建 | FPS 仅 +2 |
| 网络拉胯 | 长连接改 WebSocket | 弹幕更快但更卡 |
| 列表没复用 | 引入 RecyclerView 池化 | 中端机 +5 FPS，低端机无效 |

**3 周、3 次发版、未解决**。失败原因：没有用数据归因，凭直觉改代码——"看起来正确但与根因无关"。

### 0.3 方法派的 3 天闭环（预告）

| 天 | 动作 | 发现 / 结果 |
|---|---|---|
| D1 | 分阶段打点 + 采样 | 主线程 on-CPU 95%；火焰图四个平顶 |
| D2 | PMU 验证 | IPC = 0.7、cache-miss 27% → 内存瓶颈叠加 |
| D3 | 五项优化落地 | FPS 12 → 56（完整数据见 §7.2） |

> **重定义问题是第一步**："礼物墙卡" → "主线程 P95 帧时长 80ms、低端机 on-CPU 持续 >95%、IPC 异常低"。可量化、可监控、可设 SLO——这是后续一切的前提。

## 01.CPU 是什么：一个按时间片计费的指令执行器

### 1.1 物理本质：只做一件事的流水线

CPU 物理上只做一件事：**不停"取指 → 解码 → 执行 → 访存 → 回写"**。

```text
  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
  │Fetch │→│Decode│→│Execute│→│ Mem  │→│Write │
  │ ~1ns │  │ ~1ns │  │1-3ns │  │1-100ns│ │ ~1ns │
  └──────┘  └──────┘  └──────┘  └──────┘  └──────┘
```

两个关键推论：

1. **CPU 永远在跑**——"空闲"只是跑 idle 指令（`wfi`/`hlt`）。问题从来不是"CPU 没干活"，而是"干的活有没有价值"。
2. **访存是流水线的短板**——执行 1ns、访存可到 100ns，CPU 大量时间在"等数据"（见 §1.2）。

### 1.2 性能黄金公式：优化 CPU 有且只有三条路

```
程序耗时 = 指令数 × CPI × 时钟周期
        = 指令数 / IPC / 频率

┌─────────────────────────────────────────────┐
│ ① 指令数 ↓   算法 / 数据结构 / 缓存 / 去冗余  │ ← 业界 90% 的优化在这里
│ ② IPC ↑     缓存友好 / 少分支 / SIMD / 局部性 │ ← 最被忽视，常常收益更大
│ ③ 频率 ↑    绑大核 / 提优先级 / 防热降频      │ ← 移动端独有的大杠杆
└─────────────────────────────────────────────┘
```

**为什么 ② 常比 ① 收益大**——看缓存层级的代价：

```text
  寄存器      ~1 cycle (0.3ns)
  L1 Cache   32-64KB     4 cycles (~1ns)
  L2 Cache   256KB-1MB  12 cycles (~3ns)
  L3 Cache   2-32MB     40 cycles (~12ns)  共享
  主内存               200 cycles (~60ns)   ← 比 L1 慢 200 倍！
  Flash                       1M+ cycles    ← 慢 100 万倍
```

**一次 cache miss 浪费的时间 ≈ 跑 200 条普通指令**。所以"指令数少"不一定快，"内存访问少 / 局部性好"才重要——这就是数组顺序遍历远快于链表跳跃访问的物理原因（数据见 §6.0）。

### 1.3 时间片与上下文切换：利用率的物理来源

OS 把 CPU 切成时间片轮流分给线程。`top` 里的"CPU 利用率"本质是**时间片占用统计**：

```
CPU 时间 = user + nice + system + idle + iowait + irq + softirq + steal
利用率   = 非 idle 时间 / 总时间
```

| 类型 | 含义 | 你该关心的场景 |
|---|---|---|
| **user** | 用户态代码 | 业务热点（走火焰图） |
| **system** | 内核态 | 系统调用密集（走 §5.2-A2） |
| **iowait** | 闲着等 IO | ⚠️ 瓶颈在磁盘/网络，**不在 CPU** |
| irq / softirq | 中断处理 | 网络风暴 / 触屏洪流 |
| steal | 被宿主抢占 | 云主机 / 容器 |

**上下文切换的账**：切一次 = 保存/恢复寄存器 + TLB 刷新 + cache 变冷，单次 1-10μs，其中**大头是间接的 cache/TLB miss**。每秒数万次切换可吃掉 10-30% CPU——纯浪费。这是"线程不是越多越好"的物理根据（数据见 §6.0 实验②）。

### 1.4 异构大小核：移动 CPU 不是"8 个一样的核"

```text
   超大核 ×1            大核 ×3             小核 ×4
   Cortex-X4 3.3GHz    Cortex-A720 2.3GHz  Cortex-A520 1.9GHz
   IPC ~3.5            IPC ~2.5            IPC ~1.5
   适合：UI渲染/复杂计算   图片解码/网络        后台同步/心跳
```

对优化的颠覆性影响：

1. **同一段代码大小核耗时差 3-4 倍**——测试结论必须标注在哪个核上测的。
2. **不能拿旗舰大核的成绩代表低端机**——小核可能是 4 倍慢。
3. **线程优先级影响调度核**（nice + cgroup）——优先级低可能被按到小核上。
4. **热降频陷阱**：温度一高，即使你的线程优先级最高也会被迁到小核。
5. **DVFS**：空载时频率可能只有最高频的 1/3——**测耗时前先暖机**，否则数据全偏。

## 02.为什么重要：所有性能问题最终都在这里算账

### 2.1 现象与代价

卡顿、ANR、耗电、发热、被系统杀死——这些用户可感的问题，物理根源都要落到 CPU：

| 用户感知 | CPU 侧根因 |
|---|---|
| 列表滚动卡顿 | 主线程 on-CPU 占满 / 帧预算超支 |
| ANR | 主线程被阻塞（CPU 满载或 off-CPU 等待） |
| 发烫、掉电快 | 高频驻留 + 大核占用（能耗 ≈ 频率³） |
| 应用被杀 | 后台 CPU 超配额触发系统清理 |

**业务代价**（行业数据）：

| 指标 | 影响 | 来源 |
|---|---|---|
| CPU 持续 > 80%，ANR 率提升 3× | 崩溃率劣化 | Play Console 公开数据 |
| 发热 5℃、电量 +20% | 续航焦虑、卸载率上升 | Google Android Vitals |
| 海外低端机同任务慢 4× | 低端机用户流失 | Facebook Building for Billions |

### 2.2 健康度基准与 SLO

| 等级 | 进程 CPU% | 体感 |
|---|---|---|
| 健康 | < 30% | 流畅、不发热 |
| 注意 | 30-60% | 偶有抖动、温热 |
| 警告 | 60-85% | 明显发热 |
| 危险 | > 85% | 卡顿明显、可能降频 |
| 严重 | 持续 100% | 热保护 / ANR |

**典型 SLO**（中端机基线，需按机型分档——大小核差异决定了不能一刀切）：

| 指标 | 目标值 |
|---|---|
| 主线程 on-CPU% P95 | < 60% |
| 进程 CPU 均值 | < 25%（前台）/ < 5%（后台） |
| 上下文切换率 | < 5000 次/秒（单线程） |
| Run Queue P95 | < 核心数 |
| IPC（典型业务，ARM A 系） | > 1.5 |

### 2.3 六个反直觉问题（带着它们读下去）

1. CPU 50% 的 App 算有问题吗？→ §3.2
2. CPU 100% 一定是 CPU 瓶颈吗？→ §5.4（可能是内存瓶颈）
3. 多线程一定加速吗？→ §6.0 实验②
4. 同一段代码为什么设备间差几倍？→ §1.4
5. **CPU 利用率不高但用户卡，问题在哪？** → §3.3（线上占比极高的一类）
6. 绑大核一定快吗？→ §6.3（热降频陷阱）

## 03.如何监控：指标四件套与正确读法

### 3.1 监控什么：四件套

| 指标 | 回答的问题 | 数据源 |
|---|---|---|
| **利用率** | CPU 忙不忙 | `/proc/stat`、`/proc/[pid]/stat` |
| **负载（Run Queue）** | 队伍排多长 | `/proc/loadavg` |
| **上下文切换率** | 切换税交了多少 | `/proc/[pid]/status`（voluntary / involuntary） |
| **IPC** | 忙得有没有效率 | PMU（`simpleperf stat`） |

> **只看利用率必误判**。利用率是"忙不忙"，不回答"为什么忙"和"排队没有"。

### 3.2 利用率的三个骗局

| 骗局 | 反例 | 真相 |
|---|---|---|
| 低 = 没问题 | 进程 5%，但 user 时间集中在主线程某 200ms 窗口 → 卡 | **均值掩盖峰值**，要看分线程分窗口 |
| 高 = 有问题 | 视频编码 80% 是健康的有效计算 | 利用率高且 IPC 高 = 在干正事 |
| iowait 高 = CPU 慢 | iowait 高 = CPU 闲着等 IO | 瓶颈在磁盘/网络，**优化 CPU 是白费** |

### 3.3 利用率 × 负载四象限（归因的第一刀）

**收银台比喻**：利用率 = 收银员忙不忙；负载 = 排队人数。

| 利用率 | 负载 | 含义 | 应对 |
|---|---|---|---|
| 低 | 低 | 空闲 | 无需处理 |
| 高 | 低 | 计算密集、无排队 | **健康** |
| **低** | **高** | 大量线程在等 IO/锁，CPU 闲但任务堆积 | **off-CPU 问题，别优化 CPU** |
| 高 | 高 | 满载 + 排队 | 系统性繁忙，砍工作总量 |

> 反直觉问题 ⑤ 的答案："利用率低却卡" 几乎都是第三象限——看队列和等待，不看 CPU。

### 3.4 线上监控体系设计

```text
采集：每 1-5s 读一次进程/线程 CPU（两次采样取差，见 §4.1）
聚合：按机型分档（大小核差异），按前台/后台分场景，出 P95 而非均值
告警：主线程 on-CPU P95 > 60% 持续 5min / 后台均值 > 5% / 降频会话 > 1%
留证：指标越限时触发一次 30s 采样抓栈（§4.2），把"发生了什么"带回来
```

## 04.如何获取数据：三层采集源

### 4.1 第一层：OS 时间片累加器（线上监控主力）

**原理**：内核每个时钟中断（HZ，常见 100/250/1000）给当前线程的 utime/stime 计数 +1，通过 `/proc` 暴露。**应用只是读现成数据，开销极低。**

```bash
# /proc/stat 系统级：user nice system idle iowait irq softirq
cpu  10132153 290696 3084719 46828483 16683 0 25195

# /proc/[pid]/stat 第 14、15 列 = utime / stime（累计值）
```

**计算利用率必须两次采样取差**（单次值无意义）：

```
Δproc = (utime + stime)₂ - (utime + stime)₁
CPU%  = Δproc / Δtotal
```

Android 上的可用封装：

```kotlin
// 进程级：免 /proc 权限（Android 8+ 普通应用读不了 /proc/stat）
val cpuMs = Process.getElapsedCpuTime()          // 单调递增，两次取差
// 线程级：/proc/self/task/<tid>/stat 仍可读（自己的线程）
```

**局限**：HZ=100 时精度下限 10ms——**看不了瞬时尖刺**，只适合宏观趋势。

### 4.2 第二层：Profiler 采样（定位热点主力）

**原理**：每 10ms 暂停目标线程抓一次调用栈，"函数耗时占比 ≈ 该函数出现在栈里的频次占比"——统计学的重要性采样。99Hz 采样开销约 1-3%。

```bash
# Android 官方工具链
adb shell simpleperf record -p <pid> -g --duration 30 -o perf.data
adb shell simpleperf report -i perf.data            # 直接看热点
# 或导出 chrome trace 格式看火焰图
```

**读火焰图找"平顶"**：横轴越宽 = 该函数占用越多。四类典型平顶：

| 平顶形态 | 诊断 |
|---|---|
| 宽大的叶子函数 | 单一热点（优化它） |
| 宽大的中段（调用多样） | 公共路径（如序列化、日志） |
| 又宽又深的塔 | 抽象层滥用 / 递归 |
| 大量细碎小函数 | 内联不足 / 调用粒度太细 |

**致命局限**：**默认只看 on-CPU**。线程在等锁、等 IO 时完全不采样——off-CPU 问题要用 Perfetto 的线程状态泳道补（`sched_switch`），原理见 [篇06 卡顿与 ANR 监控治理 §4.2](https://yccoding.com/pages/b16f1c/)。

### 4.3 第三层：PMU 硬件计数器（深挖 IPC）

**原理**：CPU 内置硬件电路精确计数 cycles / instructions / cache-misses / branch-misses——**性能监控的地面真相**，零软件误差。

```bash
adb shell simpleperf stat -p <pid> --duration 10
# 关键输出：
#   instructions / cycles          → IPC（>2 优秀，<1 内存瓶颈嫌疑）
#   cache-misses / cache-references → miss rate
```

**IPC 三段判读**（CPU 100% 但慢时的唯一武器）：

| IPC | 判定 | 动作 |
|---|---|---|
| > 2 | 健康计算 | 优化指令数（§6.1） |
| 1-2 | 正常 | 优化指令数 |
| **< 1** | **内存瓶颈** | cache miss 高→改数据布局（§6.2）；别浪费时间砍指令数 |

**局限**：手机上通常需要 root / 特殊权限，**线下分析专用**。

### 4.4 三层组合定律

| 方案 | 粒度 | 开销 | 线上可用 | 主要局限 |
|---|---|---|---|---|
| OS 时间片 | 进程/线程级 | 极低 | ✅ | 精度受 HZ 限制 |
| Profiler 采样 | 函数级 | 1-3% | ⚠️ 需降频采样 | 只看 on-CPU |
| PMU 计数器 | 事件级 | 极低 | ❌ 多受限 | 需特权 |

> **线上**：① 做常态监控 + 越限时触发 ② 抓栈。**线下**：① + ② + ③ 组合，才能区分"指令多 / IPC 低 / 频率慢"三类原因——正好对应黄金公式三条路。

### 4.5 数据可信度：七个测量的坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 用墙钟测耗时 | NTP 调时数据跳变 | 用单调时钟（`nanoTime`） |
| 单次采样 | 拿到无意义的累计值 | 两次采样取差 |
| HZ 精度 | <10ms 的占用看不见 | 短任务用 PMU / ftrace |
| DVFS 变频 | 同指令数耗时不同 | 测前暖机 / 固频 |
| 温度降频 | 耗时突然变长 | 测前查温度（<35℃） |
| 跨核迁移 | 时钟不同步 | 绑核测试 |
| 采样器自扰 | 采样本身吃 CPU | 限 <99Hz |

> 上报数据必须附**机型 / 核 / 温度 / 采样口径**，否则不可作为决策依据。

## 05.如何分析：一棵决策树走天下

### 5.1 归因决策树

```text
CPU 异常
  │
  ├─ 利用率持续 > 80%？─── Yes ──► 路径 A：CPU bound（§5.2）
  │
  ├─ 利用率不高但卡顿？─── Yes ──► 路径 B：off-CPU bound（§5.3）
  │
  └─ 上下文切换 > 10K/s？── Yes ──► 路径 C：调度问题（§5.2-A3）
```

### 5.2 路径 A：利用率高（CPU bound）

```text
利用率 > 80%
  ├─ IPC < 1？ ──────────── 是 ──► 内存瓶颈！跳 §5.4（先做这个）
  ├─ user 时间占比高？ ───── 是 ──► A1：业务代码热点
  │    └─ simpleperf 采 30s → 火焰图找平顶 → 改代码（§6.1）
  └─ system 时间占比 > 30%？─ 是 ──► A2：系统调用密集
       └─ strace / Perfetto 看 syscall 频次 → 批量化
  └─ involuntary 切换多？ ── 是 ──► A3：线程数超核 / 优先级被压
       └─ 线程池缩容 / 提优先级（§6.3）
```

**A1 高频热点清单**（先对照这张表，80% 的命中率）：

| 热点 | 治理方向 |
|---|---|
| `JSON.parse / Gson.fromJson` | 流式解析 / Protobuf（§6.1.3） |
| `Bitmap.decodeStream` | 异步预解码 + 缓存（§6.1.2） |
| `Pattern.compile` 重复调用 | 正则预编译（§6.1.4） |
| `getDeclaredMethod` 反射 | 反射缓存（§6.1.4） |
| `String.format` / 拼接 | StringBuilder / 缓存 |

**A2 系统调用密集的典型形态**：频繁小 `read/write`、频繁 `mmap/munmap`、重复 `clock_gettime`、`futex` 风暴（锁竞争）、`binder_transact` 风暴（IPC 密集）。治理思路统一：**批量化、缓存、合并请求**。

### 5.3 路径 B：利用率低却卡（off-CPU，最容易漏诊）

```text
CPU% < 30% 但用户报卡
  ├─ Run Queue 高 + iowait 高？ → IO 瓶颈，看磁盘/网络（篇04 / 篇08）
  ├─ Run Queue 高 + iowait 低？ → 锁竞争，看 sched_switch / 等待链（篇03）
  └─ Run Queue 低？            → 被高优先级抢占 / cgroup 限流 / 被按到小核
```

**典型场景**：主线程等子线程的锁；主线程同步等 Binder 远端；后台被 cgroup 限配额；热限制被迁小核。

> **口诀：CPU 低但卡，不要看 CPU，看队列和等待。** 走错这条路的优化 = 礼物墙经验派的前两周。

### 5.4 路径 A 深水区：IPC 与缓存归因

```text
CPU 100%，但慢
  ├─ IPC > 2   → 健康，砍指令数
  ├─ IPC 1-2   → 正常，砍指令数
  └─ IPC < 1   → 内存瓶颈：
       ├─ cache-miss 高 → 随机访问（链表/hash 冲突）→ 改布局（§6.2.1）
       ├─ branch-miss 高 → 分支不可预测（数据无序）→ 排序 / 位图（§6.2.3）
       ├─ TLB-miss 高 → 工作集超 TLB 容量
       └─ 伪共享 → 多线程改同缓存行（§6.2.4）
```

### 5.5 案例实战：礼物墙的归因全过程

```text
礼物墙卡顿
  └─ 利用率 95% 持续高 → 路径 A
       └─ user 占比 88% → A1 业务热点
            └─ simpleperf 30s → 火焰图四平顶：
                 layout 计算 28% / 图片主线程解码 22% / 飘字矩阵 17% / 反序列化 15%
       └─ PMU：IPC = 0.7，cache-miss = 27% → 同时命中"内存瓶颈"分支
```

**双路径并存才是真相**：既有指令数过多（代码堆栈深），又有 IPC 过低（数据布局差）。经验派只盯前者，所以 3 周无果。

## 06.如何优化：黄金公式的三条路

### 6.0 先看实验数据：五组量化结论

> 以下数据来自可控微基准（千元机骁龙 695 / Android 12 / 30 次取 P50），量级比绝对值重要。

| # | 实验 | 结论 | 量级 |
|---|---|---|---|
| ① | 大小核耗时差异 | 同代码大核比小核快，**SLO 必须按机型分档** | 4× |
| ② | 上下文切换代价 | 线程数远超核数反而拖慢，**线程池要科学算** | 反向劣化 |
| ③ | 缓存友好布局 | 顺序数组 vs 链表跳跃访问，**布局影响巨大** | 5-15× |
| ④ | 伪共享 | 8 线程争抢同缓存行，并行度从 8 退化到 1.3，**对齐是必修课** | 5.7× |
| ⑤ | 分支预测 | 数据有序 vs 无序，IPC 0.6 → 3.2，**喂给 CPU 可预测的数据** | 5× |

**统一到黄金公式**：

```
程序耗时 = 指令数 / IPC / 频率
            │        │       └─ 实验①：频率差 4×
            │        └─ 实验③④⑤：缓存×一致性×预测共影响 IPC 30×
            └─ §6.1（业界 90% 教程只讲这里）
```

> **隐藏地图：指令数只占 1/3，IPC 是被忽略的另外 2/3**——这就是经验派失败的本质。

### 6.1 第一条路：减少指令数（让 CPU 少做事）

**① 算法降阶（O(n²) → O(n)）**

```kotlin
// ❌ O(n²)
for (gift in newGifts)
    for (existing in giftWall)
        if (existing.id == gift.id) merge(existing, gift)

// ✅ O(n)：哈希索引
val index = giftWall.associateBy { it.id }
for (gift in newGifts) index[gift.id]?.let { merge(it, gift) }
```

边界：n < 100 时常数因子主导，可能反而慢。

**② 异步化（不是降总量，是把总量挪出关键路径）**

```kotlin
// ❌ 主线程同步解码 30ms
override fun onBindViewHolder(h: VH, p: Int) {
    h.icon.setImageBitmap(BitmapFactory.decodeStream(...))
}
// ✅ 异步 + 占位
override fun onBindViewHolder(h: VH, p: Int) {
    h.icon.setImageResource(R.drawable.placeholder)
    decodePool.execute { val b = decode(...); h.icon.post { h.icon.setImageBitmap(b) } }
}
```

判定：任务 > 5ms 且不影响首帧 → 异步；< 1ms 异步反而亏（切换成本 0.4-0.8ms）。

**③ 序列化协议升级（JSON → Protobuf）**：JSON 每字段 200-500 指令（字符串扫描+反射），Protobuf 30-80（二进制 tag-value）。礼物墙反序列化 8μs → 1.5μs。边界：需要 Schema 管理与服务端配合。

**④ 反射 / 正则缓存**：`Pattern.compile`、`Class.forName` 每次百微秒级，重复调用 99% 是浪费。一行改动，高频场景 50-100× 收益——**性价比之王**。

```kotlin
// ❌ 每次编译   // ✅ 类加载时一次
fun isMobile(s: String) =
    Pattern.compile("^1\\d{10}$").matcher(s).matches()
private val MOBILE = Pattern.compile("^1\\d{10}$")
```

### 6.2 第二条路：提高 IPC（让 CPU 干得高效）

**① 数据布局 AoS → SoA**

```text
AoS：[id|name|cnt|ts][id|name|cnt|ts]...   ← 只用 cnt 却整块拉进 cache
SoA：[id,id,..][name,..][cnt,cnt,..][ts,..] ← 只拉 cnt 一段，命中率拉满
```

```kotlin
// ✅ 分析型计算用 SoA
class GiftColumn(val ids: LongArray, val counts: IntArray, ...)
giftColumn.counts.sum()   // 只拉 4 字节 × N
```

礼物墙此项单独贡献 IPC 0.7 → 1.4。边界：随机单条访问场景 SoA 反而慢。

**② SIMD / NEON 向量化**

```cpp
// ❌ 标量   // ✅ NEON 一次 4 个 float
for (i…) c[i]=a[i]+b[i];
for (int i = 0; i < n; i += 4)
    vst1q_f32(c+i, vaddq_f32(vld1q_f32(a+i), vld1q_f32(b+i)));
```

飘字矩阵变换 NEON 化后 -65% CPU。边界：编译器自动向量化已覆盖简单循环，只有确认的热点才手写。

**③ 减少分支（branch-less）**：分支预测失败罚 13-20 周期。把热点循环里的 if 改算术（`coerceIn`、位运算取绝对值），或**先排序让数据走向可预测**（实验⑤）。

**④ 伪共享治理（缓存行对齐）**

```java
// ❌ 两个计数器挤在同一 cache line，多核互相踢
class Counters { long countA; long countB; }
// ✅ JDK8+ 自动 64 字节隔离；高并发计数直接用分段设计
@sun.misc.Contended long countA;  @sun.misc.Contended long countB;
// ✅✅ 或直接 LongAdder（内部分段，比 AtomicLong 快 5-10×）
```

### 6.3 第三条路：频率与调度（让 CPU 跑得更快）

**① 关键路径绑大核**

```kotlin
Process.setThreadPriority(Process.THREAD_PRIORITY_DISPLAY)  // 提优先级影响选核
```

礼物墙关键路径绑大核后单帧 -28%。边界：耗电 +2-5%，**只在关键期用，结束恢复**；注意热降频会没收你的大核。

**② race-to-idle**：能耗 ≈ 频率³，"3GHz 跑 100ms + 睡 900ms" 比 "1GHz 跑 1000ms" 省电 35%。后台任务**集中跑完让 CPU 睡**，别摊在一小时里。

**③ 线程池科学化**（实验②的落地）：

```kotlin
// ❌ 无界池 Executors.newCachedThreadPool()
// ✅ CPU 密集 = 物理核数；IO 密集 = 核数 × (1 + 等待/CPU)
val cpuPool = Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors())
// ✅✅ 协程（用户态调度，切换开销 ~1/100）
launch(Dispatchers.Default) { /* CPU 密集 */ }
```

**④ 锁 → 原子 → 无锁**：锁竞争 = 上下文切换 + cache invalidation。计数用 `LongAdder`，队列用 `ConcurrentLinkedQueue`。边界：CAS 高竞争下自旋退化，极重竞争反而不如锁。

### 6.4 ROI 排序：先做哪件事

```
ROI = (P95 改善 × 影响用户比例) / (开发成本 × 风险 × 可读性损失)
```

| 优先级 | 操作 | 收益区间 | 成本 |
|---|---|---|---|
| **P0** | 主线程 IO 异步化 | 50-200% | 低 |
| **P0** | 反射/正则缓存 | 50-100× | 一行 |
| **P1** | 算法降阶 | 10-100× | 中 |
| **P1** | 数据布局（SoA/对齐） | 2-15× | 中 |
| P2 | JSON → Protobuf | 3-10× | 高（需协同） |
| P2 | 线程池 / 协程化 | 1.5-3× | 低 |
| P3 | SIMD / branch-less | 2-5× | 高 |
| P3 | 绑核 / QoS | 1.5-4× | 低但耗电 |

> **铁律：P0/P1 没做完之前，P2/P3 是过度优化。**

**礼物墙的实际执行栈**（按 ROI 顺序）：

| 阶段 | 操作 | 单步收益 | 累计 FPS |
|---|---|---|---|
| 起点 | — | — | 12 |
| Day1 | 图片解码异步化 | -22% 主线程 | 22 |
| Day1 | LongAdder 替 AtomicLong | -8% CPU | 28 |
| Day2 | GiftItem AoS → SoA | IPC 0.7→1.4 | 38 |
