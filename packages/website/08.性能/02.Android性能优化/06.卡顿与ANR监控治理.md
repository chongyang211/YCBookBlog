## 01.开篇灵魂拷问

读文章前，先问自己三个问题。答得上来，说明你已理解；答不上来，就是本文的学习目标。

### 1.1 复现之惑

**Q：用户报"卡死"，但开发机怎么试都好的，到底怎么找根因？**

**🤔 疑惑**：传统 Bug 可以本地重现 → 调试 → 修复，为什么卡顿/ANR 偏偏在开发机复现不出来？

**💡 解答**：**卡顿是线上现象，不是线下 Bug**。它的根因往往是"**用户设备状态**"（低端机颗粒劣化、系统压力大、后台应用竞争 CPU/IO、冷热机差异、运行时数据规模差异……），这些状态组合在开发机上是零概率事件。开发机能复现的叫"性能缺陷"，开发机复现不了的才叫"**卡顿问题**"——必须靠**线上数据采集**，不是本地调试。

> **心法**：**卡顿必须"先采集再归因"**，不是"先调试再采集"——这个顺序颠倒了，就是贯穿案例 3 周失败的根因。

### 1.2 栈顶之惑

**Q：ANR 发生时抓到的 `/data/anr/traces.txt`，主线程栈顶 70% 是 `nativePollOnce`，30% 是 `Object.wait`——"主线程都在等消息，怎么会 ANR"？**

**🤔 疑惑**：既然主线程栈显示它"在等消息"，就说明它"空闲"，为什么系统还判定它 ANR？

**💡 解答**：**ANR 快照只是"5s 兜底时刻的瞬时相"，不是"5s 内发生过什么的录像"**。真实现场是——主线程在前 4.8s 可能被 DB 锁等待卡住，第 4.9s 终于拿到锁、处理完消息、刚进入下一轮 pollOnce 等消息，第 5s 系统兜底抓栈——于是看到的是"在等消息"的平静画面，但案发现场早已过去。更关键的是——**70% 的 ANR 是 off-CPU 类**，主线程栈是"**无辜的旁观者**"，真因在**其他线程持锁或其他进程 Binder 慢响应**。

> **心法**：**只看主线程栈是经验派陷阱**。方法派必抓"**所有线程栈 + Binder 远端栈**"——真凶不在主线程栈顶，而在"**谁让主线程等**"的那个线程/进程里。

### 1.3 阈值之惑

**Q：ANR 系统阈值是 5s，那我们的 WatchDog 监控阈值设多少合适？是不是越小越精准？**

**🤔 疑惑**：直觉上监控阈值越小越能提前抓到问题，但阈值 500ms 会不会误报爆仓？

**💡 解答**：**WatchDog 阈值的核心逻辑是"比系统快一步"**——系统 5s 才兜底，我们 **2s 就要抓准 ANR 现场**。阈值不是"越小越好"，是"**系统兜底时刻之前的最后观察窗**"。常用阈值矩阵：
- **500ms**：捕获"明显卡顿"用于用户体验告警（不作 ANR 预警）；
- **2s**：**准 ANR 阈值**，与真实 ANR 根因 90% 同构，是治理的黄金阈值；
- **4s**：**兜底抓栈**，确保在系统 5s 判定前拿到现场；
- **≥5s**：**系统已接管**，WatchDog 失去意义。

> **心法**：**阈值不是精度参数，是"抢在系统之前"的战术窗口**——2s 阈值 + 多线程栈 + Binder 栈 = 完整现场。贯穿案例的方法派 Day 2 就是靠 WatchDog(2s) + 全栈 6 小时抓到 1240 次准 ANR，拨开了"nativePollOnce 迷雾"。

## 02.探索问题本质

### 2.1 卡顿与ANR的关系

**核心命题**：**卡顿和 ANR 不是两个问题，是同一问题的两种程度**——都是"**主线程被阻塞**"，差别只在时长。

```
   主线程响应延迟（用户感知）：
   
   < 100 ms     无感（流畅）
   100-500 ms   轻微卡顿（可感知）
   500 ms-2 s   明显卡顿（用户抱怨）
   2-5 s       严重卡顿（用户以为"崩了"）
   ≥ 5 s       ★ 系统判定 ANR（兜底惩罚）
```

**两者的工程关系**：

| 维度 | 卡顿 | ANR |
|---|---|---|
| **定义者** | 用户感知 / APM | 系统 OS |
| **阈值** | ≥ 16.67ms（丢帧）或 ≥ 100ms（可感） | 5s（输入）/ 20s（Service）/ 10s（Broadcast） |
| **处理方** | 应用层优化 | 系统弹框 / 杀进程 |
| **可控性** | 可控（代码优化） | 不可控（系统判定） |
| **发生频率** | 高（日常） | 低（极端） |
| **治理关系** | **治 ANR 的前提是治卡顿** | **ANR 是卡顿的兜底惩罚** |

> **心法**：**治理 ANR 没有银弹，只有"**让卡顿永远走不到 5s**"**——减负（治根）+ WatchDog（预警）+ 兜底（逃生）三位一体。

### 2.2 现象分类

**卡顿与 ANR 的典型现象四大类**：

| 现象 | 典型场景 | 底层根因 | 对应章节 |
|---|---|---|---|
| **交互延迟** | 点击按钮无响应 | 主线程 CPU/IO 阻塞 | §3.1 §5.1 |
| **渲染掉帧** | 列表滑动顿挫 | 单帧 > 16.67ms | §3.1 §5.1 |
| **冻帧** | 界面"冻住"几秒 | 主线程大段任务 | §3.1 §5.2 |
| **ANR / Hang** | 系统弹框 / 杀进程 | 卡顿累积超系统阈值 | §3.2 §5.2 §5.5 |

**跨平台等价映射**：

| 平台 | 卡顿术语 | ANR 等价 | 阈值 |
|---|---|---|---|
| Android | Jank / Frozen Frame | ANR | 5s/20s/10s |
| iOS | Hang | Watchdog | 启动 20s / 后台 30s |
| Web | Long Task | 页面无响应提示 | 50ms Long Task / 10-30s 冻结 |
| 嵌入式 | 看门狗预警 | 看门狗复位 | 厂商定（通常几秒） |

### 2.3 阻塞三态模型

把主线程 16.67ms 预算的使用分成**三态**，不同态对应不同治理方法：

```
   卡顿的物理来源 = 主线程在 16.67ms 预算内被迫等待 / 多算 / 算错
   
   ┌────────────────────────────────────────────────────┐
   │  A. on-CPU 卡顿（在烧 CPU）                         │
   │     物理本质：单位时间内指令数超过帧预算                │
   │     特征：CPU 100%，热点函数明显                     │
   │     例子：JSON 解析、Bitmap 解码、复杂 Layout        │
   │     治法：§5.1 主线程减负（§6.1 Looper 原理）         │
   ├────────────────────────────────────────────────────┤
   │  B. off-CPU 卡顿（在等）                            │
   │     物理本质：CPU 没忙，但主线程被切出 CPU 等外部       │
   │     特征：CPU 不高，但帧没产出                       │
   │     例子：IO Wait、锁等待、Binder/IPC 阻塞、GC STW   │
   │     治法：§5.2 跨线程协同（§6.9 Binder 阻塞原理）     │
   ├────────────────────────────────────────────────────┤
   │  C. 系统级抢占（不在 CPU 上，但不是它的错）             │
   │     物理本质：主线程被系统调度器切走                   │
   │     特征：跨进程抢占、低端机电量不足触发降频            │
   │     例子：system_server 繁忙、SurfaceFlinger 慢      │
   │     治法：§5.4 组件合规 + §5.5 ANR 兜底              │
   └────────────────────────────────────────────────────┘
```

**三态占比**（头部 App 线上统计）：

| 态 | 占卡顿比例 | 占 ANR 比例 | 治理难度 |
|---|---|---|---|
| A on-CPU | 30% | 15% | 低（profiler 直接定位） |
| **B off-CPU** | **55%** | **70%** | **高（跨线程/进程归因）** |
| C 系统级 | 15% | 15% | 极高（无法根治，只能兜底） |

> ▶▶ **回扣贯穿案例**：电商大促 ANR 的 Day 3 分析——42% DB 锁竞争 + 28% Binder 远程慢 + 18% HTTP 连接池 + 12% SDK 串行 = **88% off-CPU 类**。经验派 3 周错在"只看主线程栈"（栈顶 70% nativePollOnce），完全没看 off-CPU 真因。

### 2.4 ANR触发四大类

**ANR 的四大触发路径**（任一成立即触发）：

```
   ┌────────────────────────────────────────────────┐
   │ A. 输入事件 ANR（最常见，90%+）                   │
   │    InputDispatcher 5s 内未收到应用响应             │
   │    根因：主线程长任务 / IO / 锁 / IPC              │
   │    详见 §6.3 InputDispatcher 全链路               │
   ├────────────────────────────────────────────────┤
   │ B. Service ANR                                 │
   │    前台 Service 20s / 后台 Service 200s          │
   │    根因：Service 回调内同步重任务                   │
   │    详见 §6.4 Service 全链路                       │
   ├────────────────────────────────────────────────┤
   │ C. Broadcast ANR                               │
   │    前台 Broadcast 10s / 后台 60s                 │
   │    根因：BroadcastReceiver.onReceive 内阻塞        │
   │    详见 §6.5 Broadcast 全链路                     │
   ├────────────────────────────────────────────────┤
   │ D. ContentProvider ANR                         │
   │    发布 10s / query 内长任务                      │
   │    根因：CP.onCreate 内重任务 / query 慢           │
   │    详见 §6.6 ContentProvider 全链路               │
   └────────────────────────────────────────────────┘
```

**跨平台对应**：

| 平台 | 对应"ANR" | 触发条件 | 阈值 |
|---|---|---|---|
| Android | ANR 四大类 | 事件队列超时 | 5s/20s/10s/200s |
| iOS 启动 | Launch Watchdog | 启动流程未完成 | 20s |
| iOS 后台 | Background Watchdog | 前后台切换未完成 | 30s |
| Web | 页面无响应 | 事件循环长时间阻塞 | 10-30s（浏览器定） |
| 嵌入式 | 硬件看门狗 | 应用未喂狗 | 厂商定 |

**反直觉事实**：**不同类型 ANR 的根因往往完全不同**——Input ANR 多是"主线程卡顿"，Service ANR 多是"同步重任务"，Broadcast ANR 多是"onReceive 内阻塞"，CP ANR 多是"onCreate 串行"。治理必须按类型分开。

### 2.5 面试锚点

**Q：卡顿和 ANR 到底是什么关系？为什么说"治 ANR 的前提是治卡顿"？**

**答题模板**（关系 + 三态模型 + 治理方法论）：

> 卡顿和 ANR 不是两个问题，是**同一问题的两种程度**——都是"**主线程被阻塞**"，差别只在时长：
>
> - **卡顿**：主线程阻塞 100ms-5s，用户感知"顿一下"，APM 定义；
> - **ANR**：主线程阻塞 ≥ 5s，系统兜底惩罚（弹框/杀进程）；
> - **过渡关系**：所有 ANR 都是先"卡顿"再"累积超阈值"演化而来——**ANR 是卡顿的极端形态**。
>
> **为什么治 ANR 必须先治卡顿**：
>
> **① 阻塞三态模型**：卡顿的物理根因只有 A/B/C 三类（on-CPU/off-CPU/系统级），**ANR 的根因也是这三类，只是时间更长**。治理手段同构——治卡顿等于治 ANR 的前兆。
>
> **② 实证数据**：头部 App 统计，**70% 的 ANR 是 off-CPU 类**（主线程在等别人），这类 ANR 的本质就是"**跨线程/跨进程卡顿**"的延续。治 off-CPU 卡顿（锁治理/Binder 治理/异步化），ANR 率自然下降。
>
> **③ 工程落地**：方法派的核心手段是"**WatchDog 2s 阈值提前抓准 ANR**"——**用治卡顿的工具（LooperPrinter + WatchDog）治 ANR**，比系统 5s 兜底早 3 秒拿到现场。
>
> **一句话总结**：**ANR 不是独立问题，是卡顿不断累积失控的结果**——所以治 ANR 的三板斧是：减负（治根因卡顿）+ WatchDog（预警累积）+ 兜底（最后逃生）。

## 03.排查归因方法

### 3.1 卡顿归因决策树

卡顿归因必走的**五问决策树**：

```
   卡顿现象（单帧 > 16.67ms 或冻帧 > 700ms）
      │
      ├─【第一问】发生在哪个线程？
      │     ├─ 主线程 → ★ 核心矛盾，必治
      │     └─ 子线程 → 跨线程锁/等待，看是否反压主线程
      │
      ├─【第二问】CPU 占用高吗？
      │     ├─ 高（> 60%）→ ★ A 类 on-CPU 卡顿
      │     │     │
      │     │     ├─ 是业务代码热点吗？
      │     │     │     ├─ 是 → §5.1 异步化 / 算法优化
      │     │     │     └─ 否（系统 Binder/GC）→ §5.2 组件合规
      │     │     └─ 看火焰图栈顶
      │     │
      │     └─ 低（< 30%）→ ★ B 类 off-CPU 卡顿
      │              │
      │              ├─【第三问】主线程在等什么？
      │              │     ├─ IO（syscall read/write/fsync）→ §5.1 异步IO
      │              │     ├─ 锁（Object.wait/synchronized）→ §5.2 锁治理
      │              │     ├─ Binder（Binder.transact）→ §5.2 IPC 治理
      │              │     ├─ GC（art::gc::...）→ §5.1 内存治理（见§02内存篇）
      │              │     └─ nativePollOnce → ★ 伪装！真凶在其他线程/进程
      │              │
      │              └─【第四问】是哪个"持方"卡？
      │                    ├─ 持锁线程 → 抓全线程栈
      │                    ├─ Binder 远端 → 抓 remote peer trace
      │                    └─ 跨进程 → 看 system_server 繁忙度
      │
      └─【第五问】如何验证？
            ├─ 复现路径 → 走 §5.0 实验组
            └─ 不可复现 → 线上 WatchDog + 全栈采集
```

> **关键原则**：**五问必走，不能跳步**——跳过"主线程？"就可能把子线程 IO 当主要矛盾，跳过"CPU 高吗？"就可能把 off-CPU 问题误诊成 on-CPU。

### 3.2 ANR归因决策树

**ANR 归因的"三步法"**——从"**哪类 ANR**"倒推"**哪条路径**"：

```
   ANR 事件（traces.txt 产生 / Vitals 上报）
      │
      ├─【第一步】ANR 类型？看 anr_subject
      │     ├─ Input ANR（90%+）→ 走 §6.3 InputDispatcher 链路
      │     ├─ Service ANR → 走 §6.4 Service 链路
      │     ├─ Broadcast ANR → 走 §6.5 Broadcast 链路
      │     └─ ContentProvider ANR → 走 §6.6 CP 链路
      │
      ├─【第二步】主线程栈顶看什么？
      │     ├─ 业务代码 → §5.1 直接定位异步化
      │     ├─ nativePollOnce / Object.wait → ★ 伪装，看其他线程
      │     ├─ Binder.transact → §5.2 查远端 service
      │     ├─ art::gc → §5.1 内存治理
      │     └─ syscall（read/write/futex）→ off-CPU 类
      │
      └─【第三步】归因到持方
            ├─ 查所有线程栈（SIGQUIT trace）
            ├─ 查 Binder 远端栈（systrace / Perfetto）
            ├─ 查 CPU 占用（traces.txt 的 "CPU usage" 段）
            └─ 查 GC 日志（logcat art 标签）
```

**▶▶ 关键认知**：**ANR 栈顶常常是无辜的**——`nativePollOnce` 只是说明"**抓栈时主线程空闲**"，不代表"**5s 内都空闲**"。真凶藏在：
1. **其他线程的栈**（持锁的 DB 写入线程、HTTP 下载线程）；
2. **Binder 远端栈**（system_server、其他 App 进程）；
3. **GC 日志**（concurrent copying GC 阶段的 STW）；
4. **CPU 高占用**（其他进程抢 CPU，低端机大促场景常见）。

### 3.3 四模式归因矩阵

贯穿案例分析的 1240 次准 ANR 现场归纳出**四大归因模式**：

| 模式 | 占比 | 主线程栈顶（看起来） | 真因（本质） | 治理 |
|---|---|---|---|---|
| **A: DB 锁竞争** | 42% | `nativePollOnce` | DB 写入线程持 SQLite 写锁 + 网络下载 | §5.2 锁治理：读写锁分离、WAL |
| **B: Binder 远程慢** | 28% | `Binder.transact` | system_server 大促时变慢 | §5.2 Binder 治理：加超时+重试 |
| **C: HTTP 连接池等** | 18% | `Object.wait` | OkHttp 单连接池排队 | §5.2 连接池上限 5→32 |
| **D: 启动 SDK 串行** | 12% | 业务方法栈 | 推送/统计/支付 SDK 同步 init | §5.1 App Startup 异步化 |

**模式识别的工程意义**：

1. **70% 是 off-CPU 类**（A+B+C）——印证"**栈顶之惑**"心法；
2. **栈顶与真因往往错位**——A/C 的真因在其他线程，B 的真因在其他进程；
3. **治理手段按模式分开**——没有通用银弹，必须按模式对症下药。

> ▶▶ **回扣贯穿案例**：方法派 Day 3 的四模式归纳是整个闭环的"**认知跃迁点**"——从"看主线程栈"升级到"**按模式反向定位真因**"。这是经验派永远跨不过的那道坎。

### 3.5 面试锚点

**Q：线上出现大量 ANR 但 traces.txt 栈顶都是 nativePollOnce，你怎么定位真因？**

**答题模板**（栈顶陷阱 + 三步法 + 全栈采集 + 四模式）：

> `nativePollOnce` 栈顶是**典型的归因陷阱**——它只是说明"**抓栈时主线程空闲在等消息**"，不代表"**5s 内一直空闲**"。真实现场往往是：主线程前 4.8s 被 off-CPU 操作卡住（持锁/Binder/IO），4.9s 刚处理完消息进入下一轮 pollOnce，第 5s 系统兜底抓栈——"案发现场早已过去"。
>
> 我按**三步法**定位：
>
> **① 不信栈顶，上 WatchDog**：系统 5s 才兜底，我上 **WatchDog 2s 阈值**提前抓现场，比系统快 3s 拿到"案发瞬间"的完整线程栈。
>
> **② 抓全栈 + Binder 远端**：**不仅抓主线程栈**，还抓**所有线程栈**（找持锁线程）+ **Binder 远端栈**（找慢响应的 service）+ **GC 日志**（找 STW 时段）。
>
> **③ 按四模式反向定位**：栈顶 `nativePollOnce` 的真因通常是以下四模式之一——**A: DB 锁竞争**（看其他线程持锁情况）、**B: Binder 远程慢**（看 system_server CPU）、**C: 连接池等**（看 Object.wait + 持方信息）、**D: SDK 串行**（看启动期总耗时）。
>
> **贯穿案例实证**：大促 1240 次准 ANR，栈顶 70% nativePollOnce，但按四模式归因后——**42% DB 锁 + 28% Binder + 18% HTTP + 12% SDK = 70% off-CPU 类**。经验派 3 周错在"信栈顶"，方法派 Day 3 一天搞定归因，就靠**不信栈顶 + 全栈采集 + 四模式反推**三招。
>
> **一句话总结**：**栈顶是果，真因是因**——ANR 归因的本质是"**从卡住的瞬间倒推被谁卡住**"，这需要全栈 + 远端 + 分类思维，缺一不可。

## 04.监控体系设计

### 4.1 采集三方案

卡顿与 ANR 监控的核心矛盾是"**覆盖度 vs 开销**"——想抓完整现场就得抓全栈，一抓全栈就 CPU 开销 5-10%。所以永远**三方案组合**：

```
   ┌──────────────────────────────────────────┐
   │ ① LooperPrinter（消息级监控）              │  覆盖 95%  开销低   无原生 ANR
   ├──────────────────────────────────────────┤
   │ ② WatchDog（线程 heartbeat）              │  覆盖 100% 开销中   抓准 ANR
   ├──────────────────────────────────────────┤
   │ ③ 系统 ANR 回调 + traces.txt              │  覆盖 100% 开销零   仅官方 ANR
   └──────────────────────────────────────────┘
```

**① LooperPrinter 方案**

```kotlin
Looper.getMainLooper().setMessageLogging { log ->
    if (log.startsWith(">>>>> Dispatching")) {
        // 消息开始
        startTime = SystemClock.elapsedRealtimeNanos()
    } else if (log.startsWith("<<<<< Finished")) {
        // 消息结束
        val durMs = (SystemClock.elapsedRealtimeNanos() - startTime) / 1_000_000
        if (durMs > THRESHOLD) {
            reportBlock(durMs, mainThreadStackTrace())
        }
    }
}
```

**覆盖范围**：所有通过 Handler/Message 调度的任务——**约 95% 的主线程卡顿**。
**盲区**：Vsync 回调内部的 Choreographer doFrame、JNI 调用、系统注入事件。
**开销**：每条消息 2 次字符串处理 + 栈抓取。生产环境 1% 采样可忽略。

**② WatchDog 方案**（代表作：ANR-WatchDog）

```kotlin
class ANRWatchDog(private val timeoutMs: Long = 2000) : Thread() {
    @Volatile private var tick = 0L
    
    private val heartbeatRunnable = Runnable { tick++ }
    
    override fun run() {
        val handler = Handler(Looper.getMainLooper())
        while (!isInterrupted) {
            val prevTick = tick
            handler.post(heartbeatRunnable)
            Thread.sleep(timeoutMs)
            if (tick == prevTick) {
                // 主线程 timeoutMs 内未响应
                reportANR(mainThreadStackTrace(), allThreadStackTraces())
            }
        }
    }
}
```

**覆盖范围**：所有主线程阻塞——**100% 覆盖**（包括 Vsync 内卡顿）。
**优势**：抓到的现场是"**系统兜底之前的真实瞬间**"，归因最准。
**开销**：子线程 + 定时 post，内存无感，CPU < 0.5%。

**③ 系统 ANR 回调**

```kotlin
// Android 11+
val service = getSystemService(ActivityManager::class.java)
service.registerProcessStateCallback(...)

// 或读取 /data/anr/traces.txt
// 或监听 ApplicationExitInfo（API 30+）
val exitInfos = activityManager.getHistoricalProcessExitReasons(packageName, 0, 10)
exitInfos.filter { it.reason == REASON_ANR }.forEach { report(it.traceInputStream) }
```

**覆盖范围**：仅系统判定的 ANR（0.1% 以下）。
**优势**：权威、含完整系统信息。
**局限**：**无法预防**——系统已经杀进程了才能看到。

**三方案组合策略**：
- **开发期**：LooperPrinter 500ms 阈值 + penaltyLog（本地日志）
- **线上默认**：WatchDog 2s 阈值 + 1% 用户采样 + 全栈上报
- **兜底**：ApplicationExitInfo 持续读取历史 ANR

### 4.2 ANR捕获原理

**Android ANR 的捕获链路**（深度揭秘）：

```
   ① 事件进入 InputDispatcher 队列
       ↓
   ② InputDispatcher 等待应用响应（最多 5s）
       ↓ 超时
   ③ system_server 向目标进程发 SIGQUIT 信号
       ↓
   ④ 应用进程的 signal_catcher 线程捕获 SIGQUIT
       ↓
   ⑤ art::DumpForSigQuit → 遍历所有线程 → 写入 /data/anr/traces.txt
       ↓
   ⑥ system_server 读取 traces → 弹"应用无响应"弹框
       ↓
   ⑦ 用户选择"关闭" or 系统静默杀进程（Android 11+）
```

**三个关键机制**：

**机制一：SIGQUIT 信号驱动**
- 系统通过 Linux 信号机制通知应用"你 ANR 了"；
- 应用 signal_catcher 线程是 ART 预埋的"**后门**"——哪怕主线程完全卡死，signal_catcher 仍能响应（它是独立内核调度）；
- 这是为什么 **traces.txt 永远能生成**，不管主线程多卡。

**机制二：所有线程栈快照**
- traces.txt 不只有主线程栈，**包含所有 Java/Native 线程栈**；
- 还包含 CPU 占用、锁持有信息、GC 状态；
- **真因线索往往在这些辅助信息里**，不在主线程栈。

**机制三：Binder 远端栈的奥秘**
- 如果主线程卡在 `Binder.transact`，traces.txt 只记录了"**本地卡**"，不记录"**远端为什么慢**"；
- 需要配合 **systrace / Perfetto** 看跨进程的 Binder 调用链；
- Android 10+ 的 anr_trace 增强版可以包含 remote peer trace。

### 4.3 WatchDog前兆监控

**WatchDog 不是检测 ANR 本身，是检测"**ANR 之前的卡顿**"**——这是预防性监控的核心哲学。

**▶▶ 阈值矩阵**（分场景差异化）：

| 场景 | 阈值 | 目的 | 采样率 |
|---|---|---|---|
| 普通交互 | 2s | 准 ANR 预警，归因主力 | 10% |
| 启动期 | 1s | 启动卡顿捕获 | 100% |
| 后台任务 | 5s | 对齐系统阈值 | 1% |
| 低端机 | 1.5s | 更早预警（低端机 fsync 可能到 500ms） | 20% |

**▶▶ WatchDog 增强三特性**：

```kotlin
class EnhancedWatchDog(private val timeoutMs: Long = 2000) : Thread() {
    
    override fun run() {
        while (!isInterrupted) {
            val prevTick = tick
            handler.post(heartbeatRunnable)
            Thread.sleep(timeoutMs)
            if (tick == prevTick) {
                // ① 全线程栈
                val allStacks = Thread.getAllStackTraces()
                // ② CPU 占用（细查哪个线程在烧 CPU）
                val cpuInfo = readProcStat()
                // ③ Binder 繁忙度（看 system_server）
                val binderInfo = readBinderTransactions()
                
                reportANR(allStacks, cpuInfo, binderInfo)
            }
        }
    }
}
```

**三特性对比**：

| 特性 | 作用 | 定位场景 |
|---|---|---|
| **① 全线程栈** | 找持锁线程、慢任务线程 | §3.3 模式 A/C（DB 锁、HTTP 池） |
| **② CPU 占用** | 识别哪个线程在烧 CPU | §3.3 模式 D 启动 SDK |
| **③ Binder 繁忙度** | 看 system_server 是否被打爆 | §3.3 模式 B Binder 慢 |

### 4.6 面试锚点

**Q：线上 ANR 监控怎么做？LooperPrinter / WatchDog / 系统回调三种方案怎么选？**

**答题模板**（三方案组合 + 覆盖率 vs 开销 + 阈值矩阵）：

> ANR 监控的核心矛盾是"**覆盖度 vs 开销**"——没有任何单一方案是完美的，必须**三方案组合**：
>
> **① LooperPrinter（消息级监控）**：覆盖 **95% 主线程卡顿**，开销极低。开启简单，一行 setMessageLogging 搞定。盲区是 Vsync 回调内卡顿、JNI 调用。**适合开发期 + 线上日常监控**。
>
> **② WatchDog（线程 heartbeat）**：覆盖 **100% 卡顿**，含 Vsync 内。能抓到"**系统兜底之前的瞬间**"，归因准确度最高。CPU 开销 < 0.5%。**是线上准 ANR 预警的主力**。
>
> **③ 系统 ANR 回调**：覆盖官方 ANR，权威但滞后——**系统杀进程了才能看**。用 ApplicationExitInfo (API 30+) 读历史 ANR + traces.txt。**作兜底使用**。
>
> **阈值矩阵**：
> - 开发期 LooperPrinter 500ms（抓明显卡顿）；
> - 线上 WatchDog **2s**（准 ANR 阈值，与真 ANR 根因 90% 同构，比系统 5s 早 3s）；
> - 启动期 WatchDog 收紧到 1s（启动期对卡顿更敏感）；
> - 低端机收紧到 1.5s（设备差异大）。
>
> **全栈采集三特性**（WatchDog 必配）：
> - **全线程栈**（找持锁线程）；
> - **CPU 占用**（识别烧 CPU 的线程）；
> - **Binder 繁忙度**（看 system_server）。
>
> **贯穿案例实证**：电商大促上线 WatchDog(2s) + 全栈采集，6 小时抓到 1240 次准 ANR，Day 3 完成四模式归因，Day 4-5 治理落地——整个闭环靠的就是"**比系统快一步**"的监控设计。
>
> **一句话总结**：**ANR 监控不是等 ANR，是预防 ANR**——三方案组合 + 2s 阈值 + 全栈采集，就是线上 ANR 治理的"**雷达三件套**"。

## 05.分层治理优化

### 5.0 四组量化实验

**本节是治理动作的"**求证基石**"**。每个治理方案背后都对应一组实验数据，没有数据的优化就是凭直觉乱改。

**实验一：主线程 IO 的 ANR 代价**

| 场景 | 单次 IO 耗时 | 累积 100 次主线程耗时 | ANR 概率 |
|---|---|---|---|
| 高端机 SP.commit | 5ms | 500ms | 0.01% |
| 中端机 SP.commit | 15ms | 1.5s | 0.3% |
| 低端机 SP.commit | 50ms | 5s | **3.2%** |
| 低端机 SP.commit + 大促系统压力 | 150ms | **15s** | **28%** |

**启示**：**同一代码在低端机 + 系统压力下 ANR 率可以放大 2800×**。主线程 IO 必须零容忍。

**实验二：锁等待的 ANR 转化率**

| 子线程持锁时长 | 主线程等锁次数 | 卡顿率 | ANR 率 |
|---|---|---|---|
| 100ms | 10 次/秒 | 1% | 0.01% |
| 500ms | 5 次/秒 | 8% | 0.1% |
| 1s | 2 次/秒 | 25% | 0.5% |
| **3s** | 1 次/秒 | **80%** | **5%** |

**启示**：**子线程持锁 ≥ 1s 时 ANR 率飙升**。锁治理必须 P0 优先。

**实验三：Binder 调用超时策略**

| 策略 | Binder 慢调用 ANR 率 | 功能可用性 |
|---|---|---|
| 无超时（阻塞等待） | 2.3% | 100% |
| 超时 2s（抛异常） | 0.15% | 95%（5% 功能失败） |
| 超时 2s + 重试 1 次 | 0.08% | 99% |
| 超时 500ms + 降级（本地缓存） | 0.03% | 100% |

**启示**：**Binder 必须加超时 + 降级**，没有兜底的 Binder 调用就是定时炸弹。

**实验四：WatchDog 阈值敏感度**

| 阈值 | 捕获率 | 误报率 | 推荐场景 |
|---|---|---|---|
| 500ms | 100% | 15%（误报爆仓） | 开发期 |
| 1s | 99% | 3% | 启动期线上 |
| **2s** | **90%** | **0.3%** | **日常线上主力** |
| 3s | 60% | 0.1% | 保守场景 |
| 5s | 20% | 0% | 等于不监控 |

**启示**：**2s 是"捕获率×准确率"的最优点**——比系统 5s 早 3s，比 1s 误报率低 10 倍。

**四大实验启示合集**：

```
   主线程 IO → 低端机+大促放大 2800×        ─┐
   锁等待 → ≥1s 子线程持锁 ANR 率飙升         │
   Binder 调用 → 必须超时+降级，否则 2.3%     ├─▶ ANR 治理 = 减负 + 协同 + 监控 + 兜底
   WatchDog → 2s 阈值是黄金平衡点             ─┘
```

> **心法**：**治理顺序 = 实验顺序**——先治主线程 IO/CPU（实验一）→ 再治子线程锁（实验二）→ 再治 Binder（实验三）→ 最后上 WatchDog 监控（实验四）。顺序错了就是贯穿案例"3 周翻车"。

### 5.1 一层主线程减负

**核心命题**：**主线程零阻塞**——A 类 on-CPU 卡顿 + 自身 IO/GC 问题，这一层"**0 容忍**"是基础。

**5.1.2 App Startup 异步 init**

**5.1.4 启动期任务三原则**

### 5.2 二层跨线程协同

**核心命题**：**解决 off-CPU 类卡顿**——锁治理、Binder 治理、异步化。

**5.2.1 锁治理四招**

**招一：synchronized 粒度细化**

```kotlin
// ❌ 反例：粗粒度锁
class SessionCache {
    @Synchronized fun get(id: String): Session? { ... }
    @Synchronized fun put(id: String, s: Session) { ... }  // 和 get 互斥
}

// ✅ 正例：读写锁分离

    private val lock = ReentrantReadWriteLock()
    fun get(id: String): Session? = lock.read { ... }
    fun put(id: String, s: Session) = lock.write { ... }
}
```

**招二：SQLite WAL 模式**


**招三：避免主线程持锁等待**

```kotlin
// ✅ 正例：异步 + 回调
```

**招四：ConcurrentHashMap / CopyOnWriteArrayList**

**5.2.2 Binder 治理三原则**

**原则一：所有 Binder 调用加超时**

```kotlin

// ✅ 正例：异步 + 超时
val info = withTimeoutOrNull(2000) {
    withContext(Dispatchers.IO) { packageManager.getPackageInfo(pkg, 0) }
} ?: fallbackLocalCache()
```

**原则二：缓存 Binder 结果**

```kotlin
object PackageInfoCache {
    private val cache = ConcurrentHashMap<String, PackageInfo>()
    fun get(pkg: String): PackageInfo = cache.getOrPut(pkg) {
        try { packageManager.getPackageInfo(pkg, 0) } 
        catch (e: Exception) { getLastKnownGood(pkg) }
    }
}
```

**原则三：敏感 Binder 批量化**

```kotlin
// ❌ 反例：N 次 Binder 调用
contacts.forEach { pm.getPackageInfo(it, 0) }  // N 次 IPC

// ✅ 正例：一次批量
pm.getInstalledPackages(0)  // 一次 IPC
```

**5.2.3 连接池上限优化**

```kotlin
// ❌ 反例：OkHttp 默认连接池 5 个

// ✅ 正例：大促场景 32+

    .connectionPool(ConnectionPool(32, 5, TimeUnit.MINUTES))
    .build()
```

**收益**（贯穿案例）：HTTP 排队 ANR 占比 18% → 0%。

**5.2.4 异步 UI 更新**

### 5.4 四层合规组件

**核心命题**：**四大组件（Service/Broadcast/Provider/Activity）必须按 ANR 规则使用**——这是源头治理。

**5.4.1 Service 合规**

```kotlin
// ❌ 反例：onStartCommand 内同步重任务

    doHeavyWork()  // 可能超过 20s → ANR
    return START_STICKY
}

// ✅ 正例：IntentService 或 WorkManager
class HeavyWorker(ctx: Context, params: WorkerParameters) : CoroutineWorker(ctx, params) {
    override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
        doHeavyWork()
        Result.success()
    }
}

// ✅ 正例：显式 startForeground（避免被系统杀）
override fun onStartCommand(...): Int {
    startForeground(ID, buildNotification())
    lifecycleScope.launch { doHeavyWork() }
    return START_STICKY
}
```

**5.4.2 Broadcast 合规**

```kotlin
// ❌ 反例：onReceive 内同步任务
override fun onReceive(ctx: Context, intent: Intent) {
    writeLog(intent)   // 可能 > 10s → ANR
}

// ✅ 正例：goAsync + 异步线程
override fun onReceive(ctx: Context, intent: Intent) {
    val pending = goAsync()
    coroutineScope.launch(Dispatchers.IO) {
        try { writeLog(intent) }
        finally { pending.finish() }
    }
}
```

**5.4.3 ContentProvider 合规**

```kotlin
    return true  // 空实现
}

}
```

**5.4.4 Activity 合规**


### 5.7 启动期专项治理

**启动期是 ANR 的"**高危时段**"**——12% 的 ANR 发生在冷启动期（贯穿案例模式 D）。

```
      ├─ 统计 SDK（首屏显示后 500ms）
      └─ 其他非关键 SDK
   
   【懒加载】条件触发
      ├─ 支付 SDK（进入支付页才 init）
      ├─ 地图 SDK（打开地图页才 init）
      └─ 广告 SDK（广告位展示才 init）
```

> **① 不信栈顶 + WatchDog 2s + 全栈**：traces.txt 栈顶 70% nativePollOnce 是伪装。上线 **WatchDog(2s) + 全线程栈 + Binder 远端栈**，6 小时抓到 1240 次准 ANR 现场。
>
> **② 四模式归因**：Day 3 分析 1240 次现场得出——**42% DB 锁 + 28% Binder 慢 + 18% HTTP 池 + 12% SDK 串行 = 70% off-CPU 类**。印证"主线程栈无辜，真因在其他线程/进程"。
>
> **③ 四层治理落地**：
> - **一层减负**（§5.1）：onCreate 的 450ms SDK init → App Startup DAG 异步，降到 80ms；
> - **二层协同**（§5.2）：SQLite 启用 WAL + 读写锁分离；OkHttp 连接池 5→32；Binder 调用加 2s 超时 + 本地缓存降级；
> - **三层监控**（§5.3）：WatchDog(2s) 固化线上 + 卡顿分级告警 + 连续 3 次 >2s 阻塞自动熔断；
> - **四层组件**（§5.4）：BroadcastReceiver 全部改 `goAsync()` + Service 改 WorkManager + ContentProvider onCreate 空实现。
>
> **④ 防劣化**（§5.6）：加 Lint 规则（主线程 IO/Binder 无超时拦截）+ CI 卡口（冷启动 P99 > 2s 阻断 PR）+ 线上 SLO 告警（ANR 率 > 0.3% 自动熔断）。
>
> **R（结果）**：ANR 率 0.52% → **0.07%**（-86%）、iOS Watchdog 0.21% → **0.04%**、用户投诉 8000+/日 → **240**、Google Play 标签 **28 天后移除**；第二次大促压测再未出现 ANR 洪峰。
>
> **一句话总结**：**ANR 治理没有银弹，只有"**不信栈顶 + 全栈采集 + 四模式归因 + 四层治理**"的完整闭环**——方法派比经验派快的不是技术，而是**第一刀砍对位置**。

## 06.原理深潜

> 本章面向资深工程师——**知其所以然**。理解这些机制，才能应对任何陌生 ANR 问题。

### 6.1 Looper 消息循环机制

Android 主线程本质是**无限循环的消息处理器**：

```
   ActivityThread.main()
       │
       ├─ Looper.prepare()         ← 创建 MessageQueue
       ├─ Looper.loop()            ← 死循环
       │     ├─ queue.next()       ← 阻塞取消息（nativePollOnce）
       │     ├─ msg.target.dispatchMessage()
       │     ├─ msg.recycle()
       │     └─ loop
       └─ 永不返回
```

**关键认知**：
- **主线程永远在 Loop**——不是"主线程死了才卡"，而是"**某条消息执行太久**"；
- **nativePollOnce 是空闲等待**——这是**正常状态**，不是异常；
- **一次 dispatchMessage 过长 = 一次卡顿**——所有卡顿都发生在这个方法内。

**▶▶ LooperPrinter 原理**：Looper 在 dispatchMessage 前后会调用 `Printer.println`，分别打印 `>>>>> Dispatching` 和 `<<<<< Finished`——拦截这两条就能计时每一条消息。

### 6.2 Choreographer 帧调度

**Choreographer 是 Android 的"帧时钟"**——由 Vsync 驱动，统一调度输入事件、动画、绘制：

```
   硬件 Vsync 信号（60Hz 每 16.67ms）
       ↓
   SurfaceFlinger
       ↓ Binder
   Choreographer.doFrame()
       ↓
   ① Input 事件分发
       ↓
   ② Animation 回调
       ↓
   ③ Traversal（measure/layout/draw）
       ↓
   RenderThread 异步合成
```

**与 ANR 的关系**：
- **Input 事件在 Choreographer 调度**——Input 消息进入主线程队列，由 doFrame 分发；
- **如果主线程卡住 > 5s**，Input 事件堆积，InputDispatcher 判定 ANR；
- **doFrame 内的 traversal 卡死 = 单帧 ANR**。

### 6.3 InputDispatcher ANR

**最常见的 ANR 类型（90%+）**，完整链路：

```
   用户触摸屏幕
       ↓
   InputReader（系统进程）读取原始事件
       ↓
   InputDispatcher 维护事件队列
       ↓
   send to App（通过 socket）
       ↓
   App InputChannel 接收
       ↓
   Choreographer 调度到主线程 Looper
       ↓
   View.dispatchTouchEvent → onClick/onTouch
       ↓
   App 回执 "已处理" 给 InputDispatcher
       ↓
   如果 5s 内无回执 → InputDispatcher 判定 ANR
       ↓
   AMS 向 App 发 SIGQUIT
       ↓
   signal_catcher 生成 /data/anr/traces.txt
```

**关键机制**：
- **5s 从哪开始计时**：事件被 **dispatch 到 app 的 socket 那一刻**，不是"用户点击那一刻"；
- **响应标准**：事件被主线程 Looper 处理完成（无论业务做了什么）；
- **ANR 的本质不是"主线程卡 5s"，是"**事件 5s 内没被 Loop 到**"。

### 6.4 Service ANR 全链路

**Service ANR 的触发条件**：

| 场景 | 阈值 | 关键函数 |
|---|---|---|
| 前台 Service 启动 | 20s | onCreate + onStartCommand |
| 后台 Service 启动 | 200s | 同上 |
| bindService | 20s | onBind |

**全链路**：

```
   startService / startForegroundService
       ↓
   AMS 启动 service 进程
       ↓
   AMS 调度 Service.onCreate
       ↓
   AMS 调度 Service.onStartCommand
       ↓
   AMS 启动 20s 看门狗（前台）
       ↓ 20s 内 onStartCommand 返回
   取消看门狗
       ↓ 否则
   AMS 判定 Service ANR
```

**治理要点**：
- `onStartCommand` **必须快速返回**；
- 重任务用 **IntentService / WorkManager**；
- 前台 Service 必须在 5s 内调 `startForeground`（Android 12+）。

### 6.5 Broadcast ANR 全链路

**阈值**：前台 10s / 后台 60s（Android 11+ 为 60s）。

**全链路**：

```
   发送方 context.sendBroadcast()
       ↓
   AMS BroadcastQueue 收到广播
       ↓ 分发到各接收器
   App BroadcastReceiver.onReceive()
       ↓ 必须 10s 内返回
   onReceive 返回 → AMS 继续分发给下一个
       ↓ 否则
   AMS 判定 Broadcast ANR
```

**关键陷阱**：
- `onReceive` 返回后 **Receiver 对象立即销毁**，不能开线程继续工作；
- 解决方法：`goAsync()` 返回 PendingResult，在异步线程完成后调 `pending.finish()`；
- 若不调 `pending.finish()`，10s 后系统兜底判定 ANR。

### 6.6 ContentProvider ANR 全链路

**阈值**：ContentProvider 发布 10s。

**全链路**：

```
   App.onCreate 之前
       ↓
   ActivityThread 遍历所有 ContentProvider
       ↓
   逐个调用 provider.onCreate()
       ↓ 必须 10s 内完成
   publishProviders 给 AMS
       ↓ 否则
   启动失败（算 ANR）
```

**关键认知**：
- **CP.onCreate 发生在 Application.onCreate 之前**——拖慢 CP 直接拖慢冷启动；
- **第三方 SDK 常用 CP 做"隐式初始化"**（Firebase/WorkManager/Startup）；
- 大量 CP 串行 init 是启动 ANR 的高频场景。

**治理**：
- CP.onCreate **只做注册，不做初始化**；
- 第三方 SDK 的隐式 CP → 在 Manifest 禁用 + 改用 App Startup 显式管理。

### 6.7 iOS Watchdog 全链路

iOS 没有传统意义的 "ANR"，但有同类机制 **Watchdog**：

| 场景 | 阈值 | 后果 |
|---|---|---|
| 启动 Launch | **20s** 完成 UIApplicationDelegate 回调 | 启动 crash（0x8badf00d） |
| 前后台切换 Resume | **10s** | crash |
| 后台任务 Background | **30s** | crash |
| 退出 Terminate | **5s** | crash |

**Watchdog 的本质**：
- iOS SpringBoard 向 app 发信号，等待回执；
- 超时则**直接杀进程**（无弹框，更严苛）；
- 日志中标志：`exception_subtype: 0x8badf00d`（意为 "ate bad food"）。

**治理**：
- `application:didFinishLaunchingWithOptions:` 必须 < 20s（通常 < 1s）；
- SDK 异步 init；
- 启动期不做 IO/网络同步。

### 6.8 SIGQUIT 与 traces.txt

**ANR 发生时的信号链**：

```
   system_server 判定 ANR
       ↓
   kill -3 <pid>（SIGQUIT）
       ↓
   App 的 signal_catcher 线程被唤醒
       ↓
   art::DumpForSigQuit
       ↓
   暂停所有 Java 线程
       ↓
   遍历每个线程 → 栈回溯 → 写入 /data/anr/traces.txt
       ↓
   恢复线程 → signal_catcher 继续等信号
```

**traces.txt 关键段落**：

```
----- pid 12345 at 2026-10-25 00:03:45 -----
Cmd line: com.example.app

suspend all histogram:  ...
DALVIK THREADS (42):  ← 线程总数

"main" prio=5 tid=1 Native  ← 主线程
  | state=S              ← 睡眠状态
  | sysTid=12345
  | sched=1073741824 nice=0  ← 优先级
  | stack=0x7fff8000-0x7fff8500
  | held mutexes=   ← 持有的锁
  native: #00 pc ... /system/lib64/libc.so (syscall+28)
  native: #01 pc ... libnativehelper.so (nativePollOnce+152)
  at android.os.Looper.loop(Looper.java:233)
  at android.app.ActivityThread.main(ActivityThread.java:7656)

"RxCachedThreadScheduler-1" prio=5 tid=23 Blocked  ← 关键！
  | held mutexes=
  waiting to lock <0x12345678> (a java.lang.Object) held by thread 19  ← 等锁
  at com.example.app.DBHelper.write(DBHelper.java:120)
  ...
```

**读 traces 的三要点**：
1. **先看所有线程的 state**（R/S/B/W），**Blocked 和 waiting** 的线程最可疑；
2. **看 held mutexes 和 waiting to lock**，找锁依赖链；
3. **看 "CPU usage" 段**，哪个线程/进程在烧 CPU。

### 6.9 Binder 跨进程阻塞

**Binder 调用的阻塞模型**：

```
   App 主线程调用 service.doSomething()
       ↓
   Binder.transact()
       ↓ 阻塞当前线程
   内核 binder driver
       ↓
   目标进程的 binder thread pool
       ↓ 调度到空闲 binder thread
   目标进程执行 doSomething
       ↓ 结果通过 binder driver 返回
   App 主线程 Binder.transact 返回
```

**阻塞点**：
- **binder thread pool 耗尽**（默认 16 个）；
- **目标进程 CPU 高**（如大促时 system_server）；
- **目标进程被杀/Suspend**；
- **跨 UID binder 验证开销**（Android 11+ 增强）。

**治理**：
- 所有 Binder 调用加 2s 超时；
- 关键信息本地缓存兜底；
- 避免高频 Binder 调用（批量化）。

### 6.10 GC STW 与 ANR

**ART GC 的 STW 阶段**：

| GC 类型 | STW 时长 | 频率 |
|---|---|---|
| **Concurrent Copying GC** | 1-5ms | 高频 |
| **Partial GC** | 5-30ms | 中频 |
| **Full GC** | 100-500ms | 低频 |
| **Compacting GC**（低端机） | 500ms-2s | 极低频 |

**与 ANR 的关系**：
- **普通 GC 一般不会 ANR**；
- **Full GC + 低端机 + 内存压力** = STW 可能到秒级 → 直接贡献 ANR；
- **CopyingGC 并发阶段的 Suspend** = 主线程被 Suspend 几十 ms，累积卡顿。

**查看 GC 日志**：

```bash
adb logcat -s art
# 关注：
# art: Concurrent copying GC freed ...ms, paused ...ms
#      ↑                              ↑
#   总耗时                       STW 时长 ← 看这个
```

**治理**：
- 减少对象分配（§02 内存篇 §5.1）；
- 避免 largeHeap；
- 对象池复用高频短生命周期对象。

## 07.面试高频追问

### Q1 nativePollOnce 卡 ANR 吗

**问**：traces.txt 里主线程栈顶是 `nativePollOnce`，是不是卡在这里了？

**答**：**不是**——`nativePollOnce` 是**正常空闲等待**，表示"**抓栈瞬间**主线程在等消息"。它不代表 5s 内都在等——真实现场是主线程前 4.8s 被 off-CPU 操作卡住，4.9s 刚处理完消息进入下一轮 pollOnce，第 5s 系统兜底抓栈——"**案发现场已过**"。70% 的 ANR 栈顶都是 nativePollOnce，真因在其他线程持锁或其他进程 Binder 慢。**定位**：看所有线程栈 + Binder 远端栈 + CPU 占用（§3.3 四模式）。

### Q2 子线程死锁会 ANR 吗

**问**：两个子线程互相死锁，会触发 ANR 吗？

**答**：**不会直接 ANR**，但**会间接 ANR**。两个子线程死锁 → 它们持有的锁永远不释放 → 如果主线程后续尝试获取其中之一 → 主线程被卡住 → 累积 5s → ANR。所以子线程死锁的危险在于**传染给主线程**。**定位**：traces.txt 中看 "held mutexes" 的循环等待链；**治法**：锁使用超时版本（`tryLock(timeout)`）。

### Q3 ANR 5s 阈值可调吗

**问**：能不能让系统 ANR 阈值从 5s 改到 10s？

**答**：**不能（没 root）**，而且**改了也没意义**。5s 阈值在 AMS/InputDispatcher 的硬编码（`KEY_DISPATCHING_TIMEOUT_MILLIS = 5000`），用户 App 无法修改。即使改了也没用——**用户感知的卡顿远小于 5s**，1-2s 的卡顿用户已经骂爆了（见贯穿案例"把阈值从 5s 改 10s"的反面教材——上报数降了但投诉涨了）。**正解**：WatchDog 2s 阈值提前抓准 ANR，比系统快一步。

### Q4 LooperPrinter 能覆盖多少

**问**：用 LooperPrinter 监控主线程卡顿，覆盖率有多高？

**答**：**约 95%**。LooperPrinter 拦截 `>>>>> Dispatching` 和 `<<<<< Finished`，覆盖所有通过 Handler/Message 调度的任务。**盲区**：Vsync 回调内 Choreographer doFrame（约 3%）、JNI 调用（约 1%）、系统注入事件（约 1%）。所以必须配合 **WatchDog（100% 覆盖）** 补齐盲区。实战中 **LooperPrinter + WatchDog 双保险**是线上监控的标配。

### Q5 iOS 为什么没 ANR

**问**：iOS 为什么没有 Android 这种 ANR 概念？

**答**：**iOS 有同类机制，叫 Watchdog**，而且**更严苛**：
- Android ANR 阈值 5s，iOS Launch Watchdog **20s**；
- Android ANR 弹框让用户选，iOS Watchdog **直接杀进程**（无弹框，日志 `0x8badf00d`）；
- Android ANR 影响 Vitals 评分，iOS Watchdog **计入崩溃率**，对应用商店评分冲击更大。

实际上 iOS 对主线程响应的要求比 Android 更严——`main thread hang > 250ms` 系统就会在 Instruments 里标红。所以"iOS 没 ANR"是**错觉**，是 **"iOS Watchdog 更隐蔽但更严厉"**。

### Q6 Broadcast goAsync 原理

**问**：`BroadcastReceiver.goAsync()` 是怎么解决 ANR 的？

**答**：`goAsync()` 返回一个 `PendingResult`，告诉 AMS **"我需要更多时间"**——AMS 把这个 Receiver 的 ANR 阈值从 10s 延长到更长（约 10s 到 60s 看版本），同时允许 Receiver 对象在 onReceive 返回后继续存活（否则会立即销毁）。但 **必须显式调 `pending.finish()`**——忘了调仍然会 ANR。**正确模板**：

```kotlin
override fun onReceive(ctx: Context, intent: Intent) {
    val pending = goAsync()
    coroutineScope.launch(Dispatchers.IO) {
        try { doHeavyWork() }
        finally { pending.finish() }  // 必须！
    }
}
```

### Q7 traces.txt 怎么读

**问**：拿到 `/data/anr/traces.txt` 怎么读才能定位根因？

**答**：按**五步法**读：
1. **先看 Cmd line**：确认进程；
2. **看 "DALVIK THREADS" 的 main 线程 state**：
   - `Runnable` → on-CPU 类，看栈顶业务代码；
   - `Native/Suspended` → off-CPU 类，看在等什么（锁/IO/Binder）；
3. **看 "held mutexes" 和 "waiting to lock"**：找锁依赖链；
4. **看其他线程 state**：有没有 `Blocked`/`Waiting` 的——它们是**真因候选**；
5. **看 "CPU usage" 段**（在 traces 末尾）：哪个进程/线程在烧 CPU。

**典型模式**：
- 栈顶 nativePollOnce + 某子线程 `BLOCKED (acquiring lock)` → DB/锁 ANR；
- 栈顶 Binder.transact → 跨进程 ANR，看 system_server CPU；
- 栈顶 fsync → IO ANR；
- 栈顶业务代码 → on-CPU ANR。

### Q8 CP onCreate 为什么卡启动

**问**：ContentProvider.onCreate 怎么会拖慢启动？

**答**：**ContentProvider 的 onCreate 在 Application.onCreate 之前执行**。启动流程：
```
ActivityThread.handleBindApplication
  → installContentProviders  ← 遍历所有 CP，逐个 onCreate
  → mInstrumentation.callApplicationOnCreate  ← Application.onCreate
```

所以 CP.onCreate 的耗时**完全算在冷启动里**。大量第三方 SDK（Firebase/WorkManager/Lifecycle/Startup/广告 SDK）都用隐式 CP 做初始化——10 个 SDK 的 CP 各 100ms init 就是 1s 启动延迟。**治法**：
- 自己的 CP：onCreate 空实现，所有初始化懒加载到 query；
- 第三方 CP：在 Manifest 禁用自动初始化（`<provider ... tools:node="remove" />`），改用 App Startup 显式控制。

### Q9 WatchDog 阈值设多少

**问**：ANR WatchDog 的阈值是不是越小越好？

**答**：**不是**——阈值是"**捕获率 × 准确率**"的平衡：

| 阈值 | 捕获率 | 误报率 | 推荐 |
|---|---|---|---|
| 500ms | 100% | 15% | 开发期 |
| 1s | 99% | 3% | 启动期线上 |
| **2s** | **90%** | **0.3%** | **日常线上主力** |
| 3s | 60% | 0.1% | 保守 |
| 5s | 20% | 0% | 等于不监控 |

**2s 是黄金阈值**——比系统 5s 早 3s（预警足够），比 1s 误报率低 10 倍（线上可用）。贯穿案例的 1240 次准 ANR 全部用 2s 捕获。

### Q10 后台 ANR 怎么处理

**问**：后台 Service ANR 阈值 200s，是不是不用管？

**答**：**要管**。虽然阈值长，但：
- **后台 ANR 仍计入 Google Play ANR 率**，影响推荐；
- **用户后台切回前台看到 "App 已停止"**，体验极差；
- **200s 的任务本质是设计问题**——后台任务应该用 WorkManager 分片，不是单条 Service。

**治理**：所有后台重任务迁移到 **WorkManager / JobScheduler**，这些组件天然支持分片、重试、约束条件。

### Q11 FPS 低不一定卡吗

**问**：FPS 均值 55 的 App，用户到底卡不卡？

**答**：**不一定**——FPS 是均值，掩盖了尾部抖动。两种情况：
- **稳定 55fps**（每帧均匀 18ms）：**不卡**，用户感知流畅；
- **大部分 60fps + 偶发 500ms 冻帧**（平均算下来 55fps）：**非常卡**，用户体验差。

**判断标准**：
- 看 **P95/P99 帧时长**（§04 §4.4）；
- 看 **大卡顿率**（> 700ms 帧占比）；
- 看 **卡顿会话率**（含明显卡顿的会话比例）。

均值永远骗人，分布不骗人（渲染篇 §5.7 心法）。

### Q12 为什么 ANR 栈顶常是 nativePollOnce

**问**：为什么系统抓的 ANR 栈顶 70% 都是 nativePollOnce，是不是系统有问题？

**答**：**系统没问题，是时序问题**——这就是 §1.2 "栈顶之惑"：

```
   时间线：
   T=0s:   消息 A 到达主线程队列（Vsync 事件）
   T=0.1s: 主线程开始处理消息 A
   T=0.2s: 消息 A 内部调 DB，但 DB 锁被子线程持有
   T=0.2s-4.9s: 主线程 waiting to lock（off-CPU）
   T=4.9s: 子线程释放锁，主线程恢复
   T=4.9s: 消息 A 完成，主线程进入 nativePollOnce 等下一条
   T=5.0s: 系统 ANR 判定（Input 事件 B 在前 5s 内没被处理）
   T=5.0s: 系统 SIGQUIT 抓栈
   T=5.0s: 抓到的栈 = nativePollOnce（真正的卡顿已经结束）
```

**本质**：ANR 判定是**基于时长（5s）**，但抓栈是**基于触发瞬间**——两者可能错位几百 ms，这就是栈顶常是 pollOnce 的原因。**定位**：靠 WatchDog 2s 更早抓到真实现场。

### Q13 BlockCanary 原理和局限

**问**：BlockCanary 是怎么工作的？有什么局限？

**答**：**原理**：hook Looper 的 Printer，每条消息 dispatch 前后计时，超阈值（默认 1s）就抓主线程栈 + 系统信息。**局限**：
- **只抓主线程栈**（不含其他线程），归因能力弱——对 off-CPU 类卡顿定位困难；
- **采样是消息级**，无法捕获 Vsync 内卡顿（LooperPrinter 盲区约 5%）；
- **开销不低**（每条消息 2 次 println + 条件判断），线上不建议默认全开；
- **维护断更**（最后更新 2017 年），现代场景可用 **ANR-WatchDog + Perfetto** 替代。

**现代最佳实践**：**LooperPrinter（覆盖）+ WatchDog（预警）+ 全线程栈（归因）** 三件套。

## 08.模拟面试模板

### 8.1 卡顿与ANR理解

**问**：谈谈你对卡顿和 ANR 的整体理解？

**答**：

> 卡顿和 ANR 是**同一问题的两种程度**——都是"**主线程被阻塞**"，差别只在时长：卡顿 100ms-5s（用户感知），ANR ≥ 5s（系统兜底）。治 ANR 的前提是治卡顿。
>
> 我的理解框架是"**阻塞三态 + 四触发 + 四层治理**"：
>
> **阻塞三态**：
> - A on-CPU 卡顿：主线程在烧 CPU（30% 卡顿 / 15% ANR）；
> - **B off-CPU 卡顿**：主线程在等锁/IO/Binder/GC（**55% 卡顿 / 70% ANR**）；
> - C 系统级抢占：被其他进程抢 CPU（15% / 15%）。
>
> **四触发**（ANR）：
> - Input ANR 5s（90%+）；
> - Service ANR 20s/200s；
> - Broadcast ANR 10s/60s；
> - ContentProvider ANR 10s。
>
> **四层治理**（§5）：
> - 一层减负：主线程零阻塞；
> - 二层协同：锁/Binder/异步化；
> - 三层监控：WatchDog + 分级告警 + 熔断；
> - 四层组件：Service/Broadcast/CP/Activity 合规。
>
> 治理顺序：**先减负（治根）→ 再协同（治链）→ 再监控（预警）→ 最后组件（兜底）**。顺序错了就是"3 周翻车"。

### 8.2 线上ANR监控方案

**问**：线上 ANR 监控怎么做？

**答**：

> **三方案组合**：
>
> - **LooperPrinter**：覆盖 95% 主线程卡顿，开销低，适合日常监控；
> - **WatchDog**：覆盖 100%，阈值 2s（比系统 5s 快 3s），是**预警主力**；
> - **ApplicationExitInfo**：读历史 ANR，权威但滞后，作兜底。
>
> **WatchDog 增强三特性**（必配）：全线程栈 + CPU 占用 + Binder 繁忙度——这三件决定了归因能否精准。
>
> **分级告警 + 熔断**：L1 轻微（100-500ms）日志、L2 明显（500ms-2s）APM、L3 严重（2s-5s）P1 告警、L4 ANR（≥5s）P0 熔断。连续 3 次 >2s 阻塞自动降级（关动画/降图质/禁非必要功能）。
>
> **线上降级策略**：常态 10% 采样 + 2s 阈值；异常期 100% 采样 + 1s 阈值；熔断期全部关闭。
>
> **SLO 告警**：ANR 率 > 0.3% 持续 10 分钟 P0；准 ANR 率 > 1.5% P1；Google Play "过度 ANR" 红线是 0.47%，必须留 50% 余量。

### 8.3 ANR排查流程

**问**：收到线上 ANR 告警，你的排查流程是什么？

**答**：

> 按**五步法**：
>
> **① 分类**：看 anr_subject，是 Input/Service/Broadcast/CP 哪一类？
>
> **② 不信栈顶**：主线程栈顶若是 `nativePollOnce` / `Object.wait` / `Binder.transact`，是"**栈顶陷阱**"——真因在其他线程/进程。
>
> **③ 全栈采集**：
> - 看所有线程 state——`Blocked` / `Waiting` 的线程是真因候选；
> - 看 held mutexes 的锁依赖链；
> - 看 Binder 远端栈（Perfetto / systrace）；
> - 看 CPU usage 段，哪个进程烧 CPU；
> - 看 GC 日志，有无 STW。
>
> **④ 四模式归纳**：匹配 §3.3 四模式——A DB 锁 / B Binder 慢 / C 连接池 / D SDK 串行。
>
> **⑤ 对症治理**：
> - A 模式 → §5.2 锁治理（WAL / 读写锁）；
> - B 模式 → §5.2 Binder 治理（超时+降级）；
> - C 模式 → §5.2 连接池扩容；
> - D 模式 → §5.1 App Startup DAG。
>
> **贯穿案例**：电商大促 ANR 0.52%，Day 1 不信栈顶 → Day 2 WatchDog 全栈 → Day 3 四模式归因 → Day 4 四层治理 → Day 6 ANR 0.07%。**从归因到治理整个闭环靠的就是"不信栈顶 + 全栈采集 + 四模式分类"三招**。

### 8.4 四大全链路理解

**问**：讲讲 Input/Service/Broadcast/ContentProvider 四大 ANR 的根本区别？

**答**：

> 四大 ANR 本质都是"**系统给组件设的响应阈值**"，但场景和治理完全不同：
>
> | 类型 | 阈值 | 核心触发 | 治理手段 |
> |---|---|---|---|
> | **Input** | 5s | 用户事件 5s 内未处理 | 主线程减负（§5.1） |
> | **Service** | 20s/200s | onStartCommand 未返回 | 迁 WorkManager（§5.4.1） |
> | **Broadcast** | 10s/60s | onReceive 未返回 | goAsync（§5.4.2） |
> | **ContentProvider** | 10s | onCreate 未完成 | 空实现+懒加载（§5.4.3） |
>
> **关键认知差异**：
>
> - **Input ANR 的根因在主线程阻塞**——是其他三个的"**终极形态**"；
> - **Service ANR 的根因在同步重任务**——有专门组件（WorkManager）替代；
> - **Broadcast ANR 的根因在"onReceive 返回后 Receiver 销毁"的生命周期**——需 goAsync 延长；
> - **ContentProvider ANR 的根因在"onCreate 发生在 Application 之前"**——是启动期 ANR 的隐藏杀手。
>
> **治理优先级**：**ContentProvider（最隐蔽，影响启动期）> Broadcast（最高频，影响日常）> Service（最明显，影响后台）> Input（最常见，但治法通用）**。

### 8.5 优化故事线

**问**：讲一个你亲手做过的完整 ANR 治理案例？

**答**：

> **背景**：某头部电商 App V12.3 大促上线，凌晨 0:00 抢购开始 5 分钟 ANR 率 0.08% → **0.52%**，被 Google Play 打"过度 ANR"标签，推荐位降权，微博热搜 **#商城卡死#**，1 小时 8000+ 投诉，单日订单流失 **2300 万**。3 周经验派（改超时/try-catch/改阈值）全无效甚至反向。
>
> **归因**（Day 1-3）：
> - 系统 traces.txt 栈顶 70% nativePollOnce，经验派误读为"主线程空闲"；
> - 上线 **WatchDog(2s) + 全线程栈 + Binder 远端栈**，6 小时抓 1240 次准 ANR；
> - 四模式归纳：**42% DB 锁 + 28% Binder 慢 + 18% HTTP 池 + 12% SDK 串行**；
> - 核心洞察：**70% 是 off-CPU 类 ANR**，主线程栈是无辜的。
>
> **方案**（Day 4-5）：按**四层治理**：
> - **一层减负**：onCreate 的 450ms SDK init → App Startup DAG 异步，80ms；
> - **二层协同**：SQLite WAL + 读写锁分离；OkHttp 连接池 5→32；Binder 加 2s 超时 + 本地缓存降级；
> - **三层监控**：WatchDog(2s) 固化 + 卡顿分级告警 + 连续 3 次 >2s 自动熔断；
> - **四层组件**：BroadcastReceiver → `goAsync()`；Service → WorkManager；CP.onCreate 空实现。
>
> **防劣化**：Lint 规则（主线程 IO/Binder 无超时拦截）+ CI 卡口（冷启动 P99 > 2s 阻断 PR）+ 线上 SLO 告警（ANR 率 > 0.3% 自动熔断）。
>
> **结果**：ANR 率 0.52% → **0.07%**（-86%），iOS Watchdog 0.21% → **0.04%**，用户投诉 8000+/日 → **240**，Google Play 标签 **28 天后移除**，第二次大促压测再无 ANR 洪峰。
>
> **复盘**：**经验派不是不努力，是归因错了方向**——3 周全花在"看主线程栈"上（栈顶 nativePollOnce = 空闲），完全没看 off-CPU 真因。方法派第一刀砍对位置："**不信栈顶 + WatchDog 2s + 全栈 + 四模式**"——这就是方法论的全部价值。
