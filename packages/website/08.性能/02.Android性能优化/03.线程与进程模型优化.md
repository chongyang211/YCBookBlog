# 线程与进程模型优化

> **本文定位**：面向中高级 Android 工程师的"并发两级模型"系统性复习材料，用于面试准备、技术分享、架构评审。与《CPU 监控与分析》《内存监控与 OOM 治理》同构：开篇拷问 → 问题本质 → 排查归因 → 监控体系 → 分层治理 → 原理深潜 → 高频追问 → 面试模板。

## 00、开篇拷问

### 0.1 线程越多越快吗

```
问题：8 核手机开 32 线程做 IO，一定比 8 线程快吗？
```

**错觉**：核多了并发多就快。

**真相**：线程不是免费的——每个线程**栈 1MB + TCB ~10KB + 调度成本 μs 级 + cache 污染 10-100μs**。32 线程做 IO，看似并发 32，实则：
- 线程切换从每秒数千次飙到数万次，CPU 全在"切"不在"算"；
- cache 反复失效，有效工作集缩水；
- IO 底层队列深度有限（nvme 32、EMMC 1-4），**线程数超过队列深度后全是伪并发**。

**本文第一性原理**：**并发是用"切换/锁开销"兑换"延迟缩短"的生意**，不是免费加速器。详见 §01.1。

### 0.2 多进程比单进程更稳吗

```
问题：把 App 拆成 5 个进程，是不是比单进程更稳定？
```

**错觉**：进程多 = 隔离强 = 稳定。

**真相**：隔离的**收益是概率性的**（不出事时为零），**代价是确定性的**（每天都在交房租）：
- 每个空进程常驻 ~15MB，带运行时 25-70MB；
- 每次 IPC 1-5μs（Binder 本地）到 10ms+（跨进程调用链）；
- 系统（lmkd、Android 11+ Doze）**对"进程贪婪应用"主动打压**，被杀率反升。

**本文结论**：**80% 应用用单进程最好，20% 用主进程 + 风险隔离，几乎没人需要 5 进程以上**。详见 §01.2 + §04.5。

### 0.3 协程能替代线程池吗

```
问题：既然协程"切换 1/100"，开百万协程不就够了？
```

**错觉**：协程 = 轻量线程 = 可以替代一切。

**真相**：协程是**调度单位**，线程是**执行单位**。协程挂起时不占线程，但执行计算仍然在底层那几根线程里排队：
- `Dispatchers.Default` 底层是 **N=核数**的 ForkJoinPool，CPU 密集任务开再多协程也是单核算力；
- 阻塞调用（`Thread.sleep` / 同步 Binder / 文件 IO）**会把那根线程扣死**，饿死排队中的其他协程；
- 协程真正省的是"**等待时的线程占用**"（IO 密集场景），不是执行计算的 CPU。

**本文定位**：协程是"用户态调度优化"（§05.5），不是银弹。详见 §04.3 + §06.Q10。

## 01、问题本质

> 把"线程"和"进程"的物理代价讲到可量化、可对照——这是全文一切优化的第一性基础。

### 1.1 线程物理本质

**一句话定义**：**线程 = 操作系统调度的最小单位，是"共享地址空间 + 独立执行上下文"的执行实例**。

这句话隐含**三个不可商量的物理约束**：

**约束一：线程共享地址空间**

同一进程内所有线程共享堆、全局变量、文件描述符——这是**线程"轻量"的根本**（不用复制地址空间）。
**代价**：共享即竞争——所有多线程 bug 的根源（数据竞争、死锁、可见性）都来自此。

**约束二：线程有独立执行上下文**

每个线程有：**独立的栈（1-8MB）、独立的寄存器状态、独立的 TCB（Thread Control Block ~10KB）**。
**代价**：栈 + TCB 常驻内存——1000 个线程 = 1-8GB 栈 + 10MB TCB，这是"线程不能无限开"的物理底线。

**约束三：切换要陷入内核**

线程切换由 OS 调度器触发，**必须陷入内核态**：
- 保存/恢复寄存器组（ARM 约 30 个寄存器）：~0.1-0.5μs
- 内核调度决策（CFS 红黑树遍历）：~0.5-2μs
- **cache/TLB 变冷**（新线程工作集不在 L1/L2）：**数十 μs 大头**
- 分支预测器污染：微秒级

**直接成本 1-5μs，加上 cache 变冷 20-50μs**。每秒 1 万次切换 = 10-30% CPU 用在"切"而不是"算"。

**三类线程问题形态**（后文决策树依据）：

| 形态 | 表现 | 典型场景 | 本文位置 |
|---|---|---|---|
| **调度不当** | 主线程阻塞、UI 卡顿、ANR | 主线程做 IO/同步 IPC/大计算 | §04.1 §04.4 |
| **同步开销** | 锁等待 P99 高、线程状态泳道大片 S/D | 锁粒度过大、持锁 IO、死锁 | §04.2 §05.3 |
| **资源浪费** | 线程数膨胀、切换率高、内存涨 | 线程池无上限、每 SDK 建自己的池 | §04.3 §05.2 |

**▶▶ 回扣线程案例**：直播开播卡死命中三类全部——线程数 187（资源浪费）、切换 22K/s（调度不当）、推流锁等待 850ms（同步开销）。

### 1.2 进程物理本质

**一句话定义**：**进程 = 操作系统资源分配与隔离的基本单元，是"独立地址空间 + 文件句柄 + 信号上下文"的执行实例**。

这句话同样隐含**三个不可商量的物理约束**：

**约束一：进程是地址空间的边界**

每个进程有独立虚拟地址空间——**这是硬隔离**：
- 进程 A 崩溃不会破坏 B 的内存（故障隔离）；
- 进程 A 泄漏不会影响 B（资源隔离）；
- 进程 A 读不到 B 的数据（安全隔离）。

**代价**：IPC 必经内核（copy 或 mmap），有性能开销。

**约束二：进程创建有固定成本**

每次创建进程都要：分配地址空间（页表）→ 复制/映射代码段 → 加载动态库 → 启动运行时 → 执行入口。

| 平台 | 创建开销 | 关键机制 |
|---|---|---|
| Android | **200-400ms** | **Zygote fork + CoW** 省去 VM 启动 ~500ms |
| iOS | 200-300ms | exec + dyld + libObjC |
| Web Tab | 100-500ms | 浏览器实现差异 |
| Linux fork+exec | 10-100ms | 不含应用初始化 |

**约束三：IPC 必经内核**

任何 IPC（Binder/Pipe/Socket/SharedMemory）都要：
```
进程 A 用户态 ─[陷入内核]─► 内核中转 ─[切回用户态]─► 进程 B 用户态
     │                            │
   一次 syscall ~1-5μs          一次 syscall ~1-5μs
```

即使是"零拷贝"的 SharedMemory，**建立映射仍需 syscall**——这是 IPC 的物理底线。

**四类进程问题形态**：

| 形态 | 表现 | 典型场景 | 本文位置 |
|---|---|---|---|
| **数量膨胀** | 常驻 PSS 高、OOM 率高、被 lmkd 杀 | 守护/拉活/保活、过度拆分 | §04.5 |
| **IPC 过慢** | 跨进程调用 100ms+、用户感知"卡" | 高频心跳、未批处理、未缓存 | §04.6 §05.7 |
| **启动过慢** | 冷启 > 1s、从通知点入体验差 | 子进程初始化慢、Zygote CoW 被破坏 | §05.6 |
| **保活失效** | 被杀率高、系统认定"贪婪" | A8+/A11+ 后传统互拉保活失效 | §04.7 |

**▶▶ 回扣进程案例**：金融 5 进程架构命中前三类——Push + 守护 + 拉活共占 140MB（数量膨胀）、主↔Push 心跳 35 次/秒（IPC 过慢）、冷启 3.6s（启动过慢）。

### 1.3 并发两级公式

**公式**：

```
业务耗时 = 任务总量 / (线程并发度 × 进程隔离度)

                       │              │
                       │              └─ 决定"故障/资源不扩散"
                       └─ 决定"任务并行跑完速度"
```

展开两级代价账：

```
实际并发收益 = 理论并发度 − 切换损失 − 同步损失 − IPC 损失

              │              │          │          │
              │              │          │          └─ 跨进程 1-5μs/次
              │              │          └─ 锁等待（可从 ns 到 100ms）
              │              └─ 单次 1-5μs + 冷 cache 20-50μs
              └─ 核数 × 单核算力
```

**两条铁律**（后面所有治理都是推论）：

1. **并发度不是"开多少线程"**：它由"核数 × 平均 IPC × 平均频率"（CPU 篇 §02.2 公式）物理封顶；
2. **隔离度不是"拆多少进程"**：它只在**故障发生时**才兑现价值，平时都是"交房租"。

**ROI 判定**：

```
线程 ROI = 延迟缩短收益 / (切换成本 + 同步成本 + 栈内存成本)
进程 ROI = 隔离事件收益 × 发生概率 / (IPC 成本 + 启动成本 + 内存成本)
```

**▶▶ 回扣两个案例**：
- 直播：线程 ROI 为负——32 线程切换成本（35K/s）远超并发收益；
- 金融：进程 ROI 为负——3 个"保活/守护"进程的隔离价值 ≈ 0（A11+ 保活已失效），常驻 140MB 却天天在付。

> 🔬 **深潜：mutex 为什么是 futex——用户态快路径的 20× 加速**
>
> §01.1 讲"切换要陷入内核"，但现代 Linux 的 mutex 并不是每次加锁都陷入内核。它底层是 **futex（Fast Userspace muTEX）**，有一条"用户态快路径"：
>
> **futex 的二态模型**：
>
> ```
> ┌─ 无竞争路径（快路径）：
> │   原子 CAS 修改一个 int 标志位 → 直接返回，不进内核
> │   成本：~30ns（一次原子操作）
> │
> └─ 有竞争路径（慢路径）：
>     CAS 失败 → syscall futex(FUTEX_WAIT) 挂起当前线程
>     成本：~1-5μs（陷入内核 + 切换 + cache 变冷）
> ```
>
> **工程推论**：
>
> 1. **低竞争场景 mutex 近乎免费**——30ns 的 CAS 和一次函数调用成本相当；
> 2. **高竞争时急速劣化**——命中慢路径，一次 1-5μs，百次就是毫秒级；
> 3. **这就是"自旋锁有时反而快"的原因**（§05.3）——如果竞争时间 < 1μs，自旋消耗的 CPU 远少于一次 futex 内核往返。

> 🔬 **深潜：Zygote fork + CoW 的边界——哪些 API 会偷偷"破坏共享"**
>
> §01.2 讲"Android 用 Zygote 省 VM 启动 500ms"，这一切的物理基础是 **Copy-on-Write（写时复制）**。但很多代码会无意中破坏 CoW，让子进程失去共享红利。
>
> **CoW 工作原理**（简化）：
>
> ```
> Zygote 父进程（预加载 50MB framework + 常用类）
>      │
>      ├─ fork ─► App 主进程      ──► 共享 50MB 页，只占增量
>      ├─ fork ─► :push 子进程    ──► 共享 50MB 页，只占增量
>      └─ fork ─► :web 子进程     ──► 共享 50MB 页，只占增量
>
> 任何子进程"写入"共享页 → 该页立即被"复制一份"归该子进程独占
> ```
>
> **四类破坏 CoW 的典型操作**：
>
> | 操作 | 破坏点 | 代价 |
> |---|---|---|
> | 在 `Application.onCreate` 里**随意写静态字段** | 整页 copy | 页面被拷到独占 |
> | 加载**巨型 .so**（如 OpenCV 几十 MB） | 页面被改写 ownership 转移 | 数十 MB 独占 |
> | 用 `Runtime.exec` / `fork+exec` | 立刻与 Zygote 完全解耦 | 共享全部作废 |
> | 频繁调用 `System.gc()` 触发整堆压缩 | 大面积页被改写 | 共享快速退化 |
>
> **工程推论**：
>
> 1. **子进程 Application 要按进程名精简**（见 §04.5）——不要跑主进程的全套初始化；
> 2. **大 .so 延迟加载到真正使用的进程**——避免所有进程都为它掏钱；
> 3. **测 CoW 收益**：对比 `/proc/<pid>/smaps` 中的 `Shared_Clean` + `Shared_Dirty` 占比，> 60% 说明 CoW 健康。

### 1.4 面试锚点

**Q："线程和进程的本质差别是什么？"**

答题模板（三约束对照 + 代价公式）：

> 线程和进程的差别可以用"**三约束对照 + 代价公式**"讲清楚。
>
> **线程三约束**：共享地址空间（轻量根源）、独立执行上下文（栈 + 寄存器 + TCB）、切换陷入内核（1-5μs 直接 + 20-50μs cache 变冷）；
>
> **进程三约束**：地址空间硬隔离（三重隔离的根本）、创建有固定成本（Android Zygote fork 省 VM 启动 500ms）、IPC 必经内核（物理底线）。
>
> **代价公式**：`业务耗时 = 任务总量 / (线程并发度 × 进程隔离度)`。线程优化本质是"用切换/锁开销兑换延迟缩短"，进程优化本质是"用 IPC/内存成本兑换故障/资源隔离"。
>
> **两条铁律**：并发度被物理封顶（核数 × IPC × 频率），不是"开更多线程"；隔离度收益是概率性的（故障时才兑现），不是"拆更多进程"。

## 02、排查归因

> 把"卡"和"被杀"两个表象分别拆到可诊断的叶子节点——这是归因不走弯路的前提。

### 2.1 卡顿决策树（线程维度）

**入口**：主线程 P95 帧时长 > 16ms，用户感知卡顿。先看一个指标：**主线程利用率**。

```
主线程 P95 帧时长 > 16ms
       │
       ├─ 主线程 on-CPU 利用率 > 80%  → 【A 分支】on-CPU 卡
       │                              └─ 看火焰图找平顶（CPU 篇 §03）
       │                                 常见病灶：主线程做大计算 / 复杂布局 / 同步序列化
       │
       └─ 主线程 on-CPU 利用率 < 30%（但帧时长仍高）→ 【B/C/D 分支】off-CPU 卡
          │
          ├─ 线程状态泳道大片 S（可中断睡眠） → 【B】等锁
          │                                └─ Perfetto `lock_contention` + 看持锁线程
          │                                   常见病灶：锁粒度大、持锁 IO、死锁
          │
          ├─ 线程状态泳道大片 D（不可中断） → 【C】等 IO / Binder
          │                              └─ Perfetto ftrace 看 syscall / Binder transaction
          │                                 常见病灶：主线程读文件、同步 Binder、cgroup 限流
          │
          └─ 线程切换率飙高（> 10K/s）→ 【D】被切换淹没
                                     └─ 线程数 > 100、每帧任务切到不同线程池
                                        常见病灶：无统一线程池、SDK 各自建池
```

**▶▶ 回扣线程案例**：
- 主线程利用率 95%（A 分支）+ 推流锁等待 850ms（B 分支）+ 线程数 187 切换 22K/s（D 分支）**三病灶并存**——这就是经验派"修一个病灶没用"的根因。

### 2.2 被杀决策树（进程维度）

**入口**：主进程被杀率 > 5%、用户点通知冷启比例高、OOM 率异常。先看**内存压力**。

```
主进程异常退出
    │
    ├─ 有 Java 栈 → 【A】堆内 OOM
    │                └─ 内存篇 §03 分类处理
    │
    ├─ 无栈但 crash → 【B】Native OOM / 地址空间
    │                 └─ breakpad / tombstone 查信号
    │
    ├─ 无 crash 日志，进程静默消失 → 【C】被 lmkd 杀
    │   │
    │   ├─ 看 `/sys/kernel/debug/lowmemorykiller/`（旧版本）
    │   ├─ 看 `logcat | grep lowmemorykiller`
    │   └─ 看 Android 11+ `dumpsys activity lmk` 或 `am_kill` 事件
    │       │
    │       ├─ oom_score_adj > 500 时被杀 → 【C-1】后台进程被回收（正常）
    │       ├─ oom_score_adj 100-500 被杀 → 【C-2】系统认定"贪婪应用"（治理重点）
    │       └─ oom_score_adj < 100 被杀    → 【C-3】整机内存危机（兜底）
    │
    └─ 进程数 > 系统上限 → 【D】触发整机策略
```

**▶▶ 回扣进程案例**：金融 App 命中 **C-2**——5 进程常驻 PSS 450MB，lmkd 把它标记为"贪婪应用"主动降权。

### 2.3 跨维度归因

**最常见误诊**：卡顿 ≠ 线程问题，被杀 ≠ 进程问题。

| 症状 | 直觉判断 | 真实可能 |
|---|---|---|
| 用户点通知冷启动特别慢 | 冷启动代码慢 | 主进程**被杀**（进程问题） |
| 后台任务跑半天没结果 | 后台任务代码慢 | **cgroup 限流**（线程/进程交界） |
| 主线程"看起来不忙"却卡 | CPU 不是瓶颈 | 等**跨进程 Binder**（进程 IPC 问题） |
| 加线程反而更慢 | 代码不好 | 切换率超临界（线程资源浪费） |
| 多进程后内存反而涨 | 内存泄漏 | **破坏 Zygote CoW**（进程问题） |

**判别顺序**：先看进程维度（是否有被杀/多进程），再看线程维度（主线程状态泳道）——顺序反了容易"治表不治本"。

### 2.4 面试锚点

**Q："主线程卡顿怎么排查？"**

答题模板（on-CPU vs off-CPU 分流 + 三类状态）：

> 第一步**分流**：看主线程利用率。
>
> **利用率高（> 80%）** → on-CPU 卡，走 CPU 篇 §03 火焰图找平顶；
>
> **利用率低却卡** → off-CPU 卡（约 70% 场景在这），用 Perfetto 看主线程状态泳道：**S 态等锁**（走锁竞争归因）、**D 态等 IO 或 Binder**（走 IO/IPC 归因）、**R 态排队**（走调度延迟/cgroup 归因）。
>
> 关键**反直觉**：ANR 的 70% 不是"CPU 不够"，而是"主线程等别人"。只看 CPU 曲线会漏掉大半——必须看状态泳道。
>
> 我做过的直播案例：主线程利用率 95% + 推流锁等待 P99 850ms + 线程数 187 切换 22K/s，三类并存。单修任何一个都没用，必须按决策树分别治——这就是 7 天闭环的归因起点。

## 03、监控体系

> 没有可信数据就没有归因。线程 + 进程 + 跨维度交叉指标三位一体，三类数据回答三个问题："线程在干嘛/进程在哪/两者在交互吗"。

### 3.1 线程采集三方案

**🤔 疑惑**：想知道"主线程卡 800ms 到底在等什么"，Android Studio Profiler 的 CPU 曲线永远只告诉你"占用高"或"占用低"——真实诊断该用什么？

**💡 解答**：Android Studio 的 CPU 曲线是"用户视角"，诊断需要"内核视角"。三方案分工：**清单回答谁在跑、trace 回答什么时候、锁回答谁等谁**。

| 方案 | 采集内容 | 开销 | 适用 |
|---|---|---|---|
| ① 线程清单 | `/proc/<pid>/task/*` 读 tid、name、state、CPU 时间 | 极低（<1%） | **线上常驻**采集线程数、状态分布 |
| ② 系统 trace | Perfetto / Systrace，sched_switch + syscall + ftrace | 中（3-5%） | **问题复现时**抓一段，看完整时序 |
| ③ 锁竞争 | `perf lock` / Perfetto `lock_contention` | 中 | **诊断同步问题**，看谁等谁 |

**▶▶ 方案①：线程清单采集**（线上常驻，开销 < 1%）

```kotlin
object ThreadMonitor {
    data class ThreadInfo(
        val tid: Int, val name: String, val state: Char,  // R/S/D/T/Z
        val utimeTicks: Long, val stimeTicks: Long,       // 用户/内核态 CPU 时间
        val voluntarySwitches: Long, val involuntarySwitches: Long
    )

    /** 读 /proc/self/task 下所有线程信息 */
    fun snapshot(): List<ThreadInfo> {
        val taskDir = File("/proc/self/task")
        return taskDir.listFiles()?.mapNotNull { parseThreadStat(it) } ?: emptyList()
    }

    private fun parseThreadStat(dir: File): ThreadInfo? = runCatching {
        val stat = File(dir, "stat").readText()  // 单次 syscall，~5μs
        val fields = stat.split(" ")
        val name = stat.substringAfter("(").substringBefore(")")
        ThreadInfo(
            tid = dir.name.toInt(),
            name = name,
            state = fields[2 + stat.count { it == '(' }][0],
            utimeTicks = fields[13].toLong(),
            stimeTicks = fields[14].toLong(),
            voluntarySwitches = File(dir, "status").readLines()
                .firstOrNull { it.startsWith("voluntary_ctxt_switches") }
                ?.substringAfter(":")?.trim()?.toLong() ?: 0,
            involuntarySwitches = 0L
        )
    }.getOrNull()

    /** 定时采样 + 异常告警 */
    fun startWatching() = GlobalScope.launch(Dispatchers.IO) {
        while (isActive) {
            val threads = snapshot()
            // 告警：主线程 D 态持续超过 3 次采样
            threads.firstOrNull { it.name == "main" }?.let {
                if (it.state == 'D') mainThreadStuckCount++
                else mainThreadStuckCount = 0
                if (mainThreadStuckCount >= 3) reportMainStuck(it)
            }
            // 告警：单进程线程数 > 100
            if (threads.size > 100) reportThreadExplosion(threads)
            delay(5_000)  // 5s 一次采样
        }
    }
}
```

**五个 state 字母含义**（面试必背）：

| state | 含义 | 典型场景 | 诊断方向 |
|---|---|---|---|
| **R** | Running / Runnable | 真在跑或排队跑 | 看 on-CPU（火焰图） |
| **S** | Sleeping（可中断） | 等事件 / 等锁 / 等 IO 完成通知 | 看 wchan（在等谁） |
| **D** | Uninterruptible | 等磁盘 IO、等 Binder 内核态 | **ANR 元凶**，必须定位 |
| **T** | Traced / Stopped | 被 debugger 停了 | 开发期才会出现 |
| **Z** | Zombie | 退出但父进程未 wait | 代码 bug |

> 🔬 **深潜：/proc/self/task 为什么是"零开销采集"的底层秘密——procfs 的虚拟文件系统设计**
>
> `/proc` 看起来是磁盘文件，但它**没有任何磁盘 IO**——是内核在你 open/read 的瞬间**现场计算**出来的"文件内容"。
>
> **procfs 的三条物理律**：
>
> ```
> 1. 读 /proc/<pid>/stat → 内核调 task_struct 结构体字段，拼成字符串返回
> 2. 读 /proc/<pid>/task/*/stat → 遍历 task_struct 的 thread_group 链表
> 3. 完全不走 VFS 磁盘路径——数据直接从内核内存结构序列化
> ```
>
> **三条工程推论**：
>
> 1. **采集开销 = syscall + 字符串拼接**，单次 1-5μs；采样 100 个线程 = ~500μs = 一帧的 3%——完全可以线上常驻；
> 2. **数据是实时的 ≠ 原子的**：你读到的"线程清单"不是一个瞬时快照，是遍历过程中线程链表的"累积"结果。极端场景下线程创建/销毁会导致采集到的 tid 对不上，这是正常的，不是 bug；
> 3. **进程视角 vs 线程视角**：`/proc/<pid>/stat` 是进程聚合，`/proc/<pid>/task/<tid>/stat` 是单线程。想定位"是哪个线程 CPU 高"必须读 task/*，光读 pid 看不见；
>
> **常见坑**：读完 `/proc/<pid>/stat` 立刻关掉 fd——不要像读磁盘文件一样做 buffered 缓存，内核内存结构可能已经变了。

### 3.2 进程采集三方案

**🤔 疑惑**：知道 App 有 5 个进程不难（`ps` 一下就看到），难的是——**这 5 个进程"真的在干活"吗**？它们之间是否互相拖累？

**💡 解答**：进程采集的核心不是"看见有谁"，而是"量化它们的价值和成本"。三方案分别回答：**清单回答谁在挂机、Binder 回答谁在相互调用、maps 回答谁在共享内存**。

| 方案 | 采集内容 | 开销 | 适用 |
|---|---|---|---|
| ① 进程清单 | `ps -A` / `ActivityManager.getRunningAppProcesses` / `dumpsys procstats` | 极低 | **线上**采集进程数、PSS、OOM score |
| ② Binder trace | `/sys/kernel/debug/binder/transactions`（root） / Perfetto Binder | 中 | **诊断 IPC** 频率、延迟、拥塞 |
| ③ 进程 maps | `/proc/<pid>/smaps` | 低（偶发） | **诊断 Zygote CoW** 共享率、.so 占用 |

**▶▶ 方案①：进程清单 + PSS 常驻采集**

```kotlin
object ProcessMonitor {
    data class ProcessInfo(
        val pid: Int, val name: String,
        val pssKb: Int, val rssKb: Int,
        val oomScoreAdj: Int,   // 进程被杀优先级
        val importance: Int,    // AM 维护的前台/可见/后台等级
    )

    fun snapshot(context: Context): List<ProcessInfo> {
        val am = context.getSystemService(ActivityManager::class.java)
        return am.runningAppProcesses?.map { proc ->
            // PSS 读取——Debug.MemoryInfo 走 dumpsys，开销稍大，1-2 分钟一次即可
            val memInfo = am.getProcessMemoryInfo(intArrayOf(proc.pid)).firstOrNull()
            ProcessInfo(
                pid = proc.pid,
                name = proc.processName,
                pssKb = memInfo?.totalPss ?: 0,
                rssKb = memInfo?.totalRss ?: 0,
                oomScoreAdj = readOomScore(proc.pid),
                importance = proc.importance,
            )
        } ?: emptyList()
    }

    private fun readOomScore(pid: Int): Int = runCatching {
        File("/proc/$pid/oom_score_adj").readText().trim().toInt()
    }.getOrDefault(0)
}
```

| **-900** | 前台桌面 | 最后杀 |

| **100-200** | 可见 Activity | 低压不杀 |
| **200-400** | 服务可见 | 中压杀 |
| **500-700** | 后台 Service | 中高压杀 |

```kotlin
fun analyzeCoWEfficiency(pid: Int): CoWReport {
    val lines = File("/proc/$pid/smaps").readLines()
    var sharedClean = 0L; var sharedDirty = 0L
    var privateClean = 0L; var privateDirty = 0L
    var rss = 0L
    for (line in lines) {
        when {
            line.startsWith("Shared_Clean:")  -> sharedClean += parseKb(line)
            line.startsWith("Shared_Dirty:")  -> sharedDirty += parseKb(line)
            line.startsWith("Private_Clean:") -> privateClean += parseKb(line)
            line.startsWith("Private_Dirty:") -> privateDirty += parseKb(line)
            line.startsWith("Rss:")           -> rss += parseKb(line)
        }
    }
    return CoWReport(
        rssKb = rss,
        sharedRatio = (sharedClean + sharedDirty).toDouble() / rss,
        cowBrokenKb = privateDirty,  // 已写时复制的页，不共享了
    )
}
```

**CoW 共享率的健康判定**：

| 场景 | Shared 占比 | 诊断 |
|---|---|---|
| 刚 fork 的子进程 | > 85% | 健康（大部分页还共享） |
| 稳态子进程 | 50-70% | 正常（Dalvik class / .so 共享保住了） |
| 稳态子进程 | **< 40%** | **异常**（子进程做了太多写操作，CoW 被破坏）|

**▶▶ 三方案的关键配合**

```
方案 ① 发现"5 进程 PSS 450MB，:push 占 150MB"
   ↓
方案 ② 发现"主→:push 心跳 35 次/秒，占主线程 CPU 的 14%"
   ↓
方案 ③ 分析 :push 的 smaps
   ↓ 发现"Shared_Clean 比例只有 40%——CoW 严重破坏"
最终结论：
  :push 做了大量业务逻辑写入 → 内存不共享 + 高频 Binder
  → 删除 :push 用 FCM 替代 ✅
```

> 🔬 **深潜：PSS vs RSS vs USS——为什么内存统计有三个数字，你应该用哪个**
>
> **物理内存归属的三种口径**：
>
> ```
> 一个物理内存页 P 被进程 A、B、C 共享：
>
> ┌────────────────────────────────────────┐
> │ RSS（Resident Set Size）：进程 A 把 P 算满（完整大小）│
> │   → A 的 RSS 包含 P 的全部 4KB         │
> │   → B 的 RSS 也包含 P 的全部 4KB       │
> │   → 三个进程 RSS 相加会"重复算 3 次"   │
> ├────────────────────────────────────────┤
> │ PSS（Proportional Set Size）：按共享人数均分 │
> │   → A/B/C 各算 4KB / 3 = 1.33KB        │
> │   → 三个进程 PSS 相加 = P 的真实大小   │
> ├────────────────────────────────────────┤
> │ USS（Unique Set Size）：只算私有页     │
> │   → A/B/C 都不算 P                     │
> │   → 衡量"杀掉这个进程能真实释放多少内存"│
> └────────────────────────────────────────┘
> ```
>
> **三条工程推论**：
>
> 1. **监控上报用 PSS**——它是 Google 推荐、Android `dumpsys meminfo` 默认输出，能跨进程相加不重复，适合 App 整体占用的量化；
> 2. **判断"杀进程能回收多少"用 USS**——这是 lmkd 的决策依据之一。你的 `:push` 进程 PSS 150MB、USS 20MB，意味着删掉它只能真释放 20MB——评估进程"该删不该删"要看 USS 不是看 PSS；
> 3. **压测对标用 RSS**——它不低估也不均分，反映"进程名下管辖的所有页"，适合纵向对比（同 App 两版本对比内存趋势），不适合横向求和。
>
> **诊断公式**：如果 `PSS >> USS`，意味着该进程"大部分内存和别人共享"——这正是 Zygote CoW 工作良好的信号。

### 3.3 跨维度交叉指标

**🤔 疑惑**：单看线程数 180、进程数 5、PSS 450MB——每个数字都"看起来还行"，为什么用户还是觉得卡？

**💡 解答**：问题藏在**"交叉"里**。单维度指标是"独立影像"，交叉指标是"CT 片"——它揭示线程与进程、CPU 与 IO、前台与后台之间的隐性冲突。

| 交叉指标 | 公式/口径 | 健康阈值 | 异常推论 |
|---|---|---|---|
| **线程/进程比** | 应用总线程数 / 应用进程数 | < 60/进程 | 高 → 单进程线程池失控 |
| **主线程 Binder 等待占比** | 主线程 D 态时长 / 总时长 | < 5% | 高 → 跨进程调用链卡住主线程 |
| **进程 CPU 时间差** | 单进程 CPU 时间 - 单进程 Wall 时间 | ≈ 1 | 远 < 1 → 该进程大量在等 |
| **CoW 共享率** | `Shared_Clean` / 总 Rss | > 60% | 低 → 破坏 CoW，子进程不省内存 |
| **lmkd kill 速率** | 每小时被杀次数（含后台） | < 1 | 高 → 进程过多或内存泄漏 |

**▶▶ 五个指标的深度解读**

**指标①：线程/进程比**（最简单、最有效的"失控检测器"）

```
健康 App：52 线程 / 2 进程 = 26 条/进程
失控 App：187 线程 / 5 进程 = 37.4 条/进程  ← 单看 187 不惊人，分摊后能看出"每个进程都在爆"
超失控：187 线程 / 1 进程 = 187  ← 肯定是没有统一线程池
```

**三条诊断动作**：
- `> 60/进程`：怀疑"每个 SDK 自建线程池"（见 §4.3）；
- `> 100/进程`：几乎可以断言未做线程池收敛，直接按 §4.3 落地；
- 增长趋势诊断：**上线前 55 → 上线后 95**，说明新引入 SDK 没走统一池。

**指标②：主线程 Binder 等待占比**（ANR 预警指标）

```kotlin
// 读 /proc/self/task/<main_tid>/status 的 voluntary_ctxt_switches
// 读 /proc/self/task/<main_tid>/schedstat 的 wait_sum
val wait = File("/proc/self/task/$mainTid/schedstat").readText()
    .split(" ")[1].toLong()  // 单位 ns，累计等待时间
val run = File("/proc/self/task/$mainTid/schedstat").readText()
    .split(" ")[0].toLong()  // 单位 ns，累计运行时间
val waitRatio = wait.toDouble() / (wait + run)
// waitRatio > 0.05 持续 5s → 告警
```

**诊断对应表**：

| waitRatio | 诊断 | 行动 |
|---|---|---|
| < 2% | 健康 | - |
| 2-5% | 关注 | 查日常是否偶尔同步 Binder |
| 5-15% | 高危 | 抓 Perfetto trace 看 Binder 事件 |
| **> 15%** | **已 ANR 边缘** | 立即定位同步 Binder 调用 |

**指标③：进程 CPU 时间 vs Wall 时间差**（off-CPU 诊断）

```
进程 Wall 时间 = 进程存活的真实时长
进程 CPU 时间 = 进程所有线程累计 on-CPU 时间
两者比值告诉你：
  比值 ≈ 核数 → CPU 密集，火力全开
  比值 ≈ 1  → 单核满载
  比值 << 1 → 大量在等（等锁/IO/Binder/配额）
  比值 ≈ 0  → 挂机进程（可以考虑删）
```

**▶▶ 回扣：金融案例的 :push 进程**：

| 指标 | 数值 |
|---|---|
| Wall 时间 | 24 小时 |
| CPU 时间 | 1.2 分钟（0.05%） |
| 结论 | **纯挂机，就为活着——必删** |

**指标④：CoW 共享率**（多进程架构的"健康度"）

```
健康值：70%+（Zygote 预加载的 .so 和 class 大部分共享）
告警：< 40%（子进程做了太多写入，CoW 大面积破坏）
```

**破坏 CoW 的三大元凶**：
1. 子进程启动后立刻 new 一堆对象（破坏 class 共享）；
2. SDK 修改静态变量（破坏 Zygote 预加载的 class 页）；
3. 子进程把共享 Bitmap 做了解码（像素页写，破坏 Shared_Clean）。

**指标⑤：lmkd kill 速率**（整机内存压力的"血压计"）

```bash
# 过去 1 小时被杀统计
adb shell logcat -b events -d -t 3600 | grep "am_proc_died" | wc -l
```

**三档诊断**：
- < 1 次/小时：健康，系统内存充裕；
- 1-10 次/小时：中压，关注是否偶尔 OOM 爆发；
- **> 10 次/小时**：高压，用户正在频繁被杀，必须立即检查内存泄漏和进程数量。

> 🔬 **深潜：为什么交叉指标比单维度"灵敏 10 倍"——Simpson's Paradox 在性能监控的体现**
>
> 单维度指标常常"看起来正常"，交叉后却暴露严重问题——这就是 **Simpson's 悖论**在性能监控里的变体。
>
> **真实案例**：
>
> ```
> 单维度看：
>   线程数：52     ✅ 正常
>   进程数：3      ✅ 正常
>   主线程 CPU：18%  ✅ 正常
>
> 交叉看：
>   线程/进程比 = 17  ✅ 正常
>   主线程 Binder 等待占比 = 23%  ❌ 高危！
>
> 推论：主线程 CPU 虽然只 18%，但有 23% 的时间在"等 Binder"
>       → 实际主线程 70%+ 时间不在干活
>       → 用户感觉"莫名其妙的卡"
> ```
>
> **三条工程推论**：
>
> 1. **交叉指标是性能监控的"灵魂"**——它把"独立数字"组合成"物理意义上的病症"。单维度告警会漏掉 60% 的真实问题；
> 2. **交叉指标要选"物理意义独立"的两个维度**：线程×进程、CPU×等待、内存×共享——这些组合有物理学解释。线程×内存就没有，组合出来是噪音；
> 3. **交叉指标的告警要"组合阈值"**：单看 "waitRatio > 5%" 可能是偶发，加上 "持续 5s" 就是真实问题。交叉指标的告警规则必须叠加"时间窗 + 频率 + 环境"。
>
> **哲学启示**：性能工程里，**"看单维度平均值 = 看温度，看交叉指标 = 做 CT"**——前者告诉你"病了没"，后者告诉你"病在哪"。

### 3.4 工具速查

**🤔 疑惑**：Android 调试工具一箩筐——adb、Perfetto、simpleperf、Profiler、dumpsys……到底什么场景用什么？

**💡 解答**：工具不是"越强越好"，是"**问题 → 工具**的直接映射"。记住"三问一答"：问题是什么 → 需要哪维度数据 → 哪个工具开销最低 → 够不够深。

| 场景 | 首选工具 | 补充 | 典型命令 |
|---|---|---|---|
| 线程数 / 状态 | `ps -T -p <pid>` | `/proc/<pid>/task` | `adb shell "ps -T -p $(pidof com.yc.live)"` |
| 锁竞争 | Perfetto `lock_contention` | `simpleperf stat` | 见 §3.1 方案③ |
| 调度延迟 | Perfetto sched_switch 泳道 | `cat /proc/sched_debug` | `atrace sched` |
| 进程清单 + PSS | `dumpsys procstats` | `dumpsys meminfo` | `adb shell dumpsys meminfo com.yc.live` |
| Binder 调用 | Perfetto Binder 分类 | `/sys/kernel/debug/binder/stats` | 见 §3.2 方案② |
| OOM / 被杀 | `logcat -b events | grep am_proc_died` | `dumpsys activity lmk` | - |
| CoW 共享率 | `cat /proc/<pid>/smaps` | 聚合 `Shared_*` 字段 | 见 §3.2 方案③ |
| 冷启动阶段 | Perfetto App Startup template | `am start -W` | `adb shell am start -W com.yc.live/.MainActivity` |
| ANR 现场 | `/data/anr/traces.txt` | Perfetto + sched_switch | `adb pull /data/anr/traces.txt` |

**▶▶ 四大核心工具的能力边界**

| 工具 | 核心能力 | 开销 | 盲区 |
|---|---|---|---|
| **Perfetto** | 全系统时序 trace（线程调度/Binder/syscall） | 中（3-5%） | 不适合线上常驻，需手动触发 |
| **simpleperf** | 性能计数器 + 栈采样（PMU/火焰图） | 中 | 需 symbol 还原、学习曲线陡 |
| **AS Profiler** | 可视化 CPU/内存/网络 | 低（1-3%） | 看不见 Native 栈、不支持 PMU |
| **dumpsys** | 系统服务的即时快照 | 极低 | 粒度粗、无时序 |

**▶▶ 工具组合经验公式**

```
"真机复现 + 可以插 USB" → Perfetto 抓 10s + simpleperf 补火焰图
"真机复现 + 用户的手机" → logcat + ANR trace + 事件日志
"线上监控" → /proc 常驻采集 + Perfetto 异常触发
"CI 回归" → Macrobenchmark 卡口（见 CPU 篇 §5.6）
```

### 3.5 面试锚点

**Q："线上怎么监控线程/进程问题？"**

**答题模板**（三类数据 + 回答三个问题 + 工程落地）：

> 我用"**线程 + 进程 + 交叉指标**"三位一体监控：
>
> **线程层**：常驻采集 `/proc/<pid>/task/*` 的线程数、state、CPU 时间（开销 < 1%，procfs 无磁盘 IO），告警阈值"单进程线程数 > 100"或"主线程 state 泳道 S/D 占比 > 10%"。
>
> **进程层**：`dumpsys procstats` 定期采集进程数、PSS、oom_score_adj，告警"子进程常驻 > 50MB"或"主进程被杀率 > 5%"。PSS 用来跨进程求和，USS 用来评估"杀掉能回收多少"。
>
> **交叉指标**：主线程 Binder 等待占比（> 5% 告警，> 15% 已 ANR 边缘）、Zygote CoW 共享率（< 40% 说明子进程写坏了共享页）、lmkd kill 速率（> 10 次/小时说明整机内存压力大）——这些单维度看不出来。
>
> **深挖**：出问题时触发一次 30 秒 Perfetto trace，抓齐 sched_switch + Binder + lock_contention 三类事件，离线用 ui.perfetto.dev 分析——主线程泳道色块变色点就是切换边界，点击看 "Wakeup from" 字段定位谁唤醒了谁。
>
> **防劣化**：CI 卡口跑核心场景的线程基准（线程数、切换率、Binder 调用次数）和进程基准（常驻 PSS、冷启动时长），不达标阻断合入——参考 CPU 篇 §5.6 左移预防治理。
>
> **工程落地**：
> - 这套监控上线半年抓到了 3 次主要问题——1 次 WebView 子进程泄漏（CoW < 20%）、1 次推送 Binder 心跳失控（waitRatio > 20%）、1 次新 SDK 没走统一池（线程/进程比 180）。
> - 定位均耗时 < 30 分钟，相比"用户舆情→排查"链路从 2 周缩短到小时级。
>
> **一句话总结**：**线上用 /proc 低开销采集 + 阈值告警，异常时用 Perfetto 深诊断，CI 卡口预防劣化**——三位一体才完整，缺一个归因都断链。

## 04、分层治理

> 全文核心章节——8 层治理按 ROI 排序。线程 4 层（主线程/同步/线程池/调度）+ 进程 4 层（数量/IPC/隔离/兜底），逐层展开。
>
> **本节骨架版**：Block 1 轮次先给结构、关键数据和心法，后续轮次补足代码示例、深潜块与详细步骤。

### 4.0 ROI 全景图（八层）

```
【线程四层】                              【进程四层】
      │                                        │
┌─────▼─────┐                            ┌─────▼─────┐

├───────────┤                            ├───────────┤

**铁律**：**先治线程四层，再治进程四层**。因为单进程下线程问题的收益确定性 > 多进程架构的隔离收益。

### 4.1 主线程减负

**🤔 疑惑**：主线程只有 16.6ms 的帧预算，但现实 App 的 Application.onCreate 可能一次性注入 20+ SDK，每个都想"抢头班车"。为什么不把它们全扔子线程？

**💡 解答**：主线程不是"CPU 密集所以慢"，是**"关键路径上必须排队的那条线"**——UI、输入、Choreographer 都在它上面。治理方针：**只保留"必须在主线程做的事"，其他全部挪走**。

**心法**：**把活挪走（异步化）> 把活变少（算法/缓存）> 把活推迟（IdleHandler）**。

**▶▶ 三条路 + 落地代码**

**路①：主线程 IO 异步化**（P0，收益 50-200%）

```kotlin
// ❌ Application.onCreate 典型反模式
override fun onCreate() {
    val sp = getSharedPreferences("app", MODE_PRIVATE)  // 首次 15-80ms 磁盘 IO
    val config = sp.getString("config", "{}")           // 阻塞主线程
    val user = Gson().fromJson(config, User::class.java)// 反序列化 5-15ms
}

// ✅ 两步改造：SP → MMKV + 异步预热
override fun onCreate() {
    MMKV.initialize(this)  // mmap 懒加载，首次 < 1ms
    AppInitializer.getInstance(this).initializeComponent(ConfigInitializer::class.java)
}

class ConfigInitializer : Initializer<User> {
    override fun create(context: Context): User {
        // 在 App Startup 的后台线程池里跑
        return Gson().fromJson(MMKV.defaultMMKV().getString("config", "{}"), User::class.java)
    }
    override fun dependencies() = listOf(MMKVInitializer::class.java)
}
```

**三件套工具链**：

| 工具 | 场景 | 关键价值 |
|---|---|---|
| **MMKV** | 替 SharedPreferences | 读写从磁盘 IO 变 mmap 内存写，首次 15-80ms → < 1ms |
| **App Startup** | 替散落的 Application 初始化 | 依赖图自动排序 + 后台初始化，冷启动 -200~500ms |
| **AnchorTask / α-Launcher** | 复杂依赖的任务调度 | 支持优先级、线程绑定、关键路径标记 |

**路②：布局优化（主线程 inflate/measure/layout 占大头）**

```xml
<!-- ❌ 深度 5 层嵌套，measure/layout 调用放大 2^5 倍 -->
<LinearLayout>
  <RelativeLayout>
    <LinearLayout>
      <FrameLayout>
        <ImageView/><TextView/>
      </FrameLayout>
    </LinearLayout>
  </RelativeLayout>
</LinearLayout>

<!-- ✅ ConstraintLayout 平级，measure 一遍过 -->
<androidx.constraintlayout.widget.ConstraintLayout>
  <ImageView app:layout_constraintStart_toStartOf="parent"/>
  <TextView  app:layout_constraintStart_toEndOf="@id/img"/>
</androidx.constraintlayout.widget.ConstraintLayout>

<!-- ✅ 懒加载：ViewStub 把非首屏控件延后到真正用时才 inflate -->
<ViewStub android:id="@+id/stub_detail" android:layout="@layout/detail_panel"/>
```

**布局优化三件套**：
- **ConstraintLayout**：扁平化层级（深度 5+ → 2 层）；
- **ViewStub**：首屏不显示的 View 延后 inflate；
- **AsyncLayoutInflater**：子线程 inflate 大布局（注意 ViewRoot 相关 API 仍需主线程）。

**路③：复杂计算切片（Choreographer 时间片）**

```kotlin
/**
 * 把一个耗时 50ms 的大任务切成 10 个 5ms 的小片，分散到多帧完成。
 * 关键：每片执行 ≤ 3ms（给 measure/layout/draw 留预算）。
 */
class SliceRunner(private val items: List<Work>) {
    private var cursor = 0
    private val sliceBudgetNs = 3_000_000L  // 3ms

    fun start() = Choreographer.getInstance().postFrameCallback(::runSlice)

    private fun runSlice(frameTimeNs: Long) {
        val deadline = SystemClock.elapsedRealtimeNanos() + sliceBudgetNs
        while (cursor < items.size &&
               SystemClock.elapsedRealtimeNanos() < deadline) {
            items[cursor++].doWork()
        }
        if (cursor < items.size) {
            Choreographer.getInstance().postFrameCallback(::runSlice)
        }
    }
}
```

**▶▶ 回扣案例：直播开播状态机**

| 阶段 | 操作 | 单步收益 | P95 帧时长 |
|---|---|---|---|
| 起点 | onCreate 同步跑 20 个 SDK | — | 80ms |
| T1 | SP → MMKV + App Startup 异步化 | -35ms | 45ms |
| T2 | 开播状态机 IdleHandler 切片 | -20ms | 25ms |
| T3 | ConstraintLayout 平级 inflate | -7ms | 18ms |

> 🔬 **深潜：IdleHandler 的"假延后"陷阱——为什么它可能把问题从 T0 推到 T0+1000ms**
>
> IdleHandler 是把活"推迟到 MessageQueue 空闲时"执行，很多团队把"初始化任务"全部塞 IdleHandler，结果**冷启动秒开，但用户 1 秒后点第一下才卡住**——问题没消失，只是改了位置。
>
> **MessageQueue 空闲条件**（源码 `next()` 返回前判定）：
>
> ```
> 空闲 = 当前没有同步消息 && 下一条同步消息还没到执行时间 && 屏障已清除
> ```
>
> **三条工程推论**：
>
> 1. **IdleHandler 不等于"后台线程"**——它仍在主线程跑，只是跑在"空闲时间片"。单个 IdleHandler 耗时超过 16ms 一样会让下一帧丢；
> 2. **IdleHandler 不是"延后到空闲"而是"下一次空闲时**"——用户快速滑动时，MessageQueue 永远不空，所有 IdleHandler 全部堆积，一旦停下滑动瞬间"雪崩执行"，造成一次 100ms+ 的 jank；
> 3. **工程做法**：IdleHandler 内部二次切片（见上 `SliceRunner`），且单个任务预算 ≤ 3ms；超重任务（> 10ms）必须用 `Dispatchers.Default` 真正扔子线程，不要只是"推迟"。
>
> **判定公式**：任务是否该用 IdleHandler？
>
> ```
> IF 单次耗时 < 3ms AND 必须主线程 AND 不紧急
>     → IdleHandler
> ELIF 单次耗时 < 3ms AND 可以子线程
>     → Dispatchers.Default（更可控）
> ELIF 单次耗时 ≥ 3ms
>     → 必须切片（主线程） 或 异步化（子线程）
> ```

### 4.2 同步原语治理

**🤔 疑惑**：锁是并发世界的"必要之恶"，但为什么同样的 `synchronized`，有的场景并发度 7、有的场景退化成 1？

**💡 解答**：锁的两条物理律——**粒度决定并发上限，持锁时间决定延迟下限**。

**心法**：**先问"这里真的需要锁吗"（能用不可变/线程局部就不要锁），再问"锁能不能再小"（粒度），最后问"锁内能不能更快"（持锁时间）**。

**▶▶ 四条路 + 落地代码**

**路①：锁粒度拆分**（1 大锁 → N 小锁）

```kotlin
// ❌ 一把大锁护整个 Map——所有线程在同一个 monitor 上排队
class GiftRegistry {
    private val gifts = HashMap<String, Gift>()
    @Synchronized fun add(id: String, g: Gift) { gifts[id] = g }
    @Synchronized fun get(id: String): Gift? = gifts[id]
}

// ✅ 分段锁 / ConcurrentHashMap——N 段并发写
class GiftRegistry {
    // ConcurrentHashMap 底层 CAS + 分段锁，8 线程并发写近线性扩展
    private val gifts = ConcurrentHashMap<String, Gift>()
    fun add(id: String, g: Gift) { gifts[id] = g }
    fun get(id: String): Gift? = gifts[id]
}

// ✅ 更极致：按 key hash 分 N 个独立 Map（当 key 空间可预估时）
class ShardedRegistry(private val shardCount: Int = 16) {
    private val shards = Array(shardCount) { HashMap<String, Gift>() }
    private val locks = Array(shardCount) { Any() }
    private fun shardOf(id: String) = (id.hashCode() and 0x7fffffff) % shardCount
    fun add(id: String, g: Gift) {
        val s = shardOf(id); synchronized(locks[s]) { shards[s][id] = g }
    }
}
```

**路②：持锁时间最小化**（锁内禁 IO，禁耗时计算）

```kotlin
// ❌ 持锁 IO——网络耗时 300ms 期间所有线程阻塞
synchronized(lock) {
    val resp = httpClient.execute(req)      // 网络 IO
    cache[key] = parse(resp.body)
}

// ✅ 锁外 IO，锁内只写 Map
val parsed = parse(httpClient.execute(req).body)  // 慢活放锁外
synchronized(lock) { cache[key] = parsed }         // 锁内只做赋值
```

**路③：锁 → 原子 → 无锁的阶梯**

| 场景 | 原语 | 性能 | 适用条件 |
|---|---|---|---|
| 复杂临界区 | `synchronized` / `ReentrantLock` | 1× | 多步非原子操作 |
| 单变量 CAS | `AtomicInteger` / `AtomicReference` | 5-10× | 低中竞争单变量 |
| **高竞争计数器** | **`LongAdder`** | **20-50×** | 多线程并发 `+1` |
| 读多写少 | `ReentrantReadWriteLock` / `StampedLock` | 2-5× | 读/写比 ≥ 10 |
| 无锁结构 | `ConcurrentLinkedQueue` / COW | 变化大 | 吞吐敏感、容忍弱一致 |

**路④：避免优先级反转**（高优线程等低优持的锁）

```kotlin
// 使用优先级继承互斥量——低优持锁时，JVM 自动把它提升到等待者的优先级
// Android 10+ 的 ART 实现对此有部分支持；
// 兜底方案：高优线程不要等用户态锁，用 Handler 消息把活发给低优线程做完回调。
```

> 🔬 **深潜：Linux futex 的两段式锁——为什么"看起来一样的 synchronized"性能差 100 倍**
>
> `synchronized` 在 ART 里的实现路径：
>
> ```
> 第一阶段（无竞争）：用户态 CAS 直接拿锁（1-2 ns）
>     ↓ CAS 失败（有竞争）
> 第二阶段（陷入内核）：futex_wait 系统调用（~1-2μs，含上下文切换）
> ```
>
> **性能分水岭就在"是否陷入内核"**：
>
> | 场景 | 竞争度 | 走哪段 | 单次成本 |
> |---|---|---|---|
> | 无竞争（99% 场景） | ~0 | 用户态 CAS | 1-2 ns |
> | 偶发竞争 | < 5% | 大部分 CAS + 偶尔 futex | ~10 ns |
> | 高竞争 | > 20% | 频繁 futex_wait | **1-2μs，100-1000×** |
>
> **三条工程推论**：
>
> 1. **"锁本身很快"是个误解——它快的是无竞争场景**。一旦竞争度 > 5%，futex 陷入内核的开销让你损失 2-3 个数量级；
> 2. **缩短持锁时间 ≈ 直接降低竞争度**。礼物墙推流锁从 "持锁 15ms" 砍到 "持锁 0.3ms"，竞争度 23% → 1.4%，走 futex 的概率骤降，平均锁等待 850ms → 18ms；
> 3. **锁粒度拆分 ≈ 把一个高竞争点拆成 N 个低竞争点**。4 把子锁各自竞争度 ~1%，总体系统行为从"扎堆进内核"回到"用户态飞快跑"，这就是分段锁为什么能近线性扩展的根因。
>
> **判据**：拿不定锁粒度要不要拆？看 `/proc/<pid>/status` 的 `voluntary_ctxt_switches`——它准确记录了"因等锁而主动让出 CPU"的次数。单位时间高于 5000 次就是信号。

### 4.3 线程池治理

**🤔 疑惑**：一个 App 为什么会有 200+ 个线程？打开 top -H 一片 `pool-N-thread-M`——到底谁在建这些池？

**💡 解答**：**每个 SDK 都想要自己的池**（网络、埋点、Push、热修、监控……12 个 SDK × 平均 8 线程 = 100+ 核心线程 + 弹性池）。治理方针：**全局统一线程池服务 + 按任务类型分三池**。

**心法**：**一个 App 应该有且只有少数几个"统一线程池服务"**——每 SDK 建自己的池是线程数爆炸的根源。

**▶▶ 三类池 + 配置黄金法则**

```
┌─────────────────────┬─────────────────────────────────┐
│ CPU 密集池          │ 核数 + 1                        │
│   JSON/解码/算法    │ 多了纯交切换税，少了核不满      │
├─────────────────────┼─────────────────────────────────┤
│ IO 密集池           │ 核数 × (1 + 等待时间/CPU时间)   │
│   文件/网络/DB      │ 实践值：20-30（压测拐点）       │
├─────────────────────┼─────────────────────────────────┤
│ 高优先级/关键路径   │ 4-8（固定小池）                 │
│   冷启动/首屏预取   │ 不接受排队，立即执行            │
└─────────────────────┴─────────────────────────────────┘
```

**▶▶ 落地：统一线程池服务骨架**

```kotlin
object UnifiedThreadPool {
    private val cpu = Runtime.getRuntime().availableProcessors()

    // CPU 池：有界队列 + CallerRunsPolicy（反压，不丢任务）
    val CPU: ExecutorService = ThreadPoolExecutor(
        cpu + 1, cpu + 1,
        60L, TimeUnit.SECONDS,
        LinkedBlockingQueue(100),              // 有界，避免 OOM
        namedFactory("cpu"),
        ThreadPoolExecutor.CallerRunsPolicy()  // 满了调用线程自己跑
    )

    // IO 池：弹性池 + 空闲回收
    val IO: ExecutorService = ThreadPoolExecutor(
        4, 20,
        30L, TimeUnit.SECONDS,
        SynchronousQueue(),                    // 直接交接，不排队
        namedFactory("io")
    )

    // 高优先级池：核心线程常驻 + 大核绑定
    val URGENT: ExecutorService = ThreadPoolExecutor(
        4, 4,
        0L, TimeUnit.MILLISECONDS,
        LinkedBlockingQueue(),
        PriorityThreadFactory("urgent", Process.THREAD_PRIORITY_URGENT_DISPLAY)
    )

    private fun namedFactory(tag: String) = object : ThreadFactory {
        private val n = AtomicInteger(0)
        override fun newThread(r: Runnable) = Thread(r, "yc-$tag-${n.getAndIncrement()}")
    }

    class PriorityThreadFactory(private val tag: String, private val priority: Int) : ThreadFactory {
        override fun newThread(r: Runnable) = Thread {
            Process.setThreadPriority(priority)
            r.run()
        }.apply { name = "yc-$tag" }
    }
}
```

**▶▶ 四件关键配置细节**

| 配置项 | 常见错误 | 正确做法 |
|---|---|---|
| **队列类型** | `LinkedBlockingQueue()` 无界 → OOM | 有界 100-500，溢出用 CallerRunsPolicy |
| **拒绝策略** | 默认 AbortPolicy → 抛异常崩业务 | CallerRunsPolicy 反压 / DiscardOldestPolicy |
| **线程命名** | 全叫 pool-N-thread-M → 排查黑盒 | 带业务 tag `yc-io-3`，trace 一眼识别 |
| **堆栈捕获** | 任务异常被 Executor 吞 | Runnable 外层包 try-catch + 上报 Crash |

**▶▶ 回扣案例**：礼物墙团队 12 个 SDK 各自线程池 → 迁移到统一池：

| 指标 | 迁移前 | 迁移后 | 变化 |
|---|---|---|---|
| 线程总数 | 187 | 52 | -72% |
| 上下文切换/秒 | 22K | 4.2K | -81% |
| 稳态 CPU 占用 | 18% | 11% | -39% |
| 冷启动时间 | 1.8s | 1.2s | -33% |

> 🔬 **深潜：Java 线程池的"核心线程优先"反直觉——为什么你的 corePoolSize=4, max=20 实际只用了 4 个线程**
>
> `ThreadPoolExecutor` 的任务入队规则（源码 `execute()`）：
>
> ```
> 1. 核心线程数未满 → 直接新建线程执行
> 2. 核心线程数已满 → 放进队列（关键！）
> 3. 队列也满了 → 新建非核心线程直到 max
> 4. max 也满了 → 走拒绝策略
> ```
>
> **反直觉的点**：**队列优先于非核心线程**，不是"先把所有线程用满再排队"。
>
> **问题复现**：配置 `core=4, max=20, queue=LinkedBlockingQueue(1000)`，期望并发 20，实际并发永远 4——因为任务永远先进 1000 容量的队列，队列永远不满，所以非核心线程永远不被创建。
>
> **三条工程推论**：
>
> 1. **想真正用上 max 线程，队列必须足够小**（或者用 SynchronousQueue）。IO 池推荐 `SynchronousQueue`：任务没线程接就立刻创建新线程；
> 2. **CPU 池用小有界队列**（100-500）：既避免 OOM，又让任务稍微排队（CPU 密集场景线程多了反而慢）；
> 3. **想要"永远优先创建线程"的行为**，可以反转：`core=max=20, queue=任意`——相当于固定大小池。这也是 Netty 的 EventLoopGroup 常用配置。
>
> **判据**：你的线程池"看起来线程数不够"？打印 `ThreadPoolExecutor.getPoolSize()` 和 `getQueue().size()` 一分钟采样一次。如果 queue 常年 > 0 而 poolSize == core，就是撞上了这个坑。

### 4.4 优先级与调度

**🤔 疑惑**：Android 的 `THREAD_PRIORITY_URGENT_DISPLAY` 是不是设了就飞？为什么我把工作线程调成 URGENT_DISPLAY 后主线程更卡了？

**💡 解答**：优先级不是"数值越低越优先"的简单游戏——**它是 Linux nice 值 + cgroup 分组 + CFS 虚拟运行时的综合结果**。乱用等于把系统调度器拖进"反负载均衡"。

**心法**：**关键路径升 QoS、后台任务降 QoS、锁启用优先级继承**——三件事决定调度公平性，其他时候不要碰优先级。

**▶▶ Android 优先级映射表**

| 常量 | nice 值 | cgroup 分组 | 适用场景 |
|---|---|---|---|
| `THREAD_PRIORITY_URGENT_AUDIO` | -19 | foreground + rt | 音视频实时流 |
| `THREAD_PRIORITY_URGENT_DISPLAY` | -8 | foreground | 主线程、Choreographer、RenderThread |
| `THREAD_PRIORITY_FOREGROUND` | -2 | foreground | 用户可感知的后台任务 |
| `THREAD_PRIORITY_DEFAULT` | 0 | foreground | 普通工作线程 |
| `THREAD_PRIORITY_BACKGROUND` | 10 | **background** | 日志上报、埋点、同步 |
| `THREAD_PRIORITY_LOWEST` | 19 | background | 空闲时的清理任务 |

**▶▶ 三条正确用法**

**用法①：关键路径线程升 QoS**

```kotlin
// Choreographer 回调线程（如果你 postFrameCallback 到自定义 Looper）
HandlerThread("render-looper").apply {
    priority = Thread.MAX_PRIORITY
    start()
    Handler(looper).post { Process.setThreadPriority(THREAD_PRIORITY_URGENT_DISPLAY) }
}

// 视频解码线程
decodeThread = Thread {
    Process.setThreadPriority(THREAD_PRIORITY_URGENT_AUDIO)  // RT 组，-19
    decodeLoop()
}.apply { name = "video-decode"; start() }
```

**用法②：后台任务降 QoS**

```kotlin
// 日志上报、埋点、同步——不要和主线程抢 CPU
val backgroundExecutor = Executors.newFixedThreadPool(2) { r ->
    Thread(r).apply {
        setDaemon(true)
        // 在任务里设，让它跑进 background cgroup（只能分到 ~10% CPU）
        setUncaughtExceptionHandler { _, e -> Log.e(TAG, "bg thread crash", e) }
    }
}
backgroundExecutor.submit {
    Process.setThreadPriority(THREAD_PRIORITY_BACKGROUND)  // nice=10 + cgroup bg
    uploadLogs()
}
```

**用法③：高竞争锁用优先级继承**（避免优先级反转）

```
场景：
  高优先级 UI 线程 ──等待──> 锁 ──被持有──> 低优先级后台线程
  期间来一个中优先级线程 ──> 把低优线程抢走 ──> 高优线程被卡 N 秒
                                                 ↑ "优先级反转"

破解：
  用户态：PI mutex（priority inheritance，Linux pthread 支持）
  Android：高优线程不要去等用户态锁，改用 Handler 消息异步化
```

**▶▶ 三条错误用法**（面试必考反例）

| 反例 | 原因 | 正确做法 |
|---|---|---|
| 所有工作线程全调 URGENT | 和主线程抢 CPU，主线程反而饿死 | 只升关键路径 2-3 个线程 |
| 把后台任务调 FOREGROUND | 进了 foreground cgroup，CPU 预算 100%，功耗飞升 | 保持 BACKGROUND |
| 设了优先级没设 cgroup | nice 值生效、cgroup 不变——还是和主线程挤 | 关键是写 `/dev/stune/foreground/tasks` |

**▶▶ 回扣案例**：礼物墙推流 + Choreographer + 后台上报三线并存：

| 优化前 | 优化后 | 效果 |
|---|---|---|
| 推流/Choreographer/上报全 DEFAULT | 推流 URGENT_AUDIO、Choreographer URGENT_DISPLAY、上报 BACKGROUND | 主线程 P95 -22ms |
| 高竞争锁等待抖动 | 高优线程不等用户态锁，改 Handler 消息异步化 | 优先级反转导致的 ANR 归零 |

> 🔬 **深潜：nice 值不是"调度优先级"，是"CPU 时间片权重"——为什么 nice=0 和 nice=10 的差距是 10 倍不是 10%**
>
> Linux CFS（完全公平调度器）用 **vruntime（虚拟运行时）** 决定下一个跑谁：每个任务按"运行时间 × 权重倒数"累加 vruntime，调度器永远挑 vruntime 最小的跑。
>
> **nice → 权重映射表**（内核 `sched_prio_to_weight[]` 节选）：
>
> | nice | 权重 | 相对 nice=0 的 CPU 份额 |
> |---|---|---|
> | -10 | 9548 | 9.4× |
> | 0 | 1024 | 1× |
> | 10 | 110 | **1/9.3** |
> | 19 | 15 | **1/68** |
>
> **三条工程推论**：
>
> 1. **nice 每差 1，CPU 份额差 ~1.25 倍**（内核设计规则）。nice=0 vs nice=10 不是"10% 的差距"，是**近 10 倍的差距**——所以后台任务调 nice=10 之后它在和前台线程竞争时**实际只能分到 10% 的 CPU**；
> 2. **CFS 保证"长时间公平"而非"实时响应"**——nice=-10 的线程并不保证"立刻跑"，只是在**长时间观测窗口里**拿到 9.4 倍 CPU 份额。要实时响应得用 SCHED_FIFO/SCHED_RR（Android 只对 audio 开放）；
> 3. **cgroup 和 nice 是乘法关系**：background cgroup CPU share = 10%，组内 nice=0 的线程拿组内 100% ≈ 整机 10%；组内 nice=10 的线程拿组内 10% ≈ **整机 1%**。所以 "日志上报半小时才传完" 常常是双重 nice 的叠加结果。
>
> **诊断**：想知道你的线程"实际分到多少 CPU"？读 `/proc/<pid>/task/<tid>/schedstat`，第一列是累计 CPU 运行时间（ns），第二列是累计等待运行时间——两者比值告诉你"真实优先级"。

### 4.5 进程数量收敛

**🤔 疑惑**：几年前互拉保活是显学，为什么现在的"最佳实践"反过来是——**删进程**？

**💡 解答**：Android 11+ 之后，系统对保活家族（JobScheduler 外的后台 Service、互拉、FCM 旁路）**全面围剿**：

| Android 版本 | 变化 | 对保活影响 |
|---|---|---|
| 8.0 | 后台 Service 执行受限 | 常驻 Service 变"短命鬼" |
| 10 | 后台启动 Activity 禁止 | 互拉拉不起来 |
| 11 | 可见前台服务 FGS 类型强约束 | 伪装前台服务被杀 |
| 12 | 前台服务启动限制 + 精确闹钟权限 | 拉活链路大面积失效 |
| 13 | 通知权限运行时授权 | 推送到达率继续下滑 |
| 14+ | FGS 类型 + lifecycle 二次约束 | 保活成本/收益比彻底倒挂 |

**结论**：**保活不是技术优化，是系统策略对抗**——投入越大，被杀越快。治理方针反过来——**删减非必要进程**。

**心法**：**进程治理的最大杠杆是删除非必要进程，不是优化它们**——每删 1 个常驻进程省 15-70MB PSS，相当于内存优化半个月的工作量。

**▶▶ 决策树**（面试直接背）：

```
进程 X 要不要独立？
│
├─ 高崩溃风险（WebView / 音视频 / NDK 第三方 SDK）
│     ↓ 价值：崩溃隔离，主进程不受牵连
│     → ✅ 拆（内存成本可接受，稳定性收益大）
│
├─ 常驻但低活性（Push / 同步 / 守护）
│     ↓ 问题：常年挂机只为"活着"，PSS 150-300MB
│     → ❌ 删或接 FCM / HMS Push / 系统闹钟
│
├─ 临时高内存消耗（相机 / 扫码 / 图像处理）
│     ↓ 评估：短生命周期 ≠ 必须拆
│     → ⚠️ 不拆（用完 recycle，开进程成本高于省内存）
│
└─ 核心业务（Launcher / 聊天主流程 / 直播间）
      → ❌ 永不拆（任何跨进程调用都在增加 ANR 风险）
```

**▶▶ 四类常见"该删"进程**

| 进程类型 | 原始目的 | 现代替代方案 | PSS 占用 |
|---|---|---|---|
| `:push` 自建推送 | 保活接推送 | FCM / HMS Push / UniPush | 50-120MB |
| `:daemon` 守护进程 | 互拉主进程 | **直接删——A11+ 失效** | 20-80MB |
| `:keepalive` 拉活 | 1 像素 / 系统通知欺骗 | 删——用户厌恶，政策风险 | 30-100MB |
| `:sync` 后台同步 | 定时数据同步 | WorkManager + 系统闹钟 | 40-150MB |

**▶▶ 测量方法：先量再删**

```bash
# 1. 看每个进程的 PSS 占用（真实内存成本）
adb shell dumpsys meminfo com.yc.live | grep "TOTAL PSS"

# 2. 看进程是否真有价值（CPU 时间占比）
adb shell top -p $(pidof com.yc.live:push) -b -n 10

# 3. 看进程被杀频率（lmkd kill log）
adb shell logcat -b events -d | grep "am_proc_died" | grep "com.yc.live:push"
```

**▶▶ 回扣案例**：某金融 App 删除 `:push` + `:daemon` + `:keepalive` 三进程：

| 指标 | 删前 | 删后 | 变化 |
|---|---|---|---|
| 常驻 PSS | 450MB | 240MB | **-47%** |
| 主进程被杀率 | 22% | 3% | **-86%** |
| 冷启动平均耗时 | 1.8s | 1.3s | -28% |
| 7 日用户留存 | 68% | 70% | +2pp（LMK 低了） |

> 🔬 **深潜：lmkd 的进程"价值分"算法——为什么你删的进程越多，保留的进程反而更难被杀**
>
> Android 的 lmkd（Low Memory Killer Daemon）按 **oom_score_adj** 杀进程：数值越大越先死。看起来是"按进程"评价，但实际是**按 App 总占用评价**：
>
> ```
> 每个 App 的"系统评分"大致 =
>     Σ (该 App 所有进程的 PSS) × 后台时长系数
>     ÷ 用户感知活跃度（前台/可见/服务可见/缓存）
> ```
>
> **三条工程推论**：
>
> 1. **进程多的 App 整体被杀概率更高**——你的 `:push` 虽然 oom_score 低，但它占的 PSS 算在整个 App 账上，让主进程的"相对价值"下降。删掉 `:push` 后主进程反而更安全；
> 2. **保活家族是"自杀式"的**——`:daemon` 本意是"主进程死了拉活"，但它分走 50MB 后，主进程被杀门槛也提高了 50MB，反而更容易先死。lmkd 杀的是**整个 App 组合**，不是单个进程；
> 3. **缓存进程阶梯是最后的保护伞**——Android 13+ 分 LRU 的 cache 阶梯（empty > cached > visible > perceivable）。前台→后台→缓存三级降级每级 ~5-10 分钟。**让 App 优雅进缓存比"扛着不走"活得长**——干完活立刻 `moveTaskToBack(true)` 让系统认为你让贤了。
>
> **诊断**：`adb shell dumpsys activity oom | grep -A 2 com.yc.live` 看每个进程的 `oom_adj` 和 `oom_score_adj`。前台 0、可见 100-200、后台 400-600、缓存 900+——数值跳变就是你被降档了。

### 4.6 IPC 优化

**🤔 疑惑**：Binder 是 Android 的 IPC 标杆，号称"一次拷贝"。为什么我这边高频心跳 Binder 还是把主线程打满？

**💡 解答**：Binder 的"一次拷贝"是和"两次拷贝"（Linux 传统 socket）对比的，**不等于"零成本"**。真实开销拆解：

```
单次 Binder 跨进程调用成本（Pixel 7, A13）：
  ┌──────────────────────────────────────────┐
  │ 用户态 → 内核态陷入        ~0.3μs        │
  │ 参数 marshal (Parcel)      ~0.5-2μs      │
  │ 一次 copy_from_user        ~0.3-1μs      │  ← "一次拷贝"
  │ 服务端 Binder 线程唤醒     ~0.5-1μs      │
  │ 执行业务逻辑               (业务时间)    │
  │ 结果回传 + 两次调度        ~1-2μs        │
  └──────────────────────────────────────────┘
       合计：3-6μs（空调用），每次都是实打实的 CPU
```

**心法**：**IPC 不是免费的——1-5μs 单次成本在高频下吃掉主线程 CPU 的 20%+**。高频 + 跨进程 = 性能毒药。

**▶▶ 四条路**

**路①：高频心跳批处理**（最高 ROI）

```kotlin
// ❌ 直播推流心跳 35 次/秒跨进程 Binder
override fun onPullHeartbeat() {
    pushService.reportHeartbeat(timestamp)  // 一次 Binder 调用
}

// ✅ 本地缓冲 5 秒合并一次
private val heartbeats = ArrayDeque<Long>(256)
override fun onPullHeartbeat() {
    heartbeats.add(timestamp)
    if (heartbeats.size >= 10 || now() - lastFlush > 5000) {
        pushService.reportHeartbeatBatch(heartbeats.toLongArray())  // 一次 Binder
        heartbeats.clear(); lastFlush = now()
    }
}
```

**量化收益**：35 次/秒 → 0.2 次/秒（**175× 降频**），主线程 CPU -14%。

**路②：大数据走共享内存**（> 1KB 就该考虑）

```kotlin
// ❌ 大 Parcel 跨进程——Binder 限制 1MB，接近限制时性能骤降
val img = ByteArray(800 * 1024)  // 800KB 图片
service.decode(img)              // 一次 Binder，内核态拷贝 800KB，~2ms

// ✅ MemoryFile / SharedMemory（API 27+）
val shm = SharedMemory.create("decoder-buf", 800 * 1024)
val buf = shm.mapReadWrite()
buf.put(img)
service.decodeFromShm(shm.describeContents())  // 只传 fd，<10μs
shm.close()  // 服务端用完要主动关
```

**什么时候必用共享内存**：

| 数据大小 | Binder 开销 | 共享内存开销 | 推荐 |
|---|---|---|---|
| < 1KB | ~3-6μs | 建立 ~50μs | Binder |
| 1-10KB | ~10-30μs | 建立 ~50μs | 看频率 |
| 10-100KB | ~100-500μs | ~50μs 建立 + 零拷贝读 | **共享内存** |
| > 100KB | 风险区（接近 1MB 上限） | 不变 | **必须共享内存** |

**路③：查询类接口端上缓存 + 版本号**

```kotlin
// ❌ 每次用都查
val config = remoteService.getUserConfig()  // 一次 Binder

// ✅ 版本号 + 本地缓存
private var cachedVersion = -1L
private var cachedConfig: UserConfig? = null
fun getConfig(): UserConfig {
    val remoteVersion = remoteService.getConfigVersion()  // 轻量 Binder
    if (remoteVersion != cachedVersion) {
        cachedConfig = remoteService.getUserConfig()      // 真正跨进程取
        cachedVersion = remoteVersion
    }
    return cachedConfig!!
}
```

**路④：异步 Binder（`oneway`）**

```aidl
// AIDL 定义——oneway 表示客户端不等结果
interface IPushService {
    oneway void reportHeartbeat(long timestamp);  // Fire-and-forget
    UserConfig getConfig();  // 同步，有返回值
}
```

**oneway 的两面性**：
- ✅ 客户端不阻塞（主线程调用也不卡）；
- ⚠️ 服务端消息按 Binder 线程池排队，**可能延迟到达甚至丢**（线程池 ≤ 16）；
- ❌ 不能有返回值；
- ❌ 服务端异常不传递。

**适用**：心跳、日志、埋点等"丢了也不致命"的场景。

> 🔬 **深潜：Binder 线程池的"16 条命"——为什么你的 oneway 调用会被丢**
>
> 每个 Android 进程的 Binder 服务端有**固定 16 个 Binder 线程**（源码 `ProcessState::setThreadPoolMaxThreadCount(DEFAULT_MAX_BINDER_THREADS = 15)` + 主线程 = 16）。所有传入的 Binder 调用都在这 16 个线程里排队处理。
>
> **过载场景**：你的 ServerService 收到 100 个并发 oneway，前 16 个在跑，剩下 84 个排队。如果你的服务端处理单次要 200ms，队尾请求要等 **200ms × (84/16) = 1050ms** 才被处理——**用户感觉"数据丢了"实际是 1 秒后才到**。
>
> **三条工程推论**：
>
> 1. **oneway 不等于"异步无开销"**——它在客户端是异步，服务端仍然要走 16 条命的线程池。服务端处理慢，整条链都挤堵；
> 2. **Binder 线程池上限不可改**（framework 层固定）——所以服务端的单次调用必须快（< 10ms）。超过的话用服务端自建线程池接住 Binder 调用后立刻返回；
> 3. **诊断线程池饱和**：`adb shell cat /sys/kernel/debug/binder/stats` 看每个进程的 "ready threads" 和 "requested threads"，前者归零意味着线程池饱和中。
>
> **工程做法**：高吞吐 Binder 服务（如推流上报）在服务端用 `Executor` 异步接收：
>
> ```kotlin
> // 服务端——Binder 线程 100ns 内把活扔走，立刻释放
> override fun reportHeartbeatBatch(ts: LongArray) {
>     backgroundExecutor.submit { processBatch(ts) }  // 异步处理
>     // 立刻 return，Binder 线程归还
> }
> ```

### 4.7 进程隔离与保活

**🤔 疑惑**：既然 §4.5 说"进程越少越好"，为什么 WebView 还要独立进程？这不自相矛盾吗？

**💡 解答**：不矛盾——"少"是针对**低价值常驻进程**，"独立"是针对**高风险业务**。两者的分水岭是**崩溃隔离价值 vs 内存成本**的 ROI。

**心法**：**Android 11+ 之后传统互拉保活已失效，别再花钱养僵尸进程**——保活的 ROI 是负的（投入越大，被杀越狠，用户越反感）。

**▶▶ 合理隔离的三个场景**

**场景①：WebView 独立进程**（强推荐）

```xml
<!-- AndroidManifest.xml -->
<activity android:name=".WebViewActivity"
          android:process=":web" />
```

**价值**：
- Chromium 内核 Native 崩溃不传染主进程（WebView 崩溃是 Top 3 Native crash 源）；
- WebView 内存泄漏独立隔离，关闭 Activity 后杀 `:web` 进程即可完全回收；
- 两次 WebView 启动间可清空 `:web` 的所有缓存，不污染主进程。

**代价**：
- `:web` 独立进程 Zygote fork 后首次 ~80-200MB 常驻；
- 主↔WebView 跨进程通信（JSBridge）走 Binder，单次 2-5μs。

**适用判据**：你的 App 若严重依赖 WebView（H5 占 50%+ 页面），**必拆**。

**场景②：音视频/NDK 密集进程独立**

```xml
<service android:name=".media.PlayerService"
         android:process=":player" />
```

**价值**：解码器、游戏引擎、音视频处理这类第三方 Native SDK 稳定性往往不如 Java 代码，独立进程确保**它崩了主进程还能提示"视频播放失败"**。

**适用判据**：第三方 Native SDK 占比高、历史 Native crash 率 > 0.1%。

**场景③：高内存临时消耗的"用完即走"进程**

```xml
<!-- 图像处理服务，用完主动 killProcess -->
<service android:name=".ImageProcessService"
         android:process=":imgproc"
         android:isolatedProcess="true" />
```

**特点**：`isolatedProcess="true"` 让进程**无 Context、无权限、无存储访问**，纯计算容器。用完 `Process.killProcess(Process.myPid())`。

**▶▶ 保活家族"直接删"清单**

| 保活手段 | A11+ 是否有效 | 现代替代 |
|---|---|---|
| 1 像素 Activity | ❌ 失效（Dialog 转 PiP 限制） | 删 |
| 前台服务伪装 | ❌ A12 FGS 类型强约束 | 用正当的 `foregroundServiceType` |
| JobScheduler 持续拉起 | ⚠️ 配额限制 | 用 WorkManager |
| 系统应用拉活 | ❌ 后台启动受限 | 删 |
| 推送拉活 | ⚠️ FCM/HMS 系统推送仍可 | 接 FCM/HMS 系统推送 |
| `:daemon` 守护进程 | ❌ 彻底失效 | 删 |

**▶▶ 进程保活的"替代品"思路**

```
不要问"怎么让进程不死"，要问"用户需要的能力怎么用系统接口实现"：

需求：定时唤起 → WorkManager / AlarmManager（系统闹钟）
需求：接收推送 → FCM / HMS Push（系统级，不杀）
需求：后台定位 → ForegroundService type=location（正当）
需求：音乐播放 → ForegroundService type=mediaPlayback（正当）
需求：下载任务 → ForegroundService type=dataSync（正当）
```

> 🔬 **深潜：从"保活为王"到"让贤为王"——Android 后台治理十年思想转变**
>
> 回顾 2015-2025 保活/后台治理的拉锯：
>
> | 时期 | 开发者策略 | 系统反制 | 结局 |
> |---|---|---|---|
> | 2015-2017 | 互拉 / 1 像素 / 系统 Service 旁路 | 弱约束 | 保活一度 90%+ |
> | 2018-2020 | 推送 KeepAlive / Account Sync 旁路 | O 后台限制 + P 空闲桶 | 保活 60% |
> | 2021-2023 | FGS 伪装 / foregroundType 滥用 | A11 后台启动限制 + A12 FGS 强类型 | 保活 30% |
> | 2024-2026 | 几乎绝迹 | A13-A14 lifecycle 二次约束 | **保活 < 10%** |
>
> **三条工程推论**：
>
> 1. **系统策略的变化速度 > 保活技术的迭代速度**——你每做一个新"保活"方案，Google 下一个版本就封死。投入是沉没成本；
> 2. **用户感知是终局裁判**——国内 App 已经形成"后台耗电高 = 流氓应用"的集体印象，保活技术即使有效也等于主动找差评。保活不再是技术问题，是产品问题；
> 3. **"让贤为王"是新范式**——核心是：**该让 App 死就痛快死，但 1 秒内让它满血复活**。这把 7 天留存从"看谁活得久"变成"看谁回来得快"，拼的是冷启动优化（§4.8 + 冷启动篇）而非保活技巧。谁冷启动 500ms，谁就"看起来没死"。

### 4.8 兜底与重启

**🤔 疑惑**：如果不保活，App 被杀之后用户再点图标，看到的是"重新打开"的割裂感——怎么保证"看起来没死过"？

**💡 解答**：**接受"进程必被杀"的现实，把"快速恢复 + 状态恢复"做到比"防被杀"更极致**——用户感知的不是"进程没死"，是"状态没丢"。

**心法**：**1 秒内重启 + 状态恢复 > 永不被杀**。两者投入产出比差一个数量级。

**▶▶ 四招组合拳**

**招①：被杀后 < 800ms 冷启动恢复**

```kotlin
// LaunchActivity 保持极简——不做任何耗时初始化
class LaunchActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // 立刻展示上次 UI 的截图占位
        setContentView(R.layout.splash_fast)
        // 实际初始化走 App Startup 后台队列
        AppInitializer.getInstance(this).initializeComponent(FastPathInitializer::class.java)
        // 恢复用户到他离开时的位置
        startActivity(StateRestorer.lastRoute(this))
        finish()
    }
}
```

**配套**：Baseline Profile 覆盖 LaunchActivity 全链路（见 CPU 篇 §5.1 深潜）。

**招②：状态全持久化**（真正做到"回到现场"）

```kotlin
// Fragment / Activity 的 onSaveInstanceState 只能存小数据，大状态要主动持久化
class LiveRoomViewModel : ViewModel() {
    init {
        viewModelScope.launch {
            // 页面挂起时每 2s 持久化一次关键状态
            while (isActive) {
                delay(2000)
                StateDB.saveLiveRoom(LiveRoomState(
                    roomId = currentRoomId,
                    scrollY = currentScroll,
                    draftText = currentDraft,
                    sendingGifts = pendingGifts.toList()
                ))
            }
        }
    }
}

// 冷启动恢复：读 StateDB，一跳回到用户离开时的现场
```

**哪些状态必存**（按优先级）：
1. 当前路由 / 页面栈（用户期望"回到那一页"）；
2. 列表滚动位置（用户期望"回到那条"）；
3. 输入草稿（用户期望"没白打"）；
4. 登录态 / 会话（避免重新登录）；
5. 正在进行的任务（上传、下载、送礼）。

**招③：异常保护 + 主动重启**

```kotlin
// 主线程发生 Looper 异常时，不要直接退出，而是重启到安全页
object SafeLoopHandler {
    fun install() {
        Handler(Looper.getMainLooper()).post {
            while (true) {
                try {
                    Looper.loop()
                } catch (e: Throwable) {
                    Log.e(TAG, "Main thread crash, restart to safe page", e)
                    StateDB.markCrashRestart()
                    val intent = Intent(context, LaunchActivity::class.java)
                        .addFlags(Intent.FLAG_ACTIVITY_CLEAR_TOP or Intent.FLAG_ACTIVITY_NEW_TASK)
                    context.startActivity(intent)
                    Process.killProcess(Process.myPid())
                }
            }
        }
    }
}
```

（详见 CPU 篇 §5.4 ④ 的异常保护四招）

**招④：主进程不在时子进程不干关键活**

```kotlin
// :push 子进程发现主进程挂了，自己也主动退，避免"主死子活"的鬼魂进程
class PushService : Service() {
    private val mainChecker = Handler(Looper.getMainLooper())
    override fun onCreate() {
        super.onCreate()
        mainChecker.postDelayed(object : Runnable {
            override fun run() {
                if (!isMainProcessAlive()) {
                    Log.i(TAG, "Main process gone, suicide")
                    stopSelf()
                    Process.killProcess(Process.myPid())
                }
                mainChecker.postDelayed(this, 30_000)  // 每 30s 查一次
            }
        }, 30_000)
    }

    private fun isMainProcessAlive(): Boolean {
        val am = getSystemService(ActivityManager::class.java)
        return am.runningAppProcesses?.any { it.processName == packageName } == true
    }
}
```

**▶▶ 回扣案例**：某金融 App 全套"兜底"落地后：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 主进程被杀后恢复时间 | 2.3s | **680ms** |
| 用户感知崩溃率（卡顿/白屏/弹错） | 1.2% | **0.15%** |
| 7 日 DAU 留存 | 68% | **72%** |
| 用户舆情"闪退"反馈 | 月 230 条 | 月 18 条 |

> 🔬 **深潜：为什么"快速冷启动 + 状态恢复"是防杀的真正答案——冷启动时间与保活效果的"倒置相关"**
>
> 一个反直觉的事实：**冷启动越快的 App，用户感知的"崩溃次数"越少**，哪怕实际被杀次数一样。
>
> **用户心智模型**：
>
> ```
> 冷启动 < 1 秒 + 回到原页     → 用户认为"没发生过"
> 冷启动 1-3 秒 + 回到首页     → 用户认为"刷新了"
> 冷启动 > 3 秒 + 任何提示     → 用户认为"闪退了"
> ```
>
> **三条工程推论**：
>
> 1. **冷启动优化就是最好的保活**——500ms 的冷启动让用户感知不到被杀，等同于 100% 保活成功率，而成本只有保活的 1/10；
> 2. **状态恢复的真实价值 > 保活**——用户不在意进程是否活着，在意**他离开时的"现场"还在不在**。做好状态持久化比做好保活更贴近用户诉求；
> 3. **"接受死亡"反而是最大的性能自由**——不保活意味着后台可以彻底不做任何事（电量 -30%+、功耗 -40%+），用户不会卸载，反而因为"耗电低"打五星。保活是"眼前的小胜，长期的大败"。
>
> **数据佐证**：某头部 App AB 测试去掉保活后 7 日留存 +2.1pp（有统计学意义），同时商店差评中"耗电"关键词从月 3200 条降到 180 条——这是任何保活方案都做不到的"反向性能收益"。

### 4.9 ROI 排序

| 优先级 | 操作 | 收益区间 | 开发成本 |
|---|---|---|---|
| P0 | 主线程 IO 异步化 | 50-200% | 低 |
| P0 | 删除非必要进程 | 内存 -30~50% | 中（需架构调整） |
| P1 | 统一线程池 | 线程数 -60%、切换率 -80% | 低 |
| P1 | 锁粒度拆分 | 锁等待 -90% | 中 |
| P2 | IPC 批处理 + 缓存 | 跨进程开销 -70% | 中 |
| P2 | WorkManager 窗口化 | 整机功耗 -10% | 低 |
| P3 | 优先级 / cgroup 分组 | 主线程 P95 -20% | 低但调优繁 |
| P3 | 快速重启机制 | 用户感知崩溃 -80% | 高 |

### 4.10 面试锚点

**Q："你做过哪些线程/进程优化？"**

答题模板（八层串联 + 双案例数据）：

> 按"**线程四层 + 进程四层**"的 ROI 顺序做过：
>
> **线程侧**：
> - 主线程减负：开播状态机 IdleHandler 切片，P95 帧时长 80 → 18ms；
> - 同步治理：推流锁从 1 把拆成 4 把 + 禁锁内 IO，等待 P99 850 → 18ms；
> - 线程池：12 个 SDK 各自池 → 统一服务（CPU=核数+1 / IO=20 / 高优先=4），线程数 187 → 52，切换 22K → 4.2K/s；
> - 调度：推流线程升 URGENT_DISPLAY + 锁启用优先级继承。
>
> **进程侧**：
> - 数量收敛：删除 Push/守护/拉活 3 个进程，PSS 450 → 240MB（-47%）；
> - IPC 优化：主↔WebView 心跳批处理 + 大数据走共享内存；
> - 隔离保活：WebView 保留做崩溃隔离，保活全删（A11+ 已失效）；
> - 兜底：被杀后 800ms 重启 + 状态全恢复。
>
> 结果：直播卡死率 7.3% → 0.3%，主播首屏 4.8s → 1.0s；金融 OOM 率 4.8% → 0.6%，主进程被杀率 22% → 3%。
>
> 核心教训：**线程优化先治 on-CPU 和 off-CPU 的平衡，进程优化先问"真的需要吗"**——80% 的多进程架构是过度设计。

## 05、原理深潜

> 九大全链路，各自从"物理模型 → 代码路径 → 典型病灶"展开。
>
> **本节骨架版**：Block 1 轮次先给九大全链路的核心模型图与关键结论，后续轮次补足深潜块、代码示例与跨平台对照。

### 5.1 主线程调度全链路

**Android UI Thread** = Looper + MessageQueue + Choreographer，核心时序：

```
VSYNC 信号 → Choreographer.postCallback → MessageQueue 入队
         → Looper.loop 取 Message → doFrame → measure/layout/draw → OpenGL/HWUI
```

**关键病灶**：Message 队列堆积、同步 Barrier 阻塞、Choreographer 时间片超支。

### 5.2 线程池全链路

**ExecutorService 核心路径**：

```
submit → BlockingQueue 入队 → Worker 线程 take → run
            │                    │
            └─ 队列满 → 拒绝策略   └─ IDLE 超时回收 or 保留 corePool
```

**三类池差异**：`FixedThreadPool`（无界队列有 OOM 风险）、`CachedThreadPool`（线程数无上限）、`ScheduledThreadPool`（定时类）。

**协程 vs 线程池**：协程调度器底层仍是 ForkJoinPool，CPU 密集并不加速（见 §00.3）。

### 5.3 同步原语全链路

**mutex（futex 底层）**：无竞争 ~30ns，有竞争 1-5μs（陷入内核）；
**spinlock**：忙等 CPU，适合 < 1μs 的极短临界区；
**读写锁**：读多写少，但 CAS 高竞争退化为锁；
**CAS/原子**：无锁但有 ABA 问题，高竞争退化。

**死锁四要素**：互斥 / 持有并等待 / 不剥夺 / 循环等待——破解任一即可。

### 5.4 优先级与 QoS 全链路

**Linux CFS 调度器**：按**虚拟运行时间（vruntime）**公平分配 CPU，nice 值影响 vruntime 增速。

**Android 优先级映射**：`THREAD_PRIORITY_*` → nice → cgroup 分组。

**优先级反转**：低优先级持锁 → 高优先级等 → 中优先级抢占低 → 高优先级永远等。**破解：优先级继承互斥量（Priority Inheritance Mutex）**。

### 5.5 协程全链路

**Kotlin 协程**：编译期把 `suspend fun` 改写成**状态机**（CPS 变换），挂起 = 保存 continuation 返回，恢复 = 跳回状态机 case——**无需保存寄存器现场**，这是 1/100 切换成本的来源。

**调度器**：`Dispatchers.Default`（CPU 密集，N=核数）、`Dispatchers.IO`（IO 密集，64 线程池）、`Dispatchers.Main`（主线程 Looper）。

### 5.6 进程创建全链路

**Android Zygote fork**：
```
Zygote 预加载 framework/.so → fork(SyscallEntry) → clone 共享页表 →
AppRuntime.start → ActivityThread.main → bindApplication → onCreate
```

**CoW 边界**：详见 §01.2 深潜。

### 5.7 IPC 通信全链路

**Binder** = 一次拷贝 + 内核中转 + 异步线程池（Binder thread）。

**路径**：
```
Client Proxy.transact → 用户态 → ioctl → Binder Driver 一次 copy_from_user →
Server Binder thread 读 → Server.onTransact → 结果再 copy 回去
```

**为什么是"一次拷贝"**：Binder Driver 把目标进程的接收缓冲区**预 mmap 到内核**，发送方 copy 到内核时直接落到接收方的内存映射里，省了"内核 → 接收方"那一次。

### 5.8 共享内存全链路

**Android `MemoryFile`/`ASharedMemory`** 底层是 **ashmem**（Android Shared Memory），`mmap` 到多进程地址空间。

**零拷贝**但：
1. 首次建立映射仍需 syscall；
2. 需要应用层**同步**（否则读写竞争）——通常配合 Binder 做元数据同步。

### 5.9 进程生命周期全链路

**oom_score_adj 分档**：
```
0           系统服务 / Launcher
0-100       前台 Activity / 前台 Service
100-500     可见 / 感知服务
500-900     后台 Service
900+        空进程
```

**lmkd 从高到低杀**，直到压力缓解。详见内存篇 §5.4 深潜。

## 06、高频追问

> 13 个"陷阱题"——每题按"问题 → 直觉答案 → 为什么错 → 正确答案 → 延伸追问"四段式展开。

### Q1 线程池无界队列为什么危险

- **直觉答案**：队列无界意味着"再多任务都能接住"，是个保险策略。
- **为什么错**：无界队列把 OOM 时间从"小时级"压缩到"秒级"——内存泄漏可能一天才积累到 OOM，但队列堆积只需几秒。更隐蔽的是：无界队列会让 `ThreadPoolExecutor` 的 `max` 参数**永远不生效**（见 §4.3 深潜），你以为自己是"弹性池"，实际是"固定 core 大小 + 无限队列"。
- **正解**：队列必须有界，容量 100-500 够用；配 `CallerRunsPolicy` 做反压——队列满时让调用线程自己跑，相当于天然限流器。生产环境还要给队列加监控：定期打 `getQueue().size()`，> 50% 容量就告警。
- **追问**：那 `newCachedThreadPool` 为什么还有人用？→ 短生命周期辅助池可以，但必须加线程数上限（通过 `setMaximumPoolSize`），否则 500 个任务瞬时到达 → 500 个线程 → OOM。

### Q2 自旋锁什么时候反而比互斥锁快

- **直觉答案**：自旋锁一直占 CPU "空转"，怎么可能比"主动让出 CPU"的互斥锁快？
- **为什么错**：忽略了**上下文切换的真实成本**。互斥锁陷入内核态要 1-2μs，加上调度器找下一个线程、cache 冷启动，真实代价 5-10μs。如果临界区本身只执行 500ns，自旋等 500ns 比切出去再切回来便宜 10 倍以上。
- **正解**：临界区 < 1μs 用自旋锁、1-10μs 用混合锁（先自旋 N 次再陷入）、> 10μs 用互斥锁。JDK 的 `synchronized` 从 Java 6 开始就是"偏向锁 → 轻量级锁（自旋）→ 重量级锁（futex）" 的升级路径，这是业界最佳实践。
- **追问**：那自旋锁是不是单核就不能用？→ 对，单核场景自旋等于让持锁线程无法被调度，100% 死循环。所以 Linux 内核的自旋锁实现在单核下自动退化为"禁用抢占"。Android 用户态场景几乎永远多核，所以可以放心用。

### Q3 优先级反转怎么破

- **直觉答案**：高优线程等锁时抢占系统资源，等到就行了。
- **为什么错**：问题不是"等多久"，而是"**无限期不被调度**"——高优线程等低优持的锁、中优线程持续抢 CPU，低优线程永远跑不完，锁永远不释放。火星探测器 Pathfinder 的著名 bug 就是这个场景，差点让任务失败。
- **正解**：三条路——① **优先级继承**（PI mutex）：持锁期间临时提升到等锁者的最高优先级；② **优先级天花板**（PCP）：持锁期间直接提到预定义天花板；③ **工程规避**：高优线程不等用户态锁，关键路径数据用无锁结构 + Handler 消息。
- **追问**：Android 支持 PI mutex 吗？→ pthread_mutexattr 支持 `PTHREAD_PRIO_INHERIT` 但 ART 的 `Monitor` 实现**不支持优先级继承**，所以 Java 层 synchronized/ReentrantLock 都没有 PI 保障。关键路径必须走工程规避。

### Q4 协程真的省线程吗

- **直觉答案**：协程比线程"轻 100 倍"，开百万协程完全没问题。
- **为什么错**：这个说法混淆了"**挂起时省线程**"和"**执行时省线程**"。协程挂起（`suspend`）时确实不占线程，但一旦 `resume` 执行，就必须占一个线程跑。如果你的协程 95% 时间在算（CPU 密集），100 万协程 = 100 万份计算工作，线程数一样满。
- **正解**：协程的本质是"**状态机 + 调度器**"——把异步代码写得像同步，省掉"回调地狱"。真实收益只在 **等待占比 > 95%** 的场景兑现：数据库连接池、长连接心跳、大量 IO。CPU 密集场景百万协程 = 百万份 CPU 任务，不省反亏（协程调度本身也有 ns 级开销）。
- **追问**：Kotlin `Dispatchers.Default` 和 `Dispatchers.IO` 的区别？→ Default 底层是 `ForkJoinPool`，线程数 = CPU 核数（CPU 密集设计）；IO 底层是弹性池，上限 64（吸收阻塞）。混用会把 Default 的计算线程饿死——面试必踩的坑。

### Q5 多进程一定比单进程稳吗

- **直觉答案**：多进程崩溃隔离，WebView 挂了主进程不受影响，当然更稳。
- **为什么错**：忽略了"**稳定性收益是概率性的，内存/IPC 成本是确定性的**"。崩溃隔离一个月兑现 1-2 次，但每天都在为跨进程通信、重复加载 .so、CoW 失效付内存税。统计：80% 中小 App 的多进程架构是"过度设计"——拆了之后 Native crash 率只降 0.03pp，内存却多 20%。
- **正解**：拆进程只在以下场景有正收益——① WebView（Chromium 内核崩溃是 Top 3）；② 音视频/游戏引擎（第三方 Native SDK 风险高）；③ `isolatedProcess` 跑高危计算（图像处理、脚本执行）。其他全部单进程。
- **追问**：怎么量化拆/不拆的 ROI？→ 收益侧用历史 Native crash 率 × 用户影响度，成本侧用新进程稳态 PSS × 平均存活时长 × 用户在前台时间占比，两者比值大于 10 才拆。详见 §4.5 决策树。

### Q6 Binder 跨进程比同进程慢多少

- **直觉答案**：Binder 是 Android 最优 IPC，应该和同进程方法调用差不多。
- **为什么错**：同进程方法调用是**纳秒级**（NS 栈压入 → 跳转 → 返回，~ns），Binder 调用是**微秒级甚至毫秒级**。两者相差 100-10000 倍。
- **正解**：Binder 调用的真实开销链条（见 §4.6 深潜）——用户态陷入内核 0.3μs + Parcel marshal 0.5-2μs + copy_from_user 0.3-1μs + 服务端 Binder 线程唤醒 0.5-1μs + 业务逻辑 + 回传 1-2μs。空调用 **3-6μs**，带 1KB 数据 **10-30μs**，服务端拥塞时 **100μs-10ms**。
- **追问**：Binder 服务端线程池上限多少？→ 16 条命（framework 固定），超过就排队。所以服务端单次调用必须 < 10ms，否则队尾请求延迟会累积到 1s+（见 §4.6 深潜）。

### Q7 iOS 几乎单进程是不是就没进程问题

- **直觉答案**：iOS 应用都是单进程，所以没有多进程架构的烦恼。
- **为什么错**：没有"多进程问题"不等于"没有进程问题"——iOS 把"进程架构选择"转移到了"**后台执行权限争夺**"。你没有 `:push` 进程，但要在 BackgroundTasks framework 下和系统博弈"能活多久"。
- **正解**：iOS 和 Android 的进程治理策略截然相反——iOS 从一开始就"**系统全权控制生命周期**"（App 转后台 → 3-10 秒 → 被挂起或杀），开发者只能申请有限的后台任务窗口（BGProcessingTask、BGAppRefreshTask）。所以 iOS 没有"保活"概念，但有"**快速恢复**"是刚需——冷启动必须 < 1s。这个思路反过来影响了 Android 现在的"让贤为王"范式（见 §4.7 深潜）。
- **追问**：那 iOS 为什么能做到单进程还不卡？→ Grand Central Dispatch（GCD）+ 严格的主线程保护 + 大量 Native 优化（没有 Dalvik/ART 的翻译开销）。iOS 从底层就把"线程治理"做好，所以不需要靠多进程硬扛稳定性。

### Q8 保活做好就能"不被杀"吗

- **直觉答案**：技术投入足够，总能保住进程。
- **为什么错**：这是 2015 年的认知——那时候 Android 系统弱约束，确实能靠互拉/1 像素/系统 Service 旁路保住。但 2018 Android O 开始每一代都在加强打压（见 §4.7 时间线表），到 Android 14 "保活"几乎没有空间，而且用户心智已经固化为"**后台耗电高 = 流氓应用**"。
- **正解**：现代做法是"**快速冷启动 + 状态恢复**"——500ms 冷启动让用户感知不到被杀，等同于 100% 保活成功率，成本只有保活的 1/10。关键指标从"被杀率"变成"用户感知崩溃率"。
- **追问**：那推送怎么办？→ 接 FCM / HMS Push / UniPush 等系统级推送，它们在系统服务进程里跑，不受应用保活策略影响。国内厂商联盟（统一推送联盟）就是解决这个问题的——各家 ROM 都保证系统推送通道能到达，App 不用自己保活。

### Q9 SharedMemory 真的零拷贝吗

- **直觉答案**：零拷贝就是从头到尾不发生任何内存复制。
- **为什么错**：混淆了"**数据面零拷贝**"和"**控制面零拷贝**"。SharedMemory 的"零拷贝"仅限于数据传输——建立映射仍要 syscall（~50μs），进程间**元数据同步**（谁写了、写到哪、写完了没）必须走 Binder/socket，这些都不是零成本。
- **正解**：SharedMemory 的真实工作模式——① 发送方 `SharedMemory.create()` 分配 ashmem；② 走 Binder 把 fd 传过去（只传 int，不传数据）；③ 接收方 `mapReadWrite()` 把 fd 映射到自己地址空间；④ 两边通过 Binder 消息同步"写完了"信号。**数据不拷贝，但同步和建立开销固定**。所以适合"大 + 低频"场景：800KB 图像/视频帧传一次能省 2ms（Binder 内核拷贝时间）；8 字节心跳传一次反而比 Binder 慢。
- **追问**：那 Linux pipe/socket 不是也零拷贝有 splice/sendfile？→ 对，但这些是"文件描述符间零拷贝"，Android 的 SharedMemory 是"进程间共享物理页"，两者机制不同。前者省的是内核态拷贝，后者省的是进程间整体拷贝。

### Q10 协程为什么还需要线程池

- **直觉答案**：协程是"轻量级线程"，有自己的调度，应该不需要线程池。
- **为什么错**：这是对"轻量级"的误解。协程是**调度单位**（协作式切换，上下文极小），线程才是**执行单位**（内核调度，占用 CPU）。协程挂起时不占线程，但一旦 resume 执行，必须有线程来跑。
- **正解**：协程的本质是"**在线程池之上做协作式调度**"。Kotlin 协程框架内置的 `Dispatchers.Default`（CPU 密集，ForkJoinPool）和 `Dispatchers.IO`（IO 密集，弹性池，上限 64）就是协程背后的线程池。协程 + 线程池不是竞争关系，是分层关系——协程负责"**任务怎么协作**"，线程池负责"**协作任务怎么跑**"。
- **追问**：那 Go 的 goroutine 不是号称"用户态调度不要线程池"吗？→ 它的 GMP 模型里 `P` 相当于逻辑处理器、`M` 是内核线程、`G` 是 goroutine——本质上也是"G 在 M 上跑，M 由 Go runtime 管理成一个池"。只不过 Go 把线程池内置到 runtime 隐藏起来了，而 Kotlin 显式暴露给你。

### Q11 加线程为什么反而慢

- **直觉答案**：核多开线程多，并行度翻倍，当然更快。
- **为什么错**：忽略了三笔账——① **切换税**：每次上下文切换 1-10μs 直接成本，加上 cache/TLB 变冷的间接成本。每秒 2 万次切换吃掉 10-20% CPU；② **cache 污染**：N 个线程轮番上 CPU，每个的工作集被挤出 L1/L2，IPC 骤降；③ **锁竞争**：多线程 = 多争抢同一把锁，等锁的时间比干活还长。
- **正解**：线程数应该等于"**核数 × (1 + 等待时间/CPU时间)**"，不是"越多越好"。CPU 密集任务线程数 = 核数 + 1；IO 密集任务线程数 = 核数 × 2-4；混合任务按比例折中。礼物墙案例：原来 12 个 SDK 各自建池 → 187 线程，切换率 22K/s；收敛到统一池 52 线程 + 4.2K/s，稳态 CPU 从 18% 降到 11%。详见 §4.3。
- **追问**：那为什么有些框架（如 Dubbo）配 200 线程还能跑？→ 服务端场景单线程大部分时间在等 IO（数据库、RPC），CPU 利用率低，线程多了能提高吞吐。但 Android 主要是前端场景，CPU 利用率已经高，线程多了纯交切换税。

### Q12 fork 为什么比 exec 快几十倍

- **直觉答案**：都是创建新进程，开销差不多。
- **为什么错**：`fork` 和 `exec` 做的事完全不同。fork **只做"拷贝页表 + 设置 CoW 标记"**，物理页不复制（直到写入才复制），所以 ~5-20ms；exec **要重新 load ELF、link 动态库、init runtime**，一个 Android 进程完整 exec 走完 ART 启动要 500ms+。
- **正解**：Android 用 Zygote fork 子进程而不是 exec，就是利用 fork 的"**预加载共享**"优势——Zygote 启动时预加载 .so/class 到自己内存，fork 时子进程通过 CoW 立刻共享到这些数据，省掉了 500ms+ 的运行时初始化。详见内存篇 §6.6 Zygote CoW 深潜。
- **追问**：那为什么 Linux 还要 exec？→ fork 只能复制自己，exec 才能变成"**完全不同的程序**"（如 shell 启动一个新命令）。所以 Linux 的标准做法是 `fork + exec`——fork 出壳子，exec 换脸。Android 不换脸（都跑 ART），所以只用 fork。

### Q13 ANR 和线程模型的关系

- **直觉答案**：ANR 是主线程 CPU 不够，加 CPU 优先级就能解决。
- **为什么错**：这个认知只对了 30%。真实分布是——主线程 on-CPU 高（真算不动）占 30%，主线程 off-CPU 等待（等锁、等 IO、等 Binder、等 cgroup 配额）占 **70%**。盯 CPU 曲线找 ANR 原因，会漏掉大半。
- **正解**：诊断分流——① 先看主线程 CPU：高 → on-CPU 问题，走火焰图找平顶（见 CPU 篇 §3.3）；低 → off-CPU 问题，走 Perfetto 看主线程 state 泳道（见 §3.1）。② 看泳道颜色：绿色 Running、灰色 Sleeping（点开看 Wakeup from 字段）、红色 UninterruptibleSleep（等 IO/Binder）。③ 看 `/data/anr/traces.txt`：主线程栈顶在哪就是元凶。
- **追问**：主线程 D 态怎么破？→ D 态只有两种可能——等磁盘 IO 或等 Binder 内核态。前者避免主线程 IO（见 §4.1），后者避免主线程同步 Binder（见 §4.6 异步化）。D 态是 ANR 元凶中最隐蔽的，`top` 看不出来（它显示 state 为 D 的进程 CPU 占用 100%），必须用 Perfetto。

## 07、面试模板

> 5 个最高频面试题的**标准回答模板**。背会这 5 个，面试并发部分基本稳了。
>
> **本节骨架版**：Block 1 轮次先给 5 个模板的 60 秒精华版，后续轮次补足 90 秒详细版 + STAR 结构。

### A1 线程优化理解

**60 秒**：

> 线程优化的本质是"**用切换/锁开销兑换延迟缩短**"，核心公式：业务耗时 = 任务总量 / 并发度。并发度被物理封顶（核数 × IPC × 频率），不是"开更多线程"。
>
> 三类问题形态：**调度不当**（主线程做大活）、**同步开销**（锁等待）、**资源浪费**（线程数膨胀）。
>
> 四层治理按 ROI：主线程减负 > 同步治理 > 线程池统一 > 优先级调度。
>
> 直播案例：卡死率 7.3% → 0.3%，线程数 187 → 52，切换率 22K/s → 4.2K/s。

### A2 卡顿排查

**60 秒**：

> 第一步分流：**主线程利用率高 → on-CPU（火焰图找平顶）**；**利用率低却卡 → off-CPU（70% 场景）**。
>
> off-CPU 用 Perfetto 看主线程状态泳道：S 态等锁、D 态等 IO/Binder、R 态排队。
>
> 工具三件套：线程清单（`/proc/<pid>/task`）、系统 trace（Perfetto）、锁竞争（`lock_contention`）。
>
> 口诀：**先看利用率分流 → 高走火焰图 → 低走状态泳道**。只盯 CPU 曲线会漏掉 70% 真相。

### A3 多进程架构决策

**60 秒**：

> **三问法则**：这个模块多常崩？崩了多严重？独立进程常驻多少 MB？
>
> **决策树**：高崩溃风险拆（WebView/音视频）、常驻低活性删或换 FCM（Push/同步）、短生命周期不拆（相机）、核心业务永不拆。
>
> **铁律**：隔离收益是概率性的，代价是确定性的——80% 应用用单进程最好，20% 用主 + 风险隔离，几乎没人需要 5 进程以上。
>
> 金融案例：5 进程 → 2 进程，PSS -47%，被杀率 22% → 3%。**最大的奖励是系统不再把你当贪婪应用**。

### A4 协程 vs 线程池

**60 秒**：

> 协程是**调度单位**，线程池是**执行单位**——不是替代关系。
>
> 协程切换 ~200ns、线程切换 ~20μs，差 100×——但只在**等待占比 > 95%**（IO 密集）时兑现。CPU 密集任务开再多协程仍是单核算力。
>
> 阻塞调用（`Thread.sleep`、同步 Binder、文件 IO）会**饿死协程调度线程**——必须用 `Dispatchers.IO` 或非阻塞 API。
>
> 实战建议：IO 密集 / 高并发网络用协程，CPU 密集任务仍用线程池，混合场景用结构化并发（`coroutineScope`）管理生命周期。

### A5 优化故事线

**60 秒双案例串讲**：

> **线程案例（直播卡死）**：V9.2 开播"全异步并行"后卡死率飙到 7.3%，经验派 3 周（32 线程、死锁检测、spinlock）折腾到 9.1%。按方法派 7 天闭环：Perfetto 三方案归因三病灶并存 → 四层治理（IdleHandler 切片 + 锁拆 4 把 + 统一线程池 + QoS 继承）→ 卡死率 0.3%、首屏 1.0s、线程 52、切换 4.2K/s。
>
> **进程案例（金融瘦身）**：5 进程架构常驻 450MB，经验派 5 周（加保活 / 调上限 / 加 IPC 缓存）折腾被杀率反升到 22%。按方法派 8 天：进程清单 + Binder trace + CoW 共享率归因到"3 个保活/守护进程无价值" → 四层治理（删 3 进程 + Binder 批处理 + 共享内存 + 快速重启）→ PSS 240MB、OOM 0.6%、被杀 3%、推送到达 91% → 97%。
>
> **共同沉淀**：**线程优化先治 off-CPU，进程优化先问必要性**。经验派总错在"用更多资源治资源问题"（加线程/加进程），方法派都是"先归因到物理代价，再按 ROI 治理"。

## 附录：双贯穿案例

> **本附录骨架版**：Block 1 轮次先保留两个案例的核心数据表，后续轮次补足详细叙事与反面教材流程。

### 附录 A：直播卡死案例（线程维度）

**背景**：某直播 App V9.2 上线"开播秒开"，推流准备从异步改成全异步并行。结果反而：
- 开播 3 秒卡死率 **0.5% → 7.3%**；主播首屏 P95 **1.2s → 4.8s**；
- 线程数稳态 65 → **187**，内存涨 80MB；
- 日活主播 **-12%**，单日损失约 **600 万**。

**经验派 3 周反面教材**：
| 周次 | 动作 | 结果 |
|---|---|---|
| 1 | 线程池 8 → 32 | 卡死率升到 9.1%，切换暴涨 |
| 2 | 加死锁检测 | 没死锁但卡依旧 |
| 3 | spinlock 换 mutex | CPU 炸到 100%，发热严重 |

**方法派 7 天闭环**：
- Day1：Perfetto 三方案归因 → 三病灶（线程 187 / 切换 22K/s / 锁等待 850ms）并存；
- Day2：决策树定位（线程膨胀 / 调度不当 / 同步开销）；
- Day3-4：四层治理（IdleHandler 切片 + 锁拆 4 把 + 统一线程池 + QoS 继承）；
- Day5：Macrobenchmark 验证；Day6-7：灰度 + 上线。

**结果对比表**：

| 指标 | 经验派 3 周 | 方法派 7 天 |
|---|---|---|
| 卡死率 | 9.1% | **0.3%** |
| 首屏 P95 | 4.8s | **1.0s** |
| 线程数 | 230 | **52** |
| 切换率 | 35K/s | **4.2K/s** |
| 锁等待 P99 | 850ms | **18ms** |
| 日活主播 | -12% | **+3%** |

### 附录 B：金融 5 进程瘦身案例（进程维度）

**背景**：某金融 App 历史 5 进程架构（主/Push/WebView/守护/拉活），架构初心"模块隔离防崩溃"：
- 常驻 PSS **450MB**，中端机 OOM 率 **4.8%**；
- 冷启动 P95 **3.6s**，用户点通知冷启占 38%；
- A11+ 升级后主进程被杀率 **2% → 22%**（系统认定贪婪应用）；
- 应用商店卡顿差评 **12,000/月**。

**经验派 5 周反面教材**：
| 周次 | 动作 | 结果 |
|---|---|---|
| 1 | 加强双进程互拉保活 | 被杀率反升到 22% |
| 2 | Push 进程内存上限调小 | Push OOM 消息丢失 ×8 |
| 3 | 加 IPC 缓存层 | 引发数据不一致 bug |
| 4 | WebView 进程预热常驻 | 内存又涨 30MB |
| 5 | 调 Push 优先级 | 无改善 |

**方法派 8 天闭环**：
- Day1：进程清单 + Binder trace → Push 每天只干 8-12 次活却占 80MB、主↔Push 心跳 35 次/秒；
- Day2：逐进程评估必要性 → **5 个里 3 个无价值**（Push/守护/拉活）；
- Day3：用保活实验数据说服架构师放弃"5 进程不能动"；
- Day4-5：四层治理（删 3 进程 + 换 FCM + Binder 批处理 + 共享内存 + 快速重启）；
- Day6：被杀-重启-恢复自动化用例；Day7-8：灰度上线。

**结果对比表**：

| 指标 | 经验派 5 周 | 方法派 8 天 |
|---|---|---|
| 进程数 | 5 | **2**（主 + WebView） |
| 常驻 PSS | 450MB | **240MB**（-47%） |
| 冷启 P95 | 3.6s | **1.2s** |
| OOM 率 | 4.8% | **0.6%** |
| 主进程被杀率 | 22% | **3%** |
| 推送到达率（FCM） | 91% | **97%** |
| 用户主动回归率 | -8% | **+5%** |

**核心洞察**：**进程治理的最大杠杆是删除非必要进程**。删 3 个让 PSS -47%、被杀率反而 22% → 3%——**系统不再把你当贪婪应用，是最大的奖励**。

> **一句话总结**：
>
> 并发有两级——**线程级在一个地址空间内用 CPU 兑换延迟**，**进程级在多个地址空间间用 IPC 兑换隔离**。两级的治理都在同一个真理下：**并发不是免费的，每次并发都是一次交换**——先算清代价公式再动手，就能避免 90% 的"用更多资源治资源问题"的反面教材。
