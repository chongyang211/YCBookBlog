# 线程与进程模型优化

> **本文定位**：面向中高级 Android 工程师的"并发两级模型"系统性复习材料，用于面试准备、技术分享、架构评审。与《CPU 监控与分析》《内存监控与 OOM 治理》同构：开篇拷问 → 问题本质 → 排查归因 → 监控体系 → 分层治理 → 原理深潜 → 高频追问 → 面试模板。

## 00、开篇拷问

### 0.1 线程越多越快吗

```
问题：8 核手机开 32 线程做 IO，一定比 8 线程快吗？
```

**错觉**：核多了并发多就快。

**真相**：线程不是免费的——每个线程**栈 1MB + TCB ~10KB + 调度成本 μs 级 + cache 污染 10-100μs**。32 线程做 IO，看似并发 32，实则：
- 线程切换从每秒数千次飙到数万次，CPU 全在"切"不在"算"；
- cache 反复失效，有效工作集缩水；
- IO 底层队列深度有限（nvme 32、EMMC 1-4），**线程数超过队列深度后全是伪并发**。

**本文第一性原理**：**并发是用"切换/锁开销"兑换"延迟缩短"的生意**，不是免费加速器。详见 §01.1。

### 0.2 多进程比单进程更稳吗

```
问题：把 App 拆成 5 个进程，是不是比单进程更稳定？
```

**错觉**：进程多 = 隔离强 = 稳定。

**真相**：隔离的**收益是概率性的**（不出事时为零），**代价是确定性的**（每天都在交房租）：
- 每个空进程常驻 ~15MB，带运行时 25-70MB；
- 每次 IPC 1-5μs（Binder 本地）到 10ms+（跨进程调用链）；
- 系统（lmkd、Android 11+ Doze）**对"进程贪婪应用"主动打压**，被杀率反升。

**本文结论**：**80% 应用用单进程最好，20% 用主进程 + 风险隔离，几乎没人需要 5 进程以上**。详见 §01.2 + §04.5。

### 0.3 协程能替代线程池吗

```
问题：既然协程"切换 1/100"，开百万协程不就够了？
```

**错觉**：协程 = 轻量线程 = 可以替代一切。

**真相**：协程是**调度单位**，线程是**执行单位**。协程挂起时不占线程，但执行计算仍然在底层那几根线程里排队：
- `Dispatchers.Default` 底层是 **N=核数**的 ForkJoinPool，CPU 密集任务开再多协程也是单核算力；
- 阻塞调用（`Thread.sleep` / 同步 Binder / 文件 IO）**会把那根线程扣死**，饿死排队中的其他协程；
- 协程真正省的是"**等待时的线程占用**"（IO 密集场景），不是执行计算的 CPU。

**本文定位**：协程是"用户态调度优化"（§05.5），不是银弹。详见 §04.3 + §06.Q10。

## 01、问题本质

> 把"线程"和"进程"的物理代价讲到可量化、可对照——这是全文一切优化的第一性基础。

### 1.1 线程物理本质

**一句话定义**：**线程 = 操作系统调度的最小单位，是"共享地址空间 + 独立执行上下文"的执行实例**。

这句话隐含**三个不可商量的物理约束**：

**约束一：线程共享地址空间**

同一进程内所有线程共享堆、全局变量、文件描述符——这是**线程"轻量"的根本**（不用复制地址空间）。
**代价**：共享即竞争——所有多线程 bug 的根源（数据竞争、死锁、可见性）都来自此。

**约束二：线程有独立执行上下文**

每个线程有：**独立的栈（1-8MB）、独立的寄存器状态、独立的 TCB（Thread Control Block ~10KB）**。
**代价**：栈 + TCB 常驻内存——1000 个线程 = 1-8GB 栈 + 10MB TCB，这是"线程不能无限开"的物理底线。

**约束三：切换要陷入内核**

线程切换由 OS 调度器触发，**必须陷入内核态**：
- 保存/恢复寄存器组（ARM 约 30 个寄存器）：~0.1-0.5μs
- 内核调度决策（CFS 红黑树遍历）：~0.5-2μs
- **cache/TLB 变冷**（新线程工作集不在 L1/L2）：**数十 μs 大头**
- 分支预测器污染：微秒级

**直接成本 1-5μs，加上 cache 变冷 20-50μs**。每秒 1 万次切换 = 10-30% CPU 用在"切"而不是"算"。

**三类线程问题形态**（后文决策树依据）：

| 形态 | 表现 | 典型场景 | 本文位置 |
|---|---|---|---|
| **调度不当** | 主线程阻塞、UI 卡顿、ANR | 主线程做 IO/同步 IPC/大计算 | §04.1 §04.4 |
| **同步开销** | 锁等待 P99 高、线程状态泳道大片 S/D | 锁粒度过大、持锁 IO、死锁 | §04.2 §05.3 |
| **资源浪费** | 线程数膨胀、切换率高、内存涨 | 线程池无上限、每 SDK 建自己的池 | §04.3 §05.2 |

**▶▶ 回扣线程案例**：直播开播卡死命中三类全部——线程数 187（资源浪费）、切换 22K/s（调度不当）、推流锁等待 850ms（同步开销）。

### 1.2 进程物理本质

**一句话定义**：**进程 = 操作系统资源分配与隔离的基本单元，是"独立地址空间 + 文件句柄 + 信号上下文"的执行实例**。

这句话同样隐含**三个不可商量的物理约束**：

**约束一：进程是地址空间的边界**

每个进程有独立虚拟地址空间——**这是硬隔离**：
- 进程 A 崩溃不会破坏 B 的内存（故障隔离）；
- 进程 A 泄漏不会影响 B（资源隔离）；
- 进程 A 读不到 B 的数据（安全隔离）。

**代价**：IPC 必经内核（copy 或 mmap），有性能开销。

**约束二：进程创建有固定成本**

每次创建进程都要：分配地址空间（页表）→ 复制/映射代码段 → 加载动态库 → 启动运行时 → 执行入口。

| 平台 | 创建开销 | 关键机制 |
|---|---|---|
| Android | **200-400ms** | **Zygote fork + CoW** 省去 VM 启动 ~500ms |
| iOS | 200-300ms | exec + dyld + libObjC |
| Web Tab | 100-500ms | 浏览器实现差异 |
| Linux fork+exec | 10-100ms | 不含应用初始化 |

**约束三：IPC 必经内核**

任何 IPC（Binder/Pipe/Socket/SharedMemory）都要：
```
进程 A 用户态 ─[陷入内核]─► 内核中转 ─[切回用户态]─► 进程 B 用户态
     │                            │
   一次 syscall ~1-5μs          一次 syscall ~1-5μs
```

即使是"零拷贝"的 SharedMemory，**建立映射仍需 syscall**——这是 IPC 的物理底线。

**四类进程问题形态**：

| 形态 | 表现 | 典型场景 | 本文位置 |
|---|---|---|---|
| **数量膨胀** | 常驻 PSS 高、OOM 率高、被 lmkd 杀 | 守护/拉活/保活、过度拆分 | §04.5 |
| **IPC 过慢** | 跨进程调用 100ms+、用户感知"卡" | 高频心跳、未批处理、未缓存 | §04.6 §05.7 |
| **启动过慢** | 冷启 > 1s、从通知点入体验差 | 子进程初始化慢、Zygote CoW 被破坏 | §05.6 |
| **保活失效** | 被杀率高、系统认定"贪婪" | A8+/A11+ 后传统互拉保活失效 | §04.7 |

**▶▶ 回扣进程案例**：金融 5 进程架构命中前三类——Push + 守护 + 拉活共占 140MB（数量膨胀）、主↔Push 心跳 35 次/秒（IPC 过慢）、冷启 3.6s（启动过慢）。

### 1.3 并发两级公式

**公式**：

```
业务耗时 = 任务总量 / (线程并发度 × 进程隔离度)

                       │              │
                       │              └─ 决定"故障/资源不扩散"
                       └─ 决定"任务并行跑完速度"
```

展开两级代价账：

```
实际并发收益 = 理论并发度 − 切换损失 − 同步损失 − IPC 损失

              │              │          │          │
              │              │          │          └─ 跨进程 1-5μs/次
              │              │          └─ 锁等待（可从 ns 到 100ms）
              │              └─ 单次 1-5μs + 冷 cache 20-50μs
              └─ 核数 × 单核算力
```

**两条铁律**（后面所有治理都是推论）：

1. **并发度不是"开多少线程"**：它由"核数 × 平均 IPC × 平均频率"（CPU 篇 §02.2 公式）物理封顶；
2. **隔离度不是"拆多少进程"**：它只在**故障发生时**才兑现价值，平时都是"交房租"。

**ROI 判定**：

```
线程 ROI = 延迟缩短收益 / (切换成本 + 同步成本 + 栈内存成本)
进程 ROI = 隔离事件收益 × 发生概率 / (IPC 成本 + 启动成本 + 内存成本)
```

**▶▶ 回扣两个案例**：
- 直播：线程 ROI 为负——32 线程切换成本（35K/s）远超并发收益；
- 金融：进程 ROI 为负——3 个"保活/守护"进程的隔离价值 ≈ 0（A11+ 保活已失效），常驻 140MB 却天天在付。

> 🔬 **深潜：mutex 为什么是 futex——用户态快路径的 20× 加速**
>
> §01.1 讲"切换要陷入内核"，但现代 Linux 的 mutex 并不是每次加锁都陷入内核。它底层是 **futex（Fast Userspace muTEX）**，有一条"用户态快路径"：
>
> **futex 的二态模型**：
>
> ```
> ┌─ 无竞争路径（快路径）：
> │   原子 CAS 修改一个 int 标志位 → 直接返回，不进内核
> │   成本：~30ns（一次原子操作）
> │
> └─ 有竞争路径（慢路径）：
>     CAS 失败 → syscall futex(FUTEX_WAIT) 挂起当前线程
>     成本：~1-5μs（陷入内核 + 切换 + cache 变冷）
> ```
>
> **工程推论**：
>
> 1. **低竞争场景 mutex 近乎免费**——30ns 的 CAS 和一次函数调用成本相当；
> 2. **高竞争时急速劣化**——命中慢路径，一次 1-5μs，百次就是毫秒级；
> 3. **这就是"自旋锁有时反而快"的原因**（§05.3）——如果竞争时间 < 1μs，自旋消耗的 CPU 远少于一次 futex 内核往返。

> 🔬 **深潜：Zygote fork + CoW 的边界——哪些 API 会偷偷"破坏共享"**
>
> §01.2 讲"Android 用 Zygote 省 VM 启动 500ms"，这一切的物理基础是 **Copy-on-Write（写时复制）**。但很多代码会无意中破坏 CoW，让子进程失去共享红利。
>
> **CoW 工作原理**（简化）：
>
> ```
> Zygote 父进程（预加载 50MB framework + 常用类）
>      │
>      ├─ fork ─► App 主进程      ──► 共享 50MB 页，只占增量
>      ├─ fork ─► :push 子进程    ──► 共享 50MB 页，只占增量
>      └─ fork ─► :web 子进程     ──► 共享 50MB 页，只占增量
>
> 任何子进程"写入"共享页 → 该页立即被"复制一份"归该子进程独占
> ```
>
> **四类破坏 CoW 的典型操作**：
>
> | 操作 | 破坏点 | 代价 |
> |---|---|---|
> | 在 `Application.onCreate` 里**随意写静态字段** | 整页 copy | 页面被拷到独占 |
> | 加载**巨型 .so**（如 OpenCV 几十 MB） | 页面被改写 ownership 转移 | 数十 MB 独占 |
> | 用 `Runtime.exec` / `fork+exec` | 立刻与 Zygote 完全解耦 | 共享全部作废 |
> | 频繁调用 `System.gc()` 触发整堆压缩 | 大面积页被改写 | 共享快速退化 |
>
> **工程推论**：
>
> 1. **子进程 Application 要按进程名精简**（见 §04.5）——不要跑主进程的全套初始化；
> 2. **大 .so 延迟加载到真正使用的进程**——避免所有进程都为它掏钱；
> 3. **测 CoW 收益**：对比 `/proc/<pid>/smaps` 中的 `Shared_Clean` + `Shared_Dirty` 占比，> 60% 说明 CoW 健康。

### 1.4 面试锚点

**Q："线程和进程的本质差别是什么？"**

答题模板（三约束对照 + 代价公式）：

> 线程和进程的差别可以用"**三约束对照 + 代价公式**"讲清楚。
>
> **线程三约束**：共享地址空间（轻量根源）、独立执行上下文（栈 + 寄存器 + TCB）、切换陷入内核（1-5μs 直接 + 20-50μs cache 变冷）；
>
> **进程三约束**：地址空间硬隔离（三重隔离的根本）、创建有固定成本（Android Zygote fork 省 VM 启动 500ms）、IPC 必经内核（物理底线）。
>
> **代价公式**：`业务耗时 = 任务总量 / (线程并发度 × 进程隔离度)`。线程优化本质是"用切换/锁开销兑换延迟缩短"，进程优化本质是"用 IPC/内存成本兑换故障/资源隔离"。
>
> **两条铁律**：并发度被物理封顶（核数 × IPC × 频率），不是"开更多线程"；隔离度收益是概率性的（故障时才兑现），不是"拆更多进程"。

## 02、排查归因

> 把"卡"和"被杀"两个表象分别拆到可诊断的叶子节点——这是归因不走弯路的前提。

### 2.1 卡顿决策树（线程维度）

**入口**：主线程 P95 帧时长 > 16ms，用户感知卡顿。先看一个指标：**主线程利用率**。

```
主线程 P95 帧时长 > 16ms
       │
       ├─ 主线程 on-CPU 利用率 > 80%  → 【A 分支】on-CPU 卡
       │                              └─ 看火焰图找平顶（CPU 篇 §03）
       │                                 常见病灶：主线程做大计算 / 复杂布局 / 同步序列化
       │
       └─ 主线程 on-CPU 利用率 < 30%（但帧时长仍高）→ 【B/C/D 分支】off-CPU 卡
          │
          ├─ 线程状态泳道大片 S（可中断睡眠） → 【B】等锁
          │                                └─ Perfetto `lock_contention` + 看持锁线程
          │                                   常见病灶：锁粒度大、持锁 IO、死锁
          │
          ├─ 线程状态泳道大片 D（不可中断） → 【C】等 IO / Binder
          │                              └─ Perfetto ftrace 看 syscall / Binder transaction
          │                                 常见病灶：主线程读文件、同步 Binder、cgroup 限流
          │
          └─ 线程切换率飙高（> 10K/s）→ 【D】被切换淹没
                                     └─ 线程数 > 100、每帧任务切到不同线程池
                                        常见病灶：无统一线程池、SDK 各自建池
```

**▶▶ 回扣线程案例**：
- 主线程利用率 95%（A 分支）+ 推流锁等待 850ms（B 分支）+ 线程数 187 切换 22K/s（D 分支）**三病灶并存**——这就是经验派"修一个病灶没用"的根因。

### 2.2 被杀决策树（进程维度）

**入口**：主进程被杀率 > 5%、用户点通知冷启比例高、OOM 率异常。先看**内存压力**。

```
主进程异常退出
    │
    ├─ 有 Java 栈 → 【A】堆内 OOM
    │                └─ 内存篇 §03 分类处理
    │
    ├─ 无栈但 crash → 【B】Native OOM / 地址空间
    │                 └─ breakpad / tombstone 查信号
    │
    ├─ 无 crash 日志，进程静默消失 → 【C】被 lmkd 杀
    │   │
    │   ├─ 看 `/sys/kernel/debug/lowmemorykiller/`（旧版本）
    │   ├─ 看 `logcat | grep lowmemorykiller`
    │   └─ 看 Android 11+ `dumpsys activity lmk` 或 `am_kill` 事件
    │       │
    │       ├─ oom_score_adj > 500 时被杀 → 【C-1】后台进程被回收（正常）
    │       ├─ oom_score_adj 100-500 被杀 → 【C-2】系统认定"贪婪应用"（治理重点）
    │       └─ oom_score_adj < 100 被杀    → 【C-3】整机内存危机（兜底）
    │
    └─ 进程数 > 系统上限 → 【D】触发整机策略
```

**▶▶ 回扣进程案例**：金融 App 命中 **C-2**——5 进程常驻 PSS 450MB，lmkd 把它标记为"贪婪应用"主动降权。

### 2.3 跨维度归因

**最常见误诊**：卡顿 ≠ 线程问题，被杀 ≠ 进程问题。

| 症状 | 直觉判断 | 真实可能 |
|---|---|---|
| 用户点通知冷启动特别慢 | 冷启动代码慢 | 主进程**被杀**（进程问题） |
| 后台任务跑半天没结果 | 后台任务代码慢 | **cgroup 限流**（线程/进程交界） |
| 主线程"看起来不忙"却卡 | CPU 不是瓶颈 | 等**跨进程 Binder**（进程 IPC 问题） |
| 加线程反而更慢 | 代码不好 | 切换率超临界（线程资源浪费） |
| 多进程后内存反而涨 | 内存泄漏 | **破坏 Zygote CoW**（进程问题） |

**判别顺序**：先看进程维度（是否有被杀/多进程），再看线程维度（主线程状态泳道）——顺序反了容易"治表不治本"。

### 2.4 面试锚点

**Q："主线程卡顿怎么排查？"**

答题模板（on-CPU vs off-CPU 分流 + 三类状态）：

> 第一步**分流**：看主线程利用率。
>
> **利用率高（> 80%）** → on-CPU 卡，走 CPU 篇 §03 火焰图找平顶；
>
> **利用率低却卡** → off-CPU 卡（约 70% 场景在这），用 Perfetto 看主线程状态泳道：**S 态等锁**（走锁竞争归因）、**D 态等 IO 或 Binder**（走 IO/IPC 归因）、**R 态排队**（走调度延迟/cgroup 归因）。
>
> 关键**反直觉**：ANR 的 70% 不是"CPU 不够"，而是"主线程等别人"。只看 CPU 曲线会漏掉大半——必须看状态泳道。
>
> 我做过的直播案例：主线程利用率 95% + 推流锁等待 P99 850ms + 线程数 187 切换 22K/s，三类并存。单修任何一个都没用，必须按决策树分别治——这就是 7 天闭环的归因起点。

## 03、监控体系

> 没有可信数据就没有归因。线程 + 进程 + 跨维度交叉指标三位一体，三类数据回答三个问题："线程在干嘛/进程在哪/两者在交互吗"。

### 3.1 线程采集三方案

| 方案 | 采集内容 | 开销 | 适用 |
|---|---|---|---|
| ① 线程清单 | `/proc/<pid>/task/*` 读 tid、name、state、CPU 时间 | 极低（<1%） | **线上常驻**采集线程数、状态分布 |
| ② 系统 trace | Perfetto / Systrace，sched_switch + syscall + ftrace | 中（3-5%） | **问题复现时**抓一段，看完整时序 |
| ③ 锁竞争 | `perf lock` / Perfetto `lock_contention` | 中 | **诊断同步问题**，看谁等谁 |

**三方案的关键配合**：方案 ① 发现"线程数 187"，方案 ② 看到"主线程 D 态 800ms"，方案 ③ 定位"推流锁被 4 路争用"——缺一个归因都不完整。

**面试加分**：三方案的盲区各不相同——方案 ① 看不到锁等待时序，方案 ② 开销大不能常驻，方案 ③ 只覆盖显式锁不覆盖 cgroup 限流。**线上组合用，线下深入用**。

### 3.2 进程采集三方案

| 方案 | 采集内容 | 开销 | 适用 |
|---|---|---|---|
| ① 进程清单 | `ps -A` / `ActivityManager.getRunningAppProcesses` / `dumpsys procstats` | 极低 | **线上**采集进程数、PSS、OOM score |
| ② Binder trace | `/sys/kernel/debug/binder/transactions`（root） / Perfetto Binder | 中 | **诊断 IPC** 频率、延迟、拥塞 |
| ③ 进程 maps | `/proc/<pid>/smaps` | 低（偶发） | **诊断 Zygote CoW** 共享率、.so 占用 |

**三方案的关键配合**：方案 ① 发现"5 进程 PSS 450MB"，方案 ② 看到"主↔Push 心跳 35 次/秒"，方案 ③ 发现"子进程 Shared_Clean 比例只有 40%（CoW 严重破坏）"——这就是金融案例的完整归因链。

### 3.3 跨维度交叉指标

| 交叉指标 | 公式/口径 | 健康阈值 | 异常推论 |
|---|---|---|---|
| **线程/进程比** | 应用总线程数 / 应用进程数 | < 60/进程 | 高 → 单进程线程池失控 |
| **主线程 Binder 等待占比** | 主线程 D 态时长 / 总时长 | < 5% | 高 → 跨进程调用链 |
| **进程 CPU 时间差** | 单进程 CPU 时间 - 单进程 Wall 时间 | ≈ 1 | 远 < 1 → 该进程大量在等 |
| **CoW 共享率** | `Shared_Clean` / 总 Rss | > 60% | 低 → 破坏 CoW，子进程不省内存 |
| **lmkd kill 速率** | 每小时被杀次数（含后台） | < 1 | 高 → 进程过多或内存泄漏 |

### 3.4 工具速查

| 场景 | 首选工具 | 补充 |
|---|---|---|
| 线程数 / 状态 | `ps -T -p <pid>` | `/proc/<pid>/task` |
| 锁竞争 | Perfetto `lock_contention` | `simpleperf stat` |
| 调度延迟 | Perfetto sched_switch 泳道 | `cat /proc/sched_debug` |
| 进程清单 + PSS | `dumpsys procstats` | `dumpsys meminfo` |
| Binder 调用 | Perfetto Binder 分类 | `/sys/kernel/debug/binder/stats` |
| OOM / 被杀 | `logcat | grep "lowmemorykiller\|Low Memory"` | `dumpsys activity lmk` |
| CoW 共享率 | `cat /proc/<pid>/smaps` | 聚合 `Shared_*` 字段 |

### 3.5 面试锚点

**Q："线上怎么监控线程/进程问题？"**

答题模板（三类数据 + 回答三个问题）：

> 我用"**线程 + 进程 + 交叉指标**"三位一体监控：
>
> **线程层**：常驻采集 `/proc/<pid>/task/*` 的线程数、state、CPU 时间（开销 < 1%），告警阈值"单进程线程数 > 100"或"主线程状态泳道 S/D 占比 > 10%"；
>
> **进程层**：`dumpsys procstats` 定期采集进程数、PSS、oom_score_adj，告警"子进程常驻 > 50MB"或"主进程被杀率 > 5%"；
>
> **交叉指标**：主线程 Binder 等待占比、Zygote CoW 共享率、lmkd kill 速率——这些是单维度看不出来的。
>
> **深挖**：出问题时触发一次 30 秒 Perfetto trace，抓齐 sched_switch + Binder + lock_contention 三类事件，离线分析。
>
> **防劣化**：CI 卡口跑核心场景的线程基准（线程数、切换率）和进程基准（常驻 PSS、冷启动时长），不达标阻断合入。

## 04、分层治理

> 全文核心章节——8 层治理按 ROI 排序。线程 4 层（主线程/同步/线程池/调度）+ 进程 4 层（数量/IPC/隔离/兜底），逐层展开。
>
> **本节骨架版**：Block 1 轮次先给结构、关键数据和心法，后续轮次补足代码示例、深潜块与详细步骤。

### 4.0 ROI 全景图（八层）

```
【线程四层】                              【进程四层】
      │                                        │
┌─────▼─────┐                            ┌─────▼─────┐
│ 4.1 主线程 │  ROI 最高                 │ 4.5 数量   │  ROI 最高
│ 减负       │  改一个点收益 20-50%       │ 收敛       │  删一个进程 -15~70MB
├───────────┤                            ├───────────┤
│ 4.2 同步   │  中等 ROI                 │ 4.6 IPC   │  中等 ROI
│ 原语       │  锁粒度拆分、持锁禁 IO     │ 优化       │  批处理 + 共享内存
├───────────┤                            ├───────────┤
│ 4.3 线程池 │  中等 ROI                 │ 4.7 隔离   │  收益"概率性"
│ 治理       │  统一池、按类型分 CPU/IO   │ 保活       │  仅 WebView/音视频必要
├───────────┤                            ├───────────┤
│ 4.4 调度   │  ROI 最低（但不可或缺）   │ 4.8 兜底   │  底线保护
│ 优先级     │  关键路径升 QoS            │ 重启       │  被杀后 < 800ms 恢复
└───────────┘                            └───────────┘
```

**铁律**：**先治线程四层，再治进程四层**。因为单进程下线程问题的收益确定性 > 多进程架构的隔离收益。

### 4.1 主线程减负

**心法**：**把活挪走（异步化）> 把活变少（算法/缓存）> 把活推迟（IdleHandler）**。

**三条路**：
1. 主线程 IO 异步化（文件、SharedPreferences 替 MMKV、同步 Binder 异步化）；
2. 布局优化（ConstraintLayout 平级、ViewStub 懒加载）；
3. 复杂计算切片（Choreographer.postFrameCallback + 时间片 ≤ 3ms）。

**▶▶ 回扣线程案例**：开播状态机改用 IdleHandler 切片，主线程 P95 帧时长 80ms → 18ms。

### 4.2 同步原语治理

**心法**：**锁的粒度决定并发上限，锁的时间决定延迟下限**。

**四条路**：
1. **锁粒度拆分**——1 把大锁 → N 把小锁（礼物墙推流锁拆 4 把，锁等待 850ms → 18ms）；
2. **持锁禁 IO**——锁内只做内存操作，IO/网络必须锁外；
3. **锁 → 原子 → 无锁** 阶梯（`LongAdder` 替 `AtomicLong`，-8% CPU）；
4. **读多写少用读写锁**，但注意 CAS 高竞争退化。

### 4.3 线程池治理

**心法**：**一个 App 应该有且只有少数几个"统一线程池服务"**——每 SDK 建自己的池是线程数爆炸的根源。

**三类池 + 配置黄金法则**：
```
CPU 池：核数 + 1          （CPU 密集，超了纯交切换税）
IO 池：核数 × (1 + 等待/CPU) 或 20-30（压测拐点）
高优先级池：4-8（关键路径专用）
```

**▶▶ 回扣线程案例**：原 12 个 SDK 各自线程池 → 统一服务，线程数 187 → 52。

### 4.4 优先级与调度

**心法**：**关键路径升 QoS、后台任务降 QoS、锁启用优先级继承**——三件事决定调度公平性。

**三条路**：
1. 主线程/Choreographer 相关线程 `THREAD_PRIORITY_URGENT_DISPLAY`；
2. 后台任务 `THREAD_PRIORITY_BACKGROUND` + cgroup `background` 组；
3. 高竞争锁用**优先级继承互斥量**（避免优先级反转）。

### 4.5 进程数量收敛

**心法**：**进程治理的最大杠杆是删除非必要进程，不是优化它们**。

**决策树**：
```
┌─ 高崩溃风险（WebView/音视频解码）→ 拆（崩溃隔离价值 > 内存成本）
├─ 常驻但低活性（推送/同步）     → 删或接 FCM 系统推送
├─ 短生命周期（相机/扫码）       → 不拆
└─ 核心业务                     → 永不拆
```

**▶▶ 回扣进程案例**：金融 App 删除 Push + 守护 + 拉活 3 个进程 → 常驻 PSS -47%、主进程被杀率 22% → 3%。

### 4.6 IPC 优化

**心法**：**IPC 不是免费的——1-5μs 单次成本在高频下吃掉主线程 CPU 的 20%+**。

**四条路**：
1. 高频心跳**批处理**（35 次/秒 → 1 次/5 秒）；
2. 大数据（> 1KB）走**共享内存** / `MemoryFile`；
3. 查询类接口**端上缓存** + 版本号；
4. 异步 Binder（`oneway`）替同步 Binder（关键链路慎用）。

### 4.7 进程隔离与保活

**心法**：**Android 11+ 之后传统互拉保活已失效，别再花钱养僵尸进程**。

**合理隔离三原则**：
1. WebView 独立进程做崩溃隔离（崩了不影响主）；
2. 音视频解码独立进程（NDK 崩溃不传染）；
3. **保活/守护进程直接删，用 FCM/WorkManager 替代**。

### 4.8 兜底与重启

**心法**：**接受"进程必被杀"的现实，把"快速恢复"做到比"防被杀"更极致**——1 秒内重启 + 恢复状态 > 永不被杀。

**四招**：
1. 被杀后 < 800ms 冷启动恢复（保证 LaunchActivity 轻量）；
2. 滚动位置、草稿、登录态**全部持久化**，重启即恢复；
3. 异常保护 + 主动重启（见 CPU 篇 §5.4 ④）；
4. 多进程架构下的"**主进程不在时子进程不干关键活**"原则。

### 4.9 ROI 排序

| 优先级 | 操作 | 收益区间 | 开发成本 |
|---|---|---|---|
| P0 | 主线程 IO 异步化 | 50-200% | 低 |
| P0 | 删除非必要进程 | 内存 -30~50% | 中（需架构调整） |
| P1 | 统一线程池 | 线程数 -60%、切换率 -80% | 低 |
| P1 | 锁粒度拆分 | 锁等待 -90% | 中 |
| P2 | IPC 批处理 + 缓存 | 跨进程开销 -70% | 中 |
| P2 | WorkManager 窗口化 | 整机功耗 -10% | 低 |
| P3 | 优先级 / cgroup 分组 | 主线程 P95 -20% | 低但调优繁 |
| P3 | 快速重启机制 | 用户感知崩溃 -80% | 高 |

### 4.10 面试锚点

**Q："你做过哪些线程/进程优化？"**

答题模板（八层串联 + 双案例数据）：

> 按"**线程四层 + 进程四层**"的 ROI 顺序做过：
>
> **线程侧**：
> - 主线程减负：开播状态机 IdleHandler 切片，P95 帧时长 80 → 18ms；
> - 同步治理：推流锁从 1 把拆成 4 把 + 禁锁内 IO，等待 P99 850 → 18ms；
> - 线程池：12 个 SDK 各自池 → 统一服务（CPU=核数+1 / IO=20 / 高优先=4），线程数 187 → 52，切换 22K → 4.2K/s；
> - 调度：推流线程升 URGENT_DISPLAY + 锁启用优先级继承。
>
> **进程侧**：
> - 数量收敛：删除 Push/守护/拉活 3 个进程，PSS 450 → 240MB（-47%）；
> - IPC 优化：主↔WebView 心跳批处理 + 大数据走共享内存；
> - 隔离保活：WebView 保留做崩溃隔离，保活全删（A11+ 已失效）；
> - 兜底：被杀后 800ms 重启 + 状态全恢复。
>
> 结果：直播卡死率 7.3% → 0.3%，主播首屏 4.8s → 1.0s；金融 OOM 率 4.8% → 0.6%，主进程被杀率 22% → 3%。
>
> 核心教训：**线程优化先治 on-CPU 和 off-CPU 的平衡，进程优化先问"真的需要吗"**——80% 的多进程架构是过度设计。

## 05、原理深潜

> 九大全链路，各自从"物理模型 → 代码路径 → 典型病灶"展开。
>
> **本节骨架版**：Block 1 轮次先给九大全链路的核心模型图与关键结论，后续轮次补足深潜块、代码示例与跨平台对照。

### 5.1 主线程调度全链路

**Android UI Thread** = Looper + MessageQueue + Choreographer，核心时序：

```
VSYNC 信号 → Choreographer.postCallback → MessageQueue 入队
         → Looper.loop 取 Message → doFrame → measure/layout/draw → OpenGL/HWUI
```

**关键病灶**：Message 队列堆积、同步 Barrier 阻塞、Choreographer 时间片超支。

### 5.2 线程池全链路

**ExecutorService 核心路径**：

```
submit → BlockingQueue 入队 → Worker 线程 take → run
            │                    │
            └─ 队列满 → 拒绝策略   └─ IDLE 超时回收 or 保留 corePool
```

**三类池差异**：`FixedThreadPool`（无界队列有 OOM 风险）、`CachedThreadPool`（线程数无上限）、`ScheduledThreadPool`（定时类）。

**协程 vs 线程池**：协程调度器底层仍是 ForkJoinPool，CPU 密集并不加速（见 §00.3）。

### 5.3 同步原语全链路

**mutex（futex 底层）**：无竞争 ~30ns，有竞争 1-5μs（陷入内核）；
**spinlock**：忙等 CPU，适合 < 1μs 的极短临界区；
**读写锁**：读多写少，但 CAS 高竞争退化为锁；
**CAS/原子**：无锁但有 ABA 问题，高竞争退化。

**死锁四要素**：互斥 / 持有并等待 / 不剥夺 / 循环等待——破解任一即可。

### 5.4 优先级与 QoS 全链路

**Linux CFS 调度器**：按**虚拟运行时间（vruntime）**公平分配 CPU，nice 值影响 vruntime 增速。

**Android 优先级映射**：`THREAD_PRIORITY_*` → nice → cgroup 分组。

**优先级反转**：低优先级持锁 → 高优先级等 → 中优先级抢占低 → 高优先级永远等。**破解：优先级继承互斥量（Priority Inheritance Mutex）**。

### 5.5 协程全链路

**Kotlin 协程**：编译期把 `suspend fun` 改写成**状态机**（CPS 变换），挂起 = 保存 continuation 返回，恢复 = 跳回状态机 case——**无需保存寄存器现场**，这是 1/100 切换成本的来源。

**调度器**：`Dispatchers.Default`（CPU 密集，N=核数）、`Dispatchers.IO`（IO 密集，64 线程池）、`Dispatchers.Main`（主线程 Looper）。

### 5.6 进程创建全链路

**Android Zygote fork**：
```
Zygote 预加载 framework/.so → fork(SyscallEntry) → clone 共享页表 →
AppRuntime.start → ActivityThread.main → bindApplication → onCreate
```

**CoW 边界**：详见 §01.2 深潜。

### 5.7 IPC 通信全链路

**Binder** = 一次拷贝 + 内核中转 + 异步线程池（Binder thread）。

**路径**：
```
Client Proxy.transact → 用户态 → ioctl → Binder Driver 一次 copy_from_user →
Server Binder thread 读 → Server.onTransact → 结果再 copy 回去
```

**为什么是"一次拷贝"**：Binder Driver 把目标进程的接收缓冲区**预 mmap 到内核**，发送方 copy 到内核时直接落到接收方的内存映射里，省了"内核 → 接收方"那一次。

### 5.8 共享内存全链路

**Android `MemoryFile`/`ASharedMemory`** 底层是 **ashmem**（Android Shared Memory），`mmap` 到多进程地址空间。

**零拷贝**但：
1. 首次建立映射仍需 syscall；
2. 需要应用层**同步**（否则读写竞争）——通常配合 Binder 做元数据同步。

### 5.9 进程生命周期全链路

**oom_score_adj 分档**：
```
0           系统服务 / Launcher
0-100       前台 Activity / 前台 Service
100-500     可见 / 感知服务
500-900     后台 Service
900+        空进程
```

**lmkd 从高到低杀**，直到压力缓解。详见内存篇 §5.4 深潜。

## 06、高频追问

> 13 个"陷阱题"——每题按"问题 → 直觉答案 → 为什么错 → 正确答案 → 延伸追问"展开。
>
> **本节骨架版**：Block 1 轮次先列出 13 问主题与一句话答案，后续轮次按内存篇密度展开完整的"直觉→错因→正解→追问"四段式。

### Q1 线程池无界队列为什么危险
**一句话**：`newCachedThreadPool` 和 `LinkedBlockingQueue` 无 size 会把 OOM 从"内存泄漏"级降级到"几秒钟一发"——队列堆积比内存泄漏快几个数量级。

### Q2 自旋锁什么时候反而比互斥锁快
**一句话**：当临界区执行时间 < 1μs 时，自旋消耗的 CPU 远少于一次 futex 内核往返；超过这个阈值自旋就是纯烧电（见 §01 深潜）。

### Q3 优先级反转怎么破
**一句话**：优先级继承互斥量（Priority Inheritance Mutex）——持锁线程临时继承等锁最高优先级，避免被中优先级抢占。

### Q4 协程真的省线程吗
**一句话**：挂起时省线程（IO 密集场景），执行时仍占线程（CPU 密集场景）——百万协程的收益**只在"等待占比 > 95%"的场景兑现**。

### Q5 多进程一定比单进程稳吗
**一句话**：隔离的收益是概率性的（故障时才兑现），代价是确定性的（每天都在交房租）——80% 应用用单进程最好。

### Q6 Binder 跨进程比同进程慢多少
**一句话**：Binder 本地同步调用 1-5μs，跨进程完整调用链 100μs-10ms——比同进程方法调用慢 100-10000 倍。

### Q7 iOS 几乎单进程是不是就没进程问题
**一句话**：没多进程架构问题，但有**后台执行时限**问题——iOS 把"进程问题"转移到"系统强制回收 vs 后台任务续命"的斗争上。

### Q8 保活做好就能"不被杀"吗
**一句话**：A8+ 后 Doze/App Standby + A11+ 后进程贪婪打压，**保活成功率结构性下降**——现在的"保活"方向是"快速重启 + 状态恢复"而不是"永不被杀"。

### Q9 SharedMemory 真的零拷贝吗
**一句话**：数据传输零拷贝，但**元数据同步仍要走 Binder/syscall**，建立映射本身要 syscall——"零拷贝"是数据面不是控制面。

### Q10 协程为什么还需要线程池
**一句话**：协程是调度单位，线程是执行单位——没有线程池协程无处运行。见 §00.3 展开。

### Q11 加线程为什么反而慢
**一句话**：三笔账——切换率超临界（22K→35K/s）、cache 污染放大、锁竞争加剧。线程数超过"核数 × (1 + 等待/CPU)"后收益转负。

### Q12 fork 为什么比 exec 快几十倍
**一句话**：fork 用 CoW 共享父进程的所有页，exec 要重新 load/link/init 运行时——Android Zygote fork 省掉了后者的 500ms。

### Q13 ANR 和线程模型的关系
**一句话**：ANR 的 70% 不是主线程 CPU 不够，而是**主线程等别人**（锁 / Binder / IO / cgroup 限流）——只盯 CPU 曲线会漏掉大半。

## 07、面试模板

> 5 个最高频面试题的**标准回答模板**。背会这 5 个，面试并发部分基本稳了。
>
> **本节骨架版**：Block 1 轮次先给 5 个模板的 60 秒精华版，后续轮次补足 90 秒详细版 + STAR 结构。

### A1 线程优化理解

**60 秒**：

> 线程优化的本质是"**用切换/锁开销兑换延迟缩短**"，核心公式：业务耗时 = 任务总量 / 并发度。并发度被物理封顶（核数 × IPC × 频率），不是"开更多线程"。
>
> 三类问题形态：**调度不当**（主线程做大活）、**同步开销**（锁等待）、**资源浪费**（线程数膨胀）。
>
> 四层治理按 ROI：主线程减负 > 同步治理 > 线程池统一 > 优先级调度。
>
> 直播案例：卡死率 7.3% → 0.3%，线程数 187 → 52，切换率 22K/s → 4.2K/s。

### A2 卡顿排查

**60 秒**：

> 第一步分流：**主线程利用率高 → on-CPU（火焰图找平顶）**；**利用率低却卡 → off-CPU（70% 场景）**。
>
> off-CPU 用 Perfetto 看主线程状态泳道：S 态等锁、D 态等 IO/Binder、R 态排队。
>
> 工具三件套：线程清单（`/proc/<pid>/task`）、系统 trace（Perfetto）、锁竞争（`lock_contention`）。
>
> 口诀：**先看利用率分流 → 高走火焰图 → 低走状态泳道**。只盯 CPU 曲线会漏掉 70% 真相。

### A3 多进程架构决策

**60 秒**：

> **三问法则**：这个模块多常崩？崩了多严重？独立进程常驻多少 MB？
>
> **决策树**：高崩溃风险拆（WebView/音视频）、常驻低活性删或换 FCM（Push/同步）、短生命周期不拆（相机）、核心业务永不拆。
>
> **铁律**：隔离收益是概率性的，代价是确定性的——80% 应用用单进程最好，20% 用主 + 风险隔离，几乎没人需要 5 进程以上。
>
> 金融案例：5 进程 → 2 进程，PSS -47%，被杀率 22% → 3%。**最大的奖励是系统不再把你当贪婪应用**。

### A4 协程 vs 线程池

**60 秒**：

> 协程是**调度单位**，线程池是**执行单位**——不是替代关系。
>
> 协程切换 ~200ns、线程切换 ~20μs，差 100×——但只在**等待占比 > 95%**（IO 密集）时兑现。CPU 密集任务开再多协程仍是单核算力。
>
> 阻塞调用（`Thread.sleep`、同步 Binder、文件 IO）会**饿死协程调度线程**——必须用 `Dispatchers.IO` 或非阻塞 API。
>
> 实战建议：IO 密集 / 高并发网络用协程，CPU 密集任务仍用线程池，混合场景用结构化并发（`coroutineScope`）管理生命周期。

### A5 优化故事线

**60 秒双案例串讲**：

> **线程案例（直播卡死）**：V9.2 开播"全异步并行"后卡死率飙到 7.3%，经验派 3 周（32 线程、死锁检测、spinlock）折腾到 9.1%。按方法派 7 天闭环：Perfetto 三方案归因三病灶并存 → 四层治理（IdleHandler 切片 + 锁拆 4 把 + 统一线程池 + QoS 继承）→ 卡死率 0.3%、首屏 1.0s、线程 52、切换 4.2K/s。
>
> **进程案例（金融瘦身）**：5 进程架构常驻 450MB，经验派 5 周（加保活 / 调上限 / 加 IPC 缓存）折腾被杀率反升到 22%。按方法派 8 天：进程清单 + Binder trace + CoW 共享率归因到"3 个保活/守护进程无价值" → 四层治理（删 3 进程 + Binder 批处理 + 共享内存 + 快速重启）→ PSS 240MB、OOM 0.6%、被杀 3%、推送到达 91% → 97%。
>
> **共同沉淀**：**线程优化先治 off-CPU，进程优化先问必要性**。经验派总错在"用更多资源治资源问题"（加线程/加进程），方法派都是"先归因到物理代价，再按 ROI 治理"。

## 附录：双贯穿案例

> **本附录骨架版**：Block 1 轮次先保留两个案例的核心数据表，后续轮次补足详细叙事与反面教材流程。

### 附录 A：直播卡死案例（线程维度）

**背景**：某直播 App V9.2 上线"开播秒开"，推流准备从异步改成全异步并行。结果反而：
- 开播 3 秒卡死率 **0.5% → 7.3%**；主播首屏 P95 **1.2s → 4.8s**；
- 线程数稳态 65 → **187**，内存涨 80MB；
- 日活主播 **-12%**，单日损失约 **600 万**。

**经验派 3 周反面教材**：
| 周次 | 动作 | 结果 |
|---|---|---|
| 1 | 线程池 8 → 32 | 卡死率升到 9.1%，切换暴涨 |
| 2 | 加死锁检测 | 没死锁但卡依旧 |
| 3 | spinlock 换 mutex | CPU 炸到 100%，发热严重 |

**方法派 7 天闭环**：
- Day1：Perfetto 三方案归因 → 三病灶（线程 187 / 切换 22K/s / 锁等待 850ms）并存；
- Day2：决策树定位（线程膨胀 / 调度不当 / 同步开销）；
- Day3-4：四层治理（IdleHandler 切片 + 锁拆 4 把 + 统一线程池 + QoS 继承）；
- Day5：Macrobenchmark 验证；Day6-7：灰度 + 上线。

**结果对比表**：

| 指标 | 经验派 3 周 | 方法派 7 天 |
|---|---|---|
| 卡死率 | 9.1% | **0.3%** |
| 首屏 P95 | 4.8s | **1.0s** |
| 线程数 | 230 | **52** |
| 切换率 | 35K/s | **4.2K/s** |
| 锁等待 P99 | 850ms | **18ms** |
| 日活主播 | -12% | **+3%** |

### 附录 B：金融 5 进程瘦身案例（进程维度）

**背景**：某金融 App 历史 5 进程架构（主/Push/WebView/守护/拉活），架构初心"模块隔离防崩溃"：
- 常驻 PSS **450MB**，中端机 OOM 率 **4.8%**；
- 冷启动 P95 **3.6s**，用户点通知冷启占 38%；
- A11+ 升级后主进程被杀率 **2% → 22%**（系统认定贪婪应用）；
- 应用商店卡顿差评 **12,000/月**。

**经验派 5 周反面教材**：
| 周次 | 动作 | 结果 |
|---|---|---|
| 1 | 加强双进程互拉保活 | 被杀率反升到 22% |
| 2 | Push 进程内存上限调小 | Push OOM 消息丢失 ×8 |
| 3 | 加 IPC 缓存层 | 引发数据不一致 bug |
| 4 | WebView 进程预热常驻 | 内存又涨 30MB |
| 5 | 调 Push 优先级 | 无改善 |

**方法派 8 天闭环**：
- Day1：进程清单 + Binder trace → Push 每天只干 8-12 次活却占 80MB、主↔Push 心跳 35 次/秒；
- Day2：逐进程评估必要性 → **5 个里 3 个无价值**（Push/守护/拉活）；
- Day3：用保活实验数据说服架构师放弃"5 进程不能动"；
- Day4-5：四层治理（删 3 进程 + 换 FCM + Binder 批处理 + 共享内存 + 快速重启）；
- Day6：被杀-重启-恢复自动化用例；Day7-8：灰度上线。

**结果对比表**：

| 指标 | 经验派 5 周 | 方法派 8 天 |
|---|---|---|
| 进程数 | 5 | **2**（主 + WebView） |
| 常驻 PSS | 450MB | **240MB**（-47%） |
| 冷启 P95 | 3.6s | **1.2s** |
| OOM 率 | 4.8% | **0.6%** |
| 主进程被杀率 | 22% | **3%** |
| 推送到达率（FCM） | 91% | **97%** |
| 用户主动回归率 | -8% | **+5%** |

**核心洞察**：**进程治理的最大杠杆是删除非必要进程**。删 3 个让 PSS -47%、被杀率反而 22% → 3%——**系统不再把你当贪婪应用，是最大的奖励**。

> **一句话总结**：
>
> 并发有两级——**线程级在一个地址空间内用 CPU 兑换延迟**，**进程级在多个地址空间间用 IPC 兑换隔离**。两级的治理都在同一个真理下：**并发不是免费的，每次并发都是一次交换**——先算清代价公式再动手，就能避免 90% 的"用更多资源治资源问题"的反面教材。
