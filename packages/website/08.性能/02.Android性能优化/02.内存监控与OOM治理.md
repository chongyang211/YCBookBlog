## 01.开篇灵魂拷问

读文章前，先问自己三个问题。答得上来，说明你已理解；答不上来，就是本文的学习目标。

### 1.1 内存占用之惑

**Q：为什么你的 App 占用 200MB 还流畅，别人 100MB 却卡？**

- **直觉答案**："占用越少越好。"
- **真实答案**：**内存不是"占多少"的问题，是"什么时候有什么"的问题**。

稳定占用 200MB vs 波动占用 50–150MB，后者用户体验远差——因为波动意味着频繁 GC，每次 Stop-The-World 5–20ms 直接掉帧。

**更深一层**：GC 的开销不只是 STW，还包括：

- **扫描成本**：Mark 阶段遍历 GC Root 可达图，对象越多越慢；
- **写屏障成本**：Concurrent GC 期间，每次引用赋值都走 write barrier，拖慢业务代码 3–8%；
- **复制/压缩成本**：Moving GC 要搬运存活对象，还要修正所有指针。

所以**内存优化的第一个心法**：**稳定 >> 低占用**。

### 1.2 OOM的疑惑

**Q：为什么物理内存还够，App 却崩了？**

- **直觉答案**："内存满了才 OOM。"
- **真实答案**：**OOM 不是单一问题，而是至少 4 种独立触发机制的统称**。

| 类型 | 触发条件 | 典型表现 |
|---|---|---|
| A 堆 OOM | Java 堆到达 maxHeap | `OutOfMemoryError` |
| B 系统 OOM | 整机内存紧张 | LMK / jetsam 杀进程 |
| C 地址空间 OOM | 32 位找不到连续大块 | 物理够但分配失败 |
| D 资源耗尽 | FD / 线程到达上限 | `Too many open files` |

**C 类是面试重灾区**：32 位 App 看起来内存只用了 200MB，maxHeap 还有 300MB，但一次 20MB Bitmap 分配就能 OOM——因为虚拟地址空间碎片化后，找不到 20MB 的连续块。

**为什么会这样**？因为 malloc / mmap 要求**虚拟地址连续**，这是 CPU MMU 寻址的物理约束（页表项按连续虚拟地址映射）。不是内核不想给，是硬件决定了必须连续。

**第二个心法**：**OOM 必须先分类，才能对症施治**。

### 1.3 如何监控内存

**Q：为什么 LeakCanary 没报警，上线还是出 OOM？**

- **直觉答案**："工具没报就是没泄漏。"
- **真实答案**：**LeakCanary 有三大盲区**：

1. **只检测 Activity / Fragment / View / ViewModel**，Service / Receiver / 自定义类不管；
2. **检测延迟 30 秒+**，一次短切换的泄漏可能被漏报；
3. **看不见 Native 泄漏**，Bitmap Native 内存、JNI GlobalRef、so 库 malloc 全是盲区。

**本质原因**：LeakCanary 的核心机制是"**WeakReference + 主动 GC + ReferenceQueue**"——它的能力边界就是"Java 层 + 已知可疑对象"。这是设计约束，不是实现问题。

**第三个心法**：**监控必须组合使用——没有任何单一工具覆盖所有盲区**。

## 02.探索问题本质

### 2.1 问题现象分类

**🤔 疑惑**：卡顿、崩溃、后台被杀、发热……这些现象差异巨大，难道都是"内存"的问题？

**💡 解答**：是也不是。表现不同，但病因可以归到三类共性问题。

| 现象 | 真实病因 | 用什么工具能看到 |
|---|---|---|
| 直接崩溃 | 一次分配失败（堆/地址空间） | OOM 日志 + Dump |
| 后台被杀 | 系统整机压力大 | LMK log / jetsam log |
| 滚动卡顿 | GC 频繁 STW | Profiler Allocation |
| 越用越慢 | 内存泄漏累积 | LeakCanary |
| 发热费电 | 分配速率过高 | Profiler Memory 曲线 |

三类共性问题：

```
┌─────────────────────────────────────────────┐
│ ① 抖动（Churn）：对象生得太多太快            │
│    特征：内存曲线锯齿状，GC 频繁              │
│    典型：onDraw/onBindViewHolder 里 new     │
├─────────────────────────────────────────────┤
│ ② 泄漏（Leak）：对象活得太久，该死不死        │
│    特征：内存曲线只升不降                     │
│    典型：静态引用、Handler 持 Activity        │
├─────────────────────────────────────────────┤
│ ③ 溢出（OOM）：对象占得太大，一次爆堆          │
│    特征：进程突然崩溃                         │
│    典型：大 Bitmap、无上限缓存、地址碎片       │
└─────────────────────────────────────────────┘
```

### 2.2 三态模型说明

进一步抽象，三类问题可以统一到对象的**三态生命周期**错配：

```
   分配 ─▶ 使用 ─▶ 不可达 ─▶ 回收
    │       │        │         │
    ▼       ▼        ▼         ▼
   过快 → 抖动   过久 → 泄漏   不及时 → 溢出
```

**本质定义**：内存性能 = 对象的"生 / 存 / 死"与业务时间窗口的对齐程度。不是"占多少"，而是"该活着的活着、该死的死掉"。

**为什么这个抽象有价值**：

- **跨平台通用**：Android ART GC、iOS ARC、Web V8 GC、嵌入式 C++ Smart Pointer——底层机制不同，但都在管理"生/存/死"三态；
- **指导归因**：遇到问题先问"哪个阶段错配"，比盲目看指标高效；
- **指导治理**：抖动的治法（减少生）、泄漏的治法（缩短存）、溢出的治法（控制峰值），从模型自然导出。

**▶▶ 案例回扣**：图片浏览器案例中，经验派花 3 周"减负"（缩缓存、下采样、largeHeap）只碰了"溢出"维度，完全没管"泄漏"和"抖动"——这就是无效的原因。方法派用三态模型，5 天分别治理三类，OOM 率 8.3% → 0.4%。

### 2.3 面对面试锚点

**Q："你怎么理解内存优化？"**

**30 秒电梯答案**：内存优化的本质是"管理对象生命周期"。所有问题可以归为三类：抖动（生得太多）、泄漏（活得太久）、溢出（占得太大）。目标不是把内存压到最低，而是让对象的"生、存、死"对齐业务需要的时间窗口——稳定可预测的 200MB 远好于波动的 50-150MB。

**3 分钟展开版**：电梯答案 + 三类问题的典型案例 + 自己做过的一次优化（比如 Bitmap 下采样 + LRU 上限按 maxMemory/8 动态计算 + onTrimMemory 分级响应）。

## 03、排查归因

### 3.1 常见OOM分类

线上你拿到的 OOM 通常只有一行栈：

```
java.lang.OutOfMemoryError: Failed to allocate a 20971532 byte allocation 
  with 4194304 free bytes and 3MB until OOM
    at android.graphics.BitmapFactory.decodeStream(...)
```

你能看出"Bitmap 解码失败"，但看不出：1.到底是堆满了，还是地址空间碎片？2.是单张图太大，还是累积泄漏到临界？3.是不是 LMK 杀的（根本没日志）？

**所以第一步永远是：先分类**。

```
OOM 发生
  │
  ├─ 有 OutOfMemoryError 栈？
  │    │
  │    ├─ 是 → A 类（堆 OOM）：看 Java heap 占用，主因：缓存无上限 / 大对象 / 泄漏
  │    └─ 否，但进程被杀 → 看 LMK log 或 jetsam log
  │          └─ B 类（系统 OOM）：主因：整机压力大 + 应用未响应 onTrimMemory
  │
  ├─ Native crash + SIGSEGV/SIGABRT？
  │    └─ C 类（地址空间 OOM，32 位专属）：看 /proc/[pid]/maps 最大连续块
  │             主因：虚拟地址空间碎片，分配失败
  │
  └─ 错误信息含 "Too many open files" / "pthread_create failed"？
       └─ D 类（资源耗尽，伪装成 OOM），主因：FD 泄漏 / 线程泄漏
```

**🔑 关键认知**：四类的根因、工具、治理手段完全不同。混为一谈必然踩坑。四种约束，四种治法。**为什么分四类是本质**？因为背后是四种独立的物理约束：

- A = **语言运行时的堆上限**（JVM/ART 自己的边界，用来防止一个应用拖垮系统）
- B = **操作系统的物理 RAM**（所有进程共享的硬件边界）
- C = **CPU 的虚拟地址位宽**（32 位 vs 64 位的硬件决定）
- D = **内核的资源表上限**（FD 表、线程表的大小）

**A 类（堆 OOM）—— ART 堆上限是怎么决定的？** ART 的 maxHeap 不是写死的常量，而是在 **Zygote 启动时**由系统属性决定：

```
dalvik.vm.heapgrowthlimit = 192m   # 不加 largeHeap 的上限
dalvik.vm.heapsize        = 512m   # 加 largeHeap 的上限
dalvik.vm.heapstartsize   = 8m     # 初始堆大小
dalvik.vm.heaptargetutilization = 0.75  # GC 后目标占用率
```

**heap 增长机制**：

```
初始 heapstartsize → 对象分配 → 到 target * 1/utilization 时触发 GC
                                      ↓
                              GC 后看占用率
                                      ↓
                         ┌─ 占用高 → 扩堆（最多到 heapgrowthlimit）
                         └─ 占用低 → 收堆（最少到 heapminfree）
```

所以 ART 的 heap 是**弹性的**，不是一开始就占满 192MB。但扩堆到 heapgrowthlimit 后还不够，就抛 OutOfMemoryError。

**查看当前设备配置**：

```bash
adb shell getprop | grep dalvik.vm.heap
```

**B 类（LMK）—— oom_adj_score 的内核算法** Android 的 LowMemoryKiller 是 Linux OOM Killer 的"**提前触发版**"。核心数据结构在 `/proc/[pid]/oom_score_adj`（可调）和 `/proc/[pid]/oom_score`（内核计算）：

```
oom_score = (RSS + Swap) × 1000 / total_memory + oom_score_adj × 10
```

LMK 按 oom_score 排序，分数高的先杀。关键 oom_score_adj 值（AMS 维护）：

| 进程状态 | oom_score_adj | 相对不易被杀 | 实际案例（用户视角） |
|---|---|---|---|
| 系统进程 | -1000 | 永不杀 | `system_server`、桌面 Launcher、电话拨号器——"桌面闪退"几乎不可能，出了问题也是重启系统 |
| 前台 Activity | 0 | 几乎不杀 | 用户正在操作的"微信聊天页"——此时你打开的相机 App 内存爆了，被杀的是相机不是微信 |
| 可见进程 | 100 | 轻微保护 | 视频画中画小窗、悬浮窗聊天球、输入法——你看得到它，但焦点在别的 App |
| 感知进程（通知/服务） | 200 | 一般保护 | 网易云音乐通知栏播放中、高德导航锁屏后——用户"知道它还活着"，杀掉会被察觉 |
| 前台 Service | 300 | 较易保护 | 正在进行的文件下载、VoIP 通话——浏览器切后台下载继续，就是靠这个优先级 |
| 服务进程 | 500 | 后台保活 | 后台消息长连接、WorkManager 定时任务——杀掉后推送收不到，但不影响当前操作 |
| 后台 Activity | 700 | 优先被杀 | 按 Home 键切走的淘宝商品页——内存紧张时第一个牺牲品，切回来变成"重新加载" |
| 空进程 | 900 | 最先被杀 | 刚"退出"的美团但进程还驻留（为了下次秒开）——LMK 的"活体器官供体"，先杀它腾内存 |

**AMS 更新 oom_score_adj 的调用链**：

```
ActivityThread 生命周期切换
    ↓
ProcessStateRecord.setProcState()
    ↓
OomAdjuster.computeOomAdjLSP()  // 计算新的 adj
    ↓
ProcessList.setOomAdj()
    ↓
写入 /proc/[pid]/oom_score_adj
```

**这解释了为什么前台 Service 能保活**——它把 oom_score_adj 从 700（后台）压到 300（前台 Service），LMK 几乎不会选它。

**C 类（地址空间）—— MMU 为什么要求连续？** 32 位 CPU 的 MMU 用**多级页表**翻译虚拟地址：

```
32 位虚拟地址
┌──────────┬──────────┬──────────────┐
│ 10 bit   │ 10 bit   │   12 bit     │
│ 页目录   │ 页表     │   页内偏移   │
└──────────┴──────────┴──────────────┘
     ↓          ↓             ↓
   PDE[]  →  PTE[]  →    物理页 + offset
```

每个 PDE 覆盖 4MB（1024 × 4KB），所以**分配 > 4MB 的对象必须跨多个 PDE/PTE**。要让一段连续虚拟地址对应连续页表项，就必须找到一段"**没有被占用的连续地址区间**"——这就是"连续块"的物理含义。

碎片化后，可能剩余 500MB 虚拟地址，但分散成几百段小块；20MB 分配要求找到至少 5120 个连续页表项（20MB / 4KB），找不到就 OOM。

**D 类（资源耗尽）—— FD 和线程的物理上限**

```bash
# 查看 FD 上限
cat /proc/[pid]/limits | grep "Max open files"
# 典型值：1024（soft）/ 4096（hard）

# 查看线程上限
cat /proc/[pid]/limits | grep "Max processes"
# 典型值：几千到几万，取决于设备
```

**内核机制**：每个 FD 在内核里是一个 `struct file` 条目，占 ~200 字节。FD 表大小 = 上限 × 条目大小；每个线程占 Native 栈 1MB（默认），100 线程 = 100MB 虚拟地址。32 位设备上线程数间接受地址空间约束。

### 3.2 内存曲线识图

拿到 Profiler / 线上监控的内存曲线，形状直接告诉你病因：

```
   ↑ 内存
   │                                      ╱  单调上升 → 泄漏
   │                              ╱──────╯
   │                      ╱──────╯
   │              ╱──────╯
   │──────╱──────
   └────────────────────────────▶ 时间

   ↑ 内存
   │   ╱╲  ╱╲  ╱╲  ╱╲  ╱╲         锯齿 → 抖动
   │  ╱  ╲╱  ╲╱  ╲╱  ╲╱  ╲       （GC 频繁回收）
   │ ╱
   └────────────────────────────▶ 时间

   ↑ 内存                   ╱╲
   │                        │ │             尖峰 → 一次性大分配
   │                        │ │             （大 Bitmap/JSON）
   │_______________________╱  ╲____________
   └────────────────────────────▶ 时间

   ↑ 内存
   │                  ┌────┐
   │          ┌────┐  │    │              阶梯 → 缓存堆积
   │  ┌────┐  │    │  │    │              （缓存无上限/未淘汰）
   │__│    │__│    │__│    │_____________
   └────────────────────────────▶ 时间
```

**为什么曲线形状能映射病因**？因为每种病因对应一种独特的"分配-回收节奏"：

- **只分配不回收** → 单调上升（泄漏的物理定义）
- **分配快-回收快-周而复始** → 锯齿（Young GC 的物理表现）
- **一次大分配** → 尖峰（Large Object Space 的分配）
- **分配快-回收慢-最终 LRU 淘汰** → 阶梯（缓存命中率收敛）

**面试加分点**：说出"曲线形状 ↔ 病因"的映射，比堆砌工具名字高级得多。

🔬 深潜：锯齿波的数学模型，锯齿的**周期和振幅**可以用公式精确预测，这个公式面试里拿出来能炸场：

```
GC 周期 T = Eden 大小 / 分配速率
GC 振幅 A = Eden 大小（填满一次就 GC 一次）
每秒 STW 占比 = (GC 频率 × 单次 STW) / 1000
```

**举例（Pixel 6，Eden ≈ 4MB，Young GC STW ≈ 10ms）**：

| 分配速率 | GC 周期 | GC 频率 | 每秒 STW | 用户感知 |
|---|---|---|---|---|
| 1 MB/s | 4 秒 | 0.25 Hz | 2.5ms | 无感 |
| 5 MB/s | 800ms | 1.25 Hz | 12.5ms | 轻微 |
| 10 MB/s | 400ms | 2.5 Hz | 25ms | 掉帧 |
| 30 MB/s | 133ms | 7.5 Hz | 75ms | 持续卡 |
| 100 MB/s | 40ms | 25 Hz | 250ms | 严重卡 |

**公式的物理意义**：

- **分配速率决定 GC 频率**：Eden 大小是常量（JVM 自适应，但短期稳定），分配越快越快填满；
- **STW 决定帧预算损失**：16.67ms 是 60fps 帧预算，任何超过都会掉帧；
- **分代假说的根基**：绝大多数对象在 Young GC 时就死掉，所以 Eden 填满后"幸存者"很少，GC 耗时相对可控（扫描快）。

**反向推演**：如果你的曲线锯齿周期是 2 秒，Eden 是 4MB，那你的分配速率就是 **2 MB/s**——不需要 Profiler，看曲线就能估。

🔬 深潜：阶梯形态下的"稳态内存"。阶梯曲线最终会**水平收敛**，这是 LRU 的物理必然：

```
   内存
   │                                _______________ ← 稳态
   │                   __________┘
   │        _______┘
   │  __┘
   │_
   └─────────────────────────────────▶ 时间
     阶段 1：缓存未满，持续增长
     阶段 2：接近 maxSize，淘汰 ≈ 插入
     阶段 3：命中率收敛，内存趋于稳定
```

**稳态内存 ≈ LRU maxSize × 平均对象大小**。所以：

- 配 LRU `maxSize = maxMemory/8` 本质是**预算规划**，决定了内存天花板；
- 阶梯爬升过快 → 命中率低（每次都 miss，不断淘汰 + 插入）；
- 阶梯爬升过慢 → 可能缓存失效机制有问题（如 LRU 实际是 FIFO）。

### 3.3 内存泄漏引用链法

当你确定是泄漏（曲线单调上升），需要知道"谁没放手"。流程：

```
取 Heap Dump（hprof）
    ↓
找到泄漏对象（LeakCanary 已经点名了 LeakedActivity）
    ↓
从 GC Root 求最短引用链
    ↓
沿链向上，找第一个"不该持有 LeakedActivity 的引用"
    ↓
修复这一处（弱化 / 解绑 / 对齐生命周期）
```

**GC Root 的五大类型**（这是面试高频深挖点）：

| GC Root 类型 | 本质含义 | 常见例子 | 占泄漏比例 |
|---|---|---|---|
| **Static Field** | 类加载后常驻的静态字段 | 单例持 Context、static 容器 | 50% |
| **Thread** | 活跃线程的栈帧 + ThreadLocal | HandlerThread、未取消的 AsyncTask | 20% |
| **Native Reference** | JNI 的 GlobalRef / WeakGlobalRef | NewGlobalRef 未配对 Delete | 10% |
| **System Class** | 系统类加载器加载的类 | LocationManager.mListener 持 Activity | 10% |
| **Stack Local** | 当前线程调用栈内的局部变量 | 不常泄漏（栈帧退出就释放） | < 10% |

**为什么是这五类**？因为 JVM/ART 的 GC 需要一个**可达性判定的起点集合**——从这个集合出发做广度/深度遍历，能到达的就是存活对象，到不达的就回收。这五类是设计上必须作为起点的：类（永久加载）、线程（永久活跃）、JNI（跨堆桥梁）、系统类（系统持有）、栈（当前执行）。

**🧠 面试速记**：85% 的 Android 泄漏来自 **Static Field + Thread**。知道这个，面试里能把排查方向直接聚焦。

#### 🔬 深潜：支配树与 Retained Size

分析 hprof 时，光看"引用链"不够——还要看"**释放这个对象能回收多少内存**"。这就是 **Dominator Tree（支配树）** 的用途。

**概念**：

- **浅堆（Shallow Size）**：对象自身占用（对象头 + 字段）；
- **深堆（Retained Size）**：**如果回收这个对象，连带能回收多少**（它支配的所有对象之和）。

**支配关系**：对象 A 支配 B，当且仅当从 GC Root 到 B 的**所有路径都经过 A**。

```
     GC Root
       │
       ▼
       A ─── 支配 → B, C, D
       │
       ├─▶ B
       ├─▶ C ─── 支配 → E
       │           │
       │           ▼
       │           E
       └─▶ D
```

- A 的 Retained Size = Shallow(A) + Shallow(B) + Shallow(C) + Shallow(D) + Shallow(E)
- C 的 Retained Size = Shallow(C) + Shallow(E)

**算法**：**Lengauer-Tarjan 算法**，O(E·α(E,V))。MAT 和 LeakCanary 的 shark 库都用这个。

**工程价值**：

- 泄漏时按 Retained Size 排序，第一名就是"**真正偷走内存最多的对象**"；
- 浅堆小但深堆大的对象 = "持有一整条内存链的入口" = 治理重点；
- Activity 泄漏通常 Retained Size 几 MB 到几十 MB（整个 View 树都被持有）。

**MAT 定位泄漏的流程**：

```
1. Histogram 看哪些类对象多（Shallow Size 排序）
2. 对可疑类 → Show Objects by class
3. 选大对象 → Path to GC Roots → with all references
4. 看最短引用链，定位"第一个不该持有的强引用"
5. 对比两个时间点的 hprof（Comparison）看增量
```

#### 🔬 深潜：hprof 文件格式

**hprof** 是 JVM 定义的二进制堆转储格式，Android 兼容但有扩展。核心结构：

```
HPROF Header
┌─────────────────────────┐
│ Magic: "JAVA PROFILE 1.0.3\0"  │
│ Identifier size (4/8 bytes)    │  ← 对象引用大小
│ Timestamp                      │
└─────────────────────────┘
     ↓
Records（变长记录链）
┌─────────────────────────┐
│ Tag(1B) + Time(4B) + Length(4B) + Body │
└─────────────────────────┘
     ├─ TAG=0x01 UTF8 字符串
     ├─ TAG=0x02 Load Class
     ├─ TAG=0x05 Stack Trace
     └─ TAG=0x1C Heap Dump（最大的那一块）
         ├─ 子 TAG=0xFF Root JNI Global
         ├─ 子 TAG=0x08 Root Thread Object
         ├─ 子 TAG=0x20 Class Dump
         ├─ 子 TAG=0x21 Instance Dump
         ├─ 子 TAG=0x22 Object Array
         └─ 子 TAG=0x23 Primitive Array
```

**Android 扩展**：

- Android 的 hprof 不包含 `char[]` 的内容（为了减小文件），用 shark 库解析时特殊处理；
- Native heap 不进 hprof（这就是 Profiler 看不到 Bitmap 像素的根本原因）；
- Bitmap 的 Native pixel 地址可以通过 `NativeAllocationRegistry` 关联，shark 2.x 开始支持。

**典型大小**：一个 300MB Java heap 的 hprof 文件约 **200-500MB**。KOOM 做了"**精简 dump**"：只保留对象引用关系，去掉原始数据（如 byte[] 内容），文件可缩到 1/5 到 1/10。

```
  ├─ 曲线单调上升? Yes（每滑一张涨 5-15MB，应为 0）
  │    → 泄漏型（占 60%）

```

### 3.5 面试锚点

**Q："线上 OOM 怎么排查？"**

**STAR 结构模板**：

- **S（场景）**：图片浏览器 App 在低端 2GB 设备上 OOM 率 8.3%，远超 0.1% 的行业基准。

## 04、监控体系

### 4.1 采集四类

**🤔 疑惑**：Profiler 的 Allocation Tracker 看每个对象分配栈很爽，为什么线上不能用？

**💡 解答**：开销太大。Allocation Tracker 要在每次 `new` 处插桩，单线程吞吐降到 1/3–1/10，线上开 1% 都不行。

所有平台的内存监控方案，**本质只有 4 类**——区别在于在对象生命周期的哪一段下钩子：

```
   分配 ──▶ 引用 ──▶ 不可达 ──▶ 回收
     │       │         │         │
     ▼       ▼         ▼         ▼
   ① 分配钩子    ② 堆快照      ③ 可达性扫描   ④ 系统统计
   (Allocation  (Heap Dump)  (Reachability) (PSS/RSS)
    Tracker)
```

对比四类方案：

| 方案 | 钩子位置 | 粒度 | 开销 | 线上可用 | 适用场景 |
|---|---|---|---|---|---|
| ① 分配钩子 | 每次 new/malloc | 对象级 | **高** | ❌ | 线下深度排查 |
| ② 堆快照 Dump | 某一时刻 | 完整图 | 中（STW） | ⚠️ 按需 | 线上 OOM 后触发 |
| ③ 可达性扫描 | 可疑对象 | 对象级 | **极低** | ✅ | Activity 泄漏检测 |
| ④ 系统统计 | OS 提供 | 进程级 | **极低** | ✅ | 线上常驻监控 |

**为什么只有四类**？因为对象生命周期只有四个阶段。你的钩子要么在"分配"下，要么在"引用关系"下，要么在"可达性判定"下，要么在"回收后或从外部看"。穷举完了。

**🔑 组合定律**：没有任何单一方案能 100% 覆盖。线上必须组合——

> **④ 常驻看总量 + ③ 自动检测泄漏 + ② 触发式 Dump + ① 线下深度分析**。

#### 🔬 深潜：四类方案的插桩技术

每类方案都有一套具体的"**怎么拦截**"技术，是实现层面的核心机密：

**① 分配钩子的实现技术**

| 平台 | 技术 | 原理 |
|---|---|---|
| Android Java | ART Allocation Instrumentation | ART 的 `art_quick_alloc_object_resolved_tlab` 入口可切换到慢路径 |
| Android Native | **PLT Hook** | 改 .so 的 PLT（Procedure Linkage Table）表，让 malloc 跳到钩子函数 |
| iOS | malloc_logger / dyld 符号替换 | dyld 加载时替换 `__libc_malloc` 符号 |
| Web | V8 Allocation Profiler | V8 自带的采样钩子，默认 512KB 采样一次 |

**PLT Hook 的核心机制**（Android Native）：

```c
// 原流程：
应用调 malloc(1024)
    ↓
PLT 表项（跳转占位）
    ↓
GOT（第一次调用时填充真实 libc.malloc 地址）
    ↓
真正的 malloc

// Hook 后：
应用调 malloc(1024)
    ↓
PLT 表项
    ↓
GOT（被改写指向 my_malloc）
    ↓
my_malloc {
    record_stack();         // 记录调用栈
    return real_malloc();   // 转发到真实 malloc
}
```

bhook / xHook 这类库都是改 GOT 实现的。**不改代码、不重编译、运行时生效**是它们的核心优势。

**② 堆快照的 ART 实现**

```
Debug.dumpHprofData(path)
    ↓
VMDebug.dumpHprofData() [JNI]
    ↓
ART Hprof::DumpHeap(path, fd, direct_to_ddms)
    ↓
① SuspendAll()              // 暂停所有应用线程（STW 开始）
② WalkHeap()                // 遍历所有对象
③ WriteObjects(hprof_file)  // 写文件
④ ResumeAll()               // 恢复线程
```

**STW 时长 = 对象数量 × 单对象写入耗时**。100MB 堆通常 100ms-5s。这就是为什么 LeakCanary 做 dump 时主进程会"假死"几秒。

**③ 可达性扫描的事件驱动**

关键是 **WeakReference 的入队机制**由 GC 保证，而不是业务线程：

```c
// ART GC 完成后，遍历所有 WeakReference
for (WeakRef r : weakRefs) {
    if (r.referent 不可达) {
        r.enqueue();   // 入队到关联的 ReferenceQueue
    }
}
```

所以业务线程只需 `queue.poll()` 就能发现"哪些对象被回收了"——**事件驱动而非轮询**，这是 Java Reference 机制的核心优雅之处。

**④ 系统统计的内核来源**

应用调 `Debug.getMemoryInfo()` 最终到达 Linux 内核的 **`fs/proc/base.c`**：

```
app: Debug.getMemoryInfo(info)
     ↓
JNI: android_os_Debug_getDirtyPages()
     ↓
read("/proc/[pid]/smaps")
     ↓
内核：遍历 vm_area_struct 链表，统计每个映射区
     ↓
返回 Pss / Rss / Private_Dirty 等字段
```

**开销极低**（<1ms）因为内核本来就在维护这些数据结构（页表、vma 链表），统计是"**查询式**"而非"**计算式**"。

### 4.2 内存指标

**面试高频问**，必须答得清楚：

| 指标 | 全称 | 含义 | 用途 |
|---|---|---|---|
| VSS | Virtual Set Size | 虚拟地址空间总量 | 判定 32 位 OOM 上限（4GB） |
| RSS | Resident Set Size | 物理内存实占（含共享） | 高估，参考价值低 |
| **PSS** | Proportional Set Size | 物理内存按比例分摊共享 | **最常用**，接近"真实占用" |
| USS | Unique Set Size | 仅本进程独占的物理内存 | 评估"杀掉能释放多少" |

**🧠 记忆口诀**：

- 看进程占用 → **PSS**（线上常规监控）
- 看单进程"杀了能回收多少" → **USS**（后台杀策略）
- 看地址空间够不够 → **VSS**（32 位 OOM）
- RSS 一般不用（含共享内存，偏高）

**PSS 为什么是"按比例分摊"**？因为多个进程共享同一个物理页（比如 libc.so 的代码段），直接把这页算给某个进程都不公平。PSS 的算法是：**该页被 N 个进程共享 → 每个进程算 1/N 份**。这保证了"所有进程 PSS 之和 ≈ 系统物理内存使用"，有全局意义。详见 §6.7。

#### 🔬 深潜：Debug.MemoryInfo 的细分字段

`Debug.getMemoryInfo()` 返回的不是单一数字，而是**按内存区域细分**的多维数据：

```kotlin
val memInfo = Debug.MemoryInfo()
Debug.getMemoryInfo(memInfo)

// Java 层
memInfo.dalvikPss          // Dalvik/ART heap（Java 对象）
memInfo.dalvikPrivateDirty // Java heap 独占脏页
memInfo.dalvikSharedDirty  // Java heap 共享脏页

// Native 层
memInfo.nativePss          // malloc 分配的（含 Bitmap pixel，Android 8+）
memInfo.nativePrivateDirty // Native 独占脏页

// 其他
memInfo.otherPss           // GPU / Dex / ashmem 等
memInfo.otherPrivateDirty
memInfo.totalPss           // 以上之和
```

**读取 getMemoryStat() 的隐藏字段**（Android 23+）：

```kotlin
val stats = memInfo.memoryStats
// 隐藏字段：
// summary.java-heap       → Java 对象实际用量（含 compile 对象）
// summary.native-heap     → Native malloc 用量
// summary.code            → dex / so 代码段
// summary.stack           → 线程栈总和
// summary.graphics        → GL mtrack 显存
// summary.private-other   → 其他独占
// summary.system          → 系统分摊
// summary.total-pss       → 总 PSS
// summary.total-swap      → zram
```

**工程启示**：线上监控**单一 PSS 不够**，要分区域看——很多情况下 Native 涨得猛而 Java 稳定，直接定位到 Bitmap pixel 泄漏；code 突然涨说明 dex 加载异常。

#### 🔬 深潜：PSS 的计算代码（Linux 内核）

Linux 内核 `fs/proc/task_mmu.c` 里 PSS 的核心算法：

```c
// 简化版本
for_each_vma(vma) {
    for_each_page_in_vma(page) {
        if (page == NULL) continue;  // 未分配的虚拟页
        
        int mapcount = page_mapcount(page);  // 该物理页被几个进程映射
        pss += PAGE_SIZE * 1000 / mapcount;  // 按分摊数分（×1000 保精度）
    }
}
return pss / 1000;  // 还原
```

**关键观察**：

- `page_mapcount(page)` 不是遍历所有进程，而是查 `struct page` 的 `_mapcount` 字段（反向映射，内核预先维护）；
- 所以 PSS 查询 O(N) with N = 虚拟页数，不是 O(进程数 × N)；
- 这就是为什么 `cat /proc/[pid]/smaps` 可以在毫秒级返回。

### 4.3 前兆信号

**🤔 疑惑**：为什么 onTrimMemory 是"黄金窗口"？

**💡 解答**：OS 在内存不够之前，会先通知应用降级。你有 **5 秒到 30 分钟**不等的响应窗口——这是治理的最佳时机。

实测各级响应时窗（真实数据）：

| 级别 | 中位到被杀时间 | 应用动作 |
|---|---|---|
| TRIM_MEMORY_RUNNING_MODERATE | > 10 min | 清非必要缓存（1/2） |
| TRIM_MEMORY_RUNNING_LOW | 2 min | 积极清理（1/4） |
| TRIM_MEMORY_RUNNING_CRITICAL | 30 s | 只保留必需 |
| TRIM_MEMORY_UI_HIDDEN | 无限制 | 释放 UI 资源 |
| TRIM_MEMORY_BACKGROUND | 10 min | 后台缓存清理 |
| TRIM_MEMORY_COMPLETE | **5 s** | **全部释放**，否则必死 |

```kotlin
override fun onTrimMemory(level: Int) {
    when (level) {
        TRIM_MEMORY_RUNNING_MODERATE -> imageCache.trimToSize(imageCache.maxSize() / 2)
        TRIM_MEMORY_RUNNING_LOW -> imageCache.trimToSize(imageCache.maxSize() / 4)
        TRIM_MEMORY_RUNNING_CRITICAL -> keepEssentialOnly()
        TRIM_MEMORY_UI_HIDDEN -> releaseUIResources()
        TRIM_MEMORY_BACKGROUND -> evictBackgroundCache()
        TRIM_MEMORY_COMPLETE -> releaseEverything()
    }
}
```

**设计思想**：Android 做了 5 级渐进通知、iOS 只有 1 级 `didReceiveMemoryWarning`——反映两种设计哲学：
- Android：**渐进式告警**，让应用按级别精细响应，灵活性高但复杂；
- iOS：**二元告警**，应用收到就要全力降级，简单但激进。

两种都能用，关键是**要用**。很多应用的 OOM 可以通过响应前兆避免 70%。

#### 🔬 深潜：onTrimMemory 的内核触发链路

onTrimMemory 不是 Android 自造的概念，而是**内核压力信号到应用层的转译**。完整链路：

```
Linux Kernel: PSI (Pressure Stall Information)
    ↓ 内存压力感知（memory.pressure cgroup）
lmkd (Low Memory Killer Daemon，用户态服务)
    ↓ 根据 PSI 决定要不要触发
    ├─ 轻度：仅通知 AMS
    └─ 重度：选择 oom_score 高的进程 kill
ActivityManagerService
    ↓ scheduleTrimMemory()
ApplicationThread (IPC via Binder)
    ↓ handleTrimMemory(level)
ActivityThread → Application.onTrimMemory(level)
    ↓
ComponentCallbacks2 (所有注册的 Activity/Fragment/Service)
```

**关键机制**：

- **PSI** 是 Linux 4.20+ 新引入的内存压力感知，相比老的 "free memory 阈值"，能更准确地反映"系统是否卡在等内存"；
- **lmkd** 是 Android 11+ 把 LMK 从内核移到用户态的守护进程，更灵活可配；
- AMS 根据 lmkd 的信号 + 自己的进程状态表，决定对哪些应用发哪种 level。

**level 的来源**：

| level 常量 | 触发源 | 时机 |
|---|---|---|
| RUNNING_MODERATE/LOW/CRITICAL | 前台应用 + 系统内存压力分级 | 应用在前台运行时 |
| UI_HIDDEN | 应用自身切后台 | onStop 后 |
| BACKGROUND/MODERATE/COMPLETE | 后台进程 + lmkd 内存压力 | 应用已在后台 |

**COMPLETE 为什么 5s 内不响应就被杀**？因为 COMPLETE 是 lmkd 杀进程的"**最后预警**"——此时系统已经决定要释放内存，给应用一个"自救机会"，不响应就直接 SIGKILL。

#### 🔬 深潜：ComponentCallbacks2 的注册机制

你的 Activity 不显式 `registerComponentCallbacks()` 为什么也能收到 trim？因为 `Activity` 本身实现了 `ComponentCallbacks2`，且在 `attach()` 阶段由系统**自动注册**：

```java
// Activity.java (framework)
public class Activity extends ContextThemeWrapper 
        implements ... ComponentCallbacks2 {
    // ...
}

// ContextImpl.java
public void registerComponentCallbacks(ComponentCallbacks callback) {
    getApplicationContext().registerComponentCallbacks(callback);
}
```

**调用顺序**：

```
TrimMemory 发给 Application
    ↓
Application.dispatchTrimMemory(level)
    ↓
遍历 mComponentCallbacks[] (包含所有已注册的 Activity/Fragment/Service/自定义)
    ↓
每个 callback.onTrimMemory(level)
```

**工程启示**：自定义类（如全局缓存管理器）**必须手动 `context.registerComponentCallbacks()` 才能收到** trim 信号——这是很多应用缓存不响应内存压力的根因。

### 4.4 Canary 原理

**Q：LeakCanary 怎么知道一个对象泄漏了？**

核心是 **WeakReference + ReferenceQueue + 主动 GC** 三件套：

```java
// 简化后的核心算法
class LeakDetector {
    static ReferenceQueue<Object> queue = new ReferenceQueue<>();
    static Map<String, KeyedWeakReference> watched = new HashMap<>();

    // 1. Activity.onDestroy 时注册监听
    static void watch(Object obj) {
        String key = UUID.randomUUID().toString();
        watched.put(key, new KeyedWeakReference(obj, key, queue));
    }

    // 2. 延迟 5 秒后触发 GC
    static void checkLeak() {
        Runtime.getRuntime().gc();
        System.runFinalization();
        
        // 3. 已回收的对象 → WeakReference 入队
        for (Reference<?> r; (r = queue.poll()) != null; ) {
            watched.remove(((KeyedWeakReference) r).key);
        }
        
        // 4. 剩下没入队的 = 没被回收 = 泄漏
        for (String key : watched.keySet()) {
            reportLeak(key);
        }
    }
}
```

**核心等价关系**：

> **GC 后仍可达（WeakReference.get() ≠ null）= 被强引用持有 = 泄漏**

**设计思想**：为什么用 `ReferenceQueue` 而不是直接检查 `weakRef.get() == null`？

因为**正确性**和**性能**要求：
- `weakRef.get()` 只告诉你"当前是否已回收"，但不保证"你问的时机 GC 已经发生"；
- `ReferenceQueue` 由 GC 线程在回收后主动入队，是**事件驱动**的，无需业务线程轮询；
- 这种"GC 回调队列"是 Java 引用机制的核心设计——同样原理用在 `PhantomReference` + `Cleaner`（见 §6.4）。

**检测延迟** = 5s（避免误报）+ GC 时间 + 10s 重试 + Dump + 分析 ≈ **30 秒**。

#### 🔬 深潜：shark 的支配树算法

LeakCanary 2.x 用自研的 **shark** 库取代了 Haha 库。shark 的核心是在**不展开整个堆**的情况下算出泄漏对象的**最短引用链**。

**算法流程**：

```
1. 内存映射 hprof 文件（mmap，避免整文件读进 heap）
   ↓
2. 索引 Pass：扫描 TAG=0x1C 建立 (objectId → fileOffset) 的哈希索引
   ↓
3. 从 GC Root 做 BFS，每个节点带"距离"
   ↓
4. 第一次到达目标泄漏对象时的路径 = 最短引用链
   ↓
5. 修剪冗余（如 WeakReference、FinalizerReference 不是真泄漏）
```

**关键优化**：

- **只读 hprof，不复刻堆**：shark 用 `RandomAccessFile` + 索引，访问任意对象 O(1)，但不占内存；
- **过滤已知无害引用**：JVM Finalizer 队列、Reference 内部字段、`Thread.contextClassLoader` 等——shark 内置 50+ 过滤规则，避免把它们标为泄漏；
- **匹配预定义 `Suspicion`**：如 `Activity.mContext`、`Fragment.mHost`，看到这些路径直接触发泄漏判定。

**对比 MAT**：MAT 要先把 hprof 全解析到自己的 heap，分析 500MB hprof 可能占 2GB 内存；shark 用 mmap + 索引，分析同样大小的 hprof 只占 50-100MB，速度快 3-5 倍。

#### 🔬 深潜：如何避免 LeakCanary 误报

常见误报场景和 LeakCanary 的对策：

| 场景 | 直觉 | 实际 | shark 对策 |
|---|---|---|---|
| 异步任务未完成 | 认为泄漏 | 正在执行中，还没返回 | 延迟 5s 等异步完成 |
| Finalizer 队列积压 | 认为泄漏 | 对象在等 finalize | 过滤 FinalizerReference 持有的对象 |
| Framework bug | 认为业务代码泄漏 | 系统类持有不释放 | 内置 KnownReferences，标注"Library Leak" |
| Weak 持有 | 认为泄漏 | 其实不是强引用 | shark 识别 Reference 类不计入强引用链 |

**KnownReferences 的工程价值**：Android Framework 本身有大量已知泄漏（如 `InputMethodManager` 持有 `View`）。LeakCanary 把这些标为 "Library Leak"（弱提示），让开发者聚焦在"Application Leak"（强提示）上。

### 4.5 工具选型

| 阶段 | 工具 | 作用 |
|---|---|---|
| 开发期 | LeakCanary | 自动检测 Activity/Fragment/View 泄漏 |
| 开发期 | Profiler | Allocation Tracker + Heap Dump 深度分析 |
| 线上 | PSS/USS 常驻采集 | 看进程内存趋势 |
| 线上 | onTrimMemory 埋点 | 前兆监控 |
| 线上 | KOOM / Matrix | Java 堆 > 90% 时自动 Dump，不阻塞主进程 |
| iOS | MetricKit MXOOMReport | 系统主动上报 OOM |
| Native | malloc hook / Heaptrack | 看 Java 工具看不到的 Native 泄漏 |

**KOOM 的核心设计**：为什么它能线上用而 LeakCanary 不行？

- LeakCanary 在**主进程**直接 Dump，会 STW 100ms–10s；
- KOOM 用 **fork 子进程 + Copy-on-Write**（见 §6.6）：fork 瞬间父子进程共享同一份物理内存，子进程慢慢 Dump 时父进程继续运行，父进程修改页才真实复制。
- 这样 Dump 对主进程几乎零影响。

#### 🔬 深潜：KOOM 的三阶段时序

```
主进程                                   子进程
  │                                        │
  ├─ Java heap > 90% 触发                    │
  │                                        │
  ├─ SuspendAll() 暂停 Java 线程           │  (必须，否则 fork 中 heap 不一致)
  │                                        │
  ├─ fork() ────────────────────────────▶  启动（继承 CoW 页表）
  │                                        │
  ├─ ResumeAll() 恢复 Java 线程            │
  │  (STW < 10ms)                          │
  │                                        │
  ├─ 继续业务                               ├─ 慢慢 Dump hprof
  │  (父进程写内存 → 对应页 CoW)             │  (子进程只读，不触发 CoW)
  │                                        │
  │                                        ├─ 写完上传
  │                                        │
  │                                        └─ exit(0)
```

**三个关键点**：

1. **fork 前必须 SuspendAll**：否则 fork 瞬间可能某个 Java 线程正在改 heap（如正在 GC），父子堆状态不一致，子进程 Dump 的 hprof 会错；
2. **STW 窗口极短（10ms）**：只覆盖 Suspend → fork → Resume 三步，不包含 Dump 本身；
3. **CoW 开销有上限**：父进程只有"写入新页"才 CoW；子进程 Dump 期间父进程不太可能写入全部 300MB heap，实际 CoW 开销通常 < 原 heap 的 20%。

**边界：子进程 OOM**？

子进程继承所有父进程地址空间，自己再分配内存写 hprof，总体虚拟地址翻倍（CoW 刚 fork 时只是共享）。32 位设备上这是风险——KOOM 用**流式写入**（边 walk 边写磁盘，不缓存）规避。

#### 🔬 深潜：Matrix 和 KOOM 的差异

字节 Memlab、腾讯 Matrix、快手 KOOM 都是线上内存监控库，但技术路线不同：

| 工具 | 核心机制 | 适用 | 开销 |
|---|---|---|---|
| **LeakCanary** | WeakRef + 主进程 Dump | 线下 | 高 |
| **KOOM** | fork + CoW + 流式 Dump + 精简 hprof | 线上，大堆 | 极低 |
| **Matrix** | 内存阈值监控 + 主进程 Dump + 过滤 | 线上，小堆 | 中 |
| **Memlab (Meta)** | Puppeteer + Chrome Heap Snapshot | Web / Hybrid | 中 |

**KOOM vs Matrix 的工程取舍**：

- KOOM：fork 子进程 Dump，父进程无感知。代价：实现复杂（涉及 ptrace / mmap / 跨进程文件描述符）；
- Matrix：主进程 Dump 但做了多重过滤（只在非前台触发 + 采样 + 条件限制），实现简单但对用户仍有短暂卡顿感。

**Memlab 的差异化**：针对 Hybrid 应用（React Native、WebView）设计，用 Puppeteer 从 Chrome DevTools 拿 Heap Snapshot，能同时分析 JS 堆和 Native 堆（通过 Native handle 关联）。

### 4.6 面试锚点

**Q："你们线上怎么做内存监控？"**

**90 秒标准答案**：

> 我们线上内存监控是三层组合：
> 
> **第一层：常态监控**。每 30 秒采一次 PSS/USS 上报，看趋势曲线。阈值告警，PSS > 70% maxMemory 持续 5 分钟触发。
> 
> **第二层：前兆捕获**。监听 onTrimMemory 5 级响应，统计各级触发频次。频率飙高说明有压力。
> 
> **第三层：现场 Dump**。接入 KOOM，Java 堆 > 90% 时 fork 子进程 Dump hprof（CoW 不阻塞主进程），离线上传分析。
> 
> 线下用 LeakCanary + Profiler 兜底，CI 跑压测用例，30 分钟滚动场景 OOM 必须为 0。

## 05、分层治理

**治理分四层，严格按 ROI 顺序执行**：

```
   第一层：泄漏治理   → 修复"活得太久"
   第二层：抖动治理   → 修复"生得太多"
   第三层：溢出治理   → 修复"占得太大"
   第四层：OOM 兜底   → 承认"内存永远可能不够"，建立降级与重启
```

### 5.1 泄漏治理

**🤔 核心疑惑**：既然 GC 会自动回收，为什么还会泄漏？

**💡 解答**：GC 只回收"**不可达**"对象。只要还有一条强引用链连着 GC Root，对象就"永生"——这就是泄漏。

**Android 四大泄漏源**（按频率）：

**① 静态变量持有 Context / Activity**

```kotlin
// ❌ 单例持 Activity Context
class SingletonManager private constructor(private val context: Context) {
    companion object {
        private var instance: SingletonManager? = null
        fun init(context: Context) { instance = SingletonManager(context) }
    }
}
// ✅ 修复：永远传 ApplicationContext
SingletonManager.init(context.applicationContext)
```

**② 非静态 Handler**（经典面试题）

```java
// ❌ 隐式持有 outer Activity
class MyActivity extends Activity {
    private Handler handler = new Handler() {
        public void handleMessage(Message m) { /* ... */ }
    };
}

// ✅ 静态 + WeakReference
class MyActivity extends Activity {
    private static class SafeHandler extends Handler {
        private final WeakReference<MyActivity> ref;
        SafeHandler(MyActivity a) { ref = new WeakReference<>(a); }
        public void handleMessage(Message m) {
            MyActivity a = ref.get();
            if (a != null && !a.isFinishing()) { /* ... */ }
        }
    }
    private Handler handler = new SafeHandler(this);
    
    @Override
    protected void onDestroy() {
        super.onDestroy();
        handler.removeCallbacksAndMessages(null);  // 清空消息队列
    }
}
```

**为什么只加 WeakReference 还不够**？因为**消息队列里的 Message 本身强引用 Handler**：

```
MessageQueue → Message.target = Handler → Handler.ref = WeakRef(Activity)
```

即使 Handler 用了 WeakRef，Message 仍然强引用 Handler；而 Message 又被 MessageQueue 强引用；MessageQueue 又挂在 Looper（线程级常驻）上。所以必须 `removeCallbacksAndMessages(null)` 把 Message 从队列删掉。

**③ Listener / Callback 未解绑**

```kotlin
override fun onDestroy() {
    super.onDestroy()
    sensorManager.unregisterListener(myListener)
    locationManager.removeUpdates(myCallback)
    rxDisposable.dispose()
    coroutineJob.cancel()
}
```

**④ 匿名内部类 / Lambda 持有外部引用**

```kotlin
// ❌ Lambda 捕获外部 this
button.setOnClickListener { someField = ... }

// 子线程中更危险
Thread { doHeavyWork(this.data) }.start()  // 持有 Activity 直到任务结束
```

**设计思想**：匿名内部类为什么会隐式持有外部？因为 Java 的匿名内部类编译后是一个独立的类文件（`Outer$1`），其构造函数会接收 `outer this` 作为参数。这是 JVM 实现"闭包"的方式——用对象持有引用模拟词法作用域。

#### 🔬 深潜：Handler 泄漏的完整引用链

Handler 泄漏是面试经典题，但真要讲清楚，涉及**五层强引用**。来看完整链路：

```
Thread (GC Root，线程栈永久活跃)
  │ 强引用
  ▼
Looper (ThreadLocal 持有，每个线程一个)
  │ 强引用
  ▼
MessageQueue
  │ 强引用 (Message 链表的头)
  ▼
Message (未处理的消息)
  │ 强引用 target 字段
  ▼
Handler (匿名/非静态 Handler)
  │ 强引用 outer this
  ▼
Activity (泄漏对象！)
  │ 强引用 Views、Context 等
  ▼
整个 View 树 + 资源
```

**关键点**：

- **GC Root 入口是 Thread**：主线程永不退出，所以主线程 Looper → MessageQueue → ... 这条链永远活着；
- **Handler 加 WeakReference 只断 Handler → Activity 这一环**，但 Message → Handler 这一环还是强引用；
- Message 什么时候死？处理完或主动 remove。所以必须 `handler.removeCallbacksAndMessages(null)` 把队列里的 Message 清掉——Message 一死，Handler 的强引用链就断，Activity 才能回收。

**延伸：Message 的回收**：

Message 本身也不是 GC 回收，而是 Android 的**对象池机制**（`Message.obtain()`）复用。处理完的 Message 会被放回全局池（最多 50 个），下次 `obtain()` 复用。所以：

- 处理完一条 Message，它的 `target` / `obj` 字段会被 `recycleUnchecked()` 清空；
- 这就是为什么**处理完的 Message 不会泄漏 Handler**——池化机制主动清理。

**面试追问**：为什么 Message 要池化？因为消息频率高（主线程每秒数百条），每次 new 会导致严重抖动。池化让 Message 的分配开销趋近 0。

#### 🔬 深潜：Lambda vs 匿名内部类的字节码差异

Kotlin / Java 8 Lambda 看起来和匿名内部类一样会"持有外部"，但字节码层面完全不同：

**匿名内部类**（Java 7-）：

```java
view.setOnClickListener(new OnClickListener() {
    public void onClick(View v) { outerField = 1; }
});

// 编译后生成独立 class 文件 Outer$1.class
// 构造函数：Outer$1(Outer outer) { this.this$0 = outer; }
```

每个匿名内部类**生成一个独立的 class**，有 `this$0` 字段强引用外部。

**Lambda**（Java 8+ 用 `invokedynamic`）：

```java
view.setOnClickListener(v -> outerField = 1);

// 编译后：Outer 中生成私有静态方法 lambda$0$Outer(Outer this, View v)
// 调用点用 invokedynamic 延迟生成实现 OnClickListener 的类
```

**关键差异**：

| 维度 | 匿名内部类 | Lambda（捕获外部） | Lambda（不捕获） |
|---|---|---|---|
| class 文件 | 每个产生一个 | 运行时动态生成 | **单例复用** |
| 外部引用 | 必有 this$0 | 必有（捕获才有） | 无 |
| 内存开销 | 每个实例独立 | 每个实例独立 | 全局一个 |

**工程意义**：

```kotlin
// ✅ 不捕获外部 → Lambda 实例复用，零成本
button.setOnClickListener { Log.d("TAG", "click") }

// ⚠️ 捕获外部 → 和匿名内部类等价，每次都 new
button.setOnClickListener { someField = 1 }
```

**Kotlin 的 inline 优化**：带 `inline` 的高阶函数在调用点展开，没有 Lambda 对象创建——这是 Kotlin 比 Java Lambda 更"零成本"的原因。

### 5.2 抖动治理

**🤔 核心疑惑**：GC 不是会自动清吗？为什么分配快了会掉帧？

**💡 解答**：GC 是**同步暂停**（STW）。Young GC 单次 5–20ms，频繁触发就吃掉主线程时间。实测：
- **5 MB/s** 分配速率开始影响帧率；
- **10 MB/s** 掉 25 帧/60s；
- **30 MB/s** 持续卡顿。

**三大抖动源**：

**① 对象池（高频大对象）**

```kotlin
object PathPool {
    private val pool = ArrayDeque<Path>(50)
    fun acquire(): Path = pool.pollFirst() ?: Path()
    fun release(p: Path) { 
        p.reset()
        if (pool.size < 50) pool.add(p) 
    }
}

override fun onDraw(canvas: Canvas) {
    val path = PathPool.acquire()
    try {
        path.moveTo(0f, 0f)
        canvas.drawPath(path, paint)
    } finally {
        PathPool.release(path)
    }
}
```

**边界条件**：对象池只适合 **> 1KB 的对象**。小对象池化反而更慢——因为 JVM 的 **TLAB**（Thread Local Allocation Buffer，见 §6.3）让小对象分配几乎零成本，池操作（取/还/同步）的开销反而更大。

**② 容器选型（减少装箱）**

```kotlin
// ❌ Int 装箱 Integer
val map = HashMap<Int, User>()
map[123] = user  // new Integer(123)

// ✅ SparseArray（Android）
val map = SparseArray<User>()
map.put(123, user)  // 无装箱

// ✅ IntArray 替代 List<Int>
val ids = intArrayOf(1, 2, 3)
```

**ArrayMap vs HashMap 的内存差异**：
- HashMap 用 `Node[]` 数组存桶，每个 Node 对象额外 ~40 字节头部（见 §6.8 对象头）；
- ArrayMap 用两个数组（hash[] 和 Object[]）扁平存储，无 Node 对象；
- 小规模（< 100）场景 ArrayMap 内存降 30-50%，查询略慢（二分 vs 哈希）。

**③ 字符串拼接**

```kotlin
// ❌ 循环里 +
var s = ""
for (item in list) s += "${item.name},"  // 每次新建 String + StringBuilder

// ✅ 显式 StringBuilder
val s = StringBuilder().apply {
    list.forEach { append(it.name).append(',') }
}.toString()
```

**为什么 `+` 慢**？因为 Java `String` 是 `final`（不可变）。编译器会把 `s += "x"` 翻译成 `s = new StringBuilder(s).append("x").toString()`——循环里每次都 new 一个 StringBuilder + 新 String。

**高频抖动场景速查**：

| 场景 | 常见错误 | 修复 |
|---|---|---|
| onDraw | `new Paint()` 每帧 | 提到构造 |
| onBindViewHolder | `new SimpleDateFormat()` | 单例 / ThreadLocal |
| 列表滚动 | `list.forEach` 创 Iterator | for-index |
| JSON 解析 | 每次 new ObjectMapper | 单例 |

#### 🔬 深潜：Alloc GC 触发条件与晋升策略

抖动的本质是**频繁触发 Alloc GC**。要理解怎么治，必须懂 ART 分代 GC 的具体机制。

**对象分配路径**（ART 并发复制 GC）：

```
new Object()
    ↓
① 看 TLAB 够不够（当前线程私有缓冲）
    ├─ 够 → bump pointer 直接分配（99% 的小对象走这里）
    └─ 不够 ↓
② 看 Eden 够不够
    ├─ 够 → 原子操作切新 TLAB，继续分配
    └─ 不够 → 触发 Young GC（Alloc GC）
③ Young GC 后仍不够
    ├─ 对象 > Large Object 阈值 → 直接进 Large Object Space
    └─ 否则 → 触发 Full GC；再不够 → OutOfMemoryError
```

**Young GC 的"晋升"策略**：

存活下来的对象不是全放回 Eden，而是按**年龄**分批晋升到 Old Gen：

```
Eden ──Young GC──▶ Survivor From ──Young GC──▶ Survivor To
                        │                            │
                        │                            │
                     年龄 +1                      年龄 +1
                        │                            │
                        └──── 年龄 ≥ 15 ────▶ Old Gen（晋升）
```

**TenuringThreshold**：对象在 Survivor 区"幸存"多少次 Young GC 就晋升到 Old。ART 默认阈值 15，但有**动态调整**——Survivor 空间占用高时阈值降低，加速晋升避免抖动。

**抖动的内在矛盾**：

- 对象很快死 → Young GC 回收，没问题；
- 对象活很久 → 晋升 Old Gen，不频繁 GC，没问题；
- **最糟糕的是"中等生命周期"对象**（存活几秒到几分钟）——它们在 Survivor 之间来回复制 N 次才被回收，每次复制有开销。

**工程启示**：

- `onDraw` 里 new 的对象是"短命的"，Young GC 快速回收；
- 但高分配速率下 Young GC 频繁触发 → STW 累计超过帧预算；
- 对象池化不是消灭对象，是**把"短命对象"转成"长命对象"**——让它们一次性晋升到 Old Gen，之后不再参与频繁 GC。

#### 🔬 深潜：ArrayMap 的内部结构

Android 推荐的 ArrayMap 相比 HashMap 内存降 30-50%，秘密在于**扁平化存储**：

```java
// HashMap 的 Node 对象（Android/OpenJDK）
static class Node<K,V> {
    final int hash;      // 4B
    final K key;         // 4B (压缩指针)
    V value;             // 4B
    Node<K,V> next;      // 4B
    // + 对象头 16B = 每个 Entry 32B
}

// 1000 个 KV 对：
// HashMap 内存 ≈ 1000 × 32B (Node) + 1024 × 4B (桶数组) = 36 KB

// ArrayMap 的内部：
int[] mHashes;       // 4B × 1000 = 4 KB
Object[] mArray;     // 8B × 1000 = 8 KB (K/V 交叉放)
// 总计 12 KB，省 65%
```

**ArrayMap 的查询**：

- 对 `mHashes[]` 做**二分查找**找 hash，然后对冲突的 key 做 `.equals()` 比较；
- 复杂度 O(log N) vs HashMap O(1)，所以 ArrayMap 适合**小数据量（< 100）** 场景。

**ArrayMap 的"扩容"**：

```
初始：mHashes = int[0], mArray = Object[0]
插入第 1 个 → 扩到 int[4], Object[8]
插入第 5 个 → 扩到 int[8], Object[16]
...指数扩容
```

**但是！ArrayMap 不是无脑好**：

- 删除时要搬移数组，大量删除场景比 HashMap 慢；
- 并发修改抛 `ConcurrentModificationException`，比 HashMap 更敏感；
- 用在 > 1000 的场景，查询开销随 log N 累积。

#### 🔬 深潜：ThreadLocal 的 ThreadLocalMap

前面提到 ThreadLocal 泄漏（Q13），这里补充其内部结构帮助理解：

```
Thread
  │ threadLocals 字段
  ▼
ThreadLocalMap
  │
  ├─ Entry[] table （开放地址法，不像 HashMap 的链表）
  │     ├─ Entry[0]: key=WeakRef<ThreadLocal_A>, value=someObject
  │     ├─ Entry[1]: null
  │     └─ Entry[2]: key=WeakRef<ThreadLocal_B>, value=anotherObject
```

**关键细节**：

- **key 是 WeakReference**：ThreadLocal 变量回收后 key 自动变 null；
- **value 是强引用**：这就是泄漏的根源——key 没了，value 还在；
- **开放地址法**：发生冲突时放到下一个空位，不像 HashMap 用链表；
- **惰性清理**：每次 `get/set/remove` 时顺带扫描一下相邻 Entry，清掉 key=null 但 value 仍在的"**残骸 Entry**"。

**工程规则**：

- 用 ThreadLocal 存大对象 → 必须 try-finally 调 `remove()`；
- 线程池场景（线程永不退出）尤其危险 —— Executor 的 worker 线程可能活整个进程生命周期。

### 5.3 溢出治理

**🤔 核心疑惑**：为什么 Bitmap 是 Android OOM 的头号元凶？

**💡 解答**：一张 8K 图（7680×4320）全量解码（ARGB_8888）占 **132MB**，但屏幕只有 1080p，99% 的像素肉眼看不见。这是最大的内存浪费。

**① Bitmap 分辨率自适应**（必做）

```kotlin
fun decodeBitmap(file: File, targetW: Int, targetH: Int): Bitmap {
    // 第一遍：只读尺寸
    val bounds = BitmapFactory.Options().apply { inJustDecodeBounds = true }
    BitmapFactory.decodeFile(file.path, bounds)
    
    val sampleSize = max(
        bounds.outWidth / targetW,
        bounds.outHeight / targetH
    ).coerceAtLeast(1)
    
    val options = BitmapFactory.Options().apply {
        inSampleSize = sampleSize
        inPreferredConfig = Bitmap.Config.RGB_565  // 不透明图可用，内存减半
    }
    return BitmapFactory.decodeFile(file.path, options)!!
}
```

**实测收益**（8K 图）：

| 方案 | 内存占用 | 用户主观评分 |
|---|---|---|
| 原图直接解码 | 132 MB | 4.6 / 5 |
| inSampleSize 自适应 | 8.3 MB（**-94%**） | 4.5 / 5 |

**ARGB_8888 vs RGB_565 的内存对比**：

| Config | 字节/像素 | 透明度 | 用途 |
|---|---|---|---|
| ARGB_8888 | 4 | 有 | 默认，带透明 |
| RGB_565 | 2 | 无 | 不透明图，省一半 |
| ARGB_4444 | 2 | 低色阶 | 已废弃 |
| ALPHA_8 | 1 | 仅透明 | 蒙版 |
| HARDWARE | 0（上传 GPU） | 有 | Android 8+ 推荐 |

**② LRU 缓存严控上限**

```kotlin
class ImageCache {
    private val cache = object : LruCache<String, Bitmap>(getMaxSize()) {
        override fun sizeOf(key: String, bitmap: Bitmap) = bitmap.byteCount / 1024
    }
    
    private fun getMaxSize(): Int {
        val maxMemory = Runtime.getRuntime().maxMemory() / 1024
        return (maxMemory / 8).toInt()  // 用堆的 1/8
    }
}
```

**为什么 LRU 比 FIFO/LFU 更适合图片缓存**？因为图片访问符合"**时间局部性**"——用户近期看过的图很可能继续看（返回操作、二次浏览）。LRU 对时间局部性友好；LFU 适合"热点数据"场景；FIFO 不智能。

**③ Bitmap 复用池（inBitmap）**

```kotlin
val options = BitmapFactory.Options().apply {
    inMutable = true
    inBitmap = pool.acquire()
}
```

**边界条件**：inBitmap 只能复用**相同尺寸、相同 Config** 的 Bitmap；复用对 Android 8+ 收益降低（因为 Bitmap 已移到 Native heap，Java 堆压力本来就小了）。

#### 🔬 深潜：Bitmap 的像素存储原理

**内存占用公式**：

```
Bitmap 字节数 = 宽度 × 高度 × 字节/像素
```

**像素字节数的来源**：

```
ARGB_8888 像素布局（4 字节）：
┌────────┬────────┬────────┬────────┐
│  A(8)  │  R(8)  │  G(8)  │  B(8)  │
└────────┴────────┴────────┴────────┘
  透明度   红      绿      蓝

RGB_565 像素布局（2 字节）：
┌─────────┬──────────┬─────────┐
│  R(5)   │   G(6)   │   B(5)  │
└─────────┴──────────┴─────────┘
  绿色多一位，因为人眼对绿色更敏感
```

**8K 图的内存爆炸**：

```
7680 × 4320 × 4 = 132,710,400 字节 ≈ 132 MB
```

即使你用 largeHeap（512MB），加载 3 张 8K 图就会 OOM。

**为什么 RGB_565 "肉眼差别不大"**？

- 人眼能辨别约 1000 万种颜色；
- ARGB_8888 能表示 **1600 万 × 256（透明）** = 42 亿种，远超人眼极限；
- RGB_565 能表示 **65,536** 种（2^16），对**非照片类图片**（图标、UI 元素）几乎无感；
- 代价：**不支持透明**，有渐变色时可能出现"色带"。

#### 🔬 深潜：inBitmap 的复用机制

inBitmap 不是"复用 Bitmap 对象"，而是**复用 Bitmap 的 Native pixel 内存**：

```kotlin
val options = BitmapFactory.Options().apply {
    inMutable = true
    inBitmap = oldBitmap  // 旧 Bitmap 的 Native pixel buffer 作为新 Bitmap 的 buffer
}
val newBitmap = BitmapFactory.decodeFile(path, options)
```

**流程**：

```
1. 旧 Bitmap 的 Native pixel buffer 还在（800 × 600 × 4 = 1.9 MB）
     ↓
2. BitmapFactory 发现 inBitmap 不为 null，尝试复用
     ↓
3. 检查：
    ├─ Android 4.4-: 要求 width × height × bytePerPixel 完全相等
    └─ Android 4.4+: 要求 newWidth × newHeight × bytePerPixel <= oldBitmap.allocationByteCount
     ↓
4. 复用成功：
    ├─ 旧 Bitmap 的 Java 壳被标记为"已被夺权"（后续访问抛异常）
    ├─ Native pixel buffer 被 memset 清零
    └─ 新图像素写入该 buffer
```

**关键点**：

- 复用的是 **Native pixel 内存**，不是 Java 壳对象（Java 壳每次都新建一个，但只有 ~100 字节，影响很小）；
- 可以用"大 bitmap 复用小 bitmap"，但反之不行（4.4+ 的放宽）；
- 复用后旧 Bitmap 的像素会被覆盖，所以**要保证旧 Bitmap 不再使用**。

**Android 8+ 为什么收益降低**？因为 Bitmap pixel 已经不在 Java heap，而在 Native heap，Java heap 的 maxHeap 限制已不成瓶颈。但对 32 位地址空间 OOM 和分配速率抖动仍有缓解意义。

#### 🔬 深潜：Bitmap 对比：Android 版本演进

| Android | pixel 存储位置 | Java heap 影响 | 回收机制 |
|---|---|---|---|
| 2.3- | Native + ashmem | 少量，有专门池 | Bitmap.recycle() 必须手动 |
| 3.0 - 7.1 | **Java heap** | 大 | GC 回收 |
| 8.0+ | **Native heap** | 小壳对象 | NativeAllocationRegistry + GC |
| 10.0+ | Native heap + Hardware Bitmap | 更小 | 同上 |

**8.0 为什么又移回 Native**？因为 Java heap 的 maxHeap 限制太紧，大图加载很容易 OOM；移到 Native 后用 `NativeAllocationRegistry`（PhantomReference 子类）管理回收，既不受 maxHeap 限制，又能跟 Java GC 协同（Java 壳回收时触发 Native pixel 释放）。

**Hardware Bitmap（10.0+）**：直接上传到 GPU，Java 层只有 handle，连 CPU 内存都省了，但不能读写像素。适合"只显示不修改"的场景（如列表缩略图）。

### 5.4 兜底四招

前面三层做完还是会 OOM——总有极端情况（低端机 + 长时间使用 + 突发大图）。第四层是"**承认内存永远可能不够**"，建立兜底。

**① onTrimMemory 分级降级**（见 §4.3）

**② 升级 64 位**（Android 核武器）

```gradle
android {
    defaultConfig {
        ndk { abiFilters 'armeabi-v7a', 'arm64-v8a' }
    }
    bundle { abi { enableSplit = true } }  // 按设备分发
}
```

**实测收益**：

| 指标 | 32 位 | 64 位 |
|---|---|---|
| OOM 率 | 8.4% | **1.2%** |
| 最大连续地址块（30 分钟后） | 18 MB | > 1 GB |

**为什么 64 位是"核武器"**？因为它**从物理上消灭了 C 类（地址空间）OOM**——256TB 虚拟地址几乎用不完，碎片化不再是问题。32 位的所有缓解手段（mmap、避免大块、主动重启）都是在"3GB 虚拟地址"的紧箍咒下跳舞。

**③ 大对象 mmap 化**

```kotlin
val raf = RandomAccessFile(file, "r")
val mapped = raf.channel.map(MapMode.READ_ONLY, 0, file.length())
val byte = mapped.get(1024 * 1024)
```

**为什么 mmap 不占"连续虚拟地址大块"**？mmap 占的是**内核映射区**，与进程堆是不同的虚拟地址段。详见 §6.5。

**④ 主动重启机制**（最后防线）

```kotlin
class OomGuard {
    fun checkAndRestartIfDangerous() {
        val ratio = Runtime.getRuntime().run { 
            (totalMemory() - freeMemory()).toFloat() / maxMemory() 
        }
        if (ratio > 0.9f) {
            saveStateToDisk()  // 保存关键状态
            restartApp()       // 启动新进程 + kill 当前
        }
    }
}
```

**用户视角对比**：

| 方案 | 真实 OOM 率 | 用户感知崩溃 | 状态丢失 |
|---|---|---|---|
| 不主动重启 | 6.8% | **100%** | 100% |
| 主动重启 + 状态保留 | 0.3% | **12%** | < 5% |

**🧠 心法**：**1.5 秒主动重启 >> 不可控崩溃**。工程师经常觉得"主动 kill 自己不优雅"，但用户视角下主动重启完胜。

#### 🔬 深潜：主动重启的进程时序

"主动重启"看起来简单，但有一个必须拆开讲的时序坑：

```
❌ 错误写法（新进程启动前就 kill）
Process.killProcess(myPid())   // 当前进程立刻死
startActivity(intent)          // 永远不执行！

❌ 错误写法（时序不稳）
startActivity(intent)          // 发送 Intent 但不等启动
Process.killProcess(myPid())   // 立刻 kill
// → AMS 可能还没处理完 Intent，新进程未启动
```

**正确做法**（延迟 kill 配合新进程启动确认）：

```kotlin
fun restartApp() {
    val intent = packageManager.getLaunchIntentForPackage(packageName)!!
    intent.flags = Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TASK
    
    // 用 PendingIntent 延迟触发（确保 AMS 调度完成后再 kill）
    val pi = PendingIntent.getActivity(
        this, 0, intent,
        PendingIntent.FLAG_CANCEL_CURRENT or PendingIntent.FLAG_IMMUTABLE
    )
    
    // AlarmManager 延迟 500ms 启动新进程
    val am = getSystemService(ALARM_SERVICE) as AlarmManager
    am.setExact(AlarmManager.RTC, System.currentTimeMillis() + 500, pi)
    
    // 当前进程立刻 kill（AlarmManager 由系统独立触发，不受本进程死亡影响）
    Process.killProcess(Process.myPid())
    exitProcess(0)
}
```

**关键原理**：

- **AlarmManager 由 system_server 托管**，和应用进程独立。即使应用死掉，到时间照样触发；
- **PendingIntent 预先构造**：Intent 内容已经交给 AMS，不依赖本进程存活；
- **500ms 延迟**：留给系统清理资源（关闭 Activity、刷新 Dalvik heap）；
- **FLAG_ACTIVITY_CLEAR_TASK**：清空原 Task 栈，避免恢复到旧状态。

#### 🔬 深潜：lmkd 杀进程的决策算法

Android 11+ 的 lmkd（用户态 Low Memory Killer）决策流程：

```
1. 监听 /sys/fs/cgroup/memory.pressure （PSI 信号）
     ↓
2. 根据压力等级（SOME / FULL） 判断是否要 kill
     ↓
3. 从 /proc/*/oom_score_adj 读所有进程的分数
     ↓
4. 构建"候选杀表"：按 oom_score_adj 从高到低排
     ↓
5. 对候选进程发 SIGKILL（无法 catch）
     ↓
6. 等几秒看内存释放，不够再杀下一个
```

**lmkd 的三档阈值**（可配）：

| 等级 | PSI threshold | 行为 |
|---|---|---|
| MEDIUM | some_full_stall > 70ms | 杀 oom_score_adj >= 900 |
| CRITICAL | some_full_stall > 700ms | 杀 oom_score_adj >= 500 |
| EMERGENCY | 内核 OOM 快发生 | 杀 oom_score_adj >= 100 |

**工程启示**：

- 前台 Service 让你的 `oom_score_adj = 300`，EMERGENCY 等级下仍可能被杀；
- 系统启动 `oom_score_adj = 0` 的组件（如 Launcher），用户感知的"桌面闪退"就是这个原因；
- 应用能做的是在 onTrimMemory LOW/CRITICAL 时积极降级，让 lmkd 感知到压力缓解，避免升级到 CRITICAL kill。

### 5.5 Native 盲区

**🤔 疑惑**：为什么 Java Profiler 看不到 Bitmap 的真实内存？

**💡 解答**：Android 8+ 后 Bitmap 的像素数据**移到 Native heap**，Java 堆上只有一个很小的壳对象（约 100 字节）。Profiler 看 Java 堆看不到真实大小（可能有几十上百 MB）。

**为什么要移到 Native**？两个原因：
1. **突破 Java heap 限制**：maxHeap 只有 128-512MB，大 Bitmap 很容易撑爆；
2. **跟 GC 解耦**：Native 内存不参与 Java GC，释放更可控（通过 Bitmap 的 Cleaner 机制，见 §6.4）。

**Native 内存三大监控点**：

```kotlin
// 1. 周期性采集 Native 内存
val memInfo = Debug.MemoryInfo()
Debug.getMemoryInfo(memInfo)
val nativeHeap = memInfo.nativePss  // KB

// 2. JNI GlobalRef 必须成对管理（详见 §6.9）
JNIEXPORT void JNICALL register(JNIEnv* env, jobject cb) {
    g_callback = (*env)->NewGlobalRef(env, cb);
    // ⚠️ 必须有对应的 DeleteGlobalRef！
}

// 3. DirectByteBuffer 的 Native 内存 ≠ Java 堆
// 其释放由 Cleaner（PhantomReference 的子类）驱动，不保证即时
```

#### 🔬 深潜：NativeAllocationRegistry 的工作机制

Android 8+ 的 `NativeAllocationRegistry` 是**连接 Java GC 和 Native 内存**的关键机制，Bitmap、HardwareBuffer、Font 等都用它。

**核心思想**：Java 对象做"**壳**"，Native 内存做"**芯**"；Java 壳被 GC 时自动触发 Native 芯的释放函数。

**使用模板**：

```java
public class MyNativeResource {
    private static final long NATIVE_FINALIZER = nGetFinalizer();  // native free 函数的 C 函数指针
    private static final NativeAllocationRegistry REGISTRY =
        NativeAllocationRegistry.createMalloced(
            classLoader,
            NATIVE_FINALIZER,
            1024);  // Native 占用大小，用于 GC 启发
    
    private long nativePtr;
    
    public MyNativeResource() {
        nativePtr = nCreate();
        REGISTRY.registerNativeAllocation(this, nativePtr);
    }
}
```

**内部实现**（简化）：

```java
public void registerNativeAllocation(Object referent, long nativePtr) {
    // 1. 创建一个 Cleaner（PhantomReference 子类）
    //    关联：referent 被回收时 → 调用 freeFunction(nativePtr)
    Cleaner.create(referent, () -> {
        nativeFree(nativePtr, freeFunction);
    });
    
    // 2. 告诉 VM：有一笔 Native 内存被持有，GC 时考虑它
    VMRuntime.getRuntime().registerNativeAllocation(size);
}
```

**三个关键机制**：

1. **PhantomReference 驱动的清理**：Java 壳对象被回收 → PhantomReference 入队 → Cleaner 线程调用 freeFunction → Native 内存真正释放；
2. **VMRuntime.registerNativeAllocation(size)**：告诉 GC"**虽然你看不见这块内存，但它存在**"。GC 会把这个数值计入"**估算堆压力**"，Native 占用高时提前触发 GC；
3. **symmetric API**：有 register 就有 **registerNativeFree**，释放后要减去 size。

**对比老方案**：Android 7 之前的 Bitmap 用 `Bitmap.recycle()` **手动管理**，容易漏调；`NativeAllocationRegistry` 把这个负担交给 GC，不用再 recycle。

#### 🔬 深潜：Java heap vs Native heap 的 OOM 行为对比

| 维度 | Java heap OOM | Native heap OOM |
|---|---|---|
| 触发时机 | 分配超过 maxHeap | malloc 失败（物理不够或地址碎片） |
| 抛错 | `OutOfMemoryError` | **SIGSEGV / SIGABRT**（直接 crash）|
| 可 catch | 可以（但反模式） | **不可**（信号级） |
| GC 救济 | 可能（GC 后再试一次） | 无 |
| 栈信息 | Java 栈 | Native 栈（需 ndk-stack 符号化） |

**面试加分**：说出"Native OOM 发信号而不是抛错"，比笼统说"Native 泄漏"深刻得多。因为这决定了：

- **工具链不同**：Java OOM 用 ANR / crash log 捕获；Native OOM 需要 breakpad / crashpad 等 signal handler；
- **恢复路径不同**：Java OOM 可以在 catch 块里做降级重试；Native OOM 进程必死，只能靠主动重启机制预防。

## 06、原理深潜

> 本章是**资深向**内容，为"知其所以然"而写。前面讲"怎么做"，这里讲"为什么能这么做"。

### 6.1 GC 算法演进

**问题起点**：GC 的核心难题是——**如何快速找出"不可达"对象并释放，同时不让业务停顿太久**。

Android 从 Dalvik 到 ART 的演进路线：

| 版本 | GC 算法 | 核心改进 | 典型 STW |
|---|---|---|---|
| Android 4.x Dalvik | Mark-Sweep + Compact | 全停顿 | 50-200ms |
| Android 5.0 ART | **CMS**（Concurrent Mark Sweep） | Mark 阶段并发 | 10-50ms |
| Android 8.0+ | **CC**（Concurrent Copying） | Copy 阶段也并发 | **< 5ms** |
| Android 11+ | Generational CC | 分代，Young 更快 | **< 2ms** |
| Android 14+ | 默认 Gen CC | 全设备启用 | < 2ms |

**为什么要分代**？核心基于一个经验观察——"**弱世代假说**（Weak Generational Hypothesis）"：**绝大多数对象很快死亡，老对象活得长**。

- Young Gen 频繁回收（Minor GC），只扫新对象，速度快；
- Old Gen 很少回收（Major GC），只在空间紧张时触发；
- 跨代引用用 **Card Table**（卡表）标记脏页，Minor GC 只扫 Card Table 标记的部分 Old Gen。

**为什么 Concurrent Copying 比 Concurrent Mark Sweep 好**？因为 CMS 不搬移对象，长期运行后堆碎片化，分配大对象失败率上升；CC 在回收时顺便压缩堆（Copy = 自带 Compact），永远保持连续空闲空间。代价是**写屏障**稍重（需要跟踪 From/To 空间指针修正）。

### 6.2 三色标记法

**问题起点**：如何在**不暂停业务线程**的情况下，正确标记对象的可达性？

**经典算法**：三色标记（Tri-color Marking），把对象分三色：

```
   白色 = 还没扫描到（候选回收对象）
   灰色 = 自己被扫到，但引用的子对象还没扫完
   黑色 = 自己和所有子对象都扫完了
```

**算法流程**：

1. 初始：GC Root 置灰，其他全白
2. 从灰色集合取一个对象 → 把它的所有白色引用置灰 → 自己置黑
3. 重复 2，直到灰色集合为空
4. 剩下的白色对象 = 不可达 = 回收

**🚨 并发标记的两大难题**：

**问题 1：浮动垃圾（Floating Garbage）**

GC 扫过的对象（黑色）后来变成不可达，但本轮回收不了——没关系，下轮回收即可。

**问题 2：对象消失（Lost Object）** ⚠️ 必须解决

```
   GC 扫到 A（黑），还没扫 B（白）
   业务线程：A.ref = B（新增引用）
   业务线程：C.ref = null（原来 C 引用了 B，现在断了）
   GC 继续扫 → C 已扫过 → B 还是白 → B 被错杀！
```

**解决方案：写屏障（Write Barrier）**

两种屏障：

- **增量更新（Incremental Update，Dijkstra）**：A（黑）新增引用 B（白）时，把 A 变回灰，重新扫。CMS 采用。
- **原始快照（Snapshot At The Beginning，SATB，Yuasa）**：C 删除对 B 的引用时，把 B 置灰（"快照时你可达，就当你可达"）。G1、ZGC、ART 的 CC 采用。

**为什么 ART 用 SATB**？因为 SATB 保证"**本轮 GC 开始时的可达集合**"全部存活，不会漏；浮动垃圾由下轮回收，可接受。实现上 SATB 对业务代码干扰小（只需在引用赋值前拦截一次）。

### 6.3 TLAB 分配

**问题起点**：堆是多线程共享的，每次 `new` 都要加锁，并发高时锁竞争严重。

**解决方案**：**TLAB**（Thread Local Allocation Buffer）——每个线程在 Eden 区预分配一小块私有空间，自己 new 时直接在 TLAB 里**凸点指针（bump pointer）**，无锁。

```
   Eden 区
   ┌─────────────────────────────────────────┐
   │ Thread-1 TLAB │ Thread-2 TLAB │  共享区  │
   │  ───▶ 分配点  │  ───▶ 分配点  │          │
   └─────────────────────────────────────────┘
```

**bump pointer 分配**：

```c
// 伪代码：原子性递增 TLAB 的 top 指针
void* allocate(size_t size) {
    void* p = tlab->top;
    tlab->top += size;
    if (tlab->top > tlab->end) {
        return slow_path_allocate(size);  // TLAB 满，走加锁慢路径
    }
    return p;
}
```

**TLAB 的边界设计**：

- **大小**：默认 64KB-1MB，JVM 自适应（根据分配速率调整）；
- **超大对象**：> TLAB 1/4 的对象直接走慢路径（避免浪费 TLAB）；
- **退火**：GC 后 TLAB 重新切分，避免长期碎片。

**为什么这个设计很"工程"**？它完美利用了"**绝大多数对象是小对象 + 短命**"的事实——小对象在 TLAB 里零锁分配，Young GC 时整个 Eden 清空，TLAB 自然失效，开销摊销到 GC。

**对工程师的意义**：

- 小对象（< 1KB）的 `new` 开销 ≈ 栈分配，所以**不要盲目池化小对象**；
- 频繁分配的大对象（> 32KB）走慢路径，才是性能瓶颈，这才值得池化。

### 6.4 引用四层级

Java 的四种引用，是**精细控制生命周期**的工具。资深工程师必须分清楚：

| 引用类型 | 回收时机 | 用途 | API |
|---|---|---|---|
| **Strong**（强） | 不可达才回收 | 默认引用 | `Object o = ...` |
| **Soft**（软） | 内存不足时回收 | **内存敏感缓存** | `SoftReference` |
| **Weak**（弱） | 下次 GC 必回收 | 泄漏兜底 / 关联数据 | `WeakReference` |
| **Phantom**（虚） | 回收前通知 | **替代 finalize** | `PhantomReference` + `ReferenceQueue` |

**设计思想**：这是一个**可达性强度**的光谱——

```
   强 ━━━ 软 ━━━ 弱 ━━━ 虚
   │       │       │      │
   不回收  内存不足 下次GC  已死但等通知
   必保活  才回收   必回收  执行清理
```

**Soft vs Weak 的工程选择**：

- **Soft 适合缓存**：有内存时保留，没内存时自动让出。但实测在 ART 上 **Soft 和 Weak 行为差不多**——因为 ART 的 Soft 回收策略是"GC 时检查最后访问时间 + 当前内存压力"，并不像 HotSpot 那样严格"内存不足才回收"。
- **Weak 适合"知道但不持有"**：WeakHashMap 的 key、WeakReference 包装 Listener 的 outer 持有。

**Phantom 和 Cleaner**：

```java
// Java 9+ 推荐用 Cleaner 替代 finalize
public class Resource {
    private static final Cleaner cleaner = Cleaner.create();
    private final Cleaner.Cleanable cleanable;
    
    public Resource() {
        long nativePtr = allocateNative();
        this.cleanable = cleaner.register(this, () -> freeNative(nativePtr));
    }
}
```

**为什么 Phantom + Cleaner 比 finalize 好**？

| 维度 | finalize | Cleaner（PhantomRef） |
|---|---|---|
| 执行时机 | 不确定，可能永不执行 | 对象被回收后立即入队 |
| 性能 | 需要 Finalizer 线程两次 GC | 单次 GC 搞定 |
| 异常处理 | 异常被吞 | 可自定义 |
| 对象复活 | 可能复活自己（反模式） | 不可能 |

Android 的 `DirectByteBuffer`、`Bitmap`（新版）都用 Cleaner 机制管理 Native 内存。

### 6.5 mmap 原理

**问题起点**：为什么大文件用 mmap 比 read/write 更省内存、更快？

**核心机制**：mmap 把文件**直接映射到进程虚拟地址空间**，访问文件 = 访问内存。

```
   普通 read                   mmap
   ─────────                   ────
   用户态缓冲区              进程地址空间
       ↑                          ↑
     拷贝                      按需触发缺页
       ↑                          ↑
   内核 Page Cache  ───────  Page Cache（直接映射）
       ↑                          ↑
     磁盘                        磁盘
```

**mmap 的三大优势**：

1. **零拷贝**：无需在"内核缓冲区"和"用户缓冲区"之间来回复制；
2. **按需加载**：访问哪页才触发缺页中断加载哪页（lazy），不预读全文件；
3. **多进程共享**：MAP_SHARED 时，多个进程映射同一文件 → 共享同一份物理内存。

**mmap 的分类**：

| 类型 | flags | 用途 |
|---|---|---|
| 文件映射 | 默认 | 读写大文件（KOOM dump、MMKV） |
| 匿名映射 | `MAP_ANONYMOUS` | 大块内存（malloc 底层用它） |
| 共享映射 | `MAP_SHARED` | 多进程 IPC |
| 私有映射 | `MAP_PRIVATE` | 独立，修改触发 CoW |

**mmap 不占"连续虚拟地址大块"吗**？

严格说：**mmap 本身占虚拟地址，但占的是"内核映射区"段，与堆/栈分开**。所以 Java heap / Native heap 的碎片不影响 mmap 分配大块（反之亦然）。32 位时代，这是绕开地址碎片的重要手段。

**MMKV（微信的 KV 存储）为什么用 mmap**？

- 零拷贝：读写直接操作内存，比 SharedPreferences 的全量 reload 快 100x+；
- 崩溃不丢数据：mmap 的页由内核 flush，进程崩了内核仍会落盘；
- 跨进程：MAP_SHARED 实现共享状态。

### 6.6 Zygote CoW

**问题起点**：Android 冷启动一个 App 要几百 MB 内存（Framework、各种库），每个 App 都从头加载吗？

**解决方案**：Zygote（受精卵）——系统启动时**预加载所有常用类和资源**，fork 出一个"模板进程"；每启动 App 时 fork Zygote，继承所有预加载的东西。

**关键机制**：**Copy-on-Write**（写时复制）

```
   fork 瞬间                      父进程修改页 X
   ─────────                     ──────────────
   父进程 页表          父进程 页表
   ├─ Page X ─┐        ├─ Page X' ──▶ 物理页 X'（新）
   │          │ 共享    │
   子进程 页表 │        子进程 页表
   ├─ Page X ─┘        ├─ Page X ──▶ 物理页 X（原）
   
   fork 瞬间：父子共享所有页     修改页才真实复制一份
```

**CoW 的物理原理**：

- fork 时内核把父进程的页表复制给子进程，所有页标记为**只读**；
- 任一方试图写时触发**写保护异常**，内核分配新物理页，复制内容，更新页表为可写；
- 没写的页永远共享。

**对工程师的意义**：

- **Zygote 预加载**：Framework 类、字体、系统资源在 Zygote 加载后，所有 App 共享同一份物理内存（PSS 分摊的来源）；
- **KOOM 的 fork 子进程 dump**：fork 瞬间父子共享堆，子进程边写 hprof 边释放对应页，父进程继续运行几乎零 STW；
- **多进程架构**：子进程继承父进程的常量 / 单例，不占额外物理内存（但不能依赖，因为父进程写就 CoW 分离了）。

### 6.7 Smaps 内幕

**问题起点**：PSS 到底怎么算？`Debug.MemoryInfo` 的数字来自哪里？

**源头**：Linux 的 `/proc/[pid]/smaps`（详细内存映射）。

```
# cat /proc/1234/smaps
7f8c00000000-7f8c00010000 r-xp  00000000  08:01  12345  /system/lib/libc.so
Size:              64 kB
Rss:               48 kB
Pss:                4 kB     ← 关键：按比例分摊
Shared_Clean:      44 kB
Shared_Dirty:       0 kB
Private_Clean:      4 kB
Private_Dirty:      0 kB
Referenced:        48 kB
Anonymous:          0 kB
...
```

**PSS 的计算公式**：

```
PSS = Private_Clean + Private_Dirty + Σ(Shared_i / Shared_count_i)

即：独占页全算 + 共享页按分摊数分
```

**举例**：libc.so 被 12 个进程共享，占 48KB RSS。每个进程 PSS 分摊 48/12 = **4KB**。所有进程 PSS 之和 = 48KB = libc.so 真实物理占用。

**为什么要分 Clean / Dirty / Anonymous**？

| 类型 | 含义 | 可释放？ |
|---|---|---|
| Clean | 和磁盘一致（如 so 代码段） | 内存紧张时**直接丢弃**，再读磁盘 |
| Dirty | 被改过（如数据段） | 必须 **swap** 或 **保留** |
| Anonymous | 无文件背景（如 malloc） | 必须 swap（Android 用 zram） |

**工程启示**：

- **优化 PSS 要降 Private_Dirty**：Shared_Clean 分摊后对单进程贡献很小；
- **ClassLoader 共享**：多进程共用一个 Dex，Dex 数据段大头能分摊；
- **so 库预加载**：Zygote 预加载的 so，所有 App 共享 Shared_Clean，几乎零 PSS 增加。

### 6.8 对象头机制

**问题起点**：Java 对象到底占多少字节？`new Object()` 几个字节？

**对象内存布局**（64 位 JVM / ART）：

```
┌────────────────────────────────────────┐
│ Mark Word     （8 字节）                │  ← 哈希码 / GC 分代 / 锁状态
├────────────────────────────────────────┤
│ Class Pointer（4 字节，CompressedOops） │  ← 指向类元数据
├────────────────────────────────────────┤
│ 实例字段      （按声明顺序，含填充）        │
├────────────────────────────────────────┤
│ 对齐填充      （总大小 8 字节对齐）         │
└────────────────────────────────────────┘
```

**`new Object()` 实际占用**：

- Mark Word 8B + Class Pointer 4B = 12B，对齐到 **16B**。

**各类对象的内存成本**：

| 对象 | 字段 | 实际占用（含对齐） |
|---|---|---|
| `new Object()` | 无 | 16 B |
| `new Integer(1)` | int（4B） | 16 B |
| `new int[0]` | 长度（4B） | 16 B |
| `new int[10]` | 长度 + 10*4 = 44B | 56 B（含填充） |
| `new String("abc")` | 对 char[] 的引用 + hash | 24 B（不含 char[]） |

**CompressedOops（压缩指针）**：64 位 JVM 默认启用，把对象引用从 8 字节压到 4 字节（因为堆通常 < 32GB，用 2^35 寻址 = 32GB 已够）。

**🧠 工程意义**：

- 小对象的"壳成本"（16B 对象头）相对数据可能很大，所以 `List<Integer>` 比 `IntArray` 浪费得多；
- `ArrayMap` 把 kv 扁平存两个数组，省去每个 Entry 对象的 16B 头，小规模下节省显著；
- 字符串 `intern()` 可以让相同内容的 String 共享，但要小心 StringTable 泄漏。

### 6.9 JNI 引用三型

JNI 层的引用管理是 **Native 泄漏的重灾区**，面试高频。

| 类型 | 作用域 | 释放方式 | 用途 |
|---|---|---|---|
| **LocalRef** | 当前 JNI 调用帧 | **自动**（返回 Java 时） | 临时持有 jobject |
| **GlobalRef** | 跨 JNI 调用 | **必须手动** `DeleteGlobalRef` | 跨函数持有 |
| **WeakGlobalRef** | 跨 JNI 调用 | **必须手动** `DeleteWeakGlobalRef` | 不阻碍 GC |

**设计思想**：为什么要分三种？因为 **Java GC 不知道 Native 代码里是否还在用这个对象**——GC 只扫 Java 堆的根集。所以 JNI 层必须显式告诉 GC："这个对象我 Native 还在用，别回收"（GlobalRef），或者"我有个引用但你可以回收"（WeakGlobalRef）。

**LocalRef 的生命周期**：

```c
JNIEXPORT void JNICALL myFunc(JNIEnv* env, jobject obj) {
    jclass clazz = (*env)->FindClass(env, "java/lang/String");  // LocalRef
    // ... 用 clazz ...
    // 返回时自动释放 clazz
}
```

**LocalRef 的坑**：默认 LocalRef Table 只有 **512 项**。循环里不释放会 OOM：

```c
// ❌ 错误：循环创建 LocalRef，表撑爆
for (int i = 0; i < 10000; i++) {
    jobject s = createString(env, i);
    // 没有 DeleteLocalRef(env, s)，10000 个 LocalRef 全驻留
}

// ✅ 正确：手动释放
for (int i = 0; i < 10000; i++) {
    jobject s = createString(env, i);
    useString(s);
    (*env)->DeleteLocalRef(env, s);
}
```

**GlobalRef 的典型泄漏**：

```c
jobject g_callback;

JNIEXPORT void JNICALL register(JNIEnv* env, jobject cb) {
    g_callback = (*env)->NewGlobalRef(env, cb);  // 持有 Java 对象
    // ⚠️ 必须有对应的 unregister 调用 DeleteGlobalRef
}

JNIEXPORT void JNICALL unregister(JNIEnv* env) {
    if (g_callback) {
        (*env)->DeleteGlobalRef(env, g_callback);
        g_callback = NULL;
    }
}
```

GlobalRef 持有的 Java 对象在 GC Root 里是 **"JNI Global"** 类型。LeakCanary 看不到，MAT dump 时会标出。

### 6.10 分配器演进

Android Native 内存分配器的演进：

| 版本 | 分配器 | 特点 |
|---|---|---|
| Android 4.x | **dlmalloc** | Doug Lea 经典 malloc，简单但碎片多 |
| Android 5-10 | **jemalloc** | 多 arena 减少锁竞争，碎片少 |
| Android 11+ | **Scudo** | 安全优先：防堆溢出、UAF、double free |

**为什么从 jemalloc 换到 Scudo**？

- jemalloc 性能好，但一些漏洞（如 heap overflow）被用于攻击；
- Scudo 由 LLVM 团队开发，**安全加固**：每个分配带 cookie、chunk 之间有 guard page、随机化布局；
- 性能代价约 5-10%，但在安全和性能之间平衡。

**jemalloc 的 arena 设计**：

```
   普通 malloc              jemalloc
   ────────────             ────────
   全局锁                   多 arena（通常 4 × CPU 数）
   所有线程竞争             线程 → 哈希 → arena，分散竞争
```

**对工程师的意义**：

- **Native 内存碎片**：即使有 jemalloc，长时间频繁 malloc/free 不同大小仍会碎片化；
- **大块分配**：> 16KB 的 malloc 内部走 mmap，不走 arena；
- **工具链**：`malloc_debug`、`libwrap` 可以 hook 分配器统计用量，但有 10-30% 性能损失。

## 07、高频追问

> **面试官最爱问**的 13 个"陷阱题"。每题按"问题 → 直觉答案 → 为什么错 → 正确答案 → 延伸追问"展开。

### Q1 占用越小越好吗

- **直觉**：越小越省，当然越好。
- **错在哪**：忽略了"时间维度"。
- **正解**：**稳定 >> 低占用**。稳定 200MB vs 波动 50-150MB，后者更差——波动意味着 GC 频繁，每次 STW 5-20ms 直接掉帧。目标是"稳定在预算内"，不是"追求最低"。
- **追问**：那预算怎么定？→ 按设备 RAM 的 30% 为上限，参考行业基准（Android 中端机 < 200MB、低端机 < 100MB）。

### Q2 弱引用能防泄漏

- **直觉**：WeakReference 包一下就不泄漏了。
- **错在哪**：弱引用只保证"不阻止"回收，但回收时机**不可控**。
- **正解**：实测弱引用从"强引用消失"到"真正回收"：不施压时 P99 > 60 秒，施压时 200ms–1.5 秒，主动 System.gc() 50–80ms。所以弱引用是**兜底不是依赖**——关键路径还是要显式释放。
- **追问**：什么时候必须用 weak？→ "单向知道但不持有"的场景：子组件知道父组件存在但不想延长它的生命周期。

### Q3 largeHeap 的真相

- **直觉**：堆变大了，OOM 肯定少。
- **错在哪**：OOM 的根因如果是"泄漏/抖动/地址碎片"，变大堆没用。
- **正解**：largeHeap 只是**延后** OOM 5-10%，副作用严重：
  1. 鼓励应用占更多内存，拉高系统 RAM 压力；
  2. 单次 GC 时间变长；
  3. 对 32 位地址空间 OOM 无效（甚至加剧碎片）。
- **追问**：什么情况下该用？→ **几乎不该用**。极少数场景如游戏引擎、大图编辑，确实需要大堆才能跑业务，否则是治标不治本。

### Q4 地址空间之谜

- **直觉**：怎么可能？PSS 才 200MB，maxHeap 还有 300MB 空间。
- **错在哪**：混淆了"**物理内存**"和"**虚拟地址空间连续块**"。
- **正解**：32 位进程虚拟地址空间上限 ~3GB（用户态），但随着 alloc / release 反复进行会碎片化。运行 1 小时后，剩余 2GB 虚拟地址可能最大连续块只有 35MB——这时 20MB Bitmap 分配就 OOM。
- **追问**：怎么监控？→ 读 `/proc/[pid]/maps`，计算最大连续 free 块。< 50MB 即危险。根治方案是升级 64 位（256TB 地址空间）。

### Q5 catch OOM 的陷阱

- **直觉**：加个 try-catch 就不崩了。
- **错在哪**：catch 后未释放资源，下次分配继续 OOM，而且崩溃日志被吞。
- **正解**：**catch OOM 是反模式**。实测某 App 加 catch 后总崩溃率反而上升——因为问题被掩盖。正确做法是 catch 后立即执行**降级重试**：
  ```kotlin
  try { 
      BitmapFactory.decodeFile(path)
  } catch (e: OutOfMemoryError) {
      imageCache.evictAll()
      BitmapFactory.decodeFile(path, Options().apply { inSampleSize = 2 })
  }
  ```
- **追问**：OOM 后 System.gc() 有用吗？→ 可能有用（建议 GC），但不保证。更好的是从源头避免 OOM。

### Q6 iOS 没 GC 问题

- **直觉**：ARC 自动管理，所以 iOS 没内存问题。
- **错在哪**：ARC 不解决"**循环引用**"和"**延迟释放**"。
- **正解**：iOS 内存问题数量和 Android 相当：
  - **循环引用**：Block 捕获 self、Delegate strong 引用 → 必须 `[weak self]` 或 `weak` 关键字；
  - **Autorelease 池**：延迟释放导致瞬时峰值；
  - **Native 内存**：CoreGraphics / 视频解码不受 ARC 管；
  - **jetsam 杀进程**：等价于 Android LMK。
- **追问**：ARC 的引用计数更新为什么是线程安全的？→ 用原子操作（`atomic increment/decrement`），有 2-5% 性能开销。

### Q7 对象池误用

- **直觉**：复用对象 = 减少 GC = 性能更好。
- **错在哪**：忽略了池本身的管理开销。
- **正解**：对象池只适合**满足三个条件**的对象：
  1. 对象大（> 1KB）；
  2. 创建昂贵（含初始化逻辑）；
  3. 生命周期可控（有明确的借用-归还时机）。
- **反例**：小对象（`Integer`、`Point`）池化反而更慢——JVM 的 TLAB（见 §6.3）让小对象分配几乎零成本。
- **追问**：Bitmap 池为什么还要配 inBitmap？→ inBitmap 复用"内存"而不是对象壳子，直接把新 Bitmap 的像素写到旧 Bitmap 的 Native 内存里。

### Q8 LeakCanary 盲区

- **直觉**：工具说没泄漏就没泄漏。
- **错在哪**：LeakCanary 有三大盲区。
- **正解**：
  1. 只检测 Activity / Fragment / View / ViewModel / Service；
  2. 检测延迟 30 秒+，短切换可能漏报；
  3. 看不见 Native 泄漏（Bitmap 像素、JNI GlobalRef、so 库 malloc）。
- **追问**：怎么线上用？→ Debug 全开；Release 改用 KOOM（Java 堆 > 90% 时 fork 子进程 Dump，CoW 不阻塞主进程，详见 §6.6）。

### Q9 Bitmap OOM 本质

- **直觉**：Bitmap 占内存多，所以是图太大。
- **错在哪**：OOM 可能是地址空间碎片。
- **正解**：Bitmap OOM 可能有三种原因：
  1. 单张图太大 → inSampleSize 下采样；
  2. 累积缓存太多 → LRU 配 maxSize；
  3. 32 位地址碎片 → 升 64 位。
- **追问**：怎么判断是哪种？→ 看 OOM 栈 + 看 `/proc/[pid]/maps` 最大连续块，小于 50MB 就是地址碎片。

### Q10 后台杀的原因

- **直觉**：后台杀 = LMK = 内存不够。
- **错在哪**：后台杀的原因有很多种。
- **正解**：
  1. LMK（整机内存压力）；
  2. ANR（主线程阻塞 5 秒+）；
  3. 用户手动清理；
  4. OEM 定制策略（小米/华为后台保活策略）；
  5. 电池优化（Doze 模式）。
- **追问**：怎么降低后台被杀率？→ onTrimMemory 响应释放内存 + 关键场景起前台 Service + 适配各家 OEM 保活白名单。

### Q11 Finalize 反模式

- **直觉**：重写 `finalize()` 能在对象回收前做清理。
- **错在哪**：`finalize()` 有一堆问题：
  1. **执行时机不确定**：Finalizer 线程优先级低，可能永远不执行；
  2. **需要两次 GC**：第一次把对象放 F-Queue，第二次才真正回收；
  3. **异常被吞**：finalize 里的异常被 silently 吃掉；
  4. **对象复活**：finalize 里 `this.staticField = this` 能让对象起死回生（极反模式）；
  5. **Java 9 已 deprecated**。
- **正解**：用 **`Cleaner`（PhantomReference 子类）** 替代（见 §6.4）。Android 的 `DirectByteBuffer`、新版 `Bitmap` 都用 Cleaner。
- **追问**：为什么 Cleaner 更好？→ Cleaner 不依赖 Finalizer 线程，不会复活对象，单次 GC 就完成清理。核心是把"清理动作"和"被清理对象"分离，避免循环依赖。

### Q12 Zygote fork 快在哪

- **直觉**：fork 要复制父进程所有内存，应该很慢。
- **错在哪**：现代 Linux 的 fork 用 **Copy-on-Write**（见 §6.6）。
- **正解**：fork 瞬间**只复制页表**（几 KB），物理内存共享、页标记只读；写时才触发缺页异常真实复制。所以 fork 一个占 500MB 的 Zygote 只需几毫秒。
- **追问**：那什么时候真的会复制内存？→ 父子任一方写内存。所以 Zygote 预加载的类元数据（只读）永远共享；Java 堆因为 GC 时会移动对象（标记位、Mark Word 改写），会很快 CoW 分离。
- **再追问**：为什么 Android App 的 Dalvik heap 要在 fork 后"预加载 class"而不是 fork 前？→ 为了共享更多只读数据，减少 CoW 带来的物理内存浪费。Zygote 在启动时就预加载类元数据，所有 fork 出来的 App 共享这部分。

### Q13 ThreadLocal 泄漏

- **直觉**：ThreadLocal 不是用 WeakReference 包 key 了吗，怎么还泄漏？
- **错在哪**：WeakReference 保护的是 **key**，**value** 仍然是强引用。
- **正解**：ThreadLocal 的数据结构：
  ```
  Thread.threadLocals = ThreadLocalMap
      ├─ Entry[key=WeakRef<ThreadLocal>, value=strong Object]
  ```
  当 `ThreadLocal` 变量被回收后，key 变 null，但 value 仍强引用。只有下次 `get/set/remove` 时才会清理这个 null entry。
- **泄漏场景**：线程池里的 worker 线程**永不退出**，如果用 ThreadLocal 存了大对象但不显式 `remove()`，这个大对象会伴随线程生命周期永久存在。
- **正解**：**用完必须 `threadLocal.remove()`**。或者用 try-finally 保证清理。
- **追问**：为什么 key 用 WeakReference 而 value 不用？→ 如果 value 也 weak，程序逻辑随时可能发现 ThreadLocal 的值变 null，不可控。设计上让 key weak 已经能解决"ThreadLocal 变量被回收后，Entry 自动清理"，但要求使用者配合调 remove()。

## 附录：面试模板

> 5 个最高频面试题的**标准回答模板**。背会这 5 个，面试内存部分基本稳了。

### A1 内存优化理解

**90 秒版**：

> 内存优化的本质是"管理对象的生命周期"。所有问题可以归为三类：
> 
> **抖动**——对象生得太多太快，典型是 onDraw 里 new 对象，导致 GC 频繁、掉帧；
> **泄漏**——对象活得太久该死不死，典型是静态变量持 Activity、Handler 没清，导致内存持续上涨；
> **溢出**——单个对象占得太大，典型是 Bitmap 没做分辨率自适应，一张 8K 图能占 130MB。
> 
> 优化不是追求最低占用，而是让对象的"生、存、死"对齐业务时间窗口。目标是**稳定在预算内**——波动 50-150MB 比稳定 200MB 更差，因为波动意味着频繁 GC。
> 
> 我做过的案例：图片浏览器 OOM 率 8.3% → 0.4%，就是按这个思路，先用 LeakCanary 修泄漏、再做 Bitmap 下采样和复用池、最后接 onTrimMemory 分级响应，三类都治才有效。

### A2 OOM 排查流程

**STAR 模板**：

> 第一步**分类**：OOM 不是单一问题，先看是 A 堆 OOM（有 OutOfMemoryError 栈）、B 系统 OOM（无栈，进程被杀）、C 地址空间 OOM（32 位 Native crash）、还是 D 资源耗尽（Too many files/threads）。
> 
> 第二步**看曲线**：拉线上内存趋势图，看是单调上升（泄漏）、锯齿（抖动）、尖峰（大对象）、还是阶梯（缓存堆积）。
> 
> 第三步**抓现场**：接 KOOM 在 Java 堆 > 90% 时 fork 子进程 Dump hprof（CoW 不阻塞主进程），离线用 MAT 分析——找到泄漏对象后，查从 GC Root 的最短引用链，定位第一个"不该持有"的引用。
> 
> 第四步**对症治理**：泄漏修解绑/弱化、抖动做对象池、溢出做下采样和缓存上限、兜底做 onTrimMemory 分级响应。

### A3 LeakCanary 原理

> LeakCanary 的核心是 **WeakReference + ReferenceQueue + 主动 GC** 三件套：
> 
> 1. **监听 Activity.onDestroy**：用 `KeyedWeakReference` 包住 Activity，关联一个 ReferenceQueue。
> 2. **延迟 5 秒**后主动 `Runtime.gc()`。
> 3. **检查 ReferenceQueue**：Activity 被正常回收，WeakReference 会入队；没入队说明还有强引用拉着，判定为泄漏。
> 4. **Dump hprof + 分析引用链**：用 shark 库求从 GC Root 到泄漏对象的最短路径。
> 
> **核心等价关系**：GC 后仍可达 = 被强引用持有 = 泄漏。
> 
> **检测延迟** ≈ 30 秒，所以线上不适合用——线下 Debug 包用，线上改用 KOOM（基于 fork + CoW 的 dump 不阻塞主进程）。

### A4 ART GC 流程

> ART 从 Android 5 开始取代 Dalvik，核心演进：
> 
> **堆划分**（分代）：Young Gen（Eden + 两个 Survivor）+ Old Gen + Large Object Space。
> 
> **GC 类型**：
> - **Young GC**（Alloc GC）：Eden 满了触发，单次 5–20ms；
> - **Partial GC**：清理 Old Gen 部分区域；
> - **Full GC / Concurrent GC**：整堆，大部分阶段并发，只有 Mark Root 和 Final Mark 短暂 STW。
> 
> **核心算法**：三色标记（白/灰/黑），并发标记时用 **SATB 写屏障**解决"对象消失"问题——引用删除时把被删对象置灰，保证本轮扫描完成前的可达对象不漏。
> 
> **Android 版本演进**：
> - Android 5：CMS（Concurrent Mark Sweep），STW 10-50ms；
> - Android 8：**CC**（Concurrent Copying），STW < 5ms，顺便压缩堆避免碎片；
> - Android 11+：分代 CC，Young 更快，STW < 2ms。
> 
> **TLAB**：每线程私有分配缓冲，`new` 走 bump pointer，无锁，让小对象分配几乎零成本。

### A5 优化故事线

**背景**：某图片浏览器 App 在低端 2GB 设备上 OOM 率 8.3%，用户只能浏览 12 张图就崩，广告变现受影响。此前 3 周团队按"缩小缓存 + 强制下采样 + largeHeap"的思路做了 3 次优化，OOM 率只降到 6.5%。

**归因发现**：按 OOM 分类决策树重新分析——
- 内存曲线单调上升（泄漏型 60%）：LeakCanary 定位到 Activity → ImageAdapter → ImageView → onLayoutListener → Activity 的循环引用；
- 滚动期 GC 10-15 次/秒（抖动型 25%）：Allocation Tracker 发现 onDraw 内每帧 new 5-8 个临时 Bitmap；
- 单张 8K 图解码 240MB（溢出型 15%）：根本没做分辨率自适应。

**治理**：5 天内按 ROI 顺序执行——
- Day 1：LeakCanary 修复 12 处 listener 泄漏；
- Day 2：Bitmap 做 inSampleSize 自适应；
- Day 3：inBitmap 复用池 + 容器全 WeakHashMap；
- Day 4：onTrimMemory 5 级响应；
- Day 5：灰度验证 + A/B 实验。

**结果**：
- OOM 率：8.3% → **0.4%**（-95%）；
- 浏览深度：12 张 → **38 张**（+217%）；
- 滚动 FPS：25 → 56；
- 内存峰值（低端机）：380MB → 145MB；
- 广告变现：**+45%**，用户 D1 留存 +8%。

**沉淀**：**OOM 不是单一问题**，必须按"泄漏/抖动/溢出"三类分别诊断和治理。单优化任一类都不够——缩小缓存只是边角动作。

> **一句话总结**：
> 
> 内存治理是防守，OOM 治理是底线。防守降低底线被击穿的概率，底线保证被击穿时不至于崩盘。
> 
> **学会"生命周期对齐"思维，你拿到的不只是内存优化的钥匙，而是一切资源管理工程的通用心法**——文件描述符、网络连接、GPU 纹理、数据库连接……所有有限资源都遵循"生/存/死"三态模型。
