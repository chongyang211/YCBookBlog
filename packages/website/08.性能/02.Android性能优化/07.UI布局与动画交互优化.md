## 01.开篇灵魂拷问

读文章前，先问自己三个问题。答得上来，说明你已理解；答不上来，就是本文的学习目标。

### 1.1 层级之惑

**Q：教科书说"用 ConstraintLayout 替代嵌套 LinearLayout 可以优化性能"——那把所有布局都改成 ConstraintLayout 就对了？**

**🤔 疑惑**：很多开发者把这当成"布局优化黄金律"，无脑把 LinearLayout/RelativeLayout 全改成 ConstraintLayout——但实测简单 cell 反而**变慢 10%**，这是为什么？

**💡 解答**：**ConstraintLayout 的性能优势来自"扁平化"，不是来自 CL 本身**。CL 内部要跑**约束求解器**（Cassowary 算法），单次 measure 开销比 LinearLayout 大 2-3×。只有当嵌套层级 ≥ 4 层时，"扁平化省下的 Measure 轮次 > CL 自身的求解开销"，才有净收益。简单 cell（1-2 层）用 CL 是**负优化**。

> **心法**：**所有"经验招"都有场景边界**——ConstraintLayout 只在"嵌套 ≥ 4 层"才赢。贯穿案例第 1 周"把 LinearLayout 都改 CL"反而让简单 cell 慢 10%——这是经验派最经典的翻车姿势。

### 1.2 响应之惑

**Q：加购按钮 FPS 60、动画丝滑，用户为什么还投诉"点了没反应"？**

**🤔 疑惑**：所有指标都"对"——FPS 60、延迟数据达标，但用户还是说"卡"——指标和体验为什么背离？

**💡 解答**：**用户感知的"卡"是"**从手指按下到看到任何反馈**"的时间，不是"动画是否流畅"**。副案例电商加购的问题是：点击后业务逻辑同步跑 280ms（库存检查+购物车更新+埋点+数字刷新），**用户看到的是"按下按钮 → 冻结 280ms → 突然动画**"，哪怕动画 FPS 100，前 280ms 就是"卡"。**Doherty 阈值 100ms** 是人类工程学的物理硬线——超过 100ms 用户感知就从"即时"崩塌到"延迟"。

> **心法**：**用户感知 = 首次反馈时间 + 动画流畅度，不是单一指标**。治理顺序永远是——**第 1 步让首次反馈 < 100ms**（点击反馈/占位态/skeleton），**第 2 步让动画走合成器**。顺序颠倒就是副案例"3 周错方向"。

### 1.3 异步之惑

**Q：异步 Inflate、setLayerType HARDWARE、will-change——这些"硬件加速"手段是不是无脑开就对了？**

**🤔 疑惑**：既然官方文档说这些可以加速，那是不是全开最快？

**💡 解答**：**所有"加速"手段都是用显存/CPU 换时间，不是免费午餐**：
- **异步 Inflate**：只有创建成本 > 50ms 的复杂布局才有收益，简单 cell 异步后反而因线程切换 + Attach 闪烁**总时间变长**；
- **setLayerType HARDWARE**：为 View 创建硬件图层，**吃显存**（一个 1080p 全屏 layer 约 8MB），滥用会 OOM（主案例第 3 周 setLayerType 滥用 GPU 内存 +80MB，低端机 OOM 率升 5×）；
- **will-change / shouldRasterize**：同上，提示合成器预升层，开销也在显存。

> **心法**：**"加速"手段的本质是预支资源**——没有场景判断就全开，等于透支破产。贯穿案例 4 周翻车本质都是"**无场景地开启加速**"。

## 02.探索问题本质

### 2.1 静态 UI 与动态交互的关系

**核心命题**：**UI 性能是"静态布局 + 动态交互"同一流水线的两种时间切面**。

```
   同一主线程 + 同一渲染流水线：
   
   ┌─ 静态时间（首次或切页）─┐  ┌─ 动态时间（持续交互）────────┐
   │  Inflate               │  │  Input → dispatch → Layout │
   │  Layout（全树）         │  │  → Compose → Display         │
   │  Draw（全屏）           │  │  （每帧 16.67ms 预算）        │
   │  → 一次性产出           │  │  → 持续产出 60 fps              │
   └──────────────────────┘  └──────────────────────────────┘
         ↓ 治理手段共享：减节点 + 异步化 + 合成器加速
   ┌────────────────────────────────────────────────┐
   │ 核心共识：静态页面"产帧成本"高 → 动态交互必卡    │
   │          动态交互"持续产帧" → 静态是地基         │
   └────────────────────────────────────────────────┘
```

**两者的工程关系**：

| 维度 | 静态 UI | 动态交互 |
|---|---|---|
| **时间性质** | 一次性（Inflate 首次 / Layout 全树） | 持续（每帧 16.67ms） |
| **关键指标** | 首屏打开 P95、Inflate 时长 | FPS、输入响应 P99、帧时长分布 |
| **典型问题** | 层级深、Inflate 慢、重绘大 | 响应延迟、动画抖动、滚动卡 |
| **治理层** | 减节点 + 延 Inflate + 缩重绘 | 合成器 + 响应感知 + 异步业务 |
| **公共基础** | 三阶段成本模型（Inflate/Layout/Draw） | 同一模型，Layout/Draw 以帧为单位 |

> **心法**：**静态是地基，动态是时间轴上的延伸**——地基不稳（页面产帧成本超预算），上面任何动画都会卡。治 UI 必须先治静态，再治动态。

### 2.2 现象分类

**UI 卡顿与交互延迟的四大现象**：

| 现象 | 典型场景 | 底层根因 | 对应章节 |
|---|---|---|---|
| **首屏白屏** | 详情页打开慢、冷启首屏慢 | Inflate 过重 + 层级深 | §3.1 §5.1 |
| **滚动顿挫** | 列表滑动掉帧 | Layout 复杂 + onBindViewHolder 阻塞 | §3.1 §5.4 |
| **响应延迟** | 点击按钮 300ms 才有反馈 | 业务逻辑同步 + 事件队列拥堵 | §3.2 §5.3 |
| **动画抖动** | 动画时快时慢、P99 帧时长高 | 非合成器属性 + 强制同步布局 | §3.2 §5.2 |

**跨平台等价映射**：

| 平台 | 首屏慢 | 滚动卡 | 响应慢 | 动画抖 |
|---|---|---|---|---|
| Android | Inflate 慢 + 层级深 | RecyclerView bind 慢 | InputDispatcher 延迟 | left/top 属性动画 |
| iOS | XIB 加载 + Autolayout | UITableView cellForRow 慢 | main thread hang | frame 动画非 Core Animation |
| Web | DOM 构建 + CSSOM | 虚拟滚动 reflow | INP 高 | top/left 替代 transform |
| 跨端 | 组件树构建 | List 组件 bind | JS Bridge 阻塞 | 非原生动画 |

### 2.3 三阶段成本模型

**核心公式**：

```
   单次 UI 产出的主线程成本 = Inflate（首次） + Layout × N + Draw × M
   
   N = 当前帧需要重测量的节点数
   M = 当前帧需要重绘的节点数
```

**▶▶ 优化优先级公式**（成本 × 频次）：

```
   ① Layout per 帧：  5-50ms × 60 帧/秒 = 300-3000 ms/秒（最高）
   ② Draw per 帧：    1-20ms × 60 帧/秒 = 60-1200 ms/秒
   ③ Inflate：      50-500ms × 1 次 = 50-500 ms（一次性，但首屏关键）
```

**▶▶ 三类问题的物理根因**：

```
   ┌────────────────────────────────────────────┐
   │ A. 层级过深：树形递归成本指数级               │
   │    根因：嵌套布局 / RelativeLayout 双测量     │
   │    特征：Layout 阶段耗时 > 50ms              │
   ├────────────────────────────────────────────┤
   │ B. 重绘范围过大：onDraw 调用太多/太大          │
   │    根因：父布局 invalidate 全量；Shader 复杂  │
   │    特征：Draw 阶段耗时 > 20ms                │
   ├────────────────────────────────────────────┤
   │ C. Inflate 慢：XML 解析 + 反射 + 资源加载    │
   │    根因：层级深 + 自定义 View 多 + 大量 drawable│
   │    特征：首屏 Inflate > 200ms                │
   └────────────────────────────────────────────┘
```

**三类问题占比**（头部 App 统计）：

| 类型 | 占首屏卡顿 | 占滚动卡顿 | 治理难度 |
|---|---|---|---|
| A 层级过深 | 50% | 70% | 中（层级重构有成本） |
| B 重绘过大 | 20% | 20% | 低（局部 invalidate 即可） |
| C Inflate 慢 | **30%** | 5% | 中（预加载 / 异步 Inflate） |

> ▶▶ **回扣主案例**：新闻 App 详情页同时命中三类——A（9 层根布局 + 评论 6 层 RelativeLayout）+ B（SVG 实时解析 + 大背景 invalidate）+ C（首屏全量同步 inflate）。**经验派失败的根因是"不分类"——只治一类不可能解决三类共存的真实场景**。

### 2.4 Doherty 感知基线

**Doherty 阈值**（1982 年 IBM 研究员 Doherty 的工程学结论）：

```
   用户感知的时间分级：
   
   < 16ms       即时（单帧）              ← 动画黄金区
   16-100ms     流畅                      ← 响应黄金区
   100-300ms    可感知延迟                 ← ★ Doherty 阈值
   300ms-1s     明显卡顿                   ← 用户抱怨
   > 1s         中断感（任务重启）           ← 用户流失
```

**▶▶ 100ms 的物理意义**：
- 人类视觉皮层处理延迟约 50ms；
- 决策阈限约 50ms；
- 两者叠加 100ms 是"**感知即时**"的硬线；
- 超过 100ms 大脑启动"等待"模式，体验崩塌。

**▶▶ 60fps 的物理意义**：
- 显示器 Vsync 60Hz = 每帧 16.67ms；
- 掉一帧 = 33.33ms 用户肉眼可感；
- 连掉 3 帧 = 100ms 触碰 Doherty 阈值。

**▶▶ 三个共识**（下篇原文心法）：

| 共识 | 含义 |
|---|---|
| **平均 FPS 没用** | 用户感受的是"**最差那帧**"，必须看 P99 帧时长 |
| **120Hz 不是简单 2 倍 60fps** | 每帧预算 8.3ms，是 CPU/GPU **降维打击** |
| **GPU 不是免费的** | 开太多硬件加速层触发"**层爆炸**"，性能更差 |

> ▶▶ **回扣副案例**：电商加购点击响应 P95 **380ms**——超 Doherty 3.8 倍，哪怕动画 FPS 60 用户也说"卡"。**100ms 黄金线是人类工程学的物理硬线，不是经验值**。

### 2.5 面试锚点

**Q：UI 性能优化的本质是什么？静态布局和动态交互是什么关系？**

**答题模板**（统一视角 + 三阶段模型 + Doherty 基线）：

> UI 性能的本质是"**在 16.67ms 帧预算内完成产帧**"——所有现象（白屏/卡顿/响应慢/抖动）都是产帧成本超预算的不同时间切面：
>
> **① 静态 UI 与动态交互是同一流水线的两个时间切面**：
> - 静态：首次 Inflate + 全树 Layout + 全屏 Draw → 一次性产帧成本；
> - 动态：每帧 Input → Layout → Compose → Display → 持续产帧成本；
> - 共享同一主线程 + 同一渲染流水线。
>
> **② 三阶段成本模型**（§2.3）：
> $$单帧成本 = Inflate(首次) + Layout \times N + Draw \times M$$
> - **Layout**：成本 5-50ms × 60fps = **300-3000ms/秒**（最高优先级）；
> - **Draw**：成本 1-20ms × 60fps = 60-1200ms/秒；
> - **Inflate**：50-500ms × 一次（首屏关键）。
>
> **③ Doherty 感知基线**（§2.4）：
> - **100ms**：用户感知"即时"的物理硬线（视觉 50ms + 决策 50ms）；
> - **16.67ms**：60fps 单帧预算；
> - **P99 帧时长**：用户真实感受指标，均值 FPS 骗人。
>
> **④ 治理方法论**：
> - 静态 → 减节点 + 延 Inflate + 缩重绘；
> - 动态 → 走合成器 + 响应前置 + 异步业务；
> - **静态是地基，动态是时间轴延伸**——必须先治静态。
>
> **一句话总结**：**UI 优化没有银弹**——每个"经验招"（CL 扁平化/异步 Inflate/setLayerType）都有场景边界，**数据驱动按场景选择**是唯一正解。

## 03.排查归因方法

### 3.1 静态 UI 归因决策树

静态 UI 问题（首屏白屏 / 滚动顿挫）的**三问决策树**：

```
   UI 卡顿现象（首屏 P95 > 500ms 或 滚动 P99 > 50ms）
      │
      ├─【第一问】FrameMetrics 哪个阶段最长？
      │     ├─ Layout 阶段 > 10ms → 走 A 分支
      │     ├─ Draw 阶段 > 10ms → 走 B 分支
      │     └─ Inflate 阶段 > 50ms（仅首帧）→ 走 C 分支
      │
      ├─【A 分支：Layout 慢】
      │     ├─ 层级深 ≥ 5 → §5.1 减节点（扁平化）
      │     ├─ RelativeLayout 双测量 → §5.1 换 CL
      │     ├─ 节点数 ≥ 100 → §5.1 ViewStub 延迟
      │     └─ 复杂自定义 View onMeasure 慢 → §5.1 测量缓存
      │
      ├─【B 分支：Draw 慢】
      │     ├─ 过度绘制 ≥ 3 层 → §5.1 消除冗余背景
      │     ├─ 复杂 Shader（圆角/阴影/模糊）→ §5.1 位图化
      │     ├─ 大图未裁剪 → §5.1 缩放 + sampleSize
      │     └─ invalidate 范围过大 → §5.1 invalidate(Rect)
      │
      └─【C 分支：Inflate 慢】
            ├─ 首屏 > 200ms → §5.1 预 Inflate / AsyncLayoutInflater
            ├─ ViewStub 滥用 → §5.1 ViewStub 仅次级内容
            ├─ 第三方自定义 View 多 → §5.1 替换为简单 View
            └─ 大量 drawable 资源 → §5.1 懒加载
```

> **关键原则**：**先阶段定位，再分类治理**——绕过 FrameMetrics 直接猜测是经验派陷阱。贯穿案例 Day 2 决策树定位用了 **半天**，之前经验派 **3 周**都没定位到真因。

### 3.2 交互响应归因决策树

交互响应问题（点击慢 / 动画抖）的**三问决策树**：

```
   交互问题（响应 P95 > 100ms 或 动画 P99 > 33ms）
      │
      ├─【第一问】是"响应慢"还是"动画抖"？
      │     ├─ 响应慢（从点击到首次反馈 > 100ms）→ 走 D 分支
      │     └─ 动画抖（动画中 P99 > 33ms）→ 走 E 分支
      │
      ├─【D 分支：响应慢】
      │     用 4 段模型分析（§3.3）：
      │     ├─ T_input→T_dispatch 慢 → 主线程事件队列拥堵，上游有长任务
      │     ├─ T_dispatch→T_layout 慢 → ★ 业务逻辑过重，§5.3 异步化
      │     ├─ T_layout→T_compose 慢 → 强制同步布局，§5.2 合成器
      │     └─ T_compose→T_display 慢 → GPU 合成压力，§5.2 层优化
      │
      └─【E 分支：动画抖】
            ├─ 使用非合成器属性（left/top/width）→ ★ §5.2 换 transform/opacity
            ├─ 动画中触发 setState → §5.3 业务异步化
            ├─ 多个动画同时跑 → §5.4 防抖批量
            └─ 高频输入（滚动/手势）→ §5.4 节流
```

> **▶▶ 关键认知**：**响应慢 90% 是业务逻辑过重**（T_dispatch→T_layout），**动画抖 70% 是非合成器属性**（left/top 替代 transform）——这是副案例电商加购的两大翻车点。

### 3.3 四段延迟模型

**交互延迟的四段分解**：

```
    用户触摸                首次渲染
       │                      │
       ▼                      ▼
   T_input ─ T_dispatch ─ T_layout ─ T_compose ─ T_display
      │           │            │          │           │
      │           │            │          │           │
     事件        事件分发      布局重算    GPU 合成    屏幕显示
     进队        到应用        measure/   RenderThread VSYNC 上屏
                  Choreographer layout     SurfaceFlinger
```

**▶▶ 四段的典型瓶颈**：

| 段 | 典型耗时 | 瓶颈场景 | 治理 |
|---|---|---|---|
| T_input → T_dispatch | 1-5ms | 主线程事件队列拥堵（上游长任务） | §5.1 主线程减负 |
| **T_dispatch → T_layout** | **5-300ms** | **业务逻辑过重** | **§5.3 响应感知** |
| T_layout → T_compose | 5-50ms | 强制同步布局 / 过度重绘 | §5.1 §5.2 |
| T_compose → T_display | 10-20ms | GPU 层数多 / 图层大 | §5.2 合成器 |

> **▶▶ 关键认知**：**90% 的响应延迟集中在 T_dispatch→T_layout 这一段**——这是业务代码的锅，不是渲染管线的锅。副案例电商加购的 280ms 延迟就在这一段（库存检查 + 购物车更新 + 埋点 + 数字刷新 4 步同步）。

### 3.4 案例归因

**▶▶ 主案例（新闻 App 详情页）完整归因过程**：

**Day 1：FrameMetrics 阶段拆解**

**▶▶ 副案例（电商加购动画）归因**：

**Day 1：输入延迟 4 段埋点**

- T_input→T_dispatch = 8ms（正常）

- 飞入动画用 **left/top**（不走合成器）
- 同时触发购物车数字 setState（**强制同步布局**）

**Day 3-4：四层治理**

| 治理层 | 动作 | 对应分支 |
|---|---|---|
| 三层响应感知 | 点击立即给视觉反馈（按钮按下态 + 动画占位） | D |

**结果**：响应 P95 **380ms → 45ms**（-88%）；动画 P99 **180ms → 17ms**；转化 **-8% → +3%**（恢复并提升）。

### 3.5 面试锚点

**Q：详情页打开慢、列表滚动卡——你的排查流程是什么？**

**答题模板**（三方案 + 决策树 + 四段模型 + 案例）：

> 按**三方案组合定位 + 决策树归因 + 分层治理**三步走：
>
> **第一步：三方案采集定位**（§4.1）
> - **FrameMetrics**（阶段级）：拿到 Inflate/Layout/Draw 各阶段耗时；
> - **自定义基类计时**（节点级）：精细到单个 View 的 onMeasure/onLayout/onDraw；
> - **Choreographer FPS**（全局级）：拿到 P99 帧时长分布。
>
> **第二步：决策树归因**（§3.1）
> - Layout 阶段 > 10ms → A 分支（层级深 / RL 双测量 / 节点多）；
> - Draw 阶段 > 10ms → B 分支（过度绘制 / 复杂 Shader / invalidate 范围大）；
> - Inflate 阶段 > 200ms → C 分支（首屏全量 inflate / 第三方 View 多）；
> - 响应延迟 → 走四段模型（§3.3），90% 卡在 T_dispatch→T_layout（业务逻辑过重）。
>
> **第三步：对症治理**（§5）
> - A → §5.1 减节点（扁平化 / ViewStub / 自定义 ViewGroup）；
> - B → §5.1 缩重绘（局部 invalidate / 位图化 / 消除冗余背景）；
> - C → §5.1 延 Inflate（AsyncLayoutInflater / 预 Inflate）；
> - 响应 → §5.3 响应感知（首反馈前置 + 业务异步）。
>
> **贯穿案例实证**：新闻 App 详情页 Day 1 用 FrameMetrics 定位三阶段都有问题，Day 2 决策树分类（Inflate 380ms + Layout 每帧 45ms + Draw 每帧 22ms），Day 3-4 四层治理落地，Day 5 Macrobenchmark 验证——**6 天搞定经验派 4 周没解决的问题**。
>
> **一句话总结**：**不要凭经验改代码**——UI 优化永远是"**先阶段定位，再分类治理**"，决策树的价值就是把 UI 这个"黑盒"拆成可量化、可归因的几条路径。

## 04.监控体系设计

### 4.1 采集三方案

UI 性能监控的核心矛盾是"**精细度 vs 开销**"——想精细到单个 View 就得插桩，一插桩 CPU 开销 5-15%。所以永远**三方案组合**：

```
   ┌──────────────────────────────────────────┐
   │ ① 节点级（onMeasure/Layout/Draw 插桩）     │  精细 单 View  开销 5-15%  线下为主
   ├──────────────────────────────────────────┤
   │ ② 阶段级（FrameMetrics / PerfHUD）        │  精细 阶段级   开销 1-2%   线上主力
   ├──────────────────────────────────────────┤
   │ ③ 全局级（FPS / INP / TTI）               │  粗粒度 页面级 开销 极低   仪表盘
   └──────────────────────────────────────────┘
```

**① 节点级采集**（线下排查主力）

```kotlin
// 自定义 View 基类计时
abstract class TimedView(ctx: Context) : View(ctx) {
    override fun onMeasure(wMs: Int, hMs: Int) {
        val t = System.nanoTime()
        super.onMeasure(wMs, hMs)
        Tracer.record("Measure", javaClass.simpleName, System.nanoTime() - t)
    }
    override fun onLayout(changed: Boolean, l: Int, t: Int, r: Int, b: Int) {
        val time = System.nanoTime()
        super.onLayout(changed, l, t, r, b)
        Tracer.record("Layout", javaClass.simpleName, System.nanoTime() - time)
    }
    override fun onDraw(canvas: Canvas) {
        val t = System.nanoTime()
        super.onDraw(canvas)
        Tracer.record("Draw", javaClass.simpleName, System.nanoTime() - t)
    }
}
```

或 ASM/Aspect 编译期注入——**线下性能分析用**，线上开销太大。

**② 阶段级采集**（线上监控主力，见 §4.2）

**③ 全局级采集**（SLO 跟踪）

```kotlin
Choreographer.getInstance().postFrameCallback(object : Choreographer.FrameCallback {
    var lastTime = 0L
    override fun doFrame(frameTimeNanos: Long) {
        if (lastTime > 0) {
            val interval = (frameTimeNanos - lastTime) / 1_000_000
            FrameTracer.record(interval)  // 累计分布
        }
        lastTime = frameTimeNanos
        Choreographer.getInstance().postFrameCallback(this)
    }
})
```

**三方案对比**：

| 方案 | 钩子位置 | 粒度 | 开销 | 跨端 | 线上 | 盲区 |
|---|---|---|---|---|---|---|
| ① 节点级 | onMeasure/Layout/Draw | 单 View | 5-15% | 需适配 | 否 | 侵入式 |
| ② 阶段级 | FrameMetrics / PerfHUD | 阶段 | 1-2% | 跨端 | 是 | 不知具体 View |
| ③ 全局级 | FPS / INP | 帧 / 页面 | 极低 | 全平台 | 是 | 不知阶段 |

### 4.2 FrameMetrics 阶段拆解

**Android FrameMetrics**（API 24+）是线上监控的"**X 光片**"，直接拿到每帧每阶段耗时：

```kotlin
// 注册帧度量监听
window.addOnFrameMetricsAvailableListener({ _, metrics, _ ->
    val input = metrics.getMetric(FrameMetrics.INPUT_HANDLING_DURATION)
    val anim = metrics.getMetric(FrameMetrics.ANIMATION_DURATION)
    val layout = metrics.getMetric(FrameMetrics.LAYOUT_MEASURE_DURATION)
    val draw = metrics.getMetric(FrameMetrics.DRAW_DURATION)
    val sync = metrics.getMetric(FrameMetrics.SYNC_DURATION)
    val cmd = metrics.getMetric(FrameMetrics.COMMAND_ISSUE_DURATION)
    val swap = metrics.getMetric(FrameMetrics.SWAP_BUFFERS_DURATION)
    val total = metrics.getMetric(FrameMetrics.TOTAL_DURATION)
    
    if (total > 16_670_000L) {  // 超一帧
        FrameMetricsReporter.record(input, anim, layout, draw, sync, cmd, swap, total)
    }
}, Handler(Looper.getMainLooper()))
```

**▶▶ 各阶段代表含义**：

| 阶段 | 含义 | 典型耗时 | 瓶颈 |
|---|---|---|---|
| INPUT_HANDLING | 事件分发 | 1-5ms | 事件队列拥堵 |
| ANIMATION | 动画回调 | 1-10ms | 动画回调代码过重 |
| **LAYOUT_MEASURE** | **测量+布局** | **5-50ms** | **层级深 / RL 双测量** |
| **DRAW** | **主线程 draw** | **1-20ms** | **过度绘制 / 复杂 Shader** |
| SYNC | 同步到 RenderThread | 1-5ms | 大量 displayList |
| COMMAND_ISSUE | GPU 指令提交 | 2-10ms | 层数多 |
| SWAP_BUFFERS | GPU 合成上屏 | 5-15ms | 图层尺寸大 |

**▶▶ 跨平台对照**：

| 平台 | 阶段级 API |
|---|---|
| Android | FrameMetrics API |
| iOS | Instruments Time Profiler + Core Animation |
| Web | Performance.measure() + Long Task API |
| 跨端 | 框架内置 Performance Trace |

### 4.3 输入延迟 4 段埋点

**交互响应 4 段模型**（§3.3）的落地埋点：

```kotlin
// 在 Activity 的 dispatchTouchEvent 和 Choreographer 上双打点
class LatencyActivity : AppCompatActivity() {
    private var tInput = 0L
    private var tDispatch = 0L
    
    override fun dispatchTouchEvent(event: MotionEvent): Boolean {
        if (event.action == MotionEvent.ACTION_UP) {
            tInput = event.eventTime * 1_000_000L  // event 内置时间戳（纳秒）
            tDispatch = System.nanoTime()
        }
        return super.dispatchTouchEvent(event)
    }
}

// 业务点击时打点
button.setOnClickListener {
    val tClick = System.nanoTime()  // T_dispatch 结束
    doBusinessLogic()
    val tLayout = System.nanoTime()  // T_layout 结束
    
    Choreographer.getInstance().postFrameCallback { frameNanos ->
        val tDisplay = frameNanos  // T_display（估算）
        LatencyReporter.record(
            dispatchDelay = (tDispatch - tInput) / 1_000_000,
            layoutDelay = (tLayout - tClick) / 1_000_000,  // ★ 关键段
            displayDelay = (tDisplay - tLayout) / 1_000_000
        )
    }
}
```

**▶▶ 关键段：T_dispatch→T_layout** = 业务逻辑耗时，**90% 的响应延迟集中在此**。

### 4.6 面试锚点

**Q：线上 UI 卡顿监控怎么做？FrameMetrics / 节点级 / 全局级怎么选？**

**答题模板**（三方案组合 + 阶段拆解 + SLO）：

> UI 性能监控的核心矛盾是"**精细度 vs 开销**"——必须**三方案组合**：
>
> **① 节点级（线下主力）**：onMeasure/Layout/Draw 插桩，精细到单个 View，但开销 5-15%，**仅线下定向排查用**。
>
> **② 阶段级（线上主力）**：**FrameMetrics**（API 24+）直接拿到每帧 7 个阶段耗时（INPUT/ANIM/LAYOUT/DRAW/SYNC/CMD/SWAP）。开销仅 1-2%，是**线上监控的 X 光片**。
>
> **③ 全局级（SLO 跟踪）**：Choreographer FPS、INP、TTI——仪表盘级别，开销极低。
>
> **分场景选择**：
> - 日常监控 → ② + ③ 组合（线上）；
> - 问题排查 → 加 ① 定位到具体 View（线下）；
> - 响应延迟 → §4.3 四段埋点（T_input/T_dispatch/T_layout/T_display）。
>
> **SLO 基准**：首屏 P95 ≤ 500ms、滚动 FPS ≥ 55、帧时长 P99 ≤ 33ms、响应 P95 ≤ 100ms。
>
> **贯穿案例实证**：新闻 App 详情页 Day 1 用 FrameMetrics 定位到 LAYOUT=520ms + Inflate=380ms，节点级计时精确到"评论 cell 6 层 RelativeLayout"是瓶颈——这是经验派 4 周没定位到的真因。
>
> **一句话总结**：**精细度 vs 开销的平衡要靠分层**——线下用节点级定位，线上用阶段级监控，仪表盘用全局级跟踪，三位一体缺一不可。

## 05.分层治理优化

### 5.0 四组量化实验

**本节是治理动作的"**求证基石**"**——每个"经验招"都要有数据场景边界，否则就是无脑迷信。

**实验一：ConstraintLayout vs 嵌套 LinearLayout 的场景边界**

| 场景（嵌套层级） | LinearLayout Inflate | ConstraintLayout Inflate | Layout 总耗时 LL | Layout 总耗时 CL |
|---|---|---|---|---|
| 1 层（扁平） | 8ms | 11ms | 2.1ms | **3.5ms（CL 慢 65%）** |
| 2 层 | 15ms | 16ms | 4.2ms | 5.1ms |
| 3 层 | 25ms | 22ms | 7.8ms | 7.2ms |
| **4 层** | **42ms** | **28ms** | **18.5ms** | **8.3ms（CL 快 55%）** |
| 5 层 | 68ms | 32ms | 32ms | 9.2ms（CL 快 71%） |

**启示**：**嵌套 ≥ 4 层时 CL 才赢**，1-2 层 CL 反而慢 65%。印证 §1.1 层级之惑。

**实验二：异步 Inflate 的场景边界**

| 布局复杂度 | 同步 Inflate 耗时 | 异步 Inflate 耗时 | 收益 |
|---|---|---|---|
| 简单 cell（<10 节点） | 8ms | 15ms（线程切换） | **-87% 负收益** |
| 中等（10-50 节点） | 35ms | 25ms | +29% |
| **复杂（> 50 节点）** | **120ms** | **40ms** | **+67%** |
| 超复杂（> 100 节点，含自定义 View） | 300ms | 85ms | +72% |

**启示**：**异步 Inflate 只对 > 50 节点的复杂布局有效**，简单布局反而负收益（线程切换 + Attach 闪烁）。

**实验三：Doherty 100ms 黄金线实验**

| 响应时间 | 用户主观评分（5 分制） | 任务完成意愿 | 投诉率 |
|---|---|---|---|
| < 100ms | 4.8 | 100% | 0.01% |
| 100-200ms | 4.2 | 95% | 0.3% |
| 200-300ms | 3.5 | 85% | 1.2% |
| **300-500ms** | **2.8** | **65%** | **5.5%** |
| > 500ms | 1.9 | 40% | 15% |

**启示**：**Doherty 100ms 是用户主观评分的断崖线**，超过 100ms 评分每 100ms 掉 0.7 分。印证副案例 380ms 响应导致转化 -8%。

**实验四：合成器属性 vs 非合成器属性**

| 动画属性 | 平均帧时长 | P99 帧时长 | GPU 耗电 |
|---|---|---|---|
| left/top（非合成器） | 18ms | **120ms** | 2.3× |
| width/height（非合成器） | 22ms | 150ms | 2.5× |
| **transform（合成器）** | **4ms** | **8ms** | **1.0×** |
| **opacity（合成器）** | **3ms** | **6ms** | **0.9×** |

**启示**：**transform/opacity 比 left/top 快 10 倍**，而且耗电只有 1/2——合成器加速是动画的唯一正解。

**四大实验启示合集**：

```
   CL 扁平化 → 仅 ≥4 层嵌套才赢，否则负 65%         ─┐
   异步 Inflate → 仅 >50 节点才赢，否则负 87%        │
   Doherty 100ms → 超线每 100ms 评分掉 0.7 分       ├─▶ UI 优化没有银弹，只有场景边界
   合成器属性 → transform 比 left/top 快 10×         ─┘
```

> **心法**：**治理前先做实验**——这就是"方法派比经验派快"的本质。贯穿案例方法派 Day 5 用 Macrobenchmark 验证所有改动，经验派 4 周全凭直觉。

### 5.1 一层静态减负

**核心命题**：**减少产帧成本**——减节点 + 延 Inflate + 缩重绘。

**5.1.1 减节点：四种手法**

| 手法 | 适用场景 | 示例 |
|---|---|---|
| **删除** | 冗余容器 / 装饰 View | 移除无用的 FrameLayout 包裹 |
| **合并** | 相同角色子树 | `<merge>` 合并到父布局 |
| **扁平化** | 嵌套 ≥ 4 层 | 换 ConstraintLayout |
| **延迟** | 二级内容 | ViewStub / View.GONE 延迟 inflate |

**删除**：

```xml
<!-- ❌ 反例：冗余 FrameLayout 包裹 -->
<FrameLayout>
    <TextView android:text="Hello" />
</FrameLayout>

<!-- ✅ 正例：直接用 TextView -->
<TextView android:text="Hello" />
```

**合并**：

```xml
<!-- ❌ 反例：根 LinearLayout 嵌 LinearLayout -->
<LinearLayout>
    <LinearLayout>
        <TextView />
        <TextView />
    </LinearLayout>
</LinearLayout>

<!-- ✅ 正例：<merge> 合并 -->
<merge>  <!-- 作为 include 的子布局 -->
    <TextView />
    <TextView />
</merge>
```

**扁平化**（≥ 4 层才换 CL）：

```xml
<!-- ✅ 嵌套 5 层 LinearLayout → ConstraintLayout -->
<androidx.constraintlayout.widget.ConstraintLayout>
    <ImageView android:id="@+id/avatar" app:layout_constraintStart_toStartOf="parent" />
    <TextView android:id="@+id/name" app:layout_constraintStart_toEndOf="@id/avatar" />
    <TextView android:id="@+id/time" app:layout_constraintTop_toBottomOf="@id/name" />
</androidx.constraintlayout.widget.ConstraintLayout>
```

**延迟**（ViewStub）：

```xml
<!-- ✅ 二级内容用 ViewStub -->
<ViewStub
    android:id="@+id/stub_recommend"
    android:layout="@layout/view_recommend"
    android:layout_width="match_parent"
    android:layout_height="wrap_content" />

<!-- Kotlin 中按需 inflate -->
findViewById<ViewStub>(R.id.stub_recommend).inflate()
```

**5.1.2 延 Inflate：异步 Inflate**

```kotlin
// AsyncLayoutInflater（仅适用 > 50 节点的复杂布局）
AsyncLayoutInflater(this).inflate(R.layout.comment_item, parent) { view, _, _ ->
    parent.addView(view)
}

// 更现代：预 Inflate 池
class LayoutPreCreator {
    private val cache = ConcurrentHashMap<Int, View>()
    
    fun preInflate(ctx: Context, resId: Int) {
        thread { cache[resId] = LayoutInflater.from(ctx).inflate(resId, null) }
    }
    
    fun get(resId: Int, inflater: LayoutInflater, parent: ViewGroup?): View {
        return cache.remove(resId) ?: inflater.inflate(resId, parent, false)
    }
}
```

**▶▶ 使用边界**（见实验二）：**只对 > 50 节点的复杂布局用**，简单 cell 异步后反而负收益。

**5.1.3 缩重绘：局部 invalidate**

```kotlin
// ❌ 反例：全量 invalidate
view.invalidate()

// ✅ 正例：局部 invalidate（仅动画区域）
view.invalidate(animRect.left, animRect.top, animRect.right, animRect.bottom)
```

**5.1.4 过度绘制消除**

```xml
<!-- ❌ 反例：多层背景色重叠 -->
<FrameLayout android:background="@color/white">
    <LinearLayout android:background="@color/white">  <!-- 冗余 -->
        <TextView android:background="@color/white" />  <!-- 冗余 -->
    </LinearLayout>
</FrameLayout>

<!-- ✅ 正例：只给根布局背景 -->
<FrameLayout android:background="@color/white">
    <LinearLayout>
        <TextView />
    </LinearLayout>
</FrameLayout>
```

**检测**：开发者选项 → 开启"调试 GPU 过度绘制"，**蓝色（1x）正常、绿色（2x）警告、浅红（3x）严重、深红（4x）必治**。

**5.1.5 复杂 Shader 位图化**

```kotlin
// ❌ 反例：onDraw 中实时绘制圆角 + 阴影 + 模糊
override fun onDraw(canvas: Canvas) {
    val paint = Paint().apply {
        setShadowLayer(10f, 0f, 5f, Color.GRAY)
        maskFilter = BlurMaskFilter(5f, BlurMaskFilter.Blur.NORMAL)
    }
    canvas.drawRoundRect(..., paint)
}

// ✅ 正例：首次绘制到 bitmap，后续直接贴图
private var cachedBitmap: Bitmap? = null
override fun onDraw(canvas: Canvas) {
    if (cachedBitmap == null) cachedBitmap = createCachedBitmap()
    canvas.drawBitmap(cachedBitmap!!, 0f, 0f, null)
}
```

### 5.2 二层动态流畅

**核心命题**：**让动画走合成器 + 让高频输入不打扰主线程**。

**5.2.1 合成器加速（核心）**

```kotlin
// ❌ 反例：left/top 属性动画（走完整渲染流水线）
val animator = ObjectAnimator.ofFloat(view, "translationX", 0f, 100f).apply {
    duration = 300
    start()
}
// 其实 translationX 已经是合成器属性 ✓

// ❌ 更坏：直接改 layout params
val lp = view.layoutParams as MarginLayoutParams
lp.leftMargin = 100
view.layoutParams = lp  // 触发 requestLayout → 走完整流水线
```

**合成器白名单**（跨平台）：

| 平台 | 合成器属性 | 非合成器（避免） |
|---|---|---|
| Android | translationX/Y、scaleX/Y、rotation、alpha | left/top、width/height、margin |
| iOS | transform、opacity | frame、bounds |
| Web | transform、opacity、filter | top/left、width/height |

**5.2.2 硬件图层（场景化开启）**

```kotlin
// ✅ 动画开始时启动 HARDWARE 图层，结束时关
view.setLayerType(View.LAYER_TYPE_HARDWARE, null)
animator.addListener(onEnd = {
    view.setLayerType(View.LAYER_TYPE_NONE, null)  // 关闭释放显存
})
animator.start()
```

**▶▶ 禁忌**：
- **不要给静态 View 开 HARDWARE**（白吃显存）；
- **不要给大图层开 HARDWARE**（> 2048×2048 可能超 GPU 纹理上限）；
- **结束必须关闭**（否则显存泄漏）。

**5.2.3 消除强制同步布局**

```kotlin
// ❌ 反例：动画中触发 requestLayout
animator.addUpdateListener { 
    textView.text = "progress: ${it.animatedValue}%"  // 字体变化 → requestLayout → 卡
}

// ✅ 正例：动画中只改 transform，不改尺寸
animator.addUpdateListener {
    view.translationX = it.animatedValue as Float  // 不触发 layout
}
```

**5.2.4 高频输入（滚动/手势）**

```kotlin
// ✅ 节流：高频滚动事件合并
private var lastScrollTime = 0L
recyclerView.addOnScrollListener(object : RecyclerView.OnScrollListener() {
    override fun onScrolled(rv: RecyclerView, dx: Int, dy: Int) {
        val now = SystemClock.elapsedRealtime()
        if (now - lastScrollTime > 16) {  // 节流到 60fps
            handleScroll(dy)
            lastScrollTime = now
        }
    }
})
```

### 5.3 三层响应感知

**核心命题**：**让"首次反馈 < 100ms"**（Doherty 黄金线）。

**5.3.1 响应前置：乐观 UI**

```kotlin
// ❌ 反例：等业务完成才反馈
button.setOnClickListener {

}
```

**5.3.2 占位态 / Skeleton**

```kotlin
    recyclerView.adapter = RealAdapter(data)  // 数据到了再切换
```

**5.3.3 业务拆解异步**

```kotlin

button.setOnClickListener {
    checkInventory()       // 80ms
    updateCart()            // 60ms
    reportAnalytics()       // 40ms
    refreshBadge()          // 100ms
}

// ✅ 正例：拆成 "必须同步" + "可异步"
```

### 5.5 预防治理：左移到开发期

**5.5.1 Lint 规则**

- `NestedTooDeep`：XML 嵌套 ≥ 6 层 → 警告；
- `UselessParent`：冗余 ViewGroup 包裹 → 警告；
- `OverdrawInBackground`：子 View 重复设置背景 → 警告；
- `LeftTopAnimation`：动画中使用 left/top → 警告（改 transform）；
- `SyncInflateInRecyclerView`：onCreateViewHolder 内复杂 inflate → 建议异步。

**5.5.2 CI Macrobenchmark 卡口**

**阻断规则**：

- 列表 FPS P5 < 50 → 警告；
- 过度绘制 > 3 层 → 阻断。

**5.5.3 Code Review 清单**

- 新增 XML 嵌套 ≤ 5 层；

### 5.7 面试锚点

**Q：讲一个你亲手做过的 UI 优化案例，要有完整方法论闭环。**

**答题模板**（STAR + 三阶段 + 决策树 + 分层治理 + 实验数据）：

> **S（场景）**：某新闻 App V6.8 重构详情页（产品要求"功能更丰富"），上线后——**详情页打开 P95 1.8s**（之前 0.6s）、**评论列表 FPS 22**（之前 56）、**单 cell 创建 580ms**、**DAU 流失 6%**、**阅读完成率 -15%**，高层强力施压"必须立刻恢复"。
>
> **T（任务）**：6 天内恢复到基线以上。
>
> **A（动作）**，严格按方法论：
>
> **① 三方案组合定位**（Day 1）：FrameMetrics 拿到详情页首帧 LAYOUT=520ms + Inflate=380ms + Draw 每帧 22ms；Choreographer FPS P99=110ms；节点级计时精确到"评论 cell 6 层 RelativeLayout"是瓶颈。
>
> **② 决策树归因**（Day 2）：
> - 首屏慢 → C 分支（Inflate 慢）→ 9 层根布局 + 全量同步 inflate；
> - 滚动卡 → A 分支（Layout 慢）→ 6 层 cell + RL 双测量 + 动态高度；
> - 局部抖 → B 分支（Draw 慢）→ 评论头像 + 表情 SVG 实时解析。
>
> **③ 四层治理落地**（Day 3-4）：
> - **一层静态减负**（§5.1）：根布局 9→4 层扁平化；cell 6→2 层 CL；相关推荐 ViewStub 延迟；SVG → WebP；固定背景 setLayerType；局部 invalidate(Rect)；
> - **四层列表专项**（§5.4）：onBindViewHolder 减负（图加载/格式化全异步）；prefetchDataSource 提前测量。
>
> **④ 求证实验**（Day 5）：Macrobenchmark mock 数据跑前后对比——CL 替代仅在 ≥4 层生效（实验一印证）、ViewStub 让首屏 -30%、SVG → WebP 让 Draw -60%。
>
> **R（结果）**：详情页 P95 **1.8s → 0.55s**（-69%）；评论列表 FPS **22 → 58**；单 cell 创建 **580ms → 80ms**；内存峰值 **380MB → 220MB**；DAU 流失 **-6% → +1%**（恢复）；阅读完成率 **-15% → +3%**。

## 06.原理深潜

> 本章面向资深工程师——知其所以然。理解这些机制，才能应对任何陌生 UI 性能问题。

### 6.1 Inflate 全链路

```
   setContentView(R.layout.xxx)
       ↓
   LayoutInflater.inflate()
       ↓
   XmlResourceParser 解析 XML
       ↓ for each element
   ① createViewFromTag                ← 反射创建 View
       ├─ Class.forName(name)         ← 耗时（第一次 ~5-10ms）
       └─ Constructor.newInstance()   ← 耗时（~1-3ms）
       ↓
   ② 解析 AttributeSet                ← 读 attr 数值 / 引用 drawable
       ↓
   ③ generateLayoutParams              ← LayoutParams 实例化
       ↓
   ④ addView 到 parent                 ← 建立父子关系
       ↓
   recurse into children               ← 递归
```

**▶▶ 性能瓶颈**：
- **反射开销**：每个 View 的 `Class.forName + newInstance` 累计 2-5ms；
- **XML 解析**：复杂 XML 解析本身 5-20ms；
- **资源加载**：drawable / dimen 的 `Resources.getXxx` 累计 10-50ms。

**▶▶ 优化手段**：
- **预加载 Class**：通过 `Class.forName` 预热常用 View；
- **异步 Inflate**：`AsyncLayoutInflater`（> 50 节点场景）；
- **代码写 View**：绕过 XML 解析（Compose 的方向）；
- **Precompiled XML**：R8/ProGuard 的 resource shrinking。

### 6.2 Layout 全链路

```
   ViewRootImpl.performTraversals()
       ↓
   performMeasure
       └─ view.measure(widthSpec, heightSpec)
             ├─ onMeasure
             │    ├─ ViewGroup 遍历 child measure
             │    └─ 自身测量
             └─ setMeasuredDimension
       ↓
   performLayout
       └─ view.layout(l, t, r, b)
             ├─ onLayout
             └─ 设置子 View 位置
       ↓
   performDraw
       └─ (下节 §6.3)
```

**▶▶ RelativeLayout 的双测量问题**：
RL 的子 View 定位可能依赖其他子 View（例如 toRightOf），所以 **RL 的 onMeasure 要跑两遍 child measure**——这是为什么 RL 比 LL/CL 慢的根本原因。

**▶▶ ConstraintLayout 的约束求解**：
CL 内部跑 Cassowary 线性约束求解器——求解本身开销比 LL 大 2-3×，但省掉了嵌套层级的递归。所以 **CL 仅在深嵌套时才赢**。

**▶▶ Compose Layout 的差异**：
Compose 的 Layout 只跑一遍（child measure 返回 size + placeable），**天生没有双测量问题**——这是 Compose 布局性能的一个关键优势。

### 6.3 Draw 全链路

```
   ViewRootImpl.performDraw
       ↓
   mAttachInfo.mThreadedRenderer.draw()  ← 硬件加速路径
       ↓
   buildDrawingCommands                   ← 遍历 View 树构建 DisplayList
       └─ view.draw(canvas) 
             ├─ onDraw                    ← 开发者代码
             ├─ dispatchDraw              ← 分发到子 View
             └─ onDrawForeground          ← 前景装饰
       ↓ Sync 到 RenderThread
   RenderThread 消费 DisplayList
       ↓
   GPU 指令生成（OpenGL / Vulkan）
       ↓
   SurfaceFlinger 合成
       ↓
   显示器 Vsync 上屏
```

**▶▶ 过度绘制的物理成因**：
GPU 对每个像素做"覆盖写"——同一像素被绘制 N 次就累加 N 次开销。多层半透明背景堆叠 = 像素被重复写 N 次 = 过度绘制。

**▶▶ 复杂 Shader 的开销**：
`setShadowLayer / BlurMaskFilter / ColorMatrixColorFilter` 这些效果需要**像素级计算**（高斯模糊可能遍历每个像素周围 25-100 个点）——同一效果可能让 Draw 耗时增加 10×。

### 6.4 RecyclerView 复用全链路

```
   RecyclerView.onLayout
       ↓
   LayoutManager.onLayoutChildren
       ↓
   getViewForPosition(pos)
       ↓
   ┌─ Scrap Pool（当前屏幕外的 ViewHolder） ← 优先取
   ├─ Cache Pool（最近滚出屏幕）             ← 其次
   └─ RecycledViewPool（已 recycled 的）     ← 最后
       ↓ 都没有
   onCreateViewHolder                       ← 真实创建
       ↓
   onBindViewHolder                         ← ★ 绑定数据
       ↓
   addView
       ↓
   measure + layout
```

**▶▶ 复用机制的性能本质**：
- **Scrap**：当前 Layout 还未完成，暂存的 ViewHolder，几乎零成本；
- **Cache**：刚滚出屏幕的 ViewHolder，数据可能仍有效，不需要重新 bind；
- **RecycledViewPool**：真正复用池，需要 onBindViewHolder 重新绑定数据。

**▶▶ 典型瓶颈**：
- **onBindViewHolder 做了 IO**（同步图片解码）→ 必卡；
- **PrefetchDataSource 没开**（API 21+ 默认开）→ 空闲时不预取；
- **过度 notifyDataSetChanged**（全量刷新）→ 用 DiffUtil / AsyncListDiffer 替代。

### 6.5 Compose 渲染全链路

```
   @Composable 函数树
       ↓
   Composition（首次运行所有 @Composable）
       ↓
   SlotTable（存储 UI 状态）
       ↓ 状态变化时
   Recomposition（只重跑受影响的子树）
       ↓
   LayoutNode 树构建
       ↓
   Measure Policy（Compose 的 Layout）
       ├─ 子节点 measure → 返回 Placeable
       └─ 父节点 Placeable.place
       ↓
   Draw Scope（Compose 的 Draw）
       ↓
   和传统 View 共享 RenderThread
```

**▶▶ Compose 性能优势**：
- **Layout 单次测量**（无 RL 双测量）；
- **智能跳过**：没变的 @Composable 自动跳过 recomposition；
- **结构相等优化**：`remember { }` + `derivedStateOf { }` 可精细控制重组范围。

**▶▶ Compose 性能陷阱**：
- **不稳定参数**：传 lambda 可能触发无谓 recomposition；
- **过度 recomposition**：没用 `remember` 的计算每次都跑；
- **大列表**：没用 `LazyColumn` 的 keys 导致 bind 乱。

### 6.6 输入事件全链路

```
   硬件（触摸屏/鼠标）
       ↓ 中断
   Linux kernel driver
       ↓
   /dev/input/event0 → InputReader 线程
       ↓
   InputDispatcher 线程
       ↓ socket
   App 进程的 InputChannel
       ↓
   Choreographer 调度到主线程 Looper
       ↓
   ViewRootImpl.dispatchInputEvent
       ↓
   ViewGroup.dispatchTouchEvent（递归）
       ↓
   View.onTouchEvent / onClickListener
```

**▶▶ 性能关键点**：
- **主线程阻塞 = 事件堆积**：Looper 卡住 → 事件队列堆积 → 响应延迟；
- **Choreographer 优先级**：Input 事件 和 Vsync 同一个优先队列；
- **ANR 的时序源头**：Input 事件 5s 未响应 → ANR（见 §06 ANR 篇）。

### 6.7 动画驱动与合成器

**三种动画驱动方式**：

| 驱动方式 | 代表 API | 性能 | 适用 |
|---|---|---|---|
| **CPU 属性动画** | ObjectAnimator (translation/alpha) | 高 | 简单变换 |
| **GPU 合成器** | setLayerType HARDWARE | 极高 | 复杂动画 |
| **帧动画** | ValueAnimator + onFrame | 中 | 需要业务计算 |

**▶▶ 合成器属性 vs 非合成器属性**（见实验四）：

合成器属性（translation/scale/rotation/opacity）**只影响 Composite 阶段**，不走 Layout/Draw——相当于只告诉 GPU "把这个 layer 挪到 (100, 100)"，不需要重新绘制。

非合成器属性（left/top/width/margin）**触发 requestLayout**，走完整渲染流水线——每帧都要 measure + layout + draw + composite，开销 10×。

### 6.8 iOS / Web / 跨端对照

**▶▶ iOS 渲染链路**：

```
   UIView.setNeedsLayout
       ↓ RunLoop
   layoutSubviews（Autolayout 约束求解）
       ↓
   Core Animation Layer tree
       ↓
   Render Server（独立进程）
       ↓ GPU
   显示器
```

**特点**：
- **分进程架构**：Render Server 独立进程，天然多核；
- **Core Animation**：转换/透明度/位置都是 GPU 加速；
- **Autolayout 约束求解**：类似 CL 的 Cassowary。

**▶▶ Web 渲染链路**：

```
   HTML/CSS/JS 修改
       ↓
   DOM Tree + CSSOM Tree
       ↓
   Render Tree 构建
       ↓
   Layout / Reflow（布局）
       ↓
   Paint（光栅化）
       ↓
   Composite（层合成）
       ↓
   GPU
```

**特点**：
- **CSS transform/opacity 自动走合成器**；
- **top/left 触发 reflow**（避免）；
- **will-change** 提示浏览器预升层。

**▶▶ 跨端框架**：

| 框架 | 渲染方式 | 性能特点 |
|---|---|---|
| React Native | 原生组件 + JS Bridge | 桥接开销是瓶颈 |
| Flutter | 自绘 + Skia | 跨平台一致，但首次 Draw 开销大 |
| 微信小程序 | WebView + 原生渲染层 | 混合，取决于具体组件 |

## 07.面试高频追问

### Q1 ConstraintLayout 一定比嵌套 LinearLayout 快吗

**问**：教科书说"用 CL 替代嵌套 LL 优化性能"，总是对吗？

**答**：**不总是**——取决于嵌套层级。见 §5.0 实验一：
- 1-2 层：CL **慢 65%**（Cassowary 求解开销）；
- 3 层：持平；
- 4 层：CL 快 55%；
- 5 层：CL 快 71%。

**CL 优势来自"扁平化省掉的递归 measure"，不是 CL 本身**。盲目把所有 LL 改 CL 是贯穿案例第 1 周翻车的典型——简单 cell 反而慢 10%。

### Q2 异步 Inflate 什么时候用

**问**：AsyncLayoutInflater 是不是无脑开最快？

**答**：**不是**——仅适用 > 50 节点的复杂布局。见 §5.0 实验二：
- 简单 cell（< 10 节点）：异步后**慢 87%**（线程切换 + Attach 闪烁）；
- 复杂（> 50 节点）：异步后 **+67% 收益**。

**边界**：**布局自身 Inflate > 50ms 才用**。而且异步 Inflate 的 context 只能用 Application（不能用 Activity），不能有依赖 Activity theme 的 drawable。

### Q3 setLayerType HARDWARE 的坑

**问**：setLayerType(LAYER_TYPE_HARDWARE) 是不是能加速所有动画？

**答**：**不是**——是**用显存换时间**：
- 一个 1080p 全屏 layer 吃约 **8MB 显存**；
- 低端机 GPU 内存通常 128-256MB，开 20-30 个 layer 就 OOM；
- 贯穿案例第 3 周滥用，GPU 内存 +80MB，低端机 OOM 率 +5×。

**正确用法**：
1. **动画开始前开，结束立刻关**（否则显存泄漏）；
2. **只给"高频重绘 + 内容稳定"的 View 开**；
3. **不要给大图层开**（> 2048×2048 可能超 GPU 纹理上限）。

### Q4 为什么 transform 比 left/top 快 10 倍

**问**：都是让 View 移动，为什么 transform 性能完全不同？

**答**：**走的渲染路径完全不同**：
- **left/top**：触发 `requestLayout`，走完整流水线（measure + layout + draw + composite），每帧 10-20ms；
- **transform (translation)**：只影响 Composite 阶段，相当于告诉 GPU "把这个 layer 平移"，每帧 1-2ms。

**本质**：**transform 是合成器属性，GPU 原生支持；left/top 是布局属性，需要 CPU 重新计算所有子 View 位置**。见 §5.0 实验四——transform 比 left/top 快 10×，耗电只 1/2。

### Q5 FPS 60 但用户说卡

**问**：所有指标都对，用户为什么还抱怨？

**答**：**均值骗人，分布不骗人**。几种可能：
1. **FPS 均值 60 但 P99 帧时长 200ms**（偶发大卡顿）→ 用户肉眼可感 → 看 P99 不看均值；
2. **首次反馈 > 100ms**（Doherty 阈值）→ 哪怕后续 60fps，前 100ms 已经"崩塌"；
3. **动画整体丝滑但点击响应慢** → 响应和动画要分开看。

**正确监控**：**FPS 均值 + P99 帧时长 + 响应 P95 + 大卡顿率** 四件套。

### Q6 RecyclerView 卡的最常见原因

**问**：RecyclerView 滚动卡顿，最常见原因是什么？

**答**：**90% 是 onBindViewHolder 做了重活**：
1. **图片同步解码**（没用 Glide/Fresco 异步）；
2. **文本重格式化**（SimpleDateFormat / String.format 每次 bind 都跑）；
3. **复杂数据处理**（JSON 解析 / 对象转换）；
4. **View 层级深 + bind 中 setVisibility 触发 requestLayout**。

**正解**：
- 图加载 → Glide/Fresco；
- 格式化 → 预处理（在数据加载时就格式化好）；
- bind 只做"赋值"，不做"计算"；
- 单 cell bind < 5ms 是基线。

### Q7 Compose 的性能比传统 View 好吗

**问**：Compose 性能是不是全面碾压传统 View？

**答**：**不是全面碾压，是各有千秋**：

| 维度 | 传统 View | Compose |
|---|---|---|
| 首次 Inflate | XML 解析 + 反射 ~ 50-200ms | 直接代码执行 ~ 30-100ms |
| **布局** | 可能双测量（RL） | **单次测量 ✓** |
| **recomposition** | 全量 invalidate | **智能跳过 ✓** |
| 冷启动 | 快 | 慢（JIT 预热） |
| 包体积 | 小 | +2-5MB |
| 调试工具 | 成熟 | 较弱 |

**结论**：**Compose 在"复杂动态 UI"上性能更好**（recomposition 跳过），但**冷启动和包体积有代价**。Baseline Profile 可以缓解冷启动问题。

### Q8 为什么 Doherty 阈值是 100ms

**问**：100ms 是经验值还是物理值？

**答**：**是人类工程学的物理值**：
- **视觉皮层处理延迟**：约 50ms；
- **决策阈限**（看到 → 判断"有响应"）：约 50ms；
- **叠加 100ms** 是"感知即时"的硬线；
- **超 100ms** 大脑启动"等待"模式，体验崩塌（见 §5.0 实验三）。

1982 年 IBM 研究员 Doherty 在工程学研究中验证——**超过 100ms 用户主观评分每 100ms 掉 0.7 分**。

### Q9 过度绘制怎么治

**问**：开发者选项显示红色过度绘制，怎么治？

**答**：
1. **消除冗余背景**：子 View 和父 View 都设白色背景 → 删子 View 的；
2. **window background**：如果 Activity 已有 window background，布局根 View 不要再设 → `android:windowBackground` 用一次就够；
3. **clipRect 优化**：onDraw 中用 `canvas.clipRect` 限制绘制范围；
4. **滚动场景**：ScrollView 内 View 可能被滚出屏幕外还在 draw → 用 RecyclerView 替代。

**基线**：全屏蓝色（1x）正常、绿色（2x）可接受、浅红（3x）警告、深红（4x+）必治。

### Q10 ViewStub 和 include 区别

**问**：ViewStub 和 include 都能复用布局，有什么区别？

**答**：
- **`<include>`**：**立刻 Inflate**，就是把子布局内容"粘贴"进来，开销和写在当前文件一样；
- **ViewStub**：**延迟 Inflate**，Inflate 时只占一个空壳，调用 `stub.inflate()` 才真正创建。

**使用边界**：
- 一级必须显示的内容 → `<include>`；
- 二级可能用到的内容 → `ViewStub`（相关推荐 / 评论区 / 错误态）。

**▶▶ 坑**：ViewStub 只能 inflate 一次，第二次调会抛异常——需要用 `View.VISIBLE` 控制。

### Q11 高刷屏 120Hz 影响什么

**问**：高刷屏对性能优化有什么新挑战？

**答**：**每帧预算从 16.67ms 砍到 8.33ms**——对 CPU/GPU 是降维打击：
- 原本 10ms 的帧 60Hz 下丢 1 帧（显示器刷新间隔 16.67ms），120Hz 下丢 2 帧（刷新间隔 8.33ms）；
- 需要**更激进的减负**：onDraw < 5ms、Layout < 3ms；
- **动画必须走合成器**（CPU 完全来不及）；
- **功耗代价**：120Hz 比 60Hz 耗电多 15-30%，需要动态刷新率策略（ARR）。

### Q12 为什么动画要走合成器

**问**：合成器加速到底是什么魔法？

**答**：**合成器加速不是魔法，是硬件分工**：
- **CPU 阶段**：Measure / Layout / Draw → 画出每一帧的"图层"（Bitmap）；
- **GPU 阶段**：Composite → 把多个图层按位置叠在一起上屏；
- **合成器属性（transform/opacity）**：只告诉 GPU "把这个图层挪一下"，不需要 CPU 重画 → 跳过 Measure/Layout/Draw 三大阶段；
- **非合成器属性（left/top）**：改变图层本身大小/位置 → 必须 CPU 重画 → 走完整流水线。

**本质**：**让 GPU 的"硬件天赋"（图层叠加）发挥，不要让 CPU 做 GPU 擅长的事**。

### Q13 UI 优化的 ROI 排序

**问**：UI 优化那么多手段，优先做什么？

**答**：按 §5.6 的 ROI 矩阵：

**P0（极高 ROI，先做）**：
1. 消除过度绘制（1-2 天，Draw -40%）；
2. 响应前置 + skeleton（1 周，响应 P95 -75%）；
3. left/top → transform（3-5 天，动画 P99 -90%）；
4. onBindViewHolder 减负（1 周，FPS +20）。

**P1（高 ROI）**：
5. 层级 ≥ 5 的扁平化（1-2 周，Layout -50%）；
6. ViewStub 延 Inflate（1 周，首屏 -30%）。

**P2（中 ROI）**：复杂 Shader 位图化 / 异步 Inflate / setLayerType。

**P3（低 ROI 或负收益）**：无脑 CL 替代 LL / 无脑异步 Inflate / 全局 setLayerType。

**铁律**：**P0 没做完不要碰 P3**。

## 08.模拟面试模板

### 8.1 UI 性能整体理解

**问**：谈谈你对 UI 性能优化的整体理解？

**答**：

> UI 性能的本质是"**在 16.67ms 帧预算内完成产帧**"——所有现象（白屏/卡顿/响应慢/抖动）都是产帧成本超预算的不同时间切面。
>
> 我的理解框架是"**静态+动态双切面 + 三阶段成本 + Doherty 基线**"：
>
> **① 静态 UI 与动态交互是同一流水线**：
> - 静态：首次 Inflate + 全树 Layout + 全屏 Draw → 一次性成本；
> - 动态：每帧 Input → Layout → Compose → Display → 持续成本；
> - 共享主线程 + 渲染流水线，所以**静态是地基，动态是时间轴延伸**。
>
> **② 三阶段成本模型**：
> $$单帧成本 = Inflate(首次) + Layout \times N + Draw \times M$$
> - Layout per 帧：5-50ms × 60fps = **300-3000ms/秒**（最高优先级）；
> - Draw per 帧：1-20ms × 60fps = 60-1200ms/秒；
> - Inflate：50-500ms × 1 次（首屏关键）。
>
> **③ Doherty 感知基线**：
> - **100ms**：用户感知"即时"的物理硬线（视觉 50ms + 决策 50ms）；
> - **16.67ms**：60fps 单帧预算；
> - 用户感受看 **P99 帧时长**，不看均值。
>
> **④ 核心命题**：**UI 优化没有银弹**——ConstraintLayout 不是万能、异步 Inflate 不是万能、setLayerType 不是万能，每个"经验招"都有场景边界，**数据驱动按场景选择**。

### 8.2 布局与渲染优化

**问**：布局和渲染怎么优化？

**答**：

> 按**三阶段成本公式**对症下药：
>
> **① 治 Layout（最高优先级）**：
> - **减节点**：删冗余容器 + `<merge>` 合并 + ConstraintLayout 扁平化（≥ 4 层才用）+ ViewStub 延迟二级内容；
> - **换 LayoutManager**：RelativeLayout → ConstraintLayout（避免双测量）；
> - **自定义测量缓存**：复杂 onMeasure 结果缓存。
>
> **② 治 Draw**：
> - **消除过度绘制**：删冗余背景 + windowBackground 用一次；
> - **局部 invalidate(Rect)**：只重绘变化区域；
> - **复杂 Shader 位图化**：首次绘制到 bitmap，后续贴图。
>
> **③ 治 Inflate**：
> - **AsyncLayoutInflater**：仅 > 50 节点的复杂布局；
> - **预 Inflate 池**：热门 cell 提前创建；
> - **代码写 View**：绕过 XML 解析（或用 Compose）。
>
> **核心原则**：**每个手段都有场景边界**——CL 仅 ≥ 4 层才赢（实验一）、异步 Inflate 仅 > 50 节点才赢（实验二）、setLayerType 必须开关配对（否则显存泄漏）。

### 8.3 动画与交互治理

**问**：动画抖动、点击响应慢怎么治？

**答**：

> 两类问题分开治：
>
> **① 动画抖动（E 分支）**：
> - **根因 70% 是非合成器属性** → left/top/width/height 改成 **transform/opacity**（§5.0 实验四 快 10 倍）；
> - **动画中触发 setState / requestLayout** → 分离动画值和业务 setState；
> - **消除强制同步布局** → 动画 updateListener 中不改字体/尺寸。
>
> **② 响应延迟（D 分支）**：
> - **根因 90% 是业务逻辑过重**（T_dispatch → T_layout 慢）→ 用 **4 段埋点**精准定位；
> - **响应前置**：点击立刻给视觉反馈（按下态 + skeleton），业务异步；
> - **Doherty 100ms** 是用户感知硬线，**首次反馈必须 < 100ms**；
> - **业务拆解**：必须同步的最小化（UI 相关），其他全异步（IO/埋点/刷新）。
>
> **副案例实证**：电商加购响应 P95 380ms → 45ms，关键是三步——点击按下态立刻可见（<16ms）+ 库存检查异步（IO）+ 飞入动画用 transform（合成器）。

### 8.4 列表与声明式 UI

**问**：RecyclerView 滚动卡怎么治？Compose 性能如何？

**答**：

> **RecyclerView 优化四板斧**：
>
> 1. **onBindViewHolder 减负**：bind 只做"赋值"，不做"计算/IO"——图加载用 Glide 异步、文本预格式化、复杂数据预处理；
> 2. **PrefetchDataSource**：API 21+ 默认开，低端机可调 `initialPrefetchItemCount`；
> 3. **DiffUtil / AsyncListDiffer**：避免 `notifyDataSetChanged` 全量刷新，大列表用 AsyncListDiffer 后台 diff；
> 4. **setHasFixedSize + 固定高度**（仅 cell 高度不变时用）。
>
> **Compose 性能特点**：
> - **优势**：Layout 单次测量（无 RL 双测量）、智能跳过（没变的 @Composable 不 recompose）、代码更简洁；
> - **代价**：冷启动稍慢（JIT 预热）、包体积 +2-5MB；
> - **陷阱**：传 lambda 可能触发无谓 recomposition、没用 `remember` 的计算每次都跑；
> - **优化**：Baseline Profile 缓解冷启动、`derivedStateOf` 精细控制重组、`LazyColumn` 用 keys。

### 8.5 优化故事线

**问**：讲一个你亲手做过的完整 UI 优化案例？

**答**：

> **背景**：某头部新闻 App V6.8 重构详情页（产品要求"功能更丰富"），上线后——**详情页打开 P95 1.8s**（之前 0.6s）、**评论列表 FPS 22**（之前 56）、**单 cell 创建 580ms**、**DAU 流失 6%**、**阅读完成率 -15%**，公司高层强力施压"必须立刻恢复"。4 周经验派全无效甚至反向。
>
> **归因**（Day 1-2）：
> - **三方案组合定位**：FrameMetrics 拿到详情页首帧 LAYOUT=520ms + Inflate=380ms + Draw 每帧 22ms；Choreographer FPS P99=110ms；节点级计时精确到"评论 cell 6 层 RelativeLayout"是瓶颈；
> - **决策树归因**：首屏慢 → C 分支（9 层根布局 + 全量 inflate）；滚动卡 → A 分支（6 层 cell + RL 双测量）；局部抖 → B 分支（SVG 实时解析）。
>
> **方案**（Day 3-4）：按**四层治理**：
> - **一层静态减负**：根布局 9→4 层扁平化；cell 6→2 层 CL；相关推荐 ViewStub 延迟；SVG → WebP；固定背景 setLayerType；局部 invalidate(Rect)；
> - **四层列表专项**：onBindViewHolder 减负（图加载/格式化全异步）；prefetchDataSource 提前测量。
>
> **求证**（Day 5）：Macrobenchmark 跑前后对比——印证 **CL 仅 ≥4 层才赢**（实验一），其他改动数据全部达标。
>
> **结果**：详情页 P95 **1.8s → 0.55s**（-69%）；FPS **22 → 58**；单 cell 创建 **580ms → 80ms**；内存峰值 **380MB → 220MB**；DAU 流失 **-6% → +1%**（恢复）；阅读完成率 **-15% → +3%**。
>
> **复盘**：经验派 4 周错在"**无场景的经验招**"——"CL 全改"（简单 cell 慢 10%）+"异步 Inflate 全开"（简单 cell 反向负收益）+"setLayerType 全开"（GPU 内存 +80MB）+"固定高度"（内容显示不全）。方法派 6 天胜在"**三方案定位 + 决策树归因 + 实验求证 + 分层治理**"的完整闭环。**UI 优化没有银弹，只有场景边界**——这就是方法论的全部价值。
