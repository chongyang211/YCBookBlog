# Web 性能优化实践

> 性能不是优化出来的，是体系守护出来的——本专栏共 10 篇，用 Web 平台的机制与工具讲透"怎么做"：把「资源×时间×流水线」模型翻译成关键渲染路径、合成器、HTTP 协议栈的物理机制，配上 Lighthouse、WebPageTest、Performance API 工具链与 Core Web Vitals 指标体系。

## 二、设计原则：三线融合

10 篇在三个粒度上各用一条组织线索，而非简单拼盘：

- **旅程线定排序**：从"输入 URL"到"长期守护"，篇目顺序即一次页面访问的物理时间轴；
- **指标线定内核**：每篇用 Core Web Vitals（LCP/INP/CLS）与 TTFB/FCP 给出指标归因框架（指标镜头）；
- **闭环线定结构**：每篇按「现象→度量→归因→优化→防劣化」五步展开，篇篇独立可查。

**每篇统一体例（四件套）**：

```text
┌─ ① 旅程坐标 ── 本篇在页面访问旅程哪一站？用户可感症状是什么？
├─ ② 指标镜头 ── 本篇影响哪些 CWV/指标，归因框架挂接「资源×流水线」
├─ ③ 五步闭环 ── 现象→度量→归因→优化→防劣化，每步配 Web 工具与代码
└─ ④ 跨框架对照 ── React/Vue/原生三栏速查 + 移动端 Web 注意点
```

## 四、选题说明

**10 篇构成**：总览 1 篇（作战地图）+ 加载链路 4 篇（网络/渲染路径/资源/图片字体）+ 执行与渲染 2 篇（脚本/合成层）+ 复用与架构 2 篇（缓存/框架）+ 收官 1 篇（度量与防劣化），覆盖 Web 性能的全部主干考点。

**机动位**（如需扩展第 11 篇，二选一）：

| 候选篇 | 适合场景 |
|---|---|
| 《Web内存与泄漏治理》 | SPA 长驻应用（单页应用驻留数小时），内存增长与 detached DOM 泄漏高发 |
| 《重计算下沉 WASM》 | 图表/编解码/加密等 CPU 密集场景 |

## 五、篇间分界（防内容重叠）

四处容易写重的边界，明确分工：

| 主题 | 本篇负责 | 邻篇负责 |
|---|---|---|
| **FCP vs LCP** | 渲染路径篇管"白屏结束"（FCP：首屏开始绘制） | 资源加载篇管"主内容就绪"（LCP：最大元素加载完成） |
| **INP 两段** | 脚本篇管"输入延迟+处理延迟"（主线程任务切分） | 渲染篇管"呈现延迟"（重排重绘与合成） |
| **首次传输 vs 回访复用** | 网络篇管"首次请求的协议与链路优化" | 缓存篇管"回访请求的复用与离线" |
| **原生手段 vs 框架放大器** | 各专项篇只讲平台原生手段 | 框架篇统一收口"框架层如何放大/抑制这些手段"（如 React 的懒加载封装） |

## 八、写作排期（非目录顺序）

**先立三根柱子验证体例**，再批量推进：

| 阶段 | 篇目 | 目的 |
|---|---|---|
| 柱子篇 | 1（地图）→ 3（渲染路径）→ 6（脚本执行） | 分别代表"总览型/管线型/执行型"三种最难体例，打磨四件套模板 |
| 批量篇 | 2、4、5、7、8、9 | 模板定型后按旅程顺序推进 |
| 收官篇 | 10 | 体系向内容最后收（指标守护闭环） |

每篇建议体量：正文 700-1000 行；四件套约占 15%（坐标/镜头/对照），五步闭环主体占 85%，其中"归因"与"防劣化"两步不低于一半篇幅——这是与市面"检查清单式"文章的核心差异。
