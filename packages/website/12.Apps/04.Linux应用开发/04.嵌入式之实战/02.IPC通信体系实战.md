## 1. 案例引入

### 1.1 一次线上翻车

一个真实的嵌入式项目里，我们踩过一个非常昂贵的坑。产品结构大致是这样：

```
┌───────────┐     ┌───────────┐     ┌───────────┐
│  sensord  │ ──▶ │  logicd   │ ──▶ │   uid     │
│  采集进程 │     │  业务进程 │     │  界面进程 │
└───────────┘     └───────────┘     └───────────┘
```

一开始三个进程之间用"最简单"的方式打交道：**写文件**。

```bash
# sensord 每秒采集一帧数据，追加写入
echo "$data" >> /tmp/sensor.log
```

```cpp
// logicd 每 100ms tail 一次
std::ifstream in("/tmp/sensor.log");
in.seekg(last_pos);
while (std::getline(in, line)) { process(line); }
last_pos = in.tellg();
```

产品跑了三个月，问题一个接一个冒出来：

1. **数据丢**：`sensord` 崩溃重启期间的采集全丢，`logicd` 完全不知情。
2. **数据脏**：`sensord` 写到一半被杀，`logicd` 读到半行 JSON，反序列化崩掉。
3. **磁盘炸**：`/tmp` 是 tmpfs，占的是内存，几天后 OOM Killer 把整机拉下水。
4. **延迟高**：100ms 轮询，等于给业务永久加了 100ms 延迟。
5. **UI 抖**：`uid` 用同样办法 tail `logicd` 的输出文件，一路轮询下来，触屏点一次要 200ms 才响应。

上线三个月被逼着重构 IPC。这一节想把当初重构过程中反复问自己的那些问题，说清楚。

### 1.2 六种 IPC 排排坐

Linux 提供的 IPC 手段其实就那么几种，问题在于**每一种都在某个场景里是最好的选择，也在另一个场景里是最糟的选择**：

| IPC | 一句话 | 天生擅长 | 天生短板 |
|---|---|---|---|
| pipe / fifo | 内核环形字节流 | 父子进程、日志转发 | 单向、无消息边界 |
| 消息队列 (POSIX/SysV) | 内核带类型的消息盒 | 结构化消息、异步解耦 | 用户态内核态切换、大小受限 |
| 共享内存 shm | 一块两边都能映射的内存 | 大数据高频、低延迟 | 天生不带同步，必配 sem/mutex |
| Unix Domain Socket | 本机的 TCP | 请求-响应、fd 传递 | 需要拆帧、单个连接吞吐一般 |
| D-Bus | 系统级消息总线 | 服务发现、跨进程调用 | daemon 开销、嵌入式常被裁 |
| dma-buf / memfd | 内核托管的匿名内存 | 视频、雷达大数据零拷贝 | API 复杂、调试困难 |

看上去像六件独立工具，实际上它们之间存在**清晰的谱系**：越往下延迟越低、复杂度越高，越往上语义越丰富、代价越高。真正的问题不是"哪个最好"，是"我这条数据链，需要 IPC 保证什么"。

从这个真实翻车案例里，我们至少能提炼出六个必须回答的问题：

① 为什么"文件+轮询"不算 IPC？它到底缺了什么？ → 第 2 章
② 管道、消息队列、共享内存、UDS 到底差在哪？该按什么维度选？ → 第 3、4、5、8 章
③ 共享内存为什么必须配同步？只用一把 mutex 够吗？ → 第 4.2 - 4.3
④ Unix Domain Socket 和 TCP 是同一套 API，为什么大家都爱前者？ → 第 5 章
⑤ D-Bus 到底该不该上？嵌入式常裁掉它，是不是不需要总线？ → 第 6 章
⑥ 高速数据流（视频、雷达）为什么共享内存都嫌慢，非要零拷贝？ → 第 7 章

### 1.3 我们要回答什么

这一篇不做 API 教程，那种资料网上一抓一把。这一篇要回答的是：

- **每种 IPC 的原理边界在哪里**：内核在其中做了什么、没做什么。
- **该如何按业务选**：给出可复用的三维度决策模型。
- **为什么共享内存 + 信号量是嵌入式最常见配对**：以及裸用共享内存的隐患。
- **消息总线要不要自研**：D-Bus 用不起的场景，怎么用不到 1000 行代码搓一个够用的总线。

读完能得到：三张对比表、一份决策树、一段可运行的共享内存 ring buffer、一段 UDS 长连接骨架、一份自研消息总线的最小骨架。

## 2. 架构概览

### 2.1 IPC 的两条主线

Linux 下所有 IPC 手段，脱掉花名之后就两条主线：

```
                     ┌─────────────────────┐
                     │      IPC 世界        │
                     └────────┬────────────┘
                              │
              ┌───────────────┴───────────────┐
              │                               │
      【消息线：有边界】               【共享线：无边界】
              │                               │
      ┌───────┼───────┐               ┌───────┼───────┐
      │       │       │               │       │       │
    pipe    mq/UDS   D-Bus           shm    mmap    dma-buf
   fifo   socket    bus
```

**消息线**：内核帮你维护消息边界。你写多少一次读多少，天然带原子性。代价是每次都要**内核态用户态切换**。

**共享线**：内核只负责给两边"映射一段公共内存"，剩下的（写到哪、什么时候可读、有没有并发）**你自己搞定**。收益是零内核开销，代价是必须自己配同步。

### 2.2 为什么这么分

这个二分不是拍脑袋的，而是被内核实现的边界逼出来的。理解它，能一眼看穿新 IPC 的本质：

**论证 1：数据要不要经过内核？**
消息线必须经过内核 buffer（内核负责入队/出队/边界），所以有 `syscall` 开销；共享线映射完就再也不需要内核，所以延迟能到纳秒级。

**论证 2：谁保证一致性？**
消息线由内核保证"整条消息不撕裂"，多进程写同一 fifo 不会串行冲突；共享线由**你**保证，忘了加锁就会读到写一半的结构体。

**论证 3：语义有多远？**
从"字节流"到"结构化消息"到"命名的服务方法调用"，每往上走一层，语义就更丰富，也就多一层封装/约定。D-Bus 是消息线的顶点，dma-buf 是共享线的极致。

**论证 4：能不能跨进程组？**
pipe 只能亲子进程，fifo/mq/UDS 是有名字的可以跨进程，D-Bus 全系统总线可以跨会话——**"作用域"**是选型时最容易忽视但影响最大的维度。

**结论**：把 IPC 分为**消息线**和**共享线**，是嵌入式选型的心智地基。剩下的所有工具，都是在这两条线上按"作用域 × 语义 × 性能"三维度组合出来的。

## 3. 管道与消息队列

### 3.1 pipe与fifo

**pipe**：一对匿名 fd，只能在有亲缘关系的进程之间（fork 前建立）。**fifo**：pipe 的有名版本，通过 `mkfifo` 创建一个特殊文件，任何知道路径的进程都能打开它。两者内核实现几乎一样，都是内核里的一段环形 buffer。

```c
// pipe：父子共享
int fd[2]; pipe(fd);
if (fork() == 0) { close(fd[1]); read(fd[0], buf, sizeof buf); }
else            { close(fd[0]); write(fd[1], "hi", 2); }

// fifo：陌生进程也能用
mkfifo("/tmp/log.pipe", 0666);
// 进程 A：int fd = open("/tmp/log.pipe", O_WRONLY);
// 进程 B：int fd = open("/tmp/log.pipe", O_RDONLY);
```

pipe/fifo 的关键限制有三条：

1. **半双工**：一个 fifo 只能一个方向，双向需要建两个。
2. **无消息边界**：写 100 字节可能被拆两次读到，你必须自己在协议里带长度。
3. **单个 buffer 有上限**：Linux 默认 64KB（可 `fcntl(F_SETPIPE_SZ)` 调），满了写方会阻塞。

嵌入式里 fifo 最常见的用法是**日志转发**：应用把 log 写进 fifo，一个后台进程从 fifo 读走并落盘/上传。这样应用主逻辑不做磁盘 IO，也不会因为磁盘慢卡死。

### 3.2 内核消息队列

`mq_open / mq_send / mq_receive` 是 POSIX 消息队列，比 fifo 多出来的东西是：

- **保留消息边界**：一次 `send` 就是一条消息，读方要么整条读到，要么读不到。
- **带优先级**：`mq_send(mqd, buf, len, priority)`，`priority` 大的优先出队。
- **可异步通知**：注册 `mq_notify`，队列非空时内核给你发信号或起线程。

代价是：单条消息大小有限（默认 8KB）、队列长度有限（默认 10 条），改大要动 `/proc/sys/fs/mqueue/*`。所以消息队列不适合传大数据，只适合传"事件"、"指令"这类小结构。

```c
struct mq_attr attr = { .mq_maxmsg = 32, .mq_msgsize = 256 };
mqd_t mq = mq_open("/palm.evt", O_CREAT|O_RDWR, 0644, &attr);
mq_send(mq, (char*)&evt, sizeof evt, /*priority*/5);
```

### 3.3 什么时候选管道

**疑惑**：既然消息队列什么都能做，为什么大家还在用 fifo？

**论证**：

1. **fifo 是"文件"**：`ls -l`、`cat`、`echo >` 都能玩，调试极其友好；mq 是内核对象，只能用专用 API 观察。
2. **fifo 天生适合"流"**：日志流、指令行输入，本就是字节流，不需要边界。
3. **mq 的大小限制在嵌入式里很紧**：小结构够用，稍微复杂点就得改 sysctl，运维负担大。

**结论**：**流用 fifo，事件用 mq**。数据是"一条条独立的"（心跳、按键、状态变化）就用 mq；数据是"连续的字节流"（日志、串口透传）就用 fifo。

## 4. 共享内存与同步

### 4.1 shm的高性能真相

共享内存的核心 API 只有三步：

```c
int fd = shm_open("/palm.buf", O_CREAT|O_RDWR, 0644);
ftruncate(fd, SIZE);
void *p = mmap(NULL, SIZE, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
```

从此 `p` 这段内存，进程 A 写进去、进程 B 读到，**零 syscall、零拷贝**。

它为什么快？因为它压根不"传"数据——两边看的是**同一块物理页**。写和读都退化成纯内存访问，延迟只受 cache 影响。相比之下，pipe/mq 每次读写都要陷入内核，走 buffer 拷贝，光是上下文切换就要几百纳秒。

### 4.2 为什么必须配同步

**疑惑**：共享内存这么好，为什么用得少？

**论证**：

1. **无边界**：你写了一半 A 就来读了，读到的是"写一半"的结构体。共享内存里的结构体，永远处在"可能撕裂"的风险中。
2. **无通知**：写方写完了，读方怎么知道？只能自己轮询，或者搭配另一个通知通道（信号量、eventfd）。
3. **无并发保护**：两个写方同时写、多个读方读，内核不管，你自己不加锁就会飞。

所以共享内存**永远不能裸用**。标准配对是：

```
shm （数据） + semaphore/mutex （互斥） + eventfd/条件变量 （通知）
```

其中互斥防"写一半"，通知防"忙轮询"。这两者少一个，共享内存就退化成"高性能地狱"。

### 4.3 ring buffer实战

嵌入式最常见的共享内存用法是**单生产者-单消费者 ring buffer**——传感器写、UI 读、结构规整、性能爆炸。核心结构：

```c
struct ring_buffer {
    _Atomic uint32_t head;   // 写游标（生产者独占写）
    _Atomic uint32_t tail;   // 读游标（消费者独占写）
    uint32_t         mask;   // capacity - 1（capacity 必须 2 的幂）
    uint8_t          data[]; // 环形数据区
};

// 生产者
bool rb_push(struct ring_buffer *rb, const void *item, size_t sz) {
    uint32_t h = atomic_load_explicit(&rb->head, memory_order_relaxed);
    uint32_t t = atomic_load_explicit(&rb->tail, memory_order_acquire);
    if (h - t >= rb->mask + 1) return false;   // 满
    memcpy(rb->data + ((h & rb->mask) * sz), item, sz);
    atomic_store_explicit(&rb->head, h + 1, memory_order_release);
    return true;
}
```

三个关键点：

1. **单读单写 → 无锁**。因为 head 只有生产者动、tail 只有消费者动，各自 `_Atomic` 即可，不需要任何 mutex。多读或多写就必须补 CAS 或加锁。
2. **capacity 取 2 的幂**：`&mask` 比 `%capacity` 快得多，也不用管溢出（`h - t` 用无符号减法自动环绕）。
3. **memory_order_release/acquire 配对**：保证消费者看到 `head` 递增时，`data` 已经写完。缺一发一堆诡异 bug。

配合一个 `eventfd` 做通知（有数据时生产者写 1，消费者阻塞 read），你就得到了嵌入式最常用的**共享内存高速通道**：延迟 100ns 量级，吞吐几百 MB/s，完全跑满内存带宽。

## 5. Unix Domain Socket

### 5.1 UDS对比TCP

Unix Domain Socket 的 API 和 TCP 几乎一模一样：

```c
int s = socket(AF_UNIX, SOCK_STREAM, 0);       // 只这里不同
struct sockaddr_un addr = { .sun_family = AF_UNIX };
strcpy(addr.sun_path, "/tmp/palm.sock");
connect(s, (struct sockaddr*)&addr, sizeof addr);
send(s, buf, len, 0);
```

但**性能和语义都比 TCP 强**：

| 维度 | TCP | UDS |
|---|---|---|
| 校验和 | 必算 | 跳过（本机可靠） |
| 拷贝路径 | 用户 → 内核 → 网卡 → 内核 → 用户 | 用户 → 内核 → 用户 |
| 拥塞控制 | 有 | 无 |
| 权限控制 | 端口 | 文件权限（chmod） |
| fd 传递 | ❌ | ✅（`SCM_RIGHTS`） |

在本机进程之间通信，UDS 应当作为**默认选择**，不要用 `127.0.0.1` 走 TCP。

### 5.2 SCM_RIGHTS传fd

UDS 有个 TCP 永远做不到的能力：**把一个 fd 从进程 A 传给进程 B**。这在嵌入式里极其有用：

- 主进程 open 一个 `/dev/video0`，把 fd 交给渲染子进程，子进程直接 `read` 而不需要重新 open。
- 一个进程接收 socket 连接，把连接 fd 分发给不同 worker 进程处理（`nginx` 的经典手法）。

```c
struct msghdr msg = {0};
struct cmsghdr *cmsg;
char cbuf[CMSG_SPACE(sizeof(int))];
struct iovec iov = { .iov_base = "F", .iov_len = 1 };
msg.msg_iov = &iov; msg.msg_iovlen = 1;
msg.msg_control = cbuf; msg.msg_controllen = sizeof cbuf;

cmsg = CMSG_FIRSTHDR(&msg);
cmsg->cmsg_level = SOL_SOCKET;
cmsg->cmsg_type  = SCM_RIGHTS;
cmsg->cmsg_len   = CMSG_LEN(sizeof(int));
*(int*)CMSG_DATA(cmsg) = fd_to_send;
sendmsg(s, &msg, 0);
```

内核会在接收端**复制一份 fd 表项**，接收端拿到的是一个"崭新"的 fd，指向同一个内核 file 对象。这是零拷贝分发资源的官方姿势。

### 5.3 数据帧与粘包

UDS 的 `SOCK_STREAM` 和 TCP 一样：**是字节流，没有消息边界**。写方连发两次 100 字节，读方可能一次读到 200 字节、或者第一次读 50 第二次读 150。想在流上传"消息"，你必须自己做分帧。

生产上最常用的两种分帧：

**A. 定长头 + 变长体**（最常用）：

```
┌──────┬────────┬──────────────┐
│ 4B   │  4B    │  N bytes     │
│ MAGIC│ length │  payload     │
└──────┴────────┴──────────────┘
```

读方状态机：先攒够 8 字节头 → 校验 magic + 读出 length → 再攒够 length 字节 body → 交付上层。

**B. 分隔符**（简单场景）：JSON 一行一条，用 `\n` 分割。仅在你能保证 payload 里绝不出现分隔符时才用。

分帧写错会引发一系列诡异 bug（消息越界、内存越读），是新手区分线，一定要用**状态机**写，不要用"一把梭 read"。

## 6. D-Bus与消息总线

### 6.1 总线的意义

前面所有 IPC 都是**点对点**的：A 发给 B，B 收到。系统只有两三个进程时够用，进程一多就会出现**蜘蛛网**：

```
A ─┬─ B          A ─┬─ B ── C
   └─ C     →      ├─ D
                    └─ E ── F ── G
```

模块数从 3 涨到 10，连接数从 3 涨到几十，任何一个模块崩掉都可能带崩别人。**消息总线**的价值在于把 N×N 降成 N×1——每个模块只连总线，不再互相认识。

### 6.2 D-Bus在嵌入式的取舍

D-Bus 是 Linux 桌面世界的标准总线，提供：

- **方法调用**：像 RPC 一样调 `service.method(args)`，同步或异步。
- **信号广播**：发布-订阅模式。
- **服务发现**：谁提供了什么服务，可以运行时查询。
- **命名空间**：`org.freedesktop.NetworkManager` 这种反向域名。

**疑惑**：功能这么全，为什么嵌入式常常把它裁掉？

**论证**：

1. **daemon 开销**：`dbus-daemon` 常驻，内存和 CPU 都有底线开销，低端设备（几十 MB 内存）吃不消。
2. **依赖膨胀**：glib、expat、libdbus，链一堆库，rootfs 变大。
3. **调试门槛**：XML introspection、类型签名、总线权限规则，学习成本不低。
4. **性能天花板**：每条消息经过 daemon 中转，本机延迟就是十几微秒起步，对高频消息不友好。

**结论**：**中大型嵌入式设备**（有内存有 flash，用 systemd 生态）用 D-Bus 一切都对；**低端资源受限设备**，考虑自研轻量总线。

### 6.3 自研轻量总线

一份不到 500 行代码的最小总线，用 UDS + JSON 就能搓出来。核心是这样一个进程：

```
                           ┌──────────┐
     Client A ─── UDS ───▶ │          │
     Client B ─── UDS ───▶ │  broker  │◀── 订阅表  { "sensor/*": [A, C] }
     Client C ─── UDS ───▶ │          │◀── 路由表
                           └──────────┘
```

数据帧（沿用 §5.3 的定长头 + JSON body）：

```json
// 发布
{ "op": "pub", "topic": "sensor/temp", "payload": { "v": 36.5 } }
// 订阅
{ "op": "sub", "topic": "sensor/*" }
// 请求-响应
{ "op": "req", "id": 42, "target": "logicd.reboot", "args": {} }
{ "op": "rsp", "id": 42, "ok": true }
```

broker 主循环只做三件事：

1. `accept` 新连接，塞进客户端表。
2. `epoll_wait` 所有连接，收到帧就查订阅表分发。
3. 处理 `req/rsp`：req 时记住 `(id → 请求方 fd)`，rsp 时按表回送。

500 行代码搞定一个够 90% 嵌入式场景用的总线。**性能**：本机延迟 50-100us，吞吐几万 msg/s。比 D-Bus 简单一个数量级，够用。

## 7. 零拷贝方案

### 7.1 拷贝的代价

前面所有方案，即使是共享内存，也**至少有一次数据被写到内存里**。对通用业务够了。但对以下场景不够：

- 摄像头 30fps × 1080p × YUV：每秒 ~93MB 数据。
- 雷达点云：几 MB/帧、100Hz。
- 4K 视频转码：几百 MB/s 内存带宽。

哪怕只做一次 `memcpy`，都吃掉几十 % 的 CPU。**零拷贝**的核心思路是：**数据从产生（DMA 硬件）到消费（GPU/编码器），全程不经过 CPU 内存拷贝**。

### 7.2 dma-buf与memfd

Linux 内核提供两种"可跨进程共享的匿名内存"：

**dma-buf**：驱动分配的、可被外设 DMA 直接访问的内存。V4L2 采集到的一帧，本质就是一个 dma-buf 的 fd。这个 fd 可以通过 UDS 的 `SCM_RIGHTS` 传给渲染进程，渲染进程再交给 GPU（EGL），全程零拷贝。

**memfd**：`memfd_create` 创建的匿名内存文件，可以 `ftruncate` 后 `mmap`，也可以 `sendmsg` 传给别的进程。它是共享内存的现代替代品，好处是不占文件系统名字空间、支持 sealing（写完可以封印，别人只能读）。

```c
int fd = memfd_create("frame", MFD_ALLOW_SEALING);
ftruncate(fd, FRAME_SIZE);
void *p = mmap(NULL, FRAME_SIZE, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
// 写完
fcntl(fd, F_ADD_SEALS, F_SEAL_WRITE | F_SEAL_SHRINK | F_SEAL_GROW);
// 通过 UDS 把 fd 传出去，接收方 mmap 后只能读
```

### 7.3 何时值得零拷贝

**疑惑**：既然更快，为什么不所有场景都用？

**论证**：

1. **代码复杂度指数级上升**：需要理解 dma-buf 生命周期、fence 同步、GPU-CPU 缓存一致性。
2. **调试极难**：出问题时不是普通的内存错误，是"帧撕裂""GPU 挂起"这种，profiler 帮不上忙。
3. **收益不总在**：如果单帧只有几 KB，`memcpy` 才几微秒，零拷贝带来的复杂度不划算。

**结论**：**只在数据流 > 10MB/s 且要求实时的场景**（相机、视频、雷达、GPU 管线）用零拷贝；否则共享内存 ring buffer 就够。

## 8. 选型决策树

### 8.1 三个维度的问题

选 IPC 之前，先诚实回答三个问题：

**Q1：作用域多大？**
- 父子进程内 → pipe
- 本机跨进程 → fifo / mq / shm / UDS
- 全系统模块间 → D-Bus / 自研总线
- 跨设备 → TCP / MQTT（超出本篇范围）

**Q2：语义是什么？**
- 字节流（日志、串口透传）→ pipe/fifo/UDS 流模式
- 事件/命令（按键、状态变化）→ mq/UDS 报文/总线信号
- 大块数据（图像、点云）→ shm/dma-buf
- 方法调用（"重启这个模块"）→ UDS RPC / D-Bus 方法 / 总线 req

**Q3：性能压力多大？**
- 事件级别（几百 msg/s）→ 什么都行
- 高频（几万 msg/s）→ 共享内存 ring buffer / UDS
- 极致带宽（几百 MB/s）→ 零拷贝

### 8.2 一张图选完

把 8.1 三个维度合成一棵树：

```
需要传数据了？
├─ 只在父子进程 → pipe
│
├─ 跨进程、字节流为主？
│   ├─ 简单日志/透传 → fifo
│   └─ 请求响应/带 fd → UDS
│
├─ 跨进程、离散事件？
│   ├─ 少量事件 → 消息队列 mq
│   └─ 多对多、需广播 → 消息总线（D-Bus / 自研）
│
├─ 跨进程、大数据高频？
│   ├─ < 10MB/s → 共享内存 ring buffer
│   └─ > 10MB/s + 实时 → dma-buf / memfd 零拷贝
│
└─ 全系统调度/管理面 → D-Bus（有资源就上）
```

### 8.3 常见误用

三个最典型的选型错误：

1. **用文件当 IPC**：就是本篇开头翻车的元凶。文件不是 IPC——没通知、没边界、没原子性、没生命周期管理。
2. **本机走 TCP**：明明 UDS 更快更安全，用 `127.0.0.1` 只是"因为熟"，得不偿失。
3. **裸用共享内存**：只 `mmap` 不加锁不通知，早期跑得飞快，压力上来后各种撕裂。

## 9. 可靠性与调试

### 9.1 连接断了怎么办

任何长连接 IPC（UDS、TCP、D-Bus）都要面对：对方进程死了、我这边写了个 SIGPIPE。工程模板：

```c
// 关闭 SIGPIPE，让 write 只返回 -1 而不是杀我
signal(SIGPIPE, SIG_IGN);

for (;;) {
    ssize_t n = write(fd, buf, len);
    if (n < 0) {
        if (errno == EAGAIN)   { /* 非阻塞满 → 稍后重试 */ }
        else if (errno == EPIPE) { reconnect_with_backoff(); }
        else { log_error(); break; }
    }
}
```

**指数退避 + 上限**是重连的标准姿势：`sleep(min(1 << retry, 30))`，避免风暴。

### 9.2 消息丢了怎么查

排查顺序（从便宜到贵）：

1. **strace 挂上**：`strace -f -e trace=network,ipc -p $pid`，直接看 syscall。
2. **ss / lsof 看连接**：UDS 用 `ss -x -p`，能看到两端进程和积压。
3. **tcpdump 抓 UDS**：`tcpdump -i any -w x.pcap 'unix'`（需要内核支持，或用 socat 中继）。
4. **加统计**：每个进程内部维护 `send/recv/drop` 计数，暴露到 `/proc/self/fd/x` 或 shell 命令。
5. **加追踪 ID**：消息头带 `trace_id`，跨进程串起来，出问题按 id grep 日志。

**结论**：IPC 出问题 90% 是"根本就没发出去"，10% 才是"路上丢的"。**先查发送方，再查接收方，最后才怀疑内核。**

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到第 1 章翻车案例，六个疑问现在可以逐条回答：

| 疑问 | 答案 |
|---|---|
| ① 为什么"文件+轮询"不算 IPC？ | 第 2 章：无边界、无通知、无并发保护，本质是"共享持久介质"，不是"传输" |
| ② 各 IPC 差在哪里？ | 第 8.2 决策树：作用域 × 语义 × 性能 三维度切开 |
| ③ 共享内存为何必须配同步？ | 第 4.2：内核只给映射不给一致性，撕裂/无通知/并发全在应用层 |
| ④ UDS 相对 TCP 好在哪？ | 第 5.1：零校验、少一层拷贝、文件权限、能传 fd |
| ⑤ D-Bus 该不该上？ | 第 6.2：中大型设备直接上；低端资源受限自研轻量总线 |
| ⑥ 高速数据流为何要零拷贝？ | 第 7.1：一次 memcpy 几百 MB/s 就吃满 CPU，只能靠 dma-buf |

**重构后的 IPC 架构**——把开篇的翻车拓扑换成这样：

```
             ┌─────────────────────────┐
             │       消息总线（自研）    │
             └───┬─────────┬─────────┬─┘
                 │ UDS     │ UDS     │ UDS   （事件/命令）
             ┌───┴──┐  ┌───┴──┐  ┌───┴──┐
             │sensord│  │logicd│  │ uid  │
             └──┬───┘  └──┬───┘  └──┬───┘
                │         │         │
                └── shm ring buffer ┘     （高频数据）
                    +  eventfd 通知
```

- **事件/命令走总线**（低频、需广播、要解耦）。
- **高频传感器数据走共享内存 ring buffer**（低延迟、大吞吐），配 eventfd 通知。
- **界面进程订阅总线拿状态，从 ring buffer 拿实时数据**。

延迟从 100ms 轮询降到 <1ms，CPU 从 60% 降到 15%，磁盘不再爆，数据也不再丢。

### 10.2 一次跨进程调用的一生

以"UI 点击一下 → sensord 上报最新一帧"为例，把跨进程调用的一生画成一棵树：

```
uid 点击处理
    │
    ├─ 通过 UDS 发一条 req 给 broker         ─── §5, §6.3
    │   { "op": "req", "target": "sensord.snapshot" }
    │
    ├─ broker epoll_wait 命中 uid 的 fd     ─── §6.3
    │
    ├─ broker 查目标 → 转发给 sensord 的 fd  ─── §6.3
    │
    ├─ sensord 收到 req，读取 ring 最新帧    ─── §4.3
    │   （ring 里数据是硬件 DMA 写的，零拷贝）
    │
    ├─ sensord 把帧的 memfd fd 通过 UDS 传回 ─── §5.2 SCM_RIGHTS
    │
    ├─ broker 把 rsp 中的 fd 转给 uid       ─── §5.2
    │
    └─ uid mmap 拿到帧 → 上屏               ─── §7.2
```

从头到尾：**控制面走总线（几十字节的 JSON）**，**数据面走 dma-buf/memfd（几 MB 的帧一字节不拷贝）**。这是嵌入式生产级 IPC 的标准配方。

### 10.3 设计哲学回扣

**哲学 1：控制面 / 数据面分离**

上面这棵树最关键的洞察：**别用一条通道又传命令又传数据**。命令面要求"顺序 + 可靠 + 结构化"，数据面要求"低延迟 + 大吞吐"，两个需求冲突，硬凑一起就得妥协。**总线走控制、共享内存走数据**，各自最优。

**哲学 2：让内核当边界，别让应用当边界**

`mq` 有消息边界、UDS 有连接边界、pipe 有 EOF——**能让内核帮你分帧，就绝不自己写状态机**。裸共享内存需要自己维护 head/tail、需要自己防撕裂，代价是你要理解 memory order。凡是能少写这些的，工程上就少一堆 bug。

**哲学 3：作用域先于性能**

选 IPC 第一个问题永远是"谁跟谁通信"（作用域），不是"每秒多少条"（性能）。作用域选错，性能再高也白搭：跨设备场景选了共享内存，一天都出不了原型；父子进程场景上了 D-Bus，把简单事搞复杂。

**哲学 4：可观测性是 IPC 的一等公民**

IPC 一旦跑起来，问题都在"看不见的地方"。**设计时就要留出观测钩子**：消息头带 trace_id、维护 send/recv/drop 计数、日志里印总线拓扑。事后加观测是补丁，事前加是架构。

### 10.4 IPC速查

**60 秒选型速查**：

| 场景 | 首选 | 备选 |
|---|---|---|
| 父子进程日志 | pipe | fifo |
| 跨进程日志转发 | fifo | UDS stream |
| 结构化事件 | mq | UDS + JSON |
| 高频传感数据 | shm ring buffer + eventfd | mq（若量小） |
| 请求-响应 | UDS + 自定义帧 | D-Bus method |
| 一对多广播 | 自研总线 / D-Bus signal | 多个 UDS |
| 传 fd | UDS + SCM_RIGHTS | — |
| 视频/雷达 | dma-buf | memfd |

**共享内存的三件套原则**：

```
共享内存（数据） + 同步原语（互斥） + 通知原语（唤醒）
       shm       +   sem/atomic     +   eventfd
少任何一件，就是给未来埋坑。
```

**UDS 分帧五字诀**：**头定长、体变长、有魔数、带校验、用状态机**。

**总线自研 vs D-Bus 决策**：

```
内存 > 128MB + 用 systemd → D-Bus
其余情况              → UDS + JSON 自研（<500 行）
```
