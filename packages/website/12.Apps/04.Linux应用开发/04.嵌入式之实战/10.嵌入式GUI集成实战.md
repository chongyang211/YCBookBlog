## 1. 案例引入

### 1.1 一个卡到 12 fps 的中控屏

一款车载中控屏 Demo，用 QML 做的仪表盘 + 导航 + 音乐三合一界面，Cortex-A53 四核、Mali-G31 GPU，实测 12 fps，用户滑动列表能明显感到"顿卡感"。

问题界面的 QML 骨架是这样：

```qml
Rectangle {
    Image { source: "bg.jpg"; anchors.fill: parent }           // ← 1920x720 背景

    Row {
        Repeater {
            model: 30
            delegate: Rectangle {                              // ← 30 个卡片
                Image { source: "cover_" + index + ".png" }    // ← 每卡一张图
                Rectangle { opacity: 0.5; color: "black"; anchors.fill: parent }
                Text { text: modelData; font.pixelSize: 24 }
                DropShadow { source: parent; ... }             // ← 每卡一个投影特效
            }
        }
    }

    Component.onCompleted: {
        // 每 100 ms 强制刷新时间
        var t = new Date();
        timeLabel.text = t.toLocaleTimeString();
    }

    // 后台不停算距离，更新绑定属性
    property real distance: 0
}

// C++ 侧
QTimer t;
connect(&t, &QTimer::timeout, [&]() {
    distance = calcDistanceHeavy();                            // ← 主线程算 20ms
    emit distanceChanged();                                    // ← 每 16ms 触发一次
});
t.start(16);
```

跑起来发现：
- **RSS 从 40 MB 起步涨到 200 MB**，30 分钟后开始卡
- **GPU 使用率 90%**，`overdraw` 严重
- **主线程被 calcDistance 卡满**，触摸事件排队
- **图片没缓存**，每次滚动都重新解码

三年经验的老工程师看完扔下一句："**这不是 GUI 问题，是 GUI 用错了**。"

### 1.2 顺藤摸到根因

- **假设 1**：为什么会 200 MB？，30 张 png 每张 2 MB，未复用 + 未 release 就是 60 MB；QML 的 Item 树、DropShadow 缓存离屏 texture 又几十 MB。→ 引出 **资源管理**。
- **假设 2**：为什么 GPU 90%？，背景 + 卡片 + 遮罩 + 阴影，每像素被绘制 4~6 次，**overdraw 严重**。→ 引出 **overdraw**。
- **假设 3**：为什么主线程卡？，`calcDistanceHeavy` 20ms 在主线程跑，主线程还要处理触摸和渲染，每帧 16.6ms 根本不够。→ 引出 **worker 线程分离**。
- **假设 4**：为什么每 100ms 全量 setText？，即使字符串没变，setText 也会触发 layout + paint。→ 引出 **属性变更粒度**。
- **假设 5**：QTimer(16) 就能保证 60 fps？，不能——QTimer 只保证下一帧调度点，实际帧率由 VSync 决定。**要挂到 QML 的 frameSwapped 信号或用 `Animator`**。→ 引出 **渲染管线协作**。

```
① Widgets/QML/LVGL/Flutter 各自适合什么？   → 第 3 章
② QML 里的 MVVM 是什么？                    → 第 4 章
③ overdraw 怎么排查？                       → 第 5 章
④ 主线程不能干哪些事？                       → 第 4.3 节
⑤ 内存怎么控住？                             → 第 5.2 节
```

### 1.3 我们要回答什么

这一篇讲**嵌入式 GUI 的真实痛点：渲染性能、内存占用、跨线程数据交付**。不是 UI 设计课，是**"让 30 fps 的界面变 60 fps、把 200 MB 打到 80 MB"** 的工程课。


## 2. GUI体系概览

### 2.1 渲染管线的四层

```
┌──────────────────────────────────────────────────────────┐
│  1. Widget/QML 描述层                                       │
│      开发者写：Rectangle{ Text{...} Image{...} }            │
│      产出：场景图（Scene Graph）或对象树                    │
├──────────────────────────────────────────────────────────┤
│  2. 布局/合成层                                             │
│      QML Scene Graph / LVGL 对象树                          │
│      职责：计算位置、剪裁、合并可合并的批次                    │
├──────────────────────────────────────────────────────────┤
│  3. 图形 API 层                                             │
│      OpenGL ES / Vulkan / 软件 raster                       │
│      产出：GPU 指令流                                        │
├──────────────────────────────────────────────────────────┤
│  4. 显示子系统                                              │
│      DRM/KMS + Framebuffer + VSync                          │
│      产出：屏幕上的像素                                      │
└──────────────────────────────────────────────────────────┘
```

**每层的性能影响**：

| 层 | 主要开销 | 优化手段 |
|---|---|---|
| 描述层 | 对象数量、复杂度 | 少建对象、复用 delegate |
| 合成 | 状态改变、脏区扩展 | 减少属性变化频次 |
| 图形 API | 绘制调用数、切换 shader | 批合并、少用 effect |
| 显示 | 传输带宽、VSync 等 | 分辨率匹配、双缓冲 |

### 2.2 硬件加速的边界

**能硬件加速**：矩形填充、纹理贴图、alpha 合成、简单变换

**不能或很慢**：
- 大范围模糊（`GaussianBlur` / `DropShadow`）
- 大量文字动态渲染
- 曲线路径（SVG 复杂图形）
- 软件绘制的 Canvas

**判断标准**：一般 GPU 一帧的绘制预算 = **屏幕像素数 × 3~5 次**（overdraw 上限）。1920x720 = 138 万像素，overdraw 5x = 700 万像素 fill——超过就掉帧。


## 3. 框架选型

### 3.1 Qt-Widgets与QML

**Qt Widgets**：
- 传统 UI 框架，2000 年代技术栈
- CPU 软件渲染为主（QPainter）
- 适合：桌面级、UI 变化不多、性能不敏感

**QML**：
- 声明式 + JS，2010+ 主推
- GPU 加速（Scene Graph）
- 适合：动画多、界面复杂、追求"现代感"

**Qt Widgets 单进程 30~50 MB，QML 60~100 MB**。低端板子（<256 MB RAM）用 QML 会紧张。

**结论**：**中低端 MCU/低端 ARM** → Widgets 或 LVGL；**中高端 ARM + GPU** → QML；**桌面级** → 都行。

### 3.2 LVGL的适用场景

**LVGL**：
- 纯 C，无外部依赖（只需 malloc/free + 帧缓冲）
- 极小（30~100 KB flash，几 MB RAM）
- 软件渲染 + 可选 GPU 加速（少数芯片）
- 面向 MCU 和低端 SoC

**优点**：
- 在 STM32、ESP32 上都能跑
- 上手快，API 直观
- 组件丰富（图表、键盘、动画都自带）

**缺点**：
- 不适合复杂动画（软件渲染极限）
- 中文渲染要额外配字体
- 一切都是 C 结构体，没有面向对象

**典型场景**：智能手表、家电面板、工控 HMI

### 3.3 Flutter与Slint

**Flutter Embedded**：
- Google 出品，跨平台
- Dart 语言
- 高一致性、动画流畅
- 但内存占用大（80~200 MB），启动慢

**Slint**：
- Rust 生态出品，也支持 C++
- 声明式 DSL，编译期生成 C++
- 定位"现代的 QML 替代"
- 生态还年轻但增长快

**嵌入式现状**：Flutter Embedded 用得不多（依赖重），Slint 在起步（值得跟进）。**产品选型仍以 Qt/QML 或 LVGL 为主流**。


## 4. QML架构模式

### 4.1 MVVM实现

QML 天然适合 MVVM（Model-View-ViewModel）：

```
Model      ── C++ QAbstractItemModel 或 QObject
   ▲
   │ 数据变化
   │
ViewModel  ── C++ QObject，暴露给 QML
   ▲                (Q_PROPERTY + signals)
   │
View       ── QML，通过 property binding
```

**C++ 侧 ViewModel**：

```cpp
class MusicViewModel : public QObject {
    Q_OBJECT
    Q_PROPERTY(QString title READ title NOTIFY titleChanged)
    Q_PROPERTY(int progress READ progress NOTIFY progressChanged)
public:
    QString title() const { return title_; }
    int progress() const { return progress_; }
public slots:
    void play() { /* ... */ }
    void pause() { /* ... */ }
signals:
    void titleChanged();
    void progressChanged();
private:
    QString title_;
    int progress_ = 0;
};
```

**QML 侧 View**：

```qml
Rectangle {
    // vm 由 C++ 注入
    Text { text: vm.title }
    ProgressBar { value: vm.progress }
    Button { onClicked: vm.play() }
}
```

**优势**：View 完全声明式、无逻辑；ViewModel 全 C++，可以单元测试；Model 复用给多个 View。

### 4.2 C++对象暴露给QML

**方式 1：qmlRegisterType**（VM 是类型）

```cpp
qmlRegisterType<MusicViewModel>("com.example", 1, 0, "MusicViewModel");
```

QML 里：

```qml
import com.example 1.0
MusicViewModel { id: vm }
```

**方式 2：setContextProperty**（单例对象注入）

```cpp
engine.rootContext()->setContextProperty("vm", &musicVm);
```

QML 里直接用 `vm.xxx`。

**方式 3：qmlRegisterSingletonInstance**（Qt 5.14+）

```cpp
qmlRegisterSingletonInstance("com.example", 1, 0, "Music", &musicVm);
```

**选择**：
- **实例是应用级单例** → SingletonInstance
- **多个界面各自持有** → RegisterType
- **快速原型** → contextProperty

### 4.3 信号槽跨线程

**Qt 信号槽跨线程**通过 `Qt::QueuedConnection` 传递——**参数会拷贝，投递到目标线程的 event loop**。

**关键坑**：
1. **自定义类型必须注册**：`qRegisterMetaType<MyData>("MyData");`
2. **目标线程要有 event loop**：`QThread` 默认没有，要 `exec()` 或用 `QCoreApplication`
3. **UI 更新必须在主线程**：`QObject::connect` 的对象要 `moveToThread(qApp->thread())`

**典型的跨线程数据流**：

```cpp
// Worker 线程发数据
class DataWorker : public QObject {
    Q_OBJECT
signals:
    void newData(SensorData d);   // 在 worker 线程 emit
};

// 主线程 ViewModel 接收
class VM : public QObject {
    Q_OBJECT
public slots:
    void onNewData(SensorData d) {   // 自动在主线程执行
        data_ = d;
        emit dataChanged();
    }
};

// 连接
connect(worker, &DataWorker::newData,
        vm, &VM::onNewData,
        Qt::QueuedConnection);        // ← 关键
```


## 5. 渲染性能优化

### 5.1 overdraw排查

**overdraw**：屏幕上同一像素被绘制多次。

**Qt QML 有内置工具**：

```bash
export QSG_VISUALIZE=overdraw
./app
```

界面会用颜色叠加显示每个像素被绘制的次数：
- 绿色：1 次（正常）
- 蓝色：2 次
- 红色：3+ 次（危险）

**优化手段**：

**手段 1：不透明底部件**

```qml
// ❌ Rectangle 有 alpha 不能截断底下
Rectangle { color: "#88000000"; ... }

// ✅ 完全不透明的可以让底层不必绘制
Rectangle { color: "#000000"; opacity: 1.0; ... }
```

**手段 2：clip**

```qml
Item {
    clip: true                     // 只画可视区，超出的不算
    ListView { ... }
}
```

**注意**：`clip` 本身也有开销（额外一个 pass），**只对"确实需要裁剪"的容器用**。

**手段 3：删除多余的层**

```qml
// ❌ 半透明遮罩 + 阴影，每层都要绘
Rectangle {
    Image {}
    Rectangle { opacity: 0.5 }
    DropShadow { ... }
}
// ✅ 用 Image 里预烘焙好阴影和遮罩
Image { source: "cover_with_shadow_baked.png" }
```

### 5.2 图片缓存与懒加载

**Qt 图片加载的三阶段**：解码 → 上传 GPU → 绘制

**优化点**：

**1. asynchronous 异步加载**

```qml
Image {
    source: "large.jpg"
    asynchronous: true                // ← 不阻塞 UI 线程
    sourceSize.width: 400             // ← 直接解码到目标大小
    sourceSize.height: 300
}
```

`sourceSize` 极重要：一张 4000x3000 的图缩放显示为 400x300，如果没 `sourceSize`，会解码 4000x3000（48 MB RGBA！）到内存再缩。

**2. 用 ImageProvider 集中管理缓存**

```cpp
class ImgProvider : public QQuickImageProvider {
public:
    QPixmap requestPixmap(const QString& id, QSize* size, const QSize& req) {
        if (auto cached = cache_.get(id)) return *cached;
        auto pix = loadAndScale(id, req);
        cache_.put(id, pix);            // LRU
        return pix;
    }
};
engine.addImageProvider("myimg", new ImgProvider);
```

QML 用：`source: "image://myimg/cover_42"`

**3. 列表懒加载**

QML 的 `ListView` 默认已经"只创建可视区 + 若干缓冲的 delegate"，但要注意：

```qml
ListView {
    cacheBuffer: 200                   // ← 上下缓冲多少像素（不是数量）
    reuseItems: true                   // ← Qt 5.15+ 复用 delegate 减少创建销毁
}
```

### 5.3 帧率监控

**运行时输出 FPS**：

```bash
export QSG_INFO=1
export QSG_RENDER_TIMING=1
./app
# 每一帧输出：sync + render + swap 各阶段耗时
```

**自定义显示**：

```cpp
connect(view, &QQuickWindow::frameSwapped, this, [this] {
    frames_++;
    if (elapsed() >= 1000) {
        emit fpsChanged(frames_);
        frames_ = 0;
        reset();
    }
});
```

**目标**：**60 fps = 每帧 16.6 ms**。sync + render + swap **必须** 加起来 < 16 ms，留 buffer 给触摸和其他事件。


## 6. LVGL实战

### 6.1 对象树与内存池

LVGL 一切都是 `lv_obj_t`：

```c
lv_obj_t* screen = lv_scr_act();
lv_obj_t* btn    = lv_button_create(screen);
lv_obj_set_size(btn, 100, 50);
lv_obj_t* label  = lv_label_create(btn);
lv_label_set_text(label, "OK");
```

**内存池配置**（`lv_conf.h`）：

```c
#define LV_MEM_SIZE  (64 * 1024)          // 静态池 64 KB
// 或用系统 malloc
#define LV_MEM_CUSTOM 1
```

**规则**：
- 静态池小、可预测（推荐 MCU）
- 系统 malloc 灵活但易碎片（Linux 场景可用）

**监控**：

```c
lv_mem_monitor_t mon;
lv_mem_monitor(&mon);
printf("used: %u  frag: %d%%\n", mon.total_size - mon.free_size, mon.frag_pct);
```

### 6.2 帧缓冲与Tearing

**LVGL 的三种绘制模式**：

| 模式 | 缓冲 | 特点 |
|---|---|---|
| Direct | 直接写 framebuffer | 最省内存但可能撕裂 |
| Full | 全屏缓冲 + 一次 flush | 无撕裂但慢 |
| Partial | 局部缓冲（推荐） | 平衡 |

**Partial 配置**：

```c
static lv_color_t buf1[SCREEN_WIDTH * 40];   // 只缓冲 40 行
static lv_color_t buf2[SCREEN_WIDTH * 40];
lv_disp_draw_buf_init(&draw_buf, buf1, buf2, SCREEN_WIDTH * 40);
```

**flush 回调对接 DRM/framebuffer**：

```c
void my_flush(lv_disp_drv_t* drv, const lv_area_t* area, lv_color_t* color_p) {
    // 把 color_p 里的数据写到 framebuffer 对应区域
    fbcopy(fb, area, color_p);
    lv_disp_flush_ready(drv);
}
```

**避免撕裂**：使用双缓冲 + VSync 触发 flush，切勿在 flush 中间被显示扫描到。


## 7. 输入与资源

### 7.1 触摸事件分发

**Qt 触摸事件流**：

```
硬件驱动 → /dev/input/eventN
   │
   ▼
libinput 或 evdev 插件读取
   │
   ▼
QGuiApplication 分发 QTouchEvent
   │
   ▼
QQuickWindow → 命中检测 → 目标 Item → onPressed/Moved/Released
```

**常见坑**：
1. **触摸坐标偏移**：屏幕方向与触摸不匹配，需要 `libinput` calibration matrix
2. **多点触摸丢失**：驱动只报单点，或应用没处理 `QTouchEvent::TouchPointStates`
3. **触摸抖动**：加去抖（`accepted = false` 或应用层去抖）

**手势**：Qt 5.15+ 支持 `PinchArea`、`Flickable` 内建手势。复杂手势用 `GestureRecognizer`。

### 7.2 资源打包与压缩

**Qt 资源系统**（qrc）：把资源打进二进制。

```xml
<RCC>
    <qresource prefix="/">
        <file>images/bg.jpg</file>
        <file>qml/Main.qml</file>
    </qresource>
</RCC>
```

**优点**：无外部文件、防篡改
**缺点**：改资源要重编译；二进制变大

**图片压缩策略**：

| 格式 | 特点 | 场景 |
|---|---|---|
| PNG | 无损、alpha | 图标、UI 元素 |
| JPG | 有损、无 alpha | 背景图、照片 |
| WebP | 有损/无损、alpha、小 | 通用替代 PNG 和 JPG |
| ETC2/ASTC | GPU 原生格式，可直接贴 | 高频显示的贴图 |

**推荐**：**WebP 替代 PNG/JPG**（体积小 20~40%），高频贴图上 **ASTC**（GPU 直读，省内存 4~8x）。

**字体裁剪**：中文字体动辄 20 MB，只保留用到的字符集可以压到 500 KB：

```bash

pyftsubset SourceHanSans.ttf \
    --unicodes-file=used_chars.txt \
    --output-file=SourceHanSans-min.ttf
```

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到第 1 章"12 fps 中控屏"，五处修复：

| 问题 | 根因 | 修复 | 章节 |
|---|---|---|---|
| 30 张 png 每张 2 MB | 未 sourceSize、未复用 | sourceSize + ImageProvider LRU | §5.2 |
| overdraw 5+ | 背景/遮罩/阴影层叠 | 预烘焙 + 减层 | §5.1 |
| 主线程 calcDistance 20ms | 重计算在 UI 线程 | 移到 worker + queued signal | §4.3 |
| setText 每 100ms | 高频属性变更 | 只在真正变化时 emit | §4.1 |
| QTimer(16) 不准 | 未与 VSync 对齐 | 用 frameSwapped 或 Animator | §5.3 |

**改造后的 QML**：

```qml
Rectangle {
    Image { source: "bg_baked.webp"; asynchronous: true;
            sourceSize.width: 1920; sourceSize.height: 720; anchors.fill: parent }

    ListView {                                       // 换成 ListView，天然懒加载
        model: musicModel                            // C++ QAbstractListModel
        cacheBuffer: 400
        reuseItems: true
        orientation: Qt.Horizontal
        clip: true
        delegate: MusicCard { }                      // 单独的 Component
    }

    Text { id: timeLabel; text: vm.currentTime }     // vm 是 C++ 属性
}

// MusicCard.qml
Item {
    width: 200; height: 240
    Image {
        source: "image://covers/" + model.coverId    // 走 ImageProvider
        sourceSize.width: 200
        asynchronous: true
        anchors.fill: parent
    }
    Text { text: model.title; anchors.bottom: parent.bottom }
}
```

**改造后的 C++**：

```cpp
class MusicVM : public QObject {
    Q_OBJECT
    Q_PROPERTY(QString currentTime READ currentTime NOTIFY currentTimeChanged)
    Q_PROPERTY(qreal distance READ distance NOTIFY distanceChanged)
public:
    MusicVM() {
        // 时间更新，只在秒变化时 emit
        timer_.setInterval(1000);
        connect(&timer_, &QTimer::timeout, this, [this] {
            auto t = QDateTime::currentDateTime().toString("hh:mm:ss");
            if (t != currentTime_) { currentTime_ = t; emit currentTimeChanged(); }
        });
        timer_.start();

        // 距离计算放 worker
        worker_ = new DistanceWorker;
        worker_->moveToThread(&thread_);
        connect(worker_, &DistanceWorker::result,
                this, &MusicVM::onDistance, Qt::QueuedConnection);
        thread_.start();
    }
public slots:
    void onDistance(qreal d) {
        if (qFuzzyCompare(d, distance_)) return;   // 无变化不 emit
        distance_ = d;
        emit distanceChanged();
    }
};
```

**结果**：**12 fps → 58 fps**（60 fps 上限内已经稳定），**RSS 从 200 MB → 75 MB**，GPU 使用率从 90% → 30%。

### 10.2 一帧的一生

从"用户滑动"到"新一帧显示"的完整流程：

```
【T=0】用户手指滑动，触摸事件产生
    │
    ▼ 【1. 内核 evdev】
写入 /dev/input/eventN
    │
    ▼ 【2. libinput / QPA】
读取 → 构造 QTouchEvent
    │
    ▼ 【3. QGuiApplication 主线程】§7.1
分发 → 找到 ListView → touchMoveEvent
    │
    ▼ 【4. ListView 更新 contentX】
触发 QSGNode 属性变化
    │
    ▼ 【5. Scene Graph 同步 sync】§2.1
把 QML 对象的属性拷贝到渲染线程的 SG 树
    │
    ▼ 【6. 渲染线程】
遍历 SG 树 → 生成 OpenGL 指令
    │
    ▼ 【7. GPU】
执行绘制命令 → 写入 back buffer
    │
    ▼ 【8. VSync 到达】
显示子系统 swap buffer → back 变 front → 屏幕更新
    │
    ▼ 【9. frameSwapped 信号】
应用可以做统计、下一帧准备
```

**每一步的时间预算**（60fps 下每帧 16 ms）：

| 步 | 建议预算 |
|---|---|
| 触摸事件 | 1~2 ms |
| Sync | 1~3 ms |
| Render (GPU 处理绘制指令) | 5~10 ms |
| Swap | <1 ms |
| 剩余业务逻辑 | <5 ms |

**任何一步超时** → 掉帧 → 下一帧要等下一个 VSync（多等 16 ms）。

### 10.3 设计哲学回扣

**哲学 1：GUI 是共享资源，不能被独占**

主线程要跑渲染、要处理事件，任何"20 ms 计算"都会毁掉帧率。**GUI 主线程只做"轻量的展示逻辑"**，重活推给 worker。这与网络篇的"reactor 主循环不做重活"是同一种设计。

**哲学 2：像素也要预算**

GPU 一帧能画的像素是有上限的，overdraw 3 层就吃掉大半。**每一个 alpha 层、每一个 shadow、每一个 blur，都要问"值不值这几个 MB fill rate"**。UI 设计不能只看好看，要看合成成本。

**哲学 3：让渲染管线做它擅长的**

VSync、双缓冲、GPU 加速、异步图片解码，这些机制都存在——**不要绕过它们自己搞**。QTimer(16) 就是典型的"越俎代庖"。**顺势而为**，让渲染管线告诉你"该干活了"。

**哲学 4：资源生命周期一等公民**

图片、字体、着色器、texture buffer——都是可以泄漏、可以爆内存的资源。**从设计阶段就把它们纳入生命周期管理**（LRU、按需加载、离屏 evict），而不是等 OOM 才回头改。
