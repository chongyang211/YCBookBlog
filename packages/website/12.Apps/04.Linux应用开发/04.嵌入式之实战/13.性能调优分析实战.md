## 1. 案例引入

### 1.1 一台 CPU 90% 却说不清的车机

现场从一款车载中控裁剪。上电启动后 CPU 常年 85~95%，但用户界面还行，产品经理坚持要"把 CPU 降下来"。开发一头雾水：

```bash
# top 结果
%Cpu(s): 60.2 us,  25.4 sy,  0.0 ni,  8.2 id,  4.1 wa, 0.5 hi, 1.6 si
                                   ↑ wa 4%      ↑ si 1.6%

  PID USER      %CPU  COMMAND
 2341 root      42.1  ivi_render        ← 渲染主进程
 2450 root      18.7  can_bridge        ← CAN 总线桥接
 2501 root      12.3  log_writer        ← 日志落盘
 2103 root       6.4  audio_pipe
     ...
```

看起来"渲染吃得多"，但优化了整整两周渲染路径，CPU 只降到 80%。真正的坑不在渲染，也不在最占 CPU 的进程——**在你看不见的地方**。

```c
// log_writer.c —— 简化版
static void log_emit(const char *line) {
    static FILE *fp;
    if (!fp) fp = fopen("/data/app.log", "a");
    fprintf(fp, "%s\n", line);      // ← §7.3 每条 fprintf 都 syscall
    fflush(fp);                      // ← §6.1 每条都 fsync 语义
}

// can_bridge.c
static void on_can_frame(struct can_frame *f) {
    char buf[128];
    snprintf(buf, sizeof buf, "ID=%x DLC=%d DATA=%02x%02x...", ...);
    log_emit(buf);                   // ← 高频 CAN 帧 → 每帧都写文件
    dispatch(f);
}
```

### 1.2 顺藤摸到根因

top 看到的"CPU 高"里藏着**四个假象**：

- **看错了 %CPU**：`ivi_render` 42% 是 user 态，但真正瓶颈在 `sy=25%`+`wa=4%`，都是 CAN → log_emit 引起的 syscall 与 IO 等待。
- **misidentify hot function**：不做火焰图，永远不知道 `snprintf` + `fflush` 被 CAN 高频路径调用了 5000 次/秒。
- **off-CPU 看不见**：磁盘 IO 等待时进程不占 CPU，但整机在等，`top` 显示 `wa` 但不显示是谁。
- **中断/软中断被忽略**：`si=1.6%` 看着不高，但 CAN 中断 8000/s，每次上下文切换都吃 CPU。

真正的问题：**"CAN 高频路径同步落盘"**——每一条 CAN 帧都触发一次 open/write/fsync。修完之后 CPU 从 85% 直接降到 22%。

### 1.3 我们要回答什么

- top/htop 看 %CPU，看的到底是什么？为什么 sy 高才是真信号？ → §5.3
- 火焰图看不懂，宽格子和高栈到底哪个重要？ → §4.3
- 交叉编译的 perf 怎么装到板子上？符号怎么解析？ → §3.3 / §4.2
- CPU 不高但业务卡，off-CPU 火焰图怎么生成？ → §5.2
- 中断和软中断算不算 CPU？占比高怎么办？ → §6.3
- 优化的三板斧，为什么"批处理合并"往往收益最大？ → §7.3

## 2. 性能体系概览

### 2.1 性能问题的两个维度

嵌入式性能问题看两个坐标：

```
                   ┌──── CPU 高 ────┐
                   │                │
              吞吐够 (延迟差)   吞吐不够 (真忙)
              ↓                    ↓
         少数请求慢           多数请求都慢
         → 尾延迟排查        → 热点函数排查
                   │
                   └──── CPU 低 ────┐
                                    │
                              吞吐差 (真闲?)
                                    ↓
                         off-CPU / IO / 锁竞争 / 中断
                         → 找"CPU 在等什么"
```

**"CPU 高不等于 CPU 累，CPU 低不等于 CPU 闲"**——on-CPU 与 off-CPU 是两个独立坐标。

### 2.2 分析三板斧

嵌入式性能三板斧：

- **top/htop/mpstat**：快速定位"谁高"，给方向。
- **perf + 火焰图**：定位"哪一行热"，给函数级证据。
- **strace/blktrace/bcc**：定位"CPU 不做事时在等谁"，给因果链。

三板斧的分工：

```
          ┌───────────────────────────┐
          │      性能问题定位          │
          ├──────────┬────────────────┤
          │  快速定位│  深度分析       │
          │  top     │  perf 火焰图    │
          │  vmstat  │  bcc / strace  │
          │  iostat  │  blktrace      │
          │          │                │
          │  给方向  │  给证据         │
          └──────────┴────────────────┘
```

**"没有火焰图，就没有性能优化"**——所有靠 top 和经验优化的都是碰运气。

## 3. perf 原理

### 3.1 硬件 PMU 与软件事件

`perf` 是 Linux 内核自带的性能分析框架，底层两类事件源：

- **硬件 PMU**：CPU 内嵌的 Performance Monitoring Unit，直接计数 cycles / instructions / cache-misses / branch-misses。零成本采样，最准。
- **软件事件**：内核暴露的 tracepoint（`sched:sched_switch`、`syscalls:sys_enter_*`）与 kprobe/uprobe。灵活但代价大。

嵌入式常见的两个陷阱：

- **ARM Cortex-A 系列 PMU 支持有限**：部分 SoC 屏蔽了 PMU 权限（`perf_event_paranoid=3`），或者内核编译时没开 `CONFIG_HW_PERF_EVENTS`。查一下 `perf list` 有没有 `cpu-cycles [Hardware event]`——**没有就只能用软件采样，精度打折**。
- **`perf_event_paranoid`**：控制普通用户能不能采样内核态。默认 2 (`>=0`) 只能用户态；改到 -1 允许所有事件，嵌入式 root 环境可以放开。

```bash
echo -1 > /proc/sys/kernel/perf_event_paranoid
echo 0  > /proc/sys/kernel/kptr_restrict            # 允许看内核符号
```

### 3.2 采样 vs 追踪

perf 两种工作模式：

- **采样（`perf record -F 99`）**：每秒 99 次中断，抓当前 PC + 栈。开销小（1~3%），足够画火焰图。**99 而不是 100 是为了避开某些周期性任务对齐导致的采样偏差**。
- **追踪（`perf trace` / `perf record -e sched:*`）**：每个事件都记，开销大（20%+），用于精确因果分析。

**嵌入式默认采样**，追踪只在专项分析时用。追踪能抓到全量，但会拖垮设备。

### 3.3 交叉环境 perf 部署

板子上的 perf 必须与内核**大版本**匹配：

```bash
# 板端
apt install linux-perf              # 或从 kernel/tools/perf 交叉编译
# 或者 busybox 环境下静态编译一个 perf 上板

perf --version
# perf version 5.10.xxx              ← 必须与 uname -r 主版本一致
```

编译时的关键 flag：`LDFLAGS=-static` 让 perf 不依赖 libelf/libdw 动态库，方便直接 scp 上板。

**采样命令**（板端执行）：

```bash
perf record -F 99 -a -g --call-graph dwarf -- sleep 30
# -F 99   99Hz 采样
# -a      所有 CPU
# -g      记录调用栈
# --call-graph dwarf   用 DWARF 展开栈（栈上没 fp 也能回溯）
# sleep 30  采样 30 秒
```

`--call-graph dwarf` 依赖 `-fno-omit-frame-pointer` **或** 完整 debug info；`--call-graph lbr` 用 CPU 硬件辅助（LBR），ARM 上不可用。**嵌入式一般用 `dwarf`**，同时把 debug 符号分拆归档（第 11 篇 §6.1）。

## 4. 火焰图生成

### 4.1 三步走：record → script → svg

Brendan Gregg 的 FlameGraph 脚本套件是事实标准，三步走：

```bash
# 步骤 1：板端采样 30 秒
perf record -F 99 -a -g --call-graph dwarf -- sleep 30
# → 生成 perf.data

# 步骤 2：板端导出可读文本（不解析符号，加快）
perf script > out.perf

# 步骤 3：主机端画图（需要 FlameGraph 脚本）
scp root@dev:out.perf .
./FlameGraph/stackcollapse-perf.pl out.perf > out.folded
./FlameGraph/flamegraph.pl out.folded > flame.svg
firefox flame.svg
```

一键脚本示例：

```bash
#!/bin/sh
# on_device_perf.sh
perf record -F 99 -a -g --call-graph dwarf -- sleep "${1:-30}"
perf script > /tmp/out.perf
tar czf /tmp/perf-$(date +%s).tar.gz /tmp/out.perf $(which target-elf)
echo "拉走 /tmp/perf-*.tar.gz 到主机跑 flamegraph.pl"
```

### 4.2 符号解析与 sysroot

火焰图不好看的两大原因：**格子里全是 `[unknown]`** 或 **`+0x1234` 数字**。原因是没有符号。

三处符号来源：

- **应用符号**：编译时 `-g`，运行时不 strip 或分拆保留 `.debug` 文件。
- **共享库符号**：libc / libstdc++ 也要装对应的 `-dbg` 包，或从交叉工具链里带过来。
- **内核符号**：`/proc/kallsyms` 需要 `echo 0 > /proc/sys/kernel/kptr_restrict`；内核火焰图额外需要 `System.map`。

主机端解析时，**`perf script` 需要在采样机器上跑**（能拿到 kallsyms 和 pid 映射），或者用 `perf archive` 打包符号一起带走：

```bash
# 板端
perf archive
# → 生成 perf.data.tar.bz2，包含所有需要的符号

# 主机端
tar xf perf.data.tar.bz2 -C ~/.debug
perf script --symfs=~/.debug > out.perf
```

`--symfs` 是替代 sysroot 的关键——**告诉 perf 从哪里找符号，而不是从主机 `/`**。

### 4.3 读图的四条规则

火焰图是 X 轴按调用总时间比例、Y 轴按栈深度绘制的。**四条硬规则**：

- **宽度代表时间占比，不是执行速度**：宽格子 = 累计时间长，不一定是慢函数，可能是频繁调用的快函数。
- **高度代表调用深度，不代表性能**：栈高 = 调用链深，别去优化"高塔"，去优化"宽平顶"。
- **看顶端平顶（"平台"）**：真正吃 CPU 的是"最上层的宽平顶"——那就是当前 PC，没有再往下调用的地方。
- **左右顺序无意义**：只是字母排序，不是执行时序。

**典型模式识别**：

- **平顶宽而无内嵌高塔** → 该函数自身热（比如内存拷贝、加密循环）。
- **底部宽、逐层收窄** → 总入口多路分散，找共通子调用。
- **顶部大量 `[unknown]`** → 符号没解析对，回 §4.2 修 debuginfo。
- **`[k]` 前缀的内核函数占大头** → 系统调用密集，比如 §1.1 那种。

## 5. on-CPU 与 off-CPU

### 5.1 on-CPU：CPU 在干什么

默认 `perf record -F 99` 采的就是 on-CPU 火焰图——**只有当前正在跑的进程才被采样**。它回答：**"CPU 忙时忙在哪"**。

适用场景：

- CPU 使用率高，想知道热函数；
- 想验证优化前后差异；
- 想看某个批处理任务的耗时分布。

**不适用**：CPU 使用率不高但业务卡——说明 CPU 在等，等的东西 on-CPU 看不到。

### 5.2 off-CPU：CPU 不在干什么

**off-CPU 火焰图**用 `perf sched` 或 bcc 的 `offcputime` 采集"进程被切下 CPU 的原因和时间"：

```bash
# bcc 版（推荐，需要内核支持 BPF）
offcputime-bpfcc -f 30 > out.folded
./FlameGraph/flamegraph.pl --color=io out.folded > offcpu.svg
```

回答：**"CPU 空闲时业务在等什么"**——磁盘、锁、网络、条件变量。

**on-CPU + off-CPU 是一对**：两张图叠在一起才是完整视图。案例 §1.1 里 CAN 路径的 `fflush` 阻塞在磁盘，on-CPU 能看到 `snprintf` 热，off-CPU 能看到 `ext4_sync_file` 等磁盘——两张图必须都看。

### 5.3 用户态 vs 内核态占比

`top` 的 `%Cpu` 一行里三个关键字段：

```
%Cpu(s):  60 us,  25 sy,  8 id,  4 wa,  0 hi,  2 si
           ↑用户态 ↑内核态       ↑等IO    ↑软中断
```

**读法**：

- `us` 高、`sy` 低：应用自己算，符合直觉，看 on-CPU 火焰图。
- `us` 低、`sy` 高：应用在**触发系统调用**，syscall 密集，检查 read/write/mmap/futex 频次。
- `wa` 高：IO 阻塞，看 §6.1 iostat。
- `si` 高：软中断，通常是网络（NAPI）或定时器，看 §6.3。
- `hi` 高：硬中断，多半是硬件问题或驱动异常。

**"sy > 15% 一般是应用锅"**——嵌入式 `sy` 高最常见的是频繁 syscall（fflush、gettimeofday、read/write 小包），批量合并即可。

## 6. IO 与中断分析

### 6.1 iostat / iotop 定位磁盘

`wa` 高时第一时间跑：

```bash
iostat -xz 1
# Device  r/s    w/s    rkB/s  wkB/s   await  %util
# mmcblk0  0.0   1200.0  0.0   4800.0  25.0   98.0
#                ↑ 1200 次/秒写 IO  ↑ 磁盘 98% 忙
```

`%util > 80%` 就说明磁盘饱和；`await` 是平均等待时间，超过 20ms 明显有问题（SSD 通常 <5ms，SD 卡 10-30ms）。

`iotop -o` 看**谁在读写**：

```bash
iotop -oPa
#  TID  DISK READ  DISK WRITE  COMMAND
#  2501     0.00      4.8 M/s  log_writer  ← 元凶
#  2450     0.00      2.1 M/s  can_bridge
```

**"IO 密集不看 CPU 看 iostat"**——CPU 只是等待方，iostat 才是当事人。

### 6.2 blktrace 追踪块层

想看**具体每一次 IO 的路径**（提交到哪个队列、合并了没、什么时候完成）：

```bash
blktrace -d /dev/mmcblk0 -o - | blkparse -i -
# 8,0    0  1234  0.001234567  2501  Q  W 12345 + 8 [log_writer]
#                            ↑ pid  ↑ 请求：写 8 个扇区
```

关键字母：

- `Q` 排队 → `G` 获取 rq → `I` 插入 → `D` 派发 → `C` 完成
- `D → C` 的时间差是**设备实际处理时间**，用于区分"内核慢"还是"设备慢"。

嵌入式常用场景：判断"是不是 flash 写放大 + 磨损均衡在拖后腿"——参考第 06 篇 §3.3。

### 6.3 中断/软中断占比

`/proc/interrupts` 看硬中断计数：

```bash
watch -n 1 'cat /proc/interrupts'
#            CPU0        CPU1
#  30:  1234567890  0    GIC   can0    ← CAN 中断频次
#  31:      123456  0    GIC   eth0
```

**中断频次 × CPU 数 = 上下文切换负担**。CAN 8000 次/秒的中断，每次 5μs 处理 = 40ms/秒 = 4% CPU 硬扛。

`/proc/softirqs` 看软中断：

```
                   CPU0
NET_RX:        1234567    ← 网络接收软中断
TIMER:          234567
SCHED:          345678
```

**优化方向**：

- 硬中断高 → 加中断合并（`ethtool -C eth0 rx-usecs 100`）或用 NAPI 轮询模式。
- 软中断高 → 网络考虑绑定 CPU（`smp_affinity`），避免抢占业务 CPU。
- 定时器高 → 检查 setitimer/timerfd 是不是被大量使用。

## 7. 优化三板斧

### 7.1 算法替换

**收益上限最高，但代码改动大**。适用："热函数是 O(n²)、能换 O(n log n)"这种场景。

例子：

- 每帧遍历所有对象碰撞检测 → 换空间划分（网格/四叉树）。
- 字符串拼接 `+=` in loop → 用 buffer 一次预留 + memcpy。
- JSON 解析每次全量 → 换 SAX 流式或 FlatBuffers 零拷贝。

**判断标准**：火焰图上函数格子宽度 > 20% 且函数本身是 O(n²) 及以上 —— 换算法。宽度 < 5% 换算法收益太低，不划算。

### 7.2 缓存命中

CPU cache miss 是隐形杀手，尤其嵌入式 ARM L1 只有 32KB：

- **数据结构 SoA vs AoS**：如果每次只用结构体一个字段，SoA（Struct of Arrays）比 AoS（Array of Structs）快 3~10 倍。
- **对齐 cache line**：`__attribute__((aligned(64)))`，避免 false sharing。
- **热数据集中**：LRU 命中率、hot path 数据放同一 cache line。

例子：一个 sensor 数组，如果 for 循环里只读 `temperature`，就把 temperature 单独一个数组：

```c
// 差：AoS
struct sensor { float temp, humid, press; ... };
sensor arr[10000];
for (auto& s : arr) sum += s.temp;   // 每条 cache line 只有 1/16 有用

// 好：SoA
float temp[10000], humid[10000], press[10000];
for (int i = 0; i < 10000; i++) sum += temp[i];  // 16 个/cache line
```

用 `perf stat -e cache-misses,cache-references` 直接看命中率变化。

### 7.3 批处理合并

**嵌入式收益最大的一板斧**，因为大部分性能问题都是"高频小操作"叠加。

三种典型合并：

- **syscall 合并**：`fprintf` + `fflush` 每条日志 → 批量 buffer + 定时刷。
- **网络合并**：Nagle / TCP_CORK / MSG_MORE，见第 05 篇。
- **磁盘合并**：应用层 buffer + `fsync` 每 1000 条或 1 秒一次。

**§1.1 的修复本质就是批处理合并**：

```c
// 修复后
static char logbuf[64*1024];
static size_t log_off;

static void log_emit(const char *line) {
    size_t n = strlen(line);
    if (log_off + n + 1 > sizeof logbuf) log_flush();
    memcpy(logbuf + log_off, line, n);
    logbuf[log_off + n] = '\n';
    log_off += n + 1;
}

static void log_flush(void) {          // 定时器 1s 或 buffer 满时调
    write(log_fd, logbuf, log_off);
    log_off = 0;
    // fdatasync 也是 1s 一次
}
```

CPU 从 85% → 22%，改动不到 30 行。**收益最高的往往是最简单的代码**。

## 8. 选型决策树

### 8.1 六个维度

- **CPU 使用率**：高 → on-CPU；低但业务卡 → off-CPU。
- **热点是应用还是内核**：`us` vs `sy`，方向不同。
- **有 IO 等待吗**：`wa` > 5% → iostat/blktrace。
- **PMU 支持吗**：不支持 → 只能软件采样，精度略差。
- **能不能上板长跑**：能 → perf；不能 → 只能开发机 replay。
- **优化收益预估**：宽格子 → 优先改；窄格子 → 别浪费时间。

### 8.2 一张图选完

```
                性能问题
                   │
        ┌──────────┴───────────┐
      CPU 高？                CPU 低？
        │                       │
    us / sy?              wa 高?    锁竞争?
    ↓        ↓             ↓         ↓
    on-CPU  syscall     iostat    off-CPU
    火焰图  strace -c   iotop     perf sched
    ↓                      │
    找宽平顶            blktrace
    ↓
    § 7 优化三板斧：
       算法替换 → 缓存 → 批处理
    ↓
    perf stat 对比前后
```

### 8.3 常见误用

- **只看 top 就下结论**：`ivi_render 42%` 不等于问题在渲染，可能是被 CAN 拖累。**必须看火焰图**。
- **优化窄格子**：占 2% 的函数优化到 0% 也就省 2%，收益太低。**永远优化 > 15% 的格子**。
- **不做基线就改代码**：改完不知道有没有效果。**每次改动前后各跑一次 perf**，一图对比。
- **只看 on-CPU**：CPU 才 30% 但业务慢死，off-CPU 才是主战场。
- **忽略中断**：硬/软中断吃 CPU 是隐形的，`top` 里 `hi/si` 一定要瞄一眼。
- **PMU 数据不看**：`cache-misses` 高 = 数据结构烂，光看栈猜不到。

## 9. 可靠性与调试

### 9.1 CPU 高排查 SOP

设备 CPU 报警后，10 分钟内走完：

```bash
# 1. 分方向：us / sy / wa / si
mpstat -P ALL 1 5
# CPU 分布 + 各态占比

# 2. 定位进程
top -H -b -n 1 | head -20            # -H 看线程
pidstat -u -t 1                       # 每个线程的 CPU

# 3. 采样火焰图（30 秒）
perf record -F 99 -a -g --call-graph dwarf -- sleep 30
perf script > out.perf
scp out.perf host:
# 主机端 stackcollapse + flamegraph.pl

# 4. 定位平顶：占比 > 15% 的宽格子

# 5. 定位类型
#    - 用户态函数 → 算法或频次
#    - kernel_write / ext4_* → syscall/IO 密集
#    - futex → 锁竞争，做 off-CPU

# 6. 补 off-CPU
offcputime-bpfcc -df 30 > offcpu.folded

# 7. 验证：优化前后各一张，diff-flamegraph.pl 生成对比图
./FlameGraph/difffolded.pl before.folded after.folded | ./flamegraph.pl > diff.svg
```

**"火焰图不是只画一张，是画两张做对比"**——性能优化的证据链就是 before/after 两张图。

### 9.2 性能回归 CI 集成

嵌入式项目的性能回归常常是"某次提交把 CPU 从 20% 升到 40%"，**没有基准就发现不了**。CI 集成方案：

```bash
#!/bin/bash
# ci_perf.sh
# 1. 编译目标固件
make cross-build

# 2. QEMU 里跑标准负载 60 秒
qemu-arm ./gateway &
PID=$!
sleep 5
./run_benchmark.sh    # 触发标准负载

# 3. 采样
perf record -F 99 -p $PID -g -- sleep 60
perf script > out.perf

# 4. 生成 folded stacks
stackcollapse-perf.pl out.perf > current.folded

# 5. 对比基线
difffolded.pl baseline.folded current.folded > diff.folded
DELTA=$(awk '$2 > 0 {sum += $2} END {print sum}' diff.folded)

# 6. 阈值判断
if [ "$DELTA" -gt 100000 ]; then     # 采样点增量阈值
    echo "PERF REGRESSION!"
    flamegraph.pl diff.folded > diff.svg
    exit 1
fi

# 7. 更新基线（可选，master 分支合入时）
[ "$BRANCH" = "master" ] && cp current.folded baseline.folded
```

配合每晚 nightly 跑一次全量 benchmark，第二天早上看邮件报告。**"回归 20% 就发现，回归 200% 后再发现代价不同"**——差 30 天。

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到 §1.1 的代码，逐行标注章节：

```c
static void log_emit(const char *line) {
    static FILE *fp;
    if (!fp) fp = fopen("/data/app.log", "a");
    fprintf(fp, "%s\n", line);      // ← §7.3 每条一次 write syscall
    fflush(fp);                      // ← §6.1 每条一次 IO
}

static void on_can_frame(struct can_frame *f) {
    char buf[128];
    snprintf(buf, sizeof buf, "ID=%x DLC=%d ...", ...);  // ← §5.3 sy 25% 的元凶入口
    log_emit(buf);                                       // ← §6.3 8000/s 频次
    dispatch(f);
}
```

**真相**：CAN 8000 帧/秒 × 每帧一次 fprintf+fflush = 8000 次 syscall + 8000 次磁盘写。表现：

- **on-CPU 火焰图**：顶端宽平顶是 `vfprintf` 与 `ext4_da_write_end`。
- **off-CPU 火焰图**：`fsync` → `ext4_sync_file` 阻塞 4~15ms。
- **top**：`us=60% sy=25% wa=4%`，`sy+wa` 才是真元凶。
- **iostat**：`%util=98%`，磁盘打满。
- **top 显示的是 `ivi_render` 高**：只是它算得快、拿到 CPU 多，不是它慢；`log_writer` 因为大部分时间在等磁盘，反而 %CPU 显示低。

修复（§7.3）：64KB buffer + 1 秒定时 flush，CPU 从 85% 降到 22%。

### 10.2 一次性能优化的一生

```
[T0]  报警：设备 CPU 85%              ← §1.1 现场
       │
[T1]  快速定位（1 分钟）
       │  top → us=60 sy=25 wa=4     ← §5.3
       │  mpstat 确认所有核都高
       │
[T2]  采样火焰图（30 秒）              ← §4.1
       │  perf record -F 99 -a -g --call-graph dwarf -- sleep 30
       │  scp → 主机 flamegraph.pl
       │
[T3]  读图：顶端平顶 = vfprintf 30%
       │       ext4_da_write_end 15%
       │       can_recv 8%             ← §4.3
       │
[T4]  分类：sy 高 → syscall 密集       ← §5.3
       │  strace -c -p $(pidof can_bridge) 5s
       │  → write 40000/s, fsync 8000/s ← §6.1
       │
[T5]  假设：批处理合并能救             ← §7.3
       │  改 log_emit：ring buffer + timer
       │
[T6]  验证：before/after 两张火焰图
       │  perf record 30s × 2
       │  difffolded.pl → diff.svg
       │  → vfprintf 从 30% 降到 3%
       │
[T7]  上线灰度 24 小时
       │  CPU 稳定在 22%
       │
[T8]  写单测：CI 加 perf 回归门槛      ← §9.2
       │  阈值：CPU 增量 > 15% 阻断合入
       │
[T9]  归档：本次优化写入内部知识库
       │  下次类似问题 5 分钟能定位
```

### 10.3 设计哲学回扣

- **"性能不靠猜，靠火焰图"**：任何优化前必须先出图，任何优化后必须再出图。before/after 两张图才是证据。
- **"宽格子才值得优化"**：占 15% 以下的函数不值得动，能让 CPU 降 15% 的改动才是有效改动。
- **"批处理合并往往收益最大"**：嵌入式 90% 的 CPU 问题都是"高频小操作"，合并成"低频大操作"就够。
- **"on-CPU 和 off-CPU 是一对"**：只看 on-CPU 会漏掉一半问题，off-CPU 才能揭示"CPU 在等什么"。
- **"性能问题一天不进 CI，一年后就有回归"**：基线 + 阈值 + 报警，性能维护是流水线，不是英雄式救火。

### 10.4 性能调优速查

| 场景 | 首选工具 | 关键命令 |
|------|----------|----------|
| CPU 高定位方向 | top / mpstat | `mpstat -P ALL 1` |
| 应用热点 | perf + FlameGraph | `perf record -F 99 -g` |
| syscall 密集 | strace 汇总 | `strace -c -p $PID` |
| IO 等待 | iostat / iotop | `iostat -xz 1` |
| 块层追踪 | blktrace | `blktrace -d /dev/mmcblk0` |
| 锁竞争 / off-CPU | bcc offcputime | `offcputime-bpfcc -f 30` |
| 中断分布 | /proc/interrupts | `watch cat /proc/interrupts` |
| PMU 计数 | perf stat | `perf stat -e cache-misses,cycles` |
| 前后对比 | difffolded | `difffolded.pl a.folded b.folded` |
| 回归防护 | CI + baseline | nightly 跑 + 阈值报警 |

**一句话建议**：**先出火焰图再谈优化；一次改一处，前后各出一张图；每处改动进 CI 立基线。**
