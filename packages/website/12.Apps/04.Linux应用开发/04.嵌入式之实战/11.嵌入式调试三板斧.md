## 1. 案例引入

### 1.1 一台凌晨三点必挂的网关

现场从一个 IoT 网关裁剪出来。设备白天风平浪静，一到凌晨三点半左右必崩溃重启，日志只留下一行 `segfault at 0 ip 0000... error 4`：

```c
// gateway_worker.c —— 裁剪自真实产品
struct session {
    int  fd;
    char *buf;         // ← §5.1 heap-buffer-overflow 的种子
    size_t cap;
};

static void on_timeout(struct session *s) {
    free(s->buf);       // ← §5.1 free 后没置 NULL
    s->buf = NULL;
    // ... 释放其他字段
}

static void on_data(struct session *s, const char *p, size_t n) {
    if (n > s->cap) s->cap = n;                 // 只更新 cap
    memcpy(s->buf, p, n);                       // ← §3.3 崩在这里
}

int main(void) {
    // signal(SIGSEGV, ...) 什么都没装
    // ulimit -c 0（默认）
    // core_pattern = "core"（写不进只读根 fs）
    run_event_loop();
}
```

设备返厂日志里能看到的只有 `dmesg` 那一行。开发在办公室怎么都复现不出来，运维凌晨守机器守到崩溃：**这就是嵌入式调试的常态——你不在现场，现场也不留证据。**

### 1.2 顺藤摸到根因

问题不在这段代码本身，而在**"没有现场"**：

- `ulimit -c 0`，崩溃没落 core；
- `core_pattern = "core"`，就算落 core 也写到只读根 fs 上被丢；
- release 版 `-O2 -g0`，符号被 strip，就算拿到 core 也看不懂；
- 白天复现不了，因为白天 `on_timeout` 触发得少，晚上心跳超时高发；
- 应用没装 SIGSEGV handler，也没 minidump 上报，云端只知道"设备重启了"。

代码里藏的 bug 只是"use-after-realloc（cap 增长但 buf 没扩）"，真正贵的是**发现它需要三周**。

### 1.3 我们要回答什么

- CoreDump 为什么落不下来？怎么在只读根文件系统上留现场？ → §3.1 / §3.2
- 拿到 core，六步就能定位到崩溃行吗？ → §3.3
- gdbserver 怎么跨 x86 主机调 ARM 板？sysroot 是干嘛的？ → §4.1 / §4.3
- ASan 交叉编译要不要静态链？开销大到什么程度？ → §5.2 / §5.3
- strip 之后还想看栈，怎么办？build-id 靠谱吗？ → §6.1 / §6.2
- 三板斧到底是并列关系还是有先后？先用哪个？ → §7.2 / §8.2

## 2. 调试体系概览

### 2.1 三板斧的分工

调试问题分两类：**能复现**与**不能复现**。三板斧覆盖两条线：

```
      ┌────────────────────────────────────────────────┐
      │              嵌入式调试三板斧                    │
      ├─────────────────┬─────────────────┬────────────┤
      │  事后（不复现）  │  在线（可复现）  │  预防      │
      │  CoreDump       │  GDB / gdbserver│  ASan/UBSan│
      │                 │                 │            │
      │  留下现场        │  搭桥单步       │  提前引爆   │
      └─────────────────┴─────────────────┴────────────┘
```

一句话总结三板斧：**"CoreDump 抓尸体、GDB 现场急救、ASan 例行体检。"**

- CoreDump 是最便宜的现场：什么都不做，只要配好就能自动留。
- GDB 是最贵的现场：需要有人、有连接、能复现。
- ASan 是最主动的检查：在 QA 阶段跑一遍，把 UAF/OOB 提前引爆。

### 2.2 为什么是这三板

历史上有更多工具（strace/ltrace/perf/eBPF/rr/lldb），但嵌入式落地场景卡了两个硬约束：

- **设备资源有限**：valgrind 挂载 memcheck 慢 20 倍，直接压垮 CPU；rr 依赖硬件性能计数器，多数 ARM SoC 不支持。
- **调试不在开发机**：崩溃发生在客户现场，能带回来的只有 core、log、上报数据。

于是**CoreDump 是嵌入式默认交付项**（必须开），GDB 是**灰度/复测阶段的现场武器**，ASan 是**出厂前的例行 CI**。剩下的都是锦上添花。

## 3. CoreDump 事后现场

### 3.1 core_pattern 与 filter

`/proc/sys/kernel/core_pattern` 决定 core 落到哪里、叫什么名。**默认 `"core"` 一定要改**——它会写在进程 cwd 下，嵌入式常常 cwd 是只读根 fs，写不进就直接丢。

推荐两种落法：

```bash
# 方案 A：落到可写分区，带时间戳、pid、可执行名
echo '/data/core/core-%e-%p-%t' > /proc/sys/kernel/core_pattern

# 方案 B：管道给 systemd-coredump（发行版通用）
echo '|/lib/systemd/systemd-coredump %P %u %g %s %t %c %h' > /proc/sys/kernel/core_pattern
```

`%e/%p/%t/%s/%c` 是占位符，分别是**可执行名、pid、时间戳、信号、rlimit**。**建议一律带上时间戳**，不然多次崩溃会互相覆盖。

`coredump_filter` 决定 core 里包含哪些内存区，`0x33` 是常用值——**包含匿名私有/共享、文件私有映射，但不包含大页与文件共享**。全 dump（`0xff`）在 4GB 应用上会生成 4GB core，落盘 30 秒还没结束，进程重启窗口都过了。

### 3.2 systemd-coredump 与 ulimit

即使 `core_pattern` 配好了，还要过两道闸：

- `ulimit -c` 或 `RLIMIT_CORE` 大于 0；
- `/proc/<pid>/coredump_filter` 允许写。

嵌入式常见的坑是**systemd unit 里 `LimitCORE=` 没设**，导致业务进程的 rlimit 依然是 0：

```ini
# gateway.service —— 一定要有这两行
[Service]
LimitCORE=infinity
Environment=ASAN_OPTIONS=abort_on_error=1:disable_coredump=0
```

`disable_coredump=0` 是给 ASan 用的——**ASan 默认关闭 core**，因为它自己会打印栈；但联合调试时希望两个都留。

如果用 `systemd-coredump`，别忘了配 `/etc/systemd/coredump.conf`：`Storage=external`、`Compress=yes`、`MaxUse=200M`，防止 core 撑爆分区。

### 3.3 gdb 分析 core 的六步法

拿到 core 后**别急着 `bt`**。按这个顺序走一遍，90% 崩溃 5 分钟能定位：

```gdb
# 第 1 步：加载二进制与 core，注意用带 -g 的原版可执行
(gdb) file ./gateway.debug
(gdb) core-file ./core-gateway-1234-1690000000

# 第 2 步：看信号与崩溃线程
(gdb) info signal              # 确认是 SIGSEGV / SIGABRT
(gdb) info threads             # 找到 *星号所在线程

# 第 3 步：看栈，先粗后细
(gdb) bt
(gdb) bt full                  # 带局部变量，判断是不是空指针

# 第 4 步：跳到崩溃帧，看寄存器与源码
(gdb) frame 2
(gdb) info registers
(gdb) list                     # 看源码上下文

# 第 5 步：看变量与内存
(gdb) print s                  # 结构体全貌
(gdb) print *s                 # 追指针
(gdb) x/32b s->buf             # 看这段内存内容

# 第 6 步：多线程时逐个线程看栈
(gdb) thread apply all bt
```

**"崩在 memcpy 里 buf=NULL 或 buf=0x1"** 是 90% UAF/野指针的模样。若 `bt` 显示 `??`，是符号丢了，跳到 §6.2 用 build-id 找 debuginfo。

## 4. GDB 远程调试

### 4.1 gdbserver 与 gdb-multiarch

板子端跑 `gdbserver`，主机端跑 `gdb-multiarch`（或对应 triplet 的 `arm-linux-gnueabihf-gdb`），中间走 TCP：

```bash
# 板端
gdbserver :1234 ./gateway

# 主机端
gdb-multiarch ./gateway
(gdb) set sysroot /opt/rootfs                     # ← §4.3 关键
(gdb) target remote 192.168.1.100:1234
(gdb) continue
```

也可以 attach 已经在跑的进程：`gdbserver :1234 --attach $(pidof gateway)`，用于**在线不停机排查**。attach 期间业务是 stop 状态，看门狗会把你踹掉——先 `systemctl stop watchdog` 或临时增大 timeout。

### 4.2 断点、条件与多线程

- **条件断点**只在需要的路径上停：`break on_data if s->cap > 4096`。避免每次进来都断，能省 90% 的走路时间。
- **函数返回值断点**：`finish` 停在当前函数返回时，看返回值。
- **多线程调度锁**：`set scheduler-locking on`，让 `next/step` 只推进当前线程，避免其他线程"跑掉"。默认 off 会导致你 `next` 一次跳过 3 层调用栈。
- **反向执行（可选）**：`record`/`reverse-next`，ARM Cortex-A 上多数不支持，x86 QEMU 里好用。

### 4.3 sysroot 与符号加载

跨平台调试最容易踩的坑是**共享库找不到**。板子上的 libc.so.6、libstdc++.so.6 与主机上的完全不是一个东西，`bt` 会全是 `??`。

解法：**把板子的整个根文件系统拉到主机**（或者用编译时的 sysroot），然后：

```gdb
(gdb) set sysroot /opt/rootfs
(gdb) set solib-search-path /opt/rootfs/usr/lib
(gdb) show sysroot
```

之后 `sharedlibrary` 会自动去 `/opt/rootfs/lib/...` 找 `.so` 与 `.so.debug`。**推荐把 `set sysroot` 写进 `~/.gdbinit`**：

```gdb
# ~/.gdbinit
set print pretty on
set print array on
set print elements 200
set history save on
set confirm off
set sysroot /opt/rootfs
define bta
  thread apply all bt full
end
```

`bta` 是自定义命令，一键打印所有线程的 full backtrace，crash 现场的第一句。

## 5. ASan 内存杀手

### 5.1 ASan 的三类命中

AddressSanitizer 是 gcc/clang 自带的**运行时内存检查器**，在编译期插桩、运行期检测。它主要命中三类问题：

- **heap-buffer-overflow / stack-buffer-overflow**：越界读写，就是 §1.1 那种 `cap` 变了 `buf` 没扩的经典 UAR（use-after-realloc）。
- **use-after-free / double-free**：释放后再用、重复释放。释放时 ASan 把这块地址标为"毒页"，再访问立即抛。
- **memory leak**：进程退出时检查未释放的堆块，`LeakSanitizer` 是 ASan 的一部分。

ASan 命中会打印**分配栈 + 释放栈 + 触发栈**三条栈，这是它比 GDB 强的地方——GDB 只能看当前栈，看不到"这块内存是谁在什么时候释放的"。

### 5.2 交叉编译下的链接姿势

交叉编译时，`-fsanitize=address` 需要链接 `libasan.so`，这个库要么打进 rootfs，要么静态链接。**静态链是嵌入式常见做法**：

```cmake
# CMakeLists.txt —— 只在 Debug 或专用配置里开
option(ENABLE_ASAN "Enable AddressSanitizer" OFF)
if(ENABLE_ASAN)
  add_compile_options(-fsanitize=address -fno-omit-frame-pointer -O1 -g)
  add_link_options(-fsanitize=address -static-libasan)
endif()
```

**注意事项**：

- `-fno-omit-frame-pointer` 必开，否则栈回溯全是 `??`。
- `-O1` 而不是 `-O0`：完全关优化会让 ASan 报很多"编译器优化能消掉的假越界"。
- `-static-libasan` 让 libasan 静态进 elf，避免板子上没这个 so。
- glibc 与 musl 都支持，但 musl 版本要 ≥ 1.2，老的 musl 缺 `__libc_freeres` 会挂。

运行时用 `ASAN_OPTIONS` 精调：

```bash
ASAN_OPTIONS=abort_on_error=1:halt_on_error=1:detect_leaks=1:print_stacktrace=1 ./gateway
```

`abort_on_error=1` 让 ASan 崩溃时同时落 core，联动 §3 就是三板斧闭环。

### 5.3 性能开销与灰度策略

ASan 的常见开销：

| 指标 | 开销 |
|------|------|
| CPU | ×2 ~ ×3 |
| 内存 | ×2 ~ ×3（影子内存）|
| 二进制大小 | +30% |
| 启动时间 | +100~500ms |

**结论**：ASan 版本不能直接发到量产，但**可以在灰度/预生产灰度机器上长跑**。策略是：

- CI 每次 PR 跑一遍 ASan 单元测试（快速回归）；
- QA 有 2~5 台设备常年跑 ASan 版本（拦截长期泄漏）；
- 出厂固件用 Release 版本（关 ASan，保留 `-g` 分拆到 debuginfo）。

## 6. 符号与 debuginfo

### 6.1 strip 前的符号分拆

嵌入式固件要 strip，但 strip 之前必须**把符号表分拆出来**，否则 core 拿回来没法看：

```bash
# 编译时 -g，产出带调试信息的 elf
arm-linux-gnueabihf-gcc -O2 -g -o gateway gateway.c

# 分拆：symbols 单独存档，供事后 gdb 使用
objcopy --only-keep-debug gateway gateway.debug
objcopy --strip-debug     gateway
objcopy --add-gnu-debuglink=gateway.debug gateway

# 现在 gateway 里只留符号表引用（build-id + 文件名），瘦身完成
# gateway.debug 上传到符号服务器 / 归档
```

分拆后**部署 gateway 到设备，gateway.debug 归档保存**。crash 后拉回 core，主机端只要 gateway.debug 就能完整 bt。

### 6.2 build-id 与 debuginfo 匹配

`--add-gnu-debuglink` 依赖 build-id：链接时 `-Wl,--build-id=sha1` 会往 elf 里写一段 hash，`gateway` 与 `gateway.debug` 的 build-id 相同，gdb 才认。

```bash
readelf -n gateway | grep 'Build ID'
# Build ID: a1b2c3d4e5f6...
```

**版本管理建议**：以 build-id 为文件名归档 debuginfo：

```
/opt/symbols/a1/b2c3d4e5f6....debug     ← 与 /usr/lib/debug/.build-id/ 结构一致
```

gdb 默认会去 `/usr/lib/debug/.build-id/xx/yyyyyy.debug` 找，主机端搭一个软链或改 `debug-file-directory` 即可批量对接：

```gdb
(gdb) set debug-file-directory /opt/symbols
```

### 6.3 minidump 与远程上报

core 平均 20~200MB，无法通过 4G 回传。产线通常用 **minidump（breakpad/crashpad）**：

- 只保留栈内存、寄存器、模块列表，通常 20~200KB；
- 应用启动时装 signal handler，SIGSEGV/SIGABRT 时写 minidump 到 `/data/crash/`；
- 后台脚本压缩 + 加密 + 上传，配合服务端 `minidump_stackwalk` 解出栈。

minidump 的关键前提：**服务端要有 build-id 对应的 symbols**——所以 §6.1 的分拆必须做，不然 crash 报了也看不懂。

## 7. 三板斧联动

### 7.1 现场分类：能复现与不能复现

拿到"设备崩溃"报告时先分类：

```
                能复现？
                  │
        ┌─────────┴─────────┐
        是                   否
        │                    │
   ASan 复测        CoreDump 已有？
   ↓                    │
   命中：改代码     ┌────┴────┐
   未命中：GDB       是       否
                    │        │
                看栈定位    加装 core/minidump
                            重新等一次现场
```

**"没有 core，就没资格谈调试"**——这是嵌入式的第一定律。所以三板斧的第一件事永远是**把 core/minidump 配好**。

### 7.2 CoreDump → ASan → GDB 的闭环

现场闭环流程（也是 §10.2 的骨架）：

```
[1] 设备 crash → 落 core / minidump
[2] 拉回 core + gateway.debug → gdb bt 定位崩溃函数
[3] 崩溃函数 = 内存访问？ → ASan 版本本地复现
[4] ASan 命中 → 三条栈（分配/释放/触发）指向根因
[5] 修完 → GDB 单步走一遍确认路径
[6] 加单测 → CI 长期跑 ASan 拦截回归
```

**"CoreDump 定位到函数 → ASan 定位到指令 → GDB 定位到修复路径"**——三板斧不是并列，是流水线。

## 8. 选型决策树

### 8.1 五个维度

选择用哪一"斧"，看五个问题：

- **能不能复现**：能 → GDB / ASan；不能 → CoreDump。
- **在客户现场还是研发现场**：客户 → CoreDump/minidump；研发 → GDB。
- **CPU/内存余量**：紧 → CoreDump；宽 → ASan 长跑。
- **可交付性**：出厂固件必须 Release，不能带 ASan。
- **崩溃频次**：常态崩 → 加 ASan 兜底；偶发崩 → CoreDump 蹲守。

### 8.2 一张图选完

```
                    崩溃发生
                       │
              ┌────────┴────────┐
           能复现？             不能复现？
              │                    │
        ┌─────┴─────┐          有 core？
       是            是         │
       │            │      ┌────┴────┐
   内存问题?    非内存    有         无
       │           │      │          │
      ASan       GDB    gdb 分析   立刻装
      三条栈     单步   六步法      core/mdump
       │           │      │       重现等待
       └───────────┴──────┘
                   │
              修复 + 单测
                   │
              CI 跑 ASan 回归
```

### 8.3 常见误用

- **只开 GDB 不开 CoreDump**：能远程 attach 的问题 90% 不用 GDB 也能查；不能 attach 的问题 GDB 也没辙。**主次颠倒**。
- **ASan 直接开到生产**：ASan 内存翻倍，嵌入式跑几个小时 OOM。灰度可以，量产不行。
- **strip 后才想起没留符号**：`bt` 全 `??`，只能重新出版本复现。**先分拆再 strip**。
- **`ulimit -c 0` 忘了改**：core 落不下来，白配 `core_pattern`。
- **core 落到只读分区**：进程崩溃时写文件失败，内核放弃。落盘目录必须可写、有余量。

## 9. 可靠性与调试

### 9.1 崩溃排查 SOP

设备现场崩溃报警后，10 分钟内应该走完：

```bash
# 1. 拉回 core 与日志
scp root@dev:/data/core/core-* .
scp root@dev:/var/log/messages .

# 2. 匹配版本，找到对应 debuginfo
readelf -n core-gateway-* | grep 'Build ID'
# → a1b2c3... → 找到 gateway.debug.a1b2c3

# 3. gdb 六步法
gdb ./gateway
(gdb) core-file core-gateway-*
(gdb) bta                 # 见 §4.3，自定义命令
(gdb) frame N             # 跳到业务代码帧
(gdb) print /x variables

# 4. 结论：崩在 memcpy(NULL, ...) → 空指针
#         调用者：on_data，传入 s->buf=NULL
#         上一步：on_timeout 释放并置 NULL
# 5. 找到时序：定时器与数据回调竞争 → 加锁 or 状态机
```

上述过程**能走完，说明第 3~6 章都配到位了**——core、symbols、sysroot、debuginfo 一个不缺。

### 9.2 无 core 现场怎么办

有时候第一时间没配 core，客户又不给再来一次的机会。备选：

- **看 dmesg / journal**：`segfault at 0 ip 0x... error 4 in gateway[...+0x1234]`——`0x1234` 是崩溃指令在 elf 中的偏移。
- **用 `addr2line` 反查行号**：`addr2line -e gateway.debug -f -C 0x1234` → 精确到源码函数+行号。
- **用 objdump 看反汇编**：`objdump -d gateway | grep 1234:` 看崩溃前后几条指令，反推是哪个变量的引用。
- **反查前置日志**：应用日志里"崩溃前最后一条"往往锁定业务路径，`journalctl _COMM=gateway --since "5 min ago"`。

`addr2line` 这条链路是"没 core 时的救命稻草"——**只要留了 debuginfo，就能从 dmesg 一行错误里还原行号**。

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到 §1.1 的代码，逐行标注对应章节：

```c
struct session {
    int  fd;
    char *buf;                // ← §5.1 heap-buffer-overflow 的种子
    size_t cap;
};

static void on_timeout(struct session *s) {
    free(s->buf);             // ← §5.1 ASan 三条栈里的"释放栈"
    s->buf = NULL;
}

static void on_data(struct session *s, const char *p, size_t n) {
    if (n > s->cap) s->cap = n;    // ← §5.1 UAR 的病根：只更新 cap
    memcpy(s->buf, p, n);          // ← §3.3 gdb bt 停在这里，s->buf=NULL
}
```

**真相**：`on_timeout` 与 `on_data` 存在竞争，事件循环单线程本不会撞车，但**定时器回调与 socket 读回调在同一循环里排队**，`on_timeout` 先释放 `buf` 置 NULL 后，紧跟的 `on_data` 直接踩 NULL。

修复只需两行：**要么 `on_timeout` 后把 session 从表里摘掉**，要么 **`on_data` 前判空并按新 `cap` 重新分配**——业务层选后者。

真正贵的是**发现它需要三周**：如果 core、symbols、ASan 三件套齐了，10 分钟就能定位。

### 10.2 一次崩溃定位的一生

```
[T0]  设备崩溃                                   ← §1.1 现场
       │
       │  kernel 打印 segfault → dmesg
       │  按 core_pattern 生成 core-gateway-...   ← §3.1
       │  ulimit=infinity 允许落盘               ← §3.2
       │
[T1]  systemd 拉起 gateway 重启（Restart=on-failure）  ← 第 07 篇
       │
[T2]  云端收到 crash 上报（minidump）             ← §6.3
       │
[T3]  运维/研发用 rsync 把 core + logs 拉回主机
       │
[T4]  主机 gdb 加载：file gateway.debug           ← §6.1
       │  build-id 匹配 → 符号完整                ← §6.2
       │  bta 打印所有线程栈                       ← §4.3
       │  frame N → 定位到 memcpy(NULL, ...)      ← §3.3
       │
[T5]  ASan 版本本地跑压测                          ← §5.2
       │  命中 heap-use-after-free
       │  分配栈 / 释放栈 / 触发栈 三线合璧          ← §5.1
       │
[T6]  改代码 → gdbserver attach 单步验证           ← §4.1
       │
[T7]  CI 加回归用例（ASan long-run）              ← §5.3
       │
[T8]  灰度发布 → 生产观察 7 天 → 全量
```

一次崩溃从"看不懂"到"改完上线"，工具链每一环都不能缺。

### 10.3 设计哲学回扣

- **"没有现场，就没资格谈调试"**：CoreDump 是嵌入式默认交付项，和 log/watchdog 同级。任何新固件出厂前，第一条检查项就是"崩一次能不能落 core"。
- **"符号是 debuginfo 的护照"**：strip 之前必须分拆并归档，用 build-id 建索引。debuginfo 不归档等于事后无救。
- **"防御性调试代替防御性代码"**：不要每个函数加一堆 `assert(ptr != NULL)`，那是掩盖问题。让 ASan 在 QA 阶段替你 assert，生产代码保持简洁。
- **"三板斧是流水线，不是选择题"**：CoreDump 定位到函数、ASan 定位到指令、GDB 定位到修复路径——顺序执行，各司其职。

### 10.4 调试三板斧速查

| 场景 | 首选工具 | 关键命令 / 配置 |
|------|----------|-----------------|
| 客户现场崩溃 | CoreDump + minidump | `core_pattern`、`LimitCORE=infinity` |
| 研发现场偶发 | gdbserver attach | `gdbserver :1234 --attach $(pidof x)` |
| 内存越界/UAF | ASan | `-fsanitize=address -static-libasan -fno-omit-frame-pointer` |
| 无 core 只有 dmesg | addr2line | `addr2line -e a.debug -f -C 0x1234` |
| 多线程栈 | gdb | `thread apply all bt full`（bta 别名）|
| 符号丢失 | build-id 反查 | `readelf -n core \| grep Build` |
| 崩溃回归 | CI + ASan | PR 触发 ASan 单测；QA 长跑 ASan |

**一句话建议**：**出厂前先把 `core_pattern` / `LimitCORE` / `debuginfo 归档`三件套配齐；再去谈 GDB 和 ASan 的花式用法。**
