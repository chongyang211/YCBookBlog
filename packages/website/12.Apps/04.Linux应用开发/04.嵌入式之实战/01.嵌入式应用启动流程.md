## 1. 案例引入

### 1.1 一段真实脚本

先看一份从真实嵌入式产品裁剪出来的启动脚本。为了聚焦原理，这里只保留最核心的骨架——每一行背后都藏着一个"为什么要这么写"的教训：

```bash
#!/bin/sh
# restart.sh —— 应用重启脚本（精简骨架）
set -e

pid_file="/tmp/palmapp.pid"
base_dir=$(cd "`dirname "$0"`" && pwd)

# 【1】判活 + 停止老进程
if "$base_dir/lockcheck" -q "$pid_file"; then
    kill "$(cat "$pid_file")" && sleep 2 || true
fi
killall palmapp 2>/dev/null || true

# 【2】拉起依赖服务
[ -f /app/palmopenkit/scripts/restart.sh ] && \
    start-stop-daemon -S -b -q --exec /app/palmopenkit/scripts/restart.sh

# 【3】切工作目录 & 启动主进程（restarter 守护 palmapp）
cd /data/palmapp/
LD_LIBRARY_PATH=$base_dir/../lib:$LD_LIBRARY_PATH \
    $base_dir/restarter -s 1 -m 30 \
    -- $base_dir/../palmapp --signal-parent 10 "$@"
```

对应的 `stop.sh`：

```bash
#!/bin/sh
set -e
base_dir=$(cd "`dirname "$0"`" && pwd)

# 先杀守护，防止它把 palmapp 再拉起来
killall restarter 2>/dev/null || true

# 再杀本体
if "$base_dir/lockcheck" -q /tmp/palmapp.pid; then
    kill "$(cat /tmp/palmapp.pid)" || true
fi
killall palmapp 2>/dev/null || true
```

**现象**：脚本每天在设备上执行几次，一年下来运行几十万次，绝大多数情况下都工作良好。但偶尔会出现几个令人抓狂的怪现象：

- **进程僵尸**：`ps` 看不到 `palmapp`，但 `/tmp/palmapp.pid` 还在，下次 restart 报"PID file locked"
- **双开**：两个 `palmapp` 同时跑起来，日志文件互相覆盖
- **打不死**：`kill` 完还在跑，只能 `kill -9`
- **重启风暴**：`palmapp` 崩溃后 `restarter` 在 1 秒内拉起来 200 次，把设备烤发烫
- **依赖竞态**：`palmopenkit` 还没起来，`palmapp` 已经在读它的 socket

### 1.2 顺藤摸到根因

带着这些现象往下挖：

- **假设 1**：`kill` 完为什么还有残留？—— 因为主进程有子线程 / 子进程，`kill $pid` 只发给主进程，孤儿进程还在跑。→ 这引出**进程组 & 信号传播**。
- **假设 2**：PID 文件谁写的，谁清？—— 是被守护的进程自己写、进程退出时应该清；但如果它被 `kill -9`，写入了 PID 但没来得及清，就会留下"僵尸 PID 文件"。→ 这引出**文件锁 vs 简单 PID 文件**的差异。
- **假设 3**：`restarter` 是干嘛的？—— 一个外挂守护，让 palmapp 挂了自动拉起来，`-s 1` 是"重启间隔至少 1 秒"，`-m 30` 是"30 秒内重启超过 N 次就放弃"。这是**崩溃重启的节流保护**。
- **假设 4**：`--signal-parent 10` 是什么？—— palmapp 就绪之后主动给父进程发 `SIGUSR1`（10 号信号）表示"我起来了"，父进程收到才认为启动成功。这是**双向就绪协商**。
- **假设 5**：`LD_LIBRARY_PATH=$base_dir/../lib` 为什么必须这样写？—— 嵌入式设备没有 `/usr/local/lib` 这些标准路径，应用的 `.so` 全塞在自己目录下，运行时要显式告诉动态链接器去哪找。→ 这引出**运行时链接**。
- **假设 6**：为什么先干 `restarter` 再干 `palmapp`？—— 顺序反了，`restarter` 会立刻把 `palmapp` 再拉起来，脚本永远杀不干净。→ 这引出**停止时序的依赖反演**。

一段 20 行的脚本，藏着 6 个原理点：

```
① 嵌入式应用是被谁拉起来的？从上电到 main() 全流程？   → 第 3 章
② PID 文件为什么要配合文件锁（lockcheck）而不是裸用？ → 第 4 章
③ restarter / start-stop-daemon 到底做了什么？        → 第 5 章
④ kill / killall / --signal-parent 的信号语义？       → 第 6 章
⑤ LD_LIBRARY_PATH、base_dir、工作目录的作用？          → 第 7 章
⑥ 停止时为什么"先杀守护再杀本体"？重启为什么"先停再启"？ → 第 9 章
```

## 2. 架构概览

### 2.1 三段式生命周期

一个嵌入式应用完整生命周期，可以切成三段：**启动前 → 运行中 → 停止时**。每段都有自己的关键动作和典型坑：

```
┌───────────────────────────────────────────────────────────────┐
│                    嵌入式应用生命周期                            │
│                                                                │
│  ┌─────────────┐    ┌──────────────┐    ┌─────────────┐       │
│  │  启动阶段    │───►│  运行阶段     │───►│  停止阶段    │       │
│  │  (Startup)  │    │  (Runtime)   │    │  (Shutdown) │       │
│  └──────┬──────┘    └──────┬───────┘    └──────┬──────┘       │
│         │                  │                    │              │
│         ▼                  ▼                    ▼              │
│  1. Bootloader        1. 主循环处理        1. 收到信号         │
│  2. 内核启动          2. 崩溃 → 守护拉起    2. 释放资源         │
│  3. init 系统         3. 依赖服务通信      3. 清 PID 文件      │
│  4. 拉起 restarter    4. 心跳/看门狗       4. 通知父进程        │
│  5. 拉起 palmapp                                              │
│  6. --signal-parent 就绪                                      │
└───────────────────────────────────────────────────────────────┘
```

**三段各自的产物**：

| 阶段 | 关键动作 | 常见坑 | 我们脚本里的对应 |
|---|---|---|---|
| 启动阶段 | 拉起进程、加载动态库、就绪通知 | 依赖没起完就跑，`.so` 找不到 | `restarter → palmapp`、`LD_LIBRARY_PATH` |
| 运行阶段 | 崩溃拉起、防止双开、健康监控 | 双开覆盖数据、重启风暴 | `lockcheck`、`restarter -s 1 -m 30` |
| 停止阶段 | 反向依赖、优雅退出、清理资源 | 顺序反了杀不干净、留下僵尸 PID | `killall restarter` 先于 `kill $pid` |

### 2.2 为什么这么切

为什么把生命周期切成三段而不是"启动 + 停止"两段？

**疑惑**：直接把"运行中"合并到"启动完成"里不行吗？

**论证**：
1. **失败模式不同**——启动阶段崩溃是"起不来"（不影响老进程），运行时崩溃是"死了"（需要拉起接管），停止时崩溃是"关不干净"（残留僵尸）。**三种失败要三种应对**。
2. **责任主体不同**——启动阶段由脚本 / init 系统主导，运行阶段由守护进程（restarter）主导，停止阶段又回到脚本手上。**责任交接的边界就是段的边界**。
3. **观测手段不同**——启动阶段看串口日志和 dmesg，运行阶段看应用日志和 top，停止阶段看是否有残留进程。**观测工具的切换就是段的切换**。
4. 反向验证：如果不分段，一段 shell 脚本要同时管"启动、监控、停止"——这就是很多小项目最终跑不稳的根本原因，因为**一段脚本无法既是启动者又是守护者**（脚本退出后守护就没了）。

**结论**：三段式不是形式主义，是把"责任、观测、失败模式"三个正交维度同时编码进生命周期——每段一种角色、一套工具、一种典型故障。这就是我们脚本里 `start-stop-daemon`（启动）、`restarter`（运行）、`lockcheck + killall`（停止）三件工具各司其职的根本原因。

下面从"应用被谁拉起来的"开始。


## 3. 从上电到init

### 3.1 Bootloader阶段

**疑惑**：设备上电到 `palmapp` 跑起来，中间到底发生了什么？

**论证**：完整链路是 **上电 → Bootloader → Kernel → init → 应用**。

```
┌──────────┐  0.1s   ┌───────────┐  1~5s   ┌────────┐  3~10s   ┌──────────┐
│   上电    │─────►  │ Bootloader│─────►   │ Kernel │────────► │  init    │
│  Power   │        │  (U-Boot) │         │(Linux) │          │(systemd/ │
└──────────┘        └───────────┘         └────────┘          │ BusyBox) │
                                                              └────┬─────┘
                                                                   │
                                                                   ▼
                                                          ┌────────────────┐
                                                          │  restart.sh    │
                                                          │  ↓             │
                                                          │  restarter     │
                                                          │  ↓             │
                                                          │  palmapp       │
                                                          └────────────────┘
```

Bootloader（大部分嵌入式设备用 U-Boot）的三个核心职责：

| 职责 | 具体做什么 |
|---|---|
| 硬件初始化 | 时钟、DDR、Flash 控制器、串口 |
| 内核加载 | 从 Flash / SD / 网络把 zImage 读到 DDR |
| 参数传递 | 把 `bootargs`（如 `root=/dev/mmcblk0p2 console=ttyS0,115200`）传给内核 |

一个典型 U-Boot 环境变量：

```bash
=> printenv
bootargs=console=ttyS0,115200 root=/dev/mmcblk0p2 rootwait rw
bootcmd=mmc read 0x80000000 0x800 0x4000; bootz 0x80000000
```

**常见坑**：`bootargs` 写错（root 指向不存在的分区）→ 内核起来但找不到 rootfs → 输出 `VFS: Unable to mount root fs on unknown-block(0,0)` → 直接 panic。

### 3.2 内核解压启动

内核启动的关键节点（从 dmesg 看）：

```
[    0.000] Booting Linux on physical CPU 0x0
[    0.100] Linux version 5.10.x (gcc ...) 
[    0.500] Kernel command line: console=ttyS0,115200 root=/dev/mmcblk0p2 rw
[    1.200] Freeing unused kernel memory
[    1.300] Run /sbin/init as init process        ← 关键：内核结束，用户态开始
```

内核最后一步是 `run_init_process("/sbin/init")`——把控制权交给用户态第一个进程（PID 1）。

**常见问题**：
- 内核找不到 `/sbin/init` → 恐慌 `No init found. Try passing init= option to kernel.`
- 应对：`bootargs` 里加 `init=/bin/sh` 应急，先进 shell 再修

### 3.3 rootfs与init

用户态第一个进程 PID 1 是所有其他进程的祖先。嵌入式常见的三种实现：

| init 实现 | 特点 | 典型场景 |
|---|---|---|
| systemd | 功能全、依赖管理、并行启动、日志集成 | Ubuntu Core、多数商用 Linux 板 |
| BusyBox init | 极简、读 `/etc/inittab` 顺序执行 | 极小 rootfs、路由器、消费电子 |
| 自定义 shell 脚本 | 完全可控、极致启动速度 | 车载仪表、专用设备 |

我们脚本里的 `palmapp` 是被 `restart.sh` 拉起来的。那 `restart.sh` 又是谁拉起来的？往上翻——通常是这三种之一：

```
BusyBox init  →  /etc/inittab  →  ::respawn:/app/palmapp/scripts/restart.sh
systemd       →  /etc/systemd/system/palmapp.service  →  ExecStart=.../restart.sh
自定义脚本    →  /etc/init.d/rcS  →  /app/palmapp/scripts/restart.sh &
```

**用 systemd 的等价 unit**（作为对照）：

```ini
[Unit]
Description=Palm App Service
After=network-online.target palmopenkit.service
Wants=network-online.target
Requires=palmopenkit.service

[Service]
Type=notify
ExecStart=/app/palmapp/scripts/restart.sh
Restart=on-failure
RestartSec=1s
StartLimitBurst=30
StartLimitIntervalSec=60

[Install]
WantedBy=multi-user.target
```

这个 unit 里的 `RestartSec=1s` 对应脚本里 `restarter -s 1`，`StartLimitBurst=30` 对应 `-m 30`——**systemd 内置的能力，我们的 restarter 用 20 行 C 代码实现了**。为什么不用 systemd？因为很多老平台的 BusyBox 里没有。

### 3.4 应用被拉起时

到了 `palmapp` 真正被拉起来的这一刻，它面对的运行环境是这样的：

```
palmapp 起来时看到的世界：
┌──────────────────────────────────────────┐
│ 父进程       : restarter (PID 1234)       │
│ PPID         : restarter 的 PID           │
│ 工作目录     : /data/palmapp/  ← cd 过来的 │
│ 环境变量     :                            │
│   LD_LIBRARY_PATH=/app/palmapp/lib:...   │
│   PATH=/usr/bin:/bin (系统默认)            │
│   HOME=/ (init 环境)                      │
│ 命令行参数   : --signal-parent 10 [其他]  │
│ 打开的 FD    : 0/1/2（继承自 restarter）   │
│ 信号掩码     : 继承自父，通常没屏蔽任何信号   │
│ ulimit       : 继承自 shell 的默认限制     │
└──────────────────────────────────────────┘
```

`palmapp` 拿到这些之后要做的事：

1. **加锁**：`open("/tmp/palmapp.pid", O_CREAT|O_RDWR) + flock(fd, LOCK_EX|LOCK_NB)`——防止双开
2. **写 PID**：`write(fd, "1235\n", 5)`——为 stop.sh 提供杀入口
3. **初始化子系统**：日志、配置、IPC、UI...
4. **就绪通知**：所有初始化完成后，`kill(getppid(), SIGUSR1)`——告诉 restarter"我起来了"
5. **进入主循环**：epoll_wait / QApplication::exec() / while(1)...

`--signal-parent 10` 就是让 palmapp 在第 4 步给父进程发**第 10 号信号**（SIGUSR1）——这是双向就绪协商，第 6 章细讲。


## 4. PID文件与锁

### 4.1 单实例的必要

**疑惑**：为什么一定要防止双开？多起几个不好吗？

**论证**：嵌入式设备的资源是稀缺的、独占的——

1. **硬件设备独占**：`/dev/video0`、`/dev/input/event0`、GPIO、串口。同一时刻只能有一个进程打开。
2. **端口独占**：绑定的 TCP/UDP 端口，第二个进程 bind 会 `EADDRINUSE`。
3. **日志覆盖**：两个进程往同一个日志文件写，交错乱序，事后无法追溯。
4. **配置文件**：两个进程同时读写 `/data/config.json`，写入互相覆盖，数据损坏。
5. **消息总线冲突**：Unix Domain Socket 或 D-Bus 名字唯一，第二个来会失败或抢占。

所以**单实例**是嵌入式应用的默认要求。实现它有三种方式：

| 方式 | 原理 | 缺点 |
|---|---|---|
| 检查 PID 文件是否存在 | `[ -f /tmp/palmapp.pid ] && exit` | 崩溃残留会误判 |
| ps 查有没有同名进程 | `pidof palmapp` | 有短暂窗口双开、进程改名会漏 |
| **文件锁（推荐）** | `flock` 绑定进程生命周期，退出自动释放 | 需要小工具支持 |

我们的脚本用的是**第三种**：`lockcheck` 就是文件锁的检查工具。

### 4.2 flock文件锁

Linux 提供 `flock(2)` 系统调用来加文件锁：

```c
#include <sys/file.h>
int fd = open("/tmp/palmapp.pid", O_CREAT | O_RDWR, 0644);
if (flock(fd, LOCK_EX | LOCK_NB) == 0) {   // 拿到锁
    ftruncate(fd, 0);
    dprintf(fd, "%d\n", getpid());
    // fd 保持打开——进程一直持有锁
    // 进程退出（正常/崩溃/kill）时，内核会自动释放锁
} else {
    // 锁被占，说明已经有实例在跑
    fprintf(stderr, "already running\n");
    exit(1);
}
```

**关键性质**（"疑惑—论证—结论"）：

**疑惑**：为什么 `flock` 比"检查 PID 文件是否存在"可靠？

**论证**：
1. `flock` 与**进程生命周期绑定**——进程死了（无论是 exit / SIGSEGV / SIGKILL），内核在 `do_exit` 里遍历 fd 表调用 `flock_release`，锁自动释放。
2. "PID 文件是否存在"不与进程绑定——进程 `kill -9` 后 PID 文件残留在磁盘上，下次启动误判为"还在跑"。
3. `flock` 还支持 `LOCK_NB`（非阻塞）——立刻失败或立刻成功，不会阻塞脚本。
4. flock 是**建议性锁**（advisory）——只有主动检查锁的进程才受影响，不影响不检查的进程。这对我们够用。

**结论**：`flock` 把"检测活着"这件事从"用户态启发式判断"降级为"内核事实"——只要进程活着，锁就活着；进程一死锁就没了。这是**用内核作为事实源**的经典模式。

### 4.3 lockcheck的原理

`lockcheck -q /tmp/palmapp.pid` 做的事非常简单：

```c
// lockcheck.c，一个 <30 行的小工具
int main(int argc, char** argv) {
    int quiet = 0, i = 1;
    if (argc > 1 && strcmp(argv[1], "-q") == 0) { quiet = 1; i++; }
    if (i >= argc) return 2;

    const char* path = argv[i];
    int fd = open(path, O_RDONLY);
    if (fd < 0) {
        if (!quiet) fprintf(stderr, "no such file\n");
        return 1;   // 文件都没有 → 一定没在跑
    }
    // 尝试非阻塞加共享锁——如果拿到锁，说明没人持有独占锁 → 没在跑
    if (flock(fd, LOCK_SH | LOCK_NB) == 0) {
        flock(fd, LOCK_UN);
        return 1;   // 未锁 → 没在跑
    }
    return 0;       // 锁不上 → 已在跑
}
```

**返回值语义**（脚本用 `if` 判断）：

- **返回 0**：文件被锁 → **在跑** → `if` 分支进入 → 去 kill 它
- **返回 1**：文件没锁或不存在 → **没在跑** → `else` 分支

回看脚本：

```bash
if "$base_dir/lockcheck" -q "$pid_file"; then
    pid=$(cat "$pid_file")
    echo "Stopping process with PID $pid"
    kill "$pid" && sleep 2 || true
else
    echo "PID file $pid_file not locked. Process may not be running."
fi
```

**为什么读 PID 之前不检查文件内容是否合法？**——因为**锁在，进程就一定在**（第 4.2 结论），PID 文件的内容一定是有效的。这是靠内核事实做的信任推导。

### 4.4 PID竞争与残留

**疑惑**：`kill $pid && sleep 2` 之后还需要 `killall palmapp` 兜底吗？

**论证**：
1. `kill $pid` 只对**主进程**有效。如果 palmapp 有子进程（用了 `fork` 或 `system`），子进程会成为孤儿被 init 接管。
2. `kill` 是异步的——发完信号立刻返回，进程可能还在处理。`sleep 2` 是给进程 2 秒收尾时间。
3. 但如果进程处理 SIGTERM 慢（比如它正在 `write` 一个大文件），2 秒不够——它还没死。
4. `killall palmapp` 用**进程名**扫全表，把所有还活着的、名字叫 palmapp 的进程干掉。
5. 再检查一次：还有？—— `killall -9 palmapp` 硬杀。

**PID 复用陷阱**：Linux 的 PID 是循环使用的（32 位系统上通常 32768 后回绕）。有极小概率：

```
palmapp（PID 1234）崩溃了
系统很快复用 1234 给一个新起的 shell
restart.sh 读到 pid=1234 → kill 1234 → 杀错了别人！
```

这就是为什么"锁 + PID 文件"必须**同时**使用：
- 单看 PID 文件 → 有复用风险
- 单看锁 → 拿不到具体是谁在跑

组合起来："**锁还在 → 进程还在 → PID 文件里的 PID 一定就是它**"——三段推理才能安全 `kill`。

**结论**：一个看似简单的 PID 文件，背后是"内核锁 + PID 记录 + kill 兜底"的三重防线。任何一层缺失，都会在生产环境里踩坑。


## 5. 守护进程模型

### 5.1 start-stop-daemon

脚本里这一行：

```bash
start-stop-daemon -S -b -q --exec "$PALMOPENKIT"
```

`start-stop-daemon` 是 Debian 系（也在 BusyBox）里的一个"守护进程启动器"。参数含义：

| 参数 | 含义 |
|---|---|
| `-S`, `--start` | 启动模式 |
| `-b`, `--background` | 让进程在后台跑（fork 后 detach） |
| `-q`, `--quiet` | 减少输出 |
| `--exec PATH` | 要执行的程序 |

**它比 `nohup xxx &` 强在哪**？

**疑惑**：直接 `PALMOPENKIT &` 不就好了？

**论证**：
1. `xxx &` 让进程后台跑，但**session 和 tty 关联还在**——终端关闭时会收到 SIGHUP。
2. `nohup xxx &` 忽略 SIGHUP，但**没有做 fork-fork-setsid 的完整脱离**。
3. `start-stop-daemon -b` 做的是完整的**守护化流程**：
   - `fork()` 一次，父退出——子成为孤儿被 init 接管
   - `setsid()` 创建新 session，脱离 controlling terminal
   - `chdir("/")` 避免占用某个目录导致无法卸载
   - 关闭继承的 fd（0/1/2 重定向到 /dev/null）
4. 还提供 `--pidfile`、`--user`、`--make-pidfile` 等选项，比手写 daemon 化更规范。

**结论**：`start-stop-daemon` 是把"标准 daemon 化流程"打包成命令行工具。嵌入式里如果没有它，就得自己实现 `daemon(3)` 或 `fork+setsid` 序列——容易漏一步就出问题。

### 5.2 restarter的角色

脚本最关键的一行：

```bash
LD_LIBRARY_PATH=... $base_dir/restarter -s 1 -m 30 -- $base_dir/../palmapp --signal-parent 10 "$@"
```

`restarter` 是**外挂守护进程**。它的核心逻辑（伪代码）：

```c
// restarter.c 精简版
int restart_interval = 1;    // -s 1：两次重启间隔（秒）
int max_restarts = 30;       // -m 30：窗口内最多允许重启次数
int window_size = 60;        // 观测窗口长度（秒），生产可配置
int restart_count = 0;
time_t window_start = time(NULL);

while (1) {
    pid_t pid = fork();
    if (pid == 0) {
        // 子进程：变身为 palmapp
        execve(argv[argv_start], &argv[argv_start], environ);
        _exit(127);   // exec 失败
    }
    // 父进程：等 palmapp 死
    int status;
    waitpid(pid, &status, 0);

    // 节流：滑动窗口计数
    time_t now = time(NULL);
    if (now - window_start > window_size) {
        // 窗口过期，重置
        window_start = now;
        restart_count = 0;
    }
    if (++restart_count > max_restarts) {
        fprintf(stderr, "restart too frequent, giving up\n");
        exit(1);
    }
    sleep(restart_interval);   // -s 间隔
}
```

**restarter 的三个价值**：

| 价值 | 具体作用 |
|---|---|
| 崩溃拉起 | palmapp 挂了自动重启，不需要人工介入 |
| 重启节流 | 短时间内暴增重启会被 `-m 30` 拦截，避免烤设备 |
| 独立于业务 | palmapp 逻辑越复杂 bug 越多，restarter 逻辑简单不出错 |

### 5.3 双亲隔离与孤儿

**疑惑**：如果 restarter 自己挂了怎么办？palmapp 不就没人管了？

**论证**：
1. restarter 挂了 → palmapp 变成孤儿 → 被 init 接管
2. init 不会主动重启 palmapp（这是 restarter 的职责）
3. 所以我们需要**上一层守护**——脚本里其实靠"init 拉 restart.sh"完成：
   - init（PID 1）以 `respawn` 方式跑 restart.sh
   - restart.sh 里最后一行 `exec restarter`（前台执行）
   - restarter 挂了 → restart.sh 退出 → init 检测到 respawn 项子进程死了 → 重跑 restart.sh
4. 这样形成**三层守护**：

```
┌───────────────────────────────────────┐
│  init (PID 1，内核保证不死)              │
│    ↓ 挂了自动 respawn                   │
│  restart.sh (脚本层)                    │
│    ↓ 前台 exec                          │
│  restarter (最小守护)                    │
│    ↓ 挂了自动重启                        │
│  palmapp (业务进程)                      │
└───────────────────────────────────────┘
```

**结论**：单层守护是不够的——业务进程崩溃靠 restarter，restarter 崩溃靠 init。**三层守护是嵌入式设备"永不停机"的基本盘**。

### 5.4 崩溃重启节流

**疑惑**：为什么要 `-s 1 -m 30`？直接秒杀秒重启不是最快恢复吗？

**论证**：考虑一个真实故障场景：

```
20:00:00  palmapp 启动
20:00:03  读配置文件失败（文件被人手工改坏了）→ 崩溃
20:00:03  restarter 立刻拉起
20:00:03  又崩溃
20:00:03  又拉起
20:00:03  又崩溃 ...
→ 每秒 100+ 次重启，CPU 100%、日志爆炸、设备发烫
```

这就是**重启风暴（restart storm）**。应对：

- **`-s 1`**：两次重启之间至少 sleep 1 秒——把 100 Hz 降到 1 Hz
- **`-m 30`**：30 秒内超过若干次就放弃——避免"配置坏了永远起不来"的死循环

放弃后能怎么办？有三种选择：

| 策略 | 做法 |
|---|---|
| 静默放弃 | `exit`，等下一次人工介入 |
| 上报云端 | 发个 MQTT 消息 → 云端触发运维告警 |
| 触发整机重启 | `reboot`——试试从头来，硬件问题也许恢复 |

生产建议：三级递进——先重启进程、失败再重启 restart.sh 脚本、还失败就 `reboot`。这就是**故障自愈的分级策略**。

**结论**：崩溃重启不是"越快越好"——节流是把"频繁失败"降级为"低频失败"，给运维和用户留出反应时间。


## 6. 信号与优雅退出

### 6.1 SIGTERM的语义

`kill $pid` 默认发送 **SIGTERM（15 号信号）**。它的语义是"请你退出"——**请**，不是"必须"。

进程收到 SIGTERM 后可以：
- 立刻退出（默认行为）
- 忽略（`signal(SIGTERM, SIG_IGN)`）
- 做清理再退出（注册信号处理器）

**优雅退出的标准动作**（palmapp 应该做的）：

```c
volatile sig_atomic_t should_exit = 0;

void sig_handler(int sig) { should_exit = 1; }

int main() {
    signal(SIGTERM, sig_handler);
    signal(SIGINT,  sig_handler);
    // 上锁、写 PID、初始化...

    while (!should_exit) {
        // 主循环，检查 should_exit
        do_one_iteration();
    }

    // 清理：关闭 socket、flush 日志、释放硬件
    cleanup();
    // fd 关闭时锁自动释放，PID 文件残留但不锁着（下次 lockcheck 返回 1）
    return 0;
}
```

**常见坑**：在信号处理器里做复杂事——**大忌**！信号处理器里能安全用的函数极少（`man 7 signal-safety`），不要 `printf`、不要 `malloc`。**只置个 flag，主循环去查**。

### 6.2 signal-parent机制

`palmapp --signal-parent 10` 意思是：palmapp **就绪之后**给父进程发第 10 号信号（SIGUSR1）。

**疑惑**：为什么需要"就绪通知"？父进程不是 fork 之后就知道了吗？

**论证**：
1. `fork+exec` 成功只代表"进程起来了"，不代表"业务就绪"。palmapp 里还要：
   - 加锁、写 PID
   - 加载配置、连接数据库、启动 UI
   - 与 palmopenkit 建立 IPC
2. 这些初始化可能耗时几秒。在此期间外部调用会失败。
3. 父进程（restarter 或 restart.sh）如果不等这个信号，就不知道啥时候算"启动成功"——直接返回，日志上写"restarted"，其实业务还没起来。
4. **双向协商**：父等信号 = "我要确认你就绪"，子发信号 = "我告诉你我就绪了"。

这是 **systemd `Type=notify`** 的核心机制——通过 `sd_notify()` 系统调用告诉 systemd "READY=1"。我们用简单的 SIGUSR1 实现了同样效果。

**父进程等信号的伪代码**：

```c
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGUSR1);
sigprocmask(SIG_BLOCK, &mask, NULL);   // 先屏蔽，避免 race

pid_t child = fork();
if (child == 0) {
    execve("palmapp", ...);
} else {
    // 带超时等 SIGUSR1
    struct timespec timeout = {30, 0};   // 30 秒超时
    int sig = sigtimedwait(&mask, NULL, &timeout);
    if (sig == SIGUSR1) {
        printf("palmapp ready\n");
    } else {
        printf("palmapp not ready in 30s, kill it\n");
        kill(child, SIGKILL);
    }
}
```

### 6.3 kill到killall兜底

我们的 stop 流程按"温和 → 强硬"三级：

```bash
kill "$pid"               # 【1】SIGTERM，请求退出，给 2 秒响应
sleep 2
killall palmapp           # 【2】按名字扫全表，防止子进程残留
sleep 1
killall -9 palmapp        # 【3】SIGKILL，强杀
```

三级的必要性：

| 级别 | 信号 | 优点 | 缺点 |
|---|---|---|---|
| kill $pid | SIGTERM | 优雅、程序可清理 | 只针对主进程、可能忽略 |
| killall palmapp | SIGTERM | 覆盖所有同名进程 | 依然依赖程序响应 SIGTERM |
| killall -9 palmapp | SIGKILL | 内核直接杀，进程无法拒绝 | 无清理，可能留下损坏数据 |

**为什么不直接 SIGKILL 省事？**

**疑惑**：反正最后都要死，一步 SIGKILL 不快吗？

**论证**：
1. SIGKILL 无法被捕获——进程没机会关闭 fd、flush 缓冲、清 PID 文件。
2. 正在写文件的进程被 SIGKILL → 文件半截，配置损坏。
3. 正在写 SQLite 数据库的进程被 SIGKILL → 数据库锁残留，下次启动"database is locked"。
4. 正在与硬件交互的进程被 SIGKILL → 硬件状态不确定，下次重启可能拉不起来。

**结论**："先温柔再强硬"是**给程序自我清理的机会**。SIGKILL 是最后手段，不是首选。

### 6.4 SIGKILL的代价

再深挖一层：SIGKILL 触发时内核里发生什么？

```
kill(pid, SIGKILL)
    ↓
内核：修改目标进程的 task_struct.pending
    ↓
下次调度：进入信号处理路径 → 发现是 SIGKILL
    ↓
do_exit() → 立即执行：
    - 关闭所有 fd（触发 flock 自动释放）
    - 释放内存
    - 通知父进程 SIGCHLD
    - 变成僵尸等 wait
```

**flock 自动释放**这一步很关键——所以即使我们 SIGKILL 掉 palmapp，PID 文件的锁也会释放，下次 restart 能通过 lockcheck 判断"没在跑"。**内核事实源的可靠性再次体现**。

但是——已经 dirty 的内存页可能没 flush，用户数据丢失。所以 SIGKILL 只是最后兜底。


## 7. 环境变量与路径

### 7.1 base_dir的技巧

脚本开头这一行：

```bash
base_dir=$(cd "`dirname "$0"`" && pwd)
```

**疑惑**：为什么不直接用 `dirname "$0"`？

**论证**：`dirname "$0"` 拿到的可能是相对路径。看几种执行方式：

| 执行方式 | `$0` | `dirname "$0"` | `cd ... && pwd` |
|---|---|---|---|
| `./restart.sh` | `./restart.sh` | `.` | `/app/palmapp/scripts` |
| `bash restart.sh` | `restart.sh` | `.` | `/app/palmapp/scripts`（当前目录）|
| `/app/palmapp/scripts/restart.sh` | `/app/palmapp/scripts/restart.sh` | `/app/palmapp/scripts` | 同左 |
| 通过 init 拉起 | 可能是 `../scripts/restart.sh` | `../scripts` | 转成绝对路径 |

**结论**：`cd ... && pwd` 把 `$0` 的目录**归一化成绝对路径**。之后 `$base_dir/../palmapp`、`$base_dir/lockcheck` 都不受调用方式影响。**这是一个必须掌握的 shell 惯用法**。

### 7.2 LD-LIBRARY-PATH

```bash
LD_LIBRARY_PATH=$base_dir/../lib:$LD_LIBRARY_PATH $base_dir/restarter ...
```

**疑惑**：为什么必须显式设置 `LD_LIBRARY_PATH`？系统不是有 `/etc/ld.so.conf` 吗？

**论证**：
1. 嵌入式设备的 rootfs 通常极简，`/etc/ld.so.conf` 只包含 `/lib` `/usr/lib`。
2. 应用自己的 `.so`（Qt、boost、openssl 定制版）放在 `/app/palmapp/lib`——不在系统路径里。
3. 动态链接器（ld.so）搜索顺序：`DT_RPATH` → `LD_LIBRARY_PATH` → `DT_RUNPATH` → `/etc/ld.so.cache` → `/lib /usr/lib`。
4. 我们让运行时能找到自家 `.so`，最省事的就是 `LD_LIBRARY_PATH`。
5. 更高级的方案是**编译时**指定 `-Wl,-rpath,$ORIGIN/../lib`，让二进制自带搜索路径，运行时不需要外部设置——但需要编译权限，脚本层控不了。

**常见坑**：

```bash
# ❌ 错误：这样写会污染整个 shell 后续所有命令
export LD_LIBRARY_PATH=/app/palmapp/lib:$LD_LIBRARY_PATH
/app/palmapp/restarter ...

# ✅ 正确：只影响本次调用
LD_LIBRARY_PATH=/app/palmapp/lib:$LD_LIBRARY_PATH /app/palmapp/restarter ...
```

第二种写法是 shell 的"临时环境变量"语法——只对紧跟的这一条命令生效。

**结论**：嵌入式应用的 `.so` 放自家目录，`LD_LIBRARY_PATH` 是"最低成本的运行时链接方案"。生产追求更强隔离时，改成 `-rpath,$ORIGIN/../lib` 更好。

### 7.3 工作目录切换

```bash
mkdir -p /data/palmapp/
cd /data/palmapp/
```

**疑惑**：为什么要 `cd` 到 `/data/palmapp/`？

**论证**：进程的**当前工作目录（CWD）**影响很多事：

1. **相对路径的解析**——`fopen("config.json", "r")` 会去 CWD 找。
2. **core dump 落地**——默认 core 文件写到 CWD。
3. **日志文件**——很多程序默认写 `./log/app.log`。
4. **临时文件**——`fopen("tmp.dat", "w")` 落 CWD。

嵌入式设备**分区规划**通常是这样：

| 分区 | 挂载点 | 属性 | 用途 |
|---|---|---|---|
| system | `/` `/usr` `/app` | 只读 | 系统、应用二进制 |
| data | `/data` | 可读写 | 应用数据、日志、缓存 |
| tmp | `/tmp` (tmpfs) | 内存 | 临时文件 |

**不能在只读分区写文件**！`cd /data/palmapp/` 是把 CWD 切到"允许写"的分区。忘了 `cd` 直接跑，一旦程序想写文件，就会 `EROFS: Read-only file system`。

`mkdir -p` 保证目录存在——首次启动、data 分区刚格式化的场景都需要。

### 7.4 core文件与ulimit

脚本里注释掉的一行：

```bash
# ulimit -c unlimited
```

**为什么开发时开、生产关？**

**开发时**：崩溃就要留 core dump，供 gdb 分析。`ulimit -c unlimited` 允许任意大小 core，`/proc/sys/kernel/core_pattern` 配置文件名模板。

**生产时**：设备 Flash 空间小（可能只有几百 MB data 分区），一个 core 文件可能 100+ MB。频繁崩溃会**塞满磁盘**——比崩溃更糟。所以关掉。

替代方案：
- **minidump**：只保留崩溃现场的最小信息（几 MB），够 gdb 定位大概位置
- **符号剥离 + 崩溃上报**：把 debug symbol 存服务器，设备只上传崩溃 backtrace

这就是我们后面第 11 篇《调试三板斧》要展开的内容。


## 8. 依赖服务拉起

### 8.1 palmopenkit联动

脚本这一段：

```bash
PALMOPENKIT="/app/palmopenkit/scripts/restart.sh"
if [ -f "$PALMOPENKIT" ]; then
    start-stop-daemon -S -b -q --exec "$PALMOPENKIT"
fi
```

**疑惑**：palmapp 不是主角吗？为什么它启动脚本里要拉 palmopenkit？

**论证**：`palmopenkit` 是 palmapp 依赖的一个**平级服务**（可能提供硬件抽象、云端接入、配置中心之类的能力）。它们的关系不是父子，而是**兄弟**——运行时通过 IPC 通信。

启动时的依赖顺序：

```
时间轴:
t0    :  restart.sh 开始执行
t0+1s :  拉起 palmopenkit（-b 后台，非阻塞）
t0+1s :  palmopenkit 正在初始化中...
t0+1s :  restart.sh 继续，启动 palmapp
t0+2s :  palmapp 开始初始化
t0+3s :  palmapp 尝试连接 palmopenkit 的 socket
t0+3s :  palmopenkit 恰好初始化完成 → 连接成功
```

**存在的问题**：`start-stop-daemon -S -b` 是**非阻塞后台启动**——命令立刻返回，不等 palmopenkit 就绪。palmapp 起得早、palmopenkit 起得慢 → palmapp 连不上 palmopenkit 的 socket → 报错。

### 8.2 依赖顺序与检查

**更健壮的写法**——加个 ready 探测：

```bash
if [ -f "$PALMOPENKIT" ]; then
    start-stop-daemon -S -b -q --exec "$PALMOPENKIT"
    
    # 等 palmopenkit 就绪（探测它的 socket）
    for i in $(seq 1 30); do
        if [ -S /var/run/palmopenkit.sock ]; then
            break
        fi
        sleep 0.5
    done
    if [ ! -S /var/run/palmopenkit.sock ]; then
        echo "palmopenkit not ready in 15s"
        # 记 log，但不 exit——palmapp 可能能降级运行
    fi
fi
```

**通用的"等就绪"三种探测方式**：

| 探测方式 | 适用场景 |
|---|---|
| 探测 socket 文件 | Unix Domain Socket 服务 |
| `nc -z 127.0.0.1 8080` | TCP 端口 |
| curl 一个 `/healthz` | HTTP 服务 |
| 探测 PID 文件被锁 | 用 lockcheck 反查 |

palmapp 内部还可以做**重试**：连接失败等 1 秒再试，最多 5 次。**"上层等 + 下层重试"双保险**才是嵌入式生产级健壮性。

### 8.3 systemd风格对照

对比 systemd 的写法：

```ini
[Unit]
Requires=palmopenkit.service       # 硬依赖：palmopenkit 起不来 palmapp 也不起
After=palmopenkit.service          # 顺序：palmopenkit 先起

[Service]
Type=notify                        # 等子进程通过 sd_notify 报告就绪
NotifyAccess=main
```

systemd 帮你搞定"顺序 + 硬依赖 + 就绪等待"。BusyBox 环境下用不了，只能手写脚本——**shell 脚本能做到的事其实和 systemd 一样多，只是需要更多代码**。

**结论**：依赖服务拉起有三种模式——**并行不等（快但脆）、顺序等待（稳但慢）、异步重试（灵活）**。生产设备通常是"顺序拉起 + 就绪探测 + 客户端重试"三合一。


## 9. 停止与重启时序

### 9.1 stop.sh的时序

回看 stop.sh 的顺序：

```bash
killall "restarter" || true       # 【1】先杀守护
kill "$pid"                       # 【2】再杀本体
killall palmapp                   # 【3】兜底名字扫
```

**疑惑**：为什么必须先杀 restarter？

**论证**：假设反过来——先杀 palmapp：

```
t0     :  kill $palmapp_pid  → palmapp 收到 SIGTERM，开始清理
t0+1ms :  palmapp 退出
t0+2ms :  restarter waitpid 返回，检测到 palmapp 死了
t0+3ms :  restarter fork+exec 新的 palmapp
t0+10ms:  killall palmapp → 杀新起来的 palmapp
t0+11ms:  restarter 又拉起
t0+20ms:  又被 killall
... 
```

**永远杀不干净**——restarter 拉起速度比 killall 快。

正确顺序是**依赖反演**：**启动时从底层往上，停止时从上层往下**。

```
启动顺序：
  init → restart.sh → restarter → palmapp
  （下 → 上）

停止顺序（反过来）：
  killall restarter → kill palmapp
  （上 → 下，先断"重启机制"，再杀"业务进程"）
```

这条原则叫**"逆拓扑序停止"**（reverse topological order），systemd 里 `Before=` / `After=` 反向解析停止顺序也是这个道理。

### 9.2 restart.sh的时序

restart.sh 的时序：

```
【阶段 A：停止】
1. lockcheck 判断是否在跑
2. kill $pid  → SIGTERM
3. sleep 2 让它清理
4. killall palmapp  → 兜底同名进程
5. sleep 1
6. pidof + killall -9  → 硬杀

【阶段 B：依赖】
7. 拉起 palmopenkit（后台，非阻塞）

【阶段 C：启动】
8. mkdir -p /data/palmapp/
9. cd /data/palmapp/
10. LD_LIBRARY_PATH=... restarter -s 1 -m 30 -- palmapp --signal-parent 10
```

**注意**：stop.sh 里先杀 restarter，restart.sh 里**没有**先杀 restarter——这有讲究。

restart.sh 的调用场景是：**在 restarter 内部的 palmapp 崩了要重启**。restarter 会自动拉，一般不需要人工调 restart.sh。

而**人工调 restart.sh 时**（比如 OTA 更新完手工重启）：
- 如果 restarter 已经在跑——它会自动重拉 palmapp，restart.sh 反倒和它抢
- 如果 restarter 没跑——restart.sh 拉起完整链条

所以更严谨的 restart.sh 应该在开头先 `killall restarter`（等价于先跑 stop.sh），再重启完整链条。我们当前的 restart.sh 假设"进程崩溃场景由 restarter 内部处理，脚本只用于首次启动"——是一种简化。

**生产级的对称写法**：

```bash
# 更好的 restart.sh 骨架
$base_dir/stop.sh          # 【1】完整停止（含 restarter）
sleep 1                    # 【2】留缓冲
$base_dir/start.sh         # 【3】完整拉起
```

把 stop / start 拆开、restart 是它们的组合——这样 **"stop + start = restart"** 恒等式成立。这是运维脚本的**幂等化重构**。

### 9.3 幂等性设计

**疑惑**：什么叫幂等？

**论证**：**幂等 = 多次执行效果等同于一次执行**。运维脚本必须幂等，因为：

- 你调 restart.sh 时不知道当前是"在跑""半死""完全停"三种状态中的哪一种。
- 脚本必须不管当前状态，执行完都是"在正常跑"。

我们脚本的幂等性证据：

| 步骤 | 幂等吗 | 说明 |
|---|---|---|
| `kill $pid && sleep 2 \|\| true` | ✅ | `\|\| true` 保证不因 pid 不存在中断 |
| `killall palmapp 2>/dev/null \|\| true` | ✅ | 没进程也 OK |
| `mkdir -p /data/palmapp/` | ✅ | 目录已存在 OK |
| `cd /data/palmapp/` | ✅ | 可重复 cd |
| `restarter ...` | ✅ | 前台 exec，进程一直存在 |

**反例**：

```bash
mkdir /data/palmapp/    # ❌ 已存在会报错 → set -e 之下脚本直接 exit
mv oldfile newfile      # ❌ 第二次跑时 oldfile 不在了 → 出错
```

`set -e` + 幂等操作是 shell 脚本的"零故障"底线。

**结论**：优雅的启动脚本三件事——**依赖反演、幂等设计、失败允许**（`|| true`）。这套原则不是嵌入式独有，而是所有运维脚本的通行标准。


## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到第 1 章脚本，六个疑问现在可以逐条回答：

| 疑问 | 答案 |
|---|---|
| ① 嵌入式应用从上电到 main() 全流程？ | 第 3 章：Bootloader → Kernel → init → restart.sh → restarter → palmapp，五层交接 |
| ② 为什么用 lockcheck 而不是裸 PID 文件？ | 第 4.2 - 4.3：flock 绑定进程生命周期，进程死锁自动释放，比"文件存在"可靠 |
| ③ restarter / start-stop-daemon 做什么？ | 第 5.1 - 5.2：start-stop-daemon 是 daemon 化工具（fork+setsid+detach），restarter 是崩溃拉起 + 节流 |
| ④ kill / killall / --signal-parent 语义？ | 第 6：SIGTERM 是请求退出，SIGKILL 是强杀，signal-parent 是"我就绪了"回执 |
| ⑤ LD_LIBRARY_PATH / base_dir / cd 作用？ | 第 7：base_dir 是绝对路径归一化，LD_LIBRARY_PATH 让 ld.so 找到自家 .so，cd 是切到可写分区 |
| ⑥ 停止时为什么先杀守护再杀本体？ | 第 9.1：逆拓扑序——先断"重启机制"再杀"被守护对象"，否则永远杀不干净 |

**逐行注解版脚本**——把所有原理点标在旁边：

```bash
#!/bin/sh
set -e                                                # ← 任何命令失败立即退出，减少半死状态

pid_file="/tmp/palmapp.pid"                           # ← §4.1 单实例锁文件（tmpfs，重启即清）
base_dir=$(cd "`dirname "$0"`" && pwd)                # ← §7.1 归一化脚本目录为绝对路径

# 【1】判活 + 停止老进程
if "$base_dir/lockcheck" -q "$pid_file"; then         # ← §4.3 用文件锁判活
    kill "$(cat "$pid_file")" && sleep 2 || true      # ← §6.1 SIGTERM + 2秒清理窗口
fi
killall palmapp 2>/dev/null || true                   # ← §6.3-6.4 兜底残留

# 【2】拉起依赖服务
[ -f /app/palmopenkit/scripts/restart.sh ] && \       # ← §8.1 可选依赖
    start-stop-daemon -S -b -q --exec /app/palmopenkit/scripts/restart.sh   # ← §5.1

# 【3】切工作目录 & 启动主进程（restarter 守护 palmapp）
cd /data/palmapp/                                     # ← §7.3 切到可写分区
LD_LIBRARY_PATH=$base_dir/../lib:$LD_LIBRARY_PATH \   # ← §7.2 让 ld.so 找到自家 .so
    $base_dir/restarter -s 1 -m 30 \                  # ← §5.2 崩溃拉起 + §5.4 节流
    -- $base_dir/../palmapp --signal-parent 10 "$@"   # ← §6.2 就绪回执
```

### 10.2 一次启动的一生

把 `./restart.sh` 这一行的全过程串成一棵知识树：

```
./restart.sh (由 init 或人工触发)
        │
        ├─ 【停止阶段】§4-6
        │   ├─ lockcheck 查锁                     ─── §4.3
        │   ├─ kill $pid → SIGTERM              ─── §6.1
        │   ├─ sleep 2 让进程 cleanup            ─── §6.1
        │   ├─ killall palmapp 兜底              ─── §6.3
        │   └─ killall -9 palmapp 硬杀           ─── §6.4
        │
        ├─ 【依赖阶段】§8
        │   └─ start-stop-daemon 后台拉起 palmopenkit ─── §5.1 §8.1
        │
        ├─ 【环境阶段】§7
        │   ├─ mkdir -p /data/palmapp/           ─── §7.3
        │   ├─ cd /data/palmapp/                 ─── §7.3
        │   └─ LD_LIBRARY_PATH 设置              ─── §7.2
        │
        └─ 【启动阶段】§5
            ├─ exec restarter (脚本进程被替换)
            │
            ├─ restarter fork → child           ─── §5.2
            │   │
            │   └─ child execve palmapp        ─── §5.2
            │       │
            │       └─ palmapp 内部：
            │           ├─ 加锁 flock            ─── §4.2
            │           ├─ 写 PID              ─── §4.1
            │           ├─ 初始化子系统
            │           ├─ 连接 palmopenkit     ─── §8
            │           └─ signal-parent SIGUSR1 ─── §6.2
            │
            ├─ restarter waitpid 等 palmapp
            │
            └─ palmapp 死了 → restarter 重启      ─── §5.2
                │
                └─ 30 秒 30 次超限 → 放弃          ─── §5.4
                    │
                    └─ init 检测 restart.sh 退出 → respawn ─── §5.3
```

理解一份启动脚本的一生，就是理解一个嵌入式应用**"从生到死到复活"**的完整闭环。

### 10.3 设计哲学回扣

整理本篇的四条跨篇适用的设计哲学：

**哲学 1：内核事实源——把状态问答降级为内核查询**

我们用 `flock` 而不是"检查 PID 文件是否存在"，用 `waitpid` 而不是轮询"进程还在吗"——**只要有内核能承诺的事实，就绝不用户态启发式判断**。内核事实源是永远正确的、不会有 race、不需要额外同步。

**哲学 2：分层守护——业务信不过守护、守护信不过 init**

palmapp（业务） ← restarter（应用守护） ← restart.sh（脚本守护） ← init（内核保证）。**每一层只信任比自己更简单的下一层**。业务逻辑越复杂 bug 越多，守护逻辑越简单越可靠。这是嵌入式设备"永不停机"的秘方。

**哲学 3：逆拓扑序停止——先断因，再灭果**

启动 A → B → C（下往上）；停止 C → B → A（上往下）。先杀 restarter 再杀 palmapp——**先断"因"（重启机制），再灭"果"（业务进程）**，否则果永远除不掉。systemd 的 `Before/After` 反向解析、docker 容器编排、微服务优雅关闭，无一不遵循此律。

**哲学 4：幂等 + 允许失败——脚本必须能被反复执行**

`|| true`、`mkdir -p`、`kill && sleep 2 || true`——不管当前是什么状态，脚本执行完都要达到期望状态。**幂等把"当前状态不确定"这个难题从脚本里彻底消除**。运维自动化的核心不是"精确控制"，是"目标状态收敛"。

### 10.4 启动脚本速查

**PID 文件 + 锁的判活口诀**：

```
文件存在 + 锁被占 = 活着
文件存在 + 锁空闲 = 死了（残留 PID 文件）
文件不存在        = 从来没起过
```

**信号语义速查表**：

| 信号 | 编号 | 可捕获 | 用途 |
|---|---|---|---|
| SIGTERM | 15 | ✅ | 请求优雅退出（kill 默认） |
| SIGINT | 2 | ✅ | 交互中断（Ctrl+C） |
| SIGHUP | 1 | ✅ | 终端断开 / 重载配置 |
| SIGUSR1 | 10 | ✅ | 应用自定义（我们用它当"就绪回执"） |
| SIGUSR2 | 12 | ✅ | 应用自定义（备用） |
| SIGKILL | 9 | ❌ | 强杀，无法捕获 |
| SIGSTOP | 19 | ❌ | 暂停，无法捕获 |
| SIGCHLD | 17 | ✅ | 子进程状态变化 |

**60 秒启动诊断命令清单**：

```bash
# 看进程树，谁是父谁是子
ps -eo pid,ppid,cmd --forest | grep -E "palmapp|restarter"

# 看进程是否在跑
pidof palmapp
cat /proc/$(pidof palmapp)/status  | grep -E "^(State|PPid|Uid)"

# 看进程打开的 fd（含 PID 文件锁）
ls -la /proc/$(pidof palmapp)/fd/
cat /proc/locks | grep palmapp.pid

# 看进程用的动态库
cat /proc/$(pidof palmapp)/maps | grep '\.so' | awk '{print $6}' | sort -u
ldd /app/palmapp/bin/palmapp

# 看环境变量
tr '\0' '\n' < /proc/$(pidof palmapp)/environ

# 看当前工作目录
readlink /proc/$(pidof palmapp)/cwd

# 看 init 是谁、拉起链条
ps -eo pid,ppid,cmd | awk '$1==1'
systemctl status palmapp        # 用 systemd 时
```

**启动脚本三件套模板**（可直接复用）：

```bash
# start.sh
#!/bin/sh
set -e
base_dir=$(cd "`dirname "$0"`" && pwd)
[ -f "$base_dir/lockcheck" ] && "$base_dir/lockcheck" -q /tmp/myapp.pid && exit 0
cd /data/myapp/
LD_LIBRARY_PATH=$base_dir/../lib:$LD_LIBRARY_PATH \
    exec $base_dir/restarter -s 1 -m 30 \
    -- $base_dir/../myapp --signal-parent 10 "$@"

# stop.sh
#!/bin/sh
set -e
base_dir=$(cd "`dirname "$0"`" && pwd)
killall restarter 2>/dev/null || true
if "$base_dir/lockcheck" -q /tmp/myapp.pid; then
    kill "$(cat /tmp/myapp.pid)" 2>/dev/null || true
    sleep 2
fi
killall myapp 2>/dev/null || true
sleep 1
killall -9 myapp 2>/dev/null || true

# restart.sh
#!/bin/sh
base_dir=$(cd "`dirname "$0"`" && pwd)
"$base_dir/stop.sh"
sleep 1
exec "$base_dir/start.sh" "$@"
```

**start / stop / restart 三件套 + lockcheck + restarter 五件工具**，覆盖 90% 嵌入式应用的启动管理需求。
