## 1. 案例引入

### 1.1 一次真实的构建噩梦

一个嵌入式项目上线前一周，团队新招的同学接手了构建环境。他在 x86 PC 上跑得好好的代码，交叉编译到 ARM 板子上时出了这样一份错误清单——这是从真实生产环境裁剪出来的：

```bash
$ cmake -DCMAKE_TOOLCHAIN_FILE=./arm.cmake -B build && cmake --build build
...
[  20%] Linking CXX executable palmapp
/opt/arm-toolchain/bin/../lib/gcc/.../ld: cannot find -lssl
/opt/arm-toolchain/bin/../lib/gcc/.../ld: cannot find -lcurl
collect2: error: ld returned 1 exit status

# 硬着头皮加 -L 指到 host 的 x86 库
$ cmake -DOPENSSL_ROOT_DIR=/usr/lib/x86_64-linux-gnu ...
[  40%] Linking CXX executable palmapp
/usr/lib/x86_64-linux-gnu/libssl.so: file format not recognized
```

好不容易凑合编译过了，扔到板子上一跑：

```
# palmapp
./palmapp: error while loading shared libraries: libQt5Core.so.5:
    cannot open shared object file: No such file or directory

# 手动把 libQt5Core.so.5 塞过去
# palmapp
./palmapp: symbol lookup error: ./palmapp: undefined symbol:
    _ZN10QByteArray6resizeEi, version Qt_5

# strings libQt5Core.so.5 | grep Qt_5
Qt_5.11
# ldd 显示应用需要 Qt_5.15 → so 版本对不上
```

这一连串报错背后是**四条独立的错误**混在一起：
- **`cannot find -lssl`**：交叉编译工具链找不到 ARM 版本的库
- **`file format not recognized`**：错误地链接了 x86 的 `.so`
- **`No such file or directory`**：板子上没装依赖
- **`undefined symbol`**：装了但版本不对

新同学花了三天，最后放弃"手工凑"，才意识到应该有一套**可复用的交叉编译框架**。

### 1.2 顺藤摸到根因

翻这个故障，本质是几个概念没分清：

- **假设 1**：为什么 host 的 `-lssl` 会被链接进来？，因为默认 `find_package` 会去 host 系统路径搜索，交叉编译时**必须显式告诉它只在 sysroot 里找**。→ 这引出 **sysroot 与 find_root_path 机制**。
- **假设 2**：为什么 `.so` 找不到？，因为 rootfs 里没装 Qt，或 `LD_LIBRARY_PATH` 没设。→ 这引出 **动态链接器的搜索规则**（回扣 01 篇 §7.2）。
- **假设 3**：为什么装了还报 `undefined symbol`？，因为编译时用的头文件是 5.15，运行时的 `.so` 是 5.11，**接口签名不匹配**。→ 这引出 **ABI 与符号版本**。
- **假设 4**：为什么每次改代码要等 20 分钟？，因为没启 `ccache`、没上 `ninja`、编译并行度为 1。→ 这引出 **编译加速三板斧**。
- **假设 5**：为什么 PC 上跑得动到 ARM 就崩？，因为 PC 是 x86_64，指针是 8 字节；ARM 是 32 位，指针 4 字节，`sizeof(void*)` 不同的代码没做适配。→ 这引出 **多平台适配**。

一份编译报错，藏着五个知识点：

```
① 交叉编译工具链到底是什么，为什么不能用 host gcc？   → 第 3 章
② CMake 怎么隔离"host 依赖 vs target 依赖"？          → 第 4 章 + 第 5 章
③ 依赖库到底该 find_package、FetchContent 还是 vcpkg？→ 第 6 章
④ 编译从 20 分钟压到 3 分钟需要哪些工具？             → 第 7 章
⑤ 应该选什么工具链、什么 libc？                       → 第 8 章
```

### 1.3 我们要回答什么

这一篇不是讲 CMake 语法书，是讲**如何把"能编译"的项目升级为"工程化编译"**。目标是：任何人拉下来代码，一条命令就能在多个平台产出可发布的二进制，编译速度可预测、失败可诊断。

本篇路线：

```

   ↓

   ↓

   ↓

   ↓

   ↓

   ↓
```

## 2. 架构概览

### 2.1 交叉编译四段论

一次完整的交叉编译，可以切成四段：**工具链选取 → 依赖准备 → 源码构建 → 产出打包**。

```
┌─────────────────────────────────────────────────────────────────┐
│                    交叉编译生产管线                                │
│                                                                  │
│  ┌────────────┐    ┌────────────┐    ┌────────────┐   ┌────────┐│
│  │ 1.工具链    │───►│ 2.依赖准备  │───►│ 3.源码构建  │──►│4.打包  ││
│  │ toolchain  │    │  sysroot   │    │  cmake     │   │strip   ││
│  └─────┬──────┘    └─────┬──────┘    └─────┬──────┘   └───┬────┘│
│        │                 │                  │              │     │
│        ▼                 ▼                  ▼              ▼     │
│   gcc/ld/ar         Qt/OpenSSL         obj/lib          .tar.gz  │
│   +glibc/musl       预编译的 .so       +可执行文件      +.so 打包 │
└─────────────────────────────────────────────────────────────────┘
```

每段的**输入产物**和**典型工具**：

| 阶段 | 输入 | 产出 | 典型工具 |
|---|---|---|---|
| ① 工具链 | 目标架构（ARM/AArch64/RISC-V） | `gcc/g++/ld/ar/strip` + sysroot | Linaro / Buildroot / Yocto |
| ② 依赖准备 | 三方库源码或预编译包 | 装到 sysroot 的 `.a/.so/.h` | 交叉编译或包管理器 |
| ③ 源码构建 | 项目 CMakeLists + toolchain.cmake | `.o → .a/.so/可执行` | CMake + Ninja + ccache |
| ④ 打包 | 构建产物 + 配置文件 | rootfs 镜像 / OTA 包 | strip + tar / mkfs |

### 2.2 为什么这么分

**疑惑**：为什么不能像 PC 开发那样"一条 `make` 走完"？

**论证**：
1. **编译器不同**，PC 上 `gcc` 生成 x86 指令，板子跑的是 ARM 指令，**指令集完全不兼容**，同一个 `.o` 文件放到 ARM 上就是乱码。
2. **头文件与库不同**，PC 的 `/usr/include/openssl/ssl.h` 编译出来的代码调用 x86 版 libssl，扔到 ARM 上找不到函数入口。
3. **依赖体系不同**，PC 上 `apt install libssl-dev` 一条命令搞定，嵌入式没有包管理器，必须自己交叉编译或从固件里抠。
4. **观测手段不同**，PC 崩了直接 gdb，嵌入式要 gdbserver 远程调试，符号表还得单独管理。

四段的边界就是**架构、依赖、构建、观测**四个正交维度的切换点。**每段一种角色、一套工具、一种典型失败**，与 01 篇里应用生命周期的三段式是同一种设计思想。

下面从"工具链"开始。


## 3. 交叉编译工具链

### 3.1 toolchain四件套

**疑惑**：一说"工具链"就头大，它到底包含什么？

**论证**：一套完整的 toolchain 由**四件套**组成，缺一不可：

```
┌────────────────────────────────────────────────────┐
│  arm-linux-gnueabihf-  (工具链前缀)                 │
│                                                    │
│  ├─ gcc / g++     ← 编译器（C 前端 + C++ 前端）      │
│  ├─ binutils      ← ld/ar/nm/objdump/strip 工具集   │
│  ├─ libc          ← glibc / musl / uClibc          │
│  └─ sysroot       ← 目标平台的 headers + libs 根    │
└────────────────────────────────────────────────────┘
```

工具链的命名前缀是一个**四段式三元组**（Target Triplet）：

```
arm - linux - gnueabihf
 │      │       │
 │      │       └─ ABI（gnu 使用 glibc，musl 使用 musl，eabihf 表示硬浮点）
 │      └───────── OS（linux / bare-metal / darwin）
 └──────────────── 架构（arm / aarch64 / mips / riscv64）
```

常见组合速查：

| 前缀 | 架构 | libc | 浮点 |
|---|---|---|---|
| `arm-linux-gnueabihf-` | ARMv7 | glibc | 硬浮点 |
| `arm-linux-musleabi-` | ARMv5/v7 | musl | 软浮点 |
| `aarch64-linux-gnu-` | ARMv8 (64) | glibc | / |
| `mipsel-linux-uclibc-` | MIPS 小端 | uClibc | 软浮点 |
| `riscv64-linux-gnu-` | RISC-V 64 | glibc | / |

**用错了会怎样**：硬浮点前缀编译的 `.so` 扔到软浮点板子上跑，`ldd` 报 `wrong ELF class` 或运行时崩溃。

### 3.2 sysroot的意义

**疑惑**：为什么工具链里要带一个 sysroot？直接用 host 的 `/usr/include` 不行？

**论证**：`sysroot` 是**目标平台的"迷你根文件系统"**，包含目标架构的头文件和链接库。它扮演的角色是：

```
compile 时：#include <stdio.h>   → 去 $SYSROOT/usr/include/stdio.h 找
link    时：-lssl                → 去 $SYSROOT/usr/lib/libssl.so 找
```

**为什么必须有**：
1. **头文件是架构相关的**，`<stdint.h>` 里 `size_t` 是 4 字节还是 8 字节，取决于目标架构，不是 host。
2. **库文件是二进制**，`libssl.so` 是 x86 的 ELF 还是 ARM 的 ELF，一字之差不能互用。
3. **系统调用号不同**，`__NR_openat` 在 ARM 和 x86 上编号不一样，glibc 的调用桩要针对目标架构生成。

用编译器参数控制 sysroot：

```bash
# 显式指定 sysroot
arm-linux-gnueabihf-gcc --sysroot=/opt/arm-sysroot -o app app.c

# 也可以用 -I / -L 覆盖单独的头文件 / 库路径
arm-linux-gnueabihf-gcc \
    -I/opt/arm-sysroot/usr/include \
    -L/opt/arm-sysroot/usr/lib \
    -o app app.c
```

**`--sysroot` 与 `-I/-L` 的区别**：

| 方式 | 影响范围 | 推荐场景 |
|---|---|---|
| `--sysroot` | 所有搜索路径整体切换 | 完整的 rootfs 交叉编译 |
| `-I/-L` | 仅指定单个路径 | 临时补丁式调整 |

**结论**：sysroot 是把"目标平台的世界"打包成一个目录，编译器进入这个世界工作，产出的一定是目标平台的产物。**这是交叉编译最核心的抽象**。

### 3.3 glibc与musl之争

**疑惑**：libc 不都一样吗？为什么要有 glibc、musl、uClibc 多个版本？

**论证**：libc 是应用与内核之间的桥梁，实现同一套 POSIX 接口，但取舍完全不同：

| libc | 二进制大小 | 性能 | 兼容性 | 典型场景 |
|---|---|---|---|---|
| glibc | 大（几 MB） | 快、优化足 | 最好（GNU 扩展全） | 常规商用板子 |
| musl | 小（几百 KB） | 中等 | 兼容 POSIX，扩展少 | Alpine、极小 rootfs |
| uClibc-ng | 极小 | 一般 | 阉割版 | MIPS 老设备、路由器 |
| bionic | 中等 | 中等 | Android 专用 | Android 系统 |

**踩坑案例**：某项目在 musl 上编译，用了 glibc 独有的 `__thread` 关键字，musl 里叫 `_Thread_local`，代码 `#ifdef` 没写全，直接编译报错。

**选择建议**（一句话版）：
- **磁盘小于 32 MB** → musl / uClibc
- **要跑 Qt / Boost / Chromium** → glibc
- **不确定** → 跟随 SDK 默认，别自作主张换

**结论**：libc 选择一次定下来后不要轻易换，因为**几乎所有三方库都要针对某个 libc 重新交叉编译一次**，切换成本极高。


## 4. CMake工程化

### 4.1 target为中心

**疑惑**：老项目里 CMakeLists 全是 `include_directories()` `link_libraries()` 满天飞，好难维护。

**论证**：这是**旧式 CMake**（3.0 之前）的写法，全局副作用，很难追踪谁依赖谁。现代 CMake（3.5+）的核心思想是**"以 target 为中心"**：所有属性都绑定到具体的 target 上。

**旧式（不推荐）**：

```cmake
include_directories(${OPENSSL_INCLUDE_DIR})     # ← 全局副作用
link_directories(${OPENSSL_LIB_DIR})            # ← 全局副作用
add_executable(app main.cpp)
target_link_libraries(app ssl crypto)
```

**新式（推荐）**：

```cmake
add_executable(app main.cpp)

target_include_directories(app PRIVATE ${OPENSSL_INCLUDE_DIR})
target_link_libraries(app PRIVATE OpenSSL::SSL OpenSSL::Crypto)
target_compile_features(app PRIVATE cxx_std_17)
```

**区别**：新式把属性挂在 `app` 这个 target 上，其他 target 不受影响；旧式修改的是全局，所有 target 都被牵连。**target 是 CMake 的"进程"，属性是它的"环境变量"**。

### 4.2 PUBLIC/PRIVATE/INTERFACE

**疑惑**：`target_link_libraries(app PRIVATE ssl)` 里的 `PRIVATE` 是什么意思？

**论证**：CMake 用**三种可见性关键字**控制依赖的传递：

```
┌─────────────────────────────────────────────────────┐
│  target A 依赖 target B                              │
│                                                      │
│  PRIVATE   ：只有 A 用 B，A 不对外暴露 B            │
│  INTERFACE ：A 自己不用 B，但依赖 A 的人要用 B       │
│  PUBLIC    ：A 自己用 B，且对外暴露 B（= PRIVATE + INTERFACE）│
└─────────────────────────────────────────────────────┘
```

用一个例子理解：

```cmake
# libnet：一个封装 OpenSSL 的网络库
add_library(libnet net.cpp)
target_link_libraries(libnet
    PUBLIC  OpenSSL::SSL       # ← libnet 的头文件里 #include <openssl/ssl.h>
                              #   用 libnet 的人也必须能找到 OpenSSL 头
    PRIVATE ZLIB::ZLIB         # ← libnet 内部用 zlib 压缩，头文件不暴露
)

# app：只用 libnet
add_executable(app main.cpp)
target_link_libraries(app PRIVATE libnet)
# app 自动获得 OpenSSL 头（PUBLIC 传递），但不获得 zlib（PRIVATE 阻断）
```

**判断口诀**：
- 我的头文件 `#include` 了它 → **PUBLIC**
- 我的 .cpp 用了它，头文件没暴露 → **PRIVATE**
- 我是纯头文件库，只把接口交出去 → **INTERFACE**

**结论**：`PRIVATE/PUBLIC/INTERFACE` 是 CMake 的"信息封装"机制。用对了，项目依赖图清晰、增量编译精确；用错了，全项目都要重新编译。

### 4.3 install与export

**疑惑**：写了个 `libmylib.so`，怎么让别的项目用 `find_package(mylib)` 就能找到？

**论证**：CMake 有一套完整的**导出机制**，让你的库可以被别的项目"当三方库用"：

```cmake
# 生成 target
add_library(mylib mylib.cpp)
target_include_directories(mylib PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>   # ← 构建时用源码目录
    $<INSTALL_INTERFACE:include>                              # ← 安装后用 install 目录
)

# 安装规则
install(TARGETS mylib
    EXPORT mylibTargets
    LIBRARY DESTINATION lib
    ARCHIVE DESTINATION lib
    RUNTIME DESTINATION bin
)
install(DIRECTORY include/ DESTINATION include)

# 导出 CMake 配置
install(EXPORT mylibTargets
    FILE mylibTargets.cmake
    NAMESPACE mylib::                    # ← 别的项目用 mylib::mylib 引用
    DESTINATION lib/cmake/mylib
)

# 生成 mylibConfig.cmake（下游 find_package 找的就是它）
include(CMakePackageConfigHelpers)
configure_package_config_file(
    Config.cmake.in
    ${CMAKE_CURRENT_BINARY_DIR}/mylibConfig.cmake
    INSTALL_DESTINATION lib/cmake/mylib
)
install(FILES ${CMAKE_CURRENT_BINARY_DIR}/mylibConfig.cmake
    DESTINATION lib/cmake/mylib
)
```

下游项目使用：

```cmake
find_package(mylib REQUIRED)
target_link_libraries(app PRIVATE mylib::mylib)
```

**结论**：一个"工程化"的库必须自带 install/export，让下游 `find_package` 无缝使用。**这是从"我一个人能编译"到"团队能复用"的门槛**。


## 5. 交叉编译模板

### 5.1 toolchain.cmake骨架

一份可复用的 ARM 交叉编译 toolchain 文件：

```cmake
# arm-linux-gnueabihf.cmake
set(CMAKE_SYSTEM_NAME Linux)                    # ← 告诉 CMake 目标是 Linux
set(CMAKE_SYSTEM_PROCESSOR arm)                 # ← 目标架构

set(TOOLCHAIN_ROOT /opt/gcc-arm-linux-gnueabihf)
set(CMAKE_C_COMPILER   ${TOOLCHAIN_ROOT}/bin/arm-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER ${TOOLCHAIN_ROOT}/bin/arm-linux-gnueabihf-g++)

# 关键：告诉 CMake 去哪找目标平台的头 / 库
set(CMAKE_SYSROOT      ${TOOLCHAIN_ROOT}/arm-linux-gnueabihf/libc)
set(CMAKE_FIND_ROOT_PATH
    ${CMAKE_SYSROOT}
    /opt/arm-thirdparty       # ← 交叉编译过的 Qt/OpenSSL 装在这
)

# 关键：搜索规则的三条铁律
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)    # ← 可执行程序去 host 找（比如 pkg-config）
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)     # ← 库只在 sysroot 里找
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)     # ← 头只在 sysroot 里找
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)     # ← Config 包只在 sysroot 里找

# 编译选项：架构、优化
set(CMAKE_C_FLAGS_INIT   "-march=armv7-a -mfpu=neon -mfloat-abi=hard")
set(CMAKE_CXX_FLAGS_INIT "-march=armv7-a -mfpu=neon -mfloat-abi=hard")
```

**用法**：

```bash
cmake -DCMAKE_TOOLCHAIN_FILE=./arm-linux-gnueabihf.cmake -B build
cmake --build build -j$(nproc)
```

**关键三行的作用**：

| 变量 | 值 | 作用 |
|---|---|---|
| `CMAKE_FIND_ROOT_PATH_MODE_LIBRARY` | ONLY | 强制 `find_library` 只在目标 sysroot 里找 → 避免误链 host 的 `.so` |
| `CMAKE_FIND_ROOT_PATH_MODE_INCLUDE` | ONLY | 强制头文件只在目标 sysroot 里找 |
| `CMAKE_FIND_ROOT_PATH_MODE_PROGRAM` | NEVER | 允许可执行文件从 host 找，比如 `pkg-config` `git` |

**这就是第 1 章报错的根因**：没设 `MODE_LIBRARY=ONLY`，CMake 就傻乎乎去 host 的 `/usr/lib` 里找 `libssl.so`，找到了 x86 版本，链进来自然崩。

### 5.2 三方库交叉编译

嵌入式项目里常见的三方库交叉编译流程：

**OpenSSL**（Makefile 派）：

```bash
export CROSS_COMPILE=arm-linux-gnueabihf-
./Configure linux-armv4 \
    --prefix=/opt/arm-thirdparty \
    --openssldir=/opt/arm-thirdparty/ssl \
    no-shared no-tests
make -j$(nproc) && make install
```

**curl**（autotools 派）：

```bash
./configure \
    --host=arm-linux-gnueabihf \
    --with-sysroot=/opt/arm-sysroot \
    --with-ssl=/opt/arm-thirdparty \
    --prefix=/opt/arm-thirdparty \
    --disable-shared --enable-static
make -j$(nproc) && make install
```

**mosquitto**（CMake 派）：

```bash
cmake -DCMAKE_TOOLCHAIN_FILE=./arm-linux-gnueabihf.cmake \
      -DCMAKE_INSTALL_PREFIX=/opt/arm-thirdparty \
      -DWITH_TLS=OFF -DDOCUMENTATION=OFF \
      -B build && cmake --build build --target install
```

**结论**：所有三方库，只有编译系统三大类，**Makefile / autotools / CMake**。每类的交叉编译"魔咒"不同，但套路一样：**告诉它 host 是谁、sysroot 在哪、装到哪**。

### 5.3 一套源码多平台

同一份 `CMakeLists.txt` 要支持 PC 调试 + ARM 落地 + AArch64 新平台，怎么做？

**核心手段**：把平台差异全部塞进 `toolchain.cmake` 文件里，业务代码保持平台无关。

```
项目目录：
├── CMakeLists.txt          ← 平台无关
├── src/                    ← 业务代码
├── toolchains/
│   ├── x86_64-linux.cmake  ← PC 调试
│   ├── arm-linux.cmake     ← ARMv7 落地
│   └── aarch64-linux.cmake ← 新平台
└── scripts/
    └── build.sh <platform>
```

**build.sh 骨架**：

```bash
#!/bin/sh
set -e
PLATFORM=${1:-x86_64}                                # 默认 PC 调试

BUILD_DIR=build-$PLATFORM
TOOLCHAIN=./toolchains/${PLATFORM}-linux.cmake

if [ "$PLATFORM" = "x86_64" ]; then
    cmake -B $BUILD_DIR
else
    cmake -DCMAKE_TOOLCHAIN_FILE=$TOOLCHAIN -B $BUILD_DIR
fi

cmake --build $BUILD_DIR -j$(nproc)
```

**业务代码里怎么处理平台差异**？两种方式：

```cmake
# 方式 1：通过变量
if(CMAKE_SYSTEM_PROCESSOR MATCHES "arm|aarch64")
    target_compile_definitions(app PRIVATE EMBEDDED_BUILD=1)
endif()
```

```cpp
// 方式 2：预处理宏
#if defined(__arm__) || defined(__aarch64__)
    // 嵌入式平台的实现
#else
    // PC 的实现
#endif
```

**结论**：多平台适配的关键是**"变化点集中化"**——所有跟平台相关的选择都放在 toolchain 文件和少数几处宏里，业务代码零感知。这与后面第 10 篇 GUI 里的**平台抽象层**是同一种思想。


## 6. 依赖管理策略

### 6.1 find_package三种模式

**疑惑**：`find_package(OpenSSL REQUIRED)` 到底去哪找？为什么有时找到、有时找不到？

**论证**：CMake 的 `find_package` 有**两种查找模式**：

```
Config 模式   ： 找 <Name>Config.cmake / <name>-config.cmake
              → 由库自己提供，最规范
              → 交叉编译时受 CMAKE_FIND_ROOT_PATH 控制

Module 模式   ： 找 Find<Name>.cmake（CMake 自带或项目里写的）
              → 老库常用，需要 CMake 官方或自己写一个 Find 模块
              → 常见的 FindOpenSSL、FindThreads 都是这类
```

**优先级**：默认先 Config 后 Module，可以用 `CONFIG` 或 `MODULE` 关键字强制：

```cmake
find_package(OpenSSL REQUIRED CONFIG)   # ← 强制走 Config 模式
find_package(Threads REQUIRED MODULE)   # ← 强制走 Module 模式
```

**排查顺序**（`find_package` 找不到时按这个查）：

1. 库有没有装？装到哪了？
2. `<name>Config.cmake` 的路径在不在 `CMAKE_PREFIX_PATH` 或 `CMAKE_FIND_ROOT_PATH` 里？
3. 交叉编译时 `MODE_PACKAGE` 是不是设成 `ONLY`，但库装到了 host 目录（sysroot 外）？

### 6.2 FetchContent与vcpkg

三种依赖管理方式的对比：

| 方式 | 原理 | 适用场景 | 缺点 |
|---|---|---|---|
| `find_package` | 系统或 sysroot 已装 | 稳定、大型三方库 | 需要预先交叉编译 |
| `FetchContent` | 构建时从 git 拉源码一起编 | 小型头文件库 / 想锁死版本 | 首次构建慢，需要网络 |
| vcpkg / conan | 包管理器统一管理 | 团队多人协作、多平台 | 学习成本、交叉编译配置繁琐 |

**FetchContent 示例**（推荐用于小型库）：

```cmake
include(FetchContent)
FetchContent_Declare(
    fmt
    GIT_REPOSITORY https://github.com/fmtlib/fmt.git
    GIT_TAG        10.2.1                          # ← 锁死版本
)
FetchContent_MakeAvailable(fmt)

target_link_libraries(app PRIVATE fmt::fmt)
```

**选择建议**：
- **大型库（Qt、Boost、OpenSSL）** → find_package，预先交叉编译
- **小型库（fmt、spdlog、nlohmann-json）** → FetchContent
- **团队规模大、跨项目复用** → vcpkg

### 6.3 静态vs动态链接

**疑惑**：嵌入式里到底选静态还是动态链接？

**论证**：这是一个**四维度权衡**：

| 维度 | 静态链接（.a） | 动态链接（.so） |
|---|---|---|
| 磁盘 | 每个可执行都带一份，磁盘占用大 | 一份 .so 多个用，磁盘小 |
| 内存 | 每个进程独占一份代码段 | 多进程共享代码段，省 RAM |
| 升级 | 改一行库就得重发所有可执行 | 只替换 .so 即可 |
| 许可证 | 静态链接 GPL 库 → 你的整个程序也要开源 | 动态链接 GPL 库 → 你的代码可以闭源 |

**嵌入式的典型策略**：
- **系统级库（libc、libpthread、libstdc++）** → 动态链接（这些必然装在 rootfs 里）
- **应用私有小库** → 静态链接（避免 `.so` 版本管理麻烦）
- **大型三方库（Qt、boost）** → 动态链接（磁盘和内存双压力）

**踩坑案例**：一个产品把整个 boost 静态链进 palmapp，二进制 300 MB，Flash 都塞不下，最后改回动态链接压到 30 MB。

**结论**：**没有全静态或全动态的最优解，按库分档**。系统库动态、私有库静态、大库动态，是绝大多数嵌入式项目的甜蜜点。


## 7. 编译加速与产出优化

### 7.1 ccache与ninja

**疑惑**：改一行代码要等 20 分钟，能不能更快？

**论证**：编译慢的根源有三个：
1. **重复编译**：改一个文件，为什么整个项目都编？
2. **编译器串行**：`make -j1` 时代？
3. **make 本身慢**：`make` 每次都要扫全项目决定要不要重编。

**ccache 解决"重复编译"**：

```
第一次编译 foo.cpp → 计算 (源码+编译参数) 的 hash → 编出 foo.o → 存进缓存
第二次编译 foo.cpp → hash 一样 → 直接从缓存取 foo.o
```

启用：

```bash
sudo apt install ccache
export PATH=/usr/lib/ccache:$PATH   # 或 CMake 里 set(CMAKE_CXX_COMPILER_LAUNCHER ccache)
```

**效果**：clean build 后再 clean build，命中率 95%+，20 分钟 → 30 秒。

**ninja 解决"make 慢"**：

```bash
sudo apt install ninja-build
cmake -G Ninja -B build && ninja -C build
```

Ninja 是**为速度设计的构建器**：
- 增量编译时扫描更快（一次读所有依赖图）
- 默认最大并行（自动检测 CPU 数）
- 输出简洁（只显示当前正在编的文件）

**对比 make 与 ninja**（10 万行 C++ 项目，clean build）：

| 工具 | 时间 | CPU 占用 |
|---|---|---|
| make -j1 | 25 min | 单核跑满 |
| make -j$(nproc) | 4 min | 多核跑满 |
| ninja | 3 min | 多核跑满 + 调度更好 |
| ninja + ccache（二次编） | 15 s | 主要是链接时间 |

### 7.2 distcc与并行

对于大型项目（百万行 C++），单机 CPU 不够怎么办？**distcc** 让编译任务分发到多台机器：

```
┌────────────┐        ┌───────────┐
│  开发机    │───────►│  编译机 A │  (8 核，专门跑 gcc)
│  ninja 主控│  ...   ├───────────┤
│  distcc    │───────►│  编译机 B │
└────────────┘        └───────────┘
                       └───────────┘
```

**启用**（简版）：

```bash
# 每台编译机启动 distcc daemon
distccd --daemon --allow 192.168.1.0/24

# 开发机
export DISTCC_HOSTS='localhost/8 192.168.1.101/16 192.168.1.102/16'
export CC='distcc arm-linux-gnueabihf-gcc'
export CXX='distcc arm-linux-gnueabihf-g++'
cmake -B build && ninja -C build
```

**效果**：从 24 核到 4 台机器共 96 核，编译时间基本按核数线性下降。

**ccache + distcc 组合**：ccache 在前，distcc 在后。命中缓存的直接取，未命中的再分发。

### 7.3 二进制瘦身

编译完还要打包上板，**二进制越小越好**（省 Flash、省启动加载时间）：

**招数一：strip 剥离符号表**

```bash
arm-linux-gnueabihf-strip --strip-unneeded palmapp
# 一般能瘦 30~50%
```

**招数二：编译时 `-Os` 优化尺寸**

```cmake
set(CMAKE_CXX_FLAGS_RELEASE "-Os -DNDEBUG")   # 而非默认 -O2
```

**招数三：LTO（链接时优化）跨文件消死代码**

```cmake
include(CheckIPOSupported)
check_ipo_supported(RESULT ipo_ok)
if(ipo_ok)
    set(CMAKE_INTERPROCEDURAL_OPTIMIZATION TRUE)
endif()
```

**招数四：`--gc-sections` 丢弃未用代码段**

```cmake
target_compile_options(app PRIVATE -ffunction-sections -fdata-sections)
target_link_options(app PRIVATE -Wl,--gc-sections)
```

**招数五：UPX 压缩（谨慎用）**

```bash
upx --best palmapp
```

会让二进制启动时先解压再执行，**首次启动变慢 100~300ms**，嵌入式介意启动时间的场景不建议用。

**综合案例**：某 Qt 应用初始 45 MB，`-Os` + LTO + strip + `--gc-sections` → 12 MB，压缩比 73%。


## 8. 选型决策树

### 8.1 五个维度的问题

面对一个新项目，问自己五个问题：

1. **目标架构？**（ARMv7 硬浮点 / AArch64 / MIPS / RISC-V）
2. **rootfs 大小？**（16MB 以下选 musl，否则 glibc）
3. **要不要 Qt/Boost 这类大型库？**（有则不能选静态 + musl 组合）
4. **是否多平台适配？**（要多平台 → toolchain 文件方案）
5. **CI 环境如何？**（有大服务器 → ninja + distcc，个人机 → ccache + ninja）

### 8.2 一张图选完

```
┌────────────────────────────────────────────────────────────┐
│  START：新项目要选构建方案                                    │
└──────────────────────┬─────────────────────────────────────┘
                       │
             ┌─────────┴─────────┐
             │  只支持一个平台？   │
             └─────────┬─────────┘
              是       │       否（多平台）
               │       │        │
               ▼       │        ▼
    简单 Makefile ok   │   一定要 CMake + toolchain 文件
                       │        │
                       │        ▼
                       │  ┌──────────────────┐
                       │  │  rootfs < 32MB？ │
                       │  └──────────────────┘
                       │       是    否
                       │        │    │
                       │        ▼    ▼
                       │       musl  glibc
                       │        │    │
                       │        ▼    ▼
                       │  ┌──────────────────┐
                       │  │  要 Qt/Boost？    │
                       │  └──────────────────┘
                       │       是    否
                       │        │    │
                       │        ▼    ▼
                       │      动态   看单/多进程
                       │       Qt    (多进程动态、单进程静态可)
                       ▼
                  加编译加速：ccache + ninja + (可选 distcc)
```

### 8.3 常见误用

**误用 1**：**用 host 的 pkg-config 找 target 的库**

```bash
# ❌ 错误：pkg-config 找的是 host 的 /usr/lib/pkgconfig
pkg-config --cflags openssl
# ✅ 正确：交叉编译时用 PKG_CONFIG_LIBDIR 隔离
export PKG_CONFIG_LIBDIR=/opt/arm-sysroot/usr/lib/pkgconfig
export PKG_CONFIG_SYSROOT_DIR=/opt/arm-sysroot
```

**误用 2**：**把 `-I` 硬编码进 CMakeLists，破坏了 target 属性传递**

```cmake
# ❌ 全局副作用
include_directories(/opt/arm-thirdparty/include)
# ✅ 挂到 target 上
target_include_directories(app PRIVATE /opt/arm-thirdparty/include)
```

**误用 3**：**Release 忘了关 `-g`，二进制多了 30 MB 调试符号**

```cmake
# ✅ 显式区分
set(CMAKE_BUILD_TYPE Release)
# 或用 -g 但装机前 strip
```

**误用 4**：**发布用了 `-O3`**，实际 `-O2` 已经够，`-O3` 有时会引入未定义行为放大。


## 9. 可靠性与调试

### 9.1 链接错误怎么排

**场景 A**：`cannot find -lssl`

排查步骤：

```bash
# 1. 库到底装了没？装到哪了？
find /opt/arm-sysroot -name "libssl*"
find /opt/arm-thirdparty -name "libssl*"

# 2. 编译时到底往哪找了？加 -v 看
arm-linux-gnueabihf-gcc -v -lssl 2>&1 | grep SEARCH_DIR
# 输出：SEARCH_DIR("=/lib") SEARCH_DIR("=/usr/lib") ...

# 3. 补上正确的 -L 或改 sysroot
```

**场景 B**：`undefined reference to 'SSL_new'`

```bash
# 检查库里有没有这个符号
arm-linux-gnueabihf-nm -D /opt/arm-thirdparty/lib/libssl.so | grep SSL_new
# 有 → 链接顺序问题（把 -lssl 放到 -lmylib 后面）
# 没 → 库版本不对，SSL_new 可能改名了或被移除
```

**场景 C**：`multiple definition of`

一个符号在多个 `.a` 里都实现了。排查：

```bash
for f in libA.a libB.a; do
    arm-linux-gnueabihf-nm --defined-only $f | grep "SSL_new"
done
```

### 9.2 运行时找不到so怎么查

**场景**：板子上跑起来报 `error while loading shared libraries`。

**排查 SOP**：

```bash
# 1. 应用需要哪些 .so？
ldd /app/palmapp/bin/palmapp                    # 静态查
readelf -d /app/palmapp/bin/palmapp | grep NEEDED

# 2. 应用当前实际能找到的 .so 搜索路径
LD_DEBUG=libs /app/palmapp/bin/palmapp 2>&1 | grep search
# 输出：search path=/app/palmapp/lib:/usr/lib:/lib

# 3. .so 真的存在吗？
find / -name "libQt5Core.so*" 2>/dev/null

# 4. 存在但版本不对？
readelf -d libQt5Core.so.5 | grep SONAME    # SONAME 是运行时匹配的关键
```

**版本不匹配的深挖**：

```bash
# 应用需要 Qt_5.15
readelf -a /app/palmapp/bin/palmapp | grep "Version needs"
# 库提供的版本
strings libQt5Core.so.5 | grep "^Qt_5"
```

**修复方案**：
- 少了 .so → 装上或补全 `LD_LIBRARY_PATH`
- 版本不对 → 重新按运行时目标平台的 SDK 编译


## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到第 1 章"新同学的构建噩梦"，五条报错现在可以逐条对上原理：

| 现象 | 根因 | 章节 |
|---|---|---|
| `cannot find -lssl` | 没设 sysroot 与 `FIND_ROOT_PATH_MODE_LIBRARY=ONLY`，编译器不知道去哪找 ARM 库 | §3.2 + §5.1 |
| `file format not recognized` | 误链了 host 的 x86 `.so`，本质是上一条的延续 | §5.1 |
| `No such file or directory`（运行时） | rootfs 里没装 Qt，or `LD_LIBRARY_PATH` 未设 | §9.2 |
| `undefined symbol` | 编译期 Qt 5.15 头，运行时 Qt 5.11 `.so`，SONAME 不匹配 | §9.2 |
| 每次编 20 分钟 | 没上 ccache + ninja + 并行 | §7 |

**正确的做法**（对应第 1 章的报错）：

```bash
# 1. 用工程化的 toolchain 文件
cmake -DCMAKE_TOOLCHAIN_FILE=./toolchains/arm-linux-gnueabihf.cmake \
      -DCMAKE_PREFIX_PATH=/opt/arm-thirdparty \      # ← 让 find_package 找到预编译库
      -G Ninja -B build-arm

# 2. 上 ccache
cmake ... -DCMAKE_CXX_COMPILER_LAUNCHER=ccache

# 3. ninja 并行
ninja -C build-arm -j$(nproc)

# 4. 上板前 strip
arm-linux-gnueabihf-strip --strip-unneeded build-arm/palmapp

# 5. 打包时把 .so 也带上，避免运行时找不到
tar czf release-arm.tar.gz build-arm/palmapp lib/
```

### 10.2 一次编译的一生

从敲下 `cmake --build` 到产出可上板的二进制，完整链路：

```
cmake --build build
    │
    ├─ 【1.配置阶段】§4-5
    │   ├─ 读 CMakeLists.txt
    │   ├─ 读 toolchain.cmake                    ─── §5.1
    │   ├─ find_package(OpenSSL) → sysroot 里找   ─── §6.1
    │   ├─ target_link_libraries → 依赖图         ─── §4.2
    │   └─ 生成 build.ninja / Makefile
    │
    ├─ 【2.编译阶段】§3 + §7
    │   ├─ 每个 .cpp 计算 hash（ccache 拦截）    ─── §7.1
    │   ├─ ccache 未命中 → 调用 arm-g++          ─── §3.1
    │   │   ├─ 前端：读源码 + sysroot 头         ─── §3.2
    │   │   ├─ 中端：优化 (-Os / LTO)            ─── §7.3
    │   │   └─ 后端：生成 ARM 指令 → .o
    │   └─ ccache 命中 → 直接取缓存
    │
    ├─ 【3.链接阶段】§6
    │   ├─ arm-ld 收集所有 .o + .a               ─── §6.3
    │   ├─ 找 .so（NEEDED 记录 SONAME）          ─── §9.2
    │   ├─ --gc-sections 丢死代码                ─── §7.3
    │   └─ 产出 ELF 可执行
    │
    └─ 【4.打包阶段】§7.3
        ├─ strip 去符号表
        ├─ 拷贝 .so 到 lib/ 目录
        └─ tar/mkfs 打包
```

### 10.3 设计哲学回扣

**哲学 1：把变化点集中到边界文件**

toolchain.cmake 是"目标平台变化点"的边界，业务 CMakeLists 是"业务变化点"的边界。**变化点越集中，越容易被审查、被复用、被替换**。这与 01 篇里的"启动/运行/停止三段分离"是同一种手法。

**哲学 2：以 target 为中心，用可见性做信息封装**

`PRIVATE/PUBLIC/INTERFACE` 是 CMake 的"访问修饰符"，与 C++ 类的 `public/private` 同源。**依赖是有方向的、有边界的，不是全局共享的**。这条哲学能防止一个模块 A 的改动波及不相关的模块 B。

**哲学 3：可复现优先于速度，缓存优先于重跑**

ccache 的思想是"同样的输入必然产出同样的输出"，把这个不变式利用起来。**软件工程里所有的加速手段，本质都是识别"什么是可缓存的"**。CDN、K8s 镜像层、Docker build cache，全是这个原理。

**哲学 4：分层是治理复杂度的唯一方式**

工具链 → sysroot → 构建 → 打包，一层解决一件事。**任何试图把四层揉在一起的"一键构建脚本"，最终都会变成不可维护的巨石**。分层不是麻烦，是让麻烦不失控的手段。

**根 CMakeLists 骨架**：

```cmake
cmake_minimum_required(VERSION 3.16)
project(myproject VERSION 1.0.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

if(NOT CMAKE_BUILD_TYPE)
    set(CMAKE_BUILD_TYPE Release)
endif()

# 上 ccache
find_program(CCACHE ccache)
if(CCACHE)
    set(CMAKE_CXX_COMPILER_LAUNCHER ${CCACHE})
endif()

# 编译警告
include(cmake/CompilerFlags.cmake)

add_subdirectory(libs)
add_subdirectory(src)
```

**60 秒排错命令清单**：

```bash
# 1. 工具链装了没？
arm-linux-gnueabihf-gcc --version

# 2. sysroot 里有 libssl 吗？
find $SYSROOT -name "libssl*"

# 3. 编译时到底往哪找 lib？
arm-linux-gnueabihf-gcc -Wl,--verbose -lssl 2>&1 | grep succeeded

# 4. 可执行文件依赖了哪些 .so？
arm-linux-gnueabihf-readelf -d ./palmapp | grep NEEDED

# 5. 板子上 .so 缺哪个？
LD_DEBUG=libs ./palmapp 2>&1 | head -50

# 6. 编译慢，ccache 命中率多少？
ccache -s

# 7. 二进制多大？
arm-linux-gnueabihf-size ./palmapp
```

```

```
