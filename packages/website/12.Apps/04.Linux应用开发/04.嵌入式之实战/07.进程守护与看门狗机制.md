## 1. 案例引入

### 1.1 一夜间三千台设备失联

一个安防摄像头产品，凌晨 3 点云端监控大屏突然一片红：3200 台设备同时"离线"。运维值班盯了 10 分钟才反应过来——不是网络挂了，是**设备主进程都挂了**，且**没有自动拉起**。

排查设备端的守护脚本：

```bash
# /etc/init.d/camera_watchdog.sh
#!/bin/sh
while true; do
    if ! pidof camera_app > /dev/null; then
        echo "$(date): camera_app died, restarting..." >> /var/log/watchdog.log
        /app/camera_app &
    fi
    sleep 10
done
```

以及 camera_app 内部的"自检"：

```cpp
void CameraApp::run() {
    watchdog_.start();                        // ← 一个独立线程喂 /dev/watchdog
    for (;;) {
        auto frame = capture();               // ← 阻塞采集
        encode(frame);
        stream(frame);
    }
}

void Watchdog::start() {
    std::thread([this] {
        int fd = open("/dev/watchdog", O_WRONLY);
        for (;;) {
            write(fd, "\0", 1);               // ← 5 秒喂一次狗
            std::this_thread::sleep_for(5s);
        }
    }).detach();
}
```

现场诊断结果：
- **每台设备**：`camera_app` 主线程死锁，卡在 `encode()` 里等一把从来不释放的锁
- **喂狗线程还活着** → 硬件看门狗不触发
- **主线程活着（没崩）** → shell 脚本 `pidof` 检查也返回"活着"
- **网络心跳线程也活着** → 云端看到设备"在线"但没数据

**看起来所有守护机制都在跑，但设备实际是死的**。

售后凌晨紧急上门 200 台，重启后正常。之后一周复盘时，团队发现最原始的问题：**"进程活着"不代表"业务活着"**。

### 1.2 顺藤摸到根因

- **假设 1**：`pidof` 有效吗？，pidof 只看进程名对应的 PID 是否存在，进程死锁、CPU 卡死时**进程仍然存在**，pidof 返回真。→ 引出 **假活 vs 真活**。
- **假设 2**：喂狗线程独立于主线程，为什么这是错的？，看似"独立"更可靠，实际是**盲喂**——主线程死了它还在喂，硬件看门狗永远不触发。→ 引出 **喂狗策略**。
- **假设 3**：shell 脚本 `sleep 10 + pidof` 有什么问题？，除了假活，还有**竞态**：如果重启期间脚本又检查一次，会误启动第二个实例。→ 引出 **pidfile + flock**。
- **假设 4**：如果检测出死锁了，该重启进程还是重启整机？，得看：只是这个进程的问题（重启进程），还是外设/内核也异常（重启整机）。→ 引出 **级联恢复**。
- **假设 5**：为什么 3000 台同时挂？，可能是同一个云端配置下发触发了 bug，或凌晨 3 点某个定时任务集中触发。**恢复策略也要防雪崩**。→ 引出 **恢复的 jitter**。

```
① 硬件、systemd、应用层各防什么？        → 第 2、3、4、5 章
② 心跳怎么设计才能真正反映业务活着？      → 第 5 章
③ 单进程守护和多进程守护有什么区别？      → 第 7 章
④ 反复崩溃怎么止损？                     → 第 6 章
⑤ 什么时候该重启进程，什么时候该重启整机？→ 第 6 章
```

### 1.3 我们要回答什么

本篇讲**嵌入式设备的"生存机制"**。核心不是"进程别挂"，是"挂了能自动、正确、快速地活回来"。

```
守护体系全景 (第 2 章) → 三层防御
   ↓
硬件看门狗 (第 3 章) → 最底层兜底
   ↓
systemd 守护 (第 4 章) → 进程级重启
   ↓
应用层自检 (第 5 章) → 检测"假活"
   ↓
级联恢复 (第 6 章) → 逐级升级
   ↓
多进程守护 (第 7 章) → 复杂场景
   ↓
选型 → 排错 → 综合
```

> 📌 **本篇定位**：前面几篇讲"怎么让业务跑得好"，这一篇讲"怎么让业务出问题时快速恢复"。可靠性不是靠不出问题达到的，是靠"出了问题能扛住"达到的。


## 2. 守护体系概览

### 2.1 三层看门狗

```
┌──────────────────────────────────────────────────────────────┐
│                       三层守护体系                             │
│                                                                │
│  应用层 ──►【第 3 层】应用层健康自检                            │
│           - 心跳、超时、业务指标                                │
│           - 检测"假活"                                          │
│           - 触发：重启子模块或自杀                              │
│                                                                │
│  systemd ──►【第 2 层】进程级 Restart                          │
│           - 检测进程退出                                        │
│           - 检测 systemd watchdog 超时                          │
│           - 触发：拉起进程                                      │
│                                                                │
│  内核 ──►【第 1 层】硬件看门狗                                  │
│           - /dev/watchdog                                       │
│           - 超时不喂 → CPU 硬复位                                │
│           - 触发：整机重启                                       │
└──────────────────────────────────────────────────────────────┘
```

**每层负责一种"死"**：

| 层 | 检测什么 | 恢复 |
|---|---|---|
| 应用层 | 业务死锁、逻辑卡死、外设无响应 | 重启子模块 → 自杀让 systemd 拉 |
| systemd | 进程崩溃、abort、被 kill | 重启进程 |
| 硬件看门狗 | 内核挂了、systemd 挂了、驱动死循环 | 整机重启 |

### 2.2 为什么要分三层

**疑惑**：只用硬件看门狗不就行了吗？

**论证**：**恢复代价从下往上急剧增大**。硬件看门狗一响 = 整机断电重启 = 用户体验极差、状态全丢、还可能雪崩。**每一层都是为了"用更轻的手段解决更早发现的问题"**。

- 应用层发现死锁 → 只重启一个线程 → 用户无感
- systemd 发现进程死 → 重启进程 → 3~5 秒黑屏
- 硬件看门狗触发 → 重启整机 → 30~60 秒不可用

**结论**：**能上层解决就上层解决，硬件看门狗是最后一根稻草**。第 1 章的错误在于——只有第 1 层和第 2 层，第 3 层设计错了（喂狗独立于主线程），三层都失效。


## 3. 硬件看门狗

### 3.1 dev-watchdog的用法

Linux 提供 `/dev/watchdog` 字符设备接口，写入任意数据即"喂狗"：

```cpp
int fd = open("/dev/watchdog", O_WRONLY);
if (fd < 0) { /* 处理错误 */ }

// 设置超时（秒）
int timeout = 30;
ioctl(fd, WDIOC_SETTIMEOUT, &timeout);

// 喂狗（写任意字节）
write(fd, "\0", 1);

// 关闭前发"magic close"防止关闭后立即触发
write(fd, "V", 1);
close(fd);
```

**关键 ioctl**：

| ioctl | 用途 |
|---|---|
| `WDIOC_SETTIMEOUT` | 设置超时秒数 |
| `WDIOC_GETTIMEOUT` | 获取超时 |
| `WDIOC_KEEPALIVE` | 显式喂狗 |
| `WDIOC_GETSTATUS` | 上次复位原因 |

**"magic close"约定**：如果没写 `V` 就 close，看门狗**继续计时**（防止误关闭）。写了 `V` 再 close，才真正停止。

### 3.2 谁来喂狗

**核心决策**：**喂狗必须与业务主循环绑定**，不能独立。

- ❌ **独立喂狗线程**：主线程死锁时喂狗还活着，硬件看门狗永远不触发
- ✅ **主线程喂狗**：主线程卡了 → 超时不喂 → 复位

**推荐模式：业务心跳喂狗**

```cpp
class Watchdog {
public:
    void init() {
        fd_ = open("/dev/watchdog", O_WRONLY);
        int t = 30; ioctl(fd_, WDIOC_SETTIMEOUT, &t);
    }
    // 从业务主循环里调用
    void feed() { write(fd_, "\0", 1); }
    // 收到多个业务线程的心跳后才喂
    void heartbeat(int module_id) {
        auto now = std::chrono::steady_clock::now();
        beats_[module_id] = now;
        // 只有所有关键模块都近期喂过，才喂硬狗
        for (auto& [id, t] : beats_) {
            if (now - t > 10s) return;         // 有模块卡住 → 不喂
        }
        write(fd_, "\0", 1);
    }
private:
    int fd_;
    std::map<int, std::chrono::steady_clock::time_point> beats_;
};
```

**核心思想**：**硬狗不是"进程还活着"就喂，是"所有关键模块都还活着"才喂**。第 1 章就是错在这一步。

### 3.3 死马撞不倒硬件

**硬件看门狗的"救不了"的场景**：
1. **上电异常**：还没跑到 open watchdog 就挂了 → 硬狗不启动
2. **内核 panic**：如果 panic 时中断关闭，看门狗还能触发（多数芯片）
3. **卡在中断**：CPU 卡在中断处理没退出 → 硬狗照样触发 → 重启

**硬件看门狗最强的地方**：**它是独立于 CPU 的硬件模块**。CPU 死了它照跑，超时就拉 RESET 引脚。

**注意**：某些 SoC 的看门狗其实是内核软件模拟的（`softdog` 模块），这种"硬狗"内核挂了就跟着挂了。**产品必须确认用的是真正的硬件看门狗**。


## 4. systemd守护

### 4.1 Restart策略

systemd unit 文件里 `Restart=` 是最常用的守护开关：

| 值 | 含义 | 用途 |
|---|---|---|
| no | 不重启 | 短命脚本 |
| on-success | 正常退出才重启 | 定时任务 |
| on-failure | 非零退出、被 kill 才重启 | 常规应用 |
| on-abnormal | 崩溃、超时才重启 | 应用希望正常退出 = 停止 |
| on-abort | 只有 SIGABRT 触发 | 只保护 assert 失败 |
| on-watchdog | watchdog 超时才重启 | 配合 sd_notify |
| always | 无论怎么退出都重启 | 关键守护进程 |

**典型 unit 文件**：

```ini
[Unit]
Description=Camera Application
After=network.target
Requires=camera-driver.service

[Service]
Type=simple
ExecStartPre=/usr/bin/camera_selftest.sh              # 启动前自检
ExecStart=/app/camera_app
Restart=on-failure
RestartSec=5s                                          # 崩溃后等 5s 再拉起
StartLimitBurst=5                                      # 60s 内最多重启 5 次
StartLimitIntervalSec=60s
WatchdogSec=30s                                        # 30s 不喂 → 认为死
NotifyAccess=main

[Install]
WantedBy=multi-user.target
```

### 4.2 StartLimit防抖

**问题**：如果进程一起来就崩，`Restart=always` 会造成**死循环快速重启**，撑爆日志、把 CPU 打满。

**StartLimit** 就是刹车：`StartLimitBurst=5` + `StartLimitIntervalSec=60s` 意味着 60 秒内最多重启 5 次，超过则**放弃**。

**放弃后怎么办**？三个选择：

```ini
StartLimitAction=none         # 就这样了（默认）
StartLimitAction=reboot       # 整机重启（升到第 1 层看门狗）
StartLimitAction=reboot-force # 强制重启（跳过 shutdown 流程）
```

**推荐组合**：进程级 → 3 次内快速拉起 → 5 次仍失败 → `reboot`（让整机重启，回归初始状态）。**这就是级联恢复**。

### 4.3 systemd自带watchdog

systemd 自身就是一个**"进程看门狗 + 硬件看门狗代理"**：

```
sd_notify(WATCHDOG=1) ─── 应用喂 systemd
       │
       ▼
   systemd 定时喂
       │
       ▼
   /dev/watchdog（硬件）
```

**应用侧代码**：

```cpp
#include <systemd/sd-daemon.h>

// 初始化
sd_notify(0, "READY=1");

// 每次业务循环
for (;;) {
    doOneRound();
    sd_notify(0, "WATCHDOG=1");                        // 喂 systemd
}
```

**unit 配置**：

```ini
Type=notify
WatchdogSec=30s
Restart=on-watchdog
```

**优势**：
- **应用不直接碰 /dev/watchdog**，systemd 统一管理
- **业务真死了**（WATCHDOG=1 没发）→ systemd 会 SIGABRT 你，触发 core dump，再重启
- **systemd 死了** → 硬件看门狗超时 → 整机重启
- **应用主动 `STOPPING=1`** → 优雅退出，systemd 不认为是崩溃

**结论**：**能上 systemd notify watchdog 就上**，比自己管 `/dev/watchdog` 优雅得多。


## 5. 应用层健康自检

### 5.1 假活与真活

**"活着"的四个层次**：

```
Level 1  进程存在 (ps 能看到)          ← pidof 只测这个
Level 2  进程未阻塞 (CPU 有活动)       ← top 能看
Level 3  主线程不死锁                  ← 心跳能反映
Level 4  业务指标正常（能采到数据）    ← 业务健康度
```

**第 1 章的死锁**：Level 1、2 都活着，Level 3 死了。**只做 Level 1 检测就是耍流氓**。

### 5.2 心跳线程独立设计

**基本模式**：主线程周期性打卡，独立监听线程判活。

```cpp
class HealthMonitor {
public:
    void beat(const std::string& mod) {
        beats_[mod] = std::chrono::steady_clock::now();
    }

    // 独立线程运行
    void watchLoop() {
        while (running_) {
            auto now = std::chrono::steady_clock::now();
            for (auto& [mod, t] : beats_) {
                if (now - t > timeouts_[mod]) {
                    LOG_ERROR("%s stuck for %lds", mod.c_str(),
                              std::chrono::duration_cast<std::chrono::seconds>(now-t).count());
                    onModuleStuck(mod);            // 尝试恢复
                }
            }
            std::this_thread::sleep_for(1s);
        }
    }

    void onModuleStuck(const std::string& mod) {
        // 策略 1：先尝试重启子模块
        if (modules_[mod]->softRestart()) return;
        // 策略 2：主动退出让 systemd 拉起
        std::abort();                              // ← core dump 供事后分析
    }
};
```

**规则**：
- **打卡在业务关键点**（如"我又处理了一帧""我又循环了一次"）
- **超时值 = 正常周期 × 3**（预留抖动空间）
- **心跳失败先尝试软恢复**，不行才自杀

### 5.3 多维度健康度

**单点心跳可能骗人**——业务本身有 bug 但循环还在跑。**多维度健康度**才靠谱：

| 维度 | 检查方式 | 阈值示例 |
|---|---|---|
| 主循环心跳 | 每帧打卡 | 超 3 秒未打 = 死 |
| 内存 | RSS | 超 300 MB = 泄漏 |
| CPU | 单进程占用 | 长期 >80% = 死循环 |
| 业务数据量 | 单位时间处理帧数 | <1 fps = 卡死 |
| 网络 | 上次收到心跳 ACK | 超 60s = 断网 |
| 外设 | 传感器最近数据时间 | 超 10s = 外设挂 |

**每个维度分开告警，联合决定"是否要重启"**。

```cpp
enum HealthLevel { GREEN, YELLOW, RED };

HealthLevel evaluate() {
    if (framesPerSec() < 1) return RED;             // 直接重启
    if (rssMb() > 300) return YELLOW;               // 观察
    if (lastSensor() > 10s) return YELLOW;
    return GREEN;
}
```


## 6. 级联恢复策略

### 6.1 从模块重启到整机重启

**级联规则**：**能小则小，逐级升级**。

```
1. 模块级：某个 worker 卡住 → 停 worker + 重启 worker
   ↓ 恢复失败 or 短期内多次
2. 进程级：全进程退出 → systemd 拉起
   ↓ 60s 内 5 次仍崩溃
3. 整机级：systemd StartLimitAction=reboot → 重启
   ↓ 整机启动异常（三次 reboot 未成功）
4. 硬件级：uboot 的 bootcount 检测 → 切到备用分区 或 走 recovery
```

**实现要点**：

```ini
# /etc/systemd/system/camera_app.service
[Service]
Restart=on-failure
RestartSec=5s
StartLimitBurst=5
StartLimitIntervalSec=60s
StartLimitAction=reboot                # ← 快速崩太多 → 整机重启
```

```
# /boot/uboot 的 bootcount 逻辑（伪代码）
if bootcount > 3:
    # 三次都启动失败，切到备用分区
    setenv bootpart system_b
    reset
```

### 6.2 恢复现场保护

**恢复不能让"上次的问题"再次发生**：

1. **崩溃前 dump 状态**：主动 `abort()` 前把关键状态 dump 到 `/var/crash/` 或 syslog
2. **重启后跳过毒消息**：如果崩溃因为"上一条消息处理"，重启后要跳过它
3. **限流恢复**：整机重启后不要立刻回归高负载，先跑一段"预热期"
4. **上报云端**：崩溃 → 云端知晓 → 决策是否远程干预

**毒消息问题**：

```cpp
// 保护性设计：每次处理消息前记录 pending，处理完清除
class MessageProcessor {
    void process(Msg m) {
        writePending("/var/state/pending.msg", m);   // 落盘
        try { doWork(m); }
        catch(...) { logAndRethrow(); }
        clearPending();                              // 处理成功
    }
    // 启动时
    void init() {
        if (auto m = readPending()) {
            // 检查这条消息是不是导致上次崩溃的
            if (crashLastRun()) {
                LOG_ERROR("Skipping poison msg: %s", m.id.c_str());
                clearPending();
                return;
            }
            process(*m);                             // 恢复处理
        }
    }
};
```


## 7. 多进程守护

### 7.1 父子监控与SIGCHLD

**多进程架构**（如"主控进程 + N 个 worker"）需要一个 supervisor 管理子进程。

**关键机制**：`SIGCHLD` + `waitpid`

```cpp
void Supervisor::run() {
    signal(SIGCHLD, [](int){});                       // 只是让 pause 醒过来

    for (const auto& c : childrenCfg_) startChild(c);

    for (;;) {
        int status;
        pid_t pid = waitpid(-1, &status, WNOHANG);    // 收尸
        if (pid > 0) {
            LOG_INFO("child %d exited, status=%d", pid, status);
            auto c = findByPid(pid);
            if (shouldRestart(c, status)) {
                std::this_thread::sleep_for(backoff(c));
                startChild(c);                        // 重启
            }
        }
        pause();                                      // 等下一个信号
    }
}
```

**注意**：**每个子进程都要 waitpid**，否则会产生僵尸进程占 PID。

**推荐做法**：**直接用 systemd 而不是自研 supervisor**。除非你的场景 systemd 不适合（如没装 systemd 的 BusyBox 系统），才自研。

### 7.2 pidfile与flock

**目的**：**保证同一时刻只有一个实例**。

**古典 pidfile**：

```cpp
// ❌ 有竞态
FILE* f = fopen("/var/run/app.pid", "w");
fprintf(f, "%d\n", getpid());
fclose(f);
```

**问题**：进程崩溃时 pidfile 不会自动删，重启会看到"旧 pid"，误判"已在运行"。

**flock 方案（推荐）**：

```cpp
int fd = open("/var/run/app.pid", O_CREAT | O_RDWR, 0644);
if (flock(fd, LOCK_EX | LOCK_NB) != 0) {
    fprintf(stderr, "Already running\n");
    return 1;
}
// 写入自己的 pid
ftruncate(fd, 0);
dprintf(fd, "%d\n", getpid());
// fd 不 close，进程退出时锁自动释放
```

**关键**：`flock` 是**进程持有的锁**，进程死了内核自动释放，不需要清理。

**pidof 的正确使用**：**只作为辅助**（确认进程还活着），**不作为判活主机制**（因为假活问题）。


## 8. 选型决策树

### 8.1 五个维度

1. **业务类型**：GUI 应用 / 后台服务 / 关键实时任务
2. **恢复容忍**：允许 5s 黑屏 / 完全无感 / 挂了就挂了
3. **系统基座**：systemd / BusyBox init / 自研 init
4. **多进程**：单进程 / 多进程配合 / 松耦合微服务
5. **可靠性等级**：消费级 / 工业级 / 车规级

### 8.2 一张图选完

```
START
   │
   ├── 是关键守护进程？── 否 ──► 什么都不加
   │        │
   │        是
   │        ▼
   ├── 有 systemd？── 否 ──► BusyBox init + 自写 supervisor + pidfile
   │        │
   │        是
   │        ▼
   ├── 只需重启进程？── 是 ──► Restart=on-failure + StartLimit
   │        │
   │        否（要防死锁）
   │        ▼
   ├── 需要检测业务卡住？── 是 ──► sd_notify(WATCHDOG=1) + Type=notify
   │        │
   │        否
   │        ▼
   └── 需要硬件兜底？── 是 ──► systemd WatchdogSec + /dev/watchdog

多进程场景 → 上 systemd Unit 依赖树（Requires/After）
关键设备 → 三层看门狗全上（硬件 + systemd + 应用心跳）
```

### 8.3 常见误用

**误用 1**：**独立线程喂硬狗**

```cpp
std::thread([] { for(;;) { write(wd_fd, "\0", 1); sleep(5); } }).detach();
// ❌ 主线程死锁时它还在喂 → 硬狗永不触发
// ✅ 主循环喂狗，或多模块联合喂狗
```

**误用 2**：**shell 脚本 pidof 循环判活**

```bash
while true; do
    pidof app > /dev/null || start app          # ❌ 假活、竞态
    sleep 10
done
# ✅ 用 systemd 或 sd_notify
```

**误用 3**：**Restart=always 无 StartLimit**

```
crash → 立刻 restart → 又 crash → 死循环 → 日志爆炸、CPU 打满
✅ 加 StartLimitBurst + StartLimitIntervalSec
```

**误用 4**：**主动 `_exit(0)` 后指望 systemd 拉**

```cpp
_exit(0);                                          // 正常退出
// ❌ Restart=on-failure 不会拉起
// ✅ 要么 exit(非零)，要么用 Restart=always
```

**误用 5**：**recovery 分区不做防抖**

```
每次崩溃都切 recovery → 分区来回切 → 更混乱
✅ bootcount 判定"三次都崩"再切
```


## 9. 可靠性与调试

### 9.1 反复重启的排查

**征兆**：设备启动 → 跑几分钟 → 重启 → 循环。

**排查 SOP**：

```bash
# 1. 上次崩溃的原因（systemd）
systemctl status camera_app
journalctl -u camera_app -n 100 --no-pager

# 2. 上次重启是不是硬件看门狗触发？
cat /proc/sys/kernel/watchdog_pretimeout  # 若有
dmesg | grep -i "watchdog"
cat /sys/class/watchdog/watchdog0/bootstatus

# 3. 有没有 core dump？
ls -la /var/crash/
coredumpctl list                        # systemd-coredump

# 4. StartLimitAction=reboot 触发的？
journalctl -b -1 | grep -i "start-limit"

# 5. bootcount 记录
fw_printenv bootcount 2>/dev/null
```

**基于 core dump 分析**：

```bash
coredumpctl gdb <PID>
(gdb) bt full
(gdb) info threads
(gdb) thread apply all bt
```

### 9.2 假死的排查

**征兆**：进程存在、CPU 有活动，但业务不推进。

**排查**：

```bash
# 1. 看进程状态
ps -eLf | grep camera_app                  # 每个线程的状态
top -H -p $(pidof camera_app)             # 哪个线程 100% CPU

# 2. 附上 gdb 看栈
gdb -p $(pidof camera_app)
(gdb) thread apply all bt

# 3. 系统调用层面
strace -p $(pidof camera_app) -f -e trace=all 2>&1 | head -100

# 4. 死锁探测（多把 mutex）
# gdb 里对每个线程看它在等哪把锁

# 5. IO 阻塞？
cat /proc/$(pidof camera_app)/wchan       # 内核里等在哪个函数
cat /proc/$(pidof camera_app)/stack       # 完整内核栈
```

**wchan 常见值含义**：

| wchan | 含义 |
|---|---|
| `poll_schedule_timeout` | 在 poll/select |
| `futex_wait_queue` | 用户态锁 |
| `pipe_wait` | 管道读 |
| `io_schedule` | 磁盘 IO |
| `msleep_interruptible` | 主动 sleep |


## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到第 1 章"三千台设备一夜失联"，五处问题—五处修复：

| 问题 | 根因 | 修复 | 章节 |
|---|---|---|---|
| pidof 判活假阳性 | 只测 Level 1 | 换 sd_notify(WATCHDOG=1) | §5.1 §4.3 |
| 独立线程喂狗 | 主线程死时它还喂 | 主循环喂 systemd | §3.2 |
| shell 脚本竞态 | 无锁多实例 | flock + pidfile | §7.2 |
| 无级联恢复 | 单进程崩不了整机 | StartLimitAction=reboot | §6.1 |
| 无雪崩防护 | 3000 台同时重启 | 重启前 rand jitter 上报 | §6.2 |

**改造后的 unit 文件**：

```ini
[Unit]
Description=Camera Application
After=network.target camera-driver.service

[Service]
Type=notify
ExecStartPre=/usr/bin/camera_selftest.sh
ExecStart=/app/camera_app
Restart=on-failure
RestartSec=5s
StartLimitBurst=5
StartLimitIntervalSec=60s
StartLimitAction=reboot
WatchdogSec=30s
NotifyAccess=main
```

**改造后的应用心跳**：

```cpp
void CameraApp::mainLoop() {
    sd_notify(0, "READY=1");
    HealthMonitor hm;

    for (;;) {
        auto frame = capture();
        hm.beat("capture");
        encode(frame);
        hm.beat("encode");
        stream(frame);
        hm.beat("stream");

        // 所有关键模块都心跳过 → 喂 systemd → systemd 喂硬狗
        if (hm.allHealthy()) sd_notify(0, "WATCHDOG=1");
    }
}
```

**结果**：三层防御全部生效——死锁 30s 内被 systemd 发现，进程被 kill 重启；如果连续 5 次崩溃，`StartLimitAction=reboot` 触发整机重启；如果 systemd 也挂了，硬件看门狗 30s 后拉复位。**从人工上门 200 台变成设备自己恢复**。

### 10.2 一次崩溃到恢复的一生

从"主线程死锁"到"设备重新采集数据"的完整流程：

```
【T=0】主线程调 encode() 卡在锁
【T=0】其他线程正常，capture 心跳还在打，但 encode 打不了了
    │
    ▼ 【T=5s】HealthMonitor 发现 encode 心跳超时
onModuleStuck("encode")
    ├─ 尝试软重启 encoder → 失败（锁本身有 bug）
    └─ 走极端：abort()
    │
    ▼ 【T=5s】进程 SIGABRT，core dump 落盘 /var/crash/
    │
    ▼ 【T=5s】systemd 收到进程退出，Restart=on-failure 生效
sleep RestartSec=5s
    │
    ▼ 【T=10s】systemd 拉起新进程
ExecStartPre 自检 → ExecStart 启动
    │
    ▼ 【T=12s】新进程 sd_notify(READY=1)，业务恢复
    │
    ▼ 【T=13s】新进程读 /var/crash/latest，检测到刚刚 core dump
上报云端 crash id + backtrace
    │
    ▼ 【T=14s】业务继续
```

**总不可用时间约 14 秒，用户几乎无感**（视频丢 14 秒帧，UI 提示"重连中"）。

如果同一 60 秒内又崩了 5 次：

```
【T=X】第 5 次崩溃 → StartLimit 触发 → reboot
【T=X+30s】整机启动完成 → 硬件初始化 → 应用启动 → 恢复
```

**如果 reboot 也解决不了**（连续三次开机崩溃）：

```
uboot 检测 bootcount > 3 → 切到 system_b 分区（回滚到旧版本）
```

**最坏情况**：新老版本都启不来 → uboot 进 recovery → 等待远程 OTA。

### 10.3 设计哲学回扣

**哲学 1：分层防御，代价递增**

三层看门狗的核心思想是**"每一层比上一层代价大 10 倍"**。应用层重启一个 worker（几乎无感）、systemd 重启进程（几秒黑屏）、整机重启（几十秒）、走 recovery（几分钟）。**永远选能解决问题的最低层**，不要一有问题就整机重启。

**哲学 2："活着"要按业务定义**

Level 1 到 Level 4 每一层"活着"的定义都不同。**判活的层次要匹配你想恢复的问题**——想恢复死锁就得 Level 3、想恢复业务卡死就得 Level 4。**通用的 pidof 只解决 Level 1，是错误的默认选择**。

**哲学 3：恢复要防雪崩**

3000 台同时崩溃，不能同时重启然后同时上报 —— 否则云端也顶不住。**任何恢复动作都要 + jitter**，把冲击平摊到时间轴上。这条哲学与网络篇的"退避 + jitter"是同一个道理。

**哲学 4：让失败可诊断**

崩溃前 dump 现场、崩溃后上报云端、bootcount 记录历次尝试。**恢复不是"跑起来就好"，是"恢复完还能查为什么挂"**。没有这条，你只能看着设备来回重启，永远解决不了根因。

### 10.4 速查手册

**守护设计口诀**：

```
硬件看门狗   → 兜底，业务心跳联动喂
systemd     → 进程级，Restart+StartLimit
sd_notify   → 业务级，业务真活着才喂
StartLimit  → 防死循环，超限升级到整机 reboot

```
