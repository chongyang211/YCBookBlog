# 12.深度精讲（Framework核心机制口述版）

> 说明：本章是核心题的口述版深度精讲，讲到 Framework 源码与运行机制层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

### 12.1 Handler消息机制的完整链路

答：一句话定调，**Handler 机制是「单线程消息队列 + epoll 阻塞唤醒」的线程通信模型，MessageQueue 的 nativePollOnce 就是整条链路的心脏**。

**四件套的关系先理清**：**Looper 是线程级的单例**（ThreadLocal 存储，一个线程只有一个），**MessageQueue 是 Looper 的字段**（一对一），**Handler 是 MessageQueue 的「投递口加处理回调」**（一个队列可以有多个 Handler，**Message 用 target 字段记住谁发的，dispatch 回谁**），Message 是载荷。**sendMessage 的本质**：Message 入队（按 when 排序的链表插入）→ **唤醒队列（nativeWake，写一个字节到 eventfd/管道）**。

**主线程为什么不用 prepare**：**ActivityThread.main 是主线程的入口**，它已经在里面 Looper.prepareMainLooper() 加 loop() 了——**主线程是个「永远在跑的 Looper 循环」，App 的「主线程代码」其实全是被 Looper 分发的一条条 Message**（Activity 生命周期就是 AMS 跨进程投递过来的消息调度，这也是 ANR 的根源：生命周期消息排队 5 秒没执行完）。

**深水区一：延迟消息的实现**——不是定时器是「排序加休眠」：Message 按 when 插入链表（有序），**Looper 取队头时算「还有多久到期」，把剩余时间传给 nativePollOnce(ptr, timeoutMillis)**——**native 层就是 epoll_wait(ptr, timeout)**：没到时间的队头挂起线程（不耗 CPU），到期或新消息 nativeWake 唤醒。**所以 postDelayed(60s) 不会开定时器线程，是「睡 60 秒」**；更深的推论：**MessageQueue 没消息时 next() 无限阻塞（timeout=-1），主线程在「深睡」，ANR 检测、IdleHandler 都靠这个循环的空隙跑**。

**深水区二：同步屏障**——post 到队列的 Barrier 消息（target=null）：**next() 遇到屏障时跳过普通消息、只找「异步消息」优先返回**。用途的完整链路：**UI 更新 requestLayout → ViewRootImpl 调 postSyncBarrier 屏蔽普通消息 → Choreographer 的异步消息（vsync 帧回调）插队执行 → 帧绘制完 removeSyncBarrier**——**渲染帧能「插队」在无数延迟消息前面，靠的就是这套机制**。

**Message 的池化细节**：obtain 从 **sPool（链表，上限 50）**复用，recycle 清空字段回池——**避免高频 Message 的分配与 GC**（和 Go 的 sync.Pool 一个思想）。

收尾：Handler 机制的三句话总结，**「队列是排序链表不是定时器」「阻塞是 epoll 不是死等」「优先级靠屏障不是插队标志」**，答出这三层就从「会用」到了「懂原理」。

> 面试官追问点：为什么 IntentService 被废弃了？应答思路：它是「HandlerThread 加 Handler 的组合封装」（串行后台任务），但生命周期管理和现代后台限制（Doze 模式杀后台）让它不可靠；替代是 WorkManager（约束感知 + 持久化调度），这是一道「知道类的历史演进方向」的题。

### 12.2 Binder的一次拷贝原理

答：一句话定调，**Binder 靠「mmap 双映射」做到一次拷贝：发送方 copy_from_user 到内核，内核和接收方的缓冲区是同一块物理内存，接收方零拷贝直达**。

**对比传统方案的两次拷贝**：管道/Socket 的写路径是「发送方用户态 → copy_from_user 进内核 → copy_to_user 到接收方用户态」**两次拷贝两次上下文切换**；共享内存是零拷贝但「无同步原语、安全性裸奔」。**Binder 的定位是「一次拷贝 + 强类型接口（AIDL）+ 进程身份（UID/PID 内核背书）」**。

**mmap 的双映射机制**（深水区一，讲清楚就赢）：**接收方（服务进程）提前 mmap 一块内核的 binder 内存**——这块物理页**同时映射进内核地址空间和接收方用户地址空间**；发送数据时 binder 驱动只做**一次 copy_from_user（发送方用户态 → 内核缓冲区）**，而这个内核缓冲区恰好就是接收方映射的那块——**接收方读自己的映射地址就是数据，第二次拷贝消失了**。代价是**「一次 mmap 的内存上限（约 1MB-8MB）决定了 Binder 单次传输不能超过 1MB-8MB」**（传输大文件要走 Ashmem 匿名共享内存）。

**完整调用链**（AIDL 视角）：客户端调 stub 的代理 → **Parcel 打包（writeInterfaceToken 校验、写参数）→ ioctl(BINDER_WRITE_READ) 陷入驱动** → 驱动找到目标进程的 todo 队列挂任务、唤醒服务线程 → **服务端 IPCThreadState 读出、Parcel 解包 → Binder 线程池的线程执行 onTransact（switch code 分发到本地方法）**→ 返回值沿反向链路回去。

**深水区二：进程身份防伪造**——**Binder 驱动在事务里自动附加调用者的 UID/PID**（from kernel，不可伪造），**服务端 getCallingUid 验权**——这是 Android 权限体系的基石：**普通应用伪造不了 system 身份，因为身份不是消息里的字段而是驱动贴的「邮票」**。对比 Socket（自报身份可伪造），这是 Binder 之于 Linux 老 IPC 的安全代差。

**ServiceManager 的角色**：** Binder 世界的 DNS**——服务注册（addService）和查找（getService）都经过它（它自己是 0 号句柄的特殊 Binder）；**死亡通知（DeathRecipient）也是驱动提供的：目标进程消亡时驱动回调注册方**——客户端监听服务死活、做重连，全靠这个机制（「死亡代理」的原名）。

收尾：Binder 的设计一句话，**「mmap 换一次拷贝，驱动贴邮票换安全身份，句柄表换对象寻址」**——性能、安全、对象语义三合一，这是它淘汰老 IPC 成为 Android 基石的理由。

> 面试官追问点：为什么单次传输限制 1MB 左右？应答思路：mmap 的 binder 缓冲区按进程预分配（默认约 1MB），传输数据必须整块放进映射区；异步事务（oneway）还有另一半的限额——**超限要么 TransactionTooLargeException（这个异常实际抛在 Bundle 过大场景）要么失败重试**，大块数据的标准出路是「传 Ashmem 的 fd、数据走共享内存」。

### 12.3 RecyclerView的四级缓存机制

答：一句话定调，**四级缓存按「离屏幕的远近」和「是否需要重新绑定」分层，scrap 和 cache 是「不用重绑」的近缓存，pool 是「跨列表共享」的远缓存**。

**四级逐层讲**：

1. **Scrap（mChangedScrap / mAttachedScrap）**：**当前布局过程内部的临时Detach**——layout 前后 detach 再 attach 的 ViewHolder，**数据位置都没变，跳过重绑**（预取和 layout 复用同批 child 用）；
2. **Cache（mCachedViews，默认 size=2）**：**刚滑出屏幕的 ViewHolder 按 position 精确缓存**——**命中时「按原 position 直接复用、不重绑」**（连 onBindViewHolder 都不用跑，这是它和 pool 的本质区别）；只存最近滑出的几个（马上滑回去的场景最赚）；
3. **ViewCacheExtension**：给开发者的自定义缓存层（**很少用**，等于官方留的白板）；
4. **RecycledViewPool**：**按 viewType 分桶（SparseArray<ScrapData>，每桶默认 5 个）**——**命中只能拿到「正确类型的空壳」，必须重新 onBindViewHolder**；**跨 RecyclerView 共享**（多个列表同类型 item 复用，setRecycledViewPool 共享池）。

**流程串起来**（滑动时的 getViewForPosition）：**先 scrap/cache 按 position 查（零成本复用）→ 查 pool 按 viewType 查（重绑成本）→ 都没有 create 新的**。**与 ListView 对比的胜负手**：ListView 的 RecycleBin 两级（active/scrap），**没有按类型的池、没有差量更新、没有预取**——RecyclerView 的四级是在「重绑成本」上做了极致分层。

**深水区一：DiffUtil 的差量更新**——**notifyDataSetChanged 的暴力**：全部视为失效 → **全部重绑（即使内容没变）+ 丢失动画**。**DiffUtil 用 Myers 差分算法算出「新增/删除/移动/未变」的最小编辑脚本**：**未变的直接复用（跳过重绑）、变化的精准刷新、move 还能触发位移动画**。**AsyncListDiffer 把 diff 挪到后台线程**（主线程只做 submit 后的渲染），配合 **ListAdapter（封装好的 differ 订阅）是现代标准姿势**。底层再深一层：**Adapter 的 getItem 和 areContentsTheSame 分离**——id 相同内容不同才是「原地刷新」的精确语义。

**深水区二：预取（GapWorker）**——**滑动时空闲帧提前创建「即将进入屏幕」的 ViewHolder**：它复用 12.1 讲的 **IdleHandler 机制在主线程空闲时干活**（和 Handler 机制打通），**预取的绑定发生在滑动之外的时间片，滑到时 item 已就绪**——这是「滑动不掉帧」的隐形功臣，也解释了「为何 Cache 只有 2 却不卡」。

收尾：四级缓存答题的心法，「**每级回答两个问题：命中成本多低（要不要重绑）、覆盖场景多远（position 精确还是类型模糊）**」，DiffUtil 和预取则把「重绑」和「创建」两个成本也搬离了关键路径。

> 面试官追问点：为什么说「RecyclerView 的 View 复用粒度是 viewType 不是数据」？应答思路：pool 按 viewType 存壳，同类型不同数据的 item 共用一套布局结构——所以「类型数量爆炸」(每种数据一个 viewType) 会让 pool 分桶过多每桶都冷；正确姿势是「布局形态才定义 viewType，数据差异交给重绑」。

### 12.4 ART的编译模式演进

答：一句话定调，**Dalvik 是 JIT（边解释边编译），ART 5.0 用纯 AOT（安装时全量编译）换性能但伤安装和存储，7.0 起的混合模式（JIT + AOT + Profile）才是终局**。

**三代演进按「痛点」讲**：

1. **Dalvik（JIT）**：运行时解释执行 + 热点 JIT，**省存储但每次启动都要重新 JIT（热身慢）、费电**；
2. **ART 5.0/6.0（纯 AOT）**：**安装时 dex2oat 全量编译成机器码**——运行飞快，**代价是安装慢（大 App 十分钟级）、占双倍存储（dex + oat）、OTA 后全量重编译**；
3. **ART 7.0+（Hybrid）**：**安装只编译关键路径（或纯解释），运行时 JIT 热点采集，**空闲时 Cloud Profile（云端聚合的画像）+ 本地 Profile 指导 AOT 后台重编译**——**下次启动用上次的画像**，冷启动越用越快。

**深水区一：Profile 引导的细节**——**Profile 是「方法级热度表」**（哪些方法在启动路径上被执行）：**基准配置文件（Baseline Profile，Android 9+）由开发者上传或云端聚合**，**安装时只 AOT 这条「启动关键路径」**（几 MB 的编译量，秒级安装），**运行后的真实画像回灌，后台 dex2oat 增量补编**——「安装快启动也快」的矛盾就是这么调和的。**Jetpack 的 Macrobenchmark 写 Baseline Profile** 是现代性能优化的标准动作（首页路径预编译，冷启动直接砍 30%+）。

**深水区二：方法数 64K 的真相**——**dex 文件里方法索引是 16 位**（method reference 的 id 上限 65536），**单个 dex 的方法数炸了就 link 不过**；multidex 的机制：**主 dex 装启动必需的类（Application/入口 Activity 手工指定 keep），副 dex 运行时从 apk 解压加载（MultiDex.install 在 attachBaseContext 里跑，本身有冷启动成本）**；**5.0+ 用 ART 原生支持多 dex（oat 里多个 dex）解决了主因， multidex legacy 只服务 4.x**——所以「64K 问题」在今天更多是历史知识，但「id 索引位数决定上限」的机制值得讲。

收尾：编译模式的演进主线是「**AOT 的性能、JIT 的灵活、Profile 的数据**」三者从对立走向融合，**热度的信息（哪些代码值得编译）从「拍脑袋全编」进化成「画像精准打击」**。

> 面试官追问点：dexopt 和 dex2oat 的区别？应答思路：dexopt 是 Dalvik 时代的优化（odex：字节码的 verify+optimize，还是字节码）；dex2oat 是 ART 的编译（oat/vdex：真机器码），Android 8 后用 vdex+odex 拆分存储（vdex 存验证过的 dex、odex 存机器码）——名词的变迁对应「优化到编译」的质变。

### 12.5 LeakCanary与Matrix的监控原理

答：一句话定调，**LeakCanary 的核心是「WeakReference + ReferenceQueue 的 GC 见证机制」：弱引用对象被回收时队列里会出现它的尸体，该出现而没出现就是泄漏**。

**LeakCanary 的四步机制**：

1. **注册观察**：watchActivity/watchFragment 销毁时，把实例包进 **KeyedWeakReference（自定义弱引用）连同 ReferenceQueue** 入 watch 表；
2. **主动触发 GC**（深水区一）：**Runtime.getRuntime().gc() + 等待 100ms**——注意 **System.gc() 只是「建议」**（JVM 规范允许忽略），LeakCanary 的做法是 gc 后再跑**runFinalization 加二次确认**，确保「真回收过了」；
3. **判定**：**从 ReferenceQueue 里 remove——被回收的弱引用会出现在队列里**（GC 时自动入队）；**观察表里还在（队列里没有）= 没被回收 = 被强引用着 = 泄漏**；
4. **堆转储找链**：**Debug.dumpHprofData 导出 hprof → Shark（自研解析器，比 MAT 轻）解析出「GC Root 到泄漏对象的最短引用链」**，按「怀疑等级」排序出报告。**Shark 的价值是「移动端能跑的 hprof 解析」（裁剪索引 + 增量分析，几秒出结果）**——早期用 HAHA（MAT 的库）在手机上 OOM 自己。

**深水区二：Matrix 的卡顿监控**（和 Handler 机制打通的另一案例）：**主线程的消息执行前后插桩**——**Printer 拦截 Looper.dispatchMessage 的日志回调（setMessageLogging）**，消息开始打标记、结束打标记，**一条消息执行超阈值（如 700ms）判定卡顿**；**同时子线程周期向主线程 post 高优先级消息，主线程迟迟不处理说明被占死**（「栈采集」：卡顿时抓主线程 stack，但单次栈可能错过现场，**Matrix 的 LazyScheduler 重复采样拼接出「卡顿现场的时间切片栈」**）。更轻的方案：**Choreographer 掉帧监控（FrameCallback 的 doFrame 间隔 vs 16.7ms）**——监控的是渲染帧率不是消息耗时，两者互补。

**线上 APM 的克制**（工程感加分点）：**LeakCanary 全量 dump 只适合线下**（dump 会 stop the world 数秒），**线上方案是「KB 泄漏监控」**（腾讯的 koom 方向）：**内存阈值触发 + 增量 dump（只 dump 泄漏关联区域）+ 子进程 dump（避免主进程卡顿）**；矩阵式监控的哲学：**线下深诊断、线上轻埋点，把成本预算花在「可疑才深挖」**。

收尾：监控类工具的通用套路值得总结，**「拦截点（Looper/生命周期）+ 判定信号（队列超时/弱引用存活）+ 证据采集（栈/堆）」三件套**，LeakCanary 和 Matrix 只是三件套的两个排列组合，理解套路比记工具重要。

> 面试官追问点：为什么 watch 一个对象能证明它泄漏？应答思路：销毁回调时对象「逻辑上应该死了」，弱引用是「只观察不持有」的引用——**GC 后弱引用还活着 = 有人在强引用它 = 谁在拖着尸体不放**；引用链就是这个「谁」的名单，弱引用机制把「不可见的持有关系」变成了「可检测的存活事实」。

### 12.6 Activity启动的跨进程全链路

答：一句话定调，**Activity 启动是「两次 Binder 跨进程 + 一次进程创建」的长链路：App 进程 → system_server（AMS）→ Zygote fork（冷启动）→ 返回 App 执行生命周期**。

**六步链路**（以冷启动为轴）：

1. **App 进程发起**：`startActivity` 一路到 **Instrumentation.execStartActivity**，**通过 AMS 的 Binder 代理（IActivityManager）跨进程**进 system_server——**应用进程在这里「交出控制权」**；
2. **AMS 权衡与决策**：检查清单（Activity 注册了吗、权限够吗、目标进程活着吗）——**目标进程没活，AMS 通过 Socket 通知 Zygote fork 新进程**（**Zygote 为什么用 Socket 不用 Binder：fork 的瞬间不能有多线程（Binder 线程池会导致子进程状态混乱），Socket 是单线程安全的通信**——经典细节）；
3. **Zygote fork 出新进程**：**预加载的类和资源被 COW 共享**（启动快的根本），**新进程的入口是 ActivityThread.main**；
4. **ActivityThread.main**：**Looper.prepareMainLooper 建主线程消息循环**（12.1 的根基在这）+ **AMS 的 attachApplication 回连**（把自己的 ApplicationThread Binder 交给 AMS，这是「AMS 主动找 App」的回程地址）；
5. **AMS 下发启动事务**：**ApplicationThread.scheduleTransaction（又是 Binder，方向反过来了）**，**App 侧包装成 Message 进主线程队列**；
6. **主线程执行**：**Handler 消息里依次 handleLaunchActivity → performCreate → onStart → onResume**——**生命周期就是消息驱动的普通方法调用**。

**深水区一：为什么 ANR 卡的是主线程消息**——从链路看：**生命周期的每一步都是「AMS 投递消息 → 主线程队列 → Handler 执行」**；**主线程被前一个消息卡住（比如 onCreate 里 sleep）**，后面的生命周期消息排队等待——**「超时未处理」的 ANR 本质是「消息排队超时」**（broadcast 10s / input 5s / service 20s 三种场景不同阈值，同源机制）。

**深水区二：AMS 为什么能「指挥」你的进程**——**attachApplication 交出去的 ApplicationThread 是 App 的 Binder 服务端**：**AMS 手握每个进程的回程地址，跨进程把事务投递进来**——「系统服务调度应用」的架构本质是 **Binder 的双向连接 + 消息队列的串行化**。**理解这个模型，「Activity 生命周期是谁调的」就有了终极答案：AMS 决定时机，主线程队列决定执行**。

收尾：启动链路答题的心法，「**两次 Binder（去 AMS、回 App）+ 一次 fork（Zygote 的 Socket）+ 消息收尾（生命周期的真身）**」，ANR 和生命周期问题全部挂在这条线上。

> 面试官追问点：热启动和冷启动的链路差在哪？应答思路：跳过第 3-4 步（进程活着、Looper 转着），AMS 直接查到目标进程的 ApplicationThread 投事务——**冷启动的大部分时间花在进程创建和应用初始化**，这就是「优化都盯着 Application 和首个 Activity」的链路依据。

### 12.7 事件分发机制的三段式与滑动冲突

答：一句话定调，**事件分发是「递归下发（dispatchTouchEvent）+ 拦截权（onInterceptTouchEvent）+ 消费权（onTouchEvent）」的三段博弈，一个 DOWN 的归属决定了整串事件的归属**。

**三段职责**：**dispatchTouchEvent 是必经之路（返回值=「这一串事件我包了」）**；**onInterceptTouchEvent 是 ViewGroup 特权（「这串事件别给我的孩子了」）**；**onTouchEvent 是消费表态（「我处理这个序列」）——View 没有 onInterceptTouchEvent（没有孩子可拦截）**。**事件序列的粘性**：**DOWN 确定的消费者会收到后续 MOVE/UP 的全部**（系统按「目标」直投，不再重新竞标）——**「一串事件一个主人」是整个机制的稳定锚**。

**递归流程还原**（ViewGroup.dispatchTouchEvent 主干）：**onInterceptTouchEvent 返回 true → 自己的 onTouchEvent 处理**；false → **遍历子 View 找「事件落点内的、能处理的」**，孩子处理不了才轮到自己（**「先子后父」的默认谦让**）。**requestDisallowInterceptTouchEvent 的机制**：子 View 设置 FLAG_DISALLOW_INTERCEPT，**父的 onInterceptTouchEvent 直接不被调用**——「孩子先表态『别抢』」，**滑动冲突的内部拦截法就是它**（子类 dispatchTouchEvent 的 DOWN 里 request、MOVE 判定后 release）。

**深水区一：onTouch 与 onTouchEvent 的优先级**——**View.dispatchTouchEvent 里先查 onTouchListener**（onTouch 返回 true 就不上 onTouchEvent）→ **onTouchEvent 里再查 onClickListener**——**优先级链：onTouch > onTouchEvent > onClick**，**onTouch 拦截后 onClick 失效是常见事故**（performClick 的调用是 View 的默认行为，自定义 onTouch 绕过了它）。

**深水区二：外部拦截法的标准模板**——「父 View 的 onInterceptTouchEvent 里：**DOWN 必须 return false**（DOWN 拦了孩子收不到整串就断了）、**MOVE 按滑动方向判定**（水平位移差 > 竖直则拦截）、**UP 必须 return false（UP 拦了孩子的 click 收不到）**」——**三个 return 的时机约束**是滑动冲突题的真正考点，能讲出「为什么 DOWN 和 UP 不能拦」就是源码级理解。

收尾：事件分发答题的心法，「**三段职责一张图（必经/特权/表态）、序列粘性一个锚（DOWN 定终身）、冲突处理两套法（外部拦截父问、内部拦截子禁）**」。

> 面试官追问点：为什么 onTouchEvent 返回 false 后事件会传给父级？应答思路：分发是递归下行，孩子的 dispatch 返回 false 意味着「这层没人要」，递归栈回退时父的 onTouchEvent 接手——**「不消费就上交」是责任链的味道**（和 09 篇的责任链变体可对照）。

### 12.8 Glide四级缓存与生命周期感知

答：一句话定调，**Glide 的缓存是「四级漏斗」（活动资源→内存→磁盘→网络），生命周期感知靠「无 UI 的 SupportRequestManagerFragment 挂载请求」，Bitmap 池化让「加载图片几乎零分配」**。

**四级漏斗的每一级**：

1. **ActiveResources（活动资源）**：**正在显示的图片的弱引用表**——「屏幕上的」和「内存缓存的」分离的妙处：**内存紧张时 LRU 清掉的不会影响正在显示的**（活动表是弱引用，显示中的强引用保命）；
2. **MemoryCache（内存 LRU）**：默认 **屏幕宽高 × 4 通道的内存上限**（按设备自适应），命中直接回调；
3. **磁盘缓存**：**分「原始图（SOURCE）」和「变换后（RESULT）」两套**——**圆角/缩放后的结果单存，二次加载跳过解码和变换**；
4. **网络**：最小优先（EngineJob 发起）。

**深水区一：生命周期感知的实现**——**Glide.with(fragment) 的秘密**：**往 FragmentManager 加一个 SupportRequestManagerFragment（无 UI）**，**RequestManager 监听它的生命周期**：**onStop → pauseRequests（在途请求挂起）**、**onDestroy → cancelRequests + 清引用**——「**页面销毁请求自动取消**」不是魔法，是**一个透明 Fragment 做代理观察者**。**为什么这么绕**：直接持 Activity 引用会泄漏、监听 Activity 生命周期回调又是侵入式的——**「寄生 Fragment」是 Lifecycle 组件出现前的经典黑科技**。

**深水区二：BitmapPool 的零分配哲学**——**解码 Bitmap 的临时内存从池里借**（inBitmap 复用一块内存）：**API 19+ 允许「尺寸不精确匹配的复用」**（只要 bitmap 内存够大），**变换过程（圆角裁剪的中间 Bitmap）全程借还**——**「加载图片零 GC」**是它对低端机流畅度的最大贡献（GC 抖动是列表卡顿大户）。**和 12.1 的 Handler 消息池、09 篇的享元模式是同一思想的三个马甲**。

收尾：Glide 答题的心法，「**四级漏斗按『可见-近用-持久-远程』分层、寄生 Fragment 挂生命周期、Bitmap 池把分配也消灭**」，最后一项是深水区的分界线。

> 面试官追问点：为什么同一张图不同 ImageView 尺寸加载结果不同？应答思路：Glide 默认**按 Target 尺寸做下采样解码**（inSampleSize），不同尺寸产出不同缓存 key——override() 可以强制统一；这也是「磁盘缓存命中率忽高忽低」的一个来源（尺寸进 key）。

### 12.9 MVP、MVVM到MVI的演进逻辑

答：一句话定调，**三代的演进主线是「解耦谁和谁」：MVP 解耦 View 和逻辑（接口回调）、MVVM 解耦数据和视图（观察者自动同步）、MVI 把「状态和事件」单循环化**。

**MVC 的原罪**：Activity 既是 View 又是 Controller（XML 只是个壳）——**「上帝 Activity」千行代码的病根**；**MVP 的解法**：**Presenter 持 View 接口**（Activity 实现之），逻辑全进 Presenter——**可测性暴涨（Presenter 是纯 Java 可单测）**；**代价**：**接口爆炸（一个页面对应一堆 IView 方法）+ 生命周期地狱（异步回来 View 已销毁，判空轰炸）**。

**MVVM 的换轨**（深水区一）：**Presenter 的「主动调 View 方法」换成「暴露可观察的数据」**——View 订阅 ViewModel 的 LiveData/Flow，**数据变了 UI 自动刷**——**「数据驱动」替代「命令驱动」**：**好处**：接口砍掉了（暴露的是数据不是方法）、**生命周期问题被 LiveData 框架解决**（DESTROYED 自动解绑）；**代价**：**数据流的「多入口」问题**——一个页面十几个 LiveData，各自的更新时机交织，「最终 UI 状态」是多个流叠加的结果，**难以推理**（「这个状态哪来的」要全局搜）。

**MVI 的收敛**（深水区二）：**单一数据源（一个 UiState 不可变对象）+ 单一意图入口（所有用户行为统一成 Intent）+ 单向数据流（send(intent) → reduce → 新 State → render）**——**「状态 = f(intent, 前状态)」的纯函数化**：**每一步可追溯（日志记录 intent 流）、状态可回放（时间旅行调试）、并发安全（State 不可变）**。**代价**：样板代码（一个点击也要包装成 Intent 类）+ **State 全量更新对小改动低效**——**「MVI 是把 Redux 思想搬进 Android」**，适合状态复杂的页面，简单页面是杀鸡用牛刀。

**选型的诚实答案**：**MVP 老项目维护、MVVM 是 Jetpack 亲儿子（官方默认）、MVI 复杂状态页**——三代不是替代是**「耦合治理粒度」的进化**，能讲出「每代解决上一代的什么痛、引入了什么新痛」就是深水区。

收尾：架构题的心法，「**MVC 病在上帝类、MVP 药是接口回调、MVVM 药是数据驱动、MVI 药是状态单循环**」，最后一句话点破：「**架构选型不是追新，是选对你页面的状态复杂度**」。

> 面试官追问点：ViewModel 为什么转屏不丢数据？应答思路：ViewModel 存在 **ViewModelStore**（Activity 的「转屏存活的伴生体」，配置变更时 Activity 重建但 ViewModelStore 由 ActivityThread 保留移交）；只有「真正的销毁」（finish）才清空——**「比 Activity 活得长的非静态无泄漏单页数据容器」**是它的精确定位。

### 12.10 Kotlin协程的挂起原理

答：一句话定调，**挂起函数编译后是「带 Continuation 参数的状态机」，挂起 = 「把后续代码包成回调存入 Continuation 并让出线程」，恢复 = 「回调被调度器再次调用」**。

**CPS 变换**（Continuation Passing Style，编译器干的事）：`suspend fun foo(): T` 编译成 `fun foo(c: Continuation<T>): Any?`——**返回值 Any? 是「T 或 COROUTINE_SUSPENDED」**：**返回 COROUTINE_SUSPENDED 意味着「没算完，结果以后走 Continuation」**；返回 T 意味着「同步就完成了（假挂起，不切线程）」——**「挂起不一定真切线程」**（delay(0) 或已完成的 withContext 会同步返回）是理解性能的第一步。

**状态机的还原**（深水区一）：多个挂起点之间编译成 **when (label) 的跳转表**——**每个挂起点是一个 case，局部变量提升到状态机字段保存**；挂起时：**当前 label 和变量已存进 Continuation，函数直接 return SUSPENDED**；恢复时：**Continuation.resumeWith(value) 再次调用这个函数，label 指到下一个 case，从断点后继续**——**「协程 = 编译器生成的回调嵌套扁平化」**，和 async/await 在 JS 的编译产物（5 篇 7.4）是同一思想的两家实现。

**结构化并发的机制**（深水区二）：**Job 是树**（Scope 的 job 是父、launch 的是子）——**cancel 是树遍历（父取消级联子）**、**join/await 是父等子**、**异常向上冒泡（子失败取消父的其它子）**——**「协程的生命周期天然有组织结构」是它比「裸线程+回调」强的根本**；**SupervisorJob 是「异常不传染兄弟」的变体**（子失败只死自己）；**对比 Go**：goroutine 没有结构（泄漏要人肉防，context 是外挂的取消树），**Kotlin 把取消和层级做进了类型系统**——两家哲学的差异点。

**调度器的分层**：**Dispatchers.IO 的「弹性线程池」**（默认 64 上限可扩）、**Default 是 CPU 核数的计算池**、**Main 是 Handler 转发**；**withContext 的切换 = 「挂起点 + 恢复时在目标调度器」**——**「挂起恢复」和「线程跳转」是两个正交的机制**（挂起可以不切线程，切线程必经挂起点）。

收尾：协程答题的心法，「**挂起=CPS+状态机（编译期魔法）、结构化=Job 树（生命周期的组织学）、调度=可插拔的恢复地点**」，第一句讲给面试官，后两句讲给深水区。

> 面试官追问点：suspend 函数为什么不能在普通函数调？应答思路：它编译后需要 Continuation 参数（谁来接「以后的结果」），普通函数没有 Continuation 可传——**「suspend 传染性」的本质是「回调上下文的类型要求」**，而不是运行时限制。
