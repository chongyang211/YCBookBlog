# 13.深度精讲（Runtime与内存机制口述版）

> 说明：本章是核心题的口述版深度精讲，讲到 Runtime 源码（objc4）与运行机制层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

### 13.1 weak自动置nil的底层实现

答：一句话定调，**weak 的自动置 nil 靠「SideTable 的 weak_table 哈希表」：对象 dealloc 时 clearDeallocating 遍历它的弱引用条目，把所有 weak 指针置 nil**。

**三层结构自顶向下**：全局有个 **SideTables（64/128 个 SideTable 的哈希表，按对象地址哈希分片，锁粒度就是分片）**；每个 SideTable 三件套（**自旋锁、引用计数表 refcount_map、弱引用表 weak_table**）；weak_table 里是 **weak_entry_t**——**一个对象一条 entry，记录「指向我的所有 weak 变量的地址」**。

**登记流程**：声明 `__weak typeof(obj) weakObj = obj` 时，编译器插入 **objc_initWeak → weak_register_no_lock**：**按 obj 地址哈希定位 SideTable，把 weakObj 这个「指针变量的地址」追加进该对象的 weak_entry**（哈希结构里找不到 entry 就新建，条目多到 4 的倍数时扩容为哈希桶）。**注意存的是「weak 变量的地址」而不是值**——这样后面才有地方反向写 nil。

**置 nil 的流程**：对象引用计数归零 → **dealloc → clearDeallocating**：取出该对象的 weak_entry，**遍历其中每个 weak 变量地址，把指到的内存统一写 nil**，然后从表里摘除 entry。**所以「自动置 nil」不是魔法，是 dealloc 路径上的一次定向清扫**——这也解释了为什么 **weak 变量在 nil 之后访问是安全的（发送消息给 nil 返回 0 值）**。

**深水区一：为什么要 SideTables 分片**——**全表一把锁的话，任何对象的 weak 操作都串行全世界**；按对象地址分到 64+ 个桶，**不同对象的 weak 登记和清除天然并行**——和分库分表一个思想，objc4 源码里还用**字节翻转哈希（地址高位取模）**让相邻对象（栈上连续分配）也能打散。

**深水区二：weak 的读写开销**——**每次访问 weak 变量都走 objc_loadWeakRetained（查表加 retain 再 autorelease 的保护链）**，比 strong 访问贵一个量级：**所以「在循环里反复读 self->weakSelf」是性能反模式**，标准姿势是循环外 `__strong typeof(weakSelf) strongSelf = weakSelf` 提一次（**weak-strong dance 的真正动机，不只是防循环引用**）。

收尾：weak 机制一句话，「**登记时记住变量地址，死亡时挨家挨户写 nil**」，SideTables 的分片和 weak-strong 的提频，是「知道机制后才能推导出的工程姿势」。

> 面试官追问点：Tagged Pointer 的对象为什么不能有 weak？应答思路：Tagged Pointer（13.1 之外的优化）的值直接编码在指针里、**没有堆对象也没有 dealloc 流程**，weak 表无从挂载——系统直接在 weak_register 里断言拦截，这是「优化对象绕开引用计数体系」的边界。

### 13.2 objc_msgSend与缓存查找

答：一句话定调，**objc_msgSend 是「汇编写的缓存查找状态机」：先查缓存（哈希探测）命中就尾调用 IMP，不命中走 C 的 method_lookup，全程拒绝递归重入靠可恢复的寄存器现场**。

**为什么用汇编**（深水区一）：**调用频率冠绝全系统（每行 OC 消息调用都过它）**，汇编能做三件 C 做不了的：**尾调用（tail call）直接 jmp 到 IMP（不增加调用栈）**、**按调用约定精确保存可恢复寄存器（不会重入时破坏现场）**、**哈希探测的无开销循环**。objc4 源码里 objc-msg-arm64.s 就是这个文件。

**快速查找的三步**（按 objc_msgSend 汇编的主干走）：

1. **nil 检查 + Tagged Pointer 检查**（对象为 nil 直接返回 0，消息发给 nil 的安全语义在这实现）；
2. **取缓存**：LCacheMiss 之前先 **从 isa 指针取 class（ARM64 上 isa 是 nonpointer，要按位掩码取出 class 地址）→ 取 cache_t → 哈希计算**（**cache 哈希用 sel 与 mask 按 `sel & mask`，**比较 bucket 里的 sel，命中取 imp 尾调用**）；未命中**沿 bucket 链环形向前探测**（cache 是**开放定址的哈希表**，不满四分之三）；
3. **miss 走慢路径**：`__objc_msgSend_uncached → lookUpImpOrForward`（C 函数），**持有 cache 读写锁、methodLists 链表线性找（method list 现在是排序的，可二分）→ 找到写回缓存**；找不到进转发决议（三大阶段）。

**深水区二：cache 的并发设计**——**读多写少的「脏读安全」结构**：bucket 数组扩容时**新建表填好再原子替换指针**（读者要么看旧表要么看新表，都自洽）；**写入用字节级原子操作保证「先写 imp 再写 sel」的顺序**（**读侧看到 sel 非空就意味着 imp 已就绪**——一个无锁读的顺序设计）；实在竞争激烈才等写锁。**缓存扩容是「丢弃式」的**：翻倍时**旧缓存直接扔掉重新热身**（不搬移），摊销成本更简单。

**缓存的分层**：**class 的 cache 在 class 结构里， superclass 的缓存各自独立**——子类查不到会沿继承链往上，**每层的 cache 都会热各自的方法**（ superclass 的热点方法在 superclass 自己的缓存里命中，不污染子类缓存）。

收尾：objc_msgSend 的设计哲学是「**把 99% 的命中路径做到一条 jmp 的成本，miss 的成本再高都值得**」——缓存查找的汇编化、无锁读、扩容丢弃三个决策全部服务这个目标。

> 面试官追问点：为什么 method 查找慢路径还要做「二分」？应答思路：新版 runtime 的 method list 是「按 selector 排序的相对偏移列表」（list 内容不可变，相对地址编码省一半内存），排序结构让线性查找升级为二分——**「结构不可变」换来「查找可优化」**，和数据库索引一个思想。

### 13.3 Runloop的机制与应用全景

答：一句话定调，**Runloop 是「线程的事件循环」：休眠靠内核（mach_msg），唤醒靠端口消息，每个 Mode 有独立的 source/observer/timer 集合，Mode 切换就是「换一套事件集」**。

**结构三件套**：**CFRunLoop（每线程懒创建，字典存储）→ 多个 CFRunLoopMode → 每个 Mode 里 sources0/sources1/observers/timers 四个集合**。**一次 runloop 循环只跑一个 Mode**，**切换 Mode 要先退出再重进**（保证集合不被并发修改）——这是 Mode 的隔离语义。

**深水区一：休眠的底层**——**mach_msg 的陷阱调用**：runloop 没事干时**调 mach_msg 陷入内核等待端口消息（内核态挂起，零 CPU）**；唤醒源就是「往这个端口发消息」：**sources1 是内核端口（系统事件如 UI、GCD 唤醒都走它）**、timer 到期（内核 timer 也转成端口消息）、手动唤醒。**「Runloop 挂起线程」和 Go 的 gopark 是同一个思想：把等待交给内核，线程不空转**。

**一次循环的完整序列**（这个顺序背下来值一道题）：

1. 通知 observers：进入（kCFRunLoopEntry）；
2. 通知 observers：即将处理 timers；
3. 通知 observers：即将处理 sources0（**先标记后执行：非内核源的 UI 事件在这轮派发**）；
4. **如果有 sources1（内核端口消息）跳到 9 处理消息**（Source1 是「插队通道」）；
5. 通知 observers：即将休眠（**AutoreleasePool 的 push/pop 就挂在这个时机**——**进入休眠前 pop 排干旧的、push 开新的**，这就是「autorelease 的释放时机由 runloop 驱动」的真相）；
6. **mach_msg 休眠**，等端口消息唤醒；
7. 唤醒（端口消息/timer/GCD 调度唤醒——**GCD 的主队列任务跑在主线程 runloop 的「被 GCD 唤醒」路径**）；
8. 通知 observers：结束休眠；
9. 处理唤醒消息（timer 到期、dispatch 到主队列的 block、source1）；
10. 通知 observers：退出（kCFRunLoopExit），决定是否再来一轮。

**六种应用的机制对照**（每个一句话挂到序列上）：

1. **AutoreleasePool**：挂第 5 步，休眠前排干；
2. **事件响应/手势识别**：source1 的系统事件进队列，source0 分发给 UIApplication 再 responder chain；
3. **NSTimer**：注册进 mode 的 timers，第 3/9 步检查到期（**所以NSTimer 对 mode 敏感：滑动时 tracking mode 的切换让 default mode 的 timer 停摆**——经典 bug 的机制根源）；
4. **CADisplayLink**：和 timer 同类但按 vsync 帧驱动（也是 mode 属性）；
5. **卡顿检测**（深水区二）：**observer 监控「休眠前/唤醒后」的耗时差**——**BeforeWaiting 到 AfterWaiting 之间如果超过阈值（如 400ms），说明线程被某个 source/timer 的处理卡住**（在 9 的处理阶段耗时超长），**把这时抓的主线程栈聚合就是卡顿报告**（微信 Matrix 和 12.5 的 Android 方案异曲同工）；
6. **常驻线程**：给子线程的 runloop 加 source（port 或起 run），**否则 runloop 跑完队列立刻退出**，线程即死。

收尾：Runloop 的三句话总结，**「线程的命靠 runloop 吊着（休眠不退出）」「事件的分发靠 mode 隔离（一套集合一个世界）」「一切看起来随机的回调，都能在循环序列里找到自己的工位」**。

> 面试官追问点：主线程的 runloop 谁启动的？应答思路：main 函数末尾 UIApplicationMain 里 CFRunLoopRunInLine 起了 main runloop，**「main 函数 return 后 App 还活着」的错觉就是 runloop 在 main 之外永续循环**——理解这一点就理解了「iOS App 的本质是事件循环驱动」。

### 13.4 Block的三种类型与拷贝机制

答：一句话定调，**Block 的类型由「捕获了什么」决定：没捕获是 Global、捕获了变量且未被拷到堆是 Stack、_Block_copy 之后是 Malloc——三种类型的内存属性不同，ARC 的栈到堆升级是编译器自动做的**。

**三种类型的判定**：

1. **GlobalBlock**：**不捕获任何外部变量**（只用自己的参数或全局量）——**没有状态可保护，放数据段和函数一样**，copy 是空操作；
2. **StackBlock**：捕获了变量、且还活在栈上（MRC 时代裸声明）——**离开作用域即销毁**；
3. **MallocBlock**：StackBlock 被 copy 后的形态——**捕获的状态（__block 变量、引用的对象）整体搬到堆上，生命周期自管理**。

**ARC 下的真实形态**（深水区一）：**ARC 会把「作为返回值/赋给 strong 变量/当参数传」的栈 Block 自动 copy 成堆 Block**——所以日常写的 block 几乎都是 MallocBlock，**StackBlock 只在「strong 之外的形式持有」（如手动取地址、裸结构体）才露面**。**经典验证题**：`void (^blk)(void) = ^{...}` 打印是 Malloc（ARC 自动 copy），但 `^{...}` 直接 isKindOfClass 检查时是 Stack——**「栈块出现在右值，堆块出现在被持有后」**。

**Block 的结构体真相**：Block 是 `__block_impl + 捕获变量列表` 的结构体（**isa 指向 _NSConcreteMallocBlock 等类对象**，**desc 记录大小和 copy/dispose 帮助函数**）；**捕获 OC 对象时**，结构体里持有的是 `void *` 加 **flags 里的 BLOCK_FIELD_IS_OBJECT 标记**——copy 时对它调 objc_retain（这就是「Block 持有对象」的 ARC 实现）。

**深水区二：__block 的实现**——被 __block 修饰的变量**不是被捕获值，而是「包成 byref 结构体的引用」**：`__Block_byref_x_0 { isa; flags; x; forwarding; }`，**栈上的 Block 捕获的是这个结构体的指针**；**copy 到堆时 byref 结构体也搬到堆，且栈版本的 forwarding 指针改指堆版本**——**读 x 永远走 forwarding，栈块和堆块读写的是同一个 x**（这就是「__block 让 Block 内外共享变量」的机制）。**ARC 下 __block 修饰 OC 对象还会让 byref 结构体持有它**（MRC 时代不会——历史差异是老题）。

**循环引用的精确链路**：self 强持有 block（属性 copy），**block 结构体捕获了 self（retain）**——环成立；**weak-strong dance 的正确姿势**：`__weak typeof(self) ws = self; ^{ __strong typeof(ws) s = ws; ... }`——**weak 断环（block 不强持 self），strong 在「block 执行期间」临时持有防止执行到一半 self 释放**（不是「保证不强引用」而是「保证执行期安全」）。

收尾：Block 的心智模型一句话，「**结构体 + 捕获列表 + copy 时升级**」——类型三态是「捕获有无」和「copy 有无」的矩阵，__block 的 forwarding 是「栈堆同体」的桥梁。

> 面试官追问点：为什么 block 属性要用 copy 修饰？应答思路：MRC 时代要显式 copy 把栈块搬堆（不然属性持有一个栈块，作用域外悬空）；ARC 下 strong 也会自动 copy 效果等价——**写 copy 是「历史正确的肌肉记忆」，语义上表达「这个属性要堆块」的意图**。

### 13.5 KVO的isa-swizzling原理

答：一句话定调，**KVO 的实现在「偷换 isa」：注册观察时运行时动态造一个 NSKVONotifying_子类、把对象的 isa 指过去，重写的 setter 在「旧值新值」之间通知观察者**。

**注册时发生了什么**（setValue:forKeyPath 观察触发后）：

1. runtime 动态创建 **NSKVONotifying_原类名** 子类（**每个类只造一次，复用**）；
2. **重写被观察属性的 setter**：`willChangeValueForKey → 原实现（真的改值）→ didChangeValueForKey`（didChange 里**遍历观察者列表调 observeValueForKeyPath**）；顺带重写 **-class（骗过 introspection 返回原类，让人看不出 isa 被换了）**、-dealloc、_isKVOA；
3. **object_setClass 把对象的 isa 换到新子类**——此后这个对象的消息（setter）全部走重写版。

**深水区一：验证与绕过**——`object_getClass(obj)`（绕过 -class 的伪装）能看到 NSKVONotifying_ 前缀；**直接改成员变量（_xxx = v）不走 setter 所以 KVO 不触发**——「手动触发 KVO」的姿势：**自己调 willChange/didChange 对**（把「通知义务」从 setter 里手动接管）；**用 KVC（setValue:forKey:）会触发**（KVC 内部调了 will/did 的协议）。** isa 换类但不换内存**——**对象还是原对象，只是行为被「贴了层皮」**。

**深水区二：KVO 的三个坑与根因**：

1. **观察者和被观察者谁先释放**：**观察者 dealloc 但没 removeObserver**——被观察者下一次通知时向尸体发消息，**野指针崩溃（ClassicNSException: message sent to deallocated）**；**removeObserver 的本质是把观察者从重写 setter 的观察者表里摘掉**，没摘就是悬空条目；
2. **父类也 KVO 的问题**：子类和父类都观察同一属性（各自注册）——**重写链上多次 will/did 的顺序**（子类 setter 调 super，通知会嵌套发出），**automaticallyNotifiesObserversForKey 返回 NO 可以接管自动通知**（精细控制的官方入口）；
3. **属性是 struct/非对象类型**：KVO 支持（包 NSValue），但**依赖 setter 的 keyPath 精确性**，手滑写错路径**注册时不报错、运行时静默不触发**（observe 注册是惰性校验的）——**这是「KVO 是字符串约定松散 API」的根源性吐槽**，也解释了现代代码用 Facebook 的 KVOController 或 Combine/闭包替代。

**手写简化 KVO 的思路**（面试常考白板）：**isa 替换（object_setClass）+ 动态子类（objc_allocateClassPair 加 setter 的 method swizzling）+ 观察者表（NSMapTable 弱键）+ will/did 钩子**——**本质是「method swizzling 的对象级特化」**（swizzling 换全类的方法，KVO 只换这一个对象的 isa）。

收尾：KVO 的机制一句话，「**isa 是行为的开关，换 isa 等于换人格但保留内存**」；三个坑全部源于「字符串约定的松散」和「观察者表的生命周期」，**理解坑的根因比背坑的表象更能拿分**。

> 面试官追问点：KVO 和重写 setter 手动发通知有什么区别？应答思路：KVO 是「运行时无侵入」（不改原类代码、按对象粒度生效）；重写 setter 是「编译期侵入」（改类就影响所有实例、要发版）——**运行时的灵活 vs 编译期的明确**，工程上 KVO 省事但排错难，这也是声明式框架（Combine/RxSwift）最终替代它的原因。

### 13.6 AutoreleasePool的底层实现

答：一句话定调，**autoreleasepool 是「双向链表串起来的 4096 字节 Page 栈」，push 压哨兵、pop 到哨兵之间全 release，Runloop 驱动它周期性排干**。

**结构三级**：**AutoreleasePoolPage（C++ 结构，4096 字节一页，双向链表串父与子）**——**page 里就是个栈（从高地址往低压对象指针）**；**POOL_SENTINEL（哨兵，一个空对象地址）标记一次 push 的边界**；hotPage 是「当前活跃的最后一页」。

**push 和 pop 的语义**：`autoreleasepool {}` 编译成 `objc_autoreleasePoolPush`（**压一个哨兵）** 和 `objc_autoreleasePoolPop(哨兵)`——**pop 时从栈顶往下逐个调 release，直到碰到自己的哨兵为止**——**「push/pop 严格配对 + 嵌套按哨兵切段」**，嵌套的 pool 就像函数调用栈一样各管各段。

**对象怎么进池子**：**autorelease 调用时对象指针压入 hotPage**（页满 56 个就开新页挂链表）——**注意不是拷贝对象，只存指针**（8 字节成本）。

**深水区一：Runloop 的排干时机**——**主线程的 Runloop 每次进入休眠前（BeforeWaiting）和退出时，对最近的 pool 执行 drain（pop 到最外层哨兵再重新 push）**（和 13.3 的循环序列挂钩）——所以「autorelease 对象的释放时机」= **「本轮 runloop 即将休眠时」**：一次点击事件的所有 autorelease 对象，活到这轮消息处理完的最后一刻。**推论**：**大循环里狂建 autorelease 对象（比如 for 里读图片），要等循环结束才释放**（峰值内存爆表）——**在循环体内显式包 autoreleasepool 是标准解法**（每圈一个哨兵，每圈排干）。

**深水区二：objc_autoreleasePoolPrint 的调试法** 与 **Tagged Pointer 的豁免**——**objc_autoreleaseReturnValue 的优化**：**方法返回 autorelease 对象时，先调这个函数：如果调用方紧接着 objc_retainAutoreleasedReturnValue（编译器插桩配对），TLS 存标记 + 返回裸指针，双方省掉一次入池和一次池取**——**「调用约定层的快速通道」**（pair 化的 autorelease 消除），能讲出这个优化是深水区。

收尾：autorelease 答题的心法，「**Page 是链表化的栈、哨兵切段配对、Runloop 睡前排干、循环防爆要手动包池**」，最后一条是实战必考。

> 面试官追问点：子线程的 autorelease 谁来排干？应答思路：子线程默认没有 runloop 转着，**线程退出时 TLS 里挂着的一个 autoreleasepool 会被清**；但长期活着的子线程不退出，autorelease 对象就攒着——**「子线程大量建 autorelease 对象要自己包 pool」**是这个机制的直接推论。

### 13.7 Category的加载与+load、+initialize

答：一句话定调，**Category 的方法在运行时「附加」到类（不替换原实现，是插到方法列表前面），+load 在 main 之前按编译顺序全量调用，+initialize 首次消息时懒触发**。

**加载时机与顺序**（深水区一）：**dyld 映射 image 后，runtime 的 map_images/read_images 把 Category 的方法列表**attachClass **合并进宿主类的 class_ro_t → class_rw_t**——**合并的位置在原方法列表之前**（Category 方法排前面）——**「同名方法的覆盖」其实是「查找时先找到」**：**原实现还在列表后面，method swizzling 时可以 class_getImplemention 拿到被「遮住」的原实现**（这就是 method_exchange 的技术基础）。**多个 Category 同名方法**：**后编译的排更前（最后编译的赢）**——**「覆盖顺序由编译顺序决定」是未定义行为的官方说明**（Build Phases 的文件顺序就是答案）。

**+load 的机制**：**read_images 时直接遍历调用（不走 objc_msgSend，直接函数指针调用）**——所以：**父类 load 先于子类、类 load 先于 Category 的 load、不覆盖（各自全调一遍）**、**main 函数之前执行**（冷启动黑魔法的窗口期，鱼竿代码/FMDB 老版本都在这 hook）；**代价**：**拖慢启动（每个类的 load 串行跑）**，新工程用 +initialize 替代的趋势。

**+initialize 的机制**（深水区二）：**第一次给类（或子类）发消息时，runtime 的 class_initialize 检查「没初始化过」就调**——**走 objc_msgSend（有 runtime 完整机制）**：所以是**懒加载**（没用到的类永不调）、**父类的 initialize 先触发**（子类第一次收消息，先保证父类初始化）、**子类不实现 initialize 会调到父类的（消息机制的自然结果，经典坑：父类 initialize 被调多次，要 dispatch_once 或 判断 self==类名）**。**线程安全**：**runtime 持初始化锁调用，一个线程 initialize 时其它线程发消息会等待**——「initialize 里做重活会卡并发首调用」。

收尾：Category 答题的心法，「**附加不替换（列表前面加条目）、load 在 main 前全量直调、initialize 懒触发走消息机制**」，配对记忆：「**load 讲纪律（全调有序）、initialize 讲懒惰（首次才动）**」。

> 面试官追问点：Category 能加属性吗？应答思路：能加「属性声明」（property 语法）但**编译器不合成 ivar 和访问器**（类结构在编译期已定死，运行时补不了成员变量）——**关联对象是运行时的替补方案**（objc_setAssociatedObject 存在全局的 AssociationsManager 哈希表里，和类结构无关）。

### 13.8 ARC的插桩与所有权修饰符

答：一句话定调，**ARC 是「编译器插桩的引用计数管理」：Clang 在编译期插入 retain/release/autorelease 调用，__strong/__weak/__unsafe_unretained/__autoreleasing 是四种所有权约定**。

**四种修饰符的精确语义**：

1. **__strong（默认）**：赋值时 retain、离开作用域 release——**「我拥有它」**；
2. **__weak**：赋值不 retain，**对象 dealloc 时自动置 nil**（13.1 的机制）——「我观察它，它死我置空」；
3. **__unsafe_unretained**：不 retain 也不置 nil——**悬空风险自负**（兼容旧 API、性能敏感场景，ARC 的「裸引用逃生门」）；
4. **__autoreleasing**：**赋值时 autorelease 进池**——主要场景是 **传 NSError** 的二级指针（`NSError **error` 的实际类型是 `NSError * __autoreleasing *`，**临时变量自动包 autorelease 保证出函数后还活着**）。

**深水区一：编译器到底插了什么**——`id obj = [[NSObject alloc] init];` 在 ARC 下其实**一个 retain/release 都不多插**（**alloc/new/copy/mutableCopy 开头的方法返回「持有引用」， Caller 直接拥有——方法族约定的优化**）；**`obj = someMethod()`（普通方法）才插 objc_retainAutoreleaseReturnValue 的配对链**——**「方法名族的隐式所有权约定」**是 ARC 优化的基石（非 alloc 系返回的是 autorelease 对象，编译器用 13.6 讲的 TLS 快速通道消除池开销）。

**深水区二：ARC 与 Core Foundation 的边界**——**ARC 只管 ObjC 对象，CF 对象（CGImageRef 等）不归它管**：**桥接三兄弟**——`__bridge`（**只换类型不动引用计数**，危险：桥出去后 CF 侧没人管）、`__bridge_retained`（**桥的同时 retain，CF 侧负责 release**）、`__bridge_transfer`（**桥的同时把所有权移交 ARC**，ARC 接管 release）——**「谁持有谁释放」的条约在边界上要人脑执行**，图片/字符串的 CF 桥接泄漏是重灾区。

收尾：ARC 答题的心法，「**本质是编译期插桩不是运行时 GC、四种修饰符是所有权契约、方法族约定藏着优化、CF 边界要桥接**」，能分清「编译器插桩」和「GC」是第一道分水岭。

> 面试官追问点：ARC 下还会循环引用吗？应答思路：会，ARC 自动管理「计数的加减」不管「引用图的结构」——block 捕获 self、delegate 双向持有这些「结构问题」编译器无能为力，weak/unowned 是留给开发者的人工干预点。

### 13.9 离屏渲染的触发与代价

答：一句话定调，**离屏渲染是「GPU 先在离屏缓冲区画好、再作为纹理合成上屏」的绕路：圆角/阴影/蒙版触发它，代价是显存切换和带宽翻倍**。

**为什么圆角必须绕路**（讲机理不是背清单）：**普通渲染是「遍历图层树逐层直接写 framebuffer」**（GPU 按画家算法从后往前，一遍完事）；**圆角的裁剪需要「图层内容 + mask 一起算」**——**图层的显示内容和它的形状 mask 在两个 pass 里没法一次合成**，GPU 必须**先把图层内容画进离屏缓冲（offscreen buffer），再把 mask 应用上去，最后把结果当纹理交给合成器**——**多了一次「画进缓冲 + 从缓冲读出」的往返**。

**触发的经典清单与原因**：**cornerRadius + masksToBounds 同开**（单独 cornerRadius 只影响背景色不裁内容，不触发）、**阴影（shadowPath 未设时，要遍历子层算形状）**、**mask（CAGradientLayer 蒙版）**、**group opacity（子层半透明要合起来算）**、**shouldRasterize（主动开启离屏缓存）**。

**深水区一：离屏的三大代价**——**显存开销**（每个离屏上下文一块完整缓冲）、**上下文切换**（GPU 在 framebuffer 和离屏 buffer 间切换状态，昂贵）、**合成次数翻倍**（一次变两次）——**列表里十几个圆角头像同时滚动，GPU 时间轴被离屏 pass 塞满，掉帧**。**Instruments 的 Core Animation 的 Color Offscreen-Rendered 选项**（黄色高亮离屏区域）是定位工具。

**深水区二：正确的优化姿势对照**——**圆角**：**预渲染成圆角图片（CPU 的 CoreGraphics 裁剪，运行时零成本）**或 **CAShapeLayer + 遮罩路径（仍离屏但形状简单）** 或 iOS 13+ 的 **layer.cornerRadius 优化路径（某些场景自动处理）**；**阴影**：**shadowPath 显式指定（免遍历子层，直接用路径——最大的免费午餐）**；**shouldRasterize 的辩证**：**「主动离屏 + 缓存复用」**（复杂静态内容光栅化一次反复用，rasterizationScale 记得设屏幕倍数）——**「内容不变才缓存」**，动画里开它反而每帧重画。

收尾：离屏答题的心法，「**触发讲机理（两个 pass 才能合成的都要离屏）、代价讲三项（显存/切换/合成翻倍）、优化讲对照（预渲染/shadowPath/有条件光栅化）**」。

> 面试官追问点：CPU 的圆角裁剪（预渲染）和 GPU 离屏谁好？应答思路：看场景——静态头像用 CPU 预渲染一次（运行时零成本）最赚；**频繁变化的内容 CPU 每次重裁就亏了（CPU 挤占主线程）**——「一次性成本换运行时零成本」的买卖只对不变内容成立。

### 13.10 dyld启动流程与二进制重排

答：一句话定调，**iOS 的启动是「dyld 加载镜像 → rebase/bind → runtime 初始化 → +load → main」四幕剧，启动优化的深水区武器是二进制重排（把启动页调到前面的缺页中断阶段省时间）**。

**四幕剧的顺序**（深水区一）：

1. **dyld 加载**：**加载主二进制依赖的动态库（递归）**，**mach-o 里 LC_LOAD_DYLIB 命令决定清单**——**动态库越多加载越慢**（「合并动态库」优化的依据）；**iOS 的 dyld 3 起 Craig 主二进制的启动闭包（加载和符号信息预先算好缓存）**，二次启动跳过大部分解析；
2. **rebase（基址修正）与 bind（符号绑定）**：**ASLR 让镜像地址随机**——**rebase 修「镜像内部指针」（对已知偏移加减 slide）**、**bind 修「跨镜像引用」（把 printf 这类外部符号查表填真实地址）**——**fishhook 的原理就是利用 bind 的惰性（延迟绑定，首次调用时才填）事后改函数指针**（和 09 篇 hook 系列呼应）；
3. **runtime 初始化**：**map_images/read_images（类注册、Category attach——13.7 的时机在这）**；
4. **+load → main**：全量 +load 串行执行，然后 main。

**深水区二：二进制重排（Page In 优化）**——**缺页中断是隐藏成本**：**代码首次执行时要按 16KB 一页从磁盘读进内存**（冷启动的 IO 大头之一），**Mach-O 里函数的排列顺序（链接器默认按编译单元）决定「启动路径上的函数是否集中在一页里」**——散落的话启动要多触发几十上百次缺页。**重排的原理**：**用 clang 的 SanitizerCoverage 给启动路径打点（每个函数插入 hook）→ 真机跑一次启动收集「实际执行顺序」→ 生成 order file → 链接器按这个顺序排函数（-order_file）**——**启动函数挤进少数几页，缺页次数砍半**（微信的实践数据是主进程冷启动提升 15%+ 级别）。

**优化全景的挂点对照**（把四幕剧当靶子）：**动态库合并/删除（第 1 幕）、+load 瘦身改 +initialize（第 4 幕）、二进制重排（贯穿的缺页）、fishhook 别滥用（第 2 幕的 bind 后）**——**「先测（Instruments 的 App Launch + os_signpost）再切」是优化的纪律**。

收尾：启动题的心法，「**四幕剧（dyld/rebase-bind/runtime/ load-main）是地图、缺页中断是暗礁、二进制重排是按航行日志重排舱位**」，能讲出 order file 的采集流程就是深水区。

> 面试官追问点：rebase 为什么比 bind 快？应答思路：rebase 只需「本镜像的 slide 加减」（不查任何表，纯算术）；bind 要拿符号名查「全局符号表」（跨镜像搜索，dyld 的 lazy binding 还要每次触发）——**「内部修正算术便宜、外部解析查表贵」**，这也是懒绑定存在的原因（用到才查）。
