# 1.内存管理

### 1.1 ARC与引用计数

#### 1.1.1 ARC和MRC差在哪里？五种修饰符怎么选型

答：一句话定调，**ARC 与 MRC 的区别不是"要不要引用计数"，而是"释放代码由谁写"——ARC 是编译器在编译期插入 retain/release，MRC 是人肉手写；ARC 不是 GC**。

**本质差异三点**：① **时机**——ARC 的插桩发生在编译期（Clang 前端），运行时零额外开销、无 GC 暂停；② **错误形态**——MRC 的 bug 是"多 release 崩 / 少 release 漏"，ARC 把这类错误消灭成编译期保证；③ **能力边界**——ARC 只管 ObjC 对象，**CF 对象（CGImageRef）、malloc 内存、__bridge 桥接仍要人管**。

**五种修饰符选型**（记忆锚点："拥有关系"四个字）：

| 修饰符 | 语义 | 选型场景 |
|---|---|---|
| strong | 拥有（retain/release 插桩） | 默认，绝大多数属性 |
| weak | 不拥有 + 自动置 nil | delegate、IBOutlet、打破循环 |
| assign | 不拥有不置 nil（裸引用） | 基础类型（int/CGFloat）；对象场景是逃生门 |
| copy | 拥有一份拷贝 | NSString、block、可变容器防御 |
| retain | = strong（MRC 时代写法） | 新代码别用 |

**深水区一：ARC 下照样有内存泄漏**——三种高发：**循环引用**（block 捕获 self、NSTimer 强持 target、双向 delegate）、**CF 边界**（CGImageCreate 没配 CGImageRelease）、**桥接误用**（`__bridge` 桥出去后 CF 侧无人释放）——"ARC 时代内存管理的重心从'数引用'转移到了'防环 + 管边界'"。

**深水区二：autoreleasepool 在 ARC 下没消失**——`@autoreleasepool {}` 只是语法糖，编译成 objc_autoreleasePoolPush/Pop；**大循环里建大量 autorelease 对象（读图/拼串）要手动包池**，否则峰值内存等循环结束才回落。

收尾：ARC 答题心法，「**编译器插桩不是运行时 GC、修饰符是所有权契约、泄漏重心移到环和边界**」。深度精讲见 13.6、13.8。

> 面试官追问点：ARC 的原理是运行时的吗？应答思路：不是——**Clang 编译期插入 retain/release/autorelease 调用**，运行时只有引用计数本身在工作；这个区分是第一道分水岭，答错直接暴露没读过实现。

#### 1.1.2 weak为什么能自动置nil？底层怎么实现

答：一句话定调，**weak 的自动置 nil 靠 runtime 维护的一张全局弱引用表：对象 dealloc 时遍历所有指向它的 weak 指针、批量置 nil**。

**机制三步**：① **注册**——`id __weak w = obj` 编译成 objc_initWeak，把 w 的地址存进 **SideTable 的 weak_table**（以**对象地址做 key**，哈希定位 weak_entry）；② **存活的代价**——weak 赋值**不动引用计数**（这就是它和 assign 的语义差）；③ **置 nil**——对象 dealloc 走 clearDeallocating → **weak_clear_no_lock 遍历该对象的 entry，把所有 weak 指针写 nil**，再把自己从表里摘除。

**SideTable 的分片设计**（深水区一）——全局不是一张表而是 **64 个 SideTable 组成的 stripes**（对象指针哈希取模分片），每个 SideTable 含**自旋锁 + 引用计数表 + weak 表**——**分片的意义是锁竞争摊薄**：两个不相关对象的 weak 操作大概率落在不同片、互不加锁。

**weak_entry 的两级结构**（深水区二）——指向同一对象的 weak 指针 ≤ 4 个时用**定长数组**（内联零哈希开销），超过 4 个**升级成 hash 表**——小对象多数只有一两个 weak 引用，"先数组后哈希"是按真实分布做的优化。

收尾：weak 的心法，「**不计数、登记在册、死亡时批量清零**」——对照 assign："不计数、不登记、死后悬空"。

> 面试官追问点：weak 置 nil 是线程安全的吗？应答思路：是——置 nil 发生在 dealloc 流程内且持有 SideTable 自旋锁；但**"读 weak 变量"本身不是原子的**（读到 nil 和读到对象的窗口存在），多线程下要用 stronger 化（局部 strong 化）保证块内稳定。深度精讲见 13.1。

### 1.2 内存布局与排查

#### 1.2.1 内存五大区存什么？TaggedPointer是什么

答：一句话定调，**五大区按"谁管理生命周期"划分：栈和代码区系统全权管理，全局/常量区随进程，只有堆需要引用计数——TaggedPointer 则是"把小对象塞进指针本身、不进堆"的优化**。

**五大区速查**（锚点：从上往下地址降低）：

| 区域 | 存什么 | 谁管理 |
|---|---|---|
| 栈 | 局部变量、函数帧、block 结构体（未 copy） | 编译器自动伸缩 |
| 堆 | alloc 的对象、copy 的 block | 引用计数（ARC/MRC） |
| 全局区 | 全局变量、static 变量（未初始化在 bss） | 进程生命周期 |
| 常量区 | @"..." 字符串字面量、const | 只读 |
| 代码区 | 编译后的机器码 | 只读 |

**TaggedPointer 做了什么**：**NSNumber 装箱小整数、短 NSString**（≤7~8 字节 UTF8）时，**值直接编码进指针的位里**（arm64 用高位做标记位）——**一次 malloc 都没有、引用计数也不参与、访问即解引用**——"对象"只是个穿了指针外衣的值。

**深水区一：怎么识别**——`objc_isTaggedPointer(ptr)` 查高位标记；`[obj class]` 返回的是**按 tag 预注册的类**（NSTaggedPointerString 等），isa 里存的不是类指针而是 tag 编号——**这就是 2.1.1 nonpointer isa 的近亲**（都在指针里夹带私货）。

**深水区二：实战坑**——经典 crash：**Tagged Pointer 字符串直接 stringByAppendingString 的旧 bug**（特定字节组合拼接触发）说明"指针即数据"绕过了部分运行时检查；**对 tagged 指针做地址比较/打印**得到的是编码值不是堆地址——调试时以为是野指针其实是正常对象。

收尾：五大区的心法，「**栈快而小、堆慢而管、常量只读**」；TaggedPointer 的心法，「**小对象不配拥有堆内存**」——面试里能主动讲出"这是 malloc 成本驱动的优化"就是亮点。

> 面试官追问点：为什么 TaggedPointer 只用于小对象？应答思路：指针 64 位，**减去标记位、类 tag、扩展位后剩给数据的不多**（约56位）——放不下就回退堆对象；这也解释了"长度阈值 7/8 字节"的来源。

#### 1.2.2 循环引用怎么排查？delegate为何用weak

答：一句话定调，**排查循环引用是"工具三板斧 + 断环四招"；delegate 用 weak 的本质是"持有关系必须单向（父持子），委托是协作不是拥有"**。

**排查三板斧**（从轻到重）：

| 工具 | 用法 | 擅长 |
|---|---|---|
| Xcode Memory Graph | Debug 面板 → 找紫色感叹号对象 | 直观看环的持有链 |
| Instruments Leaks | 跑一段时间看泄漏列表 | 全量扫描、历史对比 |
| MLeaksFinder | pod 进项目，pop 时自动弹告警 | 开发期实时发现 |

**MLeaksFinder 原理**（深水区一）——**栈堆一致性**： UIViewController pop 之后**理应释放**——hook 容器的 pop，**延迟 2 秒向对象发一条无害消息**（还会触发 willDealloc），还活着就告警；配合 FBRetainCycleDetector **从可疑对象出发做 BFS 找环**——"先发现泄漏者，再找环的路径"两段式。

**delegate 为何 weak**（标准答法）——**委托方持有代理方会形成环**：`tableView.delegate = self` 时 tableView（self 的属性）强持 self（self 又强持 tableView）——weak 让**持有方向保持"控制器 → 视图"的单向树**。

**深水区二：两个反例**——① **NSTimer**：`timerWithTimeInterval:target:` **runloop 强持 timer、timer 强持 target**（self 释放不了）——iOS10 的 block API + weak 是官方解法；② **CADisplayLink** 同理——**"timer 的环不是属性修饰符能解决的"**（环在 runloop，不在你的对象图里），这是 weak delegate 问题的高阶对照组。

收尾：心法，「**泄漏排查交给工具，环的治理靠设计（单向持有）**」——delegate weak 不是语法约定，是对象图拓扑的设计原则。

> 面试官追问点：delegate 用 assign 行不行？应答思路：能编译但不安全——**assign 不置 nil，代理方释放后委托方持有野指针**，调用方法直接 crash；weak = assign 的语义 + 自动置 nil 的安全。

#### 1.2.3 僵尸对象怎么捕获野指针？NSZombie原理

答：一句话定调，**NSZombie 是"用内存换崩溃信息"：对象该 free 时把 isa 换成僵尸类、内存保留，之后任何消息都被僵尸类拦截并打印现场**。

**工作流程三步**：① 开启 NSZombieEnabled 后，对象的 **dealloc 被 runtime 接管**——**不调 free，把 isa 换成 _NSZombie_ 原类名**；② 内存**原样保留**（所以"尸体"还能被发消息）；③ **再收到任何消息**——僵尸类的核心是 **forwardInvocation（或统一入口）记录"向已释放对象发了什么 selector、调用栈是谁"**，打印后 abort——**崩溃点即案发现场**。

**为什么只能 Debug 用**（深水区一）——**内存永不释放**：僵尸对象的内存既不回收也不能复用，跑得越久涨得越快；且**每个对象 dealloc 都要走一遍检查**——Release 包开启会 OOM + 拖慢——所以 Xcode 的 scheme 勾选只在 Debug 生效。

**深水区二：线上野指针怎么办**——僵尸方案上不了线，工程上做**"收尸"变种**：① **地址钓鱼**——dealloc 后保留页（不解除映射），给这块内存写毒数据，下次访问必崩且崩在真实位置；② **延迟释放池**——对象死后先冷冻（延迟数分钟再真 free），让悬空指针大概率还在"可检测窗口"内；③ **KVO/Notification 的僵尸断言**——观察者死了没摘除的场景单独兜底。

收尾：心法，「**僵尸对象把"随机的野指针崩溃"变成"必现且带现场的一次性崩溃"**——这是所有调试类基础设施的通用思路（用确定性问题替换不确定性问题）。

> 面试官追问点：野指针、悬垂指针、僵尸对象三个术语的区别？应答思路：**野指针**（未初始化的指针，值随机）、**悬垂指针**（指向已释放内存的指针，dangling）、**僵尸对象**（被 NSZombie 机制刻意保留的"尸体"，专用于捕获悬垂指针的消息发送）——能分清术语本身就是加分项。

### 1.3 拷贝与类型

#### 1.3.1 深拷贝和浅拷贝怎么分？copy的组合规则

答：一句话定调，**浅拷贝只拷指针（引用计数 +1，两指针对同一内存），深拷贝拷内容（新内存新对象）——判据就一条：拷完改一个，另一个变不变**。

**系统类的组合规则**（核心表格，背下来）：

| 原对象 | copy | mutableCopy |
|---|---|---|
| 不可变（NSArray/NSString） | **浅拷贝（返回自身）** | 深拷贝（单层） |
| 可变（NSMutableArray） | 深拷贝（单层，产物不可变） | 深拷贝（单层，产物可变） |

**关键洞察**：不可变对象 copy 返回自身是**官方优化**（不可变对象拷了也没意义，省一次分配）——`arr2 == arr1` 为 true 不奇怪。

**深水区一：容器拷贝都是"单层深"**——`[mutableArr copy]` 复制了**容器本身**，但**内层元素还是共享指针**（元素引用计数 +1）——改数组结构互不影响，改元素内部状态互相可见；**真·完全深拷贝**要 `NSKeyedArchiver 归解档` 或 `initWithArray:copyItems:YES`（配元素的 NSCopying）或 JSON 往返——"深拷贝的深度是个梯度"是本题最深的一层。

**深水区二：属性 copy 的经典崩溃**——`@property (copy) NSMutableArray *arr`——**setter 执行 copy 后产物是不可变 NSArray**，运行时调用 addObject: 直接 **unrecognized selector**——**copy 属性只能修饰不可变类型**；NSString 用 copy 的动机：**防外部传 NSMutableString 进来后偷偷改**（防御性拷贝）。

收尾：心法，「**浅拷指针深拷内存、不可变 copy 是自身、容器拷贝单层深**」——三句话覆盖 90% 考点。

> 面试官追问点：自定义对象怎么支持拷贝？应答思路：遵守 **NSCopying 实现 copyWithZone:**（copy 走它，mutableCopy 走 NSMutableCopying 的 mutableCopyWithZone:）——**不实现协议就 copy 就是崩溃**（unrecognized selector）——顺带能答出 copy 的消息链（copy → NSObject 基类方法 → 协议方法）更好。

#### 1.3.2 id和instancetype差在哪？初始化用哪个

答：一句话定调，**id 是"放弃类型检查的万能指针"，instancetype 是"编译器能推导的相关结果类型"——初始化方法一律用 instancetype**。

**三个差异**：① **类型检查**——id 赋给任何指针都不警告（静态检查失效），instancetype 让编译器知道"返回的就是接收者的类"，接错类型直接警告；② **继承推导**（核心）——`[Parent alloc] init]` 用 instancetype 声明时，**子类调用返回子类类型**（相关结果类型，related result type）——用 id 则全链退化成 id；③ **适用范围**——id 可以做变量、参数、返回值，instancetype **只能做方法返回值**（写参数直接编译错误）。

**深水区一：为什么父类的便利构造器更需要它**——`+ (instancetype)shared` 或 `+ (id)person` 里写 `[[self alloc] init]`：instancetype 版本让 `[Student person]` 推导为 Student*；id 版本返回 id，**链式调用 `.property` 的编译提示全丢**——**类型信息在继承链上的保真度**是 instancetype 的本质价值。

**深水区二：编译器的"惯例认可"**——clang 对 **alloc/new/copy/mutableCopy 开头 + 返回本类的方法自动当 instancetype**（即使声明写 id）——所以老代码 `+ (id)newObject` 没出问题不是 id 的功劳，是**方法族命名约定**兜了底（这个约定同时被 ARC 用来判定返回对象的所有权，见 13.8 深水区）。

收尾：心法，「**id 放弃检查、instancetype 传导类型、init 族靠约定**」。

> 面试官追问点：instancetype 能声明属性或参数吗？应答思路：不能——**它只在"方法返回值"位置合法**，写 `-(void)foo:(instancetype)obj` 直接编译错误——它的语义是"这个方法的返回类型关联接收者"，离开返回值位置语义不成立。

# 2.对象模型与Runtime

### 2.1 对象与类

#### 2.1.1 OC对象的本质是什么？isa指针指向哪里

答：一句话定调，**OC 对象的本质是 `struct objc_object`——一个以 isa 为第一个成员的结构体；实例的 isa 指类对象、类对象的 isa 指元类、元类链最终收敛到根元类（isa 指向自己）**。

**对象三层与 isa 走向**（记忆图）：

```
实例对象 --isa--> 类对象 --isa--> 元类 --isa--> 根元类 --isa--> 根元类（自己）
                    ↑ super          ↑ super         ↑ super
                  父类对象        父元类        NSObject
```

**isa 存的到底是什么**：arm64 下 isa 是 `union isa_t`——**不是纯指针，是 nonpointer isa 位域**：1 bit 标记位 + 索引（magic、weakly_referenced、has_assoc、has_cxx_dtor、shiftcls 存类地址）——**64 位里只有中间 33 位左右给了类指针**——"isa 夹带元数据"是 runtime 高频优化套路（对照 TaggedPointer）。

**深水区一：类对象也是对象**——类对象是 runtime 编译期/启动期创建的 `objc_class` 实例（struct，含 superclass/cache_t/bits→ro/rw），**全局唯一**（一个类一份）；所以"对象布局在编译期确定"（成员偏移定死），运行时改不了 ivar——这就是 Category 加不了成员变量的根因（见 2.3.1）。

**深水区二：isa 的两副面孔**——**isa 指针 vs object_getClass()**：KVO 偷换 isa 后 `[obj class]` 骗你返回原类（重写了 class），**object_getClass 直读 isa 位域才是真相**（见 13.5）——"看 isa 要绕过 class 方法"是调试必备常识。

收尾：心法，「**对象 = isa + 成员变量，类 = 对象的图纸，isa 链 = 方法查找的路标**」。

> 面试官追问点：为什么类对象要是单例（全局一份）？应答思路：方法表、ivar 布局是类级共享信息——**每实例存一份是浪费**；isa 把"实例 → 图纸"的复用关系固化下来，消息机制才跑得起来。

#### 2.1.2 类对象与元类是什么关系？IMP查找怎么走

答：一句话定调，**元类是"存类方法的地方"——实例方法存类对象，类方法存元类；调用链统一走 isa 查找，这是 runtime 把两类方法塞进一套机制的设计**。

**为什么需要元类**（先讲动机再讲结构）——`[Person walk]` 是给**类对象**发消息—— objc_msgSend 的查找逻辑是"顺着 receiver 的 isa 找方法"——**类对象也要有自己的"类"来存方法**——这个"类的类"就是元类；**统一性的代价是镜像世界**：实例世界（实例→类）和类世界（类→元类）结构完全对称。

**IMP 查找的两条路**：

```
[person walk]   person --isa--> Person(类) --方法列表/缓存--> IMP（实例方法）
[Person walk]   Person --isa--> Person元类 --方法列表/缓存--> IMP（类方法）
                 查不到时走 super 链：Person元类 --super--> NSObject元类 --super--> 根元类
```

**深水区一：根元类的 super 指向 NSObject（类对象）**——所以 **NSObject 的实例方法，类对象也能调**（`[Person respondsToSelector:]` 能命中 NSObject 的实例方法）——"类名调用 NSObject 实例方法"不报错的原理就在这。

**深水区二：元类的继承链和类的继承链是两条**——`Person元类 --super--> NSObject元类`（不是 Person 的父类的元类？——是：子类元类的 super 指向父类元类，链最终到根元类）；**画 isa/super 双链图**（3.3 的孙萍图）是面试白板经典题，能一次画对直接进深水区。

收尾：心法，「**实例方法在类、类方法在元类、isa 找方法 super 找继承**」。

> 面试官追问点：+ (void)test 定义在 NSObject，[Person test] 和 [[Person new] test] 都能调吗？应答思路：类调用走元类链能命中 NSObject 元类的类方法；**实例调用走类对象链能命中 NSObject 的实例方法**——但 +test 是类方法，实例调不到（除非重名实例方法存在）——用这道题现场验证两条链的分流。

### 2.2 消息机制

#### 2.2.1 msgSend怎么查找方法？消息转发有几步

答：一句话定调，**objc_msgSend 的查找是"缓存 → 方法列表 → 父类逐级"三段，找不到进消息转发三阶段（动态解析 → 快速转发 → 完整转发），最后 resignErorr 抛 unrecognized selector**。

**查找三段**（速度从快到慢）：

1. **cache_t 缓存**——哈希（selector & mask）定位 bucket，**命中直接跳 IMP**（绝大多数调用停在这）；缓存未满哈希直存、满了 3/4 扩容重哈希（原缓存清空，见 13.2）；
2. **本类方法列表**——class_rw_t 的 sorted list **二分查找**（ro 里编译期排序）；
3. **父类链逐级**——superclass 指针向上爬，每级重复 1-2（**父类的方法也会缓存到子类缓存里吗？——会，缓存挂在接收者的类上**）。

**找不到之后的"三个救生圈"**：

| 阶段 | 钩子 | 典型用途 |
|---|---|---|
| ① 动态方法解析 | `+resolveInstanceMethod:` | @dynamic 属性、动态添加方法（runtime addMethod） |
| ② 快速转发 | `-forwardingTargetForSelector:` | 把消息转给备用接收者（组合/代理对象） |
| ③ 完整转发 | `-methodSignatureForSelector:` + `-forwardInvocation:` | 签名 + NSInvocation 自定义处理（多重转发/日志/容错） |

**三个都拒绝才走 doesNotRecognizeSelector: 抛异常**——**"转发是 runtime 给你的三次挽回机会"**。

**深水区一：为什么消息机制比函数调用慢、又为什么快得可接受**——动态绑定带来两次查找开销，但**缓存命中路径高度优化（汇编实现、无栈帧、哈希 O(1)）**；且**慢路径（转发）恰好是"出错前的缓冲带"**——功能与容错兼得（见 13.2 的汇编级分析）。

**深水区二：防崩溃的工程化**——转发三阶段是**全局兜底崩溃的官方入口**：在 ③ forwardInvocation 里替换危险方法（ NSArray 越界等也常用 swizzling，见 2.2.3）；**代价**：吞异常掩盖真 bug——"兜底要带日志上报，不是静默"。

收尾：心法，「**缓存兜住 90%、列表兜住常规、super 链兜住继承、转发兜住容错**」——四层漏斗就是 msgSend 全貌。深度精讲见 13.2。

> 面试官追问点：方法缓存为什么挂在类上而不是全局一张表？应答思路：**查找路径的第一站就是接收者的 isa 指向的类**——就近缓存访问局部性好；全局表需要全局锁 + 大哈希，竞争和内存都不可控。

#### 2.2.2 Runtime的类结构是什么？方法交换怎么用

答：一句话定调，**objc_class 的核心是 bits 指针串起的 ro（只读、编译期）和 rw（可写、运行时）双层结构——方法交换本质是"交换 rw 方法列表里两个 Method 的 IMP 指针"**。

**类结构四件套**：

```
objc_class
 ├─ isa        → 元类（2.1.2 的链）
 ├─ superclass → 父类（super 查找用）
 ├─ cache_t    → 方法缓存（2.2.1 的第一站）
 └─ bits & FAST_DATA_MASK → class_rw_t（运行时可写）
        ├─ methods/properties/protocols（二维数组：分类附加进来）
        └─ class_ro_t（编译期定死：ivars、方法名、大小）
```

**ro/rw 分层的动机**——**编译期能定的进 ro（干净、只读、省内存）**；**运行时要改的进 rw**（Category attach、addMethod 都改 rw）——"脏页集中、干净页共享"的内存哲学。

**Method Swizzling 的机制与坑**：

```objc
// 标准姿势（+load 里，dispatch_once 保护）
Method original = class_getInstanceMethod(class, @selector(viewDidLoad));
Method swizzled = class_getInstanceMethod(class, @selector(dc_viewDidLoad));
method_exchangeImplementations(original, swizzled);
// 之后调 viewDidLoad 实际执行 dc_viewDidLoad，方法体里调 dc_ 开头反而回到原实现
```

**三个坑**：① **父类方法的交换**——子类没实现该方法时 class_getInstanceMethod 会拿到父类的，**换掉影响全家**（要判断 class_addMethod 是否插入成功）；② **交换时机**——必须在 +load（见 13.7），晚了有代码已走原路径；③ **交换了缓存没刷**——老版本要 `_flush_cache`，新 runtime method_exchangeImplementations 已处理——**"交换的是 Method 结构里的 imp 字段，不是方法名"**。

**关联对象原理**（同题必带）——`objc_setAssociatedObject` 存取不走类的内存：**全局 AssociationsManager 的哈希表**（key = 对象地址 + 关联 key）——**所以 Category 能加"属性"（getter/setter + 关联对象存值）但加不了 ivar（内存布局编译期定死）**；策略参数（retain/copy/atomic）决定值的内存语义。

收尾：心法，「**ro 定生死、rw 管运行时、交换换的是 IMP 指针、关联对象住在全局表**」。

> 面试官追问点：swizzling 后如何"撤销"？应答思路：**再换一次（交换是对合操作）**——但已持有的 IMP 缓存和调用路径会短暂混乱，工程上很少真撤销，一般加开关（交换后进入自己的实现，内部判断开关决定是否执行增强逻辑）。

#### 2.2.3 Runtime四大应用场景？字典转模型的原理

答：一句话定调，**Runtime 的工程价值是"运行时改类 + 动态取值赋值"——四大场景：字典转模型、自动归档、方法交换防崩溃、动态 hook 埋点**。

**场景一：字典转模型**（核心流程三步）：

```objc
// 1. class_copyIvarList 拿到全部成员变量（含属性合成的 _ivar）
unsigned int count;
Ivar *ivars = class_copyIvarList([Model class], &count);
// 2. 逐个 ivar 取名字（_name → 去下划线映射字典 key）
// 3. KVC setValue:forKeyPath: 赋值（自动处理类型转换/嵌套）
```

**为什么比手写 setter 强**——**一个 for 循环处理任意模型**（新增字段零代码）；**局限**——类型安全弱（NSString 塞了 NSNumber 要靠 runtime type 判断兜底）、嵌套容器要递归——YYModel 的优化（_yy_propertyGenius 缓存属性元信息 + CoreFoundation 直接转换）是进阶话题。

**场景二：自动归档**——归解档原本要手写每个字段的 encode/decode——**用 class_copyIvarList + KVC 统一处理**，一个基类方法搞定全部子类。

**场景三：防崩溃**——**交换系统方法替换危险实现**：NSArray objectAtIndex: 越界返回 nil 而不是崩（配合 2.2.1 的转发兜底）；**实现路径就是 2.2.2 的 method_exchangeImplementations**——注意只 hook 自己进程，且要打日志上报（静默吞错是灾难）。

**场景四：动态埋点/AOP**——hook viewWillAppear: 统一插日志（无侵入埋点）——**"交换 + 不改业务代码 = AOP"**。

**深水区：四场景的共同本质**——**"把编译期写死的东西（字段访问、方法调用）延迟到运行时做"**——灵活性换性能和类型安全，工程上用在"横切面"（日志/容错/序列化），**业务核心逻辑别滥用**（排查困难）。

收尾：心法，「**遍历属性 + KVC = 转模型，交换 IMP = AOP 防崩，同一套 runtime API 吃遍天**」。

> 面试官追问点：字典转模型为什么用 ivar 而不是 property 列表？应答思路：ivar 列表**包含属性合成的 _ivar 且顺序稳定**，而 class_copyPropertyList 拿不到私有 ivar——**用 ivar 能覆盖更多字段**；另注意 ivar 名带下划线要去掉再查字典。

### 2.3 Category与通知

#### 2.3.1 Category怎么加载的？为何不能加变量

答：一句话定调，**Category 是运行时"附加"到类的方法列表（插队排前面），加不了成员变量是因为对象的内存布局在编译期已定死——属性可以用"关联对象"这个外挂补**。

**加载流程**（精简版，深度见 13.7）——**dyld 加载 image → read_images 把 Category 的方法 attach 进 class_rw_t（插在原方法列表前面）**——所以"覆盖"其实是"排在前面先被找到"（**原实现还在，swizzling 能捞回来**）——**多个 Category 同名方法：后编译的在更前面（Build Phases 顺序定胜负）**。

**为何不能加变量（根因链）**——对象的内存 = **编译期算好的固定偏移**（A 在 0x8，B 在 0x10...）——**Category 是运行时才 attach 的，此时改布局会让所有已存在对象的成员偏移错位**——所以编译器直接禁止；**关联对象绕开的原理**：值存在**全局 AssociationsManager 哈希表**（和对象内存无关），对象 dealloc 时 runtime 检查 has_assoc 位统一清理（2.2.2）。

**+load vs +initialize 对比**（同题高频）：

| | +load | +initialize |
|---|---|---|
| 时机 | main 之前（read_images） | 首次收到消息（懒） |
| 调用方式 | 直接函数指针（不走 msgSend） | 走完整消息机制 |
| 次数 | 每类一次（含分类的） | 父类可能被多次触发（子类不实现时） |
| 代价 | 拖启动 | 首次调用卡顿 |

**深水区一：Category vs Extension**——**Extension（匿名分类）编译期就合并进类**（能加 ivar，因为发生在布局确定前）；**Category 运行时附加**（只能加方法）——"时机决定能力"。

**深水区二：+load 的纪律**——**父类先、类先于分类、互不覆盖（都调一遍）**——冷启动 hook 的窗口期也在这（鱼竿代码）；代价是**串行拖慢启动**，新代码趋势用 +initialize。

收尾：心法，「**方法能附加、内存不能动、属性靠关联、覆盖是插队**」。深度精讲见 13.7。

> 面试官追问点：Category 和 Extension 都能给类加方法，本质区别？应答思路：**编译期合并（Extension，私有性、可加 ivar）vs 运行时附加（Category，可拆分文件、可 hook 系统类）**——Extension 是设计工具，Category 是扩展/侵入工具。

#### 2.3.2 通知的派发机制是什么？忘记移除会崩吗

答：一句话定调，**通知是"观察者模式 + 名称索引表 + 同步派发"——post 的线程就是收的线程；iOS 9 之后忘移除不再崩溃（dealloc 自动摘除），但移除仍是好习惯**。

**机制三要素**：① **注册**——addObserver 把观察者/selector/block 塞进**通知中心的全局表**（按通知名分组）；② **派发**——post 时**同步遍历该名字的观察者列表逐个调用**（在 post 线程！）；③ **移除**——removeObserver 把条目摘掉。

**同步派发的两个推论**（深水区一）——① **post 在什么线程，observe 回调就在什么线程**（UI 更新要自己切主线程）；② **观察者的执行会阻塞 post 者和后续观察者**——一个回调卡死全场卡死——**异步要用 NotificationQueue**（合并 + 投递时机：空闲时/某 runloop 模式，底层还是切 runloop 异步 post）。

**iOS 9 前后的移除差异**（深水区二）——**iOS 9 前**：观察者 dealloc 后表里留着野指针，post 时向尸体发消息 → 崩（和 KVO 同款崩溃，见 13.5 的坑 1）；**iOS 9 起**：**dealloc 时自动移除**（runtime 钩子）——**不崩但有例外**：block 版观察者持有 block、block 持有观察者照样环；**带 addObserverForName 的 token 忘释放**也是泄漏源——"不崩 ≠ 没问题"。

**通知 vs KVO vs delegate 的选型**（同题常带）——**通知是"广播"（一对多、松耦合、无序）**，KVO 是"属性的精确观察"（一对少、强约定），delegate 是"协作的协议"（一对一、强类型）——**通信方式选型先问几个接收方**。

收尾：心法，「**同步派发认准 post 线程、自动移除救了崩溃救不了泄漏、广播用通知协作用 delegate**」。

> 面试官追问点：怎么让通知回调一定在主线程？应答思路：两招——**post 线程就是回调线程**（post 前切主线程：`dispatch_async(main, post)`，影响所有观察者）；或**观察者侧各自切**（回调里 dispatch_async 回主线程，只影响自己）——前者省事后者精确，按需选。

# 3.Runloop与事件响应

#### 3.1 Runloop和线程什么关系？六种应用是什么

答：一句话定调，**Runloop 是"线程的事件循环保活器"：一一对应（一条线程一个 Runloop，懒创建）、主线程默认开启、子线程默认不开——它的本质是"休眠等事件、来了处理、处理完再睡"的 while 循环**。

**关系三条**（先答关系再谈应用）：① **一一对应**——runloop 存在全局字典里（线程 → runloop 的映射），**懒创建**（首次获取才建）；② **主线程开、子线程默认不开**——子线程不跑 runloop，任务执行完线程即回收；③ **CFRunLoop 是线程安全的、NSRunLoop 不保证**（Foundation 层没加锁）。

**Mode 的机制**（应用的共同底座）——**runloop 一次只能跑一个 mode**，事件源挂在特定 mode 上——`kCFRunLoopDefaultMode`（平时）/ `UITrackingRunLoopMode`（滚动）/ `kCFRunLoopCommonModes`（标记集合，default + tracking 都算）——**"滑动时 timer 停"的根因**：timer 挂在 default，滚动切到 tracking 后 default 的事不处理——**解法是 timer 挂 common**。

**六种应用**（每个一句话说清挂载点）：

| 应用 | 挂在哪 | 一句话机制 |
|---|---|---|
| AutoreleasePool | 主循环 Observer（BeforeWaiting 排干） | 见 13.6 深水区一 |
| 事件响应 | source0（端口事件转 13.3 的响应链） | 触摸事件唤醒 runloop 分发 |
| 手势识别 | 系统 Observer（BeforeWaiting 前切模式） | 识别期间切 mode 保证独占 |
| NSTimer | 对应 mode 的 timer 源 | 到点唤醒（受 mode 限制） |
| CADisplayLink | 同 timer（垂直同步信号） | 每帧回调（性能监控原理） |
| 卡顿检测 | 主 runloop 监听 BeforeWaiting/超时 | **两次状态间耗时超阈值 = 卡顿**（微信方案） |

收尾：心法，「**线程的保活循环、mode 是切换器、卡顿检测就是盯它睡眠**」——六应用全部是"事件源挂 mode"的变体。深度精讲见 13.3。

> 面试官追问点：子线程的 timer 为什么不跑？应答思路：**timer 依赖 runloop 调度**——子线程默认没有 runloop 转着，timer 加了也不触发；要么 `[NSRunloop currentRunLoop] addTimer + run]` 手动跑起来，要么用 GCD timer（不依赖 runloop，见 5.1）。

#### 3.2 事件响应链怎么传递？hitTest流程是什么

答：一句话定调，**事件的传递是"自上而下的命中测试（hitTest 递归）+ 自下而上的响应链（responder chain 冒泡）"两阶段——前者找第一响应者，后者找谁能处理**。

**阶段一：hitTest 命中测试**（从 window 开始递归）：

```
hitTest:withEvent: 的逻辑（伪代码）：
1. 自己 hidden / alpha<0.01 / userInteractionEnabled = NO → 返回 nil
2. pointInside:withEvent: 点不在自己边界内 → 返回 nil
3. 从后往前遍历 subviews（后加的在上面，先测上面的）
   → 子视图 hitTest 递归，子命中就返回子
4. 所有子都不命中 → 返回自己
```

**两个细节**（深水区一）：① **遍历顺序是倒序（subviews 最后一个先测）**——"最上面的视图优先命中"；② **兄弟视图重叠，命中后下面兄弟直接出局**——**hitTest 是纯几何 + 层级判定，不看响应能力**。

**阶段二：响应链冒泡**——第一响应者（如 button）不处理 → `nextResponder` 一路向上：**view → 父 view → ... → UIViewController → UIWindow → UIApplication → AppDelegate（最后丢弃）**——"自己处理不了就问爹"。

**深水区二：实战改造**——① **扩大点击热区**：重写 pointInside 让边界外的点也算命中（"返回更大的范围"）；② **穿透点击**：重写 hitTest 返回 nil 让自己不接事件（上层按钮盖住下面也能点）；③ **事件拦截**：重写 hitTest 把命中转给特定子视图——**hitTest 是事件分发的唯一入口，改它就是改分发规则**。

收尾：心法，「**hitTest 自上而下找接收者（几何）、响应链自下而上找处理者（能力）**——两阶段方向相反别搞混。

> 面试官追问点：hitTest 会被调用几次？应答思路：**同一次触摸可能多次**（系统在事件投递的不同阶段探测，甚至做"触摸预言"预判）——所以 hitTest 里别做重活/有副作用——能答出"多次调用"就超过多数候选人。

#### 3.3 UIView和CALayer怎么分工？为什么这样

答：一句话定调，**UIView 是"事件 + 布局的壳"，CALayer 是"纯绘制的核"——分工的设计目的是职责分离 + 跨平台复用（iOS/macOS 共用 CoreAnimation）**。

**分工清单**：

| 能力 | UIView | CALayer |
|---|---|---|
| 事件响应（hitTest/touch） | ✓ | ✗（无 responder 身份） |
| 布局（frame/autoLayout） | ✓ | ✗ |
| 绘制（contents/动画） | 委托给 layer | ✓（位图 + 属性） |
| 树结构 | view 树（同步维护 layer 树） | layer 树（三层副本，见 3.4） |

**为什么这样分（设计的三个理由）**：① **单一职责**——绘制（合成器消费）和交互（UIKit 管）生命周期、责任方不同；② **跨平台**——macOS 的 NSView 也用 CALayer，**把"平台无关的绘制合成"下沉到 CoreAnimation 层**；③ **性能**——layer 是纯数据（可被渲染服务进程直接读），**view 是带逻辑的重对象**——动画时只动 layer（render server 独立渲染），主线程的 view 不用管。

**深水区一：隐式动画的归属**——**直接改 layer 属性（非 UIView 动画块内）默认带 0.25s 隐式动画**（CATransaction 的默认行为）——**UIView 的 layer 关掉了它**（actions 屏蔽），**自己 new 的 layer 开着**——"为什么我建的 layer 动手自己会动"的答案。

**深水区二：双树的同步**——view 树和 layer 树**结构同步**（addSubview 同时 add sublayer）——**但只同步结构，属性动画期间 view.frame 不变、layer.presentationLayer 在动**（这是动画"看起来动了"但 view 没变的原理，见 3.4）。

收尾：心法，「**view 管人和事（事件布局）、layer 管脸面（像素）、动画只动脸不动人**」。

> 面试官追问点：为什么不直接让 UIView 兼具两者？应答思路：**职责合并会让渲染服务进程依赖 UIKit**（动画在独立进程跑，见 3.4）——分离后 CA 独立于平台和 UI 框架，**组合优于合并**的教科书案例。

#### 3.4 UIView动画的原理是什么？与CA的区别

答：一句话定调，**UIView 块动画是"属性动画的语法糖"——块内改的 layer 属性被 CA 事务捕获，渲染在独立的 render server 进程完成；与直接用 CA 的区别是"糖的浓度和控制的粒度"**。

**UIView 动画的机制三步**：

```
[UIView animateWithDuration:... animations:^{ view.frame = newFrame; }]
   ↓ ① 块内改属性时，UIView 属性 setter 内部转 layer 属性
   ↓    （CATransaction 捕获：记录"改了什么 + 目标值"）
   ↓ ② commit 时 CoreAnimation 把 layer 树拷贝出"模型层 presentation 层"
   ↓    真实 layer 立即到终值，presentation 层负责中间帧插值
   ↓ ③ 渲染发生在 render server 进程（RenderServer）
        —— 主线程只提交一次，动画期间 UI 不参与，这就是动画流畅的原因
```

**UIView 动画 vs CA 动画对比**：

| 维度 | UIView 块动画 | CABasicAnimation 等 |
|---|---|---|
| 本质 | CATransaction + 隐式动画的封装 | 显式动画对象 |
| 控制粒度 | 整体（时长/曲线/完成回调） | 精细（keyframe/path/逐帧插值模型） |
| 可动画属性 | frame/alpha/transform 等 UIView 层 | layer 全部可动画属性（cornerRadius 等） |
| 结束状态 | **frame 真的变了**（模型层更新） | **默认结束后弹回**（removedOnCompletion，模型层没变） |

**深水区一：CA 动画"弹回"的经典坑**——CABasicAnimation 结束后视图**回到原位**——因为**动画的是 presentation 层（幻灯片），模型层从没动过**——解法：`fillMode = kCAFillModeForwards + removedOnCompletion = NO`（停最后一帧）或**动画同时手动改模型层**——理解这个坑 = 理解双层的存在。

**深水区二：CADisplayLink 帧动画**——**与屏幕垂直同步信号对齐的逐帧回调**（挂 runloop，见 3.1）——自己算每一帧的值（雪花/游戏类动画）——**UIView 动画是"声明终值让 CA 插值"，displayLink 是"逐帧手绘"**——两极之间的光谱覆盖全部动画场景。

收尾：心法，「**UIView 动画是糖、CA 是底、动画在独立进程、模型层幻灯片层要分清**」。

> 面试官追问点：动画期间用户点击会命中哪个位置？应答思路：**hitTest 用的是 model layer（终值/当前 frame）**——动画"看起来"在中间但点击判定按真实属性——**想让点击跟随动画**要手动 hitTest presentationLayer（`[layer.presentationLayer hitTest:]`）——这个问题能直接筛出懂双层模型的候选人。

# 4.Block与属性关键字

#### 4.1 Block有哪三种类型？变量捕获怎么实现

答：一句话定调，**Block 是"捕获了外部变量的结构体 + 函数指针"——三种类型由"捕获有无 + 被谁持有"决定：全局块（无捕获/常驻）、栈块（有捕获/栈上）、堆块（栈块被 copy 后升级）**。

**三种类型判定矩阵**：

| 类型 | 判定 | 存活 |
|---|---|---|
| __NSGlobalBlock__ | **不捕获任何外部变量**（只用参数和全局） | 编译期确定，只读区，永不释放 |
| __NSStackBlock__ | 捕获了变量且**未被 copy** | 随栈帧，出了作用域就悬空 |
| __NSMallocBlock__ | 栈块被 copy（ARC 下赋给 strong/copy 属性自动触发） | 引用计数管理，安全带出作用域 |

**变量捕获规则**（核心）：**block 结构体里为每个捕获的变量留一个成员**——① **局部基本类型**（int/BOOL）——**值拷贝**（改的是块内的副本，块外再改也不影响块内）；② **局部对象类型**——**指针拷贝 + retain**（ARC 插桩）——这就是循环引用的源头（捕获 self = 结构体持 self）；③ **静态变量/全局变量**——**不捕获，直接访问**（存在全局区，生命周期天然覆盖 block）。

**__block 的原理**（深水区一）——**基本类型想在块内可写**：`__block int a` 被包装成 `__Block_byref_a` 结构体（**真正存值的变量搬到堆上**）——**block 捕获的是这个包装结构体的指针**——块内块外读写都重定向到同一份堆内存——**"__block 把值语义改成共享语义"**；ARC 下 __block 修饰对象还会被 block copy 时 retain（MRC 不会，这是两代差异考点）。

**深水区二：copy 的升级链**——栈块被 copy：**栈块结构体搬到堆**，捕获的 __block 包装结构体**跟着搬**（旧栈块留下 forwarding 指针指向堆版本——栈上残留引用也能找到新家）——**"栈堆同体的 forwarding 桥梁"**是白板画图题。

收尾：心法，「**结构体 + 捕获列表 + copy 升级**——类型三态是"捕获有无 × copy 有无"的矩阵」。深度精讲见 13.4。

> 面试官追问点：block 什么时候是栈块？应答思路：**ARC 下显式场景基本绝迹**（赋给强引用属性就自动 copy）——但**作为函数参数直接传字面 block 且被调用方没 copy** 时是栈块——所以第三方 API 接 block 参数要确认它"有没有逃逸"（API 文档标 escaping/non-escaping 的意义）。

#### 4.2 Block循环引用怎么破解？weakself怎么用

答：一句话定调，**环的链路是"self 强持 block 属性 + block 结构体捕获（retain）了 self"——破解靠"断环"（weak）与"执行期保护"（weak-strong dance）的分离**。

**环的精确构成**：`self.block = ^{ self.xxx }` → ① self 强持有 block（copy 属性）；② block 结构体的捕获成员持 self（retain）——**两个箭头首尾相接成环，引用计数永远 > 0**。

**三种破解姿势**（按场景选）：

```objc
// ① 基础款：weak 断环
__weak typeof(self) ws = self;
self.block = ^{ [ws doSomething]; };        // 块不持 self，环断

// ② 进阶款：weak-strong dance（块内多次用 self 且要执行期安全）
__weak typeof(self) ws = self;
self.block = ^{
    __strong typeof(ws) s = ws;              // 执行期间临时持有
    if (!s) return;                          // self 已释放就早退
    [s step1]; [s step2];                    // 两步之间 self 不会被释放
};

// ③ 传参款：block 设计成带参数回调（block 不捕获 self，调用方传）
self.block = ^(ViewController *vc) { ... };  // 谁调用谁负责传
```

**为什么②是"正确姿势"**（深水区一）——**weak 单独用有窗口风险**：块执行到一半（异步回调中途）self 释放——`[ws step1]` 后 `ws` 变 nil，`step2` 静默丢失——**strong 的语义不是"重新拥有"而是"执行期间钉住"**（块结束自动释放）——"**不是保证不强引用，是保证执行期安全**"。

**深水区二：什么情况不需要 weak**——**block 没被 self 持有**（三层判断：self 是否强持 block → block 是否捕获 self → 是否成环）——`[UIView animateWithDuration: animations:^{ self.label ... }]` **不用 weak**（UIView 不归 self 持有，块的生命周期短暂，无环）——**无脑 weak-self 是不懂原理的表现**，能说清"为什么不加"比"加上"更加分。

收尾：心法，「**先判环再动手，weak 断环、strong 钉住执行期、无环不动**」。

> 面试官追问点：weak-strong dance 里 if (!s) return 之后代码还执行吗？应答思路：**s 是局部 strong 指针**——ws 已 nil 则 s 也是 nil，return 早退；不写判断则后续对 nil 发消息全部安全无操作（OC 的 nil 语义），但**逻辑分支可能不完整**——判断的价值是"显式处理已释放"而不是防崩溃。

#### 4.3 属性关键字怎么选？copy为什么修饰字符串

答：一句话定调，**关键字选型一句话："拥有关系（strong/weak/assign）× 值语义（copy）× 线程性（atomic）"三个维度独立选——NSString 和 block 用 copy 都是"防御性拥有"**。

**选型速查**：

| 属性类型 | 修饰符 | 理由 |
|---|---|---|
| NSString / NSArray（不可变容器） | copy | 防外部传可变版本偷改（见 1.3.1 深水区二） |
| block | copy | MRC 遗产 + 语义表达"要堆块"（见 13.4 追问） |
| NSMutableArray 等可变容器 | strong | copy 会降级成不可变（崩溃坑，见 4.4） |
| delegate | weak | 断持有环（见 1.2.2） |
| 基础类型 / 结构体 | assign | 无引用计数概念 |
| 大多数对象 | strong | 默认拥有 |

**atomic 为什么不能保证线程安全**（深水区一）——**atomic 只保证"单个 setter/getter 的原子性"**（底层自旋锁，setter 和 getter 互斥）——但：① **复合操作不安全**：`self.count += 1` 是读 + 写两步，两次各自原子但中间可被打断；② **跨属性不变式不安全**：A、B 两个 atomic 属性要满足 A==B，改 A 后改 B 前有空窗——**"原子的砖头盖不出原子的房子"**；③ 有性能代价（锁 + 读写屏障），**iOS 默认 nonatomic 就是"绝大多数属性不需要"的官方表态**。

**深水区二：readonly 的正确打开方式**——.h 声明 readonly、**.m 的 class extension 里重声明 readwrite**——外部只读内部可写（比暴露自定义 setter 干净）；**getter=setter: 自定义命名**用于布尔型的 isXxx 习惯——关键字的"组合技"比单点更能体现工程素养。

收尾：心法，「**拥有看强弱、防御用 copy、线程安全靠队列锁而不是 atomic**」。

> 面试官追问点：copy 修饰 block 和 strong 修饰 block 在 ARC 下有区别吗？应答思路：**行为等价**（ARC 的 strong 属性赋值 block 时也会自动 copy）——**写 copy 是语义宣言**："这个属性要持有堆块"——MRC 时代不写 copy 会持有栈块出作用域悬空，肌肉记忆沿用至今。

#### 4.4 assign修饰对象为什么崩？三个坑说清楚

答：一句话定调，**assign 修饰对象的崩溃链是"释放后指针不置 nil → 野指针 → 向尸体发消息"；三个高频坑分别是 assign 对象、copy 修饰可变容器、以及 nullability 的静默失效**。

**坑一：assign 修饰对象**（核心机制）——`@property (assign) id obj` ——**不 retain 也不置 nil**——对象被别处释放后，**obj 里还是那块（已回收）内存的地址**——下一次 `[obj doSomething]`：内存可能已被复用（向陌生对象发消息，行为不可预测）或已 unmap（EXC_BAD_ACCESS）——**对照 weak：weak 是"不拥有 + 登记 + 死后置 nil"，assign 是"不拥有 + 不登记 + 死后悬空"**——assign 只该给基础类型用。

**坑二：copy 修饰 NSMutableArray**——**setter 执行 copy 产物是不可变 NSArray**（1.3.1 规则表），运行时调 addObject: → **unrecognized selector 崩溃**——**编译器不报错**（类型声明是 NSMutableArray，实际运行对象是 NSArray）——**可变容器一律 strong**。

**坑三：nullability 的静默失效**——`nonnull/nullable/null_resettable/null_unspecified`：① **只做编译期警告不做运行时保证**（Swift 桥接时才强约束）；② **检查是"函数级"的**——**在某个文件（或一块区域）内声明一次后，未标注的参数默认继承**——**第三方旧库引入后类型冲突，warning 一开一大片**；③ `null_resettable` 的语义："读不为 nil，写可以为 nil 置默认"（如 tintColor）——**三个标注的语义边界**比"会不会用"更容易考倒人。

收尾：心法，「**assign 是裸引用（对象勿用）、copy 是降级器（可变容器勿用）、nonnull 是君子协定（别当运行时保险）**」——三个坑的共同根因：**关键字的语义是编译期/运行期的有限承诺，超范围使用必踩雷**。

> 面试官追问点：怎么快速定位 assign 野指针崩溃？应答思路：崩溃栈看到 **message sent to deallocated 或 EXC_BAD_ACCESS** → 开 Zombie（见 1.2.3）复现——崩溃信息会打印"向已释放对象发了 selector"——顺藤摸瓜查属性声明；线上用"地址钓鱼/延迟释放"方案（1.2.3 深水区二）。

# 5.多线程

#### 5.1 GCD四种队列组合怎么用？死锁怎么发生

答：一句话定调，**四种组合 = 同步/异步（谁等谁）× 串行/并行（任务排不排队）——死锁只发生在"同步 + 目标队列是当前队列"的组合**。

**四种组合矩阵**（执行模型 + 典型用途）：

| 组合 | 行为 | 典型用途 | 风险 |
|---|---|---|---|
| 同步 + 串行 | 阻塞等前一个任务跑完 | 顺序依赖、切队列取值 | **死锁高发区** |
| 同步 + 并行 | 阻塞但任务可并行调度 | 少用（等待一组并行任务） | 死锁（罕见） |
| 异步 + 串行 | 不阻塞，任务顺序执行 | **串行队列当"锁"用**（5.5）、顺序流水线 | 无 |
| 异步 + 并行 | 不阻塞，并发执行 | 大多数后台任务、dispatch_group | 无 |

**死锁的机理**（深水区一）——`dispatch_sync(serialQueue, block)` 在**当前线程正占用该队列**时：**sync 要"等 block 执行完"，block 排在队尾要"等当前任务让出队列"**——互等 = 死锁。**经典案发现场**：

```objc
// 主线程调：主队列 + 同步 = 必死
dispatch_sync(dispatch_get_main_queue(), ^{ ... });   // ❌ 主线程等主队列，主队列等主线程

// 串行队列内再同步自己 = 必死
dispatch_sync(serialQueue, ^{                         // ❌ 同一条队列，嵌套 sync
    dispatch_sync(serialQueue, ^{ ... });
});
```

**判断口诀**：**"sync 的目标队列 == 当前正在执行的队列 → 死锁"**——与几层嵌套、什么线程无关，只看队列占用关系。

**深水区二：sync 的合法用途**——**跨队列取值**：异步往串行队列丢写任务，需要读时 `dispatch_sync(serialQueue, ^{ value = self.x; })`——**"串行队列 + sync 读 = 无锁的线程安全"**（读写都被队列串行化，见 5.5）——sync 不是洪水猛兽，**"对别的队列 sync"是安全的**。

收尾：心法，「**异步并行是常态、同步串行是锁、sync 对准当前队列是自杀**」。

> 面试官追问点：@synchronized 的原理？应答思路：底层是 **objc_sync_enter/exit + 哈希表按对象地址取递归锁**——简单但开销大（哈希查锁 + 异常安全的 try/finally）；**性能敏感场景换 os_unfair_lock 或串行队列**（5.3 选型表）。

#### 5.2 多读单写怎么实现的？栅栏和信号量怎么用

答：一句话定调，**多读单写是"读者并行、写者独占"的并发模型——GCD 实现 = 并发队列 + dispatch_barrier（栅栏写）+ 普通读**。

**栅栏方案**（标准答案）：

```objc
// 并发队列：读走普通异步/同步，写走 barrier
dispatch_queue_t queue = dispatch_queue_create("rw", DISPATCH_QUEUE_CONCURRENT);

- (id)readValue {
    __block id result;
    dispatch_sync(queue, ^{ result = self.data; });      // 读：多个可同时进
    return result;
}
- (void)writeValue:(id)v {
    dispatch_barrier_async(queue, ^{ self.data = v; });   // 写：栅栏独占
}
```

**栅栏的语义**——**barrier 任务执行时，等前面所有任务完成、后面所有任务等着**——并发队列里插一根"独木桥"：**桥前桥后并行，桥上只走一个人**——恰好是"多读单写"的形状。

**深水区一：barrier 的坑**——**只对自建的并发队列有效**：**全局队列（global queue）上的 barrier 退化成普通任务**（系统队列被所有人共享，栅栏没法独占它）——**"barrier 必须配私有并发队列"**是最常见的实战错误。

**深水区二：信号量的两个用途**（同题必带）——① **限并发数**：`semaphore(3)` + 循环里 wait/signal——最多 3 个任务同时跑（网络请求限流）；② **变异步为同步等待**：wait(FOREVER) 等异步回调 signal——**注意主线程 wait 异步回调 = 死锁隐患**（回调可能要主队列）。③ **GCD 定时器**（dispatch_source）与 NSTimer 对比：**不依赖 runloop（子线程也能跑）、精度高（不粘 mode）、可暂停取消**——5.1 追问的进阶版。

收尾：心法，「**并发队列 + 栅栏 = 免锁的多读单写；信号量管数量、栅栏管顺序**」。

> 面试官追问点：读写锁（pthread_rwlock）和栅栏方案怎么选？应答思路：**pthread_rwlock 纯内存锁更快，但要自己管递归/升级/错误处理**；**栅栏方案统一在 GCD 语义里（可组合 group/queue 玩法）、代码可读性好**——默认栅栏、极致性能才上 rwlock。

#### 5.3 OSSpinLock为什么不安全？锁怎么选型

答：一句话定调，**OSSpinLock 不安全是因为"优先级反转"：低优先级线程持锁、高优先级线程自旋等待，忙等抢占 CPU 让持锁者永远跑不完——现代替代是 os_unfair_lock**。

**优先级反转的机理**（经典三角色）：

```
高优先级线程 T1：要锁 → 自旋忙等（占着 CPU 疯狂轮询）
低优先级线程 T2：持锁 → 被 T1 抢走 CPU → 永远没机会执行 → 不放锁
T1 忙等 T2 放锁、T2 等 CPU —— 互相卡死（活锁）
```

**深水区一：为什么自旋锁怕反转、互斥锁不怕**——**自旋 = 不让出 CPU**（乐观忙等）——持锁的低优先级线程拿不到 CPU；**互斥 = 阻塞休眠**（让出 CPU）——内核调度器能照顾低优先级线程跑完临界区——**pthread_mutex 特意带 priority inheritance 应对反转**——所以 iOS 官方弃用了 OSSpinLock（libobjc 源码注释原话：unsafe）。

**锁选型表**（背熟直接过）：

| 锁 | 特性 | 场景 |
|---|---|---|
| @synchronized | 递归、对象粒度、慢 | 简单少用 |
| os_unfair_lock | **OSSpinLock 官方替代**（内核辅助解决反转） | 轻量临界区首选 |
| pthread_mutex | 通用互斥（有递归变体） | C 层/性能敏感 |
| NSRecursiveLock | 可重入 | 递归函数里的加锁 |
| dispatch_queue(串行) | "队列即锁"（5.1） | 异步友好、可组合 |
| barrier(并发队列) | 多读单写（5.2） | 缓存/数据库层 |
| NSCondition | 条件变量 | 生产者消费者 |

**深水区二：递归锁的必要性**——普通锁在**同线程重入时自死锁**（A 方法持锁调 B 方法，B 也要这把锁）——递归锁记录"持锁线程 + 计数"，同线程重入只计数不加阻——**"锁的粒度和调用链的嵌套深度"决定要不要递归锁**。

收尾：心法，「**自旋怕反转、互斥会休眠、队列当锁用是 iOS 特色**」。

> 面试官追问点：atomic 的底层就是自旋锁，为什么属性用它没被弃用？应答思路：**属性的临界区极小（一次指针赋值），忙等窗口纳秒级，反转风险可忽略**——**危险的是"长临界区 + 自旋"的组合**——锁的选型永远是"临界区长度 × 竞争烈度"的函数。

#### 5.4 NSOperation和GCD怎么取舍？依赖怎么用

答：一句话定调，**GCD 是 C 层的"轻队列 API"，NSOperation 是"对象化的任务抽象"——取舍看你要不要"任务生命周期管理"（依赖/取消/观察/KVO）**。

**能力对比**：

| 维度 | GCD | NSOperation |
|---|---|---|
| 依赖 | group（只管"全部完成"） | **addDependency 任意 DAG** |
| 取消 | 很弱（once 不好撤） | **cancel 可贯穿执行中**（配合 isCancelled 检查） |
| 状态观察 | 无 | **KVO isFinished/isExecuting/isCancelled** |
| 并发数控制 | 信号量绕 | **maxConcurrentOperationCount 直给** |
| 挂起恢复 | 暂停队列（粗） | **setSuspended（队列级）** |
| 上手成本 | 低（一行） | 高（要懂对象模型） |

**依赖的正确用法**（深水区一）：

```objc
[opB addDependency:opA];        // B 等 A —— 路径是"被依赖 → 依赖"
[queue addOperation:opA]; [queue addOperation:opB];   // 添加顺序无关，依赖说了算
```

**三个坑**：① **依赖与队列无关**（跨队列的依赖也成立，甚至可以依赖别的队列的 op）；② **cancel 不会打断执行中的任务**——**任务内部要自觉检查 isCancelled 早退**（协作式取消）；③ **op 之间别互相依赖成环**（死等，队列卡死）。

**深水区二：自定义 Operation 要重写什么**——非并发场景只需 **main**（任务体）；**并发场景要自己驱动 KVO**：重写 start（不放队列也跑）、**手动发 isExecuting/isFinished 的 KVO**（否则队列以为任务永不结束，后面全堵）——**"状态机 + KVO 通知"是自定义 op 的全部难点**，能讲清这个就到源码级了。

收尾：心法，「**GCD 管调度、Operation 管生命周期——简单并发 GCD、复杂任务图 Operation**」。

> 面试官追问点：AFNetworking 为什么基于 NSOperation？应答思路：**网络请求天然要"取消 + 状态观察 + 依赖重试"**——离开页面取消请求（GCD 做不到优雅取消）、KVO 刷新 UI 状态——**生命周期管理密度高的场景就是 Operation 的主场**。

#### 5.5 怎么实现线程安全的数组？atomic为什么不够

答：一句话定调，**线程安全容器的三套方案：串行队列（读写都排队）、栅栏队列（读并行写独占）、锁包裹（读写都加锁）——atomic 只保单次存取原子，连"读改写"都保不了**。

**方案一：串行队列（最简单）**——**所有读写都 sync/async 到同一条串行队列**——队列天然串行化 = 天然的锁；**代价**：读多场景浪费（读和读也互斥）。

**方案二：并发队列 + 栅栏（读多写少首选，5.2 的应用）**：

```objc
- (id)objectAtIndex:(NSUInteger)i {
    __block id obj;
    dispatch_sync(concurrentQueue, ^{ obj = array[i]; });       // 读：并行
    return obj;
}
- (void)addObject:(id)obj {
    dispatch_barrier_async(concurrentQueue, ^{ [array addObject:obj]; });  // 写：独占
}
```

**方案三：锁包裹**——pthread_mutex / os_unfair_lock 包住每个方法——**同步返回值方便（不用 sync 等待）**，但要小心**复合操作的原子性**。

**深水区一：atomic 为什么不够**（本题题眼）——`@property (atomic) NSMutableArray *arr` 只保证 **"arr 这个指针的读写"原子**——① **数组内部操作完全不设防**：两个线程同时 addObject（都是对数组本体的消息）——内部状态竞争；② **读改写不原子**：`self.arr = [self.arr arrayByAddingObject:x]` 中间有窗口；③ **遍历期间被改**：for-in 到一半别的线程 removeAll —— 崩溃——**"属性原子 ≠ 容器线程安全"**，一句话定音。

**深水区二：复合操作的外部一致性**——**"线程安全的容器"保不了"业务操作的原子性"**：`if (![arr containsObject:x]) [arr addObject:x]` 两步各自安全，中间照样能插队——**要么加"外部锁"包住整个业务块，要么把检查+写入做成一个队列任务**——**粒度永远由业务语义决定，容器只负责自己那一层**。

收尾：心法，「**队列即锁、读写分治用栅栏、复合操作要业务级加锁**——线程安全的本质是"粒度对齐"」。

> 面试官追问点：读多写少为什么倾向栅栏而不是读写锁？应答思路：**栅栏方案里读是"队列调度"（无锁、可并行、还能 async）**，读写锁读也要拿读锁（原子操作开销）；**且队列方案能和 GCD 生态组合**（group/barrier/优先级）——工程性优于裸锁。

# 13.深度精讲（Runtime与内存机制口述版）

> 说明：本章是核心题的口述版深度精讲，讲到 Runtime 源码（objc4）与运行机制层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

#### 13.1 weak怎么自动置nil？SideTable怎么存

答：一句话定调，**weak 的自动置 nil 靠「SideTable 的 weak_table 哈希表」：对象 dealloc 时 clearDeallocating 遍历它的弱引用条目，把所有 weak 指针置 nil**。

**三层结构自顶向下**：全局有个 **SideTables（64/128 个 SideTable 的哈希表，按对象地址哈希分片，锁粒度就是分片）**；每个 SideTable 三件套（**自旋锁、引用计数表 refcount_map、弱引用表 weak_table**）；weak_table 里是 **weak_entry_t**——**一个对象一条 entry，记录「指向我的所有 weak 变量的地址」**。

**登记流程**：声明 `__weak typeof(obj) weakObj = obj` 时，编译器插入 **objc_initWeak → weak_register_no_lock**：**按 obj 地址哈希定位 SideTable，把 weakObj 这个「指针变量的地址」追加进该对象的 weak_entry**（哈希结构里找不到 entry 就新建，条目多到 4 的倍数时扩容为哈希桶）。**注意存的是「weak 变量的地址」而不是值**——这样后面才有地方反向写 nil。

**置 nil 的流程**：对象引用计数归零 → **dealloc → clearDeallocating**：取出该对象的 weak_entry，**遍历其中每个 weak 变量地址，把指到的内存统一写 nil**，然后从表里摘除 entry。**所以「自动置 nil」不是魔法，是 dealloc 路径上的一次定向清扫**——这也解释了为什么 **weak 变量在 nil 之后访问是安全的（发送消息给 nil 返回 0 值）**。

**深水区一：为什么要 SideTables 分片**——**全表一把锁的话，任何对象的 weak 操作都串行全世界**；按对象地址分到 64+ 个桶，**不同对象的 weak 登记和清除天然并行**——和分库分表一个思想，objc4 源码里还用**字节翻转哈希（地址高位取模）**让相邻对象（栈上连续分配）也能打散。

**深水区二：weak 的读写开销**——**每次访问 weak 变量都走 objc_loadWeakRetained（查表加 retain 再 autorelease 的保护链）**，比 strong 访问贵一个量级：**所以「在循环里反复读 self->weakSelf」是性能反模式**，标准姿势是循环外 `__strong typeof(weakSelf) strongSelf = weakSelf` 提一次（**weak-strong dance 的真正动机，不只是防循环引用**）。

收尾：weak 机制一句话，「**登记时记住变量地址，死亡时挨家挨户写 nil**」，SideTables 的分片和 weak-strong 的提频，是「知道机制后才能推导出的工程姿势」。

> 面试官追问点：Tagged Pointer 的对象为什么不能有 weak？应答思路：Tagged Pointer（13.1 之外的优化）的值直接编码在指针里、**没有堆对象也没有 dealloc 流程**，weak 表无从挂载——系统直接在 weak_register 里断言拦截，这是「优化对象绕开引用计数体系」的边界。

#### 13.2 msgSend的缓存怎么设计？为什么用汇编

答：一句话定调，**objc_msgSend 是「汇编写的缓存查找状态机」：先查缓存（哈希探测）命中就尾调用 IMP，不命中走 C 的 method_lookup，全程拒绝递归重入靠可恢复的寄存器现场**。

**为什么用汇编**（深水区一）：**调用频率冠绝全系统（每行 OC 消息调用都过它）**，汇编能做三件 C 做不了的：**尾调用（tail call）直接 jmp 到 IMP（不增加调用栈）**、**按调用约定精确保存可恢复寄存器（不会重入时破坏现场）**、**哈希探测的无开销循环**。objc4 源码里 objc-msg-arm64.s 就是这个文件。

**快速查找的三步**（按 objc_msgSend 汇编的主干走）：

1. **nil 检查 + Tagged Pointer 检查**（对象为 nil 直接返回 0，消息发给 nil 的安全语义在这实现）；
2. **取缓存**：LCacheMiss 之前先 **从 isa 指针取 class（ARM64 上 isa 是 nonpointer，要按位掩码取出 class 地址）→ 取 cache_t → 哈希计算**（**cache 哈希用 sel 与 mask 按 `sel & mask`，**比较 bucket 里的 sel，命中取 imp 尾调用**）；未命中**沿 bucket 链环形向前探测**（cache 是**开放定址的哈希表**，不满四分之三）；
3. **miss 走慢路径**：`__objc_msgSend_uncached → lookUpImpOrForward`（C 函数），**持有 cache 读写锁、methodLists 链表线性找（method list 现在是排序的，可二分）→ 找到写回缓存**；找不到进转发决议（三大阶段）。

**深水区二：cache 的并发设计**——**读多写少的「脏读安全」结构**：bucket 数组扩容时**新建表填好再原子替换指针**（读者要么看旧表要么看新表，都自洽）；**写入用字节级原子操作保证「先写 imp 再写 sel」的顺序**（**读侧看到 sel 非空就意味着 imp 已就绪**——一个无锁读的顺序设计）；实在竞争激烈才等写锁。**缓存扩容是「丢弃式」的**：翻倍时**旧缓存直接扔掉重新热身**（不搬移），摊销成本更简单。

**缓存的分层**：**class 的 cache 在 class 结构里， superclass 的缓存各自独立**——子类查不到会沿继承链往上，**每层的 cache 都会热各自的方法**（ superclass 的热点方法在 superclass 自己的缓存里命中，不污染子类缓存）。

收尾：objc_msgSend 的设计哲学是「**把 99% 的命中路径做到一条 jmp 的成本，miss 的成本再高都值得**」——缓存查找的汇编化、无锁读、扩容丢弃三个决策全部服务这个目标。

> 面试官追问点：为什么 method 查找慢路径还要做「二分」？应答思路：新版 runtime 的 method list 是「按 selector 排序的相对偏移列表」（list 内容不可变，相对地址编码省一半内存），排序结构让线性查找升级为二分——**「结构不可变」换来「查找可优化」**，和数据库索引一个思想。

#### 13.3 Runloop怎么转起来的？六个应用挂哪里

答：一句话定调，**Runloop 是「线程的事件循环」：休眠靠内核（mach_msg），唤醒靠端口消息，每个 Mode 有独立的 source/observer/timer 集合，Mode 切换就是「换一套事件集」**。

**结构三件套**：**CFRunLoop（每线程懒创建，字典存储）→ 多个 CFRunLoopMode → 每个 Mode 里 sources0/sources1/observers/timers 四个集合**。**一次 runloop 循环只跑一个 Mode**，**切换 Mode 要先退出再重进**（保证集合不被并发修改）——这是 Mode 的隔离语义。

**深水区一：休眠的底层**——**mach_msg 的陷阱调用**：runloop 没事干时**调 mach_msg 陷入内核等待端口消息（内核态挂起，零 CPU）**；唤醒源就是「往这个端口发消息」：**sources1 是内核端口（系统事件如 UI、GCD 唤醒都走它）**、timer 到期（内核 timer 也转成端口消息）、手动唤醒。**「Runloop 挂起线程」和 Go 的 gopark 是同一个思想：把等待交给内核，线程不空转**。

**一次循环的完整序列**（这个顺序背下来值一道题）：

1. 通知 observers：进入（kCFRunLoopEntry）；
2. 通知 observers：即将处理 timers；
3. 通知 observers：即将处理 sources0（**先标记后执行：非内核源的 UI 事件在这轮派发**）；
4. **如果有 sources1（内核端口消息）跳到 9 处理消息**（Source1 是「插队通道」）；
5. 通知 observers：即将休眠（**AutoreleasePool 的 push/pop 就挂在这个时机**——**进入休眠前 pop 排干旧的、push 开新的**，这就是「autorelease 的释放时机由 runloop 驱动」的真相）；
6. **mach_msg 休眠**，等端口消息唤醒；
7. 唤醒（端口消息/timer/GCD 调度唤醒——**GCD 的主队列任务跑在主线程 runloop 的「被 GCD 唤醒」路径**）；
8. 通知 observers：结束休眠；
9. 处理唤醒消息（timer 到期、dispatch 到主队列的 block、source1）；
10. 通知 observers：退出（kCFRunLoopExit），决定是否再来一轮。

**六种应用的机制对照**（每个一句话挂到序列上）：

1. **AutoreleasePool**：挂第 5 步，休眠前排干；
2. **事件响应/手势识别**：source1 的系统事件进队列，source0 分发给 UIApplication 再 responder chain；
3. **NSTimer**：注册进 mode 的 timers，第 3/9 步检查到期（**所以NSTimer 对 mode 敏感：滑动时 tracking mode 的切换让 default mode 的 timer 停摆**——经典 bug 的机制根源）；
4. **CADisplayLink**：和 timer 同类但按 vsync 帧驱动（也是 mode 属性）；
5. **卡顿检测**（深水区二）：**observer 监控「休眠前/唤醒后」的耗时差**——**BeforeWaiting 到 AfterWaiting 之间如果超过阈值（如 400ms），说明线程被某个 source/timer 的处理卡住**（在 9 的处理阶段耗时超长），**把这时抓的主线程栈聚合就是卡顿报告**（微信 Matrix 和 12.5 的 Android 方案异曲同工）；
6. **常驻线程**：给子线程的 runloop 加 source（port 或起 run），**否则 runloop 跑完队列立刻退出**，线程即死。

收尾：Runloop 的三句话总结，**「线程的命靠 runloop 吊着（休眠不退出）」「事件的分发靠 mode 隔离（一套集合一个世界）」「一切看起来随机的回调，都能在循环序列里找到自己的工位」**。

> 面试官追问点：主线程的 runloop 谁启动的？应答思路：main 函数末尾 UIApplicationMain 里 CFRunLoopRunInLine 起了 main runloop，**「main 函数 return 后 App 还活着」的错觉就是 runloop 在 main 之外永续循环**——理解这一点就理解了「iOS App 的本质是事件循环驱动」。

#### 13.4 Block的类型怎么判定？栈块怎么搬上堆

答：一句话定调，**Block 的类型由「捕获了什么」决定：没捕获是 Global、捕获了变量且未被拷到堆是 Stack、_Block_copy 之后是 Malloc——三种类型的内存属性不同，ARC 的栈到堆升级是编译器自动做的**。

**三种类型的判定**：

1. **GlobalBlock**：**不捕获任何外部变量**（只用自己的参数或全局量）——**没有状态可保护，放数据段和函数一样**，copy 是空操作；
2. **StackBlock**：捕获了变量、且还活在栈上（MRC 时代裸声明）——**离开作用域即销毁**；
3. **MallocBlock**：StackBlock 被 copy 后的形态——**捕获的状态（__block 变量、引用的对象）整体搬到堆上，生命周期自管理**。

**ARC 下的真实形态**（深水区一）：**ARC 会把「作为返回值/赋给 strong 变量/当参数传」的栈 Block 自动 copy 成堆 Block**——所以日常写的 block 几乎都是 MallocBlock，**StackBlock 只在「strong 之外的形式持有」（如手动取地址、裸结构体）才露面**。**经典验证题**：`void (^blk)(void) = ^{...}` 打印是 Malloc（ARC 自动 copy），但 `^{...}` 直接 isKindOfClass 检查时是 Stack——**「栈块出现在右值，堆块出现在被持有后」**。

**Block 的结构体真相**：Block 是 `__block_impl + 捕获变量列表` 的结构体（**isa 指向 _NSConcreteMallocBlock 等类对象**，**desc 记录大小和 copy/dispose 帮助函数**）；**捕获 OC 对象时**，结构体里持有的是 `void *` 加 **flags 里的 BLOCK_FIELD_IS_OBJECT 标记**——copy 时对它调 objc_retain（这就是「Block 持有对象」的 ARC 实现）。

**深水区二：__block 的实现**——被 __block 修饰的变量**不是被捕获值，而是「包成 byref 结构体的引用」**：`__Block_byref_x_0 { isa; flags; x; forwarding; }`，**栈上的 Block 捕获的是这个结构体的指针**；**copy 到堆时 byref 结构体也搬到堆，且栈版本的 forwarding 指针改指堆版本**——**读 x 永远走 forwarding，栈块和堆块读写的是同一个 x**（这就是「__block 让 Block 内外共享变量」的机制）。**ARC 下 __block 修饰 OC 对象还会让 byref 结构体持有它**（MRC 时代不会——历史差异是老题）。

**循环引用的精确链路**：self 强持有 block（属性 copy），**block 结构体捕获了 self（retain）**——环成立；**weak-strong dance 的正确姿势**：`__weak typeof(self) ws = self; ^{ __strong typeof(ws) s = ws; ... }`——**weak 断环（block 不强持 self），strong 在「block 执行期间」临时持有防止执行到一半 self 释放**（不是「保证不强引用」而是「保证执行期安全」）。

收尾：Block 的心智模型一句话，「**结构体 + 捕获列表 + copy 时升级**」——类型三态是「捕获有无」和「copy 有无」的矩阵，__block 的 forwarding 是「栈堆同体」的桥梁。

> 面试官追问点：为什么 block 属性要用 copy 修饰？应答思路：MRC 时代要显式 copy 把栈块搬堆（不然属性持有一个栈块，作用域外悬空）；ARC 下 strong 也会自动 copy 效果等价——**写 copy 是「历史正确的肌肉记忆」，语义上表达「这个属性要堆块」的意图**。

#### 13.5 KVO怎么偷换isa的？动态子类做了什么

答：一句话定调，**KVO 的实现在「偷换 isa」：注册观察时运行时动态造一个 NSKVONotifying_子类、把对象的 isa 指过去，重写的 setter 在「旧值新值」之间通知观察者**。

**注册时发生了什么**（setValue:forKeyPath 观察触发后）：

1. runtime 动态创建 **NSKVONotifying_原类名** 子类（**每个类只造一次，复用**）；
2. **重写被观察属性的 setter**：`willChangeValueForKey → 原实现（真的改值）→ didChangeValueForKey`（didChange 里**遍历观察者列表调 observeValueForKeyPath**）；顺带重写 **-class（骗过 introspection 返回原类，让人看不出 isa 被换了）**、-dealloc、_isKVOA；
3. **object_setClass 把对象的 isa 换到新子类**——此后这个对象的消息（setter）全部走重写版。

**深水区一：验证与绕过**——`object_getClass(obj)`（绕过 -class 的伪装）能看到 NSKVONotifying_ 前缀；**直接改成员变量（_xxx = v）不走 setter 所以 KVO 不触发**——「手动触发 KVO」的姿势：**自己调 willChange/didChange 对**（把「通知义务」从 setter 里手动接管）；**用 KVC（setValue:forKey:）会触发**（KVC 内部调了 will/did 的协议）。** isa 换类但不换内存**——**对象还是原对象，只是行为被「贴了层皮」**。

**深水区二：KVO 的三个坑与根因**：

1. **观察者和被观察者谁先释放**：**观察者 dealloc 但没 removeObserver**——被观察者下一次通知时向尸体发消息，**野指针崩溃（ClassicNSException: message sent to deallocated）**；**removeObserver 的本质是把观察者从重写 setter 的观察者表里摘掉**，没摘就是悬空条目；
2. **父类也 KVO 的问题**：子类和父类都观察同一属性（各自注册）——**重写链上多次 will/did 的顺序**（子类 setter 调 super，通知会嵌套发出），**automaticallyNotifiesObserversForKey 返回 NO 可以接管自动通知**（精细控制的官方入口）；
3. **属性是 struct/非对象类型**：KVO 支持（包 NSValue），但**依赖 setter 的 keyPath 精确性**，手滑写错路径**注册时不报错、运行时静默不触发**（observe 注册是惰性校验的）——**这是「KVO 是字符串约定松散 API」的根源性吐槽**，也解释了现代代码用 Facebook 的 KVOController 或 Combine/闭包替代。

**手写简化 KVO 的思路**（面试常考白板）：**isa 替换（object_setClass）+ 动态子类（objc_allocateClassPair 加 setter 的 method swizzling）+ 观察者表（NSMapTable 弱键）+ will/did 钩子**——**本质是「method swizzling 的对象级特化」**（swizzling 换全类的方法，KVO 只换这一个对象的 isa）。

收尾：KVO 的机制一句话，「**isa 是行为的开关，换 isa 等于换人格但保留内存**」；三个坑全部源于「字符串约定的松散」和「观察者表的生命周期」，**理解坑的根因比背坑的表象更能拿分**。

> 面试官追问点：KVO 和重写 setter 手动发通知有什么区别？应答思路：KVO 是「运行时无侵入」（不改原类代码、按对象粒度生效）；重写 setter 是「编译期侵入」（改类就影响所有实例、要发版）——**运行时的灵活 vs 编译期的明确**，工程上 KVO 省事但排错难，这也是声明式框架（Combine/RxSwift）最终替代它的原因。

#### 13.6 AutoreleasePool怎么实现？何时排干

答：一句话定调，**autoreleasepool 是「双向链表串起来的 4096 字节 Page 栈」，push 压哨兵、pop 到哨兵之间全 release，Runloop 驱动它周期性排干**。

**结构三级**：**AutoreleasePoolPage（C++ 结构，4096 字节一页，双向链表串父与子）**——**page 里就是个栈（从高地址往低压对象指针）**；**POOL_SENTINEL（哨兵，一个空对象地址）标记一次 push 的边界**；hotPage 是「当前活跃的最后一页」。

**push 和 pop 的语义**：`autoreleasepool {}` 编译成 `objc_autoreleasePoolPush`（**压一个哨兵）** 和 `objc_autoreleasePoolPop(哨兵)`——**pop 时从栈顶往下逐个调 release，直到碰到自己的哨兵为止**——**「push/pop 严格配对 + 嵌套按哨兵切段」**，嵌套的 pool 就像函数调用栈一样各管各段。

**对象怎么进池子**：**autorelease 调用时对象指针压入 hotPage**（页满 56 个就开新页挂链表）——**注意不是拷贝对象，只存指针**（8 字节成本）。

**深水区一：Runloop 的排干时机**——**主线程的 Runloop 每次进入休眠前（BeforeWaiting）和退出时，对最近的 pool 执行 drain（pop 到最外层哨兵再重新 push）**（和 13.3 的循环序列挂钩）——所以「autorelease 对象的释放时机」= **「本轮 runloop 即将休眠时」**：一次点击事件的所有 autorelease 对象，活到这轮消息处理完的最后一刻。**推论**：**大循环里狂建 autorelease 对象（比如 for 里读图片），要等循环结束才释放**（峰值内存爆表）——**在循环体内显式包 autoreleasepool 是标准解法**（每圈一个哨兵，每圈排干）。

**深水区二：objc_autoreleasePoolPrint 的调试法** 与 **Tagged Pointer 的豁免**——**objc_autoreleaseReturnValue 的优化**：**方法返回 autorelease 对象时，先调这个函数：如果调用方紧接着 objc_retainAutoreleasedReturnValue（编译器插桩配对），TLS 存标记 + 返回裸指针，双方省掉一次入池和一次池取**——**「调用约定层的快速通道」**（pair 化的 autorelease 消除），能讲出这个优化是深水区。

收尾：autorelease 答题的心法，「**Page 是链表化的栈、哨兵切段配对、Runloop 睡前排干、循环防爆要手动包池**」，最后一条是实战必考。

> 面试官追问点：子线程的 autorelease 谁来排干？应答思路：子线程默认没有 runloop 转着，**线程退出时 TLS 里挂着的一个 autoreleasepool 会被清**；但长期活着的子线程不退出，autorelease 对象就攒着——**「子线程大量建 autorelease 对象要自己包 pool」**是这个机制的直接推论。

#### 13.7 Category怎么加载？两个钩子时机差在哪

答：一句话定调，**Category 的方法在运行时「附加」到类（不替换原实现，是插到方法列表前面），+load 在 main 之前按编译顺序全量调用，+initialize 首次消息时懒触发**。

**加载时机与顺序**（深水区一）：**dyld 映射 image 后，runtime 的 map_images/read_images 把 Category 的方法列表**attachClass **合并进宿主类的 class_ro_t → class_rw_t**——**合并的位置在原方法列表之前**（Category 方法排前面）——**「同名方法的覆盖」其实是「查找时先找到」**：**原实现还在列表后面，method swizzling 时可以 class_getImplemention 拿到被「遮住」的原实现**（这就是 method_exchange 的技术基础）。**多个 Category 同名方法**：**后编译的排更前（最后编译的赢）**——**「覆盖顺序由编译顺序决定」是未定义行为的官方说明**（Build Phases 的文件顺序就是答案）。

**+load 的机制**：**read_images 时直接遍历调用（不走 objc_msgSend，直接函数指针调用）**——所以：**父类 load 先于子类、类 load 先于 Category 的 load、不覆盖（各自全调一遍）**、**main 函数之前执行**（冷启动黑魔法的窗口期，鱼竿代码/FMDB 老版本都在这 hook）；**代价**：**拖慢启动（每个类的 load 串行跑）**，新工程用 +initialize 替代的趋势。

**+initialize 的机制**（深水区二）：**第一次给类（或子类）发消息时，runtime 的 class_initialize 检查「没初始化过」就调**——**走 objc_msgSend（有 runtime 完整机制）**：所以是**懒加载**（没用到的类永不调）、**父类的 initialize 先触发**（子类第一次收消息，先保证父类初始化）、**子类不实现 initialize 会调到父类的（消息机制的自然结果，经典坑：父类 initialize 被调多次，要 dispatch_once 或 判断 self==类名）**。**线程安全**：**runtime 持初始化锁调用，一个线程 initialize 时其它线程发消息会等待**——「initialize 里做重活会卡并发首调用」。

收尾：Category 答题的心法，「**附加不替换（列表前面加条目）、load 在 main 前全量直调、initialize 懒触发走消息机制**」，配对记忆：「**load 讲纪律（全调有序）、initialize 讲懒惰（首次才动）**」。

> 面试官追问点：Category 能加属性吗？应答思路：能加「属性声明」（property 语法）但**编译器不合成 ivar 和访问器**（类结构在编译期已定死，运行时补不了成员变量）——**关联对象是运行时的替补方案**（objc_setAssociatedObject 存在全局的 AssociationsManager 哈希表里，和类结构无关）。

#### 13.8 ARC的插桩原理是什么？四种所有权语义

答：一句话定调，**ARC 是「编译器插桩的引用计数管理」：Clang 在编译期插入 retain/release/autorelease 调用，__strong/__weak/__unsafe_unretained/__autoreleasing 是四种所有权约定**。

**四种修饰符的精确语义**：

1. **__strong（默认）**：赋值时 retain、离开作用域 release——**「我拥有它」**；
2. **__weak**：赋值不 retain，**对象 dealloc 时自动置 nil**（13.1 的机制）——「我观察它，它死我置空」；
3. **__unsafe_unretained**：不 retain 也不置 nil——**悬空风险自负**（兼容旧 API、性能敏感场景，ARC 的「裸引用逃生门」）；
4. **__autoreleasing**：**赋值时 autorelease 进池**——主要场景是 **传 NSError** 的二级指针（`NSError **error` 的实际类型是 `NSError * __autoreleasing *`，**临时变量自动包 autorelease 保证出函数后还活着**）。

**深水区一：编译器到底插了什么**——`id obj = [[NSObject alloc] init];` 在 ARC 下其实**一个 retain/release 都不多插**（**alloc/new/copy/mutableCopy 开头的方法返回「持有引用」， Caller 直接拥有——方法族约定的优化**）；**`obj = someMethod()`（普通方法）才插 objc_retainAutoreleaseReturnValue 的配对链**——**「方法名族的隐式所有权约定」**是 ARC 优化的基石（非 alloc 系返回的是 autorelease 对象，编译器用 13.6 讲的 TLS 快速通道消除池开销）。

**深水区二：ARC 与 Core Foundation 的边界**——**ARC 只管 ObjC 对象，CF 对象（CGImageRef 等）不归它管**：**桥接三兄弟**——`__bridge`（**只换类型不动引用计数**，危险：桥出去后 CF 侧没人管）、`__bridge_retained`（**桥的同时 retain，CF 侧负责 release**）、`__bridge_transfer`（**桥的同时把所有权移交 ARC**，ARC 接管 release）——**「谁持有谁释放」的条约在边界上要人脑执行**，图片/字符串的 CF 桥接泄漏是重灾区。

收尾：ARC 答题的心法，「**本质是编译期插桩不是运行时 GC、四种修饰符是所有权契约、方法族约定藏着优化、CF 边界要桥接**」，能分清「编译器插桩」和「GC」是第一道分水岭。

> 面试官追问点：ARC 下还会循环引用吗？应答思路：会，ARC 自动管理「计数的加减」不管「引用图的结构」——block 捕获 self、delegate 双向持有这些「结构问题」编译器无能为力，weak/unowned 是留给开发者的人工干预点。

#### 13.9 离屏渲染的触发机制？三大代价怎么治理

答：一句话定调，**离屏渲染是「GPU 先在离屏缓冲区画好、再作为纹理合成上屏」的绕路：圆角/阴影/蒙版触发它，代价是显存切换和带宽翻倍**。

**为什么圆角必须绕路**（讲机理不是背清单）：**普通渲染是「遍历图层树逐层直接写 framebuffer」**（GPU 按画家算法从后往前，一遍完事）；**圆角的裁剪需要「图层内容 + mask 一起算」**——**图层的显示内容和它的形状 mask 在两个 pass 里没法一次合成**，GPU 必须**先把图层内容画进离屏缓冲（offscreen buffer），再把 mask 应用上去，最后把结果当纹理交给合成器**——**多了一次「画进缓冲 + 从缓冲读出」的往返**。

**触发的经典清单与原因**：**cornerRadius + masksToBounds 同开**（单独 cornerRadius 只影响背景色不裁内容，不触发）、**阴影（shadowPath 未设时，要遍历子层算形状）**、**mask（CAGradientLayer 蒙版）**、**group opacity（子层半透明要合起来算）**、**shouldRasterize（主动开启离屏缓存）**。

**深水区一：离屏的三大代价**——**显存开销**（每个离屏上下文一块完整缓冲）、**上下文切换**（GPU 在 framebuffer 和离屏 buffer 间切换状态，昂贵）、**合成次数翻倍**（一次变两次）——**列表里十几个圆角头像同时滚动，GPU 时间轴被离屏 pass 塞满，掉帧**。**Instruments 的 Core Animation 的 Color Offscreen-Rendered 选项**（黄色高亮离屏区域）是定位工具。

**深水区二：正确的优化姿势对照**——**圆角**：**预渲染成圆角图片（CPU 的 CoreGraphics 裁剪，运行时零成本）**或 **CAShapeLayer + 遮罩路径（仍离屏但形状简单）** 或 iOS 13+ 的 **layer.cornerRadius 优化路径（某些场景自动处理）**；**阴影**：**shadowPath 显式指定（免遍历子层，直接用路径——最大的免费午餐）**；**shouldRasterize 的辩证**：**「主动离屏 + 缓存复用」**（复杂静态内容光栅化一次反复用，rasterizationScale 记得设屏幕倍数）——**「内容不变才缓存」**，动画里开它反而每帧重画。

收尾：离屏答题的心法，「**触发讲机理（两个 pass 才能合成的都要离屏）、代价讲三项（显存/切换/合成翻倍）、优化讲对照（预渲染/shadowPath/有条件光栅化）**」。

> 面试官追问点：CPU 的圆角裁剪（预渲染）和 GPU 离屏谁好？应答思路：看场景——静态头像用 CPU 预渲染一次（运行时零成本）最赚；**频繁变化的内容 CPU 每次重裁就亏了（CPU 挤占主线程）**——「一次性成本换运行时零成本」的买卖只对不变内容成立。

#### 13.10 dyld启动四幕怎么走？二进制重排是什么

答：一句话定调，**iOS 的启动是「dyld 加载镜像 → rebase/bind → runtime 初始化 → +load → main」四幕剧，启动优化的深水区武器是二进制重排（把启动页调到前面的缺页中断阶段省时间）**。

**四幕剧的顺序**（深水区一）：

1. **dyld 加载**：**加载主二进制依赖的动态库（递归）**，**mach-o 里 LC_LOAD_DYLIB 命令决定清单**——**动态库越多加载越慢**（「合并动态库」优化的依据）；**iOS 的 dyld 3 起 Craig 主二进制的启动闭包（加载和符号信息预先算好缓存）**，二次启动跳过大部分解析；
2. **rebase（基址修正）与 bind（符号绑定）**：**ASLR 让镜像地址随机**——**rebase 修「镜像内部指针」（对已知偏移加减 slide）**、**bind 修「跨镜像引用」（把 printf 这类外部符号查表填真实地址）**——**fishhook 的原理就是利用 bind 的惰性（延迟绑定，首次调用时才填）事后改函数指针**（和 09 篇 hook 系列呼应）；
3. **runtime 初始化**：**map_images/read_images（类注册、Category attach——13.7 的时机在这）**；
4. **+load → main**：全量 +load 串行执行，然后 main。

**深水区二：二进制重排（Page In 优化）**——**缺页中断是隐藏成本**：**代码首次执行时要按 16KB 一页从磁盘读进内存**（冷启动的 IO 大头之一），**Mach-O 里函数的排列顺序（链接器默认按编译单元）决定「启动路径上的函数是否集中在一页里」**——散落的话启动要多触发几十上百次缺页。**重排的原理**：**用 clang 的 SanitizerCoverage 给启动路径打点（每个函数插入 hook）→ 真机跑一次启动收集「实际执行顺序」→ 生成 order file → 链接器按这个顺序排函数（-order_file）**——**启动函数挤进少数几页，缺页次数砍半**（微信的实践数据是主进程冷启动提升 15%+ 级别）。

**优化全景的挂点对照**（把四幕剧当靶子）：**动态库合并/删除（第 1 幕）、+load 瘦身改 +initialize（第 4 幕）、二进制重排（贯穿的缺页）、fishhook 别滥用（第 2 幕的 bind 后）**——**「先测（Instruments 的 App Launch + os_signpost）再切」是优化的纪律**。

收尾：启动题的心法，「**四幕剧（dyld/rebase-bind/runtime/ load-main）是地图、缺页中断是暗礁、二进制重排是按航行日志重排舱位**」，能讲出 order file 的采集流程就是深水区。

> 面试官追问点：rebase 为什么比 bind 快？应答思路：rebase 只需「本镜像的 slide 加减」（不查任何表，纯算术）；bind 要拿符号名查「全局符号表」（跨镜像搜索，dyld 的 lazy binding 还要每次触发）——**「内部修正算术便宜、外部解析查表贵」**，这也是懒绑定存在的原因（用到才查）。
