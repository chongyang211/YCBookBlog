# 1.语言基础

### 1.1 类型与运算

#### 1.1.1 JS的数据类型有哪些？类型判断的几种方式怎么选

答：一句话定调，**八种类型分两族：七种原始类型不可变、按值访问；一种引用类型存堆上、按引用访问。判断方式按目标选：typeof 判原始、instanceof 判血缘、Object.prototype.toString 判真相**。

**两族类型的本质差异**（先立骨架）：原始类型共七种——number、string、boolean、undefined、null、Symbol、BigInt，**不可变**是关键性质：没法「修改」一个字符串，`s.toUpperCase()` 返回的是新字符串，所有「看起来在改」的操作都产生新值。引用类型只有 object 一族（Array、Function、Date、RegExp 都是对象），变量里存的是堆地址，**赋值和传参复制的是引用**——`b = a; b.x = 1` 会影响 a，这一句就是后面所有浅拷贝深拷贝问题的源头（见 1.2.9）。

**三种判断方式，各有辖区**：

```js
typeof 123                          // 'number'         原始类型除 null 全准确，还能识别 function
typeof []                           // 'object'         对象一律 'object'，判不了数组
[] instanceof Array                 // true             沿原型链找 Array.prototype，判引用类型的血缘
Object.prototype.toString.call([])  // '[object Array]' 内部读 Symbol.toStringTag，全类型通吃
Array.isArray([])                   // true             专为跨窗口数组设计的可靠判定
```

**选型结论**（面试要给到这一层）：判原始类型用 typeof（function 是它的特例——实现了 [[Call]] 内部方法的对象返回 'function'）；**判数组必须 Array.isArray**——instanceof 在 iframe / 跨窗口场景会失手，因为每个 realm 有自己的 Array 构造器，跨过来的数组原型链不指向本窗口的 Array.prototype；判 null 用 `x === null`（typeof 会被历史 bug 骗）；要全类型精准判断用 `Object.prototype.toString.call()`。

**深水区一：typeof 的两个历史彩蛋**。`typeof null === 'object'` 是初版 JS 的低位标签 bug——null 的全零指针撞上了对象的 000 标签，修复提案因兼容性被否，**bug 进了规范，就成了特性**；更冷的一个：`typeof document.all === 'undefined'`——规范为了兼容依赖此判断的老网站「故意说谎」，把一个真实存在的对象判成 undefined，是 JS 唯一的 willful violation（明知故犯条款）。

**深水区二：toString 也能被伪装**。`Object.prototype.toString` 读的是对象内部可自定义的 Symbol.toStringTag：

```js
const fake = { [Symbol.toStringTag]: 'Array' };
Object.prototype.toString.call(fake);  // '[object Array]' —— 说谎成功
```

所以不存在 100% 防伪的判断，只有「约定场景下最可靠」的选择。

收尾：答题顺序建议——两族差异立骨架、三种方式给辖区、落一条工程结论（数组用 Array.isArray），typeof null 的彩蛋当加分项收尾。

> 面试官追问点：为什么 typeof 未声明变量不报错？应答思路：typeof 对「未声明」和「声明未赋值」统一返回 'undefined'，是规范刻意设计的安全检查特性，`typeof x !== 'undefined'` 曾是探测全局变量是否存在的标准写法；模块化时代这个用途退场，改用 `in` 运算符与静态 import 探测。

#### 1.1.2 宽松相等与严格相等差在哪？隐式类型转换怎么发生

答：一句话定调，**=== 类型不同直接 false、不做任何转换；== 会先做隐式转换再比较，核心链路是「布尔先降级成数字、字符串遇数字转数字、对象走 ToPrimitive」——工程上默认 ===，唯一值得保留的宽松写法是 `x == null`**。

**=== 的两条规则**：类型相同比「值」（Number 按 IEEE 754 位级比较，所以 NaN !== NaN、+0 === -0 都是位级事实）；类型不同直接 false。**「不做转换」正是 === 被推崇的全部理由：结果可预测**。

**== 的简化判定流程**（完整规范版见 7.9）：

1. **布尔先降级**：`x == true` 实际是 `x == 1`——`'2' == true` 为 false 而 `'2' == 2` 为 true，**同一个值和 true 不等、和 2 相等**，说明「和 true 比」是个自欺的写法，条件判断里写 `x == true` 永远不如直接写 `x` 或 `x == 1`；
2. **字符串遇数字**：字符串转数字（`Number('')` 是 0，这是空数组等于 false 的中转站）；
3. **对象遇原始值**：对象走 ToPrimitive（valueOf → toString），`[1] == 1` 为 true 的来源；
4. **null 与 undefined 是孤岛**：只和对方相等，和 0、''、false 一律 false——它们不进转换链，这一条直接终结 `null == 0` 的争论。

**null 与 undefined 的语义分工**：undefined 是「系统说没有」——未赋值、缺参数、访问不存在的属性，语言自己产生的默认值；null 是「程序员说没有」——主动置空、占位、断开引用。**工程纪律：用 null 表达「此刻故意为空」，把 undefined 留给「非本意」**，两者混用会掩盖真正的 bug。冷知识：undefined 不是保留字（老代码能 `var undefined = 1` 覆盖它，`void 0` 是免疫写法），null 是保留字却背着 typeof 的历史冤案——两人的委屈方向正好相反。

**NaN 的判断只用 Number.isNaN**：全局 `isNaN('abc')` 为 true——它先把参数转数字，字符串被误杀；`Number.isNaN` 不转换、只对「值确实为 NaN 的 number」返回 true；零依赖的写法是 `x !== x`（利用 NaN 不自等，连 API 都不需要）。

收尾：== 的规则表不值得背全，**记住工程结论「禁用 ==、唯一例外 x == null 同时挡住 null 和 undefined」**，再能推演 [] == false（完整五步链见 7.9）就到位了。

> 面试官追问点：[] == ![] 为什么是 true？应答思路：![] 先求值——数组是对象恒为真值，取反得 false；false 降级成 0；[] 走 ToPrimitive 得 ''，'' 转数字得 0；0 == 0。「if([]) 为真、![] 为 false、[] == false 又相等」三条通路规则不同，是隐式转换的集大成题，也是「显式优于隐式」这条最佳实践的最佳论据。

#### 1.1.3 0.1加0.2为何不等于0.3？浮点数精度丢失怎么解决

答：一句话定调，**JS 的 number 是 IEEE 754 双精度浮点，二进制只能精确表示「分母为 2 的幂」的小数，0.1 和 0.2 在二进制下是无限循环小数，存储时必然截断——精度丢失发生在「存」的那一刻，不是「算」的时候**。

**存储原理一段讲透**：双精度 64 位 = 1 位符号 + 11 位指数 + 52 位尾数。十进制小数转二进制是「乘 2 取整」，0.1 转出 0.0001100110011... 无限循环——因为 0.1 = 1/10 的分母含质因数 5，而二进制只能表达分母为 2 的幂的数（0.5、0.25、0.125 都精确）。尾数只有 52 位，第 53 位起被舍入，**0.1 进内存那一刻就已经是「比 0.1 略大的近似值」**，0.2 同理；两个偏大的近似值相加，误差在进位时暴露，得到 0.30000000000000004。

**大数的安全边界**：尾数 52 位加隐含的 1 位首位共 53 位有效数字，整数安全上限因此是 2^53 - 1（Number.MAX_SAFE_INTEGER）。超过后相邻整数无法区分——**`9007199254740992 === 9007199254740993` 为 true**（后者无法表示，舍入成了前者），两个不同的整数常量竟然全等。工程信号：后端下发的长 ID（雪花算法、订单号）超过 16 位，`JSON.parse` 之后就静默损坏——解法是后端以字符串下发，前端用 BigInt 或字符串比对处理。

**解决方案按四层选**：

1. **显示层**：toFixed / toPrecision，只治「显示难看」；注意 toFixed 返回的是**字符串**，参与后续计算要转回数字；
2. **比较层**：`Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON`——EPSILON 是 1 与最近可表示数之差（2^-52），浮点相等比较的官方答案；
3. **计算层（金融正确姿势）**：**小数转整数**——金额以「分」为单位存整数，`(1099 + 500) / 100` 永远精确；或用 decimal 类库（decimal.js / big.js），原理是「存十进制有效位 + 十进制指数」，从根上绕开二进制转换；
4. **类型层**：BigInt 提供任意精度整数，`9007199254740993n + 1n` 精确，但**不能与 Number 混算**（`1n + 1` 抛 TypeError），不支持小数、JSON.stringify 遇到它直接抛错——它是「大整数方案」不是「小数方案」。

**深水区：为什么打印 0.1 还是 0.1**？存储值明明不是 0.1。因为 toString 用「最短往返表示」算法：找到能还原同一个存储位的最短十进制串，0.1 就是那个最短串。**打印出来的是门面，内存里的近似值才是本体**——能讲清这一问，才算真正理解「存储」与「显示」的分离。

收尾：答题路线——52 位尾数与二进制无限循环、MAX_SAFE_INTEGER 的 53 位由来、四层方案，落到「金融用整数分」这条工程铁律收尾。

> 面试官追问点：JSON.stringify(0.1) 为什么也不丢精度？应答思路：序列化同样走最短往返表示，保证 round-trip（parse 回来还是同一个 double）一致。延伸一问：这个坑是 JS 独有的吗？应答思路：不是——所有用 IEEE 754 双精度的语言（Java 的 double、Python 的 float）全是一样的表现，这是 IEEE 754 的账，不是 JS 的锅；JS 的特殊性只在于它「只有一种数字类型」，没得选。

### 1.2 作用域与原型

#### 1.2.1 作用域体系是怎么运作的？闭包的原理与应用是什么

答：一句话定调，**作用域回答「变量在哪里能被访问」，JS 用词法作用域——范围由代码书写位置在定义时就定死；闭包是词法作用域的自然产物：内层函数引用着外层变量，外层函数返回后这些变量依然活着**。

**三种作用域**：全局作用域、函数作用域（var 的辖区）、块级作用域（let/const 的辖区，ES6 补上的一块）。词法作用域的核心含义：**函数能访问哪些变量看它「定义在哪」，不看它「在哪被调用」**——和 this「跟着调用走」形成全书最经典的对照（见 1.2.4）。

**闭包的定义与两个形成条件**：函数与其词法环境的组合体。条件一，内层函数引用了外层变量；条件二，内层函数被传递到外层作用域之外（返回出去、赋给外部变量、注册成回调）。两个条件缺一不构成有意义的闭包——V8 层面被引用的变量会从栈提升到堆上的 Context，机制展开见 7.2。

**三大经典应用对着场景讲**：

1. **数据私有**（模块模式的地基）：计数器把状态藏进闭包，外界拿到的是「操作权」而不是「变量本身」——不暴露内部状态、只暴露接口，这是 class 出现之前 JS 的标准封装姿势；
2. **函数工厂 / 柯里化**：`makeAdder(5)` 和 `makeAdder(10)` 返回的函数各带各的环境，互不干扰——「参数分批存进层层闭包」，是函数式编程在 JS 落地的机制基础；
3. **回调携带上下文**：防抖节流里的 timer（见 3.2）、事件回调捕获循环变量——本质都是「把状态存进闭包，让回调自带记忆」，没有闭包就没有「带状态的回调」。

**闭包的代价**：被捕获的变量跟着闭包活——闭包活得久（挂到全局、注册了不清理的事件、长存的定时器），它 Context 里的大对象就陪着长命。**泄漏的不是闭包，是「活得比需要更久的闭包」**——判定标准与排查手段见 7.2、7.10。

收尾：答题按「词法作用域 → 闭包定义与条件 → 三个应用 → 内存代价」推进，最后一句收束：**闭包是 JS 封装与函数式两条路的共同地基**。

> 面试官追问点：for 循环配 setTimeout，var 和 let 的输出差异？应答思路：var 六次迭代共享同一个函数作用域变量，异步回调全部打印最终值；let 每次迭代创建独立的块级环境（规范术语 CreatePerIterationEnvironment），六个 i 各归各——答出「每迭代一个新环境」即到位，V8 的 Context 实现细节见 7.2。

#### 1.2.2 变量提升是怎么回事？暂时性死区的底层原理是什么

答：一句话定调，**var 和函数声明在「创建阶段」就被登记进环境、代码执行前即可访问；let/const 同样被登记但「不初始化」，声明语句执行前的访问直接抛 ReferenceError——这段「已登记未初始化」的窗口就是暂时性死区**。

**总纲先立住：提升不是代码被挪动，是「登记先于执行」**。引擎进入一段代码前先做创建阶段——扫一遍声明：函数声明把整个函数对象入册、var 登记为 undefined；然后才进入执行阶段逐行跑。所有提升现象都是这条时序差的推论。

**三种声明的行为对照**：

```js
console.log(a);   // undefined         var 已登记、未赋值
console.log(b);   // ReferenceError    let 处于 TDZ
console.log(fn);  // [Function: fn]   函数声明整体提升
console.log(f2);  // undefined         函数表达式只提升变量名，函数体原地待命

var a = 1;
let b = 2;
function fn() {}
var f2 = function () {};
```

**深水区一：同名声明的合并规则**。函数声明与 var 同名时，**创建阶段函数声明赢**——它连函数体一起入册，var 只是登记名字、不覆盖值；后写的函数声明覆盖先写的；var 的赋值留到执行阶段才生效。经典题：`function x(){}; var x;` 之后 x 依然是函数，那行 var 在创建阶段等于没写。

**TDZ 的底层原理**（拉开差距的一问）：规范层面两类绑定分住两处——**var 与函数声明住变量环境（VariableEnvironment），let/const 住词法环境（LexicalEnvironment）**；词法环境里的绑定创建时「未初始化」，引擎访问时区分两种失败：**「找不到」沿作用域链继续上溯（最终 not defined），「找到了但未初始化」立即抛错**。TDZ 的设计价值一句话：**把 var 时代「静默 undefined」的隐患升级为「显式报错」**——和 ESM 对 CJS 的改进是同一思路（见 7.8）。

**TDZ 的两个隐藏考点**：`typeof x; let x;` 也抛 ReferenceError——**typeof 的「安全探测」光环在 TDZ 面前失效**；函数参数默认值 `function f(a = b, b)` 里 b 在 a 的 TDZ 中——参数按从左到右初始化，右边的参数对左边不可见。

**IIFE 的现代余晖**：模块化时代它的三个残余用途——script 内联代码避免污染全局、UMD 包装（一段代码同时兼容 CJS/AMD/全局三种导出）、临时隔离作用域（let 出现之前 var 时代的方案，现在多此一举）。答「还有没有用」要给场景而不是一刀切否定。

收尾：一组对仗收束——**var 给你 undefined 的温柔陷阱，let 给你报错的严格保护**；提升是登记与执行的时差，TDZ 是登记与初始化的时差。

> 面试官追问点：函数声明和函数表达式谁提升得更「完整」？应答思路：声明在创建阶段连函数体一起入册（提升前后是同一个函数对象）；表达式只是 var 登记名字，函数体随赋值语句才诞生——所以「声明可前置使用，表达式用前必炸」。这也是很多规范「优先函数表达式」的论据：强制声明先于使用，代码的逻辑顺序一目了然。

#### 1.2.3 什么是执行上下文与执行栈？作用域链是如何形成的

答：一句话定调，**执行上下文是一段代码的「运行环境包」（变量登记在哪、this 是谁、外层环境是谁）；执行栈管理这些包的进出——进函数压栈、函数完弹栈；作用域链是每个包里那条「自己没有就沿 outer 找外层」的引用链**。

**执行上下文的组成**（ES5+ 规范版三件套）：**词法环境**——登记 let/const 绑定、持有 this、指向外层词法环境；**变量环境**——登记 var 与函数声明；**外部环境引用**——链的下一环。老教材的「变量对象 VO / 活动对象 AO」是 ES3 时代的术语（AO 是函数调用后的 VO，带参数和 arguments），**答题用新术语、补一句「旧文档叫 VO/AO」，直接体现读过规范演进**——这是本题的第一个加分位。

**执行栈的运作**：全局上下文最先入栈、待在栈底直到页面同步生命周期结束；每调用一个函数压入其上下文、返回即弹出。**栈有深度上限**（V8 一万层级左右），无终止条件的递归报「Maximum call stack size exceeded」——**栈溢出不是内存不足，是深度超限**；尾递归优化写进了 ES6 规范但只有 Safari 落地，V8 至今未实现，不能当通用手段。

**作用域链的形成——两阶段各一半**（本题主脉）：

1. **定义时定一半**：函数创建时，内部槽 [[Environment]] 记住「定义时所处的外层词法环境」——这是**词法作用域的物理载体**，与未来在哪被调用无关；
2. **调用时接一半**：函数被调时创建自己的词法环境，其 outer 指向 [[Environment]] 存的那个环境——链在这一刻缝合。

变量查找从当前环境沿 outer 逐层上溯，命中即停，到全局仍未命中报 not defined。**「定义时定链、调用时走链」两句话答全，作用域、闭包、自由变量三族题在此打通**（与 7.2 的 V8 Context 互为表里）。

**与 this 的分工**（易混点收束）：作用域链管「变量去哪找」，静态、定义时定；this 管「本次调用的主语是谁」，动态、调用时算——**箭头函数就是把 this 交给作用域链管的产物**（沿链取外层 this，见 1.2.4 / 7.3）。

收尾：三个概念一句话归位——**上下文是包、执行栈是摞、作用域链是包里的绳**；口述时给一张「全局 → A → B」的压栈图，配两阶段缝合，结构分给满。

> 面试官追问点：全局上下文和函数上下文差在哪？应答思路：全局上下文绑定全局对象（浏览器 window）、整个同步生命周期只创建一次、永不弹出；函数上下文每次调用新建（同一函数调一百次压一百个包）；还有第三种 eval 上下文——严格模式下自建独立作用域，现代编码规范里已基本绝迹，能点名就是加分。

#### 1.2.4 this的四种绑定规则是什么？箭头函数的this指向谁

答：一句话定调，**this 不由定义决定、由「调用表达式」决定——同一函数换个调法 this 就换人；四条规则按优先级排：new > 显式 > 隐式 > 默认，箭头函数是唯一的例外——它根本没有 this，直接用外层的**。

**四条规则 + 一条优先级链**：

1. **默认绑定**：独立调用 `f()`——非严格模式 this 是 globalThis（历史包袱：忘写 new 时属性漏到全局的元凶），严格模式是 undefined；
2. **隐式绑定**：`obj.f()` 的 this 是 obj（点号左侧的接收者）；**隐式丢失是最高频考点**——`const g = obj.f; g()` 与 `setTimeout(obj.f, 0)` 都丢 this：**调用表达式从「方法调用」退化成「独立调用」**，函数被当作裸值传递的那一刻就注定丢失；
3. **显式绑定**：call / apply 立即调用并指定 this（两者只差传参：apply 收数组、call 逐个收）；bind 不调用，**永久预置 this 与参数**，一次 bind 后再 call 也改不动；
4. **new 绑定**：this 指向新造的实例，**整条链的最高优先级**——bind 过的函数照样能 new，this 被 new 覆盖、bind 只留下预置参数。

**箭头函数**：规范里它没有自己的 this 槽，**沿词法作用域取「定义处外层」的 this**——「this 也词法化了」，设计动机就是终结回调丢 this（旧时代 `var self = this` 的救星）。代价三条：call/apply/bind 对它无效、不能当构造器（没有 [[Construct]]）、**不适合做对象方法与原型方法**（this 指向定义处外层，而非点号左侧的对象）。使用纪律一句话：**要「谁调用指向谁」用普通函数，要「锁定外层」用箭头**。

**隐式丢失的工程防御**：回调传方法时三个正确姿势——`obj.f.bind(obj)` 预绑、`() => obj.f()` 箭头包装、class 实例字段直接写箭头函数（React 类组件事件处理器的标准解法）。

收尾：口述顺序「四规则 → 优先级链 → 箭头例外 → 丢失防御」，规范层的 EvaluateCall 与 Reference base 展开（真正的深水区）见 7.3；call/apply/bind 的手写实现见 3.1。

> 面试官追问点：bind 之后再 new，this 指向谁？应答思路：指向新实例——new 的优先级高于 bind，bind 的 this 被覆盖、预置参数保留；这是优先级链「new > 显式 > 隐式 > 默认」的完整版收口，规范依据见 7.3。

#### 1.2.5 原型链的查找流程是什么？三要素的关系怎么理解

答：一句话定调，**JS 的继承是「对象对对象的委托」：每个对象内部槽 [[Prototype]] 指向另一个对象，读属性找不到就沿这条链上溯到 null 为止；三要素关系一句话——实例的 __proto__ 指向构造器的 prototype，构造器 prototype 的 constructor 又指回构造器**。

**三要素关系图**（口述时画出来，本题的骨架分）：

```text
function Person() {}
const p = new Person();

p.__proto__ ──────────────→ Person.prototype
Person.prototype.constructor ─→ Person
Person.__proto__ → Function.prototype    （函数也是对象，由 Function 构造）
Person.prototype.__proto__ → Object.prototype
Object.prototype.__proto__ → null        （链的终点）
```

**两条链分清楚**（最容易画错的地方）：一条是 **p 的实例链**——p → Person.prototype → Object.prototype → null，负责属性查找，方法共享的秘密就是所有实例的 __proto__ 指向同一个 prototype 对象；另一条是 **Person 的构造链**——Person → Function.prototype → Object.prototype，说明「函数自己也是对象」。两条链在 Object.prototype 汇合、终止于 null，**面试画混这两条链是本题最常见的失分点**。

**读写规则不对称**（加分位）：读属性沿链上溯、自有优先；**写属性只作用于自有层**——`p.name = 'x'` 永远在 p 自己身上创建，原型上的同名属性被「遮蔽」而不是被修改（例外：原型链上的 setter 会被触发执行）。这解释了两组常见现象：给实例赋值影响不到兄弟实例；往 `Person.prototype.hobbies`（引用类型）里 push，全体实例跟着变。

**深水区三连**：`Object.create(null)` 造出的对象没有原型链——instanceof 一切为 false、连 toString/hasOwnProperty 都没有，是「最干净的字典」（不少库用它做无污染的键值容器）；`Function.__proto__ === Function.prototype` 的自指怪象（Function 由自己「构造」）；`__proto__` 是 Object.prototype 上的历史遗留访问器属性，**规范推荐 Object.getPrototypeOf / setPrototypeOf**，直接改 __proto__ 会破坏 V8 的隐藏类假设（见 7.5）。

**new 的五步与 instanceof 的沿链判定**是本题的下半场，完整展开见 7.6。

收尾：一句总纲——**「原型是对象不是类」，JS 的继承是实例对原型的委托查找，class 是这套机制的语法糖外加严格化**。

> 面试官追问点：为什么修改 Person.prototype 会影响已有实例，整体给 prototype 赋新对象却不会？应答思路：实例的 [[Prototype]] 存的是「当时 prototype 对象的引用」——原地增删改属性是动同一个对象，老实例看得见；`Person.prototype = {...}` 是换了个新对象，老实例的引用仍指旧对象，新老实例从此两条链——这也是「给 prototype 整体赋值后 constructor 会断」连环考点的前半段（constructor 双向链见 7.6）。

#### 1.2.6 寄生组合式继承怎么实现？ES6的class底层是什么

答：一句话定调，**组合继承的缺陷是「父构造器被调两次、原型上挂着多余的实例属性」，寄生组合式用一个中间空对象把父原型链接进来——只借原型不调构造器；ES6 的 class 是这套思路的官方封装，extends 的底层就是寄生组合式**。

**先看演进链，缺陷驱动改进**（按四步走，体现「知道为什么」）：

1. **原型链继承**（`Child.prototype = new Parent()`）：实例共享父类的引用属性——一个实例 push，全体跟着变；**缺陷根源：所有实例的链上挂的是同一个父实例**；
2. **借用构造函数**（在 Child 里 `Parent.call(this)`）：引用属性不共享了，**但方法只能写在构造器里，每次调用都新建一份函数，原型复用完全丢失**；
3. **组合继承**（两者相加：call 借用 + 原型挂父实例）：日常够用的主流写法，但有暗伤——**父构造器被调了两次**：一次在 `Child.prototype = new Parent()`（为了拿原型），一次在 `Parent.call(this)`（为了拿属性）；第一次调用产生的属性**全成了原型上的冗余，还会被实例上的同名属性遮蔽**——既浪费内存又污染链；
4. **寄生组合式**（终极形态）：中间造一个空函数，`F.prototype = Parent.prototype; Child.prototype = new F()`——**只把父原型链进来，完全不执行父构造器**。两次调用归一，冗余清零。

```js
function inherits(Child, Parent) {
  const F = function () {};        // 空函数：没有副作用，只为接住原型
  F.prototype = Parent.prototype;
  Child.prototype = new F();
  Child.prototype.constructor = Child;  // 修正被覆盖的 constructor 指向
}
function Child(name) { Parent.call(this, name); }
```

**修正 constructor 那一行是手写题的失分高发区**：整体替换 prototype 会把 constructor 一起换掉，`new Child() instanceof Child` 正常但 `child.constructor === Parent`——不修的话继承链的「自描述」就是断的。

**ES6 class 的底层对照**（加分主线）：class 方法是**不可枚举**的原型方法（function 写法的 prototype 方法可枚举，for-in 会带出来）；**必须 new 调用**（内部标志 [[IsClassConstructor]]，直接调抛 TypeError——对比 function 忘写 new 时 this 悄悄挂全局的历史暗坑）；class 内部自动严格模式；**static 方法挂构造器自身**而不是 prototype（`Child.xxx` 直达，实例不可见）。

**extends 与 super 的机制**（拉开差距的一段）：派生类构造器执行时 **this 还不存在**——this 由父构造器创建，`super()` 才触发创建并「认领」this，**super() 之前访问 this 直接抛错**（TDZ 思想在 this 上的复刻，规范依据见 7.6）；super 的方法解析不走普通原型链，走函数内部槽 **[[HomeObject]]** 上溯——它指向「方法定义时所在的那个对象」，即使方法被拷到别处 super 的指向也不变，这是和「this 跟着调用走」完全相反的静态寻址。

收尾：演进链一句话收束——**JS 继承史就是「怎么只借原型、不调构造器」的优化史，寄生组合式是手写解的终点，class 是它的官方转正**。

> 面试官追问点：extends 的 super 为什么能在静态方法里指向父类？应答思路：static 方法的 [[HomeObject]] 指向「类构造器对象」本身，super 的解析沿这个槽上溯到父构造器——所以静态方法里 super 的目标是「父类」而非父原型，两套 super（构造器里的 super() 与方法里的 super.x）走的是同一条 [[HomeObject]] 机制，这一问能把 80% 只会背「super 指向父类」的候选人筛掉。

#### 1.2.7 Object.create和new的区别？怎么实现继承

答：一句话定调，**两者的分水岭只有一条：new 会执行构造函数（为了造 this、装实例属性），Object.create 只做原型链接（不执行任何函数）——一个「生孩子的同时跑一遍流程」，一个「只认血统不进门」**。

**行为对照**（先给可观察差异，再讲机制）：

```js
function Person(name) {
  this.name = name || '未命名';
  this.tags = [];            // 实例属性，new 才会有
}
Person.prototype.say = function () {};

const a = new Person('张三');          // this 被创建并装配：name、tags 都在
const b = Object.create(Person.prototype);  // 只链接原型：name/tags 都是 undefined
a.say();  // 可用——链上有
b.say();  // 也可用——链上同样有
b.name;   // undefined——构造器没跑，实例属性没装
```

**机制层**：new 走 OrdinaryCreateFromConstructor——先造空对象、链上 constructor.prototype，**再以它为 this 执行构造函数体**（属性在这一步装配）；Object.create(proto) 只做第一步的「链」——proto 参数直接成为新对象的 [[Prototype]]，**函数体一次都不执行**。所以答案是那句经典对照：**new 是「创建 + 执行 + 返回」，create 是「创建 + 链接」**。

**用 Object.create 实现纯净继承**（寄生组合式的核心零件，承接 1.2.6）：

```js
function Child() { Parent.call(this); }   // 属性：借用构造器装（只此一次调用）
Child.prototype = Object.create(Parent.prototype);  // 原型：只链接不执行
Child.prototype.constructor = Child;
```

对比 `Child.prototype = new Parent()`：后者把父构造器又跑了一遍，原型上多出一套冗余实例属性——**Object.create 版本就是寄生组合式里那个中间空函数的规范内建版**，现代代码不需要再手写 `function F(){}` 了。

**深水区一：Object.create(null) 的纯净字典**。链直接是 null——没有任何继承来的属性（连 toString、hasOwnProperty 都没有），**当键值容器最干净**：不担心 `obj['toString']` 撞上原型方法、`for-in` 不用 hasOwnProperty 过滤。老牌工具库 underscore 的源码里就用它做内部容器。代价是它不再是「普通对象」的形状：console.log 打印为空、序列化行为特殊，团队协作时要有心理预期。

**深水区二：new.target**。函数内的元属性，指向「被 new 调用时实际用的构造器」：普通 new 它等于本函数；**通过被子类 super() 调用时它指向最外层的子类**——所以父类能用 `new.target.name` 做抽象基类保护：

```js
function Abstract() {
  if (new.target === Abstract) throw new Error('抽象类不能直接实例化');
}
class Sub extends Abstract {}   // 合法：new.target 是 Sub
new Abstract();                 // 抛错
```

**static 方法**顺带答全：挂构造器自身、实例不可见（`Child.create()` 直达而 `child.create()` undefined）——和「Object.create 是 Object 的静态方法」正好互为例证：**它没挂在 Object.prototype 上，所以任何对象都调不到，只有构造器 Object 能调**。

收尾：答题收在三条对照上——执行与否（属性装不装）、链接方式（prototype 属性 vs 直接给 proto）、用途分工（new 造实例、create 造关系）。

> 面试官追问点：Object.create 的第一个参数传 null 和传 Object.prototype 差在哪？应答思路：传 Object.prototype 得到「行为接近字面量 {} 的对象」（链上有全套 Object.prototype 方法），传 null 得到「什么都不会的原始容器」——差一个完整的方法层。再补一句性能细节：字面量 {} 走 V8 更快的分配路径，Object.create 在热路径上略慢，高频小对象优先字面量。

#### 1.2.8 ES6及以后的核心新特性有哪些？各自怎么使用

答：一句话定调，**ES6+ 的主线是三件事：块级作用域补完（let/const）、语言机制原生化（Symbol/Proxy/迭代器）、数据结构标准化（Map/Set/Promise）——答题不求报菜名，挑「解决了什么」讲**。

**作用域组：let/const**。与 var 的四条硬差异——块级作用域、TDZ（规范细节见 1.2.2）、**不可重复声明**、**const 冻结「绑定」不冻结「值」**（`const obj = {}` 后 `obj.x = 1` 合法——obj 指向那个对象的引用不能换，对象内容随便改，真冻结要 Object.freeze，而 freeze 也只是浅冻结）。一条工程纪律：**默认 const、需要重赋值才 let、var 只在维护老代码时出现**。

**Symbol：防止键位撞车**。第七种原始类型，`Symbol('x')` 每次都独一无二——`obj[sym]` 不会和任何字符串键冲突。三类用途：**私有属性的模拟**（外界拿不到你的 Symbol 引用就访问不到，除非遍历 getOwnPropertySymbols）；**注册表模式**（`Symbol.for('x')` 全局登记、同 key 取同一个，跨模块共享时用）；**内置协议**（Symbol.iterator、Symbol.toPrimitive、Symbol.hasInstance、Symbol.toStringTag）——**JS 用 Symbol 把「元操作」做成了可定制协议**，对象实现了 Symbol.iterator 就能被 for-of/展开运算符消费，实现了 Symbol.toPrimitive 就能参与运算（见 7.9 的 Money 案例）。

**Proxy/Reflect：拦截层 + 操作镜像**。Proxy 在对象外面包 13 种 trap（get/set/has/deleteProperty...），`new Proxy(target, handler)`——**Vue 3 响应式的地基就是 get 收集依赖、set 触发更新**（对比 Vue 2 的 Object.defineProperty 劫持不到后加属性和数组下标，Proxy 全通吃）。Reflect 与 trap 一一对应（`Reflect.get(target, key, receiver)`），**它的存在意义是让 trap 的默认行为有官方调用方式**——正确写法的 trap 一定 `return Reflect.get(...)` 而不是自己 return target[key]，因为 target 上可能有 getter，getter 里的 this 该指向代理（receiver），自己手写取值会拿错 this。**Proxy 的天坑**：任何操作都被拦截，热路径对象上包一层性能明显下降；**handler 一旦 set 会破坏 V8 隐藏类优化**（见 7.5），框架内部才值得用。

**Map/Set：真正的键值集合**。对比 Object 的四条优势——**键可以是任意类型**（Object 的键只能字符串/Symbol，`map.set(obj, data)` 直接用对象做键）；**自带 size**；**迭代顺序等于插入顺序**（普通对象的整数键会提前排序，字符串键才按插入序，顺序敏感场景 Object 有坑）；**直接可迭代**（for-of 原生支持）。WeakMap/WeakSet 是防泄漏版：键是弱引用、不阻止 GC——**两个正当用途：给对象挂私有数据（对象销毁数据跟着消失）、缓存计算结果（WeakMap 计 memoize 的标准容器）**，不当用途是当「析构回调」用（见 7.10）。

**迭代器与生成器：一套协议一种语法**。协议层：对象实现 `[Symbol.iterator]()` 返回 `{ next() { value, done } }` 就是可迭代——**for-of、展开、解构、yield* 消费的全是这一个接口**，自己实现一个就能被所有语法吃进来。语法层：function* 的 yield 是「可暂停的函数」——**每次 yield 让出执行权，next() 恢复**，天然是「惰性序列」和「状态机」的表达工具。生成器的两个进阶冷知识：**它是实现 async/await 的历史原型**（Generator + 自动执行器 = async 的前身，见 7.4 追问）；**双向通信**——`next(x)` 的参数会作为 yield 表达式的返回值送回去，不只是单向吐值。

收尾：ES6+ 的判卷标准不是背特性清单，而是**每条讲「补了什么洞」**：let 补作用域洞、Symbol 补键冲突洞、Proxy 补元编程洞、Map 补键类型洞——「问题驱动的特性」这一句本身就是面试的表达加分项。

> 面试官追问点：WeakMap 能用来遍历或看 size 吗？应答思路：不能，这正是它的设计——弱引用的前提下不允许「观察到全体键」（枚举需要强引用住它们，自相矛盾），所以没有 size、不可迭代、只有 get/set/has/delete 四个方法；顺带一句：这也决定了 WeakMap 只能「从键取值」，不能「从值找键」。

#### 1.2.9 深拷贝和浅拷贝差在哪里？深拷贝的实现方案怎么选

答：一句话定调，**三档操作的本质差异只有一句：赋值复制「引用」、浅拷贝复制「第一层」、深拷贝「递归复制每一层」——选哪档看你要不要让副本的修改影响原对象**。

**三档差异一行代码看穿**：

```js
const a = { x: 1, nested: { y: 2 } };
const b = a;                 // 赋值：a、b 是同一个对象，b.x = 9 → a.x 也变
const c = { ...a };          // 浅拷贝：c !== a，但 c.nested === a.nested——第一层分家，深层仍共享
const d = structuredClone(a); // 深拷贝：连 nested 也是新的，改谁都互不影响
```

**浅拷贝的四个姿势与两个共同暗伤**：展开运算符、Object.assign、slice/concat（数组）、Array.from——都只复制第一层。**暗伤一：丢原型**——class 实例浅拷贝后 instanceof 失效、方法全丢；**暗伤二：getter 变值**——展开运算符「读一次 getter 存为普通属性」，语义从「活的计算属性」变成了「死快照」（完整分析见 7.7）。

**深拷贝的四套方案，按代价升序**（选型是本题的实战判卷点）：

| 方案 | 能力边界 | 适用 |
|:---|:---|:---|
| JSON.parse(JSON.stringify) | 函数/Symbol 丢失、Date 变串、循环引用直接抛错 | 数据干净、无以上类型的轻量场景 |
| MessageChannel | 异步、能处理循环引用与大部分内置对象 | 不想引库又要循环引用的浏览器场景 |
| structuredClone | 循环引用/Map/Set/TypedArray 全支持；**函数抛错、丢原型、getter 变值** | 结构化数据的标准答案（边界全表见 7.7） |
| 递归手写 / lodash cloneDeep | 完全可控：保留原型、可定制特殊类型 | class 实例、带函数的复杂对象 |

**循环引用的处理——WeakMap 是唯一正解**（手写题的核心考点）：递归前先查「这个对象拷过没有」，拷过直接返回缓存——**必须 WeakMap 不能 Map**：强引用 Map 会把临时对象引用住、阻止 GC，且这份「拷贝缓存」本身就成了泄漏源。骨架代码：

```js
function deepClone(obj, cache = new WeakMap()) {
  if (obj === null || typeof obj !== 'object') return obj;      // 原始值与函数
  if (cache.has(obj)) return cache.get(obj);                    // 循环引用：返回已拷贝的
  if (obj instanceof Date) return new Date(obj.getTime());     // 特殊类型分派
  if (obj instanceof RegExp) return new RegExp(obj.source, obj.flags);
  const clone = Object.create(Object.getPrototypeOf(obj));      // 保留原型
  cache.set(obj, clone);                                        // 先登记再递归（防环的关键顺序）
  for (const key of Reflect.ownKeys(obj)) {                     // 含 Symbol 键
    clone[key] = deepClone(obj[key], cache);
  }
  return clone;
}
```

**两处手写高频失分点**：**先 set 再递归**（先递归后登记，环还没走到头就炸栈了——登记顺序就是防环的全部）；**Reflect.ownKeys 而不是 Object.keys**（后者漏 Symbol 键）。工程级补强：超深结构递归会溢栈，要转显式栈迭代；map/set/date 各写分派分支。

收尾：选型树一句话——**一层结构用展开、结构化数据用 structuredClone、带 class 和函数的上 lodash、数据干净要性能用 JSON**；机制深挖（四宗罪全表、拷贝语义与快照语义）见 7.7。

> 面试官追问点：structuredClone 和 JSON 方案在性能上怎么比？应答思路：小对象 JSON 反而常更快（字符串化路径高度优化）；大对象、含循环引用或特殊类型时 structuredClone 稳赢——JSON 会直接抛错没有可比性。更深一层：structuredClone 走结构化克隆算法（与 postMessage 同一套），是「跨 realm 可还原」的序列化语义，JSON 只是文本格式的巧合可用。

#### 1.2.10 前端模块化方案怎么演进？CommonJS与ESM差在哪

答：一句话定调，**模块化演进是一条「从社区补丁到语言标准」的线：IIFE → CommonJS（Node 的同步加载）→ AMD/CMD（浏览器的异步加载）→ UMD（双栖兼容层）→ ESM（语言级标准，静态结构 + Live Binding）——现代答题的重心放在 CJS 与 ESM 的四组硬差异上**。

**演进史一段带过**（点名关键动机即可）：ES5 时代没有模块系统，IIFE 靠闭包造私有作用域（见 1.2.2 的现代余晖）；CommonJS 是 Node 的选择——**require 是同步的**，因为 Node 读本地文件本来就是同步快操作；浏览器端文件走网络、同步会卡死渲染，于是 AMD（require.js，依赖前置、提前执行）与 CMD（sea.js，依赖就近、惰性执行）用回调把加载做成异步；UMD 不是新方案，是「一段代码同时兼容 CJS/AMD/全局」的适配壳（IIFE 判断环境选导出方式）；ESM 由语言接管，演进到此终结。

**CJS 与 ESM 的四组硬差异**（本题主战场）：

| 维度 | CommonJS | ES Module |
|:---|:---|:---|
| 加载时机 | **运行时**加载，require 是普通函数，参数可以是表达式 | **编译期**解析 import/export，静态结构不可动态拼接（动态需求走 `import()`） |
| 值的语义 | **值拷贝**——导出那一刻的快照，源模块再改，已导入方拿不到 | **Live Binding**——名字链接到源模块的内存槽，源模块改了，导入方读到新值 |
| this | 顶层 this 是 exports | 顶层 this 是 undefined（对齐严格模式） |
| 同步性 | 同步阻塞 | 异步加载（构建/实例化/求值三阶段） |

**值拷贝 vs Live Binding 的可观察差异**（面试最好给一行代码）：

```js
// CJS：counter.js 导出 count=0，一秒后自增
const { count } = require('./counter');   // 解构拿到的是快照
setTimeout(() => console.log(count), 1100);  // 0 —— 永远是 0

// ESM：
import { count } from './counter.mjs';
setTimeout(() => console.log(count), 1100);  // 1 —— 读到的是源模块的"现在"
```

**CJS 应对快照语义的两个工程姿势**：导出对象包一层（`module.exports = { get count() {...} }`）、导出函数（`exports.getCount = () => count`——每次调用现取），**「CJS 传变化要么带壳要么带函数」**。ESM 侧的对称约束：import 进来的绑定**只读**，赋值抛 TypeError。

**深水区一：为什么 ESM 必须静态**。import/export 必须在顶层、名字必须是字符串字面量——因为**编译期要构建完整的模块依赖图**：不执行代码就能确定「谁依赖谁、导出哪些名字」，这是 tree-shaking（打包器删除未引用导出）的前提、import 提升（hoisting）的依据、也是循环依赖处理的根基（符号表先于执行就绪）。CJS 的 require 散落在 if 里也能跑，代价就是整棵依赖图只能运行时才拼得出。

**深水区二：循环依赖的行为差异**（高频追问）：A require B、B require A 时，B 拿到的是 **A 执行到一半的 exports**——已执行部分可用、未执行部分 undefined，正解是「延迟访问」（把 require 挪进函数体）。ESM 靠「符号表先行」让函数声明提升可用、let/const 在求值前抛 TDZ——**CJS 静默 undefined，ESM 显式报错**，完整三阶段机制与推演见 7.8。

**Node 的双轨现实**（工程加分项）：Node 里两者可互操作但不对称——**CJS require ESM 要用 `await import()` 动态导入**（ESM 是异步的，同步 require 拿不到）；ESM import CJS 是「把 module.exports 整体当 default」，**命名导入 CJS 的属性其实是对 default 的解构**；`.mjs/.cjs` 后缀或 package.json 的 type 字段决定归属， Node 22+ 的 require(esm) 才开始解开这个死结。

收尾：演进史一句话归位——**CJS 是运行时的对象交换（同步、快照），ESM 是编译期的符号链接（异步、活绑定）**；口述重心放四组差异表 + Live Binding 演示，循环依赖甩给 7.8 的深度版。

> 面试官追问点：既然 ESM 静态，动态场景怎么办？应答思路：`const mod = await import(path)` 是官方的动态口子——返回带命名空间的模块对象，路径可以是运行期计算的变量；代价是该 import 无法被静态分析，不参与 tree-shaking、不能被提升。典型场景：路由级代码分割（按页面懒加载）、条件加载 polyfill——**「静态是给优化器的，动态是给运行时的」**，一句收束。

# 2.异步编程

#### 2.1 事件循环是怎么运作的？宏任务微任务的顺序是什么

答：一句话定调，**浏览器事件循环只有两条铁律：一次取一个宏任务执行；宏任务结束把整个微任务队列排干（连同执行中新生出的微任务）——渲染插在两者之间。所有输出题都是这两条规则的推演**。

**先立浏览器模型**（面试画这个骨架）：一次 tick = 取一个宏任务 → **排干全部微任务** → 必要时渲染（rAF 回调 → style/layout/paint）→ 下一轮。**「排干」是关键语义**：微任务执行中入队的新微任务也要在本轮清完——这是 await 链条能连续推进的保证。

**两边阵营先分清**（判题第一步）：

| | 宏任务 | 微任务 |
|:---|:---|:---|
| 代表 | setTimeout/setInterval、I/O、UI 事件、MessageChannel | **Promise.then/catch/finally、queueMicrotask、await 后续、MutationObserver** |
| 节奏 | 一次一个 | 一次排干全部 |
| 设计目的 | 不同事情的排队 | 同一件事的收尾（尽快但不插队同步代码） |

**经典输出题的解题四步法**（实战判卷点）：

1. **同步代码先跑完**——函数调用、new Promise 的执行器都是同步，只有 then 回调进微任务；
2. **遇到 async 函数拆开看**——await 右边的表达式先同步求值，**await 之后的部分进微任务**（等值决议后入队）；
3. **宏任务里的微任务优先**——setTimeout 回调执行中产生的 then，在本轮宏任务结束时立刻排干，不等下一个 setTimeout；
4. **Promise 已决议，then 依然异步**——决议早于注册不影响「回调永远走微任务」。

```js
console.log('start');
setTimeout(() => console.log('timeout'));
Promise.resolve().then(() => console.log('then1'));
queueMicrotask(() => console.log('microtask'));
console.log('sync end');
// start → sync end → then1 → microtask → timeout
```

**Node.js 侧的增量考点**（讲出与浏览器的差异）：六阶段循环 timers → poll → check，**每个阶段切换间隙清一次微任务**；`process.nextTick` 是**优先级高于 Promise 微任务的独立队列**（每个阶段之间先清 nextTick 再清微任务），递归 nextTick 能饿死一切——官方因此建议慎用；`setTimeout(fn, 0)` 与 `setImmediate` 顺序不定（取决于启动时机），**但在 poll 阶段回调里 setImmediate 必先于 setTimeout**——这个特例是老牌考点。

**深水区一：setTimeout(fn, 0) 不是 0ms**。HTML 规范嵌套层级超过 5 层后最小间隔强制 4ms；后台标签页节流到 1000ms+；**「0」的真实语义是「不早于 0ms，实际取决于任务队列的拥挤程度」**——需要精确时序的场景（动画）要换 requestAnimationFrame（见 2.5）。

**深水区二：await 的两次让权**。`await fn()` 之后的代码不等于同步续写——**它至少让出一次微任务机会**（等 fn 决议的那个微任务），所以 async 函数里 await 前后的代码可能被中途插进来的任务打断；连续 await 是「每个 await 排一个微任务」的链式行为，机制深挖见 7.1。

收尾：口述节奏——两条铁律、宏微对照表、四步解题法、Node 增量差异，最后一句「微任务管同一件事的收尾，宏任务管不同事情的排队」收束；浏览器/Node 的规范级展开（微任务队列归属、rAF 时机）见 7.1。

> 面试官追问点：微任务队列是 V8 的还是浏览器的？应答思路：队列本身由宿主维护（浏览器走 HTML 规范的「清理微任务队列」步骤，Node 在 libuv 阶段间隙），V8 只提供入队 API——「微任务归 V8」的说法不准确，归「JS 运行时环境」。这是 7.1 的标准深水区问答，实战版答出「宿主维护、V8 入队」即可。

#### 2.2 Promise的链式调用原理是什么？组合方法怎么选

答：一句话定调，**Promise 是「单向不可逆的状态机 + then 永远异步」两条底线；链式调用的本质是 then 返回新 Promise、上一环的返回值决定下一环的走向；四个组合方法按「谁赢、败了怎么办」两问选型**。

**状态机与两条底线**：pending → fulfilled / rejected，**单向不可逆、第一次决议为准**（再 resolve 静默无效）。底线二：**then 的回调永远异步**——即使 Promise 已经决议，回调也走微任务（Promises/A+ 2.2.4），这保证了「then 注册前后」代码时序的确定性，规范层机制见 7.4。

**链式调用的三个关键认知**（实战版核心）：

1. **then 返回的是新 Promise**——`p.then(a).then(b)` 里 a 影响的是 promise2，与 p 无关，链不会「污染」源头；
2. **返回值决定下一环**：返回普通值 → 下一环直接 fulfilled；**返回新的 Promise → 下一环等它**（这是串行请求的原理）；抛异常 → 下一环 rejected；
3. **错误穿透**：then 不传第二个参数时，rejection 原样转发到下一环——**错误一路穿到最近的 catch**，这就是「catch 放链尾、中间不用层层兜」的机制依据。

```js
// 串行：返回 Promise，下一环等它
urls.reduce((p, url) => p.then(() => fetch(url)).then(r => results.push(r)), Promise.resolve());
// 穿透：中间不写 onRejected，错误直达 catch
fetchA().then(processA).then(processB).catch(handleAllFailures);
```

**四个组合方法，两问选型**（「谁算赢、有失败怎么办」）：

| 方法 | 胜负规则 | 全败时 | 典型场景 |
|:---|:---|:---|:---|
| all | 全成才成 | reject 第一个错误 | 并行取多份必需数据 |
| race | **第一个 settle**（无论成败） | — | 超时控制（Promise vs timer 赛跑） |
| allSettled | 等**全部结束** | **永不 reject** | 批量任务要「逐个汇报结果」 |
| any | **第一个成功** | reject AggregateError | 多 CDN 竞速、任一可用即可 |

**all 的经典误区**（拉开差距点）：短路只发生在「结果层面」——第一个 reject 时 all 立刻整体 reject，**但其余请求仍在跑，只是结果被丢弃，「取消」是做不到的**；要真取消必须 AbortController 配合（见 2.4）。race 的对称误区：它可能以「失败」告终（第一个 settle 的如果是 rejected），**只想超时不想竞速失败的场景要 race([task, timer.then(() => { throw new Error('timeout') })])**——让 timer 的「胜利」表现为失败。

**手写要点**（笔试高频，完整版见 3.1）：三态常量与状态判断防重复决议、**then 返回新 Promise**、**resolve 值为 thenable 时的递归展开**（这是 Promise/A+ 判卷最严的一条，机制见 7.4）、回调入队走微任务（queueMicrotask 模拟）。

收尾：答题顺序「状态机 → 链式三认知 → 组合方法表 → all/race 两个误区」；错误穿透与 thenable 展开的规范级推演见 7.4。

> 面试官追问点：Promise.all 中某个失败了，剩下的为什么还在跑、怎么真取消？应答思路：Promise 一旦创建就开始执行，all 的短路只是「不再关心结果」——传给 all 的不是「任务」而是「已经开始的结局」；真取消要么用 AbortController 让请求本身停止（fetch 原生支持），要么用包装函数把「创建 Promise」延迟到被需要时（惰性创建）。能说出「all 管理的是结局不是任务」这句，就把 90% 的候选人甩开了。

#### 2.3 async与await的底层实现是什么？错误处理怎么做

答：一句话定调，**async/await 是「用同步的写法调异步的代码」的语法层封装：async 函数返回 Promise，await 是「让权 + 恢复」的分界点——它的历史原型是 Generator + 自动执行器，规范实现则直接走 Promise 恢复机制**。

**先立两条硬规则**（一切推演的地基）：**async 函数的返回值自动包 Promise**——return 1 等价 return Promise.resolve(1)，return 一个 Promise 会被展开（不会 Promise 套 Promise）；**async 函数抛异常 = 返回 rejected Promise**——函数体内 throw 的错误不会同步炸出来，而是变成返回值的 rejected 态。

**await 的机制三步走**（口述骨架）：求值右边的表达式（同步）→ **让出执行权**（当前 async 函数挂起，控制权交回事件循环）→ 表达式决议后，**await 之后的代码作为微任务入队恢复执行**。由此推出两个常考结论：**await 后面的代码 ≈ then 的回调**——它们在同一类时序位置上；**await 只在 async 函数的「当前这一层」生效**，await 一个「内部又含 await 的函数」时，外层的 await 等的是整个函数的最终决议，不是中间过程。

**错误处理的三种姿势**（实战判卷点）：

```js
// 姿势一：try/catch 直接包（最常用；catch 不到「外层没 await 的调用」）
try {
  const data = await fetch(url);
} catch (e) { /* 处理 */ }

// 姿势二：.catch 接在 Promise 上（不想中断主流程时）
const data = await fetch(url).catch(() => fallback);

// 姿势三：给 await 的结果做包装（Go 风格 [err, data]，批量错误的统一收口）
const [err, data] = await to(fetch(url));
```

**必考坑：async 函数体外的错误捕获**——`const p = asyncTask(); p.then(...)` 不 await 不 catch，或者 `asyncTask();` 裸调用，**函数内的 reject 没人接住就成了 unhandledrejection**（全局兜底监听见 5.5）；try/catch 也**包不住定时器回调里抛的错**——try 只覆盖同步执行路径和 await 的等待点，回调里的 throw 在另一个调用栈里（见 5.5 的错误捕获矩阵）。

**串行与并行**（笔面试双高频）：

```js
// ❌ 最贵的串行错误：循环里逐个 await——三个请求 3 秒
for (const url of urls) {
  await fetch(url);          // 每个都等上一个
}
// ✅ 要并行：先「启动全部」再「统一等待」
const tasks = urls.map(url => fetch(url));  // map 不 await，全部同时启动
const results = await Promise.all(tasks);    // 总耗时 ≈ 最慢的那一个
```

**判断心法：await 写在「循环体里」是串行，写在「Promise.all 上」是并行**——`map` 里不写 await 只收集 Promise，是并行范式的标准形态。循环内的依赖判断：下一轮需要上一轮的结果才串行，否则必并行。

**深水区一：语义等价 ≠ 实现相同**。教科书说 async/await 是「Generator + 自动执行器」——历史路径上确实如此（co 库时代），但规范层面 AsyncFunction 是独立的：**await 不经 generator 的状态机转写，直接走 Promise 的 then 接回执行权**，比转写少一层包装；V8 还做过「跳过中间 Promise」的优化（曾因造成可观察的时序差异又撤回）——「语义等价、实现独立」六个字是这题的专家线，规范细节见 7.4 追问。

**深水区二：await 的两次让权**。`await 42`（await 原始值）与 `await p`（await Promise）都让权，但后者多等「决议的那个微任务」——所以 **await 后面的代码至少晚一个微任务 tick**；这也是「await Promise.resolve() 之后，某些排队中的微任务先执行」一类刁钻输出题的根源（微任务队列语义见 7.1）。

收尾：三句话归位——**返回值包 Promise、错误变 rejected、await 是让权恢复点**；口述给「串行改并行」的对照代码，错误处理给三姿势加 unhandledrejection 提醒，就覆盖了这题的完整判分面。

> 面试官追问点：为什么 for 循环里不能直接改成「await Promise.all(urls.map(fetch))」？应答思路：`map(fetch)` 会把 fetch 的第二参数位置当成 map 的 index 传进去——`fetch(url, 0)` 的 0 会被当成 RequestInit（无害但脏）；正确写法是 `urls.map(u => fetch(u))`。这是个「知道并行范式但手滑翻车」的经典扣分点，能主动指出就变成了加分点。

#### 2.4 Promise并发控制怎么实现？取消与超时方案有哪些

答：一句话定调，**并发控制是「限流启动」不是「限流创建」——调度器管的是「同时进行中的任务数」不超上限；取消与超时是两个独立关注点，fetch 时代的标准答案是 AbortController 管取消、Promise.race 管超时**。

**并发调度器（笔试最高频，背骨架 + 三个设计点）**：

```js
class Scheduler {
  constructor(limit) {
    this.limit = limit;      // 并发上限
    this.queue = [];         // 等待启动的任务
    this.active = 0;         // 正在进行
  }
  add(taskFn) {                       // taskFn: () => Promise，惰性创建
    return new Promise((resolve, reject) => {
      this.queue.push({ taskFn, resolve, reject });
      this._run();
    });
  }
  _run() {
    while (this.active < this.limit && this.queue.length) {
      const { taskFn, resolve, reject } = this.queue.shift();
      this.active++;
      taskFn().then(
        v => { this.active--; resolve(v); this._run(); },  // 完成一个，补位一个
        e => { this.active--; reject(e); this._run(); }
      );
    }
  }
}
// 100 个请求最多同时 5 个
const s = new Scheduler(5);
const results = await Promise.all(urls.map(u => s.add(() => fetch(u))));
```

**三个设计判分点**：**add 传「函数」不传 Promise**——传已创建的 Promise 等于全部已经开始跑，调度失去意义（惰性创建是可调度的前提）；**补位不分成败**——成功失败都要释放槽位，reject 后卡死整个队列是常见笔误；**while 一轮补满**——不用递归逐个补。

**取消：AbortController 是唯一真解**。Promise 本身不可取消（状态机决议不可逆），能取消的只有「底层操作」——fetch 原生接收 AbortSignal，abort 时请求真实中断（网络传输都停了，不只是丢弃结果）：

```js
const ctrl = new AbortController();
fetch(url, { signal: ctrl.signal });
setTimeout(() => ctrl.abort(), 5000);   // 5 秒后取消
// ctrl.abort() 后 promise 以 AbortError 拒绝；一个 ctrl 可以发给多个请求，一次全停
```

**「真取消」与「假取消」的分界**（拉分点）：旧式 `Promise.race([p, cancelPromise])` 只是「先到先得、丢弃另一个」——**请求本身还在跑，浪费带宽**；AbortController 才是让底层操作真正停下。判断标准一句话：**取消有没有省资源，还是只眼不见为净**。

**超时：race 的标准范式与两个补强**：

```js
function withTimeout(promise, ms) {
  let timer;
  return Promise.race([
    promise,
    new Promise((_, reject) => {
      timer = setTimeout(() => reject(new Error('TIMEOUT')), ms);
    })
  ]).finally(() => clearTimeout(timer));      // 补强①：提前完成清掉定时器
}
// 补强②：超时不止丢结果，还要断底层——现代原生一行搞定：
fetch(url, { signal: AbortSignal.timeout(5000) });   // Node 18+ / 新浏览器
```

收尾：三件事一句话归位——**调度管「同时进行」、abort 管「提前结束」、race 管「到期不等」**；实战三者常组合（列表页：调度限并发 + 单请求超时 + 翻页时 abort 旧请求），面试主动给一个组合场景就是工程级答案。

> 面试官追问点：为什么 Promise 设计成不可取消？应答思路：决议不可逆是 Promises/A+ 状态机的根基——then 的注册方（第三方）不应有权力撕毁结局，否则「一个 Promise 多处订阅」的语义会崩（A 取消了 B 还等着）。取消的正确层位在底层操作（网络、读流、定时器），Promise 只是「结果的容器」，容器不能被销毁、但生产线可以停——这正是 AbortController 被单独发明的原因。

#### 2.5 定时器有什么问题？动画帧与空闲回调的时机是什么

答：一句话定调，**setTimeout/setInterval 有三宗罪（最小间隔、后台节流、漂移），决定了它们只配当「兜底调度」——动画跟着渲染帧走用 rAF、空闲杂活跟着浏览器闲不闲走用 requestIdleCallback、重试跟着失败次数走用指数退避**。

**三宗罪逐条讲**：

1. **最小间隔**：HTML 规范规定嵌套 5 层以上的 setTimeout 最小 4ms——`setTimeout(fn, 0)` 从来不是 0ms，「0」只是「不早于」；
2. **后台节流**：后台标签页定时器被节流到至少 1000ms（Chrome 的 intensive throttling 对链条式定时器甚至到 1 分钟）——**「定时轮询」在用户切走后基本停摆，前端心跳逻辑不能依赖 setTimeout**，标准解法是 Web Worker（Worker 内定时器不受主线程节流影响）或页面可见性 API 配合；
3. **漂移**：定时器回调只是「不早于该时刻被调度」，前面压着长任务就整体顺延——**用 setInterval 做动画会肉眼可见地掉帧**，它和渲染管线完全脱钩。

**rAF：跟着渲染帧走**。requestAnimationFrame 的回调在「下一次重绘之前」执行、每帧至多一次——**浏览器保证它与渲染管线同步**：改样式落在渲染前，不浪费帧。三个实用细节：**切后台自动暂停**（省电，动画逻辑天然停）；**帧率自适应**（120Hz 屏跟 120fps，别写死 16ms）；**rAF 回调里依然要避免「写后读」**——改完 DOM 立刻读 offsetHeight 会强制同步回流（见 4.1）；rAF 不能指定延迟，等价「下一帧」，节奏控制自己记时间戳（`now - last > interval` 才干活——帧率锁的原理）。

**requestIdleCallback：浏览器闲的时候叫我**。回调携带 deadline（这一帧渲染完还剩多少毫秒），适合**可延迟的非紧急工作**：埋点上报、缓存预热、预计算。两条纪律：**deadline.timeRemaining() 用完必须收工**（一次干不完记录进度下次接着干）；**加 timeout 参数兜底**——后台标签可能长期不进 idle。rIC 兼容性差，社区标准 polyfill 用 rAF 模拟。

**请求重试：指数退避**（给骨架 + 两个进阶）：

```js
async function retry(fn, times = 3, base = 500) {
  for (let i = 0; i < times; i++) {
    try { return await fn(); }
    catch (e) {
      if (i === times - 1) throw e;
      const delay = base * 2 ** i * (0.5 + Math.random());  // 指数 + 抖动 jitter
      await new Promise(r => setTimeout(r, delay));
    }
  }
}
```

**为什么指数**：服务端过载时立刻重试是火上浇油，指数间隔（500 → 1000 → 2000）给服务端恢复窗口；**为什么加抖动**：所有客户端同一时刻重试会形成「重试风暴」，jitter 把同步重试打散；**重试资格**：只重试网络类/5xx/幂等操作，4xx 业务错误重试无意义。

收尾：一张时机选型表——延时调度 setTimeout、动画 rAF、空闲杂活 rIC、后台心跳 Worker、失败重试指数退避；核心心法一句话：**定时 API 的选择，本质是「你要跟着谁的节拍走」**。

> 面试官追问点：rAF 做动画为什么比 setInterval 顺？应答思路：rAF 的回调时机绑定渲染管线——每帧渲染前必调，天然「一帧一画」；setInterval 与渲染脱钩，一帧内可能零次或多次触发，既浪费又掉帧。与显示器 VSync 对齐是 rAF 存在的全部理由，这也是为什么动画优化铁律是「属性变更写进 rAF、没进 rAF 的样式修改都是浪费帧」。

#### 2.6 经典输出题的执行顺序怎么判？背后的原理是什么

答：一句话定调，**输出题不是玄学，是「同步栈 → 微任务排干 → 宏任务逐个」的三层遍历——给每个输出打上「哪一层、何时入队、层内第几」三个标签，标完答案自己浮出来**。

**通用解题四步 tagging 法**：

1. **同步层全跑完**：非回调代码、Promise 执行器、await 右侧表达式的求值——立即执行；
2. **微任务层按入队顺序排**：then/catch/finally、await 之后的部分、queueMicrotask——执行中产生的新微任务接排到当前队尾；
3. **宏任务一轮一轮走**：每个宏任务执行完，**重新排干微任务**，才进下一个宏任务；
4. **「多一轮」的三个来源**（拉分点）：resolve(thenable) 多排一个微任务（7.4 的 thenable 展开）；Node 的 process.nextTick 插队到所有微任务之前（7.1）；微任务里注册的 setTimeout 属于**下一轮**宏任务。

**一道综合题走全流程**（字节/阿里的原型题变体）：

```js
async function async1() {
  console.log('async1 start');     // 同步
  await async2();                   // async2 同步执行
  console.log('async1 end');        // 微任务 A（await 续体）
}
async function async2() { console.log('async2'); }

console.log('script start');        // 同步 1
setTimeout(() => console.log('timeout'), 0);    // 宏任务
async1();                           // 同步 2～4 在此触发
new Promise(resolve => {
  console.log('promise');           // 同步 5
  resolve();
}).then(() => console.log('then')); // 微任务 B
console.log('script end');          // 同步 6

// 输出：script start → async1 start → async2 → promise → script end
//      → async1 end → then → timeout
```

**两个高频分歧点的裁定**（判卷重灾区）：**async1 end 和 then 谁先**——比的是**注册顺序**：async1() 先被调用，await async2() 返回已决议的 Promise，续体立即注册入队；new Promise 的 then 注册在其后——微任务队列是 [async1 续体, then]，先注册先执行；**await 续体不是同步代码**——它虽写在函数体里，但执行位置是「微任务队列」，和 then 同层竞争。Chrome 73 之前 await 走两个微任务、之后优化成一个，老题的老答案如今是错的——**答题按现代语义讲，能主动提这句历史差异是大加分**。

**async 函数 return 的值类型**（提示要点点名）：return 原始值 → 自动包成 Promise；return Promise → **展开不套娃**（不会 Promise 套 Promise）；**return await p 与 return p 的唯一区别在 try/catch 里**——`return await p` 先在本层等，p 的 rejection 能被本层 catch 捕获后再返回；`return p` 直接透传，rejection 归调用方、本层 catch 摸不到——**这是 lint 禁 return await 的唯一白名单场景**。

收尾：输出题的满分策略不是刷题背答案，是背流程——**同步全跑、微任务排干按序、宏任务一轮一轮、每个输出打三层标签**；机制层的完整推演（thenable 展开、排干语义）见 7.1 / 7.4。

> 面试官追问点：为什么这题在 Chrome 73 前后有不同答案？应答思路：早期 await 的续体需要两个微任务（先决议再恢复），73 起 V8 优化为一个——老博客里「async1 end 在 then 之后」的答案由此而来。主动讲出「规范语义稳定、实现细节曾优化」这一层，比答对本身更能证明理解。

# 3.手写代码系列

#### 3.1 八种高频手写函数怎么实现？各自的实现要点是什么

答：一句话定调，**手写题的判卷标准从来不是「能跑」，是边界处理——每题背「一个骨架 + 一个失分点」，八题按四组记：绑定三兄弟、构造三件套、异步双星、函数式**。

**第一组：绑定三兄弟（call / apply / bind）**——核心技巧都是「借对象挂函数」：

```js
Function.prototype.myCall = function (ctx, ...args) {
  ctx = ctx == null ? globalThis : Object(ctx);   // 兜底 null/undefined + 原始值装箱
  const key = Symbol('fn');                        // 失分点①：Symbol 键防覆盖用户属性
  ctx[key] = this;
  const result = ctx[key](...args);
  delete ctx[key];
  return result;                                    // 失分点②：要返回执行结果
};
// myApply 同骨架，args 换成数组：ctx[key](...arr)
```

**bind 是三兄弟里唯一要考虑优先级的**（new 分流，见 1.2.4）：

```js
Function.prototype.myBind = function (ctx, ...preArgs) {
  const fn = this;
  const bound = function (...args) {
    return fn.apply(
      this instanceof bound ? this : ctx,    // 失分点①：new 调用时 this 换新实例
      [...preArgs, ...args]
    );
  };
  bound.prototype = Object.create(fn.prototype); // 失分点②：new bound() 要能 instanceof 原函数
  return bound;
};
```

**第二组：构造三件套（new / instanceof / 深拷贝）**：

```js
function myNew(Ctor, ...args) {
  const obj = Object.create(Ctor.prototype);        // 造对象 + 链原型（一步到位）
  const result = Ctor.apply(obj, args);            // 绑 this 执行
  return result instanceof Object ? result : obj;  // 失分点：返回对象用之、原始值丢弃
}
function myInstanceof(obj, Ctor) {
  if (obj == null || (typeof obj !== 'object' && typeof obj !== 'function'))
    return false;                                   // 失分点：原始值直接 false，不装箱
  let proto = Object.getPrototypeOf(obj);
  while (proto !== null) {
    if (proto === Ctor.prototype) return true;
    proto = Object.getPrototypeOf(proto);
  }
  return false;
}
```

深拷贝的完整骨架（WeakMap 防环 + Reflect.ownKeys 收 Symbol 键 + 保留原型）见 1.2.9 的 deepClone——**那套代码里的「先登记再递归」顺序是本组最大的失分点**。

**第三组：异步双星（Promise.all / sleep）**：

```js
function myAll(list) {
  return new Promise((resolve, reject) => {
    const ps = Array.from(list);              // 可迭代输入转数组
    const arr = [];
    let count = 0;
    if (ps.length === 0) return resolve([]);
    ps.forEach((p, i) => {
      Promise.resolve(p).then(v => {          // 失分点①：包装接住非 Promise 值
        arr[i] = v;                            // 失分点②：按下标放保序（push 会乱序）
        if (++count === ps.length) resolve(arr); // 失分点③：计数而非 length
      }, reject);                               // 首个失败直接整体 reject（短路语义）
    });
  });
}
const sleep = ms => new Promise(r => setTimeout(r, ms));
// race 同骨架去掉计数，第一个 settle 直接透传其结果——「透传」两字别自己再包一层
```

**第四组：函数式（柯里化；防抖节流见 3.2）**：

```js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);   // 参数够直接调
    return (...rest) => curried.apply(this, [...args, ...rest]); // 不够继续攒
  };
}
```

**每组的通判清单**（比背十个变体有用）：绑定组——this 兜底、Symbol 键、new 分流；构造组——返回值兜底、原始值短路、防环顺序；异步组——保序计数、resolve 包装；**所有组的公共失分点——this 与参数透传**（回调里 `fn.apply(this, args)`，事件场景 this 是元素，丢了就是 undefined 调用）。

收尾：八题难度排序口述——**bind 最难（new 分流 + 原型链）、all 最易错（保序计数）、instanceof 最易漏（原始值）**；防抖节流的完整双版实现与 leading/trailing 语义见 3.2。

> 面试官追问点：myNew 里为什么先链原型再执行构造器？应答思路：构造器执行时 this 上的方法调用靠原型链解析——先造身份再装配属性，构造器里 `this.init()` 才能找到；反过来先 apply 再链原型，构造过程中方法全是 undefined。这一问同时考察对 new 五步（见 7.6）的顺序理解，答「顺序决定 this 的可用性」就到位。

#### 3.2 防抖和节流的差异在哪里？手写实现与场景怎么选

答：一句话定调，**防抖是「事件停了才执行」（合并尾音），节流是「过程中定期执行」（保留节奏）——选型一句话：只关心结束用防抖、过程要反馈用节流**。

**场景对照表**（先给选型，判卷最快）：

| 场景 | 选型 | 理由 |
|:---|:---|:---|
| 搜索框输入联想 | 防抖 | 用户停手再请求，中间击键全是浪费 |
| resize 重算布局 | 防抖 | 拖完再算一次 |
| 滚动位置监听（吸顶/进度条） | 节流 | 过程中持续反馈 |
| 按钮防重复提交 | 防抖（leading） | 第一次就拦，不等最后一次 |
| 无限滚动加载 | 节流（或 IntersectionObserver） | 过程中持续判断 |
| 鼠标跟随/游戏射击 | 节流 | 固定节奏响应 |

**防抖实现（默认版 + leading 立即执行版 + cancel）**：

```js
function debounce(fn, wait, { leading = false } = {}) {
  let timer = null;
  const debounced = function (...args) {
    if (leading && timer === null) fn.apply(this, args);  // leading：第一次立即执行
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      if (!leading) fn.apply(this, args);                  // 默认 trailing：停了才执行
    }, wait);
  };
  debounced.cancel = () => { clearTimeout(timer); timer = null; };  // 取消接口
  return debounced;
}
```

**节流的两个实现版，行为差异是高频追问**：

```js
// 时间戳版：首次立即执行；停止触发后不会补最后一次
function throttle(fn, interval) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= interval) { last = now; fn.apply(this, args); }
  };
}
// 定时器版：首次延迟执行；停止触发后会补最后一次（trailing）
function throttleTimer(fn, interval) {
  let timer = null;
  return function (...args) {
    if (timer) return;
    timer = setTimeout(() => { timer = null; fn.apply(this, args); }, interval);
  };
}
```

**leading / trailing 的完整语义**（拉开差距的一层）：触发时机组合成四种——**leading-only**（第一次响应、停止不补）、**trailing-only**（防抖的默认）、**leading + trailing**（lodash 节流的默认：立即响应一次、停止后再补一次）、**none**。**能说出「节流也有 trailing」，就已经超过只背『首尾执行』的候选人**；lodash 的节流第三、四参数 `{ leading: true, trailing: true }` 就是在配这个。

**两个工程级补强**：**cancel 方法**——React 组件卸载时防抖回调还在飞，`setState on unmounted` 警告的经典来源，unmount 时必须 cancel（3.1 里两个实现都挂了）；**maxWait**（lodash debounce 的配置项）——**纯防抖的致命缺陷：持续触发就永远不执行**（用户连续打字十秒，搜索联想十秒不出），maxWait 设最长等待上限「到时间必执行一次」，把「等停顿」和「保底频率」结合。

**深水区两条**：**this 与参数透传**——`fn.apply(this, args)` 不能省（事件监听里 this 是元素，丢 apply 后回调里 this 变 undefined），timer 变量正是 1.2.1 说的「闭包携带状态」的教科书应用；**节流的现代替代**——滚动加载场景用 IntersectionObserver（见 6.2）把「高频触发后降频」升级为「进入视口才触发」，从降频到免监听，是这组知识的新答案。

收尾：一句话总纲——**防抖合并尾音、节流保留节奏**；答题给场景表 + 双版节流 + trailing 语义三件套，工程级补 cancel / maxWait。

> 面试官追问点：为什么说「防抖不适合搜索联想的极端场景」？应答思路：用户输入不停止防抖就永远不触发——联想列表长时间空白；解法两条：加 maxWait（最长 300ms 必出一次结果），或改 leading 节流（立即出第一批、滚动更新）。能把防抖的「等待停顿」缺陷主动暴露并给出修补，就是「会用」和「背过」的分界线。

# 4.浏览器与V8引擎

#### 4.1 从输入URL到页面渲染经历了什么？重绘回流怎么触发

答：一句话定调，**全流程八步（导航五步 + 渲染三步），判卷核心在渲染管线：解析生树 → 布局算盒 → 绘制上屏；而回流必然带重绘、重绘不一定回流——「读写分离」是性能答案的总纲**。

**导航阶段五步**（网络侧，快讲）：① URL 解析/缓存查找（强缓存直接用、协商缓存问服务器，见 5.1）；② DNS 域名解析（浏览器/系统/路由器逐级缓存，都没有才递归查询）；③ TCP 三次握手 + TLS 握手（HTTPS 在 TCP 之上再握手一轮）；④ 发请求收响应（状态码 + 资源流水）；⑤ **进程交接**——浏览器进程把数据交给渲染进程，后面全是渲染进程的舞台。

**渲染阶段三步**（判卷主场）：

1. **解析生树**：HTML → DOM 树，CSS → CSSOM 树，两树合成**渲染树**（不可见节点 display:none 在此剔除——但注意 visibility:hidden 会保留在渲染树里，这个对比是回流题的暗点）；
2. **布局（Layout/Reflow）**：计算每个节点的几何信息（位置、大小），输出盒模型；
3. **绘制（Paint）**：填充像素 → **合成（Composite）**：分层、光栅化、GPU 合成上屏——**现代浏览器把「只改 transform/opacity」的动画放在合成层，跳过布局和绘制，这是性能最好的动画属性**。

**回流与重绘的触发成本**（本题判分核心）：

| | 回流 Reflow | 重绘 Repaint |
|:---|:---|:---|
| 改什么 | 几何（宽高、位置、display、字体） | 外观（颜色、背景、阴影、visibility） |
| 代价 | 几何重算 + 重绘 + 可能的整树波及 | 仅像素重涂 |
| 关系 | **回流必带重绘** | 重绘不触发回流 |

**强制同步回流是性能杀手**（拉开差距的一层）：布局信息是**惰性计算**的，但「写后读」会打断这个优化——

```js
// ❌ 循环里读写交替：每次读 offsetHeight 都强制同步回流，N 个元素 N 次回流
els.forEach(el => { el.style.height = '10px'; console.log(el.offsetHeight); });
// ✅ 读写分离：先全部读、再全部写
const heights = els.map(el => el.offsetHeight);   // 只读：一次回流
els.forEach((el, i) => { el.style.height = heights[i] + 'px'; });  // 只写
```

**为什么读也会触发**：改了样式之后读布局，浏览器必须**当场**算出准确值——把本可批量、延后的回流提前到这一行，这就是「同步」二字的含义。

**回流优化四件套**：**读写分离**（上面的范式）；**class 切换代替多次改 style**（一次 class 改动合并成一次回流）；**脱离文档流批量操作**——DocumentFragment（见 4.4）或先 `display:none` 改完再显示（回流只发生两次）；**动画走合成层**——transform/opacity 交给 GPU，与布局绘制完全无关；配套手段：`getBoundingClientRect` 批量缓存、CSS contain 属性圈定回流范围。

收尾：口述节奏「导航快讲、渲染慢讲」；渲染管线画 DOM + CSSOM → Render Tree → Layout → Paint → Composite 五连，收在「回流必带重绘、优化就是减少读写交替」两句；事件委托原理见 4.2，跨域见 5.3。

> 面试官追问点：为什么 transform 动画比 top/left 动画流畅？应答思路：top/left 改几何信息 → 每帧回流；transform 是合成层上的矩阵变换 → 布局绘制全部跳过，GPU 直接算；will-change: transform 提前把元素提升为独立层。顺带一提副作用：合成层过多显存开销大，「能用 transform 就不用几何属性」是标准答案，能补出 will-change 的代价才算完整。

#### 4.2 事件捕获与冒泡的流程是什么？事件委托的优劣有哪些

答：一句话定调，**一个事件的生命周期是三段：捕获（从 window 向下找目标）、目标（目标元素上的回调按注册序执行）、冒泡（从目标向上回 window）——事件委托就是把回调挂在祖先节点上，等冒泡送上门来**。

**三段流程**（先画骨架）：`window → document → ... → 父节点 → 目标`（捕获）→ 目标上的回调们（目标阶段）→ `目标 → 父节点 → ... → window`（冒泡）。**addEventListener 第三参数定方向**：`true` 或 `{ capture: true }` 是捕获阶段响应（默认 false 走冒泡）；第四个常用参数 `{ once: true }`（自动解绑）与 `{ passive: true }`（见 4.3）。

**目标阶段的暗规则**（拉分点）：**目标元素上注册的回调，无论 capture 填 true 还是 false，都按「注册顺序」执行**——在目标节点上没有捕获冒泡之分，规范如此；很多人以为目标上 capture 先跑，是这题最普遍的误解。

**stopPropagation 与 stopImmediatePropagation**：前者阻止事件继续向**下一个节点**传播（同节点上已注册的其他回调照跑）；后者连**同一节点上排在后面的回调**也一并掐断。一行代码演示：

```js
btn.addEventListener('click', e => { e.stopImmediatePropagation(); });
btn.addEventListener('click', () => console.log('永远到不了'));   // 被掐
```

**事件委托**（本题的工程核心）：不逐个绑定子元素，把监听器挂在父节点，靠冒泡统一处理：

```js
list.addEventListener('click', e => {
  const li = e.target.closest('li');            // 失分点①：用 closest 找目标，防止点到 li 内部
  if (!li || !list.contains(li)) return;        //        越界保护
  if (!li.dataset.id) return;                   // 失分点②：过滤非业务元素
  handleClick(li.dataset.id);
});
```

**优劣清单**：优点三条——动态子元素**免重绑**（增删节点不用管监听器）、内存占用小（一个监听器服务 N 个元素）、批量统一逻辑好维护；局限三条——**不冒泡的事件没法委托**（focus/blur 换 focusin/focusout，mousemove 高频事件委托反而费）；**层级深的列表要 closest 逐层找**；委托逻辑与元素结构耦合，重构 DOM 时容易踩空。

收尾：三段流程 → 目标阶段暗规则 → 两 stop 的区别 → 委托骨架加优劣清单；收在一句「**委托的本质是利用冒泡把 N 份监听合并成 1 份**」；target/currentTarget 分工见 4.3。

> 面试官追问点：focus 为什么不能委托、怎么绕？应答思路：focus/blur 不冒泡（规范设计为「元素自身的事」），委托收不到；绕法是改用会冒泡的 focusin/focusout，两者语义等价只差冒泡行为。顺带一提 capture 参数对不冒泡事件的意义：capture 阶段从 window 向下，目标前的祖先都能拦到——这是「祖先要感知不冒泡事件」的另一个通道。

#### 4.3 事件对象的target与currentTarget有什么区别

答：一句话定调，**target 是「事件的起爆点」——整个传播过程不变；currentTarget 是「当前正在处理事件的节点」——捕获冒泡沿途每个节点轮流当值；两者搭配 passive 监听器，构成事件对象的三个高频考点**。

**target 与 currentTarget 的核心差异**（一行代码立住）：

```js
ul.addEventListener('click', e => {
  console.log(e.target);        // 点中的 li（或 li 里的 span）——事件从哪起爆
  console.log(e.currentTarget); // 永远是 ul——回调挂在谁身上，谁就是 currentTarget
});
```

**性质对照**：target 只读、**在整条传播链上恒定**（捕获冒泡经过八个节点，target 还是那一个 li）；currentTarget **只在回调执行期间有效**——事件流走过去了再读就是 null，所以不能把 e.currentTarget 存起来异步用（**想在异步里用监听者是谁，回调里先 `const ul = e.currentTarget` 存下来**——这是 React 合成事件池时代的同款坑）。箭头函数场景补一刀：回调里的 this === currentTarget（普通函数），箭头函数没有自己的 this，要用 currentTarget 取。

**preventDefault 与 stopPropagation 的分工**（易混点，一句话划界）：**preventDefault 管「默认行为」，stopPropagation 管「传播路径」——两个正交维度**：

| | preventDefault | stopPropagation |
|:---|:---|:---|
| 拦的是什么 | 浏览器默认动作（a 跳转、表单提交、右键菜单） | 事件继续向其他节点传播 |
| 影响谁 | 只影响默认行为 | 只影响传播 |
| 互不影响 | **阻止了传播，默认行为照发** | **阻止了默认，冒泡照走** |

典型分工场景：自定义上传——input 的 change 冒泡上报（不 stop），但拖拽区要拦掉浏览器打开文件的默认行为（preventDefault 必须调，否则拖文件直接跳页面）；「阻止链接跳转但让埋点冒泡到全局监听」也是这个分工。补一个可检查性：`e.defaultPrevented` 能查默认行为是否已被拦过——多个监听器协同时的探针。

**passive 监听器**（性能视角的必答点）：`addEventListener(type, fn, { passive: true })` 向浏览器**承诺回调不会调 preventDefault**。为什么需要：**触摸/滚轮事件里调 preventDefault 会阻止滚动，浏览器必须等回调跑完才能安心滚动——但回调里读布局、干重活，滚动就被卡住**；passive 声明「我拦不住也不拦」，浏览器立刻放心地**并行**滚动和回调——**移动端触摸流畅度的官方处方**，Chrome 对 touch/wheel 默认就是 passive（在默认 passive 的事件上调 preventDefault 会被忽略并告警）。

**三个 API 的组合拳**（工程语境收尾）：单例场景 `once: true` + `passive: true`（埋点点击、一次性引导）；滚动加载 `passive: true` 必开（见 6.2 的 scroll 监听性能）；拖拽场景 preventDefault 挡默认、stopPropagation 防外层拖拽容器打架。

收尾：答题三句话——**target 看起爆点、currentTarget 看挂载点、passive 是「不拦滚动的承诺」**；目标阶段与委托的关系见 4.2，监听器清理与内存见 7.10。

> 面试官追问点：为什么 passive 不能和 preventDefault 共存？应答思路：passive 的全部价值是让浏览器「不用等回调就能滚动」——如果还允许 preventDefault，等待就不可避免，承诺作废；所以规范规定 passive 回调里的 preventDefault 静默失效（控制台警告）。引申：需要「先判断再决定拦不拦」的场景（如左滑返回手势）不能 passive，这是流畅性与控制权的取舍，答出这层就是理解了设计而非背参数。

#### 4.4 原生DOM操作为什么慢？性能优化的手段有哪些

答：一句话定调，**DOM 操作慢的锅不在「操作本身」，在「每次操作都可能触发回流」——浏览器替你做了批处理优化（脏标记），但读写交替会让优化失效；三件武器对应三个层次：Fragment 管批量插入、离线节点管批量修改、虚拟节点管框架级最小化更新**。

**DOM 慢的三层原因**（逐层递进讲）：第一层，DOM 是 C++ 实现的重量级对象，**跨「JS 引擎 → 渲染引擎」的桥有成本**——每次 DOM API 调用都是跨界通信，属性访问、方法调用都比纯 JS 对象贵；第二层，**回流本身贵**——改几何属性让浏览器重算布局、连带重绘，一次操作可能波及整棵子树（见 4.1）；第三层（关键认知），浏览器有**脏标记优化**：连续十次改样式，回流被合并到最后一次——**理论上批量 DOM 操作不该慢**。

**那为什么实测还是慢？——因为「读写交替」击穿了脏标记**：

```js
// 十次操作，但每次读都把延迟的回流逼成同步——10 次回流
for (let i = 0; i < 10; i++) {
  el.style.width = i * 10 + 'px';
  console.log(el.offsetWidth);   // 读：此刻必须回流，拿到准确值
}
```

**本题的完整答案 = 三层成本 + 脏标记机制 + 击穿条件**，只答「触发回流」是及格线，能讲出「浏览器本来会帮你合并，是读写交替逼它现算」才是深水区。

**DocumentFragment：批量插入的离线容器**：

```js
const frag = document.createDocumentFragment();
for (const item of data) {
  const li = document.createElement('li');
  li.textContent = item;
  frag.appendChild(li);          // 插到 fragment：纯离线，不碰真实 DOM
}
ul.appendChild(frag);            // 一次性进文档——fragment 的子节点整体迁移
```

**机制**：fragment 是「轻量版 document」——往里 append **不触发回流**（不在渲染树里）；最后一次性挂载，N 次插入合并成 1 次。**对比直接 appendChild**：每次都真实插入、真实回流。适用边界：**fragment 只优化「插入」，插入的节点本身解析依然有成本**——数据量再大上虚拟列表（见 6.1）。顺带一提：**字符串 innerHTML 批量插入常常比 fragment 还快**（走解析器一次成型），但要注意 XSS 转义（见 5.2）。

**同族武器补全**：**display:none 批量改**（脱离渲染树，改完再显示——只付首尾两次回流）；**克隆替换**（clone 节点离线改完 replaceChild——老式表格重排的标准姿势）。

**history.pushState / replaceState：SPA 路由的基石**（提示要点的第三块）：**改 URL 不发请求、不刷新页面**，配合 popstate 事件实现「地址变了 → 组件切换」的前端路由：

```js
history.pushState({ page: 'detail' }, '', '/detail/42');  // 地址栏变了，页面没动
window.addEventListener('popstate', e => render(e.state.page));  // 后退/前进时重渲染
```

**与 hashchange 路由的对比**（加分点）：hash 路由（#/detail）兼容性好、不发请求天然无刷新，但带 # 不利于 SEO 与分享；pushState 的 URL 干净，**需要服务端把所有路径都兜底到入口页（history fallback）**——刷新 /detail/42 时服务器得返回 index.html 而不是 404，这是 Vue/React 路由 history 模式部署时的经典配置项。

收尾：三句话归位——**慢在跨界与回流、批处理靠脏标记但读写交替会击穿、大改用离线容器**；路由以 pushState 一句「改地址不刷新 + 服务端兜底」收束；回流细节见 4.1，超大列表见 6.1 虚拟列表。

> 面试官追问点：React/Vue 里直接操作原生 DOM 为什么是反模式？应答思路：框架维护着自己的虚拟 DOM diff 管线，直接改真实 DOM 绕过了这份「账本」——框架下一轮更新可能按旧账本覆盖你的修改（状态与视图失同步）；合规做法是 ref 拿节点在受控边界内操作。本题把 4.4 的「原生 DOM 成本」升级成了「双写冲突」——两套系统对同一份 DOM 各持一份理解，冲突只是时间问题。

#### 4.5 V8引擎的执行流程是怎样的？隐藏类与内联缓存怎么优化

答：一句话定调，**V8 的执行是「解释器打底、热点上机器码」的双层结构，性能的两大秘密武器是隐藏类（把字典对象变成 C 结构体）和内联缓存（把重复查找变成偏移量直取）**。

**执行流程四步**（先立骨架）：源码 → **Parser** 生成 AST（语法分析，早期版本还有预解析加速冷启动）→ **Ignition 解释器**生成并执行字节码（寄存器机，启动快、内存省）→ 运行中收集**类型反馈**，热点函数交给 **TurboFan** 优化编译成机器码；优化假设失效（传进来的类型变了）就**去优化（deopt）**退回字节码重跑。**双层结构的本质是「用启动速度换执行速度」**：全量编译太慢启动不起，纯解释太慢跑不起，先解释着跑、热了再上机器码。

**隐藏类（Hidden Class / Map）**：JS 对象按规范是「属性名字典」，字典查询慢；V8 给每个对象挂一个 **Map，描述「属性名 → 存储槽位」的布局**——访问变成「查一次 Map 的 offset，之后直接按偏移量取」，性能接近 C 结构体。**关键机制是转换链（transition）**：对象加属性时 V8 不新建 Map，而是沿转换树派生——**相同初始化路径的对象共享 Map**。三条最佳实践全是这条机制的推论：**构造函数里一次性初始化全部属性**（所有实例走同一条转换链、共享 Map）；**别动态加不同顺序的属性**（分叉出不同 Map，内联缓存失效）；**别 delete**（把对象打成字典慢模式，见 7.5 追问）。

**内联缓存（IC）**：每个属性访问点的字节码旁挂着**反馈向量**，记录「上次见过的 Map + 取值策略」。命中情况分三档——**单态 monomorphic**（只见一种 Map：直接内联偏移量，最快）、**多态 polymorphic**（2–4 种：逐个比对再取）、**超态 megamorphic**（超过 4 种：放弃缓存走通用查找，**性能悬崖**）。工程推论：**一个函数别处理太多形状的对象**——`format(user)` 和 `format(order)` 传两种 shape 还能多态扛住，七八种混着传直接超态；这也是「热路径函数收窄参数类型」这条优化的底层依据。

```js
// 多态悬崖的最小演示
function getX(o) { return o.x; }
getX({ x: 1 });            // 单态：起飞
getX({ x: 1, y: 2 });      // 多态：比对
getX(new Point(1));        // 又一个 shape……到第五种掉进超态
```

**GC 分代一段讲完**：新生代用 **Scavenge 半空间复制**——活对象从 From 拷到 To 空间、存活两轮晋升老生代；**适合「朝生夕死」的短命对象，成本正比于存活率而非堆大小**。老生代用**并发标记清除 + 整理**：三色标记从根集可达性出发，不可达即垃圾（解决循环引用），Mark-Sweep 清理、Mark-Compact 整理碎片；**标记并发跑、只有短暂停（Stop-the-World 收在重新标记与整理阶段）**——主线程的感知就是「偶发的小卡顿」。

收尾：答题节奏——双层结构一句、隐藏类与 IC 互为表里一句（Map 给形状、IC 记形状）、GC 分代各一句；收在总纲「**V8 用运行时类型信息赌动态性在热点上是稳定的，赌赢起飞、赌输 deopt**」；规范级深挖（标量替换、IC 反馈向量结构）见 7.5，泄漏排查见 7.10。

> 面试官追问点：为什么给对象加属性比初始化时写全慢？应答思路：初始化写全走同一条转换链、全体实例共享 Map；运行时零散加属性各自派生新 Map——既让本对象变慢（首次访问无缓存），更让消费它的函数掉档（多态→超态）。追问延伸：monomorphic 到 polymorphic 的退化是渐进的还是突变的？应答思路：反馈向量有容量上限（4 个 slot），第 5 种 Map 进来才整体清空转超态——渐进恶化、上限清零。

#### 4.6 V8的垃圾回收机制怎么运作？前端怎么避免内存泄漏

答：一句话定调，**标记清除以「从根可达」代替「有没有人引用」来定义垃圾，从根上解决循环引用；分代回收按「对象寿命」分流处理；前端防泄漏背四类高发源 + 一条纪律——「谁注册，谁清理」**。

**先讲清「为什么不用引用计数」**（史实 + 缺陷）：早期 IE 的 DOM 用引用计数——互相引用的两个对象计数永远不为零、永远不回收，**循环引用是引用计数的死穴**：

```js
let a = {}; let b = {};
a.ref = b; b.ref = a;   // 循环引用：计数互为 1
a = b = null;           // 外部引用断开，但计数仍是 1 —— 引用计数下永不回收
```

**标记清除的换脑**：从根集（全局对象、当前调用栈）出发走可达性分析——**不可达就是垃圾，哪怕你们互相抱着**。上面那对难兄难弟在标记清除下：根到不了它们，整体回收。代价是需要「暂停并遍历」，分代与并发标记都是为摊薄这个代价（见 4.5）。

**分代回收的分工逻辑**：对象寿命两极分化——绝大多数对象朝生夕死（函数内临时变量）、少数长命百岁（单例、缓存）。**新生代 Scavenge 复制式回收**：把活的从 From 拷到 To、整个 From 一把清空——**回收成本正比于存活率（死的越多越划算），短命对象的天然主场**；两轮存活晋升老生代。**老生代标记整理**：对象存活率高、复制不划算，改为原地标记清除加碎片整理，并发标记缩短停顿。**分代的本质是「按死亡率定制算法」**。

**前端四类高发泄漏源**（工程判卷核心，每类一句机制）：

| 泄漏源 | 机制 | 防御 |
|:---|:---|:---|
| 意外全局变量 | 未声明变量挂 window，根集成员永不回收 | 严格模式 + lint no-undef |
| 被遗忘的定时器 | setInterval 回调持闭包、闭包持大对象 | **clear，组件卸载必清** |
| 未解绑的事件监听 | 监听器持回调、回调持组件状态 | **removeEventListener，与 add 成对出现** |
| detached DOM | 节点移出文档但 JS 变量仍引用，整棵子树陪葬 | 移除前 `ref = null`，不把 DOM 存进长命数据结构 |

**一条总纪律**：「**谁注册，谁清理**」——SPA 组件生命周期的 onDestroy 钩子里，定时器、监听器、观察者（IntersectionObserver 等）逐个对账；**detached DOM 是最隐蔽的一类**：「从文档移除」和「JS 引用断开」是两件事，泄漏恰恰发生在只做了前者（机制全解见 7.10 的 Retainers 链路分析）。

**WeakRef/WeakMap 的正位**：把「可能有用、没死最好」的缓存挂弱引用，对象死了缓存自动失效——**它们是防泄漏的工具不是泄漏**，但 WeakRef 的 FinalizationRegistry **不可当析构用**（回调时机不确定甚至不调，见 7.10）。

收尾：答题三段式——引用计数的死穴引出标记清除、分代按死亡率分流、四类泄漏源配一条纪律；**排查工具（快照对比、分配时间线、Retainers）属于 7.10 的主场**，此处点一句「曲线先看趋势、快照再定位、Retainers 找元凶」即可。

> 面试官追问点：为什么闭包不必然泄漏、却在泄漏题里总被点名？应答思路：闭包是正常机制，短命闭包随函数返回一起回收；泄漏的充要条件是「闭包活得比需要久」——长存定时器/全局注册表攥着闭包，闭包的 Context 里又挂着大对象。答题关键是把「闭包」和「闭包的存活周期」分开表述，这句判语能把概念题答成机制题（完整版见 7.10 追问）。

#### 4.7 浏览器多进程架构是怎样的？进程与线程怎么分工

答：一句话定调，**浏览器是「多进程」的：浏览器主进程统管、每个标签页一个渲染进程（沙箱隔离）、还有 GPU/网络/插件等专职进程；渲染进程内部再分「主线程 + 合成线程 + 工作线程」——JS 只是渲染进程主线程上的住户**。

**多进程架构的分工表**（先立骨架）：

| 进程 | 职责 | 关键点 |
|:---|:---|:---|
| 浏览器主进程 | 地址栏、书签、Tab 管理、网络与磁盘调度 | 唯一常驻的「总管」 |
| 渲染进程 | 每个标签页一个：HTML/CSS/JS 执行、页面绘制 | **沙箱运行，拿不到系统权限** |
| GPU 进程 | 合成上屏、3D 加速 | 全浏览器共享一个 |
| 网络进程 | DNS、TCP、HTTP | 从主进程拆出（SOA 化演进） |
| 插件进程 | 每个插件独立 | 崩溃不连坐 |

**为什么多进程而不是多线程**（设计动机是判卷点）：①**稳定性**——一个标签页崩溃只死自己，浏览器不连坐（单进程时代一个插件崩全崩）；②**安全**——渲染进程跑在沙箱里，恶意页面拿不到文件系统与系统调用；③**公平**——每个标签页有独立的主线程，一个页面的死循环 JS 不卡别的页面。代价是内存开销（每进程一份基础运行时），Chrome 的 Site Isolation 进一步把跨站 iframe 也拆进程，防 Spectre 类侧信道。

**渲染进程内的线程分工**（本题第二判分区）：**主线程**——JS 执行、DOM 解析、样式计算、布局（事件循环跑在这里，见 2.1）；**合成线程**——把绘制好的分层交给 GPU 拼装上屏，**transform/opacity 动画可以只走合成线程，主线程被 JS 卡死时动画照样丝滑**（见 4.1 的合成层）；**光栅线程与工作线程**——分块画像素、解析 HTML/CSS；**rAF 的时机**——主线程任务排干后、渲染前（在事件循环的位置见 7.1）。

**脚本阻塞与预解析**（提示要点的最后一块）：HTML 解析器遇到无 defer/async 的 `<script>` 会**暂停解析、等下载执行完**——因为 JS 可能改 DOM，继续解析就白干；**预解析（preload scanner）**是补救：主解析器停摆时另一个线程先把后面资源的下载提前启动，**下载并行、执行串行**。`defer` 等解析完按序执行、`async` 下载完立刻插队执行——**defer 保序适合有依赖的业务脚本，async 只适合独立脚本（埋点/统计）**。`<link rel="preload">` 把预解析从启发式升级成显式声明，本质都是「**让网络与解析重叠**」。

收尾：口述节奏「进程表 → 三条设计动机 → 渲染进程内的合成线程彩蛋 → 阻塞与预解析」；收在一句「**多进程买的是隔离与安全，合成线程买的是动画不死，预解析买的是网络不闲着**」；rAF/rIC 的时机细节回看 2.5、7.1。

> 面试官追问点：为什么主线程卡死时 CSS 动画和 transform 动画还在动？应答思路：CSS 动画/transform 只改合成层的输出，由合成线程直接驱动 GPU——不经过主线程的布局绘制管线；而 JS 驱动的 top/left 动画每帧都要主线程算布局，主线程一卡全部冻结。这也是「动画优先 CSS/transform 实现」的架构级理由，能从线程分工答到这条实践就闭环了。

#### 4.8 四种前端存储方案怎么选？各自的差异与场景是什么

答：一句话定调，**四种存储按「容量、生命周期、网络行为」三轴选型：cookie 是「会随请求旅行的老古董」，Web Storage 是「同源的字符串抽屉」，IndexedDB 是「浏览器里的真数据库」——token 存哪的争论，本质是 XSS 与 CSRF 的攻防题**。

**四方案对照表**（判卷骨架）：

| | cookie | localStorage | sessionStorage | IndexedDB |
|:---|:---|:---|:---|:---|
| 容量 | 4KB | 5–10MB | 5–10MB | 数百 MB 起 |
| 生命周期 | 可设过期；**会话 cookie 关浏览器即失** | 永久（手动清） | 标签页会话 | 永久 |
| 随请求发送 | **每个同源请求自动带**（4KB × 请求数的带宽税） | 不带 | 不带 | 不带 |
| API | document.cookie（拼接字符串反人类） | 同步 KV | 同步 KV | **异步、事务、索引、游标** |
| 场景 | 服务端要读的状态（会话 ID） | 纯前端持久配置 | 表单草稿/一次性状态 | 离线数据、大缓存、PWA |

**cookie 三块冷知识**（拉分点）：**HttpOnly** 让 JS 读不到——XSS 偷不走（但 CSRF 还能带着它跑，两场攻防见 5.2）；**SameSite=Lax/Strict** 限制跨站请求携带——现代浏览器默认 Lax，直接把传统 CSRF 打掉大半；**Domain/Path** 决定作用域，`.a.com` 全子域共享。localStorage 的两条纪律：**只能存字符串**（对象要 stringify，取回要 parse）；**同步 API 阻塞主线程**——大 JSON 频繁读写会卡，大块数据该去 IndexedDB。

**token 存哪：一场攻防推演**（本题主战场，别只报结论）：

| 方案 | 中 XSS | 中 CSRF | 短板 |
|:---|:---|:---|:---|
| localStorage + 请求头带 token | ❌ 脚本可读，偷走即冒用 | ✅ 不自动随请求发 | 一旦 XSS 全盘失守 |
| HttpOnly cookie | ✅ JS 读不到 | ❌ 自动携带，CSRF 可乘 | 需要 SameSite/CSRF token 配合 |

**正解的完整形态**：**短令牌放内存（刷新即失）+ 刷新令牌放 HttpOnly + SameSite cookie**——XSS 偷不到刷新令牌、CSRF 被 SameSite 挡住、页面刷新靠内存令牌过期后用刷新令牌换新；这是「都不完美、组合防御」的教科书答案，**能讲出三层而不是二选一就是专家线**。

**大数据量：IndexedDB 的最小用法**（异步心智先立住）：

```js
const db = await new Promise((res, rej) => {
  const req = indexedDB.open('app-db', 1);
  req.onupgradeneeded = e => e.target.result.createObjectStore('cache', { keyPath: 'key' });
  req.onsuccess = e => res(e.target.result);
  req.onerror = () => rej(req.error);
});
const tx = db.transaction('cache', 'readwrite');
tx.objectStore('cache').put({ key: 'articles', data: bigPayload });  // 事务写入
```

**工程要点**：**异步事件驱动**（不是 Promise 风格，常见轻封装或 idb 库抹平）；**事务边界**——同一事务内的操作原子化；**对象仓库 + 索引**支持按键/按索引高效查询，不是 localStorage 那种全量读出再过滤；同源隔离、容量按需申请。**选型一句话：结构化、可查询、上 MB 级就该 IndexedDB**，localStorage 只配放配置和轻缓存。

收尾：三轴选型表 → token 攻防三层 → IndexedDB 最小心智；收在「**cookie 为服务端而生、Storage 为前端而生、IndexedDB 为数据而生**」一句分工；XSS/CSRF 机制全解见 5.2。

> 面试官追问点：localStorage 为什么不能设置过期时间、要过期怎么补？应答思路：规范层面它就是「同源持久 KV」，没有过期语义；补法是「存的时候带时间戳、读的时候判断惰性删除」的包装层——注意这是约定不是隔离，任何同源脚本都能读；顺带一提：多标签页竞态用 storage 事件同步（一个标签页写入会广播其他标签页），这是 localStorage 少有的跨页通信彩蛋。

# 5.网络与安全

#### 5.1 强缓存与协商缓存的流程是什么？缓存策略怎么配置

答：一句话定调，**强缓存「不问服务器直接用」，协商缓存「问一句没变再用」——两级缓存的分界线是「发不发请求」；配置策略一句话：带 hash 的静态资源走强缓存长存，HTML 入口文件走协商缓存保更新**。

**两级缓存先立骨架**（判卷第一步是分清谁在哪一级）：

| | 强缓存 | 协商缓存 |
|:---|:---|:---|
| 头字段 | `Cache-Control: max-age=31536000`（`Expires` 是 HTTP/1.0 遗产，时间受本机时钟影响，被前者覆盖） | `ETag/If-None-Match`、`Last-Modified/If-Modified-Since` |
| 要发请求吗 | **不发**，直接命中本地 | **发**（带上缓存的标识），服务器答 304 才用本地 |
| 状态码 | 200（from cache） | 304 Not Modified（无响应体） |

**两级是串联的**：先查强缓存，过期了才进入协商——协商的「请求」里带着 ETag（优先）或 Last-Modified，服务器比对没变就回 304，变了回 200 加新资源。**ETag 为什么优先**：Last-Modified 只精确到秒——「一秒内改了两次」识别不出；文件内容没变但 mtime 变了（重新部署 touch 一下）会误判失效；ETag 按内容算指纹，能识别「内容没变时间变了」和「时间没变内容变了」两类边角。

**from memory cache 与 from disk cache**（DevTools 里两行蓝字，高频追问）：**memory cache** 是渲染进程内存里的缓存——**快、但标签页关了就没、且不检查过期（preload 场景故意如此）**；**disk cache** 是磁盘缓存——慢一档、但跨会话存活。**谁吃 memory 谁吃 disk 有经验规律**：小文件、当前会话刚用过的、图片倾向 memory；大文件、跨会话的倾向 disk。刷新（F5）时两者都会用；**Ctrl+F5 强刷会带 `Cache-Control: no-cache` 请求头绕过本地缓存，直奔服务器**。

**缓存策略的工程配置**（本题主战场，按资源类型分三档）：

1. **带内容 hash 的静态资源**（`app.a3f9c2.js`）——`Cache-Control: max-age=31536000` 一年强缓存：**hash 变了 URL 就变了，天然触发新请求，长存与更新两全**（这是构建工具给文件名加 hash 的全部意义）；
2. **HTML 入口文件**——`Cache-Control: no-cache`（注意：不是 no-store！）**走协商缓存**：HTML 里引用的 hash 文件名是「资源地图」，地图必须最新——地图每次都问服务器（304 便宜），地图指向的资源放心长存；
3. **永远新鲜的 API**——`no-store` 或短 max-age，按业务容容忍度定。

**no-cache 与 no-store 的划界**（最常答错的一对）：**no-cache 不是不缓存**，是「缓存前必须协商验证」（每次都发请求，304 的话用本地——省的是响应体不是请求）；**no-store 才是真不缓存**（敏感数据、一次性响应）。一个字之差，语义天壤。

**深水区两条**：**协商缓存 304 的隐性成本**——304 虽无响应体，但仍有 TCP/TLS 握手与 RTT，高并发下「每次都问」也贵，所以 HTML 之外能 hash 的都 hash；**Service Worker 是第三级缓存**——可编程的请求拦截层（fetch 事件里自己决定回缓存还是回网络），PWA 离线能力的地基，与两级缓存的关系是「**SW 在最外层先拦**」，能答出三级结构就是加分位。

收尾：口述节奏「两级对照表 → ETag 优先的两理由 → 三档配置 → no-cache/no-store 划界」；收在一句「**hash 给静态资源长存的底气，协商给入口文件保新的通道**」。

> 面试官追问点：为什么刷新页面时有些资源 200 from cache、有些 304？应答思路：F5 的行为是「对主文档带 max-age=0 重新验证，子资源按各自策略」——所以 HTML 大概率 304（协商生效），一年强缓存的 JS 直接 200 from memory/disk cache（强缓存生效，根本没发请求）；只有强刷 Ctrl+F5 才整体绕过。能从「刷新策略只作用于主文档」这层解释，就不是背表格而是懂流程。

#### 5.2 XSS与CSRF的攻击原理是什么？各自的防御手段有哪些

答：一句话定调，**XSS 是「往你的页面里注入我的脚本」——防的是脚本执行（转义 + CSP）；CSRF 是「借你的 cookie 冒充你发请求」——防的是请求伪造（SameSite + CSRF token + 校验来源）；两者的组合拳（payload 是 img 的 CSRF、require-trusted-types）是拉分位**。

**XSS 三型 + 一个共同本质**：存储型（评论里存脚本、所有访客中招——危害最大）、反射型（恶意链接把 payload 拼进响应，一次点击一次伤害）、DOM 型（**全程不碰服务器**：URL 参数被 innerHTML 直接吃进去）。**本质一句话：不可信数据进了「可执行位置」**——前两型是服务器把数据拼进 HTML，DOM 型是前端把数据塞进能解析 HTML 的 API。

**XSS 防御三件套**：

1. **输出转义**（治本）：按落点转义——进 HTML 体转 `<>&"`、进属性转引号、进 URL 参数 encode；**框架的内建转义就是为什么 React 的 `{}` 和 Vue 的 `{{}}` 默认安全**，漏洞几乎都出现在 `dangerouslySetInnerHTML` / `v-html` 这类「显式放弃转义」的口子上；
2. **CSP**（兜底）：`Content-Security-Policy: script-src 'self'`——**即使注入成功，非白名单脚本也不执行**；进阶配置 `strict-dynamic` + nonce 允许自己人的内联脚本；
3. **避免直接拼 HTML**：富文本用 DOMPurify 白名单过滤，而不是正则黑名单。

**CSRF 的攻击链**（先讲清「借 cookie」的机制）：你在 bank.com 登录着 → cookie 还挂在那 → 访问 evil.com，它的页面里藏着 `<img src="bank.com/transfer?to=hacker&amount=10000">` → **浏览器对 bank.com 的请求自动带上你的 cookie** → 服务器只认 cookie 不认人，转账完成。**关键前提**：cookie 自动携带 + 请求能「跨站自动发起」（img/form/get 都行）。**CSRF 与 XSS 的分界**：XSS 是「在你页面里执行我的代码」（拿到 JS 权限什么都干得了），CSRF 是「在别的网站发你的请求」（**没有 JS 权限，只能发盲请求、读不到响应**）——这就是为什么 XSS 危害更全、CSRF 只能打「简单请求能完成的操作」。

**CSRF 防御三件套**：

1. **SameSite cookie**（当代首选）：`SameSite=Lax` 跨站子请求（img 这种）不带 cookie、顶层导航的 GET 带——**浏览器默认已是 Lax，传统 CSRF 大半失效**；Strict 全拦但连「从外站点链接进来」都丢登录态，业务上常嫌太狠；
2. **CSRF token**（经典双保险）：表单里埋服务器签发的随机 token，提交时校验——evil.com 拿不到 token（读不到你的页面），请求里没有它就被拒；**为什么 token 有效而 cookie 无效**：token 走的是「显式数据」，跨站拿不到；cookie 走的是「自动携带」，这是攻击的全部空间；
3. **校验 Origin/Referer**：请求头里看来源域名，不是本域拒绝——简单，注意 Referer 可能被策略去掉，Origin 更可靠。

**组合与拉分位**：**CORS 不能防 CSRF**——CSRF 用的 img/form 根本不受同源策略约束（同源策略只挡「读响应」，不挡「发请求」），别把两套机制混为一谈（见 5.3）；**「payload 是 img 的 CSRF」**是两者杂交的诡异攻击（cookie 里有 `)` 之类会破坏 img 的语法、注入 `onerror` 执行脚本）；**点击劫持**（clickjacking）是第三种「借手」攻击：透明 iframe 叠在按钮上让你亲手点——**防它靠 `X-Frame-Options: DENY` / CSP frame-ancestors**，不靠前两套。

收尾：答题给一张攻防对照表——**XSS：注入与转义；CSRF：借用与验明正身；点击劫持：叠层与禁止嵌套**；token 存储的三层防御（与 4.8 互为表里）作为收束彩蛋。

> 面试官追问点：为什么 SameSite=Lax 之后还需要 CSRF token？应答思路：Lax 挡了「跨站子资源」但放行「顶层 GET 导航」——攻击者诱导你点链接跳到 bank.com 的转账 GET（改密码、绑定手机号这类「一个 GET 就能干坏事」的接口依然可打）；再考虑老浏览器不支持 SameSite、子域信任关系被滥用等边角，token 作为「不依赖 cookie 语义」的独立校验层依然是纵深防御的一环。答出「Lax 放行顶层 GET」这个缺口，就证明真的理解 SameSite 的三档语义。

#### 5.3 跨域问题怎么产生的？多种解决方案的原理是什么

答：一句话定调，**同源策略只限制「读」，不限制「发」——跨域的本质是浏览器拦了响应；CORS 是官方白名单方案（预检 + 响应头放行），代理与 JSONP 是它的两条替代路径**。

**先立同源策略的准确边界**（大多数误解的源头）：**同源 = 协议 + 域名 + 端口全一致**（`a.com` 与 `www.a.com` 也不同源）。它管的是**脚本的读权限**：XHR/fetch 读跨域响应被拦、DOM 访问跨域 iframe 被拦、cookie/localStorage 按源隔离。**它不管的**：发请求（img/script/form 谁都能发）、**样式与脚本的「执行」**（CDN 上的 JS 照样跑）。**「能发不能读」正是 CSRF 能打、而 CORS 能防 XSS 式数据窃取的原因**（见 5.2）。

**CORS 的两条通道**（判卷核心是分清「简单请求」与「预检请求」）：

| | 简单请求 | 预检请求 |
|:---|:---|:---|
| 条件 | GET/POST/HEAD + 安全头部 + Content-Type 限三种（text/plain、multipart/form-data、**application/x-www-form-urlencoded**） | 不满足任一条——**最常见触发：JSON 的 `Content-Type: application/json`**、自定义 header、PUT/DELETE |
| 流程 | 直接发，浏览器看响应头 `Access-Control-Allow-Origin` 决定给不给 JS 读 | **先发 OPTIONS 探路** → 服务器回「允许的源/方法/头」→ 通过才发真请求 |

**OPTIONS 预检的全流程口述**：浏览器自动发 `OPTIONS` + `Access-Control-Request-Method/Headers` → 服务器答 `Access-Control-Allow-Origin/Methods/Headers` + `Max-Age`（**预检结果可缓存，Max-Age 内免重复探路**——高频接口必配，否则每个请求双倍往返）。**为什么 JSON 要预检**：预检的历史使命就是防「新增的能力」被滥用——text/plain 谁都发得动，application/json 是 fetch/XHR 时代的「新能力」，先问一句再放行。

**withCredentials 与 `*` 的死结**（拉分点）：跨域请求默认不带 cookie——`xhr.withCredentials = true`（fetch 是 `credentials: 'include'`）才带；**一旦带凭证，服务器不能用通配 `Access-Control-Allow-Origin: *`，必须精确回显当前 Origin**，且要配 `Allow-Credentials: true`。**「带 cookie 的跨域 + 通配符」是永远打不通的组合**，服务器必须动态读请求 Origin 再回写——这题答出死结原因（防任意站点携 cookie 拿数据）就是深水区。

**三条替代路径**：

1. **JSONP**（历史方案）：`<script>` 不受同源限制 → 服务器把数据裹在 `callback(data)` 里返回 → 前端定义 callback 接住。**局限四条**：只支持 GET、错误处理原始（404/500 静默失败）、**信任服务器可执行任意代码（XSS 面）**、被 CORS 取代后仅存于老接口；
2. **Nginx 反向代理**（开发与线上都常用）：前端和接口都走 `a.com`，Nginx 把 `/api/*` 转发给 `b.com`——**对浏览器来说根本没跨域**（同源策略是浏览器机制，服务器之间没有「跨域」一说）；**proxy 是「藏跨域」、CORS 是「承认跨域」**，devServer.proxy 就是开发环境的同款；
3. **postMessage**（跨窗口通信）：iframe/新窗口与父页面的官方通道——`target.postMessage(data, origin)`，收方校验 `event.origin` 再用。**安全铁律是「发方指定精确 origin、收方校验 origin」**，两边都用 `*` 就等于裸奔（这是 postMessage 事故的标准根源）。

**跨域的三个冷辨析**（加分收尾）：**资源跨域 ≠ 数据跨域**——CDN 的 JS 能跑是「脚本执行不受限」，`crossorigin` 属性才让它「以 CORS 方式取」从而拿独立缓存与报错详情；**服务器不拦跨域**——服务器该响应照响应，是浏览器把响应扣下了（所以 Postman 永远「没有跨域问题」）；**开发环境的「跨域报错」九成是代理没配对**——解法在 devServer.proxy 的 pathRewrite，不在后端 CORS 头。

收尾：口述节奏「同源边界 → 简单/预检对照表 → withCredentials 死结 → 三条路径定位（官方/隐藏/窗口）」；收在「**跨域是浏览器的防线，不是服务器的——所以所有方案都在「让浏览器放心」上做文章**」。

> 面试官追问点：为什么 CORS 预检用 OPTIONS 而不是直接发真请求看响应头？应答思路：预检的目的是「在真请求产生副作用前问清楚」——PUT/DELETE 带自定义头直接发出去，服务器已经处理了（转账已发生），浏览器再拦响应毫无意义；OPTIONS 是无语义的安全探路，通过才允许真请求。答出「拦响应拦不住副作用，必须前置拦截」这个设计逻辑，就理解了 CORS 的本质。

#### 5.4 WebSocket的原理是什么？实时方案怎么做选型

答：一句话定调，**实时方案按「谁付成本」排序：轮询是客户端傻问、长轮询是服务器装忙、SSE 是服务器单向推、WebSocket 是全双工专线——心跳保活 + 指数退避重连，是把 WebSocket 从「能连」变成「可靠」的两块拼图**。

**四种方案的本质与成本**（对照表先立住）：

| 方案 | 机制 | 方向 | 成本与短板 |
|:---|:---|:---|:---|
| 短轮询 | 客户端定时发请求 | 单向（拉） | 大量空响应、实时性 = 轮询间隔、服务器 QPS 被间隔绑架 |
| 长轮询 | 请求挂住，有数据才回 | 单向（拉装推） | 每次推送后要重建请求；挂连接耗服务器资源 |
| SSE | HTTP 长连接 + `text/event-stream` | **服务器→客户端单向** | 单向限制、HTTP/1.1 有连接数上限（默认 6）；**自带重连（Last-Event-ID 续传）与文本协议的简单** |
| WebSocket | 升级成独立 TCP 通道 | **全双工** | 需要单独的心跳/重连设计（协议本身不管）；代理/防火墙对 Upgrade 的兼容坑 |

**选型口诀**：只需要服务器推（行情、通知、AI 流式输出）——**SSE 足够且更简单**（fetch/EventSource 原生支持、过 HTTP 基础设施）；双向高频（协作编辑、游戏、即时通讯）——WebSocket；兼容老环境或要求极简——长轮询兜底。**「SSE 能解决的不上 WebSocket」是现代选型的分水岭**——尤其大模型流式回复场景，SSE 已成事实标准。

**WebSocket 握手**（一次 HTTP 升级的仪式）：客户端发 GET 带 `Upgrade: websocket` + `Sec-WebSocket-Key`（随机 base64）→ 服务器回 **101 Switching Protocols** + `Sec-WebSocket-Accept`（Key + 固定 GUID 做 SHA-1 再 base64——**防普通 HTTP 服务器误答的暗号校验**）→ 从此这条 TCP 不再说 HTTP。**能答出「WebSocket 复用 HTTP 握手是为了过 80/443 端口和现有中间件」这个设计动机**（新端口会被企业防火墙拦死）是加分位。

**心跳保活 + 断线重连**（工程判卷核心，给骨架）：

```js
class HeartbeatWS {
  connect() {
    this.ws = new WebSocket(url);
    this.ws.onopen = () => this.startHeartbeat();     // 连上就开始心跳
    this.ws.onmessage = e => this.resetHeartbeat();   // 任何消息都算活着
    this.ws.onclose = () => this.reconnect();         // 断线进入重连
  }
  startHeartbeat() {
    this.timer = setInterval(() => {
      if (this.missed++ >= 2) return this.ws.close(); // 两次没回音：判定假死，主动断开触发重连
      this.ws.send('ping');                           // 服务端约定回 pong
    }, 30000);
  }
  reconnect() {
    const delay = Math.min(30000, 1000 * 2 ** this.attempts++) + Math.random() * 500;
    setTimeout(() => this.connect(), delay);          // 指数退避 + 抖动（同 2.5）
  }
}
```

**为什么要心跳**（不是多余的仪式）：TCP 半开连接（网线拔了、NAT 超时）**不会触发 onclose**——你以为连着，其实早断了；应用层 ping/pong 是唯一可靠的「死亡探测」；**重连用指数退避**：服务器崩溃时全员秒重连是重连风暴（同 2.5 的重试逻辑），**连上后重置 attempts、补发离线期间的消息**（配合服务端消息序号做补拉）才算完整方案。

**fetch 与 axios**（提示要点的附带项，差异四条）：**拦截器**——axios 有请求/响应拦截器（token 注入、错误统一处理的前端中间件），fetch 要自己包一层；**取消**——axios 用 AbortController（新版本）或 cancel token，fetch 原生 signal；**自动 JSON**——axios 自动转换，fetch 要手动 `.json()` 且**它对 4xx/5xx 不 reject**（只有网络错误才 reject，`res.ok` 要自己判——最著名的坑）；**兼容性**——fetch 原生但老 IE 不支持，axios 全家桶。**一句话总结：fetch 是底层原语，axios 是带拦截器和转换器的工程封装**——框架自带请求库（TanStack Query 封装 fetch）正在让这道题变成历史题。

收尾：口述节奏「四方案表 → SSE/WebSocket 分水岭 → 握手暗号 → 心跳重连骨架」；收在「**选型看方向与频率，可靠性靠心跳与退避**」两句；重试的通用范式回看 2.5。

> 面试官追问点：SSE 为什么在 HTTP/1.1 下有连接数限制、HTTP/2 呢？应答思路：HTTP/1.1 每个并发请求占一条 TCP，浏览器对同域最多 6 条——开几个 SSE 标签页就把额度吃光；HTTP/2 一条 TCP 跑多个 stream，「连接数限制」问题消失。这也解释了为什么 SSE 在 HTTP/2 时代重新翻红——老基础设施的短板被新协议自然修掉，能从协议演进讲到选型变化就是深水区。

#### 5.5 前端错误捕获的手段有哪些？监控上报方案怎么设计

答：一句话定调，**错误捕获是一张「四类错误 × 四个入口」的矩阵：同步错误、异步错误、Promise 错误、资源错误各有专属入口——try/catch 只覆盖矩阵的一个角；上报方案的核心是「不丢、不堵、能定位」，SourceMap 负责「能定位」**。

**错误分类与捕获矩阵**（判卷骨架，逐格讲）：

| 错误类型 | 捕获入口 | 备注 |
|:---|:---|:---|
| 同步 JS 错误 | try/catch（局部）；**window.onerror**（全局兜底） | onerror 拿到 message/source/lineno |
| 异步回调错误（setTimeout 内 throw） | **window.onerror**（try/catch 罩不住） | 跨调用栈的错误，局部 try 无能为力 |
| Promise 未处理拒绝 | **unhandledrejection**（onerror 也不管） | 挂了 catch 的不触发；触发时已无法挽回，只能记 |
| 资源加载失败（img/script 404） | **捕获阶段的全局监听**（`addEventListener('error', fn, true)`） | 事件不冒泡，必须 capture 才能全局收 |
| iframe 内错误 | iframe 内自己的 onerror + postMessage 转发 | 跨 window 不上浮 |

**「try/catch 不能捕获什么」**（本题最经典的辨析）：try 只覆盖**同步执行路径 + await 的等待点**——setTimeout 回调、事件回调里的 throw 发生在「另一个调用栈」，try 块早就退出了；Promise 的 reject 如果被 .catch 接走，try/catch 也看不见。**结论：局部 try/catch 管「预期内的错误处理」，全局监控必须靠 onerror + unhandledrejection + capture error 三件套**——一个是业务分支，一个是安全网，职责不能互相替代。

```js
window.addEventListener('error', e => {
  if (e.target !== window) report({ type: 'resource', src: e.target.src }); // 资源错误
  else report({ type: 'js', msg: e.message, stack: e.error?.stack });        // 脚本错误
}, true);                                                                     // 必须 capture
window.addEventListener('unhandledrejection', e => report({ type: 'promise', reason: e.reason }));
```

**SourceMap 还原**（线上报错「能定位」的关键）：构建时生成 `.map` 文件，**线上不部署 map（防源码泄露）**，报错信息只有 `app.a3f9c2.js:1:8457`；上报存 stack 原文，**服务端用 source-map 库离线还原**成源码行列。两条工程细节：**跨域脚本的错误信息会被脱敏为 "Script error."**——脚本要配 `crossorigin` 属性 + CORS 响应头才能拿到完整栈（见 5.3）；**构建产物按版本归档**——hash 文件名与对应 map 都留存，三个月后的报错也能还原。

**上报方案的三条设计原则**（工程深水区）：

1. **不丢**：**sendBeacon 优先**——页面卸载时 fetch/XHR 会被浏览器取消，`navigator.sendBeacon(url, data)` 专为「临终遗言」设计（异步不阻塞卸载、浏览器保证送达）；兜底顺序：sendBeacon → `fetch(url, { keepalive: true })` → Image 打点（1×1 gif，最古老也最皮实）；**上报失败本地缓存**——存 localStorage，下次启动补报；
2. **不堵**：**采样与批量**——同一 stack 聚合去重（只报首次 + 计数）、批量合并上报、**采集自身失败要静默**（监控不能成为新 bug）；
3. **能归因**：**错误指纹**——stack 归一化（去行列号、取函数链）做 hash 做主键；上报时带上版本号、用户行为栈（报错前最后 20 个动作）、灰度标记——「捕获 → 定位 → 归因」三步，前两步在客户端，第三步在平台。

**埋点方案顺带一句**（提示要点的附带项）：代码埋点（业务事件，精确但侵入）、全埋点（监听全量事件自动上报，量大声粗）、可视化埋点（圈选配置，折中）——**错误监控是埋点体系里优先级最高的一个通道**，它不需要业务定义、永远值得全量上报。

收尾：口述节奏「矩阵表 → try/catch 边界 → SourceMap 与 Script error 脱敏 → 上报三原则」；收在「**try/catch 是业务分支，全局三件套是安全网，sendBeacon 是临终遗言**」。

> 面试官追问点：Script error 是怎么产生的、为什么需要 crossorigin？应答思路：跨域脚本抛的错，出于同源策略浏览器只给一个脱敏的 "Script error."（不给细节，防止页面探听脚本内部）——但这对监控是灾难；脚本加 `crossorigin="anonymous"` 后以 CORS 方式加载，服务器配好 Allow-Origin，浏览器认为「你被授权知道了」，返回完整栈。能讲出「这是同源策略在错误信息上的应用」就点中了本质。

# 6.性能与高频场景题

#### 6.1 JS运行时性能怎么优化？长任务与内存怎么处理

答：一句话定调，**长任务优化是「先测量后拆分」：Performance 面板找红色长条，能砍则砍、砍不掉用时间切片让出主线程；大数据量渲染的正解是虚拟列表——只渲染视口内的 DOM；内存问题则回到「曲线 → 快照 → Retainers」三板斧（7.10）**。

**第一步：识别长任务**（先测量，判卷的关键态度）：**Performance 韻板里红色长条 = 超过 50ms 的长任务**（RAIL 模型给的红线：用户感知卡顿的门槛）；代码侧用 `PerformanceObserver` 监听 `longtask` 条目可以**线上自动上报**长任务时长与归属。**为什么 50ms**：事件循环里任务超 50ms，用户的输入响应就被推迟到可感知——「卡」的定义不是慢，是「我点了没反应」。

**第二步：拆分方案三选**（按侵入度排序）：

```js
// ① 纯切片：大计算拆批，每批之间让出主线程（输入、渲染都能插进来）
async function processChunked(items) {
  const CHUNK = 1000;
  for (let i = 0; i < items.length; i += CHUNK) {
    doHeavyWork(items.slice(i, i + CHUNK));
    // 让权：宏任务间隔，给事件循环喘息窗口
    await new Promise(r => setTimeout(r));        // 或 scheduler.yield()（新 API）
    // 更精细：rIC 里干低优先级杂活（见 2.5），但 deadline 到必须收工
  }
}
// ② 搬家：把纯计算扔给 Web Worker——主线程只收结果，卡顿从根上消失
const worker = new Worker('heavy.js');
worker.postMessage(bigData);
worker.onmessage = e => render(e.data);
// ③ 原生 API：isInputPending 配合让权——「有输入等待就立刻让」，比盲等更聪明
```

**选型口诀**：数据转换、解析、加密这类**纯计算优先 Worker**（并行还彻底）；必须摸 DOM 的逐项处理用切片；新项目直接关注 `scheduler.yield()` 的落地进度。**Worker 的三个门槛**：不能碰 DOM、数据要走结构化克隆（函数传不过去，见 7.7）、通信本身有成本（小任务搬过去反而慢）。

**虚拟列表原理**（大数据量渲染的正解）：**万行数据不造万个节点，只造视口里的十几个**。三要素——**可视区高度/滚动位置 → 算出「起止索引」→ 只渲染这个窗口的条目**；两个配套：上下各留 `overscan` 几条缓冲（快速滚动不白屏）、**用总高度撑起滚动条**（一个 div 占位 height = total × itemHeight，滚动比例才是真的）。三个工程坑：**不定高条目**要预估 + 渲染后实测修正（高度缓存表）；**滚动位置锚定**（顶部插入新数据时 scrollTop 要补偿，否则跳动）；**快速滚动的白屏**靠 overscan + 骨架兜底。原理一句话：**虚拟列表把「渲染成本」从数据量 O(n) 降到视口 O(viewport)**——React-virtuoso、vue-virtual-scroller 都在这套骨架上做加固。

**rAF 与防抖节流的配合**（提示要点的第三块）：**分频用节流、对帧用 rAF**——scroll 触发的高频计算，先节流到 ~16ms 档已经够用；**要和渲染严格同步的计算（滚动进度条、粘性定位）放进 rAF**——保证「一帧一算」，不浪费帧也不抢帧（时机细节见 2.5、7.1）。典型组合：`window.addEventListener('scroll', throttledHandler, { passive: true })`——**passive 必开**（见 4.3），节流降频、rAF 对帧，双管齐下。

**内存问题的排查**不在本题重复展开——**曲线（趋势）→ 快照（对象）→ Retainers（元凶）**的三板斧全解见 7.10，此处只答一句定位：**长任务管「CPU 卡」、内存管「越来越卡」**——Performance 的内存锯齿整体上扬是后者的第一信号。首屏、图片、构建层面的优化属于工程化专题，见前端篇。

收尾：口述节奏「50ms 红线 → 切片/Worker/新 API 三选 → 虚拟列表三要素三坑 → rAF+节流配合」；收在「**性能优化先测量后动手，长任务拆的是时间，虚拟列表裁的是空间**」一句对仗。

> 面试官追问点：为什么切片能解决卡顿，明明总耗时没变？应答思路：卡顿的体验问题是「主线程被连续霸占，输入响应排不上队」——切片不减少总计算量，但每批之间事件循环获得调度窗口：用户的点击、渲染的合成都能插队执行。总时长可能略增（切换开销），但「可交互性」恢复——这是「吞吐」与「延迟」的经典取舍，能答出这两个词就是性能观的及格线。

#### 6.2 滚动加载与懒加载怎么实现？方案演进与选型是什么

答：一句话定调，**滚动加载的现代答案是 IntersectionObserver（免监听、免计算、回调只在进出视口时触发），scroll 监听是它的历史形态；图片懒加载的演进终点是 `loading="lazy"` 原生属性；回到顶部则藏着「性能与手感」的小乾坤**。

**滚动加载：两种实现正面对比**（判卷核心是讲清「为什么淘汰 scroll」）：

| | scroll 监听 + 节流 | IntersectionObserver |
|:---|:---|:---|
| 机制 | 每次滚动都触发回调 → 节流降频 → **自己算** getBoundingClientRect 判断位置 | 观察者模式：**浏览器在合适时机回调**「目标进出视口」 |
| 成本 | 高频触发 + **每次读布局（可能强制回流，见 4.1）** | 回调低频、**计算在浏览器合成线程做，不占主线程** |
| 细节负担 | 手动节流、passive、边界判断（滚动到底差多少 px）、卸载清理 | 一句 unobserve 清理，阈值 rootMargin 提前预加载 |

```js
const io = new IntersectionObserver(([entry]) => {
  if (!entry.isIntersecting) return;
  loadMore();                                  // 进视口才加载
  io.unobserve(sentinel);                      // 一次性哨兵：加载完就撤（无限列表则重新 observe 新哨兵）
}, { rootMargin: '200px' });                   // 提前 200px 触发——用户还没滚到就开始加载
io.observe(document.querySelector('.sentinel'));  // 观察列表底部的哨兵元素
```

**两条工程细节**：**rootMargin 的预加载量**是体验的关键——0px 意味着「滚到底了才开始请求」，用户必然看见 loading；**iOS Safari 12.1 以下没有 IO**，老项目要 polyfill（内部退化为 scroll 监听）。「**能不监听就不监听，要回调不要轮询**」——这是 IO 相对 scroll 的架构级优势。

**图片懒加载三代演进**（讲演进=讲原理的思路）：

1. **事件时代**：scroll + getBoundingClientRect，img 的 `data-src` 存真地址、进视口时 `img.src = dataset.src`——一切手动，节流、防抖、回流的坑全踩一遍；
2. **IO 时代**：观察 img 本身，进视口换 src——**「进视口」的判断交给浏览器**，代码剩三行；
3. **原生时代**：`<img loading="lazy">` 一行属性——浏览器自己决定加载时机（**距离视口一定距离就开始，比 IO 版更早、更省心**），配 `decoding="async"` 解码不占主线程。**原生方案的边界**：加载时机不可精细控制（没有「提前 500px」可调）、兼容性已覆盖主流但老项目仍需降级——**新项目默认原生、精细控制用 IO** 是当代选型。

**配套小件**：占位防抖动——**宽高比占位（aspect-ratio 或 padding-top 百分比）**，图片加载前后布局不跳；加载失败兜底（onerror 换默认图）；CLS（布局偏移指标）的优化项里这一条占大头。

**一键回到顶部**（小题，但有两档答案）：普通版 `window.scrollTo({ top: 0, behavior: 'smooth' })`——**平滑滚动由浏览器在合成线程执行，成本低、手感好**；但**超长列表的 scrollTo 慢是因为渲染追不上滚动**——虚拟列表场景下更好的做法是**直接重置 startIndex 再 scrollTo(0, auto)**：「跳」过去再渲染，比滚过去快十倍。**deep 一层的通用规律：平滑滚动适合短距离（展示），瞬时重置适合长距离（操作）**——本质还是「渲染成本」与「体验连续性」的取舍。

收尾：口述节奏「scroll vs IO 对照 → 三代懒加载演进 → 回到顶部的两档」；收在一句「**滚动类优化的主线是：从『我盯着滚动条』到『浏览器通知我』**」——IO 与 loading=lazy 都是这条主线的产物；节流回看 3.2，长任务回看 6.1。

> 面试官追问点：IntersectionObserver 的回调为什么说「不占主线程」？应答思路：视口交叉的持续计算（每帧都变）由浏览器在内部完成——具体在合成线程层面做位置追踪，只有「状态变化」（进/出）才回调主线程：高频的「算」在浏览器内部，低频的「通知」才给 JS。对比 scroll 监听是「高频全给 JS、自己算」——一句「把高频计算关进浏览器，只把状态变化暴露给 JS」就是本质答案。

# 7.深度精讲（语言机制与V8口述版）

> 说明：本章是核心题的口述版深度精讲，讲到 ECMA 规范步骤与 V8 引擎实现层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

### 7.1 事件循环的执行顺序怎么定？宏任务与微任务差在哪

答：一句话定调，**微任务队列是「每次 JS 调用栈清空后必须排干」的义务，宏任务是「一次一件」的权利，事件循环的全部规则就这两条**。

**浏览器的执行模型**（先立骨架）：一次 tick = 取一个宏任务执行 → **清空整个微任务队列**（包括执行微任务过程中新入队的微任务）→ 必要时渲染（rAF 回调 → style/layout/paint）→ 下一个宏任务。**微任务的「排干」语义是关键**：队列里的微任务会带着自己滋生的新微任务一起清完，这就是 `await` 链条能连续推进的机制保障。

**微任务存在的理由**（深水区之一，讲出设计动机）：回调需要在「当前同步代码执行完、但事件循环让出之前」这个时机运行，**既要异步（不阻塞当前栈）又要尽快（不等下一轮宏任务）**。Promise 的决议回调如果走宏任务，then 的延迟会受「队列前面压了多少定时器」影响；走微任务，延迟稳定为「当前栈执行完的下一个瞬间」。**微任务是用「插队权」换「确定性」的设计**。

**Node.js 的六阶段模型**（讲出和浏览器的差异就过半）：timers（执行到期的 setTimeout/setInterval）→ pending callbacks → idle/prepare → **poll（取新 IO 事件、执行 IO 回调）**→ check（setImmediate）→ close callbacks。**每个阶段切换之间清一次微任务**；而 `process.nextTick` 是比 Promise 更高优先级的独立队列，**在每个阶段之间、且优先于微任务清空**，nextTick 递归能饿死微任务甚至 IO，这是它被官方建议慎用的原因。setTimeout(0) 和 setImmediate 的顺序不定（取决于启动时是否已过 timer 阶段阈值），**但在 poll 阶段回调里 setImmediate 必先于 setTimeout**，这个特例是老牌考点。

**拉开差距的细节**：`await fn()` 后面的代码不等价于「then(fn) 的同步版」，**await 会让出微管制的执行权一次**（等 fn 的 Promise 决议的那个微任务），所以 `async function` 里 await 前后的同步代码可能被「插进来的同步代码」打断；浏览器里 rAF 在微任务之后、渲染之前执行，**「改 DOM 后读取布局」如果在同一个任务里会强制同步 layout（回流），拆到 rAF/双 rAF 里是老优化手段**。

收尾：事件循环的本质是「**单线程 + 队列的公平调度**」，微任务管「同一件事的收尾」，宏任务管「不同事情的排队」，渲染插在中间拿走它的时间片。

> 面试官追问点：微任务队列是 V8 的还是宿主的？应答思路：队列本身由宿主维护（浏览器在 HTML 规范的「清理微任务队列」步骤、Node 在 libuv 阶段间隙），V8 提供入队 API（EnqueueMicrotask），所以「微任务归 V8」的说法不准确，归「JS 运行时环境」。

### 7.2 闭包的底层是怎么实现的？V8的Context与内存泄漏

答：一句话定调，**闭包是「函数对象携带对定义时词法环境的引用」，V8 里它物化为 Context 对象，捕获的变量住在 Context 的 slot 里**。

**先讲词法作用域的静态性**：作用域链在**函数定义时**就由代码的书写位置决定（静态），不是调用时决定（动态），这就是 JS 不支持动态作用域、但 this「像」动态的对比来源。函数对象的内部槽 `[[Environment]]` 存着定义时的外层环境引用，**这个槽就是闭包的物理载体**。

**V8 的实现细节**（深水区之一）：外层函数的局部变量如果被内层函数引用，**V8 不会把它留在栈上，而是提升到堆上的 Context 对象**（每个函数调用一个 Context，被引用的变量作为 slot）。所以「闭包捕获的变量」和「普通局部变量」在 V8 里**根本不在同一个地方**：前者堆上共享、后者栈上私有。这直接解释了 `for (var i...)` 的循环共享一个 i（同一个函数作用域的 Context slot）而 `for (let i...)` **每次迭代新建一个 Context**（规范层面的 CreatePerIterationEnvironment），六次循环六个不同的 i，闭包各自各的。

**闭包的三大应用场景对着机制讲**：函数工厂（返回的函数各带各的 Context）、模块模式（IIFE 的 Context 就是私有作用域、只暴露返回的对象）、柯里化（参数分批存进层层 Context）。

**内存泄漏的准确理解**（深水区之二）：泄漏的不是「闭包本身」，是**外层函数 Context 被内层函数的 [[Environment]] 引用着、其中的大对象跟着活**。经典案例如 `el.onclick = function() { ... 不用 bigData ... }`，哪怕回调里没提 bigData，**只要外层作用域里有它且 V8 没做逃逸分析式的精确剔除（早期 V8 剔除不掉，新版本对未引用变量会优化）**，它就陪葬。防御手段：把需要的东西显式传参进内层，切断对外层 Context 的依赖面。

收尾：闭包 = 函数 + 定义时的环境，**「函数是值、环境是函数的行李」**，行李在堆上、随取随用，这也是 JS 能支撑函数式范式的机制根基。

> 面试官追问点：let 为什么能解决循环闭包问题，原理和 var 的区别？应答思路：var 的 i 挂在函数环境的唯一 slot；let 的每次迭代是独立的块级环境（规范 CreatePerIterationEnvironment），六个迭代六个环境，闭包引用的是各自环境的 i，讲出「每迭代一个环境」这句规范术语就是满分答案。

### 7.3 this的四种绑定怎么分优先级？规范层的求值流程

答：一句话定调，**this 不是函数的属性，是「调用表达式」的属性，规范层面它在每次 EvaluateCall 时重新计算，箭头函数干脆没有自己的 this**。

**规则按优先级讲**（从低到高）：

1. **默认绑定**：独立调用 `f()`，严格模式 this 是 undefined、非严格是 globalThis。**为什么有这个差异**：非严格的历史兼容（挂到全局），严格模式是 ES5 的修正，「你的 undefined 就让它 undefined，别偷偷变全局」；
2. **隐式绑定**：`obj.f()`，this 是点号左边的 Receiver。**丢失场景**是考点：`const g = obj.f; g()` 丢 Receiver 回到默认绑定；**传回调 `setTimeout(obj.f, 0)` 同理**，本质是「调用表达式变了，f 被当独立函数调」；
3. **显式绑定**：call/apply（立即调）和 bind（永久绑），bind 是**创建带预置 this 的新函数**，且一次 bind 后再 call 也改不动（bind 的优先级高于 call/apply，规范如此）；
4. **new 绑定**：构造调用，this 是新造的对象（IsConstructor 流程里 OrdinaryCreateFromConstructor 造出来的实例）。

**箭头函数为什么没有 this**（深水区）：规范里箭头函数**没有 [[ThisValue]] 内部槽，不参与 this 的计算**，它沿词法作用域链取外层的 this——**「this 也词法化了」是 ES6 的核心改动之一**。所以 `obj.f = () => this` 里的 this 不是 obj 而是定义处外层的，这既解决了回调丢 this 的痛点（旧时代要 `var self = this`），也带来了「箭头函数不能做构造器、call 对它无效」的副作用。

**规范层面的证据**（能背出术语就是深水区水平）：函数调用的求值是 EvaluateCall(func, thisValue, args)，**thisValue 的来源是 MemberExpression 的判定**：如果调用目标形如 `obj.f`（IsPropertyReference 为真），Reference 的 base 就是 Receiver；如果是纯变量引用（`f`），Reference 的 base 是环境记录，取出的 thisValue 是 undefined，再由被调函数的严格性决定「保持 undefined」或「替换成 globalThis」。

收尾：this 的混乱史是「动态 this（Java 式方法）和函数式（lambda 式）两套基因杂交」的结果，**箭头函数是 ES6 给函数式基因的正式承认**：要动态 this 用普通函数，要词法 this 用箭头。

> 面试官追问点：bind 之后还能用 new 吗？应答思路：能，规范规定 bind 出来的函数仍可构造，new 的优先级高于 bind（this 被新实例覆盖，但预置参数保留），这是优先级链「new > 显式 > 隐式 > 默认」的完整版。

### 7.4 Promise的状态机与链式原理？thenable怎么展开

答：一句话定调，**Promise 的链式调用靠「then 返回新 Promise」形成链，回调的入队时机在 resolve 那一刻，而 thenable 的异步展开是整个规范最精妙的部分**。

**状态机先立住**：pending → fulfilled/rejected，**单向不可逆**，且决议（resolve）之后再 resolve 是静默无效（第一次为准）。**「决议」和「回调执行」是两件事**：then 在 pending 时只是把回调存进两个槽，resolve 时才把回调（连带决议值）打包成微任务入队，这就是「then 的回调永远异步」的规范保证（Promises/A+ 的 2.2.4 条款），**这一条保证了即使 Promise 已决议，then 的回调也不会同步执行**——防止代码在 then 注册前后出现两种时序。

**链式的机制**：`p.then(a).then(b)` 中第一个 then 返回的不是 p 自己，**是内部 new 出的新 Promise（promise2）**，a 的返回值经过 Promise Resolution Procedure 灌进 promise2：返回普通值就 fulfill，返回 thenable 就**递归展开**，抛异常就 reject。**错误能「穿透」中间的 then 直达 catch** 的原因：then 没传 onRejected 时，规范规定该 then 的行为是「原样转发 rejection」，一层层默认透传到有 catch 的那层。

**thenable 异步展开（深水区之一，能讲清就是专家级）**：resolve 的参数如果是个 thenable（有 then 方法的对象），规范要求**再排一个微任务去调它的 then 方法**，取其结果继续决议（Promise Resolution Procedure 的 2.3.13 条款）。**这保证了「外来 thenable 和原生 Promise 的组合时序确定性」**（著名的 thenable assimilation），副作用是「resolve 一个 thenable 至少多一个微任务 tick」，这是某些输出题里「多打印一轮」的隐藏原因。

**四个组合方法的差异表**：all（全成功才成功、**首个失败即 reject**，但**其余 promise 仍会继续执行完只是结果被丢弃**）、race（**第一个 settle 的胜出，无论成败**）、allSettled（等全部 settle、永不 reject）、any（**第一个成功者胜出，全失败才 reject 一个 AggregateError**）。**深水区之二**：all 的短路是「结果层面短路不是执行层面」——传入的 promise 在调用 all 之前就已经开始跑了，**「取消」剩下的是做不到的**，需要可取消语义要靠 AbortController 配合，这是很多人答 all 时的隐藏误区。

收尾：Promise 把「回调金字塔」变成「线性链」，代价是引入一个**严格单向的状态机加一套微任务调度规则**，把「什么时候执行」从开发者手里收走，交给规范保证确定性。

> 面试官追问点：async/await 就是 generator+自动执行器吗？应答思路：语义上等价（await ≈ yield + 恢复回调排微任务），但规范实现是独立的（AsyncFunction 的 await 直接走 Promise 的 then 机制接回执行权），比 generator 转写少一层状态机包装，V8 还有 await 的优化（跳过中间 Promise 的优化曾进又出，因为造成可观察差异）。

### 7.5 V8的双层结构怎么运作？隐藏类与内联缓存怎么加速

答：一句话定调，**V8 用「解释器 Ignition + 优化编译器 TurboFan」的双层结构跑 JS，性能的秘密武器是「隐藏类+内联缓存」这对组合拳**。

**执行流程四步**：源码 → Parser 生成 AST → **Ignition 解释器生成并执行字节码**（Ignition 的寄存器机，比旧时代的基线编译快且省内存）→ 运行中收集类型反馈，**热点函数交给 TurboFan 优化编译成机器码**，优化假设失效则「去优化」回退到字节码。

**隐藏类（Hidden Class / Map）**：JS 对象是字典结构，按名字查属性应该很慢，**V8 给每个对象挂一个 Map（隐藏类），描述「属性名 → 存储槽位」的布局**，属性访问变成「按 Map 的 offset 直接取」，速度接近 C 结构体。**关键机制是转换链（transition tree）**：`{a:1}` 加 b 属性会派生新 Map，同类对象走同一条转换路径、共享 Map。**这就是「构造函数里初始化全部属性」这条最佳实践的底层依据**：不同顺序、不同属性集的对象会分叉出不同 Map，Map 分叉越多，下一步的 IC 越没法命中。

**内联缓存（IC，深水区之一）**：属性访问点（字节码的 LdaNamedProperty）旁挂着**反馈向量（Feedback Vector）**，记录「上次见过的 Map + 对应的取值策略」。命中单一 Map 叫 **monomorphic（单态，直接内联偏移量，最快）**；见到 2-4 种 Map 升级 **polymorphic（多态，逐个比对）**；超过 4 种退化 **megamorphic（超态，回退到通用查找）**。**「多态热点的性能悬崖」是 V8 调优的核心知识点**：一个函数被传入不同 shape 的对象超过四个，性能可能掉一个数量级。这解释了三条实践：别让一个函数处理太多形状的对象、别随意 delete 属性（会把对象打成**字典慢模式 Slow Mode**）、构造函数统一初始化。

**GC 的分代设计**：新生代用 **Scavenge 半空间复制**（活对象 From 拷到 To，两次 Scavenge 后晋升老生代，**适合「朝生夕死」的短命对象，复制成本和存活率成正比**）；老生代用**并发标记清除+整理**（Mark-Sweep 清理、Mark-Compact 整理碎片，标记阶段并发跑、只在重新标记短停）。**V8 的 GC 和 Go/JVM 一样是并发分代的套路**，差异在「整堆压缩的触发策略」。

**拉开差距的深水区之二**：**逃逸分析与栈分配**——局部对象如果能证明不逃出函数，TurboFan 可以把它拆散成分量直接放寄存器（标量替换），连堆都不上，**「分配本身被优化消失」**；反过来，被闭包捕获的变量必须逃逸到堆（Context，呼应 7.2），两题在此打通。

收尾：V8 的策略一句话总结，**「用运行时收集的类型信息，赌 JS 的动态性在热点上是稳定的」**，赌赢了机器码起飞，赌输了（deopt）退回字节码重跑，JS 高性能的本质是「带保险的投机」。

> 面试官追问点：为什么 delete 属性会拖慢对象？应答思路：delete 破坏隐藏类的形状假设，V8 会把对象从「快速模式」降级为「字典模式」（属性按哈希表存），后续访问走通用查找；要移除属性更好的做法是把它置 undefined（保留形状）或用 Map 数据结构管理动态键集。

### 7.6 new的执行过程有哪几步？instanceof的判定原理

答：一句话定调，**new 的本质是五步（造对象、连原型、绑 this、执行、兜底返回），instanceof 的本质是沿原型链找 constructor.prototype**。

**new 的五步**（以规范术语口述）：

1. 创建空对象 `obj = {}`；
2. **链接原型**：`obj.[[Prototype]] = constructor.prototype`（规范里是 CreateFromConstructor，从构造器的 prototype 属性取，**这就是「改写 prototype 等于改写后代蓝图」的机制**）；
3. 以 obj 为 this 执行构造函数；
4. **构造器返回对象类型则用之，否则无视返回值用 obj**（返回原始值会被丢弃，这条兜底规则是手写 new 时最容易漏的）。

**class 与 function 构造的差异**（深水区一）：class 有内部标志 **[[IsClassConstructor]]**，**不用 new 调用直接 TypeError**（function 忘了 new 则 this 挂全局，严格模式 undefined）；class 方法**不可枚举**（for-in 干净）；**super 的解析靠 [[HomeObject]] 槽位：super() 定位到 [[HomeObject]] 原型链上的父构造器**，且 **super() 调用前 this 处于未初始化状态（访问 this 抛错，类似 TDZ）**，这是 class 构造器里 this 的保护机制。

**instanceof 的判定**：`a instanceof B` 走 **OrdinaryHasInstance：取 B.prototype，沿 a 的原型链（__proto__ 逐级上溯）比对是否引用相等**，到 null 为止。所以 `Object.create(null)` 造的对象 instanceof 一切都为 false（没有原型链）；**Symbol.hasInstance 可以改写 instanceof 的行为**，这是少数可定制的运算符。

**原型链查找的规则**：读属性沿原型链上溯（自有优先），**写属性只作用于自有**（原型上的值类型属性被「遮蔽」而非修改）；setter 例外（原型链上的 setter 会被调用）。`Object.create(proto)` 只做链接不执行构造器，是继承的最小工具。

收尾：JS 的继承是「**对象链（实例→原型→原型的原型）+ 委托查找**」，class 是这套机制的语法糖（外加严格化和 super 的 [[HomeObject]] 机制），「原型是对象不是类」这一句是所有细节的总纲。

> 面试官追问点：为什么 class 里必须在 super() 之后才能用 this？应答思路：派生类构造器执行时 this 还没创建（this 由父构造器创建），super() 才触发父类构造并「认领」this；引擎用「未初始化 this」的检查防止在对象诞生前访问，是 TDZ 思想在 this 上的复刻。

### 7.7 深浅拷贝的实现与structuredClone

答：一句话定调，**浅拷贝只复制第一层引用，深拷贝要递归处理「类型分派 + 循环引用 + 特殊对象」三件事，structuredClone 是浏览器原生的标准答案但有边界**。

**浅拷贝的四个姿势对比**：`{...obj}`（丢原型和 getter）、`Object.assign({}, obj)`（同前）、`Object.create(obj)`（不是拷贝是挂原型）、`arr.slice()/concat()`（数组专用）。**「丢 getter」的细节**：展开运算符读取 getter 的值存为普通属性，语义已经变了，这是「拷贝语义」和「快照语义」的差异。

**JSON.parse(JSON.stringify) 的四宗罪**（深水区一）：

1. **函数、undefined、Symbol 直接消失**（数组里变 null 保位）；
2. **Date 变字符串**（复活不了时区）、**RegExp 变空对象**、**NaN/Infinity 变 null**；
3. **Map/Set/ArrayBuffer/TypedArray 全部报废**；
4. **循环引用直接抛异常**（JSON 是树不是图）。

**structuredClone 的能力与边界**（现代标准答案）：支持循环引用（内部用 WeakMap 记录已访问映射）、Map/Set/Date/RegExp/ArrayBuffer/TypedArray；**边界是不支持函数（抛 DataCloneError）、DOM 节点、Symbol 键（静默丢）、getter 变值、class 实例脱掉原型变 plain object**。它的定位是「**结构化数据的真深拷贝**」，不是「任意对象的复活术」。

**手写递归的核心三点**：

1. **WeakMap 处理循环引用**，**必须 WeakMap 不能 Map**：强引用 Map 会引用住临时对象阻止 GC，且缓存本身泄漏；
2. **类型分派**：数组走 Array、Date/RegExp 走各自构造器复活（`new Date(obj.getTime())`）、**普通对象用 Object.create(Object.getPrototypeOf(obj)) 保留原型**；
3. **超深对象递归会溢出**，工程级实现要转显式栈。

收尾：拷贝方案的选择树，**一层结构用展开运算符、结构化数据用 structuredClone、带 class 实例和函数的复杂对象用 lodash 的 cloneDeep、数据干净且要性能用 JSON**，四个答案按代价升序。

> 面试官追问点：为什么 structuredClone 不能拷函数？应答思路：函数的可执行体绑定了解析时的作用域（闭包），跨 realm（iframe/worker）的克隆语义无法还原闭包；结构化克隆协议是为「可序列化数据」设计的（postMessage 同源），函数不在「数据」的范畴。

### 7.8 CJS与ESM的循环依赖怎么处理？两套机制差在哪

答：一句话定调，**CJS 靠「缓存半成品 exports」让循环拿到部分完成的对象，ESM 靠「编译期提升 + Live Binding」让循环读到最新值但可能踩 TDZ，两者都是「不保证顺序只保证不死锁」**。

**CJS 的加载机制**：require 时查缓存（`require.cache` 以文件路径为键），**命中直接返回缓存的 module.exports 引用**。循环发生时（A require B、B require A）：B 拿到的是 **A「执行到一半」的 exports 对象**，A 还没执行的部分属性是 undefined，**已执行部分可用**。所以 CJS 循环的正确写法是「延迟访问」：B 里不顶层解构，把 `require('a')` 挪到函数内部运行时再取。

**ESM 的三阶段加载**（深水区一）：

1. **构建（Construction）**：递归解析模块图，**只下载解析不执行**，此时所有模块的「导出符号表」已确立（函数声明提升、var 提升到模块作用域）；
2. **实例化（Instantiation）**：把各模块的导出绑定到内存槽位，**import 的名字链接到 export 的槽位**，Live Binding 的物理实现就是「同一个内存槽的两个名字」；
3. **求值（Evaluation）**：按后序深度优先执行模块体（被依赖者先执行）。

**ESM 循环的行为**：因为符号表在执行前就绪，**循环双方都能「先声明后使用」**，函数声明可用（提升），但 **let/const 在求值前访问抛 TDZ**（模块还没执行到定义处）。这比 CJS 更可预测：**能用的永远是「已初始化的绑定」，不能用的会响亮报错**而不是悄悄 undefined。

**Live Binding 的两个推论**：export 的计数器变量在模块内自增后，**import 方读到的同步变**（值不是快照）；**import 侧是只读的**（赋值抛 TypeError）。CJS 没有这个机制：**exports 是值的拷贝**（导入那一刻的快照），所以 CJS 要传递变化得「导出对象包一层」或「导出函数」。

收尾：CJS 是「运行时的对象交换」（缓存半成品兜底），ESM 是「编译期的符号链接」（TDZ 兜底），**循环依赖在两套体系里都不该被鼓励，但 ESM 至少把病兆从「静默 undefined」升级成了「显式异常」**。

> 面试官追问点：为什么 ESM 的顶层 this 是 undefined 而 CJS 是 exports？应答思路：ESM 设计目标是模块作用域的严格化与静态化，顶层 this 绑定 undefined（对齐严格模式）；CJS 的模块本质是「包了一层的函数」，this 即 exports 是函数调用的历史产物。

### 7.9 ToPrimitive的完整规则？对象隐式转换怎么一步步走

答：一句话定调，**对象参与运算时走 ToPrimitive（按 hint 选 Symbol.toPrimitive → valueOf → toString），而 `[] == false` 的完整推演是五步链**。

**ToPrimitive 的算法**（按规范顺序背）：

1. hint 判定：`==` 和算术运算要 number，**Date 参与的 + 走 string**，普通 + 是 default；
2. 依次尝试：**`obj[Symbol.toPrimitive](hint)`**（有则用）→ **valueOf()**（结果是原始值则用）→ **toString()**（原始值则用）；
3. 全都不是原始值，抛 TypeError。

**`[] == false` 的五步推演**（能完整走下来就是深水区水平）：

```text
[] == false          // false 转 number
[] == 0              // [] 走 ToPrimitive：valueOf 返回数组（非原始值），
                     // 落到 toString 返回 ""
"" == 0              // "" 转 number
0 == 0               // true
```

**关键三则**：**null/undefined 互相相等且不等于任何其他值**（`null == undefined` 为 true，但 `null == 0` 为 false）；**NaN 与一切不等（包括自己）**；一方是对象一方是原始值才走 ToPrimitive（两边都是对象时 == 比引用）。

**+ 的独立规则**（和 == 的数字优先不同）：**任一操作数转成字符串则拼接**，`[] + []` 是 "" + "" 得 ""；**`[] + {}` 得 "[object Object]"**（数组转空串、对象转它的 toString）；而 **`{} + []` 在语句开头是「块语句 + 空表达式」结果是 0**，这种反直觉是「块语句歧义」不是类型转换的锅。

**深水区二：Symbol.toPrimitive 的工程用途**，给 Money 类实现它（number hint 返回数值、string hint 返回格式化文本），`price * 2`、`price + 100` 直接工作，这是「鸭子类型延伸到运算符层面」的进阶手法。

收尾：转换规则的心法是「**对象先变原始值（ToPrimitive 三连），再按运算符的偏好（+ 串优先、== 数字优先）各走各路**」，两大例外（null/undefined、NaN）单独记。

> 面试官追问点：为什么 `if ([])` 是真但 `[] == false` 也是真？应答思路：if 走 ToBoolean（对象一律 true，不经过 ToPrimitive），== 走 ToNumber（空数组链到 0），**两条独立的转换通路规则不同**，这正是「显式优于隐式」这条最佳实践的存在理由。

### 7.10 内存泄漏的三大来源是什么？三件排查武器怎么用

答：一句话定调，**三大泄漏源（意外全局、被遗忘的回调、detached DOM），三件排查武器（快照对比、分配录制、Retainers 读引用链）**。

**三大泄漏源按机制讲**：

1. **意外全局变量**：未声明变量直接挂 window（非严格模式），**window 上的属性 GC 永不回收**（根对象可达）；
2. **被遗忘的定时器和监听器**：setInterval 的回调持有闭包、addEventListener 持有处理函数，「组件销毁但定时器没 clear」是 SPA 的高发事故；
3. **detached DOM 节点**（深水区一）：节点从文档移除（removeChild/innerHTML 覆盖）后**本体还活着，只要 JS 变量仍引用它**（存在数组、存在闭包、存在事件回调里），整棵子树都无法回收——**「DOM 的移除」和「JS 引用的断开」是两件事**，泄漏正是「移除了但没断开」。

**三件排查武器**：

1. **堆快照对比**（Heap snapshot）：操作前后各拍一张，**按「Objects allocated between snapshot 1 and 2」过滤**，看新增对象的 retained size；**detached 节点在快照里直接有 Detached 标记**，按这个字搜最快；
2. **分配时间线**（Allocation instrumentation on timeline）：**录制每块内存的分配栈**，页面操作后看「蓝色柱子只涨不落」（分配了没回收）的条带，点开就是泄漏点的调用栈；
3. **Retainers 面板**：选中可疑对象，**看「谁引用着它」的链路**（黄色是 JS 引用、红色是 detached 的 DOM 引用），顺着链找业务代码里的持有者，这是「定位到代码行」的最后一步。

**深水区二：WeakRef 的正确理解**，`WeakRef` 和 `FinalizationRegistry` **不是可靠的 GC 回调机制**（回调时机不确定、可能不调），唯一正当用途是「缓存场景的软提示」（有最好没有拉倒）；**把它当「析构函数」用是设计错误**，JS 没有确定性析构，RAII 思想在 JS 的对应物是 try-finally 和显式的 close/dispose 协议。

收尾：泄漏排查的方法论是「**先看曲线（Memory 面板的锯齿是否整体上扬）定位现象，再用快照对比定位对象，最后用 Retainers 定位代码**」，三步各回答一个问题：有没有漏、漏的是什么、谁拽着不放。

> 面试官追问点：闭包一定会导致泄漏吗？应答思路：不一定，闭包本身是正常机制，泄漏的充要条件是「闭包活得比需要的时间久」（长存的定时器/全局缓存持有了闭包，闭包的 Context 里挂着大对象）；短命的闭包随函数返回一起回收，答题的关键是把「闭包」和「闭包的存活周期」分开。
