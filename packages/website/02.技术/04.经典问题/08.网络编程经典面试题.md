# 2.TCP与UDP

# 8.深度精讲（TCP与TLS协议口述版）

> 说明：本章是核心题的口述版深度精讲，讲到报文字段、状态机与算法演进层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

### 8.1 TCP三次握手的状态机细节

答：一句话定调，**三次握手的每一步都对应状态迁移，核心是「双方各确认一次对方的收发能力」，而 SYN Queue 和 Accept Queue 的区分是深水区**。

**状态机走一遍**（以服务端视角为轴）：CLOSED → **LISTEN**（bind + listen 之后）→ 收到 SYN 发出 SYN+ACK 进入 **SYN_RCVD** → 收到 ACK 进入 **ESTABLISHED**。客户端：CLOSED → 发 SYN 进 **SYN_SENT** → 收到 SYN+ACK 回 ACK 进 ESTABLISHED。

**为什么是三次（按「确认能力」讲）**：连接的本质是**双向各拿到两个确认**：「我能发你能收」（第一次发出、第二次被确认）和「你能发我能收」（第二次发出、第三次被确认）。**两次的问题**是服务端无法确认「自己发出的 SYN+ACK 客户端收到了」——历史失效的 SYN（网络里滞留的旧包）到达时，服务端单方面建立连接占资源，**第三次 ACK 让客户端有机会用 seq 校验拒收陈旧连接**（RST 回应），这是「防止历史连接初始化」的规范理由，比「确认双方能力」更本质。

**深水区一：两个队列**：

1. **SYN Queue（半连接队列）**：收到 SYN 还没完成三次握手的连接住这里；**SYN Flood 攻击打的就是它**——攻击者伪造源 IP 狂发 SYN 不回 ACK，队列塞满真用户进不来；
2. **Accept Queue（全连接队列）**：完成三次握手、**等待应用层 accept() 取走的连接**（内核已完成握手，accept 只是「从队列取走」这个动作，**所以「accept 之前握手已经完成」**——很多代码把 accept 误解为握手动作者会在这里翻车）；
3. **全连接队列溢出**的表现：`ss -lnt` 看 `Recv-Q/Send-Q`（监听状态下 Recv-Q 是当前 accept 队列积压），**溢出的默认行为是丢掉 ACK（客户端以为连上了，发数据被 RST）**，tcp_abort_on_overflow=1 时直接 RST。

**SYN Cookie 的防御机制**（深水区二）：队列满后不再存半连接状态，**把连接信息（四元组+时间戳的哈希）编码进 SYN+ACK 的 seq 序号里发出去**——**服务端不占任何内存**；客户端回 ACK 时（ack = seq+1），服务端**从 ack-1 反解验证 cookie 合法性**，合法直接建立连接。代价是**不能存选项协商的中间状态**（窗口缩放等要在 ACK 重带），所以 cookie 是「攻击时的降级方案」而非默认。

收尾：三次握手答到「队列双轨 + cookie 无状态防御」，就从协议背诵到了内核实现，**面试官问这题就是在筛「读过 TCP/IP 卷一还是只看过博客」**。

> 面试官追问点：listen 的 backlog 参数控制的是哪个队列？应答思路：历史上是半连接队列，现代 Linux（2.2+）**实际控制全连接队列的长度上限**（somaxconn 与 backlog 取小），半连接队列由 tcp_max_syn_backlog 控制——答出这个版本分野是加分点。

### 8.2 TIME_WAIT的深挖与治理

答：一句话定调，**TIME_WAIT 只出现在「主动关闭方」，2MSL 的寿命保护「最后的 ACK 能重传」和「旧连接的报文在网络中自然死亡」两件事**。

**为什么是 2MSL**（按两个理由讲，多数人只会背第一个）：

1. **可靠的终止**：主动方最后的 ACK 丢了，被动方会重发 FIN，**主动方必须还活着才能重发 ACK**；一个 MSL 是「ACK 到达对方的最长时间」，一个 MSL 是「对方重发 FIN 回来的最长时间」，2MSL 封顶；
2. **防止历史报文污染新连接**（更本质）：**同一个四元组（源IP、源端口、目的IP、目的端口）的旧连接数据包，必须在网络中活过一个 MSL 自然消亡**，否则新连接（恰好复用同一四元组）可能收到旧连接的迟到报文，**seq 对上就是数据错乱**——这也是「为什么不能用时间戳之外的 seq 判新旧」的根因。

**谁产生 TIME_WAIT**：**主动关闭的一方**。所以「服务端大量 TIME_WAIT」通常意味着**服务端主动断连接**（HTTP keepalive 没开、健康检查频繁建断、爬虫式短连接）。

**治理的三个层次**（深水区，按优劣排）：

1. **治本：减少主动关闭**——HTTP keep-alive / 连接池复用长连接，让「短连接风暴」消失；
2. **端口扩容**：`tcp_tw_reuse` **只允许客户端（主动发起方）复用 TIME_WAIT 端口发起新连接，且要求时间戳启用**（新连接的 TS 比旧报文大，用时间戳判新旧而不是干等 2MSL）；扩大 ip_local_port_range 增加可用端口数；
3. **危险的开关**：`tcp_tw_recycle`（**已在 Linux 4.12 被删除**）——它靠「同源 IP 的时间戳单调递增」判断复用，**NAT 环境下多主机共享一个 IP 但时间戳跳变，正常用户全被丢包**，生产事故的经典来源；`SO_REUSEADDR` 只解决 bind 冲突不解决复用。**能讲出 recycle 为什么被删，就是这题的深水区满分**。

收尾：TIME_WAIT 不是 bug 是设计——**用主动方 60 秒（Linux 的 2MSL=60s）的等待，换「连接关闭的可靠」和「新旧连接的隔离」**；治理思路永远是「先减少产生（复用连接），再扩大容量（端口），最后才是有代价的复用（reuse+时间戳）」。

> 面试官追问点：CLOSE_WAIT 堆积和 TIME_WAIT 的区别？应答思路：CLOSE_WAIT 是**被动方收到了 FIN 但自己没调 close**——全是应用层 bug（代码漏 close、慢处理积压），内核参数救不了，只能改代码；TIME_WAIT 是协议正常行为，两者「一内因一协议」，混为一谈是这题最常见的丢分点。

### 8.3 拥塞控制的算法演进

答：一句话定调，**拥塞控制在回答「网络能吃多少」，经典算法（Reno/CUBIC）用丢包当拥塞信号，BBR 改用「带宽 × 时延」的主动测量**。

**四个阶段先走一遍**（以 Reno 为轴，cwnd 是发送窗口）：

1. **慢启动**：cwnd 从 1 MSS 起步**每个 RTT 翻倍**（收到 ACK 就加，指数增长），撞到阈值 ssthresh 切换；
2. **拥塞避免**：每个 RTT 加 1 MSS（线性爬坡）；
3. **快重传**：**收到 3 个重复 ACK**（不等 RTO 超时）立即重传丢失段；
4. **快恢复**：ssthresh 减半、cwnd 设为新 ssthresh（不回到 1），直接进拥塞避免。

**慢启动为什么「慢」**：这个「慢」是相对「直接全速」而言，**指数增长其实很快**——它的慢在于起步小（避免冷启动直接打爆网络）。

**深水区一：CUBIC 的改进逻辑**——Linux 默认算法：Reno 的「减半后线性爬」在高带宽长时延（BDP 大）的管道里恢复太慢（**100ms RTT 的网络线性爬 1MSS/RTT，恢复 10MB 窗口要几百秒**）；CUBIC 的窗口是**三次函数（凹函数先快后慢逼近上次撞墙点，凸函数越过后谨慎探索）**，**和 RTT 解耦**（以时间为自变量），大管道恢复快、小管道依然温和。

**深水区二：BBR 的范式革命**：

1. **丢包信号的谬误**：经典算法把「丢包」当拥塞，但**现代网络的丢包常是缓冲区浅的误伤，深缓冲区则是「不丢包但时延暴涨」的 bufferbloat**——丢包既不充分也不必要；
2. **BDP 模型**：**最大吞吐 = 带宽 × 最小时延（BDP 是管道容量）**，BBR 主动测量这两个量（**周期性 pacing 探测带宽上限、探测最小 RTT**），**把发送速率钉在 BDP 上，而不是让队列堆积到丢包才发现**；
3. **不排队哲学**：经典算法的平衡态是「填满缓冲区」（丢包才退），**BBR 维持 in-flight ≈ BDP，队列长度趋近 0**——时延和吞吐同时最优，这是「.bufferbloat 的解药」；
4. **pacing**：BBR 必须配 pacing（发包间隔均匀化），因为**突发打包发送会在浅缓冲瞬时溢出**，这改变了内核发包调度的实现（tc fq + TCP 层协作）。

收尾：拥塞控制的演进史就是「**信号质量的进化**：丢包（滞后且有噪声）→ 时延（CUBIC 时代的 Vegas 思想被重新发掘）→ 主动测量 BDP（BBR）」，每一代都是对「网络到底拥不拥」这个判断的修正。

> 面试官追问点：流量控制和拥塞控制的窗口谁说了算？应答思路：实际发送窗口 = min(rwnd, cwnd)，rwnd 是**接收方在 ACK 里通告的**（别撑爆对端内存），cwnd 是**发送方自估的**（别撑爆网络），两把锁锁两个不同的瓶颈，慢启动阈值只在 cwnd 这条线里起作用。

### 8.4 TLS1.2/1.3握手的完整过程

答：一句话定调，**TLS 的核心是「非对称协商对称」：非对称算法（贵）只用来安全地交换预主密钥，之后全是对称加密（快）**，1.3 比 1.2 少一次往返还能 0-RTT。

**TLS1.2 的四握手**（RSA 密钥交换版，最利口述）：

1. **ClientHello**：客户端随机数 + **支持的密码套件列表**（TLS_RSA_WITH_AES_128_GCM...）+ 支持的 TLS 版本；
2. **ServerHello + Certificate + ServerHelloDone**：服务端随机数 + **选定的套件** + 证书链（服务端证书 + 中间 CA 证书）；
3. **客户端验证证书后发 ClientKeyExchange + ChangeCipherSpec + Finished**：**预主密钥用服务端证书公钥加密发出**（RSA 交换）+「后续开始加密」+ **Finished（用协商密钥加密的第一条消息，握手本身的完整性校验）**；
4. **服务端回 ChangeCipherSpec + Finished**：双方各自用「两个随机数 + 预主密钥」推导会话密钥，握手完成。

**为什么密钥要三方材料**：预主密钥 + 客户端随机数 + 服务端随机数，**随机数保证「同一对密钥每次会话的密钥都不同」（前向防重放），预主密钥保证只有持私钥者能参与**。

**深水区一：证书链验证**：浏览器只内置**根 CA（自签）**；服务端发来「叶子证书 + 中间证书」，**验证是逐级用上一级公钥解签名**（叶子被中间签、中间被根签、根在信任库），**任何一个环节失败或域名不匹配（SAN 字段）就告警**。中间证书下发的意义：**根 CA 私钥离线冷备，在线签发全靠中间层，泄漏了可以只吊销中间层**。

**深水区二：ECDHE 与前向保密**——RSA 交换的死穴：**私钥泄漏 = 历史流量的预主密钥全可解**（被录制的流量囤着等私钥）。**ECDHE 的每个连接独立做椭圆曲线 DH 临时密钥协商**（双端各生成临时密钥对，公钥互换、各自算出共享密钥，**私钥只用于签名验证身份不参与密钥计算**），**私钥泄漏也解不开历史流量——这就是前向保密**。**TLS1.3 直接砍掉 RSA 静态交换**，只留 ECDHE。

**TLS1.3 的两大提速**：

1. **1-RTT**：ClientHello 直接带上**密钥共享（key_share，ECDHE 公钥）**，服务端回包就完成协商——**握手和密钥交换折叠进前两个包**；
2. **0-RTT**（深水区三）：**复用上次会话时，客户端用 PSK（早期数据密钥）在第一个包里就带应用数据**——代价是**重放风险**（0-RTT 数据被录制重发），所以**只允许幂等请求（GET）走 0-RTT**，且服务端有抗重放窗口（单向 ticket + 时间窗）。

收尾：TLS 的安全模型是「**用 PKI（证书体系）解决身份认证，用非对称解决密钥分发，用随机数和临时密钥对抗重放与回溯**」，1.3 的演进主线是「少一次往返、废静态 RSA、上 0-RTT」。

> 面试官追问点：HTTPS 抓包为什么装根证书就能解密？应答思路：代理（Charles）做中间人——它向客户端出示自己签的伪证书（根证书已被信任所以通过验证），与客户端、与真实服务端各建一条真 TLS——**这正演示了「没有证书体系保护的密钥交换会被 MITM」**，也解释了为什么 SSL Pinning（应用层校验特定证书）能防抓包。

### 8.5 QUIC为什么基于UDP实现

答：一句话定调，**QUIC 选 UDP 不是为了「不可靠」，而是为了「绕开内核的 TCP 实现权」——在用户态重造一个可进化的传输层**。

**TCP 的「动不了」困境**：TCP 在**操作系统内核**里实现，**任何协议改进（换拥塞算法、改握手、加特性）都要等内核升级**——全世界的设备更新一轮以十年计；中间盒（NAT、防火墙）对 TCP 头的篡改和假设让新字段寸步难行。**QUIC 把传输层搬进用户态（库随应用发版），迭代周期从十年缩到三个月**——这是选 UDP 的第一动机：**要演化权**。

**在 UDP 上重建的四大件**：

1. **流多路复用且无队头阻塞**：一条 QUIC 连接跑多个 stream，**丢包只重传所在 stream 的数据，其它 stream 不被阻塞**；对比 HTTP/2 over TCP：**TCP 层的丢包会阻塞所有 stream 的字节流**（H2 的队头阻塞在传输层，QUIC 把它拆掉）——**每个 stream 独立的 ack/重传状态机**是引擎核心；
2. **加密内置且握手融合**：**QUIC 的传输头自带加密（没有明文传输层）**，且 **TLS 握手折叠进 QUIC 握手**（首包就带 ClientHello 的 key_share）；**1-RTT 建连 + 恢复会话 0-RTT**；
3. **连接迁移**：连接标识是 **Connection ID（随机 64bit）而不是四元组**——**WiFi 切 4G 时 IP 变了但 CID 不变，连接不断**；TCP 的连接身份绑四元组，换网必断（移动端 MPTCP 想解决但推进不动）；
4. **更聪明的 ACK 机制**：**单调递增的包号（含重传的新号）**——重传包号不复用，**RTT 估计算法不再被「重传歧义」（原包和重传包分不清谁的 RTT）污染**；ACK 块显式编码乱序（SACK 进化）。

**深水区一：队头阻塞的完整对比链**——HTTP/1.1 的队头阻塞在**应用层**（一个连接一次一个请求，pipelining 死于响应顺序）；H2 解决应用层（stream 并行）**但继承 TCP 层的队头阻塞**（字节流保序，一个丢包全连接等重传）；QUIC 在 stream 级别独立排序，**把队头阻塞的粒度从「连接」降到「流」**。

**深水区二：代价与生态**——UDP 在中间设备上被限速/丢弃（历史偏见：UDP=视频=P2P 滥用），**QUIC 需要伪装成正常流量特征 + 服务端部署优化（内核 UDP 收包路径没有 TCP 成熟，GSO/网卡 offload 重新打磨）**；Google 先在 Chrome+自家服务验证（46% 流量跑 QUIC），IETF 标准化后成为 HTTP/3 的底座——**「用户态协议的进化靠大厂先趟路」**是这个案例的产业启示。

收尾：QUIC 的一句话哲学，**「UDP 是内核给的那块白板，QUIC 在用户态的白板上画了 TCP 十年画不出的画」**——多路复用无阻塞、握手融合、连接迁移、包号单调，四个特性全都源于「挣脱内核的发行周期」。

> 面试官追问点：QUIC 自己做可靠传输，为什么不直接用 SCTP？应答思路：SCTP（多流传输协议）技术上有类似能力，但**中间设备对未知 IP 协议号直接丢弃**（NAT/防火墙不认识就不转发），UDP 是「唯一被普遍放行的非 TCP 通道」——**现实的网络生态比理想的协议设计更有决定权**。

### 8.6 TCP滑动窗口与流控细节

答：一句话定调，**滑动窗口是「批量发送批量确认」的流水线：发送窗口 = min(rwnd, cwnd)，窗口的左沿受 ACK 推进、右沿受窗口大小限制，零窗口靠探测死守**。

**发送方的四格结构**（把窗口讲立体）：**已发送已确认 / 已发送未确认 / 可发送未发送 / 窗口外不可发送**——**左沿=最早未确认的字节，右沿=左沿+窗口**；**收到 ACK 推左沿（窗口滑动），窗口扩大推右沿**。**累计确认**的含义：ack=N 表示「N 之前的全部收到」——**中间丢一段的话，后面收到的字节也只回旧 ack（重复 ACK），这就是快重传的信号源**。

**深水区一：零窗口与死锁的防御**——接收方通告 window=0（缓冲区满），发送方停发；**接收方腾出空间后发的「窗口更新报文」如果丢了**，双方永久互等（经典的死锁场景）。**Persist Timer（坚持定时器）**：发送方在零窗口期间**定时发 1 字节的「窗口探测」**，逼接收方重新通告窗口——探测也按指数退避但**永不放弃**（和重传定时器不同）。**糊涂窗口综合征**的两端配合：接收方「缓冲区太小不通告」（等待攒到 MSS 或缓存一半空再开窗），发送方 Nagle「攒满 MSS 再发」——**两端各自防御，合起来杜绝「小包空跑」**。

**深水区二：Nagle 与延迟确认的「负负得正」**——Nagle（发送方）：**有未确认数据时，后续小包攒着不发（攒到 ACK 或满 MSS）**；延迟确认（接收方）：**收到数据不立刻 ACK，等一小段（40-200ms）看能不能搭车（捎带响应或攒数据一起确认）**。**两者同开的最坏情形**：发送方等接收方 ACK 才发下一包，接收方又故意延迟 ACK——**RTT 平白加上延迟确认的等待**，交互式小包场景（SSH、游戏、Redis 客户端）**必关 Nagle（TCP_NODELAY）**；**写操作依赖小包低延迟的中间件（如 MySQL 协议）同样默认 NODELAY**——能讲出这个「优化打架」案例是深水区。

收尾：流控答题的心法，「**窗口是接收方（rwnd）和发送方（cwnd）双闸门取小，左沿靠 ACK 推进，零窗口有探测兜底，Nagle 和延迟确认是批量化和低延迟的取舍**」。

> 面试官追问点：窗口最大能多大？应答思路：受「窗口字段 16 位（64KB）」限制——但**窗口缩放因子（Window Scale，握手选项协商）把它左移到 2^14 倍**（1GB 级），高带宽长时延（BDP 大）网络必需；这正是「握手时没协商缩放，连接吞吐被钉死在 64KB/s 量级」这类疑难杂症的根因。

### 8.7 HTTP/2的多路复用与HPACK

答：一句话定调，**HTTP/2 的三板斧：二进制分帧（协议重写）、多路复用（一个连接并行流）、HPACK（头部压缩），但 TCP 层队头阻塞仍在——这是 HTTP/3 的动机**。

**二进制分帧层**：报文不再是文本，拆成**帧（Frame：长度+类型+标志+流ID+载荷）**——请求/响应的 Header 帧和数据帧分离，**「流（Stream）= 一个请求响应对，由流 ID 标识，帧是流的切片」**——**乱序的帧按流 ID 重组，并行流互不干扰**。

**多路复用的机制收益与边界**（深水区一）：**一个 TCP 连接上 N 个流的帧交错发送**——消除了 HTTP/1.1 的「应用层排队」（6 个连接的浏览器限制、域名分片都成历史）。**但 TCP 层的队头阻塞原样继承**：**TCP 保证字节流有序，一个报文丢失会阻塞后面所有已到达的数据（包括其它流的）交给上层**——**H2 的并发在传输层被 TCP 拖累**；Google 的实测「H2 在 1% 丢包下可能比 H1 还慢」（H1 多连接还有冗余路径）——**这就是 8.5 讲的 QUIC 的入场理由**，两题要能串起来答。

**HPACK 的三级压缩**（深水区二）：

1. **静态表**：61 个高频头部预置编码（「:method: GET」一个字节搞定）；
2. **动态表**：**两端同步维护的「本连接出现过的头部」字典**（首次发完整「user-agent: xxx」，之后一个索引号）——**连接越长命中越高，这就是「HTTP/2 要长连接」的另一层动机**；
3. **哈夫曼编码**：字符串值再压一道（高频字符短码）。

**动态表的两端同步是协议级状态**——**中间设备无法再无状态地解析 HTTP**（H1 时代代理可以文本改写），**这也解释了为什么 H2 的中间盒兼容是一场腥风血雨**。**安全细节**：动态表跨请求共享，**敏感头（Cookie）+ 随机填充的防御（Never Indexed 标志位）防止 CRIME 式的压缩侧信道攻击**——能提这一条是深水区加分。

**服务器推送（PUSH）的退场**：H2 允许服务端预测性推送资源，**Chrome 2017 起废弃**——**预测命中率低（浪费带宽）+ 与 preload 语义重复 + 中间代理难处理**，**HTTP/3 已删除 PUSH**——「特性也会被历史退场」的活案例。

收尾：H2 答题主线，「**分帧是地基、多路复用是收益、HPACK 是红利、TCP 队头阻塞是遗产**」，最后一环自然引出 H3。

> 面试官追问点：流 ID 有什么讲究？应答思路：客户端发起的流用奇数、服务端（推送）用偶数——**新旧流 ID 不复用，单调递增**，这个设计让「流的优先级排序」和「连接内状态清理」都有确定的依据；最后一个流 ID 的通告还是优雅关闭（GOAWAY）的基础。

### 8.8 强缓存与协商缓存的决策树

答：一句话定调，**缓存决策树就一句「先问本地新鲜度（强缓存）再问服务器有效性（协商缓存）」，四种字段组合覆盖全部场景，而「刷新按钮」和「回车」走的是不同的树**。

**强缓存（不发请求）**：**Cache-Control（相对秒数，优先）压倒 Expires（绝对时间）**——max-age 未过就**直接用本地副本，状态码 200（from cache）**，一个字节请求都不发。**Cache-Control 的指令族**：no-cache（可缓存但每次要协商，**不是不缓存**——最高频误解）、no-store（真不缓存）、public/private（能否被 CDN 缓存）、s-maxage（代理层的专用寿命）、immutable（新鲜期内连协商都不发）。

**协商缓存（发请求但可能不传体）**：本地副本过期后，**带条件头发问**——**ETag/If-None-Match（指纹优先）** 或 **Last-Modified/If-Modified-Since（秒级精度兜底）**；服务器判定未变**回 304（无响应体，几百字节往返）**，变了回 200 加新资源。**ETag 优先的原因**：Last-Modified 只有秒级精度（一秒内改两次检测不到）、**内容没变但 mtime 变了会误判**（重新部署全量文件 mtime 更新——ETag 的内容哈希不受影响）、**集群部署的 mtime 可能不一致**。

**深水区一：from memory cache 与 from disk cache**——**内存缓存（当前标签页存活期，图片/CSS 常见，关闭标签即失效）比磁盘快**；**Chrome 的启发式**：无 Cache-Control 的资源按「Last-Modified 距今的 10%」估寿命（启发式缓存）——**「没设缓存头的资源也被缓存了」的困惑来源**。

**深水区二：刷新行为对缓存的绕过**——**地址栏回车/链接跳转**：完整决策树（强缓存直接用）；**普通刷新（F5）**：**强制走协商**（请求带 max-age=0，强缓存被跳过，304 仍可省流量）；**强制刷新（Ctrl+F5）**：**no-cache 发出、协商也跳过，全量重拉**（还带 Pragma: no-cache）——**「测试缓存效果别用 F5」是给前端做验证的经典提醒**，**三种刷新语义不同**是这题的实战深水区。

**工程要点**：**HTML 入口禁缓存（每次协商）+ 哈希命名的静态资源长缓存（max-age=31536000 + immutable）**——文件名带内容哈希，内容变名字变，旧缓存自然失效——**「入口短命、资产永生」是部署侧的缓存架构**。

收尾：缓存答题的心法，「**决策树（强→协商→200/304）+ 字段优先级（CC>Expires，ETag>LM）+ 刷新三态（回车/F5/CF5）**」，再补部署侧的「哈希文件名」实践就完整了。

> 面试官追问点：304 响应会更新缓存的元信息吗？应答思路：会——304 可以携带新的 Cache-Control/Expires（服务器借此「续期」本地副本），这也是「动态控制客户端缓存寿命」的通道；严格说 304 携带的头「只更新与缓存相关的头」，其余头忽略。

### 8.9 DNS解析的全链路与优化

答：一句话定调，**DNS 的查询是「客户端-本地域名服务器递归、本地服务器对上游迭代」的两段式，浏览器缓存-系统缓存-路由器-hosts-本地服务器的多层缓存决定速度，HTTPDNS 是绕过它的革命**。

**两段式分工**（概念最容易混的点）：**客户端只问「本地域名服务器」（运营商的 recursive resolver），说『帮我查到结果再回来』（递归责任）**；**本地服务器自己逐级问**（迭代）：**根（给 .com 的 NS）→ 顶级域（给 example.com 的 NS）→ 权威服务器（给最终 IP）**——**「递归是责任模式，迭代是问路模式」**，一次解析背后最多四台服务器接力。

**多层缓存的位置与 TTL**：**浏览器（60s 级）→ 系统 hosts 与缓存 → 路由器 → 运营商本地服务器（TTL 递减）**——**域名的 TTL 太短（30s）会让递归层频繁回源**（DNS 查询放大），**太长（24h）会让故障切换变慢**——**TTL 是「变更速度 × 查询成本」的调节阀**（典型 300-600s 折中，大故障前会临时调短预热）。

**深水区一：DNS 劫持与污染的机理**——**劫持**：本地服务器（或路径上的劫持设备）**直接返回伪造的 A 记录**（弹广告的 302 跳转 IP）；**污染**：**伪造的应答比真应答先到**（DNS 基于 UDP 无鉴权，谁先到听谁的）——**防御：DNSSEC（对记录做签名链验证，部署率低）或干脆绕过**。

**深水区二：HTTPDNS 的绕行设计**——**把 DNS 查询从 UDP 53 搬到 HTTP(S) 80/443**：客户端直接向 HTTPDNS 服务发 HTTP 请求拿 IP——**内容加密（防污染）、直连（绕运营商 LocalDNS，杜绝劫持和跨网调度错误）、调度精确（客户端上报网络环境，服务端就近返回）**；**返回 IP 后的连接仍要过证书验证**（SNI 扩展让 IP 直连的 TLS 握手可行）——**国内 App（尤其调度敏感的 CDN/直播业务）的标准配置**。**配套的「预热与缓存」**：启动时预解析关键域名、**解析结果带 TTL 进本地缓存、失败降级系统 DNS**——HTTPDNS 是「重造 DNS 客户端」的工程。

**性能优化侧**：**dns-prefetch（对预测要用的域名预热）与 preconnect（DNS+TCP+TLS 一条龙）**、**资源的域名收敛**（H1 时代的域名分片是反向操作，H2 后又要收敛回单域名——**协议演进改变优化方向**的案例）。

收尾：DNS 答题的心法，「**两段式（递归+迭代）+ 多级缓存（TTL 是阀门）+ 两大攻击（劫持与污染）+ 一个革命（HTTPDNS）**」。

> 面试官追问点：为什么 DNS 用 UDP 又有 TCP 53 端口？应答思路：查询通常小（UDP 快、无连接开销）；**响应超过 512 字节截断转 TCP**（truncated 标志）、**区域传送（zone transfer）全量同步必须 TCP**——「快路径 UDP、大流量 TCP」的双轨设计。

### 8.10 WebSocket握手与帧协议

答：一句话定调，**WebSocket 的连接「生于 HTTP」（Upgrade 握手）、活于自己的帧协议，心跳与重连是应用层必须自建的**。

**握手机制**（借 HTTP 的壳）：客户端发 GET 带 **Upgrade: websocket / Connection: Upgrade / Sec-WebSocket-Key（16字节随机 base64）**；服务端 101 Switching Protocols + **Sec-WebSocket-Accept（Key 拼 GUID 后 SHA-1 再 base64）**——**这个回执算法的意义**：**证明服务端「懂 WebSocket 协议」而不是普通 HTTP 服务器返回了页面**（防误连与缓存代理的污染），**不是安全机制**（没有密钥协商，wss 才靠 TLS 加密）。**握手后 TCP 连接同一个，但协议状态机换到帧协议**——「连接复用、协议切换」。

**帧协议的设计**（深水区一）：

1. **帧头极简**：FIN（是否最后一帧）、opcode（**text=1/binary=2/close=8/ping=9/pong=10**）、**MASK（客户端到服务端的帧必须掩码）**、payload len（**7 位 + 16 位扩展 + 64 位扩展的三级长度编码**——小帧一个字节、大帧最多 9+8 字节）；
2. **分帧重组**：大消息拆多帧（FIN=0 的中间帧），**接收端按 opcode 聚合**——「流式发送任意大小消息」；
3. **掩码的攻击防御**：**客户端帧的 payload 与 4 字节掩码异或**——历史原因：**防止中间代理的缓存投毒**（攻击者借「看似 HTTP 的数据」污染代理缓存），**服务端帧不掩码**（服务器不被信任做这种攻击向量）。

**深水区二：心跳与断线重连的工程化**——**协议的 close/ping/pong 只是原语，业务健壮性自己搭**：

1. **心跳**：**客户端定时发 ping（应用层 JSON 也行），N 个周期没收到 pong 判死**——**为什么不用 TCP keepalive**：默认 2 小时太长、**探测不了「应用层假死」**（连接活着但进程卡死，TCP 正常收发但消息堆积）；
2. **重连退避**：立即重连风暴会打死刚恢复的服务器——**指数退避 + 抖动（jitter）**（1s,2s,4s...加随机量错峰）；
3. **消息补偿**：重连后**带最后序号拉增量**（服务端为离线期消息做队列或序号）——「连接断了」和「消息丢了」要分开治理。

**选型对照**：**单向推送（行情/通知）SSE 更简单**（纯 HTTP、自动重连、文本流）；**双向低延迟（IM/协同/游戏）WebSocket**；**HTTP/2 的 server push 已死、HTTP/3 无 push**——「双向实时」这个需求今天仍然只有 WebSocket（或 WebRTC datachannel）能优雅满足。

收尾：WebSocket 答题的心法，「**HTTP 生（Upgrade+Key 握手）、帧协议活（opcode/掩码/分帧）、心跳重连靠自建（退避加抖动）**」。

> 面试官追问点：为什么握手要自定义 Sec-WebSocket-Key 而不直接用 Origin 校验？应答思路：Key 的回执算法防「哑服务器」（不懂协议却 200 响应）；Origin 防的是「跨站滥用」（浏览器里 JS 拿用户凭证连内网 WS）——**两者防的攻击面不同，都要有**；这也是「握手安全性 = 协议证明 + 来源证明」的组合拳。
