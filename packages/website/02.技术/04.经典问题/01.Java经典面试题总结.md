# 1.语言基础

### 1.1 语法与常用类

#### Java有哪八种基本类型？包装类的缓存池有什么坑？

答：一句话定调，**八种基本类型存值本身，包装类的坑全在缓存池：valueOf 走缓存、构造器不走，== 比较因此时真时假**。

八种：byte(1字节)、short(2)、int(4)、long(8)、float(4)、double(8)、char(2)、boolean（规范未定大小，HotSpot 按 1 字节处理）。对应包装类 Byte/Short/Integer/Long/Character/Boolean。

**缓存池规则**：Byte/Short/Integer/Long 缓存 -128~127，Character 缓存 0~127，Boolean 就两个常量。Integer a = 127, b = 127，自动装箱走 IntegerCache.valueOf，a == b 为 true；换成 128，缓存外新建对象，== 变 false。**坑的根源就在这：装箱走缓存，new Integer(128) 永远是新对象**。

**拉开差距的深水区**：Integer 的缓存上界可用 -XX:AutoBoxCacheMax=N 调整，其它包装类的缓存写死（实现选择而非规范要求）——所以包装类比较的结果可能是环境相关的，这也是阿里规约强制包装类用 equals 的原因。

收尾：八种类型背熟只是入场券，能讲清 == 在缓存内外的行为差异才算过关。

> 面试官追问点：为什么 -128~127 这个区间？应答思路：byte 的范围就是 -128~127，选它做缓存是最自然的"一个字节世界"，其它数值类型沿用同一约定。

#### 各基本类型占几个字节？数值越界了怎么处理？

答：一句话定调，**越界不报错、直接环绕，处理手段三条：事前检查（上转型）、事后校正（Math.xxxExact）、终极兜底（BigInteger）**。

字节数：byte 1、short/char 2、int/float 4、long/double 8。int 上界约 21.4 亿，long 约 9.2×10^18。

**越界的本质**：补码运算溢出是环绕，Integer.MAX_VALUE + 1 直接等于 Integer.MIN_VALUE，**不抛任何异常**，这是它阴险的地方：错误会带着错误值继续往下算。

**处理三选**：事前检查用上转型，x + y 是否越界写成 (long)x + y > Integer.MAX_VALUE 再判断；事后用 JDK8 的 Math.addExact/subtractExact/multiplyExact，越界抛 ArithmeticException；真超范围直接 BigInteger（注意它不可变，每次运算都产生新对象，循环里做累加是性能事故）。

**拉开差距的深水区**：整型越界是环绕，**浮点越界是 Infinity 和 NaN**——double 乘爆得到 Infinity，NaN 和任何值都不相等（包括自己，NaN == NaN 为 false），判断要用 isNaN。

收尾：越界处理的第一原则是"运算前上转型"，而不是事后擦屁股。

> 面试官追问点：System.currentTimeMillis() 为什么用 long？应答思路：毫秒级时间戳早已超出 int 范围，用 int 存当前时间是一个经典线上事故，秒级时间戳 2038 年也会击穿 int。

#### char能存一个中文汉字吗？和编码什么关系？

答：一句话定调，**能存常用汉字（BMP 基本多文种平面内），存不了增补字符（emoji、部分生僻字），根因是 char 是 UTF-16 的代码单元，不是"一个字符"**。

char 两个字节，存的是 UTF-16 的一个 code unit。常用汉字码点都在 BMP（U+0000~U+FFFF）内，一个 char 放得下；码点超过 U+FFFF 的字符（emoji、部分古字）需要一对 char（代理对，surrogate pair）拼成，单个 char 放不下。

**三层概念捋清**：Unicode 是字符集（给字符编号，编号叫码点），UTF-8/UTF-16 是编码方案（码点怎么落地成字节）。"char 能不能存一个字"取决于这个字的码点是否在 BMP 内，而不是它是不是中文。

**拉开差距的深水区**："😂".length() == 2——**String.length() 数的是 code unit 不是字符数**，统计真实字符数要用 codePointCount；两个含代理对的字符串用 equals 比较时，比较的是代码单元序列，代理对拆开写和合体写可能不一致。

收尾：一句话记住，char 是 UTF-16 代码单元而非字符；JDK5 起 API 里真正的"字符"概念是 codePoint。

> 面试官追问点：JDK9 为什么把 String 的 char[] 改成 byte[]？应答思路：compact strings 优化——拉丁文本用 Latin-1 单字节存省一半内存，含中文等多字节文本才走 UTF-16，用哪个编码的标记存在 String 头部（coder 字段）。

#### 为什么0.1加0.2不等于0.3？浮点数怎么存的？

答：一句话定调，**0.1 在二进制里是无限循环小数，存储那一刻就被截断了，加出来的是 0.30000000000000004**。

**IEEE 754 的存储**：double 64 位 = 1 符号位 + 11 指数位 + 52 尾数位。十进制 0.1 转二进制是 0.0001100110011... 无限循环，52 位尾数装不下，第 53 位起丢弃（带舍入）。两个各自带误差的数相加，误差就在结果里暴露。

**正确比较**：一是误差范围法，Math.abs(a - b) < 1e-9；二是 BigDecimal 精确计算——**必须用字符串构造**，new BigDecimal(0.1) 传入的已经是带误差的 double，等于把错误提前锁死；BigDecimal.valueOf(0.1) 内部先走了 Double.toString，也可以。

**拉开差距的深水区**：BigDecimal 的 equals 连精度 scale 一起比，2.0 不 equals 2.00，**比数值要用 compareTo**；除法必须指定 RoundingMode，遇到除不尽（1/3）不指定直接抛 ArithmeticException；金融场景里 double 是禁区，金额用 BigDecimal 或以"分"为单位的 long。

收尾：根因一句话——二进制无法精确表示 0.1，正如十进制无法精确表示 1/3，存储即失真。

> 面试官追问点：float 和 double 谁误差大？应答思路：float 尾数 23 位约 7 位有效十进制数字，double 52 位约 15 位，尾数越短精度越差；工程默认 double，只有海量存储才权衡用 float。

#### ==和equals有什么区别？为什么必须同时重写hashCode？

答：一句话定调，**== 比基本类型的值、引用的地址；equals 比业务语义相等；hashCode 是 equals 的"分区索引"——只重写 equals 不重写 hashCode，HashMap 就丢数据**。

**== 的双语义**：基本类型比值（int 的 1 == 1），引用类型比地址（两个 new 出来的对象 == 恒 false）。equals 默认就是 ==（Object 的原生实现），重写后才有内容比较。

**为什么绑定 hashCode**：Object 的约定是 equals 相等的两个对象，hashCode 必须相等。HashMap 的查找路径是"先用 hashCode 定位桶，再用 equals 在桶内认人"。只重写 equals 的后果：两个逻辑相等的对象 hashCode 不同 → 落进不同的桶 → contains 永远找不到 → **key 存进去就等于丢了**，HashSet 去重同理失效。

**拉开差距的深水区**：hashCode 相等不代表 equals 相等（哈希碰撞，桶里排队就是为这个准备的）；equals 五条约定（自反/对称/传递/一致/对 null 返回 false）里最常被违反的是对称性——Effective Java 的经典案例：父类 Point.equals 和子类 ColorPoint.equals 互相不对称，混合放进集合后行为不可预期。

收尾：一句话——hash 定位、equals 认人，两个必须一起改。

> 面试官追问点：可变对象做 key 有什么坑？应答思路：put 之后修改了参与 hash 的字段，对象还挂在旧桶上，hashCode 变了再也找不回；要么用不可变对象做 key，要么当 key 期间绝不动它。

#### String/StringBuilder/StringBuffer有什么区别？

答：一句话定调，**String 不可变、拼接产生新对象；Builder 非线程安全但快；Buffer 全方法 synchronized；选型看"拼接次数 × 线程环境"**。

**不可变的设计动机**：字符串常量池可以全局共享（一份 "abc" 复用到天荒地老）；hashCode 可以缓存（第一次算完存起来，做 HashMap 的 key 极快）；安全性（路径、URL 这类参数传出去后无法被中途篡改）；并发天然安全。

**编译期优化**：纯常量拼接在编译期直接合并；变量拼接 JDK8 编译为 StringBuilder.append 链。**循环内拼接是重灾区**——每轮循环都 new 一个 Builder，正确做法是把 Builder 提到循环外。JDK9 起拼接改为 invokedynamic（StringConcatFactory），但循环内反复创建对象的坑依旧存在。

**拉开差距的深水区**：subString 在 JDK7u6 之前共享原数组（拷贝改为截断，导致小字符串拖着一个大 char[] 不释放，后来修复为拷贝）；String 的底层与 intern 原理深度精讲见 8.13。

收尾：单线程拼接用 StringBuilder，多线程共享用 StringBuffer，常量拼接编译器已经替你做了。

> 面试官追问点：为什么 StringBuilder 不重写 equals？应答思路：拼接器是工具不是值对象，Object 的 == 语义够用；反过来说 String 两者都重写且互相配合，才是它成为最常用 key 的原因。

#### Object的每个核心方法都是干什么用的？

答：一句话定调，**Object 的方法分三组：相等组（equals/hashCode）、协作组（wait/notify/notifyAll，本质是锁模型的一部分）、生命周期组（toString/clone/finalize，前两个是历史包袱）**。

**逐个过**：equals/hashCode 是相等语义的一对（上一题展开）。toString 默认是"类名@十六进制哈希"，日志排查的最低保障。clone 是浅拷贝：只复制字段的引用，引用类型字段两边共享，一改双变；想深拷贝要自己递归、走拷贝构造器或序列化。wait/notify 不是普通方法，**调用前提是已持有该对象的监视器锁**，否则抛 IllegalMonitorStateException——必须写在 synchronized 块内，且唤醒后要用 while 重新检查条件（防虚假唤醒）。

**finalize 为什么废弃**（JDK9 弃用）：不保证执行（GC 不跑就没有）；执行时机不定，资源释放被无限期拖延；能在 finalize 里"复活"对象（把 this 赋给静态引用），破坏 GC 假设；带 finalize 的对象要两轮 GC 才真正释放。替代：try-with-resources（确定性释放）和 Cleaner/PhantomReference（后知后觉的兜底）。

**拉开差距的深水区**：Cloneable 是标记接口，不实现直接调 clone 抛 CloneNotSupportedException——clone 方法在 Object 上、开关在接口上，这个分裂设计本身就是失败的证据。

收尾：wait/notify 归锁模型，equals/hashCode 归哈希容器，clone/finalize 是历史包袱——三个时代的东西凑在一个祖宗类里。

> 面试官追问点：wait 为什么必须配 while 而不是 if？应答思路：被唤醒不代表条件成立（虚假唤醒、条件被别人抢跑），while 会在醒来后重新检查，if 醒来直接走，条件不成立就是事故。

#### try里有return，finally还会执行吗？

答：一句话定调，**会执行，时机是 return 表达式求值之后、真正返回之前；但 finally 里写 return 是自毁装置，会吞掉 try 的返回值甚至异常**。

**执行机制**：try 里 return x 时，x 先求值存入返回槽，然后执行 finally，最后才把值送出去。所以 finally 里的代码正常都会跑，但**在 finally 里给基本类型变量重新赋值影响不了返回值**——值早拷贝进槽了。

**不执行 finally 的场景**：System.exit() 先于它；JVM 崩溃；守护线程在执行到一半时进程结束；finally 自己死循环（后面代码全没了）。

**拉开差距的深水区**：finally 里的 return 会覆盖 try 的 return 且吞掉 try 尚未抛出的异常（阿里规约明令禁止）；try-with-resources 的关闭顺序是**逆序（后声明的资源先关）**，close 抛的异常不覆盖主异常而是挂进 suppressed（getSuppressed 可取）——这是 JDK7 异常处理最精巧的设计。

收尾：finally 管资源释放，不管返回值——职责想清楚，坑就没了。

> 面试官追问点：finally 里修改返回对象的内容，方法外能看到吗？应答思路：能。返回槽存的是引用，finally 改对象字段外部拿到的就是改后状态；但改基本类型无效、让引用指向新对象也无效（槽里还是旧引用）。

#### 说一下Java的异常体系？Error和Exception的区别？

答：一句话定调，**Throwable 一分为二：Error 是 JVM 级的病不该接（OOM/StackOverflow），Exception 分受检（编译器逼你处理）与非受检（RuntimeException，运行才炸）**。

**体系**：Throwable ← Error（OutOfMemoryError、StackOverflowError、NoClassDefFoundError）+ Exception ← 受检异常（IOException/SQLException，编译期强制 try 或 throws）+ RuntimeException（NPE/数组越界/算术异常/类转换异常）。

**设计意图**：受检异常表达"可预期、可恢复"（文件不存在，该提示用户重选）；非受检表达"程序 bug"（NPE 是代码错了，修它而不是接它）；Error 表达"接了也没用"（OOM 时你连提示框都 new 不出来）。

**性能**：异常的成本大头在**构造时的 fillInStackTrace**（抓整条调用栈），抛和接本身不贵；不抛的异常是零成本——JIT 对隐式异常（空指针、除零）用硬件信号机制，根本不产生真异常对象。

**拉开差距的深水区**：受检异常是 Java 的原创也是争议之王——Kotlin/C# 全砍了它（强制声明导致 API 签名污染、lambda 里没法 throws，被迫包成 RuntimeException），语言演进的立场反水，能讲到这层就是亮点。

收尾：选型口诀——可恢复用受检，程序 bug 用非受检，JVM 的病别治。

> 面试官追问点：为什么规约禁止异常做流程控制？应答思路：构造时抓栈的常数成本乘上高频路径就是吞吐坍塌；业务失败能用返回值/null/Optional 表达，别用异常。

#### 什么是泛型擦除？哪些位置的内容会被擦除？

泛型擦除理解。深度精讲见 8.12。

答：一句话定调，**泛型只活在编译期，编译后类型参数擦成上界（无上界则 Object），但声明侧的泛型信息以 Signature 属性保留在字节码里，反射能读到**。

**擦什么**：字段的泛型类型 List<String> 擦成 List；方法参数和返回值的 T 擦成上界（<T extends Comparable> 擦成 Comparable）；方法体里局部变量的 T，编译器已经替你插好了 checkcast 强转。

**不擦什么**：类和方法的泛型声明——它们以 Signature 属性存在，getGenericReturnType/getGenericType 能还原出 List<String>。所以"擦除"擦的是运行对象身上的类型，没擦定义处的元信息。

**因此不能做的事**：new T()（运行时不知道 T 是谁）；T.class（同理）；instanceof List<String>（擦除后无差别）；new T[10]（泛型数组）。

**为什么这么设计**：兼容性。JDK5 引入泛型时，已编译的 1.4 类库必须无缝对接，擦除是向历史妥协的方案；C# 的具化泛型性能更好但没法平滑迁移。

**拉开差距的深水区**：static 方法为什么不能用类上声明的 T？因为擦除后它拿不到"每个实例各自的 T"，类的泛型参数挂在对上；static 要泛型必须自己声明 <T>。桥方法怎么保多态，见 8.12 深讲。

收尾：泛型是编译器替你插强转的语法协议，跑起来 JVM 根本不认识 <T>。

> 面试官追问点：既然擦除了，反射怎么拿到 List<String> 的 String？应答思路：读的是声明侧签名（字段/方法定义处），不是运行对象；对象身上永远拿不到 T，能拿到的只有定义处的元信息。

#### 反射的原理是什么？为什么说它性能差？

答：一句话定调，**反射是运行期读类的元信息（Class 对象是入口）来调方法改字段，性能差的锅在"查找、安全检查、无法内联"三件事上**。

**原理**：类加载后，方法区/元空间里存着类的完整描述，Class 对象是这份描述的入口。getMethod/getField 本质是查方法表/字段表（带访问权限校验），invoke 最终走 Method 的本地实现。

**性能三宗罪**：①查找是遍历（接口方法的默认方法解析尤其费）；②每次 invoke 都有访问权限检查；③JIT 看不透反射调用，无法内联，参数还得装箱进 Object[]。

**怎么救**：setAccessible(true) 跳权限检查（JDK9+ 模块化后对 JDK 内部类有额外限制）；缓存 Method 对象，别每次都 getMethod；极致场景上 MethodHandle（可被 JIT 当直接调用优化）或 LambdaMetafactory（快到接近直接调用）。

**拉开差距的深水区**：反射 + 注解是所有框架的地基（Spring 的 IOC/AOP、MyBatis、Jackson 全靠它）；且泛型信息在声明侧的 Signature 属性里，反射靠 getGenericType 拿到的其实是元信息，不是运行时对象身上的 T。

收尾：反射的慢是"相对直接调用"的慢；框架里那点开销换来了灵活性，你自己的热路径别用。

> 面试官追问点：框架为什么不嫌反射慢？应答思路：扫描和实例化集中在启动期，运行期高频调用已被动态代理和 JIT 优化接管，摊销后占比可忽略。

#### 注解分哪几类？和反射是怎么配合工作的？

答：一句话定调，**注解本身只是贴在代码上的标签，按保留期分三档（SOURCE/CLASS/RUNTIME），RUNTIME 档配合反射在运行期读取，是框架魔法的全部原理**。

**四个元注解**：@Target（能贴哪：类/方法/字段/参数）、@Retention（活多久）、@Documented（进文档）、@Inherited（子类可继承父类的注解）。

**按 Retention 分三档**：SOURCE——编译后即丢（@Override 校验完就扔、Lombok 在编译期改字节码）；CLASS——进字节码但运行不加载（ASM/AspectJ 等字节码工具的织入期用）；RUNTIME——反射可读（Spring 的 @Service、Jackson 的 @JsonProperty 全在这档）。

**与反射的配合**：Class.getAnnotation / Method.isAnnotationPresent——框架启动时扫类路径，找到贴了 @Component 的类就反射实例化放进容器，@Autowired 再反射注入。**注解负责"声明在哪"，反射负责"找到它并干活"，框架就是这两者加一个启动时扫一圈的循环**。

**拉开差距的深水区**：编译期注解处理（APT）是另一条路——处理器在编译期直接生成代码（Lombok、MapStruct），零运行时开销，性能敏感的框架选它而不是 RUNTIME 反射。

收尾：注解是被动的元数据，反射是主动的解释器，两者合体才有 Spring。

> 面试官追问点：Spring 为什么不把 @Component 做成编译期处理？应答思路：IOC 需要运行期动态性（条件装配、profile、运行时注册 Bean）；编译期注解适合"生成静态代码"，两者服务不同性质的工作。

#### JDK动态代理和CGLIB有什么区别？各自原理？

答：一句话定调，**JDK 代理基于接口（生成 $Proxy0 转发 InvocationHandler），CGLIB 基于继承（ASM 生成子类覆写方法），分界线是"你的类有没有接口、有没有被 final"**。

**JDK 动态代理**：Proxy.newProxyInstance 在运行期生成 $Proxy0——它 extends Proxy 且 implements 你的接口。**只能代理接口的根因：生成的类把唯一的继承名额用在 Proxy 上了**。所有方法调用统一转给 InvocationHandler.invoke(proxy, method, args)，再反射执行目标方法。

**CGLIB**：用 ASM 直接生成目标类的子类，覆写非 final 方法，拦截逻辑在 MethodInterceptor.intercept 里。要求类有无参构造器（子类实例化要走父类构造）；final 类和 final 方法代理不了。

**拉开差距的深水区**：①Spring 的策略：目标有接口默认 JDK，无接口用 CGLIB；Spring Boot 2.x 起默认全走 CGLIB（proxyTargetClass=true），避免接口注入时的类型歧义；②**自调用失效**：代理对象里 this.method() 走的是原对象，绕过代理——事务注解失效的经典事故，解法是拆类或 AopContext.currentProxy()；③JDK17+ 模块系统限制了动态生成类，深反射要加启动参数。

收尾：接口用 JDK、无接口用 CGLIB、final 谁也救不了、自调用谁也拦不住。

> 面试官追问点：代理对象做 equals 为什么常出问题？应答思路：JDK 代理会把 equals/hashCode 也转给 handler，若 handler 里拿目标对象比较，会出现代理与目标 equals 不对称（a.equals(b) 不等于 b.equals(a)），当 key 用要小心。

#### Java8的Lambda和Stream你用过哪些新特性？

答：一句话定调，**Lambda 不是匿名内部类的语法糖（底层是 invokedynamic 运行时生成），Stream 的核心是惰性求值：中间操作只攒管道，终止操作才遍历一次**。

**Lambda 的本质**：编译成 invokedynamic 指令，由 LambdaMetafactory 在运行期生成实现类。与匿名内部类的差别：不强制捕获外围 this（无状态 lambda 更轻）、不产生 .class 文件膨胀、JIT 可将其优化成普通方法调用。

**Stream 三段论**：源 → 中间操作（filter/map/sorted，惰性，只描述不执行）→ 终止操作（collect/reduce/forEach，触发唯一一次遍历）。**短路操作**（limit/findFirst/anyMatch）让无限流可用、能提前收工。

**拉开差距的深水区**：①并行流默认共用 ForkJoinPool.commonPool，IO 密集任务会饿死其它并行流，且有序源的合并开销可能让并行反而更慢；②peek 是带副作用的中间操作，没有终止操作触发它根本不执行，调试可以、当 forEach 用是坑；③Optional 防的是返回值 NPE，设计者明确说过它不适合做字段和参数；④新时间 API 全部不可变（LocalDate vs 可变的 Date），线程安全且月语义清晰（Month.FEBRUARY 不再是 1）。

收尾：Lambda 答原理（invokedynamic 而非糖），Stream 答惰性与短路，这两个词一出口，这题就从"用过"升级到"懂"。

> 面试官追问点：为什么说 Stream 不是数据结构？应答思路：它是管道描述符，数据仍在源里；中间操作返回的是新管道不是新数据，所有操作在一次遍历里流水完成，这是它优于"多次循环拼接"的根本原因。

### 1.2 面向对象

#### 抽象类和接口有什么区别？项目里怎么选？

答：一句话定调，**抽象类是"是什么"（is-a，模板复用），接口是"能做什么"（can-do，能力契约），选型的第一问是：我要复用骨架，还是只定义契约**。

**语法差异**：抽象类可以有构造器（供子类 super 调用）、成员变量、具体方法，单继承只能选一个爹；接口的变量默认 public static final，JDK8 后可以有 default 和 static 方法，JDK9 后可以有 private 方法，一个类可以实现多个接口。

**项目里怎么选**：模板方法模式选抽象类——骨架代码（流程、公共逻辑）写死在父类，子类填空（JDK 的 AbstractList 就是模板：get/size 抽象，其余全给你实现好了）；定义能力维度选接口——Comparable、Serializable 这种"贴上就有这个能力"的横向契约，与类继承树无关，一个类可以同时拥有多个能力。

**拉开差距的深水区**：①一个类实现两个接口有同名 default 方法，必须重写并手动指定走哪个（InterfaceA.super.method()），菱形冲突 Java 用"显式解决"而非超类优先规则；②抽象类有构造器但不能实例化——构造器存在的意义是被子类链调用，不是矛盾是分工；③default 方法是给已发布接口"无痛演进"用的（Collection 加 stream()），不是为了替代抽象类。

收尾：骨架复用用抽象类，能力拼接用接口；Java8 后界限变模糊，但"继承树 vs 能力标签"的语义分工从未变过。

> 面试官追问点：为什么接口的 default 方法不能覆盖 Object 的方法（如 toString）？应答思路：接口不继承 Object 的实现地位，若允许 default toString 会造成多实现的歧义；JLS 明确禁止，核心接口的语义必须由类层级兜底。

#### 四种内部类分别什么区别？各自用在什么场景？

答：一句话定调，**四种内部类的分界线只有一条：持不持有外围实例的引用——静态嵌套类不持有，成员/局部/匿名类都持有，匿名的额外约束是访问局部变量必须有效 final**。

**逐个过**：静态嵌套类（static class）不持有外围实例，本质是"写在别的类里面的普通类"，不依赖外部对象就能 new；成员内部类持有外围引用（Outer.this），能直接访问外围实例的字段和方法，代价是每个实例多一根指向外围的指针，还可能导致外围对象泄漏；局部内部类定义在方法里，作用域出方法即亡；匿名内部类是局部类的"声明即实例化"形态，没有类名、只能用一次，事件回调和旧式线程的标配。

**为什么匿名内部类访问局部变量必须有效 final**：局部变量在栈上，方法结束就没了，而匿名类对象的生命周期可能超过方法（回调）。Java 的解法是**拷贝一份变量的副本进匿名对象**——如果变量还能变，副本和本体就分叉了，所以干脆要求 final，让"拷贝一致性"成立。

**拉开差距的深水区**：Lambda 和匿名内部类的区别——匿名类会在自己的 this 上多包一层（this 指匿名类实例），**Lambda 不引入新 this，this 直接指外围实例**；且 Lambda 走 invokedynamic 运行时生成（见 1.1 第 14 题），不捕获外围 state 时更轻。这就是为什么循环变量能被 Lambda 用（有效 final），而成员变量随便改。

收尾：内部类的灵魂问题只有一个——它跟外围实例是什么关系；四种分类只是这个关系在不同位置（类级/方法级/表达式级）的表现。

> 面试官追问点：成员内部类为什么可能造成内存泄漏？应答思路：内部类实例持有外围引用，把内部类对象交给长生命周期容器（如静态缓存、线程池）后，外围实例被这根隐式引用拖着无法回收，匿名类做回调时是重灾区。

#### 重写和重载有什么区别？各自的规则是什么？

答：一句话定调，**重写是"子类改父类的同一个方法签名"（运行时多态），重载是"同一个类里多个同名不同参的方法"（编译期静态分派）**——一个看接收者，一个看参数。

**重写的规则"两同两小一大"**：方法名和参数列表相同；返回值和抛出的异常要更小或相同（协变返回类型允许缩窄，如父类返回 Object 子类返回 String）；**访问权限要更大或相同**（父 public 子不能 default，放大可以缩小不行）。附加规则：static/private/final 方法不能被重写。

**重载的匹配优先级**（精度从高到低）：完全匹配 → 宽化（int → long → double）→ 装箱（int → Integer）→ varargs。**坑在宽化优先于装箱**：调 f(1) 有 f(long) 和 f(Integer) 两个候选时，走 f(long)——历史上把 null 传给 f(String) 和 f(Object) 的重载会选更具体的 f(String)，不明确时编译器直接报 ambiguous。

**拉开差距的深水区**：静态方法的"重写"其实是**隐藏（hiding）**——父类 static 方法子类同名同参，调用走哪个由**编译期引用类型**决定，不走运行时多态：Parent p = new Child(); p.staticMethod() 调的是 Parent 的。分派术语化表达：重载是静态分派（编译期定），重写是动态分派（运行期查 vtable）。

收尾：重写管"接收者是谁"，重载管"参数是什么"；static 方法从不参与多态，这是被问烂却常答错的点。

> 面试官追问点：private 方法真的不能被重写吗？应答思路：不能被重写但能被"重新定义"——子类写一个同签名方法不是 override 而是新方法（没有 @Override 的语义），字节码层面父类 private 方法根本不在子类的可继承方法集里。

#### 继承和聚合有什么区别？什么时候该用哪个？

答：一句话定调，**继承是 is-a 的强绑定（子类能替换父类），聚合是 has-a 的松组合（整体持有零件），默认选聚合，继承只留给"语义上真的是"的关系**。

**两者的机制差异**：继承是编译期绑定，子类自动获得父类全部非私有成员，改父类会波及所有子类（脆弱基类问题）；聚合是运行期持有，整体对象持有零件的引用，零件可以替换、可以多个整体共享。**组合优于继承**是 Effective Java 的头条条款：聚合不破封装，只依赖零件的公开接口。

**什么时候用继承**：满足里氏替换——任何用到父类的地方换成子类行为依然正确。ArrayList is-a List 成立；"栈 extends 数组"就不成立（栈不需要中间插入，父类的行为对子类是错的），JDK 早期 Stack extends Vector 就是著名的反面教材，正确姿势是 Stack 里持有一个 Deque。

**为什么类只能单继承、接口可以多实现**：类的多继承有**菱形问题**（两个爹有同名实现，听谁的）；接口在 JDK8 前没有实现体，多实现天然无冲突，default 方法引入后的同名冲突也要求显式重写解决（见 1.2 第 1 题）。C++ 用虚继承解菱形，代价是复杂度爆炸，Java 直接砍掉。

**拉开差距的深水区**：组合/聚合/依赖三连——聚合是持有且共生命周期（部门和员工），组合是持有且零件随整体生灭（人和心脏），依赖只是用一下（方法参数）；面试能分层讲这三个词，比背 is-a/has-a 高一档。

收尾：继承表达"我是什么"，聚合表达"我有什么"；白盒复用（继承）是蜜糖，黑盒复用（聚合）才是工程默认。

> 面试官追问点：什么时候继承反而比聚合合适？应答思路：模板方法模式——流程骨架必须父类统一控制，子类只填空时，聚合反而要把所有钩子暴露成接口，组合爆炸；is-a 关系真实存在且稳定时，继承更简洁。

#### Java到底是值传递还是引用传递？为什么？

答：一句话定调，**Java 只有值传递，只是"值"有两副面孔：基本类型传的是值的拷贝，对象传的是引用的拷贝**——拷贝引用指向同一个对象，所以方法内改属性外部可见。

**三个实验讲透**：第一，传 int 给方法改值，外部不变——拷贝被改了，本体没动。第二，传一个 Person 对象，方法里改 p.name，外部可见——拷贝的引用和原引用指向同一个对象，改的是对象本身。第三，方法里 p = new Person() 再改，外部不变——**被改的是引用拷贝的指向，原引用纹丝不动**。第三个实验是判别"引用传递"的试金石：真引用传递（如 C++ 的 &）里这个赋值会改到外部引用，Java 不会。

**String 作为参数为何外部不变**：String 不可变（1.1 第 6 题），方法内对它的一切"修改"都是创建新对象并改引用拷贝的指向，落入第三个实验的情形。

**拉开差距的深水区**：参数传递的字节码视角——方法调用前引用被压入操作数栈再拷贝给局部变量表，**"传值"不是设计选择而是栈机执行模型的直接推论**；swap(Object a, Object b) 在 Java 里永远不可能成功，就是这个模型的判决。

收尾：一句话——Java 传的永远是"值的拷贝"，对象场景下这个值恰好是引用。

> 面试官追问点：那为什么有人坚称 Java 有引用传递？应答思路：把"传引用（的拷贝）"口语化说成"引用传递"；术语上引用传递指传参别名（能改外部变量本身），Java 的引用拷贝做不到别名语义，这是两码事。

#### final、finally、finalize三者的区别是什么？

答：一句话定调，**三个词只是长得像亲戚：final 是修饰符（不可变/不可覆盖），finally 是异常模型的一部分（必执行的收尾），finalize 是已废弃的回调（GC 临终关怀）——一个管编译，一个管流程，一个管回收**。

**final 的三副面孔**：修饰类——不能被继承（String、Integer）；修饰方法——不能被重写（可被重载）；修饰变量——引用不可再指别人（**final ≠ 不可变对象**：final Person p，p 仍可改字段，只是 p = new Person() 不行）。成员 final 必须在声明/构造器/实例块里完成赋值，构造完保证可见（JMM 语义下 final 字段禁止重排序出构造器）。

**finally**：见 1.1 第 8 题，管资源释放，不管返回值。

**finalize**：见 1.1 第 7 题，JDK9 起废弃，替代方案 Cleaner。

**拉开差距的深水区**：①final 类能否修改属性？能，final 锁的是继承不是字段；②为什么匿名内部类引用外部局部变量要有效 final？——跨作用域拷贝一致性（1.2 第 2 题），跟"不可变"无关，跟"拷贝不分离"有关；③**final 字段的内存语义**：构造器内对 final 字段的写，与构造器结束前的重排被禁止——其它线程拿到引用时 final 字段必是构造完成的值，这是不可变对象能线程安全发布的地基。

收尾：一个词一个世界；把它们放一道题里纯属发音巧合。

> 面试官追问点：为什么局部变量不用 final 修饰也"有效 final"就行？应答思路：JDK8 起编译器只要求"事实上没被二次赋值"，语言放宽了形式（Lambda 普及的配套），字节码层面拷贝一致性约束没变。

#### 静态方法能被重写吗？静态块的执行顺序说一下

答：一句话定调，**静态成员能被继承、不能被重写——同名同参在子类叫隐藏（hiding），调用走编译期类型不看运行时对象；执行顺序的口诀是：父静态 → 子静态 → 父实例 → 父构造 → 子实例 → 子构造**。

**为什么不能重写**：重写依赖运行时多态，多态的前提是"通过对象找方法"（vtable 查的是实际类型）。静态方法不属于任何实例，调用在编译期就按引用类型静态绑定，子类的同名方法只是**遮住了**父类的（用父类引用调用，走父类的）。这也是静态方法里不能用 this 和 super 的根因。

**完整初始化顺序**（父类 Person，子类 Man）：①父类静态变量 + 静态块（按代码顺序）②子类静态变量 + 静态块 ③父类实例变量 + 实例块 ④父类构造器 ⑤子类实例变量 + 实例块 ⑥子类构造器。静态只发生一次（类加载期），实例部分每次 new 都走一遍。

**拉开差距的深水区**：①静态块里只能访问"排在它前面"的静态变量（按代码顺序，声明在后面的读得到变量名但值是默认值——非法前向引用编译器会拦，绕过的方式是方法间接访问，值是默认值）；②**类加载不等于静态初始化**：类加载（Loading）和初始化（<clinit> 执行）是两个阶段，初始化被"首次主动使用"触发（new、访问静态、反射等），被动引用（子类引用父类常量）不触发；③常量（static final 编译期常量）在编译期就被内联进调用方，连"访问"那个类都算不上。

收尾：静态是类维度的东西，多态是对象维度的东西，两个维度永远不相遇。

> 面试官追问点：main 方法执行前 JVM 做了什么？应答思路：加载主类触发其 <clinit>（静态块此时执行），父类先初始化（接口有 default 方法才会初始化父接口）——所以静态块的异常会直接 ExceptionInInitializerError，且类标记为不可再用。

# 2.集合框架

### 2.1 List与Set

#### 说说Java的集合体系？ArrayList和LinkedList怎么选？

答：一句话定调，**两大主干 Collection 与 Map 互不继承，List 有序可重复、Set 去重、Map 键值对；ArrayList 和 LinkedList 的选型真话是：九成场景用 ArrayList，链表只在"两端频繁进出"时翻盘**。

**体系**：Collection ← List（ArrayList/LinkedList/Vector）、Set（HashSet/LinkedHashSet/TreeSet）、Queue（ArrayDeque/PriorityQueue）；Map 是独立主干（HashMap/LinkedHashMap/TreeMap/Hashtable），Set 本质上是 Map 的 key 视图（下一题展开）。Queue 家族才是 LinkedList 的真实赛场。

**选型逻辑**：ArrayList 底层 Object[]，随机访问 O(1)、尾部增摊还 O(1)、中间插删要 System.arraycopy 整段挪；LinkedList 底层双向链表，按下标访问要逐节点走 O(n)，**但头尾操作 O(1)**。所谓链表增删快是有前提的：增删的两端，或者你已经拿到了节点（迭代器位置）；按 index 找过去再删，链表全程被数组吊打。加上 CPU 缓存对连续内存的友好（链表节点内存散布，cache miss 翻倍），**工程默认无脑 ArrayList**。

**拉开差距的深水区**：Arrays.asList 的坑——返回的是**视图不是拷贝**（改它会同步改原数组），且不支持 add/remove（固定长度，调了抛 UnsupportedOperationException）；Collections.unmodifiableList 是浅不可变（元素对象仍可改）；List.of 才是真不可变。

收尾：把选型讲成"数组的缓存友好性压倒链表的理论优势"，比背复杂度表高一档。

> 面试官追问点：为什么 ArrayList 的 get 是 O(1)？应答思路：底层数组加下标直接寻址（base + index * elementSize 一条指令），这是 JVM 数组指令 aaload 的直接支持；泛型擦除后数组是 Object[]，所以不能有 List<int>（见 1.1 泛型题）。

#### ArrayList怎么扩容的？怎么保证它的线程安全？

答：一句话定调，**1.5 倍扩容 + System.arraycopy 整段搬家；线程安全别用 Vector（历史遗留），读多写少用 CopyOnWriteArrayList，通用场景上锁或换并发容器**。

**扩容机制**：无参构造初始是空数组，首次 add 分配 10；满了扩到 1.5 倍（oldCap + oldCap >> 1），10 → 15 → 22 → 33，int 溢出保护取 MAX_VALUE。扩容的代价是分配新数组加整段拷贝——所以能预估大小时，new ArrayList<>(expectedSize) 一步到位是标准优化，避免反复搬家。

**与 Vector 的区别**：Vector 的所有方法都 synchronized（锁住 this），过时不是因为它慢，而是**锁粒度太粗**：并发读也互斥、复合操作（先判空再取）还是不原子。Collections.synchronizedList 同病——包一层同步，遍历时仍要手动 synchronized(list)。

**线程安全的正确姿势**：读多写极少（监听器列表、配置表）用 **CopyOnWriteArrayList**——写时复制新数组、读永远无锁无快照，代价是每次写复制整个数组和弱一致性（迭代器不反映写后状态）；通用场景要么显式锁，要么干脆换 Queue/Map 等结构性并发方案。

**拉开差距的深水区**：CopyOnWriteArrayList 的迭代器是**创建瞬间的数组快照**，遍历期间别的线程的写它完全看不见，也不抛 ConcurrentModificationException——这不是缺陷是设计（fail-safe 语义，见 2.1 第 5 题）。

收尾：扩容答"1.5 倍 + 拷贝"，线程安全答"Vector 是错的答案，COW 是场景答案"。

> 面试官追问点：为什么 COW 不适合写多场景？应答思路：每次写复制 O(n) 数组，写放大严重且给 GC 添乱；监听器列表写一次读一万次才划算，写频繁时锁竞争反而比复制便宜。

#### LinkedList的底层是什么？和ArrayDeque怎么选？

答：一句话定调，**LinkedList 是双向链表实现了 List 和 Deque 双接口，但两头不讨好：当 List 被 ArrayList 碾压，当队列/栈被 ArrayDeque 碾压——它的存在价值主要是面试题**。

**底层结构**：双向链表，first/last 两个指针，节点三件套（item、prev、next）。它能当队列（offer/poll）也能当栈（push/pop），因为 Deque 接口两头通吃。与 ArrayList 的性能对比见 2.1 第 1 题：随机访问 O(n) vs O(1)，头尾操作 O(1) vs O(n)。

**和 ArrayDeque 怎么选**：做队列/栈，**默认 ArrayDeque**，几乎全面占优。原因：①底层是**循环数组**，头尾指针在数组里绕圈走，两头操作都是 O(1) 且无节点分配；②连续内存对缓存友好，链表每个节点都是独立堆对象，一次遍历的 cache miss 量级不同；③每个链表节点多 2 个引用的内存开销（16 字节/节点起步），还有 GC 压力。ArrayDeque 唯一的短板：不允许 null 元素（用 null 判断空位）。

**拉开差距的深水区**：ArrayDeque 的扩容是**翻倍且重新对齐**——循环数组翻倍时要把两段（头指针到尾、头到数组尾）搬到新数组，对齐到新的头尾位置，比 ArrayList 的线性拷贝多一步逻辑；LinkedList 的 size() 是 O(1)（内部维护计数，不是遍历）——这是它少数能加分的细节。

收尾：需要队列选 ArrayDeque，需要随机访问选 ArrayList，LinkedList 是那个"理论正确、实践少用"的选项。

> 面试官追问点：为什么 ArrayDeque 不允许 null？应答思路：循环数组用 null 表示空槽位，poll 返回 null 的语义已约定为"队列为空"，存 null 会让两者无法区分——和 ConcurrentHashMap 禁 null 的动机同源（见 8.7）。

#### HashSet底层怎么实现的？怎么保证元素不重复？

答：一句话定调，**HashSet 就是一个"只有 key 没有 value"的 HashMap 壳子，不重复的保证是 hashCode 分桶加 equals 认人，TreeSet 则是 TreeMap 壳子加红黑树**。

**底层实现**：HashSet 内部持有一个 HashMap，add(e) 实际执行 map.put(e, PRESENT)，PRESENT 是个共享的哑对象。所以 HashSet 的性能特征、扩容行为、null 规则（允许一个 null）全部继承自 HashMap。LinkedHashSet 再叠一层双向链表维持插入序。

**怎么保证不重复**：先 hashCode 定位桶，桶内再用 equals 逐个比对——**hash 拦住绝大多数，equals 做最后裁决**。这就是重写 equals 必须重写 hashCode 的完整闭环（1.1 第 5 题）：hash 错了根本进不了同一个桶，equals 没机会见面。

**TreeSet 的有序**：底层 TreeMap，红黑树按 Comparable 或 Comparator 排序，增删查都是 O(log n)，代价是每次操作带比较成本，遍历有序是它独有价值。

**拉开差距的深水区**：HashSet 允许一个 null（HashMap 的 null key 走单独桶 0），TreeSet 不允许 null（第一次比较就 NPE）；HashSet 的迭代顺序是"hash 后的槽位序"，看着像随机其实是确定性的（同 JDK 同数据同序，跨 JDK 不保证）——**依赖这个顺序做断言的测试会在升级 JDK 后碎掉**。

收尾：Set 不是独立数据结构，是 Map 的 key 语义视图——这句话本身就是本题的满分答案。

> 面试官追问点：HashSet 和 TreeSet 的选型？应答思路：纯去重用 HashSet（O(1)）；需要有序遍历、范围查询（subSet/headSet/tailSet）或自定义排序语义才用 TreeSet；需要插入序用 LinkedHashSet——三个 Set 对应三种"序"的定义。

#### 遍历List时怎么安全删除元素？fail-fast是什么？

答：一句话定调，**fail-fast 是"迭代期间发现结构被改，立即抛 ConcurrentModificationException 自杀止损"的机制，靠 modCount 计数器实现；安全删除只有三条正路：iterator.remove、removeIf、倒序下标遍历**。

**产生原因**：ArrayList 维护一个 modCount（结构修改次数），迭代器创建时快照一份 expectedModCount。每次 next() 检查两者是否相等，**不等说明迭代期间有人动了结构**（list.remove 而不是 iterator.remove），立刻抛 CME。这是尽力而为的错误检测：单线程里它是可靠的 Bug 信号，多线程里它是概率性的（不保证抛，但抛了一定有并发写）。

**为什么直接 list.remove 会出事**：①跳元素——删除后后面元素前移，游标却照常 ++，紧挨着被删的那个被跳过；②尾部删除的巧合——删倒数第二个元素时 next 恰好不再检查，不抛异常但删错了。

**三条正路**：迭代器自己的 remove（同步更新 expectedModCount）；JDK8 的 removeIf（内部就是迭代器删除的正确封装）；普通 for **倒序遍历**（删 i 前移的是后面的元素，已遍历过，游标 -- 不受影响）。

**拉开差距的深水区**：fail-fast vs fail-safe——java.util 的老容器都是 fail-fast（改了就炸）；java.util.concurrent 的容器是 fail-safe（COW 系迭代器拿数组快照、ConcurrentHashMap 迭代器弱一致，**遍历不炸但可能读到旧数据**）。安全的代价从"立刻失败"换成了"可能过期"，两套语义对应两种取舍。

收尾：遍历中改结构，单线程用 removeIf，并发场景直接上并发容器——别和 modCount 斗智斗勇。

> 面试官追问点：为什么 CME 是"尽力而为"而不是保证？应答思路：modCount 是普通 int 非 volatile，比较本身也非原子，纯靠单线程时序成立；它设计目标就是单线程 Bug 检测器，把并发安全寄望于它是对机制的误用。

### 2.2 Map族

#### HashMap的底层实现说一下？什么情况链表转红黑树？

1.7 与 1.8 的差异，1.8 中什么情况下转换为红黑树，构造函数中参数代表的意思。深度精讲见 8.6。

答：一句话定调，**1.8 的 HashMap 是"数组 + 链表 + 红黑树"，hash 扰动加位运算定位，链长 8 且数组 64 才树化，扩容走高低位链拆分**。

**put 主链路**：key 的 hashCode 高 16 位与低 16 位异或（扰动，让高位参与定位），`(n-1) & hash` 定位桶；桶空直接放，冲突尾插，链长到 8 且数组 ≥64 转红黑树（数组 <64 优先扩容不树化）。负载因子 0.75，元素超 `容量×0.75` 触发翻倍扩容。

**构造函数三个参数**：initialCapacity（初始容量，会被 tableSizeFor 抬到 2 的幂）、loadFactor（触发扩容的阈值比例，默认 0.75）、JDK8 起还有一个 boolean 无实际作用的兼容参数。

**1.7 到 1.8 的三大变化**：头插改尾插（修复并发扩容成环）；引入红黑树（hash 攻击兜底）；扩容从"重算每个元素的桶位"改为**高低位链一次拆分**（新位置只有原址或原址 + oldCap 两种，按 `hash & oldCap` 一刀切）——细节深讲见 8.6。

**拉开差距的深水区**：为什么容量必须是 2 的幂？`(n-1) & hash` 等价于取模但一条指令，且扩容翻倍恰好只多出一位二进制参与判定，高低位拆分才成立——**2 的幂、位运算、高低位链是同一个设计的三个面**。

收尾：本题的完整版是 8.6，这里给的是骨架加一个"三个面"的设计观。

> 面试官追问点：两个 hashCode 相同的对象怎么共存？应答思路：哈希碰撞在桶内以链表（或树）排队，定位用 hash、认人用 equals；碰撞是常态，树化只是把极端碰撞的退化从 O(n) 兜到 O(log n)。

#### 为什么树化阈值是8？退化阈值却是6而不是8？

答：一句话定调，**8 来自泊松分布：负载因子 0.5 时桶内链长到 8 的概率约千万分之六，树化是给"几乎不该发生的事"兜底；退化取 6 留 2 的缓冲带，防止 7/8 交界处来回震荡**。

**树化为什么是 8**：理想 hash 下，每个桶的元素数近似二项分布，负载因子 0.75（树化分析按 0.5 算）时桶内出现 k 个元素的概率随 k 指数级衰减——链长 8 的概率约 0.00000006。**翻译成人话：正常情况你根本见不到 8 长的链**；一旦见到，说明 hash 质量出了问题（key 的 hashCode 写烂、hash 攻击、或极端容量下的碰撞聚集），这时候红黑树把退化的 O(n) 查找兜到 O(log n)。树化是保险丝，不是性能开关。

**退化为什么是 6 而不是 8**：树拆分/缩容时节点数 ≤6 就退化回链表。如果阈值也设 8：一个桶在 7、8 之间反复增删，就会**树化、退化、再树化、再退化**地振荡，每次结构转换都是不小的开销。6 和 8 之间留出 2 的缓冲带，进入树的世界后要连续丢 2 个才退场，稳定性有了。

**拉开差距的深水区**：树化的第二条件**数组 ≥64** 常被漏掉——数组太小时碰撞多的主因是容量不足而非 hash 差，此时优先扩容（翻倍能重新均摊元素），两条件是"先治本再治标"的排序；树节点 TreeNode 占用约是普通 Node 的两倍，**树是有内存税的兜底**，所以阈值设计处处体现"能不树化就不树化"。

收尾：8 和 6 一句话——8 说"这事不该发生，发生了我兜底"，6 说"进了保险丝的世界，别轻易出来"。

> 面试官追问点：如果 hashCode 全返回 1 会怎样？应答思路：所有元素挤进同一个桶，链表疯长后树化，HashMap 退化成"红黑树的链表"——查找 O(log n) 但每次插入带比较成本，整体比正常 HashMap 慢一个量级；这反证了树化救的是结构，救不了烂 hashCode。

#### ConcurrentHashMap在1.7和1.8分别怎么实现的？

1.7 分段锁与 1.8 CAS+synchronized 的演进、size() 统计、与 Hashtable 的区别。深度精讲见 8.7。

答：一句话定调，**1.7 是分段锁（Segment 继承 ReentrantLock，默认 16 段并发度写死），1.8 抛掉 Segment 改"CAS 建桶 + synchronized 锁桶头"，锁粒度从段降到桶，读全程无锁**。

**1.7 分段锁**：整个 Map 被切成 16 个 Segment，每个 Segment 是一把独立的 ReentrantLock 罩着一个小 HashMap——写操作只锁自己那一段，不同段天然并行。局限：并发度在构造时定死（16），运行时不可扩；两层寻址（先定位段再定位桶）。

**1.8 的组合拳**：桶为空用 CAS 直接放入；桶非空 synchronized 只锁**桶头节点**（锁粒度=单桶）；读路径只依赖 volatile（Node.val/next），无锁；扩容多线程可**协助搬运**（helpTransfer）。演进的本质：把 JVM 对 synchronized 的锁升级优化红利吃进来，换掉自己造的锁。

**为什么 key/value 都不允许 null**：并发下 get 返回 null 有二义性（不存在 or 值就是 null），单线程可以 containsKey 复查，**并发下"复查"不是原子操作**，两态无法区分，干脆禁止——Doug Lea 源码注释里的原话就是这个理由。

**与 Hashtable 的区别**：Hashtable 全表一把锁（连读都互斥）+ 方法级 synchronized + 继承老的 Dictionary 类，是"让整个表串行"的粗暴方案；CHM 是"读无锁、写锁桶"。

**拉开差距的深水区**：size() 是弱一致的——baseCount 加 CounterCell[] 分摊计数（LongAdder 思想），无锁累加所以并发写时可能偏小；深度版含 sizeCtl 状态机与协助扩容，见 8.7。

收尾：演进主线一句话——锁的粒度从"整张表"到"段"再到"一个桶"，外加"能不用锁就不用"。

> 面试官追问点：synchronized 锁桶头，那扩容时链表变了怎么办？应答思路：扩容线程搬运前也走锁与 CAS 协议，搬完的桶放 ForwardingNode 哨兵；写线程看到哨兵不是等待而是加入搬运（helpTransfer），这就是"扩容不阻塞写"的机关。

#### LinkedHashMap怎么实现LRU缓存？和HashMap区别？

答：一句话定调，**LinkedHashMap = HashMap 的散列结构 + 一条贯穿全部条目的双向链表，accessOrder 模式下每次访问把节点挪到链尾，"最久未用"永远趴在链头——继承它并重写 removeEldestEntry 就是 LRU**。

**和 HashMap 的区别**：HashMap 的桶数组只管散列查找，条目之间没有顺序概念（迭代序=槽位序）；LinkedHashMap 在 Node 上加了 before/after 两个指针，把所有条目串成一条双向链表。head/tail 两个入口，遍历走链不走桶。维护成本：每次 put 和 get 都要动链（摘下、接上），常数开销略高于 HashMap。

**两种序**：insertionOrder（默认，按插入顺序遍历）和 accessOrder（构造器第二参 true，**读也会改变顺序**——每次 get 把该节点摘下来接到链尾）。

**LRU 的实现三件套**：new LinkedHashMap<K,V>(16, 0.75f, true) 开 accessOrder；重写 removeEldestEntry(eldest)，返回 size() > capacity 时 true；put 超容量时框架自动驱逐链头（最久未访问）。**注意 get 也会触发结构变动**：普通 HashMap 迭代中 get 是安全的，LinkedHashMap 的 accessOrder 下 get 也算结构修改，遍历中 get 同样可能触发 fail-fast。

**拉开差距的深水区**：手写 LRU 是这题的进阶版——HashMap + 手维护双向链表：map 存 key→节点，链表维护时序，get/put 都是"散列定位 O(1) + 链表摘接 O(1)"；与 LinkedHashMap 版的差异是**手写版能驱逐时拿到被逐 key 做回写**（LinkedHashMap 驱逐时你拿不到旧值引用，需要重写 afterNodeRemoval 钩子）。LeetCode 146 的标准解法就是手写版。

收尾：LinkedHashMap 是"给散列表记时间轴"的设计，LRU 只是链表语义的一个副产品应用。

> 面试官追问点：LRU 手写版为什么必须双向链表？应答思路：驱逐和挪位都要"摘除任意节点"，单向链表摘除需要前驱，只能从头扫 O(n)；双向链表每个节点自带前驱指针，摘接 O(1)——链表方向的选择由操作复杂度反推。

#### TreeMap的底层是什么？什么时候该用它？

答：一句话定调，**TreeMap 底层是红黑树：增删查 O(log n)，天然按 key 有序；什么时候用——需要有序遍历、范围查询、最值/排名语义时，纯 KV 查找别用它（HashMap O(1) 不香吗）**。

**红黑树的核心性质**：二叉查找树 + 五条约束（节点红或黑、根黑、红节点的孩子必须黑、任一节点到叶的黑色数量相等、叶子是黑哨兵），合起来保证**最长路径不超过最短路径的两倍**——增删后的再平衡只需 O(1) 次旋转和变色。

**为什么选红黑树而不是 AVL**：AVL 是严格平衡（左右子树高度差 ≤1），查找更快一点点；但**插入删除的再平衡代价大**（AVL 删除最坏要回溯旋转 O(log n) 次，红黑树最多 2-3 次旋转）。TreeMap 是通用容器，增删查混合负载下"近似平衡 + 改起来便宜"胜过"完美平衡 + 改起来贵"——这是工程对理论的胜利。数据库索引、内核调度也大多选红黑树系，同理。

**三个独有操作**：firstKey/lastKey（最值）、headMap/tailMap/subMap（范围视图，注意视图与原表联动）、floorKey/ceilingKey（二分定位）——这些 HashMap 给不了。

**拉开差距的深水区**：排序依据两种——key 自身实现 Comparable，或构造时传 Comparator（**两者都存在时 Comparator 优先**）；Comparator 必须与 equals 语义一致，否则会破坏 SortedMap 的规范（equals 相等但比较不为 0 的对象会被当成不同 key 重复存入）；JDK 集合里红黑树的另一处高地是 HashMap 的桶（阈值 8 后），同一个数据结构服务两种场景。

收尾：一句话选型——要"序"用 TreeMap，要"快"用 HashMap，两个都要且量大，考虑跳表（ConcurrentSkipListMap，并发场景的有序 Map）。

> 面试官追问点：为什么并发有序场景用跳表不用红黑树？应答思路：红黑树再平衡要动多个节点，并发下锁不住一棵树只好全局锁；跳表的插入只牵扯前后指针的 CAS，天然按层局部化——ConcurrentSkipListMap 就是用"以空间换锁粒度"换来的并发有序。

# 3.并发编程

### 3.1 线程基础

#### 并发的三要素是什么？有哪些保证线程安全的方式？

答：一句话定调，**三要素是原子性、可见性、有序性，分别对应"操作被拆散、改了看不见、执行被重排"三种病，对症的药是锁（原子）、volatile（可见有序）、happens-before（全局秩序）**。

**逐个看病**：原子性——i++ 是读改写三步，两个线程交错就丢更新（1.1 越界题讲过环绕，这里是丢步）；可见性——每个线程有工作内存（可理解为 CPU 缓存的抽象），改了不刷回主内存、别人读的是旧值；有序性——编译器和 CPU 为优化会指令重排，单线程结果不变（as-if-serial），多线程交错时别线程可能看到"乱序世界"。

**保证线程安全的方式按重到轻**：synchronized/Lock（三性全保，互斥是终极答案）；volatile（保可见 + 有序，不保原子，适合一写多读）；原子类 CAS（保单变量的原子，无锁）；ThreadLocal（绕开共享，各玩各的）；不可变对象（final + 正确发布，没有共享可变状态就没有并发问题——最优雅的答案）。

**拉开差距的深水区**：三要素的病根都在**硬件**——CPU 缓存层级（L1/L2/L3）造成可见性，写合并缓冲和乱序执行造成有序性，这些是物理现实；JMM（Java 内存模型）是在硬件之上立的"合同"，用 happens-before 规则告诉你什么场景能读到什么（下一题展开）。

收尾：三要素答成"三种病"，方案答成"从锁到不可变的降维阶梯"，层次感就出来了。

> 面试官追问点：为什么不可变对象是线程安全的？应答思路：安全 = 共享 × 可变同时成立；不可变砍掉"可变"，final 字段的 JMM 语义（禁止构造器内重排序出构造，见 1.2 final 题）保证发布即可见，String 就是活例子。

#### 线程有哪六种状态？sleep和wait有什么区别？

答：一句话定调，**六态是 NEW/RUNNABLE/BLOCKED/WAITING/TIMED_WAITING/TERMINATED，sleep 和 wait 的本质区别是：sleep 是"不玩了歇会儿"（不放手锁），wait 是"等条件"（必须放手锁）**。

**六态走一遍**：new 出来是 NEW；start() 后进 RUNNABLE（Java 把就绪和运行合并，操作系统层的就绪/运行由调度器管）；抢 synchronized 失败是 BLOCKED（就差锁）；主动等待进 WAITING（wait/join/park 无参）；带超时的等待是 TIMED_WAITING（sleep(ms)/wait(ms)/parkNanos）；run 结束 TERMINATED。**Java 没有 Running 态**——线程是否正在 CPU 上由 OS 说了算，这是语言层和系统层的抽象分工。

**sleep vs wait 五连差**：①归属——Thread 的静态方法 vs Object 的实例方法；②锁——sleep 抱着锁睡，wait 必须在 synchronized 里调且**释放锁**；③唤醒——sleep 到点自醒，wait 要等 notify/notifyAll；④场景——sleep 是定时器，wait 是线程间协作（条件不满足就等）；⑤位置——sleep 哪都能调，wait 只能在持锁处（否则 IllegalMonitorStateException，见 1.1 Object 题）。

**拉开差距的深水区**：yield 是"提示调度器我愿让位"（仅是提示，可能被无视，且不释放锁）；join 的本质是**当前线程在目标线程对象上 wait**，所以 t.join() 会等 t 跑完（TERMINATED 后被唤醒）；interrupt 不打断"阻塞中的 sleep/wait"而是给它们发中断信号——sleep/wait 收到 InterruptedException 会**清除中断标记并抛异常**，吞掉异常不恢复标记是经典错误。

收尾：六态里最有信息量的是"RUNNABLE 不等于在跑"；sleep/wait 答出"歇会儿 vs 等条件"，区别自然就立住了。

> 面试官追问点：为什么 wait/notify 定义在 Object 而不是 Thread？应答思路：锁是对象级的（监视器挂在对象头），等的是"这个对象的条件"，唤醒的粒度也是对象——它们是锁模型的一部分，属于谁就定义在谁身上。

#### wait和notify是怎么实现线程间通信的？

答：一句话定调，**wait/notify 的本质是"锁 + 条件队列"：每个对象监视器自带一个等待集，wait 是把自己挂进去并放锁，notify 是从里面捞一个出来去抢锁——通信的载体不是方法，是对象自带的这个队列**。

**协作的完整回合**：消费者拿锁 → while(条件不满足) wait()（**放锁、挂起、进对象的等待集**）→ 生产者拿锁 → 改条件（放入数据）→ notify()（唤醒等待集里一个，**但被唤醒者要重新抢锁**，notify 自己不出锁，出锁在方法退出时）→ 消费者抢回锁 → while 复查条件成立 → 继续干。

**三个必讲的规矩**：①必须包在 synchronized(obj) 里（wait/notify 都要求持有 obj 的监视器）；②被唤醒后用 **while 而不是 if** 复查条件——虚假唤醒、被抢跑（notify 唤醒的是"能重新检查"不是"条件已成立"）；③notify 随机捞一个、notifyAll 全捞——**默认写 notifyAll**，notify 在多条件复用一个队列时可能捞错人（唤醒了等其它条件的）。

**经典场景：生产者-消费者**：wait 的条件是"队列空"（消费者等）/"队列满"（生产者等），两个条件共用一把锁，标准写法是 notifyAll 防止只唤醒同类。ArrayBlockingQueue 内部就是这个模型的工业版（两把 Condition 分开排队，精准唤醒）。

**拉开差距的深水区**：Object 的监视器只有**一个**等待集，多个条件挤一条队——这就是 Lock 的升级点：newCondition() 可以开**多条条件队列**（notEmpty/notFull 各挂各的），await/signal 唤醒零浪费。从"一锅捞"到"分桌叫号"，是 wait/notify 到 Condition 的演进主线。

收尾：wait/notify 通信 = 一把锁 + 挂在锁上的等待队列 + while 复查——三个词讲完机制，第四个词（Condition）讲出演进。

> 面试官追问点：notify 之后被唤醒的线程立刻运行吗？应答思路：不，notify 只把它从等待集挪到锁的入口队列（BLOCKED），要先等 notify 所在线程退出同步块放锁，再参与竞争；"唤醒≠持有"，中间还有一次抢锁。

#### 一个线程占多少内存？一个进程能开多少线程？

答：一句话定调，**线程默认约 1MB 栈内存（-Xss 可调），能开多少不是 Java 说了算，是物理内存除以栈大小、再撞上 OS 的 pid/线程数上限——所以"开几千个线程就崩"是内存算术，解药是线程池或虚拟线程**。

**一个线程占多少**：栈默认 1MB（64 位 HotSpot，-Xss1m），是**保留的地址空间**而非立即占满的物理内存；实际 RSS 随使用深度增长。线程少的内存如 8MB：1MB 栈 + 内核任务结构 + JVM 侧元数据。**1000 个线程 ≈ 1GB 保留栈**，这就是"线程很贵"的算术来源。

**一个进程能开多少**：三个约束取最小——①物理内存 / 栈大小；②OS 上限（Linux 线程数默认约 1 万级、ulimit 限制 pid；macOS 有 thread limit）；③JVM 参数（-XX:ThreadStackSize）。实测经验：普通 4~8GB 堆的服务，几千线程就该看到内存吃紧和调度开销了。

**线程异常怎么处理**：execute 提交的任务抛异常走线程的 UncaughtExceptionHandler，**Worker 线程死亡、线程池补新**；submit 包成 Future，异常被吞进 Future 里，不 get 永远不知道（见 8.4 深水区）。裸 new Thread 的异常会打印到 stderr 后线程无声死亡——关键业务必须 setUncaughtExceptionHandler。

**拉开差距的深水区**：为什么不能用"开更多线程"换并发？上下文切换一次约 1~10 微秒，几千线程的调度抖动会吃掉吞吐；**JDK21 虚拟线程**把栈放到堆上（按需增长、MB 级开销降到 KB 级），百万级并发成为可能——"线程贵"这个前提正在被改写。

收尾：能开多少是道除法题；答完补一句虚拟线程，把题答到时代前沿。

> 面试官追问点：虚拟线程为什么便宜？应答思路：栈在堆上按需伸缩，阻塞时挂起的不是内核线程而是调度器上的载体；内核线程数固定在 CPU 核级，百万虚拟线程分时复用它们，把"阻塞浪费"变成了"阻塞让位"。

### 3.2 锁与同步

#### Synchronized的底层怎么实现？锁升级过程说一下

JDK6 之后的锁优化与运用场景、JVM 层实现、锁升降级。深度精讲见 8.1。

答：一句话定调，**synchronized 靠对象头 Mark Word + monitorenter/monitorexit 字节码指令实现互斥，JDK6 后有"无锁 → 偏向 → 轻量级 → 重量级"的升级链：能不用系统锁就不用**。

**底层实现**：字节码层面是 monitorenter/monitorexit（代码块）或 ACC_SYNCHRONIZED 标志（方法）；JVM 层面，每个对象关联一个 ObjectMonitor（C++ 实现），锁竞争激烈时依赖操作系统的 mutex（互斥量）——**挂起/唤醒要陷入内核态，这就是"重量级"的来源**。

**锁升级链**：无锁（Mark Word 存 hashCode/分代年龄）→ 偏向锁（只有一个线程反复拿，Mark Word 记下线程 ID，**再进来只比一次 ID**，代价近零）→ 轻量级锁（第二个线程来了，偏向撤销，栈上建 Lock Record，Mark Word 指向它，**靠 CAS 自旋**）→ 重量级锁（自旋失败/竞争持续，膨胀成 ObjectMonitor，**未抢到的线程挂起阻塞**）。升级不可逆（不能降级回偏向），且竞争激烈时轻量级自旋反而烧 CPU，重量级的挂起才是止损。

**拉开差距的深水区**：JDK15 起偏向锁被废弃默认关闭——维护成本高（撤销要 safepoint）、现代并发场景"永远单线程重入"的假设不再成立，**轻量级 CAS 直接起步**；锁升级的本质是"赌竞争烈度"：赌只有自己用（偏向）、赌竞争轻微（自旋）、赌不过认输（挂起）。

收尾：答完升级链补一句"JDK15 已默认关偏向锁"，直接把八股答成版本前沿。完整源码级见 8.1。

> 面试官追问点：为什么自旋优于阻塞？应答思路：挂起要两次内核态切换（约微秒级）加线程栈换出；锁若几条指令后就释放，自旋空转几纳秒反而赚——**赌持锁时间短**；赌输的代价是白烧 CPU，所以自旋有次数上限。

#### AQS的原理是什么？和synchronized比怎么样？

AQS 原理及与 synchronized 的对比。深度精讲见 8.2。

答：一句话定调，**AQS = 一个 volatile int state + 一条 CLH 变体的 FIFO 等待队列，全部并发原语（锁/信号量/闭锁）都是"怎么解读 state"的插件——它是造锁的框架，不是锁**。

**两个核心组件**：state（volatile int，语义由子类定义——ReentrantLock 里是重入次数、Semaphore 里是许可数、CountDownLatch 里是计数）；双向队列（抢不到的线程封装成 Node 挂队尾，用 **LockSupport.park 挂起**，head 唤醒后继用 unpark）。模板方法模式：acquire/release 的骨架写死（入队、挂起、重试），tryAcquire/tryRelease 留给子类——**JUC 的半壁锁体系都是它五六十行骨架的插件**。

**和 synchronized 比怎么样**：synchronized 是 JVM 内置锁——语言级语法、自动释放、JDK6 后性能已不差；AQS 系是 API 层锁——**可中断、可超时、可公平、可多条件**（newCondition 开多条等待队列），代价是要手动 lock/unlock（finally 里放）。选型：简单互斥用 synchronized（无脑正确），需要任何高级特性（tryLock 超时、公平、条件分流）才上 AQS 系。

**拉开差距的深水区**：AQS 的 park 线程不是 synchronized 那样挂在 ObjectMonitor 上，而是 LockSupport 直接操作——**可以指定唤醒某个线程**（unpark(thread) 先行发放许可），这是"队列式调度"精确性的地基；CLH 队列在自旋锁原版里节点各自自旋，AQS 改成 head 唤醒后继，挂起为主的玩法。

收尾：synchronized 是"一把锁"，AQS 是"锁的流水线"——把 JUC 的锁理解成同一个骨架的不同插件，并发容器瞬间少了一半知识点。完整深讲见 8.2。

> 面试官追问点：公平锁在 AQS 里怎么体现？应答思路：hasQueuedPredecessors——tryAcquire 前先查队列有没有排在前面的线程，有就不抢（乖乖去队尾）；非公平版上来先 CAS 抢一次，抢到就是插队——吞吐高的原因。

#### synchronized和ReentrantLock有什么区别？

答：一句话定调，**synchronized 是 JVM 原生锁（自动释放、单条件队列），ReentrantLock 是 AQS 实现的 API 锁（可中断、可超时、可公平、多条件）——功能全面胜出，代价是把"不会忘"变成了"必须记得 unlock"**。

**五个维度的对比**：①实现层——JVM 内置（monitorenter 指令、对象头 Mark Word）vs JUC 的 AQS（state + 队列）；②释放——异常/退出自动释放 vs **必须 finally 手动 unlock**（忘了就是死锁，一致性检查器查不出）；③功能——synchronized 只有非公平、单等待队列（Object 监视器）vs ReentrantLock 可选公平（构造参数）、可中断（lockInterruptibly）、可超时（tryLock(timeout)）、**多 Condition**（一个锁挂多条条件队列，精准唤醒）；④性能——JDK6 锁升级后常规场景已无显著差距，别再用"性能"当选型理由；⑤用法——关键字加在代码上 vs 对象调方法。

**可重入原理**：两者都重入——synchronized 靠 Mark Word/monitor 记持有线程加计数；ReentrantLock 的 AQS state 加 1 减 1，**当前线程再 lock 就是 +1，unlock 减到 0 才真放锁**。可重入防止"自己锁自己"的死锁（同一线程嵌套同步块）。

**Condition vs wait/notify**：await/signal 必须 lock.lock() 之后调（对应 wait/notify 的持锁要求）；差别在**条件队列的数量**——Object 监视器只有一条全挤着，Condition 可以 notEmpty/notFull 分桌，signal 唤醒的必是等这个条件的，**notifyAll 的"全场喊话"退化成"按桌叫号"**（3.1 第 3 题的深水区在这里闭环）。

**拉开差距的深水区**：tryLock 的实战价值——死锁预防：两个锁的获取改成 tryLock + 失败回滚已持有的，**死锁的"请求与保持"条件被打破**（循环等待成不了环）。

收尾：默认 synchronized，要"可中断/超时/公平/多条件"四件套里的任何一件，换 ReentrantLock。

> 面试官追问点：公平锁一定更好吗？应答思路：公平防饥饿但吞吐低（上下文切换多、队列纪律开销）；非公平的插队让"刚释放的锁被 CPU 上热的线程立刻接手"，缓存友好——高吞吐系统默认非公平是有意的取舍。

#### volatile的两个作用是什么？和CPU缓存什么关系？

两个重要作用与锁的对比、CPU 缓存一致性、指令重排类型。深度精讲见 8.3。

答：一句话定调，**volatile 两个作用：可见性（写立即刷主存、读走主存最新值）和有序性（禁止指令重排），唯独不保证原子性——它是"一写多读"场景的轻量同步，不是锁的替身**。

**可见性机制**：写 volatile 变量，JMM 要求对工作内存的失效处理——硬件层落地为**缓存锁/总线信号**：x86 上写 volatile 生成 lock 前缀指令，触发缓存行回写主存，并通过 **MESI 缓存一致性协议**让其它核的对应缓存行失效（Invalid），别的核再读必须重新拉主存。"改了看得见"就是这条硬件链路。

**有序性机制**：内存屏障——volatile 写前插 StoreStore、写后 StoreLoad；读前后 LoadLoad/LoadStore，**编译器和 CPU 都不许跨屏障重排**。最经典的应用是 DCL 单例：`new` 实际是分配 → 初始化 → 赋值三步，可能重排成"先赋值后初始化"，另一线程拿到半初始化对象；volatile 的屏障堵住这条缝（字节码级拆解见 8.3）。

**为什么不保原子**：i++ 是读改写三步，volatile 只保证每步读的是新值，**三个线程同时读同一个值各自加一再写回**，丢两次更新——原子性要靠 AtomicInteger（CAS）或锁。

**拉开差距的深水区**：MESI 已经保证了缓存一致性，volatile 还防的是**重排和写合并**（store buffer 的存在让"缓存一致"延迟可见），以及 JMM 层面对编译器重排的约束——**volatie 防的三个坏蛋：编译器、CPU 重排、写合并缓冲**。

收尾：一句话总结——volatile 是"状态标志位和 DCL 的标配"，复合操作场景让位给 CAS 和锁。

> 面试官追问点：volatile 数组能保证元素可见吗？应答思路：只保证引用本身的可见性，arr[i]=x 对其它线程不立即可见；要元素级就得每次写复制新数组（COW 思路）或用 Atomic 系列的数组类（AtomicIntegerArray 用Unsafe 的 volatile 语义逐元素访问）。

#### JMM是什么？happens-before的八大规则说一下

答：一句话定调，**JMM 是主内存与工作内存的抽象合同：所有共享变量在主内存，线程先拷到工作内存再操作；happens-before 是合同里的推演规则——它不禁止重排，只承诺"重排后你看不出差别"**。

**主/工作内存**：工作内存是对寄存器、CPU 缓存、写缓冲的抽象，不对应具体硬件。线程对变量的所有操作都在工作内存做，刷回主内存的时机不确定——**可见性问题的来源就是这个"不确定"**。三性的保证分工：原子性靠锁/CAS（long/double 普通读写甚至可拆两次 32 位，见 8.3 深水区），可见性靠 volatile/锁（解锁前写必对后拿锁者可见），有序性靠 volatile/锁/happens-before。

**happens-before 八大规则**：①程序顺序规则——单线程内按代码顺序（语义上）前面的操作 hb 后面的；②监视器锁规则——解锁 hb 后续加锁；③volatile 规则——volatile 写 hb 后续的读；④线程 start 规则——start() 前的操作 hb 新线程内的一切；⑤线程 join 规则——线程内的操作 hb join() 之后的代码；⑥线程中断规则——interrupt 调用 hb 被中断线程检测到中断；⑦对象终结规则——构造器结束 hb finalize 开始；⑧传递性——A hb B、B hb C，则 A hb C。

**关键理解**：hb 不是"时间上先发生"，是"结果可见性上的承诺"——**A hb B 意味着 A 的结果对 B 可见**。它是推演工具：拿几条规则一连，就能证明某段并发代码"不需要额外同步也安全"（无锁发布的合法性证明全靠它）。

**拉开差距的深水区**：JMM 允许重排但保持 as-if-serial（单线程不可感知）+ 用 hb 给多线程立"可见性的最小承诺"——**这是"性能与正确性的谈判"**：不承诺顺序（留给优化空间），只承诺可见序（保证可推理）。

收尾：JMM 答抽象（主/工作内存），hb 答性质（可见性承诺不是时序），最后补一句"它是无锁代码的合法性证明工具"。

> 面试官追问点：i++ 在单线程规则下 hb 自己，为什么多线程不安全？应答思路：hb 只在"存在同步边"的线程间传递；两个无同步的线程之间没有 hb 边，互相可以看不见对方的写——hb 的保护范围止步于同步动作的连线。

#### 死锁的四个必要条件？怎么排查和怎么解决？

四个必要条件与预防、死锁演示、thread dump 分析、活锁。深度精讲见 8.15。

答：一句话定调，**死锁四条件：互斥、请求与保持、不可剥夺、循环等待——前三个是锁的天然属性改不动，工程上主攻第四条：统一加锁顺序；排查靠 jstack 一眼定罪**。

**四条件**：互斥（资源一次一人用）；请求与保持（拿着 A 又去要 B，不放 A）；不可剥夺（别人不能抢走你手里的锁）；循环等待（A 等 B、B 等 A 成环）。**四者缺一不死锁**：因为互斥/不可剥夺是锁的本性，预防手段全打在另外两条上。

**怎么解决**：①统一加锁顺序——所有线程都按同一顺序拿锁（如按账户 ID 排序），**循环等待成不了环**，根治派；②tryLock 超时——拿不到就放掉已有的重来（ReentrantLock.tryLock），**请求与保持被打破**，止损派；③一次性申请全部资源；④缩小锁粒度、减少嵌套（最好的锁是不用锁）。

**怎么排查**：`jstack <pid>` 一把梭——输出里找 "Found one Java-level deadlock"，**JVM 自带死锁检测，直接打印持锁环**（t1 holds 0x000...1 waiting 0x000...2, t2 反之）；没有死锁标记时手动看 "waiting to lock <0x...>" 的交叉引用。可视化工具（jconsole、Arthas 的 thread -b）同源。

**手写演示**：两个线程、两把锁，t1 lock(A)→sleep→lock(B)，t2 lock(B)→sleep→lock(A)，sleep 保证两个线程都先拿到第一把——稳定复现。

**拉开差距的深水区**：活锁——线程没阻塞但一直空转（互相谦让/重试风暴），状态在变、活干不成；死锁是**卡死不动**，活锁是**忙而不前**，解药是引入随机退避让谦让错开。

收尾：预防答"统一顺序"，排查答"jstack 自带检测"，区分答"动不了 vs 空转"——三句话就是满分结构。深讲见 8.15。

> 面试官追问点：数据库死锁和 Java 死锁有什么不同？应答思路：数据库有死锁检测器（InnoDB 等待图 + 超时），发现环后主动回滚代价小的事务，"不可剥夺"被数据库亲手打破——Java 没有这层仲裁，只能靠开发者自律。

#### 公平锁、乐观锁、读写锁这些概念分别是什么？

答：一句话定调，**这三对概念是三根不同的轴：公平性（排队还是插队）、心态（先锁后动还是动了再说）、读写性（读要不要互斥）——不要混着背，按轴回答**。

**公平锁 vs 非公平锁**（排队轴）：公平——抢锁前先看队列有没有前驱，有就乖乖去队尾（AQS 的 hasQueuedPredecessors），防饥饿但吞吐低；非公平——上来先 CAS 抢一把（插队），抢不到再排队，**吞吐高是因为"刚释放的锁被手上正热的线程接走"**（缓存友好、少切换）。synchronized 只有非公平，ReentrantLock 可选。

**乐观锁 vs 悲观锁**（心态轴）：悲观——假设冲突常发生，先加锁再操作（synchronized/ReentrantLock/数据库行锁），**读也挡人，适合写多**；乐观——假设冲突少，不加锁直接干，提交时 CAS/版本号验证，**失败重试**（AtomicInteger、MVCC），读多写少时吞吐碾压。注意乐观锁的"锁"是算法不是锁对象——它根本没锁。

**读写锁 vs 互斥锁**（读写轴）：ReentrantReadWriteLock——读读共享、读写/写写互斥，**读多写少（配置表、缓存元数据）时读并发度拉满**；写锁可降级为读锁（持写锁再拿读锁再放写锁），**读锁不能升级写锁**（两个读锁同时想升级=死锁经典）。JDK8 的 StampedLock 再进一步：**乐观读**——读时不加锁，读完用版本号校验没被写就认，读路径零开销。

**拉开差距的深水区**：三根轴的交叉应用——CHM 是"悲观写（synchronized 桶）+ 无锁读（volatile）"的自定义读写方案；MVCC 是数据库的乐观读（快照版本）；选型公式：**写多悲观、读多乐观（或读写锁）、热点写考虑 LongAdder 的分段**。

收尾：三对概念各答一句"轴心"，再给一个交叉案例（CHM/MVCC），就从背名词升级到懂分类。

> 面试官追问点：StampedLock 为什么不支持重入？应答思路：它为了极致读性能放弃了 AQS 的 state 复用设计（读写状态打包在版本号戳里），重入计数无处安放——**它是特定场景的性能特化，不是 ReentrantReadWriteLock 的升级替代**。

#### 三个线程怎么顺序执行？每秒限10个并发怎么做？

答：一句话定调，**顺序执行三件套 join/CountDownLatch/单线程池，限并发一件事 Semaphore——前者是"等完成"的艺术，后者是"发许可"的艺术**。

**三个线程顺序执行（T1→T2→T3）**：①join 版——t1.start; t1.join()（当前线程等 t1 结束）再启 t2，**join 的本质是在目标线程对象上 wait**（3.1 第 2 题）；②CountDownLatch 版——每个线程开头 await 自己的 latch，前一个跑完 countDown 下一个的 latch；③单线程池版——Executors.newSingleThreadExecutor().submit(t1/t2/t3)，**队列天然保序，还免费拿到结果管理**，工程首选。

**每秒限 10 个并发**：Semaphore(10)——调用前 acquire()（拿许可，拿不到阻塞）、finally 里 release()，**同一时刻至多 10 个在跑**；如果要"每秒最多 10 个请求"（速率而非并发），上 Guava RateLimiter（令牌桶，limiter.acquire() 按速率发牌）或滑动窗口计数。区分两个词：并发上限用 Semaphore，速率上限用令牌桶/滑动窗口。

**volatile int 的 i++ 线程安全吗**：不安全——volatile 保可见有序不保原子（3.2 第 4 题），i++ 三步交错照样丢更新。

**不用锁怎么保自增**：AtomicInteger.incrementAndGet()——**CAS 循环：读旧值 → 算新值 → compareAndSet(旧，新)，失败说明有人先改了，重读重试**（无锁但不是无等待）；高热点写用 LongAdder（分段累加，读时求和，把单点 CAS 争用摊开，见 8.11）。

**拉开差距的深水区**：CountDownLatch 和 CyclicBarrier 的选择——latch 是**一次性倒计数**（等一簇任务完成，countDown 不阻塞），barrier 是**可复用的回合制**（人齐了一起放行，await 会阻塞）；"等所有人到齐再开会"用 barrier，"等所有分片干完再汇总"用 latch。

收尾：这题是工具箱抽查——join/latch/池保序， semaphore 限流，CAS 保原子，每个都一句原理收口。

> 面试官追问点：Semaphore 的许可释放两次会怎样？应答思路：release 不校验持有者，多余 release 会让许可数超过初始值（资源凭空变多）——**acquire/release 必须严格配对在 finally 里**，这也是"许可不是锁"的语义提醒。

### 3.3 并发工具

#### CAS的原理是什么？ABA问题怎么解决？

CAS 原理与 ABA 及解决方案、LongAdder 对比。深度精讲见 8.11。

答：一句话定调，**CAS 是"读取旧值 → 计算新值 → 提交时验证旧值没被改过"的无锁原子操作，硬件层一条 cmpxchg 指令；ABA 是"值从 A 改到 B 又改回 A"，验证通过但世界已经变了——解药是给值配版本号**。

**原理**：CompareAndSwap（比较并交换），Unsafe.compareAndSwapInt 底层是 x86 的 lock cmpxchg 指令（总线锁/缓存锁保证原子）。AtomicInteger.incrementAndGet 的实现：死循环里读当前值 → value+1 → CAS(value, 旧值, 新值)，**失败说明有人先改了，重读重试**——无锁但不是无等待（自旋消耗 CPU）。

**ABA 问题**：线程 1 读到 A，被挂起；期间线程 2 把 A 改成 B 又改回 A；线程 1 恢复后 CAS 发现"还是 A"，成功提交——**值相等 ≠ 没被动过**。数值累加场景无害，但链表/栈这类结构里会出人命：把节点 A 弹出又压回了一个"值相同"的新 A，指针全乱。

**解药**：版本号——JDK 提供 **AtomicStampedReference**（引用 + int 戳，CAS 要同时比对值和版本，版本只增不改回去）；不关心中间过程只关心"是否被改过"用 AtomicMarkableReference（boolean 标记）。数据库乐观锁的 version 字段是同一个思想的 SQL 版。

**拉开差距的深水区**：高并发下 CAS 的自旋风暴——大量线程同时改一个变量，几乎全失败重试，吞吐塌方；**LongAdder 的解法是分段**：一个 base 加 Cell[] 数组分摊累加，读时求和——热点拆成多个冷点，代价是读不再是精确值（弱一致快照，8.11 深讲）。

收尾：CAS 答硬件指令 + 自旋重试，ABA 答版本号，热区答 LongAdder 分段——三段连击。

> 面试官追问点：CAS 和 volatile 的关系？应答思路：AtomicInteger 的 value 本身就是 volatile 的——CAS 的"读"要读到最新值才有意义，可见性是原子性的前置；volatile 保读的可见，CAS 保改的原子，两者是搭档不是竞品。

#### ThreadLocal为什么会内存泄漏？怎么正确避免？

ThreadLocalMap 结构与弱引用设计。深度精讲见 8.8。

答：一句话定调，**泄漏的根因是"key 被回收了 value 还活着"：key 是弱引用会被 GC 拿走，value 是强引用被线程的 ThreadLocalMap 拖着——线程不死，value 不灭；避免的唯一正解是用完 remove**。

**结构**：每个 Thread 内部有一个 threadLocals 字段指向 ThreadLocalMap（**Map 挂在线程身上，不是 ThreadLocal 身上——方向反转**）；Entry 的 key 是 ThreadLocal 的**弱引用**，value 是强引用。

**泄漏的推导链**：外部不再引用某个 ThreadLocal → 它作为弱引用 key 被 GC 回收 → Entry 变成 (null → value) 的" stale 条目" → **线程还活着（线程池核心线程常年不死）→ value 被这条链拖着无法回收**。弱引用不是泄漏的原因，是**减轻泄漏的设计**（没有它，ThreadLocal 本体也回收不掉）；真正的凶手是"value 强引用 + 线程长寿"。

**怎么正确避免**：try-finally 里 remove()（清理当前线程的整个 Entry，同时顺手触发探测式清理）；线程池场景这是铁律——**线程复用，上一任任务的 value 会留给下一任**（串数据事故的来源）。set/get 时也会启发式清理碰到过的 stale 条目，但那是顺路，不能依赖。

**拉开差距的深水区**：为什么 key 设计成弱引用而不是强引用？假设 key 是强引用：外部不再用的 ThreadLocal 被 Map 的 key 拖着，**连本体都回收不了**——弱引用至少把"锁孔"拿走，让清理机制能识别出 stale 条目；这是"两害相权取其轻"的设计决策（8.8 深讲）。

收尾：泄漏答"方向反转 + 弱 key 强 value + 线程长寿"三点连线，避免答一个词：remove。

> 面试官追问点：ThreadLocal 用在哪些场景？应答思路： SimpleDateFormat 的线程封闭（每次 new 太贵、共享又不安全）、链路追踪 traceId 透传（拦截器 set，日志框架 get）、数据库连接的会话绑定——共性是"同一份数据，每个线程各要一份"。

#### 线程池的核心参数怎么设？execute和submit区别？

核心参数、execute/submit 差异。深度精讲见 8.4。

答：一句话定调，**七个参数里真正的灵魂三角是 core/max/queue——它决定线程池在"吞吐"和"资源"之间站哪边；参数公式只是起点，压测才是终点**。

**七参数速览**：corePoolSize（常驻线程数）、maximumPoolSize（上限）、keepAliveTime + unit（非核心空闲回收时间）、workQueue（任务缓冲，阻塞队列）、threadFactory（命名——**不命名的线程池排查时是灾难**）、handler（拒绝策略：Abort 抛异常 / CallerRuns 提交者自己跑 / Discard 丢弃 / DiscardOldest 丢最老）。

**execute 的三步分支**（顺序答反必扣分）：线程数 < core 直接起新线程**不排队**；core 满了进队列；队列满了起非核心直到 max，再满走拒绝策略。**核心未满时任务是插队执行的**——这一条最多人答错。

**execute vs submit**：execute 收 Runnable、无返回、异常直接打给 UncaughtExceptionHandler 且 **Worker 死亡重建**；submit 收 Runnable/Callable、返回 Future、**异常被捕获存进 Future，线程不死，不 get 就永远不知道出错**——生产事故高发区。关键任务要么 submit 后必 get，要么换 CompletableFuture（exceptionally 补救）。

**参数怎么设**：CPU 密集 N+1（多一个防缺页停顿浪费核），IO 密集 2N 或 N×(1+等待时间/计算时间)。**但面试的正确姿态是补一句**：公式是起点，实际要看压测下的队列深度、线程上下文切换次数、下游承载；**阿里规约禁用 Executors 快捷方法**（无界队列 OOM / 无限线程），手动 new，每个参数自己负责。

收尾：灵魂三角 + 三步分支 + "压测才是终点"，这三个词答完本题已经合格；ctl 位设计、Worker 不可重入锁见 8.4 深讲。

> 面试官追问点：核心线程能被回收吗？应答思路：allowCoreThreadTimeOut(true) 可以让核心线程也超时回收——默认核心线程常驻的真相是阻塞在队列 take 上不消耗 CPU（不是空转），把它关掉是拿稳定性换资源。

#### CompletableFuture怎么编排多个异步任务？

答：一句话定调，**CompletableFuture 解决 Future 的两大残废（get 只能阻塞干等、不能链式组合），核心是"回调注册 + 异常传播"的编排模型，本质是把异步流程写成声明式的流水线**。

**Future 的局限**：get() 阻塞等结果、isDone 轮询低效、**多个 Future 之间没有组合原语**（"A 完成后再跑 B"要自己写等待逻辑）——CompletableFuture 用回调把这层全包了。

**编排三件套**：thenApply（同步转换：上一步结果 → map 成新值）、thenCompose（异步串联：上一步结果 → 返回另一个 CF，**拍扁嵌套**，flatMap 的语义）、thenCombine（两路合并）。聚合两条路：allOf（等全部完成，再 join 收结果——并行调 N 个下游再汇总）、anyOf（任一完成）。每个 API 都有 Async 后缀变体：不带 Async 在**完成线程**继续跑，带 Async 丢给 ForkJoinPool 或指定线程池——**不给线程池就默认 commonPool，IO 任务会污染全局池**。

**异常处理**：CF 的异常沿流水线传播到终点——exceptionally（兜底返回默认值）、handle（正常异常都过一遍）、whenComplete（只旁观不改值）。**不处理异常的 CF 会静默吞掉它**，比 Future.get 上的异常更隐蔽。

**实战范式**：supplyAsync(查用户, pool).thenCompose(u -> supplyAsync(查订单, pool)).thenCombine(查积分, 合并).exceptionally(降级)——**串联用 compose、并行用 allOf、兜底用 exceptionally、线程池显式传**。

**拉开差距的深水区**：thenApply 挂在前一个 CF 上时若前一步已完成，回调直接在**注册线程**同步执行——你以为的异步可能一步都没离开当前线程，**全链路 Async + 自定义池才能保证不占用调用方**；超时控制 orTimeout/completeOnTimeout（JDK9）是易被漏的工程化能力。

收尾：这题的答题公式——先数落 Future 的两条罪，再按"串联/并行/兜底/线程池"四件套讲编排，最后补一句 commonPool 污染，工程味就全了。

> 面试官追问点：为什么thenCompose和thenApply要分成两个？应答思路：map 的返回值会自动包一层 Optional 再包一层就变嵌套；thenApply 返回值会被再包成 CF，返回 CF 的函数用 thenApply 会得到 CF<CF<T>>——thenCompose 就是 flatMap，专治函数本身返回异步结果的场景。

# 4.JVM与内存

#### JVM运行时数据区有哪几块？各自存什么？

答：一句话定调，**五块区域按"线程私有 vs 共享"分两堆：线程私有的程序计数器/虚拟机栈/本地方法栈，共享的堆/方法区（元空间）——"哪些随线程生灭、哪些要 GC"是分堆的意义**。

**线程私有三件**：程序计数器（当前线程执行的字节码行号，**唯一不会 OOM 的区域**， native 方法执行时值为 undefined）；虚拟机栈（每个方法调用压一个**栈帧**：局部变量表 + 操作数栈 + 动态链接 + 返回地址，栈深度超限抛 StackOverflowError，扩容失败抛 OOM）；本地方法栈（给 native 方法用，HotSpot 里和虚拟机栈合一）。

**共享两件**：堆（对象实例和数组的家，GC 的主战场，内部按分代组织——新生代 Eden+两 Survivor、老年代）；方法区（类信息、常量、静态变量——**JDK8 起由永久代改为元空间**，从 JVM 内存搬到本地内存 native memory，字符串常量池早在 JDK7 就挪进了堆）。

**为什么要用元空间替代永久代**：永久代有 -XX:MaxPermSize 上限，动态生成类（CGLIB、JSP、脚本引擎）容易 PermGen OOM；元空间使用本地内存，默认只受物理内存约束（-XX:MaxMetaspaceSize 兜底），且**字符串常量池放堆里可以被正常 GC**，Intern 泛滥不再堆积永久代。

**拉开差距的深水区**：运行时数据区是规范，各 JVM 自由发挥——HotSpot 的栈和本地方法栈合一、字符串常量池的位置变迁都是实现细节；**直接内存（DirectByteBuffer）不在五块里**，属于 native 内存，靠虚引用 + 引用队列清理（下文引用题闭环）。

收尾：答题按"私有/共享"分堆，每块带一个"存什么 + 什么错"，最后补一句 JDK8 元空间之变，就是理解而非背诵。

> 面试官追问点：一个栈帧里局部变量表的 slot �么分？应答思路：以 32 位 slot 为单位（long/double 占两个），实例方法的 slot 0 恒为 this；局部变量有 slot 复用优化（作用域结束后 slot 被后续变量顶用）——这影响 GC 根扫描时变量是否算可达，是"栈上变量影响对象存活"的冷知识。

#### 对象的创建过程说一下？怎么判断对象该回收？

对象内存布局、访问方式、判死。深度精讲见 8.10。

答：一句话定调，**对象创建五步"检查加载 → 分配 → 零值 → 设头 → 初始化"，回收判定主流是可达性分析——从 GC Roots 出发摸不到的就是垃圾**。

**创建五步**：①常量池定位类，没加载先触发加载（触发静态块的时机链见 1.2 静态题）；②分配内存——**指针碰撞**（内存规整，Serial/ParNew 这类带压缩的收集器）或**空闲列表**（内存零散，CMS 这类标记清除的）；并发安全靠 CAS 或 TLAB（线程私有分配缓冲，先在自己的 TLAB 里分，分完再申请新 TLAB——**绝大多数对象在 TLAB 里无锁分配**）；③内存清零（默认值保证字段不初始化也能用）；④设置对象头（类型指针、hash、GC 分代年龄）；⑤执行构造器 <init>（真正的赋值）。

**怎么访问对象**：句柄（引用 → 句柄池 → 对象本体和类型，**GC 移动对象只改句柄**）vs 直接指针（引用直接指对象，**少一次寻址，HotSpot 的选择**，移动对象要改所有引用，靠 safepoint 配合）。

**判断死亡——可达性分析**：从 GC Roots（栈帧局部变量、静态变量、JNI 引用、活跃线程等）向下搜索引用链，**摸不到的对象不可达 → 可回收**。真正的死亡要过两审：第一次标记后看是否要执行 finalize（对象可自救一次，已废弃，见 1.1 Object 题），无人救才真死。**引用计数为什么被弃用**：循环引用 A↔B 无外部引用却计数不为零——JVM 主流全部放弃它。

**拉开差距的深水区**：TLAB + 指针碰撞让分配快到"十条指令"量级，加上 JIT 逃逸分析（不逃逸的对象标量替换直接拆在栈上，连堆都不进）——**"Java 对象分配很贵"是个过时结论**，深讲见 8.10。

收尾：创建答五步加 TLAB，回收答 Roots 可达性加"两审"，这一题就从名词解释升维成分配与回收的工程观。

> 面试官追问点：什么对象直接进老年代？应答思路：三个入口——大对象（超过 Region/Eden 一半）、熬过 15 岁、**动态年龄判断**（Survivor 同龄对象总和过半，该岁起直接晋升），第三条最少人知道（8.5 追问同款）。

#### 怎么判断对象可以回收？有哪些GC算法？

答：一句话定调，**判定靠可达性分析（摸不到即死），算法只有三板斧——标记清除、标记复制、标记整理，所有回收器都是三板斧在分代结构上的组合变奏**。

**判定**：上一题已展开（GC Roots 可达性 + 两审制），核心一句：**从根出发摸得到的活，摸不到的才能死**。

**三算法**：标记清除（标出垃圾再逐个回收——**简单但碎片**，碎片到大对象放不下会提前 Full GC）；标记复制（活对象搬到新空间，旧空间整块清掉——**无碎片但浪费空间**，存活率低时划算）；标记整理（活对象往一头压实——**无碎片但搬活对象贵**，存活率高时划算）。

**分代假说选算法**：弱分代（朝生夕死）+ 强分代（熬得越久活得越久）→ **新生代用复制**（Eden:S0:S1=8:1:1，存活少，只浪费 10% 的 Survivor 空间）、**老年代用清除或整理**（存活多，复制不划算）。

**GC 链路的完整描述**： Minor GC（新生代，频繁而快）→ 熬过 15 次晋升老年代 → 老年代满或元空间不足 / 大对象担保失败 → Full GC（整堆加方法区，慢而伤）。**触发链里最值得讲的是"空间分配担保"**：Minor GC 前老年代要能装下新生代所有对象（最坏假设），装不下先触发一次 Full GC 腾地方——担保失败连环 GC 的来源。

**拉开差距的深水区**：并发标记的三色漏标问题——黑（标完）插新引用指向白、灰删了到白的旧引用，两者同时发生白对象被漏标存活成"浮动垃圾"的反面（被误回收才致命）；CMS 用增量更新、G1 用 SATB 破坏条件（8.5 深讲）——**把"算法"答到"并发标记的正确性"层，就是深水区门票**。

收尾：算法答三板斧 + "分代配算法"的逻辑，再把话头递给三色标记，为 CMS/G1 那题埋好桥。

> 面试官追问点：为什么 Survivor 是两块不是一块？应答思路：一块的话复制没有目的地；两块轮换让"来回复制"成立，每次 Minor 只用 Eden+一块 Survivor 共 90% 空间，另一块做下次的目的地——空间换无碎片的循环。

#### CMS和G1有什么区别？G1的Region设计说一下

分代结构、触发条件、Region 设计。深度精讲见 8.5。

答：一句话定调，**CMS 和 G1 的主线之争是"停顿的粒度"：CMS 把并发做到老年代回收但败给碎片，G1 用 Region 化的堆 + 停顿预测模型把停顿从全堆粒度降到 Region 粒度**。

**分代与触发**：新生代 Minor GC（Eden 满触发，快）、老年代 Full GC（空间不足/担保失败/元空间满，慢）。CMS 是老年代并发回收器，G1 整堆回收器（两者都是，各管各的分代）。

**CMS 的三宗罪**（G1 的出场铺垫）：浮动垃圾（标记后新产生的本轮收不了）；并发失败退化 Serial Old（预留不够变单线程全停）；**标记清除碎片**（碎到放不下大对象提前 Full GC）——三宗罪全是"并发与碎片"的代价。

**G1 的 Region 设计**：堆切成 1~32MB 等大 Region，**分代从物理变逻辑**（Eden/Survivor/Old 是动态标签不是连续区域）；每个 Region 记录回收价值（能腾多少 / 花多久），`-XX:MaxGCPauseMillis`（默认 200ms）是软目标，**每次挑性价比最高的一组 Region 组成回收集——Garbage First 名字的由来**；跨 Region 引用靠 RSet 记忆集 + 卡表写屏障维护；老年代占用过 IHOP（默认 45%）触发并发标记，之后 Mixed GC（年轻代全收 + 老年代挑高价值收）。

**拉开差距的深水区**：并发标记的漏标防线——CMS 用增量更新（记录黑→白的新引用重扫），G1 用 SATB（删除时快照旧值，按初始快照标，代价是本轮浮动垃圾）——**两种写屏障的取舍**是这题的最深一层（8.5 有完整推演）；ZGC 一句话带过：着色指针 + 读屏障，**并发整理**亚毫秒停顿，支持 TB 级堆。

收尾：答出"粒度"主线（老年代 → Region）、CMS 三宗罪、Garbage First 的名字由来，再把 SATB 一句点破，这题的含金量就到了源码层。

> 面试官追问点：G1 的 RSet 为什么占那么多内存？应答思路：每个 Region 记"谁引用我"，堆大跨引用多时 RSet 可占 1%~20%——空间换时间（扫描不用全堆）；Refinement 线程异步消化卡表脏卡，把写屏障的运行时代价摊薄。

#### 类加载的过程有哪几步？初始化顺序是什么？

类加载触发时机、初始化顺序。深度精讲见 8.9。

答：一句话定调，**加载 → 验证 → 准备 → 解析 → 初始化五步；准备给静态变量发默认值（零值），初始化才执行赋值——"默认值"和"赋值"分两步是这题最大的坑**。

**五步分工**：加载（拿二进制流、堆里建 Class 对象）；验证（字节码合法性、魔数版本、符号引用存在性——**防恶意字节码的第一道闸**）；准备（静态变量**分配内存并置零值**：static int a=1 此刻 a=0，static final 编译期常量除外——它准备期就赋终值）；解析（符号引用转直接引用，可延迟到运行期——**支持动态绑定**）；初始化（执行 <clinit>：**静态变量的显式赋值 + 静态块合并编译**，JVM 保证 <clinit> 线程安全——**类初始化天然单线程，静态单例的合法土壤**）。

**初始化顺序**（含继承）：父静态 → 子静态 → 父实例字段+实例块 → 父构造器 → 子实例字段+实例块 → 子构造器（与 1.2 静态题口诀一致，那题偏现象，这题偏原理）。

**触发时机（主动引用六种）**：new/读写静态字段/调静态方法/反射/子类初始化触发父类/main 所在类。**三种被动引用不触发**：通过子类引用父类静态字段（只初始化父类）；定义类引用常量（编译期内联，见 1.2 静态题深水区）；数组 new 只建数组对象不初始化元素类。

**拉开差距的深水区**：<clinit> 由 JVM 加锁保证单次执行——**静态内部类单例**（Holder 模式）的线程安全不靠任何锁，靠的就是这条规范；接口的初始化特殊——初始化实现类不触发接口初始化，但访问接口的 default 方法会触发（JLS 的细节分叉）。

收尾：五步各一句，重点砸在"准备零值 vs 初始化赋值"的分离和 <clinit> 的线程安全——一个坑一个彩蛋，深讲见 8.9。

> 面试官追问点：静态块和静态字段的执行顺序？应答思路：按源码顺序合并进同一个 <clinit>——写在静态块后面的静态字段赋值先执行也先被静态块读到（写在前面的静态块能看到后面字段的零值），顺序感来自源码拓扑而非语法类别。

#### 双亲委派是什么？什么场景需要打破它？

答：一句话定调，**双亲委派是"收到加载请求先甩给父加载器，父搞不定才自己来"的递归协议——保安全（核心类不被篡改）、保唯一（同一个类全局一份）；打破它的都是"需要反过来"的场景**。

**三层加载器**：启动类加载器 Bootstrap（C++ 实现，加载 JAVA_HOME/lib，**Java 里拿到的引用是 null**）；扩展类加载器 Extension（JDK9 改名 Platform，加载 ext / 平台模块）；应用类加载器 Application（加载 classpath，我们写的类多数归它）。自定义加载器继承 URLClassLoader 重写 findClass（**别重写 loadClass，那就把委派链拆了**）。

**协议与价值**：loadClass 的逻辑——先查缓存 findLoadedClass，没加载过就 parent.loadClass 递归向上，父抛 ClassNotFoundException 才自己 findClass。两大价值：**安全**（写个 java.lang.String 想覆盖核心类？委派到 Bootstrap 发现已加载，轮不到你——防核心库被注入）；**唯一**（类的相等以"类加载器 + 类名"共同判定，委派保证同一个类永远只由同一个加载器加载一次，instanceof 和强转才有意义）。

**打破的场景**（全是"父加载器看不到子加载器的类"的场景）：①JDBC 的 SPI——DriverManager 在核心库（Bootstrap）里要加载厂商 jar（classpath）里的 Driver，**父级反向伸手要子级的类**，解法：Thread.contextClassLoader（线程上下文加载器）把"正确的加载器"递进去；②Tomcat 多应用隔离——每个 webapp 一个 WebappClassLoader，**互相隔离 + 优先自己加载**（应用里可以放不同版本的依赖），双亲委派被"先本地后父级"局部反转；③热部署——同一个类换个加载器再加载一次（类身份 = 加载器+类名，新加载器加载的就是"新类"），旧 Class 随旧加载器一起卸载。

**拉开差距的深水区**：JDK9 模块化后类加载结构有变（扩展加载器变 Platform、平台模块化），但**委派模型没变**；OSGi 和 Spring Boot 的 LaunchedURLClassLoader（嵌套 jar 加载）都是"打破与重建"的工业级样本。

收尾：协议一句话、价值两词（安全、唯一）、打破三场景（SPI 反向依赖 / 容器隔离 / 热替换）——结构立住，怎么追问都不慌。

> 面试官追问点：两个不同加载器加载同一个 class 文件，得到的 Class 相等吗？应答思路：不等——Class 的身份是 (加载器, 类名) 二元组，两个 Class 对象互 instanceof 为 false；这是热部署能"替换"类的原理，也是类泄漏的经典来源（旧加载器被缓存引用拖着卸不掉）。

#### 线上CPU飙高怎么排查？OOM怎么定位？

排查链路与常用参数。深度精讲见 8.14。

答：一句话定调，**CPU 飙高三步曲"top 定进程 → top -Hp 定线程 → jstack 定代码"，OOM 两步走"jmap dump → MAT 找支配树"；两条链路的共同心法：先定位到线程，再翻译成代码行**。

**CPU 飙高链路**：①top 找到吃 CPU 的 Java 进程 pid；②top -Hp <pid> 找到进程内最热的线程 tid；③**printf '%x' 把 tid 转十六进制**；④jstack <pid> | grep -A 20 <十六进制 tid>，栈帧直接指到代码行。常见病因：死循环 / 正则回溯爆炸 / 频繁 Full GC（**GC 线程吃满 CPU，用户代码看起来没事**——jstack 会看到多个 GC 任务线程）。替代工具：Arthas 的 thread -n 3 一步到位。

**OOM 定位链路**：OOM 时先看异常信息类型——Java heap space（堆）/ GC overhead limit exceeded（GC 占比超限，98% 时间 GC 回收不到 2% 空间，**通常是堆将满的前奏**）/ Metaspace（动态类生成失控，CGLIB 泄漏）/ unable to create native thread（线程数爆）。取证：jmap -dump:live,format=b,file=heap.hprof <pid>（**-dump:live 会先触发一次 Full GC，线上慎用**）；离线用 MAT（Eclipse Memory Analyzer）看支配树（Dominator Tree）和泄漏报告——**"谁占着内存"和"谁拽着不让回收"分开看**。注意参数预设：-XX:+HeapDumpOnOutOfMemoryError 让 OOM 时自动落盘。

**GC 频繁怎么定位**：jstat -gcutil <pid> 1000 每秒一行看各代占用和 GC 次数——**Old 区锯齿状打满 + FGC 计数狂跳**就是元凶；再结合 jstat -gccause 看 LCause（上次 GC 原因）。

**常用参数一表**：-Xms/-Xmx（初始/最大堆，**生产设成一样**避免伸缩抖动）、-Xmn（新生代）、-XX:MetaspaceSize/MaxMetaspaceSize、-XX:+UseG1GC、-Xss（线程栈）。

**拉开差距的深水区**：**先问"飙高的是什么"再动手**——用户 CPU 高走 jstack 链路，GC CPU 高走 jstat 链路，元数据涨走类加载器审计（jcmd GC.class_stats）；不加区分一通 jstack 是新手画像。深讲见 8.14。

收尾：两条链路各一句口诀——"top→线程→栈"和"dump→支配树"，参数答"堆三件套加 OOM 自动落盘"。

> 面试官追问点：为什么 jmap dump 会影响服务？应答思路：dump 要 STW 暂停全世界（遍历整堆快照），堆越大停越久（几 GB 停秒级）；live 版还先 Full GC——**正确姿势是摘流量再 dump，或用 -XX:+HeapDumpOnOutOfMemoryError 提前埋好**。

#### 强、软、弱、虚四种引用分别什么场景用？

答：一句话定调，**四种引用是"JVM 回收的决心刻度"：强的绝不回收、软的内存紧张才收、弱的 GC 一来就收、虚的形同虚设只为收尸通知——刻度的意义是让你参与对象的死亡决策**。

**四档刻度**：强引用（new 出来的普通引用，**可达即活**，绝不回收）；软引用 SoftReference（内存不足要 OOM 前，回收其指向——**缓存的弹性垫**）；弱引用 WeakReference（**下次 GC 必收**，不管内存够不够——"活着就行、随死随删"的临时索引）；虚引用 PhantomReference（**get 永远返回 null**，唯一作用是配合引用队列 ReferenceQueue 在对象被回收时收到通知）。

**场景对号**：软引用——内存敏感的图片/页面缓存（内存紧张自动让路，避免 OOM）；弱引用——**ThreadLocalMap 的 key**（3.3 第 2 题：外部不用了让 GC 顺手带走）、WeakHashMap（key 没人引用了条目自动消失，适合"给对象挂临时元数据"）；虚引用——**堆外内存的收尸**（DirectByteBuffer 被 GC 时，虚引用进队列，Cleaner 收到通知释放堆外那块——堆里的壳回收了，堆外的地要有人扫）。

**拉开差距的深水区**：为什么需要四种（本题的哲学分）——**GC 的默认逻辑是"非黑即白"（可达=活，不可达=死），四档引用把灰度带进来了**：你可以声明"能放就放（软）""随死随走（弱）""死了叫我（虚）"，缓存、索引、资源清理三种需求三种刻度；软引用在 HotSpot 里的实际回收偏保守（内存压力触发的判断不等价于"快 OOM"），**生产缓存更常用 Caffeine 的 W-TinyLFU 而非裸软引用**。

收尾：刻度一句话各配一个场景——强、软（缓存）、弱（ThreadLocal key）、虚（堆外收尸），四种引用就答成了"工具箱"而非"名词表"。

> 面试官追问点：虚引用为什么比 finalize 更适合做资源清理？应答思路：虚引用回调发生在对象真正死亡后（finalize 是死前还能复活），语义干净；且 Cleaner 的执行线程独立、不拖累 GC——JDK9 起 finalize 废弃，虚引用+Cleaner 就是官方指定的接班人。

# 5.IO与序列化

#### BIO、NIO、AIO有什么区别？NIO三大组件说一下

答：一句话定调，**BIO 是"一个连接一个线程死等"，NIO 是"一个线程轮询一批连接的就绪事件"，AIO 是"内核把活干完再叫你"——三代的差别是"等的位置"从用户态逐步下沉到内核态**。

**三代模型**：BIO（同步阻塞）——accept/read 没数据就挂起，连接多则线程多（万连接 = 万线程，3.1 线程内存题的灾难现场）；NIO（同步非阻塞，JDK1.4）——read 立即返回，配合 Selector 事件轮询，**一个线程管成千上万连接**（就绪了才处理，处理时数据已就位，所以叫"同步"）；AIO（异步非阻塞，JDK1.7）——发起 read 直接返回，内核把数据**复制到你的 Buffer 完成**才回调，连"就绪后的复制"都不用你管。

**NIO 三大组件**：Channel（双向通道，替代单向的流，可以读也可以写、可非阻塞）；Buffer（数据容器，**七个 position/limit/capacity 指针 + flip() 翻转**的读写切换设计）；Selector（多路复用器——注册一批 Channel 的 OP_ACCEPT/OP_READ 事件，select() 阻塞到有事件，底层是操作系统 epoll/kqueue 的 Java 封装，见技术篇《Reactor 与 epoll》）。

**拉开差距的深水区**：①零拷贝——传统读文件发网络是"内核缓冲→用户缓冲→Socket 缓冲→网卡"四次拷贝三次切换；transferTo 走 sendfile（内核直接把页缓存发给网卡，**一次都不进用户态**）、MappedByteBuffer 走 mmap（文件映射进用户地址空间，省一次拷贝）；②DirectByteBuffer——堆外内存，**省去"堆内 → 网卡前先拷到堆外"这一步**（内核不能直接访问 JVM 堆上会移动的地址），代价是分配贵、要靠虚引用清理（4 章引用题闭环）；③AIO 在 Linux 上的真相：内核异步 IO 支持弱，Netty 一度实现又删了——**生产 NIO + Reactor 才是主流**（Netty/Redis 同款）。

收尾：三代答"等的下沉"，组件答 Channel/Buffer/Selector，深水区答零拷贝和堆外——最后一句"Netty 删过 AIO"能镇场。

> 面试官追问点：Buffer 的 flip() 干什么？应答思路：写完转读的指针翻转——position 归零、limit 定到原 position；忘 flip 是 NIO 手写代码的头号 Bug（读到 0 字节或旧数据），指针语义是 Buffer 设计的入门税。

#### Java序列化和JSON、Protobuf比各有什么优劣？

答：一句话定调，**Java 序列化是"给 JVM 自己用的二进制"（跨语言封闭、体积大、安全问题多），JSON 是"给人看的通用语"（可读但胖），Protobuf 是"给机器用的紧凑语"（快瘦但要 schema）——选型第一问：读它的还会是 Java 程序吗**。

**Java 序列化机制**：实现 Serializable（标记接口，全反射扫描字段）或 Externalizable（自己控制读写字段）；**serialVersionUID 是版本指纹**——反序列化时两边不一致直接抛 InvalidClassException；没显式声明时编译器按类结构算一个，**改一个字段就"断亲"，显式声明是纪律**。

**对比表**：

| 维度 | Java 序列化 | JSON | Protobuf |
|:--:|:---|:---|:---|
| 可读性 | 无 | 有 | 无（可配 .proto 才可读） |
| 体积 | 大（带类元数据） | 大（字段名字符串占一半） | 小（varint 编号） |
| 速度 | 慢 | 中 | 快 |
| 跨语言 | 仅 Java | 全平台 | 全平台 |
| schema | 隐式（类定义） | 无（易脏数据） | 有（.proto 强约束） |
| 安全 | 反序列化漏洞重灾区 | 相对安全 | 相对安全 |

**拉开差距的深水区**：Java 序列化被社区视为历史包袱——**反序列化是"构造任意对象执行任意代码"的入口**（readObject 会执行 readObject/readResolve 等回调，攻击面极大，历史上 CVE 成灾），Effective Java 把"避免 Java 序列化"列为条款；JSON 的字段名字符串占了传输量的大头，Protobuf 用"字段编号 + varint"（小的数一两个字节）把体积压到 JSON 的 1/3~1/5——**体积差的核心是"名字 vs 编号"**。

收尾：内部缓存可用 Java 序列化（省心），跨系统接口用 JSON（调试友好），高性能 RPC 用 Protobuf（gRPC 同款）——按"读者"选格式。

> 面试官追问点：serialVersionUID 不一致一定失败吗？应答思路：显式声明且不同 → 失败；两边都自动生成 → 类结构变了指纹必变 → 也失败；它防的就是"静默地把流错解成不合拍的类"，宁可错杀。

#### transient关键字有什么用？和static什么区别？

答：一句话定调，**transient 是实例字段的序列化豁免权：不参与序列化，反序列化回来是默认值；static 根本不属于对象，序列化只对实例状态，两者不搭界**。

**transient 的作用**：修饰实例字段 → 序列化时跳过它。用途三类：**安全敏感**（密码字段别落盘别进网络流）、**派生数据**（缓存、可以重算的中间结果，省体积）、**不可序列化的字段**（Thread、Socket 这类没法序列化的引用，不加 transient 整个对象直接抛 NotSerializableException）。

**反序列化后的值**：默认值——int 是 0、引用是 null；**如果构造器/readObject 里不做恢复，业务代码拿它就用默认值裸奔**（密码反序列化成 null 是经典事故，正确做法是自定义 writeObject/readObject 或反序列化后立刻补值）。

**和 static 的区别**：维度完全不同——transient 管"实例字段的序列化开关"，static 管"字段属于类不属于对象"；**序列化的对象是实例状态，static 字段本来就不在序列化范围内**，所以"static + transient"同时出现毫无意义（transient 那半是废话）。两者都会让字段"不进流"，但机制一个字：一个是被豁免，一个是压根不在场。

**拉开差距的深水区**：transient 只对 Java 原生序列化生效——**Jackson/Fastjson 等框架不认它**（各自用 @JsonIgnore/@Transient），跨序列化框架时要防"这个字段在 Java 序列化里安全了、在 JSON 里裸奔"的错觉；ArrayList 内部 elementData 就是 transient 的——数组尾部预留空间不序列化，writeObject 里按 size 精确写出（**自定义序列化缩减体积**的官方示范）。

收尾：transient 答三个用途 + 默认值陷阱，static 答维度不同——最后补 elementData 的例子，从"知道"变成"读过"。

> 面试官追问点：transient 字段的值反序列化后能恢复吗？应答思路：能——自定义 readObject 里补，或实现 readResolve/Externalizable 全接管；默认机制不恢复，恢复是你自己写的逻辑，框架只留了钩子。

#### 同步IO和异步IO、阻塞和非阻塞怎么区分？

答：一句话定调，**两根轴别混：阻塞/非阻塞是"没数据时你等不等"，同步/异步是"数据的最后一步复制谁来做"——组合出四象限，BIO（阻塞+同步）、NIO（非阻塞+同步）、AIO（非阻塞+异步）**。

**阻塞 vs 非阻塞**：调用 read 后没有数据——阻塞版挂起线程干等（BIO）；非阻塞版立即返回"没数据"（NIO，配合 Selector 的事件轮询使用，**非阻塞的读本身没价值，值钱的是"非阻塞 + 多路复用"的组合**——一个线程轮询一万个连接的"有没有数据"）。

**同步 vs 异步**：数据就绪后，**内核缓冲 → 用户缓冲的复制这一步**谁来搬——同步是用户线程自己调 read 搬（NIO 的 read 就绪后还得自己搬）；异步是内核搬完放进你给的 Buffer 再通知你（AIO 的回调），你连搬都没搬。判断口诀：**"自己搬 = 同步，内核搬完叫我 = 异步"**。

**一个生活比喻**：楼下取快递——阻塞：站在快递柜前死等快递员来；非阻塞同步：不停刷手机看"到了没"，到了自己下楼取；非阻塞异步：快递员直接送到你家门口再给你发消息。

**拉开差距的深水区**：UNIX 网络编程的五 IO 模型（阻塞/非阻塞/IO 多路复用/信号驱动/异步）里，**Java 的 NIO 对应"多路复用"（epoll/kqueue 的封装）而不是"非阻塞裸读"**——Selector.select() 本身是阻塞的（阻塞在事件上而非数据上），"NIO 完全不阻塞"是口误级的错误表述；Reactor 模式就是把 select 事件循环包成工程框架（Netty 的 boss/worker 线程组）。

收尾：两轴四象限 + 一句"自己搬 vs 内核搬"，最后修正"NIO 是多路复用"——这题就答穿了。

> 面试官追问点：为什么 Linux 上 AIO 没流行起来？应答思路：内核异步 IO（io_uring 之前）接口残缺、只支持直连设备的 O_DIRECT 场景；epoll + Reactor 已够好，生态惯性站在 NIO 这边——io_uring 正在改写这个故事。

#### 流为什么必须关闭？嵌套流的关闭顺序？

答：一句话定调，**关流关的不是对象，是操作系统的句柄——它是进程级的硬资源，进程不退就占用；嵌套流的铁律是后开先关，但 try-with-resources 已经替你办好了**。

**为什么必须关**：每 new 一个流，JVM 向操作系统申请一个 fd（文件描述符）——这是**内核资源**，GC 只能回收堆里的 Java 对象，**收不回内核的 fd**（Finalizer 理论上兜底但不保证执行、时机不定，1.1 Object 题）。Linux 单进程 fd 默认上限约 1024（ulimit -n），**不关流的服务跑几天就 Too many open files**，新连接新文件全打不开——半瘫状态比崩溃更难查。文件流的写还有一层：close 前的数据在用户缓冲区，**不 close 可能丢最后一段**（flush 的语义）。

**关闭的位置**：finally 里 close（老写法，模板代码十行）；**try-with-resources**（JDK7+，实现 AutoCloseable 的对象在 try 头里声明，编译器生成"逆序 close + 异常 suppress"的字节码——finally 题讲过）——**现代代码没有理由再手写 finally close**。

**嵌套流的关闭顺序**：后开先关——`new BufferedReader(new FileReader(f))` 先关 reader 再关 fileReader。原因：**外层流关闭时会连带调内层的 close**（装饰器模式把关闭也包了），先关内层再关外层时外层的 close 又对已关的内层再关一次（幂等无害但语义乱）；后开先关保证缓冲先落盘（外层 flush 顺带把内层冲净）再释放。

**拉开差距的深水区**：**跨层流的对象图**——同一个 fd 被多个 Java 流对象引用，关外层即全链关闭，只关内层则外层还挂着 fd；Scoket 流的双向关闭（shutdownOutput 半关闭）是另一支线。

收尾：为什么关答"内核 fd + fd 上限事故"，怎么关答"try-with-resources"，顺序答"后开先关 + 装饰器连带"。

> 面试官追问点：try-with-resources 里 close 抛异常会覆盖业务异常吗？应答思路：不会——业务异常优先抛，close 的异常挂到 suppressed（getSuppressed 取）；这正是它优于手写 finally 的地方：手写版 try/catch 顺序不对会吞掉主异常。

# 6.加解密与编码

> 说明：加密算法在网络协议中的应用（TLS握手、证书链）见《08.网络编程经典面试题》第3.2节，本节聚焦 Java 工程师的加密与编码实操。

#### 对称和非对称加密的区别？HTTPS怎么配合用？

答：一句话定调，**对称加密一把钥匙锁开（快，AES 每秒 GB 级），非对称两把钥匙（慢，慢三四个数量级但解决"钥匙怎么安全给"）——HTTPS 的答案是"非对称只干一件事：安全地交换对称钥匙"**。

**对称加密**：加密解密同一个密钥。AES 是当代标准（DES 已不安全，3DES 是过渡遗老）；流式快到能加密整段视频。死穴：**密钥分发**——双方都得有钥匙，钥匙怎么安全送到对方手里？（"互联网上商量一把不想让第三者知道的钥匙"本身是个鸡生蛋问题）。

**非对称加密**：公钥加密只有私钥能解（RSA/ECC）。解决分发——公钥随便广播，谁想给我发密文用公钥锁即可。代价：**慢三四个数量级**，不适合大数据量。另一用途是**数字签名**：私钥签名、公钥验签——"只有我能签，人人可验"。

**单向加密（哈希）**：MD5/SHA 系列——**不是加密**（不可逆、无密钥），是"指纹"：任意长度进、固定长度出、输入变一位输出面目全非；用途是完整性校验和签名摘要（HTTPS 握手层的 verify_data 就是哈希）。

**HTTPS 的配合**（TLS 握手简化版）：①客户端要随机数 + 支持的套件；②服务端回随机数 + **证书**（证书含公钥，由 CA 私钥签名）；③客户端验证证书链（CA 的信任传递），生成**预主密钥用服务端公钥加密**发出；④双方用三个随机数推出口相同的**会话密钥（对称）**；⑤之后所有业务数据用对称密钥加密（AES-GCM）。**非对称只在握手出场，负责"安全交换对称钥匙"；对称干全部重活**——快的管流量，慢的管信任。

**拉开差距的深水区**：为什么需要三个随机数？——**双方各出随机数防单方预测，第三个由客户端生成经公钥加密传输**，三合一的会话密钥谁都不能单独决定（前向安全的基础逻辑之一）；证书验的是"公钥属于谁"，CA 链是信任的分发链。

收尾：对称快管数据、非对称慢管握手、哈希管指纹——三个角色一句话各归位。

> 面试官追问点：为什么不全用非对称？应答思路：RSA 单核每秒约千次运算级 vs AES 的 GB 级吞吐，全非对称加密网页等于每个字节都跑一次模幂运算——握手三四个包可以慢，正文几百 KB 慢不起。

#### MD5能用来加密吗？怎么增强它的安全性？

答：一句话定调，**MD5 不是加密是哈希（不可逆、无密钥），它的正确岗位是"完整性指纹"；因为碰撞已被攻破，安全场景该换 SHA-256，口令存储该换慢哈希（bcrypt）**。

**本质与用途**：任意输入 → 固定 128 位摘要，不可逆、抗碰撞性是安全底线。正确用途：文件完整性校验（下载页的 MD5）、去重指纹（网盘秒传）、非安全场景的缓存 key。

**"加密"为什么是错的用法**：①哈希无密钥无解密，不是加密；②MD5 的**碰撞攻击已工程化**（2004 年王小云团队宣告碰撞算法，其后 chosen-prefix 碰撞让"伪造两份同指纹的不同证书"成为可演示），任何"把 MD5 值当不可伪造凭证"的设计（数字签名、完整性证明）都失效了；③**彩虹表**把"常见口令 → MD5"全表预算，裸 MD5 存密码等于明文。

**怎么增强**：分层选择——①**加盐**（存 password+salt 的哈希，同口令不同盐不同摘要，彩虹表作废）；②**慢哈希**（bcrypt/scrypt/Argon2，故意设计得慢且吃内存，**暴力枚举的速度被指数级拖垮**——数据库泄露时"每秒试十亿次"变成"每秒试一百次"）；③直接换 **SHA-256**（更长摘要、碰撞尚无实际攻击）——但注意：**SHA-256 加盐存口令仍不如 bcrypt**，快哈希天生利暴力破解。

**拉开差距的深水区**：MD5 的大致流程——**填充**（补到 512 位倍数，尾部 64 位记原始长度）、**分组**（每组 512 位拆 16 个 32 位字，**扩展到 64 轮**）、**轮函数**（四轮非线性变换 F/G/H/I + 常量表 + 左移，链式把前组摘要混入后组）；盐放的位置（拼在口令前后）有讲究——拼接式盐在长度扩展攻击下有姿势差异，HMAC（密钥先混再哈希）才是正规姿势。

收尾：一句话分层——完整性校验还能用、签名别用、存密码用 bcrypt；答出"彩虹表"和"慢哈希"两个词，这题就立住了。

> 面试官追问点：哈希冲突能避免吗？应答思路：鸽巢原理决定必碰撞（无限输入有限输出），安全哈希的设计目标不是消除而是"找不到"——计算上不可行；MD5 的问题是从"找不到"退化为"找得到"。

#### Base64是加密算法吗？它的本质原理是什么？

答：一句话定调，**Base64 是编码不是加密（无密钥人人可逆），本质是"3 字节二进制 → 4 个 ASCII 可见字符"的搬家，牺牲 1/3 体积换"任何老设备老协议都能无损过路"**。

**本质原理**：把输入按每 **3 字节（24 位）一组**切开，切成 4 段、每段 6 位，查 64 字符表（A-Z a-z 0-9 + /，补位用 =）得到 4 个字符。24 = 3×8 = 4×6——位数就是为这个换算设计的。**体积规律**：3 字节变 4 字符，**膨胀 1/3**（不足 3 字节补零，1 字节变 2 字符加两个 =，2 字节变 3 字符加一个 =）。

**为什么它利于传输**：老协议（SMTP 邮件、早期 HTTP 头）只认 ASCII 可打印字符，**二进制里的 0x00/0xFF 会被网关、转码器、邮件网关"善意修改"或截断**；Base64 把任意字节流变成"人畜无害的纯字母数字"，**牺牲 33% 体积，买到 100% 过路安全**。

**使用场景**：图片内联（`data:image/png;base64,...` 省一次请求，但 +33% 体积且不能独立缓存，**小图标合适、大图是反模式**）；HTTP 头传二进制（Basic Auth 的 user:pass）；JWT 的 payload 编码；证书/MIME 邮件附件。

**拉开差距的深水区**：**为什么 64 而不是 128/256 个字符**——可用字符里凑不够 128 个"全球协议都保证不被动"的可见字符（大写+小写+数字+2 个符号刚好 64，且 2 的幂方便位运算切分）；**Base64Url**（+ / 换成 - _）是为 URL 场景改造（+ 在 URL 里是空格、/ 是路径符）；**它给不了任何保密**（没有密钥，解码即还原）——把 Base64 当"加密"用是真实世界高频事故（"密码 Base64 一下"等于裸奔）。

收尾：编码不是加密（3 字节 → 4 字符换过路安全），这一句 + "为什么是 64"的冷知识，够了。

> 面试官追问点：Base64 和 Hex 编码怎么选？应答思路：Hex 是 1 字节 → 2 字符（膨胀 100%）但大小写不敏感、肉眼可读无歧义；Base64 膨胀 33% 更省流量——**存指纹/校验值用 Hex（人要看），传数据用 Base64（机器要快）**。

# 7.高频代码题

#### 手写一个生产者消费者？两个线程怎么交替打印？

生产者消费者（wait/notify 与 BlockingQueue 两种写法）、交替打印、DCL 单例。

答：一句话定调，**生产者消费者的骨架是"一把锁 + while 条件 + notifyAll"（3.1 第 3 题的落地），工业版直接 ArrayBlockingQueue 一行解；交替打印的钥匙是"锁对象本身就是条件，谁持有谁说话"**。

**版本一：wait/notify 原生版**：

```java
class Buffer {
    private final Queue<Integer> queue = new LinkedList<>();
    private final int cap = 5;
    private final Object lock = new Object();

    public void put(int v) throws InterruptedException {
        synchronized (lock) {
            while (queue.size() == cap) lock.wait();   // while 防虚假唤醒
            queue.offer(v);
            lock.notifyAll();                          // 全场喊话，防捞错人
        }
    }
    public int take() throws InterruptedException {
        synchronized (lock) {
            while (queue.isEmpty()) lock.wait();
            int v = queue.poll();
            lock.notifyAll();
            return v;
        }
    }
}
```

三个判分点：**while 而不是 if**（被唤醒后条件可能又被抢跑）、notifyAll 而不是 notify（多条件混用一队列时 notify 可能捞错人，3.1 第 3 题）、wait 抾 InterruptedException 要往外抛而不是吞（线程中断语义保留）。

**版本二：BlockingQueue 一行版**：`ArrayBlockingQueue<Integer> q = new ArrayBlockingQueue<>(5);` 生产者 q.put(v)（满则阻塞），消费者 q.take()（空则阻塞）——**put/take 内部就是版本一的双 Condition 工业化**（notEmpty/notFull 分桌精准唤醒）。

**两个线程交替打印 1~100**（同步块版，注意 **锁对象就是通信载体**）：

```java
class Turn {
    private final Object lock = new Object();
    private boolean oddTurn = true;                    // 轮到谁

    public void print(boolean odd) throws InterruptedException {
        for (int i = odd ? 1 : 2; i <= 100; i += 2) {
            synchronized (lock) {
                while (oddTurn != odd) lock.wait();    // 不是我就等
                System.out.println(i);
                oddTurn = !oddTurn;                    // 交棒
                lock.notifyAll();
            }
        }
    }
}
// new Thread(() -> t.print(true)).start(); new Thread(() -> t.print(false)).start();
```

注意点：状态 flag 要**在锁内读写**（不加锁的 flag 就是数据竞争）；交棒后 notifyAll 唤醒对方。

**拉开差距的深水区**：DCL 单例——**volatile 不能省**（new 的三步重排，8.3 有字节码级拆解）：

```java
class Singleton {
    private static volatile Singleton instance;
    static Singleton get() {
        if (instance == null)                    // 第一次检查：无锁快路径
            synchronized (Singleton.class) {
                if (instance == null) instance = new Singleton();  // 二次检查
            }
        return instance;
    }
}
```

**更优雅的替代**：静态内部类 Holder（<clinit> 的 JVM 线程安全，4 章类加载题闭环）或 enum（防反射防序列化）。

收尾：wait/notify 版背熟"while + notifyAll"两个判分点，交替打印记住"锁即载体"，DCL 记住"volatile 不能省"——手写题的分数全在这些细节里。

> 面试官追问点：为什么不能用 sleep 做"轮到我了"的等待？应答思路：sleep 不释放锁——你睡着也抱着锁，对方连检查条件的资格都没有，程序直接死锁成"一人独木桥"；wait/sleep 的锁语义正是 3.1 第 2 题的落地检验。

#### 手写一个LRU缓存？get和put怎么做到O(1)？

答：一句话定调，**LRU = HashMap 定位 + 双向链表记时序：hash 管"快"（O(1) 找到），链表管"序"（O(1) 摘接）——两个 O(1) 相乘，get/put 才都是 O(1)**。

**先讲为什么需要两件套**：只 hash 无链——不知道谁最久没用（淘汰没依据）；只链表无 hash——找节点要 O(n)（提不到 O(1)）。**设计思路是"让每个操作都落在两件套各自 O(1) 的能力上"**：定位交给 hash，时序调整交给链。

**版本一：LinkedHashMap 三行版**（面试先给这个，再被追问手写）：

```java
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int cap;
    LRUCache(int cap) { super(cap, 0.75f, true); this.cap = cap; }   // accessOrder=true
    protected boolean removeEldestEntry(Map.Entry<K,V> e) {
        return size() > cap;                                        // 超容自动驱逐链头
    }
}
```

原理见 2.2 LinkedHashMap 题：accessOrder 下每次 get 把节点挪链尾，**链头永远是最久未用**。

**版本二：手写 HashMap + 双向链表**（LeetCode 146 标准题，真正的考点）：

```java
class Node { int k, v; Node prev, next; }          // 双向链表节点
class LRUCache {
    private final int cap;
    private final Node head = new Node(), tail = new Node();       // 哨兵：摘头接尾不用判空
    private final Map<Integer, Node> map = new HashMap<>();

    LRUCache(int cap) { this.cap = cap; head.next = tail; tail.prev = head; }

    public int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        unlink(n); linkFirst(n);                   // 挪到队首=最近使用
        return n.v;
    }
    public void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) { n.v = value; unlink(n); linkFirst(n); return; }
        if (map.size() == cap) {                   // 淘汰链尾（最久未用）
            Node last = tail.prev;
            unlink(last); map.remove(last.k);      // 驱逐时要回写就抓这一刻
        }
        n = new Node(); n.k = key; n.v = value;
        linkFirst(n); map.put(key, n);
    }
    private void unlink(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void linkFirst(Node n) { n.next = head.next; n.prev = head;
                                     head.next.prev = n; head.next = n; }
}
```

**四个判分细节**：①**哨兵头尾**（dummy head/tail）——摘接逻辑不用写 null 判断，代码减半；②**节点里存 key**（不是只存 value）——**驱逐链尾时才能 map.remove(last.k)**，只存 value 的写法驱逐时找不到 key（LeetCode 上这题最常见的提交失败点）；③双向而不是单向——摘任意节点要前驱指针，**单向摘除必须从头扫，O(n)**（2.2 LinkedHashMap 追问同源）；④HashMap 的 value 存的是**节点引用**不是值本身——O(1) 拿到节点才能 O(1) 摘接。

**拉开差距的深水区**：进阶三连——**LRU 的并发版**（分段锁或 CAS 链表，工业样本是 Caffeine）；**LFU 的 O(1) 版**（频率桶双向链表套双向链表，LeetCode 460 的 Hard）；Caffeine 的 W-TinyLFU（**Count-Min Sketch 统计频率 + 新旧条目入场仲裁**，用"近似 LFU"的内存成本击败精确 LRU）——答出"手写版之上还有工业版"，这题的层次就全了。

收尾：先讲"两个 O(1) 相乘"的设计观，再三行 LinkedHashMap 表态，最后手写版把"节点存 key + 哨兵 + 双向"三个细节立住——满分结构。

> 面试官追问点：为什么 Redis 用 LRU 而不维护精确的 LRU 链表？应答思路：精确 LRU 要全局双向链表（每次访问都动锁竞争的共享结构），Redis 选择**近似 LRU**（随机采样 N 个 key 淘汰其中最久未用的，对象头里记个时间戳）——用少量误差换掉了全局链表的内存与并发开销，和 LongAdder 分段是同一种"精度换吞吐"的智慧。

# 8.并发与JVM深度精讲（源码与字节码级口述版）

> 说明：本章是并发与 JVM 两章核心题的口述版深度精讲，讲到字节码与 HotSpot 源码层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

### 8.1 Synchronized的底层实现？锁升级的完整过程

答：一句话定调，**JDK6 之后 synchronized 不是重量级锁，而是一条「无锁 → 偏向 → 轻量级 → 重量级」的单向升级链，所有状态变化都发生在对象头的 Mark Word 里**。

**先说字节码层**。同步代码块编译后是 `monitorenter` 指令加两个 `monitorexit`（正常路径一个、异常路径一个，所以看到两个 exit 不是 bug）；而同步方法不走这两条指令，是在方法访问标志里加 `ACC_SYNCHRONIZED`，调用时由 JVM 隐式包一层 monitor 语义。**能说出这个区别，面试官就知道你看过字节码**。

**再说 Mark Word 的位布局**（64 位系统占 8 字节）：同一个 64 位，不同锁态存不同内容，靠末尾的锁标志位区分。无锁态是 hashCode(31位) + 分代年龄(4位) + 偏向位(1) + 锁标志(01)；偏向态把 hashCode 换成线程 ID(54位) + epoch(2位)；轻量级是整个 62 位存指向线程栈 Lock Record 的指针（标志 00）；重量级存 ObjectMonitor 指针（标志 10）。**注意无锁和偏向的标志位都是 01，靠前面那一位偏向位区分**。

**逐级看升级的触发条件**：

1. **偏向锁**：第一次获取时 CAS 把线程 ID 写进 Mark Word，之后同一线程再进入只比对 ID、连 CAS 都省。它有 4000 秒延迟开启（`-XX:BiasedLockingStartupDelay`），因为启动初期竞争多、偏向反而亏；
2. **轻量级锁**：第二个线程来竞争，偏向撤销（要等全局安全点，这是偏向锁最贵的地方），升级为轻量级。每个线程在自己的栈帧里建 Lock Record，CAS 把 Mark Word 换成自己 Lock Record 的指针，抢不到就自旋重试；
3. **重量级锁**：自旋超过自适应次数阈值（JVM 根据上一次自旋的成功率动态调整），膨胀为 ObjectMonitor。拿不到锁的线程进 `_EntryList` 队列并被 park 挂起，调用 wait 则进 `_WaitSet`。**「重」的本质不是锁本身，是线程挂起和唤醒要经过用户态到内核态的切换，一次上下文切换大约几万纳秒，而一次空 CAS 只要几纳秒，差了四个数量级**。

**拉开差距的深水区**：

1. **批量重偏向与批量撤销**：一个类的偏向锁撤销到 20 次（`BiasedLockingBulkRebiasThreshold`），JVM 认为这批对象本来就该给新线程，批量重偏向；撤销到 40 次直接对这个类关闭偏向；
2. **偏向锁在 JDK15 被默认废弃**（JEP 374）：撤销要 safepoint、代码维护复杂，而现代高并发应用里无竞争场景越来越少，收益覆盖不了成本。**能主动讲这个演进，说明你的知识是活的**；
3. JIT 的两个优化：**锁消除**（逃逸分析发现对象不逃出方法，new StringBuffer 的 synchronized 直接删掉）和**锁粗化**（循环里反复加同一把锁，合并到循环外一次加）。

收尾：锁升级的设计哲学是「按竞争烈度付费」：没竞争白嫧偏向，轻竞争 CAS 自旋，重竞争才动用内核。**降级**只在 GC 时整体重置，不存在运行时主动降级。

> 面试官追问点：为什么 wait/notify 必须在 synchronized 块内调用？应答思路：wait 的语义是「释放 monitor 并进 _WaitSet」，不在 monitor 内就没有锁可释放，直接抛 IllegalMonitorStateException；这也是它区别于 LockSupport.park 的地方（park 不需要持有锁）。

### 8.2 AQS是怎么用state和队列实现同步的？

答：一句话定调，**AQS 的全部秘密就是一个 volatile int state 加一条 CLH 变体的双向等待队列，state 的语义由子类定义**。

**先讲 state**：它是 `volatile int`，修改走 CAS。ReentrantLock 里它是重入次数、Semaphore 里是许可数、CountDownLatch 里是倒计数。**同一个框架支撑起半个 juc 包，靠的就是「同步器的 acquire/release 流程固定，state 语义开放」这个设计**。

**再讲队列**：AQS 是 CLH 锁的变体。原始 CLH 是自旋锁（每个节点盯着前驱的状态转），AQS 的改动是**节点拿到不到锁不自旋等到底，而是 LockSupport.park 挂起**，由前驱释放时 unpark 唤醒。队列有个哑头节点，真正的等待者挂在 head 之后，Node 的 waitStatus 里 SIGNAL(-1) 表示「释放时记得唤醒我」。

**acquire 的源码四步**（独占模式，`ReentrantLock.lock` 的路径）：

1. `tryAcquire`：模板方法，子类实现。非公平锁上来先 CAS 抢一把 state，抢到就把 exclusiveOwnerThread 设为自己；公平锁先调 `hasQueuedPredecessors()` 检查队列有没有前驱，有就不抢；
2. 抢不到 `addWaiter`：CAS 快速入队尾部，失败进 `enq` 自旋重试（处理并发入队和空队列初始化哑头）；
3. `acquireQueued`：自旋判断「我的前驱是不是 head」，是才有资格再 tryAcquire；不是就 `shouldParkAfterFailedAcquire` 把前驱的 waitStatus 改成 SIGNAL，然后 park 挂起。**注意先改前驱状态再挂起的顺序：保证自己睡着后前驱释放时一定会叫醒我**；
4. 被唤醒后重试获取，成功把自己设为新 head；期间被中断过的话补一个 `selfInterrupt`（AQS 的 park 不响应中断标志位，要手动补）。

**公平与非公平的差距就在第一步**：非公平允许「插队」（新线程不检查队列直接 CAS），吞吐更高是因为**刚释放锁的线程大概率还活着 CPU 缓存里，让它直接拿走，省了一次唤醒队列头线程的上下文切换**；代价是队列中的线程可能长时间拿不到锁。

**拉开差距的深水区**：

1. **ReentrantLock 的可重入实现**：tryAcquire 时先判断 `exclusiveOwnerThread == 当前线程`，是就 `state + 1`，不需要 CAS（只有自己在改）；
2. **Condition 的底层**：每个 Condition 有一条**单向等待队列**（和同步队列是两条队列），await 把节点从同步队列摘下放进条件队列并释放锁，signal 把节点从条件队列迁移回同步队列尾部。**「两条队列的迁移」就是 Condition 的全部**；
3. **为什么用双向链表**：唤醒时要找前驱（cancelAcquire 跳过取消节点时要改前驱的 next），单向链表做不到。

收尾：AQS 把「队列、挂起、唤醒」这些脏活全包了，子类只回答两个问题：state 怎么算获取成功、怎么释放。这就是模板方法模式在并发领域的教科书应用。

> 面试官追问点：synchronized 和 ReentrantLock 怎么选？应答思路：三个差异答层次（实现层：JVM 内置 vs AQS 库实现；功能层：ReentrantLock 有公平/可打断/超时/多条件变量；性能层：JDK6 后锁升级让 synchronized 不落下风），结论是「无特殊需求用 synchronized，需要高级特性才用 Lock」。

### 8.3 volatile是怎么保证可见性和有序性的？

答：一句话定调，**volatile 只有两个语义：可见性和有序性，唯独没有原子性；它的底层是「MESI 协议 + 内存屏障」的双层保障**。

**先建立 JMM 的模型**：Java 内存模型把世界抽象成主内存和工作内存，线程对变量的操作必须在工作内存完成再回写（read/load/use/assign/store/write 八种原子操作）。**JMM 是规范，MESI 是硬件实现，两者之间还隔着编译器**——这句话是理解本题的钥匙。

**可见性这层，深水区在这**：很多人答「volatile 靠 MESI 保证可见性」，半对。MESI（Modified/Exclusive/Shared/Invalid 四态）保证的是**硬件缓存层**的一致：一个核写了缓存行，其他核的副本自动失效。但**编译器会把变量缓存进寄存器**，这层 MESI 管不到。volatile 的真正增量是：禁止这个寄存器缓存（每次 use 都强制 load）+ 写后强制刷回主存并失效其他副本。所以准确的说法是：**MESI 管硬件缓存，volatile 补齐编译器这一层**。

**有序性这层，落到 JLS 的屏障插入策略**（这是能背出细节的加分点）：

1. volatile 写之前插 StoreStore、写之后插 StoreLoad；
2. volatile 读之后插 LoadLoad 和 LoadStore；
3. 其中 **StoreLoad 是全屏障，最贵**（它要等所有写指令落地才能执行后面的读），x86 上用 `lock` 前缀指令实现，这解释了为什么 volatile 写有额外成本。

**DCL 半初始化问题讲到位要落到字节码**。`instance = new Singleton()` 编译后是三条：

```text
0: new           # 分配内存，引用压栈
3: dup
4: invokespecial # 调 <init> 初始化对象
7: putstatic     # 把引用赋给 instance
```

允许重排的是 4 和 7（分配 → 赋值 → 初始化）。线程 A 走到 7 还没执行 4，线程 B 第一次判空发现非 null，直接返回一个**字段全是默认值的半初始化对象**。volatile 的 StoreStore 屏屏障禁止 `invokespecial` 与 `putstatic` 重排，才堵上这条缝。**讲到字节码三步，这个问题就答穿了**。

**为什么不保证原子性**：i++ 是 read-modify-write 三步，volatile 保证每步读的是新值，但三个线程可以同时读到同一个值、各自加一、先后写回，丢两次更新。要原子性用 AtomicInteger（CAS 循环）或锁。

**拉开差距的深水区**：JLS 的 17.7 条规定 **long 和 double 的普通读写允许拆成两次 32 位操作**（32 位平台的历史遗留），单线程无感，多线程下另一个线程可能读到「高低位各取一半」的缝合值；`volatile long` 保证单次写入。这是极少人知道的规范级细节。

收尾：volatile 是「一写多读」场景的轻量同步（状态标志位、DCL），复合操作场景让位给 CAS 和锁。

> 面试官追问点：happens-before 和 volatile 什么关系？应答思路：happens-before 是 JMM 判断可见性的规则集（程序顺序、监视器锁、volatile、线程 start/join、传递性），volatile 写-读建立一条 happens-before 边，配合传递性推导出「写之前的所有操作对读之后都可见」，这就是它能支撑 DCL 的数学基础。

### 8.4 线程池的源码实现？ctl字段和Worker的设计

答：一句话定调，**ThreadPoolExecutor 的核心是一个 AtomicInteger 的 ctl 字段加三条 execute 分支，Worker 线程「常驻」的真相是阻塞在队列的 take 上**。

**先讲 ctl 的位设计**：`private final AtomicInteger ctl = new AtomicInteger(...)`，**高 3 位是运行状态（RUNNING/SHUTDOWN/STOP/TIDYING/TERMINATED），低 29 位是线程数**，一个字段同时管两个语义。为什么打包？因为「检查状态 + 增减线程数」需要原子完成，两个字段就要两把锁。**能讲出这个位运算设计，说明你真读过源码**。

**execute 的三步分支**（源码顺序）：

1. 当前线程数 < corePoolSize：直接 `addWorker(core=true)` 起新线程执行，**不排队**（这是很多人答反的点：核心线程未满时任务是插队执行的，不进队列）；
2. 核心满了：`workQueue.offer` 入队。入队成功后再 double-check（防止入队后线程池被 shutdown），发现没有存活线程就补一个；
3. 队列也满了：尝试 `addWorker(core=false)` 起非核心线程，线程数达到 maximumPoolSize 还失败，走 `reject`（默认 AbortPolicy 抛异常）。

**Worker 的设计有个必讲的细节**：Worker 内部类**继承了 AQS 且把 state 初始化为 -1、且不可重入**。目的是双重的：state=-1 让「Worker 刚创建还没开始跑 runWorker」之前，`interruptIfStarted` 的中断请求被挡掉（-1 表示还不能中断）；不可重入的独占锁表达「任务运行中（持锁）不允许中断」的语义，只有 getTask 拿不到任务空闲下来（释放锁）才响应 shutdown 的中断。

**核心线程「常驻」的真相**：runWorker 是个 while 循环反复 getTask，getTask 里区分两种取法：线程数超了 core（或允许核心超时）用 `poll(keepAliveTime)`，时间到没任务返回 null、线程退出；否则用 `take()` **无限阻塞等任务**。所谓常驻，就是阻塞在队列上不消耗 CPU，不是空转。

**shutdown 与 shutdownNow 的语义**：SHUTDOWN 不收新任务但把队列里的跑完；STOP 两者都不要，中断所有线程并把队列剩余任务 drainTo 出来作为返回值。

**拉开差距的深水区**：

1. **execute 和 submit 的异常行为差异**：execute 里任务抛异常会直接打到线程的 UncaughtExceptionHandler 且该 Worker 线程死亡、补一个新的；**submit 把任务包成 FutureTask，异常被捕获存进 Future，线程不死，不调 get 你永远不知道出了错**——生产事故的常见来源；
2. **为什么阿里规约禁用 Executors 快捷方法**：newFixedThreadPool 和 newSingleThreadExecutor 用的是**无界 LinkedBlockingQueue**，任务堆积直接 OOM；newCachedThreadPool 的 maximumPoolSize 是 Integer.MAX_VALUE，可能创建无限线程。手动 new ThreadPoolExecutor，每个参数自己负责；
3. 参数怎么定：CPU 密集 N+1（多一个防缺页停顿浪费），IO 密集 2N 或 N*(1+等待时间/计算时间)。**但正确的答案是「公式只是起点，压测才是终点」**。

收尾：线程池的本质是「用队列做缓冲、用线程复用做降本」，三个参数（core/max/queue）决定它在「吞吐」和「资源」之间站哪边。

> 面试官追问点：线程池的线程抛异常后会怎样？应答思路：execute 路径 Worker 死亡重建（代价是新建线程），submit 路径异常被吞进 Future；所以关键任务要么用 submit 后必 get，要么给 ThreadPoolExecutor 设置 UncaughtExceptionHandler。

### 8.5 G1的Region设计？和CMS比强在哪里？

答：一句话定调，**分代回收建立在两条经验假说上，G1 用 Region 化的堆加停顿预测模型解决了 CMS 的碎片与失控问题**。

**先讲分代的地基**：弱分代假说（绝大多数对象朝生夕死）和强分代假说（熬过多次回收的对象会活很久）。推论就是：**新生代用复制算法**（Eden:S0:S1 = 8:1:1，存活对象在两个 Survivor 间来回倒，默认 15 岁「晋升」老年代，浪费只有 10% 的空间），**老年代用标记整理或标记清除**（存活率高，复制不划算）。

**CMS 的三宗罪**（为 G1 的出场做铺垫）：并发标记清除，停顿短，但 ①**浮动垃圾**（标记后新产生的垃圾本轮收不了）②**并发失败退化 Serial Old**（老年代预留空间不够，并发回收变单线程全停）③**标记清除的碎片**（没有整理，碎片到一定程度大对象放不下，提前触发 Full GC）。

**G1 的四层设计**：

1. **Region 化的堆**：把堆切成 1-32MB（2 的幂）的等大 Region，角色（Eden/Survivor/Old/Humongous）不再是物理连续区域而是动态标签，**「分代」从物理分变成逻辑分**，这是 G1 革新的根基；
2. **停顿预测模型**：`-XX:MaxGCPauseMillis`（默认 200ms）是个软目标，G1 跟踪每个 Region 的回收价值（能腾出多少空间 / 预计花多久），**每次只挑选一组「性价比」最高的 Region 组成回收集**。Garbage First 这个名字就是「优先收垃圾最多的」；
3. **RSet（记忆集）**：每个 Region 记录「有哪些别的 Region 里的对象引用了我」（points-into），扫描时只看自己的 RSet 而不用扫全堆。维护靠**写屏障 + 卡表**：引用写入时 post-barrier 把对应 512 字节的卡标 dirty，Refinement 线程异步更新 RSet。**跨代引用问题是分代回收的原罪，RSet 就是赎罪的代价**（可能占堆的 1%-20% 空间）；
4. **SATB**：并发标记防漏标（下一段展开）。

**三色标记的漏标问题是本题的深水区**。白（未访问）灰（自己标了、孩子没标完）黑（自己和孩子都标完），「对象消失」必须同时满足两个条件：**赋值器插入了一条或多条从黑色对象到白色对象的新引用；赋值器删除了全部从灰色对象到该白色对象的直接或间接引用**。破坏任何一个就能保证正确：

1. **增量更新**（CMS 的方案）：破坏条件一，黑色对象插入指向白的新引用时，写屏障记录这个黑引用，重新把它变灰再扫一遍（关注「新增」）；
2. **SATB**（G1 的方案）：破坏条件二，引用被删除时，写屏障把**删除前的旧值快照下来**，按初始快照的对象图做标记，本轮哪怕真变了也下轮再收（关注「删除」），代价是产生浮动垃圾。

**G1 的回收节奏**：Young GC 正常收新生代 Region；老年代占用达到 `InitiatingHeapOccupancyPercent`（默认 45%）触发全局并发标记，标记完做 **Mixed GC**（年轻代全收 + 老年代挑高价值的收）；Full GC 是兜底（JDK10 之前是单线程 Serial，JDK10 起并行，这是版本细节加分点）。

收尾：从 CMS 到 G1 的主线是「把停顿从全堆粒度降到 Region 粒度」，而 ZGC（着色指针 + 读屏障，并发整理）进一步把停顿降到亚毫秒、支持 TB 级堆——**回收器的进化史，就是停顿时间和吞吐量的谈判史**。

> 面试官追问点：什么对象会直接进老年代？应答思路：三个入口：大对象（超过 Region 一半直接进 Humongous）、年龄到 15、**动态年龄判断**（Survivor 中同龄对象总大小超过 Survivor 一半，该年龄及以上直接晋升），第三个最少人知道。

### 8.6 HashMap的源码细节？扩容的高低位链是什么

答：一句话定调，**1.8 的 HashMap 是「数组 + 链表 + 红黑树」，演进主线是给哈希冲突做兜底，而它的扩容有一个极聪明的「高低位链拆分」**。

**先讲 put 链路**：key 先做 hash 扰动，**hashCode 的高 16 位与低 16 位异或**，让高位参与定位（数组长度短时低位决定一切，不扰动等于浪费了 hashCode 的一半信息）；定位用 `hash & (n-1)`，**容量必须是 2 的幂，与运算等价取模但一条指令**。桶空直接放，非空尾插（1.7 头插改尾插，为修复并发扩容成环）。

**树化双条件**：链表长度 ≥8 **且数组长度 ≥64**，后者不满足优先扩容（扩容也能拆链）。阈值 8 来自**泊松分布**：负载因子 0.5 时链长到 8 的概率约千万分之六，树化是极端兜底，正常不该出现。退化阈值 6 防止在 7/8 之间震荡。

**拉开差距的深水区**：

1. **扩容的高低位链**：翻倍后节点新位置只有两种，原址或「原址 + oldCap」，判据是 `hash & oldCap` 是否为 1（多出来的那一位）。1.8 的 resize 不重算 hash，把链拆成 lo/hi 两条尾插到新位置，**O(n) 一次遍历完成迁移，还天然保序**；
2. **TreeNode 为什么同时维护双向链表**：树节点同时串着链（prev/next），**扩容拆分时按链表走一遍就完成树的拆分与退化**，不用对树做结构操作。红黑树只是查找的加速结构，链才是迁移的骨架；
3. **树化的真实前提**是「key 不可变且 hashCode 分散」，如果 hashCode 写得烂（全返回 1），HashMap 会退化成「树化的链表」，比纯链表还慢（树的常数更大）。

**并发问题按版本讲**：1.7 头插在并发扩容时两个线程交错，**next 指针互相指形成环**，之后 get 死循环；1.8 改尾插修了成环，但 put 的「判空+写入」非原子，并发下**后写的覆盖先写的（丢数据）**。结论不变：并发场景换 ConcurrentHashMap。

收尾：HashMap 的设计是「常见路径极致快（位运算定位），病态路径有保底（树化）」，两个阈值（8 和 6）都是为「病态极少发生」这个假设服务的。

> 面试官追问点：负载因子为什么是 0.75？应答思路：空间与时间的折中（0.5 太浪费、1 冲突激增），结合泊松分布参数取值让链长期望落在常数级；能补一句「这是经验值不是数学最优，标准库选择的是统计意义上的甜点」。

### 8.7 ConcurrentHashMap怎么做到读无锁写锁桶的？

答：一句话定调，**1.8 的 ConcurrentHashMap 是「CAS 建桶 + synchronized 锁单桶 + sizeCtl 状态机 + 多线程协助扩容」的组合，读操作全程无锁**。

**先讲 get 为什么无锁**：Node 的 val 和 next 都声明为 volatile，**读路径只有「table 引用 → Node → val/next」三级 volatile 读**，配合写侧的 happens-before，读到的一定是最新值。**「读无锁、写锁桶」是它的第一设计原则**。

**put 的五步**：

1. 计算 hash（再抹上 SPREAD 扰动），table 未初始化先 initTable（**sizeCtl CAS 从 0 到 -1 抢初始化权**）；
2. 桶为空：**casTabAt 直接 CAS 放入**，成功返回，失败自旋重来（说明有竞争）；
3. 桶头是 ForwardingNode（hash=-1，扩容期间的哨兵）：**当前线程先去 helpTransfer 协助扩容**，搬完再回来 put（「人多力量大」的扩容设计）；
4. 桶非空：**synchronized 锁住桶头节点**，链表尾插或树化插入——锁粒度是单桶，不同桶天然并行；
5. addCount 计数（CAS baseCount，失败转 **CounterCell 数组分摊热点**，LongAdder 的思想），检查是否触发扩容。

**拉开差距的深水区**：

1. **sizeCtl 是一个多状态字段**：-1 表示正在初始化；**负数 -N 表示「N-1 个线程在协助扩容」**；正数表示扩容阈值（未初始化时表示初始容量）。一个 int 讲完了「锁、计数、阈值」三件事；
2. **多线程协助扩容**：扩容线程认领「桶区间 stride」（按 CPU 核数分），各自从 transferIndex 原子领取区段迁移，搬完的桶放 ForwardingNode。**新来的写线程看到哨兵不是等待而是加入搬运**，这是「扩容不阻塞写」的机关；
3. **为什么 key/value 都不允许 null**：并发下 get 返回 null 有二义性（「不存在」还是「值就是 null」），HashMap 单线程可以用 containsKey 复查，**并发下「复查」不是原子操作，两态无法区分，干脆禁止**。Doug Lea 在源码邮件里的原话就是这个理由。

收尾：1.7 的分段锁（Segment 继承 ReentrantLock）到 1.8 的「CAS + 单桶 synchronized」，锁粒度从「段」降到「桶」，**且利用了 synchronized 在低竞争下的锁升级优势**，这是一次「把 JDK 自身的优化红利吃到并发容器里」的演进。

> 面试官追问点：size() 是精确值吗？应答思路：baseCount 加 CounterCell 的求和，无锁累加所以是「弱一致快照」，并发写时可能偏小；设计上就用 LongAdder 换掉了 AtomicLong 的单点争用。

### 8.8 ThreadLocalMap的哈希设计和清理机制是什么？

答：一句话定调，**ThreadLocalMap 是 Thread 的字段不是 ThreadLocal 的（方向反转），用开放定址法线性探测，泄漏的根因是「key 被回收了 value 还活着」**。

**先讲结构的反转**：每个 Thread 内部有一个 threadLocals 字段指向 ThreadLocalMap，**Map 的 key 是 ThreadLocal 对象本身（的弱引用），value 是存的值**。「线程持有数据、ThreadLocal 只是索引」的设计，让多个 ThreadLocal 共享一个 Map，而不是每个 ThreadLocal 持有所有线程的表（后者会导致 ThreadLocal 自己无法被 GC）。

**哈希与探测（深水区之一）**：ThreadLocal 的 threadLocalHashCode 以**增量 0x61c88647（2^32 的黄金分割数）递增**，再 & (len-1) 定位——黄金分割增量让连续创建的 ThreadLocal 在 2 的幂长度的数组里**天然均匀散开**，这是开放定址法能工作的前提。冲突时**线性探测下一个 slot**（不是 HashMap 的拉链），所以 Entry 数组必须保持稀疏（阈值 2/3 就扩容）。

**弱引用的角色要讲准确**：Entry 的 key 是弱引用，ThreadLocal 外部强引用断开后，key 可被 GC 回收成 stale entry（key=null）。**弱引用不是泄漏的原因，是补救的开始**：它让「忘删的 ThreadLocal 本身」至少能被回收，并给清理逻辑留下可识别的墓碑。

**泄漏的完整链路**：Thread 活着 → threadLocals 活着 → Entry 活着 → **value 被强引用着**（key 已死 value 未死）。线程池场景 Thread 几乎永生，value 跟着永生。**清理机制两套**：expungeStaleSlot 探测式清理（在 set/get 碰到 stale 时，从墓碑位向后清理并把**其后因探测留下的 entry 前移填补空洞**，保证探测链不断）；还有全量替换式（resize 时清一半）。**但清理是「顺路的」，没有任何路径经过的 stale entry 永远不清理**，所以 remove() 必须手动调。

收尾：正确姿势是 try-finally 里 remove；线程池传上下文要警惕 InheritableThreadLocal 在池化线程上的「继承错乱」（子线程是复用的旧线程），那是 TransmittableThreadLocal 要解的问题。

> 面试官追问点：为什么用线性探测不用拉链？应答思路：Entry 数量少（一个线程的 ThreadLocal 通常个位数）、数组小，探测的缓存友好和低分配开销胜过拉链的稳定性；黄金分割增量保证低冲突，是「规模小所以选简单方案」的典型。

### 8.9 类加载五阶段各做什么？打破双亲委派的场景

答：一句话定调，**双亲委派的本质是「同一个类只被同一个加载器加载一次」，打破它的三个著名场景全是「隔离或反向依赖」的需求**。

**五个阶段的动作要分开讲**：

1. **加载**：全限定名 → 字节流（class 文件/网络/动态生成）→ 方法区数据结构 + 堆上 Class 对象；
2. **验证**：四小项（文件格式魔数版本、元数据语义、字节码指令合法如栈不会下溢、符号引用可解析）；
3. **准备**：static 变量**分配内存并设零值**（value=0 不是代码里的初值），但 **final static 常量此时就赋 ConstantValue**——这就是「常量在编译期已入常量池」的体现；
4. **解析**：符号引用换直接引用（可延迟到首次使用，HotSpot 的懒解析）；
5. **初始化**：执行 <clinit>（编译器按源码顺序收集 static 赋值和 static 块），**JVM 保证 <clinit> 的线程安全（类初始化锁），这也是「静态内部类单例」的并发安全来源**。

**触发初始化的判定要讲「被动引用」**（深水区一）：new/读写静态字段/调用静态方法、反射、子类初始化先初始化父类；**三种不算**：通过子类引用父类的静态字段（只初始化父类）、**数组定义 `A[] a = new A[10]`（触发的是数组类的加载，不触发 A）**、引用编译期常量（进常量池不触发）。

**打破双亲委派的三个场景**（深水区二）：

1. **SPI 反向依赖**：JDBC 的 DriverManager 在核心库（Bootstrap 加载）里要加载厂商实现（classpath），父加载器看不见子加载器的类，**解法是线程上下文类加载器（TCCL），把子加载器「走私」给父**；
2. **Tomcat 的 Web 隔离**：每个 webapp 一个 WebappClassLoader，**先自己加载（web 优先）再委托**，实现「两个应用同库不同版本共存」；破坏的是「唯一性」换「隔离性」；
3. **热部署/OSGi**：网状委派，模块自己的加载规则，为「卸载重载」服务。

收尾：双亲委派不是 JVM 强制的机制（是 ClassLoader.loadSource 的默认实现模板），**它是「类唯一性 + 安全（核心类不被伪造，比如自定义的 java.lang.String 永远到不了 Bootstrap）」的约定**，打破它就是在拿这两个保证换别的需求。

> 面试官追问点：如何实现热替换？应答思路：自定义加载器每次加载新版本类（不同 ClassLoader 的同名类是不同 Class），旧实例等 GC；难点是「引用旧类的对象无法自动迁移」，所以热替换多限于方法体（如某些 agent 方案走 Instrumentation 重定义字节码，不换 Class 对象）。

### 8.10 对象创建的五步？TLAB和指针压缩的原理

答：一句话定调，**对象创建五步走，「TLAB 让分配快到一条指针加法」，布局是「12 字节头 + 实例数据 + 8 字节对齐」**。

**创建五步**：类检查（加载过没）→ **分配内存** → 零值初始化 → **设置对象头** → 执行 <init>。

**分配的三个层次**（深水区一）：

1. **TLAB（线程本地分配缓冲）**：Eden 里给每个线程划一块私有地盘，**分配就是「指针碰撞：移动 top 指针 + 返回旧值」，完全无锁**。TLAB 用完再 CAS 申请新的一块，把锁竞争从「每次分配」摊薄到「每块 TLAB 一次」；
2. **指针碰撞 vs 空闲列表**：堆规整（有压缩的 GC）用指针碰撞，不规整（CMS 这种标记清除）用空闲列表——**分配方式其实由 GC 的整理能力决定**；
3. **大对象直接进老年代**（-XX:PretenureSizeThreshold，避免 Eden 来回复制）。

**内存布局三段**：对象头（**Mark Word 8 字节 + 类型指针 4 字节（指针压缩开启时，指向方法区的 Class 元数据）**，数组再加 4 字节 length）→ 实例数据（**字段重排**：HotSpot 按类型大小降序（longs/doubles → ints → shorts/chars → bytes/booleans → 引用）填隙，同类字段聚集，这也是「父类字段在子类前、但整体可能重排」的规则来源）→ **对齐填充补到 8 的倍数**。

**指针压缩是必讲的数字**（深水区二）：CompressedOops 用 4 字节存引用（配合 8 字节对齐，**4 字节 × 2^32 = 32GB 的可寻址上限，这就是「堆超 32G 压缩失效、反而可能变慢」的算术根源**——引用膨胀到 8 字节，缓存密度下降）。

**访问方式二选一**：**句柄池**（引用指向句柄，句柄含对象和类型两个指针；GC 移动对象只改句柄，访问多一跳）；**直接指针**（引用就是对象地址；访问快一跳，GC 移动对象要改所有引用）。**HotSpot 用直接指针**，因为它的 GC 有记忆集（RSet/card table）能定位「谁引用了这个对象」，改引用的成本可控，换来了更热的访问路径。

收尾：对象这题的全链路是「TLAB 保证分配快、对象头承载 GC 与锁的全部元数据、压缩指针用对齐换密度、访问用直接指针换速度」，四个决策全在拿空间换时间或反之。

> 面试官追问点：对象一定在堆上吗？应答思路：规范说「对象在堆」，但 JIT 的逃逸分析对标量替换后，「逻辑上的对象」可能被拆成寄存器里的几个标量，连堆都没上；所以准确表述是「字节码语义在堆，机器码可以不上堆」。

### 8.11 CAS的ABA问题？LongAdder为什么比AtomicLong快？

答：一句话定调，**CAS 是「一条 CPU 指令完成比较加交换」，ABA 是「值回到原样但历史变了」，LongAdder 用「分段累加」把 AtomicLong 的单点竞争拆掉**。

**CAS 的三层落地**：Java 层 `Unsafe.compareAndSwapInt`（native）→ JVM 层 `Atomic::cmpxchg` → **x86 的 `lock cmpxchg` 指令**（`lock` 前缀锁缓存行保证原子，多核下通过 MESI 协议让其它核的缓存行失效）。**它是乐观锁的硬件根基**：「先读旧值，操作完 CAS 写回，失败说明有人插手」。

**ABA 的完整机理**：CAS 只比对「值相等」，**不感知「中间变过」**——经典场景是无锁栈：线程 1 读到栈顶 A，准备 CAS(A→C)；线程 2 抢先弹出 A、弹出 B、又把 A 压回去；**线程 1 的 CAS 成功，但此刻的 A 节点的 next 已经不是当初那个**——链表结构被破坏。**解法是 AtomicStampedReference**（值 + 版本号的二元组，版本号单调递增，比较的是「值和版本都相等」）； weaker 的方案是 AtomicMarkableReference（一个 boolean 标记）。**实际业务里 ABA 概率不低的场景**：金额先扣再加回、状态先改再改回——**「数据相等」和「事件没发生」是两回事**。

**深水区：LongAdder 的分段思想**——AtomicLong 的竞争模型是「所有线程 CAS 同一个 volatile long」，高并发下大量自旋失败；LongAdder 的解法：

1. **base 加 Cell[] 数组**：无竞争时 CAS base，**有竞争时按线程哈希路由到不同 Cell 各自累加**，sum() 时把 base 加所有 Cell 求和（**最终一致，不保证瞬时精确**）；
2. **@Contended 注解**：**每个 Cell 独占缓存行（前后各补 128 字节）**，避免相邻 Cell 的伪共享（false sharing）让 CAS 互相拖慢；
3. **惰性创建**：Cell 数组懒初始化，**上限是 CPU 核数**（再多是纯浪费——同时运行的核就那么多）。

**读多写少要精确读的场景（计数展示）AtomicLong，纯写入计数（打点统计）LongAdder**——「精确性换吞吐」的取舍。

收尾：CAS 题的心法，「**硬件层一条指令、ABA 用版本号、高并发计数用 LongAdder 的分段**」，能讲 Cell 和伪共享就是读过源码的。

> 面试官追问点：为什么 CAS 不用锁总线？应答思路：早期确实锁总线（代价极高）；现代 CPU 锁缓存行（MESI 保证独占），只有缓存行跨边界或 uncached 内存才退化锁总线——**「锁的粒度从总线降到缓存行」是 CAS 性能的硬件进化史**。

### 8.12 泛型擦除后桥方法是怎么保证多态的？

答：一句话定调，**泛型是编译器的类型检查游戏，运行时全部擦成边界类型（Object 或 extends 的上限），桥方法是编译器为了让「擦除后的世界」仍然多态正确打的补丁**。

**擦除的三条规则**：`T` 无界擦成 `Object`、`T extends Number` 擦成 `Number`、**擦除后字节码里只有边界类型和 checkcast 插入的强转**。**三个证据**：`new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()` 为 true（同一个类）；**不能 `new T()`**（运行时不知道 T 是谁，而且构造器可能私有）；**不能 `new T[10]`**（数组的协变性和类型安全冲突，只能 `(T[]) new Object[10]` 带堆污染警告）。

**桥方法（深水区一）**是必讲的机制：父类 `class Node<T> { void set(T item){} }`，子类 `class MyNode extends Node<String> { void set(String item){} }`——**擦除后父类的方法签名是 `void set(Object)`，子类的是 `void set(String)`**，按 JVM 方法决议规则**这根本不是 override**（参数不同）！编译器在子类合成一个桥方法：`void set(Object item) { set((String) item); }`——**签名匹配父类（多态成立），内部强转调真方法**。`Class.getMethods()` 里能看到 `bridge` 标志的合成方法，**`@Override` 在源码层成立而字节码层靠桥支撑**——这就是「泛型是语法糖」的最硬证据。

**深水区二：PECS 的编译器视角**——`<? extends T>`（生产者）：**擦除后按 T 处理，写入被编译器禁止**（`list.add(null)` 之外全报错，因为编译器无法证明任何具体类型是 T 的子类）；`<? super T>`（消费者）：**擦除后按 Object 处理，读取只能声明为 Object**（写入 T 及子类是安全的）。**「编译期在哪些操作上放行/拦截」就是通配符的全部语义**，不是运行时魔法。

**运行时怎么拿泛型**：**泛型信息在字段签名、方法签名和类的 GenericSuperclass 里保留着**（`getGenericSuperclass` 拿到 ParameterizedType）——**Gson 的 TypeToken 和 Jackson 的 TypeReference 就是靠「匿名子类固化父类泛型参数」这条通道**（`new TypeToken<List<String>>(){}` 的 `{}` 让泛型落进字节码签名），**「擦除了但签名里留了痕」的辩证关系是深水区终点**。

收尾：泛型题的心法，「**擦成边界、证据三个、桥方法补多态、PECS 是编译器拦截规则、TypeToken 靠签名残留**」。

> 面试官追问点：为什么 Java 不学 C# 的具化泛型（reified generics）？应答思路：具化需要修改 JVM 字节码规范和类加载机制（类型参数成为运行时元数据），而擦除让泛型代码与旧字节码二进制兼容（C# 是 CLR 生来就设计好的）；**兼容性债决定了演进路线**，这是语言工程取舍的经典案例。

### 8.13 String常量池在哪？intern在JDK7前后什么区别？

答：一句话定调，**字面量进常量池（JDK7 起在堆里）、intern 是「池里有就返回池引用」、new String 永远在堆上新建本体**。

**先钉死两个经典题的答案**：

1. `String s = new String("ab")` 创建几个对象？**最多两个**：「ab」字面量在类加载的常量解析阶段进池（如果之前没有），**new 在堆上再造一个本体**——**常量池里的和堆上的是两个对象，s 指向堆那个**；
2. 
```java
String a = "hello";
String b = "he" + "llo";     // 编译期常量折叠，b 就是池里的同一引用
String c = "he";
String d = c + "llo";         // 变量拼接 → StringBuilder → 新堆对象
a == b  // true
a == d  // false
d.intern() == a  // true
```
**「字面量拼接编译期折叠、变量拼接运行时新建」是这两题的分界线**。

**intern 的语义（JDK7 的行为变化是考点）**：调用时**池里没有等值串就把「这个对象」登记进池并返回它**——**JDK6 池在 PermGen，intern 会把串复制进 Perm；JDK7+ 池在堆，intern 登记的是引用**（不复制）。于是经典行为差异：`new String("a").intern() == new String("a")` 在 JDK6 是 false（复制了两份），**JDK7+ 的 first-intern 模式下某些案例变 true**（首次 intern 登记了那个堆对象引用）。

**深水区一：StringTable 的结构**——**池是一个固定桶数的 Hashtable（JDK8 默认 60013 桶）**，**哈希碰撞的桶内是链表**；`-XX:StringTableSize` 可调，**大量 intern 会加剧桶内链表（intern 变 O(n)）**，`-XX:+PrintStringTableStatistics` 在退出时打印桶数和碰撞情况——「**intern 不是免费午餐，池也是要维护的哈希表**」。

**深水区二：JDK9 的 Compact Strings**——**String 的内部存储从 `char[]` 改成 `byte[]` 加 coder 标志**（LATIN1 或 UTF16）：**纯 Latin1 的串一个字符一字节（省一半内存）**，只有含非 Latin1 字符的串才用两字节——**「绝大多数业务串是 ASCII」的统计事实换 50% 内存**；这个改动对上层的 API 透明，但**反序列化/反射碰 value 字段的代码会碎**。

收尾：String 池题的心法，「**字面量进池、new 不进池、拼接看编译期还是运行时、intern 的 JDK7 行为变化、StringTable 是真哈希表**」五连发。

> 面试官追问点：String 为什么设计成不可变（配合常量池）？应答思路：池的共享前提是「没人能改」——可变的 String 共享一份池引用意味着「一个人改，所有人遭殃」；不可变是常量池、hashCode 缓存、线程安全三个特性的共同地基，**这是一道「设计因果链」题而不是「背特性」题**。

### 8.14 线上CPU飙高和OOM的完整排查流程是什么？

答：一句话定调，**CPU 飙高三步曲（top→thread -n→jstack 对照 nid）、OOM 三步曲（jmap dump→MAT 支配树→引用链定位），Arthas 是「不 dump 的在线手术刀」**。

**CPU 飙高的完整流程**（数字要具体）：

1. `top` 找到 CPU 高的 Java 进程 pid；
2. `top -Hp <pid>` 找到进程内 CPU 高的线程 tid；
3. `printf '%x\n' <tid>` 转十六进制；
4. `jstack <pid> | grep -A 30 <hex>` 找到线程栈——**栈顶就是烧 CPU 的代码**。

**分支判断（深水区一）**：**top 里 us 高（用户态）**→ 业务代码死循环或正则回溯；**sy 高（内核态）**→ 系统调用频繁（IO 风暴或锁竞争导致的 futex）；**GC 线程（"GC task thread"/"G1 Young RemSet"）占用高**→ 内存问题不是代码问题，转 OOM 排查路线。**jstack 的 RUNNABLE 状态要会细分**：可能是真算 CPU，也可能是**阻塞在 socketRead（NIO 的 epollWait 也显示 RUNNABLE）**——**「RUNNABLE 不等于在烧 CPU」，要看栈顶是 java 代码还是 native 方法**。

**OOM 排查的完整流程**：

1. 先确认 OOM 类型（heap space / GC overhead limit exceeded / Metaspace / Direct memory——**类型决定方向**）；
2. `jmap -dump:live,format=b,file=heap.hprof <pid>`（**live 会先触发一次 full GC 只留活对象**，生产要掂量停顿）；
3. MAT 打开：**Dominator Tree（支配树）按 Retained Heap 排序**，**最大的对象点开 Path to GC Roots（排除弱引用）**——引用链上的业务类就是泄漏源；
4. 常见嫌疑人：**ThreadLocal 没 remove（8.8 的机制）、静态集合无限增长、连接/流没关、Classloader 泄漏（Metaspace 型，热部署场景）**。

**深水区二：不能 dump 的生产环境怎么办**——`jmap -histo:live <pid>`（只打直方图不 dump，秒级）；**Arthas 的在线能力**：`dashboard` 实时面板、`thread -n 3` 直接给最忙线程栈、`heapdump` 按需、**`watch/trace` 在线观测方法出入参和耗时（不重启不改代码）**——「**重武器 dump 只在事后，轻武器 Arthas 在线止血**」的分层策略。

收尾：排查题的心法，「**先分类（CPU 还是内存、用户态还是 GC）、再拿证据（栈和堆）、最后看链（引用链和调用链）**」，每一步有工具、有数字、有分支判断。

> 面试官追问点：jstack 抓一次够吗？应答思路：CPU 问题抓一次即可（高 CPU 线程持续在跑）；**死锁和偶发卡顿要抓多次对比**（间隔 5 秒抓 3 次，同一线程同一栈顶=卡住，栈在变化=正常执行）——「多次采样对比」是分析的基本功。

### 8.15 jstack怎么自动检测死锁？活锁和饥饿的区别？

答：一句话定调，**死锁四条件里「循环等待」是唯一可编程打破的，jstack 能自动检测 Java 层死锁因为它会做「等待图找环」**。

**四个必要条件**（缺一不死）：**互斥、持有并等待、不可剥夺、循环等待**——**工程上主攻第四条**：给锁排序（所有线程按全局一致的顺序拿锁，环就闭不起来）；**tryLock 带超时**是第二防线（破坏「不可剥夺」——拿不到就放弃已持有的，退避后重试）。

**手写死锁（笔试点，考的是真正理解）**：

```java
Object a = new Object(), b = new Object();
new Thread(() -> { synchronized(a){ sleep(1000); synchronized(b){} } }).start();
new Thread(() -> { synchronized(b){ sleep(1000); synchronized(a){} } }).start();
```

**1000ms 是让两个线程都拿到第一把锁**——没有这个 sleep，第一个线程可能直接跑完，死锁变成「运气题」。

**jstack 的自动检测**：**线程转储里输出 "Found one Java-level deadlock"**，并给出环的完整链（thread-1 等待 monitor 被 thread-2 持有、thread-2 等待被 thread-1 持有的）——**检测原理是构建「线程→等待的锁→持有线程」的等待图，找强连通环**；**synchronized 的锁信息记录在对象头和 monitor 里，jstack 拿得到；ReentrantLock 的 owner 也能查（JDK 自带工具对 juc 锁的支持稍弱，ThreadMXBean 的 findDeadlockedThreads 是编程式检测入口）**。

**深水区一：活锁与饥饿**——**活锁**：线程没阻塞但一直在「改状态又退回」（两个线程互相 tryLock 失败都释放重来，永远错开），**修法是引入随机退避**（错开重试节奏）；**饥饿**：线程长期抢不到（优先级低或锁总是被插队），**公平锁是解法但牺牲吞吐**——三者都是「并发活性故障」，和死锁并列。

**深水区二：数据库死锁的对照**——MySQL 的 InnoDB 会**主动死锁检测（等待图找环）并回滚代价小的事务**，或等 `innodb_lock_wait_timeout` 超时——**「数据库选了主动检测加回滚，应用层通常只能预防和重启」**，因为数据库能回滚事务而应用回滚不了半执行的逻辑；**间隙锁（gap lock）的死锁是业务层最难防的**（两个事务锁的范围交叉，肉眼难看出环）。

收尾：死锁题的心法，「**四条件答全、手写带 sleep、jstack 等待图找环、锁排序加 tryLock 双保险、活锁饥饿辨析**」，最后补数据库对照就是加分项。

> 面试官追问点：怎么系统性预防团队代码的死锁？应答思路：静态层面 Codereview 检查「嵌套加锁的顺序是否全局一致」（可写工具扫描嵌套锁的获取序）；动态层面压测环境开 `-XX:+DetectDeadlocks` 类检测；**设计层面减少嵌套锁本身（一把粗锁或无锁结构）比排序纪律更可靠**——「最好的锁是没用的锁」。
