# 1.创建型模式

#### 1.1 单例有哪五种实现？DCL为什么要volatile

答：必问题。一句话定调，**五种实现的差异全在「懒加载、线程安全、防破坏」三个维度的组合上——饿汉用类加载换安全、DCL 用 volatile 加锁换懒、静态内部类白嫖 JVM、枚举是唯一三防全满**。

**五种速览**：饿汉——类加载即创建（安全不懒）；懒汉加方法锁——懒但每次 getInstance 都抢锁（性能灾难）；**DCL 双重检查**——第一重判空挡住后续的锁开销、第二重挡住「等锁期间别人已初始化」；静态内部类——**外部类加载不触发内部类**（懒）+ `<clinit>` 类初始化锁（安全），代码零锁；枚举——JVM 层保证实例唯一。

**DCL 为什么必须 volatile**：`new` 不是原子的——「分配内存 → 初始化对象 → 赋值引用」三步可能重排成「分配 → 赋值 → 初始化」；**另一个线程在第一重判空处拿到了「已赋值但未初始化」的半成品**——volatile 同时戴两顶帽子：禁止重排 + 保证可见性，一顶都不能少。

**防破坏的两条线**：反射——私有构造器里「已存在即抛异常」；反序列化——实现 readResolve 用既有实例替代产物——**但只有枚举在 JVM 层免疫两者**（Constructor.newInstance 对枚举直接拒绝）。

**深水区**：三种线程安全来源的演进——**显式锁（DCL）→ 类初始化锁（静态内部类）→ JVM 特殊化（枚举）**，逐级「从手写到白嫖」；能讲出这条线说明理解的是机制不是模板。

收尾：心法，「**要懒 DCL/内部类、要防御枚举、要简单饿汉**」；反射攻防的完整推演与「构造器抛异常为什么防不住」见 7.1 深度精讲。

> 面试官追问点：构造器里抛异常为什么防不住反射？应答思路：setAccessible(true) 已越过 private 检查，攻击者还能用反射先把 instance 字段置 null 绕过存在性检查——**只有「让第二次构造必然失败」（枚举的 JVM 拒绝）才是真防线**，「检查存在性」类防御全是可绕过的软门槛。

#### 1.2 哪几种单例天然线程安全？懒加载怎么兼得

答：一句话定调，**天然线程安全的来源只有三个：类初始化锁（饿汉、静态内部类）、枚举的 JVM 特殊化、DCL 的 volatile+锁——「懒加载与线程安全兼得」的标准答案是静态内部类：JVM 保证 `<clinit>` 串行，你一行锁都不用写**。

**天然安全的两员**：饿汉——安全由「**类只初始化一次**」保证（类初始化锁天然串行），不懒（不管用不用都占内存——冷启动敏感的组件不该饿）；**静态内部类**——懒与安全的兼得：**外部类加载时不加载内部类**（实例化的时机被藏进「首次引用」这个懒时点）+ JVM 保证 `<clinit>` 只跑一遍——「白嫖 JVM 机制」的优雅解。

**Android 里的两个「系统级单例」**：Application——每进程一个、系统创建（你不用写单例，它就是）；数据库/SP 的 getInstance 惯用法——**用 Application Context 做持有者**（宿主的生命周期决定泄漏风险，与内存管理篇的 Context 选型同源）。

**深水区**：`<clinit>` 锁的规范语义（拿到初始化锁的线程执行、其他线程阻塞——和 C++ 的 Meyers 单例是同一机制的 Java 版）；**ARM 上 volatile 的真实成本**（内存屏障阻止流水线优化——高频读路径更该用「holder + final」的发布安全模式，而不是每次读都过屏障）。

收尾：心法，「**饿汉安全不懒、内部类两全其美、枚举免疫破坏**」。

> 面试官追问点：静态内部类「代码零锁」凭什么线程安全？应答思路：安全不是没有锁，是锁被 JVM 藏了——类初始化锁是隐式的（规范保证的 `<clinit>` 串行）；能答出「显式锁 → 类锁 → JVM 特殊化」的三级演进，说明你把单例题答成了 JVM 题。

#### 1.3 三种工厂模式的区别？分别应对什么变化

答：一句话定调，**三种工厂的差异全在「实例化的决定权放在哪、应对的变化是几维」——简单工厂决定权在工厂（违反开闭）、工厂方法下放客户端（开闭达标、类爆炸）、抽象工厂应对「产品族」的二维变化**。

**三种递进**：
- **简单工厂**：静态方法加 switch 按参数造产品——**加产品要改工厂代码**（踩了开闭原则的「对修改关闭」红线）；适合产品少且稳定；
- **工厂方法**：一个产品配一个工厂——**加产品等于加一对新类，旧代码零改动**（开闭达标）；代价是类数量翻倍；
- **抽象工厂**：**变化维度从「单个产品」升到「产品族」**——UI 套件整体换肤（Button+Text+Input 一套）：**新增族容易（加一个工厂）、新增产品种类难（所有工厂都要改）**——和工厂方法的开闭方向正好互补。

**选型三问**：产品稳不稳定（稳定→简单工厂）？会不会持续加产品（会→工厂方法）？**需求是不是「成套换」**（是→抽象工厂）。

**深水区**：**简单工厂不是原罪**——两三个实现且半年不动的场景，工厂方法是过度设计（5.2 的「按变化频率判断」）；Spring 的 BeanFactory 是「注册表化的工厂」（把工厂推向极致的形态，三级缓存解循环依赖见 7.6 深讲）。

收尾：心法，「**决定权在哪、变化几维、开闭押注哪边**」三问定位三种工厂。

> 面试官追问点：抽象工厂「加产品种类要改所有工厂」为什么还能接受？应答思路：它的适用前提是「产品族结构稳定、族的种类会增长」——**开闭原则永远只对「押中了的那个变化方向」开放**，没有对所有方向都开闭的设计；模式选择的本质是「对未来变化的押注」，能答出这层就不是背 UML。

#### 1.4 DI容器的本质是什么？它是工厂的进化吗

答：一句话定调，**DI 容器 = 工厂 + 反射 + 注解 + 注册表 + 依赖图 + 生命周期管理——「工厂的进化」这个说法成立，但更准确的是：它不光把 new 从业务代码里清除了，还替你决定了「依赖的装配顺序」**。

**四层拆解**：
1. **注册**：注解/配置声明 Bean（@Component/@Bean——元数据层，「要造什么」的清单）；
2. **实例化**：**反射替代手写 new**——工厂的自动化形态（工厂方法是「每个产品一个工厂类」，容器是「一个万能工厂按注册表反射造一切」）；
3. **装配**：**依赖图分析决定创建顺序**（A 依赖 B 就先造 B——拓扑排序）；循环依赖是图上的环，三级缓存解它（7.6 深讲）；
4. **生命周期**：scope 管理（单例/原型/请求级）+ init/destroy 回调。

**「控制反转」的精确语义**：从「对象自己 new 依赖」变成「容器把依赖递进来」——**反转的是「依赖的决策权」**（谁创建、造哪个实现、造几个、什么时候销毁），不是什么玄学；「面向接口编程」由此落地：业务只声明接口类型，实现选哪个是容器的配置问题。

**三种实现路线的分野**：Spring（运行时反射 + 字节码增强）；Hilt（**编译期生成装配代码——缺依赖直接编译失败**）；Koin（**运行时 Service Locator**——严格说不是注入是查找）——「**编译期安全 vs 运行时灵活**」是 DI 框架的第一分水岭。

**深水区**：**Service Locator 与 DI 的本质差异**——Locator 是「用的人去拿」（依赖关系藏在方法体里，读构造签名看不出来）；DI 是「容器递进来」（**依赖声明在签名上——依赖即文档**）；可测试性的差距全部来自这里（构造注入能纯 new 传 mock，Locator 要先初始化整个容器）。

收尾：心法，「**注册-反射-装配-生命周期四层；反转的是决策权不是别的**」。

> 面试官追问点：为什么官方推荐构造器注入而不是字段注入？应答思路：三条工程理由——final 不可变、缺依赖启动即失败（fail fast）、**循环依赖直接报错逼你拆坏设计**（字段注入能跑通循环依赖恰恰是纵容）——能答出「循环依赖报错是特性不是缺陷」就是分水岭。

#### 1.5 Builder解决什么问题？和工厂怎么分工

答：一句话定调，**Builder 解决「构造参数爆炸」的两条烂路——重叠构造器不可读、setter 流水线不安全；它的本质是「配置过程流式、生效瞬间原子」；与工厂的分界：工厂管「造哪种」（类型决策），Builder 管「这种怎么配」（参数组装）**。

**两条烂路先摆出来**：**重叠构造器**——参数一多就是一堆重载，`new Pizza(10, true, false, true)` 调用可读性为零；**JavaBeans 模式**——无参构造加一堆 setter——**对象在 set 完之前处于不一致状态**（可能被并发读到半成品）且天然可变。

**Builder 的解法**：构造参数全部变成 builder 的链式方法（每个返回 this）、build() 一次性交给目标构造器——「**配置阶段随便改、生效点原子**」。

**OkHttp 的范本**：Request.Builder 内部可变，build() 时**拷贝进 Request 的 final 字段**——「**建造期可变、使用期不可变**」：这是线程安全的根源（多线程共享一个 Request 无锁），也解释了「复用同一个 Builder 连续造多个 Request、中途改配置会互相影响」（Builder 是共享可变状态）。

**与工厂的分工**：**「选型」与「配型」互补不竞争**——Retrofit 两样都用：Retrofit.Builder 配参数（建造者），CallAdapterFactory 换实现（工厂）。

**深水区**：StringBuilder 是「可变产品」（build 语义弱化成 toString，更接近缓冲）——**判据是「造完的产品暴露不暴露 setter」**；Lombok @Builder 三坑（默认值丢失要 @Builder.Default、无参构造被顶要补注解、toBuilder 的复制式修改）在 7.7 深讲。

收尾：心法，「**两烂路一解法、可变建造器造不可变产品、选型归工厂配型归 Builder**」。

> 面试官追问点：为什么 Builder 的方法能链式而 setter 返回 void？应答思路：一行返回值的差别，语义差一个模式——setter 的语义是「改状态」（操作到此为止），builder 方法的语义是「继续配置」（操作返回继续操作的能力）；fluent API 的通用设计（Stream、StringBuffer 同款）就是这句话的展开。

#### 1.6 浅克隆和深克隆差在哪？原型模式怎么用

答：一句话定调，**浅克隆只复制「第一层」（引用照抄，内层共享），深克隆递归复制「每一层」（彻底分家）——「共享到哪一层」是唯一的分界线；Java 的 clone 默认是浅的，而 clone 本身有三宗罪，拷贝构造器是更稳的原型实现**。

**两者的边界**：浅克隆——基本类型复制值、**引用类型复制引用**：原型和克隆体共享内层对象（改克隆体的 list，原型也变——**事故的经典现场**）；深克隆——内层递归克隆，两边彻底独立。

**clone 的三宗罪**：
1. **不调构造器**——对象创建绕过了构造函数，**写在构造器里的约束逻辑（参数校验、final 初始化）全部失效**；
2. **与 Cloneable 的配合很怪**——接口不声明任何方法，但 Object.clone 会 instanceof 检查它（不实现就抛 CloneNotSupportedException——历史包袱设计）；
3. **默认浅**——深克隆要自己递归，内层对象的 clone 权限和可见性全是坑。
《Effective Java》的结论：**用拷贝构造器 / 拷贝工厂替代 clone**（`new ArrayList(other)` 本身就是原型模式的朴素实现）。

**原型模式的本体**：**「以现有对象为模板造新对象」替代「从零 new」**——适合「创建成本高」（大对象初始化贵，复制比重建便宜）与「结构复杂」（组合态难以一步步拼）的场景；new 出的副本再逐字段改差异（「模板+微调」）。

**深水区**：**序列化绕道深克隆**——writeObject/readObject 一轮往返等于全图复制（简单但重，且要求全图可序列化）；**Spring 的 prototype scope 与「克隆」无关**——它是「每次注入新实例」的语义，不是以旧模板复制——命名相近的两个概念要主动切开。

收尾：心法，「**浅共享内层、深彻底分家、clone 三宗罪、拷贝构造器更稳**」。

> 面试官追问点：浅克隆「共享内层」什么时候反而是优点？应答思路：只读且昂贵的内部结构（大配置表、常量树）共享是「合理享元」（见 2.8/7.10）——**深浅的选择不是道德题，是共享边界题**：共享谁、谁能改谁；能答出「按可变性划共享边界」说明你在做设计判断而不是背定义。

# 2.结构型模式

#### 2.1 两种适配器的实现差异？典型场景有哪些

答：一句话定调，**两种适配器的差异在「复用的来源」——类适配器靠继承（能直接用父类方法但被单继承锁死）、对象适配器靠组合（委托转发，能适配整个家族）——它是「组合优于继承」的教科书现场**。

**两种实现的对照**：
- **类适配器**：`Adapter extends Adaptee implements Target`——方法体里直接调继承来的方法（**省掉转发样板**）；代价是 Java 单继承的名额被烧掉（不能再继承别的，且只能适配这一个具体类）；
- **对象适配器**：`Adapter implements Target { private Adaptee adaptee; }`——每个方法委托转发；**能适配 Adaptee 及其所有子类、运行期还能换实例**（测试时换 mock 很顺手）。

**两个典型场景**：
- **InputStreamReader**：字节流转字符流的适配——StreamDecoder 把 InputStream 的世界翻译成 Reader 的世界（「编码」是这次翻译的核心参数）；
- **ListView/RecyclerView 的 Adapter**：**把「数据的世界」适配成「View 的世界」**——RecyclerView.Adapter 只留三个抽象方法（onCreateViewHolder/onBindViewHolder/getItemCount），**「数据怎么变成界面」的全部变化被隔离在这三个回调里**——适配器模式的工程价值：变化边界清晰、调用方（RecyclerView）完全不知道数据长什么样。

**深水区**：**适配器与装饰器的边界**——适配器「转换接口」（两套接口的翻译官，接口形状变了），装饰器「增强同一接口」（接口不变，能力叠加）；**与门面（2.5）的边界**——适配是「接口转接」、门面是「简化入口」，前者解决「不匹配」后者解决「太复杂」。

收尾：心法，「**类适配器烧继承名额、对象适配器吃组合红利；翻译官只管接口转接**」。

> 面试官追问点：为什么工业代码里对象适配器远多于类适配器？应答思路：两个理由——单继承名额稀缺（花在适配上就不能花在业务建模上）+ 组合能适配整个家族（Adaptee 的子类天然被覆盖，继承方案要每个子类写一个适配器）——**「继承名额要花在刀刃上」是组合优于继承的落地版**。

#### 2.2 装饰器与继承有什么区别？IO流怎么应用

答：一句话定调，**装饰器是「运行期组合的继承」——把「能力的叠加」从类图里的静态继承，变成运行时按需组装的自由拼装；IO 体系是它最完整的工业实现**。

**继承的病**：能力组合在类图里焊死——「可缓冲的文件流」「可缓冲可数据读的管道流」——**m 种来源 × n 种能力 = m×n 个类**（类爆炸），且编译期定死、运行期不能改。

**装饰器的解法**：实现同接口、内部包一个同接口实例、方法转发前后加料——`new BufferedInputStream(new FileInputStream(f))` 按需任意层堆叠，**m + n 个类覆盖 m×n 种组合**。

**IO 体系的四角色**（把这个背下来 IO 体系就通了）：**InputStream 是抽象组件**、**FileInputStream 是具体组件**（真有数据来源）、**FilterInputStream 是抽象装饰器**（持有一个 inner、方法默认全转发）、**BufferedInputStream/DataInputStream 是具体装饰器**——「来源」和「能力」两个正交维度自由组合。

**与代理的区分一句带过**：代码结构同构，**意图分野——装饰器是调用方主动要求增强、代理是框架在边界控制访问**（「你知道你在用装饰器，你不知道你在用代理」）——完整的源码级对照见 7.8 深度精讲。

收尾：心法，「**装饰器=运行期的继承、组合正交维度、FilterInputStream 是抽象装饰器的样板**」。

> 面试官追问点：为什么要有 FilterInputStream 这个抽象装饰器？直接让 BufferedInputStream implements InputStream 不行吗？应答思路：抽象装饰器把「持有一个 inner + 默认转发」的样板集中一处——具体装饰器只写增量逻辑；没有它，每个装饰器都要抄一遍全套转发——**「抽象层解决重复」是模式结构里的公共招式**（和 AQS 的模板方法是同一思想）。

#### 2.3 三种代理怎么实现？JDK为何只能代理接口

答：必问题。一句话定调，**三种代理的差异在「转发器怎么来」——静态代理手写、JDK 运行时造「实现接口的转发器」、CGLIB 运行时造「子类拦截器」；「只能代理接口」的根因不是技术限制而是「单继承名额被 Proxy 占了」**。

**三种实现**：
- **静态代理**：手写一个类实现同接口、每个方法转发 target——样板代码与接口方法爆炸，但零 magic 完全可控（接口十几个方法就要写十几个转发）；
- **JDK 动态代理**：Proxy.newProxyInstance 生成的代理类 **extends java.lang.reflect.Proxy + implements 业务接口**——**这就是只能代理接口的根因：单继承名额被 Proxy 占了**，没有第二个名额去继承目标类；每个方法体都是「打包 Method 和参数，转发给 InvocationHandler.invoke」；
- **CGLIB**：ASM 字节码直接造「目标类的子类」，方法拦截进 MethodInterceptor.intercept，**super 调用是真实执行的通道**（intercept 里手动 invokeSuper）——限制同样来自继承：final 类/方法不可代理、private 天然不可见。

**深水区一句带过**：**自调用失效**——目标类内部 this.methodB() 不走代理（this 是裸对象），**@Transactional 方法互调失效是同一根因**——「代理增强的是外部调用面」；invoke 里递归陷阱、性能翻案、Spring 代理选择策略的完整版见 7.2 深度精讲。

收尾：心法，「**静态靠手写、JDK 造转发器、CGLIB 造子类、限制全来自继承**」。

> 面试官追问点：为什么 Spring Boot 2 起默认全走 CGLIB？应答思路：消除「同一 Bean 按接口注入成功、按具体类注入失败」的不一致陷阱（有接口时 JDK、无接口时 CGLIB 的自动切换让行为依赖偶然）——**一致性的工程价值大于「理论上的接口纯净」**；能答出「代理选择影响注入语义」说明真踩过坑。

#### 2.4 代理的四种进阶场景？Retrofit怎么用代理

答：一句话定调，**四种代理变体对应四种「控制」——远程代理控制访问透明性、虚代理控制创建时机、保护代理控制权限、智能引用控制生命周期开销——「代理控制的是调用方意识不到的那一面」**。

**四种场景的机制**：
1. **远程代理**：RPC stub——**本地调用的语法、网络调用的实质**，序列化/连接/重试全被中间层吃掉（Android AIDL 的 Proxy、gRPC 的 stub 都是）；
2. **虚代理**：图片懒加载占位——**「先给个壳，真品按需到」**；重对象（大图/字体/连接）的延迟创建，第一次真正访问才触发实例化；
3. **保护代理**：权限校验前置——Spring Security 的方法拦截（能不能调，在目标知道之前就决定了）；
4. **智能引用**：裸引用做不到的「记账行为」——首次访问触发加载、引用计数决定回收（C++ 智能指针是这个名字的极端形态）。

**Retrofit 的应用**：动态代理「**无中生有实现接口**」——你调 apiService.getUser()，invoke 里拿到 Method、解析注解生成请求模板交给 OkHttp——**接口没有实现类，代理对象本身就是实现**；这也是「声明式接口」的运行时地基（声明在前、实现在代理里生成）。

**深水区**：四种变体的公共本质——「**调用方以为在直接调目标，控制逻辑是中间层偷加的**」（与装饰器的「主动增强」形成动机镜像，见 7.8）；**虚代理与享元的边界**——虚代理管「创建时机」（一个壳对应一个真品），享元管「复用」（多场景共享同一个真品）。

收尾：心法，「**四种变体四种控制，控制的共同点是调用方无感**」。

> 面试官追问点：虚代理和享元怎么区分？应答思路：虚代理是「延迟」（壳→真品一对一，只是把创建往后拖）；享元是「共享」（多场景复用同一真品，省的是分配）——**「延迟创建 vs 共享创建」**；答出「一个管时间一个管空间」这组对偶就到位。

#### 2.5 外观模式什么时候用？统一入口怎么设计

答：一句话定调，**外观是「复杂子系统的窄门」——把多步交互压成一次调用，价值的另一半是变化隔离（子系统怎么重构，门面后面的事）；「入口收敛了，横切能力才有挂载点」**。

**什么时候用**：子系统演化复杂（交互步骤多、顺序有讲究、调用方只需要主流路径）——**判断标准是「调用方该不该知道子系统的内部步骤」**：不该知道就该有门面。

**两个工业样本**：
- **Glide.with().load().into()**——背后 RequestManager/Engine/解码器/缓存全是子系统，**三个链式调用是门面**：调用方表达「意图」（拿图显示），从不接触「步骤」；
- **API 网关**——认证、路由、限流、聚合一次打通：**入口收敛的另一重收益**：横切能力（审计/监控/限流）全部挂在唯一的门口，而不用散在每个调用方。

**与适配器的区分**：适配器**转接口**（A 的形状给 B 用，解决「不匹配」）、门面**造新入口**（简化交互，解决「太复杂」）——一个是翻译官、一个是前台。

**深水区**：**门面的滥用面**——「上帝门面」变成新的大杂烩；纪律是**门面只暴露「意图级方法」，不暴露「能力级方法」**（Glide 不会把「设置解码器」暴露给你）；门面与分层的配合——门面站在层边界上，**层内自由演化、层间只认门面**（重构子系统不影响调用方的前提）。

收尾：心法，「**窄门 + 变化隔离 + 横切挂载点，三重价值一个入口**」。

> 面试官追问点：门面和「封装」有什么区别？应答思路：封装是类级「藏数据与实现」，门面是**子系统级「藏交互与顺序」**——门面是封装的粒度升级；能答出「藏的对象从字段变成步骤」说明抓到了模式的本质而不是名词。

#### 2.6 树形结构怎么统一处理？组合模式怎么设计

答：一句话定调，**组合模式统一「叶子与容器」——让调用方用同一个接口处理整棵树，递归是它的引擎；View 体系是它的工业巅峰**。

**机制三角色**：Component（统一接口——operation）、Leaf（叶子：干自己的活）、**Composite（容器：持 children 列表，operation 递归转发给孩子）**——「**对树的任何操作 = 对根调用一次 + 容器逐层转发**」。

**两个工业样本**：
- **View 体系**：View 是叶子、ViewGroup 是容器——绘制（draw 递归）、事件分发（dispatchTouchEvent 递归）全靠「容器把操作转发给孩子」；**ViewGroup extends View（叶子与容器同根）**——调用方拿到的永远是 View，不需要区分叶子和容器——「树的操作统一性」是整个 UI 框架的根基；
- **文件与文件夹**：File 与 Directory——du 命令的递归聚合（size = 各孩子之和）；**与迭代器配合**：树的遍历细节（深度优先的栈、广度优先的队列）被迭代器抽象掉，调用方只 for-each。

**深水区**：**add/remove 放哪的经典争议**——「透明式」把 add 放接口（叶子也继承 add，调用时抛异常：一致但牺牲类型安全）vs「安全式」只有容器有 add（类型安全但调用方要 instanceof 区分）——AWT 走透明、集合框架走安全，**「一致性与类型安全」没有全赢解，只有场景选择**。

收尾：心法，「**统一接口 + 容器递归转发 + 叶子容器同根**」，add 的放置争议是它的设计签名。

> 面试官追问点：为什么说事件分发是组合模式的「带钩子递归」？应答思路：纯组合是「容器无条件转发」；ViewGroup 的递归里插了 onInterceptTouchEvent（转发前先问自己要不要拦截）——**模式 + 一个判定钩子 = 交互框架的雏形**（Android 篇 13.7 的完整三段式就是这套递归的工程化），能看出「模式之上的增量」就是理解不是背诵。

#### 2.7 多维度怎么自由组合？桥接模式怎么设计

答：一句话定调，**桥接把「两个独立变化的维度」从继承的笛卡尔积里拆出来——各建一套层级、用组合连接，类爆炸从 m×n 降到 m+n；「桥」就是那根组合引用**。

**继承膨胀的病灶**：Shape × Color 的组合——RedCircle/BlueCircle/RedSquare/BlueSquare...**m×n 个叶子类，每加一个颜色全家族都要动**；**识别口臭信号**：「形容词+名词」的类名（RedCircle 这种）就是笛卡尔积的现场。

**桥接的解法**：Shape 层只管形状、**持有一个 Color 的抽象引用**——「形状的世界」和「颜色的世界」各成体系、组合连接；m 个形状 + n 个颜色 = m + n 个类，自由组合 m×n 种效果。

**工业马甲**：**JDBC**——API（Connection/Statement）与实现（各数据库 Driver）两个维度桥接（DriverManager 持 driver 引用，桥在 API 侧）；日志门面（SLF4J 的接口体系 × Logback/Log4j 的实现体系）；「平台维度 × 功能维度」的跨端框架（绘制抽象 × 各平台实现——与 Flutter/Compose 的渲染抽象呼应）。

**深水区**：**桥接 vs 适配器**——适配器是「事后补救」（已有两个接口不匹配，转换一下）、桥接是「事前设计」（预判两个维度都会变，先分离）；**桥接 vs 策略**——形似（都持一个抽象引用），分野在目的：**桥接的双方都是可扩展的层级体系，策略是单点的可替换算法**。

收尾：心法，「**两个维度两套层级、组合引用是桥、m+n 替代 m×n**」。

> 面试官追问点：为什么说「优先用组合」能自动消灭大部分桥接需求？应答思路：组合关系天然把「变化维度」拆成字段（Shape 有个 color 字段，一开始就不会写 RedCircle）——**桥接常常是「修复继承错误的手术」**：老代码已经用继承纠缠了两个维度，桥接是把它拆开的手段；新代码一开始就组合，这场手术根本不用做——「模式治病，好的初期设计让病不发生」。

#### 2.8 享元模式是什么？valueOf缓存池的原理

答：一句话定调，**享元 = 「共享细粒度对象」：同样的内容只造一份、按内容索引复用——Integer.valueOf 的 [-128,127] 缓存池是教科书实现，「装箱的边界」是那道百年 == 笔试题的原理**。

**valueOf 的机制**：类加载时静态初始化 **IntegerCache**（预创建 [-128,127] 的 Integer 数组）；`Integer a = 127` 装箱走 valueOf 拿缓存里的**同一个对象**——`a == b` 为 true；**128 超出范围 new 了新对象**——`==` 为 false——「包装类用 == 比较的偶发翻车」全部来自这条缓存边界（Short/Byte/Character 同款，Character 只缓存 [0,127]）。

**String 常量池同款思想**：字面量 intern 复用——**「不可变是可共享的前提」**：String 与 Integer 都不可变，内容永远等价于身份，按内容索引才安全——这条前提是享元合法性的根基（与 2.9 的内部状态呼应）。

**为什么是 [-128,127]**：规范保证的最小范围——**命中率 × 内存代价的平衡点**（小整数使用频率最高的经验值）；`-XX:AutoBoxCacheMax` 可调——设计者承认「按业务分布调优」，能报出可调参数说明读过规范。

**深水区**：**自动装箱的事故场景**——高频循环里的装箱（`for` 里 `sum += i` 的 Long 装箱、HashMap 的包装类 key）产生海量小对象拖慢 GC——**「装箱在热路径上要显式规避」**是享元知识的实战出口。

收尾：心法，「**按内容共享、不可变是前提、缓存边界是 == 事故的根源**」。

> 面试官追问点：为什么缓存池不做得更大？应答思路：池的收益 = 命中率 × 重复分配的代价，代价 = 常驻内存 × 预创建时间——数值分布越靠大数越稀疏，**大池的收益边际递减而内存线性增长**；规范给最小保证、JVM 参数留调优口——「经验默认值 + 可调逃生门」是这类设计决策的标准形态。

#### 2.9 享元的内外状态怎么划分？线程池是享元吗

答：一句话定调，**内部状态是「可共享的不变部分」（进对象），外部状态是「每次使用场景不同的部分」（走方法参数）——享元对象不持有外部状态，这是「一个对象服务多个上下文」的合法性来源**。

**内外划分的标准姿势**：围棋棋子——颜色是内部状态（进对象：黑白两色全盘只有两个实例）、**位置是外部状态（不能塞进棋子——每个位置上的棋子会变）**，落子时把坐标作为参数传给共享的棋子对象；**Message 的字段槽位是「壳」（内部结构），消息内容是每次覆盖的外部状态**——「什么能共享、什么只能传」按「会不会变」一刀切开。

**线程池是享元吗——严格说不是**（高频辨析）：**享元共享的是「状态」**（值不变所以可共享——Integer 缓存是教科书享元）；**池化复用的是「实例」**（状态每次被重写，共享的是**分配成本**）——线程池、Message 对象池、Bitmap 池本质是池化，**借了享元「共享省内存」的哲学**——能分清这条界，说明不是背名词（三个马甲按「身份-壳-内存」的复用粒度对照见 7.10 深度精讲）。

**深水区**：**「外部状态塞进享元对象」是用错的第一现场**——池化对象带上了业务状态 = 并发灾难（连接池的连接带用户态、线程池的 Runnable 捕获了请求级变量——**「池里只能放无状态的东西」是纪律**，违反它的代价是随机出现的串数据 bug）。

收尾：心法，「**内部进对象、外部走参数、池里只能放无状态**」。

> 面试官追问点：享元和单例的区别是什么？应答思路：单例约束「存在性」（这个类型全局只有一个实例）；享元约束「重复性」（**每个内容一个实例，池里可以有多个不同值的实例**）——Integer 缓存池里有 256 个 Integer，谁也不是单例；「一个管数量、一个管重复」，这组对偶比背定义更能证明理解。

# 3.行为型模式

#### 3.1 观察者模式的推与拉？EventBus怎么用

答：必问题。一句话定调，**观察者的本质是「依赖关系的倒置」——主体不再逐个调用依赖者，而是维护订阅表广播；推与拉是「数据塞进参数还是让观察者自己取」的取舍**。

**经典结构**：Subject 维护 List\<Observer\>（attach/detach/notify），状态变更遍历调 update——「**调用的方向反转：从『我知道谁依赖我、我调他』变成『你注册、我广播』**」。

**推与拉的取舍**：
- **推模型**：数据塞进 update 参数——观察者省事，**但参数结构成了双方的耦合面**（加字段全体观察者跟着改签名）；
- **拉模型**：只传主体引用，观察者按需取——**灵活但观察者要了解主体内部**（取多深合适是个永恒的拿捏）；**EventBus 的事件对象是「结构化推」**——推的东西是一个自描述对象，两边的耦合降到只剩事件类型。

**EventBus/ LiveData / RxJava 的演进一句带过**：观察者（直接持有）→ EventBus（**订阅表从主体身上拆下来变成全局中介**——解耦的代价是追踪链路断裂）→ LiveData（**订阅绑定生命周期自动解绑**）→ RxJava（**订阅可组合可取消**）——每一步都在给上一步的代价打补丁，完整演进见 7.4 深度精讲。

**深水区**：**广播的顺序与异常**——遍历通知时某个观察者抛异常，后面的观察者还收得到吗（EventBus 默认全停，RxJava 的错误传播策略可配）——**「通知的健壮性要不要隔离」是生产代码和 demo 的分界**；线程模型（订阅回调跑在哪个线程）是所有事件框架的第一设计决策。

收尾：心法，「**调用方向反转、推拉看耦合面、订阅的生命周期管理是现代框架的主战场**」。

> 面试官追问点：观察者模式和回调函数什么区别？应答思路：回调是「一对一的函数级订阅」（一个事件一个 hook，编译期确定）；观察者是「一对多的对象级订阅」（运行期可增可删）——**「量级与时机」两维不同**；EventBus 一类框架本质是「把回调的注册键从字段名换成事件类型字符串」。

#### 3.2 if-else太多怎么办？策略模式怎么消除

答：一句话定调，**if-else 的罪不在语法，在「变化的东西和不变的东西缠在一起」——策略把「每种做法」变成对象、注册表解决「按 key 找到它」，重构完成态是「新增分支零改动」**。

**病灶三宗罪**（支付渠道的 switch 是经典现场）：**每加渠道改同一个函数**（改动触面集中、merge 冲突高发）；**无法单测「只测一个分支」**（mock 要喂全上下文）；**函数随业务线性膨胀**（半年后三百行）。

**重构三步**：
1. **抽策略接口**：`PayChannel { String key(); PayResult pay(Order o); }`——每个渠道一个实现类，互不知晓；
2. **注册表替代 switch**：`Map<String, PayChannel>`——**Spring 的注入魔法在这里发光**：构造参数收 `List<PayChannel>`，容器自动收集所有实现，构造里逐个入表——注册逻辑零 switch；
3. **上下文只剩路由**：`map.get(channel).pay(order)`，找不到统一抛业务异常。

**什么时候不该重构**（深水区）：**分支 2-3 个且半年没动过的，策略是过度设计**——类数量的成本买了没人用的灵活性；**判断标准是「变化的频率」不是「if-else 的行数」**——「模式为变化服务，不为美感服务」。注解驱动注册、异常类型选择（业务 400 还是 bug 500）的细节在 7.9 深讲。

收尾：心法，「**罪在缠绕不在语法、接口+注册表两步走、按变化频率决定动不动**」。

> 面试官追问点：策略模式和「把 if-else 换成 Map」有什么区别？应答思路：Map 只是「查找结构的替换」；策略的完整价值在「每个做法成为独立类」——可独立测试、可携带自己的配置与状态、可在运行期组合；**「消灭 if-else」是副产品，「隔离变化」才是目的**——答出这层说明你重构过而不是看过。

#### 3.3 状态流转怎么建模的？迁移表和策略的差异

答：一句话定调，**状态模式把「每个状态的行为」变成对象，状态间自己知道「下一步去哪」——与策略的分野只有一个：谁来选择行为，客户端选是策略、对象内部自动流转是状态**。

**订单状态的场景**：待支付 → 已支付 → 已发货 → 已完成（加取消/退款分支）——**if-else 建模的病**：「当前是什么状态、下一步能干什么」散落在每个方法里，加一个状态全方法体检。

**状态模式的建模**：Context 持 state 引用、委托给它；**每个状态类里写清「我能响应什么、响应后迁去哪」**——pay() 在待支付状态里把 Context 迁到已支付，在已支付状态里直接拒绝——「**规则就近声明**：迁移逻辑和状态定义在同一个文件里」。

**迁移表是另一种建模**（深水区一）：**状态 × 事件 → 次态**的二维表 + 一个解释器循环——**表驱动把规则做成数据**（新状态加一行、可热更新、可可视化）；**状态类把规则做成代码**（有类型安全、方法可以有复杂逻辑）——**「规则简单量大选表、规则复杂带副作用选类」**；工作流引擎（状态机库 Squirrel/Stateless4j）本质是表驱动的工业化。

**与策略的对照**（深水区二）：**选择权归属**——策略每次由客户端显式选（这次用支付宝是用户选的）；状态由上一状态自动流转（订单推进不需要外部每次指定）；**状态类通常持 Context 引用**（要发起迁移），策略不持（拿了就是越权）——同一「多态替换分支」的结构，这一条引用决定了名字。

收尾：心法，「**状态对象自己知道去哪、规则就近声明、选择权归客户端是策略归自己是状态**」。

> 面试官追问点：状态模式的类膨胀怎么办？应答思路：简单状态机用「枚举 + switch」或迁移表就够（十二个状态类维护不动是真实痛点）；**状态类值得写的前提是「状态有行为」**——迁移规则之外各状态有独立的副作用逻辑才值得类化；「先表后类、膨胀了再拆」的演进路径比一步到位务实。

#### 3.4 责任链怎么实现？OkHttp和事件分发谁在用

答：一句话定调，**责任链把「一串处理者」串成流水线——每个节点决定「处理、放行、还是短路」；它的两种形态是「递归栈式」（OkHttp，请求下行响应上行）与「序列传递式」（事件分发，消费即终止）**。

**经典结构**：Handler 持 next 引用，处理不了往下传；**每个节点的自由度**是模式的核心——自己决定传不传（短路）、传给谁之前干什么（前后处理）。

**两个工业样本**：
- **OkHttp 拦截器**：chain.proceed 的递归结构——**请求沿栈下行、响应沿栈回溯**，每环在 proceed 前后做对称处理（重试/缓存/连接全在这条链上）；应用拦截器与网络拦截器是「同一机制插在链的不同位置 = 不同观测面」（源码级剖析见 7.3）；
- **Android 事件分发**：dispatchTouchEvent 的递归下行 + **onTouchEvent 返回 true 即消费终止**——「父传子不回头」的序列语义，与 OkHttp 的「对称往返」形成形态对照。

**与 Servlet Filter / Koa 洋葱圈的同构**：doFilter 前后分别是请求与响应处理——**「中间件」这个词的三大生态（Java Filter、Node 洋葱圈、Redux middleware）全是责任链的递归变体**——能跨生态点名同构，说明理解的是模式本身。

**深水区**：**链的两种短路语义**——OkHttp 式「每一环都必然经过」（重试环决定不再 proceed 才短路）vs 事件分发式「被消费就不再往下」（返回 true 截断）；**链的组装时机**——静态配置（Filter 注解扫描）vs 运行时构造（OkHttp 每次 RealCall 现拼），组装时机决定「链能不能按请求定制」。

收尾：心法，「**串起来、各自决定、短路语义认清楚；递归式看 OkHttp、传递式看事件分发**」。

> 面试官追问点：责任链的「链上找不到处理者」怎么办？应答思路：必须有兜底语义——OkHttp 不 proceed 就没有响应（编译器逼不了你、运行时直接断流）；事件分发的终点是 Activity 的 onTouchEvent（没人处理交给最外层）；**「没处理」是 bug 还是被允许的结束态，设计时要显式回答**——这题考的是边界意识。

#### 3.5 算法骨架怎么固定细节？模板方法怎么设计

答：一句话定调，**模板方法用「父类定骨架、子类填空格」——把「不变的流程」焊死在父类，只把「会变的步骤」留成抽象钩子；AQS 是它的工业巅峰**。

**机制**：父类的 final 模板方法按固定顺序调用若干步骤，**步骤分两类**——抽象方法（子类必须实现）与**钩子方法（父类给默认实现，子类按需覆写）**；「**流程控制权在父类**」是与「子类随意组合步骤」的本质差异。

**两个工业样本**：
- **AQS**：acquire 的骨架（tryAcquire → 排队 → 挂起）焊死，**tryAcquire 留白给子类**（ReentrantLock/CountDownLatch/Semaphore 全是「同一个骨架不同的填空」——一套并发骨架养活整个锁家族）；
- **AsyncTask**：onPreExecute → doInBackground（抽象）→ onPostExecute 的骨架固定——钩子的经典滥用反面：钩子太多等于把骨架拆散了。

**深水区**：**模板方法与回调的等价性**——「子类填空」完全可以用「传函数参数」替代（JdbcTemplate 的写法：execute(回调) 替代 extends）——**「继承换组合」的重构方向**在 JDK/框架演进里反复出现（Servlet 的 HttpServlet 保留模板、Spring 全转回调式）；**钩子的纪律**：钩子只该影响「可选步骤」，改「流程结构」的钩子是设计失控的信号。

收尾：心法，「**骨架焊死、步骤留白、钩子管可选不管流程**」。

> 面试官追问点：模板方法为什么被现代框架边缘化？应答思路：继承是它绕不开的税——为了填一个空格继承整个骨架（拿到一堆不想要的公开成员、破坏封装、测试要造子类）；回调/组合（lambda 时代传行为）达到了同样效果且无继承耦合——**「模式的意图不变、实现的语法随语言进化」**，能答出这层是跨时代的语言观。

#### 3.6 迭代器怎么设计？fail-fast是什么

答：一句话定调，**迭代器把「遍历的细节」从容器里拆出来——集合不暴露内部结构也能被遍历；fail-fast 是「遍历中结构被改就立刻翻脸」，fail-safe 是「遍历副本温柔妥协」——一个是防错一个是免责**。

**迭代器的价值**：**统一遍历接口**（ArrayList 与 LinkedList 用同一个 for-each）+ **隐藏内部结构**（调用方不依赖 size+get 也不依赖链表指针）——「**遍历这个动作被抽象成对象**」才有了后面的流式 API（Stream 的 spliterator 是迭代器的性能强化版）。

**fail-fast 的机制**：**modCount 版本号**——结构性修改（add/remove）计数 +1；迭代器创建时快照 expectedModCount，**每次 next 检查不一致立即抛 ConcurrentModificationException**——「**快速失败比悄悄出错好**」的防御哲学（错误暴露在案发现场而不是之后的数据错乱）。

**fail-safe 的机制**：遍历副本或快照（CopyOnWriteArrayList 的写时复制、ConcurrentHashMap 的弱一致迭代器）——**遍历绝不抛异常，但可能读到旧数据**——「**安全语义的两种买法：要么异常的确定性、要么数据的时效性**」。

**深水区**：**fail-fast 不保证并发安全**——它只是「尽力而为的检测」（规范原文：不能依赖它做正确性，它只该用于 debug bug）；**单线程也能触发**（遍历中 remove 触发版本号不一致——正确姿势 iterator.remove() 或 removeIf，它会在迭代器内部同步计数）；**for-each 的语法糖**——编译器把 enhanced for 展开成 iterator 调用，所以「for-each 里 remove 报错」的根源在这。

收尾：心法，「**遍历抽象成对象、fail-fast 是版本号快查、fail-safe 拿时效换确定**」。

> 面试官追问点：为什么 iterator.remove() 就不触发 fail-fast？应答思路：迭代器自己的 remove **在删之前同步了 expectedModCount**（拿锁式更新自己的快照）；集合的 remove 是外部动刀、迭代器的 remove 是内部手术——「同一操作、两个身份、权限不同」，能答出「版本号由谁更新」就答到了根。

#### 3.7 请求怎么封装成对象？命令模式怎么实现

答：一句话定调，**命令模式把「请求」从方法调用升格为对象——方法调用的四个时间自由度（延迟、排队、撤销、记录）全靠这次升格获得；Runnable 是 Java 里最无处不在的命令接口**。

**核心机制**：`Command { void execute(); }`——**调用方与执行方之间插入一个对象层**：发出方只造命令（不必知道谁来执行、怎么执行）、执行方收命令（不必知道谁发的、为什么发）——「**请求的物化**」让「请求」第一次能被存储、传输、比较、撤销。

**四大收益对应四个场景**：
- **延迟执行**：Runnable/线程池任务队列——命令躺在队列里等调度（**线程池的阻塞队列里排的全是命令对象**）；
- **撤销重做**：编辑器的 undo 栈——命令对象存「执行前的现场」，undo 调它的逆向方法（**可撤销命令要成对设计 execute/undo**）；
- **排队与优先级**：调度系统按命令排序（优先级队列里排的是对象不是函数）；
- **审计记录**：命令的执行日志 = 操作历史（重放攻击的放行清单也是命令流）。

**与策略的分野**（深水区）：形似（都是「行为对象化」），**意图不同——策略是「怎么做的选择」（一种做法的替代品），命令是「做这件事的请求」（一次行动的载体）**；判据：对象的生命周期里「执行几次」——策略随叫随到无状态复用，命令常常「一对象一执行」且带现场。

收尾：心法，「**请求升格为对象，换来延迟/排队/撤销/记录四个自由度**」。

> 面试官追问点：函数式接口时代命令模式还有意义吗？应答思路：lambda 让「物化」的样板消失（() -> doThing() 就是一个命令对象），**但模式的价值没消失——撤销要存现场、队列要存优先级、审计要存发起者**，这些「带数据的命令」 lambda 装不下还得类化；「语法糖消灭样板、消灭不了语义」。

#### 3.8 状态怎么保存和恢复？备忘录模式怎么实现

答：一句话定调，**备忘录把「状态的快照」从对象身上拆出来存——关键约束是「对象自己能存取、外人不可见」（宽接口与窄接口的分离）；onSaveInstanceState 是 Android 里的工业实现**。

**三角色**：Originator（被存档者——创建/恢复快照）、Memento（快照载体——**对 Originator 宽、对 Caretaker 窄**）、Caretaker（存档管理者——**只传不读**）——「**存档的内容对管理者黑盒**」是封装的纪律：管理者不该知道存了什么字段。

**两个工业样本**：
- **编辑器撤销**：每次操作前存快照入栈，undo 弹栈恢复——**快照粒度的权衡**：全量快照（简单但内存贵）vs 增量快照（只存 diff、恢复时要回放）——与数据库 WAL、虚拟 DOM diff 的取舍同源；
- **Activity 的 onSaveInstanceState**：系统在「可能被回收」时来收快照（Bundle 传给你自己填、系统只负责存和还）——**Bundle 是天然的 Memento：进程外可序列化、对系统黑盒**；恢复双通道（onCreate 的 savedInstanceState 与 onRestoreInstanceState）见 Android 篇 1.1.2。

**深水区**：**快照的不可变性**——Memento 应当不可变（存档被改等于历史被篡改）；**备忘录与原型（1.6）的形似**——都「造对象的副本」，分野在目的：原型为了「以旧造新」（副本是新产品），备忘录为了「回到过去」（副本是存档）；**大对象的快照成本**——频繁全量快照是内存刺客（编辑器每次击键存整个文档 → 存 diff 或分片）。

收尾：心法，「**快照外移、管理者黑盒、粒度按成本权衡**」。

> 面试官追问点：为什么 Memento 强调「Caretaker 不能读内容」？应答思路：管理者一旦能读快照，就会产生依赖（按字段做逻辑、改字段做 hack）——**封装被打破后 Originator 的演化自由就没了**（加个字段忘了同步管理者的 hack 就是 bug）；「窄接口」是拿访问控制换演化自由，和「依赖即文档」（1.4）是同一价值观。

#### 3.9 网状依赖怎么变成星型依赖？中介者怎么用

答：一句话定调，**中介者把「N×N 的网状交互」收编成「N×2 的星型」——所有对象只认识中介、由它转发协调；收益是解耦、代价是中介自己长成新上帝，MVC 里的 Controller 就是它**。

**机制**：Colleague 只持 Mediator 引用、交互全部发给它；Mediator 持所有 Colleague、按事件路由——**「谁和谁说话」的知识从每个对象身上集中到一处**。

**三个样本**：
- **聊天室**：用户只发消息给服务器、服务器路由给目标——**中介天然是「中心化架构」的模式化身**（消息队列、网关、调度中心全是它的工业放大）；
- **MVC 的 Controller**：View 与 Model 不直接说话、Controller 居中协调——「**C 的本职就是中介**」（MVC 变体之争本质是「中介的权限边界」之争）；
- **机场调度塔台**：飞机不互相协商跑道、全部听塔台——**「多方协议」场景没有中介就是死锁现场**。

**深水区**：**中介者的上帝化**——路由逻辑全堆在 Mediator 里，它自己变成千行大杂烩——治理三招：**按业务域拆多个中介**（事件总线按 topic 分发）、路由规则外置（配置/注册表）、中介只转发不做业务；**与观察者（3.1）的组合**——中介内部常拿事件广播实现路由（EventBus 本质是「无路由逻辑的中介者」：把协调简化成纯转发）——「**中介决定谁收到、观察者广播给所有订阅者**」。

收尾：心法，「**网变星、知识集中、警惕中介上帝化**」。

> 面试官追问点：中介者和门面（2.5）都「居中协调」，差在哪？应答思路：门面是**单向简化**（外面进来的调用被简化，子系统不认识门面）；中介是**双向协调**（Colleague 们互相认识它、它认识所有 Colleague，交互在它体内流转）——**「入口的窄门」与「枢纽的路由」**；答出「子系统/同事对象是否反向持有它」这条判据就精确了。

#### 3.10 访问者解决什么问题？双分派为什么不常用

答：一句话定调，**访问者解决「结构稳定、操作易变」时的新增问题——在不改元素类的前提下挂新操作；双分派是它的机制核心；它不常用是因为押错了前提：现实里结构比操作更容易变**。

**它解决的问题**：元素家族（Circle/Square）稳定、**操作频繁加**（导出 XML、渲染、压缩...）——普通做法每个操作都是「给每个元素加方法」（结构改动、全家族体检）；访问者把**操作做成对象、元素只留一个 accept 方法**——**新操作 = 新 Visitor 类，元素零改动**——**双分派**：`element.accept(visitor)` → 元素回调 `visitor.visit(this)`——**第一次分派按元素类型进入 accept、第二次按元素真实类型进入 visit 的重载**——两个维度的类型才被同时展开成方法表。

**为什么极少用**（模式的自我背叛在深水区）：它的开闭只押「操作变」——**结构一变（加新元素类型），所有 Visitor 全部要改**（每个访问者都要补 visit(新元素)）；**现实多数系统「结构比操作爱变」**，与访问者的前提正好相反；加上双分派的绕（编译器重载解析的坑：visit(this) 按静态类型匹配）、性能与可读性税——**「能用的前提是元素家族真的稳定」**（编译器 AST、文档模型这类「结构几十年不变」的领域才是它的主场——javac 的树遍历、DOM 的序列化）。

收尾：心法，「**结构稳操作变才值得用、双分派是机制核心、押错前提就是负资产**」。

> 面试官追问点：既然不常用为什么还考？应答思路：它是**唯一把「双分派」讲清楚的载体**——理解它等于理解「重载是编译期、覆写是运行期」的分派全景（instanceof 链的穷举为什么是反模式、多态的正确打开方式）；**考的不是你会不会用，是你懂不懂类型分派的底层**——能答出这层，说明你看穿了面试题的出题意图。

# 4.易混模式对比（高频考点）

#### 4.1 观察者与发布订阅的区别？事件中心的存在

答：必问题。一句话定调，**两者差在「有没有中间人」——观察者是双方直接握手（Subject 持有 Observer 列表），发布订阅隔了个事件中心（双方向中介注册、互相不认识）——解耦升级的代价是追踪链路断裂**。

**结构对照**：观察者——`Subject { List<Observer> }`，attach/detach/notify 全在主体身上，**双方知道彼此的类型**；发布订阅——Publisher 只管往事件中心发「topic + payload」，Subscriber 按 topic 订阅——**依赖从「对象引用」降级成「字符串约定」**。

**解耦的两面**（深水区一）：收益——发布方不用关心「谁在听、有几个在听」（换订阅者零改动）；代价——**「谁订阅了这个事件」要翻注册表才知道**（IDE 找不到调用链）、**事件风暴**（几十种事件互相触发，数据流变成蜘蛛网）——**解耦买的是「修改自由」，付的是「理解成本」**。

**工程补丁史**（深水区二）：**LiveData 用生命周期绑定给观察者打补丁**（防泄漏注册）、**RxJava 用 Disposable 链管订阅生命周期**（防忘退订）、**类型化事件**（用枚举/类替代字符串 topic 换回编译期检查）——「**每代框架都是在给上一代的解耦代价打补丁**」。

收尾：心法，「**差在中间人、买修改自由付理解成本、补丁都在管订阅的生命周期**」。

> 面试官追问点：EventBus 属于哪个？应答思路：它是发布订阅（全局事件中心），但**订阅粒度是方法级**（register 整个对象、反射找 @Subscribe）——比经典发布订阅更松也更难追踪，所以组件化时代被「有宿主的事件」（LiveData/SharedFlow 的作用域收口）替代——能结合演进答而不是背定义就到位。

#### 4.2 装饰器和代理怎么区分？代码结构几乎一样

答：一句话定调，**两者的代码结构完全同构（同接口 + 包一个实例 + 转发加料），区分它们的不是代码是意图——装饰器回答「如何增强」、代理回答「如何控制」；判据一句话：你知道你在用装饰器，你不知道你在用代理**。

**同构先摆出来**：两者都是「实现同接口、内部持一个同接口实例、方法转发前后加料」——**看类图永远分不出来**。

**分野在「包装的发生学」**（深水区一）：**装饰器由调用方显式组装**——`new Buffered(new FileInputStream(f))`，「我要增强」是使用者的决定，可任意层堆叠；**代理由框架在边界处生成**——Spring 在 Bean 初始化后包一层，「被代理」对调用方透明（你注入的本来就是代理）——「**组装权在谁手里，模式就姓什么**」。

**意图的三个推论**：装饰器**同层可叠加**（Buffered + Data 双装饰很正常）、代理通常单层（包两层代理是设计问题）；装饰器**只加功能不改语义**（转发必达目标）、代理可以**拒绝转发**（权限不够、连接失败——控制权包括说不）；装饰器与目标**同生命周期视角**、代理常常**管理目标的生命周期**（虚代理按需创建）。

收尾：心法，「**同构不同意图、组装权定姓氏、代理有权说不**」；源码级的同构对照与「OkHttp Interceptor 是两者混血」见 7.8 深度精讲。

> 面试官追问点：既然结构一样，为什么 GoF 要拆成两个模式？应答思路：模式是「意图的词汇表」不是「结构的分类学」——拆开是为了让名字携带动机（说「我用代理」就传达了「控制访问」的意图）——**「模式是给人读的设计语言」**，能答出这层说明理解了模式的本质是沟通。

#### 4.3 策略与状态的本质差异？切换的主体是谁

答：一句话定调，**两者结构同构（Context 持一个可替换的行为对象），分野只在「选择权」——客户端每次显式选是策略、对象内部自动流转是状态；这一条判据延伸出「持不持 Context 引用」的第二个差异**。

**结构对照**：Context 持 Strategy 引用、委托调用；Context 持 State 引用、委托调用——**UML 上是同一个图**。

**三个差异连坐**：
1. **选择权**：策略——「这次用支付宝」是用户/调用方每次决定的；状态——「订单从待支付到已支付」是状态机自己推进的（外部只触发事件不指定次态）；
2. **Context 引用**：策略通常不持（拿了就是越权——策略不该知道调用它的上下文）；**状态类通常持 Context**（要发起迁移必须能回调它）——这一条是看代码就能认出的硬判据；
3. **生命周期**：策略对象**无状态可复用**（单例策略很常见）；**状态对象常带迁移知识**（知道下一个状态是谁，要么持要么查表）。

**深水区**：两者可以组合——**状态机里「每个状态的具体行为」内部用策略**（状态的 pay 逻辑委托给注入的支付策略）；「**状态决定在哪干、策略决定怎么干**」的分工模式在订单/工作流系统里很常见——能讲出组合场景说明不是背对比表。

收尾：心法，「**选择权归属是主判据、Context 引用是硬判据、两者可组合不是互斥**」。

> 面试官追问点：既然状态自动流转，「客户端误触发非法迁移」怎么防？应答思路：迁移合法性内建于状态类——已支付状态的 pay() 直接拒绝/抛异常（非法迁移在源头被拦）；表驱动方案则在校验层拦（事件×状态查表不通过即拒）——**「规则就近声明」的防错价值在这题兑现**，与 3.3 的建模呼应。

#### 4.4 模板方法与策略怎么区分？组合优于继承

答：一句话定调，**两者都在「固定流程中替换可变部分」，机制正交——模板靠继承（子类填空格，流程焊死在父类）、策略靠组合（注入行为对象，流程写在 Context 里）；「组合优于继承」的时代，模板正在被回调式重写**。

**机制对照**：模板方法——父类 final 方法定骨架、子类覆写钩子（**流程与填充点绑在继承链上**）；策略——Context 按固定顺序调用注入的策略（**流程在组合方、策略只是无状态算法**）。

**三个实战差异**：
1. **可变粒度**：模板的子类能感知「整个流程」（能看到第几步、前后有什么）；**策略对流程一无所知**（只被叫了一声 run）——「要感知流程的位置用模板、纯算法替换用策略」；
2. **复用性**：策略对象无状态可全局复用（一个 Comparator 服务全项目）；模板的子类与父类绑死（每个使用场景一个子类）；
3. **运行期替换**：策略可随时换（setStrategy），**模板的实现在编译期就焊死了**。

**深水区**：**演进证据链**——JdbcTemplate 把「模板方法继承」重写成「execute(回调) 组合」、Servlet 的 HttpServlet 保留模板而 Spring MVC 全转回调——**「lambda 让『传行为』的成本降到零」**（3.5 深水区的展开）；**但模板没死**：AQS 这类「骨架本身复杂、子类只填一两个点」的场景，继承的强约束反而是资产（把你按在正确的轨道上填空）。

收尾：心法，「**继承填空 vs 组合注入、感知流程 vs 纯算法、按可变粒度选**」。

> 面试官追问点：什么时候「明知组合更好」还选模板方法？应答思路：三个信号——骨架复杂且不允许子类改流程顺序（并发框架：步骤顺序错了是死锁，**强约束是安全资产**）；扩展点是「受保护的协作」（子类要访问父类的受保护状态）；扩展点数量少且稳定——**「约束的价值超过灵活性」的场景，继承的缺点反而是优点**。

# 5.设计原则与思想

#### 5.1 UML六种关系怎么理解？组合聚合差在哪

答：一句话定调，**六种关系按「强度与语义」排成光谱——依赖（用一下）→ 关联（长期持有）→ 聚合（拥有但可分家）→ 组合（拥有且共生死）→ 泛化（is-a）→ 实现（can-do）；组合与聚合的分界线只有一条：生命周期是否绑定**。

**光谱逐个过**：
- **依赖**：方法参数/局部变量——「用一下就走」（UML 虚线箭头）；
- **关联**：成员字段——「长期知道你」（导航方向有单向双向）；
- **聚合**：字段持有但**各自独立生死**——车队与车（车队散了车还在）——「整体-部分，但可拆」；
- **组合**：字段持有且**部分随整体生死**——人与心脏（人没了心脏不独立活）——「**生命周期绑定是唯一硬判据**」，代码上常表现为「部分在整体的构造器里创建、在整体的销毁里释放」；
- **泛化/实现**：is-a 与 can-do（继承与接口）。

**代码层面的体现**（深水区一）：聚合与组合**在字段声明上长得一模一样**（`private Car car;`）——**区分在「谁创建谁」**：组合是整体自己 new（构造器里创建、随整体释放），聚合是外部传进来 set（注入的、生命周期归别人）——**「创建权归属」是代码里真正可操作的判据**，比「业务上像不像车队」可靠得多。

**为什么面试爱考**（深水区二）：**聚合/组合的选择 = 谁管生命周期的决策**——Spring 世界里全是聚合（容器管生命周期，业务类只持有引用）；UI 世界里全是组合（ViewGroup 创建并销毁 child）——**能说清「我项目里哪个是聚合哪个是组合、为什么」**，比背六个定义值钱。

收尾：心法，「**光谱按强度排、生死绑定是组合判据、创建权归属是代码抓手**」。

> 面试官追问点：既然聚合组合代码一样，为什么 UML 还要区分？应答思路：UML 表达的是「设计意图」（这个关系是不是共生死），给读者传递生命周期约定——**「代码表达机制、模型表达意图」**；阅读者看见组合就知道「删整体时要考虑部分」，这是纯代码读不出来的信息。

#### 5.2 过度设计怎么判断？什么时候不该用模式

答：一句话定调，**过度设计的定义是「为不会发生的变化支付了灵活性税」——判据不是模式用了几个，而是「押注的变化方向对不对」；唯一可靠的判断输入是变化的历史频率，不是对未来的想象**。

**过度设计的三个面孔**：
1. **为想象中的扩展留口子**——「以后可能会有十种支付方式」（实际三年就两种）→ 一堆接口 + 工厂 + 注册表，每次改需求要在五层文件里跳；
2. **用错方向的灵活性**——押注「操作会变」上了访问者（3.10），结果变的是结构——灵活性本身成了负债；
3. **模式表演**——四行代码的 Builder、两个实现加 SPI 机制——模式的复杂度成了简历驱动开发的证据。

**判断的三个输入**：
- **变化的历史**：这块代码过去改了几次、每次改的是什么维度——**「过去沿一个维度反复变的，未来大概率继续变」**，没变过的维度押注要谨慎；
- **变化的成本对称性**：**「先简单实现 + 变了再重构」的成本**，常常低于「预付全套灵活性」——重构工具（IDE 自动化、测试覆盖）让「等变化来了再动手」越来越便宜；
- **团队的理解成本**：模式对新手是智力税——**「读不懂的灵活」等于没有灵活**。

**深水区**：**「害怕重构」才是过度设计的心理根源**——因为不敢动老代码所以想一次设计到位；正确姿势是**「用测试覆盖买重构自由」**：有了测试网，简单实现随时可以演化成模式——**「模式应该是长出来的，不是画出来的」**。

收尾：心法，「**押注变化的历史频率、重构成本对称性、模式是长出来的**」。

> 面试官追问点：「YAGNI」和「开闭原则」矛盾吗？应答思路：不矛盾——开闭说「不要改已稳定的代码，用扩展承接变化」；YAGNI 说「没出现的变化别预付」——**统一在「按真实变化行动」**：已发生的变化用开闭承接、未发生的变化用 YAGNI 拦截——两条原则是同一枚硬币的两面，能统一它们说明不是背教条。

#### 5.3 高内聚低耦合怎么理解？落地手段有哪些

答：一句话定调，**内聚是「一个模块只操心一件事」、耦合是「改动一个模块要连带知道多少别处」——它们是同一枚硬币的两面；落地三板斧是职责划分、接口抽象、依赖倒置**。

**两个概念的操作化定义**（不要背形容词，要能测量）：
- **内聚的可测量判据**：改一个「业务理由」要动几个模块——只动一个就是高内聚（「这个类的存在理由能一句话说清吗」是自检问题）；
- **耦合的可测量判据**：改 A 模块时，需要「知道/通知/同步修改」的模块数——**耦合度 = 修改的传播半径**。

**落地三板斧**：
1. **职责划分**：按「变化的理由」切模块（不是按技术层切）——**「会因为同一原因变化的放一起，不会的分开」**（这既是内聚的定义也是切分的方法）；
2. **接口抽象**：模块间只通过窄接口说话——**耦合面收窄到接口签名**（内部实现随便重构，2.5 门面的价值之一）；
3. **依赖倒置**：**细节依赖抽象、抽象不依赖细节**——高层与低层都指向中间的接口层（5.4 展开），「谁实现谁」变成配置问题。

**深水区**：**耦合的隐性形态**——时间耦合（A 必须先于 B 调用）、数据耦合（共享一个可变对象）、语义耦合（A 的行为依赖 B 的某个文档约定）——**语义耦合是重构时最炸的一种**（「我以为这个字段不会是 null」）；**低耦合的正确姿势是「控制耦合的方向和宽度」，不是消灭耦合**（零耦合的系统是不存在的，调用本身就是耦合）。

收尾：心法，「**内聚看存在理由、耦合看修改半径、三板斧按顺序上**」。

> 面试官追问点：「数据驱动」算不算低内聚？应答思路：看数据的解释权归谁——解释权集中在少数模块（引擎读 schema 渲染）是高内聚（「配置的多样性」和「逻辑的稳定性」分离）；解释权散落各处（到处 if-else 解析同一个字段）是低内聚——**内聚的单位是「解释权」不是「代码位置」**，这个视角能分辨大多数「看起来分散其实内聚」的设计。

#### 5.4 六大设计原则的含义？代码层面怎么体现

答：一句话定调，**六大原则是「面向对象设计的可操作清单」——单一职责管「拆多细」、开闭管「怎么接变化」、里氏管「继承的纪律」、接口隔离管「接口多窄」、依赖倒置管「箭头指向谁」、迪米特管「知道多少」；前五条服务一个目标：可维护性**。

**逐条带代码判据**：
- **单一职责（SRP）**：「变化的理由只有一个」——判据：**类的公开方法能不能分成互相无关的几组**（能分就该拆）；
- **开闭（OCP）**：**对扩展开放、对修改关闭**——判据：加新行为时「加新代码」还是「改老代码」（3.2 的注册表重构是标准落地）；
- **里氏替换（LSP）**：**子类必须能无感替换父类**——判据：子类有没有「加强前置条件、削弱后置条件、抛父类不抛的异常」——经典反面：**父类说「不会返回 null」，子类偶尔返回**（Stack extends Vector 的历史事故：栈语义被序列化方法破坏）；
- **接口隔离（ISP）**：**实现方不该被迫实现用不到的方法**——判据：接口的方法数与实现类的「空实现」数量（一堆空实现 = 接口该拆）；
- **依赖倒置（DIP）**：**高层低层都依赖抽象**——判据：业务代码 import 的是具体类还是接口（MVP 的 Presenter 依赖 IView 接口、Spring 的构造注入都是落地）；
- **迪米特（LoD）**：**只和直接朋友说话**——判据：链式调用深挖 `a.getB().getC().getD()`（对 C/D 的依赖是隐性的——改 C 的接口会炸到这行）。

**深水区一**：**LSP 是继承的使用说明书**——违反 LSP 的继承是「白捡代码」的幻觉（父类的所有约定都要遵守，「继承是契约不是复制」）；**深水区二**：**迪米特与 fluent API 的冲突**——Stream 链 `list.stream().filter().map()` 连环点号却不算违规（**每个返回的都是「正在进行的表达」而非内部结构**）——「判据是点的后面是不是内部零件」，能分清说明懂的是精神不是条文。

收尾：心法，「**六条各管一件事、判据都在代码里能指出来、全为可维护性服务**」。

> 面试官追问点：六大原则有优先级冲突怎么办？应答思路：真实冲突常在「单一职责 vs 接口数量」（拆细了接口爆炸）——解法不是二选一而是**按「变化的维度」重新切**（按业务理由拆的职责自然对齐未来的变化）；原则是工具不是法律，**「服务可维护性」是最终裁决标准**——能举一个自己项目里原则打架的案例就是满分答案。

#### 5.5 设计模式的本质三句话是什么？怎么识别

答：一句话定调，**三句话——面向接口编程（依赖的方向）、组合优于继承（复用的方式）、封装变化（修改的隔离）；识别模式的过程就是「先找到『什么在变、什么不变』再对号入座」**。

**三句话各自统领什么**：
- **面向接口编程**：所有结构型模式的地基（装饰器/代理/桥接/适配器全是「围绕接口做文章」）——依赖指向抽象，实现可换；
- **组合优于继承**：装饰器对继承的替代（2.2）、策略对模板的替代（4.4）、桥接对继承膨胀的手术（2.7）——**「用『持有 + 委托』替代『is-a』」**；
- **封装变化**：策略封装「算法变」、状态封装「状态变」、观察者封装「观察者变」、工厂封装「产品变」——**每个模式名后面都藏着一个「变化的名字」**。

**识别的实操路径**（面试官问「你项目里用了什么模式」时的正确打开方式）：
1. **先说变化**：这块需求里「什么是稳定的、什么反复在变」（支付渠道变、UI 不变）；
2. **再说模式**：所以用策略 + 注册表把变化隔离在……
3. **最后说代价**：付出的成本是类数量、换来的是新增渠道零改动——**「变化 → 模式 → 账单」的三段式**比背模式名高一个量级。

**深水区**：**三句话的统一性**——它们都是「依赖管理」：接口编程管依赖的方向、组合管依赖的方式、封装变化管依赖的隔离——**设计模式的本质是「一门关于依赖的学问」**（依赖往哪指、怎么指、怎么隔离），能讲到这层就把 23 个模式收进了一个框架。

收尾：心法，「**方向、方式、隔离三个词收编全部模式；识别题按『变化→模式→账单』作答**」。

> 面试官追问点：GoF 23 个模式要全背吗？应答思路：高频的十个（单例/工厂/建造者/适配器/装饰器/代理/外观/观察者/策略/责任链）覆盖 90% 的实战与面试；**模式的价值排序由你的业务决定**（做中间件的看责任链、做业务的看策略观察者）——「**按变化类型建索引，不按 GoF 的目录背**」是过来人答案。

#### 5.6 设计原则的三道代码题？怎么拆类扩展

答：一句话定调，**三道代码题考的都是「同一件事的两面」——拆（单一职责）与扩（开闭）；答题模板是「先诊断违规点 → 给重构方案 → 报开闭收益」**。

**第一道：违反单一职责的类怎么拆**——诊断：一个类里「用户校验 + 数据库存取 + 短信通知」三个变化理由（任何一处业务规则变都要动这个类、测试要连数据库）；重构：按变化理由拆三件（Validator/Repository/Notifier），**用门面或编排服务串起来**（拆完调用方不能跟着遭殃）——**拆类的同时要保持对外接口稳定，这是「拆」的纪律**。

**第二道：开闭原则给结算系统加支付方式**——诊断：`pay(channel)` 里的 if-else 每加渠道全改（3.2 的同款病灶）；重构：PayChannel 接口 + 注册表路由 + Spring 注入自动收集——**报收益：「新渠道 = 新增一个类 + 零行老代码修改」**——这道题实际就是 3.2/7.9 的现场版，答题时直接复用那套「接口 + 注册表 + 兜底异常」三步。

**第三道：依赖倒置在 MVP/MVVM 中的体现**——诊断：View 直接 new Presenter（实现类写死）的问题（换实现要改 View、Presenter 没法脱离 UI 测试）；重构：**View 依赖 IPresenter 接口、Presenter 依赖 IView 接口**——两个具体类互不 import，依赖箭头全部指向抽象——**「接变化的接口方向」在这题可视化出来**（MVVM 的 ViewModel 暴露 LiveData/StateFlow 也是同一原则：View 依赖的是「可观察的数据契约」不是 ViewModel 的具体类型）。

**深水区**：三道题的共同陷阱——**「拆/扩之后的胶水层」才是丢分点**：拆了类谁负责编排（编排服务/门面）、注册表的兜底异常、接口粒度会不会又违反接口隔离——**原则题的满分线在「重构后的完整性」不在「原则名词」**。

收尾：心法，「**拆类保接口稳定、扩展走注册表、箭头指向抽象；胶水层是丢分点**」。

> 面试官追问点：拆类之后「谁来编排」为什么重要？应答思路：拆出去的职责要有重新汇合的地方（否则调用方要自己按顺序调三家）——编排层集中「流程知识」，这正是模板方法/门面/中介者的用武之地；**「拆与合是成对动作」**，只答拆不答合，方案在生产环境就是半成品。

# 6.框架中的模式辨认与手写题

#### 6.1 四道高频手写题？DCL和EventBus怎么写

答：一句话定调，**手写题的判卷标准不是「能跑」是「并发语义与边界处理」——DCL 考 volatile 的必要性、EventBus 考注册表与线程模型、敏感词链考短路语义；每题背「一个骨架 + 一个失分点」**。

**手写 DCL 单例**：骨架——双重判空夹锁 + volatile；**失分点是答不出「为什么 volatile」**（new 的三步重排 → 半初始化对象逃逸——1.1 的推演要能现场讲）；加分动作：主动提「更稳的写法是静态内部类或枚举」——**「写 DCL 但知道它不是最优」是资深信号**。

**手写策略+工厂重构 if-else**：骨架——策略接口 + Map 注册表 + 兜底异常（7.9 的三步）；失分点——**注册表没人填**（忘了构造时收集实现）或兜底直接返回 null（业务异常和 bug 的边界不区分，7.9 追问点的现场版）。

**手写简化 EventBus**：骨架——`Map<Class<?>, List<Subscription>>` 两级结构（**按事件类型分桶是 O(1) 派发的关键**）+ post 按类型查桶遍历回调；**失分点**——unregister 的移除语义（遍历中删除的 ConcurrentModificationException，3.6 的现场版）、线程模型缺失（「回调跑在 post 的线程」要不要切，至少要能指出这是个设计决策）。

**手写责任链敏感词过滤**：骨架——Handler 持 next + setNext 的流式组装 + 每环处理不了的传下去；**失分点**——「处理了但不截断」与「处理且截断」的语义没区分（敏感词过滤要「替换后继续传」而不是短路——**链的语义由业务定，不是照抄 OkHttp**）。

收尾：口述策略——**每题动手前先讲「我的数据结构是什么、语义边界在哪」**，「先报结构」就是加分项（11.1 手写题同款心法）。

> 面试官追问点：手写 EventBus 为什么要两级 Map 而不是一个 List？应答思路：一级结构 post 时要**遍历全表逐个 instanceof**（O(n) 且类型判断散落）；两级按类型分桶后查桶直取（O(1)）——**「索引结构服务于查询模式」**，这题实际是在考你「注册表」这个词的含金量。

#### 6.2 主流框架用了什么模式？辨认清单是什么

答：一句话定调，**辨认框架的模式不是报菜名，是「说出模式解决了这个框架的什么问题」——一张清单按「框架 → 模式 → 买单的变化」组织，面试才有说服力**。

**五框架的辨认清单**（每条带「解决的问题」）：
- **OkHttp**：**责任链**（拦截器链——「请求处理步骤易变」：重试/缓存/连接按需插拔）+ **建造者**（Builder——参数多且可选）+ **外观**（OkHttpClient 收敛配置入口）——深讲见 7.3；
- **Retrofit**：**动态代理**（接口无实现类的「声明式 API」——「把注解翻译成请求」）+ **建造者** + **适配器**（CallAdapter 把 Call 适配成 Observable/suspend——「返回类型的适配」）；
- **Glide**：**享元/池化**（BitmapPool——「高频分配的 GC 成本」，7.10）+ **责任链**（解码器的职责传递）+ **外观**（with().load().into() 三连）；
- **Spring AOP**：**代理**（运行时织入）+ **责任链**（拦截器链执行）+ **策略**（JDK/CGLIB 的代理选择）+ **模板方法**（BeanPostProcessor 扩展点）——**一个功能串四模式**，辨认题最好用的样本，深讲见 7.5；
- **Handler 体系**：**生产者-消费者**（消息队列）+ **享元**（Message 池）+ **观察者变体**（回调的注册分发）——与 Android 篇 13.1 串讲。

**答题的降维结构**：面试官问「你项目里用了什么模式」——按 **「变化 → 模式 → 账单」** 三段式答（5.5 的模板）：「支付渠道反复加（变化），用策略 + 注册表隔离（模式），代价是类数量、换来新增零改动（账单）」——**比报十个模式名可信一个量级**。

**深水区**：**框架的模式是「长出来的」**——OkHttp 的责任链最初不是照 GoF 画的，是「重试/缓存逻辑解耦」的工程需求长成了这个形状；**辨认的最高境界是反推**：看到一个设计先猜「它隔离了什么变化」，再对照源码验证——这个能力直接迁移到自己项目的架构评审。

收尾：心法，「**辨认按『框架→模式→买单的变化』答、项目题按『变化→模式→账单』答、最高境界是反推**」。

> 面试官追问点：为什么框架都长得像（责任链+建造者+外观三件套）？应答思路：因为它们面对同构的问题——「处理步骤要可插拔」（责任链）、「配置项多且可选」（建造者）、「子系统复杂要窄门」（外观）是所有框架的公共痛点；**模式的集中出现是「问题同构」的证据**——能答出「框架相似是因为痛点相似」就把辨认题答成了架构题。

# 7.深度精讲（框架源码中的模式口述版）

> 说明：本章是核心题的口述版深度精讲，讲到框架源码与模式实现细节层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

#### 7.1 单例的五种实现怎么对比？破坏防线怎么建

答：一句话定调，**五种实现的优劣全在「懒加载、线程安全、防破坏」三个维度，枚举是唯一三项全满的答案**。

**五种按三个维度打分**：

1. **饿汉式**：类加载即实例化——线程安全（类初始化锁天然保证），**不懒**（不管用不用都占内存），反射可破（构造器 setAccessible 后 new）；
2. **懒汉式加方法锁**：懒了也安全，**但每次 getInstance 都抢锁**，性能灾难；
3. **DCL 双重检查**：懒且只在首次竞争——**第一重判空挡住后续的锁开销，第二重判空挡住「等锁期间别人已初始化」**；**volatile 是命门**：防止 new 的「分配-初始化-赋值」重排导致别的线程拿到半初始化对象（细节在 Java 篇 8.3 的字节码分析）；
4. **静态内部类**：**JVM 的类初始化锁做同步**——内部类首次被引用才加载（懒），`<clinit>` 由 JVM 保证线程安全（安全），**代码里一行锁都没有**，是「白嫖 JVM 机制」的优雅解；
5. **枚举**：**JVM 层面保证实例唯一**——`values()` 反射创建枚举会直接被 Constructor.newInstance 拒绝（Enum 检查），**反序列化走 readResolve 也返回既有实例**，三防全满。

**深水区一：反射破坏的攻防**——普通单例防反射的手段是**私有构造器里加「已存在即抛异常」**，但攻击者可以先 setAccessible 再用反射把 instance 字段置 null 绕过；**防反序列化**要实现 readResolve（ObjectInputStream 读到该方法就用其返回值替代反序列化产物）。**只有枚举在 JVM 层面免疫两者**——《Effective Java》推枚举单例的底层依据。

**深水区二：线程安全的真源**——DCL 的安全靠 volatile + 锁，静态内部类的安全靠 **`<clinit>` 的隐式锁**（JVM 规范：类的初始化由拿到初始化锁的线程执行，其他线程阻塞等待——和 03 篇 11.10 的 Meyers 单例是同一机制的 Java 版）。**三种同步来源（显式锁、类初始化锁、枚举的 JVM 特殊化）逐级「从手写到白嫖」**，能讲出这条演进线就是深水区。

收尾：单例的答题心法，「**要懒就 DCL 或内部类，要绝对防御就枚举，要简单就饿汉**」，并主动讲出每种「线程安全的来源」，是这题从模板到理解的分界。

> 面试官追问点：为什么构造器抛异常防不住反射？应答思路：反射先 setAccessible(true) 已越过 private 检查，攻击者还能用反射修改静态 instance 字段绕过存在性检查；只有「让构造第二次必然失败」（如在枚举里 JVM 直接拒绝）才防得住。

#### 7.2 JDK和CGLIB怎么实现代理？差异在哪

答：一句话定调，**JDK 代理靠「运行时实现接口」生成子类（Proxy + InvocationHandler），CGLIB 靠「运行时继承目标类」生成子类（ASM 字节码 + MethodInterceptor），「只能代理接口」的限制来自「Java 单继承 + 代理类已继承了 Proxy」**。

**JDK 动态代理的三件套**：

1. **Proxy.newProxyInstance** 生成的代理类**继承 java.lang.reflect.Proxy 并实现业务接口**——**这就是只能代理接口的根因：单继承的名额被 Proxy 占了**，没有第二个名额去继承目标类；
2. 代理类的每个方法体都是「**把 Method 对象和参数打包，转发给 InvocationHandler.invoke**」——所以调用端 `proxy.foo()` 实际进的是 handler；
3. **invoke 的第一个参数 proxy 是代理对象自己**，在里面调 method.invoke(proxy) 会无限递归（handler 转代理、代理转 handler）——**经典笔试点：要调目标必须持有 target 引用自己传**。

**CGLIB 的路线**：用 **ASM 直接写字节码**，生成「目标类的子类」——**重写非 final 的 public/protected 方法，方法体拦截进 MethodInterceptor.intercept**，**super.xxx() 是真实调用的通道**（intercept 里手动调 MethodProxy.invokeSuper）。**限制也来自继承**：final 类/方法不能代理（没有子类可造），private 方法天然不可见。

**深水区一：两者的真实性能与选择**——历史结论（反射调用慢）**在现代 JVM 已翻案**：JDK 8+ 的 Method.invoke 走 method handle 的 intrinsic 优化后，**JDK 代理的调用开销与 CGLIB 相当**（CGLIB 的 FastClass 机制——**为每个方法生成 int 索引避免反射查方法**——在 JDK 优化后优势消失）；**Spring 的默认策略**：目标有接口默认 JDK、无接口自动 CGLIB（Spring Boot 2 起默认全 CGLIB，**为避免「注入具体类型失败」的接口/类代理不一致坑**）。

**深水区二：代理的「自调用失效」问题**——**目标类内部 this.methodB() 不走代理**（this 是裸对象不是代理），**AOP 的 @Transactional 方法互调失效是同一根因**；解法：AopContext.currentProxy() 拿代理再调、或自注入。**这是「动态代理增强的是外部调用面」这个本质的推论**，能讲出事务失效案例就落地了。

收尾：动态代理的心智模型，「**编译期没有这个类，运行时造一个『转发器』**」，JDK 转发给接口、CGLIB 转发给父类方法，**选择不是性能问题而是「目标有没有接口、能不能继承」的适配问题**。

> 面试官追问点：为什么 MyBatis 的 Mapper 接口没有实现类也能被注入？应答思路：JDK 代理不需要实现类——MapperProxy 实现 InvocationHandler，invoke 里按「接口全名+方法名」找到 SQL 执行，**代理对象本身就是那个「实现」**，这是动态代理「无中生有实现接口」能力的极致应用。

#### 7.3 OkHttp的责任链怎么递归？源码怎么读

答：一句话定调，**OkHttp 的拦截器是「责任链的递归变体」：RealInterceptorChain 携带 index 递归调用下一环，请求下行、响应上行，「应用拦截器和网络拦截器看到的是链的不同横截面」**。

**核心源码只有二十行**（能背出主干就是读过源码）：`RealCall.execute` 构造 `List<Interceptor>`（用户的应用拦截器 + RetryAndFollowUp + Bridge + Cache + Connect + 网络拦截器位置 + CallServer），`chain.proceed(request)` 的实现是「**取出 index 拦截器、new 一个 index+1 的新 Chain、调 interceptor.intercept(newChain)**」——**递归而不是循环**，每一环的 intercept 内部自己决定调不调 proceed（不调就短路，链在它这里终止）。

**五个内置拦截器的分工**（按链序）：

1. **RetryAndFollowUp**：重试与重定向（proceed 包在循环里，失败按策略重试、3xx 跟随 Location）；
2. **BridgeInterceptor**：补全协议头（Content-Length、Cookie、gzip），**「应用层报文变网络层报文」的翻译官**；
3. **CacheInterceptor**：**条件请求的实现者**——缓存有 ETag/Last-Modified 就加 If-None-Match/If-Modified-Since 发出去，304 就用缓存体（网络往返 1 次但省传输）；**注意 Cache 在链上的位置：在 Connect 之前**——命中缓存连连接都不建；
4. **ConnectInterceptor**：**从连接池取或新建 RealConnection**（TCP/TLS 握手发生在这层）；
5. **CallServer**：真正写请求读响应（okio 流操作）。

**深水区一：两种拦截器的横截面差异**——**应用拦截器（addInterceptor）在链头尾**：**只调用一次**（重试重定向都发生在它「一次 proceed」的内部）、看得到原始请求和最终响应、**看不到中间的缓存命中和连接细节**；**网络拦截器（addNetworkInterceptor）紧贴 CallServer**：**重定向每跳都执行一次**、能拿到真实的网络请求（含 Bridge 补的头的最终版）、**能看到缓存 304 的中间响应**。「同一机制插在链的不同位置 = 不同观测面」是责任链模式的精髓应用。

**深水区二：责任链的两种形态对比**——**OkHttp 的「递归栈式」**（请求沿栈下行、响应沿栈回溯，每环可以做前后处理）vs **Android 事件分发的「序列传递式」**（onTouchEvent 返回 true 就消费终止，父传子不回头）vs **Servlet Filter 的「双向链」**（doFilter 前后分别是请求和响应处理，和 OkHttp 同构）。**能对比三种实现说明你理解的是模式本身而不是某个框架**。

收尾：OkHttp 拦截器答题的降维打击句，「**责任链的递归实现让『中间件』可以在 proceed 前后做对称处理，这和 Koa/Express 的洋葱圈、Redux middleware 是同一个结构**」——一句话连通三个生态。

> 面试官追问点：自定义重试拦截器为什么要包住 proceed 的 try-catch 而不是靠 RetryAndFollowUp？应答思路：RetryAndFollowUp 管「协议级重试」（连接失败/可重试的路由异常），业务级重试（429/限流退避）语义不同要自己写——**框架的链设计恰好给了业务方自定义环节的插槽**。

#### 7.4 观察者到EventBus怎么演进？代价是什么

答：一句话定调，**观察者模式的本质是「订阅关系的倒置」：主体不再调用依赖者，而是维护一张订阅表广播，EventBus 的进化是「把这张表从主体身上拆下来，变成全局中介」**。

**经典观察者的两个角色**：Subject 维护 `List<Observer>`（attach/detach/notify），状态变更时遍历调 update——**「推模型」把数据塞进 update 参数，「拉模型」只传主体引用让观察者自己取**（推省事但耦合数据结构，拉灵活但观察者要了解主体）。

**深水区一：从观察者到发布订阅的「中介化」**——经典观察者**双方直接持有引用**（Subject 知道每个 Observer），发布订阅**加了个事件中心**：发布者只发「topic + payload」，订阅者按 topic 注册——**双方向事件中心注册，互相不认识**。这个解耦的代价与收益：**事件中心成了全局依赖的集散地**（追踪「谁订阅了这个事件」要翻注册表，调试链路断裂），**「事件风暴」是模式滥用的报应**（几十种事件互相触发，数据流变成蜘蛛网）——**LiveData 的 Lifecycle 绑定和 RxJava 的 Disposable 链，都是在给「解耦的代价」打补丁**（前者防泄漏观察者、后者管订阅生命周期）。

**EventBus 的实现要点**（手写题的高配版）：

1. **注册**：反射扫 Subscriber 类的方法，**找 @Subscribe 注解的签名**，按「事件类型 → 方法列表」入两级 map（**按事件类型分桶是 O(1) 派发的关键**）；
2. **派发**：post(event) 按类型查桶，**线程模型决定执行线程**（MAIN/POSTING/ASYNC，每线程一个队列 + Handler 转发）；
3. **粘性事件**：缓存最后一份事件，新订阅者注册时补投（**「晚到者也能拿到历史」的广播语义扩展**）；
4. **性能优化点**：**注解扫描的反射结果缓存**（Class → SubscriberMethod 的 map，同类只扫一次），高版本用编译期 APT 生成索引替代运行时反射（EventBus 3 的 subscriber index）——**「运行时反射挪到编译期」是框架优化的通用套路**。

**深水区二：背压问题的模式本质**——观察者是「推」模式，**生产快于消费时观察者被动挨打**（事件堆积或丢）；RxJava 的背压策略（Buffer/Drop/Latest）本质是**给推模型加「订阅者反馈速率」的通道**（request(n) 拉回一点拉的语义）——**Flow（协程）/ Reactor 的冷流干脆改成「按需拉」**，把控制权还给消费者。**「推拉的钟摆」是异步模型的永恒主题**。

收尾：观察者家族的答题线，「**经典观察者（直接引用）→ EventBus（全局中介+反射注册）→ 响应式流（带背压控制的管道）**」，每一步都在解决上一步的解耦代价。

> 面试官追问点：LiveData 为什么天然防内存泄漏而 EventBus 不防？应答思路：LiveData 的观察注册绑定 Lifecycle（LifecycleOwner 传进 observe），**DESTROYED 时自动移除**（生命周期的观察者模式嵌套了一层）；EventBus 的注册是手动的 register/unregister 忘了就泄漏——**「把订阅的生命周期托管给宿主」是现代组件的标配设计**。

#### 7.5 Spring AOP怎么选代理？织入时机在哪

答：一句话定调，**Spring AOP 是「动态代理的模式应用」：运行时给 Bean 包一层代理织入切面，接口走 JDK、无接口走 CGLIB，代理对象的生成时机在 Bean 初始化之后**。

**AOP 的三个核心概念先钉死**：**切点（Pointcut，哪些方法）+ 通知（Advice，before/after/around 干什么）+ 织入（Weaving，什么时候把切面装进去）**——Spring 只做**运行期动态代理织入**（对比 AspectJ 的**编译期/类加载期字节码织入**，后者能织 final 方法、构造器、字段访问，能力更强但要独立的编译器/agent——**「运行期便利 vs 织入能力」的分野**）。

**代理的创建时机**（深水区一）：**BeanPostProcessor 的 postProcessAfterInitialization**——普通 Bean 初始化完，AnnotationAwareAspectJProxyCreator 判断「有没有切点命中这个类」，命中就 **ProxyFactory 包装**（getProxy 按有无接口选 JDK/CGLIB）放回容器。推论：**容器里注入的是代理对象，this 引用的是裸对象**（自调用失效的根源，7.2 讲过的同一本质）。

**两种代理的选择逻辑**（深水区二）：**proxyTargetClass 标志决定**——默认有接口用 JDK（代理实现接口）、无接口自动 CGLIB；**Spring Boot 2 起默认 proxyTargetClass=true**（全 CGLIB），动机是消除「同一 Bean 按接口注入能成功、按具体类注入失败」的不一致陷阱。**CGLIB 代理对 Bean 的额外要求**：不能是 final 类、方法不能 final（不能重写就织不进去）、**构造器会被调用两次**（一次造目标、一次造子类代理实例——视觉上像「初始化两次」的经典疑惑，其实是两个对象）。

**拦截的执行链**：**ReflectiveMethodInvocation 持拦截器链（把 @Before/@After 解析成 MethodInterceptor 数组）**，proceed 的递归结构和 OkHttp 拦截器同构（**责任链在三个框架里的同一形态**）——@Around 自己控制 proceed 的位置，@Before 在 proceed 前自动插，**「声明式注解最终变成拦截器链的组装」**。

收尾：Spring AOP 的模式清单——**代理模式（核心机制）+ 责任链（拦截器执行）+ 策略（JDK/CGLIB 选择）+ 模板方法（BeanPostProcessor 的扩展点）**，一个功能串四个模式，是「模式辨认」类问题最好用的例子。

> 面试官追问点：@Transactional 什么场景失效？应答思路：五连答——自调用（this 不走代理）、方法非 public（CGLIB 也重写不了）、异常被 catch 吞掉（通知看不到）、默认只回滚 RuntimeException（受检异常要 rollbackFor）、多线程里异常（事务绑定 ThreadLocal 连接）。**每条都能落回「代理增强的是外部调用面」这一根因**，这样答就不是背清单而是讲原理。

#### 7.6 三种工厂怎么递进？三级缓存怎么解环

答：一句话定调，**三种工厂的差异在「实例化的决定权放哪、应对的变化维度是什么」，而 Spring 的 BeanFactory 是「工厂的工厂加注册表」，它的三级缓存把循环依赖解成了「提前暴露半成品」**。

**三种工厂的递进**：

1. **简单工厂**：一个静态方法加 switch 按参数造产品——**决定权集中在工厂方法里**，加产品要改工厂（**违反开闭**），适合产品少且稳定；
2. **工厂方法**：每个产品配一个工厂类，客户端 new 具体工厂——**决定权下放到客户端**，加产品「加一对类」不改旧的（开闭达标），代价是类爆炸；
3. **抽象工厂**：**变化维度从「一个产品」升到「产品族」**——UI 套件（Button+Text+Scroll 一整套）整体换肤，ConcreteFactory 一次造一族；**新增产品种类难（要改所有工厂），新增族容易**——和工厂方法的开闭方向正好互补。

**深水区一：Spring 三级缓存解循环依赖**——A 依赖 B、B 依赖 A 的死结怎么解：

1. **一级 singletonObjects**：成品 Bean；
2. **二级 earlySingletonObjects**：**实例化但未装配完的半成品**；
3. **三级 singletonFactories**：**ObjectFactory（造半成品的 lambda）**。

流程还原：A 实例化后**先把「自己的工厂」放进三级缓存**再开始装配 → 装配需要 B → B 装配时需要 A → **从三级缓存拿到 A 的工厂，earlyReference 提前拿到 A 的半成品引用**（够 B 完成装配）→ B 成品入一级 → A 拿到 B 继续装配完成。**「不等造完就先发引用」是解环的钥匙**；三级缓存存工厂而不是直接存对象，是为了**让 AOP 代理有「按需延迟决策」的机会**（有代理需求时工厂返回代理，无需求返回原对象）。**构造器注入解不了**（实例化都没发生，没有半成品可暴露）、**prototype 解不了**（没有缓存容器）——这两条是追问的标配。

**深水区二：DI 与「控制反转」的精确语义**——** BeanFactory 是「注册表（BeanDefinition）+ 反射（实例化）+ 依赖图（装配顺序）+ 生命周期（init/destroy 回调）」的合体**；**「反转」反转的是「谁创建谁」：从「对象自己 new 依赖」变成「容器把依赖递进来」**——工厂模式的极致形态是「把 new 这个动作本身从业务代码里清除」。

收尾：工厂题的心法，「**三种工厂按『决定权在哪、变化维度几维』排；Spring 的答案是注册表化工厂，三级缓存是它最漂亮的一仗**」。

> 面试官追问点：@Autowired 和构造器注入哪个好？应答思路：构造器注入让依赖不可变（final）+ 缺依赖时启动即失败（fail fast）+ 循环依赖直接报错（逼你拆坏设计）——**字段注入能跑通循环依赖恰恰是纵容**；官方推荐构造器注入的理由全是工程性的。

#### 7.7 Builder怎么链式设计？Lombok有什么坑

答：一句话定调，**Builder 解决「构造参数爆炸」的三宗罪，链式调用的本质是「返回 this 的流式 API」，OkHttp 的范本是「建造期可变、使用期不可变」**。

**先看不用 Builder 的两条烂路**：**重叠构造器**（参数一多，`new Pizza(size, cheese, pepperoni, sausage, ham...)` 十个重载）**调用方可读性为零**（`new Pizza(10, true, false, true)` 谁知道哪个是哪个）；**JavaBeans 模式**（无参构造加一堆 setter）**对象在「set 完之前」处于不一致状态**（可能被并发读到半成品）且天然可变。

**Builder 的解法**：**构造参数全部变成 builder 的方法（每个方法返回 this 形成链）**，**build() 一次性把参数交给目标构造器**——**「配置过程流式、生效瞬间原子」**。

**深水区一：OkHttp 的 Builder 是「可变建造器 + 不可变产品」**——**Request.Builder 内部字段是普通可变的**（链式 set 就是改字段），**build() 时把值拷贝进 Request，后者的字段是 final**——**建造期随便改、造完不可改**：线程安全的根源（多线程共享一个 Request 无锁）、也能解释「复用同一个 Builder 连续造多个 Request 但中途改配置会互相影响」（Builder 是共享可变状态）。**对照反面**：StringBuilder 是「可变产品」（build 语义弱化为 toString），它更接近「缓冲」不是严格的建造者——**「Builder 造完通常不暴露 setter」是语义判据**。

**深水区二：Lombok @Builder 的三个坑**——**①默认值丢失**：类字段写了 `private int timeout = 5000;`，@Builder 生成的 builder 字段是 0（**默认值只对构造器/字段初始化生效，Builder 路径绕过了它**），要 @Builder.Default 显式声明；**②无参构造消失**：@Builder 生成全参构造，原无参构造被顶掉，JSON 反序列化等依赖无参构造的框架报错——要 @NoArgsConstructor 加 @AllArgsConstructor 补救；**③toBuilder 的语义**：`@Builder(toBuilder = true)` 提供「以现有对象为底本的复制式修改」（`req.toBuilder().url(newUrl).build()`）——**不可变对象的「伪修改」惯用法**。

**和工厂的分界**：**工厂关心「造哪一种」（类型决策），Builder 关心「这一种怎么配」（参数组装）**——Retrofit 两样都用：Retrofit.Builder 配参数（建造者），CallAdapterFactory 换实现（工厂）。

收尾：Builder 题的心法，「**重叠构造器与 JavaBeans 的病、链式返回 this 的形、可变建造器加不可变产品的神、Lombok 三坑的实战**」，最后一句「**Builder 是把构造的复杂度从调用方搬进一个一次性脚本**」点题。

> 面试官追问点：为什么 Builder 的方法能链式而 setter 不能？应答思路：setter 返回 void（语义是「改状态」），Builder 的方法返回 this（语义是「继续配置」）——一行代码的差别，语义差一个模式；fluent API 的通用设计（Stream、StringBuffer 同款）就是「每个操作返回继续操作的能力」。

#### 7.8 装饰器与代理的同构结构？意图怎么分野

答：一句话定调，**装饰器和代理的代码结构完全同构（「实现同接口、内部包一个同接口实例、方法转发前后加料」），区分它们的不是代码是意图：装饰器回答「如何增强」，代理回答「如何控制」**。

**同构性先摆出来**（能自己写出这个同构对照就是过线）：

```java
class Decorator implements Iface {          class Proxy implements Iface {
    private final Iface inner;                  private final Iface target;
    Decorator(Iface i){ inner = i; }            Proxy(Iface t){ target = t; }
    void op() {                                 void op() {
        before();                                  checkAccess();
        inner.op();                                target.op();
        after();                                   log();
    }                                            }
}                                              }
```

**两者的分野在「包装的发生学」**（深水区一）：**装饰器由调用方显式组装**（`new Buffered(new FileInputStream(f))`——**「我要增强」是使用者的决定**，且可任意多层堆叠）；**代理由框架在边界处生成**（Spring 在 Bean 初始化后包一层——**「被代理」对调用方是透明的**，你注入的本来就是代理）。**一句话判据：「你知道你在用装饰器，你不知道你在用代理」**。

**Java IO 是装饰器的教科书**（把它的设计逻辑讲透）：**InputStream 是抽象组件**，**FileInputStream 是具体组件**（真有字节来源），**FilterInputStream 是抽象装饰器**（持有一个 InputStream 的字段，方法默认转发），**BufferedInputStream/DataInputStream 是具体装饰器**——**「组合优于继承」的极致**：如果用继承，「可缓冲的文件输入流、可缓冲的可数据读的管道流」是 m×n 的类爆炸；装饰器把「来源」和「能力」做成两个正交维度自由组合。

**代理的三变体对应三种控制**（深水区二）：**远程代理**（控制「透明访问远端」，RPC stub 把网络细节藏掉）、**虚代理**（控制「创建时机」，图片懒加载占位符）、**保护代理**（控制「访问权限」，Spring Security 的方法拦截）。**它们共同点是「调用方以为在直接调目标，控制逻辑是中间层偷加的」**——和装饰器的「调用方主动要求增强」形成动机镜像。

收尾：这题的终极答案，「**GoF 的结构型模式本来就是同一批组合关系的不同动机分类——装饰器和代理共享代码，分野在 UML 图旁边的需求文档里**」；能说出这句，说明你懂的是设计而不是类图。

> 面试官追问点：OkHttp 的 Interceptor 是装饰器还是代理？应答思路：调用方主动 addInterceptor 组装（装饰器的发生学），但每层做的是「控制重试、缓存、连接」（代理的控制语义）——**生产级框架经常是两者的混血**，这也是「模式是语言不是法律」的最好例证。

#### 7.9 策略加注册表怎么消if-else？何时不用

答：一句话定调，**if-else 的罪不在语法在「变化的东西和不变的东西缠在一起」，策略把「每种做法」变成对象、工厂或注册表解决「按 key 找到它」，重构的完成态是「新增分支零改动」**。

**先看病灶**（支付场景的经典 switch）：

```java
public PayResult pay(String channel, Order order) {
    if ("ALIPAY".equals(channel)) { /* 支付宝SDK组装、签名、调用... */ }
    else if ("WECHAT".equals(channel)) { /* 微信证书、xml包装、调用... */ }
    else if ("UNION".equals(channel)) { /* 银联... */ }
    throw new UnsupportedChannelException();
}
```

**三个具体罪行**：**每加渠道改这个函数**（改动的触面集中在一处，merge 冲突高发）；**测试要 mock 整个 switch**（无法单测「只测微信分支」）；**函数随业务线性膨胀**（半年后三百行）。

**重构三步**：

1. **抽策略接口**：`PayChannel { String key(); PayResult pay(Order o); }`——**每个渠道一个实现类，互不知晓**；
2. **注册表替代工厂 switch**：`Map<String, PayChannel>`，**Spring 的注入魔法在这里发光**——`PayService(PayService 构造参数 List<PayChannel> channels)`，**容器把所有实现自动收集**，构造里 `channels.forEach(c -> map.put(c.key(), c))`——**注册逻辑零 switch**；
3. **上下文只剩路由**：`pay(channel, order) { return map.get(channel).pay(order); }`——**找不到的兜底统一抛异常**。

**深水区一：注解驱动的注册**——策略多到不想手写 key() 时，**自定义 @Channel("ALIPAY") 注解 + 容器启动时扫描**（或 Spring 的 beanName 约定）；**「注册的元数据」从代码升到注解**，模式的可维护性又进一步。**深水区二：什么时候不该重构**——**分支数 2-3 且半年没动过的，策略是过度设计**（类数量换来的灵活性没人用）；**判断标准是「变化的频率」不是「if-else 的行数」**——这是「模式为变化服务，不为美感服务」的原则落地。

**和状态模式的对照收尾**：**策略由「调用方每次显式选」**（这次用支付宝是用户选的），**状态由「对象内部自动流转」**（订单从待支付到已支付是生命周期推进）——**同一个「多态替换分支」的结构，选择权的归属决定叫什么模式**。

收尾：这题面试官要的不是 UML，是「**你重构过没有**」——讲一个真实的 switch 到策略的迁移（含单元测试怎么变简单），比背十个模式名值钱。

> 面试官追问点：map.get 返回 null 的防御怎么做？应答思路：Optional.ofNullable 包装加自定义异常（带 channel 值的错误消息）；更深一层——**「不支持的渠道」是业务异常还是系统 bug**？前端传错是业务（400），漏实现某个约定渠道是 bug（500），异常类型的选择体现你对边界的理解。

#### 7.10 享元模式的三个马甲？复用粒度怎么比

答：一句话定调，**享元 = 「共享内部状态、外部状态调用方传」，它的三个工业马甲是 Integer 缓存池、Handler 的 Message 池、Glide 的 BitmapPool——复用粒度一个比一个狠**。

**两个状态的划分是设计核心**：**内部状态（intrinsic）：对象间可共享的不变部分**（Integer 的值、Message 的字段槽位）；**外部状态（extrinsic）：每个使用场景不同的部分**（这个消息发给谁、什么时间发）——**享元对象不持有外部状态，方法参数临时传入**，这是「一个对象服务多个上下文」的合法性来源。

**三个马甲的对照表**（深水区一，按复用粒度递进）：

1. **Integer.valueOf 的缓存池**：**[-128, 127] 预创建的 Integer 对象共享**（类加载时静态初始化 IntegerCache.cache 数组）——**复用的是「对象身份」**；**经典笔试题**：`Integer a = 127, b = 127` 时 `a == b` 为 true（装箱走 valueOf 拿缓存），**128 时为 false**（超范围 new 了新对象）——**「装箱缓存的边界」是这道百年老题的原理**；String 常量池同款思想（字面量 intern 复用）；
2. **Handler 的 Message 池**：`obtain()` 从 **sPool（单链表，上限 50）**摘一个复用，`recycle()` 清空字段回池——**复用的是「对象壳」**（字段每次覆盖），**比 Integer 更进一步：身份都换了，只省了分配和 GC**；**「Message 没回收导致池耗尽」和「recycle 后还在用」是两个经典 bug**（后者在 debug 模式有检测）；
3. **Glide 的 BitmapPool**：**inBitmap 机制连「内存」都复用**——**解码时把池里一块够大的 Bitmap 内存直接当目标缓冲**（API 19+ 允许尺寸不精确匹配）——**复用粒度到达字节数组层，「分配」这个动作被消灭**；代价是**尺寸不匹配的复用会浪费内存**（拿了 1MB 的池子装 100KB 的图），池的淘汰策略（LRU 按尺寸桶）在平衡这个浪费。

**深水区二：池化 vs 享元的辨析**——**线程池是享元吗？严格说不是**：**享元共享的是「状态」（值不变所以可共享）**，**池化复用的是「实例」（状态每次被重写，共享的是分配成本）**；Message 池、Bitmap 池本质是池化（借了享元「共享省内存」的哲学），Integer 缓存才是教科书享元（**值就是内部状态，天然共享**）——**能分清这两个概念的分界，说明不是背名字的**。

收尾：享元题的心法，「**内部状态可共享是合法性、外部状态外置是纪律、三个马甲按『身份-壳-内存』的粒度递进**」，最后补一句「**享元是拿『共享的复杂度』换『分配的成本』，池满了和线程安全是它的两个暗坑**」。

> 面试官追问点：Message 池为什么用链表不用数组？应答思路：复用的语义是「栈式借用归还」（用完就还、先还先用），链表头插头取 O(1) 且无需容量搬移；数组下标管理（环形的 bitmap 标记空闲位）适合固定分配器（如 slab），Message 的数量波动大，链表最简——**数据结构服务于复用的访问模式**。
