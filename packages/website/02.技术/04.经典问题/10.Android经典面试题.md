# 1.四大组件与Application

### 1.1 Activity与Fragment

#### 1.1.1 Activity有哪几种启动模式？生命周期怎么走

答：必问题。一句话定调，**四种启动模式的差异只在「任务栈的归属与复用规则」一条轴上——standard 谁调谁栈、singleTop 栈顶去重、singleTask 栈主清场、singleInstance 独占一栈；生命周期不是七个回调的清单，是「AMS 投递消息 → 主线程队列执行」的外在表现**。

**四种启动模式**：standard——每次新建压进调用者任务栈；singleTop——**栈顶去重**（复用走 onNewIntent，**栈中已有但不在栈顶照样新建**，这是高频陷阱）；singleTask——目标栈清场（affinity 匹配的栈里位于它之上的全部出栈）+ 栈内唯一；singleInstance——singleTask 再加**独占一栈**（别的 Activity 进不了它的栈）。

**任务栈的补充维度**：taskAffinity 与 FLAG_ACTIVITY_NEW_TASK 的配合——**「NEW_TASK + 不同 affinity」才真正开新栈**，flag 与清单声明两套体系会在代码里打架；常用 Flags 的组合语义（CLEAR_TOP / SINGLE_TOP / NEW_TASK）是启动模式题的代码面。

**onSaveInstanceState 的触发时机**：按 Home、锁屏、被高优先级 App 覆盖等「**可能被系统回收**」的场景才存；**API 28 起官方保证它在 onStop 之前**（28 之前与 onPause 的先后顺序不确定）。

**深水区**：Activity 启动流程（Instrumentation.execStartActivity → AMS → Zygote fork 或复用进程 → ApplicationThread.scheduleTransaction → 主线程 Handler 消息里执行 performCreate）——**「生命周期回调是谁在调」的终极答案：AMS 决定时机，ActivityThread 的消息队列决定执行**。完整链路的口述版见 13.6 深度精讲。

收尾：答题心法，「**启动模式按『栈归属 + 复用规则』两问分类，生命周期按『消息驱动』理解**」，最后把 13.6 的跨进程链路串上就是深水区。

> 面试官追问点：singleTask 启动时目标栈不存在会发生什么？应答思路：AMS 先建（或找到 affinity 匹配的）任务栈再压入实例——「先栈后 Activity」的顺序；顺带补一句「同一个 app 的任务栈可以有多个（affinity 不同）」，就是加分层。

#### 1.1.2 各回调方法的区别？onNewIntent何时触发

答：一句话定调，**onStart/onStop 管「可见性」、onResume/onPause 管「前台可交互」——这是两把不同的尺子；onNewIntent 是「复用已存在实例」时的补偿回调，它替代的是 onCreate**。

**两把尺子**：可见（onStart↔onStop）——对用户可见与否：**弹半透明 Dialog 不触发 onStop（还可见）但触发 onPause（失去前台）**，「可见但不可交互」就是这个窗口；前台（onResume↔onPause）——焦点归属：onPause 里最该停的是「耗电的交互逻辑」（动画/相机/传感器）。

**onNewIntent 的三件事**：触发条件——singleTop 栈顶复用、singleTask/singleInstance 栈内复用；**坑——intent 不会自动更新 getIntent() 的返回，要手动 setIntent(intent) 或直接用回调参数**；执行时机——onRestart/onStart 之后、onResume 之前。

**configChanges 避免重建**：清单里 orientation|screenSize 后，转屏不重建改走 onConfigurationChanged——**「承接变更」替代「重启承接」**，但这是延迟问题不是消除（多窗口/分屏的尺寸变化可能没覆盖全）。

**深水区**：恢复的双通道——onCreate 的 savedInstanceState（重建场景才有）与 onRestoreInstanceState（**只要恢复就一定走、且在 onStart 之后，不用判空**）的分工；onPause 的串行性（前一个不退、后一个不来）对页面启动速度的传导。

收尾：心法一句，「**可见看 start/stop、交互看 resume/pause、复用看 onNewIntent、重建看 save/restore——四对回调各管一段**」。

> 面试官追问点：为什么官方不建议在 onPause 里做存储？应答思路：Activity 切换是串行的——新 Activity 的启动要等前一个 onPause 走完（Android 10 前），onPause 里写文件会直接拖慢下一个页面启动；持久化放 onStop 或 onSaveInstanceState——「读快写慢」的分工。

#### 1.1.3 Fragment生命周期怎么走？通信方式有哪几种

答：一句话定调，**Fragment 比 Activity 多了「视图层」这一档生命周期——onCreateView/onDestroyView 管视图、onCreate/onDestroy 管实例；add/replace/show/hide 的差异全在「视图是否重建」这条轴上**。

**三层生命周期**：实例层（onAttach→onCreate→onDestroy→onDetach）、视图层（onCreateView→onViewCreated→onDestroyView）——**「实例活着但视图死了」是 Fragment 特有的中间态**（ViewPager 相邻页销视图不销实例就是这个态）；add/show/hide 与 replace 的差异——add 叠加（都活着，show/hide 只切可见性、**视图状态全保留**），replace 是 remove+add（**旧 Fragment 整个重建，状态丢失**）——「来回切换用 hide、单向流程用 replace」的依据就是要不要保留视图状态。

**通信三代演进**：接口回调（老式、样板多、双向耦合）；**共享 ViewModel**（两个 Fragment 拿同一个 Activity 作用域的 ViewModel——官方首推，「数据放第三方、双方解耦」）；**FragmentResult API**（FragmentManager 的一对一/广播式结果传递，替代已废弃的 setTargetFragment）。

**深水区**：commit 与 commitNow/commitAllowingStateLoss 的差异（**onSaveInstanceState 之后 commit 抛异常的原理**——状态丢失窗口）；子 Fragment 与 ViewPager2 的 BEHAVIOR_RESUME_ONLY_CURRENT_FRAGMENT（「非当前页停在 onStart」把懒加载判据交给生命周期，见 1.1.4）。

收尾：心法，「**Fragment 比 Activity 多一个视图层；通信演进是「接口 → 共享 ViewModel → 结果 API」**」。

> 面试官追问点：为什么 Fragment 构造函数不能传参数？应答思路：配置变更重建时系统只能反射无参构造——setArguments 的 Bundle 会跟着实例一起恢复，所以传参必须走 Bundle；FragmentFactory 是官方后来的补丁，但「Bundle 是唯一重建安全的通道」这个结论不变。

#### 1.1.4 Fragment怎么做懒加载？常见坑有哪些

答：一句话定调，**懒加载的本质是「把数据请求从视图创建挪到『真正可见且就绪』的时刻」——判据在三代演进里从人肉信号走到生命周期信号，核心永远是「两个信号取交集」**。

**三代演进**：早期 ViewPager 的 setUserVisibleHint（isVisibleToUser）——**它的调用在 onCreateView 之前**（Fragment 还没初始化），必须配合「是否已准备」的布尔位；show/hide 切换的 onHiddenChanged——配合 isAdded 判断；**现代方案：Lifecycle**——ViewPager2 + maxLifecycle 把「当前页 onResume、其余页停在 onStart」交给框架，**懒加载判据直接退化成「onResume 才请求」**——信号交给生命周期是演进终点。

**三个常见坑**：
- **getActivity() 返回 null**：异步回调（网络回来）时 Fragment 已 detach——防御是判空，更根本的是**把数据请求放进 ViewModel**（回调落在 VM 层，UI 只订阅，时序解耦）；
- **视图重叠**：系统重建时 FragmentManager 恢复了旧实例，Activity 的 onCreate 又 add 了一个新实例——**防御是「只在 savedInstanceState == null 时 add」**；
- **参数读取的时机**：arguments 的 Bundle 在 attach 时就绪，onCreate 就能读——「数据早于视图」，别等 onCreateView。

收尾：心法一句，「**懒加载三代是『人肉信号 → 生命周期信号』；三个坑全是『异步回来的时序对不上』**」。

> 面试官追问点：setUserVisibleHint 为什么被废弃？应答思路：它的调用时机先于 onAttach，「信号到了但人还没准备好」制造了永恒的窗口期；现代 API 用生命周期对齐信号（RESUME 即「可见且就绪」），把「取交集」的活交给了框架——答出「信号与生命周期不对齐」即到位。

### 1.2 Service与广播

#### 1.2.1 Service两种启动方式的区别？怎么保活

答：一句话定调，**startService 是「我启动你、你自管生死」（退出页面也活），bindService 是「我们绑定、共存亡」（连接断开自动销）——同一个 Service 可以同时处于两种状态，两者都退出才销毁**。

**两种方式的对照**：start——onCreate 一次 + **onStartCommand 多次**（每次 start 的 intent 逐次到达）、stopSelf/stopService 才停，适合「后台独立任务」（音乐播放）；bind——onCreate→onBind（**onStartCommand 不触发**）、**所有 binder 断开才销毁**，适合「组件间接口调用」；**bind 的连接是 GC Root，onDestroy 前 forget unbind 就是泄漏**。

**前台 Service 与后台限制**：8.0+ 后台 startService 直接抛异常——**出路是 startForegroundService + 5 秒内 startForeground 挂通知**（超时 ANR）；后台任务的标准答案是 **WorkManager**（约束感知 + 持久化 + 系统调度）——IntentService 的谢幕正是这条演进线（串行 HandlerThread 封装 → 后台限制下不可靠 → WorkManager 接棒）。

**保活方案与上限**：onStartCommand 的返回值三档（**START_STICKY 重启但 intent 丢 / REDELIVER 重启带原 intent / NOT_STICKY 不重启**）；前台服务（通知常驻，最正统）；1 像素、双进程互拉在 Doze 与厂商管控下成功率极低——**保活的上限是系统策略，不是应用代码**；Android 14 的 foregroundServiceType 强制声明是保活的合规化收口。

收尾：心法，「**start 管独立任务、bind 管接口调用、后台任务交 WorkManager、保活的尽头是前台服务**」。

> 面试官追问点：STICKY 和 REDELIVER 怎么选？应答思路：STICKY 被杀后重启但 intent 为 null（「任务不重放」）；REDELIVER 重启并重放最后的 intent（「任务必须送达」）；NOT_STICKY 不重启——按「任务是否幂等、是否必须完成」选返回值，能讲语义而不是背名字就对了。

#### 1.2.2 广播分为哪几种？两种注册方式的差异在哪

答：一句话定调，**广播按「有序性」和「作用域」两个维度切——普通/有序管分发顺序，本地/系统管边界；动态与静态注册的核心差异是「接收者随谁活、随谁死」**。

**种类**：普通广播（sendBroadcast）——异步分发、顺序不保证；有序广播（sendOrderedBroadcast）——按 priority 逐个送达、可 abortBroadcast + 结果逐级回传（**「责任链的分发版」**）；本地广播（LocalBroadcastManager，现代替代是 Context.registerReceiver 的 RECEIVER_NOT_EXPORTED）——**不跨进程、不进系统、零 Binder 开销**；粘性广播已废弃。

**注册方式**：动态注册（registerReceiver）——**跟随注册者的生命周期**，Activity 销毁前必须 unregister（静态持有 + 忘记反注册是事故源）；静态注册（manifest）——安装即注册、进程没启动也能收；**8.0 起除少数豁免（BOOT_COMPLETED 等）外禁止静态收隐式广播**——动态注册成为主流。

**深水区**：广播的安全两侧——发送方 receiverPermission、接收方 requirePermission，**签名级权限防伪造**（第三方伪装系统广播的攻击面）；分发实现是 AMS 的 ReceiverList 队列——一条系统广播唤醒所有注册进程，是待机电量大户（这也是 Batch 广播合并与静态限令的根因）。

收尾：心法，「**有序看 priority、边界看本地化、注册方式看生命周期、安全看权限两侧**」。

> 面试官追问点：为什么 8.0 禁止静态注册隐式广播？应答思路：一条系统广播（拍照/蓝牙连接）会唤醒所有静态声明的应用进程——「广播风暴」是待机电量杀手；豁免名单之外一律动态注册，**单播化、动态化是系统的省电方向**——能答出「进程唤醒成本」而不是「规定如此」就是深水区。

### 1.3 Provider、Context与启动

#### 1.3.1 Provider的启动时机？数据共享怎么实现

答：一句话定调，**ContentProvider 是「进程启动时自动安装、首次使用时才拉活目标」的跨进程数据通道——URI 解析后走 AMS 查找，Cursor 的数据走匿名共享内存，控制信令走 Binder**。

**启动时机**：进程创建后、**Application.onCreate 之前**安装（attachBaseContext 之后，系统按 authority 注册）——所以「**每个进程声明的 Provider 都在启动时被创建**」是它的隐藏成本（启动优化时 Provider 拖速是常客，解法是 android:process 分离或延迟初始化）；**拉活对方进程发生在首次 query 时**（AMS 查 authority 表，目标进程没活就 fork）。

**数据共享的实现链路**：URI 三段结构（scheme://authority/path，**authority 是全局唯一键**）；query 先经 AMS 解析出目标 Provider 的 Binder 代理；**Cursor 的数据传输用匿名共享内存（Ashmem）**——「大量数据走内存、控制信令走 Binder」，和 Binder 大数据走 Ashmem 的结论互相印证（见 13.2）。

**深水区**：Provider 的线程模型——onCreate 在主线程、**query/insert 在 Binder 线程池**（并发访问的同步责任在实现方）；call() 的自定义命令通道（不建 Cursor 的轻量调用）；**权限三件套**——readPermission/writePermission + **URI grant 的临时授权**（FLAG_GRANT_READ_URI_PERMISSION，分享图片给微信的机制）。

收尾：心法，「**安装随进程、拉活随首次使用、传输是 Binder + 共享内存、安全靠权限与临时授权**」。

> 面试官追问点：Provider 和 Application.onCreate 谁先执行？应答思路：attachBaseContext → **Provider 安装与 onCreate** → Application.onCreate——所以 Provider 的 onCreate 里拿到的 Application 是「半初始化」的（onCreate 还没跑）——「Provider 里别依赖 Application 的状态」，能报出这个顺序就是源码级理解。

#### 1.3.2 Context有哪几种？为什么会引起泄漏

答：一句话定调，**Context 四种（Application/Activity/Service/Receiver 各自的 ContextWrapper），差异在「生命周期」和「能力边界」两条轴——泄漏的全部原因是「长生命周期持有了短生命周期」**。

**能力对照**：Activity/Service 的 Context 能干「带 UI 的活」——**show Dialog 必须用 Activity Context**（window token 校验）；Application 里 startActivity 必须加 FLAG_ACTIVITY_NEW_TASK（没有任务栈容器）——**能力差异的背后全是 token**。

**泄漏三大场景**：静态/单例持 Activity Context（单例活一辈子、Activity 被拖死）；**非静态内部类的隐式持有**——Handler/Thread/AsyncTask 持外部 Activity 引用，「**匿名内部类对象活得比外部类久就是泄漏**」（静态内部类 + WeakReference 是标准解）；注册的监听器忘反注册（广播/观察者，与 1.2.2 同源）。

**防御原则**：**生命周期不匹配的场合一律用 ApplicationContext**（单例、长时任务）；短引用用完即清；用 LeakCanary 的弱引用观察验证（判定机制见 13.5 深度精讲）。

收尾：心法，「**能力看 token、泄漏看生命周期错配、防御用 Application Context 或静态 + 弱引用**」。

> 面试官追问点：为什么 Dialog 用 Application Context 会崩？应答思路：Dialog 构造需要 window token（Activity 的 token 才能挂到 WindowManager），Application 没有 token——BadTokenException；用 DialogFragment 或 Activity Context 才有「挂靠资质」，讲 token 而不是背结论就是加分。

#### 1.3.3 App冷启动流程是什么？链路经过哪些角色

答：一句话定调，**冷启动是「点击图标 → Launcher 发 Intent → AMS 决策（可能 fork 新进程）→ ActivityThread 建消息循环 → 生命周期逐个执行」的长链路——Application.onCreate 是全进程的初始化，首个 Activity 的 onCreate 是首页的初始化，优化的两把刀各砍一段**。

**完整链路**：Launcher 收点击 → startActivity 经 Binder 进 system_server（AMS 决策：注册了没、权限够没、进程活着没）→ **进程没活：Zygote fork（Socket 通知、COW 共享预加载类与资源）→ ActivityThread.main 建主线程 Looper** → attachApplication（App 把 ApplicationThread 的 Binder 交给 AMS 当「回程地址」）→ AMS 下发 scheduleTransaction（Binder 反向）→ **主线程消息队列依次执行：Application.onCreate → Activity 的 performCreate → onStart → onResume**。

**冷/热启动的差别**：热启动跳过 fork 与进程初始化（进程活、Looper 转）——**冷启动耗时的大头在「进程创建 + Application + 首个 Activity」，优化就盯着这三段**。

**优化两把刀**：Application 瘦身（延迟初始化/按需初始化、启动框架把初始化任务建拓扑排序后异步化——**有向无环依赖图**是启动框架的核心）；**Baseline Profile**（启动关键路径的 AOT 预编译画像，冷启动直接砍 30%+，机制详见 13.4 的 Profile 演进）。

**深水区**：白屏/闪屏的来源（Application 初始化期间窗口已建、首页未绘完——「窗口已显、内容未就绪」的空窗）；ANR 与链路的关系（生命周期全是消息，主线程被堵就超时——**ANR 的本质是消息排队超时**，完整口述见 13.6 深度精讲）。

收尾：心法，「**链路背三段（fork / 初始化 / 生命周期），优化砍两刀（Application 瘦身 + Baseline Profile），ANR 的根子是消息排队**」。

> 面试官追问点：冷启动白屏能彻底消除吗？应答思路：窗口（启动预览）在内容就绪前就已显示——改 windowBackground 可以把白屏换成品牌图但**不能消除空窗**，真正缩短靠启动提速；「能区分『掩盖』和『提速』」是这题的分界线。

# 2.Handler与消息机制

#### 2.1 Handler四件套的关系？延迟消息怎么实现

答：必问题。一句话定调，**Handler 是「单线程消息队列」的线程通信模型——Looper 是线程级单例、MessageQueue 是它的字段、Handler 是投递口加处理回调、Message 是载荷；延迟消息不是定时器，是「排序链表 + epoll 定时休眠」**。

**四件套的关系**：**Looper 用 ThreadLocal 存储（一个线程只有一个）**；MessageQueue 与 Looper 一对一；**一个队列可以有多个 Handler——Message.target 字段记住谁发的，分发时回到谁**；Message 从 sPool（链表池，上限 50）复用——「消息池化避免高频分配 GC」。

**主线程为什么不用 prepare**：ActivityThread.main 是主线程入口，它已经 Looper.prepareMainLooper() + loop() 了——**「App 的主线程代码」其实全是被 Looper 分发的一条条 Message**（Activity 生命周期就是 AMS 跨进程投递的消息，这也是 ANR 的根源）。

**延迟消息的实现**：Message 按 when 插入有序链表；Looper 取队头时算「还有多久到期」，把剩余时间传给 nativePollOnce(ptr, timeout)——**native 层就是 epoll_wait：没到时间挂起线程不耗 CPU，到期或新消息 nativeWake 唤醒**。所以 postDelayed(60s) 不开定时器线程，是「睡 60 秒」。

**HandlerThread 与 IntentService**：HandlerThread = 「prepare + loop 封装好的工作线程」，提供串行的后台消息队列；IntentService 是它 + Handler 的组合封装（串行任务，因后台限制被废弃 → WorkManager 接棒，见 1.2.1）。

**深水区**：ThreadLocal 怎么做到线程隔离（每个 Thread 自带 ThreadLocalMap，Looper 存在「线程自己的表」里）——这也是「子线程直接 new Handler 崩」的原因（没 prepare，当前线程的表里没有 Looper）。

收尾：三句话背下来，「**队列是排序链表不是定时器、阻塞是 epoll 不是死等、多 Handler 靠 target 分流**」——epoll 细节与同步屏障的完整口述见 13.1 深度精讲。

> 面试官追问点：主线程 loop() 是死循环，为什么不算 ANR？应答思路：ANR 的定义是「特定消息超时没执行完」（input 5s / broadcast 10s / service 20s），不是循环本身——循环空转时线程在 epoll 挂起（零 CPU），消息来了才醒来干活；**「死循环」是待机，「超时」才是病**，能分清这两者是这题的分界线。

#### 2.2 IdleHandler有什么用？同步屏障的原理

答：一句话定调，**IdleHandler 是「队列空闲时的回调挂载」，同步屏障是「让异步消息插队的一枚特殊 token（target=null）」——两者是 Handler 机制为「优先级」预留的两个口子**。

**IdleHandler 的机制**：MessageQueue.next() 发现没有可执行消息（要阻塞前）时，遍历 idle 回调列表——**「队列难得闲，杂活这时干」**；回调返回 false 自动摘除（一次性），返回 true 常驻（每次空闲都叫）。**经典应用**：首帧后的延迟初始化、**RecyclerView 的预取（GapWorker 就是挂在 IdleHandler 上）**——「不占关键路径的时间片」是它的价值定位。

**同步屏障的机制**：postSyncBarrier 往队列插一条 **target=null 的消息**（正常消息必须有 target 才能分发，null 就是天然标记）；next() 遇到屏障时**跳过所有普通消息、只找「异步消息」优先返回**。**完整应用链路**：UI 更新 requestLayout → ViewRootImpl 的 scheduleTraversals **postSyncBarrier + Choreographer 以异步消息注册帧回调** → 帧消息插队执行（doFrame 走 measure/layout/draw）→ 完成后 removeSyncBarrier——**渲染帧能越过无数延迟消息，靠的就是这套机制**。

**深水区**：postSyncBarrier 是 hide API（系统专用，反射可调但不该调）；屏障与异步消息的配对关系——**屏障只对「post 时标记 async」的消息生效**（sendMessageAtFrontOfQueue 的系统内部用法），普通业务消息永远排在屏障后面。

收尾：心法，「**IdleHandler 管空闲时的杂活、屏障管紧急时的插队——一个是空闲税，一个是优先级税**」，与 13.1 的 epoll 链路连起来讲就是完整深水区。

> 面试官追问点：如果渲染不用同步屏障会怎样？应答思路：帧回调（16.7ms 一次）要和业务延迟消息一起按 when 排队——一条 postDelayed(500ms) 的消息插在中间，这一帧就要等 500ms 才执行（肉眼可见卡顿）——**「渲染的确定性是屏障机制买来的」**，答出这个因果就到位。

# 3.View体系与UI

#### 3.1 View三大绘制流程是什么？事件分发怎么走

答：必问题。一句话定调，**三大流程是「measure 定尺寸（约束自上而下传、结果自下而上回）→ layout 定位置（父定子的四边）→ draw 画内容」的递归流水线，总入口是 performTraversals，而它的节拍来自 Choreographer 的 VSYNC 信号**。

**入口链路**：invalidate/view 改动 → ViewRootImpl.scheduleTraversals（**postSyncBarrier + Choreographer 注册帧回调**，见 2.2）→ VSYNC 到 → doFrame → performTraversals → 依次 performMeasure / performLayout / performDraw。

**measure 的核心是 MeasureSpec**：三种模式——EXACTLY（match_parent/具体值）、AT_MOST（wrap_content——**上限定了大小随便**）、UNSPECIFIED（父不约束，ScrollView 的场景）；**MeasureSpec 由「父的 size+mode」和「子的 LayoutParams」合成**——「约束是一层层加工传递的」。自定义 View 的必考坑：**wrap_content 不处理 onMeasure 时等价于 match_parent**（AT_MOST 模式下默认实现拿了父的剩余空间）。

**layout 与 draw**：layout——父调 child.layout(l, t, r, b)，自定义 ViewGroup 在 onLayout 里定每个子的位置；draw 的六步顺序（背景 → onDraw → dispatchDraw → 滚动条等装饰），**onDraw 别干布局的活**（分工是流程纪律）。

**自定义 View 三种方式**：继承 View 重写 onDraw（要处理 wrap_content 和 padding——两个必坑）、继承 ViewGroup（要 onLayout）、继承现有控件做扩展（工作量最小）。

**事件分发一句话带过**：dispatchTouchEvent 必经 → onInterceptTouchEvent 是 ViewGroup 特权 → onTouchEvent 是消费表态，**DOWN 定终身（一串事件一个主人）**——完整三段式与滑动冲突见 13.7 深度精讲。

收尾：心法，「**measure 传约束、layout 定四边、draw 按六步**；两坑必答（wrap_content 与 padding）」。

> 面试官追问点：requestLayout 和 invalidate 的区别？应答思路：requestLayout 标脏「尺寸位置」——走完整 measure/layout/draw 链；invalidate 只标脏「绘制」——跳过前两段只 draw；invalidate 不触发 measure 的设计是「**改什么就重算什么**」的分层流水线——顺带说出「ViewRootImpl 用 mLayoutRequested 标记区分两种脏」是源码级加分。

#### 3.2 滑动冲突的场景有哪些？内外拦截法怎么用

答：一句话定调，**滑动冲突按「同向/异向叠加」分两类，解法只有两个方向——外部拦截法（父的 onInterceptTouchEvent 判定）与内部拦截法（子 requestDisallowInterceptTouchEvent 抢先禁拦截）**。

**三类场景**：内外同向（ScrollView 嵌 RecyclerView——谁滑的问题）；内外异向（ViewPager 嵌 RecyclerView——系统已按方向内置判定）；复杂嵌套（地图控件内放列表——按业务自定义阈值）。

**外部拦截法（父问）**：父的 onInterceptTouchEvent 里三拍——**DOWN 必须 return false**（拦了子收不到整串事件）、MOVE 按滑动方向判定（水平位移差 > 竖直则拦）、**UP 必须 return false**（拦了子的 click 没了）——**三个 return 的时机约束是这道题真正的考点**。

**内部拦截法（子禁）**：子类 dispatchTouchEvent 的 DOWN 里 requestDisallowInterceptTouchEvent(true)（父的 onInterceptTouchEvent 直接不被调用）、MOVE 判定「这串事件该给父」时 release——「**孩子先表态别抢，要的时候再还**」，适合父控件不可改的场景。

**onTouch 与 onTouchEvent 的优先级**：View.dispatchTouchEvent 里 **onTouch(true) 短路 onTouchEvent → onClick 收不到**——「onTouch 里顺手 return true 把点击干掉了」是常见事故（performClick 的默认链路被绕过）。

**深水区**：**嵌套滚动协议（NestedScrollingParent/Child）**——系统把「父子协商」标准化：子先问父「你要消费多少」、剩下的自己滑（CoordinatorLayout/RecyclerView 都实现了）——「拦截是抢答、协议是协商」，现代控件优先用协议。

收尾：心法，「**拦截两法（父问/子禁）+ 三拍纪律（DOWN/MOVE/UP）+ 协议化演进（nested scrolling）**」，事件流细节串 13.7。

> 面试官追问点：ViewPager 嵌 RecyclerView 为什么默认不冲突？应答思路：两层防线——ViewPager 的 onInterceptTouchEvent 按水平方向判定拦截，加上 ViewPager2 与 RecyclerView 之间走嵌套滚动协议（子先消费再交父）——「**不是没有冲突，是冲突已被框架预置的判定与协议吃掉了**」。

#### 3.3 RecyclerView缓存有几级？每层怎么复用

答：必问题。一句话定调，**四级缓存按「离屏远近」和「要不要重绑」分层——scrap 是布局现场的临时收容、cache 是按 position 的精确命中（不重绑）、pool 是按 viewType 的跨列表共享（要重绑）**。

**四级职责**：一 Scrap（mChangedScrap/mAttachedScrap）——**当前布局过程内部被 detach 的 ViewHolder**（数据位置没变，跳过重绑）；二 Cache（mCachedViews，默认 2）——**刚滑出屏幕的按 position 精确缓存，命中直接复用不重绑**（这是它和 pool 的本质区别，马上滑回去最赚）；三 ViewCacheExtension——开发者自定义层（很少用，官方留的白板）；四 **RecycledViewPool（按 viewType 分桶，每桶默认 5）**——**命中只拿到正确类型的空壳，必须重新 onBindViewHolder**，可跨列表共享（setRecycledViewPool）。

**命中链**：getViewForPosition → 先 scrap/cache 按 position 查（零成本）→ pool 按 viewType 查（重绑成本）→ 都没有才 create——**与 ListView 对比的胜负手就在这：ListView 两级缓存、没有类型池、没有差量更新、没有预取**。

**DiffUtil 的差量更新**：notifyDataSetChanged 的暴力（全视为失效 → 全重绑 + 丢动画）对比 **DiffUtil 用 Myers 差分算最小编辑脚本**——未变的复用（跳过重绑）、变化的精确刷新、move 还触发位移动画；**AsyncListDiffer 把 diff 挪后台、ListAdapter 封装订阅**是现代标准姿势；底层是 areItemsTheSame（id）与 areContentsTheSame（内容）分离的精确语义。

**深水区**：预取（GapWorker）——滑动时空闲帧提前创建「即将进入屏幕」的 ViewHolder，**挂在主线程的 IdleHandler 上**（和 2.2 打通）——「重绑和创建都被搬离关键路径」。

收尾：心法，「**每级答两问：命中成本（要不要重绑）、覆盖范围（position 还是类型）**」，完整口述版见 13.3 深度精讲。

> 面试官追问点：为什么 cache 命中不重绑、pool 命中要重绑？应答思路：cache 存的是「原 position 的一手绑定」（数据没变，绑定依然有效）；pool 只承诺「类型正确」（同类型不同数据都要能装进来）——**缓存的契约不同，成本就不同**；答出「pool 的复用粒度是形态不是数据」就到深水区。

#### 3.4 布局层级怎么优化？过度绘制怎么排查治理

答：一句话定调，**布局优化是两把尺——「层级浅」（measure/layout 是递归全树，深度即成本）和「绘制省」（过度绘制 = 同一像素被画多遍）**；工具是调试 GPU 过度绘制 + Layout Inspector + Perfetto 三件套。

**层级优化三板斧**：**ConstraintLayout**——用约束求解替代多层嵌套（嵌套容器的约束逐层传递、要多次 measure；约束直接解出各子 View 的位置，**大部分场景单次测量完成**）；**merge**——被 include 的布局根标签直接合并进父（消灭无意义的包装层）；**ViewStub**——**零成本的懒加载占位**（不 inflate 不绘制，setVisibility 时才创建，适合「大多时候不显示」的页面块）。

**过度绘制的治理**：开发者选项「调试 GPU 过度绘制」看色块——**红（4 倍）必治、紫（3 倍）尽量**；两大来源：windowBackground 与内容背景叠画（主题里去 windowBackground 是列表页的经典动作）、多层不透明底色叠画——**「不画看不见的」**。

**统计与加载**：Perfetto 看 inflate 的耗时分布（IO 读 XML → 反射创建 View 的成本）；**AsyncLayoutInflater 的取舍**（布局膨胀挪后台线程，代价是「拿 View 变成异步回调」）；**bindViewHolder 里的耗时**——数据转换只算一次（缓存转换结果）、DiffUtil 预计算，把「每帧都在算」的活变成「提交时算一次」。

**深水区**：ConstraintLayout 不是银弹——一两层的简单 LinearLayout 反而更快（约束求解本身有成本）——**「按层级深度决策，不按名字决策」**；Compose 声明式直接跳过 XML inflate（编译期组件树），是这条优化线的终局（见 10.5）。

收尾：心法，「**层级三板斧（约束/merge/ViewStub）、绘制两来源（背景叠画）、测量用工具说话**」。

> 面试官追问点：ViewStub 和 Gone 的区别？应答思路：Gone 的 View **已经 inflate**（内存与 XML 解析成本已花，只是不 measure/draw）；ViewStub 在 show 之前**根本没创建**——「省的是创建的钱，付的是时序的钱（异步获取实例）」；频繁切换用 Gone、大块冷门用 ViewStub。

#### 3.5 屏幕刷新的机制是什么？FPS监控怎么设计

答：一句话定调，**刷新机制三段：VSYNC 硬件节拍 → Choreographer 按类型编排回调 → performTraversals 执行绘制；FPS 监控的本质是「在 doFrame 的回调里数帧间隔」，而流畅度看的不是均值是方差**。

**从 invalidate 到上屏**：invalidate 打脏标记（不立即绘制）→ ViewRootImpl.scheduleTraversals：**postSyncBarrier + Choreographer.postCallback（异步消息，见 2.2）** → 下一个 VSYNC 信号到 → doFrame 依次跑三类回调（**INPUT / ANIMATION / TRAVERSAL**——输入、动画、绘制的固定次序）→ performTraversals → GPU 渲染 → 双缓冲交换上屏。

**Choreographer 的角色**：帧的「编排者」——**按 VSYNC 节拍把三类回调排进当帧**；**掉帧的检测点就在 doFrame 的开头**（scheduledFrameTime 与实际时间差）——系统的 JankStats 也从这取数。

**VSYNC 与缓冲**：VSYNC 是硬件的统一节拍（60/90/120Hz），**把「随机的绘制」对齐到「节拍的绘制」**；双缓冲防撕裂（前帧显示后帧绘制），**三缓冲是「掉帧后的缓冲垫」**（掉一帧时用第三块缓冲救回来，代价是多一帧延迟）。

**流畅度的正确口径**：**平均 FPS 会骗人**——59 的均值可以是「58 帧流畅 + 2 帧各卡 500ms」；更真实的口径是**慢帧/卡帧次数（JankStats 的分位数统计：P90/P95 帧耗时）**——「方差比均值诚实」。

**FPS 监控的设计**：Choreographer.postFrameCallback 挂回调——**两次 doFrame 的时间差 vs 屏幕周期**（16.7ms/60Hz），超阈值计数、聚合成慢帧率上报；线下用 Perfetto 的帧泳道看每一帧的「时间花在哪」（见 8.8 工具篇）。

收尾：心法，「**节拍是 VSYNC、编排是 Choreographer、执行是 Traversals；监控数的是帧间隔方差**」。

> 面试官追问点：为什么有了 VSYNC 还要三缓冲？应答思路：VSYNC 解决「何时画」的节拍问题，双缓冲解决「画与显示的冲突」；但一旦某帧超时（GC/重活），双缓冲下这一拍直接缺帧；**第三块缓冲允许「下一帧先准备着」，用一帧的延迟换掉帧率的下降**——工程上典型的「延迟换流畅」交易。

#### 3.6 三种动画体系的区别？属性动画原理是什么

答：一句话定调，**补间动画（View 动画）只改绘制不改属性——「假移动」；帧动画是图片序列轮播；属性动画是「时间驱动的 setter 调用」——真改属性，所以事件响应区域跟着走**。

**三者的机制**：补间——对 View 的绘制矩阵做变换（translate/scale/rotate/alpha 的 Transformation），**layout 的四边一动不动，点击区域原地不动**；帧动画——AnimationDrawable 按帧切图（成本是图片内存，大帧动画是 OOM 常客）；属性动画——ValueAnimator 把「时间进度」经插值器、估值器换算成**具体值逐帧调 setter**，View 的属性真的变了。

**插值器与估值器的分工**：插值器改「时间→进度」的曲线（0~1，加速/回弹的数学）；估值器把「进度」映射成具体值（ArgbEvaluator 管颜色过渡）——**「曲线归插值器、数值归估值器」**两件套可自由组合。

**setX 与 setTranslationX 的坐标系**：x = left + translationX——**left 是 layout 定的「原始位」，translationX 是动画专用的「偏移位」**；动画改 translation 不动 layout（避免每帧重排——动画性能的设计根源），事件分发按 x 算所以点击区域跟手。

**深水区**：属性动画的帧驱动在 **Choreographer 的 ANIMATION 回调队列**（与 VSYNC 节拍绑定，见 3.5）——「动画帧与渲染帧同节拍」是它丝滑的机制根源；**ObjectAnimator 靠反射找 setter**（没有 setter 要手动 setValue 或加注解暴露）；硬件加速下简单动画可提升到 RenderThread 执行（**UI 线程被卡住时动画照跑**——与 WebView 篇的合成动画同一思想）。

**AnimatorSet 的编排**：playTogether/playSequentially + after/before/with 的关系 DSL——「编排是图，不是链」。

收尾：心法，「**补间假移动、属性真 setter、帧序列吃内存**；插值器管曲线、估值器管数值」。

> 面试官追问点：为什么补间动画 translate 后点击还在原地？应答思路：invalidate 只重算绘制矩阵（视觉位置），mLeft/mTop（layout 四边）没变，事件分发按 mLeft/mTop 判定——**「画在哪」和「边界在哪」是两套数据**，属性动画的诞生动机就是消除这个分裂。

# 4.虚拟机与构建体系

#### 4.1 apk的打包流程是什么？三种签名差异在哪

答：一句话定调，**打包是「资源 → 字节码 → dex → 组装 → 对齐签名」的流水线；签名三代的演进主线是「保护范围的扩大」——v1 只保 jar 条目、v2 保整个文件、v3 加密钥轮换**。

**打包流程五步**：aapt2 编译资源（XML → 二进制资源 + 资源索引表，生成 R 类）→ javac/kotlinc 编译成 class → **d8/dex 把 class 合并成 dex**（寄存器式指令 + 方法索引表）→ 资源 + dex + so + assets 组装成 zip → zipalign（对齐）→ apksigner 签名。

**签名三代对照**：
- **v1（JAR 签名）**：META-INF 三个文件（MANIFEST.MF 摘要 → SF → RSA）——**只校验文件条目，zip 的元数据区（注释区等）不在保护范围**——往 zip 注释区塞东西能绕过（Janus 漏洞的攻击面）；
- **v2（APK 签名方案）**：**把整个 apk 按 1MB 分块做全文件校验**（zip 注释区也被覆盖）——防篡改从「条目级」升到「文件级」，且校验一次完成（v1 要逐条目算摘要，安装更快）；
- **v3**：v2 基础上加**密钥轮换链（proof-of-rotation）**——升级签名密钥不用换包名重发包。

**深水区**：v1+v2 同时存在时的坑（旧系统走 v1 校验，被 Janus 式篡改绕过——所以 minSdk ≥ 24 只签 v2/v3 更安全）；**zipalign 必须在 v2 签名之前**（签名后再动 zip 会破坏全文件校验——顺序不是流程洁癖是签名正确性）。

收尾：心法，「**打包五步、签名三代、保护范围逐代扩大**」，v2 全文件校验与顺序约束是加分点。

> 面试官追问点：zipalign 为什么必要？应答思路：把 so 和资源按 4 字节/内存页对齐——运行时 mmap 可以**直接映射使用（零拷贝读取）**；未对齐的数据必须先拷贝进对齐缓冲才能用——「对齐是给 mmap 省一次拷贝」，答出 mmap 才是根。

#### 4.2 Gradle怎么自定义插件？依赖怎么配置

答：一句话定调，**Gradle 的执行模型是「配置阶段建 task 有向无环图 → 执行阶段按图跑」；implementation 与 api 的差异是依赖「是否传染」（下游编译期可见性）——不传染换来的是增量编译的隔离**。

**生命周期**：配置阶段（评估所有 build.gradle、建 task 图）→ 执行阶段（只跑目标 task 及其依赖）——**「配置阶段做的每件事，每次构建都要重付」**，configuration cache（缓存配置结果）与 convention plugin（把公共配置抽成插件）都是对这个阶段的治理。

**implementation vs api**：api 传递依赖（下游模块编译时能看见上游的类——**上游一改，全下游重编**）；implementation 不传递（下游只见本模块的公开 API）——**编译隔离换增量速度**，「面向接口的模块边界」是副产品收益。

**从编译到 apk 的 task 链**：generateR/BuildConfig → aidl/renderscript → 资源合并 mergeResources → javac/kotlinc → **dex 合并（d8）→ mergeAssets → package → 签名**——耗时统计用 --profile / build scan 找大头。

**自定义插件三种形态**：build script 内联（一次性）、buildSrc（仓库内共享）、**convention plugin + version catalog（现代标准——配置也版本化）**；插件本质是 Plugin<Project> 的 apply 往构建里挂 task/改配置。

**深水区**：**transform API 废弃 → AGP 8 的 Instrumentation API**——老 transform 是「全局拦截中间产物」（每个 variant 都跑、无法声明精确输入输出、增量构建失效）；新 API **按类粒度做 ASM 字节码注入、增量友好**——「字节码注入的官方化」也是埋点框架的演进方向。

收尾：心法，「**配置阶段建图、执行阶段跑图；implementation 是编译隔离、convention plugin 是配置复用**」。

> 面试官追问点：为什么 transform 被废弃？应答思路：三个病——全局性（所有 variant 被动参与）、输入输出不精确（增量机制失效，全量重跑）、抢占中间产物（多个 transform 串成责任链但顺序不受控）——新 API 把粒度从「产物」缩到「类」，增量构建的钥匙是「可声明的输入输出」——**「transform 时代慢在增量永远失效」**。

#### 4.3 ClassLoader体系是什么？双亲委派怎么打破

答：一句话定调，**Android 的类加载是 BootClassLoader（系统类）→ PathClassLoader（应用类）的两级链，双亲委派是「先问父亲」的查重协议——打破它的正当理由只有一个：「我要抢在系统前面加载自己的版本」**。

**三兄弟**：PathClassLoader（**已安装 apk 的 dex**，应用默认的类加载器）、DexClassLoader（老版本可指定 optimizedDirectory 加载任意 dex——插件化的基础，8.0 后与 Path 趋同）、InMemoryDexClassLoader（内存 dex，动态化与加固的方向）。

**双亲委派的机制**：loadClass 先交给 parent 找，父亲找不到才 findClass 自己找——**保证 java.lang.String 这种系统类全局唯一**（自定义同名类顶不上去）；Android 的链是 BootClassLoader（framework 类）→ PathClassLoader（app dex）。

**打破与正当性**：**热修复（Tinker）**——把修复后的 dex **插到 PathList 数组的前面**（loadClass 遍历时先命中修复类）——「子优先」的逆序注入；插件化——重写 loadClass 拦截目标类转发到自己的 DexClassLoader。**打破的都是「查找顺序」，不是「安全边界」**（系统类依然被 Boot 锁死）。

**class 与 dex 的差异**：class 是单类文件（**栈式指令集**）；dex 是多 class 合并的注册表格式（**寄存器式指令集**，指令更短但寄存器多）——**方法索引 16 位就是 64K 限制的根源**（见 4.4）。

收尾：心法，「**两级链、先问父亲、打破只为抢先**」——热修复的完整原理（加载时机与重启必要性）见 9.2。

> 面试官追问点：为什么热修复补丁 dex 必须在 app 重启时生效？应答思路：类一经加载就进缓存的 resolvedClass 表，后续同名类直接命中缓存**不会再次查找**——补丁 dex 插入再晚，已加载的类也换不掉——「类加载是一次性拍卖，落槌不反悔」，这是类加载方案必须重启的机制根源。

#### 4.4 Dalvik和ART差在哪？编译模式怎么演进

答：一句话定调，**演进是「解释执行慢 → 纯 AOT 安装慢 → JIT + AOT + Profile 混合」三步——主线是全量编译的税与解释执行的慢之间的折中，最终用「画像」把编译火力集中到热路径**。

**三代演进**：
- **Dalvik（JIT）**：运行时解释 + 热点即时编译——**省安装但每次启动都重新 JIT**（热身慢、费电）；
- **ART 5.0/6.0（纯 AOT）**：安装时 dex2oat 全量编译成机器码——运行飞快，**代价是安装分钟级、双倍存储（dex + oat）、OTA 后全量重编**；
- **ART 7.0+（混合）**：安装只编译关键路径 → 运行时 JIT 热点 + **画像采集（Profile）** → 空闲时后台 AOT 增量补编——**「下次启动用上次的画像」，冷启动越用越快**。

**dexopt 与 dex2oat 的区别**：dexopt 是 Dalvik 时代的优化（odex 还是字节码，verify+optimize）；dex2oat 是 ART 的真编译（**oat/vdex：机器码**）——「优化到编译」的质变；8.0 后 vdex 与 odex 拆分存储（vdex 存验证过的 dex、odex 存机器码）。

**64K 与 multidex**：dex 的方法索引是 16 位（65536 上限）——**单个 dex 方法数炸了就 link 不过**；multidex 的机制：主 dex 装启动必需类（手工 keep），副 dex 运行时在 attachBaseContext 里加载（本身有冷启动成本）；**5.0+ ART 原生多 dex**，legacy multidex 只服务 4.x——但 minSdk 低的项目依然带着这笔税。

**深水区**：Baseline Profile（开发者/云端聚合的画像，安装即 AOT 启动关键路径——**首页路径预编译，冷启动砍 30%+**，Macrobenchmark 是标准工具链）——**「编译火力从拍脑袋全编进化成画像精准打击」**。

收尾：心法，「**AOT 的性能、JIT 的灵活、Profile 的数据**三者融合」——完整口述（含 Profile 引导细节）见 13.4 深度精讲。

> 面试官追问点：为什么 dex 的方法索引要设计成 16 位？应答思路：寄存器式指令集里方法引用是高频操作数，**短索引是为了指令密度**（dex 靠它比 class 更省空间）——代价就是 64K 上限；这是一个「格式大小 vs 引用范围」的取舍，「能讲出设计动机而不是背 65536」就是深水区。

# 5.IPC与Binder

#### 5.1 Binder的原理是什么？一次拷贝怎么实现

答：必问题。一句话定调，**Binder 的定位是「一次拷贝 + 强类型接口（AIDL）+ 驱动背书的进程身份」——mmap 双映射消灭第二次拷贝，UID/PID 由驱动贴上不可伪造，这是它淘汰老 IPC 的性能与安全双代差**。

**为什么不用老 IPC**：管道/Socket 两次拷贝（用户态→内核→用户态）+ 两次上下文切换；共享内存零拷贝但**无同步原语、安全性裸奔**；Binder 是「一次拷贝 + 有同步 + 有身份」的折中。

**一次拷贝的 mmap 实现**：**接收方提前 mmap 一块内核 binder 内存——这块物理页同时映射进内核和接收方用户空间**；发送时驱动只做一次 copy_from_user（发送方用户态 → 内核缓冲区，而它恰好就是接收方的映射区）——**接收方读自己的映射地址就是数据，第二次拷贝消失了**。代价：mmap 区上限约 1MB → **单次传输的体积限制**（TransactionTooLargeException），大数据传 Ashmem 的 fd 走共享内存。

**AIDL 的生成代码**：.aidl 编译成一对——**Stub**（服务端：Binder 服务端，onTransact 里按 code switch 分发到本地方法）+ **Proxy**（客户端：parcel 打包参数 → transact 陷入驱动 → 读回结果）；**oneway 修饰**（异步：不等返回不等执行，靠队列缓冲）。

**ServiceManager 与死亡代理**：ServiceManager 是 **Binder 世界的 DNS**（0 号句柄，addService/getService 都经它）；**死亡代理（DeathRecipient）是驱动提供的服务**——目标进程消亡时驱动回调注册方（客户端监听服务死活做重连，不依赖应用层心跳）。

**跨进程方案选型**：文件/SP（不可靠无同步）→ Messenger（串行低频消息）→ **AIDL（复杂高频接口）**→ ContentProvider（数据共享型，见 1.3.1）→ Socket（跨设备/跨系统）。

收尾：心法，「**一次拷贝靠 mmap、接口强类型靠 AIDL、身份可信靠驱动、大数据走 Ashmem**」——epoll 级的完整链路口述见 13.2 深度精讲。

> 面试官追问点：Zygote 为什么用 Socket 而不用 Binder？应答思路：fork 的瞬间不能有多线程（Binder 线程池会让子进程带着别人的半截事务出生，状态混乱）——Socket 是单线程安全的通信；这是「**机制约束选型**」的典型题，和 13.6 启动链路里 Zygote fork 的细节串起来讲最完整。

# 6.网络、数据与WebView

#### 6.1 网络优化和监控怎么做？如何抓包与防抓包

答：一句话定调，**网络优化按「请求层（少发）→ 传输层（省流）→ 体验层（快反馈）」三层做减法；抓包的原理是「中间人 + 被信任的假证书」，防抓包就是把信任链收回来**。

**优化三层**：请求层——合并请求、CDN 就近、预加载（空闲时预取下一页数据）、缓存策略（ETag/OkHttp Cache 兜底）；传输层——HTTP/2 多路复用、gzip/brotli 压缩、图片 webp 化；体验层——**弱网专项**（超时分级、重试退避、接口降级与本地兜底数据、「先渲染缓存再刷新」的骨架方案）。

**监控**：用 OkHttp 的 **EventListener 把一次请求分解成 DNS / 连接 / TLS / 传输各段耗时**——慢在哪一段一目了然（采集点挂在自定义 EventListener，见 12.3 与 6.2）；成功率、慢请求占比、弱网占比按地区/版本聚合。

**抓包原理与防抓包对照**：抓包三步——设代理 → 设备安装并**信任中间人的自签证书** → 中间人分别与两端握手解密。防抓包三板斧——**证书锁定（SSL Pinning，锁定证书或公钥）**、检测系统代理/VPN 配置并拒绝连接、**target 24+ 默认不信任用户 CA**（release 包天然不可被 Charles 直接抓）。攻防的另一端：Frida hook 绕过锁定、双向校验（客户端也验服务端之外还带私有协议）——**「防抓包是提高成本，不是绝对安全」**。

**深水区**：证书锁定的坑——**锁证书还是锁公钥**：服务端换证书（正常轮换）而公钥不变时，锁公钥的方案不崩——「锁公钥不锁证书」是工程正确姿势；debug 构建信任用户 CA 给 QA 留测试口子，release 锁死——**按构建变体分流信任**。

收尾：心法，「**优化三层减法、监控分段定位、抓包信任链攻防**」。

> 面试官追问点：为什么 target 24 之后 Charles 默认抓不了 HTTPS？应答思路：Android 7.0 起应用默认**只信任系统 CA，不再信任用户安装的 CA**（中间人证书恰恰装在用户区）——这是平台级的防中间人；debug 构建显式配置 networkSecurityConfig 信任用户 CA 才能测——「平台的信任边界收紧」是这题的根。

#### 6.2 OkHttp的责任链设计？连接池怎么复用

答：必问题。一句话定调，**OkHttp 的骨架是「责任链拦截器」——一次请求是一条从重试到 I/O 的链；应用拦截器在链头、网络拦截器在重试之后——位置决定视角**。

**五环责任链**：RetryAndFollowUpInterceptor（**重试与重定向的决策环**）→ BridgeInterceptor（补请求头/处理 cookie/gzip）→ CacheInterceptor（缓存命中与条件请求）→ ConnectInterceptor（**从连接池取或建连接**）→ CallServerInterceptor（真正的 socket I/O）。**每一环只做一件事、依次加工 Request/Response**——这是「责任链」在源码里的教科书应用（对照 12.3 分发器看全貌）。

**两种拦截器的位置差异**：addInterceptor（应用层）——**重定向只跑一次、看到的是最终结果**（适合加签名/埋点/日志）；addNetworkInterceptor（网络层）——**每次实际网络交互都跑**（能看到重定向的每一跳、原始 wire 数据——适合抓包式调试）。面试高频坑：「签名为什么不能加在网络拦截器」——重定向会产生中间请求，签名位置错会重复计算/丢失。

**连接池复用**：ConnectionPool 默认 **5 个空闲连接、5 分钟存活**——**按路由（host+端口+代理）匹配复用**；HTTP/2 之下**一个连接可以并发跑多个请求**（多路复用让「连接数」不再是并发瓶颈）；清理是后台线程的定期巡检 + LRU 驱逐。

**深水区**：DNS 的可替换（Dns 接口——**HttpDNS 防劫持**就是替换实现）；Request 的**不可变设计**（newBuilder 每次产新对象）——多线程共享安全 + 拦截器链上互不污染；**EventListener 是监控的官方采集点**（6.1 的分段耗时全靠它）。

收尾：心法，「**五环一条链、位置定视角、连接按路由复用**」；完整链路与分发器队列见 12.3。

> 面试官追问点：为什么 Request 设计成不可变？应答思路：一次请求可能被多个拦截器串行加工、被多线程读写（异步调用 + 取消）——不可变让「加工」变成「派生新对象」，原请求永不脏；顺带说出「自定义签名拦截器里 newBuilder().header().build() 的写法就是在消费这个设计」。

#### 6.3 Retrofit的原理是什么？动态代理怎么用

答：一句话定调，**Retrofit 是「用动态代理把接口声明翻译成 HTTP 请求」的库——只做翻译不做运输，I/O 全部交给 OkHttp**。

**动态代理的机制**：`retrofit.create(Api::class.java)` 里是 **Proxy.newProxyInstance**——你调接口方法时，invoke 拦截到 **Method 对象**：解析方法上的注解（@GET/@POST/@Query/@Path）+ 参数注解 → 装配成 **ServiceMethod（请求模板：路径、头、参数的组装规则）** → 参数逐个填充 → 生成 okhttp3.Request 交给 OkHttp。**「接口没有实现类却有方法体」的全部秘密就在动态代理**。

**三个可插拔适配器**：**Converter**（响应体 → 对象，Gson/Moshi——数据层的翻译官）；**CallAdapter**（把 Call<T> 换成你要的返回类型——RxJava 的 Observable、**suspend 挂起函数**——「返回类型的工厂」）；这正是「Retrofit 只管翻译」的证据：换适配器就换编程模型，OkHttp 一行不动。

**suspend 函数怎么适配**：挂起方法编译后带 **Continuation 参数**——适配器用 **suspendCancellableCoroutine** 把「挂起恢复」桥接到「阻塞式 enqueue**：协程挂起等回调，响应到了 resume；取消协程 → cancel OkHttp call——「协程的结构化取消」（10.6）传导到网络层的完整链路。

**深水区**：ServiceMethod 按 **Method 缓存（ConcurrentHashMap）**——注解解析一次终身复用（动态代理每次调用都拦截，但翻译模板只建一次）；接口方法不能 private/static（代理生成的是实现类，不可见/不可调——高频追问）。

收尾：心法，「**动态代理拦截方法、注解翻译成模板、两个适配器换数据与模型**」。

> 面试官追问点：Retrofit 为什么不直接做网络请求？应答思路：分层解耦——Retrofit 负责「接口怎么声明」、OkHttp 负责「请求怎么发」——换 HTTP 引擎不动业务接口、换序列化器不动网络层；「一个库只回答一个问题」是开源组件的设计课，答出分层意图比答源码更深。

#### 6.4 五种持久化方案怎么选型？原理差异在哪

答：一句话定调，**选型两问定生死：结构化与否（键值 vs SQL）、同步与否（阻塞 vs 协程）——结构化走 SQLite 系（Room 官方封装），键值按「单进程快（MMKV）/ 协程化（DataStore）/ 老兼容（SP）」选**。

**SP 的三宗罪**：**首次 getXxx 触发全量 loadFromDisk**（整个文件读进内存才返回）；**apply 也是全量写**（改一个键全文件重写，只是挪到子线程）；commit 同步阻塞主线程 + MODE_MULTI_PROCESS 不可靠（已废弃）——「全量」是它的原罪。

**MMKV**：mmap 内存映射（**写入只到内存页，OS 异步回写**——省掉 I/O 等待）、**protobuf 增量追加**（写新键不重写全文件）、多进程支持（文件锁 + CRC 校验）——细节见 12.8 开源库章。

**DataStore**：**协程 Flow 异步化**（所有读写挂起，消除 ANR 风险）、Preference（简单键值）与 Proto（强类型）两种、官方迁移助手 from SharedPreferences——「SP 的正统继任者」。

**SQLite 与 Room**：SQL 的全量能力（查询/事务/索引）；**Room 是编译期封装**——@Dao 的 SQL 在**编译期校验**（拼错表名直接编译失败），生成实现代码；返回 Flow/LiveData 感知变化；GreenDao/WCDB（微信出品，多进程与加密增强）是性能特化路线。

**深水区**：SQLite 的 **WAL 模式**（写日志不阻塞读——「读写并发」的关键开关）；Room 编译期生成的是「你手写的 SQLite 模板代码」，运行时没有魔法。

收尾：心法，「**结构化 SQL、键值看场景、SP 只做兼容**」，一张选型表按「结构化 × 并发 × 进程」三轴画。

> 面试官追问点：为什么 SP 的一次 get 也可能卡？应答思路：get 是「等全量加载」——首次访问触发 loadFromDisk（异步线程读文件），但 getNow 要数据就得 join 等待——**onCreate 里立刻 get 的话，你等的是整个文件解析完**；「改一个键等全文件」是接口语义决定的，与线程无关。

#### 6.5 两种序列化方式差在哪？Parcelable为何快

答：一句话定调，**Serializable 是「反射 + 自描述的通用格式」（慢但可持久化跨语言），Parcelable 是「Android 传输专用的显式协议」（快但只为内存）——一个用通用换性能，一个用场景换性能**。

**Serializable**：JVM 标准机制——**反射遍历全部字段读写**、格式自描述（类结构信息也进流）、支持持久化到磁盘与跨语言边界；**serialVersionUID** 是版本一致性校验（不写则按类结构哈希——改字段反序列化直接崩）。

**Parcelable 为什么快**：** writeToParcel/Creator 是显式手写协议**——写什么读什么都是代码，**没有反射、没有自描述开销**；专为 Binder/Intent 的内存传输设计（序列化结果直接进 Ashmem/映射区，见 5.1）——「**快是砍掉的东西换来的**」：砍了自描述、砍了跨语言、砍了跨设备。

**代价与边界**：Parcelable **不适合磁盘持久化**——格式与类实现强绑定、版本演化脆弱（官方文档明说不建议）；磁盘场景依然 Serializable/JSON/ProtoBuf 的地盘。

**@Parcelize**：编译期生成 writeToParcel/Creator 样板——**协议还是 Parcelable，只是不写了**（Kotlin 编译器插件生成，零运行时差异）。

收尾：心法，「**内存传输 Parcelable、磁盘与跨语言 Serializable/JSON**」，分界线是「要快还是要通用」。

> 面试官追问点：Bundle 里两种都放，为什么 IPC 推荐 Parcelable？应答思路：Binder 单次传输有 1MB 级限制（5.1）——Parcelable 的序列化产物更小（无类结构描述）+ 更快（无反射），在「按字节计价的通道」里优势被放大；顺带一句「Intent 传大对象本身就是反模式，传 id 或走文件/ContentProvider」是工程加分层。

#### 6.6 AsyncTask的原理与不足？替代方案是什么

答：一句话定调，**AsyncTask 是「串行工作线程 + Handler 回主线程」的封装，两大遗产问题——串行排队与生命周期不感知——决定了它的废弃；现代答案是「UI 异步协程、后台任务 WorkManager」两条线**。

**原理**：默认走 **SERIAL_EXECUTOR（串行队列）**——一个任务慢，后面全部排队（要并行得手动 executeOnExecutor(THREAD_POOL_EXECUTOR)，版本行为还改过：1.6 并行、3.0 改串行——「默认行为不稳定」本身就是设计失败）；结果经 **InternalHandler 切回主线程** onPostExecute。

**两大不足的根源**：**生命周期不感知**——AsyncTask 持有 Activity 引用（非静态内部类的隐式持有，见 1.3.2），页面销毁后 onPostExecute 还在跑——泄漏 + 崩溃双杀；**没有取消语义的配合**——cancel 后回调照样可能执行。

**替代方案按场景**：页面内异步（网络请求 → UI）→ **协程 lifecycleScope/ViewModelScope**（结构化取消与生命周期自动对齐——见 10.6）；保证执行的后台任务（上传/同步）→ **WorkManager**（约束感知 + 持久化，见 1.2.1）；串行后台消息 → HandlerThread（见 2.1）。

**深水区**：AsyncTask 的废弃官宣（API 30+）本质是「通用异步框架输给专用工具」——它同时想当「线程池 + 生命周期组件 + UI 桥」，三件事都没做好；**协程的挂起恢复模型把「切线程」变成语法**（withContext），「回主线程」不再是一个环节而是一种写法。

收尾：心法，「**串行排队 + 生命周期失控 = 废弃；页面协程、后台 WorkManager**」。

> 面试官追问点：如果维护老代码里的 AsyncTask，最小改造是什么？应答思路：改 ViewModelScope + suspend 函数（生命周期自动管理）；异步逻辑搬到 Repository 层（UI 层只挂起等结果）——「不是换个 API，是把异步收进结构化并发」，能答出迁移思路说明真用过协程。

#### 6.7 WebView怎么交互与优化？泄漏怎么排查

答：一句话定调，**WebView 三大主题——交互（JSBridge 双向通道）、性能（内核 + 预加载 + 离线包）、稳定（泄漏与崩溃的隔离治理）**。

**交互双向通道**：JS 调 Native——**addJavascriptInterface 注入对象**（4.2 以下反射漏洞的历史事故 + @JavascriptInterface 注解修复）；Native 调 JS——**evaluateJavascript**（带回调拿返回值）；工程化封装是 **JSBridge**（协议 + callbackId 配对 + 队列——通道细节与 06 跨端篇 6.4 同源）。

**内核与兼容**：系统 WebView（可独立更新，版本碎片化）vs **X5（腾讯内核，自带统一版本）**——混合开发的兼容性按「ROM 版本碎片严重程度」决策。

**性能三板斧**：**WebView 池预加载**（启动时先创建好、页面直接取——WebView 初始化是百毫秒级冷启成本）；**离线包**（H5 资源打包下发、拦截资源请求走本地文件——加载速度逼近原生 + 弱网可用）；DNS 与 cookie 预热（首次打开的隐性耗时项）。

**泄漏排查与防御**：泄漏源三件——WebView 用了 Activity Context（改 ApplicationContext 创建）、**内部线程（WebViewCore 等）持有外部引用**（销毁后线程还活着）、注册的 JS 接口对象未清理。防御阶梯：**onDestroy 里先 loadUrl("about:blank") 再 destroy + 手动从视图树摘除**（不保证根治）→ **终极方案：独立进程跑 WebView**——泄漏被进程边界关住、内核 native 崩溃不拖死主进程、退出页面杀进程内存立即归还——「**用进程边界买隔离**」。

收尾：心法，「**交互双向通道、性能预热加离线、稳定靠进程隔离**」。

> 面试官追问点：为什么很多大厂把 WebView 放独立进程？应答思路：三笔账——泄漏账（WebView 的泄漏面复杂到无法根治，进程退出全额归还）、崩溃账（内核 native crash 只杀子进程，主进程无感）、内存账（WebView 内存占用大，页面退出 kill 进程立即释放）——**「治理不了就把爆炸半径缩小」**是这道题的工程思维内核。

# 7.图片与内存

#### 7.1 图片加载全链路怎么做？如何减少内存占用

答：一句话定调，**图片内存优化的主线是「让解码后的位图匹配显示尺寸」——原始尺寸是设计稿的事，屏幕上只需要显示尺寸那么多像素；全链路按「加载前算账 → 加载中采样 → 加载后治理」三段布防**。

**内存怎么算**：宽 × 高 × 每像素字节数——**ARGB_8888 每像素 4 字节**（默认）：一张 1080×1920 的图 ≈ 8MB——「内存大头永远是位图」是图片治理的出发点。

**加载前算账**：**不加载就能读边界**——BitmapFactory.Options 的 **inJustDecodeBounds = true** 只解析出宽高不分配像素内存——「先量尺寸再决定怎么装」。

**加载中采样**：**inSampleSize 采样解码**——按「显示尺寸 / 原始尺寸」算 2 的幂次采样比（**采样比只取 2 的幂**——解码器按行跳读，非 2 幀无加速收益）；格式选择——**RGB_565 无透明通道场景砍一半内存**（每像素 2 字节）；**BitmapFactory 的区域解码 BitmapRegionDecoder** 支撑超大长图（按视口取块解码，配合 12.2 的 Glide 大图方案）。

**加载后治理**：大图检测（加载前后 dump 尺寸与显示尺寸对比，超标告警——上线兜底）；圆角处理的路线对比——**BitmapShader 画圆角**（shader 裁剪，不产新位图）优于裁切新 Bitmap（省一次分配，与 13.8 的 BitmapPool 哲学一致）。

**深水区**：**dpi 的坑**——drawable 不同 dpi 目录的图解码尺寸不同（hdpi 的图在 xxhdpi 设备按 2 倍缩放解码——**内存翻 4 倍**，「大图放错目录」是真实的 OOM 事故源）；**同一张图不同尺寸加载产物不同**（缓存 key 含尺寸，见 12.2/13.8）。

收尾：心法，「**先读边界再采样、格式按需选、圆角用 shader、目录按 dpi**」。

> 面试官追问点：inSampleSize 为什么只取 2 的幂？应答思路：解码器对 2 的幂可以做「行/列等距跳读」（直接跳过整行整列的解码计算），任意比例的采样要逐像素插值反而更慢——**「省内存的前提是不添计算」，工程优化从不做负优化**。

#### 7.2 Glide缓存机制是什么？生命周期怎么感知

答：必问题。一句话定调，**Glide 的缓存是「四级漏斗」（活动资源 → 内存 LRU → 磁盘 → 网络），生命周期感知靠「无 UI 的寄生 Fragment 挂载请求」，Bitmap 池化把分配也消灭——三级优化各管一段：查得快、挂得住、分得省**。

**四级漏斗**：**ActiveResources（弱引用表，正在显示的）**——与内存缓存分离的妙处：**LRU 内存紧张清掉的不会影响正在显示的**（强引用保命、弱引用只做索引）；**MemoryCache（LruResourceCache，上限按屏幕自适应）**；**磁盘缓存分 SOURCE（原图）/RESULT（变换后）两套**——「圆角缩放的结果单存，二次加载跳过解码和变换」；网络最小优先。

**生命周期感知的实现**：**Glide.with(fragment) 往 FragmentManager 塞一个无 UI 的 SupportRequestManagerFragment**——RequestManager 监听它的生命周期：onStop 挂起在途请求、onDestroy 取消并清引用——「**页面销毁请求自动取消**不是魔法，是透明 Fragment 做代理观察者」（Lifecycle 组件出现前的经典黑科技）。

**Bitmap 池化**：**LruBitmapPool 配合 inBitmap 复用**——解码临时内存从池里借、用完还（API 19+ 允许尺寸不精确匹配的复用）——**「加载图片零 GC」**是低端机流畅的最大贡献（GC 抖动是列表卡顿大户）。

**深水区**：**缓存 key 的组成**（url + 签名 + 宽高 + 变换——「同图不同尺寸不同 key」的命中率陷阱）；RequestManager 按 Fragment/Activity 维度隔离（with 的重载决定请求挂在谁的生命周期上）。

收尾：心法，「**四级漏斗、寄生 Fragment、Bitmap 池**」——完整源码级口述见 13.8 深度精讲；加载链路与超大图见 12.2。

> 面试官追问点：为什么 with(context) 和 with(fragment) 的请求命运不同？应答思路：with 的参数决定「请求挂载的宿主」——Application 作用域的请求不随页面销毁（活到进程级，适合预加载），Fragment 作用域随页面走（防泄漏防过期）——「**选宿主就是选生命周期**」，用错重载要么泄漏要么提前取消。

#### 7.3 Bitmap内存怎么计算？采样加载怎么做

答：一句话定调，**Bitmap 的内存账是「宽 × 高 × 像素字节」三因子，但宽高不是图片文件的宽高——是「解码后」的宽高，dpi 缩放、采样、inBitmap 三件事都在动这个账本**。

**基础账**：ARGB_8888（4 字节/像素，默认）、RGB_565（2 字节，无透明）、ALPHA_8（1 字节）——**一张 4000×3000 的照片 ARGB_8888 解码 = 48MB**，这就是「加载原图直接 OOM」的算术。

**宽高会被谁改**：一，**dpi 缩放**——drawable 目录与设备 dpi 不匹配时，解码宽高按倍率缩放（drawable-hdpi 的图在 xxhdpi 设备按 480/240 = **2 倍**放大解码——**内存翻 4 倍**）；二，**inSampleSize**——每翻一倍宽高各除二（内存除四）；三，targetDensity（Glide 按 Target 尺寸下采样）。

**采样的标准流程**（手写必会）：inJustDecodeBounds 读原始宽高 → 按期望尺寸算 inSampleSize（循环 `while (h/s > reqH || w/s > reqW) s *= 2`）→ 关闭 justDecodeBounds、带着 inSampleSize 真解码——「**两次解码：第一次量尺寸，第二次装数据**」。

**深水区**：**inBitmap 的复用**——把一块已有 Bitmap 的内存直接给新解码用（要求 API 19+ 且字节够大）——Glide 的池化就是它的工业化封装（见 7.2）；**BitmapFactory vs ImageDecoder**（API 28+ 的现代 API——解码即裁剪/圆角一步完成，硬件位图支持）；**硬件位图（HARDWARE 配置）**——像素存显存不占 Java 堆，绘制更快但不可读写像素（不能再 Canvas 加工）。

收尾：心法，「**三因子算账、两件事动宽高（dpi 与采样）、两次解码是标准姿势**」。

> 面试官追问点：硬件位图为什么省内存还有人不敢用？应答思路：它把像素挪到显存（Java 堆统计里消失，GC 压力骤减），但**不可逆操作**——读像素、Canvas 重绘、传给需要 Bitmap 的老 API 全会崩；「共享元素动画 + 磁盘缓存序列化」场景是重灾区——**省内存的收益与失去的灵活性要按使用场景称重**。

#### 7.4 内存泄漏怎么排查治理？监控方案怎么设计

答：一句话定调，**排查是「对比堆快照找只增不减的引用链」，治理按「长生命周期持有短生命周期」的源头分类，线上监控用「弱引用 + 触发式 dump」把成本花在可疑处**。

**排查三步法（线下）：Memory Profiler**：操作疑似路径（开关页面/往返）→ 拍堆快照对比 → **看 Retained Size 只增不减的对象 → 引用链找 holder**。**LeakCanary 的判定机制**——WeakReference + ReferenceQueue 的「GC 见证」：销毁回调时弱引用观察，主动 GC 后队列里没出现 = 被强引用着 = 泄漏（完整四步见 13.5）；**Shark 解析 hprof 出最短引用链**，几秒出报告。

**泄漏源分类治理**（按持有方）：**静态/单例持 Context**（换 ApplicationContext，见 1.3.2）；**非静态内部类的隐式持有**（Handler/AsyncTask——静态内部类 + WeakReference；kotlin 用内部 lambda 同样隐式捕获）；**注册不反注册**（广播/观察者——onDestroy 配对）；**资源未关**（Cursor/Stream——try-finally 或 use 扩展）；**WebView 的复杂泄漏面**（进程隔离兜底，见 6.7）。

**线上监控的设计**（工程克制）：**全量 dump 是 stop the world 数秒**——线上不能这么玩；标准方案是「**阈值触发 + 增量 dump + 子进程 dump**」（koom 的路线）：内存涨速异常才采样、只 dump 泄漏关联区域、dump 挪出主进程——**「线下深诊断、线上轻埋点」**。

**深水区**：内存基线的建立（启动后/首页稳定态的 PSS 常态值——偏离基线才报警，比绝对阈值科学）；**GC 后内存仍在涨**才是泄漏的信号（一次涨不一定是泄漏，可能是缓存正当扩张）——「**趋势比快照诚实**」（与 3.5 流畅度的方差口径同一哲学）。

收尾：心法，「**线下快照对比、源头分类治理、线上阈值触发**」。

> 面试官追问点：为什么「泄漏了一定 OOM」这句话不对？应答思路：泄漏是「该回收的没回收」，OOM 是「分配时空间不够」——小泄漏在低频路径上可能永远到不了 OOM 的量级；监控的意义正是「在 OOM 之前用趋势发现它」——**「泄漏是病，OOM 是病危通知」，两者不是同一件事**。

#### 7.5 OOM是怎么产生的？场景监控与治理方案

答：一句话定调，**OOM 是「分配的瞬间没有连续空间」——它可能是内存真满了，也可能是「单次申请超限」（Bitmap 太大）、甚至「文件描述符耗尽伪装的 OOM」；治理按场景分诊，监控按「分位数趋势」预警**。

**三类产生场景**：一，**堆内累计**——泄漏积累到上限（7.4 的长线治理）；二，**单次大分配**——原图解码（7.3 的采样治理）、「一次加载整段 JSON/列表全量数据」；三，**非堆的伪装者**——**fd 耗尽（Too many open files 报的也是 OOM）**、线程数耗尽、native 内存（WebView/so 层）把进程总内存顶到上限（Java 堆没满但进程被 LMK 盯上）——「**OOM 不全是 Java 堆的事**」。

**分场景治理**：位图——采样 + 池化 + RGB_565（7.1/7.3）；数据——分页加载 + 流式解析；native——进程隔离（6.7）+ so 侧的分配追踪（malloc 调试）；fd——Cursor/Stream 的生命周期配对治理（7.4 的资源类）。

**监控方案**：**OOM 前的预警**——内存水位（PSS 趋势 + 涨速）、**Debug.getMemoryInfo 拿各分区（Java 堆/native/pss）**按版本聚合看分位；**OOM 现场的保留**——崩溃时 dump（子进程）+ 「崩溃前最后 N 秒的内存事件流」（大对象分配记录）；**FD 监控**——/proc/self/fd 定期清点，逼近上限告警。

**深水区**：**onTrimMemory 的分级响应**（TRIM_MEMORY_UI_HIDDEN 起逐级加码——清缓存、池缩容）——「系统给应用的内存压力广播，响应它比扛着它体面」；**大内存的低端机降级**（按 deviceMemoryClass 决定缓存上限/原图策略）——「按设备的内存阶级定制体验」。

收尾：心法，「**OOM 分三类诊（累计/单次/伪装）、监控看趋势、治理配场景**」。

> 面试官追问点：为什么加了大堆（largeHeap）还是 OOM？应答思路：largeHeap 抬高的是 Java 堆上限，对三类场景只救「堆内累计」一类——native 内存、fd、单次超大分配（超上限的 Bitmap 照样崩）一概无效；**「加堆是延长期限不是治病」**，方案该治源头（采样/分页/关资源），能分清「救急与治病」就是工程分界线。

# 8.性能优化与稳定性

#### 8.1 崩溃是怎么产生的？治理降级方案有哪些

答：一句话定调，**崩溃分两条线：Java 崩溃是「未捕获异常沿调用栈到顶」、Native 崩溃是「信号触发进程终止」——治理是「捕获 → 归因 → 修复」三级跳，降级是「崩溃前的最后防线」**。

**两条产生线**：Java——异常抛到 Thread 的顶层无人接住，Runtime 通知 defaultUncaughtExceptionHandler 后进程退出——**捕获手段：setDefaultUncaughtExceptionHandler 里 dump 堆栈 + 上报**；Native——SIGSEGV/SIGABRT 等信号触发，**捕获手段：注册信号处理函数写 minidump**（breakpad/xcrash），信号处理函数里能做的事极其有限（async-signal-safe——所以只能写文件不能打日志）。

**治理三步**：捕获（上述两线）→ **归因**——堆栈符号还原（native 要 so 符号表，与 4.1 的构建产物管理打通）、**崩溃指纹聚类**（同因崩溃去重排 Top）→ 修复（业务修复或热修复——9.2）。

**降级防线**：关键路径 try-catch 兜底 UI（防「一崩全黑」）、**安全模式**——启动时检测连续崩溃自动进降级配置（关动画/关 WebP/砍特性，把 app 从崩溃循环里捞出来）、崩溃率门禁（灰度版本超阈值禁全量——8.5）。

**深水区**：捕获链的「临终遗言」语义——handler 处理完要把流程**交回系统让进程正常退出**，不交回就是「假活」（下次崩溃又进来，死循环）；「捕获的意义是现场保留不是续命」。

收尾：心法，「**Java 拦异常、Native 拦信号、归因靠聚类、降级进安全模式**」。

> 面试官追问点：为什么捕获了崩溃 app 还是会死？应答思路：uncaughtHandler 是「进程退出前的回调」，不是「异常回收器」——真正要续命得自己重启进程（崩溃后拉起另一个进程，被系统判定恶意也会被清）；能分清「保留现场」和「阻止死亡」是这题的分界线。

#### 8.2 ANR产生的原理是什么？信息怎么分析治理

答：一句话定调，**ANR 是「特定消息在超时窗口内没处理完」——本质是主线程消息排队超时（13.1/13.6 的机制层），四类场景不同阈值、同源机制**。

**四类场景与阈值**：input 5s（触摸事件没人处理）、broadcast 10s（onReceive 卡死）、service 20s（生命周期回调超时）、provider publish 10s——**计时方是系统进程（AMS/system_server），不是应用自己**——所以 ANR 的判定应用拦不住，只能「不超时」。

**机制层还原**：生命周期与广播全是主线程消息——**前一个消息堵住（IO/锁/计算），后面的生命周期消息排队**——「超时未处理」= 排队超时；这也解释了治理方向全是「主线程减负」。

**信息收集与分析**：系统侧——**/data/anr/traces.txt**（ANR 时刻全部线程的栈 + 锁状态 + 持锁者）、DropBox、bugreport；应用侧——**线上 APM 的 Watchdog**：子线程周期向主线程 post 标记消息，**迟迟没被执行说明主线程被占**——主动 dump 自己的栈（比系统 traces 更快更全——系统只在 ANR 后才写）。**分析三步**：看主线程栈在干什么（锁等待？IO？计算？）→ 看它等的锁被谁持有（traces 里的 held by）→ 对照时间线定位元凶消息。

**治理**：主线程禁 IO/禁锁（StrictMode 检测）、Application 瘦身（1.3.3）、onReceive 里只转手（重活交 goAsync 的 pendingResult 或 WorkManager）。

收尾：心法，「**计时在系统、超时在排队、分析看栈找锁、治理给主线程减负**」。

> 面试官追问点：ANR 和卡顿（8.3）什么关系？应答思路：卡顿是「主线程忙」的现象（一帧超时），ANR 是「忙到系统判定失责」的法律后果（特定消息超时）——短卡顿永远到不了 ANR，长卡顿必然是 ANR 的前奏；Watchdog 和 Matrix 的监控原理同源（都是「探测消息多久被执行」），答出「现象与判定」的层次即可。

#### 8.3 卡顿原因怎么定位？监控和治理方案怎么设计

答：一句话定调，**卡顿是「单帧超时」（渲染耗时 > 屏幕周期）——定位按「一帧的时间花在哪」拆解（输入/动画/measure/layout/draw/合成），监控分「帧间隔统计」与「消息耗时打点」两条技术路线**。

**原因三类**：主线程被占（GC 抖动/锁/IO——最常见的「别人的锅」）；布局太深（measure/layout 递归全树——3.4）；绘制太重（过度绘制、大位图——7.1）。

**监控两条路线**：一，**Choreographer 帧间隔**（postFrameCallback 数 doFrame 间隔 vs 屏幕周期——**渲染帧率视角**，见 3.5）；二，**Looper Printer 消息打点**（setMessageLogging：消息开始/结束打标记，单条消息超阈值判卡顿——**「元凶消息」视角**，Matrix 的路线，见 13.5）——前者告诉你「掉了多少帧」，后者告诉你「哪条消息干的」。

**卡顿现场的抓取难点**：卡顿发生时抓一次栈，大概率抓到的是「路过的无辜函数」（元凶可能已经跑完）——**解法是重复采样拼「时间切片栈」**（卡顿窗口内每 N ms 采一次，聚合出高频出现的函数——Matrix 的 LazyScheduler）——「单次栈会撒谎，切片栈才诚实」。

**治理**：按拆解结果对症——消息元凶（异步化/拆分）、布局（3.4 三板斧）、图片（7.1 采样）；**列表卡顿的三级排查模板**：bind 耗时（数据计算挪异步/DiffUtil）→ 布局层级（扁平化）→ 图片解码（采样 + 池化——13.3/13.8）。

收尾：心法，「**一帧拆解定位、两条路线监控、切片栈抓现场、三级模板治列表**」。

> 面试官追问点：线上怎么把卡顿归因到具体代码？应答思路：消息打点拿到「元凶消息的开始时间与耗时」+ 同窗口的切片栈聚合出「高频函数」——两份数据按指纹聚合成 Top 卡顿堆栈（离线符号还原）；**「归因 = 定位消息 × 聚合栈」两个证据链交叉**，单靠任何一边都是猜测。

#### 8.4 App启动怎么优化？页面打开耗时怎么统计

答：一句话定调，**启动优化的框架是「先定义口径再谈优化」——T0 到 T1 的耗时统计（fork 到真正可交互），治理按「进程初始化 → 首帧渲染 → 数据依赖」三段归因，手段按依赖关系拓扑展开**。

**耗时统计的口径**：线下——Perfetto 看进程创建到首帧的每一道工序（8.8）；线上——**reportFullyDrawn() 手动打「真正可交互」点**（首页数据到位 + 首帧渲染完成的业务口径，而不是「显示了空壳」）——「**指标口径定义了优化的天花板**」，用 reportFullyDrawn 而不是 onWindowFocusChanged 是这道题的态度分。

**治理三段归因**：进程初始化——**Application.onCreate 与 Provider 的隐藏成本**（1.3.1 的「每个 Provider 启动时都被创建」）；首帧渲染——布局层级（3.4）、首页图片（7.1）、异步 inflate；数据依赖——**首页数据并行预取**（进程启动即发请求，不等首页 onCreate）。

**手段清单**：延迟初始化（懒加载）、**启动任务框架（DAG 拓扑排序——把「能并行的并行、有依赖的按序」自动化**）、闪屏窗主题适配（windowBackground 消白屏——1.3.3）、**Baseline Profile**（13.4 的编译画像，冷启动砍 30%+）。

**深水区**：StrictMode 检测启动期主线程 IO（diskRead/diskWrite 罚日志）；**「全异步」的幻觉**——任务间有依赖（推送依赖通道、通道依赖网络），**无视依赖的全异步只是把串行挪了个地方**，拓扑排序才是正解。

收尾：心法，「**口径先行（reportFullyDrawn）、三段归因、拓扑并行、Profile 兜底**」。

> 面试官追问点：怎么证明你的启动优化有效？应答思路：线上分版本对比 T1 分位值（P50/P90——不是均值，与 3.5 同理），**控制变量**（同机型分布、同地区），灰度版本看回归——「优化不量化等于没优化」，能主动报出「对比口径」是资深信号。

#### 8.5 稳定性做了哪些优化？量化收益怎么证明

答：一句话定调，**稳定性的答法要有三层：指标体系（崩溃率/ANR 率/泄漏检出率）、专项治理（Top 聚类/OOM 专项/疑难 hook）、量化闭环（版本对比 + 灰度门禁的数字）——没有数字的稳定性工作等于没做**。

**指标体系**：崩溃率两个口径——**用户级（崩溃用户数/日活）**（体验口径，大用户量的重灾区最醒目）与**次数级**（技术口径，单人多次崩溃别被用户数稀释）；ANR 率、卡顿率（8.2/8.3 的产出）、泄漏检出率（LeakCanary 线下）——**指标必须归一化到日活/启动数**才有可比性。

**专项治理三板斧**：**Top 崩溃聚类**（崩溃指纹去重——8.1，Top10 治理完再排下一批，滚动清零）；**OOM 专项**（7.5 的三类分诊）；**疑难杂症的 hook 兜底**——厂商 ROM 差异（某机型系统组件的坑用 hook 系统类绕过）、第三方 SDK 的补丁注入（4.2 的字节码注入是 hook 的现代载体）。

**量化闭环**：治理前后**版本对比**（崩溃率从 X 降到 Y，附机型/场景下钻）；**灰度门禁**——灰度版本崩溃率超基线阈值自动禁全量（把稳定性从「事后复盘」变成「事前闸门」）；换算成业务成本（崩溃导致的留存/客服量——「技术指标翻译成钱」是最有说服力的汇报）。

**深水区**：**「稳定性是统计学」**——新版本崩溃率波动要问样本量与置信区间（小流量灰度的偏差可能比治理效果还大）；防回归机制（崩溃修复配自动化回归用例 + 监控告警——「修了不加防是不完整的闭环」）。

收尾：心法，「**指标归一化、专项滚动治、门禁前置、收益翻译成业务语言**」。

> 面试官追问点：说一个你完整闭环的稳定性专项？应答思路：结构化讲「发现（监控告警）→ 归因（堆栈聚类 + 线下复现）→ 修复（业务改/hook 兜底/热修）→ 防回归（用例 + 门禁）→ 收益（版本对比数字）」五步——面试官要的是「闭环的完整性」而不是「问题难度」。

#### 8.6 线程怎么统一优化治理？CPU排查怎么做

答：一句话定调，**线程治理的核心动作是「收编」——统一创建入口（命名/优先级/异常兜底）、按用途分池（IO 池大 CPU 池小）、异步按「要不要生命周期、要不要约束」选工具**。

**现状病三件**：各处 new Thread 无命名（traces 里全是 Thread-123——排查时没法对号）；**线程数爆炸**（每线程默认 ~1MB 栈内存，几十个野线程就是几十 MB）；**优先级乱**（后台任务抢主线程时间片——卡顿的隐形元凶）。

**收编三板斧**：统一线程工厂——**命名 + uncaughtExceptionHandler + 优先级**在一处收口（traces 里能叫出名字的线程才是好线程）；按用途分池——**IO 密集开大池（阻塞型，64 上限够用）、CPU 密集开小池（核数为准）**——与协程 Dispatchers.IO/Default 的设计同构（10.6）；第三方库的线程监控（OkHttp/Glide 各自有池——全量 task 清点把「别人家的线程」也纳入账本）。

**CPU 排查**：**/proc/self/task 遍历各线程的 utime/stime**（线上高 CPU 时的主动采样——哪根线程在烧 CPU）；对应的栈 dump（谁烧的 + 在干什么）；线下 Perfetto 的 **CPU 泳道**（8.8——每核上跑的线程与调度延迟一目了然）。

**异步方式谱系**：Thread（原始）→ HandlerThread（串行后台——2.1）→ 线程池 → **协程（结构化并发，10.6）** → **WorkManager（要约束要保证执行的，1.2.1）**——「按需求选工具而不是按习惯选」。

收尾：心法，「**入口收编、按池分工、CPU 看账本、异步按需求选型**」。

> 面试官追问点：线程数是越少越好吗？应答思路：IO 阻塞型任务多线程是「用内存换吞吐」的正当交易（64 个线程等 IO 比排 4 个队快）；CPU 密集型多过核数就是纯开销（上下文切换税）——**「多少合适」的答案在负载类型里，不在一个数字里**，能按负载分型回答就到位。

#### 8.7 系统为什么会杀进程？回收的优先级怎么排

答：一句话定调，**系统杀进程按「进程优先级（oom_adj）+ 内存压力」两轴决策——adj 越高越先死（前台几乎不死、空进程最先死），切后台 adj 升高 + Doze 冻结就是「后台易被杀」的全部机制**。

**进程五级与 adj**：前台（可见/正在交互）→ 可见（被遮挡部分）→ 服务（有 startService 在跑）→ 缓存（后台 Activity 的缓存）→ 空进程（只剩壳复用）——**oom_adj 数值从低到高，LMK（lowmemorykiller/lmkd）内存吃紧时从 adj 高的开始杀**——「优先级是系统对『谁对用户重要』的记账」。

**切后台为什么易被杀**：Activity 不可见 → 进程降为 cached 级（adj 升高）→ 内存压力一来它就在候选名单前排；**Doze 模式再叠加冻结**（CPU/网络受限）——「后台保活对抗系统的路是死路」（1.2.1），**正确姿势是接受被杀 + 恢复现场**：状态存档（onSaveInstanceState）、任务补跑（WorkManager 持久化）、拉活靠系统调度（推送/AlarmManager）而不是自己拉自己。

**深水区**：**adj 的动态联动——bindService 的隐藏语义**：系统把「被绑定」视为强依赖，**绑方进程活着，被绑进程的 adj 被拉平到同级**（不能比依赖者先死）——「保活的合法通道是让系统认为有依赖」（前台服务绑通知、与系统服务交互都是这个机制的正当用法）；多进程架构里主/子进程相互拉 adj 是隐形耦合（子进程 bind 主进程时谁死谁活要设计）。

收尾：心法，「**adj 定生死、后台必然降级、保活走依赖、恢复靠存档**」。

> 面试官追问点：为什么有的 app 后台很久不死？应答思路：三个机制叠加——前台服务（合法的常驻声明）、被系统或前台进程 bind（adj 拉平）、播放/定位这类「用户可感知」的状态让系统不敢杀（杀了通知栏还挂着就是事故）——**「活得久的后台不是对抗出来的，是让系统认为杀了影响体验」**——能答出机制而不是「用了保活 SDK」就到位。

#### 8.8 四大性能工具怎么解读？各自的原理是什么

答：一句话定调，**四件工具按「拦截点 + 判定信号 + 证据采集」三件套理解——Perfetto 是系统级时间线、LeakCanary 是弱引用见证、Matrix 是消息打点加切片栈、线上 APM 是轻埋点聚合——没有全能工具，只有按阶段选工具**。

**Perfetto/Systrace**：系统与应用的全视角时间线——**CPU 泳道（每核在跑什么线程）、渲染帧泳道（每帧的 measure/layout/draw 工序与超时红块）、锁与调度的延迟**——「一帧的时间里系统在干什么」全在这张图上；Perfetto 是 Systrace 的继任（SQL 查询 + 长时间录制）；**解读口诀：先看红块在哪条泳道，再看那段时间谁在 CPU 上跑**——它答的是「现场全景」（8.3/8.4 的线下武器）。

**LeakCanary**：弱引用 + ReferenceQueue 的 GC 见证机制——**观察表里的弱引用「GC 后还活着 = 有强引用拖着 = 泄漏」**，dump 后 Shark 解析出最短引用链（完整四步与 7.4 的排查法、13.5 的深讲）。

**Matrix 卡顿监控**：**Looper Printer 的消息 start/end 打点**（定位元凶消息）+ **卡顿窗口内的重复采样拼「时间切片栈」**（单次栈会撒谎——8.3 的难点）——线上卡顿归因的标准范式。

**线上 APM 的克制**：全量 dump/全量 trace 在线上是自毁——**采样、聚合、按版本分位**是三原则；「**线下深诊断、线上轻埋点**」的分工（8.1/8.2/8.3 的线上侧全部遵循）——监控本身不能成为性能问题。

收尾：心法，「**Perfetto 看全景、LeakCanary 管泄漏、Matrix 抓卡顿现场、APM 做线上聚合**」——监控类工具的通用套路（拦截点/信号/证据）见 13.5 深度精讲。

> 面试官追问点：为什么 LeakCanary 只能线下用？应答思路：它要「主动 GC + 全量 dump + 解析引用链」——dump 是 stop the world 数秒（线上用户直接卡死），解析在移动端也曾 OOM（Shark 之前的 HAHA 库时代）——**「诊断的深度和运行的代价成正比」，线上只能采样轻量版（7.4 的 koom 路线）**——答出成本结构就是工具选型的深水区。

# 9.安全与热修复

#### 9.1 安全防御怎么落地？Xposed原理是什么

答：一句话定调，**安全防御是三道墙：传输层（防抓包）、运行层（防 hook/防调试）、业务层（防篡改防逆向）；Xposed 的原理是「替换 ART 方法的执行入口」——把方法的 native 入口指针换成一个跳板函数**。

**三道墙的分工**：传输层——SSL Pinning + 代理检测（抓包原理与攻防细节在 6.1 已深讲，此处一句带过）；运行层——**反调试**（ptrace 自附加检测、调试器标志）、**hook 检测**（检测关键类的方法入口是否被换、检测 xposed 的类与 so 是否已加载）、**完整性校验**（签名校验防二次打包、so 校验防注入）；业务层——**关键逻辑服务端化**（客户端只留展示，破解了也没有可偷的逻辑）、代码混淆（ProGuard/R8 混淆 + native 化核心算法）——「**客户端永远是不可信环境，安全的核心是把秘密放在服务端**」。

**Xposed 的两层机制**：一，**寄生方式**——替换 app_process（Zygote 的真身），**Zygote 启动时注入 hook 框架 → 所有 fork 出的应用进程天生带着 hook 出生**——「污染源头」是它能 hook 一切的原因（对照 8.7 的 Zygote fork）；二，**hook 实现**——ART 上修改 **ArtMethod 的 entry_point（方法入口指针）**，指向自己的跳板函数，跳板里先跑 hook 回调再调原实现——「调用方无感的方法偷换」；Magisk 时代的 LSPosed（Riru/Zygisk 注入）是同一思想的现代实现。

**反 Xposed 的对应**：检测已加载的 xposedBridge 类名、检测方法 entry 与预期不符（关键方法校验入口）、核心逻辑走 native/服务端——**「hook 与反 hook 是同一块内存的攻防」**。

**深水区**：Frida 是另一条路线——**运行时把 JS 引擎注进目标进程**（不依赖 Zygote，进程活着就能注入，hook 任意 native 函数）；字节码注入（4.2 的 Instrumentation API）是「合法的 hook」——编译期植入 vs 运行期偷换，手段相同时机不同。

收尾：心法，「**三道墙按「传输/运行/业务」纵深布防，hook 的本质是入口指针偷换，秘密永远放服务端**」。

> 面试官追问点：为什么 Xposed 能 hook 所有 app？应答思路：它住在 Zygote 里——所有应用进程都是 Zygote fork 的孩子（13.6），孩子天生继承父亲的注入——**「与其 hook 一万个进程，不如 hook 它们的父亲」**；答出「源头污染」的杠杆思维就到位。

#### 9.2 热修复的原理是什么？类加载怎么实现修复

答：一句话定调，**热修复三条路线——类加载（换 dex，要重启但兼容性最好）、底层替换（换方法入口指针，即时生效但脆弱）、资源/so 替换——与插件化的差异是「体内换血 vs 体外挂载」，两者共享 dex 注入与资源加载两个底座**。

**类加载路线（Tinker 类）**：补丁 dex 与原 dex 的差异合成 → **插到 PathList 队列最前面**（4.3 的「逆序注入」）→ 类加载时先命中修复类。**生效前提：类还没被解析**（「类加载是一次性拍卖」——已加载的类命中缓存不重查）——**所以必须重启**；优势是全平台兼容（只用官方加载机制）、补丁可以很大（整个类重发）。

**底层替换路线（AndFix 类）**：**直接替换已加载方法的 ArtMethod 入口/字段**（方法级热替换，不用重启、即时生效）；缺陷——**ArtMethod 的内存布局随 ART 版本变**（每个版本结构体不同，offset 硬编码，ROM 碎片化下随时崩）——「**在别人的内存布局上施工**」是它被边缘化的根本原因；Sophix 的工程化是「替换优先、失败降级类加载」的中间派。

**插件化的对照**：插件化是**体外挂载**——DexClassLoader 加载外部 apk 的 dex + **资源加载的难题**（自己 new AssetManager 并 addAssetPath 注入插件资源路径，解决资源 ID 冲突与引用）；热修复是**体内换血**（替换已有的类与资源）——「两者技术上互为表里，工程目标不同」。

**深水区**：资源热修的难点——运行时替换 Resources（new 一个塞回 Activity 的 mResources，且 ID 分配要避开冲突）；so 修复是 System.load 重新指向 + native 层的符号地址更新。

收尾：心法，「**类加载换血要重启、方法替换快但脆弱、资源与 so 各有专门通道**」。

> 面试官追问点：为什么 Tinker 要重启而 AndFix 不用？应答思路：类加载方案的生效窗口在「类被解析之前」（插队只在拍卖开始前有意义）；方法替换动的是「已加载类的执行入口」——不依赖加载时序，所以即时生效；**「两条路线的差异本质是『修改加载时序』还是『修改已加载结构』」**——答出这个对比维度就是深水区。

# 10.架构与新技术

#### 10.1 组件化模块间怎么通信？ARouter原理是什么

答：一句话定调，**组件化通信分两族——页面跳转走路由表（字符串解耦类引用），服务调用走接口下沉（接口放公共层、实现在业务层运行时发现）——两族的共同原则是「模块间不直接依赖」**。

**页面跳转（路由）**：ARouter 的机制——**编译期 APT 扫描 @Route 注解生成路由表**（ARouter$$Group 类），运行时按组懒加载进 Warehouse 缓存，跳转时查表反射创建目标（完整机制见 12.5）——「**字符串路由把编译期的类依赖换成运行时的表查找**」：模块 A 不 import 模块 B 的任何类，也能跳到 B 的页面。

**服务与数据（接口下沉）**：跨模块的方法调用不能只靠路由——**「api 模块」模式**：接口定义放公共 api 模块（全员可见），实现藏在业务模块，ARouter 的 **IProvider 服务发现**做运行时定位——「编译期只依赖抽象、运行时再找实现」（对照依赖倒置原则）。

**事件与数据同步**：跨模块事件用总线（LiveData/SharedFlow 的全局容器）或事件总线——注意「全局事件」的治理（谁发谁收要可追溯，滥用总线是组件化的反面）。

**深水区**：组件化的根基是 Gradle 多模块的依赖治理（4.2）——「**组件化是工程问题不是技术问题**」：模块边界、依赖方向（业务模块不许互相依赖、只许依赖 api）、独立编译与独立运行（壳工程 + 组件可单独成 app 调试）。

收尾：心法，「**页面走路由、服务走接口下沉、事件收口全局总线、依赖只许指向抽象**」。

> 面试官追问点：字符串路由比 Intent 的类引用好在哪？代价是什么？应答思路：好——编译期零类依赖（可独立编译/跳转可配置/拦截器可插拔）；代价——**路径写错要到运行时才炸**（没有编译期校验）——「用运行时校验换编译期解耦」，理解成「路由表是弱化版的接口契约」就通了。

#### 10.2 四种架构模式的演进？各自数据流向是什么

答：一句话定调，**演进主线是「解耦谁和谁」：MVP 解耦 View 和逻辑（接口回调）、MVVM 解耦数据和视图（观察者自动同步）、MVI 把状态和事件单循环化——三代是耦合治理粒度的进化，不是追新**。

**MVC 的原罪**：Activity 既是 View 又是 Controller（XML 只是个壳）——「上帝 Activity」的病根；**MVP 的药**：Presenter 持 View 接口、逻辑全进 Presenter——可测性暴涨；**代价**：接口爆炸 + 异步回来 View 已销毁的判空地狱。

**MVVM 的换轨**：Presenter 的「主动调 View 方法」换成「暴露可观察的数据」——**View 订阅 ViewModel 的 LiveData/StateFlow，数据变了 UI 自动刷**（「数据驱动」替代「命令驱动」）；**ViewModel 与 DataBinding 的配合**——DataBinding 是「观察者的 XML 糖」（表达式层自动订阅更新），现代写法已经弱化 DataBinding、直接在代码里订阅。

**MVI 的收敛**：单一数据源（UiState 不可变）+ 单一意图入口（所有用户行为统一成 Intent）+ **单向数据流（send(intent) → reduce → 新 State → render）**——「状态 = f(intent, 前状态)」的纯函数化，可追溯可回放；代价是样板代码。

**单向数据流的理解**：数据永远「向下流」（state → UI）、事件永远「向上流」（UI → intent → reduce）——**「UI 永远是状态的投影」**是这四个模式的公共终点，MVI 只是把它推到极致。

收尾：完整口述版（每代解决上一代什么痛、引入什么新痛）见 13.9 深度精讲。

> 面试官追问点：MVI 为什么适合状态复杂的页面？应答思路：多 LiveData 的「多入口叠加」让最终状态难以推理（13.9 深水区）——MVI 把「状态怎么变」收敛成一条 reduce 链，**「可推理性」是它花样板代码买的最大资产**；简单页面用 MVVM 就够——「架构选型是对状态复杂度的匹配」。

#### 10.3 Jetpack组件原理？Lifecycle怎么实现

答：一句话定调，**Jetpack 组件的公共底座是「生命周期感知」——Lifecycle 把「生命周期的回调」变成「可订阅的事件流」，ViewModel/LiveData/WorkManager 全是它上面的上层建筑**。

**Lifecycle 的实现**：**LifecycleRegistry 维护 Event/State 两套状态机**（ON_CREATE → ON_RESUME...的事件序列、INITIALIZED → DESTROYED 的状态层级），广播给所有观察者；**感知的实现是 ReportFragment**——无 UI 的透明 Fragment 挂进 Activity 转发生命周期（**与 Glide 的寄生 Fragment 同一思想——13.8**；Lifecycle 出现后 Glide、协程的 lifecycleScope 都改用了官方感知）。

**ViewModel 的跨配置存活**：存在 Activity 的 **ViewModelStore**（配置变更时 Activity 重建、Store 由 ActivityThread 保留移交，真销毁才清空）——「比 Activity 活得长的非静态无泄漏容器」。

**LiveData**：观察者 + 生命周期感知 + 版本号去重（细节陷阱见 10.4）；**Room**：编译期校验 SQL 的 SQLite 封装（6.4）；**WorkManager**：约束感知 + 持久化的任务调度（1.2.1）——注意它是「保证执行」的场景不是「立刻执行」；**Navigation**：单 Activity 多 Fragment 的路由栈管理（参数安全传递、回退栈可控）。

**深水区**：**为什么全家桶都长在 Lifecycle 上**——「忘记取消订阅」是所有异步组件的人祸根源（7.4 的泄漏大户）——**把生命周期变成可订阅的流，让每个组件自己绑定自己**（协程的 lifecycleScope 就是这套思想的终态：作用域即生命周期）。

收尾：心法，「**Lifecycle 是底座、寄生 Fragment 是感知的实现、全家桶是订阅者**」。

> 面试官追问点：ViewModel 为什么不用静态单例实现「活得比 Activity 长」？应答思路：静态的生命周期是进程级（永不清 = 泄漏），ViewModelStore 的存活是「配置变更级」——**存活窗口精确匹配业务需求（转屏不丢、退出即清）**；「存活时长的精确性」才是设计目标，能答出这个就超过背原理。

#### 10.4 LiveData有哪些陷阱？粘性事件怎么解决

答：一句话定调，**LiveData 的四个陷阱全来自「版本号去重 + 主线程约束 + 粘性回放」三个设计决定的副作用——每个坑的解法都是对设计意图的还原**。

**陷阱一：连续 set 相同数据收到几次**：**一次**——观察者带 mVersion，分发时比较「数据版本 > 观察者版本」才通知——**「值语义的去重」（状态是幂等的，相同状态不重放是正确设计）**。

**陷阱二：连续 postValue 相同数据**：**可能丢中间值**——postValue 用「mPending 标志 + 锁」保证只往主线程 post 一次 Runnable——**多次 post 在主线程真正执行前到达的话，只有最后一次的值被广播**（「最后值语义」——后台线程连续计数用它必丢）。

**陷阱三：线程约束**：observe 必须主线程（checkMainThread 直接抛）、setValue 必须主线程、**postValue 任意线程**（内部 Handler 切主线程）——「observe 里创建的包装对象要正确挂到主线程的生命周期上」是约束的根源。

**陷阱四：粘性事件**：新观察者注册立刻收到「注册前的最后值」（版本回放）——**事故场景**：一次性事件（弹 toast/跳转）在页面 B 注册时被重放（A 的旧事件又炸一次）；**解法三代**——SingleLiveEvent（单次事件约定）、**Event wrapper（消费标记：数据包一层「是否已读」，观察者读后置位）**、**SharedFlow（replay = 0——现代正解）**。

**深水区**：**粘性不是 bug 是「状态语义」**——LiveData 建模的是「状态」（迟到的订阅者拿到当前状态是正确的），事故发生在「拿状态容器装事件」——**「事件与状态的建模错配」才是根因**，答出这层就是设计层的理解。

收尾：心法，「**去重看版本、postValue 是最后值、observe/set 主线程、粘性治本换 SharedFlow**」。

> 面试官追问点：为什么 LiveData 的粘性是设计而不是缺陷？应答思路：状态是幂等的——「当前值」对任何时刻的订阅者都有效（页面转屏重建后恢复数据全靠粘性）；事件是瞬时的——重放等于事故；**「用状态容器发事件」才是用法错误**——能分清「值语义/事件语义」两个建模维度就是深水区。

#### 10.5 Compose与Flutter差在哪？怎么选型

答：一句话定调，**两者共享「声明式 + 状态驱动」的意识形态，分岔在运行环境的产权——Compose 住在 Android 的 View 生态里（可互操作、渲染走系统管线），Flutter 自带引擎（跨端像素级一致）——「一个是升级装修、一个是另起炉灶」**。

**声明式与命令式的分野**：命令式——自己 setX/setText（UI 是「操作的累积结果」，状态散在代码各处）；声明式——**UI = f(state)**，状态变了框架自动算新 UI——「**UI 从此只是状态的投影**」（10.2 单向数据流的 UI 版）。

**Compose 的三件核心**：**重组（recomposition）**——状态变化只重跑「读了该状态的 Composable」（粒度到函数）；**remember/derivedStateOf**——跨重组的记忆（remember 缓存对象、derivedStateOf 收敛依赖防止过度重组）——**「重组是声明式的税，记忆化是治理手段」**；**副作用 API**——LaunchedEffect 把副作用绑定「组合的生命周期」（key 变了重启协程——生命周期感知在声明式世界的新形态）。

**Modifier 链的原理**：**不是集合是嵌套**——每个 Modifier 是「包装器工厂」，链式调用逐层包裹（padding 先后顺序影响视觉结果的根源——外 padding 与内 padding 是不同的嵌套顺序）。

**渲染管线对比**：Compose 的终点是 Android 的 RenderNode/RenderThread（**系统管线的原住民**，与 View 世界无缝互操作——一个页面里混用 View 与 Composable 是官方支持的）；**Flutter 自带 Skia/Impeller**——不依赖系统控件（像素级跨端一致，代价是包体积与「和平台风格的割裂感」——6.5 的产权视角）。

**选型**：需要与现有 View 工程渐进共存/团队 Kotlin 化 → Compose；强跨端一致/团队已有 Dart → Flutter——「**按生态产权和迁移成本选，不是按 API 好看选**」。

收尾：心法，「**同一意识形态、不同产权边界；Compose 赢在互操作、Flutter 赢在一致性**」。

> 面试官追问点：Compose 的重组为什么可能引发性能问题？应答思路：状态读取粒度设计不当（大 Composable 读了高频状态——每次输入都整块重组）——治理三件：**状态下沉（读取点收窄）、derivedStateOf（读的是「依赖变化」而不是「源状态」）、不可变集合**——「重组是税，设计的税制很重要」是这道题的总结句。

#### 10.6 Kotlin协程原理是什么？挂起函数怎么实现

答：一句话定调，**协程是「编译器生成的回调扁平化」+「结构化的生命周期树」——挂起不阻塞线程（让出）、创建成本从 MB 级栈到 KB 级对象；基础层答「三件套与挂起语义」，源码级深讲见 13.10**。

**与线程的三处本质差异**：**挂起不阻塞**——线程被释放去跑别的协程（「等待的是协程不是线程」）；**成本**——线程默认 ~1MB 栈（8.6 的线程治理成本），协程是堆上对象（KB 级，十万并发无压力）；**结构化**——协程天然长在作用域树上（取消/异常沿树传播，10.7 的取消传播）。

**挂起函数的原理（一层）**：编译器把 `suspend fun` 做 **CPS 变换**（结果走 Continuation 回调）+ **状态机化**（挂起点之间是 when(label) 跳转表，局部变量提升为字段）——「**挂起 = 存现场并让出，恢复 = 回调带参续跑**」；**挂起不一定真切线程**（同步完成的假挂起直接返回）——完整状态机还原见 13.10 深度精讲。

**三件套**：**Scope**——生命周期的容器（ViewModelScope/lifecycleScope——作用域即生命周期，10.3 的终态）；**Job**——树形结构（父取消级联子、子异常冒泡取消兄弟）；**Dispatchers**——「恢复的地点」（IO 弹性池/Default 核数池/Main 是 Handler 转发）。

**Flow 与 RxJava 的对照**：**背压的语义差异**——RxJava 是推式（生产快过消费要选策略，12.4）；**Flow 是拉式冷流**——消费端挂起，生产端自然停下（「背压不存在，因为拉式天然同步」）；热流场景（事件总线/状态）用 SharedFlow/StateFlow（replay/scope 两参数定语义——10.4 粘性事件的正解）。

收尾：心法，「**挂起是编译期魔法、结构化是运行时组织、Flow 用拉式消灭背压**」。

> 面试官追问点：为什么 Flow 是冷流而 SharedFlow 是热流？应答思路：冷流「每次收集重新执行生产逻辑」（一对一，像函数调用）；热流「生产与消费解耦、接入即广播」（像 LiveData 的粘性语义——replay 参数决定给新订阅者回放几个）——**「冷热的选择 = 生产要不要跟随消费」**，答出这组对偶即到位。

#### 10.7 Kotlin高频语法有哪些？扩展函数怎么实现

答：一句话定调，**Kotlin 高频考点的底层是「编译器干了三件事」——作用域函数是 lambda 的语法糖、扩展函数是静态方法、by lazy 是编译器生成的双检锁——糖在编译期全部还原成 Java 可懂的样子**。

**作用域函数五兄弟一张表**：两轴——上下文（`it` 还是 `this`）与返回（返回自身还是结果）：let/also（it；let 返回结果、also 返回自身）、run/apply（this；run 返回结果、apply 返回自身）、with（非扩展的 run）——**「构造后配置用 apply、判空转换用 let」是实战口诀**。

**扩展函数的真相**：**编译成「接收者为第一参数的静态方法」**——所以：不能被子类覆写（没有虚分派）、不能被反射当成员找、**静态解析**（调用哪个看编译期类型不看运行时）——「**编译期糖不能骗运行时**」；空安全扩展（String? 上的扩展——判空在编译期）是它的合理用法。

**密封类与枚举**：密封类是「子类受限的类族」（when 全覆盖 + **每个子类可携带不同字段**——对 Result 的 Success(data)/Error(e) 建模）；枚举是「单例常量集合」（字段结构统一）——**「数据结构不同用密封类、纯常量用枚举」**。

**inline 与 reified**：inline 把函数体贴进调用处——**lambda 的对象分配与跨调用的开销被消除**（高阶函数的税）；**reified 只能在 inline 函数里用**——泛型擦除后类型不在了，但**贴进调用处的代码能看到真实类型**（`T::class.java` 直接拿）——「reified 是借内联的窗口对抗泛型擦除」。

**by lazy 的原理**：委托生成「synchronized 双检锁 + 首次计算存字段」的等价代码；自定义委托实现 getValue/setValue（属性访问的编译期翻译）。

**深水区**：**协程作用域的取消传播**——结构化的「父取消级联子」是作用域函数树形管理的延伸（10.6），Kotlin 的语言设施（作用域/委托/内联）恰好都是协程语义的地基——「语言特性和并发模型是配套设计的」。

收尾：心法，「**糖编译期还原：作用域是 lambda、扩展是静态、lazy 是双检锁**」。

> 面试官追问点：扩展函数能被 override 吗？应答思路：不能——静态方法没有虚分派表项，子类「同签名扩展」只是另一个静态函数（调用哪个由编译期类型决定）——「想多态就老老实实写成员或用接口」；能答「静态解析」这个根就到位。

# 11.高频手写题

#### 11.1 Android四个高频手写？思路要点是什么

答：一句话定调，**手写题的判卷标准从来不是「能跑」，是「数据结构 + 时序」——每题背「一个骨架 + 一个失分点」，先报结构再写代码**。

**手写 Handler 简化版**：数据结构——**按 when 排序的链表 + 一把锁**（Message 带 next）；骨架——MessageQueue.enqueueMessage 有序插入 + Looper 的 `for(;;)` 取队头执行；失分点两个——**延迟消息的有序插入**（新消息按时间找位置，不是尾插）与 **线程安全**（synchronized 入队 + wait/notify 阻塞唤醒——对照 09 篇生产者消费者的锁语义）。

**手写事件分发伪代码**：三段递归——ViewGroup.dispatch：**先问 onIntercept**（true 走自己的 onTouchEvent，false 遍历子 View 递归 dispatch）→ 孩子都不接、自己 onTouchEvent 兜底；失分点——**「DOWN 定终身」的序列粘性**（DOWN 拍板后，后续 MOVE/UP 直投消费者不再竞标——13.7 的稳定锚）——伪代码里要有个「记录 mTarget」的成员。

**手写 ViewCacheExtension**：场景——「特定 position 的强约束复用」（系统四级缓存不满足的自定义需求）；骨架——自建 `Map<position, View>` + getViewForPosition 钩子里查表返回 + **滑动后失效回收**；失分点——忘配 setItemViewCacheSize 的配合语义（13.3 的层级关系要先理清）。

**手写热修复类加载器思路**：骨架——反射拿 PathList 的 dexElements 数组 → **补丁 dex 数组 + 原数组拼接（补丁在前）** → set 回去；时机——attachBaseContext（4.3 的「拍卖开始前插队」）；失分点——**忘了多 ClassLoader 的宿主场景**（宿主和插件各一套 PathList，插错宿主无效）。

收尾：口述策略——**每题先讲「我的数据结构是什么」再动手**，「先报结构」本身就是加分项（面试官听的是你的建模过程）。

> 面试官追问点：手写 Handler 怎么支持「一个队列多个生产者」？应答思路：入队方法加 synchronized（多个线程的 enqueueMessage 互斥）+ next() 在锁内 wait（空队列睡、入队 notify）——**「锁管生产消费两端，通知管阻塞唤醒」**；能主动讲并发语义（而不是写完才补线程安全）就是这题的资深分。

# 12.开源库高频问题

#### 12.1 EventBus的原理是什么？线程怎么切换

答：一句话定调，**EventBus 是「方法引用的注册表」——register 时收集 @Subscribe 方法建表，post 按事件类型查表分发；线程切换是「分发时按线程模型换执行环境」——三个 Poster 各管一种投递方式**。

**注册与收集**：register 遍历订阅者类找 @Subscribe 方法——3.x 默认**反射扫描**（慢），官方优化是 **APT 索引（SubscriberInfoIndex）**——编译期生成「类 → 订阅方法」的查找表，运行时零反射——「**注解处理器的三板斧之一：把运行时反射编译期化**」（与 ARouter/Hilt 同一思想，见 12.5/12.6）。

**post 的分发流程**：事件对象 → `subscriptionsByEventType` 查出订阅者列表（**按优先级排序**，高优先级可 cancelEventDelivery 终止后续）→ 逐个反射 invoke——「**事件类型就是查表的 key**」（这也是「同名泛型擦除后事件收不到」这类坑的根源）。

**线程切换的实现**：四种线程模型对三个 Poster——**HandlerPoster（主线程 Handler，MAIN）**、**BackgroundPoster（队列串行，BACKGROUND）**、**AsyncPoster（每任务一个线程池提交，ASYNC）**；POSTING 直接在 post 调用线程同步执行——「**线程模型决定的是 invoke 在哪个环境跑，事件本体不变**」。

**粘性与泄漏**：postSticky 存进 stickyEvents Map，**新 register 时查表补发最近事件**（粘性回放，与 10.4 LiveData 粘性同因——「状态语义」）；**Subscription 持有订阅者实例**——unregister 忘调就是泄漏（「注册型组件的反注册纪律」与 1.2.2/7.4 同源）。

**深水区**：EventBus 的被替代不是功能问题而是**可追溯性**——发送方与接收方无显式连接（IDE 找不到调用链），全局事件多了就是「隐式耦合地狱」；组件化时代的替代：LiveData/SharedFlow 的**作用域收口**（事件至少有宿主）。

收尾：心法，「**反射/索引收集、类型查表分发、三个 Poster 切线程、粘性是状态语义**」。

> 面试官追问点：register 为什么必须传实例而不能传类？应答思路：订阅方法的 invoke 需要接收者对象（反射 invoke(obj, args)）——注册的本质是「**方法引用 + 实例**」的绑定；这也是泄漏的根源：表持有实例、实例持有页面——「注册表是 GC Root 链」答出来就是内存安全层。

#### 12.2 Glide的完整加载流程？缓存key怎么生成

答：一句话定调，**加载链路是「with 管生命周期 → into 建 Request → key 生成 → Engine 过四级缓存 → DecodeJob 执行」；缓存 key 的设计原则只有一条——「一切影响最终位图的输入都必须进 key」**。

**完整链路**：`Glide.with(context)`——创建/复用 RequestManager（**绑定寄生 Fragment 拿生命周期**——13.8 深讲）；`asBitmap().load(url)`——RequestBuilder 收集参数；`into(target)`——生成 SingleRequest 并 begin → **Engine.load(key, …)** 进缓存漏斗与任务调度（内存命中直接回调、未命中发起 DecodeJob）。

**缓存 key 的组成**：**EngineKey = url + 签名 + 宽高 + 变换 + options**——「**任何改变解码产物的参数都要进 key，否则命中就是错误复用**」；这就是「同图不同尺寸 = 不同 key」（7.2 的命中率陷阱）和 **signature 机制**（url 不变内容变时——服务端换图、头像更新——用签名强制失效）的设计依据。

**执行侧**：DecodeJob 按数据源走「磁盘 RESULT → SOURCE 网络取」→ 解码（**下采样按 Target 尺寸**）→ **Transformation（圆角/模糊）→ 产物回写缓存**——变换后的结果单独缓存（RESULT 级），二次加载跳过解码和变换。

**三个专项能力**：超大图——**BitmapRegionDecoder 区域解码**（按视口取块，配合长图控件）；**inBitmap 复用**——解码内存从 LruBitmapPool 借还（「加载零 GC」——13.8）；Gif 与视频帧——解码器插拔（Registry 注册制——Glide 可定制性的核心）。

收尾：心法，「**with 管生命周期、key 管一致性、Engine 管漏斗、Registry 管扩展**」——四级缓存与池化的源码级口述见 13.8。

> 面试官追问点：为什么 url 相同却要提供 signature 机制？应答思路：url 是「地址」不是「内容」——服务端在同一个 url 下换了图，key 不变缓存就永远旧——**signature 是「把内容版本编译进 key」的逃生通道**；能答出「key 的合法性依赖输入完备」这层设计因果就是深水区。

#### 12.3 OkHttp分发器怎么调度？完整链路怎么走

答：一句话定调，**Dispatcher 是「异步请求的限流调度器」——ready/running/promoted 三个队列配 64/每主机 5 两个阀门；同步请求不走调度（自己占线程自担阻塞）——「限流是异步请求的待遇」**。

**调度机制**：enqueue → 先进 **readyAsyncCalls** 排队；promote 的条件——**运行中总数 < 64 && 该主机运行数 < 5** → 挪进 runningAsyncCalls 并提交线程池；每个请求 finished 时从 running 摘除、**ready 队头依次 promote**——「**完成一个放进来一个**」的滚动窗口。

**两种限制的用意**：总量 64——防线程池无谓膨胀（线程上下文切换税——8.6）；**每主机 5——防单目标占满连接饿死其它主机**（公平性阀门）——「限流的两把尺：总量防过载、分主机防独占」。

**完整链路一句话**：请求先经 Dispatcher 的门（异步）→ **拦截器五环链**（重试 → 桥接 → 缓存 → 连接 → 服务端，6.2 深讲）→ 连接层——**ConnectionPool 默认 5 空闲/5 分钟存活**、按路由复用、后台线程定期 LRU 清理 socket；HTTP/2 多路复用让「一个连接并发多请求」（连接数需求骤减——每主机 5 的限制实质在放宽）。

**深水区**：**同步 execute 不进 Dispatcher 队列**（直接在调用线程跑完整链）——但 runningSyncCalls 有登记（便于批量 cancel）——「调度管的是异步的排队，登记管的是取消的可达」；**EventListener 的每个回调点都对应链路的一道工序**（6.1 的分段监控挂在这）。

收尾：心法，「**三队列滚动窗口、两把限流尺、同步请求只登记不排队**」。

> 面试官追问点：为什么每主机限制是 5？应答思路：这是 HTTP/1.1 时代「并发数 = 连接数」的经验值（浏览器同款限制）；HTTP/2 一个连接就能跑满并发——限制的实际意义从「物理连接保护」变成「单目标的公平性配额」——「**数字是时代的产物，语义随协议演进**」，能答出这层就是深水区。

#### 12.4 RxJava线程怎么切换？背压策略怎么选

答：一句话定调，**线程切换的本质是「订阅链上的换轨点」——subscribeOn 决定「生产从哪个线程启动」（只有第一个生效）、observeOn 在链上插「换轨站」（可多次）；背压是推式流的先天问题，五种策略是「下游处理不完时上游怎么办」的契约**。

**调度器的本质**：Scheduler = Worker 的工厂——io（缓存线程池，弹性）、computation（固定核数）、main（Android 的 Handler 转发）——「**调度器是「执行环境的抽象」，Worker 才是干活的**」。

**subscribeOn 只生效一次的原理**：订阅动作是「自下而上沿链传播的一瞬间行为」——**最靠近数据源的那个 subscribeOn 把「向上的传播」接到目标线程上，更上游的订阅代码已经跑在那个线程里**——再写多少个都被短路；observeOn 不同——它在链上插一个「把下游回调 post 到目标线程」的中转站——**每个 observeOn 都是一个站**。

**背压与 Flowable 五策略**：Observable 无背压（发射不管下游死活）；**Flowable 的契约是 request(n)**——下游声明「我还能收多少」；策略按「积压怎么办」选——**BUFFER**（无界缓冲，OOM 风险）、**DROP**（丢弃）、**LATEST**（只留最新）、**ERROR**（超限抛异常——「宁可失败不可膨胀」）、**MISSING**（自己处理）——「**策略是契约不是参数，选错语义是线上事故**」。

**与协程 Flow 的对比**：Flowable 的背压要「策略配置」，**Flow 的背压是语义自带的**（挂起即拉式——消费不快生产自然停，10.6）——「RxJava 用策略解决推式的过速、Flow 用拉式消灭过速本身」；选型：存量 RxJava 维护、多操作符复杂流水线 → RxJava；新项目协程生态 → Flow。

收尾：心法，「**订阅向上传、切换向下投；subscribeOn 定产地、observeOn 设驿站；背压选型先读契约**」。

> 面试官追问点：为什么 observeOn 可以多次而 subscribeOn 只有一次？应答思路：订阅是「一次性的向上建链」（沿链传播一回就完——第一次换轨后后面都在那）；数据是「持续性的向下流动」——每个 observeOn 都能拦截「下一次事件往哪个线程投」——**「建链是一次动作、流动是持续过程」决定了两者的次数语义**。

#### 12.5 ARouter路由表怎么生成？怎么跨模块跳转

答：一句话定调，**ARouter 是「编译期生成路由表 + 运行期懒加载查表」的两段式——编译期 APT 把 @Route 收集成 Group 类，运行期首次跨组跳转才加载组表；参数注入、拦截器、服务发现是查表机制的三个扩展**。

**编译期（表怎么来）**：APT 扫描注解生成三类代码——**ARouter$$Root**（组名 → 组的索引，「目录」）、**ARouter$$Group$$xxx**（组内 path → 类的映射表，「页码」）、**@Autowired 生成的 xxx$$Autowired**（参数注入器，「快递单」）——「**注册从反射/运行时挪到编译期**」（12.1 的同一三板斧）。

**运行期（表怎么用）**：init 只加载 Root（知道有哪些组）；**首次访问某组才加载对应 Group 进 Warehouse 缓存**——懒加载的设计动机：全量路由表的「类加载 + 反射创建」都在启动关键路径上——「**启动期只买目录，跳转时才买货**」（1.3.3 的启动治理视角）。

**跳转的三步**：navigation(path) → 查 Group 表定位目标类 → **反射创建** → **@Autowired 参数注入**（Intent 的 Bundle 桥接——受 Bundle 类型限制的参数走 SerializationService 序列化过渡）。

**拦截器与服务**：**IInterceptor 按 priority 组成跳转路径上的责任链**（登录校验、埋点插拔——「路由的责任链」）；**IProvider 服务发现**与路由同表——**返回的实例缓存复用**（服务即单例）——跨模块方法调用的底层（10.1 的接口下沉）。

**深水区**：拦截器在**路由表加载前就注册**（跳转必经），且跨模块的拦截器靠 gradle 插件自动合并——「编译期产物的跨模块聚合」是组件化基建的通用难题。

收尾：心法，「**编译期造目录、运行期懒加载、跳转三步（查表/反射/注参）、拦截器是路由的责任链**」。

> 面试官追问点：路由表为什么要懒加载而不是 init 全建好？应答思路：表项的构建成本 = 类加载 + 反射（每条几十毫秒级），全量预建会挤占启动（1.3.3 的两把刀全被它挡道）；懒加载把成本摊到「真正用到时」——**「启动优化与组件化基建的博弈」是这个设计的真实背景**。

#### 12.6 Hilt依赖注入的原理？编译期生成了什么

答：一句话定调，**Dagger2 是「编译期解依赖图的代码生成器」——注解声明图的节点和边，生成的是「零反射的手工装配代码」；Hilt 是官方把 Android 的组件生命周期预置进图里，把 Component 样板收编**。

**编译期三步**：声明——**@Inject 构造器**（「这个类型的依赖从这里来」）、**@Module + @Provides**（第三方类没有构造权时的工厂）；连图——**@Component**（把所有依赖连成图并**校验：缺绑定直接编译失败**）；生成——xxx_Factory（每个 @Inject 类一个）+ xxx_Impl（Component 的实现，装配链是**纯 new 的调用序**）——「**编译期就证明图是通的，线上没有「装配失败」**」。

**限定符与作用域**：@Named/@Qualifier——同类型多实现的区分（「图的边要有名字」）；**作用域注解（@Singleton/@ActivityRetained）的真相是「实例挂在哪个 Component 上」**——Singleton 挂 Application 级组件（进程单例）、ActivityRetained 挂转屏存活的组件（10.3 的 ViewModel 同窗口）——「**作用域 = 生命周期归属的声明**」。

**Hilt 对 Dagger 的封装**：Dagger 要手写 Component 树（Application → Activity → Fragment 各自建），Hilt **预置了 Android 的组件树** + @AndroidEntryPoint 入口注解自动生成接入代码——「**把「每个项目重复搭的架子」标准化进库**」。

**与 Koin 的取舍**：Koin 是**运行时 Service Locator**（DSL 注册、运行时查找）——上手快、无代码生成；代价——**缺依赖运行时才炸**（Dagger 在编译期就拦住）+ 运行时查找的微量开销——「**编译期图校验 vs 运行时注册表**」是两家的分水岭，选型按团队对「编译期安全」的估值。

收尾：心法，「**注解声明图、编译期校验、生成纯 new、作用域即归属**」。

> 面试官追问点：为什么叫「依赖注入」而不是「高级工厂」？应答思路：工厂是「调用方主动要」；注入是「**容器沿图装配，控制权反转给图**」——构造函数只声明「我需要什么」，谁造、怎么造、造几个全在图里；「控制反转」的落点是**依赖的决策权从业务代码挪到装配层**——答出所有权转移就到位。

#### 12.7 Coil和Glide怎么选型？各自差异是什么

答：一句话定调，**Coil 是「协程时代的图片库」——生命周期感知从寄生 Fragment 换成协程作用域、取消即作用域取消；Glide 是「功能全面的老将」——生态、池化、定制面宽——选型按「技术栈一致性 vs 功能覆盖面」**。

**Coil 的三处本质差异**：
- **生命周期 = 协程作用域**——load 挂在 lifecycleScope/ViewModelScope 上，**页面销毁作用域取消 → 请求自动停**（「寄生 Fragment 的现代替代」——13.8 对照；与 10.6 协程结构化同一机制）；
- **全链路协程**——load 是挂起函数、支持 suspend 的自定义 fetcher/decoder（**扩展点也是协程 API**——写自定义加载器和写业务代码同一语言）；
- **默认关掉 Bitmap 池**——Android O 后大堆与并行 GC 让分配回收变便宜，**池化的收益撑不起它的复杂度**——「优化要对当前的成本结构」。

**Glide 的护城河**：功能覆盖面（巨图/视频帧/复杂变换/多格式）、**Registry 的解码器插拔体系**（12.2——可定制性的架构）、十年生态（各种奇形怪状场景的现成答案）。

**选型依据**：新 Kotlin 项目、全链路已协程化 → **Coil**（技术栈一致性：取消、异常、并发的语义全统一）；重度图片业务、老工程渐进迁移 → **Glide**（成熟度与文档）；「**按栈选而不是按跑分选**」。

**深水区**：Coil 的内存占用优势来源——**代码量小（方法数少）+ 默认不池化（峰值低）**；Glide 的对象图大（RequestBuilder/Engine/多级任务）是「功能全面」的另一面——「**功能密度的税**」。

收尾：心法，「**Coil 赢在一致性（协程栈）、Glide 赢在覆盖面（生态）**」。

> 面试官追问点：Coil 为什么敢不做 Bitmap 池？应答思路：池化解决的是「高频分配 → GC 抖动」（13.8 的低端机哲学）——Android O 起 GC 并行化、分配路径优化，**分配的税降了**；池的复杂度（尺寸匹配、并发借还、失效）是恒定的——「**收益随平台进步递减、成本恒定，砍掉是理性的**」——能答出「优化要看平台成本结构的变化」就是深水区。

#### 12.8 MMKV为什么比SP快？mmap的原理是什么

答：一句话定调，**MMKV 快在两刀各砍掉 SP 的一个「全量」——mmap 让「写」停在内存页（OS 异步刷盘），增量追加让「写」不再重排整个文件；SP 慢在「读要全量加载、写要全量落盘」的双全量**。

**mmap 的原理**：把文件映射进进程地址空间——**写入就是 memcpy 到内存页**，操作系统的 writeback 机制异步刷盘——「**应用视角的写是内存级的**」；对照 SP：commit 是「同步全量写盘」（阻塞主线程）、apply 是「异步全量写」（还是全量，只是挪走）——「**mmap 消灭的是「等盘」**」。

**增量追加的文件结构**：**protobuf 编码的 key-value 追加写**——写新值 = 文件尾 append（旧值成为垃圾，**读取时按「后者覆盖前者」取最新**）；文件翻倍扩容；**垃圾占比超阈值触发全量重写**（MMKV 的 GC 时机）——「**单键的写成本从 O(文件) 降到 O(值)**」。

**崩溃与断电的边界**：进程崩溃**不丢**（内核页缓存还在，下一个进程映射同文件可见）；**断电可能丢最后一段**（writeback 时机由 OS 决定）——「性能换的是最后几秒的持久性」——对 KV 配置类数据是可接受的取舍。

**多进程支持**：**文件锁串行化并发写 + CRC 校验 + 校验失败读临时备份重试**——多进程的正确性三件套；每进程独立 mmap，锁保证可见性顺序。

**对比与迁移**：DataStore 协程化但不 mmap（写速度差一档）；MMKV 的代价——**全量加载进内存**（大文件内存开销，与 SP 同病）+ 键值结构无查询能力（结构化数据仍然归 SQLite 系——6.4 的选型三轴）；SP 迁移有官方 importFrom。

收尾：心法，「**mmap 砍「等盘」、追加砍「重排」、断电丢尾换写速**」。

> 面试官追问点：mmap 断电丢数据，为什么大家还用它？应答思路：持久性的分级——「进程崩溃不丢」mmap 免费拿到（页缓存在内核）；「断电不丢」需要 fsync 级强刷（性能回到 commit 时代）；KV 配置的写入频率与丢失容忍决定了「**要崩溃级不要断电级**」是理性选择——「持久性是分级的，按业务买档位」答出分级思维就到位。

# 13.深度精讲（Framework核心机制口述版）

> 说明：本章是核心题的口述版深度精讲，讲到 Framework 源码与运行机制层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

#### 13.1 Handler机制完整链路？阻塞唤醒怎么实现

答：一句话定调，**Handler 机制是「单线程消息队列 + epoll 阻塞唤醒」的线程通信模型，MessageQueue 的 nativePollOnce 就是整条链路的心脏**。

**四件套的关系先理清**：**Looper 是线程级的单例**（ThreadLocal 存储，一个线程只有一个），**MessageQueue 是 Looper 的字段**（一对一），**Handler 是 MessageQueue 的「投递口加处理回调」**（一个队列可以有多个 Handler，**Message 用 target 字段记住谁发的，dispatch 回谁**），Message 是载荷。**sendMessage 的本质**：Message 入队（按 when 排序的链表插入）→ **唤醒队列（nativeWake，写一个字节到 eventfd/管道）**。

**主线程为什么不用 prepare**：**ActivityThread.main 是主线程的入口**，它已经在里面 Looper.prepareMainLooper() 加 loop() 了——**主线程是个「永远在跑的 Looper 循环」，App 的「主线程代码」其实全是被 Looper 分发的一条条 Message**（Activity 生命周期就是 AMS 跨进程投递过来的消息调度，这也是 ANR 的根源：生命周期消息排队 5 秒没执行完）。

**深水区一：延迟消息的实现**——不是定时器是「排序加休眠」：Message 按 when 插入链表（有序），**Looper 取队头时算「还有多久到期」，把剩余时间传给 nativePollOnce(ptr, timeoutMillis)**——**native 层就是 epoll_wait(ptr, timeout)**：没到时间的队头挂起线程（不耗 CPU），到期或新消息 nativeWake 唤醒。**所以 postDelayed(60s) 不会开定时器线程，是「睡 60 秒」**；更深的推论：**MessageQueue 没消息时 next() 无限阻塞（timeout=-1），主线程在「深睡」，ANR 检测、IdleHandler 都靠这个循环的空隙跑**。

**深水区二：同步屏障**——post 到队列的 Barrier 消息（target=null）：**next() 遇到屏障时跳过普通消息、只找「异步消息」优先返回**。用途的完整链路：**UI 更新 requestLayout → ViewRootImpl 调 postSyncBarrier 屏蔽普通消息 → Choreographer 的异步消息（vsync 帧回调）插队执行 → 帧绘制完 removeSyncBarrier**——**渲染帧能「插队」在无数延迟消息前面，靠的就是这套机制**。

**Message 的池化细节**：obtain 从 **sPool（链表，上限 50）**复用，recycle 清空字段回池——**避免高频 Message 的分配与 GC**（和 Go 的 sync.Pool 一个思想）。

收尾：Handler 机制的三句话总结，**「队列是排序链表不是定时器」「阻塞是 epoll 不是死等」「优先级靠屏障不是插队标志」**，答出这三层就从「会用」到了「懂原理」。

> 面试官追问点：为什么 IntentService 被废弃了？应答思路：它是「HandlerThread 加 Handler 的组合封装」（串行后台任务），但生命周期管理和现代后台限制（Doze 模式杀后台）让它不可靠；替代是 WorkManager（约束感知 + 持久化调度），这是一道「知道类的历史演进方向」的题。

#### 13.2 Binder一次拷贝怎么实现？双映射是什么

答：一句话定调，**Binder 靠「mmap 双映射」做到一次拷贝：发送方 copy_from_user 到内核，内核和接收方的缓冲区是同一块物理内存，接收方零拷贝直达**。

**对比传统方案的两次拷贝**：管道/Socket 的写路径是「发送方用户态 → copy_from_user 进内核 → copy_to_user 到接收方用户态」**两次拷贝两次上下文切换**；共享内存是零拷贝但「无同步原语、安全性裸奔」。**Binder 的定位是「一次拷贝 + 强类型接口（AIDL）+ 进程身份（UID/PID 内核背书）」**。

**mmap 的双映射机制**（深水区一，讲清楚就赢）：**接收方（服务进程）提前 mmap 一块内核的 binder 内存**——这块物理页**同时映射进内核地址空间和接收方用户地址空间**；发送数据时 binder 驱动只做**一次 copy_from_user（发送方用户态 → 内核缓冲区）**，而这个内核缓冲区恰好就是接收方映射的那块——**接收方读自己的映射地址就是数据，第二次拷贝消失了**。代价是**「一次 mmap 的内存上限（约 1MB-8MB）决定了 Binder 单次传输不能超过 1MB-8MB」**（传输大文件要走 Ashmem 匿名共享内存）。

**完整调用链**（AIDL 视角）：客户端调 stub 的代理 → **Parcel 打包（writeInterfaceToken 校验、写参数）→ ioctl(BINDER_WRITE_READ) 陷入驱动** → 驱动找到目标进程的 todo 队列挂任务、唤醒服务线程 → **服务端 IPCThreadState 读出、Parcel 解包 → Binder 线程池的线程执行 onTransact（switch code 分发到本地方法）**→ 返回值沿反向链路回去。

**深水区二：进程身份防伪造**——**Binder 驱动在事务里自动附加调用者的 UID/PID**（from kernel，不可伪造），**服务端 getCallingUid 验权**——这是 Android 权限体系的基石：**普通应用伪造不了 system 身份，因为身份不是消息里的字段而是驱动贴的「邮票」**。对比 Socket（自报身份可伪造），这是 Binder 之于 Linux 老 IPC 的安全代差。

**ServiceManager 的角色**：** Binder 世界的 DNS**——服务注册（addService）和查找（getService）都经过它（它自己是 0 号句柄的特殊 Binder）；**死亡通知（DeathRecipient）也是驱动提供的：目标进程消亡时驱动回调注册方**——客户端监听服务死活、做重连，全靠这个机制（「死亡代理」的原名）。

收尾：Binder 的设计一句话，**「mmap 换一次拷贝，驱动贴邮票换安全身份，句柄表换对象寻址」**——性能、安全、对象语义三合一，这是它淘汰老 IPC 成为 Android 基石的理由。

> 面试官追问点：为什么单次传输限制 1MB 左右？应答思路：mmap 的 binder 缓冲区按进程预分配（默认约 1MB），传输数据必须整块放进映射区；异步事务（oneway）还有另一半的限额——**超限要么 TransactionTooLargeException（这个异常实际抛在 Bundle 过大场景）要么失败重试**，大块数据的标准出路是「传 Ashmem 的 fd、数据走共享内存」。

#### 13.3 RecyclerView四级缓存？命中成本怎么分层

答：一句话定调，**四级缓存按「离屏幕的远近」和「是否需要重新绑定」分层，scrap 和 cache 是「不用重绑」的近缓存，pool 是「跨列表共享」的远缓存**。

**四级逐层讲**：

1. **Scrap（mChangedScrap / mAttachedScrap）**：**当前布局过程内部的临时Detach**——layout 前后 detach 再 attach 的 ViewHolder，**数据位置都没变，跳过重绑**（预取和 layout 复用同批 child 用）；
2. **Cache（mCachedViews，默认 size=2）**：**刚滑出屏幕的 ViewHolder 按 position 精确缓存**——**命中时「按原 position 直接复用、不重绑」**（连 onBindViewHolder 都不用跑，这是它和 pool 的本质区别）；只存最近滑出的几个（马上滑回去的场景最赚）；
3. **ViewCacheExtension**：给开发者的自定义缓存层（**很少用**，等于官方留的白板）；
4. **RecycledViewPool**：**按 viewType 分桶（SparseArray<ScrapData>，每桶默认 5 个）**——**命中只能拿到「正确类型的空壳」，必须重新 onBindViewHolder**；**跨 RecyclerView 共享**（多个列表同类型 item 复用，setRecycledViewPool 共享池）。

**流程串起来**（滑动时的 getViewForPosition）：**先 scrap/cache 按 position 查（零成本复用）→ 查 pool 按 viewType 查（重绑成本）→ 都没有 create 新的**。**与 ListView 对比的胜负手**：ListView 的 RecycleBin 两级（active/scrap），**没有按类型的池、没有差量更新、没有预取**——RecyclerView 的四级是在「重绑成本」上做了极致分层。

**深水区一：DiffUtil 的差量更新**——**notifyDataSetChanged 的暴力**：全部视为失效 → **全部重绑（即使内容没变）+ 丢失动画**。**DiffUtil 用 Myers 差分算法算出「新增/删除/移动/未变」的最小编辑脚本**：**未变的直接复用（跳过重绑）、变化的精准刷新、move 还能触发位移动画**。**AsyncListDiffer 把 diff 挪到后台线程**（主线程只做 submit 后的渲染），配合 **ListAdapter（封装好的 differ 订阅）是现代标准姿势**。底层再深一层：**Adapter 的 getItem 和 areContentsTheSame 分离**——id 相同内容不同才是「原地刷新」的精确语义。

**深水区二：预取（GapWorker）**——**滑动时空闲帧提前创建「即将进入屏幕」的 ViewHolder**：它复用 13.1 讲的 **IdleHandler 机制在主线程空闲时干活**（和 Handler 机制打通），**预取的绑定发生在滑动之外的时间片，滑到时 item 已就绪**——这是「滑动不掉帧」的隐形功臣，也解释了「为何 Cache 只有 2 却不卡」。

收尾：四级缓存答题的心法，「**每级回答两个问题：命中成本多低（要不要重绑）、覆盖场景多远（position 精确还是类型模糊）**」，DiffUtil 和预取则把「重绑」和「创建」两个成本也搬离了关键路径。

> 面试官追问点：为什么说「RecyclerView 的 View 复用粒度是 viewType 不是数据」？应答思路：pool 按 viewType 存壳，同类型不同数据的 item 共用一套布局结构——所以「类型数量爆炸」(每种数据一个 viewType) 会让 pool 分桶过多每桶都冷；正确姿势是「布局形态才定义 viewType，数据差异交给重绑」。

#### 13.4 ART编译模式怎么演进？Profile是什么

答：一句话定调，**Dalvik 是 JIT（边解释边编译），ART 5.0 用纯 AOT（安装时全量编译）换性能但伤安装和存储，7.0 起的混合模式（JIT + AOT + Profile）才是终局**。

**三代演进按「痛点」讲**：

1. **Dalvik（JIT）**：运行时解释执行 + 热点 JIT，**省存储但每次启动都要重新 JIT（热身慢）、费电**；
2. **ART 5.0/6.0（纯 AOT）**：**安装时 dex2oat 全量编译成机器码**——运行飞快，**代价是安装慢（大 App 十分钟级）、占双倍存储（dex + oat）、OTA 后全量重编译**；
3. **ART 7.0+（Hybrid）**：**安装只编译关键路径（或纯解释），运行时 JIT 热点采集，**空闲时 Cloud Profile（云端聚合的画像）+ 本地 Profile 指导 AOT 后台重编译**——**下次启动用上次的画像**，冷启动越用越快。

**深水区一：Profile 引导的细节**——**Profile 是「方法级热度表」**（哪些方法在启动路径上被执行）：**基准配置文件（Baseline Profile，Android 9+）由开发者上传或云端聚合**，**安装时只 AOT 这条「启动关键路径」**（几 MB 的编译量，秒级安装），**运行后的真实画像回灌，后台 dex2oat 增量补编**——「安装快启动也快」的矛盾就是这么调和的。**Jetpack 的 Macrobenchmark 写 Baseline Profile** 是现代性能优化的标准动作（首页路径预编译，冷启动直接砍 30%+）。

**深水区二：方法数 64K 的真相**——**dex 文件里方法索引是 16 位**（method reference 的 id 上限 65536），**单个 dex 的方法数炸了就 link 不过**；multidex 的机制：**主 dex 装启动必需的类（Application/入口 Activity 手工指定 keep），副 dex 运行时从 apk 解压加载（MultiDex.install 在 attachBaseContext 里跑，本身有冷启动成本）**；**5.0+ 用 ART 原生支持多 dex（oat 里多个 dex）解决了主因， multidex legacy 只服务 4.x**——所以「64K 问题」在今天更多是历史知识，但「id 索引位数决定上限」的机制值得讲。

收尾：编译模式的演进主线是「**AOT 的性能、JIT 的灵活、Profile 的数据**」三者从对立走向融合，**热度的信息（哪些代码值得编译）从「拍脑袋全编」进化成「画像精准打击」**。

> 面试官追问点：dexopt 和 dex2oat 的区别？应答思路：dexopt 是 Dalvik 时代的优化（odex：字节码的 verify+optimize，还是字节码）；dex2oat 是 ART 的编译（oat/vdex：真机器码），Android 8 后用 vdex+odex 拆分存储（vdex 存验证过的 dex、odex 存机器码）——名词的变迁对应「优化到编译」的质变。

#### 13.5 LeakCanary怎么判定泄漏？监控套路是什么

答：一句话定调，**LeakCanary 的核心是「WeakReference + ReferenceQueue 的 GC 见证机制」：弱引用对象被回收时队列里会出现它的尸体，该出现而没出现就是泄漏**。

**LeakCanary 的四步机制**：

1. **注册观察**：watchActivity/watchFragment 销毁时，把实例包进 **KeyedWeakReference（自定义弱引用）连同 ReferenceQueue** 入 watch 表；
2. **主动触发 GC**（深水区一）：**Runtime.getRuntime().gc() + 等待 100ms**——注意 **System.gc() 只是「建议」**（JVM 规范允许忽略），LeakCanary 的做法是 gc 后再跑**runFinalization 加二次确认**，确保「真回收过了」；
3. **判定**：**从 ReferenceQueue 里 remove——被回收的弱引用会出现在队列里**（GC 时自动入队）；**观察表里还在（队列里没有）= 没被回收 = 被强引用着 = 泄漏**；
4. **堆转储找链**：**Debug.dumpHprofData 导出 hprof → Shark（自研解析器，比 MAT 轻）解析出「GC Root 到泄漏对象的最短引用链」**，按「怀疑等级」排序出报告。**Shark 的价值是「移动端能跑的 hprof 解析」（裁剪索引 + 增量分析，几秒出结果）**——早期用 HAHA（MAT 的库）在手机上 OOM 自己。

**深水区二：Matrix 的卡顿监控**（和 Handler 机制打通的另一案例）：**主线程的消息执行前后插桩**——**Printer 拦截 Looper.dispatchMessage 的日志回调（setMessageLogging）**，消息开始打标记、结束打标记，**一条消息执行超阈值（如 700ms）判定卡顿**；**同时子线程周期向主线程 post 高优先级消息，主线程迟迟不处理说明被占死**（「栈采集」：卡顿时抓主线程 stack，但单次栈可能错过现场，**Matrix 的 LazyScheduler 重复采样拼接出「卡顿现场的时间切片栈」**）。更轻的方案：**Choreographer 掉帧监控（FrameCallback 的 doFrame 间隔 vs 16.7ms）**——监控的是渲染帧率不是消息耗时，两者互补。

**线上 APM 的克制**（工程感加分点）：**LeakCanary 全量 dump 只适合线下**（dump 会 stop the world 数秒），**线上方案是「KB 泄漏监控」**（腾讯的 koom 方向）：**内存阈值触发 + 增量 dump（只 dump 泄漏关联区域）+ 子进程 dump（避免主进程卡顿）**；矩阵式监控的哲学：**线下深诊断、线上轻埋点，把成本预算花在「可疑才深挖」**。

收尾：监控类工具的通用套路值得总结，**「拦截点（Looper/生命周期）+ 判定信号（队列超时/弱引用存活）+ 证据采集（栈/堆）」三件套**，LeakCanary 和 Matrix 只是三件套的两个排列组合，理解套路比记工具重要。

> 面试官追问点：为什么 watch 一个对象能证明它泄漏？应答思路：销毁回调时对象「逻辑上应该死了」，弱引用是「只观察不持有」的引用——**GC 后弱引用还活着 = 有人在强引用它 = 谁在拖着尸体不放**；引用链就是这个「谁」的名单，弱引用机制把「不可见的持有关系」变成了「可检测的存活事实」。

#### 13.6 Activity启动怎么跨进程？完整链路是什么

答：一句话定调，**Activity 启动是「两次 Binder 跨进程 + 一次进程创建」的长链路：App 进程 → system_server（AMS）→ Zygote fork（冷启动）→ 返回 App 执行生命周期**。

**六步链路**（以冷启动为轴）：

1. **App 进程发起**：`startActivity` 一路到 **Instrumentation.execStartActivity**，**通过 AMS 的 Binder 代理（IActivityManager）跨进程**进 system_server——**应用进程在这里「交出控制权」**；
2. **AMS 权衡与决策**：检查清单（Activity 注册了吗、权限够吗、目标进程活着吗）——**目标进程没活，AMS 通过 Socket 通知 Zygote fork 新进程**（**Zygote 为什么用 Socket 不用 Binder：fork 的瞬间不能有多线程（Binder 线程池会导致子进程状态混乱），Socket 是单线程安全的通信**——经典细节）；
3. **Zygote fork 出新进程**：**预加载的类和资源被 COW 共享**（启动快的根本），**新进程的入口是 ActivityThread.main**；
4. **ActivityThread.main**：**Looper.prepareMainLooper 建主线程消息循环**（13.1 的根基在这）+ **AMS 的 attachApplication 回连**（把自己的 ApplicationThread Binder 交给 AMS，这是「AMS 主动找 App」的回程地址）；
5. **AMS 下发启动事务**：**ApplicationThread.scheduleTransaction（又是 Binder，方向反过来了）**，**App 侧包装成 Message 进主线程队列**；
6. **主线程执行**：**Handler 消息里依次 handleLaunchActivity → performCreate → onStart → onResume**——**生命周期就是消息驱动的普通方法调用**。

**深水区一：为什么 ANR 卡的是主线程消息**——从链路看：**生命周期的每一步都是「AMS 投递消息 → 主线程队列 → Handler 执行」**；**主线程被前一个消息卡住（比如 onCreate 里 sleep）**，后面的生命周期消息排队等待——**「超时未处理」的 ANR 本质是「消息排队超时」**（broadcast 10s / input 5s / service 20s 三种场景不同阈值，同源机制）。

**深水区二：AMS 为什么能「指挥」你的进程**——**attachApplication 交出去的 ApplicationThread 是 App 的 Binder 服务端**：**AMS 手握每个进程的回程地址，跨进程把事务投递进来**——「系统服务调度应用」的架构本质是 **Binder 的双向连接 + 消息队列的串行化**。**理解这个模型，「Activity 生命周期是谁调的」就有了终极答案：AMS 决定时机，主线程队列决定执行**。

收尾：启动链路答题的心法，「**两次 Binder（去 AMS、回 App）+ 一次 fork（Zygote 的 Socket）+ 消息收尾（生命周期的真身）**」，ANR 和生命周期问题全部挂在这条线上。

> 面试官追问点：热启动和冷启动的链路差在哪？应答思路：跳过第 3-4 步（进程活着、Looper 转着），AMS 直接查到目标进程的 ApplicationThread 投事务——**冷启动的大部分时间花在进程创建和应用初始化**，这就是「优化都盯着 Application 和首个 Activity」的链路依据。

#### 13.7 事件分发怎么递归下发？滑动冲突怎么解决

答：一句话定调，**事件分发是「递归下发（dispatchTouchEvent）+ 拦截权（onInterceptTouchEvent）+ 消费权（onTouchEvent）」的三段博弈，一个 DOWN 的归属决定了整串事件的归属**。

**三段职责**：**dispatchTouchEvent 是必经之路（返回值=「这一串事件我包了」）**；**onInterceptTouchEvent 是 ViewGroup 特权（「这串事件别给我的孩子了」）**；**onTouchEvent 是消费表态（「我处理这个序列」）——View 没有 onInterceptTouchEvent（没有孩子可拦截）**。**事件序列的粘性**：**DOWN 确定的消费者会收到后续 MOVE/UP 的全部**（系统按「目标」直投，不再重新竞标）——**「一串事件一个主人」是整个机制的稳定锚**。

**递归流程还原**（ViewGroup.dispatchTouchEvent 主干）：**onInterceptTouchEvent 返回 true → 自己的 onTouchEvent 处理**；false → **遍历子 View 找「事件落点内的、能处理的」**，孩子处理不了才轮到自己（**「先子后父」的默认谦让**）。**requestDisallowInterceptTouchEvent 的机制**：子 View 设置 FLAG_DISALLOW_INTERCEPT，**父的 onInterceptTouchEvent 直接不被调用**——「孩子先表态『别抢』」，**滑动冲突的内部拦截法就是它**（子类 dispatchTouchEvent 的 DOWN 里 request、MOVE 判定后 release）。

**深水区一：onTouch 与 onTouchEvent 的优先级**——**View.dispatchTouchEvent 里先查 onTouchListener**（onTouch 返回 true 就不上 onTouchEvent）→ **onTouchEvent 里再查 onClickListener**——**优先级链：onTouch > onTouchEvent > onClick**，**onTouch 拦截后 onClick 失效是常见事故**（performClick 的调用是 View 的默认行为，自定义 onTouch 绕过了它）。

**深水区二：外部拦截法的标准模板**——「父 View 的 onInterceptTouchEvent 里：**DOWN 必须 return false**（DOWN 拦了孩子收不到整串就断了）、**MOVE 按滑动方向判定**（水平位移差 > 竖直则拦截）、**UP 必须 return false（UP 拦了孩子的 click 收不到）**」——**三个 return 的时机约束**是滑动冲突题的真正考点，能讲出「为什么 DOWN 和 UP 不能拦」就是源码级理解。

收尾：事件分发答题的心法，「**三段职责一张图（必经/特权/表态）、序列粘性一个锚（DOWN 定终身）、冲突处理两套法（外部拦截父问、内部拦截子禁）**」。

> 面试官追问点：为什么 onTouchEvent 返回 false 后事件会传给父级？应答思路：分发是递归下行，孩子的 dispatch 返回 false 意味着「这层没人要」，递归栈回退时父的 onTouchEvent 接手——**「不消费就上交」是责任链的味道**（和 09 篇的责任链变体可对照）。

#### 13.8 Glide四级缓存怎么漏斗？生命周期怎么挂

答：一句话定调，**Glide 的缓存是「四级漏斗」（活动资源→内存→磁盘→网络），生命周期感知靠「无 UI 的 SupportRequestManagerFragment 挂载请求」，Bitmap 池化让「加载图片几乎零分配」**。

**四级漏斗的每一级**：

1. **ActiveResources（活动资源）**：**正在显示的图片的弱引用表**——「屏幕上的」和「内存缓存的」分离的妙处：**内存紧张时 LRU 清掉的不会影响正在显示的**（活动表是弱引用，显示中的强引用保命）；
2. **MemoryCache（内存 LRU）**：默认 **屏幕宽高 × 4 通道的内存上限**（按设备自适应），命中直接回调；
3. **磁盘缓存**：**分「原始图（SOURCE）」和「变换后（RESULT）」两套**——**圆角/缩放后的结果单存，二次加载跳过解码和变换**；
4. **网络**：最小优先（EngineJob 发起）。

**深水区一：生命周期感知的实现**——**Glide.with(fragment) 的秘密**：**往 FragmentManager 加一个 SupportRequestManagerFragment（无 UI）**，**RequestManager 监听它的生命周期**：**onStop → pauseRequests（在途请求挂起）**、**onDestroy → cancelRequests + 清引用**——「**页面销毁请求自动取消**」不是魔法，是**一个透明 Fragment 做代理观察者**。**为什么这么绕**：直接持 Activity 引用会泄漏、监听 Activity 生命周期回调又是侵入式的——**「寄生 Fragment」是 Lifecycle 组件出现前的经典黑科技**。

**深水区二：BitmapPool 的零分配哲学**——**解码 Bitmap 的临时内存从池里借**（inBitmap 复用一块内存）：**API 19+ 允许「尺寸不精确匹配的复用」**（只要 bitmap 内存够大），**变换过程（圆角裁剪的中间 Bitmap）全程借还**——**「加载图片零 GC」**是它对低端机流畅度的最大贡献（GC 抖动是列表卡顿大户）。**和 13.1 的 Handler 消息池、09 篇的享元模式是同一思想的三个马甲**。

收尾：Glide 答题的心法，「**四级漏斗按『可见-近用-持久-远程』分层、寄生 Fragment 挂生命周期、Bitmap 池把分配也消灭**」，最后一项是深水区的分界线。

> 面试官追问点：为什么同一张图不同 ImageView 尺寸加载结果不同？应答思路：Glide 默认**按 Target 尺寸做下采样解码**（inSampleSize），不同尺寸产出不同缓存 key——override() 可以强制统一；这也是「磁盘缓存命中率忽高忽低」的一个来源（尺寸进 key）。

#### 13.9 MVP到MVI的演进逻辑？解耦对象是什么

答：一句话定调，**三代的演进主线是「解耦谁和谁」：MVP 解耦 View 和逻辑（接口回调）、MVVM 解耦数据和视图（观察者自动同步）、MVI 把「状态和事件」单循环化**。

**MVC 的原罪**：Activity 既是 View 又是 Controller（XML 只是个壳）——**「上帝 Activity」千行代码的病根**；**MVP 的解法**：**Presenter 持 View 接口**（Activity 实现之），逻辑全进 Presenter——**可测性暴涨（Presenter 是纯 Java 可单测）**；**代价**：**接口爆炸（一个页面对应一堆 IView 方法）+ 生命周期地狱（异步回来 View 已销毁，判空轰炸）**。

**MVVM 的换轨**（深水区一）：**Presenter 的「主动调 View 方法」换成「暴露可观察的数据」**——View 订阅 ViewModel 的 LiveData/Flow，**数据变了 UI 自动刷**——**「数据驱动」替代「命令驱动」**：**好处**：接口砍掉了（暴露的是数据不是方法）、**生命周期问题被 LiveData 框架解决**（DESTROYED 自动解绑）；**代价**：**数据流的「多入口」问题**——一个页面十几个 LiveData，各自的更新时机交织，「最终 UI 状态」是多个流叠加的结果，**难以推理**（「这个状态哪来的」要全局搜）。

**MVI 的收敛**（深水区二）：**单一数据源（一个 UiState 不可变对象）+ 单一意图入口（所有用户行为统一成 Intent）+ 单向数据流（send(intent) → reduce → 新 State → render）**——**「状态 = f(intent, 前状态)」的纯函数化**：**每一步可追溯（日志记录 intent 流）、状态可回放（时间旅行调试）、并发安全（State 不可变）**。**代价**：样板代码（一个点击也要包装成 Intent 类）+ **State 全量更新对小改动低效**——**「MVI 是把 Redux 思想搬进 Android」**，适合状态复杂的页面，简单页面是杀鸡用牛刀。

**选型的诚实答案**：**MVP 老项目维护、MVVM 是 Jetpack 亲儿子（官方默认）、MVI 复杂状态页**——三代不是替代是**「耦合治理粒度」的进化**，能讲出「每代解决上一代的什么痛、引入了什么新痛」就是深水区。

收尾：架构题的心法，「**MVC 病在上帝类、MVP 药是接口回调、MVVM 药是数据驱动、MVI 药是状态单循环**」，最后一句话点破：「**架构选型不是追新，是选对你页面的状态复杂度**」。

> 面试官追问点：ViewModel 为什么转屏不丢数据？应答思路：ViewModel 存在 **ViewModelStore**（Activity 的「转屏存活的伴生体」，配置变更时 Activity 重建但 ViewModelStore 由 ActivityThread 保留移交）；只有「真正的销毁」（finish）才清空——**「比 Activity 活得长的非静态无泄漏单页数据容器」**是它的精确定位。

#### 13.10 Kotlin协程挂起原理？状态机怎么运转

答：一句话定调，**挂起函数编译后是「带 Continuation 参数的状态机」，挂起 = 「把后续代码包成回调存入 Continuation 并让出线程」，恢复 = 「回调被调度器再次调用」**。

**CPS 变换**（Continuation Passing Style，编译器干的事）：`suspend fun foo(): T` 编译成 `fun foo(c: Continuation<T>): Any?`——**返回值 Any? 是「T 或 COROUTINE_SUSPENDED」**：**返回 COROUTINE_SUSPENDED 意味着「没算完，结果以后走 Continuation」**；返回 T 意味着「同步就完成了（假挂起，不切线程）」——**「挂起不一定真切线程」**（delay(0) 或已完成的 withContext 会同步返回）是理解性能的第一步。

**状态机的还原**（深水区一）：多个挂起点之间编译成 **when (label) 的跳转表**——**每个挂起点是一个 case，局部变量提升到状态机字段保存**；挂起时：**当前 label 和变量已存进 Continuation，函数直接 return SUSPENDED**；恢复时：**Continuation.resumeWith(value) 再次调用这个函数，label 指到下一个 case，从断点后继续**——**「协程 = 编译器生成的回调嵌套扁平化」**，和 async/await 在 JS 的编译产物（5 篇 7.4）是同一思想的两家实现。

**结构化并发的机制**（深水区二）：**Job 是树**（Scope 的 job 是父、launch 的是子）——**cancel 是树遍历（父取消级联子）**、**join/await 是父等子**、**异常向上冒泡（子失败取消父的其它子）**——**「协程的生命周期天然有组织结构」是它比「裸线程+回调」强的根本**；**SupervisorJob 是「异常不传染兄弟」的变体**（子失败只死自己）；**对比 Go**：goroutine 没有结构（泄漏要人肉防，context 是外挂的取消树），**Kotlin 把取消和层级做进了类型系统**——两家哲学的差异点。

**调度器的分层**：**Dispatchers.IO 的「弹性线程池」**（默认 64 上限可扩）、**Default 是 CPU 核数的计算池**、**Main 是 Handler 转发**；**withContext 的切换 = 「挂起点 + 恢复时在目标调度器」**——**「挂起恢复」和「线程跳转」是两个正交的机制**（挂起可以不切线程，切线程必经挂起点）。

收尾：协程答题的心法，「**挂起=CPS+状态机（编译期魔法）、结构化=Job 树（生命周期的组织学）、调度=可插拔的恢复地点**」，第一句讲给面试官，后两句讲给深水区。

> 面试官追问点：suspend 函数为什么不能在普通函数调？应答思路：它编译后需要 Continuation 参数（谁来接「以后的结果」），普通函数没有 Continuation 可传——**「suspend 传染性」的本质是「回调上下文的类型要求」**，而不是运行时限制。
