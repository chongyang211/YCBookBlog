# 1.面向对象基础

#### 1.1 C语言和C++有什么区别？两者是否完全兼容

答：一句话定调，**C++ 是 C 之上加了四套大件——类与继承、模板、异常、引用与重载，兼容是绝大多数但不是百分之百，裂缝就藏在语言律师最爱钻的角落**。

**编程范式**：C 是面向过程，函数加结构体打天下；C++ 是多范式语言——面向对象、泛型、过程式可以混着用。**类型检查**：C++ 更严格——C 允许 `int* p = malloc(4)`（void* 隐式转换），C++ 必须强转；C 可以不声明原型就调函数，C++ 直接编译错。**内存管理**：C 靠 malloc/free（手动、面向字节），C++ 主推 new/delete（会调构造析构）加 RAII（8 章）。**标准库**：C 的 printf/strcpy 对 C++ 的 iostream/STL，后者是模板化的容器算法体系。

**兼容性的裂缝**：最典型的是隐式 void* 转换（那行 malloc 在 C++ 里不过编译）；关键字冲突——C 里合法的标识符 class、new、template 在 C++ 成了保留字；函数名 mangle 规则不同，C++ 编译的符号 C 链接器认不出，要靠 extern "C" 桥接（1.3）。精确的说法是：**C++ 兼容 C 的绝大多数代码，但不是 C 的超集**——存在合法 C 却编不过 C++ 的程序。

**拉开差距的深水区**：C++ 从 C 继承的三大历史包袱——以 \0 结尾的字符串（strlen 的 O(n) 和缓冲区溢出的根）、数组退化成指针（丢长度）、不做边界检查；extern "C" 为什么是双向的（C++ 调 C 库要包、C 库头文件被 C++ 包含也要包，`#ifdef __cplusplus` 三行是标准姿势）。

收尾：区别答"范式加四套大件"，兼容答"绝大多数但非超集"，裂缝答 void* 转换、关键字、mangle 三处。

> 面试官追问点：怎么把 C 代码安全地混进 C++ 工程？应答思路：头文件统一包 extern "C" 三行守卫；C 代码当独立模块用 C 编译器编成库，C++ 侧只见声明不见实现；绝不拿 C++ 编译器重编 C 源文件——**混合的正确姿势是链接层混合，不是源码层混合**。

#### 1.2 引用与指针的区别是什么？底层是如何实现的

答：一句话定调，**引用是"必须绑定、不能换人、自动解引用"的别名，底层实现就是指针常量——语义上是另一个物种，机器码上是同一个东西**。

**六个区别**：引用必须初始化且不能为空（空引用不存在，谁说他有空引用那是指针越界的 UB）；绑定后不能改指别人（一仆不事二主）；没有"引用的引用"，但指针可以套娃到二级三级；`sizeof(r)` 返回目标的大小而 `sizeof(p)` 永远是指针 8 字节；使用时不需要解引用（r.x 直接写，p 要写 p->x）；`++` 的语义不同——引用的 ++ 是目标的 ++，指针的 ++ 是步进。

**底层实现**：编译器把引用实现成 const 指针（T* const），传引用和传指针生成的汇编完全一致——**引用是编译器层面的语法糖，不是运行期的独立实体**。这也是"为什么没有空引用"的答案：语法上要求必须初始化，编译器强制检查。

**返回值的红线**：不能返回局部变量的引用（栈帧销毁即悬空，和 C 的野指针同款事故）；可以返回类成员、静态变量、堆对象的引用——但返回类成员引用会暴露内部实现，权衡使用。

**拉开差距的深水区**：右值引用 T&& 打破"引用只是别名"的朴素理解——它专门绑定"快死的值"，配合移动语义把资源偷走（4.1.1）；引用取不到"自己的地址"——`&r` 拿到的是目标的地址，引用本身在编译后就消失了，这也是调试器里引用和指针显示差异的根源。

收尾：区别答六个维度（空、重绑定、套娃、sizeof、解引用、++），底层答 const 指针语法糖，红线答不返回局部引用。

> 面试官追问点：传引用和传指针既然汇编一样，为什么接口设计首选引用？应答思路：引用把"非空保证"写进了类型系统——调用者一眼知道"必须给我一个有效的对象"，空指针检查可以省掉；指针参数则暗示"可能为空或可能改指向"，**参数类型本身就是接口文档**。

#### 1.3 C++为什么支持重载？名字修饰是什么规则

答：一句话定调，**C++ 支持重载是因为编译器把参数类型编码进了符号名，C 不编码所以同名函数打架——重载是编译期的名字游戏，不是运行期魔法**。

**重载的规则**：同名、同作用域、参数表不同（个数、类型、顺序三者有其一）；**返回值不同不能构成重载**——调用点只看实参就能决议，不看返回值，两个仅返回值不同的函数会让 `f(1)` 无法裁决。const 成员函数能构成重载（this 指针类型不同：`T*` 与 `const T*`），这是"读接口和写接口分离"的正规手段。

**name mangling 的规则**：编译器把作用域加参数类型编码进符号——GCC 下 `void f(int)` 变成 `_Z1fi`、`void f(double)` 变成 `_Z1fd`，命名空间和类名还会继续嵌套进去。**链接器眼里它们根本不是同名符号**，所以能共存。C 不做 mangle，`void f(int)` 和 `void f(double)` 都叫 `f`，链接期必炸——这就是"C 不支持重载"的全部真相。

**extern "C" 解决什么**：关闭 mangle，让符号回到 C 的裸函数名——C++ 调 C 库时，C++ 侧拿 mangle 后的名字去找 `f` 当然找不到，包上 extern "C" 就对上了；跨语言头文件的标准三行守卫（`#ifdef __cplusplus`）是 1.1 讲过的姿势。

**拉开差距的深水区**：重载决议的优先级——精确匹配优于模板推导、模板推导优于省略号，多个可行时"更特化的模板"赢；`void f(int)` 与 `void f(int, int = 1)` 同存时调 `f(1)` 是二义性编译错——**默认参数和重载打架时，编译器不猜**；运算符重载的限制（不能造新运算符、不能改变优先级、&& / || 的短路语义会丢）。

收尾：C 不支持的原因答"符号不编码"，规则答"参数三要素加返回值不算"，extern "C" 答"关掉 mangle 桥接两套命名法"。

> 面试官追问点：怎么查看编译器给函数起的真名？应答思路：nm 看目标文件符号，管道接 c++filt 反修饰成人话；反着用也行——报 undefined reference 时拿 nm 对照两边符号名，就能确认是不是 extern "C" 没包——这题顺手把工具链考察也覆盖了。

#### 1.4 friend友元函数有什么作用？是否破坏封装

答：一句话定调，**friend 是类亲手递出去的后门钥匙：指定的函数或类可以访问私有成员，但钥匙单向、不传递、不继承——封装约束的是访问路径，不是绝对禁止**。

**三种形态**：友元函数（非成员函数声明后可访问私有，典型场景是 operator<<——输出流的左操作数是 ostream 不是本类，写成成员根本排不对参数序）；友元类（对方类的全体成员函数都能访问，双向授权要两边各写一句）；友元成员函数（只授权另一个类的某个函数，写法最繁琐还要前向声明）。

**三条铁律**：单向——你声明它是友，它并不自动认你，想互相访问两边都得写；不传递——友元的友元不是友元，你朋友的朋友不欠你人情；不继承——派生类不享受基类收下的友情，你的钥匙开不了你儿子的门。

**是否破坏封装**：有限度。封装的目的不是"绝对保密"，是"让访问集中在我认可的路径上"——friend 恰恰是类**主动授权**的路径，比把成员 public 暴露给所有人克制得多。**判断标准：friend 用在"两个类本来就该紧密协作"的边界上（运算符重载、容器和迭代器），是设计；用在"懒得写 get 函数"上，才是破坏**。

收尾：作用答"授权访问私有"，铁律答"单向、不传递、不继承"，破坏性答"主动授权路径，边界场景是设计、偷懒场景是破坏"。

> 面试官追问点：operator<< 为什么必须是友元？应答思路：成员函数的左操作数被 this 占死，想要的 os << x 根本排不上；写成非成员友元，左参是 ostream、右参是本类，流式调用才成立——**这道题顺手验证"友元是接口设计的刚需"而不是封装的漏洞**。

#### 1.5 面向对象的三大特性是什么？各自的实现机制

答：一句话定调，**封装把数据和操作捆进 class 加访问控制，继承让类按血缘复用，多态让父指针在运行期表现出子的行为——前两个是编译期的组织手段，多态才是运行期机制**。

**封装**：private/protected/public 三档访问控制，加 class 把"数据和相关函数"圈成一体。要点是**不变式**：私有数据只有成员函数能碰，成员函数保证对象永远处于合法状态——封装保护的不是字段，是字段之间的约束关系。**继承**：public/protected/private 三种方式（2.2 详谈），语义是 is-a——派生类对象里含一个基类子对象，这也是"父指针指向子对象为什么天然合法"的内存基础。**多态**：virtual 函数加 vptr/vtable——运行期按实际类型分派，完整链路是 2.3 与 11.1 的主菜。

**多态三要素**：基类的 virtual 函数、基类指针或引用、指向派生类对象——三个凑齐才有动态分派；用对象直接调用、或者函数没标 virtual，都是静态绑定。顺带分清两类多态：**编译期多态**是重载和模板（静态分派，零运行期成本），**运行期多态**是虚函数（动态分派，代价是一次间接跳转加阻止内联）。

**拉开差距的深水区**：三大特性在标准库里的真实用法——STL 几乎不用继承和虚函数，靠模板和泛型打天下（"多态"由迭代器和模板在编译期完成），这是"面向对象三大件不是唯一答案"的最好教材；CRTP（奇异递归模板基类）用继承加模板在编译期模拟虚函数，把动态分派的开销归零，是性能敏感代码的常用替代。

收尾：封装答"访问控制护不变式"，继承答"is-a 加基类子对象"，多态答"三要素加运行期分派"，深水区答 STL 的反例。

> 面试官追问点：为什么说"封装保护的是不变式而不是数据"？应答思路：一个 Date 类，年月日三个字段各自合法没意义，"2 月没有 31 天"才是约束——把字段 public 出去，任何外部代码都能写出非法组合；私有加成员函数，等于把"修改必须经过体检"写成了制度——**数据本身不值钱，数据的合法性才值钱**。

#### 1.6 重载重写和隐藏怎么区分？各自的规则是什么

答：一句话定调，**重载是同作用域同名不同参，重写是跨作用域同签名的虚函数，隐藏是跨作用域同名就遮蔽——作用域和 virtual 是两个开关，组合出三种结果**。

**一张表分清三者**：

| 维度 | 重载 overload | 重写 override | 隐藏 hiding |
|:--:|:--|:--|:--|
| 发生范围 | 同一作用域 | 派生类对基类 | 派生类对基类 |
| 参数要求 | 必须不同 | 必须完全相同 | 只要同名即可 |
| 需要 virtual | 不需要 | 必须（或标 override） | 无关 |
| 绑定时机 | 编译期 | 运行期 | 编译期 |

**隐藏的坑是本题主菜**：基类有一组重载 f(int) 和 f(double)，派生类只写了 f(int)——**另外那个 f(double) 也一起被藏了**，通过派生对象调 f(3.14) 直接编译错。名字查找是"找到第一个作用域就停"，不是"把所有重载凑一起再决议"。修法：派生类里 `using Base::f;` 把基类版本引进来。

**重写的防手滑机制**：签名必须严格一致（连 const 限定都要对齐），手滑写错签名就退化成隐藏，多态悄悄失效还编译不报错——**C++11 的 override 关键字是为此而生**，标了它，编译器替你核对签名；基类析构函数必须 virtual 是同一个故事（2.4）。

**运算符重载的限制顺带一句**：不能发明新运算符、不能改优先级和结合性、&& 和 || 重载后丢失短路求值——所以逻辑运算符原则上不重载。

**拉开差距的深水区**：默认参数加虚函数的组合——虚函数是运行期决议，默认参数是编译期按**静态类型**绑定的，`Base* p = &d; p->vf()` 会调到派生的函数体、但用基类的默认参数值，"函数是儿子的、参数是老子的"这种缝合行为专治自信。

收尾：一表三区别，隐藏答"同名全遮蔽加 using 引回"，重写答"override 显式标注防手滑"。

> 面试官追问点：为什么 C++ 的名字查找要设计成"隐藏"而不是"合并重载"？应答思路：这是继承自 C 的名字查找规则（找到同名的第一个作用域就停），跨作用域收集重载集会显著复杂化；Java 选择了合并、C++ 选择了遮蔽加 using 手动引入——**理解设计取舍比背结论更能体现段位**。

#### 1.7 初始化列表什么时候必须用？构造析构顺序怎样

答：一句话定调，**const 成员、引用成员、没有默认构造的类成员，这三类"生来不能被赋值"的必须用初始化列表；构造顺序是基类、成员按声明序、函数体，析构严格逆序**。

**三类必须用列表的成员**：const 成员（创建后不可再改，函数体里赋值等于二次修改，编译器直接拒绝）；引用成员（绑定不能重来，1.2 的铁律）；没有默认构造的类类型成员（进函数体之前它必须已经存在，而它没有"默认存在"的方式）。普通成员写列表也更优——列表是"直接构造成型"，函数体赋值是"先默认构造再覆盖"，**前者少一次开销，对重型成员是白捡的性能**。

**顺序陷阱**：初始化顺序**只跟声明顺序一致**，跟你在列表里怎么写毫无关系。`int b; int a;` 声明，构造写 `S(): a(1), b(a + 1)`——实际执行时 b 先出生，此刻 a 还是垃圾值。编译器会告警 -Wreorder，工业代码必须开。规则背后：析构要逆序，构造顺序必须确定，声明序是全类可见的唯一稳定依据。

**构造与析构的全序**：构造 = 基类（按继承声明序）→ 成员（按声明序）→ 构造函数体；析构 = 函数体 → 成员逆序 → 基类逆序。**像叠盘子，怎么叠上去就怎么撤下来**。

**成员函数里调虚函数为什么没有多态**：基类构造执行时，vptr 还指着基类的 vtable（派生部分尚未出生），此刻调虚函数走的是基类版本——**对象没造完之前，它还不是它自己**；析构期同理，先拆到基类，虚调用也只剩基类。深挖见 11.1。

收尾：三类必须答"const、引用、无默认构造"，顺序答"声明序说了算加 -Wreorder"，虚函数答"构造期 vptr 指当前层"。

> 面试官追问点：为什么不能在构造函数体里初始化 const 成员？应答思路：const 的语义是"初始化后不可修改"，进入函数体意味着成员已经完成初始化，任何写入都是赋值——对 const 是二次修改；初始化列表发生在"成员出生那一刻"，是唯一合法的赋值窗口——**这题本质是"初始化"和"赋值"是两个语言动作的辨析**。

#### 1.8 拷贝构造与赋值运算符区别？三五法则是什么

答：一句话定调，**拷贝构造是"造一个新对象"，赋值是"改一个已有的对象"，判据是有没有新对象诞生；三五法则是"你在管资源，就得把五个特殊函数当一套来管"**。

**两者判据**：`String b(a)` 和 `String b = a` 都是拷贝构造（新对象出生，一步到位）；`b = a` 是拷贝赋值（b 已存在，先释放旧资源、再拷贝新资源、还要处理自我赋值）。赋值比构造多两件事，所以两个函数的实现不一样——**用拷贝构造的实现去写 operator= 是经典错误**。

**三五法则（Rule of Three / Five）**：析构、拷贝构造、拷贝赋值三件，加移动构造、移动赋值凑五件（C++11）。核心规则：**自定义了其中任何一个，就基本该把五个全部想一遍**。逻辑链：需要自定义析构 = 类在管裸资源（new 的指针）；管裸资源时，编译器默认的"逐成员拷贝"只会抄指针地址——两份对象指向同一块内存，析构时 double free。反过来，没管资源的类（成员全是 string、vector、智能指针）五个全不用写，这就是 **Rule of Zero**——现代 C++ 的首选答案。

**什么时候会自动触发这些函数**：值传参、值返回、容器插入（vector 扩容搬迁）、初始化另一个对象——拷贝构造无处不在，这也是它比赋值更高频的原因。

**拉开差距的深水区**：编译器在什么情况下拒绝生成默认版本——成员里有 unique_ptr 时拷贝被删除（独占语义传染）、有 const 成员时赋值被删除；"三法则只写三个"在移动时代的隐患尤其大——没有移动构造的类在 vector 扩容时退回拷贝，性能差十倍还不报错（4.1.2 的 noexcept 话题）。

收尾：判据答"有没有新对象"，赋值答"多释放旧资源和防自赋值两件事"，法则答"管资源就五件套，能不管就 Rule of Zero"。

> 面试官追问点：为什么"自定义了析构就大概率需要自定义拷贝"？应答思路：自定义析构的唯一常见动机是类持有需要特殊释放的资源，而默认拷贝是浅拷贝成员——指针被抄两份，析构必然释放两次；**析构里有 delete，拷贝构造里就该有 new，两处代码天然成对**——这条推理链是三法则的证明过程。

#### 1.9 深拷贝和浅拷贝差在哪里？什么时候必须自定义

答：一句话定调，**浅拷贝只抄指针不抄房子——两份对象共享同一块资源，析构时 double free；深拷贝连房子一起新建，各住各的**。

**默认行为是浅拷贝**：编译器生成的拷贝构造（和拷贝赋值）是逐成员复制——成员是 int 就抄 int，成员是 `char*` 就抄那个地址。**指针被抄的是"地址"不是"地址里的东西"**，于是两个对象的指针指向同一块堆内存。

**double free 的完整事故链**：`String s2 = s1`（默认浅拷贝）→ s1.data 和 s2.data 指向同一块 buffer → main 结束 → s2 析构 delete 了 buffer → s1 析构再 delete 同一块 → **堆元数据已经面目全非，第二次 delete 触发 abort 或更晚的神秘崩溃**——和 C 文件里讲过的堆破坏延迟性一模一样，事故现场离案发地十万八千里（C 的 2.7）。

**必须自定义拷贝构造的时机**：类里有裸指针指向自己申请的资源（new/malloc 出来的）；反过来，成员全是值语义（string、vector、智能指针）的类，默认浅拷贝就是正确的深拷贝——**"深浅"的根源不在语法在资源所有权**。

**深拷贝的标准写法三步**：按目标大小申请新空间 → 拷贝内容（不是地址）→ 析构时只释放自己的。拷贝赋值还要先释放自己手里的旧资源，并防自我赋值（`if (this == &rhs) return *this;` 或直接用 copy-and-swap，8.2）。

**拉开差距的深水区**：深拷贝的性能替代——写时复制（COW，string 的历史方案，因多线程下引用计数的原子开销被 C++11 标准废弃）和移动语义（资源直接换主，4.1.2）；"浅拷贝有时是对的设计"——shared_ptr 的拷贝本来就是共享语义，关键是**共享必须显式（智能指针）、不能意外（裸拷贝）**。

收尾：浅拷贝答"抄地址不抄内容"，事故链答"两次 delete 同一块"，时机答"裸指针管资源就必写"。

> 面试官追问点：怎么快速判断一个类会不会被浅拷贝坑？应答思路：看三个问题——有没有裸指针成员、析构里有没有 delete、拷贝构造是不是编译器默认的；三个都对上就是定时炸弹——顺手补一句"改成 unique_ptr 成员直接拆弹"，把 1.8 的 Rule of Zero 串起来。

#### 1.10 空类为什么占1个字节？含虚函数为何占8字节

答：一句话定调，**空类 1 字节是为了"不同对象有不同地址"，多出的 8 字节是虚表指针 vptr 的门票钱；静态成员和成员函数都不住在对象里**。

**1 字节的由来**：C++ 规定完整对象的大小至少为 1——如果空类是 0 字节，`Empty a[10]` 的十个元素就会挤在同一地址，`&a[i] == &a[j]` 恒成立，指针无法区分对象，数组的指针算术直接失效。**那 1 字节是个占位符，保证"每个对象至少租得起一个门牌"**。

**含虚函数 +8**：每个多态对象头部都藏一个 vptr（64 位平台 8 字节），指向该类的 vtable（2.3 与 11.1 的主菜）——同类全体对象共享一张表，但**每个对象都要自带一根指向表的指针**。空类加上一个虚函数，sizeof 从 1 跳到 8，这个跳变就是"多态的入场费"。

**不占对象空间的三样东西**：静态成员变量（住在全局/静态区，全类共享一份，C 文件 2.2 讲过 static 的老家）；成员函数（生成后躺在代码区，本质是带 this 参数的普通函数）；const 静态整型常量的类内初始化（也不占）。**对象里只有两样：数据成员和 vptr**。

**对齐后的算术**：`class A { char c; }` 有虚函数时，8（vptr）+ 1（c）再按 8 对齐补到 16——对齐规则和 C 文件 4.1 完全同源；继承空基类的派生类，空基类子对象被 EBO（空基类优化）压成 0 字节——**同样是空，做基类可以白住，做对象必须交 1 字节房租**。

**拉开差距的深水区**：EBO 的边界——空基类优化不是标准强制而是"允许实现"，MSVC 对多级空基类继承有历史限制；`[[no_unique_address]]`（C++20）把"空成员也压成 0"的待遇扩展到了成员身上——allocator 在容器里的零开销实现全靠它。

收尾：1 字节答"不同对象不同地址"，8 字节答"vptr 入场费"，不占空间答"静态成员、成员函数、还有 EBO 的白住"。

> 面试官追问点：空类既然 1 字节，为什么空基类可以是 0？应答思路：基类子对象不需要独立取址——通过派生类对象总能定位它，"不同对象不同地址"由派生对象整体保证；C++ 允许实现把空基类压到 0，编译器家家都这么干，还顺手成就了 EBO——**同一个"空"，做主角要交房租，做配角可以隐身**。

# 2.虚函数与多态底层

#### 2.1 虚函数和纯虚函数的区别？析构函数为何要虚

深度精讲见 11.11。

答：一句话定调，**虚函数给"可被覆盖"开通道，纯虚函数强制子类必须覆盖并把宿主类变成抽象类；构造函数不能虚因为 vptr 还没出生，析构函数必须虚否则 delete 父指针只拆一半**。

**虚函数与纯虚函数**：virtual 有默认实现，子类可覆盖可不覆盖，类可以实例化；`= 0` 纯虚函数把"必须覆盖"写成合同，含纯虚的类是抽象类——**不能创建对象，天生当接口用**（Java 的 interface 就是它）。纯虚也可以有函数体，但只能通过 Base::f() 显式调用，虚表里挂的是"未实现"的标记。

**构造函数为什么不能是虚的**：虚调用依赖 vptr，而 vptr 要靠构造函数来安装——先有鸡还是先有蛋（11.1 展开到汇编层）。加上语义也不通：构造时你知道自己要造的是什么类型，不需要"运行期才决定"。

**析构函数为什么必须虚**：`Base* p = new Derived; delete p;`——析构非虚时 delete 静态绑定，只执行 ~Base，**Derived 新增的那半截资源原地泄漏**，程序还不报错；虚析构让 delete 按实际类型走完整的析构链。规则化表述：**任何要被基类指针 delete 的类，析构必须 public virtual**。

**拉开差距的深水区**：构造期间调虚函数没有多态（1.7 讲过"对象没造完之前还不是它自己"），析构期间同理——先拆到哪层就只认哪层的虚函数；虚函数与内联的矛盾——通过对象直接调用可内联，通过指针调用必然间接跳转，编译器自己会放弃内联（11.1）。

收尾：区别答"通道对强制"，构造答"vptr 鸡生蛋"，析构答"不虚只拆一半"。

> 面试官追问点：什么时候析构函数不需要虚？应答思路：类不被继承、或不通过基类指针删除——两者都成立时非虚析构反而更优（省 vptr 和虚调用）；工程上把"会不会被多态删除"当成接口设计决策写进文档，而不是无脑全加 virtual——**virtual 是合同的一部分，不是免费的安全带**。

#### 2.2 三种继承方式怎么区分？菱形继承问题如何解决

深度精讲见 11.6。

答：一句话定调，**public 继承是 is-a（接口照单全收），protected/private 继承是"按实现继承"的收窄；菱形继承的两份基类副本靠 virtual 继承压成一份，代价是把基类子对象的构造权上交给最终类**。

**三种方式的访问规则**：public 继承——基类的 public 成员在派生类仍是 public，父指针能指向子对象，这是唯一表达 is-a 的方式；protected 继承——基类的 public 和 protected 到派生类都变 protected，外界看不见，派生类内部可用；private 继承——全部变 private，连"孙类"也看不到。**后两种是"复用实现"而不是"复用接口"**——想用组合替代（has-a）时，EBO（1.10）是 private 继承仅存的正当用途。

**菱形继承的三重罪**：D 同时继承 B 和 C、而 B/C 都继承 A——D 对象里装着**两份 A 子对象**：访问 d.a_member 直接二义编译错（要写 d.B::a_member）；A 被构造两次；内存白白翻倍。经典受害者是 iostream 体系（istream、ostream 都继承 ios）。

**虚继承的解法**：B、C 改成 `virtual public A`——虚继承把"每条路径各带一份 A"改成"最终类统一持有一份共享的 A"。机制：A 子对象的位置不再固定，通过**虚基表（vbptr）记录偏移**间接定位；**A 的构造从 B/C 的责任上交给 D**——B、C 的构造函数里对 A 的初始化被忽略，由 D 直接调 A 的构造。完整内存布局见 11.6。

**拉开差距的深水区**：为什么 C++ 圈子共识是"少用多继承"——菱形要虚继承兜底、虚继承有间接寻址开销、构造权反转让代码难读，Java 干脆砍成"单继承加接口"；组合优于继承的工程法则——is-a 用 public 继承，其他场景优先想"能不能持有一个成员"而不是"再继承一层"。

收尾：三方式答"只有 public 是 is-a"，菱形答"两份副本三重罪"，解法答"virtual 继承压成一份、构造权上交"。

> 面试官追问点：虚继承下 B 的构造函数里对 A 的初始化为什么被忽略？应答思路：如果 B 照常初始化 A、C 也初始化 A，共享的那一份 A 就要被写两次——规则干脆规定"中间类不碰虚基"，只有最终类 D 有权构造 A；这解释了为什么虚继承类的构造函数写起来"和直觉不一样"，**是共享语义在构造期的必然推论**。

#### 2.3 虚函数表存放在哪里？多态调用是如何完成的

深度精讲见 11.1。

答：一句话定调，**vtable 编译期生成、放在只读数据段、同类的所有对象共享一份，每个对象自带 vptr；虚调用是"取 vptr、查表、间接跳转"三步，比普通调用多两次访存还挡住内联**。

**存放位置**：vtable 在编译期就填好了，链接后躺在 .rodata（只读数据段）——尝试改写它就是段错误（C 文件 2.7 的老朋友）。**一个类一张表**：同类全体对象共享；非虚函数和静态成员函数不进表（它们不需要运行期决议）。vptr 藏在每个对象头部，由构造函数逐层安装——基类构造先指基类表，派生构造再改写成自己的表（1.7 的"还没造完不是自己"）。

**多态调用的三步**：`p->f()` 编译成——第一步取对象头部的 vptr；第二步按编译期算好的固定偏移取出表项（函数地址）；第三步间接 call。**偏移在编译期已知**，所以运行期的全部代价是两次内存加载（vptr 和表项，通常都在缓存里）加一次间接跳转——几纳秒级，真正的代价是**挡住了内联**，热路径上这才是大头。

**多重继承的布局**：`class C : public A, public B` 的对象有两个 vptr（A、B 子对象各一）；C* 转 B* 时指针要加偏移做 this 调整；B 的虚表里 C 覆写过的函数表项是 **thunk**——先修正 this 再跳真实函数的小段胶水代码。讲得出 thunk，这题就从八股变成理解（11.1）。

**拉开差距的深水区**：vtable[-1] 是 typeinfo（typeid 和 dynamic_cast 的数据源）、vtable[-2] 是 offset-to-top（跨类型指针修正用）——dynamic_cast 的向下转型就是运行时沿 RTTI 链比对；对比 C 文件 4.2 的"函数指针表模拟多态"——C++ 的虚函数就是编译器替你生成那张 ops 表并把指针塞进每个对象，**语言机制没有魔法，只有自动化**。

收尾：位置答".rodata 共享一份"，调用答"三步固定偏移"，代价答"挡内联"，thunk 和 RTTI 槽位是深水区路标。

> 面试官追问点：为什么说虚函数的真正代价不是跳转而是挡内联？应答思路：现代 CPU 分支预测对间接跳转的命中率很高，几次访存加跳转只有纳秒级；但内联是优化的放大器——内联后才能常量传播、死代码消除、循环展开，虚调用像一道墙把这些优化全挡在函数边界外——**热点函数里的一次虚调用，失去的是整条优化流水线**。

#### 2.4 虚析构函数深入怎么设计？不写会带来什么问题

答：一句话定调，**基类析构不虚，delete 父指针只拆基类那一截，派生类的资源原地沉默泄漏；两条正规设计——要么 public virtual，要么 protected 非虚，把"删不全"和"不许删"分而治之**。

**不写虚析构的泄漏现场**：`Base* p = new Derived; delete p;`——delete 静态绑定到 ~Base，Derived 部分的成员（new 出来的 buffer、打开的 fd、持有的锁）**全部原地泄漏**，进程不崩、日志无声，valgrind 才能抓到（C 文件 2.6 的 still reachable / definitely lost 分级）。这是"设计期错误、运行期沉默"的典型代表，也是智能指针出现前 C++ 的头号资源事故源。

**两条设计路线**：类会被基类指针删除——析构 **public virtual**（多态基类的标配，2.1 的规则）；类不许通过基类指针删除（纯接口约束、或想禁用多态删除）——析构 **protected 非虚**：外部 `delete p` 直接编译错，派生类内部照常调用。**protected 把"删不全"这种运行期事故，前移成"不许删"的编译期错误**——错误越早暴露代价越小，这是这题的设计哲学。

**纯虚析构的冷知识**：可以声明 `virtual ~Base() = 0;` 让类变抽象，但**必须提供函数体**——派生类析构链的最后一步会调到基类析构，链接器需要它的定义；"纯虚"在这唯一一种场景下不代表"没有实现"。

**拉开差距的深水区**：`unique_ptr<Base>` 和 `shared_ptr<Base>` 在这事上的行为分岔——unique_ptr 的删除器随类型走，`unique_ptr<Base>(new Derived)` 不虚析构照样泄漏；shared_ptr 的控制块在构造时记住了**创建时的完整类型**，`shared_ptr<Base>(new Derived)` 析构时能正确调到 ~Derived——**同一个"父指针管子对象"，两种智能指针给出两种答案**，能讲清这层的候选人凤毛麟角。

收尾：泄漏答"只拆一半还无声"，设计答"public virtual 对 protected 非虚"，深水区答两种智能指针的行为分岔。

> 面试官追问点：为什么 shared_ptr 能"记住"实际类型而 unique_ptr 不能？应答思路：shared_ptr 的类型信息在**堆上的控制块**里，构造那一刻（还知道是 Derived）就把删除函数指针存进去，之后无论怎么拷贝转型，控制块不变；unique_ptr 运行期只有"裸指针加类型"，删除动作静态绑定到声明类型——**胖指针带状态、瘦指针零开销**，两种设计各有立场。

# 3.内存管理与智能指针

#### 3.1 new和malloc区别在哪？底层如何实现

深度精讲见 11.14。

答：一句话定调，**malloc 只给你一块裸内存，new 给你一个对象——new 是"operator new 分配 + 构造函数"两步，delete 是"析构 + operator new 释放"两步，失败行为一个返回 NULL 一个抛异常**。

**六个区别**：类型安全——new 返回具体类型指针（`int* p = new int`），malloc 返回 void* 要强转；构造析构——new 会调用构造函数、delete 调析构，malloc 只管字节（POD 无感、非 POD 天壤之别）；失败行为——malloc 返回 NULL、new 抛 bad_alloc（3.2 详谈）；身份——malloc 是库函数、new 是运算符（可按类重载，定制内存策略的入口）；大小——new 由编译器算 sizeof，malloc 手写；配套——new[]/delete[] 还会在头部记录元素个数供逐个析构（3.2）。

**new 的两步过程**：`new T(args)` = 先 operator new(sizeof(T)) 拿一块内存（operator new 内部通常就是调 malloc，C 文件 2.3 的整条分配链原样复用）→ 再在这块内存**原地**调构造函数。delete 反过来：先调析构 → 再 operator delete 释放。**"分配"和"构造"在语言层面是两个动作**，这是 placement new 存在的前提。

**placement new 的用法**：`new (buf) T(args)`——不在堆上分配，而是在调用者给的地盘 buf 上原地构造。三大用途：内存池（一次批发、零散原地构造，C 文件 2.4 的池子配上它才完整）、容器（vector 的 emplace_back 在预留空间上直接构造）、对象复用（析构后不还内存、再 placement new 一个新的）。配套纪律：**placement new 出来的对象必须显式调析构函数**（p->~T()），且只能析构一次。

**拉开差距的深水区**：operator new 可重载三级——全局、类级、带额外参数的 placement 版本，STL allocator 的 allocate 就是定制入口；new 出来的内存和 malloc 出来的不能混着释放（delete 一块 malloc 的内存是 UB）——**配对不是风格问题，是堆元数据的一致性问题**（C 文件 2.5）。

收尾：本质答"裸内存对完整对象"，两步答"分配加构造"，placement new 答"给地盘原地造、析构要手动"。

> 面试官追问点：为什么 placement new 的对象要手动调析构？应答思路：析构函数由 delete 触发，而 delete 的前半步是"调用 operator delete 释放这块内存"——placement new 的内存不是 operator new 给的，不能走 delete 全流程；所以拆开用：析构手动调、内存按它来的方式还（池子回收或根本不还）——**谁分配谁释放，构造析构与内存管理解耦**，这正是这题的设计内涵。

#### 3.2 new失败抛什么异常？与delete怎么配对

答：一句话定调，**new 失败默认抛 bad_alloc，nothrow 版才返回 nullptr；set_new_handler 是全局兜底钩子；new[] 与 delete[] 必须配对，因为数组头部藏了"元素个数"这张账单**。

**失败行为两套**：`new int[10]` 失败抛 std::bad_alloc——异常时代的正确姿势是 RAII 自动清理（栈回溯时局部对象逐个析构），而不是逐行判空；`new (std::nothrow) int[10]` 返回 nullptr——兼容老代码或异常被禁的嵌入式场景。**判空的错误习惯**：对普通 new 写 `if (p == nullptr)` 是死代码——它抛异常根本走不到判空那行。

**set_new_handler**：注册全局回调，operator new 分配失败时先调它——回调里可以释放缓存再返回重试、写日志、或干脆 terminate；返回后 new 重新分配，再失败再调（无限循环的可能要自己防）。这是"全局内存压力的最后一道闸门"。

**new[]/delete[] 为什么必须配对**：`new T[10]` 分配时在内存头部多存一个元素个数（cookie）——delete[] 读它**逐个调用析构**再按整块释放；用 delete（不带 []）——只析构第一个元素，释放地址还偏了一个 cookie 的位置。**析构漏九个、free 地址错位，泄漏和堆破坏二选一**，有时还能都拿到。反向配对（new 单对象配 delete[]）同样是 UB。

**配对总表**：malloc/free、new/delete、new[]/delete[]、placement new/显式析构——**四套体系内部配对，跨体系混用全是 UB**；工程结论：裸 new 能不用就不用（智能指针和容器代劳），必须用时在类的封装边界内配对。

**拉开差距的深水区**：类带自定义 operator new 时，new[] 的 cookie 布局由实现决定（有的编译器对"平凡析构"的类还能优化掉 cookie，直接省掉那几个字节）——所以 sizeof 和"实际分配大小"之间的关系是实现细节，别拿来算术；C++17 的对齐 new——over-aligned 类型自动走带对齐参数的 operator new 重载（C 文件 3.5 的对齐话题在 C++ 侧的收口）。

收尾：失败答"抛 bad_alloc 加 nothrow 逃生口"，handler 答"全局兜底钩子"，配对答"四套体系各管各的"。

> 面试官追问点：为什么 delete[] 需要知道元素个数而 free 不需要？应答思路：free 只要"这块内存多大"（chunk 头里有，C 文件 10.2），delete[] 还要"这块内存里有几个对象要析构"——析构次数是类型语义，裸字节大小推不出来，只好分配时把个数记进 cookie——**这个字节就是"C++ 对象模型"比"C 内存模型"多付的账**。

#### 3.3 三种智能指针怎么选择使用？各自的原理是什么

深度精讲见 11.2。

答：一句话定调，**默认 unique_ptr（零开销独占），确需共享才 shared_ptr（控制块计数），只观察不拥有用 weak_ptr——选型顺序就是把所有权从独占到共享到旁观捋一遍**。

**unique_ptr**：独占所有权，不可拷贝只能移动——所有权语义直接写进类型系统（赋值给另一个 unique_ptr 编译错）。**零开销**：sizeof 等于裸指针（无状态删除器靠 EBO 不占空间，1.10）；数组特化 unique_ptr<T[]> 自动把 delete 换成 delete[]。**默认首选**：能用独占就独占，性能和裸指针一样、责任清晰。

**shared_ptr**：共享所有权靠**控制块**——堆上一个独立结构，两个原子变量 use_count（强引用）和 weak_count（弱引用）。**线程安全的精确边界**：多线程同时拷贝/析构不同的副本，计数原子地正确；但对象本身的并发读写、以及对同一个 shared_ptr 实例的并发操作，都不安全——**"计数安全"不等于"内容安全"**。致命纪律：同一个裸指针构造两次 = 两个控制块 = 双重析构；类内部要拿自身指针用 enable_shared_from_this（内部藏一个 weak_ptr）。

**weak_ptr**：只增加 weak_count、不延长对象生命周期——**专治循环引用**：A、B 互持 shared_ptr 时 use_count 永不归零、双双成漏；把一方改成 weak_ptr，环就断了。使用前 lock() 升级成 shared_ptr（原子检查对象还活着没），活着的拿到、死掉的拿到空。

**选型口诀**：**默认 unique_ptr，共享才 shared_ptr，观察用 weak_ptr，裸指针只做"借用"不做"拥有"**。

**拉开差距的深水区**：unique_ptr 的移动语义让它在函数间"传递所有权"（工厂返回值、容器存储）；shared_ptr 的拷贝是原子操作——高频路径上多一次原子加也心疼，对象池或侵入式引用计数（intrusive_ptr）是性能敏感场景的替代；手写简化版 shared_ptr 考的是"拷贝加计数、析构减计数归零释放"加"防自赋值"三件事（11.2 有完整控制块剖析）。

收尾：三种各一句话——unique 独占零开销、shared 控制块共享、weak 观察断环。

> 面试官追问点：为什么 weak_ptr 的 lock() 能"原子地"确认对象活着？应答思路：lock 内部对控制块做原子的"use_count 是否为零"检查加提升，两步合成一个 CAS——如果分开"先检查再提升"，检查完到提升前对象可能刚好被最后一个 shared_ptr 释放，拿到的是悬空——**这是并发版"检查与动作的时间窗"问题**（对照 C 文件 7.1.3 的条件变量丢失唤醒）。

#### 3.4 make_shared优势在哪？比直接new好在哪

答：一句话定调，**make_shared 把对象和控制块合并成一次分配——少一次 malloc、缓存局部性好、还堵住异常安全的历史漏洞，代价是 weak 活着时对象内存要陪葬**。

**三连赚**：**一次分配**——`shared_ptr<T>(new T)` 要 new 一次对象、再分配一次控制块，两次堆分配两次开销；make_shared 把两者合并成**一整块**，malloc 少调一次。**缓存局部性**——对象和控制块物理相邻，访问计数和访问数据大概率同一个缓存行搞定。**异常安全**——C++17 之前 `foo(shared_ptr<T>(new T), may_throw())` 的求值顺序允许"先 new、再调第二个参数、抛异常"——new 出来的指针还没进 shared_ptr 就泄漏了；make_shared 是单次调用，不存在这个窗口（C++17 改了求值顺序，但写 make_shared 依旧是最省心的形态）。

**代价与边界**：一整块内存要等 use_count 和 weak_count **双归零**才能释放——weak_ptr 长寿的场景下，大对象早就析构了、**内存却要陪着 weak 一起等**（对象析构是及时的，内存回收不是）；**不能自定义删除器**（需要时退回 shared_ptr 构造版）；**私有构造函数的类用不了**（make_shared 要替你调构造，而它不是你 friend）。

**选型规则一句话**：默认 make_shared，两个例外——要自定义删除器、或"大对象加长寿 weak_ptr"的内存敏感场景，才回 shared_ptr<T>(new T) 分离分配。

**拉开差距的深水区**：make_unique 为什么 C++14 才补上——make_shared 有"合并分配对 weak 的影响"这种性能权衡需要委员会慢慢吵，make_unique 没有任何争议（不共享、无控制块），纯属"没争议反而来得晚"的趣闻；顺带能答 unique_ptr 一律配 make_unique——统一写法消灭"裸 new 出现在表达式里"的所有漏洞。

收尾：三赚答"一次分配、局部性、异常安全"，代价答"weak 陪葬加不能定制删除器"，规则答"默认 make、例外才裸 new"。

> 面试官追问点：为什么对象析构了、内存却可以不还？应答思路：析构（调 ~T）和释放（operator delete）是两个动作——make_shared 的一整块里，use_count 归零只触发析构对象的那一段，控制块所在的那段内存还要等 weak_count 归零；**"对象死了"和"地皮退了"在共享指针的世界里是两件事**，这正是 3.1 讲的"构造析构与内存管理解耦"在共享场景的镜像。

# 4.现代C++特性

### 4.1 移动语义与类型推导（4 题）

#### 4.1.1 左值和右值怎么区分？移动语义的原理是什么

深度精讲见 11.3。

答：一句话定调，**左值有名字能取址、右值是"没身份的将亡之物"；移动语义是给右值发一张"可以掏空你"的许可证——资源偷过来、指针置空，把深拷贝降成指针搬家**。

**值类别三分**：左值——有名字、可取地址、生命周期归作用域管（变量、成员、解引用结果）；纯右值——字面量、按值返回的临时对象，"生来就是为死"的值；将亡值（xvalue）——被 move 转换过的左值，身份还是那堆资源、标签已是"随便拿"。**快速判据：能对它取 & 的就是左值**。

**移动语义的原理**：拷贝构造复制内容（深拷贝的 O(n)），移动构造**只偷指针**——把源对象的资源句柄拿过来、源指针置空，源对象留在"有效但未指定"状态（能析构、能重新赋值，但内容别假设）。开销从 O(n) 降到 O(1)，vector 扩容、字符串拼接、大对象传递全靠它翻身。

**三个配套件**：std::move——static_cast<T&&>，零指令，只负责把左值"重贴成右值标签"骗过重载决议（4.1.2 详谈）；std::forward——万能引用加引用折叠实现**值类别透传**（参数原来是左值转发后还是左值，规则在 4.2.3）；RVO/NRVO——编译器在调用方栈上直接构造返回值，连移动都省，C++17 对纯右值强制省略——**所以 return std::move(local) 是反模式：它把可 RVO 的纯右值强行变成将亡值，亲手禁用了优化**。

**拉开差距的深水区**：右值引用变量本身是左值（有名字）——`void f(T&& x)` 里想再移动 x 必须再写 std::move(x)，这是最常挂的坑；auto&& 是万能引用（auto 在推导语境）而 void f(Widget&&) 是纯右值引用（类型定死）——4.2.3 的判定条件在这提前预热。

收尾：区分答"名字加取址"，原理答"偷指针置空源"，配套答"move 重贴标签、forward 透传、RVO 直接构造"。

> 面试官追问点：为什么拷贝构造不能替代移动构造？应答思路：能，但代价是白白付出深拷贝——vector 扩容搬一万个元素，拷贝版每人复制一份字符串，移动版每人挪一根指针；**移动语义的本质不是"新功能"而是"把'将亡之物不必保留'这条信息喂给类型系统"**，让编译器有依据选便宜的那条路。

#### 4.1.2 std::move做了什么？被move后状态如何

答：一句话定调，**std::move 编译后一个字节代码都不生成，它只是重贴右值标签的 static_cast；真正搬东西的是移动构造函数；被 move 后的对象处于"有效但未指定"状态**。

**move 的真身**：`static_cast<T&&>(x)`——把左值表达式转换成将亡值，作用只有一个：让重载决议在"拷贝版本 T&"和"移动版本 T&&"之间选中后者。**它不做任何"搬"的动作**——没写移动构造的类，move 之后照样走深拷贝，这是第二常见的误解（第一常见是以为 move 会空指针崩溃）。

**被 move 后的状态**：标准术语叫"有效但未指定（valid but unspecified）"——析构安全、赋值安全、可以调 empty()/size() 这类不依赖具体内容的接口；但 **string s2 = std::move(s1) 之后 s1 里还剩几个字符是实现说了算**，读它的值是逻辑错误不是编译错误。纪律：被 move 的对象只做"重新赋值"或"销毁"两种操作。

**五法则的移动侧**：写了移动构造/移动赋值，析构和两个拷贝同样要通盘考虑（1.8）——移动只是把资源换主，资源的生老病死还是要有完整的管理链。没写移动构造时编译器在"没声明拷贝、没声明析构"的条件下才自动生成——**手写了析构的类往往连移动都自动没了**，退化回拷贝是隐形性能事故。

**noexcept 与 vector 扩容**：扩容搬迁用的是 move_if_noexcept——**移动构造标了 noexcept 才敢用移动**：扩容到一半抛异常，移动过的元素已经被掏空、回滚不了；拷贝版旧数组完好无损可安全回滚。所以**给移动构造标 noexcept 不只是风格，它直接决定 vector 扩容快十倍还是慢十倍**——vector<T> 搬迁前拿 std::move_if_noexcept 探测，就是这条规则在库里的落点。

**拉开差距的深水区**：成员函数的引用限定符（`void f() &&`）让"只许右值调用的接口"成为类型系统的一部分——std::optional::value() 的移动重载就是靠它保证"从将亡对象里搬走内容"只在正确的值类别上发生。

收尾：move 答"零指令只贴标签"，状态答"有效但未指定、只许重赋值或销毁"，noexcept 答"扩容快慢的开关"。

> 面试官追问点：为什么移动构造必须标 noexcept 而 vector 才肯用？应答思路：vector 的扩容合同是"强异常安全"——失败时旧数组必须原样保留；移动是破坏性搬运，半路抛异常等于旧数据也丢了；拷贝是非破坏性的，失败时释放新数组即可回滚——**noexcept 是移动操作"可被更强保证使用"的资格证**。

#### 4.1.3 auto的推导规则是什么？decltype怎么推导

答：一句话定调，**auto 走模板 T 的推导规则（剥引用剥顶层 const），decltype 原样报类型不动 Cv；auto 是"让编译器替你写"，decltype 是"让编译器替你读"——一个省事一个较真**。

**auto 三条规则**：`auto x = expr` 按模板实参推导——**丢弃引用和顶层 const**（const int& 进来，x 是 int 副本）；auto& 保住引用、auto* 只接指针、auto&& 是万能引用（左值推成 &、右值推成 &&，4.2.3）。auto 也能当返回值（C++14）——lambda 和模板函数的救星，但**公共 API 慎用**：返回类型藏在实现里，读接口的人要靠文档。

**decltype 的两条路**：给它**变量名**——报声明的完整类型（含引用和 const）；给它**表达式**——按值类别裁决：纯右值给 T、左值给 T&、将亡值给 T&&。**最阴的坑：decltype(x) 是 int，decltype((x)) 是 int&**——双括号把"变量名"变成了"左值表达式"，值类别规则接管，结果多出一个引用。

**decltype(auto)**（C++14）：把 decltype 的较真规则接到 auto 的省事语法上——**转发函数的完美返回**：`decltype(auto) f() { return g(); }` 原样保留 g() 返回的引用和 const，普通 auto 会把 & 剥掉导致悬空或拷贝。

**结构化绑定**（C++17）：`auto [k, v] = map_entry;`——编译器生成隐藏的引用成员，k 和 v 是别名不是拷贝；配合 auto&/const auto& 控制是否拷贝整个 entry——**它是"给结构成员起短名"的语法糖，不是"解构赋值"**。

**拉开差距的深水区**：auto 推导和模板推导的唯一差异——`auto x = {1, 2}` 推成 initializer_list 而模板不会；braced-init-list 的特殊规则是 auto 的"方言"。auto 用在循环里的一处经典陷阱：`for (auto e : big_map)` 每轮深拷贝元素——**该写 const auto& 或 auto&& 的地方写 auto，等于在循环里白搬 N 次家**。

收尾：auto 答"剥引用剥顶层 const"，decltype 答"变量名报类型、表达式看值类别加双括号坑"，decltype(auto) 答"转发返回的完美形态"。

> 面试官追问点：什么时候必须用 decltype 而不能用 auto？应答思路：需要"精确到引用和 const"的场景——转发返回值（auto 剥 & 直接悬空）、模板元编程里提取依赖类型（typename T::iterator 加 decltype 探测表达式类型）；**auto 是给人省事的（损失 Cv 信息无所谓），decltype 是给机器转发的（差一个 & 都不行）**。

#### 4.1.4 std::function与bind怎么配合使用？

答：一句话定调，**function 是"什么可调用对象都能装"的万能容器，靠类型擦除实现统一接口；bind 是"预绑参数"的适配器，现代代码里九成已被 lambda 取代**。

**function 的原理**：类型擦除——内部用一个小缓冲区（SBO，小对象优化）直接装下小的 lambda，装不下的去堆上；调用时经一次间接跳转分发到真正的 operator()。**代价清单**：间接调用挡内联（对照 2.3 的教训）、拷贝 function 要拷贝捕获状态、构造可能分配堆——热路径上这三条都心疼。

**bind 的用法与退场**：`auto f = std::bind(func, _1, 42, _2)` 把第二个参数钉死成 42、留下两个占位符——参数重排、预绑定、适配老接口三招。**被 lambda 取代的原因**：lambda 同样能捕获、还能移动捕获、代码就地可读、没有"占位符顺序是绑定参数序"这种反直觉——`[x = std::move(a)](int y) { func(y, 42); }` 语义直白得多。bind 仅存的场景：C 风格函数指针兼容、极老代码维护。

**三者选型表**：回调类型编译期已知、追求性能——**模板参数**（调用点内联，零开销）；要装"异构回调集合"（容器存各种 callable、跨接口传递）——**std::function**（统一类型是刚需）；就地轻量定义——**lambda**（默认答案）。

**拉开差距的深水区**：function 的 SBO 阈值——标准库实现通常给 2-3 个指针的栈上空间，超过就堆分配——**捕获大的 lambda 装进 function 每次拷贝都是一次 malloc**，高频回调场景要测；C++23 的 move_only_function 把"不可拷贝可移动"的闭包也纳入容器（独占回调、网络 handler 的正确容器）。

收尾：function 答"类型擦除加间接跳转"，bind 答"被 lambda 取代的占位符适配器"，选型答"模板要性能、function 要统一、lambda 要就地"。

> 面试官追问点：为什么说 function 挡内联而模板不挡？应答思路：模板参数在编译期类型确定，调用点直接静态绑定成普通函数调用，内联一路绿灯；function 运行期才知道装的是谁，调用必须经函数指针间接跳——**和虚函数同款的结构，代价也同款**（2.3），这道题是"静态多态 vs 动态分发"在回调世界的一次重演。

### 4.2 Lambda与模板（6 题）

#### 4.2.1 Lambda的捕获方式有哪些？底层如何实现

深度精讲见 11.7。

答：一句话定调，**Lambda 是编译器生成的匿名类——捕获列表就是成员变量，operator() 就是函数体；值捕获是拷贝进成员、引用捕获是成员存引用，悬空引用是它唯一的毒牙**。

**捕获全家福**：`[x]` 值捕获（拷贝一份进闭包）、`[&x]` 引用捕获（存引用，改的是本体）、`[=]` 全值、`[&]` 全引用；`[this]` 捕获 this 指针（成员访问都经它，**本质是引用捕获的变体**——对象死了成员全悬空）、`[*this]`（C++17）拷贝整个对象快照；**初始化捕获** `[y = std::move(x)]`（C++14 广义捕获）——把 move-only 对象搬进 lambda 的唯一姿势。

**mutable 的语义**：值捕获默认生成 const operator()——闭包里的副本只读；mutable 去掉这个 const，**修改的是闭包里的副本不是外面的原值**（每次调用同一闭包才跨调用保留修改）。

**底层实现**：编译器把 lambda 翻译成一个匿名类——捕获成员按捕获列表生成，函数体成为 operator()。**无捕获的 lambda 能隐式转换成函数指针**（没有状态的闭包和函数等价），所以它能传给 C API 当回调（pthread_create 的老朋友）；带捕获的不行——有状态，函数指针装不下。

**悬空引用——唯一的毒牙**：`[&]` 捕局部变量，lambda 生命周期超过作用域（存进回调表、塞进线程、延迟执行）→ 引用悬空、UB。**纪律：同步就地执行才许 [&]；任何异步、存储、跨线程场景一律值捕获或 move 捕获**——`[x = std::move(obj)]` 是异步世界的标准答案。

**拉开差距的深水区**：捕获对 sizeof 的影响——[&] 只存一根栈指针？不对，通常每个引用一个成员（8 字节/个），[=] 大对象捕获会让闭包胖到 function 装不下堆分配（4.1.4 的 SBO）；泛型 lambda（auto 形参，C++14）的 operator() 是模板成员——一个闭包类型适配多种参数。深挖见 11.7。

收尾：捕获答"成员变量的生成规则"，底层答"匿名类加 operator()"，纪律答"异步必值捕获或 move 捕获"。

> 面试官追问点：为什么捕获列表里的 this 是"最隐蔽的悬空"？应答思路：`[&]` 会顺手把 this 也引用捕获，而成员函数里的 lambda 十有八九访问成员——对象析构后回调触发，读的是废墟上的字段；C++17 特意发明 [*this] 就是为了给"我要快照"一个显式语法——**[&] 在成员函数里等于埋雷，*[this] 才是排雷按钮**。

#### 4.2.2 模板特化偏特化是什么？SFINAE如何工作

深度精讲见 11.13。

答：一句话定调，**特化是给某个特定类型定制一份实现，偏特化是给"某一类形状"的类型定制；SFINAE 是"替换失败不算错误"——重载竞赛里摔倒的候选安静退场，不惊动裁判**。

**特化与偏特化**：全特化 `template<> class vector<bool>`——所有模板参数钉死，bool 版按位压缩是教科书案例；偏特化 `template<class T> class vector<T*>`——只定型"指针家族"，T* 共用一份指针特化逻辑。**函数模板没有偏特化**（只有全特化和重载）——需要"按形状分派"时用重载或转到类模板的辅助结构上（traits 的经典舞台）。

**SFINAE（Substitution Failure Is Not An Error）**：模板实参替换进签名时产生的**"只有签名层面的失败"**不算编译错，只让这个候选从重载集出局。**惯用法 enable_if**：`template<class T, typename = std::enable_if_t<std::is_integral<T>::value>> void f(T);`——T 是整数类型时"有 ::type"、替换成功参与竞争；不是时没有 ::type、签名替换失败、静默退场。**失败只许发生在"签名里"，函数体内的错误照样报**——这是 SFINAE 和 if constexpr 的分界。

**三种用法**：按类型属性启用/禁用重载（is_integral、is_pointer 家族）；检测类有没有某成员（void_t 惯用法——有 ::type 就能匹配、没有就 SFINAE 出局）；标签分派的老配新用。

**拉开差距的深水区**：C++20 的 concepts 把这一切语法化——`template<std::integral T> void f(T);` 一行替代 enable_if 的天书，报错信息从"三层模板展开"变成"integral 不满足"；**concepts 不是新能力，是 SFINAE 的官方糖衣**——能讲出这层演进关系，说明你不是背历史而是理解动机。深挖见 11.13。

收尾：特化答"钉死全部对定型一类"，SFINAE 答"签名失败安静退场"，深水区答"concepts 是 SFINAE 的糖衣"。

> 面试官追问点：SFINAE 和 if constexpr 都能"按类型裁剪"，什么时候用谁？应答思路：SFINAE 作用在**签名**——决定"这个函数参不参加重载竞争"（影响接口集合，编译期选择给谁）；if constexpr 作用在**函数体**——同一个函数内部按类型选分支（实现内部的裁剪）；**接口层的分流用前者，实现层的分流用后者**，混用多半是设计还没想清。

#### 4.2.3 万能引用T&&是什么？引用折叠规则怎么算

答：一句话定调，**T&& 出现在"类型正在被推导"的语境里是万能引用（左值右值都收），出现在类型定死的地方只是普通右值引用；折叠四式一句话——只有 && 碰 && 才是 &&，其余全折成 &**。

**万能引用的判定**：必须同时满足两条——T 是正在推导的模板参数（或 auto&&），且参数恰好形如 T&&。`template<class T> void f(T&& x)` 是万能引用（T 随调用现场推导）；`void f(Widget&& x)` 不是（类型定死，纯右值引用）；**`const T&&` 不是**（const 挡住了推导语境）；类模板成员 `void f(T&&)` 要看 T 是类实例化时定死的（成员函数随类定型）——多半不是。

**折叠四式**：`& + & = &`、`& + && = &`、`&& + & = &`、`&& + && = &&`。**记忆法：引用是传染的，只要沾上一个左值引用就全是左值引用**。C++ 不存在"引用的引用"，折叠规则是模板推导中 T 和 T&& 组合时的"合法化程序"。

**万能引用的接收逻辑**：传左值 widget → T 推成 Widget& → 参数类型 Widget& && 折叠成 Widget&（左值引用，稳稳接住）；传右值 Widget 临时对象 → T 推成 Widget → 参数类型 Widget&&（右值引用，吃掉将亡值）。**一个 T&& 两种身份，靠 T 里有没有藏 & 区分**——这也是 std::forward 能工作的全部地基。

**与完美转发的闭环**：std::forward<T>(x) 是"条件转换"——T 是 Widget&（说明来的是左值）就转回左值引用，T 是 Widget（来的是右值）就转成右值引用——**把参数来时的值类别原样透传到下一层**（4.1.1 的闭环在这补完）。

**拉开差距的深水区**：auto&& 也是万能引用（auto 在推导语境）——范围 for 里 `for (auto&& e : container)` 是"万能元素引用"，配合 decay-copy 系列惯用法出现在标准库源码各处；传数组或函数类型时的退化规则（数组退化指针）会让 T 的推导多一层花样，能主动提一句就是加分。

收尾：判定答"推导语境加恰好 T&&"，折叠答"沾 & 全 &"，作用答"forward 值类别透传的地基"。

> 面试官追问点：为什么 std::forward 需要 T 显式指定而 std::move 不用？应答思路：move 的目标永远唯一（变右值），不需要信息；forward 有两个方向（保持左值 or 变右值），方向信息藏在模板参数 T 里——调用方显式写 forward<T> 就是在告诉它"按这个方向转"；**move 是无条件转换、forward 是有条件转换，参数 T 就是那个条件**。

#### 4.2.4 可变参数模板的展开方式？折叠表达式怎么写

答：一句话定调，**参数包的展开三板斧——递归加终止重载、逗号表达式老 trick、C++17 折叠表达式一统天下；sizeof... 是唯一能"数"参数包的操作**。

**递归展开（经典版）**：每层吃掉一个参数、剩下的转发给下一层，配一个零参数的重载收尾：

```cpp
void print() {}                              // 终止重载
template<class T, class... Rest>
void print(T first, Rest... rest) {
    std::cout << first;
    print(rest...);                          // 递归吃包
}
```

**折叠表达式（C++17，现代版）**：`(std::cout << ... << args);` 一行替代整段递归——**四种形态**：一元左折、一元右折、二元左折、二元右折（有无初值、从哪头结合的排列组合）。求和写 `(args + ...)`、全真写 `(... && args)`、顺序打印写 `(std::cout << ... << args)`——**递归版编译器展开后生成的本来就是一串调用，折叠表达式只是省掉了手写递归的胶水**。

**sizeof... 的用法**：`sizeof...(args)` 编译期得参数个数（数的是元素不是字节）；参数包**只能整体展开，不能按下标取第 N 个**——要取就得配合 tuple 的 get 或首尾拆递归。

**老 trick 一枚**：C++11 时代的逗号展开 `int dummy[] = { (print(args), 0)... };`——利用数组初始化强制顺序求值；折叠表达式出现后它进了博物馆，但老代码里要认得出来。

**拉开差距的深水区**：完美转发的变长版 `template<class... Args> emplace(Args&&... args) : val(std::forward<Args>(args)...)`——**参数包加万能引用的组合**是容器 emplace 系列的全部原理：一个展开号同时转发 N 个参数、保持各自值类别；折叠表达式做编译期计算——`((N *= Args::value), ...)` 编译期连乘，运行期零成本。

收尾：三板斧答"递归、逗号、折叠"，sizeof... 答"数元素不数字节"，深水区答"emplace 的原理就是这题"。

> 面试官追问点：为什么参数包不能像数组那样 args[0] 取值？应答思路：参数包是**编译期的异构集合**——每个元素类型都可以不同，没有统一的下标语义；按下标取本质是"编译期查表"，得转成 tuple 用 get——**异构集合的下标是类型级别的（tuple_element），不是数值级别的**，这道题考的是对"参数包本质是类型集合"的理解。

#### 4.2.5 模板实现为什么放头文件？两种实例化怎么分

答：一句话定调，**模板不是代码而是"生成代码的配方"，编译器实例化时必须看见完整定义，而 C++ 的编译单元互相是瞎子——所以定义只能进头文件；显式实例化是"替你在我的 cpp 里生成一份"的补充手段**。

**为什么必须头文件**：`vector<int>` 用的那一刻，编译器要把 T=int 代进模板**生成真实代码**（实例化）——生成需要看见完整定义。声明在头文件、实现写在 .cpp：使用者的编译单元 include 的只有声明，实例化不出代码，链接期 undefined reference。**普通函数只要声明就能编（地址留给链接器），模板不行——它要先"造"出函数才谈得上地址**。

**隐式实例化（默认）**：谁用谁造——每个用 f<int>() 的 .cpp 都生成一份代码，链接器靠**模板实例的弱符号机制**（C 文件 6.4 的老朋友）自动合并成一份；省心，但每个编译单元都要解析完整模板定义——**编译时间的大头**。

**显式实例化**：在一个 .cpp 里写 `template class vector<MyType>;`（类）或 `template void f<int>(int);`（函数）——主动生成这一份；其他单元 extern 声明引用它。**两大用途**：想把模板实现藏进 .cpp（发布库不想暴露源码、想给二进制 ABI 上保险）；削减编译时间（只在一处展开）。代价：必须手动列出要实例化的类型清单，漏一个就是链接错。

**拉开差距的深水区**：C++11 的 extern template——显式声明"这个实例别在本单元生成，用别处的"，预编译头大户（ios 的 operator<< 家族）靠它砍掉海量的重复实例化；**模板的"编译防火墙"困境**——concepts 和 modules（4.3.2）都在从不同角度削这座大山：modules 让"导出编译好的定义"成为可能，模板头文件依赖是它们最直接的受益场景之一。

收尾：原因答"配方要看见全文才能造"，隐式答"谁用谁造加弱符号合并"，显式答"一处造、别处 extern、清单要自己管"。

> 面试官追问点：为什么链接器能把各单元重复生成的模板实例合并成一份？应答思路：编译器给隐式实例标的是弱符号（C 文件 6.4），链接器允许多个弱定义共存、任选其一——普通函数的强符号撞上就报 multiple definition；**模板从语言设计上就依赖弱符号机制**，这题把 C 链接器和 C++ 模板串成了一条线。

#### 4.2.6 if constexpr怎么裁剪？与普通if差在哪

答：一句话定调，**普通 if 两个分支都得是合法代码，if constexpr 在编译期把不成立的分支整个丢弃——假分支里写的代码可以对当前类型不合法，这是模板代码的一次大解放**。

**裁剪机制**：`if constexpr (std::is_integral_v<T>)`——条件在编译期求值，不成立的分支**不实例化**：真分支里用 T 做整数运算、假分支里调 T::begin()，两边各自只在条件成立时才检查合法性。**普通 if 没有这个待遇**：哪怕运行期永远走左分支，右分支的代码也必须编译通过——模板参数相关的"类型专属操作"在普通 if 里直接报错。

**与普通 if 的本质区别一句话**：普通 if 是"运行期选一条路走、两条路都得修"；if constexpr 是"编译期就把没选的路拆掉"。**凡是分支合法性依赖模板参数的条件，必须 if constexpr**。

**替代 tag dispatch 的老写法**：从前按类型分派要写两个重载加 iterator_traits<It>::iterator_category 标签结构体各领一条路——if constexpr 一条函数体内嵌全部分支，**从"重载集分派"变成"单函数内裁剪"**，可读性和维护性双赢；std::advance、distance 的实现都经历过这次改写。

**一个易混点**：if constexpr 的条件是"编译期常量表达式"，但不能把运行期变量塞进去——`if constexpr (n > 0)` 里 n 是变量直接编译错；**它裁的是类型的不确定性，不是值的不确定性**。

**拉开差距的深水区**：未取分支里**模板化的代码**不实例化，但**非模板的语法错误**照样报——裁剪豁免的是"类型相关的不合法"，不是"随便写错"；C++17 之前的等价写法是 enable_if 加两个重载（4.2.2 的分工：接口层 enable_if、实现层 if constexpr）；折叠表达式加 if constexpr 组成的编译期算法库（编译期排序、编译期字符串）是模板元编程的进阶玩具。

收尾：机制答"假分支不实例化"，区别答"两条路都修对拆掉一条路"，定位答"实现层裁剪，接口层仍归 SFINAE"。

> 面试官追问点：if constexpr 的 else 分支里 return，会怎样？应答思路：被丢弃分支的 return 不参与返回类型推导——真分支 return 42、假分支 return 3.14 时，auto 返回类型只看活下来的分支；这正是"裁剪"语义的延伸——**被扔掉的代码连"发言权"都没有**，返回类型推导自然也忽略它。

### 4.3 新标准特性（2 题）

#### 4.3.1 C++11到17的核心特性有哪些？各自怎么用

答：一句话定调，**C++11 是分水岭（自动类型、移动语义、并发一整套），14 是小修小补，17 是工程实用件大礼包——面试按"这个特性解决什么痛点"来答，比背清单高两个段位**。

**C++11（重点全在这）**：auto 与 decltype（4.1.3）；右值引用与移动语义（4.1 的整章地基）；lambda（4.2.1）；nullptr——类型安全空指针，终结"NULL 是 0、0 是整数重载选错"的历史惨案；范围 for（就是 auto&& 加 begin/end 的语法糖）；初始化列表与统一初始化 `{}；override/final（1.6 的防手滑）；enum class（带作用域的强枚举，不再隐式转 int）；智能指针（第 3 章）；std::thread 与 atomic（第 7 章）；constexpr（编译期函数的起点）；可变参数模板（4.2.4）。

**C++14（小版本三件套）**：泛型 lambda（参数写 auto）；函数返回类型推导；make_unique（3.4 的"来得晚"趣闻）。

**C++17（工程实用件）**：结构化绑定（4.1.3 的"给成员起短名"）；if constexpr 与折叠表达式（4.2 的两大裁剪）；**std::optional**——"可能没有值"的类型化表达，终结哨兵值和 magic number（-1 表示失败的时代）；**std::variant**——类型安全的 union，配 visit 做"按类型分派"；**string_view**——零拷贝字符串切片（6.4 的生命周期陷阱）；并行算法（std::sort 加个执行策略参数就多线程）。

**拉开差距的深水区**：答清单不如答"为什么 11 是分水岭"——移动语义重定义了值语义、lambda 重定义了回调、thread 重定义了并发支持（语言级 memory model）；**C++ 从 11 开始"每三年一版"的节奏**，17 的 optional/variant/string_view 是"吸收社区库（Boost.Optional、Boost.Variant）进标准"的代表——能讲出特性来源的演进史，说明你真用过而不是背过。

收尾：11 答分水岭三件套（移动、lambda、并发），14 答小修，17 答 optional、variant、string_view 三实用件。

> 面试官追问点：项目里只准升到 C++11，你最想念 14/17 的哪三个特性？应答思路：挑"直接消灭样板代码"的说——结构化绑定（少写 .first/.second）、if constexpr（消灭 tag dispatch 的双函数）、make_unique（三行变一行）；**答"想念什么"比答"有什么"更能暴露真实使用经验**——这是这题的隐藏考点。

#### 4.3.2 C++17与C++20新增了哪些重要特性？

答：一句话定调，**17 把工程痛点扫干净（optional、variant、string_view、结构化绑定），20 是范式升级四件套（concepts、coroutines、ranges、modules）——17 是"补工具"，20 是"换打法"**。

**C++17 补工具**：折叠表达式（4.2.4 一行吃参数包）；CTAD 类模板实参推导——`std::pair p(1, 2.0)` 不用再写模板参数，构造函数自动反推；if constexpr（4.2.6）；optional/variant/any 三件套（4.3.1）；string_view；并行算法；内联变量（头文件里定义全局变量不再 ODR 出事，C 文件 6.4 的 C++ 解）。

**C++20 四件套**：**concepts**——模板约束一等公民，`template<std::integral T>` 替代 enable_if 天书，报错信息从"三层模板展开"变成"约束不满足"（4.2.2 的糖衣说）；**coroutines**——co_await/co_yield/co_return 三个关键字加编译器状态机改写，异步代码写成交替执行的同步样貌，**是语言级底座不是库**（库层的 generator/task 要自己搭或用 cppcoro）；**ranges**——`views::filter | views::transform` 管道式惰性算法链，配投影参数（`ranges::sort(v, {}, &S::age)` 按 age 排）终结仿函数样板；**modules**——import 替代 #include 的文本包含，编译隔离和编译速度的世代升级（4.2.5 的头文件大山被正面强拆）。

**三个小而甜**：spaceship `<=>`——一次定义三路比较，全套六个比较运算符编译器自动合成；`std::format`——类型安全的 printf 终于进标准；constexpr 大扩容（string、vector 可编译期用）。

**拉开差距的深水区**：**coroutines 的三层结构**——关键字（语言）、promise_type（定制点）、库（generator/task）——"为什么 C++20 只给了底座没给 generator" 是标准库体积和政治权衡的经典八卦；ranges 的惰性求值——**管道每过一层是包一层迭代器，零拷贝但别指望零开销**，性能敏感处要测。

收尾：17 答"扫痛点"，20 答"concepts 换写法、coroutines 换异步、ranges 换算法、modules 换编译"。

> 面试官追问点：为什么 C++20 的协程被吐槽"难用"？应答思路：标准只给了 co_await 机制和 promise_type 定制点，连最基础的 generator 都要用户自己写——语言层追求最大灵活性、把易用性留给库，结果就是"底座先行、体验后补"（C++23/26 在补）；对比 Go 的 goroutine 一把梭，**C++ 的选择是"给框架作者造工具"而不是"给应用开发者造工具"**——能辩证答出这层设计哲学，这题就到顶了。

# 5.关键字与类型系统

#### 5.1 C++四种类型转换怎么用？各自安全性如何

深度精讲见 11.8。

答：一句话定调，**static_cast 干常规转换、dynamic_cast 靠 RTTI 做安全向下转型、const_cast 只动 const、reinterpret_cast 按位重解释——从"编译器帮你查"到"后果自负"严格递减，命名转换比 C 风格强转强在"意图写在脸上"**。

**四件套分工**：static_cast——数值转换（int→double）、上行转换（Derived*→Base*，编译器已知安全的方向）、显式调用单参构造；**不查运行期类型**，下行转换（Base*→Derived*）用它属于"我知道我在干什么"的裸奔。dynamic_cast——多态类型的向下/横向转换，运行期沿 RTTI 链比对实际类型，**指针失败返回 nullptr、引用失败抛 bad_cast**——安全但慢。const_cast——加/去 const 的唯一通道，典型场景"调一个没标 const 的老接口但你知道它不改"；**去掉 const 后真写只读内存照样段错误**（C 文件 3.1 讲过 const 局部在栈上能改、常量区改即崩）。reinterpret_cast——指针类型重解释、指针与整数互转，**一个字节都不动只换眼镜**；序列化、硬件寄存器访问的老搭档，安全性为零。

**C 风格强转 (T)x 为什么被禁**：它按"能试的依次试"（const_cast、static_cast、reinterpret_cast 的组合），**你不知道这次实际走的是哪条**——命名转换把"我在做什么"写进代码，review 时一眼识别危险等级。

**const/constexpr/mutable 三兄弟顺带分**：const 运行期只读（初始化可以晚到）；constexpr 编译期常量（值必须编译期可算）；mutable 专给"逻辑 const 但物理可变"的成员开口子（缓存、mutex 成员在 const 成员函数里照样能改）。

**拉开差距的深水区**：dynamic_cast 的代价——RTTI 链是类型名字符串逐级比对，深继承体系下热点路径能测出延迟；**为什么基类必须有虚函数**——RTTI 信息挂在 vtable[-1]（2.3），没虚函数的类根本没这张表；去虚拟化（devirtualization，9.2）是编译器把 dynamic_cast 的检查在编译期做掉的优化。

收尾：四件各一句话，安全性答"从查到不查递减"，C 风格答"不知道走哪条路"。

> 面试官追问点：const_cast 去掉 const 后写入会怎样？应答思路：看这块内存的真实属性——原对象本来非 const（只是经 const 引用进来），改了没事；原对象真 const 且进了常量区（全局 const、字符串字面量），写就是 UB/段错误；**const_cast 改的是"访问路径的权限"，改不了"内存本身的地契"**——这也是"const 是编译期合同不是运行期保险"的完整表达。

#### 5.2 const成员函数怎么用？顶层底层怎么区分

答：一句话定调，**const 成员函数把 this 收窄成 const T*，const 对象只能走 const 成员函数；顶层 const 锁"变量本身"、底层 const 锁"指向的东西"——一个看名字一个看目标，分清它拷贝构造的重载决议才不迷路**。

**const 成员函数**：签名末尾的 const 改的是 this 指针类型（T* 变 const T*，5.1 讲过这构成重载）——函数体里改成员直接编译错。**两条铁律**：const 对象只能调 const 成员函数（非 const 的调不了，编译期拦）；非 const 对象优先调非 const 版（两个版本并存时）——**读接口统一加 const 是设计纪律，"这个函数不改状态"是合同的一部分**。

**mutable 的配合**：const 成员函数里想改"不影响逻辑状态的物理成员"（缓存、mutex、懒计数）——mutable 成员豁免 const 检查；**mutable 的正当用途只有"逻辑 const"**，用来偷改业务字段是滥用（review 里重点盯）。

**顶层 const 与底层 const**：顶层 const——对象本身是 const（`int* const p` 锁指针不能改指）；底层 const——指向物是 const（`const int* p` 锁内容不能改）；**判定法：星星左边是底层、星星右边是顶层**（C 文件 3.1 的"左物右针"）。`const int* const p` 双锁齐全。

**为什么必须分清**：拷贝构造的参数是"底层 const"的判定题——`T(T& other)` 和 `T(const T& other)` 是两个不同的构造，string 的 c_str() 返回 const char* 传给需要 char* 的接口就卡在底层 const 上；**顶层 const 不参与模板推导**（C 文件 4.1 的对齐口诀之外，这又是一个"只影响赋值不影响类型"的限定词）。

**拉开差距的深水区**：const 成员函数里调用的函数如果没标 const，链路整个断掉——**const 正确性是传染病，一条链上谁不正确谁断**，这也是"从第一行代码就写 const"比"事后补 const"便宜十倍的原因；C++17 的 std::as_const——把左值显式转成 const 引用，防"非 const 重载做了不同的事"（as_const(s).operator[] 保证只读语义）。

收尾：成员函数答"this 被收窄加两条铁律"，mutable 答"逻辑 const 的豁免通道"，顶层底层答"星星左底右顶"。

> 面试官追问点：为什么 const 成员函数和 mutable 是天生一对？应答思路：const 的承诺是"逻辑状态不变"而不是"一个字节不动"——缓存的填充让下次查询更快、mutex 的加锁保证线程安全，都不改变"这个对象代表什么"；mutable 是标准给"物理可变、逻辑不变"开的一扇正门，**不开这扇门的代价是开发者干脆不写 const——正确的工具才配得上正确的行为**。

#### 5.3 static成员属于谁？为什么要在类外定义

答：一句话定调，**静态成员属于类不属于对象——住在全局/静态区、全类共享一份；类内只是声明，定义必须在类外（或 inline），因为编译器要保证"全程序恰好一份实体"**。

**属于谁的**：静态成员变量不占对象空间（1.10 讲过它住在全局区，同类全体共享）；静态成员函数没有 this 指针——**它访问不了非静态成员**（没有对象上下文，拿不到 this），只能碰静态成员和全局变量。这直接决定了它的用途：工厂方法（不依赖实例就能造对象）、单例的 instance()（7.5）、类级工具函数。

**为什么必须在类外定义**：类内的 `static int count;` 只是**声明**（告诉编译器有这个符号、类型是什么）；实体（分配内存）必须且只能存在一份——**类会在多少个翻译单元里被 include，就有多少份"类定义"，如果类内直接定义，多文件包含必然 multiple definition**（C 文件 6.4 的强符号撞车）。标准解法：类外一行 `int Foo::count = 0;`（一个 cpp 里定义）或 C++17 的 `inline static int count = 0;`（inline 语义容忍多份、链接器合并）。

**初始化的规则**：const 静态整型可以在类内直接初始化（`static const int N = 10;`，还是要类外定义才能取地址）；其他类型必须类外初始化；**静态成员的初始化顺序在跨翻译单元间不确定**——static initialization order fiasco（两个 cpp 里的全局对象互相依赖，谁先初始化看运气），解法是 Meyers 单例（函数内局部 static，7.5）。

**静态局部变量的线程安全**：C++11 起标准保证"局部 static 的初始化是线程安全的"（第一次调用时加一次性锁）——**这是 Meyers 单例不需要 DCL 的全部法律依据**（7.5 详谈）；老标准下它是竞态重灾区。

**拉开差距的深水区**：C++17 的 inline static 变量是"头文件库"（header-only）的基石——以前要专门开个 cpp 放定义，现在头文件一行解决；静态成员函数不能是 virtual（vptr 挂在对象上、static 没对象）——这题反过来验证了 2.3 的"vptr 属于对象"。

收尾：属于谁答"类不住对象"，类外定义答"恰好一份实体的法律保障"，this 答"没有对象上下文"。

> 面试官追问点：为什么 C++11 敢保证局部 static 初始化线程安全，而全局 static 不敢？应答思路：局部 static 的初始化时机是确定的——第一次执行到那行，编译器插一个一次性标志加锁就能守住；全局 static 的初始化发生在 main 之前，跨翻译单元的顺序标准不定义、也没法守（"另一个 cpp 里的构造函数正在跑"无从拦截）；**时机确定才锁得住，这就是 Meyers 单例把"全局"藏进"局部"的全部动机**。

#### 5.4 inline本质是什么？与ODR什么关系

答：一句话定调，**现代 C++ 里 inline 的核心语义早不是"请求内联"，而是"允许多份定义、链接器合并"的 ODR 豁免——内联是优化器的自由，ODR 豁免才是程序员写给链接器的合同**。

**语义的变迁**：远古时代 inline 是"请把这函数展开进调用点"的性能请求——今天**优化器自己决定谁内联**（哪怕你没写 inline，短的照样内联；写了 inline 的递归照样不内联）；**inline 真正的法律作用**：允许多个翻译单元里出现相同定义（头文件里定义函数，被 N 个 cpp include），链接器靠弱符号机制合并成一份（C 文件 6.4 的机制在 C++ 的专门化）。

**为什么 inline 函数必须定义在头文件**：内联发生在编译期，调用点要展开函数体就必须**看见函数体**——定义藏在 .cpp 里，别的翻译单元只有声明，想内联也没得展开（和模板必须头文件同构，4.2.5）；加上 ODR 豁免，头文件定义 + 多处 include + 链接合并，整条链才通。

**与 ODR 的关系**：ODR（单一定义规则）说"非 inline 函数全程序只能有一份定义"；inline 是这张铁律的**白名单**——"我保证每个翻译单元里的定义一字不差，请链接器任选一份"。**这个保证靠人守**：两个 cpp 里的同名 inline 函数如果长得不一样，是 UB（链接器随机挑一份，行为看运气）——这就是"inline 函数必须定义在头文件"的深层原因：单一来源，想不一致都难。

**构造析构里的隐式代码**：inline 的类外定义陷阱——空构造函数不空：成员的构造、基类构造、异常处理框架都是编译器**悄悄塞进函数体**的代码；构造函数即使写了 `{}`，里面的隐式调用链让它膨胀成"最不 inline 的函数"——**写代码时看到的代码量和编译器实际生成的代码量，在构造析构上差得最远**（9.2 的优化话题在这预热）。

**拉开差距的深水区**：inline 变量（C++17）——`inline int global_counter = 0;` 头文件里定义全局变量不炸 ODR，header-only 库的最后一块拼图（5.3 已接过头）；constexpr 函数隐含 inline、类内定义的成员函数隐含 inline——这些隐式规则决定了"为什么很多函数不用写 inline 也合法"。

收尾：本质答"ODR 豁免不是性能请求"，头文件答"编译期要看见函数体加单一来源"，隐式代码答"空构造不空"。

> 面试官追问点：既然优化器自己决定内联，inline 关键字是不是没用了？应答思路：性能语义确实退役了，但 ODR 豁免语义无可替代——头文件里的函数、模板、constexpr 都靠它活着；准确说法是"inline 从性能建议演变成了链接语义"，**看懂一个关键字的角色变迁，比背十个关键字的定义更能体现语言理解深度**。

# 6.STL与常用库

#### 6.1 STL常见容器底层怎么实现？各自怎么选型

答：一句话定调，**vector 连续数组、list 双向链表、deque 分段连续、map 红黑树、unordered_map 哈希表——选型先问"要什么复杂度"（随机访问/中间插删/查找），再问"迭代器和缓存"两个隐藏维度**。

**五件底层**：vector——连续内存，随机访问 O(1)、尾部插删均摊 O(1)、中间插删 O(n)、扩容整体搬家（6.2 主菜）；list——双向链表，任意位置插删 O(1)（**拿到迭代器的前提下**），随机访问 O(n)，缓存不友好（节点散落堆上）；deque——**分段连续**：一组固定大小的缓冲区加一张中控 map（指针数组）——头尾插删 O(1) 且支持随机访问，"两头开的 vector"；map/set——红黑树，有序、查找插入删除 O(log n)、迭代器按序遍历；unordered_map——哈希表开链法，均摊 O(1) 查找、无序、rehash 时全表搬家（6.3 主菜）。

**选型三步**：第一步问访问模式——下标随机访问选 vector/deque，纯查找选 hash（不要求序）或树（要求序）；第二步问插删位置——尾部 vector、两头 deque、中间频繁插删 list（但 list 经常输给 vector：**连续内存的缓存收益常常打败链表的理论插删优势**）；第三步问附加要求——需要有序遍历/范围查询选树系，需要稳定迭代器（插删不影响其他元素）选 list 或节点型容器。

**拉开差距的深水区**：**list 为什么经常打不过 vector**——链表每节点一次 malloc（C 文件 2.3 的分配开销）、节点地址随机（每次跳转都是缓存 miss）、指针占额外内存；遍历为主的场景 vector 快 5~10 倍——**"理论复杂度"输给"硬件友好性"是本题主菜**；priority_queue 是 vector 包 heap，queue/stack 是 deque 的适配器（容器适配器不改底层只改接口）。

收尾：五个底层各一句话，选型答"访问模式、插删位置、有序要求"三问，深水区答"缓存打败链表"。

> 面试官追问点：什么时候必须用 list 不能用 vector？应答思路：两个硬条件——插删时**其他元素的迭代器和指针必须保持有效**（vector 扩容/搬移会全部失效），或者元素大到你舍不得搬（一个元素 1KB，中间删除 vector 要搬半箱）；没有这两个约束的"中间插删"需求，**排序后批量操作的 vector 方案往往更快**——答出"我先质疑这个需求"的候选人，选型观就立住了。

#### 6.2 vector的扩容机制是什么？reserve怎么用

深度精讲见 11.4。

答：一句话定调，**扩容是"申请更大的新家、全家搬迁、旧家退租"三步，倍率 1.5 或 2 看实现；reserve 提前订房免搬迁，resize 连人都请进去——两个函数一字之差差在"要不要构造元素"**。

**扩容三步**：容量满再 push_back——①申请新内存（新容量 = 旧容量 × 增长因子，GCC 是 2 倍、MSVC 是 1.5 倍）→ ②**搬迁**：逐个元素移动（移动构造 noexcept 才走移动，4.1.2 的 move_if_noexcept）或拷贝到新家 → ③旧内存析构加释放。**均摊 O(1) 的数学**：单次搬迁 O(n)，但 n 次推送只搬 log(n) 次，总代价摊回去还是常数——倍率增长保证"搬迁次数按指数递减"。

**为什么是 1.5~2 倍**：太小（如 +1）搬迁次数线性涨，太大浪费内存（扩一次用不满）；**1.5 的彩蛋**：按 1.5 倍序列增长，旧内存块的大小之和永远小于新块——理论上旧块迟早能被后续分配复用（2 倍则永远不够），减少堆碎片（C 文件 2.3）。

**reserve 与 resize**：reserve(n)——只订房（capacity 到 n），**size 不变、不构造任何元素**，下标访问 [i] 越界是 UB（size 之外）；resize(n)——把"入住人数"调到 n，多退少补（补的走值初始化构造、退的走析构）。**口诀：capacity 是房间数、size 是入住数——reserve 改房间、resize 改入住**。工程纪律：知道量级就 reserve，扩容搬迁和反复 malloc 一起省掉。

**erase-remove 惯用法**：`v.erase(std::remove(v.begin(), v.end(), val), v.end());`——std::remove 是"把不删的往前挪、返回新逻辑尾"，**它根本没删东西**（算法层碰不到容器大小），erase 才把逻辑尾之后的真身裁掉——两步合起来才是完整的删除（6.6 详谈 remove）。

**emplace_back 与 push_back**：push_back 先构造临时对象再**移动/拷贝**进去；emplace_back 把构造参数**转发到容器内存上原地构造**（4.2.4 的变长万能引用转发是它的全部原理）——省一次移动，参数复杂的大对象收益明显；**两者对 vector<string> 这种可移动类型差距不大**，别神化。

**拉开差距的深水区**：扩容后**所有迭代器、指针、引用全部失效**（新家新地址，6.5 的主菜）；shrink_to_fit 请求归还多余容量（非强制、实现可拒绝）；swap 的容量清零技巧——`vector<int>().swap(v)` 真释放（赋空和 clear 只改 size 不退内存）。深挖见 11.4。

收尾：三步答"搬家"，倍率答"1.5 的复利彩蛋"，两个函数答"房间数对入住数"。

> 面试官追问点：push_back 强烈依赖移动构造，扩容到底拷贝还是移动谁说了算？应答思路：vector 拿 move_if_noexcept 探测——移动构造存在且标了 noexcept 才用移动，否则退回拷贝；所以**没写移动构造的类扩容走深拷贝、写了没标 noexcept 的照样走深拷贝**；一个 noexcept 关键字值十倍扩容性能，4.1.2 的账在这里结清。

#### 6.3 map与unordered_map怎么选？

答：一句话定调，**要有序（范围查询、按序遍历）选 map 的红黑树，纯查键值对选 unordered_map 的哈希表——一个 O(log n) 稳如老狗，一个均摊 O(1) 偶尔翻车，先问"要不要序"再问"能不能接受最坏情况"**。

**怎么选**：map——红黑树（自平衡二叉搜索树），增删查 O(log n)、**迭代按 key 有序**、支持 lower_bound/upper_bound 范围查询、最坏情况有保证；unordered_map——哈希表（开链法），增删查**均摊 O(1)**、无序、最坏 O(n)（全撞一条链）、rehash 时一次全表搬迁加迭代器全失效。**默认答案：不要求序就 unordered_map**，工程里九成的 map 用法其实只是字典查询。

**哈希冲突与 rehash**：负载因子（size / bucket_count）超过 1（默认）触发 rehash——桶数翻倍（实现各异）、**所有元素重新散列**到新桶；一次 rehash 是 O(n)，摊到之前的每次插入还是常数。**最坏情况的画像**：key 全部散到同一桶（哈希函数太差或被针对），链表退化成线性表——这也是哈希 flooding 攻击的原理（服务端用随机种子防）。

**自定义类型的两把钥匙**：struct 当 key 要提供**哈希仿函数**（返回 size_t）和**相等判断**——**"哈希相等"和"值相等"必须配套**：a == b 时 hash(a) 必须等于 hash(b)；漏配的典型症状是"插入成功但永远查不到"。

**几个隐藏维度**：内存——节点型容器的指针开销（红黑树每节点 3 指针，哈希表外加桶数组）；迭代器稳定性——两者插删都只影响被删元素的迭代器（**节点型容器的好处**，对照 vector 扩容全失效）；异常——哈希函数抛异常时 unordered_map 的保证弱于 map。

**拉开差距的深水区**：**float/NaN 不能当 unordered_map 的 key**——NaN != NaN，相等判断破坏，查不到自己刚插的；性能压测惯例——**先测缓存命中再谈复杂度**，百万级数据下 unordered_map 的散列跳转常常跑不赢内存紧凑的 sorted vector 加二分——**数据结构选型的最后一问永远是"测了吗"**。

收尾：选型答"先问序再问最坏"，冲突答"链表退化与 rehash 搬家"，自定义答"哈希和相等必须配套"。

> 面试官追问点：为什么 unordered_map 是"均摊 O(1)"而 map 是"稳定 O(log n)"？应答思路：前者把常数摊给了"偶发的 rehash 全表搬迁"和"冲突链长"，单次操作可能 O(n) 但长期平均回得来；后者每次都是实打实的树高比对——**"均摊"买的是平均速度、"稳定"买的是延迟上界**，对延迟敏感的交易/实时系统，这道选型题的答案会反过来。

#### 6.4 SSO短字符串优化？string_view陷阱在哪

答：一句话定调，**SSO 把短字符串直接存进 string 对象内部、免堆分配；string_view 是"只读的非拥有切片"——零拷贝的代价是你必须保证原字符串活得比它久**。

**SSO 短字符串优化**：string 对象里有一个**内嵌缓冲区**（libstdc++ 15 字节、libc++ 22 字节左右），短于阈值的字符串直接住里面——**零 malloc、零间接寻址、缓存完美**；长字符串才切到"堆指针加长度"模式。判据：sizeof(string) 固定 32 字节左右，内部靠 tag 位区分"本地还是远端"。**这是 C++ 里最著名的"对象内嵌备胎"设计**，也是"短字符串占字符串使用大头"这个经验规律换来的工程红利。

**COW（写时复制）为什么被废弃**：C++98 时代的 string 允许多个 string 共享一份缓冲、写时才复制——理论上省内存，**死于多线程**：引用计数的原子加解锁在无竞争场景也付代价（C 文件 3.3 讲过原子操作不便宜），加上"operator[] 可能触发复制"这种隐蔽的失效语义；C++11 明确禁止 COW——**"每个 string 独占内容"换来的是并发安全加可预测性**，省内存的任务交给了 string_view。

**string_view 的本质**：`(指针, 长度)` 二元组——不拥有、只读、零拷贝的切片；函数参数接收字符串的默认答案是 `std::string_view`（替代 `const string&`——**接受 string、字面量、char 数组统统免拷贝**，也不强迫调用方造临时 string）。

**生命周期陷阱**：view 只是"借光"——**原 string 析构/缩容/被 move，view 悬空**，读它就是 UB。三个经典事故：`string_view sv = fmt_and_return();`（返回内部临时 buffer 的切片，出函数即悬空）；把 view 存成成员（持有周期比源头长）；`string_view sv = std::to_string(x);`（右值 string 活不过当前行，分号即死）。**纪律：view 只做"函数参数"和"短命的局部"，不当长期持有者**。

**拉开差距的深水区**：SSO 阈值上的拷贝行为突变——跨过阈值的 string 拷贝从" memcpy 本地缓冲"跳成"堆分配"，性能曲线上有一道坎；view 的 remove_prefix/remove_suffix 是 O(1) 切片（这正是解析器/协议代码爱它的原因）；C++17 之后的演进——std::span（任意类型的非拥有视图）把 string_view 的哲学推广到全类型。

收尾：SSO 答"内嵌缓冲免堆"，COW 答"死于多线程的原子税"，view 答"借光不当业主"。

> 面试官追问点：为什么 const string& 参数没有 string_view 好？应答思路：传字面量 "abc" 时，const string& 要**构造一个临时 string**（可能堆分配）才接得住；string_view 直接把 (指针, 长度) 包起来，零分配零拷贝；反过来 view 不能接需要 null 结尾的 C API（不保证 \0 在哪）——**view 优化的是"进函数"的那一下，C API 边界上该还原 string 的还得还原**。

#### 6.5 STL迭代器什么时候失效？五种分类是什么

深度精讲见 11.9。

答：一句话定调，**失效规律一句话记牢：连续容器（vector/deque/string）动结构就全体失效，节点容器（list/map）只有被删的那个失效，unordered 系 rehash 全体失效——五种分类按"能走多远"排辈分**。

**失效三规律**：vector/string——**扩容全体失效**（搬家了，6.2），中间插删**插入/删除点之后的失效**（后面的元素往前搬）；deque——头尾插入迭代器仍有效但**中间插删全体失效**（分段结构重排）；list/map/set——**节点容器，插删只废被删的那个**（其他节点地址不动，这是链式结构的红利，6.1）；unordered_map/set——**rehash 全体失效**（重新散列），平时插删只废被删的（6.3）。

**实战纪律**：循环中删除元素——`for (it = v.begin(); it != v.end();)` 里 `it = v.erase(it)`（erase 返回下一个有效迭代器）是标准写法；vector 连续 erase 是 O(n²) 的慢速炸弹，批量删除用 erase-remove（6.2/6.6）；**修改 map 的 value 不废迭代器（key 没动），但改 key 等于变更结构，标准直接禁止**。

**五种分类**：input（单遍只读，能读一次）、output（单遍只写）、forward（多遍读写，forward_list）、bidirectional（双向，list/map/set）、random_access（随机跳，vector/deque）——**每升一级多一项能力**：从"只能往前走一步"到"能正负 n 地跳"。分类的意义：算法按最低要求写——std::sort 要求 random_access（要能跳着分区），list 因此用不了它得用成员函数；std::advance 对不同级别自动选"一步一步走"还是"一次跳到位"（tag dispatch 的经典应用，4.2.6 讲过 if constexpr 现在接管了这类分派）。

**拉开差距的深水区**：**"失效"和"UB"的关系**——失效迭代器不等于"立刻崩"，更多时候是"读到旧地址的脏数据"或"指向已析构对象"——**沉默错误比崩溃更贵**（C 文件 2.7 的哲学重演）；reverse_iterator 的 base() 场景坑——rit.base() - 1 才是它真正指向的位置；深挖见 11.9。

收尾：规律答"连续全体、节点局部、rehash 全体"，纪律答"erase 返回值接管循环"，分类答"能走多远排辈分"。

> 面试官追问点：为什么 std::sort 拒绝 list 的迭代器？应答思路：sort 的分区算法要求"O(1) 跳到区间中间"（快排的 pivot 挑选）——bidirectional 只能一步步挪，复杂度直接退化；所以 list 给了成员函数 sort（链式归并，对链表结构反而更快）；**算法对迭代器分类的要求，本质是"这个算法的复杂度承诺建立在哪种跳跃能力上"**。

#### 6.6 sort底层是什么？remove与erase怎么配

答：一句话定调，**sort 是"快排加堆排加插排"的内省排序——快排递归过深就切堆排、区间变短就切插排，三个算法各取所长；remove 只搬不删，erase 只删不搬——配起来才是完整的删除**。

**内省排序（introsort）三段论**：主体快排——平均 O(n log n)、缓存友好（连续内存跳跃少）；**递归深度超过 2·log₂n 切堆排**——堵住快排的 O(n²) 最坏情况（精心构造的"杀手序列"专打朴素快排，堆排最坏也是 O(n log n)）；**区间小于 16 左右切插排**——小区间里插排的常数小（没有递归开销、分支预测友好），收尾阶段统一扫一遍插排。**C++ 标准只承诺 O(n log n)**，内省排序是实现这道承诺的标准答案（"内省"introspective 指算法自己监控自己的健康度）。

**remove 与 erase 的配合**：std::remove **不改变容器大小**——它是纯算法（只有迭代器、碰不到容器），做的是"把不删的元素前移，返回新逻辑尾"：

```cpp
auto new_end = std::remove(v.begin(), v.end(), 42);  // 42"消失"，后半段是未指定值
v.erase(new_end, v.end());                             // 真正的物理删除
// C++20 起一行替代：std::erase(v, 42);
```

**为什么这样设计**：算法库统一操作"迭代器区间"（不依赖具体容器，泛型的代价），删除元素必然要"收缩容器"——这一步只有容器自己能做；**erase-remove 是"算法管搬、容器管删"的分工合同**；C++20 的 std::erase(v, val) 终于把这坨惯用法收编成一行。

**lower_bound/upper_bound 一句话**：两者都要求**有序区间**、二分 O(log n)——lower_bound 返回"第一个 >= value 的位置"，upper_bound 返回"第一个 > value 的位置"；equal_range 一把返回两个（构成等值区间）。**记忆法：lower 是"下界闭"、upper 是"上界开"**——[lower, upper) 恰好是所有等值元素。

**for_each 与 lambda**：for_each(v.begin(), v.end(), [](auto& x){ x *= 2; })——和范围 for 等价的算法形态；**现代选型**：简单遍历用范围 for（可读性），需要"和标准算法组合"（transform、sort 配 comparator）时才用算法加 lambda；C++20 ranges 让 `ranges::for_each(v, f)` 免写迭代器对。

**拉开差距的深水区**：**sort 不稳定**（相等元素的相对顺序可能变）——要稳定用 stable_sort（归并，需要 O(n) 辅助空间）；sort 的 comparator 必须"严格弱序"（a<b 和 b<a 不能同时真）——违者的分区逻辑可能越界，和 C 文件 5.4 的"comparator 三态"同一原理的 C++ 重演；partial_sort（只保证前 k 个有序）是"top-K 不用全排序"的省法。

收尾：sort 答"快排为体、堆排兜底、插排收尾"，remove 答"搬不删"，erase 答"删不搬"，配对答"算法与容器的分工合同"。

> 面试官追问点：为什么快排递归过深要切堆排而不是继续硬扛？应答思路：深度超过 2·log₂n 说明分区严重失衡（每次切出来的子区间一边倒）——继续递归不但栈深危险、复杂度还在滑向 O(n²)；堆排不依赖分区质量（建堆 O(n)、取最值 O(log n) 稳定），**在"分区失灵"的病态输入上它是唯一的确定性保底**——内省排序的"内省"就是监测到病态立刻换医生的自我纠错。

# 7.并发编程

#### 7.1 C++多线程工具有哪些？六种内存序是什么

答：一句话定调，**C++11 把并发写进语言——thread 管执行流、mutex 管互斥、condition_variable 管等待、atomic 管无锁快路径；六种内存序从 relaxed（只保原子）到 seq_cst（全局全序），是"性能换保证"的六档价目表**。

**四件套分工**：std::thread——线程的创建与 join/detach（7.2）；std::mutex 家族——互斥访问，配 lock_guard/unique_lock 这两个 RAII 守卫（手写锁守卫见 10.1）做到"异常也不忘解锁"；std::condition_variable——"等条件成立"的睡眠加唤醒（7.3 的主菜）；std::atomic<T>——单个变量的原子读写加 RMW（fetch_add 的 CAS 循环，对照 Java 篇的 AtomicInteger），计数器、标志位这类"单变量热点"免锁直接上。

**六种内存序一览**（7.4 详谈）：memory_order_relaxed——只保证本操作原子，不管顺序（纯计数器够用）；acquire/release 一对——建立"发布与获取"的同步关系（写 release、读 acquire，配对保证看到对方发布前的全部写入）；acq_rel——读写都有的 RMW 操作（fetch_add）两头兼顾；consume——依赖序（实践中被编译器当 acquire 处理，标准劝退）；seq_cst——默认档，全局全序，最贵也最不会错。**选型直觉：不懂就默认 seq_cst，懂了才降档**。

**与 C 文件的衔接**：pthread 的互斥锁、条件变量语义完全同构（C 文件 7.1.3），std 版只是 RAII 化的封装；C 的 volatile 不管原子性（C 文件 3.3）——C++ 的 atomic 才是正解，两份文件在这题上完成交接。

**拉开差距的深水区**：C++11 同时定义了**内存模型**（memory model）——多线程下什么写操作对什么读可见、何时可见，这是编译器和 CPU 重排的边界合同；没有语言级内存模型前，全靠 volatile 加硬件屏障的土法炼钢；**"atomic 保证单个变量原子，不保证一段逻辑原子"**——多个 atomic 的组合操作照样要锁，这是 atomic 与 mutex 的真正分界。

收尾：四件套各一句话，内存序答"性能换保证的六档"，纪律答"不懂默认 seq_cst"。

> 面试官追问点：atomic 和 mutex 都能保护共享计数器，选谁？应答思路：单变量的加减（统计计数、引用计数）用 atomic——一条 CAS 指令的事，锁要付出睡眠唤醒的系统调用代价；涉及"多个变量要保持一致"（转账的两个余额）atomic 无能为力，必须临界区；**atomic 是单变量快路径的武器，mutex 是逻辑一致性的武器**。

#### 7.2 join和detach的区别？RAII怎么封装

答：一句话定调，**join 是"等它干完再走"（父线程阻塞收尸），detach 是"从此各走各路"（线程变野进程自己活）；thread 对象析构时两者都没做过——直接 terminate，这是 C++ 里最著名的"析构即审判"**。

**两者语义**：join——调用线程阻塞到目标线程结束，回收资源拿退出状态（pthread_join 的 C++ 皮，C 文件 7.1.1）；detach——分离所有权，线程结束后系统自动回收（变成守护型野线程），**detach 后 thread 对象不再关联任何线程，joinable() 为 false**。共同纪律：**thread 析构时若仍 joinable（既没 join 也没 detach），std::terminate 直接杀进程**——没有商量，这是标准逼你表态："这条线程的结局必须由你亲口交代"。

**为什么这么凶**：join 等于"资源该谁收"、detach 等于"资源系统收"——C 时代忘了 join 出僵尸、忘了 detach 漏线程；C++ 把"忘了"的代价从"隐性问题"升级成"当场暴毙"——**把运行期的沉默错误改成启动期的巨响，是 C++ 资源管理哲学的缩影**。

**RAII 封装（thread_guard）**：

```cpp
class thread_guard {
    std::thread t;
public:
    explicit thread_guard(std::thread t_) : t(std::move(t_)) {}
    ~thread_guard() { if (t.joinable()) t.join(); }   // 异常路径也收尸
    thread_guard(const thread_guard&) = delete;        // 独占
    thread_guard& operator=(const thread_guard&) = delete;
};
```

析构里兜底 join——**函数任何出口（正常返回、异常栈回溯）都保证收尸**，这是 RAII 在线程上的应用（8.1 的思想提前落地）。

**jthread（C++20）**：析构自动 join（不用手写 guard）、内置 stop_token 协作式取消（"请求停止"而不是"强杀"）——**标准库把 thread_guard 收编成了语言级默认**。

**拉开差距的深水区**：detach 的三大暗坑——分离线程引用捕获局部变量（悬空，4.2.1 的毒牙）、main 结束时分离线程被连坐杀掉（活没干完）、分离线程用了进程级资源（退出顺序未定义）；工程纪律：**能 join 不 detach，必须 detach 的线程只能碰全局资源和自己的参数副本**。

收尾：join 答"阻塞收尸"，detach 答"所有权交系统"，terminate 答"析构逼你表态"，guard 答"析构兜底 join"。

> 面试官追问点：为什么 C++20 jthread 选择"析构自动 join"而不是"自动 detach"？应答思路：detach 是隐患放大器（生命周期没人管），join 是最安全的默认——哪怕代价是析构多等一会；**标准的设计倾向：宁可慢也要对**，和 5.3"局部 static 才敢保证线程安全"是同一条哲学——时机确定才管得住。

#### 7.3 条件变量怎么使用？为何要配unique_lock

深度精讲见 11.5。

答：一句话定调，**wait 是"解锁、睡觉、醒来重新拿锁"三合一的原子序列，unique_lock 是唯一能配合这套动作的锁（要中途解锁再锁回，lock_guard 做不到）；等待必须用谓词版 wait——虚假唤醒是真实存在的**。

**标准用法骨架**：

```cpp
std::mutex m;
std::condition_variable cv;
std::queue<int> q;

// 消费者
std::unique_lock<std::mutex> lk(m);
cv.wait(lk, [] { return !q.empty(); });   // 谓词版：等价于 while(!pred) wait(lk)
int x = q.front(); q.pop();

// 生产者
{ std::lock_guard<std::mutex> lk(m); q.push(42); }
cv.notify_one();
```

**为什么必须 unique_lock**：wait 内部要"把锁放开让生产者进去、睡醒后再把锁拿回来"——**锁要在 wait 手里反复开关**；lock_guard 只在析构时解锁一次、中途没有 unlock 接口，类型系统直接拒绝；unique_lock 还支持延迟加锁、try_lock、移动转移，是为"锁的生命周期复杂"场景生的。

**为什么 wait 要配谓词（或 while）**：虚假唤醒（spurious wakeup）——条件变量可能在没有任何 notify 的情况下醒来（实现效率的妥协，pthread 继承来的特性）；漏唤醒——notify 在 wait 之前发生就蒸发掉（时间窗，C 文件 7.1.3 的丢失唤醒）。**两道保险合一：`while (!pred) cv.wait(lk)`，谓词版 wait 就是这个循环的官方封装**。

**notify_one 与 notify_all 的选择**：单条件单一消费者——notify_one（少惊动）；多条件变量共享一把锁、或"条件的成立方式不止一种"——notify_all（防止唤醒的线程等的不是这个条件、真正的目标却没被叫醒）。

**修改共享变量为什么必须加锁**：哪怕只是一次 bool 写入——和条件判断之间存在时间窗（"检查完刚要睡、对方改完刚要 notify"正好错过），且非原子的读写本身是数据竞争 UB；**锁在这里保护的不是那一个字节，是"检查与睡眠"这段临界逻辑**。

**拉开差距的深水区**：notify 时持锁还是放锁——放锁后 notify 更快（被唤醒者不用立刻等锁），持锁内 notify 时序更简单，各有取舍；C++20 的 atomic.wait/notify——单变量的等待唤醒免掉 mutex 加 cv 的整套重量级机械；深挖见 11.5。

收尾：wait 答"三合一原子序列"，锁答"要中途开关所以 unique"，谓词答"虚假唤醒加漏唤醒双保险"。

> 面试官追问点：为什么 notify 前通常要先解锁？应答思路：被 notify 的线程醒来第一件事是抢锁——你持着锁 notify，它立刻醒来又立刻阻塞在锁上，白白多一次上下文切换；先解锁再 notify，唤醒即拿锁一步到位；**代价是解锁到 notify 之间别的线程可能插队改状态**——所以这不是性能优化铁律，是要结合谓词一起考虑的取舍。

#### 7.4 六种内存序怎么选？atomic与mutex选谁

深度精讲见 11.12。

答：一句话定调，**六档价目从 relaxed 到 seq_cst——relaxed 只保单变量、acquire/release 配对建同步、seq_cst 全局全序；选型口诀"计数用 relaxed、发布用 acq/rel、不懂默认 seq_cst"**。

**六档语义**：relaxed——本操作原子，无任何顺序约束（纯计数器：统计值加一，没人靠它的顺序读别的数据）；release（写侧）——"我之前的全部写操作，读到我这笔的人必须也能看到"（发布）；acquire（读侧）——"我读到对方的 release 写之后，对方发布前的全部内容对我可见"（获取）；acq_rel——RMW 操作（fetch_add）两头都占；consume——理论上的依赖序，实践中别用（编译器直接当 acquire 处理，标准已不推荐）；seq_cst（默认）——所有 seq_cst 操作构成**全局全序**，所有线程看到的顺序一致，最贵也最不容易错。

**什么时候必须 seq_cst**：多个原子变量的顺序依赖全局一致时——经典反例是 Dekker 互斥（两个标志位的"检查对方再设自己"），acquire/release 版在弱内存模型（ARM）上会双双进门；**"一个变量的发布同步"acq/rel 够用，"多个变量之间的顺序"常常要 seq_cst**。生产纪律：从 seq_cst 开始，profile 证明热点再降档，降档处写注释。

**atomic 与 mutex 的性能对比**：无竞争场景——atomic 的 fetch_add 是一条指令（x86 的 lock 前缀），mutex 无竞争时也就一次 CAS（futex 快路径，C 文件 10.13），差距小；**有竞争场景分岔**——atomic 自旋重试烧 CPU 但不睡眠，mutex 让出 CPU 但要付出上下文切换（微秒级）；结论：单变量热点 atomic 赢，复杂临界区 mutex 赢，"逻辑一致性"只有 mutex 能给（7.1 的分界）。

**拉开差距的深水区**：x86 是强内存模型（TSO）——seq_cst 和 acq/rel 在指令层常常没区别，**差异只在弱模型（ARM）和编译器重排上**——所以"在我机器上没复现"在这类 bug 上是废话；memory_order 是写给编译器和 CPU 的合同，违反它不是"可能乱序"是"允许乱序"（和 4.2.5 的 UB 优化同款逻辑）；深挖见 11.12。

收尾：六档各一句话，口诀答"计数、发布、默认"，分界答"单变量 atomic、逻辑一致性 mutex"。

> 面试官追问点：为什么 x86 上"感觉不到"内存序问题？应答思路：x86 的 TSO 只允许"写读重排"这一种宽松，acquire/release 语义硬件免费送；但编译器重排依然存在（store 乱序优化），ARM 上硬件乱序全开——**内存序 bug 是"平台依赖"的 bug，在 x86 测过不代表在手机上是对的**——这题考的是"你的并发正确性靠什么保证"，答案只能是内存模型而不是运气。

#### 7.5 线程安全的单例模式怎么写？为什么不用DCL

深度精讲见 11.10。

答：一句话定调，**C++11 后线程安全单例就三行——Meyers 单例（函数内局部 static）；DCL 双检锁是 C++11 之前的无奈，它的经典写法在没有内存模型保证时就是错的**。

**Meyers 单例（标准答案）**：

```cpp
class Singleton {
public:
    static Singleton& instance() {
        static Singleton inst;    // 局部 static：首次执行时初始化
        return inst;              // C++11 保证这个初始化线程安全
    }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
private:
    Singleton() = default;
};
```

法律依据就是 5.3 那条："**局部 static 的初始化，C++11 保证线程安全**"——多个线程同时首次调用 instance()，只有一个线程执行构造、其余阻塞等它完成；编译器插的一次性标志加锁替你看门。零模板、零手动同步、析构顺序还天然正确（构造的反序）。

**DCL 为什么退役**：双重检查锁——先无锁判空（快路径）、空了再加锁、再判一次（防别人抢先造好）、再构造。**C++11 之前的经典 bug**：`p = new Singleton` 是"分配、构造、赋值指针"三步，CPU 和编译器都可能重排成"先赋指针后构造"——第二个线程在第一道检查里拿到非空指针、访问的是**没构造完的对象**。当年要用 volatile 加内存屏障修，而且各平台写法不同——**没有语言级内存模型，DCL 就是平台赌博**；C++11 后用 atomic 加 acquire/release 能写对，但既然 Meyers 三行就对了，何必。

**call_once 版（备选）**：`std::once_flag` 加 `std::call_once`——适合"初始化的不是对象而是一段动作"（比如初始化某个全局库）；和 Meyers 是同一等级的保证，代码重一点但意图更显式。

**单例本身要不要用**：工程视角补一句——单例是**全局可变状态的化身**（隐式耦合、测试难并行、生命周期失控），现代设计优先依赖注入；**"怎么写对单例"是语言题，"要不要用单例"是设计题**，两题分开答显成熟。

**拉开差距的深水区**：Meyers 的析构坑——程序退出时其他线程还在用单例（static 析构顺序对静态对象有保证、对使用时序没有）；CRTP 单例基类模板 `template<class T> struct Singleton` 让业务类"继承即单例"；深挖见 11.10。

收尾：答案答"Meyers 三行"，依据答"局部 static 的 C++11 保证"，DCL 答"没有内存模型时就是错的"。

> 面试官追问点：Meyers 单例的构造和析构分别在什么时机？应答思路：构造在"第一次调用 instance()"（可能是 main 前也可能是运行中任何时候——取决于首次调用点），析构在静态对象清理阶段（atexit 注册的逆序）；**它把初始化从"程序启动"推迟到"首次使用"**，这既是懒加载的红利，也是"析构时别人还在用"风险的同源。

#### 7.6 future与async怎么用？两种启动策略是什么

答：一句话定调，**future 是"取将来结果"的凭证，promise 是"将来填结果"的承诺，async 是"把任务扔出去换凭证"的快捷方式；启动策略 async 立刻开线程、deferred 惰性求值——默认策略是坑，必须显式指定**。

**四件套关系**：std::future<T>——结果凭证（get 只能调一次，阻塞等结果；抛出的异常也经它传递）；std::promise<T>——手动版承诺（set_value 填结果、配对 future），适合"结果产生地和等待地完全解耦"的底层管线；std::packaged_task——把"可调用对象"包成任务，调用它时自动把返回值塞进 future（**函数到任务的适配器**）；std::async——快捷方式，一行把任务扔出去换 future。

**两种启动策略**：`std::launch::async`——立刻新起线程执行；`std::launch::deferred`——不执行，等 future.get() 时才在**当前线程**惰性求值（等于同步但延迟）；**默认 std::launch::async | std::launch::deferred 由实现二选一**——你不知道拿到的是并发还是惰性，这是个坑。

**async 的两大经典坑**：坑一——**future 析构会阻塞**（async 启动的任务）：拿到 future 不 get 就丢弃，析构函数等你执行完才走（准同步陷阱）；坑二——默认策略的 deferred：写 `auto f = std::async(task)` 以为并发了，实际 deferred 惰性——**直到 get 才发现全程串行**。生产纪律：永远显式写 `std::launch::async`，或干脆用线程池/task 库。

**task-based 对 thread-based 的优势**：thread 只给你"执行流"，异常和返回值都拿不回（线程函数抛异常直接 terminate）；future 把**返回值和异常打包进凭证**——跨线程的异常传递是 async 体系最大的工程红利（worker 里 throw、主线程 get 时原样抛出）。

**拉开差距的深水区**：`std::future` 的局限——一次性的（get 完就废）、不组合（没有 then 链）；C++20 协程（4.3.2）和第三方（folly::Future、continuable）都在补"组合式异步"；shared_future 支持多次 get（多个等待者共享结果）；**为什么 async 析构要等**——标准委员会在"泄漏执行 vs 静默不等"之间选了保守，这个设计争议至今。

收尾：四件套答"凭证、承诺、适配器、快捷方式"，策略答"async 开线程、deferred 惰性、默认是坑"，红利答"异常也能跨线程"。

> 面试官追问点：为什么说 std::async 的默认策略是"最危险的默认"？应答思路：它把"是否并发"这个语义级决策交给了实现——同一个程序在两个标准库下行为不同（一个真并行、一个假并发）；并发正确性靠的是"明确知道什么在并行"，**默认策略恰好剥夺了这份明确**——所以 cppreference 和Effective Modern C++ 同声劝退：写 async 就显式带 launch。

# 8.异常安全与RAII

#### 8.1 C++异常安全分几个级别？析构为何不抛异常

深度精讲见 11.15。

答：一句话定调，**异常安全三级别——基本保证（不漏不坏但不保证原值）、强保证（要么成功要么原封不动）、不抛保证；RAII 是这一切的地基，而"析构不抛"是地基里的钢筋**。

**三个级别**：基本保证——异常抛出后对象处于**合法状态**（不变式没破、资源没漏），但值可能变了；强保证——要么完整成功、要么**回滚到调用前**（对外像什么都没发生，copy-and-swap 是标准实现，8.2）；不抛保证（noexcept）——承诺绝不抛（析构、swap、移动操作应当尽力到这级）。**给接口标级别的工程意义**：调用方按级别决定要不要写回滚逻辑——合同思维，和 noexcept 标注（4.1.2）一脉相承。

**RAII 思想**：资源获取即初始化——**把资源的生命周期绑给栈对象的生命周期**，栈回溯时析构函数逐层自动执行，异常路径也能把锁、内存、fd 收干净；try/catch 是控制流，RAII 才是资源管理的正解——**手动 try/catch 配 delete 是 C++ 的原始形态，RAII 把它变成了类型系统的义务**（lock_guard、unique_ptr、thread_guard 全是这一个思想的实例）。

**析构为什么不能抛**：栈回溯时逐层调析构——**一个析构抛了，正好在异常传播的半路上，两个异常同时飞就是 terminate**（C++11 起析构默认隐式 noexcept，抛了直接死）；工程面：析构是"最后的清道夫"，它失败没有任何人能收场；所以析构里的可能失败操作要么吞掉记日志、要么设计成显式的 close() 让用户自己调。

**noexcept 的双重身份**：语义承诺——"我不抛"（违者 terminate）；优化授权——vector 扩容靠它决定走移动还是拷贝（4.1.2 的资格证）；**它把"承诺"变成了编译器可用的信息**——这是 C++ 的典型风格：文档不如合同，合同不如类型。

**拉开差距的深水区**：强保证的代价——每个"修改类"操作都要先备份或双写，热路径付不起；**分界策略**：叶子操作给强保证、聚合操作只给基本保证（异常发生时整体状态合法但内部进度可变）；把"级别"当预算花。深挖见 11.15。

收尾：三级别各一句话，RAII 答"生命周期绑定"，析构答"两个异常同时飞就死"。

> 面试官追问点：为什么 C++11 让析构默认 noexcept？应答思路：C++98 时代析构可以抛、栈回溯撞上就 terminate——但"可以抛"诱导开发者写出必死代码；C++11 干脆把默认值改成不抛（想抛要显式写 noexcept(false)，等于自己签字画押）；**把容易写错的默认行为翻转成安全默认**，和 jthread 自动 join（7.2）是同一套标准委员会哲学。

#### 8.2 copy-and-swap是什么？赋值运算符怎么写

答：一句话定调，**copy-and-swap 把 operator= 拆成"拷贝（可能失败）→ swap（绝不失败）→ 析构旧值"三段——失败只发生在拷贝阶段，此时自己一个字节没动，强异常安全白送**。

**标准写法**：

```cpp
T& T::operator=(T other) {   // 注意：值传递！拷贝在进函数前完成
    swap(*this, other);       // noexcept 交换
    return *this;
}                             // other 析构，带走旧资源
```

**三段的分工**：拷贝——参数按值传入，**新资源在"别人（参数）"手里构造**，失败了异常飞出去、*this 原封不动（8.1 强保证达成）；swap——成员级交换（move 语集的 swap 全是 noexcept），指针换主零失败可能；析构——参数离开作用域，带走**旧资源**。**自赋值自动免疫**：自己拷自己，拷贝一份再换回来，结果正确——不用写 if (this == &rhs)。

**为什么不直接写"delete 旧的、new 新的"**：`if (this != &rhs) { delete[] buf; buf = new char[...]; }` ——**delete 完成后 new 抛异常，对象处于"资源已放、新资源没到"的非法态**，基本保证都悬；copy-and-swap 的核心洞察是**"先造新的、再交旧的"**——顺序一换，失败窗口就消失了。

**代价与边界**：多一次拷贝——拷贝开销大的类，"移动赋值 + 显式分支"更快（现代做法：写 `operator=(T&&)` 单独处理右值，copy-and-swap 兜左值）；**swap 依赖成员的 swap 是否 noexcept**——哪个成员 swap 会抛，整条链的强保证就断（8.1 的"级别当预算"）。

**拉开差距的深水区**：copy-and-swap 和 1.9 的深拷贝三步（释放旧、申请新、拷贝）是同一道题的两个时代答案——前者把"释放旧"推到**最后**（借参数析构之手），后者把"释放旧"放在**最前**（失败窗口的来源）；**"资源管理的难，难在失败路径"是本题真正想考的**——一切顺利的代码谁都会写，异常安全问的全是"半路出事你在哪一步"。

收尾：三段答"拷贝可能失败、交换绝不失败、析构带走旧的"，强保证答"失败时自己一字未动"，代价答"多一次拷贝"。

> 面试官追问点：为什么 swap 一定是 noexcept？应答思路：swap 做的是成员间的指针/标量交换——纯移动字节、不分配不查找不调用可能抛的外部接口；标准给 std::swap 的契约就是"不抛"；**copy-and-swap 的整个安全大厦，恰好建立在"最便宜的操作最可靠"这条朴素的物理事实上**。

# 9.编译链接与底层性能

#### 9.1 ODR单一定义原则是什么？符号冲突怎么解决

答：一句话定调，**ODR 说"一个实体全程序只能有一份定义"，inline 是豁免白名单，weak symbol 是链接器的合并手段——符号冲突的定位三板斧是 nm、对照头文件、查链接顺序**。

**ODR（One Definition Rule）**：非 inline 函数和全局变量，全程序（跨所有翻译单元）恰好一份定义，声明可以无限多；类、inline 函数、模板允许每个翻译单元各有一份**完全相同**的定义（链接器合并，5.4 与 4.2.5 的原理）。**违反 ODR 不保证报错**——链接器随机挑一份、未定义行为悄悄发生，这是它比一般错误阴险的地方。

**符号冲突的两种典型**：multiple definition——头文件里定义了非 inline 的函数或全局变量，两个 cpp include 就撞车（修法：加 inline、改 static、拆声明进头文件定义进 cpp，C 文件 6.4 的完整版）；undefined reference——声明有了没人定义（忘写实现、lib 链接顺序错、mangle 不匹配 1.3、模板定义不在头文件 4.2.5）。

**weak symbol 的作用**：链接器允许多个弱符号共存、任选其一，**强符号优先于弱符号**——模板隐式实例化、inline 函数、__attribute__((weak)) 的默认实现（库给兜底、用户可覆盖）全靠它活；**weak 是链接世界的"接口默认实现"机制**。

**定位三板斧**：nm -u 列 undefined 符号、c++filt 反 mangle 对照两边名字是否一致；readelf/objdump 看符号的强弱属性和归属；头文件自查——"定义"和"声明"逐个过堂。

**拉开差距的深水区**：ODR 违反里最阴的"两份定义长得不一样"（inline 函数在不同 cpp 里被宏改出差异）——链接器挑一份、另一份的逻辑凭空消失，症状是"改了 A 处代码不生效"；**修链接玄学问题的经验：症状越玄学越先怀疑定义重复，而不是怀疑人生**；C++17 内联变量（5.3/5.4）给了头文件全局变量的合法出路。

收尾：ODR 答"恰好一份"，weak 答"合并与默认实现"，定位答"nm 加对照加查序"。

> 面试官追问点：为什么 ODR 违反常常不报错？应答思路：链接器的世界观里符号只有"名字"，两个同名弱符号它无法知道"语义不同"——挑一份是它的合法行为；只有强强相撞它才必须报警；**语言层面要求"定义必须逐字相同"是给人守的规矩，机器只认名字——把这条差距讲明白，就理解了为什么 ODR 违反是 UB 而不是 error**。

#### 9.2 编译器会做哪些常见优化？去虚拟化是什么意思

答：一句话定调，**常量折叠、内联、循环展开、RVO 是四大件；去虚拟化（devirtualization）是编译器"证明出这个虚调用只有一个可能目标"后把它改回静态调用——把多态的间接跳转偷渡回内联的世界**。

**四大件一句话**：常量折叠——编译期能算的全算掉（`3*4` 直接变 12，constexpr 逻辑的延伸）；内联——函数体展开进调用点，**是一切其他优化的前提**（展开后才能跨函数做常量传播和死代码消除，2.3 讲过"内联是优化的放大器"）；循环展开——一次迭代干几件事，减少循环变量维护和分支；RVO——返回值直接在调用方构造，省拷贝省移动（4.1.1）。

**去虚拟化（devirtualization）**：虚调用本来运行期才知道调谁（2.3 的三步）；**当编译器能证明"实际类型只有一种"**——`std::unique_ptr<Derived> p = make_unique<Derived>(); p->virtualMethod()`：类型系统写死是 Derived、对象没逃逸，虚调用退化为普通调用，还能继续内联；性能上等于**把多态的税退了**。

**final 的性能作用**：`class Derived final` 或 `void method() final`——告诉编译器"没有更深的派生了"：经由 Derived* 或引用的虚调用，**候选目标封闭**，去虚化绿灯放行；它同时防止同事继续派生（设计约束）和给优化器开证明（性能授权）——**final 是写给人的合同，顺手成了编译器的证据**。

**其他高频优化顺带**：死代码消除（结果没人用就删）、指令调度（重排无依赖指令填流水线）、自动向量化（SIMD，前提是别名分析过关——C 文件 3.6 restrict 在 C++ 的镜像）。

**拉开差距的深水区**：LTO（链接期优化）——跨翻译单元内联，把"头文件才能内联"的枷锁撬开一条缝（4.2.5 的缓解方案）；PGO（按 profile 优化）——按真实运行分布排分支和内联；**去虚化的边界**：类型一旦逃出编译器视野（存进容器、跨 so 边界），证明崩溃、退回虚调用——**为什么"在我机器上很快"在另一个链接单元不成立**，这题给出底层答案。

收尾：四大件各一句话，去虚化答"证明出唯一目标就退税"，final 答"给人的合同顺手成了编译器的证据"。

> 面试官追问点：怎么验证优化真的发生了？应答思路：看汇编（godbolt 上 -O2 对比，找 call 指令消失）；看优化报告（-Rpass=inline 之类的编译器开关）；benchmark 三角验证；**"我猜编译器会优化"和"我看到它优化了"之间隔着一个 -S**——把验证动作说出来，比背十条优化特性更有说服力。

#### 9.3 内存对齐alignas怎么用？伪共享怎么避免

答：一句话定调，**alignas 声明对齐要求、alignof 询问对齐值（继承 C 的对齐规则再加一层语法）；伪共享是"两个线程各写各的变量、却共享同一缓存行"——缓存一致性协议的乒乓扣罚，alignas(64) 隔开病床是标准疗法**。

**alignas/alignof 用法**：`alignas(64) char buf[4096];` 把缓冲区按 64 字节（一条缓存行）对齐——DMA、SIMD 加载、原子操作都偏爱对齐地址；`alignas(T)` 让结构体对齐到另一个类型的边界；`alignof(T)` 编译期查询对齐值（对标 C 的 _Alignof/alignof 关键字，C 文件 4.1 的两条对齐规则在 C++ 原样生效）；**alignas 只能提高不能降低**——想把对齐降到更小得用 packed 扩展（GCC 属性），代价自负（非对齐访问在 x86 是慢、在部分 ARM 是崩溃）。

**伪共享（false sharing）的机理**：缓存一致性协议（MESI）的粒度是**缓存行（64 字节）**，不是变量——两个线程分别频繁写两个**逻辑上无关**的变量，只要它们挤在同一行：线程 A 写一下，B 的缓存行副本失效、重新同步；B 写一下，A 又失效——**变量没共享，缓存行共享了**。症状极具迷惑性：代码完全无锁、无竞争，多线程跑分比单线程还慢。

**标准疗法**：把"每线程高频写"的变量隔到不同缓存行——`struct alignas(64) PaddedCounter { std::atomic<int> v; char pad[64 - sizeof(int)]; };` 或 C++17 的 `std::hardware_destructive_interference_size`（标准替你问"这机器的缓存行多大"）。**判据**：profile 里 perf c2c / cache miss 集中、去掉多线程反而变快——先怀疑伪共享。

**与 C 文件的呼应**：对齐的两条规则（偏移对齐、总大小补齐）完全同源（C 文件 4.1）；C++ 额外给了 alignas 语法和硬件干涉常量，**把"编译器扩展的暗规矩"升格成了语言标准**。

**拉开差距的深水区**：伪共享和"真共享"的区分——真共享是线程写**同一个**变量（需要锁或 atomic），伪共享是写**不同**变量但**同一行**（不需要锁、需要距离）；`[[no_unique_address]]`（1.10）省空对齐填充，alignas(64) 反着用增加填充——**空间布局是并发性能的隐形变量**；perf c2c 是定位伪共享的专用武器，能报出名字的就是加分项。

收尾：alignas 答"提高对齐给硬件铺路"，伪共享答"变量没共享行共享了"，疗法答"64 字节隔病床加 perf c2c 确诊"。

> 面试官追问点：为什么缓存行是 64 字节而不是 1 字节？应答思路：一致性协议按"行"广播失效和同步，行大→单次同步摊薄成本低、但假共享概率高；行小→同步精细但流量爆炸——64 是"空间局部性红利对假共享代价"的工程折中；**理解了这个折中，就理解了为什么伪共享是"硬件设计的副产品"而不是软件 bug**。

# 10.高频手写代码题

#### 10.1 String与智能指针怎么写？锁守卫如何实现

答：一句话定调，**手写 String 考的是"三五法则全家桶"，手写智能指针考的是"所有权语义加 RAII"，锁守卫考的是"构造拿锁、析构放锁"的极致 RAII——三道题考的全是同一件事：资源全生命周期的手工管理能力**。

**手写 String 的判分点清单**（完整骨架）：

```cpp
class String {
public:
    String(const char* s = "")                       // 构造
        : data_(new char[strlen(s) + 1]) { strcpy(data_, s); }
    ~String() { delete[] data_; }                    // 析构

    String(const String& o)                          // 拷贝构造：深拷贝（1.9）
        : data_(new char[strlen(o.data_) + 1]) { strcpy(data_, o.data_); }
    String& operator=(String o) noexcept {           // 赋值：copy-and-swap（8.2）
        swap(o); return *this;
    }
    String(String&& o) noexcept                      // 移动构造：偷指针（4.1.2）
        : data_(o.data_) { o.data_ = nullptr; }
    void swap(String& o) noexcept { std::swap(data_, o.data_); }
private:
    char* data_;
};
```

判分五件套：深拷贝、copy-and-swap 赋值（自赋值天然免疫）、**noexcept 移动**（vector 扩容的资格证）、swap 成员（给 copy-and-swap 当地基）、析构释放。**面试官看的就是"你能不能把散落各章的知识拼成一个能跑的类"**。

**手写 unique_ptr 要点**：T* ptr_ 成员；**delete 拷贝构造和拷贝赋值**（独占语义写进类型系统，3.3）；移动构造偷指针置空源；析构 delete——**五个函数里"删掉两个"就是 unique_ptr 的灵魂**；能再写 operator*/operator->、get()、release()（交出所有权）、reset()（换新并释放旧）就是满分版。

**锁守卫（lock_guard 简版）**：

```cpp
template<class M>
class lock_guard {
    M& m;
public:
    explicit lock_guard(M& m_) : m(m_) { m.lock(); }   // 构造拿锁
    ~lock_guard() { m.unlock(); }                       // 析构放锁：异常路径也解锁
    lock_guard(const lock_guard&) = delete;             // 守卫不可拷贝
    lock_guard& operator=(const lock_guard&) = delete;
};
```

**"构造拿锁、析构放锁"八个字就是 RAII 的全部**——异常抛出时栈回溯照样走到析构、锁必然释放（8.1 的地基）；不可拷贝防止"守卫被复制成两个、双重解锁"。

**拉开差距的深水区**：String 的进一步追问必然是"和 std::string 差在哪"（SSO 6.4、COW 历史）或"移动赋值怎么写"（noexcept 版 operator=(String&&)）；unique_ptr 追加"为什么删除器是空类型参数"（EBO 零开销，1.10/3.3）——**手写题的终点永远是"你知不知道标准库为什么长这样"**。

收尾：String 答"五件套拼装"，unique_ptr 答"删掉拷贝就是灵魂"，锁守卫答"八字 RAII"。

> 面试官追问点：手写 String 为什么必须先写析构函数？应答思路：析构是"这个类到底管不管资源"的宣言——析构里有 delete[]，后续每个函数（拷贝、赋值、移动）都围绕"这份资源怎么交接"展开；**先定析构就是先定所有权**——三五法则（1.8）的创作顺序从来不是"从上往下写"，是"从资源往两边推"；答出这个顺序感，手写题就从"默写"升级成了"设计"。

#### 10.2 单例模式怎么手写？线程安全的队列怎么实现

答：一句话定调，**单例考"局部 static 加删拷贝"三行功夫，线程安全队列考"锁加条件变量加两件事"——手写队列的判分点全在边界：谓词等待、通知时机、超时返回**。

**单例的两种标准写法**（7.5 的手写版）：

```cpp
// Meyers 单例：局部 static，C++11 保证初始化线程安全
class Singleton {
public:
    static Singleton& instance() { static Singleton i; return i; }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
private:
    Singleton() = default; ~Singleton() = default;
};

// call_once 版：初始化"一段动作"时用
static std::once_flag flag;
static void init_once() { std::call_once(flag, [] { /* 全局初始化 */ }); }
```

**手写线程安全队列的完整骨架**（判分点标注在注释）：

```cpp
template<class T>
class BlockingQueue {
    std::mutex m_;
    std::condition_variable cv_;
    std::queue<T> q_;
public:
    void push(T v) {
        { std::lock_guard<std::mutex> lk(m_); q_.push(std::move(v)); }
        cv_.notify_one();                            // 解锁后通知（7.3 的取舍）
    }
    T pop() {
        std::unique_lock<std::mutex> lk(m_);         // 必须 unique_lock（wait 要中途解锁）
        cv_.wait(lk, [&] { return !q_.empty(); });   // 谓词版：防虚假唤醒（7.3）
        T v = std::move(q_.front()); q_.pop();
        return v;
    }
    template<class Rep, class Period>
    bool pop_for(T& out, std::chrono::duration<Rep, Period> ttl) {
        std::unique_lock<std::mutex> lk(m_);
        if (!cv_.wait_for(lk, ttl, [&] { return !q_.empty(); }))
            return false;                            // 超时路径显式返回
        out = std::move(q_.front()); q_.pop();
        return true;
    }
};
```

**判分五点**：unique_lock（wait 中途解锁的刚需）；谓词版 wait（虚假唤醒双保险）；notify 的时机意识（锁内简单、锁外快）；**wait_for 超时版**（带 deadline 的 pop，7.6 的 future 之外的另一种超时武器）；**move 语义贯穿**（push/pop 全程 std::move，4.1 的知识落在容器操作上）；再提"关闭队列"（析构前唤醒全部消费者退出：加 closed 标志加 notify_all）就是工程满分版。

**拉开差距的深水区**：有界队列需要第二把条件变量——not_empty 加 not_full（满了 push 也得等）；**无锁队列（SPSC ring buffer）的存在**——单生产者单消费者场景用 atomic 索引就能免锁（7.1/7.4 的实战出口），多生产者多消费者才老实上锁；面试官问"你这个队列能改成无锁吗"，标准答案是"先问清几生产几消费，再谈方案"。

收尾：单例答"Meyers 三行加删拷贝"，队列答"锁加条件变量加谓词加超时"，深水区答"按生产者消费者数量选并发方案"。

> 面试官追问点：为什么 pop_for 用 wait_for 的谓词重载而不是先 wait_for 再手写 if？应答思路：`wait_for(lk, ttl, pred)` 在超时时段内**反复检查谓词**（虚假唤醒醒来还会再判），超时才返回 false；手写版"等一下再看一眼"只判一次——虚假唤醒白白吃掉剩余的超时预算；**谓词重载把"循环"藏进了标准库，让调用方少写一个容易错的循环**——这题和 7.3 是同一知识点在"写库"视角下的复考。

# 11.深度精讲（对象模型与底层机制口述版）

> 说明：本章是核心题的口述版深度精讲，讲到对象内存模型、库实现与编译器行为层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

### 11.1 虚函数表如何生成与存放？多态调用怎么完成

答：一句话定调，**vtable 在编译期生成、放在只读数据段、同类的所有对象共享一份，虚调用的代价是「两级解引用加一次间接跳转」**。

**对象侧**：含虚函数的类，对象头部多一个 vptr（8 字节），这就是「空类 1 字节、带虚函数变 8 字节」的来源。**vptr 由构造函数设置**：基类构造先把 vptr 指向基类的 vtable，派生类构造再改写成自己的。这直接解释了两个经典问题：**基类构造函数里调用虚函数没有多态**（此刻 vptr 还指着基类表，派生类部分尚未出生）；以及**为什么构造函数不能是虚的**（虚调用依赖 vptr，而 vptr 要靠构造函数来初始化，鸡生蛋问题）。

**调用侧**，`p->f()` 编译成三步：取 vptr、按固定偏移找到表项、间接 call。**偏移在编译期已知**，所以虚调用的成本是两次内存加载（vptr 和表项，通常都在缓存里）加一次间接跳转，比普通函数多几纳秒，但**阻止了内联**，这才是热路径上虚函数的真实代价。

**多重继承的布局是深水区**：`class C : public A, public B`，C 的对象里有两个 vptr（A 子对象一个、B 子对象一个）。**把 C* 转成 B* 时指针要加上 A 子对象的偏移量做 this 调整**；B 的虚表里那些 C 覆写过的函数，表项不是简单函数地址而是 **thunk**：一小段先「把 this 减去偏移修正回 C 对象头」再跳到真实函数的胶水代码。能讲出 thunk，这题就从八股变成了理解。

**再深一层**：vtable 的下标 0 之前还挂着两个槽，**vtable[-1] 是 typeinfo（typeid 和 dynamic_cast 的数据源），vtable[-2] 是 offset-to-top（用于 dynamic_cast 的跨类型指针修正）**。dynamic_cast 做向下转型的原理就是运行时沿 RTTI 链表比对，失败返回 nullptr（引用则抛 bad_cast）。

收尾：虚函数表机制的分工很清晰，编译器生成表和调用点、构造函数安装 vptr、链接器把表放进 .rodata、CPU 付出间接跳转的代价，四者合谋实现了「零成本抽象」里「成本不为零但很接近零」的那部分。

> 面试官追问点：虚函数能内联吗？应答思路：通过对象直接调用（非指针/引用）且编译器能看到类型时，静态绑定后可以内联；通过指针调用是运行期决议，内联基本无望，这也是性能敏感代码用 CRTP（奇异递归模板）替代虚函数的动机。

### 11.2 三种智能指针的区别？控制块与引用计数原理

答：一句话定调，**unique_ptr 是零开销的独占所有权（就是那个裸指针的 RAII 壳），shared_ptr 的全部复杂度都在「控制块」这一个结构里**。

**先讲 unique_ptr 为什么零开销**：它只是把裸指针包进对象，析构时 delete，**没有引用计数、大小就是裸指针**（无删除器版本）。默认删除器是空类，靠 EBO（空基类优化）不占空间；`unique_ptr<T[]>` 的偏特化还自动把 delete 换成 delete[]。它不可拷贝只能移动，所有权语义在类型系统里就写死了。

**shared_ptr 的控制块**（真正的考点）：引用计数不是存在对象里，而是独立的堆上结构，**两个原子变量：use_count（强引用）和 weak_count（弱引用，实现上通常「实际值-1」作为标记）**。三个关键行为：

1. **原子操作保证计数的线程安全**：多线程同时拷贝/析构同一个 shared_ptr 的不同副本，计数正确；但**线程安全仅止于计数，指向的对象本身和同一个 shared_ptr 实例的并发读写都不安全**，这句话能说准确就赢了一半；
2. **use_count 归零只析构对象**，还要等 weak_count 也归零才释放控制块本身；
3. **循环引用的解法**就是 weak_ptr 只增加 weak_count，对象生命周期看 use_count，weak_ptr 访问前必须 lock() 升级成 shared_ptr（原子检查 use_count 是否为 0）。

**拉开差距的深水区**：make_shared 的利弊。`make_shared<T>()` 把**对象和控制块一次性分配在同一块内存**（省一次分配、缓存局部性好、异常安全）；代价是**有 weak_ptr 存活时，整个内存块（包括对象遗体）都无法释放**，对象早该析构了但内存要陪葬到 weak_count 归零。大对象加长寿命 weak_ptr 的组合，反而应该用 `shared_ptr(new T)` 分离分配。

**再深一层**：控制块只在「第一次从裸指针构造 shared_ptr」时创建，**同一个裸指针构造两次会产生两个控制块、双重析构直接崩溃**；类内部拿自身裸指针的正确姿势是继承 `enable_shared_from_this`（内部藏一个 weak_ptr，shared_from_this 时升级）。

收尾：智能指针的选型口诀，**默认 unique_ptr，需要共享才 shared_ptr，需要观察不拥有用 weak_ptr，裸指针只做「借用」不做「拥有」**。

> 面试官追问点：shared_ptr 的原子计数为什么不用锁？应答思路：计数增减是单变量 CAS/fetch_add，原子指令足够；用 mutex 反而引入挂起开销，得不偿失。追问延伸：计数是原子的，但「检查+动作」（如 if(use_count==1) 就改）不是原子的，这类逻辑仍需外层锁。

### 11.3 左值右值怎么划分？std::move与完美转发原理

答：一句话定调，**std::move 一个字节代码都不生成，它只是 static_cast 到右值引用的「重贴标签」，真正搬东西的是移动构造函数**。

**先分清值类别**：表达式分左值（有名字可取址）和右值（纯右值 prvalue 与将亡值 xvalue）。**左值引用绑左值，右值引用 `T&&` 绑右值**，但两者绑定后本身都是左值（有名字），这就是「右值引用变量要再次移动必须再 std::move」的原因，也是最容易挂的坑。

**std::move 的真身**：`static_cast<T&&>(x)`，**编译后是零指令**。它的作用是骗过重载决议，让 `vector(const T&)`（拷贝）和 `vector(T&&)`（移动）这对重载选中后者。移动构造做的事：**把源对象的资源指针偷过来（浅拷贝指针），再把源指针置空**，源对象留在「有效但未指定」状态（能析构、能重新赋值，但别假设内容）。

**完美转发的本质是引用折叠**：模板参数 `T&&` 是「万能引用」（推导语境才成立），传左值时 T 推成 `T&`，`T& &&` 折叠成 `T&`；传右值 T 推成 `T`，保持 `T&&`。**std::forward<T> 的实现就是条件转换：是左值就转回左值引用，是右值就转回右值引用**，从而把参数的值类别原样穿透到下一层。而 `std::forward` 与 `std::move` 的区别只在于「是否保留左值性」。

**RVO 讲到位要分标准**：C++17 之前返回纯右值是「允许优化」（编译器在调用方栈上直接构造，跳过拷贝/移动，**即使拷贝构造函数有副作用也允许跳过**）；**C++17 起对纯右值是强制省略**（同一性质表达式的临时量物化被延迟，`return T{}` 连移动构造都不再需要）；**NRVO（具名返回值优化）到今天仍是可选的**，所以「返回局部变量」依赖的是编译器好心。这也是为什么「return std::move(local)」是反模式：**它把可 RVO 的纯右值场景强行变成 xvalue，反而禁用了优化**。

**拉开差距的深水区**：vector 扩容时如何对待元素的移动，用的是 `move_if_noexcept`：**移动构造标了 noexcept 才用移动，否则退回拷贝**。因为扩容到一半抛异常，移动了一半的旧数据无法恢复（源已被掏空），拷贝则旧数组完好无损。所以「给移动构造标 noexcept」不只是风格问题，**它直接决定 vector 扩容快十倍还是慢十倍**。

收尾：移动语义的完整链路是「值类别提供语法区分 → 右值引用提供绑定目标 → move/forward 提供类型转换 → 移动构造提供资源转移」，四环缺一不可。

> 面试官追问点：为什么成员函数限定符要区分 && 版本？应答思路：`void f() &&` 让「右值才能调用的接口」成为可能（如 std::optional::value 的移动语义），资源窃取类操作在左值上调用是逻辑错误，类型系统直接拦下。

### 11.4 vector的核心细节？扩容机制与惯用法详解

答：一句话定调，**vector 是「三个指针管理一段动态内存」（begin/end/capacity_end），所有行为都能从这三个指针推出来**。

**扩容的三步原子操作**：push_back 发现 size==cap，分配 2 倍（GCC）或 1.5 倍（MSVC）的新内存，把旧元素搬过去（可移动则移动、不可移动或抛异常风险则拷贝），析构旧元素并释放旧内存。**均摊 O(1) 的数学**：n 次 push_back 总搬运次数是 1+2+4+...+n < 2n，摊到每次是常数。

**增长因子的取舍是深水区**：为什么不选 2 而选 1.5？一个流传的说法是**斐波那契式增长（1.5 的多次累加大约能拼回旧内存块）**，增长因子为 2 时申请的新块永远大于之前所有释放块之和，旧内存永远无法复用；1.5 时几代之后的空闲块有机会合并承接新请求。**2 的好处是容量始终是 2 的幂、移位算地址快**，GCC 选空间激进、MSVC 选复用友好，这是工程取舍不是对错题。

**reserve 与 resize 的分界**：reserve 只动 capacity 指针、**不构造任何对象**（内存是裸的）；resize 会构造/析构元素使 size 到位。推论：reserve 之后用下标访问仍是 UB（size 没变），**这是 reserve 惯用法最常见的翻车点**。

**emplace_back 与 push_back 的区别讲到构造层面**：push_back 接受一个已构造的对象（临时对象要经过一次移动或拷贝进容器）；emplace_back 用 `::new (p) T(args...)` **在容器内存上直接原地构造**，省掉临时对象的构造和移动。对 `vector<pair<int,big>>` 这种，emplace_back(1, x) 比 push_back({1,x}) 少一次 big 的移动构造；但**对 int、指针这类平凡类型两者生成的代码一样**，「emplace 永远更快」是过度简化。

**拉开差距的深水区**：

1. **迭代器失效的精确规则**：扩容后所有迭代器失效（内存都换址了）；**push_back 不扩容时，end 失效但已有元素的迭代器仍有效**（C++ 标准的明确保证）；insert 在中间会让插入点之后的迭代器失效。erase-remove 惯用法 `v.erase(remove_if(...), v.end())` 的原理就是 remove 把要留的元素前移、返回逻辑新尾，erase 一次截断；
2. **shrink_to_fit 为什么只是「请求」**：它内部就是 swap 技巧 `vector<T>(v).swap(v)` 的封装，**重新分配一份紧凑内存再交换**，原内存归还分配器，不做原址收缩（做不到，realloc 语义对非平凡类型不安全）。

收尾：vector 的强大不在「动态数组」，而在它把「扩容时机、异常安全、迭代器失效」这些坑都按标准写死了，三个指针加一份保证，就是它取代手写动态数组的全部理由。

> 面试官追问点：vector<bool> 为什么是坑？应答思路：标准把它特化成位压缩代理（operator[] 返回代理对象不是 bool&），导致取地址失败、和 auto 配合出诡异类型，需要 bool 语义应该用 vector<char> 或 deque<bool>。

### 11.5 条件变量的使用原理？wait机制与虚假唤醒

答：一句话定调，**条件变量必须配谓词使用，因为「虚假唤醒」和「丢失唤醒」两个失败模式都只有谓词能救**。

**先讲 wait 的原子性（这是 unique_lock 的原因）**：`cv.wait(lock, pred)` 等价于 `while(!pred()) cv.wait(lock)`，而裸的 wait 内部做两件事：**原子地「释放锁 + 挂起」**，被唤醒后再「重新加锁」。之所以要原子，是为了堵住「检查条件之后、挂起之前」的窗口：不原子的版本里，另一线程恰好在这个窗口改条件并 notify，信号蒸发，本线程睡死。**「释放+挂起」的原子性由内核保证（Linux 的 futex 就是为这个设计的），而 lock_guard 不支持中途解锁，所以 wait 只能用 unique_lock**。

**虚假唤醒的根源讲到 OS 层**：条件变量的唤醒在 Linux 上靠 futex 系统调用，而 futex 的语义是「许可」而不是「通知」：**wait 被唤醒的瞬间许可就被消费了，即使这次唤醒源于一个和你无关的信号或 spurious 的系统行为**。POSIX 明确允许 pthread_cond_wait 在没有任何 notify 的情况下返回。所以醒来之后**必须重新检查条件**（while 循环），因为「被唤醒」不携带「条件成立」的保证，它只代表「值得再看一眼」。

**丢失唤醒的完整链路**：notify 时没有任何线程在等，这个通知不会保存、不会重放（条件变量无状态）。如果共享条件不在锁内修改，就可能「消费者刚检查完条件为假、还没来得及 wait，生产者改条件并 notify、然后消费者才睡下」，**睡在了通知之后**。锁内修改条件让「检查」和「挂起」与「修改」和「通知」互斥，消除这个竞态。

**拉开差距的深水区，notify 在锁内还是锁外**：锁外 notify 的理由是**避免「惊群后立刻撞锁」**：被唤醒的线程要重新拿锁，notify 持锁的话唤醒了也拿不到锁、白白上下文切换一次。锁内 notify 的理由是**某些平台（尤其 glibc 的 pthread 实现）在锁外 notify 存在唤醒丢失的边界情形**（写顺序的重排在弱内存模型上的问题）。实践结论：**不确定就先 unlock 再 notify（性能敏感），或者 notify 在锁内但唤醒逻辑必须有谓词兜底（正确性优先）**，能把这个 trade-off 讲成选择题，就是深水区水平。

**notify_one 与 notify_all 的选择**：单条件单消费者用 notify_one；**多条件变量共享一把锁、或「条件」是多种资源的广播**，必须 notify_all，否则唤醒的可能不是等这个条件的那类线程。

收尾：条件变量的正确姿势一以贯之，**条件在锁内改、wait 带谓词、醒来第一件事是重新检查**，这三条守住的不是语法，是「检查与等待的原子性」和「唤醒与条件的因果性」。

> 面试官追问点：能不能用「轮询+sleep」替代条件变量？应答思路：能但错，轮询的延迟和 CPU 消耗不可兼得（间隔短烧 CPU、间隔长响应慢），条件变量是「事件驱动的挂起与唤醒」，等待成本为零，这正是同步原语存在的意义。

### 11.6 菱形继承的问题在哪？虚继承的内存布局详解

答：一句话定调，**菱形继承的病是「两份基类子对象」，虚继承的药是「共享一份 + 通过偏移量表间接访问」，代价是访问虚基类的成员多一次内存间接**。

**先看病理**：`B、C 都继承 A，D 继承 B、C`，普通继承下 **D 里有两份 A 子对象**（B 带一份、C 带一份）。`d.aMember` 二义性编译报错，被迫写 `d.B::aMember` 才能消歧；更隐蔽的是**数据冗余**：逻辑上唯一的 a 成员存了两份，改 B 路的那份 C 路看不见。

**虚继承的解法**：B、C 虚继承 A 后，**A 子对象在 D 的布局里只保留一份，放在对象末尾**，B、C 子对象里不再直接包含 A，而是各带一个 vbptr（虚基类指针），指向**虚基类表（vbtable）**，表里存着「本子对象到共享 A 的偏移量」。访问 `d.aMember` 时：**取 vbptr → 查表拿偏移 → this 加偏移 → 访问成员**，一次间接寻址。

**为什么偏移要放表里而不是直接放指针**（深水区一）：**同一个 B 子对象在不同最终类型里的偏移不同**——B 单独实例化时没有虚基类布局、B 作为 D 的一部分时偏移是 X、B 作为另一个菱形 E 的一部分时偏移是 Y。**vbtable 是「每个最派生类型一份」的静态数据**，代码不写死偏移，运行期按表查，才能一套代码适配所有布局。

**this 调整的连锁反应**（深水区二）：把 `D*` 转 `B*` 时指针要偏移到 B 子对象处（编译期常量偏移），**但从 B* 再 static_cast 回 D* 就不可能了**——B 子对象不知道自己在哪个最终类型里，此时走 dynamic_cast，它**沿 RTTI 链（vtable[-1] 的 typeinfo）比对并在 vtable[-2] 的 offset-to-top 辅助下完成跨子对象修正**。菱形继承把「指针运算」彻底逼成了「运行期查表」。

**实践立场**：虚继承是「语言提供的解药，但毒性不小」——布局复杂、初始化顺序特殊（**虚基类由最派生类直接初始化，中间层 B、C 的构造函数对 A 的初始化被忽略**）、性能多一次间接。现代 C++ 的主流答案是**用组合代替多继承、用接口（纯虚类）代替数据继承**，虚继承主要出现在 IO 流库这种历史设计中。

收尾：菱形继承考的不是语法，是「对象模型如何用指针和表模拟动态的相对位置」，能把 vbtable 讲成「每种最终类型一份的偏移账本」，这题就答透了。

> 面试官追问点：为什么虚基类由最派生类初始化？应答思路：A 只有一份，如果 B 和 C 的构造函数都初始化它就会执行两次；规则改成「最派生类负责、中间层初始化列表对 A 的调用被跳过」，保证唯一性。

### 11.7 Lambda的底层实现？捕获方式与悬空引用陷阱

答：一句话定调，**每个 lambda 表达式都是编译器生成的一个匿名类，捕获的变量是它的成员变量，operator() 默认是 const 的**。

**闭包类型的展开**：`[x](int y){ return x+y; }` 大致等价于：

```cpp
struct __lambda {
    int x;                        // 捕获的变量成为成员
    int operator()(int y) const { return x + y; }  // 默认 const
};
```

**mutable 的真实含义**：operator() 默认 const，**按值捕获的 x 在函数体内是 const 的，改它编译报错**；mutable 就是去掉这个 const，允许修改「闭包自己那份拷贝」（不影响外部原变量）。按引用捕获不受影响（const 引用也能改指物）。

**无捕获 lambda 转函数指针**（深水区一）：没有捕获的闭包没有状态，编译器额外生成一个**静态函数**，转换运算符 `operator FunctionPtr()` 返回它的地址——**这是 lambda 能喂给 C API 回调（如 qsort、pthread_create）的机制根源**。带捕获的 lambda 有状态、塞不进一个函数指针，只能用 std::function（类型擦除）或传 context 参数。

**捕获 this 的悬空陷阱**：`[this]` 和 `[*this]`（C++17）有本质区别——**[this] 捕获的是 this 指针的值（八字节），对象析构后 lambda 里的 this 悬空**，异步回调场景是重灾区；`[*this]` 才是把整个对象拷一份进闭包。C++20 的 dclstyle 是 `[=]` 显式弃用警告，就是为了把这个坑从默认行为里挖出来。

**std::function 的代价 vs 模板参数**（深水区二）：function 用**类型擦除 + 堆上的调用包装**统一了「任何签名兼容的可调用体」，代价是**间接调用阻断内联 + 捕获大时堆分配**；而 **lambda 直接作为模板参数（auto&& f）传递，编译器看到具体闭包类型，operator() 直接内联**。STL 算法的 comparator 设计成模板参数而非 function，就是让 lambda 白嫖内联。

收尾：lambda 的本质是「编译器替你写了仿函数类」，理解了「捕获即成员」，const、mutable、悬空、性能四个问题全部自洽。

> 面试官追问点：两个内容一样的 lambda 相等吗？应答思路：不相等，闭包类型是编译器生成的独立类型，连 == 都没定义；无捕获闭包才可以转函数指针后比较地址（同一转换目标地址相同是标准保证的）。

### 11.8 四种cast的底层实现？各自的安全边界在哪

答：一句话定调，**四种 cast 的分野是「静态检查的强弱」，dynamic_cast 是唯一做运行期检查的，它依赖 RTTI，而 RTTI 挂在 vtable 上**。

**四种的定位**：

1. **static_cast**：编译期类型检查，做「有明确定义的转换」（数值类型互转、上行派生类指针转基类、void* 还原）。**下行转换（基类转派生）它能编译通过但不检查**——转错了是 UB，它只保证「类型之间有转换路径」，不保证「这个对象真的是那个类型」；
2. **dynamic_cast**：**运行期沿 RTTI 链验证**，失败返回 nullptr（指针）或抛 bad_cast（引用）。深水区一：**它要求多态类型（至少一个虚函数）**，因为 RTTI 的入口是 vtable[-1] 的 typeinfo 指针，**没有 vtable 的类型连「身份证」都没处挂**。下行转换的实际过程：取目标类型的 typeinfo，**沿源对象的类继承图做上溯匹配**，找到还要经 vtable[-2] 的 offset-to-top 修正 this（多重继承的兄弟子对象间切换）；
3. **const_cast**：只改常量性/易变性。**合法用途是「穿过const API 拿回可变视图」（如老 C 库参数不科学）； UB 红线是「改本身定义为 const 的对象」**——底层 const 对象可能真在 rodata，改是段错误或逻辑炸弹；
4. **reinterpret_cast**：位模式重解释，**唯一「合法且可移植」的用途是指针与整数互转（回转后比较）**；指针类型间互转后**解引用是 UB**（除按 unsigned char 查看表示），函数指针互转调用也是 UB——它只保证「转回来还是原来的值」。

**拉开差距的深水区二：C 风格 cast 的危险**——`(T*)expr` 的语义是「**依次尝试 const_cast、static_cast、static_cast+const、reinterpret_cast 的组合**，取第一个能编译的」。**它能无声地做出 reinterpret 级别的危险转换**（比如把 const char* 经由 int* 中转改掉），四个具名 cast 的存在就是把「我当时知道我在干什么」写进代码；**在泛型代码里 C 风格 cast 还会偷偷做「T 到 U 的隐式用户转换」**，行为随模板参数漂移，是模板代码的隐雷。

收尾：选型口诀——数值转换用 static，多态下行用 dynamic，穿 const 用 const，位重解释用 reinterpret；**C 风格 cast 的每一处使用都等价于四个具名 cast 的某一个，写代码时应翻译成具名的，翻译不出来的就是危险的**。

> 面试官追问点：dynamic_cast 为什么慢？应答思路：运行期做继承图遍历（最坏 O(深度×宽度)）加指针修正，且挡内联；高频路径的替代是「自己存类型标签的 switch」或在设计上用 visitor 消灭下行转换。

### 11.9 STL迭代器何时失效？各容器失效规则详解

答：一句话定调，**失效规则由「容器的内存策略」决定：连续内存的容器一动全抖，节点容器只死自己，而 unordered 容器有个「迭代器失效但指针不失效」的特殊条款**。

**逐容器的精确规则**：

1. **vector**：**扩容（size 超过 capacity）→ 全部迭代器失效**（整块内存搬家）；**不扩容的 push_back → 只有 end() 失效**，已有元素的迭代器仍有效（标准明确保证，很多书上写「全失效」是错的）；**中间 insert/erase → 插入/删除点之后的失效**（元素搬移）；
2. **deque**：**两端插入 → 迭代器全失效但引用不失效**（中心 map 扩了但节点没搬）；中间插入 → 全失效；
3. **list**：**插入不失效任何迭代器，删除只失效被删的那个**。erase 的正确姿势是 `it = lst.erase(it)`（**返回下一个有效位置**），因为 erase 后 it 已死，++it 是 UB；
4. **map/set（红黑树）**：同 list，**插入零失效、删除只失效被删节点**。这个性质支撑了「遍历中删除」的经典写法：`for(auto it = m.begin(); it != m.end();) { if(cond) it = m.erase(it); else ++it; }`；
5. **unordered_map**（深水区）：**rehash 时全部迭代器失效，但指向元素的指针和引用不失效**——因为节点本身没搬（桶数组换了、节点重挂），标准把这条写成了明确保证。**insert 只在触发 rehash 时才失效迭代器，erase 只失效被删者**。

**erase-remove 惯用法的机制**（拉开差距的点）：`v.erase(remove_if(v.begin(), v.end(), pred), v.end())` 里，**remove 系列只搬不移除**——把不删的元素前移覆盖要删的，返回「逻辑新尾部」，**容器 size 不变、尾部留着待覆盖的垃圾**；erase 真正砍掉尾巴。两步走的原因：remove 是纯算法没有容器权限，**「搬移」能做「释放」不能做**，这是 STL「算法与容器分离」设计的直接后果。

**失效的本质再深一层**：vector 失效因为「地址换了」（内存连续必须整体搬），节点容器不失效因为「节点地址是身份」（指针即节点），**unordered 的「迭代器死、指针活」是因为迭代器封装了「桶位置」而指针只关心「节点位置」**——失效规则不是背的，是对象模型的推论。

收尾：答题时给三档结论——连续容器「一动查全表」、节点容器「只死被删者」、哈希容器「rehash 全死但指针活」，加一句 erase 返回下一个有效迭代器，就是满分结构。

> 面试官追问点：遍历 vector 时 push_back 会怎样？应答思路：可能触发扩容（全失效），即使不扩容 end() 也失效——**缓存 end() 迭代器是经典错误**（`for(auto it=v.begin(); it!=v.end(); ++it)` 每次重取 end 是正确姿势的深层原因）。

### 11.10 Meyers单例为什么线程安全？静态初始化的保证

答：一句话定调，**C++11 起「局部 static 的初始化」被标准保证线程安全（magic statics），实现是编译器埋的 guard variable，所以 DCL 从此退位成历史文物**。

**Meyers 单例**：

```cpp
static Singleton& instance() {
    static Singleton inst;   // C++11：并发调用也只初始化一次
    return inst;
}
```

**guard variable 的机制**（深水区一）：编译器把这段代码改写成「**先原子检查 guard 标志 → 未初始化则 __cxa_guard_acquire 拿锁（拿不到的线程挂起或自旋）→ 执行构造 → __cxa_guard_release 置标志唤醒等待者**」。guard 是每个静态局部变量一个的字节级标志，**首次通过的线程执行构造，其他线程等到完成**——所以线程安全不是免费的，是「一次隐藏的锁」，高并发首次访问有竞争成本（之后是纯原子读）。

**为什么 DCL 不再需要**：DCL 的全部复杂度（volatile/atomic 内存序）都是在手搓「惰性初始化的线程安全」，**guard variable 已经把这事儿标准化了**。C++11 之前的标准没这个保证（某些编译器有扩展），所以老代码里的 DCL 不是错，是历史。

**两个对比项**：

1. **call_once/once_flag**：语义上和 magic statics 等价（pthread_once 的 C++ 化），**优势是「初始化内容」可以是任意代码块而非单个对象**（比如初始化一组全局资源），劣势是多一层显式结构；
2. **静态成员初始化顺序问题**（深水区二）：跨编译单元的全局对象**初始化顺序标准未定义**（static initialization order fiasco），A.cpp 的全局对象构造时调用 B.cpp 的全局对象可能还没构造。**Meyers 单例「首次使用时才构造」的特性顺带治好了这个病**——这是它比「类外定义静态成员」更好的第二个理由，比线程安全更隐蔽也更实用。

**单例的其他姿势按槽点排**：饿汉式（启动即构造，浪费且可能 fiasco）；返回指针版（调用方可能 delete，危险）；C++17 的 inline static 成员（解决顺序问题但仍是饿汉）。

收尾：现代 C++ 单例的答案收敛为一句话——**局部 static 加引用返回**，线程安全交给标准（6.7 节）、初始化顺序交给惰性、删除交给不可 delete（私有析构或 =delete）。

> 面试官追问点：单例的析构顺序怎么保证？应答思路：静态对象的析构按构造的逆序、进程退出时统一执行；如果单例依赖另一个静态对象，析构时对方可能已死（static destruction order fiasco），解法是 leaky singleton（故意不析构，atexit 都不管）或用函数内 static 的 nanny 对象控制顺序。

### 11.11 虚析构函数为什么必须？析构降级与泄漏场景

答：一句话定调，**基类析构非虚时 delete 基类指针只执行基类析构（派生类成员泄漏加未定义行为），而析构期间虚函数会「降级」为静态绑定——析构是从派生到基类的逐层「拆除脚手架」**。

**泄漏的机理还原**：`Base* p = new Derived(); delete p;`——**Base 的析构非虚，delete 的调用点直接绑定 `Base::~Base()`**（静态绑定，不看实际类型），Derived 的析构体根本不执行——**Derived 里 new 出来的成员没人释放**；更糟的是标准规定这是 UB（内存布局可能不匹配）。**加 virtual 后**：delete 走 vtable 找到的是 **「派生类析构函数的 deleting destructor」**，先 ~Derived 再 ~Base（**析构链自动级联**）——「**基类析构要不要 virtual」的判据是「这个类会不会被基类指针 delete**」。

**析构期间的虚函数降级**（深水区一）：**~Derived 执行时，vptr 已经被改成指向 Derived 的 vtable（再往上走 ~Base 时又改成 Base 的）**——**此时在 ~Derived 里调用虚函数 foo()，实际执行的是 Derived::foo() 而不是更下层的 override**——因为「更下层的部分已经拆了」，**让虚调用打到已析构的部分是灾难**，语言规则主动降级保护。**这和「构造函数里调虚函数只有当前层的版本」是对称的：构造自底向上装、析构自顶向下拆，两头的中间态里虚表都只反映「已存在的层」**。

**深水区二：析构函数的三件套**——编译器为带虚析构的类生成**两个入口**：**complete destructor（D1）**：析构整个对象（成员加基类）；**deleting destructor（D2）**：调 D1 再 operator delete 释放内存——**vtable 里存的是 D2**（delete p 时走虚表拿 D2，析构加释放一体完成）；**基类析构（D0 基类版）**在多重继承下还有 thunk 调整。**「一个析构函数在对象文件里有两三个化身」**是「我看过汇编」级别的细节。

**protected 非虚析构的设计智慧**：把基类析构设 protected——**外部无法通过基类指针 delete（编译期拦截），派生类内部析构可以调**——「**想禁止多态删除又不想付虚表的代价**」的标准答案（std::function 等标准库组件用的这个手法）。

收尾：虚析构题的心法，「**泄漏机理（静态绑定绕过派生析构）、降级对称性（构造析构两头虚表都是半成品）、D1/D2 双入口、protected 的零开销替代**」。

> 面试官追问点：构造函数为什么不能是虚的？应答思路：虚调用依赖对象里的 vptr，而 vptr 是构造函数安装的——鸡生蛋死锁；且构造时「完整类型未知」，虚构造在语义上就是矛盾（你要构造的正是那个「最派生」的东西）——**克隆函数 clone() 是「虚构造」语义的标准替代**。

### 11.12 atomic的六种内存序？各自语义与使用场景

答：一句话定调，**六种序是「限制重排和保证可见性的强度分级」：relaxed 只保证原子性、acquire-release 建立同步配对、seq_cst 是默认的全局总序，x86 的强内存模型让大部分序免费**。

**六种的语义速记**：

1. **relaxed**：**只原子不同步**——计数器自增够了，但「写完另一个线程立刻看见」不保证；
2. **consume**：**事实上被废弃**——数据依赖的传播理论上比 acquire 弱（更快），但编译器太难实现，标准「建议按 acquire 对待」；
3. **acquire**（读）/ **release**（写）：**配对建立 happens-before**——release 写之前的所有写，对 acquire 读之后的代码可见（**一写一读构成同步边**）；
4. **acq_rel**：读改写操作（fetch_add）同时具备两侧语义；
5. **seq_cst**：**除了 acquire-release 的效果，还保证「所有 seq_cst 操作存在全局单一的总顺序」**——多线程看一组 seq_cst 操作的顺序一致（默认值，最强也最贵）。

**为什么需要它（经典反例）**：四个变量两个线程——r1/r2 都读到对方后写的旧值（store-store 重排的体现）——**两个线程各自的「写 x 再读 y」顺序在对方看来可能颠倒**；acquire/release 修不了这个（它是成对同步不是全局序），**只有 seq_cst 保证 r1=r2=0 不可能同时发生**——「 Dekker 互斥的 flag 交换」这类算法必须 seq_cst。

**深水区一：x86 的 TSO 天生强**——**x86 只允许 StoreLoad 重排**（LoadLoad/LoadStore/StoreStore 都不发生），所以 acquire/release 在 x86 上**编译成普通 mov（零成本）**，**只有 seq_cst 的写需要 mfence 挡 StoreLoad**——「**C++ 的内存序是给弱内存模型（ARM）设计的抽象，x86 是它的贵族特权版**」；ARM 上 acquire/release 要 dmb 屏障，**跨平台代码的内存序正确性要在 ARM 上验证**。

**深水区二：DCL 为什么 seq_cst 而不用 acq_rel**——`instance = new Singleton()` 的关键是「初始化写到发布写的顺序」——release 写（instance 赋值）之前的构造不能重排到之后，**单看这一对用 release 就够**；但**判断端的读和写端组成的「双重检查」在弱内存模型下的完整证明依赖更细的条件**——**写 seq_cst 是成本最低的正确性保障**（x86 上就一条 mfence），除非 profile 证明这行是瓶颈才降级——「**默认最强、证明后再放松」的工程纪律**。

收尾：内存序题的心法，「**relaxed 计数、acq-rel 配对同步、seq_cst 全局总序、x86 免费序、默认最强再放松**」。

> 面试官追问点：memory_order_consume 为什么弃用？应答思路：它想利用「数据依赖天然有序」（读了指针再用它指向的数据，硬件天然保证顺序）省掉屏障，但**编译器会做依赖破坏的优化（寄存器传播、重算替换）**，语义几乎无法保证——GCC 曾经实现又放弃，标准标记「不鼓励使用」；C++20 给了它的替代方案（[[carries_dependency]]），实践上还是 acquire 一把梭。

### 11.13 模板特化与偏特化怎么写？SFINAE的原理

答：一句话定调，**特化是「给特定类型开小灶」（全特化换实现、偏特化换维度），SFINAE 是「让不匹配的候选静默退出重载决议」，两者都是编译期的类型分派机制**。

**全特化与偏特化的语法边界**（高频坑）：**函数模板只能全特化，不能偏特化**（标准禁止——和重载决议的交互太复杂，用重载代替）；**类模板两者都行**：

```cpp
template<typename T> struct Vector { /* 通用 */ };
template<> struct Vector<bool> { /* 全特化：位压缩版 */ };
template<typename T> struct Vector<T*> { /* 偏特化：指针版 */ };
template<typename K, typename V> struct Map { };
template<typename V> struct Map<int, V> { /* 偏特化第一个参数 */ };
```

**匹配规则**：**全特化 > 偏特化 > 主模板**（最特化的赢）；函数模板的「偏特化需求」用**重载**满足（`template<typename T> void f(T)` 加 `void f(int*)` 的重载决议天然选更特化的）。

**SFINAE 的机制还原**（深水区一）：**Substitution Failure Is Not An Error**——**模板实参替换进签名时如果产生非法类型/表达式，这个候选被静默移除，不报编译错**（只有全部候选都失败才报）。经典武器：

```cpp
// enable_if：条件不满足时 type 不存在 → 候选消失
template<typename T,
         typename std::enable_if<std::is_integral<T>::value, int>::type = 0>
void f(T);   // 只接受整数
```

**void_t 检测惯用法**（更优雅）：**利用「无表达式的非法替换」探测类型特性**——`template<typename T, typename = void> struct has_reserve : false_type {};` 加 `template<typename T> struct has_reserve<T, void_t<decltype(declval<T>().reserve(0))>> : true_type {};`——**有 reserve 成员的 T 的特化匹配成功（void_t 那个更特化），没有的落回 false 版**——**「用特化匹配的成功与否当类型判断的返回值」**。

**深水区二：C++20 concepts 如何取代这一切**——`template<typename T> requires Reserveable<T> void f(T)`——**约束从「让候选静默消失」变成「显式声明的契约」**：错误信息从几百行的替换失败堆栈变成「constraint not satisfied: Reserveable<T>」；**重载决议的语义更清晰（constraints 的包含关系决定优先级）**——**SFINAE 是「利用错误恢复机制的元编程」，concepts 是「正大光明的语言特性」**——能讲出这个演进的动机就是深水区。

收尾：模板分派题的心法，「**类模板可偏特化、函数模板用重载、SFINAE 是静默退出、void_t 是探测惯用法、concepts 是正规军**」。

> 面试官追问点：为什么函数模板禁止偏特化？应答思路：函数有重载决议这个「天然的优选机制」，偏特化和重载的优先级交织会产生不可解的歧义（标准委员会权衡后的决定）；类没有重载、必须靠特化分派——**「类走特化、函数走重载」是语言设计的一致性**。

### 11.14 new与malloc的六个差异？两步构造与配对规则

答：一句话定调，**new 是「operator new 分配内存 + 构造函数执行 + 类型安全 + 失败抛异常」，malloc 只是「给你一块字节」，六个维度逐层展开**。

**六个差异逐条**（每条一句话加一个细节）：

1. **类型**：malloc 返回 `void*` 要强转，new 返回具体类型指针——编译器检查；
2. **构造**：**new 先 operator new 拿内存、再placement-new 调构造**（`new(p) T(args)` 的裸形态）；delete 先调析构再 operator delete——**对象生命周期完整，malloc 只有字节**；
3. **失败行为**：**malloc 失败返回 NULL**；**new 失败默认抛 bad_alloc**（不返回检查 NULL 是不够的）——`new(std::nothrow)` 才是返回 null 的旧行为；
4. **大小**：malloc 要手算 `sizeof(T) * n`，new 表达式自己算——**数组 new 还要额外存「元素个数」的头**（delete[] 靠它逐个析构，**这就是 new[]/delete[] 必须配对、new/delete 混用会崩的原因**）；
5. **可重载**：**operator new 可以按类重载**（自定义分配策略：内存池、日志）——类级优先于全局级；malloc 只能链接期替换；
6. **对齐**：**C++17 起 aligned new 支持 over-aligned 类型**（alignas(64) 的对象 malloc 可能不保证对齐，operator new 按对齐值分配）。

**深水区一：operator new 的两段协议**——`Foo* p = new Foo` 的完整展开：`operator new(sizeof(Foo))` 拿裸内存 → `static_cast<Foo*>(p)->Foo::Foo()` 构造——**placement new 是这个协议的「裸用」**（内存谁给谁管：容器和内存池的标准姿势：`allocator::allocate` 加 `allocator::construct`）；**new_handler 链**：内存不足时 operator new 先调 `set_new_handler` 注册的回调（给你机会释放缓存或 abort），回调返回后再试——**「失败前的最后商量」机制**。

**深水区二：混用的灾难清单**——**new 分配 + free 释放**：**非平凡析构对象跳过析构 + 内存块头格式不兼容（operator new 的块头 vs malloc 的 chunk 头）→ 堆损坏**；**malloc 分配 + delete**：delete 试图调析构和按 operator delete 的头解析——同样崩；**唯一安全的组合是同族配对**——**「allocator 谁分配谁释放」是跨库边界的铁律**（dll 的 malloc 和 exe 的 free 在不同 CRT 上也是这个坑）。

收尾：new/malloc 题的心法，「**内存 + 构造是本质差异、六维度是展开框架、placement new 是裸协议、混用必崩在同族头格式**」。

> 面试官追问点：delete this 合法吗？应答思路：语法合法（成员函数里 this 是指针），但要满足三个条件：对象是 new 出来的（非数组非栈）、**调完 delete this 后这个对象不能再碰任何成员**（including this 指针本身）、**引用计数场景的最后一步**（最后一个 release 的引用调 delete this 是这个用法的主要正当场景）——「自杀式释放」的纪律问题。

### 11.15 RAII的核心思想？异常安全三级别怎么分

答：一句话定调，**RAII 是「资源生命周期绑定栈对象」，异常安全的三个级别回答「异常抛出后对象处于什么状态」：基本保证（合法但未定）、强保证（要么成功要么回滚）、不抛保证（析构和 swap）**。

**三个级别的精确定义**：

1. **基本保证**：异常后**对象仍然处于合法状态（不变量没破）但值不确定**——没有泄漏、没有崩溃，但「原来是什么」丢了；**最低底线，所有代码必须达到**；
2. **强保证**：异常后**对象回到操作前的状态（像什么都没发生）**——「事务语义」；
3. **noexcept（不抛）**：**承诺绝不抛**——**析构函数隐式要求不抛**（栈展开途中再抛 = terminate 直接死）、swap 是移动语义体系的地基。

**copy-and-swap：强保证的标准实现**（深水区一）：

```cpp
Widget& operator=(const Widget& rhs) {
    Widget tmp(rhs);      // 可能抛（拷贝）——抛了 *this 未动
    swap(*this, tmp);     // noexcept——交换指针
    return *this;         // tmp 析构旧数据
}
```

**「所有可能失败的工作（拷贝）先在临时对象上做完，成功后只做不可能失败的交换」**——异常发生在任何一步，原对象都完好；**代价是多一次拷贝**（移动语义时代：`Widget tmp(std::move(rhs))` 或按值传参让编译器优化）——**强保证的账单是性能，业务关键路径才值得付**。

**深水区二：为什么析构不能抛**——异常触发**栈展开（stack unwinding）**：逐层调局部对象析构；**如果某层析构又抛出新异常，此刻有两个异常同时活跃——C++ 没有双异常模型，直接 terminate**——所以析构里的异常必须 catch 吞掉（或转发给回调记录）；**C++11 的 noexcept 声明是显式契约**：违反直接 terminate（比未声明时代「未定义行为」更可诊断）；**析构默认隐式 noexcept(true)**——你写 `~Foo() { mayThrow(); }` 编译器自动包 catch。

**noexcept 的性能红利**（连接 11.3）：**vector 扩容用 move_if_noexcept**——**移动构造标了 noexcept 才敢用移动**（移动抛了旧数据已掏空无法回滚，强保证破灭）；没标的退回拷贝（旧数据完好）——**「一个 noexcept 标注决定扩容快十倍还是慢十倍」**，这是 noexcept 从「文档」变「性能开关」的机制。

收尾：异常安全题的心法，「**三级别按「异常后对象什么状态」定义、copy-and-swap 是强保证模板、析构不抛是铁律、noexcept 是移动时代的性能开关**」。

> 面试官追问点：异常安全的代价什么时候不值得付？应答思路：强保证的 copy-and-swap 多一次拷贝，热点路径可能不可接受；实践中「关键操作强保证、内部步骤基本保证加日志」的分层很常见——**安全级别和性能一样是设计决策不是信仰**，能说出「这里我故意只要基本保证因为……」才是真的懂。
