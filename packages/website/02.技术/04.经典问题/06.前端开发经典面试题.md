# 1.HTML与CSS经典问题

### 1.1 布局与定位

#### 1.1.1 盒模型分哪两种？box-sizing的作用是什么

答：一句话定调，**两种盒模型的差异只有一条：width 这把尺子量到哪——标准盒模型量到内容区，IE（怪异）盒模型一杆子量到 border 内沿，box-sizing 就是切换这把尺子的开关**。

**两套规则**：标准盒模型（box-sizing: content-box，默认）：实际占宽 = width + padding + border + margin——写 width: 100px 再加 padding，元素就被撑大；IE 盒模型（box-sizing: border-box）：width 包含内容区 + padding + border，padding 增大时内容区自动缩小，总尺寸恒定。

**工程默认**：`* { box-sizing: border-box }` 几乎是所有 reset 的标配，理由是**流式布局的心智负担**：百分比宽度（width: 100%）加 padding 会溢出父容器，border-box 下总宽永远等于声明的 width，12 列 + gutter 的栅格不用 calc 就能算清。

**深水区**：border-box 管不到 margin——`width: 100%` 的元素再加大 margin 一样溢出；`height: 100%` 的坑是「参照父级显式 height，父级没写就退化成 auto」。另外 border-box 下「内容区被 padding 挤没」是合法状态（width 小于 padding + border 时内容区为 0，元素不塌陷）。

收尾：这题的加分点是能报出「box-sizing 只影响 width/height 的计算口径，不影响 margin」，以及 border-box 成为业界默认的动机是布局算术的可预测性。

> 面试官追问点：既然工程上都用 border-box，为什么规范还保留 content-box 作默认？应答思路：默认值要向后兼容，且「width 即内容宽度」对替换型元素（img/canvas 的绘制区域）语义更自然——图片的 content 尺寸就是资源尺寸；reset 成 border-box 是团队约定，不是语言默认。

#### 1.1.2 BFC的原理是什么？触发条件和应用有哪些

答：必问题。一句话定调，**BFC 是页面上的「独立排版沙箱」：内部元素的布局变化不外溢，外部也不影响它——三大经典问题（margin 塌陷、浮动溢出、环绕文字）的解法全都是「把相关元素包进 BFC」**。

**两个核心行为**：一，BFC 内部的垂直 margin 只在内部折叠、不与外部折叠——**给兄弟盒子的父级建立 BFC，margin 塌陷消失**；二，BFC 不与浮动元素重叠且包含内部浮动——**父级 overflow: hidden 清浮动、侧栏浮动 + 主栏 BFC 实现两栏自适应**，都是这条的推论。

**触发条件**：overflow 非 visible、float 非 none、position: absolute/fixed、display: flow-root（现代专用、零副作用）、flex/inline-block/table-cell。

**深水区**：margin 折叠的完整规则（正正取大、正负相加、负负取绝对值大；父子穿透是最反直觉的场景）；display: flow-root 是规范专门为「只要 BFC 不要副作用」发明的值——能报出它就证明知识在更新。

收尾：实战三招（清浮动/防塌陷/自适应布局）+ flow-root 收尾，完整版口述见 8.7 深度精讲。

> 面试官追问点：为什么 overflow: hidden 能清浮动但不被推荐？应答思路：清浮动的原理是触发 BFC 后「高度计算包含浮动子元素」；副作用是溢出内容被裁剪，现代首选 display: flow-root——零副作用触发。

#### 1.1.3 flex与grid布局怎么选？核心属性有哪些

答：一句话定调，**flex 是一维的「空间分配器」，grid 是二维的「网格划分器」——单方向排布选 flex，行列结构同时确定选 grid；两栏/三栏布局按 flex/grid/float+BFC/absolute/表格五套对照答**。

**flex 的骨架**：容器属性管全局（flex-direction 定主轴、justify-content 主轴分布、align-items 交叉轴对齐、flex-wrap 换行）；项目属性管个体——flex 是 grow（分剩余空间）、shrink（缩超占空间）、basis（基准尺寸）的缩写，**flex: 1 = 1 1 0%**（基准为 0 均分，与 flex: auto = 1 1 auto 的差异在内容尺寸是否参与分配）。

**grid 的骨架**：grid-template-columns/rows 定义轨道（`repeat(12, 1fr)`、minmax、auto-fill + minmax 做响应式卡片），grid-template-areas 用命名区域把布局「画」出来；gap 统一控制间距。

**两栏/三栏五套实现对照**：flex（中间列放最前 DOM 优先 + flex-grow）、grid（template-areas 一行画完，fr 单位唯一不用算的「中间自适应两侧固定」）、float + BFC（考古）、absolute（固定侧栏）、table（等高需求的活化石）。

**深水区**：flex 子项的 min-width: auto 陷阱（内容过长不收缩，要 min-width: 0 才能触发 shrink）；grid 自动放置的顺序算法；flex 换行后最后一行的对齐残留问题。

收尾：选型一句话——**不确定用 flex（组件内布局），结构确定用 grid（页面级布局）**；圣杯双飞翼这类历史题先答古法再补 grid 现代版，层次立刻拉开。

> 面试官追问点：flex: 1 的三个分量分别是什么？应答思路：grow=1（等分剩余空间）、shrink=1（允许压缩）、basis=0%（忽略内容基准）——三个分量讲全，再指出 flex: 1 与 flex: auto 在「内容宽度悬殊」时的分配差异，就是加分项。

#### 1.1.4 定位有哪几种？层叠上下文与z-index怎么用

答：一句话定调，**五种定位的本质是「参照物 + 是否脱流」两张表：static 不定位、relative 原位偏移、absolute 相对最近定位祖先、fixed 相对视口、sticky 滚动阈值内 fixed；而 z-index 只在「同一个层叠上下文内」才可比**。

**五种取值**：relative——不脱流、原占位保留、常作 absolute 的定位锚；absolute——脱流、相对最近非 static 祖先（找不到就是初始包含块，**不是 body**）；fixed——相对视口，**祖先带 transform/filter 时退化成相对该祖先**（最常见的坑）；sticky——relative 与 fixed 的混合体，父容器滚出视口时失效。

**z-index 生效条件**：position 非 static（或 flex/grid 子项）才有 z-index 语义；**比较只发生在同一层叠上下文内**——根元素、position + z-index、transform、opacity < 1、flex 子项等都会创建上下文。

**深水区**：「z-index: 9999 不生效」的排查路径：先看祖先有没有创建层叠上下文把自己困住（transform 祖先把 fixed 变 absolute 的连锁坑）、再看是否与目标不在同一上下文、最后确认在比的是谁的 z-index——**层叠上下文是隔离舱，舱内数字再大也压不过舱外**。

收尾：层叠顺序七层图（背景→负 z-index→块级→浮动→行内→z-index: 0→正 z-index）能徒手画出来就是深水区选手；FLIP 动画（First-Last-Invert-Play，用 transform 做列表位移动画）正是「层叠上下文 + 合成层」两个知识点的综合应用。

> 面试官追问点：为什么 fixed 元素在带 transform 的父级里表现异常？应答思路：规范规定 transform 非 none 的元素成为 fixed 的包含块（本意是给 transform 局部坐标系），视口定位失效、改锚到祖先——「为一个特性顺带改了另一个特性」的经典规范案例。

#### 1.1.5 元素的水平垂直居中怎么实现？各方案怎么选

答：一句话定调，**居中方案先过两问：行内还是块级？尺寸已知还是未知？——flex 一套通吃，absolute 三件套是深水区**。

**水平居中**：行内用 text-align: center；定宽块级用 margin: auto；不定宽块级用 flex 或包一层 inline-block。

**垂直居中**：单行文本 line-height = height；已知高度的 absolute + 负 margin；**未知高度的 absolute + transform: translate(-50%, -50%)**（transform 的百分比参照自身尺寸，所以不用知道高度）；flex 的 justify-content + align-items。

**深水区三件套**：一，absolute + margin: auto + inset: 0 四面拉伸（不写宽高占满父级，写了就居中——**溢出时贴边不丢内容**，比 transform 版更能处理「子比父大」的场景）；二，行内元素的幽灵空白节点（图片底部几像素空隙来自基线下延，vertical-align: middle / display: block / font-size: 0 三种解法）；三，display: grid + place-items: center（现代最短写法）。

收尾：答题按「flex → absolute + translate → margin: auto + inset」递进，最后补一句每种方案对「子元素尺寸未知」和「超出父级」的兼容差异——说明是按场景选，不是背菜单。

> 面试官追问点：img 底部为什么有几像素空隙？应答思路：img 是行内替换元素，默认基线对齐，行盒基线下方的空间就是那几像素——答出「行盒的基线机制」即到位，三种解法对应三个层面。

#### 1.1.6 圣杯和双飞翼布局怎么实现？瀑布流如何做

答：一句话定调，**圣杯与双飞翼解决同一道题——「中间主体优先渲染、两侧宽度固定」，差异只在中间列怎么腾位置：圣杯用父级 padding + relative 负偏移，双飞翼用中间列再包一层**。

**圣杯三步**：三列全浮动且中间列 DOM 放最前；父容器 padding-left/right 给两侧腾固定宽度；两侧列 margin-left 负值拉到两侧 + relative 微调。**临界坑**：中间列宽度小于两侧之和时布局错乱，需要 min-width 兜底。

**双飞翼**：中间列外面再包一层容器，内容直接自适应，侧栏负 margin 拉上来——**用一层额外 div 换掉了 relative 偏移的心智负担和 min-width 临界问题**，结构解耦更稳定。

**瀑布流三套实现**：CSS 多列（columns）——实现最快但**填充按列不按行**、顺序竖着走，只适合无序流；absolute + JS 计算每张卡片落到最矮列——可控但自管重排；虚拟化方案——大数据量时定高分栏 + 窗口裁剪。**选型按「是否在意顺序」**：在意顺序用绝对定位，不在意用多列。

**深水区**：弹窗的**滚动穿透**——body overflow: hidden 锁滚动（要补偿滚动条宽度防抖动，或 position: fixed + top: -scrollY 记忆位置），移动端还有 touchmove preventDefault + passive 陷阱；吸顶是 sticky 的主场。

收尾：圣杯双飞翼是 float 时代的考古题，价值是秀对盒模型和负 margin 的理解；现代同需求用 grid template-areas 一行解决——先古法后现代。

> 面试官追问点：双飞翼比圣杯多一层 div，值得吗？应答思路：圣杯的 relative 偏移依赖父级 padding 精确匹配、有 min-width 临界问题；双飞翼把「腾位置」从父级 padding 改成中间列内层，多一层换稳定性——工程上永远划算。

### 1.2 移动端与响应式

#### 1.2.1 移动端适配方案怎么选？1px边框问题怎么解决

答：必问题。一句话定调，**适配的本质是「同一份 CSS 在不同宽度设备上等比缩放」——rem 是「根字号做换算基准」的动态方案，vw 是把基准交给浏览器原生的单位；1px 问题是 DPR 缩放的副作用**。

**单位三兄弟**：em 相对父级 font-size（层层嵌套会读错基准）、rem 相对根字号（基准唯一）、vw/vh 视口百分比（1vw = 视口宽 1%，**原生免 JS**）。flexible 方案：JS 动态设根字号 + data-dpr 缩放；现代方案直接 PostCSS px-to-viewport 转 vw，零运行时成本。根字号常设 37.5 是「设计稿 750 / 10」的整除约定。

**1px 边框问题**：DPR=2/3 的设备上 1 物理像素 = 0.5/0.33 CSS 像素，写 1px 实际渲染 2-3 物理像素显得粗——**解法三代**：viewport 整体缩放（initial-scale = 1/dpr，副作用是第三方库坐标问题）、**伪元素 + transform: scaleY(0.5)（最主流）**、border-image/svg（样式可换）。

**深水区**：安全区域 env(safe-area-inset-*) 配 viewport-fit=cover 处理刘海与底部横条；**vh 的移动端坑**——地址栏伸缩导致 100vh 不稳定，现代解法 dvh。

收尾：现代版主推 vw + PostCSS 自动换算，rem 是 flexible 时代的遗产方案，1px 问题答 scaleY 伪元素版即收。

> 面试官追问点：vw 方案什么场景会翻车？应答思路：超大屏（iPad 横屏）把元素等比放大到失真——解法是 clamp 上下限（`font-size: clamp(12px, 2vw, 16px)`）；答出「无约束的等比缩放不总是体验最优」就是分层思维。

#### 1.2.2 响应式设计的断点怎么定？响应式图片怎么用

答：一句话定调，**断点该按「内容在哪开始难看」定，而不是抄设备清单——移动优先用 min-width 向上增强，图片响应式是 DPR × 视口双维度的 srcset 问题**。

**断点方法论**：先做窄屏版本，拉伸窗口观察哪里布局崩（导航挤爆、卡片过宽），崩的那个宽度就是断点——**断点是内容的函数，不是设备的函数**。移动优先基础样式写窄屏、增强向上叠加，好处是 CSS 与体验的增量方向一致。

**响应式图片双维度**：srcset + x 处理 DPR（1x/2x/3x 拿不同分辨率资源）；srcset + sizes 处理视口宽度——sizes 告诉浏览器「这张图最终显示多宽」("100vw"、"(max-width: 600px) 50vw")；picture + source 处理格式降级（avif → webp → jpg）。**核心是「让浏览器自己选」**——它知道自己的 DPR、视口、网络状况，比 JS 判断准。

**深水区**：容器查询（@container）把响应式从视口解耦到父容器——组件在侧栏和主区各自适配，这是组件化时代断点的归宿，选答加分；loading="lazy" 原生懒加载与 data-src 手动方案的取舍。

收尾：一句话收束——**断点服从内容、图片交给浏览器、优先级 mobile-first**。

> 面试官追问点：srcset 和 sizes 缺一个会怎样？应答思路：只有 srcset + x 时，「小视口 + 高 DPR」会拿过大的图（375px 宽 + 3x 屏选了 1200w 浪费流量）；sizes 补上「最终渲染宽度」，浏览器按「显示宽度 × DPR」选最优——两属性合起来才是完整决策链。

### 1.3 渲染与动画

#### 1.3.1 两种CSS动画怎么选？transform为何更快

答：一句话定调，**transition 是「属性变化时的补间」——两态、被动、需要触发；animation 是「独立的时间线」——多帧、可循环、可自动播放；性能军规是只动 transform 和 opacity，因为它们走合成器，完全绕开布局和绘制**。

**两者的选择**：hover 展开、状态切换用 transition（声明式：什么属性、多久、什么缓动）；循环、多阶段、需要播放控制（暂停/反向/重播）用 animation（keyframes 定义任意中间帧）。**事件差异**：transition 实战以 transitionend 为主（新规范补了 run/start/cancel 但使用率低）；animation 有 animationstart/iteration/end 三个事件，可用 animation-play-state 暂停。

**transform 为什么快**：CSS 属性动画的代价分层——几何属性（width/top）触发回流重绘、颜色类触发重绘、**transform/opacity 只触发合成层的 GPU 纹理变换**（矩阵运算在 GPU 做，不动布局树和绘制指令）——把动画从 left 换成 translateX，就是从 CPU 布局换成 GPU 合成。

**will-change 与滥用**：它是「提前建层」的预告提示，写在动画前、动画后要移除——**无节制 will-change 造成层爆炸**（每层独立栅格化 + 内存），DevTools 的 Layers 面板专查这个。贝塞尔曲线（cubic-bezier）控制时间→进度的映射，弹性动画的本质是缓动函数。

收尾：选型一句话「交互反馈 transition、叙事循环 animation」，性能一句话「**合成三件套：transform、opacity、will-change 伺候好**」。

> 面试官追问点：为什么主线程被 JS 卡死时 transform 动画依然丝滑？应答思路：transform/opacity 的插值由合成器在合成线程完成，不依赖主线程——layout/paint 动画主线程一卡就掉帧，合成动画只是页面其他部分冻结、动画本身照跑。

#### 1.3.2 重绘和回流怎么触发？如何规避与利用合成层

答：一句话定调，**回流必然重绘、重绘不一定回流——回流算几何、重绘制像素、合成交纹理，三者代价递减；优化的本质是让变化尽量落在流水线最下游**。

**回流的触发清单**：几何属性变化（width/height/position/font-size）、DOM 结构变化（增删节点）、**读取布局信息的 API**（offsetTop/getBoundingClientRect/scrollTop——强制同步布局）、窗口 resize。

**读写交错是性能杀手**：浏览器用脏标记把回流延迟到帧末批量执行，但读布局 API 要「此刻的精确值」，被迫立刻回流——循环里「改一次读一次」就是 N 次回流；**防御三招：批量读、缓存读、统一写**（改样式前先把要读的值存变量），或用 rAF 把写操作挪到帧边界。

**合成层的利用与规避**：动画只用 transform/opacity 是利用；批量修改的高级做法是 DocumentFragment 一次插入、改 class 替代逐条改 style、脱离文档流改完再插回（display: none 冷藏）。

收尾：完整管线、rAF/rIC 时机与层爆炸的反面，深度精讲见 8.1 的口述版。

> 面试官追问点：为什么「循环里读十次 offsetTop」没有想象中糟？应答思路：同一帧内第二次读取命中布局缓存（布局没脏就不重算），真元凶是读写交错——写弄脏布局后再读才强制重算；答出「脏标记 + 缓存命中」说明读的是机制不是清单。

#### 1.3.3 CSS选择器优先级怎么算？伪类伪元素差在哪

答：一句话定调，**优先级是四元组 (inline, id, class, 元素) 从左到右逐位比较、不进位；伪类记在 class 位、伪元素记在元素位——这是两者在优先级层面的本质区别**。

**四元组算法**：行内样式记 (1,0,0,0)、id 记 (0,1,0,0)、class/属性选择器/伪类记 (0,0,1,0)、元素/伪元素记 (0,0,0,1)——**11 个 class 压不过 1 个 id（不进位比较）**。!important 是体系外的最后一层：同 important 再比四元组，同级后者赢。`*` 与 :where() 永远是 0；:is() 取参数里最高位（它的优先级陷阱）。

**伪类与伪元素**：伪类描述「状态」——:hover/:focus/:nth-child 是满足条件的元素本身；伪元素创建「不存在于 DOM 的抽象节点」——::before/::placeholder。优先级上：一个伪类顶一个 class，一个伪元素顶一个元素。

**深水区**：:nth-child(n) 数「所有兄弟」里的第 n 个（再验证选择器），:nth-of-type(n) 只在「同类型兄弟」里数——**`.box:nth-child(2)` 在前面插一个 span 就失配**，这就是 nth-child 脆弱的原因；选择器从右向左匹配，长选择器反而更慢——**BEM 的短类名不止是工程习惯，还是性能答案**。

收尾：优先级答「四元组不进位」、伪类伪元素答「状态 vs 虚拟节点」、工程答「一个 class 搞定不要叠十层」。

> 面试官追问点：为什么 :is() 的优先级取参数最高位而不是按实际匹配算？应答思路：优先级是选择器的静态属性，解析期就确定——运行时匹配到哪个参数不影响优先级；「优先级先于匹配求值」这个设计答出来，说明读的是规范不是博客。

### 1.4 HTML与语义化

#### 1.4.1 语义化标签有哪些意义？无障碍与SEO怎么做

答：一句话定调，**语义化是「写给机器的 API」——视觉用 CSS 实现，结构语义才是 HTML 的本职；SEO 与无障碍是同一件事的两个受益方，靠的都是解析 HTML 的机器**。

**三层收益**：SEO——爬虫对语义标签加权（h1-h6 层级、strong/em 强调、a 的 href）；可读性——维护者读结构不读 div 嵌套；无障碍——屏幕阅读器按语义朗读（nav/main/button 可聚焦可回车）。

**无障碍工程三件套**：alt 是「图挂了 + 读屏」双保险（装饰图用空 alt 跳过）；aria-* 是语义的补丁层（aria-label 给无文字按钮命名、role 重定义语义）——**第一原则：能用原生语义就不要 aria 打补丁**（原生 button 自带键盘行为，div + role="button" 要自己补一整套键盘处理）；标题层级不跳级，一页一个 h1。

**深水区**：loading="lazy" 是 HTML 层的原生懒加载（内置 IntersectionObserver），与 data-src 手动方案相比零 JS 成本但不可调阈值；过度语义（每段都 article）和 div 一把梭一样是反模式。

收尾：主线一句——**语义是给机器的接口，样式是给人的接口**；爬虫、读屏、浏览器自身都在读这份 HTML。

> 面试官追问点：div + class 能实现一模一样的视觉，语义化的价值怎么量化？应答思路：视觉等价但机器行为不等价——SEO 权重、读屏导航（跳过 nav 直达 main）、原生控件的键盘/焦点/事件语义全是白送的；反例：a 加 onclick 不写 href——tab 聚焦不到、爬虫不识别为链接，「视觉相同、行为残废」就是量化的反面。

#### 1.4.2 HTML5核心API有哪些？各适用什么场景

答：一句话定调，**HTML5 的 API 主线是「把过去靠插件和 hack 的能力原生化」——路由依赖 history、双向实时依赖 WebSocket/SSE、CPU 密集靠 Web Worker**。

**history 与路由**：pushState/replaceState 改 URL 不刷新（SPA history 路由的基础），popstate 监听回退。hash 与 history 的对比三行：hash 带 # 不需要服务端支持；history 干净、**但刷新/直访要服务端配 fallback**（所有路由回指 index.html）。深水区：pushState 不触发 popstate（自己压的要自己渲染）、bfcache 与 scrollRestoration。

**WebSocket 与 SSE**：WebSocket 全双工、支持二进制、自有协议（ws://）——聊天/协作/游戏；SSE 是 HTTP 长连接上的**单向**服务端推送、自动重连、文本 only——通知流、行情推送这类只需单向的场景 SSE 更轻。

**Web Worker**：开真线程跑 CPU 密集任务（图片处理、大计算、大 JSON 解析），**代价是独立全局作用域（没有 window/document）、postMessage 结构化克隆通信、不能直接操作 DOM**（存储方案对比见 JS 篇）。深水区：SharedArrayBuffer + Atomics 的共享内存路线（需 COOP/COEP 安全头）、OffscreenCanvas 把绘制挪进 Worker。

收尾：按「路由/实时/多线程」三主线各报一个「什么时候不用它」——history 要 SSR 兜底、单向推送用 SSE、Worker 有 DOM 禁手，判断力比清单值钱。

> 面试官追问点：WebSocket 和 SSE 为什么不互相替代？应答思路：SSE 走原生 HTTP（代理/防火墙全兼容、断线自动重连、EventSource 语义简单）但单向 + 文本；WebSocket 全双工 + 二进制，但要自己实现重连/心跳/鉴权——「单向用 SSE、双向用 WebSocket」，答出重连与协议成本就到位。

# 2.Vue经典问题

### 2.1 响应式与渲染

#### 2.1.1 Vue2和Vue3响应式差异？Proxy强在哪里

答：必问题。一句话定调，**响应式 = 依赖收集（谁在用我）+ 派发更新（我变了通知谁），Vue2 用 defineProperty 劫持 getter/setter、Vue3 用 Proxy 劫持整个对象操作，差距在「拦截面的完整性」**。

**Vue2 的机制**：递归遍历 data 给每个属性定义 getter/setter，getter 收集 Watcher、setter 派发更新（进异步队列 nextTick 统一执行）。

**Vue2 的三宗罪**：新增/删除属性拦截不到（要 Vue.set/Vue.delete 打补丁）；数组下标和 length 拦不到（改为劫持 push/pop/shift/unshift/splice/sort/reverse 七个变异方法）；初始化要递归全量劫持（大对象初始化慢）。

**Proxy 强在哪**：拦截 get/set/deleteProperty/has 等 **13 种操作**，新增删除天然可拦；**惰性代理**——get 触发时值是对象才递归包 Proxy，初始化 O(1)；依赖结构从「每属性一个 Dep」升级为 **targetMap（WeakMap→Map→Set）三级结构**，effect 取代 Watcher 打通函数式写法。

收尾：两个断言值得背——「Proxy 解决拦截完整性、惰性解决初始化成本」，完整口述版见 8.2 深度精讲。

> 面试官追问点：为什么 Vue3 仍不建议直接改数组 length？应答思路：Proxy 能拦截 set(length)，但语义上会连带影响所有下标，触发全量更新代价大；Vue3 的处理是警告 + 推荐整体替换或用会触发下标 set 的方式。

#### 2.1.2 v-model双向绑定的本质？组件上怎么自定义

答：一句话定调，**v-model 是编译期语法糖——表单元素上展开为 :value + @input，组件上展开为 :modelValue + @update:modelValue，所谓双向绑定就是「下行 props + 上行事件」的约定**。

**表单元素上的差异**：input/textarea 用 value + input；checkbox/radio 用 checked + change；select 用 value + change——**同一语法糖按表单类型展开成不同的属性与事件对**，这是很多人背不全的点。

**组件上的自定义**：子组件声明 props: ['modelValue'] + emit('update:modelValue')；**Vue3 支持参数化多 v-model**——`v-model:title="t"` 展开为 :title + @update:title，一个组件可同时双向多个值（Vue2 只有 .sync 干这事）。

**三个内置修饰符的实现**：lazy 换 change 事件（失焦才同步）、number 用 parseFloat 把字符串转数字（转不动则保留原值）、trim 首尾去空白——**修饰符不是运行时魔法，是编译期改变生成的事件处理代码**；Vue3 组件还能自定义修饰符（通过 modelModifiers props 拿到）。

收尾：答题主链「语法糖 → 展开 → 组件自定义 → 修饰符是编译期行为」，最后点一句「v-model 没有违反单向数据流——数据仍然只有一条下行通道，事件是上行通道」。

> 面试官追问点：v-model 是双向数据流吗？应答思路：不是——它是单向数据流的语法封装，父传子 props、子 emit 事件父改数据，环只存在于父子约定之间；答出「双向的是视图与数据，不是组件间数据流」即到位。

#### 2.1.3 虚拟DOM和diff算法原理？key的作用是什么

答：必问题。一句话定调，**虚拟 DOM 是「用 JS 对象描述 UI，变更先比对象再最小化操作 DOM」，diff 的三前提是同层比较、同类型深比、key 复用——Vue2 双端比对、Vue3 预处理加最长递增子序列**。

**虚拟 DOM 的价值与代价**：价值是声明式编程模型 + 跨端能力 + 最小化 DOM 操作；代价是「生成 vnode + diff」本身的开销——Vue3 用编译优化（patchFlag）把这笔税降回来。

**diff 三前提**：只同层比（跨层移动当删除+新增）、同类型才深比（标签不同整棵替换）、**key 是节点身份证**——有 key 才能复用移动；**index 作 key 两个坑**：头插数据全列表错位复用 + 带状态元素（输入框）复用错误的 DOM（状态串位）；随机数作 key 复用率为零。

**双端 vs LIS**：Vue2 四指针头尾匹配处理常见移动模式；Vue3 先同步头尾预处理，剩余部分求**最长递增子序列——LIS 里的不动、不在 LIS 里的才移动**，数学上把移动次数压到最小。

收尾：同层、类型、key 三前提 + 本框架的策略（双端/LIS/React 单向），能对比两家取舍就到深水区——完整版见 8.6 深度精讲。

> 面试官追问点：为什么 Vue 的 diff 能做双端优化而 React 不做？应答思路：Vue 全量内存 diff 可以任意挪指针；React Fiber 可中断、回退指针现场恢复复杂，单向扫描配合 lane 标记更适合流式处理——两种工程取向，性能争论的根源在这。

#### 2.1.4 nextTick的原理是什么？什么时机获取DOM

答：一句话定调，**改数据后 DOM 不是立即更新——Vue 把 watcher 去重后放进异步队列，在微任务里统一 flush；nextTick 就是把你的回调插到 flush 之后，所以回调里能拿到更新后的 DOM**。

**异步渲染队列**：一次事件循环里改十次数据，Watcher 去重后只有一次真正重渲染——批量是性能设计，副作用是「同步代码里拿不到新 DOM」。

**为什么选微任务**：微任务在本次事件循环内、渲染之前执行——flush 放微任务能保证「同一次渲染前把所有状态改完」，且比宏任务早一帧；nextTick 内部是降级链（Promise.then → MutationObserver → setImmediate/setTimeout），Vue3 直接用 Promise 不再降级。

**使用时机**：改数据后要读 DOM 尺寸/操作 DOM（focus、滚动定位）时包在 nextTick 里；created 里拿 DOM 也是它（虽然更推荐用 mounted）。

**深水区**：多次 nextTick 的回调按注册顺序先进先出；Vue3 的调度器刷新（render + updated 钩子）本身也通过微任务排队、且排在用户回调之前——**所以 nextTick 回调执行时 updated 已跑完**，这正是「nextTick 里拿更新后 DOM」的时序保证。

收尾：一句话「**批量更新是设计，nextTick 是这个设计的配套出口**」。

> 面试官追问点：为什么宏任务做不了这件事？应答思路：宏任务排在渲染之后才执行，同一轮改动要等下一帧才 flush，用户先看到旧状态再看到新状态（丢帧感）；微任务在渲染前执行，一帧内完成「改完+渲完」——时序差一帧就是体验差一级。

#### 2.1.5 ref和reactive的区别？为什么ref要.value

答：必问题。一句话定调，**分工本质是语言的类型约束：Proxy 只能代理对象，原始值包不了——ref 用 { value: xxx } 盒子包原始值再代理盒子，所以访问必须 .value，这不是设计缺陷而是「原始值无引用」的最小代价解**。

**两者的分工**：reactive 管对象（Proxy 直接代理，不需要 .value）；ref 管一切（原始值装盒子，对象内部其实转交 reactive）；模板里 ref 自动解包（编译器语法糖），script 里必须 .value。

**两个高频坑**：一，**reactive 解构丢失响应**——解构是值的拷贝，拆出来的普通变量和原对象断链，解法 toRefs 把每个属性转成「指向原属性的 ref」；props 解构同理要 toRefs(props)。二，**给 reactive 整体赋新值**（obj = {...}）会换掉代理对象引用，历史订阅失效——要整体替换就用 ref，或 Object.assign 原地改。

**深水区**：shallowRef 只代理第一层（大数据结构跳过深层递归，性能手段，代价是深层修改不触发——要配 triggerRef）；ref 的深层响应是「.value 是对象时惰性转 reactive」；vue 宏的编译期响应（ref-sugar 思路）消掉 .value 是编译器干的，运行时机制没变。

收尾：背下两个断言——「**reactive 管对象、ref 管一切（含原始值）**」「.value 是原始值无引用的语言事实」，完整版见 8.2 深水区。

> 面试官追问点：为什么不能让 Proxy 直接代理原始值？应答思路：Proxy 的 target 必须是对象（new Proxy(42, handler) 直接报错），原始值按值传递、没有稳定的内存引用可供代理挂靠——ref 盒子是唯一的语言级出路，能讲清这个语言约束就超过 80% 候选人。

### 2.2 组件与状态

#### 2.2.1 Vue组件通信方式有哪些？各适合什么场景

答：一句话定调，**按「组件关系」选通信方式——父子 props/emit、跨级 provide/inject、全局状态管理、透传 $attrs、模板引用 defineExpose，事件总线已被 Vue3 官方抛弃**。

**五种方式按关系选**：父子——props 下行 + emit 上行（单向数据流的正统通道），v-model 是它俩的语法糖；跨级——provide/inject（依赖注入，免逐层透传，**默认非响应式，要传 ref/computed 保响应**）；兄弟/任意——状态管理库（Pinia）共享响应式状态；**$attrs 透传**——Vue3 把 $listeners 合并进 $attrs，没声明的 props 自动落到根元素（class/style 合并规则要注意）；模板引用——ref 拿实例 + defineExpose 显式暴露（组合式 API 默认封闭，比 Vue2 更安全）。

**事件总线的谢幕**：Vue3 移除 $on/$off，事件总线失去基础设施——**全局可变状态被官方定性为反模式**（来源不清、时序难追），替代品：全局用 Pinia、组件间短暂通信用 mitt 库或 props 链。

**深水区**：provide/inject 的响应式——注入「值的引用」而非「值」（provide('x', ref)），子组件拿到的是响应式源；跨层级的反向通知用「注入方法」模式（父 provide 一个修改函数，子调用它改父状态），避免子组件直接改注入物。

收尾：选型口诀「**有数据流用 props/emit，隔代依赖用 provide，全局共享用 Pinia，DOM 操作用 ref+expose**」。

> 面试官追问点：provide/inject 为什么默认不响应？应答思路：provide 的值是发起时的一次快照式传递（不追踪后续变化），要跨时序共享必须传 ref/computed（共享的是「响应式容器」而不是「当时的值」）——答出「容器 vs 值」的区分即到位。

#### 2.2.2 computed和watch的区别？使用场景怎么选

答：一句话定调，**computed 是「派生值」——缓存 + 依赖不变不重算；watch 是「响应副作用」——数据变化执行回调；watchEffect 是「自动依赖的立即执行版」，三者按「要值还是要行为」选**。

**computed 的本质**：惰性求值 + 缓存——依赖不变直接返回缓存，多次读取只算一次；有副作用的场景（请求、改 DOM）不要写进 computed。Vue3 深水区：缓存机制从「依赖队列」升级为 **dirty 标记**（依赖变 → 标脏 → 读时才重算），嵌套 computed 的脏标记逐层传播。

**watch 的三件配置**：deep（深度遍历监听，代价是逐层递归追踪 + 对比）、immediate（立即执行一次）、**onCleanup 清理副作用**——回调第二次触发前执行上次的清理（防竞态：上一次请求回来时丢弃）。

**watchEffect 的差异**：立即执行 + 自动收集依赖（用到谁听谁），适合「依赖多且懒得列」的副作用；watch 显式声明依赖源 + 拿新旧值，适合「明确的观察」。调度时机默认 pre（组件更新前），flush: 'post' 拿更新后 DOM。

**深水区**：watch 源写函数 vs 写对象（`() => obj.a` 只听一个属性，`obj` 整体要 deep）；watch ref 与 reactive 的差异（ref 监听 .value 整体替换，reactive 隐式 deep）。

收尾：选型一句话——**要展示结果用 computed、要执行动作用 watch、依赖懒得声明用 watchEffect**。

> 面试官追问点：computed 和 methods 的差异被问烂了，反过来问「computed 里发请求会怎样」？应答思路：破坏纯函数约定——缓存语义要求同依赖同结果，请求引入时序不确定性；且 computed 何时重算不受你控制（读取驱动），副作用的触发点失控——答出「缓存的契约容不下副作用」即到位。

#### 2.2.3 生命周期钩子执行顺序？父子组件顺序是什么

答：一句话定调，**父子生命周期像括号嵌套：创建是父先、挂载完成是子先（父 beforeMount → 子全部生命周期 → 父 mounted）——因为 DOM 深度优先，内层先完成**。

**挂载顺序**（记住这一条就够推导）：父 setup → 父 beforeMount → 子 setup → 子 beforeMount → 子 mounted → 父 mounted。**更新的联动顺序**：父 beforeUpdate → 子 beforeUpdate → 子 updated → 父 updated。**销毁**：父 beforeUnmount → 子 unmounted → 父 unmounted。

**组合式 API 的对照**：setup 执行在 beforeCreate 之后、created 之前（所以 setup 里拿不到 this、也等价于「created 的逻辑位」）；beforeDestroy/destroyed 改名 beforeUnmount/unmounted——语义修正（组件卸载不等于销毁，还可能被 keep-alive 缓存）。

**keep-alive 的第三组钩子**：缓存组件不重复走 created/mounted，取而代之 activated（激活）/deactivated（失活）——**离开缓存的组件不销毁、只是失活**，定时器等副作用要在这对钩子里挂卸。

**深水区**：父子 updated 的触发是「各自渲染队列独立入队」还是联动？——父更新导致子 props 变，子才更新；子自身状态变不通知父。这解释了为什么「父 updated 时子一定 updated 完」在 props 驱动场景成立。

收尾：记「**创建父先、完成子先**」八个字，其余全部可以现场推导。

> 面试官追问点：为什么 mounted 里拿到的 $el 一定有内容，而子组件的 mounted 先于父？应答思路：挂载是深度优先的递归插入——子树先完成 DOM 构建，父的 mounted 回调才被调用；所以父 mounted 里可以安全地 querySelector 到子孙 DOM，而子 mounted 里拿不到兄弟组件的 DOM。

#### 2.2.4 Pinia和Vuex差异在哪？mutation为何被移除

答：一句话定调，**两家的灵魂都是单向数据流（state 只能被 action 改），Pinia 砍掉 mutation 不是简化而是纠错——mutation 是为 devtools 时间旅行服务的仪式，不是必需品**。

**mutation 的历史使命**：Vuex 用「同步 mutation + 异步 action」的分离让 devtools 能确定性地追踪每步状态变化（异步调度追踪成本高）；代价是每个状态修改都要写「action 调 mutation」的样板代码。**Pinia 的解法**：devtools 直接订阅 action（同步异步都能记录），仪式失去必要性——action 里直接改 state，代码量砍半。

**其余五处升级**：去 module 嵌套——每个 store 独立定义、store 间直接互相引用（不再有 namespace 字符串）；天然 TS 推导——不用包装函数+类型断言；**组合式 store**——defineStore 第二参可以写 setup 函数（ref/computed/function 自由组织）；体积减半；DevTools 集成不变。

**持久化与工程件**：持久化用 pinia-plugin-persistedstate（localStorage 同步指定字段）；SSR 用 hydrate 状态注入；**$patch 批量修改**（对象或函数两种形式）替代 mutation 的「一改一提交」。

**深水区**：store 间依赖是「在使用时引入」（函数里 useOtherStore()）避免循环引用；store 是单例但 setup 写在函数外层会丢失组件作用域——响应式部分必须写在 setup 内。

收尾：答「mutation 为何被移除」的准确说法是「**它解决的是工具问题，不是架构问题；工具进步后仪式就成了负担**」。

> 面试官追问点：Pinia 去 mutation 后 devtools 怎么做时间旅行？应答思路：devtools 通过 $subscribe 订阅 state 变化 + action 订阅，每次变更生成快照——快照链就是时间旅行的轨道；同步异步的区分不再重要，因为快照以「变化时刻」为单位而不是「调用栈」为单位。

### 2.3 生态与优化

#### 2.3.1 Vue3组合式API解决什么？编译优化做了哪些

答：一句话定调，**组合式 API 解决的是「关注点散落」——options 把一个功能拆进 data/methods/computed 三处；编译优化解决的是「运行时全量 diff 的税」——静态提升 + patchFlag 让 diff 只碰动态节点**。

**组合式 API 的两笔账**：代码组织——同一功能的 ref/计算/副作用写在一起，可自由拆成 composables；逻辑复用——替代 mixin（命名冲突 + 来源不明两大原罪），useXxx 函数是显式依赖、显式返回。**新组件三件**：Fragment（多根节点，不再需要套 div）、Teleport（传送到 body 等目标，弹窗/tooltip 不受父级 overflow 层叠污染）、Suspense（异步组件的 loading 协调）。

**编译优化两板斧**：**静态提升（hoistStatic）**——静态节点提到 render 函数外只创建一次，重渲染跳过；**patchFlag 靶向更新**——动态节点打标记（class/text/props 等），diff 时静态块直接跳过、动态属性按 flag 精确比对——**这是「Vue 模板可静态分析」换来的运行时收益，JSX 流派拿不到**（对照 React：任意表达式编译期不可知，只能运行时全量 diff + memo 边界）。

**深水区**：cacheHandlers 缓存内联事件（避免重渲染因函数引用不同而失效，配合 v-memo 缓存子树）；block tree ——动态节点收集进平铺数组，diff 从「递归整树」变「遍历数组」，复杂度与模板大小解耦。

收尾：一句话收束——**组合式 API 是给开发者的（组织代码），编译优化是给机器的（跳过静态）**，两者拼起来回答「Vue3 为什么快又好写」。

> 面试官追问点：为什么 React 不做 patchFlag 这类编译优化？应答思路：JSX 是任意表达式（手写 render 逻辑编译期不可知），Vue 模板是受限 DSL（结构静态可分析）——**模板约束换编译期信息**是两家性能路线的分水岭，详见 8.6。

#### 2.3.2 Vue Router两种模式差异？导航守卫怎么用

答：一句话定调，**hash 靠 hashchange 不惊动服务器、history 靠 pushState 干净但要服务端兜底；导航守卫是一条「失活→全局→路由→组件→确认」的流水线，权限就挂在 beforeEach**。

**两种模式**：hash——URL 带 #，hashchange 事件驱动、不发起服务器请求、**部署零配置**、丑且 SEO 弱；history——pushState/replaceState 改 URL 不刷新、popstate 监听回退、**刷新/直访要服务端配 fallback**（所有路由回指 index.html）——选型三行答完。

**守卫的完整执行顺序**（背链不背清单）：导航触发 → 失活组件 beforeRouteLeave → **全局 beforeEach** → 复用组件 beforeRouteUpdate → 路由独享 beforeEnter → 激活组件 beforeRouteEnter（**这里拿不到 this，只能 next(vm => ...) 在确认后访问**） → 全局 beforeResolve → 导航确认 → 全局 afterEach（ analytics 埋点挂这）。

**动态/权限路由两套方案**：**前端全量**——路由表全量定义 + meta.roles 过滤，登录后按角色 addRoute 注册可见子集（简单但路由表体积和逻辑暴露在前端）；**后端下发**——登录后接口返回路由表 addRoute 动态注册（前端只留映射组件的映射表）——选型按「权限粒度 + 路由表是否敏感」。

**深水区**：addRoute 后首次跳转的白屏问题（匹配不到要 next(to.fullPath) 重进一次）；路由懒加载 `() => import()` 与 webpack 魔法注释（/* webpackChunkName */）分包。

收尾：守卫答「完整链 + 权限挂全局钩子」，模式答「三行对比 + fallback」——这题就完整了。

> 面试官追问点：beforeRouteEnter 为什么拿不到 this？应答思路：守卫执行时组件**还未创建**（导航确认在前、实例化在后）——它是唯一支持 next 回调传 vm 的守卫，回调在 mounted 之后执行；能讲出「守卫先于实例化」的时序本质，说明真懂了。

#### 2.3.3 Vue项目性能优化怎么做？六个手段是什么

答：一句话定调，**Vue 的性能优化从三层做减法——渲染层（少 diff）、组件层（少渲染）、数据层（少追踪），六个手段每层两个**。

**渲染层**：一，**v-if 与 v-show 的取舍**——频繁切换用 v-show（display 切换，初次成本高）、条件渲染用 v-if（真移除，惰性）；二，**v-for 的两条军规**——必带 key（复用链路见 2.1.3）、**v-if 不与 v-for 同节点**（Vue3 中 v-if 优先级更高拿不到循环变量，要包 template 层）。

**组件层**：三，**大列表虚拟滚动**——可视窗口裁剪 + 上下缓冲，DOM 数量从 N 降到常数（见 7.2 场景题）；四，**组件懒加载与 keep-alive**——defineAsyncComponent 按需分包 + 路由级懒加载；keep-alive 缓存组件实例跳过重挂载（缓存要配 include 白名单，防内存膨胀）。

**数据层**：五，**shallowRef 处理大对象**——跳过深层代理（如 echarts 实例、编辑器实例这类「只需要整体替换感知」的对象），深层修改用 triggerRef 手动触发；六，**v-memo 缓存子树**——依赖数组不变整块跳过 diff（Vue3 特性，列表项级的 memo 粒度）。

**深水区**：事件与定时器在 unmounted 清理（Vue3 无 $off，组合式函数的 onScopeDispose 是正解）； SSR 场景的优化边界（客户端注水成本见 8.10）。

收尾：六个手段按「渲染/组件/数据」三层报，每层先讲「层的问题」再讲手段——结构化比背清单高一档。

> 面试官追问点：shallowRef 和 markRaw 有什么区别？应答思路：shallowRef 是「浅响应」——只有 .value 整体替换触发更新（内部仍可读写）；markRaw 是「标记永不代理」——对象根本不进响应式系统（Vue3 会警告用 reactive 包 markRaw 对象）——前者是降低追踪粒度，后者是彻底退出系统，按「要不要感知整体替换」选。

# 3.React经典问题

### 3.1 组件与Hooks

#### 3.1.1 函数组件和类组件差在哪？为什么推函数组件

答：一句话定调，**类组件的状态挂在实例上（this 一辈子不变、值是变的），函数组件每次渲染整个函数重跑（props/state 变量是新的、函数是新的）——这个「快照模型」是理解两者差异与一切闭包陷阱的钥匙**。

**三处硬差异**：this——类组件靠 this 读状态（**this 是同一个、this.state 是会换的**，所以 setTimeout 里 this.state.count 拿到的可能是旧值）；逻辑复用——类组件靠 HOC/renderProps（嵌套地狱），函数组件靠自定义 Hook（普通函数调用，无嵌套无命名冲突）；代码组织——类把一个功能拆进 lifecycle 方法里（ componentDidMount 里干三件不相干的事），函数组件按关注点用 Effect 组织。

**为什么主推函数组件**：逻辑复用是表层理由，深层是** Hooks 让 React 拿到「状态与 UI 的彻底解耦」**——状态不依赖实例，才有了并发渲染下「渲染可中断可重放」的安全前提（类组件的实例状态在重放里会脏）。

**类组件的遗留场景**：Error Boundary（getDerivedStateFromError 目前没有 Hook 版，官方说法是「不常见到值得加 API」）；老库的 this 依赖与 ref 转发（forwardRef 老写法）。

收尾：答这题的暗线是「**类=长存实例模型，函数=快照渲染模型**」——后面 3.1.2 的闭包陷阱、3.2.1 的可中断渲染全建立在这条线上。

> 面试官追问点：函数组件里 setTimeout 拿到旧 state 是 bug 还是设计？应答思路：是设计——每次渲染是一个快照，回调闭包捕获的是「那次渲染的 state」；要最新值用函数式更新 setCount(c => c+1) 或 useRef 存最新值——能答「快照不是过期」就对了。

#### 3.1.2 Hooks为什么不能写条件里？链表原理是什么

答：必问题。一句话定调，**hooks 的状态不存在对象上而是存在 Fiber 的 memoizedState 单链表里，靠「调用顺序」对应槽位——条件分支导致某次渲染少调一个 hook，后面全部错位到别人的状态槽**。

**链表原理**：React 不记录「useState 叫什么名字」，只记录「第 N 个 hook」——第一次渲染建立链表（每个节点存值+更新队列），重渲染按同样的顺序遍历。**所以规则的本质是「顺序稳定」而非「数量固定」的语法洁癖**——早 return、if 包裹、循环里调用全都会破坏顺序。

**闭包陷阱与函数式更新**：setCount(count + 1) 连点三次只加一（每次回调捕获的都是渲染时的 count 快照）——**解法 setCount(c => c + 1)**，更新函数拿的是「队列里的最新值」，绕开闭包。深水区：更新函数会被排进 hook 的 update 链表，渲染时 reduce 汇总。

**useState 与 useReducer 的选择**：状态是「多字段强关联的下一状态」（登录表单的 loading/error/data）用 useReducer（一个 action 描述整体变化）；**下一种状态依赖上一种状态**时 reducer 是唯一解；简单独立值用 useState。

收尾：一句话「**hook 记的是位置不是名字**」——这条解释了规则、闭包陷阱和迁移的一切。

> 面试官追问点：为什么 React 不做成「按 key 对应」而要坚持顺序？应答思路：按 key 存需要用户传稳定 key 且每次渲染额外比对，顺序在绝大多数场景天然稳定（只要函数从头跑到尾）——**用「最小约定换零成本定位」**；顺带能答出 eslint-plugin-react-hooks 的 rules-of-hooks 正是顺序规则的静态检查（exhaustive-deps 管的是依赖数组完整性）就是加分。

#### 3.1.3 useEffect的执行时机是什么？清理函数何时跑

答：一句话定调，**useEffect 是「提交后的被动副作用」——DOM 更新完成后异步调度、不阻塞浏览器绘制；清理函数在「下一次 effect 前」和「卸载时」各跑一次**。

**依赖数组的四档语义**：不传数组每次渲染后都跑；空数组只在挂载后跑一次（卸载前清理）；传依赖只在依赖变化后跑；**返回的 cleanup 在「下次 effect 执行前」先跑**——订阅/取消订阅的对称性由它保证。

**严格模式的双调用**：React18 严格模式下挂载-卸载-再挂载各一次（effect 跑两遍）——**目的是暴露「缺清理的副作用」**（订阅了没退订，跑两遍立刻泄漏）；修复姿势不是关掉严格模式，是把 effect 写成对称的。

**useLayoutEffect 与 useEffect 的先后**：useLayoutEffect 在 DOM 变更后**同步**执行（阻塞浏览器绘制）、useEffect 在**绘制后异步**执行——读布局再改样式的场景（tooltip 定位、防闪烁）用 layout 版，其余用普通版（同步占主线程是它的代价）。

**深水区**：effect 的「定时」不是微任务——它有独立的调度（commit 后的 passive effect 队列），React 保证按组件树顺序执行；**依赖数组的「引用相等」是判据**——对象/函数字面量每次都是新引用，这就是 exhaustive-deps 报警的来源，解法是 useCallback/useMemo 或把「依赖意图」收敛进函数式更新。

收尾：答题主链「**渲染 → commit DOM → 画屏 → 被动 effect**」，时机讲清楚，清理讲「下次前+卸载时」两拍。

> 面试官追问点：为什么清理函数不能是 async？应答思路：cleanup 要求同步完成「取消动作」，而异步清理的取消时机不可控（await 后组件可能已卸载）；异步 effect 的正解是 AbortController/取消标志 + 清理函数同步设置标志——「异步流程配同步取消信号」是这个模型的标准搭配。

#### 3.1.4 useMemo和useCallback区别？渲染怎么优化

答：一句话定调，**useMemo 缓存「计算结果」、useCallback 缓存「函数引用」（本质是 useMemo(() => fn) 的特例）——两者都靠依赖数组判命中，都解决「每次渲染引用变化」引发的连锁重渲染**。

**三件套的配合**：父组件传函数给 memo 子组件——**不包 useCallback 每次新引用，memo 浅比较直接失效**；useMemo 防止昂贵计算的重复执行 + 防止「计算产物是对象」导致的下游比较失效；React.memo 用浅比较决定跳过重渲染——**三者是「缓存-稳定-拦截」的一条链**。

**什么时候不需要优化**：计算的执行时间小于「维护缓存 + 比较依赖」的成本（大多数 map/filter）；组件本身很轻、渲染开销小于 memo 浅比较 props 的开销——**React 官方立场是「把 memo 当性能工具箱里的最后一件」**，先量后用。

**useTransition 与并发渲染**：把状态更新标记为**可中断的低优先级**（不阻塞用户输入），isPending 提供过渡态——「搜索输入即时响应、结果列表慢点出现」的官方解法；useDeferredValue 是它的值语义版。

**深水区**：memo 的浅比较陷阱——props 里带 children（JSX 每次 new）或对象字面量，比较永远不等；「用 useMemo 才是对的」的真正场景：**引用语义依赖**（effect 依赖、memo 子组件）而不是「计算很贵」。

收尾：口径背一句——**useCallback 稳引用给下游、useMemo 稳值给下游、memo 拦截无谓渲染；优化先量再做**。

> 面试官追问点：useCallback(fn, []) 能替代 useMemo 吗？应答思路：useCallback 是 useMemo 的函数特例（返回值是函数时省一层壳），但空依赖意味着闭包冻结——里面读到的 state 永远是首次渲染的快照；「缓存引用」和「冻结闭包」是两件事，混用就是闭包陷阱的 hook 版。

#### 3.1.5 受控组件和非受控组件差在哪？表单方案怎么选

答：一句话定调，**受控是「值活在 state、每次击键都 setState 重渲染」，非受控是「值活在 DOM、提交时才取」——选择按「每个字符要不要参与 React 世界」**。

**受控组件**：value + onChange 把输入框变成单向数据流的投影——**好处是实时校验、条件禁用、格式化输入全在渲染里自然表达**；代价是每次击键一次重渲染（大表单上要拆组件把 state 下沉）。

**非受控组件**：defaultValue + ref 在提交时读值——文件输入（value 只读）**只能**非受控；代价是无法实时响应输入过程。深水区：`defaultValue` + `key` 重置模式的取舍（用 key 强制重建组件清空表单）。

**表单库的原理**：react-hook-form 的思路是**非受控 + 注册**——ref 注册到原生表单，输入不触发 React 渲染（uncontrolled 的性能）、校验在库的订阅体系里跑，提交时一次性收集；与受控方案（Formik 每击键 setState）对比，大表单的输入延迟差一个量级——**「受控的一致性 vs 非受控的性能」就是表单库选型的分水岭**。

**深水区**：受控里「每键 setState」的优化思路——state 下沉到最小使用组件、useTransition 降优先级、防抖不改变重渲染只改下游。

收尾：答题三行「受控 = 单向数据流投影、非受控 = DOM 是事实源、表单库 = 注册制非受控」，选型一句话「小表单受控、大表单上库」。

> 面试官追问点：受控组件每次击键全组件树重渲染，为什么还能用？应答思路：React 的协调成本远低于想象（diff 后打补丁），加上「state 下沉 + memo 拦截」可以收敛重渲染范围——真正的分界是「表单里有没有每键联动的高开销逻辑」（自动联想、联动校验），有才需要非受控或库方案。

### 3.2 原理与生态

#### 3.2.1 Fiber架构解决了什么？时间切片怎么实现

答：必问题。一句话定调，**Fiber 把「不可中断的递归渲染」改写成「可暂停的链表遍历」——child/sibling/return 三指针把树变链表，时间片用完就存现场还主线程，双缓冲树让恢复只是指针切换**。

**老架构的病**：React15 同步递归 diff，千级组件一口气跑上百毫秒，主线程占死、动画掉帧——JS 单线程没有抢占，唯一出路是「**大任务拆小、主动让权**」。

**三个核心件**：Fiber 节点（链表化的工作单元）；**双缓冲树**（current 在屏 / workInProgress 在建，commit 时指针原子切换）；**两阶段语义**——render 可中断可重跑（严格模式双调用就是暴露不纯代码）、commit 不可中断（替换树 + DOM 操作 + 同步生命周期）。

**时间切片**：MessageChannel 宏任务做切片心跳（不是 setTimeout，嵌套定时器有 4ms 钳制）；**Lane 模型用 31 位二进制表示优先级**，高优先级可打断低优先级 render 插队——「输入响应优先于数据加载」的机制根基。

收尾：Fiber 的本质一句话——**「渲染的同步独占」改成「时间片上的链表遍历」，让 React 拿到调度权，调度权让出优先级这个新维度**——完整版见 8.3 深度精讲。

> 面试官追问点：为什么时间切片用 MessageChannel 而不是 setTimeout 或 requestIdleCallback？应答思路：setTimeout 嵌套 5 层后被钳到 4ms 最小间隔（不可控的延迟碎片）；rIC 的执行时机太不可预期（可能一直不空闲）；MessageChannel 是「不进任务队列头部钳制」的宏任务，能稳定在每帧留出的空隙里回调——三种的排除法答出来就是深水区。

#### 3.2.2 React合成事件是什么？和原生事件差在哪

答：一句话定调，**合成事件是 React 在原生事件之上做的一层「统一包装 + 根节点委托」——浏览器差异抹平、事件池复用、跨越 17 版本的委托位置迁移是它的三条主线**。

**机制**：原生监听器只挂在**应用根容器**（React17 起；之前是 document）——所有组件事件冒泡到根再分发——**换根的原因**：多 React 应用共存时 document 委托互相打架 + 渲染到 portal/不同容器时语义更准。事件对象是 SyntheticEvent（合并了 stopPropagation/preventDefault 的统一接口）。

**与原生事件的三个差异**：一，**e.stopPropagation() 阻断的是 React 的分发链，document 上的原生监听器照样触发**（React17 改根容器后，根容器的原生监听也会触发）——要拦原生得用原生捕获或 e.nativeEvent.stopImmediatePropagation；二，阻止默认行为：受控表单里 e.preventDefault() 的兼容性封装（ie 的 returnValue）——React 已抹平；三，**target 与 currentTarget 的语义保留**——合成事件在分发时保持了正确的模拟冒泡链。

**深水区**：事件池（React16 复用事件对象、异步访问 e.target 得到 null——17 移除这个优化，因为混淆大于收益）；**合成事件与原生混用顺序**——原生捕获监听在 React 合成分发之前（捕获阶段先于根的冒泡分发）。

收尾：答「是什么（包装+委托）→ 差在哪（拦截边界）→ 17 迁移的 why」，这题从八股变成理解题。

> 面试官追问点：为什么 17 把委托从 document 挪回根容器？应答思路：一是 document 是全局共享地盘（多个 React 实例/第三方库监听 document 会互相影响）；二是渐进升级场景下 v16/v17 混用时事件顺序错乱——「根容器自治」同时解决两个工程问题，这是答案的加分层。

#### 3.2.3 React状态管理怎么选？Context的陷阱是什么

答：一句话定调，**Context 的陷阱是「value 变化导致所有消费组件重渲染」——它传的是「渲染快照」不是「订阅」；选型的第一刀是「服务端状态与客户端状态分离」**。

**Context 的机制与陷阱**：Provider 的 value 每次 React 渲染都是新对象（字面量），**所有 useContext 消费者无条件重渲染**（不比较、不选择字段）——高频变化的值放 Context 就是全局重渲染。缓解：value 拆多个 Context、用 useMemo 稳 value、children 提升（jsx 属性不依赖 value 就不会被波及）——**但 Context 的定位是「低频全局依赖」（主题/语言/登录态），不是状态管理**。

**客户端状态三强**：**Zustand**——store 是 hook（useStore 选择器订阅，只订阅用到的字段，重渲染粒度最小），上手最快，中小项目默认选型；**Redux Toolkit**——单向数据流 + devtools 时间旅行 + 中间件生态，大团队协作规范首选；**MobX**——响应式依赖追踪（细粒度订阅），心智从 React 的「快照」切回 Vue 的「代理」，适合重表单重状态应用。

**第一刀：服务端状态与客户端状态分离**——服务器数据（列表/详情/缓存失效/重试去重）交给 **React Query（TanStack Query）**（缓存键 + staleTime + 请求去重 + 突变后失效），客户端只留「UI 状态 + 用户输入」——**大多数「状态爆炸」其实是把服务端状态错放进了客户端库**。

**深水区**：Zustand 选择器的相等比较陷阱（返回新对象要用 shallow 合并比较）；React Query 的 staleTime 与 gcTime 的语义差异（过期了还能先给旧值再后台刷）。

收尾：选型两句话——**先分离「服务端/客户端」两族状态；客户端库按「团队规模 × 订阅粒度需求」选**。

> 面试官追问点：Context 和 Redux 都能全局共享，本质差在哪？应答思路：Context 是「依赖注入 + 渲染扩散」（无订阅语义，value 一变全员重渲染）；Redux 是「store 外置 + 选择器订阅」（组件只订阅切片，store 更新不经过 React 渲染链）——「扩散 vs 订阅」是机制层的差异，答这个而不是答「Redux 有中间件」。

#### 3.2.4 React Router路由怎么设计？懒加载怎么配合

答：一句话定调，**React Router v6 的设计主线是「配置变组件、嵌套变 Outlet」——动态路由 useParams、嵌套路由 Outlet、守卫用 render-props 包装、懒加载用 React.lazy + Suspense 在路由边界收口**。

**动态与嵌套**：动态段 `path: "/user/:id"` 用 useParams 拿参；**嵌套路由用 <Outlet> 占位**——父路由的布局壳（导航/侧栏）不重渲染，子路由换内容——v6 相比 v5 最大的表达升级就是它，配路由的「组件树感」。

**守卫的实现**：没有 Vue Router 那样的官方守卫链——**包装组件模式**：<RequireAuth> 检查登录态，未登录 <Navigate to="/login" replace>；权限路由同构（<RequireRole role="admin">）——组合优于配置，守卫是可复用的包装组件。

**懒加载配合**：`const Page = React.lazy(() => import('./Page'))` + **路由级 <Suspense fallback={<Spinner/>}>**——Suspense 在路由边界兜住异步组件的加载态；深水区：**预加载策略**（hover 菜单项时提前触发 import，点击时已就绪）与手动分包的取舍；v6.4+ 的 loader（在渲染前取数，路由即数据边界）是进阶方向。

**深水区**：嵌套路由 + 懒加载的组合坑（Suspense 位置放错导致父布局一起闪烁——Suspense 要包在 Outlet 的最近边界）；路由集中配置与组件树声明两种风格（useRoutes 配置式更适合权限过滤）。

收尾：答题主链「动态参数 → Outlet 嵌套 → 包装式守卫 → lazy + Suspense 收口」——四步就是 v6 的全景。

> 面试官追问点：Suspense 的 fallback 会替换整个路由还是局部？应答思路：取决于 Suspense 的放置位置——包住整个 <App> 则全屏 fallback，包在 Outlet 边界则只有子路由区域闪 loading；「边界收敛到变化区域」是悬念设计的核心，也是这题真正想听的工程判断。

#### 3.2.5 Server Components是什么？边界在哪里

答：一句话定调，**Server Components 是「在服务端执行、零客户端 JS、序列化成 UI 协议流回浏览器」的组件形态——它划的不是「服务端/客户端」的地界，而是「哪段代码值得打包发给用户」的地界**。

**机制与边界**：RSC 在服务端执行完直接产出序列化描述流（不含任何 JS 发到客户端）——**RSC 不能有 state/effect/事件处理器**（没有 JS 运行时），交互逻辑全部下放给客户端组件（'use client' 标注）；**边界规则是单向的**：服务端组件可以 import 客户端组件（交互岛就是这么来的）；反过来客户端组件**不能直接 import 服务端组件**，只能通过 children/props 接收服务端渲染好的内容——「能嵌套、不能反向引用」。

**三件配套**：**Suspense 协调异步**——服务端组件取数时 Suspense 圈住 fallback，流式发送；**use() 的语义**——在组件内「等待」一个 promise 或读 context（比 await 更组件化的原语，取消语义随组件卸载自动回收）；**Actions（'use server'）**——表单的 action 直接指向服务端函数，渐进增强下 JS 未加载也能提交（HTML form 的原生行为）——**表单从「受控三件套」回归到「HTML 语义 + 服务端验证」**。

**深水区**：RSC 与 SSR 的关系是最高频追问——**SSR 是「首屏 HTML 快」（组件代码仍在客户端要注水），RSC 是「组件代码根本不进客户端」**；一个页面通常三层结构：RSC 壳（取数/布局）→ 客户端交互岛（表单/动画）→ SSR 首屏（把壳预渲染成 HTML）。

收尾：一句话「**RSC 的本质是给前端组件引入了新的执行环境维度——过去的维度是『哪个生命周期』，现在是『哪台机器』**」。

> 面试官追问点：RSC 数据获取和 SSR 页面里 useEffect 取数有什么本质区别？应答思路：effect 取数是「先渲染空壳 → JS 就绪 → 再取数 → 再渲染」（双次渲染 + 客户端瀑布）；RSC 在服务端把数据直接织进组件树，一次流式送达——**「数据在组件树生成之前就位」vs「树先生成再等数据」**，时序差是体验差的根源。

# 4.工程化与性能优化

### 4.1 构建工具链

#### 4.1.1 loader与plugin差在哪？构建流程怎么走

答：必问题。一句话定调，**loader 是「文件转换器」（单一输入输出、按 pipeline 串行），plugin 是「流程干预者」（监听全生命周期钩子做任意事）——loader 管「怎么编译一种文件」，plugin 管「构建过程的任何时刻」**。

**Webpack 构建三段流程**：初始化（合并配置、实例化 Compiler、挂插件）→ 编译（从 entry 递归 buildModule：**loaders 转换源 → parse 成 AST → 找依赖递归**，形成模块图）→ 输出（chunk 组合、模板渲染、seal 后写产物）——**plugin 的本质是 tap 进 Compiler 的几十个钩子**（compilation/emit/optimize 等），在流程的任意节点插逻辑。

**Tree Shaking 的原理与限制**：依赖 ESM 的**静态结构**（import/export 是编译期已知拓扑，require 是运行期动态）——「模块没被引用的导出」标记为 unused，压缩阶段删除；**限制三条**：CJS 包摇不掉（要有 ESM 版本）、有副作用的模块默认不敢删（package.json sideEffects 白名单告诉打包器「哪些纯」）、动态导入按需保留。

**深水区**：loader 的执行顺序是**从右到左、从下到上**（compose 而非 pipe，函数式的历史遗产）；pitch 阶段可以短路后续 loader。

收尾：HMR 的五步链路（监听 → 补丁 → WebSocket 推 hash → JSONP 拉补丁 → accept 替换）深度精讲见 8.8——这题答「一横（流程）一纵（loader/plugin 定位）」就完整。

> 面试官追问点：为什么 babel-loader 开 cache 后还要 exclude node_modules？应答思路：缓存解决的是「重复转换的成本」，exclude 解决的是「根本不该转换的范围」——node_modules 里 99% 是已编译产物（或按 browserslist 兼容目标不需要再转），排除一次胜过缓存一万次，「避免工作」永远优先于「加速工作」。

#### 4.1.2 Vite为什么这么快？和Webpack差在哪

答：一句话定调，**开发态的 Vite 是「不打包」——浏览器原生 ESM 按需请求一个模块才编译一个，冷启动从 O(整个项目) 变成 O(入口模块)；重活前置给 esbuild，生产构建换回 Rollup**。

**三段式**：一，**原生 ESM 按需编译**——`<script type="module">` 入口，中间件拦截请求现编译现返回，首屏只编译首屏用到的模块；二，**esbuild 预构建**——CJS 依赖转 ESM（Go 编写全并行，比 JS 写的 babel 快 10-100 倍）+ 零散小文件合并（lodash-es 几百个文件合成一个，减少 HTTP 次数），缓存按 lockfile 哈希存 node_modules/.vite；三，**HMR 沿 importers 向上找失效边界**——边界内热替换、边界外整页刷新，不是重新打包。

**和 Webpack 的差异一句话**：Webpack dev 也要全量构建 bundle（分钟级冷启动），Vite 把 bundle 工作推迟给浏览器——**「先全量后可用」vs「请求即编译」是两条路线的分水岭**。

**为什么生产换 Rollup**：dev 要「快」（不打包），生产要「体积和兼容」（tree-shaking 深度、代码分割、压缩）——Rollup 的 ESM 原生打包是老江湖；副作用是 **dev/prod 差异成为 Vite 的原罪**（极少数 bug 只在一边复现），`vite build --mode development` 提供一致性校验。

收尾：完整口述版（含追问首屏请求瀑布）见 8.4 深度精讲。

> 面试官追问点：原生 ESM 按需编译的代价是什么？应答思路：嵌套 import 的串行发现造成请求瀑布（深链路首屏请求更多），解法三件——预构建合并减少请求数、modulepreload 注入预加载、optimizeDeps.include 提前收编深依赖；能答「按需的代价是瀑布、预构建是对它的补偿」即到位。

#### 4.1.3 Babel的编译流程是什么？polyfill怎么配

答：一句话定调，**Babel 是「parse → transform → generate」三段流水线：字符串到 AST、visitor 模式改树、树回字符串——preset 是 plugin 的套餐，polyfill 与 transform-runtime 的差异是「补环境还是不污染全局」**。

**三段流水线**：@babel/parser 生成 AST → @babel/traverse 按 visitor（进入/退出节点）跑 transform 插件 → @babel/generator 输出代码 + sourcemap。**preset 与 plugin 的顺序**：plugin 先于 preset、**同组内从前往后**（preset 倒序）——为什么箭头函数插件在前面（先转语法才能让后续插件处理目标结构）。

**polyfill 两种方案的差异**：@babel/preset-env + useBuiltIns: 'entry'——全量 import core-js，按 browserslist 不裁剪（污染全局，重复引入）；**transform-runtime**——检测到用到的特性按需**以局部变量形式注入**（Promise → _Promise），不污染全局、**helper 函数复用不重复打包**——库开发必用（库不该污染宿主全局），应用开发可直接 core-js 全量 + 按需引入。

**browserslist 的作用**：它是「目标环境的单一事实源」——preset-env 按 targets 决定转哪些语法（新 Chrome 不转箭头函数）、postcss/autoprefixer 按它决定加哪些前缀——**一处配置三处受益**（转译、polyfill、CSS 前缀），写在 package.json 或 .browserslistrc。

**深水区**：语法糖（箭头函数、可选链）vs API（Promise、Array.includes）是两类问题——**语法可转译、API 只能补实现**，preset-env 管「转」，core-js 管「补」，混淆这两层是 polyfill 配错的根源。

收尾：答题主链「三段流水线 → plugin/preset 顺序 → 语法转译 vs API 补实现」——最后一组对比是把配置题答成原理题的关键。

> 面试官追问点：为什么库必须用 transform-runtime 而应用可以用全量 polyfill？应答思路：应用是最终环境的主人（污染的是自己，可控）；库的代码跑在宿主环境里——注入全局 Promise 相当于篡改宿主，且多个库各自污染互相打架——「局部注入 + helper 去重」是库的礼貌，也是 npm 生态的共存协议。

#### 4.1.4 Monorepo方案怎么选？pnpm的原理是什么

答：一句话定调，**pnpm 的核心是「内容寻址存储 + 符号链接」——全局 store 存所有包版本、node_modules 里只放链接，根治 npm 扁平化的幽灵依赖；Monorepo 的选型看「任务编排需不需要远程缓存」**。

**pnpm 三层结构**：全局 store（~/.pnpm-store，按内容哈希存文件，**磁盘上每个包版本只存一份**）→ 虚拟 store（node_modules/.pnpm 里每个包版本的硬链接）→ 项目 node_modules（**直接依赖的符号链接**，不在顶层直接可见）。**依赖访问的严格性**：只有 package.json 声明的依赖能被 require——未声明的「借来的」依赖（幽灵依赖）直接报错，**把隐式依赖从运行时错误前移到安装期**。

**npm/yarn 扁平化的病**：提升（hoisting）把所有依赖平铺到顶层——包能用没声明的依赖（上线换包管理器/依赖树变化就崩）、同名包重复时提升结果不确定。

**Monorepo 任务的编排**：pnpm workspace（协议 workspace:* 本地包引用，不发 npm 就能用）+ **Turborepo/Nx 的任务编排与缓存**——拓扑序并行（turbo run build 时 utils 先于 app）、**任务输出按输入哈希缓存**（命中跳过整段构建）——大仓提速一个数量级；远程缓存让 CI 和全组共享命中。

**取舍**：multirepo 适合「边界清晰、独立发布、团队分散」；monorepo 换来的是**原子跨库提交、统一版本策略、代码共享零成本**，代价是仓库体积、CI 复杂度和权限粒度（CODEOWNERS 治理）。

收尾：答题主线「pnpm 的链接结构解决什么病 → 任务缓存解决什么慢 → monorepo 的收益对照代价」。

> 面试官追问点：为什么 pnpm 用符号链接而不是全部硬链接？应答思路：node_modules 顶层需要「包目录」的语义（package.json 可读、peer 解析正确），符号链接保持目录结构；硬链接用于 store 到 .pnpm 的文件层（同盘零拷贝）——**目录语义用软链、文件存储用硬链**，两层各司其职，答出这个分工就是读源码级理解。

#### 4.1.5 工程规范怎么落地？lint到CI的链路是什么

答：一句话定调，**规范落地的链路是「编辑时警告 → 提交时拦截 → 流水线卡点」三层漏斗，每层各司其职：编辑器管体验、git hook 管本地最后一道、CI 管不可绕过的强制**。

**ESLint 与 Prettier 的分工**：ESLint 管「代码质量与潜在问题」（no-unused-vars、no-implicit-globals），Prettier 管「格式风格」（缩进/换行/引号）——重叠区用 eslint-config-prettier 关掉 ESLint 的格式规则（避免两套规则打架）；**风格之争的解法不是讨论而是格式化自动化**（保存即格式化 + lint-staged 提交时兜底）。

**提交链三件套**：**husky**——把 git hook 变成项目内可共享的配置（.husky 目录）；**lint-staged**——只对暂存区文件跑 lint/format（全仓 lint 在大项目里是分钟级，增量是唯一可用的粒度）；**commitlint**——提交信息按 Conventional Commits 校验（feat/fix/chore + scope），**它是后面一切自动化的数据源**（生成 changelog、语义化版本推断都读 commit message）。

**CI 流水线的卡点设计**：lint → type check → test → build → deploy 的顺序按「反馈速度 + 失败概率」排（快的先卡）；**CI 的存在意义是「不可绕过」**——本地 hook 可以 --no-verify 跳过，CI 不能——所以「规范是否真的落地」的唯一判据是 CI 有没有同名卡点。

**深水区**：规则迁移策略——新规则只对新代码生效（ESLint 的 overrides 按 git blame 过滤、或用 rule 管理工具），避免「一条新规则两千个报错」导致规则被搁置；**规范上线比规则完美更重要**。

收尾：一句话——**规范不是文档，是「能拦截的流水线」；没有 CI 卡点的规范等于不存在**。

> 面试官追问点：lint-staged 为什么不直接全量 lint？应答思路：全量 lint 的耗时随仓库线性增长（分钟级），对提交节奏是灾难；暂存区是「这次提交实际会改变的内容」——校验粒度和提交粒度对齐，既快又准；全量 lint 挪到 CI 定期跑（或仅对 diff 跑），「快慢分层」是工程化的通用思路。

### 4.2 性能优化与监控

#### 4.2.1 打包体积优化怎么做？代码分割原理是什么

答：一句话定调，**体积优化的主刀是「代码分割」——把「一个 bundle 全量加载」改成「按路由/按交互切分按需到达」，分析、分割、压缩三板斧**。

**代码分割的原理**：**静态 import 是打包器的依赖图边**（必须进主包），**动态 import() 是运行时才解析的切分点**——打包器把它独立成 chunk + 生成加载器；路由级分割（React.lazy / Vue 异步组件）是它的最常见应用——**首屏 JS 从「全量」砍到「当前路由」**；splitChunks 把公共依赖（多入口共享的 vendor）抽公共包，防重复打包。

**体积分析三步**：webpack-bundle-analyzer（产物可视化，揪「意外引入的大依赖」——一个 lodash 整包 70KB 的经典事故）→ 按需引入（lodash-es 按模块、组件库 babel-plugin 按需）→ 确认 ESM 版本（Tree Shaking 的前提，见 4.1.1）。

**传输优化**：**gzip/brotli 压缩**（brotli 再小 15%-20%，静态资源预压缩 + CDN 边缘解压）、**CDN 就近 + 边缘缓存**（DNS 直达边缘节点）、**preload 当前路由的关键资源**（font/CSS），prefetch 预取下个路由（优先级语义完全不同，见 8.5）。

**深水区**：分割粒度的权衡——chunk 过碎导致请求瀑布（HTTP/2 缓解但不消除）；**魔法注释 /* webpackChunkName */ 与手动分包**的控制粒度；现代打包器的「依赖预构建」与分割的关系（Vite dev 的预构建是「合并小文件」，分割是「切开大文件」，方向相反各治一病）。

收尾：三板斧的顺序背下来——**先分析（找意外）再分割（按路由）后压缩（省传输）**，没分析直接分割是盲盒优化。

> 面试官追问点：splitChunks 的 chunks: 'all' 和默认 'async' 差在哪？应答思路：async 只分割动态导入的共享依赖（首屏 bundle 可能重复打包共享代码），all 把首入口的公共依赖也抽出来——收益是去重、代价是「首屏多一次公共包请求」，按「公共代码占比」决策；能答出这个 trade-off 说明不是背配置。

#### 4.2.2 首屏加载优化怎么做？SSR和SSG如何选型

答：必问题。一句话定调，**首屏优化按「网络传输、资源解析、渲染路径」三层做减法，度量口径 LCP 定靶心；SSR/SSG 的选型按「数据变化频率 × 个性化程度」选渲染时机**。

**三层减法**：网络层——HTTP/2 多路复用、brotli、CDN、preconnect/preload/prefetch 的优先级语义；资源层——**路由级代码分割**（首屏 JS 只含当前路由）、**关键 CSS 内联**（首屏样式直接 style 进 HTML 省一次往返）、图片 webp/avif + srcset + 懒加载（**但 LCP 主图要 preload + fetchpriority=high，懒加载会误伤**）；渲染层——**骨架屏占位真实布局**（防 CLS 抖动，感知性能好于白屏和 spinner）。

**SSR/SSG/预渲染的选型**：**SSR**——服务端执行组件出 HTML（首字节即可渲染，代价是 TTFB 变长 + 要保活 Node 服务 + hydration 成本）；**SSG**——构建期出静态 HTML（TTFB 极短，CDN 全缓存，适合内容不变的路由）；**预渲染**——构建期把 CSR 页面无头浏览器跑一遍存 HTML（SEO 快速补救，不用改架构）；**按「数据变化频率 × 个性化程度」选**——静态内容 SSG、动态但结构稳定用 ISR（过期后台再生成）、强个性化 SSR、纯后台 CSR。

**深水区**：hydration 的成本常被低估——**客户端注水要把整棵组件树重新执行一遍**（「首屏快但可交互慢」是 SSR 的原生矛盾），React18 的流式 SSR + 选择性注水把代价分期。

收尾：心法一句——**每层做减法：请求少一个、体积小一号、渲染早一步**；完整体系化方案见 8.5 深度精讲。

> 面试官追问点：为什么用了 SSR 还要做代码分割？应答思路：SSR 解决「首字节到可看的 HTML」，分割解决「JS 到达的可交互时间」——注水需要客户端组件代码，不分割就是「整棵树的 JS 都要下载完才能注水」，两刀砍在不同链路段，不是替代关系。

#### 4.2.3 Core Web Vitals是什么？三大指标怎么优化

答：一句话定调，**三大 Vitals 各押一个用户体验维度——LCP 押「主要内容何时可见」、INP 押「交互是否及时」、CLS 押「布局是否稳定」，全部是真实用户指标（RUM），优化手段各有一条主刀**。

**LCP（Largest Contentful Paint，≤2.5s）**：视口内最大元素（主图/大标题块）的渲染完成点——优化主刀是「**提前 + 减小**」：preload + fetchpriority、CDN/预连接压 TTFB、图片格式与尺寸、SSR/SSG 直接出 HTML、去掉阻塞渲染的同步脚本。

**INP（Interaction to Next Paint，≤200ms）**：取代 FID 的「全程交互响应」指标（取所有交互的最差分位）——FID 只测「首帧延迟」（输入到主线程空闲），INP 测「输入到下一帧绘制」的完整链路。优化主刀是「**让主线程有空**」：拆长任务（scheduler.yield 主动让权、把大计算切片分帧）、减少重渲染、事件处理器瘦身、避免同步布局。

**CLS（Cumulative Layout Shift，≤0.1）**：意外布局位移的累计分——**「意外」是关键词，用户点击引起的位移不算**。优化主刀是「**占位**」：图片视频显式 width/height（或 aspect-ratio）、字体 swap 期间用 size-adjust 占位、动态内容插入前预留空间、骨架屏。

**周边指标与工具**：FCP/TTI 的辅助定位作用（FCP 慢在资源、TTI 慢在长任务）；**性能预算（budget）**——把指标变成「CI 卡点」（包体积超 200KB 直接红）；Lighthouse 是实验室数据（Lab）的代表，**现场数据（Field/RUM）才是 Vitals 的判定口径**——两套数据差异本身就是排查线索（实验室环境测不出弱网用户的 INP）。

收尾：一句口诀「**LCP 管可见、INP 管跟手、CLS 管不跳**」——三个维度分别对应资源、主线程、布局三把刀。

> 面试官追问点：为什么 FID 被淘汰换成 INP？应答思路：FID 只测第一次交互的「输入延迟」（到主线程接上为止），漏掉处理和渲染阶段的卡顿；INP 覆盖全部交互的完整链路（输入→处理→绘制）并取最差分位——「抽样一次」升级「全程最差」，更能反映真实体验。

#### 4.2.4 前端性能监控怎么做？错误上报方案怎么设计

答：一句话定调，**监控是「采集（指标/错误/行为）→ 上报（不丢不卡）→ 还原（定位到代码行）」的闭环——采集用浏览器原生观察者，上报的核心约束是「页面随时会死」**。

**指标采集**：PerformanceObserver 订阅 LCP/CLS/longtask（被动回调不阻塞）；**web-vitals 官方库**封装好边界处理（LCP 在首次输入后停止计分等）；FPS 用 rAF 差值法（连续帧间隔超过阈值计数掉帧）。

**错误捕获的四张网**：window.onerror（同步 JS 错误，含行列号）、**unhandledrejection（Promise 未捕获 rejection——最常漏的一张）**、资源错误（error 事件的捕获阶段冒泡不上去，要在 window 上 addEventListener(..., true)）、框架层（Vue errorHandler / React ErrorBoundary 兜 UI 崩溃）。

**SourceMap 还原**：产物上传 CDN 时**把 map 文件传到监控平台而不发布到线上**（防源码泄漏），上报行列号 → 服务端用 map 反解出源码位置——「错误堆栈里的 minified 位置」到「commit 里的具体行」全靠它。

**上报的深水区**：**sendBeacon** 是页面卸载时的正解（异步且不阻塞卸载，浏览器保证发出）；fetch keepalive 是它的替代（带响应语义）；普通 unload 里发 XHR 会丢（页面一死请求取消）——**「页面死亡前的最后一份报告」是这个子题的灵魂**；采样与批量（错误聚合去重 + 按指纹抽样）防止上报本身把服务打爆。

收尾：闭环句——**采集要全（四张网）、上报要活（beacon）、还原要准（SourceMap）**，三者缺一就是「有监控但没用」。

> 面试官追问点：为什么 unload 里的 fetch 会丢而 sendBeacon 不会？应答思路：unload 后页面进入销毁，普通请求随时被浏览器取消；sendBeacon 是「交给浏览器进程的移交」——请求脱离页面生命周期，页面死了也继续发——**把请求的所有权从页面移交给浏览器**就是它存在的理由；fetch keepalive 是它的替代（带响应语义）。

### 4.3 微前端

#### 4.3.1 微前端解决什么问题？qiankun沙箱怎么实现

答：一句话定调，**微前端解决的是「巨石应用的拆分与共存」——多团队多技术栈同住一个页面；qiankun 用沙箱解决「window 争抢」，核心机制是「读共享、写隔离」的 Proxy 代理**。

**为什么需要微前端**：巨石应用拆分（十万行级代码库的发布耦合——改一行全量回归）、技术栈渐进迁移（老 Angular 新 React 共存）、**独立部署是硬需求**（子应用独立仓库独立流水线独立发版）——如果不需要「独立部署」，组件库就够了，这是微前端的入场券。

**沙箱两代**：**SnapshotSandbox**——激活时拍 window 快照、失活时 diff 还原（卸载时还原现场的朴素方案），缺陷是不支持多实例 + diff 性能差；**ProxySandbox**——每个子应用一个 Proxy 代理 fakeWindow，代码跑在 with(fakeWindow) 里——**get 先查自己、没有才透传真 window（读共享）；set 一律写进自己的（写隔离）**——多实例并存的根基。

**配套三件套**：**样式隔离**——默认 dynamic style 运行时改写，strictStyleIsolation 用 Shadow DOM（弹窗挂 body 就逃出 shadow，「UI 穿透」是它的代价）；**路由隔离**——activeRule 匹配 + 子应用路由库 patch（pushState 劫持通知主应用）；**应用通信**——initGlobalState 是主应用持有的 observable store。

**深水区**：iframe 的对照——隔离最彻底但「双份上下文（内存×N）、路由手动同步、弹窗坐标、postMessage 序列化」的集成成本高；**qiankun 的 JS 沙箱是「iframe 的隔离收益减去集成成本」的折中**。

收尾：完整口述（含 Proxy 读写不对称的细节）见 8.9 深度精讲；答题主链「解决什么（独立部署）→ 靠什么（沙箱）→ 配什么（三件套）」。

> 面试官追问点：新框架为什么不直接用 iframe？应答思路：iframe 的隔离是「全有」，但通信成本、白屏成本、布局成本全是「全无」——Shadow DOM 的样式穿透、postMessage 的序列化税、双份 CSS/JS 的内存，在「高频通信 + 统一 UX」的业务里不可接受；微前端的演进史就是「隔离强度换集成体验」的取舍史。

# 5.Node.js与SSR

#### 5.1 Node事件循环和浏览器差异？六个阶段是什么

答：一句话定调，**浏览器事件循环是「一个宏任务 + 排干微任务」的两段模型，Node 是 libuv 驱动的「六阶段轮询」——timers、pending、poll、check、close 五个有活干的阶段绕圈跑，微任务夹在阶段之间和 nextTick 队列排干**。

**六个阶段**：timers（到期的 setTimeout/setInterval 回调）→ pending callbacks（系统级延迟错误）→ **poll（取新 IO 事件，执行 IO 回调；没活干时会算下一次 timer 的等待时间）** → check（setImmediate 回调）→ close callbacks（socket 关闭等）；idle/prepare 是内部轮空位。**poll 阶段是灵魂**：队列为空且有 setImmediate 时跳去 check、有到期 timer 时跳回 timers、都没有就阻塞等待。

**与浏览器的三处差异**：一，**微任务的排空时机**——浏览器在「每个宏任务后」，Node 在「**每个阶段之间**」（以及每个宏任务后）——一个阶段里跑十个 IO 回调，中间不夹微任务的话会连续跑完（新版 Node 已向浏览器对齐到「每个回调后」）；二，**setImmediate/setTimeout(0) 的顺序不确定**（取决于进入循环的位置——IO 周期里 immediate 先、主模块直接调用则看 timer 就绪时机）；三，**process.nextTick 是独立优先队列**——排在所有微任务之前，递归 nextTick 能饿死事件循环（这是它的滥用警告）。

**深水区**：nextTick 与 queueMicrotask 的正确选择——nextTick 是「当前操作完成后立即执行」（能赶在任何 IO 之前），微任务是「promise 语义的对齐」；框架解耦内部阶段用 nextTick、用户代码等微任务。

收尾：答题主链「六阶段绕圈 → poll 的调度逻辑 → 与浏览器的三个差异」，nextTick 的饿死警告是加分收尾。

> 面试官追问点：为什么 nextTick 会饿死事件循环而微任务不会？应答思路：nextTick 回调里再调 nextTick 会向同一个队列追加——队列永远排不完，循环进不到下一阶段；微任务虽然也全排，但 promise 语义天然「不再追加自身」，递归微任务要靠 await 让步——**「队列自追加」是饿死的结构性原因**。

#### 5.2 Node的模块机制是什么？幽灵依赖怎么解决

答：一句话定调，**Node 的模块史是「CJS 同步 require 与 ESM 静态 import 的共存史」——幽灵依赖是 npm 扁平化的病，pnpm 用「链接结构 + 严格访问」根治**。

**CJS 与 ESM 的共存与互操作**：CJS 是运行时同步加载（require 返回 module.exports，值拷贝）；ESM 是编译期静态结构（import/export 是拓扑，**live binding**——导出变了导入方看得到）。**互操作的不对称**：ESM 可以 import CJS（default 具名映射靠猜测 heuristics），**CJS 不能 require ESM**（异步语义塞不进同步函数）——传统解法是动态 import()；新版 Node（22+）已实验性支持 require ESM，但仅限「可同步加载的模块图」，异步边界依然进不来。package.json 的 type 字段决定 .js 按哪套解析。

**扁平化与幽灵依赖**：npm/yarn 把所有依赖**提升**到 node_modules 顶层——require 的解析规则是「逐级向上找」，于是**没声明的包也能 require 到（借来的）**——依赖树的偶然结构成了运行时的隐形契约：上游某天修掉提升，你的构建就崩；同包多版本提升谁看运气，**「能跑」依赖的是偶然性**。

**pnpm 的根治**：.pnpm 里按「包名@版本」存每个版本的完整链接结构，**顶层只有 package.json 声明过的直接依赖的符号链接**——未声明的依赖 require 直接报错——**把幽灵依赖从「上线后随机爆炸」前移到「安装期确定性报错」**。

收尾：答题主链「两种模块的差异 → 提升的病 → 链接的药」；pnpm 细节在 4.1.4 已深讲，这里点「严格访问」即可。

> 面试官追问点：live binding 到底解决什么问题？应答思路：CJS 的导出是「加载时刻的值拷贝」，循环依赖时先拿到未完成的对象；ESM 的 binding 是「指向同一变量槽的引用」，循环引用的模块能看到对方后续的赋值——**循环依赖的可预测性**是 live binding 的设计动机，也是「为什么 ESM 是静态的」的答案。

#### 5.3 Express和Koa差在哪？Nest的IoC是什么

答：一句话定调，**Express 是「线性回调数组」——next 一路往下走不回头；Koa 是「洋葱圈」——await 之后的代码在响应路上逆序再跑一遍；Nest 用 IoC 把「对象的组装」从业务代码里没收**。

**两种中间件模型**：Express——app.use 压入数组，next() 调下一个，**响应路径不复用**（想统一处理后置逻辑要手动再挂一个中间件）；Koa——**async/await 后的代码是「响应的一半」**（计时、错误兜底、响应头统一修改都在 await next() 之后）——顺带解决「async 中间件的错误处理」：洋葱外层 try/catch 能接住任何内层的 reject（Express 4 的同步签名接不到 async 错误，要手动 next(err)）。

**Nest 的 IoC**：控制反转——**类的依赖不再自己 new，而是声明（constructor 注入）+ 容器按依赖图装配**——好处是「依赖可替换」（Controller 依赖 Service 接口，测试换 mock、换实现不动业务）+ 「生命周期统一托管」（单例、作用域、销毁钩子）；Module/Provider/Inject 的装饰器体系只是这套思想的语法；**AOP 是它的第二层红利**（拦截器/管道/守卫按切面织入）。

**深水区**：Express 5 才原生支持 async 错误捕获（这个时间差本身就是 Koa 存在的理由）；Koa 的「context 一对象贯穿」与 Express 的「req/res 双对象」的心智差异。

收尾：三家的分水岭一句话——**Express 是路由器的年代产物、Koa 是 async 原生的一代、Nest 是架构约束的一代**，选型按「要库还是要框架」。

> 面试官追问点：洋葱圈模型里中间件的执行顺序？应答思路：注册序进、逆序出——A 注册先于 B：A 前半 → B 前半 → 最内层逻辑 → B 后半（await next() 之后的代码）→ A 后半；「请求路上一圈、响应路上一圈」，画得出这个图就到位。

#### 5.4 Stream和Buffer怎么理解？背压问题怎么处理

答：一句话定调，**Buffer 是「二进制数据的容器」，Stream 是「数据的移动方式」——背压是「生产快于消费」的缓冲危机，解法是尊重 highWaterMark 的返回信号**。

**Buffer 的内存分配**：堆外内存（C++ 层申请）——小块从 8KB 的内存池里切（避免频繁系统调用的池化设计），**超过池一半（约 4KB）的分配绕过池直接独立申请**；Buffer.alloc vs allocUnsafe（unsafe 不清零更快但可能残留旧数据——安全敏感场景必须 alloc）。

**Stream 的四种类型**：Readable（可读）、Writable（可写）、Duplex（双向，如 TCP socket）、Transform（转换管道，如加密/压缩——**输入输出是同一条加工流水线**）。

**背压（Backpressure）**：可读流每秒产 100MB、可写流（慢速网络）每秒消费 1MB——**不处理就全缓冲在内存里直到 OOM**。机制：write() 返回 false 表示「内部缓冲超了 highWaterMark」——**正确姿势是暂停读取、等 drain 事件再继续**；**pipe() 内置了这套暂停-恢复逻辑**（这就是「能用 pipe 就别手写循环」的原因）；深水区：pipeline()（自动错误传播 + 清理，替代 pipe 的现代 API）与手写 async iterator（for await...of 天然尊重背压）。

**大文件处理的流式方案**：HTTP 下载大文件——createReadStream + pipe 到响应（不整体读入内存，**内存占用从文件大小降到 chunk 大小**）；上传的分片接收（formidable/busboy 也是流式解析 multipart）。

收尾：答题主链「Buffer 装数据 → Stream 移数据 → 背压管速度」——write 返回 false 必须停，是这题的纪律性收尾。

> 面试官追问点：highWaterMark 设大设小各有什么代价？应答思路：小值——暂停恢复频繁（吞吐下降）；大值——缓冲内存占用高（延迟回压感知，内存峰值大）；**它是「吞吐 vs 内存」的旋钮**，默认 16KB 的取值就是两端的中间点——答出 trade-off 的性质比记住数字重要。

#### 5.5 Node进程管理怎么做？cluster原理是什么

答：一句话定调，**cluster 的原理是「主进程创建监听 socket、worker 共享端口句柄、操作系统轮询分发连接」——多核利用不是靠多进程自己实现的，是靠「端口复用 + 内核调度」白送的**。

**cluster 机制**：fork 出的 worker 通过 IPC 从主进程拿到 **server handle 的引用**（不是各自 listen，是**共享同一个句柄**），新连接由操作系统**轮询（Round-Robin，非 Windows）分给空闲 worker**——注意分发的是「连接」不是「请求」（长连接场景会负载不均，keep-alive 高的连接黏住 worker）。

**pm2 的增值**：负载均衡（cluster 模式）、**守护与重启策略**（异常退出自动拉起、max_memory_restart 内存阈值重启）、日志聚合、零停机 reload（**reload 逐个重启、graceful 等连接排空**——fork 之间还是有毫秒级的服务窗口）。

**worker_threads vs child_process**：child_process——独立进程（独立 V8 实例，通信走 IPC 序列化，**适合隔离型任务**：跑不信任的脚本、可崩溃的子任务）；worker_threads——**同一进程内的真线程**（共享进程内存，MessageChannel 通信 + **SharedArrayBuffer 可零拷贝共享**，适合 CPU 密集的计算）；**「计算共享内存用 threads、任务隔离用 process」**。

**深水区**：Node 的单线程指「JS 执行线程」，**IO 本身一直是多线程的**（libuv 线程池）——所以「Node 单线程慢」的批评只对 CPU 密集成立；cluster 的 worker 数不必然等于核数（内存密集型应用要按内存预算算）。

收尾：主链「句柄共享 → 连接分发 → pm2 托管 → 线程/进程选型」——最后补「IO 多线程」的事实修正就是深水区。

> 面试官追问点：为什么 cluster 分发连接而不是分发请求？应答思路：分发粒度在传输层（OS 只认 socket）——Node 无法把 HTTP 请求从连接里拆出来再转发；后果是 keep-alive 长连接的所有请求黏在同一个 worker——高并发的现代 HTTP（默认长连接）会显著不均，这是很多人「上了 cluster 依然有的核忙死有的核闲死」的根源。

#### 5.6 SSR同构渲染原理是什么？注水的坑有哪些

答：一句话定调，**同构 = 同一份组件代码跑两遍：服务端 renderToString 出首屏 HTML，客户端 hydrate 复用 DOM 重建组件树——「快的是表象，注水的成本是代价」**。

**两阶段**：render——服务端执行组件（**只跑 render 相关生命周期**，window/document 不可用的原因就是 Node 里没它们，`typeof window !== 'undefined'` 是双端分支守卫），HTML 里嵌序列化初始数据（window.__INITIAL_STATE__）；hydrate——客户端 JS 就绪后**不重新创建 DOM，而是「遍历现有 DOM 建组件树、绑事件、还原 state」**，hydration mismatch（双端渲染不一致：时间戳/随机数/UA 判断）会警告。

**注水的四个坑**：一，**整树同步注水**——大树注水期间主线程占满（可交互时间被推迟），「首屏快但可交互慢」是 SSR 的原生矛盾；二，**双端数据不一致的 mismatch**——根因治法是「双端同源数据保证确定性渲染」；三，**内存泄漏**——服务端是长驻进程，「组件级的状态当成页面级使用」（全局单例、事件监听不清理）会随请求累积——**服务端要像写库一样写组件**；四，window/document 直用——用 onMounted/useEffect 包裹或 typeof 守卫。

**框架实现思路**：Nuxt/Next 把「路由 → 数据 → 渲染 → 注水」做成约定（getServerSideProps/getServerData 的数据注入点 + hydrateRoot/hydrate）——框架的价值是把坑变成约定。

**深水区**：React18 流式 SSR + 选择性注水把注水成本分期（边渲染边 flush、优先注水用户正在交互的边界）。

收尾：主线一句「**HTML 快是表象、注水慢是代价、流式与选择性注水是把代价分期**」——完整版（含 SSR/SSG/ISR 选型）见 8.10 深度精讲。

> 面试官追问点：为什么 SSR 要小心模块级（单例）状态？应答思路：浏览器里单例属于「一个用户」，服务端进程服务所有用户——模块级单例在并发请求间共享，A 用户的数据泄漏给 B（经典生产事故）；解法是「每个请求新建 store 实例」（app.createContext/requestId 关联）——**「代码同构、状态不能同构」**是这句口诀的全部。

# 6.跨端与小程序

#### 6.1 小程序为什么设计双线程？通信序列化开销在哪

答：必问题。一句话定调，**双线程是「管控换性能」的设计——逻辑层跑 JS、渲染层跑 WebView，中间隔着一层序列化桥；牺牲通信效率换来「代码碰不到 DOM、页面可控可审计」**。

**为什么双线程**：浏览器里 JS 与渲染共用主线程，互相能直接操作 DOM——小程序的诉求是**管控**（开发者代码不能随意操作页面、劫持支付流程、注入恶意脚本），所以**逻辑层（JsCore，无 DOM/BOM）与渲染层（WebView）物理隔离**——代码「想改页面只能通过官方的 setData 接口」，官方成为唯一通道，天然可审计、可控降级。

**通信的序列化开销**：逻辑层与渲染层是两个环境，**setData 的数据必须序列化成字符串跨线传输**（JSON 序列化 + bridge 分发）——这是「setData 不能传大对象/不能传函数」的根本原因；**频繁 setData 是小程序卡顿第一来源**——每次通信都是「序列化 + 桥 + 反序列化 + 重渲染」，数据量大时（长列表全量刷新）单次可达几十毫秒。优化三板斧：**数据最小化（只传变化字段）、频率节流（合并一次传输）、路径更新**（`this.setData({'list[2].checked': true})` 局部更新不传全列表）。

**深水区**：Skyline 渲染引擎——放弃 WebView 改自绘渲染管线（逻辑层与渲染层合并调度），绕开 WebView 的兼容性税和 DOM 排版开销，这是「双线程税」被官方承认后的演进方向；WXS 就是「在渲染层跑代码减少跨线通信」的补丁（见 6.3）。

收尾：答题主链「为什么分（管控）→ 代价是什么（序列化桥）→ 怎么补（setData 纪律 + Skyline）」。

> 面试官追问点：为什么不直接用 Web Worker 那样的多线程？应答思路：Worker 依然是「同一页面的代码」，宿主对 Worker 的管控与对主线程无差别；小程序的分线程是「不同进程容器」（逻辑层独立 JsCore、渲染层独立 WebView），**隔离的目的是安全边界而不是计算并行**——Worker 求性能、双线程求管控，出发点不同。

#### 6.2 Taro和uni-app怎么选？编译时运行时差在哪

答：一句话定调，**跨端框架的两大流派是「编译时」（把你的代码翻译成各端原生代码，性能好但受约束）与「运行时」（在各端跑一个 JS 解释器执行你的代码，自由但开销大）——Taro 是编译时起步、补运行时，uni-app 是编译时为主、条件编译特色**。

**编译时**：模板/组件在构建期静态翻译——Taro 早期把 JSX 递归转成各端模板（**静态分析的限制：动态结构、复杂表达式翻译不了**，所以 Taro3 引入运行时补全表达力）；**运行时**：小程序里跑一个「DOM 的 JS 模拟层」（Taro3 的 template + data 驱动模拟 DOM，react-reconciler 挂在模拟 DOM 上）——任意 React 代码都能跑，**代价是模拟层本身的体积和 setData 次数**。

**uni-app 的特色是条件编译**：`#ifdef mp-weixin` 按平台裁剪代码——一码多端但「端差异显式写在代码里」，与 Taro 的「编译时尽量抹平、抹不平才运行时」是两种工程哲学。

**选型考量三行**：团队技术栈（React 系 Taro、Vue 系 uni-app）；性能预算（编译时产物更贴近原生、运行时有模拟层税）；生态（uni-app 的插件市场和 HBuilderX 工具链 vs Taro 的开源生态与 React 生态亲和）。

**深水区**：remax 的运行时方案——「Reconciler 直接对接小程序渲染层」把运行时流派做到极致（真实 DOM 树映射成小程序节点树，reconciler 驱动 setData），是理解「运行时流派到底在模拟什么」的最佳教材。

收尾：判断题——**看一段跨端代码，能指出哪些部分编译时消掉了、哪些落进运行时**，选型就不再是背参数。

> 面试官追问点：运行时方案为什么必然有性能下限？应答思路：模拟 DOM 层每次 diff 的结果都要经 setData 序列化跨线（双线程的桥，见 6.1）——真实 DOM 是进程内指针操作、模拟 DOM 是跨进程序列化，**这个税来自架构层（小程序双线程）而不是框架层**，运行时框架只是把税从「编译期躲不开」变成「可以精细优化」。

#### 6.3 WXS为什么执行快？分包加载的机制是什么

答：一句话定调，**WXS 快是因为它跑在渲染层线程——不跨桥、不用序列化、直接联动渲染；分包是把「整个小程序」的体积约束拆成「按需加载的单元」**。

**WXS 为什么快**：页面数据驱动的计算（格式化、过滤、联动动画）如果写在 JS（逻辑层），**每次数据变化都要跨线一次**（逻辑层算完 setData 回渲染层）；WXS 在**渲染层线程**执行（WebView 里的一等公民），事件回调里直接改数据、渲染层**当场重渲染，全程不跨线**——「高频交互 + 轻计算」场景（拖尾、惯性滚动、表单联动校验）是它的主场。限制：**不是 JS 完整运行环境**（无 DOM API 子集、语法受限、不能异步）。

**分包加载**：主包放「启动必须」（tabBar 页面 + 公共资源），分包是「独立的功能域」（按业务线拆）——**用户进哪个业务才下载哪个包**（首包体积从全量降到主包，下载耗时同步下降）；独立分包更进一步——**不依赖主包可独立运行**（扫码直达的活动页，冷启动不用等主包）；**分包预下载**——进入某页面时提前拉即将用到的分包（配置 rules，把「用户可能去哪」的预测变成下载指令）。

**深水区**：主包与分包的共享代码（公共组件放哪——放主包会被所有用户下载、放分包间要重复；-commonSharedChunk/公共分包策略）；分包后路由跳转的体积审计（跳转前检查目标包是否就绪）。

收尾：两件事一条线——**都在给「双线程 + 体积」还债：WXS 还通信税、分包装体积税**。

> 面试官追问点：WXS 能发请求或调 wx API 吗？应答思路：不能——渲染层线程没有 wx.request 这类逻辑层 API（能力在逻辑层注册），WXS 只做「纯计算 + 改视图」；**它快的本质就是「没有能力、所以不用跨线」**，能力与性能在这里是同一枚硬币。

#### 6.4 JSBridge的原理是什么？H5和原生怎么通信

答：一句话定调，**JSBridge 是「给 WebView 里的 JS 开一条调用原生能力的通道」——上行两条路（URL 拦截、注入 API），下行一条路（evaluateJavascript），通信的封装层是「协议 + 任务队列」**。

**上行（JS 调原生）两条路**：**URL scheme 拦截**——iframe 发自定义协议（`jsbridge://method?params`），原生拦截 shouldOverrideUrlLoading 解析分发（兼容性最好、所有 WebView 都可用）；**注入 API**——addJavascriptInterface（Android）/ messageHandlers（iOS）直接把原生对象注入 window（类型安全、无序列化 hack，但有版本兼容与安全历史问题，Android 4.2 前的反射漏洞是著名事故）。

**下行（原生调 JS）**：evaluateJavascript——原生主动执行一段 JS 字符串（页面环境里 eval），回调就靠它（JS 发请求时带 callbackId，原生处理完 evaluate 回调 JS 的全局函数）。

**通信封装层的两件事**：**协议设计**（method + params + callbackId 的消息格式，JSON 序列化）；**线程队列**——JS 侧调用要排队（原生处理是异步的）、回调需要超时与去重——**「请求-回调」配对是封装层的核心复杂度**。

**离线包与热更新**：H5 资源打包下发（而非每次 CDN 拉），原生 WebView 拦截资源请求走本地文件——**加载速度逼近原生 + 弱网可用**；热更新是「离线包版本管理」（diff 包 + 签名校验）。

**深水区**：能力边界——H5 调摄像头/推送要原生写对应 Bridge 方法，「一端一实现、H5 侧做适配层」是真实工程的成本结构。

收尾：答题主链「上行两条路 → 下行一条 → 封装两件事 → 离线包加速」，能把「请求-回调配对」点出来就是写过的人。

> 面试官追问点：URL 拦截方案的并发怎么处理？应答思路：拦截是「一帧一次」的串行通道（部分 WebView 上频繁 iframe 会被合并或丢弃）——高频调用必须「合并请求、一次带上批参数」或改用注入 API 通道；这解释了「为什么老项目要迁移注入方案」——通道吞吐量限制而不是协议限制。

#### 6.5 Flutter与RN的渲染差异？跨端怎么选型

答：一句话定调，**RN 是「JS 写原生控件」（桥接到系统 View），Flutter 是「自绘引擎画像素」（Skia/Impeller 直接出帧）——差在「渲染的产权」：一个租系统的、一个自己的**。

**RN 的架构**：JS 写组件 → **桥（Bridge）序列化传给原生侧创建真实 View**（旧 Bridge 的 JSON 序列化是性能瓶颈）——新架构 Fabric 把通信改为 **JSI 直连**（C++ 层持有 JS 对象引用、不再 JSON 序列化）+ 新渲染器按 C++ 生成 shadow tree 批量合并提交——**它始终是「JS 逻辑 + 原生控件渲染」**，各端观感天然原生。

**Flutter 的架构**：Dart 编译成原生机器码（AOT），**widget 树 → element 树 → renderObject 树**，Skia/Impeller 在自己的光栅化管线里直接画帧——**不依赖系统控件**：像素级一致（设计稿即所得）、不背各端控件的兼容税；代价是**包体积（自带渲染引擎 + 字体 + 框架）与原生控件的割裂感**（系统升级的新控件 Flutter 要自己画）。

**与原生的通信**：RN 走 JSI/原生模块；Flutter 的 Platform Channel——同样是「消息通道 + 编解码」，但**通信频率低一个数量级**（渲染不依赖通信，只有业务能力调用才跨层）。

**选型四维**：性能上限（重动画/一致性 UI → Flutter）；动态性（RN 的 JS 远程更新在部分场景占优；Flutter 的动态性受限）；团队技术栈（JS 系 vs Dart 学习曲线）；生态成熟度（RN 的 npm 生态 vs Flutter 的 widget 体系）。一句话——**「要像素级一致和性能 → Flutter；要贴原生观感和 JS 生态 → RN」**。

收尾：记住产权那句——**渲染的产权决定性能的税**：租用系统控件交「桥的税」，自绘引擎交「包体积的税」。

> 面试官追问点：RN 新架构为什么能摆脱序列化？应答思路：JSI 让 JS 引擎直接持有 C++ 对象引用（JS 与原生同进程内存操作，不再 JSON 化）；渲染侧 Fabric 用不可变 shadow tree 支持并发合成与批量提交——**「引用共享」替代「文本协议」**是所有跨层通信优化的共同终点（对照 6.2 的运行时、6.4 的注入 API）。

#### 6.6 Electron的架构是什么？安全问题怎么配置

答：一句话定调，**Electron = 「Chromium 渲染 + Node 主进程」的双进程架构——主进程管窗口与系统、渲染进程跑页面；安全的全部要义是一句「不信任渲染进程」**。

**双进程职责**：**主进程**（唯一、Node 环境）——窗口生命周期、系统 API（菜单/托盘/对话框）、进程管理；**渲染进程**（每个窗口/BrowserView 一个、Browser 环境）——跑页面；**IPC 是两世界的唯一正交通道**（ipcMain/ipcRenderer，经 contextBridge 暴露安全接口）。

**preload 是安全模型的关键层**：渲染进程默认裸奔（XSS 就是整个应用的沦陷），**preload 脚本在页面加载前注入**——contextBridge.exposeInMainWorld 把「白名单化的 IPC 方法」暴露给页面，页面代码只能用暴露过的能力——**「最小暴露面」原则**。

**安全配置四件套**：**contextIsolation: true**（上下文隔离——页面 JS 与 preload 的原型链隔离，防原型污染直达 preload 特权）；**nodeIntegration: false**（渲染进程禁 Node——页面 XSS 时不至于拿到 fs/child_process）；**禁 webSecurity/允许 navigations 的白名单**（setWindowOpenHandler 拦截跳转）；**CSP**（内容安全策略拦内联脚本注入）——**这套组合的每一次放开，都是在把「网页权限」升级成「系统权限」**。

**包体积优化**：Electron 壳约 80MB 起步——fuses 收紧（按需裁剪特性）、asar 打包、体积审计（大依赖白名单）；深水区：**用原生模块的 rebuild 成本**（electron-rebuild 编译针对 Electron 的 ABI）。

收尾：架构答「双进程 + IPC + preload 三层」，安全答「默认全关、白名单开放、隔离上下文」——**Electron 事故史的总结就是「把不信任的网页当操作系统管理员用」**。

> 面试官追问点：为什么 nodeIntegration: false 是默认安全基线？应答思路：渲染进程跑的是远程内容（应用页面也可能被 XSS），一旦 JS 拿到 Node API（require('child_process')），XSS 的破坏半径从「页面内」扩大到「整个系统」；关掉它把 JS 权限封回浏览器模型，能力升级只经 contextBridge 白名单——**「能力最小化」是纵深防御的第一层**。

# 7.高频手写与场景题

#### 7.1 手写Vue响应式和diff？思路要点是什么

答：一句话定调，**手写题的判卷标准从来不是「能跑」，是「边界处理」——响应式两版（defineProperty/Proxy）、diff 讲三前提、useState 讲链表，每题背「一个骨架 + 一个失分点」**。

**手写响应式（两版对照答）**：defineProperty 版——`Object.defineProperty(obj, key, { get() { dep 收集 activeFn; return val }, set(nv) { val = nv; dep.notify() } })`，**失分点是忘记递归深层对象**；Proxy 版——`new Proxy(obj, { get(t, k) { track(t, k); return Reflect.get(t, k) }, set(t, k, v) { Reflect.set(t, k, v); trigger(t, k); return true } })`——**加分点是 targetMap（WeakMap→Map→Set）三级结构与惰性代理**（get 时值是对象才递归包）。

**手写简化版 diff**：三前提先声明（同层、同类型、key）——**骨架是「旧 children 建索引 map（key→下标）→ 遍历新 children → 命中则复用 patch、未命中则新建 → 剩余旧节点删除」**——失分点是忘处理「旧节点剩余清理」和「文本节点快捷路径」；能讲「这个朴素版是 O(n) 但移动多」就引出了双端/LIS 的进阶话头（对照 8.6）。

**手写 useState（链表模拟）**：模块级单例 `stateHooks 数组 + index`——首次渲染 push 进数组、重渲染按 index 取——**闭包 setState 拿到的是「当时渲染的 cell」，所以要标记 dirty 触发整体重跑**——失分点是 index 忘在每次渲染开头重置（这就是 3.1.2 的顺序规则）。

**事件总线 mitt 与深拷贝**：mitt 的骨架是 `Map<type, Set<handler>>` 的 on/off/emit 三方法（失分点：off 按引用删，匿名函数删不掉）；深拷贝（WeakMap 防循环引用 + 保留原型）详见 JS 篇手写题。

收尾：口述策略——**每题先讲数据结构（Dep/链表/Map），再讲「触发-收集-更新」的时序，最后报失分点**——有结构的答案比代码本身值钱。

> 面试官追问点：手写 Proxy 版响应式怎么处理数组？应答思路：Proxy 天然拦截 push（set trap 触发多次：下标 + length）——讲出「一次 push 触发两次 set，需要去重」；对照 Vue2 为数组专门劫持七个变异方法的历史——能对比出「Proxy 的完整性」就是这道手写题的深水区。

#### 7.2 高频场景设计题怎么答？虚拟列表到埋点SDK

答：一句话定调，**场景设计题答的是「约束分析 + 数据结构选择 + 边界处理」三段式——先问清约束（数据量/一致性要求/降级预期），再给方案，最后主动报边界**。

**虚拟列表（两版）**：**定高版**——`startIndex = Math.floor(scrollTop / itemH)`，可视区渲染 `[startIndex, startIndex + Math.ceil(viewportH/itemH) + buffer]`，容器撑起总高（占位 div 防滚动条跳动）——**核心是「渲染窗口由 scrollTop 直接推导」O(1)**；**动态高版**——预估算高度渲染 → ResizeObserver 实测缓存（heights 数组 + 前缀和定位）——**失分点是跳转滚动条抖动**（估算与实测的差值修正）。深水区：快速滚动的「白屏窗口」（加大 buffer + 渲染骨架占位）。

**图片懒加载指令**：IntersectionObserver 观察进入视口 → 换 src → unobserve 释放——**比 scroll 监听强在「浏览器算交叉、不占主线程」**；边界：首屏图不懒（LCP 误伤，见 4.2.2）、loading 占位与加载失败兜底。

**前端水印方案**：canvas 生成水印图 → 转 dataURL 平铺（background-repeat）或 absolute 覆盖层——**防篡改是核心**：MutationObserver 监听水印节点（被删除/修改 → 立即重建）+ 属性锁（对开发者工具删除的兜底是「监听 body 子树变更」）；进阶：按用户 ID 生成溯源水印。

**表单动态渲染引擎**：schema 驱动（JSON 描述字段：type/label/校验规则）→ 组件映射表（type → 组件）递归渲染 → **联动规则（显隐/级联）声明为依赖表达式**——答「映射表 + 依赖收集」两个核心件就够，剩下是工程细节。

**埋点 SDK**：采集（页面 PV/点击/性能/错误四类）→ **批量上报（队列 + 定时/满 N 条 flush，见 4.2.4 的 sendBeacon）→ 失败重试（指数退避 + 本地缓存兜底）**；**设计灵魂是「上报不能影响业务」**——采样、独立域名（绕浏览器并发限制）、队列降级。

收尾：五道题共用一个答题模板——**「约束是什么 → 数据结构选什么 → 哪里会坏怎么兜」**，模板比题库通用。

> 面试官追问点：虚拟列表为什么必须用占位容器撑高度？应答思路：列表只渲染几十个元素时滚动条按「几十个」计算——总高度失真导致滚动比例错误；占位容器把「总高度」与「实际渲染」解耦，滚动条始终反映全集——**「滚动条诚实」是虚拟化可用性的前提**。

#### 7.3 线上白屏问题怎么排查？内存泄漏用什么查

答：一句话定调，**白屏排查按「资源 → 执行 → 渲染」三层漏斗走，先确认「HTML 到没到、JS 崩没崩、DOM 挂没挂」三问；内存泄漏靠「对比堆快照」找「只增不减的引用链」**。

**白屏三层漏斗**：**资源层**——HTML 状态码/CDN 异常/资源 404/跨域（DevTools Network 全红排查）；**执行层**——JS 抛错（白屏 80% 是这里）：**「入口 JS 崩了、React/Vue 没接住」**（ErrorBoundary/Vue errorHandler 接住渲染兜底 UI）、老浏览器语法不兼容（构建 target 覆盖真实用户 UA）；**渲染层**——样式把内容藏了（z-index/overflow/display 的意外组合）、路由匹配空组件、SSR 注水失败卸载整树。**排查武器**：错误监控的「首屏报错」聚合（白屏时上报通常已捕获元凶）、按 UA/版本/灰度维度切分定位新增面。

**内存泄漏排查（Memory 面板三步法）**：**拍快照 → 操作疑似路径（开关弹窗/路由往返）→ 再拍快照对比**——看 **Retained Size 只增不减的对象 → 引用链找 holder**。三大经典源：**未清理的定时器/监听器**（setInterval 忘 clear、window listener 忘 remove）、**游离 DOM**（变量引用已移除的节点）、**闭包意外持有**（挂在全局的回调引用了大对象）。Detached 节点过滤 + Summary 视图的「Objects allocated」对比是两个高频动作。

**长任务定位（Performance 面板）**：录制交互 → 看主线程火焰图的红块（>50ms 长任务）——**自下而上（Bottom-Up）视图按耗时排叶子函数**找到元凶；深水区：Long Task API + LoAF（Long Animation Frames）在生产采集。

**请求失败的降级方案**：重试（幂等才可重试）→ 缓存兜底（上次的 localStorage 数据 + 过期标记）→ UI 降级（骨架换占位提示）——**「降级链路在需求评审时就该有」是这题的价值观收尾**。

收尾：白屏答「三层漏斗 + 三问」，内存答「快照对比 + 三大源」——方法论比工具名值钱，工具只是方法的执行件。

> 面试官追问点：为什么内存泄漏要「操作后对比」而不是只看一次快照？应答思路：泄漏的定义是「应该回收的没回收」——静态快照看不出「应该」；操作前后对比才能把「随操作增长的」从背景噪声里筛出来（框架自身的常驻对象不是泄漏）——**「对比是实验设计，快照只是数据」**。

#### 7.4 大文件上传如何设计？分片断点续传怎么实现

答：一句话定调，**大文件上传的主线是「分片转并发、hash 保完整、断点靠状态」——Blob.slice 切片 + 整体 hash 做身份证 + 已传分片查询实现秒传续传**。

**分片与并发**：`file.slice(start, end)` 切成固定大小（5MB 上下）的 Blob——**上传从「一个不可重试的大请求」变成「可独立重试的小请求」**；**并发控制池**（同时最多 3-4 个分片在飞，见 JS 篇的并发调度器）：完成的槽位补位新分片，单个分片失败只重试自己。

**hash 校验（整体身份证）**：**全量 hash 用 Web Worker 算**（spark-md5 增量喂入分片，主线程不被卡死）——深水区：**大文件全量 hash 太慢 → 抽样 hash**（首尾块 + 中间随机块）牺牲准确性换速度；hash 的三个用途：**秒传**（服务端已有同 hash 直接完成）、**断点查询的 key**、**完整性校验**。

**断点续传**：上传前带 hash 问服务端「这个文件传到哪了」——**返回已成功的分片列表，客户端跳过它们只传缺的**；服务端在全部分片到位后合并（合并请求带总分片数做校验），临时分片设过期清理（防半成品占盘）。

**四个配套场景**：**实时协作**（OT 针对文本的变换合并、CRDT 用数据结构达成无冲突合并——答概念边界即可：OT 需要中心服务器、CRDT 服务器只做分发）；**扫码登录**（二维码带 token，**轮询起步 → 升级长连接** WebSocket/SSE，登录后长连接复用做消息推送）；**乐观更新与回滚**（先改本地 UI 提升感知速度，请求失败回滚 + 提示；**回滚的竞态**：失败时用户已又操作了，要用「操作序号」丢弃过期回滚）；上传进度与取消（AbortController 断在分片粒度）。

收尾：设计题的加分结构——**把「上传」拆成「分片、hash、状态」三个正交关注点分别回答**，边界（抽样 hash、回滚竞态）自己先说出来。

> 面试官追问点：为什么分片上传能防「传一半断网重来」？应答思路：状态在服务端持久（已收分片落盘），客户端重启后凭 hash 查询增量——**「断点」的本质是把上传状态从连接生命周期中剥离，挂到「文件 hash」这个稳定 key 上**——连接可断、状态不丢，这是一切续传设计的共同思想。

# 8.深度精讲（渲染与框架机制口述版）

> 说明：本章是核心题的口述版深度精讲，讲到渲染管线源码级流程与框架内核机制层面。每题结构：一句话定调 → 分层展开 → 拉开差距的深水区 → 收尾，面试时按此节奏口述。

#### 8.1 浏览器渲染流程是怎样的？重绘回流怎么优化

答：一句话定调，**渲染管线是「解析建树 → 布局 → 绘制 → 合成」四段流水线，回流的代价比重绘高一个数量级，而合成层的存在让 transform 动画可以完全绕开前两段**。

**完整管线走一遍**：HTML 解析成 DOM 树、CSS 解析成 CSSOM，**两者合成 Render Tree（只含可见节点，display:none 的不在、head 不在）**；Layout（回流）计算每个节点的几何位置（盒模型递归计算）；Paint 生成绘制指令列表（记录绘制顺序，分层）；Composite 合成器把各图层栅格化后的纹理交给 GPU 合成上屏。

**回流的触发清单**：几何属性变化（宽高、位置、字体）、DOM 结构变化（增删节点）、读取布局信息（offsetTop/getBoundingClientRect/scrollTop **这类「强制同步布局」是隐性回流大户**）、窗口 resize。**读写交错是性能杀手**：JS 改样式（标脏）后立刻读布局，浏览器被迫立刻回流拿准确值（脏标记机制被击穿），循环里「改一次读一次」就是 N 次回流，**防御手段是批量读、统一写（读到的值先存变量），或用 rAF 把写操作挪到帧边界**。

**合成层是深水区一**：满足条件的元素（transform 3D、will-change、video、opacity 动画）会被提升为独立合成层，**它有自己的纹理，transform/opacity 变化只影响合成器（GPU 上做矩阵运算），完全不触发 Layout 和 Paint**。这就是「动画只用 transform 和 opacity」这条军规的底层依据。**层爆炸是它的反面**：大量元素被提升成独立层（比如无节制用 translateZ(0) 提升性能），**每层都要独立栅格化、层间要管理内存，反而卡死**，Chrome DevTools 的 Layers 面板就是查这个的。

**深水区二：rAF 的时机**：它注册的回调在「每帧渲染的样式计算之前」执行，**保证一帧内代码改的样式在当帧生效，不会丢帧**；而 setTimeout 的回调时机和渲染节拍无关，可能错过当帧的 paint（半帧后执行又要等下帧）。rIC（requestIdleCallback）在帧的空闲期执行，**适合非紧急任务，但要接受回调可能分多次执行、且 deadline.timeRemaining 不够时要把工作切片**。

收尾：渲染优化的本质是「**让变化发生在流水线的最下游**」：能合成不重绘、能重绘不回流、能批量不交错，三个「能」字对应流水线的三段成本。

> 面试官追问点：getBoundingClientRect 为什么会引发强制回流？应答思路：浏览器对布局采用脏标记延迟计算，但这个 API 要返回「此刻的精确几何」，只能同步执行一次 Layout 才能答对，多次读取同一帧内第二次会走缓存（布局没脏），读写交错才每次都真算。

#### 8.2 Vue响应式原理怎么演进？依赖收集怎么做

答：一句话定调，**响应式 = 「依赖收集（谁在用我）+ 派发更新（我变了通知谁）」两件事，Vue2 用 defineProperty 劫持 getter/setter，Vue3 用 Proxy 劫持整个对象操作，差距在「拦截面的完整性」**。

**Vue2 的机制**：初始化时递归遍历 data，**每个属性定义 getter/setter**。**getter 里做依赖收集**：全局有个 Dep.target（当前正在求值的 Watcher），getter 触发时「属性自己的 Dep 把这个 Watcher 收进订阅列表」；**setter 里做派发更新**：值变了就遍历 Dep 通知所有 Watcher 调 update（进异步队列去重，nextTick 后统一执行，这就是「改数据 DOM 不立即更新」的原因）。

**Vue2 的三宗罪**（Proxy 要解决的）：**新增/删除属性拦截不到**（没有对应的 trap，所以要 Vue.set/Vue.delete 打补丁）；**数组下标和 length 拦不到**（defineProperty 对数组索引自定义会带来巨大性能开销，Vue2 干脆放弃，改为**劫持七个变异方法**——重写 push/pop/shift/unshift/splice/sort/reverse，原型链上插一层，调用时手动触发更新）；**初始化要递归全量劫持**（深层对象一次性加 getter/setter，大对象初始化慢）。

**Vue3 的 Proxy 机制**（深水区一）：`new Proxy(target, handler)` 拦截 get/set/deleteProperty/has 等 **13 种操作**，新增删除天然可拦截。**惰性代理是性能关键**：get 触发时如果值是对象，才递归包 Proxy（**用到才深入**，初始化 O(1)，解决了 Vue2 的全量递归）。**依赖收集的结构也换了**：从「每个属性一个 Dep」变成 **targetMap（WeakMap：对象 → Map：属性 → Set<effect>）三级结构**，effect（副作用函数）取代 Watcher，和函数式写法（effect(fn) 自动追踪 fn 里用到的所有响应式数据）打通。

**深水区二：ref 为什么还要存在**——Proxy 的死穴是**只能代理对象，原始值（number/string）包不了**。ref 的方案是「把原始值装进 { value: xxx } 的盒子再代理盒子」，所以访问必须 .value；编译器在模板里自动解包（语法糖），**.value 的存在不是设计缺陷而是「原始值无引用」这个语言事实的最小代价解**。**toRef/toRefs 的解构保活**：reactive 对象解构后丢失响应（解构是值的拷贝），toRefs 把每个属性转成「指向原属性的 ref」，读写转发到原对象，保住了响应链。

收尾：Vue3 响应式的两个断言值得背下来——「Proxy 解决拦截完整性、惰性解决初始化成本」，以及「**reactive 管对象、ref 管一切（含原始值）**」的分工本质是语言的类型系统约束。

> 面试官追问点：为什么 Vue3 仍不能检测数组 length 直接赋值？应答思路：Proxy 能拦截 set(length)，但语义上「改 length 会连带影响所有下标」，触发全量更新代价大；Vue3 的处理是拦截后警告（写 length 直接赋值不推荐），数组更新推荐整体替换或用会触发下标 set 的方式。

#### 8.3 Fiber架构怎么运作？并发渲染的原理是什么

答：一句话定调，**Fiber 把「不可中断的递归渲染」改写成「可暂停的链表遍历」，双缓冲树（current/workInProgress）让中断和恢复的代价降为指针切换，Scheduler 用时间切片决定「谁先跑」**。

**先讲老架构的病**：React 15 的 reconciliation 是**同步递归**，组件树一旦开始 diff 就要一口气跑完（diff 千级组件可能上百毫秒），期间主线程被占死，**动画掉帧、输入卡顿都来自这段独占**。JS 单线程没有抢占式调度，唯一的出路是「**把大任务拆小、主动让出控制权**」。

**Fiber 的数据结构**：每个组件实例对应一个 Fiber 节点，**child/sibling/return 三个指针把树改写成链表**（深度优先遍历不需要递归栈，**循环加指针就能走完全树，走到任何节点都可以停下来**）。每个 Fiber 是一个「工作单元」，**render 阶段（可中断的 reconcile）每处理完若干单元就检查时间片是否用完，用完了保存现场（memoizedState 等挂在 Fiber 上）、把控制权还给浏览器，下个时间片从断点继续**。

**双缓冲树**（深水区一）：屏幕上对应 current 树，**新一轮更新在 workInProgress 树上重建**（复用 Fiber 节点、alternate 指针互相指）；**中断和恢复的现场就是「构建到一半的 workInProgress」**；commit 时 workInProgress 整体替换 current（指针切换，原子生效），这就是「双缓冲」——和显卡的前后帧缓冲同一思想。

**两阶段的语义分界**：**render 阶段可中断可重跑**（结果不落屏，中断重来没有副作用问题），所以 React 严格模式下会故意双调用组件函数（暴露不纯的副作用代码）；**commit 阶段不可中断**（替换树、执行生命周期的同步部分、操作 DOM），**useEffect 的回调被调度到 commit 后的异步时机**（passive effect），useLayoutEffect 在 DOM 变更后同步执行（读布局信息的正确钩子）。

**Scheduler 与优先级**（深水区二）：时间切片在浏览器上是 **MessageChannel 的宏任务**（不是 setTimeout，因为嵌套定时器有 4ms 最小间隔的钳制）；**Lane 模型用 31 位二进制表示优先级**（同步的 SyncLane 最高、过渡的 TransitionLane 低），**高优先级更新可以插队：打断正在进行的低优先级 render、先渲染自己**，被打断的低优先级更新在 bailout 时**复用（ lanes 对比）或重放**。这就是「输入响应优先于数据加载」这类体验优化的机制根基。

收尾：Fiber 的一句话总结，**「渲染的同步独占」改成「时间片上的链表遍历」**，架构上让 React 拿到了调度权，调度权让出了「优先级」这个新维度。

> 面试官追问点：为什么 hooks 不能写在条件里（链表说法的准确版）？应答思路：hooks 状态存在 Fiber 的 memoizedState 单链表上，按调用顺序对应；条件分支导致某次渲染少调一个 hook，后面的 hook 全部错位到别人的状态槽，所以规则是「顺序稳定」而非「数量固定」的语法要求。

#### 8.4 Vite为什么这么快？按需编译原理是什么

答：一句话定调，**开发态的 Vite 是「不打包」：入口是 ESM 依赖图按需加载，冷启动从 O(整个项目) 变成 O(入口模块），预构建只处理 CJS 依赖**。

**Webpack 的冷启动瓶颈**：dev 启动也要**全量构建 bundle**（分析依赖图、编译打包全部模块），项目越大启动越慢（分钟级），**而且改一行代码热更新也要重新处理受影响的 chunk**。

**Vite dev 的三段式**：

1. **浏览器原生 ESM**：入口文件直接 `<script type="module">`，浏览器**请求一个模块 Vite 才编译一个**（中间件拦截按需转换），首屏只编译首屏用到的模块，**冷启动时间和项目总大小解耦**；
2. **esbuild 预构建**：node_modules 里的 CJS 包（不支持 ESM）用 esbuild 转成 ESM，**esbuild 是 Go 写的、全并行编译，比 JS 写的 babel/terser 快 10-100 倍**；同时把零散依赖（比如 lodash-es 几百个小文件）合并成单文件，**减少浏览器按模块请求的 HTTP 次数**（深水区一：依赖缓存按 lockfile 哈希存 node_modules/.vite，锁文件没变直接命中）；
3. **HMR 精确失效**：编辑文件时**沿导入方（importers）向上传播失效边界**，HMR 边界内的模块热替换、边界外整页刷新，**不是重新打包而是按模块图通知**。

**深水区二：为什么生产构建换回 Rollup**——开发和生产的目标不同：dev 要「快」（原生 ESM 不打包），**生产要「体积和兼容」**（tree-shaking 深度、代码分割、压缩、旧浏览器降级），Rollup 的 ESM 原生打包在这三件事上是老江湖。**「dev 和 prod 环境差异」由此成为 Vite 的原罪**（深水区三）：dev 走 Vite 中间件、prod 走 Rollup，**极少数 bug 只在某一边复现**（比如 CJS 依赖的裸导入语义差异），Vite 的解法是 `vite build --mode development` 提供一致性校验手段。

收尾：Vite 快的本质是「**把 bundle 的工作推迟给浏览器的 ESM 加载器，把重活（依赖）前置给 esbuild 的原生速度**」，一句话：**按需 + 原生**。

> 面试官追问点：Vite 的按需编译会不会让首屏请求瀑布更深？应答思路：会（嵌套 import 的串行发现），所以有预构建合并（减少请求数）和模块preload（`import(...)` 转成带 `<link rel=modulepreload>` 的注入），深链路场景用 optimizeDeps.include 提前收编。

#### 8.5 首屏加载如何体系化优化？LCP指标怎么用

答：一句话定调，**首屏优化按「网络传输、资源解析、渲染路径」三层做减法，度量口径 LCP 定靶心**。

**第一层网络**：

1. **传输协议**：HTTP/2 多路复用（解决 HTTP/1 的队头阻塞，域名分片的旧优化作废）、brotli 压缩（比 gzip 再小 15%-20%）、**CDN 就近 + 边缘缓存**（静态资源 DNS 查到边缘节点）；
2. **连接提前**：**preconnect（提前完成 DNS+TCP+TLS 三次握手）> dns-prefetch（只做 DNS）**；**preload 加载当前路由必需的关键资源（字体、关键 CSS，as 属性指定类型才不重复下载）**；**prefetch 空闲时预取下个路由**，两者的优先级语义完全不同。

**第二层资源**：

1. **代码分割**：路由级 lazy（React.lazy/Vue 异步组件），**首屏 JS 从「全量」砍到「当前路由」**，bundle 分析揪出意外引入的大依赖；
2. **关键 CSS 内联 + 其余异步**：首屏样式直接 `<style>` 进 HTML（省一次往返），非关键 CSS 改 media=print 加 onload 切换；
3. **图片**：webp/avif（体积砍半）、**响应式 srcset**（按 DPR 和视口选尺寸）、**懒加载（loading=lazy 或 IntersectionObserver）**、**LCP 主图反而要 preload + fetchpriority=high**（它是 LCP 的直接元素，懒加载会误伤）。

**第三层渲染**：

1. **SSR/SSG 的选择**（深水区一）：SSR 服务端出 HTML（首字节即可渲染，**但 TTFB 变长、要保活 Node 服务**）；SSG 构建期出静态（TTFB 极短，**适合内容不变的路由**）；**hydration 的成本常被低估——客户端注水要把整棵组件树重新执行一遍**，流式 SSR + 选择性注水（React 18）按需注水缓解；
2. **骨架屏**：占用真实布局（防 CLS 抖动），比白屏和 spinner 的「感知性能」都好。

**度量定靶**（深水区二）：LCP 的四个「贡献者」按耗时拆解——**TTFB（慢在服务端/网络）、资源加载时长（慢在体积/CDN）、渲染延迟（慢在 JS 阻塞）**，先看 Element Timing 定位「哪个元素是 LCP」，再决定攻哪一层，**没有度量的优化是盲盒**。

收尾：首屏优化的心法是「**每层做减法：请求少一个、体积小一号、渲染早一步**」，而 LCP 的拆解链路保证每一刀都砍在瓶颈上。

> 面试官追问点：preload 和 prefetch 用错会怎样？应答思路：preload 用在非当前路由的资源是抢带宽（高优先级占坑）；prefetch 大量滥用在弱网设备上浪费流量；两者的判据是「当前渲染路径必需 → preload，下一跳可能需要 → prefetch」。

#### 8.6 虚拟DOM与diff怎么演进？双端和LIS差在哪

答：一句话定调，**diff 的本质是「同层比较加 key 复用」，Vue2 用双端比对、Vue3 改成「预处理加最长递增子序列」，React 的 Fiber diff 只对同类型列表做单向扫描**。

**为什么是 O(n) 不是 O(n³)**：树diff 的朴素算法是「每层每个节点和另一层每个节点比」（O(n²)×深度=O(n³)），**三大框架共同的前置约定把它砍成 O(n)**：**只同层比**（跨层移动当删除+新增处理）+ **同类型才深比**（标签不同直接替换整棵子树）——**用「放弃跨层复用」换线性复杂度**，这是工程上「够用的近似」。

**key 的机制还原**：同层列表 diff 时，**key 是节点的身份证**——有 key 能「旧 vnode 数组里的这项移到新位置」（DOM 节点移动复用）；**用 index 当 key 的两个坑**：头插数据时全列表错位复用（性能差）+ **带状态的元素（输入框）复用了错误的 DOM**（状态串位）；**随机数当 key 更糟**（每次渲染都是全新节点，复用率为零）。

**Vue2 双端 vs Vue3 最长递增子序列**（深水区一）：Vue2 的双端比较（新旧列表各两个指针，头头/尾尾/头尾/尾头四种匹配）能处理「头尾移动」的常见模式；**Vue3 先做「同步头尾」的预处理（跳过已相同的两端），剩余中间部分「新列表找旧列表的映射 + 求最长递增子序列」**——**LIS 里的节点不动（相对顺序稳定），不在 LIS 里的才移动**。数学上把「移动次数」压到最小（移动最少 = 不动最长 = LIS），这是「把启发式换成最优子结构」的算法升级。

**React 的单向扫描与标记**（深水区二）：Fiber 的 reconcile 对 children 是**单向遍历**（第一轮同步可复用的、key 对不上就跳出），**跳出后第二轮用 map 剩余旧 child 处理移动与删除**——**没有双端优化的原因**：Fiber 可中断的架构里「回退指针」成本高（打断后现场恢复复杂），单向扫描配合「lane 标记副作用」更适合流式处理。**Vue 全量内存 diff vs React 可中断调度**是两种工程取向，性能争论的根源在这。

收尾：diff 的答题心法，「**同层、类型、key 三前提讲清楚，再讲自己框架的处理策略（双端/LIS/单向）**」，能对比两家的取舍就到深水区了。

> 面试官追问点：为什么 Vue 需要编译优化（patchFlag）而 React 不做？应答思路：Vue 是「编译器知道模板结构」的流派（静态节点跳过、动态节点打 flag 精确比对）；React 是「JSX 任意表达式」流派（编译期拿不到结构信息，运行时全量 diff + 跳过 memo 化边界）——**模板约束换编译期信息**是两家性能路线的分水岭。

#### 8.7 BFC的底层行为是什么？触发与应用怎么记

答：一句话定调，**BFC 是「页面上的独立排版沙箱」：内部怎么乱都不外溢，外部也不影响它，触发它靠 overflow/float/position/flex 的一行 CSS**。

**BFC 的两个核心行为**（比背触发条件重要）：

1. **垂直 margin 不和外部折叠**：BFC 内部元素的 margin 只在内部折叠——**「两个兄弟盒子 margin 折叠」的解法就是给其中一个包 BFC 容器**；
2. **不与浮动元素重叠、包含内部浮动**：**清浮动（父容器 overflow:hidden 撑开高度）和两栏自适应布局（侧栏浮动、主栏 BFC 不侵入）都是这条的推论**。

**触发条件的记忆法**：让元素「脱离正常流或建立新格式化上下文」的属性——`overflow: 非 visible`、`float: 非 none`、`position: absolute/fixed`、`display: flow-root（现代专用，无副作用）`、`display: flex/inline-block/table-cell`（它们本身是其他格式化上下文）。

**深水区一：margin 折叠的规则细节**——折叠只发生在**普通流的块级盒子间**（BFC 之间、浮动、绝对定位不参与）；**相邻兄弟、父与第一个/最后一个子元素、空块自身的上下 margin 三种场景**；**折叠取较大值且正负号有规则**（正正取大、正负相加、负负取绝对值大）。**「父子折叠」是最反直觉的**：子元素的 margin-top 「穿透」父元素边界（父没建立 BFC 也没 border/padding 阻隔时）——「给父加 overflow:hidden」治的就是这个。

**深水区二：为什么 flex/grid 能当 BFC 用**——严格说 flex 容器建立的是 **flex formatting context**（不是 BFC 本体），但**对 margin 折叠和浮动包含表现出同样的隔离行为**；**display:flow-root 是 CSS 规范专门为「只要 BFC 不要副作用」发明的值**（overflow:hidden 会裁剪、float 会脱流，flow-root 都不会）——**能报出 flow-root 就证明你的知识在更新**。

收尾：BFC 答题的口诀，「**记两个行为（margin 不外折、浮动不互扰），触发条件按『脱流或新上下文』理解，实战三招（清浮动/防折叠/自适应布局）**」。

> 面试官追问点：为什么 overflow:hidden 能清浮动？应答思路：触发 BFC 后「包含内部浮动」是 BFC 的定义性行为（高度计算包含浮动子元素）；副作用是裁剪溢出内容，所以现代首选 display:flow-root。

#### 8.8 HMR热更新的链路是什么？为什么用WebSocket

答：一句话定调，**HMR 的链路是「文件监听 → 增量编译出补丁 → WebSocket 推 manifest → 浏览器 JSONP 拉补丁 → module.hot 回调换模块」，失败降级整页刷新**。

**五步链路**：

1. **监听**：webpack 的 watch 模式（fs.watch/轮询）感知文件变化，**增量编译（缓存上次模块图只重编受影响链路）**；
2. **编译产物**：输出**两个新文件（更新模块的 chunk + manifest 清单：hash 变化和模块 id 映射）**；
3. **推送**：dev server 通过 **WebSocket 推 hash**（不推内容，只通知「有新版本」）；
4. **拉取**：浏览器端 HMR runtime 收到 hash，**对比本地 → 向 server 发 JSONP/AJAX 请求拉 manifest 和更新的 chunk**；
5. **替换**：**从入口模块回溯找 update 的接受者**——模块自己调 `module.hot.accept` 就地替换（**组件库的 accept 回调里 rerender**）；**找不到接受者逐层上抛，到入口还没人就 hot.apply 失败 → location.reload 整页刷新**（降级路径）。

**深水区一：模块热替换的「接受边界」**——accept 的语义分两层：**`accept(自身模块)`**（我更新我自己，如入口文件）和 **`accept(依赖模块, 回调)`**（我的依赖变了，回调里处理——**Vue/React 的 loader 实现正是给每个组件自动注入 `accept(() => rerender(vm))`**，所以业务代码「无感热更新」，是框架 loader 替你写了 accept）。

**深水区二：HMR 保存状态的边界**——**模块替换是新函数换旧函数，「模块级变量被重置」**（const 计数器回零）；React 的 Fast Refresh（进阶版 HMR）**保留组件 state 的机制**：签名对比（组件函数的签名变了 state 丢弃、没变复用）+ **组件树位置稳定**；**「热更新保留一切状态」在原理上不可能**（闭包旧变量无法迁移），能讲清这个边界是深水区。

收尾：HMR 的答题心法，「**WebSocket 只传信号、JSONP 拉补丁、accept 决定替换边界、失败降级刷新**」四句话，再补一句「框架的丝滑热更新是 loader 注入 accept 的功劳」。

> 面试官追问点：为什么用 WebSocket 而不是轮询？应答思路：编译完成的时间点不可预测，推送模型（事件驱动零延迟）；HMR 之外 WebSocket 还承担「编译错误Overlay」的实时推送——dev server 的「全双工通知通道」复用。

#### 8.9 qiankun沙箱怎么实现？读共享写隔离是什么

答：一句话定调，**qiankun 的沙箱有两代：SnapshotSandbox（快照对比）给低版本浏览器、ProxySandbox（代理隔离）是主力，「多实例代理 + with 包裹」实现变量级隔离**。

**为什么需要沙箱**：多个子应用同住一个 document，**全局 window 是共享的**——A 应用写 `window.jQuery = v1`、B 写 v2 互相覆盖；沙箱的目标是「**每个子应用有自己的一套全局变量视图**」。

**SnapshotSandbox 的机制**（深水区一）：**激活时拍 window 的快照，失活时 diff（对比当前 window 和快照，把子应用改过的属性恢复原值、新增的删除）**——**「卸载时还原现场」的朴素方案**；缺陷：**不支持多实例同时激活**（两个子应用交替快照会互相打架）且**遍历 window 的 diff 性能差**。

**ProxySandbox 的机制**（主力）：**为每个子应用 new 一个 Proxy 代理 fakeWindow**，子应用代码被改写后跑在 `with(fakeWindow) { ... }` 里——**变量查找先走 proxy 的 get**：**fakeWindow 自己有的属性返回自己的，没有的才透传真 window（读共享、写隔离）**；**set 一律写进 fakeWindow（不污染真 window）**；**deleteProperty 同理只删自己的**。**多实例并存的原理**：每个子应用的 proxy 独立，写操作互不可见——「写隔离、读共享」的折中让公共库（react）还能复用缓存。

**深水区二：JS 沙箱之外的三件事**——**样式隔离**：默认 dynamic style（运行时改写 style 标签加前缀作用域），**experimentalStyleIsolation 是 ShadowRoot 或 scope 变体，strictStyleIsolation 用 Shadow DOM**（副作用：弹窗挂 body 就逃出 shadow 了，**「UI 穿透」是 Shadow DOM 隔离的代价**）；**路由隔离**：URL 的变化要路由到对应子应用（activeRule 匹配）且**子应用的路由库要 patch（history 的 pushState 劫持通知主应用）**；**应用间通信**：initGlobalState 是「主应用持有的 observable store」（观察者模式的又一应用）。

收尾：qiankun 答题的心法，「**沙箱解决的是 window 争抢，Proxy 的读写不对称（读共享写隔离）是灵魂，样式路由通信是配套三件套**」。

> 面试官追问点：为什么不用 iframe 直接隔离？应答思路：iframe 隔离最彻底（独立 window/document），但代价是「**双份 CSS/JS 上下文（内存×N）、路由要手动同步、弹窗居中算的是 iframe 内坐标、通信走 postMessage 序列化**」——qiankun 的 JS 沙箱是「**iframe 的隔离收益减去 iframe 的集成成本**」的折中方案。

#### 8.10 SSR同构注水原理是什么？流式方案怎么优化

答：一句话定调，**SSR 的两阶段是「服务端 renderToString 出 HTML + 客户端 hydrate 复用 DOM 重建组件树」，注水的成本是「整棵树的事件绑定与状态重建」，流式 SSR 与选择性注水是对它的优化**。

**render 阶段**：服务端执行组件函数产出 **HTML 字符串**（**只跑 render 相关生命周期/副作用**——**window/document 不可用的原因：Node 里没有它们**，代码里的 `typeof window !== 'undefined'` 守卫就是双端分支）；**HTML 里嵌 序列化的初始数据（window.__INITIAL_STATE__）**——客户端拿到「**首屏立即可见的静态结构 + 渲染所需的数据**」。

**hydrate 阶段**（深水区一）：客户端 JS 就绪后 **hydrateRoot 而非 createRoot**——**不做「创建 DOM」而是「遍历现有 DOM 建立组件树、绑定事件、还原 state」**；**hydration 会 diff 服务端 HTML 和客户端首渲染结果**，**不一致警告 mismatch**（时间戳、随机数、UA 判断等双端差异是重灾区）。**注水是「整棵树的同步工作」**：大树注水期间主线程占满（可交互时间被推迟）——**「首屏快但可交互慢」是 SSR 的原生矛盾**，FCP 的收益和 TTI 的代价要一起报。

**React 18 的两个解药**（深水区二）：

1. **流式 SSR（renderToPipeableStream）**：**边渲染边 flush**——用 Suspense 圈住慢组件（数据未就绪先出 fallback 占位），**已完成的先发给浏览器**（不必等整棵树）；数据到了再流式补 `<template>` 片段和内联指令替换 fallback——**「分批发货」取代「攒齐再发」**；
2. **选择性注水（Selective Hydration）**：**优先注水「用户正在交互的部分」**——Suspense 边界作为注水单元，**点击某个区域会把它所在的边界提到注水队列最前**；配合流式 SSR，**页面可以「先看到、边交互边注水」**，把注水从「一次性大坝」变成「可插队的队列」。

**SSR/SSG/ISR 的选型**：**内容静态（文档/博客）→ SSG**（构建期出 HTML，CDN 全缓存，TTFB 极小）；**内容动态但结构稳定（电商详情）→ ISR**（Next 的增量静态：过期后台再生成，命中期间返回旧页）；**强个性化（用户时间线）→ SSR**；**纯客户端（后台系统）→ CSR**——**按「数据变化频率 × 个性化程度」选渲染时机**。

收尾：SSR 答题的主线，「**HTML 快是表象，注水慢是代价，流式与选择性注水是把代价分期**」，选型则是「**渲染时机对齐数据特性**」。

> 面试官追问点：为什么 hydration mismatch 是 error 而不是静默用客户端结果？应答思路：mismatch 意味着「服务端和客户端对同一数据的视图不同」——静默修正会引发「用户看到的内容突然变化」（闪变），React 选择警告加局部重渲染暴露问题；根因治法是「双端同源数据」保证确定性渲染。
