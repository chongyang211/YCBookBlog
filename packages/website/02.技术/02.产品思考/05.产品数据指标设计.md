## 1. 案例引入

### 1.1 DAU 涨答不上

上一篇糖果充学会了 MVP。三个月过去，团队做的所有 MVP 都上线了：发票 A4 识别、客户对账门户、供应商晚到发票补录、月度亮点摘要——真正做的都是真需求。

糖果充盯着后台看板得意——**DAU 从 300 涨到 390，月度涨幅 30%**。他决定在部门季度会上好好汇报一次。

**部门季度会** (在场:老板 A 总、CFO、销售总监、糖果充)：

```
糖果充: (自信) "本季度我们的财务对账系统 DAU 从 300 涨到 390, 
              涨幅 30%。核心功能发票识别月度识别 5000+ 次,
              客户对账门户 5 家大客户全接入。"

A 总:   "不错。但我问几个问题——付费转化率现在是多少?"

糖果充: "……付费? 这是内部系统, 没有付费。"

A 总:   "哦对, 那客户对账门户呢? 5 家大客户接入了, 客户续约率呢?"

糖果充: "……续约率我不知道, 那是销售侧的数据。"

A 总:   "那单客户的 LTV (生命周期价值) 呢? 获客成本回本周期呢?"

糖果充: "……我们是财务系统, 主要看 DAU 就好了吧?"

A 总:   "小杨, DAU 涨 30% 好不好, 取决于你为了涨这 30% 花了什么代价。
        如果为了涨 DAU, 我们错过了对账准确率, 客户续约率会掉。
        如果为了涨 DAU, 我们让系统变复杂, 老用户会烦。
        你只看 DAU, 相当于开车只看油表, 不看方向盘。"

糖果充: (愣住)
```

会后糖果充回工位，把过去 3 个月看过的所有数据整理了一遍：

```
糖果充过去 3 个月盯着的数据:
  DAU              ✓ 每天看
  月度新增用户      ✓ 每周看
  发票识别次数      ✓ 每天看
  系统访问 PV       ✓ 每周看
  接口平均耗时      ✓ 每天看
  服务可用性        ✓ 每天看

糖果充从没看过的数据:
  ❌ 用户对账错误率 (核心业务价值)
  ❌ 用户 7 日留存率 (真实用户粘性)
  ❌ 客户续约率 (商业健康度)
  ❌ 客户 NPS (口碑指数)
  ❌ 单客户 LTV (商业价值)
  ❌ 单用户月度使用时长 (深度使用)
  ❌ 客户对账门户异常上报率 (质量护栏)
```

**糖果充看的都是"好看"的指标, 从没看过"真正决定产品健康度"的指标**。

**更糟的**：他去问李姐"最近用系统感觉怎么样"，李姐说：

```
李姐: "系统挺好用的, 但你上个季度加的一堆新功能, 
      我用不惯的时候没人管。上次有一次识别错了金额, 
      我上报了两周了, 没人回复。你们是不是不太在乎小问题?"

糖果充: (第二次愣住)
```

DAU 涨 30% 的同时，**系统的实际使用质量在下降**，**用户投诉响应机制没建**，**糖果充完全不知道**——因为他从来没看过这些指标。

### 1.2 顺藤摸根因

带着这条线往下挖：

- **假设 1**：糖果充懒得看数据？——不是，他每天都在看，看得很勤
- **假设 2**：数据平台不给力？——不是，公司数据平台功能齐全
- **假设 3**：糖果充不懂数据分析？——**部分是**，但更根本的是**他不知道该看什么**
- **假设 4**：那"该看什么"取决于什么？——**取决于产品的目标**。糖果充的产品目标是"帮公司财务和客户高效对账"，DAU 只是过程指标，不是目标指标
- **假设 5**：什么样的指标能真正反映"高效对账"？——**对账准确率、对账周期时长、客户续约率、NPS**——这些才是真价值
- **假设 6**：糖果充为什么只看 DAU？——**DAU 是最容易看到的、最容易涨的、最容易汇报得好听的**——**虚荣指标陷阱**
- **假设 7**：有系统的方法吗？——**北极星指标 + AARRR + 指标分层**，本篇主线
- **假设 8**：作为工程师，我怎么参与指标设计？——**埋点规范 + 数据看板 + 护栏机制**

仔细分析这次翻车的根因：

```
表象                                真实问题
────────────────────────────────────────────────
"DAU 涨了 30% 是好事"              → 虚荣指标, 不反映产品真价值
"看板漂亮 → 产品健康"              → 混淆了"运行状态"和"业务价值"
"内部系统不用管付费"                → 内部系统也有价值指标 (对账准确率/客户续约)
"用户没投诉 = 满意"                 → 沉默用户 ≠ 满意用户, 无 NPS 无口碑度量
"我盯着看板努力工作"                → 盯错方向, 相当于开车看油表不看路
```

**根因**：糖果充**只有数据消费能力, 没有指标设计能力**。他会看别人做好的数据看板, 但不会**主动定义"什么数据才真正反映我的产品健康"**。**指标 = 你告诉自己看哪里, 也就告诉团队往哪里走**——错的指标 = 错的方向。

这一段里至少藏着 8 个原理点：

```
① 指标体系应该怎么分层?                                → 第 2 章
② 什么是北极星指标? 一个团队为什么只能有一个?           → 第 3 章
③ AARRR / RARRA 怎么用? 为什么是留存不是拉新?           → 第 4 章
④ 什么是虚荣指标? 如何识别?                             → 第 5 章
⑤ 如何搭建"北极星 + 一级 + 二级 + 护栏"四层?            → 第 6 章
⑥ 作为工程师, 如何设计埋点?                            → 第 7 章
⑦ 指标反模式?                                          → 第 8 章
⑧ 不同岗位指标设计变形?                                → 第 9 章
```

### 1.3 要回答什么

这个事故就是本篇的**主线案例**。带着上面 8 个问号往下走。本篇路线：

```
指标体系四层全景 (第 2 章)
   ↓
北极星指标 (第 3 章) ─→ 解开"只看一个指标, 看哪个"
   ↓
AARRR / RARRA (第 4 章) ─→ 解开"用户旅程各阶段看什么"
   ↓
虚荣 vs 可执行 (第 5 章) ─→ 解开"漂亮的数据不等于健康"
   ↓
四层落地 (第 6 章) ─→ 解开"从北极星拆到二级指标"
   ↓
埋点规范 (第 7 章) ─→ 解开"作为工程师怎么落地"
   ↓
反模式 (第 8 章) + 跨岗位 (第 9 章)
   ↓
综合案例 (第 10 章) ─→ 糖果充重建指标体系
```

📌 **本篇定位**：这是"产品思考"系列的**决策力升级**。前四篇讲"看到用户、挖到真需求、做取舍、做 MVP"，本篇讲"**做完之后, 怎么知道做对了没有**"。**指标体系 = 产品的仪表盘**——但仪表盘不等于方向盘, 你得先知道要去哪, 才能设计仪表盘。**这一篇教你做仪表盘, 也教你区分仪表盘和方向盘的差别**。

## 2. 指标全景图

### 2.1 指标四层

一个完整的产品指标体系, 应该分四层:

```
┌───────────────────────────────────────────────────────────┐
│                    指标四层                                 │
├───────────────────────────────────────────────────────────┤
│                                                            │
│  ★ 北极星指标 (1 个)                                       │
│    整个产品/团队最重要的那一个数字, 反映用户核心价值        │
│                                                            │
│  ↓                                                         │
│                                                            │
│  📊 一级指标 (3-5 个)                                       │
│    直接影响北极星, 团队每周关注                             │
│                                                            │
│  ↓                                                         │
│                                                            │
│  📈 二级指标 (10-20 个)                                     │
│    影响一级指标, 各子模块/团队负责                           │
│                                                            │
│  ↓                                                         │
│                                                            │
│  🛡 护栏指标 (5-10 个)                                     │
│    不能被牺牲的底线 (质量/性能/合规/安全)                    │
│                                                            │
└───────────────────────────────────────────────────────────┘
```

**四层属性速查**:

| 层 | 数量 | 更新频率 | 谁看 | 糖果充 V1 状况 |
|---|:---:|:---:|:---:|---|
| 北极星 | 1 个 | 月度 | 全团队 + 老板 | ❌ 没有 |
| 一级 | 3-5 个 | 周度 | 团队 leader | ❌ 只有 DAU |
| 二级 | 10-20 个 | 日度 | 模块负责人 | 混乱, 有一堆但不成体系 |
| 护栏 | 5-10 个 | 实时 | on-call 值班 | 只有服务可用性 |

### 2.2 为什么这么切

指标不就是"多看几个数据"吗? 为什么要切成四层?

**论证**:

**1.没北极星就没方向**——每天数据看一堆, 但没有"最重要的那一个", 团队会在细节里迷失。**北极星的价值不是"给出答案", 是"逼团队做出选择"**——你必须承认哪一个指标是最重要的, 其他都是次要的。糖果充 V1 死在这里, 他每天看 DAU, 因为 DAU 最好看, 不是因为 DAU 最重要。

**2.没一级指标就无法拆解北极星**——北极星是结果, 你不能直接"做北极星", 只能通过做一级指标让它涨。一级指标是**"我今天能做什么让北极星涨"**的答案。**一级指标 = 团队每周的行动清单**。

**3.没二级指标就无法归因**——一级指标涨了或跌了, 是哪个具体原因? 二级指标回答这个问题。**二级指标 = 归因层**——不做二级指标, 你永远只知道"变了", 不知道"为什么变"。

**4.没护栏指标就会翻车**——为了涨北极星, 团队会做各种激进决策 (加复杂功能、缩短流程、绕过审核...)。护栏指标是**"再急也不能破的底线"**——性能不能崩、错误率不能超、合规不能违反。**护栏 = 让北极星涨得健康, 而不是涨得畸形**。

反向验证: **没这四层会怎样**? 答案就是第 1 章, 糖果充盯着 DAU 三个月, 完全不知道产品到底健不健康。

**结论**: 四层的本质是**"从战略到执行"的分层管理**——北极星定方向, 一级指标定行动, 二级指标做归因, 护栏兜底不翻车。**四层缺一都会失衡**。

## 3. 北极星指标 OMTM

### 3.1 什么是北极星

**北极星指标 (North Star Metric, NSM)**, 也叫 **OMTM (One Metric That Matters)**, 概念来自硅谷创业圈:

> **一个产品团队在一段时期内, 只应该有一个"最重要的指标"——所有决策都指向让这个指标涨。**

**为什么只能有一个**? 因为**多目标 = 无目标**。你不可能同时最大化"用户量"、"付费率"、"满意度"、"留存"——它们经常互相冲突。**必须选择一个, 才能真的做取舍**。

**经典案例**:

```
Facebook 北极星:       月活用户数 (MAU)
                     → 一切为拉新 + 留住用户
                     
Airbnb 北极星:        订晚数 (Nights Booked)
                     → 一切为让房东列更多房 + 让客人多订
                     
Slack 北极星:         团队发送 2000+ 条消息数
                     → 一切为让新团队突破"活跃阈值"

Spotify 北极星:       用户听音乐总时长
                     → 一切为让用户更多打开 + 更长收听
```

**注意**: 北极星**因产品阶段不同而不同**。同一个产品:

```
早期:  可能是"注册用户数" (证明有人要)
成长期: 可能是"月活" (证明产品有留存)
成熟期: 可能是"付费转化率" (证明产品能变现)
```

**不是所有指标都能当北极星**。真正的北极星必须同时满足**三个标准**。

### 3.2 三个标准

```
┌────────────────────────────────────────────────────────┐
│                北极星的三个标准                          │
├────────────────────────────────────────────────────────┤
│  ① 反映用户真价值    这个指标涨, 意味着用户真的得到了价值 │
│                                                          │
│  ② 反映商业健康度    这个指标涨, 意味着公司也在健康增长   │
│                                                          │
│  ③ 团队可以直接影响  团队每周的动作能让它涨或跌            │
└────────────────────────────────────────────────────────┘
```

**用三个标准检查常见候选指标**:

| 候选指标 | 反映用户价值? | 反映商业健康? | 团队可影响? | 是否合格? |
|---------|:---:|:---:|:---:|:---:|
| DAU (日活) | 部分 (打开就算, 不代表价值) | 部分 | ✓ | 半合格 |
| PV (页面浏览) | ✗ (可能是刷不出结果) | ✗ | ✓ | 不合格 (虚荣) |
| 注册用户总数 | ✗ (只是有人来) | ✗ (可能都是僵尸) | ✓ | 不合格 |
| 付费转化率 | 部分 (只反映付费一步) | ✓ | ✓ | 半合格 |
| 用户完成核心动作次数 | ✓ | ✓ | ✓ | **合格** ★ |
| 服务可用性 SLA | ✗ | ✗ | ✓ | 不合格 (是护栏) |

**核心洞察**: **"用户完成核心动作次数"** 通常是最佳北极星候选——因为它**同时**反映用户价值 + 商业价值 + 团队可影响。

### 3.3 找北极星四步

**四步法**找北极星:

```
Step 1: 定义"用户价值时刻"
        什么时候你的用户"真正得到价值"?
        例: 对账系统的用户价值时刻 = 
            "李姐月末对完账, 数据正确, 准时下班"

Step 2: 找到"价值动作"
        用户在价值时刻做了什么关键动作?
        例: "使用系统完成了当月完整的对账 (标记为已完成)"

Step 3: 定义指标
        把价值动作变成可测量的指标
        例: "月度成功完成对账的用户数 x 完成次数"
        (成功 = 无差错 + 按时完成)

Step 4: 三标准验证
        反映用户价值? ✓ (真做完对账才算数)
        反映商业健康? ✓ (客户对账门户续约的核心指标)
        团队可影响? ✓ (团队做的功能都影响这个)
        → 合格
```

**拿糖果充的对账系统练手**:

```
之前的候选 (糖果充盯的): DAU
问题: DAU 涨了但用户可能是登录看了一眼就走, 
      不能反映"是否真的对完账"

新候选: "月度成功完成对账人次"
定义: 一位用户在一个月内完成一次"月度对账关闭"操作 = 1 人次
      (关闭 = 已核对完毕, 数据锁定)
      
计算示例:
  李姐 6 月完成一次 = 1
  其他 4 位财务各完成 1 次 = 4
  5 家客户各完成 1 次 = 5
  6 月总人次 = 10

三标准验证:
  ✓ 反映用户价值: 完成关闭 = 真的对完账
  ✓ 反映商业健康: 客户续约的核心, 财务效率的核心
  ✓ 团队可影响: 减少错误、加速对账、扩大客户量都影响它

→ 这就是糖果充的北极星
```

**北极星找到后, 团队的行动会自然重排**:

```
之前的行动: 加功能 → 涨 DAU
现在的行动: 减少对账错误 → 涨"成功完成对账人次"
           缩短对账周期 → 涨"月度对账次数"
           扩大客户量 → 涨"参与对账人数"

从"我做了多少功能" 转向 "用户真的完成了多少对账"
```

## 4. AARRR 与 RARRA

### 4.1 AARRR 海盗指标

**AARRR** (读作"啊啊啊啊啊", 也叫**海盗指标**) 是硅谷早期最流行的产品分析框架, 由 500 Startups 的 Dave McClure 提出:

```
┌───────────────────────────────────────────────────┐
│                AARRR 用户旅程五阶段                 │
├───────────────────────────────────────────────────┤
│                                                     │
│  A - Acquisition  (获取)  用户如何找到你             │
│      指标: 新增用户数、渠道分布、CAC (获客成本)      │
│                                                     │
│  A - Activation   (激活)  用户第一次得到价值          │
│      指标: 激活率、首次成功率                        │
│                                                     │
│  R - Retention    (留存)  用户是否回来              │
│      指标: 次日/7 日/30 日留存                       │
│                                                     │
│  R - Revenue      (变现)  用户是否付费              │
│      指标: 付费转化率、ARPU、LTV                     │
│                                                     │
│  R - Referral     (推荐)  用户是否推荐给别人         │
│      指标: NPS、K 因子、邀请转化率                    │
│                                                     │
└───────────────────────────────────────────────────┘
```

**AARRR 的价值**: 把用户旅程切成 5 段, 每段用一个指标衡量, **形成漏斗**。你可以清楚看到"用户在哪一步流失最多", 从而知道"该优化哪一步"。

### 4.2 RARRA 进化

**AARRR 的缺陷**: 顺序是 A → A → R → R → R, 隐含了"**先拉新, 再留存**"的逻辑。但硅谷 2018 年后逐渐意识到——**这个顺序是错的**。

**Gabor Papp 提出 RARRA 修正版**:

```
┌───────────────────────────────────────────────────┐
│         RARRA - 留存优先的用户旅程                  │
├───────────────────────────────────────────────────┤
│                                                     │
│  R - Retention    (留存)   ★ 最优先                │
│      拉再多人都白搭, 留不住 = 漏水的桶              │
│                                                     │
│  A - Activation   (激活)                            │
│      让新用户第一次得到价值, 才有留存               │
│                                                     │
│  R - Referral     (推荐)                            │
│      老用户推荐才是最有效的拉新                     │
│                                                     │
│  R - Revenue      (变现)                            │
│      有留存有推荐才有稳定收入                       │
│                                                     │
│  A - Acquisition  (获取)  ← 最后再考虑              │
│      前面几步都跑通了, 拉新才有意义                 │
│                                                     │
└───────────────────────────────────────────────────┘
```

**核心洞察**: **"先做留存, 再做拉新"**——如果留存 < 30%, 拉再多人都是漏水的桶; 如果留存 > 60%, 每一个新用户都是稳定资产。

**AARRR vs RARRA 的对比**:

```
AARRR 心态: "我们要涨 100 万用户!"
  → 花大钱做广告 → 拉来 100 万 → 90% 一周内流失 → 剩 10 万
  → 三个月后需要再拉 100 万才能维持 → 陷入"拉新+流失"死循环

RARRA 心态: "我们要让 1 万用户留下来"
  → 深度访谈这 1 万用户 → 找到激活点 → 留存率从 30% 升到 70%
  → 老用户 NPS 高 → 主动推荐 → 拉新是"意外惊喜"
  → 每一个新用户都是稳定资产
```

**结论**: **早期产品应该先看 RARRA 中的第一个 R (留存), 别去拉新**。糖果充盯 DAU 涨 30% 就得意, 其实完全没看留存——**新增用户第 8 周还在用的比例**可能只有 20%, 意味着 DAU 涨的 30% 里大多数是"新来但下个月就走"的用户。

### 4.3 产品走一遍

**糖果充的对账系统 AARRR 拆解**:

| 阶段 | 指标 | 现状数据 | 问题 |
|------|------|--------|------|
| A (获取) | 新增用户/月 | 40 (公司内新加入 + 新客户接入) | 数字对但没意义 (内部系统) |
| A (激活) | 首次成功对账率 | ??? (糖果充没看过) | **盲区** |
| R (留存) | 7 日留存 | ??? | **盲区** |
| R (变现) | 客户对账门户 ARPU | ??? | **盲区** |
| R (推荐) | 老客户推荐新客户 | ??? | **盲区** |

**5 个阶段, 糖果充只跟踪了 1 个 (A 获取), 剩下 4 个全是盲区**。

**用 RARRA 重新看**:

```
R (留存) 第一优先级:
  数据补齐: 用户次月留存 (第一次注册后, 次月还在用的比例)
  实际拉数据: 45% (低于健康线 60%)
  意味着: 每两个新用户就有一个下个月流失
  行动: 找出流失原因 (访谈 20 位一个月没登录的用户)
  
A (激活):
  数据补齐: 首次登录 7 天内完成一次对账的比例
  实际拉数据: 30%
  意味着: 70% 新用户注册后从不真正使用
  行动: 优化新用户引导流程

R (推荐):
  数据补齐: 客户 NPS (0-10 分, "你会推荐给同事吗")
  实际拉数据: 首次调研平均 6 (中等偏下)
  意味着: 用户觉得"能用"但不足以主动推荐
  行动: 提升核心体验, 目标 NPS > 7

R (变现):  
  数据补齐: 单客户年度使用价值 (客户对账门户直接影响续约)
  数据待定
  
A (获取) 反而是最后:
  拉新暂缓, 先解决前面 4 个问题
```

**行动重排**: 糖果充之前把 60% 精力放在"新增用户 (拉新)", 现在应该把 60% 精力放在**留存和激活**——**先让漏水的桶补上**。

## 5. 虚荣与可执行

### 5.1 虚荣指标的诱惑

**虚荣指标 (Vanity Metrics)**: 好看、易涨、可展示, 但**不反映产品真价值**的指标。工程师和产品经理都容易陷入**虚荣指标陷阱**——因为它们:

```
① 数字大, 汇报时好看
② 容易涨 (加个入口就涨了)
③ 老板容易看懂 (DAU 谁都懂)
④ 不用做真难的事就能涨
```

糖果充盯 DAU 就是典型的**虚荣指标陷阱**——**DAU 涨 30% 让他觉得"我做得不错", 但真正的健康指标 (留存/NPS/对账准确率) 他一个都不知道**。

### 5.2 十个虚荣反例

工程师和产品经理最容易被以下 10 个虚荣指标欺骗:

| # | 虚荣指标 | 为什么是虚荣 | 应该看的可执行指标 |
|---|---------|-------------|------------------|
| 1 | 注册用户总数 | 累加值只涨不跌, 掩盖流失 | 月活用户数 (MAU) |
| 2 | 页面 PV | 可能是刷不到内容反复刷 | 用户完成关键动作次数 |
| 3 | 下载量 | 下载 ≠ 使用 | 首次使用率 + 7 日留存 |
| 4 | DAU | 打开一下就走也算 | 月度成功完成核心动作人次 |
| 5 | 微信公众号阅读 10万+ | 阅读 ≠ 记住 ≠ 行动 | 转发率 + 后续转化 |
| 6 | 系统响应时间平均值 | 平均值掩盖长尾体验 | P95 / P99 响应时间 |
| 7 | 客户签约总额 | 一次性大单可能续约率极低 | 月度经常性收入 MRR + 续约率 |
| 8 | 员工数量 | 团队大 ≠ 战斗力强 | 人均产出 + 项目交付质量 |
| 9 | 代码行数 | 越多可能是越糟 | 功能上线速度 + Bug 密度 |
| 10 | 会议次数 | 开会多 ≠ 决策多 | 决策数 + 决策落地率 |

**结论**: **虚荣指标的共同特征——只看增量, 不看质量; 只看动作, 不看结果**。

### 5.3 可执行四特征

**可执行指标 (Actionable Metrics)** 与虚荣指标相反, 具备四个特征:

```
┌────────────────────────────────────────────────────┐
│           可执行指标的四个特征                       │
├────────────────────────────────────────────────────┤
│  ① 反映因果    指标变化能追溯到具体动作/事件         │
│  ② 反映用户价值 涨了对用户是真好, 不是幻觉           │
│  ③ 可比较     有横向 (竞品) 或纵向 (历史) 参照     │
│  ④ 可干预     团队做具体动作可以让它变化              │
└────────────────────────────────────────────────────┘
```

**判断一个指标是不是可执行的四问**:

```
问 1: 这个指标涨了/跌了, 我能说出至少 3 个具体原因吗?
      (反映因果: 能 → 可执行; 不能 → 虚荣)

问 2: 这个指标涨了, 用户是不是真的更开心/更有价值?
      (反映用户价值: 是 → 可执行; 不是 → 虚荣)

问 3: 这个指标有没有历史对比/竞品对比?
      (可比较: 是 → 可执行; 只有绝对值 → 虚荣)

问 4: 如果这周我们要让它涨 10%, 我们能列出至少 3 个行动吗?
      (可干预: 能 → 可执行; 不能 → 虚荣, 因为你没法影响它)
```

**拿糖果充的候选指标练手**:

| 候选指标 | 因果 | 用户价值 | 可比较 | 可干预 | 判决 |
|---------|:---:|:---:|:---:|:---:|:---:|
| DAU | ✓ | ✗ | ✓ | ✓ | **半虚荣** |
| 月度成功对账人次 | ✓ | ✓ | ✓ | ✓ | **可执行** ★ |
| 注册用户总数 | ✗ | ✗ | ✗ | ✓ | **虚荣** |
| 系统 SLA 可用率 | ✓ | 间接 | ✓ | ✓ | **可执行 (护栏)** |
| PV | ✗ | ✗ | ✓ | ✓ | **虚荣** |
| 客户 NPS | ✓ | ✓ | ✓ | ✓ | **可执行** ★ |
| 客户续约率 | ✓ | ✓ | ✓ | ✓ | **可执行** ★ |

## 6. 指标四层落地

有了北极星、AARRR、可执行指标的知识后, 现在拿糖果充的产品**完整搭一遍指标四层**:

### 6.1 北极星层

```
北极星: 月度成功完成对账人次
定义:   一位用户在一个月内完成一次"月度对账关闭"操作 = 1 人次
        (关闭 = 已核对完毕 + 数据锁定 + 无重开)
目标:   Q4 达到 40 人次/月 (当前 25)

三标准验证:
✓ 用户真价值: 完成关闭 = 真的对完账, 是核心业务价值
✓ 商业健康:   客户续约的直接驱动 (客户对账门户核心 KPI)
✓ 可影响:     发票识别/门户/摘要功能都影响它
```

### 6.2 一级指标层

一级指标 = 直接影响北极星的**3-5 个驱动指标**:

```
一级指标 1: 月度活跃用户数 (MAU)
   逻辑: 用户不来就不可能完成对账
   目标: Q4 达到 500 (当前 390)

一级指标 2: 首次对账成功率
   逻辑: 新用户第一次能不能完整跑通对账流程
   目标: Q4 达到 60% (当前 30%)

一级指标 3: 平均对账周期时长
   逻辑: 对账越快, 用户越愿意在系统里完成
   目标: Q4 从 3 天缩短到 1 天

一级指标 4: 用户次月留存率
   逻辑: 留不住的用户永远完成不了下月对账
   目标: Q4 达到 65% (当前 45%)

一级指标 5: 客户 NPS
   逻辑: NPS 高 = 长期用 + 主动推荐 = 更多完成对账
   目标: Q4 达到 7 (当前 6)
```

**注意**: 一级指标之间**互相印证**——都涨意味着北极星稳涨; 只有 MAU 涨其他都跌, 意味着 DAU 是虚荣涨。

### 6.3 二级指标层

二级指标 = 影响一级指标的**具体归因指标**(10-20 个):

```
影响 [MAU]:
  - 新用户注册数
  - 现有用户次日登录率
  - 用户流失预警 (30 天未登录数)

影响 [首次对账成功率]:
  - 新用户引导完成率
  - 首次上传发票成功率
  - 首次遇到错误的分布 (发现引导缺口)

影响 [平均对账周期时长]:
  - 发票识别平均耗时
  - 用户手动修正次数
  - 数据加载 P95

影响 [用户次月留存]:
  - 用户月度使用次数分布
  - 核心功能使用广度 (用了 N 个功能中的几个)
  - 主动上报错误数 (证明还在深度使用)

影响 [NPS]:
  - 各功能满意度分项
  - 用户投诉响应时长
  - Feature Request 采纳率
```

### 6.4 护栏指标层

护栏指标 = **不能被牺牲的底线**(5-10 个):

```
质量护栏:
  🛡 对账准确率 ≥ 99.5%
  🛡 服务可用性 ≥ 99.9%
  🛡 P95 响应时间 ≤ 500ms
  🛡 系统崩溃率 ≤ 0.01%

安全护栏:
  🛡 数据泄露事件 = 0
  🛡 权限越权访问 = 0

合规护栏:
  🛡 财务数据保留 ≥ 7 年
  🛡 审计日志完整率 = 100%

用户体验护栏:
  🛡 用户投诉响应时长 ≤ 24h
  🛡 严重 Bug 修复时长 ≤ 48h
```

**护栏的重要性**: 一级指标激进地涨, 但护栏破了, 就是"涨得不健康"。糖果充 V1 只有 SLA 一个护栏, **对账准确率、用户投诉响应、数据保留合规都是盲区**——一旦哪个爆雷就是重大事故。

**四层完整可视化**:

```
┌───────────────────────────────────────────────────────┐
│  北极星: 月度成功完成对账人次 = 40 (target)              │
├───────────────────────────────────────────────────────┤
│  一级指标 (5 个):                                       │
│  MAU 500  |  首次成功 60%  |  周期 1天  |  留存 65%     │
│                        NPS 7                            │
├───────────────────────────────────────────────────────┤
│  二级指标 (15+ 个):                                      │
│  新增/流失/首次引导/识别耗时/月度频次/满意度分项/...     │
├───────────────────────────────────────────────────────┤
│  护栏指标 (10 个):                                       │
│  准确率/可用性/P95/安全/合规/投诉响应/Bug 修复           │
└───────────────────────────────────────────────────────┘
```

**看板节奏**:

```
北极星: 月度会评审 (老板 + 团队)
一级:  周会评审 (团队 Leader)
二级:  日看板 (模块负责人)
护栏:  实时告警 (值班 on-call)
```

## 7. 埋点设计规范

**四层指标是产品的语言, 埋点是工程师的语言**。作为工程师, 你落地指标体系的关键是**做好埋点**。

**埋点四大规范**:

**规范 1: 事件命名**

```
❌ 错误命名: 
  click_button_1
  page_view
  action

✅ 正确命名 (动词_对象_场景):
  submit_reconcile_close     (提交对账关闭)
  view_invoice_recognition   (查看发票识别页)
  click_export_pdf           (点击导出 PDF)

命名规则:
- 全小写 + 下划线分隔
- 动词开头 (view / click / submit / complete)
- 对象具体 (不是 button, 而是 reconcile_close)
- 加场景 (identify_which_page)
```

**规范 2: 事件属性**

每个事件应该带**上下文属性**, 方便后续分析:

```json
{
  "event": "submit_reconcile_close",
  "user_id": "u_12345",
  "user_role": "finance_staff",
  "reconcile_month": "2019-09",
  "reconcile_type": "monthly",
  "invoice_count": 234,
  "error_count": 2,
  "manual_correction_count": 5,
  "duration_seconds": 3600,
  "device": "web",
  "timestamp": "2019-09-30T18:00:00Z"
}
```

**属性设计原则**:
- **who**: user_id / user_role / team_id
- **what**: 事件对象的具体上下文 (invoice_count, reconcile_month)
- **how**: 用户是怎么完成的 (manual_correction_count 反映困难程度)
- **when/where**: timestamp / device / page_path

**规范 3: 去重与幂等**

```
问题: 用户网络抖动导致同一动作触发 3 次埋点
解决: 
- 客户端本地去重 (10 秒内同一 event + user 只发 1 次)
- 服务端幂等 (基于 idempotency_key)
- 数据平台去重 (基于 event_id 唯一约束)
```

**规范 4: 埋点版本管理**

```
问题: 埋点定义修改后, 老数据和新数据不一致
解决:
- 每个事件带 schema_version
- 修改事件属性时, 保持向后兼容 (不删旧字段, 只加新字段)
- 重大结构变更时, 使用新事件名 (v2 后缀)
```

**埋点设计流程**:

```
① 产品/数据: 定义指标 (北极星/一级/二级/护栏)
   ↓
② 工程师: 拆解成埋点事件清单
   ↓
③ 工程师+数据: 定义事件 schema (name + 属性 + 版本)
   ↓
④ 工程师: 编码实现 + 测试用例
   ↓
⑤ 数据: 验证数据流 + 建看板
   ↓
⑥ 全员: Review 数据是否能算出目标指标
```

**结论**: **埋点是工程师能"参与产品决策"的最有力工具**。埋点做得好 = 团队有靠谱数据 = 决策靠数据不靠嘴; 埋点乱做 = 数据不准 = 谁嗓门大听谁的。**工程师主导埋点规范 = 工程师主导数据文化**。

## 8. 指标反模式

工程师做指标最容易犯的 8 个反模式:

| 反模式 | 症状 | 危害 | 修复 |
|--------|------|------|------|
| 只看虚荣指标 | 天天盯 DAU/PV/注册数 | 盯错方向, 白努力 | 用四问法过滤, 建立北极星 |
| 指标一堆无优先级 | 30 个指标同等看 | 团队被稀释, 抓不住重点 | 分四层, 北极星只 1 个 |
| 只看总数不看分层 | 只有一个总平均值 | 掩盖长尾问题 | P95/P99 + 分群 (新老/角色/场景) |
| 没有护栏 | 拉北极星不管质量 | 涨的畸形, 早晚翻车 | 5-10 个护栏底线 |
| 埋点乱设 | 事件名/属性无规范 | 数据没法交叉分析 | 严格命名 + schema 版本管理 |
| 只看不做 | 数据看板漂亮, 没行动 | 数据成摆设 | 每周基于数据决策 3 件事 |
| 指标不复盘 | 指标定好就不改 | 阶段变化后指标失效 | 每季度复盘一次指标合理性 |
| 老板要哪个看哪个 | 汇报导向的指标 | 团队被临时性指标带偏 | 有稳定的四层, 老板问的临时看 |

**结论**: 这 8 条覆盖了工程师做指标 95% 的翻车场景。做完指标体系后自检一遍。

## 9. 给不同岗位的话

**如果你是做硬件的**: 硬件产品的北极星通常不是 DAU (硬件用户使用频率天然低), 而是**"用户满意度 NPS"** 或 **"设备正常使用率"**。**留存指标**在硬件里变形为**"使用天数占持有天数的比例"**——用户买了设备是每天用还是买回家就落灰? 这才是硬件产品健康度。**护栏指标**在硬件里尤其重要——**故障率、召回率、售后响应时长**, 一个爆点就是重大商业事件。**硬件铁律**: **北极星就一个, 护栏必须硬, 因为返厂太贵了**。

**如果你是做算法的**: 算法工程师最容易只看**技术指标** (准确率/召回率/F1), 完全没看**业务指标**。真正的算法产品北极星是**"用户接受推荐/结果的比例"** 或 **"用户没有绕过算法自己找答案的比例"**。**留存指标**在算法里是**"用户对算法结果的信任度"**——用户是不是每次都要重新验证一遍? 那就是算法没得到信任。**护栏指标**必须有**"badcase 数"、"用户投诉数"、"人工兜底介入率"**——一次严重 badcase 可能引发 PR 危机。**算法铁律**: **业务指标 > 技术指标, 用户信任 > 模型精度**。

**如果你是做运维 / SRE 的**: 运维平台的北极星是**"研发同事一次性上线成功率"** 或 **"故障平均恢复时长 MTTR"**。**留存指标**变形为**"研发主动使用工具的比例 vs 被迫使用"**——工具好用不好用, 看研发是不是主动用。**护栏指标**是**"重大故障数、跨部门事故传播率、on-call 半夜叫醒次数"**——运维产品做得好 = 半夜大家都能睡觉。**运维铁律**: **减少 3 点被叫起来的次数 > 一切炫酷仪表盘**。

**如果你在传统行业 (银行/制造/政企/医疗)**: 传统行业的指标最容易被"任务完成率"绑架——**"KPI 完成 100%"** 但用户实际不满意。真正健康的北极星是**"用户 (客户/员工/公众) 有没有主动推荐/使用/回访"**。**留存指标**在传统行业尤其难做——**用户来了不来是政策/合规决定的, 不是产品决定的**——但你可以看**"用户超出规定使用次数的比例"** 或**"用户主动填反馈问卷的比例"**, 这才反映真价值。**护栏指标**必须包含**"合规审计通过率、投诉响应时长、数据泄露事件"**。**传统行业铁律**: **反映用户真实感受的间接指标 > 完成规定动作的直接指标**。

## 10. 综合案例

### 10.1 重建指标体系

回到糖果充。被 A 总在季度会上问懵后, 他找老周喝了一次咖啡, 老周只讲了三句话:

```
老周: "第一句, DAU 涨 30% 说明有更多人来敲门, 
      但不说明来敲门的人真的进屋了, 更不说明进屋的人喜欢屋子。

     第二句, 你要建的不是数据看板, 是产品的仪表盘 + 方向盘。
     仪表盘告诉你速度, 方向盘决定你去哪里。
     
     第三句, 找到你的北极星, 然后往它走。中间的所有指标只是路标, 
     不是目的地。"
```

糖果充回去做了一件事: **推倒重来, 建四层指标体系**。

**第一步: 找北极星** (花了 3 天)

- 团队讨论 + 用户访谈 + 三标准验证
- 候选: DAU / 完成对账人次 / 客户续约率 / 用户 NPS
- 最终选定: **"月度成功完成对账人次"** (兼顾用户价值 + 商业健康 + 团队可影响)
- 目标: Q4 达到 40 人次 (当前 25)

**第二步: 拆一级指标** (花了 2 天)

- 5 个一级指标: MAU / 首次成功率 / 对账周期时长 / 次月留存 / 客户 NPS
- 每个指标明确目标值 + 周会评审节奏

**第三步: 拆二级指标 + 护栏** (花了 3 天)

- 二级指标 15 个 (按一级指标分组)
- 护栏指标 10 个 (质量 4 + 安全 2 + 合规 2 + 体验 2)

**第四步: 埋点规范化 + 数据看板** (花了 1 周)

- 事件命名规范化 (从旧的 button_click_1 升级到 submit_reconcile_close)
- Schema 版本管理
- 三层数据看板 (北极星月度会 / 一级周会 / 二级日看板 / 护栏实时告警)

**第五步: 用户投诉响应机制** (花了 3 天)

- 之前李姐上报错误 2 周无响应 → 补上 24 小时护栏机制
- 建工单系统 + 自动流转 + 责任人 + SLA

**四层指标体系上线后, Q4 数据**:

```
北极星 (月度成功对账人次):
  Q3 结束: 25
  Q4 结束: 42 (超目标)

一级指标:
  MAU:               390 → 480     (+23%)
  首次成功率:         30% → 62%    (+107%)
  对账周期时长:       3 天 → 1.2 天 (-60%)
  次月留存:           45% → 68%    (+51%)
  客户 NPS:           6 → 7.5      (+25%)

护栏指标:
  对账准确率:         99.2% → 99.7%  ✓
  P95 响应:          800ms → 380ms  ✓
  用户投诉响应:       2 周 → 8 小时   ✓ (改进最大)
```

**下一次季度会 (Q4)**, A 总的反馈:

```
A 总: "小杨, 这次你带来的是一份'仪表盘', 不是'成绩单'。
      我一眼看到北极星, 一眼看到 5 个驱动指标, 一眼看到 10 个护栏。
      更重要的是, 我看得到 Q3 到 Q4 每个指标的变化 + 每个变化背后的动作。
      这就是我要的季度会。"

糖果充: (这次说得出话了)
```

### 10.2 指标能力回望

回望糖果充这次翻车 + 重建的全过程, **数据指标能力**的本质是:

```
初级:  只看别人做好的看板, 关心"数字大不大"           (数据消费者)
中级:  会看几个基础指标, 但不知道谁重要                (半懂状态)
高级:  能设计北极星 + 一级指标, 会用 AARRR             (指标设计者)
资深:  四层完整体系 + 埋点规范 + 数据文化               (数据主导者)
大师:  用数据驱动整个团队做决策, 数据 = 语言             (数据文化建设者)
```

**数据指标的四个心法**:

```
① 一个团队一个北极星, 一个北极星统所有
② 看得漂亮 ≠ 做得健康, 虚荣指标是甜蜜的毒药
③ 留存优先于拉新, 漏水的桶再多水也留不住
④ 有护栏才有健康增长, 无护栏的涨是畸形涨
```

**数据指标的哲学**: **仪表盘 ≠ 方向盘**。数据不会告诉你"该往哪里去", 数据只会告诉你"你在哪里, 你走得多快"。**方向是你自己定的 (北极星), 数据只是印证方向对不对**。

**数据的另一句名言**: **"数据只会回答你问的问题。你若问错问题, 它会用一个完美的错误答案奖励你。"** 这就是虚荣指标的本质——**你没问对问题, DAU 就用完美的答案骗你三个月**。

### 10.3 速查与练习

**指标体系自检卡** (每季度做一次):

```
□ 1. 我有明确的北极星指标吗? 只有一个吗?
□ 2. 北极星通过了三标准 (用户价值/商业健康/团队可影响)?
□ 3. 我有 3-5 个一级指标吗? 都能影响北极星吗?
□ 4. 我有 10-20 个二级指标吗? 覆盖一级指标的归因吗?
□ 5. 我有 5-10 个护栏指标吗? 覆盖质量/安全/合规/体验?
□ 6. 我的埋点有命名规范 + schema 版本管理吗?
□ 7. 每周基于数据做至少 3 个决策吗? 还是数据看完就忘?
□ 8. 我用四问法过滤过虚荣指标吗? 团队不再盯 DAU 了吗?
```

**指标体系速查表**:

| 场景 | 动作 |
|---|---|
| 想设计新指标体系 | 先定北极星, 再往下拆 |
| 团队盯着 DAU/PV 看 | 用四问法诊断, 大概率是虚荣 |
| 一级指标涨了 | 看二级归因, 看护栏没破 |
| 一级指标跌了 | 优先看留存 (漏水的桶) |
| 老板问付费/续约 | 有对应的一级或二级指标可答 |
| 埋点不规范 | 从事件命名 + schema 版本开始 |
| 数据看板漂亮但无行动 | 每周固定 3 个基于数据的决策 |
| 拉新和留存冲突 | 先做留存 (RARRA), 拉新是后置 |

**30 天指标练习**:

```
Week 1 (北极星定义):
  拿你负责的产品, 走完"找北极星四步法":
  ① 定义用户价值时刻
  ② 找到价值动作
  ③ 定义指标
  ④ 三标准验证
  和团队 3 位讨论, 直到达成共识

Week 2 (指标体系四层):
  基于北极星, 拆 3-5 个一级指标
  基于一级, 拆 10-20 个二级指标
  独立列 5-10 个护栏指标
  验证: 每层指标都能算出数字吗? 有归属人吗?

Week 3 (虚荣指标清理):
  拿团队当前看的所有指标, 逐个用四问法过滤
  找出至少 5 个虚荣指标, 集中在团队会上"退休"
  用可执行指标替换

Week 4 (埋点 + 看板):
  重新审视一个模块的埋点:
  ① 事件命名是否规范?
  ② 属性是否包含 who/what/how/when?
  ③ 版本管理是否有?
  ④ 数据能算出目标指标吗?
  搭一个新看板, 一级指标周会用
```

**练完 30 天你会得到什么**:
- 一份属于你团队的**四层指标体系文档**
- 一种反射: **听到"涨了 X%" 先问"哪个指标, 是不是虚荣的"**
- 一种自信: **敢在老板面前用北极星 + 归因回答任何"产品健康度"问题**
- 一种能力: **主导团队从"数据消费者"升级为"数据决策者"**
