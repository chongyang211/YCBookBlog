## 引子 · 凌晨三点的 API Key 事件

小李某天早上上班，看到 GitHub 邮件：「**Your API Key has been exposed on a public repository**」。

他打开日志——**AWS 账单已经飙升到 5000 美元**。一个匿名黑客用他昨天不小心 push 的 AWS Access Key，跑了一夜的 EC2 挖矿。

小李手忙脚乱地把敏感 commit 删了、`push --force` 覆盖了远程——但 API Key 已经泄露十几个小时了。他花了一整晚：

1. 到 AWS 后台**立刻吊销**那把 Key。
2. 生成新的 Key，全项目替换。
3. 用 `git filter-repo` **重写整个 Git 历史**，把敏感文件从每一个 commit 里抹掉。
4. 强制推送到远程，让所有队友重新 clone。
5. 联系 AWS 支持申请赔偿——**这次亏损了 3000 美元**。

**这一夜，让小李把「Git 事故预案」写进了团队 Wiki 的头版**。

## 二、灾难急救的四步心法

发生任何 Git 事故，请**先深呼吸，再执行下面四步**——90% 的事故按这四步都能救回来。

**第 1 步 · 冷静**（30 秒）
- **不要再敲任何命令**。
- 关掉终端窗口。
- 泡杯茶。

**第 2 步 · 备份**（1 分钟）

```bash
# 把整个仓库目录复制一份——一切救援都从这个副本开始
cp -r my-project my-project-backup
```

**第 3 步 · 侦查**

```bash
git status
git log --oneline --all --graph
git reflog                       # 最关键的一条
```

**第 4 步 · 精确出手**

**从下面十大事故里找到对应小节，按步骤操作**。

**⚡ 铁律**：**任何救援命令，都在备份上先试一遍**。

## 三、常见事故急救手册

### 3.1 手滑 `reset --hard`，代码没了

**症状**：跑了 `git reset --hard HEAD~N`（或类似），突然发现代码没了。

**救命三步**：

```bash
# 1. 看 reflog，找到「消失前」的 commit
git reflog
# 会看到：
# abc123 HEAD@{0}: reset: moving to HEAD~1     ← 就是这条毁了我
# def456 HEAD@{1}: commit: my precious work    ← 我要救的 commit！

# 2. 一步救回来
git reset --hard HEAD@{1}
# 或直接
git reset --hard def456
```

**⚠️ 前提**：**你至少 commit 过一次**。**从没 commit 的工作区改动，reflog 也救不回**——因为 reflog 只记录 HEAD 移动，不记录工作区变化。

**关键洞察**：Git 的所有 commit 至少保留 **30 天**（`gc.reflogExpireUnreachable` 默认 90 天）——所以哪怕昨天的手滑，明天来救也来得及。

### 3.2 误 commit 了敏感信息（API Key / 密码）

**⚠️ 这是最严重的事故——因为它会传播**。**看到的第一秒钟就要立刻行动**。

**第一优先级：吊销密钥**（不是删代码）

```bash
# 立刻！去对应平台后台吊销那把 Key
# AWS / GCP / Azure / GitHub Token / npm Token / 数据库密码……
```

**只删掉 commit 不够**——只要历史里存在过，就假定它已被爬虫爬走。**唯一安全的做法是吊销 + 换新**。

**第二步：清除 Git 历史**（推荐 `git filter-repo`）

```bash
# 安装
pip install git-filter-repo

# 备份仓库（做任何 filter-repo 之前都要备份）
cp -r my-project my-project-backup

# 从所有历史中删除某个文件
cd my-project
git filter-repo --path config/secrets.yml --invert-paths

# 或按内容替换（把某个字符串替换成 REDACTED）
git filter-repo --replace-text <(echo 'AKIAIOSFODNN7EXAMPLE==>REDACTED')

# 强制推送到远程（⚠️ 团队需要全部重新 clone）
git push --force --all
git push --force --tags

# 通知所有协作者
```

**第三步：从远程平台后台请求彻底删除**

- GitHub：Settings → Contact Support → 请求删除敏感数据的缓存。
- GitLab：类似流程。

**⚡ 防患于未然**（更重要）：

```bash
# 安装 pre-commit hook 扫敏感信息
npm install --save-dev @secretlint/secretlint-rule-preset-recommend secretlint

echo 'npx secretlint "**/*"' > .husky/pre-commit
```

**推荐工具**：
- **[gitleaks](https://github.com/gitleaks/gitleaks)**：扫历史和当前的敏感信息。
- **[git-secrets](https://github.com/awslabs/git-secrets)**：AWS 官方，防 AWS Key 泄露。
- **[trufflehog](https://github.com/trufflesecurity/trufflehog)**：深度扫描 + 熵检测。

### 3.3 误 commit 了 100MB 的大文件

**症状**：push 失败——GitHub 单文件限制 100MB。

**如果还没 push**：

```bash
# 找到大文件所在的 commit
git rev-list --objects --all | \
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | \
  awk '$1=="blob"' | sort -k3 -n | tail -10

# 用 filter-repo 从历史中删除
git filter-repo --path big-file.zip --invert-paths
```

**长期方案：用 Git LFS**（大文件存储）

```bash
git lfs install
git lfs track "*.psd" "*.mp4" "*.zip"
git add .gitattributes
git add big-file.psd
git commit -m "feat: add design asset"
git push
```

**LFS 的工作原理**：Git 里只存**一个指针文件**（几十字节），真实文件存到 LFS 服务器。

**⚠️ 提示**：LFS 有流量和存储配额（GitHub 免费版每月 1GB 流量 + 1GB 存储）。大团队要注意成本。

### 3.4 冲突解错了，代码乱套

**症状**：merge 后测试挂了、代码逻辑变了——冲突解错了。

**如果还没 commit**：

```bash
git merge --abort               # 中止 merge，回到合并前状态
git rebase --abort              # 中止 rebase
```

**如果已经 commit（还没 push）**：

```bash
git reset --hard HEAD~1         # 回到合并前
git merge origin/other --no-ff  # 重新合并
# ⚠️ --hard 会丢工作区改动，先 stash
```

**如果已经 push 了**（公共分支）：

```bash
# 不能 reset --hard 强推——会毁掉别人的历史
# 生成一个反向 commit
git revert -m 1 <merge-commit-id>
git push
```

**`revert -m 1` 的含义**：反做一个 merge commit，`-m 1` 表示「保留第一个父提交（也就是当前分支）的状态」。

### 3.5 detached HEAD，工作丢了

**症状**：`git checkout abc123` 之后写了一些代码，`git commit` 了几次——然后 `git switch main`，代码没了。

**原理**：detached HEAD 状态下的 commit 没有分支指着，切走后就成了「孤儿」。**但它们还在 objects 里**——用 reflog 能找到。

**救命**：

```bash
git reflog
# 找到 detached HEAD 时期的最后一个 commit
git switch -c rescue-branch abc123
# 用它建一个分支，工作就回来了
```

**长期习惯**：**detached HEAD 状态下要工作，先 `git switch -c new-branch`** 建分支。

### 3.6 `git commit --amend` 之后 push 失败

**症状**：改了上一个 commit 的 message 或补了文件，然后 push——被拒绝。

**原理**：`amend` 生成了一个**新 commit**（SHA-1 变了），远程还是旧的——不是快进关系。

**如果 commit 还没被别人 fetch**（比如你的个人 feature 分支）：

```bash
git push --force-with-lease           # 安全强推
```

**如果 commit 已经被别人 fetch/pull 了**（公共分支）：

**不要 `amend`，不要 `--force`**——**接受这次「多一个 commit」的事实**：

```bash
# 撤销 amend
git reset --soft HEAD@{1}
# 重新做一个正常的 commit
git commit -m "fix: correct typo (addendum)"
```

**这就是「已 push 的 commit 永不 amend」的原因**——一 amend 就变成公开事件。

### 3.7 merge 到了错误的分支

**症状**：本来要 `merge feature-a` 到 `develop`，手滑合到了 `main`。

**如果还没 push**：

```bash
git reset --hard HEAD@{1}       # reflog 回到合并前
```

**如果已经 push**：

```bash
git revert -m 1 <merge-commit-id>
git push
```

**永远不要在公共分支上 reset + force push**——用 revert。

### 3.8 `.gitignore` 不生效

**症状**：写了 `.gitignore`，但某个文件还是被跟踪。

**原理**：`.gitignore` 只对 **untracked 文件**生效——**如果文件已经被 tracked，加 .gitignore 也没用**。

**解决**：

```bash
# 从跟踪中移除（但保留工作区文件）
git rm --cached my-file.log
git commit -m "chore: stop tracking log files"

# 现在 .gitignore 就生效了
```

**批量处理**（比如整个目录）：

```bash
git rm -r --cached node_modules/
git commit -m "chore: gitignore node_modules"
```

### 3.9 SSH 连不上 / permission denied

**症状**：`git push` 报 `Permission denied (publickey)`。

**排查五步**：

```bash
# 1. 测试 SSH 连接
ssh -T git@github.com
# 期望：Hi username! You've successfully authenticated

# 2. 看看有没有 SSH key
ls -la ~/.ssh/
# 期望能看到 id_ed25519 和 id_ed25519.pub

# 3. 看看公钥是否加到了 GitHub 后台
cat ~/.ssh/id_ed25519.pub
# 把内容对比 GitHub → Settings → SSH Keys 里的

# 4. 看看 ssh-agent 是否加载了 key
ssh-add -l
# 如果没加载：
ssh-add ~/.ssh/id_ed25519

# 5. 检查 remote URL 是不是 SSH 格式
git remote -v
# 应该是 git@github.com:... 而不是 https://...
git remote set-url origin git@github.com:user/repo.git
```

**特殊场景：多个 GitHub 账号**——用 `~/.ssh/config`：

```
Host github-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_personal

Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_work
```

对应的 remote URL 改成：`git@github-personal:user/repo.git`。

### 3.10 仓库越用越大、越用越慢

**症状**：`.git/` 目录动辄几个 GB，`git status` 都要卡几秒。

**排查**：

```bash
# 看仓库大小
du -sh .git

# 找出最大的对象
git rev-list --objects --all | \
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | \
  awk '$1=="blob"' | sort -k3 -n | tail -10
```

**优化四招**：

```bash
# 1. 清理无用引用 + gc
git gc --aggressive --prune=now

# 2. 只保留最近历史（浅克隆）
git clone --depth=1 <URL>

# 3. 从历史中删除大文件（详见 3.3）
git filter-repo --strip-blobs-bigger-than 100M

# 4. 迁移到 Git LFS（针对二进制资产）
git lfs migrate import --include="*.psd,*.mp4"
```

## 四、心智模型剖析：为什么 Git 后悔药特别多

Git 的每一个「后悔药」，都对应它的一个设计特征：

| 后悔药 | 原理 | 保留期 |
|---|---|---|
| **`reflog`** | 每次 HEAD 移动都记日志 | 默认 30~90 天 |
| **对象不删** | commit 用 SHA-1 索引，任何 commit 只要被引用就不会被 GC | 永久（有引用时） |
| **git fsck** | 全量扫描 `.git/objects/`，找出「孤儿」对象 | 只要没 gc 就还在 |
| **stash** | 存在 `refs/stash` 里，明确 drop 才消失 | 手动清理 |

**核心思想**：**Git 不删数据，它只是「不再指向」数据**。所有的「删除」，其实都是「取消引用」。

**只有一件事真的不可逆**：**`git gc --prune=now` 之后**，没有任何引用（reflog / branch / tag / stash）指向的对象，会被物理删除。

**所以**：**只要你 commit 过一次**，30 天内任何操作都有救；**从来没 commit 过的工作区改动**，reset --hard 之后**没救**。

## 五、`git fsck` 与 `git gc`：仓库自检与瘦身

**`git fsck`** —— 检查仓库完整性 + 找孤儿对象：

```bash
git fsck --full
# 输出：dangling commit abc123... （这些是「浮尸」，没引用但还没被 gc）

git fsck --unreachable --lost-found
# 把浮尸放到 .git/lost-found/ 目录（终极救援）
```

**`git gc`** —— 垃圾回收 + 打包：

```bash
git gc                          # 温和的清理
git gc --aggressive             # 深度打包（慢但省空间）
git gc --prune=now              # ⚠️ 立即清理孤儿对象（不可逆！）
```

**⚠️ 用 `--prune=now` 之前**——先 `git fsck` 看看有没有你还想救的对象。

## 六、Git 内部一致性深度剖析：对象校验、dangling、损坏修复

这一节把 `git fsck` 的能力和背后的原理讲透——**当仓库真的坏了，你需要知道 Git 是怎么救的**。

### 6.1 Git 的三大一致性保证

Git 依靠**SHA-1 内容寻址**天然自带三重校验：

**保证一：对象完整性**  
每个对象存的内容 `<type> <size>\0<content>` 经过 SHA-1 计算得到地址。**读取时重算一遍，如果不匹配，就是「对象损坏」**——磁盘错误、传输错误都能发现。

**保证二：引用完整性**  
每个 tree 引用若干 blob 和子 tree，每个 commit 引用一个 tree 和若干父 commit。**只要根 commit 有效，整个可达图都是可校验的**——任何篡改都会导致 SHA 不匹配。

**保证三：历史不可篡改性**  
每个 commit 包含父 commit 的 SHA-1——**篡改任何一个历史 commit，都会让它之后所有 commit 的 SHA 变化**。这就是为什么 Linus 说 Git 是「加密强度的时间机器」。

### 6.2 `git fsck` 能发现什么

`git fsck`（file system check）扫描整个 `.git/objects/`，检查每个对象：

```bash
# 完整扫描（推荐）
git fsck --full

# 更严格（把警告也当错误）
git fsck --strict

# 显示 dangling 对象（无引用的对象）
git fsck --dangling

# 一并检查 reflog 里引用的对象
git fsck --reflogs

# 不网络查询（快）
git fsck --no-progress --no-fetch
```

**能发现的问题**：

| 现象 | 意义 |
|---|---|
| **missing** | 引用的对象文件不存在——磁盘丢失或人为删除 |
| **corrupt** | 对象文件存在但 SHA-1 校验失败——磁盘损坏或恶意篡改 |
| **broken link** | 某个 tree 引用了不存在的 blob |
| **dangling commit / blob / tree** | 存在但没有任何引用能到达——通常是 amend / reset 留下的孤儿 |
| **unreachable** | 与 dangling 类似，但更严格（不可从任何 ref 到达） |

**注意**：**dangling 不是错**——它是 gc 的正常回收目标。**missing 和 corrupt 才是真错**。

### 6.3 dangling 对象：不是错误，是「等着被回收的孤儿」

**什么是 dangling**？——**没有任何 ref 或其他对象指向它**的对象。

**dangling 的三个来源**：

1. **`git commit --amend`**——旧 commit 变成孤儿。
2. **`git reset` / rebase**——被跳过的 commit 变成孤儿。
3. **删除分支后 commit 没被别人引用**。

**dangling 对象保留多久**？——**默认 90 天**（`gc.pruneExpire`）。之后 `git gc` 会真的删掉。

**利用 dangling 救数据**：

```bash
# 找出所有 dangling commit
git fsck --dangling | grep commit

# 查看某个 dangling commit
git show <SHA>

# 恢复：把它拉回一个分支
git branch recovered-work <SHA>
```

### 6.4 gc 时间线：Git 什么时候真的删数据

**Git 的「删除」是分层的**——它不会立刻真删，给你充分的救援窗口：

```
第 0 天：你做了危险操作（reset --hard、amend）
   ↓
   相关对象变成 dangling
   ↓
第 30 天：reflog 中的 unreachable 条目过期
   ↓
   (gc.reflogExpireUnreachable = "30 days" 默认)
   ↓
第 90 天：gc 会清理 unreachable 且 dangling 的对象
   ↓
   (gc.pruneExpire = "2 weeks" 默认，但需要满足其他条件)
   ↓
   对象真的从磁盘删除，无法恢复
```

**触发 gc 的条件**：

- 手动：`git gc`
- 自动：当松散对象超过 `gc.auto`（默认 6700）时，某些命令（commit、fetch）会顺便触发 `gc --auto`
- 强制立即：`git gc --prune=now --aggressive`（**危险！立即删除所有 unreachable**）

**紧急救援窗口**：

```
你 reset --hard 之后：
├── 0-30 天：reflog 完整可用 → 100% 能救
├── 30-90 天：reflog 已过期但对象还在 → 需要 fsck 找 dangling → 90% 能救
├── 90 天后：可能已被 gc 清理 → 只能从远程或同事那里找回
└── 从未推送过 + 已 gc → 彻底没了
```

### 6.5 损坏仓库的修复流程

**症状**：`git status` 报错 `object <SHA> is corrupt` 或 `bad object <SHA>`。

**修复步骤**：

**Step 1 · 确认损坏范围**

```bash
git fsck --full 2>&1 | tee fsck.log
grep -E "^(missing|corrupt)" fsck.log
```

**Step 2 · 尝试从远程或同事拉回缺失对象**

```bash
# 有幸远程有完整对象
git fetch origin

# 缺失特定 pack 时
git repack -a -d
```

**Step 3 · 从其他 clone 手工补对象**

```bash
# 从同事那里 rsync 特定对象过来
scp colleague:their-repo/.git/objects/ab/cdef... .git/objects/ab/

# 或者用 git bundle 打包他仓库的所有对象过来
# 在他那儿：
git bundle create backup.bundle --all
# 传过来后：
git bundle unbundle backup.bundle
```

**Step 4 · 最坏情况：抢救可用数据 → 重建仓库**

```bash
# 1. 找出所有还能读的 commit（fsck 不报 missing 的那些）
git fsck --lost-found
# → 会把 dangling 对象写到 .git/lost-found/ 目录

# 2. 手工从 lost-found 里挑关键 commit
ls .git/lost-found/commit/
git show <SHA>

# 3. 建新分支
git branch salvaged-<name> <SHA>

# 4. 如果 .git 完全没救了，从新 clone 一份，把工作区文件 cp 过去
```

### 6.6 SHA-1 碰撞演习（进阶）

想验证 Git 对 SHA-1 碰撞的防御？——**下载 SHAttered 的两个 PDF**（<https://shattered.io/>），尝试 add 到同一个仓库：

```bash
git add shattered-1.pdf
git commit -m "first"
git add shattered-2.pdf   # 这一步会失败！
# error: <SHA> is corrupt (SHA-1 mismatch)
```

Git 会**主动识别 SHAttered 特征并拒绝**。这是 Git 2.13.1（2017 年 6 月）加入的防御。你可以亲眼验证。

> **⚡ 一句话**  
> **Git 是自我校验的时间机器**——即使磁盘悄悄翻转一位，fsck 也能发现。**这是 Linus 用 SHA-1 换来的最深礼物**。

## 七、真实事故复盘：那些改变行业的 Git 灾难

历史上有几起著名的 Git / 版本控制事故，**改变了整个行业的最佳实践**。学习它们，比听十遍教条都管用。

### 7.1 GitLab 2017 · 数据库删库事件（史诗级）

**时间**：2017 年 1 月 31 日晚上 11 点。

**经过**：
1. GitLab 生产数据库主库压力过大，运维 YP 决定在从库上恢复。
2. 恢复过程中，YP 敲错命令——**`sudo rm -rf` 到了主库的数据目录**。
3. 300 GB 生产数据在 2 秒内消失。
4. **然后发现**：所有五种备份机制**都不可用**——
   - LVM 快照？没配。
   - Azure 磁盘快照？没配。
   - pg_dump？空文件。
   - Amazon S3 备份？404。
   - Regular backup？没跑。

**结果**：**约 6 小时数据丢失**，700 多个仓库、5000 个 commit 永远消失。

**GitLab 的做法**（教科书级公关）：
- **全程直播恢复过程**（YouTube 5 万人围观）。
- **发布详尽的 post-mortem**（<https://about.gitlab.com/blog/2017/02/10/postmortem-of-database-outage-of-january-31/>）。
- **公开所有内部时间线**——错误、慌乱、深夜、绝望，一切透明。
- **发起 The Database Recovery Fund**——补偿受影响用户。

**行业启示**：
- **备份不测试等于没备份**——GitLab 的五种备份都有，但都没验证过恢复流程。
- **危险命令要加人机确认**——`rm -rf` 应该有二次校验。
- **透明比掩盖更有力量**——GitLab 因此事件反而获得了社区尊重。

### 7.2 SHAttered · 第一次真实的 SHA-1 碰撞（2017.02）

前文第 02 章已介绍——SHAttered 事件让 Git 团队紧急发布 2.13.1 加入检测。**它是「理论安全」向「工程安全」的分水岭**。

**行业启示**：
- 密码学算法有生命周期——SHA-1 用了 20 年（1995-2017），现在轮到 SHA-256。
- 「不用来防攻击者」不是不加固的理由——Linus 的原始判断被现实推翻。

### 7.3 Uber 2016 · Git 泄露 AWS 密钥事件

**经过**：Uber 前员工在自己的**公开 GitHub 仓库**里，误 commit 了公司 AWS 密钥。攻击者扫描到密钥，登录 AWS S3，**下载了 5700 万用户 + 60 万司机的个人信息**。

**Uber 的后续操作（错误示范）**：
- 支付 10 万美元给攻击者「让他们删数据」（俗称买通勒索者）。
- **对外隐瞒事件 一年**。
- 2017 年新任 CEO 上任后**公开披露**——被美国 FTC 罚款 1.48 亿美元。

**行业启示**：
- **secrets 永远不能进 Git**——用环境变量、密钥管理服务（AWS KMS / Vault）。
- **Git 历史里的密钥必须立刻作废**——即使 revert 掉，历史里还是能翻出来。
- **公开仓库出事影响巨大**——GitHub 现在有 secret scanning，你 push 密钥它会自动通知。

### 7.4 Bitbucket 2020 · 数据中心磁盘故障事件

**经过**：Atlassian Bitbucket 云的一台核心存储服务器磁盘阵列故障——**部分仓库数据损坏**。

**Atlassian 的响应**：
- 从对象级别恢复（`git fsck` + `pack` 重建）。
- 结合 CI 缓存和用户本地 clone 补齐缺失对象。
- **总恢复时间 3 天**——但用户数据 100% 找回。

**行业启示**：
- **Git 的对象寻址天生适合分布式恢复**——每个 clone 都能贡献。
- **对象存储与业务分离**是好设计。

### 7.5 GitHub 2018 · 24 小时降级事件

**经过**：2018 年 10 月 21 日，GitHub 网络分区，**多个数据中心的 MySQL 主从数据不一致**。GitHub 决定放弃部分数据以保一致性——**24 小时内网页版和 API 部分功能不可用**。

**行业启示**：
- **CAP 定理是真的**——网络分区时，你要么保 CP 要么保 AP。
- **透明公关**——GitHub 详尽的 post-mortem 被写进多本 SRE 教材。

### 7.6 你能从这些事故学到什么

1. **备份要定期演练** —— 你的 CI 也应该定期 `git clone` 一次，然后 `git fsck`。
2. **secrets 永远不进 Git** —— 用 `.env` + `.gitignore`。
3. **危险操作前手动 `git bundle` 一份全量备份** —— 5 秒钟的动作，救过无数人。
4. **公开透明 > 掩盖粉饰** —— 你的用户能从你的 post-mortem 感受你的技术诚意。

> **⚡ 一句话**  
> **别人的血泪史，就是你的教科书**。每一起事故都用真金白银换来了教训——**不学它们，就得自己重演**。

## 八、动手实战：亲手制造一场灾难并救回来

**演习一场，胜过看十本书**。跟着敲：

```bash
mkdir git-disaster && cd git-disaster
git init -b main

# 建立一些历史
for i in 1 2 3 4 5; do
  echo "commit $i" > file.txt
  git add . && git commit -m "feat: commit $i"
done

git log --oneline

# ────── 灾难 1：reset --hard ──────
echo "important work" > critical.txt
git add . && git commit -m "feat: critical"

git reset --hard HEAD~3          # 😱 消失了！
git log --oneline                # 少了三个 commit

# 救援
git reflog
LATEST=$(git reflog | head -2 | tail -1 | awk '{print $1}')
git reset --hard $LATEST         # 回来了 ✅
git log --oneline

# ────── 灾难 2：删了分支 ──────
git switch -c important-work
echo "important" > work.txt
git add . && git commit -m "feat: important work"
git switch main
git branch -D important-work     # 😱 分支删了！

# 救援
git reflog
COMMIT=$(git reflog | grep "important work" | head -1 | awk '{print $1}')
git switch -c important-work $COMMIT
git log --oneline                # 分支回来了 ✅

# ────── 灾难 3：commit 了敏感信息 ──────
echo "API_KEY=sk_live_ABC123" > .env
git add .env && git commit -m "chore: env"    # 😱 密钥泄露！

# 救援：不是简单的 rm，要重写历史
# （生产环境用 git filter-repo，此处演示 filter-branch）
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch .env" \
  --prune-empty --tag-name-filter cat -- --all

git log --all --oneline
git show HEAD -- .env            # 应该看不到内容了

# ⚠️ 真实场景下 filter-repo 更快更安全
# 而且必须：
# 1. 到 API 平台吊销 Key
# 2. push --force 到远程
# 3. 通知所有人重新 clone

# ────── 灾难 4：detached HEAD 丢了工作 ──────
FIRST=$(git log --oneline | tail -1 | awk '{print $1}')
git checkout $FIRST              # ⚠️ detached
echo "orphan work" >> file.txt
git commit -am "orphan"          # 😱 没分支！
ORPHAN=$(git rev-parse HEAD)

git switch main
# 现在 orphan commit 好像消失了？

git reflog | head -10            # 但它还在 reflog 里
git switch -c rescue $ORPHAN     # ✅ 救回来了

# ────── 收尾：查看仓库健康 ──────
git fsck --full
git gc --aggressive
```

**这段脚本让你亲身经历四场灾难 + 四次救援**——练手比读一百遍教程都值。

## 九、急救九诫

出事之后，不要慌，把这九条抄下来贴在显示器上：

1. **出事的第一件事——冷静，泡杯茶**。急救过程中犯的二次错误，往往比第一次错误更致命——GitLab 2017 就是活生生的例子。
2. **第二件事——把整个目录整体 `cp -r` 备份一份**。任何救援命令都在**备份上**先试一遍，跑通了再动原仓库。
3. **`git reflog` 是救命第一命令**——只要你曾经 commit 过（而不是只 add 过），90% 的事故它能救。默认保留 30～90 天。
4. **`git fsck --lost-found` 是救命第二命令**——从 orphan blob 里挖出没 commit 但 add 过的内容。
5. **敏感信息泄露——先吊销密钥、再删代码、最后走通报流程**。反过来做等于零。
6. **公共分支不 reset、不 amend、不 force push**——出事用 `revert`。别让你的救援成为别人的灾难。
7. **`git gc --prune=now` 是不可逆核弹**——用之前先 `git fsck --unreachable` 看看会炸掉什么。
8. **`--force` 之前先 `--dry-run`，`--force-with-lease` 优于 `--force`**——它会检查远端有没有别人先 push。
9. **不出事的时候**装好 pre-commit（gitleaks 扫密钥）、LFS（拦大文件）、CI 的 push-protection——**最好的急救是不出事**。

> 前六条应对已发生的事故，第七、八条防止「救援中制造新灾难」，第九条从根本上减少事故。
