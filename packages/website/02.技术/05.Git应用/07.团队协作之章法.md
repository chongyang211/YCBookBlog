## 引子 · 从 5 人到 50 人的团队爆炸

小李的团队从 5 人扩张到 50 人。他一开始很自信——Git 用得那么熟，还怕带团队？

但事情失控得比想象快得多：

- **第一周**：三个人同时改 `main` 分支，冲突不断。
- **第二周**：一个实习生 `push --force` 覆盖了历史。
- **第三周**：一次上线，回滚了 4 小时，因为没人说得清「究竟改了什么」。
- **第四周**：一次紧急 hotfix，找不到「上一个稳定版本」在哪个 commit。
- **第五周**：新人的 commit message 五花八门，无法生成 changelog。

**小李意识到**：**Git 只是工具，工作流才是灵魂**。

那个周末，他花了两天写下团队的《Git 治理白皮书》——**分支模型 + 提交规范 + 审查流程 + CI 门禁**。

从此，团队再没出过这类事故。

## 二、三种主流工作流

**没有最好的工作流，只有最合适的工作流**。选型的核心是**你的团队规模 × 发布节奏 × 产品形态**。

### 2.1 Git Flow：大厂经典

**发明者**：Vincent Driessen（2010 年）  
**适用**：**有明确版本发布**的软件（桌面软件、SDK、多版本维护的 SaaS）。

**五种分支**：

```
   main（生产）  ──┬────────┬─────────┬───────  （每次发布打 tag）
                   │        │         │
   release/1.0 ────┘        │         │
                            │         │
   develop      ────┬────┬──┴──┬────┬─┴─────  （下一个版本的集成分支）
                    │    │     │    │
   feature/x  ─────┘    │     │    │
   feature/y  ──────────┘     │    │
   hotfix/z   ────────────────┴────┘         （紧急修复）
```

**分支的角色**：

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | **生产版本**——每次合入都打 tag、发版 | 永久 |
| `develop` | **下一个版本的集成分支** | 永久 |
| `feature/*` | 单个功能 | 完成即删 |
| `release/*` | 发布准备（改 bug、写文档） | 发版即删 |
| `hotfix/*` | 生产紧急修复 | 修完即删 |

**优点**：结构清晰，多版本维护友好。  
**缺点**：**过于复杂**——对现代持续交付团队来说是负担。

### 2.2 GitHub Flow：轻量迭代

**发明者**：GitHub（2011 年）  
**适用**：**Web 产品、SaaS、快速迭代**的团队。

**只有一条主线 + 短命 feature 分支**：

```
   main ──┬───┬───┬───┬───┬───►
          │   │   │   │   │
          f1  f2  f3  f4  f5   （每个 feature 分支 = 一次 PR = 一次上线）
```

**流程**：

1. 从 `main` 建 feature 分支（几小时到几天，绝不超过一周）。
2. 写代码、多次小 commit。
3. 提 PR → CI 全绿 → review 通过。
4. 合入 `main`（自动或手动触发部署）。
5. 删除 feature 分支。

**优点**：简单、快速、持续交付友好。  
**缺点**：需要**强 CI + 完善测试**——`main` 必须永远可发布。

### 2.3 Trunk-Based Development：极致持续集成

**适用**：**大规模团队 + 高频发布**（Google、Meta 都在用变种）。

**只有 `main`——所有人直接往 main 提交**，用 **Feature Flag** 隔离未完成功能：

```
   main ──┬─┬─┬─┬─┬─┬─┬─┬─┬─►     （所有人的 commit 直接进 main）
                          │
                          └── 每个 commit 都触发 CI + 部署
```

**关键机制**：

- **Feature Flag**：新功能默认关闭，用配置开关控制上线时机。
- **Trunk 永远绿**——CI 挂了要立即修复（10 分钟内）。
- **Very short-lived branch**（如果非要用分支的话），几小时就合。

**优点**：极致的集成频率，减少 merge 冲突。  
**缺点**：**门槛极高**——需要成熟的 CI、Feature Flag 平台、测试覆盖。

### 2.4 三种工作流对比

| 维度 | Git Flow | GitHub Flow | Trunk-Based |
|---|---|---|---|
| **分支复杂度** | 高（5 种） | 低（2 种） | 极低（1 种） |
| **发布节奏** | 定期版本（月/季） | 按需（日/周） | 持续（小时/分钟） |
| **CI 要求** | 中等 | 高 | 极高 |
| **团队规模** | 中小型 | 中小到中大型 | 大型 |
| **产品形态** | 桌面/SDK/多版本 | Web/SaaS | 大型 SaaS |
| **心智负担** | 记 5 种分支 | 记 1 条主线 | 记 Feature Flag |

**⚡ 我的推荐**：**多数团队用 GitHub Flow 就够了**。如果你在多版本维护（比如同时维护 v1、v2、v3），再上 Git Flow。除非你有 Google 的工程实力，不然别碰 Trunk-Based。

### 2.5 GitLab Flow：中庸之道

GitLab 官方在 2014 年提出的**折中方案**——它认为 Git Flow 太复杂，GitHub Flow 又不够管多环境部署（dev / staging / prod）。GitLab Flow 的答案是：**主干 + 环境分支**。

```
main（开发主干）
  ↓ 合入
pre-production（预发）
  ↓ 合入
production（生产）
```

或者按 release 分支：

```
main
  ↓ 分出
2-3-stable（v2.3 版本线）
  ↓ 分出
2-4-stable（v2.4 版本线）
```

- **优势**：环境和分支一一对应，很直观；同时支持多版本维护。
- **劣势**：分支数目膨胀（每个版本一条），需要清晰的 release 流程。
- **适合谁**：**开源项目 + SaaS 混合体**——GitLab 自己就是这么管的。

### 2.6 工作流的演进史与思想根源

这四种工作流不是同时出现的，它们**各自代表了一种时代思潮**：

- **2010 年 · Git Flow 诞生**——作者 **Vincent Driessen**，荷兰工程师，在自己博客发了篇文章《A successful Git branching model》，一夜爆红。当时的软件业还是**季度发布 / 半年发布**的节奏，Git Flow 的「多个长期分支」正好适配。**Driessen 本人 2020 年发了一条更新，坦诚**：「**这个模型是 2010 年 SaaS 尚未普及时设计的。对于今天频繁发布的 SaaS 团队，请用 GitHub Flow 或 Trunk-Based**」——这段自我修正在业界流传甚广。
- **2011 年 · GitHub Flow 出现**——Scott Chacon（GitHub CTO、Pro Git 作者）在博文里推广。它是**GitHub 平台对协作模式的重塑**——不需要 develop 分支，因为「合并到 main 就该能上线」。GitHub Flow 的兴起 = **持续部署（CD）文化的兴起**。
- **2000 年代早期 · Trunk-Based 的地下史**——其实 Trunk-Based 不是新概念。Google 在 2000 年代初期就在用「大家全部 commit 到 trunk」的模式（Perforce 时代），后来迁移到自研的 Piper。**Paul Hammant** 在 2015 年写了《Trunk-Based Development》一书，把这套隐秘的实践正式命名并推广。**理念**：分支是浪费，长期分支是灾难——**「commit 就是集成」**。
- **持续演进 · 三大流派的融合**——今天多数团队用的是**混合体**：小 feature 走 GitHub Flow，大版本走 Git Flow 的 release 分支，热修用 hotfix 短命分支——**没有教条，只有适配**。

> **⚡ 一句话**  
> 工作流没有对错，只有**「你的团队规模、发布节奏、可靠性要求」的最优组合**。选 workflow 就像选衣服——**看场合，不追潮流**。

## 三、分支命名与提交规范

### 3.1 分支命名规范

**推荐模板**：

```
   <type>/<issue-id>-<short-description>
```

**例子**：

- `feat/1234-add-dark-mode`
- `fix/5678-login-crash`
- `chore/upgrade-webpack`
- `hotfix/9999-oom-crash`
- `refactor/split-user-service`

**type 收敛到 6-8 个**：

| 前缀 | 含义 |
|---|---|
| `feat/` | 新功能 |
| `fix/` | 修 bug |
| `hotfix/` | 生产紧急修复 |
| `refactor/` | 重构 |
| `perf/` | 性能优化 |
| `chore/` | 构建/工具/依赖 |
| `docs/` | 文档 |
| `test/` | 测试 |

**⚠️ 反例**：

```
   ❌  xiaoming-dev
   ❌  temp
   ❌  test1、test2、test3
   ❌  new-branch
```

### 3.2 Conventional Commits 深度剖析

第 03 章讲过基础。这里深入到**如何用它自动生成 changelog、决定版本号**。

**完整模板**：

```
<type>(<scope>): <subject>

<body>

<footer>
```

**semantic-release 的自动化魔法**——它读 commit 类型，自动决定版本号：

| commit 类型 | 版本号变化 | 例子 |
|---|---|---|
| `fix:` | patch（1.0.0 → 1.0.1） | fix: correct typo |
| `feat:` | minor（1.0.0 → 1.1.0） | feat: add dark mode |
| `feat!:` / body 里有 `BREAKING CHANGE:` | major（1.0.0 → 2.0.0） | feat!: remove legacy API |

**footer 常用 keys**：

- `Closes #123`：自动关联 issue。
- `Refs #456`：引用（不关闭）。
- `Signed-off-by:`：DCO 签名。
- `BREAKING CHANGE: xxx`：破坏性改动说明。

**一个完整例子**：

```
feat(auth): add SMS-based login

Support China Mobile / Unicom / Telecom.
Add 60s countdown after sending code.

Closes #234
BREAKING CHANGE: removed the old email-only login flow.
```

`semantic-release` 读了这条 commit，会：
- 自动把版本从 `1.5.0` 升到 `2.0.0`（因为有 `BREAKING CHANGE`）。
- 自动生成 CHANGELOG.md 条目。
- 自动打 tag `v2.0.0`。
- 自动发布到 npm / GitHub Release。

**这就是「commit 规范」的复利效应**——**它把混乱的日常提交，变成了自动化流水线的燃料**。

### 3.3 用工具强制规范：commitlint + husky

**规范只有强制才有用**——靠自觉一定会失守。

**三件套配置**（Node 项目）：

```bash
npm install --save-dev husky @commitlint/cli @commitlint/config-conventional

# 初始化 husky
npx husky init

# 配置 commitlint
echo "export default { extends: ['@commitlint/config-conventional'] };" > commitlint.config.js

# 添加 commit-msg 钩子
echo 'npx --no -- commitlint --edit "$1"' > .husky/commit-msg
```

**效果**：

```bash
git commit -m "改了点东西"
# ❌ 直接拒绝提交，报错：
# ⚠ subject may not be empty
# ⚠ type may not be empty
```

**用工具替代人肉审查**——commit 规范从此坚不可摧。

## 四、Code Review 的艺术

Code Review（CR）是团队协作里**成本最低、收益最高**的活动。

**CR 的四个目的**：

1. **抓 bug**——早发现早修，成本指数级下降。
2. **分享知识**——让不写这块的人也懂这块。
3. **对齐规范**——统一代码风格与设计思想。
4. **建立文化**——「代码是团队资产，不是个人财产」。

**PR 提交者的清单**：

- [ ] 一个 PR 只做一件事
- [ ] 单元测试通过
- [ ] 描述清楚：**为什么改**、**改了什么**、**怎么测**
- [ ] 有 UI 改动的附截图 / GIF
- [ ] 关联 issue（`Closes #123`）
- [ ] 自我 review 一遍 diff

**Reviewer 的清单**：

- [ ] 功能是否正确
- [ ] 是否有隐藏 bug（边界、并发、异常）
- [ ] 是否符合团队规范（命名、结构、注释）
- [ ] 是否有更简洁的实现
- [ ] 测试是否充分
- [ ] 有没有安全隐患（SQLi / XSS / 敏感信息）

**Review 沟通的四条心法**：

1. **对事不对人**——「这个函数太长了」 vs 「你写的函数太长了」。
2. **给理由，不下命令**——「用 useMemo 会更好，因为……」 vs 「用 useMemo」。
3. **区分 nit（挑刺）和 must（必改）**——`nit:` 前缀表示「不改也行」，`must:` 表示「必须改」。
4. **审查者不是仲裁者**——分歧上升到团队讨论，别陷入拉锯。

**⚡ 老手秘诀**：**PR 不要大**——300 行以内 reviewer 认真看，1000 行以上普遍「LGTM 但没细看」。**大改动拆多个 PR**。

## 五、CI/CD 与 Git 的联动

**CI/CD** = 「持续集成 / 持续部署」——**让每次 push 都自动走一遍质量门禁**。

**典型 CI 触发点**：

```
   PR 提交    ──▶ CI：跑测试 + 静态检查 + 构建 → 报告结果
   PR 合入 main ──▶ CD：自动部署到测试环境
   打 tag v*  ──▶ CD：自动部署到生产环境
```

**一份最小的 GitHub Actions 配置**（`.github/workflows/ci.yml`）：

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run lint
      - run: npm run test
      - run: npm run build
```

**CI 的四条准则**：

1. **快**——10 分钟以内。慢了大家就懒得等，会绕开。
2. **稳**——不能出「flaky test」（时好时坏）。不然大家开始「盲重跑」。
3. **早发现**——静态检查、类型检查越早越好。
4. **和 PR 深度集成**——不通过 CI，PR 不能合。

## 六、分支保护：团队治理的底线

**GitHub / GitLab 的 Branch Protection Rules**——`main` 分支的最后一道防线：

**必配的四条**：

- [x] 禁止直接 push（必须走 PR）
- [x] PR 需要至少 1~2 个 approve
- [x] 所有 CI status 必须通过
- [x] 禁止 force push、禁止 delete

**加分项**：

- [x] 必须有 CODEOWNERS 里的人 approve
- [x] Dismiss stale reviews（有新 commit 后重新 review）
- [x] Require signed commits（GPG 签名）
- [x] Linear history（不允许 merge commit，强制 squash / rebase）

**⚠️ 「Include administrators」也必须打勾**——不然「大佬绕规矩」会成为常态。

## 七、Monorepo vs Polyrepo：世纪之争

一个组织有 20 个项目——**放一个 Git 仓库（monorepo）里**，还是**放 20 个仓库（polyrepo）里**？——这是过去十年前端 / 后端架构圈争论最激烈的问题之一。

### 7.1 两种极端对比

| 维度 | Monorepo（单仓） | Polyrepo（多仓） |
|---|---|---|
| **仓库数** | 1 个大仓 | N 个独立仓 |
| **代码共享** | 直接 import，一次 refactor 影响全部 | 需要发包 / submodule / npm |
| **构建工具** | 需要专门的构建系统（Bazel / Nx / Turborepo） | 各仓库独立 |
| **CI/CD** | 需要「只跑受影响项目」的智能 CI | 各仓库独立 CI |
| **权限管理** | 精细到目录（CODEOWNERS） | 天然按仓库隔离 |
| **上手门槛** | 高（工具复杂） | 低（Git 就够） |
| **典型代表** | Google（Piper）、Meta、Uber、Twitter | 大多数中小团队 |

### 7.2 Monorepo 的巨大优势

**优势一：一次 refactor，改遍全项目**  
在 monorepo 里，你可以一个 commit 里同时改「基础库 + 5 个使用者」。在 polyrepo 里这就是「发 6 个 PR、跨 6 个仓库」的地狱。**Monorepo 让「大规模变更」成为可能**——这是 Google 能持续演进核心库的关键。

**优势二：原子性**  
一次 commit = 一个逻辑变更。**跨项目的变更也是原子的**——不会出现「A 项目发了新版但 B 项目没跟上」的中间态。

**优势三：全局一致性**  
所有项目用同一个版本的依赖库、同一套 lint 规则、同一套构建规则——**没有「谁的规范才是对的」这种争论**。

**优势四：发现和复用**  
所有代码都在一个仓库里 grep——**代码发现极其高效**。想找「有没有人写过 XX 功能」，一个 `grep -r` 就搞定。

### 7.3 Monorepo 的代价

**代价一：Git 会崩**  
Git 是为「一个项目一个仓库」设计的。**几十万个文件的 monorepo，`git status` 都能几秒**。所以需要：
- **partial clone**（第 05 章讲过）
- **sparse-checkout**（只 checkout 自己关心的目录）
- **file-system monitor**（Git 2.37+ 的 fsmonitor，加速 status）

**代价二：需要专用构建系统**  
一次改动可能影响 100 个项目——CI 不能全跑一遍。需要「**增量构建 + 智能测试选择**」的工具：
- **Bazel**（Google 开源）——用 BUILD 文件精确声明依赖图，只 build 受影响的目标。
- **Nx**（前端主流）——TypeScript 生态的 monorepo 工具。
- **Turborepo**（Vercel 出品）——Nx 的现代化替代，更轻量。
- **Lerna**（老牌，已被 Nx 收编）——npm 包管理型 monorepo。
- **Rush**（微软）——大型 TypeScript monorepo。
- **pnpm workspaces / yarn workspaces**——最轻量的方案。

**代价三：权限精细化**  
一个仓库容纳全部项目 → **需要「谁能改哪部分」的精细控制**。用 **CODEOWNERS 文件**：

```
# .github/CODEOWNERS
# 每一行：路径 + 负责人（PR 会自动请他 review）
/apps/mobile/           @mobile-team
/packages/ui/           @design-team @alice
/infra/                 @devops
*.sql                   @dba-team
```

### 7.4 Polyrepo 的适用场景

Polyrepo 不是「落后」，很多场景它是最优解：
- **不同语言 / 不同技术栈**：一个 Go 后端 + 一个 Vue 前端，各自独立 CI 更省事。
- **有明确的外部消费者**（比如你发 SDK 给客户）——独立仓库更清晰。
- **团队小、项目少**——上 monorepo 是杀鸡用牛刀。

### 7.5 现代前端的 monorepo 复兴

2020 年前后，前端圈掀起 monorepo 热潮：
- **Turborepo / Nx** 让搭 monorepo 从「需要 SRE 团队」变成「一条命令」。
- **pnpm workspaces** 让依赖管理不再噩梦。
- **微前端架构 + 共享组件库**天然适合 monorepo。

**推荐配置**（现代前端 monorepo）：

```
my-monorepo/
├── apps/
│   ├── web/                # 主站
│   ├── admin/              # 后台
│   └── mobile/             # 移动端
├── packages/
│   ├── ui/                 # 共享组件库
│   ├── utils/              # 工具函数
│   └── config/             # 共享配置（eslint / tsconfig）
├── turbo.json              # Turborepo 配置
├── pnpm-workspace.yaml     # pnpm workspaces 配置
└── package.json
```

> **⚡ 一句话**  
> **Monorepo 不是「更好」，只是「不同」**——它拿「工程投入」换「代码一致性和演进力」。小团队用它是负担，大团队离了它是灾难。

## 八、大厂案例研究：Google / Meta / 微软 / Netflix

理论看多了，我们看看**真实世界的巨头怎么用 Git**——每一家都是活的教科书。

### 8.1 Google：宇宙最大 Monorepo（不用 Git）

**惊人事实**：**Google 内部不用 Git**。他们用一个叫 **Piper** 的内部系统，是 Perforce 的定制版。

- **规模**：**200 亿行代码，2016 年数据**（现在应该更大）——**世界上最大的单一仓库**。
- **每天 4 万次 commit**、**每周 250 万次构建**。
- **每个开发者可以直接改任何目录**——通过强制的 code review + 静态分析保证安全。
- **99% 走 Trunk-Based**——所有代码合入主干，用 feature flag 控制上线。

**Google 为什么不用 Git**？—— Git 处理不了 200 亿行代码的规模。Piper 是**专门为超大 monorepo 定制的**——支持虚拟文件系统、按需拉取、精细权限。

**Google 的做法后来公开分享**：
- **《Software Engineering at Google》**（O'Reilly 2020）——Google 官方公开工程文化。
- **VCS 一章** 详细讲了 Piper 的设计。

Google 的 **Bazel** 就是内部构建系统 Blaze 的开源版——Monorepo 时代的核心工具。

### 8.2 Meta（Facebook）：世界第二大 Monorepo，用 Mercurial

**Meta 用 Mercurial（Hg），不是 Git**——因为 Git 处理他们仓库大小时性能不够，而 Meta 决定深度定制 Mercurial 而非切换到 Git。

- **规模**：**十亿级文件**、每天数万 commit。
- **他们的做法**：与 Mercurial 社区深度合作，贡献了 **Watchman**（文件系统监听）、**EdenFS**（虚拟文件系统）等大量基础设施。
- **Sapling**：Meta 2022 年开源了自己的 Mercurial 分支，叫 Sapling（<https://sapling-scm.com>）——**兼容 Git 仓库**，但用 Hg 的更清爽的命令。

**Meta 的公开分享**：
- **"Facebook Chose Mercurial"** 系列博客——讲了他们为什么没选 Git。
- **EdenFS 论文**：VFS 加速大 monorepo。

### 8.3 微软：Windows 迁到 Git（用 VFS for Git）

**背景**：Windows 源代码 **3 亿行代码、300 GB 仓库、4000 个开发者**——微软 2017 年决定**迁移到 Git**。这是软件史上最大的一次 VCS 迁移。

**问题**：Git 处理 300 GB 仓库直接崩。

**解法**：微软开发了 **VFS for Git**（Virtual File System for Git，后来叫 **GVFS**）——**按需下载文件**。开发者电脑上看起来所有文件都在，实际只在访问时才拉。

**结果**：
- **Windows 团队成功迁到 Git**——一次 clone 从「一天」变成「几分钟」。
- VFS for Git 后来演进为 **Scalar**（微软官方开源）——集成到 Git 上游，成为 **partial clone** 和 **sparse-checkout** 的基础。
- **微软收购 GitHub**（2018 年）与这段经历直接相关——他们已经是「大 Git 用户」。

**公开分享**：<https://github.com/microsoft/scalar>

### 8.4 Netflix：分布式团队 + Polyrepo + 严格 CI

Netflix 是 polyrepo 派的代表：
- **数百个微服务**，每个一个 GitHub 仓库。
- **各团队自主选择工作流**——从 Git Flow 到 Trunk-Based 都有。
- **共同规范**：Semantic Versioning + Conventional Commits + 严格的 CI（Spinnaker 是他们开源的部署系统）。

**Netflix 的启示**：**微服务时代，polyrepo 是自然选择**——每个团队独立演进，通过 API 契约通信。

### 8.5 你的团队该学谁？

| 团队规模 | 建议 |
|---|---|
| **1-10 人** | GitHub Flow + polyrepo，简单直接 |
| **10-50 人** | GitHub Flow + 少数几个 monorepo（把强耦合的放一起） |
| **50-500 人** | 引入 Nx / Turborepo，逐步 monorepo 化关键领域 |
| **500+** | 学微软：VFS 或 Scalar，考虑迁到大规模 monorepo |
| **数千人** | 学 Google / Meta：需要专职团队维护 VCS 基础设施 |

> **⚡ 一句话**  
> **大厂的答案不能照抄——他们的问题和你不一样。但他们的思考路径值得学**：什么规模需要什么工具，什么工具解决什么问题。

## 九、Semantic Versioning 与自动化发布

工作流讲到最后，绕不开一个话题：**发版本**。团队协作的下游是**产出物**——库、SDK、App。**如何让版本号有意义、如何自动化发版流程**，是每个成熟团队都要面对的问题。

### 9.1 Semantic Versioning（SemVer）

**格式**：`MAJOR.MINOR.PATCH`（如 `2.3.1`）。

**规则**：
- **MAJOR**：不兼容的 API 变更（破坏性变更）。
- **MINOR**：向下兼容的新功能。
- **PATCH**：向下兼容的 bug 修复。

**特殊后缀**：
- `2.3.0-alpha.1`：内测版
- `2.3.0-beta.2`：公测版
- `2.3.0-rc.1`：候选版
- `2.3.0+build.123`：构建元数据

**关键理念**：**版本号是给下游的合同**——升 MAJOR 意味着「用户必须修改代码才能用新版」。**遵守 SemVer，等于遵守合同**。

**违反 SemVer 的经典事故**：
- **npm 生态里，无数库 minor 版本引入破坏性变更**——导致 `npm install` 突然挂掉。这是 npm 后来强制引入 `package-lock.json` 的原因之一。
- **Node.js 的版本策略**：**奇数版本是实验版，偶数版本是 LTS**（长期支持）——这是一种对 SemVer 的扩展约定。

### 9.2 Conventional Commits → 自动版本号

如果每次 commit 都遵循 Conventional Commits（第 3.2 节讲的），**版本号可以自动推导**：

- `fix:` → PATCH
- `feat:` → MINOR
- `feat!:` 或 `BREAKING CHANGE:` → MAJOR

**工具生态**：
- **semantic-release**：读 commit message → 自动决定版本号 → 自动生成 CHANGELOG → 自动发 npm 包。
- **release-please**（Google 出品）：GitHub Action，自动开 release PR，包含版本升级 + CHANGELOG。
- **standard-version** / **commit-and-tag-version**：本地版工具。
- **changesets**：monorepo 的多包版本管理神器（Turborepo / Nx 推荐）。

### 9.3 一个真实的自动化发版流水线

```
开发者提交 feat: xxx 到 main
  ↓
GitHub Actions 触发 release-please
  ↓
release-please 分析所有 commit，开一个 Release PR
  ├── 修改 package.json 版本号
  ├── 更新 CHANGELOG.md
  └── 创建 tag（暂未推）
  ↓
维护者审核 → 合并 Release PR
  ↓
GitHub Actions 检测到合并
  ├── 打 tag（如 v2.3.1）
  ├── 创建 GitHub Release
  ├── 发布到 npm
  └── 通知 Slack
```

**这个流程一旦搭起来，从此发版只需要一次 review + 一次点击**——从「手动改版本号 + 手动写 CHANGELOG + 手动发布」的一小时降到 5 分钟。

### 9.4 CHANGELOG 的书写之道

**Keep a Changelog** 是被广泛采用的 CHANGELOG 规范：<https://keepachangelog.com/zh-CN/>

```markdown
# Changelog

## [2.3.0] - 2025-08-13
### Added
- 新增 SSO 登录支持

### Changed
- 优化查询接口响应速度 3 倍

### Fixed
- 修复用户名含空格时崩溃

### Deprecated
- `login()` API 将在 v3.0 移除，请用 `authenticate()`

## [2.2.1] - 2025-07-30
### Fixed
- 修复 IE11 兼容性

## [2.2.0] - 2025-07-15
...
```

**六种标准分组**：Added / Changed / Deprecated / Removed / Fixed / Security。

> **⚡ 一句话**  
> **好的版本管理 = 好的合同**。SemVer + Conventional Commits + 自动化工具——**从此发版是艺术，不是苦力**。

## 十、心智模型剖析：为什么工作流很重要

工作流的本质是**减少「不确定性」**——

- **哪个分支是最新可发布的？** → `main` 或 `develop`（明确答案）
- **一个功能开发到哪一步了？** → 看 PR 状态
- **上一个稳定版本在哪？** → 看 tag
- **紧急 bug 怎么修？** → hotfix 流程

**没有工作流**，这些问题**每次都要问人**——团队 50 人，一个人一天回答 5 个，就是 250 次沟通开销。

**有了工作流**，这些答案**沉淀在流程和工具里**——新人第一天就能自己找答案。

> **⚡ 一句话**  
> **工作流不是限制，是给团队装上「集体记忆」**。

## 十一、动手实战：搭一个团队 Git 治理框架

假设你是新组长，第一天上任要在 team GitHub 上落地治理。跟着敲：

```bash
# ────── 阶段 1：配置分支保护（在 GitHub 网页上） ──────
# Settings → Branches → Add rule
# Branch name pattern: main
# ☑ Require pull request before merging
#   ☑ Require approvals: 1
#   ☑ Dismiss stale reviews
# ☑ Require status checks to pass
#   ☑ Require branches to be up to date
# ☑ Do not allow bypassing (Include administrators)

# ────── 阶段 2：Node 项目配置 commit 规范 ──────
cd my-team-repo
npm install --save-dev husky @commitlint/cli @commitlint/config-conventional

npx husky init
echo 'npx --no -- commitlint --edit "$1"' > .husky/commit-msg

cat > commitlint.config.js <<'EOF'
export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'type-enum': [
      2,
      'always',
      ['feat', 'fix', 'hotfix', 'refactor', 'perf', 'chore', 'docs', 'test', 'style', 'revert']
    ],
    'subject-case': [0]      // 不检查大小写（中文项目建议关掉）
  }
};
EOF

git add .
git commit -m "chore: setup commitlint + husky"

# ────── 阶段 3：加 CI ──────
mkdir -p .github/workflows
cat > .github/workflows/ci.yml <<'EOF'
name: CI
on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run lint --if-present
      - run: npm run test --if-present
      - run: npm run build --if-present
EOF

git add .
git commit -m "ci: add GitHub Actions workflow"

# ────── 阶段 4：加 PR 模板 ──────
mkdir -p .github
cat > .github/PULL_REQUEST_TEMPLATE.md <<'EOF'
## 为什么改（Motivation）

## 改了什么（What）

## 怎么测（How to test）

## 相关 issue
Closes #

## Checklist
- [ ] 一个 PR 只做一件事
- [ ] 单元测试已通过
- [ ] 更新了相关文档
EOF

git add .
git commit -m "docs: add PR template"

# ────── 阶段 5：加 CODEOWNERS ──────
cat > .github/CODEOWNERS <<'EOF'
# 全局所有者
*                       @team-lead

# 前端
/src/frontend/          @alice @bob

# 后端
/src/backend/           @carol @dave

# CI/构建
/.github/               @team-lead
EOF

git add .
git commit -m "chore: add CODEOWNERS"

git push origin main
```

**做完这五步，你的团队 Git 治理框架就落地了**——commit 规范强制、PR 模板固定、CODEOWNERS 分工、CI 门禁把关。

## 十二、团队十诫

1. **选一个工作流，写进 Wiki**——不写下来就等于没有。
2. **`main` 永远可发布**——CI 挂了就丢下手上的活先修。
3. **分支保护是底线，Include administrators 也要打勾**。
4. **一个 PR 一件事，300 行内**。
5. **commit 规范强制**——用 commitlint，不靠自觉。
6. **Review 对事不对人**，`nit:` 和 `must:` 分开。
7. **合并前先 rebase**（或自动 squash），减少历史噪音。
8. **CI 必须快**——10 分钟以内。
9. **敏感信息永不入库**——**每次 add 之前扫一眼**。
10. **每季度总结一次 Git 事故**——从事故里迭代规范。
