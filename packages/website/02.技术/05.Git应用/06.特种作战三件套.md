## 引子 · 一段 200 个 commit 里的幽灵 bug

小李接到测试同事的报告：**登录功能挂了**。

他打开代码——一周前还是好的。这一周里，团队合入了 200 多个 commit。他挨个 commit 试？——那要试到明天。

老同事拍拍他肩膀：「用 `git bisect`。」

十分钟后，小李找到了那个 commit——是**一个看似毫不相关的性能优化**，误改了某个 utils 函数的默认参数，间接影响到了登录。

**200 个 commit，10 分钟锁定**——这就是 Git 特种兵的力量。

## 二、stash：把手上的活先塞进抽屉

**场景**：你在 `feature-a` 上写了半天，还没到能 commit 的程度。这时线上出 bug，需要立刻切到 `hotfix` 分支。

**不用 stash 的话**：
- 强行 `git switch hotfix` → **Git 会拒绝**（工作区改动可能冲突）。
- 硬 commit 一次 `WIP` → 后面还得回来 `reset` 或者 `commit --amend`。
- 手动复制文件到外面 → 大师才这么干。

**用 stash 的话**：

```bash
git stash                          # 把工作区、暂存区的改动都塞进抽屉
git stash push -m "wip: login"     # 带说明的 stash（推荐）

git switch hotfix                  # 现在工作区干净了，可以切分支
# ... 修 bug ...
git switch feature-a

git stash pop                      # 把抽屉里的东西倒出来，删除 stash 记录
# 或者：
git stash apply                    # 倒出来，但保留 stash 记录
git stash list                     # 看抽屉里都有什么
# stash@{0}: On feature-a: wip: login
# stash@{1}: WIP on main: ...

git stash show stash@{1}           # 看某个 stash 的改动
git stash drop stash@{1}           # 删除某个 stash
git stash clear                    # 清空所有 stash
```

**高级用法**：

```bash
git stash push --keep-index         # 只 stash 未 add 的部分（暂存区保留）
git stash push -- path/to/file      # 只 stash 某个文件
git stash push -u                   # 连 untracked 文件也 stash（重要！）
```

**⚠️ 常见坑**：
- `git stash` **默认不 stash untracked 文件**——新建的文件会被留下。用 `-u` 参数。
- **合并冲突时 pop stash** 也可能冲突——处理方式跟普通合并一样。
- **stash 是本地的**——不会随 push 传出去。切换电脑不会同步。

**记忆口诀**：**「stash 是抽屉，不是保险箱」**——用完就取，别囤积。囤了十个 stash 之后你自己都不知道每个是什么。

## 三、cherry-pick：摘一颗别处的樱桃

**场景**：一个 bugfix 是在 `develop` 分支上修的，但线上跑的是 `release-1.0` 分支。你不能把整个 `develop` 合到 `release-1.0`（还有很多未测试的功能），**只想要那一个 commit**。

**cherry-pick 就是干这个的**：

```bash
git switch release-1.0
git cherry-pick abc123             # 把 abc123 这个 commit 「复制」过来
# 会在当前分支产生一个新的 commit（内容一样，但 SHA-1 不同）

# 多个 commit
git cherry-pick abc123 def456 ghi789
git cherry-pick abc123..ghi789     # 连续范围（不含 abc123）
git cherry-pick abc123^..ghi789    # 连续范围（含 abc123）

# 处理冲突
# 若冲突：解决 → git add → git cherry-pick --continue
git cherry-pick --continue
git cherry-pick --abort            # 放弃 cherry-pick
```

**特殊场景**：

```bash
# 只想要那个 commit 的改动，但不立即 commit
git cherry-pick -n abc123          # -n = --no-commit

# cherry-pick 一个 merge commit（需要指定跟哪个父提交对比）
git cherry-pick -m 1 abc123        # -m 1 = 相对第一个父
```

**cherry-pick 的本质**：

```
   源分支：      A ── B ── [C] ── D          （要 pick 的是 C）
                        │
                        ▼（把 C 的 diff 提取出来）
   当前分支：    X ── Y ── C'                  （C' 是 C 的复制）
```

**注意**：`C'` 和 `C` 的 SHA-1 **不一样**——因为父提交不同。它们在**内容上**一样，但在**身份上**是两个 commit。

**⚠️ 什么时候不该 cherry-pick**：
- **要合并的 commit 很多**——直接 merge 或 rebase 更好。
- **不要把 cherry-pick 当合并用**——两次 cherry-pick 同一个 commit 到两条分支，历史里就出现了「双胞胎」，后面 merge 时可能会有奇怪的问题。

**记忆口诀**：**「cherry-pick 一次一颗，多了就 merge / rebase」**。

## 四、bisect：二分查找的破案神器

**场景**：一周前的版本正常，今天挂了。中间 200 个 commit。哪一个引入了 bug？

**手动测试**：200 次 × 5 分钟 = 16 小时。

**二分查找**：`log2(200) ≈ 8` 次 × 5 分钟 = **40 分钟**。

这就是 `git bisect` 的价值——**用二分法把线性搜索变成对数搜索**。

**流程**：

```bash
# 1. 开启 bisect
git bisect start

# 2. 告诉 Git 当前这个版本是「坏的」
git bisect bad

# 3. 告诉 Git 一个已知的「好的」版本
git bisect good v1.0                # 或者具体的 commit ID：git bisect good abc123

# Git 会自动切到中间的 commit，让你测试

# 4. 测试
# ... 运行测试、复现 bug ...

# 5. 报告结果
git bisect good                     # 如果这个版本好
# 或
git bisect bad                      # 如果这个版本坏

# Git 继续二分，切到下一个中点，你继续测试 → 报告，直到锁定

# 6. 结束
git bisect reset                    # 回到原来的分支
```

**Git 会告诉你**：

```
abc123 is the first bad commit
Author: xxx <email>
Date:   2025-06-20

    perf: optimize utils

 src/utils.js | 5 +++--
 1 file changed, 3 insertions(+), 2 deletions(-)
```

**神奇之处**：`log2(200) ≈ 8` 次测试就能锁定——即使你完全不知道 bug 在哪。

**进阶：自动化 bisect**

如果你能写一个脚本自动判断「这个版本是好是坏」，可以让 Git 全自动跑：

```bash
# 假设你有一个测试脚本 test.sh
# 退出码 0 = good，非 0 = bad

git bisect start
git bisect bad
git bisect good v1.0
git bisect run ./test.sh            # 自动跑，直到找到那个 commit
```

**5 分钟锁定一个隐藏了两周的 bug**——这就是自动化 bisect 的威力。

**⚠️ bisect 的两个陷阱**：

1. **中间有些 commit 可能编译不过 / 跑不了**——用 `git bisect skip` 跳过。
2. **bug 不是「非黑即白」的**——如果 bug 是概率性的，bisect 可能会误判。

## 五、彩蛋一号 · blame：找出代码的作者

**场景**：你在读一段代码，发现一行看不懂——**这行是谁写的，什么时候写的，为什么写**？

```bash
git blame src/login.js
# 输出：每行代码前面加上 「commit ID + 作者 + 时间」

git blame -L 10,20 src/login.js     # 只看 10-20 行
git blame -w src/login.js           # 忽略空白改动
git blame -M src/login.js           # 检测同文件内代码移动
git blame -C src/login.js           # 检测跨文件的代码复制
```

**结合 log 深挖**：

```bash
# 看到某行是 abc123 引入的，查看那次 commit 的完整信息
git show abc123
```

**⚡ 老手心法**：**blame 不是找罪人，是找上下文**。你想理解代码，最快的路径是「找到当初写它的 commit，看 commit message 里的『为什么』」。

**GUI 版本更爽**：VS Code 装 GitLens 插件，鼠标悬停在任何一行都能看 blame。

## 六、彩蛋二号 · worktree：一份仓库开出多个工作区

**场景**：你在 `feature-a` 上写了一半，突然要看下 `main` 分支上某段代码——切过去意味着 `feature-a` 的 IDE 状态、断点、node_modules 都要重来。

**worktree 让一份仓库同时 checkout 多个分支**：

```bash
# 在 ../hotfix 目录里 checkout hotfix 分支
git worktree add ../hotfix hotfix
# 或建新分支
git worktree add -b hotfix ../hotfix

cd ../hotfix                       # 切到新工作区
# 这里的分支是 hotfix，跟原目录的分支互不影响！

# 完事之后清理
git worktree remove ../hotfix
git worktree list                  # 看所有 worktree
```

**心智模型**：一个 `.git/` 目录 + N 个工作区，共享所有对象和历史，但工作区独立。

**⚠️ 限制**：不能在两个 worktree 里 checkout 同一个分支（避免冲突）。

**适用场景**：
- 同时对比多个分支的代码
- CI/CD 里跑并行测试
- 大项目里频繁切分支太慢，改用 worktree 提速

## 七、彩蛋三号 · notes：给 commit 贴便签

**Git commit 一旦生成，SHA-1 就锁死——修改任何一个字节，就是一个新 commit**。但有时候你就想「补充说明」——比如「这个 commit 后来发现有个副作用」「这个 commit review 通过是谁签的」——**改 message 会改 SHA，怎么办**？

**答案**：`git notes`——附加在 commit 上的**外部便签**，**不改 commit 本身**。

```bash
# 给最新 commit 加一条 note
git notes add -m "Reviewed-by: Alice; Broken on macOS"

# 给指定 commit 加
git notes add -m "note content" <SHA>

# 编辑（打开编辑器）
git notes edit <SHA>

# 查看某个 commit 的 note
git log --show-notes            # 在 log 里显示
git notes show <SHA>            # 单独看

# 删除
git notes remove <SHA>

# 列出所有 notes
git notes list
```

**notes 的工作原理**：
- notes 存在一个**独立的 ref**：`refs/notes/commits`——它是一个特殊的 tree 对象。
- 每条 note 是一个 blob，通过 tree 结构与目标 commit SHA 关联。
- **修改 note 不改 commit 的 SHA**——两者是「附加关系」，不是「包含关系」。

**push / pull notes**（默认不会自动同步）：

```bash
# 手动推 notes
git push origin refs/notes/commits

# 自动推 notes 的配置
git config --global remote.origin.push +refs/notes/*:refs/notes/*
```

**notes 的经典用法**：

1. **CI 状态标记**：Jenkins / GitHub Actions 跑完可以给 commit 加个 note，标注「构建成功」「测试覆盖率 XX%」。
2. **Code Review 备注**：把 reviewer 意见附在 commit 上。
3. **Post-mortem 分析**：某个 commit 被证明引入了 bug，加一个 note 说明「此 commit 已被 revert，参考 issue #123」。
4. **Junio C Hamano 的用法**：Git 项目自己用 notes 记录 review 讨论。

**namespace 支持**（同一 commit 挂多种便签）：

```bash
git notes --ref=review add -m "..." <SHA>
git notes --ref=ci add -m "..." <SHA>
git log --show-notes=review
```

> **⚡ 一句话**  
> **commit 是石碑，notes 是便利贴**——**当你需要「不改历史却又要附加信息」的时候，它是唯一的正解**。

## 八、彩蛋四号 · filter-branch / filter-repo：历史重写的核武器

有一天你会遇到这种噩梦：
- 「三年前有人把公司私钥 commit 进了 GitHub 公开仓库」
- 「某个二进制文件 200 MB，历史里滚动 50 次，仓库 10 GB 了」
- 「作者邮箱写错了几百次，`Author: xxx@old.com` 全要改成 `xxx@new.com`」

**你需要「重写历史」**——不是 revert，而是**从记录里彻底抹掉**。这是 Git 提供的核武器级功能。

### 8.1 filter-branch（老工具，已不推荐）

`git filter-branch` 从 Git 1.5 就存在，用来批量改写历史。**但它有致命缺陷**：极慢、容易用错、内存爆炸、Git 官方从 2.24 起**在其文档里明确警告：不推荐使用**。

老命令样子（了解即可）：

```bash
# 从整个历史中删除某个文件（老方法）
git filter-branch --tree-filter 'rm -f secret.key' HEAD
```

### 8.2 filter-repo（现代推荐，Elijah Newren 出品）

**`git filter-repo`** 是 Git 官方推荐的替代品——**同一个 Elijah Newren 开发**（也就是写 ort 合并策略那位）。它**比 filter-branch 快 10-100 倍**，接口清晰、少踩坑。

**安装**（不是 Git 内置，需要独立安装）：

```bash
# macOS
brew install git-filter-repo

# Ubuntu
sudo apt install git-filter-repo

# pip 通用
pip install git-filter-repo
```

**典型使用场景**：

**场景 1：从历史中彻底删除某个文件**

```bash
# 备份仓库先！filter-repo 会改写所有 commit
cp -r my-repo my-repo-backup

cd my-repo
git filter-repo --path secret.key --invert-paths
# --path 指定文件，--invert-paths 意为「删除匹配的，保留其余」

# 强推到远程（同事要重新 clone！）
git push origin --force --all
git push origin --force --tags
```

**场景 2：删除大文件（瘦身仓库）**

```bash
# 找出所有大 blob
git filter-repo --analyze
cat .git/filter-repo/analysis/blob-shas-and-paths.txt | head

# 删除 5MB 以上的文件
git filter-repo --strip-blobs-bigger-than 5M
```

**场景 3：批量改邮箱**

```bash
git filter-repo --mailmap ./mailmap.txt
# mailmap.txt 内容：
# 新邮箱 <new@example.com> 旧邮箱 <old@example.com>
```

**场景 4：把一个子目录提取成独立仓库**

```bash
# 只保留 packages/website/ 的历史
git filter-repo --path packages/website/
# 从此仓库只有 packages/website/ 下的内容和相关历史
```

### 8.3 历史重写的三条铁律

1. **改写历史 = 改所有相关 commit 的 SHA-1**——所有 clone 都要重新拉。**团队协作时慎用**。
2. **改写前必须备份**——`cp -r repo repo.bak`，或者至少 `git bundle create backup.bundle --all`。
3. **改写完必须 force push**——`git push --force --all && git push --force --tags`。事先通知所有协作者！

### 8.4 冷知识：BFG Repo-Cleaner

另一个流行的历史重写工具是 **BFG（Big Friendly Giant）**——用 Java 写的，专注两件事：删大文件、擦密码。速度飞快，但功能没 filter-repo 全。

```bash
# 用 BFG 删除某文件
bfg --delete-files secret.key
git reflog expire --expire=now --all && git gc --prune=now --aggressive
```

> **⚡ 一句话**  
> **不到万不得已，不要重写历史**。真到那一天，用 `filter-repo`，别用 `filter-branch`。

## 九、stash 底层揭秘：它其实是三个 commit

Git 里几乎所有「魔法」，剥开都是普通对象。**stash 也不例外**——它本质上就是**三个 commit**。

**你以为 stash 是「藏在某处的补丁」——错**。每次 `git stash`，Git 在幕后做的是：

```
1. 拿工作区状态 → 造一个 tree 对象（W）
2. 拿暂存区状态 → 造一个 tree 对象（I）  
3. 造两个 commit：
   ├── commit I（暂存区快照）：parent = HEAD
   └── commit W（工作区快照）：parents = HEAD, I
4. 更新 refs/stash → 指向 W
```

**用图表示**：

```
       HEAD (原来的 commit)
        │
        ├──── commit I ──── commit W  ← refs/stash 指向 W
        │        (index)      (working tree)
```

**关键发现**：

- **stash 是一个 merge commit**——有两个 parent（HEAD 和 I）。
- **stash 记录在 `.git/refs/stash`**——就是一个普通引用，值为 W 的 SHA。
- **stash 列表存在 `.git/logs/refs/stash`**——就是 reflog 机制的复用！`stash@{0}`、`stash@{1}` 这些语法，本质就是 reflog 语法。

**你可以亲眼验证**：

```bash
git stash push -m "test stash"
cat .git/refs/stash            # 40 位 SHA
cat .git/logs/refs/stash       # reflog 格式
git cat-file -p refs/stash     # 看这个 commit 长啥样
# parent abc123... (HEAD)
# parent def456... (I)
# ...
# WIP on main: xxxxxx last commit message
```

**几个进阶用法**：

```bash
# 用 stash 的一部分创建分支
git stash branch feature-from-stash stash@{0}
# 等价于：
#   git checkout -b feature-from-stash <HEAD 时的 commit>
#   git stash pop stash@{0}

# stash 未跟踪的文件
git stash push -u -m "including untracked"

# stash 只暂存的部分（Git 2.35+）
git stash push --staged

# 只 stash 某几个文件（--patch 交互式）
git stash push --patch

# 看某次 stash 的 diff
git stash show -p stash@{2}
```

**为什么这个设计精妙**？——因为 **stash 复用了 Git 的对象机制**：它不是「特殊数据」，它就是 commit。所以你可以 `cherry-pick` 一个 stash、`log` 一个 stash、把 stash 转成分支——**一切「对 commit 有用的操作」，对 stash 都有用**。这就是 Unix 哲学的胜利：**用最少的机制，达成最大的能力**。

> **⚡ 一句话**  
> **stash 不是魔法，它就是两个 commit + 一个引用**——理解了这一点，你对 Git 的敬畏会升级为掌控。

## 十、bisect 二分算法可视化 + `git bisect run` 自动化

`git bisect` 用二分查找定位 bug，前面第四节讲过原理，这一节讲**它的算法细节**和**如何全自动跑**。

### 10.1 二分查找的可视化

假设你有 8 个 commit（A~H），A 是 good，H 是 bad：

```
A(good) — B — C — D — E — F — G — H(bad)
                             ↑
                    第一步：中间点 D
```

**Step 1**：测试 D → 结果 good。Bug 在 D 之后：

```
D(good) — E — F — G — H(bad)
                 ↑
        第二步：中间点 F
```

**Step 2**：测试 F → 结果 bad。Bug 在 F 或更早：

```
D(good) — E — F(bad)
             ↑
     第三步：中间点 E
```

**Step 3**：测试 E → 结果 good。**Bug 是 F 引入的**（F 是第一个 bad）。

**8 个 commit，3 步定位**——比线性查找快 log 倍。**1000 个 commit 只需要约 10 步**。

### 10.2 「非线性历史」时的算法

如果历史不是线性的（有 merge），Git 会**选一个「拓扑上合理的中点」**——即使有分支交错，也能收敛。这个算法叫 **binary bisection on DAG**——Git 团队在 2005 年 Junio 亲自实现的，是 Git 少见的「有正式论文级别复杂度分析」的算法。

### 10.3 `git bisect run` 全自动破案

上面的例子还要人肉 `git bisect good` / `git bisect bad`——**其实完全可以让 Git 自己跑**。

**核心命令**：`git bisect run <脚本>`——脚本返回 0 就是 good，非 0 就是 bad。

**实战案例：找出让单测挂掉的 commit**

```bash
# 1. 标记起止
git bisect start
git bisect bad HEAD              # 现在挂了
git bisect good v1.0             # 一个月前 v1.0 是好的

# 2. 让 Git 自动跑（用单测作为判断）
git bisect run npm test

# Git 会自动 checkout 每一个中点 → 跑 npm test → 根据退出码 good/bad → 继续二分
# 十几分钟后：
# def456... is the first bad commit
```

**判断脚本的写法**（这是精髓）：

```bash
#!/bin/bash
# check.sh - 特殊退出码约定：
#   0        → good
#   1-124    → bad
#   125      → skip（当前 commit 无法测试，跳过）
#   128+     → 中止 bisect

# 编译
make clean && make
if [ $? -ne 0 ]; then
  exit 125    # 编译失败 → 跳过这个 commit
fi

# 跑测试
./run-tests
exit $?       # 0 = good, 非 0 = bad
```

**几个进阶技巧**：

```bash
# 记录 bisect 的过程日志
git bisect log > bisect.log

# 从日志重放
git bisect replay bisect.log

# 只在某个路径查找
git bisect start -- path/to/dir

# 跳过某个 commit（无法测试时）
git bisect skip

# 结束
git bisect reset
```

**Linus 亲述**：在 Linux 内核开发中，Linus 曾用 `git bisect run` **在 500 个 commit 里，几个小时自动定位到一个内核 panic 的引入点**——这在 Git 之前是不可想象的调试效率。

> **⚡ 一句话**  
> **bisect 是「让计算机替你做二分查找」——bisect run 是「让计算机替你做整场调查」**。这是效率工具的天花板。

## 十一、blame 追溯算法：Git 是怎么找到「原始作者」的

`git blame file.txt` 会告诉你每一行是谁写的、什么时候写的。**但如果这一行代码是从别的文件移过来的呢？被格式化过呢？被小改过呢**？

**Git 的 blame 算法非常聪明**——它能追到「真正的原始作者」，不被后来的搬运工遮蔽。

### 11.1 三级 blame

```bash
# 基础 blame（谁最后碰过这一行）
git blame file.txt

# 检测「同一文件内移动」的 blame（把移动的行归给原作者）
git blame -M file.txt

# 检测「跨文件复制/移动」的 blame（最强大）
git blame -C file.txt

# 更激进的跨文件检测（找所有 commit 里的复制来源）
git blame -C -C -C file.txt      # -C 越多，扫描越广

# 只看某几行
git blame -L 10,20 file.txt

# 只看某行的历史（一路追溯到最初）
git log -L 15,25:file.txt
```

**`-M` 与 `-C` 的差别**：
- **`-M`（Move）**：检测**同一文件内**行的移动/重排。
- **`-C`（Copy）**：检测**跨文件**的复制或移动——例如「这一行原本在 old.js 里，被复制到 new.js」——git 会告诉你原作者。

### 11.2 blame 追溯算法的原理

对每一行，Git 递归回溯：

```
1. 这一行在当前 commit 的 file.txt 里？
   → 上一版本 file.txt 里也有？
     → 是：继续回溯到更早
     → 否：找到「引入者」

2. 如果启用了 -C，还会检查：
   → 这一行是不是从其他文件复制过来的？（用相似度匹配）
   → 是：把责任归给原文件
```

**为什么 blame 有时不准**？——因为**格式化工具（Prettier / gofmt）会重写所有行**，导致每一行都变成「最新格式化时刻」的责任。**解决方案**：

**`.git-blame-ignore-revs` 文件**（Git 2.23+）——列出「大规模格式化」的 commit SHA，blame 时自动跳过：

```
# .git-blame-ignore-revs
# Migrate to Prettier
abc123def456...
# Rename all variables to camelCase
789abcdef012...
```

配置：

```bash
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

从此 `git blame` 会**穿透**这些格式化 commit，找到真正的作者。**GitHub 也支持这个文件**——把它 commit 进仓库，GitHub 网页版 blame 也会尊重它。

### 11.3 blame 的社交礼仪

Linus 曾开玩笑：「`git blame` 本来叫 `git praise`（表扬）会不会更好」——因为**大多数情况下你不是要「指责」谁，而是要「找当年做决定的人问原因」**。

**用 blame 的礼仪**：
- **不要用 blame 甩锅**——用 blame 找上下文。
- **找到作者后，先看当时的 commit message + PR 讨论**——大部分「诡异代码」都有当年的合理原因。
- **对格式化工具友好**——用 `.git-blame-ignore-revs` 让别人的 blame 体验也好。

> **⚡ 一句话**  
> **blame 不是审判，是考古**——它帮你回到「当年那个决定」的语境里，而不是当法官。

## 十二、心智模型剖析：几件武器的共同哲学

stash、cherry-pick、bisect 表面上完全不同，但它们**共享一个哲学**——**Git 把「时间」当成一等公民**。

- **stash**：把「此刻的时间片」封存起来，需要时解封。
- **cherry-pick**：把「某个时刻的改动」搬到另一条时间线上。
- **bisect**：在时间轴上做**二分探测**，找到「变坏」的那一刻。

这也是 Git 与其他版本工具的最大区别——**它不只是记录时间，它把时间做成可编辑、可搬运、可搜索的资产**。

**你越熟悉这三件套，越会理解一个事实**：

> **「历史不只是过去的记录，它是你未来的杠杆。」**

## 十三、动手实战：破一个真实的幽灵 bug

模拟一次真实场景——**用三件武器合作破案**。

```bash
# ────── 舞台准备 ──────
mkdir bisect-lab && cd bisect-lab
git init -b main
cat > math.js <<'EOF'
function add(a, b) { return a + b }
module.exports = { add }
EOF
echo 'console.log(require("./math").add(1, 2))' > test.js
git add . && git commit -m "chore: initial"

# 造 10 个 commit，其中第 5 个引入 bug
for i in 1 2 3 4; do
  echo "// change $i" >> math.js
  git commit -am "feat: change $i"
done

# 第 5 个：引入 bug
sed -i.bak 's/a + b/a - b/' math.js && rm math.js.bak
git commit -am "perf: optimize add"     # 表面看是性能优化，实际改错了！

for i in 6 7 8 9 10; do
  echo "// change $i" >> math.js
  git commit -am "feat: change $i"
done

# 现在 bug 就在中间的某个 commit——但我们「不知道」是哪个
node test.js                             # 输出：-1（应该是 3！）

# ────── 三件武器登场 ──────

# 1️⃣ 先用 stash 保存正在写的代码（模拟你手上还有活）
echo "wip" > wip.js
git add wip.js
git stash push -u -m "wip: my work"

# 2️⃣ 用 bisect 找出 bug
git bisect start
git bisect bad                           # 当前是坏的
git bisect good HEAD~10                  # 10 步以前是好的

# 手动测试并报告（这里模拟自动）
# Git 会切到中间的 commit，你跑 node test.js 看结果

# 或者自动跑：
cat > check.sh <<'EOF'
#!/bin/bash
result=$(node test.js 2>/dev/null)
[ "$result" = "3" ]
EOF
chmod +x check.sh

git bisect run ./check.sh                # 自动二分

# 输出：xxx is the first bad commit（那就是 "perf: optimize add"）
git bisect reset

# 3️⃣ 假设修复也已经在别的分支修好，用 cherry-pick 把修复摘过来
# （在真实项目里，你会新开分支修，然后 cherry-pick 或 revert）
git revert <bad_commit_id> --no-edit     # 直接生成一个反做 commit

node test.js                             # 输出：3 ✅

# 4️⃣ 恢复 stash
git stash pop                            # 手上的活回来了

# 5️⃣ 用 blame 复盘：看谁写了那行错代码
git blame math.js
```

**这段脚本完整演示了三件武器的合作破案**——一次典型的 senior 开发者日常。

## 十四、特种兵九诫

1. **stash 是抽屉，不是保险箱**——用完就取。
2. **stash 记得 `-u`**——不然 untracked 文件会被留下。
3. **cherry-pick 一次一颗**，多了就 merge。
4. **cherry-pick 产生的是新 commit**——SHA-1 会变。
5. **bisect 二分找 bug**——线性 200 步→对数 8 步。
6. **能写脚本判断好坏，用 `git bisect run`**——纯自动化破案。
7. **blame 找上下文，不找罪人**——它是理解代码的钥匙，不是审判的法官。

## 十六、思考题

1. **`git stash` 之后你切了 20 个分支，然后想 pop 那个 stash**——stash 会和当前分支的哪个版本合并？如果冲突了怎么办？
2. **`git cherry-pick` 一个 merge commit 会怎么样？** 为什么必须加 `-m` 参数？
3. **你用 bisect 找到 bug 引入的 commit——但那次 commit 里改了 50 个文件**。接下来你会怎么继续深挖？（提示：`git show --stat` + 逐文件分析）
4. **假设 200 个 commit 里，第 20~40 个 commit 因为依赖缺失编译不过**——bisect 走到那里会怎么办？（提示：`bisect skip`）
5. **`git blame` 看到某行是「三年前的匿名提交，作者已经离职」**——你怎么继续深挖那行的历史？（提示：`git log -p -S "关键字"` 找引入该关键字的 commit）
