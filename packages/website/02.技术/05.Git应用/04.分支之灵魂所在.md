## 引子 · 「谁在改 login.js」的群消息

小李入职新公司的第一周，见识了一个「奇特」的团队协作方式：

> **【前端群】12:03**  
> 小王：谁在改 login.js？我要动它  
> 小张：我在改，别动，我改完通知你  
> 小李（心里）：？？？

一个前端团队 12 个人，每天都在群里喊「谁在改什么，谁不要动」。原因很简单——**他们还在用 SVN，还在直接往 `trunk` 上写代码**。

小李把公司的仓库迁移到 Git 之后，做了一件事：**让每个人都开自己的分支**。

从此，群里的对话变成了：

> **【前端群】14:20**  
> 小王：我这个 PR 谁 review 一下？  
> 小张：我这边 PR 也提了，等你合了我 rebase

**同一个 login.js，两个人同时改，谁也不用等谁**——这就是分支的魔力。

## 二、分支的本质：一个 40 字节的文件

请打开你的终端：

```bash
cd 任意一个 git 仓库
cat .git/HEAD
# 输出：ref: refs/heads/main

cat .git/refs/heads/main
# 输出：a1b2c3d4e5f6...（40 位 SHA-1）
```

**看清了吗**——`main` 分支，只是一个叫 `main` 的文本文件，里面只有 40 个字节：一个 commit 的 SHA-1。

**这就是 Git 分支的全部秘密**：

- 建分支 = **新建一个 40 字节的文件**（毫秒级）。
- 切分支 = **把 HEAD 指向另一个文件**（毫秒级）。
- 删分支 = **删掉那个文件**（毫秒级）。

对比 SVN——SVN 的分支是「服务器上复制整个目录」，一个大项目要几分钟。**这就是为什么 SVN 世界里大家不敢开分支，Git 世界里人人都在开分支**。

> **⚡ 关键洞察**  
> Git 之所以叫「分布式版本控制之王」，本质就是因为**分支便宜到人人都用得起**。这是 Linus 用「一个 40 字节的文件」换来的巨大胜利。

## 三、`.git/refs/` 完整地图：分支存在哪、怎么打包、怎么找

上一节说「分支就是 `.git/refs/heads/xxx` 里的一个文件」——这一节我们把整个 `refs` 世界看清楚。

**`.git/refs/` 目录结构**：

```
.git/refs/
├── heads/                  ← 本地分支
│   ├── main
│   ├── develop
│   └── feature/
│       └── login           ← 「feature/login」分支就是这个文件
├── tags/                   ← 标签
│   ├── v1.0.0
│   └── v2.0.0-rc1
├── remotes/                ← 远程跟踪分支
│   └── origin/
│       ├── HEAD            ← 指向远程默认分支
│       ├── main
│       └── develop
└── stash                   ← stash 也是一个 ref（下一章讲）
```

**几个洞察**：

1. **分支名可以带斜杠**——`feature/login` 就是 `refs/heads/feature/login`，Git 会自动创建子目录。这就是为什么 GitHub 上你能看到 `feature/xxx` `hotfix/xxx` `release/xxx` 这种分层命名——**它们不是逻辑分类，是真实的目录层级**。
2. **`refs/heads/`、`refs/tags/`、`refs/remotes/` 三个命名空间独立**——你可以同时有一个叫 `v1.0.0` 的分支和一个叫 `v1.0.0` 的标签（**但强烈不推荐**，因为 `git checkout v1.0.0` 会歧义）。
3. **每个文件的内容都是 40 位 SHA-1**（附注 tag 除外，它指向 tag 对象而不是 commit）。

**问题来了**：一个大项目可能有几千个分支和几万个 tag——`refs/` 目录会不会很卡？

**答案：会**。这就有了 `packed-refs`。

**`packed-refs` 文件**：Git 会定期把 `refs/` 目录里的散文件**打包**成一个纯文本文件：

```
# .git/packed-refs
# pack-refs with: peeled fully-peeled sorted
abc123... refs/heads/main
def456... refs/heads/develop
789abc... refs/tags/v1.0.0
^tag123...                     ← ^ 开头表示附注 tag 剥离出的 commit SHA
fedcba... refs/remotes/origin/main
...
```

- **好处**：几千个引用只需要一次文件 open，不用 open 几千次——大幅加速 `git branch`、`git tag`、`git fetch` 等操作。
- **触发时机**：`git gc` 会自动打包；也可以手动 `git pack-refs --all`。
- **打包后**：`refs/heads/xxx` 文件可能不存在，`packed-refs` 里有它。**Git 会先查散文件，再查 packed-refs**——两者都可能包含引用。
- **散文件优先**：如果 `refs/heads/main` 文件存在，就用它的值，忽略 `packed-refs` 里同名条目。

**你可能踩过的坑**：

- **`git branch -d` 之后重启一下发现分支又「复活」了**——这是因为你有 alias 或工具误改了 `packed-refs`。**规矩**：**不要手动编辑 `packed-refs`**，用 `git update-ref -d refs/heads/xxx` 来精确删除。
- **误删分支后想恢复**：`git reflog` + `git branch xxx <SHA>` 就能救回来。但**如果分支 push 过了，同事仓库里的 `refs/remotes/origin/xxx` 还在**——从他们那里也能找回。

**refs 的三大操作命令（Plumbing 层）**：

```bash
# 读一个 ref 的当前值
git rev-parse refs/heads/main
git rev-parse main             # 简写

# 更新一个 ref（比 git branch 更底层）
git update-ref refs/heads/main <SHA>
git update-ref refs/heads/main <newSHA> <oldSHA>    # 原子 CAS 操作

# 删除一个 ref
git update-ref -d refs/heads/feature/dead

# 列出所有 refs
git for-each-ref
git for-each-ref refs/heads/          # 只列本地分支
git for-each-ref --format='%(refname:short) %(objectname:short) %(subject)'
```

**一个高级用法：symbolic-ref**

`HEAD` 是一个特殊的引用——它不指向 commit，而**指向另一个引用**：

```
# .git/HEAD 的内容
ref: refs/heads/main
```

这就是 **symbolic ref（符号引用）**——一个指向指针的指针。**修改它**：

```bash
git symbolic-ref HEAD refs/heads/develop    # 相当于 git switch develop（但不改工作区）
git symbolic-ref HEAD                        # 读当前 HEAD 指向哪
```

> **⚡ 一句话**  
> `refs/` 是 Git 的**索引层**（快速定位历史入口），`objects/` 是**存储层**（存所有内容）。**理解了这一分层，你就理解了 Git 的架构**。

## 四、分支的日常操作

### 4.1 创建 / 切换 / 删除

```bash
# 老命令（还能用，但不推荐）
git branch feature-login             # 创建分支（但不切过去）
git checkout feature-login           # 切过去

# 现代命令（Git 2.23+，推荐）
git switch -c feature-login          # 创建并切换（一步到位）
git switch main                      # 切回主分支
git switch -                         # 切回上一个分支（老手最爱）

# 基于某个 commit 建分支
git switch -c hotfix abc123          # 基于 abc123 建分支

# 删除分支
git branch -d feature-login          # 安全删除（未合并会拦截）
git branch -D feature-login          # 强制删除（危险）
```

**⚡ 推荐**：从 2019 年起，Git 官方引入了 `git switch` / `git restore` 来替代过载的 `git checkout`。**新代码用新命令**，代码可读性会好很多。

### 4.2 查看分支

```bash
git branch                     # 列出本地分支（* 号是当前分支）
git branch -a                  # 列出所有分支（含远程）
git branch -v                  # 显示每个分支的最新 commit
git branch --merged            # 已合并到当前分支的
git branch --no-merged         # 未合并的（删分支前的必查）
```

**老手工作流**：清理已合并的分支——

```bash
git branch --merged main | grep -v main | xargs git branch -d
# 一行命令删掉所有已合并到 main 的旧分支
```

### 4.3 重命名分支

```bash
git branch -m old-name new-name         # 重命名
git branch -m new-name                  # 重命名当前分支
```

## 五、合并的两条路：merge 与 rebase

分支开出去了，早晚要回家。回家的路有两条——**merge**（合并）和 **rebase**（变基）。这是 Git 世界里最容易「教条化」的一对——**看透它们的本质，你就不会再纠结**。

### 5.1 三种 merge：fast-forward、three-way、squash

**（1）Fast-forward（快进合并）**

**场景**：从 `main` 拉出 `feature`，`main` 没有新 commit。

```
   合并前：
      A ── B ── C        ← main
                 \
                  D ── E ← feature

   git switch main
   git merge feature

   合并后：
      A ── B ── C ── D ── E     ← main, feature（一起前移）
```

- 没有产生新 commit——**只是把 `main` 指针往前挪**。
- 图形干净，历史直线。
- **默认行为**——只要能 fast-forward，Git 就 fast-forward。

**（2）Three-way merge（三方合并）**

**场景**：`main` 也有新 commit。

```
   合并前：
      A ── B ── C ── F        ← main
                 \
                  D ── E      ← feature

   git switch main
   git merge feature

   合并后：
      A ── B ── C ── F ── M        ← main
                 \       /
                  D ── E           ← feature
```

- 产生一个 **merge commit（M）**，有**两个父提交**。
- 历史里能清楚看到「这是一次合并」——有分叉的痕迹。

**（3）Squash merge（压缩合并）**

```
   合并前：
      A ── B ── C ── F        ← main
                 \
                  D ── E      ← feature

   git switch main
   git merge --squash feature
   git commit -m "feat: add login"

   合并后：
      A ── B ── C ── F ── S        ← main
                                    (S 是 D+E 压成的一个 commit)
```

- 把 feature 分支的多个 commit **压成一个**再合入。
- 历史干净——`main` 上看不到 feature 的碎片 commit。
- **代价**：feature 的历史被抹平——**不适合公共分支**。

**三者对比表**：

| 合并方式 | 是否有 merge commit | 历史形态 | 适合场景 |
|---|---|---|---|
| Fast-forward | 无 | 直线 | 简单功能、快速合入 |
| Three-way | 有 | 分叉→合并 | 大功能、保留完整历史 |
| Squash | 无（但有一个压缩 commit） | 直线 | 团队约定「一 PR 一 commit」 |

### 5.2 rebase 的本质：commit 的移植手术

**rebase 干的是完全不同的事**——它把一系列 commit「摘下来」，「贴到」另一条分支上。

```
   rebase 前：
      A ── B ── C ── F        ← main
                 \
                  D ── E      ← feature

   git switch feature
   git rebase main

   rebase 后：
      A ── B ── C ── F        ← main
                       \
                        D' ── E'   ← feature（D、E 被「重放」成 D'、E'）
```

**关键点**：

- `D'` 和 `E'` 是**全新的 commit**——SHA-1 变了。
- 从图上看：feature 分支「拔起来」，「插到 main 的最新处」。
- 历史变成一条**干净的直线**——就像 feature 是**从 F 开始**写的一样。

**为什么 `D'` 的 SHA-1 变了？** 因为 commit 的 SHA-1 包含**父提交的 SHA-1**——父提交从 C 换成 F，SHA-1 一定变（回忆第 02 章的对象结构）。

### 5.3 何时用 merge，何时用 rebase

这是 Git 世界永恒的「圣战」，我给你**一条工程上真正管用的规则**：

> **「私域用 rebase，公域用 merge」**

**私域**（还没 push、还没有别人依赖）：
- 用 `git rebase` 让历史保持干净直线。
- 用 `git rebase -i`（交互式）修 commit message、合 commit、删 commit。

**公域**（已 push、别人已 fetch）：
- **千万不要 rebase**——你会改写别人已经拿到手的历史，导致下次 pull 一片混乱。
- 用 `git merge`——它是**加法**，永远不改写已有 commit。

**⚡ 一句黄金律**：**「已 push 的 commit，永远不 rebase、不 amend、不 reset」**。

**交互式 rebase（黑魔法）**：

```bash
git rebase -i HEAD~5             # 编辑最近 5 个 commit
```

打开编辑器：

```
pick abc123 feat: add login
pick def456 fix: typo in login
pick ghi789 style: format code
pick jkl012 feat: add logout
pick mno345 fix: typo in logout
```

把 `pick` 改成：
- `pick`：保留
- `reword`：改 message
- `edit`：改内容
- `squash`：合并到上一个
- `fixup`：合并到上一个（丢弃 message）
- `drop`：丢弃

**神奇的一分钟**：五个混乱的 commit → 两个漂亮的 commit → 提 PR → 队友夸你 commit 写得清爽。

## 六、three-way merge 算法：Git 是怎么「聪明」合并的

上一节讲了三种 merge，但**Git 究竟怎么知道哪些改动可以自动合、哪些必须问你**？答案是 **three-way merge（三方合并）算法**——所有 VCS 里最优雅的算法之一。

**核心思想**：不看「你改了什么、我改了什么」，而是**看「相对于共同祖先，你和我各自改了什么」**。

**举个例子**：

```
共同祖先 base (C1)：
  line 1: hello
  line 2: world
  line 3: git

你的分支 ours (C2)：           他的分支 theirs (C3)：
  line 1: hello                 line 1: HELLO         ← 大写了
  line 2: world                 line 2: world
  line 3: GIT                   line 3: git           ← 没改
  line 4: rocks                 line 4: (无)
```

**Git 的合并逻辑**（对每一行独立判断）：

| 行 | base | ours | theirs | 结论 |
|---|---|---|---|---|
| 1 | hello | hello | HELLO | ours 没改 → 用 theirs 的 HELLO |
| 2 | world | world | world | 双方都没改 → 保留 world |
| 3 | git | GIT | git | theirs 没改 → 用 ours 的 GIT |
| 4 | (无) | rocks | (无) | 只有 ours 加了 → 用 rocks |

**合并结果**：

```
line 1: HELLO
line 2: world
line 3: GIT
line 4: rocks
```

**没有冲突**——因为**每一行至少有一方没动**。这就是 three-way merge 的核心：**「相对基点的改动没重叠，就可以自动合」**。

**什么时候会冲突**？——当**同一行 base、ours、theirs 三个版本都不同**时：

```
line 1 in base:    hello
line 1 in ours:    HELLO
line 1 in theirs:  hola
```

Git 无法判断你想要 HELLO 还是 hola——只能停下来问你。这就是冲突。

**算法可视化**：

```
     base (最近公共祖先)
      /  \
     /    \
   ours   theirs
     \    /
      \  /
     merge commit
```

**寻找 base 的算法**：`git merge-base` 用「最近公共祖先」（LCA, Lowest Common Ancestor）算法。当两条分支有多个 LCA 时（叫「criss-cross merge」，双向合并过），会用 **recursive** 策略——**把多个 LCA 递归合并成一个虚拟 base**，再做 three-way。

**你可以手动查 base**：

```bash
git merge-base feature main       # 输出 base 的 SHA
git merge-base --all feature main # 如果有多个 base，都列出来
```

**看 diff 时开启「三方视图」**（远比默认的二方视图信息量大）：

```bash
git config --global merge.conflictstyle diff3

# 冲突时会看到：
<<<<<<< HEAD (ours)
HELLO
||||||| base
hello
=======
hola
>>>>>>> feature (theirs)
```

**多出的 `||||||| base` 部分显示了共同祖先**——**看到三方，你才能做出正确判断**。

> **⚡ 强烈建议**  
> 装完 Git 立刻执行：`git config --global merge.conflictstyle diff3` ——从此你的冲突解决效率翻倍。**这是 Pro Git 都推荐但很多人不知道的神配置**。

## 七、Merge Strategies 全景：ort / recursive / octopus / ours / subtree

`git merge` 底下其实藏着**六种合并策略**，每种适配不同的场景。你日常用到的 `git merge` 只是「默认策略」——但**理解全部六种，你才是真正的 merge 高手**。

**通过 `-s <策略>` 或 `-X <选项>` 指定**：

| 策略 | 适用场景 | 特点 |
|---|---|---|
| **`ort`** | 默认（Git 2.34+），双分支合并 | 三方合并的现代重写版，快 5-10 倍，2021 年由 Elijah Newren 主导 |
| **`recursive`** | 老版本默认，双分支合并 | 处理多 base 时递归合并 |
| **`resolve`** | 快速双分支合并 | 简化版 recursive，处理不了多 base |
| **`octopus`** | 三个及以上分支同时合并 | 「章鱼合并」——不能有冲突，否则直接失败 |
| **`ours`** | 强制用 ours 完全覆盖 theirs | 用于「记录一次 merge 但保留自己的版本」 |
| **`subtree`** | 一个仓库嵌入另一个仓库的历史 | 用于 subtree 合并（第 06 章讲） |

**每个策略还有若干 `-X` 选项**（Options）——常见的：

- `-X ours`：冲突时**自动用 ours 的版本**（不同于 `-s ours`，只在冲突时用，其他能合的还是三方合）。
- `-X theirs`：冲突时自动用 theirs 的版本。
- `-X ignore-space-change` / `-X ignore-all-space`：忽略空白差异。
- `-X patience` / `-X histogram`：换 diff 算法。
- `-X renormalize`：合并前先重新规范化换行符（跨平台合并神器）。

**举几个实战场景**：

**场景 1：合并 config 文件时，永远用当前分支的版本**

```bash
git merge feature -X ours
# 这不会跳过 feature 的其他改动，只是在冲突时选 ours
```

**场景 2：把老分支的 `README` 合过来，但代码全按自己的**

```bash
git checkout feature -- README.md      # 只取那一个文件
```

——其实不用 merge，用 checkout 更精准。

**场景 3：`git pull` 一直报换行符冲突（跨平台常见）**

```bash
git pull -X renormalize
# 或永久配置：git config merge.renormalize true
```

**场景 4：章鱼合并（同时合并 3 个 feature 分支到 develop）**

```bash
git switch develop
git merge feature/a feature/b feature/c
# Git 默认会用 octopus 策略
```

——**前提**：三个分支互不冲突。有冲突就直接失败，Git 不会问你——因为章鱼合并不支持冲突解决。**多分支同时合并的场景**：内核开发、大版本发布集成。

**场景 5：强制记录一次「假合并」**

```bash
git merge feature -s ours
# 生成一个 merge commit（历史图上看是合并了），但内容完全没变
# 用途：告诉 Git「我评估过 feature 分支，决定不采纳它」
```

**ort 策略的诞生故事**（Git 演进史彩蛋）：

Elijah Newren（Git 核心开发者）在 2021 年发现 recursive 策略在大仓库（如 Linux 内核）的合并**慢得离谱**——一次合并要几分钟。他花了两年时间重写整个合并模块，代号 **ort**（"Ostensibly Recursive's Twin"，「表面上是 recursive 的双胞胎」）。ort 在保持完全语义兼容的前提下，**平均快 5-10 倍**，在极端场景（重命名密集）**快 100 倍**。Git 2.34 把 ort 定为默认策略——这是 Git 近十年最大的性能改进。

> **⚡ 一句话**  
> **默认策略 ort 已经够好用**——但记住 `-X ours/theirs` 和 `octopus`，紧急场景能救命。

## 八、冲突：Git 唯一叫你亲自动手的时刻

Git 的自动合并算法非常聪明——**大部分时候它都能自己搞定**。但当两个人**改了同一行**的时候，Git 会停下来说：**「这个我判断不了，请你亲自来。」**

**冲突的产生过程**：

```
   共同祖先 A：
     function login() { return 'v1' }

   分支 X：
     function login() { return 'v2-from-X' }

   分支 Y：
     function login() { return 'v3-from-Y' }

   git merge Y ── 冲突！
```

**冲突文件的样子**：

```javascript
function login() {
<<<<<<< HEAD
  return 'v2-from-X'
=======
  return 'v3-from-Y'
>>>>>>> feature-y
}
```

**解冲突的三步**：

```bash
# 1. 打开冲突文件，删掉 <<<、===、>>> 标记，改成你想要的样子
function login() {
  return 'v3-from-Y'   // 保留 Y 的版本
}

# 2. 告诉 Git 「我处理好了」
git add login.js

# 3. 完成合并
git commit                      # 走 merge 流程
# 或者
git rebase --continue           # 走 rebase 流程
```

**万一冲突太多，想放弃**：

```bash
git merge --abort               # 中止 merge
git rebase --abort              # 中止 rebase
```

**冲突的三个心法**：

1. **冲突不是失败，是需要人为决策的信号**——没有它，你反而危险。
2. **冲突越多说明分支活得越久**——所以要**短命分支**（几小时到几天，不要几周）。
3. **冲突解完了，跑一遍测试再 commit**——冲突文件常常语法都对，但语义已经乱。

## 九、rerere：让 Git 记住你解决过的冲突

**rerere = "reuse recorded resolution"（复用已记录的解决方案）**——这是 Git 一个几乎被埋没的宝藏功能。

**问题场景**：你在一条长期 feature 分支上开发，主分支 main 一直在更新。你要**反复 rebase 或 merge main 到 feature**——每次都遇到**相同的冲突**（因为你和主线改的地方相似）。**每次都手动解一遍，累到吐血**。

**rerere 的解法**：**记住你解决过的冲突，下次自动重放**。

**启用**：

```bash
git config --global rerere.enabled true
```

启用后，每次你解决冲突时，Git 会**偷偷记下**「原始冲突长啥样」和「你解成什么样」。下次遇到同样的冲突，它直接自动应用。

**工作原理**：

```
第一次冲突：
  ┌──────────────────────────────┐
  │ <<<<<<< HEAD                 │
  │ old_login()                  │
  │ =======                      │
  │ auth_login()                 │
  │ >>>>>>> main                 │
  └──────────────────────────────┘
        ↓ 你手工解决为：new_login()

  Git 记下：
    .git/rr-cache/<hash>/preimage   ← 原始冲突长这样
    .git/rr-cache/<hash>/postimage  ← 你解成这样

第二次同样冲突（rebase / merge 再来）：
  Git 发现「哦，这个 preimage 我见过」
  → 自动应用 postimage → 冲突自动消失
```

**你需要做什么**：

```bash
# 1. 开启一次
git config --global rerere.enabled true

# 2. 正常解冲突（第一次照旧手工）
git merge main
# ... 手工编辑冲突文件 ...
git add .
git rerere status                # 看当前有哪些 rerere 记录
git commit

# 3. 下次同样冲突再来
git merge main
# → Git 直接自动解开
# → 你只需要 git add & git commit

# 高级操作
git rerere status                # 查看当前活跃的冲突记录
git rerere diff                  # 看 rerere 帮你解开的部分
git rerere clear                 # 清空缓存
git rerere forget <file>         # 让 Git 「忘掉」某个冲突解法
```

**rerere 的三个进阶技巧**：

1. **与 rebase 组合使用**——rebase 反复迭代时，rerere 是救命的。**长期 feature 分支必开**。
2. **配合 `merge.conflictstyle = diff3`**——三方视图能让 rerere 更准确。
3. **rerere 是本地的**——不会 push、不会 clone。团队协作时每个人独立学习自己的冲突模式。

**为什么这个功能几乎没人用**？——因为**它是隐形的**，Git 官方界面几乎不提。但**Junio C Hamano（Git 首席维护者）在维护 Git 项目自身时天天用它**——因为 Git 项目每天要 merge 上百个 PR，rerere 是他的救命稻草。

> **⚡ 一句话**  
> **rerere 是 Git 送给「长期分支开发者」的秘密武器**——一行配置，从此少解一半冲突。

## 十、心智模型剖析：分支不是分叉，是指针

初学者的心智误区是把分支想成「一串 commit」：

```
   ❌ 误解：
   feature 分支 = [D, E]
   main 分支 = [A, B, C]
```

**这是错的**。分支只是**一个指针，指向某一个 commit**：

```
   ✅ 正确：
   feature 分支 = 指向 E 的指针
   main 分支 = 指向 C 的指针
```

**至于「哪些 commit 属于哪个分支」——Git 根本不记这件事**。它只记录：**每个 commit 有哪些父提交**。「属于 feature」这个概念，是从**从 E 向父提交回溯的所有 commit** 反推出来的。

这就是为什么：

- **删除分支不会删 commit**——只是删了那个指针；commit 还在 `.git/objects/` 里躺着。
- **`git branch --contains abc123`** 可以查「哪些分支包含这个 commit」——本质是从每个分支的头 commit 往回走能不能碰到 `abc123`。
- **一次误删的分支**，只要能记起最后一个 commit 的 SHA-1，就能 `git branch new-name abc123` 复活。

> **⚡ 一句话**  
> **分支是「入口」，不是「归属」**。Git 的世界里，commit 不归属于任何分支——它只归属于自己的父提交链。

## 十一、`detached HEAD`：新手最迷惑的现象

**场景**：你敲了 `git checkout abc123`（一个 commit ID，而不是分支名）。

Git 会警告你：

```
Note: switching to 'abc123'.
You are in 'detached HEAD' state.
```

**发生了什么？**

正常时，`HEAD` 指向**分支**，分支再指向**commit**：

```
   HEAD ──▶ main（分支）──▶ commit
```

`detached HEAD` 时，`HEAD` **直接指向 commit**，绕过了分支：

```
   HEAD ──▶ commit（没有分支中间层）
```

**这样有什么后果？**
- 你在这里做的 commit，**没有任何分支指着它**。
- 一旦你 `switch main` 切走，这些 commit 就成了「孤儿」——最后被 GC（垃圾回收）清理。

**救命方法**：

```bash
# 如果你想保留 detached 状态下的工作：
git switch -c my-rescue           # 建一个分支，把当前位置固定下来
```

**日常场景**：
- `git checkout v1.0.0`（切到某个 tag）→ 是 detached，因为 tag 不是分支。
- `git bisect` 的过程 → 会短暂 detached，属正常。

**记忆口诀**：**「HEAD 不站在分支上，你就是浮萍」**。

## 十二、动手实战：一次完整的分支协奏曲

打开终端，把下面这段一口气敲完——你将亲历分支的完整生命周期：

```bash
# 初始化
mkdir git-branch-lab && cd git-branch-lab
git init -b main
echo "v1" > app.js
git add . && git commit -m "chore: initial"

# ────── 场景 1：Fast-forward ──────
git switch -c feature-a
echo "feature A" >> app.js
git commit -am "feat: add A"

git switch main
git merge feature-a               # fast-forward，图形干净
git log --oneline --graph --all

# ────── 场景 2：Three-way merge ──────
git switch -c feature-b
echo "feature B" >> app.js
git commit -am "feat: add B"

git switch main
echo "main hot fix" >> app.js
git commit -am "fix: main hotfix"

git merge feature-b               # 会产生 merge commit（可能有冲突）
# 若冲突：编辑 app.js → git add . → git commit

git log --oneline --graph --all

# ────── 场景 3：Rebase ──────
git switch -c feature-c
echo "feature C" >> app.js
git commit -am "feat: add C"

git switch main
echo "main tweak" >> app.js
git commit -am "chore: tweak"

git switch feature-c
git rebase main                   # 把 feature-c 移植到 main 最新处
git log --oneline --graph --all

# ────── 场景 4：交互式 rebase ──────
echo "typo1" > tmp.js && git add . && git commit -m "feat: work 1"
echo "typo2" >> tmp.js && git add . && git commit -m "feat: work 2"
echo "typo3" >> tmp.js && git add . && git commit -m "fix: typo"

git rebase -i HEAD~3              # 打开编辑器，把三个 commit 合成一个
# 把第二、三行改成 squash 或 fixup
git log --oneline

# ────── 场景 5：detached HEAD 与救命 ──────
FIRST=$(git log --oneline | tail -1 | awk '{print $1}')
git checkout $FIRST               # ⚠️ detached
echo "orphan work" >> app.js
git commit -am "orphan"           # 这个 commit 没分支！
git switch -c rescue-branch       # ✅ 救回来

# ────── 场景 6：清理已合并分支 ──────
git switch main
git branch --merged main | grep -v main | xargs -I {} git branch -d {} || true

git log --oneline --graph --all
```

**六个场景，一次走完**——你会亲眼看到 `--graph` 输出里的**图形变化**，这比任何文字讲解都清楚。

## 十三、分支八诫

1. **一个分支一个目的**——feature、fix、chore、experiment 各归各。
2. **分支命名有前缀**——`feat/`、`fix/`、`chore/`、`hotfix/`（下一章会详细讲）。
3. **分支要短命**——功能拆小，几小时到几天完成。分支活得越久，冲突越多。
4. **公共分支上不 rebase**——只加 merge commit。
5. **私有分支上敢 rebase**——保持历史干净。
6. **合并前先 rebase**——让 PR 是干净的 fast-forward，减少 merge 噪音（团队约定）。
7. **每次 merge / rebase 后跑测试**——语法过了，语义未必过。
8. **删完的分支要清理**——用 `--merged` + `xargs` 一行搞定。

## 十五、思考题

1. **如果 `git branch feat` 就是新建一个 40 字节的文件，那为什么 `git checkout feat` 之后工作区会变化？** 是什么把工作区文件也切换过去的？
2. **`git merge` 产生的 merge commit，有两个父提交**——它的 tree 是怎么算出来的？（提示：三方合并算法）
3. **你在私有分支上 rebase 了公共分支的旧 commit**——push 会发生什么？你想 `--force` 强推，会给团队带来什么灾难？
4. **在什么场景下应该保留 `--no-ff`（禁止 fast-forward）？** 有些团队的规范强制要求所有合并都是 three-way——他们的理由是什么？
5. **`git rebase -i` 可以把 10 个 commit 合成 1 个——但如果这 10 个 commit 都是 3 个月前的旧 commit，你还能这么做吗？** 会有什么副作用？
