## 引子 · 一个失控的凌晨三点

小李是我们全书的主人公，一位工作三年的前端工程师。他第一次「意识到 Git 很重要」的那个夜晚，我至今还记得——

> 凌晨三点，他给我发来一条微信：「哥，我 `git reset --hard` 了一下，代码全没了，我明天就要交付……」

他花了三天写完的功能，被一条陌生的命令抹平。他慌得手心冒汗、脑子空白，第一反应是**重装 Git**——就像 Windows 崩了重装系统一样。

我告诉他：「打开终端，敲 `git reflog`。」

十分钟后，他所有代码都回来了。

他在电话那头愣了很久，然后说了一句让我记到现在的话：

> **「原来我用了三年 Git，从来没真的懂过它。」**

小李的故事，是许多开发者的缩影。我们每天与 Git 打交道，却像开了三年车却从不打开发动机盖——**能开，但一遇到故障就抓瞎**。

本章，就是要在你动手写第一行代码之前，先打开 Git 的引擎盖，让你看清它的**骨架**、它的**血脉**、它的**灵魂**。

## 一、学习目标

读完本章，你应当能够：

- **画出**：Git 的三区五态、DAG 提交图、四大心智坐标系。
- **说出**：blob、tree、commit、tag 四种对象的差异与关系。
- **理解**：为什么 `git reset --hard` 可以被 `reflog` 找回来。
- **建立**：一张贯穿全书的「Git 世界地图」，后续每学一条命令，都能在这张图上找到它的坐标。

**本章不需要你敲很多命令**——它是全书的「先验知识」，是让后面九章的每一次操作，都有一个**可解释的坐标位置**。

## 二、Git 的三张面孔

要真正读懂 Git，你需要先接受一个事实——**Git 有三张面孔**，它们同时存在，缺一不可：

| 面孔 | 你看到的 | 它其实是 |
|---|---|---|
| **第一张：命令行工具** | `git add`、`git commit`、`git push` | 一层薄薄的 CLI 外壳 |
| **第二张：内容寻址文件系统** | `.git/objects/` 目录 | 一个用 SHA-1 索引的**键值数据库** |
| **第三张：分布式协作协议** | `push` / `pull` / `fetch` | 一套基于图论的**同步引擎** |

**多数人只看到第一张脸**，所以只能背命令；**少数人看到第二张脸**，于是能读懂 `.git` 目录；**极少数人看到第三张脸**，因此能设计工作流、优化 CI/CD、排查任何冲突。

本书的目标，就是让你**同时看清三张脸**。

> **⚡ 关键洞察**  
> Git 的命令行是给人用的，但它的**内部结构是为机器设计的**。理解内部结构，你会发现命令行其实非常一致——所有看似复杂的操作，都在做同一件事：**移动指针 + 生成新对象**。

## 三、Git 的三层架构：Porcelain / Plumbing / Internals

Git 官方文档里有两个术语，几乎所有人都跳过不看，其实它们**是理解 Git 全貌最关键的一对词**：

- **Porcelain 命令**（瓷器命令）——面向用户的、优雅的高层命令：`add`、`commit`、`push`、`log`、`status`……
- **Plumbing 命令**（管道命令）——面向内部的、原始的底层命令：`hash-object`、`cat-file`、`update-index`、`write-tree`、`commit-tree`、`rev-parse`、`update-ref`……

这个隐喻来自英语中的卫浴系统——**瓷器（马桶、洗手盆）是给用户的漂亮外壳，管道是藏在墙里的真正机械**。Git 把命令分成这两层，是有意为之：

```
   ┌─────────────────────────────────────────────────┐
   │   Porcelain（瓷器层）：面向人类                    │
   │   git add / commit / push / log / status ...    │
   ├─────────────────────────────────────────────────┤
   │   Plumbing（管道层）：面向机器与脚本               │
   │   hash-object / cat-file / update-index / ...   │
   ├─────────────────────────────────────────────────┤
   │   Internals（内部）：对象数据库 + 引用            │
   │   .git/objects/ · .git/refs/ · .git/HEAD ...    │
   └─────────────────────────────────────────────────┘
```

**理解这三层架构，你会豁然开朗**：

- 每一条 Porcelain 命令，本质上都是**若干条 Plumbing 命令的组合**。
- 每一条 Plumbing 命令，本质上都是**对 `.git/` 里几个文件的读写**。
- **Git 之所以可以脚本化、可以嵌入 CI/CD、可以被 GitHub 之类的平台包装成 UI，就是因为它有严格的 Plumbing 层**——机器可以稳定调用它。

> **⚡ 一句话**  
> **Porcelain 变化很快，Plumbing 几乎不变**。Linus 早在 2005 年就定下：「Porcelain 是可以推倒重来的，但 Plumbing 是永远向后兼容的」——这就是为什么你 20 年前的 `hash-object` 脚本今天还能跑。

后面第 02 章的实战里，我们就会**用纯 Plumbing 命令，不用一句 `git add / commit`，从零造出一个 commit**——那时你会真正看到 Git 的骨架。

## 四、四大心智坐标系

一切复杂系统，都需要坐标系来定位。Git 有**四个坐标系**——空间、时间、身份、语义。它们像四条经纬线，编织出整个 Git 世界。

### 4.1 空间坐标：三区五态

Git 在你的电脑上把文件分成三个「区」，文件在这三个区之间流动，形成五种「状态」。

```
   ┌──────────────┐   git add    ┌──────────────┐   git commit   ┌──────────────┐
   │   工作区     │ ───────────▶ │   暂存区     │ ─────────────▶ │   版本库     │
   │ Working Tree │              │  Staging     │                │  Repository  │
   │              │ ◀─────────── │  (Index)     │ ◀───────────── │  (.git/)     │
   └──────────────┘  git restore └──────────────┘   git reset    └──────────────┘
```

**三区**：
- **工作区（Working Tree）**：你眼睛能看到的文件，磁盘上的实际内容。
- **暂存区（Staging / Index）**：一个**临时候选箱**，装着「即将成为下一个 commit」的快照。
- **版本库（Repository）**：`.git/` 目录，装着**所有历史快照**——一旦进去，永不消失（除非手动清理）。

**五态**：
- **未跟踪（Untracked）**：Git 完全不认识的文件。
- **未修改（Unmodified）**：跟版本库一致。
- **已修改（Modified）**：工作区变了，但没 `git add`。
- **已暂存（Staged）**：`git add` 之后、`git commit` 之前的中间态。
- **已提交（Committed）**：安全落地进 `.git/objects/`，永久保存。

> **⚡ 记忆口诀**  
> **「改（Modified）→ 存（Staged）→ 交（Committed）」**——一切 Git 命令，都是在推动文件在这三态之间前进或后退。

### 4.2 时间坐标：DAG 有向无环图

Git 的历史不是一条直线，而是一张图——**Directed Acyclic Graph（有向无环图）**：

```
                    ┌── C4 ── C5 ──▶ feature
                    │
    C1 ── C2 ── C3 ─┤
                    │
                    └── C6 ── C7 ──▶ main
```

- 每个节点是一个 **commit**。
- 每个 commit 都有 **0 到 N 个「父提交」**——一次普通 commit 有 1 个父；merge commit 有 2 个父；根 commit 有 0 个父。
- 时间**只向前流动**，不允许回环（这就是「无环」的含义）。

理解这张图，你就理解了**所有分支操作的本质**——不过是「在图上加节点、移指针」而已。

> **⚡ 关键洞察**  
> Git 的 `log`、`branch`、`merge`、`rebase`、`cherry-pick`……本质上都是**图操作**。所以第 04 章讲分支时，我们会反复回到这张 DAG 图。

### 4.3 身份坐标：SHA-1 与对象数据库

Git 给每一份内容都算一个 40 位十六进制的 **SHA-1 哈希**（例如 `a1b2c3d4...`），作为它的**永久身份证**。

```
    ┌──────────┐  hash()  ┌──────────────────────────────────────────┐
    │ 文件内容  │ ───────▶ │ a1b2c3d4e5f6...（40 位十六进制）           │
    └──────────┘          └──────────────────────────────────────────┘
```

`.git/objects/` 是一个巨大的键值仓库：

- **Key**：40 位 SHA-1
- **Value**：内容对象（blob / tree / commit / tag）

**四种对象**：

| 对象类型 | 存了什么 | 类比 |
|---|---|---|
| **blob** | 一个文件的内容（不含文件名） | 一个「快照塞进袋子」 |
| **tree** | 一个目录：包含哪些文件、哪些子目录 | 一份「目录清单」 |
| **commit** | 一次快照：指向根 tree + 作者 + 时间 + 父提交 | 一张「快照的封面」 |
| **tag** | 一个带说明的命名指针（附注标签） | 一枚「贴标签的签名」 |

**它们的关系**：

```
      commit ──▶ tree ──┬─▶ blob（README.md）
                        ├─▶ blob（package.json）
                        └─▶ tree（src/）──┬─▶ blob（main.js）
                                          └─▶ blob（utils.js）
```

一个 commit 指向根 tree，根 tree 指向若干 blob 和子 tree……**整个仓库就是一棵 Merkle 树**——这也是 Git 完整性验证的数学基础。

> **⚡ 历史彩蛋**  
> Merkle 树最早用于 Ralph Merkle 在 1979 年提出的密码学结构，后来被用于区块链、IPFS、BitTorrent。Git 是第一个把它带进主流软件工程的工具——Linus 用它换来了「任何一 bit 的改动都能被立刻发现」的完整性。

### 4.4 语义坐标：三种指针

对象是「死」的数据，指针是「活」的入口。Git 只有三种指针：

| 指针 | 指向 | 作用 |
|---|---|---|
| **HEAD** | 当前所在位置 | 「你现在站在哪」 |
| **branch（分支）** | 某个 commit | 「一条工作线的名字」 |
| **tag（标签）** | 某个 commit | 「一个不动的里程碑」 |

分支和 HEAD 是**会动的**——每次 commit，它们跟着往前挪一步；标签是**不动的**——它一旦贴上，就永远指向那一个 commit（除非强制删除）。

```
                                          HEAD
                                            │
                                            ▼
                    ┌── C4 ── C5 ──▶ feature（分支：可动）
                    │
    C1 ── C2 ── C3 ─┤                      main（分支：可动）
                    │                       │
                    └── C6 ── C7 ──────────▶
                              │
                              └──── v1.0.0（标签：不动）
```

> **⚡ 一句话**  
> **分支不是「一堆 commit 的集合」，而是「一个指向某个 commit 的 40 字节文件」**——所以创建分支才会那么快。

## 五、Git 的六大设计哲学

四大坐标系是「Git 长什么样」，那**为什么长成这样**？Chacon 在《Pro Git》里、Loeliger 在《Version Control with Git》里，都总结过 Git 骨子里的设计哲学。综合两本书 + Linus 历年演讲，我把它凝练成六条：

**哲学一：一切都是对象，一切对象都用 SHA-1 命名。**  
Git 只认识四种对象——blob / tree / commit / tag。它们都通过 `SHA-1(内容)` 得到一个 40 位地址。**没有名字，没有属性，只有内容与哈希**。这就是所谓的 **Content-Addressable File System（内容寻址文件系统）**——Git 的世界里，「你是谁」完全由「你装了什么」决定。

**哲学二：快照，不是差量。**  
SVN、CVS 存的是「相对于上一版本的差异」；Git 存的是**完整的目录快照**。你可能担心「这不会占很多空间吗」——不会，因为**内容寻址天然去重**（内容不变 → SHA-1 不变 → 复用同一个 blob）。快照式的好处：任何一个 commit 都是**自包含的**，可以独立恢复，不依赖任何父版本。

**哲学三：三区分离，让「改动」和「提交」解耦。**  
工作区（写代码的地方）、暂存区（组织下一个 commit 的地方）、版本库（永久历史）——三者分开的意义是：**你可以先「乱改」，再慢慢「组织」，最后「优雅提交」**。这就是 `git add -p` 存在的意义：把混乱的现场，剪辑成清晰的历史。

**哲学四：分支是廉价的。**  
在 SVN 里建分支要拷贝整个仓库，慢到不敢用；在 Git 里建分支只是**写一个 40 字节的文件**——耗时几毫秒。这一条哲学彻底改变了软件开发的方式：**分支从「珍稀资源」变成「日常用品」**，于是有了 GitHub Flow、Trunk-Based Development、feature branch 这些工作流。

**哲学五：本地优先，远程按需。**  
每一次 `clone` 都拿到**完整的历史**。日常的所有查看、diff、commit、branch、merge——**都在本地完成**，不需要网络。只有 `push` / `fetch` 时才与远程通信。这个哲学让 Git 在飞机上、地铁里、断网时都能高效工作——这是 SVN 时代想都不敢想的自由。

**哲学六：数据不可变，历史可追溯。**  
一旦一个对象进了 `.git/objects/`，它就**永远存在**（除非被 gc 主动清理）——即使 `reset --hard`、即使删除分支、即使强推。这就是为什么 `reflog` 能救回你 30 天内的任何操作。**Git 的历史是加法结构**——你只能往前加，不能真的删除，只能「不再指向」。

> **⚡ 关键洞察**  
> 六条哲学彼此咬合：内容寻址 → 快照可复用 → 分支很便宜 → 本地可完整 → 数据不可变 → 历史可追溯。**这是一个环环相扣的设计闭环**——去掉任何一条，Git 就不再是 Git。

理解了这六条哲学，你就能**推理出 Git 的绝大多数命令行为**，而不是靠死记硬背。

## 六、`.git/` 目录完整解剖

Git 把它的整个世界，装进了一个叫 `.git/` 的目录里。**打开这个目录，你就等于打开了 Git 的心脏**。

```
.git/
├── HEAD                      # 当前所在位置（一行字符串：ref: refs/heads/main）
├── config                    # 本仓库的配置（remote / user / core.* / ...）
├── description               # 仓库描述（gitweb 用，几乎没人管）
├── index                     # 暂存区（二进制文件，第 03 章会详解）
├── hooks/                    # 客户端与服务端钩子脚本（pre-commit / post-merge ...）
│   ├── pre-commit.sample
│   ├── post-commit.sample
│   └── ...
├── info/
│   └── exclude               # 只对当前仓库生效的 ignore 规则（不入版本）
├── logs/                     # 引用移动的历史（reflog 的存储位置）
│   ├── HEAD                  # HEAD 的移动日志
│   └── refs/
│       └── heads/
│           └── main          # main 分支的移动日志
├── objects/                  # 对象数据库（Git 的心脏中的心脏）
│   ├── ab/                   # SHA-1 前 2 位作为目录名
│   │   └── cdef123...        # SHA-1 后 38 位作为文件名（loose object）
│   ├── info/
│   └── pack/                 # 打包后的对象（pack file，节省空间）
│       ├── pack-xxx.pack     # 内容
│       └── pack-xxx.idx      # 索引
├── refs/                     # 引用（分支、标签、远程分支）
│   ├── heads/                # 本地分支
│   │   ├── main              # 40 位 SHA-1
│   │   └── feature/xyz
│   ├── tags/                 # 标签
│   │   └── v1.0.0
│   └── remotes/              # 远程跟踪分支
│       └── origin/
│           ├── HEAD
│           └── main
├── packed-refs               # 打包后的引用（一个文件里塞多个 ref）
├── COMMIT_EDITMSG            # 上一次 commit message 的草稿
├── ORIG_HEAD                 # 危险操作前的 HEAD 备份（reset / merge 会写）
├── FETCH_HEAD                # 上一次 fetch 拉回来的 tip
└── MERGE_HEAD                # 正在进行的 merge 的另一方（冲突时能看到）
```

**核心三兄弟**：

- **`.git/objects/`**——**存储层**：所有 blob / tree / commit / tag。每个对象一个文件（loose）或多个塞进一个 pack 文件。
- **`.git/refs/`**——**索引层**：分支、标签、远程分支，全是「指向某个 commit 的 40 字节文本文件」。
- **`.git/HEAD`**——**入口层**：一行字符串，告诉 Git「你现在站在哪」。

**只要这三个部分完整，仓库就完整**——即使删掉 `hooks/`、`logs/`、`config/`，仓库照样能跑。

> **⚡ 动手一试**  
> 现在打开你的任何一个项目，敲 `find .git -type f | head -20`——你会亲眼看到上面这些文件真的存在。**Git 不神秘，它只是一堆文件而已**。

## 七、VCS 家族横向对比：Git 到底赢在哪

在 Git 出现之前，版本控制的世界有过很多玩家。今天多数人只用 Git，但**理解它们的差异，才能理解 Git 为什么赢**。

| 系统 | 诞生年 | 类型 | 存储模型 | 现状 |
|---|---|---|---|---|
| **SCCS** | 1972 | 本地（单机） | 差量（interleaved deltas） | 化石级 |
| **RCS** | 1982 | 本地（单机） | 反向差量 | 化石级 |
| **CVS** | 1986 | 集中式（C/S） | 差量 + 文件级 | 几乎绝迹 |
| **Subversion (SVN)** | 2000 | 集中式（C/S） | 差量 + 目录级 + 原子提交 | 少量遗留系统 |
| **Perforce** | 1995 | 集中式（C/S） | 差量 + 文件级锁 | 游戏行业主流 |
| **BitKeeper** | 1998 | 分布式 | 快照 + 差量 | 已停产（2016 年开源） |
| **Bazaar (bzr)** | 2005 | 分布式 | 快照 | 已停止开发 |
| **Mercurial (hg)** | 2005 | 分布式 | 快照（revlog） | 部分大厂在用 |
| **Darcs** | 2003 | 分布式 | Patch 代数 | 学术项目 |
| **Fossil** | 2007 | 分布式（含 Wiki/Bug） | SQLite | SQLite 团队自用 |
| **Git** | 2005 | 分布式 | 快照 + 内容寻址 | **绝对主流** |

**几个特别值得对比的对象**：

**Git vs SVN**——集中式 vs 分布式：
- SVN 的历史在服务器上，Git 的历史在每一个 clone 里。
- SVN 的分支是「拷贝目录」，Git 的分支是「40 字节的引用」。
- SVN 的 revision 是自增数字（r1, r2, r3），Git 是 SHA-1（无中心可分配自增号）。

**Git vs Mercurial**——两个 2005 年同月出生的双胞胎：
- Hg 用 Python 写，Git 用 C 写（性能是 Git 胜的关键之一）。
- Hg 的分支是「commit 上的一个属性」（永久），Git 的分支是「独立的引用」（可删）。
- Hg 更简洁友好，Git 更强大灵活——**Git 赢在 GitHub 的生态爆炸**（2008 年 GitHub 上线是历史转折点）。

**Git vs Perforce**——两种世界观的对撞：
- Perforce 用**悲观锁**（改文件前先 checkout 锁定），Git 用**乐观并发**（大家随便改，冲突了再合）。
- Perforce 擅长巨型二进制（游戏资源），Git 需要 LFS 才能玩转大文件。
- **游戏、影视、EDA 行业**至今用 Perforce——因为它们的资产以 GB 级二进制为主。

**Git vs Fossil**——SQLite 作者 D. Richard Hipp 的反潮流之作：
- Fossil 把仓库、Bug、Wiki、论坛全放进一个 SQLite 文件——**一个仓库自带项目管理**。
- 哲学是「All in one」，Git 是「Do one thing well」（Unix 哲学）。
- SQLite 团队一直用 Fossil 管自己的代码，是 Git 之外少见的自成一派。

> **⚡ 关键洞察**  
> Git 不是「技术上最优雅」的方案（学习曲线陡峭是公认的），但它是**「哲学最激进 + 生态最庞大」的方案**。Linus 押对了「分布式」和「快照」两条大方向，剩下的由 GitHub、GitLab、Gitea 生态补齐。**技术演进的历史，从来不是最优雅的赢，而是最合时宜的赢**。

## 八、命令的分类地图

Git 的命令看似繁多，其实只有六类。把这张表贴在显示器旁，任何命令你都能找到它的家：

| 分类 | 代表命令 | 干什么用 | 章节 |
|---|---|---|---|
| **① 创建 / 克隆** | `init` / `clone` | 从零启动或复制仓库 | 第 02 章 |
| **② 快照三区** | `status` / `add` / `commit` / `restore` / `reset` | 在三区之间搬运数据 | 第 03 章 |
| **③ 分支操作** | `branch` / `checkout` / `switch` / `merge` / `rebase` | 图上加点、移指针 | 第 04 章 |
| **④ 远程同步** | `remote` / `push` / `pull` / `fetch` / `clone` | 跨机器同步 DAG | 第 05 章 |
| **⑤ 历史与恢复** | `log` / `diff` / `blame` / `reflog` / `revert` / `cherry-pick` / `bisect` | 查、改、找、回 | 第 03、06、08 章 |
| **⑥ 高级 / 特种** | `stash` / `tag` / `worktree` / `submodule` | 特殊场景 | 第 06、07 章 |

**记住：所有命令都在做三件事之一——**

1. **加对象**（`add`、`commit`、`merge`）
2. **移指针**（`branch`、`checkout`、`reset`）
3. **同步图**（`push`、`pull`、`fetch`）

看穿这三件事，Git 就不再神秘。

## 十、初学者最容易踩的 15 个心智误区

Loeliger 在《Version Control with Git》里花了整整一章讲「常见误解」——因为**Git 的痛，八成来自误解，只有两成来自命令本身**。这里精选 15 个最常见的：

**误区 1 · 「Git 记录的是差异」**——错。Git 记录的是**快照**（每次 commit 存完整目录树），差异是「显示时」现算的。

**误区 2 · 「commit ID 是随机的」**——错。commit ID 是 SHA-1(tree + parents + author + message)，**完全由内容决定**。改一个字节，ID 就变。

**误区 3 · 「分支是一系列 commit」**——错。分支只是**一个指针**（40 字节的文件），指向某个 commit。「分支包含的 commit」是「从这个指针能回溯到的所有 commit」。

**误区 4 · 「删除分支会丢代码」**——不一定。如果那些 commit 还能被其他分支 / tag / reflog 引用到，就不会丢；只有**完全孤立**的 commit，才会在 gc 之后消失。

**误区 5 · 「`git pull` 就是 `git fetch`」**——错。`git pull = git fetch + git merge`（或 `git fetch + git rebase`）。**pull 会改工作区，fetch 不会**。

**误区 6 · 「`git checkout` 是切换分支的命令」**——不精确。`checkout` 是个「万能瑞士军刀」，能切分支、能恢复文件、能进 detached HEAD……**Git 2.23 已经拆成 `git switch` 和 `git restore` 两个更清晰的命令**。

**误区 7 · 「rebase 比 merge 高级」**——错。它们**没有优劣，只有场景**：rebase 让历史更线性、更好读；merge 保留了真实的分叉历史。**私有分支用 rebase，共享分支只用 merge**。

**误区 8 · 「`git reset --hard` 之后代码就永远没了」**——错。只要你 commit 过，`git reflog` 30 天内都能找回。真正找不回的是**从未 commit 过**的工作区代码。

**误区 9 · 「暂存区多此一举」**——错。暂存区是 Git 的独特设计——它让你**先自由地改，再优雅地组织提交**（用 `git add -p`）。没有暂存区，就没有原子提交。

**误区 10 · 「大文件适合放 Git」**——错。Git 对源代码天生友好，但**大二进制文件会让仓库无限膨胀**（因为每次修改都要存新快照，无法差量压缩）。大文件请用 Git LFS 或独立存储。

**误区 11 · 「`.gitignore` 能忽略已跟踪的文件」**——错。`.gitignore` 只对**尚未跟踪**的文件生效。已跟踪的文件要用 `git rm --cached` 先撤销跟踪。

**误区 12 · 「`git log` 显示的是全部历史」**——不一定。`git log` 默认只显示**当前分支可达**的历史，其他分支的 commit 需要 `--all`。

**误区 13 · 「已推送的 commit 不能修改」**——技术上能（用 `git push -f`），但**社会上不能**。一旦别人已经拉过你的 commit，你强推等于给他们制造灾难。

**误区 14 · 「Git 保证不丢数据」**——不完全。Git 通过 SHA-1 保证**数据完整性**（内容是否被篡改），但不保证**数据不被人为删除**（`git gc --aggressive` 或某些插件确实能删对象）。

**误区 15 · 「`origin/main` 就是远程的最新状态」**——错。`origin/main` 是「你**上次 fetch 时**的远程 main 快照」，不是「此刻远程的实时状态」。要看最新，得先 `git fetch`。

> **⚡ 一句话**  
> 这 15 个误区，每一个都埋着一起线上事故。把它们内化为「反射」，你就跨过了从「Git 新手」到「Git 玩家」的第一道门槛。

## 十二、动手实战：五分钟环游 Git 世界

本书从第一分钟就坚持「读一百遍不如敲一遍」。请打开终端，跟着敲下面这段脚本——你会在**五分钟内亲眼看到 Git 的四大坐标系**：

```bash
# 1. 创建一个临时仓库
mkdir git-world && cd git-world
git init

# 2. 建一个文件，看看工作区（空间坐标）
echo "Hello Git" > README.md
git status                         # 看到：Untracked

# 3. 加入暂存区
git add README.md
git status                         # 看到：Staged

# 4. 提交——产生第一个 commit（时间坐标）
git commit -m "chapter 01 · first commit"
git log --oneline                  # 看到 SHA-1（身份坐标）

# 5. 看看 .git/objects/ 里真的多了对象
find .git/objects -type f | head   # 看到具体的对象文件

# 6. 用底层命令看看对象类型（身份坐标）
FIRST=$(git rev-parse HEAD)
git cat-file -t $FIRST             # 输出：commit
git cat-file -p $FIRST             # 显示 commit 内容

# 7. 顺藤摸瓜，看 tree 对象
TREE=$(git cat-file -p $FIRST | grep tree | awk '{print $2}')
git cat-file -t $TREE              # 输出：tree
git cat-file -p $TREE              # 显示这棵树包含的文件

# 8. 再看到最底层的 blob（文件内容）
BLOB=$(git cat-file -p $TREE | awk '{print $3}')
git cat-file -t $BLOB              # 输出：blob
git cat-file -p $BLOB              # 输出：Hello Git

# 9. 看看语义坐标：HEAD、branch、tag
cat .git/HEAD                      # 看到：ref: refs/heads/main（或 master）
cat .git/refs/heads/*              # 看到指向的 SHA-1

# 10. 打个标签，理解「不动的指针」
git tag v0.1
cat .git/refs/tags/v0.1            # 看到跟 commit 一样的 SHA-1
```

**十条命令，走完了四大坐标系**——空间（第 2-4 步）、时间（第 4 步）、身份（第 5-8 步）、语义（第 9-10 步）。

如果你亲手敲到了这里，恭喜——你已经比 90% 只会 `add / commit / push` 的开发者更懂 Git 了。

## 十四、思考题

1. **为什么 Git 用 SHA-1 而不是自增 ID？** 如果两个人在两台机器上分别 commit，会不会 ID 冲突？
2. **`.git/objects/` 目录里的 blob 只存内容，不存文件名——那 Git 是怎么知道「哪个 blob 对应哪个文件」的？**（提示：翻回 tree 对象的定义）
3. **HEAD、分支、tag 都能指向 commit，那它们本质上有区别吗？** 为什么 Git 要设计三种指针？
4. **画出一张你所在项目的心智地图**——用本章的四大坐标系（空间 / 时间 / 身份 / 语义），画出你项目的现状。
5. **合并冲突的本质是什么？** 用 DAG 的图论视角回答，不要用「两个人改了同一行」这种表面描述。
