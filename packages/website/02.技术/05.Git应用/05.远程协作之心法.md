## 引子 · 一次 force push 引发的血案

小李在新公司主导了 Git 迁移，走上人生巅峰。团队蒸蒸日上——直到那个周三的下午。

一位新入职的实习生，在 `main` 分支上写了一个功能。他觉得历史「不够干净」，于是敲下了那条命令：

```bash
git rebase -i HEAD~10
```

他把过去十个 commit——**其中包含了另外三个同事的 commit**——「压缩」成了一个。然后：

```bash
git push --force
```

**几秒钟后，Slack 爆炸了**：

> 「谁把 main 分支覆盖了？」  
> 「我今天早上的 commit 呢？」  
> 「测试环境挂了！」

**血案的根因**是：那个实习生**改写了公共分支的历史**，并**强推覆盖了所有人本地已经拿到的历史**。

小李花了一整晚，靠三位同事的 `reflog` 才把丢的 commit 一个一个救回来。

那天之后，小李在团队 Wiki 首页写下了一句话：

> **「已 push 的 commit，永远不 rebase、不 amend、不 force push。」**

这就是本章要教你的**远程协作第一心法**。

## 二、远程仓库的心智模型

**远程仓库（remote）** 本质是：**另一台电脑上的 `.git/` 目录**。它可以在 GitHub、GitLab、Gitee、自建服务器，或者你同事的另一台电脑上。

```
   ┌─────────────────────────────┐
   │  远程仓库（origin）           │
   │   .git/                     │
   │   ├── objects/              │
   │   └── refs/                 │
   └─────────┬───────────────────┘
             │  网络
   ┌─────────┴───────────────────┐
   │                             │
   ▼                             ▼
 你的电脑                        队友的电脑
 .git/objects/                   .git/objects/
 .git/refs/                      .git/refs/
```

**关键洞察**：
- **没有「主」和「从」**——每个 clone 都是完整仓库。所谓「服务器」只是一个**大家约定的同步点**。
- **origin 只是一个别名**——你可以叫它任何名字，也可以有多个 remote。
- **你在本地做的所有事情，都不会影响远程**——直到你 `push`。

**默认的 remote 名字**：

- `origin`：`git clone` 时自动创建的默认 remote。
- `upstream`：约定俗成的「原始仓库」别名（fork 场景下）。

## 三、连接远程：SSH 与 HTTPS

**两种协议**：

| 协议 | URL 样子 | 认证方式 | 优缺点 |
|---|---|---|---|
| **HTTPS** | `https://github.com/user/repo.git` | 用户名+Token | 简单、能穿透防火墙；但每次要输凭据 |
| **SSH** | `git@github.com:user/repo.git` | SSH 公私钥 | 一次配置永久免密；被限制在部分公司网络 |

**推荐**：**日常开发用 SSH**，被防火墙拦截时切换 HTTPS。

**SSH 配置三步**：

```bash
# 1. 生成密钥对
ssh-keygen -t ed25519 -C "your_email@example.com"
# 一路回车，密钥默认存在 ~/.ssh/id_ed25519（私钥）和 id_ed25519.pub（公钥）

# 2. 把公钥内容添加到 GitHub / GitLab 后台
cat ~/.ssh/id_ed25519.pub
# 复制输出，去 GitHub → Settings → SSH Keys → Add new

# 3. 测试连接
ssh -T git@github.com
# 输出：Hi username! You've successfully authenticated
```

**⚠️ 安全禁忌**：
- 私钥（`id_ed25519`）**永远不能上传到任何地方**——它是你的身份证。
- 不要把私钥放进 Docker 镜像、CI 环境（应该用 Deploy Key 或 CI 提供的机制）。

**修改 remote URL**：

```bash
git remote -v                            # 查看当前 remote
git remote set-url origin git@github.com:user/repo.git    # 换成 SSH
git remote add upstream https://github.com/orig/repo.git   # 添加第二个 remote
git remote remove upstream               # 删除 remote
```

## 四、数据同步的三个动作

**核心命令只有三个**——clone、fetch、push。`pull` 是 `fetch + merge` 的组合，不是原子命令。

### 4.1 clone：把整个仓库复制到本地

```bash
git clone git@github.com:user/repo.git
git clone https://github.com/user/repo.git my-dir       # 指定目录名
git clone --depth=1 <URL>                                # 浅克隆（只要最近一版）
git clone --branch=develop <URL>                         # 只克隆某个分支
git clone --recurse-submodules <URL>                     # 带子模块一起
```

**clone 做了什么**：
1. 下载**完整的 `.git/objects/`**。
2. 下载**所有分支引用**。
3. 自动 `checkout` 默认分支到工作区。
4. 自动把远程加为 `origin`。

### 4.2 fetch：只下载，不合并

```bash
git fetch origin                # 拉取 origin 的所有分支更新（不影响工作区）
git fetch origin main           # 只拉某个分支
git fetch --all                 # 所有 remote 都拉一遍
git fetch --prune               # 清理远程已删的分支的本地引用
```

**fetch 的重要特性**：
- 只更新 `origin/main`、`origin/develop` 这些**远程追踪分支**。
- **不动你的本地分支**（`main`、`develop`）。
- 不动工作区。

**这就是为什么老手宁可 `fetch` 也不 `pull`**——先看看远程有什么变化，再决定合并策略。

### 4.3 push：把本地提交传送出去

```bash
git push origin main                     # 把本地 main 推到 origin
git push -u origin feature-login         # 首次推新分支，同时建立追踪
git push --tags                          # 推标签
git push --delete origin old-branch      # 删除远程分支
git push --force                         # ⚠️ 强推（覆盖远程历史，危险）
git push --force-with-lease              # ✅ 安全的强推（远程若被别人改过就拒绝）
```

**push 的两条铁律**：
1. **首次推分支**用 `git push -u origin <branch>`——`-u` 建立**追踪关系**，以后就能直接 `git push` / `git pull`。
2. **强推优先用 `--force-with-lease`**——它会检查远程是否被别人改过，如果被改过就拒绝，避免误覆盖同事的工作。

### 4.4 pull：`fetch` + `merge`/`rebase` 的组合

```bash
git pull                        # 默认 = fetch + merge
git pull --rebase               # fetch + rebase
git pull --ff-only              # 只允许 fast-forward（推荐！）
```

**⚡ 老手心法**：**很少直接 `git pull`**。宁可两步：

```bash
git fetch origin
git log HEAD..origin/main        # 看看远程比我多了什么
git merge origin/main            # 或 git rebase origin/main
```

**理由**：`git pull` 会**自动 merge**——但你**看都没看远程改了什么**就 merge，容易搞出「意料之外的 merge commit」。老手宁可花 20 秒 `fetch` + `log` 看一眼。

**推荐设置**（写进 `~/.gitconfig`）：

```ini
[pull]
    ff = only              # 默认只允许 fast-forward，冲突时明确报错
```

## 五、追踪分支：本地与远程的桥梁

每个本地分支可以「追踪」一个远程分支。这层关系让 `git push` / `git pull` 不用每次都指定分支名。

```bash
# 查看追踪关系
git branch -vv
# 输出：
# * main    a1b2c3 [origin/main]     latest commit
#   feat/x d4e5f6 [origin/feat/x: ahead 2, behind 1] ...

# 手动建立追踪
git branch --set-upstream-to=origin/main main
# 或首次 push 时用 -u
git push -u origin feature-x
```

**追踪分支的信息量**：

- `ahead 2`：本地比远程多 2 个 commit，可以 `push`。
- `behind 1`：远程比本地多 1 个 commit，需要 `pull`。
- `ahead 2, behind 1`：**分叉了**——需要 merge 或 rebase。

**三种远程分支表示**：

| 表示 | 含义 | 谁在动 |
|---|---|---|
| `main` | 本地分支 | 你 |
| `origin/main` | **远程追踪分支**（本地缓存） | `git fetch` 时更新 |
| `origin` 上的 `main` | 真正远程的分支 | 别人 push 时更新 |

**⚠️ 常见误区**：`origin/main` **不是**「实时的远程」——它只是**你上一次 `fetch` 时的远程快照**。所以看远程是否有更新，必须先 `fetch`。

## 六、Pull Request：远程协作的社交礼仪

**Pull Request（PR）** / **Merge Request（MR）** 不是 Git 本身的功能——它是 GitHub / GitLab / Gitee 这些平台在 Git 之上加的**社交层**。但**它是现代协作的通用礼仪**。

**一次 PR 的完整流程**：

```
   1. fork 原仓库              → 你的账号下多一个副本
   2. clone 你的 fork
   3. 建 feature 分支
   4. 写代码 + commit
   5. push 到你 fork 的 feature 分支
   6. 到 GitHub 网页发起 PR    → 目标：原仓库的 main
   7. 团队 review（提意见）
   8. 你根据意见改代码 + push  → PR 自动更新
   9. 通过 review + CI
   10. maintainer 点 Merge     → 你的 commit 进入原仓库主线
   11. 删除 feature 分支       → 清清爽爽
```

**PR 的黄金心法**：

1. **一个 PR 一件事**——不要把「加功能 + 修 bug + 重构」塞一个 PR。
2. **PR 描述写清楚**：**为什么改**、**改了什么**、**怎么测的**。
3. **保持 PR 小**——300 行以内最理想，超过 1000 行 reviewer 就开始「LGTM 但没细看」。
4. **Draft PR**——写到一半可以先开 Draft，让 reviewer 早期看方向对不对。
5. **面对 review 意见，讨论优先于争辩**——review 是团队财富，不是个人攻击。

**分支保护规则（Branch Protection）**——`main` 分支通常配置：

- 禁止直接 push
- 必须通过 PR
- 至少 1~2 位 reviewer 批准
- CI 全绿
- 禁止 force push

**这四条规矩，就是团队 Git 治理的底线**。

## 七、Tag：不动的里程碑

**Tag** 是给某个 commit 打的「不动的标签」。用来标记发布版本、里程碑事件。

```bash
# 轻量标签（只是一个别名）
git tag v1.0.0

# 附注标签（推荐——带作者、时间、消息、可签名）
git tag -a v1.0.0 -m "Release 1.0.0"

# 给指定的 commit 打标签
git tag -a v1.0.0 abc123 -m "Release 1.0.0"

# 查看
git tag                               # 列出所有 tag
git tag -l "v1.*"                     # 按模式过滤
git show v1.0.0                       # 看 tag 详情

# 推送 tag（重要！push 默认不推 tag）
git push origin v1.0.0                # 推单个
git push --tags                       # 推所有

# 删除
git tag -d v1.0.0                     # 删本地
git push --delete origin v1.0.0       # 删远程
```

**版本号推荐用 SemVer**：

```
   v {MAJOR} . {MINOR} . {PATCH}
     大改      新功能    修 bug
```

- `v1.0.0` → `v1.0.1`：修 bug
- `v1.0.0` → `v1.1.0`：加功能，兼容
- `v1.0.0` → `v2.0.0`：破坏性改动

**Tag 与 GitHub Release**：GitHub 上打了 Release，其实底层就是 tag + 额外的说明页面。**Release Notes 是 tag 的社交外壳**。

## 八、心智模型剖析：push / pull 底层做了什么

**`git push` 底层的四步**（简化）：

1. **协商共同祖先**：本地问远程「你有哪些 commit？我有哪些？」
2. **打包缺失对象**：把远程没有的 blob / tree / commit 打成 pack 文件。
3. **传输**：pack 文件走 SSH 或 HTTPS 传过去。
4. **更新远程引用**：告诉远程「把你的 `refs/heads/main` 移到我推的这个 commit」。

**关键性质**：

- **只传缺失部分**——不是每次都传整个仓库（这是 pack 的功劳）。
- **默认拒绝非快进推送**——如果远程分支不是本地分支的祖先，push 会被拒绝。这就是**为什么 `git push --force` 才能覆盖历史**。

**`git pull` 底层的两步**：

1. **fetch**：把远程的对象和引用拉到本地（更新 `origin/main`）。
2. **merge 或 rebase**：把 `origin/main` 合并到本地 `main`。

**默认策略取决于配置**：

```bash
git config pull.rebase false    # merge（默认）
git config pull.rebase true     # rebase
git config pull.ff only         # 只快进（推荐）
```

**⚡ 老手推荐**：`pull.ff = only` + 手动 fetch/merge/rebase。**明确性大于自动化**。

## 九、Git 传输协议全景：smart/dumb HTTP、SSH、git://、file://

`git push` 和 `git fetch` 在网络层到底是怎么传数据的？**答案：Git 支持四大传输协议**——每种适配不同场景。理解它们，你就能诊断 99% 的网络问题。

### 9.1 四大协议对比

| 协议 | URL 前缀 | 端口 | 加密 | 认证 | 现状 |
|---|---|---|---|---|---|
| **Local** | `/path/to/repo` 或 `file://...` | — | 否 | 文件系统权限 | 本地或 NFS 场景 |
| **Git** | `git://...` | 9418 | 否 | **无认证** | 只读镜像，几乎绝迹 |
| **SSH** | `git@host:path` 或 `ssh://...` | 22 | 是 | SSH 密钥 | 主流之一 |
| **HTTPS** | `https://...` | 443 | 是 | 密码 / token | 主流之一 |
| **HTTP（旧）** | `http://...` | 80 | 否 | 密码 | 已被 HTTPS 取代 |

**几点冷知识**：

- `git://` 协议**没有加密、没有认证**——只能用来 clone 只读镜像。GitHub 曾经支持 `git://github.com/...`，**2022 年 3 月正式关停**（安全问题）。
- **SSH 是运维圈的最爱**——公私钥认证、加密传输、能免密码。GitHub Actions、CI/CD 系统都推荐 SSH。
- **HTTPS 是防火墙时代的救星**——很多公司防火墙只放 80/443 端口，SSH 22 端口被封。所以内网、隔离环境几乎只能用 HTTPS。
- **GitHub 2021 年 8 月起，HTTPS 强制用 Personal Access Token**，不再接受账号密码。这是 Git 历史上一次重要的安全升级。

### 9.2 Smart HTTP vs Dumb HTTP

HTTP 协议内部还分**两代**：

- **Dumb HTTP（哑 HTTP）**——服务器只是普通静态文件服务器，Git 客户端**逐个下载对象文件**。慢、笨、不支持 push。**现在几乎绝迹**。
- **Smart HTTP（智能 HTTP）**——服务器上跑一个 `git-http-backend` CGI 程序，Git 客户端与它「协商」——只下载「你缺少的对象」。**这才是现代 GitHub / GitLab 用的**。

**从 URL 看不出来是哪一种**——都是 `https://...`。**握手时 Git 客户端会先问服务器：**「你懂 smart HTTP 吗？」——懂就走 smart 协议，不懂降级到 dumb。

### 9.3 pack negotiation（打包协商）——Git 网络传输的核心

不管走 SSH 还是 HTTP，Git 传输的核心都是同一件事：**协商双方各自有哪些对象，然后把「你没有的」打包成一个 pack 文件传过去**。

**push 时的协商过程**：

```
你（本地）              →           远程（GitHub）

1. 我要 push refs/heads/main
                        →
2. 我有这些 refs（列出 tips）
                        ←   
3. 我这边 main 是 abc123，你的 def456
   我算一下：你还缺哪些对象
                        →
4. 我给你造个 pack 文件，含 3.2 MB 数据
                        →   pack file →
5. 你解压 pack、更新 refs、告诉我结果
                        ←
6. 更新成功 / 失败（rejected）
```

**过程精妙之处**：**Git 只传「差集」——你没有的对象**。这就是为什么改一行代码 push 只用几 KB，而不是几十 MB。

**你能看到这个过程**：

```bash
GIT_TRACE_PACKET=1 git push origin main
# 会打印每一个协议 packet，能看到 want/have 的协商
```

### 9.4 SSH 密钥的一切

大多数人用 SSH，但从没深究过密钥怎么配。这里给你**一次到位的完整流程**：

```bash
# 1. 生成密钥对（推荐 Ed25519，比 RSA 更安全、更短）
ssh-keygen -t ed25519 -C "you@example.com"

# 会生成两个文件：
#   ~/.ssh/id_ed25519      ← 私钥（不能给任何人）
#   ~/.ssh/id_ed25519.pub  ← 公钥（可以贴到 GitHub）

# 2. 把公钥贴到 GitHub Settings > SSH Keys
cat ~/.ssh/id_ed25519.pub    # 复制这里的输出

# 3. 测试连接
ssh -T git@github.com
# Hi <yourname>! You've successfully authenticated...

# 4. 一台机器多个 GitHub 账号？配 ~/.ssh/config
cat >> ~/.ssh/config << 'EOF'
Host github-work
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_work

Host github-personal
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_personal
EOF

# 使用时把 URL 里的 github.com 换成 github-work
git clone git@github-work:company/repo.git
```

**SSH 密钥安全铁律**：

- **私钥永远不出机器**——不 push、不上传、不发消息。
- **公钥可以随便贴**——GitHub / GitLab / 服务器 authorized_keys 都行。
- **定期轮换**——每 1-2 年换一次密钥，撤掉旧的。
- **别用 RSA 1024**——已经被证明可破解。用 Ed25519 或 RSA 4096+。

### 9.5 HTTPS 与 credential helper

HTTPS 每次 push 都要输密码？——不用。用 **credential helper**：

```bash
# Mac：用系统钥匙串
git config --global credential.helper osxkeychain

# Windows：用 Windows 凭据管理器
git config --global credential.helper manager

# Linux：用内存缓存（15 分钟）
git config --global credential.helper 'cache --timeout=3600'

# 全平台：用官方 Git Credential Manager
# https://github.com/git-ecosystem/git-credential-manager
```

**GitHub Personal Access Token 生成**：Settings → Developer settings → PAT → Generate new token。**存到 credential helper，从此免密码**。

> **⚡ 一句话**  
> **内网 / 家里 → SSH，企业内隔离 → HTTPS**——两个都会，走遍天下。

## 十、shallow clone 与 partial clone：大仓库的救命稻草

Linux 内核仓库 5 GB，Chromium 仓库 40 GB，Windows 仓库 300 GB——**「完整 clone」不再是理所当然的操作**。Git 演进出了两大「按需下载」机制。

### 10.1 shallow clone（浅克隆）

**只克隆最近 N 个 commit**——历史被截断。

```bash
# 只要最近 1 个 commit
git clone --depth=1 https://github.com/torvalds/linux.git

# 只要最近 30 天
git clone --shallow-since="30 days ago" <URL>

# 只要某个分支
git clone --single-branch --branch=main <URL>

# 后续加深
git fetch --deepen=10       # 再往前多要 10 个 commit
git fetch --unshallow       # 变回完整仓库
```

**shallow clone 的限制**：

- **不能 push 全部历史**（因为你就没有全部）——但可以正常 push 新 commit。
- **`git log` 只能看到浅层内的历史**。
- **有些操作会退化**——比如某些 merge、bisect。

**主要用途**：
- **CI/CD**：CI 只需要最新代码，不需要历史——`--depth=1` 能省几十倍时间。
- **一次性构建**：只 build 一次的场景。
- **大仓库快速浏览**。

### 10.2 partial clone（部分克隆）——Git 2.19+ 新特性

比 shallow 更聪明——**克隆完整的 commit 历史，但按需下载 blob 或 tree**。

```bash
# 不下载任何 blob（只要 commit + tree）
git clone --filter=blob:none <URL>

# 不下载大于 1 MB 的 blob
git clone --filter=blob:limit=1m <URL>

# 只下载指定路径下的 tree（部分树）
git clone --filter=sparse:oid=<blob-hash> <URL>
```

**工作原理**：

- Git 只下载**元数据**（commit + tree）。
- 当你 checkout 某个分支时，Git **按需从服务器拉那些 blob**。
- 从此每一次 checkout 都可能触发网络请求。

**partial clone 的适用场景**：
- **超大仓库**：Windows / Android 这种数百 GB 级别。
- **Monorepo**：你只关心其中一小部分文件。
- **需要完整历史，但不需要所有文件内容**——比如做提交历史分析。

**结合 `sparse-checkout`（稀疏检出）**：

```bash
# 完整克隆但只 checkout 指定子目录
git clone --filter=blob:none --sparse <URL>
cd <repo>
git sparse-checkout set frontend/ shared/
# 从此工作区只会有 frontend/ 和 shared/
```

- **微软的 VFS for Git**（后来叫 GVFS）就是这套思路的先驱，用来管理 Windows 3 亿行代码。
- **Meta（Facebook）** 用类似技术管理他们的 Mercurial monorepo。

> **⚡ 一句话**  
> shallow = 少历史；partial = 少内容。**大仓库时代，两者是必备武器**。

## 十一、submodule vs subtree：仓库嵌套的两条路

一个仓库里想嵌套另一个仓库（比如一个主项目引用一个共享库），Git 提供了两种截然不同的方案——**submodule 和 subtree**。它们**代表两种世界观**。

### 11.1 submodule（子模块）——「引用式」

**核心思想**：主仓库只存一个「指针」，指向另一个仓库的某个 commit。

```bash
# 添加子模块
git submodule add https://github.com/user/lib.git third_party/lib
git commit -m "chore: add lib as submodule"

# clone 一个含子模块的仓库时，需要递归 clone
git clone --recurse-submodules <URL>

# 或者 clone 后再单独初始化
git submodule update --init --recursive

# 更新子模块到最新
cd third_party/lib
git pull origin main
cd ..
git add third_party/lib
git commit -m "chore: bump lib"
```

**submodule 的机制**：
- 主仓库存的是**一个 gitlink 对象**（模式 160000），值为子模块的 commit SHA-1。
- 子模块的代码**物理上不在主仓库的对象数据库里**——它是**独立仓库**。
- `.gitmodules` 文件记录了子模块的 URL 和路径。

**submodule 的痛点**：
- 每个人都得手动 `submodule update` 才能同步。
- 切分支时子模块**不会自动跟着切**。
- clone 忘了 `--recurse-submodules` 就得再来一遍。

### 11.2 subtree（子树）——「合并式」

**核心思想**：把另一个仓库的**代码直接合进主仓库**，历史也合进来。

```bash
# 添加 subtree
git subtree add --prefix=third_party/lib https://github.com/user/lib.git main --squash
# --squash：压缩子仓库的所有历史为一个 commit

# 更新 subtree
git subtree pull --prefix=third_party/lib https://github.com/user/lib.git main --squash

# 把 subtree 里的改动推回原仓库
git subtree push --prefix=third_party/lib https://github.com/user/lib.git feature-branch
```

**subtree 的机制**：
- 子仓库的代码**物理上在主仓库的对象数据库里**——就是一个普通目录。
- **没有额外配置文件**（`.gitmodules` 那种）——完全透明。
- **clone 主仓库时不需要任何特殊操作**——所有内容都在。

### 11.3 何时用哪个？

| 场景 | 推荐 |
|---|---|
| 想让子仓库保持完全独立（分开维护、分开版本） | **submodule** |
| 想让所有人 clone 后就能编译，不需要额外命令 | **subtree** |
| 想向子仓库贡献代码（双向工作） | **submodule**（更清晰） |
| 主要是「用别人的库」 | **subtree**（更简单） |
| CI/CD 复杂度低 | **subtree** |
| 项目组要求「所有依赖必须锁定版本」 | **submodule** |

**Google 和 Meta 的选择**：都不用 submodule 也不用 subtree——他们用 **monorepo**，把所有代码放一个仓库里。这是第三条路，第 07 章会讲。

> **⚡ 一句话**  
> **submodule 是「引用」，subtree 是「拷贝」**。选哪个，取决于你希望「独立」还是「一体」。

## 十二、Git 签名：GPG、SSH、S/MIME 三种方案

GitHub 上你可能见过 commit 旁边的绿色 **Verified** 徽章——那就是**已签名的 commit**。它保证「**这个 commit 真的是这个人签的，不是别人冒名的**」。

### 12.1 为什么要签名？

**故事**：2019 年发生过一次事件——攻击者用**别人的名字和邮箱**提交了大量恶意 commit 到某开源项目。因为 Git 的 `user.name` 和 `user.email` 只是**普通字符串**，谁都能填别人的——不签名的话，历史里的作者信息**根本无法验证**。

签名解决的问题：**证明「这个 commit 确实是我签的」**。

### 12.2 三种签名方案对比

| 方案 | 出现时间 | 密钥基础设施 | 上手难度 | 现状 |
|---|---|---|---|---|
| **GPG** | 2005（Git 从一开始就支持） | GPG 密钥 + 公钥服务器 | 高（需要配 gpg-agent） | 老牌方案 |
| **SSH** | Git 2.34（2021） | 复用你已有的 SSH 密钥 | 低 | **现代推荐** |
| **X.509 / S/MIME** | Git 2.19+ | 企业 CA 证书 | 中 | 企业内网 |

### 12.3 SSH 签名（现代推荐）

**Git 2.34+** 支持用 SSH 密钥签名——**你已经在用 SSH 推代码，那就复用同一把密钥签 commit，一分钟配好**：

```bash
# 1. 告诉 Git 用 SSH 签名，指定用哪个公钥
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub

# 2. 默认所有 commit 都签
git config --global commit.gpgsign true
git config --global tag.gpgsign true

# 3. 手动签一个 commit
git commit -S -m "feat: something"

# 4. 查看签名
git log --show-signature -1

# 5. 上传公钥到 GitHub Settings → SSH and GPG keys → New SSH key
#    选 "Signing Key"（不是 "Authentication Key"）
```

### 12.4 GPG 签名（老牌方案）

```bash
# 1. 生成 GPG 密钥
gpg --full-generate-key
# 选 RSA and RSA、4096 位、期限自选

# 2. 列出密钥
gpg --list-secret-keys --keyid-format=long
# sec   rsa4096/ABCDEF1234567890 ...

# 3. 配置 Git
git config --global user.signingkey ABCDEF1234567890
git config --global commit.gpgsign true

# 4. 导出公钥（贴到 GitHub）
gpg --armor --export ABCDEF1234567890
```

### 12.5 验证签名

```bash
# 单个 commit
git verify-commit HEAD

# log 里显示签名状态
git log --show-signature

# tag 验证
git verify-tag v1.0.0
```

**GitHub / GitLab 会显示徽章**：
- ✅ **Verified**：签名有效
- ⚠️ **Unverified**：无签名或签名无效
- 🚫 **Signed by unknown**：签名有效但公钥不在 GitHub 记录里

### 12.6 什么时候必须签？

- **开源项目 maintainer**：证明每个 release tag 真的是你打的。
- **金融 / 医疗 / 安全关键**：合规要求。
- **多人共享的构建环境**：CI 服务器上要能验证「这真是那个开发者提的」。

**日常个人项目可以不签**——但**养成习惯不会错**。SSH 签名一分钟配好，几乎零负担。

> **⚡ 一句话**  
> **签名不是可有可无的花哨功能——它是历史真实性的唯一防线**。Git 提供了工具，用不用取决于你。

## 十三、动手实战：从零到一次完整的 PR

以 GitHub 为例，走一次完整的开源协作流程：

```bash
# ────── 阶段 1：Fork + Clone ──────
# 在 GitHub 上 fork 目标仓库到你的账号（网页操作）

git clone git@github.com:YOUR_USERNAME/some-project.git
cd some-project

# 加上「原仓库」的地址，方便同步上游
git remote add upstream git@github.com:ORIGINAL/some-project.git
git remote -v
# 应该看到：
# origin    git@github.com:YOUR/some-project.git    (fetch/push)
# upstream  git@github.com:ORIGINAL/some-project.git (fetch/push)

# ────── 阶段 2：建功能分支 ──────
git switch -c feat/dark-mode

# ────── 阶段 3：写代码 + 提交 ──────
# ... 写代码 ...
git add .
git commit -m "feat(theme): add dark mode support"

# 多做几个 commit
# ... 更多代码 ...
git commit -am "test(theme): add dark mode tests"

# ────── 阶段 4：同步上游（防止 PR 冲突） ──────
git fetch upstream
git rebase upstream/main            # 保证 PR 是干净的 fast-forward

# ────── 阶段 5：推到自己的 fork ──────
git push -u origin feat/dark-mode

# ────── 阶段 6：网页发起 PR ──────
# GitHub 上点「Compare & pull request」
# 填清楚：
#   - 标题：feat(theme): add dark mode support
#   - 描述：动机、方案、测试情况、截图（如果有 UI）

# ────── 阶段 7：根据 review 修改 ──────
# ... 改代码 ...
git commit -am "fix: address review comments"
git push                            # PR 会自动更新（因为 upstream 已经设置）

# 若需要压缩 commit：
git rebase -i upstream/main         # 把多次修改合成一个漂亮的 commit
git push --force-with-lease         # ⚠️ 私有 PR 分支上可以，公共分支绝不

# ────── 阶段 8：合并后清理 ──────
# maintainer 合并 PR 之后：
git switch main
git fetch upstream
git rebase upstream/main            # 同步本地 main
git push                            # 更新自己的 fork
git branch -d feat/dark-mode        # 删本地
git push --delete origin feat/dark-mode   # 删远程
```

**这段脚本浓缩了开源协作的完整仪式**——你在 GitHub 上任何一个 star 上百的开源项目里提 PR，走的都是这套流程。

## 十四、远程八诫

1. **公共分支永不 rebase / amend / force push**（新人第一戒律）。
2. **首次 push 用 `-u`**，建立追踪，之后 `git push` / `git pull` 免参数。
3. **强推优先 `--force-with-lease`**——它会检查远程有没有别人的新 commit。
4. **`git pull.ff = only`**——把「自动 merge」变成「明确报错」。
5. **敏感信息（密钥、密码、Token）永不 push**——一旦历史里有，事后删了也没用（详见第 08 章）。
6. **PR 一个只做一件事**——300 行内最理想。
7. **提 PR 前，先 `rebase upstream/main`**——保证 PR 是干净的 fast-forward。
8. **合并后立即删分支**——公共分支不留野草。

## 十六、思考题

1. **如果 `origin/main` 和你本地 `main` 分叉了（各有新 commit）**，`git pull` 默认行为是什么？如果你配了 `pull.ff = only`，它会怎么做？为什么后者更安全？
2. **`git push --force` 和 `git push --force-with-lease` 到底有什么不同？** 举一个 `--force-with-lease` 能救你但 `--force` 会毁掉团队的场景。
3. **你 fork 了一个项目，一年之后想同步上游最新的 100 个 commit**——你会怎么操作？（提示：`upstream` remote + rebase）
4. **一个 PR 已经开了 500 行，reviewer 让你「拆成两个 PR」**——怎么拆？（提示：`git rebase -i` + 建两个新分支 + `cherry-pick`）

## 下一章预告

一个人 + 分支 + 远程——你已经掌握了 Git 的**主战武器**。但真实开发里，总有一些「特种任务」需要**特种兵**：

- 「我 add 了一半，突然要切分支处理紧急问题」——**stash**（暂存箱）
- 「另一个分支的某个 commit 我要」——**cherry-pick**（摘樱桃）
- 「我不知道 bug 是哪次 commit 引入的，历史 200 条」——**bisect**（二分查找）
- 「这行代码是谁写的？」——**blame**（追凶）

**第 06 章 · 特种作战三件套**——把 Git 从「日常工具」升级为「战术平台」。

> 「三件武器，改变一个战场。」
