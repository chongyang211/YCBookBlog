## 一、🚀 开始与配置

### 🎬 1.1 新建一个本地仓库

> 从零开始，第一次 `git init`。

```bash
mkdir my-project && cd my-project
git init --initial-branch=main
echo "# My Project" > README.md
cat > .gitignore <<EOF
node_modules/
.env
.DS_Store
*.log
EOF
git add .
git commit -m "chore: initial commit"

# 关联远程（先在 GitHub / GitLab 建好空仓库）
git remote add origin git@github.com:user/repo.git
git push -u origin main
```

⚠️ **忘记建 `.gitignore` 就 push**——`node_modules` / `.env` 上去就再也擦不干净了（除非用 filter-repo 重写历史）。

### 🎬 1.2 克隆一个远程仓库

> 加入一个已有项目。

```bash
git clone git@github.com:team/project.git
cd project

# 想放到自定义目录名
git clone git@github.com:team/project.git my-dir

# 只拉最新一次 commit（大仓库救星）
git clone --depth 1 git@github.com:team/project.git

# 只克隆某个分支
git clone -b develop --single-branch git@github.com:team/project.git
```

💡 CI 环境建议 `--depth 1`，本地长期开发别用（`bisect`、`blame` 会看不到历史）。

### 🎬 1.3 配置个人身份（首次装 Git 必做）

```bash
git config --global user.name "杨充"
git config --global user.email "your@email.com"
git config --global init.defaultBranch main
git config --global pull.ff only                # pull 只允许 fast-forward
git config --global core.editor "code --wait"   # 用 VS Code 编辑 message
git config --global core.autocrlf input         # macOS/Linux（Windows 用 true）
git config --global fetch.prune true            # fetch 自动清理远端已删引用
```

**看看当前生效的配置来自哪个文件**：

```bash
git config --list --show-origin
```

### 🎬 1.4 多身份切换（公司项目 + 个人项目）

> 公司邮箱和个人邮箱不能混用。

**方案 A · 单仓库覆盖全局**（简单）：

```bash
cd company-project
git config user.name "张三"
git config user.email "zhangsan@company.com"
```

**方案 B · 按目录自动切换**（推荐，一次配终身）：

```bash
# ~/.gitconfig 全局默认（个人）
[user]
    name = 杨充
    email = personal@email.com

# ~/.gitconfig 追加：进 ~/work/ 目录自动切公司身份
[includeIf "gitdir:~/work/"]
    path = ~/.gitconfig-work

# ~/.gitconfig-work
[user]
    name = 张三
    email = zhangsan@company.com
    signingkey = COMPANY_GPG_KEY
```

⚠️ **邮箱写错了**：过去所有 commit 都不算你在 GitHub 的贡献——用 `git log --author` 排查。

### 🎬 1.5 首次配置 SSH 密钥

```bash
# 1) 生成 ed25519 密钥（比 rsa 更现代）
ssh-keygen -t ed25519 -C "your@email.com"

# 2) 加入 ssh-agent
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# 3) 复制公钥内容
cat ~/.ssh/id_ed25519.pub
# macOS：
pbcopy < ~/.ssh/id_ed25519.pub

# 4) 粘贴到 GitHub → Settings → SSH keys

# 5) 测试
ssh -T git@github.com
```

⚠️ 出现 `Permission denied (publickey)` → 90% 是密钥没加到 agent，或加错了账号。

### 🎬 1.6 配置 GPG / SSH 签名（提交显示 Verified 徽章）

```bash
# GPG 方式
gpg --full-generate-key                       # 选 RSA 4096
gpg --list-secret-keys --keyid-format=long    # 找到 KEY_ID
git config --global user.signingkey KEY_ID
git config --global commit.gpgsign true       # 每次 commit 自动签

# 现代 SSH 签名（Git 2.34+，用 SSH key 签，无需 GPG）
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
```

💡 GitHub / GitLab 都要把公钥重新添加到「Signing keys」栏（跟「Authentication keys」是分开的）。

## 二、📝 提交代码

### 🎬 2.1 看一眼再提交（好习惯）

```bash
git status -s               # 简洁状态
git diff                    # 未 add 的改动
git diff --staged           # 已 add 未 commit 的改动
git diff HEAD               # 全部未 commit 的改动（工作区 + 暂存区）
git diff --stat             # 只看统计（哪些文件改了多少行）
```

💡 **先看再 add，先 add 再 commit——每一步都要「看得见」**。

### 🎬 2.2 提交所有改动

```bash
git add .                           # 加当前目录所有改动
git add -A                          # 加整个仓库所有改动（含删除）
git commit -m "feat: add login"

# 一步到位（跳过 add，只对已跟踪文件生效）
git commit -am "feat: add login"
```

### 🎬 2.3 精细提交部分改动（`add -p`）

> 一次改了 3 个功能，想分成 3 个 commit。

```bash
git add -p            # 交互式：每个 hunk 问你 y/n/s(拆分)/e(手改)
git commit -m "feat: part 1"

git add -p
git commit -m "refactor: part 2"
```

💡 **`add -p` 是资深工程师的日常**——commit 越小越好回滚、越好 review。

### 🎬 2.4 修改上一次 commit（还没 push）

```bash
# 只改 message
git commit --amend -m "fix: 正确的 message"

# 追加漏 add 的文件到上次 commit
git add forgotten.js
git commit --amend --no-edit         # 不改 message

# 改作者（如身份配错了）
git commit --amend --author="New Name <new@email>" --no-edit
```

⚠️ **已经 push 过就别 amend**——除非确定没人拉过（否则要 `--force-with-lease`）。

### 🎬 2.5 把一个大 commit 拆成多个

> 上次一口气提交了太多改动，想拆开。

```bash
git reset --soft HEAD~1        # 撤销 commit，改动回到暂存区
git reset HEAD                 # 再把暂存区放回工作区
git add -p                     # 分批 add
git commit -m "feat: part 1"
git add -p
git commit -m "test: part 2"
```

### 🎬 2.6 合并连续多个 commit 为一个（squash）

```bash
git rebase -i HEAD~5           # 打开最近 5 个 commit 的编辑窗口
# 把后 4 行的 pick 改成 squash（或 s）
# 保存 → 编辑合并后的 message → 保存
```

💡 只想合并 message 不想留旧 message → 用 `fixup`（或 `f`）代替 `squash`。

## 三、🌿 分支操作

### 🎬 3.1 新建分支 + 切过去

```bash
# 现代命令（Git 2.23+，推荐）
git switch -c feat/login              # 基于当前分支新建并切换
git switch -c feat/login origin/main  # 基于远程 main 新建

# 老命令（兼容旧版本）
git checkout -b feat/login
```

### 🎬 3.2 切换分支

```bash
git switch main
git switch -                          # 回到上一个分支（像 cd -）
git checkout main                     # 老写法
```

⚠️ 工作区有未提交改动时切换：
- 改动跟目标分支不冲突 → 会带过去
- 冲突 → 拒绝切换 → 先 `git stash` 或 commit

### 🎬 3.3 基于某个提交 / tag / 远程分支建分支

```bash
git switch -c hotfix/urgent v1.2.0            # 基于 tag
git switch -c debug abc123                    # 基于某个 commit
git switch -c feat/x origin/feature-x         # 基于远程分支
```

### 🎬 3.4 查看所有分支

```bash
git branch                    # 本地分支
git branch -a                 # 本地 + 远程
git branch -r                 # 仅远程
git branch -vv                # 显示每个分支的上游 + 最新 commit
git branch --merged main      # 已合并进 main 的分支
git branch --no-merged main   # 未合并进 main 的分支
```

### 🎬 3.5 重命名分支（本地 + 远程）

```bash
# 本地重命名
git branch -m old-name new-name           # 改别的分支
git branch -m new-name                    # 改当前分支

# 同步到远程（三步）
git push origin :old-name                 # 删远程旧的
git push -u origin new-name               # 推新的
```

### 🎬 3.6 删除分支

```bash
# 本地
git branch -d feat/done          # 安全删（未合并会拒绝）
git branch -D feat/abandon       # 强制删（未合并也删）

# 远程
git push origin --delete feat/done
# 或（老写法）
git push origin :feat/done
```

### 🎬 3.7 批量清理已合并进 main 的本地分支

```bash
git branch --merged main | grep -Ev '^\*|main|master|develop' | xargs -r git branch -d
```

💡 每周清一次，让 `git branch` 输出短短几行。

### 🎬 3.8 查看分支关系图

```bash
git log --oneline --graph --all --decorate

# 配成 alias（一次配终身）
git config --global alias.lg "log --oneline --graph --all --decorate"
git lg
```

## 四、🔀 合并代码

> **本节是全书最高频操作，请重点收藏**。

### 🎬 4.1 普通 merge（保留分叉历史）

> 把 feature 分支合进 main，保留分叉历史线。

```bash
git switch main
git pull                              # 先同步一下
git merge feat/login                  # 合并
git push
```

💡 如果 feature 从最新 main 分出且没别的人动 main → 会 **fast-forward**（不产生 merge commit）。

### 🎬 4.2 强制留下 merge commit（`--no-ff`）

> 保留「这是一次合并」的痕迹，便于日后整体回滚。

```bash
git merge --no-ff feat/login -m "Merge feat/login into main"
```

💡 GitHub 的「Create a merge commit」按钮 = `--no-ff`。**团队协作推荐**。

### 🎬 4.3 rebase（把历史变直线）

> 想让 feature 分支「站在最新 main 之上」，历史更干净。

```bash
git switch feat/login
git fetch origin
git rebase origin/main

# 遇到冲突 → 解决 → 继续
git add <冲突文件>
git rebase --continue

# 想放弃这次 rebase
git rebase --abort
```

⚠️ **公共分支永远不要 rebase**——会让所有拉过它的人炸掉。

### 🎬 4.4 交互式 rebase（整理历史）

> merge 前把 5 个乱糟糟的 commit 整理成 2 个漂亮的 commit。

```bash
git rebase -i HEAD~5
# 编辑器打开后，把每行的 pick 改成：
#   pick   → 保留
#   reword → 只改 message
#   squash → 合并到上一个 commit，合并 message
#   fixup  → 合并到上一个 commit，丢弃 message
#   drop   → 删除这个 commit
```

### 🎬 4.5 squash merge（合成一个 commit 后再合并）

> feature 分支上有一堆碎 commit，希望到 main 上只呈现一个 commit。

```bash
git switch main
git merge --squash feat/login
git commit -m "feat: add login (#123)"
```

💡 GitHub 「Squash and merge」按钮 = 此操作。**适合大量小 commit 的 feature**。

### 🎬 4.6 三种合并方式对比

| 方式 | 命令 | 历史线条 | 何时用 |
|---|---|---|---|
| **fast-forward** | `git merge` | 一条直线 | feature 简短、无人动 main |
| **merge commit** | `git merge --no-ff` | 保留分叉 | 团队协作，需可追溯完整 feature |
| **rebase** | `git rebase main` | 直线（feature 前移） | 私有分支，追求整洁 |
| **squash merge** | `git merge --squash` | 只留 1 个 commit | feature 有很多碎 commit |

### 🎬 4.7 合并只想要某几个文件

> 想合别人分支上的部分改动，不合全部。

```bash
git checkout other-branch -- path/to/file1 path/to/file2
# 或现代写法：
git restore --source other-branch --staged --worktree path/to/file
git commit -m "chore: sync files from other-branch"
```

### 🎬 4.8 合并时保留某一方的版本

```bash
# 冲突时全部用 我方（当前分支）版本
git merge -X ours other-branch

# 冲突时全部用 对方（要合入的分支）版本
git merge -X theirs other-branch
```

⚠️ `-X ours` ≠ `-s ours`：前者只在冲突时用我方，后者**整个合并的内容都用我方**（相当于假装合了，实际啥也没变）。

## 五、🍒 Cherry-pick（挑选提交）

### 🎬 5.1 把别处的一个 commit 摘到当前分支

```bash
git switch main
git cherry-pick abc123
```

### 🎬 5.2 一次挑多个（连续 或 离散）

```bash
# 连续区间（左开右闭）：不含 abc123，含 def456
git cherry-pick abc123..def456

# 连续区间（左闭右闭）：都含
git cherry-pick abc123^..def456

# 离散的多个
git cherry-pick abc123 def456 789xyz
```

### 🎬 5.3 摘过来但先不 commit（想再改改）

```bash
git cherry-pick -n abc123        # -n = --no-commit
# 改代码 / 改 message
git commit
```

### 🎬 5.4 摘一个 merge commit

```bash
git cherry-pick -m 1 <merge-sha>     # -m 1 表示保留第一父的分支视角
```

⚠️ merge commit 的 cherry-pick 要指定 `-m`，否则报错。

### 🎬 5.5 cherry-pick 冲突了

```bash
# 冲突 → 手动解决 → 继续
git add <冲突文件>
git cherry-pick --continue

# 跳过这一个（若在批量 pick 中）
git cherry-pick --skip

# 放弃整个 cherry-pick
git cherry-pick --abort
```

### 🎬 5.6 只想要 commit 里的部分文件

> commit 里改了 5 个文件，只想要其中 2 个。

```bash
# 方案：先 cherry-pick 不提交，再选择性 reset
git cherry-pick -n abc123
git reset HEAD                       # 全部退到工作区
git add path/to/file1 path/to/file2  # 只 add 想要的
git checkout -- .                    # 丢弃其他改动
git commit -m "chore: pick partial from abc123"
```

## 六、💥 解决冲突

### 🎬 6.1 冲突长什么样

打开冲突文件，你会看到：

```
<<<<<<< HEAD
console.log("我这边的写法");
=======
console.log("对方的写法");
>>>>>>> feat/other
```

- `<<<<<<< HEAD` 到 `=======`：**当前分支**的内容
- `=======` 到 `>>>>>>> xxx`：**要合入的分支**的内容

💡 开 `merge.conflictstyle = zdiff3` 后会多显示「共同祖先」段，判断更准。

### 🎬 6.2 merge 冲突处理三步走

```bash
# 1) 看谁冲突了
git status                    # 红字的就是冲突文件

# 2) 一个一个改（编辑器打开，删掉标记符 <<< === >>>）
code path/to/conflict.js

# 3) 改完标记为已解决 + 提交
git add path/to/conflict.js
git commit                    # merge 会自动生成 message，直接保存

# ⛔ 想放弃这次 merge
git merge --abort
```

### 🎬 6.3 rebase 冲突处理

```bash
# rebase 中冲突 → 解决 → 继续
git add <冲突文件>
git rebase --continue

# 跳过这个 commit（若这个 commit 已经不需要）
git rebase --skip

# 放弃整个 rebase，回到 rebase 前状态
git rebase --abort
```

### 🎬 6.4 快速采纳「我方 / 对方」全部改动

> 冲突文件不想手动改，直接选一方。

```bash
# 用我方的版本（当前分支）
git checkout --ours path/to/file
git add path/to/file

# 用对方的版本（要合入的分支）
git checkout --theirs path/to/file
git add path/to/file
```

⚠️ **rebase 中的「ours / theirs」是反的**：因为 rebase 视角下，你的 commit 是「对方」，被 rebase 到的分支是「我方」。

### 🎬 6.5 用可视化工具解决冲突

```bash
git mergetool                        # 用默认工具

# 配 VS Code 为默认
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait $MERGED'
```

**推荐工具**：VS Code（自带三窗对比）、GitLens 插件、Meld、Beyond Compare。

### 🎬 6.6 让 Git 记住冲突的解法（rerere）

> 你在 rebase 时解过一次某个冲突，下次同样冲突自动应用。

```bash
git config --global rerere.enabled true
```

💡 长时间维护的 feature 分支反复 rebase main 时救星级功能。

### 🎬 6.7 现代化的冲突显示（zdiff3）

```bash
git config --global merge.conflictstyle zdiff3
```

之后冲突会显示：

```
<<<<<<< HEAD
我方
||||||| 共同祖先
祖先版本
=======
对方
>>>>>>> feat/other
```

💡 多了「祖先」段，能一眼看出谁改动了什么。

## 七、⏪ 回退与撤销

> **本节是急救高频区，请重点收藏**。

### 🎬 7.1 撤销工作区的改动（还没 add）

```bash
# 撤销某个文件（现代写法）
git restore path/to/file

# 撤销所有工作区改动（⚠️ 不可逆）
git restore .

# 老写法（等价）
git checkout -- path/to/file
```

### 🎬 7.2 撤销已 add 到暂存区的改动（unstage）

```bash
# 现代写法
git restore --staged path/to/file
git restore --staged .

# 老写法
git reset HEAD path/to/file
```

💡 **文件回到「已改但未 add」状态**，工作区内容不变。

### 🎬 7.3 撤销最近 1 个 commit（本地，未 push）

```bash
# 撤销 commit，改动保留在暂存区
git reset --soft HEAD~1

# 撤销 commit，改动保留在工作区（暂存区清空）
git reset --mixed HEAD~1     # 默认，可省略 --mixed

# 撤销 commit + 丢弃改动（⚠️ 危险，改动全丢）
git reset --hard HEAD~1
```

### 🎬 7.4 撤销最近 N 个 commit

```bash
git reset --soft HEAD~3         # 撤销近 3 个，改动堆在暂存区
git reset --hard HEAD~3         # 撤销近 3 个 + 丢改动
```

### 🎬 7.5 撤销已 push 到远程的 commit（公共分支）

> **公共分支绝对不能 reset + force push**——会让协作者炸掉。用 `revert`。

```bash
# 生成一个「反做」的新 commit
git revert abc123
git push

# revert 多个（会一个个交互）
git revert abc123 def456

# revert 但先不 commit（想合并成一个 revert）
git revert -n abc123 def456
git commit -m "revert: rollback of feature X"
```

### 🎬 7.6 revert 一次 merge commit

```bash
# -m 1 = 保留 main（第一父）的历史，撤销来自 feature 的部分
git revert -m 1 <merge-sha>
```

⚠️ revert 一次 merge 后，**同一个 feature 不能直接再 merge**——Git 会认为「你已经合过了」。需要先 revert 那个 revert，或者重开 feature 分支。

### 🎬 7.7 回退到某个具体 commit / tag

```bash
# 本地硬回退（⚠️ 未提交改动会丢）
git reset --hard v1.0.0
git reset --hard abc123

# 生产环境的正确做法：从旧 tag 建 hotfix 分支
git switch -c hotfix/rollback v1.0.0
# 修复 → 提交 → merge 回 main
```

### 🎬 7.8 找回被 reset / 误删的 commit（reflog 救命）

```bash
# 1) 看历史操作记录（reflog 记录 HEAD 每一次移动）
git reflog

# 2) 找到目标 commit 的 SHA（比如 abc123）
# 3) 恢复
git reset --hard abc123
# 或建个分支救回来
git switch -c rescue abc123
```

💡 **reflog 默认保留 90 天**——90% 的「commit 消失」事故都能救。

### 🎬 7.9 找回被删的分支

```bash
git reflog | grep <branch-name>          # 找到该分支最后的 SHA
git switch -c <branch-name> <sha>
```

### 🎬 7.10 硬回退救命三招（顺序执行）

> 万一 `git reset --hard` 手误了：

```bash
# 招 1：reflog 找回
git reflog
git reset --hard HEAD@{1}      # 回到 reset 之前

# 招 2：fsck 挖 orphan commit
git fsck --lost-found

# 招 3：Time Machine / 网盘同步 / IDE 本地历史
# 大多数 IDE（VS Code / IntelliJ）都有本地文件历史
```

### 🎬 7.11 撤销一次 push（`--force-with-lease`）

> 私有分支上 push 错了，想「像没发生过」。

```bash
git reset --hard HEAD~1
git push --force-with-lease           # 优于 --force：会检查有没有别人先 push
```

⚠️ `--force-with-lease` 是「有条件的强推」，比 `--force` 安全，但**仍然不能用在公共分支**。

## 八、🚚 同步远程

### 🎬 8.1 拉取远程更新（老手推荐 fetch + 手动）

```bash
# 【推荐】老手做法：分两步，明确性大于自动化
git fetch origin
git log HEAD..origin/main --oneline    # 看看远端多了什么
git merge origin/main                  # 或
git rebase origin/main

# 【新手快捷】pull = fetch + merge
git pull

# pull 时用 rebase 而不是 merge（历史更干净）
git pull --rebase
git pull --rebase --autostash          # 自动 stash 未提交的改动
```

💡 全局配 `pull.rebase = true` 让所有 `git pull` 都变 rebase 模式。

### 🎬 8.2 推送本地更新

```bash
git push                              # 推当前分支
git push -u origin feat/xxx           # 首次推送 + 关联上游
git push --tags                       # 推所有 tag
git push origin v1.0.0                # 推单个 tag

# 全局配「首次 push 自动 -u」
git config --global push.autoSetupRemote true
```

### 🎬 8.3 处理 push 被拒（rejected non-fast-forward）

> 报错：`Updates were rejected because the remote contains work...`

```bash
# 说明远程有你没有的 commit → 先同步再 push
git fetch origin
git rebase origin/main         # 或 git merge origin/main
git push
```

⚠️ **千万别直接 `git push --force`**——除非你是这个分支的唯一使用者。

### 🎬 8.4 同步 fork 的上游

```bash
# 首次配 upstream
git remote add upstream https://github.com/original/repo.git

# 同步（fork 主分支跟上原仓库）
git fetch upstream
git switch main
git rebase upstream/main           # 或 merge
git push origin main               # 推回自己的 fork
```

### 🎬 8.5 添加 / 修改 / 删除 remote

```bash
git remote -v                              # 看当前有哪些 remote
git remote add upstream <url>              # 加
git remote set-url origin <new-url>        # 改
git remote rename origin old-origin        # 改名
git remote remove origin                   # 删
```

### 🎬 8.6 从 HTTPS 切到 SSH（或反之）

```bash
# 看当前 URL
git remote -v

# 改为 SSH
git remote set-url origin git@github.com:user/repo.git

# 改为 HTTPS
git remote set-url origin https://github.com/user/repo.git
```

### 🎬 8.7 clone 慢/断了怎么办

```bash
# 浅克隆（只拉最新一次 commit）
git clone --depth 1 <url>

# 已经 shallow 了，想拉全部历史
git fetch --unshallow

# 部分克隆（Git 2.19+，超大仓库）
git clone --filter=blob:none <url>
```

## 九、📦 发布与打 Tag

### 🎬 9.1 打一个 tag

```bash
# 轻量 tag（不推荐，无签名/message）
git tag v1.0.0

# 【推荐】附注 tag（带 message、作者、时间）
git tag -a v1.0.0 -m "Release 1.0.0: 首个正式版"

# 【生产推荐】带签名 tag
git tag -s v1.0.0 -m "Release 1.0.0"

# 给历史某个 commit 打 tag
git tag -a v0.9.0 abc123 -m "补打 0.9.0 tag"
```

### 🎬 9.2 查看 / 推送 tag

```bash
git tag                             # 列所有 tag
git tag -l 'v1.*'                   # 按 pattern 过滤
git show v1.0.0                     # 看 tag 详情

# 推送
git push origin v1.0.0              # 推单个
git push origin --tags              # 推所有 tag

# 全局配「push 时自动带 tag」
git config --global push.followTags true
```

### 🎬 9.3 删除 tag

```bash
# 本地
git tag -d v1.0.0

# 远程
git push origin --delete v1.0.0
# 或
git push origin :refs/tags/v1.0.0
```

### 🎬 9.4 基于 tag 建 hotfix 分支（生产环境救急）

> 生产用的是 v1.2.0，现在有紧急 bug 要修，但 main 已经跑到 v2.0-beta 了。

```bash
git switch -c hotfix/v1.2.1 v1.2.0
# 修复
git commit -am "fix: critical bug"
git tag -a v1.2.1 -m "Hotfix 1.2.1"
git push -u origin hotfix/v1.2.1
git push origin v1.2.1

# 把修复也合回 main
git switch main
git cherry-pick <hotfix-sha>       # 或 merge
```

### 🎬 9.5 生成 CHANGELOG

```bash
# 手动看两个 tag 之间的 commit
git log v1.0.0..v1.1.0 --oneline --no-merges

# 自动生成（需 conventional-commits 规范）
npx conventional-changelog -p angular -i CHANGELOG.md -s

# 一次性生成全部历史
npx conventional-changelog -p angular -i CHANGELOG.md -s -r 0
```

### 🎬 9.6 一键自动发版（release-please / semantic-release）

**GitHub Actions 中配 release-please**（Google 出品）：

```yaml
# .github/workflows/release.yml
name: release-please
on:
  push:
    branches: [main]
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: google-github-actions/release-please-action@v4
        with:
          release-type: node
```

💡 你只需按 Conventional Commits 规范 commit（feat / fix / …），机器人自动：**升版本号 → 生成 CHANGELOG → 打 tag → 建 GitHub Release**。

### 🎬 9.7 语义化版本速记

| 变更 | 版本号 | 示例 |
|---|---|---|
| Breaking change（不兼容） | **主**版本号 +1 | 1.2.3 → 2.0.0 |
| feat（新功能，向后兼容） | **次**版本号 +1 | 1.2.3 → 1.3.0 |
| fix（bug 修复） | **补丁**版本号 +1 | 1.2.3 → 1.2.4 |

Conventional Commits 前缀：`feat:` / `fix:` / `docs:` / `style:` / `refactor:` / `perf:` / `test:` / `chore:` / `feat!:`（breaking）。

## 十、🗑️ 删除与清理

### 🎬 10.1 删除文件（本次删掉，历史还在）

```bash
git rm path/to/file
git commit -m "chore: remove unused file"
```

### 🎬 10.2 只是从 Git 里移除但保留本地文件

> 已经 commit 了 `.env`，想让 Git 别再跟踪它，但本地要留着。

```bash
git rm --cached .env
echo ".env" >> .gitignore
git commit -m "chore: stop tracking .env"
```

### 🎬 10.3 删除一整个目录

```bash
git rm -r path/to/dir
git commit -m "chore: remove dir"
```

### 🎬 10.4 从整个历史里彻底删除文件（敏感数据泄露急救）

> ⚠️ 用于**密码 / 密钥 / 大文件**误 commit 后从历史里连根拔起。

```bash
# 【推荐】现代工具 git-filter-repo
pip install git-filter-repo
git filter-repo --path secrets.env --invert-paths

# 【备选】BFG（老牌快速）
bfg --delete-files secrets.env
git reflog expire --expire=now --all
git gc --prune=now --aggressive

# 强推到远程（团队要通知所有人重新 clone）
git push --force
```

⚠️ **改历史后，所有协作者必须重新 clone**——他们本地的旧历史会跟远程冲突。**先在群里通知！**

### 🎬 10.5 删除某个中间 commit

```bash
git rebase -i HEAD~5           # 找到那个 commit
# 把它那行的 pick 改为 drop（或 d）
# 保存 → 处理可能的冲突
```

### 🎬 10.6 清理未跟踪的文件（工作区）

```bash
# 先预演（重要！）
git clean -n                   # 只看会删啥
git clean -nd                  # 含目录
git clean -ndx                 # 含被 .gitignore 忽略的

# 确认无误后真删
git clean -f                   # 删未跟踪文件
git clean -fd                  # 含目录
git clean -fdx                 # 含 ignored（会删 node_modules 等）
```

⚠️ **`clean` 不可逆**——先 `-n` 预演，再 `-f`。

### 🎬 10.7 清理已合并的本地分支

```bash
# 一次性删所有已合并进 main 的本地分支
git branch --merged main | grep -Ev '^\*|main|master|develop' | xargs -r git branch -d
```

### 🎬 10.8 清理本地对远程已删分支的引用

```bash
git fetch --prune              # 清理这次
git remote prune origin        # 只清理不 fetch

# 一次配终身
git config --global fetch.prune true
```

### 🎬 10.9 清理 stash

```bash
git stash list                 # 看有哪些
git stash drop stash@{0}       # 删单个
git stash clear                # 全删（⚠️ 不可逆）
```

### 🎬 10.10 缩减仓库体积（gc / repack）

```bash
git gc                         # 自动打包，安全
git gc --aggressive            # 深度打包，慢但省空间
git gc --prune=now             # ⚠️ 立即清理不可达对象（reflog 里的救命 commit 也会没）

# 看仓库有多大
git count-objects -vH
```

⚠️ `--prune=now` 是**不可逆核弹**，除非你确定要清理，否则永远别加。

## 十一、💾 stash 临时保存

### 🎬 11.1 快速藏一份改动

> 手上有活没写完，突然要切分支救火。

```bash
git stash                              # 藏起来（含 add 和未 add 的，但不含 untracked）
git stash push -m "wip: 登录功能一半"    # 带描述（推荐）
git stash -u                           # 含 untracked 文件
git stash -a                           # 含 untracked + ignored
```

### 🎬 11.2 恢复 stash

```bash
git stash list                         # 看有哪些 stash
git stash show stash@{0}               # 看某个 stash 的摘要
git stash show -p stash@{0}            # 看具体 diff

git stash pop                          # 弹出最新的（用了就删）
git stash pop stash@{2}                # 弹出指定的
git stash apply                        # 应用但不删（保险起见）
git stash apply stash@{2}
```

⚠️ `pop` 遇冲突时**不会自动删 stash**，解决冲突后手动 `git stash drop stash@{0}`。

### 🎬 11.3 只 stash 部分文件

```bash
# 交互式选择要 stash 的 hunk
git stash push -p -m "wip: 只藏样式"

# 直接指定文件
git stash push -m "wip: 藏样式" -- src/*.css
```

### 🎬 11.4 从 stash 建一个分支

> 藏了很久的 stash，主分支变化太大，`pop` 冲突严重。

```bash
git stash branch feat/from-stash stash@{2}
# Git 会：基于 stash 创建时的 commit 建分支 + 应用 stash + 删 stash
```

### 🎬 11.5 stash 底层揭秘

`git stash` 实际上创建了 **2~3 个 commit**：

- `refs/stash^1`：工作区快照
- `refs/stash^2`：暂存区快照
- `refs/stash^3`（可选）：untracked 快照

所以理论上 stash 也可以被 `git fsck --lost-found` 挖回。

## 十二、🔍 查询与破案

### 🎬 12.1 看某行代码是谁写的（blame）

```bash
git blame path/to/file
git blame -L 100,120 path/to/file            # 只看 100~120 行
git blame --ignore-rev <格式化 commit>        # 忽略某次纯格式化
git blame --ignore-revs-file .git-blame-ignore-revs   # 常规忽略
```

💡 **`blame` 是找上下文，不是找罪人**。往往你需要的是 commit message 里的「为什么这么写」。

### 🎬 12.2 二分找 bug 引入点（bisect）

> 现在有 bug，但 100 个 commit 之前是好的，中间哪个 commit 引入的？

**手动版**：

```bash
git bisect start
git bisect bad                            # 当前是坏的
git bisect good v1.0.0                    # v1.0.0 是好的

# Git 会自动 checkout 到中间点，你测试 → 告诉它 good 或 bad
git bisect good     # 或 git bisect bad
# ... 一直循环 ...
git bisect reset                          # 找完退出
```

**全自动版（有测试脚本时）**：

```bash
git bisect start HEAD v1.0.0
git bisect run pytest tests/test_bug.py
# 或
git bisect run npm test
```

💡 100 个 commit 用二分法只要 log2(100)≈7 次即可定位。

### 🎬 12.3 找某段代码是何时/由谁引入的（pickaxe）

```bash
# 按字符串（-S）
git log -S "loginWithSSO(" --source --all

# 按正则（-G）
git log -G "TODO.*urgent" --patch

# 显示每一次引入这个字符串的 diff
git log -S "loginWithSSO(" -p
```

### 🎬 12.4 看某个文件的完整历史（含重命名）

```bash
git log --follow --oneline -- path/to/file
git log --follow -p -- path/to/file       # 每次改动的 diff 也看
```

### 🎬 12.5 看某一行的演变历史

```bash
git log -L 100,120:path/to/file           # 看 100~120 行的历史
git log -L :funcName:path/to/file         # 看某个函数的历史
```

### 🎬 12.6 对比两个分支

```bash
git diff main..feature                    # 看 feature 相对 main 多的改动
git diff main...feature                   # 从共同祖先算起
git diff --stat main..feature             # 只看统计
git diff --name-only main..feature        # 只看变了哪些文件

# 看 feature 上还有 main 没合并的 commit
git log main..feature --oneline
```

### 🎬 12.7 我这周做了什么（周报神器）

```bash
git log --author="$(git config user.name)" \
        --since="1 week ago" \
        --pretty=format:'%h %s' \
        --no-merges

# 想跨仓库统计？在包含多个仓库的目录下：
for d in */; do (cd "$d" && echo "=== $d ===" && git log --author="$(git config user.name)" --since="1 week ago" --oneline --no-merges 2>/dev/null); done
```

### 🎬 12.8 谁贡献最多（作者排行榜）

```bash
git shortlog -sne --all
git shortlog -sne --since="6 months ago"
```

### 🎬 12.9 看某次 commit 改了什么

```bash
git show abc123                       # 完整 diff
git show --stat abc123                # 只看统计
git show abc123 -- path/to/file       # 只看某个文件
git show abc123:path/to/file          # 看某个 commit 时该文件的内容
```

### 🎬 12.10 搜 commit message

```bash
git log --grep="fix.*login" -i --oneline
git log --grep="fix" --grep="perf" --oneline    # OR
git log --grep="fix" --grep="login" --all-match --oneline   # AND
```

## 十三、一日 Git 流水线

**一个典型开发者的完整一天**，浓缩成 10 条命令：

```bash
# 早上 · 到岗
git switch main
git fetch origin
git rebase origin/main                # 同步

# 开工 · 新任务
git switch -c feat/task-123

# 上午 · 写代码 + 多次小 commit
git add -p                            # 精细地 add
git commit -m "feat: xxx"
git commit -m "test: xxx"

# 中午 · 临时救急
git stash push -m "wip"               # 手上有活，切去救火
git switch hotfix
# ... 救火 ...
git switch -
git stash pop

# 下午 · 继续开发
git commit -am "feat: yyy"

# 傍晚 · 收尾
git fetch origin
git rebase origin/main                # 保持 PR 干净
git push -u origin feat/task-123

# 提 PR
gh pr create --title "..." --body "..."

# 晚上 · 修 review 意见
git commit -am "fix: address review"
git push

# 合并后清理
git switch main
git pull
git branch -d feat/task-123
```

**这 10 条命令，覆盖了 90% 的日常操作**——练熟了就是老手。

## 十四、命令快查表

**按频率排序**——从每天都用到偶尔一用：

| 频率 | 命令 | 一句话 |

## 十五、组合拳精选：老手才知道的 30 个骚操作

前面的场景是「一招一式」，这一节讲**组合拳**——老手用了以后回不去的黑魔法。全部经过实战检验，可以直接拷进你的 `.gitconfig` 或备忘录。

### 🥋 侦查类

```bash
# 1) 谁最近改过某个文件？（按提交时间倒序）
git log --follow --pretty=format:'%h %an %ar : %s' -- path/to/file

# 2) 找某段代码是什么时候加进来的（-S = pickaxe，按字符串增删找 commit）
git log -S "someFunction(" --source --all

# 3) 找某段代码最近一次被改是什么时候（-G = 按正则找 diff）
git log -G "TODO.*urgent" --patch

# 4) 谁在哪个分支上还有未合并的 commit？
git for-each-ref --format='%(refname:short) %(authorname)' refs/heads/ | \
  while read b a; do
    n=$(git rev-list --count main..$b 2>/dev/null)
    [ "$n" != "0" ] && echo "$b: +$n commits ($a)"
  done

# 5) 我这两周做过什么？（周报神器）
git log --author="$(git config user.name)" \
  --since="2 weeks ago" --pretty=format:'%h %s' --no-merges

# 6) 某次 commit 影响到了哪些文件？
git show --stat <sha>

# 7) 谁在这个仓库贡献最多？（作者排行榜）
git shortlog -sne --all

# 8) 某文件从诞生到现在的所有版本
git log --all --oneline --follow -- path/to/file
```

### 🧹 清理类

```bash
# 9) 一次性删掉所有已合并进 main 的本地分支
git branch --merged main | grep -Ev '^\*|main|master|develop' | xargs -r git branch -d

# 10) 一次性清理远程已经不存在的本地引用
git fetch --prune  # 或永久开启：git config --global fetch.prune true

# 11) 列出所有从未 push 过的本地分支（怕漏掉工作）
git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads/ | \
  grep -v '\[' 

# 12) 把未跟踪垃圾清干净（-d 含目录，-x 含被 ignore 的）
git clean -fdx --dry-run   # 先看看会删啥
git clean -fdx             # 确认无误再来
```

### 🎯 精确类

```bash
# 13) 只 checkout 别的分支上的某个文件（不切换分支）
git checkout other-branch -- path/to/file
# 现代写法（Git 2.23+）：
git restore --source other-branch --staged --worktree path/to/file

# 14) 修改历史中某个 commit 的作者信息（只改一次）
git rebase -i <sha>^  # 把那行改成 edit
git commit --amend --author="New Name <new@email>" --no-edit
git rebase --continue

# 15) 快速找出「引入 bug 的那次 commit」的父提交（配合 bisect）
git rev-parse <sha>^
```

### 🩹 修复类

```bash
# 16) 上个 commit message 拼错了（还没 push）
git commit --amend

# 17) 忘记 add 的文件加进上个 commit（不改 message）
git add forgotten.js && git commit --amend --no-edit

# 18) 把最近 3 个 commit 合成 1 个
git reset --soft HEAD~3 && git commit -m "feat: consolidated"
# 更优雅的：
git rebase -i HEAD~3   # 把后 2 行改成 squash（或 fixup）

# 19) 我在 master 上直接干了活，怎么办？
git switch -c feature/oops   # 直接把当前工作转成新分支
git switch master
git reset --hard origin/master  # master 回到干净
```

### 🕵️ 调试类

```bash
# 20) 看某一行是从哪个 commit 来的（比 blame 更快看历史）
git log -L 100,120:src/foo.js

# 21) 二分找 bug 全自动（有测试脚本时）
git bisect start HEAD v1.0.0
git bisect run pytest tests/test_bug.py

# 22) 看两个分支的差异摘要（不看 diff 内容）
git diff --stat main..feature

# 23) 只对比两个分支中修改过的文件列表
git diff --name-only main..feature
```

### 🚀 高效类

```bash
# 24) 在多个仓库间快速切换环境（worktree）
git worktree add ../repo-hotfix hotfix/urgent
cd ../repo-hotfix   # 独立目录，不影响主工作区

# 25) 让 git log 有语法高亮的 diff（内置无需插件）
git log -p --color-words

# 26) 把当前 commit 打包成 tar.gz（分发用）
git archive --format=tar.gz --prefix=myproj/ HEAD > myproj.tar.gz

# 27) 让 git 显示当前分支的祖先图谱
git log --graph --oneline --all --decorate --simplify-by-decoration

# 28) 只克隆最新一次 commit（大仓库救星）
git clone --depth 1 https://github.com/xxx/big-repo.git

# 29) 部分克隆（Git 2.19+，仓库很大时神器）
git clone --filter=blob:none <url>

# 30) 快速在 GitHub 上打开当前仓库
gh repo view --web
# 或纯 git：
git config --global alias.open '!f() { xdg-open $(git remote get-url origin | sed "s/git@github.com:/https:\\/\\/github.com\\//;s/.git$//"); }; f'
```

**⚡ 一句话总结**：这 30 招每天用不到 5 招，但**关键时刻能救命**——收藏起来，用一年就成老手。

## 十六、别名工程学：把 `~/.gitconfig` 打磨成利器

`~/.gitconfig` 不是随手配一下的**样板文件**，而是**每天陪你 8 小时的乐器**——磨得越顺手，工作效率越高。这一节给出一份**经过多年实战沉淀的 gitconfig 蓝本**。

### 12.1 完整的 `~/.gitconfig` 蓝本

```ini
# ─── 身份 ────────────────────────────
[user]
    name = 杨充
    email = your@email.com
    signingkey = ABCD1234       # GPG/SSH 签名密钥

# ─── 通用行为 ────────────────────────
[init]
    defaultBranch = main
[core]
    editor = code --wait
    autocrlf = input            # macOS/Linux；Windows 用 true
    excludesfile = ~/.gitignore_global
    pager = delta               # 用 delta 让 diff 有语法高亮（可选）
[pull]
    ff = only                   # pull 只允许 fast-forward，禁止隐式 merge
[rebase]
    autoStash = true            # rebase 时自动 stash/pop 工作区
    autoSquash = true           # 识别 fixup!/squash! 前缀
[push]
    default = current           # push 默认推当前分支同名
    followTags = true           # push 时自动带上 tag
    autoSetupRemote = true      # 首次 push 自动 -u
[fetch]
    prune = true                # fetch 时自动删除远端已删的引用
    pruneTags = true
[merge]
    conflictstyle = zdiff3      # 显示三方 diff，冲突更清晰（Git 2.35+）
    tool = vscode
[mergetool "vscode"]
    cmd = code --wait $MERGED
[diff]
    algorithm = histogram       # 更聪明的 diff 算法（比默认 myers 好）
    colorMoved = zebra          # 移动的代码用不同颜色显示
    renames = copies            # 检测复制而不仅是重命名
[log]
    date = iso                  # 时间显示 ISO 格式
[color]
    ui = auto
[commit]
    gpgsign = true              # 所有 commit 自动签名（可选）
    verbose = true              # commit 时 message 底下显示 diff

# ─── 别名（灵魂所在）─────────────────
[alias]
    # 状态与查看
    st = status -sb
    lg = log --oneline --graph --all --decorate
    lgs = log --oneline --graph --all --decorate --stat
    last = log -1 HEAD --stat
    who = shortlog -sne --all

    # 增删改
    cm = commit -m
    ca = commit --amend --no-edit
    cane = commit --amend
    unstage = restore --staged
    discard = restore
    undo = reset HEAD~1

    # 分支
    br = branch
    bra = branch -a
    cleanup = "!git branch --merged main | grep -Ev '^\\*|main|master|develop' | xargs -r git branch -d"

    # 同步
    sync = "!git fetch origin && git rebase origin/$(git symbolic-ref --short HEAD)"
    up = pull --rebase --autostash

    # 差异
    df = diff
    dfs = diff --staged
    dfw = diff --word-diff

    # 侦查
    find = "!f() { git log --pretty=format:'%h %s' -S\"$1\"; }; f"
    who-changed = "!f() { git log --pretty=format:'%h %an %ar : %s' --follow -- \"$1\"; }; f"

    # 救急
    wip = "!git add -A && git commit -m 'WIP'"
    unwip = reset HEAD~1

    # 打开当前仓库
    open = "!f() { xdg-open $(git remote get-url origin | sed 's|git@github.com:|https://github.com/|;s|.git$||'); }; f"
```

### 12.2 别名的三个层次

| 层次 | 定义 | 举例 |
|---|---|---|
| 🥉 **单命令简写** | 把长命令缩成两字母 | `st = status -sb`, `br = branch` |
| 🥈 **组合命令** | 把常见命令组合固化 | `sync = !git fetch && git rebase` |
| 🥇 **参数化脚本** | 用 `!f() { ... }; f` 写小函数 | `find = "!f() { git log -S\"$1\"; }; f"` |

**⚠️ 别名铁律**：**别把危险操作简写**——比如别把 `git reset --hard` 缩成 `rh`，多敲两个字母的成本，比不小心敲错的代价低多了。

### 12.3 全局 `.gitignore_global`

配了 `core.excludesfile` 之后，可以把「跟仓库无关、但自己电脑上会有」的垃圾集中忽略：

```
# ─── macOS ────────────
.DS_Store
._*

# ─── IDE ──────────────
.idea/
.vscode/
*.swp
*.swo

# ─── 环境 ─────────────
.env.local
.envrc

# ─── 临时 ─────────────
*.log
*.tmp
```

**好处**：`.gitignore` 里就不用重复写这些电脑级别的东西，团队仓库更干净。

**⚡ 一句话总结**：`~/.gitconfig` 是**每天用的乐器**——花一个下午调好，用十年。

## 十七、GUI vs CLI：什么时候用什么工具

Git 的哲学是命令行，但不代表所有场景都必须命令行。**老手都是「命令行主战 + GUI 辅助」**——各用其长。

### 13.1 场景匹配表

| 场景 | 首选工具 | 原因 |
|---|---|---|
| 日常提交 | CLI (`git add -p` / `commit`) | 精确、可脚本化、可练手感 |
| 复杂冲突解决 | GUI (VS Code / GitLens) | 三窗对比看得清 |
| 交互式 rebase | GUI (`gitui` / Fork / Tower) | 拖拽比记 pick/squash/fixup 直观 |
| 查看历史图谱 | GUI (`gitk` / GitGraph / Fork) | 图形化的 DAG 比 `git lg` 更立体 |
| Cherry-pick 一批 commit | GUI (Fork / SourceTree) | 多选比循环 `cherry-pick` 快 |
| 深挖 blame 上下文 | GUI (GitLens) | 悬浮显示 commit 详情 |
| CI/CD 集成 | CLI（脚本） | GUI 不适合自动化 |
| 大量文件的 diff review | GUI (`meld` / VS Code diff) | 目录树 + 侧栏切换效率高 |
| bisect 破案 | CLI（`git bisect run`） | GUI 支持有限 |
| 教学 / 演示 | GUI + CLI 结合 | 图形化直观 + 命令展现原理 |

### 13.2 老手常用的 GUI 工具

- **VS Code + GitLens 插件**：编辑器内 blame、历史、diff——最贴合开发流的选择
- **Fork**（macOS/Windows）：轻快、免费、交互式 rebase 很爽
- **Sublime Merge**：Sublime 家出品，极简、极快
- **lazygit / gitui**：终端下的 TUI，键盘党最爱
- **`gitk` + `git-gui`**：Git 官方自带，简陋但可靠

### 13.3 命令行党的三大坚持

1. **CI / hooks / 脚本 必须 CLI**——GUI 无法自动化。
2. **教学时 必须 CLI**——GUI 掩盖了 Git 的思维模型。
3. **服务器上 只能 CLI**——GUI 无从谈起。

**⚡ 一句话总结**：**CLI 是内功，GUI 是招式**——内功不深，招式用不出真威力。

## 十八、常用配置详解：那些 `git config` 里被埋没的宝藏

`git config --list` 列出的选项有几百个，但真正影响日常体验的不到 20 个。这一节挑最值得配的讲清楚：

### 14.1 让 diff 更聪明

```bash
# 用 histogram 算法（比默认 myers 更擅长处理移动的代码块）
git config --global diff.algorithm histogram

# 检测代码块移动，用斑马纹显示
git config --global diff.colorMoved zebra

# 检测复制文件（不只是重命名）
git config --global diff.renames copies

# 显示 3 行上下文（默认）→ 5 行
git config --global diff.context 5
```

### 14.2 让 merge 冲突更好看

```bash
# 冲突显示 3 方对比（Git 2.35+），比默认 2 方清楚得多
git config --global merge.conflictstyle zdiff3

# 记住每次冲突的解法，下次自动应用
git config --global rerere.enabled true
```

### 14.3 让 rebase 更省心

```bash
git config --global rebase.autoStash true    # rebase 前自动 stash
git config --global rebase.autoSquash true   # 识别 fixup!/squash! 前缀
git config --global rebase.updateRefs true   # rebase 时自动更新 stacked 分支（Git 2.38+）
```

### 14.4 让 push/pull 更安全

```bash
git config --global pull.ff only              # pull 只允许 fast-forward
git config --global push.default current      # push 默认推当前分支同名
git config --global push.autoSetupRemote true # 首次 push 自动 -u
git config --global fetch.prune true          # fetch 自动 prune
```

### 14.5 让签名成为默认

```bash
git config --global user.signingkey ABCD1234
git config --global commit.gpgsign true       # commit 自动签名
git config --global tag.gpgsign true          # tag 自动签名
```

### 14.6 让 commit 更认真

```bash
git config --global commit.verbose true       # commit 时下面显示 diff，方便复查
git config --global commit.template ~/.gitmessage  # 用模板提示 message 格式
```

`~/.gitmessage` 内容示例（Conventional Commits）：

```
# <type>(<scope>): <subject>
#
# type: feat / fix / docs / style / refactor / test / chore
# subject: 祈使句，小写开头，不加句号
#
# <body>
#
# <footer> — Closes: #issue
```

### 14.7 让性能起飞

```bash
# 大仓库开启文件系统监视器（Git 2.37+），status 秒开
git config --global core.fsmonitor true
git config --global core.untrackedCache true

# 并行 index 更新
git config --global index.threads 4

# 打包时用多线程
git config --global pack.threads 0     # 0 = 用所有核
```

**⚡ 一句话总结**：这 20 项配置花 10 分钟设置一次，享用一辈子——**Git 老手和新手的差距，一半在别名，一半在这里**。
