## 1. 案例引入

### 1.1 一次批量返厂

一款车载 T-BOX 产品，量产铺货 8 个月后开始批量返厂：**Flash 挂了，设备启动到一半 kernel panic**，`dmesg` 里满屏 `mtd: bad block`。

从售后回收的板子拆下 NAND Flash 一测，**磨损计数普遍超过 15,000 次**（该型号 SLC 标称 100,000 次擦写寿命）。看起来还很富余，但设备内部又确实起不来。

翻代码看到有几处可疑的写操作：

```cpp
// 定位服务：每 100 ms 写一次 GPS 到本地文件
void GpsWorker::onFix(const Fix& f) {
    std::ofstream ofs("/data/last_gps.txt");   // ← truncate 覆盖写
    ofs << f.toJson();
    ofs.flush();
    fsync(fileno(ofs.rdbuf()->__file()));      // ← 强刷 Flash
}
```

```cpp
// 日志：每条日志都 sync
Logger::write(const std::string& line) {
    fprintf(logFile_, "%s\n", line.c_str());
    fflush(logFile_);
    fsync(fileno(logFile_));                   // ← 每行都 fsync
}
```

```cpp
// 事件计数器：每次事件累加后落盘
void EventCounter::inc() {
    counter_++;
    saveToFile();                              // ← 打开 → 写入 → 关闭，一次事件一次
}
```

这三段代码看着都"很小心"，实际每一段都在**加速把 Flash 写坏**。

### 1.2 顺藤摸到根因

- **假设 1**：为什么擦写寿命 10 万次的 SLC，8 个月就挂了？，因为**同一个逻辑地址频繁重写**，如果没有磨损均衡（或者均衡不好），会集中把某几个物理块写坏。→ 引出 **磨损均衡**。
- **假设 2**：为什么"每 100ms 写 300 字节"这么小的写入会伤 Flash？，因为 **NAND 的最小擦除单位是 128 KB**，写 300 字节实际擦掉 128 KB 再写回来 → **写放大 400 倍**。→ 引出 **写放大**。
- **假设 3**：为什么 `fsync` 每次都调？，因为怕丢数据。但 `fsync` 会**强制 FTL flush 到物理 Flash**，绕过了缓存合并的机会。→ 引出 **fsync 的代价**。
- **假设 4**：为什么用 `ofstream` 覆盖写而不是 append？，覆盖写触发**擦除 + 重写整个块**，而 append 可能命中"页写"（更轻）。→ 引出 **写模式的选择**。
- **假设 5**：为什么用 ext4 而不是 UBIFS？，因为团队"没想那么多、默认就用 ext4 了"。**在裸 NAND 上跑 ext4，磨损均衡完全不能发挥**。→ 引出 **文件系统与介质匹配**。

```
① 存储介质那么多，什么时候选 NOR/NAND/eMMC？    → 第 3 章
② 为什么写 300 字节实际擦 128 KB？              → 第 4 章 + 第 5 章
③ 怎么估算 Flash 寿命够不够用？                  → 第 5.2 节
④ 分区怎么切才能兼顾 OTA 与掉电？               → 第 6 章
⑤ 断电了数据一定丢吗？怎么防？                   → 第 7 章
```

## 2. 存储体系概览

### 2.1 分层视图

```
┌───────────────────────────────────────────────────────────────┐
│  应用层    │  数据库 (SQLite) / KV 存储 / 日志                   │
├───────────────────────────────────────────────────────────────┤
│  文件系统  │  ext4 / f2fs / UBIFS / squashfs / overlayfs        │
├───────────────────────────────────────────────────────────────┤
│  块层      │  Linux Block Layer (bio / request_queue)           │
│           │  ↑ 只有块设备（eMMC / SD / UFS）经过这层            │
├───────────────────────────────────────────────────────────────┤
│  FTL 层    │  eMMC 内建 / UBI (软件 FTL)                        │
│           │  职责：磨损均衡、坏块管理、垃圾回收                  │
├───────────────────────────────────────────────────────────────┤
│  介质层    │  NOR Flash / NAND Flash / eMMC / SD / UFS          │
└───────────────────────────────────────────────────────────────┘
```

**块设备 vs MTD 设备**：
- **块设备**：eMMC/SD/UFS 内部已有 FTL 芯片，对外像硬盘，Linux 走 block layer（`/dev/mmcblk0`）
- **MTD 设备**：裸 NAND/NOR Flash 没 FTL，Linux 通过 MTD 子系统访问（`/dev/mtd0`），配合 UBI 软件层做 FTL

### 2.2 为什么这么切

**疑惑**：为什么要区分"块设备"和"MTD 设备"？直接都当块设备用不行？

**论证**：因为 **Flash 的物理特性和硬盘完全不同**：

| 差异 | 硬盘/SSD | 裸 Flash |
|---|---|---|
| 最小读单位 | 512 B / 4 KB | Page（2~16 KB） |
| 最小写单位 | 同上 | Page（不能"改" 只能"擦后写"） |
| 最小擦除单位 | / | Block（128 KB ~ 4 MB） |
| 支持"覆盖写" | 是 | 否 |
| 有物理磨损 | 有（但 FTL 已处理） | 有（**软件必须处理**） |

**结论**：**裸 Flash 必须有一层做 FTL**，才能给上层"能覆盖写、能随机写"的假象。这一层要么在芯片里（eMMC），要么在软件里（UBI）。**忘了这一层，直接把 ext4 铺到裸 NAND 上就是灾难**——第 1 章的返厂就是这么来的。


## 3. 存储介质对比

### 3.1 NOR vs NAND

| 维度 | NOR Flash | NAND Flash |
|---|---|---|
| 读速度 | 快（可直接执行 XIP） | 慢一点 |
| 写速度 | 慢 | 快 |
| 擦除速度 | 慢 | 快 |
| 单块擦除 | 64~128 KB | 128 KB~4 MB |
| 容量 | 小（几 MB~64MB） | 大（几百 MB~几十 GB） |
| 单价 | 贵 | 便宜 |
| 寿命 | 10 万次 | SLC 10 万 / MLC 1 万 / TLC 千次 |
| 坏块 | 出厂无坏块 | 出厂就有 |
| 典型用途 | 引导 + 少量固件 | 主存储 |

**用一句话选**：
- **只放引导/内核** → NOR
- **要放 rootfs + 数据** → NAND / eMMC

### 3.2 eMMC与SD

**共同点**：内部有 NAND + FTL 控制器，对外是块设备接口。

**差异**：

| 维度 | eMMC | SD 卡 |
|---|---|---|
| 焊接 | BGA 焊到板上 | 插拔 |
| 品控 | 车规级/工规级 | 消费级 |
| 磨损均衡 | 强（含 SLC 缓存） | 弱 |
| 掉电保护 | 部分型号有 PLP | 极少有 |
| 寿命 | TBW 数百 GB~数 TB | 数十 GB |
| 价格 | 稍贵 | 便宜 |

**血泪教训**：**产品级设备不要用 SD 卡做主存储**。SD 卡的 FTL 是"消费品级"，主要为相机等场景优化——大文件顺序写好，小随机写差。嵌入式典型的日志/数据库场景会加速把它写坏。

### 3.3 UFS的价位段

**UFS**：eMMC 的高级替代，基于 SCSI 协议，支持全双工、命令队列。速度接近 SSD，价格是 eMMC 的 2~3 倍。

**选型建议**：
- **入门/工业** → eMMC（成熟、稳定、便宜）
- **要求高吞吐（如车载 4K 录像）** → UFS
- **可插拔存储** → SD（只作为"辅助介质"，不放关键数据）


## 4. Flash的三大特性

### 4.1 写前擦除

**核心事实**：Flash 单元只能从 1 变成 0，不能从 0 变回 1。要"改写"必须**先擦除整块（全部变 1）再重新写入**。

```
初始状态：  1111 1111 1111 1111    (擦除后)
写入 0x5A： 0101 1010 1111 1111    (可以写)
想改成 0xFF：需要先擦除整个 block，才能变回 1
```

**含义**：
- **写小数据 = 擦大块** → 写放大问题的根源
- **不能"append 到已有 page"**（一个 page 也只能写一次）

**FTL 的巧妙**：不做原地写，而是找一块干净的块写新数据，然后把老块标记为"垃圾"，等 GC 慢慢擦。

### 4.2 磨损均衡

**背景**：Flash 每个 block 有擦写次数上限（SLC 10 万、MLC 1 万、TLC 千次）。如果只写某几个 block，很快就把它们写坏。

**磨损均衡（Wear Leveling）**：把写入**均匀分散**到所有 block 上。

- **动态均衡**：只在活跃 block 之间调度（简单）
- **静态均衡**：把长期不动的数据（如内核镜像）搬走，让"死块"也参与轮转（更彻底）

**eMMC 内部有磨损均衡**，UBI 也有。但 **裸 NAND 上跑 ext4 = 无磨损均衡**——ext4 认为逻辑地址 == 物理地址，写日志时反复写同一区域，直接把那块 block 写死。这就是第 1 章的根因。

### 4.3 坏块管理

**NAND 出厂就有坏块**（约 2% 以内），且**使用中会陆续冒出新坏块**。

**软件必须做的事**：
- **坏块表（BBT）**：记录哪些是坏块，读写时跳过
- **写完校验**：写完读回来对比，发现异常标记为坏块
- **迁移**：坏块上的数据搬到新块

**UBI 层**（Linux 上）做的就是这套。**你在裸 NAND 上跑 ext4 而不上 UBI，坏块管理为零**。


## 5. 写放大与寿命

### 5.1 什么是写放大

**定义**：应用真正想写 N 字节，Flash 实际擦写了 M 字节，**写放大系数 WA = M/N**。

**写放大来源**：

```
应用写 512 字节
    │
    ▼
文件系统写 4 KB（page 对齐）        ← WA=8
    │
    ▼
FTL 迁移旧数据 + GC 回收整块       ← WA×2~5
    │
    ▼
最终擦写 128 KB block              ← 总 WA 可能 20~400
```

**极端案例**：
- 每 100ms 覆盖写 300 字节 → 每次擦 128 KB → **WA ≈ 400**
- 一天写入 = 300 B × 10 次/s × 86400 s ≈ 260 MB（应用视角）
- Flash 实际磨损 = 260 MB × 400 = **约 100 GB/天**

如果是 4 GB SLC NAND，寿命 100,000 次擦写 → 总擦写量 400 TB → **理论撑约 11 年**
但如果磨损均衡不好，集中打某几个块 → 半年报废。

### 5.2 寿命估算公式

**估算法**：

```
Flash 寿命 (天) = (总容量 × 擦写次数上限) / (每天实际擦写量)

每天实际擦写量 ≈ (每天应用写入量) × 写放大系数

注意：磨损均衡效率影响"总容量 × 次数"能否被均匀消耗
```

**厂商 TBW（Terabytes Written）**：eMMC 厂商给的官方指标，直接除以每天写入量即可估算。

| 场景 | 每天写入量 | 4GB eMMC (TBW=100GB) 寿命 |
|---|---|---|
| 只写日志（append）100 MB/天 | 100 MB | ~1000 天 ≈ 3 年 |
| 日志 + KV 状态 500 MB/天 | 500 MB | 200 天 ≈ 7 个月 |
| 视频缓存 5 GB/天 | 5 GB | 20 天 |

**结论**：**做产品之前必须估算寿命**。写入模型算完，再决定用什么介质、什么容量。

### 5.3 降低写放大

**招数一：Append-only 日志**

```cpp
// ❌ 每次全量覆盖
std::ofstream ofs("/data/state.txt");
ofs << currentState;

// ✅ 只 append
std::ofstream ofs("/data/state.log", std::ios::app);
ofs << event;
// 定期做 compaction（合并 + 清理老 log）
```

**招数二：批量提交**

```cpp
// ❌ 每次事件都 fsync
for (auto& e : events) {
    writeToFile(e);
    fsync(fd);                                 // 100 次 fsync
}

// ✅ 批量
for (auto& e : events) writeToFile(e);
fsync(fd);                                     // 1 次 fsync
```

**招数三：小数据放 tmpfs 或 RAM**

```
频繁变化但不重要的数据（如统计计数）→ 放 /tmp（tmpfs 内存文件系统）
每小时或每 N 次落盘一次持久化
```

**招数四：合适的文件系统**

```
裸 NAND      ： 必须 UBIFS（有磨损均衡）
eMMC/SD      ： ext4 / f2fs（f2fs 专为 Flash 设计，写放大更低）
只读部分     ： squashfs（打包压缩，不产生写）
```

**招数五：调 mount 参数**

```bash
# 关闭 access time 更新
mount -o noatime,nodiratime ...

# ext4：data=writeback 比默认 ordered 快，但掉电风险高
# ext4：延迟提交
mount -o data=writeback,commit=30 ...
```

**综合优化前后对比**（第 1 章场景）：

| 优化 | 每天 Flash 擦写量 |
|---|---|
| 优化前（覆盖写 + fsync） | ~100 GB |
| 改 append + 批量 fsync | ~800 MB |
| 换 f2fs + noatime | ~500 MB |
| 内存缓冲 + 定时刷盘 | ~200 MB |

**寿命从 8 个月 → 8 年+**。


## 6. 分区策略

### 6.1 只读只写分离

**核心思想**：**能只读的一律只读，可写的越小越好**。

理由：
1. **只读分区不磨损**（squashfs 或 ext4 挂 `ro`）
2. **只读分区不怕掉电损坏**
3. **只读分区可以做完整性校验**（dm-verity）

**典型分区布局**：

```
┌─────────────────────────────────────────────────┐
│ Boot  │ System (RO) │ Config (RW) │ Data (RW)   │
│  8MB  │    1 GB     │    16 MB    │    1~4 GB   │
└─────────────────────────────────────────────────┘
     │           │              │            │
     │           │              │            └─ 日志、缓存、用户数据
     │           │              └─ 少量配置文件
     │           └─ rootfs + 应用（squashfs 或 ext4 ro）
     └─ U-Boot + 内核 + DTB
```

### 6.2 A/B分区支持OTA

**问题**：升级时如果只有一套 system，写到一半掉电就变砖。

**A/B 方案**：两份 system 分区，交替升级：

```
┌────────────────────────────────────────────────────┐
│ Boot │ SystemA │ SystemB │ Config │ Data │ Misc    │
└────────────────────────────────────────────────────┘

启动时：Bootloader 读 misc 分区，知道当前活跃是 A 还是 B
OTA：   下载新版本写入非活跃分区，写完 → 校验 → 切换活跃分区标志
失败：  Bootloader 自动回退到旧分区，永远有可启动版本
```

**成本**：system 分区容量翻倍。但对可靠性极大提升，主流方案。

### 6.3 分区表模板

一份可复用的模板（GPT / 8 GB eMMC）：

| 分区 | 大小 | 类型 | 挂载 | 用途 |
|---|---|---|---|---|
| bootloader | 8 MB | raw | / | U-Boot |
| bootenv | 512 KB | raw | / | U-Boot 环境变量 |
| dtb | 512 KB | raw | / | 设备树 |
| kernel_a | 32 MB | raw | / | 内核镜像 A |
| kernel_b | 32 MB | raw | / | 内核镜像 B |
| system_a | 1 GB | squashfs | / (ro) | rootfs A |
| system_b | 1 GB | squashfs | 备用 | rootfs B |
| vendor | 200 MB | ext4 (ro) | /vendor | 私有配置 |
| config | 16 MB | ext4 | /etc | 可写配置 |
| data | 4 GB | f2fs | /data | 用户数据 |
| misc | 1 MB | raw | / | OTA 状态、slot 指示 |
| logs | 128 MB | ext4 | /var/log | 循环日志 |

**关键**：
- system 挂 ro，不容易损坏
- data 挂 f2fs（对 Flash 友好），单独一个分区，坏了不影响系统启动
- logs 单独分区（限量），日志爆了不撑爆 data
- misc 存 A/B 切换标志


## 7. 掉电保护

### 7.1 掉电场景分类

**掉电对应用的伤害有三级**：

| 等级 | 表现 | 触发 |
|---|---|---|
| L1：应用状态丢失 | 未 flush 的 write 丢了 | write 到 page cache 没 fsync 就断电 |
| L2：文件损坏 | fsck 报错、部分数据错乱 | fsync 到 FTL 未落盘 |
| L3：文件系统崩溃 | mount 失败、需要 mkfs 重装 | 元数据（如 inode）写到一半断电 |

L1 是常态，L2 靠 journal 保护，**L3 是致命的**——设备变砖。

### 7.2 原子写与COW

**原子写模式**：对关键文件的更新，用"写新 + rename"三步保证：

```cpp
// ❌ 覆盖写（掉电 = 文件半破损）
std::ofstream("/data/config.json") << json;

// ✅ 原子写
{
    std::ofstream tmp("/data/config.json.tmp");
    tmp << json;
    tmp.flush();
    fsync(fileno(tmp.rdbuf()->__file()));      // 1. 先 sync 内容
}
rename("/data/config.json.tmp",
       "/data/config.json");                    // 2. 原子 rename
int dfd = open("/data", O_RDONLY);
fsync(dfd);                                     // 3. sync 目录
close(dfd);
```

**为什么**：POSIX 保证 `rename` 是原子的——要么是老文件，要么是新文件，不会有"半新半旧"。

**Copy-On-Write（COW）**：文件系统层做同样的事。**btrfs / f2fs / UBIFS** 天然 COW：写新数据到空块，元数据切换指针，掉电时最多丢当前正在写的一次，之前的数据不动。

### 7.3 journal的代价

**ext4 的 journal**：数据/元数据写完之前，先写一份 journal log。掉电重启时 fsck 根据 journal 恢复。

三种 journal 模式：

| 模式 | 保护 | 性能 |
|---|---|---|
| journal | 数据 + 元数据 | 最慢，最安全（写两遍） |
| ordered（默认） | 只元数据，但数据先写 | 中等 |
| writeback | 只元数据，数据顺序不保证 | 最快，掉电可能读到旧数据但文件系统结构不坏 |

**嵌入式实用建议**：
- 系统分区（只读）→ 不需要 journal
- 数据分区 → 默认 ordered
- 只关心结构完整、内容可重建 → writeback

**journal 也吃 Flash**——每次写都要写 journal，写放大加倍。这是 f2fs 的动机：**为 Flash 而生的 log-structured file system**，天然 COW，不需要传统 journal。


## 8. 选型决策树

### 8.1 六个维度

1. **容量需求**：MB / GB / 数十 GB
2. **写入模式**：只读 / 少量写 / 大量随机写 / 大量顺序写
3. **每天写入量**：MB / GB
4. **目标寿命**：3 年 / 5 年 / 10 年
5. **成本预算**：便宜优先 / 性能优先
6. **可靠性等级**：消费级 / 工业级 / 车规级

### 8.2 一张图选完

```
START
   │
   ├── 只放 bootloader/kernel？── 是 ──► NOR Flash (spi-nor + squashfs)
   │        │
   │        否
   │        ▼
   ├── 容量 < 256 MB？── 是 ──► NAND + UBI + UBIFS
   │        │
   │        否
   │        ▼
   ├── 容量 256 MB ~ 32 GB？── 是 ──► eMMC + ext4/f2fs
   │        │
   │        否
   │        ▼
   ├── 要求高吞吐（车载/工控）？── 是 ──► UFS + ext4/f2fs
   │        │
   │        否
   │        ▼
   └── 消费级临时存储？── 是 ──► SD 卡（但不放关键数据）

选好介质后：
  只读分区 → squashfs（省空间、防写坏）
  可写分区 → ext4 (成熟) 或 f2fs (Flash 友好)
  裸 NAND  → 必须 UBIFS
  A/B 分区 → OTA 场景一定要
```

### 8.3 常见误用

**误用 1**：**裸 NAND 上跑 ext4**

```
后果：ext4 假设块设备等价物理块，无磨损均衡，几个月就写坏
✅ 正确：NAND 必须 UBI + UBIFS
```

**误用 2**：**用 SD 卡当产品主存储**

```
后果：SD 卡消费级 FTL，小随机写伤 Flash，一年内批量返厂
✅ 正确：eMMC（车规级）
```

**误用 3**：**所有分区都 rw**

```
后果：系统分区被误改，回滚困难；写坏概率放大
✅ 正确：system 挂 ro
```

**误用 4**：**覆盖写关键配置文件**

```
后果：掉电 → 文件半破损 → 应用启动失败
✅ 正确：临时文件 + rename 原子替换
```

**误用 5**：**每条日志 fsync**

```
后果：写放大 100x，Flash 加速磨损
✅ 正确：批量 fsync（每 N 条 或每 T 秒一次）
```


## 9. 可靠性与调试

### 9.1 寿命监控

**eMMC 有 SMART/EXT_CSD 寄存器**，读出剩余寿命：

```bash
# 查看 eMMC 健康度（需 mmc-utils）

# 关键字段
DEVICE_LIFE_TIME_EST_TYP_A     : 0x02   # 类型 A 使用 10~20%
```

### 9.2 掉电压测

**压测方案**：
1. 编写脚本反复写入 + 随机断电（继电器控制电源）
2. 每次上电后 fsck，看是否 fs 损坏

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到第 1 章"车载 T-BOX 批量返厂"，五处问题——五处修复：

| 问题 | 根因 | 修复 | 章节 |
|---|---|---|---|
| GPS 每 100ms 覆盖写 | 写放大 400x | 改 append，1 分钟 checkpoint | §5.3 §7.2 |
| 日志每行 fsync | 写放大加倍 | 每 100 条或 5s fsync 一次 | §5.3 |
| 事件计数器频繁落盘 | 高频小写 | tmpfs 缓冲，1 分钟或退出时落盘 | §5.3 |
| 裸 NAND 上跑 ext4 | 无磨损均衡 | 改 UBI + UBIFS | §4.2 §8.3 |
| 无分区隔离 | 数据爆撑坏系统 | 独立 data/logs 分区 | §6.1 |

**改造后**（原代码等价重写）：

```cpp
// GPS：批量 append + 定时 fsync
class GpsWriter {
    std::ofstream ofs_{"/data/gps.log", std::ios::app};
    Timer timer_;
public:
    GpsWriter() { timer_.every(60s, [this]{ ofs_.flush(); fsync(fd()); }); }
    void write(const Fix& f) { ofs_ << f.toJson() << '\n'; }   // 不 fsync
};

// 日志：async logger + 批量刷盘
class Logger {
    SpscRing<std::string, 8192> queue_;
    std::thread worker_;
    void loop() {
        std::vector<std::string> batch;
        while (running_) {
            drain(batch, 100 /* 或 timeout 5s */);
            for (auto& l : batch) fs_ << l << '\n';
            fs_.flush();
            fsync(fd());
        }
    }
};

// 事件计数：内存 + tmpfs 缓冲
class EventCounter {
    std::atomic<uint64_t> cnt_{0};
    Timer timer_;
public:
    EventCounter() { timer_.every(60s, [this]{ persist(); }); }
    void inc() { cnt_++; }
    void persist() {
        writeAtomic("/data/event_counter", std::to_string(cnt_));
    }
};
```

**结果**：日均 Flash 擦写从 100 GB 降到 200 MB，理论寿命从 8 个月 → 10 年+。

### 10.2 一次写入的一生

从 `write("/data/xxx", 300 bytes)` 到真正落盘，完整走一遍：

```
应用调用 write(fd, buf, 300)
    │
    ▼ 【1. VFS 层】
sys_write → 找到 f_op->write
    │
    ▼ 【2. 文件系统层（ext4）】§7.3
写入 page cache 的 page（4 KB）
标记 dirty
返回给用户（还没到 Flash！）
    │
    ▼ 【3. 用户调用 fsync 或 pdflush 定时刷】
调 f_op->fsync → 写 journal
    │
    ▼ 【4. Block 层】§2.1
生成 bio → 提交到 request_queue
    │
    ▼ 【5. eMMC 驱动】
通过 CMD25 (多块写) 发到 eMMC 控制器
    │
    ▼ 【6. eMMC 内部 FTL】§4.2 §4.3
    ├─ 找一块干净的 page 写入
    ├─ 更新 L2P 映射表
    ├─ 磨损均衡检查
    ├─ 老 page 标记 invalid
    └─ 触发 GC（异步）
    │
    ▼ 【7. NAND cell】§4.1
物理写入完成，返回 ACK
    │
    ▼ 【8. 一层层返回】
eMMC 控制器 → 驱动 → Block → FS → VFS → 用户返回 write 成功
```

**关键洞察**：**你 write 完不代表落盘**。中间任何一层的 cache 都可能"骗"你。**只有 fsync 完成才敢说"数据安全"**，而 fsync 会同步触发 3~7 步，代价很大。这就是"批量 fsync"和"COW 文件系统"存在的理由。

### 10.3 设计哲学回扣

**哲学 1：物理边界反向约束软件**

Flash 有物理磨损，这不是一个可以"多加机器"绕开的问题。**软件设计必须让写入模式匹配物理特性**——append 好于覆盖，批量好于零散，只读好于可写。忽视物理边界的代码，跑在实验室里没事，量产 3 个月就返厂。

**哲学 2：分区是隔离级别**

数据分区坏了不该影响系统能不能启动，日志爆了不该占满数据分区。**每个可写分区都是一个"故障域"**，规划分区就是规划故障隔离。这和微服务架构的思路是一样的。

**哲学 3：可靠性 = 冗余 + 幂等 + 校验**

A/B 分区是冗余，原子写 rename 是幂等，checksum 是校验。**三样齐全，掉电、写坏、传输错都能扛**；缺一样，都会在小概率场景炸雷。

**哲学 4：先算账再动手**

寿命估算不是可选项。**每天写入量 × 写放大 × 使用年限 = 需求总擦写量**，与 Flash 的 TBW 对比，差 10 倍就要换方案。工程师不算账，就是把风险留给售后。

### 10.4 速查手册

**存储设计四步走**：

```
1. 估算写入量 → 判断介质容量与寿命
2. 分区规划    → 只读/可写分离，A/B 冗余
3. 写入模式    → append + 批量 + 原子替换
4. 掉电压测    → 上量产前 1000 次断电测试
```
