## 1. 案例引入

### 1.1 每 72 小时准时重启的定位器

现场从一款 4G 定位器裁剪。设备每 72 小时准时重启一次，日志里看到的是 `oom-killer` 敲门：

```c
// tracker_uploader.c —— 简化版
typedef struct point { double lat, lon; int64_t ts; char *tag; } point_t;

static point_t *queue[65536];
static int head = 0, tail = 0;

// 每 1 秒采集一个点
static void on_sample(double la, double lo) {
    point_t *p = malloc(sizeof(point_t));   // ← §5.1 泄漏点 1
    p->lat = la; p->lon = lo; p->ts = now_ms();
    p->tag = strdup(build_tag());           // ← §5.1 泄漏点 2
    queue[tail++ & 0xFFFF] = p;
}

// 每 10 秒批量上传
static void on_upload(void) {
    if (net_down()) return;                 // ← §4.1 网络断了就直接返回
    for (int i = head; i != tail; i++) {
        upload(queue[i & 0xFFFF]);          // 上传成功
        // free(queue[i & 0xFFFF]);        // ← §5.1 漏了这行
    }
    head = tail;
}
```

日志显示的是"OOM"，第一反应大家都以为是**"内存泄漏"**——但用 `top` 看 RSS，只涨到 30MB 就被杀，设备明明有 128MB 内存。到底哪里出了问题？

### 1.2 顺藤摸到根因

三个坑叠在一起：

- **泄漏是真的**：`on_sample` 里 malloc/strdup 的对象上传后没 free。
- **限额是真的**：这个进程被 cgroup 限制到 32MB，`memory.max=32M`，OOM 是 cgroup 级别的，不是整机。
- **看数错了**：`top` 看的是整机可用，看不到 cgroup 限额，也看不出 PSS 与 RSS 差异。
- **网络断连时泄漏加速**：`net_down()` 直接 return，采样继续入队，队列指数膨胀。
- **glibc arena 假象**：free 之后 RSS 也不降，导致"看起来已经泄漏"的错觉。

真正藏的技术点：**"看到 RSS 涨不等于泄漏，看不到 RSS 涨也不等于没泄漏"**——嵌入式内存问题的核心矛盾。

### 1.3 我们要回答什么

- `/proc/pid/smaps` 里的 RSS/PSS/VSS 到底信哪个？ → §3.2 / §3.3
- glibc 明明 free 了为什么 RSS 不降？换 jemalloc 有救吗？ → §4.1 / §4.2
- valgrind 那么慢，嵌入式怎么用？ASan 与 heaptrack 谁更合适？ → §5.1 / §5.2
- 整机没爆但进程被杀，是不是 cgroup 干的？ → §6.2
- 定长包 1KB × 1w 个和随机大小该用不同分配器吗？ → §7.1
- 线程栈 8MB × 200 线程 = 1.6GB，虚拟地址空间会不会爆？ → §7.3

## 2. 内存体系概览

### 2.1 三层内存视角

嵌入式排查内存要同时用三层视角，只看一层必错：

```
┌───────────────────────────────────────────────────────┐
│  第三层：整机                                          │
│    /proc/meminfo：MemTotal / MemFree / Available      │
│    看不出 cgroup、看不出 arena 空洞                    │
├───────────────────────────────────────────────────────┤
│  第二层：cgroup / 进程                                 │
│    /proc/pid/status: VmRSS / VmSize                   │
│    /sys/fs/cgroup/.../memory.current                  │
│    真实"进程用了多少"                                  │
├───────────────────────────────────────────────────────┤
│  第一层：地址空间                                       │
│    /proc/pid/maps + smaps                             │
│    每一段是什么、Anon / File-backed / Shared          │
│    分配器 arena 的碎片形态                             │
└───────────────────────────────────────────────────────┘
```

**"从大到小逐层往里挖"**：先看整机，再看进程，最后看地址段。反过来看会漏掉限额和整机余量。

### 2.2 嵌入式内存的四种"死法"

不是所有"内存问题"都是泄漏，四种死法要分清：

- **真泄漏**：分配路径远大于释放路径，RSS/PSS 单调上升。
- **碎片化**：分配和释放对称，但空洞对齐不上，可用内存被撕成碎片，`malloc(N)` 失败。
- **一次性大分配**：正常场景下不出，某个批量 case 一次要 100MB。
- **虚拟地址空间耗尽**：`mmap` / 线程栈占满 32 位地址空间，看着 RSS 才 200MB 却 OOM。

**"泄漏用 heaptrack，碎片化用 mallinfo，突发用 core dump，vsz 用 maps"**——排查工具要对号入座。

## 3. 进程内存布局

### 3.1 虚拟地址空间的六块

任何 Linux 进程的虚拟地址空间由六部分构成：

```
高地址
 ┌────────────────────────┐
 │   内核空间（不可见）     │
 ├────────────────────────┤
 │   栈  Stack ↓          │  main + 各线程栈（pthread_create 独立）
 ├────────────────────────┤
 │   mmap 区域             │  动态库 / mmap 文件 / 大块 malloc
 │   ↕                    │
 ├────────────────────────┤
 │   堆  Heap ↑            │  brk/sbrk 增长，ptmalloc arena
 ├────────────────────────┤
 │   BSS / Data           │  全局变量
 ├────────────────────────┤
 │   Text                 │  代码段（只读）
 └────────────────────────┘
低地址
```

嵌入式两个关键差异：

- **32 位 ARM 用户空间只有 3GB**（TASK_SIZE 3GB/1GB），每个线程默认 8MB 栈，理论上只能开 384 个线程。
- **mmap 区域与堆相向增长**，中间是共享库和大块 malloc，长期运行会把中间"缝隙"逐渐填死。

### 3.2 从 smaps 读懂真实占用

`/proc/pid/smaps` 是"每段一份的详单"，格式如下：

```
7f8a1c000000-7f8a1c400000 rw-p 00000000 00:00 0      [heap]
Size:               4096 kB    ← 虚拟大小（VSS 组成）
Rss:                1200 kB    ← 已在物理内存中
Pss:                 900 kB    ← 按共享比例分摊
Anonymous:          1200 kB    ← 匿名（真堆分配）
Shared_Clean:          0 kB
Private_Dirty:      1200 kB    ← 真正"你独占且脏"的部分
```

四条速查规则：

- **看 `Pss` 累加**：判断进程真实内存占用，共享库不重复计算。
- **看 `Anonymous`**：判断堆和栈的分配情况，与 File-backed 分开。
- **看 `Private_Dirty`**：这是**真正无法回收的部分**，杀掉进程才能还给内核。
- **看段数**：`wc -l /proc/pid/maps` 段数快速上涨 = 泄漏 mmap（比如 dlopen 泄漏）。

工具：`pmap -X <pid>`、`smem -k -P gateway` 是 smaps 的可读封装。

### 3.3 RSS/PSS/VSS 的取舍

三个指标各有陷阱：

| 指标 | 含义 | 陷阱 |
|------|------|------|
| VSS | 虚拟地址总量 | 包含没落物理的 mmap 保留区，虚高 |
| RSS | 已落物理 | 共享库被多次计算，多进程共享时膨胀 |
| PSS | 按共享比例分摊 | 最准，但需要读 smaps，稍慢 |

**结论**：**监控用 PSS，报警阈值也用 PSS**；`top` 那列 RSS 看看就行，别当结论。

`/sys/fs/cgroup/xxx/memory.current` 是 cgroup 视角的"进程实际消费"，对齐 PSS，是最推荐的**在线监控数据源**。

## 4. 分配器与碎片化

### 4.1 glibc ptmalloc 的坑

glibc 的 ptmalloc（malloc/free）在嵌入式里有三个反直觉行为：

- **free 不一定还内核**：小块（<128KB）free 后进 fastbin/tcache，RSS 不降。只有大块（`M_MMAP_THRESHOLD` 默认 128KB 以上）用 mmap，free 时才 munmap。
- **多线程默认多 arena**：每个线程可能挂到独立 arena，导致**同一份数据在多个 arena 里各留一份**，VSS 虚高。`export MALLOC_ARENA_MAX=2` 是嵌入式常用防御。
- **碎片不可主动整理**：free 后的空洞挂在 bin 上，只有相邻空洞合并，`malloc_trim(0)` 可以尝试还内核，但只能还"堆顶"连续的部分。

**"glibc 的 free 是逻辑释放，不是物理释放"**——记这一句就够了。

### 4.2 jemalloc / tcmalloc / mimalloc

三种常见替代：

- **jemalloc**：碎片控制最好，Redis/Rust 默认用它。适合长驻服务、随机大小分配。
- **tcmalloc**：Google 出品，多线程分配快，thread-local cache。
- **mimalloc**：微软出品，实现最新，小对象性能强。

三种都通过 `LD_PRELOAD` 或链接时替换 malloc：

```bash
LD_PRELOAD=/usr/lib/libjemalloc.so.2 ./gateway
```

嵌入式**首选 jemalloc**：碎片少、支持 `malloc_stats_print` 输出详细指标，配合 `MALLOC_CONF=stats_print:true` 上线可诊断。

### 4.3 碎片化的度量与复现

碎片化度量三个指标：

- **`mallinfo2().uordblks`**：已分配总量。
- **`mallinfo2().fordblks`**：free 但没还内核的量。
- **碎片率**：`fordblks / (uordblks + fordblks)`，超过 50% 就该警惕。

复现碎片化最简单的 case：交替分配大小对象：

```c
for (int i = 0; i < 100000; i++) {
    void *p1 = malloc(16);       // 小对象
    void *p2 = malloc(64);
    void *p3 = malloc(4096);     // 大对象
    free(p2);                    // 只 free 中间的
}
// 现在中间是"64B 空洞"，再分配 4KB 就用不上
```

一段时间后 `malloc(1MB)` 会失败 —— **有内存，但没连续内存**。修复方向：定长对象走内存池（§7.1），随机大小换 jemalloc（§4.2）。

## 5. 泄漏检测

### 5.1 valgrind 与 ASan 的分工

两者都能查内存泄漏，但成本与场景不同：

| 维度 | Valgrind memcheck | ASan |
|------|------|------|
| 需要重编译 | ❌ 不需要 | ✅ 需要 `-fsanitize=address` |
| CPU 开销 | ×10 ~ ×30 | ×2 ~ ×3 |
| 内存开销 | ×2 | ×2 ~ ×3（影子内存）|
| 报错精度 | 分配栈 + 泄漏点 | 分配栈 + 释放栈 + 触发栈 |
| 嵌入式适用 | 只能开发机跑 | 可上板灰度 |

**结论**：**嵌入式开发阶段用 ASan（第 11 篇），Valgrind 只在开发机上短跑**。板上跑 valgrind 慢到看门狗一定咬。

### 5.2 heaptrack / massif 的适用面

ASan 擅长"报出泄漏"，但**不擅长"分析趋势"**。想知道"过去 10 分钟哪个函数分配最多、哪些对象活得最久"，用：

- **heaptrack**（KDE 出品）：记录每次 malloc/free，跑完出交互图。开销 ×2 左右，比 valgrind 轻。
- **massif**（valgrind 子工具）：定时快照堆，出堆图。慢，但只需要单次快照就能看曲线。

嵌入式典型用法：

```bash
# 开发机上跑，把 core 拉回来分析
heaptrack ./gateway
# 生成 heaptrack.gateway.*.gz
heaptrack --analyze heaptrack.gateway.*.gz
```

heaptrack 输出**"Top consumers by allocations / by peak / by leaked"**三视图，直接告诉你"泄漏的分配栈是哪一条"。

### 5.3 LD_PRELOAD 轻量注入

不想改代码、不想重编译，就用 LD_PRELOAD 拦截 malloc/free 做统计。核心思路：

```c
// libmemtrace.c —— 骨架
static __thread int  in_hook;               // 防重入
static _Atomic uint64_t alloc_bytes, free_bytes;

void *malloc(size_t n) {
    static void *(*real)(size_t);
    if (!real) real = dlsym(RTLD_NEXT, "malloc");
    void *p = real(n);
    if (!in_hook && p) {
        in_hook = 1;
        atomic_fetch_add(&alloc_bytes, n);
        // 记录 backtrace(3 层)、写入 ring buffer
        in_hook = 0;
    }
    return p;
}

void free(void *p) {
    static void (*real)(void*);
    if (!real) real = dlsym(RTLD_NEXT, "free");
    real(p);
    // 差分记账
}
```

上板启动：

```bash
LD_PRELOAD=./libmemtrace.so ./gateway
kill -USR1 $(pidof gateway)      # 触发 dump 统计到 /tmp/memtrace.log
```

**注意事项**：

- `in_hook` 必须是 `__thread`，否则 hook 里调用 `dlsym`/`printf` 自己触发 malloc → 死循环。
- backtrace 只取 3 层（`__builtin_return_address(0/1/2)`），聚合成"分配点指纹"。
- 落盘用 ring buffer + 信号触发 dump，避免每次 malloc 都写文件。

这份工具**只有几百行**，比 valgrind 轻两个数量级，嵌入式生产环境可以短期开启。

## 6. OOM 与 cgroup

### 6.1 overcommit 的三档

`vm.overcommit_memory` 决定内核是否允许"透支":

| 值 | 行为 | 适用 |
|----|------|------|
| 0 | 启发式：小额允许，大额拒绝 | 默认，桌面/服务器 |
| 1 | 总是允许 | 内存超卖，如 Redis fork |
| 2 | 严格：总量不超过 `RAM×ratio + swap` | **嵌入式推荐** |

嵌入式**推荐 `vm.overcommit_memory=2` + `vm.overcommit_ratio=80`**：让 malloc 在真的超支时就返回 NULL，而不是等到 OOM Killer 杀你。业务代码要检查 malloc 返回值，形成对齐。

### 6.2 cgroup memory 限制

systemd unit 里配 `MemoryMax=` 是嵌入式限流的常用做法：

```ini
[Service]
MemoryMax=64M
MemoryHigh=48M           # 软限：接近时开始回收
MemorySwapMax=0          # 禁用 swap
OOMPolicy=stop           # 触发时 stop 整个 unit（不重启爆炸循环）
```

**cgroup OOM 与整机 OOM 是两回事**：

- 整机 OOM：`/proc/meminfo` 里 MemAvailable 极低，内核挑 oom_score 最高的杀。
- cgroup OOM：某个 cgroup 超 `memory.max`，只杀该 cgroup 里的进程；`dmesg` 里能看到 `Memory cgroup out of memory`。

案例 §1.1 就是 cgroup OOM，看整机内存永远正常。**排查第一句：`cat /proc/pid/cgroup` + `cat /sys/fs/cgroup/xxx/memory.max`**。

### 6.3 oom_score_adj 优先级

不想被 OOM 杀掉的关键进程，调低 `oom_score_adj`：

```bash
echo -900 > /proc/$(pidof watchdog_agent)/oom_score_adj  # 尽量别杀我
echo  500 > /proc/$(pidof log_dumper)/oom_score_adj      # 优先杀这个
```

范围 -1000 ~ 1000，越低越难杀。**看门狗、上报进程一律 -800~-900**，日志压缩、临时工具一律 +500。给关键进程一根"救命稻草"。

## 7. 内存池与栈监控

### 7.1 定长内存池

定长对象走内存池，一次性 mmap 一大块，切成固定大小的槽位：

```c
typedef struct pool {
    void  *base;
    size_t obj_size;
    void  *free_list;      // 单链表，串起来空闲槽
} pool_t;

void pool_init(pool_t *p, size_t obj, size_t n) {
    p->base = mmap(NULL, obj*n, ...);
    p->obj_size = obj;
    p->free_list = NULL;
    for (size_t i = 0; i < n; i++) {
        void *slot = (char*)p->base + i * obj;
        *(void**)slot = p->free_list;
        p->free_list = slot;
    }
}

void *pool_alloc(pool_t *p) {
    void *r = p->free_list;
    if (r) p->free_list = *(void**)r;
    return r;
}

void pool_free(pool_t *p, void *ptr) {
    *(void**)ptr = p->free_list;
    p->free_list = ptr;
}
```

三条收益：

- **零碎片**：所有槽一样大，永远合得上。
- **分配 O(1)**：单链表头出头进，不需要遍历。
- **RSS 稳定**：一次性 mmap 上限，free 只是逻辑归还。

适用场景：会话、包、事件——**"数量级已知、大小固定、生命周期短"** 的对象。

### 7.2 对象池与 slab

定长池的升级：**对象池**在池里维护"可复用对象"而不是"内存槽"，避免每次分配后再构造：

```c
Session *sess_acquire(void) {
    Session *s = pool_alloc(&sess_pool);
    session_reset(s);            // 就地复位，不重新构造
    return s;
}

void sess_release(Session *s) {
    session_teardown_light(s);   // 关连接但不析构
    pool_free(&sess_pool, s);
}
```

**Linux 内核 slab 分配器就是这个思路**：把频繁 alloc/free 的同型对象放进 cache，减少分配开销。用户态自己写一个 slab 也不难——一个 pool + 一个 constructor + 一个 destructor。

### 7.3 栈溢出检测

嵌入式线程栈的两个陷阱：

- **默认 8MB 太大**：`pthread_attr_setstacksize(&a, 128*1024)` 常设 64KB~256KB。
- **递归/大局部数组直接爆栈**：`char buf[64*1024]` 局部数组直接把栈打穿，SIGSEGV 无栈可回溯。

编译期防御：`-fstack-protector-strong` 在栈末尾插 canary，写坏时立即 abort，比 UAF 好定位。

运行时监控：读 `/proc/pid/status` 的 `VmStk` 看栈大小，或者读每个线程的 `/proc/pid/task/tid/status`。**栈满**时 mmap growup 失败，直接 SIGSEGV，`dmesg` 有 `stack overflow`。

一个 shell 快速看栈使用：

```bash
for tid in $(ls /proc/$(pidof gateway)/task); do
    grep VmStk /proc/$(pidof gateway)/task/$tid/status
done
```

## 8. 选型决策树

### 8.1 六个维度

- **能不能改代码**：能 → ASan / 内存池；不能 → LD_PRELOAD。
- **内存量大小**：小设备（<256MB）→ jemalloc + 严格 overcommit；大设备可以放松。
- **分配特征**：定长高频 → 内存池；随机大小 → jemalloc。
- **是不是长驻**：长驻 → 关心碎片；短进程 → 关心峰值。
- **调试可停机**：可以 → valgrind/heaptrack 开发机跑；不能 → smaps + LD_PRELOAD 在线采样。
- **有没有 cgroup**：有 → 先看 memory.current，别被整机 free 骗了。

### 8.2 一张图选完

```
                   内存问题
                     │
        ┌────────────┴────────────┐
     RSS 单调涨？              突然 OOM？
        │                          │
   泄漏排查                  ┌─────┴─────┐
   ┌──┴──┐                 整机?      cgroup?
   开发机  上板              │            │
   │       │             top/meminfo   memory.current
   heaptrack LD_PRELOAD    │            │
   ASan     smaps 段数      调低 RSS   调整 MemoryMax
   ↓         ↓                       oom_score_adj
   分配栈   泄漏点
        │
   RSS 涨但 free 也涨？
        │
    碎片化 → jemalloc / 内存池
```

### 8.3 常见误用

- **只看 top 的 RES**：看不出 cgroup，看不出 arena 空洞。**先看 PSS + memory.current**。
- **glibc free 后期待 RSS 降**：期望错了，需要 `malloc_trim(0)` 或换 jemalloc。
- **valgrind 上板跑**：慢到看门狗咬。**valgrind 只开发机**。
- **上线才想起没设 MemoryMax**：一个进程泄漏拖垮整机。**cgroup 是嵌入式默认交付项**。
- **线程栈默认 8MB 开几百线程**：VSS 打爆 32 位地址空间。**必设 stacksize**。
- **ASan 直接上量产**：内存翻倍、CPU 减半，量产扛不住。**灰度长跑，量产 Release**。

## 9. 可靠性与调试

### 9.1 内存持续增长排查 SOP

设备"内存缓慢上涨"报警后按顺序走：

```bash
# 1. 确认涨的是谁：整机 / cgroup / 进程
cat /proc/meminfo | grep -E 'MemTotal|MemAvailable|Anon|Slab'
cat /sys/fs/cgroup/system.slice/gateway.service/memory.current
cat /proc/$(pidof gateway)/status | grep -E 'VmRSS|VmSize|VmData'

# 2. 看进程内部：哪块段在涨
pmap -X $(pidof gateway) | sort -k4 -n | tail -20   # 按 RSS 排序，看头部
wc -l /proc/$(pidof gateway)/maps                    # 段数快速涨 = mmap 泄漏

# 3. 看分配器：是不是碎片
gdb -p $(pidof gateway)
(gdb) call (int)malloc_stats()                       # 打印到 stderr

# 4. 采样式确认：LD_PRELOAD 版本跑几分钟
LD_PRELOAD=./libmemtrace.so systemctl restart gateway
sleep 300 && kill -USR1 $(pidof gateway) && cat /tmp/memtrace.log

# 5. 精细复现：heaptrack 在开发机
heaptrack ./gateway_x86 --replay-of=captured.log
```

**"整机 → cgroup → 进程 → 段 → 分配点"** 是排查方向，粒度逐层收窄。

### 9.2 突发 OOM 排查

设备突然被 OOM Killer 杀掉，日志里没铺垫，按顺序：

```bash
# 1. 谁杀的？内核还是 cgroup
dmesg -T | grep -i 'oom-killer\|Memory cgroup out of memory'
journalctl -u gateway | grep -i oom

# 2. 死前的最后一次快照（如果配了）
cat /var/log/gateway_mem.log | tail -50

# 3. 死后重启，第一时间抓一次
systemctl start gateway
sleep 10 && cat /sys/fs/cgroup/.../memory.stat > /tmp/before.log
sleep 60 && cat /sys/fs/cgroup/.../memory.stat > /tmp/after.log
diff /tmp/before.log /tmp/after.log

# 4. 一次性大分配？看 max_usage
cat /sys/fs/cgroup/.../memory.peak
```

**"突发 OOM 90% 是一次性大分配"**：批量任务、一次性 dump、大 buffer。找到那个批量任务的入口，改成流式或分片处理。

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到 §1.1 的代码，逐行标注章节：

```c
static point_t *queue[65536];       // 64K 槽位 × 指针 = 256KB，先不炸

static void on_sample(double la, double lo) {
    point_t *p = malloc(sizeof(point_t));  // ← §5.1 泄漏点：无对应 free
    p->tag = strdup(build_tag());          // ← §5.1 二级泄漏
    queue[tail++ & 0xFFFF] = p;            // ← 环形覆盖，前面的指针直接丢
}

static void on_upload(void) {
    if (net_down()) return;                 // ← §6.2 网络断时不释放
    for (int i = head; i != tail; i++) {
        upload(queue[i & 0xFFFF]);
        // free(queue[i & 0xFFFF]);         // ← §5.1 漏了释放
    }
    head = tail;
}
```

**真相**是三个坑叠加：

- `on_sample` malloc + strdup 后没 free；
- 环形缓冲覆盖导致老指针丢失（**最隐蔽**）——即便记得 free，覆盖后也 free 不到；
- 断网时 `on_upload` 直接 return，队列持续入不清理，泄漏加速；
- cgroup `MemoryMax=32M`（§6.2），30MB 就 OOM，整机看着没事。

修复思路（三选一）：

- 队列改成"入前先释放旧槽"或用 `std::deque` 全量存储；
- 上传失败也要清理，或落盘转本地队列（第 05 篇 §5 断线重连策略）；
- 定长 `point_t` 走内存池（§7.1），彻底消除 malloc/free 对称问题。

### 10.2 一次内存增长的一生

```
[T0]  设备启动，RSS = 6MB                     ← §3.2 稳态
       │  ptmalloc 初始化，主 arena
       │  cgroup MemoryMax=32M              ← §6.2
       │
[T1]  运行 1 小时，RSS = 18MB
       │  on_sample × 3600 次 → 3600 个 point + tag
       │  队列覆盖丢 1500 个指针 → 1500 × ~64B = 96KB 泄漏/h
       │
[T2]  网络抖动 10 分钟，RSS = 23MB
       │  on_upload 直接 return，泄漏加速 10×
       │  ptmalloc arena 内碎片累积          ← §4.1
       │
[T3]  运行 72 小时，PSS = 30MB
       │  memory.current 逼近 32M           ← §6.2
       │  memory.high 触发回收 → 无可回收    ← ptmalloc 不还内核
       │
[T4]  下一次 on_sample → 分配失败
       │  → cgroup OOM Killer → kill -9
       │  dmesg: "Memory cgroup out of memory"
       │
[T5]  systemd Restart=on-failure → 拉起     ← 第 07 篇
       │  循环
       │
[T6]  运维发现"72 小时周期性重启"
       │  ↓
       │  SOP §9.1：看 memory.current + smaps
       │  → 定位到 heap 段持续涨
       │  → LD_PRELOAD memtrace 复现       ← §5.3
       │  → 分配栈指向 on_sample
       │
[T7]  换定长内存池 → RSS 稳定在 8MB
       │  72 小时循环消失
```

### 10.3 设计哲学回扣

- **"泄漏不是 RSS 涨，是 PSS 单调不降"**：短期涨是正常抖动，只有单调不降 24 小时以上才算泄漏。用 PSS/memory.current 建监控。
- **"分配器决定了 free 的物理含义"**：glibc free 是逻辑归还，不是物理归还。想让 RSS 下来，要么 jemalloc，要么内存池，要么重启。
- **"cgroup 是嵌入式内存的第二道墙"**：一个进程失控不能带走整机。**MemoryMax + oom_score_adj + Restart** 三件套是标配。
- **"能定长就别随机长"**：碎片化的根因是随机大小。会话、事件、包这类高频对象一律走内存池，一劳永逸。

### 10.4 内存排查速查

| 场景 | 首选工具 | 关键命令 |
|------|----------|----------|
| 谁在涨？ | smem / pmap | `smem -t -k -P gateway` |
| 段级涨？ | maps / pmap -X | `wc -l /proc/pid/maps` |
| 泄漏定位 | heaptrack | `heaptrack ./app`（开发机） |
| 上板采样 | LD_PRELOAD hook | 自研 memtrace |
| 碎片 | mallinfo / jemalloc | `MALLOC_CONF=stats_print:true` |
| cgroup 限 | memory.current/max | `cat /sys/fs/cgroup/.../memory.*` |
| OOM 现场 | dmesg | `dmesg -T \| grep -i oom` |
| 分配器换装 | LD_PRELOAD | `LD_PRELOAD=libjemalloc.so.2` |
| 栈使用 | /proc/pid/task | `grep VmStk .../status` |
| 报警指标 | PSS + memory.current | 阈值：MemoryMax × 80% |

**一句话建议**：**上线前先把 `MemoryMax` + `oom_score_adj` + `PSS 监控`三件套配齐；再谈"要不要换 jemalloc"。**
