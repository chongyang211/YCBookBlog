## 1. 案例引入

### 1.1 一次多线程翻车

一个手持终端项目，采集心率、血氧、体温三路传感器数据，回调到 Qt GUI 显示。老代码是单线程轮询，每 100ms 循环读一次，用户操作时按钮点击有 300~500ms 的卡顿。

新同学接手后决定"上多线程"：

```cpp
// 新同学的第一版
class SensorHub {
public:
    void start() {
        std::thread([this] { readHeart(); }).detach();
        std::thread([this] { readSpo2();  }).detach();
        std::thread([this] { readTemp();  }).detach();
    }

    void readHeart() {
        while (running_) {
            auto v = hw_->readHeart();
            data_.heart = v;                          // ← 未加锁
            emit heartChanged(v);                     // ← 跨线程发信号
        }
    }
    // spo2/temp 类似
private:
    struct Data { int heart, spo2, temp; } data_;
    Hardware* hw_;
    bool running_ = true;
};
```

上板测试后现场炸锅：

- **现象 1**：Qt 界面偶发闪退，日志一片 `QObject::connect: Cannot queue arguments`。
- **现象 2**：3 个线程 CPU 加起来 240%，把整个 4 核 A53 都占满，触摸响应更慢了。
- **现象 3**：数据偶发跳变，血氧 98% 突然显示 328%——跨线程读写 int 没做同步。
- **现象 4**：跑 4 小时后进程被 OOM killed，`top` 显示 RSS 从 30 MB 涨到 800 MB。

新同学的结论："线程根本不能用，还是回到单线程轮询吧！"

### 1.2 顺藤摸到根因

翻这个"翻车"，藏着五个概念性错误：

- **假设 1**：为什么开线程更慢？，因为 while(1) 死循环空转，没有任何 sleep 或事件等待，三个核瞬间跑满。→ 引出 **忙等 vs 事件驱动**。
- **假设 2**：为什么 GUI 会闪退？，因为 `emit` 跨线程发信号，参数类型没注册到 Qt 元系统，`QueuedConnection` 无法序列化。→ 引出 **跨线程数据交付**。
- **假设 3**：为什么数值会跳变？，因为对 int 的读写不是原子的（尤其 32 位 ARM 上），一半写完另一半在读，读到"新旧混合"值。→ 引出 **原子操作与 memory order**。
- **假设 4**：为什么内存会涨到 OOM？，因为 detach 的线程一直分配临时对象没有回收，泄漏被并发放大。→ 引出 **线程生命周期管理**。
- **假设 5**：为什么线程创建这么"轻"却拖垮系统？，因为线程创建代价是 8~16 KB 栈 + 上下文切换成本，三个空转线程等于三个核在做无用功。→ 引出 **线程池、协程、reactor 三种降耗方式**。

```
① 为什么"更多线程"不代表"更快"？        → 第 2 章 + 第 3 章
② mutex 到底该怎么用？粒度怎么定？        → 第 4 章
③ 无锁队列真的比锁快吗？                  → 第 5 章
④ 协程能替代线程吗？                      → 第 6 章
⑤ 高并发时到底该用什么模型？              → 第 7 章 + 第 8 章
```

## 2. 并发模型全景

### 2.1 三种并发模型

现代应用的并发模型可以归为三类：

```
┌─────────────────────────────────────────────────────────────────────┐
│                       三种并发模型                                    │
│                                                                       │
│  ┌────────────────┐  ┌─────────────────┐  ┌─────────────────────┐  │
│  │ 1.线程模型      │  │ 2.事件驱动模型   │  │ 3.协程模型            │  │
│  │  一任务一线程   │  │  单线程+eventloop│  │  用户态调度+挂起恢复    │  │
│  └────────────────┘  └─────────────────┘  └─────────────────────┘  │
│                                                                       │
│  代表：pthread、    代表：libuv、       代表：Go、C++20 coroutine    │
│       thread_pool          reactor              Boost.Asio            │
│                                                                       │
│  优点：思维直观、   优点：无锁、内存省、  优点：像同步代码写异步、       │
│       内核调度            单核也高并发         无 callback 地狱         │
│                                                                       │
│  缺点：切换开销、   缺点：callback 地狱、 缺点：调试复杂、栈管理复杂     │
│       锁竞争              CPU 密集会阻塞       编译器/库要求高           │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 嵌入式的取舍

**疑惑**：嵌入式设备 CPU 和内存都紧张，到底选哪种？

**论证**：先明确两条：**嵌入式很少纯 CPU 密集**（真做 CPU 密集会上 DSP 或专用芯片），**嵌入式很多是 IO 密集**（读传感器、收网络包、写 Flash）。IO 密集意味着"等 IO"是主线，"算得多快"次要。

因此嵌入式的组合选择：

| 场景 | 推荐模型 | 原因 |
|---|---|---|
| 传感器采集（3~10 路） | 线程池（小池 2~4 个线程） | 简单、够用 |
| 网络服务（100~1000 连接） | reactor 单线程 或 主从 reactor | 内存省、无锁 |
| 内部消息投递 | 线程池 + 无锁队列 | 兼顾吞吐与低延迟 |
| 大量并发 IO（>1k） | 协程 + reactor | 写起来像同步 |
| GUI | 单线程 event loop（Qt 强制） | Qt 主线程必须处理 UI |

**结论**：**嵌入式不是"线程越多越好"，而是"够用就好，能省则省"**。第 1 章的翻车根源就是"更多线程 = 更快"的错觉。


## 3. 线程池的正确姿势

### 3.1 为什么要线程池

**疑惑**：每次任务都 `std::thread(...)` 不就好了？

**论证**：每次创建线程的代价：
1. **内核态创建 task_struct + 内核栈**（8~16 KB）
2. **用户态分配栈**（默认 8 MB，可调）
3. **上下文切换**（保存/恢复寄存器）

嵌入式 4 核 A53 上，创建 + 销毁一次线程约 100~500 μs。**这个时间可以处理几千个短任务**。

线程池的核心思想是**"复用"**：预先创建 N 个线程，用任务队列分发。

```
┌────────────────────────────────────────────────────────┐
│  ThreadPool                                             │
│                                                         │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐         │
│  │ Worker 1 │    │ Worker 2 │    │ Worker N │         │
│  └────┬─────┘    └────┬─────┘    └────┬─────┘         │
│       │               │                │                │
│       └───────────────┴────────────────┘                │
│                       ▼                                 │
│           ┌─────────────────────┐                       │
│           │  TaskQueue (锁保护)  │                       │
│           └──────────┬──────────┘                       │
│                      │                                  │
│  submit(task) ───────┘                                  │
└────────────────────────────────────────────────────────┘
```

一个最小的 C++17 线程池骨架（生产级要在此基础上加优雅退出、超时、优先级）：

```cpp
class ThreadPool {
public:
    explicit ThreadPool(size_t n) {
        for (size_t i = 0; i < n; ++i) {
            workers_.emplace_back([this] { workerLoop(); });
        }
    }
    ~ThreadPool() { stop(); }

    template <class F>
    void submit(F&& task) {
        {
            std::lock_guard<std::mutex> lk(mu_);
            queue_.emplace(std::forward<F>(task));
        }
        cv_.notify_one();                        // ← 唤醒一个 worker
    }

    void stop() {
        {
            std::lock_guard<std::mutex> lk(mu_);
            running_ = false;
        }
        cv_.notify_all();
        for (auto& t : workers_) if (t.joinable()) t.join();
    }

private:
    void workerLoop() {
        for (;;) {
            std::function<void()> task;
            {
                std::unique_lock<std::mutex> lk(mu_);
                cv_.wait(lk, [this] { return !running_ || !queue_.empty(); });
                if (!running_ && queue_.empty()) return;
                task = std::move(queue_.front());
                queue_.pop();
            }
            try { task(); }
            catch (const std::exception& e) { /* log */ }
        }
    }

    std::vector<std::thread>            workers_;
    std::queue<std::function<void()>>   queue_;
    std::mutex                          mu_;
    std::condition_variable             cv_;
    bool                                running_ = true;
};
```

**关键点**：`cv_.wait` 让空闲 worker 挂起不占 CPU，`notify_one` 精准唤醒一个（不是 `notify_all` 惊群）。

### 3.2 线程数怎么定

**疑惑**：`std::thread::hardware_concurrency()` 返回 4，我就开 4 个线程？

**论证**：分两种任务：

**CPU 密集型**：线程数 ≈ 核数（多了徒增切换开销）

**IO 密集型**：线程数 = 核数 × (1 + 等待时间 / 计算时间)

举例：如果一个任务 CPU 算 20 ms、等 IO 80 ms，比值 4，则线程数 = 核数 × 5 = 20。

**嵌入式实用公式**：

| 任务性质 | 线程数建议 |
|---|---|
| 纯 CPU（如图像 filter） | 核数（或核数-1 留给主线程） |
| 纯 IO（如 socket 读写） | 用 reactor，别用线程池 |
| 混合（如 HTTP 服务） | 核数 × 2~4 |
| 后台维护（如日志刷盘） | 1~2 个专用线程 |

**踩坑**：某项目 4 核开了 32 线程做 IO，`vmstat` 显示 `cs`（上下文切换）从 1k/s 涨到 50k/s，CPU 30% 都花在切换上，性能反而下降。

### 3.3 任务队列的类型

**疑惑**：`std::queue + mutex` 就够了吗？

**论证**：随着并发压力上升，任务队列本身会成为瓶颈。可选：

| 队列类型 | 特点 | 场景 |
|---|---|---|
| `std::queue + mutex` | 简单、稳定 | 中低并发（<10k QPS） |
| 无锁 MPMC 队列（moodycamel） | 高吞吐、低延迟 | 高并发生产者/消费者 |
| SPSC ring buffer | 极致低延迟 | 单生产者单消费者（如日志） |
| 优先级队列 | 支持任务优先级 | 有实时性要求 |

**结论**：**队列选择跟着并发规模走**，不要一上来就上无锁——无锁调试极难，只在真的需要时用。


## 4. 同步原语

### 4.1 mutex的性能陷阱

**疑惑**：`std::mutex` 用得对不对？

**论证**：mutex 的性能陷阱不在 mutex 本身，而在**锁粒度**和**持有时间**：

```cpp
// ❌ 大锁粒度：整个函数锁住
void updateAll(const Data& d) {
    std::lock_guard<std::mutex> lk(mu_);
    heavyCompute(d);              // ← 100 ms 在锁里
    map_[d.key] = d;              // ← 真正要保护的只有这一行
    notifyObservers(d);           // ← 又 50 ms 在锁里
}

// ✅ 小锁粒度：只锁真正需要的
void updateAll(const Data& d) {
    auto result = heavyCompute(d);           // ← 锁外
    {
        std::lock_guard<std::mutex> lk(mu_);
        map_[d.key] = std::move(result);     // ← 锁内极短
    }
    notifyObservers(d);                      // ← 锁外
}
```

**mutex 的其他陷阱**：
1. **锁保护的是数据，不是代码**。要问自己："我在保护什么变量？"
2. **锁的顺序要一致**。多个 mutex 时，A→B 加锁再 B→A 就是死锁。
3. **锁里不要调用别人的回调**。回调可能反过来加锁，导致 reentrant。

**结论**：mutex 是"最小限度使用"的工具。**能不用则不用，能锁小则不锁大，能锁短则不锁长**。

### 4.2 读写锁的适用场景

**疑惑**：`shared_mutex` 是不是永远比 `mutex` 快？

**论证**：**不是**。读写锁有额外的簿记开销：需要维护读者计数、写者优先策略等。当"读远远多于写、且读时间较长"时才有优势。

**经验阈值**：

| 场景 | 建议 |
|---|---|
| 读:写 < 5:1 | 用 mutex（简单） |
| 读:写 > 100:1 且读操作 > 1μs | 用 shared_mutex |
| 只读几乎不变 | 用 immutable + shared_ptr 原子替换（拷贝写） |

**免锁读的极简技巧**（Copy-On-Write）：

```cpp
class ConfigCache {
public:
    std::shared_ptr<const Config> get() {
        return std::atomic_load(&cfg_);           // 原子读，无锁
    }
    void update(Config newCfg) {
        auto p = std::make_shared<Config>(std::move(newCfg));
        std::atomic_store(&cfg_, p);              // 原子写替换
    }
private:
    std::shared_ptr<const Config> cfg_;
};
```

**关键**：读方永远拿到一个不变的 snapshot，没有锁；写方替换指针，代价是拷贝一次。

### 4.3 条件变量的三段式

**疑惑**：`cv.wait(lk)` 我总记不清参数。

**论证**：条件变量的**正确三段式**：

```cpp
std::unique_lock<std::mutex> lk(mu_);
cv_.wait(lk, [this] { return predicate_; });     // ← 关键：带 predicate
```

**为什么必须带 predicate**（虚假唤醒防御）：

```cpp
// ❌ 错误：可能被虚假唤醒
lk.lock();
if (!ready_) cv_.wait(lk);                       // ← 醒来时 ready_ 可能还是 false
consume();                                        //   → 崩溃

// ✅ 正确：predicate 循环检查
cv_.wait(lk, [this] { return ready_; });
consume();
```

`cv.wait(lk, pred)` 展开等价于：

```cpp
while (!pred()) cv.wait(lk);
```

**通知方**的写法：

```cpp
{
    std::lock_guard<std::mutex> lk(mu_);
    ready_ = true;                                // ← 必须在锁内改
}
cv_.notify_one();                                 // ← 通知可以在锁外
```

**notify_one vs notify_all**：
- 只有一个 worker 能干活 → `notify_one`（省惊群）
- 状态变化让所有 worker 重新评估 → `notify_all`

### 4.4 原子操作与memory_order

**疑惑**：`std::atomic<int>` 和 `volatile int` 有什么区别？

**论证**：
- `volatile` 只是告诉编译器"这个变量不要优化掉读写"，**不保证原子性、也不保证内存顺序**。
- `std::atomic<T>` 是**真的原子读写 + 可控内存顺序**。

**memory_order 六个值**，实用只需三个：

| 值 | 含义 | 用途 |
|---|---|---|
| `relaxed` | 只保证原子性，不管顺序 | 计数器 |
| `acquire/release` | 建立同步关系（配对使用） | 无锁数据结构、发布/订阅 |
| `seq_cst`（默认） | 全局顺序一致，最强也最慢 | 不确定就用它 |

**典型模式：发布数据**

```cpp
// 生产者
data_.value = 42;                                       // 1. 写数据
ready_.store(true, std::memory_order_release);          // 2. 发布 ready

// 消费者
if (ready_.load(std::memory_order_acquire)) {           // 3. 看到 ready
    int v = data_.value;                                // 4. 一定能看到 42
}
```

**保证**：`release`（步 2）之前的所有写，对 `acquire`（步 3）之后的读一定可见。**这是无锁编程的根基**。

**结论**：能用 `mutex` 就不用 `atomic`；用 `atomic` 尽量默认 `seq_cst`；只有性能测出瓶颈时才降到 `acquire/release`；`relaxed` 只用在真的不需要同步的地方（如统计计数）。


## 5. 无锁编程

### 5.1 无锁队列的本质

**疑惑**：无锁真的比有锁快吗？

**论证**：无锁不等于"没有等待"，是"用 CAS 循环代替阻塞"。收益取决于**竞争强度**：

```
低竞争   ： mutex ≈ 无锁（都不用真的阻塞或重试）
中竞争   ： 无锁略胜
高竞争   ： 无锁大胜（省了系统调用和唤醒开销）
超高竞争 ： 无锁反而更差（CAS 反复失败重试）
```

**推荐做法**：
1. 先用 mutex，测出真的是瓶颈再上无锁
2. 别自己写，用成熟库（`moodycamel::ConcurrentQueue`、`boost::lockfree`）
3. 单生产者单消费者才自己写（相对简单）

### 5.2 SPSC队列的实现要点

一个生产者一个消费者的环形队列（无锁），是**最常见的自定义并发结构**：

```cpp
template <typename T, size_t N>
class SpscRing {
    static_assert((N & (N - 1)) == 0, "N must be power of 2");
public:
    bool push(T v) {
        auto w = write_.load(std::memory_order_relaxed);
        auto next = (w + 1) & (N - 1);
        if (next == read_.load(std::memory_order_acquire)) return false;  // 满
        buf_[w] = std::move(v);
        write_.store(next, std::memory_order_release);                    // 发布
        return true;
    }

    bool pop(T& out) {
        auto r = read_.load(std::memory_order_relaxed);
        if (r == write_.load(std::memory_order_acquire)) return false;    // 空
        out = std::move(buf_[r]);
        read_.store((r + 1) & (N - 1), std::memory_order_release);
        return true;
    }

private:
    alignas(64) std::atomic<size_t> write_{0};              // ← 独占 cache line
    alignas(64) std::atomic<size_t> read_{0};               //   避免伪共享
    T buf_[N];
};
```

**关键点**：
1. **N 为 2 的幂** → `& (N-1)` 代替 `% N`，快很多
2. **`alignas(64)`** → 读写指针放在不同 cache line，避免伪共享
3. **一端 acquire，另一端 release** → 建立数据可见性同步

**性能对比**（100 万次 push/pop，A53 1.2GHz）：

| 实现 | 耗时 |
|---|---|
| `queue + mutex` | 180 ms |
| SPSC ring | 25 ms |

**结论**：**SPSC 场景（如日志、埋点）用 ring buffer**。多对多场景请用成熟无锁库，不要自造。


## 6. 协程的定位

### 6.1 协程为什么复兴

**疑惑**：协程 90 年代就有，为什么最近才火？

**论证**：
1. **异步编程的痛**：回调地狱（callback hell），错误传播、上下文携带都非常麻烦。
2. **线程太贵**：一个线程 1~8 MB 栈，10 万连接需要 100 GB+ 内存。
3. **协程的甜蜜点**：**用同步的写法做异步的事**，栈仅几 KB。

对比三种写法：

```cpp
// 1. 同步阻塞（简单但线程贵）
Response r = http.get(url);           // 阻塞
process(r);

// 2. 异步回调（省线程但难写）
http.getAsync(url, [](Response r) {
    process(r);                       // ← 回调地狱
});

// 3. 协程（既省又好写）
Response r = co_await http.get(url);  // 挂起当前协程，不阻塞线程
process(r);
```

### 6.2 有栈vs无栈

协程有两种实现路线：

| 类型 | 代表 | 特点 | 缺点 |
|---|---|---|---|
| 有栈协程（stackful） | Boost.Context、libco、golang | 每个协程有独立栈，可在任意深度挂起 | 栈内存分配复杂 |
| 无栈协程（stackless） | C++20、Rust、Python asyncio | 编译器生成状态机，栈开销极小 | 只能在 `co_await` 点挂起 |

**嵌入式选择**：
- **想最快看到效果 + 兼容老编译器** → Boost.Context / libco（有栈）
- **上 C++20 + 追求性能** → C++20 协程（无栈）

### 6.3 C++20协程要点

C++20 协程的"三件套关键字"：

```cpp
Task<int> fetchData(int id) {
    auto conn  = co_await connect(host);        // 挂起，等 IO 完成
    auto data  = co_await conn.read(id);        // 再挂起
    co_return data.size();                      // 返回值
}
```

**Task<T> 的编译器约定**：
- 内部要有 `promise_type`（编译器用来管理协程状态）
- `promise_type` 要提供 `initial_suspend / final_suspend / get_return_object / return_value / unhandled_exception`
- 挂起对象要提供 `await_ready / await_suspend / await_resume`

**协程的运行时选择**：C++20 只提供语言机制，**调度器要自己接**。嵌入式常用两种：
1. **接到 reactor 的 event loop 上**（Boost.Asio 已内置支持）
2. **接到线程池上**

**结论**：C++20 协程语言层完备，但**运行时生态还年轻**。嵌入式生产环境推荐 **Boost.Asio 或 libco** 起步，等生态稳定再迁到 C++20。


## 7. 事件循环与reactor

### 7.1 单reactor的结构

**疑惑**：一个线程能处理几千个连接？

**论证**：靠 `epoll_wait` 一次拿一批就绪的 fd，逐个分发处理。**只要每个处理够短，单核吞吐可以到几十万 QPS**。

```
┌────────────────────────────────────────────────────────┐
│                单 reactor 线程                          │
│                                                         │
│   ┌────────────────────┐                                │
│   │ epoll_wait()       │──就绪 fd 列表──┐               │
│   └────────────────────┘                │               │
│           ▲                              ▼               │
│           │            ┌─────────────────────────────┐  │
│           │            │  分发器（EventLoop）         │  │
│           │            │  for fd in ready: handle()  │  │
│           │            └─────────────────────────────┘  │
│           │                              │               │
│           │            ┌──────┬──────┬───┴──────┐       │
│           │            ▼      ▼      ▼          ▼       │
│           │        accept  read   write     timer       │
│           │            │      │      │          │       │
│           └────────────┴──────┴──────┴──────────┘       │
└────────────────────────────────────────────────────────┘
```

**代码骨架**：

```cpp
int epfd = epoll_create1(EPOLL_CLOEXEC);
epoll_event evs[64];

for (;;) {
    int n = epoll_wait(epfd, evs, 64, timeout_ms);
    for (int i = 0; i < n; ++i) {
        auto* h = static_cast<Handler*>(evs[i].data.ptr);
        h->handle(evs[i].events);         // ← 分发
    }
    runExpiredTimers();                   // ← 定时器
}
```

### 7.2 主从reactor

**疑惑**：单 reactor 遇到 CPU 密集怎么办？

**论证**：单 reactor 的死穴是"某个 handler 阻塞就全线卡住"。主从 reactor 把 IO 和业务分开：

```
┌──────────────────────────────────────────────────────┐
│  主 Reactor：只做 accept                                │
│      │                                                 │
│      └── 新连接 ──► 从 Reactor 池（N 个线程）           │
│                          │                             │
│                          ├─ 从 Reactor 1（epoll IO）    │
│                          ├─ 从 Reactor 2（epoll IO）    │
│                          └─ 从 Reactor N（epoll IO）    │
│                          │                             │
│                          └── CPU 密集任务 ──► 工作线程池 │
└──────────────────────────────────────────────────────┘
```

**Reactor 之外还要有**：
1. **工作线程池**：处理长任务（协议解析、DB 查询）
2. **定时器堆**：小根堆或时间轮

**libuv、muduo、Boost.Asio 都是这个架构**。嵌入式直接用 muduo（C++）或 Asio 的 `strand`。

**结论**：**IO 由 reactor 收，业务由线程池干**，两者用无锁队列桥接。这是高并发嵌入式服务的黄金架构。


## 8. 选型决策树

### 8.1 五个维度

1. **任务性质**：CPU 密集 / IO 密集 / 混合
2. **并发规模**：<100 / 100~1k / 1k~10k / >10k
3. **延迟要求**：ms 级 / us 级 / ns 级
4. **代码复杂度可接受**：接受回调 / 只想同步写法
5. **编译器与库支持**：老编译器 / C++20 / Boost

### 8.2 一张图选完

```
START：新增并发需求
   │
   ├── 是 GUI 更新？ ── 是 ──► 主线程 event loop（Qt）
   │        │
   │        否
   │        ▼
   ├── 并发数 < 100？── 是 ──► 线程池 2~4 线程 + mutex
   │        │
   │        否
   │        ▼
   ├── IO 密集且并发 > 1k？── 是 ──► reactor + 工作线程池
   │        │                                    │
   │        否                                   ▼
   │        │                            用 Boost.Asio 或 muduo
   │        ▼
   ├── CPU 密集 > 核数？── 是 ──► 线程池 = 核数 + 任务队列
   │        │
   │        否
   │        ▼
   ├── 写起来像同步很重要？── 是 ──► 协程（C++20 或 Asio）
   │        │
   │        否
   │        ▼
   └── 默认：线程池 + std::mutex
```

### 8.3 常见误用

**误用 1**：**忙等空转**

```cpp
while (!ready_) {}                                // ❌ 100% CPU
while (!ready_) std::this_thread::sleep_for(1ms);// ⚠ 好点但仍轮询
cv_.wait(lk, [this]{ return ready_; });          // ✅
```

**误用 2**：**detach 线程做长任务**

```cpp
std::thread([this]{ heavyWork(); }).detach();     // ❌ 无法追踪、无法优雅退出
// ✅ 交给线程池
pool_.submit([this]{ heavyWork(); });
```

**误用 3**：**跨线程读写普通变量**

```cpp
bool running_ = true;                              // ❌ 32位ARM上非原子
std::atomic<bool> running_{true};                  // ✅
```

**误用 4**：**锁里发信号槽**

```cpp
{
    std::lock_guard<std::mutex> lk(mu_);
    data_ = v;
    emit changed(v);                              // ❌ 可能重入锁
}
// ✅ 锁外发
Data snap;
{
    std::lock_guard<std::mutex> lk(mu_);
    data_ = v;
    snap = v;
}
emit changed(snap);
```


## 9. 可靠性与调试

### 9.1 死锁的排查

**征兆**：进程"僵住"，CPU 0%，pstack 显示多个线程都停在 `pthread_mutex_lock`。

**排查步骤**：

```bash
# 1. 附上 gdb 看栈
gdb -p <pid>
(gdb) thread apply all bt
# 找到停在 __lll_lock_wait 的线程

# 2. 看它在等哪把锁
(gdb) thread 3
(gdb) frame 5
(gdb) print *mutex
# 看 __owner 字段是哪个 tid

# 3. 顺藤找过去
(gdb) thread <owner_tid>
(gdb) bt
# 看它又在等哪把锁 → 形成环 → 死锁
```

**预防手段**：
- **全局锁顺序**：所有代码都按同一顺序加锁（比如按地址顺序）
- **`std::lock(m1, m2)`**：一次锁多把（内部保证顺序）
- **超时锁**：`try_lock_for(100ms)`，超时报告

### 9.2 竞态的排查

**征兆**：偶发数据错乱、崩溃，日志无规律。

**利器**：**ThreadSanitizer**（TSan）

```cmake
target_compile_options(app PRIVATE -fsanitize=thread -g)
target_link_options(app PRIVATE -fsanitize=thread)
```

TSan 会在运行时监控**每个内存位置的访问历史**，发现"多个线程访问、没有 happens-before 关系"就报告。

**输出示例**：

```
WARNING: ThreadSanitizer: data race
  Read of size 4 at 0x0000012c by thread T3:
    #0 SensorHub::readHeart() sensor.cpp:14
  Previous write of size 4 by thread T2:
    #0 SensorHub::readHeart() sensor.cpp:14
```

一目了然：line 14 的 `data_.heart` 被多线程无同步访问。

**嵌入式的坑**：TSan 内存开销大（RSS ×5~10），只在开发机运行，不上板。


## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到第 1 章"三线程读传感器"的翻车，五个问题——五处修复：

| 现象 | 根因 | 修复 | 章节 |
|---|---|---|---|
| CPU 240% | while(1) 忙等 | 用 poll/select 阻塞等待硬件事件 | §2.2 §4.3 |
| Qt 闪退 | 跨线程 emit 未注册元类型 | `qRegisterMetaType<Data>()`，或队列 + 主线程转发 | §8.3 误用4 |
| 数值跳变 | 普通 int 跨线程读写 | 改 `std::atomic<int>` 或加 mutex | §4.4 |
| 内存涨到 800 MB | detach 线程无生命周期管理 | 换成线程池，或 `jthread` 管理 | §3.1 §8.3 误用2 |
| 触摸响应更慢 | 三线程占满 4 核 | 改单线程 reactor，各传感器 fd 加进 epoll | §7 |

**改造后的架构**：

```
┌───────────────────────────────────────────────────┐
│  主线程（Qt EventLoop）                             │
│    ├─ 处理 UI 事件                                  │
│    └─ 接收 queued signal，刷新界面                  │
│                                                     │
│  IO 线程（1 个 reactor）                            │
│    ├─ epoll 监听心率/血氧/体温 3 个 fd              │
│    └─ 数据到达 → 无锁队列 → 通知主线程              │
└───────────────────────────────────────────────────┘
```

**从 3 线程 + 240% CPU 变成 2 线程 + 15% CPU，触摸响应从 500ms 降到 30ms。**

### 10.2 一次任务的一生

一个"用户点按钮 → 采一次心率 → 显示到 UI"的完整链路：

```
用户点击按钮
    │
    ▼ 【1. Qt 主线程】
Button::clicked → 发 signal
    │
    ▼ 【2. 通过 QueuedConnection 投递到 IO 线程】§4.3 条件变量类似机制
    │      Qt 内部：post event to IO thread's queue
    │
    ▼ 【3. IO 线程 epoll_wait 醒来】§7.1
epoll_wait 返回 → 分发到 handler
    │
    ▼ 【4. 发起硬件读取】
write(hw_fd, "READ_HEART") → 挂进 epoll 等结果
    │      （不用等，直接返回 epoll_wait 继续等下一个事件）
    │
    ▼ 【5. 硬件 100ms 后返回数据】
epoll_wait 醒来 → read(hw_fd, buf, ...)
    │
    ▼ 【6. 数据通过 std::atomic + notify 交付主线程】§4.4
data_.store(heart, release);
QMetaObject::invokeMethod(ui, &UI::update, Qt::QueuedConnection);
    │
    ▼ 【7. 主线程 event loop 拾起】
UI::update(v) → label->setText(...)
```

**总耗时 ≈ 100 ms（几乎全是硬件耗时），CPU 占用 <5%**。这就是"IO 密集 + reactor + 主线程 UI"的经典组合。

### 10.3 设计哲学回扣

**哲学 1：并发不是加线程，是选择"等的方式"**

四种等的方式：
- **忙等**：耗 CPU（除非硬实时才用）
- **休眠等**：`sleep()`（响应慢）
- **锁等**：`mutex.lock()`（内核挂起）
- **事件等**：`epoll_wait/cv.wait`（挂起且可精准唤醒）

**"选对等的方式，比选对线程数更重要"**。第 1 章的翻车全在于错选了"忙等"。

**哲学 2：数据的生命周期决定同步方式**

- 短生命周期、单线程使用 → 栈变量、无需同步
- 跨线程但很快消费 → 消息传递（队列）
- 长期共享、频繁读写 → mutex / atomic
- 长期共享、读多写少 → COW / shared_ptr 原子替换

**结论**：**先想数据怎么流，再决定同步用什么**。

**哲学 3：小锁粒度胜过大锁**

用户经常担心"锁多了会不会死锁"，其实更常见的是"一把大锁把并发变串行"。**锁的正确颗粒度是"够保护数据一致性即可"**，不是"图省事一把锁到底"。

**哲学 4：无锁不是目标，性能达标是目标**

有的团队盲目追求"无锁架构"，结果代码难改、bug 难查、性能提升 5%。**"先能跑对，再谈跑快"**——mutex 能扛住的，就别上无锁。

### 10.4 速查手册

**并发决策口诀**：

```
先问 IO 还是 CPU
IO 密集用 reactor，CPU 密集用线程池
锁能小别锁大，锁能短别锁长
notify 精准唤醒，wait 一定带 predicate
跨线程数据只走 atomic 或队列
```
