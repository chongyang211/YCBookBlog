## 1. 案例引入

### 1.1 一次OTA后集体挂载失败

一款医疗手持设备，OTA 升级到 2.1.0 版本后，运维接到 500+ 台设备告警：**开机进度条卡在 30%**，串口日志显示：

```
[   6.331] EXT4-fs (mmcblk0p4): couldn't mount as ext3 due to feature
[   6.334] EXT4-fs (mmcblk0p4): error loading journal
[   6.340] Buffer I/O error on device mmcblk0p4, logical block 32
[   6.345] mount: /data: can't read superblock on /dev/mmcblk0p4
[  10.221] systemd[1]: Failed to mount /data
[  10.223] systemd[1]: local-fs.target: Dependency failed
[  10.228] systemd[1]: Emergency mode enabled
```

设备直接进了 emergency shell，用户看不到界面。

拉出一台设备 eMMC 到实验台上分析：

```bash
# fsck 报告
$ e2fsck -f /dev/mmcblk0p4
Superblock has invalid journal (inode 8).
Clear journal? no
The journal superblock is corrupt.
Journal block checksum error
...
```

事后回看，这次 OTA 只是把应用二进制换了新版本，**没有动 /data 分区**。为什么 /data 会坏？

翻代码看到 OTA 脚本在重启前做了这样一步：

```bash
# ota_finish.sh
sync
umount /data          # ← 有时返回 non-zero，忽略了
reboot -f             # ← 直接强制重启
```

以及应用里的日志组件：

```cpp
// AsyncLogger 里用 mmap 写日志文件
void*  buf_ = mmap(nullptr, LOG_SIZE, PROT_WRITE, MAP_SHARED, fd_, 0);
memcpy(buf_ + offset, line.data(), line.size());
offset += line.size();
// 没 msync
```

短短几行，藏着 5 个文件系统层面的坑。

### 1.2 顺藤摸到根因

- **假设 1**：为什么 `umount /data` 失败？，因为 AsyncLogger 里还有 mmap 映射着 /data 上的文件，进程没退出，umount 报 `busy`，脚本"忽略了"。→ 引出 **umount 的陷阱**。
- **假设 2**：为什么 `sync` 没救回来？，`sync` 只 flush page cache，**不 flush mmap 的脏页**——mmap 需要 `msync`。→ 引出 **mmap 与 fsync 关系**。
- **假设 3**：为什么 journal 会坏？，ext4 默认 `data=ordered`，元数据先写 journal，掉电（这里是"强制 reboot"）时 journal 可能只写了一半。→ 引出 **journal 三种模式**。
- **假设 4**：为什么不是自动恢复？，e2fsck 默认在 emergency shell 下要人工介入，systemd 见到挂载失败就停在 emergency。→ 引出 **fstab 的 passno**。
- **假设 5**：为什么不选一个天然抗掉电的文件系统？，因为团队从 x86 服务器思维带来了 ext4 默认配置。**嵌入式该用 f2fs 或加强 ext4 mount option**。→ 引出 **选型**。

```
① ext4/f2fs/UBIFS/squashfs 各自什么场景？→ 第 2 章
② ext4 挂载参数怎么调？                    → 第 3 章
③ 裸 NAND 上的 UBIFS 怎么用？             → 第 4 章
④ 只读根 + overlayfs 是什么套路？          → 第 5、6 章
⑤ fsync/msync 的坑在哪？                  → 第 9 章
```

### 1.3 我们要回答什么

上一篇讲存储介质与分区，这一篇讲**文件系统本身的选型和调优**。核心问题是：**给定介质与分区，怎么配置文件系统让它扛得住五年产品生命周期**。

## 2. 文件系统全景

### 2.1 五种典型文件系统

```
┌────────────────────────────────────────────────────────────────┐
│              嵌入式常见文件系统                                    │
│                                                                  │
│  ext4       ─ 通用块设备（eMMC/SD/UFS），成熟，有 journal        │
│  f2fs       ─ 块设备但为 Flash 优化，log-structured，写放大低    │
│  UBIFS      ─ 裸 NAND 专用，工作在 UBI 之上                     │
│  squashfs   ─ 只读、高压缩，rootfs / vendor 用                  │
│  overlayfs  ─ 叠加层，只读下 + 可写上                            │
│  tmpfs      ─ 内存文件系统，掉电即失                             │
│  ramdisk    ─ 内存块设备，可作为 initramfs                      │
└────────────────────────────────────────────────────────────────┘
```

**关键特性对照**：

| FS | 介质 | 掉电抗性 | 压缩 | 写放大 | 只读 |
|---|---|---|---|---|---|
| ext4 | 块设备 | journal | 无 | 中 | 可 |
| f2fs | 块设备 | COW | 无 | 低 | 可 |
| UBIFS | 裸 NAND | 强 | 有（lzo/zstd） | 由 UBI 管 | 可 |
| squashfs | 任意 | 天然不写 | 极强 | 0 | 强制 |
| overlayfs | 分层 | 依赖 upper | 无 | 依赖 upper | 混合 |
| tmpfs | 内存 | 无（掉电即失） | 无 | 无物理写 | 可 |

### 2.2 场景与文件系统的匹配

**典型嵌入式分区布局**：

```
┌──────────────────────────────────────────────────────┐
│ /boot        ext4 或 vfat  (只读大部分时间)             │
│ /            squashfs      (只读，只在 OTA 时替换)      │
│ /vendor      squashfs      (只读，出厂固化)             │
│ /etc         overlayfs     (下层只读默认，上层可写)     │
│ /data        ext4 或 f2fs  (可写主战场)                │
│ /var/log     ext4 或 f2fs  (独立分区，防日志爆盘)       │
│ /tmp         tmpfs         (临时文件，掉电即失)          │
│ /run         tmpfs         (运行时数据，PID 文件等)     │
└──────────────────────────────────────────────────────┘
```

**匹配原则**：**只读的用 squashfs、多写的用 f2fs、系统性用 ext4、临时用 tmpfs、裸 NAND 只能 UBIFS**。


## 3. ext4深度调优

### 3.1 挂载参数详解

**嵌入式常用挂载参数**：

```bash
mount -t ext4 -o noatime,nodiratime,errors=remount-ro,commit=30 \
    /dev/mmcblk0p4 /data
```

| 参数 | 作用 | 建议 |
|---|---|---|
| `noatime` | 不更新访问时间戳 | 一定要开（省写放大） |
| `nodiratime` | 不更新目录访问时间 | 一定要开 |
| `errors=remount-ro` | 出错时改只读，防止损坏扩大 | 一定要开 |
| `errors=panic` | 出错直接 kernel panic（配合看门狗） | 高可靠性场景 |
| `commit=N` | 每 N 秒同步一次 journal | 30~60s（默认 5s，嵌入式可以放宽） |
| `data=writeback` | 数据不受 journal 保护 | 只在允许丢内容的场景 |
| `barrier=0` | 关闭写屏障（更快但更危险） | 除非有 PLP，不建议关 |
| `discard` | 支持 TRIM | eMMC 5.0+ 且驱动支持 |

**fstab 示例**：

```
/dev/mmcblk0p4  /data  ext4  noatime,nodiratime,errors=remount-ro,commit=30  0  2
```

**passno**：
- `0`：不 fsck
- `1`：根文件系统，最先 fsck
- `2`：其他文件系统，并行 fsck

### 3.2 journal的三种模式

```
data=journal    → 数据 + 元数据都进 journal    → 最安全，写放大 2x
data=ordered    → 只元数据进 journal，数据先落 → 默认，平衡
data=writeback  → 只元数据进 journal，数据顺序不保证 → 最快，掉电丢内容
```

**data=writeback 的风险**：掉电时可能出现"文件被 truncate 到 0 又写了新内容 → journal 记录了 truncate 但新内容还没落 → 掉电后 e2fsck 恢复 → 文件是 0 字节"。**对于日志这种"丢就丢"的数据可以用，配置文件绝不能用**。

**用 tune2fs 修改**：

```bash
tune2fs -o journal_data_writeback /dev/mmcblk0p4
# 或临时 mount 时 -o data=writeback
```

**关 journal**（极端场景，如日志分区）：

```bash
tune2fs -O ^has_journal /dev/mmcblk0p4
```

**代价**：掉电必损坏文件系统结构。**除非你能保证不会掉电或愿意每次开机 fsck**，否则不要关。

### 3.3 mkfs.ext4的关键参数

```bash
mkfs.ext4 -L data -m 0 -O ^has_journal -T largefile4 \
    -E stride=32,stripe-width=32 /dev/mmcblk0p4
```

| 参数 | 作用 |
|---|---|
| `-L` | label（fstab 里可用 `LABEL=xxx`） |
| `-m 0` | 预留给 root 的空间比例改 0（默认 5%，嵌入式浪费） |
| `-O ^has_journal` | 关 journal |
| `-T largefile` | inode 少（大文件多） |
| `-T news` | inode 多（小文件多） |
| `-E stride=N,stripe-width=M` | 对齐到底层块大小（eMMC 常见 128KB） |
| `-b 4096` | 块大小（默认 4KB） |

**stride 与 stripe-width**：这是与底层 Flash Erase Block 大小对齐的关键。eMMC 内部 EB 通常 512 KB，块大小 4 KB，stride = 512 KB / 4 KB = 128。**对齐后写放大能降 20~40%**。

**查询底层块**：

```bash
cat /sys/block/mmcblk0/queue/optimal_io_size
cat /sys/block/mmcblk0/queue/minimum_io_size
```


## 4. UBIFS实战

### 4.1 MTD-UBI-UBIFS三层

**裸 NAND 上的完整栈**：

```
┌──────────────────────────────────────┐
│ 应用层 open("/data/xx")               │
├──────────────────────────────────────┤
│ UBIFS：文件系统层                     │
│  ├─ 文件/目录/权限                     │
│  ├─ 压缩（lzo/zstd）                  │
│  └─ TNC 索引                           │
├──────────────────────────────────────┤
│ UBI：卷管理 + 逻辑擦除块              │
│  ├─ 磨损均衡                           │
│  ├─ 坏块管理                           │
│  └─ 逻辑→物理映射                      │
├──────────────────────────────────────┤
│ MTD：字符/块 抽象                     │
│  ├─ /dev/mtd0（原始）                  │
│  └─ read/write/erase 原语              │
├──────────────────────────────────────┤
│ 硬件：NAND Flash                       │
└──────────────────────────────────────┘
```

**每一层职责**：
- **MTD**：把 NAND 抽象为"擦除块 + 页"的接口
- **UBI**：在 MTD 上做磨损均衡、坏块管理、逻辑卷
- **UBIFS**：在 UBI 卷上实现文件系统

### 4.2 UBI卷的创建

**从零开始**（假设 `/dev/mtd0` 是要用的 NAND 分区）：

```bash
# 1. 擦除
ubiformat /dev/mtd0 -y

# 2. attach（把 MTD 变成 UBI 设备）
ubiattach -m 0 -d 0   # 得到 /dev/ubi0

# 3. 创建卷
ubimkvol /dev/ubi0 -N rootfs -s 128MiB
ubimkvol /dev/ubi0 -N data   -m           # -m = 用剩余全部

# 4. 挂载
mount -t ubifs ubi0:rootfs /mnt/rootfs
mount -t ubifs ubi0:data   /data
```

**关键概念**：
- **PEB（Physical Erase Block）**：物理擦除块（NAND 硬件的）
- **LEB（Logical Erase Block）**：逻辑擦除块（UBI 提供的抽象）
- **卷（Volume）**：由多个 LEB 组成，可以动态扩缩容

**fstab 里的写法**：

```
ubi0:data  /data  ubifs  defaults  0  0
```

**内核参数**（把某 MTD 分区自动 attach）：

```
ubi.mtd=0
```

### 4.3 压缩与坏块处理

**UBIFS 内置压缩**：mkfs 时选择压缩算法

```bash
mkfs.ubifs -x zstd -m 2048 -e 126976 -c 2000 -o ubifs.img \
    -r ./rootfs
```

| 参数 | 作用 |
|---|---|
| `-x` | 压缩算法：`none / lzo / zlib / zstd` |
| `-m` | min IO size（NAND page 大小） |
| `-e` | LEB size |
| `-c` | 最大 LEB 数（决定卷大小上限） |

**压缩算法对比**：

| 算法 | 压缩率 | 速度 | 场景 |
|---|---|---|---|
| none | 1x | 极快 | 已压缩的文件（jpg/mp4） |
| lzo | 2x | 快 | 默认 |
| zlib | 3x | 慢 | rootfs 需要极致小 |
| zstd | 2.5x | 较快 | 现代平衡选择 |

**坏块处理**：UBI 层自动做，UBIFS 只需要知道 LEB 计数。**产品设计要预留 3~5% 的容量给磨损均衡和坏块替换**。


## 5. squashfs只读根

### 5.1 为什么要只读根

**只读 rootfs 的三大好处**：

1. **不可写 = 不可损坏**（掉电、误操作都不影响）
2. **可校验**（配合 dm-verity 或 hash 表）
3. **压缩率高**（比 ext4 小 40~60%）

**典型场景**：手持设备、白电、车载中控。**服务器一般不这么做**（需要频繁改配置）。

### 5.2 mksquashfs的选择

```bash
mksquashfs ./rootfs rootfs.squashfs \
    -comp zstd -Xcompression-level 15 \
    -b 65536 \
    -no-recovery \
    -no-fragments
```

| 参数 | 作用 | 建议 |
|---|---|---|
| `-comp` | 压缩算法 | zstd（新内核）或 lz4（追求速度） |
| `-Xcompression-level` | 压缩等级 | zstd 15 或更高（离线打包不心疼时间） |
| `-b` | 块大小 | 64 KB~1 MB（越大压缩率越高，随机读越慢） |
| `-no-fragments` | 不合并小文件片段 | 单文件访问快 |
| `-not-compressed` | 已压缩后缀不再压 | `.jpg .mp4 .zip` 加入 |

**压缩算法性能**（rootfs 100 MB → 压后）：

| 算法 | 大小 | 解压速度 |
|---|---|---|
| gzip | 32 MB | 中等 |
| xz | 26 MB | 慢 |
| lz4 | 40 MB | 极快 |
| zstd | 30 MB | 快 |

**推荐**：**zstd**——嵌入式解压快、压缩率不差、内核 4.14+ 已支持。


## 6. overlayfs叠加层

### 6.1 只读加可写的组合

**需求**：rootfs 是 squashfs 只读，但用户/应用还是要能改配置。

**overlayfs 解法**：把可写层"盖"在只读层上。

```
用户看到的：/etc/config.json
     │
     ▼
  overlayfs
     ├── upperdir /overlay/upper/etc/config.json  (可写，如果有就用这个)
     └── lowerdir /rootfs/etc/config.json         (只读，兜底)
```

**语义**：
- 读：先看 upper，没有则看 lower
- 写：写到 upper（如果原来在 lower，先 copy-up 到 upper）
- 删：在 upper 建 whiteout（假装删除）

### 6.2 lower-upper-work三层

**挂载语法**：

```bash
mkdir -p /overlay/upper /overlay/work
mount -t overlay overlay \
    -o lowerdir=/rootfs,upperdir=/overlay/upper,workdir=/overlay/work \
    /merged
```

| 目录 | 存储位置 | 说明 |
|---|---|---|
| lowerdir | 只读介质（squashfs） | 基础层 |
| upperdir | 可写介质（ext4/f2fs） | 修改层 |
| workdir | 与 upperdir 同分区 | overlayfs 内部使用 |
| merged | 挂载点 | 用户看到的合并视图 |

**fstab 示例**：

```
overlay  /merged  overlay  lowerdir=/rootfs,upperdir=/overlay/upper,workdir=/overlay/work  0  0
```

### 6.3 OTA场景的层管理

**A/B 系统 + overlayfs 的组合威力**：

```
系统 A（squashfs 只读）─┐
                        │
系统 B（squashfs 只读）─┼─► lowerdir（活跃那一份）
                        │
数据层（ext4）─────────┴─► upperdir

OTA：更新非活跃系统 → 切换 lowerdir → overlay 自动指向新系统
     upperdir 中的用户配置全保留
```

**回滚**：切回旧系统很容易——lowerdir 换回来即可，upperdir 不动。

**升级前需要"清理"的场景**：如果新版本的 lower 里已经带了某个文件，但 upper 里有个"过时的旧版覆盖"，会出现"新系统被旧配置覆盖"。**OTA 后要标记 upper 里的哪些文件可以 evict**。


## 7. tmpfs与ramdisk

### 7.1 内存文件系统

**tmpfs**：文件放在内存里，掉电全丢，但速度极快、不磨损 Flash。

```bash
mount -t tmpfs -o size=64M,mode=1777 tmpfs /tmp
```

**关键参数**：

| 参数 | 作用 |
|---|---|
| `size=N` | 最大容量（不占用直到真的用） |
| `nr_inodes=N` | 最大 inode 数 |
| `mode=1777` | 权限（1777 = sticky bit + 全部可写） |

**tmpfs vs ramdisk**：

| 维度 | tmpfs | ramdisk |
|---|---|---|
| 分配方式 | 按需（省内存） | 预分配（浪费） |
| 交换到 swap | 可以（如果启用） | 不可 |
| 大小限制 | 弹性 | 固定 |
| 现代推荐 | ✅ | ❌ |

**结论**：**用 tmpfs，不要用 ramdisk**。ramdisk 是老式方案，tmpfs 全面胜出。

### 7.2 什么放内存什么落盘

**放 tmpfs**：
- 临时文件（`/tmp`）
- 运行时状态（`/run`，如 PID 文件、socket）
- 频繁变化但不重要的缓存（如缩略图）
- 日志的当前正在写的部分（周期性刷落盘）

**必须落盘**：
- 用户数据
- 配置
- 崩溃日志
- 事件计数（关机前 sync）

**折中方案（"内存日志 + 定时刷盘"）**：

```cpp
class HybridLogger {
    // 前 1 MB 在内存，超过或每 30s 落盘
    RingBuffer<Line> mem_{1 * 1024 * 1024};
    std::ofstream disk_{"/data/log/app.log", std::ios::app};

    void write(Line line) {
        mem_.push(line);
        if (mem_.usage() > 0.8 || elapsed(30s)) flush();
    }
    void flush() {
        for (auto& l : mem_.drain()) disk_ << l << '\n';
        disk_.flush();
    }
};
```


## 8. 选型决策树

### 8.1 六个维度

1. **介质类型**：eMMC / SD / 裸 NAND / NOR
2. **读写比**：只读 / 少写 / 多写
3. **写放大容忍**：低（长寿命）/ 高（短寿命也 OK）
4. **可靠性等级**：消费 / 工业 / 车规
5. **压缩需求**：需要（空间紧张）/ 不需要
6. **是否 OTA**：需要 A/B / 不需要

### 8.2 一张图选完

```
分区用途？
   │
   ├── boot / kernel        → raw 或 vfat（uboot 常识别）
   │
   ├── rootfs (只读)         → squashfs + zstd
   │
   ├── vendor / assets       → squashfs (只读)
   │
   ├── config (少量可写)     → overlayfs 组合（lower squashfs + upper ext4）
   │
   ├── data (大量可写)
   │   ├── 介质是 eMMC/SD/UFS
   │   │   ├── 高性能优先    → f2fs（写放大低）
   │   │   └── 稳定优先      → ext4 + noatime + commit=30
   │   └── 介质是裸 NAND     → UBIFS
   │
   ├── log                   → 独立 f2fs 或 ext4，定期轮转
   │
   └── tmp / run             → tmpfs
```

### 8.3 常见误用

**误用 1**：**裸 NAND 上跑 ext4**

```
后果：磨损集中，几个月挂
✅ UBIFS
```

**误用 2**：**ext4 不加 noatime**

```
后果：每次读都写 atime → 写放大加倍
✅ mount -o noatime
```

**误用 3**：**关 journal 图快**

```
掉电 → fs 破损 → 只能 mkfs 重装
✅ 保留 journal，用 data=ordered 或 data=writeback
```

**误用 4**：**overlayfs 的 workdir 和 upperdir 在不同分区**

```
overlayfs 拒绝挂载
✅ workdir 必须与 upperdir 同分区
```

**误用 5**：**所有分区一个 ext4**

```
日志爆盘 → 用户数据也没空间 → 应用崩溃
✅ 至少 data/log 分开
```


## 9. 可靠性与调试

### 9.1 fsync与mmap陷阱

**核心事实**：

```
write()  → 数据到 page cache（未落盘）
fsync()  → 强制 page cache 落到 Flash

mmap 写 → 数据到 page cache（通过内存映射）
msync()  → 强制 mmap 脏页落到 Flash
```

**第 1 章的坑**：mmap 写了日志但没 msync，"强制 reboot"时脏页在 page cache 里没落盘。虽然 reboot 前有 `sync`，但 `sync` 通常也 flush mmap（依内核版本）——但如果 mmap 映射的文件所在分区已经 umount 失败……

**正确写法**：

```cpp
void AsyncLogger::flush() {
    msync(buf_, LOG_SIZE, MS_SYNC);         // ← 关键：mmap 要 msync
    // 或
    munmap(buf_, LOG_SIZE);                 // 反正也要退出，就 unmap
    fsync(fd_);                             // 保险再 sync 一次
}
```

**fsync vs fdatasync**：

| API | 保证 |
|---|---|
| `fsync(fd)` | 文件内容 + 元数据（大小、修改时间）都落盘 |
| `fdatasync(fd)` | 只保证内容 + 决定文件是否可读的元数据（不 sync mtime） |
| `sync()` | 全系统所有 fs 触发 flush（不保证完成） |
| `syncfs(fd)` | 指定文件所在 fs 触发 flush |

**结论**：**普通写用 fdatasync**（省了不必要的元数据 IO），**关键场景用 fsync**。

### 9.2 掉电后的fsck

**fsck 在何时运行**：
1. fstab 里 `passno` 非零 → 开机自动运行
2. mount 失败且 `errors=continue` → 手动运行
3. tune2fs `-c/-i` 设置的间隔检查

**fsck 输入参数**：

```bash
fsck -f  -y /dev/mmcblk0p4         # -f 强制 -y 全部 yes
fsck -p /dev/mmcblk0p4             # 自动修可安全修复的，不能修则退出
```

**嵌入式 fstab 建议**：

```
/dev/mmcblk0p4  /data  ext4  noatime,errors=remount-ro  0  2
```

- `passno=2` → 开机 fsck
- `errors=remount-ro` → 运行中出错自动切只读，防止损坏扩大

**UBIFS**：**没有 fsck**——UBIFS 是 log-structured，重启时自动重放 log，损坏概率极低。

**f2fs**：有 `fsck.f2fs`，但通常 mount 时会自动做恢复。


## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到第 1 章"OTA 后集体挂载失败"，五处修复：

| 问题 | 根因 | 修复 | 章节 |
|---|---|---|---|
| umount 失败被忽略 | mmap 未解除、fd 未关 | umount 失败 → 停止 OTA 或再等再试 | §9.1 |
| mmap 写日志无 msync | 强制 reboot 时脏页丢 | `msync(MS_SYNC)` 或 `munmap` | §9.1 |
| journal 损坏 | data=ordered + 强制断电 | 改 `data=writeback` 用于日志，或用 f2fs | §3.2 |
| emergency shell 卡住 | 无自动 fsck | fstab `passno=2` + `errors=remount-ro` | §9.2 |
| ext4 在 eMMC 上写放大高 | 未调参 | `noatime,commit=30` + stride 对齐 | §3.1 §3.3 |

**改造后的关键脚本**：

```bash
# ota_finish.sh 改造版
set -e

# 1. 通知所有可能持有 fd 的应用先自主释放
killall -SIGUSR1 camera_app 2>/dev/null || true
sleep 2

# 2. 强制 sync
sync

# 3. 尝试 umount，失败重试 3 次
for i in 1 2 3; do
    umount /data && break
    sleep 1
    if [ $i -eq 3 ]; then
        # 用 fuser 找出持有者
        fuser -vm /data
        # 强制 lazy umount 作为最后手段
        umount -l /data
    fi
done

# 4. sync 再确认
sync

# 5. 记录到 misc 分区（供下次开机检查）
echo "ota_finish_ok" > /misc/ota_status

reboot
```

**改造后的日志组件**：

```cpp
class AsyncLogger {
public:
    void handleSignal(int sig) {
        if (sig == SIGUSR1) {
            // OTA 前，收到信号 → 释放 mmap，flush 到磁盘
            msync(buf_, LOG_SIZE, MS_SYNC);
            munmap(buf_, LOG_SIZE);
            fsync(fd_);
            close(fd_);
            exit(0);
        }
    }
};
```

**改造后的 fstab**：

```
/dev/mmcblk0p4  /data      ext4      noatime,nodiratime,commit=30,errors=remount-ro   0  2
/dev/mmcblk0p5  /var/log   ext4      noatime,data=writeback                            0  2
tmpfs           /tmp       tmpfs     size=64M,nodev,nosuid                             0  0
tmpfs           /run       tmpfs     size=16M,nodev,nosuid                             0  0
```

**结果**：OTA 后启动成功率从 92% 提升到 99.98%，剩下的 0.02% 由 A/B 分区回滚保护。

### 10.2 一次挂载的一生

从内核 `mount -t ext4 ...` 到用户能 open 文件的完整流程：

```
mount("/dev/mmcblk0p4", "/data", "ext4", flags, "noatime,...")
    │
    ▼ 【1. VFS】sys_mount
根据 fs_type 找到 ext4 的 fs_operations
    │
    ▼ 【2. ext4 fill_super】§3.3
读 superblock → 校验魔数、feature 位
    │
    ├─ feature 不认识 → 返回 EINVAL
    └─ journal 损坏 → 尝试 recovery
    │
    ▼ 【3. journal 重放】§3.2
如果上次没干净 umount → 读 journal → 应用未完成的事务
    │
    ▼ 【4. inode 表建立】
根 inode 加载
    │
    ▼ 【5. 挂载点更新】
把 /data 目录的 inode 指向新的 root
    │
    ▼ 【6. 返回】
    │
    ▼ 【应用】open("/data/config.json")
VFS 沿挂载树走到 ext4 → 走 ext4 的 ->open → 分配 file 结构 → 返回 fd
```

**掉电重启时的差异**（步 3）：
- 干净 umount → journal 是空的 → 秒速挂载
- 未干净 umount → 有未完成事务 → journal 重放 → 慢一些但正常
- journal 本身损坏 → **挂载失败** → 需要 e2fsck 修复 → 第 1 章的场景

### 10.3 设计哲学回扣

**哲学 1：只读的一定要只读**

只读分区 = 一个不会因意外损坏的资产。**能只读就只读**——出厂固件、系统镜像、静态资源。它们放在 squashfs 里，比放在 ext4 rw 上少了整整一类故障。

**哲学 2：分区就是故障域**

日志爆盘不影响数据分区，data 崩了不影响 rootfs 启动，config 坏了还能回默认。**每次做"这些能放一起吗"的决策时，问自己"哪个坏了不能牵连哪个"**。

**哲学 3：write ≠ 落盘**

fsync、msync、fdatasync、sync、syncfs——**每一个都必须精确使用**。这是嵌入式与服务器最大的差异：服务器可以假设"电永远不断"，嵌入式不能。**代码里每一次数据关键点，必须问：这里 crash 或断电，我能承受什么？**

**哲学 4：文件系统是介质的翻译层**

ext4 的思维是"块设备"，UBIFS 的思维是"NAND"，squashfs 的思维是"只读镜像"。**用错文件系统 = 让翻译器讲一门它不认识的语言**——不是 bug 频出就是性能崩塌。第 1 章的问题追根到底是"用 ext4 思维打嵌入式的仗"。

### 10.4 速查手册

**文件系统匹配口诀**：

```
只读大区    → squashfs
块设备可写  → ext4 or f2fs
裸 NAND    → UBIFS
临时数据    → tmpfs
组合叠加    → overlayfs
```

**紧急排错命令清单**：

```bash
# 1. 挂载状态

# 2. 谁在用某目录（防 umount 失败）
```
