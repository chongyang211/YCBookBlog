## 1. 案例引入

### 1.1 一次上云翻车

一个智能水表项目，10 万台设备上电后要 MQTT 连云平台，每 5 分钟上报一次读数。测试阶段 100 台设备跑得好好的，上线放开到 5 万台后，运营端投诉：

- **投诉 1**：约 15% 设备"离线"，但设备端日志显示 MQTT 连接正常，还在往外发数据。
- **投诉 2**：上报数据经常延迟 30~60 秒，超出业务约定的 10 秒。
- **投诉 3**：某地一场雷雨断网 3 小时后，恢复了但 40% 的设备没能自动重连。
- **投诉 4**：云端偶发收到"上个月的数据"，时间戳都对，就是隔了很久才收到。
- **投诉 5**：接入 TLS 后设备启动多用了 5 秒，客服热线被打爆。

排查过程中发现设备端代码是这样的：

```cpp
// 简化的原始代码
void MqttClient::run() {
    while (true) {
        int rc = mosquitto_connect(mosq_, host_, 1883, 60);
        if (rc != 0) {
            sleep(3);                                 // ← 固定 3 秒重连
            continue;
        }
        while (mosquitto_loop(mosq_, 1000, 1) == 0) {
            // 发数据
            mosquitto_publish(mosq_, nullptr, "water/data",
                              buf.size(), buf.data(), 0, false);   // ← QoS 0
        }
    }
}
```

短短几行代码，藏着 5 个坑：**没心跳保活、固定重连间隔造成雪崩、QoS 0 无确认、没有离线队列、TLS 冷启动没优化**。

### 1.2 顺藤摸到根因

- **假设 1**：为什么"设备端认为连接正常"但云端认为"离线"？，因为 TCP 是**半打开连接**——中间路由器 NAT 表老化后，双方都不知道链路已死。没有 keepalive 或 MQTT 心跳的话，会持续认为"连着"。→ 引出 **心跳的必要性**。
- **假设 2**：为什么会有 30 秒延迟？，因为 MQTT broker 端在网络抖动时启用了指数退避，但设备端固定 3 秒重连产生"惊群"，broker 被打爆后又拒绝连接。→ 引出 **退避 + jitter**。
- **假设 3**：为什么断网 3 小时后 40% 恢复不了？，因为 broker 里的 session 过期了，设备端没做 Clean Session 处理，重连后订阅关系全丢。→ 引出 **持久会话**。
- **假设 4**：为什么会收到"上个月的数据"？，因为 QoS 0 不做确认，网络卡时消息积压在设备本地未发送，恢复后一股脑发出去，但设备没重新打时间戳。→ 引出 **QoS 与离线队列**。
- **假设 5**：为什么 TLS 让启动慢 5 秒？，因为每次都完整握手，10 万设备同时连时 CPU 都跑满在做椭圆曲线运算。→ 引出 **TLS 复用**。

## 2. 通信协议全景

### 2.1 四层协议怎么选

```
┌───────────────────────────────────────────────────────────────┐
│  应用层  │ MQTT │ HTTP │ CoAP │ WebSocket │ 自定义二进制协议    │
├───────────────────────────────────────────────────────────────┤
│  传输层  │            TCP                │     UDP              │
├───────────────────────────────────────────────────────────────┤
│  网络层  │                       IP                             │
├───────────────────────────────────────────────────────────────┤
│  链路层  │ Ethernet │  WiFi   │  4G/5G  │ LoRa │ Zigbee │ BLE │
└───────────────────────────────────────────────────────────────┘
```

**协议特性对照表**：

| 协议 | 传输 | 特点 | 典型场景 |
|---|---|---|---|
| TCP 自定义 | TCP | 最灵活，什么都要自己实现 | 私有网关、私有云 |
| HTTP/1.1 | TCP | 请求-响应、无状态、好调试 | 配置下发、OTA 校验 |
| WebSocket | TCP | 全双工、长连接 | 实时推送、控制指令 |
| MQTT | TCP | 发布-订阅、心跳、QoS | 大规模 IoT |
| CoAP | UDP | REST 风格、省流量 | 极低功耗设备 |
| UDP 广播 | UDP | 局域网设备发现 | Zeroconf/mDNS |

### 2.2 嵌入式典型组合

**智能家居设备**：MQTT/TLS 上云 + HTTP 下 OTA + mDNS 本地发现

**工业网关**：Modbus/CAN 采集 + MQTT/自研 TCP 上云

**低功耗表计**：CoAP/UDP 上报（NB-IoT 网络下省电）

**手持终端**：HTTP + WebSocket（借鉴 Web 生态调试方便）

**结论**：**协议选择随场景走**，没有"最好"，只有"最合适"。选之前先问：并发量、实时性、断网容忍、流量成本。


## 3. TCP的三大坑

### 3.1 粘包与半包

**疑惑**：我 send 了 3 次 100 字节，对端 recv 一次收到 300 字节，代码就崩了？

**论证**：**TCP 是字节流协议**，没有"消息边界"概念。发送方和接收方看到的是一条字节流，不是离散消息。发送方可能把三次 send 合并（Nagle）、接收方可能一次读到多条或半条。

**三种解包方案**：

| 方案 | 实现 | 优缺点 |
|---|---|---|
| 固定长度 | 每包固定 N 字节 | 简单但浪费带宽 |
| 分隔符 | 用 `\n` / `\r\n\r\n` 分割 | 需要转义，如 HTTP 头 |
| 长度前缀 | 前 2/4 字节写长度 + payload | 最常用 |

**长度前缀的最小实现**：

```cpp
// 发送
uint32_t len = htonl(data.size());
send(fd, &len, 4, 0);
send(fd, data.data(), data.size(), 0);

// 接收：从循环 buffer 里解包
class FrameCodec {
    std::vector<uint8_t> buf_;
public:
    void feed(const uint8_t* p, size_t n) { buf_.insert(buf_.end(), p, p+n); }
    bool nextFrame(std::vector<uint8_t>& out) {
        if (buf_.size() < 4) return false;                       // 长度不足
        uint32_t len = ntohl(*reinterpret_cast<uint32_t*>(buf_.data()));
        if (buf_.size() < 4 + len) return false;                 // payload 不足
        out.assign(buf_.begin() + 4, buf_.begin() + 4 + len);
        buf_.erase(buf_.begin(), buf_.begin() + 4 + len);
        return true;
    }
};
```

**踩坑**：
1. 长度字段忘了字节序转换（`htonl/ntohl`）→ 大小端不同设备通信崩
2. 没做长度上限校验 → 恶意包写 `4GB` 长度，`resize` 把内存耗光

### 3.2 nagle与延迟ack

**疑惑**：为什么小包发送有几十毫秒延迟？

**论证**：这是**Nagle + Delayed ACK 联手作恶**：

- **Nagle**：发送方"攒一攒再发"（未确认的小包会等），默认开启
- **Delayed ACK**：接收方"攒一攒再回 ACK"（默认延迟 40ms），也是默认开启

两者叠加 → **写小包 - 攒着 - 40ms 超时才发 - 收方 40ms 后才 ACK - 下一批小包才能发**。总延迟可能 40~200ms。

**修复**：

```cpp
int flag = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));   // 关 Nagle
```

**何时关 Nagle**：需要低延迟交互（如指令控制、心跳）。**何时保留 Nagle**：批量数据传输（带宽利用率更重要）。

### 3.3 keepalive与半打开连接

**疑惑**：TCP 不是可靠传输吗？为什么会有"半打开连接"？

**论证**：TCP 只保证**发出去的包按顺序、无差错**到达。它**不主动检测**对端是否活着——如果对端断电、拔网线，本端 socket 依然处于 `ESTABLISHED` 状态。

**只有真的 send/recv** 才会因超时或 RST 发现。这就是"半打开"。

**解决办法有两层**：

**TCP 层 Keepalive**：

```cpp
int on = 1;
setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &on, sizeof(on));

int idle = 30, intvl = 10, cnt = 3;                    // 30s 无活动开始探测
setsockopt(fd, IPPROTO_TCP, TCP_KEEPIDLE,  &idle,  sizeof(idle));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPINTVL, &intvl, sizeof(intvl));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPCNT,   &cnt,   sizeof(cnt));
```

**应用层心跳**（推荐）：

```cpp
// 每 20 秒发一个心跳包，60 秒无回复视为断开
timer.every(20s, [this] { sendHeartbeat(); });
onRecv([this](Msg m) {
    lastActive_ = now();
});
timer.every(5s, [this] {
    if (now() - lastActive_ > 60s) reconnect();
});
```

**为什么应用层心跳更好**：
1. **粒度可控**（TCP Keepalive 默认 2 小时才发第一次）
2. **携带业务信息**（心跳里可以捎带状态、时间同步）
3. **通过 NAT/防火墙**（TCP Keepalive 有些 NAT 不认，应用层数据一定被识别为"活动"）

**结论**：**嵌入式一律用应用层心跳**，TCP Keepalive 作为兜底。


## 4. MQTT实战

### 4.1 MQTT为什么适合IoT

**特点归纳**：
1. **发布-订阅**：设备只关心 topic，不用知道其他设备的存在
2. **长连接**：一次握手，之后持续复用，省流量省 CPU
3. **心跳内建**（PINGREQ/PINGRESP）
4. **QoS 三级**：从 0（发就忘）到 2（恰好一次）
5. **遗嘱（LWT）**：设备异常掉线，broker 代发一条"我死了"消息
6. **协议极简**：最小固定头 2 字节

一个典型的 MQTT 拓扑：

```
                    ┌─────────────┐
                    │  MQTT Broker │
                    │   (EMQX)    │
                    └──────┬──────┘
              ┌────────────┼────────────┐
              │            │            │
        ┌─────▼───┐  ┌─────▼───┐  ┌────▼────┐
        │设备1     │  │设备2     │  │云端后台  │
        │pub temp │  │sub cmd  │  │sub temp │
        └─────────┘  └─────────┘  └─────────┘
```

### 4.2 QoS三级选择

| QoS | 语义 | 交互 | 场景 |
|---|---|---|---|
| 0 | 最多一次 | 发就忘 | 高频次要数据（心率、加速度） |
| 1 | 至少一次 | PUB→PUBACK | 关键上报（异常告警） |
| 2 | 恰好一次 | PUB→PUBREC→PUBREL→PUBCOMP | 强一致（结算、开关命令） |

**QoS 选择原则**：
- **QoS 越高，延迟越大、broker 存储越贵**
- **QoS 0 也不代表一定丢**，TCP 层已经很可靠，只是"进程崩了没重发"
- **绝大部分场景 QoS 1 够用**

**踩坑**：
- 全用 QoS 2 → broker 存储 IO 打爆
- 全用 QoS 0 → 关键命令丢失
- QoS 只是保证"到达一次"，**不保证消息按发送顺序到达**——需要顺序请自己在 payload 里带 seq_id

### 4.3 遗嘱与保留消息

**遗嘱（Last Will）**：连接时告诉 broker："如果我异常掉线，请代发这条消息"

```c
mosquitto_will_set(mosq, "device/status/dev001",
                   strlen("offline"), "offline", 1, true);
```

**用途**：设备突然掉电时，broker 主动向"设备状态"topic 发 `offline`，云端能第一时间知道。

**保留消息（Retained）**：某 topic 上最后一条被标 retain 的消息会被 broker 保留，**新订阅者一订阅立刻收到这条**

```c
mosquitto_publish(mosq, NULL, "device/config/dev001",
                  cfg.size(), cfg.data(), 1, true);   // retain=true
```

**用途**：设备重启后订阅 `device/config/xxx`，立刻拿到最新配置，不用向云端主动请求。

**结论**：**LWT + Retained 是 MQTT 的两个杀手锏**，能省掉大量业务代码。


## 5. HTTP与WebSocket

### 5.1 HTTP的应用场景

**HTTP 在嵌入式的正确用途**：

| 用途 | 原因 |
|---|---|
| OTA 下载固件 | 断点续传（Range）、CDN 加速、成熟 |
| 配置管理 | RESTful 语义清晰、debug 工具多 |
| 简单上报（低频） | 请求响应模型天然适合"发送 + 确认" |
| 云函数触发 | Serverless 生态友好 |

**HTTP 的坑**：
1. **每次请求都要重建 TCP + TLS**（除非 keep-alive）→ 高频用一定慢
2. **文本协议开销大**（header 好几百字节）→ 流量成本高
3. **不适合服务端主动推送**（用长轮询或 WS 代替）

**HTTP/1.1 keep-alive 用法**（省重复建连开销）：

```
Connection: keep-alive
Keep-Alive: timeout=60, max=100
```

设备端用 curl 库时确保**复用同一个 handle**，而不是每次 `curl_easy_init`。

### 5.2 WebSocket vs 长轮询

**需求**：云端要给设备推消息。

**方案对比**：

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| HTTP 短轮询 | 客户端每 N 秒发 GET | 简单 | 延迟大、流量浪费 |
| HTTP 长轮询 | 服务器 hold 请求直到有数据 | 延迟低 | 每次响应后要重新建立 |
| WebSocket | HTTP Upgrade 后全双工 | 双向、低延迟、开销小 | 需要 broker/proxy 支持 WS |
| MQTT | 发布-订阅 | 更适合多对多 | 需要 broker |

**选择**：
- **只想给"少量设备"推消息** → WebSocket
- **大规模 IoT** → MQTT
- **能改协议就上 WS 或 MQTT，别用长轮询**


## 6. 断线重连体系

### 6.1 心跳与超时判定

**规则**：
- **心跳间隔** = ~20 秒（穿过多数 NAT 保活）
- **超时判定** = 心跳间隔 × 2~3（不要单次超时就断，防抖）
- **心跳失败** = 主动关连接 + 重连（而不是等 TCP Keepalive）

### 6.2 指数退避与jitter

**疑惑**：第 1 章那个"固定 3 秒重连"错在哪？

**论证**：**惊群**——网络恢复瞬间，10 万台设备同时向 broker 发起连接，broker 顶不住。**指数退避 + 随机抖动**是解药：

```
第 1 次失败：等 1s   × (1 + rand(0, 0.5))
第 2 次失败：等 2s   × (1 + rand(0, 0.5))
第 3 次失败：等 4s
第 4 次失败：等 8s
...
最大不超过 60s
```

代码：

```cpp
class Backoff {
public:
    Duration next() {
        Duration d = base_ * (1 << std::min(attempt_, kCap));
        double jitter = 1.0 + double(rand()) / RAND_MAX * 0.5;   // +0 ~ +50%
        attempt_++;
        return std::min(Duration(d.count() * jitter), max_);
    }
    void reset() { attempt_ = 0; }
private:
    Duration base_  = 1s;
    Duration max_   = 60s;
    int      attempt_ = 0;
    static constexpr int kCap = 6;                               // 最大翻倍 6 次
};
```

**为什么加 jitter**：即使指数退避，10 万设备算出来的重连时刻还是集中在 `t=1s, 2s, 4s...`，加随机抖动才能真正分散。

### 6.3 离线队列与去重

**需求**：断网期间产生的数据不能丢，恢复后要补发。

**离线队列设计**：

```
┌──────────────────────────────────────────┐
│   本地 SQLite/文件 队列                    │
│   ┌────────────────────────────────┐     │
│   │ seq | timestamp | topic | body │     │
│   └────────────────────────────────┘     │
│                                            │
│   在线：直接发 + 落队列（等 PUBACK 再删）  │
│   离线：只落队列                          │
│   恢复：从队列头开始重发（按 seq 顺序）    │
└──────────────────────────────────────────┘
```

**去重机制**：
- 每条消息带全局唯一 `msg_id`（设备 ID + seq）
- 云端做幂等：`msg_id` 已见过就丢弃
- **不要依赖 QoS 2**：broker 端存储代价大，且不跨 broker

**结论**：**离线队列 + 幂等 msg_id + QoS 1**，是嵌入式上云的黄金三件套。


## 7. 安全传输

### 7.1 TLS的握手成本

**疑惑**：TLS 到底贵在哪？

**论证**：TLS 1.2 完整握手需要 **2 个 RTT + 一次非对称加密**。ARM Cortex-A53 上 ECDHE + RSA 2048 一次握手约 200~500ms，弱设备（Cortex-M4）更是要 2~5 秒。

**优化手段**：

1. **升 TLS 1.3**：1 个 RTT，握手时间腰斩
2. **Session Resumption**：复用之前的会话密钥，跳过非对称计算
3. **ECC 证书代替 RSA**：ECDSA 256 位 ≈ RSA 3072 位强度，但计算快 5~10 倍
4. **硬件加速**：SoC 有 crypto 引擎（如 ARM CryptoCell）就用起来
5. **降级到 PSK**：预共享密钥，跳过整个证书体系（IoT 私有场景可用）

### 7.2 证书管理

**要点**：
1. **不要写死证书**，放到设备读写分区，支持远程更新
2. **CA 证书**放只读分区，验证服务端用
3. **客户端证书 + 私钥**放安全存储（TEE / eFuse / 加密分区）
4. **过期前 30 天**自动申请续签

**双向认证（mTLS）**：设备也向服务端证明身份。适用于**高价值场景**（工业、医疗）。

**证书验证的坑**：
- 系统时间不对 → 证书"未生效"或"已过期"（第一次开机没同步时间常见）
- CA bundle 缺失 → 全部证书都被判"不受信任"
- 服务端名 (SAN) 校验失败 → 用 IP 连接时如果证书只签了域名会报错


## 8. 选型决策树

### 8.1 六个维度

1. **并发规模**：单机 <100 / 单集群 100~10k / 大规模 >100k
2. **实时性**：秒级 / 100ms 级 / 10ms 级
3. **数据方向**：单向上报 / 双向 / 服务器主动推
4. **网络质量**：稳定局域网 / 波动 4G / 极弱 NB-IoT
5. **设备算力**：Cortex-A / Cortex-M / 8bit MCU
6. **安全等级**：无 / TLS / mTLS / 硬件根信任

### 8.2 一张图选完

```
需要与云通信
   │
   ├── 只是偶尔上传/下载文件？── 是 ──► HTTP + keep-alive
   │        │
   │        否
   │        ▼
   ├── 需要服务端主动推？── 否 ──► HTTP 短/长轮询
   │        │
   │        是
   │        ▼
   ├── 大规模（>1k 设备）？── 是 ──► MQTT + TLS
   │        │
   │        否
   │        ▼
   ├── 只有少量设备且要全双工？── 是 ──► WebSocket
   │        │
   │        否
   │        ▼
   └── 私有协议/工业专用？── 是 ──► 自定义 TCP + 长度前缀
```

### 8.3 常见误用

**误用 1**：**HTTP 高频轮询**

```
设备每 5 秒 GET 一次 → 一天 17,280 次请求 → 流量爆
✅ 改 MQTT 长连接
```

**误用 2**：**全用 QoS 2**

```
broker 存储压力翻 5 倍
✅ 只在强一致关键点用 QoS 2，其他 QoS 1
```

**误用 3**：**没做粘包解包**

```
自研 TCP 协议时 recv() 直接当消息处理
✅ 上长度前缀 + Codec 类
```

**误用 4**：**证书硬编码到代码**

```
过期一次要发全量 OTA
✅ 分区存证书，支持热更新
```


## 9. 可靠性与调试

### 9.1 tcpdump的正确用法

**上板抓包**（前提：rootfs 里有 tcpdump 或 tshark）：

```bash
# 抓 MQTT 端口的所有流量
tcpdump -i eth0 -w /tmp/mqtt.pcap 'port 1883 or port 8883'

# 抓与云端 IP 的握手包（-s 0 抓完整长度）
tcpdump -i any -s 0 -w /tmp/tls.pcap 'host cloud.example.com and port 8883'

# 拉到 PC 上 Wireshark 分析
scp root@device:/tmp/mqtt.pcap ./
```

**分析要点**：
- `[SYN]` `[SYN,ACK]` `[ACK]` 完整 → TCP 建连正常
- `Client Hello` → `Server Hello` → `Certificate` → TLS 握手包
- `RST` 出现 → 有一方主动断开
- 长时间无数据但也无 FIN → 半打开连接

### 9.2 网络故障的分层排查

**排查 SOP**（从底往上）：

```bash
# 1. 物理链路 up 吗？
ip link show eth0                                  # 看 state UP

# 2. IP 拿到没？
ip addr show eth0

# 3. 网关通吗？
ping -c 3 $(ip route | grep default | awk '{print $3}')

# 4. DNS 解析行吗？
nslookup cloud.example.com

# 5. 目标 IP 通吗？
ping -c 3 cloud.example.com

# 6. 端口通吗？
nc -zv cloud.example.com 8883

# 7. TLS 握手能过吗？
openssl s_client -connect cloud.example.com:8883 -showcerts

# 8. MQTT 能连吗？
mosquitto_sub -h cloud.example.com -p 8883 --cafile ca.crt \
              --cert dev.crt --key dev.key -t 'test/#' -v
```

**每一步失败对应的诊断**：

| 失败点 | 诊断 |
|---|---|
| link down | 硬件问题或驱动 |
| 拿不到 IP | DHCP 服务器 / 网线 |
| ping 网关失败 | 网关配置错 / 网关挂了 |
| DNS 失败 | resolv.conf 错或 DNS 服务器不通 |
| ping IP 失败 | 中间路由或防火墙 |
| 端口不通 | 服务端防火墙或没起 |
| TLS 失败 | 证书 / 时间 / 版本 |
| MQTT 失败 | 认证或 topic 权限 |


## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到第 1 章"10 万水表上云翻车"，五个投诉逐一对上：

| 投诉 | 根因 | 修复 | 章节 |
|---|---|---|---|
| 15% 设备"离线" | 无心跳，半打开连接 | 应用层 20s 心跳 + LWT | §3.3 §4.3 |
| 数据延迟 30~60s | 固定 3s 重连造成惊群 | 指数退避 + jitter | §6.2 |
| 断网 3h 后 40% 失联 | 无持久 session | Clean Session=0 + 重订阅 | §4.3 §6.1 |
| 收到"上个月数据" | QoS 0 无确认 + 无离线队列 | QoS 1 + 本地队列 + msg_id 去重 | §4.2 §6.3 |
| 启动慢 5s | TLS 每次完整握手 | Session Resumption + ECC 证书 | §7.1 |

**改造后的连接管理器骨架**：

```cpp
class MqttManager {
public:
    void start() {
        pool_.submit([this] { runLoop(); });
        heartbeat_.every(20s, [this] { publishHeartbeat(); });
        watchdog_.every(5s,  [this] { checkAlive(); });
    }
private:
    void runLoop() {
        Backoff bo;
        while (running_) {
            if (connect() == 0) {
                bo.reset();
                subscribe();
                flushOfflineQueue();                // 补发本地队列
                loopUntilDisconnect();
            }
            std::this_thread::sleep_for(bo.next());
        }
    }
    void publish(std::string topic, Bytes body) {
        auto msg = MsgWithId{genId(), std::move(topic), std::move(body)};
        if (connected_) sendWithAck(msg, 1);        // QoS 1
        offlineQueue_.push(msg);                    // 无论成败都落地，等 PUBACK 再删
    }
    // ... 心跳、去重、TLS session resume
};
```

**结果**：设备离线率从 15% 降到 0.3%，平均上报延迟从 40s 降到 3s，断网恢复率从 60% 升到 99.5%，冷启动从 5s 降到 1.2s。

### 10.2 一条消息的一生

设备读到水表读数后，一条消息完整流转：

```
水表读数产生
    │
    ▼ 【1. 应用调用 publish】§4.2
publish("water/data/dev001", {seq, ts, value})
    │
    ▼ 【2. 落本地离线队列】§6.3
SQLite: INSERT INTO outbox (seq, msg_id, topic, body) ...
    │
    ▼ 【3. 通过 MQTT 客户端发出】QoS 1
mosquitto_publish → TCP send
    │
    ▼ 【4. TLS 记录层加密】§7.1
TLSRecord{app_data} → send()
    │
    ▼ 【5. TCP 层封装】§3.1
[seq][ack][flags][payload] → 网络
    │
    ▼ 【6. 云端 broker 收到 → PUBACK】§4.2
    │
    ▼ 【7. 设备收到 PUBACK 后删除 outbox 对应行】§6.3
DELETE FROM outbox WHERE msg_id = ?
    │
    ▼ 【8. broker 转发给云端订阅者】§4.1
云端服务 subscribe("water/data/#") → 处理
    │
    ▼ 【9. 服务端幂等：如果 msg_id 已见 → 丢弃】§6.3
    │
    ▼ 【10. 写入业务库】
```

**任何一步失败**：
- 步 6 未收 PUBACK → outbox 里还在，下次重连补发
- 步 8 broker 挂了 → 设备 keepalive 超时 → 重连
- 步 9 重复 → msg_id 去重

**全链路的可靠性**建立在**离线队列 + 幂等 msg_id + 应用心跳**上，而不是任何单一 QoS。

### 10.3 设计哲学回扣

**哲学 1：可靠性是端到端的，不是靠某一层**

TCP 可靠不代表消息不丢，MQTT QoS 1 也不代表消息不重。**真正的可靠性是"发送方持久化 + 接收方幂等"**，中间任何层挂了都能补回来。

**哲学 2：重连是常态，不是异常**

网络会抖动、设备会掉电、云端会重启。**代码应该假设"连接随时会断"**，而不是把重连当异常处理路径。第 1 章的固定 3 秒重连就是把重连当异常。

**哲学 3：所有超时都要有随机性**

只要有超过 100 个客户端，任何固定周期都会造成惊群。**心跳、重连、重发全部要 + jitter**。

**哲学 4：调试信息比"能跑"更重要**

上万台设备的问题不能一台台看，**必须在协议里预留 seq_id、trace_id、client_id**，服务端聚合起来看趋势。

### 10.4 速查手册

**四条网络编程铁律**：

```
1. 一切协议都要考虑粘包（TCP）或丢包（UDP）
2. 一切心跳都要能感知半开连接
3. 一切重连都要指数退避 + jitter
4. 一切消息都要幂等（唯一 id + 去重）
```
