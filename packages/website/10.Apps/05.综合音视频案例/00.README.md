# MiniPlayer 五端对照：从 0 到 1 打造跨平台音视频播放器

本案例是 `10.Apps` 卷的**毕业设计级综合案例**：我们用**同一个产品需求**——一个"能播放、能后台、能收藏、能同步歌词"的本地音视频播放器——用 **5 种技术栈**在 **6 个平台**上做一遍"母语级"实现：

- **Android**：Java + AndroidX（XML + Activity）
- **iOS**：Objective-C（UIKit + AVFoundation）
- **Web**：Vue 3（Composition API + Pinia）
- **Qt 桌面（Linux + macOS + Windows 三合一）**：C++ + Qt 6 Widgets——**一份 CMake 工程，产出三份原生可执行文件**
- **Electron 桌面（Linux + macOS + Windows 三合一）**：React + TypeScript + **自写 C++ 共享库（CMake 产出 .so / .dylib / .dll，koffi FFI 加载）**——演示"**C++ 作为服务被 JS 调**"的工程哲学，和 Qt 篇形成"**原生主语言 vs. 跨语言桥接**"的最强对照

一次集齐 **Java / OC / JS / C++** 四大主流语言系，覆盖 Android / iOS / Web / Linux / macOS / Windows 六个平台。学完这套案例，你收获的不是"会写几个播放器"，而是**同一个需求在不同平台约束下如何演化出不同的架构决策**——这是远超"会用某个框架"的跨平台工程能力。

> **为什么 Qt 和 Electron 都做？** 它们都用 C++、都三端、都走 CMake，但工程哲学完全不同：Qt 篇以 C++ 为主语言、UI 直接用 Qt Widgets；Electron 篇以 TypeScript/React 为主语言、C++ 包成共享库通过 FFI 被调用。前者代表"原生思路"，后者代表"Web 桥接思路"——这是真实世界桌面应用两条主流路线。

> **写作体例**：本案例仿照《C++ 入门到精通》的 [迷你KV存储引擎](/pages/97f31a/) 与 [迷你编译器解释器](/pages/d647c8/) 两篇毕业设计的结构——**渐进学习节奏 + 灵魂三问 + 阶段目标卡片 + 验收命令**。每端 1 篇，每篇按 9 个阶段推进，绝不一上来甩 4000 行代码。

## 产品定位

> **做一个"能跑能停、能后台、能收藏、能同步歌词"的本地音视频播放器——音频对标网易云/千千静听，视频对标 Infuse/PotPlayer 的基础功能子集。**

三条产品原则：

1. **纯本地优先**：媒体来自本机文件系统扫描，一期不引入服务端。这保证五端对称、离线可用、教学聚焦。
2. **音视频平衡覆盖**：两种形态的**基础能力都必须齐全**（音量/字幕/全屏/画中画/多轨切换都在），但渲染层统一走系统播放器，不陷入编解码泥潭。
3. **平台惯例优先**：后台播放、通知控制、耳机线控等能力，每端用该平台的"官方正教"实现，这正是本案例的教学价值所在。

## 五端技术栈总表

这是本案例**最重要的一张表**，每一行都是一次"同一需求 → 五种本地化实现"的对照练习。**Qt 桌面列**和 **Electron 桌面列**各自覆盖 Linux / macOS / Windows 三个平台——一份代码三端通吃，但两者的"用 C++ 的方式"完全不同。

| 层级 | Android (Java+AndroidX) | iOS (Objective-C) | Web (Vue 3) | **Qt 桌面** | **Electron 桌面** |
|------|------------------------|-------------------|-------------|-------------|-------------------|
| UI 框架 | XML + Activity + RecyclerView | UIKit + UITableView + Storyboard | Vue 3 + Vite + Pinia | Qt 6 Widgets (QMainWindow + QListView) | React 19 + Vite + Zustand + Tailwind 4 |
| 主语言 | Java | Objective-C | TypeScript | C++17 | TypeScript + **C++17（原生扩展）** |
| 音频引擎 | ExoPlayer / MediaPlayer | AVPlayer / AVAudioPlayer | HTMLAudioElement + Web Audio | QMediaPlayer + QAudioOutput | HTMLAudioElement + Web Audio（Chromium） |
| 视频引擎 | ExoPlayer + PlayerView | AVPlayer + AVPlayerLayer | `<video>` | QMediaPlayer + QVideoWidget | `<video>`（Chromium 原生 PiP） |
| 后台与通知 | ForegroundService + MediaSessionCompat | AVAudioSession + MPRemoteCommandCenter | Page Visibility + Media Session API | **Linux**: D-Bus MPRIS<br>**macOS**: MPNowPlayingInfoCenter<br>**Windows**: SMTC | **同 Qt 三平台**，但封装在**自写 C++ 共享库 `mp_native`** 中，由 Node.js 通过 koffi FFI 调用 |
| 文件扫描 | MediaStore | NSFileManager / MPMediaLibrary | File System Access API | `std::filesystem` + QDirIterator | Node.js `fs.opendir`（异步迭代） |
| ID3 元数据 | MediaMetadataRetriever | AVAsset metadata | music-metadata-browser | TagLib (C++) | **TagLib (C++)，封装在 `mp_native`** |
| 本地 DB | Room | FMDB / SQLite C API | IndexedDB (Dexie) | QSqlDatabase | better-sqlite3（Node 原生模块） |
| 跨语言边界 | — | — | — | — | **C ABI + koffi FFI**（本篇独特考点） |
| 异步模型 | HandlerThread + ExecutorService | GCD + NSOperationQueue | Promise + async/await | QThread + 信号槽 | Promise + Node Worker Threads；主进程 ↔ renderer 走 IPC |
| 架构模式 | MVVM | MVC + Delegate | Composition API + Pinia | MVC + 信号槽 | 三进程 (main / preload / renderer) + Zustand |
| 主题切换 | DayNight | UITraitCollection | CSS 变量 + `prefers-color-scheme` | `QStyleHints::colorScheme()` | `nativeTheme.themeSource` + Tailwind `dark:` |
| 播放队列 | List + ExoPlayer Playlist | AVQueuePlayer | Pinia store 数组 | QVector + 自管理 | Zustand store 数组 |
| 代码共享度 | — | — | — | **三端 95% 共享** | **三端 95% 共享 + C++ 层 90% 共享、5% `#if __linux__/__APPLE__/_WIN32` 分流** |
| 产物形态 | APK | IPA | Web Bundle | ELF + .app + .exe（同一工程） | AppImage/deb + .dmg + .exe（Electron 壳 + 平台 `.so`/`.dylib`/`.dll`） |
| 工程哲学 | 原生主语言 | 原生主语言 | 浏览器纯 Web | **C++ 作主语言** | **C++ 作服务提供者，被 TS 调用** |

## 共享五层架构

五端共享同一套分层架构，每端的目录结构保持**三段式对齐**（`ui/` `service/` `data/`）：

```text
┌────────────────────────────────────────────────┐
│  UI 层        Activity / UIViewController /    │
│               Vue 组件 / QWidget               │
├────────────────────────────────────────────────┤
│  Controller / ViewModel 层（状态管理）          │
├────────────────────────────────────────────────┤
│  PlayerService（播放、队列、状态广播、后台）     │
├────────────────────────────────────────────────┤
│  MediaRepository（扫描 / 元数据 / DB 聚合）      │
├────────────────────────────────────────────────┤
│  Platform Engine（ExoPlayer / AVPlayer /        │
│                  <audio>/<video> / QMediaPlayer）│
└────────────────────────────────────────────────┘
```

> 读者在不同端之间切换时，"**同名目录做同件事**"，心智负担最小。详细设计见 [01.架构设计与五端对照](/pages/mp5arch/)。

**路径一（推荐）：主攻一端 + 通读其余四端**

1. 选你最熟悉的一端，完整做完 9 个阶段（动手）；
2. 其余四端只读"架构对照 + 阶段⑥后台播放 + 各端特色坑"三部分（精读）；
3. 最后回看五端总表，体会每行背后的架构权衡。

**路径二：五端并行**

每做完一个阶段就切到另一端做同一阶段。适合时间充裕（100h+）且想横向打通的读者，风险是容易烂尾，建议最多并行两端。

**路径三：对照式速读**

只读不写，把五端文档当"API 对照手册"用，适合已经会某一端、想快速了解其他平台做法的读者。

**路径四：桌面双主修（Qt + Electron）**

两篇都是 C++ + 三端产物，但工程哲学截然不同——这是本案例最高价值的"同底不同术"对照。做完 Qt 篇再做 Electron 篇，你会深刻理解"**原生主语言 vs. 跨语言桥接**"的工程权衡。预估 60-70h。

### Qt 桌面端如何运行与查看（Linux / macOS / Windows）

Qt 6 在三端都是一等公民，**同一份 CMake 工程产出三份原生可执行文件**：

```bash
# Linux（Ubuntu 22.04/24.04）
sudo apt install -y qt6-base-dev qt6-multimedia-dev cmake g++ \
                    libsqlite3-dev libtag1-dev \
                    gstreamer1.0-plugins-good gstreamer1.0-plugins-bad gstreamer1.0-libav
cmake -B build -S . && cmake --build build -j
./build/MiniPlayer                 # 弹原生 ELF 窗口
```

```bash
# macOS（Intel + Apple Silicon 均可）
brew install cmake ninja qt@6 taglib
export CMAKE_PREFIX_PATH="$(brew --prefix qt@6)"
cmake -B build -S . && cmake --build build -j
open ./build/MiniPlayer.app        # 弹原生 .app（Dock 出图标）
```

```powershell
# Windows 11（vcpkg 方案）
C:\vcpkg\vcpkg install qtbase:x64-windows qtmultimedia:x64-windows taglib:x64-windows
cmake -B build -S . -DCMAKE_TOOLCHAIN_FILE=C:\vcpkg\scripts\buildsystems\vcpkg.cmake
cmake --build build -j
.\build\MiniPlayer.exe             # 弹原生 .exe
```

### Electron 桌面端如何运行与查看（Linux / macOS / Windows）

Electron 篇要**同时**具备：Node.js 工具链 + 对应平台的 C++ 工具链（用于编译 `mp_native` 共享库）。流程是**先 CMake 产出 .so/.dylib/.dll，再 Electron 加载并打包**：

```bash
# Linux（Ubuntu 24.04）
sudo apt install -y cmake g++ pkg-config libtag1-dev libdbus-1-dev
pnpm install
pnpm native:build         # 产出 resources/native/libmp_native.so
pnpm dev                  # 弹 Electron 窗口（dev 模式热更新）
pnpm dist:linux           # 产出 dist/MiniPlayer-x.y.z.AppImage + .deb
```

```bash
# macOS
brew install cmake taglib pkg-config
pnpm install
pnpm native:build         # 产出 resources/native/libmp_native.dylib
pnpm dev
pnpm dist:mac             # 产出 dist/MiniPlayer-x.y.z-universal.dmg
```

```powershell
# Windows 11
C:\vcpkg\vcpkg install taglib:x64-windows
pnpm install
pnpm native:build         # 产出 resources\native\mp_native.dll
pnpm dev
pnpm dist:win             # 产出 dist\MiniPlayer-Setup-x.y.z.exe (NSIS)
```

## FAQ

**Q1：为什么不做 Flutter / React Native / Compose Multiplatform 一套代码跨五端？**
本案例的教学目标是**理解每个平台的原生机制**（后台、通知、媒体会话），跨平台框架恰恰把这些差异抹平了。学完本案例再学跨平台框架，你会清楚它替你做了什么、付出了什么代价。

**Q2：视频播放会不会太重？**
不会。各端的视频能力都是系统播放器级别的（ExoPlayer/AVPlayer/`<video>`/QMediaPlayer），渲染层各自接到 PlayerView / AVPlayerLayer / video 标签 / QVideoWidget 即可。我们不碰 FFmpeg 软解。

**Q3：可以只做音频跳过视频吗？**
可以。视频密集功能集中在**阶段④**（可整段跳过），阶段②的扫描过滤视频类型即可。但建议至少做到"全屏 + 字幕 + 画中画"三件套。

**Q4：字幕支持到什么程度？**
一期支持 **SRT / VTT 两种外挂字幕格式**，支持多字幕轨切换（内嵌字幕由系统播放器直接解析）。更复杂的 ASS 特效字幕放挑战题。

**Q5：画中画 PiP 各端都支持吗？**
支持矩阵：Android 7.0+、iOS 14+ / iPadOS、Web（Chrome/Edge/Safari）、Qt 桌面（Linux/macOS/Windows 三端均无系统级 PiP，用"置顶迷你窗口"等效实现）、**Electron 桌面（三端均原生支持 Chromium Picture-in-Picture Window API，体验最佳）**。

**Q6：格式支持到什么程度？**
音频：mp3 / aac / m4a / flac / wav / ogg。视频：mp4(H.264/H.265) / mkv / mov / webm；mkv 和 H.265 在部分端需要系统/浏览器层支持。阶段②扫描按文件头探测而非仅扩展名，不支持的格式灰显并给出原因提示。

**Q7：Qt / Electron 桌面端没有对应平台的机器怎么办？**
- **想跑 Linux 版**：Mac 用 UTM + Ubuntu、Windows 用 WSL2 + WSLg，都是开箱有图形界面；
- **想跑 macOS 版**：**必须有 Mac 真机**——Apple 的工具链（Xcode/codesign/notarize）全部强绑定 macOS，无法在其他系统编译；
- **想跑 Windows 版**：Mac 用 Parallels/UTM 装 Windows 11、或租云服务器；
- 一期只跑一端也完全可行，两份桌面工程本身都保证"将来回到另一端时直接 build 过"。Qt 篇详见 [05](/pages/mp5qt0/) §2，Electron 篇详见 [06](/pages/mp5elec/) §2。

**Q8：Windows 平台只用 Qt / Electron，不单独做一份 WPF 吗？**
Qt 版和 Electron 版的 Windows 产物都是**原生 PE 可执行文件**，调用的都是系统 Media Foundation + SMTC，日常功能完全够用。如果想体验 "Fluent UI + 更深融入 Windows 生态" 这条原生路线，去看 [07.挑战题](/pages/mp5more/) 的 WPF 版——主线保持"5 端 × 6 平台"的最小闭环，挑战题负责"同平台另一条工程路线"的进阶拓展。

**Q9：Qt 桌面篇和 Electron 桌面篇都用 C++，到底学哪个？**
两篇都值得学，它们代表了桌面开发的**两条主流路线**：
- **Qt 篇**：C++ 作主语言，UI、业务、系统集成全是 C++。适合"要极致性能、要原生外观、团队本来就是 C++ 栈"的场景（代表产品：Krita、Qt Creator）。
- **Electron 篇**：TypeScript/React 作主语言，C++ 只负责"必要的系统 API 封装 + 性能关键算法"，通过 C ABI + koffi FFI 被 JS 调用。适合"UI 迭代快、团队前端为主、但又需要少量系统能力"的场景（代表产品：VS Code、Figma Desktop、Obsidian）。
- 学两篇最大的收获是**学会"何时用 C++"的工程决策**——这远比掌握某个具体框架更重要。
