## 1. 案例引入

```bash
# 2015 年，一个"小项目"的文件数量：
js/
  jquery.min.js      # 第三方库
  app.js             # 主逻辑（800行）
  utils.js           # 工具函数（200行）

# 2023 年，同样业务的项目：
src/
  components/BaseButton.vue
  components/UserCard.vue
  ...（还有 80+ 个组件）
  composables/useAuth.ts
  stores/user.ts
  ...（还有 30+ 个模块）

# 问题来了：
# 1. 这些文件之间的依赖关系怎么管理？
# 2. CSS/图片/字体/TS 文件怎么"打包"到一起？
# 3. 开发时怎么做到修改代码后 0.3 秒就看到效果？
# 4. 生产环境怎么压缩到 200KB 以内？
```

**前端工程化要解决的就是这四个核心问题**。本文提供全景概览，后续各篇深入展开。

## 3. 模块化历程

### 3.1 蛮荒时期

```javascript
// 2005 年——所有脚本挂 window
// <script src="jquery.js"></script>
// <script src="app.js"></script>
// <script src="utils.js"></script>
window.$ = jQuery;           // 全局污染
window.MY_APP = {};          // 手动"命名空间"
window.MY_APP.utils = {};    // 嵌套命名空间——但本质还是全局变量
```

**问题**：依赖顺序必须手动管理，变量名冲突，无法 Tree Shaking。

### 3.2 CommonJS

```javascript
// a.js
module.exports = { foo: 1 };

// b.js
const a = require('./a');
console.log(a.foo);  // 1
```

**特点**：同步加载（适合 Node），动态 `require`，运行时解析；**不能在浏览器中直接使用**。

### 3.3 AMD

```javascript
// RequireJS 时代
define(['jquery', 'utils'], function($, utils) {
    return { init: function() {} };
});
```

**特点**：异步加载，但语法冗长，依赖前置声明。

### 3.4 ES Module

```javascript
// 静态导入——编译时确定依赖关系
import { ref, computed } from 'vue';
import type { User } from './types';

// 动态导入——运行时按需加载
const module = await import('./heavy-component.vue');

// 静态结构 → Tree Shaking 成为可能
// 编译时分析 → 构建工具可以精确定位依赖
```

### 3.5 各方案对比

| 方案 | 加载方式 | TreeShaking | 浏览器 | Node | 现状 |
|---|---|---|---|---|---|
| 全局变量 | 手动 | ❌ | ✅ | ✅ | 被淘汰 |
| CommonJS | 同步 `require` | ❌ | ❌ | ✅ | Node 传统 |
| AMD | 异步 `define` | ❌ | ✅ | ❌ | 被淘汰 |
| ES Module | 静态 `import` | ✅ | ✅ | ✅ | **标准** |

## 4. 构建工具

### 4.1 无构建之痛

```html
<!-- 浏览器无法直接识别这些文件 -->
<script type="module">
    import { ref } from 'vue';              // ❌ 找不到模块
    import style from './app.css';          // ❌ 浏览器不支持 CSS import
    import logo from './logo.png';          // ❌ 浏览器不支持图片 import
    import { fetchUser } from '@/api/user'; // ❌ 路径别名浏览器不理解
</script>
```

### 4.2 构建职责

```
源码（开发者写的）→ 构建工具 → 产物（浏览器能运行的）

转换内容：
  .vue/.tsx  → .js              语法转换
  .scss      → .css             样式编译
  @/api/user → ./src/api/user   路径解析
  import()   → 代码分割         按需加载
  console.log → (移除)          压缩优化
  图片 > 8KB  → base64 / URL     资源处理

构建结果（dist/）：
  index.html                     入口 HTML
  assets/index-[hash].js         主 JS bundle
  assets/vendor-[hash].js        第三方库 bundle
  assets/index-[hash].css        样式文件
  assets/logo.[hash].png         图片资源
```

### 4.3 工具演进

```
2012  Grunt   ─→  任务运行器（手动配置每个转换步骤）
2014  Gulp    ─→  流式构建（比 Grunt 快）
2014  Webpack ─→  bundler 时代（一切皆模块，loader/plugin 生态）
2020  Vite    ─→  ESM 原生支持（开发环境 0 打包，毫秒级启动）
```

**Webpack 的核心贡献**：提出 "一切皆模块" 的理念，通过 Loader 处理非 JS 文件，Plugin 扩展构建流程。

**Vite 的核心创新**：开发环境不打包，利用浏览器原生 ESM；生产环境用 Rollup 打包。

## 5. 包管理器

现代前端项目动辄依赖几百个开源包（Vue 一装，node_modules 里就是上万个文件）。**包管理器（Package Manager）就是负责"把别人的代码装进项目、装对版本、装出一致性"的工具**——npm、yarn、pnpm 都属于这一类。在进入具体工具之前，先建立两个共识：没有它世界有多糟，以及它到底干了哪几件事。

### 5.1 无包管理时代

```text
2010 年前的典型做法：
1. 打开 jquery.com → 下载 jquery.min.js → 拖进项目 lib/ 目录
2. 想用 dayjs？再去官网下载一个 → 手动放对位置
3. 某个库发新版了？重新下载、手动替换、祈祷没改坏
4. 依赖 A 依赖 B、B 又依赖 C？自己顺藤摸瓜一个个找

结果：lib/ 目录里躺着 20 个来路不明的 .js 文件，
     没人知道它们的版本，更没人敢升级
```

### 5.2 核心职责

| 职责 | 一句话 | 对应机制 |
|---|---|---|
| 下载安装 | 一条命令拉取任意开源包 | Registry 远程仓库 |
| 版本管理 | 精确控制"用哪个版本" | 语义化版本（semver：`^` `~` `=`） |
| 依赖解析 | A 依赖 B、B 依赖 C，自动理清 | 依赖树分析 |
| 环境复现 | 团队每个人装出完全相同的结果 | 锁文件（lock file） |
| 脚本执行 | 统一入口运行构建/测试/启动命令 | package.json 的 scripts 字段 |

**通用工作流**（npm / yarn / pnpm 完全一致）：

```text
安装依赖 → 写入依赖清单（package.json）→ 清单 + 锁文件提交 Git
        → 团队任何人 clone 后一条命令还原出完全一致的环境
```

### 5.3 三者关系

三者干同一件事、共享同一个 npm Registry 生态（互相完全兼容），差别只在**安装策略与工程取舍**：

| 工具 | 出场时间 | 一句话人设 |
|---|---|---|
| **npm** | 2010 | 官方亲儿子，随 Node 自带，零门槛默认选择 |
| **yarn** | 2016 | Facebook 出品，用并行安装 + 首创锁文件倒逼 npm 进步 |
| **pnpm** | 2017 | 社区出品，用全局存储 + 硬链接把速度和磁盘做到极致 |

后文三节分别展开，第 9 节给出横向对比与选型建议。

## 6. npm 详解

### 6.1 npm 是什么

**npm（Node Package Manager）** 是随 Node.js 一起安装的**包管理器**，2010 年诞生，是目前世界上最大的软件注册表。它解决一个朴素的问题：**"别人的代码怎么拿进来用、怎么管理版本、怎么带着团队保持一致"**。

npm 这个词其实包含三层含义：

| 层 | 是什么 | 类比 |
|---|---|---|
| npm Registry | 托管 200 万+ 开源包的云端仓库（npmjs.com） | Maven 中央仓库 / PyPI / CocoaPods 仓库 |
| npm CLI | 命令行工具（`npm install` 等） | `git` 命令 / `pod` 命令 |
| package.json | 项目内的依赖清单与脚本配置 | Podfile / requirements.txt |

**最小工作流**（每个前端项目的起点）：

```bash
npm init -y                # 1. 生成 package.json（项目身份证）
npm install vue            # 2. 安装依赖 → 写入 dependencies + 生成 node_modules/
npm install -D vite        # 3. 安装开发依赖（-D = --save-dev）
npm run dev                # 4. 执行 package.json 里的 scripts 脚本
```

```json
// package.json 就是项目的"身份证 + 菜谱"
{
  "name": "my-app",
  "scripts": {
    "dev": "vite",           // npm run dev 实际执行 vite
    "build": "vite build",
    "lint": "eslint src/"
  },
  "dependencies": { "vue": "^3.4.0" },      // 运行时要用的包
  "devDependencies": { "vite": "^5.0.0" }   // 只有开发/构建时用
}
```

**常用命令速查**：

| 命令 | 作用 |
|---|---|
| `npm install` | 按 package.json + 锁文件安装全部依赖 |
| `npm install <pkg>` | 安装某个包并写入 dependencies |
| `npm install -D <pkg>` | 安装为开发依赖（构建工具、linter 等） |
| `npm uninstall <pkg>` | 卸载并从 package.json 移除 |
| `npm update` | 更新依赖到允许范围内的最新版 |
| `npm run <script>` | 执行 scripts 里定义的命令 |
| `npx <pkg>` | 临时执行一个包（不安装到项目），如 `npx husky init` |

> 与其他技术栈对照：npm 之于前端 ≈ Maven/Gradle 之于 Java ≈ pip 之于 Python ≈ CocoaPods/SPM 之于 iOS。后文的"依赖地狱"、锁文件、pnpm，都是在 npm 这块地基上长出来的进阶话题。

### 6.2 依赖地狱

```
项目 A 依赖 lodash@4.17.0
项目 A 同时依赖 dep-b，而 dep-b 依赖 lodash@3.10.0

npm v2：
  node_modules/
    A/
      node_modules/lodash@4.17.0   ← 嵌套，目录超深
    dep-b/
      node_modules/lodash@3.10.0   ← 嵌套，重复安装

npm v3+：
  node_modules/
    lodash@4.17.0                   ← 扁平化（提升到顶层）
    dep-b/
      node_modules/lodash@3.10.0   ← 版本冲突时保留嵌套
```

### 6.3 锁文件机制

```
package.json      → "lodash": "^4.17.0"   语义化范围
package-lock.json → "lodash": "4.17.21"   精确版本（提交到 Git）

# 为什么需要锁文件？
# A 电脑安装时为 4.17.21
# 一周后 ^4.17.0 可能已经更新到 4.17.25
# B 电脑安装时会安装 4.17.25——团队不一致！
# 锁文件确保：所有人安装相同的依赖树
```

### 6.4 依赖类型

```json
{
  "dependencies": {
    "vue": "^3.4.0"        // 生产需要
  },
  "devDependencies": {
    "vite": "^5.0.0",      // 仅开发需要
    "typescript": "^5.3.0",
    "eslint": "^8.0.0"
  },
  "peerDependencies": {
    "vue": "^3.0.0"        // 宿主项目需要安装（插件库常用）
  }
}
```

## 7. yarn 简史

### 7.1 yarn 是什么

**yarn** 是 Facebook 在 2016 年联合 Google、Tilda 等推出的包管理器。诞生背景很有意思：当年 npm（v4 时代）安装慢、输出混乱、**没有锁文件**——同样的 package.json，两台电脑可能装出不同的依赖树。yarn 针对这三点做了彻底重构，反过来倒逼 npm 在 v5 中引入了 `package-lock.json`。

**一句话定位**：yarn 是 npm 的"高性能替代品"，两者生态完全兼容（都从 npm Registry 拉包），只是安装器不同。

### 7.2 解决痛点

| 当年 npm 的问题 | yarn 的解法 |
|---|---|
| 串行安装，慢 | **并行下载** + 全局缓存，速度提升数倍 |
| 版本不确定（依赖树漂移） | **首创 `yarn.lock` 锁文件**，安装结果可复现 |
| 输出日志冗长难读 | 简洁的 emoji 进度输出 |
| 断网不能装包 | **离线模式**：缓存命中即可安装 |

> 2020 年后的 npm（v7+）已经吸收了 yarn 的大部分优点（锁文件、并行、缓存），这也是 yarn 存在感下降的根本原因。

### 7.3 命令与特性

```bash
yarn                 # 等价 npm install
yarn add vue         # 等价 npm install vue
yarn add -D vite     # 等价 npm install -D vite
yarn remove vue      # 等价 npm uninstall vue
yarn dev             # 等价 npm run dev（run 可省略）
```

**杀手级特性 Workspaces（monorepo）**：一个仓库管理多个包，依赖只装一份、包之间直接互相引用——这是大厂（Vue、React、Babel 仓库）选择 yarn 的历史原因，如今 pnpm workspaces 已同样成熟。

### 7.4 版本现状

- **Yarn 1（Classic）**：2016-2019 的主流版本，仍被大量老项目使用，但已停止功能更新；
- **Yarn 2+（Berry）**：2020 年重写，主打 **PnP（Plug'n'Play）**——取消 node_modules 目录，用 `.pnp.cjs` 文件直接映射依赖路径。理念激进但生态兼容问题多，采用率一直不高；
- **现状**：新项目首选已很少是 yarn，常见选择是 **npm（零配置）或 pnpm（更快更严格）**。

## 8. pnpm 详析介绍

### 8.1 pnpm 是什么

**pnpm（performant npm）** 诞生于 2017 年，口号是"快速的、节省磁盘空间的包管理器"。它在 npm 兼容生态的前提下，用两个核心设计同时解决了**磁盘浪费**和**幽灵依赖**两大顽疾，是目前新项目的热门首选（Vue、Vite、Element Plus 官方仓库均在使用）。

### 8.2 内容寻址存储

```
npm/yarn：每个项目独立安装 node_modules（100 个项目 → 100 份依赖副本）
pnpm：    全局存储 + 硬链接（100 个项目 → 1 份存储 + 硬链接）

工作原理：
  1. 全局存储 ~/.pnpm-store 按文件内容寻址（内容相同只存一份）
  2. 项目的 node_modules 里只是指向全局存储的硬链接
  3. 不同项目用到相同版本的包 → 磁盘上只有一份数据

优势：
  1. 磁盘节省 50%+（装得越多省得越多）
  2. 安装速度更快（命中缓存时接近秒装）
  3. 天然支持增量更新（内容寻址，改哪个链接哪个）
```

### 8.3 幽灵依赖

**什么是幽灵依赖（Phantom Dependency）**：

```
你只声明了 vue，但 npm 扁平化后 node_modules 长这样：
  node_modules/
    vue/            ← 你声明的
    lodash/         ← vue 的间接依赖，被"提升"到了顶层
                     ← 你的代码 import lodash 也能跑！

问题：哪天 vue 不再依赖 lodash，你的代码就悄悄崩了
      —— 你 import 了一个从未声明过的"幽灵"
```

**pnpm 的解法**：node_modules **非扁平化**，只有 `package.json` 里声明的包出现在顶层，间接依赖被锁在 `.pnpm` 虚拟目录里——非法引用直接报错，把问题暴露在安装期而不是线上。

### 8.4 命令对照

| 操作 | npm | yarn | pnpm |
|---|---|---|---|
| 安装全部依赖 | `npm install` | `yarn` | `pnpm install` |
| 添加生产依赖 | `npm i vue` | `yarn add vue` | `pnpm add vue` |
| 添加开发依赖 | `npm i -D vite` | `yarn add -D vite` | `pnpm add -D vite` |
| 卸载 | `npm un vue` | `yarn remove vue` | `pnpm remove vue` |
| 运行脚本 | `npm run dev` | `yarn dev` | `pnpm dev` |
| 执行一次性命令 | `npx xxx` | `yarn dlx xxx` | `pnpm dlx xxx` |

## 9. 对比与选型

| 维度 | npm | yarn | pnpm |
|---|---|---|---|
| 出品方 | Node.js 官方 | Facebook（Meta） | 社区（Zoltan Kochan） |
| 锁文件 | package-lock.json | yarn.lock | pnpm-lock.yaml |
| 安装速度 | 中（持续改进） | 快 | 最快 |
| 磁盘占用 | 每项目独立 | 每项目独立 | 全局共享，最省 |
| 依赖严格性 | 扁平化（有幽灵依赖风险） | 扁平化（同左） | 非扁平，最严格 |
| monorepo | 支持较弱 | workspaces 成熟 | workspaces 成熟且更快 |
| 生态兼容 | —— | 完全兼容 | 完全兼容 |

**选型建议**：

1. **个人小项目**：npm 就够——零安装、Node 自带、无心智负担；
2. **团队/新项目**：pnpm——速度、磁盘、严格性三赢，锁文件保证一致性；
3. **老项目**：跟随现有锁文件，不要混用三种工具（一个仓库只认一个包管理器，可用 `packageManager` 字段 + `corepack` 强约束）。

## 11. 速查总表

| 维度 | 工具 | 一句话 |
|---|---|---|
| 模块化 | ESM (`import`/`export`) | 标准答案，浏览器+Node 通用 |
| 构建 | Vite (新) / Webpack | Vite 开发快，Webpack 生态全 |
| 包管理 | pnpm | 最快最省空间，严格依赖 |
| 代码规范 | ESLint + Prettier | 查错 + 格式化 |
| Git | Husky + lint-staged | 提交前自动检查 |
| CI/CD | GitHub Actions / Jenkins | 自动化测试和部署 |

**工程化的本质**：不是某个工具，而是一套**从源码到生产环境的可控、可复现、可优化的流程体系**。
