## 1.案例引入介绍

### 1.1 截然不同的速度

```bash
# 同一个 Vue 3 + TS 项目（200+ 组件）

# Webpack Dev Server
npm run dev    # 启动 12 秒
修改 App.vue   # HMR 更新 2.8 秒 ← 大型项目更慢

# Vite
npm run dev    # 启动 0.4 秒  ← 大项目也不怎么变
修改 App.vue   # HMR 更新 0.03 秒 ← 恒快
```

**Vite 不只是"快一点的 Webpack"，它是完全不同的架构范式。**

### 1.2 开发体验不同

数字本身没有痛感，翻译成一天的开发节奏才有：

| 场景 | Webpack | Vite | 差距含义 |
|---|---|---|---|
| 每天保存 200 次（HMR） | 200 × 2.8s ≈ **9.3 分钟纯等待** | 200 × 0.03s = **6 秒** | 心流被打断 200 次 vs 不断流 |
| 冷启动到可调试 | 12s+ | 0.4s | "泡杯咖啡再回来" vs "秒进" |
| 修改后看到反馈 | 2.8s | 0.03s | 超过 1s 大脑会"切出去"，< 100ms 感觉"即时" |

> **心法**：开发工具的速度不是"省了几秒"，是**保住心流**——HMR 超过 1 秒，大脑就会从代码上下文里"切出去"再"切回来"，一次切换的认知成本远大于等待本身。

### 1.3 三个灵魂拷问

读原理之前，先问自己三个问题——本文 §2 会逐一回答：

**Q1 启动之惑**：为什么 Webpack 启动随项目变大线性变慢（12s → 30s+），而 Vite 启动**几乎和项目大小无关**（0.4s）？

> 提示：Webpack 启动时在做什么"全量工作"？Vite 启动时**根本没编译你的业务代码**。

**Q2 HMR 之惑**：改一个 `App.vue`，Vite 怎么知道**只需要编译这一个文件**，而不用重新处理其他 199 个？

> 提示：浏览器请求粒度变了——从"要一个 bundle"变成"要一个模块"。

**Q3 生产之惑**：开发这么快，生产构建是不是也这么快？

> 提示：**恰恰相反**——生产构建反而是 Vite 流程里相对慢的一环，而且用的不是 esbuild。

### 1.4 两个反直觉预告

在深入原理前，先戳破两个最常见的误解：

**误解一："Vite 快是因为 esbuild"**

**错**。esbuild 只负责预构建（§4）和转译，**真正的核心是浏览器原生 ESM**——是"按需编译"的架构范式快，不是某个工具快。esbuild 换成 swc，范式不变依然快。

**误解二："开发快，生产也快"**

**不一定**。生产构建走的是 Rollup（§2.3 双引擎），且 dev 和 prod 的**行为差异**（依赖预构建 vs 完整打包）是"本地跑得好好的，一上线就翻车"的经典坑来源——§7 构建优化会展开。

### 1.5 数据可信度边界

以上数据基于：Vue 3 + TS 项目、200+ 组件、依赖树中等复杂度（约 30 个 node_modules 直接依赖）、M1 MacBook。你的实际数值会因**依赖树规模、机器性能、代码复杂度**浮动，但**两个趋势恒定**：

1. 项目越大，Webpack 启动/HMR 越慢，Vite 几乎不变；
2. Vite 的 HMR 恒定在 100ms 量级（因为它只编译单文件）。

> **思考题（带着读全文）**：既然"按需编译"这么好，为什么生产环境不直接用它，而要回退到 Rollup 打包？——答案在 §2.3。

## 2. Vite 核心原理

### 2.1 Webpack 为什么慢

```
Webpack 开发模式：

  所有源文件 → 打包成 Bundle → Dev Server → 浏览器加载
  (入口文件 + 依赖递归)    (整个项目)    (一个几百 KB 的 bundle)
  
  项目越大 → 模块越多 → 依赖图越复杂 → 打包越慢
  修改一个文件 → 重新打包 → 重新加载 bundle → 慢
```

**深入一层**：慢的根源是**工作粒度错配**——Bundle 的完整性要求 Webpack 启动前必须递归遍历完整个依赖图（否则产物不闭合），所以启动成本是 O(全部模块)；而 HMR 的失效边界是 bundle 而非单个文件，改 1 个文件也要沿 chunk 依赖链向上重算。**只要"先打包后服务"这个前提不变，怎么优化（缓存/增量）都只是常数级缓解，复杂度上界不会变**。

### 2.2 Vite 为何快

```
Vite 开发模式：

  Dev Server 启动 → 等待浏览器请求
       ↓
  浏览器请求 main.ts
       ↓
  Vite 拦截 → 编译单个 main.ts → 返回
       ↓  main.ts 内部 import { ref } from 'vue'
  浏览器请求 vue 模块
       ↓
  Vite 拦截 → 返回预构建好的 vue
       ↓  main.ts 内部 import App from './App.vue'
  浏览器请求 App.vue
       ↓
  Vite 拦截 → 编译单个 App.vue → 返回

核心差异：Webpack：启动时把所有文件"做成一锅饭"；Vite：来了客人再"按需炒菜"
```

**深入一层**：Vite 不是把编译工作"消灭"了，而是**把成本从"启动时刻"转移到了"每个请求时刻"**——总工作量没变，但被摊薄成了 O(改动模块数)。更关键的是，模块解析的职责交还给了浏览器：浏览器的原生 ESM 加载器天然知道"谁 import 谁"，Vite 只需应答单个请求，所以启动与项目大小无关、HMR 天然精确到单文件——这正是 §1.3 前两问的答案。

### 2.3 双引擎架构

```
开发环境：              生产环境：
┌──────────────┐       ┌──────────────┐
│ 浏览器 ESM    │       │  Rollup      │
│ (原生模块)    │       │ (打包器)     │
└──────┬───────┘       └──────┬───────┘
       │ 按需请求              │ 一次性打包
       ▼                      ▼
  单文件按需编译         所有文件统一打包
  (esbuild 做转译)       (Rollup 成熟稳定)
```

**为什么开发用 esbuild，生产用 Rollup？**

| 对比 | esbuild | Rollup |
|---|---|---|
| 速度 | 极快（Go 语言） | 快（JS 语言） |
| 生态 | 插件有限 | 丰富的 Rollup 插件 |
| 打包 | 不够成熟 | 多年验证的生产级打包 |
| 代码分割 | 弱 | 完善 |
| CSS 处理 | 有限 | 丰富 |

### 2.4 Rollup 是什么

Rollup 是一个**以 ES Module 为第一公民的生产级打包器**（2015 年发布）。三个关键定位：

1. **Tree Shaking 的发明者**——第一个基于 ESM 静态分析实现"摇掉死代码"的打包器（Webpack 的 Tree Shaking 正是借鉴它）；
2. **产物最干净**——输出接近手写的 ESM 代码，无运行时 hack，所以成为**库开发**的事实标准（Vue、React 自身的发行包都是 Rollup 打出来的）；
3. **Vite 的生产引擎**——`vite build` 的底层就是 Rollup，产物的代码分割、摇树、hash 命名质量都来自它。

> **回答 §1.5 思考题**：既然"按需编译"这么好，为什么生产不直接用？——因为生产的目标和开发**完全相反**：开发要"快反馈"，生产要"少请求 + 可缓存 + 兼容旧浏览器"。生产必须把几百个 ESM 请求**合并成少数几个 bundle**（减少瀑布请求）、做完整 Tree Shaking、生成 contenthash 长缓存文件名——这些都是"打包器"的活，所以 Vite 生产回退到成熟稳定的 Rollup。（Vite 5+ 实验性的 Rolldown 正是"用 Rust 重写 Rollup"来统一双引擎，说明两者迟早合一，但架构思想不变。）

**一句话总结**：**esbuild 管"快"（开发转译/预构建），Rollup 管"好"（生产产物质量）**——双引擎各司其职，这正是 Vite 架构设计的精髓。

## 3.配置文件详解

先看全貌，然后逐块拆开讲：

```typescript
// vite.config.ts —— 五大配置块总览
export default defineConfig({
    plugins: [...],   // ① 插件：扩展 Vite/Rollup 能力
    resolve: {...},   // ② 模块解析：路径别名等
    server: {...},    // ③ 开发服务器：端口/代理
    build: {...},     // ④ 生产构建：分包/sourcemap
    css: {...},       // ⑤ CSS：预处理器选项
})
```

### 3.1 plugins：插件体系

```typescript
import vue from '@vitejs/plugin-vue'
import AutoImport from 'unplugin-auto-import/vite'
import Components from 'unplugin-vue-components/vite'
import { visualizer } from 'rollup-plugin-visualizer'

export default defineConfig({
    plugins: [
        vue(),                                          // Vue SFC 编译：.vue 单文件 → JS
        AutoImport({
            imports: ['vue', 'vue-router', 'pinia'],    // 自动导入 ref/computed 等
            dts: 'src/auto-imports.d.ts'                // 生成类型声明，IDE 才有提示
        }),
        Components({
            dts: 'src/components.d.ts'                  // 组件自动注册：免手写 import
        }),
        visualizer({ open: true })                      // 构建后自动打开体积分析报告
    ],
})
```

**要点**：

- **Vite 插件 = Rollup 插件的超集**——大部分 Rollup 插件直接可用（如 `rollup-plugin-visualizer`），这就是 §2.3 双引擎共享生态的实现方式；
- **`enforce: 'pre' | 'post'`** 控制插件执行顺序（pre 在 Vite 核心插件前，post 在后），等价于 Webpack 的 `enforce`；
- `AutoImport`/`Components` 的 `dts` 必须配——否则 `ref` 不 import 就用，TS 直接报错。

### 3.2 resolve.alias：路径别名

```typescript
import { resolve } from 'path'

export default defineConfig({
    resolve: {
        alias: {
            '@': resolve(__dirname, 'src'),
            '@components': resolve(__dirname, 'src/components'),
            '@views': resolve(__dirname, 'src/views')
        }
    }
})
```

**要点与坑**：

- **好处**：`import x from '@/utils/request'` 替代 `../../utils/request`——目录重构不再牵一发动全身；
- **⚠️ 必须同步 tsconfig.json**——alias 只管构建器，TS 不认识照样飘红：

```json
// tsconfig.json
{
    "compilerOptions": {
        "paths": {
            "@/*": ["src/*"],
            "@components/*": ["src/components/*"],
            "@views/*": ["src/views/*"]
        }
    }
}
```

- **ESM 项目没有 `__dirname`**——用 `fileURLToPath(new URL('./src', import.meta.url))` 代替（本仓库 mini-player 的 vite.config.ts 就是这么写的）。

### 3.3 server：开发服务器与代理

```typescript
export default defineConfig({
    server: {
        port: 3000,
        host: true,          // 监听 0.0.0.0 —— 真机通过局域网 IP 访问
        open: true,          // 启动后自动打开浏览器
        proxy: {
            '/api': {
                target: 'http://localhost:8080',
                changeOrigin: true,
                rewrite: (path) => path.replace(/^\/api/, '')
            }
        }
    }
})
```

**proxy 的三个参数各管一件事**：

| 参数 | 作用 | 什么时候需要 |
|---|---|---|
| `target` | 把 `/api/xxx` 转发到 `http://localhost:8080/api/xxx` | 前后端分离联调 |
| `changeOrigin: true` | 请求头 Host 改为 target 的域名 | 后端做了 Host 校验（如网关/虚拟主机），不改会被拒 |
| `rewrite` | 改写路径：`/api/user` → `/user` | **后端路由里没有 `/api` 前缀**时必须加，否则 404 |

**要点**：

- `host: true` + `--host` 的价值在**真机调试**——手机连同一 WiFi 访问 `http://<电脑IP>:3000`（配合 §4.6 真机代理食用更佳）；
- 代理解决的是**开发期跨域**：浏览器同源策略只约束浏览器，服务器转发不受限。生产环境的跨域靠 Nginx / CORS，**proxy 配置不会进产物**；
- WebSocket 代理要加 `ws: true`（如本地起 WebSocket 服务时）。

### 3.4 build：生产构建与分包

```typescript
export default defineConfig({
    build: {
        outDir: 'dist',
        sourcemap: 'hidden',        // 详见 §5：'hidden' 比 false/true 更优
        rollupOptions: {
            output: {
                manualChunks: {     // 分包策略
                    'vue-vendor': ['vue', 'vue-router', 'pinia'],
                    'ui-vendor': ['element-plus']
                }
            }
        },
        chunkSizeWarningLimit: 1000 // 单 chunk 警告阈值（KB）
    }
})
```

**核心是 manualChunks——为什么要手动分包？**

```text
不分包：业务代码 + vue + element-plus 全在一个 index.js 里
        → 改一行业务代码 → 整个 bundle hash 变化 → 用户重新下载 1MB+

分包后：vue-vendor.xxx.js（几乎不变，长缓存命中）
        ui-vendor.xxx.js（升级 UI 库才变）
        index.abc123.js（业务代码，经常变，但只有几十 KB）
        → 用户日常更新只下载业务小包，vendor 走浏览器缓存
```

**要点**：

- **分包的本质是"按变化频率分组"**——变化频率差异越大的代码越该拆开（呼应 [`05.前端性能优化`](https://yccoding.com/pages/web-perf/) 缓存策略篇）；
- `sourcemap: 'hidden'`：生成 map 但不公开（报错还原走监控平台），详见 §5；
- `chunkSizeWarningLimit` 只是**调报警阈值**，不是优化——真想减小 chunk 请做代码分割（动态 import）。

### 3.5 css：预处理器全局注入

```typescript
export default defineConfig({
    css: {
        preprocessorOptions: {
            scss: {
                // 每个 scss/vue 文件编译前自动注入这段
                additionalData: `@use "@/styles/variables.scss" as *;`
            }
        }
    }
})
```

**要点**：

- **解决什么**：变量/mixin 不用每个文件手写 `@use`——注入一次，全局生效；
- **⚠️ 只注入"无输出"的文件**（变量、mixin、function）——如果注入的是含样式规则的文件，**每个组件都会重复产出这份 CSS**，产物膨胀；
- Dart Sass 新版用 `@use ... as *`，旧语法 `@import` 已废弃（deprecation 警告）；
- Less/Stylus 同理，换对应 key 即可（`less: { additionalData: ... }`）。

## 4.Vite 最核心的优化

### 4.1 为何需要预构建

```
问题：import { ref } from 'vue'
  vue 在 node_modules 下有 500+ 个内部模块文件
  如果直接按需加载，浏览器要发 500+ 个 HTTP 请求——爆炸

Vite 的解决方案：预构建
  1. 启动时扫描 node_modules 依赖
  2. 将 500+ 个文件合并为少量 ESM 包
  3. 浏览器只需请求 1~2 个文件
```

**更深一层**：爆炸的根源是"串行瀑布"——浏览器必须先拿到模块 A 的代码才知道要请求 B，依赖树多深、请求就排多深，再叠加浏览器同域名只有 6 条并发连接的限制。此外很多 npm 包是 CommonJS 格式，浏览器只认 ESM，**不预构建翻译根本跑不起来**——所以预构建既解决"请求数爆炸"，也解决"格式不通"。

```
预构建过程：
  node_modules/vue/
    dist/vue.runtime.esm-bundler.js
    packages/reactivity/src/...
    packages/runtime-core/src/...
    ...500+ 个模块
        ↓ esbuild 打包
  node_modules/.vite/deps/
    vue.js     (一个文件，包含所有 vue 模块)
```

### 4.2 自定义预构建

```typescript
export default defineConfig({
    optimizeDeps: {
        include: ['lodash-es', 'dayjs'],          // 强制预构建
        exclude: ['your-local-package'],           // 排除（开发中的本地包）
        esbuildOptions: {
            target: 'es2020'                       // 预构建目标
        }
    }
});
```

## 5. Vite vs Webpack：全维度对比

### 5.1 架构差异

```
Webpack：
  Source → Bundle → Dev Server → 浏览器加载 bundle
  
  所有模块都先打包，浏览器只加载一个（或几个）bundle
  优点：成熟的打包策略
  缺点：项目越大启动越慢

Vite：
  Dev Server 启动 → 浏览器按需请求 → 单文件编译返回

  不打包，利用浏览器原生 ESM
  优点：启动和 HMR 极快
  缺点：对 ESM 不支持的旧浏览器无效（但生产构建用 Rollup 可覆盖）
```

### 5.2 速度对比（200+ 组件项目）

| 指标 | Webpack 5 | Vite 5 | 倍数 |
|---|---|---|---|
| 冷启动 | 12~30s | 0.3~1.5s | 10~30× |
| HMR | 1~5s | <50ms | 20~100× |
| 生产构建 | 45~120s | 25~60s | 1.5~2× |

### 5.3 选型建议

```
你的场景？
├── 新项目（Vue 3 / React 18+）→ Vite（强烈推荐）
├── 旧项目维护（Vue 2 + Webpack 生态深绑定）→ 维持 Webpack
├── 需要兼容 IE11 → Webpack（Vite 不支持）
├── 微前端 / Module Federation → Webpack（Vite 当前较弱）
└── 组件库开发 → Vite（library mode 简单易用）
```

## 6. 环境变量

```bash
# .env                  # 所有环境
VITE_APP_TITLE=我的应用

# .env.development      # npm run dev
VITE_API_URL=http://localhost:8080/api

# .env.production       # npm run build
VITE_API_URL=https://api.example.com
```

```typescript
// 使用
console.log(import.meta.env.VITE_API_URL)
console.log(import.meta.env.MODE)      // 'development' | 'production'
console.log(import.meta.env.DEV)       // true/false
console.log(import.meta.env.PROD)      // true/false

// 类型声明
// env.d.ts
/// <reference types="vite/client" />
interface ImportMetaEnv {
    readonly VITE_API_URL: string
}
```

**注意**：只有 `VITE_` 前缀的变量才会暴露给前端代码——这是一种安全机制。

```typescript
build: {
    // 目标浏览器
    target: 'es2020',              // 现代浏览器默认

    // 分包
    rollupOptions: {
        output: {
            manualChunks: {
                'vue-vendor': ['vue', 'vue-router'],
                'vendor': ['lodash-es', 'dayjs']
            }
        }
    },

    // CSS 代码分割
    cssCodeSplit: true,
    cssMinify: 'lightningcss',    // 比 cssnano 快 2~3×

    // 压缩
    minify: 'esbuild',             // 或 'terser'
}
```

## 8. 速查表

| 特性 | Vite | Webpack |
|---|---|---|
| 冷启动** | < 1s | 10~30s |
| HMR** | < 50ms | 1~5s |
| 构建** | 快 | 较快 |
| 生态插件 | 快速增长 | 最丰富 |
| 学习曲线 | 低（零配置可用） | 中 |
| 旧浏览器 | 仅生产（Rollup） | 全链路支持 |
| 配置文件 | `vite.config.ts` | `webpack.config.js` |
| 核心原理 | ESM + esbuild + Rollup | 打包 + Loader/Plugin |

> \*\* 数值取决于项目规模

**Vite 一句话**：开发环境利用浏览器原生 ESM 实现零打包启动与毫秒级 HMR，生产环境用 Rollup 保证成熟稳定的打包质量。
