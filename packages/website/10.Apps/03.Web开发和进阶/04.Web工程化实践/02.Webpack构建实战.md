## 1.为何需要Webpack

一句话回答：**浏览器只认 HTML / CSS / JS，而现代前端工程里 80% 的代码浏览器"看不懂"——Webpack 就是中间那个"翻译 + 打包 + 优化"的角色。** 下面从一个真实项目出发，把"不用它会怎样、用了它会怎样"讲透。

**先看一个通俗类比：做一桌年夜饭**——Webpack 就是你的"后厨总管"。你要端出一桌菜（浏览器能跑的产物）。从**主菜**开工（`entry` 入口），主菜要配菜、配菜要酱汁、酱汁要基础食材——这条"食材链"就是**依赖图**。而后的每个知识点，都能在这张餐桌上找到位置：

| 年夜饭里的事 | Webpack 知识点 |
|---|---|
| 生的、冻的、腌的食材要先洗切解冻才能下锅 | **Loader**：把 TS/Vue/SCSS 加工成浏览器认识的 JS/CSS |
| 光炒菜不够，还要摆盘、封盒、贴标签 | **Plugin**：压缩、生成 HTML、提取 CSS |
| 20 道菜一口气做完太慢，按上菜节奏分批做 | **代码分割**：首屏只加载需要的那部分 |
| 客人说某道菜咸了，只重做那道，不动整桌 | **HMR**：只替换变化的模块，页面状态不丢 |
| 柜里 100 罐调料今晚只用 3 罐，只拿这 3 罐 | **Tree Shaking**：删掉未使用的代码 |
| 每道菜贴"名字 + 出锅时间"，没变的菜不重做 | **contenthash 缓存**：内容不变就不重新下载 |

记住这张餐桌，后文每一节都是在把它翻译成真实代码。

### 1.1 从 Vue 项目说起

```bash
src/
  main.ts              # 入口
  App.vue              # Vue 组件
  components/
    BaseButton.vue
    UserCard.vue
  styles/
    global.scss         # SCSS 预处理器
  assets/
    logo.svg            # SVG 图标
    bg.png              # 大图

# 浏览器能运行这些吗？
# main.ts           → 需要编译 TS
# *.vue             → 需要编译 SFC（单文件组件）
# global.scss       → 需要编译 SCSS → CSS
# logo.svg / bg.png → 需要转为 URL 或 base64
# import { ref }    → 需要解析 vue 模块路径
```

### 1.2 手动构建会怎样

假设完全没有构建工具，上面这个项目要靠"人肉"跑起来，每一步都是灾难：

| 环节 | 手动做法 | 痛点 |
|---|---|---|
| TypeScript | 手动 `tsc` 逐个编译，产物另存 | 每次改代码都要手动跑，容易忘、容易脏 |
| Vue 组件 | 手写 `template` 字符串或 render 函数替代 SFC | 丢失单文件组件的开发体验，模板无法预编译优化 |
| SCSS | 手动 `sass global.scss global.css` | 编译产物和源码两套文件，改错地方是常态 |
| 图片资源 | 手动转 base64 或算相对路径 | 尺寸阈值全靠感觉，大图内联直接拖垮首屏 |
| 模块引用 | `<script>` 按依赖顺序手写几十个标签 | **顺序错一个就白屏**；全局变量互相污染（没有模块作用域） |
| 第三方库 | 手动下载 min.js 放进 lib/ 目录 | 版本升级全靠复制粘贴，依赖关系无人管理 |
| HTTP 加载 | 页面发出 50+ 个文件请求 | 请求瀑布流，首屏时间不可接受 |
| 上线前 | 手动压缩、手动改文件名防缓存 | 漏一步就是线上事故 |

> 历史注脚：2012 年前后社区用 Grunt/Gulp 编排这些"任务"，但它们只解决"**自动化**"，不解决"**依赖关系**"——脚本该按什么顺序拼、模块之间谁引用谁，依然要人管。Webpack 的突破在于从"任务流"转向"**依赖图**"：它把每个文件当作模块，从入口出发递归分析 `import`/`require`，自动理清所有依赖关系。

### 1.3 用了 Webpack 会怎样

同样的项目，加上 Webpack 后开发与发布各只剩**一条命令**：

```bash
npm run dev     # 开发：编译 + 起本地服务 + 热更新
npm run build   # 发布：编译 + 打包 + 压缩 + 加 hash
```

前后对比：

| 维度 | 不用 Webpack | 用了 Webpack |
|---|---|---|
| 文件形态 | 源码直接给浏览器，多数跑不起来 | 100+ 个异构文件 → 3~5 个浏览器完美运行的静态文件 |
| 模块化 | 手写 script 顺序、全局变量 | 直接写 `import`，依赖自动解析 |
| 新语言/新语法 | 用不了（浏览器不认） | TS / SCSS / 新 ES 特性全部可用（Loader 转译） |
| 开发体验 | 改一行 → 手动编译 → 手动刷新 | 保存即热更新（HMR），页面状态不丢 |
| 加载性能 | 50+ 个请求瀑布流 | 合并打包 + 代码分割 + gzip，首屏可量化优化 |
| 缓存策略 | 手动改文件名防缓存 | 文件名自动带 `contenthash`，内容不变就不重新下载 |
| 上线质量 | 手动压缩，靠自觉 | 自动压缩/摇树/删 console，流程可复现 |

**Webpack 的职责**：将 100+ 个异构文件，构建为浏览器能完美运行的 3~5 个静态文件。

### 1.4 Webpack 核心功能

| 功能 | 解决什么问题 | 关键配置 |
|---|---|---|
| 模块打包 | 把散落文件按依赖图合并为产物 | `entry` + `output` |
| Loader 转译 | 让浏览器"看懂" TS/Vue/SCSS 等异构文件 | `module.rules` |
| Plugin 扩展 | 压缩、生成 HTML、提取 CSS 等构建增强 | `plugins` + Tapable 钩子 |
| 代码分割 | 按需加载 + 长缓存，降低首屏成本 | `optimization.splitChunks` |
| HMR 热更新 | 保存即生效且保留页面状态 | `devServer.hot` + WebSocket 推送 |
| Tree Shaking | 删除未使用代码，减小产物体积 | `usedExports` + `sideEffects: false` |
| 文件指纹与缓存 | contenthash 实现精准的浏览器缓存 | `[contenthash:8]` + `cache.type: 'filesystem'` |
| Dev Server | 本地服务 + 代理，模拟线上环境 | `devServer`（`proxy` / `historyApiFallback`） |

### 1.5 Webpack 的定位

- **vs Grunt/Gulp**：它们是"任务流"（按配置依次执行任务），Webpack 是"模块打包器"（以依赖图为中心组织一切）——前者管流程，后者管依赖。
- **vs Rollup**：Rollup 更适合打包纯 JS 库（产物干净），Webpack 更适合打包**应用**（资源、分割、HMR 生态全）。
- **vs Vite**：Vite 用"浏览器原生 ESM + esbuild 预构建"让开发态免打包，但**生产构建底层就是 Rollup**。理念不同，解决的仍是同一类问题，详见下一篇 [03.Vite构建实战](https://yccoding.com/pages/web-vite/)。

> 学 Webpack 的真正收益不是背配置，而是理解"**前端为什么需要编译**"这套心智模型——换到任何新构建工具（Vite / Rspack / Turbopack）上，这套模型都能直接迁移。

## 2. Webpack 核心概念

### 2.1 从依赖图开始

```
Webpack 从 Entry 开始，递归构建模块依赖关系：

    main.ts ─┬── App.vue ─┬── BaseButton.vue
             │            ├── UserCard.vue
             │            └── global.scss → _variables.scss
             ├── vue (node_modules)
             ├── vue-router (node_modules)
             └── utils/format.ts → dayjs (node_modules)

这张"依赖图"告诉 Webpack：
  - 哪些模块需要被打包（所有被引用的模块）
  - 模块顺序是什么（入口→第一层→第二层→...）
  - 哪些可以拆分成单独文件（代码分割）
```

### 2.2 四大核心配置

```javascript
// webpack.config.js
module.exports = {
    // 1. Entry：告诉 Webpack 从哪里开始构建
    entry: './src/main.ts',

    // 2. Output：产物输出到哪里
    output: {
        path: path.resolve(__dirname, 'dist'),
        filename: 'js/[name].[contenthash:8].js',  // 文件名 + 哈希
        clean: true                                 // 清除上次构建
    },

    // 3. Loader：处理非 JS 文件（TS/Vue/SCSS/图片）
    module: {
        rules: [
            { test: /\.ts$/,  use: 'ts-loader' },           // TS → JS
            { test: /\.vue$/, use: 'vue-loader' },          // Vue SFC
            { test: /\.scss$/, use: ['style-loader','css-loader','sass-loader'] },
            { test: /\.(png|svg)$/, type: 'asset' },        // 图片资源
        ]
    },

    // 4. Plugin：扩展 Webpack 构建能力（压缩/提取CSS/生成HTML/热更新）
    plugins: [
        new HtmlWebpackPlugin({ template: './index.html' }),
        new MiniCssExtractPlugin({ filename: 'css/[name].[hash].css' })
    ]
};
```

**一张图看懂 Loader vs Plugin**：

```
Loader：转换器（一对一或链式）
  输入 A 类型文件 → Loader 转换 → 输出 B 类型文件
  例：scss → sass-loader → css-loader → style-loader → DOM <style>

Plugin：增强器（全局）
  在构建各阶段注入逻辑——开始、结束、编译中、输出前……
  例：压缩 JS、生成 HTML、提取 CSS、复制静态资源
```

### 2.3 模式与调试

`mode` 决定了 Webpack "为谁构建"——这是四大配置之外最基础的一个：

```javascript
module.exports = {
    mode: 'production'   // 'development'（开发）| 'production'（生产）| 'none'（原始）
};
```

| | development | production |
|---|---|---|
| 代码压缩 | ❌（要可读、要快） | ✅ Terser 自动压缩 |
| Tree Shaking | ❌ | ✅ 自动开启 |
| SourceMap | 完整（方便调试） | 默认隐藏（防源码泄露） |
| 构建速度 | 快（跳过优化） | 慢（优化全开） |

**调试打包后代码靠 `devtool`（SourceMap 策略）**：

```javascript
module.exports = {
    // 开发推荐：速度快、按行映射
    devtool: 'eval-cheap-module-source-map',
    // 生产可选：不把 map 发到线上，仅在报错上传时用
    // devtool: 'hidden-source-map'
};
```

### 2.4 路径别名设置

Vue 项目里满屏的 `@/api/user`、`@/styles/variables.scss`，`@` 就来自这里：

```javascript
module.exports = {
    resolve: {
        // import 时可以省略这些后缀：import App from './App'
        extensions: ['.ts', '.vue', '.js', '.json'],
        alias: {
            '@': path.resolve(__dirname, 'src')   // '@/api/user' → 'src/api/user'
        }
    }
};
```

> 注意：TS 项目还要在 `tsconfig.json` 里配 `compilerOptions.paths` 同步别名，否则编辑器会报"找不到模块"。

### 2.5 构建流程一览

把前面的配置串成一条流水线，Webpack 的一次构建大致走五步：

```
① 初始化       读取 webpack.config.js → 创建全局唯一的 Compiler 对象
② 构建依赖图    从 Entry 递归读取文件，每个文件经过 Loader 链"翻译"成模块
③ 封装 chunk   按规则把模块组合成 chunk（入口 chunk / 异步 chunk / 公共 chunk）
④ 优化         Tree Shaking → 代码分割 → 压缩（production 模式的重头戏）
⑤ 输出 emit    把 chunk 写成 dist 里的静态文件
```

`npm run dev` 和 `npm run build` 跑的就是这条流水线的两种跑法：

| | `npm run dev` | `npm run build` |
|---|---|---|
| 编译范围 | 增量（首次全量，之后只编译变更模块） | 每次全量 |
| 产物位置 | **内存**（不写 dist，改完即失效） | 磁盘 `dist/`，长期可用 |
| 优化开关 | 跳过压缩/摇树（快是第一目标） | 压缩 + Tree Shaking + 分割全开 |
| SourceMap | 完整，方便浏览器调试 | 按需隐藏，防源码泄露 |
| 进程行为 | 编译完不退出 → 起 DevServer 常驻、监听文件变化触发 HMR | 写完产物即退出 |

所以"dev 快、build 慢"不是性能差距，而是**设计取舍**：dev 为开发体验牺牲优化，build 为线上质量牺牲时间。

**Plugin 的工作机制**就藏在这条流水线里：`Compiler` 和 `Compilation` 对象上挂满了各阶段的**钩子（Tapable）**——初始化、编译中、优化前、输出前……Plugin 就是在某个钩子上注册回调，"搭便车"介入构建过程。理解了这张图，§4 手写 Plugin 就是水到渠成。

## 3. Loader 深入

### 3.1 链式调用原理

```
.scss 文件处理流程：

1. sass-loader     → 将 SCSS 编译为 CSS 字符串
2. css-loader      → 解析 CSS 中的 @import / url()，返回 CSS 模块
3. style-loader    → 将 CSS 注入 DOM（<style> 标签）
   或 MiniCssExtractPlugin.loader → 提取为独立 .css 文件

链式规则：从后往前执行（右→左，或下→上）
use: ['style-loader', 'css-loader', 'sass-loader']
     ↑ 最后执行       ↑             ↑ 先执行
```

### 3.2 常用 Loader 速查

| Loader | 作用 | 配置示例 |
|---|---|---|
| `ts-loader` | TS→JS（使用 tsc 编译） | `use: 'ts-loader'` |
| `babel-loader` | JS 语法降级（不检查类型） | `use: { loader: 'babel-loader', options: { presets: ['@babel/preset-env'] } }` |
| `vue-loader` | Vue SFC 编译 | 配合 `VueLoaderPlugin` |
| `css-loader` | 解析 CSS import/url | `options: { modules: true }` 开启 CSS Modules |
| `sass-loader` | SCSS/SASS → CSS | 需要 `dart-sass` 或 `node-sass` |
| `postcss-loader` | Autoprefixer/Tailwind 等 | `postcss.config.js` |
| `asset`(内置) | 图片/字体复制或内联 | `type: 'asset', parser: { dataUrlCondition: { maxSize: 8*1024 } }` |

### 3.3 核心实战配置

```javascript
// 完整的 module.rules 配置
module: {
    rules: [
        // TypeScript
        {
            test: /\.tsx?$/,
            exclude: /node_modules/,
            use: {
                loader: 'ts-loader',
                options: {
                    transpileOnly: true,      // 仅转译不检查（快），配合 fork-ts-checker-plugin
                    appendTsSuffixTo: [/\.vue$/]
                }
            }
        },
        // Vue SFC
        {
            test: /\.vue$/,
            use: 'vue-loader'
        },
        // SCSS
        {
            test: /\.scss$/,
            use: [
                isDev ? 'style-loader' : MiniCssExtractPlugin.loader,
                'css-loader',
                {
                    loader: 'sass-loader',
                    options: {
                        additionalData: `@import "@/styles/variables.scss";`
                    }
                }
            ]
        },
        // 图片处理
        {
            test: /\.(png|jpe?g|gif|svg|webp)$/i,
            type: 'asset',          // Webpack 5 内置 Asset Module
            parser: {
                dataUrlCondition: {
                    maxSize: 8 * 1024   // < 8KB → base64 内联
                }
            }
        }
    ]
}
```

## 4. Plugin 深入

### 4.1 常用 Plugin 速查

| Plugin | 作用 | 核心原理 |
|---|---|---|
| `HtmlWebpackPlugin` | 生成 HTML，自动注入打包后的 JS/CSS | 钩在 `emit` 阶段：读模板渲染 HTML，从 compilation 拿入口 chunk（含 hash 文件名）注入 `<script>`/`<link>` |
| `MiniCssExtractPlugin` | 提取 CSS 为独立文件 | Loader 把 CSS 模块化，Plugin 在产出 chunk 时把 CSS 模块合并成 `.css` 文件——才能做 contenthash 长缓存 |
| `DefinePlugin` | 注入编译时常量（如 `process.env.NODE_ENV`） | 编译期纯文本替换 + 配合 Terser 死代码消除，摇掉 `"production"` 之外的分支 |
| `CopyWebpackPlugin` | 复制静态资源到 dist | 绕过 module graph 和 Loader 管线，`emit` 阶段原样写出——零转换开销 |
| `ForkTsCheckerWebpackPlugin` | 独立进程做 TS 类型检查（不阻塞构建） | fork 独立进程跑 `tsc --noEmit`，主进程只转译，检查与构建并行 |
| `TerserPlugin` | JS 压缩（Webpack 5 内置） | 基于 AST 做空白压缩 / 标识符混淆 / 死代码删除，多 worker 并行 |
| `CssMinimizerPlugin` | CSS 压缩 | 基于 postcss AST（cssnano）压缩规则，与 Terser 同一套并行调度 |

### 4.2 核心配置实战

```javascript
plugins: [
    // 生成 HTML
    new HtmlWebpackPlugin({
        template: 'public/index.html',
        favicon: 'public/favicon.ico',
        inject: true                       // 自动注入 script/css
    }),

    // CSS 提取
    new MiniCssExtractPlugin({
        filename: 'css/[name].[contenthash:8].css',
        chunkFilename: 'css/[id].[contenthash:8].css'
    }),

    // 编译时环境变量
    new webpack.DefinePlugin({
        __VUE_OPTIONS_API__: JSON.stringify(true),
        __VUE_PROD_DEVTOOLS__: JSON.stringify(false)
    })
]
```

### 4.3 手写最简 Plugin

有了 §2.5 的流水线心智模型，Plugin 的真身其实非常朴素：**一个带 `apply` 方法的类**，在钩子上注册回调即可。下面写一个"输出前打印产物清单"的插件：

```javascript
// plugins/LogPlugin.js
class LogPlugin {
    apply(compiler) {                          // compiler：全局唯一的构建环境
        // 在"写入 dist 之前"的 emit 钩子上注册异步回调
        compiler.hooks.emit.tapAsync('LogPlugin', (compilation, callback) => {
            const files = Object.keys(compilation.assets);   // 本次要输出的所有文件
            console.log('本次将输出：', files);
            callback();                        // 异步钩子必须回调，否则构建卡住
        });
    }
}

// webpack.config.js
plugins: [new LogPlugin()]
```

三个关键角色一句话记住：

| 角色 | 是什么 | 类比（§1 年夜饭） |
|---|---|---|
| `Compiler` | 全局唯一的构建环境，从初始化活到输出 | 后厨总管 |
| `Compilation` | **一次**编译的资源集合（watch 模式下会有多轮） | 本轮做好的那桌菜 |
| `hooks.emit` | 输出前的钩子时机（还有 compile / done 等几十个） | "菜出锅前"这个时间点 |

## 5. 代码分割（Code Splitting）

> 代码分割不是某一个配置，而是三种方式各管一层：**懒加载**管"按需加载"，**多入口**管"多页面"，**splitChunks** 管"公共复用"。实战中三者经常同时出现。

### 5.1 动态导入懒加载（最常用）

用 `import()` 函数代替静态 `import`，被导入的模块会**自动拆成独立文件**，用到时才加载——Vue Router 的路由懒加载就是它的标配应用：

```javascript
// 静态导入：User.vue 会被打进主包，首屏就要下载
import User from './views/User.vue';

// 动态导入：User.vue 单独打包成 user.js，访问 /user 时才请求
const routes = [
    {
        path: '/user',
        component: () => import(/* webpackChunkName: "user" */ './views/User.vue')
    }
];
```

`/* webpackChunkName: "user" */` 魔法注释可以给拆出的文件命名，否则是 `1.js`、`2.js` 这种无意义编号。

### 5.2 多入口分割

多页面应用（MPA）给每个页面一个入口，各自打出独立产物：

```javascript
module.exports = {
    entry: {
        app: './src/main.ts',        // 主站
        admin: './src/admin.ts'      // 后台管理——用户不会同时用两者
    },
    output: {
        filename: 'js/[name].[contenthash:8].js'   // [name] = app / admin
    }
};
```

### 5.3 公共模块提取（splitChunks）

前两种解决"拆出独立文件"，`splitChunks` 解决"多个 chunk 都引用了同一份代码"——把它提取成公共文件，只下载一次：

```javascript
optimization: {
    splitChunks: {
        chunks: 'all',          // 所有类型的 chunk 都优化
        cacheGroups: {
            // 方式 1：Vue 全家桶独立 chunk
            vueVendor: {
                test: /[\\/]node_modules[\\/](vue|vue-router|pinia)[\\/]/,
                name: 'vue-vendor',
                priority: 10
            },
            // 方式 2：其他第三方库
            vendor: {
                test: /[\\/]node_modules[\\/]/,
                name: 'vendor',
                priority: 5
            },
            // 方式 3：公共模块（被 3+ chunks 引用的模块提取）
            common: {
                minChunks: 3,
                name: 'common',
                priority: 1,
                reuseExistingChunk: true
            }
        }
    }
}
```

**代码分割的效果**：

```
原来：app.js (800KB)     ← 修改一行代码，用户重新加载 800KB

分割后：
  vendor.js     (300KB)  ← 第三方库变化少，强缓存
  vue-vendor.js (150KB)  ← Vue 版本稳定，强缓存
  common.js     (100KB)  ← 公共模块
  app.js        (250KB)  ← 业务逻辑经常变
  # 修改业务代码，用户只需重新加载 250KB
```

## 6. HMR 热更新原理

### 6.1 工作原理

```
HMR 完整流程：

1. Webpack Dev Server 启动 WebSocket 服务
2. 浏览器加载页面时，自动注入 HMR Runtime（小型 WebSocket 客户端）
3. 开发者修改代码 → Webpack 重新编译 → 计算变化文件的最小依赖图
4. WebSocket 推送变化给浏览器：
   { type: "hash", hash: "abc123" }          ← 新构建的 hash
   { type: "ok" }                             ← 构建完成
   { type: "update", modules: {...} }        ← 变化的模块
5. HMR Runtime 替换变化模块（不刷新页面）
   ├── CSS 变化 → 只替换 <style> 内容（状态保留）
   ├── JS 变化 → 替换模块 + 重新执行（Vue 组件保留状态）
   └── 无法 HM 的模块 → 降级为整页刷新
```

### 6.2 配置

```javascript
devServer: {
    port: 3000,
    hot: true,              // 开启 HMR
    open: true,             // 自动打开浏览器
    historyApiFallback: true, // SPA History 模式兜底
    proxy: {                // API 代理
        '/api': 'http://localhost:8080'
    }
}
```

## 7. Tree Shaking 与打包优化

### 7.1 Tree Shaking 原理

```javascript
// math.js
export const add = (a, b) => a + b;
export const sub = (a, b) => a - b;   // 未使用

// app.js
import { add } from './math';          // 只引入 add

// 构建结果：
// sub 函数不会出现在最终产物中 ← Tree Shaking 的效果

// 前提条件：
// 1. 使用 ES Module（静态导入）而非 CommonJS
// 2. 生产模式（mode: 'production'）
// 3. package.json 的 sideEffects: false
```

### 7.2 完整优化配置

```javascript
optimization: {
    minimize: true,
    minimizer: [
        new TerserPlugin({
            terserOptions: {
                compress: {
                    drop_console: true,     // 删除 console
                    drop_debugger: true     // 删除 debugger
                }
            }
        }),
        new CssMinimizerPlugin()             // CSS 压缩
    ],
    splitChunks: { /* 如上述 5.1 配置 */ },
    runtimeChunk: 'single'                   // Runtime 代码单独提取
}
```

### 7.3 打包分析

优化之前先"体检"——`webpack-bundle-analyzer` 把产物体积画成一张矩形树图，谁大谁一目了然：

```bash
npm i -D webpack-bundle-analyzer
```

```javascript
const { BundleAnalyzerPlugin } = require('webpack-bundle-analyzer');

plugins: [
    new BundleAnalyzerPlugin()   // npm run build 后自动打开 http://localhost:8888
]
```

**看图三问**：

1. 最大的方块是谁？→ 大块 `node_modules` 考虑按需引入（如 Element Plus 全量 → unplugin 按需）或换轻量库（moment → dayjs）；
2. 有没有重复依赖？→ 同一个库的不同版本被打进两次，用 `resolve.alias` 收敛；
3. 有没有意外打进来的文件？→ 本该走 CDN 的大文件、忘了 exclude 的测试数据。

## 8. 缓存策略

"让构建变快"和"让用户二次访问变快"是两件事，分别对应两层缓存：

### 8.1 构建缓存（给机器看）

```javascript
module.exports = {
    cache: {
        type: 'filesystem',    // 将缓存写入磁盘（node_modules/.cache/webpack）
        // 下次构建直接从缓存读取——大型项目构建时间减少 50%+
    }
};
```

### 8.2 浏览器缓存（给用户看）

靠 §2.2 的 `[contenthash:8]` 文件指纹：**内容变 → hash 变 → URL 变 → 浏览器重新下载；内容没变 → 文件名不变 → 直接命中本地缓存**。

配合 §5 的分割，可以做出"缓存分层"：

```text
1. vendor + vue-vendor：很少变化 → contenthash 稳定 → 用户长期强缓存
2. common chunk：较少变化 → 中等缓存收益
3. app chunk：每次可能不同 → 只有它需要重新下载
```

> 效果：修改一行业务代码，用户只需重新下载 app chunk（如 250KB），而不是整个 800KB。

## 9. 速查表

| 概念 | 职责 | 示例 |
|---|---|---|
| Entry | 入口起点 | `entry: './src/main.ts'` |
| Output | 输出配置 | `filename: '[name].[hash].js'` |
| mode | 构建模式（决定压缩/摇树等默认行为） | `mode: 'production'` |
| devtool | SourceMap 策略 | `devtool: 'eval-cheap-module-source-map'` |
| resolve.alias | 路径别名 | `'@': path.resolve(__dirname, 'src')` |
| Loader | 文件转换 | `ts-loader`/`vue-loader`/`css-loader` |
| Plugin | 构建增强 | `HtmlWebpackPlugin`/`MiniCssExtractPlugin` |
| splitChunks | 代码分割 | `vue-vendor`/`vendor`/`common` |
| HMR | 热更新 | 局部替换模块，保留状态 |
| TreeShaking | 摇树优化 | 移除未使用代码 |
| filesystem cache | 磁盘缓存 | 二次构建快 50%+ |

**Webpack 一句话**：从入口出发，递归解析依赖图，通过 Loader 链处理异构模块，通过 Plugin 注入构建流程，最终输出为浏览器可用的静态资源。
