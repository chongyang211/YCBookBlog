# 第六章：MiniPlayer · Electron 桌面端实现（Web 技术栈 + C++ 原生扩展）

> **前置阅读**：[00.总览](/pages/miniplayer5/)、[01.架构设计与四端对照](/pages/mp5arch/)、[05.Qt桌面端实现](/pages/mp5qt0/)（强烈建议对照阅读，本篇多次与之互指）。
>
> **本文定位**：本篇是 MiniPlayer 的**"Web 桥接派"桌面实现**——用 **Electron + React** 做 UI 与业务，用 **C++ 写一个 `mp_native` 共享库**（CMake 产出 Linux `.so` / macOS `.dylib` / Windows `.dll`），再通过 **koffi FFI** 从 Node.js 主进程调用。读完本篇你会掌握：**（1）Electron 三进程模型与 IPC 契约**；**（2）如何用 C++ 写一个 C ABI 稳定、三端编译的扩展库**；**（3）如何在 Electron 中加载并安全地调用这个库**；**（4）如何把 C++ 产物随 Electron 一起打包分发**。
>
> **与 Qt 篇的关系**：Qt 篇是"**C++ 直接作主语言**"，Electron 篇是"**C++ 作服务提供者，被 JS 调用**"。两篇都用 C++、都三端、都走 CMake，但工程哲学与边界划分完全不同——这正是本案例"4 种技术栈"叙事里，Electron 存在的独立价值。

### 1.2 为什么用 Vite 而不是 Next.js

Next.js 的核心能力（SSR / RSC / Server Actions / 路由系统）**在 Electron 场景几乎全部失效**：

- Electron 加载 `file://` 协议，必须走 `output: 'export'` 静态导出模式；
- 单窗口应用的路由极简，Next 的文件路由反而笨重；
- Vite 冷启动约 300ms，Next 需要 2-3s，调试体验差距明显；
- `electron-vite` 这个脚手架专为 Electron 优化（main / preload / renderer 三入口自动分离）。

> 如果你已有 Next.js 的 Web 版、想复用页面组件做桌面版，可以保留 Next；但**纯新建桌面应用，Vite 是更正确的选择**。

### 1.3 哪些功能用 C++，哪些留在 JS

划一条清晰的边界——这是本篇最重要的工程决策：

| 功能 | 实现侧 | 理由 |
|------|-------|------|
| 文件扫描（遍历） | **JS**（Node fs） | fs.opendir 性能够用，异步迭代天然适配 |
| **媒体元数据提取** | **C++（TagLib）** ⭐ | music-metadata 对 FLAC Vorbis Comment、ID3v2.4 的解析有坑；TagLib 是业界事实标准 |
| **封面图提取** | **C++（TagLib + 内存直出）** | 大图走内存指针传回 JS 更快 |
| **音频指纹/文件探测** | **C++**（libmagic 风格 header 嗅探） | 按文件头探测而非扩展名（§00.README Q6 要求） |
| **LRC 解析** | **C++** | 教学目的——演示 C ABI 返回变长数组的三种策略 |
| 本地 DB | **JS**（better-sqlite3） | 已经是 C++ 原生模块，无需再包一层 |
| 播放引擎 | **JS**（`<audio>` + Web Audio） | Chromium 自带，别重复造轮子 |
| **系统媒体控制** | **C++（MPRIS/MPNowPlaying/SMTC）** ⭐ | 这是和 Qt 篇**对照最鲜明**的部分 |
| 全局快捷键 | **JS**（Electron globalShortcut） | 已封装好，没必要再 FFI |

> **一条铁律**：JS 能解决且性能够的，就留在 JS；只有"系统 API 原生接口"或"算法/格式解析规范复杂"的，才下沉到 C++。否则你会掉进"为了用 C++ 而用 C++"的陷阱。

### 1.4 五层架构与进程模型

Electron 的三进程把 [01.架构设计](/pages/mp5arch/) 的五层架构**物理切分**：

```text
┌──────────────────── Renderer Process (Chromium) ────────────────────┐
│ ⑤ UI 层          React 组件 + Tailwind                              │
│ ④ ViewModel 层   Zustand store（对标 Pinia / LiveData）              │
│ ③ PlayerService  Web Audio Graph + <audio>/<video>                  │
├───────────────────────── preload.ts (contextBridge) ────────────────┤
│                  安全窗口：仅暴露白名单 API 到 renderer              │
├──────────────────── Main Process (Node.js) ─────────────────────────┤
│ ② MediaRepository fs + better-sqlite3                               │
│ ① Platform Native koffi → libmp_native.{so|dylib|dll}               │
└─────────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
                       ┌────────────────────┐
                       │ C++ 原生扩展       │
                       │ mp_native/         │
                       │ ├── CMakeLists.txt │
                       │ ├── include/*.h    │ ← C ABI 头文件（JS 侧参考）
                       │ └── src/*.cpp      │
                       │                    │
                       │ 产物（随平台）:    │
                       │ ├── libmp_native.so   (Linux)  │
                       │ ├── mp_native.dylib   (macOS)  │
                       │ └── mp_native.dll     (Windows)│
                       └────────────────────┘
```

**三条进程纪律**（违反必翻车）：

1. **renderer 永远不直接访问 Node API**：`nodeIntegration: false` + `contextIsolation: true`，所有系统能力经 preload 的 `contextBridge.exposeInMainWorld` 透出。
2. **FFI 只在 main 进程调**：koffi 加载 dylib 后，renderer 想用能力必须走 `ipcRenderer.invoke(channel, args)`。严禁把 koffi 对象暴露给 renderer。
3. **C 边界只传基础类型**：string / int / buffer（指针+长度）/ struct；**不要试图在 FFI 边界传 C++ 对象或 STL 容器**。详见 §3.3。

## §3 C++ 原生扩展设计（最关键的一节）

本节是整篇的**技术骨架**。先讲清楚 C ABI 的三个设计原则，后面所有 C++ 代码都遵循它们。

### 3.1 为什么必须是 C ABI 而不是 C++ ABI

C++ 的 ABI（名字修饰、异常传播、虚表布局、STL 实现）**在不同编译器甚至同编译器不同版本间不兼容**。而 koffi 以及几乎所有 FFI 都基于 **C ABI**——它由操作系统固化、几十年不变。

**结论**：你的 C++ 代码**内部**可以尽情用 class / template / STL / 异常，但**导出给 FFI 调的那一层函数必须用 `extern "C"` 包装**，参数只用 C 基础类型。

### 3.2 C ABI 头文件设计（`native/include/mp_native.h`）

```c
// mp_native.h —— C ABI 唯一导出头
// 规则：仅使用 C 基础类型；字符串用 UTF-8 const char*；
//      变长数据用「指针 + 长度 + 释放函数」三件套。
#ifndef MP_NATIVE_H
#define MP_NATIVE_H

#include <stdint.h>
#include <stddef.h>

#ifdef _WIN32
  #define MP_API __declspec(dllexport)
#else
  #define MP_API __attribute__((visibility("default")))
#endif

#ifdef __cplusplus
extern "C" {
#endif

/* ========== 版本与通用 ========== */
MP_API const char* mp_version(void);          // 返回静态字符串，不要 free
MP_API void mp_free(void* ptr);               // ⭐ 释放所有本库返回的堆内存

/* ========== 元数据（阶段②）========== */
typedef struct {
  const char* title;      // UTF-8，可能为 NULL
  const char* artist;
  const char* album;
  int32_t     duration_ms;
  int32_t     bitrate_kbps;
  int32_t     sample_rate;
  int32_t     channels;
  const char* mime;       // "audio/mpeg" 等
} MpMetadata;

// 成功返回 0，失败返回负错误码。out 必须是栈上的 MpMetadata。
// 内部字符串字段的生命周期：由 mp_metadata_release 一次性释放。
MP_API int mp_metadata_read(const char* file_path, MpMetadata* out);
MP_API void mp_metadata_release(MpMetadata* meta);

// 提取封面：成功时 *out_data 指向堆内存（PNG/JPEG 原始字节），用完 mp_free。
MP_API int mp_metadata_cover(const char* file_path,
                             uint8_t** out_data, size_t* out_size,
                             const char** out_mime);

/* ========== 文件探测（阶段②）========== */
typedef enum { MP_FMT_UNKNOWN=0, MP_FMT_MP3, MP_FMT_FLAC, MP_FMT_M4A,
               MP_FMT_WAV, MP_FMT_OGG, MP_FMT_MP4, MP_FMT_MKV,
               MP_FMT_MOV, MP_FMT_WEBM } MpFormat;

MP_API MpFormat mp_probe(const char* file_path);   // 读前 16 字节，比扩展名可靠

/* ========== LRC 解析（阶段⑦）========== */
typedef struct { int64_t time_ms; const char* text; } MpLrcLine;

// 返回行数；*out_lines 指向堆数组（含 N 个 MpLrcLine）；文本也在同一堆块中。
// 释放：mp_lrc_release(*out_lines)
MP_API int mp_lrc_parse(const char* lrc_utf8, size_t len,
                        MpLrcLine** out_lines);
MP_API void mp_lrc_release(MpLrcLine* lines);

/* ========== 系统媒体控制（阶段⑥）========== */
typedef struct {
  const char* title;
  const char* artist;
  const char* album;
  int32_t     duration_ms;
  int32_t     position_ms;
  int32_t     playing;       // 0 暂停 / 1 播放
  const char* cover_path;    // 可为 NULL
} MpNowPlaying;

typedef void (*MpMediaCallback)(int32_t action, void* user_data);
// action 枚举：0=Play 1=Pause 2=Toggle 3=Next 4=Prev 5=SeekMs(user_data 当 int64_t*)

MP_API int  mp_sysmedia_init(MpMediaCallback cb, void* user_data);
MP_API void mp_sysmedia_update(const MpNowPlaying* info);
MP_API void mp_sysmedia_shutdown(void);

#ifdef __cplusplus
}
#endif
#endif // MP_NATIVE_H
```

### 3.3 C ABI 边界三条设计规则

1. **所有权要显式**：谁分配谁释放。本库分配的内存**必须**通过 `mp_free` / `mp_metadata_release` / `mp_lrc_release` 释放，决不能让 JS 侧用 free() 或者让 C++ 侧用 delete 来处理对方分配的内存——Windows CRT 和 Linux glibc 的 heap 不互通，混用必崩溃。

2. **变长数据统一「指针 + 长度 + 释放函数」三件套**：避免字符串用 `\0` 结尾然后被二进制数据截断。

3. **结构体用值传递或裸指针，别用 C++ 对象**：`MpMetadata` 这种 POD struct 在三端 Clang/GCC/MSVC 的内存布局是一致的；一旦掺入 `std::string` 就 ABI 爆炸。

### 3.4 示例实现：元数据提取（`native/src/metadata.cpp`）

```cpp
#include "mp_native.h"
#include <taglib/fileref.h>
#include <taglib/tag.h>
#include <taglib/tpropertymap.h>
#include <cstring>
#include <cstdlib>

static char* dup_utf8(const TagLib::String& s) {
  if (s.isEmpty()) return nullptr;
  const auto u8 = s.to8Bit(true);   // UTF-8
  char* buf = static_cast<char*>(std::malloc(u8.size() + 1));
  std::memcpy(buf, u8.data(), u8.size());
  buf[u8.size()] = '\0';
  return buf;
}

extern "C" int mp_metadata_read(const char* file_path, MpMetadata* out) {
  if (!file_path || !out) return -1;
  TagLib::FileRef f(file_path);
  if (f.isNull() || !f.tag()) return -2;

  auto* tag = f.tag();
  auto* ap  = f.audioProperties();

  out->title        = dup_utf8(tag->title());
  out->artist       = dup_utf8(tag->artist());
  out->album        = dup_utf8(tag->album());
  out->duration_ms  = ap ? ap->lengthInMilliseconds() : 0;
  out->bitrate_kbps = ap ? ap->bitrate() : 0;
  out->sample_rate  = ap ? ap->sampleRate() : 0;
  out->channels     = ap ? ap->channels() : 0;
  out->mime         = nullptr;   // 简化示例，可根据扩展名填
  return 0;
}

extern "C" void mp_metadata_release(MpMetadata* m) {
  if (!m) return;
  std::free((void*)m->title);  m->title = nullptr;
  std::free((void*)m->artist); m->artist = nullptr;
  std::free((void*)m->album);  m->album = nullptr;
}

extern "C" void mp_free(void* p) { std::free(p); }
extern "C" const char* mp_version(void) { return "mp_native 1.0.0"; }
```

**关键点**：`#include <taglib/...>` 这些 C++ 头文件只出现在 `.cpp` 内部；**导出符号的声明在 `.h` 里是纯 C**。

### 3.5 CMake 工程（三端共用一份）

```cmake
# native/CMakeLists.txt
cmake_minimum_required(VERSION 3.26)
project(mp_native LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_POSITION_INDEPENDENT_CODE ON)
set(CMAKE_CXX_VISIBILITY_PRESET hidden)      # 关键：仅 MP_API 符号可见
set(CMAKE_VISIBILITY_INLINES_HIDDEN YES)

# ========== 平台源文件分流 ==========
set(SRC
  src/metadata.cpp
  src/probe.cpp
  src/lrc.cpp
)
if(WIN32)
  list(APPEND SRC src/sysmedia/smtc_win.cpp)
  enable_language(CXX)
elseif(APPLE)
  enable_language(OBJCXX)
  list(APPEND SRC src/sysmedia/nowplaying_mac.mm)
elseif(UNIX)
  list(APPEND SRC src/sysmedia/mpris_linux.cpp)
endif()

add_library(mp_native SHARED ${SRC})
target_include_directories(mp_native PUBLIC include)

# ========== 依赖 ==========
find_package(TagLib REQUIRED)
target_link_libraries(mp_native PRIVATE TagLib::tag)

if(APPLE)
  target_link_libraries(mp_native PRIVATE
    "-framework Foundation" "-framework MediaPlayer" "-framework AppKit")
elseif(UNIX)
  find_package(PkgConfig REQUIRED)
  pkg_check_modules(DBUS REQUIRED dbus-1)
  target_include_directories(mp_native PRIVATE ${DBUS_INCLUDE_DIRS})
  target_link_libraries(mp_native PRIVATE ${DBUS_LIBRARIES})
elseif(WIN32)
  target_link_libraries(mp_native PRIVATE windowsapp)   # WinRT 运行时
endif()

# ========== 输出到 Electron 可直接 require 的位置 ==========
set_target_properties(mp_native PROPERTIES
  OUTPUT_NAME mp_native
  LIBRARY_OUTPUT_DIRECTORY ${CMAKE_SOURCE_DIR}/../resources/native
  RUNTIME_OUTPUT_DIRECTORY ${CMAKE_SOURCE_DIR}/../resources/native)
```

## §4 koffi 加载层（`src/main/native/`）

### 4.1 平台路径解析（`loader.ts`）

```ts
// src/main/native/loader.ts
import path from 'node:path';
import { app } from 'electron';

export function resolveNativeLibPath(): string {
  const base = app.isPackaged
    ? path.join(process.resourcesPath, 'native')     // 打包后：Resources/native
    : path.join(__dirname, '../../resources/native'); // 开发时：工程根 resources/native

  const name = process.platform === 'win32' ? 'mp_native.dll'
             : process.platform === 'darwin' ? 'libmp_native.dylib'
             : 'libmp_native.so';
  return path.join(base, name);
}
```

### 4.2 FFI 绑定（`bindings.ts`）

```ts
// src/main/native/bindings.ts
import koffi from 'koffi';
import { resolveNativeLibPath } from './loader';

const lib = koffi.load(resolveNativeLibPath());

// —— 结构体定义（对应 mp_native.h 的 MpMetadata）——
const MpMetadata = koffi.struct('MpMetadata', {
  title:        'string',   // koffi 自动 UTF-8 转换
  artist:       'string',
  album:        'string',
  duration_ms:  'int32',
  bitrate_kbps: 'int32',
  sample_rate:  'int32',
  channels:     'int32',
  mime:         'string',
});

// —— 函数签名 ——
export const native = {
  version:         lib.func('mp_version',          'string', []),
  free:            lib.func('mp_free',             'void',   ['pointer']),
  metadataRead:    lib.func('mp_metadata_read',    'int',    ['string', koffi.out(koffi.pointer(MpMetadata))]),
  metadataRelease: lib.func('mp_metadata_release', 'void',   [koffi.pointer(MpMetadata)]),
  probe:           lib.func('mp_probe',            'int',    ['string']),
  // LRC / 封面 / 系统媒体见后续章节
};

// —— 友好包装：自动管理内存 ——
export function readMetadata(filePath: string) {
  const meta: any = {};
  const rc = native.metadataRead(filePath, meta);
  if (rc !== 0) throw new Error(`metadata_read failed: ${rc}`);
  const safe = { ...meta };   // 复制一份出来
  native.metadataRelease(meta);
  return safe;
}
```

**关键细节**：

- `koffi.out(...)` 表示该参数是输出型，koffi 会自动分配空间并在调用后读回；
- 返回 `string` 类型时 koffi 做 UTF-8 → JS string 的拷贝，所以**原生侧释放后 JS 侧的值仍然有效**；
- 永远在 JS 层**先复制再释放**，别反过来。

### 阶段② 媒体扫描与导入（3h）⭐ C++ 首次登场

**目标**：扫描目录 → 调 C++ 提取元数据 → 列表显示；支持拖拽文件、粘贴 URL。

**JS 侧（`src/main/ipc/scanner.ts`）**：

```ts
import { ipcMain, dialog } from 'electron';
import fs from 'node:fs/promises';
import path from 'node:path';
import { readMetadata } from '../native/bindings';

const AUDIO_EXT = new Set(['.mp3','.flac','.m4a','.wav','.aac','.ogg']);
const VIDEO_EXT = new Set(['.mp4','.mkv','.mov','.webm']);

async function* walk(dir: string): AsyncGenerator<string> {
  for (const entry of await fs.readdir(dir, { withFileTypes: true })) {
    const full = path.join(dir, entry.name);
    if (entry.isDirectory()) yield* walk(full);
    else yield full;
  }
}

ipcMain.handle('scanner:scan', async (_e, root: string) => {
  const items = [];
  for await (const f of walk(root)) {
    const ext = path.extname(f).toLowerCase();
    if (!AUDIO_EXT.has(ext) && !VIDEO_EXT.has(ext)) continue;
    try {
      const meta = readMetadata(f);     // ⭐ 调 C++
      items.push({ path: f, type: AUDIO_EXT.has(ext) ? 'audio':'video', ...meta });
    } catch (err) {
      console.warn('skip', f, err);
    }
  }
  return items;
});
```

**C++ 侧**：§3.4 已给出 `mp_metadata_read` 完整实现。

**与 Web 篇对照**：Web 篇用 `music-metadata-browser`，对 FLAC Vorbis Comment 的 `METADATA_BLOCK_PICTURE` 解析曾踩坑；本篇用 TagLib 一次解决。

**稳定 ID 策略**：和 Qt 篇一致（`SHA1(path + size + mtime)`），这段**用 Node 的 crypto 做即可**——没必要下沉到 C++。

**验收**：

### 阶段③ 核心播放控制（4h）

**目标**：实现 §01 §1.5 的音频控制组：play/pause/seek/speed/volume/mute/A-B/queue。

**本阶段纯 JS**，没有 C++ 下沉的必要。核心在 `src/renderer/service/audioGraph.ts`：

```ts
// 构建 Web Audio Graph：source → gain(volume) → gain(crossfade) → EQ chain → destination
export class AudioGraph {
  private ctx = new AudioContext();
  private src!: MediaElementAudioSourceNode;
  private volumeGain = this.ctx.createGain();
  private crossfadeGain = this.ctx.createGain();
  // EQ 10 频段将在阶段⑨接入

  attach(el: HTMLAudioElement) {
    this.src = this.ctx.createMediaElementSource(el);
    this.src.connect(this.volumeGain)
            .connect(this.crossfadeGain)
            .connect(this.ctx.destination);
  }
  setVolume(v: number)      { this.volumeGain.gain.value = v; }
  setMuted(m: boolean)      { this.volumeGain.gain.value = m ? 0 : /* restore */ 1; }
  // A-B 循环：监听 timeupdate，position ≥ b 时 seek 回 a
}
```

**位置节流**：参照 [01.架构设计 §1.4](/pages/mp5arch/) 的 200ms 规则，用 `requestAnimationFrame` + 节流（跟 Qt 的 QTimer 对照）。

**进度条拖拽**：参照 Qt 篇的 `seeking` 标志位（[05.Qt §5](/pages/mp5qt0/)），拖动时冻结外部更新，释放时才真正 seek——这是**四端同款坑**。

### 阶段④ 视频增强（3h）⭐ 平台差异集中区

**目标**：全屏、宽高比、PiP、字幕、多轨、截图、旋转。

| 能力 | Electron 实现 |
|------|-------------|
| 全屏 | `win.setFullScreen(true)`（主进程 IPC 控制）或 `videoEl.requestFullscreen()`（DOM 层） |
| 宽高比 | CSS `object-fit: contain/cover/fill` + `transform: scaleX(16/9*h/w)` |
| **PiP** | `video.requestPictureInPicture()`（Chromium 原生支持，三端都能用，**比 Qt 篇的"置顶迷你窗"方案真实体验更好**）|
| 字幕 | `<track kind="subtitles" src=".vtt">`；SRT 需 JS 转 VTT |
| 多轨 | `video.audioTracks / video.textTracks`（**Electron 需 `--enable-features=AudioVideoTracks` 启动参数**） |
| 截图 | `canvas.drawImage(video, ...)` → `toBlob('image/png')` → 保存到 `app.getPath('pictures')` |
| 旋转 | CSS `transform: rotate(90deg)` + 容器尺寸补偿 |

**与 Qt 篇对照**：Qt 的 PiP 要自己造置顶小窗，Electron 直接 Chromium 原生 PiP 一行搞定；但 Qt 的字幕渲染（QMediaPlayer 内部） 比 Web `<track>` 支持的格式多（Qt 可解 ASS）。

### 阶段⑤ 本地持久化（3h）

**目标**：SQLite 建表 → 歌单/收藏/评分/历史/断点续播。

用 **better-sqlite3**（同步 API，桌面场景正合适；内部已是 C++ 原生模块）。表结构**和 Qt 篇完全一致**，直接复用 schema：

#### 6.2 JS 侧回调桥（`src/main/ipc/system-media.ts`）

```ts
import koffi from 'koffi';
import { native } from '../native/bindings';
import { BrowserWindow } from 'electron';

const MpMediaCallback = koffi.proto('MpMediaCallback', 'void', ['int32', 'pointer']);

export function setupSystemMedia(win: BrowserWindow) {
  const cb = koffi.register((action: number, _user: unknown) => {
    // ⚠ 原生回调可能在任意线程！先 marshal 到主线程
    setImmediate(() => {
      const map = { 0:'play', 1:'pause', 2:'toggle', 3:'next', 4:'previous' };
      win.webContents.send('sysmedia:action', map[action as 0|1|2|3|4]);
    });
  }, koffi.pointer(MpMediaCallback));

  native.sysmediaInit(cb, null);
}
```

**线程安全这一条是整篇最容易出事的地方**：MPRIS 的 dbus loop、SMTC 的 ThreadPool、macOS 的 remote command 都在非主线程回调；而 Electron 的 webContents.send 必须在主线程调。用 `setImmediate` 跳回主线程 event loop 是最简方案。

#### 6.3 与 Qt 篇的横向对照

| 维度 | Qt 篇做法 | Electron 篇做法 |
|------|---------|---------------|
| MPRIS 调用方 | C++ Qt 代码**直接**用 QDBus | C++ 代码用 **libdbus**（因为无 Qt 依赖），再被 JS 调 |
| 回调回主线程 | Qt 信号槽（跨线程自动 marshaling） | setImmediate + webContents.send |
| 行号对比 | §09 Qt 篇约 300 行 C++ | 本篇约 350 行 C++ + 50 行 TS 胶水 |

## §6 调试与排错速查表

| 症状 | 原因 | 解法 |
|------|------|------|
| `Error: Could not load library ...` | `.so/.dylib/.dll` 路径不对或缺依赖 | Linux: `ldd libmp_native.so`；macOS: `otool -L`；Windows: Dependency Walker |
| 运行时 crash 无堆栈 | 多半是 C ABI 边界的内存越界/双重释放 | 开 `-fsanitize=address` 重编 + `ASAN_OPTIONS=detect_leaks=1` |
| `koffi.load` 成功但函数全返回 0/NULL | 符号没导出（visibility=hidden 没加 MP_API） | `nm -gD libmp_native.so \| grep mp_` 验证符号表 |
| macOS 弹"无法验证开发者" | .dylib 未单独公证 | §9 公证流程 |
| Windows 启动找不到 TagLib.dll | vcpkg 的 dll 没一起复制 | electron-builder `extraResources` 把它加上 |
| 系统媒体回调导致 Electron 卡死 | 非主线程调了 webContents.send | 必过 setImmediate / `app.whenReady` |
| 开发期能跑，打包后 C++ 失效 | `app.isPackaged` 分支逻辑的路径错 | `console.log(process.resourcesPath)` 验证 |

## §8 本篇小结

- **Electron ≠ 单纯前端套壳**：真正的桌面应用能力来自主进程的 Node + 原生扩展，renderer 只是 UI
- **C ABI 是 FFI 的通用语**：你在 Rust、Go、Python、Node 任何语言调 C++ 库，技术栈底层都走这一套
- **C++ 代码既可以作主语言（Qt 篇），也可以作服务提供者（本篇）**：工程哲学的差异远大于技术难度差异
- **本篇最有价值的一张图**是 §1.4 的三进程 + FFI 边界图；最有价值的一节是 §3 的 C ABI 设计三原则
