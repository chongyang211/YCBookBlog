## 01.本端选型说明

### 1.1 为什么是 Qt 6 Widgets 而不是 GTK / QML / Electron / 单平台原生

| 方案 | 跨桌面能力 | 评价 |
|------|----------|------|
| **Qt 6 Widgets** ⭐ | Linux/macOS/Windows 三端一等公民 | **选它**——QMediaPlayer 10 行出声；信号槽天然对应四端"状态广播"；CMake 一等公民；30 年工业验证 |
| Qt 6 QML | 同样三端 | 动效漂亮但与 UIKit/Vue 心智重叠度低；教学对照性弱 |
| GTK4 + GStreamer | Linux 一流，macOS/Windows 二等公民 | 跨平台质量不如 Qt；GStreamer 手动管线对新手过重 |
| Electron + Vue | 全平台 | **与本案例 Web 端完全重复**，零教学增量 |
| 各平台原生三份（WPF / AppKit / GTK） | — | 工作量 ×3；想体验这条路线可去 [07.挑战题](/pages/mp5more/) 的 WPF 版 |

### 1.2 Qt 跨桌面的真实价值

一份代码产出三份原生可执行文件的工程现实：

```text
mini_player_desktop/
├── CMakeLists.txt                ← 单一构建系统
├── src/                          ← 95% 共享代码（UI/播放/DB/扫描/歌词/EQ）
│   ├── ui/
│   ├── service/
│   └── data/
└── platform/                     ← 5% 平台特化（§09）
    ├── linux/MprisAdapter.cpp         ← D-Bus MPRIS
    ├── macos/MPNowPlayingAdapter.mm   ← Objective-C++ 混编
    └── windows/SmtcAdapter.cpp        ← C++/WinRT

构建产物：
  Linux   → ./MiniPlayer                   （ELF, ~15MB）
  macOS   → ./MiniPlayer.app               （Bundle, ~35MB 含 Qt 框架）
  Windows → ./MiniPlayer.exe               （PE + DLLs, ~40MB）
```

**95% 共享的根本原因**：

- **UI**：QWidget 本身就是跨平台抽象，`QMainWindow`/`QListView`/`QSlider` 在三端表现为原生外观；
- **音视频**：QMediaPlayer 底层按平台自动桥接——Linux→GStreamer / macOS→AVFoundation / Windows→Media Foundation；
- **数据库**：SQLite 跨平台 C 库，`QSqlDatabase` 三端二进制兼容；
- **异步**：QThread + 信号槽模型三端完全一致；
- **文件系统**：`std::filesystem` 与 `QFile` 已抽象路径分隔符与权限模型。

### 1.3 "跨桌面派" vs "原生派"的工程权衡

Qt 桌面是"**一份代码跨平台**"的工程路线。真实工程里还有另一条路——"**各平台原生三份**"（Windows 用 WPF/WinUI、macOS 用 AppKit/SwiftUI、Linux 用 GTK）：

| 维度 | Qt 跨桌面派（本篇） | 各平台原生派（如 WPF） |
|------|-------------------|---------------------|
| 跨平台 | ✅ 一份代码三端 | ❌ 每端各写一份 |
| 融入系统生态 | 良好（原生外观，但 Fluent/Material 深度不如原生） | 极致（动效、控件完全是系统亲儿子） |
| 包体积 | 稍大（含 Qt DLLs） | 极小（系统框架自带） |
| 启动速度 | 快（本机代码直接起） | 快（但 .NET 等有冷启动） |
| 工作量 | ×1 | ×3 |
| 招聘匹配 | 跨平台桌面岗位（WPS、VSCode、Figma 桌面） | 原生应用岗位（Office 插件、OA 系统） |

**本案例的选择**：主线用 Qt 覆盖三平台，想体验原生派路线（以 Windows WPF 为代表）去看 [07.挑战题](/pages/mp5more/) 的扩展篇——同样是 Windows，WPF 怎么在 Fluent UI、SMTC 融入、启动速度上做得更深。两条路线在真实工程里都存在，这正是教学价值所在。

### 1.4 Qt Multimedia 的真相：它只是"遥控器"

`QMediaPlayer` 不解码媒体——它是**平台媒体后端的统一遥控器**：

| 平台 | 实际后端 | 需要安装什么 |
|------|---------|-----------|
| Linux | **GStreamer** | `gstreamer1.0-plugins-good/bad/libav` |
| macOS | **AVFoundation**（同 iOS） | 系统自带，零安装 |
| Windows | **Media Foundation** | 系统自带（Win10 1809+） |

这个事实决定两件事：

1. 装环境必须按平台配好后端（Linux 最容易踩坑，§02 详述）；
2. 视频渲染用 `QVideoWidget`，我们不碰解码（与四端"不碰 FFmpeg"原则一致）。

### 2.2 Linux 平台搭建

#### 方案 A：原生 Linux（最推荐）

**环境**：Ubuntu 22.04 / 24.04 LTS 桌面版。

```bash
# 1. 安装工具链与 Qt 6（Ubuntu 24.04 自带 Qt 6.4）
sudo apt update
sudo apt install -y \
  build-essential cmake ninja-build \
  qt6-base-dev qt6-multimedia-dev \
  libsqlite3-dev libtag1-dev \
  gstreamer1.0-plugins-good gstreamer1.0-plugins-bad gstreamer1.0-libav

# 2. 构建与运行
cd mini_player_desktop
cmake -B build -S . -G Ninja -DCMAKE_BUILD_TYPE=Debug

./build/MiniPlayer        # ← 弹出原生窗口
```

```cpp
void ProgressSlider::keyPressEvent(QKeyEvent* e) {
    if (m_durationMs <= 0) { QWidget::keyPressEvent(e); return; }
    const qint64 step = qMax<qint64>(1000, m_durationMs / 20);
    switch (e->key()) {
        case Qt::Key_Left:  emit seek(qMax<qint64>(0, m_positionMs - step)); return;
        case Qt::Key_Right: emit seek(qMin<qint64>(m_durationMs, m_positionMs + step)); return;
        case Qt::Key_Home:  emit seek(0); return;
        case Qt::Key_End:   emit seek(m_durationMs); return;
    }
    QWidget::keyPressEvent(e);
}
```

1. **颜色 token 全部 QSS 变量化**（Qt 6 QSS 不支持 `--var`，所以这里是硬编码到 property selector 分支里；Web/Android 可以用 CSS vars / theme attr，是 Qt 相对弱的一环）
2. **主题切换瞬时**：QSS 的 property 选择器重匹配通过 `style()->unpolish(w) + polish(w) + update()` 三连触发，不需要重启窗口
3. **系统切换自动同步**：`QStyleHints::colorSchemeChanged` 信号在 macOS/Windows 10+/Linux (xdg-desktop-portal) 都生效

## 09.平台特化专题：系统媒体控制 【阶段⑤⭐⭐·本篇灵魂章节】

> 本章是"**95% 共享 + 5% 平台特化**"中那 5% 的全部所在。三端的锁屏/耳机/蓝牙/媒体键控制走完全不同的三套 API，但我们用统一的 `SystemMediaAdapter` 接口把它们抽象到同一个水位。

**灵魂三问**：

> 1. 为什么 Linux 用的是"协议"（MPRIS）而 macOS/Windows 用的是"API"？（Linux 桌面自由拼装哲学 vs 苹果微软生态闭环）
> 2. 三端的"系统媒体控制激活点"分别在哪？（Linux: 启动即注册 / macOS: 首次播放时激活 AVAudioSession / Windows: SMTC 对象创建）
> 3. 为什么说这一章才是本篇真正的教学高峰？（95% 代码都在"用 Qt"，这一章才在"用操作系统"）

### 9.1 统一接口 `SystemMediaAdapter`

### 9.2 Linux 实现：MPRIS（D-Bus 协议）

- Step 9.2.1 D-Bus 基础 15 分钟速成：总线/服务名/对象路径/接口

- Step 9.2.3 `qdbusxml2cpp` 生成骨架 → 实现属性（PlaybackStatus/Metadata/Position）与方法（Play/Pause/Next/Seek）
- Step 9.2.4 `Seeked` 信号：拖动进度条后广播，锁屏控件同步跳
- Step 9.2.5 `QSystemTrayIcon`：托盘菜单（播放/暂停/上下首/退出）+ `closeEvent` 拦截 → hide 到托盘

### 9.3 macOS 实现：MPNowPlayingInfoCenter + MPRemoteCommandCenter

- Step 9.3.1 Objective-C++ 混编入门：`.mm` 文件 + CMake `OBJCXX` 开启 + 在 C++ 类里调 OC API

- Step 9.3.3 `MPNowPlayingInfoCenter.defaultCenter.nowPlayingInfo`：填 `MPMediaItemPropertyTitle`、`MPMediaItemPropertyArtist`、`MPNowPlayingInfoPropertyElapsedPlaybackTime` 等 key
- Step 9.3.4 `MPRemoteCommandCenter`：订阅 `playCommand`、`pauseCommand`、`nextTrackCommand`、`changePlaybackPositionCommand`
- Step 9.3.5 macOS 菜单栏迷你控制器（可选，`NSStatusItem` 等价于 Linux 托盘）
- ⚠️ 造 BUG 现场：没在 `MACOSX_BUNDLE` 下跑，`MPNowPlayingInfoCenter` 不工作（必须是 `.app` 不是裸可执行）

```objc

void MPNowPlayingAdapter::setMetadata(const MediaItem& item) {
```

## 10.均衡器 + 睡眠定时 【阶段⑧】

- Step 10.1 EQ 实现策略——`QMediaPlayer` 没有直挂 EQ 接口，三端走各自路径：
  - **Linux**：GStreamer `equalizer-10bands` 元素插入管线
  - **macOS**：`AVAudioEngine` + `AVAudioUnitEQ`（更现代也更强）
  - **Windows**：XAudio2 的 `FXEQ` 效果器
  - 用抽象类 `EqualizerBackend` 隔离，上层 10 滑块 UI 完全共享
- Step 10.2 预设/自定义 + SQLite 存 JSON（5 预设 + 自定义曲线）
- Step 10.3 睡眠定时：`QTimer` + 音量渐弱（`QPropertyAnimation` 控 volume，三端共用）
- Step 10.4 曲目间淡入淡出（crossfade）：两个 `QMediaPlayer` 实例交替 + volume 交叉
- 🧪 **验收**：三端 EQ 都能听出"低音增强"的差异；睡眠定时到点音量平滑归零

### 📎 对应代码（v0.1 工程 · 睡眠定时已实现）

| 关注点 | 工程文件 | 关键 API/技巧 |
|-------|---------|--------------|
| 睡眠定时核心 | `service/SleepTimer.{h,cpp}` | `QTimer` + `remainingMs` 计算 + 最后 10 秒**线性淡出** |
| 淡出算法 | `SleepTimer::onTick` 内 `ratio = remain / 10000` | 不用 QPropertyAnimation（节省对象开销），每 500ms tick 一次直接 `setVolume(saved * ratio)` |
| 取消时恢复 | `SleepTimer::cancel` | 恢复 `m_savedVolume`，避免用户觉得"音量被偷走了" |
| UI 控件 | `ui/SettingsPage.cpp` 睡眠卡片 | `QSpinBox` + 启动/取消按钮 + 500ms UI tick 显示剩余时间 |
| 空选保护 | `SettingsPage::onStartTimer` | 没当前曲目直接 Toast 提醒 |

**EQ 保留的扩展点**：当前 `PlayerService` 用 `QAudioOutput` 简单输出。若接 EQ，有两种工程路径：

```cpp
// 路径 A（推荐）：平台特化，走各自 DSP
//   Linux  → GStreamer equalizer-10bands 插件
//   macOS  → AVAudioEngine + AVAudioUnitEQ
//   Windows→ XAudio2 FXEQ
// 用一个 EqualizerBackend 抽象，和 SystemMediaAdapter 一个套路。

// 路径 B（三端共用但受限）：换成 QAudioSink + 自己做 PCM 滤波
//   QAudioDecoder → BiquadFilter 链（10 阶）→ QAudioSink
//   能跑但 PCM 层串接增加复杂度，仅适合音频，不适合视频。
```
