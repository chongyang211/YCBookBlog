## 01.本端选型说明

### 1.1 为什么是 Qt 6 Widgets 而不是 GTK / QML / Electron / 单平台原生

| 方案 | 跨桌面能力 | 评价 |
|------|----------|------|
| **Qt 6 Widgets** ⭐ | Linux/macOS/Windows 三端一等公民 | **选它**——QMediaPlayer 10 行出声；信号槽天然对应五端"状态广播"；CMake 一等公民；30 年工业验证 |
| Qt 6 QML | 同样三端 | 动效漂亮但与 WPF/UIKit 心智重叠度低；教学对照性弱 |
| GTK4 + GStreamer | Linux 一流，macOS/Windows 二等公民 | 跨平台质量不如 Qt；GStreamer 手动管线对新手过重 |
| Electron + Vue | 全平台 | **与本案例 Web 端完全重复**，零教学增量 |
| 各平台原生三份 | — | **与本案例 Windows WPF 篇对比过**：那是另一条路线，详见 §1.3 |

### 1.2 Qt 跨桌面的真实价值

一份代码产出三份原生可执行文件的工程现实：

```text
mini_player_desktop/
├── CMakeLists.txt                ← 单一构建系统
├── src/                          ← 95% 共享代码（UI/播放/DB/扫描/歌词/EQ）
│   ├── ui/
│   ├── service/
│   └── data/
└── platform/                     ← 5% 平台特化（§09）
    ├── linux/MprisAdapter.cpp         ← D-Bus MPRIS
    ├── macos/MPNowPlayingAdapter.mm   ← Objective-C++ 混编
    └── windows/SmtcAdapter.cpp        ← C++/WinRT

构建产物：
  Linux   → ./MiniPlayer                   （ELF, ~15MB）
  macOS   → ./MiniPlayer.app               （Bundle, ~35MB 含 Qt 框架）
  Windows → ./MiniPlayer.exe               （PE + DLLs, ~40MB）
```

**95% 共享的根本原因**：

- **UI**：QWidget 本身就是跨平台抽象，`QMainWindow`/`QListView`/`QSlider` 在三端表现为原生外观；
- **音视频**：QMediaPlayer 底层按平台自动桥接——Linux→GStreamer / macOS→AVFoundation / Windows→Media Foundation；
- **数据库**：SQLite 跨平台 C 库，`QSqlDatabase` 三端二进制兼容；
- **异步**：QThread + 信号槽模型三端完全一致；
- **文件系统**：`std::filesystem` 与 `QFile` 已抽象路径分隔符与权限模型。

### 1.3 "跨桌面派" vs "原生派"——与本案例 Windows WPF 篇的真实对照

本案例在 Windows 平台**同时产出两个版本**，不是重复，而是真实工程的两条路线对照：

| 维度 | Qt 版（本篇） | WPF 版（[06.Windows端](/pages/mp5win0/)） |
|------|-------------|--------------------------------------|
| 跨平台 | ✅ 一份代码三端 | ❌ 仅 Windows |
| 融入 Windows 生态 | 良好（原生外观，但不如 WPF 深） | 极致（Fluent UI、SMTC、WinUI 迁移路径） |
| 包体积 | ~40MB（含 Qt DLLs） | ~2MB（.NET 自带） |
| 启动速度 | 快（本机代码） | 稍慢（.NET 冷启动） |
| 开发体验 | Qt Creator / Visual Studio（CMake 工程） | Visual Studio 原生 .NET 项目 |
| 招聘匹配 | 跨平台桌面岗位（WPS、VSCode、Figma 桌面） | Windows 原生应用岗位（office 插件、OA 系统） |

**教学结论**：这两条路线在真实工程里都存在，各有适用场景——**Qt 走的是"工程效率优先"，WPF 走的是"平台融入优先"**。本案例让你在同一个产品需求下亲手实现两次，就是为了让你能真正判断"我这个新项目该选哪条"。

### 1.4 Qt Multimedia 的真相：它只是"遥控器"

`QMediaPlayer` 不解码媒体——它是**平台媒体后端的统一遥控器**：

| 平台 | 实际后端 | 需要安装什么 |
|------|---------|-----------|
| Linux | **GStreamer** | `gstreamer1.0-plugins-good/bad/libav` |
| macOS | **AVFoundation**（同 iOS） | 系统自带，零安装 |
| Windows | **Media Foundation** | 系统自带（Win10 1809+） |

这个事实决定两件事：

1. 装环境必须按平台配好后端（Linux 最容易踩坑，§02 详述）；
2. 视频渲染用 `QVideoWidget`，我们不碰解码（与五端"不碰 FFmpeg"原则一致）。

## 02.环境矩阵：Linux / macOS / Windows 三平台搭建 【会话0】

> **三选一开发即可，推荐三端都跑一次完整构建以验证"真跨平台"**。所有平台共用一份 CMakeLists.txt。

### 2.1 共通工具链要求

| 工具 | 最低版本 | 用途 |
|------|---------|------|
| CMake | 3.21+ | 跨平台构建 |
| Qt | 6.4 LTS+ | 核心框架（推荐 6.5+ 字幕 API 更完整） |
| C++ 编译器 | 支持 C++17 | GCC 11 / Clang 14 / MSVC 2019 16.11+ |
| Ninja | 1.10+ | 构建加速（可选，但强烈推荐） |
| TagLib | 1.12+ | ID3 元数据 |
| SQLite | 系统自带/Qt 内置 | 本地数据库 |

### 2.2 Linux 平台搭建

#### 方案 A：原生 Linux（最推荐）

**环境**：Ubuntu 22.04 / 24.04 LTS 桌面版。

```bash
# 1. 安装工具链与 Qt 6（Ubuntu 24.04 自带 Qt 6.4）
sudo apt update
sudo apt install -y \
  build-essential cmake ninja-build \
  qt6-base-dev qt6-multimedia-dev \
  libsqlite3-dev libtag1-dev \
  gstreamer1.0-plugins-good gstreamer1.0-plugins-bad gstreamer1.0-libav

# 2. 构建与运行
cd mini_player_desktop
cmake -B build -S . -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j
./build/MiniPlayer        # ← 弹出原生窗口
```

**验收**：弹窗出现 + 终端无 GStreamer 报错。

4. 开启共享目录（SPICE WebDAV）或 `git clone`；

### 2.3 macOS 平台搭建

```bash
# 1. 安装 Xcode Command Line Tools + Homebrew + Qt
xcode-select --install
brew install cmake ninja qt@6 taglib

# 2. 让 CMake 找到 Qt
export CMAKE_PREFIX_PATH="$(brew --prefix qt@6)"

# 3. 构建与运行
cd mini_player_desktop
cmake -B build -S . -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j
open ./build/MiniPlayer.app        # ← 弹出原生 .app 窗口（Dock 出现图标）
```

**验收**：
- Finder 看到 `MiniPlayer.app`，右键"显示包内容"结构正确（`Contents/MacOS/MiniPlayer` + `Contents/Resources/`）；
- 跟随系统深色/浅色模式自动切换外观（Qt 6 自动处理）；
- `open MiniPlayer.app` 从终端启动，Dock 图标出现。

**Apple Silicon 注意事项**：

- Homebrew 的 Qt 已经是 ARM64 原生版本，无需 Rosetta；
- 想做 Universal Binary（arm64 + x86_64），需要用官方 Qt 安装器（brew 版本不支持交叉编译），详见 §11.2。

**IDE 选择**：
- Qt Creator（`brew install --cask qt-creator`）：三端一致的开发体验，推荐；
- Xcode（通过 `cmake -G Xcode`）：原生调试器更顺手；
- VS Code + CMake Tools：轻量级。

### 2.5 单一 CMakeLists.txt 支撑三端

本篇的 CMake 工程**不用任何 if-else 分平台**，全靠 Qt 的构建系统自动处理：

```cmake
cmake_minimum_required(VERSION 3.21)
project(MiniPlayer VERSION 1.0 LANGUAGES CXX)

# macOS 需要 Objective-C++ 混编
if(APPLE)
    enable_language(OBJCXX)
endif()

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_AUTOMOC ON)
set(CMAKE_AUTORCC ON)
set(CMAKE_AUTOUIC ON)

if(MSVC)
    add_compile_options(/utf-8)
endif()

find_package(Qt6 6.4 REQUIRED COMPONENTS
    Core Gui Widgets Multimedia MultimediaWidgets Sql
    $<$<PLATFORM_ID:Linux>:DBus>
)

qt_standard_project_setup()

qt_add_executable(MiniPlayer
    WIN32 MACOSX_BUNDLE          # ← Windows 隐藏控制台、macOS 产出 .app
    src/main.cpp
    # ... src/ 下的全部文件（95% 共享）
)

# 平台特化：§09 展开
if(LINUX)
    target_sources(MiniPlayer PRIVATE platform/linux/MprisAdapter.cpp)
    target_link_libraries(MiniPlayer PRIVATE Qt6::DBus)
elseif(APPLE)
    target_sources(MiniPlayer PRIVATE platform/macos/MPNowPlayingAdapter.mm)
    target_link_libraries(MiniPlayer PRIVATE
        "-framework MediaPlayer" "-framework AVFoundation")
elseif(WIN32)
    target_sources(MiniPlayer PRIVATE platform/windows/SmtcAdapter.cpp)
    target_link_libraries(MiniPlayer PRIVATE WindowsApp.lib)
endif()

target_link_libraries(MiniPlayer PRIVATE
    Qt6::Widgets Qt6::Multimedia Qt6::MultimediaWidgets Qt6::Sql
)

# macOS Bundle 元信息
if(APPLE)
    set_target_properties(MiniPlayer PROPERTIES
        MACOSX_BUNDLE_INFO_PLIST ${CMAKE_SOURCE_DIR}/platform/macos/Info.plist.in
        MACOSX_BUNDLE_BUNDLE_NAME "MiniPlayer"
        MACOSX_BUNDLE_GUI_IDENTIFIER "com.yccoding.miniplayer"
    )
endif()
```

> **本节核心一张图**：全部三端用**同一条命令** `cmake --build build` 就能跑通——这正是选 Qt 的根本理由。

## 04.媒体扫描与列表 【阶段②】

> 🎯 **阶段目标**：`std::filesystem` 递归扫描媒体目录，TagLib 读元数据，`QListView` 展示三 Tab。

- Step 4.1 `MediaItem` 结构体（对照架构篇 §1.3，`enum class MediaType` + `std::optional` 封面路径）
- Step 4.2 `MediaScanner`：`recursive_directory_iterator` + 扩展名过滤 + 错误码处理（权限/软链环）
- Step 4.3 **三端默认扫描目录差异**：
  - Linux: `~/Music`、`~/Videos`
  - macOS: `~/Music`、`~/Movies`（注意 Movies 不是 Videos！）
  - Windows: `%USERPROFILE%\Music`、`%USERPROFILE%\Videos`
  - 用 `QStandardPaths::writableLocation(QStandardPaths::MusicLocation)` 跨平台取真实路径
- Step 4.4 **后台扫描**：`QThread` + `moveToThread`（对照 Android Executor / iOS GCD / Web Worker）
- Step 4.5 扫描进度信号：每 50 个文件 `emit progressChanged(done, total)`
- Step 4.6 TagLib 读 ID3/Vorbis/AAC 元数据 + 封面导出 cache
- Step 4.7 `QAbstractListModel` + `QListView` + 三 Tab（`QTabWidget`）
- Step 4.8 委托绘制：封面缩略图 + 两行文字（`QStyledItemDelegate`）
- ⚠️ 造 BUG 现场：先在主线程同步扫描 `~` 下 10 万文件，UI 冻结 20 秒，再挪线程
- 🧪 **验收**：三端各放入 500 个测试文件，扫描进度条流畅，列表滚动 60fps

## 09.平台特化专题：系统媒体控制 【阶段⑤⭐⭐·本篇灵魂章节】

> 本章是"**95% 共享 + 5% 平台特化**"中那 5% 的全部所在。三端的锁屏/耳机/蓝牙/媒体键控制走完全不同的三套 API，但我们用统一的 `SystemMediaAdapter` 接口把它们抽象到同一个水位。

**灵魂三问**：

> 1. 为什么 Linux 用的是"协议"（MPRIS）而 macOS/Windows 用的是"API"？（Linux 桌面自由拼装哲学 vs 苹果微软生态闭环）
> 2. 三端的"系统媒体控制激活点"分别在哪？（Linux: 启动即注册 / macOS: 首次播放时激活 AVAudioSession / Windows: SMTC 对象创建）
> 3. 为什么说这一章才是本篇真正的教学高峰？（95% 代码都在"用 Qt"，这一章才在"用操作系统"）

### 9.1 统一接口 `SystemMediaAdapter`

```cpp
// src/service/SystemMediaAdapter.h
class SystemMediaAdapter : public QObject {
    Q_OBJECT
public:
    virtual void setMetadata(const MediaItem& item) = 0;
    virtual void setPlaybackState(PlayerState::State state) = 0;
    virtual void setPosition(qint64 positionMs, qint64 durationMs) = 0;
signals:
    void playRequested();
    void pauseRequested();
    void nextRequested();
    void previousRequested();
    void seekRequested(qint64 positionMs);
};

// 工厂方法在三端分别返回不同实现
SystemMediaAdapter* SystemMediaAdapter::create(QObject* parent);
```

### 9.2 Linux 实现：MPRIS（D-Bus 协议）

- Step 9.2.1 D-Bus 基础 15 分钟速成：总线/服务名/对象路径/接口
- Step 9.2.2 MPRIS 规范：`org.mpris.MediaPlayer2` + `org.mpris.MediaPlayer2.Player` 两个 XML 定义
- Step 9.2.3 `qdbusxml2cpp` 生成骨架 → 实现属性（PlaybackStatus/Metadata/Position）与方法（Play/Pause/Next/Seek）
- Step 9.2.4 `Seeked` 信号：拖动进度条后广播，锁屏控件同步跳
- Step 9.2.5 `QSystemTrayIcon`：托盘菜单（播放/暂停/上下首/退出）+ `closeEvent` 拦截 → hide 到托盘
- ⚠️ 造 BUG 现场：故意不处理 D-Bus 服务名冲突，同跑两个实例 → 注册失败，再修（唯一实例锁）
- 🧪 **验收**：GNOME Shell / KDE Plasma 锁屏控件出现 MiniPlayer；键盘媒体键可控制；托盘控制 OK

### 9.3 macOS 实现：MPNowPlayingInfoCenter + MPRemoteCommandCenter

- Step 9.3.1 Objective-C++ 混编入门：`.mm` 文件 + CMake `OBJCXX` 开启 + 在 C++ 类里调 OC API
- Step 9.3.2 `AVAudioSession` 等价物：macOS 不用 session，但要在 Info.plist 声明 `NSAppleMusicUsageDescription`（可选）
- Step 9.3.3 `MPNowPlayingInfoCenter.defaultCenter.nowPlayingInfo`：填 `MPMediaItemPropertyTitle`、`MPMediaItemPropertyArtist`、`MPNowPlayingInfoPropertyElapsedPlaybackTime` 等 key
- Step 9.3.4 `MPRemoteCommandCenter`：订阅 `playCommand`、`pauseCommand`、`nextTrackCommand`、`changePlaybackPositionCommand`
- Step 9.3.5 macOS 菜单栏迷你控制器（可选，`NSStatusItem` 等价于 Linux 托盘）
- ⚠️ 造 BUG 现场：没在 `MACOSX_BUNDLE` 下跑，`MPNowPlayingInfoCenter` 不工作（必须是 `.app` 不是裸可执行）
- 🧪 **验收**：macOS 控制中心（点击右上角图标）出现 MiniPlayer 正在播放卡片；AirPods 控制 OK；锁屏控件 OK

**代码桥接示例**：

```objc
// platform/macos/MPNowPlayingAdapter.mm
#import <MediaPlayer/MediaPlayer.h>
#include "MPNowPlayingAdapter.h"

void MPNowPlayingAdapter::setMetadata(const MediaItem& item) {
    NSMutableDictionary* info = [NSMutableDictionary dictionary];
    info[MPMediaItemPropertyTitle] =
        [NSString stringWithUTF8String:item.title.toStdString().c_str()];
    info[MPMediaItemPropertyArtist] =
        [NSString stringWithUTF8String:item.artist.toStdString().c_str()];
    info[MPMediaItemPropertyPlaybackDuration] = @(item.durationMs / 1000.0);
    [MPNowPlayingInfoCenter defaultCenter].nowPlayingInfo = info;
}
```

### 9.4 Windows 实现：SMTC（SystemMediaTransportControls）

- Step 9.4.1 C++/WinRT 15 分钟入门：`winrt::init_apartment()` + 投影头文件
- Step 9.4.2 从 `MediaPlayer`（WinRT）或自己 new 一个 `SystemMediaTransportControls` 实例
- Step 9.4.3 填 `DisplayUpdater.MusicProperties`（Title/Artist/AlbumTitle）+ 封面 `Thumbnail`
- Step 9.4.4 订阅 `ButtonPressed` 事件：Play/Pause/Next/Previous
- Step 9.4.5 任务栏缩略图进度：`ITaskbarList3::SetProgressValue`（Shell API）
- Step 9.4.6 任务栏缩略图工具栏按钮：`ITaskbarList3::ThumbBarAddButtons`
- ⚠️ 造 BUG 现场：Qt 窗口没拿到正确的 HWND → SMTC 不弹（`QWidget::winId()` 转 `HWND` 的坑）
- 🧪 **验收**：按音量键的"媒体控制叠加层"出现 MiniPlayer；蓝牙耳机按键 OK；任务栏缩略图显示进度

### 9.5 三端对照速查

| 能力 | Linux (MPRIS) | macOS (MPNowPlaying) | Windows (SMTC) |
|------|-------------|---------------------|----------------|
| 协议/API 类型 | D-Bus 协议 + XML 规范 | Objective-C API | WinRT COM API |
| 代码量 | ~250 行（含生成的 D-Bus 骨架） | ~120 行 Objective-C++ | ~150 行 C++/WinRT |
| 元数据填充 | Variant Map | NSDictionary | DisplayUpdater |
| 控制回调 | D-Bus 方法实现 | RemoteCommandCenter target+selector | ButtonPressed 事件 |
| 锁屏控件 | GNOME/KDE 的媒体 widget | 系统控制中心 + 锁屏 | 媒体控制叠加层（音量键触发） |
| 调试工具 | `dbus-monitor` / `d-feet` | 控制中心本身即预览 | 直接按音量键预览 |

## 12.挑战题

1. **Qt QML 版**：用相同的后端 C++ 代码（`PlayerService`/`MediaRepository`）配 QML UI，对比 Widgets 的开发效率差异；
2. **BSD / Haiku 支持**：Qt 其实能跑在更多类 Unix 系统上，试试 FreeBSD；

4. **用 PipeWire 替代 PulseAudio** 后端并验证（Linux）；
5. **macOS SwiftUI 版**：用 Swift + SwiftUI 复刻一份，对照"Qt 跨桌面派 vs 苹果原生派"的真实工程差异（这其实是本案例原来的"第六端"构想，现在作为挑战题）；
6. **性能对比**：三端相同代码启动时间、内存占用、CPU 曲线实测，写一份 benchmark 报告。
