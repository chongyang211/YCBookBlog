# 第一章：MiniPlayer 架构设计与五端对照

本文是五端实现的**公共设计基座**：五篇端实现文档都假设你已经读过本文。我们将确定五件事——**分层架构、数据模型、播放状态机、接口契约、五端 API 映射**。读完本文，你在任何一端动手写代码前，都已经知道"要造哪几个类、每个类管什么、类之间怎么说话"。

---

## 1.1 为什么五端要共享一套设计

**因为本案例的教学价值就藏在"同与不同"里**：

- **同的部分**（数据模型、状态机、分层）：证明这些是"产品本质"，与平台无关；
- **不同的部分**（引擎 API、后台机制、异步模型）：暴露每个平台的"物理约束"，这才是平台工程的考点。

如果不先固化公共设计，五端各写各的，读者做完 Android 再看 iOS 会像换了一个项目；固化之后，五端代码**像同一个灵魂穿五件衣服**。

## 1.2 五层架构详解

```text
┌─────────────────────────────────────────────────────┐
│ ⑤ UI 层                                             │
│    Activity/Fragment · UIViewController · Vue 组件   │
│    · QWidget/Window · XAML View                     │
│    只做"展示 + 转发用户动作"，不持有播放状态           │
├─────────────────────────────────────────────────────┤
│ ④ Controller / ViewModel 层                         │
│    持有 PlayerState，把引擎事件翻译成 UI 可订阅的状态  │
│    Android: ViewModel+LiveData · iOS: 控制器属性+KVO │
│    Web: Pinia store · Qt: QObject 属性+信号          │
│    WPF: ViewModel+INotifyPropertyChanged            │
├─────────────────────────────────────────────────────┤
│ ③ PlayerService 层（每端的心脏）                     │
│    播放/暂停/seek/倍速/队列管理/下一首决策            │
│    后台生命周期（前台服务/AVAudioSession/MPRIS/SMTC） │
├─────────────────────────────────────────────────────┤
│ ② MediaRepository 层                                │
│    扫描文件系统 → 读元数据 → 写入/读取本地 DB        │
│    对上层暴露"全部/音频/视频/我喜欢/历史"五类查询      │
├─────────────────────────────────────────────────────┤
│ ① Platform Engine 层（平台黑盒）                     │
│    ExoPlayer · AVPlayer · <audio>/<video>            │
│    · QMediaPlayer · MediaElement                    │
└─────────────────────────────────────────────────────┘
```

**三条铁律**（五端通用，违反任何一条都会在阶段④⑤翻车）：

1. **依赖只能向下**：UI → ViewModel → Service → Repository → Engine。Engine 永远不知道 UI 的存在。
2. **播放状态只有一个数据源**（Single Source of Truth）：全部来自 PlayerService，UI 只是它的镜像。谁让 UI 自己记录 `isPlaying`，谁的进度条就会跳动。
3. **引擎事件统一向上翻译**：Engine 的回调/信号先进入 Service，由 Service 归一化为统一事件，再广播给 ViewModel。

## 1.3 数据模型（五端共享）

### 核心实体

```text
MediaItem                     // 音频和视频统一建模
├── id: long                  // 稳定主键（路径的 hash）
├── type: MediaType           // AUDIO / VIDEO
├── path: string              // 绝对路径
├── title: string             // 元数据标题，缺省用文件名
├── artist: string
├── album: string
├── durationMs: long
├── coverPath: string?        // 提取出的封面缓存路径
└── addedAt: long             // 入库时间

PlayRecord                    // 播放历史
├── mediaId: long
├── playedAt: long
└── positionMs: long          // 播放到哪里（断点续播用）

Favorite                      // 我喜欢
└── mediaId + favoredAt

LyricLine                     // 歌词行
├── timeMs: long              // [mm:ss.xx] 解析结果
└── text: string
```

### 五端类型映射表

| 模型字段 | Android (Java) | iOS (OC) | Web (TS) | Linux (C++) | Windows (C#) |
|---------|----------------|----------|----------|-------------|--------------|
| MediaItem | `class MediaItem` + Room `@Entity` | `MediaItem : NSObject` | `interface MediaItem` | `struct MediaItem` | `class MediaItem` (record) |
| 枚举 MediaType | `enum class`（Java int） | `typedef NS_ENUM` | union type `"audio" \| "video"` | `enum class MediaType` | `enum MediaType` |
| 时间戳 | `long` | `NSTimeInterval` / `uint64_t` | `number` | `std::chrono::milliseconds` | `long` / `TimeSpan` |
| 列表 | `List<>` + DiffUtil | `NSArray` | `Media[]` | `std::vector` | `ObservableCollection` |
| 空值 | `@Nullable` | 指针 nil / `NSNull` | `?` / `undefined` | `std::optional` | `?` / null |

> **对照考点**：OC 没有原生枚举泛型集合、C++ 没有反射、Web 的 number 会丢 long 精度（id 用 string）——这些"语言物理约束"会直接影响数据模型在每端的落地形态。

## 1.4 播放状态机（五端共享）

```text
                 prepare(path)
    ┌────────┐ ───────────────→ ┌───────────┐  onReady   ┌─────────┐
    │ IDLE   │                  │ PREPARING │ ─────────→ │ PAUSED  │
    └────────┘ ←─────────────── └───────────┘            └─────────┘
        ↑          error()           ↑  ↑                  play() ↓ ↑ pause()
        │                           │  └────────────────┌─────────┐
        │         stop()            └───────────────────│ PLAYING │
        └───────────────────────────────────────────────└─────────┘
                                                              ↓ error()
                                                          ┌─────────┐
                                                          │  ERROR  │
                                                          └─────────┘
```

**状态广播五元组**（UI 唯一允许消费的播放状态）：

```text
PlayerState {
  state:        IDLE | PREPARING | PLAYING | PAUSED | ERROR
  currentMedia: MediaItem?
  positionMs:   long      // 每 200~500ms 节流上报
  durationMs:   long
  speed:        float     // 0.5 ~ 2.0
}
```

**五端状态广播机制对照**（本文最重要对照之一）：

| 能力 | Android | iOS | Web | Linux | Windows |
|------|---------|-----|-----|-------|---------|
| 状态持有 | ViewModel + LiveData/MutableStateFlow | 控制器属性 + KVO/委托回调 | Pinia `ref` 响应式 | QObject 属性 + `property`/信号 | ViewModel + `INotifyPropertyChanged` |
| 位置节流 | Handler `postDelayed` 循环 | `CADisplayLink` / `addPeriodicTimeObserver` | `requestAnimationFrame`/`setInterval` | `QTimer` 200ms | `DispatcherTimer` |
| 生命周期安全 | LiveData 自动感知 | weak delegate | 组件卸载清理 watcher | Qt 父子对象树自动销毁 | 弱事件/绑定自动解耦 |

## 1.5 PlayerService 接口契约

五端的 Service 层都实现同一组方法（伪代码，各端映射为 interface / protocol / 抽象基类 / Duck typing）：

```text
interface PlayerService {
  // —— 播放控制 ——
  prepare(media: MediaItem)            // 装载并暂停在 0
  play() / pause() / toggle()
  seekTo(positionMs: long)
  setSpeed(rate: float)

  // —— 队列 ——
  setQueue(items: MediaItem[], startIndex: int)
  next() / previous()                  // 受播放模式影响
  setMode(mode: SEQUENCE | REPEAT_ONE | SHUFFLE)

  // —— 状态订阅 ——
  observeState(): Observable<PlayerState>

  // —— 后台能力（阶段⑤）——
  enterBackground() / exitBackground()
  onSystemMediaAction(action: PLAY|PAUSE|NEXT|PREV|SEEK)

  // —— 均衡器（阶段⑧）——
  setEqualizerBand(band: int, gainDb: float)
}
```

**五端"接口契约"落地形态对照**：

| 端 | 契约形态 | 备注 |
|----|---------|------|
| Android | Java `interface` + `PlayerService` 实现类 | Service 可先做普通类，阶段⑤再迁入 ForegroundService |
| iOS | OC 协议 `@protocol PlayerServiceProtocol` | 配合 delegate 回调 |
| Web | TS `interface` + Pinia store 内部实现 | 契约主要用于约束 store 的 actions |
| Linux | 抽象基类 `class PlayerService` + 信号 | 用 Qt 信号做 observeState |
| Windows | C# `interface` + 实现类 | MVVM 命令直接调用接口 |

按功能逐条映射，写代码时当"字典"查：

| 功能 | Android | iOS | Web | Linux | Windows |
|------|---------|-----|-----|-------|---------|

| 倍速 | `setPlaybackParameters` | `rate` 属性 | `playbackRate` | `setPlaybackRate` | `SpeedRatio` |
| 进度监听 | `Player.Listener` | `addPeriodicTimeObserver` | `timeupdate` 事件 | `positionChanged` 信号 | `MediaEnded`/Timer 轮询 |
| 取元数据 | `MediaMetadataRetriever` | AVAsset `metadata` | music-metadata-browser | TagLib `Tag`/`AudioProperties` | TagLibSharp |
| 列表 UI | RecyclerView + Adapter | UITableView + DataSource | `<TransitionGroup>`/v-for | QListView + QAbstractListModel | ListView/ItemsControl + DataTemplate |
| 本地 DB | Room | FMDB | Dexie (IndexedDB) | SQLite C API | sqlite-net-pcl |
| 系统媒体控制 | MediaSessionCompat | MPRemoteCommandCenter | Media Session API | MPRIS (D-Bus) | SMTC |
| 通知/常驻指示 | Notification +ForegroundService | 锁屏信息（无传统通知） | Web Notification | 系统托盘 QSystemTrayIcon | 任务栏进度 + 缩略图按钮 |

## 1.8 全局约定

1. **命名**：五端类名统一 `PlayerService / MediaRepository / MediaScanner / LyricsParser / EqualizerController`，只换各端命名风格（OC 前缀 `MP`、C++ 命名空间 `mp::`）。
2. **时间单位一律毫秒**（`long`），只在调用引擎 API 的最后一刻转换（iOS 秒、Web 秒）。
3. **线程规则**：扫描和 DB 在后台线程/协程；UI 只在主线程；引擎回调一律 post 回主线程。
4. **错误分层**：引擎错误 → Service 归一化为 `PlaybackException(code, message)` → UI 统一 Toast/Snackbar 提示。
5. **测试素材**：仓库提供 `assets/media/` 目录（2 首 mp3 + 1 个 mp4 + 对应 .lrc），五端自测用同一套素材，保证截图/验收输出一致。
