# 第七章：MiniPlayer 挑战题与扩展

完成五端实现后，本篇给出五个方向的进阶路线。每个方向独立成题，含目标、难度、提示与验收标准，适合作为组队学习或训练营的赛题。

---

## 7.1 方向一：macOS SwiftUI 版（苹果原生派对照）

| 项目 | 说明 |
|------|------|
| 难度 | ★★★★ |
| 预估 | 15 - 20 小时 |
| 前置 | iOS 端 + Qt 桌面端均已完成（大量 AVFoundation + 对照素材可复用） |

**目标**：用 Swift + SwiftUI 复刻 MiniPlayer 核心功能（阶段①-⑤），与 [05.Qt桌面端](/pages/mp5qt0/) 的 macOS 版形成 **"同一个苹果平台，跨桌面派 vs 苹果原生派"** 的真实工程对照。

**为什么单独做一次 SwiftUI 版？** Qt 桌面已经覆盖 macOS，这里 SwiftUI 的教学增量在于**另一条路线**：

| 维度 | Qt 版（05 篇的 macOS 产物） | SwiftUI 版（本挑战题） |
|------|-------------------------|---------------------|
| 跨平台 | 同一代码跑三端 | 仅 macOS，但顺手复用 iOS 代码 |
| UI 范式 | 命令式（信号槽） | 声明式（@State / @Observable） |
| 平台融入度 | 良好 | 极致（菜单栏/控制中心/聚焦/原生动效） |
| 包体积 | ~35MB（含 Qt 框架） | ~3MB（系统框架） |
| 语言 | C++ | **Swift**（本案例补齐的第六大语言系） |

**提示**：

- 播放引擎与 iOS 同源（`AVPlayer`），可对照 [03.iOS端实现](/pages/mp5ios0/) 看清"同框架、不同平台惯例"；
- macOS 特有考点：`NSWindow` 多窗口、菜单栏（`MenuBarExtra`）、Dock 徽标进度、`MPNowPlayingInfoCenter`（在 macOS 上作用于控制中心）；
- 声明式 UI 心智最接近 Web 的 Vue，可横向对照（@Observable ≈ Pinia store）。

**验收**：菜单栏迷你控制器 + 播放 + 媒体库三 Tab + 持久化 + 跟随系统深色模式。

## 7.2 方向二：HLS 流媒体播放

| 项目 | 说明 |
|------|------|
| 难度 | ★★★☆ |
| 预估 | 6 - 10 小时/端 |
| 前置 | 任一端阶段③完成 |

**目标**：在已有播放器上增加"网络流"入口，播放 HLS 直播/点播源。

**各端要点**：

| 端 | 方案 |
|----|------|
| Android | ExoPlayer 原生 HLS |
| iOS | AVPlayer 原生 HLS（苹果自家协议） |
| Web | Safari 原生 / 其余用 hls.js |
| Qt 桌面 | **Linux**: GStreamer `hlsdemux`/`souphttpsrc` · **macOS**: AVFoundation 原生 · **Windows**: 系统支持视 codec（可选 FFmpegInteropX） |
| Windows 原生 (WPF) | FFmpegInteropX 或系统支持视 codec 而定 |

**进阶**：自建 Nginx + ffmpeg 推流，把"直播自己的桌面"作为端到端素材。

**验收**：播放一个公开 HLS 测试源，起播 < 3 秒，seek 正常。

## 7.3 方向三：云同步与多端接力

| 项目 | 说明 |
|------|------|
| 难度 | ★★★★★ |
| 预估 | 20+ 小时 |
| 前置 | 任两端已完成 |

**目标**：最小服务端（Go 或 Node.js）+ 五端接入，实现"我喜欢/播放历史/断点"跨端同步。

**设计要点**：

1. 数据模型直接复用架构篇 §1.3（PlayRecord/Favorite 已天然是同步友好的 append-only 结构）；
2. 服务端只做三张表的 REST CRUD + JWT 鉴权，不做实时推送（v1）；
3. 冲突策略：断点取"最后播放时间更大者"，收藏做并集；
4. 安全基线：鉴权全链路、SQL 全参数化、上传文件白名单 + 大小限制。

**验收**：手机听歌到 1:23，桌面端打开同一首自动续播。

## 7.4 方向四：Qt QML 重构版

| 项目 | 说明 |
|------|------|
| 难度 | ★★★☆ |
| 预估 | 10 - 15 小时 |
| 前置 | [05.Qt桌面端](/pages/mp5qt0/) 已完成 |

**目标**：保留 Qt 桌面端的 C++ 后端（`PlayerService`/`MediaRepository`），把 UI 从 Widgets 换成 QML + Qt Quick。

**对照考点**：

- Widgets（命令式、原生外观、CPU 渲染）vs QML（声明式、GPU 加速、动效华丽）；
- 同一份 `PlayerService` 用两种 UI 框架消费，验证 §1 分层架构的"UI 层可替换"原则；
- 评估为什么 WPS、VSCode 这类工具软件选 Widgets，而车机、广告机类选 QML。

**验收**：QML 版和 Widgets 版同时安装共存，功能一致，启动时间与内存实测对比报告。

## 7.6 毕业自测清单

全部答对，说明五端案例真正吃透：

1. 五端的"播放状态唯一数据源"分别落在哪个类？（每端报出类名）
2. 进度条拖动标志位问题在几端出现过？为什么这是必然问题？
3. Android ForegroundService / iOS AVAudioSession / Web 媒体键 / **Qt 桌面的 MPRIS+MPNowPlayingInfoCenter+SMTC 三件套** / WPF SMTC——哪些是"协议"哪些是"API"？背后平台哲学差异是什么？
4. 五端文件扫描 API 分别是什么？各自的沙盒/权限模型差异？
5. 如果明天要支持一个新格式（如 opus），五端分别要动哪里？
6. **Qt 跨桌面派** vs **各平台原生派**（WPF/SwiftUI/GTK）在 Windows 平台的真实工程取舍是什么？你的下一个桌面项目会选哪条？
