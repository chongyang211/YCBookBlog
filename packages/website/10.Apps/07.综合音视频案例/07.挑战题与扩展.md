# 第七章：MiniPlayer 挑战题与扩展

完成四端实现后，本篇给出六个方向的进阶路线。每个方向独立成题，含目标、难度、提示与验收标准，适合作为组队学习或训练营的赛题。

---

## 7.1 方向一：Windows WPF 原生版（跨桌面派 vs 原生派对照）

| 项目 | 说明 |
|------|------|
| 难度 | ★★★★ |
| 预估 | 18 - 24 小时 |
| 前置 | [05.Qt桌面端](/pages/mp5qt0/) 已完成（有可对照素材） |

**目标**：用 C# + WPF + XAML + MVVM 复刻 MiniPlayer（阶段①-⑨），与 Qt 桌面端的 **Windows 产物**形成 **"跨桌面派 vs 原生派"** 的真实工程对照。

**为什么单独做一次 WPF 版？** Qt 桌面已经覆盖 Windows，WPF 的教学增量在于**另一条路线**：

| 维度 | Qt 版（05 篇的 Windows 产物） | WPF 版（本挑战题） |
|------|---------------------------|---------------------|
| 跨平台 | ✅ 一份代码三端 | ❌ 仅 Windows |
| 融入 Windows 生态 | 良好（原生外观，但 Fluent/SMTC 深度不如原生） | 极致（Fluent UI、SMTC、WinUI 迁移路径） |
| 包体积 | ~40MB（含 Qt DLLs） | ~2MB（.NET 自带） |
| 启动速度 | 快（本机代码） | 稍慢（.NET 冷启动，但对用户感知差异不大） |
| 开发体验 | Qt Creator / Visual Studio（CMake 工程） | Visual Studio 原生 .NET 项目 |
| 语言 | C++ | **C#**（本挑战题补齐的第五大语言系） |
| 招聘匹配 | 跨平台桌面岗（WPS、VSCode、Figma 桌面） | Windows 原生岗（Office 插件、企业 OA、政务客户端） |

**技术栈**：

| 层级 | 选型 |
|------|------|
| UI 框架 | WPF + XAML（MVVM：DataBinding + ICommand） |
| 音视频引擎 | `MediaElement`（底层 Media Foundation） |
| 后台与通知 | **SMTC**（SystemMediaTransportControls，WinRT 原生）+ 任务栏缩略图进度 + 缩略图按钮 |
| 文件扫描 | `Directory.EnumerateFiles` + Shell32 |
| 元数据 | TagLibSharp |
| 本地 DB | sqlite-net-pcl / EF Core |
| 异步 | `async/await` + `Task` |
| 架构 | MVVM：ViewModel + `INotifyPropertyChanged` + `ObservableCollection` |
| 主题 | `ResourceDictionary` 动态合并 + 跟随系统 `AppsUseLightTheme` |
| .NET 版本 | **.NET 8 LTS** |

**提示**：

- WPF 的 XAML 数据绑定 + `INotifyPropertyChanged` + `ICommand` 是业界 **最早最完整**的 MVVM 体系（Android Jetpack 的 ViewModel+LiveData 明显借鉴了它）——本挑战题是观察"MVVM 血统"的最佳样本；
- SMTC 比 Qt 篇中的 Windows 实现更深：WPF 可直接拿 WinRT 的 `SystemMediaTransportControls`，与 Media Foundation 深度联动；
- 任务栏能力对比：Qt 用 Shell API 手动做任务栏进度，WPF 可直接用 `TaskbarItemInfo` 一行声明；
- "**9 阶段 × WPF 实现**"文档骨架可参考 05.Qt桌面端篇完全同构，重点落在 §09 "SMTC + 任务栏"这一节的差异。

**验收**：
- 阶段①-⑨功能完整；
- 包体 < 10MB（AOT 发布可到 15MB）；
- SMTC 控件在"按音量键的媒体控制叠加层"完美出现；
- 任务栏缩略图进度 + 缩略图按钮都工作。

> **教学结论**：Qt 走"工程效率优先"，WPF 走"平台融入优先"。两条路线在真实工程里都存在，亲手实现两次，才能真正判断"我这个新项目该选哪条"。

## 7.2 方向二：macOS SwiftUI 版（苹果原生派对照）

| 项目 | 说明 |
|------|------|
| 难度 | ★★★★ |
| 预估 | 15 - 20 小时 |
| 前置 | iOS 端 + Qt 桌面端均已完成（大量 AVFoundation + 对照素材可复用） |

**目标**：用 Swift + SwiftUI 复刻 MiniPlayer 核心功能（阶段①-⑤），与 Qt 桌面端的 **macOS 产物**形成 **"同一个苹果平台，跨桌面派 vs 苹果原生派"** 的真实工程对照。

**为什么单独做一次 SwiftUI 版？** Qt 桌面已经覆盖 macOS，这里 SwiftUI 的教学增量在于**另一条路线**：

| 维度 | Qt 版（05 篇的 macOS 产物） | SwiftUI 版（本挑战题） |
|------|-------------------------|---------------------|
| 跨平台 | 同一代码跑三端 | 仅 macOS，但顺手复用 iOS 代码 |
| UI 范式 | 命令式（信号槽） | 声明式（@State / @Observable） |
| 平台融入度 | 良好 | 极致（菜单栏/控制中心/聚焦/原生动效） |
| 包体积 | ~35MB（含 Qt 框架） | ~3MB（系统框架） |
| 语言 | C++ | **Swift**（补齐 Apple 现代栈） |

**提示**：

- 播放引擎与 iOS 同源（`AVPlayer`），可对照 [03.iOS端实现](/pages/mp5ios0/) 看清"同框架、不同平台惯例"；
- macOS 特有考点：`NSWindow` 多窗口、菜单栏（`MenuBarExtra`）、Dock 徽标进度、`MPNowPlayingInfoCenter`（在 macOS 上作用于控制中心）；
- 声明式 UI 心智最接近 Web 的 Vue，可横向对照（@Observable ≈ Pinia store）。

**验收**：菜单栏迷你控制器 + 播放 + 媒体库三 Tab + 持久化 + 跟随系统深色模式。

## 7.3 方向三：HLS 流媒体播放

| 项目 | 说明 |
|------|------|
| 难度 | ★★★☆ |
| 预估 | 6 - 10 小时/端 |
| 前置 | 任一端阶段③完成 |

**目标**：在已有播放器上增加"网络流"入口，播放 HLS 直播/点播源。

**各端要点**：

| 端 | 方案 |
|----|------|
| Android | ExoPlayer 原生 HLS |
| iOS | AVPlayer 原生 HLS（苹果自家协议） |
| Web | Safari 原生 / 其余用 hls.js |
| Qt 桌面 | **Linux**: GStreamer `hlsdemux`/`souphttpsrc` · **macOS**: AVFoundation 原生 · **Windows**: 系统支持视 codec（可选 FFmpegInteropX） |

**进阶**：自建 Nginx + ffmpeg 推流，把"直播自己的桌面"作为端到端素材。

**验收**：播放一个公开 HLS 测试源，起播 < 3 秒，seek 正常。

## 7.4 方向四：云同步与多端接力

| 项目 | 说明 |
|------|------|
| 难度 | ★★★★★ |
| 预估 | 20+ 小时 |
| 前置 | 任两端已完成 |

**目标**：最小服务端（Go 或 Node.js）+ 四端接入，实现"我喜欢/播放历史/断点"跨端同步。

**设计要点**：

1. 数据模型直接复用架构篇 §1.3（PlayRecord/Favorite 已天然是同步友好的 append-only 结构）；
2. 服务端只做三张表的 REST CRUD + JWT 鉴权，不做实时推送（v1）；
3. 冲突策略：断点取"最后播放时间更大者"，收藏做并集；
4. 安全基线：鉴权全链路、SQL 全参数化、上传文件白名单 + 大小限制。

**验收**：手机听歌到 1:23，桌面端打开同一首自动续播。

## 7.5 方向五：Qt QML 重构版

| 项目 | 说明 |
|------|------|
| 难度 | ★★★☆ |
| 预估 | 10 - 15 小时 |
| 前置 | [05.Qt桌面端](/pages/mp5qt0/) 已完成 |

**目标**：保留 Qt 桌面端的 C++ 后端（`PlayerService`/`MediaRepository`），把 UI 从 Widgets 换成 QML + Qt Quick。

**对照考点**：

- Widgets（命令式、原生外观、CPU 渲染）vs QML（声明式、GPU 加速、动效华丽）；
- 同一份 `PlayerService` 用两种 UI 框架消费，验证 §1 分层架构的"UI 层可替换"原则；
- 评估为什么 WPS、VSCode 这类工具软件选 Widgets，而车机、广告机类选 QML。

**验收**：QML 版和 Widgets 版同时安装共存，功能一致，启动时间与内存实测对比报告。

## 7.7 毕业自测清单

全部答对，说明四端案例真正吃透：

1. 四端的"播放状态唯一数据源"分别落在哪个类？（每端报出类名）
2. 进度条拖动标志位问题在几端出现过？为什么这是必然问题？
3. Android ForegroundService / iOS AVAudioSession / Web 媒体键 / **Qt 桌面的 MPRIS+MPNowPlayingInfoCenter+SMTC 三件套**——哪些是"协议"哪些是"API"？背后平台哲学差异是什么？
4. 四端文件扫描 API 分别是什么？各自的沙盒/权限模型差异？
5. 如果明天要支持一个新格式（如 opus），四端分别要动哪里？
6. **Qt 跨桌面派** vs **各平台原生派**（WPF/SwiftUI/GTK）在同一个 Windows/macOS 平台的真实工程取舍是什么？你的下一个桌面项目会选哪条？
