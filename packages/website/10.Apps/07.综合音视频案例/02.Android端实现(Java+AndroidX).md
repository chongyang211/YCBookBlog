## 01.本端选型说明

### 1.1 为什么选 ExoPlayer 不选 MediaPlayer

| 对比项 | MediaPlayer | ExoPlayer (Media3) |
|-------|-------------|-------------------|
| 视频支持 | 需自己接 SurfaceView | PlayerView 开箱即用 |
| 播放列表 | 无，需自己管理 | Playlist API 原生支持 |
| 状态回调 | 简陋，易泄漏 | Listener 体系完整 |
| 倍速 | 6.0+，精度差 | `PlaybackParameters` 精细 |
| HTTP/HLS | 手动 | 内置 |
| 后台结合 | 需自己接 MediaSession | MediaSession 集成成熟 |

教学上两者都会碰：§02 MVP 用 `MediaPlayer` 20 行跑通（感受原始 API），§04 重构换 `ExoPlayer`（感受工程化收益），这个"先丑后好"的过程正是 Android 进阶要体会的。

### 1.2 UI 栈选型

- **XML + Activity/Fragment + ViewBinding**：与"Android 提升进阶"卷调性一致，纯 Java 全程可用；
- RecyclerView + DiffUtil 做列表；ViewModel + LiveData 做状态；
- 不引入 Compose（需 Kotlin，超出本端语言设定）。

### 1.3 项目目录结构

见 [01.架构设计 §1.7](/pages/mp5arch/#_1-7-目录结构三段式对齐) 的 `ui/ service/ data/` 三段式。

## 02.环境搭建与 MVP 骨架 【阶段①】

> 🎯 **阶段目标**：工程跑起来，点一个按钮，播放 assets 里硬编码的 mp3。不做列表、不做后台、不做状态管理。

**灵魂三问**（动手前先想清楚）：

> 1. 为什么 MVP 先用 `MediaPlayer` 而不是 ExoPlayer？（答：20 行 vs 引依赖+构建器；先让程序跑起来，再让它好起来）
> 2. 为什么用 ViewBinding 而不是 `findViewById`？
> 3. 为什么第一版不做 Service？（答：MVP 阶段 Activity 生命周期就是播放器生命周期，提前抽象是过度设计）

- Step 2.1 新建 Empty Activity 工程 + Gradle 依赖清单（viewBinding / media3 / room / lifecycle）
- Step 2.2 `assets/media/` 放入测试素材（仓库提供）
- Step 2.3 最小 UI：一个"播放/暂停"按钮 + 一个进度 TextView
- Step 2.4 `MediaPlayer` 硬编码播放 + `setOnPreparedListener` + 释放（onDestroy）
- 🧪 **验收**：点按钮出声，旋转屏幕不崩溃（`onDestroy` 释放重建）

## 03.媒体扫描与列表 【阶段②】

> 🎯 **阶段目标**：扫描设备音乐目录，展示"全部/音频/视频"三个 Tab 的媒体库列表，点击条目开始播放。

- Step 3.1 `MediaItem` 实体 + `MediaType` 枚举（对照架构篇 §1.3）
- Step 3.2 扫描器 `MediaScanner`：`MediaStore` 查询 vs 自扫描目录（讲透取舍：权限、性能、离线 SD 卡）
- Step 3.3 运行时权限：`READ_MEDIA_AUDIO/VIDEO`（API 33+）与旧版 `READ_EXTERNAL_STORAGE` 的分叉
- Step 3.4 `MediaMetadataRetriever` 读标题/艺术家/时长，封面提取到 cache 目录
- Step 3.5 `RecyclerView` + `ListAdapter` + `DiffUtil` 三个 Tab
- Step 3.6 扫描放 `ExecutorService` 后台线程，进度条通知 UI
- 🧪 **验收**：`adb push` 两首 mp3 + 一个 mp4 后下拉刷新，列表出现且元数据正确
- ⚠️ 常见坑：`MediaStore` 在国产 ROM 上的差异；`MediaMetadataRetriever` 不 release 导致 fd 泄漏

## 04.播放控制与状态管理 【阶段③⭐】

> 🎯 **阶段目标**：建立五端共享的 PlayerState 状态机；完成播放/暂停/上下首/进度拖动/倍速；视频画面层接入。

**灵魂三问**：

> 1. 播放状态的"唯一数据源"是谁？（答：PlayerService，UI 只是镜像）
> 2. 进度条拖动中 vs 自动前进，两种更新怎么不打架？（答：`isUserSeeking` 标志位 + 只在非拖动时同步）
> 3. 为什么把 `MediaPlayer` 换成 ExoPlayer？（对照 §1.1 表格逐条验证）

- Step 4.1 定义 `PlayerState` 五元组 + `PlayerService` 最小实现（普通类，非 Android Service）
- Step 4.2 引入 Media3 ExoPlayer，迁移 §02 的播放逻辑
- Step 4.3 `PlayerViewModel` + `LiveData<PlayerState>`；位置节流：Handler 500ms 轮询 vs ExoPlayer `setProgressUpdateListener`
- Step 4.4 SeekBar 双向绑定（拖动标志位）
- Step 4.5 播放模式（顺序/单曲/随机）与 `next()/previous()` 决策树
- Step 4.6 倍速 0.5x - 2.0x：`PlaybackParameters`
- Step 4.7 播放页 UI：大封面 + 控制bar + 视频模式切换（`PlayerView`，音频模式隐藏）
- ⚠️ 造 BUG 现场：先故意让 Activity 自己维护 `isPlaying`，运行看到 SeekBar 跳动，再修
- 🧪 **验收**：切后台回来状态不丢；倍速切换无爆音；视频模式可全屏

## 05.本地持久化 Room 【阶段④】

> 🎯 **阶段目标**：播放历史、我喜欢、断点续播、扫描结果缓存全部落库，重启 App 秒开。

- Step 5.1 Room 三件套：`@Entity`（MediaItem/PlayRecord/Favorite）、`@Dao`、`@Database`

- Step 5.6 `MediatorLiveData` 合并库数据与播放状态

## 06.后台播放 + 通知 【阶段⑤⭐⭐·平台能力高峰】

> 🎯 **阶段目标**：息屏后台继续播音频；通知栏与锁屏控件可控制播放；耳机线控/蓝牙可用；视频后台自动暂停。

**灵魂三问**：

> 1. 为什么必须是 Foreground Service？（答：后台执行限制 + 进程优先级 + 用户可见性三重原因）
> 2. MediaSessionCompat 和 Notification 是什么关系？（答：Session 是状态源，通知只是"显示器"之一，锁屏/手表/车载都读 Session）
> 3. 耳机拔出为什么要暂停？（`AudioManager.ACTION_AUDIO_BECOMING_NOISY`）

- Step 6.1 `PlayerService` 升级为真正的 `Service` + `startForeground`
- Step 6.2 通知渠道 + 常驻媒体通知（`NotificationCompat.MediaStyle` + `MediaSessionCompat.Token`）
- Step 6.3 MediaSession 四件套：`setPlaybackState` / `setMetadata` / `Callback`（接收通知栏动作）/ `setActive`
- Step 6.4 Android 12+ `PendingIntent.FLAG_IMMUTABLE`、13+ `POST_NOTIFICATIONS` 运行时权限
- Step 6.5 耳机拔出暂停 + `MediaButtonReceiver` 线控
- Step 6.6 视频模式 `onStop` 自动暂停（平台惯例）
- ⚠️ 造 BUG 现场：故意不 setPlaybackState，锁屏控件灰显，再修
- 🧪 **验收**：息屏 10 分钟音乐不停；锁屏可暂停/切歌；拔耳机立即暂停

## 09.均衡器 + 睡眠定时 + 设置 【阶段⑧】
