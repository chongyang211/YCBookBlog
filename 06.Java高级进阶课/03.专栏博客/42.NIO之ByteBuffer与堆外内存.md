## 42.1 开篇：一次"无故"的 OOMKilled——堆才用 60% 容器就被杀了

线上一个 Netty 网关，配置如下：

```bash
docker run --memory=4g \
  app:latest \
  -Xms2g -Xmx2g \
  -XX:MaxMetaspaceSize=256m
```

监控显示**堆使用率稳定在 60%（1.2GB）**，应用却被 OOMKilled。`dmesg` 一查：

```
Memory cgroup out of memory: Killed process 1 (java) 
total-vm:8520320kB, anon-rss:4194304kB, file-rss:0kB
```

**RSS 4GB 顶满整个容器**——而堆只用了 1.2GB。剩下的 2.8GB 去哪了？

`pmap -x <pid>` 一看：
```
Address           Kbytes  Mode    Mapping
00007f8c00000000  2097152 rw---   [ anon ]   ← 堆 2GB
00007f8b80000000  2680000 rw---   [ anon ]   ← 神秘的 2.6GB ★
00007f8a40000000   262144 rw---   [ anon ]   ← Metaspace 256M
...
```

继续用 NMT (Native Memory Tracking)：
```
Internal:
    Direct Buffers   2.5GB   ← 真凶
```

**真凶**：Netty `PooledByteBufAllocator` 默认开了 16 个 PoolArena × 单 chunk 16MB × 多级缓存，**默认上限 = 堆大小**（2GB）但实际使用还会膨胀。配上 17 篇讲过的 `-XX:MaxDirectMemorySize` **没有显式设上限**——堆外内存默认上限就是 `-Xmx`！

> 这一篇要解决的核心问题：
> - **ByteBuffer 是怎么工作的**？为什么 11 篇说"少一次拷贝"还不够？
> - **DirectByteBuffer 申请的 native 内存什么时候、被谁回收**？
> - **堆外内存泄漏怎么排查**？
> - **Netty 为什么不用 JDK 的 ByteBuffer**？

11 篇是**广度**——把 BIO/NIO/AIO 五种 IO 模型讲清楚；42 篇开始**走深度**——把 NIO 三大组件之一的 **Buffer** 一次性钻到 native 内存层。

## 42.2 ByteBuffer 状态机：四指针的不变式

### 42.2.1 capacity / position / limit / mark 的角色分工

ByteBuffer 是 NIO 最反直觉的 API——一个数组居然要用 4 个指针管理：

```java
public abstract class Buffer {
    private int mark = -1;
    private int position = 0;
    private int limit;
    private int capacity;
    // ...
}
```

**铁律**：`0 ≤ mark ≤ position ≤ limit ≤ capacity`

| 指针 | 含义 | 比喻 |
|---|---|---|
| `capacity` | 容量上限，**创建后不变** | 杯子总容量 |
| `position` | 下一个读 / 写位置 | 当前水位线 |
| `limit` | **可读 / 可写的边界** | 杯口刻度（可调） |
| `mark` | 临时书签，`reset()` 回到这里 | 折角的页面 |

**读写两种模式下指针含义会切换**——这是新手最容易卡住的点：

```
写模式（put）：
    position    →    要写入的下一个位置
    limit       →    capacity（能写到杯顶）

  ┌────────────┬─────────────┐
  │ 已写数据   │  剩余空间   │
  └────────────┴─────────────┘
   ↑           ↑              ↑
   0           position        limit=capacity

读模式（get）：
    position    →    要读取的下一个位置  
    limit       →    上次写到哪里（数据边界）

  ┌────────────┬─────────────┐
  │  已读数据  │ 待读数据    │
  └────────────┴─────────────┘
   ↑           ↑              ↑
   0           position        limit
                                       capacity
```

**写完之后必须 flip 才能读**——否则 limit 还是 capacity，读出来全是垃圾。这是 ByteBuffer 最经典的踩坑现场。

### 42.2.2 flip / compact / rewind / clear 四件套源码

```java
// flip：写模式 → 读模式
public Buffer flip() {
    limit = position;     // ★ 把"上次写到哪"记成 limit
    position = 0;         // ★ 从头开始读
    mark = -1;            // 丢弃 mark
    return this;
}

// rewind：再读一遍（不改 limit）
public Buffer rewind() {
    position = 0;
    mark = -1;
    return this;
}

// clear：写模式准备重新写（不擦数据，只重置指针！）
public Buffer clear() {
    position = 0;
    limit = capacity;
    mark = -1;
    return this;
}

// compact：保留未读数据，剩余空间继续写
public ByteBuffer compact() {
    int pos = position();
    int rem = limit() - pos;
    // 把 [position, limit) 的内容搬到 [0, rem)
    System.arraycopy(hb, ix(pos), hb, ix(0), rem);
    position(rem);                  // 紧接未读数据继续写
    limit(capacity());
    discardMark();
    return this;
}
```

**4 个方法的本质对照**：

| 方法 | 何时用 | 数据是否保留 | 指针变化 |
|---|---|---|---|
| `flip()` | 写完转读 | ✅ 全保留 | `limit ← position; position ← 0` |
| `clear()` | 读完转写 | ❌ 数据被覆盖 | `position ← 0; limit ← capacity` |
| `rewind()` | 重新读一遍 | ✅ 全保留 | 仅 `position ← 0` |
| `compact()` | 半读半写（未读完想继续写） | ✅ 未读部分保留 | 把未读数据搬到头部，position 跟随 |

**典型读写循环**（NIO 服务端代码标配）：

```java
ByteBuffer buf = ByteBuffer.allocate(1024);

// 写入
channel.read(buf);          // 写模式
buf.flip();                 // ★ 转读
process(buf);               // 读处理

// 部分读完，剩余继续接收
buf.compact();              // ★ 残留数据移到头部 + 转回写模式
channel.read(buf);          // 继续写
buf.flip();
process(buf);
```

**反直觉的 clear()**：名字像"清空"，但**不会擦数据**，只是把指针打回原点——下次写会覆盖旧数据。这个命名是 NIO API 设计的历史包袱。

### 42.2.3 视图缓冲区：asReadOnlyBuffer / slice / duplicate

ByteBuffer 提供 **3 种"视图"**——共享底层数组，独立维护指针：

```java
ByteBuffer original = ByteBuffer.wrap("HELLO_WORLD".getBytes());

// ① duplicate：完整副本视图（共享数据，独立指针）
ByteBuffer dup = original.duplicate();
// dup 和 original 共享底层 byte[]，但各自有 position/limit/mark

// ② slice：从 position 开始的子视图
original.position(6);
ByteBuffer sliced = original.slice();
// sliced 看到的是 "WORLD"，capacity = 5
// sliced 写入会反映到 original 的 [6, 11)

// ③ asReadOnlyBuffer：只读副本
ByteBuffer ro = original.asReadOnlyBuffer();
ro.put((byte) 'X');     // ❌ 抛 ReadOnlyBufferException
```

**实战用途**：
- `slice` 用于**分片解析协议**——TCP 报文头/体分别用 slice 获取，避免拷贝；
- `duplicate` 用于**多线程读同一份数据**——每个线程独立维护读位置；
- `asReadOnlyBuffer` 用于**对外暴露不可篡改的数据**——零拷贝防御性。

> Netty ByteBuf 的 `slice()` / `duplicate()` API 借鉴自这里，但实现更现代（refcount 引用计数）。

## 42.3 HeapByteBuffer vs DirectByteBuffer：真实拷贝路径

11 篇说 DirectBuffer "少一次拷贝"——这话**对但不准**。来看真实链路。

### 42.3.1 HeapBuffer 写 socket 的"临时 DirectBuffer"真相

```java
ByteBuffer heapBuf = ByteBuffer.allocate(1024);   // 堆内
heapBuf.put(data);
heapBuf.flip();
socketChannel.write(heapBuf);                     // ← 写网络
```

很多人以为"堆内字节直接写到内核"——错。真实流程：

```
[1] heapBuf 数据在 JVM 堆里                                       
        │                                                           
        ▼                                                           
[2] JVM 申请一块"临时 DirectBuffer"（堆外）  ← ★ 隐藏的拷贝          
        │                                                           
        ▼                                                           
[3] 数据从 heapBuf 拷贝到临时 DirectBuffer                            
        │                                                           
        ▼                                                           
[4] 系统调用 write(fd, directBufferAddress, len)                    
        │                                                           
        ▼                                                           
[5] 内核从 DirectBuffer 拷贝到 socket 发送缓冲区                     
        │                                                           
        ▼                                                           
[6] 网卡发送
```

**为什么 JVM 必须做这次拷贝**？因为**GC 会移动堆内对象**——内核态正在用这个地址做 DMA 时，如果 Java 堆的 GC 把数组挪了位置，**内核读到的是脏数据**。所以 JVM 在调用系统 write 前，**先把数据复制到不会被 GC 移动的堆外内存**，再传地址给内核。

而 DirectByteBuffer **天生就在堆外**——不会被 GC 移动，**省掉这一次拷贝**：

```
DirectBuffer 写 socket：
[1] DirectBuf 数据已在堆外                                        
        │                                                          
        ▼                                                          
[2] 系统调用 write(fd, directBufferAddress, len)                   
        │                                                          
        ▼                                                          
[3] 内核从 DirectBuffer 拷贝到 socket 发送缓冲区                    
        │                                                          
        ▼                                                          
[4] 网卡发送
```

### 42.3.2 IOUtil.write 源码逐行剖析

直接看 JDK 内部实现 `sun.nio.ch.IOUtil.write`（精简版）：

```java
static int write(FileDescriptor fd, ByteBuffer src, ...) throws IOException {
    if (src instanceof DirectBuffer) {
        return writeFromNativeBuffer(fd, src, ...);   // ✅ 直走 native
    }

    // ⚠ HeapBuffer 走这条路：必须先拷贝到临时 DirectBuffer
    int pos = src.position();
    int lim = src.limit();
    int rem = lim - pos;

    ByteBuffer bb = Util.getTemporaryDirectBuffer(rem);   // ★ 申请临时 DB
    try {
        bb.put(src);                                       // ★ 拷贝
        bb.flip();
        src.position(pos);                                 // 还原 src position
        int n = writeFromNativeBuffer(fd, bb, ...);
        if (n > 0) src.position(pos + n);
        return n;
    } finally {
        Util.offerFirstTemporaryDirectBuffer(bb);          // 还回缓存池
    }
}
```

**Util.getTemporaryDirectBuffer 的玄机**——它是个 **ThreadLocal 缓存池**：

```java
// sun.nio.ch.Util
private static final ThreadLocal<BufferCache> bufferCache = ...;

public static ByteBuffer getTemporaryDirectBuffer(int size) {
    BufferCache cache = bufferCache.get();
    ByteBuffer buf = cache.get(size);              // 复用
    if (buf == null) buf = ByteBuffer.allocateDirect(size);
    return buf;
}
```

**坑点**：每个线程各持一个 cache，缓存的临时 DirectBuffer 长期不释放——**线程数多 + IO 频繁的应用，堆外内存会被 ThreadLocal 缓存"吃掉"**。这就是为什么很多 Netty 应用即使没用 PooledByteBufAllocator 也会有几百 MB 堆外占用。

`-Djdk.nio.maxCachedBufferSize=<bytes>` 可以限制 ThreadLocal 缓存大小（JDK 8u102+）——**生产建议必设**。

## 42.4 DirectByteBuffer 的回收链路：Cleaner + PhantomReference

DirectByteBuffer 的内存**不在 JVM 堆内**——GC 不会直接管它。回收链路靠 **Cleaner + PhantomReference**。

### 42.4.1 构造函数里的 native 申请

```java
// java.nio.DirectByteBuffer (JDK 17 简化)
DirectByteBuffer(int cap) {
    super(-1, 0, cap, cap);
    boolean pa = VM.isDirectMemoryPageAligned();
    int ps = Bits.pageSize();
    long size = Math.max(1L, (long)cap + (pa ? ps : 0));
    
    Bits.reserveMemory(size, cap);                 // ★ 全局账簿登记
    
    long base = 0;
    try {
        base = UNSAFE.allocateMemory(size);        // ★ malloc native 内存
    } catch (OutOfMemoryError x) {
        Bits.unreserveMemory(size, cap);
        throw x;
    }
    UNSAFE.setMemory(base, size, (byte) 0);
    address = base;
    
    cleaner = Cleaner.create(this, new Deallocator(base, size, cap));   // ★ 注册回收钩子
    att = null;
}
```

**3 个关键动作**：
1. `Bits.reserveMemory` —— 在**全局账簿**记账，超 `MaxDirectMemorySize` 抛 OOM；
2. `UNSAFE.allocateMemory` —— 真正调用 `malloc` 申请 native 内存；
3. `Cleaner.create` —— 注册"幽灵引用 + 回调"，DirectByteBuffer 对象被 GC 时触发释放。

### 42.4.2 Cleaner 链表与 ReferenceHandler 线程

`Cleaner` 本质是一个 **PhantomReference 子类**：

```java
public class Cleaner extends PhantomReference<Object> {
    private static final ReferenceQueue<Object> dummyQueue = new ReferenceQueue<>();
    private static Cleaner first = null;            // 全局双向链表头
    private Cleaner next, prev;
    private final Runnable thunk;                    // 释放回调

    public static Cleaner create(Object referent, Runnable thunk) {
        Cleaner c = new Cleaner(referent, thunk);
        // 加入全局链表（防止 Cleaner 自己被 GC）
        synchronized (lock) {
            c.next = first;
            if (first != null) first.prev = c;
            first = c;
        }
        return c;
    }

    public void clean() {                            // ★ 释放方法
        if (!remove(this)) return;                   // CAS 防重复
        try {
            thunk.run();                             // 执行 Deallocator
        } catch (Throwable e) { ... }
    }
}

// DirectByteBuffer 内部的 Deallocator
private static class Deallocator implements Runnable {
    private long address;
    private long size;
    private int capacity;
    public void run() {
        if (address == 0) return;
        UNSAFE.freeMemory(address);                  // ★ free native 内存
        address = 0;
        Bits.unreserveMemory(size, capacity);        // ★ 全局账簿减账
    }
}
```

**完整回收时序**：

```
[1] DirectByteBuffer 对象不可达（业务无引用）
            │
            ▼
[2] Young GC / Full GC 扫描到这个 DBB 对象
            │
            ▼
[3] 与 DBB 绑定的 Cleaner（PhantomReference）入 ReferenceQueue
            │
            ▼
[4] JVM 启动时创建的高优先级守护线程 ReferenceHandler 轮询队列
            │
            ▼
[5] ReferenceHandler 调用 cleaner.clean()
            │
            ▼
[6] Cleaner.thunk.run() → Deallocator.run()
            │
            ▼
[7] UNSAFE.freeMemory(address) → glibc free()
            │
            ▼
[8] Bits.unreserveMemory 减账 → 释放配额
```

**最关键的一点**：**回收依赖 GC 触发**——只有 DirectByteBuffer 这个**包装对象**被 GC，native 内存才会被释放。这就直接埋下了 §42.6 的 4 大泄漏现场。

### 42.4.3 JDK 8 sun.misc.Cleaner vs JDK 9+ jdk.internal.ref.Cleaner

JDK 9 模块化后，`sun.misc.Cleaner` 移到 `jdk.internal.ref.Cleaner`——**业务代码默认访问不到**。

```java
// JDK 8 的"野路子"——主动触发回收
ByteBuffer buf = ByteBuffer.allocateDirect(1024);
((sun.nio.ch.DirectBuffer) buf).cleaner().clean();    // ✅ JDK 8 可用

// JDK 9+：被模块系统挡住
((sun.nio.ch.DirectBuffer) buf).cleaner().clean();    // ❌ IllegalAccessError
```

**JDK 9+ 替代方案**——使用新的 `java.lang.ref.Cleaner` 公开 API（24 篇讲过）：

```java
// 但 DirectByteBuffer 自身的 Cleaner 仍是内部 API
// 想主动释放只能：
//   1. 设 buf = null + System.gc()  ← 不可控
//   2. --add-opens java.base/jdk.internal.ref=ALL-UNNAMED 后反射调
//   3. 用第三方库 sun.misc.Unsafe 直接 freeMemory（自管 address）
```

**生产建议**：**永远不要主动调 cleaner.clean()**——线上踩过的坑：
- A 线程用 `buf.put(data)` 还在写；
- B 线程提前调 `clean()` 释放了 native 内存；
- A 线程写到野指针 → JVM crash（不是抛异常，是 SIGSEGV）。

## 42.5 Bits 全局账簿与 -XX:MaxDirectMemorySize 的真相

`java.nio.Bits` 是堆外内存的**全局会计**：

```java
// JDK 17 (java.nio.Bits 简化版)
private static final AtomicLong RESERVED_MEMORY = new AtomicLong();
private static final AtomicLong TOTAL_CAPACITY = new AtomicLong();
private static final AtomicLong COUNT = new AtomicLong();

private static final long MAX_MEMORY = VM.maxDirectMemory();

static void reserveMemory(long size, long cap) {
    if (tryReserveMemory(size, cap)) return;          // 配额够：登记
    
    // 配额不够 —— 触发清理
    final JavaLangRefAccess jlra = SharedSecrets.getJavaLangRefAccess();
    boolean interrupted = false;
    try {
        do {
            try {
                refprocActive = jlra.waitForReferenceProcessing();   // 等 GC
            } catch (InterruptedException e) {
                interrupted = true;
                refprocActive = false;
            }
        } while (!tryReserveMemory(size, cap) && refprocActive);
        
        // 还是不够 —— 主动 GC ★
        System.gc();                                   // ★ 求 Full GC
        
        // 再尝试 9 次（每次 sleep 增大）
        long sleepTime = 1;
        int sleeps = 0;
        while (true) {
            if (tryReserveMemory(size, cap)) return;
            if (sleeps >= MAX_SLEEPS) break;
            try {
                if (!jlra.waitForReferenceProcessing()) {
                    Thread.sleep(sleepTime);
                    sleepTime <<= 1;
                    sleeps++;
                }
            } catch (InterruptedException e) {
                interrupted = true;
            }
        }
        
        // ★ 最终失败，抛 OOM
        throw new OutOfMemoryError(
            "Cannot reserve " + size + " bytes of direct buffer memory ...");
    } finally {
        if (interrupted) Thread.currentThread().interrupt();
    }
}
```

**关键 4 点**：

#### ① Bits 是 ByteBuffer.allocateDirect 的"门卫"
- 走 `allocateDirect` 的所有内存都登记 → 看得见、可控；
- **`Unsafe.allocateMemory` 直接申请的 native 不走 Bits**——账簿外内存（参见 §42.6.3）。

#### ② -XX:MaxDirectMemorySize 的默认值
看 `VM.maxDirectMemory()` 的源码：

```java
public static long maxDirectMemory() {
    if (directMemory == 0) directMemory = Runtime.getRuntime().maxMemory();
    return directMemory;
}
```

**没显式设 = 默认等于 -Xmx**！17 篇就强调过这一点：
- `-Xmx2g` → 堆外默认上限**也是 2GB**；
- 容器只有 4GB → 堆 2GB + 堆外 2GB = 顶满。

**生产必设**：
```bash
-XX:MaxDirectMemorySize=512m       # 显式上限
-Djdk.nio.maxCachedBufferSize=8192 # 限制 ThreadLocal 临时 DB 缓存
```

#### ③ 账簿超额触发 System.gc()
配额不够时 Bits 会**主动调 `System.gc()`**——这个机制反过来又触发新坑（见 §42.6.2）：
- 一旦设了 `-XX:+DisableExplicitGC`（很多团队的标配 JVM 参数）；
- `System.gc()` 被屏蔽 → DirectByteBuffer 包装对象不及时回收；
- 9 次尝试后仍超额 → 抛 `OutOfMemoryError: Direct buffer memory`。

#### ④ 与 NMT 的差异
- **Bits** 只看到 `allocateDirect` 走的内存；
- **NMT (Native Memory Tracking)** 看到所有 JVM 内部的 native 申请；
- **pmap** 看到 OS 视角的全部 RSS（含 JNI、glibc malloc、jemalloc fragment）；
- 三者数字往往**不一致**——排查泄漏要三个一起看（详见 §42.7）。

## 42.6 堆外内存泄漏 4 种典型现场

### 42.6.1 现场一：Full GC 触发不及时（Old 区有空间）

```java
// 高频小 Buffer 场景
while (true) {
    ByteBuffer buf = ByteBuffer.allocateDirect(1024);   // 1KB
    process(buf);
    // buf 出循环立刻不可达
}
```

**症状**：
- 堆使用率不高（20%~30%），Young GC 频繁但不触发 Full GC；
- 但堆外内存持续上涨；
- 因为 DirectByteBuffer **包装对象** 1KB 都不到——晋升老年代后**老年代远没满**，触发不了 Full GC；
- native 内存却有 1MB、10MB 在那里没释放。

**复现 + 监控**：
```
堆: 30% ──── 30% ──── 35% ──── 35%   ← 看堆没事
堆外: 200M ─ 800M ─── 1.5G ─── 2.0G   ← 这边在涨
                                            ↑ OOM 时刻
```

**修复**：
```bash
# 选项 1：让 Bits 主动 System.gc()（默认就是开启）
# 不要加 -XX:+DisableExplicitGC

# 选项 2：复用 DirectBuffer
ByteBuffer reusable = ByteBuffer.allocateDirect(1024);
while (true) {
    reusable.clear();
    process(reusable);
}

# 选项 3：用 Netty 的对象池（PooledByteBufAllocator）
```

### 42.6.2 现场二：System.gc 被 -XX:+DisableExplicitGC 屏蔽

某 RPC 框架团队的真实事故：
```bash
# 团队标配 JVM 参数（继承自老业务）
-Xmx4g -XX:+UseG1GC -XX:+DisableExplicitGC   # ★ 屏蔽 System.gc
```

切到 NIO + DirectByteBuffer 后：
- 业务每秒 5000 次小 IO，每次申请 4KB DirectBuffer；
- `Bits.reserveMemory` 不够 → 调 `System.gc()` → **被屏蔽**；
- 内存不释放 → 9 次重试后抛 `OutOfMemoryError: Direct buffer memory`。

**修复**：
```bash
# 选项 1：移除 DisableExplicitGC（推荐）
# 选项 2：保留但加 ExplicitGCInvokesConcurrent（让 G1 用并发模式响应 System.gc）
-XX:+DisableExplicitGC -XX:+ExplicitGCInvokesConcurrent     # ❌ 矛盾，前者会屏蔽

# 实际有效的写法：去掉 Disable，仅留 Concurrent
-XX:+ExplicitGCInvokesConcurrent
```

### 42.6.3 现场三：Unsafe.allocateMemory 绕开 Cleaner

```java
// ❌ 危险代码
public class FastBuffer {
    private final long address;
    public FastBuffer(int size) {
        this.address = UNSAFE.allocateMemory(size);   // 不走 Bits / 不带 Cleaner
    }
    // 业务用完忘了调 free —— native 内存永久泄漏
}
```

**特征**：
- `Bits.RESERVED_MEMORY` 看起来很小；
- `pmap` 显示进程 RSS 持续增长；
- NMT `Internal` 类别可能看不到（`Other` 或 `Unknown`）。

**修复**：所有 `Unsafe.allocateMemory` 必须配 try-finally + `UNSAFE.freeMemory`，或用 `java.lang.ref.Cleaner` 注册自动回收（24 篇讲过的姿势）。

### 42.6.4 现场四：Netty 直接内存（PoolArena）泄漏

Netty 的 `ByteBuf` 用引用计数管理：

```java
// ❌ 经典泄漏：忘记 release
ByteBuf buf = channel.alloc().directBuffer(1024);
process(buf);
// 漏 buf.release();  ← refCnt 不归零，永不回到池
```

**特征**：
- Netty 启动 ResourceLeakDetector 后日志告警 `LEAK: ByteBuf.release() was not called before it's garbage-collected.`；
- 进程 RSS 持续上涨；
- `PooledByteBufAllocatorMetric` 显示 `usedDirectMemory` 不释放。

**修复**：
- 任何分配的 `ByteBuf` 必须 `release()` 或交给 `SimpleChannelInboundHandler`（自动释放）；
- 启动加 `-Dio.netty.leakDetection.level=PARANOID`（开发环境）；
- 生产配 `-Dio.netty.leakDetection.level=ADVANCED`（采样 1%）。

## 42.7 排查工具链：NMT + pmap + jcmd 三件套

### 42.7.1 NMT (Native Memory Tracking) ——JVM 视角

```bash
# 启动时开启
java -XX:NativeMemoryTracking=detail -jar app.jar

# 任意时刻查询
jcmd <pid> VM.native_memory summary

# 输出示例
Total: reserved=4523072KB, committed=2154872KB
-     Java Heap (reserved=2097152KB, committed=2097152KB)
                            (mmap: reserved=2097152KB, committed=2097152KB) 
-       Internal (reserved=856321KB, committed=856321KB)         ← ★ DirectByteBuffer 在这
                            (malloc=856288KB) 
-           Code (reserved=247000KB, committed=68000KB) 
-             GC (reserved=89000KB, committed=89000KB)
-       Compiler (reserved=12000KB, committed=12000KB)
-         Symbol (reserved=22000KB, committed=22000KB)
- Native Memory Tracking (reserved=8000KB, committed=8000KB)

# 拍快照对比（baseline + diff）
jcmd <pid> VM.native_memory baseline
... 等业务跑一段时间 ...
jcmd <pid> VM.native_memory summary.diff       # 看增量！
```

**关键技巧**：**先 baseline 再 diff**——绝对值意义不大，**增量才能定位泄漏**。

### 42.7.2 pmap —— OS 视角

```bash
pmap -x <pid> | sort -k 2 -rn | head -20

# 找异常大块
00007f8b80000000 2680000 2680000 2680000 rw---   [ anon ]   ← 单块 2.6GB 太可疑
```

**对照 NMT**：
- pmap 显示 RSS = 4GB；
- NMT 显示 committed = 3GB；
- **差额 1GB** = JVM 看不到的 native（JNI、glibc 内部 fragment、第三方 native 库）。

### 42.7.3 jcmd VM.native_memory + GC.run 联调

```bash
# 1. 拍 baseline
jcmd <pid> VM.native_memory baseline

# 2. 强制 Full GC
jcmd <pid> GC.run

# 3. 对比 diff
jcmd <pid> VM.native_memory summary.diff

# 如果 GC 后 Internal 大幅下降 → DirectByteBuffer 泄漏（GC 前没释放）
# 如果 GC 后 Internal 不变 → 不是 ByteBuffer 问题，可能是 JNI / Unsafe 直接申请
```

### 42.7.4 ByteBuffer 视角：自带的 MBean

```java
import java.lang.management.ManagementFactory;
import java.lang.management.BufferPoolMXBean;

for (BufferPoolMXBean pool : ManagementFactory.getPlatformMXBeans(BufferPoolMXBean.class)) {
    System.out.printf("%s: count=%d, used=%dMB, capacity=%dMB%n",
        pool.getName(),
        pool.getCount(),
        pool.getMemoryUsed() / 1024 / 1024,
        pool.getTotalCapacity() / 1024 / 1024);
}

// 输出：
// direct: count=1024, used=512MB, capacity=512MB        ← Bits 视角
// mapped: count=10,   used=2048MB, capacity=2048MB      ← MappedByteBuffer
```

**生产监控**：把 `direct` 池接入 Prometheus，配上限告警——比等 OOM 早发现 30 分钟。

## 42.8 零拷贝在 Java 中的对应 API

11 篇讲了零拷贝原理，这里专攻 **Java API 对应关系**——什么场景调什么方法：

### 42.8.1 mmap：MappedByteBuffer

```java
try (FileChannel ch = FileChannel.open(Path.of("big.dat"), READ, WRITE)) {
    MappedByteBuffer mmap = ch.map(MapMode.READ_WRITE, 0, ch.size());
    // 后续读写 mmap 直接操作 OS page cache，不走 read/write 系统调用
    mmap.put(0, (byte) 0xFF);
    mmap.force();   // 同步刷盘
}
```

**适用**：随机读写大文件（DB index、日志聚合、Kafka log segment）。

**坑点**：
- `MappedByteBuffer` 也是 DirectByteBuffer 子类——**回收时机靠 GC**；
- 解除映射只能等 GC 或重启 JVM；
- 文件 > 2GB 要分段 map（map 单次最大 Integer.MAX_VALUE）；
- mmap 的 Page Fault 计入用户进程 RSS，**容器内存监控会显示成"应用占用"**。

### 42.8.2 sendfile：FileChannel.transferTo

```java
// 文件 → socket，零拷贝
try (FileChannel file = FileChannel.open(path, READ);
     SocketChannel sock = SocketChannel.open(addr)) {
    long transferred = 0;
    long total = file.size();
    while (transferred < total) {
        transferred += file.transferTo(transferred, total - transferred, sock);
    }
}
```

**底层**：Linux 上对应 `sendfile(2)` 系统调用——**数据全程在内核态**，不进用户态。

**对照传统拷贝（4 次拷贝 + 4 次上下文切换）**：

```
传统 read/write：
  磁盘 ─DMA→ 内核 page cache ─CPU→ 用户 buffer ─CPU→ 内核 socket buffer ─DMA→ 网卡
  
sendfile：
  磁盘 ─DMA→ 内核 page cache ─CPU→ 内核 socket buffer ─DMA→ 网卡
  （省掉用户态的 1 次拷贝 + 2 次上下文切换）

sendfile + DMA scatter-gather (Linux 2.4+)：
  磁盘 ─DMA→ 内核 page cache ─DMA→ 网卡
  （连最后那次 CPU 拷贝也省了）
```

**Kafka 的高吞吐秘密之一**：log 文件 → consumer socket 全走 `transferTo`。

### 42.8.3 splice / tee 与 FileChannel.transferFrom

```java
// transferFrom：socket → 文件
try (SocketChannel sock = SocketChannel.open(addr);
     FileChannel file = FileChannel.open(path, WRITE, CREATE)) {
    long received = 0;
    while ((received += file.transferFrom(sock, received, Long.MAX_VALUE)) > 0) {
        // ...
    }
}
```

JDK 内部对应 Linux `splice(2)` ——通过内核 pipe 中转，仍然零用户态拷贝。

**总结对照表**：

| Java API | Linux 系统调用 | 用途 |
|---|---|---|
| `MappedByteBuffer` | `mmap` | 大文件随机读写 |
| `FileChannel.transferTo` | `sendfile` / `splice` | 文件→socket |
| `FileChannel.transferFrom` | `splice` | socket→文件 |
| `Unsafe.copyMemory` | `memcpy` | 堆外内存间拷贝 |

## 42.9 Netty 为什么自造 ByteBuf 不用 JDK 的 ByteBuffer

设计层面 Netty 有 5 大不满：

| 痛点 | JDK ByteBuffer | Netty ByteBuf |
|---|---|---|
| ① 读写指针 | 共用 position（要 flip） | **readerIndex + writerIndex 分离**——不用 flip |
| ② 容量 | 固定（不能扩容） | **动态扩容**（capacity 可变） |
| ③ 池化 | ThreadLocal 临时缓存 | **PooledByteBufAllocator**（jemalloc 风格 PoolArena） |
| ④ 引用计数 | 无（依赖 GC + Cleaner） | **ReferenceCounted**（refCnt 显式管理） |
| ⑤ 复合视图 | 只能 slice 单个连续段 | **CompositeByteBuf**（多块拼装零拷贝） |

```java
// JDK ByteBuffer 的尴尬
buf.put(data1);
buf.flip();                 // 转读
process(buf);
buf.compact();              // 转写
buf.put(data2);             // ← 4 行才完成的事

// Netty ByteBuf 的优雅
buf.writeBytes(data1);
process(buf);               // 内部读，不影响写指针
buf.writeBytes(data2);      // 直接继续写
```

**reader/writer 双指针设计**最体现差距——读和写互不打扰，对协议解析 / 编码场景**直接降低心智成本一个数量级**。

`PooledByteBufAllocator` 也是大杀器——内部参考 jemalloc：
- **PoolArena × 16**（默认 = CPU 核数 × 2）——分散竞争；
- **PoolChunk** 16MB 大块 → 切分成 PageRun → 切分成 SubPage；
- 每线程 `PoolThreadCache` 缓存最近释放的 ByteBuf——**99% 分配命中线程缓存**；
- 释放回池避免反复 `malloc`/`free`。

> Netty 把 JDK ByteBuffer 当**底层 native 内存载体**——`PoolArena` 内部仍然 `ByteBuffer.allocateDirect`——但**对外的 API 完全自造**。这也回答了第 11 篇结尾埋的伏笔："Netty 是 NIO 的最佳实践"。

## 42.10 实战 5 条死规矩

1. **生产必设 `-XX:MaxDirectMemorySize`**——别让默认 = `-Xmx` 把容器顶满；
2. **必设 `-Djdk.nio.maxCachedBufferSize`**——限制 ThreadLocal 临时 DB 缓存（如 `=8192`）；
3. **不要加 `-XX:+DisableExplicitGC`**——会让 Bits 的 fallback System.gc 失效，DirectBuffer 提前 OOM；可以用 `-XX:+ExplicitGCInvokesConcurrent` 替代；
4. **生产必接 `BufferPoolMXBean` 监控**——把 direct 池 used/capacity 接 Prometheus + 阈值告警；
5. **优先用 Netty `PooledByteBufAllocator` + 严格 release 检查**——比裸用 ByteBuffer 安全得多；leakDetection 至少开 ADVANCED。

## 42.11 灵魂三问 & 速查表 & 下一篇预告

### 42.11.1 灵魂三问

1. **HeapByteBuffer 写 socket 真的是"零拷贝"吗？**
   - 不是。HeapByteBuffer 写 socket 时 JDK 会**先拷贝到一个临时 DirectByteBuffer**（JVM 不能让 native 调用直接读 GC 可能移动的堆内数据）；
   - 临时 DB 在 ThreadLocal 缓存里复用——这就是为什么很多 Netty 应用即使没用 PooledByteBufAllocator，堆外仍占几百 MB；
   - DirectByteBuffer 才能省掉这次拷贝——直接把 native 地址传给系统调用。

2. **为什么 DirectByteBuffer 的回收依赖 GC 不能立即释放？**
   - JVM 不直接管理 native 内存——靠 PhantomReference + Cleaner 在 DirectByteBuffer **包装对象** 被 GC 时触发释放；
   - 包装对象很小（几十字节），不容易触发 Full GC；
   - 后果：堆使用率 30% 时堆外可能已经几个 GB 不释放；
   - 应对：① 让 Bits 主动 System.gc（不要 DisableExplicitGC） ② 复用 Buffer ③ 用 Netty 池化。

3. **Bits、NMT、pmap、BufferPoolMXBean 看到的数字为什么不一致？**
   - **Bits**: 只看 `ByteBuffer.allocateDirect` 走的内存（`MaxDirectMemorySize` 配额管这个）；
   - **BufferPoolMXBean**: 等同 Bits 的视角 + MappedByteBuffer；
   - **NMT**: 全部 JVM 内部的 native（堆 + Code Cache + GC + Symbol + Internal 等），但**不含 JNI 库自己 malloc 的**；
   - **pmap (RSS)**: OS 视角，包含全部—— JVM 内部 + JNI + glibc fragment + mmap 文件页；
   - 排查泄漏：先 `BufferPoolMXBean` 看 ByteBuffer，再 `NMT diff` 看 JVM 视角，最后 `pmap` 看 OS 实际占用。

### 42.11.2 速查表

| 想做的事 | API / 命令 |
|---|---|
| 创建堆外 Buffer | `ByteBuffer.allocateDirect(size)` |
| 写完转读 | `buf.flip()` |
| 读完转写（保留未读） | `buf.compact()` |
| 重置指针重新写（不擦数据） | `buf.clear()` |
| 内存映射文件 | `channel.map(MapMode.READ_WRITE, 0, size)` |
| 文件→socket 零拷贝 | `fileChannel.transferTo(pos, count, socketChannel)` |
| 限制堆外上限 | `-XX:MaxDirectMemorySize=512m` |
| 限制临时 DB 缓存 | `-Djdk.nio.maxCachedBufferSize=8192` |
| 开启 NMT | `-XX:NativeMemoryTracking=detail` |
| 排查堆外 | `jcmd <pid> VM.native_memory summary.diff` |
| 监控 ByteBuffer 池 | `ManagementFactory.getPlatformMXBeans(BufferPoolMXBean.class)` |
| Netty 泄漏检测 | `-Dio.netty.leakDetection.level=ADVANCED` |
