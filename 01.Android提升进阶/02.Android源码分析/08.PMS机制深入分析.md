### 01.PMS概述与设计背景
<a name="01"></a>

#### 1.1 PMS在系统中的角色

PackageManagerService（PMS）是Android系统中最核心的系统服务之一，负责管理设备上所有已安装应用的信息。它运行在SystemServer进程中，在系统启动的早期阶段就被创建。

从全局角度看PMS的位置：

```
Android系统服务架构中PMS的位置：
                         ┌─────────────────┐
                         │   Applications   │
                         │  (各种应用进程)    │
                         └────────┬─────────┘
                                  │ Binder IPC
                         ┌────────▼─────────┐
                         │  PackageManager   │
                         │   (客户端代理)     │
                         └────────┬─────────┘
                                  │
                    ┌─────────────▼──────────────┐
                    │      SystemServer进程        │
                    │  ┌─────────────────────┐    │
                    │  │ PackageManagerService│    │
                    │  │  (PMS核心服务)       │    │
                    │  └──────────┬──────────┘    │
                    │             │                │
                    │  ┌──────────▼──────────┐    │
                    │  │    installd          │    │
                    │  │ (Native安装守护进程)  │    │
                    │  └─────────────────────┘    │
                    └─────────────────────────────┘
```

PMS的核心定位是：**Android系统的"应用注册中心"**。所有应用的组件信息、权限声明、签名信息都在PMS中注册和管理。AMS启动Activity时需要向PMS查询组件信息，应用安装时由PMS完成解析和注册，权限检查也由PMS提供数据支持。

#### 1.2 PMS的核心职责

PMS承担的职责非常广泛，从以下几个维度来理解：

```
PMS核心职责全景图：
├── 1.包信息管理
│   ├── 解析所有APK的AndroidManifest.xml
│   ├── 维护包名→Package的全局映射
│   ├── 维护组件→包的反向映射
│   └── 提供查询接口（getPackageInfo、resolveActivity等）
├── 2.安装与卸载
│   ├── 新安装：复制APK→解析→dex编译→注册组件→发广播
│   ├── 覆盖安装：签名校验→替换→数据迁移
│   ├── 卸载：移除APK→清理数据→注销组件→发广播
│   └── Split APK分包安装
├── 3.权限管理
│   ├── 权限定义（normal/dangerous/signature/privileged）
│   ├── 安装时权限自动授予
│   ├── 运行时权限动态授予/撤销
│   └── 权限检查（checkPermission）
├── 4.签名与安全
│   ├── APK签名验证（V1/V2/V3/V4）
│   ├── 覆盖安装的签名一致性检查
│   ├── SharedUserId签名匹配
│   └── 安装来源验证
├── 5.Intent解析
│   ├── 显式Intent的组件查找
│   ├── 隐式Intent的Filter匹配
│   └── 多结果时的优先级排序
└── 6.数据持久化
    ├── packages.xml（包信息）
    ├── packages-backup.xml（备份）
    ├── runtime-permissions.xml（运行时权限）
    └── package-restrictions.xml（用户限制）
```

#### 1.3 PMS与其他系统服务的关系

PMS不是孤立运行的，它与多个系统服务存在紧密协作：

**PMS与AMS的关系**：AMS在启动四大组件时，都需要先通过PMS查询组件信息。例如startActivity时，AMS调用PMS的resolveActivity获取ActivityInfo，确认目标组件存在且调用者有权限。

**PMS与installd的关系**：PMS自身运行在Java层，但实际的文件操作（如复制APK到/data/app、创建数据目录、执行dex编译）由Native层的installd守护进程完成。两者通过Binder通信。installd拥有root权限，能够操作系统受保护的目录。

**PMS与UserManagerService的关系**：Android支持多用户，每个用户可以有不同的应用安装状态。PMS需要与UserManagerService协作，维护每个用户的包状态（如是否安装、是否禁用）。

#### 2.1 SystemServer中PMS的创建

PMS在SystemServer的startBootstrapServices阶段创建，这是系统启动最早的服务启动阶段之一：

```java
// frameworks/base/services/java/com/android/server/SystemServer.java
private void startBootstrapServices() {
    // 先启动Installer服务（PMS依赖它）
    Installer installer = mSystemServiceManager.startService(Installer.class);
    // 启动AMS
    mActivityManagerService = ActivityManagerService.Lifecycle.startService(
            mSystemServiceManager, atm);
    // 创建PMS实例——注意这里直接调用静态方法
    mPackageManagerService = PackageManagerService.main(mSystemContext, 
            installer, mFactoryTestMode != FactoryTest.FACTORY_TEST_OFF, mOnlyCore);
    // PMS创建后立即设置给AMS
    mActivityManagerService.setSystemProcess();
```

#### 2.3 包扫描的核心源码

包扫描是PMS启动中最耗时的阶段，核心方法是`scanDirTracedLI`和`scanPackageLI`：

```java
private void scanDirLI(File scanDir, int parseFlags, int scanFlags, long currentTime) {
    final File[] files = scanDir.listFiles();
    if (ArrayUtils.isEmpty(files)) return;
    
    // 并行解析提升速度
    try (ParallelPackageParser parallelPackageParser = new ParallelPackageParser(
            mSeparateProcesses, mOnlyCore, mMetrics, mCacheDir, mPackageParserCallback)) {
        for (File file : files) {
            final boolean isPackage = (isApkFile(file) || file.isDirectory())
                    && !PackageInstallerService.isStageName(file.getName());
            if (!isPackage) continue;
            parallelPackageParser.submit(file, parseFlags);
        }
        // 收集并处理解析结果
        for (;;) {
            ParallelPackageParser.ParseResult parseResult = parallelPackageParser.take();
            if (parseResult == null) break;
            if (parseResult.throwable == null) {
                addForInitLI(parseResult.pkg, parseFlags, scanFlags, currentTime, null);
            }
        }
    }
}
```

`commitScanResultLocked`将包信息写入PMS全局数据结构：

```java
private void commitScanResultLocked(ScanResult result) {
    final PackageSetting pkgSetting = result.pkgSetting;
    // 注册包信息到全局Map
    mSettings.insertPackageSettingLPw(pkgSetting, result.pkg);
    // 注册四大组件到ComponentResolver
    if (result.pkg != null) {
        mComponentResolver.addAllComponents(result.pkg, chatty);
    }
    // 注册KeySet信息
    KeySetManagerService ksms = mSettings.mKeySetManagerService;
    ksms.addScannedPackageLPw(result.pkg);
}
```

```java
public class PackageParser {
    public Package parsePackage(File packageFile, int flags, boolean useCaches) {
        Package parsed = useCaches ? getCachedResult(packageFile, flags) : null;
        if (parsed != null) return parsed;
        if (packageFile.isDirectory()) {
            parsed = parseClusterPackage(packageFile, flags); // Split APK
        } else {
            parsed = parseMonolithicPackage(packageFile, flags); // 单APK
        }
        cacheResult(packageFile, flags, parsed);
        return parsed;
    }
}
```

#### 4.3 四大组件解析流程

Activity解析涉及多种启动模式和标志位：

```java
private Activity parseActivity(Package owner, Resources res,
        XmlResourceParser parser, int flags, String[] outError, boolean receiver) {
    Activity a = new Activity(mParseActivityArgs, new ActivityInfo());
    ActivityInfo ai = a.info;
    ai.name = parser.getAttributeValue(null, "name");
    ai.launchMode = parser.getAttributeIntValue(null, "launchMode", LAUNCH_MULTIPLE);
    ai.screenOrientation = parser.getAttributeIntValue(null, "screenOrientation", UNSPECIFIED);
    // 解析<intent-filter>
    while ((type = parser.next()) != END_DOCUMENT) {
        if (parser.getName().equals("intent-filter")) {
            ActivityIntentInfo intent = new ActivityIntentInfo(a);
            parseIntent(res, parser, true, true, intent, outError);
            a.intents.add(intent);
        }
    }
    return a;
}
```

### 05.APK安装流程源码分析
<a name="05"></a>

#### 5.1 安装入口与Session机制

从Android 5.0开始，APK安装引入了Session机制：

```
APK安装的完整流程：
用户点击安装 → PackageInstaller UI
  → PackageInstallerSession.commit()
    → PMS.installStage()
      → Handler处理INIT_COPY消息
        → installPackageLI()

安装子流程：
1.复制APK到临时目录(/data/app/vmdl*)
2.解析APK(PackageParser)
3.签名验证(覆盖安装检查一致性)
4.冻结旧应用(防止安装过程中运行)
5.调用installd(创建数据目录、移动APK、设置权限)
6.dex编译(dex2oat)
7.注册到PMS(更新mPackages、注册组件、授予权限)
8.发送广播(ACTION_PACKAGE_ADDED)、解冻应用
```

#### 5.2 installPackageLI核心源码

```java
private void installPackageLI(InstallArgs args, PackageInstalledInfo res) {
    // 1.解析APK
    final PackageParser.Package pkg = pp.parsePackage(tmpPackageFile, parseFlags);
    // 2.签名验证
    PackageParser.collectCertificates(pkg, false);
    // 3.检查覆盖安装
    synchronized (mLock) {
        final PackageSetting ps = mSettings.mPackages.get(pkg.packageName);
        if (ps != null && !checkUpgradeKeySetLP(ps, pkg)) {
            res.setError(INSTALL_FAILED_UPDATE_INCOMPATIBLE, "Signature mismatch");
            return;
        }
    }
    // 4.冻结旧应用
    final PackageFreezer freezer = freezePackageForInstall(pkg.packageName, ...);
    try {
        if (replace) replacePackageLIF(pkg, parseFlags, scanFlags, args, res);
        else installNewPackageLIF(pkg, parseFlags, scanFlags, args, res);
    } finally {
        freezer.close();
    }
    // 5.发送广播
    if (res.returnCode == INSTALL_SUCCEEDED) {
        sendPackageBroadcast(Intent.ACTION_PACKAGE_ADDED, pkg.packageName, ...);
    }
}
```

### 06.签名验证机制源码分析
<a name="06"></a>

#### 6.1 签名方案演进V1到V3

```
V1签名（JAR签名，1.0+）
- 对每个文件单独计算摘要，记录在META-INF/
- 缺点：不保护ZIP元数据，验证需解压每个文件

V2签名（APK签名方案v2，7.0+）
- 对整个APK文件签名，存储在APK Signing Block
- 优点：验证快，保护整个文件完整性

V3签名（9.0+）
- 在V2基础上增加签名密钥轮转（Key Rotation）
- 通过proof-of-rotation链记录签名历史

V4签名（11+）
- 支持增量安装（ADB Incremental），基于Merkle Hash Tree
```

#### 6.2 V2签名的Block结构

```
APK文件结构（含V2签名）：
区域1：ZIP Entry Contents（所有文件条目）
区域2：APK Signing Block（签名块）
  ├── Block Size
  ├── ID-Value Pair: ID=0x7109871a（V2签名数据）
  ├── ID-Value Pair: ID=0xf05368c0（V3签名数据）
  ├── Block Size
  └── Magic: "APK Sig Block 42"
区域3：ZIP Central Directory
区域4：ZIP End of Central Directory
```

```java
public static SigningDetails verify(String apkPath, int minSignatureSchemeVersion) {
    try { return verifyV3Signature(apkPath); }
    catch (SignatureNotFoundException e) { }
    try { return verifyV2Signature(apkPath); }
    catch (SignatureNotFoundException e) { }

}
```

```java
private boolean checkUpgradeKeySetLP(PackageSetting oldPs, AndroidPackage newPkg) {
```

#### 7.2 权限授予流程源码

```java
private void grantPermissionsLPw(AndroidPackage pkg, boolean replace, String packageOfInterest) {
    for (String permName : pkg.getRequestedPermissions()) {
        final BasePermission bp = mSettings.mPermissions.get(permName);
        final int level = bp.protectionLevel & PermissionInfo.PROTECTION_MASK_BASE;
        switch (level) {
            case PROTECTION_NORMAL:    // 安装时自动授予
                permissionsState.grantInstallPermission(bp);
                break;
            case PROTECTION_DANGEROUS: // 不自动授予，需运行时请求
                break;
            case PROTECTION_SIGNATURE: // 检查签名匹配后授予
                if (canGrantSignaturePermission(pkg, bp))
                    permissionsState.grantInstallPermission(bp);
                break;
        }
    }
}
```

```java
// 权限检查链路
// Activity.checkSelfPermission() → ContextImpl → AMS → PMS
int checkPermission(String permName, String packageName, int userId) {
    final PackageSetting ps = mPackageManagerInt.getPackageSetting(packageName);
    if (ps == null) return PERMISSION_DENIED;
    if (ps.getPermissionsState().hasPermission(permName, userId))
        return PERMISSION_GRANTED;
    return PERMISSION_DENIED;
}

// 运行时权限授予链路
// requestPermissions → GrantPermissionsActivity → PermissionManagerService
void grantRuntimePermission(String packageName, String permName, int userId) {
    ps.getPermissionsState().grantRuntimePermission(bp, userId);
    mSettings.writeRuntimePermissionsForUserLPr(userId, false);
    mOnPermissionChangeListeners.onPermissionsChanged(uid);
}
```

### 08.Intent解析与组件匹配源码
<a name="08"></a>

#### 8.1 resolveIntent核心流程

```java
public ResolveInfo resolveIntent(Intent intent, String resolvedType, int flags, int userId) {
    // 1.查询所有匹配的Activity
    final List<ResolveInfo> query = queryIntentActivitiesInternal(intent, resolvedType, flags, userId);
    // 2.选择最佳
    return chooseBestActivity(intent, resolvedType, flags, query, userId);
}
```

显式Intent直接按ComponentName查找；隐式Intent通过ComponentResolver的IntentFilter匹配。

#### 8.2 IntentFilter匹配算法

匹配分四个维度，全部通过才算匹配成功：

```
1. Action匹配：Intent的action必须在Filter的action列表中
2. Category匹配：Intent的所有category都必须在Filter中存在
3. Data匹配：分层匹配 scheme → authority → path → mimeType
4. 优先级：SCHEME_SPECIFIC_PART > HOST > SCHEME > EMPTY
```

#### 8.3 chooseBestActivity选择逻辑

多个匹配结果时的选择策略：
1. 只有一个结果，直接返回
2. 按priority/preferredOrder/isDefault排序，有差异则取最高
3. 查询用户设置的默认应用（findPreferredActivityNotLocked）
4. 没有默认应用，返回ResolverActivity（选择器弹窗）

#### 8.4 隐式Intent解析的优先级

```
优先级规则：
显式Intent > 隐式Intent
系统应用Filter > 普通应用
高priority > 低priority
用户默认应用 > 无偏好 → 弹出选择器
特殊：App Links（autoVerify）优先匹配HTTP Intent
```


### 09.应用卸载与覆盖安装源码
<a name="09"></a>

#### 9.1 deletePackageLIF卸载流程

```
应用卸载完整流程：
卸载请求 → 多用户判断（单用户标记/全部用户真删除）
  → 冻结应用 → 杀死进程(AMS.forceStop)
    → 从PMS注销组件 → installd清理文件(APK、数据目录、dex缓存)
      → 更新packages.xml → 发送PACKAGE_REMOVED + PACKAGE_FULLY_REMOVED广播
```

#### 9.2 覆盖安装的判断与处理

覆盖安装的关键检查：签名一致性 + 版本号不降级（除非INSTALL_ALLOW_DOWNGRADE）。

replacePackageLIF的核心流程：冻结→杀进程→注销旧组件→安装新包→注册新组件→dex编译→发送PACKAGE_REPLACED广播。注意覆盖安装保留/data/data/下的用户数据。

#### 9.3 Split APK分包机制

```
Split APK结构：
/data/app/com.example.app-1/
├── base.apk               ← 基础APK（必须）
├── split_config.arm64_v8a.apk  ← ABI分包
├── split_config.xxhdpi.apk     ← 密度分包
├── split_config.zh.apk         ← 语言分包
└── split_feature_video.apk     ← 功能模块分包
```

PackageParser的parseClusterPackage方法先解析base APK，再依次解析每个split APK。

#### 9.4 系统应用特殊处理

系统应用不能真正删除。如果用户安装过更新：删除/data/app下的更新包，恢复/system下的原始版本。如果没有更新过：仅对当前用户标记disabled，不删除文件。


### 10.PMS数据持久化机制
<a name="10"></a>

#### 10.1 packages.xml文件结构

packages.xml存储在/data/system/目录，记录所有包的安装信息、权限定义、签名等。主要节点：`<permissions>`定义权限、`<package>`记录每个包的codePath/版本/签名/安装者、`<shared-user>`记录共享UID。

#### 10.2 writeLPr持久化源码

PMS通过Settings.writeLPr()将内存中的包信息写入packages.xml。采用先写备份文件再重命名的策略保证原子性。持久化时机包括：安装/卸载/更新完成后、权限变更后、系统启动扫描完成后。

#### 10.3 运行时权限状态保存

运行时权限保存在独立的`runtime-permissions.xml`文件中，按用户分别存储在`/data/system/users/{userId}/`目录下。权限授予/撤销后立即触发持久化。

#### 10.4 首次启动与数据恢复

PMS构造时先尝试读取packages.xml。如果文件损坏则读取packages-backup.xml。如果两者都不存在，说明是首次启动（mFirstBoot=true），需要完整扫描所有APK目录。OTA升级后会触发权限重新授予和dex重编译。


### 11.PMS性能优化与演进
<a name="11"></a>

#### 11.1 并行扫描优化机制

PMS使用ParallelPackageParser利用多线程并行解析APK，显著减少开机扫描时间。线程池大小通常为4个线程，每个线程独立解析一个APK，解析结果通过阻塞队列收集。

#### 11.2 增量安装与Streaming

Android 11引入增量安装（Incremental Installation），通过IncFS文件系统实现按需下载APK数据块。配合V4签名的Merkle Hash Tree，可以在APK尚未完全下载时就开始安装和运行。

#### 11.3 Android 12+的PMS重构

Android 12对PMS进行了大规模重构，将原来2万+行的巨型类拆分为多个子模块：PackageManagerService（主类简化）、InstallPackageHelper（安装逻辑）、DeletePackageHelper（卸载逻辑）、ScanPackageUtils（扫描逻辑）等。采用Computer快照模式，减少锁竞争。

#### 11.4 PackageManagerInternal设计

PackageManagerInternal是PMS提供给系统内部其他服务的接口，避免跨进程Binder调用。AMS等服务通过LocalServices.getService(PackageManagerInternal.class)直接获取Java引用调用，性能远优于Binder IPC。


### 12.总结与面试要点
<a name="12"></a>

#### 12.1 PMS核心流程总结

```
PMS关键流程速记：
启动 → 读packages.xml → 扫描系统/用户APK → 注册组件 → 写packages.xml → Ready

```

#### 12.2 高频面试题深度解析

**Q：PMS是何时启动的？启动过程做了什么？**
A：在SystemServer的startBootstrapServices阶段，通过PMS.main()创建。启动分五阶段：初始化Settings→扫描系统APK→扫描用户APK→更新权限并持久化→创建PackageInstaller并标记Ready。

**Q：APK安装的完整流程是怎样的？**
A：安装通过Session机制触发，核心步骤：复制到临时目录→PackageParser解析→签名验证→冻结旧应用→installd创建目录&移动APK→dex2oat编译→注册到PMS数据结构→授予权限→发送PACKAGE_ADDED广播→解冻。

**Q：V1/V2/V3签名有什么区别？**
A：V1对每个文件签名（不保护ZIP元数据，验证慢），V2对整个APK签名（快速验证，保护完整性），V3增加签名密钥轮转支持。PMS验证时优先V3→V2→V1。

**Q：运行时权限的检查流程？**
A：应用调用checkSelfPermission→ContextImpl→AMS→PMS.checkPermission→查询PackageSetting的PermissionsState。运行时权限按userId维度存储，支持多用户不同授权状态。
