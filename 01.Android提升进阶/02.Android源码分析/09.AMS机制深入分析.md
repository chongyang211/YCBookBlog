### 01.AMS概述与设计背景
<a name="01"></a>

#### 1.1 AMS在系统中的角色

ActivityManagerService（AMS）是Android系统中最核心的系统服务，没有之一。它运行在SystemServer进程中，统一管理所有应用的四大组件生命周期、进程创建与回收、内存管理等。

```
AMS在系统架构中的位置：
┌─────────────────────────────────────┐
│            应用层                     │
│  App1(Activity/Service/Receiver/CP) │
│  App2(Activity/Service/Receiver/CP) │
└────────────────┬────────────────────┘
                 │ Binder IPC (IActivityManager)
┌────────────────▼────────────────────┐
│           SystemServer进程           │
│  ┌──────────────────────────┐       │
│  │  ActivityManagerService  │       │
│  │  (组件管理+进程管理)      │       │
│  └─────────┬────────────────┘       │
│            │                         │
│  ┌─────────▼────────────────┐       │
│  │ ActivityTaskManagerService│       │
│  │ (Activity/Task专属管理)   │       │
│  └──────────────────────────┘       │
│                                      │
│  PMS  WMS  InputManagerService ...   │
└──────────────────────────────────────┘
```

AMS的核心定位：**Android系统的"总调度器"**。它决定了哪个Activity显示在前台、哪个进程应该被杀死、哪个Service可以在后台运行。

#### 1.2 AMS的核心职责

```
AMS核心职责全景：
├── 1.四大组件生命周期管理
│   ├── Activity：启动、暂停、恢复、停止、销毁
│   ├── Service：启动、绑定、解绑、停止
│   ├── BroadcastReceiver：注册、注销、分发
│   └── ContentProvider：启动、发布、获取
├── 2.进程管理
│   ├── 进程创建（通过Zygote fork）
│   ├── 进程优先级计算（OOM_adj）
│   ├── 进程回收（配合LMK）
│   └── 进程间通信协调
├── 3.Task与Activity栈管理
│   ├── Task的创建与切换
│   ├── Back Stack管理
│   ├── 最近任务列表
│   └── 多窗口/分屏支持
├── 4.ANR检测与处理
│   ├── Service超时检测
│   ├── Broadcast超时检测
│   ├── Input事件超时检测
│   └── ANR信息收集与输出
└── 5.权限与安全
    ├── 组件启动权限检查
    ├── 进程间调用权限验证
    └── 后台启动限制
```

#### 1.3 AMS与ATMS的关系演进

从Android 10开始，Google将Activity和Task相关的管理逻辑从AMS中拆分到ActivityTaskManagerService（ATMS）：

```
Android 9及之前：
  AMS一个类管理所有（代码量巨大）
  
Android 10：
  AMS：进程管理、Service、Broadcast、ContentProvider、OOM_adj
  ATMS：Activity生命周期、Task管理、最近任务、多窗口

两者的关系：
  ATMS持有AMS的引用，AMS也持有ATMS的引用
  ATMS运行在同一个SystemServer进程中
  对外仍通过IActivityManager接口暴露
```

```java
        mSystemReady = true;
        
        // 杀死在AMS Ready之前启动的非持久化进程
        removeProcessLocked(proc, false, true, "system update done");

    if (goingCallback != null) {
        goingCallback.run();

        // 阶段3：恢复最近任务
        mAtmInternal.resumeTopActivities(false);
        
        // 阶段4：发送开机广播
        broadcastIntentLocked(null, null, null,
                new Intent(Intent.ACTION_BOOT_COMPLETED),
                null, finisher, 0, null, null, ...);
    }
}
```

### 04.Activity管理与调度源码
<a name="04"></a>

#### 4.1 startActivity的AMS侧流程

从应用调用startActivity到AMS处理的完整链路：

```
startActivity调用链路：
Activity.startActivity(intent)
  → Instrumentation.execStartActivity()
    → ATMS.startActivity() [Binder IPC]
      → ActivityStarter.execute()
        → startActivityUnchecked()
          → 1.权限检查（checkStartAnyActivityPermission）
          → 2.解析Intent（PMS.resolveIntent获取ActivityInfo）
          → 3.确定目标Task（根据launchMode/flags/affinity）
          → 4.暂停当前Activity（schedulePauseActivity）
          → 5.判断是否需要创建新进程
          → 6.创建ActivityRecord并加入Task
          → 7.通知应用端创建Activity
```

```java
// ActivityStarter.java 核心方法
private int startActivityUnchecked(ActivityRecord r, ActivityRecord sourceRecord,
        IVoiceInteractionSession voiceSession, ...) {
    
    // 1.根据启动模式计算目标Task
    computeLaunchingTaskFlags();
    computeSourceStack();
    
    // 2.查找或创建目标Task
    ActivityRecord reusedActivity = getReusableIntentActivity();
    if (reusedActivity != null) {
        // 复用已有的Activity（singleTask/singleInstance等）
        if ((mLaunchFlags & FLAG_ACTIVITY_CLEAR_TOP) != 0) {
            // 清除目标Activity上面的所有Activity
            reusedActivity.getTaskRecord().performClearTaskLocked(r, mLaunchFlags);
        }
    }
    
    // 3.将ActivityRecord添加到Task
    mTargetStack.startActivityLocked(r, ...);
    
    // 4.触发Resume流程
    mRootWindowContainer.resumeFocusedStacksTopActivities(mTargetStack, r, ...);
    
    return START_SUCCESS;
}
```

#### 4.2 ActivityStack与Task管理

ActivityStack管理着Task的集合，以及Activity的生命周期切换：

```java
// RootWindowContainer.resumeFocusedStacksTopActivities()
//   → ActivityStack.resumeTopActivityUncheckedLocked()
//     → resumeTopActivityInnerLocked()

private boolean resumeTopActivityInnerLocked(ActivityRecord prev, ActivityOptions options) {
    final ActivityRecord next = topRunningActivity(true);
    
    // 1.暂停当前Activity
    if (mResumedActivity != null) {
        pausing = true;
        startPausingLocked(false, next, false);
        // 通过Binder通知应用端：schedulePauseActivity
        return false; // 等暂停完成后再resume
    }
    
    // 2.目标进程是否已启动
    if (next.app != null && next.app.thread != null) {
        // 进程已存在，直接resume
        next.app.thread.scheduleResumeActivity(next.appToken, ...);
    } else {
        // 进程不存在，需要先创建进程
        mService.startProcessAsync(next, ...);
        // 进程创建完成后通过attachApplication回调继续
    }
    return true;
}
```

#### 4.3 Activity状态机与生命周期驱动

```
Activity在AMS中的状态机：
INITIALIZING → STARTED → RESUMED → PAUSING → PAUSED → STOPPING → STOPPED → FINISHING → DESTROYED

状态切换由AMS驱动，通过Binder通知应用端执行对应生命周期：
AMS                                       应用端
scheduleResumeActivity()  ────────→  handleResumeActivity()
schedulePauseActivity()   ────────→  handlePauseActivity()
scheduleStopActivity()    ────────→  handleStopActivity()
scheduleDestroyActivity() ────────→  handleDestroyActivity()

Android 9+通过ClientLifecycleManager和TransactionExecutor管理：
ClientTransaction
├── addCallback(LaunchActivityItem)
├── addCallback(ResumeActivityItem)
└── setLifecycleStateRequest(PauseActivityItem)
```

#### 4.4 启动模式在AMS中的实现

```
四种启动模式在AMS中的Task处理逻辑：
standard（默认）：
  每次创建新的ActivityRecord，放入调用者的Task

singleTop：
  如果目标Activity已在栈顶 → 不创建新实例，调onNewIntent
  否则 → 同standard

singleTask：
  查找匹配affinity的Task
  找到 → 将该Task移到前台，清除目标Activity上方的Activity
  没找到 → 创建新Task

singleInstance：
  独占一个Task（该Task中只有这一个Activity）
  如果已存在 → 直接切到前台，调onNewIntent
```


### 05.Service管理源码分析
<a name="05"></a>

#### 5.1 startService完整流程

```
startService调用链路：
Context.startService(intent)
  → ContextImpl.startServiceCommon()
    → AMS.startService() [Binder IPC]
      → ActiveServices.startServiceLocked()
        → startServiceInnerLocked()
          → bringUpServiceLocked()
            → 1.查找或创建ServiceRecord
            → 2.检查Service所在进程是否已启动
            → 3.若进程未启动，先通过Zygote fork
            → 4.通过Binder通知应用端：scheduleCreateService
            → 5.通知应用端：scheduleServiceArgs(onStartCommand)
```

```java
// ActiveServices.java
ComponentName startServiceLocked(IApplicationThread caller, Intent service,
        String resolvedType, int callingPid, int callingUid, ...) {
    
    // 1.查找ServiceRecord
    ServiceLookupResult res = retrieveServiceLocked(service, null, ...);
    ServiceRecord r = res.record;
    
    // 2.后台启动限制检查（Android 8.0+）
    if (!r.startRequested && !fgRequired) {
        if (isBackgroundStartDisallowed(callingUid)) {
            throw new BackgroundServiceStartNotAllowedException(...);
        }
    }
    
    // 3.启动Service
    ComponentName cmp = startServiceInnerLocked(smap, service, r, ...);
    return cmp;
}

private String bringUpServiceLocked(ServiceRecord r, int intentFlags,
        boolean execInFg, boolean whileRestarting, boolean permissionsReviewRequired) {
    
    // 进程已启动
    if (r.app != null && r.app.thread != null) {
        sendServiceArgsLocked(r, execInFg, false);
        return null;
    }
    
    // 进程未启动，先创建进程
    ProcessRecord app = mAm.startProcessLocked(procName, r.appInfo, ...);
    
    // 进程创建完成后，在attachApplicationLocked中继续启动Service
    if (!mPendingServices.contains(r)) {
        mPendingServices.add(r);
    }
    return null;
}
```

#### 5.2 bindService与连接管理

```java
// bindService的AMS侧处理
int bindServiceLocked(IApplicationThread caller, IBinder token, Intent service,
        String resolvedType, IServiceConnection connection, ...) {
    
    // 1.查找ServiceRecord
    ServiceLookupResult res = retrieveServiceLocked(service, ...);
    ServiceRecord s = res.record;
    
    // 2.记录绑定关系
    AppBindRecord b = s.retrieveAppBindingLocked(service, callerApp);
    ConnectionRecord c = new ConnectionRecord(b, activity, connection, flags, ...);
    
    // 3.启动Service（如果未启动）
    bringUpServiceLocked(s, ...);
    
    // 4.请求Service返回IBinder
    // 通过scheduleBindService通知应用端调用onBind
    r.app.thread.scheduleBindService(r, i.intent.getIntent(), rebind, ...);
    
    return 1;
}
```

```
ServiceRecord
├── bindings: Map<IntentFilter, IntentBindRecord>

│       ├── apps: Map<ProcessRecord, AppBindRecord>
│       │   └── AppBindRecord

│       │       └── client: ProcessRecord（调用者进程）
│       └── binder: IBinder（Service返回的Binder对象）
└── connections: Map<IBinder, List<ConnectionRecord>>
```

#### 5.3 Service的后台限制演进

```
Service后台限制的演进：
Android 8.0：禁止后台应用startService（会抛异常）
  → 替代方案：startForegroundService + 5秒内调startForeground

Android 12：前台Service启动限制
  → 禁止后台应用启动前台Service（除特定豁免场景）
  → 替代方案：WorkManager、JobScheduler

Android 14：进一步限制
  → 前台Service必须指定foregroundServiceType
  → dataSync类型有6小时超时限制
```

```java
public void setServiceForegroundLocked(ComponentName className, IBinder token,
```

```java
                userId, receiver);
        mRegisteredReceivers.put(receiver.asBinder(), rl);
    }
    
    // 2.创建BroadcastFilter并注册
    BroadcastFilter bf = new BroadcastFilter(filter, rl, callerPackage,
            callerFeatureId, receiverPermission, callingUid, userId, ...);
    rl.add(bf);
    
    // 3.加入全局IntentResolver
    mReceiverResolver.addFilter(bf);
    
    return sticky; // 返回sticky广播
}
```

#### 6.2 sendBroadcast分发流程

```java
// AMS.broadcastIntentLocked()
final int broadcastIntentLocked(ProcessRecord callerApp, String callerPackage,
        String callerFeatureId, Intent intent, ...) {
    
    // 1.处理系统特殊广播（如BOOT_COMPLETED、PACKAGE_ADDED等）
    final String action = intent.getAction();
    if (Intent.ACTION_PACKAGE_REMOVED.equals(action)) {
        // 通知PMS等系统服务
    }
    
    // 2.查找静态注册的接收者（PMS中注册的）
    List<ResolveInfo> registeredReceivers = null;
    if ((intent.getFlags() & Intent.FLAG_RECEIVER_REGISTERED_ONLY) == 0) {
        registeredReceivers = collectReceiverComponents(intent, ...);
    }
    
    // 3.查找动态注册的接收者
    List<BroadcastFilter> receivers = null;
    receivers = mReceiverResolver.queryIntent(intent, ...);
    
    // 4.分发到并行队列（动态注册的无序广播）
    if (receivers != null && receivers.size() > 0) {
        BroadcastQueue queue = broadcastQueueForIntent(intent);
        BroadcastRecord r = new BroadcastRecord(queue, intent, ...);
        queue.enqueueParallelBroadcastLocked(r);
        queue.scheduleBroadcastsLocked();
    }
    
    // 5.分发到有序队列（有序广播 + 静态注册的接收者）
    if (registeredReceivers != null || isOrderedBroadcast) {
        BroadcastRecord r = new BroadcastRecord(queue, intent, ...);
        queue.enqueueOrderedBroadcastLocked(r);
        queue.scheduleBroadcastsLocked();
    }
    
    return ActivityManager.BROADCAST_SUCCESS;
}
```

#### 6.3 有序广播与并行广播

```
并行广播：
- 同时通知所有接收者，不等待处理结果
- 动态注册的非有序广播走此路径
- 通过BroadcastQueue.deliverToRegisteredReceiverLocked()直接分发

有序广播：
- 按优先级顺序，逐个通知接收者
- 上一个处理完（调用finish）后才通知下一个
- 可以中止（abortBroadcast）、修改结果（setResult）
- 静态注册的接收者默认走有序队列
```

#### 6.4 广播超时与ANR

```
广播ANR超时时间：
前台广播队列：10秒
后台广播队列：60秒

超时检测流程：
1. 分发广播时发送延迟消息 BROADCAST_TIMEOUT_MSG
2. 接收者处理完毕调finishReceiver()时取消定时器
3. 超时未完成 → 触发broadcastTimeoutLocked()
4. 收集ANR信息 → 弹出ANR对话框
```

#### 7.2 getContentResolver的调用链

```
ContentResolver查询流程：
context.getContentResolver().query(uri, ...)
  → ContentResolver.query()
    → acquireProvider(uri) → 获取IContentProvider代理
      → ActivityThread.acquireProvider()
        → 本地缓存中查找
```

#### 7.3 Provider的引用计数与生命周期

AMS通过引用计数管理Provider的生命周期。当最后一个客户端释放引用后，如果Provider所在进程没有其他组件运行，进程优先级会降低，最终可能被系统回收。

```
Provider引用管理：
acquire → refCount++（AMS记录哪些进程在使用）
release → refCount--
refCount == 0 → 更新进程OOM_adj → 可能被LMK回收
```


### 08.进程管理与OOM_adj
<a name="08"></a>

#### 8.1 进程优先级体系

```
Android进程优先级（OOM_adj值，越低优先级越高）：
┌──────────────────────────────────────────┐
│ NATIVE_ADJ (-1000)  → 系统Native进程      │
│ SYSTEM_ADJ (-900)   → SystemServer         │
│ PERSISTENT_PROC_ADJ (-800) → 持久化进程    │
├──────────────────────────────────────────┤
│ FOREGROUND_APP_ADJ (0)    → 前台应用       │
│ VISIBLE_APP_ADJ (100)     → 可见但非前台    │
│ PERCEPTIBLE_APP_ADJ (200) → 可感知进程     │
│ PERCEPTIBLE_LOW_ADJ (250) → 低可感知       │
├──────────────────────────────────────────┤
│ BACKUP_APP_ADJ (300)        → 备份进程     │
│ HEAVY_WEIGHT_APP_ADJ (400)  → 重量级进程   │
│ SERVICE_ADJ (500)           → Service进程  │
│ HOME_APP_ADJ (600)          → Home进程     │
│ PREVIOUS_APP_ADJ (700)      → 上一个应用   │
│ SERVICE_B_ADJ (800)         → B类Service   │
├──────────────────────────────────────────┤
│ CACHED_APP_MIN_ADJ (900)    → 缓存进程     │
│ CACHED_APP_MAX_ADJ (999)    → 最低优先级   │
└──────────────────────────────────────────┘
```

#### 8.2 OOM_adj的计算算法

```java
// OomAdjuster.java
private boolean computeOomAdjLocked(ProcessRecord app, int cachedAdj, ...) {
    // 按优先级从高到低判断
    
    // 1.前台Activity
    if (app.hasActivityInVisibleTask()) {
        adj = FOREGROUND_APP_ADJ;
        procState = PROCESS_STATE_TOP;
    }
    
    // 2.前台Service
    else if (app.hasForegroundServices()) {
        adj = PERCEPTIBLE_APP_ADJ;
        procState = PROCESS_STATE_FOREGROUND_SERVICE;
    }
    
    // 3.绑定了前台Activity的Service
    else if (isServiceBoundToForeground(app)) {
        adj = VISIBLE_APP_ADJ;
    }
    
    // 4.正在接收广播
    else if (app.hasRunningReceiver()) {
        adj = FOREGROUND_APP_ADJ;
    }
    
    // 5.正在运行的Service
    else if (hasStartedService(app)) {
        adj = SERVICE_ADJ;
    }
    
    // 6.缓存进程（无活跃组件）
    else {
        adj = cachedAdj; // 900-999
    }
    
    // 7.将adj值写入内核
    ProcessList.setOomAdj(app.pid, app.uid, adj);
}
```

#### 8.3 进程回收策略

AMS配合Linux内核的LMK（Low Memory Killer）进行进程回收：

```
进程回收的触发条件：
1. 内存不足时LMK按OOM_adj从高到低杀进程
2. AMS主动杀死超出缓存进程数量限制的进程
3. AMS杀死后台进程以释放内存
4. 用户手动从最近任务中清除

AMS缓存进程限制：
默认最多保留32个缓存进程
超出限制时杀死LRU列表末尾的进程
```

#### 8.4 LMK与进程保活

```
LMK工作机制：
内核内存不足 → 触发LMK
  → 遍历进程列表，按OOM_adj排序
    → 从adj最高（最不重要）的进程开始杀死
      → 直到释放足够内存

常见进程保活手段及AMS的对抗：
1. 双进程守护 → Android 5.0+通过forceStopPackage杀死同UID所有进程
2. 1像素Activity → Android 10+限制后台启动Activity
3. 前台Service → Android 12+限制后台启动前台Service
4. JobScheduler保活 → 系统会合并执行，不保证及时性
```

```java
// ActiveServices.java
private void bumpServiceExecutingLocked(ServiceRecord r, ...) {
    // 设置超时定时器
    if (r.executeNesting == 0) {
        if (r.app != null) {
            // 前台Service：20秒，后台Service：200秒
            long timeout = r.isForeground ? SERVICE_TIMEOUT : SERVICE_BACKGROUND_TIMEOUT;
            Message msg = mAm.mHandler.obtainMessage(
                    ActivityManagerService.SERVICE_TIMEOUT_MSG);
            msg.obj = r.app;
            mAm.mHandler.sendMessageDelayed(msg, timeout);
        }
    }
    r.executeNesting++;
}

// 超时处理
void serviceTimeout(ProcessRecord proc) {
    // 检查是否有Service执行超时
    for (ServiceRecord sr : proc.executingServices) {
        if (sr.executeFg) {
            long timeout = SERVICE_TIMEOUT;
            if (now > sr.executingStart + timeout) {
                // 触发ANR
                mAm.mAnrHelper.appNotResponding(proc, ...);
            }
        }
    }
}
```

```java
final void broadcastTimeoutLocked(boolean fromMsg) {
    // 超时检查
    long now = SystemClock.uptimeMillis();
    BroadcastRecord r = mDispatcher.getActiveBroadcastLocked();

}
```

### 10.AMS与WMS的协作
<a name="10"></a>

#### 10.1 协作架构设计

AMS管理组件生命周期，WMS管理窗口显示。两者在Activity的启动、切换、销毁等场景中需要紧密协作：

```
AMS与WMS的协作架构：
AMS（组件侧）              WMS（窗口侧）
ActivityRecord ←──────→ WindowState
TaskRecord    ←──────→ Task(Window)
ActivityStack ←──────→ DisplayContent

协作通过WindowContainerController接口完成
Android 10+通过WindowOrganizerController统一管理
```

#### 10.2 Activity启动时的窗口创建

```
Activity启动时AMS与WMS的协作时序：
1. AMS创建ActivityRecord
2. AMS通知WMS添加AppWindowToken
3. AMS通知应用端创建Activity（scheduleLaunchActivity）
4. 应用端创建Window，调用WindowManager.addView()
5. WMS创建WindowState，关联到AppWindowToken
6. WMS进行窗口布局计算
7. SurfaceFlinger合成显示
```

#### 10.3 转场动画的协调

Activity切换时的动画由AMS和WMS共同协调：AMS决定切换时机（旧Activity pause完成），WMS执行动画（窗口的进入/退出动画）。Android 12引入的SplashScreen也是WMS管理，但由AMS触发时机。


### 11.AMS的演进与ATMS重构
<a name="11"></a>

#### 11.1 Android 10的ATMS拆分

Android 10将Activity和Task管理从AMS中拆分到ActivityTaskManagerService（ATMS），目的是减小AMS的代码量、明确职责边界、为未来架构演进做准备。

#### 11.2 Android 12的TaskFragment

Android 12引入TaskFragment概念，支持Activity Embedding（活动嵌入）。一个Task中可以包含多个TaskFragment，每个TaskFragment可以独立管理自己的Activity栈。这是大屏设备适配的基础架构。

#### 11.3 未来架构趋势

```
AMS架构演进趋势：
1. 持续拆分：更多逻辑从AMS中独立出去
2. 窗口化统一：AMS和WMS的界限逐渐模糊（WindowOrganizer）
3. 多屏适配：更好的多屏幕、折叠屏支持
4. 后台限制增强：更严格的后台进程和组件限制
```

### 12.总结与面试要点
<a name="12"></a>

#### 12.1 AMS核心流程总结

```
AMS关键流程速记：
启动 → SystemServer创建 → 初始化BroadcastQueue/ActiveServices → systemReady → 启动Launcher
Activity → startActivity → 权限检查 → PMS解析Intent → 确定Task → pause当前 → 创建进程(可选) → resume目标
Service → startService → 查找ServiceRecord → 创建进程(可选) → scheduleCreateService → onStartCommand
Broadcast → sendBroadcast → 查找接收者 → 并行分发(动态) + 有序分发(静态/有序) → 超时ANR
进程管理 → OomAdjuster计算adj → 写入内核 → LMK按adj回收
```

#### 12.2 高频面试题深度解析

**Q：AMS是什么？核心职责有哪些？**
A：AMS是运行在SystemServer进程中的核心系统服务，管理四大组件生命周期、进程创建与回收、OOM_adj计算、ANR检测、Task管理等。Android 10后Activity/Task管理拆分到ATMS。

**Q：startActivity的完整流程？**
A：应用调startActivity→Instrumentation→ATMS(Binder IPC)→ActivityStarter执行：权限检查→PMS解析Intent→确定目标Task→暂停当前Activity→判断是否需创建进程→创建ActivityRecord加入Task→通知应用端创建Activity。

**Q：OOM_adj是什么？进程回收顺序？**
A：OOM_adj是进程优先级数值（-1000到999），值越低越重要。AMS通过OomAdjuster根据进程中运行的组件计算adj，写入内核。LMK内存不足时从adj最高的进程开始杀。前台Activity=0，前台Service=200，缓存进程=900-999。

**Q：ANR的检测机制？**
A：三种ANR场景：Service超时（前台20s/后台200s）、Broadcast超时（前台10s/后台60s）、Input超时（5s）。AMS在分发任务时启动定时器，任务完成时取消。超时则收集traces.txt（线程堆栈）和CPU/内存信息。
