# 第4章：C++ GDB与LLDB实战

> 当日志不够用、采样定位太糙、Sanitizer 也没抓到时，你手里最后的武器就是调试器。这一篇把 GDB 和 LLDB 的核心能力拆成"用得上的命令"和"背后机制"两张图，让调试器从"偶尔用用"变成你的日常工具。

---

## 00.文章元信息

- **适用读者**：对 `gdb` / `lldb` 有基本印象，但日常只用 `run` / `bt` / `print`，希望把调试器当作主力生产工具。
- **前置知识**：能在 Linux / macOS 下编译运行 C++；了解进程、信号、内存布局基本概念。
- **阅读方式**：第 01-03 章是"常用命令速查"，第 04-07 章是"高阶能力和机制"，可交替阅读、边用边查。

## 01.调试器能为你做什么：从"看现场"到"导演现场"

很多人把调试器当"看现场的工具"——断点停下，打印几个变量，然后 continue。这只是调试器能力的 10%。真正的调试器能让你：

1. **看**：完整的栈、寄存器、内存、线程、符号；
2. **改**：直接修改变量、寄存器、甚至代码；
3. **跳**：跳过一段代码、重新执行某段、修改 PC；
4. **注入**：调用任意函数、执行任意表达式；
5. **脚本化**：Python / Lua 自动化；
6. **远程**：通过 gdbserver / lldb-server 调试远程进程；
7. **事后**：用 coredump 在没有进程的情况下"时光倒流"。

掌握了 2-7，你会发现很多"只能加 log 反复部署调试"的问题能在本地几分钟解决。

## 02.GDB 核心命令速查

> 不追求罗列全命令，只列**日常 80% 场景覆盖**的命令。按"调试阶段"组织，便于查询。

### 2.1 启动和附加

```bash
gdb ./program                  # 启动带可执行文件
gdb ./program core             # 用 coredump 事后调试
gdb -p 12345                   # 附加到运行中的进程
gdb --args ./program arg1 arg2 # 传递参数
gdb -ex 'break main' -ex 'run' ./program  # 启动时自动执行命令
```

### 2.2 执行控制

| 命令 | 简写 | 作用 |
|------|------|------|
| `run` | `r` | 开始执行 |
| `continue` | `c` | 继续执行 |
| `next` | `n` | 单步（不进入函数） |
| `step` | `s` | 单步（进入函数） |
| `finish` | `fin` | 执行到当前函数返回 |
| `until 行号` | `u` | 执行到指定行 |
| `kill` | `k` | 杀掉被调试进程 |

### 2.3 断点

```
break main.cpp:42              # 按文件:行号
break MyClass::foo             # 按函数名（支持重载和命名空间）
break 42 if x > 100            # 条件断点
rbreak ^foo_                   # 正则断点（所有以 foo_ 开头的函数）
tbreak func                    # 一次性断点（触发后自动删除）
catch throw                    # 在所有 throw 处停下
catch catch                    # 在所有 catch 处停下
catch signal SIGSEGV           # 捕获特定信号
info breakpoints / info b      # 查看所有断点
delete 3                       # 删除断点 3
disable 3 / enable 3           # 禁用/启用断点
commands 3                     # 给断点 3 添加自动命令（命中时执行）
  > silent
  > print x
  > continue
  > end
```

### 2.4 查看现场

```
backtrace / bt                 # 栈回溯
bt full                        # 栈回溯 + 每帧的局部变量
frame 3 / f 3                  # 切换到第 3 帧
up / down                      # 上一帧 / 下一帧
info locals                    # 当前帧的局部变量
info args                      # 当前帧的参数
info registers / info r        # 寄存器
info threads                   # 所有线程
thread 2                       # 切换到线程 2
info sharedlibrary             # 加载的共享库
```

### 2.5 打印与表达式

```
print x                        # 打印变量 x
print *p                       # 解引用
print arr[0]@10                # 打印数组连续 10 个元素
print /x value                 # 按十六进制打印（/d 十进制 /t 二进制 /c 字符）
print sizeof(MyClass)          # 打印表达式
print func(42)                 # 调用函数（慎用，有副作用）
set print pretty on            # 让结构体按缩进格式打印
set print elements 1000        # 打印数组时最多显示 1000 项
ptype obj                      # 查看对象类型
whatis obj                     # 简要类型信息
```

### 2.6 内存与反汇编

```
x /16x 0x7ffe1234              # 按 16 字节十六进制打印内存
x /16i $pc                     # 反汇编当前 PC 附近 16 条指令
disassemble main               # 反汇编 main
disassemble /m main            # 反汇编 + 源码交错
info frame                     # 当前栈帧的寄存器布局、保存位置
```

### 2.7 watchpoint（监视点）

```
watch x                        # x 被修改时停下
rwatch x                       # x 被读取时停下
awatch x                       # x 被读或写时停下
```

硬件 watchpoint 只有 4 个（DR0-DR3），超过会退化为软件——极慢。用 `info watch` 能看到当前类型。

### 2.8 其他常用

```
set pagination off             # 关闭分页（便于脚本）
set logging on                 # 把输出记录到 gdb.txt
set print thread-events off    # 不打印线程启停消息（减少噪音）
layout src                     # TUI 模式，分屏显示源码
layout asm                     # TUI 显示汇编
Ctrl-X A                       # 切换 TUI 模式
```

## 03.LLDB 命令对照表

macOS 默认是 LLDB；很多公司的 Linux 工具链也正在切到 LLDB（因为它是 LLVM 项目的一部分、API 更现代）。LLDB 和 GDB 在"目标"上相同，但命令风格不同。

### 3.1 LLDB vs GDB 对照

| 操作 | GDB | LLDB |
|------|-----|------|
| 启动 | `gdb ./a.out` | `lldb ./a.out` |
| 运行 | `run`/`r` | `run`/`r` 或 `process launch` |
| 附加 | `gdb -p N` | `lldb -p N` 或 `process attach --pid N` |
| 断点（文件行号） | `b file.cpp:42` | `b file.cpp:42` 或 `breakpoint set -f file.cpp -l 42` |
| 断点（函数名） | `b main` | `b main` 或 `breakpoint set -n main` |
| 条件断点 | `b 42 if x>10` | `breakpoint set -l 42 -c 'x>10'` |
| 继续 | `c` | `c` 或 `continue` |
| 单步不入 | `n` | `n` 或 `thread step-over` |
| 单步进入 | `s` | `s` 或 `thread step-in` |
| 返回 | `finish` | `finish` 或 `thread step-out` |
| 栈 | `bt` | `bt` 或 `thread backtrace` |
| 切帧 | `f 3` | `f 3` 或 `frame select 3` |
| 打印变量 | `p x` | `p x` 或 `expression x` |
| 查看变量 | `info locals` | `frame variable` / `fr v` |
| 线程列表 | `info threads` | `thread list` |
| 内存 dump | `x /16x addr` | `memory read --size 1 --format x --count 16 addr` 或 `me r -s 1 -f x -c 16 addr` |
| 寄存器 | `info r` | `register read` / `re r` |
| 反汇编 | `disas main` | `disassemble -n main` 或 `di -n main` |
| 设置 watchpoint | `watch x` | `watchpoint set variable x` |

### 3.2 LLDB 独有/更好用的特性

- **`expression` (`p`) 更强**：能直接执行任意 C++ 表达式，包括 Lambda、构造对象。
  ```
  (lldb) p new std::string("hello")
  (lldb) p ((MyClass*)0x7fff1234)->get_name()
  ```
- **别名系统**：`command alias mybt thread backtrace` 自定义命令。
- **Python 脚本**：`script print(lldb.frame.FindVariable('x').GetValue())`，完整 Python API。
- **更精确的 frame 变量**：`frame variable -L`（按内存布局显示）、`-R`（显示原始指针）。

## 04.高阶能力一：脚本化调试

调试器不是只能手动点的工具——它是"可编程的观察者"。

### 4.1 GDB 的自动化断点

```
(gdb) break process_request
(gdb) commands
> silent
> printf "request: id=%d, size=%d\n", req->id, req->size
> if req->size > 1000000
>   printf "LARGE REQUEST at %s:%d\n", __FILE__, __LINE__
> end
> continue
> end
```

程序运行时 **不会停**，但每次命中这个点都会打印一行日志。这就是"**日志断点（dprintf）**"——没有修改源代码就在运行时加了日志。

GDB 7.7 起提供了更简洁的语法：

```
dprintf process_request, "req id=%d size=%d\n", req->id, req->size
```

### 4.2 GDB Python 扩展

```python
# save as mycommand.py
import gdb

class PrintAllObjects(gdb.Command):
    def __init__(self):
        super().__init__("print-all", gdb.COMMAND_USER)
    def invoke(self, arg, from_tty):
        vec = gdb.parse_and_eval(arg)
        size = int(vec['_M_impl']['_M_finish'] - vec['_M_impl']['_M_start'])
        for i in range(size):
            item = gdb.parse_and_eval(f"{arg}._M_impl._M_start[{i}]")
            print(f"[{i}] = {item}")

PrintAllObjects()
```

在 GDB 里 `source mycommand.py`，然后就可以 `print-all myvec`。

**实用场景**：
- 自定义 pretty-printer（让 `std::unordered_map` 直接打印所有键值对）；
- 自动巡检（每次命中某断点，自动检查一组 invariant）；
- 提取调试信息（从 coredump 批量提取所有线程的栈到文件）。

### 4.3 LLDB 的 Python 接口

LLDB 的 Python API 更"对象化"：

```python
# lldb script mode
(lldb) script
>>> target = lldb.target
>>> process = target.process
>>> thread = process.selected_thread
>>> for frame in thread:
...     print(f"{frame.idx}: {frame.GetFunctionName()} at {frame.line_entry.file}:{frame.line_entry.line}")
```

这让你能写"分析脚本"——比如"找出所有线程里调用了某函数的线程"。

### 4.4 pretty-printer：让容器可读

原生 GDB 打印 `std::map` 会得出一团乱麻的红黑树内部结构。libstdc++ 自带的 pretty-printer 把它变成 `{key1: value1, key2: value2}`。开启：

```bash
# .gdbinit
python
import sys
sys.path.insert(0, '/usr/share/gcc/python')
from libstdcxx.v6.printers import register_libstdcxx_printers
register_libstdcxx_printers(None)
end
```

libc++ (Clang) 自带类似机制。自己项目的容器也可以写 pretty-printer，极大提高调试效率。

## 05.高阶能力二：远程调试与核心调试

### 5.1 gdbserver：调试不在本机的进程

场景：调试嵌入式设备上的程序、调试容器里的进程、调试测试环境里的服务。

```bash
# 目标机
gdbserver :12345 ./program arg1

# 开发机
gdb ./program
(gdb) target remote TARGET_IP:12345
```

gdbserver 只是个轻量代理（几百 KB），负责转发 ptrace 请求。所有符号解析、表达式求值都在开发机本地做——所以**开发机必须有对应的可执行文件和符号**。

### 5.2 lldb-server

LLDB 的对应工具：

```bash
# 目标机
lldb-server platform --listen "*:12345" --server

# 开发机
lldb
(lldb) platform select remote-linux
(lldb) platform connect connect://TARGET_IP:12345
(lldb) target create ./program
(lldb) run
```

### 5.3 核心调试（Post-mortem）

进程已经死了，只有 coredump 时：

```bash
# 生成 coredump
ulimit -c unlimited    # 开启
cat /proc/sys/kernel/core_pattern  # 查看 core 路径

# 分析
gdb ./program core
(gdb) bt              # 崩溃时的栈
(gdb) info threads    # 所有线程
(gdb) thread apply all bt  # 所有线程的栈
```

**关键技巧**：

- **coredump 必须用**和**生成时同版本的二进制**来加载——否则地址和符号对不上；
- **保留 debug info**：即使 strip 了二进制，独立保存 `.debug` 文件，GDB 能自动找到（`set debug-file-directory`）；
- **多节点环境**：生产环境的 coredump 通常需要拷回本地，加上符号服务器（`debuginfod`、自建）能大规模简化流程。

### 5.4 reverse-debugging（时光倒流）

GDB 支持"**反向执行**"——但需要被调试的程序被记录过：

```
(gdb) target record-full        # 开启记录
(gdb) continue                  # 运行到断点
(gdb) reverse-continue          # 反向运行到上一个断点
(gdb) reverse-step              # 反向单步
```

代价：记录过程会让程序慢 50-100 倍。适用于"本地复现的复杂 bug、希望多次回放"的场景。`rr` 工具（Mozilla 出品）是更好的替代——录制时几乎零开销，回放时支持完整的反向执行。

## 06.高阶能力三：读懂优化后的代码

实际项目大多以 `-O2` 或 `-O3` 编译。优化会做几件让调试器"犯难"的事：

### 6.1 常见"优化后迷雾"

| 现象 | 原因 | 对策 |
|------|------|------|
| `<optimized out>` | 变量被放寄存器后生命周期结束 | `-Og`（针对调试的优化级别）或 `volatile` |
| 断点设不进去 | 函数被 inline | `info function func_name`、在调用点设断点 |
| 单步跳来跳去 | 代码被重排 | `layout asm` 看汇编、用 `stepi` |
| 打印的值"不对" | 变量尚未被写入、或已被覆盖 | 看汇编确认实际时刻 |
| 断点位置漂移 | 行号被合并 | 在相邻行多设几个断点 |

### 6.2 `-Og`：专为调试的优化级别

`-O0` 太慢、`-O2` 太"奇怪"。GCC/Clang 的 `-Og` 是折衷：做不破坏调试体验的优化（内联、常量折叠）、不做破坏性的优化（激进重排、SSA 简化）。生产项目可以：

- 开发构建用 `-Og -g3`；
- CI 测试用 `-O2 -g`（接近生产）；
- 发布构建用 `-O3 -g`（带独立 debug info）。

### 6.3 读 `<optimized out>` 的变量

```
(gdb) info locals
i = <optimized out>
```

三种对策：

1. **改编译级别**：`-Og` 通常能保留大部分局部变量。
2. **看寄存器**：优化后变量常在寄存器里。看汇编确定 i 在哪个寄存器，`info r rax` 取值。
3. **强制变量保留**：
   ```cpp
   volatile int debug_i = i;   // volatile 阻止优化
   asm volatile("" : : "r"(i));  // 告诉编译器"这个值被汇编用了"
   ```

### 6.4 关于 `__attribute__((noinline))`

某些关键函数在调试时希望永远不被 inline：

```cpp
__attribute__((noinline)) void important_func() { /* ... */ }
```

可以稳定被 `break` 命中、栈回溯里稳定出现。不少项目对关键路径函数默认加这个。

## 07.调试器的底层原理小结

### 7.1 两大基石

- **ptrace**（详见《调试技巧和原理分析》09 章）：让 tracer 控制和观察 tracee 的内核接口。
- **DWARF 调试信息**（详见《崩溃流程和捕获原理》06 章）：把二进制地址映射回源码位置、变量名、类型。

调试器就是这两者的组合：ptrace 是"手"，DWARF 是"眼"。

### 7.2 调试信息在哪里

```bash
readelf -S binary | grep debug    # 看有哪些 DWARF section
objdump -h binary | grep debug    # 同上
file binary                       # 看是否 stripped
```

常见 DWARF section：`.debug_info`（主信息）、`.debug_line`（行号表）、`.debug_abbrev`（缩写表）、`.debug_str`（字符串池）。

**split debug info** 是现代做法：编译时 `-gsplit-dwarf`，调试信息进 `.dwo` 文件，二进制里只留索引。减小二进制体积、加快链接。

### 7.3 调试器看不到什么

即使 DWARF 完整，某些东西调试器看不到：

- **宏展开后的代码位置**：DWARF 能记录到 `.debug_macro`，但实际上大部分编译器不生成；
- **模板实例化的实际体**：DWARF 里的类型名是实例化后的（如 `vector<int>`），但源码位置会指向模板定义文件；
- **inline 后的执行顺序**：能看到调用栈有 inline，但时间先后是模糊的。

理解这些"看不到的"能帮你避免"调试器明明这么说，怎么不对"的困惑。

## 08.思考题

1. 你的程序崩溃，但 coredump 里 `bt` 显示栈全是 `??`。请列出至少 4 个可能的原因和对应排查方法。
2. 如何用 GDB 的 Python API 写一个脚本，找出所有线程中**持有某个特定 mutex** 的线程？
3. 一个经常崩溃的服务上了生产，但你不能本地复现。现在拿到一个 coredump，如何最大限度地从中提取有用信息？（至少 5 个角度）
4. `print x` 结果是 `<optimized out>`，但 `print &x` 给出了地址。这说明什么？如何读出值？
5. 用 `rr` 录制一个程序的执行，回放时能做哪些"正常 GDB 做不到"的事？
6. 为什么"condition 断点"比"用 printf 在同一位置条件输出"慢得多？
