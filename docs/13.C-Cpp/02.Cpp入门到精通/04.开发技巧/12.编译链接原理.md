## 01.先说个问题

### 1.1 背景介绍一下

项目结构如下：

```
project/
├── Account.h
├── Account.cpp
├── BankUserManager.cpp
```

当写完了代码之后，就开始进行编译，如下所示：

```bash
CHONGYYANG-MB1:bank yangchong$ g++ BankUserManager.cpp
```

### 1.2 遇到问题报错

然后遇到报错，报错如下：

```text
Undefined symbols for architecture arm64:
  "Account::deposit(double)", referenced from:
      Bank::deposit(std::__1::basic_string<char, std::__1::char_traits<char>, std::__1::allocator<char>> const&, double) in BankUserManager-397329.o
  "Account::transfer(Account&, double)", referenced from:
      Bank::transfer(std::__1::basic_string<char, std::__1::char_traits<char>, std::__1::allocator<char>> const&, std::__1::basic_string<char, std::__1::char_traits<char>, std::__1::allocator<char>> const&, double) in BankUserManager-397329.o
  "Account::getName() const", referenced from:
      FileManager::saveToFile(Bank const&, std::__1::basic_string<char, std::__1::char_traits<char>, std::__1::allocator<char>> const&) in BankUserManager-397329.o
ld: symbol(s) not found for architecture arm64
clang++: error: linker command failed with exit code 1 (use -v to see invocation)
```

### 1.3 问题原因

你遇到的错误是由于链接器（Linker）找不到 `Account` 类的实现导致的。

具体来说，编译器在编译 `BankUserManager.cpp` 时，发现它依赖于 `Account` 类的成员函数（如 `deposit`、`withdraw`、`transfer` 等），但在链接阶段，这些函数的实现没有被找到，因此报错。

### 1.4 问题原因分析

1. **`Account` 类的实现未编译**，你可能将 `Account` 类的声明和实现分开了（例如，`Account.h` 和 `Account.cpp`），但在编译时没有将 `Account.cpp` 一起编译。

2. **未正确链接目标文件**，如果你已经编译了 `Account.cpp`，但没有将生成的目标文件（如 `Account.o`）与 `BankUserManager.cpp` 的目标文件链接在一起，也会导致这个问题。

## 02.解决方法尝试

### 2.1 确保文件被编译

**确保 `Account` 类的实现文件被编译**，项目结构如下：

```
project/
├── Account.h
├── Account.cpp
├── BankUserManager.cpp
```

在终端中，确保同时编译 `Account.cpp` 和 `BankUserManager.cpp`：

```bash
g++ Account.cpp BankUserManager.cpp -o BankUserManager
```

### 2.2 确保文件路径正确

如果 `Account.h` 和 `Account.cpp` 不在同一目录下，需要在编译时指定正确的路径。例如：

```bash
g++ src/Account.cpp src/BankUserManager.cpp -o BankUserManager
```

### 2.3 Makefile管理编译

如果项目较大，可以使用 `Makefile` 来管理编译过程。例如：

```makefile
CXX = g++
CXXFLAGS = -std=c++11
TARGET = BankUserManager
SRCS = Account.cpp BankUserManager.cpp
OBJS = $(SRCS:.cpp=.o)

all: $(TARGET)

$(TARGET): $(OBJS)
    $(CXX) $(CXXFLAGS) -o $(TARGET) $(OBJS)

%.o: %.cpp
    $(CXX) $(CXXFLAGS) -c $< -o $@

clean:
    rm -f $(OBJS) $(TARGET)
```

然后在终端中运行：

```bash
make
```

### 2.4 检查编译器架构

如果你在 ARM64 架构（如 Apple Silicon）上编译，确保编译器支持该架构。你可以使用以下命令检查编译器版本和架构：

```bash
g++ -v
```

如果编译器不支持 ARM64，可以尝试安装支持 ARM64 的编译器，或者使用交叉编译工具。

## 03.编译流程原理

```
project/
├── Account.h
├── Account.cpp
├── BankUserManager.cpp
```

- `Account.h` 包含 `Account` 类的声明。
- `Account.cpp` 包含 `Account` 类的实现。
- `BankUserManager.cpp` 包含 `main` 函数，使用 `Account` 类。

### 3.1 编译指令解读

```bash
g++ Account.cpp BankUserManager.cpp -o BankUserManager
```

**1. `g++`**

`g++` 是 GNU C++ 编译器，用于编译和链接 C++ 程序。它是 GCC（GNU Compiler Collection）的一部分。

**2. `Account.cpp` 和 `BankUserManager.cpp`**

这两个是 C++ 源代码文件：

- `Account.cpp`：包含 `Account` 类的实现。
- `BankUserManager.cpp`：包含 `main` 函数或其他逻辑，依赖于 `Account` 类。

编译器会分别编译这两个文件，生成目标文件（`.o` 文件），然后将它们链接在一起。

**3. `-o BankUserManager`**

`-o` 是编译器的选项，用于指定输出文件的名称。`BankUserManager` 是生成的可执行文件的名称。

如果没有 `-o` 选项，编译器会默认生成一个名为 `a.out` 的可执行文件（在 Linux/macOS 上）。

### 3.2 命令执行过程

当运行 `g++ Account.cpp BankUserManager.cpp -o BankUserManager` 时，编译器会执行以下步骤：

1. **编译阶段**
- 编译器将 `Account.cpp` 编译成目标文件（`Account.o`）。
- 编译器将 `BankUserManager.cpp` 编译成目标文件（`BankUserManager.o`）。

2. **链接阶段**
- 编译器将 `Account.o` 和 `BankUserManager.o` 链接在一起，生成最终的可执行文件 `BankUserManager`。

### 3.3 编译文件思考

`BankUserManager.cpp` 依赖于 `Account` 类，而 `Account` 类的实现在 `Account.cpp` 中。

如果只编译 `BankUserManager.cpp`，编译器会报错，因为它找不到 `Account` 类的实现。

通过同时编译 `Account.cpp` 和 `BankUserManager.cpp`，编译器可以找到所有必要的代码，并正确生成可执行文件。

### 3.4 运行命令

在终端中进入项目目录，然后运行：

```bash
g++ Account.cpp BankUserManager.cpp -o BankUserManager
```

如果编译成功，会生成一个名为 `BankUserManager` 的可执行文件。你可以运行它：

```bash
./BankUserManager
```

`g++ Account.cpp BankUserManager.cpp -o BankUserManager` 的作用是：

1. 编译 `Account.cpp` 和 `BankUserManager.cpp`。
2. 将生成的目标文件链接在一起。
3. 生成一个名为 `BankUserManager` 的可执行文件。

通过这条命令，你可以将多个 C++ 源文件编译成一个完整的可执行程序。

## 04.项目编译原理

### 4.1 编译详细流程

```
Account.cpp  --> 预处理 --> 编译 --> 汇编 --> Account.o
BankUserManager.cpp --> 预处理 --> 编译 --> 汇编 --> BankUserManager.o
Account.o + BankUserManager.o --> 链接 --> BankUserManager（可执行文件）
```

### 4.2 预处理（Preprocessing）

**作用**：处理源代码中的预处理指令（如 `#include`、`#define` 等），生成一个“纯净”的 C++ 文件。

**具体步骤**：

- 将 `#include` 指令替换为对应头文件的内容。例如，`#include "Account.h"` 会被替换为 `Account.h` 文件的内容。
- 展开宏定义（`#define`）。
- 处理条件编译指令（如 `#ifdef`、`#ifndef` 等）。

**输出**：生成一个临时文件（通常以 `.i` 或 `.ii` 为扩展名），其中包含所有预处理后的代码。

### 4.3 编译（Compilation）

**作用**：将预处理后的 C++ 代码转换为汇编代码。

**具体步骤**：
- 编译器（`g++`）对预处理后的代码进行语法和语义分析。
- 生成与目标平台（如 ARM64、x86_64）相关的汇编代码。

**输出**：生成汇编文件（通常以 `.s` 为扩展名）。

### 4.4 汇编（Assembly）

**作用**：将汇编代码转换为机器码（目标文件）。

**具体步骤**：
- 汇编器将汇编代码转换为机器指令。
- 生成目标文件（`.o` 文件），其中包含机器码和符号表（用于链接阶段）。

**输出**：生成目标文件（`Account.o` 和 `BankUserManager.o`）。


### 4.5 链接（Linking）

**作用**：将多个目标文件和库文件合并，生成最终的可执行文件。

**具体步骤**：
- 链接器（`ld`）将 `Account.o` 和 `BankUserManager.o` 合并。
- 解析符号引用（如 `BankUserManager.o` 中对 `Account` 类方法的调用）。
- 将标准库（如 `libstdc++`）和其他依赖库链接到可执行文件中。

**输出**：生成可执行文件（`BankUserManager`）。


### 4.6 可执行文件

**作用**：包含机器码和运行时信息，可以直接在操作系统上运行。

**具体内容**：

- 机器码：CPU 可以直接执行的指令。
- 符号表：用于调试和动态链接。
- 段信息：如代码段（`.text`）、数据段（`.data`）、未初始化数据段（`.bss`）等。


### 4.7 关键点说明

1. **预处理**：处理 `#include` 和宏定义，生成纯净的 C++ 代码。
2. **编译**：将 C++ 代码转换为汇编代码。
3. **汇编**：将汇编代码转换为机器码（目标文件）。
4. **链接**：将多个目标文件和库文件合并，生成可执行文件。

### 4.8 为何需要链接

- `BankUserManager.cpp` 依赖于 `Account` 类的实现，而 `Account` 类的实现在 `Account.cpp` 中。
- 在编译阶段，`BankUserManager.cpp` 只知道 `Account` 类的声明（通过 `Account.h`），但不知道其实现。
- 在链接阶段，链接器将 `Account.o` 和 `BankUserManager.o` 合并，解析符号引用，生成完整的可执行文件。


## 05.深入编译器内部

前面讲了编译的大致流程（预处理→编译→汇编→链接），但"编译"这一步其实内部非常复杂。这一节用银行项目的代码深入拆解编译器内部到底做了什么。

### 5.1 编译器做了什么

编译器的核心任务是：**把人写的 C++ 代码翻译成机器能执行的指令**。

这个翻译过程不是一步到位的，而是分成多个阶段，像流水线一样依次处理：

```
源代码(.cpp) → 词法分析 → 语法分析 → 语义分析 → 中间代码生成 → 代码优化 → 目标代码生成(.s)
```

每一个阶段都有明确的输入和输出，下面逐个来看。

### 5.2 词法分析阶段

**做什么**：把源代码的字符流拆分成一个个有意义的"词"（Token）。

就像你读一篇英文文章，第一步是识别出每个单词，而不是一个字母一个字母地看。

以 `Account.cpp` 中的一行代码为例：

```cpp
void Account::deposit(double amount) {
```

词法分析器会把它拆成以下 Token：

| Token | 类型 |
|-------|------|
| `void` | 关键字 |
| `Account` | 标识符 |
| `::` | 作用域运算符 |
| `deposit` | 标识符 |
| `(` | 左括号 |
| `double` | 关键字 |
| `amount` | 标识符 |
| `)` | 右括号 |
| `{` | 左花括号 |

**关键点**：词法分析只关心"这是什么词"，不关心这些词组合起来是什么意思。如果你写了 `123abc`，词法分析阶段就能发现这不是一个合法的 Token，会报词法错误。

### 5.3 语法分析阶段

**做什么**：把 Token 序列组织成一棵**抽象语法树**（AST，Abstract Syntax Tree），检查代码的语法结构是否正确。

就像读懂一个句子不仅要认识单词，还要理解主谓宾的结构。

对于 `void Account::deposit(double amount) { balance += amount; }`，语法分析器会构建类似这样的树：

```
FunctionDefinition
├── 返回类型: void
├── 类名: Account
├── 函数名: deposit
├── 参数列表
│   └── 参数: double amount
└── 函数体
    └── 复合赋值表达式 (+=)
        ├── 左: balance
        └── 右: amount
```

**关键点**：语法分析检查的是代码结构是否合法。比如你写了 `void deposit(double,) {}`，多了一个逗号，语法分析阶段就会报错 `expected parameter declarator`。但语法分析**不检查**变量是否已声明、类型是否匹配等问题。

### 5.4 语义分析阶段

**做什么**：在语法树的基础上检查代码的**含义是否正确**。

语法正确不等于语义正确。比如 `"hello" + 3.14` 语法上没问题，但语义上不合法。

以银行项目为例，语义分析器会检查：

1. **类型检查**：`deposit(double amount)` 的参数是 `double`，如果你调用 `account.deposit("abc")`，语义分析会报类型不匹配。
2. **作用域检查**：`balance` 是 `Account` 类的成员变量，在 `deposit` 方法里可以访问；但如果你在 `main` 函数里直接写 `balance += 100`，语义分析会报"未声明的标识符"。
3. **访问权限检查**：如果 `balance` 是 `private` 成员，外部直接访问会报错。
4. **函数签名匹配**：调用 `transfer(Account& to, double amount)` 时，参数数量和类型必须匹配。

**关键点**：语义分析是编译器帮你"检查逻辑"的阶段。很多编译报错（比如 `use of undeclared identifier`、`no matching function for call to`）都出自这个阶段。

### 5.5 中间代码生成

**做什么**：把语法树转换成一种**与平台无关**的中间表示（IR，Intermediate Representation）。

为什么不直接生成机器码？因为中间代码有两个好处：

1. **方便优化**：在 IR 上做优化比在汇编上容易得多。
2. **跨平台**：同一份 IR 可以生成 ARM64（Apple Silicon）或 x86_64（Intel）的机器码。

以 `balance += amount;` 为例，生成的 IR（以 LLVM IR 为例）大致如下：

```llvm
%1 = load double, double* %balance      ; 读取 balance 的值
%2 = load double, double* %amount       ; 读取 amount 的值
%3 = fadd double %1, %2                 ; 浮点加法
store double %3, double* %balance       ; 结果存回 balance
```

**关键点**：你用 `clang++ -S -emit-llvm Account.cpp` 可以查看实际生成的 LLVM IR，这是理解编译器行为的好方法。

### 5.6 代码优化阶段

**做什么**：对中间代码进行优化，让生成的程序更快、更小。

编译器优化是一个非常深的领域，这里举几个常见例子：

**1. 常量折叠**：编译期直接算出结果

```cpp
// 优化前
double fee = 100 * 0.05;
// 优化后（编译器直接算出 5.0）
double fee = 5.0;
```

**2. 内联展开**：把小函数直接"复制粘贴"到调用处，省去函数调用开销

```cpp
// 如果 getBalance() 只是 return balance;
// 编译器可能把 account.getBalance() 直接替换为访问 account.balance
```

**3. 死代码消除**：删除永远不会执行的代码

```cpp
if (false) {
    cout << "这行永远不会执行";  // 编译器会删掉这段
}
```

**关键点**：`g++` 通过 `-O` 参数控制优化等级：
- `-O0`：不优化（默认，适合调试）
- `-O1`：基础优化
- `-O2`：推荐的优化等级（速度和大小的平衡）
- `-O3`：激进优化（可能增大代码体积）
- `-Os`：优化代码大小

### 5.7 目标代码生成

**做什么**：把优化后的中间代码转换成**目标平台的汇编代码**。

对于 Apple Silicon Mac（ARM64），`balance += amount;` 最终会变成类似这样的 ARM64 汇编：

```asm
ldr     d0, [x0, #8]     ; 从对象偏移8字节处加载 balance 到寄存器 d0
ldr     d1, [sp, #16]    ; 从栈上加载 amount 到寄存器 d1
fadd    d0, d0, d1        ; d0 = d0 + d1（浮点加法）
str     d0, [x0, #8]     ; 将结果存回 balance
```

你可以用 `g++ -S Account.cpp` 生成汇编文件 `Account.s`，查看完整的汇编代码。

### 5.8 用案例串联全流程

以银行项目中 `account.deposit(500.0)` 这一行调用为例，串联编译器内部全流程：

```
源代码: account.deposit(500.0);

→ 词法分析: [account] [.] [deposit] [(] [500.0] [)] [;]
           标识符  点运算符 标识符  左括号 浮点常量 右括号 分号

→ 语法分析: 构建AST
           MemberFunctionCall
           ├── 对象: account
           ├── 方法: deposit
           └── 参数: 500.0 (double)

→ 语义分析:
           ✓ account 是 Account 类型（已声明）
           ✓ Account 类有 deposit(double) 方法
           ✓ 500.0 是 double，参数类型匹配
           ✓ deposit 是 public 方法，可以调用

→ 中间代码: call void @Account::deposit(%class.Account* %account, double 500.0)

→ 代码优化: （此处没有什么可优化的，保持原样）

→ 目标代码:
           mov     x0, x19          ; 把 account 对象地址放入 x0
           fmov    d0, #500.0       ; 把 500.0 放入浮点寄存器
           bl      _ZN7Account7depositEd  ; 调用 Account::deposit
```

到这一步，汇编器会把汇编代码变成 `.o` 目标文件中的二进制机器码，然后交给链接器完成最终的拼接。


## 06.深入链接器内部

上面讲了编译器内部的工作原理，接下来深入链接器。链接器是"把碎片拼成整体"的关键角色。

### 6.1 符号表是什么

每个 `.o` 目标文件都有一个**符号表**（Symbol Table），记录了该文件**定义**了哪些符号和**引用**了哪些符号。

编译 `Account.o` 后，它的符号表大致包含：

| 符号名 | 类型 | 说明 |
|--------|------|------|
| `Account::deposit(double)` | 已定义 | 在这个文件中有实现 |
| `Account::withdraw(double)` | 已定义 | 在这个文件中有实现 |
| `Account::transfer(Account&, double)` | 已定义 | 在这个文件中有实现 |
| `Account::getName() const` | 已定义 | 在这个文件中有实现 |

编译 `BankUserManager.o` 后，它的符号表大致包含：

| 符号名 | 类型 | 说明 |
|--------|------|------|
| `main` | 已定义 | 程序入口 |
| `Account::deposit(double)` | 未定义 | 调用了但不知道实现在哪 |
| `Account::transfer(Account&, double)` | 未定义 | 调用了但不知道实现在哪 |
| `Account::getName() const` | 未定义 | 调用了但不知道实现在哪 |

你可以用 `nm Account.o` 命令查看目标文件的符号表，其中 `T` 表示已定义，`U` 表示未定义。

### 6.2 符号解析过程

链接器的核心工作就是**符号解析**：把所有 `.o` 文件的符号表汇总，给每个"未定义"符号找到"已定义"的实现。

```
BankUserManager.o 需要:               Account.o 提供:
  Account::deposit(double) [未定义]  →  Account::deposit(double) [已定义] ✓
  Account::transfer(...)   [未定义]  →  Account::transfer(...)   [已定义] ✓
  Account::getName()       [未定义]  →  Account::getName()       [已定义] ✓
```

如果所有未定义符号都能找到对应的定义，链接成功。如果某个符号找不到定义，就会报错：

```
ld: symbol(s) not found for architecture arm64
```

这就是最开始我们遇到的那个错误——只编译了 `BankUserManager.cpp`，`Account.o` 没有参与链接，所以 `Account` 类的符号全部找不到。

### 6.3 静态链接和动态链接

链接有两种方式：

**静态链接**：在编译时把所有代码打包到一个可执行文件中。

```bash
# 生成静态库
ar rcs libaccount.a Account.o
# 静态链接
g++ BankUserManager.cpp -L. -laccount -o BankUserManager
```

特点：
- 可执行文件较大（包含了所有依赖的代码）
- 运行时不需要外部库文件
- 库更新后需要重新编译

**动态链接**：在程序运行时才加载外部的共享库。

```bash
# 生成动态库（macOS 上是 .dylib，Linux 上是 .so）
g++ -shared -o libaccount.dylib Account.o
# 动态链接
g++ BankUserManager.cpp -L. -laccount -o BankUserManager
```

特点：
- 可执行文件较小
- 多个程序可以共享同一个库（节省内存和磁盘）
- 库更新后不需要重新编译主程序（只要接口不变）

### 6.4 静态库与动态库区别

用银行项目举个直观的例子来对比：

| 对比项 | 静态库（.a / .lib） | 动态库（.dylib / .so / .dll） |
|--------|----------------------|-------------------------------|
| 打包方式 | `Account.o` 的代码直接复制进可执行文件 | 运行时才从外部文件加载 |
| 文件大小 | 可执行文件较大 | 可执行文件较小 |
| 更新方式 | 改了 `Account.cpp` 要重新编译整个项目 | 只需要替换 `.dylib` 文件 |
| 部署方式 | 只需要一个可执行文件 | 需要带上 `.dylib` 文件 |
| 典型场景 | 嵌入式设备、独立分发的工具 | 系统库、大型项目的模块化 |

### 6.5 链接顺序的影响

链接器处理目标文件和库的顺序是**有讲究**的。链接器从左到右扫描文件：

```bash
# 正确：先放使用者，再放提供者
g++ BankUserManager.o -laccount -o BankUserManager

# 可能出错：如果 account 库又依赖其他库，顺序不对会报错
g++ -laccount BankUserManager.o -o BankUserManager
```

**原则**：被依赖的库放在后面。如果 A 依赖 B，B 依赖 C，链接顺序应该是 `A B C`。

### 6.6 常见链接错误分析

| 错误信息 | 含义 | 解决方法 |
|----------|------|----------|
| `undefined symbol` | 符号未定义，缺少实现 | 确保对应的 `.cpp` 文件被编译并参与链接 |
| `duplicate symbol` | 符号重复定义 | 检查是否在头文件中写了函数实现（应该用 `inline` 或移到 `.cpp`） |
| `symbol(s) not found for architecture` | 目标架构不匹配 | 确保所有 `.o` 文件都是同一架构编译的 |
| `library not found for -lxxx` | 找不到库文件 | 检查库文件路径，用 `-L` 指定搜索路径 |


## 07.CMake构建工具

前面我们用 `g++` 手动编译，用 `Makefile` 管理编译。但当项目变大，文件变多，`Makefile` 也会变得复杂难以维护。这时候就需要更高级的构建工具——CMake。

### 7.1 为什么需要CMake

还是以银行项目为例，回顾一下手动编译的痛点：

**文件少的时候**：一条命令搞定

```bash
g++ Account.cpp BankUserManager.cpp -o BankUserManager
```

**文件多了以后**：假设项目扩展成这样

```
project/
├── include/
│   ├── Account.h
│   ├── Bank.h
│   └── FileManager.h
├── src/
│   ├── Account.cpp
│   ├── Bank.cpp
│   ├── FileManager.cpp
│   └── main.cpp
├── test/
│   └── test_account.cpp
└── lib/
    └── libutils.a
```

手动编译命令变成：

```bash
g++ -Iinclude src/Account.cpp src/Bank.cpp src/FileManager.cpp src/main.cpp -Llib -lutils -o BankUserManager
```

问题越来越多：
1. 每次加新文件都要改命令
2. 不同平台（macOS/Linux/Windows）编译命令不同
3. 依赖关系管理困难
4. 没有增量编译（每次都全量编译，浪费时间）
5. 手写 `Makefile` 繁琐且容易出错

**CMake 就是用来解决这些问题的。**

### 7.2 CMake是什么

CMake 不是编译器，而是一个**构建系统生成器**（Build System Generator）。

它的工作是：读取你写的 `CMakeLists.txt` 配置文件，然后**自动生成**对应平台的构建文件：
- 在 macOS/Linux 上生成 `Makefile`
- 在 Windows 上生成 Visual Studio 项目文件
- 也可以生成 Ninja 构建文件等

```
CMakeLists.txt  →  CMake  →  Makefile / VS项目 / Ninja文件  →  编译器  →  可执行文件
```

所以 CMake 的本质是：**你只写一份配置，CMake 帮你生成各平台的构建脚本**。

### 7.3 CMakeLists基本结构

一个最简单的 `CMakeLists.txt` 长这样：

```cmake
# 指定 CMake 最低版本要求
cmake_minimum_required(VERSION 3.10)

# 定义项目名称和使用的语言
project(BankSystem LANGUAGES CXX)

# 设置 C++ 标准
set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# 添加可执行文件，指定需要编译的源文件
add_executable(BankUserManager Account.cpp BankUserManager.cpp)
```

就这么几行，等价于我们之前写的 `g++ Account.cpp BankUserManager.cpp -o BankUserManager`。

但 CMake 的强大之处在于：当项目复杂度增加时，它的配置依然清晰可控。

### 7.4 用CMake管理银行项目

回到我们的银行项目，现在用 CMake 来管理：

**项目结构**：

```
project/
├── CMakeLists.txt          ← 新增的 CMake 配置文件
├── Account.h
├── Account.cpp
└── BankUserManager.cpp
```

**CMakeLists.txt 内容**：

```cmake
# 1. 最低版本要求
cmake_minimum_required(VERSION 3.10)

# 2. 项目信息
project(BankSystem 
    VERSION 1.0 
    LANGUAGES CXX
)

# 3. C++ 标准
set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# 4. 添加可执行文件目标
add_executable(BankUserManager 
    Account.cpp 
    BankUserManager.cpp
)
```

**构建步骤**：

```bash
# 第一步：创建构建目录（保持源码目录干净）
mkdir build
cd build

# 第二步：运行 CMake 生成构建文件
cmake ..

# 第三步：编译
make

# 第四步：运行
./BankUserManager
```

**为什么要创建 `build` 目录？** 这叫"外部构建"（Out-of-source Build）。CMake 会生成大量中间文件（`Makefile`、`CMakeCache.txt`、`.o` 文件等），放在单独的 `build` 目录里，不会污染源代码目录。想清理时直接 `rm -rf build` 即可。

### 7.5 CMake核心命令详解

逐行拆解 `CMakeLists.txt` 中的每条命令：

**1. `cmake_minimum_required(VERSION 3.10)`**

指定这个项目需要的 CMake 最低版本。不同版本的 CMake 支持的功能不同，设置版本要求可以避免用户用太旧的 CMake 导致配置失败。

**2. `project(BankSystem VERSION 1.0 LANGUAGES CXX)`**

定义项目名称、版本和使用的编程语言：
- `BankSystem`：项目名，会设置 `PROJECT_NAME` 变量
- `VERSION 1.0`：项目版本号
- `LANGUAGES CXX`：告诉 CMake 只使用 C++ 编译器（`CXX` 代表 C++，`C` 代表 C）

**3. `set(CMAKE_CXX_STANDARD 11)`**

设置 CMake 变量。`CMAKE_CXX_STANDARD` 是 CMake 内置变量，指定 C++ 标准版本。等价于 `g++` 的 `-std=c++11` 参数。

**4. `add_executable(BankUserManager Account.cpp BankUserManager.cpp)`**

这是最核心的命令——定义一个**构建目标**：
- `BankUserManager`：目标名称（生成的可执行文件名）
- 后面的参数：需要编译的源文件列表

CMake 会自动：
- 分析每个源文件的依赖关系
- 生成正确的编译命令
- 处理增量编译（只重新编译修改过的文件）

### 7.6 CMake工作原理

CMake 的工作分为两个阶段：

**配置阶段（Configure）**：执行 `cmake ..`

1. 读取 `CMakeLists.txt`
2. 检测系统环境（编译器路径、版本、平台架构等）
3. 处理所有 CMake 命令，生成内部的构建模型
4. 生成 `CMakeCache.txt`（缓存配置结果，下次不用重新检测）
5. 生成构建文件（`Makefile` 等）

**构建阶段（Build）**：执行 `make`

1. 读取 CMake 生成的 `Makefile`
2. 根据依赖关系确定编译顺序
3. 调用编译器编译每个源文件
4. 调用链接器生成可执行文件

用流程图表示：

```
CMakeLists.txt
     │
     ▼ (cmake ..)
┌─────────────────────┐
│   配置阶段           │
│  · 检测编译器        │
│  · 检测平台          │
│  · 解析CMake命令     │
│  · 分析依赖关系      │
└─────────┬───────────┘
          │
          ▼
  Makefile（自动生成）
          │
          ▼ (make)
┌─────────────────────┐
│   构建阶段           │
│  · 编译 Account.cpp  │
│  · 编译 BankUser...  │
│  · 链接生成可执行文件 │
└─────────┬───────────┘
          │
          ▼
  BankUserManager（可执行文件）
```

### 7.7 CMake构建流程图解

将前面所有知识串联起来，看看从 `CMakeLists.txt` 到最终可执行文件的**完整链路**：

```
  你写的文件                CMake 做的事               编译器/链接器做的事
  ─────────               ──────────               ─────────────────
  CMakeLists.txt  ──→  解析配置、生成 Makefile
                                │
                                ▼
  Account.cpp    ──→  Makefile 指导编译  ──→  预处理→编译→汇编 → Account.o
  BankUser...cpp ──→  Makefile 指导编译  ──→  预处理→编译→汇编 → BankUserManager.o
                                                    │
                                                    ▼
                                          Account.o + BankUserManager.o
                                                    │
                                                    ▼ (链接)
                                            BankUserManager (可执行文件)
```

所以 CMake 本身并不编译代码，它只是帮你**自动化了管理编译的过程**。真正干活的还是 `g++`/`clang++` 和 `ld` 链接器。

### 7.8 多目录项目管理

当项目文件变多，通常会按功能分目录。CMake 天然支持多目录项目管理：

**项目结构**：

```
project/
├── CMakeLists.txt              ← 顶层 CMake 文件
├── include/
│   ├── Account.h
│   ├── Bank.h
│   └── FileManager.h
├── src/
│   ├── CMakeLists.txt          ← 子目录 CMake 文件
│   ├── Account.cpp
│   ├── Bank.cpp
│   ├── FileManager.cpp
│   └── main.cpp
└── test/
    ├── CMakeLists.txt          ← 测试目录 CMake 文件
    └── test_account.cpp
```

**顶层 CMakeLists.txt**：

```cmake
cmake_minimum_required(VERSION 3.10)
project(BankSystem VERSION 1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# 添加头文件搜索路径（所有子目录都能用）
include_directories(${PROJECT_SOURCE_DIR}/include)

# 添加子目录，CMake 会去读取子目录中的 CMakeLists.txt
add_subdirectory(src)
add_subdirectory(test)
```

**src/CMakeLists.txt**：

```cmake
# 收集当前目录下所有 .cpp 文件
file(GLOB SOURCES "*.cpp")

# 生成可执行文件
add_executable(BankUserManager ${SOURCES})
```

**test/CMakeLists.txt**：

```cmake
add_executable(test_account test_account.cpp)

# 链接被测试的源文件（这里简单起见直接编译）
target_sources(test_account PRIVATE 
    ${PROJECT_SOURCE_DIR}/src/Account.cpp
)
```

**核心命令说明**：
- `include_directories()`：添加头文件搜索路径，等价于 `g++ -I` 参数
- `add_subdirectory()`：告诉 CMake 去处理子目录中的 `CMakeLists.txt`
- `file(GLOB ...)`：用通配符收集文件，避免手动列举每个 `.cpp`
- `target_sources()`：给已有目标追加源文件


## 08.CMake进阶实践

### 8.1 添加第三方库依赖

实际项目经常需要依赖第三方库。以银行项目为例，假设要加一个 JSON 库来保存数据：

```cmake
cmake_minimum_required(VERSION 3.10)
project(BankSystem VERSION 1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 11)

# 查找系统中安装的第三方库
find_package(nlohmann_json REQUIRED)

add_executable(BankUserManager 
    Account.cpp 
    BankUserManager.cpp
)

# 链接第三方库到目标
target_link_libraries(BankUserManager PRIVATE nlohmann_json::nlohmann_json)
```

**核心命令**：
- `find_package()`：在系统中查找已安装的库。`REQUIRED` 表示找不到就报错停止
- `target_link_libraries()`：把库链接到指定目标。`PRIVATE` 表示这个依赖只对当前目标生效，不传递给依赖它的其他目标

### 8.2 条件编译控制

CMake 支持根据条件控制编译行为，比如区分 Debug 和 Release 模式：

```cmake
cmake_minimum_required(VERSION 3.10)
project(BankSystem VERSION 1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 11)

add_executable(BankUserManager Account.cpp BankUserManager.cpp)

# 根据构建类型设置不同的编译选项
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    # Debug 模式：不优化，开启调试信息
    target_compile_options(BankUserManager PRIVATE -g -O0)
    # 定义宏，代码中可以用 #ifdef DEBUG 判断
    target_compile_definitions(BankUserManager PRIVATE DEBUG)
elseif(CMAKE_BUILD_TYPE STREQUAL "Release")
    # Release 模式：开启优化
    target_compile_options(BankUserManager PRIVATE -O2)
endif()
```

使用方式：

```bash
# Debug 构建
cmake -DCMAKE_BUILD_TYPE=Debug ..
make

# Release 构建
cmake -DCMAKE_BUILD_TYPE=Release ..
make
```

### 8.3 生成静态库和动态库

前面第6章讲了静态库和动态库的概念，现在用 CMake 来生成它们：

```cmake
cmake_minimum_required(VERSION 3.10)
project(BankSystem VERSION 1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 11)

# 生成静态库 libaccount.a
add_library(account_static STATIC Account.cpp)

# 生成动态库 libaccount.dylib（macOS）或 libaccount.so（Linux）
add_library(account_shared SHARED Account.cpp)

# 设置库文件的输出名称（去掉 _static/_shared 后缀）
set_target_properties(account_static PROPERTIES OUTPUT_NAME account)
set_target_properties(account_shared PROPERTIES OUTPUT_NAME account)

# 主程序链接静态库
add_executable(BankUserManager BankUserManager.cpp)
target_link_libraries(BankUserManager PRIVATE account_static)
```

**核心命令**：
- `add_library(name STATIC sources)`：生成静态库
- `add_library(name SHARED sources)`：生成动态库
- `set_target_properties()`：设置目标属性，如输出名称
- `target_link_libraries()`：链接库到可执行文件

### 8.4 安装和打包

CMake 还可以配置项目的安装规则，方便部署：

```cmake
# 安装可执行文件到 /usr/local/bin
install(TARGETS BankUserManager DESTINATION bin)

# 安装头文件到 /usr/local/include
install(FILES Account.h DESTINATION include)

# 安装库文件到 /usr/local/lib
install(TARGETS account_shared DESTINATION lib)
```

执行安装：

```bash
cmake --build build
cmake --install build
# 或者
cd build && make install
```

### 8.5 构建工具对比总结

学完这些，回头对比一下不同的构建方式：

| 构建方式 | 适用场景 | 优点 | 缺点 |
|----------|----------|------|------|
| `g++` 手动编译 | 几个文件的小项目 | 简单直接 | 文件多了命令太长，无增量编译 |
| `Makefile` | 中小型项目 | 支持增量编译，规则灵活 | 语法复杂，跨平台困难 |
| `CMake` | 中大型项目 | 跨平台、自动依赖分析、生态完善 | 需要学习 CMake 语法 |

**选择建议**：

- 练习用的小项目（1~3 个文件）：直接 `g++` 手动编译
- 有一定规模的项目：使用 CMake
- 实际工作中的 C++ 项目：基本都用 CMake（它已经是 C++ 社区的事实标准）

### 8.6 完整项目CMake示例

最后给出一个完整的、可在实际项目中参考的 `CMakeLists.txt`：

```cmake
# ============================================
# 银行管理系统 - CMake 构建配置
# ============================================

# 最低版本要求
cmake_minimum_required(VERSION 3.10)

# 项目基本信息
project(BankSystem 
    VERSION 1.0.0
    DESCRIPTION "A simple bank management system"
    LANGUAGES CXX
)

# ---- 编译选项 ----
set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
# 禁用编译器扩展，保证代码可移植性
set(CMAKE_CXX_EXTENSIONS OFF)

# ---- 头文件路径 ----
include_directories(${PROJECT_SOURCE_DIR}/include)

# ---- 源文件收集 ----
file(GLOB LIB_SOURCES "${PROJECT_SOURCE_DIR}/src/*.cpp")
# 从库源文件中排除 main.cpp
list(FILTER LIB_SOURCES EXCLUDE REGEX ".*main\\.cpp$")

# ---- 构建库 ----
# 将 Account 等业务逻辑编译为库，方便主程序和测试复用
add_library(bank_lib STATIC ${LIB_SOURCES})
target_include_directories(bank_lib PUBLIC ${PROJECT_SOURCE_DIR}/include)

# ---- 构建主程序 ----
add_executable(BankUserManager ${PROJECT_SOURCE_DIR}/src/main.cpp)
target_link_libraries(BankUserManager PRIVATE bank_lib)

# ---- 构建测试（可选） ----
option(BUILD_TESTS "Build test programs" OFF)
if(BUILD_TESTS)
    enable_testing()
    file(GLOB TEST_SOURCES "${PROJECT_SOURCE_DIR}/test/*.cpp")
    foreach(TEST_FILE ${TEST_SOURCES})

        add_executable(${TEST_NAME} ${TEST_FILE})
        target_link_libraries(${TEST_NAME} PRIVATE bank_lib)
        add_test(NAME ${TEST_NAME} COMMAND ${TEST_NAME})
    endforeach()
endif()

# ---- 安装规则 ----
install(TARGETS BankUserManager DESTINATION bin)
```

## 09.深挖：链接器内部的真实工作

前面 06 章讲了链接器"做什么"；这一节讲它"**具体怎么做**"——这对于排查链接错误、理解 ABI 兼容性、做二进制优化都是必备知识。

### 9.1 符号解析的单遍扫描算法

链接器处理命令行参数是**从左到右单遍**的，并维护两个集合：

- **已解析符号集（Defined）**：目前已经看到的函数/全局变量定义。
- **未决符号集（Undefined）**：被引用但还没找到定义的符号。

对每个输入参数（.o 或 .a）的处理：

- **如果是 .o**：**全部**加入——它的所有定义进 Defined、所有引用进 Undefined；
- **如果是 .a（静态库）**：只提取那些**能满足当前 Undefined**的 .o；一个 .a 里的 .o 如果当前没人需要，**整个丢弃**。

单遍扫描带来一个工程后果：**"要先声明后使用"**。

```bash
gcc main.o -lfoo   # 正确：main 用到 libfoo 的符号时，libfoo 已经在等待
gcc -lfoo main.o   # 错误：libfoo 扫描时 Undefined 为空，它的所有 .o 都被丢弃
```

这就是为什么 `undefined reference to 'foo_init'` 经常要改命令行参数顺序——不是代码错了，是链接顺序错了。

### 9.2 循环依赖和 --start-group

实际项目里可能出现循环依赖：libA 用 libB、libB 又用 libA。单遍扫描会失败（无论谁先，都会丢另一个的 .o）。解决方式：

- **`-Wl,--start-group libA.a libB.a -Wl,--end-group`**：告诉链接器重复扫描这段直到不再有新的 Undefined 被解决。性能略差但解循环依赖。
- **重新设计库依赖**：循环依赖是架构坏味道，长期解药是拆库。

### 9.3 重定位：段合并后地址的修正

当链接器把所有 .o 的 `.text` 合并成一段时，每个函数在最终二进制里的地址都变了。所有对这些地址的引用（函数调用的 `call` 指令、全局变量的 `mov` 指令等）都要修正。.o 文件里记录这些需要修正的位置的是**重定位表（`.rela.text`、`.rela.data`）**。

每一条重定位记录包含：

- **偏移**：需要修改的位置（在合并前的 .text 里的偏移）；
- **符号**：引用的目标符号；
- **类型**：修改方式（R_X86_64_PC32 = 32 位 PC 相对地址；R_X86_64_64 = 绝对 64 位地址；R_X86_64_PLT32 = 走 PLT 间接跳转等）。

链接器按类型计算新地址，写回段里。这是"机械但不简单"的工作——得到大量 cryptic 的链接错误（"relocation truncated to fit"、"relocation R_X86_64_PC32 against symbol ..."）都源于这里。

### 9.4 GOT 和 PLT：动态链接的核心

静态链接完成后地址就定了；但动态链接时，共享库的加载地址是**运行时**决定的（ASLR、不同进程不同地址）。怎么让共享库里的函数调用/全局变量访问不依赖"编译期地址"？答案是 **GOT（Global Offset Table）和 PLT（Procedure Linkage Table）**。

**GOT**：每个共享库有自己的 GOT，里面是**所有外部符号的实际地址**。这张表由动态链接器（`ld-linux.so` / `dyld`）在库加载时填好。代码访问外部全局变量时走 GOT：

```asm
mov rax, [rip + foo@GOTPCREL]   ; 从 GOT 读 foo 的实际地址
mov rax, [rax]                   ; 实际读 foo 的值
```

**PLT**：对外部函数调用，直接用 GOT 调用会触发"每次都要动态链接器解析"——太慢。PLT 做了**lazy binding**：

```
    第一次调用 foo():
    call foo@PLT
         │
         ▼
    foo@PLT:                 // 自动生成的跳板
      jmp [foo@GOT]          // GOT 里初始指向 PLT 下一条指令
      push id_of_foo
      jmp 解析器              // 第一次落到这里，解析器填好 foo@GOT
    
    之后调用 foo():
    call foo@PLT
         │
         ▼
    foo@PLT:
      jmp [foo@GOT]          // GOT 已填好 foo 的实际地址，直接跳转
```

第一次慢（有动态解析），第二次之后就只是"两次间接跳转"。理解了 GOT/PLT，就懂了为什么"共享库里的函数调用比静态链接贵一点"——每次都多走一次间接。

### 9.5 PIE 与 ASLR：为什么现代 Linux 的可执行文件也是"共享库"

以前可执行文件是 **ET_EXEC**（固定加载地址，编译期就定了绝对地址）；现代 Linux 发行版默认把可执行文件编成 **PIE（Position-Independent Executable，ET_DYN）**——和共享库一样，加载地址是运行时决定的。

好处：**ASLR（Address Space Layout Randomization）对可执行文件也生效**——攻击者猜不到代码、栈、堆的地址，缓冲区溢出利用难度大增。

代价是所有代码都要是"位置无关的"——不能硬编码绝对地址，所有全局引用都走 GOT。性能损失约 1-3%，但安全收益巨大。所以现代 C++ 工具链默认开 PIE。

### 9.6 COMDAT 与"一次定义规则"（ODR）

C++ 的 inline 函数、模板实例化、类的虚函数表——这些东西可能在多个 .o 里重复定义。链接器如何处理？

答案是 **COMDAT 组（section group）**。每个 inline 函数/模板实例化被放到一个唯一命名的 COMDAT 组（用 mangled name 做 key），链接器看到多个相同名字的 COMDAT 组时，**只保留一份**（随便哪份，通常是第一份）。

这就是为什么：

- 你可以把 inline 函数放头文件，多个 .cpp 包含它没事；
- 同一个模板实例化（`std::vector<int>`）在 50 个 .cpp 里用到，最终二进制只有一份代码；
- 但如果两个 .cpp 的"同名 inline 函数"**定义内容不同**——链接器也只保留一份，你实际拿到的是随机其中一个（这就是"ODR 违反"的可怕之处，链接器不报错）。

## 10.ELF 文件结构速览

理解编译链接，绕不过 ELF 格式。Linux 下的 .o、.so、可执行文件都是 ELF。

### 10.1 ELF 的三视图

ELF 文件有两种组织方式：

- **链接视图（Section View）**：给链接器看，按"段"（`.text`、`.data`、`.rela.text`、`.symtab` 等）组织。.o 文件主要是这个视图。
- **执行视图（Segment View）**：给加载器看，按"段"（PT_LOAD、PT_DYNAMIC 等）组织。可执行文件和 .so 主要是这个视图。

两个视图的切换由 ELF 头部和 section/program header 描述。`readelf -S file` 看 section，`readelf -l file` 看 segment。

### 10.2 常见 section 的用途

| Section | 用途 | 只读 | 可执行 |
|---------|------|------|--------|
| `.text` | 代码 | 是 | 是 |
| `.rodata` | 字符串字面量、const 全局 | 是 | 否 |
| `.data` | 已初始化全局变量 | 否 | 否 |
| `.bss` | 未初始化全局变量（文件里不占空间） | 否 | 否 |
| `.symtab` | 符号表 | - | - |
| `.strtab` | 字符串表（符号名存储） | - | - |
| `.rela.text` | `.text` 的重定位表 | - | - |
| `.eh_frame` | 栈展开信息 | 是 | 否 |
| `.debug_*` | DWARF 调试信息 | 是 | 否 |
| `.got` / `.plt` | 动态链接表 | 混合 | - |

### 10.3 用工具检视

- `nm file.o`——列出符号表；`U` = undefined、`T` = text（全局）、`t` = text（static）、`W` = weak。
- `objdump -d file`——反汇编。
- `objdump -r file.o`——查看重定位表。
- `readelf -h file`——ELF 头；`readelf -a file`——所有信息。
- `strings file`——提取可打印字符串（常用于快速查版本、license）。
- `ldd executable`——列出动态库依赖。
- `strace ./program`——看程序运行时的系统调用，能辅助诊断启动失败。

这些命令组合起来能解答"我的二进制为什么那么大""为什么启动慢""为什么找不到符号"这类问题 90% 的情况。熟练程度和是否"会 C++"是正相关的。

## 11.小结：编译链接的思考模型

### 11.1 三个心智模型

- **把编译器当翻译机**：源码 → AST → IR → 汇编 → 机器码。每一步都有优化发生，搞不清为什么快/慢时用 `-S` 看汇编。
- **把链接器当拼图师**：输入是一堆碎片（.o、.a、.so），输出是一张拼好的图（可执行文件）。拼接规则是"每个符号唯一定义"——ODR 违反是拼图错了。
- **把动态链接当约会**：库和程序在运行时相遇，运行时协议是 ABI + GOT/PLT。两者必须按同一份协议约会，否则 crash。

2. `a.a` 依赖 `b.a`，`b.a` 又依赖 `a.a` 里的某个新函数。正确的链接命令是什么？
3. 你发现 `ldd` 显示程序依赖 `libfoo.so.1`，但运行时报 `libfoo.so.2: version 'XXX' not found`。这是什么情况？如何修复？
4. 一个共享库里的全局变量每次 `dlopen` 都重新初始化，还是保留上次的值？如果多个进程 `dlopen` 同一个 .so，它们的全局变量是同一份吗？
