## 01.崩溃的原因

### 1.1 内存访问违规

1. **空指针解引用**：CPU尝试访问受保护的内存地址0x0，触发硬件异常。

```cpp
int* ptr = nullptr;
*ptr = 42; // 崩溃：访问地址0x0
```

**底层原理**：虚拟地址空间的前几页（通常是0x0-0xFFF）被操作系统标记为不可访问（Guard Page）。CPU的MMU在地址翻译时发现该页不在页表中，触发Page Fault（#PF）。内核检测到这是一个非法访问，向进程发送SIGSEGV信号。

2. **野指针解引用**：访问已释放或未初始化的指针。

```cpp
int* ptr = new int(42);
delete ptr;
*ptr = 100; // 崩溃：访问已释放内存（Use-After-Free）
```

**底层原理**：内存释放后，操作系统可能已将该内存区域标记为不可访问。但如果内存被复用给其他对象，可能不会立即崩溃，而是产生更隐蔽的数据损坏——这是Use-After-Free漏洞的危险所在。

3. **缓冲区溢出**：数组越界、字符串操作超出分配空间。

```cpp
char buffer[10];
strcpy(buffer, "This string is way too long for the buffer!");
// 崩溃：栈帧被破坏，返回地址被覆盖
```

**底层原理**：写入超出分配内存边界，破坏了相邻的栈帧数据（包括保存的寄存器值和返回地址）。当函数返回时，CPU跳转到被破坏的地址，执行非法指令或访问非法内存。

4. **双重释放（Double Free）**：

```cpp
int* ptr = new int(42);
delete ptr;
delete ptr; // 崩溃：双重释放
```

**底层原理**：内存管理器（如glibc的ptmalloc）维护着空闲链表。第一次free将块标记为空闲并放入链表。第二次free时，该块已在空闲链表中，再次插入会破坏链表结构，导致后续的malloc/free操作崩溃。现代内存分配器通常能检测到双重释放并调用abort()。

### 1.2 栈溢出

1. **无限递归或过深的递归**导致栈空间耗尽：

```cpp
void recursiveFunction() {
    char buffer[1024]; // 每次递归占用1KB+栈空间
    recursiveFunction(); // 无限递归
}
```

**底层原理**：线程栈空间有限（Linux默认8MB，可通过`ulimit -s`查看）。每次函数调用都在栈上分配新的栈帧（包括返回地址、保存的寄存器、局部变量）。当栈指针超出栈的Guard Page时，触发SIGSEGV。

```
高地址
┌─────────────┐
│   栈底       │
│   ...        │
│   递归帧N    │ ← 最新的递归调用
│   递归帧N-1  │
│   ...        │
│   递归帧1    │
│   main帧    │
├─────────────┤
│  Guard Page  │ ← 碰到这里就触发SIGSEGV
├─────────────┤
│   堆/其他    │
低地址
```

2. **栈上分配过大的局部变量**：

```cpp
void bigStackAllocation() {
    int huge_array[10000000]; // 约40MB，远超栈大小
    huge_array[0] = 1;       // 崩溃
}
```

### 1.3 整数除零

整数除法中除数为零：

```cpp
int a = 10;
int b = 0;
int c = a / b; // 崩溃：整数除零
```

**底层原理**：CPU执行DIV/IDIV指令时，如果除数为0，触发#DE（Divide Error）异常。内核将此中断转换为SIGFPE信号发送给进程。

**注意**：浮点除零**不会崩溃**，而是产生特殊值：

```cpp
double a = 1.0;
double b = 0.0;
double c = a / b;  // 不崩溃，c = +inf（正无穷）
double d = -a / b; // 不崩溃，d = -inf（负无穷）
double e = b / b;  // 不崩溃，e = NaN
```

这是因为IEEE 754标准定义了浮点除零的行为，而整数除零是未定义行为。

### 1.4 未处理异常

C++异常未被catch块捕获，导致`std::terminate`被调用：

```cpp
void throwingFunction() {
    throw std::runtime_error("something went wrong");
}

int main() {
    throwingFunction(); // 未捕获 → std::terminate() → abort() → SIGABRT
}
```

**底层原理**：异常在栈展开过程中没有找到匹配的catch块，当展开到main函数仍然没有，C++运行时调用`std::terminate()`，默认行为是调用`abort()`，生成SIGABRT信号。

**noexcept违反**也会触发terminate：

```cpp
void safe_function() noexcept {
    throw std::runtime_error("oops"); // noexcept函数抛异常
    // 直接调用std::terminate()，不进行栈展开
}
```

### 1.5 断言失败

assert宏的条件不满足，导致程序终止：

```cpp
#include <cassert>

void process(int* data, size_t size) {
    assert(data != nullptr && "data must not be null");
    assert(size > 0 && "size must be positive");
    // ...
}

int main() {
    process(nullptr, 0);
    // 输出: Assertion failed: data != nullptr && "data must not be null"
    //       file example.cpp, line 4
    // 然后调用 abort() → SIGABRT
}
```

**底层原理**：`assert`宏在条件为false时调用`abort()`。在Release模式（定义了NDEBUG宏）中，assert被展开为空语句，不会有任何检查。

### 1.6 系统资源耗尽

**内存不足（OOM）**：

```cpp
try {
    // 尝试分配100GB内存
    char* huge = new char[100ULL * 1024 * 1024 * 1024];
} catch (const std::bad_alloc& e) {
    std::cerr << "内存分配失败: " << e.what() << std::endl;
}

// 如果使用nothrow版本
char* ptr = new(std::nothrow) char[100ULL * 1024 * 1024 * 1024];
if (!ptr) {
    std::cerr << "分配失败，返回nullptr" << std::endl;
}
```

**文件描述符耗尽**：

```cpp
// 不断打开文件但不关闭
std::vector<int> fds;
while (true) {
    int fd = open("/dev/null", O_RDONLY);
    if (fd == -1) {
        perror("open failed"); // errno = EMFILE (Too many open files)
        break;
    }
    fds.push_back(fd);
}
// ulimit -n 查看限制（通常1024或4096）
```

### 1.7 多线程问题

**数据竞争（Data Race）**：

```cpp
int counter = 0;

void increment() {
    for (int i = 0; i < 1000000; i++) {
        counter++; // 非原子操作，实际是：读-改-写 三步
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();
    // counter 可能远小于2000000
    // 更严重的情况：如果是对指针的竞争访问，可能直接崩溃
}
```

**底层原理**：`counter++`在汇编层面是`load → add → store`三条指令。两个线程可能同时读到相同的值，各自加1后写回，导致更新丢失。对于复杂数据结构的并发修改，可能破坏内部一致性导致崩溃。

**死锁导致的超时崩溃**：

```cpp
std::mutex m1, m2;

// 线程1: 先锁m1再锁m2
void thread1() {
    std::lock_guard<std::mutex> g1(m1);
    std::this_thread::sleep_for(std::chrono::milliseconds(1));
    std::lock_guard<std::mutex> g2(m2); // 死锁：等待m2
}

// 线程2: 先锁m2再锁m1
void thread2() {
    std::lock_guard<std::mutex> g2(m2);
    std::this_thread::sleep_for(std::chrono::milliseconds(1));
    std::lock_guard<std::mutex> g1(m1); // 死锁：等待m1
}

// 解决：使用std::lock同时锁定多个互斥量
void safe_thread() {
    std::scoped_lock lock(m1, m2); // C++17，自动按一致顺序加锁
}
```

### 1.8 非法指令

CPU执行了未定义的指令（如数据被当作代码执行，或编译器生成了目标平台不支持的指令）：

```cpp
// 通过函数指针跳转到数据区域
int data = 0x12345678;
void (*func_ptr)() = reinterpret_cast<void(*)()>(&data);
func_ptr(); // SIGILL：数据被当作指令执行
```

**底层原理**：CPU在解码阶段发现无法识别的操作码，触发#UD（Undefined Opcode）异常，内核将其转换为SIGILL信号。

### 1.9 主动终止

```cpp
// abort(): 立即终止，生成核心转储，发送SIGABRT
abort();

// exit(code): 正常终止流程（调用atexit注册的函数、刷新IO缓冲）
exit(1);

// _exit(code): 立即终止，不执行清理
_exit(1);

// std::terminate(): C++运行时终止，默认调用abort()
std::terminate();

// std::quick_exit(code): 不调用析构函数，只调用at_quick_exit注册的函数
std::quick_exit(1);
```


## 02.崩溃的流程

### 2.1 硬件异常

CPU在执行指令过程中检测到非法操作，触发硬件中断：

```
x86架构的常见异常向量：
#0  DE  - 除零错误 (Divide Error)
#6  UD  - 无效操作码 (Invalid Opcode)
#12 SS  - 栈段错误 (Stack-Segment Fault)
#13 GP  - 通用保护故障 (General Protection Fault)
#14 PF  - 页面错误 (Page Fault)
```

当异常触发时，CPU会：
1. 停止当前指令的执行
2. 保存当前状态（指令指针、标志寄存器等）到栈
3. 通过IDT（中断描述符表）跳转到内核的异常处理程序

### 2.2 信号生成

内核的异常处理程序识别异常类型，将其映射为POSIX信号：

```
硬件异常          →    POSIX信号
─────────────────────────────────
Page Fault(非法)  →    SIGSEGV (11)
Divide Error      →    SIGFPE  (8)
Invalid Opcode    →    SIGILL  (4)
Bus Error         →    SIGBUS  (7)
```

内核通过`force_sig_info()`向目标进程发送信号，信号包含以下信息：
- `si_signo`：信号编号
- `si_code`：详细的错误原因（如SEGV_MAPERR表示地址未映射、SEGV_ACCERR表示权限错误）
- `si_addr`：触发异常的内存地址

### 2.3 信号处理

```
信号到达进程后的处理逻辑：

1. 检查进程是否注册了信号处理函数（通过signal/sigaction）
   ├── 是 → 执行用户注册的处理函数
   │         ├── 处理函数正常返回 → 恢复执行（但对于SIGSEGV等通常会再次触发）
   │         └── 处理函数调用abort/exit → 进入终止流程
   └── 否 → 执行默认处理
             ├── SIGTERM: 终止进程
             ├── SIGSEGV: 终止进程 + 核心转储
             ├── SIGFPE:  终止进程 + 核心转储
             └── SIGKILL: 立即终止（不可捕获）
```

### 2.4 核心转储

如果系统配置允许（`ulimit -c`不为0），内核在进程终止前生成核心转储文件（core dump）：

```bash
# 查看和设置核心转储大小限制
ulimit -c           # 查看（0表示禁用）
ulimit -c unlimited # 不限制大小

# 设置核心转储文件的路径和命名模式
echo "/tmp/core.%e.%p.%t" > /proc/sys/kernel/core_pattern
# %e: 可执行文件名
# %p: 进程ID
# %t: 时间戳
```

核心转储文件包含：
- 进程的虚拟内存快照（所有可读的内存页）
- CPU寄存器值（包括程序计数器、栈指针等）
- 信号信息（哪个信号导致的崩溃）
- 线程信息（所有线程的状态）

### 2.5 进程终止

内核执行进程终止流程：
1. 释放进程占用的所有资源（内存页、文件描述符、信号量等）
2. 向父进程发送SIGCHLD信号
3. 设置退出状态（包含终止信号编号）
4. 父进程通过wait/waitpid获取退出状态

```cpp
// 父进程获取子进程的崩溃信息
int status;
pid_t child = wait(&status);
if (WIFSIGNALED(status)) {
    int sig = WTERMSIG(status);
    printf("子进程被信号 %d (%s) 终止\n", sig, strsignal(sig));
    if (WCOREDUMP(status)) {
        printf("已生成核心转储文件\n");
    }
}
```

### 2.6 崩溃流程全景图

```
用户空间                           内核空间                     硬件
─────────                        ─────────                    ─────
                                                              CPU执行指令
                                                                 │
                                                              检测到异常
                                                              (如#PF)
                                                                 │
                                                              触发中断
                                                                 │
                                  IDT查表 ←─────────────────────┘
                                     │
                                  异常处理程序
                                     │
                                  映射为POSIX信号
                                     │
                                  发送信号给进程
                                     │
用户信号处理 ←───────────────────────┘
   │
   ├─ 有自定义handler
   │  ├─ 记录崩溃信息
   │  ├─ 生成minidump
   │  └─ 调用abort()
   │
   └─ 无自定义handler（默认）
      │
      └─ 终止进程 ────────────────→ 生成core dump
                                        │
                                     释放资源
                                        │
                                   通知父进程(SIGCHLD)
```


## 03.崩溃监听原理

### 3.1 Linux信号处理

```cpp
#include <csignal>
#include <cstdlib>
#include <iostream>
#include <execinfo.h>
#include <unistd.h>

// 信号安全的写函数（printf在信号处理函数中不安全）
void safe_write(const char* msg) {
    write(STDERR_FILENO, msg, strlen(msg));
}

void signalHandler(int signal, siginfo_t* info, void* context) {
    // 信号处理函数中只能调用"异步信号安全"的函数
    // 不安全的：printf, malloc, new, std::cout
    // 安全的：write, _exit, signal相关函数
    
    safe_write("\n=== CRASH DETECTED ===\n");
    
    // 输出信号信息
    switch(signal) {
        case SIGSEGV: safe_write("Signal: SIGSEGV (Segmentation Fault)\n"); break;
        case SIGABRT: safe_write("Signal: SIGABRT (Abort)\n"); break;
        case SIGFPE:  safe_write("Signal: SIGFPE (Floating Point Exception)\n"); break;
        case SIGILL:  safe_write("Signal: SIGILL (Illegal Instruction)\n"); break;
        case SIGBUS:  safe_write("Signal: SIGBUS (Bus Error)\n"); break;
    }
    
    // 输出崩溃地址
    if (info) {
        char addr_buf[64];
        snprintf(addr_buf, sizeof(addr_buf), "Fault address: %p\n", info->si_addr);
        safe_write(addr_buf);
    }
    
    // 获取堆栈跟踪（backtrace在某些实现中是信号安全的）
    void* array[50];
    int size = backtrace(array, 50);
    safe_write("Stack trace:\n");
    backtrace_symbols_fd(array, size, STDERR_FILENO);
    
    // 恢复默认信号处理并重新触发，以生成核心转储
    struct sigaction sa;
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sigaction(signal, &sa, nullptr);
    raise(signal); // 重新触发信号，使用默认处理（生成core dump）
}

void setupCrashHandler() {
    struct sigaction sa;
    sa.sa_sigaction = signalHandler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK; // SA_SIGINFO获取详细信息
    
    sigaction(SIGSEGV, &sa, nullptr);
    sigaction(SIGABRT, &sa, nullptr);
    sigaction(SIGFPE,  &sa, nullptr);
    sigaction(SIGILL,  &sa, nullptr);
    sigaction(SIGBUS,  &sa, nullptr);
    
    // 设置备用信号栈（防止栈溢出时无法处理信号）
    static char alt_stack[SIGSTKSZ];
    stack_t ss;
    ss.ss_sp = alt_stack;
    ss.ss_size = SIGSTKSZ;
    ss.ss_flags = 0;
    sigaltstack(&ss, nullptr);
}
```

### 3.2 C++异常处理

```cpp
#include <exception>
#include <iostream>
#include <stdexcept>
#include <cxxabi.h>

void terminateHandler() {
    // 获取当前异常的类型信息
    std::exception_ptr eptr = std::current_exception();
    
    if (eptr) {
        try {
            std::rethrow_exception(eptr);
        } catch (const std::exception& e) {
            // 获取异常的真实类型名
            int status;
            const char* name = typeid(e).name();
            char* demangled = abi::__cxa_demangle(name, nullptr, nullptr, &status);
            
            std::cerr << "Unhandled exception of type: " 
                      << (demangled ? demangled : name) << std::endl;
            std::cerr << "what(): " << e.what() << std::endl;
            
            free(demangled);
        } catch (...) {
            std::cerr << "Unhandled exception of unknown type" << std::endl;
        }
    } else {
        std::cerr << "std::terminate called without active exception" << std::endl;
        // 可能的原因：
        // 1. noexcept函数抛出异常
        // 2. 析构函数在栈展开中抛异常
        // 3. 直接调用std::terminate
    }
    
    abort(); // 生成核心转储
}

int main() {
    std::set_terminate(terminateHandler);
    // ...
}
```

### 3.3 sigaction vs signal

```cpp
// signal() 的问题：
// 1. 行为在不同系统上不一致（System V vs BSD语义）
// 2. 不能获取信号的附加信息（si_addr等）
// 3. 在某些系统上，处理器执行后会被重置为默认
signal(SIGSEGV, handler); // 不推荐

// sigaction() 更可靠：
// 1. 行为一致
// 2. 可以通过SA_SIGINFO获取详细信息
// 3. 可以设置SA_ONSTACK使用备用栈
// 4. 可以设置信号掩码
struct sigaction sa;
sa.sa_sigaction = handler;
sa.sa_flags = SA_SIGINFO | SA_ONSTACK;
sigaction(SIGSEGV, &sa, nullptr); // 推荐
```


## 04.崩溃分析流程

### 4.1 获取崩溃状态

崩溃分析需要以下信息：

```
必要信息：
1. 崩溃时的寄存器状态（尤其是PC/RIP指令指针）
2. 完整的栈回溯（Call Stack / Backtrace）
3. 崩溃信号和地址（SIGSEGV at 0x0000000）
4. 崩溃时的线程信息

辅助信息：
5. 编译时的符号表（debug symbols）
6. 源代码与构建版本对应关系
7. 运行时的日志信息
8. 内存映射信息（/proc/pid/maps）
```

### 4.2 核心转储分析

```bash
# 1. 确保启用核心转储
ulimit -c unlimited

# 2. 编译时保留符号信息
g++ -g -o myapp myapp.cpp

# 3. 运行程序（崩溃后会生成core文件）
./myapp

# 4. 查看核心转储文件
file core
# core: ELF 64-bit LSB core file, x86-64, version 1 (SYSV)
```

### 4.3 使用GDB分析core dump

```bash
# 加载core dump
gdb ./myapp core

# 常用分析命令：
(gdb) bt            # 查看完整栈回溯（最重要）
(gdb) bt full       # 查看栈回溯 + 局部变量
(gdb) info threads  # 查看所有线程
(gdb) thread 2      # 切换到线程2
(gdb) frame 3       # 切换到第3个栈帧
(gdb) info registers # 查看寄存器状态
(gdb) x/10i $rip    # 查看崩溃点附近的指令
(gdb) print *ptr    # 检查变量值
(gdb) info sharedlibrary # 查看加载的共享库

# 多线程崩溃分析
(gdb) thread apply all bt # 打印所有线程的栈回溯
```

**GDB分析实例**：

```
(gdb) bt
#0  0x0000000000401234 in processData (data=0x0) at main.cpp:42
#1  0x0000000000401345 in handleRequest (req=...) at server.cpp:156
#2  0x0000000000401567 in main () at main.cpp:89

分析：
- 帧#0：崩溃在processData函数，data参数为0x0（空指针）
- 帧#1：handleRequest调用了processData，传入了空指针
- 根因：handleRequest没有对req中的数据做空指针检查
```

### 4.4 符号化与addr2line

当只有地址信息（如从生产环境的崩溃日志中获取）时，使用addr2line将地址转换为源码位置：

```bash
# 输出：

```


## 05.底层核心原理

### 5.1 Linux信号处理机制

信号处理涉及用户态和内核态的频繁切换：

```
正常执行（用户态）
       │
   系统调用/异常
       │
       ↓
   进入内核态
       │
   处理异常 + 发送信号
       │
   从内核返回前检查：有pending信号？
       │
       ├─ 无：正常返回用户态
       │
       └─ 有：
           1. 保存用户态上下文到用户栈（sigframe）
           2. 修改返回地址为信号处理函数
           3. 返回用户态
               │
           4. 执行信号处理函数
               │
           5. 处理函数返回，调用sigreturn系统调用
               │
           6. 内核恢复原始上下文
               │
           7. 返回用户态继续原来的执行
```

**关键细节**：信号处理函数运行在**用户态**，但内核通过修改用户栈和返回地址来"劫持"控制流。这就是为什么信号处理函数中只能使用"异步信号安全"的函数——因为你可能中断了malloc/printf等非可重入函数。

### 5.2 C++异常与信号的关系

```
C++异常和信号是两套完全独立的机制：

C++异常:
  - 由throw语句触发
  - 通过栈展开（Stack Unwinding）传播
  - 可以携带任意类型的异常对象
  - 完全在用户态处理
  - 析构函数在栈展开过程中被调用

信号:
  - 由硬件异常或内核事件触发
  - 通过内核的信号传递机制处理
  - 只携带信号编号和少量附加信息
  - 涉及内核态切换
  - 不触发C++析构函数

关键区别:
  SIGSEGV等信号不能用try/catch捕获
  try {
      int* p = nullptr;
      *p = 42; // SIGSEGV，不是C++异常
  } catch (...) {
      // 不会到达这里！
  }
  
  某些编译器扩展（如MSVC的__try/__except）可以捕获SEH异常
  但这不是标准C++的一部分
```

### 5.3 栈回溯的底层实现

栈回溯是崩溃分析中最关键的信息。它的实现依赖于栈帧的组织方式：

```
方法1：帧指针（Frame Pointer）回溯
  优点：简单快速
  缺点：需要编译时保留帧指针（-fno-omit-frame-pointer）

  高地址
  ┌─────────────────┐
  │   返回地址N      │  ← 通过RBP链找到每一帧的返回地址
  │   保存的RBP(N)  │  ← RBP[N] 指向上一帧的RBP
  │   局部变量       │
  ├─────────────────┤
  │   返回地址N-1    │
  │   保存的RBP(N-1)│  ← RBP[N-1] 指向上一帧的RBP
  │   局部变量       │
  ├─────────────────┤
  │   ...           │
  低地址

  回溯算法：
  current_rbp = register RBP
  while (current_rbp != 0) {
      return_addr = *(current_rbp + 8)  // 返回地址在RBP上方
      print(return_addr)
      current_rbp = *current_rbp        // 跟随RBP链
  }

方法2：DWARF展开信息（.eh_frame段）
  优点：即使优化掉帧指针也能正确回溯
  缺点：较慢，需要解析DWARF信息
  
  编译器在.eh_frame段中记录了每条指令处的栈帧状态：
  - CFA（Canonical Frame Address）的计算规则
  - 各个寄存器的保存位置
  
  libunwind库就是基于DWARF信息实现栈回溯的
```

### 5.4 崩溃捕获框架设计

生产级崩溃捕获框架（如Google Breakpad/Crashpad）的设计：

```
核心设计原则：
1. 在崩溃进程外处理（用独立的子进程）
   - 崩溃进程的内存可能已损坏
   - 在损坏的进程中做复杂操作不可靠

2. 最小化崩溃处理器中的操作
   - 信号处理函数中只做最基本的通知
   - 复杂的dump生成由外部进程完成

3. 使用minidump而非完整core dump
   - minidump只包含关键信息（线程栈、寄存器、模块列表）
   - 大小通常只有几百KB（vs core dump可能几GB）

架构：
┌──────────────┐     ┌──────────────┐
│  应用进程      │     │  监控进程      │
│              │     │              │
│  信号处理:    │ ──→ │  生成minidump  │
│  通知监控进程  │pipe │  上传到服务器   │
│              │     │  符号化处理     │
└──────────────┘     └──────────────┘
```

```cpp
// 简化的崩溃捕获框架
class CrashHandler {
    int pipe_fds[2]; // 管道，用于通知监控进程
    pid_t monitor_pid;
    
public:
    void install() {
        pipe(pipe_fds);
        
        // fork出监控进程
        monitor_pid = fork();
        if (monitor_pid == 0) {
            // 子进程：监控进程
            close(pipe_fds[1]);
            monitorLoop(pipe_fds[0]);
            _exit(0);
        }
        
        close(pipe_fds[0]);
        
        // 父进程：注册信号处理函数
        setupSignalHandlers();
    }
    
private:
    void onCrash(int signal) {
        // 信号处理函数中只做最小操作
        // 写入信号编号到管道，通知监控进程
        write(pipe_fds[1], &signal, sizeof(signal));
        
        // 等待监控进程完成dump
        // 然后恢复默认信号处理，让进程正常终止
    }
    
    static void monitorLoop(int read_fd) {
        int signal;
        if (read(read_fd, &signal, sizeof(signal)) > 0) {
            // 在独立进程中安全地执行：
            // 1. 生成minidump
            // 2. 收集系统信息
            // 3. 上传崩溃报告
            generateMinidump(getppid());
            uploadCrashReport();
        }
    }
};
```

**总结**：崩溃处理是系统级编程的核心能力。理解从硬件异常到信号处理的完整链路，掌握GDB和核心转储分析技巧，才能在生产环境中快速定位和修复问题。

## 06.DWARF 与 .eh_frame：栈回溯的秘密

前文 5.3 的栈回溯只讲了"帧指针法"。但现代 C++ 程序 90% 都没有帧指针（`-O2` 默认 `-fomit-frame-pointer`），真正让 Backtrace 能工作的是 **DWARF 调试信息 + `.eh_frame` 段**。这一节把这个机制讲透。

### 6.1 为什么需要 `.eh_frame`

异常展开需要能从任意代码位置往上回溯栈，直到找到匹配的 catch。但编译器优化后，"栈帧的结构"对于每个函数的每一段汇编都不一样——入口几条指令还没分配栈、中间段栈大小是 N、某个寄存器被保存到栈上的某个偏移、某个临时值生命周期结束了寄存器被重用……

`.eh_frame` 就是一张**"每个汇编地址对应的栈帧布局表"**：告诉展开程序"当 PC 在这个范围时，CFA（Canonical Frame Address，上一帧栈顶）的计算方式是 `rsp + 16`、`rbp` 保存在 `CFA - 8`、返回地址在 `CFA - 0`"等等。

### 6.2 CIE 和 FDE：编码格式

`.eh_frame` 由两类条目组成：

- **CIE（Common Information Entry）**：公共信息——ABI 约定的初始寄存器规则、指针编码格式、个性函数指针。通常一个 .o 只有一两个 CIE。
- **FDE（Frame Description Entry）**：每个函数（甚至每个"冷热分离"的代码片段）一个 FDE，描述"这段地址范围的栈帧变化"。

FDE 里存的不是完整布局，而是一串**变化指令**：比如"在 PC+4 处，sp 减了 32"、"在 PC+8 处，rbp 保存到了 CFA-8"。展开程序解析时用一个小虚拟机（"DWARF CFI 虚拟机"）依次执行这些指令，重建出每个地址的完整布局。

### 6.3 展开流程的完整分解

展开器（libunwind / libgcc_s 里的 `_Unwind_*` 函数）做这几件事：

1. 从当前 PC 查找 `.eh_frame_hdr`（按地址排序的索引），二分找到对应的 FDE。
2. 解析 FDE 的指令流，构建出当前 PC 的寄存器恢复规则。
3. 按规则读取栈上保存的寄存器，特别是返回地址和上一帧的 CFA。
4. 把寄存器值恢复到"上一帧的视角"（相当于"时光倒流一层"）。
5. 对新的 PC 重复步骤 1-4，直到栈底。

这个过程对性能的影响：**栈回溯每一帧大约 1-10μs**。所以异常展开的成本主要来自这个（而不是匹配 catch 的时间）。

### 6.4 怎么保证 `.eh_frame` 存在

这是一个经常被忽略的工程问题。默认 GCC/Clang 都生成 `.eh_frame`（即使关闭异常也生成，因为它也用于 `backtrace()`）。但以下场景会丢：

- `-fno-asynchronous-unwind-tables`：禁用，二进制变小但无法回溯。
- 链接时 strip（`strip --strip-debug`）不会移除 `.eh_frame`（它在 loadable 段里）。
- 但 `strip --strip-all` 会移除 `.debug_info`（DWARF），只保留 `.eh_frame`——仍能栈回溯，但符号名变成地址。

**生产环境推荐**：保留 `.eh_frame`、strip 掉 `.debug_*`，把完整 DWARF 单独存档。崩溃时，先用 `.eh_frame` 得到地址栈，线下用归档的 DWARF 做 addr2line 解析。Google Breakpad、sentry-native 都是这个模式。

## 07.异步信号安全：信号处理器里的禁忌

第 3.1 节给了信号处理的代码模板，但信号处理器有一个**绝对不能违反**的规则：只能调用**异步信号安全（async-signal-safe）**的函数。违反这个规则是 C++ 里最隐蔽的 UB 来源之一。

### 7.1 为什么信号处理器如此受限

信号是**异步中断**：它可以在程序执行的任意指令之间插入。如果主程序正好在 `malloc` 的内部（持有了 malloc 的全局锁），信号处理器又调用 `malloc`——死锁。如果主程序正在写 `stdout` 缓冲区中间，信号处理器又写 `stdout`——缓冲区损坏。

POSIX 规定了一份**async-signal-safe 函数清单**（`man 7 signal-safety`），只有这些能在信号处理器里调用：

- `write`、`read`、`_exit`（**不是** `exit`）
- `signal`、`sigaction`、`kill`
- `getpid`、`getppid`
- `alarm`、`nanosleep`
- 绝大多数不加锁的系统调用

**绝对禁止**的：

- `printf` / `fprintf` / `std::cout`（持有 stdio 锁）
- `malloc` / `free` / `new` / `delete`（持有 malloc 锁）
- `pthread_mutex_lock`（可能死锁）
- C++ 异常（展开不可重入）
- 几乎所有 C++ 标准库函数

### 7.2 崩溃处理器的正确实现模式

因为不能用 printf、不能 malloc，生产级崩溃处理器的标准做法是：

1. **信号处理器里只做最少的事**：拿到 siginfo、上下文，用 `write(STDERR_FILENO, ...)` 输出固定格式的错误标记（一般是预先准备好的静态字符串）。
2. **栈回溯用 `backtrace()` + `backtrace_symbols_fd()`**：前者是异步信号安全的，后者不是（会 malloc）——所以只用 `backtrace_symbols_fd` 直接写到文件描述符，不做字符串分配。
3. **重型工作交给外部进程**：在信号处理器里 `fork` 出子进程（或 exec 出独立的 crash reporter），让子进程在"安全环境"里做 minidump 生成、网络上传等。这就是 Google Breakpad、crashpad 的核心设计。

### 7.3 常见反模式

```cpp
void handler(int sig) {
    std::cout << "crashed!\n";   // ❌ stdout 可能被损坏
    std::ofstream log("crash");  // ❌ 构造函数可能 malloc
    log << get_stacktrace();     // ❌ 不可重入
    std::exit(1);                // ❌ exit 不是 async-safe，用 _exit
}
```

这段看似合理的代码在大概率情况下能工作——但一旦主程序崩溃时正在持有 malloc 锁，处理器就会死锁，导致进程挂起不退出，看起来像"卡死"而不是"崩溃"。这种偶发现象是生产环境调试最折磨人的问题之一。

### 7.4 `sigaltstack`：为什么栈溢出也要有退路

一个棘手的场景：**栈溢出导致 SIGSEGV**。此时信号处理器会被调用——但处理器也要用栈！如果共用同一个栈，处理器自己也会立即栈溢出，死循环 → 进程被内核强杀。

`sigaltstack` 让你预先分配一块"备用栈"，告诉内核：**信号处理器用这块备用栈，不要动原栈**。注册方式：

```c
stack_t ss;
ss.ss_sp = malloc(SIGSTKSZ);
ss.ss_size = SIGSTKSZ;
ss.ss_flags = 0;
sigaltstack(&ss, NULL);

struct sigaction sa;
sa.sa_flags = SA_ONSTACK;    // 关键：告诉内核用备用栈
sa.sa_sigaction = handler;
sigaction(SIGSEGV, &sa, NULL);
```

有了 sigaltstack，即便原栈爆了，处理器仍能在备用栈上完成"写错误日志、触发 abort"的工作。这是所有生产级崩溃框架的标配。

## 08.进程终止与僵尸：崩溃后的最后一公里

很多人把"进程崩溃"和"进程退出"当成一回事。实际上进程终止是一个**多阶段过程**，理解它能解决"崩溃后为什么没 coredump"、"为什么进程还在进程表里"这些生产问题。

### 8.1 进程终止的完整流程

以 SIGSEGV 为例：

1. **CPU 触发异常 → 内核收到 #PF (page fault)**；
2. 内核查页表，发现是非法访问 → **向进程发 SIGSEGV**；
3. 进程未注册 SIGSEGV 处理器 → **内核执行默认动作：terminate with core dump**；
4. 内核在 `/proc/sys/kernel/core_pattern` 指定路径写 coredump（受 `ulimit -c` 限制）；
5. 调用每个线程的 exit handler、释放 fd 和内存、关闭文件句柄；
6. 把退出码、信号号、rusage 写入 task_struct；
7. 向父进程发 SIGCHLD；
8. 进程进入 **zombie 状态**——task_struct 还在，但资源已释放；
9. 父进程 `wait()`/`waitpid()` → 回收 task_struct，进程彻底消失。

### 8.2 僵尸进程的成因与处理

如果父进程**不 wait**，子进程 task_struct 一直留在系统里——这就是僵尸进程。它不占 CPU、不占内存（已释放），但占一个 PID 和一个 task_struct 槽。极端情况 PID 耗尽（默认 32768），系统无法再创建新进程。

两种标准解决方式：

- **父进程处理 SIGCHLD**：`signal(SIGCHLD, SIG_IGN)` 让内核自动 reap（POSIX 2001 起支持）；或注册 handler 在里面 `waitpid(-1, &status, WNOHANG)` 循环回收。
- **两次 fork**：父 fork 出"中间进程"，中间进程立即 fork 出"工作进程"后自己 exit——工作进程被 init（PID 1）接管，init 会自动 reap。daemon 程序的标准做法。

### 8.3 coredump 没生成的六种常见原因

生产环境遇到"崩溃但没 core 文件"的排查清单：

1. `ulimit -c 0`——用户栈的软限制未开（最常见）。
2. `/proc/sys/kernel/core_pattern` 指向了 `|` 管道（比如 systemd-coredump、abrt），core 被转交给系统服务，要从那里拿。
3. 程序 setuid/setgid——出于安全考虑，默认禁止写 core（需要 `fs.suid_dumpable=1`）。
4. core 文件路径所在文件系统空间不足或无写权限。
5. 程序手动关闭了 core：`setrlimit(RLIMIT_CORE, 0)` 或 `prctl(PR_SET_DUMPABLE, 0)`。
6. 容器里的 rlimit 被 Kubernetes/Docker 默认设为 0。

排查时按顺序验证这 6 点，通常能找到根因。

### 8.4 OOM killer 与崩溃的区别

一种特殊的"崩溃"：**OOM killer**。Linux 在物理内存不足时会选一个进程杀掉（SIGKILL）。被 SIGKILL 杀的进程：

- **没有信号处理机会**（SIGKILL 不可捕获、不可忽略、不可阻塞）；
- **没有 coredump**；
- **没有析构函数调用**——资源直接丢弃。

所以"进程在高内存场景下突然消失，没有任何日志"时，优先查 `dmesg | grep -i "oom"` 或 `/var/log/kern.log`。OOM 的选择算法基于 `/proc/<pid>/oom_score`——可以通过 `oom_score_adj` 告诉内核"优先别杀我"。

## 09.总结与思考

### 9.1 崩溃处理的成熟度阶梯

| 阶段 | 能力 | 典型技术栈 |
|------|------|-----------|
| Level 1 | 能看到崩溃消息 | `stderr` + 默认信号处理 |
| Level 2 | 能生成 coredump | `ulimit -c`、GDB 事后分析 |
| Level 3 | 运行时捕获栈回溯 | `sigaction` + `backtrace` |
| Level 4 | 异步信号安全的最小处理器 | `sigaltstack` + `_exit` + 固定字符串 |
| Level 5 | 生产级崩溃报告 | Breakpad / crashpad 级别（外部进程 minidump + 符号服务器 + 上报系统） |

Level 3 是大部分团队的能力；Level 4-5 需要专门的崩溃基础设施。选择哪个级别取决于你的产品形态：命令行工具 Level 3 够；桌面软件/移动 App 至少 Level 4；大规模服务端应该 Level 5。

### 9.2 与调试技巧一章的互补关系

本章讲的是**"事后"分析崩溃的机制**；调试技巧章讲的是**"事中"介入的调试器**。它们互补：

- 开发/测试阶段 → 调试器（GDB、LLDB）+ Sanitizer 尽早捕获；
- 预发/灰度 → Sanitizer + coredump 双保险；
- 生产环境 → 崩溃捕获框架 + 符号服务器 + 日志。

越往后阶段，介入的侵入性越低，分析的难度越大——这就是为什么"生产环境的崩溃调试"被认为是 C++ 工程师的高级能力。

### 9.3 思考题

1. 程序启动时在多线程环境里递归调用 `std::string` 构造，偶发崩溃在 libc 内部。coredump 里栈回溯看到的是 `malloc_consolidate`。这是什么问题？如何 localize？
2. 你的服务收到 SIGTERM 时想做"优雅退出"——关闭连接、刷新日志、等待任务完成。为什么你的 handler 不能直接写 `logger.info("shutdown")`？正确做法是什么？
3. 一个进程 coredump 总是生成在 `/var/lib/systemd/coredump/`。怎么把它拿出来用 GDB 分析？`coredumpctl` 怎么用？
4. 在 Docker 容器里跑的 C++ 服务崩溃了，但 `docker logs` 里没任何输出，`kubectl exec` 也没 core 文件。你怎么定位？
5. 你要给一个闭源的 C++ SDK 加上崩溃捕获（你不能改它的源代码）。有哪几种侵入方式？各自的权衡是什么？
