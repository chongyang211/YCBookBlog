## 01.前言：一个"只有 30 行代码"的崩溃

### 1.1 真实场景

某天下午，一位同学发来求助：

> "我就写了个遍历数组的函数，跑起来第一行是对的，第二行 `Bus error: 10`，完全看不懂。"

打开他的项目一看，几十个文件、多个类、读文件、继承多态——复杂得足以劝退任何新手。但真正触发崩溃的那段代码，抽离出来其实只有**30 行不到**。

**好的调试，第一步永远是：把问题简化到最小可复现案例（MCVE, Minimal Complete Verifiable Example）**。复杂工程里的 bug 无非三种：

1. 逻辑 bug — 能在简化案例里稳定复现；
2. 交互 bug — 只在组件组合时出现，但仍能用两三个文件复现；
3. 环境 bug — 换台机器就好了（不在本文讨论范围）。

本案例属于第一种。我们把它简化为下面这段代码，作为**全文唯一的主线**，贯穿始终。

### 1.2 最小可复现案例

创建 `crash.cpp`：

```cpp
// crash.cpp —— 这就是本文贯穿始终的案例，一共 22 行
#include <iostream>
#include <string>

struct Employee {
    int         id;
    std::string name;
};

int main() {
    int n = 2;                              // ① 声明有 2 个员工
    Employee** arr = new Employee*[n];      // ② 分配 2 个指针槽

    arr[0] = new Employee{1, "Alice"};      // ③ 只填了第 0 个

    for (int i = 0; i < n; ++i) {           // ④ 遍历 2 个
        std::cout << "id=" << arr[i]->id
                  << ", name=" << arr[i]->name << "\n";
    }
    return 0;
}
```

编译、运行：

```bash
$ g++ crash.cpp -o crash
$ ./crash
id=1, name=Alice
Bus error: 10
```

两个现象非常扎眼：

- **第一行成功打印** — 说明 `arr[0]` 是合法的；
- **第二次访问就崩** — 信号是 `SIGBUS (10)`。

整篇文章，我们要回答三个问题：

1. 这个信号是什么？为什么不是 `Segmentation fault`？
2. 到底是哪一步、哪一行代码出了问题？如何证明？
3. 修复后，如何证明它真的被修好了（而不是"恰巧不崩了"）？

### 1.3 本文能带给你什么

| 层次 | 你将学到 |
|------|----------|
| 信号层 | SIGBUS / SIGSEGV 的本质、`si_code` 的使用、平台差异 |
| 工具层 | lldb / ASan / 编译告警三种排查路径的组合与互补 |
| 方法层 | 最小化复现、建立假设空间、证据链交叉验证、根因分析 |
| 修复层 | 补丁 / 防御 / 重构三层方案 + 论证修复的完整流程 |
| 工程层 | 把一次调试沉淀成团队的 CI 防线 |

读完你会发现：**调试的本质，不是"猜代码哪里错了"，而是"把怀疑空间一步步缩小到唯一答案"**。


## 02.第一层：读懂崩溃信号

看到错误的第一件事，不是打开调试器，而是**读懂这条错误信息本身**。越是看不懂的错误，越是要先弄清它的"字面意思"。

### 2.1 Bus error 到底是什么

`Bus error` 是 shell（或运行时）对 **`SIGBUS`** 信号的文字化显示。具体触发链路是：

```
CPU 检测到异常 ──→ 内核把异常翻译成信号 ──→ 发送 SIGBUS 给进程
                                                    │
                            进程没装信号处理器 ─────┤
                                                    ↓
                              内核执行默认动作：终止 + 写 core
                                                    ↓
                        shell 检测到子进程异常退出：打印 "Bus error: 10"
```

| 维度 | 说明 |
|------|------|
| 信号名 | SIGBUS |
| macOS 编号 | 10（Linux 上是 7） |
| 触发源头 | 硬件异常 / 内核 mmap 子系统 / Mach VM |
| 默认动作 | 终止进程 + 生成 core dump |
| 典型成因 | 野指针、未对齐访问、mmap 文件越界、写只读段 |

### 2.2 SIGBUS vs SIGSEGV 的本质

这两个信号经常混用，但机制截然不同：

```
   ┌───────────────────────────────────────────┐
   │  进程访问虚拟地址 p                        │
   └─────────────────┬─────────────────────────┘
                     ↓
   ┌───────────────────────────────────────────┐
   │  MMU 查页表，把虚拟地址翻译为物理地址        │
   └─────────────────┬─────────────────────────┘
                     │
         ┌───────────┼───────────┐
         ↓           ↓           ↓
   页表项缺失     权限不符      页表存在但
   (unmapped)   (write ro)    物理访问失败
         ↓           ↓           ↓
      SIGSEGV    SIGSEGV       SIGBUS
   (MAPERR)    (ACCERR)      (ADRERR/ADRALN)
```

| 信号 | 根源 | 经典场景 |
|------|------|----------|
| SIGSEGV | MMU 级：页表缺失 / 权限不符 | 空指针解引用、野指针落到未映射区、写 const 段 |
| SIGBUS | 总线级：页存在但物理访问失败 | 未对齐原子操作、mmap 文件被截断后访问尾部、硬件 ECC 错 |

但在 x86 / x86_64 用户态代码里，二者**经常互相冒充**——因为一个"野指针落到某个奇怪地址"可能走进 MMU 也可能走进总线，具体分到哪种，取决于操作系统的异常翻译策略。

### 2.3 "10" 不是错误码，是信号号

一开始很多人会把 `Bus error: 10` 的 `10` 当成 errno。其实它是**信号编号**，`kill -l` 可以验证：

```bash
$ kill -l | tr ' ' '\n' | grep BUS
10) BUS
```

所以 `Bus error: 10` 翻译成人话就是："进程收到 10 号信号（SIGBUS），已被强制终止。"

### 2.4 si_code：信号的副标题

同一个 SIGBUS 其实有多种子类型，内核通过 `siginfo_t.si_code` 告诉你具体原因：

| `si_code` | 含义 | 典型触发 |
|-----------|------|----------|
| `BUS_ADRALN` | 地址未对齐 | 对未对齐地址做原子/SIMD 操作 |
| `BUS_ADRERR` | 物理地址不存在 | 访问被截断 mmap 文件的尾部 |
| `BUS_OBJERR` | 对象特定硬件错 | ECC 错误 |

SIGSEGV 同理：`SEGV_MAPERR`（页不存在）、`SEGV_ACCERR`（权限不足）。

在调试器里可以直接看：

```
(lldb) thread info
  stop reason = EXC_BAD_ACCESS (code=1, address=0x0)
```

这里的 `code=1` 就是 `si_code`。本案例 `address=0x0`——说明我们解引用了一个近似于空的地址。

### 2.5 为什么 macOS 给 SIGBUS，Linux 给 SIGSEGV

同一份 `crash.cpp`：

- 在 Linux 上通常报 `Segmentation fault (core dumped)`；
- 在 macOS 上报 `Bus error: 10`。

**不是你的代码变了，是操作系统对同一个底层异常的翻译策略不同**：

- **Linux**：对几乎所有 MMU 错误都发 SIGSEGV，SIGBUS 只在少数场景（mmap 截断、对齐、ECC）才发；
- **macOS (Darwin/XNU)**：继承自 BSD，在 Mach VM 的某些中间状态下也把 MMU 错翻译成 SIGBUS。

这一段不是闲话——它直接影响排查思路：**"换个平台信号就变了" ≠ "代码没问题"**。在 macOS 上修好了，Linux 上依然可能有别的表现，反之亦然。所以 CI 要跨平台。


## 03.第二层：构建排查假设空间

信号层面看完，现在进入第二层——在**还没打开调试器之前**，先用经验构建一个"假设空间"。这一步非常关键：

**没有假设空间的调试，是在大海里捞针；有假设空间的调试，是在有限清单里逐项排除。**

### 3.1 经验主义排查清单

C++ 崩溃，99% 出自下面 8 种模式之一。按出现频率排序：

| # | 模式 | 典型写法 | 崩溃信号 |
|---|------|----------|----------|
| 1 | 空指针解引用 | `p->f()` 其中 `p == nullptr` | SIGSEGV |
| 2 | 野指针 / 未初始化指针 | `T* p; p->f();` | SIGSEGV / SIGBUS |
| 3 | 数组越界 | `arr[i]` 其中 `i >= size` | SIGSEGV / SIGBUS / 静默错误 |
| 4 | Use-After-Free | `delete p; p->f();` | SIGSEGV |
| 5 | 栈溢出 | 无限递归、巨型栈对象 | SIGSEGV / SIGBUS |
| 6 | Double-Free | `delete p; delete p;` | SIGABRT |
| 7 | 对齐访问错误 | `*(int*)(buf+1) = 1;` | SIGBUS |
| 8 | 写入只读段 | `s[0] = 'H'; // s 是字面量` | SIGSEGV / SIGBUS |

### 3.2 从输出推理程序状态

回到案例。观察到的事实：

```
id=1, name=Alice       ← 成功打印
Bus error: 10          ← 然后崩了
```

从这两行能推出什么？

- **事实 A**：至少有一次 `arr[i]->id` 和 `arr[i]->name` 访问是成功的 ⇒ `arr[0]` 指向了一个合法对象；
- **事实 B**：循环条件 `i < n` 至少让循环进了第二次（`i=1`）；
- **事实 C**：信号是 SIGBUS（address=0x0 或类似）⇒ 第二次访问的 `arr[1]` 不是合法指针。

**这三条事实把假设空间一下缩小到 "第二次循环时 arr[1] 不合法"**。对比 3.1 的清单：

- 排除 #1（空指针）：因为 `arr[0]` 不是空；但 `arr[1]` 可能是；
- 高度怀疑 #2（野指针）：`new T*[n]` 只分配指针槽，不初始化内容；
- 高度怀疑 #3（越界）：但本例 `i < n` 是严格按 `n=2` 来的，不算越界——是 `arr[1]` 本身就没被赋值。

### 3.3 列出五条可能路径

到此我们有了一个**假设清单**，顺序按"成本低的先验证"排列：

| 假设 | 验证方式 | 预计成本 |
|------|----------|----------|
| H1：`arr[1]` 是未初始化的野指针 | lldb 打印 `arr[1]` | 2 分钟 |
| H2：`arr[1]` 是 nullptr，但 macOS 把 null deref 映射为 SIGBUS | lldb 打印地址 | 2 分钟 |
| H3：`new Employee*[2]` 因内存不足返回部分分配 | 极罕见，先搁置 | - |
| H4：编译器优化导致循环越界 | 关 -O0 重试 | 已经做了 |
| H5：`std::string` 内部 SSO 未初始化崩在打印上 | ASan 抓 | 5 分钟 |

**有了清单，调试就不再是"我不知道从哪下手"，而是"先验证 H1，花 2 分钟"**。这就是调试方法论的第一次胜利。


## 04.第三层：搭建"可以调试"的环境

进入工具层之前，花三分钟把"能看见信息"的环境搭起来。很多人调试半天无果，不是工具不行，是**编译选项根本没带符号**。

### 04.1 调试编译：三件套

### 4.1 调试编译：三件套

```bash
g++ -g -O0 -Wall -Wextra crash.cpp -o crash
```

| 选项 | 作用 | 不加的后果 |
|------|------|------------|
| `-g` | 生成 DWARF 调试信息 | lldb 里看到的是裸地址而非行号 |
| `-O0` | 关闭优化 | 变量可能被优化掉，`frame variable` 显示 `<optimized out>` |
| `-Wall -Wextra` | 打开常用告警 | 错过编译期能揪出的一半 bug |

**经验**：日常开发 `-O0 -g`；CI 上额外跑一轮 `-O2 -g` 以防优化引入的 UB 暴露；发布构建才是 `-O2`/`-O3` 不带 `-g` 或把 `-g` 分离成 `.debug` 包。

### 4.2 打开 core dump

一旦崩溃是"偶发"的，能不能抓到 core 直接决定能否修复：

```bash
ulimit -c unlimited          # 当前 shell 打开
./crash                      # 崩溃后生成 core
lldb ./crash -c /cores/core.*  # 事后分析
```

macOS core 默认在 `/cores/`，Linux 用 `cat /proc/sys/kernel/core_pattern` 看当前路径。

### 4.3 改掉 a.out 的坏习惯

很多人习惯 `g++ a.cpp` 不加 `-o`，生成默认 `a.out`。两个坏处：

1. **core dump 文件名变成 `core.a.out.<pid>`**，过几天自己都不认识；
2. **lldb 栈回溯里显示的是 `a.out\`...`**，一眼看过去不知道是哪个项目。

养成习惯：永远 `-o <有意义的名字>`。


## 05.排查方向一：用 lldb 看现场

现在开始真正动手。lldb（macOS）和 gdb（Linux）命令几乎一一对应，以下以 lldb 为例。

### 5.1 run 到崩溃点

```
$ lldb ./crash
(lldb) target create "./crash"
Current executable set to './crash' (arm64).

(lldb) run
id=1, name=Alice
Process 12345 stopped
* thread #1, queue = 'com.apple.main-thread',
  stop reason = EXC_BAD_ACCESS (code=1, address=0x0)
    frame #0: 0x0000000100003a4c crash`main at crash.cpp:15:30
   12      arr[0] = new Employee{1, "Alice"};
   13
   14      for (int i = 0; i < n; ++i) {
-> 15          std::cout << "id=" << arr[i]->id
   16                    << ", name=" << arr[i]->name << "\n";
   17      }
   18      return 0;
```

**四个关键信息**：

1. `stop reason = EXC_BAD_ACCESS` — 底层异常，对应用户态信号 SIGBUS/SIGSEGV；
2. `code=1, address=0x0` — 访问的地址是 `0x0`，即几乎可以断定是 null；
3. `frame #0 ... crash.cpp:15` — 崩溃精确到 15 行；
4. `->` 标记的那一行 — 直接指向 `arr[i]->id` 这个解引用。

### 5.2 bt 看调用栈

```
(lldb) bt
* thread #1, stop reason = EXC_BAD_ACCESS (code=1, address=0x0)
  * frame #0: crash`main at crash.cpp:15:30
    frame #1: libdyld.dylib`start + 1
```

本案例调用栈简单（只有 main），真实项目可能几十层，此时 `bt` 给的就是**事发时的完整代码路径**。

**关键动作**：永远先 `bt`，看崩溃是在"自己的代码里"还是在"库函数里"。

- 崩在库里（如 `std::string` 内部）——99% 是上游传给库的参数就是坏的；
- 崩在自己代码里——直接看那一行。

### 5.3 frame variable 看状态

```
(lldb) frame variable
(int) n = 2
(Employee **) arr = 0x0000600000004010
(int) i = 1
```

这三行已经把假设 H1 坐实了一半：

- `n = 2` → 循环要跑两次；
- `i = 1` → 已经成功跑完 i=0，正在 i=1 崩的；
- `arr` 本身是合法地址（堆上）。

### 5.4 p 表达式验证假设

继续验证"`arr[1]` 到底是什么":

```
(lldb) p arr[0]
(Employee *) $0 = 0x0000600000008020

(lldb) p arr[1]
(Employee *) $1 = 0x0000000000000000    ← null!

(lldb) p arr[1]->id
error: Couldn't apply expression side effects : Couldn't dematerialize a result variable: couldn't read its memory
```

**真相大白**：

- `arr[0]` 是合法指针 → 第一行输出正常；
- `arr[1]` 是 `nullptr` → 对它 `->id` 就是在访问地址 `0x0`，内核翻译成 SIGBUS（macOS）/ SIGSEGV（Linux）。

> 等等，`new Employee*[n]` 的指针槽应该是"未初始化的垃圾值"才对，为什么这里是 `nullptr`？  
> 这里其实存在**实现差异**：
> - 有的 libc++/libstdc++ 在 debug 构建下会把 `new T*[n]` 清零；
> - 有的 allocator 从 fresh page 里拿内存，page 本身就是清零的；
> - 也可能是栈/堆的历史数据恰好是 0。  
> 真实世界里 `arr[1]` 是 "垃圾值 / nullptr / 历史数据" 都可能——**这本身就是野指针最恐怖的地方：不确定性**。

lldb 给出的证据链：**"`arr[1] == 0x0`，对其解引用触发 EXC_BAD_ACCESS"**。但这是**症状**（crash site），真正的**病因**（bug site）在哪里？回到 crash.cpp，是第 11 行——`arr[0]` 被赋值了，`arr[1]` 没有。这就是 **"crash site ≠ bug site"** 的典型案例。


## 06.排查方向二：让 ASan 开口说话

lldb 能告诉你"崩的那一刻是什么"，但对"为什么会这样"需要你自己推理。如果你希望工具直接告诉你"谁分配的、分配了多大、你越界读了多少字节"——那就是 **AddressSanitizer**。

### 6.1 一行编译选项打开 ASan

```bash
g++ -g -O1 -fsanitize=address -fno-omit-frame-pointer crash.cpp -o crash_asan
./crash_asan
```

注意：

- `-fsanitize=address` 必须同时在**编译**和**链接**阶段都传；
- `-O1` 是为了保留一些内联信息但不过度优化；
- `-fno-omit-frame-pointer` 保证 ASan 能可靠回溯栈。

### 6.2 读懂 ASan 报告的四块信息

针对本案例，修改版演示 ASan 的威力——我们让崩溃变成"越界读"而不是 null deref：

```cpp
// crash_v2.cpp —— 用访问 arr[2] 模拟越界
int main() {
    int n = 2;
    Employee** arr = new Employee*[n];
    arr[0] = new Employee{1, "Alice"};
    arr[1] = new Employee{2, "Bob"};
    std::cout << arr[2]->id << "\n";       // 越界
    return 0;
}
```

ASan 输出：

```
==45623==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x60400000dff0
READ of size 8 at 0x60400000dff0 thread T0
    #0 0x10... in main crash_v2.cpp:8
    #1 0x7fff... in start

0x60400000dff0 is located 0 bytes to the right of 16-byte region
[0x60400000dfe0,0x60400000dff0) allocated by thread T0 here:
    #0 0x10... in operator new[](unsigned long)
    #1 0x10... in main crash_v2.cpp:4

SUMMARY: AddressSanitizer: heap-buffer-overflow crash_v2.cpp:8 in main
```

**四块关键信息**：

| 区块 | 告诉你什么 |
|------|------------|
| 错误类型 | `heap-buffer-overflow` —— 不是 UAF、不是栈溢出，是堆越界读 |
| 错误位置 | `crash_v2.cpp:8` —— 精确到代码行 |
| 分配位置 | `crash_v2.cpp:4`，大小 16 字节 —— 你只分配了 2 个指针槽（2×8=16），第 3 个槽不存在 |
| 访问方式 | `READ of size 8` —— 读了 8 字节（即一个指针），落在了合法区右侧 0 字节处 |

**这四块信息一结合，根因就是"你声称要分 3 个，其实只分了 2 个"——ASan 的威力在于：它把"人要思考 30 分钟的推理"直接变成 5 秒钟的报告**。

### 6.3 ASan 的 shadow memory 原理

ASan 不是黑魔法。理解它的原理能帮你判断 **"ASan 为什么没抓到我这个 bug"**。

**核心思想：为每 8 字节真实内存分配 1 字节的"影子内存"**，记录这 8 字节的可访问性。

```
真实内存       shadow 内存
0x60400000dfe0 → shadow[X]     = 0x00 (全 8 字节可访问)
0x60400000dfe8 → shadow[X+1]   = 0x00 (全 8 字节可访问)
0x60400000dff0 → shadow[X+2]   = 0xFA (redzone, 越界标记)
0x60400000dff8 → shadow[X+3]   = 0xFA
```

**每次内存访问插桩**：编译器把 `*p` 改写成"先查 shadow、再真访问"：

```
shadow_addr  = (p >> 3) + SHADOW_OFFSET
shadow_value = *shadow_addr
if (shadow_value != 0 && offset_in_8bytes >= shadow_value)
    report_error(...)
*p   // 正常访问
```

这也解释了几个常被误解的点：

| 现象 | 原理解释 |
|------|----------|
| ASan 慢 2-5 倍 | 每次访存多了 5-10 条指令 + 查 shadow 的缓存抖动 |
| ASan 能检测 UAF | free 时不立刻归还，放入 quarantine，shadow 标记 freed |
| ASan 内存翻倍 | 1/8 shadow + quarantine 最多 256MB + 每块堆的 redzone |
| ASan 漏报语义错误 | 对齐合法的访问它说 OK，不管你意图是什么 |
| ASan 对 mmap 无效 | 不经过 malloc，shadow 默认全 0（可访问）—— 需要手动 poison |

### 6.4 ASan 和 lldb 的互补

| 对比维度 | lldb | ASan |
|----------|------|------|
| 什么时候用 | 崩溃现场、线上 core | 开发期、CI |
| 信息粒度 | 停在那一刻的状态 | 分配位置 + 访问位置 + 错误类型 |
| 能否找到非崩溃 bug | 不能 | 能（只要越界被触发） |
| 启动成本 | 零，随时可连 | 要重编 |
| 运行开销 | 0 | 2-5x 慢、2-3x 内存 |
| 典型场景 | "为什么现在这一刻在这里崩了" | "代码里还有没有其他潜在越界" |

**实战组合**：**开发默认开 ASan，生产崩了用 lldb 分析 core**。


## 07.排查方向三：静态阅读与 review

前两个方向都是"运行时"手段。还有一类方向被严重低估：**光看代码就能看出来**。

### 7.1 编译器告警是最便宜的 Sanitizer

很多野指针/越界 bug，在 **`-Wall -Wextra -Wpedantic`** 下会被直接告警。本案例其实在 `-O2` 时 clang/gcc 就会提示：

```
warning: 'arr[1]' is used uninitialized [-Wuninitialized]
```

但大多数人习惯忽略 warning。**treat warnings as errors（`-Werror`）**，是成本最低、收益最高的调试设置之一。

### 7.2 用 `-Wall -Wextra` 重编一次

```bash
g++ -Wall -Wextra -Wpedantic -Werror crash.cpp -o crash
```

如果编译器在这一步就告警或报错，后面 lldb / ASan 全都省了。**免费的早期防线不要放过**。

### 7.3 unitialized memory 的五种味道

C++ 中"未初始化"有很多种，崩溃的形态也各异。记住这张表，下次看报错时能更快定位：

| 来源 | 代码 | 初值 | 结果 |
|------|------|------|------|
| 局部变量 | `int x; use(x);` | 未定义 | UB，开 `-O2` 后行为不确定 |
| `new T[n]` | `int* p = new int[3];` | 未定义 | 数组内容是垃圾 |
| `new T[n]()` | `int* p = new int[3]();` | 0 | 值初始化 |
| `new T*[n]` | `T** p = new T*[3];` | 未定义 | 本案例的情况 |
| `make_unique<T[]>` | `auto p = std::make_unique<int[]>(3);` | 0 | 安全 |

**本案例的根本改法**：`new Employee*[n]` → `new Employee*[n]()`，所有槽会被 `nullptr`-init，越界会变成**可预测的** null deref 而不是不可预测的野指针。


## 08.三路交叉验证：锁定根因

到这里，三个排查方向都给出了证据。把它们交叉比对，才是"论证"这一步。

### 8.1 三个证据链的交汇

| 证据来源 | 给出的事实 |
|----------|------------|
| lldb | 崩在 `crash.cpp:15`，`arr[1] == 0x0` |
| ASan（越界版）| `arr[i]` 访问了分配区右侧，分配点在第 4 行 |
| 编译告警 | `arr[1] is used uninitialized` |

三条证据**相互印证、无矛盾**，共同指向同一根因：

> **"第 11 行只给 arr[0] 赋了值，第 14 行循环却要访问 arr[0] 和 arr[1]，arr[1] 的值未初始化。"**

调试里最怕的是三条证据**互相矛盾**——那意味着你的心智模型出了问题，或者 bug 是多因复合的。本案例三路一致，确认可以进入修复阶段。

### 8.2 区分"crash site"与"bug site"

> **The crash site is rarely the bug site.**  
> 崩溃的位置，往往不是 bug 本身的位置。

| 术语 | 本案例 |
|------|--------|
| Crash site | 第 15 行 `arr[i]->id`（症状暴露处）|
| Bug site | 第 11 行漏掉了 `arr[1] = ...`（真正错处）|

在真实大项目里，crash site 可能在别人写的某个库函数里，你要从那里**一帧一帧往上回溯**，直到找到自己代码的某个错误假设——那才是 bug site。这就是为什么 `bt` 比 `frame #0` 更重要。

### 8.3 写下一句话根因

调试结束时，给自己写一句**不带技术名词的、能给产品经理看懂的**根因描述：

> "程序说要显示 2 个员工，但实际上只填了 1 个员工的信息进数组，显示第二个员工时就崩了。"

如果你能一句话讲清楚，说明你真的懂了。如果讲不清楚，回到证据链重新看。


## 09.修复方案：从补丁到重构

不同级别的修复对应不同的工程格局。

### 9.1 修复 A：最小改动（一行）

补上漏写的那行：

```cpp
arr[0] = new Employee{1, "Alice"};
arr[1] = new Employee{2, "Bob"};        // ← 补上
```

**适用场景**：紧急 hotfix、代码冻结期、不方便大改。  
**局限**：只修这一处，下一处类似的"漏赋值"还会崩。

### 9.2 修复 B：防御式编程

承认人会犯错，用机制兜底：

```cpp
int n = 2;
Employee** arr = new Employee*[n]();    // ① 所有槽先置 nullptr

arr[0] = new Employee{1, "Alice"};
// 忘了赋 arr[1] 也没关系

for (int i = 0; i < n; ++i) {
    if (!arr[i]) continue;              // ② 防御检查
    std::cout << "id=" << arr[i]->id << "\n";
}
```

**适用场景**：代码多人维护、边界情况难以穷举。  
**局限**：仍然在用裸指针 + 双源真相（`n` 和 `arr` 独立维护），结构本身脆弱。

### 9.3 修复 C：根治式重构

换掉数据结构，用 RAII 容器：

```cpp
#include <memory>
#include <vector>

std::vector<std::unique_ptr<Employee>> emps;

emps.emplace_back(std::make_unique<Employee>(1, "Alice"));
emps.emplace_back(std::make_unique<Employee>(2, "Bob"));

for (const auto& e : emps) {
    std::cout << "id=" << e->id << ", name=" << e->name << "\n";
}
```

**适用场景**：长期维护的核心代码。  
**优点**：

- `emps.size()` **永远等于实际元素数**——"双源真相"消失；
- 没有裸 `new` / `delete`——内存自动管理，析构自动；
- 遍历用 range-based for——没有越界可能；
- `unique_ptr` 保证每个对象唯一所有权，不会 double-free。

### 9.4 三种修复的取舍

| 修复 | 改动量 | 能不能防未来类似 bug | 推荐场景 |
|------|--------|----------------------|----------|
| A：补一行 | 1 行 | 不能 | 紧急发版 |
| B：零初始化 + null 检查 | 2-3 行 | 能防野指针，不防越界 | 过渡期 |
| C：vector + unique_ptr | 重写 5-10 行 | 能防 A/B 所有问题 | 长期代码 |

**资深工程师的选择**：**A + C**——紧急发一个 A 版止血，下一个迭代立刻做 C 版重构。这才是"把一次 bug 变成一次代码质量提升"的做法。


## 10.论证修复：证明而不是"跑一遍"

这是整个流程里最容易被忽略、但最关键的一步。

### 10.1 论证 ≠ 运行 ≠ 解决

很多人修完代码的"验证"是：

```bash
./crash
# 没崩
# 好了！
```

**跑一遍没崩 ≠ 修好了**。只能证明"这一次这条路径没崩"。要真正"论证修复有效"，至少需要三件事：

1. **路径覆盖**：让原来的崩溃路径再走一遍（必要不充分）；
2. **边界覆盖**：让周边路径（边界值）也走一遍；
3. **机制覆盖**：用工具（ASan）证明**不存在同类 bug 的可能**。

### 10.2 边界用例回归表

针对本案例，至少构造下表的用例：

| 用例 | 输入 | 期望 |
|------|------|------|
| n=0 | 空数组 | 不崩，正常输出（0 行）|
| n=1 | 1 个元素 | 正常显示 1 行 |
| n=2 | 2 个元素（原崩溃路径）| 正常显示 2 行 |
| n=100 | 100 个元素 | 正常显示 |
| 部分未填 | 声明 n=3 但只填 2 个 | 修复 B/C 下不崩，修复 A 下崩（暴露 A 的局限）|

最后一行特别重要——它**反向证明了修复 A 的不完备性**，让你明白"为什么要升级到 C"。

### 10.3 ASan 二次验证

```bash
g++ -fsanitize=address -g -O1 crash.cpp -o crash_asan
./crash_asan
```

运行上表所有用例，ASan 不报任何错误 → 基本可以宣称"这个文件里没有堆越界、UAF、内存泄漏"。

### 10.4 压力与 fuzzing

```bash
for n in $(seq 0 1000); do
    echo $n | ./crash_asan > /dev/null || echo "fail at n=$n"
done
```

跑 1000 次都不崩，认为足够稳定。更进一步可以用 libFuzzer / AFL 做模糊测试，用随机输入挖深层的 UB。

### 10.5 写一条可以跑进 CI 的测试

最后一步，把这次的经验沉淀成自动化：

```cpp
// test_crash.cpp
#include <gtest/gtest.h>

TEST(EmployeeList, HandlesPartiallyFilled) {
    auto emps = make_employees({{1, "Alice"}, {2, "Bob"}});
    EXPECT_EQ(emps.size(), 2);
    // 如果回归成旧代码，ASan 会抓
}
```

**这条 test 的价值远大于"跑通一次"**：

- 今后任何人重构这块代码，CI 立刻告警；
- 整条调试经验被封存为可执行的文档；
- 相当于给团队的代码基线加了一道 **免疫接种**。


## 11.泛化：Bus error 的其他场景

本案例的 SIGBUS 是"野指针 → null deref → macOS 翻译成 SIGBUS"。实际工作中 SIGBUS 还有几种"花式触发法"，提前熟悉，免得下次遇到时摸不着头脑。

### 11.1 mmap 文件被截断

```cpp
int fd = open("data.bin", O_RDONLY);           // 假设文件只有 100 字节
char* p = (char*)mmap(nullptr, 4096,            // 但 mmap 了 4KB
                      PROT_READ, MAP_PRIVATE, fd, 0);
char c = p[200];                                // SIGBUS (BUS_ADRERR)
```

**为什么？** mmap 的页面必须能从文件对应位置读到；读超过文件实际长度那部分时，内核发 SIGBUS。

### 11.2 栈溢出

```cpp
void f() { char buf[16 * 1024 * 1024]; f(); }    // 每层 16MB 栈
```

栈指针跑出栈 guard page，触发 SIGSEGV/SIGBUS。

### 11.3 对齐访问错误

```cpp
char buffer[16];
int* p = reinterpret_cast<int*>(buffer + 1);     // 偏移 1，非 4 对齐
__atomic_store_n(p, 1, __ATOMIC_SEQ_CST);         // ARM 上 SIGBUS
```

x86/x64 对未对齐"容忍"（性能降但不崩），ARM/RISC-V 某些模式下直接发 SIGBUS（`BUS_ADRALN`）。

### 11.4 写入只读段

```cpp
char* s = "hello";     // 字面量在 .rodata
s[0] = 'H';             // SIGSEGV (Linux) / SIGBUS (可能)
```

开 `-Wwrite-strings` 编译期就能告警。


## 12.方法论：把本案例抽象成通用流程

最后一层——把这次调试的动作抽象成**可复用的流程图**。

### 12.1 崩溃排查的五步闭环

```
  ┌─────────────────────────────────────────┐
  │ 1. 最小复现 (MCVE)                        │
  │    把 bug 剥离到 < 50 行代码              │
  └──────────────────┬──────────────────────┘
                     ↓
  ┌─────────────────────────────────────────┐
  │ 2. 建立假设空间                           │
  │    列出可能 3-5 种原因，按成本排序         │
  └──────────────────┬──────────────────────┘
                     ↓
  ┌─────────────────────────────────────────┐
  │ 3. 多路径证据                             │
  │    lldb + ASan + 编译告警，三角验证        │
  └──────────────────┬──────────────────────┘
                     ↓
  ┌─────────────────────────────────────────┐
  │ 4. 根因总结                               │
  │    写一句话的 bug 描述                     │
  └──────────────────┬──────────────────────┘
                     ↓
  ┌─────────────────────────────────────────┐
  │ 5. 修复 + 论证 + 沉淀                     │
  │    A/B/C 三级修复 + 回归 + CI 用例        │
  └─────────────────────────────────────────┘
```

### 12.2 三层防御模型

```
┌────────────────────────────────────────────┐
│ 编译期：-Wall -Wextra -Werror -Wpedantic   │
│         clang-tidy、cppcheck               │
├────────────────────────────────────────────┤
│ 运行期：-fsanitize=address,undefined       │
│         valgrind、lldb/gdb                 │
├────────────────────────────────────────────┤
│ 回归期：单元测试、CI + ASan、Fuzz          │
└────────────────────────────────────────────┘
```

任一层拦住，bug 就不会出现在用户那里。这三层都是**成本固定、收益指数级增长**的投资。

### 12.3 排查中的心法

- **先读信号，再打工具**：连错误信息都没看懂就开调试器，等于在黑屋子里打手电；
- **永远有假设空间**：没有假设的调试是蒙，有假设才能用证据排除；
- **多路径交叉验证**：单一证据不可信，三条一致的证据才叫根因；
- **crash site ≠ bug site**：被动看崩的位置只是起点；
- **验证要比修复更严格**：修一处容易，证明"这一类都没了"难；
- **把每次调试沉淀成 CI**：否则你每次都在重复同一类错误。


## 13.总结与思考

回头看这 22 行案例，我们从一个简单的 `Bus error: 10` 走过了：

| 层次 | 内容 |
|------|------|
| 信号层 | SIGBUS vs SIGSEGV、si_code、平台差异 |
| 假设层 | 8 种常见崩溃模式、假设空间排序 |
| 工具层 | lldb 看现场、ASan 抓根因、编译器告警兜底 |
| 论证层 | 三路证据交叉、crash site vs bug site |
| 修复层 | 补丁 / 防御 / 重构三层方案 |
| 验证层 | 边界表、ASan 二次验证、压测、CI 用例 |
| 方法层 | 五步闭环、三层防御、心法六条 |

**真正的调试能力不是"记住多少命令"，而是"能不能把一个看似无从下手的崩溃，用系统化的流程逼到唯一真相"**。这篇文章里的案例只有 22 行，但你掌握的流程可以处理 22 万行的项目。

留给你的几个思考题：

1. 如果本案例在 Linux 上崩成 SIGSEGV 而不是 SIGBUS，你的排查路径会变吗？哪些步骤会变，哪些不变？
2. 假如崩溃是 10% 概率偶发的，前述哪些工具仍然适用？哪些失效？怎么补？
3. 如果把 `new Employee*[n]` 改成 `new Employee*[n]()`，你能用 ASan 抓到同样的 bug 吗？为什么？
4. 假设你是 CI 负责人，要把本案例的教训**系统化**嵌入团队流程，你会加哪些检查？
5. 有没有一类崩溃是本文方法论解决不了的？（提示：数据竞争、内存损坏在别处发生而在当前线程暴露）

> 调试不是寻找答案，而是不断缩小不确定性。  
> 信号是第一手证据，工具是放大镜，方法论是地图，经验是直觉。四者缺一不可。
