## 1. 案例引入

### 1.1 一段反常代码

以下代码是一段真实的 Android 生产事故复盘。开发同学信誓旦旦："`userName` 声明成 `String` 不是 `String?`，Kotlin 保证不为 null，怎么可能 NPE？"结果，线上崩溃率飙升 3%。

```kotlin
// UserRepo.kt —— 从 Java 侧的老 RPC 客户端拉数据
class UserRepo(private val rpc: JavaRpcClient) {

    fun greet(uid: Long): String {
        val userName: String = rpc.getUserName(uid)   // 声明成非空 String
        return "Hello, ${userName.uppercase()}"       // 崩在这里，为什么？
    }
}
```

```java
// JavaRpcClient.java —— 老代码，没打 @Nullable/@NotNull 注解
public class JavaRpcClient {
    public String getUserName(long uid) {
        // 用户不存在时返回 null
        return db.query(uid);
    }
}
```

*[骨架占位：真实堆栈信息、事故上报量、发生条件]*

### 1.2 顺藤摸到根因

**表象**：Kotlin 类型系统宣称"非空类型永远不为 null"，但案例里 `String` 变量装进了 `null`。这不是矛盾吗？

*[骨架占位：反编译 `greet` 函数，展示 Kotlin 编译器**没有**在赋值处插入空检查]*

### 1.3 我们要回答什么

看到这里，我们至少积累了 6 个疑问：

1. **`T` 与 `T?` 在 JVM 字节码里究竟是同一个类，还是两个类？**
2. **`Nothing` 是什么类型？为什么它是所有类型的子类型？**
3. **`?.` `?:` `!!` 三个运算符编译后各自变成什么字节码？**
4. **平台类型 `T!` 为什么能同时表现得像 `T` 和 `T?`？**
5. **智能转换（smart cast）什么时候会"失灵"？**
6. **空检查在热路径上究竟带来多大开销？**

这些疑问，我们在第 3~9 章逐一取证，在第 10 章统一作答。

## 2. 架构概览

### 2.1 三层类型体系

Kotlin 类型系统在**空安全维度**上分三层：

```
┌────────────────────────────────────────────────────┐
│  可空引用类型         String? / User? / Int? / ...  │
├────────────────────────────────────────────────────┤
│  非空引用类型         String  / User  / Int  / ...  │
├────────────────────────────────────────────────────┤
│  平台类型（隐式）      String! / User! / ...          │  ← 来自 Java
└────────────────────────────────────────────────────┘
```

*[骨架占位：三层结构大图 + 每层的编译期语义 + 运行期表征]*

### 2.2 为什么这么切

**疑惑**：为什么不像 Rust 那样用 `Option<T>` 枚举，或像 Java 那样用 `Optional<T>` 包装类？

**论证**：
1. Rust 无历史包袱，直接用代数数据类型很干净——但每次访问要 `match`，语法笨重
2. Java `Optional` 是包装类——每次都多一次对象分配，性能不可接受
3. Kotlin 选择**类型系统内建**：`T?` 与 `T` 在**类型标记**上有区别，在**运行时字节码**上完全相同——**零开销**
4. 代价：需要引入"平台类型"来做 Java 互操作的转换缓冲

**结论**：Kotlin 空安全是**编译期机制**，不是运行期机制——这是它零开销的秘密。

## 3. 类型系统数学

### 3.1 T是T可空子类

**疑惑**：`String` 与 `String?` 是什么关系？

**论证**：

*[骨架占位：从子类型规则推导；能否从 `String` 隐式转为 `String?`；反之呢]*

**结论**：`T <: T?`，即"非空类型是可空类型的子类型"。因此 `String` 可以赋值给 `String?`，反之则被编译器拒绝。

### 3.2 Nothing是万能子类

`Nothing` 是**无实例**类型。`throw` 和 `TODO()` 都返回 `Nothing`。

*[骨架占位：类型系统里"没有实例的类型"如何做到"所有类型的子类型"]*

```kotlin
fun fail(): Nothing = throw IllegalStateException()

val x: Int = fail()      // OK，因为 Nothing <: Int
val s: String = fail()   // OK，因为 Nothing <: String
```

## 4. 编译期NPE消除

### 4.1 安全调用字节码

一段简单的 Kotlin：
```kotlin
fun length(s: String?): Int? = s?.length
```

**疑惑**：`?.` 编译后到底是什么？

**论证**：`javap -p -v` 输出（关键片段）：

```
public static final java.lang.Integer length(java.lang.String);
   0: aload_0
   1: ifnull   14         // 如果 s == null 跳转到 14
   4: aload_0
   5: invokevirtual  #12 // Method java/lang/String.length:()I
   8: invokestatic   #18 // Method Integer.valueOf:(I)Integer
  11: goto     15
  14: aconst_null         // 返回 null
  15: areturn
```

*[骨架占位：逐条汇编讲解，重点关注 IFNULL 与装箱]*

**结论**：`?.` 编译为 `IFNULL` 分支 + 装箱，是**每次调用两条指令**的开销。

### 4.2 Elvis兜底展开

*[骨架占位：`s ?: default` 编译为 `IFNULL` + 分支，等价于三元 `s == null ? default : s`]*

### 4.3 双感叹号真相

**疑惑**：`s!!` 真的只是"我保证非空"吗？

**论证**：
```
   0: aload_0
   1: dup
   2: ifnonnull  14
   5: invokestatic #7   // Intrinsics.throwNpe:()V
   ...
```

**结论**：`!!` 编译为**显式空检查 + `Intrinsics.throwNpe()` 调用**，一旦为 null 就抛出 `KotlinNullPointerException`。它不是"忽略检查"，而是"如果为空就崩"。

## 5. 契约与智能转换

### 5.1 smart_cast触发条件

```kotlin
fun printLength(s: String?) {
    if (s != null) {
        println(s.length)      // 这里 s 被智能转为 String
    }
}
```

**疑惑**：编译器凭什么信任 `if (s != null)` 之后的 `s` 一定非空？

**论证**：
1. Kotlin 编译器做**流敏感分析**（flow-sensitive analysis）
2. 只有当变量在检查点到使用点之间**不可能被并发修改**时，才允许智能转换
3. 因此局部 `val`、局部 `var`（未被 Lambda 捕获修改）可以，成员 `var`、`open val` 不行

**结论**：智能转换是**编译期语法糖**——本质上是"编译器帮你把 `s.length` 改写成 `(s as String).length`"。

### 5.2 contract关键字

`kotlin.contracts` 让**普通函数**也能引导编译器做智能转换：

```kotlin
@OptIn(ExperimentalContracts::class)
fun String?.isNullOrEmptyExt(): Boolean {
    contract { returns(false) implies (this@isNullOrEmptyExt != null) }
    return this == null || this.isEmpty()
}
```

*[骨架占位：契约的四种基本形式：`returns`、`returnsNotNull`、`callsInPlace`、`implies`]*

### 5.3 智能转换的边界

*[骨架占位：3 种失效场景 + 每种给出编译器错误信息]*

### 5.4 var与open失效

```kotlin
class C {
    var s: String? = null
    fun f() {
        if (s != null) {
            println(s.length)     // ❌ 报错
        }
    }
}
```

**原因**：`s` 是成员 `var`，可能被其它线程改成 null。

**解法**：`val local = s; if (local != null) println(local.length)`。

## 6. 平台类型内幕

### 6.1 T叹号双面性

**平台类型 `T!` 的语义**："既可能非空也可能可空，编译器不检查"——把责任推给了程序员。

*[骨架占位：Kotlin IDE 在悬浮窗里显示 `String!`，但代码里无法写出 `String!` 字面]*

### 6.2 注解影响推断

Java 侧加注解后：

| Java 声明 | Kotlin 看到的类型 |
|---|---|
| `String getX()` | `String!`（平台类型） |
| `@NotNull String getX()` | `String`（非空） |
| `@Nullable String getX()` | `String?`（可空） |

**Kotlin 编译器识别的空注解流派**：JetBrains、Android Support、JSR-305、FindBugs、Lombok…

*[骨架占位：完整识别列表 + 优先级]*

### 6.3 Nullable注解生态

*[骨架占位：Java 侧团队协议：Interface 一律标注解；Data class 转换层做空校验]*

### 6.4 平台类型放行代价

回到 1.1 节的案例——Java `getUserName` 没打注解，Kotlin 看到的是 `String!`，赋值给 `String` 时编译器**不检查**，运行时 null 长驱直入。

**结论**：**平台类型是空安全体系的软肋，也是 Java 生态迁移的必要妥协**。

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到 1.1 节的 6 个疑问：

1. **`T` 与 `T?` 在字节码里是同一个类** —— 都是 `java.lang.String`，区别只在 `@NotNull/@Nullable` 注解与调用点的空检查。
2. **`Nothing` 是所有类型的子类型** —— 通过类型系统数学证明，用来让 `throw` 表达式能出现在任何位置。
3. **`?.` 编译为 `IFNULL` + 装箱；`?:` 编译为 `IFNULL` + 分支；`!!` 编译为 `IFNULL` + `Intrinsics.throwNpe()`**。
4. **平台类型 `T!` 是编译器给出的"两可"标注** —— 既能当 `T` 用也能当 `T?` 用，编译器不做静态检查，责任交给程序员。
5. **智能转换在成员 `var`、`open val`、跨模块属性时失效** —— 因为并发修改的可能性存在。
6. **空检查开销约每次 1~2 条 JVM 指令**，JIT 通常能消除；`Int?` 的装箱代价才是真正的性能杀手。

**案例的根因**：`rpc.getUserName()` 返回 `String!`，Kotlin 编译器"放行"了这个赋值，Java 侧的 null 在 `uppercase()` 处爆发。

**修复**：给 Java 侧加 `@Nullable`，让 Kotlin 侧看到 `String?`，强制处理空情况。

### 10.2 一个可空变量一生

```
声明 val s: String? = null
  ↓
存入本地变量表 slot 0
  ↓
使用 s?.length
  ↓ 
编译为 IFNULL + INVOKEVIRTUAL + INVOKESTATIC(装箱)
  ↓
JIT 阶段：C2 尝试消除空检查
  ↓
运行期：如果 s == null 直接跳转返回 null
```

*[骨架占位：全生命周期时序图]*

### 10.3 设计哲学回扣

- **编译期前移**：把运行期 NPE 挪到编译期发现，是最经济的检查
- **零开销抽象**：`T?` 在字节码上与 `T` 完全一样，只有调用点做空检查
- **软兼容平台边界**：为了 Java 生态引入 `T!` 平台类型——原则性妥协
- **智能转换比强制标注更友好**：编译器帮你做能做的检查，剩下的靠契约

### 10.4 空安全速查表

| 场景 | 推荐写法 | 反例 |
|---|---|---|
| 可空对象方法调用 | `s?.length` | `if (s != null) s.length else null` |
| 可空对象兜底 | `s ?: "default"` | `if (s == null) "default" else s` |
| 断言非空 | `requireNotNull(s)` | `s!!` |
| 平台类型 | 显式标注 `String?` 或 `String` | 依赖推断的 `String!` |
| 深层链 | `a?.b?.c?.let { ... }` | 一堆 `!!` |
