## 1. 案例引入

### 1.1 一段反常代码

以下代码是一段"看起来完全正确"的缓存实现，但生产环境里出现了**缓存穿透**——命中率从预期的 95% 掉到 30%：

```kotlin
// UserCache.kt
data class User(
    val id: Long,
    val name: String,
    val tags: MutableList<String>        // ⚠ 注意：MutableList
)

class UserCache {
    private val cache = mutableMapOf<User, String>()
    
    fun put(user: User, data: String) { cache[user] = data }
    fun get(user: User): String? = cache[user]
}

fun main() {
    val u = User(1, "K", mutableListOf("a", "b"))
    val cache = UserCache()
    cache.put(u, "profile")
    
    u.tags.add("c")             // 事后修改了 tags
    println(cache.get(u))       // 输出 null ！！！
}
```

*[骨架占位：真实事故上报量、影响面、DAU 损失]*

### 1.2 顺藤摸到根因

**表象**：同一个 `u` 对象放进去又取出来，居然取不到？

*[骨架占位：反编译 `data class User` 的 `hashCode()`，发现它遍历所有字段做 hash——包括那个 `MutableList`；`tags` 一变，`hashCode` 就变，HashMap 定位到了别的 bucket]*

### 1.3 我们要回答什么

看到这里，我们至少积累了 6 个疑问：

1. **`data` 关键字究竟触发编译器生成了哪些方法？**
2. **`equals` 的生成实现如何逐字段比较？是否深比较？**
3. **`copy` 是深拷贝还是浅拷贝？字节码上如何实现？**
4. **`componentN` 是什么？为什么支持 `val (a, b) = point`？**
5. **为什么 `data class` 继承 `data class` 是坏味道？**
6. **`data class` 与 Java 16 `Record` 有什么本质差别？**

## 2. 架构概览

### 2.1 五项自动生成

`data` 关键字触发编译器生成 5 类成员：

```
┌────────────────────────────────────────────┐
│ data class User(val id: Long, val name: S) │
└────────────────────────────────────────────┘
                      ↓ 编译器生成
┌────────────────────────────────────────────┐
│ + equals(Any?): Boolean                    │
│ + hashCode(): Int                          │
│ + toString(): String                       │
│ + copy(id: Long, name: String): User       │
│ + component1(): Long / component2(): S     │
└────────────────────────────────────────────┘
```

### 2.2 为什么这么切

**疑惑**：为什么不让开发者自己写这 5 个方法？

**论证**：
1. 手写这 5 个方法冗余、易错，Java 项目里每个 POJO 都要抄一遍
2. Lombok 用注解处理器解决，但依赖第三方且 IDE 支持不一致
3. Kotlin 干脆在**语言层**内建——`data` 一词即完成
4. 生成的代码遵循固定模板，行为可预测，字节码可稳定

**结论**：`data` 是 Kotlin 对"POJO 样板代码"的语言级消灭。

## 3. equals契约详解

### 3.1 五大契约条款

任何 `equals` 都必须满足（继承自 Java `Object`）：

1. **自反性**：`x.equals(x) == true`
2. **对称性**：`x.equals(y) == y.equals(x)`
3. **传递性**：`x.equals(y) && y.equals(z)` → `x.equals(z)`
4. **一致性**：多次调用结果相同（不涉及可变状态时）
5. **null 处理**：`x.equals(null) == false`

### 3.2 生成代码逐行

`data class User(val id: Long, val name: String)` 的 `equals` 反编译（简化）：

```java
public boolean equals(Object other) {
    if (this == other) return true;
    if (other == null || getClass() != other.getClass()) return false;
    User u = (User) other;
    return id == u.id && Intrinsics.areEqual(name, u.name);
}
```

**关键点**：
- 用 `getClass()` 严格类型匹配（不是 `instanceof`）——这决定了继承的痛点
- 引用类型用 `Intrinsics.areEqual` 处理 null

*[骨架占位：`Intrinsics.areEqual` 源码；为什么用它而不是 `Objects.equals`]*

### 3.3 与Java比较

*[骨架占位：Java IDE 生成的 `equals` vs Kotlin 生成的 `equals` 字节码差别]*

### 3.4 字段类型影响

| 字段类型 | equals 表达式 |
|---|---|
| `Int/Long/Boolean/Char` | `==` 直接比 |
| `Double/Float` | `Double.compare` |
| 引用类型 | `Intrinsics.areEqual` |
| 数组 | `Arrays.equals`（Kotlin 1.5+） |

## 4. hashCode实现细节

### 4.1 生成算法逐行

```java
public int hashCode() {
    int result = Long.hashCode(id);
    result = 31 * result + name.hashCode();
    return result;
}
```

**算法**：31 进制多项式，`h = 31·h + field.hashCode()`。这与 Java `String.hashCode()` 一致。

*[骨架占位：31 而非 32 的历史理由；数据分布均匀性验证]*

### 4.2 与Objects工具类

*[骨架占位：Kotlin 生成的代码 vs `java.util.Objects.hash(...)` 的区别（后者会装箱）]*

### 4.3 可变字段风险

**回到 1.1 案例**：`MutableList` 参与 `hashCode` 计算——列表元素一变，`hashCode` 就变，HashMap 找不到 bucket。

*[骨架占位：`Guava Immutable*` 保护方案；`Collections.unmodifiableList` 的局限；kotlinx.immutable]*

### 4.4 大字段性能坑

**结论**：`data class` 里出现大字段（长字符串、大数组）会让 `hashCode` 变昂贵。建议：
1. 只把"识别字段"标 `data`，其它字段用普通类
2. 或缓存 `hashCode`（`by lazy`）

## 5. copy浅拷贝本质

### 5.1 copy字节码剖析

```kotlin
val u = User(1, "K")
val u2 = u.copy(name = "K2")
```

反编译 `copy`：
```java
public final User copy(long id, String name) {
    return new User(id, name);      // 直接调主构造
}
```

**关键**：`copy` 就是"用同样类型创建新实例"——对**引用类型字段**只是**引用复制**，没有深拷贝。

### 5.2 命名参数配合

```kotlin
data class User(val id: Long, val name: String, val age: Int = 0)

val u = User(1, "K", 20)
val u2 = u.copy(name = "K2")      // 只改 name，其它继承
```

编译器为 `copy` 生成的默认参数就是"原对象的字段值"——本质是 `copy(id: Long = this.id, ...)`。

### 5.3 可变字段陷阱

```kotlin
data class Order(val id: Long, val items: MutableList<Item>)

val o1 = Order(1, mutableListOf(Item(1)))
val o2 = o1.copy()
o2.items.add(Item(2))
println(o1.items.size)     // 2 —— o1 也被改了！
```

### 5.4 深拷贝的正解

*[骨架占位：三种方案对比]*
1. **不用可变集合**：`data class Order(val id: Long, val items: List<Item>)`
2. **手写 deepCopy 扩展函数**
3. **借助 kotlinx.serialization 序列化再反序列化**

## 6. 解构声明底层

### 6.1 componentN约定

`data class` 的每个主构造属性都会生成 `componentN` 函数，`N` 从 1 开始按声明顺序：

```kotlin
data class Point(val x: Int, val y: Int)

val p = Point(3, 5)
val (a, b) = p
// 等价于：
// val a = p.component1()
// val b = p.component2()
```

### 6.2 解构字节码

*[骨架占位：`val (a, b) = p` 反编译，展示 `component1/2` 的实际调用]*

### 6.3 集合结合解构

```kotlin
for ((k, v) in map) { }             // Map.Entry 的 componentN
listOf("a" to 1).forEach { (k, v) -> }
```

*[骨架占位：`Pair` / `Triple` / `Map.Entry` 的 componentN 定义]*

### 6.4 非data类解构

普通类也可以支持解构——**手动定义** `component1/2` 函数：

```kotlin
class C(val a: Int, val b: Int) {
    operator fun component1() = a
    operator fun component2() = b
}
```

## 7. 数据类与继承

### 7.1 open_data被禁止

Kotlin **禁止 `open data class`**（更准确地说：从 Kotlin 1.1 起 data class 可以继承普通类，但仍然是 final 的）：

```kotlin
open data class A(val x: Int)    // ⚠ 部分版本禁止，或警告
```

### 7.2 继承破坏对称性

假设允许 `data class B(val x: Int, val y: Int) : A(x)`：

```kotlin
val a = A(1)
val b = B(1, 2)
a.equals(b)     // ? A 的 equals 只比 x，返回 true
b.equals(a)     // ? B 的 equals 比 x 和 y，返回 false
```

**对称性被打破**！这就是"为什么 data class 不允许开放继承"的类型系统答案。

*[骨架占位：Bloch《Effective Java》第 10 条的对应讨论]*

### 7.3 sealed组合方案

正确做法：用 `sealed class` 做**代数数据类型**的骨架，`data class` 做**每个变体**：

```kotlin
sealed class Result<out T>
data class Success<T>(val data: T) : Result<T>()
data class Failure(val error: Throwable) : Result<Nothing>()
```

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到 1.1 节的 6 个疑问：

1. **`data` 生成的方法**：`equals` / `hashCode` / `toString` / `copy` / `componentN`——共 5 类。
2. **`equals` 逐字段浅比较**——对引用类型调用 `Intrinsics.areEqual` 委托给字段的 `equals`。
3. **`copy` 是浅拷贝**——直接把字段的引用值传给新构造的对象。
4. **`componentN` 让解构成为可能**——按主构造声明顺序生成 `component1/2/...`。
5. **`data class` 继承破坏 `equals` 对称性**——语言层禁止。
6. **与 Record 的差别**：Record 用 invokedynamic，Kotlin data class 生成传统方法体；Record 无 `copy`；访问器命名不同。

**案例根因**：`MutableList` 字段参与了 `hashCode` 计算——修改字段后 hash 变化，HashMap 找不到旧 key。

**修复方案**：
1. 用只读 `List` 代替 `MutableList`；或
2. 用不参与 `equals/hashCode` 的字段：把 `tags` 从主构造挪到类体：
```kotlin
data class User(val id: Long, val name: String) {
    var tags: MutableList<String> = mutableListOf()   // 不参与 equals/hashCode
}
```

### 10.2 一个data类一生

```
声明 data class User(val id: Long, val name: String)
  ↓
kotlinc 编译时展开：
  - 主构造字段
  - equals/hashCode/toString
  - copy
  - component1/component2
  ↓
javap 输出：字段 + 方法列表
  ↓
运行期：put/get 到 HashMap 时，hashCode 决定 bucket
  ↓
若字段可变：hashCode 变化 → HashMap 混乱
```

*[骨架占位：完整时序图]*

### 10.3 设计哲学回扣

- **语言层消灭 boilerplate**：`data` 一词抵得上 30 行手写代码
- **不可变即安全**：`data class` 主构造用 `val` 是黄金实践
- **约定优于配置**：`componentN` / `equals` 都是编译器约定，不用手动开关
- **继承是限制而非能力**：`data class` 默认 final 是 Bloch 原则的落地

### 10.4 数据类速查表

| 特性 | 触发条件 | 生成物 |
|---|---|---|
| `equals` | data 修饰 | 逐字段浅比较 |
| `hashCode` | data 修饰 | 31 进制多项式 |
| `toString` | data 修饰 | `User(id=1, name=K)` |
| `copy` | data 修饰 | 主构造字段全参数 |
| `componentN` | data 修饰 | 按主构造顺序 |
| 只对主构造字段生效 | data 修饰 | 类体字段不参与生成 |
