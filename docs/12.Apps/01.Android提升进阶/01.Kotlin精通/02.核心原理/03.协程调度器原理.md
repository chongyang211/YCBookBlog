## 1. 案例引入

### 1.1 一段反常代码

以下是一段生产事故——某 Android App 上线后偶发"点了保存按钮什么都没发生"，用户投诉但无法复现：

```kotlin
// SettingsViewModel.kt
class SettingsViewModel : ViewModel() {

    fun save(config: Config) {
        viewModelScope.launch(Dispatchers.IO) {         // ① 切到 IO
            val ok = repo.save(config)                   // ② suspend 调用
            withContext(Dispatchers.Main) {              // ③ 切回主线程
                if (ok) view.showToast("保存成功")
                else throw IllegalStateException("保存失败")   // ④ 这里抛异常
            }
        }
    }
}
```

**症状**：`throw` 后 App **既不崩溃、也不弹 Toast**——异常仿佛消失了。日志里也没有堆栈。

*[骨架占位：真实堆栈（其实是错过的）、事故上报量、Firebase 未捕获率]*

### 1.2 顺藤摸到根因

**表象**：为什么 `throw` 出的异常没有传播出来？

*[骨架占位：反编译整段 `launch` 内容，展示状态机的异常传播路径；对比加 `CoroutineExceptionHandler` 前后的行为]*

### 1.3 我们要回答什么

看到这里，我们至少积累了 7 个疑问：

1. **`suspend` 关键字在字节码上到底做了什么？**
2. **一段挂起函数在字节码里如何"暂停并恢复"？**
3. **`Dispatchers.IO` 与 `Dispatchers.Default` 各自的线程池长什么样？**
4. **`viewModelScope.launch` 里抛出的异常去哪里了？**
5. **`Job` 与 `SupervisorJob` 差在哪？**
6. **协程真的比线程"轻"吗？轻多少？**
7. **`CancellationException` 为什么被特殊处理？**

## 2. 架构概览

### 2.1 协程五层结构

```
┌──────────────────────────────────────────────────────┐
│              CoroutineContext（上下文）                │
│  ┌──────┐ ┌──────────┐ ┌──────────────┐ ┌─────────┐  │
│  │ Job  │ │Dispatcher│ │ExcHandler    │ │Elements │  │
│  └──────┘ └──────────┘ └──────────────┘ └─────────┘  │
└──────────────────────────────────────────────────────┘
                          ↑
                     结构化并发
                          ↓
┌──────────────────────────────────────────────────────┐
│              CoroutineScope（作用域）                  │
└──────────────────────────────────────────────────────┘
                          ↓
              launch / async / withContext
                          ↓
              suspend fun 状态机执行
```

*[骨架占位：五层大图 + 每层核心接口]*

### 2.2 为什么这么切

**疑惑**：为什么把 `Job`、`Dispatcher`、`ExceptionHandler` 全塞进一个 `CoroutineContext` Map？

**论证**：
1. 协程执行时需要多种正交能力：调度、生命周期、异常处理、名字…
2. 用一个通用的 `Element` 接口 + `Map` 抽象，支持"任意扩展"
3. 上下文可以通过 `+` 组合，通过 `[]` 取值，语法自然
4. 传递上下文只需传一个引用，避免多参数臃肿

**结论**：`CoroutineContext` 是"能力集合的开放式携带"设计——**每个协程都是一颗上下文树**。

## 3. 挂起函数本质

### 3.1 suspend编译签名

```kotlin
suspend fun fetchUser(id: Long): User { ... }
```

编译后 Java 侧签名：
```java
public static Object fetchUser(long id, Continuation<? super User> $completion);
```

**变化**：
- 参数末尾加了一个 `Continuation<T>`
- 返回类型变成 `Object`（要么是 `User`，要么是特殊哨兵 `COROUTINE_SUSPENDED`）

*[骨架占位：这就是 CPS（Continuation-Passing Style）变换的语言级实现]*

### 3.2 CPS变换机理

```
原函数：           A → B → C → return R
CPS 变换后：       A(cont) → B(cont') → C(cont'') → cont.resumeWith(R)
```

每一个"下一步"都作为参数传给当前步。

*[骨架占位：CPS 与传统 callback hell 的区别；编译器如何自动做 CPS]*

### 3.3 状态机反汇编

```kotlin
suspend fun demo(): Int {
    val a = suspendCall1()      // 挂起点 1
    val b = suspendCall2()      // 挂起点 2
    return a + b
}
```

编译成状态机（伪代码）：
```java
Object demo(Continuation $cont) {
    switch ($cont.label) {
        case 0:
            $cont.label = 1;
            Object r1 = suspendCall1($cont);
            if (r1 == COROUTINE_SUSPENDED) return COROUTINE_SUSPENDED;
            $cont.a = r1;
            // fall through
        case 1:
            $cont.label = 2;
            Object r2 = suspendCall2($cont);
            if (r2 == COROUTINE_SUSPENDED) return COROUTINE_SUSPENDED;
            return (int)$cont.a + (int)r2;
    }
}
```

**结论**：**一个挂起函数 = 一个状态机 = 一个类**。每个挂起点是一个 case。

### 3.4 挂起点即分支

*[骨架占位：一个 `suspend fun` 有 N 个挂起点，就有 N+1 个 case；`label` 字段是状态机指针]*

## 4. Continuation内幕

### 4.1 状态机字段布局

编译器为每个 `suspend fun` 生成一个继承 `ContinuationImpl` 的类，字段包括：
- `label`：状态编号
- 每个跨挂起点的局部变量（如 `a`、`b`）
- 外层参数（如 `id`）

*[骨架占位：javap 输出完整字段列表；对比手写状态机的复杂度]*

### 4.2 label与resumeWith

```
挂起：状态机 return COROUTINE_SUSPENDED，控制权回到 Dispatcher
    ↓
异步操作完成，调用 continuation.resumeWith(Result.success(v))
    ↓
resumeWith 内部再次调用状态机的 invokeSuspend
    ↓
状态机根据 label 跳转到下一个 case，继续执行
```

### 4.3 COROUTINE_SUSPENDED

`COROUTINE_SUSPENDED` 是 `kotlin.coroutines.intrinsics` 里定义的**哨兵对象**：

```kotlin
public val COROUTINE_SUSPENDED: Any = CoroutineSingletons.COROUTINE_SUSPENDED
```

**语义**：函数返回它表示"我暂停了，等下再来"；返回真实值表示"我完成了"。

### 4.4 尾调用优化

*[骨架占位：`suspend fun` 若只调用另一个 `suspend fun` 并直接返回，会做"尾挂起优化"，不生成状态机]*

## 5. Dispatcher调度机制

### 5.1 Main调度实现

Android 上 `Dispatchers.Main` 由 `AndroidDispatcherFactory` 提供，底层是 `Handler.post(...)`——把 continuation 放到主线程 Looper 队列。

*[骨架占位：MainDispatcherLoader 的 ServiceLoader 机制；immediate 变体的用途]*

### 5.2 IO线程池模型

`Dispatchers.IO` 底层是 `DefaultDispatcher` 共享的 CoroutineScheduler，但**允许阻塞线程数**扩展到 `64` 或核数（取更大）。

*[骨架占位：CoroutineScheduler 源码剖析——工作窃取队列、CPU permit 计数、阻塞线程弹性扩容]*

### 5.3 Default线程池

`Dispatchers.Default` 用同一个 CoroutineScheduler，线程数 = 核数，专供 CPU 密集任务。

*[骨架占位：与 Java `ForkJoinPool.commonPool()` 的对比]*

### 5.4 Unconfined特殊性

**危险调度器**——在当前线程立即执行，直到第一个挂起点为止。**只用于单元测试或极特殊场景**。

## 6. 结构化并发

### 6.1 CoroutineScope层级

每个 `CoroutineScope` 持有一个 `Job`，`Job` 之间形成父子树。

```
Application scope
  └─ viewModelScope
       └─ launch { ... }              ← child
             └─ launch { ... }        ← grand-child
```

### 6.2 Job父子关系

**规则**：
- 父 Job 取消 → 所有 child 取消
- 任一 child 抛异常（非 Cancellation） → 父 Job 取消 → 兄弟取消

### 6.3 取消传播机制

*[骨架占位：Cancel 从上向下传播；Complete 从下向上等待；一张父子树的图]*

### 6.4 协作取消要点

```kotlin
launch {
    while (isActive) {           // 必须自查
        yield()                  // 或调用挂起函数
        heavyCompute()
    }
}
```

**忘记检查 `isActive` 是最常见的取消不响应原因**。

## 7. 异常传播规则

### 7.1 Job与Supervisor差异

| 类型 | child 抛异常 | 影响 |
|---|---|---|
| `Job` | 传播到父 → 兄弟被取消 | 一荣俱荣一损俱损 |
| `SupervisorJob` | 只影响自己 | 独立故障 |

### 7.2 ExceptionHandler生效

```kotlin
val handler = CoroutineExceptionHandler { _, e -> Log.e("Coro", "err", e) }
scope.launch(handler) { throw IllegalStateException() }
```

**关键规则**：
- `CoroutineExceptionHandler` **只对根协程** `launch` 生效
- `async` 不用 handler——异常在 `.await()` 时抛出

### 7.3 async异常延迟

```kotlin
val deferred = scope.async { throw RuntimeException() }
// 这里不会崩，直到：
deferred.await()   // 才抛出
```

### 7.4 CancellationException

**特殊约定**：`CancellationException` **不算错误**——它是取消信号。

*[骨架占位：如果自定义异常继承了 CancellationException 会怎样——被静默吞掉的坑]*

## 8. Flow与协程关系

### 8.1 Flow是冷流

```kotlin
val flow = flow { emit(1); emit(2) }    // 冷流，还未开始
flow.collect { println(it) }             // 触发时才开始生产
```

Flow 每次 `collect` 都会**独立执行 `flow { }` 内部**——因此叫"冷流"。

### 8.2 与Sequence差别

| 特性 | Sequence | Flow |
|---|---|---|
| 是否支持挂起 | 不支持 | 支持 |
| 是否有背压 | 无 | 有 |
| 消费方 | 同步 | 协程内 |

### 8.3 StateFlow与SharedFlow

- `StateFlow`：热流，保留最新值，替代 Android LiveData
- `SharedFlow`：热流，可配置 replay buffer，替代 EventBus

*[骨架占位：两者的场景对比、订阅生命周期]*

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到 1.1 节的 7 个疑问：

1. **`suspend` 关键字触发 CPS 变换**——函数末尾加 `Continuation` 参数，返回类型变 `Object`。
2. **挂起函数是状态机**——每个挂起点是一个 case，`label` 是状态编号。
3. **`Dispatchers.IO`** 与 **`Default`** 共享 CoroutineScheduler，只是 IO 允许阻塞线程弹性扩容。
4. **`viewModelScope.launch` 内抛异常**——被 `viewModelScope` 的 Job 捕获，向上传播到 `viewModelScope.coroutineContext` 里的 `CoroutineExceptionHandler`——**如果没有 handler，就静默丢弃**。
5. **`Job` 传播异常，`SupervisorJob` 隔离异常**。
6. **协程比线程轻 100~1000 倍**——线程栈 1MB，协程状态机 100~200 字节。
7. **`CancellationException` 是取消信号，不是错误**——被协程库特殊处理。

**案例根因**：`viewModelScope` 用的是 `SupervisorJob + Dispatchers.Main`——`launch` 抛出的普通异常本应传播到 `CoroutineExceptionHandler`，但 `viewModelScope` **默认没配置 handler**——异常被 `handleCoroutineException` 里的 `handleUncaughtCoroutineException` 记录（Debug 才可见）后**丢弃**。

**修复**：
1. 用 `try/catch` 包住 `throw` 处；或
2. 给 `viewModelScope.launch` 加 `CoroutineExceptionHandler`
3. **杜绝在协程里裸抛异常**——用 `Result` 或 `sealed class` 明示错误

### 10.2 一个suspend一生

```
写下 suspend fun fetchUser(id: Long): User
    ↓
kotlinc CPS 变换 → 生成 fetchUser(id, cont) + FetchUser$Continuation 状态机类
    ↓
调用点 launch { val u = fetchUser(1) } → 分配 Continuation 对象
    ↓
Dispatcher 分派到线程池执行状态机
    ↓
遇到 delay/withContext → return COROUTINE_SUSPENDED
    ↓
异步事件回调 → cont.resumeWith(value)
    ↓
Dispatcher 再次调度状态机，label 跳转下一 case
    ↓
最终返回 User，父协程被通知完成
```

*[骨架占位：完整状态机执行时序图]*

### 10.3 设计哲学回扣

- **CPS 变换是并发抽象的语言级实现**：不引入新关键字，只加了 `suspend`
- **结构化并发消灭 Goroutine 泄漏**：每个协程必属于一个 scope
- **上下文即能力集合**：`CoroutineContext` 用"开放式携带"取代多参数
- **协程不是"更轻的线程"，是"用状态机模拟的线程"**：本质是内存里的状态而非 OS 资源

### 10.4 协程速查表

| 场景 | 推荐 API |
|---|---|
| 发射后不管 | `launch` + handler |
| 要拿返回值 | `async` + `await` |
| 切线程 | `withContext(dispatcher)` |
| 并发拉多接口 | `coroutineScope { async; async; await; await }` |
| 只关心最新一次 | `collectLatest` / `mapLatest` |
| 独立故障子协程 | `supervisorScope` |
| 超时控制 | `withTimeout` / `withTimeoutOrNull` |
