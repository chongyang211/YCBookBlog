## 1. 案例引入

### 1.1 一段反常代码

以下代码是一个真实事故——某 SDK 用 `by lazy(LazyThreadSafetyMode.NONE)` 做全局配置的懒加载，线上偶发 `NullPointerException`：

```kotlin
// AppConfig.kt
object AppConfig {
    val instance: Config by lazy(LazyThreadSafetyMode.NONE) {   // ⚠ NONE 模式
        parseConfig()
    }
}

// 多个线程同时启动时：
Thread { AppConfig.instance.timeout }.start()
Thread { AppConfig.instance.timeout }.start()   // 偶发返回 null
```

*[骨架占位：真实上报——偶发概率约 0.02%，但影响面广]*

### 1.2 顺藤摸到根因

**表象**：`Config?` 声明的字段返回 null？还是 `parseConfig()` 里的字段没初始化就被读到？

*[骨架占位：反编译 `AppConfig.instance` 的 getter，展示 `UnsafeLazyImpl` 内部字段的读取顺序；无 volatile 写入]*

### 1.3 我们要回答什么

看到这里，我们至少积累了 6 个疑问：

1. **`by lazy` 编译后到底生成了什么？多少个类、多少个字段？**
2. **`SYNCHRONIZED / PUBLICATION / NONE` 三种模式各自的实现有什么区别？**
3. **属性委托 `by` 与类委托 `by` 是同一个关键字，语义是同一回事吗？**
4. **`Delegates.observable` 的通知机制怎么工作？为什么容易泄漏？**
5. **`KProperty<*>` 是什么？为什么每次 getter 调用都要传它？**
6. **类委托与 Java 动态代理 `Proxy.newProxyInstance` 差在哪？**

## 2. 架构概览

### 2.1 委托两大家族

```
Kotlin `by` 关键字
├── 类委托 (Class Delegation)
│   └── class C : I by impl { ... }
│       ├── 编译器为每个接口方法生成转发桩
│       └── 编译期完成，零反射
└── 属性委托 (Property Delegation)
    └── val prop: T by delegate
        ├── 编译器生成 backing field 存储 delegate
        └── getter/setter 内调用 delegate.getValue()/setValue()
```

### 2.2 为什么这么切

**疑惑**：为什么 Kotlin 把两种截然不同的语义都用 `by` 表达？

**论证**：
1. 两者都是**"把行为委托给另一个对象"**——语义在直觉上一致
2. 都通过**编译期代码生成**实现，不依赖反射
3. 都体现"组合优于继承"的设计哲学
4. 让 API 使用者一眼看出"这不是继承，是委托"

**结论**：`by` 是 Kotlin 对"组合模式"的语言级支持——把 GoF 的委托模式变成一个关键字。

## 3. 属性委托字节码

### 3.1 getValue约定方法

```kotlin
val name: String by delegate
```

**约定**：`delegate` 对象必须提供 `getValue(thisRef, property): T` 方法（`var` 还要 `setValue`）。这不是接口约束，是**编译期约定**。

*[骨架占位：`operator` 关键字让 `getValue` 参与约定]*

### 3.2 编译器生成字段

```kotlin
class Foo {
    val name: String by MyDelegate()
}
```

反编译（简化）：
```java
public final class Foo {
    private final MyDelegate name$delegate = new MyDelegate();      // 字段
    
    static final KProperty[] $$delegatedProperties = { ... };       // 静态字段
    
    public final String getName() {
        return name$delegate.getValue(this, $$delegatedProperties[0]);
    }
}
```

**生成物**：
1. 一个 `xxx$delegate` 字段存放委托对象
2. 一个 `$$delegatedProperties` 静态数组存放 `KProperty` 引用
3. getter 内调用 `delegate.getValue(this, property)`

### 3.3 KProperty是什么

`KProperty<*>` 是 `kotlin.reflect` 里的接口，代表属性的元信息（名字、返回类型、注解等）。每个委托属性会被编译器"注册"一个 `KProperty` 实例。

*[骨架占位：优化——`optimizedCallableReferences` 让 KProperty 生成更精简]*

### 3.4 setValue对称结构

`var` 属性的 `by` 委托同时生成 `setter`，内部调用 `delegate.setValue(this, property, newValue)`。

## 4. lazy三种模式

### 4.1 SYNCHRONIZED默认

**默认模式**——用 `synchronized` 保证多线程只初始化一次：

```kotlin
val name: String by lazy { compute() }    // 默认 SYNCHRONIZED
```

内部实现（简化）：
```kotlin
private class SynchronizedLazyImpl<T>(initializer: () -> T) : Lazy<T> {
    private var _value: Any? = UNINITIALIZED
    override val value: T
        get() {
            if (_value !== UNINITIALIZED) return _value as T
            synchronized(this) {
                if (_value !== UNINITIALIZED) return _value as T
                _value = initializer()
                return _value as T
            }
        }
}
```

*[骨架占位：双重检查锁模式；`UNINITIALIZED` 哨兵；`_value` 需要 volatile 吗]*

### 4.2 PUBLICATION实现

**多线程可并发初始化**，但只有一个结果被"发布"：

```kotlin
val name by lazy(LazyThreadSafetyMode.PUBLICATION) { compute() }
```

内部用 `AtomicReferenceFieldUpdater.compareAndSet` 让并发的初始化竞争，胜者的值被采用，其它值被丢弃。

**代价**：`initializer` 可能被多次调用（副作用要小心！）。

### 4.3 NONE性能最优

**单线程模式**——不加锁，只用普通字段：

```kotlin
val name by lazy(LazyThreadSafetyMode.NONE) { compute() }
```

**风险**：多线程访问未初始化的属性时，**字段写入尚未 flush 到主内存**，另一线程可能看到 `null` 甚至部分初始化对象。这就是 1.1 案例的根因。

### 4.4 双重检查锁真相

*[骨架占位：`_value` 字段是 volatile 吗？双重检查锁在 JMM 下的正确性分析；synchronized 是否已经足够]*

## 5. 类委托字节码

### 5.1 接口方法转发

```kotlin
interface Repo { fun save(): Int; fun load(): Int }
class RepoImpl : Repo { override fun save() = 1; override fun load() = 2 }
class LoggingRepo(val delegate: Repo) : Repo by delegate
```

反编译 `LoggingRepo`：
```java
public final class LoggingRepo implements Repo {
    private final Repo $$delegate_0;
    public LoggingRepo(Repo delegate) { this.$$delegate_0 = delegate; }
    public int save() { return $$delegate_0.save(); }           // 编译器生成
    public int load() { return $$delegate_0.load(); }           // 编译器生成
}
```

**结论**：编译器为每个接口方法生成"转发桩"。零反射、零动态开销。

### 5.2 delegate字段生成

字段名规则：`$$delegate_N`，N 从 0 递增（支持多接口委托给多个对象）。

### 5.3 override覆盖机制

选择性 override 接口方法即可只增强特定方法：

```kotlin
class LoggingRepo(val delegate: Repo) : Repo by delegate {
    override fun save(): Int {
        println("before save")
        return delegate.save()             // 或调用 $$delegate_0.save()
    }
    // load 由编译器生成的转发桩处理
}
```

### 5.4 与Proxy动态代理

| 维度 | Kotlin 类委托 | Java Proxy |
|---|---|---|
| 生成时机 | 编译期 | 运行时字节码生成 |
| 性能 | 直接方法调用 | 反射 + `InvocationHandler` |
| 类型安全 | 编译期强类型 | 弱类型（`Object` 参数） |
| 语法负担 | 一个 `by` 关键字 | 匿名内部类 + 反射 |

## 6. 内建委托家族

### 6.1 observable源码

```kotlin
var name: String by Delegates.observable("init") { prop, old, new ->
    println("$old -> $new")
}
```

内部实现（简化）：
```kotlin
abstract class ObservableProperty<T>(initial: T) : ReadWriteProperty<Any?, T> {
    private var value = initial
    override fun getValue(thisRef: Any?, prop: KProperty<*>) = value
    override fun setValue(thisRef: Any?, prop: KProperty<*>, new: T) {
        val old = value
        if (!beforeChange(prop, old, new)) return
        value = new
        afterChange(prop, old, new)              // 触发监听
    }
    protected open fun beforeChange(...): Boolean = true
    protected open fun afterChange(...): Unit = Unit
}
```

### 6.2 vetoable否决实现

```kotlin
var age by Delegates.vetoable(0) { _, _, new -> new >= 0 }
```

**`beforeChange` 返回 false 时不写入新值**——用于拒绝无效赋值。

### 6.3 notNull保护委托

```kotlin
var name: String by Delegates.notNull()
name.length      // 未赋值前访问抛异常
name = "K"       // 之后正常
```

**用途**：延迟初始化非空 `var`（相当于 `lateinit var` 的 API 版本）。

### 6.4 Map委托取值

```kotlin
class User(map: Map<String, Any>) {
    val name: String by map
    val age: Int by map
}

val u = User(mapOf("name" to "K", "age" to 20))
```

用 `Map.getValue` 约定从 map 中读取属性——常见于 JSON、Preferences 等场景。

## 7. 自定义属性委托

### 7.1 ReadWriteProperty接口

自定义可读写属性委托的最简写法——实现 `ReadWriteProperty<Any?, T>`：

```kotlin
class LoggedProp<T>(private var value: T) : ReadWriteProperty<Any?, T> {
    override fun getValue(thisRef: Any?, prop: KProperty<*>): T {
        println("get ${prop.name}")
        return value
    }
    override fun setValue(thisRef: Any?, prop: KProperty<*>, new: T) {
        println("set ${prop.name} = $new")
        value = new
    }
}
```

### 7.2 provideDelegate高级

`provideDelegate` 让委托的**创建**也可参与——比如在属性绑定时做校验：

```kotlin
class Preference<T>(val default: T) {
    operator fun provideDelegate(
        thisRef: Any?, prop: KProperty<*>
    ): ReadWriteProperty<Any?, T> {
        checkPreference(prop.name)
        return PreferenceImpl(prop.name, default)
    }
}

class Settings {
    var name by Preference("default")   // provideDelegate 被调用
}
```

## 8. 委托性能代价

### 8.1 一次方法转发

**类委托**：每次调用多一次虚方法调用——通常被 JIT 内联，几乎零开销。

### 8.2 KProperty创建

**属性委托**：每次 getter 都要传 `KProperty` 引用；`KProperty` 由编译器生成、静态字段缓存——一次创建，重复使用。

### 8.3 lazy对象额外开销

`by lazy { }` 生成一个 `Lazy<T>` 实现类的实例——**每个属性一个对象**。10 万个 lazy 属性 = 10 万个对象。

*[骨架占位：`by lazy` 与手写双重检查锁字段的内存对比]*

### 8.4 JIT能否消除

**结论**：类委托的转发调用通常能被 JIT 消除；属性委托的 `getValue` 调用是否被内联取决于是否 `inline` 版本（如 `Lazy.getValue` 就是 `inline`）。

## 9. 事故案例复盘

### 9.1 lazy_NONE死锁

*[骨架占位：`NONE` 模式的可见性问题；即使不"死锁"，也可能读到未完全构造的对象]*

**典型现象**：字段类型是 `Config`（非空），运行时读到 `null`——因为其它线程看到了未初始化的 `Config` 引用。

### 9.2 observable泄漏Fragment

```kotlin
class MyFragment : Fragment() {
    var user: User by Delegates.observable(User("init")) { _, _, _ ->
        updateUI()               // 隐式引用 Fragment.this
    }
}
```

**问题**：Lambda 捕获 `this`，只要 `user` 变量还活着，Fragment 就无法回收。

*[骨架占位：正确姿势——用 `WeakReference` 或 `viewLifecycleOwner`]*

### 9.3 类委托绕过override

```kotlin
class Repo : IRepo { override fun save(): Int { return 1 }; fun helper() = save() }
class Logging(delegate: IRepo) : IRepo by delegate {
    override fun save() = 999
}

val logging = Logging(Repo())
logging.save()             // 999
logging.helper()           // 1（内部调用了 Repo 自己的 save！）
```

**根因**：`helper()` 是 `Repo` 的方法，`Logging` 没有它——调用 `helper()` 实际上跳到 `Repo` 实例上，看不到 `Logging.save` 的覆盖。

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到 1.1 节的 6 个疑问：

1. **`by lazy` 生成一个 `Lazy<T>` 实现字段 + `KProperty` 静态引用**——每属性一个对象。
2. **`SYNCHRONIZED`** 用锁 + 双重检查；**`PUBLICATION`** 用 CAS 允许并发但只发布一个；**`NONE`** 无同步，只能单线程访问。
3. **属性委托 `by` 与类委托 `by` 是**不同的编译期机制**——只是关键字复用。前者委托 getter/setter，后者委托接口方法。
4. **`Delegates.observable` 用继承 `ObservableProperty` 的模板方法模式**——Lambda 里若引用 `this` 就容易泄漏。
5. **`KProperty` 是编译器生成的属性元数据引用**——每属性一个静态实例，运行时用于反射与委托传参。
6. **类委托是**编译期**方法转发**，Java Proxy 是**运行时**字节码动态生成——前者更快、更类型安全。

**案例根因**：`lazy(NONE)` 无 volatile / synchronized 保证——线程 A 完成初始化后写 `_value` 字段，尚未 flush 到主存；线程 B 读到部分初始化的 `Config` 对象，其内部字段仍为默认值 null。

**修复**：
1. 改成默认的 `by lazy { }`（`SYNCHRONIZED`）
2. 或用 `volatile` 字段 + 手写双重检查
3. **绝不用 `NONE` 除非能证明单线程访问**

### 10.2 一个lazy委托一生

```
写下 val cfg: Config by lazy { parseConfig() }
    ↓
kotlinc 编译期：
  - 生成 cfg$delegate: Lazy<Config> 字段
  - 生成 $$delegatedProperties[N] 静态 KProperty
  - 生成 getCfg() { return cfg$delegate.getValue(this, prop) }
    ↓
运行期首次调用 getCfg()：
  - SynchronizedLazyImpl.value getter
  - 检查 _value != UNINITIALIZED？否
  - 加锁 → 再检查 → 调 initializer()
  - 存入 _value，返回结果
    ↓
后续调用：直接返回 _value（快路径）
```

### 10.3 设计哲学回扣

- **组合优于继承**：委托关键字让"has-a"变成一等公民
- **约定优于配置**：`getValue/setValue` 是约定不是接口——灵活性与类型安全并存
- **编译期完成，零反射**：Kotlin 委托机制的运行时开销极小
- **让危险模式显式化**：`LazyThreadSafetyMode.NONE` 强迫开发者显式选择——不做默默假设

### 10.4 委托速查表

| 场景 | 推荐 |
|---|---|
| 单线程延迟初始化 | `by lazy(NONE)` |
| 多线程延迟初始化 | `by lazy { }` |
| 属性变化监听 | `Delegates.observable` |
| 属性变化否决 | `Delegates.vetoable` |
| 无初始值非空 var | `Delegates.notNull()` 或 `lateinit var` |
| 从 Map 取值 | `by map` |
| 组合多接口 | 类委托 `by delegateN` |
| 需要拦截创建 | `provideDelegate` |
