## 1. 案例引入

### 1.1 一段反常代码

以下代码是一个真实的性能事故——某高频路径调用 `forEachIndexed`，同事觉得"就是个循环工具函数"，业务上线后性能监控发现该点吃了 15% CPU：

```kotlin
// HotPath.kt
fun processEvents(events: List<Event>) {
    var total = 0L
    events.forEachIndexed { i, ev ->             // 高频调用，QPS 数十万
        if (ev.type == 1) total += ev.amount
    }
    submit(total)
}
```

同事把 `forEachIndexed` 改成手写 for 循环，CPU 降到 5%——**30 倍的性能差**？可是 `forEachIndexed` 明明是标准库的 `inline` 函数啊。

*[骨架占位：真实 APM 火焰图；差异原因分析——原来同事用的是自己封装的 `forEachIndexed` 忘加 inline]*

### 1.2 顺藤摸到根因

**表象**：一个 30 行的高阶函数，加不加 `inline` 关键字，性能差 30 倍。

*[骨架占位：反编译两版代码，对比 Lambda 对象的分配次数]*

## 2. 架构概览

### 2.1 四关键字关系

```
inline fun ... (crossinline block1, noinline block2, ...) { ... }
  │              │                  │
  │              │                  └─ 该 Lambda 参数不内联，作为对象保留
  │              └─────────────────── Lambda 可内联但禁止非局部返回
  └──────────────────────────────────  函数整体在调用点展开

inline fun <reified T> parse(...)
                 │
                 └──── 类型参数 T 在内联后可通过 T::class 反射
```

*[骨架占位：四关键字关系图]*

### 2.2 为什么这么切

**疑惑**：为什么不直接让 JVM JIT 内联，而要让 Kotlin 编译期做内联？

**论证**：
1. JVM JIT 内联只在**方法足够热**时才做，冷路径没优势
2. Kotlin 的高阶函数 + Lambda 是**结构性**的语言特性——每次调用 `list.filter { }` 都需要一个 Lambda 对象
3. Kotlin 编译期内联让 Lambda **完全消失**——不留分配、不留调用
4. 更重要的是——只有编译期内联，才能实现 `reified`（类型信息注入）和"非局部返回"

**结论**：`inline` 是 Kotlin 高阶函数的**能力放大器**——没有它，`filter/map/apply/let` 都会成为性能陷阱。

## 3. inline展开机制

### 3.1 调用点即函数体

```kotlin
inline fun measure(block: () -> Unit): Long {
    val start = System.nanoTime()
    block()
    return System.nanoTime() - start
}

// 调用方
val time = measure { doWork() }
```

编译后调用方大致等价于：
```kotlin
val start = System.nanoTime()
doWork()                                 // Lambda 内容原地展开
val time = System.nanoTime() - start
```

**关键**：Lambda 体、函数体**全部原地展开**。

### 3.2 Lambda对象消除

未 inline 版本：
```
NEW SomeLambda$1                          // 分配 Lambda 对象
INVOKEVIRTUAL measure(kotlin.jvm.functions.Function0)  // 调用
```

inline 版本：
```
INVOKESTATIC doWork()                     // 直接调 doWork
```

**Lambda 对象消失**——分配、GC 压力、虚函数调用全消失。

### 3.3 非局部返回实现

```kotlin
inline fun findFirst(list: List<Int>, cond: (Int) -> Boolean): Int? {
    for (x in list) if (cond(x)) return x       // 这里 return 是 findFirst 的
    return null
}

fun demo(): Int {
    findFirst(listOf(1, 2, 3)) {
        if (it == 2) return -1               // ⚠ 这个 return 属于 demo，不属于 Lambda
    }
    return 999
}
```

**非局部返回**：Lambda 里的 `return` 能跳出**外层普通函数**——只有内联的高阶函数才允许这种写法。

*[骨架占位：字节码上 `return` 就是普通的 `IRETURN`，能这样跳出是因为 Lambda 内容已经被展开在外层函数体内]*

## 4. noinline与crossinline

### 4.1 noinline使用时机

**问题**：如果 inline 函数的 Lambda 参数**需要保存起来**（比如放进列表），Lambda 就不能被消除，必须保留为对象——这时用 `noinline`。

```kotlin
inline fun register(
    inlineHandler: () -> Unit,          // 会被展开
    noinline delayedHandler: () -> Unit  // 保存起来，稍后调用
) {
    inlineHandler()
    pendingList.add(delayedHandler)     // 需要引用 Lambda 对象，必须 noinline
}
```

### 4.2 crossinline限制

**问题**：如果 Lambda 参数会被**传递到另一个非内联位置调用**（比如内部类的方法），我们仍然可以 inline 它——但**必须禁止非局部返回**（因为返回目标已丢失）。

```kotlin
inline fun runOnUiThread(crossinline block: () -> Unit) {
    handler.post { block() }            // block 在 Runnable.run() 里被调用
}

runOnUiThread {
    // return           // ⚠ 编译报错，crossinline 禁止非局部返回
}
```

### 4.3 非局部返回禁止

*[骨架占位：`crossinline` 只让 Lambda 内联但禁止 `return`；如果需要早退可用 `return@runOnUiThread`（局部返回）]*

### 4.4 三者组合矩阵

| 修饰 | Lambda 被内联 | 允许非局部返回 | 可保存为对象 |
|---|---|---|---|
| 默认 (inline 函数的 Lambda) | ✅ | ✅ | ❌ |
| `crossinline` | ✅ | ❌ | ❌ |
| `noinline` | ❌ | ❌ | ✅ |

## 5. reified破解擦除

### 5.1 JVM泛型擦除

Java/Kotlin 在 JVM 上都受"类型擦除"限制：
```java
List<String> l = ...;
if (l instanceof List<Integer>) { }   // ⚠ 编译报错，无法运行时区分
```

**擦除的历史原因**：Java 5 引入泛型时为兼容旧字节码，泛型信息只留在编译期。

### 5.2 reified替换机理

Kotlin 的 `reified` 结合 `inline` 让泛型"复活"：

```kotlin
inline fun <reified T> Any.isType(): Boolean = this is T

val ok = "hi".isType<String>()   // 编译时展开为 "hi" is String
```

**核心机制**：函数被 inline 时，编译器把 `T` **替换为具体类型**（在这里是 `String`），因此 `is T` 变成 `is String`——可正常编译。

### 5.3 字节码类型嵌入

```kotlin
inline fun <reified T> loadJson(json: String): T = Gson().fromJson(json, T::class.java)

val u: User = loadJson(text)
```

编译后调用点：
```
Gson().fromJson(text, User.class)   // T::class.java 被替换为 User.class
```

**结论**：`reified` 让 `T::class` / `is T` / `as T` 都成为可能——因为它们最终被替换成具体类。

### 5.4 无inline不reified

**规则**：`reified` **必须**与 `inline` 一起用，否则类型参数无从替换。

## 6. 内联的代价

### 6.1 代码膨胀实测

一个 5 行的 inline 函数被调用 100 次 → 生成的字节码相当于 500 行。

*[骨架占位：实测数字——某 200 KB kotlin 类库开启大量 inline 后膨胀到 350 KB]*

### 6.2 JIT优化影响

**副作用**：函数体过大时，JIT C2 编译器可能因为方法字节码 > 8000 字节而**拒绝优化**。

### 6.3 二进制大小坑

Android APK 有 dex 方法数上限——过度 inline 会让方法数虚假膨胀。

### 6.4 public_inline_ABI风险

**严重问题**：如果一个 `public inline fun` 是库的 API，函数体变化会**破坏二进制兼容**——因为老调用方已经把函数体展开到自己的字节码里。

*[骨架占位：Kotlin 提供 `@PublishedApi` 注解让 private/internal 的辅助 API 能被 public inline 引用]*

## 7. value类零开销

### 7.1 value类历史演进

- Kotlin 1.3：实验性 `inline class`
- Kotlin 1.5：稳定为 `@JvmInline value class`
- Kotlin 2.0：与 Valhalla（Java）方向对齐

### 7.2 字节码擦除表现

```kotlin
@JvmInline
value class UserId(val value: Long)

fun greet(uid: UserId) { ... }
```

字节码：
```
public static void greet-XX(long)     // 方法签名参数是 long，不是 UserId
```

**结论**：`value class` 在字节码上**擦除**为底层类型——真·零开销包装。

### 7.3 装箱触发条件

以下情况仍会装箱为普通对象：
- 用作**泛型参数** `List<UserId>`
- 用作**可空类型** `UserId?`
- 用作**接口引用** `Any` / 接口

### 7.4 与JEP401对比

Java Valhalla JEP 401（value types）会做类似事情，但在 **JVM 层**，比 Kotlin 编译期擦除更彻底。

## 9. 与其他语言对比

### 9.1 Cpp的inline关键字

C++ `inline` 是"允许 ODR 违反"提示 + "建议内联"提示——编译器有最终决定权。

### 9.2 Rust单态化机制

Rust 泛型走**单态化**——每个具体类型生成一份代码，本质与 `reified` 类似，但覆盖所有泛型（不需要额外标记）。

### 9.3 CSharp具化泛型

C# 泛型在 CLR 层保留类型信息（reified generics）——无需额外关键字，运行时可以 `typeof(T)`。

### 9.4 三者取舍

| 语言 | 泛型策略 | 优点 | 缺点 |
|---|---|---|---|
| Java/Kotlin | 擦除 | 兼容旧字节码 | 无法 `is T` |
| Kotlin `reified` | 编译期展开 | 局部具化 | 只在 inline 内 |
| Rust | 单态化 | 完全具化 | 编译慢、二进制大 |
| C# | CLR 保留 | 完全具化 + 运行时反射 | 运行时开销 |

## 10. 综合案例串讲

### 10.1 案例真相揭晓

回到 1.1 节的 6 个疑问：

1. **`inline` 让编译器把函数体 + Lambda 都在调用点原地展开**——Lambda 对象消失。
2. **Kotlin Lambda 是 `FunctionN` 接口的匿名实现**——非 inline 时每次调用要分配对象。
3. **`crossinline` 禁止非局部返回，`noinline` 保留 Lambda 对象，`reified` 保留类型信息**——三者互补。
4. **JVM 泛型擦除源于兼容性**——`reified` 通过 inline 展开时把 `T` 替换为具体类型，从而绕过擦除。
5. **`inline` 的代价**：代码膨胀、二进制大小、JIT 二次内联失败、public API 稳定性。
6. **`value class` 借助 inline 思想做类型包装的零开销**——但泛型/接口/可空场景仍会装箱。

**案例根因**：那位同事封装的 `forEachIndexed` **没有加 inline**——每次调用都要分配一个 `Function2` Lambda 对象，QPS 数十万时 GC 压力巨大。

**修复**：加上 `inline` 关键字，Lambda 消失，性能回归。

### 10.2 一个inline_reified一生

```
写下 inline fun <reified T> parse(json: String): T
    ↓
kotlinc 编译时：函数体保存在 metadata 中
    ↓
调用点 val u: User = parse(text)
    ↓
kotlinc 展开：把 T 替换为 User，函数体原地插入
    ↓
最终字节码：Gson().fromJson(text, User.class)
    ↓
运行期：直接反射调用，无泛型擦除困扰
```

### 10.3 设计哲学回扣

- **零开销抽象**：编译期做的事，运行期就不用做
- **能力叠加而非替代**：inline + reified + crossinline 组合表达能力
- **代价前置**：内联膨胀是编译期代价，换来运行期收益
- **不与 JVM 硬碰**：擦除无法改，就在语言层"局部"绕过

### 10.4 内联速查表

| 场景 | 是否 inline |
|---|---|
| 接受 Lambda 参数的高阶函数 | ✅ inline |
| 需要 `reified T` | ✅ 必须 inline |
| 需要"非局部返回" | ✅ 必须 inline（默认参数 Lambda） |
| 需要保存 Lambda 稍后调用 | inline + noinline |
| Lambda 会在异步/回调里执行 | inline + crossinline |
| 不接 Lambda 的普通函数 | ❌ 不 inline（无收益） |
| 大函数（>30 行） | ❌ 不 inline（膨胀） |
| public API 且函数体可能演进 | ❌ 谨慎 inline |
