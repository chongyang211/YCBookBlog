# 02.QML引擎与渲染原理

> QML 不是"解释执行的 HTML"——它是编译为 C++ 对象树的 GPU 优化渲染器。理解引擎原理，才能写出高性能嵌入式 UI。

## 1. 案例引入

### 1.1 一个让人困惑的性能现象

```qml
// 某工程师在 ARM 板上写了这段代码：
ListView {
    model: 500
    delegate: Rectangle {
        width: 100; height: 100
        color: "blue"
        Rectangle {
            anchors.centerIn: parent
            width: 50; height: 50; color: "red"
            rotation: 45
        }
    }
}
```

**现象**：滑动到第 50 个 Item 后掉帧严重，GPU 利用率却只有 30%。

**疑惑**：
- 不是 GPU 瓶颈 —— 为什么还是卡？
- QML 不是声称"硬件加速"吗？
- 问题到底是 QML 引擎还是 Scene Graph？

### 1.2 揭开谜底：批处理打断

每个 delegate 内部有一个 `rotation: 45` 的嵌套 Rectangle。
Scene Graph 的批处理渲染需要**相同的材质 + 相同的状态**。
每个旋转的子 Rectangle 打断了批处理，500 个 Item = 1000 个 Draw Call！

```
不旋转（同材质）：
  Draw Call 1: 画 500 个蓝色 Rectangle（批处理 ✓）
  Draw Call 2: 画 500 个红色 Rectangle（批处理 ✓）
  总共 2 个 Draw Call → 极快

有旋转（异材质）：
  Draw Call 1: 画蓝色 Rectangle 1
  Draw Call 2: 画红色旋转 Rectangle 1  ← 状态变化,打断批处理
  Draw Call 3: 画蓝色 Rectangle 2
  Draw Call 4: 画红色旋转 Rectangle 2  ← 又打断
  ...（重复 500 次）
  总共 1000 个 Draw Call → GPU 虽然不忙，但 CPU 和状态切换爆炸
```

**本章带你深入 QML 引擎和 Scene Graph 内部，理解"为什么"以及"如何避免"这类问题。**

## 2. QML 引擎到底做了什么

### 2.1 从 QML 文本到 C++ 对象树

```
QML 执行流程（三步）：

Step 1: 词法/语法分析（QQmlEngine）
  QML 文本 → Token → AST（抽象语法树）
  
  例：Rectangle { width: 100 } 
       → AST: ObjectLiteral(Rectangle) { PropertyBinding(width, 100) }

Step 2: 对象实例化（QQmlComponent）
  AST → 创建 C++ QObject 对象树
  Rectangle → new QQuickRectangle()
  属性绑定 width: 100 → setProperty("width", 100)
  
  每个 QML 对象的背后都是一个真实的 C++ 对象！
  QML 不是解释执行——它是一次性编译为 C++ 对象树。

Step 3: 属性绑定求值（QQmlBinding）
  建立绑定依赖图
  当 parent.width 变化 → 自动更新 children.anchors
```

### 2.2 对象树 vs 渲染树

```
QML 对象树（C++ QObject Tree）：
  这是"逻辑树"——管理属性、信号、绑定关系

  Window
    └── Rectangle (id: root)
         ├── Text (id: title)
         └── Rectangle (id: button)
              └── Text (id: btnText)

Scene Graph 渲染树（QSGNode Tree）：
  这是"渲染树"——管理 GPU 绘制命令

  WindowNode
    └── RectangleNode (root, position=(0,0), size=(800,480))
         ├── TextNode (title, text="Hello")
         └── RectangleNode (button)
              └── TextNode (btnText)

关键: 不是一一对应的！只有可见的可视元素才会创建渲染节点。
```

### 2.3 编译时 vs 运行时

```qml
// 编译时处理：
import QtQuick    // 模块导入——编译时解析到对应 C++ 类型
Item {             // 类型发现——编译器查找 QQuickItem 类
    width: 100     // 属性——编译器检查 width 是否为 Item 的合法属性
}

// 运行时处理：
property int counter: 0  // 运行时动态属性
Component.onCompleted: {
    // JavaScript——运行时在 V4 引擎（Qt 内嵌 JS 引擎）执行
}

Loader { source: "dynamic.qml" }  // 运行时动态加载
```

## 3. Scene Graph 渲染管线（核心原理）

### 3.1 Scene Graph 是什么

```
Scene Graph = Qt Quick 的 GPU 渲染引擎

没有 Scene Graph（Qt Widget）:
  Component::paintEvent() {
      // 每个 Widget 自己用 QPainter 画
      // 各自提交各自的绘制命令
      // 没有批处理 → Draw Call 爆炸
  }

有 Scene Graph（Qt Quick）:
  QML 对象树 → 同步 → Scene Graph 节点树
                              ↓
                          遍历 + 批处理 + 排序
                              ↓
                          生成优化后的渲染命令
                              ↓
                          批量提交到 OpenGL/Vulkan/Null Backend
```

### 3.2 渲染的四个阶段

```
渲染线程（独立于 GUI 线程）每帧循环：

Phase 1: 同步（Synchronization）
  ┌─────────────────────────────────┐
  │ QObject Tree (GUI Thread)       │
  │  width 变了? opacity 变了?      │
  └───────────────┬─────────────────┘
                  │ 只拷贝变化
                  ▼
  ┌─────────────────────────────────┐
  │ Scene Graph Tree (Render Thread)│
  │   更新变化的节点属性              │
  └─────────────────────────────────┘

Phase 2: 预处理（Preprocessing）
   为需要 Offscreen Buffering 的节点分配 FBO
   （ShadeEffect, Opacity < 1 的组合节点等）

Phase 3: 渲染（Rendering）
  遍历节点树 → 生成绘制命令 → 批量提交 OpenGL

Phase 4: 交换缓冲区（Swap）
  eglSwapBuffers() → 显示新帧
```

### 3.3 批处理渲染——性能关键

```
Scene Graph 的"秘密武器"：

无批处理（逐节点渲染）：
  for each node:
    glUseProgram(node.shader)  ← 切换着色器（昂贵）
    glBindTexture(node.texture) ← 绑定纹理（昂贵）
    glDrawArrays(...)           ← 一次只画一个节点
  → 1000 个节点 = 1000 次状态切换 = 慢

Scene Graph 批处理（按材质分组）：
  1. 按 shader + texture + blendMode 排序
  2. 相同状态的节点归为一组
  3. 每组一次 glUseProgram + 一次 glDrawArrays(含多个节点)
  
  分组前: [A, B, A', C, B', C', A'']
  分组后: [A, A', A''] [B, B'] [C, C']
  → 1000 个节点 → 3~5 个 Draw Call → 极快
```

**回到案例**：为什么 `rotation: 45` 打断批处理？

```
Scene Graph 的批处理条件：
  ✅ 相同 shader
  ✅ 相同 texture
  ✅ 相同 opacity
  ✅ 相同 blendMode
  ❌ 相同 transform matrix（旋转/缩放/平移改变了矩阵）

rotation: 45 → 改变了 transform 矩阵 → 无法和其他节点批处理 → Draw Call 翻倍
```

## 4. 渲染线程与 GUI 线程

### 4.1 双线程模型

```
┌─────────────────────┐       ┌─────────────────────┐
│    GUI Thread       │       │   Render Thread     │
│  (主线程)            │──────→│  (独立线程)          │
│                     │ 同步  │                     │
│  - 事件处理          │       │  - Scene Graph 遍历  │
│  - JS 执行           │       │  - 批处理            │
│  - 属性更新          │       │  - OpenGL 调用       │
│  - 绑定求值          │       │  - 交换缓冲区         │
│                     │       │                     │
│  1000 次/秒          │       │  60 次/秒            │
└─────────────────────┘       └─────────────────────┘

关键细节：
  - 两个线程共享 Scene Graph 数据
  - GUI Thread 可以标记节点为"脏"（dirty）
  - Render Thread 在下一帧的同步阶段获取变化
  - 阻塞 GUI Thread 不会阻塞 Render Thread（反之亦然）
```

### 4.2 对开发者的影响

```
场景 1: 修改 QML 属性
  rectangle.color = "red"
  → GUI Thread 标记该节点 dirty
  → 下一帧 Render Thread 发现变化 → 更新 GPU 数据
  → 不影响当前帧的渲染

场景 2: JavaScript 密集计算
  for (let i = 0; i < 100000; i++) { /* 耗时计算 */ }
  → 阻塞 GUI Thread
  → 动画不流畅（因为 GUI 无法更新属性）
  → 但当前帧的渲染不受影响（Render Thread 独立）
```

## 5. 嵌入式渲染后端详解

### 5.1 四种渲染后端

```
EGLFS（嵌入式首选）：
  - 直接写 framebuffer + OpenGL ES
  - 不需要 X11/Wayland 窗口系统
  - 适合：ARM Linux 无桌面环境

LinuxFB（纯软件渲染）：
  - CPU 直接写 framebuffer（无 GPU）
  - 适合：资源极受限设备（无 GPU）

XCB / Wayland（桌面 Linux）：
  - 标准桌面环境的 Qt Quick 后端
  - 适合：开发调试、桌面应用

Offscreen（测试用）：
  - 不输出到屏幕，内存中渲染
  - 适合：CI 自动化测试
```

### 5.2 EGLFS 的运行原理

```
┌─────────────────────────────────┐
│         QML 应用                 │
├─────────────────────────────────┤
│         Qt Quick                 │
├─────────────────────────────────┤
│         QPA - EGLFS              │
│  ┌───────────────────────────┐  │
│  │  1. 打开 /dev/fb0          │  │
│  │  2. 获取屏幕参数             │  │
│  │  3. 创建 EGL Display        │  │
│  │  4. 创建 EGL Surface        │  │
│  │     (绑定到 fb0)            │  │
│  │  5. OpenGL ES 直接绘制到 fb0 │  │
│  └───────────────────────────┘  │
├─────────────────────────────────┤
│        Linux Kernel              │
│  ┌───────────────────────────┐  │
│  │ GPU 驱动 → framebuffer     │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘

关键：
  - 接管 /dev/fb0（独占模式，通常）
  - 绕过窗口管理器——不存在窗口概念
  - 启动速度极快（无 X11 启动等待）
```

### 5.3 软件渲染降级策略

```cpp
// 运行时检测 GPU 可用性
// 如果无 GPU ——回退到软件渲染
QQuickWindow::setSceneGraphBackend("software");

// 软件渲染后端：
// - 使用 Qt GUI 的 QPainter 模拟 OpenGL 调用
// - 直接写 /dev/fb0
// - 性能远低于 GPU，但在无 GPU 设备"能跑"
```

## 7. 速查表

| 概念 | 一句话 |
|---|---|
| QQmlEngine | QML 解析 + JS 执行 + 插件管理 |
| QQmlComponent | AST → C++ 对象树 |
| QObject Tree | 逻辑层（属性/信号/绑定） |
| Scene Graph | 渲染层（GPU 批处理绘制） |
| GUI Thread | 事件处理 + JS + 属性更新 |
| Render Thread | Scene Graph 遍历 + 批处理 + OpenGL |
| EGLFS | 无窗口系统的嵌入式渲染后端 |
| Draw Call | 一次 GPU 绘制命令（越少越快） |
| Batch | 相同状态的节点打包绘制 |

**核心哲学**：
```
QML 之所以快，不是因为"解释得快"——
而是它被"编译"为 C++ 对象树，
并由 Scene Graph 用 GPU 批处理渲染。

理解 Scene Graph 的批处理规则 = 等于掌握了 QML 性能的命门。
```
