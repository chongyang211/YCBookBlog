# 01.嵌入式GUI技术全景

> 从嵌入式 GUI 选型到 Qt/QML 架构全景——为什么 QML 是嵌入式交互界面的最优解？本文是整个专栏的"地图"。

## 1. 案例引入

### 1.1 一个真实的嵌入式 GUI 选型故事

```
某工业 HMI 触摸屏项目需求：
  硬件：ARM Cortex-A7, 512MB RAM, 无 GPU
  软件：Linux 3.10 内核, 无 X11/Wayland
  要求：60fps 仪表盘动画, < 2s 启动


团队尝试了三个方案：
  方案 A: C++ Widget + QPainter   → 启动 1.5s, CPU 绘制卡到 15fps

为什么 QML 能在这种受限设备上流畅运行？
答案就在 QML 的架构设计中——本章为你揭秘。
```

## 2. 嵌入式 GUI 技术选型全景

### 2.1 技术方案对比矩阵

```
┌────────────────┬──────────┬──────────┬──────────┬──────────┬──────────────┐
│     方案       │  启动速度 │  渲染性能 │  内存占用 │  开发效率 │   硬件要求    │
├────────────────┼──────────┼──────────┼──────────┼──────────┼──────────────┤
│ Qt Widget      │  快 ★★★  │ 中(CPU绘)│ 低 ★★★★★ │ 中 ★★★  │ 无GPU也可    │
│ Qt Quick(QML)  │  快 ★★★★ │ 高(GPU加速)│ 低 ★★★★ │ 高 ★★★★★│ OpenGL ES 2.0│
│ HTML5/Electron │  慢 ★    │ 低(浏览器)│ 高 ★    │ 高 ★★★★★│ 需较强CPU    │
│ LVGL(C绘图)    │ 极快 ★★★★│ 低(CPU)   │ 极低★★★★★│ 低 ★★   │ MCU/MPU皆可  │
│ Flutter(嵌入)  │  中 ★★  │ 高(Impeller)│ 中 ★★★  │ 高 ★★★★│ OpenGL/Vulkan│
│ SDL2+自绘      │  快 ★★★★ │ 低(CPU)   │ 低 ★★★★★ │ 极低 ★  │ 无GPU也可    │
└────────────────┴──────────┴──────────┴──────────┴──────────┴──────────────┘
```

### 2.2 各方案的"能力边界"详解

**Qt Widget（传统桌面方案）**：

```
渲染方式：QPainter → CPU 做所有光栅化
优势：
  - 启动极快（无 JS 引擎）
  - 内存极小（纯 C++）
  - 不需要 GPU
劣势：
  - 所有像素由 CPU 计算 → 动画密集场景降帧严重
  - QStyleSheet 能力弱 → 复杂 UI 难实现
  - 声明式 UI 表达能力差 → 代码膨胀
适用：资源极度受限、UI 简单、不需要动画的工控面板
```

**Qt Quick(QML)（嵌入式首选）**：

```
渲染方式：Scene Graph → GPU 批处理渲染
优势：
  - GPU 承担所有矩阵变换和像素填充 → 稳定 55~60fps
  - 声明式 QML → 描述 UI 比命令式 Widget 少 60% 代码
  - Scene Graph 内部的"只有变化才绘制"机制 → 即使 CPU 弱也不影响动画流畅度
  - QPA 抽象 → 同一套代码在桌面和 ARM 板都能跑
劣势：
  - 依赖 OpenGL ES 2.0+（需 GPU 或 Mesa 软渲染）
  - QML Engine + V4 JS Engine 增加启动时间和内存
  - 学习曲线：C++ → QML → JS → 元对象系统
适用：需要动画/复杂交互的 HMI、仪表盘、嵌入式多媒体终端
```

**HTML5/Chromium（为何不选）**：

```
问题根源：浏览器引擎是"通用渲染引擎"
  一个 Chromium 启动做了很多嵌入式不需要的事情：
    - 加载 50+ 系统字体
    - 初始化 WebRTC / WebSocket / Web MIDI / Web Bluetooth …
    - 启动多进程架构(renderer/gpu/utility/network)
    - 解析 8000+ 行 user-agent stylesheet

实测数据（ARM Cortex-A7, 512MB）：
  启动时间：8~12s（无预加载）/ 3~5s（预加载但常驻 200MB 内存）
  内存占用：380MB（基础）→ 600MB（中等页面）
  渲染性能：30fps（静态）/ 12fps（含 CSS 动画）

何时选用？
  - 显示 Web 内容（地图/图表库/监控面板已有 H5 版本）
  - 团队只有前端工程师
  但建议：用 Qt WebEngine 嵌入浏览器，而非整个 App 跑在浏览器里
```

**LVGL（MCU 级轻量方案）**：

```
LVGL = Light and Versatile Graphics Library
定位：MCU（如 STM32）上的 GUI，而非 MPU（Linux）

渲染方式：自己实现像素绘制 → 写 framebuffer
优势：
  - 内存占用极低（< 64KB）
  - 不依赖 OS（裸机 STM32 也能跑）
  - 学习曲线低（C 语言）
劣势：
  - 没有 GPU 加速，复杂动画吃力
  - 没有成熟的 IDE / 布局系统 / 国际化
  - 生态小——没有像 Qt 的 20+ 个模块
适用：单片机仪表（单色屏/小彩屏）
```

### 2.3 什么时候选 QML？

```
选 QML 的充分条件（满足 2 个即可）：
  □ 需要流畅动画（≥30fps）
  □ 需要复杂 UI（嵌套布局/多页面/自定义控件）
  □ 需要触摸交互（手势/滑动/长按）
  □ 需要多分辨率适配（同一套 QML 跑 480p / 720p / 1080p）
  □ 团队有 C++ 能力（或愿意学 C++）
  □ 硬件有 GPU 或 Mesa 软渲染（OpenGL ES 2.0+）

不选 QML 的场景：
  ✗ 单色/低分辨率屏幕 + 无动画 → LVGL 或 C++ Widget
  ✗ 纯文本/命令行交互 → ncurses 或无 GUI
  ✗ 团队只有 JS 工程师且不学 C++ → 用 Web 方案但接受性能代价
```

## 3. Qt 框架深度解析

### 3.1 Qt 的核心模块家族

```
Qt 框架（20+ 模块）分四大类：

【基础模块】（必备）
  QtCore      → 信号槽 / 事件循环 / QObject / 线程 / 容器
  QtGui       → 2D 图形 / 字体 / OpenGL / QPainter
  QtWidgets   → QPushButton / QLabel / QMainWindow ...

【Quick 模块】（QML 生态）
  QtQuick     → QML 引擎 + Scene Graph
  QtQuick.Controls  → Button / Slider / Switch ...
  QtQuick.Layouts   → RowLayout / ColumnLayout / GridLayout
  QtQuick.Window    → Window 类型
  QtQuick.Shapes    → ShapePath（矢量绘制）

【多媒体/网络】
  QtMultimedia → 摄像头 / 音频播放
  QtNetwork    → TCP / UDP / HTTP

【嵌入式特有】
  QtSerialPort → 串口通信
  QtSerialBus  → CAN 总线（工业自动化核心）
  QtSvg        → SVG 矢量图渲染
```

> **关键概念——QPA（Qt Platform Abstraction）**：
> QPA 是 Qt 和底层操作系统的桥梁。桌面 Linux 用 XCB/Wayland，
> 嵌入式设备用 EGLFS（Graphics，直接写 framebuffer + OpenGL ES）。
> 这就是为什么 QML 可以在"没有桌面环境"的嵌入式板子上跑。

### 3.4 QPA 插件切换实战

```bash
# 同一个可执行文件，切换不同的渲染后端：

# 桌面模式（带 X11/Wayland）
./myapp                           # 自动选择

# 强制桌面模式
./myapp -platform xcb              # X11 桌面

# 嵌入式模式（无窗口系统，直接写 framebuffer）
./myapp -platform eglfs            # GPU 加速的嵌入式模式

# 纯软件渲染模式（无 GPU，CPU 直接写 /dev/fb0）
./myapp -platform linuxfb          # 纯 CPU 绘制

# 调试/开发模式
./myapp -platform offscreen        # 内存中渲染(不显示)
```

## 4. QML 与其他 UI 方案的本质区别

### 4.1 QML vs HTML5：渲染管线对比

```
HTML5 的渲染（Chromium 为例）：

  HTML → 解析 → DOM Tree → CSS 解析 → Style Resolution
       → Layout Tree (CPU密集) → Layer Tree → Paint
       → Commit → Tiling → Raster → Draw (GPU)
       → 如果你修改了某个元素的 width：
         ├── 重新计算 Layout（所有受影响的子元素）
         ├── 重新 Paint 涉及的图层
         └── 重新 Raster + Composite

QML 的渲染（Qt Quick Scene Graph）：

  QML → 解析 → QObject Tree → 绑定求值 → 同步到 Scene Graph
       → Preprocess (分配FBO) → Batch Render → Swap
       → 如果你修改了某个元素的 width：
         ├── GUI Thread：标记该节点 dirty
         ├── Scene Graph：只更新该节点 + 受影响的兄弟节点（锚布局）
         └── 不需要全局 Layout 重算

核心差异：
  HTML5 的 DOM 是通用文档模型 → Layout 是全局的 → 重排成本高
  QML 的 QObject Tree 是轻量属性树 → 只有锚点/定位器触发局部重算
```

### 4.2 为什么 QML 比 HTML5 更适合嵌入式

```
场景：仪表盘指针每 16ms 更新一次角度

HTML5 + Canvas：
  requestAnimationFrame(() => {
    ctx.clearRect(...);          // 清空上一帧
    ctx.save();                  // 保存状态
    ctx.rotate(angle);          // 应用旋转变换
    ctx.drawImage(needle, ...); // 绘制指针
    ctx.restore();              // 恢复状态
  });
  → 每帧 5 次 JS 调用 → V8 引擎 JIT → GPU 提交一次 draw
  → 在 ARM 设备：JS 执行可能是瓶颈（10~15ms）

QML + Scene Graph：
  RotationAnimation {
    target: needle; property: "rotation"
    from: 0; to: 360; duration: 1000
  }
  → 没有 JS 循环！引擎内置的 Animator 直接操作 Scene Graph transform
  → 每帧只更新一个 transform matrix → 无需 CPU 渲染
  → 在 ARM 设备：< 1ms（全部在 GPU 上完成）
```

### 4.3 QML vs Qt Widget：声明式 vs 命令式

```
Widget 方式（命令式）：
  QPushButton *btn = new QPushButton("点击", this);
  btn->setGeometry(100, 200, 120, 40);
  btn->setStyleSheet("background-color: blue");
  // 每一步显式"做"
  // 当 parent 大小改变时——你需要手动 resize

QML 方式（声明式）：
  Button {
      anchors.centerIn: parent
      width: 120; height: 40
      text: "点击"
      background: Rectangle { color: "blue" }
  }
  // 描述"最终长什么样"，引擎负责计算变化
  // 当 parent 大小改变时——引擎自动重新计算 anchors
```

**代码量对比**（一个 800x480 仪表盘界面）：

| 统计 | Widget | QML |
|---|---|---|
| 总代码行数 | ~1200 行 | ~500 行 |
| 布局代码 | ~200 行（手动 setGeometry） | ~40 行（anchors） |
| 适配代码 | ~100 行（resizeEvent） | 0 行（声明式锚点自动适配） |

## 5. QML 编译管线详解

### 5.1 从 .qml 到 GPU 渲染的完整链路

```
开发时（.qml 文件作为资源）：

  main.qml（文本）
      ↓ QQmlEngine::load()
  词法/语法分析(QmlJS 解析器) → AST
      ↓ QQmlComponent::create()
  实例化 QObject 树
      ↓ QQmlBinding 绑定求值
  QQuickItem 更新属性
      ↓ update() 标记脏节点
  QQuickWindow → 下一帧同步 Scene Graph
      ↓ QSGBatchRenderer
  批处理分组 → 生成 OpenGL/Vulkan 命令
      ↓ glDrawElements()
  GPU 渲染 → framebuffer → 屏幕

生产优化（编译缓存）：

  main.qml
      ↓ qmlcachegen（离线编译）
  main.qmlc（预编译字节码）
      ↓ QQmlEngine 加载
  跳过解析阶段 → 更快启动
```

### 5.2 QQmlApplicationEngine 的各职责

```cpp
// main.cpp —— 每一行背后的机制

int main(int argc, char *argv[]) {
    // 1. QGuiApplication → 初始化 Qt + 事件循环
    QGuiApplication app(argc, argv);

    // 2. QQmlApplicationEngine
    //    - 创建 V4 JS Engine
    //    - 注册 QtQuick 模块的内置类型
    //    - 解析 import 语句
    QQmlApplicationEngine engine;

    // 3. 加载 QML
    //    - 读取 main.qml (从 qrc 或文件)
    //    - 词法/语法分析 → AST
    //    - 类型检查（width 的类型是 int 吗？）
    //    - 创建 QObject 树
    //    - 评估属性绑定（anchors 等）
    engine.load(QUrl("qrc:/main.qml"));

    // 4. 检查加载错误
    if (engine.rootObjects().isEmpty())
        return -1;

    // 5. 进入事件循环
    //    - 等待事件（用户触摸、网络数据...）
    //    - 每帧触发 Scene Graph 渲染
    //    - 直到 app.quit() 或窗口关闭
    return app.exec();
}
```

## 6. 嵌入式平台运行原理

### 6.1 无窗口系统的 Qt Quick 运行链路

```
桌面 Linux 运行（有 X11/Wayland）：

  QML App → Qt Quick → QPA-XCB → X Server → GPU Driver → 屏幕
  问题：启动 X Server 需要 1~2 秒，内存多占用 50MB

嵌入式 Linux 运行（无窗口系统——EGLFS）：

  QML App → Qt Quick → QPA-EGLFS → DRM/KMS → GPU Driver → 屏幕
  优势：
    1. 绕过 X Server → 启动快 1~2 秒
    2. 独占 framebuffer → 无窗口管理器干扰 → 渲染更高效
    3. 内存占用少 50MB+
    4. EGL = Khronos 标准（OpenGL ES 的窗口系统接口）
      EGLFS = EGL + Full Screen（直接接管帧缓冲）

何时用 EGLFS：
  ✅ 全屏独占应用（HMI/仪表盘/广告机）
  ✅ 资源受限设备
  ❌ 需要同时显示多个窗口（选用 Wayland）
```

### 6.2 EGLFS 启动流程

```cpp
// Qt 内部 EGLFS 插件的启动过程（简化）：

// Step 1: 打开 DRM 设备
int fd = open("/dev/dri/card0", O_RDWR);
// DRM = Direct Rendering Manager，内核 GPU 管理框架

// Step 2: 获取显示资源
drmModeRes *resources = drmModeGetResources(fd);
// 获取：分辨率/刷新率/连接状态

// Step 3: 创建 EGL 上下文
EGLDisplay display = eglGetDisplay(EGL_DEFAULT_DISPLAY);
eglInitialize(display, ...);
eglBindAPI(EGL_OPENGL_ES_API);
eglChooseConfig(display, configs, ...);

// Step 4: 创建离屏表面（绑定到 framebuffer）
EGLSurface surface = eglCreateWindowSurface(display, config, nativeWindow, ...);

// Step 5: Qt Quick 的 Scene Graph 开始渲染
// 每帧：eglSwapBuffers() → 显示到屏幕
```

### 6.3 LinuxFB：当没有 GPU 时的纯软件渲染

```
LinuxFB 后端 = 纯 CPU 写 /dev/fb0（无需 GPU 驱动）

适用场景：
  - 老芯片无 GPU（如 Freescale i.MX28）
  - GPU 闭源驱动不可用
  - 嵌入式 Linux 不带 DRM/KMS

运作方式：
  QML 的 Scene Graph → Qt Quick 2D Renderer（纯软件）→ QPainter
  → 逐像素写 framebuffer → 屏幕

性能代价：
  同一套 QML 代码：
    EGLFS（GPU）→ 55fps, CPU 8%
    LinuxFB → 25fps, CPU 85%
```

### 6.4 驱动适配问题排查表

```
| 现象                        | 可能原因                        | 解决方案                          |
|-----------------------------|---------------------------------|-----------------------------------|
| EGLFS 启动失败               | 未加载 GPU 内核驱动              | modprobe 加载 GPU 驱动            |
| 屏幕花屏/撕裂               | DRM 不支持 VSync                | export QT_QPA_EGLFS_SWAPINTERVAL=1|
| 触摸点击位置偏移             | 多点触控驱动/evdev 未正确配置   | 检查 /dev/input/event*           |
| QML 渲染慢（GPU 利用率低）   | 未使用 EGLFS（默认走 XCB）      | export QT_QPA_PLATFORM=eglfs     |
| 画面不更新（黑屏）           | 使用了双缓冲但未 swap            | 检查 eglSwapBuffers() 是否调用   |
```

## 7. QML 技术全景：不只是 UI

### 7.1 QML 生态能力全景

```
┌─────────────── QML 应用 ───────────────┐
│                                         │
│  ┌─────────┐ ┌──────────┐ ┌──────────┐ │

│       │            │             │       │

│  └─────────────────────────────────────┘ │
│                    │                      │
└────────────────────┼──────────────────────┘
                     ▼
             Linux 内核 + 硬件
             (CPU/GPU/串口/CAN/触摸屏)
```

**QML 不只是"画界面"的工具——它可以驱动整个嵌入式终端**：
- GUI：QML 声明式 + Scene Graph GPU 渲染
- 通信：C++ 层处理 CAN 总线 / Modbus / MQTT / 串口
- 存储：QtSql 操作 SQLite（本地）或远程数据库
- 多媒体：摄像头预览、音频播放
- 触控：多点触摸手势识别
- 更新：OTA 远程升级（Qt 程序 + QML 资源）

## 10. 速查表

| 概念 | 一句话解释 |
|---|---|
| QML | 声明式 UI 语言，编译为 C++ 对象树 |
| Qt Quick | QML 的渲染框架（含 Scene Graph） |
| Scene Graph | GPU 优化渲染管线，批处理绘制命令 |
| QPA | 平台抽象层，适配 X11/Wayland/EGLFS/framebuffer |
| EGLFS | 无窗口系统的嵌入式渲染后端（GPU 加速） |
| LinuxFB | 纯 CPU 写 framebuffer（无 GPU 退路） |
| QML Engine | 解析 QML 文本 → 创建 QObject 树 → 管理绑定 |
| V4 Engine | Qt 内嵌 JS 引擎，执行 QML 中的 JavaScript |
| MOC | 元对象编译器，生成信号槽/反射代码 |
| qmlcachegen | QML 预编译工具，跳过运行时解析加速启动 |
| QObject Tree | QML 侧的逻辑对象树（属性/信号） |
| Scene Graph Tree | 渲染侧的节点树（GPU 绘制命令） |
| Draw Call | 一次 GPU 绘制命令提交（越少越快） |
| Batch | 同材质节点打包为一次 Draw Call |
