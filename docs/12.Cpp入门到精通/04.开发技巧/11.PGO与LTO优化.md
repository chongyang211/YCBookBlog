## 01.编译期能做什么

### 1.1 优化等级回顾

GCC/Clang 主要等级：

| 等级 | 关键开关 | 典型加速 | 体积变化 | 调试难度 |
|------|----------|----------|----------|----------|
| `-O0` | 无 | 1× | 1× | 容易 |
| `-O1` | 基本优化 | 1.3× | 0.95× | 容易 |
| `-O2` | 默认生产档 | 1.8× | 1.0× | 中 |
| `-O3` | 激进（向量化、循环展开） | 2.0× | 1.05× | 中 |
| `-Os` | 优先体积 | 1.5× | 0.85× | 中 |
| `-Ofast` | `-O3` + 数学放松 | 2.1× | 1.05× | 难 |

注意 `-Ofast` 会打开 `-ffast-math`，破坏 IEEE 754 严格语义（NaN/Inf 处理、结合律），**不要在金融、科学计算无脑开**。

### 1.2 优化的可见性边界

编译器优化能力强弱，**取决于它能"看见"多少代码**：

```
单文件优化（不开 LTO）
   编译 a.cpp 时，看不到 b.cpp 的函数体
   → b.cpp 的函数永远不能被内联进 a.cpp
   → 只能按"假设它任意可怕"来保守处理

链接时优化（LTO）
   编译每个 .cpp 时存的是 IR（不是机器码）
   链接时把所有 IR 拼起来再优化
   → 真正的"全程序优化"
```

**结论**：相当大一部分代码的"性能损失"，仅仅是因为它跨越了文件边界。LTO 是"零成本"的修补。

### 1.3 PGO 与 LTO 的位置

```
源码 → 编译 → 链接 → 二进制
       ↑       ↑      ↑
      PGO     LTO    BOLT（链接后再优化）
```

三者可以叠加：**PGO + LTO + BOLT** 是 Meta、Google 等公司用于 C++ 服务的"满血组合"，对 ChromeOS、Clang 编译器自身、HHVM 都有公开数据展示 10%-30% 的性能提升。


## 02.LTO 链接时优化

### 2.1 不开 LTO 的代价

```cpp
// foo.cpp
int helper(int x) { return x * 2 + 1; }

// main.cpp
int main(int argc, char**) {
    return helper(argc);
}
```

不开 LTO：`main` 看不见 `helper` 的实现，必须真的 call helper。  
开 LTO：链接器看见 `helper` 体小且只一处调用，直接 inline 后 fold 成 `return argc * 2 + 1`。

不仅是 inline，跨文件的"用不到的全局变量删除""跨翻译单元常量传播""间接调用变直接调用"这些机会都靠 LTO。

### 2.2 工作流程

```
[a.cpp] ──clang -flto── ▶ a.o（含 LLVM bitcode）
[b.cpp] ──clang -flto── ▶ b.o（含 LLVM bitcode）
                              │
                              ▼
                    [linker + LTO plugin]
                              │
                              ▼
              全程序 IR 合并 → 全程序优化 → 链接
                              │
                              ▼
                          [a.out]
```

GCC 用 `-flto`，Clang 用 `-flto`（默认 ThinLTO，加 `-flto=full` 开 Full）。链接时间会显著上升（5-30 分钟级），是要付的代价。

### 2.3 Full LTO vs ThinLTO

| 维度 | Full LTO | ThinLTO |
|------|----------|---------|
| IR 合并 | 全合并到一个模块 | 每个模块独立但有 summary |
| 跨模块 inline | 任意 | 通过 summary 决策 |
| 增量编译 | 改一行全链 | 仅重链涉及的模块 |
| 并行度 | 单线程优化阶段 | 高度并行 |
| 链接时间 | 慢（10-30×） | 较慢（2-4×） |
| 优化强度 | 最强 | 接近 Full LTO（实测 95%） |
| 工程推荐 | 最终 release | 日常 dev / CI |

ThinLTO 是 Chrome、Clang、Rust 默认采用的方案——**接近 Full LTO 的效果，但工程上能接受的链接时间**。


## 03.PGO 三阶段

PGO（Profile-Guided Optimization）的核心思想：**让编译器知道实际运行时的分支频率、调用频率、循环次数**，据此做更聪明的决策。

### 3.1 instrumented PGO

经典三步：

```bash
# 第 1 步：插桩编译
clang++ -O2 -fprofile-generate -o bin_inst app.cpp

# 第 2 步：跑代表性负载
./bin_inst < typical_input.txt

# 第 3 步：用 profile 数据重编译
llvm-profdata merge -o app.profdata default_*.profraw
clang++ -O2 -fprofile-use=app.profdata -o bin app.cpp
```

插桩版本会在每个分支、每个函数入口加计数器，跑完一份 `.profraw`。第三步编译器读着这份"剧本"做优化。

代价：**插桩版本本身慢 30-50%**，且要确保训练负载具有代表性（见 6.1）。

### 3.2 sampling PGO

省掉插桩，直接对**生产环境**的 release 二进制采样：

```bash
# 用 perf 录制
perf record -e br_inst_retired.near_taken:upp -b -o perf.data ./bin
# 转成 LLVM 格式
create_llvm_prof --binary=bin --profile=perf.data --out=app.prof
# 重编译
clang++ -O2 -fprofile-sample-use=app.prof app.cpp
```

优势：

- 不用插桩版本，跑生产负载零干扰
- 持续从生产采集，profile 永远新鲜
- 误差比插桩 PGO 大 5%-10%，但工程上可接受

**Google/Facebook 的 C++ 后端服务普遍走这条路**。

### 3.3 BOLT 二进制重排

BOLT（Binary Optimization and Layout Tool）是 Meta 开源的"链接后再优化"工具：

```
[bin]（已编译完）
  +
[bin 运行时 perf profile]
  ↓ llvm-bolt
[bin.bolt]（更优的代码布局）
```

它做不到 PGO 那种"重新决定 inline"的事，但能：

- **基本块重排**：把 hot path 紧凑放在一起，减少 icache miss
- **函数重排**：相互调用频繁的函数排到相邻地址
- **函数拆分**：把 cold path（错误处理）甩到 .text.cold 段

实测 HHVM、Clang 自身用 BOLT 在 PGO 之上还能再提 5%-10%——**所有提升都来自 icache/iTLB 命中率改善**，不改变任何指令语义。


## 04.PGO 改善了什么

### 4.1 内联决策

不开 PGO，编译器对"是否 inline 一个函数"只能看：

- 函数体大小
- 调用点数
- 静态启发式（叶子函数偏向 inline 等）

开 PGO 后，编译器额外知道：

- 这个 callsite 一年被调了 1 万亿次还是 100 次
- 这个被调用者 99% 时候在 hot path 还是 cold path

```cpp
inline int parse(const char* s) { /* 50 行复杂解析 */ }

void hot_loop() {
    for (auto& msg : messages) parse(msg);   // 1 亿次
}
void debug_dump() {
    parse(g_buf);   // 1 次
}
```

PGO 知道：**为 hot_loop 内联 parse（即便变大也值），对 debug_dump 不内联**——同一个函数在不同 callsite 被区别对待。

### 4.2 块布局重排

```cpp
int f(int x) {
    if (unlikely(x < 0)) {
        // 错误处理 30 行
    }
    return x * 2;   // 99% 走这里
}
```

不开 PGO，"30 行错误处理"和"return x * 2"在二进制里可能交错排列，导致 hot path 频繁跳过 cold 块（iTLB miss 增加）。

PGO 让编译器把 hot 块紧凑排在一起，cold 块统一甩到 `.text.cold`。**等于一个零成本的 `__builtin_expect`**，但更精确。

### 4.3 寄存器分配

寄存器分配是 NP-hard 问题，编译器只能用启发式。如果不知道哪条路径热，**冷路径上的变量可能抢占了热路径上的寄存器**。

PGO 让编译器倾向于把热路径上的变量留在寄存器，冷路径变量该 spill 就 spill。这是隐性收益，但累计起来很可观。

### 4.4 间接调用专门化

```cpp
struct Base { virtual void f() = 0; };
struct A : Base { void f() override; };
struct B : Base { void f() override; };

void process(Base* b) { b->f(); }
```

PGO 发现 99% 时候 `b` 是 `A*`，编译器会把 `b->f()` 改成：

```cpp
if (typeid(*b) == typeid(A)) A_f_inlined(b);  // 专门化的快路径
else b->f();                                   // 兜底虚调用
```

这叫 **devirtualization with speculative inline**——把虚调用变成"99% 直接调用 + 1% 虚调用"，热路径完全没有间接跳转。**对面向对象代码价值极大**。


## 05.attribute 手动提示

不上 PGO 时，可以手工给编译器一些提示。

### 5.1 likely 与 unlikely

C++20 起标准化为属性：

```cpp
if (x < 0) [[unlikely]] {
    handle_error();
}
return x * 2;
```

效果类似 PGO 的块布局，但只能影响一处。**只在确实是极端不平衡（>90/10）的分支上加**，普通分支加了反而误导编译器。

### 5.2 hot 与 cold

```cpp
__attribute__((hot)) void main_loop() { ... }
__attribute__((cold)) void log_error() { ... }
```

`hot` 让函数被放进 `.text.hot`，更激进 inline、更多寄存器。`cold` 反之，且自动 imply `[[unlikely]]` 的调用点。

### 5.3 always_inline 取舍

```cpp
__attribute__((always_inline)) inline int hash(int x) { ... }
```

强制 inline，**绕过编译器启发式**。

何时用：

- 极小的工具函数（accessor、bit 操作）
- 模板化包装层（避免 N 倍代码膨胀失控）
- 跨语言/跨段调用接缝

何时不用：

- 函数体超 20 行，inline 后膨胀代价 > 收益
- 调用点很多，会让 icache 撑爆

**强制 inline 不是"越多越好"，过度使用会让 icache miss 反向恶化性能**。


## 06.工程实施

### 6.1 训练集设计

PGO 的成败取决于训练集是否代表生产负载。三条原则：

| 原则 | 说明 |
|------|------|
| 覆盖主要 code path | 不能只跑 happy path，错误路径会被误认为 cold |
| 时长足够 | 至少跑到关键循环执行 10 万次以上 |
| 数据分布真实 | 用真实流量回放，不要造均匀分布的假数据 |

反例：用 50 个固定请求的 benchmark 当训练集，结果 PGO 把这 50 个请求路径优化到极致，生产真实流量反而变慢——**过拟合**。

### 6.2 CMake 集成

```cmake
option(ENABLE_PGO "" OFF)
option(PGO_PHASE "generate or use" "")

if(ENABLE_PGO)
  if(PGO_PHASE STREQUAL "generate")
    add_compile_options(-fprofile-generate=${CMAKE_BINARY_DIR}/pgo)
    add_link_options(-fprofile-generate=${CMAKE_BINARY_DIR}/pgo)
  elseif(PGO_PHASE STREQUAL "use")
    add_compile_options(-fprofile-use=${CMAKE_SOURCE_DIR}/pgo/merged.profdata)
    add_link_options(-fprofile-use=${CMAKE_SOURCE_DIR}/pgo/merged.profdata)
  endif()
endif()

# LTO（CMake 3.9+）
include(CheckIPOSupported)
check_ipo_supported(RESULT lto_ok)
if(lto_ok)
  set_property(TARGET myapp PROPERTY INTERPROCEDURAL_OPTIMIZATION TRUE)
endif()
```

### 6.3 CI 流水线

成熟实施：

```
nightly_pgo:
  1. build with -fprofile-generate
  2. run benchmark suite (代表性负载，30 分钟级)
  3. llvm-profdata merge
  4. 把 profdata 放到 artifact 仓
  5. 触发 release build with -fprofile-use + LTO
  6. 跑回归测试 + 性能对比
  7. 通过则发布

monthly_bolt:
  1. 用 release bin 部署到 canary
  2. perf record 24h
  3. llvm-bolt 重排
  4. 灰度替换
```


## 07.收益与陷阱

| 项 | 典型收益 | 主要代价 | 风险 |
|----|----------|----------|------|
| `-O2 → -O3` | 0%-15% | 体积+5% | 偶有性能反降 |
| `+ LTO` | 5%-10% | 链接时间×3 | 调试更难 |
| `+ PGO` | 5%-25% | 训练流程复杂 | 训练集不准则反噬 |
| `+ BOLT` | 5%-10% | 部署流程多一步 | 二进制 hash 变 |
| 全部叠加 | 15%-50% | 全部代价之和 | 复杂度高 |

**反向陷阱**：

1. **PGO 失效**：生产数据分布变了（活动期 vs 平时），旧 profile 反而误导。需要**周期性更新 profile**。
2. **LTO 让调试更难**：跨模块内联后，gdb 显示的 backtrace 可能"跳过"中间几层。release 用 `-flto=thin -g -gline-tables-only` 平衡。
3. **`[[likely]]` 滥用**：强制提示后，万一分布翻转就是反向放大损失。**没数据就别加**。
4. **`-Ofast` 破坏数值语义**：浮点比较、NaN 判断会出错。除非你确认整个项目能容忍。
5. **`-march=native` 锁机器**：只在自己的机器跑得更快，部署到老机器直接 SIGILL。**生产用 `-march=x86-64-v3` 这类基线**。


## 08.思考题

1. PGO 优化后某个函数变慢，可能的根因有哪些？怎么排查？
2. ThinLTO 在 100 个文件的项目和 10000 个文件的项目里，性能/链接时间比有什么区别？
3. `[[likely]]` 已经存在，PGO 还有必要吗？哪些场景必须 PGO？
4. BOLT 不能修改任何指令语义，它的优化空间到底有多大？为什么 5%-10% 不算少？
5. 一个程序开 `-O3 -flto -march=native` 后跑得更慢，最常见的两个原因是什么？
