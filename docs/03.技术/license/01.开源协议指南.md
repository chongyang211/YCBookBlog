# 开源协议完全指南

## 一、为什么要了解开源协议

### 1.1 如果你不懂协议，可能会遇到这些问题

- 用了某开源库写商业软件，结果被告侵权
- 自己开源的项目被人拿去闭源卖钱，你却没法治
- 公司代码里不小心引入了 GPL 协议，被迫把整个产品开源
- 想用某库但不知道该遵守什么条件

**一句话**：协议决定了你能做什么、不能做什么、需要遵守什么。

### 1.2 协议的核心三问

任何开源协议本质上都在回答三个问题：

- **能用吗？**（可以商用吗？可以修改吗？可以分发吗？）
- **有什么条件？**（需要署名吗？需要开源吗？需要保留协议吗？）
- **有什么限制？**（不能做什么？专利怎么办？商标怎么办？）

## 二、常见协议速查表

| 协议 | 商用 | 修改 | 分发 | 闭源 | 专利 | 署名 | 传染性 |
|------|:----:|:----:|:----:|:----:|:----:|:----:|:------:|
| MIT | ✅ | ✅ | ✅ | ✅ | ❌ | ✅ | 无 |
| Apache 2.0 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | 无 |
| BSD 2-Clause | ✅ | ✅ | ✅ | ✅ | ❌ | ✅ | 无 |
| BSD 3-Clause | ✅ | ✅ | ✅ | ✅ | ❌ | ✅ | 无 |
| GPL 2.0 | ✅ | ✅ | ✅ | ❌ | ❌ | ✅ | ⚠️ 强 |
| GPL 3.0 | ✅ | ✅ | ✅ | ❌ | ✅ | ✅ | ⚠️ 强 |
| LGPL | ✅ | ✅ | ✅ | ✅ | ❌ | ✅ | ⚠️ 弱 |
| MPL 2.0 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ⚠️ 文件级 |
| Unlicense | ✅ | ✅ | ✅ | ✅ | ❌ | ❌ | 无 |

> **传染性**：如果你的代码使用了该协议的代码，你的代码也必须用相同协议开源。强传染 = 整个项目被传染，弱传染 = 只有修改的部分需要开源。

## 三、主流协议详解

### 3.1 MIT —— 最宽松，最流行

```text
MIT License

Copyright (c) 2025 杨充

Permission is hereby granted, free of charge, to any person obtaining a copy
of this software and associated documentation files (the "Software"), to deal
in the Software without restriction, including without limitation the rights
to use, copy, modify, merge, publish, distribute, sublicense, and/or sell
copies of the Software, and to permit persons to whom the Software is
furnished to do so, subject to the following conditions:
（必须保留上述版权声明和许可声明）
```

**特点**：
- 几乎没有任何限制，最宽松
- 只需要保留版权声明和许可声明
- 不提供专利授权，不承担任何责任

**适合**：
- 希望最大化使用率的个人项目
- 工具库、框架（如 React、Vue、jQuery 都用 MIT）
- 不想管别人怎么用的开源作者

**不适合**：
- 需要专利保护的商业项目
- 不希望别人拿你的代码闭源卖钱的公司

**实际使用**：
```bash
# 1. 在你项目根目录创建 LICENSE 文件
# 2. 填入 MIT 协议文本，替换版权年份和名称
# 3. 在 package.json 中声明
```

```json
{
  "license": "MIT"
}
```

### 3.2 Apache 2.0 —— 含专利保护

```text
Apache License 2.0

- 允许商用、修改、分发、闭源
- 必须保留版权声明、许可声明、修改说明
- 明确授予专利权
- 不能用作者/机构名称做推广
```

**与 MIT 的核心区别**：
- **有专利授权**：贡献者明确授权你使用其专利
- **有修改说明要求**：修改过的文件需要标注
- **有商标保护**：不能未经许可使用项目名称做推广

**适合**：
- 涉及专利技术的项目
- 大公司/基金会主导的项目（如 Kubernetes、Android、Spring）
- 需要专利保护云服务不被"抢走"的场景

**不适合**：
- 纯个人小工具（MIT 更简单）

### 3.3 GPL —— 传染性最强，"开源病毒"

```text
GNU General Public License v2.0 / v3.0

核心要求：如果你使用了 GPL 协议的代码，你的整个项目也
必须以 GPL 协议开源。
```

**GPL v2 vs v3**：

| 特性 | GPL v2 | GPL v3 |
|------|--------|--------|
| 传染性 | 强 | 强 |
| 专利授权 | 隐式 | 显式 |
| Tivoization 防护 | 无 | 有（不允许硬件锁定） |
| 兼容 Apache 2.0 | ❌ | ✅ |

**适合**：
- 坚信软件应该永远自由的理想主义者
- 不想让大公司白嫖的核心基础设施（如 Linux）

**不适合**：
- 商业产品（用了就必须开源整个产品）
- 需要闭源的任何场景

### 3.4 LGPL —— GPL 的"温和版"

```text
GNU Lesser General Public License

允许商业软件通过动态链接库（.dll/.so/.dylib）使用 LGPL 代码，
而不需要将整个软件开源。
```

**关键规则**：
- **动态链接**：可以闭源使用
- **静态链接**：需要开源（因为编译进了你的二进制文件）
- **修改 LGPL 库本身**：修改部分必须开源

**适合**：
- 基础类库希望广泛传播（如 FFmpeg、Qt 的某些版本）
- 既保护核心代码，又允许商业使用

### 3.5 BSD —— 比 MIT 多一条"禁止背书"

```
BSD 2-Clause = MIT 的等价版
BSD 3-Clause = MIT + 禁止用作者名义推广
```

**BSD 3-Clause 的第三条**：未经特别书面许可，不得使用本软件贡献者或机构名称来支持或推广本软件的衍生产品。

**适用场景**：
- 和 MIT 几乎一样
- 如果你在意别人用你的名气推广他们的产品，选 BSD 3-Clause

### 3.6 MPL 2.0 —— 文件级传染

```text
Mozilla Public License 2.0

只传染文件级别：修改了哪个文件，哪个文件需要开源。
项目其他文件可以闭源。
```

**适合**：
- 想在商业产品中混用开源代码
- 比 GPL 宽松，比 MIT 严格

## 四、如何选择协议

```
你的目标是什么？
│
├── 希望最大化使用率，不在乎别人闭源商用
│   → MIT 或 BSD 2-Clause
│
├── 既要宽松，又要有专利保护
│   → Apache 2.0
│
├── 不想让大公司闭源白嫖
│   → GPL v3
│
├── 核心代码保护，但允许商业使用
│   → LGPL 或 MPL 2.0
│
└── 完全放弃所有权利，进入公共领域
    → Unlicense 或 CC0
```

### 选择矩阵

| 你的需求 | 推荐协议 |
|---------|---------|
| 个人小工具，无所谓别人怎么用 | MIT |
| 公司项目，需要专利保护 | Apache 2.0 |
| 基础库，希望商业软件也能用 | MIT / Apache 2.0 |
| 核心产品，不想被竞品闭源复制 | GPL 3.0 |
| 混合开源/闭源项目 | MPL 2.0 |
| 完全放弃版权 | Unlicense |

## 五、实际使用指南

### 5.1 在 GitHub 上添加协议

```bash
# 方式一：创建仓库时选择
# GitHub 创建仓库页面有 "Add a license" 下拉框

# 方式二：手动添加
cd your-project
curl -o LICENSE https://raw.githubusercontent.com/licenses/license-templates/master/templates/mit.txt
# 编辑 LICENSE，替换 [year] 和 [fullname]
```

### 5.2 在 package.json 中声明

```json
{
  "name": "my-project",
  "license": "MIT"
}
```

常用 SPDX 标识符：
```
MIT, Apache-2.0, GPL-2.0-only, GPL-3.0-only,
LGPL-3.0-only, BSD-2-Clause, BSD-3-Clause,
MPL-2.0, Unlicense
```

### 5.3 如何在代码中加协议头

```javascript
// Copyright (c) 2025 杨充
// 
// This source code is licensed under the MIT license found in the
// LICENSE file in the root directory of this source tree.

export function myFunction() {
  // ...
}
```

### 5.4 多协议项目

如果你的项目包含不同协议的代码：

```
my-project/
├── LICENSE              ← 主协议（MIT）
├── NOTICE               ← 说明哪些部分用了其他协议
├── third-party/
│   └── libfoo/           ← 这部分用 Apache 2.0
└── src/
    └── libbar/           ← 这部分用 BSD 3-Clause
```

## 六、常见误区

### 误区一：GitHub 上公开的代码就可以随便用

**错。** 没有 License 的代码默认保留所有权利（All Rights Reserved），你连看都不该看（严格来说）。GitHub 公开 ≠ 开源。

### 误区二：MIT 协议不需要署名

**错。** MIT 要求保留版权声明，也就是要署名。只是不要求你必须开源你的衍生代码。

### 误区三：修改了 GPL 代码但没发布就不违规

**对。** GPL 的传染性只在"分发"时触发。如果只是内部使用，不需要开源。但一旦分发给外部（包括 SaaS 形式），就触发传染。

### 误区四：Apache 2.0 和 GPL v2 兼容

**错。** Apache 2.0 和 GPL v2 不兼容，不能混用。但 Apache 2.0 和 GPL v3 兼容。

### 误区五：用了 MIT 库，被告了作者负责

**错。** 几乎所有开源协议都包含免责声明：**软件按"原样"提供，不提供任何明示或暗示的保证**。出了问题作者不负责。

## 七、企业场景

### 7.1 作为使用者

在引入第三方库之前，用工具扫描依赖的协议：

```bash
# npm 项目
npx license-checker --summary

# 或使用 FOSSA / Snyk / Black Duck 等商业工具
```

### 7.2 作为开源者

选择协议时考虑：
- 你的项目是公司资产还是个人项目（公司项目通常用 Apache 2.0）
- 是否想限制竞品（选 GPL）
- 是否希望被广泛采用（选 MIT）

### 7.3 GPL 的云服务漏洞（AGPL）

标准 GPL 只在你"分发"代码时触发传染。如果通过云服务（SaaS）提供功能，不算"分发"，可以绕过 GPL。

**AGPL (Affero GPL)** 补上了这个漏洞：只要用户通过网络使用你的服务，就触发传染。MongoDB 就在被 AWS 白嫖后从 AGPL 改成了更严格的 SSPL。

## 八、总结

| 原则 | 说明 |
|------|------|
| 默认选 MIT | 90% 的项目用 MIT 就够了 |
| 需要专利保护选 Apache 2.0 | 大公司/涉及专利的核心项目 |
| 不想被闭源白嫖选 GPL | 但会减少使用率 |
| 公共领域选 Unlicense | 完全放弃版权 |
| **没有 License ≠ 开源** | 默认保留所有权利 |
| **保留 LICENSE 文件** | 这是你对使用者的唯一法律文件 |
