## 01.HTTP代理设计

### 1.1 什么是代理

**疑惑**：客户端直接和服务器通信就好了，为什么要在中间加一个代理？

**答疑**：代理（Proxy）是客户端和服务器之间的"中间人"，它接收客户端的请求，转发给服务器，再把响应返回给客户端。代理的价值在于：它可以在转发过程中做很多事情——缓存、过滤、负载均衡、安全审计、加速等。

### 1.2 正向代理

正向代理代表**客户端**向服务器发送请求。服务器不知道真正的客户端是谁。

```
客户端 → [正向代理] → 服务器
         代表客户端       不知道真正的客户端
```

典型场景：
- **翻墙/科学上网**：客户端通过境外代理访问被屏蔽的网站
- **企业网络管控**：所有员工的网络流量经过代理，企业可以审计和过滤
- **隐藏客户端身份**：服务器只能看到代理的IP，看不到客户端真实IP

### 1.3 反向代理

反向代理代表**服务器**接收客户端的请求。客户端不知道真正的服务器是谁。

```
客户端 → [反向代理] → 服务器集群
不知道真正的服务器   代表服务器
```

典型场景：
- **负载均衡**：将请求分发到多台后端服务器
- **SSL终止**：在代理层处理HTTPS加解密，后端服务器只需处理HTTP
- **安全防护**：隐藏真实服务器IP，防止直接攻击
- **缓存加速**：缓存静态资源，减轻后端压力

### 1.4 正向与反向代理对比

| 对比项 | 正向代理 | 反向代理 |
|--------|---------|---------|
| 代表谁 | 客户端 | 服务器 |
| 谁配置 | 客户端配置 | 服务器端配置 |
| 隐藏谁 | 隐藏客户端 | 隐藏服务器 |
| 对谁透明 | 对服务器透明 | 对客户端透明 |
| 典型软件 | Shadowsocks, Squid | Nginx, HAProxy |

### 1.5 代理的典型应用

**Nginx反向代理配置示例**：

```nginx
upstream backend {
    server 192.168.1.10:8080 weight=3;
    server 192.168.1.11:8080 weight=2;
    server 192.168.1.12:8080 weight=1;
}

server {
    listen 80;
    server_name api.example.com;
    
    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

`X-Forwarded-For` 头部记录了请求经过的所有代理IP，格式为：`client, proxy1, proxy2`。这是在多层代理环境中追溯客户端真实IP的标准方式。

**代理服务器的处理流程**：

```text
反向代理处理一个请求的完整流程：

1. 接收客户端请求
   解析HTTP请求，提取Host头部和URL路径

2. 路由匹配
   根据Host和路径匹配配置中的location规则
   确定应该将请求转发到哪个upstream

3. 选择后端服务器
   根据负载均衡算法选择一台后端服务器
   检查该服务器是否健康（健康检查）

4. 转发请求
   建立到后端的TCP连接（或复用已有连接）
   修改必要的请求头（Host, X-Forwarded-For等）
   转发请求体

5. 接收后端响应
   读取后端服务器的响应
   可以缓存响应内容（如果配置了缓存）

6. 返回客户端
   将响应返回给客户端
   记录访问日志
```

**代理的请求头处理**：

代理在转发请求时需要处理多个头部：

| 头部 | 处理方式 | 目的 |
|------|---------|------|
| Host | 可能修改（proxy_set_header Host） | 让后端知道原始域名 |
| X-Real-IP | 添加 | 传递客户端真实IP |
| X-Forwarded-For | 追加 | 记录代理链 |
| X-Forwarded-Proto | 添加 | 传递原始协议（http/https） |
| Connection | 通常删除 | 逐跳头部不应转发 |
| Transfer-Encoding | 可能修改 | 代理可能改变编码方式 |


## 02.HTTP缓存设计

### 2.1 为什么需要缓存

**疑惑**：网络速度已经很快了，为什么还需要缓存？

**答疑**：即使网络速度再快，从服务器获取数据也需要：DNS解析 + TCP握手 + TLS握手 + 请求传输 + 服务器处理 + 响应传输。而缓存可以将数据存在离用户更近的地方（本地磁盘、内存），直接读取，延迟几乎为零。

缓存的收益：
1. **减少带宽消耗**：避免重复传输相同的数据
2. **降低服务器压力**：大量请求被缓存拦截，不到达服务器
3. **加快页面加载**：本地缓存的响应时间约0ms，远快于网络请求

### 2.2 缓存的层级

```
浏览器缓存（内存/磁盘）
    ↓ 未命中
代理缓存（CDN/Nginx/Varnish）
    ↓ 未命中
源服务器（应用缓存/Redis）
    ↓ 未命中
数据库
```

### 2.3 强缓存机制

强缓存：客户端直接使用本地缓存，不向服务器发送任何请求。

**Expires（HTTP/1.0）**：
```http
Expires: Thu, 10 Apr 2025 20:00:00 GMT
```
缺点：依赖客户端和服务器的时钟同步，如果客户端时间不准，缓存行为就不正确。

**Cache-Control（HTTP/1.1，优先级高于Expires）**：
```http
Cache-Control: max-age=3600    # 缓存有效期3600秒
Cache-Control: no-cache        # 每次都需要向服务器验证
Cache-Control: no-store        # 完全不缓存
Cache-Control: public          # 可被任何缓存存储
Cache-Control: private         # 只允许浏览器缓存，不允许CDN等缓存
```

| 指令 | 含义 | 适用场景 |
|------|------|---------|
| max-age=N | 缓存N秒内有效 | 静态资源（CSS/JS/图片） |
| no-cache | 必须先验证才能使用缓存 | 频繁变化的资源 |
| no-store | 禁止任何缓存 | 敏感数据（银行页面） |
| public | 可被共享缓存存储 | CDN可缓存的公共资源 |
| private | 只能被私有缓存存储 | 包含用户个人信息的响应 |
| immutable | 资源永远不变 | 带hash的静态资源 |

**疑惑：no-cache和no-store名字相似，有什么区别？**

**答疑**：
- `no-cache` 并**不是**"不缓存"的意思！它的意思是"可以缓存，但每次使用前必须向服务器验证"（即触发协商缓存）
- `no-store` 才是真正的"不缓存"——不在任何地方存储任何副本
- 这是HTTP缓存中最容易混淆的两个指令

```text
no-cache的工作流程：
  浏览器有缓存 → 但标记了no-cache → 发送条件请求验证
  → 服务器返回304（未变化）→ 使用缓存 ← 节省了传输开销
  → 服务器返回200（变化了）→ 使用新内容

no-store的工作流程：
  浏览器不保存任何副本 → 每次都完整请求 → 每次都传输完整数据
```

### 2.4 协商缓存机制

协商缓存：缓存过期后，客户端向服务器验证资源是否发生变化。如果没变，服务器返回 304 Not Modified（不含响应体），客户端继续使用本地缓存。

**方式一：Last-Modified / If-Modified-Since**

```http
# 首次响应
HTTP/1.1 200 OK
Last-Modified: Wed, 09 Apr 2025 10:00:00 GMT

# 后续请求（缓存过期后）
GET /style.css HTTP/1.1
If-Modified-Since: Wed, 09 Apr 2025 10:00:00 GMT

# 服务器判断：资源未修改
HTTP/1.1 304 Not Modified
```

**方式二：ETag / If-None-Match**

```http
# 首次响应
HTTP/1.1 200 OK
ETag: "abc123def456"

# 后续请求
GET /style.css HTTP/1.1
If-None-Match: "abc123def456"

# 服务器判断：ETag匹配，资源未变
HTTP/1.1 304 Not Modified
```

| 对比项 | Last-Modified | ETag |
|--------|--------------|------|
| 精度 | 秒级（1秒内多次修改无法识别） | 字节级（内容变则ETag变） |
| 性能 | 只需比较时间 | 需要计算hash |
| 优先级 | 低 | 高（ETag优先） |

### 2.5 缓存决策流程

```
浏览器发起请求
    │
    ├── 本地有缓存？
    │    ├── 否 → 向服务器请求资源 → 缓存响应
    │    └── 是 → 强缓存未过期？
    │              ├── 是 → 直接使用缓存（200 from cache）
    │              └── 否 → 发送条件请求（If-Modified-Since / If-None-Match）
    │                        ├── 304 → 使用本地缓存
    │                        └── 200 → 使用新资源，更新缓存
```

**最佳实践（现代前端资源缓存策略）**：

```
HTML文件：       Cache-Control: no-cache（每次验证，保证获取最新版本）
CSS/JS(带hash)：Cache-Control: max-age=31536000, immutable（缓存一年）
API响应：        Cache-Control: no-store 或 private, max-age=0
图片/字体：      Cache-Control: max-age=2592000（缓存30天）
```

核心思想：HTML是入口文件，必须保持最新；CSS/JS文件名包含内容hash（如 `app.a1b2c3.js`），内容变则文件名变，可以安全地设置超长缓存。


## 03.CDN加速原理

### 3.1 CDN是什么

CDN（Content Delivery Network，内容分发网络）是一个由分布在全球各地的边缘节点组成的网络。它将源站的内容缓存到离用户最近的节点上，用户请求时直接从最近的节点获取，大幅减少延迟。

### 3.2 CDN的工作流程

```
用户在北京访问 static.example.com/logo.png

1. DNS解析：static.example.com → CNAME → cdn.example.net
   → CDN智能DNS根据用户IP返回北京节点IP

2. 用户请求北京CDN节点
   ├── 节点有缓存 → 直接返回（命中率通常 > 90%）
   └── 节点无缓存 → 回源
        ├── 向上级CDN节点请求
        └── 最终向源站请求，然后缓存在节点上
```

**CDN的DNS解析过程详解**：

```text
完整的CDN DNS解析链路：

1. 用户浏览器请求 static.example.com
2. 本地DNS → 权威DNS
3. 权威DNS返回 CNAME: static.example.com → cdn.example.net
4. 本地DNS继续解析 cdn.example.net
5. CDN的全局负载均衡DNS（GSLB）收到查询
6. GSLB根据以下信息做决策：
   - 用户IP的地理位置
   - 各CDN节点的健康状况和负载
   - 用户的运营商（电信/联通/移动）
7. GSLB返回最优CDN节点的IP地址
8. 用户直接连接该CDN节点

整个过程对用户完全透明，用户只知道自己访问了 static.example.com
```

### 3.3 CDN回源机制

当CDN边缘节点没有缓存用户请求的资源时，需要向源站获取，这个过程叫"回源"。

回源策略：
- **主动回源**：CDN节点发现缓存过期，主动向源站拉取新资源
- **被动回源**：用户请求触发回源
- **预热推送**：提前将内容推送到CDN节点，避免首次访问的回源延迟

**回源优化设计**：

```text
回源面临的问题和解决方案：

问题1：大量边缘节点同时回源（缓存同时过期）
方案：合并回源（Request Coalescing）
  多个边缘节点对同一资源的回源请求，在中心节点合并为一个
  只向源站发送一次请求，响应共享给所有请求方

问题2：源站故障时的降级
方案：过期缓存兜底（Stale-While-Revalidate）
  当源站不可用时，使用已过期的缓存继续提供服务
  Cache-Control: max-age=3600, stale-while-revalidate=86400
  → 过期后1天内，先返回旧缓存，后台异步更新

问题3：回源带宽过大
方案：范围请求 + 条件请求
  只请求变化的部分（Range）
  或使用If-Modified-Since验证是否需要重新传输
```

CDN缓存遵循HTTP缓存头部（Cache-Control、Expires等），但也允许在CDN控制台自定义缓存规则（如强制缓存某些路径、忽略源站的no-cache指令等）。


## 04.代理协议与头部

### 4.1 Via头部追踪

当请求经过代理时，每个代理都应该在Via头部中添加自己的标识：

```http
Via: 1.1 proxy1.example.com, 1.0 proxy2.example.com

格式：协议版本 代理标识 [, 协议版本 代理标识]
```

Via头部的作用：
1. **追踪请求路径**：知道请求经过了哪些代理
2. **防止循环**：代理发现Via中包含自己的标识，说明请求在循环，应该拒绝
3. **协议版本协商**：了解中间代理支持的HTTP版本

### 4.2 X-Forwarded头部族

在多层代理环境中，服务器需要知道原始客户端的信息。HTTP定义了一系列X-Forwarded头部：

```text
客户端(1.2.3.4) → 代理1(5.6.7.8) → 代理2(9.10.11.12) → 服务器

请求到达服务器时的头部：
X-Forwarded-For: 1.2.3.4, 5.6.7.8
X-Forwarded-Proto: https
X-Forwarded-Host: www.example.com
X-Forwarded-Port: 443
```

| 头部 | 作用 | 示例 |
|------|------|------|
| X-Forwarded-For | 客户端真实IP链 | `1.2.3.4, 5.6.7.8` |
| X-Forwarded-Proto | 原始协议 | `https` |
| X-Forwarded-Host | 原始Host | `www.example.com` |
| X-Real-IP | 客户端真实IP（Nginx专用） | `1.2.3.4` |

**安全注意事项**：

```text
X-Forwarded-For是可以被客户端伪造的！

恶意客户端发送：
X-Forwarded-For: 10.0.0.1（伪造的IP）

经过代理后：
X-Forwarded-For: 10.0.0.1, 恶意客户端真实IP

如果服务器简单地取第一个IP作为客户端IP，就会被欺骗

正确做法：
1. 只信任自己控制的代理添加的IP
2. 从右往左取，跳过已知的代理IP
3. 或使用PROXY Protocol（更安全）
```

### 4.3 PROXY Protocol

PROXY Protocol是HAProxy提出的协议，在TCP连接建立后、发送HTTP数据前，先发送一行客户端信息：

```text
PROXY协议v1格式（文本）：
PROXY TCP4 1.2.3.4 5.6.7.8 12345 80\r\n
       │     │        │      │    │
    协议类型  客户端IP  代理IP  客户端端口 服务端口

随后就是正常的HTTP数据
```

**优势**：
1. 在TCP层传递客户端信息，HTTP头部无法伪造
2. 不仅适用于HTTP，也适用于任何TCP协议
3. 支持TCP和UDP
4. Nginx、HAProxy、AWS ELB等都支持

### 4.4 透明代理设计

**疑惑：有些代理我们完全感知不到它的存在，它是怎么做到的？**

**答疑**：这就是**透明代理（Transparent Proxy）**。它通过网络设备（路由器或交换机）将流量重定向到代理服务器，客户端完全不知道自己经过了代理。

```text
普通代理：
  客户端设置代理地址 → 将请求发给代理 → 代理转发给服务器
  （客户端知道代理的存在）

透明代理：
  客户端发送请求 → 路由器/交换机截获 → 重定向到代理 → 代理转发
  （客户端以为自己直接连接服务器）
```

透明代理的常见应用：
- **企业网络审计**：记录员工的所有网络访问
- **运营商缓存**：缓存热门内容减少骨干网流量
- **内容过滤**：屏蔽不良网站
- **流量劫持**：注入广告（不道德但存在）

**透明代理对HTTPS的影响**：透明代理无法解密HTTPS流量（除非安装了自己的根证书），因此只能基于SNI（Server Name Indication，TLS握手中的明文域名）来做过滤和路由，无法查看或修改具体的请求内容。


## 05.缓存的深度设计

### 5.1 Vary头部与缓存Key

**疑惑：同一个URL，不同的用户可能需要不同的内容（如不同语言、不同编码），缓存如何区分？**

**答疑**：通过 `Vary` 头部。它告诉缓存服务器："对于这个URL，除了URL本身，还要根据这些请求头来区分缓存。"

```http
# 服务器响应
HTTP/1.1 200 OK
Vary: Accept-Encoding, Accept-Language
Content-Encoding: gzip
Content-Language: zh-CN
```

```text
缓存Key的计算：

不使用Vary：
  缓存Key = URL
  所有用户命中同一份缓存

使用 Vary: Accept-Encoding, Accept-Language：
  缓存Key = URL + Accept-Encoding值 + Accept-Language值
  
  GET /page → Accept-Encoding: gzip, Accept-Language: zh-CN  → 缓存A
  GET /page → Accept-Encoding: br, Accept-Language: zh-CN    → 缓存B
  GET /page → Accept-Encoding: gzip, Accept-Language: en-US  → 缓存C
```

**Vary: * 的特殊含义**：表示每个请求都需要不同的响应，实际上等同于禁用缓存。

### 5.2 缓存失效策略

缓存失效是计算机科学中最难的问题之一。常见的缓存失效策略：

```text
缓存失效（Cache Invalidation）策略：

1. 基于TTL的过期
   设置缓存的最大存活时间
   到期后需要重新验证或获取新资源
   实现简单，但无法立即感知资源变化

2. 主动清除（Purge）
   当源站内容变化时，主动通知CDN/缓存清除该资源
   实时性好，但需要额外的通知机制
   
3. 基于版本的缓存（推荐）
   URL中包含版本号或内容hash
   app.v2.js 或 app.abc123.js
   内容变化 = URL变化，旧缓存自然不再被请求
   
4. 标签验证（ETag）
   缓存过期后通过ETag向源站验证是否仍有效
   有效则返回304，无效返回新内容
```

### 5.3 缓存穿透与雪崩

在高并发场景下，缓存系统面临几个经典问题：

```text
1. 缓存穿透（Cache Penetration）
   请求一个一定不存在的数据，每次都穿过缓存直接查库
   
   攻击者请求 /api/users/99999999（不存在的用户）
   → 缓存中没有 → 查数据库 → 数据库也没有 → 不缓存
   → 下次请求同样的，还是穿透到数据库
   
   防御：
   - 缓存空值（key存在但value为null，短TTL）
   - 布隆过滤器（在缓存前快速判断数据是否存在）

2. 缓存击穿（Cache Breakdown）
   某个热点key在过期的瞬间，大量请求同时到来
   
   热门商品的缓存过期 → 瞬间1000个请求同时查数据库
   
   防御：
   - 互斥锁（只有一个请求去查库，其他等待）
   - 热点数据永不过期（后台异步更新）

3. 缓存雪崩（Cache Avalanche）
   大量key同时过期，或缓存服务器宕机
   
   所有缓存在同一时刻过期 → 所有请求涌向数据库 → 数据库崩溃
   
   防御：
   - 过期时间加随机值，避免同时过期
   - 缓存集群高可用（Redis Cluster/Sentinel）
   - 多级缓存（本地缓存 + 分布式缓存）
   - 限流降级（熔断器模式）
```

### 5.4 边缘计算与ESI

**ESI（Edge Side Includes）**是一种在CDN边缘节点上组装页面的技术：

```text
传统方式：
  源站生成完整页面 → CDN缓存整个页面
  问题：页面中有一部分是个性化的（如用户名），导致整个页面无法缓存

ESI方式：
  源站返回带ESI标签的模板 → CDN缓存模板
  CDN在边缘节点组装：静态部分从缓存读取，动态部分实时请求

页面模板：
  <html>
    <header>公共导航栏（缓存30天）</header>
    <esi:include src="/api/user-greeting" />  ← CDN实时请求
    <content>文章内容（缓存1天）</content>
    <footer>公共页脚（缓存30天）</footer>
  </html>
```

现代CDN已经发展到了**边缘计算**的阶段，如Cloudflare Workers、AWS Lambda@Edge等。可以在CDN边缘节点上运行自定义的代码逻辑，不仅仅是缓存和组装，还能做A/B测试、请求重写、身份验证等。


## 06.CDN深度架构

### 6.1 CDN多级缓存架构

CDN不是简单的"一层缓存"，而是多级缓存架构：

```text
CDN多级缓存：

  用户
   │
   ↓
  边缘节点（Edge/PoP）     ← 分布在各城市，离用户最近
   │ 未命中
   ↓
  区域中心节点（Regional）  ← 分布在各省/大区，减少回源
   │ 未命中
   ↓
  中心节点（Origin Shield） ← 通常1~3个，保护源站
   │ 未命中
   ↓
  源站（Origin Server）     ← 客户的真实服务器

优势：
- 边缘节点命中率：90%+
- 真正回到源站的请求：< 5%
- 源站压力大幅减轻
```

**疑惑：为什么不只用一级缓存（边缘节点直接回源）？**

**答疑**：假设有100个边缘节点，某个热门资源的缓存全部过期，如果每个节点都直接回源，源站瞬间收到100个相同请求。而使用多级架构，100个节点先访问区域中心节点（假设10个），10个区域中心节点再访问Origin Shield（1个），Origin Shield只向源站发起1个请求。这就是**回源收敛**的设计。

### 6.2 CDN智能调度

CDN的核心能力之一是将用户请求调度到最优节点：

```text
CDN调度策略：

1. 基于地理位置
   根据用户IP的地理位置，返回最近的CDN节点
   北京用户 → 北京节点
   上海用户 → 上海节点

2. 基于网络质量
   实时探测各节点到用户的网络质量（延迟、丢包率）
   选择网络质量最优的节点

3. 基于负载
   考虑各节点的当前负载（CPU、带宽、连接数）
   避免将请求调度到已过载的节点

4. 基于运营商
   相同运营商优先（电信用户→电信节点）
   跨运营商访问延迟通常较高

5. 动态权重
   综合以上因素，动态计算每个节点的权重
   权重 = f(距离, 延迟, 负载, 运营商匹配度)
```

调度实现方式：
- **DNS调度**：不同用户解析到不同节点IP（最常用）
- **HTTP重定向调度**：302重定向到最优节点
- **Anycast调度**：多个节点共享同一IP，路由协议自动选择最近节点

### 6.3 CDN安全防护

CDN天然是一道安全屏障：

```text
CDN的安全能力：

1. DDoS防护
   CDN有大量节点和带宽，可以吸收DDoS攻击流量
   攻击者需要打垮所有CDN节点才能影响源站
   大型CDN的总带宽可达Tbps级别

2. WAF（Web Application Firewall）
   在CDN边缘节点上部署规则引擎
   过滤SQL注入、XSS、CSRF等常见攻击
   在请求到达源站之前就拦截恶意请求

3. Bot管理
   识别并拦截爬虫、扫描器等自动化工具
   通过JavaScript挑战、验证码、行为分析等手段

4. 源站隐藏
   用户只知道CDN节点的IP，不知道源站的真实IP
   即使CDN节点被攻击，源站也不受影响

5. 速率限制
   限制单IP的请求频率
   防止暴力破解和CC攻击
```

### 6.4 CDN与HTTPS

CDN处理HTTPS需要特殊的设计考量：

```text
CDN的HTTPS部署模式：

模式1：全链路HTTPS
  用户 ──HTTPS──→ CDN边缘节点 ──HTTPS──→ 源站
  最安全，但性能开销较大（双重TLS握手）

模式2：边缘HTTPS + 回源HTTP
  用户 ──HTTPS──→ CDN边缘节点 ──HTTP──→ 源站
  性能好，但CDN到源站之间不加密
  适用于CDN和源站在同一内网的场景

模式3：边缘HTTPS + 回源HTTPS（自签名）
  用户 ──HTTPS──→ CDN边缘节点 ──HTTPS(自签名)──→ 源站
  折中方案，CDN到源站之间加密但不验证证书
```

**CDN与HTTPS的证书管理**：

CDN需要在全球的边缘节点上部署用户的证书。这涉及：
1. **证书分发**：将证书安全地分发到所有节点
2. **SNI支持**：同一IP上托管多个域名的证书
3. **证书自动续期**：与Let's Encrypt等CA集成，自动续期
4. **私钥安全**：在CDN节点上存储私钥的安全性问题

一些CDN服务商（如Cloudflare）提供了**无密钥SSL**（Keyless SSL）方案：CDN节点不存储私钥，TLS握手中需要私钥的操作远程调用客户的密钥服务器完成。这样客户无需将私钥交给CDN。
