# 09.长链接方案的设计

> **本篇定位**：长连接是 IM、推送、直播弹幕、IoT 遥测、在线协作的"血管"。20 篇《实时通信设计原理》讲透了协议层——WebSocket 帧结构、MQTT QoS、TCP 保活；本文则聚焦**工程层**：**海量长连接系统怎么落地？心跳如何错峰？重连如何避免雪崩？接入层如何水平扩展？消息如何跨节点路由？**从一次 800 万设备春节推送雪崩讲起，把长连接系统的每一层地基敲一遍。

## 一、案例引入：800 万设备的春节推送雪崩

### 1.1 事故现场：45 分钟"黄金时段"归零

某 IoT 平台连着 800 万台智能设备（摄像头、门锁、家电），春节营销团队拍板："凌晨 0 点整给全量设备推 `新年快乐`，同步唤起 App 展示大红包！"运维团队测过，接入层单机能扛 50 万连接，16 台机器 800 万连接绰绰有余，值班群里说好"零点整看数据"。

**0:00:00**，推送任务触发。业务侧同步下发 800 万条 `type=greeting` 消息。
**0:00:03**，接入层 CPU 从 20% 飙到 95%。监控告警群开始刷屏：`connection reset by peer` 铺天盖地。
**0:00:10**，客户端首波断连触发。因为设备 SDK 里写死了 `重连间隔=1s`，40% 的设备开始以 1Hz 频率狂敲接入层。
**0:00:30**，TCP 握手洪水彻底压垮 nginx-stream，整个接入层雪崩，**800 万设备全部掉线**。
**0:01:00**，运维手动扩容到 32 台，但设备端"1 秒重连"没有随机抖动，扩容进来的机器**瞬间又被打死**。
**0:15:00**，紧急给客户端下发限流指令（走另一条推送通道通知设备"重连间隔改成 30s"），流量才逐步回落。
**0:45:00**，系统完全恢复，可春晚黄金时段已经过了 45 分钟。

### 1.2 顺藤摸根因：不是"服务器不行"，是"设计不对"

事后复盘，锁定 5 处设计缺陷（每一处都是长连接系统的经典雷区）：

| # | 缺陷 | 直接后果 |
|---|---|---|
| ① | 800 万条消息**同时**下发，未做**推送侧分片** | 接入层瞬间 QPS 冲上 800 万，超出单机 300 倍 |
| ② | 客户端**固定 30s 心跳**，未错峰 | 每 30s 有 800 万个心跳同时到达（心跳风暴） |
| ③ | 重连**固定 1s 间隔无抖动** | 掉线后 1s 集体重连，重连 QPS = 800 万 |
| ④ | 接入层用 `sessionMap` 存本地内存 | 跨机器路由靠**广播**，节点越多广播风暴越猛 |
| ⑤ | 单条消息**无 ACK 无重试** | 掉线期间消息全丢，恢复后用户看到"跳号红包" |

翻代码，客户端 `WebSocketClient.reconnect()` 干干净净就一行 `handler.postDelayed(reconnect, 1000)`。看起来简单，实际上把 800 万台设备变成了"800 万个同步时钟"——这就是 DDoS 攻击最爱的形态，只不过施法者是自己。

### 1.3 七个"为什么"：疑惑清单

同事们围过来，一连串问题砸下：

1. **为什么 HTTP 短连接扛不住 IM/IoT？非要用长连接吗？** —— 长连接的"本质收益"是什么？
2. **心跳到底该多久一次？30 秒？60 秒？还是自适应？** —— 心跳的物理约束是什么？
3. **800 万设备同时重连，如何做到"不打死自己"？** —— 退避+抖动算法为什么必须成对出现？
4. **单机 50 万连接是怎么撑起来的？瓶颈在哪？** —— 文件句柄、epoll、内存各占多少？
5. **接入层 16 台机器，用户 A 发消息给用户 B，B 挂在别的机器上怎么找？** —— 连接路由怎么设计？
6. **同一个账号 PC + 手机 + 平板都在线，消息该怎么发？** —— 多端在线的三种投递语义？
7. **弱网（信号 2 格、地铁、电梯）连接反复抖动，怎么让用户体感"一直在线"？** —— 断线重连如何做到"用户无感"？

这 7 问就是本文的地图。逐个拆解完，第 10 章会用"一台设备的一天"把它们全部串回来。

## 二、架构决策三角：实时性 × 可用性 × 省电

长连接系统本质上是在**三个方向**上做联合最优化：

```
              实时性（延迟 <100ms、消息不丢）
                     ▲
                    /│\
                   / │ \
                  /  │  \
                 / 长 │ 连\
                /  接  │ 系 \
               /   系  │  统 \
              ────────┼──────
          可用性（99.99%）    省电（心跳/流量/CPU）
        + 海量在线（千万级）
```

任何"银弹方案"号称三边全占的，八成隐藏了成本或牺牲了某一维：

* **推 vs 拉**：拉（轮询）省心简单但**实时性归零**——第 18 篇讲透了。
* **心跳 30s vs 300s**：300s 省电但**掉线感知晚**（NAT 超时窗口窗外，收不到 FIN）。
* **同机路由 vs 广播路由**：同机快但**可用性差**（对端挂了消息投不出去）；广播万无一失但**性能崩**（O(N) 消息扇出）。

**架构选择的本质，是选择"要接受哪个代价"，而不是"哪个方案最好"**。IoT 场景省电优先接受秒级延迟；IM 场景实时性优先接受手机稍微费电；股票行情实时+可用双优先直接砸钱堆机器。这一节先立骨架，后续每一章都是这个三角的落子。

## 三、长连接的"存在本质"：短连接扛不住的三件事

问："我用 HTTP + 1 秒轮询也能实现 IM，为什么还要引入长连接？"这是新人最常问的问题，答案要拆成三层。

### 3.1 建连成本：TCP 三次握手 + TLS 四次握手 = 5 RTT

一次 HTTPS 短请求的时间开销：

| 阶段 | 耗时（4G 网络 RTT≈80ms） |
|---|---|
| DNS 解析 | 50~200ms（首次） |
| TCP 三次握手 | 1 RTT = 80ms |
| TLS 1.2 握手 | 2 RTT = 160ms（TLS 1.3 只要 1 RTT） |
| 请求发送+响应 | 1 RTT = 80ms |
| **总计** | **约 400ms + DNS** |

如果 IM 客户端每秒发一条心跳走 HTTPS 短连接：**每秒 400ms 都花在了握手上，真实业务时间只剩 600ms**，还没算电池消耗和后端 CPU。

**长连接把这 4 个 RTT 摊到"一辈子"**——一条 TCP 连接建立一次，可以复用几小时甚至几天，摊销后每条消息的握手开销趋近于 0。这是长连接第一个"存在本质"。

### 3.2 服务端主动推送：短连接根本没有"推"的能力

HTTP 短连接的通信语义是**客户端问、服务端答**。服务端有新消息想推给客户端，只能靠客户端来"取"——要么轮询（第 18 篇讲的方案），要么 SSE/长轮询（受限于 HTTP 1.1 半双工，一个连接同一时刻只能一个方向传数据）。

长连接天生**全双工**：TCP 层不区分谁是客户端谁是服务端，任何一方随时可以发数据。这让"服务端主动通知"变成 O(1) 单条消息，而不是 O(N) 次轮询请求。

### 3.3 有状态：可以做"在线状态"和"会话保持"

短连接是无状态的（每次请求都是新连接、新五元组），"用户在线"这个语义需要**额外用心跳 + 定时器**模拟。长连接天生有状态——**连接活着 = 用户在线**，服务端可以直接根据连接的存在性做"消息投递、离线转存、@ 提醒"等语义决策。

**总结**：长连接不是"更好的 HTTP"，而是**另一种通信原语**。它的本质是"把 5 RTT 建连成本一次性摊销 + 建立双向推送通道 + 保持连接态"。这三件事，短连接一件都做不了。

### 3.4 什么时候不该用长连接？

* **信息类页面**（新闻、商品详情）：无实时推送需求，短连接 + CDN 更省钱。
* **调用型 API**（下单、支付）：请求-响应语义，短连接 + HTTP2 已经够快。
* **极低频交互**（一天几次）：长连接维护成本高于收益。

**记住**：长连接是"通信基础设施"，不是"性能银弹"。用错场景反而是负担。

## 四、协议选型：WebSocket / MQTT / 自研 TCP 怎么选

第 20 篇《实时通信设计原理》已把三种协议的**帧结构、握手、QoS**讲透，本节只讲**工程选型逻辑**。

### 4.1 三种协议的"人设定位"

| 协议 | 定位 | 帧最小开销 | 适合场景 |
|---|---|---|---|
| **WebSocket** | 浏览器友好的通用长连接 | 2~14 字节 | Web IM、协作文档、H5 直播弹幕 |
| **MQTT** | IoT 专用，Broker 中心化 | 2 字节（PUBLISH） | 智能家居、车联网、传感器 |
| **自研 TCP** | 极致性能可控 | 可压至 4~8 字节 | 头部 IM（微信、QQ）、游戏 |

### 4.2 决策链：先看客户端，再看规模

```
是浏览器？ ── 是 ─→ WebSocket（唯一选择，浏览器不能开裸 TCP）
    │
    否
    ↓
是 IoT 设备（低算力/低带宽/需 QoS）？ ── 是 ─→ MQTT（Broker 中心化天然省事）
    │
    否
    ↓
连接规模 > 1000 万 或 消息 QPS > 100 万？
    │
    ├─ 是 ─→ 自研 TCP（微信 mmtls、支付宝 mmtls；Netty + Protobuf）
    │
    └─ 否 ─→ WebSocket（Netty / Socket.IO 生态成熟，够用）
```

### 4.3 案例回看：本文事故场景该选什么？

IoT 平台 800 万设备，明显 MQTT 场景——**为什么当时用了 WebSocket？** 复盘发现是"团队之前 Web IM 用过 WebSocket，惯性延续"。选错协议的代价：

* WebSocket 无 QoS 语义，掉线期间消息**必须应用层重新实现**（该团队没做）→ 消息丢失。
* WebSocket 无 Retained Message（保留消息）→ 新连接上来收不到"上次的最新状态"，用户看到"跳号"。
* WebSocket 无 Will（遗嘱消息）→ 设备异常离线，服务端要等心跳超时才知道，感知慢 30~60 秒。

**教训**：协议选型是"路径依赖"最严重的决策，一旦上线，切换成本极高。宁可前期多花 3 天调研，也不能上线后再改。

## 五、心跳保活：错峰、自适应、双向

心跳是长连接的"心电图"，做错就是全局定时炸弹。案例中"每 30s 全量心跳同时到达"就是典型灾难。

### 5.1 心跳的物理约束：NAT 超时

**为什么必须有心跳？** TCP 连接本身没有"心跳"概念——只要没数据流动，双方 socket 都以为对方还活着。但**中间的 NAT 设备（家用路由器、运营商 NAT、云 LB）会主动回收长期无流量的连接映射表项**：

| 网络环境 | NAT 超时窗口 |
|---|---|
| 家用 Wi-Fi 路由器 | 5~15 分钟 |
| 4G/5G 运营商 NAT | 5 分钟（严格）到 30 分钟 |
| 企业 NAT | 30 分钟 |
| 云 LB（AWS ALB） | 60 秒（默认，可调） |

**结论**：心跳周期必须 **< 最小 NAT 超时时间**，业界经验值是 **270 秒**（低于运营商 5 分钟阈值留 30s 安全边际）。但……

### 5.2 心跳过频的隐性代价

心跳 30s vs 270s，服务端 QPS 差 9 倍：

| 心跳周期 | 100 万在线 QPS | 手机每小时唤醒次数 | 每天流量（每条心跳 30B） |
|---|---|---|---|
| 30s | 33,333 QPS | 120 次 | 259 KB |
| 60s | 16,666 QPS | 60 次 | 129 KB |
| 180s | 5,555 QPS | 20 次 | 43 KB |
| 270s | 3,703 QPS | 13 次 | 29 KB |

**每次心跳都会唤醒手机 Modem 芯片**，Modem 从休眠到通信态耗电≈50mAh。心跳从 30s 改到 270s，手机每天多续航 20~40 分钟。

### 5.3 智能心跳算法：微信的"最优心跳"

固定心跳=laziness。微信 2013 年就给出了**基于 NAT 探测的动态心跳算法**，逻辑是：

```
1. 首次连接：心跳周期从 4.5min 开始探测
2. 心跳成功 → 逐步增大（4.5 → 5 → 5.5 → ...），直到失败
3. 心跳失败 → 记录当前 T 为"NAT 超时上限"，下次周期用 T - 30s
4. 每个网络环境（Wi-Fi、4G、5G）独立学习一套 T
5. 网络切换时重新探测
```

**收益**：微信手机端心跳能拉长到 3~5 分钟，比 30s 省电近 10 倍。**代价**：算法复杂度、探测期间可能"感知晚"。

### 5.4 心跳错峰：把"同步时钟"打散

案例雪崩的直接原因：800 万设备**心跳时钟同步**——都是从"连接建立那一刻"开始每 30s 一次，结果**在自然日尺度上会因为服务器负载调度而聚集**。修复方案：

```java
// 客户端每次心跳时，间隔加入 ±10% 的随机抖动
long jitter = (long)(baseInterval * 0.1 * (Math.random() * 2 - 1));
long nextHeartbeat = baseInterval + jitter;  // 30s * (0.9 ~ 1.1)

// 服务端可以下发全局心跳偏移
// SDK 首次连接时，服务端返回 offset = hash(deviceId) % baseInterval
// 后续心跳时间 = 上次心跳 + baseInterval，天然错峰
```

**效果**：800 万设备的心跳请求在 30s 窗口内均匀分布，服务端峰值 QPS 从瞬时 800 万降到平稳 27 万。**这就是"打散同步时钟"的威力**。

### 5.5 双向心跳：谁应该主动

心跳到底是**客户端 PING、服务端 PONG**，还是**服务端 PING、客户端 PONG**？

* **客户端主动 PING**：简单，服务端只需被动响应；但服务端**无法主动感知**客户端网络异常。
* **服务端主动 PING**：服务端能提前感知，但服务端要维护"下次给每个连接发心跳的时刻"→ **8000 万连接维护 8000 万定时器**，成本高。
* **双向**：客户端主动 PING（保 NAT），服务端定期扫描"最后收到消息时间 > 2×心跳"的连接主动断开（清僵尸连接）。**业界主流选择**。

## 六、断线重连：退避、抖动、上限——数学证明的三件套

重连算法做错，就是"800 万台自研 DDoS"。

### 6.1 三个必须的机制

任何生产级重连都由三个正交机制组合：

1. **指数退避（Exponential Backoff）**：`interval = min(base × 2^n, cap)`
2. **随机抖动（Jitter）**：`interval = interval × (1 + rand(-0.5, 0.5))`
3. **上限截断（Cap）**：`interval ≤ 60s`

### 6.2 数学证明：为什么必须"退避+抖动"缺一不可

假设 N 个客户端同时断连，我们想让服务端**每秒重连 QPS ≤ M**。

**方案 A：固定 1 秒重连**（案例做法）。t=1 时刻 QPS = N。**必炸**。

**方案 B：只指数退避不抖动**。所有客户端都是 `1, 2, 4, 8, 16, ...`。QPS 分布：t=1 时 N，t=3 时 N，t=7 时 N……**峰值 QPS 不变**，只是把炸的时间点推后了。

**方案 C：只随机不退避**。`interval = rand(0, 60s)`。首波 QPS = N/60，看似平稳。但**如果服务端首波扛不住，客户端会不断重连**，每分钟都是 N/60，稳态 QPS = N/60。**规模够大照样炸**。

**方案 D：退避 + 抖动**。第 n 轮重连时刻分布在 `[base·2^(n-1), base·2^n]`。**每一轮的窗口越来越宽**，QPS 随时间指数衰减，且**同一轮内 QPS 均匀分布**。这才是数学上无懈可击的方案。

### 6.3 标准实现（Java 参考）

```java
public class ReconnectStrategy {
    private static final long BASE_INTERVAL = 1000;   // 1s
    private static final long CAP = 60_000;            // 60s
    private static final double JITTER_RATIO = 0.5;    // ±50%
    private int attempts = 0;

    public long nextDelay() {
        // 1. 指数退避
        long backoff = Math.min(BASE_INTERVAL * (1L << Math.min(attempts, 10)), CAP);

        // 2. 抖动：full jitter 或 equal jitter
        // Full jitter：区间 [0, backoff]  ── AWS 推荐，最激进的打散
        long delay = (long)(Math.random() * backoff);

        // 或者 Equal jitter：区间 [backoff/2, backoff] ── 更保守
        // long delay = backoff / 2 + (long)(Math.random() * backoff / 2);

        attempts++;
        return delay;
    }

    public void onConnectSuccess() {
        attempts = 0;  // 关键：成功后必须重置
    }
}
```

**注意点**：
* `attempts` 用 `Math.min(attempts, 10)` 防止 `1L << 63` 溢出。
* 成功连接后**必须重置** `attempts`——否则一次网络抖动会永久拉高退避。
* 首次断连可以不退避（`attempts=0` 时立即重试一次），提升用户体感。

### 6.4 服务端配合：拒绝时告诉客户端"什么时候来"

高级做法是**服务端主动引导重连时机**。当接入层过载时，服务端不是直接断开，而是返回：

```json
{ "action": "reconnect", "after_ms": 30000, "target": "gate-cluster-b.example.com" }
```

客户端遵循 `after_ms` 延迟，甚至**切到另一个集群**。这就是"**优雅降级 + 引流**"，微信、支付宝都在用。

## 七、海量连接的单机极限：C10M 之路

案例中"单机 50 万连接"是什么概念？瓶颈在哪？为什么不是 500 万？

### 7.1 连接的"物理成本"

单条 TCP 连接的资源占用：

| 资源 | 每连接开销 | 100 万连接需要 |
|---|---|---|
| 文件描述符（fd） | 1 个 | 1M（默认 65535 远不够） |
| 内核 socket 缓冲区 | 读缓冲 87KB + 写缓冲 16KB（默认） | 103 GB（吓人） |
| 应用层 Channel 对象 | Netty ≈ 2KB | 2 GB |
| epoll 红黑树节点 | ≈ 200B | 200 MB |
| **合计（理论最小）** | ≈ 105 KB | **≈ 100 GB** |

**结论**：默认参数下，单机 100 万连接需要 100GB 内存——这就是为什么工程实践中"要调参"。

### 7.2 调参"六件套"

```bash
# 1. 系统级 fd 上限（默认 1024，必调）
ulimit -n 2000000
echo "* soft nofile 2000000" >> /etc/security/limits.conf
echo "fs.file-max = 2000000" >> /etc/sysctl.conf

# 2. TCP 缓冲区（默认过大，长连接消息小，可以压缩）
sysctl -w net.ipv4.tcp_rmem="4096 8192 16384"     # 从 87K 压到 16K
sysctl -w net.ipv4.tcp_wmem="4096 8192 16384"

# 3. TIME_WAIT 快速回收（对客户端友好，主动断连场景关键）
sysctl -w net.ipv4.tcp_tw_reuse=1
sysctl -w net.ipv4.tcp_fin_timeout=15

# 4. SYN 队列（防握手洪水，本文案例场景关键）
sysctl -w net.ipv4.tcp_max_syn_backlog=65535
sysctl -w net.core.somaxconn=65535

# 5. 端口范围（服务端不受限，但作代理时关键）
sysctl -w net.ipv4.ip_local_port_range="1024 65535"

# 6. epoll（Linux 天然支持，无需调，但要用 ET 模式）
```

调完后，一台 32C64G 机器可以稳撑 **50~100 万长连接**（连接稀疏、消息量小的场景），这就是"单机 C1M（Concurrent 1 Million）"。

### 7.3 单机 C10M 的进阶技巧

想突破 C1M 到 C10M？靠上面这些还不够，得动 IO 模型：

| 技术 | 收益 | 代价 |
|---|---|---|
| DPDK 用户态协议栈 | 绕过内核，直接操作网卡 | 需要网卡驱动改造、部署复杂 |
| SO_REUSEPORT 多进程 | 单机多进程，每进程独立 accept | 需要业务侧支持连接复制 |
| eBPF 卸载心跳 | 心跳在内核直接响应，不进用户态 | 逻辑受限、调试难 |
| 边缘接入 + 内层聚合 | 接入层只做协议解析，业务层聚合 | 架构复杂度+1 |

**工程实践**：多数公司选择 **单机 C1M + 横向扩展**——比死磕单机 C10M 稳、可运维、可弹性。案例事故的正确解法是"扩容 + 错峰"，不是"堆单机极限"。

## 八、连接路由：跨节点消息投递

单机 100 万连接，1000 万在线就是 10 台机器。**用户 A 挂在 gate-01，用户 B 挂在 gate-05，A 发消息给 B 怎么找到 gate-05？** 这就是长连接系统的**路由核心问题**。

### 8.1 三种主流方案

| 方案 | 原理 | 适用规模 |
|---|---|---|
| **广播** | A 发消息到 gate-01，gate-01 广播给所有 gate，谁上有 B 谁转发 | ≤ 5 台机器 |
| **中心化路由表**（Redis） | gate 启动时把自己的 userId 列表写入 Redis Hash | 万级机器都能撑 |
| **一致性哈希** | userId → gate 直接算出来（客户端连接时就决定挂哪台） | 需要客户端配合 |

案例事故的接入层就是"广播路由"——16 台机器每次消息**广播到 15 台**，QPS 直接翻 15 倍，这也是雪崩的助推剂之一。

### 8.2 中心化路由：Redis 会话表设计

Redis 数据结构：

```
key: session:userId:{123}
value: hash {
    "gateNode": "gate-05",         // 挂在哪台接入机
    "connectionId": "c-abcd1234",  // 具体哪个连接
    "device": "iOS",
    "loginAt": 1706788800,
    "lastActive": 1706790000
}
TTL: 5 分钟（心跳到达时刷新，掉线后 5min 内自动清理）
```

**投递流程**：

```
A 发消息给 B (userId=456)
    ↓
gate-01 收到 → GET session:userId:456
    ↓
返回 {gateNode: "gate-05"}
    ↓
gate-01 通过内网 RPC 转发给 gate-05
    ↓
gate-05 从本地连接表拿到 connection，写入 socket
```

**关键点**：
* **心跳时刷新 TTL**：保证挂载信息鲜活。
* **异常掉线要主动删**：客户端主动 close 或服务端探测到断连时，`DEL session:userId:456`——否则消息会往"僵尸节点"投递。
* **Redis 挂了怎么办**：主从 + 哨兵，或改为 Redis Cluster；同时**内存里缓存热数据**做 fallback。

### 8.3 多接入点：全球部署与就近接入

千万级用户+全球部署，还要考虑：

```
北京用户 ──→ 北京接入集群（低延迟）
上海用户 ──→ 上海接入集群
海外用户 ──→ 新加坡接入集群
    ↓                ↓
   全部注册到中央路由（异地多活的 Redis / etcd）
    ↓
跨集群消息通过 MQ（Kafka）异步转发
```

**如何决定用户挂到哪个集群**？DNS 智能解析 + HTTPDNS + 客户端 ping 测速三层结合。这个话题另开一篇讲，本文不展开。

## 九、消息可靠：ACK、重传、去重、离线

案例中"跳号红包"就是消息不可靠的典型症状。TCP 保证不了应用层可靠——TCP 只保证"数据发到内核缓冲区"，进程崩溃、断连、超时，都会丢消息。

### 9.1 应用层 ACK 协议

参考 MQTT QoS 1 的思路，自己实现应用层 ACK：

```
Server → Client:  PUSH  msgId=1001  content="新年快乐"
                    ↓
Client → Server:  ACK   msgId=1001
                    ↓
Server 收到 ACK 才删除待重传队列
```

**服务端伪代码**：

```java
public void sendMessage(String userId, Message msg) {
    // 1. 存待确认队列（Redis List / MySQL）
    pendingRepo.put(userId, msg.getId(), msg);

    // 2. 通过连接发出去
    Channel channel = connectionManager.get(userId);
    channel.writeAndFlush(msg);

    // 3. 启动定时器：3 秒内没收到 ACK 就重传
    scheduler.schedule(() -> {
        if (pendingRepo.contains(userId, msg.getId())) {
            resend(userId, msg);  // 最多重试 3 次
        }
    }, 3, TimeUnit.SECONDS);
}

public void onAckReceived(String userId, String msgId) {
    pendingRepo.remove(userId, msgId);  // 删除待确认
}
```

### 9.2 客户端去重

有 ACK 就有重复——网络抖动导致 ACK 丢失，服务端重传，客户端会收到相同 msgId。客户端必须做**幂等**：

```java
// 客户端消息去重表（最近 1 万条 msgId，LRU）
private LinkedHashMap<String, Boolean> recentMsgs = new LinkedHashMap<>(10000);

public void onMessageReceived(Message msg) {
    if (recentMsgs.containsKey(msg.getId())) {
        // 重复消息，只回 ACK，不业务处理
        sendAck(msg.getId());
        return;
    }
    recentMsgs.put(msg.getId(), true);
    process(msg);
    sendAck(msg.getId());
}
```

### 9.3 离线消息：连不上也不丢

用户手机没电、进电梯、断网——消息该丢吗？**当然不能**。离线消息通过**"发送时同步落库 + 上线时拉取"**保证：

```
发送时（无论用户在不在线）：
    INSERT INTO offline_msg (user_id, msg_id, content, created_at) VALUES (...)
    AND
    尝试通过连接投递（在线才成功）

用户上线时（连接建立时）：
    SELECT * FROM offline_msg WHERE user_id = ? AND status = 'pending' ORDER BY created_at
    ↓
    批量下发给客户端
    ↓
    客户端 ACK 后 UPDATE 为 'delivered'
```

**注意**：离线消息表要**分片**（第 6 篇讲过），千万级用户不做分片必炸。

### 9.4 消息顺序：单会话内保序

IM 场景中同一个会话（用户 A 和用户 B 之间）的消息**必须严格有序**。做法：

* **服务端下发有序**：给每条消息分配单调递增的 `seqId`（用第 7 篇的号段模式生成）。
* **客户端按 seq 排序**：收到 `seq=1, 3, 2` 时，等待 `seq=2` 到位再显示。
* **拉取兜底**：客户端定期用最大已收到 seq 拉服务端，发现漏了就补拉。

## 十、多端在线与弱网：让"用户"而非"连接"在线

"多端在线"是 IM 的标准需求：手机、PC、平板、Web 都能同时登录。**同一条消息该只发一份还是四份？** 答案是**看语义**。

### 10.1 三种多端策略

| 策略 | 语义 | 场景 |
|---|---|---|
| **全端投递** | 所有在线端都收到 | 微信 IM（消息漫游） |
| **单端投递** | 只发给主设备（最近活跃的） | 部分银行 App（只推手机不推 PC） |
| **智能投递** | PC 活跃时不推手机（避免打扰） | 钉钉、飞书 |

**全端投递**实现：session 表结构改成 List：

```
key: session:userId:{123}
value: hash {
    "iOS": { "gateNode": "gate-01", "connectionId": "..." },
    "Android": { "gateNode": "gate-05", "connectionId": "..." },
    "PC": { "gateNode": "gate-02", "connectionId": "..." }
}
```

投递时遍历所有端，每端独立跟踪 ACK 与已读状态。**已读同步**（一端读了另一端也变已读）通过额外的"已读消息广播"实现。

### 10.2 弱网兼容：让用户感觉"一直在线"

弱网场景（信号 2 格、地铁、电梯）的核心矛盾：**连接会频繁断，但用户不想看到"连接中……"**。解法：

1. **UI 与连接解耦**：客户端 SDK 内部维护连接状态机，UI 层只看"消息队列"是否有积压——**只要发送队列在推进，UI 就显示"在线"**。
2. **发送即入队**：用户点发送时，消息**立刻入本地待发送队列并显示在会话列表**（带"发送中"角标），SDK 异步保证送达。
3. **快速切换网络**：Wi-Fi ↔ 4G 切换时，客户端**不等旧连接超时**，检测到 `NetworkChanged` 立即主动断开 + 重连（业务无感）。
4. **背景保活**：iOS 后台通过 PushKit VoIP、Android 通过厂商推送通道（华为/小米/OPPO Push）**保底**，长连接不通就走 Push。

**结论**：用户体感的"一直在线"，是**多重通道兜底 + 客户端 SDK 智能重连 + UI 状态解耦**共同作用的结果，任何单一手段都不够。

## 十一、反例合集：三类典型翻车

### 11.1 反例一：心跳越频繁越可靠？

**认知误区**：以为心跳越短，掉线感知越快，越可靠。

**真相**：
* 心跳 5 秒 → 手机电池 24 小时干掉，用户卸载 App。
* 心跳 5 秒 → 服务端 QPS 是 60s 的 12 倍，扛不住时反而**主动断连**加剧掉线。

**正确姿势**：智能心跳（微信方案）在网络稳定时拉到 3~5 分钟，网络切换时才快速探测。

### 11.2 反例二：本地 sessionMap 存挂载信息

案例接入层的 `sessionMap` 就是坑：

```java
// 案例中的错误做法
Map<String, Channel> sessionMap = new ConcurrentHashMap<>();

// 消息投递：本地没找到？广播！
public void send(String userId, Message msg) {
    Channel ch = sessionMap.get(userId);
    if (ch != null) {
        ch.writeAndFlush(msg);
    } else {
        // 广播到所有 gate 节点问"userId 在你那吗？"
        broadcastToAllGates(userId, msg);
    }
}
```

16 台机器广播 = 每条消息乘以 15。10 万 QPS 直接放大到 150 万 QPS——**服务器不为业务干活，全用来广播了**。

**正确姿势**：中心化 Redis 会话表（本文 §8.2），O(1) 定位。

### 11.3 反例三：ACK 只是"打日志"

案例中 SDK 收到消息只打了个日志 `Logger.info("received msg")` 就当结束——**没回 ACK**、**没做去重**、**没落本地库**。结果：

* 服务端认为没送达 → 无限重传 → 客户端消息重复展示。
* 客户端崩溃重启 → 内存里的"已收到"记录全丢 → 服务端已删的消息永远丢了。

**正确姿势**：ACK、去重、本地持久化——**三件套一样都不能少**。

### 11.4 反例演进：从事故版到最终版

```
V0（事故版）：
  ✗ WebSocket 协议、无 ACK
  ✗ 固定 30s 心跳、固定 1s 重连
  ✗ 本地 sessionMap 广播路由
  ✗ 800 万消息一次性下发

V1（补救版）：修主要漏洞
  ✓ 加应用层 ACK + 客户端去重
  ✓ 重连改指数退避+抖动
  ✓ Redis 中心化会话表
  ✓ 推送侧改分片下发（每秒 5 万）

V2（工程化版）：可运维、可观测
  ✓ 智能心跳（4~5 分钟）
  ✓ 服务端引导重连（下发 target/after）
  ✓ 离线消息 + 顺序保证
  ✓ 多端在线 + 已读同步

V3（大规模版）：全球+多云
  ✓ 就近接入（DNS + HTTPDNS）
  ✓ 跨地域 MQ 异步转发
  ✓ 单机 C1M + 弹性扩缩
  ✓ 双通道保底（长连接 + 厂商 Push）
```

### 12.3 四条长连接系统的设计哲学

**哲学一：连接是资源，不是实体。** 一条 TCP 连接不代表"用户在线"——用户是**逻辑实体**，连接只是它的**当前化身**。任何设计都要允许连接消失、迁移、重建，不能把业务状态挂在连接对象上。

**哲学二：客户端是不可信的定时器。** 800 万个客户端的定时器天然同步（都从 T0 开始计时），任何"每 X 秒做一次 Y"的行为都会形成尖峰。**永远加抖动、永远做退避、永远设上限**——这是长连接工程师的三大铁律。

**哲学三：可靠不是 TCP 给的。** TCP 只保证字节序不丢；应用层是否可靠，取决于是否有 ACK、重传、去重、持久化。**"因为用了 TCP 所以不会丢消息"是最常见的初学者认知错误**。

**哲学四：用户体感 > 连接状态。** 用户不关心连接是否断了，只关心消息是否送达、发出去有没有回声。UI 层要把连接状态**折叠**到消息队列的进度上——只要队列在推进，用户就觉得"在线"。

### 12.4 长连接系统速查表

| 决策点 | 首选 | 备选 | 禁忌 |
|---|---|---|---|
| 协议 | WebSocket（浏览器）/ MQTT（IoT）/ 自研 TCP（超大规模） | Socket.IO（快速原型） | HTTP 长轮询长期方案 |
| 心跳 | 智能心跳 4~5 分钟 | 固定 60s | 5s 高频心跳 |
| 重连 | 指数退避 + 抖动 + 上限 60s | 服务端引导 target | 固定间隔 1s |
| 路由 | Redis 中心化会话表 | 一致性哈希直连 | 本地 sessionMap 广播 |
| 单机 | Netty + 调参 + C1M | eBPF/DPDK C10M | 死磕单机放弃扩展 |
| 可靠 | ACK + 重传 + 去重 + 持久化 | 只 TCP 可靠 | 依赖"TCP 不会丢包" |
| 多端 | 全端投递 + 已读同步 | 单端投递（简单场景） | 多端各收各的 |
| 弱网 | UI 解耦 + 快速切网 + Push 保底 | 单纯堆重连次数 | 用户看到"离线" |

## 十三、写在最后

长连接系统是"看似简单，实则处处地雷"的工程领域。从 800 万设备雪崩到"一台设备的一天"畅通无阻，中间的每一步——协议选型、心跳错峰、退避抖动、路由中心化、ACK 可靠、多端在线、弱网兼容——都不是"选一个方案"这么简单，而是**"选择接受哪个代价"**的决策。

第 18 篇讲的是"什么时候不用长连接（改用轮询）"，第 20 篇讲的是"长连接的协议内核（WebSocket/MQTT 帧结构）"，本文讲的是"长连接系统的工程骨架"。三篇合起来，你就有了从**协议 → 场景 → 工程**的完整视野。

**当你下次面对"800 万设备零点推送"的场景时，希望你脑子里先冒出的不是"扩容"，而是——"推送分片、心跳错峰、重连抖动、ACK 兜底"**。这，就是长连接系统设计的真正功力。
