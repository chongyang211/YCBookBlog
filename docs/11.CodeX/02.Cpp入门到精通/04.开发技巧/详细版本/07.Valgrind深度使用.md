## 01.Valgrind 是什么

### 1.1 定位与边界

Valgrind 是一套基于"动态二进制翻译（DBI，Dynamic Binary Instrumentation）"的程序分析框架，1999 年由 Julian Seward 开发，最初目标是检测 Memcheck 类内存错误，后来演进为一组工具的集合。

它的定位很清楚：

| 它是 | 它不是 |
|------|--------|
| 运行时插桩工具 | 编译期检查工具（那是 clang-tidy） |
| 模拟 CPU 执行的"沙盒" | 真实硬件执行 |
| 不需要重新编译就能跑（但带 `-g` 才能看到符号） | 零开销（典型 10-50× 慢） |
| 可以检查闭源二进制 | 可以检查内核态代码 |

注意一个常被忽视的边界：**Valgrind 只能跑 Linux/x86_64、AArch64 等少数 ABI**，macOS 支持自 macOS 10.13 后基本停止维护，因此 Apple Silicon 上要查内存问题，**应该选 ASan 而不是 Valgrind**。

### 1.2 与 ASan 的本质区别

很多读者会问：有了 ASan，为什么还要 Valgrind？

| 维度 | ASan（编译期插桩） | Valgrind（运行时翻译） |
|------|--------------------|------------------------|
| 介入时机 | 编译时改写 IR，插入 `__asan_load*` 调用 | 程序启动后翻译每条指令 |
| 是否需重编译 | **必须** `-fsanitize=address` | 不需要，但带 `-g` 才有符号 |
| 性能开销 | 约 2× | 约 10-50× |
| 内存开销 | 影子内存 1:8 | 影子值 1:1，外加 VEX 翻译缓存 |
| 未初始化检测 | 不支持（要用 MSan） | **Memcheck 原生支持** |
| 检测闭源库 | 无法（要重编） | 可以（直接跑） |
| 错误粒度 | 字节级（redzone） | bit 级（影子值） |
| 覆盖范围 | 有插桩的代码 | 包括 libc / 动态库 |

**结论**：写自己的代码用 ASan，调闭源/老二进制/未初始化怀疑用 Valgrind。

### 1.3 工具家族总览

```
Valgrind Core（VEX + 调度器）
   ├── Memcheck     ─ 内存错误（默认工具）
   ├── Cachegrind   ─ Cache/分支预测模拟
   ├── Callgrind    ─ 调用图 + Cachegrind
   ├── Helgrind     ─ POSIX 线程错误
   ├── DRD          ─ 另一种数据竞争检测
   ├── Massif       ─ 堆使用快照
   ├── DHAT         ─ 堆访问模式（Dynamic Heap Analysis Tool）
   └── Lackey/None  ─ 教学/基线
```


## 02.核心架构原理

### 2.1 动态二进制翻译

Valgrind 不是"调试器"，它是**一台运行你程序的虚拟机**。流程如下：

```
原始 ELF 程序
   │ 启动时被 valgrind 接管
   ▼
取一段（Block）原生指令 → 反汇编 → 转成 VEX IR
   │
   ▼
工具（Memcheck 等）对 VEX IR 插桩，比如在 load 前插入"查影子位"
   │
   ▼
VEX IR → 重新编译成原生指令 → 写入 translation cache
   │
   ▼
跳转到 cache 中执行；每个 basic block 第一次都要翻译
```

这就解释了为什么 Valgrind 慢：**每条指令都被翻译过，并且插了若干检查指令**。但也解释了为什么它强大：**任何指令都逃不过它的视野**，包括你没源码的 `libssl.so`。

### 2.2 VEX 中间表示

VEX 把不同 CPU（x86_64/ARM/PPC）的指令统一翻译成无副作用的 SSA 形式：

```
mov rax, [rdi+8]      ─ x86 原始
        ↓ VEX 翻译
t1 = Add64(GET:I64(rdi), 0x8:I64)
t2 = LDle:I64(t1)
PUT(rax) = t2
```

工具拿到的就是这种 IR，对其中的 `LDle` 节点插入 `helper_load_check(t1, 8)` 即可实现"任何 8 字节加载都先查影子值"。**这是 Valgrind 工具能复用的核心原因**：所有工具不直接面对汇编，而是统一的 VEX。

### 2.3 影子值机制

Memcheck 给每个内存字节维护两个 1-bit 元数据：

| 位 | 名称 | 含义 |
|----|------|------|
| A-bit | Addressable | 这个字节是否可访问（已 malloc/未 free） |
| V-bit | Valid（每位一个） | 这个 bit 是否被初始化过 |

注意 V-bit 是**比特级**的，意味着 `int x; x = (x & 0xff) | 0x100;` 这种部分初始化也能精确追踪。这是 ASan 做不到的。

影子值还会"传播"：

```c
int a;            // V-bits 全 1（未初始化）
int b = 5;        // V-bits 全 0（已初始化）
int c = a + b;    // c 的 V-bits = a 的 V-bits（脏值传染）
if (c > 10) ...   // 真正"使用"未初始化值，此时报警
```

这个"延迟报警"很关键：**只在使用未初始化值做出可观测行为时才报错**，避免了"copy 一下就报错"的噪音。


## 03.Memcheck 实战

### 3.1 八类经典报告

```bash
g++ -O0 -g demo.cpp -o demo
valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./demo
```

报告分类：

| 报告类型 | 触发条件 | 典型修复 |
|----------|----------|----------|
| Invalid read/write | 越界、UAF | 检查指针生命周期 |
| Use of uninitialised value | 读了脏值并影响控制流 | 显式初始化 |
| Conditional jump on uninit | 同上，`if(x)` 这类分支 | 同上 |
| Mismatched free/delete | `new[]` 配 `delete` 等 | 修配对 |
| Invalid free | 双重释放、释放栈地址 | 用 RAII |
| Overlap memcpy | `memcpy` src/dst 重叠 | 改 `memmove` |
| Definitely lost | 完全丢失指针的内存 | 修复泄漏 |
| Still reachable | 程序退出时仍有引用 | 通常无害但建议清理 |

### 3.2 未初始化的传播

这是 Memcheck 最闪光的能力。看一段隐蔽的 bug：

```cpp
struct Pkt { uint16_t type; uint16_t len; uint32_t data; };
void send(int fd) {
    Pkt p;
    p.type = 1;
    p.len  = 4;
    // p.data 忘记赋值！
    write(fd, &p, sizeof(p));   // 4 字节脏数据流向网络
}
```

ASan **抓不到这个 bug**（栈变量已合法分配）。Memcheck 配合 `--track-origins=yes` 给出：

```
Syscall param write(buf) points to uninitialised byte(s)
   at 0x...: write (in /lib/...)
   by 0x...: send(int) (demo.cpp:8)
 Uninitialised value was created by a stack allocation
   at 0x...: send(int) (demo.cpp:3)
```

`--track-origins=yes` 会把每个未初始化 bit 的"出生地"记下来，开销翻倍但调试时极有价值。

### 3.3 自定义内存池

如果项目有 arena allocator，Memcheck 默认无法识别"哪些被分配、哪些被释放"。需要手工告诉它：

```cpp
#include <valgrind/memcheck.h>

void* arena_alloc(size_t n) {
    void* p = bump_ptr; bump_ptr += n;
    VALGRIND_MAKE_MEM_UNDEFINED(p, n);   // 标为已分配但未初始化
    VALGRIND_MALLOCLIKE_BLOCK(p, n, 0, 0);
    return p;
}
void arena_free(void* p) {
    VALGRIND_FREELIKE_BLOCK(p, 0);
    VALGRIND_MAKE_MEM_NOACCESS(p, /*size from metadata*/);
}
```

这套宏在不开 Valgrind 时是空操作（编译进去无开销），开了之后能让 Memcheck 像看待 `malloc` 一样看待你的池。


## 04.Callgrind 性能剖析

### 4.1 调用图采集原理

```bash
valgrind --tool=callgrind ./demo
callgrind_annotate callgrind.out.<pid>
```

Callgrind 不像 perf 那样**采样**——它**确定性地记录每条指令**：每个函数进入/退出都打点，每个 basic block 的指令数都计数。**结果可重复**（适合性能回归测试），但**速度慢 20-50×**。

它和 perf 的对比：

| 维度 | perf（采样） | Callgrind（计数） |
|------|--------------|-------------------|
| 数据获取 | 周期性中断采样 | 每条指令计数 |
| 结果稳定性 | 有抖动 | 完全确定 |
| 运行开销 | <5% | 20-50× |
| 真实时间感知 | 有（按 CPU cycle） | 无（按指令数估算） |
| 适合场景 | 生产 profiling | 算法复杂度对比 |

### 4.2 KCachegrind 解读

`callgrind.out` 文件可以用 KCachegrind/QCachegrind 图形化展示：

```
[函数列表]   按 Self / Incl 排序
   │
   ▼ 点开函数
[调用者图]   谁调用了我，各贡献多少 cycle
[被调用图]   我调用了谁，各占多少
[源码视图]   每行指令数和 cache miss
```

工程价值：能直接看到"这个函数被 17 处调用，A 路径贡献了 80%"，比火焰图更适合**算法层调优**。

### 4.3 缓存模拟分析

加 `--cache-sim=yes`（或用 Cachegrind）后，会模拟 L1i/L1d/LL 三级缓存（默认参数自动从 CPU 读取）：

```
==1==   I refs:        4,238,193,012
==1==   I1  misses:        1,320,455
==1==   LLi misses:           45,213
==1==   D refs:        2,113,552,091  (1,401,201,231 rd + 712,350,860 wr)
==1==   D1  misses:       58,304,201
==1==   LLd misses:        1,201,553
```

注意：这是**模拟值**，硬件实际行为受预取器、推测执行影响，但**相对趋势可信**——它适合"我改完之后 cache miss 少了多少"这种 A/B 对比，不适合"绝对延迟"判断。


## 05.Helgrind 与 DRD

### 5.1 锁顺序检测

Helgrind 维护一张"锁的偏序图"：每次成功获取锁，记录"在持有锁 A 时获取了锁 B"。如果之后看到反向顺序（先 B 再 A），立即报警。

```cpp
// 线程 1
pthread_mutex_lock(&a); pthread_mutex_lock(&b);   // a → b
// 线程 2
pthread_mutex_lock(&b); pthread_mutex_lock(&a);   // b → a，死锁隐患
```

Helgrind 会在线程 2 第二次加锁时直接报：`lock order "a before b" violated`。  
注意：**它能在没有真正死锁时就报警**，因为它检测的是"潜在违反"而不是"已经死锁"。这是它比线上死锁排查强的地方。

### 5.2 数据竞争识别

Helgrind 用 happens-before 关系建模：

- `pthread_create` → 子线程开始：HB
- 同一锁的 unlock → 后续 lock：HB
- `cond_signal` → `cond_wait` 返回：HB

如果两次访问同一变量、至少一次是写，且**两者之间没有 HB 链**，就是 race。

### 5.3 与 TSan 的取舍

| 维度 | Helgrind | TSan |
|------|----------|------|
| 实现 | 运行时插桩（Valgrind 工具） | 编译期插桩（`-fsanitize=thread`） |
| 速度 | 50-100× 慢 | 5-15× 慢 |
| 误报 | 较多（`std::atomic` 经常误报） | 很少 |
| 锁顺序违反 | **支持** | 部分支持 |
| 推荐场景 | 没法重编、要查闭源库 | 自有代码、CI 例行检查 |


## 06.Massif 堆剖析

### 6.1 快照采集策略

```bash
valgrind --tool=massif --time-unit=B ./demo
ms_print massif.out.<pid>
```

Massif 会在堆分配/释放时**采样**生成快照（默认 100 个，超过则合并旧的）。`--time-unit=B` 表示以"已分配字节数"为时间轴，比 ms 更适合做**峰值分析**。

### 6.2 峰值定位实战

输出会画出 ASCII 图：

```
    MB
2.000^                                            #
     |                                          ::#
     |                              :@:@:@:@:@:::#:
     |                            :::@:@:@:@:@:::#:
     |
     0 +---------------------------------------------> B
     0                                            123M
```

`#` 标记的就是峰值快照，下方会列出"这一刻每个调用栈贡献了多少"，能精确定位"哪个函数在哪一刻吃了 1.2GB"。这比"最终泄漏多少"更适合**OOM 类问题**。


## 07.工程化使用

### 7.1 性能开销控制

| 优化项 | 效果 | 命令 |
|--------|------|------|
| 关闭 origin tracking | 提速 2× | `--track-origins=no` |
| 减少调用栈深度 | 提速 1.5× | `--num-callers=8`（默认 12）|
| 关闭 leak check | 提速 1.2× | `--leak-check=no` |
| 仅检测特定模块 | 视代码量 | `--trace-children=yes` 配 `--ignore-fn` |

实战经验：在 CI 跑全套约 10× 慢，在本地 debug 单个测试用 `--track-origins=yes` 全开，**目的不同档位不同**。

### 7.2 抑制文件编写

第三方库（OpenSSL、Qt、glibc）经常报已知误报，需要写抑制：

```
{
   openssl_uninit_in_RAND
   Memcheck:Cond
   fun:RAND_*
   ...
}
```

四要素：名字 / 工具:类别 / 调用栈帧 / `...` 通配。运行时加 `--suppressions=my.supp`，定位新建抑制可用 `--gen-suppressions=all`。

### 7.3 接入 CI 的姿势

```yaml
# GitHub Actions 片段
- name: Memcheck
  run: |
    valgrind --error-exitcode=1 --leak-check=full \
             --suppressions=ci/valgrind.supp \
             --gen-suppressions=all \
             ./build/tests
```

`--error-exitcode=1` 让有错误时 CI 失败；`--gen-suppressions=all` 让新增的误报自动打印出抑制片段，方便加到 supp 文件。

**频次建议**：

- 每个 PR：跑 ASan（快），不跑 Valgrind
- nightly：跑 Valgrind + Helgrind 全套
- release 前：跑 Massif 看堆峰值


## 08.局限与误报

| 局限 | 说明 | 应对 |
|------|------|------|
| 不支持 macOS Apple Silicon | 官方维护停滞 | 改用 ASan/leaks |
| 不识别 SIMD/AVX-512 部分指令 | VEX 翻译不全 | `--vex-iropt-level=0` 或换 ASan |
| 不能跑实时性程序 | 慢 50× 破坏时序 | 只用于功能测试 |
| 锁原语依赖 pthread | 自旋锁/atomic 自实现锁报误报 | 用 `ANNOTATE_*` 宏标注 |
| 内存池不识别 | 不知道你的 arena | 用 client request 宏标注 |
| `mmap` 大段内存检测弱 | A-bit 维护开销大 | 关心区域用宏标注 |


## 09.思考题

1. 一个程序在 ASan 下不报错，在 Valgrind Memcheck 下报"Uninitialised value"——可能的原因是什么？
2. Helgrind 给 `std::atomic<int>` 报了 race，怎么判断是不是误报？
3. 为什么 Callgrind 测出来 A 函数占 50%，perf 测出来只占 5%？
4. 一个长跑服务用 Massif 跑发现峰值堆 4GB 而最终 100MB，最有可能的问题是什么？
5. 当 Valgrind 的输出里出现大量 `???`（无符号），最可能漏了哪个编译选项？
