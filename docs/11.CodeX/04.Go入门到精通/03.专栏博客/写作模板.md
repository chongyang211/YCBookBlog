# 00.专栏写作模板

> 本文件用于规范《Go 核心原理深度专栏》全 36 篇的统一写作风格。
> **每写一篇新文章前，请先对照本模板检查骨架是否齐全。**
> 标杆参考：[01.内存模型与栈堆布局](./01.内存模型与布局.md)

---

## 一、文件命名与编号

- 命名格式：`NN.标题（控制在8字内）.md`
- 编号 NN 为两位数，从 01 开始，全册按主题顺序连续编号至 36
- 标题要**"技术名词 + 落点"**，避免空泛（❌ "Go 内存" → ✅ "内存模型与布局"）
- 二级标题、三级标题：**最少 6 字，最多 9 字**，对仗工整

## 二、骨架结构（10 章法）

每篇文章必须包含以下 10 章，缺一不可：

```
1. 案例引入       ← 真实生产事故 / 反直觉代码片段，制造悬念
2. 架构概览       ← 一张总图 + 一段"为什么这么设计"的反向论证
3~9. 核心原理拆解  ← 5~7 章，每章一个独立子主题，章内 4~9 节
   每章至少包含：runtime 源码片段/Plan9 汇编/数据结构图 + "疑惑—论证—结论" 段
10. 综合案例串讲  ← 必须回扣第 1 章的案例，逐一回答第 1 章的所有疑问
   并升华出 3~4 条"设计哲学"
```

**核心原则**：第 1 章埋的所有疑问，第 10 章必须**全部回答**。中间章节是"取证过程"。

## 四、写作风格红线

### 4.1 语气与人称
- 用 **"我们"** 不用 **"你/笔者"**——拉近距离，把读者当同行
- 句末**避免"了哦呢嘛"**等弱化语气词
- 关键结论用 `**加粗**`，给读者打靶子
- 保持技术文章的冷静克制，**不用感叹号**

### 4.2 论证模式（重点）

每个核心原理点必须按 **"疑惑 → 论证 → 结论"** 三段式展开：

```markdown
**疑惑**：为什么 Go 的栈初始只有 2KB，却不担心栈溢出？

**论证**：
1. C 线程栈固定 8MB——100 万个线程需要 8TB 虚拟内存，不现实
2. Go 的 goroutine 栈初始 2KB，通过连续栈机制按需 2× 扩容
3. 每次扩容触发 `morestack` → 分配新栈 → 复制旧栈数据 + 调整指针 → 释放旧栈
4. 从 2KB 扩容到 1GB 只需要约 20 次扩容，每次约 ~1μs
5. 反向验证：分段栈的"热点分裂"在循环中能触发 100 万次分配，连续栈只触发 ~20 次

**结论**：2KB 起步不是"抠门"，是用"一次性复制代价"换"无热点分裂"的设计选择。
```

**严禁**直接抛结论（"goroutine 栈初始 2KB 是因为省内存"）——读者要的是**推导过程**。

### 4.3 图示要求

- 内存布局、数据结构、执行流程必须配 **ASCII 图**（用 Unicode 框线 ┌─┐│└─┘）
- 表格用于横向对比（≥3 项时）
- **每个核心子章节至少有 1 个图或表**
- 架构总图（第 2 章）必须用 ASCII 图给出全景

**ASCII 图示例**（Go 分配器架构）：

```
goroutine 调用 new(T)
        │
        ▼
获取当前 P 的 mcache
        │
        ├── mcache.alloc[spanClass] 有可用 mspan？
        │      ├── 有 → O(1) 拿空闲槽 → 返回
        │      └── 无 → 去 mcentral 拿
        │
        └── mcentral 也没有 → mheap 从 OS mmap → 初始化 mspan → 返回
```

### 4.4 代码片段

Go 代码必须可运行（含 `package main` + `import`）——就算简化了也要能跑：

- **runtime 源码引用**——优先引用真实 runtime 源码（标注文件路径，如 `runtime/malloc.go`），简化时注明"简化"
- **Plan9 汇编**——`go tool compile -S` 产物，标注对应源代码行，关键指令加注释
- 注释用中文，贴在被解释行的**上方或右侧**
- 单段代码 **不超过 50 行**，超过就拆
- 逃逸分析报告用 `go build -gcflags="-m"` 输出，标注关键行

**Go 汇编基本格式**：

```asm
TEXT main.sum(SB), NOSPLIT, $0-16   ; 函数名、标志、栈帧大小
    MOVQ    AX, (SP)                 ; 栈上操作
    CALL    runtime.newobject(SB)    ; 调用 runtime
    RET
```

### 4.5 篇间衔接

- 第 10 章末尾必须过渡：`> **下一篇**：我们已经 XXXX，下一步进入 [NN+1.标题](NN+1.xxx.md)——xxx。`
- 开篇（> 引用块）说明本篇在专栏中的定位

**速查表示例**：

**堆分配四级结构**：

| 层级 | 锁粒度 | 用途 |
|---|---|---|
| mcache | 无锁（per-P） | goroutine 最常用的分配入口 |
| mcentral | 有锁（per-spanClass） | mcache 的补给站 |
| mheap | 全局锁 | OS mmap 页面分配 |
| OS (mmap) | 系统调用 | 真正的虚拟内存申请 |

## 六、Go 专属要求（区别于 C++ 专栏）

| 要求 | 说明 |
|---|---|
| **runtime 源码下沉** | 凡涉及 GC/调度器/内存/栈/通道，必须引用 `runtime/` 下的具体源码文件和函数名（如 `runtime/malloc.go:mallocgc`） |
| **Plan9 汇编佐证** | 关键流程给出 `go tool compile -S` 汇编片段（不是 x86-64 AT&T），标注"栈检查序言""写屏障"等关键位置 |
| **逃逸分析贴原报** | 讨论堆/栈分配时，贴 `go build -gcflags="-m"` 的原始输出，标注 `moved to heap / does not escape` |
| **pprof 实战导向** | 内存/CPU/goroutine 相关的文章必须配 pprof 诊断命令和输出解读 |
| **GODEBUG 可复现** | 涉及 GC/sched 的文章，给出 `GODEBUG=gctrace=1` 或 `GODEBUG=schedtrace=1000` 输出解读 |
| **Go 版本标注** | 行为在版本间有差异时标注引入版本（如"Go 1.3 分段栈→连续栈""Go 1.14 异步抢占""Go 1.22 循环变量语义变化"） |
| **goroutine 视角** | 凡涉及并发/阻塞，必须落到"当前 G 在做什么？G 的状态是什么？" |
| **无 UB 讨论** | Go 是内存安全语言，不需要讨论未定义行为——但需要讨论 "data race"（标注 `go run -race` 检测方式） |
| **单编译器** | Go 只有 gc 编译器（gccgo 不讨论），不涉及多编译器对比 |

## 七、章节自检清单

写完一篇后，逐条对照：

- [ ] 第 1 章是真实生产案例吗？**不是教科书例子**？
- [ ] 第 1 章末尾是否列出了 **5~8 个待解答的疑问**（编号 ①②③...）？
- [ ] 第 2 章是否给了**一张 ASCII 架构总图**？
- [ ] 第 2 章是否有"为什么这么设计"的反向论证？
- [ ] 中间章节每章是否有 **"疑惑—论证—结论"** 段？
- [ ] 中间章节是否每章都至少有 **1 个图或表**？
- [ ] 关键原理处是否引用了 **runtime 源码**（文件+函数名）？
- [ ] 是否有 `go build -gcflags="-m"` 或 `go tool compile -S` 的产物？
- [ ] 第 10.1 节是否**逐条**回答了第 1 章的疑问？
- [ ] 第 10.2 节是否串起本篇 **80% 以上**的知识点？
- [ ] 第 10.3 节是否提炼出可迁移的 **3~4 条设计哲学**？
- [ ] 第 10.4 节是否给出了可截图保存的速查表？
- [ ] 全篇标题是否 ≤8 字且包含"技术名词 + 落点"？
- [ ] **篇尾是否过渡到下一篇**？

## 九、写作前置 SOP

```mermaid
flowchart LR
    A[选题] --> B[找一段真实的生产事故/反直觉代码<br/>作为开篇案例]
    B --> C[列出 5~8 个疑问<br/>这就是中间章节的提纲]
    C --> D[每个疑问对应一个章节<br/>规划 3~9 共 7 章]
    D --> E[画架构总图<br/>确定关键 runtime 源码文件]
    E --> F[按"疑惑→论证→结论"<br/>填充每一节<br/>配源码/汇编/pprof]
    F --> G[第 10 章逐一回扣案例<br/>升华设计哲学]
    G --> H[自检清单逐项过]
    H --> I[更新 README 状态]
```
