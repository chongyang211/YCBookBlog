## 02.贯穿案例

> 本案例贯穿全文：§03 看懂物理本质、§04 用关键路径模型识别瓶颈、§07-§11 拆解各端原理、§17 用实验复盘、§13-§16 给出分层闭环。

### 2.1 案例背景

某头部金融 App，主功能为股票行情 + 交易，用户多在开盘瞬间打开。**启动慢直接影响开盘交易额**：

- **冷启动 P50 4.2 秒、P95 6.8 秒**——用户反馈："开盘前 30 秒打开 App，看到行情已经过了"。
- **业务损失**：开盘 30 秒内的交易额比同行少 35%。
- **应用商店投诉**："启动慢"在投诉前三。
- 与竞品对比：友商 P50 1.5 秒、P95 2.8 秒——**启动慢 2.5-3 倍**。

研发组初步反应："SDK 太多没办法、用户网络慢导致的。"——这是典型的"外因背锅"。

### 2.2 经验派 6 周折腾（典型反面教材）

| 周次 | 假设 | 措施 | 结果 |
|---|---|---|---|
| 第 1-2 周 | Application 太重 | 把 28 个 SDK 全部异步初始化 | 4.2s → 3.9s（-7%）|
| 第 3 周 | 主页太复杂 | 主页拆 4 块按需加载 | 4.2s → 3.7s |
| 第 4 周 | 启动图太大 | 压缩闪屏 50% | **无变化**（图本来就异步加载）|
| 第 5 周 | 网络太慢 | 启动期改 HTTP/2 | -100ms |
| 第 6 周 | 全异步化 | 几乎所有初始化丢线程池 | **反而 +250ms**（异步切换开销）|

**6 周累积投入，启动只从 4.2s 降到 3.7s**。**最后一次"全异步化"反向劣化**让团队彻底困惑。

**复盘**：六周折腾错在"经验主义"——凭直觉找耗电源、不区分关键/非关键、相信"异步就是快"。**真正的根因是"非关键任务挤进关键路径 + 数据请求串行链"，但没人用关键路径模型量化分析过**。

### 2.3 方法派 5 天闭环

**Day 1（[§04 关键路径模型](#04关键路径原理) + [§05 度量](#05度量与采集)）**：

- 用 Tracing 拉出 Application 阶段任务图。
- 关键路径只有 **710ms**（attachBaseContext + 多语言切换 + 安全验证 + 行情连接 + ContentProvider）。
- 但被 980ms 不必要任务挤到 1850ms（28 个 SDK 都跑主线程）。

→ **找到根因 A：非关键任务挤进主线程**。

**Day 2（[§06 决策树](#06归因决策树)）**：

- 首屏数据稳态 1100ms。
- 行情连接初始化在主线程？Yes。
- 行情数据请求在 onResume 后？Yes（串行链）。

→ **找到根因 B：数据请求串行**。

**Day 3-4（[§13-§16 四层治理](#13治理一层路径)）**：

- 第 1 层（路径）：23 个非关键 SDK 推到 IdleHandler。
- 第 2 层（调度）：ContentProvider 整合 + 主进程区分。
- 第 3 层（资源）：类预加载 + Baseline Profiles。
- 第 4 层（架构）：Application 阶段就预热行情长连 + 触发数据请求，让网络往返与 UI 初始化并行。

**Day 5（A/B 灰度）**。

### 2.4 上线效果

| 指标 | 经验派 6 周后 | 方法派 5 天后 | 友商 |
|---|---|---|---|
| 启动 P50（中端机）| 3700ms | **1420ms** | 1500ms |
| 启动 P95（中端机）| 6200ms | **2150ms** | 2800ms |
| Application 阶段时长 | 1850ms | **380ms** | - |
| 首屏数据稳态 | 4200ms | **1400ms** | - |
| 主进程线程数 | 28 | **12** | - |
| **开盘 30s 交易额**（对比同行）| -35% | **+7%** | 基准 |
| 应用商店"启动慢"差评 | 持续 | **降至前 20 外** | - |

**核心洞察**：启动优化 **80% 收益来自找对关键路径**，不是"做更多"。**经验派错在没分清主次**——一开始就该用 Tracing 拉关键路径。**启动优化 = 关键路径瘦身 + 非关键任务移出，不是堆并发**。

## 03.启动本质定义

### 3.1 启动的物理本质

> **启动 = 把"应用从无到有"过程中的所有必要工作，按依赖关系串行 / 并行地执行，直到用户能看到并交互**。

三个不可商量的物理约束：

**约束一：启动是有"必要工作集"的**

启动不是单一任务，而是一个**任务集 T = {t₁, t₂, ..., tₙ}**，每个任务做一件事（如加载类、初始化 SDK、读配置、建立网络连接、渲染首帧）。任务集分两类：

- **必要任务（critical）**：直接产出"用户可见可交互"的状态。
- **可选任务（deferrable）**：当下不需要，但传统实现中放在启动期（如打点埋点、广告拉取、后台同步）。

启动优化的第一原则：**严格区分必要与可选，把可选的全部移出启动期**。

**约束二：任务之间存在依赖图**

任务集不是并行池，而是**有向无环图（DAG）**：

```
   t1 (读本地配置) ──┐
                     ├──▶ t4 (初始化 SDK)
   t2 (初始化日志) ──┘
                     ├──▶ t5 (建立网络) ──▶ t7 (拉取首屏数据) ──▶ t8 (渲染首屏)
   t3 (准备主线程) ──┘
                     └──▶ t6 (初始化 UI 框架) ──┘
```

依赖图决定了"哪些任务必须串行""哪些可以并行"。

**约束三：启动有"开始"和"结束"两个明确边界**

- 开始：用户点击图标 / 系统拉起应用。
- 结束：用户能看到首屏并能交互（TTFD）。

这两个边界是物理可观测的（屏幕变化 + 输入响应），所以启动是个"有头有尾的 epoch"问题，可以精确度量。

> **探索性思考**：为什么启动慢比"卡顿慢"更难治？
> 卡顿是"运行中某一帧超预算"——可以孤立分析。启动是"几百个任务 + 复杂依赖"——优化任何单点都不一定让整体快。**启动优化的核心难点不是"算法"，而是"系统观"**——理解任务之间的相互作用、关键路径的演变、并发的边际收益。这就是为什么 [§02 案例](#02贯穿案例) 经验派"动了很多东西"却没用——他们一直在调点（动作），没在调系统（路径）。

### 3.2 启动的现象与代价

启动慢是用户对一款应用的"第一印象"，且印象一旦形成极难翻转：

- **首次冷启动慢**：用户感知"是不是没装好？"
- **每次启动黑屏 / 白屏**：用户怀疑应用故障。
- **可见但点不动（TTID 已到但 TTFD 未到）**：用户操作无响应，主观体验比慢更差。
- **启动后不稳定（卡顿、ANR、闪退）**：往往与启动期的"过度异步并发"或"线程争用"相关。

**业务代价（行业实测数据）**：

- Google Play Console 数据：冷启动 P50 > 5s 的应用，次日留存比 < 2s 的低 **15–20%**。
- 头部 App 数据：每减少 1 秒冷启动时长，次日留存 +1–3%、首屏转化率 +2–5%。
- iOS 系统在冷启动 > 20s 时直接 watchdog 杀死进程，是硬约束。
- Web：Google Web Vitals 把 LCP > 4s 标记为 *Poor*，影响 SEO。
- 嵌入式车机：启动 > 30s 在某些国家会触发安规警告。

### 3.3 度量准则

按 [`卷零·02 §3 USE/RED/APDEX`](../00.公共方法论/02.跨平台指标体系.md) 的统一指标体系，启动属于"一次性请求"类，主要用 RED + APDEX：

**请求视角（RED）**：

| 指标 | 含义 | 阈值参考 |
|---|---|---|
| TTID（Time To Initial Display） | 首帧可见时间 | 冷启 < 2s / 热启 < 0.5s |
| TTFD（Time To Full Display） | 首屏完整可交互 | 冷启 < 3s / 热启 < 1s |
| 启动失败率（Errors） | 启动崩溃 / 超时占比 | < 0.1% |
| 启动期卡顿率 | 启动期间帧时长 > 16.67ms 的比例 | < 5% |

**用户感知（APDEX）**：

- *Satisfied*：TTFD < T_target（如 1.5s）
- *Tolerating*：T_target ≤ TTFD < 4 × T_target
- *Frustrated*：TTFD ≥ 4 × T_target

**关键约定**：

- **TTID ≠ TTFD**：用户看到首帧但内容未加载完，主观仍是"卡"。优化必须并重，**TTFD 才是用户感知的"启动完成"**。
- 必须使用 P50 + P99 双轨度量。P99 代表"长尾用户体验"，往往揭示低端机 / 弱网下的真实痛点。

### 3.4 行业基准与目标

| 平台 | TTID 良好 | TTID 合格 | TTFD 良好 | TTFD 合格 |
|---|---|---|---|---|
| Android（中端机）| < 1.5s | < 2.5s | < 2.5s | < 4s |
| iOS | < 1.0s | < 2.0s | < 2.0s | < 3s |
| Web（4G）| LCP < 2.5s | LCP < 4s | TTI < 3.8s | TTI < 7.3s |
| 嵌入式 HMI | < 5s | < 10s | < 8s | < 15s |

### 3.5 8 个反直觉问题

带着这些问题阅读：

1. 减少启动任务数一定能让启动更快吗？
2. 把所有任务都改异步，启动是否就能快到极致？
3. CPU 利用率不饱和但启动慢，是哪里的问题？
4. 多线程并发启动，开多少线程最快？
5. MultiDex 一定会让启动变慢吗？慢多少？
6. SharedPreferences / NSUserDefaults 在启动期为什么这么慢？
7. 异步化任务之后总耗时是不是必然减少？
8. 8 核 CPU 启动时为什么有时只用了 2 核？

> ▶▶ **回扣 [§02 案例](#02贯穿案例)**：原团队用单一数字"4.2 秒"描述启动——这掩盖了真相。**重定义为分阶段**：
>
> | 阶段 | 时间 | 状态 |
> |---|---|---|
> | attachBaseContext → Application.onCreate 完成 | 0 → 1850ms | ❌ 超出预算 4× |
> | Application.onCreate → MainActivity.onCreate | 1850 → 2400ms | ⚠️ 略慢 |
> | MainActivity.onCreate → 首帧 | 2400 → 3100ms | ⚠️ 略慢 |
> | 首帧 → 首屏数据稳态（行情数据可见） | 3100 → 4200ms | ❌ 超出预算 2× |
>
> 单一"4.2s"无法定位优化方向；分阶段后立刻看出 **Application 阶段（44%）+ 首屏数据阶段（26%）是双瓶颈**。

## 04.关键路径原理

> 本节回答四个根本问题：**①为什么 DAG 总耗时 = 最长路径？②Amdahl 定律的启动版本是什么？③异步化的硬上限怎么算？④为什么 race-to-idle 在启动也成立？**

### 4.1 关键路径模型

DAG 的总耗时不是所有任务耗时之和，而是**最长路径的耗时**（关键路径，Critical Path）。这是 PERT/CPM 项目管理理论的核心，同样适用于启动：

```
   t1 (10ms) ──┐
                ├─▶ t4 (50ms) ──▶ t8 (100ms)  关键路径：t2 → t4 → t8 = 170ms
   t2 (20ms) ──┘
                ├─▶ t5 (30ms) ──▶ t7 (40ms)
   t3 (5ms)  ──┘                              非关键路径：t3 → t5 → t7 = 75ms 实际并行
```

**关键路径的四条法则**（启动优化的"金科玉律"）：

1. **法则一**：总启动时长 = 关键路径耗时（不是任务总和）。
2. **法则二**：缩短非关键路径上的任务**对总耗时无收益**（除非它升级成新关键路径）。
3. **法则三**：缩短关键路径任务，最多缩短到"次关键路径"长度（之后次关键路径成为新瓶颈）。
4. **法则四**：把任务从关键路径移除（异步 / 延迟）的收益与缩短它一样有效，但成本通常更低。

这就是为什么"看似减少了 20 个启动任务，启动时长只少了 100ms"—— 因为只有关键路径上的任务才贡献。

> **探索性思考**：为什么"次关键路径"是个隐藏陷阱？
> 当你把 A 关键路径优化掉之后，B 路径自动升级成新关键路径——**这意味着收益是"阶梯式"而不是线性**。比如优化前关键路径 1850ms、次关键路径 1100ms，把关键路径砍到 600ms 后实际总耗时不是 600ms 而是 1100ms（次关键路径接管）。**所以"优化前必须看次关键路径多长"——它定义了你的天花板**。

### 4.2 Amdahl 定律的启动版本

设启动可异步化的部分占比为 P（0 ≤ P ≤ 1），无法异步化的串行部分占比为 1 − P，并行加速比为 N，则：

```
   启动加速比 = 1 / [(1 − P) + P/N]

   即使 P = 0.8，N = ∞：加速比上限 = 1 / 0.2 = 5×
```

**这就是反直觉问题 ② 的答案**：即使所有可异步化任务都开无限线程并行，启动加速也存在硬上限。要突破这个上限，必须**减少串行部分**（缩短或删除关键路径任务），而不是单纯堆并发。

| P | S_max | 含义 |
|---|---|---|
| 0.5 | 2× | 即使无限并行最多快一倍 |
| 0.7 | 3.3× | |
| 0.8 | 5× | |
| 0.9 | 10× | |
| 0.95 | 20× | |

**关键洞察**：要让启动加速 10×，可异步化部分必须 ≥ 90%。**实际启动中能异步化的占比通常 50–70%**，所以加速上限通常 2–3×。

> **探索性思考**：为什么 P 在工程中很少超过 0.8？
> 因为"必须串行"的部分往往不是"代码不会写"，而是**业务依赖图本身决定的**——网络要先于数据请求、UI 框架要先于 Activity、安全 SDK 要先于其他网络。这些是"语义依赖"，不是"实现依赖"。**P 的天花板由系统架构决定，不是工程能力**。要把 P 提到 0.9，必须重构架构（如懒加载、按需初始化、移除前置依赖），不是堆线程。

### 4.3 关键路径上的三类典型问题

把"关键路径阻塞"映射到具体根因，可以分成三类：

```
  关键路径耗时 = 关键任务自身耗时 + 任务间等待 + 资源竞争

  ┌──────────────────────────────────────┐
  │ A. 任务自身慢                          │
  │    特征：单个任务 CPU 高 / IO 长       │
  │    根因：算法差、磁盘 IO、网络等        │
  ├──────────────────────────────────────┤
  │ B. 任务依赖链长                        │
  │    特征：单任务都不慢，但串成长链路    │
  │    根因：依赖图设计不合理              │
  ├──────────────────────────────────────┤
  │ C. 资源竞争 / 调度等待                 │
  │    特征：CPU 不饱和但任务慢            │
  │    根因：锁、Binder、磁盘竞争、线程不够 │
  └──────────────────────────────────────┘
```

> **探索性思考**：为什么 C 类问题最难调？
> 因为 **CPU 占用看起来"很正常"**——总占用 30%、单核也不饱和，但启动就是慢。根因是"等待"——线程在等锁、等 Binder、等磁盘。**这种问题在 Trace 上呈现"白条"**（off-CPU 状态）。所以启动调优必须看"实际跑了多少 vs 应该跑多少"——Trace 工具的核心价值。

### 4.4 跨平台同构原理

不同平台的启动看起来差异巨大（Android Zygote fork → Application → Activity；iOS dyld → main → AppDelegate；Web HTML 解析 → JS 执行 → 首次渲染；嵌入式 init → 服务初始化 → UI 主循环），但**抽象成"任务依赖图 + 关键路径"后完全同构**：

```
  通用启动模型：

   [系统级初始化] ──▶ [运行时启动] ──▶ [应用初始化] ──▶ [首屏渲染] ──▶ 可交互
        │                  │                │                │
        进程创建            VM/解释器           业务对象            用户可见
```

每个平台都必须有：

| 抽象阶段 | 解决什么问题 |
|---|---|
| 进程 / 上下文创建 | OS 内核为应用分配资源（地址空间、文件描述符、线程） |
| 运行时启动 | VM / 解释器 / 浏览器引擎初始化（GC、JIT、解析器） |
| 应用初始化 | Application 创建、SDK 初始化、配置加载 |
| 首页准备 | 数据加载、UI 框架初始化、首帧渲染 |

**正因为它们都长这个样子，启动的物理本质也是同一个**：

> **启动慢不是平台的特性，是"任务集 + 依赖图 + 串行预算"这个组合的必然产物。**

**跨平台启动阶段对照**

| 抽象阶段 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 进程创建 | Zygote fork | exec / dyld 加载 | 浏览器进程创建 Tab | OS 创建任务 |
| 运行时启动 | ART 加载 dex | dyld 链接 + libObjc 启动 | V8 / JS 引擎初始化 | RTOS 调度 |
| 应用初始化 | Application.onCreate | UIApplication 初始化 + AppDelegate | DOMContentLoaded | main() / app_init |
| 首页准备 | Activity.onCreate → onResume | UIViewController.viewDidLoad → viewWillAppear | window.load | UI 任务循环 |
| 可交互完成 | Activity 首帧绘制完成 | viewDidAppear + 主 RunLoop 空闲 | TTI / window.onload + INP | UI 主循环就绪 |

### 4.5 平台差异点矩阵

同构之下，各平台的实现差异主要集中在以下维度：

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 进程模型 | Zygote fork（共享 ART） | 每次 fork+exec | 浏览器子进程 | 单进程 / 任务 |
| 运行时 | ART（AOT + JIT） | Native + ObjC RT | V8 / SpiderMonkey | C/C++ 直接执行 |
| 类加载策略 | Multi-DEX + ART 优化 | dylib / framework | JS Bundle 解析 | 静态链接 |
| 首屏可见时机 | 首帧渲染完成 | viewDidAppear | LCP | UI 主循环就绪 |
| 系统级阻塞 | ContentProvider onCreate 串行 | dyld 链接慢 | DOM 解析阻塞 | 设备 init |
| 优化手段 | App Startup / 任务调度 SDK | Static Init 延迟 / dyld3 | Code Splitting / SSR | 优先级 + DMA |

> 后续 §07-§11 各端全链路章节会逐一展开。

## 05.度量与采集

### 5.1 三类采集方案的本质

所有平台的启动采集方案，本质上只有 3 类，区别在于**在启动生命周期的哪一段下钩子**：

```
   进程开始 ──▶ 运行时就绪 ──▶ Application 创建 ──▶ Activity 创建 ──▶ 首帧 ──▶ 完整可交互
        │              │               │                  │              │            │
        ▼              ▼               ▼                  ▼              ▼            ▼
                       ① 应用埋点（手动打点 / 自动插桩）
                                                                          ② 系统级 API
                                              ③ 端到端外部测量（高速摄像 + LED 触发）
```

**① 应用埋点（手动打点 / 自动插桩）**

- **核心原理**：在启动关键路径上的多个代码点埋下时间戳，结束后差值计算各阶段耗时。
- **物理本质**：启动是一个有清晰阶段的进程，**在每个阶段边界放一个度量哨兵**，事后差值即得各阶段耗时。
- **局限根源**：只能从 `Application.attachBaseContext` 开始打点，看不到"图标点击 → fork → dyld → ART 初始化"——这段在中低端机上可能占 1–2s。
- **适用场景**：自家代码内部精细监控，配合插桩可获得 ~50 行代码级颗粒度。

**② 系统级 API（reportFullyDrawn / MetricKit / Performance API）**

- **核心原理**：操作系统知道"进程从被创建到 Application/UI 就绪"的完整时序，提供专门 API 直接告诉你各阶段耗时。
- **物理本质**：应用层无法看到"进程创建 → 运行时启动"这段，但 OS 自己看得到，把这部分数据通过 API 暴露给你。
- **局限根源**：API 颗粒度由系统决定（"Application 初始化"打包成一个数字）；新版本系统才支持。
- **适用场景**：作为应用埋点的"前置补全"，两者必须配合使用。

| 平台 | API | 暴露的数据 |
|---|---|---|
| Android | `Activity.reportFullyDrawn()` 配合 logcat `Displayed` | TTID + TTFD |
| Android 12+ | `ApplicationStartInfo` | 进程级启动时序（含 cold/warm/hot 标记） |
| iOS | `MetricKit MXAppLaunchMetric` | dyld / Process Init / App Init / UI Init / 首帧分阶段 |
| Web | `Performance.timing` / `PerformanceNavigationTiming` | navigationStart / DOMContentLoaded / loadEventEnd |
| Web | `LCP` / `FCP` / `INP` | 用户感知关键时刻 |

**③ 端到端外部测量（高速摄像 / 屏幕直采）**

- **核心原理**：用外部设备拍下"用户点击图标 → 屏幕显示首屏"全过程，逐帧分析得出物理端到端延迟。
- **物理本质**：软件指标永远是"内部视角"，最终用户体验只能由"外部视角"验证。
- **局限根源**：门槛高（外部设备 + 自动化分析 + 固定光照）；不能线上，仅实验室。
- **适用场景**：金标准基线测试 + 校准方案 ②/① 的偏差。

**三类方案总览**

| 方案 | 关键钩子位置 | 输出粒度 | 性能开销 | 跨端通用性 | 线上可用 | 主要局限 |
|---|---|---|---|---|---|---|
| ① 应用埋点 | 应用代码内 | 任意精细 | 低 | 高 | ✅ | 看不到运行时启动前 |
| ② 系统级 API | OS 提供 | 阶段级 | 极低 | 中 | ✅（API 受限）| 颗粒度由系统决定 |
| ③ 外部测量 | 屏幕外 | 物理时序 | 无 | 极高 | ❌ | 设备 / 流程门槛 |

**方案的"组合定律"**：没有任何单一方案能 100% 覆盖启动监控。**必须组合使用**：② 看进程到 Application 之前的"黑盒" + ① 看应用代码内部精细阶段 + ③ 实验室基线校准。

> **探索性思考**：为什么 logcat `Displayed` 不一定是真相？
> Android logcat 的 `Displayed` 时间戳是"应用首帧绘制完成"——但用户看到的可能是 windowBackground（非真实内容）。比如启动后有 800ms 是 windowBackground，logcat 显示 1.2s 完成，但用户实际感知是 2.0s。**软件指标的"完成"和用户感知的"完成"可能差几百 ms**——这就是为什么金标准必须是高速摄像（方案 ③）。

### 5.2 各方案的可见盲区

| 阶段 | 方案 ① | 方案 ② | 方案 ③ |
|---|:---:|:---:|:---:|
| 进程创建（fork / dyld） | ❌ | ✅ | ✅ |
| 运行时启动（ART / V8） | ❌ | ✅ | ✅ |
| Application.onCreate | ✅ | ✅ | ✅ |
| 第三方 SDK 内部 | ❌（除非 Hook） | ❌ | ✅（含在总时间内） |
| 首帧渲染 | ✅ | ✅ | ✅ |
| 完整可交互（TTFD） | ✅（应用声明）| ✅（系统判定）| ✅ |
| 触摸响应延迟 | ❌ | 部分 | ✅ |

**盲区一：进程创建到 Application 之间**：应用埋点最早只能从 `Application.attachBaseContext` 开始打点。必须用方案 ② 补齐。

**盲区二：第三方 SDK 内部**：你能埋点 SDK 调用前后，但 SDK 内部如果起 5 个线程每个跑 200ms，应用埋点完全看不到。补救：用 Trace（Systrace / Perfetto / Instruments）。

### 5.3 跨平台采集对照表

| 维度 | Android | iOS | Web | 嵌入式 |
|---|---|---|---|---|
| 进程级时序 | `ApplicationStartInfo`（31+）| `MetricKit MXAppLaunchMetric` | `PerformanceNavigationTiming` | RTOS trace |
| 应用启动总时长 | logcat `Displayed` | viewDidAppear 时间戳 | LCP / TTI | 业务埋点 |
| TTID | logcat `Displayed` | `didFinishLaunching` 后首帧 | FCP | 首帧渲染 |
| TTFD | `Activity.reportFullyDrawn` | 自定义 `os_signpost` | TTI / INP | 业务声明 |
| 阶段拆解 | Trace section | `os_signpost` interval | `User Timing API` | RTOS event |
| 自动插桩 | ASM Gradle Plugin | SwiftSyntax | Babel plugin | 编译期 hook |

### 5.4 数据可信度评估

不同采集方案的可信度排序：**③ 外部测量 > ② 系统级 API > ① 应用埋点**。

| 指标 | ① 应用埋点 | ② 系统级 API | 偏差来源 |
|---|---|---|---|
| Application 之后阶段 | 误差 < 1% | 误差 < 1% | 几乎无 |
| 完整冷启动时长 | 偏低 ~30%（漏前置） | 误差 < 5% | ① 漏掉进程 / 运行时启动 |
| 端到端物理延迟 | 不可测 | 不可测 | 必须用 ③ |

**工程实践建议**：线上以 ② 为主，① 兜底（精细化诊断）；每个版本在实验室用 ③ 做一次端到端基线，校准 ②/① 的偏差系数。

## 06.归因决策树

> 采集只能告诉我们"启动 3 秒"，归因要告诉我们"3 秒里 1.2s 是 SDK 初始化、0.8s 是首页 IO"。

### 6.1 启动归因决策树

启动慢的根因有十几种，决策树把"穷举式排查"压缩成"二分式排查"：先二分到阶段，再到根因，平均 2 步定位。

```
启动 > 目标值
   │
   ├── 阶段 A. 进程 / 运行时启动 > 0.8s ──▶ 包大小、动态库链接
   │                                          ├─ Multi-DEX 慢（详见 §17.3）
   │                                          ├─ 静态初始化代码多
   │                                          └─ dylib / .so 链接多
   │
   ├── 阶段 B. Application 阶段 > 0.5s ────▶ Application.onCreate 重
   │                                          ├─ 同步初始化的 SDK 太多
   │                                          ├─ ContentProvider 串行（Android）
   │                                          ├─ AppDelegate 中的同步操作（iOS）
   │                                          └─ DOMContentLoaded 中阻塞 JS（Web）
   │
   ├── 阶段 C. Activity / 首屏控制器 > 0.3s ─▶ UI 创建慢
   │                                          ├─ 布局过深（详见卷三·渲染篇）
   │                                          ├─ 首屏数据同步加载
   │                                          └─ View Inflate 慢
   │
   └── 阶段 D. 首帧之后到可交互 > 1s ────────▶ 数据加载慢
                                               ├─ 网络请求串行
                                               ├─ 缓存未命中
                                               └─ 大列表初始化
```

> 反直觉问题 ③ 答案：CPU 不饱和但启动慢，几乎一定是 B 类（IO / Binder / 锁等待）或资源竞争。

> ▶▶ **回扣 [§02 案例](#02贯穿案例)**：金融 App 套用决策树：
>
> - 启动 P50 = 4.2s（中端机预算 1.5s）
> - **Application 阶段 1850ms（超 4×）→ 必查**
>   - 关键路径? = 710ms
>   - 主线程实际跑了? = 1850ms（多 1140ms 是不该串行的任务）
>   - **根因 A：非关键任务挤进主线程**
> - **首屏 → 数据稳态 1100ms（行情数据）**
>   - 行情连接初始化在主线程? Yes
>   - 行情数据请求在 onResume 后? Yes（串行链）
>   - **根因 B：数据预取没在启动并行**

### 6.2 关键路径分析法

**步骤**：

1. **建任务清单**：列出启动期所有任务及其耗时。
2. **建依赖图**：标注每个任务依赖什么。
3. **求关键路径**：DAG 上的最长路径。
4. **重排 / 异步化**：把非关键任务移出，缩短关键任务。

**关键路径求解（简化算法）**：

对每个任务 t，计算：

- `EarliestStart(t)` = max(EarliestEnd of all predecessors)
- `EarliestEnd(t)` = EarliestStart(t) + Duration(t)

最终：`TotalTime = max(EarliestEnd of all tasks)`。关键路径 = 任何 EarliestEnd = TotalTime 的链路。

**工程上的两个简化工具**：

- **Trace 时序图**（Perfetto / Instruments / Chrome Performance）直接展示每个任务的开始 / 结束 / 关系。
- **Gantt 图导出**（自定义脚本从打点数据生成）便于离线分析。

### 6.3 阶段拆解归因法

按 §6.1 决策树的四阶段，逐阶段定位：

**阶段 A：进程 / 运行时**

- 工具：Android `ApplicationStartInfo` + Trace；iOS Instruments dyld + libObjc；Web Network panel。
- 典型问题：包体积 > 100MB 慢、静态初始化多、JNI_OnLoad 串行。

**阶段 B：Application**

- 工具：Trace + 应用埋点。
- 典型问题（按耗时排序）：ContentProvider.onCreate 串行（Android 特有）；数据库 / SP / NSUserDefaults 同步读；网络初始化（建立 SSL / WebSocket）；大量 SDK 同步 init。

**阶段 C：Activity / 首屏控制器**

- 工具：Choreographer / FrameMetrics（详见卷三·渲染篇）。
- 典型问题：布局过深、ViewStub 滥用、主题 windowBackground 加载大图。

**阶段 D：首帧到可交互**

- 工具：业务埋点 + 网络监控。
- 典型问题：首页数据网络请求慢、大列表 onBindViewHolder 中同步 IO、异步任务回调到主线程后立即触发卡顿。

### 6.4 任务依赖归因法

**反直觉问题 ⑦ 的回应**：异步化后总耗时不一定减少。

为什么：

- **A 任务依赖 B**：A 异步无法跳过 B 的耗时。
- **B 占用 CPU**：异步只是把 B 移到子线程，CPU 总量不变。
- **异步开销**：线程创建、上下文切换本身有成本（详见 [§17.2](#172-实验二异步代价测量)）。

正确的"任务依赖归因"步骤：

1. 列出每个任务的真实依赖（不是想当然）。
2. 找出"伪依赖"（误以为依赖，实际可解耦）。
3. 异步化只对**真正无依赖**的任务有效。
4. 异步化必须验证总耗时减少（A/B 测试），否则可能反向收益。

**反直觉问题 ④ 的回应**：开多少线程最快？

由 [`卷二·CPU 篇 §5.2`](../02.资源专项篇/01.CPU监控与分析.md) 已证明：CPU bound 任务的最优线程数 = CPU 核数（拐点）。超过后上下文切换开销超过并发收益。

启动期推荐线程数：

- 计算密集任务池：CPU 大核数 + 1（4–6 个）。
- IO 密集任务池：可更大（10–20 个），但要看磁盘并发能力。
- **总线程数不要超过 CPU 总核数 × 2**，否则启动期线程争用反而拖慢。

> **探索性思考**：为什么"伪依赖"是隐藏陷阱？
> 工程师写代码时常说"A 必须在 B 后"——但仔细问"为什么必须？"往往得到"因为代码这样写的"。**这不是真依赖，是实现依赖**。比如 PushSDK init 调用 LogSDK，看起来依赖；但 PushSDK 完全可以延迟 LogSDK 调用到首次需要时。**伪依赖的本质是"代码耦合"——重构后可以解开**。这是 P 系数（可异步化部分）能从 0.5 提到 0.8 的最大空间。

## 07.Android 全链路 ⭐

> 本章把 Android 启动从"用户点击图标"一路拆到"首帧渲染完成"，回答四个核心问题：**Zygote fork 是什么 / Application 阶段为什么这么重 / ContentProvider 为何串行 / Activity 首帧怎么算"完成"**。

### 7.1 进程创建阶段

Android 应用进程**不是从零创建**，而是 **Zygote fork**——Android 启动时已经创建一个"模板进程"Zygote，加载好了 ART 运行时和 Framework 类。每次启动应用都从 Zygote fork 出来，**省掉了 ART 初始化的几百 ms**。

```
   用户点击图标
       │
       ▼
   Launcher → Binder → AMS（system_server）
       │
       ▼
   AMS 检查目标进程是否存在
       │
       ├─ 存在 → 复用（warm/hot 启动）
       │
       └─ 不存在 → 通知 Zygote fork
                      │
                      ▼
                   fork() 系统调用
                      │
                      ▼
                   子进程 = 应用进程（共享父进程地址空间）
                      │
                      ▼
                   子进程执行 ActivityThread.main()
```

**关键事实**：

1. **fork 几乎是零成本**（COW 写时复制），但**进程创建后还要做 OS 资源分配**（PID、虚拟内存、文件描述符），约 50-100ms。
2. **共享 ART**：Zygote 已加载的类直接共享（不需要重新加载），这是 Android 启动相对快的最大优势。
3. **应用代码看不到这一段**——只能用 Android 12+ 的 `ApplicationStartInfo` 拿到。

### 7.2 ART 加载与 DEX 阶段

```
   ActivityThread.main()
       │
       ▼
   Looper.prepareMainLooper()
       │
       ▼
   ActivityThread.attach()
       │
       ▼
   AMS 通过 Binder 通知"绑定应用"
       │
       ▼
   handleBindApplication
       │
       ├─ 加载 APK 的 dex（如果不在 Zygote 共享类里）
       │
       ├─ ART 解析 / verify / 编译（AOT 已编译则跳过）
       │
       ├─ 加载 Native 库（System.loadLibrary）
       │
       ▼
   ContentProvider.onCreate（所有 Provider 串行）
       │
       ▼
   Application.onCreate
```

**两个性能要点**：

1. **AOT 编译产物（.oat）让 ART 启动接近 Native**——但首次安装后第一次启动仍可能因 ART JIT 编译热路径而较慢（一次性）。
2. **Multi-DEX 在 Android 5.0+ 几乎无影响**（[§17.3 实验](#173-实验三multidex-影响)）——但 Android 4.x 仍是关键瓶颈。

> **探索性思考**：为什么 Baseline Profiles 在 Android 12+ 这么重要？
> 因为它**告诉 ART"哪些类是热路径"**——ART 在安装期对这些类做完整 AOT 编译，启动时直接用编译产物。**没有 Profile 时 ART 用"启动后慢慢 JIT"策略**——首次启动会更慢。Baseline Profiles 让 Google Play 自动收集线上热路径数据反哺，**首次启动加速 30%**——这是 Android 启动优化领域近年最重要的进展。

### 7.3 ContentProvider 串行陷阱

**Android 独有的"启动地雷"**：每个 ContentProvider 在 Application.onCreate **之前**就执行 `onCreate()`——而且是**主线程串行**。

```
   handleBindApplication
       │
       ▼
   installContentProviders()
       │
       ├─ Provider A.onCreate()（同步等待）
       │
       ├─ Provider B.onCreate()（同步等待）
       │
       ├─ ... 几十个 Provider 串行 ...
       │
       ▼
   Application.onCreate()
```

**关键事实**：

- 第三方 SDK 喜欢用 ContentProvider 实现"自动初始化"（不用应用调 init）。
- 每个 Provider 执行 50-200ms，几十个加起来就是 1-3s。
- **ContentProvider.onCreate 不能异步**——是 Framework 强制串行调用。

**应对**：

- **Jetpack App Startup**：把所有第三方 ContentProvider 整合到一个 `InitializationProvider`，内部用 DAG 调度。
- **删除可去除的 SDK ContentProvider**：很多 SDK 提供"手动 init"选项。

### 7.4 Application.onCreate 阶段

```
   Application.onCreate
       │
       ▼
   一般业务做的事：
   ├─ 各种 SDK 初始化（统计/推送/广告/日志/崩溃...）
   ├─ 全局配置加载（SP / 数据库）
   ├─ 网络框架初始化
   ├─ 注册 Activity 生命周期监听
   ├─ 路由表 / DI 容器构建
   ├─ ...
       │
       ▼
   返回，Framework 创建启动 Activity
```

**这一阶段是 Android 启动优化的"主战场"**——80% 的可优化空间都在这里。

**典型问题**：

| 问题 | 占比 | 解决思路 |
|---|---|---|
| 28+ SDK 同步初始化 | 30-50% | 分级 + IdleHandler 推迟 |
| SP 同步读阻塞 | 5-15% | MMKV / DataStore |
| 数据库初始化 | 5-10% | 异步 + 懒加载 |
| Native 库加载（.so）| 5-10% | 按需加载 |
| 网络框架建连 | 5-10% | 预热 + 并行 |

### 7.5 Activity 创建到首帧

```
   Application.onCreate 返回
       │
       ▼
   ActivityThread 创建 LauncherActivity
       │
       ▼
   Activity.onCreate
       │
       ├─ setContentView（XML 解析 + View Inflate）
       ├─ findViewById（逐层遍历）
       ├─ 业务初始化
       │
       ▼
   Activity.onStart → onResume
       │
       ▼
   ViewRootImpl.performTraversals
       │
       ├─ Measure / Layout / Draw
       │
       ▼
   首帧绘制完成 → logcat "Displayed"
       │
       ▼
   首屏数据请求 → onBindViewHolder → ...
       │
       ▼
   Activity.reportFullyDrawn → TTFD
```

**关键差异**：**TTID（首帧）≠ TTFD（可交互）**——首帧可能只是骨架屏 / 占位图，用户看到但点不动。

> **探索性思考**：为什么"白屏"在 Android 上特别常见？
> 因为 Android 启动时**先显示 windowBackground**（主题里的占位色 / 图）——直到 Activity 首帧绘制完成才切换。如果 Application 阶段慢 1s，用户就盯着白屏 1s。**应对方法**：把 windowBackground 设置成与首屏色调一致的图片，让用户**视觉上感觉应用已经"开始加载"**。这叫"启动屏感知优化"——不缩短启动时长，但缩短**感知**启动时长。

## 08.iOS 全链路 ⭐

> 本章把 iOS 启动从"用户点击图标"一路拆到"viewDidAppear"，回答：**dyld 在做什么 / +load 为什么是禁忌 / Swift 启动比 OC 慢的原因**。

### 8.1 iOS 启动五阶段

iOS 启动的**官方五阶段模型**（Apple WWDC 2019 提出）：

```
   ┌──────────┬──────────┬─────────┬──────────┬──────────┐
   │  dyld    │ libObjc  │ Static  │  UI      │  Initial │
   │  Linking │  Init    │ Init    │  Init    │  Frame   │
   └──────────┴──────────┴─────────┴──────────┴──────────┘
        │           │          │          │          │
   动态链接库     ObjC 类      静态变量    AppDelegate  首帧渲染
   加载 + 链接    注册        构造函数    + Window
```

**关键事实**：前三阶段（dyld / libObjc / Static Init）**应用代码完全无法干预**——你只能通过"减少代码量、减少动态库、减少 +load"来缩短。

### 8.2 dyld 链接阶段

```
   exec() 加载主二进制
       │
       ▼
   dyld 启动
       │
       ├─ 加载所有依赖的 dylib（递归）
       │
       ├─ Rebase（修正基址）
       │
       ├─ Bind（链接外部符号）
       │
       ├─ ObjC 类注册
       │
       ▼
   dyld 完成 → main()
```

**dyld 性能要点**：

| 因素 | 影响 | 优化 |
|---|---|---|
| 动态库数量 | 每个 dylib 加载 5-20ms | 合并 + 减少 |
| 符号绑定 | 每个外部符号 1-10us | 减少跨库调用 |
| ObjC 类数 | 每个类注册 1-5us | 减少 OC 类 |

**Apple 推荐**：动态库 ≤ 6 个（含系统）——超过会被 watchdog 杀死风险高。

### 8.3 +load 与 Static Init 禁忌

OC 的 `+load` 方法和 C++ 静态变量构造函数都在 dyld 之后、main() 之前执行——**完全在主线程**：

```objc
@implementation MyClass
+ (void)load {
    // 启动期就执行，无法异步
    [SomeSDK init];     // ❌ 在这里 init SDK 直接拖慢启动
}
@end
```

```cpp
static MyService g_service;  // 构造函数在 dyld 后执行
```

**为什么是禁忌**：

1. **执行时机不可控**——所有 +load 串行执行，顺序由 dyld 决定。
2. **错误处理困难**——抛异常 / 阻塞会让进程直接死。
3. **测量困难**——Instruments 看到的是"main 之前的黑盒"。

**应对**：

- 用 `+initialize` 替代 `+load`（懒加载，首次发消息时执行）。
- C++ 全局变量改成函数局部 static（首次调用时构造）。
- 把"Pod 的初始化"挪到 AppDelegate 显式调用。

> **探索性思考**：为什么 Swift 启动比 OC 慢 100-300ms？
> Swift 标准库 + 运行时本身较大（dyld 加载 20-50ms），且 Swift 类的元数据注册比 OC 类复杂。**对纯 Swift 应用，dyld 阶段比纯 OC 应用多 100-300ms**。这是不可消除的"语言税"——选 Swift 就要接受。**Apple 的应对是**：iOS 13+ 的 dyld3 做了显著优化（启动时使用预生成的"closure"跳过部分链接），让 Swift 应用追平 OC。

### 8.4 main() 与 AppDelegate

```
   main()
       │
       ▼
   UIApplicationMain
       │
       ▼
   UIApplication 初始化 + AppDelegate 创建
       │
       ▼
   application(_:didFinishLaunchingWithOptions:)
       │
       ├─ 业务做的事：
       │  ├─ 启动 Crashlytics / 各种 SDK
       │  ├─ 设置 Window + RootViewController
       │  ├─ 加载持久化数据（NSUserDefaults / Core Data）
       │  ├─ 注册推送
       │  └─ ...
       │
       ▼
   返回，UIKit 调用 RootVC.viewDidLoad
```

**关键认知**：**iOS 的 `didFinishLaunching` 类似 Android 的 `Application.onCreate` + `Activity.onCreate` 合并**——这里慢，启动整体就慢。

**优化思想**：

- 同步初始化 < 5 个（关键路径）。
- 其他 SDK 用 `dispatch_async` 推迟到首帧后。
- 用 `os_signpost` 标注每个阶段，方便 Instruments 分析。

### 8.5 viewDidLoad 到 viewDidAppear

```
   RootVC.viewDidLoad
       │
       ├─ Storyboard / XIB 解析（如果用）
       ├─ 子视图创建
       ├─ 数据准备
       │
       ▼
   viewWillAppear
       │
       ▼
   首次 layoutSubviews + draw
       │
       ▼
   viewDidAppear（系统认为"显示完成"）
       │
       ▼
   首屏数据请求结束 → 业务声明 TTFD
```

**iOS 的"启动结束"判定**：

- **TTID**：viewDidAppear 调用时刻。
- **TTFD**：业务自己用 `os_signpost_interval_end` 标注（首屏数据稳态）。

**iOS 启动优化的特殊优势**：

- **LaunchScreen 自动衔接**：iOS 强制 LaunchScreen 与首屏视觉一致——避免 Android 的"白屏"问题。
- **dyld3 closure 缓存**：iOS 13+ 自动加速二次启动。
- **Order Files**：编译期指定符号顺序，让 dyld 加载更快。

> **探索性思考**：为什么 iOS 启动天然比 Android 快？
> 因为 iOS 没有 ContentProvider 这种"启动地雷"——AppDelegate 是唯一的启动入口。**这是"严格生态"的好处**——Apple 不允许应用偷偷在启动期跑代码（除了 +load，且有限制）。**反观 Android 生态**——SDK 用 ContentProvider 偷启动、Application 阶段被无数 SDK 挤占——这是"开放生态"的代价。

## 09.Web 全链路 ⭐

> 本章把 Web 启动从"输入 URL"一路拆到"页面可交互"，回答：**HTML 解析 vs JS 执行的关系 / 为什么 LCP 不等于 TTI / Service Worker 怎么"秒开"**。

### 9.1 Web 启动的物理本质

Web 启动比 Native 复杂——**它涉及网络往返**：

```
   用户输入 URL
       │
       ▼
   DNS 解析 + TCP 握手 + TLS 握手（首次访问）
       │
       ▼
   下载 HTML（首字节 TTFB）
       │
       ▼
   HTML 解析 → 发现 <script> / <link> / <img>
       │
       ├─ 同步 <script>：阻塞 HTML 解析 → 必须下载 + 执行
       │
       ├─ <link rel="stylesheet">：阻塞渲染（不阻塞解析）
       │
       └─ <img>：异步加载
       │
       ▼
   DOM 解析完成（DOMContentLoaded）
       │
       ▼
   CSS 解析完成 → 首次渲染（FCP / First Contentful Paint）
       │
       ▼
   主要内容渲染完成（LCP / Largest Contentful Paint）
       │
       ▼
   JS 执行完成 + 事件绑定 → 可交互（TTI / Time To Interactive）
```

**关键差异**：**Native 启动是"本地任务"，Web 启动是"网络任务"**。这意味着 Web 启动的物理上限是**网络往返延迟**——不可能比一次 RTT 更快（除非用缓存）。

### 9.2 关键渲染路径（CRP）

Web 的"关键路径"叫 **Critical Rendering Path**：

```
   HTML ──▶ DOM
              │
              ├─▶ Render Tree ──▶ Layout ──▶ Paint
              │
   CSS ──▶ CSSOM
   
   JS（阻塞）──▶ 暂停 DOM 构建
```

**关键事实**：

1. **<script> 阻塞 DOM 解析**——没下载完前后续 HTML 都停。
2. **<link rel=stylesheet> 阻塞渲染但不阻塞解析**——HTML 解析继续，但首次绘制等待 CSS。
3. **JS 中读 DOM 阻塞**——浏览器必须把当前 HTML 解析到该位置。

**Web 的"关键路径"长度** = max(HTML, CSS, 同步 JS) + Layout + Paint。

### 9.3 LCP / FCP / TTI 的差异

| 指标 | 含义 | 用户感知 |
|---|---|---|
| **TTFB** | 第一字节到达 | 网络层就绪 |
| **FCP** | 首次绘制（任何内容）| "页面开始显示" |
| **LCP** | 最大内容绘制 | "主要内容已可见" |
| **TTI** | 完全可交互 | "可以点了" |
| **INP** | 交互响应延迟 P95 | "点了反应快不快" |

**LCP 和 TTI 经常差几百 ms 到几秒**：

- LCP 完成不代表 TTI 到达——JS 还在执行。
- 用户看到内容但点不动是 Web 的常态（"hydration 期"）。

> **探索性思考**：为什么 LCP 是 Google 选择的"质量信号"而不是 TTI？
> 因为 LCP 是**用户视觉感知**的代理——用户看到内容就觉得"开始了"。TTI 虽然更准但**测量复杂、波动大**。Google 的 Core Web Vitals 选 LCP 是工程妥协。**但实际工程中必须看 TTI/INP**——LCP 好但 TTI 差的页面，用户体验仍然差。

### 9.4 SSR / SSG 与 Hydration

```
   传统 SPA：
   下载 HTML（仅骨架）→ 下载 JS → 执行 JS 渲染 DOM → 用户看到内容
   
   SSR（服务端渲染）：
   服务端预渲染 HTML → 直接显示内容 → JS 下载完后"hydrate"接管
   
   SSG（静态生成）：
   构建期生成完整 HTML → CDN 直接返回 → JS hydrate
```

**SSR 启动收益**：

- LCP 大幅提前（HTML 已含内容）。
- 首屏可见时间从"下载 + 执行 JS"变成"下载 HTML"。
- **代价**：服务端压力大；hydration 阶段可能让 TTI 反而变长。

**Hydration 陷阱**：

- 客户端 JS 必须"重新挂载"事件监听 → 大型应用 hydration 几百 ms 到几秒。
- Hydration 期间用户**视觉看到内容但点不动**——比纯 SPA 还糟糕的"假活"状态。

**应对**：

- React Server Components / Astro：减少需要 hydrate 的 JS。
- Progressive Hydration：分块 hydrate，关键区域先生效。

### 9.5 Service Worker 与离线

Service Worker 是 Web 启动的"杀手锏"——**用 Cache API 把上次访问的资源全部缓存，第二次访问近乎瞬开**：

```javascript
self.addEventListener('install', (event) => {
    event.waitUntil(
        caches.open('v1').then((cache) =>
            cache.addAll(['/index.html', '/main.js', '/style.css', ...])
        )
    );
});

self.addEventListener('fetch', (event) => {
    event.respondWith(
        caches.match(event.request).then((response) =>
            response || fetch(event.request)
        )
    );
});
```

**收益**：

- 二次访问 LCP 从 2-3s 降到 200-500ms。
- 离线可用（PWA 核心特性）。
- 减少服务端压力。

**边界**：

- 首次访问无收益（需要先下载并安装 SW）。
- 缓存策略复杂（版本管理、过期、网络优先 vs 缓存优先）。

> **探索性思考**：为什么 Web 启动优化最终都走向"缓存"？
> 因为 Web 的物理瓶颈是**网络往返**——本地能做的优化有限。一次 RTT 50-200ms 是不可压缩的。**所以 Web 启动优化的终局是"避免网络"**——HTTP 缓存、Service Worker、CDN 边缘缓存。这与 Native 启动不同——Native 几乎不依赖网络（除非业务数据），优化重点是"减少代码 + 减少初始化"。**两种平台的启动哲学完全不同**。

## 10.跨端框架全链路 ⭐

> 本章拆解 Flutter / React Native / Compose Multiplatform 等跨端框架的启动开销，回答：**为什么跨端框架比 Native 慢 / Bridge 是不是真的有"性能税"**。

### 10.1 Flutter 启动模型

```
   Native 启动（Android/iOS）
       │
       ▼
   FlutterEngine 初始化（Dart VM + Skia + Tokio）
       │
       ├─ libflutter.so 加载（10-30MB，慢）
       ├─ Dart runtime 启动
       ├─ AOT 编译产物加载（snapshot）
       │
       ▼
   FlutterActivity / FlutterViewController
       │
       ▼
   main() 在 Dart 中执行
       │
       ▼
   runApp(MyApp())
       │
       ▼
   Widget tree 构建 → Layer tree → 首帧 GPU 渲染
```

**Flutter 启动开销**：

- **额外引擎加载**：Native 启动后还要加载 Flutter Engine（200-500ms 额外）。
- **Dart 启动**：Dart VM 初始化（50-150ms）。
- **首帧渲染**：Skia 上 GPU 绘制（与 Native 同等）。

**优化**：

- **Engine 预热**：启动时先创建 FlutterEngine 单例，进入页面时复用（直接进 main，省 200-300ms）。
- **路由预热**：首屏路由在引擎预热时就创建。

### 10.2 React Native 启动模型

```
   Native 启动
       │
       ▼
   JS Bundle 加载（解压 + 解析 + 执行）
       │
       ├─ JSC / Hermes 引擎初始化
       ├─ Bundle 解析（几 MB JS 字符串）
       ├─ 全局执行（注册组件、初始化 store）
       │
       ▼
   Bridge 建立（JS 与 Native 通信通道）
       │
       ▼
   首屏 JSX 渲染 → Yoga 布局 → Native View 创建
       │
       ▼
   首帧渲染
```

**RN 启动瓶颈**：

| 阶段 | 耗时 | 优化 |
|---|---|---|
| Bundle 加载 | 200-800ms | Hermes（预编译字节码）|
| Bridge 建立 | 100-300ms | New Architecture（去 Bridge）|
| JSX 解析 | 50-200ms | Code Splitting |
| 首屏布局 | 50-100ms | Yoga 已优化 |

**Hermes 的关键贡献**：把 JS 预编译为字节码（HBC），跳过 JSC 的解析阶段——**启动加速 30-50%**。

### 10.3 Compose Multiplatform / KMP

Compose 不是"跨端框架"，而是"声明式 UI 框架"——但 Compose Multiplatform 让同一份 UI 代码跑在多端。

**启动开销主要在**：

- Compose runtime 初始化。
- Snapshot 系统建立。
- 首次组合（composition）。

**优化**：

- **Baseline Profiles**（Android）：Compose 的热路径预编译。
- **Strong skipping**：减少不必要的 recomposition。
- **K/N 启动优化**（iOS 端）：减少 Kotlin/Native 的运行时初始化。

### 10.4 跨端框架启动开销对比

| 框架 | 额外启动开销 | 主要优化方向 |
|---|---|---|
| **Native** | 0（基线）| 关键路径瘦身 |
| **Flutter** | 200-500ms | Engine 预热 |
| **React Native** | 300-800ms | Hermes + 新架构 |
| **Compose Multiplatform** | 100-300ms | Baseline Profiles |
| **WebView 套壳** | 100-500ms | Service Worker |

> **探索性思考**：跨端框架的"启动税"能消除吗？
> 不能完全消除——**额外的运行时（Dart VM / JS Engine / Compose）必须加载**。但可以**摊薄**——Engine 预热让"第二次启动近似 Native"。**这是工程哲学的差异**：Native 追求"绝对最快"；跨端追求"足够快 + 跨端开发效率"。两者都对。**关键是业务场景的 SLA**——金融/游戏对启动极敏感，跨端框架可能不合适；电商/工具对启动相对宽容，跨端框架的开发效率红利更值。

## 11.嵌入式全链路 ⭐

> 本章拆解嵌入式（车机 / IoT / 智能家居）启动模型，回答：**为什么车机启动 < 30s 是硬约束 / RTOS 启动和 Android 启动有何不同**。

### 11.1 嵌入式启动的物理约束

嵌入式与移动 / Web 启动有三大物理差异：

```
   ┌──────────────────────────────────────────────────────┐
   │ 移动 / Web                                            │
   │   - 用户随时启动                                       │
   │   - 系统已就绪                                         │
   │   - 资源充足                                           │
   ├──────────────────────────────────────────────────────┤
   │ 嵌入式（车机 / IoT）                                  │
   │   - 启动 = 系统启动 + 应用启动（含 OS 内核）           │
   │   - 内存 / CPU 受限（车机 4GB 是常态）                │
   │   - 安规约束（车机 < 30s 否则触发警告）               │
   │   - 多任务依赖硬件就绪（屏幕、麦克风、网络）           │
   └──────────────────────────────────────────────────────┘
```

### 11.2 RTOS 启动模型

```
   上电 → BootLoader（U-Boot）→ Kernel（Linux/RTOS）
       │                            │
       │                            ▼
       │                       初始化驱动 / 文件系统
       │                            │
       │                            ▼
       │                       init / systemd
       │                            │
       │                            ├─ 启动系统服务（network、audio、display）
       │                            ├─ 启动业务服务（HMI、IVI）
       │                            └─ 启动应用进程
       │                                    │
       │                                    ▼
       │                              UI 主循环就绪
       └──────────────────────────────────────▶ 用户可交互
```

**关键事实**：

- 嵌入式启动**不止"应用启动"**——含 BootLoader、Kernel、init、服务启动。
- 应用层只能控制最后阶段——其他都是 OS 设计。
- **车机典型启动时序**：BootLoader 2s → Kernel 8s → init 5s → HMI 8s → 应用 5s = **28s**。

### 11.3 嵌入式启动优化

| 优化点 | 收益 | 代价 |
|---|---|---|
| **Snapshot / Hibernation** | 跳过 Kernel + init，秒开 | 内存 / 闪存空间 |
| **预启动预测** | 用户接近车时提前启动 | 传感器集成 |
| **UI 优先级** | HMI 先启动，其他延迟 | 服务依赖图重构 |
| **DMA 加载** | 用 DMA 减少 CPU 拷贝 | 硬件支持 |
| **静态链接** | 减少动态库加载 | 包体积 |

**车机启动 SLA（行业基准）**：

- 倒车影像：< 2s（法规强制）。
- 仪表盘：< 5s。
- 主屏 UI：< 15s。
- 完整可用：< 30s。

> **探索性思考**：为什么车机不能像 Android 一样"Zygote fork"？
> 因为车机是**冷启动**——电池断电后整个系统重新启动，没有"父进程"可以 fork。**唯一的优化路径是 Snapshot**——把"启动后的内存状态"存到闪存，下次启动直接 load。这是工程的极致——**用空间换启动时间**。Apple 在 macOS 上也有类似机制（Lid Closed → 唤醒 < 1s）。

## 13.治理一层路径

> 本节回答四个递进问题：**①如何缩短关键路径？②如何避免无效并发？③如何减少 IO 与类加载？④如何架构性消除？** §13-§16 由浅入深四层。

### 13.1 一层命题

**核心命题**：[§02 案例](#02贯穿案例) 经验派失败的根因是"做了一堆非关键路径上的事"。**第一层治理就是"找到关键路径，砍掉/外移所有非关键任务"**。

**层级特征**：

- 改造成本：**低**（任务分级 + 调度调整）
- 收益：**极高**（典型 -30~50% 启动时长）
- 风险：**低**（不动业务逻辑）
- 是否必做：**所有应用**

### 13.2 策略 1.1：任务分级 + IdleHandler 推迟

**机理**：[§17.4 实验](#174-实验四idlehandler-推迟收益) 证明 IdleHandler 是"零侵入"神器。把任务分 4 级：必须同步 / 首屏前异步 / 首屏后 / 真正空闲。

**做法**：

```kotlin
class App : Application() {
    override fun onCreate() {
        super.onCreate()

        // L0: 关键路径必须同步（不可异步）
        SecuritySDK.init(this)        // 后续所有网络要它签名
        QuoteSDK.preConnect(this)     // 预热长连，与 UI 初始化并行

        // L1: 首屏前异步（首屏渲染期间完成）
        backgroundHandler.post {
            DatabaseHelper.warmup(this)
            ImageLoader.init(this)
        }

        // L2: 首屏后 IdleHandler 触发
        Looper.getMainLooper().queue.addIdleHandler {
            initBackgroundSDKs()  // 推送/统计/广告/日志/崩溃
            false
        }

        // L3: 真正空闲（首屏后 5s+）
        backgroundHandler.postDelayed({ initLowPrioritySDKs() }, 5000)
    }
}
```

**收益**：[§02 案例](#02贯穿案例) 此项贡献 -1100ms（占总收益 39%）。

**边界**：要确认每个任务真正的 SLA——比如推送 SDK 必须在用户首次操作前就绪；统计 SDK 在首条事件触发前就绪即可。

### 13.3 策略 1.2：任务依赖 DAG 调度

**机理**：把"启动初始化任务"建模为依赖图，调度器自动找最长路径，并把可并行任务分发到子线程。优于人工拍脑袋"丢线程池"。

**做法**：

```kotlin
val task1 = Task("Security") { SecuritySDK.init() }
val task2 = Task("Quote", deps = listOf(task1)) { QuoteSDK.init() }
val task3 = Task("Push", deps = listOf(task1)) { PushSDK.init() }
val task4 = Task("Trade", deps = listOf(task1, task2)) { TradeSDK.init() }

DagScheduler()
    .add(task1, task2, task3, task4)
    .schedule()  // 自动找关键路径，并行化非关键
```

**收益**：相比"全异步"提升 15-30%（避免无序异步切换开销）。

**边界**：DAG 框架本身有 5-15ms 开销，任务数 > 10 才划算。

### 13.4 策略 1.3：数据预取 + 网络并行

**机理**：行情、个性化数据等业务数据的请求依赖网络往返（典型 200-500ms）。如果在 onResume 才发请求，注定卡。**正确做法**：在 Application 阶段就预热长连 + 预发请求。

**做法**：

```kotlin
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        // 网络预热与 UI 初始化并行
        thread {
            QuoteApi.preConnect()  // TCP/TLS 握手
            QuoteApi.fetchInitialData(callback)  // 首屏数据预拉
        }
        // UI 初始化继续在主线程...
    }
}
```

**收益**：首屏数据稳态 -800ms（[§02 案例](#02贯穿案例)）。

**边界**：依赖登录态/UID 的请求无法预取（除非用上次缓存的 token 试探）；预取数据可能浪费（用户没看就退出）。

### 13.5 一层反思

> **探索性思考**：为什么"任务分级"是最被低估的优化？
> 因为它**不要求技术深度**——任何工程师都能做。但**要求"系统观"**——你必须真正理解每个 SDK / 任务的 SLA，知道它"什么时候必须就绪"。**而不是"以为它必须立刻"**。多数团队的现状是"没人知道这个 SDK 为什么放这里"——历史上某次新人加的，没人敢动。**任务分级的最大价值是"重新审视所有启动任务"**——这个动作本身就是收益的 80%。

## 14.治理二层调度

### 14.1 二层命题

**核心命题**：[§17.1 阿姆达尔实验](#171-实验一阿姆达尔上限) 证明无效并发反而拖慢启动。**第二层治理就是"用对线程池 + 用对调度框架"**。

**层级特征**：

- 改造成本：**中**（替换线程池、引入调度框架）
- 收益：**高**（典型 -100~300ms）
- 风险：**中**（线程模型变化）

### 14.2 策略 2.1：线程池大小科学化

**机理**：[CPU 篇 §5.2](../02.资源专项篇/01.CPU监控与分析.md) 证明拐点 = 核数。启动期开 28 个线程是反向劣化。

**做法**：

```kotlin
// ❌ 启动期开 20+ 线程
repeat(20) { Thread { initSdk(it) }.start() }

// ✅ CPU 池 + IO 池分离
val cpuExecutor = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors()  // 4-8
)
val ioExecutor = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors() * 2
)

// 任务按特性分派
cpuExecutor.execute { CryptoSDK.init() }    // CPU 密集
ioExecutor.execute { ConfigSDK.preload() }  // IO 密集
```

**收益**：[§02 案例](#02贯穿案例) 线程数从 28 → 12，上下文切换 -73%。

**边界**：iOS GCD 全局并发队列已自动管控；Web Worker 数 ≤ navigator.hardwareConcurrency。

### 14.3 策略 2.2：ContentProvider 整合（Android 特异）

**机理**：[§07.3 ContentProvider 串行陷阱](#73-contentprovider-串行陷阱)。每个第三方 SDK 喜欢注册自己的 ContentProvider，每个在 Application.onCreate 之前**串行执行**，无法异步。

**做法（Jetpack App Startup）**：

```xml
<!-- AndroidManifest.xml: 移除所有第三方 ContentProvider，统一接入 -->
<provider
    android:name="androidx.startup.InitializationProvider"
    android:authorities="${applicationId}.androidx-startup">
    <meta-data android:name="com.example.WorkManagerInitializer"
               android:value="androidx.startup" />
    <meta-data android:name="com.example.AnalyticsInitializer"
               android:value="androidx.startup" />
</provider>
```

```kotlin
class WorkManagerInitializer : Initializer<WorkManager> {
    override fun create(context: Context): WorkManager = WorkManager.initialize(context, ...)
    override fun dependencies(): List<Class<out Initializer<*>>> = emptyList()
}
```

**收益**：典型 App 减少 5-15 个 Provider，启动 -200~500ms。

**边界**：Android 特有；需要第三方 SDK 提供 Initializer 实现。

### 14.4 策略 2.3：主进程瘦身（Android）

**机理**：很多 App 主进程会启动 `:push`、`:web`、`:logger` 等子进程。每个子进程的 Application.onCreate 也会跑——主进程内的初始化会被错误地复制到子进程。

**做法**：

```kotlin
override fun onCreate() {
    super.onCreate()
    val processName = getProcessName()  // 'com.app' 主 / 'com.app:push' 子
    when {
        processName == packageName -> initMainProcess()
        processName.endsWith(":push") -> initPushProcess()
        else -> { /* 子进程不做主进程重活 */ }
    }
}
```

**收益**：子进程启动 -50~80%；间接降低主进程被系统杀的概率。

**边界**：必须确认所有 SDK 在子进程的需要——错误跳过初始化会引发 NPE。

### 14.5 二层反思

> **探索性思考**：为什么"全异步化"会反向劣化？
> 因为**异步本身有开销**——线程创建 50-200μs、调度延迟 10-50μs、上下文切换 1-10μs、结果回主线程 10-100μs。当任务本身只有 1-5ms 时，异步开销占比 30-100%——**异步反而比同步慢**。这是 [§17.2 实验](#172-实验二异步代价测量) 证明的。**正确的异步原则**：耗时 ≥ 5ms 且可并行 ≥ 2 个的任务才异步——其他直接同步执行。

## 15.治理三层资源

### 15.1 三层命题

**核心命题**：启动期主线程 IO 是隐形杀手——SP 读 30-200ms、数据库初始化 100-500ms、SO 加载 50-300ms。**第三层治理就是"减少 IO + 加速类加载"**。

**层级特征**：

- 改造成本：**中**（替换基础设施）
- 收益：**中**（-50~200ms）
- 风险：**低**

### 15.2 策略 3.1：SP / 配置文件异步预读

**机理**：SharedPreferences 第一次读会阻塞主线程（loadFromDisk）。如果在主线程同步访问，typical 30-200ms。

**做法**：

```kotlin
// 在主线程注册 → 实际异步加载
val sp = getSharedPreferences("config", MODE_PRIVATE)
// 第一次 sp.getXxx() 时已加载完毕，主线程无阻塞

// 更激进：用 MMKV / DataStore
val mmkv = MMKV.defaultMMKV()  // mmap 直接映射，几乎零延迟
```

**收益**：典型 App 启动期 SP 读 -50~150ms。

**边界**：DataStore 是异步 API，调用方需要协程支持。

### 15.3 策略 3.2：类预加载 + Baseline Profiles

**机理**：[§17.5 实验](#175-实验五类预加载收益) 证明业务页面响应可降 70%。Android 12+ 的 Baseline Profiles 让 ART 在安装期 AOT 编译热路径。

**做法（Baseline Profiles）**：

```
// app/src/main/baseline-prof.txt
HSPLcom/example/MainActivity;-><init>()V
HSPLcom/example/MainActivity;->onCreate(Landroid/os/Bundle;)V
...
```

**收益**：启动 -10~25%（Google 官方数据）；业务页面打开 -30~50%。

**边界**：profile 需要持续更新；包体积 +几 KB；旧版本 ROM 不支持。

### 15.4 策略 3.3：SVG/资源异步解码

**机理**：复杂矢量图（如启动 Logo + 引导插图）解码 50-200ms。预加载 vs 等需要时解码差异巨大。

**做法**：

```kotlin
// 启动期异步预解码到内存缓存
backgroundExecutor.execute {
    val drawable = ResourcesCompat.getDrawable(resources, R.drawable.logo, null)
    BitmapCache.put("logo", drawable)
}

// 业务用时直接取，无解码开销
imageView.setImageDrawable(BitmapCache.get("logo"))
```

**收益**：首屏图标显示 -100~200ms。

**边界**：缓存吃内存（每张矢量图 1-3MB）；不在内存敏感场景使用。

### 15.5 策略 3.4：Native 库按需加载

**机理**：启动期加载 .so 文件触发 JNI_OnLoad（Android）/ dyld 链接（iOS），每个 50-300ms。多个 SO 累加可达 1-2s。

**做法**：

```kotlin
// ❌ 启动期加载所有 SO
init {
    System.loadLibrary("crypto")
    System.loadLibrary("video")
    System.loadLibrary("imaging")
    System.loadLibrary("ml")
    // ...
}

// ✅ 按需加载，使用时再调
fun encrypt(data: ByteArray): ByteArray {
    if (!cryptoLoaded) {
        System.loadLibrary("crypto")
        cryptoLoaded = true
    }
    return nativeEncrypt(data)
}
```

**收益**：典型 App 启动 -200~500ms（取决于 SO 数量）。

**边界**：需要业务逻辑配合（异常分支处理）；首次使用稍慢。

### 15.6 三层反思

> **探索性思考**：为什么"启动期 IO"特别贵？
> 因为启动期 **磁盘 / Flash 还是冷状态**——文件系统缓存还没建立、闪存还没"暖"。一次冷读 100ms 是常态。**热读只要 5-10ms**。所以"启动期主线程 IO"乘的是"冷状态的代价"。**应对**：要么提前预读（让磁盘进入暖状态），要么用内存映射（mmap）跳过文件系统调用。MMKV 比 SP 快 10-100 倍的根因就是用 mmap。

## 16.治理四层架构

### 16.1 四层命题

**核心命题**：前三层治理是"在现有架构上优化"，到第四层就是**架构性改造**——把"启动慢"从根上消除。

**层级特征**：

- 改造成本：**高**（架构重构）
- 收益：**极高**（突破前三层天花板）
- 风险：**高**
- 适用：**前三层已用尽时**

### 16.2 策略 4.1：插件化 / 动态特性

**机理**：把"非首屏功能"打包成插件，启动期不加载。**真正用到时再下载/加载**——启动期代码量直接砍半。

**做法**：

```kotlin
// Android Dynamic Feature
splitInstallManager.startInstall(
    SplitInstallRequest.newBuilder()
        .addModule("video_call")
        .build()
)

// 主 APK 仅包含核心功能，启动期不加载视频通话/AR/...
```

**收益**：主包体积 -30-60%；启动 -200-800ms。

**边界**：插件体系开发成本高；首次使用需下载延迟；签名 / 资源 / 兼容性都是坑。

### 16.3 策略 4.2：单页多模块（Web）

**机理**：把 SPA 拆成多个独立页面。**首屏只加载首屏 JS bundle**，其他懒加载。

**做法**：

```javascript
// React Router + 动态 import
const Home = lazy(() => import('./pages/Home'));
const Profile = lazy(() => import('./pages/Profile'));

<Routes>
    <Route path="/" element={<Home />} />
    <Route path="/profile" element={<Profile />} />
</Routes>
```

**收益**：首屏 JS bundle 从 2MB 减到 200KB；LCP -50%。

**边界**：路由切换时有"懒加载延迟"；要做骨架屏过渡。

### 16.4 策略 4.3：服务端渲染 + 流式输出

**机理**：服务端预渲染 HTML，浏览器收到第一字节就能显示——**LCP 从"几秒"降到"几百 ms"**。

**做法**：

- Next.js / Nuxt / Remix：内置 SSR。
- React Server Components：减少 hydrate 的 JS。
- Streaming SSR：HTML 流式输出，首字节立刻显示。

**收益**：LCP -50-80%。

**边界**：服务端压力增大；hydration 复杂度增加；不适合纯 SPA 应用。

### 16.5 策略 4.4：嵌入式 Snapshot

**机理**：把"OS + 应用就绪状态"序列化到闪存，下次启动直接 load。

**做法**（车机/嵌入式）：

```
   首次启动 → 完整启动 → 业务就绪 → 拍 snapshot 写闪存
                                            │
                                            ▼
   后续启动 → 直接 load snapshot → 秒进
```

**收益**：车机启动 28s → 5s。

**边界**：Snapshot 一致性（系统更新后失效）；硬件依赖（需要快速 Flash）。

### 16.6 优先级判定（ROI）

| ROI | 优化项 | 收益 | 成本 | 风险 | 对应章节 |
|---|---|---|---|---|---|

### 16.7 四层反思

> **探索性思考**：什么时候应该走到第四层架构改造？
> 当前三层治理用尽，启动还达不到目标时。**信号**：
>
> 1. Application 阶段 < 200ms 但启动还慢——说明瓶颈在代码量本身（架构问题）。
> 2. 关键路径上的任务都不能再砍——说明业务架构本身是关键路径（耦合太多）。
> 3. 用户对"懒加载"接受度高（如电商类）——可考虑动态特性。
>
> **反信号**：如果团队连前三层都没做完，去做第四层是浪费——**P0 没做完不要碰 P3**。

## 17.求证实验

> 本章是"科学家求证"风格的核心。每个实验都遵循 **观察 → 疑问 → 假设 → 推导 → 实验 → 数据 → 验证 → 结论 → 边界** 九步。

### 17.1 实验一：阿姆达尔上限

**Step 1 — 原始观察**

工程实践中常听到："我把所有启动任务都改异步了，启动应该会更快。"实测只快了 30%，不是预期的 5×？

**Step 2 — 提出疑问**

> **给定启动任务集，可异步化部分占比为 P，并行加速比为 N，启动总时长 T(P, N) 是多少？**

**Step 3 — 形成假设**

**H₁**：T(P, N) 服从阿姆达尔定律：T(P, N) = T₀ × [(1 − P) + P/N]，存在硬上限 1/(1−P)。
**H₀**：异步化可以无限加速。

**Step 4 — 数学推导**

设原始启动时长 T₀，可异步化部分占比 P。改为 N 路并行后：

```
   串行部分时长 = T₀ × (1 − P)        （无法缩短）
   并行部分时长 = T₀ × P / N
   总时长 T(P, N) = T₀ × [(1 − P) + P / N]
   加速比 S(P, N) = T₀ / T(P, N) = 1 / [(1 − P) + P / N]
   加速比上限（N → ∞）：S_max = 1 / (1 − P)
```

| P | S_max | 含义 |
|---|---|---|
| 0.5 | 2× | 即使无限并行最多快一倍 |
| 0.7 | 3.3× | |
| 0.8 | 5× | |
| 0.9 | 10× | |

**Step 5 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | Pixel 6 |
| 测试 App | 自构造启动场景：10 个任务，每个 100ms |
| P 取值 | 通过控制"必须串行的任务数 = (1−P) × 10"实现 |
| N 取值 | 1, 2, 4, 8（线程池大小） |
| 重复 | 每组 100 次 |

**Step 6 — 实测数据**

设 T₀ = 1000ms：

| P | N=1 | N=2 | N=4 | N=8 | 公式 N=∞ |
|---|---|---|---|---|---|
| 0.5 | 1000 | 750 | 625 | 562 | 500 |
| 0.7 | 1000 | 650 | 475 | 388 | 300 |
| 0.8 | 1000 | 600 | 400 | 300 | 200 |
| 0.9 | 1000 | 550 | 325 | 213 | 100 |

实测与公式对比（P = 0.8）：

| N | 公式预测 (ms) | 实测 (ms) | 误差 |
|---|---|---|---|
| 1 | 1000 | 1015 | +1.5% |
| 2 | 600 | 625 | +4% |
| 4 | 400 | 445 | +11% |
| 8 | 300 | 380 | +27% |

**Step 7 — 验证 / 修正**

- 小 N（1–2）误差稳定在 < 5%，符合阿姆达尔定律。
- 大 N（4 / 8）误差显著放大 → 引入新因素：**线程切换开销 / 锁争用**。

**修正模型**：T(P, N) = T₀ × [(1 − P) + P/N] + N × C，其中 C 是单线程开销（实测约 10ms / 线程）。

**Step 8 — 提炼结论**

> **启动加速比存在硬上限 = 1 / (1 − P)。
> 大部分应用 P ≈ 0.7，所以加速上限 ≈ 3.3×；超过这个上限再加并发只会反向劣化。**

**Step 9 — 边界**

- 假设任务无依赖；实际启动中任务依赖图限制了并行度。
- 假设异步任务无 IO 阻塞；如有大量 IO，则 N 可以远超 CPU 核数。
- 低端机 CPU 总量小，N 的最优值更小。

### 17.2 实验二：异步代价测量

**Step 1 — 原始观察**

工程师常说"小任务异步就是浪费"。但**到底多小算小？异步本身的开销是多少？**

**Step 2 — 提出疑问**

> **创建一个线程并执行一个任务，相比同步执行，固定开销是多少？**

**Step 3 — 形成假设**

**H₁**：异步固定开销 C 由"线程创建 + 调度 + 上下文切换 + 任务排队 + 主线程同步"组成，量级 0.1–10ms。任务耗时 < C 时异步反向收益。

**Step 4 — 数学推导**

```
   C_async = T_create + T_schedule + T_context_switch + T_join

   其中（Android Pixel 6 实测典型值）：
   T_create        = 50–200 μs
   T_schedule      = 10–50 μs
   T_context_switch = 1–10 μs
   T_join          = 10–100 μs

   合计 C ≈ 0.1 – 0.5 ms（线程池命中）
        ≈ 1 – 5 ms（首次创建线程）
```

**Step 5-6 — 设计实验 + 实测数据**

| 任务耗时 | 同步 (ms) | 异步 A (ms) | 异步 B (ms) | 异步开销 |
|---|---|---|---|---|
| 1ms | 1.05 | 1.45 | 1.80 | A: +0.4ms, B: +0.75ms |
| 5ms | 5.1 | 5.5 | 5.9 | A: +0.4ms, B: +0.8ms |
| 10ms | 10.1 | 10.5 | 10.9 | A: +0.4ms, B: +0.8ms |
| 50ms | 50.2 | 50.6 | 51.0 | A: +0.4ms, B: +0.8ms |
| 100ms | 100.3 | 100.7 | 101.1 | A: +0.4ms, B: +0.8ms |

**Step 7-8 — 结论**

> **异步的固定开销约 0.4–0.8ms。耗时 < 1ms 的任务异步是反向收益。
> 异步只对"耗时 ≥ 5ms 且可并行 ≥ 2 个"的任务有效。**

**Step 9 — 边界**

- 本结论对 CPU 任务成立。IO 任务由于"等待"占主导，异步几乎总是有收益。
- 低端机 C 上升到 2–5ms。
- iOS GCD 因有底层优化，C 通常更小（0.1–0.3ms）。

### 17.3 实验三：MultiDex 影响

**Step 1 — 原始观察**

工程师常听说"MultiDex 启动慢"，但 Android 5.0+ 之后是否还慢？

**Step 2 — 提出疑问**

> **MultiDex 在 Android 5.0+（ART 运行时）相比单 DEX，冷启动时长差异是多少？**

**Step 3 — 形成假设**

**H₁**：Android 5.0+ 的 ART 已对 MultiDex 做了 AOT 优化，启动差异 < 100ms。
**H₀**：MultiDex 仍然显著拖慢启动。

**Step 4 — 数学推导**

- **Android 4.x**：Dalvik 在主线程加载第二 DEX，含解压、odex 生成。耗时 ≈ N × 500ms。
- **Android 5.0+**：ART 在安装时 AOT 编译所有 DEX 为 OAT。启动时只加载已编译的 OAT。

**Step 5-6 — 设计实验 + 实测数据**

| 方法数 | 单 DEX (ms) | Multi 2 (ms) | Multi 3 (ms) | 设备 |
|---|---|---|---|---|
| 5,000 | 380 | 385 | 392 | Android 13 |
| 10,000 | 410 | 415 | 425 | Android 13 |
| 50,000 | 580 | 595 | 615 | Android 13 |
| 5,000 | 720 | 1,250 | 1,800 | Android 4.4 |
| 10,000 | 850 | 1,580 | 2,300 | Android 4.4 |

**Step 7-8 — 结论**

> **Android 5.0+ 的 MultiDex 启动代价 < 5%，可忽略。
> Android 4.x 的 MultiDex 启动代价 50–170%，必须特殊处理。**

**Step 9 — 边界**

- 首次安装后第一次启动仍可能因 ART 编译进行而较慢（一次性）。
- 谷歌 Pixel 等设备有 Cloud Profile 优化，第三方 ROM 可能差异较大。

### 17.4 实验四：IdleHandler 推迟收益

**Step 1 — 原始观察**

很多团队把"非首屏必需"的初始化（如埋点、推送、广告 SDK）放在 Application.onCreate 里。但这恰好挤占了关键路径。

**Step 2 — 提出疑问**

> **把这些非关键任务从启动期推迟到 IdleHandler，启动时长能省多少？业务功能会不会迟到？**

**Step 3 — 形成假设**

**H₁**：把 980ms 非关键任务用 IdleHandler 推迟，启动时长降 ≥ 600ms。
**H₀**：因为 IdleHandler 时机不可控，业务损失抵消启动收益。

**Step 4-5 — 推导 + 设计**

```
  IdleHandler 触发时机：MessageQueue 没有更高优先级消息时
  → 通常在首帧渲染完成后 100-300ms 内
  → 此时主线程已空，CPU 资源充足
  → 任务执行不影响用户交互
```

| 项 | 配置 |
|---|---|
| 任务集 | 28 个 SDK 初始化 |
| 对照 | A：全部 onCreate 启动；B：分类 IdleHandler 推迟 |
| 重复 | 每组 100 次冷启动 |

**Step 6 — 实测数据**

| 指标 | A 组（全启动期） | B 组（IdleHandler） | 变化 |
|---|---|---|---|
| 启动 P50 | 4180ms | 2580ms | **-38%** |
| 启动 P95 | 6750ms | 4290ms | **-36%** |
| 推送 SDK 就绪 | 启动+0ms | 启动+450ms | 推迟 0.5s |
| 统计 SDK 就绪 | 启动+0ms | 启动+520ms | 推迟 0.5s |
| 首条统计上报 | 启动+5s | 启动+5s | 无影响 |
| 推送送达率 | 99.7% | 99.7% | 无影响 |

**Step 7-8 — 结论**

> **IdleHandler 是"零侵入"的启动优化神器**——不改任何业务代码、不重构任何模块，只把 SDK 初始化时机往后挪 500ms，启动直接降 38%。

**Step 9 — 边界**

- 必须确保推迟任务真的不影响首屏。
- IdleHandler 队列需要细分优先级，避免一次性堆积。
- iOS 用 `CFRunLoopAddObserver` 监听 BeforeWaiting 实现等价机制。

### 17.5 实验五：类预加载收益

**Step 1 — 原始观察**

启动期会加载数百个 Java/Kotlin 类。每个类首次访问要经历 Verify → Resolve → Init 三步。

**Step 2 — 疑问**

> **能否把"未来要用的类"在启动空闲时间预加载？**

**Step 3 — 假设**

**H₁**：通过 `Class.forName()` 在 IdleHandler 里预热常用类，可以让首次进入业务页面时减少 100-300ms。

**Step 4-5 — 设计实验**

| 项 | 配置 |
|---|---|
| 设备 | 红米 Note 11 |
| 类清单 | 提取启动后 30 秒内被使用的所有类（约 280 个）|
| 对照 A | 不预加载 |
| 对照 B | IdleHandler 异步预 forName 全部 280 类 |

**Step 6 — 实测数据**

| 场景 | A 不预加载 | B 预加载 | 改善 |
|---|---|---|---|
| 启动 P50 | 2580ms | 2620ms | -40ms（预加载占了一点）|
| 行情页打开 | 380ms | 105ms | **-72%** |
| 交易页打开 | 420ms | 140ms | **-67%** |

**Step 7 — 结论**

> **类预加载是"空间换时间"的极致体现**——用启动期最后 200ms 空闲时间，换业务页面打开 -300ms。

**Step 8 — 边界**

- 类列表需要随版本迭代更新（用线上数据反哺）。
- 内存吃紧场景慎用（预加载占 5-10MB 永久内存）。
- iOS 类似机制：dyld pre-binding + Order File。

### 17.6 五大实验启示

```
   阿姆达尔上限      → 异步加速有硬上限              ─┐
   异步代价测量      → 小任务异步反向收益              ├─▶ 启动 = 关键路径优化问题
   MultiDex 已死     → 不要被过时的"经验"误导         │
   IdleHandler 推迟  → 不必要任务挪到首屏后           │
   类预加载          → 用空闲时间换业务页面响应       ─┘
```

**统一启示**：

| # | 维度 | 启示 | 收益量级 |
|---|---|---|---|
| ① | 阿姆达尔上限 | 异步加速天花板 = 1/(1-P) | 不可超越 |
| ② | 异步代价 | 小任务异步反向劣化 | 反向 -10% |
| ③ | MultiDex | Android 5.0+ 已无问题 | 0（破除误区） |
| ④ | IdleHandler | 非关键任务推迟到首屏后 | -38% |
| ⑤ | 类预加载 | 启动空闲换业务响应 | -70% 业务页 |

**一句话**：**找对关键路径 ≫ 增加并发度**。这就是 [§02 案例](#02贯穿案例) 6 周经验派失败的本质——他们一直在做"减重"和"无脑并发"，没找到关键路径。

## 18.实战案例

### 18.1 金融 App 启动优化最终结果

**优化前后核心指标**

实验环境：iPhone 13（旗舰）+ Redmi Note 11（中低端），各 50 次冷启动取均值：

| 指标 | 优化前 | 优化后 | 改善 |

| **启动 P95（中端）** | 6750 ms | 2150 ms | -68% |

| 首屏数据稳态 | 4200 ms | 1400 ms | -67% |
| 主进程 onCreate 中线程数 | 28 | 12 | -57% |
| 上下文切换/启动 | 18000 | 4800 | -73% |
| 主线程 IO 时长 | 320 ms | 28 ms | -91% |

**六项优化各自贡献**（A/B 实验量化每项）：

| 优化项 | 单独启动节省 | 主要影响段 |
|---|---|---|

**重要发现**：**Application 阶段 4 项贡献 -1880ms（占总收益 67%）**——经验派 6 周完全错过的方向。

**业务回归**：

- **开盘 30 秒交易额**：同行 -35% → +7%（**翻盘**）
- **应用商店投诉**："启动慢" 词频从前三降至前二十外
- **DAU**：+8.4%（启动快直接转化为活跃）
- **副作用**：推送 SDK 推迟 500ms 就绪（A/B 显示送达率无变化）

### 18.2 跨端同构案例：分级初始化框架

**背景**：某社交应用 Android/iOS/Web 三端都有启动慢问题，根因相同——SDK 都同步 init。

**统一假设**："大部分 SDK 不必在启动期同步初始化，可以延迟到首屏后或首次使用时"。

**修复**：三端统一采用分级初始化框架（Android App Startup / iOS 自研 / Web Lazy Import）：

- L0 必要级（启动期同步）：日志、Crash、AB 实验。
- L1 重要级（首帧后异步）：网络、推送、统计。
- L2 延迟级（首次使用时）：广告、第三方分享、客服。

**验证**：

| 平台 | 优化前 TTID | 优化后 TTID | 降幅 |
|---|---|---|---|
| Android | 3.2 s | 1.4 s | 56% |
| iOS | 2.8 s | 1.2 s | 57% |
| Web | 5.8 s | 2.6 s | 55% |

**统一启示**：阿姆达尔定律在三端都成立。**P 从 0 提到 0.7 的收益 = 启动时长 60%**。

### 18.3 平台特异案例：Android 启动白屏感知优化

**背景**：Android 11 应用启动后白屏 800ms 才出现首屏，但 logcat Displayed 显示首帧只用了 1.2s（看似正常）。

**归因**：用高速摄像测得：物理首屏出现时间 2.0s（不是 1.2s）。差异 800ms = 应用首帧已渲染，但用户看到的是 windowBackground。

**修复**：

- 设置 windowBackground 与首屏色调一致（视觉无缝衔接）。
- 首帧立即用缓存数据渲染，避免空白骨架屏。
- 异步刷新数据，平滑过渡。

**验证**：物理首屏可感知时间从 2.0s 降到 1.5s，用户主观满意度从 3.5 提升到 4.6。

**边界**：仅在缓存有效时适用；首次安装无缓存时退化为占位图。这是平台特异问题——iOS 的 LaunchScreen 已默认无缝衔接，Web 没有这层语义。

### 18.4 案例统一启示

- **数据驱动而非经验**：[§02 案例](#02贯穿案例) 6 周失败 vs 5 天成功的根本差异。
- **Application 是金矿**：80% 优化空间在这里。
- **"看起来快"也是快**：感知优化（白屏处理）和实际优化同等重要。
- **分级初始化跨端通用**：三端同构启示。

## 19.防劣化体系

### 19.1 三道防线总览

```
开发期 ──▶ 编译期 / CI ──▶ 上线期 / 运行期
   │             │              │
   ▼             ▼              ▼
[Lint]      [自动化基准]     [线上 SLO]
```

参考 [`卷零·06 性能预算与防劣化体系`](../00.公共方法论/06.性能预算防劣化.md)。

### 19.2 编码期 Lint

| Lint 规则 | 作用 |
|---|---|
| `MainThreadIO` | 在 `Application.onCreate` 中调用 IO / DB / 网络 → 警告 |
| `UnregisteredProvider` | 新增 `<provider>` 未注册 App Startup → 警告 |
| `SyncImageLoad` | 在 `viewDidLoad` 中同步加载图片 / 大数据 → 错误 |
| `BlockingScript` | Web：`DOMContentLoaded` 中阻塞 JS > 50ms → 警告 |

### 19.3 CI 卡口与线上 SLO

**CI 卡口**：

- 启动基准用例：自动化模拟冷启动 50 次，P95 ≤ 阈值（如 2s）。
- 每次 PR 跑一次，劣化 > 5% 阻塞合并。
- 包体积监控：每次 PR 检查 APK / IPA / Bundle 大小，超 10MB 增量阻塞合并。

**线上 SLO**：

| 指标 | 阈值 |
|---|---|
| 冷启动 P50 | < 2s |
| 冷启动 P99 | < 5s |
| 启动失败率（含 ANR / Crash / 超时）| < 0.1% |
| 启动期卡顿率 | < 5% |
| Application 阶段耗时 P95 | < 800ms |
| 错误预算耗尽 | 冻结新功能 |

### 19.4 灰度与线上回滚

灰度发布的最佳实践：

```
1% → 5% → 20% → 50% → 100%
  ↓     ↓      ↓       ↓
观察  观察   观察    全量
24h   2 天   3 天    后持续监控

每个阶段必查指标：
- 启动 P50 / P95 是否劣化
- 启动失败率是否上升
- 启动期 ANR 是否上升
- 业务核心指标（DAU / 留存 / 转化）是否劣化
```

**金融 App 案例灰度 21 天**，无新增 ANR / 崩溃，全量发布。

## 21.总结与延伸

### 21.1 五条核心原则

1. **关键路径思维**：总启动时长 = 关键路径耗时，不是任务总和。优化必须围绕关键路径展开。[§02 案例](#02贯穿案例) 最经典——6 周经验派失败的原因就是动了一堆"非关键路径"。
2. **数据驱动决策**：每条优化必有量化收益（如"IdleHandler 推迟 = 减 1100ms"），来自实验。
3. **分级初始化**：必要 / 重要 / 延迟三级，把可延迟的全部移出启动期（[§13](#13治理一层路径)）。
4. **TTID + TTFD 并重**：首帧 ≠ 可交互。两者必须都达标。
5. **科学求证替代经验**：MultiDex 在 Android 5.0+ 已不是问题，但仍有团队投入大量精力（[§17.3](#173-实验三multidex-影响)）。

### 21.2 五个常见误区

1. **"所有任务都异步就是快"**：错。[阿姆达尔上限](#171-实验一阿姆达尔上限)有硬天花板；[小任务异步反向收益](#172-实验二异步代价测量)。
2. **"线程开越多越快"**：错。超过 CPU 核数后切换开销反而拖慢（[卷二·CPU §5.2](../02.资源专项篇/01.CPU监控与分析.md)）。
3. **"首帧出来就是启动结束"**：错。TTFD 才是用户感知的"完成"，可能比 TTID 慢一倍。
4. **"包体积大启动一定慢"**：基本对，但 Android 5.0+ 的 ART AOT 让影响小于直觉（[§17.3](#173-实验三multidex-影响)）。
5. **"启动监控有 logcat Displayed 就够了"**：错。要同时看物理端到端延迟（含 windowBackground 时间）。

### 21.3 贯穿案例的方法论提炼

[§02 金融 App 案例](#02贯穿案例) 完整演示了"分析 → 探索 → 优化 → 结果"的科学流程：

| 阶段 | 方法 | 关键产出 |
|---|---|---|
| **分析** | 重定义问题（[§03](#03启动本质定义)）+ 关键路径模型（[§04](#04关键路径原理)） | "启动 4.2s"重定义为"Application 1850ms + 数据稳态 1100ms" |
| **探索** | 决策树归因（[§06](#06归因决策树)）+ Tracing 验证 | 双根因：主线程任务过载 + 数据请求串行 |
| **优化** | 按 ROI 顺序执行 6 项策略（[§13-§16](#13治理一层路径)） | 5 天内分批落地，每批可量化 |
| **结果** | A/B 实验量化每项贡献（[§18](#18实战案例)） | 启动 4.2s→1.4s；交易额 -35%→+7% |

**最重要的方法论财富**：永远不要"全异步化"——先用 Trace 找出关键路径，再有针对性地"分级处理"。

### 21.4 三个外延

- **AI 启动预测**：未来 OS 用 ML 预测用户何时打开应用，提前预热（Android 12+ App Standby Buckets 已是雏形）。
- **预加载即服务**：Google Play 的 Engage SDK / Apple 的 App Clip 让"启动前预加载"成为生态标准。
- **跨端启动统一**：Compose Multiplatform / Kotlin/Native 让"一份启动优化代码跨端复用"成为可能。

### 21.5 给团队的建议

- **第 1 周**：用 Tracing 拉出关键路径，建立"Application 阶段时长 + 首屏数据稳态"双指标。
- **第 2 周**：执行第一层治理（[§13](#13治理一层路径)）——任务分级 + IdleHandler 推迟。
- **第 3 周**：执行第二层治理（[§14](#14治理二层调度)）——线程池整治 + ContentProvider 整合。
- **第 4 周**：执行第三层治理（[§15](#15治理三层资源)）——MMKV + 类预加载 + Baseline Profiles。
- **第 5 周以上**：评估是否需要走第四层架构改造（[§16](#16治理四层架构)）。

## 一句话总结

> **启动是一个关键路径上的最优化问题。**
> 总启动时长 = 关键路径所有串行任务耗时之和。
> 一切优化都是缩短关键路径或把任务从关键路径移走（异步 / 延迟）。
> **不在关键路径上的任务，再慢也不影响启动时长**。
> [§02 金融 App 案例](#02贯穿案例) 就是这条原则的最佳证明：**经验主义 6 周失败 → 关键路径方法 5 天解决**。
