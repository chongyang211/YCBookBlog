## 01.程序卡顿概念

### 1.1 QT卡顿的概念

在 Qt 应用中，“卡顿”指的是**用户界面（UI）无法及时响应用户输入或无法按预期频率（通常是 60 FPS，即每 16.7 毫秒一帧）流畅刷新的现象**。

具体表现包括：

*   点击按钮、滑动列表、输入文字等操作后，界面反应迟缓。
*   动画播放不流畅，有拖影或跳跃感。
*   窗口移动或调整大小时，内容刷新慢，出现残影。

### 1.2 为什么会卡顿

Qt 作为一个 GUI 框架，其运行基础是**事件循环（Event Loop）**。卡顿的根本原因几乎总是：**主线程（UI 线程）被长时间的计算或阻塞操作所占用，导致事件循环无法及时处理新到来的事件和重绘请求。**

为了理解这个原理，需要先了解 Qt 的核心工作机制：**Qt 的心脏——>事件循环 (QEventLoop)**

每个 Qt 应用至少有一个事件循环（在主线程中，由 `QApplication::exec()` 启动）。它不停地做一件事：

1. **检查事件队列**：是否有新事件到来？（如鼠标点击、键盘输入、定时器超时、网络数据到达、重绘请求等）。
2. **处理事件**：将事件分发给相应的目标对象（`QObject`）。
3. **处理任务**：处理事件循环本身需要执行的任务，比如处理排队的信号槽调用（Qt 的默认连接方式，`Qt::AutoConnection`，在跨线程时是异步的，但在同一线程内是同步的，其实相当于直接函数调用）。

**理想状态**：这个循环执行得飞快，大部分迭代都在几毫秒内完成。用户的操作（事件）能立刻得到处理，界面定时重绘，应用感觉非常流畅。

**卡顿状态**：如果在处理某个事件或任务时，执行了一个非常耗时的操作（比如一个复杂的计算循环，或者一个阻塞的 I/O 调用），那么事件循环就会**停在这个任务上**。在此期间：

1. 新来的用户输入事件（如鼠标移动、点击）只能在队列里等待，无法被处理。用户会觉得界面“冻住了”，没反应。
2. 重绘事件（`QPaintEvent`）也无法被处理。系统要求界面每秒重绘 60 次，但如果某次重绘请求被延迟了几十甚至几百毫秒，动画和滚动就会看起来“卡”了。

### 1.3 如何避免卡顿

解决方案的核心思想是：**保持主线程（事件循环）的轻量和自由，让它能快速响应 UI 事件。**

1. 将耗时操作移至工作线程 (QThread)。使用 `QThread` 或 `QtConcurrent` 来在后台执行繁重的计算和阻塞的 I/O 操作。通过**信号槽机制**将结果发送回主线程，由主线程来安全地更新 UI。
2. 优化 UI 更新频率。对于高速变化的数据，不要每次都更新 UI。可以设置一个定时器，比如每 100ms 更新一次 UI。
3. 优化绘制。确保 `paintEvent()` 方法极其高效。只绘制需要更新的区域（`event->rect()`）。
4. 避免太多事件导致阻塞。过多的信号槽连接和发射确实会导致 Qt 应用卡顿，核心原因依然是 **阻塞了主事件循环（Main Event Loop）**。

### 1.4 信号槽事件分析

过多的信号槽主要通过两种机制导致卡顿：

1. **同步执行的信号槽（同一线程）**：直接阻塞事件循环。
2. **异步排队但处理过载的信号槽（跨线程）**：导致事件队列积压，延迟了其他事件（如UI绘制、用户输入）的处理。

> 1.情况一：同一线程内的信号槽（最需要警惕！）

这是导致卡顿的最常见和最直接的原因。

*   **机制**：在**同一个线程**中发射信号时，Qt 的默认连接方式（`Qt::AutoConnection` 会识别为同线程，退化为 `Qt::DirectConnection`）意味着**槽函数的调用是同步的、立即执行的**。它本质上就像一个直接的函数调用。
*   **过程**：`emit signal()` -> **立即**-> `slot()` 被调用 -> `slot()` 执行完毕 -> `emit signal()` 后面的代码继续执行。
*   **为何卡顿**：
  *   如果你在一个紧凑的循环中（例如 `for(int i = 0; i < 100000; ++i)`）频繁发射信号，并且连接的槽函数执行起来哪怕只是稍微耗时（例如每次执行需要 0.1 毫秒），整个循环就会在主线程中占用可观的CPU时间（100000 * 0.1ms = 10秒！）。
  *   在这**整整10秒**内，主事件循环被这个漫长的循环和槽函数调用完全阻塞，无法处理任何UI事件（重绘、鼠标点击等），应用就会完全卡死。

**结论**：在同一线程中，密集发射信号 + 耗时槽函数 = 直接、严重的卡顿。

> 2.情况二：跨线程的信号槽（通常更安全，但也有极限）

这是 Qt 推荐处理耗时操作的方式：在工作线程执行计算，通过信号槽将结果发回主线程更新UI。

*   **机制**：跨线程发射信号时，默认连接方式（`Qt::AutoConnection` 会识别为跨线程，退化为 `Qt::QueuedConnection`）意味着信号的传递是**异步的**。发射信号时，信号参数会被打包成一个 **事件（QEvent）**，放入接收者线程的事件队列中，然后发射线程立即继续执行，不会等待。
*   **过程**：`工作线程 emit signal()` -> **立即返回** -> 主线程的事件循环在**下次空闲时**从队列中取出这个事件 -> 调用主线程中对应的 `slot()`。
*   **为何也可能卡顿**：
  1.  **槽函数本身耗时**：虽然信号的发射是异步的，不会阻塞工作线程，但**在主线程中执行的槽函数**如果本身很耗时，当它被执行时，依然会阻塞主事件循环。例如，工作线程每秒发射10次信号来更新UI，而主线程的槽函数需要50毫秒来处理数据并更新一个复杂的表格，这就会导致主线程每秒钟有大约500ms被占用，界面帧率会急剧下降，感到明显卡顿。
  2.  **信号发射频率过高**：如果工作线程发射信号的频率极高（例如微秒级别），主线程的事件队列可能会被海量的信号事件塞满。虽然单个事件处理很快，但巨大的数量会导致事件队列膨胀，其他重要事件（如界面重绘事件`QPaintEvent`）需要排队等待很久才能被处理，从而造成界面更新不及时的卡顿感。

**结论**：在跨线程情况下，卡顿的根源不再是信号发射本身，而是（1）主线程槽函数处理太慢**或（2）信号事件在队列中积压过多。

## 02.卡顿监听方案

### 2.1 帧率监控

监控帧率：通常，我们可以通过监控QML页面的帧渲染或者窗口的绘制事件来估算帧率。如果帧率低于某个阈值，我们可以认为发生了卡顿。

设计一个帧率分析器（FrameAnalyzer），用于监控和统计应用程序的帧率（FPS，Frames Per Second）以及检测掉帧情况。

**设计关键技术点和思路**：在每一帧渲染完成后触发，实时计算当前帧率和平均帧率。当前帧率计算fps = 1000.0 / elapsed，其中 elapsed 是帧间时间（毫秒）。使用 QElapsedTimer 来精确测量帧间时间间隔。通过信号（emit）通知外部帧率更新和掉帧事件，便于与其他模块交互。

方案1：基于QQuickWindow的帧率监控

```cpp
connect(quickWindow, &QQuickWindow::frameSwapped, 
        this, &FramerateMonitor::onFrameRendered);

void FramerateMonitor::onFrameRendered() {
    m_frameCount++;  // 每次帧渲染完成才计数
}
```

方案2：监听Qt的绘制事件

```cpp
class FramerateMonitor : public QObject {
private:
    void installEventFilter() {
        // 安装事件过滤器，监听绘制事件
        QApplication::instance()->installEventFilter(this);
    }
    
    bool eventFilter(QObject *obj, QEvent *event) override {
        if (event->type() == QEvent::Paint || 
            event->type() == QEvent::UpdateRequest) {
            m_frameCount++;  // 每次绘制事件才计数
        }
        return QObject::eventFilter(obj, event);
    }
};
```

### 2.2 事件循环监控

监控事件循环：我们可以通过安装一个定时器来定期检查事件循环的处理时间。如果事件循环中处理一个事件的时间过长，则可能发生了卡顿。

设计事件循环监视器（EventLoopWatcher），用于监控 Qt 应用程序的事件循环（QEventLoop）的性能，特别是检测长时间阻塞的事件处理。

设计关键技术点和思路：通过定时器（QTimer）定期检查事件循环的性能，确保事件处理不会长时间阻塞主线程。

### 2.3 Js执行耗时监控

QML 的卡顿很多源于复杂的 JavaScript 操作。自定义性能监控装饰器

**设计原理**：创建一个通用的函数，用来包装任何可能耗时的 JavaScript 函数，并自动记录执行时间。

**实现方式优点**：可重用，对业务代码侵入性相对较小。**缺点**：需要修改函数调用方式。

```qml
// Perf.js
.pragma library

function measure(func, funcName) {
    return function() {
        var start = new Date().getTime();
        try {
            return func.apply(this, arguments);
        } finally {
            var end = new Date().getTime();
            var duration = end - start;
            if (duration > 16) { // 如果超过一帧的时间
                console.warn(`[PERF] ${funcName} took ${duration}ms`);
            }
        }
    };
}
```

### 2.4 渲染性能监控

实现了一个渲染性能分析器（RenderProfiler），用于监控 Qt Quick 应用程序的渲染性能，特别是同步（Synchronizing）和渲染（Rendering）阶段的耗时。

设计关键技术点和思路：

1. 实时监控，通过连接到 QQuickWindow 的信号，实时监控渲染流程中的关键阶段（同步和渲染）。如果同步或渲染阶段的耗时超过阈值，则提出告警通知。 
2. 数据统计，记录同步和渲染阶段的耗时，并计算总耗时、平均耗时以及各阶段的占比。提供统计数据，便于分析渲染性能。

### 2.5 监听方案建议

**设计建议：**

1.  **开发阶段**：**QML Profiler 是首要工具**。遇到卡顿，立即用它来定位是 JavaScript、绑定还是渲染的问题。
2.  **测试阶段**：在测试版本中嵌入**自定义的 FPS 组件**，并设置阈值报警（如连续3帧低于30FPS则记录日志），以便在长时间的自动化测试中发现偶发卡顿。
3.  **针对性优化**：使用 `Console.time()` 或**自定义装饰器**来监控你怀疑的重点函数。使用 `QSG_VISUALIZE` 检查是否存在渲染问题。
4.  **发布阶段**：移除非必要的监控代码（如FPS显示），但可以保留一个轻量级的、可通过配置开关的“性能日志”功能，以便在客户现场出现问题时有据可查。

## 03.卡顿监听实践

### 3.1 方案敲定和选择

实践方案：监控帧率 + 事件循环监控

目标：1.检测到测试复现的界面卡住问题，并能恢复；2.可以感知到我们应用在 主线程做的一些不合理操作，为将来优化做参考

### 3.2 监控帧率实践

大概设计思路：

1. FPS计算（性能指标）：统计一个时间窗口内的总帧数，计算平均帧率，反映整体渲染性能。
2. 卡顿检测（响应性指标）：监控单帧渲染时间间隔，当单帧耗时超过阈值时触发卡顿警告。

```cpp
class FramerateMonitor : public QObject {
  Q_OBJECT

public:
  explicit FramerateMonitor(QObject* parent = nullptr, int intervalMs = 1000);
  ~FramerateMonitor();

  void start();
  void stop();
  
  // 连接到QML窗口进行真正的帧率监控
  void connectToWindow(QQuickWindow* window);
  
  // 设置获取当前页面名称的回调函数
  void setCurrentPageNameCallback(std::function<QString()> callback);
  
  // 设置卡顿检测阈值
  void setStuckThreshold(int thresholdMs);

signals:
  // 发送帧率更新信号。通过信号 fpsUpdated(double fps) 报告当前帧率
  void fpsUpdated(double fps);
  // 通过信号 frameStuck(int durationMs, const QString& pageName) 报告卡顿持续时间和页面名称
  void frameStuck(int durationMs, const QString& pageName);

private slots:
  void checkFrameRate();      // 定期统计和报告帧率
  void onFrameRendered();     // 每帧渲染完成时调用

private:
  QTimer m_timer;             // 定期报告定时器
  QElapsedTimer m_frameTimer; // 用于FPS统计的计时器
  QElapsedTimer m_stuckTimer; // 用于卡顿检测的计时器
  
  qint64 m_lastFrameTime = 0; // 上一帧的时间戳，用于卡顿检测
  int m_frameCount = 0;       // 帧计数器，统计实际渲染的帧数
  int m_intervalMs;           // 帧率报告间隔时间，默认1000ms
  int m_stuckThreshold = 200; // 卡顿检测阈值(ms)，超过此时间认为卡顿
  
  QQuickWindow* m_window = nullptr; // QML窗口引用
  std::function<QString()> m_getCurrentPageNameCallback; // 获取当前页面名称的回调函数
};
```

具体的实现文件如下。实时响应设计

1. 异步信号机制：通过emit fpsUpdated(fps)和emit frameStuck(duration)发送监控结果
2. 非阻塞监控：监控过程不影响主线程的正常渲染流程
3. 即时卡顿检测：每次调用都检查是否发生卡顿，确保及时发现问题

```cpp
// 构造函数
FramerateMonitor::FramerateMonitor(QObject *parent, int intervalMs)
    : QObject(parent), m_intervalMs(intervalMs), m_frameCount(0) {
    
    // 连接定期报告定时器
    connect(&m_timer, &QTimer::timeout, this, &FramerateMonitor::checkFrameRate);
    
    // 设置默认的页面名称回调函数
    m_getCurrentPageNameCallback = []() -> QString {
        return "Unknown";
    };
    
    YT_LOGI("FramerateMonitor created with interval: " << intervalMs << "ms");
}

FramerateMonitor::~FramerateMonitor() {
    stop();
    YT_LOGI("FramerateMonitor destroyed");
}

void FramerateMonitor::connectToWindow(QQuickWindow* window) {
    if (m_window) {
        // 断开之前的连接
        disconnect(m_window, &QQuickWindow::frameSwapped, 
                  this, &FramerateMonitor::onFrameRendered);
        YT_LOGI("Disconnected from previous window");
    }
    
    m_window = window;
    if (m_window) {
        // 连接到真正的帧渲染信号
        connect(m_window, &QQuickWindow::frameSwapped, 
                this, &FramerateMonitor::onFrameRendered);
        YT_LOGI("FramerateMonitor connected to QQuickWindow for real FPS monitoring");
    } else {
        YT_LOGW("FramerateMonitor: window is null, cannot monitor real FPS");
    }
}

void FramerateMonitor::start() {
    m_frameCount = 0;
    m_lastFrameTime = 0;
    m_frameTimer.start();
    m_stuckTimer.start();
    m_timer.start(m_intervalMs);
    
    YT_LOGI("FramerateMonitor started - interval: " << m_intervalMs 
           << "ms, stuck threshold: " << m_stuckThreshold << "ms");
}

void FramerateMonitor::stop() {
    m_timer.stop();
    
    if (m_window) {
        disconnect(m_window, &QQuickWindow::frameSwapped, 
                  this, &FramerateMonitor::onFrameRendered);
    }
    
    YT_LOGI("FramerateMonitor stopped");
}

void FramerateMonitor::setCurrentPageNameCallback(std::function<QString()> callback) {
    m_getCurrentPageNameCallback = callback;
}

void FramerateMonitor::setStuckThreshold(int thresholdMs) {
    if (thresholdMs > 0) {
        m_stuckThreshold = thresholdMs;
        YT_LOGI("FramerateMonitor stuck threshold set to: " << thresholdMs << "ms");
    }
}

// 【核心】每帧渲染完成时调用 - 真正的帧率统计
void FramerateMonitor::onFrameRendered() {
    m_frameCount++;  // 真正的帧计数：每次QML渲染完一帧时+1
    
    // 卡顿检测：检测单帧渲染时间
    const qint64 currentTime = m_stuckTimer.elapsed();
    if (m_lastFrameTime > 0) {
        const qint64 frameDuration = currentTime - m_lastFrameTime;
        
        // 检测卡顿：单帧时间超过阈值
        if (frameDuration > m_stuckThreshold) {
            QString pageName = "Unknown";
            if (m_getCurrentPageNameCallback) {
                pageName = m_getCurrentPageNameCallback();
            }
            
            YT_LOGW("Frame stuck detected on page: " << pageName.toStdString() 
                   << " duration: " << frameDuration << "ms (threshold: " 
                   << m_stuckThreshold << "ms)");
            emit frameStuck(static_cast<int>(frameDuration), pageName);
        }
    }
    m_lastFrameTime = currentTime;
}

/**
 * @brief 定期统计和报告帧率。每1000ms统计一次累积的帧数，计算并报告FPS
 * 
 * 这个方法由定时器定期调用，负责：
 * 1. 统计在时间间隔内的实际渲染帧数
 * 2. 计算真实的FPS值
 * 3. 发出帧率更新信号
 * 4. 重置计数器开始新一轮统计
 * 
 * 真正的FPS计算原理：
 * - m_frameCount 记录的是实际渲染的帧数（通过frameSwapped信号统计）
 * - 使用公式：FPS = 实际帧数 / (时间间隔/1000)
 * - 这样计算出的是真实的渲染帧率，而不是定时器频率
 */
void FramerateMonitor::checkFrameRate() {
    const qint64 elapsed = m_frameTimer.elapsed();
    
    if (elapsed >= m_intervalMs) {
        if (m_frameCount > 0) {
            // 计算真正的帧率：实际渲染帧数 / 时间
            const double fps = m_frameCount / (elapsed / 1000.0);
            
            YT_LOGI("Real FPS: " << fps << " (frames: " << m_frameCount 
                   << ", time: " << elapsed << "ms)");
            
            emit fpsUpdated(fps);
        } else {
            // 没有检测到帧渲染，可能窗口未连接或应用暂停
            YT_LOGW("No frames detected in " << elapsed << "ms - window connected: " 
                   << (m_window != nullptr));
            emit fpsUpdated(0.0);
        }
        
        // 重置计数器开始新一轮统计
        m_frameCount = 0;
        m_frameTimer.restart();
    }
}
```

**FPS计算原理**：1.统计在设定时间间隔内的帧数；2.使用公式：FPS = 帧数 / (时间间隔/1000)；3.达到统计间隔后重置计数器，开始新一轮统计。

**卡顿检测原理**：1.记录每次调用的时间戳；2.计算与上次调用的时间间隔；3.如果间隔超过阈值，认为发生了帧卡顿。

潜在改进点，当前实现存在一个逻辑问题：checkFrameRate()是由定时器触发的，但它试图统计"帧数"，这实际上统计的是定时器触发次数，而不是真正的渲染帧数。

更准确的做法应该是在每次实际渲染完成时调用一个onFrameRendered()方法来增加帧计数。



### 3.3 监控事件循环实践

核心设计思想概括：事件循环监控器采用了事件过滤器拦截 + 时间间隔分析的设计思想

1. 全局事件拦截机制：1.利用Qt的QApplication::installEventFilter()机制；2.拦截所有Qt事件：鼠标、键盘、绘制、定时器等所有事件都会经过监控点；3.非侵入式监控：不修改原有业务逻辑，纯粹作为观察者存在。
2. 时间间隔阻塞检测算法：1.通过测量连续事件之间的时间间隔来判断UI线程是否被阻塞；2.正常情况：事件处理快速，间隔很短；3.阻塞情况：某个事件处理耗时过长，导致后续事件延迟。

```cpp
  Q_OBJECT
public:
  EventLoopMonitor(QObject *parent = nullptr);
  ~EventLoopMonitor();
  // 启动监控功能

  // 停止监控功能

  // 内联常量函数，获取当前设置的阈值
  int getThreshold() const { return m_threshold; }

signals:  // Qt信号访问控制符，定义可发射的信号
  // 事件循环阻塞信号，携带阻塞持续时间（毫秒）
  void eventLoopBlocked(int durationMs);

private:
  bool eventFilter(QObject *obj, QEvent *event) override;
  // 高精度计时器成员变量，用于测量事件处理时间
  QElapsedTimer m_eventTimer;
  // 监控状态标志，默认为false（未监控状态）

};
```

设计优势：1.全面覆盖：监控所有类型的Qt事件，无遗漏；2.实时性强：事件级别的监控粒度，响应迅速；3.轻量级：仅记录时间戳和简单比较，性能开销极小

```cpp
    if (!m_monitoring) {
        m_monitoring = true;
        m_lastEventTime = 0;
        m_eventTimer.start();
        qApp->installEventFilter(this);
    }
}

void EventLoopMonitor::stop() {
    if (m_monitoring) {
        m_monitoring = false;
        qApp->removeEventFilter(this);
    }
}   

bool EventLoopMonitor::eventFilter(QObject *obj, QEvent *event) {
    static qint64 lastEventTime = 0;
    if(m_monitoring) {
        const qint64 now = QDateTime::currentMSecsSinceEpoch();
        // 检测事件处理间隔
        if(lastEventTime > 0) {
            const qint64 delta = now - lastEventTime;
            if(delta > m_threshold) {
                emit eventLoopBlocked(static_cast<int>(delta));
            }
        }
        lastEventTime = now;
    }
    return QObject::eventFilter(obj, event);
}
```

1. 只能检测到阻塞发生，但无法定位具体的阻塞代码位置
2. 时间间隔测量：只能知道两个事件之间的时间差，不知道是哪个具体操作导致的阻塞
3. 缺乏调用栈信息：无法追踪到具体的函数调用链

## 06.帧率监控原理

### 6.1 帧率监控核心

`connect(m_window, &QQuickWindow::frameSwapped, this, &FramerateMonitor::onFrameRendered);` 如何实现帧率监控？

这个连接的作用是监控QQuickWindow的帧率。具体来说，它连接了QQuickWindow的frameSwapped信号和FramerateMonitor类的onFrameRendered槽函数。

**QQuickWindow::frameSwapped信号**：

在Qt Quick中，QQuickWindow是用于显示Qt Quick场景的窗口。当一帧渲染完成并且已经交换到屏幕（即交换缓冲区，swap buffers）时，会发出frameSwapped信号。

这个信号表示一帧已经呈现在屏幕上。注意，这个信号是在GPU将后缓冲区交换到前缓冲区之后发出的，也就是我们通常说的垂直同步（VSync）之后。

**FramerateMonitor::onFrameRendered槽函数**：

这是一个自定义的槽函数，用于记录帧渲染完成的时间点。在这个函数中，我们可以记录当前时间，然后计算与上一帧的时间间隔，从而得到帧率。

### 6.2 frameSwapped本质

为什么使用frameSwapped信号？因为frameSwapped信号是在一帧真正显示到屏幕之后发出的，所以它是最准确的帧结束时间点。使用这个信号可以避免将渲染队列中的等待时间计算在内，从而得到真实的显示帧率。

`frameSwapped` 信号的本质

- **触发时机**：在 GPU 完成一帧渲染并将前后缓冲区交换后触发
- **技术含义**：表示一帧图像已经完全呈现到屏幕上
- **与渲染循环的关系**：
  ```plaintext
  QQuickWindow 渲染循环：
  1. 同步阶段：处理动画、更新场景
  2. 渲染阶段：生成命令列表，提交到GPU
  3. 交换阶段：交换前后缓冲区 ← frameSwapped 在此刻触发
  4. 等待垂直同步(VSync)
  ```

### 6.3 帧率一般是多少

垂直同步（VSync）的影响：大多数显示器的刷新率是60Hz，这意味着每秒最多显示60帧。如果应用程序开启了垂直同步（默认情况下Qt可能开启），那么最大帧率会被限制在显示器的刷新率（通常是60FPS）。有些显示器的刷新率可能更高（如120Hz、144Hz等），那么最大帧率可能会相应提高。

Qt Quick应用程序的默认帧率：对于Qt Quick应用程序，默认情况下，如果场景没有变化，渲染可能会被抑制，因此帧率可能会低于最大值。当有动画或变化时，会尽量以最大帧率运行。

正常帧率：如果应用程序运行在60Hz的显示器上，并且没有性能问题，那么正常的帧率应该接近60FPS。如果帧率低于60，可能意味着存在性能瓶颈。

正常帧率范围：在60Hz的显示器上，如果应用程序能够稳定在60FPS，那么这是理想的。如果帧率波动很大，或者持续低于60，可能需要优化。但是，如果应用程序不需要高帧率（例如，只是显示静态内容），那么帧率可以很低，甚至为0（因为没有帧交换）。

### 6.4 帧率影响因素

1. 界面复杂度。过多的QML元素，高分辨率图片
2. 布局计算。频繁的布局更新，复杂的锚点关系
3. JavaScript执行。复杂的QML JavaScript计算，频繁的属性绑定更新
4. 硬件和系统因素。

## 07.事件监控原理
### 7.5 性能分析优化

事件监控对UI线程的影响。这是一个很重要的问题，因为性能监控本身不应该成为性能瓶颈。事件监控对UI线程的影响分析

原始实现的问题：

1. 每个事件都被监控：包括高频的MouseMove、Paint等事件 
2. 无采样控制：100%监控所有事件 
3. 固定开销：每个事件都执行时间计算和比较

优化后的性能特性：

1. 轻量级模式（默认启用）：跳过高频但不重要的事件类型；只监控关键的用户交互和业务事件。性能影响：几乎为零 
2. 采样率控制：可设置1-100%的监控采样率。默认100%，可根据需要调整；50%采样率可减少一半性能开销 
3. 延迟计算：只在检测到阻塞时才获取页面名称；避免不必要的回调函数调用
