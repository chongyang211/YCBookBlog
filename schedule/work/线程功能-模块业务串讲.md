# facility/thread 线程基础设施 · 业务串讲

> **一句话定位**：全工程的线程底座——`Thread` 把「一条命名线程」封装成「一个 io_context + 一个队列」，`Post/CoSpawn` 即「把任务挂到该线程串行执行」；`Threads` 提供 6 条全局命名线程（main/network/heartbeat/iot/ota_install/license）+ 动态建线程入口；`ThreadPool`（2 线程）专职**阻塞任务卸载**（磁盘查询/同步 HTTP/MMKV 刷盘），结果自动回到发起线程。前八篇串讲里反复出现的「XXThread 语义」，根都在这 8 个文件、约 300 行。
> **场次**：45 分钟（代码量小但语义密度高，难点在线程即队列模型与 AsyncExec 语义）　**听众**：同组开发 / 评审人 / 后续接手者
> **对照模版**：`06.技术模版/04.业务串讲的模版.md` 第 08 章　**代码基线**：`palm_app_linux/src/facility/thread/`（8 文件全量精读 + 全仓调用方核对，2026-10-08 审阅）

## 1. 需求与业务背景  [10min · 先现象后价值]

### 1.1 需求来源与问题
- **来源**：工程里协程（asio）与阻塞调用（SE 芯片、MMKV、磁盘 SQL、同步 HTTP）长期共存；各业务域需要可预期的执行位置（「这段代码跑在哪条线程」）。
- **问题**：① 若不收口线程创建，`new std::thread` 散落各处——线程数失控、无名线程无法排障（`top`/`ps` 里全是匿名）；② 「业务对象 + 该对象的线程」需要稳定绑定（report 模块的非线程安全基类全靠「固定线程执行」保证）；③ 主线程要同时跑 asio 与宿主事件泵（插件化场景）；④ 阻塞调用若占用业务线程，会把整条队列堵死（识别线程卡 3 秒 = 漏单）。
- **目标**：命名线程创建收口；每线程一个队列、入队即串行；`thread_local` 让任意代码拿到「当前线程」的入口；阻塞任务卸载到专用池并自动回传结果。

### 1.2 业务边界
- **做**：Thread/ThreadPool 封装、6 全局线程、动态线程与可扩展线程、this_thread 快捷入口。
- **不做**：线程优先级/亲和性设置；池的动态扩缩容（固定 2）；跨线程任务取消（Post 出去无法撤回）；进程级退出编排（各线程 Stop 顺序由持有方决定）。

### 1.3 关键业务规则
- **6 条全局线程**（threads.h:14-25，名字数组 static_assert 对齐，threads.cpp:9-10）：
  | 线程 | 职责（来自前八篇串讲的使用现场） |
  |---|---|
  | `main`（=kUiThread 别名） | DeviceFsm 协程、BiComm 主线程约束；**借 main 函数线程运行**（不新建） |
  | `network` | 网络检测/测速的阻塞执行（co_spawn 桥）、MQTT 跨线程 Reconnect |
  | `heartbeat` | report 模块序列化入队（FillBeforeQueue 的线程归属安全性） |
  | `iot` | 指令分发（DispatchCmd）、OTA 调度 |
  | `ota_install` | 升级安装 |
  | `license` | **激活+授权互斥共享**（Story 136057693：SE 操作串行化） |
- **动态线程**：`CreateThread` / `CreateExtensibleThread`——paas_shadow 的 `"property"`、MqttService 的 `"mqtt"` 走这里。
- **ThreadPool 用途**（全仓调用方已核对）：**磁盘/阻塞**——`COUNT(*)` 查询（pos_request_handler.cpp:674/:684，注释「AC-10b 不得 MainThread 直查」）、识别网络请求（pos_session.cpp:341、palm_session_controller.cpp:280/:381/:921）、MMKV 刷盘（config.cpp:224）、系统属性（device.cpp:236）、CPU 模式（system_interface.cpp:223）、verify_record。

### 1.4 改动范围（模块组成）
- **[基类]** `thread.h/.cpp`（~140 行）：Thread + this_thread 命名空间。
- **[全局表]** `threads.h/.cpp`：6 线程枚举/名字、Init、CreateThread。
- **[扩展]** `extensible_thread.h/.cpp`：宿主事件泵桥（main 专用）。
- **[池]** `thread_pool.h/.cpp`：2 线程 + AsyncExec。

## 2. 整体设计与模块划分  [10min · 先图后讲]

### 2.1 架构与分层
```
 Application（friend）── RunMainThread：main 函数线程借跑（ExtensibleThread）
        │
 Threads（单例，持 6 个 unique_ptr<Thread>）
   ├ main ← StartInCurrentThread（不建线程）
   ├ network / heartbeat / iot / ota_install / license ← new Thread + Start()
   └ ThreadPool::Instance()->Start()（2 条 thr_p_0/1）
 ┌────────────────────────────────────────────┐
 │ Thread = io_context + std::thread           │
 │   Post(f)   → 挂到本线程队列，串行执行         │
 │   CoSpawn(c) → 协程跑在本线程 executor        │
 │   Executor() → 交给别的模块做桥（co_spawn 目标）│
 │ this_thread::Handle() ← thread_local 注册    │
 ├────────────────────────────────────────────┤
 │ ExtensibleThread：RunCtx = 循环{            │
 │   run_one();  plugin_ctx_handler_();  }      │
 │  （asio 任务与宿主事件泵交替）                │
 ├────────────────────────────────────────────┤
 │ ThreadPool（io_context 共享 + 2 线程）        │
 │   AsyncExec(ex, token, func, args...)        │
 │   → 任务 post 到池线程执行                    │
 │   → 结果 post 回调用方 executor，handler(ret)  │
 └────────────────────────────────────────────┘
```
分层关键：**「线程即队列」**——每条 Thread 就是一个 io_context，Post 的任务是这条线程的私有队列，天然 FIFO 串行；**「executor 即线程句柄」**——把 `Executor()` 交给别的模块（如 `co_spawn(Threads::NetworkThread()->Executor(), …)`），就是在往这条线程的队列里放东西。桥模式（detection/mqtt/report 八篇串讲反复出现的写法）全部建立在这个语义上。

### 2.2 模块划分与职责
| 模块 | 职责 | 切分理由 |
|---|---|---|
| `Thread` | 一条命名线程 + io_context | 最小单元 |
| `this_thread` | 当前线程的 thread_local 快捷入口 | 让库代码（base_cmd 等）免传参拿到「我跑在哪」 |
| `Threads` | 全局线程表 + 动态创建收口 | 线程创建不允许散落 |
| `ExtensibleThread` | asio 与宿主事件泵共存 | 仅 main 用（编译开关） |
| `ThreadPool` | 阻塞卸载 + 结果回传 | 业务线程不被阻塞调用堵死 |

### 2.3 核心数据流（一次识别请求的线程旅行）
```
MainThread: 识别协程发起
 → co_await ThreadPool::AsyncExec(this_thread::Executor(), use_awaitable,
        [req_data]{ /* 同步 HTTP 刷掌请求 */ })        pos_session.cpp:341
    ① 任务 post 到 thr_p_0/1 执行（阻塞 3s 不影响任何业务线程）
    ② 完成后 handler(ret) post 回 MainThread executor
 → MainThread 协程恢复，拿到结果继续 FSM 决策
（对比：网络检测/测速把阻塞体 co_spawn 到 network 线程——
  两种卸载选择：专用命名线程 vs 共享池，见 4.4）
```

## 3. 逐模块实现讲解  [25min · 业务意图先行]

### 3.1 `Thread`　thread.h/.cpp
- **构造**：`ctx_(1)`（thread.cpp:29）——io_context 并发提示 1，**单线程跑 io_context 的正确姿势**（不预留多线程数据结构）。
- **Start()**（:19-25）：建 std::thread → `SetupThreadLocal`（thread.cpp:31-35：`this_thr=this` 注册 thread_local、取 pthread_self、`pthread_setname_np`）→ `work_guard`（防 run() 无任务时退出）→ `ctx_.run()`。
- **StartInCurrentThread**（thread.h:53-59）：不建线程，**借当前线程**跑——只有 main 用（Application 启动时）。
- **Stop()**（thread.cpp:27）：`ctx_.stop()`——**run() 返回但队列不排空**（见 6.2-T1）；析构 Stop + join（:12-17，等在途任务跑完）。
- **this_thread 命名空间**（thread.h:87-101）：`Handle()` 返回 thread_local 的 `this_thr`；`Post/CoSpawn/Executor` 均转发到**当前线程**——base_cmd 的 `WaitSchedExecuteTimeRunTask` 用 `this_thread::Executor()` 建定时器（base_cmd.h:128），即「把定时器挂到调用方自己的线程」。
- **protected 构造 + friend Threads**——外部不能 `new Thread`，线程创建必须经 `Threads::CreateThread`（收口）。

### 3.2 `Threads`　threads.h/.cpp
- **Init()**（threads.cpp:37-44）：从 `kMainThread+1` 循环创建 5 条（**跳过 main**——main 由 `RunMainThread` 借线程启动，threads.h:50-59，`USE_PLUGGABLE_MAIN_IO_CTX` 时是 ExtensibleThread）+ `ThreadPool::Start()`。
- **CreateThread/CreateExtensibleThread**（:17-29）：动态线程——`new` + SetName + Start，**返回裸指针**（见 6.2-T2）。
- **kUiThread=kMainThread 别名**（threads.h:16）：历史兼容残留。

### 3.3 `ExtensibleThread`　extensible_thread.cpp
- **RunCtx**（:11-16）：`while(!stopped){ run_one(); plugin_ctx_handler_(); }`——每处理一个 asio 任务，泵一次宿主事件。`SetPluginCtxHandler` 经 `ctx_.dispatch` **在线程内**换 handler（:7-9，线程安全赋值）。
- 用途：仅 main（编译开关 `USE_PLUGGABLE_MAIN_IO_CTX`）——「asio 事件循环与宿主事件泵共存」的桥。

### 3.4 `ThreadPool`　thread_pool.h/.cpp
- **2 条线程共享一个 io_context**（名字 `thr_p_0/1`，thread_pool.cpp:26）。
- **AsyncExec**（thread_pool.h:40-71）：asio completion-token 风格——`async_initiate` 把 `func(args...)` 打包 post 到池线程执行；完成后把 `handler(ret)` post 回**调用方传入的 executor**。`HandlerTypeSelector` 处理 void/非 void 的 handler 签名差异（:30-37）。
- 调用现场（全仓已核对）：磁盘 `COUNT(*)`（AC-10b 明令禁止 MainThread 直查）、识别同步 HTTP、MMKV `sync`、系统属性、CPU 模式——**全是「不能堵业务线程」的场景**。

## 4. 核心代码实现细节与原理（重点）  [10min · 讲透原理]

### 4.1 深挖①：「线程即队列」模型
- 每条 Thread 一个 io_context，Post 的任务串行 FIFO——所以**「跑在 XXThread 上」=「与该线程上其他任务互斥」**。report 模块的非线程安全基类（FillBeforeQueue 只在 HeartBeatThread）、激活的 LicenseThread（SE 串行化）、iot 的 DispatchCmd（IotThread）全部建立在这条不变量上——**不加锁，用线程归属换并发安全**（业务上报串讲 4.2 同一论断）。
- `ctx_(1)` 与 work_guard 的配合：并发提示 1 告诉 asio 不要为多线程预留；work_guard 防队空时 run() 返回线程退出。

### 4.2 深挖②：this_thread 的 thread_local 机制
```cpp
// thread.cpp:10
static thread_local Thread* this_thr = nullptr;
// SetupThreadLocal（:31-35）：每条 palm 线程启动时注册自己
this_thr = this;  id_ = pthread_self();  pthread_setname_np(...);
```
- **价值**：库代码（base_cmd、Device::GetSystemProp）不必知道「我被谁调用」——`this_thread::Executor()` 自动挂到调用方线程。`WaitSchedExecuteTimeRunTask` 的定时器因此天然与命令的其余部分同线程互斥。
- **边界**：thread_local 只在 `SetupThreadLocal` 走过的线程有值——**第三方线程（detached std::thread、外部回调线程）上 `Handle()` 返回 nullptr**，调 this_thread::Post 即空指针崩溃（6.2-T3）。

### 4.3 深挖③：main 的两个特殊形态
- **借线程**：`StartInCurrentThread`——main 函数线程直接 `ctx_.run()`，main 永不返回（Application 生命周期即 main 生命周期）；好处是 UI/宿主框架认得「主线程」就是这条。
- **双泵交替**：ExtensibleThread 的 `run_one + plugin_ctx_handler`——**注意特征**：asio 无任务时 `run_one` 阻塞等待，宿主泵不会被执行（宿主事件只在 asio 有活动的间隙被泵）。这是该编译开关的行为特征，宿主事件频率与 asio 活动耦合（6.2-T6）。

### 4.4 深挖④：AsyncExec 的「跨线程执行、结果回发起线程」
```
调用方线程 A：co_await Pool->AsyncExec(A 的 executor, token, func)
  ① func 打包 post 到池 ctx_（thr_p_0/1 某条执行，阻塞无所谓）
  ② 结果 ret 捕获，post 回 A 的 executor
  ③ A 上 handler(ret) 触发——协程恢复/回调执行都在 A
```
- **语义本质**：asio 的标准「offload + completion」封装，等价于 `boost::asio::post` 的双向版——**发起线程不阻塞（co_await 挂起），池线程不持有调用方状态（ret 按值带回）**。
- **两种卸载的选型**（结合 2.3）：长而独占的领域（网络检测最坏 11s、测速 15s）用**专用命名线程**（network）；短而并发的杂项（DB/属性/刷盘毫秒级）用**共享池**。判断依据：任务时长 × 频率是否值得一条专属线程。

## 5. 边界、异常与测试  [5min · 别一笔带过]

### 5.1 异常与降级
- Stop 后 Post：任务入队但永不执行，**无告警**（io_context::stop 语义如此）。
- `GlobalThread(type)` 在 `Threads::Init()` 之前调用：`.get()` 返回 null——激活模块 `PostToLicenseThread` 的降级分支（激活串讲 A6）防御的就是这个窗口。
- 池满载：AsyncExec 任务在池队列排队——无拒绝机制，只是延迟。

### 5.2 边界条件
| 场景 | 行为 |
|---|---|
| Post 后线程 Stop | 任务丢弃不执行、无告警（6.2-T1） |
| 第三方线程调 this_thread | Handle()=nullptr → 崩溃（6.2-T3） |
| Post 出去的任务想撤回 | 无取消机制——设计上「发射后不管」 |
| 动态线程忘记 delete | 线程永跑 + 泄漏（6.2-T2） |
| main 上 Post 大任务 | 堵 UI——AC-10b 类规则靠 review 保证 |

### 5.3 测试覆盖
- **零单测**。本模块是全工程被引用最广的设施（八篇串讲全部依赖其语义），却没有一行测试——「Post 串行性」「AsyncExec 回传线程正确性」「Stop 丢弃语义」全靠使用方自觉。属于底座型技术债：语义改动无护栏，只能靠全量回归。

## 6. 踩坑与接手注意事项（含审阅发现）  [审阅 + 雷区]

### 6.1 开发中坑
- **「跑在哪条线程」是接口契约的一部分**：跨模块调用时先确认对方的线程约束（如 BiComm 必须 MainThread、SE 必须 LicenseThread）——选错线程轻则竞态、重则 UAF（各串讲雷区里已有多例）。
- **不要在业务线程上做阻塞调用**：同步 HTTP/磁盘一律 `AsyncExec` 或专用线程——识别请求 3 秒堵住 MainThread 的代价是漏单。

### 6.2 接手者雷区地图（⚠️ 本次审阅发现）
| # | 现象 | 代码位置 | 风险 / 建议 |
|---|---|---|---|
| **T1** | **Stop() 丢弃队列任务且无告警**：`ctx_.stop()` 让 run() 返回，队列剩余任务不执行；Stop 后 Post 静默入队永不跑 | thread.cpp:27 | 销毁线程前先确认队列空（或 drain：stop 前循环 `run_for`）；至少给 Stop 加「队列非空」LOG_W |
| **T2** | **动态线程裸指针无生命周期管理**：`CreateThread` 返回裸指针，Threads 只持 6 个全局线程；property/mqtt 线程归调用方 delete，忘记=永跑+泄漏；`~Thread` 是 Stop+join（**阻塞等在途任务**，在锁内 delete 会死锁） | threads.cpp:17-29 | 改 `unique_ptr` 返回或注册表托管；注意 ~Thread 的 join 语义——持有锁的线程上 delete Thread = 死锁 |
| **T3** | **this_thread 在非 palm 线程返回 nullptr**：detached std::thread（captureLog）/外部回调线程（MQTT 库内）调 this_thread::Post → 空指针崩溃 | thread.cpp:10/:39 | 库代码在不确定线程语境处先判 `Handle()` 非空，降级为显式线程参数 |
| **T4** | 池仅 2 线程、无队列上限：识别 DB+网络并发时 AsyncExec 排队延迟叠加（可观测为「识别变慢」但根因在池） | thread_pool.h:27 | 高峰期日志带池队列深度；必要时扩容——但先确认 2 线程是否真瓶颈 |
| **T5** | `kUiThread=kMainThread` 别名残留；`Name()`/`GetName()` 重复定义 | threads.h:16、thread.h:29/:44 | 清理别名与重复方法（外部引用较多，分批改） |
| **T6** | ExtensibleThread 的宿主泵与 asio 活动耦合：`run_one` 阻塞期间宿主事件不被泵 | extensible_thread.cpp:11-16 | 仅 `USE_PLUGGABLE_MAIN_IO_CTX` 生效；宿主事件低延迟要求高时改 `run_for(0ms)+自旋` 或宿主泵独立线程 |
| **T7** | `Threads::Init()` 前调 GlobalThread 得 null——依赖 Application 启动顺序的隐式契约 | threads.h:32 | 防御性判空已有先例（激活 A6）；新模块启动期谨慎使用 |

**给接手者的硬提醒**：
- 🔴 **选线程先于写代码**：新功能的线程选型（6 全局 / 动态命名 / 池）在设计阶段定，写完再挪 = 全链路竞态排查。
- 🟡 `CoSpawn` 的协程**不要**在体内长时间阻塞——它占的就是那条业务线程；要阻塞先 `AsyncExec`。
- 🟡 跨线程 Post 捕获对象生命周期自负（八篇串讲的 alive_flag/weak_ptr 模式是标准答案）——本模块不提供任何保证。
