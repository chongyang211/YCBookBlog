# service/iot 平台指令功能 · 业务串讲

> **一句话定位**：平台对设备的**运维指令通道**——`IotService` 双通道拉指令（HTTP 轮询 60s/300s + MQTT type2 实时推送），经「回执 → 时间可信 → 过期 → 三层去重 → 状态门」校验链后按 `cmd_name` 分发给 10 个命令对象；每个命令继承 `IotBaseCmd` 状态机，把执行状态经 `ReliableRequest` 入队可靠送达（断网/重启补发），高危命令（重启/恢复出厂）靠「先回执、后执行」时序保证重启后平台不丢单。
> **场次**：60 分钟（核心是 base_cmd 状态机与 10 个命令的共性/个性，踩坑集中在 shell 拼接安全）　**听众**：同组开发 / 评审人 / 后续接手者
> **对照模版**：`06.技术模版/04.业务串讲的模版.md` 第 08 章　**代码基线**：`palm_app_linux/src/service/iot/`（iot_service + cmds/ 21 文件 + entity/ 5 文件，2026-10-08 审阅；高危结论已逐行实测）

## 1. 需求与业务背景  [10min · 先现象后价值]

### 1.1 需求来源与问题
- **来源**：平台需要远程运维设备——重启/重启 App/恢复出厂（高危三件套）、日志采集上传/清理/存储 dump（排障三件套）、NTP 对时、远程开门、BiComm 代理（转发给上位机 POS 执行）。
- **问题**：① 指令回执若走一次性 HTTP，**断网/重启即丢**——平台永远不知道指令执行到哪一步，也不敢下发高危指令；② 同一指令经 MQTT 推送与 HTTP 轮询**双通道重复到达**，必须幂等；③ 时间不可信（1970）时无法校验过期，已过期指令可能被误放行。
- **目标**：秒级触达（MQTT）+ 轮询兜底；回执可靠送达（断电不丢）；跨重启幂等；时间不可信时安全优先拒绝。

### 1.2 业务边界
- **做**：指令拉取/分发/去重/状态机/可靠回执；10 个内置命令；BiComm 代理转发；uploadLog 双向（平台下发 + 设备主动发起 `log-upload-instructions` 反向通道）。
- **不做**：指令的鉴权与排程（平台侧）；`DeviceAction` 的实际重启/擦除动作（facility 层）；BiComm 协议本体（biz/pos）。

### 1.3 关键业务规则
- **指令状态机**（base_cmd.h:22-33，与平台 InstructionState 一致）：10→20(DEVICE_RECEIVED)→30(DISPATCHED)→40(EXECUTING)→50/60(SUCC/FAIL 终态)；70/80/90 为平台侧超时/取消。字符串↔数值三种互转（:36-77，HTTP JSON 用字符串、proto 用数值）。
- **回执可靠送达语义**：request_id = `id_seq_state`（同 seq 不同 state 不撞键）；task_id = `id_seq`（**同任务状态互斥**——终态入队清掉未送达的旧中间态）；**终态满重试、中间态快速放弃**（iot_service.cpp:62-70 注释：过时的中间态无价值）。
- **高危命令时序**：`SetSuccessState`（入队刷盘）→ `WaitLastTerminalSent(5s)`（尽力确认送达）→ 才执行重启/擦除——**先回执、后执行**。

### 1.4 改动范围（模块组成）
- **[中枢]** `iot_service.h/.cpp`：拉取（HTTP `execute-list` + MQTT type2→proto→entity 复用）、校验链、cmd_name 分发 if-链、轮询间隔切换。
- **[基类]** `base_cmd.h/.cpp`：状态机 + 可靠上报 + `KeepSelf/DeleteLater` 生命周期自持 + 定时执行。
- **[命令族]** cmds/ 10 组：reboot/restartApp/factoryReset（高危三件套）、uploadLog/captureLog/logClean/dumpStorageInfo（日志四件套）、syncNtp、remoteDoorOpen、BiComm 代理基类。
- **[实体]** entity/ 5 文件 + 2 gtest（round-trip）。

## 2. 整体设计与模块划分  [10min · 先图后讲]

### 2.1 架构与分层
```
 平台指令 ──HTTP GET /iot/devices/{sn}/instructions/execute-list（60s/300s 轮询）
        └──MQTT type2 down/{sn}（实时推送，linkcomm.proto InstructionLinkMsg）
 ┌─────────────────────────────────────────────────────┐
 │ IotService（单例）                                    │
 │  PullInstructionTask → RequestPullcmd（HTTP）         │
 │  OnMqttInstructionMessage（proto→entity 复用）          │
 │  DispatchCmd 校验链：                                  │
 │    ① 回执 20 → ② 时间可信守卫 → ③ 过期校验 →           │
 │    ④ 三层去重 → ⑤ snapshot 状态门 → DispatchToInternal │
 │  UpdatePollingInterval（MQTT 在线且首拉成功 → 300s）     │
 ├─────────────────────────────────────────────────────┤
 │ IotBaseCmd（状态机 + ReliableRequest 回执 + 自持）      │
 │   ├ 高危三件套：先回执→Wait(5s)→异步执行                 │
 │   ├ 日志四件套：collect→presign→PUT / SCOPE_EXIT 清理   │
 │   ├ syncNtp：自研 SNTP → 写 RTC                        │
 │   └ remoteDoorOpen/BiComm：代理上位机，时效 90s 守卫     │
 └─────────────────────────────────────────────────────┘
   依赖：ReliableRequest（回执队列）、Network、MqttService、
        TimeStateManager（时间可信）、BaseFrequencyScheduler、MMKV
```
分层关键：**「分发」与「执行」彻底分离**——IotService 只做校验与路由，命令对象自治（自持生命周期 + 自报状态）；**双通道在 entity 层合流**（MQTT proto 转成与 HTTP 相同的 `entity::Instruction`，走同一条 DispatchCmd），校验链只写一份。

### 2.2 模块划分与职责
| 模块 | 职责 | 切分理由 |
|---|---|---|
| `IotService` | 拉取/校验/分发/间隔切换 | 唯一入口，幂等收口 |
| `IotBaseCmd` | 状态机/可靠回执/生命周期/定时执行 | 10 个命令共享的全部机制 |
| 高危三件套 | reboot/restartApp/factoryReset | 同构外壳，动作委托 `DeviceAction` |
| 日志四件套 | uploadLog/captureLog/logClean/dumpStorage | 排障域 |
| BiComm 族 | 代理转发上位机 | 不自己干活，只做时效守卫+回调 |

### 2.3 核心数据流（平台下发重启指令为例）
```
平台创建指令（id, name=restartDevice, execute_time, expire_time, snapshot.seq）
 → MQTT type2 推送（或 60s 轮询拉到）
 → IotThread: DispatchCmd
     ① ReportInstructionState(20 DEVICE_RECEIVED)   —— ReliableRequest 入队
     ② TimeStateManager::IsTimeTrusted()？不可信 → 报 60 拒绝
     ③ expire_time <= now？过期 → 报 60 拒绝
     ④ 内存 deque(16) + MMKV(24h TTL) 查重
     ⑤ snapshot.state 必须是 10/20/30（未处理过）
 → IotCmdRebootDevice::Create(...)->Start()
     KeepSelf → 基类 Start（报 30 DISPATCHED）
     → WaitSchedExecuteTimeRunTask（支持平台定时下发）
     → SetExecutingState(40) + UploadStateNow()
     → SetSuccessState("")：终态同步入队刷盘 + 挂 promise + DeleteLater
     → WaitLastTerminalSent(5s)：等 ReliableRequest 送达回调 set_value
     → DeviceAction::RebootDeviceAsync()  ← 先回执后执行
（若 5s 内未送达：返回 false 但照样重启——MMKV 持久化保证开机后补发）
```

## 3. 逐模块实现讲解  [25min · 业务意图先行]

### 3.1 `IotService::Init` 与双通道切换　iot_service.cpp:88-150
- **要点**：MMKV 去重实例（`iot_cmd_dedup`，TTL 24h，:90-105 启动恢复已执行 id）；60s 调度任务（`requires_time_synced=true`，:107-113）；注册 MQTT type2 handler（:116-121）；**间隔切换规则**（:123-134 + :145-150）：MQTT 连接只标记不切换，**须本次连接周期内 HTTP 首拉成功**才 60s→300s；断连重置回 60s——与 paas_shadow 同款「MQTT 为主、HTTP 兜底」语义。

### 3.2 `DispatchCmd` 校验链　:231-306（模块的心脏）
顺序与理由（**顺序本身就是安全设计**，别调换）：
1. **回执 20 先行**（:252-253）：平台先销「已到达」，后续拒绝也有痕迹；
2. **时间可信守卫**（:259-265，Story 136515343）：1970 状态下无法校验过期，**安全优先拒绝**（宁可误杀不可误放行）；
3. **过期校验**（:266-272）：仅当平台下发了 expire_time 才做；
4. **三层去重**（:276-290）：内存 deque（16 条）+ MMKV（跨重启、24h TTL）——通过后**同时写入两层**；
5. **snapshot 状态门**（:296-302）：snapshot.state 必须是 10/20/30（未处理过）——**这里不能上报失败**，否则重复上报会把指令钉死在终态，后续轮询也无法再执行（注释 :295 点明）。

### 3.3 MQTT 指令消息　:373-418
- **要点**：proto→entity 转换（state 数值→字符串兼容，:394-395）后**复用同一条 DispatchCmd**；解析失败**不上报**的三条理由（:377-380 注释，讲给评审听）：拿不到真实 instruction_id 上报无法关联；误报终态会钉死指令；立即触发一次轮询兜底。MQTT handler 回调在 MQTT 线程，**必须 Post 到 IotThread**（:414-417）。

### 3.4 命令族一览
| 命令 | cmd_name | 机制要点 | 线程 |
|---|---|---|---|
| 重启 | `restartDevice` | 先回执→Wait 5s→`RebootDeviceAsync`（reboot_device.cpp:16-26） | IotThread |
| 重启 App | `restartApp` | 与 reboot 逐行同构，仅 `RestartAppAsync`（:23） | IotThread |
| 恢复出厂 | `factoryReset` | 同构，`FactoryResetAsync`；「擦什么」在 facility 层 | IotThread |
| 上传日志 | `uploadLog` | collect（白名单+libzip 打包）→presign（直调 Network 5s）→PUT 限速 1MB/s；5 时点 StatusReporter 桥接 BiComm（:129-133）；`SCOPE_EXIT` 清理 | IotThread |
| 抓日志 | `captureLog` | detached 线程跑 `QLog/tcpdump/sys` 三类；超时 180s 可下发 | std::thread |
| 清日志 | `logClean` | 白名单前缀 + canonical 二次校验 + 分区根保护 + 8 条黑名单（log_clean_cmd.cpp:46-114） | IotThread |
| 存储 dump | `dumpStorageInfo` | `du` 重定向 → 手工 new 子 uploadLog 上传（:52-82） | IotThread |
| NTP 对时 | `syncNtp` | `NtpTimeSync::SyncTime`（自研 SNTP，UDP 手写包，offset 校验写 RTC） | IotThread |
| 远程开门 | `remoteDoorOpen` | header-only，全继承 `IotBiCommCmd`；时效 90s（=轮询 60s+余量 30s，:14） | BiComm |
| BiComm 基类 | （多个） | 不干活只代理：`BiCommManager::Execute` + 时效守卫（时间不可信直接拒）+ 三回调驱动终态（bicomm_cmd.cpp:41-103） | MainThread |

## 4. 核心代码实现细节与原理（重点）  [10min+ · 讲透原理]

### 4.1 挑选的核心代码
4 处：**① 状态机与可靠回执**（base_cmd 全套）；**② 高危命令「先回执后执行」**；**③ 双通道收敛与间隔切换**；**④ 三层去重**。

### 4.2 专深①：状态机与可靠回执　base_cmd.cpp:37-144
```cpp
// SetState（:37-65）：单调性校验（回退拒绝）→ seq++ → 分两路
终态(≥50)：cancel 延迟 timer → 挂 terminal_sent_promise_ → caller 线程同步 DoUploadState()
           （ReliableRequest::Submit 入队即刷盘，掉电安全）→ DeleteLater()
中间态：起 upload_timer 1s → 到期另起 detached 线程 DoUploadState()
// DoUploadState（:97-144）
request_id = id_seq_state   // 同 seq 不同 state 不撞键
task_id    = id_seq         // 同任务状态互斥：终态清掉未送达的旧中间态
终态 reliable=true（满重试）/ 中间态 false（过时快速放弃）
```
**为什么这么写（原理）**：
- **中间态 1s 去抖**：40 之类的中间态天然批量合并——同一命令 1s 内多次 SetState 只发最后一条，减少队列噪音；终态例外**同步刷盘**，因为终态之后命令要自灭/进程要死，没有「等下一拍」的机会。
- **request_id/task_id 两级键**：request_id 决定「这一条要不要发」，task_id 决定「同一指令的旧状态还要不要」——终态入队清掉未送达的 20/30（如过期拒执时 60 清掉 20），**平台看到的是最终真相而不是中间噪音**。
- **KeepSelf/DeleteLater**（:23-35）：`self_ = shared_from_this()` 把生命周期交给命令自己——**到达终态上报入队后**才允许 `self_.reset()` 析构。外部 Create 后裸 `task->Start()` 不持引用也不会悬空——这是整个命令族「发射后不管」的前提。

### 4.3 专深②：高危命令「先回执后执行」　reboot_device.cpp:16-26
```cpp
SetExecutingState(40); UploadStateNow();
SetSuccessState("");                                   // 终态同步入队刷盘（MMKV）
if (!WaitLastTerminalSent(std::chrono::seconds(5)))     // 尽力确认送达
  LOG_W(...);                                          // 超时也照样执行——
DeviceAction::Instance()->RebootDeviceAsync(...);       // MMKV 补发兜底
```
**为什么这么写（原理）**：
- **为什么先报成功**：`RebootDeviceAsync` 一执行进程就没了——**重启之后没有机会上报**。所以成功回执必须发生在死之前；「已报成功但没重启成」（RebootDeviceAsync 失败）是已知接受盲区，靠 `WaitLastTerminalSent` 超时返回 false 只打日志不补救（:24 注释：现有行为兜底）。
- **WaitLastTerminalSent 的信号源**（base_cmd.cpp:120-129）：终态入队时挂 OnResult 回调，`ReliableRequest` 送达（含拒收/放弃）后 `promise->set_value()`；promise 用 shared_ptr 让它**独立于命令生命周期**（DeleteLater 后回调仍安全触发）。5s 超时返回 false 不抛错——语义是「尽力送达确认」而非承诺。
- **三重兜底闭环**：5s 等待（快路径）+ MMKV 同步刷盘（开机后 ReliableRequest 补发，慢路径）+ 重启后 `IotService::Init` 恢复去重 id（防重启后平台重投同一指令双执行）。

### 4.4 专深③：双通道收敛与防重入　iot_service.cpp:170-200
- `pulling_` CAS 防重入（:171-175）：轮询回调是 kAsync 多线程执行模式（:111），MQTT 触发的兜底轮询可能与之并发。
- MQTT 推送解析失败 → **Post 一次立即轮询**（:381）兜底；指令执行链统一在 IotThread 串行。
- 间隔切换的 `pull_success_once_` 门（:146-150 + :183-188）：MQTT「已连接」≠「通道健康」，**须 HTTP 首拉成功**才信任 MQTT 而拉长轮询——防止「MQTT 假在线 + 300s 轮询」叠加放大延迟。

### 4.5 专深④：三层去重　iot_service.cpp:276-302
```
① 内存 deque(16)：本进程内快速判重（O(16) 线性扫）
② MMKV(24h TTL)：跨重启判重——重启后 Init 恢复（:90-105）
③ snapshot 状态门：同一 id 若平台侧已推进到 40+ 则拒收（不去重入队也不上报）
```
**为什么三层**：① 是②的写穿缓存（同键双写，:282-289）；② 解决「重启后平台重投同一指令」；③ 解决「平台侧状态已推进，设备重复消费」——**前两层防重复执行，第三层防重复消费**（指令已执行过但平台重发历史快照时，靠 snapshot.state 识别）。MMKV TTL 24h 平衡存储与窗口（:40-41 注释：防无限膨胀）。

## 5. 边界、异常与测试  [5min · 别一笔带过]

### 5.1 异常与降级
- 时间不可信：拒绝执行（含远程开门）——安全优先（Story 136515343 + bicomm_cmd.cpp:44-49）；代价是**重启未对时期间远程开门/定时指令全部失败**。
- 指令过期：报 60 拒绝；未下发 expire_time 则不校验（`>0` 才判）。
- MQTT 解析失败：不上报+触发轮询兜底（3.3）。
- 未知 cmd_name：报 `ERR_PALM_INSTRUCTION_UNIMPLEMENTED`（:364-369）。
- 状态回退：SetState 单调性校验直接拒绝（base_cmd.cpp:39-41）。

### 5.2 边界条件
| 场景 | 行为 |
|---|---|
| execute_time 在未来 | WaitSchedExecuteTimeRunTask 定时等待（steady_clock 换算防系统时间跳变，base_cmd.h:122-127） |
| log_end_time 毫秒/秒二义 | 魔数 `>10000000000` 判别（capture_log_cmd.cpp:78） |
| du 退出码非零（system 返回 256） | `ret>=0` 照样走上传（dump_storage_info.cpp:62——吞错误，见 6.2-R2） |
| 同一指令平台重发历史快照 | snapshot 状态门拒收 |
| captureLog 命令失败 | 仍 SetSuccessState（capture_log_cmd.cpp:99，只有异常才 Fail） |

### 5.3 测试覆盖
- **已有**：`instruction_entity_test.cpp` / `instruction_presign_entity_test.cpp`——纯实体 JSON round-trip 与缺字段容错（与 paas_shadow 的 entity 测试同风格）。
- **未覆盖（open 风险）**：**命令族与 base_cmd 状态机零单测**——KeepSelf/DeleteLater 生命周期、WaitLastTerminalSent 语义、三层去重、间隔切换全部靠真机；`captureLog`/`dumpStorageInfo` 的 shell 拼接行为只能真机验证。修改 base_cmd 必须带真机回归清单（先回执后执行时序是高危语义）。

## 6. 踩坑与接手注意事项（含审阅发现）  [审阅 + 雷区]

### 6.1 开发中坑
- **校验链顺序别调换**（3.2）：先回执再校验——平台需要「到达了但被拒绝」的痕迹；时间守卫放在过期校验**之前**是因为 1970 时连「是否过期」都不可判。
- **snapshot 状态门处不能上报**：误报终态 = 把指令钉死，后续轮询也无法再执行（:295 注释）——这是本模块最容易犯的错。
- **task_id 互斥语义**：改 `DoUploadState` 的键规则前想清楚「终态清中间态」的用途，否则平台看到一堆中间噪音。
