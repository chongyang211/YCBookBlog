# biz/notifier 通知器 · 业务串讲

> **一句话定位**：内部状态变化到外部通知的**统一翻译层**——`LightNotifier` 把状态机/会话的灯效意图翻译成 SDK 写灯（设备侧唯一灯效出口）；`PosNotifier` 把 Device/Flow/License 三轨状态变化翻译成 POS 上行报文（0xA8/0xAB/0xAC/B0/B2…）。两类的共同架构：**纯订阅-转发执行器**——不持有业务状态、不做决策，只做「订阅 → 映射 → 派发」，所有操作线程封闭在主线程。
> **场次**：35 分钟（4 文件约 490 行，但每行都是协议契约）　**听众**：同组开发 / 评审人 / 后续接手者
> **对照模版**：`06.技术模版/04.业务串讲的模版.md` 第 08 章　**代码基线**：`palm_app_linux/src/biz/notifier/`（2026-10-09 全量精读，含 base64 双重载实测核验）
> **前置阅读**：《刷掌会话》palm_flow 三层（FlowState/FlowEvent 来源）、《指令功能》pos_request_handler（Send* 家族）

## 1. 需求与业务背景  [6min · 先现象后价值]

### 1.1 需求与业务背景
- **来源**：spec FR-19（POS 上行双轨）+ 灯效 spec §3.2.2/§4.7。模组内部到处在变状态（设备状态机切换、刷掌 flow 推进、License 授权迁移），**外部有两类消费者**：LED 硬件（用户看得见的反馈）与上位机 POS（收银流程依赖的状态/事件流）。
- **问题**：① 老架构里灯效与 POS 上行散落在各业务点直调（`PalmCoreManager::SetLightState`、`SendStateChangeMsg` 谁想发谁发）——加一种状态要改 N 处、漏发无人发现；② DeviceFsm 与 palm_flow 是两棵状态树，`kPalmRunning` 期间的状态归属两棵树都有说法，上行边界不清会**双发或漏发**；③ 硬件测试需要绕过状态机直驱灯效，旁路一开就容易失控。
- **目标**：灯效单一执行出口（含测试旁路也走同一出口）；POS 上行按双轨切分互不重叠；事件型上行集中路由。

### 1.2 业务边界
- **做**：灯效订阅-应用-pending 补发；Device 轨/Flow 轨/License 轨三轨上行映射与去重；9 种 FlowEvent 的上行路由；JSON 容错解析与 base64 封装。
- **不做**：灯效**内容**决策（哪个状态配哪种灯——在 DeviceStateBase.BaselineLight / PosSession）；报文编码与 transport（pos_request_handler）；状态推进本身（device_state_machine / palm_session_controller）。

### 1.3 关键业务规则
- **灯效两来源一出口**（light_notifier.h:19-25）：状态切换时 BaselineLight 自动派；`kPalmRunning` 期 PosSession 经 `ReportFlowLight` 转发（**仅 current_==kPalmRunning 生效，其它时刻丢弃**）——Flow 灯只在 Flow 的宿主状态下有效。本 Notifier 是**唯一最终执行出口**，业务侧不再直调 `PalmCoreManager::SetLightState`。
- **POS 三轨分工**（pos_notifier.h:18-26）：Device 轨（非 PalmRunning 的设备态）/ Flow 轨（PalmRunning 期的 PosState + 事件型上行）/ License 轨（story 136057693：0xB0 状态、0xB2 授权结果）。分轨由 `PosStateCode()` 返回 0 表达「本态不在本轨上行」——**映射责任在各状态类，Notifier 只查表**。
- **去重策略不对称（刻意）**：灯效**不去重**（light_notifier.cpp:42-43——SDK 收连续相同值会重启呼吸动画/重新计时，是预期行为）；PosState **去重**（flow_last_pos_state_，pos_notifier.cpp:145-149——重复 StateChange 对收银流程是噪音）。
- **Device 回 Idle 重置 Flow 去重**（pos_notifier.cpp:93-96）：否则两次刷掌会话间 `flow_last_pos_state_` 残留，下一次 PalmRunning 的首个 Detecting 被去重吞掉。
- **硬测旁路仍走唯一出口**（story 137464471，light_notifier.h:37-43）：inspect 测试的原始灯效（颜色轮巡+随机目标确认）状态机表达不了，`SetInspectLight` 旁路进入但**仍路由 ApplyLight**——不变量优先于纯度。

### 1.4 改动范围（链路组成）
- **[灯效]** `light_notifier.h/.cpp`（76 行）：订阅→ApplyLight→pending 补发。
- **[上行]** `pos_notifier.h/.cpp`（273 行）：三轨订阅 + OnFlowEvent 九分支路由。
- **[依赖]** device_state_machine（Subscribe/SubscribeLight/Meta→PosStateCode）、palm_session_controller（SubscribeFlowChange/SubscribeFlowEvent）、license_manager（两 signal）、pos_request_handler（Send*/OnPalmResult 家族）。

## 2. 整体设计与模块划分  [5min · 先图后讲]

### 2.1 通知流全景图
```
┌─ 内部状态源 ──────────────────────────────────────────────┐
│ DeviceStateMachine（设备态 + BaselineLight）                │
│ PalmSessionController（FlowState 变化 + FlowEvent 事件）    │
│ LicenseManager（AuthStateChange / AuthActionResult）       │
└──────┬───────────────────────┬───────────────────────────┘
       │ SubscribeLight         │ Subscribe / SubscribeFlowChange/Event / 两 signal
┌──────▼───────┐        ┌──────▼────────┐
│ LightNotifier │        │  PosNotifier   │
│  OnLight      │        │ OnDeviceChange │──PosStateCode()查表→SendStateChangeMsg
│  ApplyLight ──┼──┐     │ OnFlowChange   │──FlowState→PosState 映射+去重
│ (唯一灯效出口) │  │     │ OnFlowEvent    │──九分支 variant 路由
└───────────────┘  │     │ OnLicense*     │──0xB0 / 0xB2
                   │     └──────┬────────┘
                   ▼            ▼
        PalmCoreManager::SetLightState   PosRequestHandler::Send* / On*
        （SDK 未就绪→pending 暂存）        （编码+transport，见《指令功能》）
```
分层关键：**Notifier 是「翻译器」不是「决策者」**——映射表（PosStateCode）住在状态类里、灯效内容住在状态类里，Notifier 只负责订阅管理、去重策略、容错解析与派发。新增一种状态→状态类给 PosStateCode 返回值即可，Notifier 零改动（OCP）。

### 2.2 模块职责
| 组件 | 职责 |
|---|---|
| `LightNotifier` | 灯效订阅 → ApplyLight（唯一出口）→ SDK 未就绪 pending 补发 → inspect 旁路收编 |
| `PosNotifier` | 三轨订阅 → 状态映射与去重 → 事件路由（0xA8/0xAB/0xAC/0x01/OnPalmResult/OnBindResult/OnScanCodeResult） |

## 3. 逐模块实现讲解  [12min · 业务意图先行]

### 3.1 LightNotifier：76 行的「守门员」
- **Init/Shutdown**（light_notifier.cpp:16-29）：全部 `Threads::MainThread()->Post`——订阅建立与断开都在主线程，无锁；`scoped_connection` RAII 兜底。
- **ApplyLight 三段**（:41-62）：① `last_applied_` 记录（仅调试）；② SDK 未就绪 → `pending_light_ = ls`（**latest-wins**：后续变化直接覆盖，灯效只关心当前态）+ 一次性订阅 `InitSucSig`；③ 已就绪 → `pending_light_.reset()`（幂等清理）+ `SetLightState`。
- **OnSdkInitSuc**（:64-74）：补发 pending 后**主动 disconnect**——一次性连接用完即断，不留常驻订阅。
- **SetInspectLight**（:35-39）：旁路直通 ApplyLight，连 pending 语义都继承——测试期 SDK 未就绪也会被补发。

### 3.2 PosNotifier：三轨与九路由
- **Init**（pos_notifier.cpp:25-38）：一次 Post 里建 Device 轨 + License 轨订阅（License 两个 signal 是 `RegisterStateCallback/RegisterAuthResultCallback` 返回 connection）。
- **SetRequestHandler/SetPalmFlowSubscriber 延迟注入**（:50-79）：handler 与 controller 由 BootStrapper/Controller::Run 在就绪后注入——**订阅建立晚于构造**，解决循环依赖（Notifier 依赖 Controller 订阅接口，Controller 运行期又依赖 Notifier 上行）。
- **OnDeviceChange**（:81-100）：`Meta(ev.to)->PosStateCode()` 查表派发；`kIdle` 时重置 Flow 轨去重状态（1.3 规则）。
- **OnFlowChange**（:102-150）：switch 全枚举穷尽（**无 default**——新增 FlowState 编译期报错，-Wswitch 是免费的全量回归）；仅 `kDetecting/kPalmEntered → kStateCodeDetecting` 上行，其余 16 态显式不上行且**每个 case 带注释说明谁负责**（kWaitingBindInput→0xAC、kVerify*→0xAB 等——不上行的原因比上行的更值得注释）。
- **OnFlowEvent 九分支**（:152-270）：

| 事件 | 上行 | 要点 |
|---|---|---|
| PalmStatusUpEvent | SendPalmStatusMsg | 状态码直通 |
| RecognizeStartEvent | 0xA8 kOptImgReady(0x01) | 识别开始 |
| OnPalmResultEvent | OnPalmResult | exit_code==0 且 JSON 非空 → 解析 9 字段；否则只传 code+sid（3.3 深挖） |
| OnBindResultEvent | OnBindResult | 绑掌结果（区别于识别），字段 Handler 统一序列化 base64 |
| OnScanResultEvent | OnScanCodeResult | story 135810205 从 Controller 直派迁入 |
| NeedVerifyEvent | 0xAB | base64(JSON{sid,timeout,verify_method}) |
| NeedBindInputEvent | 0xAC | story 137286676 反扫码复用（enroll_type=kScanInput） |
| HostAckCompleteEvent | 0xA8 kSessionEnded | base64(JSON{exit_code}) |
| OnPalmSessionStartEvent | 0xA8 0x03 kPalmWakeAutoStart | **config_base64 快照**（4.3 深挖） |

- **License 轨**（:58-69）：0xB0 只带 to+summary（无错误码）；0xB2 带 ret_code+error_msg——**通知与结果的分野**。

## 4. 核心代码实现细节与原理（重点）  [10min · 讲透原理]

### 4.1 深挖①：灯效「单一执行出口」不变量
- **为什么**：旁路一旦直调 `PalmCoreManager::SetLightState`，pending 补发、日志、调试字段全部旁路——测试能过、产线偶发「灯不亮」查无实据。`SetInspectLight` 的注释（light_notifier.h:37-43）明说：**inspect 仍路由 ApplyLight，保住本类作为唯一灯效执行点**——不变量优先于「禁止旁路」的洁癖。
- **pending latest-wins 的正确性**：灯效是「当前态」的函数，不是历史队列——SDK 初始化完成前状态切了三次（如 Boot→Activate→Idle），补发中间态毫无意义且会闪灯；只补最后一笔 = 最终一致。
- **一次性连接的纪律**：`init_suc_conn_` 在 OnSdkInitSuc 末尾无条件 disconnect（:73）——即使 pending 为空也断开，不留常驻回调。

### 4.2 深挖②：双轨边界与「去重策略跟着通道语义走」
- **边界规则**：`kPalmRunning` 的 PosState 只能 Flow 轨发（Device 轨 PosStateCode 返回 0）；`kShowingResult*` 的结果态也不走 Device 轨（已由 OnPalmResult 事件上行）——**同一个事实只从一个轨出**，这是防止双发的根本。
- **去重不对称的原理**：灯效重复派发 = SDK 重启呼吸动画（**外部有状态副作用，重复是特性**）；POS StateChange 重复派发 = 上位机状态机收到噪音（**消费方无副作用，重复是 bug**）。去重与否不是代码风格，是**通道消费语义**决定的——评审时看到两个 Notifier 去重策略相反，先问通道语义再质疑实现。
- **去重状态重置点**（:93-96）：去重窗口必须与「会话边界」对齐——Device 回 Idle 即一局结束，`flow_last_initialized_=false` 保证下一局首个 Detecting 必达。**去重状态的生命周期 = 消费方语义周期**，不是实现方便的周期。

### 4.3 深挖③：config_base64 快照——emit 时序列化防竞态
- **问题**（pos_notifier.cpp:256-257 注释）：session 启动通知（0xA8 0x03）要带 config；若路由到**发送时**才序列化，而用户此刻经 0x0B 改了 config——**上行的是「现在的 config」而非「会话启动时的 config」**，事后对账对不上。
- **解法**：emit 时（Controller 构造 OnPalmSessionStartEvent）就把 config 序列化成 base64 快照，Notifier 透传——**把「读取时机」绑定到「事实发生时机」**。与《刷掌会话》O5 的「happen_time 用事件真实时刻而非投递时刻」、《业务上报》两阶段填充同构：**跨线程传递的数据，快照优于引用**。
- **JSON 容错三重校验**（:176-177）：`parse(json, nullptr, false)`（非抛出模式）→ `!is_discarded()`（语法）→ `is_object()`（形状）——任何一步失败降级为「只传 code+session_id」+ LOG_W。**协议字段解析永不抛异常**是上行链路的底线：识别已成功，不能死在结果通知的 JSON 上。

### 4.4 深挖④：线程封闭与延迟注入
- 两个 Notifier 的**所有**公开方法第一行都是 `Threads::MainThread()->Post`（含 Shutdown）——类内零锁零原子，正确性靠「只被主线程碰」。订阅回调（signal）本身也在主线程发（状态机/Controller 均主线程驱动），全链路单线程。
- **延迟注入解决循环依赖**：PosNotifier 构造时 Controller 尚未运行——SetPalmFlowSubscriber 把「订阅 Controller」推迟到 Controller::Run 之后。若在构造期强订阅，初始化顺序就要全局排序；延迟注入把**依赖关系的建立时机交给懂时序的人**（BootStrapper）。

## 5. 边界、异常与测试  [4min · 别一笔带过]

### 5.1 边界条件
| 场景 | 行为 |
|---|---|
| SDK 未就绪时来灯效 | pending 暂存（latest-wins），InitSuc 一次性补发 |
| Flow 灯在非 kPalmRunning 到达 | ReportFlowLight 侧丢弃（本类的上游保证） |
| PosStateCode()==0 | 本态不上行（kPalmRunning 归 Flow 轨、kShowingResult* 已走 OnPalmResult） |
| recognize_info_json 解析失败 | 降级 code+sid，不抛异常 |
| exit_code != 0 | 不解析 JSON，全默认字段 |
| Device 回 Idle | Flow 轨去重状态归零 |
| handler 未注入 | 全部回调 `if (!pos_handler_) return`（静默丢弃） |

### 5.2 测试覆盖
- 本模块**无专属单测**——作为纯转发层，其正确性由两头契约测试间接保证（device_state 的 PosStateCode 各态、pos_request_handler 的报文编码）。风险：**映射回归（如某态 PosStateCode 改值）无测试拦截**，依赖上位机联调发现（6.2-N3 相关）。
