# assets/scripts 部署脚本载荷 · 业务串讲

> **一句话定位**：opkg 包的**脚本载荷与打包管线**——`assets/scripts/` 四文件（restart.sh / stop.sh / restarter / lockcheck）安装到 `/app/palmapp/scripts/` 构成监督塔的全部执行件；`scripts/opkg/` 把 tar.gz 打成 ipk/apk 并挂上四段生命周期脚本（preinst/postinst/prerm/postrm），postinst 的 stop→start 编排与监督塔的 do_recover 形成「安装即重启」闭环。本篇是《启动应用-模块业务串讲》的**姊妹篇**——监督塔三层细节彼篇已讲透，本篇聚焦三块增量：**lockcheck 探活原理**、**opkg 生命周期交互**、**打包管线的跨平台工程**。
> **场次**：35 分钟（4 载荷文件 + 5 控制脚本 + 1 构建脚本，约 700 行 shell/C++）　**听众**：同组开发 / 评审人 / 后续接手者

## 1. 需求与业务背景  [6min · 先现象后价值]

### 1.1 需求与业务背景
- **来源**：palmapp 以 opkg 包（ipk/apk）形态交付到设备——包里除了 palmapp 二进制与 lib，还需要一组**脚本执行件**：开机怎么拉起、坏了怎么救、怎么停、以及安装/卸载时怎么与运行中的实例交接。
- **问题**（决定本篇三块内容的）：① 「palmapp 活着吗」这个判定不能靠 `kill -0`（PID 复用会假阳性）；② **安装新包时旧实例正在跑**——谁来停、停完谁拉起、正在自愈的脚本被杀怎么办；③ 构建机是 macOS、目标是 Linux——tar/ar 的平台差异会让 ipk 在设备端解不开。
- **目标**：探活零误判；安装/升级/卸载与监督塔无缝交接；跨平台打包一次成功。

### 1.2 业务边界
- **做**：四文件载荷契约、lockcheck 探活器、opkg 生命周期四脚本、tar.gz→ipk/apk 打包管线、pm/opkg 设备端指令。
- **不做**：监督塔的崩溃分类/恢复分发（见《启动应用》3.2-3.4）；OTA 下载与 ota_pending 写入（upgrade_schd）；恢复事件上报（RecoveryReporter，《业务上报》3.5）。

### 1.3 关键业务规则
- **载荷布局**（相对路径网）：`/app/palmapp/` 下 `palmapp`（二进制）+ `lib/` + `scripts/{restart.sh, stop.sh, restarter, lockcheck}`——restart.sh 全部用 `$base_dir/lockcheck`、`$base_dir/../palmapp`、`$base_dir/../lib` 相对引用，**无绝对路径依赖**。
- **lockcheck 退出码契约**（lockcheck.cpp:57-79）：`0` = locked（有进程持锁 = palmapp 活着）、`1` = unlocked（无锁 = 死了）、`2` = 错误——**0 表示「被锁」而非「成功」，反直觉**。
- **pid 文件契约**：`/tmp/palmapp.pid` 由 palmapp 自己写入并持 `lockf` 锁（单一事实源）；`/tmp/restart_sh.pid` 由 S99 写（探活用 `kill -0`，S99palmapp:100-106）——**两种 pid 文件两种探活法**，见 4.3。
- **生命周期编排**：`postinst` = 逃逸门（`APP_POST_INSTALL_NO_RESTART=true` 则不重启）→ `S99 stop` → `sleep 3`（rkaiq 摄像头守护稳定期，postinst:10「tmp workaround」）→ `S99 start`；`prerm` 只 `S99 stop`；`postrm` 只 `sync`——**卸载保留 /data/palmapp 全部数据**。
- **打包格式契约**：源包名必须 `包名_场景_v版本.tar.gz`（readme:15 + opkg-build.sh:29-31 sed/grep 解析）——格式错即产出错误元数据。

### 1.4 改动范围（链路组成）
- **[载荷]** `assets/scripts/`：restart.sh（375 行）、stop.sh（23 行）、restarter（二进制 ← `tools/restarter/restarter.cpp` 223 行）、lockcheck（二进制 ← `tools/lockcheck/lockcheck.cpp` 80 行）。
- **[生命周期]** `scripts/opkg/control/`：control（模板，Version 构建时注入）、preinst（空）、postinst、prerm、postrm。
- **[打包]** `scripts/opkg/opkg-build.sh`（158 行）+ readme.md。

## 2. 整体设计与模块划分  [5min · 先图后讲]

### 2.1 调用全景图（谁调用谁）
```
 打包机：opkg-build.sh  tar.gz ──→ ipk + apk（adb/pm 双通道安装）
 ─────────────────────────────────────────────────────
 设备端 opkg install palmapp_x.ipk
   preinst（空）→ 解包覆盖 /app/palmapp/ → postinst：
     S99 stop（→ stop.sh：killall restart.sh → restarter → lockcheck 杀 palmapp）
     sleep 3（rkaiq）→ S99 start（→ 起监督塔）
 ─────────────────────────────────────────────────────
 监督塔（启动应用串讲已讲透，此处只画引用关系）：
   S99palmapp ──起──→ restart.sh ──lockcheck──→ /tmp/palmapp.pid（palmapp 持锁）
                        │──起──→ restarter ──fork/exec──→ ../palmapp（--signal-parent 10）
                        │──do_recover──→ opkg install ──→ postinst ──killall──→ restart.sh（自己）
                        │                              └→ S99 start（新版本塔复活）
   卸载：prerm（S99 stop）→ postrm（sync，数据保留）
```
分层关键：**「打包侧只管交接，运行侧只管活着」**——postinst/prerm 从不直接 killall 业务进程，一切经 S99/stop.sh 走监督塔的正式停止链（顺序敏感的三步杀）；监督塔的 do_recover 反向信任 postinst 的重启编排——**两条链在 opkg install 处闭环**。

### 2.2 模块职责
| 组件 | 职责 |
|---|---|
| `restart.sh` / `stop.sh` / `restarter` | 监督塔执行件（启动应用串讲 3.1-3.5） |
| `lockcheck` | lockf 探活器（本篇深挖 4.1） |
| `control/*` | opkg 四段生命周期 + 元数据模板 |
| `opkg-build.sh` | tar.gz → ipk/apk 跨平台打包 |

## 3. 逐模块实现讲解  [12min · 业务意图先行]

### 3.1 `lockcheck`：80 行探活器　tools/lockcheck/lockcheck.cpp
- **流程**（:50-79）：`open(pid_file, O_RDWR)` → `lockf(fd, F_TLOCK, 0)` 非阻塞试探 → `EACCES/EAGAIN` = 别人持锁 → 输出 "locked"、退出 **0**；抢到锁 = 无人持有 → 立即 `F_ULOCK` 释放 → 输出 "unlocked"、退出 **1**。
- **消费方**：restart.sh:219（决定要不要杀旧 palmapp）、stop.sh:16（决定要不要 kill）——都是 `if "$base_dir/lockcheck" -q "$pid_file"` 直接当条件（退出 0 = 活着 = 进 if）。
- `-q` 静默 / `-v` 冗余 / 退出 2 = open/lock 系统错误——错误与「未锁」严格区分（:65-69）。

### 3.2 opkg 生命周期四脚本　scripts/opkg/control/
- **postinst**（:1-11）：`sync` → 逃逸门 `[ "$APP_POST_INSTALL_NO_RESTART" = "true" ] && exit 0` → S99 可执行才继续 → stop → sleep 3 → start。**逃逸门的用途**：安装方想自己控制重启时机（如升级流程分批重启）。
- **prerm**（:4-5）：只 S99 stop——卸载前交还给系统。
- **postrm**（:4）：只 sync——**不删 /data/palmapp**（日志/MMKV/上报队列全保留，重装即恢复——与 factory_reset `data_app` 的「重装捆绑 app」语义呼应）。
- **preinst**：空（6.2-K5）。

### 3.3 `opkg-build.sh`：tar.gz → ipk/apk　scripts/opkg/opkg-build.sh
- **双入口**（:20-47）：给 tar.gz（从文件名解析 `包名_场景_v版本`，:29-31）或给目录+四显式参数。
- **control 注入**（:93-102）：拷模板后**重写** control——`Package/Version` 来自包名解析、`Flavor` 仅当包内含 `res/files/app_type` 才写（:86-90）——**模板里的 `Version: 0.7.0` 只是占位**，不是硬编码（6.2-K4）。
- **ipk 三件套**：debian-binary=2.0 + control.tar.gz + data.tar.gz → `ar` 归档 → 同一文件拷贝为 `.apk`（**apk 后缀只是 adb 安装的格式要求**，与 Android APK 无关——readme:37）。
- **macOS bsdtar 处理**（:5-15）：Sonoma+ 给每个文件盖 `com.apple.provenance` 扩展属性，bsdtar 经 PAX 头序列化——`COPYFILE_DISABLE`（只管 AppleDouble）与 `--no-mac-metadata`（只管 resource fork）**都不管这个**，必须 `--no-xattrs`；GNU tar 默认不存 xattr 无需处理。
- **非 GNU ar 的手工归档**（:116-147）：macOS 的 ar/llvm-ar 写 `__.SYMDEF` 且把偶数对齐填充计入成员 size——Linux 端解出带尾随垃圾的 tar.gz（gzip 报 trailing garbage、GNU tar 直接失败）。解法：`build_ipk_ar` **手工构造 SysV 格式 ar 归档**（size 精确到字节、奇数补 `\n` 对齐）——任意平台 ar/tar 均可正确读取。

## 4. 核心代码实现细节与原理（重点）  [10min · 讲透原理]

### 4.1 深挖①：lockf 探活为什么胜过 `kill -0`（本篇核心增量）
- **`kill -0` 的竞态**：PID 文件写着 1234，进程死了，系统把 1234 分配给别的进程 → `kill -0 1234` 成功 → **误判「活着」**（S99 对 restart_sh.pid 用的是这招，S99palmapp:100-106——因为 restart.sh 不持锁，只能如此，且 pid 文件在 /tmp 每次开机清零、被误判的代价只是「跳过本次启动」）。
- **lockf 的结构性优势**：锁随**持锁进程**存在——进程死亡内核自动释放锁，**零残留状态、零 PID 复用问题**。「活着」的判定从「查一个数字是否存在」变成「锁是否还被持有」——**活性由内核管理而非文件内容**。这是 palmapp（关键进程，误判代价是叠加实例）用 lockcheck、restart.sh（低危）用 kill -0 的分层依据。
- **单一事实源**：pid 文件由 palmapp 自己写并持锁——「谁写谁锁」消灭了写文件与加锁之间的窗口（若由 restarter 代写，进程起死之间就有一段「文件在、锁不在」的模糊态）。
- **退出码 0=locked 的反直觉**（lockcheck.cpp:62-64）：语义是「探到了锁」而非「执行成功」——调用方当条件用没问题（`if lockcheck` = `if 活着`），但 `$?` 判断风格的新代码极易搞反（6.2-K1）。

### 4.2 深挖②：安装与自愈的闭环（postinst ↔ do_recover）
```
do_recover（restart.sh:174-187）                    postinst（control/postinst:6-11）
  write_recovery_event(...)   ← 必须先写！             S99 stop → killall restart.sh
  opkg install --force-reinstall pkg ────────→          （杀死发起安装的 restart.sh 自己）
      ↑ 解压覆盖 /app/palmapp/                            sleep 3 → S99 start
      │（原地覆盖，不产生缺失文件——S99:16-18 注释的根基）    → 新版本 restart.sh 复活新 palmapp
```
- **为什么事件必须先写**（restart.sh:179-182 注释）：postinst 的 stop 链会 `killall restart.sh`——**正在执行 opkg install 的脚本被自己触发的安装杀死**，install 之后的任何代码（包括写事件）都不会执行。「先写意图、后执行、成功则不补写、失败才补写终态」——**写前杀后**的时序是这条链的生死线。
- **rc 的传递**：restart.sh 被 killall 后 `rc` 拿不到 opkg 的真实返回码（进程死了）——但事件已写 `retry_ota 0`（意图），成功与否由 postinst 的 S99 start 兜底：新版本起来了 = 成功；起不来 = 下一层（S99 beacon → factory_reset）。
- **`--force-reinstall --force-downgrade`**（restart.sh:184）：自愈场景版本可能回退（新包坏→重装旧包），必须显式允许降级。

### 4.3 深挖③：探活三件套的分层选型
| 机制 | 用在 | 误判代价 | 为什么 |
|---|---|---|---|
| lockf（lockcheck） | palmapp | 叠加实例/误杀 | 内核管理活性，零残留 |
| `kill -0`（pid 文件） | restart.sh（S99 层） | 跳过本次启动 | restart.sh 不持锁，pid 在 /tmp 每次开机清零 |
| `killall`（进程名） | stop.sh / postinst 链 | 同名误杀（低概率） | 一次性广播杀，无需任何状态文件 |
- 三种机制按「误判代价 × 状态可得性」分层——**没有万能探活，只有与代价匹配的探活**。

### 4.4 深挖④：打包管线的两个跨平台坑（注释即文档的范本）
- **bsdtar xattr**（opkg-build.sh:5-15 注释）：完整记录了「试过哪两个方案、为什么不管用、哪个管用」——`COPYFILE_DISABLE` 只抑制 AppleDouble、`--no-mac-metadata` 只抑制 resource fork，`com.apple.provenance` 走 PAX 头必须 `--no-xattrs`。
- **ar 归档**（:116-124 注释）：`__.SYMDEF` 成员 + 对齐字节计入 size → Linux 解包 trailing garbage——与其绕 macOS ar 的行为，**手工构造格式**（70 行 `build_ipk_ar`）保证字节精确。两条注释都是「踩坑后把决策写进代码」的范例——与 restart.sh 的 Plan A 注释、palm_flow 的 scene_attach 教训注释同族。

## 5. 边界、异常与测试  [4min · 别一笔带过]

### 5.1 边界条件
| 场景 | 行为 |
|---|---|
| APP_POST_INSTALL_NO_RESTART=true | postinst 不重启（安装方自控时机） |
| S99 不存在/不可执行 | postinst/prerm 直接 exit 0（容忍变体安装） |
| 安装中断 | 原地覆盖不产生缺失文件（S99 skip 兜底注释的根基） |
| lockcheck open 失败 | 退出 2（与「未锁」的 1 严格区分） |
| palmapp 崩溃后 pid 文件残留 | 锁随进程死亡已释放 → unlocked → 正确判死 |
| 卸载 | 数据全保留（/data/palmapp），重装即恢复 |
| 包名格式错误 | sed/grep 解析静默产出错误元数据（6.2-K4） |

### 5.2 测试覆盖
- **发布验证**：`guard-release-verify.sh`（启动应用串讲 5.2——监督塔的验证）；打包管线**无自动验证**（ipk 字节级正确性靠 build_ipk_ar 的确定性构造 + 设备端 pm install 联调）。
- pm/opkg 指令族（readme:36-45）是手工验收面：`pm list/info/files/install/remove`。
