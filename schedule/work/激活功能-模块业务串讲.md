# service/activation 激活功能 · 业务串讲

> **一句话定位**：设备的**首次入网身份建立**——扫激活码（四种格式）→ 域名证书校验 → 三步 SE 国密密钥交换（start / confirm-key-change / confirm）→ 域名双存储落盘（系统属性主 + SE 芯片备）；`ActivationService` 管业务协议，`ActivationController` 用 11 状态 HFSM 编排并联动设备总状态机，失败文案统一带 `[trace_id:xxx]` 单号（客服免导设备日志即可后台检索）。
> **场次**：60-90 分钟（模块横跨业务层/FSM 层/域名校验/proto，难点在五步协议与 SE 交换时序）　**听众**：同组开发 / 评审人 / 后续接手者
> **对照模版**：`06.技术模版/04.业务串讲的模版.md` 第 08 章　**代码基线**：`palm_app_linux/src/service/activation/`（2026-10-08 审阅；三项高危结论已逐行实测确认）
> **关联串讲**：《网络库》（BuildErrorNotification/签名体系/trace 生成）、《业务上报》（O4 错误码治理，trace 尾缀最初来源）

## 1. 需求与业务背景  [10min · 先现象后价值]

### 1.1 需求来源与问题
- **来源**：海外/私有化部署场景——设备出厂时不知道后台域名，需要**扫激活码**完成：域名注入 + 与后台的**SE 国密密钥交换**（设备身份的可信根）+ 服务场景绑定。
- **问题**：① 激活码格式历经多代（wxpact://、action flat、JSON 数组、裸 protobuf），扫码入口必须全兼容；② 域名若只存一处，恢复出厂/刷机后即丢——设备变「砖」需返厂；③ 激活中途断网/重启，重试必须幂等（SE 已处于半交换状态时的续走）；④ 失败排障要跨设备/后台两端，缺单号只能靠导日志。
- **目标**：四格式激活码全兼容；域名双存储互为备份；五步协议幂等可续走；trace 贯穿三次请求；失败文案可直接给客服。

### 1.2 业务边界
- **做**：扫码解析（`IsActivationCode` 轻量检测 + 四格式解析链）、域名校验（/license 下载证书→根证书验签→CN 匹配）、五步激活协议、域名双存储对齐、HFSM 编排与 DeviceFsm 联动、trace 会话串联。
- **不做**：SE 芯片内部密钥运算（SeKeyStore）；服务场景选择与绑定（Linux 版五步即完成，activation_service.h:217 注释）；NTP 时区设置（只同步时间）；上位机扫码分发（`TryHandleScanCode` 判非激活码返回 false 交支付链路）。

### 1.3 关键业务规则
- **五步协议**（三步走网络 + 两步走 SE）：
  | Step | 接口 | 签名类型 | 备注 |
  |---|---|---|---|
  | 1 CheckActivationStatus | —（本地） | — | SE 出厂检查 + 域名对齐；未确认过则补发 confirm（空 scene） |
  | 2 start | POST `/activation/devices/{sn}/activation/start` | ACTIVATION | 请求 protobuf、响应 JSON；拿服务端密钥列表 |
  | 3 SE 交换 + confirm-key-change | POST `.../confirm-key-change` | ACTIVATION | SE `ExchangeKeyWithServer` → 上报设备侧密钥 → 拿 confirm_code |
  | 4 SE confirm | —（本地） | — | `ConfirmExchangeKeyWithServer(confirm_code)` + 域名双写 |
  | 5 confirm | POST `.../activation/confirm` | **DEVICE** | 落 `MarkActivationConfirmed`（MMKV） |
- **超时口径**：激活请求统一 **60s**（`network.h:31-32` `kActivationRequestTimeout`），常规 IoT 15s——弱网首次入网容忍度更高。
- **trace 规则**（story 137332527，ADR 落地）：start 首请求**不传 trace**，由网络层生成随 `IoTResponse.trace_id` 带回（activation_service.cpp:549-556）；服务持有 `activation_trace_id_`，step 3/5 经 override 通道透传（:708/:890）——**三次请求串成同一条激活链路**，串联不受并发心跳影响。开机补发 confirm 时 trace 为空（Reset 已清）→ 新请求新 trace（:884-885 注释明示语义）。
- **错误文案口径**：网络层失败直接透传 `resp.error_message`（Network 已拼好尾缀）；本层「HTTP 成功但内容异常」的判定（svr_keys 空/JSON 解析失败）由本层拼单号。

### 1.4 改动范围（模块组成）
- **[业务层]** `activation_service.h/.cpp`（~1100 行）：五步接口、四格式解析、域名双存储、trace 持有。
- **[FSM 层]** `activation_controller.h/.cpp` + `fsm/activation_fsm.hpp`（hfsm2 声明式 11 状态）+ 第三方 `fsm/hfsm2/`。
- **[域名校验]** `domain_validator.h/.cpp` + test。
- **[协议]** `proto/PalmActivation.proto`（海外激活码 + 五步消息 + 旧版服务场景消息族）。

## 2. 整体设计与模块划分  [10min · 先图后讲]

### 2.1 架构与分层
```
 扫码事件 → ActivationController.TryHandleScanCode(:113-121)
   ├ IsActivationCode？非激活码 → false 交支付扫码链路
   └ 是 → FSM 事件（QRCodeScanned）
 ┌──────────────────────────────────────────────────────┐
 │ ActivationController（FSM 编排，LicenseThread 串行）     │
 │  hfsm2：Idle→CheckActivationStatus→NotActivated→        │
 │    WaitingForQRCode→QRCodeScanned→StartActivation→      │
 │    KeyExchange→ConfirmKeyExchange→Activated（11 态）      │
 │  Error 态 update() 判可重试 → 回 WaitingForQRCode         │
 │  NotifyActivationPhase(:496-543) → DeviceFsm 联动         │
 ├──────────────────────────────────────────────────────┤
 │ ActivationService（业务协议，协程）                       │
 │  StartActivationFromQRCode（4 格式解析→SetActivationSession│
 │    →NTP 预同步→ValidateActivationDomain）                 │
 │  五步接口；activation_trace_id_ 会话持有；Reset 清理        │
 │ DomainValidator：/license 下载证书→根证书验签→CN 匹配      │
 ├──────────────────────────────────────────────────────┤
 │ 双存储：prop ro.vendor.palmactivation.server_host（主）   │
 │         SE SetSeCustomSvrUrl（备）——双向自动对齐           │
 │ MMKV：kConfigKeyActivationConfirmed（确认标志跨重启）      │
 └──────────────────────────────────────────────────────┘
   依赖：SeKeyStore（密钥交换）、Network（ACTIVATION/DEVICE/SIMPLE
        三类签名都用到）、hfsm2、OpenSSL X509
```
分层关键：**协议（Service）与编排（Controller/FSM）分离**——FSM 只管状态迁移和回调时机，网络细节全在 Service；**域名单点 `SetIotDeviceHost`** 是激活对网络层的唯一注入（后续所有业务请求都用它）。

### 2.2 模块划分与职责
| 模块 | 职责 | 切分理由 |
|---|---|---|
| `ActivationService` | 五步协议 + 解析 + 双存储 | 业务语义单点 |
| `ActivationController` + FSM | 状态编排、DeviceFsm 联动、phase 去重通知 | 编排/协议解耦，FSM 可独立测试（理论上） |
| `DomainValidator` | 激活域名证书校验 | 独立安全边界（防假域名钓鱼） |
| `PalmActivation.proto` | wire 契约 | 双端同源 |

### 2.3 核心数据流（一次完整激活）
```
扫码 → TryHandleScanCode → FSM: WaitingForQRCode → QRCodeScanned(存 qr_data)
 → OnEnterQRCodeScanned → Service.StartActivationFromQRCode
    ① 4 格式解析（action: flat / [[JSON / wxpact://base64 / 裸 protobuf）
    ② network->SetActivationSession(domain, session_id, session_key)
    ③ NTP 预同步（失败不阻塞）
    ④ DomainValidator.CheckDomainValid（/license + 根证书 + CN）
 → FSM: QRCodeParsed → StartActivation
 → Service.StartPalmDeviceActivation（ACTIVATION 签名，60s）
    resp.trace_id → activation_trace_id_（会话 trace 起点）
 → FSM: ActivationStarted → KeyExchange
 → Service.ExchangeAndConfirmKeys（SE 交换 → confirm-key-change，透传 trace）
 → FSM: KeyExchangeSuccess → ConfirmKeyExchange
 → Service.ConfirmKeyExchangeToSE（SE confirm + StoreServerDomain 双写）
    → ConfirmPalmDeviceActivation（DEVICE 签名，透传 trace）
    → MarkActivationConfirmed（MMKV）
 → FSM: ActivationConfirmed → Activated（OnActivated→Reset 清临时态）
 → NotifyActivationPhase(kActivated) → DeviceFsm ResolveIdleTarget
```

## 3. 逐模块实现讲解  [25min · 业务意图先行]

### 3.1 扫码入口与四格式解析　activation_service.cpp:65-205
- **两级口径**：`IsActivationCode`（:65-91）轻量检测**三条**（`wxpact://` 前缀 / 含 `action:100000000` / `[[` 开头）用于扫码分流（非激活码不误上报上位机）；完整解析链（:109-148）按 `action:` → `[[JSON]]` → `wxpact://base64` → 裸二进制 顺序分发。
- **要点**：flat 解析（:1072-1159）按 `,`/`:` 切 token、校验 `action == 100000000`（activation_service.h:268）且有 has_any_field 检查；JSON 解析（:1014-1067）只要求非空二维数组（宽松，靠后续 `ValidateActivationCode:157` 兜底）——**两种解析器严格度不一致**（见 6.2-A11）。解析成功后统一做：清 confirmed 标志、`SetActivationSession`、NTP 预同步、自动域名校验（:184-201）。

### 3.2 域名双存储对齐　activation_service.cpp:278-406
- **StoreServerDomain（:278-309）**：prop 主写（`ro.vendor.palmactivation.server_host`）+ SE 备写（失败仅 LOG_W）——**prop 成功即算成功**，SE 是备份不是双写事务。
- **GetVerifiedServerDomain（:373-406）**：prop 非空 →（SE 空或不一致则回写 SE）返回 prop；prop 空、SE 非空 → 恢复 SE→prop；都空 → nullopt（异常）。
- **为什么双存储**：恢复出厂清 prop 后 SE 仍在（SE 数据独立于系统分区）——设备靠 SE 兜底恢复域名，避免变砖；反向（prop 有 SE 无）则同步补 SE。

### 3.3 五步协议与 SE 交换时序　activation_service.cpp:409-910
- **Step 1（:409-478）**：SE 延迟初始化（:414-424，`Initialize` 不做——避免与其他应用竞争 SE）→ `HasExchangedKeyWithServer` 判出厂 → 域名对齐 → **未确认过则补发 confirm（空 scene，:452-468）**；后端业务错误视为已确认（:461）——幂等续走的关键。
- **Step 3 的风险时序**（:609-732）：`ExchangeKeyWithServer` **先改写 SE 状态**（:625-671），然后才调 confirm-key-change（:704）——服务端此时失败，SE 已处于半交换态（见 6.2-A2）。
- **Step 4（:735-792）**：SE confirm → 域名双写（失败仅警告 non-critical）→ confirm（注意注释 :770：后台通知必须在 SetActivationStatus 之前，否则 OnActivated 会清掉 activation_code_）→ `ClearActivationSession`。
- **补发链路**：`MarkActivationConfirmed`（:907-910）落 MMKV + Flush——确认标志跨重启，Step 1 补发据此判断。

### 3.4 HFSM 编排　fsm/activation_fsm.hpp:123-423
- **11 态平级**（PeerRoot，无嵌套）：Idle / CheckActivationStatus / NotActivated / WaitingForQRCode / QRCodeScanned / StartActivation / KeyExchange / ConfirmKeyExchange / Activated / PalmServiceUnavailable / Error。
- **两处 `update()` 自动迁移**：NotActivated→WaitingForQRCode（:211-215）；**Error 态判可重试**（:408-422）——`IsActivationErrorRetryable`（unified_errcode_iot.h:217-231：网络/超时/解析可重试，SE 芯片错不可重试）→ 存 retry 字段回 WaitingForQRCode；WaitingForQRCode 的 **exit 回调（:237-243）清 retry 字段**——下一轮扫码从干净状态开始。
- **错误统一入口** `HandleErrorEvent`（:142-157）：写 context（error_code/message/**retry_server_code**）→ `changeTo<Error>`。

### 3.5 Controller：LicenseThread 与 DeviceFsm 联动　activation_controller.cpp
- **LicenseThread**（Story 136057693）：激活与授权共享同一线程——SE 操作串行化（避免 SE 并发访问）+ FSM 事件顺序保证；例外是 DeviceFsm 联动协程走 MainThread（:522/:532/:551）。
- **NotifyActivationPhase**（:496-543）：phase 去重后广播；kActivated → `DeviceStateMachine::ResolveIdleTarget`（已授权→kIdle，未授权→kLicenseUnauthorized）；kError/kPalmServiceUnavailable → 退回 kUnactivated。
- **最小时序修复**（:272-294 注释，现网踩过）：OnEnterActivated 必须**先** `OnActivationStatusChanged`（内部 `is_activated_.store(true)`）**再** `NotifyActivationPhase(kActivated)`——顺序反了 DeviceFsm 守卫拒绝切换、设备卡 kActivating。

## 4. 核心代码实现细节与原理（重点）  [10min+ · 讲透原理]

### 4.1 深挖①：五步协议与 SE 交换的时序设计
- **为什么 start 响应是 JSON 而请求是 protobuf**：历史演进（:568 起解析 `svr_keys` 数组）——双端契约即如此，proto 里 `StartPalmDeviceActivationResp`（:355-357）定义了但**实际走 JSON**。接手改协议先和后端确认两套形态谁生效。
- **签名类型三级**：start/confirm-key-change 用 **ACTIVATION**（会话密钥，激活中身份尚在建立）；confirm 用 **DEVICE**（SE 已确认交换，设备身份已可信——**升级签名即协议进度的表达**）；域名校验用 **SIMPLE**（固定密钥，尚未有任何身份）。**签名类型隐含了信任级别**——这是串讲最值得讲的一句。
- **SE 半交换的续走设计**：Step 1 补发 confirm 的空 scene + 「后端业务错误视为已确认」（:461）——幂等兜底让「走到一半断电」的设备重启后能走完剩余步骤而不必重扫。

### 4.2 深挖②：trace 会话串联（ADR 落地）
```
start（不传 trace）→ 网络层 GenerateTraceparent 生成
                    → IoTResponse.trace_id 随响应带回（:556 存 activation_trace_id_）
confirm-key-change（透传 :708）┐
confirm（透传 :890）          ┴─ 三请求同一 trace，客服一个号查整条激活链
Reset/OnActivated → activation_trace_id_.clear()（:248-256）
重启后：trace 丢失 → 补发 confirm 用新 trace（新请求语义，:884-885）
```
- **为什么首请求不传而由网络层生成**：调用方（激活服务）在 start 之前**没有理由知道 trace**——让首请求自然产生，随响应带回，此后由业务层持有（ADR 做法 B 的混合落地：`start_new_trace` 参数已不出现在激活链路，override 通道承担串联）。
- **串联 vs 独立的取舍**：补发 confirm 用新 trace 是**有意语义**（不是 bug）——重启后的补发是新请求，旧 trace 的日志上下文已在服务端，强行串联反而误导。

### 4.3 深挖③：域名双存储的恢复语义（3.2 已述，此处讲「为什么 prop 优先」）
- prop 是**运行时唯一被读取的数据源**（Network 只认 prop）；SE 是**抗恢复出厂的备份**。双写不做事务（SE 失败仅警告）——因为**最终一致性靠 GetVerifiedServerDomain 的双向同步收敛**，不需要两写原子。这与 paas_shadow 的 c_data/c_ver 两次写脱节问题形成对照：那里没有对齐机制所以出了死锁，这里有对齐机制所以可以放弃原子性。

### 4.4 深挖④：域名校验的安全边界　domain_validator.cpp:60-304
```
GET /license（SIMPLE 签名）→ JSON 取 "license" 字段（证书 PEM）
→ 剥 PEM + base64 解码 → d2i_X509(DER)
→ LoadRootCertificate（内置 res/certs/domain_certificate.crt，3 路径回退 :306-332）
→ X509_verify（根公钥验单证书签名，:210）
→ 有效期 + CN 精确匹配（:288-304）
```
- **防什么**：假域名钓鱼——攻击者让设备指向自己的假后台，若没有根证书验签环节，设备就会与假后台完成密钥交换，**设备身份的根从此被劫持**。域名校验是激活信任链的地基。
- **错误文案带单号**：`WithLicenseTraceId`（:53-56）——/license 请求已发出、服务端有记录，「谁生成文案谁带单号」。

## 5. 边界、异常与测试  [5min · 别一笔带过]

### 5.1 异常与降级
- NTP 预同步失败：不阻塞激活（:184-189）——域名校验里的证书有效期判定受影响（时间不可信时窗口判断失真，联动 6.2-A1）。
- SE 不可用（未初始化）：`ReturnUnactivatedStatus` 走未激活路径；SE 初始化延迟到首次 `CheckActivationStatus`（:414-424）。
- LicenseThread 不可用：**降级为调用线程直接执行**（:478-481）——破坏单线程假设（6.2-A6）。
- 后台业务错误（HTTP 200 + server_code≠0）：补发场景视为已确认（:461）；正常场景走 `MapActivationServerCodeToModule`（268566642→40427，其余 20407 兜底）。

### 5.2 边界条件
| 场景 | 行为 |
|---|---|
| 四种激活码格式 | 全兼容（但裸二进制经扫码入口不可达，6.2-A10） |
| 恢复出厂（prop 清空） | SE 兜底恢复（GetVerifiedServerDomain） |
| 激活中断电重启 | Step 1 补发 confirm 幂等续走 |
| confirm 网络成功但业务失败 | 视为已确认（幂等优先） |
| 非激活码扫码 | `IsActivationCode=false` → 交支付链路 |
| DeviceFsm 忙（OTA/Recovering） | `OnActivationStart` 被拒 → OnError 终止整套激活（:545-564） |
| 可重试错误 | FSM Error::update → 回 WaitingForQRCode；SE 芯片错滞留 Error |

### 5.3 测试覆盖
- **已有**：`activation_fsm_test.cpp`——仅 Phase 枚举值/事件可构造/字段赋值（**无任何状态转换测试**）；`domain_validator_test.cpp`——测的是**遗留死结构** `DomainValidationResult`（:51-55 自述「仅测试编译通过」），真实校验逻辑零覆盖；可重试白名单测试在 unified_errcode_iot_test（:66-89）。
- **未覆盖（open 风险，本模块最重）**：**FSM 状态迁移、五步协议、四格式解析、双存储对齐、域名校验（时区 Bug 正是漏网之鱼）全部无单测**——A1 时区 Bug 属「一行代码、肉眼难察、单测一写就现形」的典型，已在 6.2 列为修复+补测首选。

## 6. 踩坑与接手注意事项（含审阅发现）  [审阅 + 雷区]

### 6.1 开发中坑
- **OnEnterActivated 时序**：先 `OnActivationStatusChanged` 再 `NotifyActivationPhase`（:272-294）——顺序反了设备卡 kActivating，现网踩过。
- **Step 4 内部顺序**：后台通知必须在 `SetActivationStatus` 之前（:770 注释）——否则 OnActivated→Reset 清掉 activation_code_，通知拿不到场景信息。
- **签名类型别「统一」**：ACTIVATION/DEVICE/SIMPLE 三级对应信任级别（4.1），「顺手统一」会破坏服务端验签预期。
