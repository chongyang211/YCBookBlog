# service/paas_shadow 属性功能（设备影子）· 业务串讲

> **一句话定位**：设备与云端的**双向属性同步**——cloud-side 属性是云端下发的「期望值」（权威配置），device-side 属性是设备上报的「已记录值」（业务层的重启恢复源）；模块用「版本号 + 三向收敛 + ack」把两侧在不稳定的网络与重启环境下最终对齐，并通过 signals 把变化实时推给业务层。
> **场次**：60 分钟（13 个文件约 2500 行，难点集中在版本体系与两个现网死锁/分叉问题的修复）　**听众**：同组开发 / 评审人 / 后续接手者
> **对照模版**：`06.技术模版/04.业务串讲的模版.md` 第 08 章　**代码基线**：`palm_app_linux/src/service/paas_shadow/`（2026-10-08 审阅，13 文件全量精读）

## 1. 需求与业务背景  [10min · 先现象后价值]

### 1.1 需求来源与问题
- **来源**：云端配置需要下发到设备（语言/时区、ADB 开关、刷掌行为参数、调试环境、运维策略、License 状态）；设备状态需要上报给云端留存（软件版本、运维开关、授权状态）。同一份语义在两侧都要「断电不丢、重启恢复」，且离线期间的变更不能丢。
- **问题**（三个现网真实故障，理解了它们就理解了为什么代码长这样）：
  1. **状态分叉**：云端纠正了 device-side 记录，只写了缓存没通知业务内存——「缓存已是新值、内存仍是旧值，用户必须重启一次才生效」；
  2. **重投死锁**：版本索引与数据两次写入脱节——云端按索引判「设备落后」无限重投，设备按数据判重无限 skip，属性永不生效且无法自恢复；
  3. **断线丢推**：MQTT 推送在断线窗口丢失（broker 不为离线设备保留），靠轮询兜底最长要等 300s。
- **目标**：双向同步最终一致；变化实时通知业务层（signals）；断电/重启/断线/恢复出厂全场景下版本不回退、不丢变更。

### 1.2 业务边界
- **做**：cloud-side 下发（HTTP diff 轮询 + MQTT type6 推送双通道）、device-side 上报（批量 + 实时两路径）、版本门与 ack、本地 KV 缓存（Config standalone）、Provider 取值抽象（三类来源）、PendingQueue 补报。
- **不做**：属性的业务语义解释（各业务模块自己订阅 signal 解析 JSON）；MQTT 连接管理（MqttService 持有，本模块只注册 handler + 订阅信号）；scope 维度扩展（当前全部走 `kScopeTypeGlobal=2/"global"`）。

### 1.3 关键业务规则
- **双侧语义**（本模块最重要的概念）：
  | 侧 | 写入方 | 语义 | 本地 key |
  |---|---|---|---|
  | cloud-side | 云端下发 | **期望值**（权威配置变更） | `c_data:` / `c_ver:` |
  | device-side | 设备上报 | **已上报值**（业务层的重启恢复源） | `d_data:` / `d_ver:` |
- **属性清单**（paas_shadow_constants.h）：`device_behavior`（language/time_zone）、`operate_adb`、`palm_behavior`（app_type、allow_palm_wake、mode_after/host_wake、output_protocol/content、result_action_mode、hybrid_enroll_method + 三项 local-only 不同步云端）、`device_debug`（zerus_id）、`device_ops`（download_strategy/disable_self_recovery）、`module_auth`（license 状态，Story 136057693）。
- **版本规则**：uint32 单调；**时间戳版本** `now - 1000000000`（kTimeVersionOffset，impl.cpp:24）——同一秒内重复写则 `last+1` 兜底（:150-154）；MQTT 推送 `version==0` 视为强制更新（:819）。
- **两种信号口径**（impl.h:28-45，接手最易混淆处）：
  - `CloudSidePropertyChangedSignal` = 云端**期望值**变更（权威配置）→ 业务层应用新配置；
  - `DeviceSidePropertyRefreshedSignal` = 设备侧**已上报值**的本地缓存被云端记录纠正 → 订阅者**只做重新加载，禁止反向上报**（否则与云端来回覆盖）。

### 1.4 改动范围（模块组成）
- **[门面]** `paas_shadow.h`（单例壳，6 个公开方法）→ `paas_shadow_impl.h/.cpp`（1100 行，全部逻辑）。
- **[协议]** `paas_shadow_client.h/.cpp`（4 个 HTTP 接口）+ `property_entity.h`（13 个实体 + JSON 序列化）。
- **[缓存]** `paas_shadow_cache.h/.cpp`（四类 key 的读写 + 对齐检查）。
- **[抽象]** `property_provider.h`（三类取值来源）+ `paas_shadow_constants.h` / `paas_shadow_utils.h`。
- **[测试]** 两个 gtest（constants + entity round-trip）。

## 2. 整体设计与模块划分  [10min · 先图后讲]

### 2.1 架构与分层
```
业务层（PalmBehavior / DeviceOps / ModuleAuth...）
  ├─ RegisterProvider()（Start 前）      ← 取值抽象：设备侧值的来源
  ├─ Get*SideProperty() / Update*()      ← 同步 API（读写本地缓存/触发上报）
  └─ GetSignal(id) / GetDeviceSideRefreshSignal(id)  ← 变更通知（boost::signals2）
 ┌───────────────────────────────────────────────────┐
 │ PaasShadow（门面单例）→ PaasShadowImpl              │
 │   Init()：cache only（开机即有本地值可读）            │
 │   Start()：激活后调（开网络同步）                     │
 │     ├ property_thread_（独立线程）                   │
 │     │   ├ Schedule() 协程：30s tick 主循环           │
 │     │   ├ 立即 Pull（cloud+device 各一次）           │
 │     │   └ MQTT type6 handler（转发到本线程）          │
 │   ├ PaasShadowClient：4 个 HTTP 接口（5s 超时）      │
 │   │   POST /iot/devices/{sn}/device-side-properties/diff │
 │   │   PUT  /iot/devices/{sn}/device-side-properties      │
 │   │   POST /iot/devices/{sn}/cloud-side-properties/diff  │
 │   │   POST /iot/devices/{sn}/ack-cloud-side-properties   │
 │   └ PaasShadowCache：Config standalone "paas_shadow" │
 │       d_data/d_ver/c_data/c_ver 四类 key              │
 └───────────────────────────────────────────────────┘
   依赖：Network（签名 HTTP）、MqttService（type6 下行 + 连接态信号）、
        Config（本地 KV）、Threads（property 线程）
```
分层关键：**门面单例 → 实现单例**双层（与 Report/PaasShadow 一致的壳模式）；网络细节全在 Client，持久化全在 Cache，**Impl 只管状态机**——三个现网故障的修复（RefreshedSignal / Realign / 重连加速）全部落在 Impl，恰好说明状态机才是这个模块的心脏。

### 2.2 模块划分与职责
| 模块 | 职责 | 切分理由 |
|---|---|---|
| `PaasShadowImpl` | 同步状态机（Schedule 主循环、三向收敛、版本门、PendingQueue） | 全部核心语义单点 |
| `PaasShadowClient` | 4 个 wire 接口的请求/解析 | 协议与状态机隔离 |
| `PaasShadowCache` | 四类 key 读写 + `IsCloudVersionIndexAligned` | 持久化与对齐检查单点 |
| `property_entity` | 13 个实体 To/FromJson | 纯序列化可单测 |
| `DeviceSidePropertyProvider` | 取值抽象（三类来源） | 设备侧值的来源多态 |
| signals 两族 | cloud 变更 / device 刷新 | 两种语义刻意分开 |

### 2.3 核心数据流（云端下发一个配置为例）
```
运营平台改 palm_behavior.allow_palm_wake = true (v12)
 → MQTT type6 推送（或 60s/300s HTTP diff，断线时由轮询兜底）
 → ShouldProcessProperty: remote v12 > local v10 → 过版本门
 → ProcessCloudSidePropertyUpdate（impl.cpp:830-862）
     c_data/c_ver 落盘 → CloudSidePropertyChangedSignal 通知业务
     → ack /ack-cloud-side-properties（v12, success）
 → 业务层（如 PalmBehavior）收到信号 → 应用新配置 → 值变化时走
     UpdateDeviceSidePropertyRealtime 上报 device-side（d_data 新版本）
 → 云端记录设备已生效值；下一轮 diff 只剩版本对齐（no-op）
```

## 3. 逐模块实现讲解  [25min · 业务意图先行]

### 3.1 生命周期：Init / Start / PullDone 三阶段　impl.cpp:160-254
- **业务意图**：开机先有本地值可读（不依赖网络），激活后才开网络同步，首次设备侧 Pull 完成前禁止新写入（防版本冲突）。
- **要点**：`Init()` 只建 cache（:160-170）；`Start()` 创建 `property_thread_` + `Schedule()` 协程 + 两次立即 Pull（:195-210，注释明示「Pull 先于心跳上报，避免版本号冲突」）+ 注册 MQTT handler 与连接态信号（:218-251）；`PullDone` 是一个 `compare_exchange_strong` 单次翻转门（:799-803）。

### 3.2 `Schedule()` 主循环　impl.cpp:611-679
- **业务意图**：一个 30s tick 的循环承载四件事，各自独立计时。
- **四件事**：① 批量上报（300s，失败 5 次退避 600s，:632-640）；② Pull device-side（60s，:650-657）；③ Pull cloud-side（60s 或 MQTT 连接时 300s；重连加速请求 `exchange` 消费、失败不回灌，:659-672）；④ `RefreshSystemRuntimeProviders`（:675）。
- **要点**：时间未同步整轮跳过（:622-625，签名 HTTP 会失败）；`cloud_pull_interval_sec_` 动态切换在首次 cloud pull 成功后才生效（:884-887）。

### 3.3 `PaasShadowClient`：4 个 wire 接口　client.cpp
- **要点**：路径含 device_sn（:40/:81/:127/:168）；**diff 请求带本地版本列表**，云端只返回有差异的属性——流量最小化；`UpdateDeviceSideProperties` 用 **PUT**（:82），其余 POST；错误码本地定义 `268569649/650`（:15-16，与 unified_errcode 隔离）；HTTP 层成功即 `resp.code=0`，**业务级 error_list 只记录不重试**（:93-99 + :724-731）——部分条目失败不阻塞整批。

### 3.4 `PaasShadowCache`：四类 key 与对齐检查　cache.cpp
- **业务意图**：值与版本分开存（`d_data`/`d_ver`...）——diff 请求只需扫版本 key，不用解析全部数据。
- **要点**：`SaveCloudSidePropertyToCache` **两次 SetValue 写入**（数据 + 版本索引，:97-115）——这就是 c_ver/c_data 脱节的来源（两次写非原子）；`IsCloudVersionIndexAligned` 缺字段取 -1（:137-138，必然触发 realign）；`Dump()` 并列打印 c_ver 与 c_data（:316-322，脱节直接可见，不用翻日志）。

### 3.5 Provider 取值抽象　property_provider.h
- **三类来源**（:13-17）：`kCloudDerived`（云端派生，权威在 cloud-side，InitialProviderFetch 跳过，:535-537）/ `kEventDriven`（事件驱动：上位机指令、授权变更）/ `kSystemRuntime`（系统运行时，支持 `GetRefreshIntervalSec()` 定时刷新，默认 60s）。
- **约束**：`GetValue()` 在 property_thread_ 上调用——实现者必须线程安全、不得耗时（网络请求禁止，:25-26）。

### 3.6 两族 signals 与通知　impl.cpp:1019-1074
- **要点**：通知前先拷 shared_ptr 出锁再触发（:1025-1032，避免持锁回调死锁）；信号异常 catch 住不向上抛（:1044-1046）；`NotifyDeviceSidePullDone` 的顺序是固定的：**FlushPendingQueue → InitialProviderFetch → callbacks**（:1077-1081，FR-1.2/FR-3.1 语义，乱序会导致补报值被 provider 初值覆盖或回调时序错乱）。

## 4. 核心代码实现细节与原理（重点）  [10min+ · 讲透原理]

### 4.1 挑选的核心代码
4 处（前三处各对应一个现网故障的修复）：**① device-side 三向收敛与 RefreshedSignal**；**② 版本门 + realign 死锁自愈**；**③ 时间戳版本 + PullDone 门 + PendingQueue**；**④ 双通道动态间隔与重连加速**。

### 4.2 专深①：三向收敛（PullDeviceSideProperties）　impl.cpp:737-806
```
对云端 diff 返回的每条 device-side 属性，与本地缓存比较：
  本地无缓存      → saved：落盘 + NotifyDeviceSidePropertyRefreshed（业务层补加载）
  remote 版本 == 本地 → no-op（仅版本对齐确认）
  remote 版本 >  本地 → updated：覆盖本地 + 值变才通知
  remote 版本 <  本地 → pushed：反向上报本地值（云端旧，本地新）
```
**为什么这么写（原理）**：
- **三向收敛本质是 CRDT 式的单调版本合并**：谁版本高听谁的，两侧最终对齐，不需要协调者。`pushed` 分支是关键——上次上报成功但本地缓存回滚（或同设备另一会话写入）时，**设备主动纠正云端**。
- **`RefreshedSignal` 只在值确实变化时发**（:779-785，注释明示「避免纯版本号推进触发无谓回调」），且订阅者只做重载不反向写——这是修复「状态分叉」的机制：d_data 是业务层的**重启恢复源**，缓存被纠正后必须让内存跟上，否则缓存/内存分叉，用户要重启一次才生效（现网已出现）。
- 计数日志 `saved/updated/pushed`（:794-797）是排障第一入口——三个数说明三向合并各自发生了多少。

### 4.3 专深②：版本门 + realign 死锁自愈　impl.cpp:808-946
```cpp
// 版本门（HTTP diff 与 MQTT 推送共用，:808-828）
bool ShouldProcessProperty(remote, out_old_version) {
  if (remote.property_version == 0) return true;   // MQTT 强制推送
  if (!local.has_value()) return true;              // 新属性
  return remote.property_version > out_old_version; // 严格更新才处理
}
// realign（stale 分支时调用，:910-946）
IsCloudVersionIndexAligned(local) == false
  → 重写 c_data + c_ver 强制对齐 → 补发 ack
```
**为什么这么写（原理）**：
- **版本门是双通道一致性的前提**：HTTP diff 和 MQTT 推送是乱序到达的两条流，没有版本门就会旧值覆盖新值（乱序回退）。门统一在 `ShouldProcessProperty`，两条路径（:896/:974）共用同一判定——**一处门，两路收口**。
- **死锁的形成与自愈**：`SaveCloudSidePropertyToCache` 两次 SetValue 写 c_data 和 c_ver，现网出现过脱节（c_data=v5 而 c_ver=v4）。此后**云端按 c_ver 判「设备落后」→ 无限重投 v5；设备按 c_data 判重 → 无限 skip**——属性永不生效、永不 ack、重启也读旧值（现网已出现）。自愈三步：识别（`IsCloudVersionIndexAligned`）→ 重写两个 key 对齐 → 补发 ack 让云端停止重投。**幂等重投（索引一致）与脱节（索引落后）的区分**是设计核心：前者直接返回（:922-924），后者才 realign。
- **`version==0` 强制处理**：MQTT 推送通道无法保证带版本语义时的逃生门。

### 4.4 专深③：时间戳版本 + PullDone 门 + PendingQueue
```cpp
// PrepareDeviceSideProperty（impl.cpp:118-158）
if (!last_property && !pull_done) return false;     // PullDone 前拒写（转 PendingQueue）
auto new_version = now > kTimeVersionOffset ? now - kTimeVersionOffset : kVersionMin;  // :147
if (new_version <= last_version) new_version = last_version + 1;   // :150-154 同秒兜底
SaveDeviceSidePropertyToCache(out_property);         // 先落盘再进等待队列
```
**为什么这么写（原理）**：
- **时间戳版本（`now - 1000000000`）**：恢复出厂清空云端记录后，若用 0 起自增计数，新设备的 v1 会被云端判「更老」；时间戳版本天然单调且跨恢复出厂不回退（:146 注释）。**代价**：版本失去紧凑性，但属性量级小，无所谓。
- **PullDone 前拒写**：本地无缓存且未 Pull 时，无法知道云端已有版本——贸然上报会用**比云端更老的版本**写（版本冲突）。所以先把请求暂存 `pending_queue_`（key = `identifier_scopeType_scopeValue` 天然去重、只留最后一次值，:202-204），PullDone 后 Flush（:501-527）。**这是「拒写-暂存-补报」三段式，不是简单拒绝**。
- **先落盘再进等待队列**（:156）：`waiting_property_map_` 不持久化，重启即丢——但缓存里有，下一轮 Pull 的 `pushed` 分支会把值重新推给云端。**等待队列可以丢，因为缓存 + 三向收敛是恢复源**（设计闭环）。
- **实时路径失败自动回退批量队列**（:400-407）——两条路径不是并列而是兜底链：realtime 失败 → waiting map → 300s 批量重试。

### 4.5 专深④：双通道动态间隔与重连加速　impl.cpp:99-102/:659-672
- **动态间隔**：MQTT 连接且 cloud pull 成功过一次 → 60s→300s（HTTP 降为兜底）；MQTT 断开 → 回 60s。
- **重连加速（2026-09-16 增强，:227-236 注释）**：断线窗口内云端推送已丢（broker 不为离线设备保留），原靠轮询最长等 300s；MQTT 重连信号置位 `cloud_pull_requested_`，Schedule 循环 ≤30s（tick 粒度）内 `exchange` 消费——**失败不回灌**（:660 注释，防抖：失败由既有间隔或下次重连再触发）。
- **降级边界（注释明示，:232-235）**：MQTT 重连有 give-up（120 次 ≈ 2h）后阻塞等待链路态跳变唤醒；断网 ≥2h 且链路态无跳变（门店上游断网）时恢复后无 ConnectedSig——加速不生效，退回 60s/300s 轮询，**行为与增强前一致**（不劣化）。

### 4.6 性能与复杂度
- Schedule 30s tick，每轮至多 1 次批量 + 2 次 pull + provider 刷新，全部串行在 property_thread_（无并发重入）。
- diff 只传版本列表（非全量数据）；ack 单条。
- 缓存读写 O(1)（KV），版本收集 O(n)（扫 c_ver/d_ver 前缀 key）。

## 5. 边界、异常与测试  [5min · 别一笔带过]

### 5.1 异常与降级
- 时间未同步：整轮跳过（签名 HTTP 必失败），自动恢复。
- device_sn 为空：4 个接口统一 `ERR_PALM_IOT_DEVICE_SN_EMPTY` 直接失败。
- JSON 解析失败：nullopt / 异常捕获，get 返回空串。
- MQTT 断线：HTTP 轮询兜底；≥2h 长断网退回纯轮询（见 4.5）。
- 信号回调抛异常：catch 住记日志，不影响其他订阅者。

### 5.2 边界条件
| 场景 | 行为 |
|---|---|
| 恢复出厂后重报 | 时间戳版本不回退（4.4） |
| 同一秒内两次写 | `last+1` 兜底（:150-154） |
| PullDone 前业务调 Update | 拒写 → PendingQueue 暂存（保留最后一次值） |
| Start 后再 RegisterProvider | 拒绝（FR-2.2，:487-489） |
| MQTT 推 version==0 | 强制处理（无版本语义逃生门） |
| 云端重复下发已确认版本 | 索引一致 → 幂等重投，直接返回 |
| c_ver/c_data 脱节 | realign + 补 ack（死锁自愈） |
| 批量上报失败 | 回退 waiting map，5 次后退避 600s |
| realtime 失败 | 自动回退批量队列（兜底链） |
| error_list 非空（HTTP 成功） | 只记录不重试（部分失败不阻塞整批） |

## 6. 踩坑与接手注意事项（含审阅发现）  [审阅 + 雷区]

### 6.1 开发中坑
- **两族信号别用混**：`CloudSidePropertyChanged` = 期望值变更（应用配置）；`DeviceSidePropertyRefreshed` = 已上报值被纠正（只重载，禁止反向上报）。搞反会出现设备与云端来回覆盖。
- **`UpdateDeviceSideProperty` 返回 true ≠ 已上报**：只表示「已受理」（含进了 PendingQueue）；真正上报时刻由 Schedule 决定。调用方要立即生效走 Realtime + callback。
- **业务级 error_list 不重试**：HTTP 200 但某条目报错（如版本冲突）只记日志（client.cpp:93-99）——排查「上报成功但云端没记录」时先看 error_list 日志，不是 HTTP 层。
