# facility/scheduler 基频调度器 · 业务串讲

> **一句话定位**：全工程的**周期任务底座**——1 秒基频定时器 + `frequency_multiplier` 整数倍分频，任务按「名称注册 / 优先级排序 / 三种执行模式」派发；频率可运行时调整（`SetTaskMultiplier`），可启停（`SetTaskEnabled`）。前九篇串讲里所有「每 N 秒做一次」的语义（上报 60s、资源指标 5min、指令轮询 60↔300s、License 检查 1h）都落在这 3 个文件约 280 行上。
> **场次**：30-45 分钟（模块小而精，难点在 tick 分频模型与任务生命周期）　**听众**：同组开发 / 评审人 / 后续接手者
> **对照模版**：`06.技术模版/04.业务串讲的模版.md` 第 08 章　**代码基线**：`palm_app_linux/src/facility/scheduler/`（3 文件全量精读 + 全仓 12 处调用方核对，2026-10-08 审阅）

## 1. 需求与业务背景  [8min · 先现象后价值]

### 1.1 需求来源与问题
- **来源**：周期性任务散落各模块（上报队列上传、资源指标采集、指令轮询、License 到期检查、升级查询、网络测速自动触发、时间信任轮询）——若各自起 timer/线程，定时器数量与线程数双失控，且频率无法统一治理。
- **问题**：① 频率常需**运行时调整**（MQTT 在线时指令轮询 60s→300s、上报失败退梯降频）；② 所有任务若同刻触发会造成资源尖峰；③ 时间未同步时敏感任务（签名 HTTP）必须整轮跳过；④ 任务执行耗时需可观测（慢任务告警）。
- **目标**：一个调度器管所有周期；频率/启停动态可调；错峰执行；时间门控；执行统计与慢任务告警。

### 1.2 业务边界
- **做**：基频 1s 分频调度、优先级排序派发、kSync/kAsync 双模式、动态频率与启停、时间同步门控、执行统计（total/max/min/失败数）。
- **不做**：cron 表达式（只有整数倍频率）；任务重入防护（同任务上一轮未完下一轮照发，调用方自防）；固定时刻调度（只有周期+offset）；kCoroutine 模式（**预留未实现，注册即静默不执行**）。

### 1.3 关键业务规则
- **分频公式**（base_frequency_scheduler.cpp:108-109）：
```cpp
task.tick_counter++;
if (task.tick_counter > task.initial_offset &&
    (task.tick_counter - task.initial_offset) % task.frequency_multiplier == 0)
  → 就绪
```
  tick 从 1 起、`initial_offset` 相位平移——**offset 是相位不是延迟**（改 multiplier 时相位不变，tick_counter 不重置）。
- **派发顺序**：每 tick 收集就绪任务 → 按优先级排序（kCritical 0 → kLow 3，:115-117）→ 逐个 Dispatch。
- **执行模式**（DispatchTask :124-138）：kSync 在调度线程执行（**纪律 <10ms**）；kAsync post 到 2 线程池；kCoroutine 无操作。
- **动态接口语义**：`SetTaskMultiplier` 只改频率不改启用态；`SetTaskEnabled` 只改启停不改频率（h:68-72 注释明示）——两旋钮独立。

### 1.4 调用方全景（全仓 12 处已核对）
| 调用方 | 任务名 | multiplier | 模式 | 动态行为 |
|---|---|---|---|---|
| report_service | `report_upload_{table_id}` ×3 | 60 | **kSync**（<1ms 只投递，实际执行在自己的 2 线程池） | Stop 时逐队列 Unregister |
| metrics_resource_reporter | 资源指标 | 300（5min）offset 15s | — | Stop 时 Unregister；私有化下禁用 |
| iot_service | `iot_command_polling` | 60↔300 | kCritical kAsync offset 10 | SetTaskMultiplier 随 MQTT 连接态切换；`requires_time_synced=true` |
| verify_record_reporter | 上报轮 | 动态 target | kLow kAsync | **失败退梯降频**（:343-344）；Stop 双 Unregister |
| upgrade_schd | 升级查询 | 正常↔NoPush | — | 随 MQTT 切换；Stop 时 Unregister |

## 2. 整体设计与模块划分  [8min · 先图后讲]

### 2.1 架构与分层
```
 RegisterTask(name, multiplier, func, priority, mode, offset, time_synced)
 ┌────────────────────────────────────────────────┐
 │ BaseFrequencyScheduler（单例）                   │
 │  Start(): 匿名线程跑 scheduler_ctx_              │
 │   base_timer_ 1s → OnBaseTick → ScheduleTasks    │
 │     ├ 锁内：遍历 map，tick++，收集就绪任务(裸指针)  │
 │     ├ 锁外：按优先级排序 → DispatchTask           │
 │     │    ├ kSync  → 调度线程直接 ExecuteTask       │
 │     │    ├ kAsync → post 到 iot_pool_(2 线程)     │
 │     │    └ kCoroutine → TODO 无操作               │
 │     └ 重挂 1s timer（从派发完成后起算）             │
 │  ExecuteTask: 时间门控 → func() → 统计/慢任务告警   │
 └────────────────────────────────────────────────┘
   任务表 std::map<string, TaskDescriptor> + tasks_mutex_
```
分层关键：**「一个定时器 + 一个表」**——所有周期任务共享一条 1s tick 链，分频在 tick 计数里做；**派发与执行分离**（kSync 立即执行、kAsync 落池）让调度线程不被网络 I/O 堵死——与线程串讲「专用线程 vs 共享池」同一套选型思想。

### 2.2 模块职责
| 组件 | 职责 |
|---|---|
| tick 链（OnBaseTick/ScheduleTasks） | 分频判定 + 优先级排序 |
| DispatchTask/ExecuteTask | 模式派发 + 时间门控 + 统计 |
| 管理接口四件套 | Register/Unregister/SetEnabled/SetMultiplier |
| TaskDescriptor.stats | 每任务执行数/失败数/总耗时/max/min |

## 3. 逐模块实现讲解  [15min · 业务意图先行]

### 3.1 注册与管理四件套　.cpp:21-61
- **RegisterTask**（:21-40）：`tasks_[name] = std::move(desc)`——**同名重注册=静默覆盖**（tick 与统计清零），幂等 init 方便但意外双注册会互相吞（6.2-S5）。
- **Unregister/SetEnabled/SetMultiplier**：全部 `tasks_mutex_` 下操作 map；**Unregister 是 erase——立即销毁 TaskDescriptor**（这是 6.2-S1 的根源）。

### 3.2 tick 链与派发　.cpp:63-138
- **Start**（:63-80）：`running_` CAS 防重入；建 2 线程池 + io_context + **detached 匿名线程**跑 tick 链（:75-79，无 pthread_setname——`top` 里是匿名线程，6.2-S7）。
- **OnBaseTick**（:88-97）：ScheduleTasks 后 `expires_after(1s)` 重挂——**从派发完成后起算，不是固定时刻表**；kSync 任务耗时直接拖慢 tick 节拍（6.2-S3）。
- **ScheduleTasks**（:99-122）：锁内收集 `ready`（**裸指针**，:110）→ 锁外排序派发。

### 3.3 ExecuteTask：门控与观测　.cpp:140-164
- **时间门控**（:144-147）：`requires_time_synced` 的任务在时间不可信时整轮跳过（CheckTimeSyncedOrSkipLog 带 60s 日志节流）——iot 指令轮询、License 检查等签名类任务的统一安全网（与激活串讲 A1、指令串讲的时间守卫同族）。
- **统计与告警**（:149-163）：try/catch 包住 func（异常不逃逸、计 failures）；>100ms 打慢任务告警（:161-163）；total/max/min 全累计——**每任务自带性能档案**，排障先看这里。

## 4. 核心代码实现细节与原理（重点）  [8min · 讲透原理]

### 4.1 深挖①：分频模型的三个语义细节
- **offset 是相位**：`(tick - offset) % multiplier == 0`——offset 平移整个调度相位，配合随机初始 offset 错开各任务（h:56 注释「避免同一时刻执行造成资源竞争」）。report 三队列的 offset 步长 5s、metrics 的 15s 都是这个用法。
- **改 multiplier 相位不变**：SetTaskMultiplier 不重置 tick_counter——60→300 的下一次触发落在 `(tick - offset) % 300 == 0` 的下一个格点，**最长再等 300s**（不是立刻）；300→60 同理最长 60s。MQTT 联动降频的延迟特征由此而来（iot/upgrade 的切换注释都基于这个语义）。
- **kSync 的节拍漂移**：timer 从「派发完成」起算——kSync 慢任务直接拉长基频节拍，所有任务跟着慢。**「kSync < 10ms」是全模块最硬的纪律**（h:31 注释），report 的 kSync 投递任务 <1ms 正是为此（report 只把任务 post 到自己池，真正上传在池里）。

### 4.2 深挖②：优先级与执行模式的组合语义
- 优先级只影响**同 tick 内的派发顺序**（排序 :115-117），不影响抢占——kCritical 不会打断已跑的 kLow。
- kSync 串行占调度线程、kAsync 并发占池：**同 tick 就绪的一批 kAsync 任务在 2 线程池里最多 2 并发**，其余排队——高峰 tick（如整点对齐的多任务）实际是「排队串行化」，这是错峰 offset 存在的理由。

### 4.3 深挖③：无重入防护——调用方自防
- 同一任务上一轮还在池里排队/执行，下一 tick 到期**照发**——两轮并发。周期 < 任务耗时时实例堆积。
- 已核对的调用方里 iot 的 `pulling_` CAS（指令串讲 4.4）是标准答案；其余调用方靠「周期 >> 耗时」的余量兜底。**新增任务时先问自己：这任务可能超过自己的周期吗？** 超过就加自防或加大 multiplier。

### 4.4 深挖④：调用方的三种动态模式（1.4 表的归纳）
1. **环境联动调频**（iot/upgrade 随 MQTT 60↔300）——`SetTaskMultiplier`；
2. **失败退梯**（verify_record :343-344）——失败周期性降频，恢复后升回；
3. **自禁用 once-ish**（preload_key、time_trust）与 **Enable 代替 Unregister**（network_diagnosis :131-144，注释「不注销，仅禁用——Start 可重新启用」）——第 3 种实际上绕开了 Unregister 的生命周期问题（见 S1）。

## 5. 边界、异常与测试  [5min · 别一笔带过]

### 5.1 异常与降级
- 任务抛异常：ExecuteTask 捕获，计 failures，调度器不崩（:150-156）。
- 时间未同步：敏感任务整轮跳过（60s 节流日志）。
- 慢任务：>100ms 告警；kSync 慢任务拖节拍（4.1）。

### 5.2 边界条件
| 场景 | 行为 |
|---|---|
| 同名重注册 | 静默覆盖（tick/统计清零），6.2-S5 |
| Unregister 时任务在途 | **UAF 窗口**（6.2-S1） |
| kCoroutine 注册 | 静默不执行无告警，6.2-S6 |
| multiplier 中途修改 | 相位不变，下次落新格点（最长等一个新周期） |
| 任务周期 < 耗时 | 实例堆积并发，调用方自防（4.3） |
| Stop 后 Start | running_ CAS 允许；tick_counter 不清（延续相位） |

### 5.3 测试覆盖
- **已有**：`base_frequency_scheduler_test.cpp`——**「复制 + 守护」模式**（:3-5 注释：不 include 头文件以斩断依赖链，复制关键常量/枚举，static_assert + TEST 双守护与原定义一致）——这是个值得推广的解耦测试写法。
- **未覆盖（open）**：**调度行为零单测**——分频判定（offset/multiplier 边界）、优先级排序、模式派发、动态接口、时间门控全部没有可执行测试（测试文件只守护常量）。改 ScheduleTasks 分频公式无护栏（4.1 的三个语义细节全靠人肉）。

## 6. 踩坑与接手注意事项（含审阅发现）  [审阅 + 雷区]

### 6.1 开发中坑
- **kSync 纪律**：<10ms，违者拖累全模块节拍——需要重活就 kAsync 或像 report 那样「kSync 只投递、执行落自己的池」。
- **周期与耗时比**：设计任务时周期 ≥ 3× 预期耗时，否则要自防重入（4.3）。

### 6.2 接手者雷区地图（⚠️ 本次审阅发现）
| # | 现象 | 代码位置 | 风险 / 建议 |
|---|---|---|---|
| **S1** 🔴 | **Unregister 的 UAF 窗口**：ScheduleTasks 锁内收集的是**裸指针**（:110），锁外排序派发（:115-121）；kAsync 把裸指针 post 进池队列（:132）；UnregisterTask 是 erase **立即析构 TaskDescriptor**（:44）——指针在 `ready`/池队列/调度栈上期间被 Unregister，后续 `task->exec_mode`/`task->func()` 即 UAF。**Unregister 有 6 个活跃调用方**（metrics/verify×2/license/upgrade/report_service），Stop 与在途 tick 竞争即崩 | .cpp:99-138/:42-45 | 修法方向：shared_ptr<TaskDescriptor> 存 map（erase 只减引用，在途轮次安全结束）；或 Unregister 改「先 SetEnabled(false) + 延迟 erase」。现网概率低（Stop 都发生在模块安静期）但真实存在 |
| **S2** | 统计字段无锁写：ExecuteTask 在池线程写 `total_*`（:152-160），与 SetMultiplier 等锁内写并发——不同字段实践上良性，形式上是 data race | .cpp:149-163 | 把 stats 并入锁内或改 atomic；至少注释声明现状 |
| **S3** | kSync 慢任务拖节拍：timer 从派发完成起算，无节拍补偿 | .cpp:88-96 | 已有 >100ms 告警；长期可改为固定时刻表（`expires_at`）+ 漂移统计 |
| **S4** | kCoroutine 注册即静默死任务（TODO 无告警） | .cpp:134-136 | RegisterTask 对 kCoroutine 打 LOG_W，或直接删该枚举值 |
| **S5** | 同名重注册静默覆盖（tick/统计清零，吞掉原任务） | .cpp:39 | 重名打 LOG_W；或 Register 返回 bool |
| **S6** | Start 的 tick 线程 detached 且未命名 | .cpp:75-79 | 加 `pthread_setname_np`（排障时 `top` 可见）；Stop 不 join（detached）语义可接受 |

**给接手者的硬提醒**：
- 🔴 **新代码优先 SetTaskEnabled 而不是 Unregister**——S1 的现实规避（network_diagnosis 已是范例）；必须 Unregister 时先 Enable(false) 让在途轮次排空再延迟注销。

- 🟡 新任务的 `initial_offset` 用随机值（h:56 注释）——对齐到 0 会造成整点尖峰。
