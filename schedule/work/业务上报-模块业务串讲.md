# service/report 业务上报 · 业务串讲

> **一句话定位**：模组所有业务事件的**统一上报出口**——业务侧 `Create() → 填字段 → Commit()` 三步产出一个事件，框架接管其余一切：心跳线程序列化 → 按 log_id（16160/25261/99001）分道入**加密持久化队列**（断电不丢）→ 独立线程池每 60s 批量取出 → 自研 OTLP Builder 封装 → `/iot/report/logs|metrics` 发后台；失败回滚重试，Metrics 过期即弃。
> **场次**：60 分钟（模块横跨 25 个文件、四层架构，难点集中在队列语义与 OTLP 拼装）　**听众**：同组开发 / 评审人 / 后续接手者
> **对照模版**：`06.技术模版/04.业务串讲的模版.md` 第 08 章　**代码基线**：`palm_app_linux/src/service/report/`（+ 上游 `service/report_service.cpp`，2026-10-08 审阅）

## 1. 需求与业务背景  [10min · 先现象后价值]

### 1.1 需求来源与问题
- **来源**：多个 Story 汇聚到同一出口——137913126（palm.* 会话事件族 + trace/span，FR-1/2/5）、136969382（识别方式熔断 FR-3.4 + 核验台账 FR-4.2）、137345399（网络诊断结果 FR-4.1）、135784881（client_trace_id 会话级链路）、136123576（自愈事件）、76593838（识别耗时埋点解耦）。
- **问题**：① 业务事件上报散落各处，各写各的 JSON、各发各的请求；② 断网/重启时在途数据全丢，事后无法补录；③ 后台要按模块区分数据（IoT / App / Metrics 三张表），还要能按事件时刻检索；④ 排障需要把设备端事件与后台日志串起来（trace 凭据）。
- **目标**：一个入口、三条通道、持久化不丢、OTLP 标准格式、事件级 trace_id/span_id、按事件真实时刻入档。

### 1.2 业务边界
- **做**：Logs 双表（16160 IoT/OTA/自愈，25261 App 会话/守护/诊断）+ Metrics 单表（99001 资源/识别指标）；加密落盘队列；批量上传（200 条/次）；失败重试（Logs）/ 时效丢弃（Metrics）。
- **不做**：真接 OpenTelemetry SDK（`opentelemetry_entity` 是**自研手写的 OTLP JSON 模型**，零第三方依赖）；合并/节流（无去重，队列来多少发多少）；MQTT 通道（5 个 action 常量已定义，调用点全 TODO 未接入）；温度采集（资源指标仅 CPU/内存/磁盘 7 项）。

### 1.3 关键业务规则
- **三张表口径**（log_id 即 table_id，决定队列与 scope）：
  | table | 内容 | 通道 | scope.name |
  |---|---|---|---|
  | **16160** MMPayPalmIoTReport | 网络/OTA/自愈（kApiRequestFail、7 个 kOtaPerformUpgrade、kRecover*） | `/iot/report/logs` | "16160" |
  | **25261** MMPayPalmAppTerminalReport | palm.* 会话 5 事件族、熔断、核验台账、摄像头、Guard 守护、网络诊断 | `/iot/report/logs` | "25261"（**后端靠 scope.name 区分模块**，只支持数字 scope） |
  | **99001** | 资源 Gauge（CPU/内存/磁盘）+ 识别三 Gauge | `/iot/report/metrics` | 按指标组分 |
- **事件语义**：`action_type`（start/end/doing）、`route`（cloud/local）、`end_state`（success/fail/abort）、`work_mode/palm_mode` 四值——Logs/Metrics 共享词表（report_attribute_keys.h:20-39）。
- **持久化语义**：Commit 只投递不确认；跨重启靠落盘队列补投；Metrics 网络失败**直接丢弃**（时效数据过期无意义）；Logs 网络失败回滚重试。

### 1.4 改动范围（模块组成）
- **[框架]** `report.h/.ipp`（静态门面）+ `report_item_base.h/.cpp/.ipp`（CRTP 基类 + Holder）。
- **[抽象]** `abs/` 三个 builder 接口头 + `opentelemetry_entity.h/.cpp`（自研 OTLP 模型）。
- **[协议]** `protocol/` 五个 Item 定义（两条 Logs 表 + 一条 Metrics 注册壳 + 会话专用 Item）。
- **[具体]** 7 组上报器/采集器（资源指标、识别指标、摄像头、自愈、App Logs builder）。
- **[上游]** `service/report_service.cpp`（真正的单例：队列管理、调度、上传）。

## 2. 整体设计与模块划分  [10min · 先图后讲]

### 2.1 架构与分层
```
业务代码（任意线程）
  PalmXxxItem::Create() → 填业务字段 → item.Commit()
        │ FillInContext()（调用线程：填 happen_time/session）
        ▼ HeartBeatThread::Post ──── 单线程串行，非线程安全基类的安全前提
  FillBeforeQueue()（填 SN/版本/env_id/seq）→ JSON 序列化（StripNull）
        ▼ ReportService::ReportTo(kTableId)
  加密持久化队列 /userdata/.palmos/report/palmapp_<table_id>
  （cross::ReportQueue，kReportQueueSecret 加密）
        ▼ BaseFrequencyScheduler 每 60s 触发（多队列错峰步长 5s）
  独立 2 线程池 Take(200) → abs/ Builder 封 OTLP JSON
        ▼ Network::IotDeviceRequest
  /iot/report/logs（16160/25261 批量）| /iot/report/metrics（99001 逐条）
```
分层关键：**「谁产生、谁填写、谁投递、谁上传」四级各司其职**——业务线程只填业务字段，设备指纹在心跳线程统一填，持久化由 ReportService 管，协议封装在 abs 层。业务侧对通道/格式/重试**零感知**。

### 2.2 模块划分与职责
| 模块 | 职责 | 切分理由 |
|---|---|---|
| `Report` + `ReportItemHolder` | 唯一入口、RAII 独占所有权 | 上报语义单点 |
| `ReportItemBase<T>` | 公共字段采集器（SN/env_id/seq） | CRTP 消除重复字段 |
| `protocol/` 五 Item | 定义 kTableId 与业务字段 | 每张表一个 Item，通道即类型 |
| `abs/` 三 Builder | OTLP Logs/Metrics 组装 | 协议细节与业务隔离 |
| `opentelemetry_entity` | OTLP 数据模型 + JSON 序列化 | 自研替代 OTel SDK，零依赖 |
| 7 组具体上报器 | 各业务域的采集与装载点 | 谁的数据谁负责填 |
| `ReportService` | 队列、调度、上传、重试 | 持久化与投递语义单点 |

### 2.3 核心数据流（一次识别会话事件为例）
```
PalmActionEventReporter::Emit（palm.* 事件族唯一装载点）
 → PalmSessionReportItem（25261，刻意不提供 Report* 快捷函数）
 → 填 18 个会话字段（session_id/client_trace_id/work_mode/end_state/last_state）
 → Commit() → 心跳线程 → 队列 palmapp_25261
 → 60s 后 Take(200) → PalmAppReportLogsBuilder
     trace_id ← client_trace_id（32hex→16 字节）
     span_id  ← traceparent 位移 36 截 16hex
     timeUnixNano ← 事件真实 happen_time
 → POST /iot/report/logs（scope.name="25261"）→ 后台按模块分表检索
```

## 3. 逐模块实现讲解  [25min · 业务意图先行]

### 3.1 `Report` 门面与 Holder　report.h:14-28、report.ipp:12-22
- **业务意图**：入口唯一、所有权清晰。
- **要点**：`Report` 是**纯静态门面**（真单例是 `ReportService`）；`ReportItemHolder<T>` 是 RAII 独占包装——`Commit()` 只投递（report_item_base.ipp:10-13），未 Commit 则析构静默丢弃（忘记 Commit = 事件没发生，不产生半成品）。

### 3.2 `ReportItemBase<T>`：两阶段填充　report_item_base.h:33-125
- **业务意图**：公共字段（SN/版本/flavor/env_id/seq）只填一处；**基类刻意非线程安全**（:36/:41 注释），安全性由「FillBeforeQueue 只在 HeartBeatThread 执行」的结构保证。
- **要点**：`REPORT_PROTOCOL_REGISTER` 宏静态注册 table_id→业务名（:129-131），`ReportService::DoInit()` 据此自动建队列——**新增一张表 = 加一个 Item 定义 + 一个宏，零改动框架**。

### 3.3 `protocol/` 五个 Item：通道即类型
- **要点**：`PalmReportItem<Derived>` CRTP 基类约 40 个业务字段 + 8 个快捷静态函数（`ReportAction/ReportEvent/ReportActionResult/ReportActionExt(Num)`，palm_report_item.h:120-189）——**业务侧一行完成装载**。`PalmIotReportItem`（16160）/`PalmAppReportItem`（25261，多 `opt_frame_image_id/opt_work_mode`）；`PalmMetricsReportItem` 是**空壳**（只有 kTableId=99001，仅用于注册 Metrics 队列）；`PalmSessionReportItem` 独立继承、**刻意不给快捷函数**（:166-170）——唯一装载点是 `PalmActionEventReporter::Emit`，防止绕过会话语义乱填。

### 3.4 `abs/` 三个 Builder + `opentelemetry_entity`
- **业务意图**：OTLP 协议封装；`BaseLogsBuilder` 头注释（:24-39）画出完整层次 ExportLogsServiceReq → ResourceLogs → ScopeLogs（scope.name=25261，后端靠它区分模块）→ LogRecord（attributes 必带 action）。
- **要点**：`BaseOpentelemetryBuilder` 的 `CreateKeyValue<T>()` 用 if constexpr 按类型分派（:77-107）；`opentelemetry_entity` 完整复刻 OTLP 三族数据模型（Logs/Metrics/Trace，.h:79-516，含 Gauge/Sum/Histogram/ExponentialHistogram/Summary），`ToJson/FromJson` 全手工 nlohmann——**不是接 OTel SDK**，是自研轻量复刻。

### 3.5 七组具体上报器（业务域逐个过）
| 上报器 | 机制 | 要点 |
|---|---|---|
| `metrics_resource_reporter` | 调度器：基频 1s×300=**5 分钟一次**，首偏移 15s；`PALM_PRIVATE_DEPLOY` 下禁用 | CPU 用**两次快照差值**算使用率，首次只存快照不上报（cpp:48-52） |
| `device_resource_metrics_builder` | 采集 CPU/内存/磁盘 7 项 Gauge，scope=`device_resource_monitor` | 摄像头指标**预留未接入**（.h:28-29） |
| `recognition_metrics_reporter` | 3 个 Gauge：`palm_recognize_result`（值恒 1，**靠 result/palm_mode/recognition_path 标签区分，成功率由后端聚合**）、优选耗时、云端识别耗时 | `ReportLocalRecognizeDuration` 直发解耦（见 4.4） |
| `camera_status_reporter` | 致命错误即时上报 + FlushQueue 抢在重启前发出；**恢复延迟 20min 才报**（kRecoveryDelaySec=20*60，防崩溃循环刷绿） | 只允许相机致命码（PalmCoreFatalClassifier 判定） |
| `recovery_reporter` | 开机读 `/data/palmapp/guard/recovery_event`（guard.sh 写）→ 解析 → 上报 → **乐观 unlink** | 解析失败保留文件下个开机重试；Commit 无返回值，跨重启投递交给持久化队列 |
| `palm_app_report_logs_builder` | 25261 Logs 的 OTLP Builder | trace/span 拼装 + happen_time（见 4.3） |
| （`opentelemetry_entity`） | 自研序列化层 | 见 3.4 |

## 4. 核心代码实现细节与原理（重点）  [10min+ · 讲透原理]

### 4.1 挑选的核心代码
4 处：**① 两阶段填充与线程安全设计**；**② 持久化队列的投递语义**（Logs 重试 vs Metrics 丢弃）；**③ OTLP trace/span/timeUnixNano 拼装**；**④ 识别耗时「到达即发」解耦**。

### 4.2 专深①：两阶段填充与线程安全
```cpp
// report.ipp:12-22（全文仅 10 行，整个框架的心脏）
template <typename T>
void Report::ReportItem(ReportItemHolder<T>&& item) {
  item->FillInContext();                     // ① 调用线程：填 happen_time / session
  Threads::HeartBeatThread()->Post([item = std::move(item)]() {
    item->FillBeforeQueue();                 // ② 心跳线程：填 SN/版本/env_id/seq
    nlohmann::json jo(*item);
    std::string j = cross::comm::DumpJsonStripNull(&jo);
    ReportService::Instance()->ReportTo(T::kTableId, std::move(j));  // 入持久化队列
  });
}
```
**为什么这么写（原理）**：
- **`FillInContext` 必须在调用线程**：happen_time 是「事件真实发生时刻」、session 上下文绑定调用方语境——一旦切线程就变成「投递时刻」，事件排序失真。
- **`FillBeforeQueue` 必须在单线程**：基类非线程安全（env_id_ 等静态成员无锁），靠「HeartBeatThread 唯一执行」保证——**不加锁，用线程归属换性能**。所以新增公共字段时，凡是天然单线程可填的放 `FillBeforeQueue`，需要调用线程语境的放 `FillInContext`。
- **`DumpJsonStripNull`**：空字段不进 JSON——同一 action 的字段集不同形态不同，避免后端解析出满屏 null。

### 4.3 专深②：持久化队列投递语义
```
队列：cross::ReportQueue，/userdata/.palmos/report/palmapp_<table_id>，加密落盘
调度：BaseFrequencyScheduler 每 60s 触发（kSync <1ms 只投递）；多队列错峰步长 5s
上传：独立 2 线程池（kReportThreadPoolSize=2），每次 Take(200)
```
**为什么这么写（原理）**：
- **Logs 失败 `RestoreTaken` 回滚重试**（report_service.cpp:173-177）：队列 Take 是「借出」，失败还回去——事件类数据不能丢（审计/排障价值随时间不衰减）。
- **Metrics 网络失败直接丢弃**（:265-273）：Gauge 是时效性数据，5 分钟前的 CPU 使用率重传毫无意义，反而污染趋势线——**「可丢性」是数据类型属性，由通道（kTableId）决定**，不是全局开关。
- **未知 table_id 丢弃**（:170-171）：防死循环——未知队列既发不出去又不该重试，静默丢弃是唯一收敛选择。
- **乐观 unlink + Commit 无返回值**（recovery_reporter.h:8-12）：跨重启投递交给持久化队列兜底，Commit 到入队之间的微秒窗口是**已知接受盲区**——工程上用「大概率成功 + 落盘兜底」换上报 API 的无阻塞签名。

### 4.4 专深③：OTLP trace/span/timeUnixNano 拼装　palm_app_report_logs_builder.cpp:79-129
```cpp
// trace_id ← client_trace_id（32hex → 16 字节）
// cpp:26-53 HexToBytes 严格校验——刻意不复用 BufferUtils（无校验）
// span_id ← traceparent（长度 55、偏移 36 截 16hex）；本地场景随机生成（:106-123）
// timeUnixNano ← 事件真实 happen_time（:87-92），不是上报时刻
```
**为什么这么写（原理）**：
- **trace_id 取 client_trace_id 而非网络层 trace**：client_trace_id 是会话级（story 135784881），一次刷掌尝试从端到后台串成一条——后台拿 trace_id 直接检索本会话日志。
- **HexToBytes 严格校验**：trace 字段是排障凭据，**写坏一个字节整条链路断**——宁可解析失败留空，不让脏数据上 wire。不复用 BufferUtils 的理由注释写明（无校验）。
- **span_id 从 traceparent 固定位移截取**：W3C 格式 `00-{32hex}-{16hex}-01` 长度恒 55、span 段位移恒 36——位移截取零解析成本（与 network 模块 `substr(3,32)` 同一手法）。
- **timeUnixNano 用 happen_time**：事件 9:00 发生、9:03 上报成功，入档时刻必须是 9:00——否则按时间窗检索事件会漏。**「事件时间」与「投递时间」是两个正交概念**，OTLP 的 timeUnixNano 语义是前者。

### 4.5 专深④：识别耗时「到达即发」解耦　recognition_metrics_reporter.h:96-134
- **旧范式问题**：端侧耗时靠 FSM 状态机在特定状态采集——SDK 埋点系统性晚到 3~11ms，状态机已走过去，**旧范式丢 84% 样本**。
- **修正**（story 76593838）：`ReportLocalRecognizeDuration` 由 SDK 埋点**到达即发**，刻意与 FSM 解耦（cpp:184-225）。教训值得推广：**指标采集点跟着数据产生点走，不要跟着消费数据的状态机走**。
- 另注意 137514528 的硬契约：后台 `avg_over_time` 60s——采集频率改变会直接改变聚合语义。

## 5. 边界、异常与测试  [5min · 别一笔带过]

### 5.1 异常与降级
- 私有化部署（`PALM_PRIVATE_DEPLOY`）：Metrics 与识别指标**静默禁用**（metrics_resource_reporter.cpp:18-21、recognition_metrics_reporter.cpp:64-66/:185-187），Logs 通道无此开关——**两通道行为不对称**，见 6.2-R10。
- 断电/重启：落盘队列补投（这是持久化队列存在的全部理由）。
- 摄像头致命错误：即时上报 + `FlushQueue(25261)` 抢在重启前发出（camera_status_reporter.cpp:28-30）。

### 5.2 边界条件
| 场景 | 行为 |
|---|---|
| 忘记 Commit | 析构静默丢弃，不产生半成品事件 |
| Holder 二次 Commit | **空指针崩溃**（无防护，见 6.2-R9） |
| Logs 上传失败 | RestoreTaken 回滚，下轮重试 |
| Metrics 上传网络失败 | 直接丢弃（时效性） |
| 未知 table_id | 丢弃防死循环 |
| 队列文件损坏/重叠/重开 | ReportQueue 内建校验自恢复（reportqueue_test_inc.h 14 用例） |
| CPU 首次采集 | 只存快照不上报（差值无基准） |
| 崩溃循环重启 | 摄像头恢复状态延迟 20min 才报（防刷绿） |

### 5.3 测试覆盖
- **ReportQueue 容错**（vendor_src/cross/report/reportqueue_test_inc.h）：文件损坏/重叠/重开校验 14 个 FRIEND_TEST 用例——持久化语义最有保障的一层。
- **verify_record_reporter_test.cpp**（20+ 用例）：5 字段最小化、20 条分批、传输/业务失败重试阶梯、毒批隔离、网络恢复退梯——引用 report 模块最重的测试。
- **network_stat_test.cpp**：ReportTdi/ReportDeviceRequest 烟雾级（NO_THROW）。
- **未覆盖（open 风险）**：**report 模块本体（Report 门面 / ItemBase / 各 Builder / 各 Reporter）无直接单测**——trace 拼装（4.4）、两阶段填充（4.2）的回归全靠联调。这与 speedtest 模块（完整单测）形成鲜明对照，是本模块最大的工程短板。

## 6. 踩坑与接手注意事项（含审阅发现）  [审阅 + 雷区]

### 6.1 开发中坑
- **「事件时间 vs 投递时间」**：分析后台数据、写检索条件时先想清楚用哪个——timeUnixNano 是 happen_time，队列延迟最大可到分钟级，别把投递延迟当成事件延迟。
- **成功率的口径**：`palm_recognize_result` 值恒 1，**成功率是后端按标签聚合出来的**——改标签集 = 改后台所有看板口径，需与数据侧同步。
- **新增表 = Item + 宏**：kTableId 走 `REPORT_PROTOCOL_REGISTER` 静态注册，忘记宏则 DoInit 不建队列、事件被「未知 table_id」丢弃且无日志级别告警。

### 6.2 接手者雷区地图（⚠️ 本次审阅发现 11 处，按严重度排序）
