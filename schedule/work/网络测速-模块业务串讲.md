# network/diagnosis/speedtest 网络测速与弱网分级 · 业务串讲

> **一句话定位**：用一次 ~5MB 文件下载采样出「带宽 + RTT」两个数，按短板法判成四级弱网等级（良好/一般/较差/弱网）+ 断网态，供推送策略降级（FR-3.3）与运维上报（FR-4）消费；测速文件未就绪时自动降级为「只测 RTT」，不缓存降级状态、文件就绪即自动恢复。
> **场次**：45-60 分钟（模块小而精，难点集中在采样口径与分级算法）　**听众**：同组开发 / 评审人 / 后续接手者
> **对照模版**：`06.技术模版/04.业务串讲的模版.md` 第 08 章　**代码基线**：`palm_app_linux/src/facility/network/diagnosis/speedtest/`（Story 137345399，T2.1/T2.2，FR-2.1/2.2/2.4/2.5，2026-09-08 审阅）
> **模块文件**：`speed_tester.h/.cpp`（测速执行器）、`weak_level.h/.cpp`（弱网分级判定器）+ 两个 catch2 单测（**本模块有完整单测**，与 detection 模块形成对照）

## 1. 需求与业务背景  [10min · 先现象后价值]

### 1.1 需求来源与问题
- **来源**：Story 137345399（O4 网络诊断）T2 任务簇——T2.1 弱网分级、T2.2 测速执行器；承接 detection（T1，四层检测回答「断没断、断在哪」）之后回答「**没断，但有多差**」。
- **问题**：商户现场网络质量参差（收银高峰共享带宽、私有化部署跨专线），刷掌识别对延迟敏感；但设备端只有「连上/连不上」两态——推送策略无法按网络质量降级（弱网还全量推图），运维也拿不到「当时网络多差」的量化证据。
- **目标**：（1）单次测速产出**带宽 kbps + RTT ms** 双指标 + 采样证据；（2）按阈值表判**四级弱网等级**，连续失败兜底判弱网；（3）测速源（服务端 `/speedtest` 文件）未就绪时**降级只测 RTT**，就绪后自动恢复；（4）等级供推送策略（FR-3.3）与上报（FR-4）消费。

### 1.2 业务边界
- **做**：下载窗口采样测速（TTFB=RTT、4s 窗口）、降级探测、弱网分级状态机、触发原因标注（manual/periodic/network_change/after_detection）、阈值 profile 结构化（预留云端下发）。
- **不做**：自动触发管理（30min 周期/网络变化事件/检测后触发——T2.3 在上游门面 `NetworkDiagnosis`）；测速与检测的编排（门面 T2.4）；多并发测速（单例串行，NetworkThread 上执行）；上传测速（只有下载方向）；海外阈值校准（默认表为国内商户基准，weak_level.h:6）。

### 1.3 关键业务规则
- **分级表**（FR-2.2，weak_level.h:7-13）：
  | 等级 | 阈值（短板法：双达标取最高级） | 等效带宽 |
  |---|---|---|
  | 良好 good | ≥2 Mbps **且** ≤200ms | ≥250 KB/s |
  | 一般 fair | ≥1 Mbps **且** ≤500ms | 125~250 KB/s |
  | 较差 poor | ≥0.16 Mbps **且** ≤1000ms | 20~125 KB/s |
  | 弱网 weak | <0.16 Mbps **或** >1000ms **或连续 2 次测速失败** | <20 KB/s |
  | 断网 disconnected | 检测失败且失败层为**连通层/服务层**（detection 通道判定） | — |
  | 未测 unknown | 初值，不参与推送/上报 | — |
- **口径规则**：RTT = **TTFB**（首字节时间，T0.1 定案）；带宽窗口**从首字节起算**（纯吞吐）；微秒级计时精度；`bandwidth_kbps = -1` 表示降级未测；降级成功也算 `success=true`（AC-5）。
- **失败计数语义**：测速失败 +1、成功清零、网络切换只重置计数（等级维持）——「连续 2 次」是跨触发原因的累计口径。

### 1.4 改动范围（模块内组成）
- **[执行器]** `SpeedTester`（单例）：URL 拼装（override 优先）→ full 下载采样 → 降级探测 → 三态出报告。
- **[判定器]** `WeakLevelClassifier`：纯函数分级（短板法）+ 检测通道断网判定 + 样本状态机（失败计数/等级，原子成员）。
- **[数据结构]** `SpeedTestReport`（FR-2.5）：指标 + 等级 + **P0 采样证据**（sample_bytes/transfer_ms/window_expired/high_bw_estimate，供 UI 核对带宽可信度）。

### 2.1 架构与分层
```
  NetworkDiagnosis 门面（T2.3 触发管理 + T2.4 编排）
        │ Run(trigger) / classifier() 消费
 ┌──────┴─────────────────────────────────────────────┐
 │ SpeedTester（单例，持有 classifier_）                │

 │        │成功                          │成功          │
 │        ▼                              ▼              │
 │   RecordSample(bw,rtt)        RecordDegradedSample() │
 │   （双维刷新+清零计数）        （仅清零，等级维持）     │
 │        └────────双双失败────────▶ RecordFailure()    │
 │                                      （连续2次→weak） │
```

分层关键：**「测量」与「判定」分离**——SpeedTester 只管把网络质量变成两个数，WeakLevelClassifier 只管把两个数变成等级（纯函数可穷举单测）；降级/恢复策略在执行器，等级语义在判定器。

### 2.2 模块划分与职责
| 模块 | 职责 | 切分理由 |
|---|---|---|
| `SpeedTester::TryFullDownload` | 窗口采样下载，产出 bw/rtt + 采样证据 | 测量逻辑单点，口径集中 |
| `SpeedTester::TryDegradedProbe` | health endpoint TTFB 探测 | 与 full 正交，独立超时（5s） |

| 样本状态机 | 失败计数 / 等级维护 / 网络切换重置 | 跨次测速的记忆，原子化 |

### 2.3 核心数据流（一次周期测速）

## 3. 逐模块实现讲解  [20min · 业务意图先行]

### 3.1 `SpeedTester::RunSync` 三态主干　speed_tester.cpp:120-179
- **业务意图**：一次测速 = full 先试 → 失败降级 → 双失败记账，三态出报告。
- **要点**：默认值先置 `bandwidth=-1 / rtt=-1`（125-126，降级未测口径）；full 成功 → `RecordSample(bw/1000.0, rtt)`（148，**kbps→Mbps 换算在这一个点**）；降级成功 → `RecordDegradedSample()`（166，等级维持）；全失败 → `RecordFailure()`（175）且 `mode` 填 degraded 表示「最后尝试形态」（174，注释明示）。

### 3.2 `ComposeSpeedTestUrl`：URL 三级口径　speed_tester.cpp:181-187
- **业务意图**：服务端 `/speedtest` 接口（T0.6）对齐进度不确定，URL 要可注入、可兜底、可缺省。
- **三级**：`speedtest_file_url_` override（T0.6 对齐后 `SetSpeedTestFileUrl` 注入）> `host + kSpeedTestFilePath`（默认拼装）> **空**（host 未配置 → 直接降级，FR-2.4「测速文件未就绪」涵盖）。

### 3.3 `TryFullDownload`：窗口采样　speed_tester.cpp:189-259（核心，见 4.2 深挖）
- **业务意图**：不下载完整文件，用固定时间窗估带宽——**省流量（4s 窗口而非 5MB 全量）且弱网强网统一口径**。
- **要点**：必须带 `Accept: application/octet-stream`（203-205，**不带会拿到 Base64 JSON，测速直接失真**——服务端 marshaler 按该 Header 分流）；样本有效性判定 `(window_expired || http_ok) && first_byte_seen && total_bytes>0`（230）——完整下完 5MB（高带宽）时窗口可能未满但 HTTP 200，同样有效。

### 3.4 `TryDegradedProbe`：降级 TTFB 探测　speed_tester.cpp:261-300
- **业务意图**：测速文件不可用时，至少回答「延迟多少」。
- **要点**：WriteCallback **首字节即 return false 断开**（275-282）——不拉 body，一个包测完；0 字节响应（WriteCallback 未触发）退化为**整体请求耗时兜底**（285-294，RTT 高估但可用），判定收紧为 `status < 500`（287，spec §9.3）；超时 5s 独立于 full 的 15s。

### 3.5 `WeakLevelClassifier`：分级判定器　weak_level.h/.cpp
- **业务意图**：把「两个数」变成「一个等级」，语义要能被推送策略直接消费。
- **要点**：`Classify` 纯函数（34-48）；`ClassifyFromDetection` 只认**连通层/服务层**失败为断网（50-63）——物理/本地层失败是设备侧配置问题，不占断网态（否则插网线问题会被当成「网络断了」触发推送降级）；状态机四个入口（RecordSample / RecordDegradedSample / RecordFailure / OnNetworkSwitched）全部落 atomic 成员（152-153，跨线程：NetworkThread 写样本、MainThread 处理网络切换）。

### 3.6 `SpeedTestReport` 与 JSON 口径　speed_tester.cpp:86-102
- **业务意图**：报告三通道（上报/wire/推送）统一字符串口径。
- **要点**：`weak_level` 输出**字符串**（"good"/...，91，spec §9.4 不透传 enum 数值——下游解析不依赖编译期枚举值）；P0 采样证据四字段全量输出（96-100），UI 用它判断「这个带宽可信吗」（window_expired=false 且 transfer<100ms → 参考值）。

## 4. 核心代码实现细节与原理（重点）  [15min · 讲透原理]

### 4.1 挑选的核心代码
3 处：**① 窗口采样的口径设计**（TTFB、首字节起算、abort-by-callback、精确端点）；**② 短板法分级算法**（「或」→「AND」的实现 + 开闭边界）；**③ 降级语义与状态机**（不缓存降级、等级维持的原理）。

### 4.2 专深①：窗口采样的口径设计
```cpp
// speed_tester.cpp:206-221 采样回调（SampleState 闭包）
req.SetWriteCallback(HttpRequest::WriteCallback{[&st](std::string data, intptr_t) -> bool {
  const auto now = std::chrono::steady_clock::now();
  if (!st.first_byte_seen) {
    st.first_byte_seen = true;
    st.first_byte_at = now;                        // TTFB = RTT（T0.1 定案）
  }
  st.total_bytes += data.size();
  if (now - st.first_byte_at >= kSampleWindow) {   // 窗口从首字节起算
    st.window_expired = true;
    st.window_end_at = now;                        // 精确端点（spec §9.2）
    return false;                                  // 主动中断（curl abort-by-callback）
  }
  return true;
}});
// 242-249  计算
const auto transfer_end = st.window_expired ? st.window_end_at : end;  // 窗口中断用精确端点
auto transfer_us = duration_cast<microseconds>(transfer_end - st.first_byte_at).count();
if (transfer_us <= 0) transfer_us = 1;             // 高带宽首包即完的除零保护
bandwidth_kbps = total_bytes * 8.0 / transfer_us * 1000.0;             // 微秒精度
```
**为什么这么写（原理）**：
- **窗口从首字节起算，不是从请求发起**：弱网下 TTFB 可能 2s——若窗口含建连，「建连 2s + 传输 2s」会被记成 4s 窗口，带宽直接腰斩低估（注释 213-214 点明）。**RTT 与带宽是两个正交指标，各用各的起算点**：RTT = start→首字节，带宽 = 首字节→窗口满。
- **主动中断而不是等超时**：`return false` 是 curl 的 abort-by-callback 机制——窗口一满立刻断流，不用下完 5MB（省流量），也不用吃 15s 总超时。**样本有效性由我方 `window_expired` 标志判定**（230），不耦合 cpr 的中断错误码（中断在 cpr 眼里是 error，我方眼里是正常采样完成）——这是「语义自持」的典型做法。
- **`window_end_at` 精确端点**：中断后 curl 还要做 cleanup（关连接、收尾），若用 `GetSync()` 返回后的时刻算传输时长，会把 cleanup 延迟算进窗口、低估带宽——所以**在回调里当场记下窗口满的精确时刻**（217，spec §9.2）。
- **微秒级精度**（249）：窗口 4s 内可能只传几百 KB，毫秒级截断误差在 kbps 结果上会被放大；`bytes×8/µs×1000` 全程 double。
- **不对称保护**（244-245）：`transfer_us<=0` 强制 1µs（首包即完是高带宽真实场景，保住样本）；`rtt_us<=0` 直接判失败（首字节时刻 == 发起时刻，时钟不可信，弃样本）。

### 4.3 专深②：短板法分级算法
```cpp
// weak_level.cpp:34-48
if (bandwidth_mbps >= t.good_bandwidth_mbps && rtt_ms <= t.good_rtt_ms) return kGood;
if (bandwidth_mbps >= t.fair_bandwidth_mbps && rtt_ms <= t.fair_rtt_ms) return kFair;
if (bandwidth_mbps >= t.poor_bandwidth_mbps && rtt_ms <= t.poor_rtt_ms) return kPoor;
return kWeak;
```
**为什么这么写（原理）**：
- **「或」语义怎么变成「AND」**：spec 表格写「良好：带宽 ≥2 或延迟 ≤200」这类「或」口径，实现却是「带宽下限 **AND** 延迟上限」双达标——因为表格的「或」是**描述每一级的现象**，而判级要回答「**两个维度各自最好能支撑哪一级**，取交集」。短板效应：3Mbps + 800ms → 带宽达良好、延迟只达较差 → **较差**（weak_level.h:17 验证用例）。串行 if 从高到低，第一个双达标即返回——O(1) 且天然短路。
- **开闭边界是刻意设计**：poor 级闭边界（`≥0.16` 且 `≤1000` 都算 poor），weak 级开边界（`<0.16` 或 `>1000`）。所以 **0.16Mbps + 1000ms 恰好是 poor**（双闭边界压线通过），0.15 或 1001 才掉 weak——边界矩阵 12 组单测锁死（weak_level_test.cpp:21-70）。改阈值时千万别顺手把 `>=`/`<=` 改成 `>`/`<`，会移动压线样本的归属。
- **断网态从检测通道借**（50-63）：测速通道只能看到「连不上」（表现为失败），分不清「网线没插」还是「后台挂了」；detection 的 fail-fast 首败结果带层级——**连通/服务层失败 = 断网**（真网络问题，触发推送降级），**物理/本地层失败 = 设备侧配置问题**（运维上门换线/改配置，降推送没用）→ kUnknown 交还测速通道。双通道各答各的，不重复判定。

### 4.4 专深③：降级语义与样本状态机
```cpp
// speed_tester.cpp:130（降级不缓存）     weak_level.h:130-133（降级样本）
// 1. full 模式先试（FR-2.4：不缓存降级状态，文件就绪即自动恢复）
if (TryFullDownload(...)) { ... }
WeakLevel RecordDegradedSample() {
  consecutive_failures_.store(0);              // 仅清零失败计数
  return static_cast<WeakLevel>(current_level_.load());  // 等级维持，不参与短板判定
}
```
**为什么这么写（原理）**：
- **为什么不缓存降级状态**：若记「上次降级了，这次直接降级」，服务端文件就绪后设备**永远不会自动恢复 full**（没人通知它）。每次先试 full 的代价是：未就绪期间每次测速都付一次失败尝试（404 快速失败时几秒；网络差时最坏吃满 15s 超时）——**用每次的小代价换自动恢复能力**，且测速本身是 30min 低频动作，可接受。
- **为什么降级样本等级维持而不是重判**：降级只有 RTT 没有带宽，短板法需要**双维度**——若拿 -1 带宽去判，必然掉 weak（带宽 <0.16），等于「测速源故障」被记成「网络变差」，触发错误的推送降级。所以降级样本只当**链路活性证据**（清失败计数——能连上说明没断），等级等下一次 full 样本刷新。首样本即降级 → kUnknown（没基线可维持，宁可不判）。
- **失败计数的「连续」语义**（weak_level.cpp:72-79）：`fetch_add` 原子自增，达阈值（默认 2）直接判 weak；未达阈值**维持上次等级**——避免一次抖动就把好等级抹掉。网络切换只重置计数不重置等级（81-83）：spec 字面语义是「新环境重新数失败」，等级靠切换后 10s 内的快速测速刷新（FR-2.3）。

### 4.5 性能与复杂度
- full：最坏 15s（建连 5s + 窗口 4s + 余量），正常 4s 窗口封顶 + TTFB；流量 ≈ 窗口内下载字节（弱网几十 KB、强网几 MB）。
- 降级：5s 封顶，一个包（首字节即断）。
- 分级：O(1) 三级 if；状态机全原子操作，无锁。

## 5. 边界、异常与测试  [5min · 别一笔带过]

### 5.1 异常与降级
- host 未配置：URL 为空 → 跳过 full 直接降级（154-156）；降级也依赖 host，host 空则降级也失败 → 全失败记账。
- 0 字节响应（降级探测）：WriteCallback 不触发 → 整体请求耗时兜底（RTT 高估，可用）。
- 窗口未满但文件下完（高带宽）：HTTP 2xx + 有字节 → 有效样本（229-230）。
- 首字节时刻 == 发起时刻（rtt_us≤0）：弃样本判失败（245）。

### 5.2 边界条件
| 场景 | 行为 |
|---|---|
| 带宽 2.0Mbps + 200ms | 恰好 good（双闭边界压线） |
| 带宽 0.15Mbps / 延迟 1001ms | weak（开边界） |
| 3Mbps + 800ms | poor（短板法：延迟拖累） |
| 首样本即降级 | kUnknown，不判定 |
| 降级期间等级 | 维持上次 full 等级 |
| 传输 <100ms | `high_bw_estimate=true`，带宽仅供参考（251） |
| 服务端返回 Base64 JSON（忘带 Accept 头） | 不会发生——Header 硬编码带上（205）；接手别删 |
| 弱网下 4s 只传了 20KB | 有效（窗口满中断），bw≈40kbps → weak |

## 6. 踩坑与接手注意事项（含审阅发现）  [审阅 + 雷区]

### 6.1 开发中坑
- **kbps→Mbps 换算只有一个点**：`RecordSample(bw / 1000.0, rtt)`（speed_tester.cpp:148）。报告里是 kbps、分级器吃 Mbps——**动任何一个单位都要回头查这行**，差 1000 倍的 bug 单测能抓住（边界矩阵），联调才能发现。
- **Accept 头是隐式契约**：不带 `application/octet-stream` 服务端返回 Base64 JSON——测速「成功」但带宽严重失真（Base64 膨胀 + JSON 框架字节）。服务端接口文档与这行硬编码互为契约。
- **窗口中断在 cpr 眼里是 error**：样本有效性看 `window_expired` 标志，别在 `resp.error` 上加判定逻辑——会把正常采样当失败。

### 6.2 接手者雷区地图（⚠️ 本次审阅发现的注意点）
| # | 现象 | 代码位置 | 风险 / 建议 |
|---|---|---|---|
| **S1** | **两处「网络类型」口径不同** | 本模块 `network_type` 取 `NetworkInfo::GetNetworkType()`（wifi/cellular/ethernet/other/none，speed_tester.cpp:36-50）；detection 物理层 items 的接口标注是 sysfs 视角（ethernet/wireless/usb/can，physical_layer_strategy.cpp:174-179） | 都叫「网络类型」但**数据源与枚举不同**（连接管理视角 vs 网卡视角）。Debug 页/上报同时展示两处时别混用，文档与下游解析需区分 |
| **S2** | 全失败时 `mode="degraded"` | speed_tester.cpp:174（注释「最后尝试形态」） | 语义是「最终尝试的是降级」，不是「本次运行在降级模式」——full 其实也试过。下游若按 mode 统计降级占比，**全失败样本会被计入降级**；需明确统计口径是否要排除 `success=false` |
| **S3** | 降级探测 RTT 高估的兜底分支 | speed_tester.cpp:285-294 | 0 字节响应时 RTT = 整体请求耗时（含完整响应收尾），系统性高估。阈值判定用的是 `rtt_ms <=` 上限——**高估会把等级往低拉**（偏保守），是可接受的取舍，但分析弱网误判数据时要记得这条 |
| **S4** | `classifier()` 暴露非 const 引用 | speed_tester.h:116 | 外部可直接改状态机的等级/计数。当前为 FR-3.3/FR-4 消费便利刻意开放；**别在别处顺手调用 Record* 改状态**——样本记录入口必须收敛在 SpeedTester 三态主干，否则「连续失败」语义被绕过 |
| **S5** | `GetCurrentThresholdProfile` 是编译期常量 | weak_level.cpp:10-14 | 云端下发覆盖是**预留入口**（返回引用、static 初始化）。实现下发时注意：单测断言的是默认值，`static` 缓存会吞掉运行时更新，需要改成可刷新的存储 |
| **S6** | 未就绪期间每次测速都先失败一次 | speed_tester.cpp:130（不缓存降级） | 设计取舍：自动恢复 vs 每次小代价。404 快速失败无妨；**若服务端把 /speedtest 挂在慢路径上（超时而非 404），未就绪期每 30min 白吃 15s 超时**——T0.6 上线前确认失败形态 |

**给接手者的硬提醒**：
- 🔴 改分级阈值必须**保开闭边界**（poor 闭、weak 开）并跑 12 组边界矩阵单测——压线样本归属一变，下游推送策略行为就变。
- 🔴 `RecordSample/RecordDegradedSample/RecordFailure` 只能从 `RunSync` 三态主干调用，别在新代码里直接调分类器记账。
- 🟡 RTT 与带宽的起算点不同（发起时刻 vs 首字节时刻）——调采样逻辑时两个时间轴别搞混。
- 🟡 `high_bw_estimate`（<100ms）意味着样本量太少带宽不可信，消费端（推送策略/报表）要把它当参考值过滤。
- 🟡 上游门面才是触发管理（T2.3）；本模块只收 `SpeedTestTrigger` 标注原因，别在 SpeedTester 里加定时器。
