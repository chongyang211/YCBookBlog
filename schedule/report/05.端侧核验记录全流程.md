
> 范围：`src/service/verify_record/`（VerifyRecordStore + VerifyRecordReporter）。端侧识别（local route）的核验记录留存与补报（story 136969382）。与 report/ 管道的关系：本模块是**独立的点对点补报链路**（自有 SQLCipher 台账 + 专用 HTTP 端点），不经 ReportQueue/OTLP 管道。

## 一、功能定位

云端识别的核验记录由**服务端**在识别请求链路内直接落库；**端侧识别不经服务端**——命中后必须由设备端本地留存（加密台账），择机批量补报服务端。

两个单例，职责严格分离（各自可独立单测）：

| 组件 | 职责 | 边界 |
|---|---|---|
| `VerifyRecordStore` | **只管 DB**：SQLCipher 加密台账的增删查、失败分类标记、清理 | 不碰 HTTP |
| `VerifyRecordReporter` | **只管上报编排**：定时轮/drain/降频/即时触发/每日例行 | 不碰 SQL |

## 二、数据模型（VerifyRecord，10 字段三类）

| 类别 | 字段 | 说明 |
|---|---|---|
| **上报（5）** | `device_record_id`（32hex 幂等键，服务端按 device_sn+此值唯一去重）/ `user_id` / `palm_id` / `palm_direction`（1左 2右 0未知，纯透传）/ `pass_time`（UTC 秒） | 请求体只含这 5 个 |
| **仅本地（3）** | `user_name` / `tag_names` / `physical_card_no` | ⚠️ **PII 红线：禁止进任何日志**，服务端实时查不需要端上外发 |
| **仅内部（2）** | `retry_count`（仅业务类失败计数）/ `last_try_time`（退避控制） | 重试与隔离机制 |

## 三、全流程

### 3.1 产生：端侧识别命中（palm_session_controller.cpp RecordLocalVerifyResult）

```text
LocalRecognizing 端侧命中（last_local_identify_result.code == 0）
  | kDecidePostRec 决策分支
  v
RecordLocalVerifyResult(ctx)
  - 仅端侧需要：云端路径由服务端落库，未命中/超时不产生记录
  - scene_attach 解析失败 -> 放弃留存（空记录对服务端无意义），仅告警
  - 组装 10 字段（device_record_id = GenerateRecordId()）
  v
VerifyRecordStore::InsertAsync(record, on_success)
  - 内部 ThreadPool 派发——磁盘 IO 绝不进刷掌主链路，调用方立即返回
  - INSERT OR IGNORE（device_record_id 主键，幂等）
  - 写失败不改本次刷掌业务结果，仅 LOG_E + 打点
  - on_success（线程池线程）-> VerifyRecordReporter::TriggerImmediate()   <- FR-5.2 即时上报
```

### 3.2 上报编排（三条触发路径汇入同一轮）

| 路径 | 触发 | 说明 |
|---|---|---|
| 定时轮 | 调度器任务 `verify_record_report`，基础 5min（开机首延迟 60s，尽快处理重启前积压） | 基础探测 |
| 即时轮 | 落库成功回调 `TriggerImmediate()` | 联网时秒级完成，不等定时轮；降频期间每次刷掌=一次免费网络探测 |
| 恢复加速 | MQTT 重连成功 `ConnectedSig` -> `OnNetworkRecovered()`（post 到线程池，不阻塞 MQTT 事件循环） | 复位降频阶梯 + 即时轮，积压秒级补传；降级边界：MQTT give-up（约 2h）后断网恢复无此信号，退回 drain 兜底 |

三方共用 `ReportPendingRecords(immediate)`，CAS 互斥（`reporting_`）抢不到则置 `pending_trigger_` 由进行中轮末尾补跑（有界：`kMaxPendingReruns=1`，防"断网 + 刷掌间隔 < HTTP 超时"退化为每 10s 失败请求死循环）。

### 3.3 单轮周期（ReportPendingRecords）

```text
QueryBatch(now)
  - 过滤：retry_count < 10（毒记录隔离）AND 退避未到期跳过
  - 排序 pass_time ASC（先进先出），上限 20 条/批（服务端契约）
  v
ReportOneBatch
  - BuildRequestBody：只装 5 个上报字段（PII 不出端）
  - POST /wecardpalm/device/report-palm-verify-records（DEVICE 签名，10s）
  - 成功 -> DeleteBatch（上报成功即删，表内记录天然全部"未上传"）
        -> drain-on-success：立即取下一批连续排空（上限 50 批 = 1000 条）
  - 失败 -> MarkBatchFailed 两分类：
      传输类（网络不通/超时）-> 只更新 last_try_time，不消耗 retry_count
        （门店断网数天属常态，计数会让记录不知情耗尽预算永不上报）
      业务类（服务端可达但写库失败）-> retry_count+1 + 指数退避（1min->2->4…封顶 30min）
        -> 达 10 次进隔离区，返回首次隔离数供告警
  v
ApplyAdaptiveFrequency（FR-5.1 自适应降频，仅传输类失败计数）
  连续失败轮 0~2 -> 5min；3~5 -> 10min；6~11 -> 20min；>=12 -> 30min 封顶
  任一成功立即恢复正常周期；降频只推迟"探测"，绝不推迟"排空"（drain 在轮内连续）
```

### 3.4 每日例行（RunDailyMaintenance）

- 每小时 tick 检查：「当日未执行 且 本地钟点 >= 3 点」+ MMKV 日期幂等；
- 覆盖夜间断电门店（运行期永不经过凌晨 3 点——开机后首个 tick 充当触发器）；
- 动作：清理 30 天前从未成功上报的记录（FR-6）+ 隔离区复位重探（FR-4.2，retry 清零给毒记录第二次机会）。

## 四、可靠性设计汇总

| 机制 | 针对的场景 |
|---|---|
| InsertAsync 线程池派发 | 磁盘 IO 不阻塞刷掌 |
| SQLCipher + 损坏降级重建（`.corrupt.<ts>` 取证） | db 文件损坏不阻断刷掌（"台账不可用远好于刷不了掌"） |
| 失败两分类 | 断网数天不丢上报预算 |
| drain-on-success + 50 批上限 | 断网恢复后快速补报 vs 不长时间独占线程 |
| 传输类失败不计数 + 记录级指数退避 + 任务级降频 | 三层刹车各管一层 |
| pending_trigger 有界补跑 | 关闭 drain 结束瞬间新落库的竞态窗口 |
| PII 仅本地 + 日志红线 | 合规（user_name/tag_names/物理卡号不出端、不进日志） |
| device_record_id 幂等 + 上报成功即删 | 重试重复上报被服务端唯一索引吸收 |

## 五、观察点

1. `consecutive_fail_cycles_` 为内存态不持久化——重启后降频阶梯归零，首轮探测代价仅一次失败请求（注释已声明，属有意取舍）；
2. 单连接 + mutex 全串行的 DB 线程模型，前提是"业务量极小"——若未来记录量级增长（如高频场馆），需重估；
3. MQTT give-up 后的恢复盲区（断网 >=2h 且链路态无跳变）依赖 drain 兜底——定时轮本身也是出站请求，数据不丢但补报延迟最多 30min（降频封顶时）。
