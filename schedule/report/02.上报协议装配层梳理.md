
> 范围：`src/service/report/abs/` 三个 Builder 基类。它们负责把 ReportQueue 里的 JSON 逐条装配成 OTLP 标准结构，是《report-全流程说明.md》中"Builder 装配"环节的实现层。

## 一、类关系总览

```text
BaseOpenTelemetryBuilder（抽象基座，不可直接用）
├── BaseLogsBuilder          -> Logs 协议（16160 / 25261 两通道共用）
|   └── PalmAppReportLogsBuilder（25261 专属覆写）
└── BaseMetricsBuilder       -> Metrics 协议（99001）
（BaseTraceBuilder：注释中预留，未实现）
```

## 二、BaseOpenTelemetryBuilder——协议基座

**作用**：提供全部 OTLP 装配的公共工具，定义"一条 JSON 如何变成属性数组"。

| 能力 | 说明 |
|---|---|
| `setScopeName` / `getScopeName` | 作用域名（**服务端路由键**），默认 `"16160"`；25261 通道由 `ReportService::ReportLogs` 显式 set |
| `CreateKeyValue<T>` | 模板化键值对：string/bool 装原值，**所有整数/浮点统一转 double**（OTLP AnyValue 约束） |
| `BuildResource()`（virtual） | 默认 Resource 4 属性：`os.type="Linux"` / `os.version`(ROM 版) / `app.version` / `device.sn` |
| `BuildAttributes(json)` | **JSON -> attributes 的通用翻译器**：逐键遍历，string/bool/int/float 装原值，null 跳过，复杂类型 dump 成字符串；单键转换失败跳过不中断 |
| `CreateScope(name, version)` | 仪表化作用域（version 默认 "1.0.0"） |
| `GetCurrentTimeMillis` 等 | 时间戳 / JSON 安全读取小工具 |

## 三、BaseLogsBuilder——Logs 协议（16160 / 25261）

**作用**：把队列里的每条 JSON 装配成 OTLP `ExportLogsServiceReq`。

### 数据结构层次（一条 rpt = 一个完整 ResourceLogs）

```text
ExportLogsServiceReq
└── ResourceLogs[]                    <- 每条 rpt 一个
    ├── Resource.attributes[]         <- BuildResource()（子类可覆写，见 PalmApp 6 项）
    └── ScopeLogs
        ├── Scope.name                <- getScopeName()（"16160"/"25261"，服务端按此路由）
        └── LogRecord
            ├── time_unix_nano        <- 装配时刻 now（注意：非 happen_time！）
            ├── severityNumber/Text   <- 恒 INFO
            └── attributes[]          <- JSON 全键翻译（BuildAttributes）+ action 键值（可选）
```

### 关键机制

- `setAction(key, value)`：为无 action 字段的 JSON 追加路由属性（如通用心跳）；
- `BuildLogRecord` 为 virtual：**PalmAppReportLogsBuilder 覆写它**实现 25261 的三个特殊变换——`happen_time` 覆写 timeUnixNano（消除断网补发的时间偏移）、`client_trace_id` -> traceId、`traceparent` span 段 -> spanId；
- 单条装配失败仅 LOG_E 跳过该条，不影响批次；
- 字段数据：attributes = 队列 JSON 的全部键值（各协议 Item 字段直传），无裁剪。

## 四、BaseMetricsBuilder——Metrics 协议（99001）

**作用**：把队列 JSON 装配成 OTLP `ExportMetricsServiceReq`。当前实现专化为"心跳计数"形态。

### 数据结构层次

```text
ExportMetricsServiceReq
└── ResourceMetrics[]                 <- 每条 rpt 一个
    ├── Resource.attributes[]         <- 基座默认 4 项（device.sn 等）
    └── ScopeMetrics
        ├── Scope.name                <- getScopeName()
        └── Metric[]
            ├── name                  <- setAction 的值，否则取 JSON 的 "action" 键
            └── sum（Sum 类型，DELTA，monotonic）
                └── NumberDataPoint
                    ├── start/end_time_unix_nano <- 装配时刻 now
                    ├── value = "1"              <- 恒 1（事件计数语义）
                    └── attributes[]             <- JSON 全键翻译
```

### 关键机制

- `setAction` 语义与 Logs 不同——这里用作 **metric.name**（指标名）；
- 内置 `CreateSumMetric / CreateGaugeMetric` 工具，头注释列出五种指标类型（Gauge/Sum/Histogram/ExponentialHistogram/Summary）与 DELTA/CUMULATIVE 聚合语义，**当前只用 Sum**，Histogram 等预留；
- 与 Logs 的本质差异：Metrics 是"一条 JSON = 一个值为 1 的计数数据点 + 全字段进 data_point.attributes"，数值本身不进 value。

## 五、三通道落地对照

| | Logs(16160) | Logs(25261) | Metrics(99001) |
|---|---|---|---|
| Builder | BaseLogsBuilder（直接实例化，scope 手动 set） | PalmAppReportLogsBuilder（覆写 BuildResource/BuildLogRecord） | BaseMetricsBuilder |
| 典型数据 | OTA/通用埋点（ext_key×3 简化模型） | 通用 action + 刷掌会话事件族（23 字段严格协议） | 心跳/资源/识别指标 |
| 特殊装配 | 无（JSON 直通 attributes） | happen_time -> 时间戳、trace 链、6 项 Resource | action -> metric.name、value=1 |
| 端点/批次 | /iot/report/logs，<=200 条/批 | 同左 | /iot/report/metrics，逐条发 |
| 失败语义 | RestoreTaken 重试 | 同左 | 网络失败丢弃（时效性） |

## 六、观察与可选优化项

1. **BaseLogsBuilder 的时间戳口径**：`time_unix_nano` 取装配时刻（出队时），断网积压补发后事件时间会偏移——25261 已用 `happen_time` 覆写解决；16160 通道没有这层处理，对时间敏感的埋点（如 OTA 进度）靠 JSON 内字段兜底，后台检索需注意区分时间键；
2. **BaseMetricsBuilder 目前是"心跳专用"形状**（value 恒 "1"、Sum/DELTA、`BuildScopeMetrics` 硬编码 `BuildHeartBeatMetric`）：后续资源指标若要上 Gauge/Histogram，建议按指标类型拆分构建方法，避免该类职责继续膨胀。
