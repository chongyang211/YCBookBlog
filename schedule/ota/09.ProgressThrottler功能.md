
## 文件作用

`DownloadProgressThrottler` 是 OTA 下载链路上的 **“进度采样器 + 心跳节流器”**，夹在 curl 与上层上报之间：

```
libcurl progress 回调(~每秒,原始字节计数,频率高)
        │ OnBytes(dl_total, dl_now)
        ▼
DownloadProgressThrottler
  ① 滑动窗口采样(供速率计算 + 弱网判定)
  ② 时间节流(至多每 interval 一次外发)
        │ 心跳(累计进度, 尾窗速率)
        ▼
upgrade_schd 的 progress_cb → 组装 16160 埋点
```

解决的问题：curl 回调频率太高，不能每次都发埋点；而“进度百分比、实时网速”又需要历史样本才能算——这个类把“高频采样、低频上报、窗口测速”三件事合在一个 30 行的无锁类里(单线程使用，无需锁)。

## 核心函数 `OnBytes` 的思路(:40-70)

目的：让平台能持续看到“下载到哪了、网速多快”——为平台的进度展示和弱网归因提供数据，同时绝不能因为观测本身影响下载主链路。

核心设计思想：每一次字节到来都默默记账，攒够 60 秒发一次摘要，摘要里的速度用账本首尾差值算，全程不挡下载的路。

四步，每步一个关注点：

**① 归一化(:42-44)**——把 curl 的“本次传输字节”换算成“整个文件的绝对字节”：

```cpp
downloaded = base_offset_ + dl_now;   // base_offset = 断点续传起点，dl_now 是本次传输字节
total     = base_offset_ + dl_total;  // Range 下载时 dl_total 是剩余量
```

这就是为什么续传场景平台看到的百分比是连续的(如 33% → 36%),而不是从 0% 重新爬。

**② 滑动窗口采样(:46-49)**——`(时间, 累计字节)` 压入 deque,同时淘汰超出 interval 的旧样本。窗口里始终保留“最近一个 interval 内的轨迹”，这是速率计算和 `LastWindowSpeedBps()` 的数据基础。

**③ 时间节流(:51-52)**——`距上次外发 < interval` 直接返回。注意“节流不采样”：样本照收，只是不外发。`last_report_` 在构造时初始化为当前时刻，所以**第一次心跳恰好在启动后 interval 时刻**。

**④ 计算速率并外发(:54-68)**——速率 = **窗口首尾两个样本的差值/时间差**(首尾差分，不是逐样本求和平均——O(1) 计算，天然抵抗毛刺)：

```cpp
speed = (back.bytes - front.bytes) / (back.time - front.time)
```

两道防御：样本 <2 个不算(返回 0);`back.bytes < front.bytes`(服务端重置导致的字节回退)按 0 处理，防负速率。最后 try/catch 包住外发——**回调异常绝不能炸掉下载线程**，这是“观测组件不干扰主链路”的契约(返回值恒 `true` 也是为了不让 curl 中止传输)。

## 三个 getter 的用途(:72-93)

不是给心跳用的，是给**弱网判定**用的——`IsWeakNetworkStall`(download_service.cpp)在下载失败时读这三个值做 30520 归因：

| getter | 判定用途 |
|---|---|
| `DownloadedBytes()` | =0 → 数据流从未建立，是“连接超时”而非“弱网”，排除出 30520 |
| `HasSpeedSample()` / `LastWindowSpeedBps()` | 有样本且尾窗速率 <1KB/s → 弱网低速熔断(首选判定)；没样本才落 libcurl 文案兜底 |

## 一个值得知道的设计细节

`now_fn` 可注入(默认 `steady_clock::now`)——就绪为单测设计：测试可以注入假时钟，精确构造“30 秒内 900 字节”这类弱网场景，不用真等时间流逝。`base_offset` 与 `interval` 同理，都是为了让这个类在真实下载之外可以被确定性验证。
