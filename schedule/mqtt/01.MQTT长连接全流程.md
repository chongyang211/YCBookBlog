
> 范围：`src/service/mqtt/`（MqttService 门面 / MqttClient 抽象基类 / DeviceMqttClient 设备实现 / interface::PaasMqtt 全局信号门面 / linkcomm.proto 线上格式）。MQTT 长连接是设备与 IoT 后台之间的实时通道。

## 一、功能定位

| 职责 | 说明 |
|---|---|
| **下行即时推送** | 云端任务秒达：OTA 任务秒推（type 1）、IoT 指令（type 2）、影子 cloud-side 属性（type 6）等，免等轮询周期 |
| **上行请求-响应** | `Request(message_type, body, timeout)` 按 message_id 匹配响应的同步调用 |
| **在线状态与断线语义** | 连接/断开/失败信号是影子、核验记录等模块"网络恢复加速"的信号源 |

## 二、组件分层

```text
MqttService（门面单例）
|   持有 mqtt_thread_（专线程）+ DeviceMqttClient；信号桥接到 PaasMqtt
|   Start 前 RegisterDownMessageHandler 会缓冲，Start 时统一灌入
├── MqttClient（抽象基类，PIMPL 隔离 async_mqtt）
|   ├── 纯虚注入点：GetDeviceSn() / SignSeCommonAuth()（设备特异性与 SE 签名）
|   ├── 信号：ConnectedSig(耗时ms) / ConnectFailedSig / DisconnectedSig(含断开原因)
|   └── Request / RegisterDownMessageHandler / Reconnect / SetDeviceDomainHost
└── DeviceMqttClient（具体实现）
    ├── GetDeviceSn -> Device::GetSn()
    └── SignSeCommonAuth -> SeKeyStore::SignCommonAuth（SE 芯片 SM2 签名，防重放计数）
interface::PaasMqtt（全局信号门面）
    ConnectedSig / ConnectFailedSig / DisconnectedSig
    —— 供拿不到 MqttClient 引用的模块订阅（NetworkMonitorService / Shadow / verify_record）
linkcomm.proto —— MqttDownMessage{header{message_type, message_id, encoding}, body} 线上格式
```

设计要点：业务模块经 `MqttService::RegisterDownMessageHandler` 注册自己的下行类型，**无需持有 MqttClient 引用**——避免网络层到单个业务模块的反向依赖；`interface::PaasMqtt` 同理解决信号订阅的可达性问题。

## 三、连接建立（mqtt_client.cpp）

| 项 | 值/机制 |
|---|---|
| broker | `link-{激活域名}:443`（SetDeviceDomainHost 加 `link-` 前缀；域名来自激活流程） |
| 协议/传输 | MQTT 3.1.1 + TLS（握手超时 10s，连接超时 10s），clean session |
| 认证 | username = `IOTDEVICE-SHA256-SM2|{sn}|{ts}|{nonce16}`；password = Base64(protobuf PaasSignPackage)，签名字节由 **SE 芯片**对 `magic/se_sn/version/timestamp/counter/random + username` 做 SM2 签名（防重放计数）——密钥不出 SE |
| keepalive | 60s；PINGRESP 接收超时 90s（1.5 倍）主动断链；**KeepAliveWatchdog**：90s 无任何包强关连接——避免 TCP 半开假在线（否则要等约 16min 重传超时） |
| 订阅 | `down/{sn}`（QoS1，实时推送）+ `resp/{sn}`（QoS1，同步请求响应） |
| 重连后 | `SyncUnAck()`：向 `req` topic 发 `MESSAGE_TYPE_UP_SYNC_UN_ACK_MESSAGE`，**拉取未 ack 的下行消息**——broker 侧补发，弥补离线窗口 |

## 四、下行分发

```text
down/{sn} 收到 publish
  -> 解析 MqttDownMessage protobuf（失败丢弃）
  -> encoding == ZSTD -> 解压 body
  -> 去重窗口（kDedupWindowSize=1000，QoS1 重复投递防御）
  -> DispatchDownMessage(message_type, message_id, body) -> 注册的模块 handler
  -> resp/{sn} 另按 message_id 匹配 pending Request 完成同步调用
```

已注册的下行 handler：

| type | 消费方 | 用途 |
|---|---|---|
| 1 `MESSAGE_TYPE_DOWN_OTA` | upgrade_schd.cpp | OTA 任务秒推（免等轮询） |
| 2 `DOWN_INSTRUCTION` | iot_service.cpp | IoT 远程指令 |
| 6 `MESSAGE_TYPE_DOWN_CLOUD_SIDE_PROPERTY` | paas_shadow_impl.cpp | 影子属性推送（见《docs/shadow/02.cloud-side-下行同步.md》下行通道二） |

handler 注册**独立于连接状态**，且 Start 前注册会被缓冲——解决"业务先于服务起"的时序问题。

## 五、断线与重连（mqtt_client.cpp:230-267）

```text
连接成功 -> ConnectedSig(elapsed_ms) -> SyncUnAck() + KeepAliveWatchdog 启动
连接失败 -> 退避重试（kReconnectIntervalsMs 阶梯）
  - 连续失败达 10 次（约 30s）-> ConnectFailedSig（一次）
  - 累计 120 次 -> give up：发 ConnectFailedSig("reconnect give up")
      -> co_await WaitForReconnect() 休眠，等外部 Reconnect() 唤醒后重置计数
  - 任何成功 -> retry 重置
```

外部唤醒路径：`MqttService::Reconnect()` <- **NetworkMonitorService**（链路变化探测后调用，见《docs/network/01.网络监视服务全流程.md》第五节）-> `mqtt_client_->Reconnect()`。

⚠️ **口径勘误**：mqtt_client.cpp:44 标注 give-up 为 `~1h`，但 shadow/verify_record 源码注释多处写"120 次约 2h"——两处注释不一致，实际时长取决于退避阶梯总和，排查以 mqtt_client.cpp 为准（建议统一注释）。

## 六、信号消费图（ConnectedSig 的下游）

```text
ConnectedSig
  |- PaasShadowImpl：mqtt_connected_=true -> 轮询 60s->300s；重连置 cloud_pull_requested_
  |- VerifyRecordReporter：OnNetworkRecovered -> 复位降频 + 即时补报轮
  |- （未来模块）订阅 interface::PaasMqtt::Global() 即可，无需触碰 client
ConnectFailedSig("reconnect give up")：网络长期不可用的明确信号（可对接告警）
DisconnectedSig：携带真实断开原因（paused / keepalive 超时 / 协议错误等）
```

## 七、观察点

1. **give-up 时长注释不一致**（约 1h vs 约 2h，见第五节）——多处注释需统一；
2. `MqttClient::Request` 的同步请求-响应未检索到明确调用方（`req` topic 上行存在）——若确无使用属预留能力；
3. MQTT 层 QoS1 + SyncUnAck 补发不保证业务不重复（1000 窗口仅去重窄时段重投）——各消费方自备幂等（OTA 靠任务 uid 去重与 Busy 锁、影子靠版本判重）；
4. 心跳 Metrics 注释代码中 `scope="mmiot"`（字符串）与 99001 数字 scope 是两套用法——接入 Report 时二选一；
5. `MqttService` 析构顺序（先 client Stop 再删线程）有注释强调防悬垂——修改生命周期时保持该顺序。
