> 范围：`src/service/license/` + yt-mobile-auth 静态库（story 136057693）。

## 一、定位：刷掌业务的商用授权门闸

License 回答一个问题：**这台设备是否有权运行刷掌业务**。核心判据 `CanStartPalm()` 仅在 `AuthState::kAuthorized` 时放行——它是刷掌启动的硬门闸（pos_request_handler 前置校验 + StartPalm 判据均消费）。

属性三元组之外，license 用两个维度描述自身：**AuthState（7 值授权状态）** 与 **LicenseSummary（appid + expire_time，wire 仅传这两个字段）**。

## 二、组件分工

| 组件 | 职责 | 边界 |
|---|---|---|
| `LicenseManager`（单例） | AuthState 状态机、复检收敛、扫码授权编排、DeviceFsm 联动、Shadow 上报、0xB0/0xB2 广播 | 不做解密（委托 Decoder）、不做 HTTP（委托 yt 库经 Proxy） |
| `QrLicenseDecoder` | 授权码解码：Base64 -> MiniDecryptor 解密 ZIP -> qr.json -> 时间戳校验 | 三种 code_type（gen_lic/feed_lic/get_device_info） |
| `LicenseNetworkProxy` | yt-mobile-auth 的 INetworkProxy 实现：桥接 cpr/curl | 同步阻塞（授权库 worker 线程调用） |
| `LicenseStorage` | license 文件读写 `/data/persist/cloud_p.lic`，原子写 | 不加密（验签在授权库内） |
| yt-mobile-auth 静态库 | 验签/校验核心；SN 库内自读 `/proc/device-tree/serial-number` | 经 C API（yt_auth_*）交互 |

## 三、双状态机模型：AuthState × DeviceFsm

License 模块的核心复杂度在于**两台状态机的联动**：

```text
AuthState（7 值，LicenseManager 持有，原子）
  kUnknown / kChecking / kUnauthorized / kAuthorizing / kAuthorized / kExpired / kError
        │ ResolveLicenseDeviceState()
        ▼
DeviceFsm license 设备态（DeviceStateMachine 仲裁）
  kLicenseChecking / kLicenseUnauthorized / kLicenseRefreshing / kLicenseAuthorizing
        │ OnEnter / OnExit 钩子回调 LicenseManager
        ▼
  扫码启停（StartCodeScan(kScanLicense)）+ 失败重仲裁（OnEnter 复核不一致返回 false）
```

映射规则：kAuthorized -> nullopt（无 license 态，调用方落到激活检查）；kChecking/kUnknown -> kLicenseChecking；kAuthorizing -> kLicenseAuthorizing（保护态）；kUnauthorized/kExpired/kError -> kLicenseUnauthorized。

联动铁律：

1. **AuthState 的唯一所有者是 LicenseManager**——目标设备态由它解析（`ResolveLicenseDeviceState`），调用方不自行判断；
2. **所有状态变化事件经 `RefreshAuthState(reason)` 统一收敛**（禁止直调 CheckAuthLocal），见 02 篇；
3. **OnEnter/OnExit 钩子只由设备态结构体调用**——模块不对外暴露命令式启停扫码接口。

## 四、线程模型

| 线程 | 职责 |
|---|---|
| MainThread | 扫码分发入口（TryHandleScanCode 轻量预检）、0xB0/0xB2 信号发射、授权扫码启停 |
| **LicenseThread** | DoAuthorize 全流程（与激活流程**同线程串行，天然互斥**）、RefreshAuthState/CheckAuthLocal、时间可信回调处理 |
| ThreadPool | Store/Decoder 重活、InsertAsync 类异步派发 |
| NTP 线程 | 时间可信事件源（回调内 Post 回 LicenseThread） |

网络代理（LicenseNetworkProxy::PostJson）是授权库内部 worker 线程的**同步阻塞调用**，超时 10s 建连 + 60s 整包——会同步拉长 kLicenseAuthorizing 保护态停留。

## 五、生命周期与启动时序

```text
BootStrapper（激活后段；license 依赖激活产出的域名/SN 环境）
  └─ LicenseManager::Init()（LicenseThread 语义，manager.cpp:156-226）
       1. 注入网络代理（yt_auth_set_network_proxy）
       2. license 文件三岔路：
          无文件 -> kUnauthorized（不等时间）
          有文件 + 时间已同步 -> LoadAndCheckLicense + PostExitToSteady
          有文件 + 时间未同步 -> kChecking（等时间可信事件）
       3. 订阅 TimeStateManager 时间可信回调 -> ForceReportShadow
          +（仅 kChecking 时）LoadAndCheckLicense + PostExitToSteady
       4. 注册 ModuleAuthProvider -> PaasShadow（须在 PaasShadow::Start 前）
```

时序保证（suppress_fsm_drive_）：Init 期间抑制 SetAuthState 的 ResolveIdleTarget 驱动（此时 DeviceStateMachine 尚未 Start）；时间可信回调即使立即触发，也会因 FIFO 排在 Init 完成之后，不会在抑制解除前执行 LoadAndCheckLicense。

## 六、关键常量速查

| 项 | 值 | 位置 |
|---|---|---|
| license 文件 | `/data/persist/cloud_p.lic`（tmp+rename 原子写） | license_storage.h |
| 网络代理超时 | 10s 建连 + 60s 整包 | license_network_proxy.h:41-42 |
| RefreshAuthState 去抖 | 100ms | LicenseManager |
| 复检周期 | 1h 常规；kChecking 期间 30s 快速轮询 | FR-7.3 / RefreshReason |
| 0xB0 / 0xB2 | 状态跃迁通道 / 授权动作结果通道（ret_code 用 409xx 段） | license_types.h |
| Shadow 属性 | `module_auth`：module_license_status（0/1/2）+ module_license_expiry_time | paas_shadow_constants.h |

## 七、观察点

1. `CanStartPalm` 硬门闸——license 失效直接停刷掌业务，kExpired 恢复依赖扫码重授权或 gen_lic 拉云端；
2. 网络代理 60s 超时拉长保护态停留——弱网下 kLicenseAuthorizing 停留最长可达分钟级；
3. kError 态（授权库/IO 错误）的自动恢复路径需确认（复检能否自愈 vs 依赖 Deinit/Init 重入）；
4. `suppress_fsm_drive_` 与时间可信回调 FIFO 的时序论证有详细注释——改动 Init 流程时需重新核对。
