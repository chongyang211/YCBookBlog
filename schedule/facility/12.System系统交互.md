# Facility · 12 System 系统交互

> 系列第十二篇。覆盖 system/ 模块：SystemInterface（Linux 原生机制直连）与 SystemServer（vendor 闭源库动态加载门面）的双路线分工。承接《01.总览与分层架构.md》。

## 一、定位

L1 基础件（依赖 device/thread），**两个类两种路线**：

| 类 | 路线 | 覆盖能力 |
|---|---|---|
| `SystemInterface`（单例） | **直接系统交互**：sysfs / netlink / ifaddrs 等原生 Linux 机制 | 音量、CPU 省电、USB 模式、分区、网络管理+事件、Reboot/FactoryReset/Upgrade、硬件信息 |
| `SystemServer`（全静态门面） | **dlopen vendor 闭源库** libsystemserver.so | system_update / system_recovery / system_reboot / config_get|set_usb_mode / audio_play 六个函数 |

消费方：device_action（Reboot）、OTA installer（UpgradeSystem）、network 层（网络信息/信号源）、biz（USB 模式切换等）。

## 二、SystemInterface：原生机制直连

**能力域**（全部 awaitable 协程 + error_code，system_interface.h:20-105）：

| 域 | 内容 |
|---|---|
| 音量 | Get/SetVolume |
| CPU 省电 | SetCpuPowerSaveMode——**sysfs 直写** /sys/devices/system/cpu/cpuN/online，保留 2 核关其余（:40-72，核数≤2 时视为已省电） |
| USB 模式 | UsbMode 位掩码（Adb/Rndis/Uvc/Ums/Cdc 及预组合），Get/Set + SwitchUsbMode（单独关某特性） |
| 分区 | GetPartitionInfo（root/oem/oem_backup/app/userdata/all） |
| 网络 | 按 wifi/ethernet/cell 查询；Scan/Connect/DisconnectWifi；三网功率 Get/Set；GetCellBsInfo 基站信息 |
| 重启/恢复 | Reboot 三模式（**Normal/Bootloader/Recovery**，:91-95）、FactoryReset、UpgradeSystem、GetHwInfo |

**网络事件信号源**（:84-88 + netlink 监听线程）：

```text
构造即 StartNetlinkMonitor（:36-38, :87-94）
  → 专属 std::thread 跑 NetlinkMonitorLoop（rtnetlink socket 监听）
  → 5 个 signals2 信号派发：NetworkConnectChanged / StrengthChanged /
    ScanWifiCompleted / WifiConnectResult / DefaultNetworkChanged
退出机制：pipe 写一字节唤醒 poll（:96-108，经典自停管道）
```

接口名→网络类型推断（:79-85）：wlan→wifi / eth|usb|rndis→ethernet / rmnet|wwan→cell——类型识别基于命名约定。

## 三、SystemServer：vendor 库的动态加载门面

**加载**（:30-63）：构造时 `dlopen("libsystemserver.so", RTLD_LAZY)` + dlsym 逐个取 6 个函数指针——**每个函数独立可空容错**（取不到仅 LOG_E，调用时返回 -1）。句柄进程生命周期持有，不 dlclose（单例，可接受）。

**调用模式**（以 UpgradeSystem 为例，:66-89）：async_initiate → 投 **Threads::Pool() 通用线程池**执行阻塞 vendor 调用 → 完成后 post 回调用方 executor——与 SeKeyStore/Link 同款协程模式（《09》《10》篇）。

**语义要点**：

| 方法 | vendor 函数 | 语义 |
|---|---|---|
| UpgradeSystem(img, ver, mac) | system_update | OTA 镜像安装（OTA installer 消费） |
| RebootSync / Reboot | system_reboot | 重启 |
| FactoryResetSync | system_recovery(**2**) | 2 = RECOVERY_DATA_APP：清用户数据+应用数据（O4 文档，:204 注释）——**机型相关语义硬编码** |
| SetUsbMode(mode) | config_set_usb_mode(mode, **0**) | 0=立即生效（1=重启后生效，:143） |
| PlayAudio(path, vol) | audio_play | 本地音频播放 |

## 四、分工判断与观察点

**为什么有两个类**：SystemInterface 走标准 Linux 接口（可移植、可测试）；SystemServer 走 vendor 闭源库（能力 vendor 才有：安全升级/恢复出厂/音频）。升级/重启/USB 在**两个类都有接口**（签名不同：error_code vs int）——调用方按语义选（SystemInterface 版带模式参数，SystemServer 版是 vendor 封装）。

**观察点**：

1. **SystemServer::Reboot() 是伪协程**（:179-181）：直接调 RebootSync() 在**调用方线程阻塞**执行——与同文件其他方法的"投通用线程池"模式不一致（DoRebootAsync 模板定义了却未使用，死代码）。对 reboot 语义影响小（调用后系统重启进程即死），但风格不一致易误导；
2. **vendor 库缺失静默降级**：6 个函数任一缺失 → 该能力返回 -1，不 crash——但调用方（device_action/OTA）拿到的 -1 无法区分"库缺失"与"执行失败"，排障时先看启动日志有无 "Failed to load/dlsym"；
3. **netlink 监听线程是又一执行载体**：裸 std::thread + pipe 自停（《03.线程模型与调度.md》线程全景"自持"类实例——se、p2p_link、netlink monitor）；
4. **构造即起线程**：SystemInterface 首次 Instance() 就创建监听线程——函数内 static 保证运行期首次调用，无静态初始化顺序问题；但勿在静态初始化上下文触碰 Instance()；
5. FactoryReset(2) 与 SetUsbMode(…,0) 的魔法数有注释锚定机型文档——换机型时这两处是必查点（与 activation 的 device_model="O4" 硬编码同性质，《docs/activation/05.五步激活协议与联动.md》观察点 2）。
