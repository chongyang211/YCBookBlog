# Facility · 05 故障恢复与韧性

> 系列第五篇。覆盖"预防→兜底→限频重启→通知上位机→进程外守护"五层韧性漏斗、Recover 完整决策链、DeviceFsm 联动与恢复埋点语义。承接《01.总览与分层架构.md》。

## 一、五层韧性漏斗

```text
L1 预防   hook/：pthread_create 符号挂钩（dlsym RTLD_NEXT），纠正父进程
          （restarter/guard）继承来的实时调度策略/优先级，子线程回落 SCHED_OTHER
          （pthread.cpp:55，HOOK 宏开关 :13-19）
L2 兜底   crash/：std::set_terminate handler——未捕获异常时用**预分配 512 缓冲**
          写 fatal 日志再 abort（exception_track.cpp:11-34，crash 中禁止再分配）
L3 限频重启 recover/：错误提交 → 限频/仲裁判定 → kRecovering 状态权 → 执行恢复
          （完整决策链见第二节）
L4 优雅退出 device_action/：重启/恢复出厂/应用重启**先经 PosLink 通知上位机
          （注入式 NotifySender，device_action.h:33），延迟 5s 再执行**（NotifyAndDelay :57）
L5 进程外守护 restarter → guard.sh 双层守护（app.cpp:119-127 "double-layer
          recovery pipeline" 注释）；崩溃分类契约与 restarter 分类规则见《02.启动与退出编排.md》第四节
```

## 二、Recover 处理流程（recover.cpp）

**提交与执行解耦**（SubmitDeviceError/AppError，:33-49）：入口先发提交埋点，随后 `HeartBeatThread()->CoSpawn` 异步处理——**提交者不阻塞、不感知恢复结果**（fire-and-forget，返回值仅记日志）。

### 2.1 HandleDeviceError 决策链（:86-115）

```text
1. 限频检查：Config 读重启时间点 → 60min 窗口计数 ≥1？
   是 → 上报 state=exceed（超限被拒）→ co_return false（不重启）
2. 仲裁：reboot_delay_timer_ 已设置 → 拒绝（防并发重复重启）；
   并 app_restart_delay_timer_.reset() —— 设备级优先，取消 pending 的 app 重启
3. uptime 门槛：GetAppUptime() < 2min → 设延迟定时器补足差值再重启
   （避开启动期误判——业务尚未跑起来就重启无意义且无法归因）
4. SaveDevRebootTimes（Config 记录本次，供下次限频统计）
5. PerformDeviceReboot
```

### 2.2 HandleAppError 决策链（:117-137）

```text
1. 仲裁：reboot_delay_timer_ 或 app_restart_delay_timer_ 任一已设置 → 拒绝
2. uptime 门槛：同样 < 2min → 延迟补足（与设备重启共用同一门槛）
3. PerformAppRestart
```

**三个注意点**：
- app 重启**没有时间窗限频**（常量仅设备重启有）——并发互斥靠 delay timer，持续压制靠 L5 外部守护；
- **设备级优先**：HandleDeviceError 会 reset 掉 pending 的 app 重启定时器（:99）——同一时刻只允许一个恢复动作在途，且重的优先；
- Perform 顺序不对称：AppRestart **先上报 handle 埋点再重启**（重启后不可达，PerformAppRestart 不会返回）；DeviceReboot **先调 RebootDevice 再补上报**（调用返回后进程仍在，来得及上报）。

## 三、DeviceFsm 联动（v6.4 spec §3.6，:141-152）

`PrepareRecoverAction` 是所有恢复动作的前置门：

```text
DeviceStateMachine::RequestEnter(kRecovering, kFromExternalRequest)
  被拒（非 Accepted/AlreadyIn）→ 放弃恢复（设备此刻有更高优先级业务在跑）
  → WaitAppSessionIdle(1, 3s) 等刷掌会话空闲（超时也继续，仅 LOG_E）
```

即：恢复不是无条件执行——**刷掌/激活/OTA 等业务在跑时，Recover 会被 DeviceFsm 仲裁拦下**。这层仲裁与 L4 的"通知上位机 + 5s 延迟"共同保证恢复动作不打断用户。

## 四、恢复埋点语义（iwiki 约定，:169-224）

| action | 时机 | 关键字段 |
|---|---|---|
| kRecoverDeviceSubmit | 设备错误提交时 | `report_module_key`=from 来源；`state`=normal；**exceed=超限被拒**（复用同 action 区分） |
| kRecoverAppSubmit | app 错误提交时 | 同上（无 state 字段） |
| kRecoverDeviceHandle | 重启执行时 | `ext_number_key`=自愈手段（reboot），`ext_number_value_1`=执行结果 |
| kRecoverAppHandle | app 重启执行时 | `ext_number_key`=restart，同上 |

平台侧据此可回答：谁报的错（module_key）、错是什么（result_code/msg）、恢复了吗（handle + 结果）、被限频拦了吗（state=exceed）。

## 五、限频参数（recover.cpp:51-57）

| 常量 | 值 | 含义 |
|---|---|---|
| kRecoverDevErrTimeMaxSaveCnt | 10 | Config 保存最近 10 次设备重启时间点 |
| kRecoverDevRebootCheckDur | 60min | 限频统计窗口 |
| kRecoverDevRebootMacCntInDur | 1 | 窗口内**最多 1 次**设备重启（防重启风暴） |
| kRecoverDevRebootAppUptimeThr | 2min | **uptime 门槛，设备重启与 app 重启共用**（>1min IoT 初查周期，避开启动期误判） |

窗口统计用**墙钟**（system_clock，:59-74）——时间未同步期的失真见《04.NTP时间体系.md》观察点。

## 六、调用方与错误来源

- `SubmitDeviceError / AppError`（recover.h:13-14）：biz/service 的异常统一入口；
- 已知调用方：service/guard/guard_schd.cpp:17（守护调度）、bootstrap/platform_bridge_impl.cpp:17（平台桥错误）；
- 恢复出口：DeviceAction::RebootDevice / RestartApp（reason 前缀 `recover:{from}` 便于日志归因）→ L4 通知上位机 → SystemServer / `_RestartNow`。

## 七、接入检查清单

**新错误需要触发恢复**：
1. 走 `Recover::SubmitDeviceError/AppError`，禁止模块内直接调 SystemServer::Reboot（绕过限频、DeviceFsm 仲裁与上位机通知）；
2. 区分恢复动作等级：app 重启（轻）优先于设备重启（重），仅底层不可恢复故障用设备重启；
3. 错误须先经 report 通道留痕再恢复——"无痕重启"无法事后归因；
4. `from` 参数填稳定模块标识（进 report_module_key 与日志 reason），不要用临时字符串。

**新增崩溃/异常路径**：
1. C++ 异常自动进 terminate handler（L2）；信号崩溃依赖 L5 外部守护 + 重启后 RecoveryReporter 补报（联动见《02.启动与退出编排.md》第二/四节）；
2. L2 预分配缓冲模式（crash 中禁止堆分配）是硬约束，handler 内只能用栈/静态内存。

**红线**：
- DeviceAction 的 5s 延迟是给上位机的收尾缓冲，不得压缩或跳过通知直接重启；
- 限频参数调整需同时评估重启风暴（调松）与故障设备滞留（调紧）两个方向；
- 不要绕过 PrepareRecoverAction 单独调 PerformXXX——绕过即绕过 kRecovering 仲裁，可能在刷掌中撕掉会话。

## 八、观察点

1. 限频窗口依赖墙钟（第五节），时间跳变场景可能短时失真——已有 10 次记录平滑，暂无需进一步处理；
2. AppRestart 无独立时间窗限频（限频常量仅设备重启有）——app 级防护 = delay timer 互斥 + 2min uptime 门槛 + DeviceFsm 仲裁 + L5 外部守护；若出现 app 级重启风暴（各层都拦不住的持续崩溃），优先查外部守护日志与 guard.sh 分类；
3. delay timer 互斥是成员变量级（无锁），CoSpawn 在 HeartBeatThread 串行执行所以实际无并发——但若未来多线程提交，"检查+设置"非原子，存在双重启窗口，需注意；
4. HandleDeviceError 中 pending app 重启被设备重启**静默取消**（reset 不上报）——平台侧会看到 AppSubmit 后无对应 AppHandle，排查时注意这层语义；
5. hook 为编译产物（interpose 库），是否生效取决于链接方式，建议自检流程中加一条"子线程调度策略 = SCHED_OTHER"的验证项。
