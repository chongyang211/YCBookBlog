# Pos · 03 传输层与帧协议

> 系列第三篇，承接《02.总览与架构.md》。覆盖 pos_transferer：串口初始化、收包路径、**发送三向 dispatch**、双 ACK 语义、连接状态与巡检切换。

## 一、两个角色

| 角色 | 形态 | 职责 |
|---|---|---|
| PosLinkServerHolder | 函数内静态单例（:155） | 持有 pos_link::PosLinkServer：串口绑定/帧协议/收包线程/连接回调；经 weak_ptr 反向通知 PosTransferer |
| PosTransferer | Transferer 基类子类 | 对上暴露三个发送 API（Send / SendAndGetResponse / SendFrameError）+ OnReceiveData 收包回灌 |

StopPosLinkServer()（:228）：单向停串口服务——仅供巡检切换 p2p_link（两链路互斥）；**恢复仅靠重启**（kInspecting 唯一出口是停+重启，刻意不提供运行时重启路径，:132-135 注释）。

## 二、串口配置与初始化（PosLinkServerHolder 构造，:108-123）

```text
PosLinkServer::Create({msg_begin_tag=0x7E, msg_end_tag=0x7E, need_escape=true})
  → BindSerial("/dev/ttyS2", 115200, /*flow_control=*/false)
     失败：仅 LOG_E，进程继续跑但永远不通（上位机侧表现"无响应"）
  → 自建 std::thread：
       AcceptReqs()（收包循环，自续投递）
       AsyncWaitConnectivityChanged（连接状态回调，处理完自续挂下一次）
       server_->Start()
```

帧协议要素：**0x7E 帧头尾 + 转义**（need_escape，payload 中的 0x7E 由 pos_link 库转义）——帧解析细节封装在独立 pos_link 库内，本层只见解出的 Request{msg_id, data}。

## 三、收包路径（跨线程唯一入口，:161-193）

```text
AsyncAcceptRequest（循环）
  → 提取 PosAppCommReq{msg_cmd, ...}（data 头部定长结构，不足按 0 填充）
  → Threads::MainThread()->Post：
      组 DataPackage{function_id=msg_cmd, data, ext_data=msg_id hex 串, is_response=false}
      → PosTransferer::OnReceiveData(pkg)      ← 进入 HandleRequest 分发（04 篇）
      → NeedAutoResponse(cmdid) ? SendAutoResp : 无
```

**双 ACK 语义**：NeedAutoResponse 覆盖四类指令（:24-34）——**0x05 StopPalm / 0x0B Control / HostStateChange / CameraLight**。这四类收包即自动回空 ACK（帧头 reply_msg_code=0），业务逻辑随后再回正式 Resp——上位机收到两级确认：ACK（"我收到了"）+ Resp（"处理结果"）。新增"收到即回执"类指令时在此表登记。

## 四、发送三向 dispatch（Send，:255-302）——本篇核心

| 分支 | 判定 | 底层 API | msg_id 语义 | 典型流量 |
|---|---|---|---|---|
| 1. 业务 Resp | is_response == true（**优先判定**） | AsyncSendResponse | **原 Req 的 msg_id**（从 ext_data 还原）——上位机按 msg_id 匹配 pending callback | 0xAD BiComm 业务应答 |
| 2. Request 型 | is_response==false 且 IsRequestCmd | **AsyncRequest**（等对端响应） | 新分配 msg_id，等 reply | 0xA3 结果 / 0xA5 优选图 / 0xAB / 0xAC / 0xA7 / 0xA1 等 15 类（:36-57 全表） |
| 3. 兜底 notification | 其余 | AsyncSendResponse | 无原 msg_id 可匹配（历史行为，:299-301） | 部分通知类 |

**血泪教训（:251-254 注释原文）**：0xAD 业务 Resp 曾因只按 IsRequestCmd 路由而错走 AsyncRequest（分配新 msg_id），上位机按 msg_id 匹配不到 → 表现为 **err=110 超时**。修复 = 把 is_response 判断提到最前。**新增"需要回包给上位机原请求"的指令时，走分支 1（is_response=true），绝不能走分支 2**。

NeedHandleResponse（:59-67）：仅 QueryHostInfo / PlayTts 两类 Request 的响应数据需要回灌 OnReceiveData（内部继续处理），其余 Request 的 resp_data 丢弃（只看 error_code）。

## 五、三个对外 API

| API | 返回 | 用途 |
|---|---|---|
| Send(DataPackage) | error_code | 常规三向 dispatch（上文） |
| SendAndGetResponse(data) | (error_code, reply_msg_code, resp_data) 三元组 | **BiComm 直用**——需要 resp_data 内容的场景（:304-323，底层同为 AsyncRequest） |
| SendFrameError(ext_data, cmd_id, reply_msg_code) | error_code | **帧层错误响应**：reply_msg_code 直接写帧头 PosMsgReplyHeader、body 恒空——用于"未知 cmd_id""协议版本错"等帧层语义（:325-345）。与业务 Resp 的区别：业务 Resp 帧头 reply_msg_code 恒 0、业务 ret_code 放 body |

线程细节：三个 API 的底层调用都 co_spawn 到 **link 自己的 executor**（串口线程）执行，完成后回到调用方协程——上层无感。

## 六、连接状态

- HandleConnectivityChanged（:195-206）：串口连接/断开 → Post 主线程 → PosTransferer::ConnectionStateChangeSig——Controller 订阅（"与旧 PosSession::OnCreate 对齐"，用于灯效/上报链路的连接感知）；
- IsConnected()：当前 link 存在且未关闭；
- 心跳检查 SetupHeartbeatCheck 已被注释（:120, :166-167）——**无应用层心跳**，死链靠请求超时与 connectivity 回调暴露。

## 七、观察点

1. **三张指令表需随新指令同步维护**：NeedAutoResponse / IsRequestCmd / NeedHandleResponse——新增 0x 指令漏登记任一表，表现为路由错误（如走兜底分支导致上位机匹配不到）；三个 switch 相邻，建议合并为一张指令属性表；
2. 分支 3（兜底 notification）无 msg_id 匹配语义——通知类天然无请求方所以安全，但容易被误用于"需要回执"的场景，新指令接入前先对照第四节 dispatch 表；
3. ReportSendRequest/Response 已摘除（:355-361 空函数）——串口收发统计已移除，如需吞吐观测需重接埋点；
4. BindSerial 失败不 fail-fast（第二节）——启动日志搜 "pos link serial port bind" 确认链路是否活着；
5. 帧解析（0x7E/转义/校验）封装在 pos_link 独立库内——帧层 bug 需进 pos_link 库排查，本层只能看到解出的 Request。
