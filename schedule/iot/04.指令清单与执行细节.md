# IoT · 指令清单与执行细节

> 系列第四篇。9 个指令逐个的执行细节。承接《03.指令执行框架.md》（IotBaseCmd 生命周期与状态 API）。

## 一、指令类继承体系

```text
IotBaseCmd（生命周期/状态/上报，见 03 篇）
├── 直接实现：rebootDevice / restartApp / factoryReset / syncNtp / uploadLog
│             fileCleanCmd / dumpStorageInfo / captureLog
└── IotBiCommCmd（BiComm 中转基类：指令转发上位机执行，结果回传设备）
    └── remoteDoorOpen（远程开门）
```

两类执行形态：

- **设备自执行**：SetExecuting -> 业务动作 -> SetSuccess/Fail（高危类额外等终态回执）；
- **BiComm 中转**：设备收到指令 -> 转发上位机执行 -> 等上位机回执 -> 状态随回执设置。

## 二、高危三兄弟（执行即杀进程）

`rebootDevice / restartApp / factoryReset` 三者实现同构（以 reboot 为例，reboot_device.cpp:15-27）：

```text
Start：KeepSelf -> IotBaseCmd::Start -> Post RealStart（IotThread）
RealStart：
  WaitSchedExecuteTimeRunTask(execute_time)     <- 定时执行
    SetExecutingState(0, "preparing to reboot")
    UploadStateNow()                            <- (1) 显式刷 40 中间态
    SetSuccessState("")                         <- (2) 先写终态 50（还没重启！）
    WaitLastTerminalSent(5s)                    <- (3) 阻塞等 50 回执送达（最多 5s）
    DeviceAction::RebootDeviceAsync(...)        <- (4) 最后才真正重启
```

**顺序设计**（源码注释明示）：重启 = 进程马上被杀，一切上报必须赶在被杀前完成——40 中间态显式刷一次、终态 50 在**动作执行前**写入、阻塞最多 5s 等"执行成功"回执送达平台销单，避免平台以为未完成而**下次开机重复下发**。三步顺序保证无论重启发生在哪一刻，后台都不会丢状态。factoryReset 同构；restartApp 语义相同（进程重启）。

## 三、syncNtp（NTP 对时）

```text
SetExecutingState(0, "NTP sync started")
NtpTimeSync::SyncTime()        <- 同步阻塞（最长 15s，运行在 IotThread）
  成功 -> SetSuccessState("NTP sync done")
  失败 -> SetFailState(error_code, error_msg)
```

注意与操作码 10003 NTP（qcloud 篇）的实现差异：指令版同步执行不丢线程池（IotThread 本就是工作线程），操作码版在 MainThread 需要丢线程池——同一动作两种宿主的线程策略不同。

## 四、uploadLog（最复杂的指令）

### 4.1 入口：路径白名单（Start，upload_log.cpp:69-95）

| 平台下发的 log_target_path | 映射 | 收集内容 |
|---|---|---|
| /sdcard/wxpayface/log | app_logs | palmapp 日志目录（可带 log_file_rule 正则过滤） |
| /sdcard/iotsystem/log | system_logs | syslog 目录（规则过滤但 syslog 系列必收）+ dmesg + system_info.txt |
| 其他非空路径 | 原样 | 白名单校验：必须以 /data 或 /userdata 开头，否则 60 FAIL（ERR_PALM_LOG_UPLOAD_PATH_NOT_ALLOWED）——防路径穿越/任意目录读取 |
| 空 | 默认 app_logs | |

### 4.2 执行三步（Run，独立 upload_log 线程）

```text
step1 CollectLogs：
  Logger::FlushSync（先刷日志）
  按目标收集文件（正则过滤；syslog 必收规则；系统模式额外收 dmesg +
    system_info.txt：内核版本/uptime/meminfo/df/日志 Top10/ps lw/ifconfig，
    du 与 ls 均带 timeout 10s 防 FS 异常卡死）
  -> 打包 ZIP（IOT_log_{cmd_id}.zip）-> 算 size + MD5
step2 GetUploadUrl：
  POST /iot-palm/instruction/cos/presign {device_sn, prefix_path, ext:zip}
  -> 返回 upload_url / download_url / content_type（COS 预签名）
step3 UploadLogs：
  PUT upload_url（x-ms-blob-type BlockBlob，限速 1MB/s）-> 2xx 成功
终态：SetSuccessState(biz_result = {result: download_url}) / SetFailState
```

### 4.3 五时点 BiComm 状态桥接

执行过程每次推进同步调 status_reporter_(phase, ec, msg, url) -> UploadLogHandler -> BiCommManager 通知上位机（弱引用持有，防生命周期悬垂）：

| phase | 含义 |
|---|---|
| 0x20 | 收集中（kCollectingLog） |
| 0x21 | 压缩/取 URL |
| 0x22 | 上传 COS |
| 0x10 | 完成（带 download_url） |
| 0x11 | 失败（带 ec/msg） |

上位机可据此展示进度条。异常路径（exception/unknown）同样走 0x11 通知 + SetFailState；SCOPE_EXIT 保证临时 zip/目录清理。

## 五、remoteDoorOpen 与 IotBiCommCmd 框架

remoteDoorOpen 是 IotBiCommCmd 子类——设备不自执行，转发上位机执行：

| 机制 | 说明 |
|---|---|
| 框架职责 | 自动获取 BiCommManager 并校验、构造 callback、投 MainThread（BiCommManager 线程约束）、error_msg JSON 解析提取 message + 兜底 |
| 子类只实现 | GetCmdName（remoteDoorOpen）/ GetExecutingDescription |
| 可选覆写 | OnBiCommCompleted / OnBiCommFailed / GetBiCommParams |
| 时效失效 | GetMaxExecuteDelaySeconds()=90：now - execute_time 超过 90s -> 指令已失效（设备可能经历断网/断电），直接报失败不开门（取值依据：MQTT 断连轮询 60s + 网络余量 30s）——远程开门是实时性指令，过期开门有安全风险 |

## 六、运维三件套（fileCleanCmd / dumpStorageInfo / captureLog）

与 04 篇 Story 137924309 相关的日志运维指令，均为设备自执行形态（SetExecuting -> 清理/采集/打包 -> 终态），模式同 uploadLog 的收集阶段（无 COS 上传）。

## 七、观察点

1. system()/popen 使用：AppendKernelLogs（dmesg 重定向）与 AppendSystemInfo（popen 多条命令）——命令均为代码内常量、无用户输入拼接，无注入面；但属安全规则关注 pattern，新增命令建议继续走"常量命令表"；
2. uploadLog 白名单校验用前缀匹配（find(...) == 0）——/data_evil 这类前缀重叠路径可绕过（应校验 /data/ 带斜杠），建议修正；
3. uploadLog 的 zip 打包在 IotThread 派生的 upload_log 线程执行——不阻塞指令分派；SCOPE_EXIT 清理临时文件；
4. syncNtp 同步阻塞最长 15s 在 IotThread——同轮询周期内其他指令会排队；
5. remoteDoorOpen 的 90s 失效语义依赖设备时间可信——与门闸 3 的时间守卫呼应。
