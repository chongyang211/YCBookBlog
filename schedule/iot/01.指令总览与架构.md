# IoT 指令通道 · 总览与架构

> 系列入口：本篇是 IoT 指令模块的总览，细节见同目录 02~05。
> 范围：`src/service/iot/`（IotService + cmds/ 指令框架）+ 可靠请求联动 + OTA 宿主关系。

## 一、定位：指令的可靠执行与状态必达

IoT 指令通道回答一个问题：**云端如何可靠地让设备做一件事，并且知道设备做到了没有**。

与数据上报（report/影子）的本质差异：

| | 数据上报（report/影子） | 指令通道（本模块） |
|---|---|---|
| 数据方向 | 设备 -> 云端（事实/状态） | 云端 -> 设备（动作意图）-> 回报执行结果 |
| 失败语义 | 各通道差异化（重试/丢弃） | 状态经 ReliableRequest 必达；指令幂等重推续传 |
| 核心复杂度 | 字段口径与时机 | 去重防重放 + 状态机推进 + 杀进程指令的回执竞态 |

三个核心维度：**IotCmdState（10~90 指令状态机）**、**双层去重（内存 16 条 + MMKV 终态集）**、**ReliableRequest 状态必达（request_id 幂等 + task_id 互斥）**。

## 二、组件分层

```text
IotService（门面单例）
├── 轮询任务（BaseFrequencyScheduler，60s/300s 动态）
├── MQTT handler（MESSAGE_TYPE_DOWN_INSTRUCTION=2，经 MqttService 注册）
├── 双层去重（last_cmd_ids_ 内存 16 条 + cmd_dedup_kv_ MMKV 终态集 TTL 24h）
├── DispatchCmd 门闸链 -> DispatchToInternal 分派
├── ReliableRequest（状态必达，request_id = cmd_id_seq_state 幂等）
├── cmds/base_cmd.h（IotBaseCmd 生命周期基类）+ cmds/*（9 个具体指令）
└── OTA 宿主：Init 内启动 IotUpgradeSchd（OTA 任务另有 MQTT type-1 handler）
```

组件协作边界：

1. IotService **只管获取与分派**（门闸链通过后创建指令任务即返回）；
2. **执行与状态推进在 IotBaseCmd 子类**（含定时执行、终态回执等待）；
3. **状态必达在 ReliableRequest**（指令状态与业务解耦，断网/重启自动补发）。

## 三、双通道与轮询间隔动态调整

```text
通道 (1) HTTP 轮询：GET /iot/devices/{sn}/instructions/execute-list
        周期动态：默认 60s；"MQTT 已连 且 本连接周期 HTTP 拉取成功过一次" -> 300s
通道 (2) MQTT 推送：MESSAGE_TYPE_DOWN_INSTRUCTION=2
        秒级到达，与轮询共用同一 DispatchCmd 门闸链
间隔调整信号：PaasMqtt Connected/Disconnected + 首拉成功（pull_success_once_）
        MQTT 断连 -> 重置标志回 60s
```

设计逻辑：MQTT 在线时推送为主，但**先证实 HTTP 链路可用**才敢放稀轮询——两条独立证据链，避免 MQTT 假在线漏指令。

## 四、线程模型

| 线程 | 职责 |
|---|---|
| 调度器线程池 | 轮询任务触发（kCritical，需时间同步） |
| HTTP（轮询内联） | execute-list 拉取 |
| **IotThread** | DispatchCmd 串行分派、指令执行编排（高危指令的 WaitLastTerminalSent 同步等待在此，勿在 MainThread 调 Start） |
| HeartBeatThread | ReliableRequest 入队相关（状态上报路径见 05 篇） |
| MQTT 线程 | 推送到达 -> handler（OnMqttInstructionMessage 内部转 IotThread） |

## 五、生命周期与启动时序

```text
BootStrapper -> IotService::Init()（iot_service.cpp:88-143）
  1. 恢复指令去重 MMKV（iot_cmd_dedup，TTL 24h）-> last_cmd_ids_（超 16 淘汰最旧）
  2. 注册轮询任务（60s 周期，随机 offset，requires_time_synced=true）
  3. 注册 MQTT type-2 handler（Start 前缓冲机制，见 mqtt 篇）
  4. 订阅 PaasMqtt Connected/Disconnected -> 间隔动态调整
  5. IotThread 启动 IotUpgradeSchd::Init()（OTA 调度器，含其自有 MQTT type-1 handler）
        运行期：轮询/MQTT -> 门闸链 -> 指令任务 -> 状态必达（02~05 篇）
```

OTA 宿主关系：IotUpgradeSchd 的任务来源有二——自有 MQTT type-1 秒推 + 自有 HTTP 轮询（upgrade 专用接口），与指令通道并列；IoT 指令（uploadLog/remoteDoorOpen 等）与 OTA 无关，二者仅共享 Init 入口与 IotThread。

## 六、IotCmdState 状态机总览（10~90）

```text
10 DISTRIBUTING（平台分发中）
  -> 20 DEVICE_RECEIVED        <- 拉到/收到即报（DispatchCmd 门闸第 2 步）
  -> 30 DEVICE_DISPATCHED      <- IotBaseCmd::Start
  -> 40 EXECUTING              <- 业务执行中（可多次报）
  -> 50 EXECUTED_SUCC          <- 终态（满重试）
  -> 60 EXECUTED_FAIL          <- 终态（满重试；过期/时间不可信/未实现在此收敛）
旁路：70 DISTRIBUTE_TIMEOUT / 80 EXECUTE_TIMEOUT / 90 CANCELED（平台侧语义为主）
```

- 快照语义：指令携带 snapshot.seq/state，设备跳过已处理状态、report_seq 续增（详见 05 篇）；
- 终态（50/60）才持久化去重（详见 02 篇掉电续传语义）。

## 七、观察点

1. `last_cmd_ids_` 容量 16 较小——平台积压重推超过 16 条不同指令时最旧条目（含 MMKV）被淘汰，可能重复执行，依赖指令自身幂等；
2. 高危指令（restart/reboot/factoryReset）的 WaitLastTerminalSent 同步等待运行在 IotThread——Main 调用会卡 UI；
3. IotCmdState 三套互转（枚举/字符串/数值）集中在 base_cmd.h——平台侧增状态需同步三处；
4. 轮询间隔调整依赖"连接周期"语义标志——MQTT 假在线（半开）场景由 mqtt 篇 KeepAliveWatchdog 兜底。
