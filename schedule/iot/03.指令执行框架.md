# IoT · 指令执行框架（IotBaseCmd）

> 系列第三篇，承接《02.指令下发与去重.md》。覆盖指令通过门闸链之后的执行侧框架：IotBaseCmd 生命周期、状态设置与上报、定时执行、高危指令终态回执等待，以及新增指令的开发步骤。

## 一、生命周期总览

```text
DispatchToInternal
  └─ IotCmdXxx::Create(id, seq, execute_time, params)->Start()
       ├─ SetState(30 DEVICE_DISPATCHED)        # 状态 + 上报入可靠队列
       ├─ execute_time 在未来？
       │    是 -> WaitSchedExecuteTimeRunTask（steady_timer 定时唤醒）
       │    否 -> 立即执行业务
       ├─ 执行中：SetExecutingState(40)（业务可多次推进）
       ├─ 终态：SetSuccessState(50) / SetFailState(60)
       │    -> MarkCmdTerminalDedup（终态持久化去重，见 02 篇）
       │    -> 高危指令：WaitLastTerminalSent(timeout) 同步等回执送达
       └─ DeleteLater（KeepSelf 自持有引用释放，对象销毁）
```

**自持有生命周期**：执行期间对象经 self_（shared_ptr）自持有（KeepSelf），DeleteLater 释放——任务不受分派方生命周期影响，调用方无需管理删除。

## 二、状态设置三 API 与上报时机

| API | 状态 | 典型时机 |
|---|---|---|
| SetExecutingState(biz_state, biz_data) | 40 EXECUTING（+业务子状态） | 长耗时指令的过程推进 |
| SetSuccessState(biz_result) | 50 EXECUTED_SUCC | 业务成功 |
| SetFailState(err_code, err_msg) | 60 EXECUTED_FAIL | 业务失败（err_code 用 unified_errcode 段） |

每次设置内部：更新 state_data_ -> DoUploadState()（状态 JSON 经 ReliableRequest 入可靠队列，Submit 内含同步刷盘，断网/重启/掉电不丢）-> 终态额外触发 MarkCmdTerminalDedup（02 篇去重持久化）。

时序契约：**终态（50/60）已成功入可靠队列后才写 MMKV 去重**——MarkCmdTerminalDedup 由 SetState 在该条件下调用（iot_service.h:31-33）。另有 UploadStateNow() 手动即时上报。

## 三、定时执行（WaitSchedExecuteTimeRunTask）

指令携带 execute_time（平台指定执行时刻）时：

```text
execute_time > now：steady_timer 定时到点 -> 执行业务 lambda -> promise 返回 future
execute_time <= now：立即执行
timer 被 cancel（对象销毁）-> promise 设异常 -> future 侧感知
```

- 定时基于 **steady_timer**（不受系统时间跳变影响，from_time_t 换算一次）；
- 平台"定时重启/定时清理"类指令的落地机制；等待期间对象 KeepSelf 保活。

## 四、WaitLastTerminalSent（高危指令终态回执）

**问题**：restart/reboot/factoryReset **执行即杀进程**——终态刚入可靠队列进程即死亡，平台看到状态延迟到达（虽可由持久化补发兜底，但慢）。

**机制**（base_cmd.h:110-113, 179-183）：

```text
SetSuccess/FailState 之后、DeleteLater 之前（同线程契约）：
  WaitLastTerminalSent(timeout)
    - 终态入队时创建 terminal_sent_promise_（shared_ptr 独立于指令对象
      生命周期，DeleteLater 后仍可被 ReliableRequest OnResult 安全触发）
    - future.wait_for(timeout) 阻塞等待
        送达/拒收/放弃 均视为出队完成 -> true（本轮闭环）
        超时/网络异常 -> false（依赖 reliable_request 持久化补发兜底）
```

同步阻塞运行在 **IotThread**——调用方不可在 MainThread 调 Start（01 篇线程模型警告）；promise 与对象解耦是关键：DeleteLater 后回调仍能 set_value。

## 五、新增指令开发步骤

1. cmds/ 新建类继承 IotBaseCmd，构造传 {cmd_id, seq, execute_time, params}；
2. 实现业务逻辑：过程推进用 SetExecutingState，终态用 SetSuccessState/SetFailState——**禁止绕过状态 API 直接发网络**（状态必达与去重持久化都挂在 SetState 上）；
3. execute_time 定时语义免费获得（基类）；
4. 执行即杀进程的指令：终态后调 WaitLastTerminalSent；
5. iot_service.cpp DispatchToInternal 注册 cmd_name 分派分支（未注册报 UNIMPLEMENTED 终态）；
6. 幂等自查：平台重推（02 篇掉电/淘汰场景）时重复执行是否安全。

## 六、观察点

1. WaitSchedExecuteTimeRunTask 用 std::result_of（C++17 已弃用）——可换 std::invoke_result_t；
2. WaitLastTerminalSent 超时值与 ReliableRequest 重试节奏的配比需确认（太短会频繁走持久化补发慢路径）；
3. 授权流程的 completion 单槽模型与指令框架的多任务并行（每指令独立对象）是两种并发模型——勿混淆；
4. upload_timer 成员未见使用点——疑似预留/残留。
