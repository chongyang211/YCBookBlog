# IoT · 状态上报与联动

> 系列第五篇。覆盖指令状态如何"必达"平台：ReportInstructionState 详解、与 ReliableRequest 队列的关系、三套状态互转维护点、模块间联动。

## 一、ReportInstructionState 详解（iot_service.cpp:44-77）

指令状态上报的唯一出口（门闸 2 的 20 上报、IotBaseCmd 的 30/40/50/60 都走这里）：

```text
POST /iot/devices/{sn}/instructions/{cmd_id}/update-exec-state
  body = UpdateInstructionExecStateReq{
    device_sn, instruction_id,
    seq = cmd_seq + 1,            # 从 snapshot.seq 续增，服务端单调校验
    state, error_code / error_msg  # 仅失败态填错误
  }
  ▼ 不直调 Network，而是 ReliableRequest::Submit：
    request_id = "{cmd_id}_{seq}_{state}"   # 幂等键：同状态重试不重复
    task_id    = "{cmd_id}_{seq}"           # 任务互斥键：同任务同 seq 的新状态入队
                                            # 时清掉未送达的旧状态（过期拒执 60 清未送达的 20）
    full_retry = state >= 50                # 终态（50/60）满重试必达；
                                            # 中间态（20/30）过时无价值，快速放弃
    category   = kCategoryCmdState
```

| 设计 | 针对 |
|---|---|
| request_id 三段幂等 | 同一状态多次入队/重试不重复送达 |
| task_id 互斥 | 乱序场景：拒执 60 入队时清掉还在队里的 20，平台不会先收到 60 又收到 20 |
| 终态满重试 / 中间态快速放弃 | "设备收到了"过时无价值；"执行成功/失败"必须让平台知道 |
| 可靠队列持久化 | 断网/重启期间状态不丢（重启后补发） |

## 二、IotCmdState 三套互转（维护点）

base_cmd.h 集中三套转换，**平台侧增状态需同步三处 + 增枚举值**：

| 转换 | 用途 |
|---|---|
| 枚举 <-> 字符串（IotCmdStateToString/FromString） | HTTP JSON 接口（snapshot.state 是字符串） |
| 数值 -> 枚举（IotCmdStateFromValue） | MQTT protobuf 二进制的枚举数值 |

状态值域：10/20/30/40/50/60/70/80/90；非法值归 kUnknown。

## 三、snapshot.seq 续增的单调语义

指令自带 snapshot（平台记录的执行进度）：`report_seq = snapshot.seq` 起步，每次 ReportInstructionState 后递增。保证：

1. 服务端按 seq 单调校验，乱序（如重推后补发的旧中间态）不会回卷状态；
2. 设备重启/重推场景下，新上报的状态 seq 一定大于平台已记录值。

## 四、与 ReliableRequest 的关系

ReliableRequest 是跨模块的可靠请求基础设施（mmap 持久化、断网补发、GiveUp 回调）：

| 使用方 | category | 内容 |
|---|---|---|
| IotService / IotBaseCmd | kCategoryCmdState | 指令状态（本篇） |
| OTA 上报 | （自有 category） | 升级状态必达（见 OTA 方案文档） |
| 其他 | - | 需要必达的少量关键请求 |

队列唤醒的三条路径（网络信号 / 入队 / 心跳旁证）见《docs/heart/01.心跳服务全流程.md》。实现细节对照《docs/report/04.report核心实现分析.md》的队列事务语义（同款 take/commit/restore 思想）。

## 五、模块间联动

| 联动点 | 说明 |
|---|---|
| MQTT | type-2 下行走同一 DispatchCmd 门闸链；Connected/Disconnected 驱动轮询间隔（01 篇） |
| TimeStateManager | 门闸 3 的时间不可信守卫 + 轮询任务 requires_time_synced 门闸 |
| OTA（IotUpgradeSchd） | Init 宿主关系；OTA 任务走自有 type-1 handler 与轮询，不经指令门闸链 |
| Heartbeat | 心跳成功 NotifyHeartbeatOk 唤醒可靠队列扫描（状态补发的加速路径） |
| uploadLog -> BiComm | 指令执行状态除平台外，五时点同步通知上位机（04 篇 4.3） |

## 六、观察点

1. request_id 含 state——同一 seq 的"重试后状态变化"会生成新 request_id，不会互相幂等掉（正确）；但同一状态的重试被幂等吸收（正确）——理解此设计后再改；
2. task_id 互斥只清"同 cmd_id+seq"的旧态——若平台 snapshot.seq 回卷重推，可能出现新旧 seq 交叉，依赖服务端单调校验兜底；
3. 中间态快速放弃窗口：20/30 入队后立即断网且未送达，平台侧该指令会停留在"平台已分发"——符合"过时无价值"设计，但平台侧超时策略需覆盖此态；
4. IotCmdState 数值转换对未知值归 kUnknown（0）——非法值指令会在门闸 5 被跳过且不上报（静默），排查时注意。
