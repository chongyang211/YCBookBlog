
PaasShadow · device-side 上行同步。device-side 属性是**设备上报给云端的事实状态**（module_auth / software_version / device_ops 等），本篇覆盖它的写入入口、版本冲突防护与 Provider 自动取值。

## 一、两条写入入口

| API | 语义 | 路径 |
|---|---|---|
| `UpdateDeviceSideProperty` | **批量**：进 `waiting_property_map_` 缓冲，随 Schedule 循环每 300s（kSendIntervalSec）由 `SendDeviceSideProperties` 统一上报 | 写 → 等 → 批量 POST UpdateDeviceSideProperties |
| `UpdateDeviceSidePropertyRealtime` | **实时**：立即上报 + `callback(code, message)` 通知结果 | 写 → 即时 POST |

**选型提示**：批量路径最长 300s 延迟——时效敏感的属性（如授权状态变更）必须走 Realtime；低频状态快照用批量以合并网络开销。

所有写入先经 `PrepareDeviceSideProperty` 附加本地版本号，然后存在两条去向：直接发送，或（未 PullDone 时）进 PendingQueue。

## 二、首次 Pull 门闸与版本冲突防护

### 问题：为什么 Pull 完成前不能直接写？

首次 `PullDeviceSideProperties` 完成前，本地缓存为空、不知道云端已存的版本。此时接受写入并上报，会带一个**低于云端已存的版本号**——写入被云端忽略或造成版本回退。

### 门闸机制（impl.h:194-200）

```text
Start → PullDeviceSideProperties（diff：本地版本 vs 云端记录）
  ├─ 云端版本更高（本机上一次上报成功但本地缓存回滚 / 同一设备的其他会话写入）
  │    → 云端 d_data 覆盖本地缓存
  │    → DeviceSidePropertyRefreshedSignal 广播
  │       （业务收到后只重新加载本地缓存，勿反向上报——避免来回覆盖；
  │        现网问题：缓存已是新值、内存仍是旧值，用户必须重启才生效）
  └─ Pull 完成 → device_side_pull_done_.store(true)
       ├─ InitialProviderFetch()：对所有 Provider 首次取值（值变才上报）
       └─ FlushPendingQueue()：补报暂存的写请求
```

### PendingQueue 设计

- key = `identifier_scopeType_scopeValue`——**天然去重，仅保留最后一次值**（连续多次写同一属性，只有最终值有意义）；
- 每条含 `realtime` 标记与 realtime 专用的 callback，flush 时按原语义（批量/实时）补报；
- 仅"已初始化但 Pull 未完成"时暂存；其他情况（未 Init 等）直接失败返回。

业务侧感知：`IsDeviceSidePullDone()` 查询 + `RegisterDeviceSidePullDoneCallback` 注册回调（如启动期需要确认属性已同步再行动的场景）。

## 三、Provider 抽象（自动取值上报）

### 3.1 接口契约（property_provider.h）

```cpp
class DeviceSidePropertyProvider {
  std::string GetValue();              // 返回 JSON 值；在 property_thread_ 上调用
                                       // ⚠️ 必须线程安全，且禁止耗时操作（网络请求等）
  std::string GetIdentifier();         // 属性标识（"software_version" / "module_auth" / …）
  int32_t  GetScopeType();             // 默认 global
  std::string GetScopeValue();
  PropertySourceType GetSourceType();  // 三选一，决定刷新方式
  int32_t GetRefreshIntervalSec();     // 仅 kSystemRuntime 生效，默认 60s；0 = 不定时刷新
};
```

### 3.2 三种来源类型

| 类型 | 语义 | 刷新方式 | 例子 |
|---|---|---|---|
| `kCloudDerived` | 云端派生：值来自 cloud-side 属性的设备侧 mirror | 随 cloud 变更 / Pull 刷新 | mirror 类属性 |
| `kEventDriven` | 事件驱动：由本地事件产生（上位机指令、授权变更等） | 事件发生时业务手动 Realtime 上报 | module_auth 授权状态 |
| `kSystemRuntime` | 系统运行时：从系统 prop / SDK / 硬件读取 | **定时刷新**（GetRefreshIntervalSec） | software_version（60s） |

### 3.3 调度与去重

```text
PullDone → InitialProviderFetch()：所有 Provider 首次取值
Schedule 循环 → RefreshSystemRuntimeProviders()：
  对每个 kSystemRuntime Provider，距上次刷新 >= GetRefreshIntervalSec() 时取值
  与缓存/已上报值比对 → 值变才组装上报（去重），值不变零网络开销
```

设计论证实例（SoftwareVersionProvider，heartbeat_service.cpp:39-41）：60s 刷新周期 + 值去重后，60s 与 300s 的实际网络开销相同——刷新频率可以大胆设，成本由去重兜底。

### 3.4 现网注册者

| Provider | identifier | 类型 | 注册位置 |
|---|---|---|---|
| `SoftwareVersionProvider` | software_version | kSystemRuntime（60s） | heartbeat_service.cpp:27-42（bootstrapper :330 统一注册段） |
| `PalmBehaviorProvider` | palm_behavior | — | bootstrapper.cpp:327 注释（PalmBehavior::Init 注册） |

注册时序：**必须先于 `PaasShadow::Start()`**（否则 PullDone 首报无它）。

## 四、上报失败处理

- `SendDeviceSideProperties` 失败计数（`send_fail_count_`）；
- 失败不影响缓存中的新值——下个 300s 周期自动重试（值未变则由 diff 版本机制兜底）；
- Realtime 失败通过 callback 通知业务，由业务决定重试策略。

## 五、观察点

1. 批量路径 300s 延迟是隐含契约，接入文档（05 篇）需显式提醒；
2. `DeviceSidePropertyRefreshedSignal` 的"只重载缓存、勿反向上报"约束靠注释约定——recognition_mode 曾误订此信号（02 篇教训）；
3. Provider GetValue 的"轻量"约束同样靠注释——若实现者塞入 IO，会拖慢 property_thread_ 上的整个 Schedule 循环。
