# Pos · 02 总览与架构

> 系列入口。范围：`src/biz/pos/`——模组侧的"POS 协议门面"：通过串口（`/dev/ttyS2` 115200，0x7E 帧）与上位机收银机收发 0x 协议字。分主题：03 传输层与帧协议 / 04 上行指令字典 / 05 下行通知帧族与正向识别链 / 06 BiComm 指令与旁路 / 07 遗留代码对照与迁移映射；快速通读见《01.Pos模块全流程分析.md》。

## 一、定位

**只管"和上位机说话"，不管刷掌流程**——会话状态流转、业务事件上报全在 palm_flow 状态机；pos 层负责协议翻译：把 FSM 的事件/状态变成上位机听得懂的 0x 字，把上位机的指令翻译成对 FSM 的喂入。两层经 `PalmSessionController` 单点互调（pos 层调它进/出会话、喂事件；它经 `GetGlobalPosRequestHandler()` 反向调 pos 层发通知帧）。

## 二、分层结构（活跃部分）

```text
上位机(POS 收银机)
   ↕ 串口 0x 帧（pos_link 库：0x7E 帧头尾 + 转义）
pos_transferer        传输层：持有 PosLinkServer 单例，三向发送（Send / SendAndGetResponse / SendFrameError）
   ↕
pos_request_handler   协议中枢（单例，经 GetGlobalPosRequestHandler() 获取）：
                      上行 HandleRequest 大分发（0x04/0x0E/0x05/0x0D/0xA6/0x14/0xAD…）
                      + 下行通知帧构建（0xA3 结果 / 0xA5 优选图 / 0xAB 加验 / 0xAC 绑定 / 0xA7 测速）
   ↕
PalmSessionController（palm_flow FSM）
   ↕ 内部策略：MakePalmFlowStrategy（Controller :667，产出 profile + Verdict 决策）
旁路：bicomm_manager（0xAD 双向指令）/ upload_log_handler / speed_test_notifier（0xA7）
```

## 四、线程模型（3 个边界，1 个收敛点）

- **全部业务收敛在 MainThread 协程**：`HandleRequest` 分发、0xA3/0xA7 发送均 `Threads::MainThread()->CoSpawn`；BiCommManager 明确约束"所有方法必须在 MainThread 调用"；
- 跨线程仅 3 处边界：
  1. **串口专用线程**：`PosLinkServerHolder` 自建 `thr_`，收包后 Post 主线程（跨线程唯一入口）；发送时再 post 回串口线程写帧（《03》篇）；
  2. **识别/加验 HTTP**：由 palm_flow 侧（Controller ConsumeAction）发起——线程归属与超时详见《docs/palm-flow-state-machine.md》与 network 请求管线篇；
  3. **IotThread**：仅 uploadLog 的后端 HTTP 调用与软超时定时器串行于此，避免阻塞刷掌主链路；结果经 mutex 保护的映射表回主线程（《06》篇）。

## 六、与 palm_flow 的分工

| | palm_flow | biz/pos |
|---|---|---|
| 职责 | 会话状态流转、业务事件上报（`palm.*.result` / metrics） | 与上位机的全部协议细节（帧/字段/base64/ACK） |
| 边界 | 只产生"语义事件"（结果/加验请求/绑定通知…） | 只做"协议翻译"，不含刷掌业务逻辑 |

互调唯一通道：pos 层 → `PalmSessionController`（进/出会话、喂事件）；Controller → `GetGlobalPosRequestHandler()`（反向发通知帧）。

## 七、遗留代码清单（详见《07.遗留代码对照与迁移映射.md》）

- `pos_session.*` / `strategy/`：无调用点的旧架构代码，保留作 palm_flow 迁移对齐参考；

## 八、上位机侧接入架构

**背景**：PosLink 协议栈目前只有 C++ 实现（Android 走 Djinni/JNI AAR），Windows / macOS 侧（Electron）无法直接调用，需要一条复用同一协议栈的接入路径。

**目标**：让 `paymax-pos-link-electron`（Electron 上位机 Demo）复用 `pos_link/` C++ 核心，与 O41 模组、Android 侧保持协议一致，避免纯 TS 重写导致的协议 drift。

**做法**（两层）：
1. **C ABI 封装层**（`pos_link/c_api/`，新增）：把 C++ 核心包装为纯 C 导出（`pl_client_create` / `pl_connect_serial` / `pl_send_start_palm` 等），产出 Win x64/x86 DLL + macOS Intel/arm64 dylib；C++ 核心零改动，CMake 经 `POS_LINK_BUILD_C_API` option 独立开启，不影响现有 Android / Windows 构建。
2. **koffi FFI + 全平台子进程桥接**：Electron 不在主进程直接 FFI，而是 fork 一个 Node 子进程（bridge-worker）加载 DLL/dylib，主进程与子进程间走 stdio 上的 NDJSON 通信（照搬 `paymax-iot-link-electron` 成熟模式）。

**原理思想**：
- **C ABI 是 FFI 互操作的最大公约数**——几乎所有 FFI 方案（koffi、N-API 等）都以 C ABI 为通用标准，包一层 C 即可跨语言复用；
- **协议升级零成本**——协议栈只有 C++ 一份实现，升级后 Win/Mac 重编产物即跟进；
- **子进程隔离**——pos_link 内部用 Boost.Asio 线程做串口 IO 与回调，直接在 Electron 主进程 FFI 有跨线程回调阻塞/崩溃风险；子进程隔离后串口阻塞 UI 风险为 0，崩溃可直接重启，协议边界收敛在 NDJSON 一条路径上。
