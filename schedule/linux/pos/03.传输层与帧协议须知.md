# Pos · 03 传输层与帧协议

本篇按**业务流程**组织：先交代角色与物理层，再沿两个通信方向（**上位机 → 模组** 指令下发、**模组 → 上位机** 结果与事件推送）逐跳讲解——帧格式、msg_id、双 ACK、去重等概念在流程中顺势引入，最后汇总贯穿机制、连接生命周期与观察点。

---

## 一、角色与物理层

### 1.1 两个角色

| 角色 | 形态 | 职责 |
|---|---|---|
| PosLinkServerHolder | 函数内静态单例（:155） | 持有 pos_link::PosLinkServer：串口绑定/帧协议/收包线程/连接回调；经 weak_ptr 反向通知 PosTransferer |
| PosTransferer | Transferer 基类子类 | 对上暴露三个发送 API（Send / SendAndGetResponse / SendFrameError）+ OnReceiveData 收包回灌 |

### 1.2 物理层：RS232 串口

双方之间是一条 **RS232 串口**。RS232（EIA-232）是最经典的**串行通信接口标准**，定义设备间串口通信的电气特性与信号线：

| 特性 | 说明 |
|---|---|
| 通信方式 | 全双工串行——数据按位顺序传输 |
| 关键信号线 | TXD（发送）/ RXD（接收）/ GND（地），最简三线即可通信 |
| 电平 | 负逻辑 ±3~15V（与芯片 TTL 电平相反，直连需 MAX3232 类转换芯片） |
| 速率 | 双方约定波特率，**本项目为 115200**（见下文 BindSerial） |
| 距离 | 近距离（典型 ≤15m） |

**分层理解**——RS232 只解决"0 和 1 用什么电压、走哪根线"；本篇之后的所有内容（帧格式、功能码、双 ACK、会话）定义的是"这些字节代表什么业务含义"。协议与物理层解耦：同款帧协议未来若换 USB 虚拟串口，无需任何改动。

### 1.3 两端串口端点（三项目实现事实）

| 端 | 设备节点 | 波特率/流控 | 代码位置 |
|---|---|---|---|
| 模组（palm_app_linux） | `/dev/ttyS2` | 115200，无流控 | `pos_transferer.cpp:111` · `BindSerial("/dev/ttyS2", 115200, false)` |
| 上位机（Android SDK） | 按**机型映射**解析节点（默认 `/dev/ttyS0`） | 115200 | Demo `DeviceSerialPortResolver.resolve()` + `PalmHelper.serialPort(path, 115200)` |

补充事实：

- **同口多用途**：ttyS2 另有符号链接 `/dev/tty_uart_p2p`（p2p_link 备用线路经 CH9329 切换）；产检自检用 `/dev/ttyS3` 回环（不占用 ttyS2）——见 `p2p_link.cpp` / `device_inspect_controller.cpp`
- **实现栈**：pos_link 库经 asio `serial_port` 打开节点 + `termios`（raw 模式）配置收发——跨平台（模组 Linux / Android NDK）同一套代码
- **工程实践**：上位机不同机型串口节点不同，集中收敛在"机型 → 节点"映射（`DeviceSerialPortResolver`，按 `Build.MODEL` 解析，未匹配回落默认值）——新增机型只改映射表，不散落硬编码

## 二、方向一：上位机 → 模组（指令下发）

以"POS 下发 0x05 StopPalm"为例，走完一整条链路（其他指令同构）。

**代码调用链**（跨两层四个项目）：

```text
【上位机侧（Android SDK，Java → C++ 跨语言，详见 06 篇）】
PalmManager.startPalmEx / stopPalm（PalmManager.java，:132 加载 libpalm_manager）
  └─ ConnectionManager → djinni Client 代理
       └─ ClientConfig（serialPath/baud，ConnectionManager.java:471 toClientConfig）
            └─ JNI：native_client.cpp → client_impl.cpp
                 └─ pos_link 协议核组帧（0x7E / CRC32）→ 串口写

【模组侧（palm_app_linux）】
Reader 收包协程（pos_link_impl.h:280-）
  └─ read_parser_.Parse()（pos_parsing.cpp：0x7E 定界 / 去转义 / CRC32）
       └─ DispatchMsg（pos_link_impl.h:300-）
            └─ recent_accepted_msgids_ 去重 → accepted_reqs_ 入队
AcceptReqs（pos_transferer.cpp:161-193，link 线程）
  └─ 提取 PosAppCommReq → MainThread Post
       └─ PosTransferer::OnReceiveData
            ├─ NeedAutoResponse ? 自动空 ACK（双 ACK 第一级）
            └─ PosRequestHandler::HandleRequest（pos_request_handler.cpp:241-330
               按 function_id 分发：0x04/0x05/0x09/0x0D/0x14/0xAD…）
                 └─ 业务（FSM React / 查询 / 配置）→ 业务 Resp（双 ACK 第二级）
```

### 2.1 上位机组帧（帧格式概念在此引入）

上位机把业务请求组装成一帧（22B 帧头 + 业务体 + 5B 帧尾）：

```text
| msg_tag 0x7E | msg_length(4) | protocol_ver 0x01 | encoding_ver 0x01
| msg_id(10) = type(0x03) + datetime(7,BCD) + msg_no(2)
| checksum_type 0x01(CRC32) | reserved(4)
| 业务体：msg_cmd(2)=0x0005 + 字段…
| CRC32(4) | msg_end_tag 0x7E
```

三个关键概念：

- **msg_cmd**：功能码（0x01~0x15 / 0xA0~0xB5，全表见《04.上行指令字典.md》）
- **msg_id**：msg_type + BCD 时间 + 序号——用于应答匹配与**去重**（下文 2.3）
- **转义**：业务体中的 0x7E 由 pos_link 库转义，接收侧还原

### 2.2 模组收帧：串口参数与 Reader 协程

模组侧 `PosLinkServerHolder` 构造时完成初始化（:108-123）：

```text
PosLinkServer::Create({msg_begin_tag=0x7E, msg_end_tag=0x7E, need_escape=true})
  → BindSerial("/dev/ttyS2", 115200, /*flow_control=*/false)
     失败：仅 LOG_E，进程继续跑但永远不通（上位机侧表现"无响应"）
  → 自建 std::thread：
       AcceptReqs()（收包循环，自续投递）
       AsyncWaitConnectivityChanged（连接状态回调，处理完自续挂下一次）
       server_->Start()
```

BindSerial 内部不止 open 节点，随后 set_option 五连（pos_link_server.cpp:80-105）：

```text
baud_rate(115200) / parity::none / character_size(8) / stop_bits::one
/ flow_control(use_flow_control ? hardware : none)   ← 本项目传 false
```

任一 set_option 抛异常 → BindSerial 返回 false，行为同 open 失败。

server `Start()`（串口模式，:118-131）把串口包成 `PosLink` 实例（每链路一个，pos_link_impl.h:37 `PosLinkImpl`），Start 即 post **Reader / Writer 两个常驻协程**。

**Reader（收包协程，pos_link_impl.h:280-）**：

```text
async_read 串口 → read_stream_.commit(n)
  → while (read_stream_.size())
        read_parser_.Parse(read_stream_)           ← pos_parsing：0x7E 定界/去转义/CRC32/拆 header+body
  → 解析成功 → DispatchMsg(std::move(msg))
  → 解析错误仅 LOG_E 并继续消费流（坏帧不卡死后续）
  → 尾部自续 Reader()（常驻循环）
```

另有 `StartWithCleanCache()`（:73-）：启动前先异步读掉串口残留缓冲（5KB 上限/100ms 超时），清历史脏数据后再进正常循环。

### 2.3 去重：DispatchMsg 的第一道关（:300-）

```text
IsReq（msg_type=0x03）：
  ① 去重：查 recent_accepted_msgids_ 环形缓冲
     （上位机请求 5s 超时会重试 3 次——若响应其实已送达，重发帧在此拦截，
       对应帧层错误码 0x7 DuplicatedErr）
  ② 未重复 → accepted_reqs_.push_back({msg_id, data})
            → accepted_reqs_ev_.AsyncNotifyOne()
```

去重缓冲容量 `kRecentAcceptedMsgidMaxNums` 定义在同源库内——重试风暴超过容量时最旧 msg_id 滑出、可能放行一条重复帧（概率极低，知晓即可）。

### 2.4 跨线程交接：AcceptReqs → 主线程

```text
AcceptReqs（PosLinkServerHolder 自建线程，循环）
  → 提取 PosAppCommReq{msg_cmd, ...}（data 头部定长结构，不足按 0 填充）
  → Threads::MainThread()->Post：
      组 DataPackage{function_id=msg_cmd, data, ext_data=msg_id hex 串, is_response=false}
      → PosTransferer::OnReceiveData(pkg)      ← 进入 HandleRequest 分发（04 篇）
      → NeedAutoResponse(cmdid) ? SendAutoResp : 无
```

**线程边界**：协议收发（Reader/Writer/AcceptReqs 等待）永远在 link 线程；业务处理（OnReceiveData → HandleRequest → FSM）永远在主线程——互不阻塞。

### 2.5 双 ACK 与 HandleRequest 分发

**双 ACK 语义**：NeedAutoResponse 覆盖四类指令（:24-34）——**0x05 StopPalm / 0x0B Control / HostStateChange / CameraLight**。这四类收包即自动回空 ACK（帧头 reply_msg_code=0），业务逻辑随后再回正式 Resp——上位机收到两级确认：ACK（"我收到了"）+ Resp（"处理结果"）。新增"收到即回执"类指令时在此表登记。

分发明细（每条指令处理什么）见《04.上行指令字典.md》。

### 2.6 应答回帧：reply_msg_id 匹配

业务处理完成后回正式 Resp：

```text
| msg_tag 0x7E | … | msg_id(10) = type(0xFB) + …
| reply_header：reply_msg_id(10) + reply_msg_cmd(2) + reply_msg_code(4)
| 业务体：msg_cmd + ret_code + …
| CRC32 | 0x7E
```

**硬约束（2026-06-08 兼容设计 v3）**：帧头 `reply_msg_code` **恒 0**，业务 `ret_code` 只放 body——v1 曾把业务码写帧头，上位机误判为帧层错误（历史踩坑）。真正的帧层错误走专用通道 `SendFrameError`（见 3.4）。

## 三、方向二：模组 → 上位机（结果与事件推送）

**代码调用链**（以识别收敛发 0xA3 为例）：

```text
【模组侧（palm_app_linux）】
业务收敛（RecognitionFinish / EnrollmentFinish / VerificationFinish）
  └─ PosTransferer::Send（pos_transferer.cpp:255-302 三向 dispatch）
       ├─ 分支1 业务 Resp：AsyncSendResponse（原 Req 的 msg_id）
       ├─ 分支2 Request 型：AsyncRequest（新 msg_id，等 POS 响应）
       └─ 分支3 兜底 notification：AsyncSendResponse
  └─ Writer 协程 → pos_writing.cpp 组帧（转义 / CRC32）→ 串口

【上位机侧（Android SDK）】
pos_link 协议核收帧解析（去转义 / CRC32）→ client_impl.cpp
  └─ native_client_biz_listener（C++ 业务监听器）
       └─ Djinni 反向回调（C++ → Java）
            └─ CallbackDispatcher 切调度线程
                 └─ ModuleEventListener / PalmBehaviorListener → Demo
```

### 3.1 什么时候发：业务收敛点

模组在业务收敛/事件产生时向 POS 推送（均为 Request 型，等 POS 响应）：

| 功能码 | 触发时机 |
|--------|----------|
| 0xA3 | 识别/录掌/绑定/加验收敛（含未注册 306 中途成绩单） |
| 0xA5 / 0xA6 / 0xA1 | 激活变化 / 升级状态 / 模组状态 |
| 0xA7 / 0xA8 | 网速测试 / 掌事件（优选图/切注册/会话起止） |
| 0xAB / 0xAC | 加验通知 / 录掌等待通知（转身份输入） |
| 0xB0 / 0xB2 / 0xB3 / 0xB5 | 授权状态 / 授权结果 / 升级建议 / 自动激活确认 |

### 3.2 怎么发：三向 dispatch（Send，:255-302）

| 分支 | 判定 | 底层 API | msg_id 语义 | 典型流量 |
|---|---|---|---|---|
| 1. 业务 Resp | is_response == true（**优先判定**） | AsyncSendResponse | **原 Req 的 msg_id**（从 ext_data 还原）——上位机按 msg_id 匹配 pending callback | 0xAD BiComm 业务应答 |
| 2. Request 型 | is_response==false 且 IsRequestCmd | **AsyncRequest**（等对端响应） | 新分配 msg_id，等 reply | 0xA3 结果 / 0xA5 优选图 / 0xAB / 0xAC / 0xA7 / 0xA1 等 15 类（:36-57 全表） |
| 3. 兜底 notification | 其余 | AsyncSendResponse | 无原 msg_id 可匹配（历史行为，:299-301） | 部分通知类 |

**血泪教训（:251-254 注释原文）**：0xAD 业务 Resp 曾因只按 IsRequestCmd 路由而错走 AsyncRequest（分配新 msg_id），上位机按 msg_id 匹配不到 → 表现为 **err=110 超时**。修复 = 把 is_response 判断提到最前。**新增"需要回包给上位机原请求"的指令时，走分支 1（is_response=true），绝不能走分支 2**。

### 3.3 Writer：组帧与响应优先

`Writer` 发送协程：`resp_calls_` 队列**响应优先**发送（先回对方的 Resp，再发自己的请求/推送）；实际组帧在 `pos_writing.cpp`（header 22B + 转义 + CRC32 + end_tag）；写失败（非 operation_aborted）→ 通知 `conn_ev_` 关链路。

### 3.4 帧层错误专用通道：SendFrameError

收到不认识的 cmd_id / 协议版本不符时，经 `SendFrameError`（:325-345）回错误帧——reply_msg_code 直接写帧头（0x2=未知指令等，:37-49 帧层错误码表）、body 恒空。与业务 Resp 的区别：业务 Resp 帧头 reply_msg_code 恒 0、业务 ret_code 放 body。

### 3.5 三个对外 API 与 NeedHandleResponse

| API | 返回 | 用途 |
|---|---|---|
| Send(DataPackage) | error_code | 常规三向 dispatch（上文） |
| SendAndGetResponse(data) | (error_code, reply_msg_code, resp_data) 三元组 | **BiComm 直用**——需要 resp_data 内容的场景（:304-323，底层同为 AsyncRequest） |
| SendFrameError(ext_data, cmd_id, reply_msg_code) | error_code | 帧层错误响应（上文 3.4） |

NeedHandleResponse（:59-67）：仅 QueryHostInfo / PlayTts 两类收到的 Request，其响应数据需要回灌 OnReceiveData（内部继续处理），其余 Request 的 resp_data 丢弃（只看 error_code）。

线程细节：三个 API 的底层调用都 co_spawn 到 **link 自己的 executor**（串口线程）执行，完成后回到调用方协程——上层无感。

## 四、贯穿机制速查

| 机制 | 要点 |
|---|---|
| msg_id | type(0x03 Req/0xFB Resp) + BCD 时间 + 2B 序号；Resp 靠 reply_msg_id 关联原 Req |
| 去重 | recent_accepted_msgids_ 环形缓冲；容量 `kRecentAcceptedMsgidMaxNums`（同源库内） |
| 双 ACK | 四类指令（0x05/0x0B/HostStateChange/CameraLight）自动空 ACK + 业务 Resp |
| reply_msg_code | 帧头恒 0；业务 ret_code 在 body；帧层错误走 SendFrameError |
| 超时重试 | 请求 5s 超时、3 次重试；重发帧被模组去重拦截 |
| 转义/CRC32 | 业务体 0x7E 转义；CRC32 校验帧头+业务体 |

## 五、连接生命周期

- **建立**：PosLinkServerHolder 构造（§2.2）——BindSerial + 专属线程 + Start；
- **连接状态**：HandleConnectivityChanged（:195-206）串口连接/断开 → Post 主线程 → `ConnectionStateChangeSig`——Controller 订阅（灯效/上报链路的连接感知）；`IsConnected()` 当前 link 存在且未关闭；
- **无应用层心跳**：心跳检查 SetupHeartbeatCheck 已注释（:120, :166-167）——死链靠请求超时与 connectivity 回调暴露；
- **巡检互斥**：`StopPosLinkServer()`（:228）单向停串口服务——仅供巡检切换 p2p_link（两链路互斥）；**恢复仅靠重启**（kInspecting 唯一出口是停+重启，刻意不提供运行时重启路径）。

## 六、观察点

1. **三张指令表需随新指令同步维护**：NeedAutoResponse / IsRequestCmd / NeedHandleResponse——新增 0x 指令漏登记任一表，表现为路由错误（如走兜底分支导致上位机匹配不到）；三个 switch 相邻，建议合并为一张指令属性表；
2. 分支 3（兜底 notification）无 msg_id 匹配语义——通知类天然无请求方所以安全，但容易被误用于"需要回执"的场景，新指令接入前先对照 3.2 dispatch 表；
3. ReportSendRequest/Response 已摘除（:355-361 空函数）——串口收发统计已移除，如需吞吐观测需重接埋点；
4. BindSerial 失败不 fail-fast（§2.2）——启动日志搜 "pos link serial port bind" 确认链路是否活着；
5. 帧解析（0x7E/转义/校验）封装在 pos_link 独立库内——帧层 bug 需进 pos_link 库排查，本层只能看到解出的 Request；
6. **协议核与 Android SDK 同源**：`pos_link/` 库同时被模组（palm_app_linux）与上位机（palm_manager/android/pos_link）引用，报文结构由 `palm_manager/scripts/commands.yaml` 单一事实源生成 `generated/pos_app_commands.gen.h`——改协议先改 yaml 重新生成，两侧同步；
7. 去重缓冲容量 `kRecentAcceptedMsgidMaxNums` 在同源库内——上位机重试风暴超过容量时最旧 msg_id 滑出、可能放行一条重复帧（概率极低，知晓即可）；坏帧只 LOG_E 不断链，真正的死链靠 connectivity 回调与请求超时暴露。
