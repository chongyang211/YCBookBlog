# 网络监视服务（NetworkMonitorService）全流程

> 范围：`src/service/network/`。本目录 = **网络状态监视**（network_monitor_service.*，活跃代码）+ 网络协议契约（tdi_interface.proto / palmapp.proto，接口定义存档）。运行时逻辑只有 NetworkMonitorService 一个类。

## 一、功能定位

感知设备网络变化，解析网络类型并维护全局网络状态单例（`NetworkInfo`），同时作为多个"依赖网络恢复"机制的**触发源头**：网络恢复后联动 NTP 对时与 MQTT 重连，间接点亮影子推送、可靠请求、核验记录补报等各模块的恢复加速路径。

## 二、组件与状态单例

| 组件 | 职责 |
|---|---|
| `NetworkMonitorService` | 监听链路变化信号、探测网络类型、更新状态、联动下游 |
| `NetworkInfo`（facility/network/network_info.h） | 全局网络状态单例（NetworkType + ConnectState）；写入口 `friend class NetworkMonitorService`——**只有本服务能更新**，状态源唯一 |

proto 文件（tdi_interface / palmapp）是网络接口层协议契约：`TdiRequest/TdiResponse/TdiPushMessage` + `TdiPushMessageType` 枚举为后台推送接口类型注册表（文件内注释：每次新增推送接口在此处添加类型定义，需与后台对齐）。与活跃代码无直接 include 关系。

## 三、全流程

### 1. 启动（bootstrapper.cpp:190，Phase 1 早期）

```text
Init()
  |- 订阅 SystemInterface::NetworkConnectChangedSig      <- 系统层链路变化信号
  |    变化 -> post MainThread -> 延时 1s -> QueryNetworkType()
  |    （1s 延迟：等链路稳定，避免拿到切换中间态）
  |- 立即 CoSpawn 一次 QueryNetworkType()                <- 启动时先探测一次
```

### 2. 单次探测（QueryNetworkType，network_monitor_service.cpp:34-70）

```text
SystemInterface::GetNetwork("")            <- 系统接口查询
  | 失败 -> LOG_E，保持原状态
  v 解析 JSON 数组，取第一项的 "sType"
  - 空数组      -> NetworkType=kNone + kDisconnected（判定断网）
  - "cell"      -> kCellular
  - "wifi"      -> kWifi
  - "ethernet"  -> kEthernet
  - 其他        -> kOther
  v
NetworkInfo 单例更新（type + connected）   <- 全局网络状态唯一写入口
  v 三个下游联动（仅判定连网时）：
  - NtpTimeSync::OnNetworkConnected()     <- 触发 NTP 对时（签名 HTTP/心跳依赖时间同步）
  - MqttService::Reconnect()              <- MQTT 重连请求（已连或 mqtt_enabled 关闭时 no-op）
  - LOG_I 当前网络类型
```

## 四、状态消费者（NetworkInfo 的读方）

| 消费方 | 用途 |
|---|---|
| `report_item_base.h` FillBeforeQueue | 每条上报自动带 `network_type` 字段 |
| `speed_tester.cpp`（网络诊断） | 测速报告标注网络类型 |
| `NetworkInfo::IsConnected` 类查询 | 各处"网络可用"快判（注意与"某次请求成功"旁证的语义差异，参见 heart/verify_record 文档） |

## 五、联动意义（为什么网络变化要触发 NTP + MQTT）

本服务是多个"依赖网络恢复"机制的触发源头之一：

| 下游 | 依赖原因 |
|---|---|
| NTP 对时 | 签名 HTTP 必须时间同步（心跳/PaasShadow 的 Skip 门闸都等它） |
| MQTT 重连 | 影子推送、可靠请求、verify_record 恢复加速都以 MQTT 连接为信号源 |
| （间接）verify_record / PaasShadow 的恢复加速 | 本服务触发的 Reconnect 成功 -> ConnectedSig -> 那两个模块的恢复路径被点亮 |

即：**链路层跳变 -> NetworkMonitorService -> MQTT 重连 -> ConnectedSig -> 各模块恢复加速**，是断网恢复告知的正规路径（shadow/verify_record 文档提到的"链路态跳变"即此处）。

## 六、观察点

1. `QueryNetworkType` 只取 JSON **数组第一项**的 sType——多网络接口并存时（如 eth+wifi）优先级由系统接口返回顺序决定，设备侧无择优逻辑；
2. `GetNetwork` 失败时**保持原状态不更新**——链路已断但状态可能仍是 kConnected，依赖下一次变化信号纠正（心跳失败 / ReliableRequest 旁证路径补位）；
3. 断网判定依赖"空数组"返回——若系统接口断网时返回非空残条目，会误判连网；
4. proto 文件与活跃代码无直接 include 关系，属接口契约存档，改协议时需与后台对齐。
