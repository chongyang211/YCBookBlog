# License · 授权状态机与复检收敛

> 系列第二篇，承接《01.总览与架构.md》。覆盖 AuthState 7 值流转、与 DeviceFsm 的仲裁链、RefreshAuthState 统一收敛机制，以及 kChecking 阶段的"伪结论"专题。

## 一、AuthState 7 值定义与流转

| 值 | 含义 | 进入条件 |
|---|---|---|
| `kUnknown(0)` | 初始未知 | 构造默认 |
| `kChecking(1)` | 启动期 NTP 等待 + 首次本地校验中 | Init：有 license 文件但时间未同步 |
| `kUnauthorized(2)` | 未授权 | 无 license 文件 / 校验失败 / 授权失败回落（source 非 refreshing） |
| `kAuthorizing(3)` | 授权流程进行中 | DoAuthorize 进入（扫码解密/验签/拉云端签名/覆盖等待） |
| `kAuthorized(4)` | 已授权 | license 有效且未过期；或 kFromRefreshing 授权失败保留旧 license |
| `kExpired(5)` | 已过期 | 复检发现 endtime 已过 |
| `kError(6)` | 授权库/IO 错误 | 授权库调用异常 |

**流转主线**：

```text
kUnknown ──Init──> kChecking（有文件等时间）或 kUnauthorized（无文件）
kChecking ──时间可信──> LoadAndCheckLicense ──> kAuthorized / kUnauthorized / kExpired
kUnauthorized/kExpired --扫码授权成功--> kAuthorizing --> kAuthorized
kAuthorized --复检发现过期--> kExpired
kAuthorized（kFromRefreshing 授权失败）--> 保留 kAuthorized
kUnauthorized（授权失败，source 非 refreshing）--> 保持 kUnauthorized
任意 --DoAuthorize 进入--> kAuthorizing（临时保护）
kError：授权库调用异常进入；恢复路径待确认（见 01 篇观察点 3）
```

## 二、与 DeviceFsm 的仲裁链

```text
AuthState 变化（SetAuthState）
  ├─ MaybeReportShadow（module_auth 属性，去重）
  ├─ state_signal_（0xB0 广播）
  └─ 若非 Init 抑制期（suppress_fsm_drive_）：ResolveIdleTarget 驱动 DeviceFsm
        │ ResolveLicenseDeviceState() 映射（LicenseManager 是 AuthState 唯一所有者）
        ▼
DeviceState：kAuthorized -> nullopt（落到激活检查）
             kChecking/kUnknown -> kLicenseChecking
             kAuthorizing -> kLicenseAuthorizing（保护态，互斥挡刷掌）
             kUnauthorized/kExpired/kError -> kLicenseUnauthorized（扫码态）
```

要点：

1. **映射逻辑收敛在 LicenseManager**——`DeviceStateMachine::ResolveIdleTarget` 只调 `ResolveLicenseDeviceState()`，不自行判 AuthState；
2. kAuthorized 返回 nullopt 是刻意设计：授权正常时 license 层"隐身"，Idle 目标由激活检查接棒；
3. OnEnter 复核失败（AuthState 与设备态不匹配）返回 false → 状态机自动 `RequestEnter(ResolveIdleTarget())` 重仲裁——自愈闭环。

## 三、RefreshAuthState：复检的统一收敛入口

### 3.1 为什么必须收敛

授权状态可能被多种运行时事件影响（时间跳变、license 过期临界点、激活完成、保护态退出）。若各触发点自行调 CheckAuthLocal + 驱动状态机，会出现：并发复检竞态、去抖失效、状态机被多方驱动。FR-3.9 因此规定：**所有触发点必须经 RefreshAuthState(reason)，禁止直调 CheckAuthLocal 或 RequestEnter(ResolveIdleTarget())**。

### 3.2 触发源（RefreshReason 全表）

| reason | 触发源 | 时机 |
|---|---|---|
| kBootInit | 启动首次 | Init |
| kNtpSync | NTP 完成 / 运行时时间跳变 | TimeStateManager 回调 |
| kPeriodicTimer | 1h 常规定时 | 调度任务 |
| kCheckingTicker | kChecking 期间 30s 快速轮询 | 同上（旧机制残留，现以时间可信回调为主） |
| kPrePalmCheck | pos_request_handler 前置校验 | StartPalm 请求时 |
| kActivationDone | 激活成功后 | ActivationController |
| kProtectedExit | 保护态 OnExit | kPalmRunning / kActivating / kUpgrading 退出 |
| kLicenseFileEvent | license 文件变化 | 预留 |

reason 不影响业务逻辑，仅用于日志/打点归因。

### 3.3 内部管线（manager.cpp:690-716）

```text
RefreshAuthState(reason)   —— 任意线程可调，内部投递 LicenseThread
  ├─ 100ms 去抖（last_refresh_ms_）：多触发源短窗合并为一次复检
  ├─ 跳过条件 1：in_authorizing_ —— 授权中不复检
  │    （DoAuthorize 结束后会自然驱动状态收敛）
  ├─ 跳过条件 2：current_state == kChecking —— 检查中不复检（见第四节专题）
  ▼
CheckAuthLocal()（:476-）
  ├─ in_authorizing_ 再查（双保险）
  ├─ yt_auth_get_endtime() / yt_auth_get_appid()
  ├─ endtime 判定：未过期（kAuthorized+summary）/ 已过期（kExpired）
  └─ 跃迁则 SetAuthState → 自然驱动状态机 + Shadow 上报 + 0xB0
```

### 3.4 消费方：kPrePalmCheck 的位置

`pos_request_handler` 收到 StartPalm 时前置调 `RefreshAuthState(kPrePalmCheck)` + `CanStartPalm()`——保证"上一轮心跳后 license 恰好过期"的场景下，本次刷掌被正确拒绝（而不是用过期的 CanStartPalm 缓存值）。

## 四、专题：kChecking 阶段的"伪结论"不可回退问题

**现象**：Init 时有 license 文件但时间未同步（设备刚开机、NTP 未完成）——此时 license 尚未 load 进授权库（`yt_auth_init_by_path` 未调），`yt_auth_get_endtime()` 返回 <=0。若此时执行 CheckAuthLocal，会得出"无有效 license"的结论并把状态机推进到 **kLicenseUnauthorized——该迁移不可回退**，即使随后时间同步、license 加载成功也无法自然回到正确状态。

**防御（双重）**：

1. RefreshAuthState 跳过条件 2：`kChecking` 时直接 return（manager.cpp:705-710 注释完整论证）；
2. kChecking 的**唯一出口**是 TimeStateManager 时间可信回调 → `LoadAndCheckLicense()`（先 `yt_auth_init_by_path` 加载，再 CheckAuthLocal）——出口独占，不存在其他路径误触发。

**同类防御**：`in_authorizing_` 跳过——授权流程中 license 库处于中间态，复检同样会得出伪结论；DoAuthorize 的 Succeed/FailAuthorize 自己负责终态设置。

**维护提醒**：新增任何"周期任务/事件回调"时，若会触碰 CheckAuthLocal，必须遵守同一收敛约定（经 RefreshAuthState + 尊重两个跳过条件），否则会重新引入伪结论路径。

## 五、ForceReportShadow 与复检的关系

时间可信回调里除了 LoadAndCheckLicense 还会 `ForceReportShadow()`——因为时间未同步期间 shadow 上报可能被跳过（或 flush 失败后去重机制不再重发），时间可信是"确定能发网络请求"的第一个可靠时点。去重 + 强制补报的完整语义见《05.联动与接入指南.md》。
