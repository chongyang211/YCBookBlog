# IoT · 指令下发与去重

> 系列第二篇，承接《01.总览与架构.md》。覆盖指令从"到达设备"到"进入执行"之间的全部门闸：双通道触发、六道门闸链、去重持久化设计。

## 一、双通道触发

### 1.1 HTTP 轮询（PullInstructionTask，iot_service.cpp:179-209）

```text
调度器触发（60s/300s 动态，kCritical，需时间同步）
  - pulling_ CAS 防重入（上轮未结束则跳过本轮）
  - GET /iot/devices/{sn}/instructions/execute-list
  - 本连接周期首拉成功（pull_success_once_ CAS）-> UpdatePollingInterval 切 300s
  - 指令列表非空 -> post IotThread 串行 DispatchCmd
  - 失败 -> LOG_W（下轮重试；MQTT 断连时已回 60s 兜底）
```

### 1.2 MQTT 推送（OnMqttInstructionMessage，type-2 handler）

秒级到达，解析 MqttDownMessage 后**走同一 DispatchCmd 门闸链**——推送与轮询行为完全一致，不存在"推送绕过门闸"的路径。推送丢失（断线窗口）由 SyncUnAck 补拉 + 轮询兜底（见 mqtt 篇）。

### 1.3 轮询间隔的连接周期语义

| 标志 | 置位 | 重置 |
|---|---|---|
| mqtt_connected_ | ConnectedSig | DisconnectedSig |
| pull_success_once_ | 本周期 HTTP 拉取成功 | DisconnectedSig |

规则：两者同时为真 -> 300s，否则 60s。"先证实 HTTP 链路可用再放稀"的双证据设计——MQTT 假在线（TCP 半开）场景由 mqtt 篇 KeepAliveWatchdog 兜底。

## 二、DispatchCmd 六道门闸链（iot_service.cpp:240-318）

```text
DispatchCmd(instruction)（IotThread 串行）
  门闸 1：cmd_id / cmd_name 非空
  门闸 2：上报 20 DEVICE_RECEIVED
          report_seq = snapshot.seq + 1（续增，保证服务端 seq 单调）
          经 ReliableRequest 必达（断网/重启补发）
  门闸 3：过期守卫（cmd_expire_time > 0 时才校验）
          - 时间不可信（IsTimeTrusted=false）-> 60 FAIL（ERR_PALM_TIME_UNTRUSTED）
            安全优先：1970 时期无法校验时效，拒绝执行而非误放行
          - 已过期 -> 60 FAIL（ERR_PALM_INSTRUCTION_EXPIRED）
  门闸 4：双层去重（见第三节）
          - MMKV 终态集命中 -> 静默跳过（终态由 reliable_request 补发送达）
          - 内存 last_cmd_ids_ 命中 -> 拒绝
          通过 -> 写 last_cmd_ids_（容量 16，淘汰最旧并同步删 MMKV）
  门闸 5：snapshot.state 过滤
          仅 DISTRIBUTING / DEVICE_RECEIVED / DEVICE_DISPATCHED 可执行；
          其余跳过且不上报失败（避免重复上报把指令误标终态）
  门闸 6：DispatchToInternal -> IotCmdXxx::Create(...)->Start()（见 03 篇）
          未实现 cmd_name -> 60 FAIL（ERR_PALM_INSTRUCTION_UNIMPLEMENTED）
```

## 三、去重持久化设计（专题）

### 3.1 两层结构

| 层 | 载体 | 容量 | 写入时机 | 作用 |
|---|---|---|---|---|
| 内存层 | last_cmd_ids_ deque | 16 条 | DispatchCmd 通过后立即 | 本轮会话快速判重 |
| 持久层 | cmd_dedup_kv_（MMKV，TTL 24h） | 随内存淘汰同步删 | **仅终态且终态已入可靠队列后**（MarkCmdTerminalDedup，由 IotBaseCmd::SetState 调用） | 跨重启判重 |

### 3.2 核心语义：终态才持久化的掉电续传设计

```text
指令到达 -> 内存去重记录 -> 执行中……
  - 正常到达终态 50/60 且状态已入可靠队列
      -> MMKV 写入 cmd_id -> 此后平台重推命中 -> 静默跳过
        （终态由 reliable_request 队列补发送达，不丢）
  - 掉电/重启中断于终态前
      -> 不在 MMKV 去重集 -> 平台重推触发重新执行
        （幂等指令自动续传；非幂等由平台撤回/重推策略兜底）
  - 重启恢复：Init 从 MMKV 恢复终态 id 集合（超 16 淘汰最旧）
```

为什么不在 Dispatch 阶段就写 MMKV：若指令执行一半掉电，去重集已含该 id -> 平台重推被静默跳过 -> 指令永远停在中间态。延迟到终态写入是"至少一次执行"与"防重放"的平衡点。

### 3.3 容量与淘汰

内存容量 16：超限淘汰最旧，**同步删 MMKV 条目**（两层一致）；MMKV 条目 TTL 24h 防膨胀。⚠️ 组合边界：平台积压重推 >16 条不同指令时，最旧条目两层同时淘汰 -> 可能重复执行，依赖指令自身幂等（恢复出厂/重启等执行即终态，天然幂等）。

## 四、排查指引："指令没收 到 / 重复执行"

| 症状 | 排查顺序 |
|---|---|
| 下发但设备无动作 | 1) PullInstruction got N instructions（拉到没）2) Duplicate instruction received（去重命中）3) already expired / time untrusted（门闸 3）4) already processed, state=（snapshot 过滤，平台状态未回卷）5) Unimplemented internal IoT command（分派表没有） |
| 指令重复执行 | 1) MMKV iot_cmd_dedup 是否含该 id（终态是否入队成功）2) 是否触发 16 条淘汰 3) 平台重推时 snapshot.state 是否正确回卷 |
| 平台状态停在中间态 | 查 reliable_request 队列积压（状态入队失败 LOG_E）与终态是否被 task_id 互斥清掉（05 篇） |
