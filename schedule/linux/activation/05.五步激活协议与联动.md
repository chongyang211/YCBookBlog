# Activation · 五步激活协议与联动

> 系列第五篇。覆盖 StartActivationFromQRCode 入口到五步协议的完整实现细节、trace 串联机制、补发 confirm 的宽容策略与接入检查清单。承接《02.状态机与阶段流转.md》《03.扫码与激活码解析.md》《04.域名与证书校验.md》。

## 一、五步协议总览（activation_service.cpp）

| Step | 接口 | 端点 | 签名 | SE 操作 | 产物 |
|---|---|---|---|---|---|
| 1 | CheckActivationStatus | 无网络（纯本地） | - | Init + 固件升级检查 + HasExchangedKeyWithServer | REGISTERED/UNREGISTERED 判定 |
| 入口 | StartActivationFromQRCode | （内含证书校验，见 04 篇） | - | - | activation_code_ + SetActivationSession |
| 2 | StartPalmDeviceActivation | POST /activation/devices/{sn}/activation/start | ACTIVATION | GetAllSePubKeys | server_keys_ + activation_trace_id_ |
| 3 | ExchangeAndConfirmKeys | POST .../activation/confirm-key-change | ACTIVATION | 逐 key ExchangeKeyWithServer | confirm_code_ |
| 4 | ConfirmKeyExchangeToSE | （内含 Step5） | - | ConfirmExchangeKeyWithServer | 域名落地 + REGISTERED |
| 5 | ConfirmPalmDeviceActivation | POST .../activation/confirm | DEVICE | - | activation_confirmed 标志 |

## 二、入口：StartActivationFromQRCode（:93-205）

四路解析（见 03 篇）-> ValidateActivationCode（version/session_id/session_key/server_domain 四必填）：

1. 清除 activation_confirmed 标志（新一次激活流程开始，Config）；
2. SetActivationSession(domain, session_id, session_key)——后续激活请求签名基础；
3. 激活前 NTP 同步 SyncTimeWithDomain(domain)——失败仅 LOG_W 非阻塞（为证书有效期校验兜底时间，见 04 篇观察点 1）；
4. ValidateActivationDomain -> 证书校验（04 篇）；失败错误码原样透传（不统一转域名错误），error_message 已含 trace_id 文案。

## 三、Step 1：CheckActivationStatus（:409-478）

```text
1. SE 延迟初始化（Init 不再初始化 SE，此处首次触碰；IsInited 检查 + Init）
   成功后附带 SeFirmwareInstaller::CheckAndUpgrade()（SE 固件内置升级检查）
2. HasExchangedKeyWithServer() 判出厂状态
   SE API 失败或未出厂 -> ReturnUnactivatedStatus（UNREGISTERED）
3. 已出厂 -> GetVerifiedServerDomain() 域名对齐（04 篇）
   都为空 -> 异常态按未激活处理
4. SetIotDeviceHost(domain) <- 全部 IoT 请求寻址切到专属域名
5. 补发 confirm（宽容策略，见第五节）
6. SetActivationStatus(REGISTERED) -> OnActivated 清理资源
```

## 四、Step 2~4：密钥交换链

### 4.1 Step 2 StartPalmDeviceActivation（:481-606）

- 请求体 protobuf：device_sn + hardware_info{host_sn, os=Linux, device_model, se_sn} + activation_context{app_version, rom_version} + se_keys[]（SE 全部公钥，auth_code/verify_code 首次为空由服务端返回）；
- 响应 svr_keys[]（index/public_key/auth_code/verify_code）存 server_keys_；
- **trace 串联**（story 137332527）：本次尝试首个请求不传 trace_id，网络层生成会话 trace 随响应带回，`activation_trace_id_` 持有——供后续 confirm-key-change / confirm 经 override 通道透传，三接口串成同一条激活链路（串联不受并发心跳影响）。

### 4.2 Step 3 ExchangeAndConfirmKeys（:609-732）

```text
for 每个 svr_key：
  SeKeyStore::ExchangeKeyWithServer(index, pub_key, auth_code, verify_code)
    -> (device_auth_code, device_verify_code)     <- SE 内部完成密钥协商
  GetSeDevPubKey(index) 取设备公钥，组装 exchanged_keys_info
-> POST confirm-key-change（透传 activation_trace_id_）
-> 响应 confirm_code_（服务端签发的确认凭据）
任一 key SE 交换失败 -> SE_CHIP_ERROR 整体失败
```

### 4.3 Step 4 ConfirmKeyExchangeToSE（:735-792）——激活成功的关键步骤

```text
1. SeKeyStore::ConfirmExchangeKeyWithServer(confirm_code_)   <- SE 正式固化密钥
   失败 -> SE_CHIP_ERROR
2. StoreServerDomain(server_domain)                            <- 域名落地（prop+SE）
   失败仅警告（non-critical）
3. ConfirmPalmDeviceActivation()                               <- 通知后台（非关键）
   失败仅警告
4. SetActivationStatus(REGISTERED) -> OnActivated：Reset 清临时数据 + SE 资源释放
5. ClearActivationSession()                                    <- session_id/key 不再需要
```

顺序契约（:775 注释）：Step5 必须在 SetActivationStatus 之前——后者触发 OnActivated 清掉 activation_code_，前者的 scene 取自它。

### 4.4 Step 5 SendConfirmActivationRequest（:868-905）

- 请求体 protobuf：device_sn + scene（取自激活码）；
- **DEVICE 签名**（非 ACTIVATION——confirm 是"以设备身份"的通知，start/confirm-key-change 才是激活会话身份）；
- 成功 -> MarkActivationConfirmed（Config 写 true + Flush）；
- 启动期补发时 trace 为空 -> 网络层生成新 trace（语义上是新请求）。

## 五、补发 confirm 的宽容策略（:451-468）

CheckActivationStatus 发现"SE 已出厂但 activation_confirmed 标志为 false"时补发 confirm：

| 补发结果 | 处理 |
|---|---|
| 成功 | MarkActivationConfirmed |
| HTTP 5xx 且 server_code != 0 | **视为已确认**（LOG_W + MarkActivationConfirmed）——后端明确返回业务错误，大概率是"已确认过/重复 confirm"，不反复补发 |
| 其他失败（网络/超时等） | 不置标志，下次开机再补发 |

标志为 true 时跳过。该标志在 StartActivationFromQRCode（新激活流程开始）时清除。

## 六、对外联动与接入检查清单

### 6.1 联动点

| 联动 | 说明 |
|---|---|
| Phase 回调 | NotifyActivationPhase（去重）-> PosRequestHandler SendActivationStatusChangeMsg 上报上位机（02 篇第五节） |
| DeviceFsm | OnActivationStart RequestEnter(kActivating)，被拒 -> OnError 终止（02 篇） |
| Network | SetActivationSession（激活签名上下文）/ SetIotDeviceHost（激活后寻址）/ ClearActivationSession |
| NtpTimeSync | 激活前按域名 SyncTimeWithDomain（非阻塞） |
| SeFirmwareInstaller | Step1 SE 初始化后检查内置固件升级 |
| Config | activation_confirmed 标志（补发 confirm 的依据） |

### 6.2 接入检查清单

**新增激活步骤/子步骤**：
1. 失败一律走 ActivationResult（code/server_code/error_message），error_message 由 Network 层备好最终文案（含 trace_id 尾缀），不再拼原始 response_body；
2. 需要 trace 串联的请求透传 activation_trace_id_；首个请求留空由网络层生成；
3. 临时产物（server_keys_/confirm_code_）登记进 Reset() 清理清单。

**新增激活前置条件**：
1. 评估是否需要 activation_confirmed 同款"宽容补发"语义（幂等 + 后端错误视为完成）；
2. 非关键步骤（域名落地失败、confirm 失败）显式 LOG_W + 不阻断——激活成败只由 SE 密钥链决定。

**通用红线**：
- session_key / auth_code / verify_code / confirm_code 不进日志（session_key 不落任何 LOG，key index 与长度可打）；
- SE 操作失败必须区分"未出厂"（正常）与"芯片异常"（SE_CHIP_ERROR），不可混用。

## 七、观察点

1. **补发 confirm 的宽容判据偏宽**：任何"5xx 且 server_code 非 0"都视为已确认——若后端新增一种 5xx 业务错误（真失败），会被误标 confirmed，该设备将永不补发。可考虑精确匹配已知的"已确认"码；
2. 硬编码 device_model="O4"（:519）——换机型需改代码，建议入构建配置；
3. Step2~4 无重试机制，失败即回扫码态重走全流程（SE 密钥交换幂等，重来成本低，可接受）；
4. Step4 内嵌 Step5（非关键）+ 启动期补发（宽容）双保险，confirm 语义上"至多一次生效、至少一次尝试"——后端需幂等；
5. activation_trace_id_ 持有于 service 成员——若并发两次激活流程（理论不可达：FSM 单飞）会互相覆盖 trace；Reset 时清空。
