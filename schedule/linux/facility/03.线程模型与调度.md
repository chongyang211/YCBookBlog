# Facility · 03 线程模型与调度

> 系列第三篇。覆盖线程全景、Thread 抽象与 this_thread 语义（含空指针坑）、1s 基频调度器内部机制、并发接入规约。承接《01.总览与分层架构.md》。

## 一、线程全景

运行期共有四类执行载体，**不止全局线程组的 6 个**：

| 类别 | 线程 | 职责 | 创建方 |
|---|---|---|---|
| 全局线程组 | main（kUiThread 同名别名） | 业务协程、信号处理、DeviceFsm、灯效派发 | Threads::Init |
| | network | 网络请求协程 | 同上 |
| | heartbeat | 心跳、Recover 等慢协程 | 同上 |
| | iot | IoT 服务 | 同上 |
| | ota_install | OTA 安装（重活隔离） | 同上 |
| | license | Story 136057693：激活+授权互斥共享 | 同上 |
| 调度器专属线程 | scheduler（detach） | 1s 基频 tick + kSync 任务执行 | BaseFrequencyScheduler::Start（:75-79） |
| 线程池 | iot_pool ×2 | kAsync 定时任务执行 | 同上（:66，Start 时懒创建） |
| 自持/一次性 | link 自持线程、协程内 detach | P2P 厂测、临时并发 | 各模块 |

每个全局 `Thread` = `io_context + std::thread`（thread.h:17，构造传并发数 1）；主线程特殊：`StartInCurrentThread` 在**当前线程**跑 io_context（work_guard 保活，thread.h:54-59）——进程没有独立主循环，main 线程的 io_context 就是主循环。

## 二、Thread 抽象与 this_thread 语义

**thread-local 句柄机制**（thread.cpp:10,31-39）：

```cpp
static thread_local Thread* this_thr;   // 仅 Thread::Start / StartInCurrentThread 时注册
Thread* this_thread::Handle() { return this_thr; }
```

由此得出两条硬规则：

1. **`this_thread::Post/CoSpawn` 语义 = "派发到当前代码所在的全局线程"**——代码跑在哪个全局线程，this_thread 就是谁。适合"贴着当前线程继续"的写法（如 bootstrapper 里 Post BizStart）；
2. **非全局线程组内 `this_thread` 是空指针崩溃**：iot_pool_ 工作线程、调度器线程、任何自建 std::thread 都没执行过 SetupThreadLocal，`Handle()` 返回 nullptr，`this_thread::Post` 直接解引用崩溃。**在这些线程里派发必须显式 `Threads::GlobalThread(type)->Post(...)`**。

其他要点：

- 线程名经 `pthread_setname_np` 设置（:34）——top/htop 可见 main/network/heartbeat/iot/ota_install/license，排障时按名对号；
- `ExtensibleThread`（extensible_thread.h:8）：覆写 RunCtx 可在 io_context run 前挂 plugin 初始化（plugin_ctx_handler_），全局组外的"可插拔线程"扩展点；
- 协程即 boost::asio C++20 awaitable；`Post` 收可调用对象、`CoSpawn` 收协程，全链路无回调地狱。

## 三、BaseFrequencyScheduler 内部机制

**tick 线程模型**（重要：tick 不在 main）：

```text
Start()（幂等，running_ exchange）
  → iot_pool_ = thread_pool(2)（懒创建）
  → scheduler_ctx_（专属 io_context）+ base_timer_（steady_timer 1s）
  → detach 的专属 std::thread 跑 scheduler_ctx_->run()
      │ 每 1s OnBaseTick（:88-97，末尾重挂 timer 形成循环）
      ▼
ScheduleTasks（:99-122）
  1. 拿 tasks_mutex_ 遍历 tasks_：tick_counter++；
     到期判定 (counter − initial_offset) % multiplier == 0 且 enabled
  2. 出锁后按 priority 升序排序（kCritical=0 … kLow=3，数值越小越先）
  3. DispatchTask：
     kSync      → 调度线程内同步执行（约定 ≤10ms，:127）
     kAsync     → post 到 iot_pool_（网络 IO 等可能阻塞的任务，:130-133）
     kCoroutine → 预留 TODO，当前空实现（:134-136）
```

**任务注册 API**（RegisterTask，:58-64）：name 唯一键（注册/注销/启停/改频都靠它）；`initial_offset_sec` 错峰首延迟——注释要求用随机值避免同 tick 任务扎堆；`requires_time_synced` 时间门控。

**执行层防护**（ExecuteTask，:140-159）：

| 防护 | 机制 |
|---|---|
| 时间门控 | requires_time_synced 且 `!CheckTimeSyncedOrSkipLog` → 跳过（委托 TimeStateManager::IsTimeTrusted，Story 136515343；`last_skip_log_` 60s 日志节流防刷屏） |
| 异常隔离 | try/catch：任务抛异常计 `total_failures` + LOG_E，**不打断 tick、不波及其他任务** |
| 内建统计 | 每任务记 total_executions / total_failures / total_time / max_time / min_time（TaskDescriptor :94-99） |

**动态控制**：`SetTaskEnabled`（启停不改频率）、`SetTaskMultiplier`（改频不改启停）——NTP 慢档切换、按连接态降档重试都靠这两者组合（04 篇第四节）。

消费示例：OTA 轮询（MQTT 已连 1min 档/未连 5min 档）、心跳、License 周期检查、NTP boot/periodic 同步均注册于此。

## 四、并发接入规约

1. **新任务**：默认走 scheduler 注册（倍数周期），禁止各模块自起 std::thread/自建 timer；
2. **执行模式**：重活/网络 IO 选 kAsync；调度线程内只做 ≤10ms 轻活（状态检查、Post 派发）——kSync 超时会顺延同 tick 后续任务；
3. **this_thread 可用域**：仅限全局线程组内；iot_pool_/调度线程/自建线程中必须显式 `Threads::GlobalThread(type)->Post`（第二节硬规则 2）；
4. **互斥专用线程**：需要独占线程的重流程（激活/授权、OTA 安装）用专用线程组条目，不与业务协程混跑；
5. **跨线程状态**：通过 Post 到所属线程串行化（DeviceStateMachine 单例 + 主线程串行化即此模式，device_state_machine.h:24-39），不引入新锁；
6. **palm_core SDK 回调**：统一 Post MainThread 后经 signals2 派发（palm_core_manager.h:34 注释），订阅方默认在主线程执行，禁止在订阅回调里做阻塞 IO。

## 五、观察点

1. kSync 任务"≤10ms"是约定非强制（无超时强杀）——但 TaskDescriptor 有 per-task 耗时统计可事后归因；超时任务的直接后果是**顺延同 tick 后续任务**（调度线程被占用），新增 kSync 任务需评审；
2. **调度器统计有采集无出口**：total_executions/耗时等统计存于 TaskDescriptor，但未提供查询/导出接口——若要做调度健康监控，加一个只读快照接口即可，成本很低；
3. iot_pool_ 固定 2 线程承载全部 kAsync 任务，无队列水位监控——kAsync 任务平均耗时接近其周期时会出现堆积（下游表现为任务触发间隔漂移），排查"定时任务不准点"时先想到这里；
4. LicenseThread 由激活与授权共享（互斥语义），新增第三个使用方前需重新评估互斥模型；
5. 调度器线程 detach 且无 join——Stop() 只 stop io_context + join iot_pool_，进程退出依赖 main 先于调度线程结束的时序，属可接受的进程生命周期约定，但注意不要在退出路径依赖"调度器已完全停止"。
