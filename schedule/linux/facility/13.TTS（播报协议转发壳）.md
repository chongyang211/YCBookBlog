# Facility · 13 TTS（播报协议转发壳）

> 系列第十三篇。覆盖 tts/ 模块：空壳播放接口 + custom handler 注入转发上位机播报 + 音量持久化。承接《01.总览与分层架构.md》。

## 一、定位（与表面描述不同——重要）

> ⚠️ 历史描述勘误：早期文档写的"HTTP 云端合成 + 本地缓存"**已过时**。当前实现是刻意掏空的壳——源码注释直说："播放方法：空实现，仅回调 custom_tts_handler"（tts.cpp:12-14）、"网络/缓存方法：空实现"（:91-93）。

**真实的 TTS 链路是转发给上位机播报**，模组本地不发声——与 PosLink 的设计哲学一致（上位机是人机交互面）。

| 文件 | 内容 |
|---|---|
| tts.h | 接口形状：PlayTts / PlayTtsEx（两种 beep 重载）/ PlayTtsWithBeep + 音量族 |
| tts.cpp（104 行） | 音量持久化（真实实现）+ 空壳播放 + 注入点 |

## 二、真实数据流

```text
biz 调 PlayTts(text)                          ← session_driver.cpp:417/527
  （激活成功播报、掌纹重试提示等 Wordings）        （fire-and-forget，detached）
      │
DoPlayTts（:16-23）
  空文本短路 → custom_tts_handler(code, text, speedup, volume)
      │ handler 由 biz 层注入（唯一注入方）：
      │ pos_request_handler.cpp:167
      ▼
SendTtsMsg(code, /*tip=*/"", text)  →  PosLink 消息  →  上位机 TTS 播报
```

返回值恒 0——**fire-and-forget**：模组不感知上位机是否真的播了。

## 三、唯一有真实实现的部分：音量管理

| API | 实现 |
|---|---|
| SetVolume | volume_ 内存 + **Config 持久化**（key `volume:tts`）+ FlushAsync 异步刷盘——跨重启保留 |
| GetVolume | TtsVolumeLoader 静态局部对象惰性加载（首次读 Config，默认 **0.75**，:68-79） |
| SetVolumeHandler | 动态调音钩子（场景化音量，如夜间调低） |
| GetRealTimeVolume | base × handler——实时音量，作为参数传给 custom handler |

## 四、设计模式：老框架迁移的稳定契约层

接口形状（PlayTts / PlayTtsEx / speedup / code 参数）从 wepalm SDK 时代迁移而来（与 biz 层 session.h 的迁移痕迹同款）——**保留签名、掏空实现、靠注入点接新架构**。biz 层调用代码无需感知播放方式变化。

## 五、观察点

1. **音量闭环悬空**：GetRealTimeVolume() 算出的 volume 传给 handler，但注入的 handler 调 SendTtsMsg(code, "", text) **不带 volume**（pos_request_handler.cpp:168）——模组侧音量设置与上位机播报音量未打通，volume 参数语义空转（上位机大概率自管音量）；
2. **线程契约靠惯例**：注释 "handler will be called from main thread"（tts.h:52）但实现不保证——handler 实际执行线程 = PlayTts 调用方线程；当前调用方都经主线程 CoSpawn 才成立，新调用方在其他线程会破契约；
3. DoPlayTts 的 custom_handle_before 参数（:60）从未使用——死参数；
4. 返回恒 0：播放失败（上位机离线、消息发送失败）调用方无感知——当前文案播报可接受，"必须播报"场景需扩展；
5. SetVolume 每次触发 FlushAsync——音量调节是低频操作无碍，UI 滑条连续调用会产生大量异步刷盘。
