
> 范围：`src/service/paas_shadow/`（门面 PaasShadow + 编排 PaasShadowImpl + 传输 PaasShadowClient + 缓存 PaasShadowCache + 取值抽象 DeviceSidePropertyProvider）。设备影子 = 云端与设备之间的属性双向同步机制（对标 AWS IoT Shadow）。

## 一、功能定位

| 方向 | 语义 | 例子 |
|---|---|---|
| **cloud-side（云端期望值）** | 云端下发的权威配置，设备拉取+推送双通道，ack 确认 | `palm_behavior`（刷掌行为配置）、`device_behavior`（语言/时区）、`operate_adb`、`device_debug`、`device_ops`（下载策略/自恢复开关）、识别模式 |
| **device-side（设备上报值）** | 设备状态/运行时属性上行云端 | `module_auth`（授权状态/过期时间）、`software_version`（三版本，HeartbeatService 的 Provider）、`device_ops` |

业务方通过两个信号消费：

- `CloudSidePropertyChangedSignal`：云端期望值变更（**权威配置通道**）；
- `DeviceSidePropertyRefreshedSignal`：本地上报值被云端记录纠正——订阅者只应重新加载本地缓存，**勿反向上报**（避免与云端来回覆盖；现网曾出现"缓存已是新值、内存仍是旧值、必须重启才生效"的分叉）。

常量与属性 key 见 `paas_shadow_constants.h`（scope 默认 `kScopeTypeGlobal=2` / `"global"`；palm_behavior 区分云端同步字段与本地-only 字段）。

## 二、组件分层

```text
PaasShadow（门面单例）
└── PaasShadowImpl（编排核心，独占 property_thread_）
    ├── PaasShadowClient     # HTTP 传输：diff / update / ack 四个接口（激活后可用）
    ├── PaasShadowCache      # 持久缓存（Config/MMKV）：c_data+c_ver / d_data+d_ver
    ├── DeviceSidePropertyProvider（抽象）# 设备侧取值：业务实现 GetValue，注册进影子
    └── 信号表 / PendingQueue / waiting_property_map_
```

`Schedule` 循环（property_thread_ 协程，tick 30s）驱动周期任务：PullDevice（60s）/ PullCloud（动态 60s~300s）/ SendDevice（300s）。**时间未同步门闸**：签名 HTTP 必败期跳过并节流日志。

## 三、cloud-side 下行流程（权威配置变更）

```text
双通道取新值：
  (1) HTTP diff 轮询：PullCloudSideProperties（携带本地版本索引）
      间隔自适应：默认 60s；MQTT 已连且轮询成功过至少一次 -> 300s
      （MQTT 推送为主时把拉取放稀；MQTT 断开自动回 60s 兜底）
  (2) MQTT 推送：MqttService 注册 type-6 下行 handler
      （broker 不为离线设备保留消息 -> 断线窗口内的下发靠轮询兜底）
        |
        v
ShouldProcessProperty 版本判重（两通道共用）
  - remote version <= 缓存 -> skip（云端幂等重投）
      检测 c_ver/c_data 脱节（现网死锁：云端无限重投 / 设备无限 skip）
      -> RealignCloudVersionIndexIfNeeded 重写对齐 + 补 ack
  - MQTT version==0 -> 强制处理
  v
ProcessCloudSidePropertyUpdate
  - SaveCloudSidePropertyToCache（c_data + c_ver 两次写）
  - SendCloudSidePropertyAck（确认给云端，含 error_code）
  - GetSignal(identifier) 广播 -> 业务订阅者落地：
      palm_behavior（刷掌行为配置）/ device.cpp（语言时区 / ADB / debug）
      / device_ops（下载策略、自恢复开关）/ recognition_mode_config
      注意：订阅须在 PaasShadow::Start() 之前完成，否则首次 Pull 通知丢失
        （palm_behavior.cpp 有注释强调）
```

2026-09-16 增强：MQTT 重连成功 -> 置 `cloud_pull_requested_` -> Schedule 30s tick 内立即拉 diff（断线窗口内丢失的推送不再等最长 300s；失败不回灌）。降级边界：MQTT give-up（120 次约 2h，mqtt_client.cpp:257）后阻塞于 WaitForReconnect、无 ConnectedSig，退回 60s/300s 轮询兜底（与增强前行为一致）。

## 四、device-side 上行流程

### 4.1 首次 Pull 门闸（防版本冲突）

```text
Start -> PullDeviceSideProperties（diff：本地版本 vs 云端记录）
  - 云端版本更高（本机上报成功但缓存回滚 / 同设备其他会话写入）
      -> 云端 d_data 覆盖本地 + DeviceSidePropertyRefreshedSignal
        （业务重新加载本地缓存，消除"缓存新 / 内存旧，必须重启"分叉）
  - PullDone -> device_side_pull_done_ 置位
      - InitialProviderFetch：对所有 Provider 首次取值（值变才上报）
      - FlushPendingQueue：补报 PullDone 前被暂存的写请求
```

**PendingQueue 设计**：Pull 完成前本地缓存为空，此时接受写入会上报旧版本（低于云端已存）造成冲突——未 PullDone 前写请求进 pending（key = identifier_scopeType_scopeValue，天然去重保留最后一次），PullDone 后统一 flush。

### 4.2 两种写入 + Provider 自动取值

| 写入方式 | 语义 |
|---|---|
| `UpdateDeviceSideProperty` | 批量：进 `waiting_property_map_`，随 300s（kSendIntervalSec）周期 SendDeviceSideProperties 上报 |
| `UpdateDeviceSidePropertyRealtime` | 实时：立即上报 + callback 通知结果 |

**Provider 抽象**（业务零感知同步）：

```cpp
GetValue()                    // 返回 JSON 值；在 property_thread_ 调用，须线程安全且轻量
GetIdentifier()               // 如 "software_version" / "palm_behavior" / "module_auth"
GetScopeType()/GetScopeValue()// 默认 global
GetSourceType()               // kCloudDerived（云端派生 mirror）/ kEventDriven（本地事件）/ kSystemRuntime（可定时刷新）
GetRefreshIntervalSec()       // 仅 kSystemRuntime 生效，默认 60s；0 = 不定时刷新
```

调度：PullDone 后 `InitialProviderFetch` 首次取值；kSystemRuntime 类按间隔定时刷新（`RefreshSystemRuntimeProviders`）。**值不变不上报**（去重）。现网注册者：`SoftwareVersionProvider`（heartbeat_service，60s，上报 palmapp/ROM/SE 三版本）、`PalmBehaviorProvider` 等——注册时序要求见 bootstrapper.cpp:327-331（须在 PaasShadow::Start 之前）。

## 五、可靠性设计要点

| 机制 | 针对的问题 |
|---|---|
| c_ver/c_data 版本索引 + 脱节修复（RealignCloudVersionIndexIfNeeded） | 两次 SetValue 脱节 -> 云端无限重投 / 设备无限 skip 死锁（现网事故） |
| 首次 Pull 门闸 + PendingQueue | 本地空缓存写入导致版本冲突（上报旧版本低于云端已存） |
| DeviceSidePropertyRefreshedSignal | 本地缓存被云端纠正后内存/缓存分叉（现网"必须重启才生效"） |
| HTTP 轮询兜底 + MQTT 推送加速 + 重连即拉（cloud_pull_requested_） | 推送丢失（broker 不保离线消息）与断线窗口的配置时效 |
| cloud_pull_interval 动态（60s <-> 300s） | MQTT 可靠时降低轮询成本 |
| Provider 值去重（值变才报） | 无谓网络开销 |
| 时间同步门闸 + 未同步跳过节流日志 | 签名请求必败期的空转 |

## 六、观察点

1. `UpdateDeviceSideProperty` 批量路径 300s 一个周期——时效敏感的属性必须走 Realtime 版本；
2. c_ver/c_data 为两次独立 SetValue，脱节修复是**事后补救**（stale 判定时触发）——根治需事务化单键写；
3. MQTT give-up 约 2h 盲区与 verify_record 相同（依赖轮询兜底，源码注释已声明）；
4. 业务订阅时序约束（须在 Start 前订阅 cloud-side 信号 / 注册 Provider）靠注释约定，无运行时防护；
5. recognition_mode_config.cpp:129 的实测教训：误订 device-side refresh 信号导致云端切换后设备毫无反应——cloud 期望值订阅一律用 `GetSignal(identifier)`。
