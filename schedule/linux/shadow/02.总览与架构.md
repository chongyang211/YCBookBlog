# PaasShadow 设备影子 · 总览与架构

> 系列入口：本篇是影子模块的总览，分主题细节见同目录 02~05。
> 范围：`src/service/paas_shadow/` + bootstrapper 启动时序 + 消费方信号订阅。

## 一、定位：云端与设备的属性双向同步

设备影子（对标 AWS IoT Shadow）解决一个问题：**设备与云端各自持有属性副本，双向收敛到一致**。两个方向语义完全不同：

| 方向 | 语义 | 权威方 | 例子 |
|---|---|---|---|
| **cloud-side**（云端期望值） | 云端下发的**权威配置**，设备是执行方 | 云端 | `palm_behavior`（刷掌行为配置）、`device_behavior`（语言/时区）、`operate_adb`、`device_debug`、`device_ops`（下载策略/自恢复开关）、识别模式 |
| **device-side**（设备上报值） | 设备状态/运行时属性的**事实上报**，云端是记录方 | 设备 | `module_auth`（授权状态/过期时间）、`software_version`（app/ROM/SE 三版本）、`device_ops` |

属性以 `(identifier, scope_type, scope_value)` 三元组定位，默认全局 scope（`kScopeTypeGlobal=2` / `"global"`）。

业务方通过两个信号消费变更——**选错信号是本模块最常见的接入错误**（见 observation 5 与 05 篇）：

| 信号 | 语义 | 订阅者应该做 |
|---|---|---|
| `CloudSidePropertyChangedSignal` | 云端下发的**期望值变更**（权威配置变更） | 应用新配置 |
| `DeviceSidePropertyRefreshedSignal` | 设备侧**已上报值**的本地缓存被云端记录纠正 | 仅重新加载本地缓存，**勿反向上报**（避免与云端来回覆盖） |

## 二、组件分层

```text
PaasShadow（门面单例，paas_shadow.h）
└── PaasShadowImpl（编排核心，paas_shadow_impl.h，独占 property_thread_）
    ├── PaasShadowClient      # HTTP 传输：GetDeviceSidePropertiesDiff / UpdateDeviceSideProperties
    │                         #           / GetCloudSidePropertiesDiff / AcknowledgeCloudSideProperty
    ├── PaasShadowCache       # 持久缓存（Config/MMKV）：c_data+c_ver（cloud）/ d_data+d_ver（device）
    ├── DeviceSidePropertyProvider（抽象，property_provider.h）# 设备侧取值：业务实现，注册进影子
    ├── 信号表                # 按 identifier 的 CloudSidePropertyChanged / DeviceSidePropertyRefreshed
    ├── PendingQueue          # PullDone 前暂存的写请求
    └── waiting_property_map_ # 批量写缓冲
```

线程模型：

| 线程 | 职责 |
|---|---|
| `property_thread_`（Impl 独占） | Schedule 循环、pull/push/ack、Provider 取值、信号广播 |
| MQTT 线程 | cloud-side 推送到达 → 仅 post 转移，不在 MQTT 事件循环做重活 |
| 调用方线程 | 门面 API（Get/Update/Register）——Provider.GetValue 须线程安全且轻量 |

## 三、Schedule 循环与周期任务

`Schedule` 协程（tick 30s）驱动三个周期任务；**系统时间未同步则整轮跳过**（签名 HTTP 必败，跳过日志有节流）：

| 任务 | 周期 | 说明 |
|---|---|---|
| PullDeviceSideProperties | 60s 固定 | device-side diff：取云端版本差，本地落后则被覆盖（详见 03 篇） |
| PullCloudSideProperties | **动态 60s ↔ 300s** | cloud-side diff；MQTT 已连且轮询成功过至少一次 → 300s（推送为主，拉取放稀），否则 60s 兜底（详见 02 篇） |
| SendDeviceSideProperties | 300s | 批量上报 `waiting_property_map_` 缓冲的写入（详见 03 篇） |

附加触发：MQTT 重连成功 → 置 `cloud_pull_requested_` → 下一 tick 立即拉 cloud diff（降级边界：MQTT give-up 约 2h 后无信号，退回轮询兜底）。

## 四、生命周期与时序约束（bootstrapper）

```text
静态初始化阶段        各业务模块 Init（含信号订阅、RegisterProvider）
        │                 ⚠️ 必须全部先于 PaasShadow::Start()——否则首次 Pull 的
        │                    变更通知/Provider 首报丢失（palm_behavior.cpp:268 注释）
        ▼
BootStrapper
  ├─ ...（providers 统一注册段，bootstrapper.cpp:327-331：PalmBehaviorProvider /
  │      HeartbeatService::RegisterProviders 等，私有化部署 PALM_PRIVATE_DEPLOY 下影子整体禁用）
  ├─ PaasShadow::Init()      仅建缓存
  ├─ PaasShadow::Start()     激活后启动网络同步（HTTP + MQTT type-6 handler 注册）
  ▼
Schedule 循环运行，直到进程退出
```

三条时序铁律（违反即丢首报/丢通知，均靠注释约定、无运行时防护）：

1. 信号订阅先于 `Start()`；
2. Provider 注册先于 `Start()`；
3. 设备侧写入在首次 PullDone 前会被暂存（PendingQueue，详见 03 篇），不丢但延迟。

## 六、观察点

1. 批量写路径最长 300s 延迟——时效敏感属性必须走 `UpdateDeviceSidePropertyRealtime`；
2. c_ver/c_data 两次独立 SetValue 非事务，脱节靠 stale 判定时的事后修复（详见 04 篇）；
3. MQTT give-up（约 2h）盲区：重连加速与 verify_record 同款边界，退回轮询兜底；
4. 时序约束无运行时防护，全靠注释与新接入者自觉（05 篇检查清单兜底）。
