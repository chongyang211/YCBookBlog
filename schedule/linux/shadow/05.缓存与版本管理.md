# PaasShadow · 缓存与版本管理

> 系列第四篇。`PaasShadowCache`（paas_shadow_cache.h/.cpp）是影子的持久层：独立 `Config::CreateStandalone("paas_shadow")` 实例（MMKV），为 cloud/device 两侧维护"数据 + 版本索引"四类键。本篇覆盖键设计、版本语义、脱节事故复盘与调试手段。

## 一、键设计（四类键）

每条属性以 `(identifier, scope_type, scope_value)` 定位，展开为两个键：

| 前缀 | 键格式 | 内容 | 作用 |
|---|---|---|---|
| `c_data:` | `c_data:{id}_{scope_type}_{scope_value}` | CloudSideProperty 完整 JSON（值+版本+三元组） | cloud-side 属性值本体，`GetCloudSideProperty` 的读取源 |
| `c_ver:` | 同上格式 | 轻量 JSON：`{property_identifier, scope_type, scope_value, property_version}` | **版本索引**：diff 请求（GetCloudSidePropertyVersions 遍历）与判重的快速通道 |
| `d_data:` | 同上格式 | DeviceSideProperty 完整 JSON | device-side 属性值本体 |
| `d_ver:` | 同上格式 | 同 c_ver 结构 | device-side 版本索引 |

版本索引单独成键的理由（源码注释）：**diff 请求只需版本号**——遍历全量 c_data 反序列化成本高，索引扫描轻。

## 二、写入与版本语义

```text
SaveCloudSidePropertyToCache / SaveDeviceSidePropertyToCache
  ├─ SetValue(c_data, 完整 JSON)        ← 写 1
  └─ SetValue(c_ver,  版本 JSON)        ← 写 2（独立调用）
```

**两次独立 SetValue，非事务**——这是本模块唯一已知的现网事故根源（第三节）。

版本号语义（与云端 diff 协议对齐）：

| 值 | 语义 |
|---|---|
| 递增整数 | 正常版本演进，diff 按此判断设备落后/领先 |
| MQTT 推送 version == 0 | 强制处理（跳过判重，02 篇） |
| 本地无键 | 视为 kVersionDefault（首次） |

device-side 版本的另一层作用：**本地写入前须保证不低于云端已存版本**——这正是首次 Pull 门闸（03 篇）存在的原因：空缓存时无从得知云端版本，盲目写入会回退版本。

## 三、脱节死锁事故复盘（c_ver 落后于 c_data）

### 3.1 症状

云端配置反复下发，设备始终不生效。

### 3.2 根因

`SaveCloudSidePropertyToCache` 两次写之间非原子。现网出现 **c_data=v5、c_ver=v4**：

```text
云端视角：c_ver=v4 < v5 → "设备落后"，无限重投 v5
设备视角：c_data 判重，v5 已存在 → 无限 skip
→ 双方僵持，属性永不生效且无法自恢复（任何一轮重投结果相同）
```

### 3.3 检测：IsCloudVersionIndexAligned（cache.cpp:120-149）

- 读 c_ver：**缺失或空 → false**（索引丢失同样触发 realign）；
- 解析失败 → false；
- `j.value("property_version", -1)`：**缺字段取 -1**——注释明示"不可能与合法版本相等，必然触发 realign"（哨兵值设计）；
- 与 c_data 的 property_version 不等 → false（脱节）。

### 3.4 修复：RealignCloudVersionIndexIfNeeded（impl 层）

- **仅在属性被判 stale 时调用**（判重 skip 分支）——正常路径零开销；
- 索引已一致 → 纯云端幂等重投，直接返回；
- 索引落后 → 重写 c_ver 对齐 c_data 版本 + **补发 ack**（让云端知道设备已消费，终止重投）；
- HTTP 轮询与 MQTT 推送两条路径共用同一入口。

### 3.5 根治方向（未实施）

两次写改**事务化单键写**：把版本内嵌进 c_data 一个键（diff 需要版本时遍历解析），或 MMKV 层提供多键原子写。当前"事后修复"已在 stale 路径覆盖了死锁窗口，代价是每次 stale 多一次索引读写。

## 四、版本扫描（diff 请求的数据源）

`GetCloudSidePropertyVersions / GetDeviceSidePropertyVersions`：

- 遍历 `AllKeys()`，按 `c_ver:` / `d_ver:` 前缀过滤；
- 解析每个索引 JSON → `{identifier, scope_type, scope_value, property_version}` 数组；
- 单键解析失败 LOG_E 跳过（坏索引不阻塞其余属性同步）；
- 非空时打一行汇总日志（`[id_scope,(v)]` 格式），排查 diff 行为时先看这行。

⚠️ 扫描成本随属性数线性增长（AllKeys + 逐键读），当前属性个位数无感知；属性规模上来后可考虑内存索引。

## 五、调试手段

| 手段 | 内容 |
|---|---|
| `Dump()` | cloud 侧逐条打印 `值 (c_data v{n}, index aligned/OUT-OF-SYNC)`——**脱节直接可见**（cache.cpp:316-322 注释：dump 中必须能直接看出，否则只能翻日志）；device 侧打印值+版本 |
| `GetTotalKeys / GetAllKeys / ClearAll` | 键数/全键/清空（debug 页与测试用；ClearAll 后需重新 Pull，否则触发首次 Pull 门闸语义） |
| 版本汇总日志 | 每次取版本索引时输出（见第四节） |

## 六、观察点

1. **非事务双写是结构性弱点**：Realign 已兜住 stale 路径，但理论上 c_ver 写成功而 c_data 写失败（反向脱节：索引超前）目前**无检测**——索引超前时 diff 不报差异、c_data 读旧值，症状是"设备版本号新但值旧"；量级概率极低（MMKV 单写失败罕见），但根治需事务化单键写（第三节 3.5）；
2. `GetCloudSidePropertyFromCache` 打印完整属性值（LOG_I）——cloud 属性含行为配置，注意日志量与敏感度；
3. `ClearAll` 无保护——仅限 debug 页使用，运行期误调会触发整轮重新 Pull + 属性重新生效流程；
4. `Config::CreateStandalone("paas_shadow")` 独立实例与主 Config 隔离——影子缓存损坏不会污染其他配置域，反之亦然。
