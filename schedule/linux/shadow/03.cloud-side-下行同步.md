# PaasShadow · cloud-side 下行同步

> 系列第二篇，承接《01.总览与架构.md》。cloud-side 属性是**云端权威配置**（palm_behavior / device_behavior / operate_adb / device_debug / device_ops / recognition_mode），本篇覆盖它如何到达设备并生效，以及"云端改了配置但设备没反应"的排查路径。

## 一、双通道取新值

```text
通道 ① HTTP diff 轮询（兜底 + 兜精度）
  PullCloudSideProperties：携带本地版本索引（GetCloudSidePropertyVersions）
  → 云端返回有差异的属性 → 逐条走"版本判重 → 处理 → ack"
  间隔自适应（UpdateCloudPullIntervalSec，impl.cpp:99-102）：
    默认 60s（kPullIntervalSec）
    MQTT 已连 且 HTTP 轮询成功过至少一次 → 300s（kPullIntervalSecMqtt，推送为主拉取放稀）
    MQTT 断开 → 自动回 60s

通道 ② MQTT 推送（低延迟）
  MqttService 注册 type-6 下行 handler（MESSAGE_TYPE_DOWN_CLOUD_SIDE_PROPERTY，impl.cpp:218-222）
  到达即转移 property_thread_ 处理，同一套"版本判重 → 处理"管线
  ⚠️ broker 不为离线设备保留消息——断线窗口内的下发只能靠轮询兜底
```

两通道共用 `ShouldProcessProperty` 判重与 `ProcessCloudSidePropertyUpdate` 处理管线，行为完全一致。

## 二、版本判重（ShouldProcessProperty）

| 情形 | 判定 | 动作 |
|---|---|---|
| remote version > 缓存版本 | 新配置 | 进入处理管线 |
| remote version <= 缓存版本 | skip（云端幂等重投） | 先查 `IsCloudVersionIndexAligned`：c_ver 与 c_data 脱节 → 触发 Realign（见第三节）；索引一致 → 直接跳过 |
| MQTT 推送 version == 0 | **强制处理** | 不判重（推送协议的特殊语义） |

`out_old_version` 用于信号广播（无缓存条目时为 kVersionDefault）。

## 三、c_ver / c_data 脱节死锁（现网事故专题）

**背景**：缓存每条 cloud 属性写两个键——`c_data`（属性值+版本）与 `c_ver`（版本索引，供 diff 请求携带）。两次独立 `SetValue` 非事务，现网出现过 **c_data 已是 v5 而 c_ver 仍是 v4** 的脱节（paas_shadow_cache.h:28-36 注释）。

**死锁机理**：

```text
云端按 c_ver 判断"设备落后" → 无限重投 v5
设备按 c_data 判重           → v5 已存在，无限 skip
→ 属性永远无法生效且无法自恢复
```

**修复（RealignCloudVersionIndexIfNeeded，仅 stale 判定时触发）**：

- 索引已一致 → 说明确实是云端重投，直接返回（无害）；
- 索引落后 → 重写缓存对齐版本 + 补发 ack，打破死锁；
- HTTP 轮询与 MQTT 推送两条路径共用。

> 根治思路（未实施）：c_data/c_ver 事务化单键写。见《04.缓存与版本管理.md》。

## 四、处理管线（ProcessCloudSidePropertyUpdate）

```text
ProcessCloudSidePropertyUpdate(remote, old_version)
  1. SaveCloudSidePropertyToCache        # c_data + c_ver
  2. SendCloudSidePropertyAck            # 确认给云端（identifier/scope/version/error_code/error_msg）
  3. NotifyCloudSidePropertyChanged      # GetSignal(identifier) 广播
       → (identifier, scope_type, scope_value, value, old_version, new_version)
```

业务订阅方（**必须在 PaasShadow::Start() 之前订阅**，否则首次 Pull 通知丢失）：

| 订阅者 | identifier | 落地动作 |
|---|---|---|
| `palm_behavior.cpp:270` | `palm_behavior` | 刷新刷掌行为配置（PalmBehavior::Config）+ 重启恢复语义 |
| `device.cpp:527` | `device_behavior` | 语言/时区切换 |
| `device.cpp:546` | `operate_adb` | ADB 开关 |
| `device.cpp:627` | `device_debug` | debug 配置（zerus_id） |
| `device.cpp:669` | `device_ops` | OTA 下载策略 / 自恢复开关 |
| `recognition_mode_config.cpp:131` | recognition mode | 识别模式切换（⚠️ 该文件 :129 教训：曾误订 device-side refresh 信号导致云端切换后设备无反应） |
| `palm_behavior.cpp:282` | `palm_behavior`（device-side refresh） | 供订阅对照的"正确用法"示例：仅重载缓存，不反向上报 |

## 五、重连加速与降级边界（2026-09-16 增强）

```text
MQTT 重连成功（ConnectedSig）
  → cloud_pull_requested_.store(true)
  → Schedule 下一 tick（≤30s）消费：exchange(false) 后无条件 PullCloud
     （失败不回灌——由既有间隔或下一次重连再触发）
```

**降级边界**：MQTT give-up（120 次重试 ≈ 2h，mqtt_client.cpp:257）后阻塞于 `WaitForReconnect()` 停止出站，仅由 NetworkMonitorService 在**链路态跳变**时唤醒。故断网 ≥约 2h 且链路态无跳变（门店上游宽带故障、整夜断网）时，恢复后不再有 ConnectedSig → 加速不生效，退回 60s/300s 轮询兜底（与增强前行为一致，配置最终仍会到达）。

## 六、排查指引："云端改了配置，设备没生效"

按序核对：

1. **时间同步**：Schedule 有时间门闸，未同步整轮跳过（查日志 skip 节流记录）；
2. **激活状态**：影子网络同步在激活后启动（Start 前置）；
3. **订阅时序**：业务是否在 `PaasShadow::Start()` 前完成 `GetSignal(identifier).connect`——晚了丢首次 Pull 通知（后续变更仍能收到）；
4. **信号选型**：是否误订 `GetDeviceSideRefreshSignal`（cloud 配置必须订 `GetSignal`，recognition_mode 教训）；
5. **版本卡死**：日志中同一版本反复到达但无处理 → 疑似 c_ver/c_data 脱节（正常应被 Realign 自愈，若 Realign 亦失败需查 MMKV 健康）；
6. **长断网**：>2h 断网 + 无链路跳变场景属已知降级边界（第五节），配置会在下一轮询周期（最长 300s）到达。
