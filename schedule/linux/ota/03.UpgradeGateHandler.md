`UpgradeGateHandler` 是 **OTA“建议升级（ADVICE）”的用户确认关卡**——对应 OTA 全流程图中【关卡】环节，位于下载完成之后、安装开始之前。

## 它解决的问题

后台下发的升级任务有三种模式（`upgrade_mode`）：

| 模式 | 语义 | 过不过关卡 |
|---|---|---|
| FORCE / ATONCE | 强制/立即升级 | 不问，直接装 |
| **ADVICE** | **建议升级** | **必须先问用户"升不升级"** |

ADVICE 是“温和升级”：包下载好了，但不能静默安装，要先经上位机弹窗征求用户同意——这个“问 + 等回复 + 分流”的流程就封装在 `UpgradeGateHandler` 里（story 136589242）。

## 核心机制：0xB3 双向询问

```
模组 ──0xB3（task_id + version + changelog + timeout=10s）──► 上位机弹窗
上位机 ──回复 user_choice──► 模组
    0x01 Approve（同意） / 0x02 Reject（拒绝） / 0x03 Timeout（超时兜底）
```

模组侧 10s 兜底超时（`kNotifyTimeoutSec`）：上位机倒计时以 `timeout_seconds` 字段为准，但模组自己也有 `operator||` 竞速的 timer——**SDK 崩溃/冻结时只有模组能自保**，超时合成 Timeout 走兜底安装。

## 六种情形的裁决表（HandleAdviceGate 核心）

| # | 情形 | 结果 | 记冷却 |
|---|---|---|---|
| 1 | 非 ADVICE（FORCE/ATONCE） | 直接放行 | — |
| 2 | 冷却窗内（同 task_id+version 60min 内已拒绝过） | 静默跳过 | — |
| 3 | gate 未注入（上位机从未连接） | 兜底安装（FR-3.3，视作 UPGRADE_NOW） | 否 |
| 4 | 回复 131（老上位机不认识 0xB3） | **降级为 FORCE 静默安装**（FR-6.1） | 否 |
| 5 | 链路失败（send_result≠0） | 本轮跳过，下轮重试 | 否 |
| 6 | Approve / **Timeout** | 进入安装 | 否 |
| 7 | **Reject** | 跳过 + **记 60min 冷却** | **是** |

三个设计要点：

1. **冷却 KV 持久化**（`advice_cd::<task_id>::<version>` → Config）：拒绝后 60min 内不重复弹窗——轮询最快 1min 一轮，没有冷却会每分钟弹一次窗骚扰用户；持久化到 Config 保证重启不丢。注：`IsInCooldown` 也供 Filter 阶段前置过滤（冷却期内连下载都省了）；
2. **Timeout 也安装**（FR-3.3）：用户不回应 10s 后视为默许兜底安装——建议升级不能因为用户不看弹窗就永远不装；
3. **老上位机兼容**：回复 131 = 不支持 0xB3，自动降级 FORCE，保证升级不被卡死。

## 与 IotUpgradeSchd 的关系

```
IotUpgradeSchd（编排器）
   │  SetAdviceGate(gate_fn)      // 注入 0xB3 发送函数（真正的 PosLink 收发在外部）
   ▼
advice_gate_（本类）
   └─ HandleAdviceGate(downloaded_tasks)   // 下载完成后、安装前调用（主线程协程）
        └─ co_return kept_tasks            // 幸存任务进入安装流程
```

从编排器**抽离成独立类**的原因（头文件注释）：保持 schd ~200 行不膨胀、冷却 KV/Mutex 契约不外泄、ADVICE 行为改动只碰一个类。注意安装过程状态（Installing/Success/Failed/Rebooting）**不归它管**——走常规 0xA6 通道。

**一句话总结**：`UpgradeGateHandler` = ADVICE 建议升级的“用户同意关卡”——对应 OTA 里“下载完先问用户装不装”这一环，核心是 0xB3 询问 + 10s 兜底 + 老上位机降级 + 拒绝后 60min 冷却，保证“建议升级”既尊重用户意愿又不会被无限搁置。
