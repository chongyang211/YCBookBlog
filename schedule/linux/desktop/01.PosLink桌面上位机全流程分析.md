# PosLink 桌面上位机 · 01 全流程分析

> 系列入口见《README.md》。本篇是快速通读：跟踪一次「连接 → 握手 → 刷掌识别」从 UI 点击到串口字节、再从模组推送回到屏幕的完整调用链。分层细节与组件表见《02.总览与架构.md》。

## 一、全景调用链

```text
Renderer (React Hook)          Main (Electron)              Bridge Worker           C API (dylib/dll)
────────────────────           ───────────────              ─────────────           ─────────────────
usePosLinkConnect
  │ window.posLink.init()
  │ window.posLink.connect()
  │ window.posLink.sendHandshake()
        │ preload contextBridge          PosLinkBridge            bridge-worker           pl_* 导出
        ├─ ipc invoke ──────────────►  ipc/pos-link.handler
        │                               │ bridge.request()  ──►  消息循环 (串行)
        │                               │                      │ koffi 声明  ──────►  pl_client_create
        │                               │                      │                      pl_connect_serial
        │                               │                      │                      pl_send_handshake
        │                               │                      │                            │ 封送 → pos_link 核心
        │                               │                      │                            │   ↕ Asio io 线程
        │                               │                      │                            │ 串口 0x7E 帧 ──► O41 模组
        │                               │                      │  ◄── box 捕获响应 ────────┘
        │                               │  ◄─ {id, result} ────┘
        │  ◄─ Promise resolve ──────────┘
  ▼
useVerifyProcess (0xA3 推送走反向事件流)
        ◄─ webContents.send ────────── PosLinkBridge.onPush ◄─ worker 事件消息 ◄─ pl_push_callback ◄─ 0xA3
```

关键分工：**渲染层只发语义请求**；串口链路、FFI、回调全部收敛在 Main 进程与 worker 子进程；每层只依赖下一层的 Promise / 事件接口。

## 二、连接流程（逐步）

以 Home 页选择串口点击「连接」为起点，入口 `hooks/usePosLinkConnect.ts` 的 `connect()`，状态梯 `idle → connecting → handshaking → ready`。

| 步 | 渲染层 | 跨进程 | Main / Worker | C API 层 |
|---|---|---|---|---|
| 1 | `window.posLink.init()` | IPC `poslink:init` | `PosLinkBridge.init()`：fork utilityProcess → 等 `worker-ready`（10s 超时）→ 把主进程解析好的库绝对路径经 `init{libPath}` 传入 | worker 内 `koffi.load()` dlopen + `pl_abi_version()` |
| 2 | — | — | ABI 校验：`pl_abi_version() === 期望值`，不匹配 → 拆掉 worker，抛结构化 `abi-mismatch: reported=N expected=M` | — |
| 3 | `window.posLink.create()` | `poslink:create` | worker 执行 `pl_client_create`，并在此刻注册 push / 连接状态转发回调；主进程安装事件 tap | 句柄创建 |
| 4 | `window.posLink.connect(path, baud)` | `poslink:connect` | worker `pl_connect_serial`（阻塞调用，worker 串行消费消息所以安全）→ 主进程侧返回 `{rc}` | 成功后 spawn Asio io 线程驱动核心 |
| 5 | `window.posLink.sendHandshake({protocolVersion:0x0201, minProtocolVersion:0x0200})` | `poslink:sendHandshake` | worker `pl_send_handshake`，box 模式捕获异步响应 → Promise 回填 | 核心发 0x0201 帧，10s 超时等 0x0200 |
| 6 | `window.posLink.sendQueryInfo()` | `poslink:sendQueryInfo` | 同上，`pl_send_query_info` | 0xA0 → 模组 JSON 信息透传 |
| 7 | `parseDeviceInfo(infoRaw)` 渲染设备面板；phase=`ready` | — | — | — |

设计约束：**握手时机由 shell（bridge/worker 层）约定，业务层不自行决定何时握手**——`connect()` 后紧跟的 `sendHandshake` 是渲染层状态梯的固定梯级（协议 0x0201/0x0200）。

失败分支（在 `connect()` 内统一收敛）：

| 现象 | 判定位置 | 结果 |
|---|---|---|
| ABI 版本不匹配 | 步 2，Main | `AppError{kind:'abi-mismatch'}` → 终态 ErrorModal，提示重装 |
| 握手被模组拒绝（ret_code 130/131/132/134） | 步 5，渲染层 `fromHandshakeRetCode` | `kind:'incompatible'` 弹窗 + **自动 disconnect**，保证下次从干净链路开始 |
| 握手超时 / IO / 协议错 | 步 5，`fromPlStatus` | 普通 error banner |
| 串口权限拒绝（EACCES） | 步 4，`refineSerialPermission` | 专用 macOS 隐私与安全性设置指引文案 |
| 链路自发断开（拔线） | 连接状态回调，任何梯级 | `lostLink=true`、塌缩回 idle，Home 路由到 `/disconnect` 专页一键重连 |

自愈设计：渲染层 reload 后 React 状态归 idle，但串口链路活在 Main 进程——hook 挂载时探测 `isConnected`，存活则直接跳 `ready` 并补拉设备信息；路由守卫必须等 `hydrated` 落地再判定 `phase==='idle'`，否则 /verify 页 reload 会被误弹回首页。

## 三、识别流程（逐步）

入口 `hooks/useVerifyProcess.ts`（/verify 页），状态机：

```text
idle ──Start──▶ starting ──ret=0──▶ scanning ──0xA3 匹配且识别成功──▶ result-success
                  │                  │
                  │ ret≠0 / IPC 错   ├─ Cancel ──▶ cancelling ──▶ idle
                  ▼                  ├─ 0xA3 ret≠0 / 类型不符 ──▶ result-failure
              result-failure         └─ 0xA3 session 不符 → 丢弃 + warn（留在 scanning）
```

**正向链路**：

1. `start()` 发 `sendStartPalm({bizType: 0x0001})`，同表走的仍是「IPC → bridge → worker → `pl_send_start_palm`」一条路；同步 ref 镜像 `st.current.phase` 做重入保护（连点防护：setState 与 effect 刷帧之间的一拍间隙也会拦下）。
2. 响应 `retCode===0` 取出 `sessionId` 记入 ref，进入 `scanning`。
3. 模组完成识别后推 **0xA3**：`pl_push_callback`（io 线程）→ worker 内**同步拷贝**载荷物化为 JS 值（C 指针绝不逃逸回调）→ 事件消息 `{event:'push', type, payload}` → 主进程事件 tap → `webContents.send` 广播 → 渲染层 `onPush` 消费。

**0xA3 消费的三道闸门**（`useVerifyProcess` 订阅回调内）：

| 闸门 | 规则 | 不通过时 |
|---|---|---|
| 阶段闸 | 仅 `scanning` 态消费 | 带外推送直接忽略 |
| session 严格匹配 | `push.sessionId !== 当前 sessionId` 丢弃 | warn 日志，留在 scanning（模组可能推上个会话的残留） |
| recognize_type 守卫 | result_data 解析后非识别类型（如录入/扫描配置错） | `result-failure`（retCode=-2），**绝不渲染为成功** |

成功路径：`parseResultData` 做 UTF-8 正确解码（避免中文用户名 mojibake），**白名单拷贝身份字段**（user_id/user_name/palm_id/palm_direction/message），凭证字段（session_key/otc/server_code）在解析期即被丢弃——组件结构性无法拿到，也不落日志（日志只有 ret_code + session 短哈希）。

**取消与清理**（D-9/A-9）：

- `cancel()`：发 StopPalm 但**不等待响应**，UI 立即回 idle；1s 容忍定时器兜底慢模组；
- 扫描中卸载页面：unmount 自动补发 StopPalm（fire-and-forget）；
- 链路丢失：`connected=false` 时 scanning/starting 直接塌缩回 idle；
- 无 UI 级扫描超时（D-8）：会话超时归模组管，由模组推终态 0xA3。

## 四、贯穿全程的三条横切机制

### 4.1 请求-响应：Promise RPC over 消息通道

所有请求走同一条 `{id, method, params}` → `{id, result|error}` 通道。主进程 `PosLinkBridge.request()` 用 pending Map + 单次 message 监听配对；worker 单线程串行消费（与 C API「同一句柄回调不可重入、`pl_send_*` 阻塞 10s」的语义天然契合）。worker 异常退出：reject 全部 pending → **一次性重生**（重新 fork + 重新 init），第二次死亡报 error 放弃。

### 4.2 事件：推 / 连接状态反向流

| 源 | 触发 | 传播路径 | 渲染层消费 |
|---|---|---|---|
| 0xA1 模组状态 | 模组推送 | callback → worker 事件 → tap → 广播 | `usePosLinkConnect` 更新状态条 |
| 0xA3 识别结果 | 识别完成 | 同上 | `useVerifyProcess` 三道闸门 |
| PlConnState | 连接状态机 | 同上 | 拔线判定（userInitiated 区分主动断开与自发断开） |
| debug:onTraffic | 每个请求 | handler 附加回显（cmd/rc/耗时/响应摘要截断 200 字符） | /debug 实时流量环形缓冲（300 条） |

### 4.3 错误：统一 AppError 模型

三层错误在渲染层收敛为 `AppError{kind, code, i18nKey, detail}`（`lib/errors.ts`）：

- C API 层 `PlStatus`（成帧层错误：-1 参数 / -2 未连接 / -11 超时 / -13 模组拒绝…）→ `fromPlStatus`；
- 协议层 ret_code（各响应结构体内部，位宽按命令区分 u16/u32）→ `fromHandshakeRetCode` 等；
- IPC / bridge 层异常（worker 死亡、abi-mismatch）→ `fromAbiMismatch` / `fromUnknown`。

UI 只按 `kind` 决定呈现形态：`incompatible` / `abi-mismatch` / `preflight` 三类必弹终态 ErrorModal，其余 banner / toast；文案一律走 `i18nKey`（en/zh/ja/pt 四语言，`en.ts` 为权威，缺 key 是编译错误）。

## 五、一次识别的字节级时序（示例）

```text
UI 点击连接
  → poslink:connect            pl_connect_serial        串口打开
  → poslink:sendHandshake      0x0201 ──►  ◄── 0x0200   版本协商
  → poslink:sendQueryInfo      0x00A0 ──►  ◄── 0xA0     设备信息 JSON
  UI 进入 ready，状态条随 0xA1 推送实时刷新
UI 点击开始验证
  → poslink:sendStartPalm      0x0004 ──►  ◄── 0x04     ret=0, session_id
  用户刷掌 …
                               ◄── 0xA3 push            识别结果（base64 JSON，14 字段透传）
  三道闸门 → 白名单解析 → result-success 卡片
UI 点击取消（或离开页面）
  → poslink:sendStopPalm       0x0005 ──►  ◄── 0x05     UI 先回 idle，1s 容忍
```

指令码与帧格式以模组侧《poslink协议文档-用户版.md》与《04.上行指令帧字典.md》为准；C API 结构体与 ret_code 位宽以 `pos_link/c_api/include/pos_link_c_api.h`（冻结头）为唯一事实源。
