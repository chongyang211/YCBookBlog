# 07. 业务流程与状态机

> 系列第七篇。覆盖 renderer 业务层的两个状态机（连接梯 `usePosLinkConnect`、识别流程 `useVerifyProcess`）、行为读写（`usePalmBehavior`）、统一错误模型（`AppError`）、模组 ret_code 映射（`lib/ret-codes.ts`）与日志导出管道。承接《06.IPC与进程模型.md》——06 讲"通道怎么走"，本篇讲"业务在通道上如何推进与收敛"。端到端速览见《01.上位机全流程分析.md》。

## 一、业务层组成

| 文件 | 状态机/职责 | 消费的 ABI 面 |
|------|------------|--------------|
| `hooks/usePosLinkConnect.ts` | 连接梯（5 phase） | init / connect_serial / handshake / query_info / disconnect / onConnectionState / onPush(0xA1) / isConnected |
| `hooks/useVerifyProcess.ts` | 识别流程（6 phase） | start_palm / stop_palm / onPush(0xA3) / last_error |
| `hooks/usePalmBehavior.ts` | 行为读写（无状态机，写-回读闭环） | set_palm_behavior / query_palm_behavior |
| `lib/errors.ts` | AppError 统一错误模型（fromXxx 构造器族） | —（分类 PlStatus 与握手 ret_code） |
| `lib/ret-codes.ts` | 模组 ret_code → i18n 文案映射 | — |
| `lib/forward-logs.tsx` | 渲染层 console + 未捕获异常转发 | forwardLog |

三个 hook 均由 `PosLinkProvider`（layout 根）挂载一次、页面经 `usePosLink()` 共享同一实例——串口链路活在主进程，renderer 状态不跨导航存活，单实例是"页面间看到同一连接"的前提（PosLinkProvider.tsx 头注释）。

## 二、连接梯（usePosLinkConnect）

### 2.1 状态梯与迁移

```text
idle ──connect()──▶ connecting ──串口开成功──▶ handshaking ──握手通过──▶ ready
  ▲                    │                          │                        │
  │   init 失败/串口失败│        版本被拒(130/131/132/134) │                │ disconnect()
  │   ──────自动断线────┘        → incompatible + 自动断线 │                ▼
  │                                                        └───────── disconnecting ──▶ idle
  ◀──────────────── 链路自发断开（任意运行档）: lostLink=true + 塌缩到 idle ─────────────────
```

| 运行档 | 职责 | 失败处理 |
|--------|------|----------|
| connecting | `pl_connect_serial` 打开串口 | rc≠0 → `lastError()` 取详情 → `fromPlStatus` + `refineSerialPermission`（权限拒绝给专用文案，R-5）→ idle |
| handshaking | **shell 自动发起协议握手**（0x0201/0x0200，D-7——业务层无权决定何时握手）| 线缆层拒绝（ret_code 130/131/132/134）→ `fromHandshakeRetCode` → **incompatible**；传输层失败（超时/IO）→ `fromPlStatus`；两者都**自动断开**再回 idle（下一轮从干净线缆开始） |
| ready | QueryInfo 拉设备信息（一次）+ 0xA1 推送持续刷新 moduleState | — |
| disconnecting | 用户主动断开（覆盖"握手中点断开"：pending 握手的迟来结果因 phase 已离开梯顶而被丢弃，T4.4） | finally 归 idle |

### 2.2 三个机制设计

1. **ladder 镜像 ref**：连接状态回调跑在主进程事件桥上，而 phase 在 React state——用 `ladder.current`（useRef 同步镜像）让回调读到"当前" phase 而无需重订阅。`userInitiated` 标志区分"用户主动断开"与"链路自发丢失"：仅后者置 `lostLink=true`（驱动首页路由到 /disconnect）；
2. **reload 自愈（hydrated）**：串口链路活在主进程，renderer 刷新会把 React 状态重置回 idle 而设备仍连着。挂载时 probe `isConnected()`：活链 → 直跳 ready + 重拉 QueryInfo；`hydrated` 让守卫区分"还没查"与"查过确实 idle"——否则每次 /verify 刷新都会被误弹回首页；
3. **重入防护**：`busy || phase !== 'idle'` 直接 return（spec 边界）。

## 三、识别流程状态机（useVerifyProcess）

### 3.1 状态图（spec palm-flows FR-1~FR-6）

```text
idle ──start()──▶ starting ──ret=0──▶ scanning ──0xA3(ret=0,RECOGNITION,同session)──▶ result-success
                    │                    │
                    │ ret≠0 / IPC 错      ├─ Cancel ─▶ cancelling ─(1s 容忍)─▶ idle
                    ▼                    ├── 0xA3(ret≠0 / recognize_type 非识别) ─▶ result-failure
                result-failure           └── 0xA3(异 session_id) → 丢弃 + warn，保持 scanning
  （result-* ──reset()──▶ idle）
```

### 3.2 五道守卫（每道都有测试背书）

| 守卫 | 规则 | 违例处置 |
|------|------|----------|
| 重入防护 | `st.current.phase !== 'idle'` 直接 return；ref 与 setState **同步**更新——仅靠 effect 回写会滞后一拍，快速双击会绕过守卫把 StartPalm 发两次（测试驱动的修复） | 静默忽略 |
| session 严格匹配（FR-4） | 0xA3 的 session_id ≠ 本次 start 返回值 → 丢弃 + warn | 保持 scanning |
| recognize_type 守卫（FR-4） | result_data 非 recognition 载荷（enrollment/scan 配置错） | result-failure，**retCode=-2**，绝不渲染为成功 |
| 链路丢失塌缩（FR-1 边界） | connected=false 且 phase∈{starting,scanning} → 0ms 延迟塌缩到 idle（同步 setState 会触发 cascading-render lint） | idle，session 清空 |
| unmount 自动停（A-9） | scanning/starting 中卸载 → fire-and-forget StopPalm | — |

**Cancel 语义（D-9）**：StopPalm 发出但**不等待响应**——UI 立即经 cancelling 回 idle（1s 定时器兜底慢模组）。**无 UI 级扫描超时（D-8）**：会话超时归模组拥有，由 0xA3 推送终态。

**隐私白名单（A-13）**：成功事件的 identity 仅拷贝白名单字段（user_id/user_name/palm_id/palm_direction/message）；`session_key` / `otc` / `server_code` 在解析层即丢弃（`lib/recognize-result.ts`），永不过桥到 UI。日志只打 ret_code + session 短哈希（FR-9），身份字段（PII）不入日志。

## 四、行为读写（usePalmBehavior）

单参数 `allow_palm_wake`（"ON"/"OFF"，snake_case，R-3 定案）的**写-回读闭环**：

```text
mount → query → base64(JSON) → allow_palm_wake
toggle → set(key, value)
    ret 0        → 回读（read-back 为 Toggle 位置的唯一真相）→ success toast
    ret 1        → unknown param_key  → 回滚 + unsupported toast
    ret 2        → invalid param_value → 回滚 + invalid toast
    其他/IPC 错   → 回滚 + error toast
```

UI **永不信任自己的乐观写**——Toggle 位置只认回读值（spec"回读确认已更新"）。失败一律回滚到 prev，三秒 toast 自清。

## 五、AppError 统一错误模型（lib/errors.ts）

设计决策 10：**渲染层所有错误必须结构化**——kind 驱动 UI 处置、i18nKey 驱动文案（禁止裸字符串上屏）、detail 驱动日志与横幅副行。

### 5.1 两级处置

| 处置 | kind | 场景 |
|------|------|------|
| **Modal**（终态弹窗） | `incompatible` / `abi-mismatch` / `preflight` | 协议版本不兼容、ABI 版本不符、原生库缺失——请重装/退出 |
| **Inline banner** | `transport` / `timeout` / `protocol` / `remote` / `unknown` | 其余全部 |

### 5.2 构造器族

| 构造器 | 输入 | 要点 |
|--------|------|------|
| `fromPlStatus(rc, detail)` | PlStatus 负值 | 11 个负码 → 专属 i18n key + kind 映射表；未列码回退 unknown |
| `refineSerialPermission(err)` | 串口打开失败 | detail 匹配 `permission\|denied\|eacces` → 改写为 macOS 隐私授权引导文案（R-5） |
| `fromHandshakeRetCode(ret, detail)` | 握手线缆层 ret_code | **130/131/132/134 → incompatible**（模组拒绝，独立命名空间，D-13）；其余 → protocol |
| `fromAbiMismatch(reported, expected)` | `pl_abi_version()` 校验 | bridge-client 抛出的**唯一结构化 init 失败**，hook 层正则解析还原 |
| `fromPreflight(reason, path)` | 原生库缺失/不可读 | worker 启动前置检查 |
| `fromUnknown(e)` | 裸异常兜底 | String(e) |

注意**两套码空间正交**（D-13）：PlStatus 负值（传输/成帧层）与握手 ret_code 130+（线缆业务层）不合并；`PL_ERR_SERIAL_OPEN_FAILED = -5` 目前仅存在于 TS 镜像（见观察点 4）。

## 六、模组 ret_code 映射（lib/ret-codes.ts）

0xA3 ret_code 与 StartPalm 应答携带 **100~199 模组本地码分区**，映射表以 **Android SDK ErrorCode.java 为权威源**：

| 码 | i18n key | 码 | i18n key |
|----|----------|----|----------|
| 101 | networkDisconnected | 110 | recognizeLocalFail |
| 102 | unsupportedPalmMode | 111 | recognizeNetworkError |
| 103 | unsupportedBizType | 113 | fsmInternal |
| 104 | sessionAlreadyStarted | 114 | qualityFailed |
| 105 | upgrading | 164 | recognizeTimeout |
| 106 | deviceBusy | 165 | noMatch |
| 107 | notActivated | | |
| 108 | deviceNotReady | | |

- **165 的产品决策（2026-09-16）**：文案是"端侧识别未找到"，刻意**不是**"未注册"；
- **1000+ 服务端业务码**挂在 `server_code` 字段，解析层作为凭据丢弃（A-13），不在本映射范围；
- 未映射码回退为**原始码 + 模组自带 message**（行为不回归）。

## 七、日志导出与日志管道

两条出口汇入**同一份 main.log**（electron-log v5，`~/Library/Logs/PosLink Tool/`，按日轮转 + 5MB 上限）：

```text
console.*（渲染层，forward-logs 包装）
window error / unhandledrejection（未捕获异常钩子）
   └─ forwardLog(log:forward IPC) ──▶ [renderer] 标签 ──▶ main.log
bridge worker stdout/stderr ────────▶ [worker] 标签 ────▶ main.log
主进程自身日志 ─────────────────────▶ （无标签）────────▶ main.log + dev 终端
```

- **未捕获异常钩子**（2026-11-09 增补）：`window.error` / `unhandledrejection` 不经过 console，专设监听经同管道转发（含堆栈）——页面崩溃可在终端与 main.log 直接定位；
- **/logs 页导出**：`listLogFiles()` 列目录 → `exportLogsZip(mode)`（recent7 / all，系统保存对话框，取消静默回 idle）→ `revealLastExport()` 在访达定位；
- **审计约束**：日志与注释必须英文（`npm run audit:all`），渲染层日志只打 ret_code + session 短哈希，PII 不入日志（FR-9/A-13）。

## 八、接入检查清单

**新增业务动作（如 enrollment 页）**：
1. 仿 `useVerifyProcess` 建 hook：phase 状态机 + `st.current` 同步镜像 ref（重入防护靠 ref 不靠 effect）；
2. 推送消费必须做 **session 严格匹配** + **载荷类型守卫**（异类型绝不渲染为成功）；
3. 失败走结构化 `failure` 对象（retCode + message），渲染走 ret-codes 映射或原始码兜底；
4. 错误一律 `fromXxx()` 构造 AppError，禁止裸 string 上屏；
5. 身份字段过解析层白名单，日志只出短哈希。

**新增错误码**：PlStatus 负值 → `errors.ts` 两张映射表 + i18n 词典；模组 ret_code → `ret-codes.ts` 表 + 词典。两处漏配的行为不同（前者回退 unknown + 原始码，后者回退原始码 + 模组 message）。

## 九、观察点

1. **错误处置分流分散在页面层**：modal/inline 的 `MODAL_KINDS` Set 定义于 (main)/page.tsx——新增终态 kind 时需记得同步，可考虑下沉到 errors.ts 统一出口；
2. **connect 的 useCallback 依赖 `[busy, phase]`**：梯子推进期间 hook 返回新函数引用，依赖它的下游 effect 会随之重跑——目前无消费方受影响，新增依赖此回调的 effect 时注意；
3. **usePalmBehavior 只管一个参数**：`allow_palm_wake` 是"写-回读"范本的唯一实例，第二个行为参数出现时应把"写-回读-回滚-toast"骨架参数化而非复制；
4. **TS 镜像与 C 头的 -5 漂移**：`protocols/index.ts` 已有 `PL_ERR_SERIAL_OPEN_FAILED = -5`（errors.ts 也在消费），但 C 头 `pos_link_c_api.h` 的 PlStatus 枚举中**无此码**（-4 直接跳 -10）——属 08 篇"镜像同步"范畴的前兆案例，C 头冻结流程需回补或 TS 侧摘除；
5. **桥缺失时的静默降级口径不一**：useVerifyProcess 靠链路塌缩回 idle，usePalmBehavior 置 null，usePosLinkConnect 靠 hydrated——`isBridgeReady()`（近期为浏览器调试新增的守卫）尚未纳入这套体系，三 hook 的浏览器降级行为依赖各自实现，建议后续统一。
