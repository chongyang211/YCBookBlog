# PosLink 桌面上位机 · 05 原生桥接层设计

> 范围：`electron/sdk/` 全目录 + `native/` 暂存与打包链路——JS 世界与 dylib/dll 之间的全部代码。线程与内存规则见《04.线程模型与内存契约.md》，进程/IPC 外围见《06.IPC与进程模型.md》。

## 一、文件地图

| 文件 | 进程 | 职责 |
|---|---|---|
| `declarations.ts` | worker | koffi 结构体/回调原型/17 符号声明；`PosLinkApi` 类型化接口 |
| `callbacks.ts` | worker | C 回调 → 纯数据消息；同步拷贝铁律；box 响应捕获（《04》） |
| `bridge-worker.ts` | worker | RPC 方法表 + 串行消息循环；唯一 `koffi.load` 点 |
| `bridge-client.ts` | main | `PosLinkBridge`：fork worker、ABI 校验、Promise RPC、事件 tap、一次性重生 |
| `loader.ts` | worker(+测试) | `native/<platform>-<arch>/` 布局解析；缺失 loud fail |
| `loader-main.ts` | main only | 打包环境解析（extraResources）+ 启动预检；与 loader.ts 分文件是因 utilityProcess 内 require('electron') 不可用 |
| `abi.ts` | main | `pl_abi_version` 期望值镜像 + env 覆盖 |
| `index.ts` | — | 桶导出 |

## 二、koffi 声明层（`declarations.ts`）

**唯一事实源是冻结头文件** `pos_link_c_api.h`：每个 koffi struct 的注释携带头文件第 6 节 ABI 指纹预期（尺寸/定宽前缀偏移）——头文件漂移时 C 侧静态断言先炸，TS 侧凭注释即可肉眼比对（无自动同步，见《10》风险）。

两条封送规则（模块头注强制）：

1. **ret_code 位宽精确（D-13）**：StartPalm/SetPalmBehavior 是 `uint16_t`，Handshake/StopPalm 是 `uint32_t`，注释明言 "do not widen"；
2. **`(const char*, size_t)` 尾部坍缩为 TS string**：长度不在 JS 侧传递，marshal 时由 koffi 重新推导。

内容：11 个 `koffi.struct`（逐一对齐 C 结构体）、5 个 `koffi.proto` 回调原型（枚举参数按 `int32_t` 声明）、17 符号签名表 `declarePosLink()`（koffi 的 C 签名字符串 DSL，如 `'int pl_send_handshake(void *, PlHandshakeReq *, PlRespCallback *, void *)'`），以及渲染桥消费的 `PosLinkApi` 强类型接口（`PlClientHandle = unknown`——句柄对 JS 完全不透明）。

符号配方与 S1 的 `tests/koffi_smoke.mjs` 逐字一致——koffi 可行性由该冒烟先行验证过。

## 三、库加载与路径解析

### 3.1 布局约定（`loader.ts`）

```text
native/<platform>-<arch>/libposlink.dylib    (darwin)
native/<platform>-<arch>/pos_link_c_api.dll  (win32)
```

- `native/` 目录**永不提交**，由脚本从 S1 构建树暂存（见第七节）；
- 缺失即抛 `LibraryMissingError`（loud fail），错误信息直接写明暂存命令来源。

### 3.2 主进程解析与预检（`loader-main.ts`）

- 打包后从 `process.resourcesPath/native/<dir>/` 解析（extraResource 落点）；dev 回退 checkout 暂存布局；
- **绝对路径由主进程解析后经 `init{libPath}` 传给 worker**——utilityProcess 内拿不到可靠的 `resourcesPath`（其 `__dirname` 在 asar 里）；
- 启动预检 `preflightLibrary()`：首窗口加载前只查**存在性 + 可读性**。架构不匹配不在此查——dlopen 自身报错更精确，且随后 ABI 版本校验兜底；预检的目的是避免"UI 起来了但连接永远失败"的困惑路径，缺失/不可读 → 弹窗退出而非 worker 内 dlopen 抛栈。

### 3.3 ABI 版本校验（`abi.ts`）

- `DEFAULT_EXPECTED_ABI_VERSION = 0`（S1 冻结值），唯一事实源是头文件 `pl_abi_version()` 实现，此处手工镜像；
- 严格相等比较（`isAbiCompatible` 保持函数形态便于将来放宽区间）；
- `POSLINK_EXPECTED_ABI` env 覆盖仅服务 e2e 注入（置 999 强造不匹配用例），生产固定默认值；
- 不匹配的处理在 `bridge-client.ts`：销毁 worker（错误库继续留在里面，后续 create/connect 必然踩错布局）→ 抛结构化 `abi-mismatch: reported=N expected=M`，渲染层正则解析后升格为终态 ErrorModal（《01》步 2）。

## 四、worker RPC（`bridge-worker.ts`）

消息协议（utilityProcess `parentPort`，structured clone）：

```text
parent → worker : { id, method, params }
worker → parent : { id, result } | { id, error } | { event, … } | { event: 'worker-ready' }
```

**阻塞语义**：`pl_send_*` 是阻塞 C 调用（默认 10s 超时），worker 逐条串行处理——一个在途请求延后下一个，与 C API 同句柄串行设计精确匹配，无需额外排队机制。

方法表要点：

- `init`：`koffi.load(libPath)` + `declarePosLink`，返回 `abiVersion`（主进程据此校验）；
- `create`：`pl_client_create`，NULL 即抛错；创建后立刻注册 push（单回调双槽）与连接状态转发——事件从这一刻起流向主进程；
- 6 个类型化 `send*`：统一走 `blockingSend(decodeType, invoke, map)` 三段式——注册一次性回调（box）→ 阻塞调用 → 从 box 取 koffi 已拷贝的值做字段重命名（`ret_code→retCode`，snake→camel）。`koffi.decode` 在回调内已完成 C 内存拷贝，map 阶段池已销毁也无碍（《04》§4.2）；
- `sendRaw`：独立实现——payload 走 `Buffer`，回调内按 `uint8_t[len]` 同步 decode；
- `destroy`：句柄置空，幂等；
- 未知 method → 结构化 error 回包；启动即发 `worker-ready`（主进程 10s 等待）。

## 五、主进程桥（`bridge-client.ts`）

`PosLinkBridge extends EventEmitter`，对外形态 `init() → create() → connect(...) → send*() → destroy()`，事件 `push` / `connection` / `worker-exit` / `worker-restarted`。

| 机制 | 实现 |
|---|---|
| fork | `utilityProcess.fork(bridge-worker.js, {stdio:'pipe'})`——stdio 接管进 electron-log（`[worker]` 标签汇流，一个日志文件讲完整故事）；ready 等待 10s 超时 |
| Promise RPC | `request()`：自增 id + pending Map + 单次 message 监听配对；worker 死亡时全量 reject |
| 事件 tap | `create()` 后安装持久 tap：`{event:'push'|'connection'}` 消息转 EventEmitter（请求监听器只消费自己的响应，两类监听互不干扰）；worker 重生后重装 |
| 一次性重生 | worker 异常退出 → reject 全部 pending → `respawnedOnce` 门闸放行一次重生（重新 fork + 重新 init + `worker-restarted` 事件）；第二次死亡发 `error` 放弃。重生后句柄清零，渲染层须回到 Home 重走连接梯 |
| 测试钩子 | `crashWorkerForTest()`：对 pid 直接 SIGKILL（utilityProcess.kill 无信号参数），驱动真实崩溃重生路径（e2e 用例） |
| ABI 校验 | `init()` 内：`pl_abi_version()` 比对 → 不匹配 `destroy()` 后抛结构化错误（见 3.3） |

## 六、连接梯与 bridge 的配合

`bridge-client` 是纯能力层（不持业务状态），连接梯/识别状态机在渲染层 hook（《07》）。配合关系：

- 每次用户点击连接都完整走 `init → create → connect`：init 捕获 abi-mismatch（唯一结构化 init 失败）；create 触发事件 tap 安装；
- 渲染层 reload 后靠 `isConnected` 探测自愈（《01》），bridge 无需感知页面生命周期；
- worker 重生事件经 IPC `poslink:onWorkerEvent` 广播，渲染层据此塌缩回 idle。

## 七、native 暂存与打包链路

```text
S1 构建树                          demo 仓库                        安装包
../.builds/palm-release ──stage──► build/native/<plat>-<arch>/ ──extraResources──► <resources>/native/
（dev 用 ../.builds/palm）            │ 17/17 符号门禁               （mac: build/native/darwin-${arch}）
                                      └─ fix:native-deps
                                         收集 Homebrew 依赖闭包 → 拷入 lib/
                                         install_name_tool 改写 @loader_path
                                         ad-hoc 重签
```

- `scripts/stage-native.mjs`：拷贝 `libposlink.dylib` / `pos_link_c_api.dll` 后立即执行 S1 的 `verify_symbols.sh`（17 导出 / 0 泄漏），损坏产物直接中止——**门禁复用同一份脚本，S1/S2 不可能各维护一套标准**；
- `scripts/fix-native-deps.sh`：解决 macOS Homebrew 绝对路径问题（`/opt/homebrew/...` 在用户机器不存在）——递归收集依赖闭包（boost/protobuf/fmt/spdlog/zlib 等）、重写全部 `LC_LOAD_DYLIB`、ad-hoc 重签，使 DMG 在干净机器可运行；
- `electron-builder.yml`：原生库必须在 **asar 之外**（`koffi.load` → dlopen 需真实磁盘文件），mac 走 extraResources、只随当前目标切片（arm64 包不含 x64 库）；输出 DMG（identity:null 未签名）/ NSIS / AppImage（保留但不在范围）；
- `scripts/poc.mjs` / `e2e.mjs` 从开发树显式 `--from` 暂存；`pack.mjs` 从发布树暂存——**开发树与发布树分离**，e2e 永远测"刚刚构建的核心"。

## 八、本层的守护与缺口

| 守护 | 覆盖 |
|---|---|
| C 侧静态断言 + koffi 注释指纹 | 结构体布局漂移 |
| stage 时 17/17 符号门禁 | 导出面漂移 |
| 启动预检 + ABI 整数校验 | 库缺失 / 换错库 / 版本不匹配 |
| koffi smoke（S1）+ 25 项无头 e2e（S2） | 签名可声明性、整链行为 |

缺口（已知且接受）：C 头文件 → TS 声明是**手工镜像**，无代码生成；头文件演进时靠三处静态断言 + 指纹注释 + 符号门禁兜底，但 ret_code 位宽等语义变化仍依赖评审纪律——完整评估见《10.风险与遗留事项.md》。

## 九、给"换宿主"的启示

本层与 Electron 强耦合的点只有两处：utilityProcess fork 与 `process.resourcesPath` 解析。若迁移到其他 Node 宿主（CLI、服务端），`declarations.ts` + `callbacks.ts` + `blockingSend` 模式可整体平移，只需替换进程隔离手段（如 child_process + 同样的消息协议）——这正是当初选 koffi 而非 N-API addon 的动机之一：声明层无编译步骤、跨宿主可移植。
