# PosLink 桌面上位机 · 09 测试与质量门禁

> 范围：两个工程的全部自动化验证——demo 侧（vitest 单测 / 无头 e2e / audit 扫描器 / `release:check`）与 c_api 侧（PTY 双真实栈集成 / 无环境单测 / 符号与禁用词门禁 / sanitizer / CI）。各机制的架构背景见《03.C_API契约与ABI设计.md》《05.原生桥接层.md》《06.IPC与进程模型.md》；已知缺口与风险汇总见《10.风险与遗留事项.md》。

## 一、门禁全景

质量验证按"离产物远近"分四层，越靠右越接近发布：

```text
层 1  单元测试        vitest 63 例（demo 渲染层+主进程）
                      pl_env_free_tests 10 组（c_api 无环境逻辑）
层 2  集成测试        test_mock_server（PTY 环回 + 双真实栈，70 检查）
                      无头 e2e（真 Electron + 真 dylib + mock 模组）
层 3  静态门禁        audit 5 扫描器（禁用词/语言红线/敏感信息/i18n）
                      verify_symbols（17 导出 0 泄漏）/ verify_banned_words
层 4  发布门禁        release:check 全链 → stage-native 符号门禁
                      → package_release 重跑符号门禁 → sanitizer（本地）
```

执行入口：

```bash
npm run test            # 层 1（需 Node 22，见 7.1）
npm run e2e             # 层 2（自动 tsc + 暂存 dylib + 启动 Electron 无头入口）
npm run audit           # 层 3（5 扫描器全跑）
npm run release:check   # 层 1+2+3 + lint + format:check + 双 tsc —— 发布前必跑
```

## 二、单元测试（vitest，5 文件 / 63 例）

```bash
npm run test    # vitest run
```

| 文件 | 覆盖 |
|------|------|
| `hooks/useVerifyProcess.test.tsx` | 加验状态机全场景：happy path（idle→starting→scanning）、重入守卫、ret_code≠0/IPC 拒绝失败路径、0xA3 消费（匹配 session + ret=0 → success；**异 session 丢弃**（A-8）；recognize_type≠1 守卫；坏 result_data 不崩（A-7））、带外 push 忽略、取消不等待 StopPalm（D-9） |
| `lib/errors.test.ts` | AppError 模型：错误分类、i18n key 映射 |
| `lib/recognize-result.test.ts` | base64 result_data 解析：字段提取、坏输入不抛 |
| `lib/ret-codes.test.ts` | 模组 ret_code 100~199 → 友好文案 key 映射完整性 |
| `electron/ipc/log-collect.test.ts` | 主进程日志收集/导出（07 篇"日志导出"的底层） |

约定：

- 全部纯函数/状态机级别 mock IPC，**不依赖真 dylib**——秒级反馈，任何提交前都应跑；
- `useVerifyProcess` 的用例名直接对应规格条款（FR-2/FR-4/A-7/A-8/D-9），状态机行为变更时先改用例。

## 三、c_api 集成测试（PTY 双真实栈）

`pos_link/c_api/tests/`——这套设计的核心思想：**除了串口硬件，其余全真**。真 dylib + 真 WxpayPosLink 核心 + 真 Asio io 线程，只有模组是 mock。

### 3.1 mock 模组（PTY 环回）

`tests/mock_module_main.cpp` 用 `posix_openpt` 造一对伪终端：c_api 句柄连 slave，master 侧跑**真实的 `pos_link::PosLink` 协议栈**扮演模组（组帧/解析/应答/推送全真）。支持 stdin 指令注入推送（`push_state <n>` / `push_recognize <session>`），demo 侧无硬件联调也复用它（见 4.2）。

### 3.2 `test_mock_server.cpp`（70 检查，0 失败）

覆盖矩阵：

- 6 个类型化请求的成功 + 模组拒绝路径；
- D-13 边界值（u16 0xFFFF / u32 0xFFFFFFFF 经诊断码通道）；
- AC-12 raw/typed 字节一致（memcmp 全帧比对）；
- 未知命令透传（reply_msg_code=2 → PL_ERR_REMOTE + 原样码）；
- 推送订阅/派发/ACK 纪律矩阵（已建模+已订阅→0 / 未订阅→0 丢弃 / 未建模→131）;
- 10 线程并发注册风暴。

### 3.3 `test_env_free.cpp`（10 组，无任何环境依赖）

StrPool（5）+ MapReplyMsgCode（1）+ StatusName（1）+ SetLastError（3）。以 `-UNDEBUG` 编译保证 Release 下断言存活；独立可执行 `pl_env_free_tests`。

### 3.4 sanitizer 快照（本地，2026-11-04）

| 构建 | 结果 |
|------|------|
| ASan+UBSan（`.builds/palm-asan`） | 70/0；c_api 文件 0 发现；24 项 misaligned 为主干既有债务（AC-1 不动主干） |
| TSan（`.builds/palm-tsan`） | 70/0；harness 线程契约修复后 0 告警 |
| LeakSanitizer | macOS SIP 阻断 `detect_leaks`——归 Linux CI（未建） |

## 四、无头 e2e（真 Electron + 真 dylib + mock 模组）

```bash
npm run e2e    # tsc → stage dylib（.builds/palm）→ npx electron e2e-main.js
```

`electron/e2e-main.ts` 是**无窗口、无 UI 的独立入口**：跳过 preload/渲染层，直接在主进程语境验证完整桥接链（koffi → dylib → mock 模组 PTY）。`check(label, cond)` 逐项计数，结束打一个 PASS/FAIL 结论并以退出码 0/1 收场——可无头进 CI。

覆盖序列：环境变量守卫（防真实环境误跑）→ create → connect（rc=PL_OK）→ CONNECTED 事件回调 → handshake/startPalm/stopPalm/setPalmBehavior（rc 与 retCode 双校验）→ 断开清理。这是"preload 之外整条链都真"的最小发布冒烟——**30s 进度节拍等传输层行为的下次回归也挂在此入口扩展**。

> 历史注：Phase 0 的 `poc/`（FFI 可用性验证）已于 2026-11-10 删除——其验证目标被本 e2e 与单测覆盖，设计沿革记录在 139157860 story 文档。

## 五、静态门禁（`npm run audit`，5 扫描器）

`scripts/audit.mjs all`——源码树的合规扫描，全部纯 Node 实现、零外部依赖：

| 扫描器 | 规则 | 依据 |
|--------|------|------|
| `ban-words` | 源码禁出现 刷掌/测速/掌纹/掌静脉/签到/扫码/刷脸/指纹（清单 `ban-words.json`）——桌面侧代码对协议业务词保持中立，词表定义文件自身豁免 | AC-9 |
| `non-english-logs` | 日志字符串必须英文（对外交付红线） | 设计决策 7 |
| `non-english-comments` | 注释必须英文；**`scripts/` 目录豁免**（2026-11-07 团队决策：构建脚本面向内部维护者） | 同上 |
| `log-sensitive` | 日志不得含 session_key/otc/server_code 等敏感字段 | spec A-13 |
| `i18n-no-placeholder` | 四语言词典 key 集合一致、无占位残留 | — |

旁路同族门禁（c_api 侧，独立脚本）：

- `verify_symbols.sh`：dylib 导出**恰好** 17 个 `pl_*`、零内部符号泄漏（AC-4）；`stage-native.mjs` 暂存与 `package_release.sh` 打包时**各重跑一次**；
- `verify_banned_words.sh`：c_api README/include/src/scripts/tests 的中文协议词扫描。

## 六、发布门禁链

```bash
npm run release:check
# = audit（5 扫描器）→ lint → format:check
#   → tsc --noEmit（electron 工程 + 渲染工程）
#   → vitest（63 例）→ e2e（无头真 Electron）
```

全绿后 `npm run pack[:target]`——pack 链上还有两道**产物门禁**：

1. `stage-native.mjs`：拷贝 dylib 进 `native/` 时跑 `verify_symbols.sh`（坏产物进不了暂存区）；
2. `scripts/package_release.sh`（c_api 发布打包）：对**打包后的 dylib** 重跑符号门禁（AC-4：交付树自身过闸）。

## 七、CI 与运行环境

- **CI**：`.gitlab-ci.yml` 的 `pos_link:c_api:macos-arm64-standalone`——触碰 `pos_link/c_api/**` 或 `pos_link/CMakeLists.txt` 的推送触发 darwin-arm64 独立构建 + koffi smoke（`tests/koffi_smoke.mjs`，17/17 符号可调用）；
- **Node 版本**：demo 侧 vitest/rollup 原生绑定按 **Node 22**（`.nvmrc`）安装——Node 20 跑 `npm run test` 会报 rollup `MODULE_NOT_FOUND`，先 `nvm use`；
- **本机交叉验证**：`.builds/palm-asan` / `palm-tsan` 由 `setup-macos-deps` 后的宿主工具链构建（见《DEPENDENCIES.md》）。
