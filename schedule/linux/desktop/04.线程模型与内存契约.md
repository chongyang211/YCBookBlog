# PosLink 桌面上位机 · 04 线程模型与内存契约

> 范围：从 C API 到 Electron 的跨线程规则与指针生命周期——这套契约是回调不崩、数据不悬空的全部依据。API 面本身见《03.C契约与ABI设计.md》，worker/主进程封装见《05.原生桥接层设计.md》。

## 一、四个线程域全景

```text
域 A  Renderer（React）          单线程事件循环；不做任何线程决策，只发 IPC、收事件
域 B  Electron Main              IPC handler；事件 tap 广播；串口枚举（serialport 只列不开）
域 C  bridge-worker              koffi.register 的 C 回调在这里触发（= 域 D 的 io 线程）；
                                 RPC 消息循环串行处理 pl_send_* 阻塞调用
域 D  dylib 内 Asio io 线程       每句柄一条；驱动核心 io_context；所有 C 回调的触发点
```

关键事实：**koffi 的回调直接跑在域 D**（dylib 内部线程）上——所以 worker 里的回调代码必须是"同步拷贝后立即返回"的短临界区；域 C 的消息循环与域 D 的回调天然并发，靠的是 copy-then-call 与同步拷贝两条铁律（下文二、四）。

## 二、c_api 内部线程模型（`src/pl_internal.h`）

### 2.1 句柄生命周期

```text
调用方线程                         dylib                          io_worker 线程
──────────                        ─────                          ──────────────
pl_client_create()
  │ new PlClient{}（core 未启动）
  ▼
pl_connect_serial(h,…)
  │ core->ConnectSerial(...)
  │ 成功 → spawn io_worker 跑 core->Start() ──────────────────► 阻塞驱动 io_context
  ▼
  … 请求/推送均在 io 线程派发 …
pl_disconnect(h) 或 pl_client_destroy(h)
  │ shutting_down_ = true（原子闩）
  │ core->Stop()      —— 令 Start() 返回
  │ io_worker_.join() —— 等线程退出
  ▼
（仅 destroy）delete PlClient；shared_ptr 归零 → 核心对象析构
```

- 析构顺序靠 `shared_ptr` 引用计数收敛：回调先跑完 → refcount 归零 → io_context + socket 析构，拆除期间不撕裂在途回调。
- 只有 create/destroy/connect/disconnect 四个函数触碰线程；其余 `pl_*` 只检查 `shutting_down_` 后转发。
- `PlClient` 禁拷贝禁移动（mutex/thread 成员），句柄本身堆分配、指针身份稳定。

### 2.2 回调派发：copy-then-call（不可重入保证）

- 四组回调槽位（0xA3 push / 0xA1 push / 连接状态 / 日志）由 `callback_mu_` 保护；
- io 线程派发时**锁内只拷出 `(fn, ctx)`，解锁后才调用**——用户回调执行期间不持锁，也绝不会同句柄重入（D-6）；
- `shutting_down_` 原子闩：disconnect/destroy 置位后，io 线程每次派发前检查短路，避免触碰将释放的状态；
- `conn_state` 原子量：`pl_is_connected` 免锁查询。

注意边界：**同一句柄的回调永不同时出现在调用栈上；不同句柄可能并发派发**（各自独立 io 线程）。

### 2.3 one-shot io_context（重连契约，易踩坑）

核心 `PosLinkClient` 在 io_context 层面是 **one-shot**：`Stop()` 永久停机不重启；链路自发断开后死实例留在句柄里。因此：

- **句柄可复用，核心实例不可**——每轮 connect（非首次）由 `pl_connect_serial` 内部换入**全新的** `PosLinkClient`（`core_ever_connected` 标记驱动，e2e 驱动的修复 2026-11-06）；
- 调用方视角的正确姿势：断开后重新 `pl_connect_serial` 同一句柄是合法的；绝不要试图在断开后"恢复"旧连接对象。

## 三、内存契约（c_api 侧）

| 对象 | 所有权 | 生命周期规则 |
|---|---|---|
| `PlClientHandle` | dylib（`new PlClient`） | 只能 `pl_client_destroy` 释放；`free()/delete` 是 UB；destroy 后任何使用是 UB |
| 回调载荷指针（`const char*` / resp 结构体） | dylib 的 **StrPool** | **仅本次回调执行期间有效**；回调返回瞬间池销毁、指针悬空；需续用必须在回调内 `memcpy` |
| 空字符串字段 | 静态 `""` 字面量 | `intern("")` 零分配快路径；指针恒非 NULL，调用方可直接比 `""` |
| 请求入参（req 结构体、raw payload） | 调用方 | 同步语义：`pl_send_*` 返回前由封送层拷入线缆帧，返回后调用方可立即复用/释放 |
| 诊断消息（`pl_last_error_message`） | 线程级 256B 缓冲 | 指针在本线程**下一次 ABI 调用前**有效；超长尾部 `...` 截断；未记录过可能为 NULL |
| 日志回调 `msg` | dylib | 不保证 NUL 结尾，**必须用 `msg_len`** |

**StrPool 设计**（`src/pl_strpool.h`）：每次回调帧建一个池，封送层对每个 `std::string` 做 `intern()` 得到稳定 NUL 结尾指针；实现为 `vector<unique_ptr<char[]>>`——每条精确分配、无对齐戏法、可审计（突变测试友好）；**非线程安全但无需如此**（只在 io 线程逐帧创建，调用方触碰不到）。

选这套"帧作用域池"而非 arena 或调用方管理的动机：调用方 retention 惩罚为零（不拷贝就悬空，契约清晰）；正确拷贝的调用方不为每条推送付出隐性堆滞留。

## 四、koffi / worker 侧规则（demo 侧契约）

### 4.1 同步拷贝铁律（`electron/sdk/callbacks.ts` 头注）

> every C callback fires on the dylib's internal Boost.Asio io thread … COPY synchronously inside the callback (koffi.decode + string materialization), THEN post the plain-data message. **Never let a C pointer escape the callback.**

落地形态：

```text
C 回调（域 D）                    worker（域 C）
──────────────                   ──────────────
koffi.register(fn)
  │ koffi.decode(payload,'PlRecognizeResultPush')   ← 在回调内物化为 JS 值
  │ 组装纯数据对象 {retCode, sessionId, resultData}
  │ post(...)  ──────────────────►  事件消息（纯数据，无 C 指针）
  └ return（池此刻销毁，无人在用）
```

一个 koffi 回调按 `type` 分发占满 0xA3/0xA1 两个 push 槽位（dylib 每槽位单回调，正好复用）；连接状态回调无指针载荷，直接转发。

### 4.2 box 模式（阻塞调用的响应捕获）

`pl_send_*` 是异步注册 + 回调应答，而 worker 的 RPC 循环需要阻塞语义：`captureResp(box, decodeType)` 注册一次性 `PlRespCallback`，回调内 decode 后写入 `box.v`，随后 `pl_send_*` 同步返回、sender 从 box 读结果。box 间接层还解决 TS 控制流分析对闭包赋值变量收窄的问题。

### 4.3 worker 串行循环

- 消息循环逐条处理：一个 `pl_send_*` 阻塞（最长 10s）期间后续消息排队——与 C API 同句柄不可重入语义天然契合，无需 worker 内再加锁；
- worker 崩溃域：FFI/核心的任何崩溃只死 worker 进程；主进程 reject 全部 pending → 一次性重生（重 fork + 重新 `koffi.load` + 重新 init，重生后句柄从零开始）→ 渲染层收到 `worker-restarted` 回 Home。第二次死亡才向上报错。

## 五、跨层契约速查（改动前必读）

| 契约 | 违反后果 |
|---|---|
| 回调内同步拷贝，指针不出回调 | 读取已释放内存（间歇性乱码/崩溃，难复现） |
| ret_code 位宽逐字对齐（u16/u32） | 高字节截断，错误码误判 |
| 断开/销毁期间回调可能已入队 | 依赖 `shutting_down_` 短路；调用方不得在回调里同步调用 destroy 同句柄 |
| 重连走重新 connect（内部换新核心实例） | 复用死 io_context → 请求全部无响应 |
| worker 内一次只处理一条消息 | 若改并发，需重审同句柄不可重入假设 |
| destroy 后不得再使用句柄 | UB（含 `-20` 之外的场景） |
