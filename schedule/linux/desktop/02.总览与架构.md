# PosLink 桌面上位机 · 02 总览与架构

> 系列入口（上接《README.md》）。范围：`poslink-desktop-demo/`（S2 上位机 Demo）与 `pos_link/c_api/`（S1 C ABI 层）的整体架构、组件表与职责边界。端到端调用链见《01.全流程分析.md》；传输细节分主题：03 C API 契约 / 04 线程与内存 / 05 原生桥接 / 06 IPC 与进程 / 07 业务流程 / 08 协议字典 / 09 测试门禁 / 10 风险遗留。

## 一、定位

**只管"和模组说话 + 把话说给人听"**——刷掌业务决策（会话超时、匹配策略、凭证生成）全在模组侧与后台；上位机负责协议搬运（握手/启停/查询/行为参数）、识别结果呈现、设备运维辅助（日志导出、调试控制台）。协议栈全仓只有 C++ 一份实现，桌面侧经 C ABI 复用，与 Android AAR、模组侧保持同一份协议逻辑（协议升级零成本）。

两条设计红线：

1. **C ABI 是 FFI 互操作的最大公约数**——C++ ABI 不稳定，扁平 C 函数 + POD 结构体才能被 koffi 可靠声明；头文件冻结（S1），TS 侧镜像须人工同步（见《08》）。
2. **子进程隔离 FFI**——c_api 内部用 Boost.Asio 线程做串口 IO 与回调，直接在 Electron 主进程 FFI 有跨线程回调阻塞/崩溃风险；worker 崩溃可一次性重生，主进程无恙。

## 二、分层结构

```text
O41 刷掌模组
   ↕ 串口 0x7E 帧（115200 默认）
pos_link C++ 核心（WxpayPosLink + WxpayCrossComm，零改动）
   ↕ C++ 对象调用
pos_link/c_api（libposlink.dylib / pos_link_c_api.dll）
   纯 C11：17 个 pl_* 导出；每句柄一条 Asio io 线程；回调帧作用域 StrPool
   ↕ koffi FFI（utilityProcess 内）
bridge-worker.ts   唯一 FFI 接触点：串行 RPC 消息循环 + 回调同步拷贝 → 事件消息
   ↕ {id, method, params} ↔ {id, result|error} / {event,…}
bridge-client.ts   主进程 PosLinkBridge：worker 生命周期 + Promise 化 + 事件 tap
   ↕ ipc/main.handle + webContents.send
preload.ts         contextBridge 白名单：window.posLink / window.app（唯一 API 面）
   ↕
Renderer（Next.js 16 静态导出 + React 19）
   PosLinkProvider（连接梯单例）+ 各流程 Hook 状态机 + i18n 四语言
```

进程视角（3 个进程 + 1 个外部模组）：

```text
┌─ Electron Main ──────────────┐   ┌─ utilityProcess (bridge-worker) ─┐
│ 窗口/app://协议/单实例锁       │   │ koffi.load(dylib/dll)            │
│ IPC handler × 4 组            │◄─►│ pl_* 调用（串行 RPC）             │──── 串口 ──► O41
│ electron-log / electron-store │   │ C 回调 → 同步拷贝 → 事件消息       │
│ serialport 枚举（只列不开）     │   └──────────────────────────────────┘
└──────────────▲───────────────┘
               │ contextBridge
┌─ Renderer ───┴───────────────┐
│ Next.js 页面 + React Hooks    │  （无 Node、sandbox、contextIsolation）
└──────────────────────────────┘
```

## 五、进程与线程模型（收敛点与边界）

**渲染层**：无任何线程决策，全部经 IPC；连接梯/识别状态机在 React Hook 内。

**主进程**：IPC handler 同步转发到 bridge；事件经 `webContents.send` 广播到所有窗口；串口枚举用 serialport **只列不开**（打开权在 c_api）。

**worker 子进程**：消息循环串行——一个 `pl_send_*` 阻塞期间后续消息排队（与 C API 同句柄回调不可重入天然契合）；C 回调在 c_api 的 io 线程触发，worker 内同步拷贝后转成事件消息。

**c_api 内部**：每句柄一条 Asio io 线程（连接成功后 spawn，disconnect/destroy 先 Stop 再 join）；回调 copy-then-call 不可重入；**io_context one-shot——重连必须换新实例**（跨层重要契约）。

崩溃域：worker 内崩溃（FFI/核心）不影响主进程；一次性重生后句柄清零，渲染层收到 `worker-restarted` 回 Home。详见《04》《06》。

## 六、职责边界（S1 ↔ S2 分工）

| | pos_link/c_api（S1） | poslink-desktop-demo（S2） |
|---|---|---|
| 负责 | C ABI 面、封送、错误分类、ACK 纪律、诊断 | utilityProcess 封装、koffi 声明、结构体 TS 镜像、UI/UX、i18n、日志、打包 |
| 不负责 | 重连策略、JSON/base64 解析、任何宿主封装 | 协议逻辑（禁止在 TS 侧重写协议栈） |
| 契约 | 冻结头文件 + ABI 版本整数 | 镜像声明 + `pl_abi_version()` 启动校验 |

## 八、与模组侧（biz/pos）的对照

模组侧同走 PosLink 协议，但角色对调：模组是 server（0x7E 帧 server 端、0xA3/0xA1 推送发起方），桌面是 client（指令发起方、推送消费方）。协议语义（握手版本协商、session_id、ret_code 命名空间）两边共用一份 C++ 核心，不会 drift；本系列只记录桌面侧的封送与消费规则。
