# 08. 协议字典与 TS 镜像

> 系列第八篇。覆盖协议常量与类型的三份镜像（C 头 → `protocols/index.ts` → `electron/sdk/declarations.ts` + `callbacks.ts`）、逐节对照关系、镜像同步规则，以及**实测存在的四处漂移**（2026-11-10 全量核对）。C 头是唯一真相源（single source of truth）。

## 一、三份镜像的关系

```text
pos_link/c_api/include/pos_link_c_api.h     ← 唯一真相源（C11，ABI 指纹静态断言）
        │
        ├─▶ protocols/index.ts              ← 镜像 A：常量 + TS 类型
        │   （renderer / bridge worker / main 三方共享，spec FR-1）
        │
        └─▶ electron/sdk/
            ├── declarations.ts             ← 镜像 B：koffi FFI 封送声明
            │   （结构体字段类型串 + 函数签名，spec FR-2/T2.2）
            └── callbacks.ts                ← 镜像 B'：回调的 TS 包装
```

- **镜像 A** 面向业务：11 个 PlStatus 常量 + `statusName()` 可读名、连接状态/推送类型、8 个响应/推送 interface、4 个请求 interface；
- **镜像 B** 面向封送：koffi 的字段类型字符串（`'uint16_t'`…）与函数签名串，`bridge-worker.ts`/`callbacks.ts` 消费；
- 依赖方向单向：业务 hook → protocols → declarations；**禁止业务代码绕过 protocols 直接 import declarations 的常量**。

## 二、逐节对照表（C 头 ↔ TS）

### C 头 Section 1（枚举）

| C 枚举 | 镜像 A（protocols） | 镜像 B（declarations） | 状态 |
|--------|--------------------|------------------------|------|
| PlStatus（11 码） | ✅ 常量 + `statusName()` 可读名 | 仅作 `int32_t` 函数参数，无枚举镜像 | ⚠️ **双向漂移**（见第四节） |
| PlConnState（4 值） | ✅ 4 常量 | ✅（onConnectionState 回调参数） | 一致 |
| PlPushType（2 值，D-12） | ✅ 2 常量 | ✅ | 一致 |
| PlLogLevel（5 级） | ❌ **缺失** | PlLogCallback 类型已声明 | ⚠️ **TS 缺失**（见第四节） |

### C 头 Section 3（结构体）

| C 结构体 | 镜像 A interface | 镜像 B 字段封送 | ret_code 位宽（D-13） |
|----------|------------------|-----------------|----------------------|
| PlHandshakeReq/Resp | HandshakeRequest/Resp | ✅ 逐字段 | Resp ret_code = **u32** |
| PlStartPalmReq/Resp | StartPalmRequest/Resp | ✅（session_id @ offset 8，u16 后 4 字节填充） | ret_code = **u16**，注释"never widen" |
| PlStopPalmReq/Resp | （无 Req——无载荷） | ✅（1 字节 reserved 占位） | Resp ret_code = **u32** |
| PlQueryInfoReq/Resp | QueryInfoResp | ✅ | 无 ret_code |
| PlSetPalmBehaviorReq/Resp | SetPalmBehaviorRequest/Resp | ✅ | ret_code = **u16**（1=未知 key / 2=非法值） |
| PlQueryPalmBehaviorReq/Resp | QueryPalmBehaviorResp | ✅ | 无 ret_code（base64 透传，D-11） |
| PlRecognizeResultPush（推送） | RecognizeResultPush | ✅（session_id @ 8） | ret_code = **u32** |
| PlModuleStatePush（推送） | ModuleStatePush | ✅（sizeof==2） | 无 ret_code |

镜像 A 独有的三个 interface（**C 头无对应**，属"TS 收窄"而非漂移）：

- `HandshakeRequest` / `StartPalmRequest` / `SetPalmBehaviorRequest`：C 侧 `const char* + size_t` 变长对在 TS 塌缩为纯 string——长度由 bridge 在封送前重推（protocols :124-126 注释）；
- `RawRequest` / `RawResponse`：`pl_send_raw` 逃生通道的载荷形态（cmdId + Uint8Array）。

### C 头 Section 5（17 函数）

`declarations.ts:227-261` 全部 17 个函数签名已镜像（`lib.func(...)` koffi 声明），无缺漏。

## 三、镜像同步规则（现状）

1. **真相源唯一**：C 头的 ABI 指纹静态断言（`POSLINK_STATIC_ASSERT`）是布局与位宽的权威；protocols 头注释明示 "Do NOT change values here without re-freezing the header"；
2. **冻结策略**（C 头文件头）：破坏性变更（删/改宽/重排）必须 bump `pl_abi_version()` + SOVERSION；增量变更（新枚举值、末尾追加函数、启用 reserved[]）向后兼容、版本号不变；
3. **位宽纪律**（D-13）：`declarations.ts` 每个 ret_code 字段注释 EXACT 位宽，封送进 C 结构体时禁止加宽（R-2：加宽会静默截断高字节）；
4. **同步方式**：目前**纯手工**——无生成器、无 CI 比对（见第六节缺口）。

## 四、实测漂移清单（2026-11-10 全量核对）

| # | 漂移 | 方向 | 影响 |
|---|------|------|------|
| 1 | `PL_ERR_SERIAL_OPEN_FAILED = -5` 仅 TS 有，C 头无（-4 直接跳 -10） | TS 超前 | `errors.ts`/`errors.test.ts` 已消费；C 侧该场景实际以 -10 IO + errno 文案表达（`refineSerialPermission` 靠 detail 文案匹配权限拒绝正是为此）——功能可用，但码表不对齐 |
| 2 | `PL_ERR_SHUTTING_DOWN = -20` 仅 C 头有，TS 全链无 | C 超前 | dylib 销毁后误用时 TS 侧 `fromPlStatus(-20)` 落 unknown + `status_-20`，无专属文案 |
| 3 | `PlLogLevel`（5 级）C 头有，protocols 无 | C 超前 | 无法以常量引用日志级别 |
| 4 | `pl_set_log_callback` koffi 声明存在，但 **callbacks.ts 无 TS 回调包装** | 半镜像 | dylib 内部日志（spdlog）未接入 Electron 日志管道——Phase 5 log-dump（设计决策 10）待实装 |

前三条是枚举值漂移，第 4 条是功能缺口。共同根因：**同步靠人工，TS 侧无编译期守护**（C 侧有静态断言，TS 侧对"值是否与 C 一致"零校验）。

## 五、镜像同步的操作规则（给改协议的人）

1. **改 C 头（真相源）在先**：新枚举值/新字段/新函数按冻结策略调整，跑 `gcc -std=c11 -fsyntax-only` + 静态断言；
2. **`pl_abi_version()` 按策略递增**（破坏性才 bump）；
3. **同步镜像 A**（protocols/index.ts）：常量 + interface，含 ret_code 位宽注释；
4. **同步镜像 B**（declarations.ts）：koffi 字段类型串 + offset 注释（对照 C 静态断言的期望值）；
5. **跑 TS 侧消费方测试**：`errors.test.ts` / `ret-codes.test.ts` / e2e（`npm run e2e` 的 mock 模组按同码表应答）；
6. **重新 staging + 门禁**：`npm run stage:native`（S1 符号门禁）后重启 dev 验证。

## 六、校验缺口与改进建议

| 现状 | 缺口 | 建议 |
|------|------|------|
| C 侧：静态断言锁布局/位宽（编译期） | 断言只在 C 编译时跑，TS 侧无感知 | 保持（TS 无法读 C 断言） |
| TS 侧：纯手工对照 | 枚举值/字段漂移只能靠全量核对发现（本次 -5/-20 均为此类） | ① 低成本：CI 加脚本从 C 头 `grep` 枚举值与 protocols 常量做 diff；② 中成本：写一个 C 头解析生成器产出的 protocols 常量段（头文件格式稳定，C11 + 固定风格，正则可解析） |
| `pl_abi_version()` 运行时可查 | 值不变不代表内容没漂移（增量变更不 bump） | worker 启动时除 ABI 版本外，可校验关键枚举值（如向 dylib 查询——需 C 侧新增自省函数，属 C 头增量变更） |

## 七、观察点

1. **-5 与 -20 的收敛方向需定夺**：-5（TS 独有）建议在 C 头补登记（冻结策略允许增量新增枚举值），-20（C 独有）建议 TS 镜像补齐 + errors.ts 加专属文案——两者都收敛后码表重新对齐；
2. **log-dump 是第 4 条漂移的完整解**：PlLogLevel 镜像 + callbacks.ts 包装 + worker 接线三步实装后，dylib 内部日志（spdlog）汇入 main.log，同时消化 PlLogLevel 缺失问题；
3. **declarations.ts 的 offset 注释是人工指纹**：`session_id @ 8 (u32 + 4 pad)` 这类注释与 C 静态断言数值一一对应，改 C 结构体时必须人工核对——生成器方案（第六节）能一并消除该负担。
