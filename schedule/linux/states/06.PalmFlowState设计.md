# PalmFlowState 设计

`PalmFlowStateBase` 是整个状态机体系的 **"状态公共底座"**，只有 3 个成员，但承担了 3 个关键职责。先看清它是什么，再用一次完整时序串起来。

## 一、三重身份（对应 3 个成员）

### 身份 ①：所有状态的统一类型（`class PalmFlowStateBase : public FSM::State`）

继承 HFSM2 的状态基类，全项目 **21 个状态**（5 个 Head + 16 个 leaf）全部继承它——FSM 定义（`M::Composite<...>`）里的每个状态名因此都满足 HFSM2 的类型约束。它本身**不含任何业务逻辑**：业务全在子类的 `enter/react/update` 里。

### 身份 ②：react 名称穿透（`:34` 的 using）

```cpp
using PalmFlowFsmDef::FSM::State::react;
```

解决 C++ 名称隐藏问题：HFSM2 靠"对任意事件类型解析出一个 `react`"来分发事件。子类一旦定义了自己的 `react(const VerifyDataEvent&, ...)`，基类的空模板 react 就被隐藏——未匹配的事件找不到 react 会编译失败。这行 using 把基类模板放回来；所以每个子类 react 声明前都有一句 `using PalmFlowStateBase::react;`。**作用：状态只处理自己关心的事件，其余事件静默穿透给父状态**。

### 身份 ③：状态进入时的"对外表现"入口（`BroadcastEnter` + `LightFor`）

这是它的核心价值——**把 FSM 内部的状态变化翻译成外部世界可感知的三样东西**：

```
BroadcastEnter(control, FlowState::kXXX)
   ├─ LightFor(ctx)                    ← 虚函数：这个状态该亮什么灯
   └─ fsm_ctx.broadcast(kind, exit_code, exit_result, light)   ← 闭包 → wrapper
        ├─ LOG_I("PalmFlow: X -> Y")   ← 设备日志（排查状态流转的主线索）
        ├─ change_sig_(PalmFlowChange) ← 订阅者：Controller（session.end 等）/ PosNotifier（0xAA 等上行通知）
        ├─ DeviceStateMachine::ReportFlowLight(light)  ← 灯效出口
        ├─ last_broadcast_state_ = to  ← 记录"最后广播状态"（session.end 的 last_state 来源）
        └─ Wake()                      ← 唤醒 RunLoop 检查 Action 队列/Done
```

`LightFor` 是唯一虚函数：默认 `kIdle`，各状态 override 声明自己的灯——`Detecting`→kDetecting、等待态→kLoading、`Stopping`→按 `exit_code` 返回 kSuccess/kIdle/kWarning（结果灯色在这里决定）。

## 二、完整时序：以"加验收敛 → 进入 Stopping"为例

```
VerifySubmittingState::react(VerdictPostRecEvent)        ← FSM 内部
  │ DispatchPostRec<VerificationFinishState>(V_Complete)
  │   └─ changeTo<VerificationFinishState>               【只记计划，不切换】
  ▼
[计划执行] Verifying 子树 exit（disarm_timer）
  ▼
[计划执行] VerificationFinishState::enter
  │   enter 为空 → 不调 BroadcastEnter
  │   ⇒ 无广播、无灯变、无日志 —— 外部世界不知道这个瞬态存在过
  ▼
fsm_->update()（wrapper React 的第二拍）
  │ VerificationFinishState::update
  │   ├─ EmitVerificationResult（发 palm.verification.result）
  │   └─ DispatchResultExit → changeTo<StoppingState>    【记计划】
  ▼
[计划执行] VerifyingHead exit → StoppingState::enter
  │
  │ ★ 这里就是 PalmFlowStateBase 登场的时刻：
  │
  │ StoppingState::enter 第一行：
  │   BroadcastEnter(control, FlowState::kStopping)
  │     │
  │     ├─ this->LightFor(ctx)          ← 虚分派到 Stopping 的 override：
  │     │                                  exit_code==0 → kSuccess
  │     │                                  USER_NOT_ENROLLED → kIdle
  │     │                                  其他非零 → kWarning
  │     │                               （结果灯色在这一刻定死）
  │     │
  │     └─ fsm_ctx.broadcast(kStopping, exit_code, exit_result, light)
  │          │（这是 wrapper 构造时绑定的 std::function 闭包）
  │          │
  │          ├─ LOG_I("PalmFlow: VerifySubmitting -> Stopping exit_code=0")
  │          ├─ change_sig_(PalmFlowChange{from=VerifySubmitting, to=Stopping, ...})
  │          │     ├─→ Controller::Subscribe 回调
  │          │     │     └─ ev.to==kStopping → EmitSessionEnd（palm.session.end）
  │          │     └─→ PosNotifier → 上行通知 / 状态映射
  │          ├─ DeviceStateMachine::ReportFlowLight(kSuccess)  ← 结果灯亮起
  │          ├─ last_broadcast_state_ = kStopping              ← session.end 的
  │          │                                                    last_state 数据源
  │          └─ Wake() → RunLoop 被唤醒 → 消费 kRunOnStop Action
  ▼
Stopping.react(StopOkEvent) → Done → 一轮结束
```

## 三、对比：瞬态 vs 常规状态（同一个基类的两种用法）

| | 常规状态（Stopping/Verifying/Detecting…） | 瞬态（Entry/Finish/ResultObtained） |
|---|---|---|
| `enter` 第一行 | `BroadcastEnter(control, kKind)` | **空**（故意不广播） |
| 外部感知 | 日志 + change 广播 + 灯效 | 完全无感 |
| `LightFor` | override（各状态专属灯） | 不 override（反正不会被调） |
| 存在的意义 | 业务阶段，用户可感知 | 纯内部流转的"过路节点" |

### ⚠️ 瞬态关键约束：逻辑必须放 update，不能放 enter

**HFSM2 的 `enter(PlanControl&)` 没有 changeTo 能力**（进入中的状态不许宣布转向）。瞬态的使命天然是"干完活立刻跳走"（如 Finish：emit + changeTo\<Stopping\>），所以整套逻辑必须放在有 changeTo 的 `update(FullControl&)` 里。

执行保证：wrapper 的 `React()` = `react()` + `update()` 两连击——到达瞬态的唯一方式是某 react 内 `changeTo<瞬态>`，其后必有一次 `update()`，瞬态的 update **必然被执行**。

🔴 **警示（两连瞬态卡死）**：一次 React 只推进一个瞬态。若瞬态 A 的 update 内 `changeTo<瞬态 B>`，B 的 update 永远轮不到 → FSM 卡死（Finish 初版曾因此卡死，表现为识别成功后灯一直转圈）。瞬态必须直落**非瞬态**（常规状态/Head），项目内 RegisterEntry / VerifyEntry / ResultObtained / 3 个 Finish 全遵守此模式。

## 四、四钩子速查（enter / exit / react / update）

| 钩子 | 何时被调 | 通俗理解 | 控制对象 | 本项目约定 |
|---|---|---|---|---|
| `enter` | 状态被激活（转换计划执行时） | **登场**：亮灯、打点、挂闹钟 | `PlanControl&`（**不能 changeTo**） | 第一行 `BroadcastEnter`（瞬态除外）；`arm_timer`；写 ctx 时间戳 |
| `exit` | 状态被离开 | **谢幕**：摘干净 enter 挂的东西 | `PlanControl&` | 第一行 `disarm_timer()`（对称清理，无 timer 时 no-op） |
| `react` | 事件到达且本状态活跃 | **值守**：来事接事，不关心的穿透 | `EventControl&` | 只处理声明过的事件；**不做 IO**——重活 `request_action` 外包给 Controller |
| `update` | 每次框架心跳（无事件也调） | **巡检**：没事件也被拍一拍 | `FullControl&` | 瞬态推进（Entry/Finish/ResultObtained）；条件检查（Detecting 重试上限） |

### 控制对象能力矩阵

```
              changeTo   入队Action   发事件   arm/disarm timer
enter(Plan)      ❌          ✅          ✅           ✅
exit(Plan)       ❌          ❌          ❌           ✅(disarm)
react(Event)     ✅          ✅          ✅           ✅
update(Full)     ✅          ✅          ✅           ✅

能力递增：enter/exit < react ≤ update
enter 不能 changeTo ⇒ "想自动跳转？去 update"（瞬态模式的由来）
```


### 实战全流程：WaitingBindInput 的一生（HOST 录掌等待）

**剧情**：用户刷掌 → 云端说“此人未注册” → FSM 进 `WaitingBindInput` 等 40 秒，期间收银员在上位机录入信息下发，绑定成功。

```
═══════════ enter：状态登场（一次性）═══════════

[计划执行] WaitingBindInputState::enter(PlanControl&)
│  ① BroadcastEnter(control, kWaitingBindInput)
│       ├─ LOG_I("PalmFlow: RegisterSubmitting -> WaitingBindInput")
│       ├─ PalmFlowChange 广播 → PosNotifier（0xAA 通知上位机）
│       └─ ReportFlowLight(kLoading)          ← 灯开始转圈
│  ② ctx.enroll_wait_enter_ts = now()         ← wait_ms 计时起点
│  ③ ctx.enroll_wait = kBindInput             ← 登记"我在等绑定"（Finish 上报分派的依据）
│  ④ arm_timer(kBindInputRequest, 40s)        ← 挂闹钟：40s 内没等到就超时
│  ⑤ emit NeedBindInputEvent → 0xAC 通知上位机："请下发用户信息"

═══════════ react：值守期（事件来了才动，可来多次）═══════════

── 事件①：BindPalmRequestEvent（上位机 0x09 用户信息到了）──
WaitingBindInputState::react(BindPalmRequestEvent, EventControl&)
│  ① 校验 session_id（防上一轮的迟到事件串进来）
│  ② ctx.pending_bind_user_info = ev.user_info
│  ③ disarm_timer()                  ← 闹钟光荣退休（HTTP 在途期间不该被 124 打断）
│  ④ request_action(kProcessBindPalm) ← 只入队，react 立即返回！
│        │
│        └─▶ 【React 阶段结束 → wrapper 调 fsm_->update() → 本状态无 update → 跳过
│              → RunLoop 被唤醒 → Controller::ConsumeAction(kProcessBindPalm)
│                 co_await BindPalmFlow（/bind-palm HTTP，含内部重试）
│                 完成后 machine_->React(BindPalmResultEvent)】
│
── 事件②：BindPalmResultEvent（绑定结果回来，三分支）──
react(BindPalmResultEvent)
│  ├─ code==0 成功：
│  │    ctx.exit_code=0 + completion_source=kBindFinished
│  │    + changeTo<EnrollmentFinishState>      【记计划，不切换】
│  ├─ 116（掌库满）等不可重试失败：
│  │    ConvergeEnrollSubmitFailure → changeTo<EnrollmentFinishState>
│  └─ 网络抖动等可重试失败：
│       留在本状态 + 发 0xAC 错误码通知，等收银员重试
│       （不重挂 timer —— 40s 首窗继续倒数，重试不续命）

── 事件③：StateTimeoutEvent（40s 到了还没等到）──
react(StateTimeoutEvent)
│  ctx.exit_code = 124 (PALM_SESSION_TIMEOUT)
│  ctx.completion_source = kNormal
│  changeTo<EnrollmentFinishState>

═══════════ exit：状态谢幕（与 enter 对称）═══════════

[计划执行] 离开本状态前：
WaitingBindInputState::exit(PlanControl&)
│  └─ disarm_timer()        ← 关闹钟（若已 disarm 则无害 no-op）
│     —— 至此本状态对系统的影响全部清零，不留悬空 timer

═══════════ update：无事件的"巡检拍"（本状态没用它，借用邻居演示）═══════════

WaitingBindInput 是纯事件驱动，没有 update。需要 update 的两类典型：

① 瞬态推进 —— EnrollmentFinishState（下一步要进的收敛桥）：
EnrollmentFinishState::update(FullControl&)
│  ├─ EmitBindingResult(ctx, exit_code)     ← palm.binding.result 在此发出
│  └─ DispatchResultExit → changeTo<Stopping>
│     （enter 里干不了 changeTo → 只能借 update 这一拍跳走）

② 条件检查 —— DetectingState：
DetectingState::update(FullControl&)
│  └─ if (retry_count > max_opt_retry) → 收敛结束（无事件也能主动离场）
```

### timer 生命周期约定（对称原则）

`enter` 里 `arm_timer(kind, duration)` ↔ `exit` 里 `disarm_timer()`——一挂一摘严格配对。未挂 timer 的状态调 disarm 是无害 no-op。特例：等待态在收到数据**转入 HTTP 阶段**时主动 disarm（如 WaitingBindInput 收到 BindPalmRequest），避免 HTTP 在途期间被 124 打断。

## 五、21 个状态清单（分类速查）

| 分类 | 状态 | 特征 |
|---|---|---|
| **Head**（5） | RootHead / RunningHead / BizProcessHead / RecognizingHead / RegisteringHead / VerifyingHead | Composite 父状态；RunningHead 承载 StopReq/ScanComplete 全局拦截；不调 BroadcastEnter |
| **常规 leaf**（9） | Starting / Detecting / PalmEntered / OptPassed / LocalRecognizing / Recognizing(Cloud) / RegisterSubmitting / WaitingBindInput / WaitingScanInput / RegisterByCodeSubmitting / Verifying / VerifySubmitting / WaitingHostAck | enter 广播 + LightFor override；timer 挂/摘对称；react 处理业务事件 |
| **瞬态 leaf**（6） | Created / Done / RecognizeEntry / RegisterEntry / VerifyEntry / RecognitionFinish / EnrollmentFinish / VerificationFinish / ResultObtained | enter 空、不广播、不 override LightFor；逻辑在 update（changeTo 直落非瞬态） |

> Head 实际 6 个（含 RootHead）；leaf 计 15 个常规/瞬态混合——总数以 `palm_flow_fsm_def.h` 为准，此处按用途分类便于记忆。

## 六、一句话总结

`PalmFlowStateBase` = **给全部 21 个状态统一"出生证明"（HFSM2 类型）+ "发言人"（BroadcastEnter/LightFor：状态一进入就对外广播变化、定灯色、唤醒调度）+ "外交豁免"（react 穿透：不关心的事件静默放过）** 的最小公共底座——业务逻辑在子类，它只负责"每个状态如何被外部世界看见"。
