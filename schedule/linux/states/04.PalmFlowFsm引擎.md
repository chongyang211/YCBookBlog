

## `palm_flow_fsm_def.h` 的作用

这是状态机的**结构定义文件**——前面三问里的 `FlowAction`/`FlowContext`/`FlowEvent` 在这里是“词汇”，这个文件才是把 HFSM2 引擎、状态层次和转移图**装配起来**的地方。

用刷掌业务串起整个状态机，跟着**一位顾客的真实刷掌经历**走一遍，看状态机各角色在业务里对应什么。业务主线（ hybrid 模式，最完整的剧情）

```text
顾客伸手刷掌
   │
   ▼
【Detecting 检测】── 手掌进没进框？没进就一直等
   ▼
【PalmEntered → OptPassed 优选】── 拍到最好的那一帧（这就是上报里 opt_frame_image_id 的来源）
   ▼
【RecognizingHead 识别窗】
   ├─ 端侧识别？云端识别？── 这里分派（LocalRecognizing / Recognizing 两个叶子）
   │
   ├─ 认出来了 → 【RecognitionFinish 结算台】📊 发 palm.recognition.result (result_code=0)
   │
   └─ 没注册（306）→ 结算台照样开发票 📊 palm.recognition.result (306, srv=100025)
        │                  ——这就是"中途成绩单"：识别这步失败了，但剧情没完
        ▼
【RegisteringHead 注册窗】—— 顾客是新客，得先录掌
   ├─ 探测（RegisterSubmitting）
   ├─ 等顾客按提示操作（WaitingBindInput / WaitingScanInput）
   └─ 录入完成 → 【EnrollmentFinish 结算台】📊 发 palm.enrollment.result / palm.binding.result
        ▼
（若需加验）【VerifyingHead 加验窗】
   └─ 0xAB 通知上位机 → 等 0x0D → 提交 /verify-palm
       └─ 【VerificationFinish 结算台】📊 发 palm.verification.result
   ▼
【ResultObtained 总出口】── 发 0xA3 结果给上位机
   ▼
【WaitingHostAck】── 等上位机签收（不签=160，业务其实已成功）
   ▼
【Stopping → Done】── 会话拆除
   └─ 📊 发 palm.session.end —— 一场刷掌的唯一"剧终行"
```

对应到设计角色

| 设计角色 | 刷掌业务含义 |
|---|---|
| **Head（父状态）** | 它不是某个具体步骤，而是“这块业务的规矩或者边界” |
| **State（叶子）** | 业务里的每一步：伸手、优选、发识别请求、等绑定…… |
| **RecognizingHead 等三个 Head** | 识别窗/注册窗/加验窗——**三类业务的边界**，事件类型（recognition/enrollment/verification）就按窗口归属划分 |
| **RunningHead** | “本次刷掌从伸手到结束”的全程——**中途顾客抽手（abort）**，大厅直接送客 |
| **BizProcessHead** | “业务办理中不可打断”——识别 HTTP 还没回来时，上位机的取消请求要排队 |
| **Finish 结算台** | **五个事件里前三个的产生点** |
| **瞬态** | 不产生事件、不留痕迹的过场：比如“识别→注册”的切换指引 |

### 1.状态的“工具箱”

`PalmFlowFsmContext`（第 37–51 行），HFSM2 注入的业务 Context，状态通过 `control.context()` 访问：

- `biz_ctx` — 就是上一问的 `FlowContext`（业务数据黑板）；
- 五个 `std::function` 闭包 — 状态对机器的全部操作接口：`request_action`（入队 Action）、`emit_event`（上行事件）、`broadcast`（状态变化广播）、`arm_timer`/`disarm_timer`（状态超时）。由 `PalmFlowMachine` 构造时绑定（即上次看到的 `DoRequestAction` 等 wrapper）。

用闭包而非直接引用 wrapper class，是为了**打破循环依赖**：状态头文件只依赖本文件 + state_base。

### 2.HFSM2 配置与类型别名（第 55–56 行）

`C` / `M` 把 `PalmFlowFsmContext&` 配置为 HFSM2 的 Context 类型，`FSM` 别名（第 208 行起）就是**整棵状态树的声明**。

### 3.状态类前向声明（第 60–86 行）— 状态的“花名册”

Head = Composite（子状态机区域）的父状态，`M::Composite<RunningHead, ...>` 语法中，第一个模板参数就是 Head。它有三重身份：

| 身份 | 说明 | 本文件实例 |
|---|---|---|
| **区域标识** | 它“活动”= 其子树中某个叶子在活动；进入区域即进入它 | `RunningHead` 活动 = 正处于运行期某个子状态 |
| **可编程状态** | 自己也有 enter/exit/**react**——react 用于**区域级统一事件处理**，覆盖区域内所有子状态，子状态无需各自重复 | `RunningHead.react` 统一处理 `StopReq(kAbort)` → 覆盖全部运行子状态直转 Stopping（:148, :198-199 注释） |
| **路由锚点** | 外部可用 `IsActive<XxxHead>()` 判断"当前在哪类业务” | Controller 用 `IsActive<VerifyingHead>()` 决定 HTTP 路由到 `/verify-palm` 还是 `/recognize`（:209-210） |

6 个 Head（`RootHead`/`RunningHead`/`BizProcessHead`/`RecognizingHead`/`RegisteringHead`/`VerifyingHead`），具体行为实现在 `palm_flow_states.h/.cpp`。本文件 6 个 Head 的职责分层：

| Head | 区域语义 | 统一职责 |
|---|---|---|
| `RootHead` | 整棵状态机根 | — |
| `RunningHead` | 一轮刷掌的运行期 | **StopReq(kAbort) 统一出口**：任意运行子状态直接进 Stopping，跳过 ResultObtained 不发 0xA3 |
| `BizProcessHead` | 业务处理期（识别/注册/加验的共同父） | **不可打断边界**：其子树沿用 FSM 级 IsInterruptible 规则（HTTP in-flight 不被撕掉）；Strategy Verdict（V_*）由其子状态派发 |
| `RecognizingHead` | 识别子树（端侧/云端分派） | 子树内含 RecognitionFinish 收敛桥 |
| `RegisteringHead` | 注册子树（探测/等待绑定/反扫码） | 同上（EnrollmentFinish）；Waiting* 归入即继承不可打断规则（:230-236 注释的设计理由） |
| `VerifyingHead` | 加验子树 | 同上（VerificationFinish） |

### 4.状态机的“地图”

层次结构（HFSM2 三层 Composite）：

```
RootHead
├── Created / Starting                          （叶子）
├── Composite<RunningHead>                      （运行期区域）
│     ├── Detecting / PalmEntered / OptPassed   （叶子）
│     ├── Composite<BizProcessHead>             （业务处理区域）
│     │     ├── Composite<RecognizingHead>      识别子树（4 叶）
│     │     ├── Composite<RegisteringHead>      注册子树（6 叶）
│     │     ├── Composite<VerifyingHead>        加验子树（4 叶）
│     │     ├── ResultObtained / WaitingHostAck （叶子）
│     └──（StopReq 在 RunningHead.react 拦截）
└── Stopping / Done                             （叶子）
```

层级本身承载语义：`StopReqEvent` 由 `RunningHead.react` 统一处理（任意运行子状态都可被打断 → kAbort 直转 Stopping）；而 BizProcessHead 子树不可打断（业务提交中不许停）。

一句话：Head 是“区域”——决定事件拦截范围（如 abort 统一出口）、子树归属（如不可打断规则）和外部路由判据；State 是“业务步骤”——真正干活的地方。判断一个新逻辑放哪：跨子状态统一处理 → 放 Head；单个业务步骤 → 放叶子；多个叶子共用一段收敛逻辑 → 收敛桥（Finish 模式）。

### 5.State（叶子状态）

具体业务状态。直接承载状态行为（enter/exit/react/update），状态变迁发生在叶子之间。按形态分四类：

| 类别 | 状态 | 特点 |
|---|---|---|
| 稳态（等待/处理） | Detecting / PalmEntered / OptPassed / Verifying / WaitingBindInput / WaitingScanInput 等 | 停留等事件/超时 |
| 提交态 | Recognizing（云端 HTTP）/ RegisterSubmitting / VerifySubmitting / RegisterByCodeSubmitting | 发请求等响应 |
| **瞬态** | 三个 `*Entry`（enter 空、update 直转）、`ResultObtained`（update 按 completion_source 分派）、三个 `*Finish`（收敛桥：update 发业务事件后 DispatchResultExit） | 一拍即走；**enter 里不能 changeTo** 是 HFSM2 约束，瞬态逻辑全放 update |
| 终态壳 | Created / Starting / Stopping / Done | 生命周期边界 |

│    │                                   # kNormal/kBind/kScan 路径另 emit OnSessionCompleteEvent

文件里的大段 ASCII 注释就是**完整状态转移图**：`Created→Starting→Detecting→PalmEntered→OptPassed` 主干、三条决策边（`V_Submit`→识别 / `V_EnterRegister`→注册 / `V_Complete`→出口）、加验子树流程、录掌等待的重试循环与 124 超时、`ResultObtained`→`WaitingHostAck`→`Stopping`→`Done` 的收尾链。

一句话总结：`palm_flow_fsm_def.h` 是状态机的**装配图纸**——声明状态层次树（`FSM` 别名）和状态的执行环境（Context + 闭包 API），转移逻辑图以注释形式画在这里，具体状态行为在 `palm_flow_states.cpp`，运行时由 `palm_flow_machine.cpp` 实例化。
