
## Abort 结束流程分析

`abort` 是状态机的**静默终止路径**——不产生任何业务结果上报，直接收尾退出。与正常完结路径（ResultObtained → 0xA3 → WaitingHostAck/Stopping）的关键区别是**全程绕过结果出口**。

### 触发源（三个入口，殊途同归）

```
① 上位机 0x05 StopPalm
   PosRequestHandler → Controller::RequestStop → DeviceFsm 退 PalmRunning
   → IGracefulExit::RequestExit (controller:1675)
      └─ 短路检查: IsBizFinished() 已在收尾则直接返回
      └─ machine_->React(StopReqEvent{})

② DeviceFsm 抢占/切换（如自检、升级接管 PalmRunning）
   → graceful exit → 同上调 RequestExit

③ 启动失败
   StartingState.react(StartFailEvent) → completion_source=kAbort → Stopping
```

### FSM 内部流转（四步）

```
① RunningHead.react(StopReqEvent)          (states.cpp:190)
   运行区任意子状态（Detecting/PalmEntered/识别/注册提交中…）
   一处拦截，写 ctx.completion_source = kAbort
   → changeTo<Stopping>                    ← 跳过 ResultObtained，不发 0xA3

② StoppingState.enter                      (states.cpp:302)
   ├─ BroadcastEnter（LightFor 对 kAbort 返 kIdle——不闪结果灯，避免闪黄灯）
   ├─ request_action(kRunOnStop)           ← 唯一保留的工单：停 SDK
   └─ kAbort 分支【不 emit OnSessionCompleteEvent】——静默，无结果展示

③ Controller: ConsumeAction(kRunOnStop)
   StopPalmDetect + StopCodeScan + DisconnectSdkSignals → React(StopOkEvent)

④ Stopping.react(StopOkEvent) → changeTo<Done>   (states.cpp:338)
   DrainActionsUntilDone 检测 Done 跳出 → ResetRoundState（断信号/清 pending） 本轮生命周期终结
```

### Abort 与正常完结的差异对照

| 环节 | 正常完结 (kNormal/kScan/kBind) | Abort (kAbort) |
|---|---|---|
| ResultObtained | 经过，按完结源发 0xA3 | **绕过** |
| 0xA3 结果报文 | 发给上位机 | **不发** |
| OnSessionCompleteEvent | Stopping 发出 → 触发结果灯 3s 窗口 + ScheduleAutoStart | **不发**（纯静默） |
| 结果灯 | kSuccess/kWarning | kIdle（保持原状） |
| WaitingHostAck | 可能经过 | 不可能 |
| kRunOnStop 停 SDK | 有 | 有（唯一共同点） |
| 轮间清理 | ResetRoundState | ResetRoundState |

### 两个保护性细节

1. **重入保护**：`RequestExit` 先查 `IsBizFinished()`（Stopping/Done 状态）——如果一轮已在正常收尾，重复的 Stop 请求直接忽略，不会把 Stopping 再次打断；
2. **不可打断区的例外**：`IsInterruptible()` 对 BizProcessHead 返回 false（提交中不打断），但这是给 DeviceFsm 抢占仲裁用的——一旦真的走到 `React(StopReqEvent)`，RunningHead 依然会兜底拦截（FSM 级最终防线）。

一句话：**abort = “写 kAbort 标记 → 跳过所有结果上报 → 只停 SDK → Done”**，语义是“这一轮作废，什么都不上报，安静退出”。


## 用一个场景理解 Abort

**场景：顾客正在刷掌，掌还没完全按好，收银员点了“取消”**

```
时刻 T0  顾客上掌，状态机走到 Detecting/PalmEntered，正在采集
时刻 T1  收银员点取消 → 上位机发 0x05 StopPalm
时刻 T2  Controller 收到 → React(StopReqEvent)
时刻 T3  RunningHead 拦截：completion_source=kAbort → 直跳 Stopping
时刻 T4  停检测、关灯 → Done，本轮作废
```

这一轮**没有产生任何业务结果**：掌没识别成功也没识别失败，POS 端不需要收到“成功/失败”报文，也不该弹结果页。所以：

- ❌ 不发 0xA3（没有“结果”可报）
- ❌ 不走 ResultObtained（结果出口没意义）
- ❌ 不亮成功/失败灯（保持原状）
- ✅ 只做一件事：**把 SDK 干净地停下来**，然后 Done

## 类比

正常完结 = 网购正常签收：下单（识别/注册请求）→ 出库发货（ResultObtained）→ 生成交易记录（0xA3）→ 展示订单详情（结果灯）。

Abort = 下单后立刻取消订单：但商家仓库不知情还是把货发了——订单系统不该把这笔“已取消订单的发货”记成一笔成功交易。abort 抑制就是订单系统里“已取消的订单，后续动作一律不记账”的规则，关单（Done）。

## 三个触发时机，同一个含义

| 场景 | 触发 |
|---|---|
| 收银员主动取消 | 0x05 StopPalm |
| 设备要做别的事（升级/自检抢摄像头） | DeviceFsm 抢占 → graceful exit |
| SDK 都没启动成功 | StartFail → 也按 abort 静默退 |

**一句话：Abort = “这轮不算了，安静收摊”**——保证取消操作不会让上位机误以为收到了一次刷掌结果，也不会留下亮着的检测灯和没关的摄像头。
