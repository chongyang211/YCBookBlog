
## 一、码格式与识别

激活码支持三种格式（`IsActivationCode` 轻量前缀检测，`activation_service.h:110-117`）：
- `wxpact://` 前缀（base64 protobuf）
- `action:100000000,...` 扁平格式（palm_core SDK ActionCodeResult）
- `[[...]]` JSON 数组格式

**注意**：与操作码/License 的分发顺序在 `OnCodeScanResult` 里是互斥先到先得——激活码只在 **设备未激活** 且激活状态机处于 `WaitingForQRCode` 时才被消费，其余状态静默吞掉（防止激活码误当业务码上报 POS）。

## 二、全流程状态机（ActivationFsm，跑在 LicenseThread）

```
设备启动 → Checking（检查激活状态）
   │ CheckActivationStatus：SE 出厂状态 + 域名双重存储对齐（prop 优先，SE 备份）
   ├─ 已在册 ──────────────────────────→ Activated（正常开机路径）
   └─ 未在册 → NotActivated → WaitingForQRCode
                 │ OnEnter：StartCodeScan(kScanActivation) 开扫码器 ⭐
                 │ 等运维扫激活码
                 ▼
          扫码 → OnCodeScanResult 分发 → TryHandleScanCode → ReactQRCodeScanned
                 │ ① QRCodeScanned：解析二维码（三种格式）+ 域名证书校验
                 │    → PalmActivationCode{session_id, server_domain}
                 │    → StoreServerDomain（prop + SE 双写）
                 ▼
           StartActivation ② POST /activation/devices/{sn}/activation/start
                 │ → 获取服务端密钥 server_keys_
                 │ （DeviceFsm: RequestEnter(kActivating)，被拒如 OTA 中 → 终止）
                 ▼
           KeyExchange ③ server_keys_ 与 SE 芯片交换密钥
                 │ → POST confirm-key-change → 得 confirm_code_
                 ▼
           ConfirmKeyExchange ④ 用 confirm_code_ 向 SE 芯片确认写入
                 │ ★ 激活成功的关键步骤（密钥真正落进 SE 硬件）
                 ▼
           Activated → is_activated_=true → DeviceFsm 退回稳态（仲裁 Idle/LicenseUnauthorized）
```

**任一步失败** → Error 状态 → `IsActivationErrorRetryable` 判断：
- **可重试**（扫码/解析/域名/start/密钥交换/confirm 失败 + 网络类 20101/20102/20104/20407）→ 回 `WaitingForQRCode` 重新扫码
- **不可重试**（fatal，如 SE 芯片错误）→ 停在 Error 等人工介入

## 三、关键设计点

| 设计 | 说明 |
|---|---|
| **域名双重存储** | `ro.vendor.palmactivation.server_host`（首选）+ SE 芯片（备份），两处对齐校验——防单点丢失导致“已激活却读不到域名” |
| **SE 硬件密钥** | 激活的本质是把服务端签发的密钥安全写进 SE 芯片（`ConfirmKeyExchangeToSE`），之后所有云端通信用它认证；SE 不可调用有独立状态 `kPalmServiceUnavailable` |
| **线程模型** | 整个 FSM + 四步协议都钉在 LicenseThread（事件 Post 过去、协程也在它的 executor 上），扫码事件从 MainThread 跨线程投递 |
| **DeviceFsm 联动**（v6.4） | 激活开始抢占 `kActivating`（OTA/自愈中会被拒）；成功 `RequestExitToSteady` 仲裁；失败退 `kUnactivated` |
| **时序敏感点** | `OnEnterActivated` **必须先** `is_activated_=true` 再广播 phase——否则 Idle 迁移守卫（查 IsActivated）会拒绝切换，设备卡死在 kActivating（代码注释里记录过这个 bug） |
| **Step 5 缺席** | `ConfirmPalmDeviceActivation` 定义了但 Linux 版不需要（无场景选择/绑定步骤） |

## 四、错误码段（404xx，`unified_errcode_iot.h`）

| 码 | 含义 |
|---|---|
| 40406 / 40417 / 40418 | 密钥交换 / 交换确认 / 激活确认失败 |
| 40410 | 激活状态检查失败 |
| 40412 / 40413 | 扫码失败 / 二维码解析失败 |
| 40414 / 40415 | 域名校验失败 / 域名未设置 |
| 40416 | start 接口失败 |
| 40419 | SE 芯片操作错误 |
| 40427 | 设备未在册（服务端 268566642 映射） |

## 五、日志锚点（排查用，按时间序）

```
ActivationController: CodeScan started, waiting for QR code   ← 开扫码等码
ActivationController: OnEnterQRCodeScanned                    ← 码被识别
  OnEnterQRCodeScanned: Parsing QR code data, size=
    Session ID: / Server Domain:                              ← 解析成功
StartPalmDeviceActivation failed/success                     ← Step2
ExchangeAndConfirmKeys failed/success                        ← Step3
ConfirmKeyExchangeToSE success - Activation completed!       ← Step4 成功
ActivationController: Error is retryable / fatal             ← 失败定性
ActivationController: OnEnterActivated - Device is now activated ← 终态
```

**一句话总结**：激活码 = 未激活设备的“出生证”——扫码拿到服务端地址，走四步协议（start → SE 换钥 → confirm → SE 确认写入）把信任根写进 SE 硬件；可重试错误回到等码状态，重扫即重试。
