# 操作码（qcloud://）业务全流程

> 范围：`src/service/operations/`（QRCodeOperationHandler / ActionCodeProcessor / ActionCodeVerifier / CommonKeyManager）。操作码是**扫码拦截式设备运维**：运维人员出示特制二维码（`qcloud://` 前缀），设备扫码拦截后执行运维动作（重启/恢复出厂/NTP 对时/进调试/进检测/网络诊断），并经 0xAA 通道把结果通知上位机弹窗展示。
>
> 与《01.扫码流程全流程链路.md》的关系：操作码是扫码分发**第一优先级**——`TryHandle` 返回 true 时 PalmCoreManager 不发 `CodeScanResultSig`，运维码与业务码物理隔离，互不干扰。

**组件分工**：

| 组件 | 职责 |
|---|---|
| `QRCodeOperationHandler` | 编排：扫码拦截、设备态 `kOpProcessing` 进入/退出、6s 防抖、35s 超时保护、0xAA 结果通知 |
| `ActionCodeProcessor` | 解析（base64 -> protobuf）、三级风险分派、有效期/查重前置检查、执行动作 |
| `ActionCodeVerifier` | RSA SHA256 验签 |
| `CommonKeyManager` | 公共验签公钥管理（预加载/缓存/拉取）+ 高风险一次性 detail 获取 |

## 一、码的格式与安全分级

```
qcloud:// + base64( protobuf ActionCode{ sign_type, sign, payload } )
                        payload = ActionCodePayload{ action_code, valid_type, end_time, verify_code }
```

| 风险级 | action_code 段 | 签名要求 | 验证方式 | 附加校验 |
|---|---|---|---|---|
| 低风险 | 10000~19999 | `SIGN_TYPE_NONE` 免签 | 无（码号段即约束） | 无 |
| 中风险 | 20000~99999 | 公钥验签 | **离线验签**：缓存公共公钥（无缓存则在线拉取） | 设备已激活 + 有效期校验 |
| 高风险 | 100000~199999 | 公钥验签（**强制服务端取钥，不用缓存**） | 验签后按 verify_code 换服务端详情（一次性，服务端二次确认） | verify_code 10min 一次性防重 + 已激活 + 有效期 |

**前置检查**（中/高风险公共，processor.cpp:110-156）：

1. 设备已激活（`ActivationController::IsActivated`）——未激活设备不可被运维码操作；
2. 有效期：`VALID_TYPE_PERIOD` 时 `now > end_time + 60s` 判过期（**60s 时钟容差**，吸收设备时钟偏差）；
3. 高风险专属：`verify_code` 非空 + 端侧查重（内存 set + deque，**TTL 600s** 过期淘汰，重复扫码报 `ALREADY_USED`）。

## 二、全流程（一个码从扫到执行）

```
扫码 -> PalmCoreManager::OnCodeScanResult（明文日志）
  |
  v TryHandle（qrcode_operation_handler.cpp:55）—— 三重拦截
  |- 前缀不是 qcloud:// -> 放行走业务码链路
  |- processing_ 已在处理 -> return true 静默拦截（防 SessionDriver 接手）
  |- 6s 同码防抖命中 -> return true 静默拦截（覆盖上位机弹窗倒计时 5s+余量）
  |
  v ProcessActionCodeFlow 协程（35s 总超时保护 = NTP 15s + 网络 30s + 余量）
  |- (1) RequestEnter(kOpProcessing) -- 设备状态机让位（刷掌让位）
  |     被拒 -> 0xAA kOpFailed "device busy" + 记防抖 -> 退出
  v
  |- (2) ActionCodeProcessor::ProcessActionCode
  |     前缀校验 -> base64 -> protobuf(ActionCode) -> payload
  |     按 sign_type 分派：
  |       低风险 ----------------------> 直接执行
  |       中风险 -- 公钥(缓存->服务端拉取) -> 验签 -> 执行
  |       高风险 -- 公钥(强制拉新) -> 验签 -> verify_code 换服务端详情 -> 解析完整码 -> 执行
  |                 （防重: verify_code 10min TTL，重复码报 ALREADY_USED）
  v
  |- (3) ExecuteAction（action_code_processor.cpp:288）
  |
  |- 等待完成：sam condition_variable || 35s 超时
  |   （同步完成已检测跳过等待——notify_one 先于 async_wait 会丢失的坑已处理；
  |    超时 -> 0xAA kOpFailed "processing timeout" + 记防抖 + 退出）
  v
  |- (4) 失败 -> 0xAA kOpFailed + 退稳态 + 记防抖
  |- (5) 成功且 irreversible（重启/重启App/恢复出厂——动作已执行）
  |     -> 直接收尾，不发通知不退状态（进程即将消亡）
  |- (6) 成功非 irreversible -> 0xAA{event} -> 退稳态 + 记防抖
  ExitToSteadyIfProcessing：仅当仍处于 kOpProcessing 才退
  （防 kInspecting 等高优先级态抢占后误退出）
```

**0xAA 事件类型**（operations::EventType）：0x01 重启 / 0x02 恢复出厂 / 0x03 NTP 完成 / 0x04 进调试 / 0x05 操作失败 / 0x07 进检测 / 0x09 网络诊断（0x06 被摄像头致命错误占用，禁复用）。`notify_sender_` 由 PosRequestHandler 注入（与 DeviceAction 同款 0xAA 通道）。

## 三、7 个已实现动作

| action_code | 动作 | 风险级 | 通知事件 | 特殊处理 |
|---|---|---|---|---|
| 10003 | 网络检测 | 低 | `kNetworkDiagnosis` | 结果由上位机 UI 展示 |
| 10007 | NTP 对时 | 低 | `kNtpSyncOk`/失败 | SyncTime 最长 15s，丢线程池执行后跳回主线程 |
| 10008 | 进入 Debug | 低 | `kEnterDebug` | 仅通知，设备侧无状态变化（调试由上位机处理） |
| 10009 | 进入设备自检 | 低 | `kEnterInspect` | DeviceInspectController 内部申请 kInspecting |
| 20001 | 重启设备 | 中 | `kReboot` | **不可逆**：执行后直接返回，不发通知不退状态 |
| 20002 | 重启应用 | 中 | `kReboot` | 同上 |
| 100004 | 恢复出厂 | 高 | `kFactoryReset` | 同上（高风险全链路校验） |

**不可逆动作的特殊语义**（`ProcessActionCodeFlow:152-156`）：重启/恢复出厂执行后进程即将消亡，跳过通知和状态退出，直接 `co_return`。

## 四、配套机制

| 机制 | 说明 |
|---|---|
| **公钥预载** | `Init` 起 10s 周期任务预载通用公钥（拉到即停），中风险验签优先用缓存——保证首次扫码时缓存已就绪 |
| **有效期** | `VALID_TYPE_PERIOD` 时校验 end_time，含 60s 时钟容忍（设备时钟偏差） |
| **一次性防重** | 高风险 verify_code 存 10min TTL 队列，防同一授权码重复执行恢复出厂；最终一次性保证在服务端 detail 分配侧（端侧重启失忆由服务端兜底，两层缺一不可） |
| **高风险强制拉新钥** | 不用缓存公钥——防公钥轮换后的陈旧密钥风险 |
| **防抖一致性** | 成功/失败/超时/被拒四种结局**都**记 6s 防抖——不支持的操作码重试也不会成功 |
| **状态抢占保护** | 退出时校验仍在 `kOpProcessing` 才退（可能已被自检 kInspecting 抢占） |

## 五、日志锚点（排查用）

```
QRCodeOperationHandler: action code detected, len=       <- 识别为操作码
QRCodeOperationHandler: already in progress / （防抖静默）
QRCodeOperationHandler: RequestEnter rejected            <- 设备忙被拒
ActionCodeProcessor: parsed code={}, sign_type={}        <- 解析出动作号与签名类型
ActionCodeProcessor: execute action_code={}              <- 实际执行
QRCodeOperationHandler: notify host, event=0xXX          <- 通知上位机
QRCodeOperationHandler: failed, ec=, msg=                <- 失败原因（404xx 错误码段）
QRCodeOperationHandler: processing timeout               <- 35s 超时
```

排查提示：

- "码已用报错"先分清是端侧 10min TTL 拒绝（`duplicate verify_code`）还是服务端 detail 已消费（`fetch detail failed`）；
- 高风险流程 detail 拉取阶段回调槽被移出，理论上存在超时与完成双发通知的极小窗口（35s > 拉钥+detail 各 10s）；
- 防抖 6s 与宿主弹窗 5s 倒计时耦合（`kDebounceInterval`）——宿主改倒计时需同步此处常量。

## 六、一句话总结

**操作码是"扫一扫配置设备"的通道，按风险分级做渐进式校验（免签 -> 验签 -> 服务端二次确认），互斥 + 双重防抖保证同一码不被反复触发，结果经 0xAA 通知上位机弹窗**。与业务码链路的分岔点就在分发链第一优先级 `TryHandle`。
