## 01.Commit规范概述

### 1.1 为何需要提交规范

**疑惑**：代码能跑就行，commit message随便写不行吗？

**答疑**：当你半年后需要查找一个Bug的引入时间，面对以下两种提交记录：

```
// 无规范的提交记录
fix bug
update
修改了一些东西
test
asdfgh

// 有规范的提交记录
fix(login): 修复登录页面密码输入框无法获取焦点的问题 #1234
feat(order): 新增订单批量导出功能，支持CSV和Excel格式
refactor(network): 将OkHttp3升级到4.x，统一超时配置
```

哪种能快速定位问题一目了然。规范化的提交信息是**项目的可追溯文档**。

### 1.2 规范的核心价值

| 价值 | 说明 |
|------|------|
| 自动生成CHANGELOG | 工具可从commit自动生成版本变更日志 |
| 快速定位问题 | `git log --grep="fix(login)"` 精确搜索 |
| 触发CI/CD | 特定类型的commit可触发自动化流程 |
| 代码审查效率 | reviewer 一看标题就知道改了什么 |
| 团队协作 | 统一风格，降低沟通成本 |


## 02.CommitMessage格式

### 2.1 标准格式定义

采用 **Conventional Commits** 规范（Angular 风格）：

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **type**（必填）：提交类型
- **scope**（可选）：影响范围（模块名）
- **subject**（必填）：简短描述，不超过50个字符
- **body**（可选）：详细描述，说明 what 和 why
- **footer**（可选）：关联issue编号、Breaking Changes

### 2.2 类型标识说明

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(user): 添加手机号注册功能` |
| `fix` | 修复Bug | `fix(cart): 修复数量为0时仍可结算的问题` |
| `docs` | 文档变更 | `docs(api): 补充接口返回码说明` |
| `style` | 格式调整（不影响逻辑） | `style: 统一缩进为4个空格` |
| `refactor` | 重构（不新增功能/不修Bug） | `refactor(db): 提取公共查询方法` |
| `perf` | 性能优化 | `perf(list): 列表滚动使用虚拟化渲染` |
| `test` | 测试相关 | `test(login): 补充登录失败的单元测试` |
| `build` | 构建工具/依赖变更 | `build: 升级Gradle到8.0` |
| `ci` | CI/CD配置变更 | `ci: 添加自动化代码检查流程` |
| `chore` | 其他杂项 | `chore: 更新.gitignore` |
| `revert` | 回退提交 | `revert: 回退feat(user)的注册功能` |

### 2.3 scope范围说明

scope 标识此次修改影响的模块，常见取值：

```
// Android项目
feat(login): ...       // 登录模块
fix(network): ...      // 网络层
refactor(base): ...    // 基础库

// Web项目
feat(component): ...   // 组件
fix(router): ...       // 路由
perf(bundle): ...      // 打包

// iOS项目
feat(UIKit): ...       // UI层
fix(CoreData): ...     // 数据层
```

### 2.4 正确和错误示例

**正确示例**：

```bash
feat(payment): 接入微信支付SDK，支持App支付和H5支付

- 集成微信SDK v6.8.0
- 封装统一支付接口PaymentManager
- 添加支付结果回调处理

Closes #456
```

```bash
fix(image): 修复大图加载时OOM崩溃

问题原因：未对超大图片进行采样压缩
解决方案：加载前通过BitmapFactory.Options计算采样率

Fixes #789
```

**错误示例**：

```bash
# 错误1：无类型标识
修复bug

# 错误2：描述模糊
fix: update

# 错误3：描述过长（超过50字符）
feat: 添加了一个非常复杂的用户登录注册找回密码修改密码的完整功能模块

# 错误4：中英混杂不统一
fix(login): fixed 登录 bug
```


## 03.分支管理规范

### 3.1 分支命名规则

```
分支类型        命名格式                    示例
───────────    ─────────────────────      ────────────────────
主分支          main / master              main
开发分支        develop                    develop
功能分支        feature/<模块>-<描述>       feature/login-wechat
修复分支        fix/<issue号>-<描述>        fix/789-oom-crash
发布分支        release/<版本号>            release/2.1.0
热修复分支      hotfix/<版本号>-<描述>       hotfix/2.0.1-payment
```

### 3.2 分支工作流

```
main ──────●──────────────●──────────── (生产环境)
            \            /
develop ─────●──●──●──●──●───────────── (开发环境)
              \  \     /
feature/A ─────●──●───/                 (功能开发)
                \
feature/B ───────●──●                   (功能开发)
```


## 04.代码审查规范

### 4.1 PR提交规范

Pull Request 描述模板：

```markdown
## 变更说明
简述本次PR的目的和主要变更内容

## 变更类型
- [ ] feat: 新功能
- [ ] fix: Bug修复
- [ ] refactor: 重构
- [ ] perf: 性能优化

## 影响范围
涉及的模块和可能影响的功能

## 测试说明
如何验证本次变更

## 关联Issue
Closes #xxx
```

### 4.2 审查检查清单

- [ ] 代码符合项目编码规范
- [ ] commit message 符合规范
- [ ] 无硬编码的敏感信息（密钥、密码等）
- [ ] 新增代码有必要的注释
- [ ] 已考虑边界情况和异常处理
- [ ] 无明显的性能问题


## 05.跨平台对比

### 5.1 各平台Git规范

| 平台/公司 | 规范标准 | 工具支持 |
|-----------|---------|---------|
| Google | Angular Commit Convention | commitlint |
| 阿里 | 阿里Java开发手册 | p3c插件 |
| 微软 | Conventional Commits | husky + lint-staged |
| 开源社区 | Semantic Versioning | semantic-release |

**自动化工具推荐**：

```bash
# 安装 commitlint（Node.js项目）
npm install --save-dev @commitlint/cli @commitlint/config-conventional

# 配置 husky 钩子（提交时自动校验）
npx husky add .husky/commit-msg 'npx commitlint --edit $1'

# Android/Java 项目可使用 Git Hook
# .git/hooks/commit-msg 中添加正则校验
```
