## 01.漏洞与 bug 的边界

### 1.1 一个 bug 的"上位过程"

不是所有 bug 都是漏洞。一个 bug 要变成"可被利用的漏洞"，通常要走完三步：

```
[内存破坏]   攻击者能控制某段内存的内容或地址
   │
   ▼
[控制流劫持] 内存破坏导致 PC（程序计数器）落到攻击者预期位置
   │
   ▼
[载荷执行]   攻击者代码在受害进程权限下运行
```

**理解这个链路**很重要：本章每节既讲"怎么破坏"，也讲"哪一步能被防御打断"。打断任意一步，整条链就废了。

### 1.2 三大漏洞家族

| 家族 | 典型代表 | C++ 中常见来源 |
|------|----------|----------------|
| 内存安全 | 栈溢出、堆溢出、UAF、double-free | 裸指针、`memcpy` 越界、生命周期错乱 |
| 类型安全 | 类型混淆、向下转换错误 | `reinterpret_cast`、`union`、`memcpy` 替代赋值 |
| 算术安全 | 整数溢出、符号回绕 | `size_t * size_t`、`int` 当索引 |

C++ 是这三类漏洞的"高发语言"，原因在于**它把"性能可控"放在了"内存安全"之前**——编译器不会替你 bound check，运行时不会替你管生命周期。这意味着安全性是**程序员的责任**，不是语言的兜底。

### 1.3 攻击模型与威胁面

讨论漏洞前要先界定"威胁来自哪里"：

| 威胁面 | 输入来源 | 防御重点 |
|--------|----------|----------|
| 网络协议解析 | socket buffer | 边界检查、长度先验证 |
| 文件解析（图片/视频/PDF） | 不可信文件 | fuzzer + 沙箱 |
| IPC / 共享内存 | 同机其他进程 | 类型校验、权限隔离 |
| RPC 反序列化 | 远程节点 | schema 校验、长度上限 |
| 用户态命令行 | 本地用户 | 通常威胁等级低，但 setuid 程序例外 |

**安全编码的第一原则**：所有跨越信任边界的输入都假设是恶意的。


## 02.栈溢出深析

### 02.1 栈帧结构回顾

x86_64 SystemV ABI 下一个典型函数栈帧：

```
高地址
  ┌────────────────────┐
  │   caller's frame   │
  ├────────────────────┤
  │   return addr      │ ← 栈溢出的"金苹果"
  ├────────────────────┤
  │   saved rbp        │
  ├────────────────────┤
  │   stack canary     │ ← -fstack-protector 插入
  ├────────────────────┤
  │   局部变量 buf[64]  │ ← 写超过 64 字节就侵入上方
  ├────────────────────┤
  │   局部变量 ...      │
  └────────────────────┘
低地址（rsp）
```

栈是**向低地址生长**的，但局部变量在自己的栈帧里**向高地址写**——所以"写多了"会爬到 `return addr` 上面。

### 2.2 经典覆盖路径

```cpp
void vuln(const char* s) {
    char buf[64];
    strcpy(buf, s);   // ← 输入 > 64 字节就溢出
}
```

如果攻击者输入是 `[填充 72 字节] + [伪造的 return addr]`，那么 `vuln` 返回时 PC 跳到攻击者指定地址。早期攻击会把"填充"换成 shellcode，并让 return addr 指向栈上的 shellcode——这叫 **stack smashing**。

后来 NX 让栈不可执行，攻击者改用 **ROP（Return-Oriented Programming）**：把"return addr"换成一连串"已有代码片段（gadget）的地址"，每个 gadget 以 `ret` 结尾，串成一个图灵完备的程序。

### 2.3 Stack canary 原理

GCC `-fstack-protector-strong` 会在栈帧里插入"金丝雀"：

```
function entry:
   load canary from %fs:0x28 → save to [rbp - 8]
   ... 函数体 ...
function exit:
   load [rbp - 8], compare with %fs:0x28
   if mismatch → __stack_chk_fail（abort）
```

`%fs:0x28` 是 TLS 中的随机值（启动时 `pthread_create` 设置）。攻击者要覆盖 return addr 必须先经过 canary，而 canary 含一个 `\x00` 字节阻止 strcpy 类传播，且每个进程不同——这就阻断了"经典栈溢出"。

但要注意 canary **只防覆盖 return addr，不防覆盖局部变量本身**。比如：

```cpp
void f() {
    bool admin = false;
    char buf[64];
    gets(buf);             // 溢出 65 字节就改了 admin
    if (admin) grant();    // 仍然会被绕过
}
```

变量布局上 `admin` 在 `buf` **下方**（栈向低地址生长，编译器为了 canary 防御常把数组放在变量上方），但**对象内的字段顺序、变量布局并不绝对**——这就引出 `-fstack-protector-strong` 的"重排栈变量"附加效果。


## 03.堆溢出与 UAF

### 3.1 chunk 头被改写

glibc ptmalloc 的每个 chunk 前 16 字节是元数据：

```
  ┌─────────────────────────┐
  │  prev_size (8 bytes)    │
  ├─────────────────────────┤
  │  size + flags (8 bytes) │ ← 包含 PREV_INUSE、IS_MMAPPED
  ├─────────────────────────┤
  │  user data starts here  │ ← malloc 返回的指针
  └─────────────────────────┘
```

写超出 user data 区域，就改了**下一个 chunk 的 prev_size 和 size**。后续 free 时分配器会按这些字段做 `unlink` 操作，攻击者就能让 `unlink` 写一个任意位置——这是 **House of XXX** 系列攻击的核心。

现代 glibc 加了大量校验（fastbin double-free check、tcache_perthread_struct 校验、unsorted bin 大小校验），让经典 House 越来越难，但**根本上能不能防御**取决于你能否避免堆溢出本身。

### 3.2 Use-After-Free 链

```cpp
class Session {
public:
    virtual void process() = 0;
};
class Admin : public Session { void process() override; };

void handle() {
    Session* s = new Admin();
    delete s;            // 释放，但指针没置 nullptr
    s->process();        // ← UAF：vptr 已经在自由链上
}
```

UAF 的危险性在于："释放后这块内存被 malloc 重新分配给攻击者控制的对象"，于是 `s->process()` 实际跳到攻击者控制的 vptr 指向的函数。这就是 **vtable hijacking**，浏览器、JS 引擎漏洞中最常见。

防御层：

1. 编码层：智能指针 + 弱引用（`weak_ptr`）+ 释放后立即置空
2. 编译层：`-fsanitize=address`（开发期）、MTE / Memory Tagging（ARM v8.5+）
3. 运行时：`MALLOC_OPTIONS=junk` / Hardened malloc 释放后填充 0xfd
4. 缓解层：CFI（控制流完整性）使 hijack 后的跳转被拦下

### 3.3 double-free 与 tcache

```cpp
free(p);
free(p);  // 同一指针二次释放
```

ptmalloc 的 fastbin/tcache 用单链表管理空闲 chunk。double-free 会让链表出现环，下一次 malloc 同一 size 时，攻击者拿到一个仍被某个变量引用的内存——这叫 **fastbin dup**。

glibc 2.27+ 在 tcache 添加了 key 字段做"是否已在 cache 中"检查，2.29+ 加强为"链表链路完整性"校验。但 **任何用户态防御都防不住攻击者读到 key 后伪造**——这是为什么操作系统层（PAC、MTE）才是终极防线。


## 04.整数溢出陷阱

### 4.1 有符号 vs 无符号

C++ 标准对二者的态度截然不同：

| 类型 | 溢出行为 | 编译器假设 |
|------|----------|------------|
| 有符号 int 溢出 | **未定义行为（UB）** | 编译器假设永不溢出，可能优化掉检查 |
| 无符号 int 溢出 | 良定义，回绕（mod 2ⁿ） | 算术上正常 |

经典坑：

```cpp
int len = get_user_input();
if (len + 16 < BUF_SIZE)        // ← UB：编译器可能直接消掉这个分支
    memcpy(buf, src, len);
```

GCC 在 `-O2` 下会真的消掉这个分支（因为它推导：有符号 `len + 16 < SIZE` 等价于 `len < SIZE - 16`，假设永不溢出）。这是 CVE-2009-1897（Linux kernel SOCK_SENDPAGE）的同类问题。

### 4.2 大小计算的回绕

```cpp
size_t alloc_size = count * sizeof(Item);   // count 是用户输入
Item* p = (Item*)malloc(alloc_size);
for (size_t i = 0; i < count; ++i) p[i] = ...;  // 用 count 写
```

`count = SIZE_MAX / sizeof(Item) + 1` 时，乘法回绕 → `alloc_size` 极小 → `malloc` 成功 → 但循环写了远超 buffer 的区域。

CWE-190：Integer Overflow to Buffer Overflow。

### 4.3 安全的算术写法

C++20 提供 `<numeric>` 中的安全算术（`add_sat`/`mul_sat` C++26 才进），目前推荐：

```cpp
#include <limits>
#include <cstdint>

bool checked_mul(size_t a, size_t b, size_t& out) {
    if (a != 0 && b > std::numeric_limits<size_t>::max() / a)
        return false;   // 会溢出
    out = a * b;
    return true;
}

// GCC/Clang 内建（更高效）
if (__builtin_mul_overflow(a, b, &out)) return false;
```

工程纪律：**所有"长度类"输入计算前必须先做范围检查**。把 size 当 `int`（带符号、可负）是常见错误，应统一用 `size_t` 并做上限校验。


## 05.格式化字符串

### 5.1 任意读写原理

```cpp
printf(user_input);   // 错！应该 printf("%s", user_input)
```

如果 `user_input = "%x %x %x %x"`，`printf` 会按"格式化字符串带 4 个参数"的约定，从栈/寄存器里读 4 个值并打印——**等于把进程内存泄漏出来**。

进一步的 `%n` 把"已输出字符数"写到指定地址，这就是**任意写**。

### 5.2 现代编译器防御

```cpp
__attribute__((format(printf, 1, 2)))
void mylog(const char* fmt, ...);
```

`format` 属性让编译器对调用点做格式串校验。开 `-Wformat-security` 后，`printf(user)` 这种"格式串非常量"会直接告警。生产代码应**全量打开 `-Werror=format-security`**。


## 06.类型混淆与裁剪

### 6.1 reinterpret_cast 风险

```cpp
struct A { int x; };
struct B { int x; virtual void f(); };
A a;
B* b = reinterpret_cast<B*>(&a);
b->f();   // a 没有 vptr，访问越界
```

`reinterpret_cast` 不做任何校验，本质是"重解释比特"。在 C++ 里它的**唯一安全用途**是字节级序列化（且最好用 `std::bit_cast`，C++20）。

### 6.2 vptr 劫持

继承体系下虚函数调用是 `*(*obj)()`——先取对象前 8 字节作为 vptr，再调用 `vptr[idx]`。如果攻击者能写 vptr，就直接劫持控制流。

防御：CFI（下一节），以及编码层的"避免裸 cast、用 `dynamic_cast`、敏感对象放 `final`"。


## 07.防御机制纵深

### 7.1 ASLR 与 PIE

ASLR（Address Space Layout Randomization）每次启动随机化各段基址：

| 段 | 是否随机化 | 启用条件 |
|----|------------|----------|
| 栈 | 默认开 | 内核 |
| mmap/堆 | 默认开 | 内核 |
| 主程序 .text | **需 PIE** | `-fPIE -pie` 编译链接 |
| 共享库 | 自带 | `-fPIC` |

不开 PIE，主程序 .text 还是固定地址，ROP gadget 的位置就是确定的。**生产代码必须开 PIE**。

验证：`checksec ./bin` 看到 `PIE: enabled`。

### 7.2 NX/DEP 与 W^X

栈和堆默认 NX（不可执行），靠 ELF 段 flag `PF_X` 控制；mmap 时 `PROT_EXEC` 受 SELinux/AppArmor 策略限制。

W^X 原则（write XOR execute）："任何一段内存，要么可写，要么可执行，不能同时具备"。JIT 引擎要执行新生成代码，必须先 `mprotect` 改 EXEC 再去掉 WRITE。

### 7.3 RELRO 与 Fortify

| 机制 | 作用 | 编译选项 |
|------|------|----------|
| Partial RELRO | `.got.plt` 仍可写，但 `.got` 只读 | `-Wl,-z,relro` |
| Full RELRO | 启动后 GOT 全部只读 | `-Wl,-z,relro,-z,now` |
| FORTIFY_SOURCE | 编译期把 `strcpy/memcpy` 替换为带 size 检查的版本 | `-D_FORTIFY_SOURCE=2 -O2` |
| FORTIFY 3 | 更激进，识别更多 size 表达式 | `-D_FORTIFY_SOURCE=3`（GCC 12+） |

`_FORTIFY_SOURCE` 的精妙之处：在编译期能算出 buf 大小时，把 `memcpy(buf, src, n)` 替换成 `__memcpy_chk(buf, src, n, sizeof(buf))`，在 n 超 `sizeof(buf)` 时直接 `__chk_fail` abort。**写代码完全无感**，但拦截了大量 strcpy 类问题。

### 7.4 CFI 控制流完整性

CFI 的核心思想：**间接调用（虚函数、函数指针）只能跳到"合法目标集合"**。Clang `-fsanitize=cfi` 在每个虚调用前插入：

```c
if (!is_valid_vtable(vptr_class_id)) __ubsan_handle_cfi_check_fail();
real_call();
```

合法目标集合在编译/链接期通过类型签名计算出来。即便攻击者改了 vptr 让它指向另一个 vtable，只要类型不匹配就被 CFI 拦下。

代价：要求 LTO（合法集合需全程序信息）。但对安全敏感程序（浏览器、JIT）几乎是标配。


## 08.编码层防御

写代码的人能做的远比想象多：

| 实践 | 阻断的漏洞类型 |
|------|----------------|
| 全部用 `std::string` / `std::vector` | 栈/堆溢出 |
| 用智能指针，`unique_ptr` 优先 | UAF / double-free |
| 容器访问用 `at()` 而非 `[]`（性能不敏感处） | 越界 |
| 输入边界用 `std::span` 传 | 越界、长度不一致 |
| 永远 `printf("%s", x)`，不要 `printf(x)` | 格式化字符串 |
| 算术先用 `__builtin_*_overflow` 或 `safe_numerics` 校验 | 整数溢出 |
| `reinterpret_cast` 替换为 `std::bit_cast` | 类型混淆 |
| 敏感类用 `final`，避免被继承 | vptr 劫持 |
| 编译开 `-Wall -Wextra -Werror -D_FORTIFY_SOURCE=2` | 一大批静态可发现问题 |
| 链接开 `-Wl,-z,relro,-z,now -pie` | ROP / GOT 写 |
| CI 里跑 ASan + UBSan + fuzzer | 运行时可触发问题 |

**银弹不存在，纵深防御是唯一路**。每一层只要拦下 70%，三层叠加就只剩 2.7%。
