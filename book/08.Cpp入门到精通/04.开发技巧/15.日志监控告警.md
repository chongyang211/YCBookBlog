## 01.可观测性三件套

### 1.1 logs / metrics / traces

```
日志（Logs）       离散事件   "10:23:01 user 1234 login failed: bad password"
指标（Metrics）    时间序列   "login_fail_rate{region=cn} = 0.3 /s"
追踪（Traces）     调用链     "request abc → svc-a (3ms) → svc-b (12ms) → db (45ms)"
```

三者关系：

- **指标告诉你"出了什么事"**（错误率上升）
- **日志告诉你"为什么"**（具体哪个用户、什么报错）
- **追踪告诉你"在哪一步"**（链路上哪段拖慢/失败）

只有日志的服务：故障时翻日志比翻天书还慢。  
只有指标的服务：知道病但不知道病灶。  
**真正能 30 分钟止损的服务，三者都有**。

### 1.2 各自的代价模型

| 数据类型 | 写入开销 | 存储成本 | 查询代价 |
|----------|----------|----------|----------|
| 日志 | 中（fmt + IO） | 高（每次事件都存） | 全文检索贵 |
| 指标 | 低（counter inc） | 低（聚合后只存数字） | 即时图表 |
| 追踪 | 中-高（每 span 一条） | 高（按 trace 全存） | 中 |

**重要结论**：

- 高频路径（百万 QPS）**不能** info 级别日志，但可以 metric
- 低频/出错路径再考虑详细日志
- 全量追踪不可承受，必须采样（见 6.3）

### 1.3 选型决策

新服务从零搭建，建议顺序：

1. **先 metrics**：CPU/内存/QPS/错误率/延迟分布——成本最低、价值最高
2. **再日志**：只在出错路径详细记，正常路径只 INFO 概要
3. **后追踪**：跨服务调用 ≥3 跳就上 OpenTelemetry

**反例**：很多团队从"打日志"开始，等日志爆量才回头加 metric——多走半年弯路。


## 02.日志深度

### 2.1 等级与适用

| 等级 | 含义 | 频率 | 例子 |
|------|------|------|------|
| TRACE | 函数级调用 | 不开（仅本地调试） | "Entering parse() with n=128" |
| DEBUG | 详细诊断 | 仅故障期开启 | "Cache miss for key=foo, fallback to db" |
| INFO | 业务里程碑 | 每请求 ≤1 条 | "Order 12345 created for user 67" |
| WARN | 异常但可恢复 | 偶发 | "Retry 1/3 after timeout" |
| ERROR | 业务失败 | 实际错误 | "Payment failed: invalid card" |
| FATAL | 进程将退出 | 极罕见 | "Cannot bind port 8080" |

**纪律**：

- INFO 以下不应在生产开启
- ERROR 应被 metric 计数并参与告警
- 不要 INFO 级别打"用户密码不正确"这种**安全敏感信息**

### 2.2 结构化日志

文本日志 vs 结构化（JSON）：

```
# 文本（差）
2024-01-15 10:23:01 [info] order 12345 paid by user 678 amount 99.5

# 结构化（好）
{"ts":"2024-01-15T10:23:01Z","level":"info","msg":"order paid",
 "order_id":12345,"user_id":678,"amount":99.5,"trace_id":"abc..."}
```

收益：

- ELK / Loki / Datadog 能直接按字段过滤聚合
- `order_id=12345` 即查即得，不用写 regex
- 不同人对"消息文本"的写法不一致，结构化字段统一

C++ 选 spdlog/glog 加 JSON formatter，或直接用 `fmt::format` 自己拼。

### 2.3 上下文穿透

一个请求处理涉及十几次日志，必须有 **trace_id** 把它们串起来：

```cpp
// 进入请求处理时
auto trace_id = req.headers["X-Trace-Id"];
if (trace_id.empty()) trace_id = generate_uuid();

// 用 thread_local 存
struct LogContext {
    static thread_local std::string trace_id;
};
thread_local std::string LogContext::trace_id;

// 自定义 spdlog formatter 自动加进去
class TraceIdFlag : public spdlog::custom_flag_formatter {
    void format(const spdlog::details::log_msg&, const std::tm&,
                spdlog::memory_buf_t& dest) override {
        dest.append(LogContext::trace_id);
    }
    std::unique_ptr<custom_flag_formatter> clone() const override {
        return std::make_unique<TraceIdFlag>();
    }
};
```

这样每条日志自动带 trace_id，**无需在每个 log 调用里手动传**。异步任务/线程池要在调度时显式拷贝上下文（C++ 没 Go 的 goroutine-local 那么自然）。

### 2.4 异步与无锁

同步日志的问题：

```cpp
log_info("...");   // 调 fmt 格式化 + 写文件 IO，主线程阻塞
```

50 μs 一条，1 万 QPS 就花 50% CPU 在日志上。**生产服务必须异步**：

```
[业务线程]                 [无锁队列]              [后台日志线程]
   produce log entry  →    SPSC/MPMC ring   →     consume + flush
```

实现要点：

- **无锁 SPSC/MPSC ring buffer**：避免 mutex
- **批量写盘**：积累 4-64 KB 再 `write`
- **背压策略**：队列满时是丢日志、阻塞，还是降级——必须明确
- **进程退出时 flush**：注册 `atexit`，崩溃信号里也尝试同步 flush

## 03.spdlog 实战

### 3.1 基本用法

```cpp
#include <spdlog/spdlog.h>
#include <spdlog/sinks/rotating_file_sink.h>
#include <spdlog/async.h>

int main() {
    spdlog::init_thread_pool(8192, 1);   // 队列 8K，1 个后台线程
    auto logger = spdlog::rotating_logger_mt<spdlog::async_factory>(
        "app", "logs/app.log",
        100 * 1024 * 1024,    // 100 MB rotate
        10);                  // 保留 10 个
    spdlog::set_default_logger(logger);
    spdlog::set_level(spdlog::level::info);
    spdlog::set_pattern(R"({"ts":"%Y-%m-%dT%H:%M:%S.%e%z","lvl":"%l","msg":%v})");
    
    spdlog::info("start, pid={}", getpid());
}
```

### 3.2 异步 sink 原理

spdlog 的 async logger 内部：

```
log() 调用
  ↓
打包成 async_msg（把 fmt 字符串、参数 type-erased 进消息体）
  ↓
塞进 mpmc_blocking_queue（基于 ringbuffer + 条件变量）
  ↓
后台 worker 取出 → 真正格式化 → 写 sink
```

注意：

- 格式化在后台做，业务线程只付"打包"的代价（约 1-2 μs）
- 队列满时有三种策略：`block_retry`（默认，阻塞）/ `discard_oldest` / `discard_newest`
- 后台 worker 单线程足够（100 万 QPS 都吃得下），多线程反而因锁互争更慢

### 3.3 生产配置示例

```cpp
// 经验配置
spdlog::init_thread_pool(
    /* queue size */ 65536,
    /* threads     */ 1);

auto sink = std::make_shared<spdlog::sinks::rotating_file_sink_mt>(
    "logs/svc.log", 200 * 1024 * 1024, 30);

auto logger = std::make_shared<spdlog::async_logger>(
    "svc", sink,
    spdlog::thread_pool(),
    spdlog::async_overflow_policy::overrun_oldest);  // 满了丢老的

logger->set_level(spdlog::level::info);
logger->flush_on(spdlog::level::warn);   // 警告及以上立即刷盘
spdlog::flush_every(std::chrono::seconds(3));  // 兜底每 3 秒
```

`overrun_oldest` 选择是关键：**业务可用性 > 日志完整性**——日志写不动时宁可丢也不要拖垮主流程。


## 04.日志的反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 循环里 INFO 日志 | 几小时打爆磁盘 | 改 DEBUG / 抽样 / 改成 metric |
| 日志含密码、token | 安全事故 | 脱敏或不打 |
| 日志是唯一的"取证"通道 | 故障时根本翻不动 | 关键事件双写到事件总线 |
| 用日志做监控（grep 错误数） | 慢、不稳定 | 错误打 metric counter |
| 错误处理后不日志 | 静默失败 | 至少 WARN |
| 日志文本里带换行 | 解析失败 | 换行替换为 `\n` 字面量 |
| 不限 rotate / 保留期 | 磁盘爆满 | rotate by size + retention by days |
| `printf` 直接到 stderr | 没 timestamp、没 level、易丢 | 用 logger 框架 |


## 05.metrics 体系

### 5.1 四大类指标

| 类型 | 含义 | 例子 |
|------|------|------|
| Counter | 单调递增计数 | `http_requests_total` |
| Gauge | 可上可下的瞬时值 | `memory_bytes_used` |
| Histogram | 分布（桶计数） | `request_latency_seconds` 的 P50/P99 |
| Summary | 客户端预聚合分位 | `latency_summary{quantile=0.99}` |

P99 延迟极重要：**平均延迟漂亮但 P99 1 秒**意味着 1% 用户体验糟糕，常被忽视。Histogram 是首选，因为可以服务端聚合多实例的真实 P99。

### 5.2 标签维度爆炸

```cpp
counter.WithLabels({{"path", req.path}, {"user_id", req.uid}}).Increment();
```

这是经典灾难：`user_id` 千万级 → 千万条时间序列 → Prometheus OOM。

**纪律**：标签维度（cardinality）

- 总条数 ≤ 1 万
- 每个 label 取值 ≤ 100
- **绝不**用 user_id / order_id 这种唯一标识符做 label
- 高基数维度去日志/追踪里查，不要塞 metric

### 5.3 RED 与 USE 方法

两套行业级方法论：

**RED**（请求侧）：

| 缩写 | 全称 | 监控对象 |
|------|------|----------|
| R | Rate | 每秒请求数 |
| E | Errors | 失败请求数 |
| D | Duration | 延迟分布 |

**USE**（资源侧）：

| 缩写 | 全称 | 监控对象 |
|------|------|----------|
| U | Utilization | 使用率 |
| S | Saturation | 饱和度（队列长度） |
| E | Errors | 资源错误（IO error 等） |

最小生产监控就是**每个服务的 RED + 主机/容器的 USE**——这两套铺好就能解决 80% 的运维问题。


## 06.分布式追踪

### 6.1 trace 与 span

```
trace_id = abc123
   │
   ├── span_a "POST /order"   (root, 100ms)
   │      │
   │      ├── span_b "auth"   (child of a, 5ms)
   │      ├── span_c "stock"  (child of a, 30ms)
   │      │      │
   │      │      └── span_d "db.query"  (child of c, 25ms)
   │      └── span_e "pay"    (child of a, 60ms)
```

每个 span 含：

- `trace_id` / `span_id` / `parent_span_id`
- 开始/结束时间
- 服务名 / 操作名
- 标签（status_code、db.statement、…）
- 事件（业务里程碑）

### 6.2 OpenTelemetry

OpenTelemetry 是 CNCF 的标准追踪 SDK，C++ 版可用：

```cpp
#include <opentelemetry/trace/provider.h>

auto tracer = opentelemetry::trace::Provider::GetTracerProvider()
                  ->GetTracer("svc");
auto span = tracer->StartSpan("handle_order");
auto scope = tracer->WithActiveSpan(span);

// 调下游时把 trace_id 注入 HTTP header
opentelemetry::trace::Propagator propagator;
propagator.Inject(carrier, opentelemetry::context::RuntimeContext::GetCurrent());
```

下游服务从 header 提取 trace_id，**两端的 span 通过 trace_id 串起来**。

### 6.3 采样策略

全量 trace 不可承受，必须采样。三种典型策略：

| 策略 | 描述 | 适合 |
|------|------|------|
| 头部采样（head-based） | 入口随机决定是否追踪 1% | 高 QPS、性能优先 |
| 尾部采样（tail-based） | 全采但出口决定是否保留 | 想抓所有错误 |
| 自适应采样 | 错误/慢请求 100%、成功 0.1% | 工程性价比最高 |

实施要点：**采样决定要在 trace 起点做并随 header 传递**——否则上游采了下游不采，链路断掉。


## 07.告警工程

### 7.1 告警的黄金法则

```
[症状告警] 告警面向用户可感知症状，不告警内部状态
[可执行]   每条告警都对应一个 runbook，知道立即做什么
[紧急性]   一旦告警，必须现在就处理；非紧急的进 dashboard
```

反例：

- "CPU 80%" → 用户感知不到，应该改"P99 延迟超 1s"
- "DB 连接池占用 70%" → 内部指标，不应直接报警；只在导致下游错误率上升时报
- "磁盘剩 20%" → 不紧急（还有 N 天空间），变成 ticket 而非 page

### 7.2 SLO 驱动告警

SLO（Service Level Objective）：业务承诺的服务质量指标。

```
SLO: 99.9% 请求成功，P99 < 500ms（30 天滚动）
```

由此推导：

- 错误预算 = 0.1% × 请求量
- 燃烧速度 = 当前错误数 / 单位时间预算
- **燃烧速度 > 14.4× 即页面级告警**（30 天预算 2 小时烧完）
- **燃烧速度 > 6×** 即 ticket 级别（6 小时烧完）

这套来自 Google SRE，**让告警和业务承诺直接挂钩**，不再凭工程师拍脑袋设阈值。

### 7.3 告警疲劳治理

告警太多的恶果：

- 工程师麻木，真告警被忽略
- 半夜电话频繁，团队稳定性下降
- 信噪比低 = 整个监控失效

治理动作：

| 动作 | 目标 |
|------|------|
| 每月 review 告警清单 | 静默 N 周没触发的，要么删要么调 |
| 合并相关告警 | 一次故障产生的 10 个告警合成 1 个 |
| 设置抑制规则 | 上游故障期间抑制下游告警 |
| 引入 deduplication | 同类告警 5 分钟内只发一次 |
| 分级路由 | P0 电话、P1 短信、P2 邮件、P3 dashboard |

经验：**每个 oncall 周期 ≤ 5 个真告警**才算健康。超过就要做减法。


## 08.故障演练

监控不是装好就完事——**没演练过的监控等于没监控**。

| 演练类型 | 频率 | 验证点 |
|----------|------|--------|
| 模拟下游超时 | 月度 | 错误率告警是否响、链路是否清晰 |
| 模拟主机宕 | 季度 | 切流是否生效、监控是否捕获 |
| 模拟磁盘满 | 季度 | 日志是否优雅降级 |
| 红蓝对抗 | 年度 | 真实故障演练，含响应流程 |

Chaos Engineering（混沌工程）的本质：**主动制造故障验证韧性**。Netflix 的 Chaos Monkey 是开山鼻祖。

C++ 服务做演练特别要测：

1. 内存压力下的行为（OOM killer 触发前是否能告警）
2. 信号风暴（kill -SEGV 后 core dump 能不能产生）
3. 文件描述符耗尽（accept 失败时的退避）


## 09.思考题

1. 一个 100k QPS 的服务，每请求 1 条 INFO 日志，假设日志 200 字节，每天产生多大日志？带宽和存储如何规划？
2. trace 全采样 vs 1% 采样，在 5 个微服务串联时定位错误的差异有多大？
3. P99 延迟突然从 50ms 涨到 500ms，但 metric 平均延迟没变化——可能的原因和排查思路？
4. 告警值班一周收到 200 条 page，70% 是同一个根因——怎么减负？
5. 同样的服务在中美双地部署，metric 系统应该如何设计？时间序列要分还是合？
