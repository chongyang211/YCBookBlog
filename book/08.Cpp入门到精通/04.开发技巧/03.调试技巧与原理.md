## 01.调试的基本思想

### 1.1 调试的本质

调试（Debugging）的本质是**缩小问题范围的过程**。从一个可观察的错误现象出发，通过系统性的方法逐步定位到导致错误的代码行。

```
调试的思维模型：

症状（可观察）        →  原因（不可见）
─────────────         ─────────────
崩溃/段错误           空指针解引用
输出结果错误           逻辑错误/边界条件
性能低下              算法复杂度/缓存未命中
死锁/卡住             锁顺序错误/竞争条件
内存持续增长           内存泄漏
```

### 1.2 调试的基本流程

```
1. 复现（Reproduce）
   │ 稳定复现是调试的前提
   │ 如果不能稳定复现，收集环境信息、增加日志
   ↓
2. 隔离（Isolate）
   │ 缩小问题范围：哪个模块？哪个函数？哪行代码？
   │ 方法：二分法注释代码、最小化测试用例
   ↓
3. 定位（Locate）
   │ 使用调试器、日志、断言精确定位
   │ 理解代码的预期行为 vs 实际行为
   ↓
4. 修复（Fix）
   │ 修改代码，确保修复不引入新问题
   ↓
5. 验证（Verify）
   │ 运行原来的复现步骤，确认问题解决
   │ 运行回归测试，确保没有副作用
   ↓
6. 预防（Prevent）
   添加测试用例、断言、文档
```

### 1.3 常见的调试工具

| 工具 | 用途 | 场景 |
|------|------|------|
| GDB/LLDB | 交互式调试 | 逻辑错误、崩溃分析 |
| AddressSanitizer | 内存错误检测 | 越界、Use-After-Free、泄漏 |
| ThreadSanitizer | 线程安全检测 | 数据竞争、死锁 |
| UBSanitizer | 未定义行为检测 | 整数溢出、空指针 |
| Valgrind | 内存检测与分析 | 泄漏、未初始化读取 |
| perf | 性能分析 | CPU热点、缓存未命中 |
| strace | 系统调用追踪 | IO问题、权限问题 |
| ltrace | 库调用追踪 | 库函数调用序列 |
| objdump/nm | 二进制分析 | 符号表、反汇编 |


## 02.GDB调试核心技巧

### 2.1 基本操作

```bash
# 编译时必须加-g保留调试信息
g++ -g -O0 -o myapp main.cpp

# 启动GDB
gdb ./myapp

# GDB核心命令
(gdb) run [args]        # 运行程序
(gdb) run < input.txt   # 重定向输入
(gdb) continue (c)      # 继续执行
(gdb) next (n)          # 单步执行（跳过函数调用）
(gdb) step (s)          # 单步执行（进入函数调用）
(gdb) finish            # 执行到当前函数返回
(gdb) until 100         # 执行到第100行
(gdb) return [value]    # 强制从当前函数返回
(gdb) quit (q)          # 退出GDB
```

### 2.2 断点管理

```bash
# 设置断点
(gdb) break main.cpp:42       # 在文件第42行设断点
(gdb) break processData       # 在函数入口设断点
(gdb) break MyClass::method   # 在类方法上设断点

# 条件断点（只在条件满足时中断）
(gdb) break main.cpp:42 if count > 100
(gdb) break processData if ptr == 0x0

# 临时断点（只触发一次）
(gdb) tbreak main.cpp:42

# 管理断点
(gdb) info breakpoints      # 列出所有断点
(gdb) delete 3              # 删除编号3的断点
(gdb) disable 2             # 禁用编号2的断点
(gdb) enable 2              # 启用编号2的断点

# 监视点（变量值变化时中断）
(gdb) watch counter          # counter被修改时中断
(gdb) rwatch *0x7fff1234     # 内存地址被读取时中断
(gdb) awatch data->size      # 被读或写时中断

# 捕获点
(gdb) catch throw            # C++异常抛出时中断
(gdb) catch catch            # C++异常捕获时中断
(gdb) catch syscall write    # write系统调用时中断
```

### 2.3 变量和内存检查

```bash
# 打印变量
(gdb) print counter          # 打印变量值
(gdb) print *ptr             # 解引用指针
(gdb) print arr[0]@10        # 打印数组前10个元素
(gdb) print/x value          # 十六进制格式
(gdb) print/t value          # 二进制格式
(gdb) print sizeof(MyStruct) # 打印类型大小

# 显示表达式（每次停下来都自动打印）
(gdb) display counter
(gdb) display/x *ptr
(gdb) undisplay 1            # 取消显示

# 检查内存
(gdb) x/10wx 0x7fff1234     # 从地址开始打印10个32位字（hex格式）
(gdb) x/20bx ptr            # 从ptr开始打印20个字节
(gdb) x/5i $rip             # 从当前指令开始反汇编5条指令
(gdb) x/s str_ptr           # 以字符串格式打印

# x命令格式: x/[数量][格式][单位] 地址
# 格式: x(hex) d(decimal) u(unsigned) o(octal) t(binary) s(string) i(instruction)
# 单位: b(byte) h(halfword,2B) w(word,4B) g(giant,8B)

# 类型信息
(gdb) ptype myObject         # 打印对象的类型定义
(gdb) info locals            # 打印所有局部变量
(gdb) info args              # 打印函数参数
```

### 2.4 多线程调试

```bash
# 查看线程
(gdb) info threads           # 列出所有线程
  Id   Target Id         Frame
* 1    Thread 0x7f... "main"     at main.cpp:42
  2    Thread 0x7f... "worker1"  at worker.cpp:100
  3    Thread 0x7f... "worker2"  at worker.cpp:87

# 切换线程
(gdb) thread 2               # 切换到线程2

# 对所有线程执行命令
(gdb) thread apply all bt    # 打印所有线程的栈回溯
(gdb) thread apply 2 3 bt    # 打印线程2和3的栈回溯

# 线程调度控制
(gdb) set scheduler-locking on    # 只运行当前线程（其他线程冻结）
(gdb) set scheduler-locking step  # 单步时只运行当前线程
(gdb) set scheduler-locking off   # 所有线程自由运行（默认）

# 在特定线程上设断点
(gdb) break worker.cpp:100 thread 2
```


## 03.内存调试工具

### 3.1 AddressSanitizer

```bash
# 编译时启用（GCC/Clang都支持）
g++ -fsanitize=address -g -O1 -o myapp main.cpp

# ASan能检测的问题：
# - 堆缓冲区溢出（Heap Buffer Overflow）
# - 栈缓冲区溢出（Stack Buffer Overflow）
# - 全局缓冲区溢出（Global Buffer Overflow）
# - Use-After-Free
# - Use-After-Return（使用-fsanitize-address-use-after-return=always）
# - Double-Free
# - 内存泄漏（配合-fsanitize=leak）
```

```cpp
// ASan会自动检测并报告这些问题
void heap_buffer_overflow() {
    int* arr = new int[10];
    arr[10] = 42;  // ASan报告：heap-buffer-overflow
    delete[] arr;
}

void use_after_free() {
    int* p = new int(42);
    delete p;
    *p = 100;  // ASan报告：heap-use-after-free
}

void stack_buffer_overflow() {
    int arr[10];
    arr[10] = 42;  // ASan报告：stack-buffer-overflow
}
```

**ASan的底层原理**：

```
ASan使用影子内存（Shadow Memory）追踪内存状态：

应用内存                     影子内存
┌───────────────┐           ┌────────┐
│  8 bytes      │  ──映射──→ │ 1 byte │
│               │           │        │
└───────────────┘           └────────┘

影子字节的含义：
0x00: 全部8字节可访问
0x01-0x07: 前1-7个字节可访问
0x80+: 各种不可访问状态
  0xfa: 堆缓冲区右侧的红区
  0xfd: 已释放的内存
  0xf1: 栈缓冲区左侧的红区
  0xf3: 栈缓冲区右侧的红区

每次内存访问前，编译器插入检查代码：
  shadow_value = shadow_mem[addr >> 3]
  if (shadow_value != 0 && (shadow_value < (addr & 7) + size))
      report_error()  // 非法访问！

性能开销：约2x慢，内存约2-3x
```

### 3.2 Valgrind

```bash
# 运行Memcheck（默认工具）
valgrind --leak-check=full --show-leak-kinds=all ./myapp

# 常见输出解读
==1234== Invalid read of size 4          # 读取非法内存
==1234==    at 0x401234: func (main.cpp:42)
==1234==  Address 0x5a2c040 is 0 bytes after a block of size 40 alloc'd
==1234==    at 0x4C2BE45: operator new[](unsigned long) (vg_replace_malloc.c)
# → 堆缓冲区溢出：访问了紧随40字节分配块之后的内存

==1234== Use of uninitialised value      # 使用未初始化的值
==1234== Conditional jump depends on uninitialised value(s)
# → 分支条件依赖于未初始化的变量

==1234== LEAK SUMMARY:
==1234==    definitely lost: 72 bytes in 3 blocks    # 确定泄漏
==1234==    indirectly lost: 1,024 bytes in 1 blocks # 间接泄漏
==1234==    possibly lost: 0 bytes in 0 blocks       # 可能泄漏
==1234==    still reachable: 256 bytes in 2 blocks   # 程序结束时仍可达
```

**Valgrind的底层原理**：

```
Valgrind是一个动态二进制翻译框架：
1. 不修改源程序，运行时翻译机器码
2. 将每条x86指令翻译为Valgrind的中间表示（VEX IR）
3. 在VEX IR上插入检测代码
4. 将带检测的IR编译回机器码执行

优点：不需要重新编译
缺点：运行速度约为正常的10-30倍
```

### 3.3 ThreadSanitizer

```bash
# 编译时启用
g++ -fsanitize=thread -g -O1 -o myapp main.cpp

# TSan检测的问题：
# - 数据竞争（Data Race）
# - 死锁（Deadlock，使用-fsanitize=thread配合锁检测）
```

```cpp
// TSan会报告数据竞争
int counter = 0;

void thread_func() {
    counter++;  // TSan报告：data race on 'counter'
}

int main() {
    std::thread t1(thread_func);
    std::thread t2(thread_func);
    t1.join();
    t2.join();
}
```

```
TSan输出示例：
WARNING: ThreadSanitizer: data race (pid=1234)
  Write of size 4 at 0x7f1234 by thread T1:
    #0 thread_func() main.cpp:4
  Previous write of size 4 at 0x7f1234 by thread T2:
    #0 thread_func() main.cpp:4
  Location is global 'counter' of size 4
```

## 06.调试的底层原理

### 6.1 ptrace系统调用

GDB等调试器的核心依赖于`ptrace`系统调用：

```c
#include <sys/ptrace.h>

// ptrace是Linux调试的基础设施
long ptrace(enum __ptrace_request request, pid_t pid, void *addr, void *data);

// 常用请求：
PTRACE_ATTACH    // 附加到目标进程
PTRACE_DETACH    // 分离
PTRACE_PEEKTEXT  // 读取目标进程的代码/数据
PTRACE_POKETEXT  // 修改目标进程的代码/数据
PTRACE_GETREGS   // 读取寄存器
PTRACE_SETREGS   // 设置寄存器
PTRACE_SINGLESTEP // 单步执行一条指令
PTRACE_CONT      // 继续执行
PTRACE_SYSCALL   // 在系统调用入口/出口停下

// ptrace的工作模式：
// 1. 调试器通过ptrace附加到目标进程
// 2. 目标进程变为"被追踪"状态
// 3. 目标进程遇到信号或断点时，暂停并通知调试器
// 4. 调试器通过ptrace检查/修改目标进程状态
// 5. 调试器通过ptrace让目标进程继续执行
```

### 6.2 断点的实现原理

**软件断点**（最常用）：

```
原理：用INT3指令（0xCC）替换目标地址的原始指令

设置断点：
1. 调试器保存目标地址的原始字节
2. 用PTRACE_POKETEXT将该字节替换为0xCC (INT3)

触发断点：
1. CPU执行到0xCC，产生#BP异常
2. 内核向目标进程发送SIGTRAP
3. 进程暂停，调试器收到通知

恢复执行：
1. 调试器恢复原始字节（PTRACE_POKETEXT）
2. 将RIP寄存器回退1（指向被替换的指令）
3. 单步执行原始指令
4. 重新设置断点（再次替换为0xCC）
5. 继续执行

示例：
原始代码:  0x401234: 48 89 e5    mov rbp, rsp
设断点后:  0x401234: CC 89 e5    int3 + 垃圾
```

### 6.3 单步执行的原理

```
x86 CPU的EFLAGS寄存器中有一个TF（Trap Flag）位：
  TF=1: CPU执行每条指令后产生#DB（Debug Exception）
  TF=0: 正常执行

单步执行流程：
1. 调试器通过PTRACE_SINGLESTEP请求单步
2. 内核设置目标进程的EFLAGS.TF = 1
3. 恢复目标进程执行
4. CPU执行一条指令后触发#DB
5. 内核自动清除TF位，向进程发送SIGTRAP
6. 进程暂停，调试器检查新状态
```

### 6.4 监视点的原理

```
硬件监视点利用CPU的调试寄存器（DR0-DR7）：

DR0-DR3: 4个地址寄存器（监视的内存地址）
DR6:     状态寄存器（哪个监视点被触发）
DR7:     控制寄存器（监视类型和长度）

设置监视点：
1. 调试器将目标地址写入DR0-DR3之一
2. 在DR7中配置监视类型：
   00 = 仅执行断点
   01 = 数据写入
   10 = I/O读写（通常不用）
   11 = 数据读取或写入
3. 配置监视长度：1/2/4/8字节

触发：
1. CPU在执行每条指令时检查内存访问是否命中DR0-DR3
2. 命中时触发#DB异常
3. 内核向进程发送SIGTRAP

限制：
- 只有4个硬件监视点
- 如果需要更多，GDB会退化为软件实现（非常慢）
```

**总结**：调试是C++开发中最重要的实践技能之一。理解调试器的底层原理（ptrace、断点实现、单步执行），掌握内存检测工具（ASan、Valgrind、TSan），善用编译器警告和静态分析，才能在复杂的C++项目中快速定位和解决问题。

## 07.ThreadSanitizer 与 happens-before 模型深度解析

前面 03.3 只简单介绍了 TSan 的用法。真正理解 TSan 需要先建立**happens-before**这个并发编程的核心概念——它是所有现代数据竞争检测器（TSan、Helgrind、Java Race Detector）的理论基础。

### 7.1 什么是 happens-before 关系

Leslie Lamport 1978 年论文里定义：**对于两个内存操作 A 和 B，如果存在一条"事件链"把 A 连到 B，我们说 A happens-before B**。这条链由三种边组成：

1. **程序顺序（program order）**：同一线程内，前面的操作 happens-before 后面的操作。
2. **同步边（synchronization edge）**：线程间，释放-获取语义（release-acquire）的操作建立 happens-before：
   - 解锁 happens-before 同一把锁的下一次加锁；
   - 原子变量的 release store happens-before 同一变量的 acquire load（且前者已经发生）；
   - 线程 `join` happens-before `join` 返回后的操作；
   - `std::atomic_thread_fence` 建立显式边。
3. **传递性**：如果 A hb B 且 B hb C，则 A hb C。

**数据竞争的精确定义**：两个线程访问同一内存位置，至少一方是写，且**两者之间没有 happens-before 关系**，就是数据竞争——未定义行为。

### 7.2 TSan 是如何检测 happens-before 的

TSan 不靠"暴力跑几万次"碰运气，它用的是**vector clock（向量时钟）**算法：

- 每个线程维护一个"向量时钟"：`VC[i]` 表示本线程已知的线程 i 的"最新时间戳"。
- 每次线程本地操作，本线程的时钟 `VC[self]++`。
- 每次同步操作（解锁、release store、join）：**发送方把自己的向量时钟"附加"到同步点**。
- 接收方的同步操作（加锁、acquire load、join 后）：把同步点的向量时钟**合并**到自己的：`VC[i] = max(VC[i], remote_VC[i])`。
- 每次内存访问都记录"访问时的向量时钟快照"。

检测：当线程 A 访问某内存位置（写）后，线程 B 再访问它（写或读）——如果 B 当前的向量时钟里 `VC[A]` 小于 A 访问时的时间戳，说明 A 的写对 B "还不可见"——**数据竞争**。

这个算法在理论上是精确的（不会漏报也不会误报，前提是没用到未被 TSan 拦截的同步原语如信号、内联汇编）。代价是：内存占用 5-10 倍，运行速度慢 5-15 倍。

### 7.3 TSan 在真实项目里的使用纪律

TSan 最大的误用是"遗漏同步原语"。自定义的 lock-free 代码、裸用 `volatile`、手写 spin-loop 都可能不被 TSan 识别为同步点，导致**误报**。处理方式：

- 能用标准原子/锁就不要自己写；
- 必须自己写时，用 `ANNOTATE_HAPPENS_BEFORE` / `ANNOTATE_HAPPENS_AFTER` 手动告诉 TSan（需要包含 `sanitizer/tsan_interface.h`）；
- CI 里至少让 TSan 跑一轮完整测试——数据竞争是**最典型的"平时不出、上线必出"**的问题。

### 7.4 happens-before 对日常编码的启示

理解这个模型后，你会自然地形成几个编码直觉：

- **所有共享数据访问都必须被某条 happens-before 边覆盖**——要么在同一线程，要么被 mutex/atomic 保护。
- **`volatile` 不建立 happens-before**——它只禁止编译器优化，不提供线程间可见性保证。用它做线程同步是 C++ 里的经典 UB。
- **`std::atomic<T>` 的默认内存序是 `seq_cst`**——它建立的 happens-before 是"全局一致"的总顺序，最强最慢。如果你改成 `memory_order_relaxed`，就失去了 happens-before 保证——只有原子性。
- **条件变量必须配合 mutex 使用**——不是因为 API 强制，而是 `wait` 需要 mutex 的 unlock 来建立 happens-before。

## 08.perf 与火焰图的采样原理

第 5 章只介绍了 perf 的命令。要真正读懂 perf 的输出，需要理解它**如何采样 CPU**。

### 8.1 为什么是"采样"而不是"跟踪"

精确跟踪每条指令（比如 Valgrind callgrind）是**动态插桩**——给每个函数加探针，代价大、速度慢 10-50 倍。perf 走的是另一条路：**硬件性能计数器（PMU）+ 周期中断**。

CPU 里有几个硬件寄存器（Performance Monitoring Counters, PMC）能计数事件：CPU 周期、cache miss、分支预测失败、指令数、页面错误等。perf 的工作方式：

1. 用 `perf_event_open` 系统调用配置 PMC，比如"每 1,000,000 个 CPU 周期触发一次中断"；
2. 中断触发时，内核查询当前栈，记录"程序计数器（PC）+ 调用栈"到环形缓冲区；
3. 用户态 `perf record` 把缓冲区写入文件；
4. `perf report` 把样本聚合成统计。

这就是"采样"：每秒 1000 次左右（取决于事件频率），每次记录一个"当前位置"。统计意义上，热点函数被采样到的概率正比于它占 CPU 的时间。

### 8.2 采样的准确性与失真

采样方法有几个固有限制：

- **分辨率由采样频率决定**：1kHz 采样意味着最低能分辨 1ms 级的事件。更短的函数只能被统计意义地看到。
- **skid**：中断触发时，CPU 的 pipeline 里已经有几十条指令在飞，perf 记录的 PC 通常不是"真正触发事件的指令"，而是附近几条。这就是为什么有时火焰图上某函数的开销"看起来不对"——真正开销在前一两条指令。
- **栈回溯精度**：默认用帧指针（`-fno-omit-frame-pointer`）回溯栈。如果编译时开启了 `-fomit-frame-pointer`（-O2 默认），回溯会不准——需要用 `--call-graph dwarf`（用 DWARF 调试信息重建栈，慢但准）或 `--call-graph lbr`（用 Intel Last Branch Record，硬件辅助，快且准）。

### 8.3 perf_event_open 的数据流

这个系统调用是 Linux 性能分析的基石。它的参数：

- **type / config**：选择事件类型（硬件事件 / 软件事件 / 缓存事件 / tracepoint）。
- **sample_period / sample_freq**：采样间隔（多少个事件采一次，或目标频率）。
- **sample_type**：采样时记录什么（PC、栈、寄存器、时间戳）。

内核态发生中断时，handler 会写入环形 mmap 缓冲区，用户态 `perf` 通过 `poll` 或 `read` 取数据。这个设计让 perf 能低开销地持续运行（开销通常 <5%）。

### 8.4 火焰图为什么有效

Brendan Gregg 的火焰图把"每个样本的调用栈"从下到上堆起来，宽度等于样本数、颜色随机。它的价值不在图形本身，而在**把上千个栈样本可视化成一幅图**——人眼能一眼看出"哪一条路径占 CPU 最多"。

读火焰图的几个要点：

- **看宽不看高**：宽度代表 CPU 时间，高度只是调用栈深度（深不代表慢）。
- **看"平顶"**：火焰图顶部的"平台"就是热点（函数执行很多时间未进一步调用）。
- **差分火焰图**：对比两次采样（优化前/后），能直接看出哪些函数变快了、哪些变慢了。

### 8.5 perf 的其他高级用法

perf 不止是 CPU 采样：

- **`perf stat`**：统计事件计数（不采样，开销最小）——快速确认"这段代码 cache miss 高不高"。
- **`perf annotate`**：把采样结果叠加到汇编上，能看到哪条指令最热。
- **`perf sched`**：调度分析，找出被切走 CPU 的线程。
- **`perf trace`**：类似 strace 但更轻量。
- **`perf lock`**：锁竞争分析。

熟练使用 perf 是从"会写 C++"到"会调优 C++"的分水岭。

## 09.ptrace 的完整工作流程

ptrace 是 GDB、strace、反调试保护、沙箱等的底层基础。前文 06.1 给了一段代码，这里讲清楚它真正的运作流程。

### 9.1 两个进程的舞蹈

ptrace 涉及两个进程：**tracer（调试器）** 和 **tracee（被调试进程）**。它们的关系通过系统调用建立：

```
tracer                          tracee
  |                               |
  |--- fork() ---|                |
  |              |--- execve() -> 变为 tracee
  |                               |  (执行 PTRACE_TRACEME 或 PTRACE_ATTACH)
  |                               |
  |<-- SIGCHLD (stop notification) 
  |
  | 循环:
  |  waitpid(tracee)              |
  |  read regs/memory             |
  |  modify regs/memory           |
  |  ptrace(PTRACE_CONT, ...)     |
  |                               |--> 继续执行
  |                               |    (遇到断点/信号再停)
```

每当 tracee 停下（收到信号、触发断点、单步完成），内核通过 SIGCHLD 通知 tracer，tracer `waitpid` 之后可以**检查 tracee 的完整状态（寄存器、内存）并修改**，然后用 `PTRACE_CONT` 让它继续。

### 9.2 信号的"拦截路径"

这是 ptrace 最巧妙的设计：**被 trace 的进程收到任何信号时，信号先被投递给 tracer**。

- tracee 收到 SIGSEGV → 内核先暂停 tracee → 通过 SIGCHLD 告诉 tracer "tracee 想收 SIGSEGV"；
- tracer 用 `waitpid` 看到这个信号，可以：
  - 吞掉（`ptrace(PTRACE_CONT, pid, 0, 0)`）；
  - 按原样投递（`ptrace(PTRACE_CONT, pid, 0, SIGSEGV)`）；
  - 修改后投递（`ptrace(PTRACE_CONT, pid, 0, SIGTERM)`）。

这让 GDB 能实现"catch signal"：某些信号由调试器处理，某些原样传给程序。也是为什么**GDB 里程序收到 SIGSEGV 不会立即死**——调试器先截住了它。

### 9.3 断点的真正实现：0xCC 替换

GDB 在代码段设断点的步骤：

1. 从目标地址读一个字节（`ptrace(PTRACE_PEEKTEXT)`），保存到断点表；
2. 把该地址写入一字节 `0xCC`（x86 的 INT3 指令）（`ptrace(PTRACE_POKETEXT)`）；
3. tracee 运行到该地址，CPU 执行 INT3 → 触发 #BP 异常 → 内核转为 SIGTRAP → 投递给 tracer；
4. tracer 查断点表，识别是哪个断点，恢复原字节，把 PC 减 1（因为 INT3 已经让 PC 前进了），交给用户处理。

**单步继续**：用户继续时，断点处的代码是**原字节**——但我们下次还要在这里停。所以 GDB 的做法是：先单步执行一条（执行那个原字节），单步完成后再把 `0xCC` 写回去。这就是为什么单步过断点时 CPU 要"暂停两次"。

### 9.4 条件断点是怎么实现的

`break 30 if i > 100` 看似神奇，实际上是在断点位置放 INT3，命中时 GDB：

1. 通过 ptrace 读取 tracee 的寄存器和内存；
2. 在 GDB 自己的"表达式求值器"里算 `i > 100`；
3. 如果为真 → 真停下来给用户；如果为假 → 自动 `continue`。

这就是为什么条件断点**比无条件断点慢 100-10000 倍**——每次命中都要做一次"停止→读内存→求值→继续"的往返。性能敏感场景应该改用"日志断点（dprintf）"或者给源代码临时加 `if` + 普通断点。

### 9.5 硬件断点 vs 软件断点

x86 CPU 提供了 4 个调试寄存器（DR0-DR3）——可以监视 4 个内存地址的访问。GDB 的 `watch` 命令优先使用它们：

- **硬件监视点**：零开销（CPU 硬件实现）、精确到指令级、但只有 4 个。
- **软件监视点**：GDB 每执行一条指令都检查变量值——慢 1000 倍以上。

`info watch` 能告诉你当前使用的是哪种。如果你一次加了 5 个 watch，第 5 个必然是软件实现——在紧密循环里会让程序慢到跑不动。

## 10.总结与思考

### 10.1 调试能力的三个层次

- **第一层：会用工具**（断点、单步、`print`）。
- **第二层：会挑工具**（什么时候用 ASan vs TSan vs Valgrind？什么时候用 GDB vs perf？）。
- **第三层：懂工具的原理**（知道为什么 TSan 有时会误报、为什么条件断点特别慢、为什么火焰图的宽度代表什么）。

到第三层，你不再被工具牵着走——遇到工具不支持的场景，能自己定位问题的思路来源于**对底层机制的理解**。这也是本章整体的目标。

### 10.2 调试纪律：从"救火"到"防火"

好的调试不是"bug 出来了再查"，而是**在写代码时就让 bug 容易被查出来**：

- 打开所有编译器警告（`-Wall -Wextra -Wpedantic`）；
- CI 里跑 ASan、UBSan、TSan 三套 Sanitizer；
- 所有断言都保留在 release 里（`assert` 在 NDEBUG 下被禁用，但你可以自己定义 `CHECK`）；
- 日志是"运行时的调试器"——关键路径必须有日志，且能按模块开关；
- 让 coredump 始终可用（`ulimit -c unlimited` + 存储路径规划）。

这些投入看似"额外"，但每次线上故障节省的时间都远超当初的建设成本。

### 10.3 思考题

1. 用 `gdb` 调试一个优化过的程序（`-O2`），你会看到很多变量"被优化掉"。想想为什么？如何保留关键变量？（提示：`volatile`、`__attribute__((used))`、`__asm__ __volatile__("" : : "r"(x))`）
2. 一个程序启动时在多线程里初始化 `std::map`，偶尔崩溃。ASan 不报、TSan 报数据竞争。你如何定位？修复策略有哪些？
3. 火焰图显示 `memcpy` 占 30% 的 CPU 时间——这是问题吗？如果是，如何优化？如果不是，该往哪里看？
4. `perf record -g` 对一个带 `-fomit-frame-pointer` 编译的二进制跑出来的栈不准。有哪三种方法能让它变准？（提示：重编、dwarf、lbr）
5. 用 ptrace 实现一个最简单的"系统调用过滤器"需要哪些步骤？它和 seccomp 的差别在哪？
