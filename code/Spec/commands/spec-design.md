# Command: spec-design

## 命令名称

`spec-design`

## 作用

当需求较大、较复杂或技术方案尚不明确时，基于原始需求（`docs/intake/xxx.md`）先产出一份**技术方案（Design）**，供团队评审。评审通过后，再由 `/spec-draft` 基于「原始需求 + 技术方案」一起起草 spec，使 spec 更准确、边界更清晰。

> 这是一个**可选的前置环节**，位于阶段零（Draft）**之前**。小需求 / 改动清晰的需求可直接跳过，走 `/spec-draft`。

## 与 spec-plan 的区别（必读，避免混淆）

| 维度 | 技术方案 Design（本命令，阶段零前·可选） | 实施计划 Plan（`/spec-plan`，阶段二） |
|------|------|------|
| 时机 | **spec 之前**（需求大 / 方案不确定时） | **spec 已 ready 之后** |
| 输入 | 原始需求 `docs/intake/` | 已 ready 的 spec |
| 关注点 | 整体架构、技术选型、**方案对比与取舍**、模块划分、跨系统/跨仓库影响、可行性、风险预判 | 落地到**具体文件**的改动清单、Phase 步骤、实施顺序 |
| 颗粒度 | 方案级（用什么思路、为什么这样选） | 执行级（改哪些文件、按什么顺序） |
| 关键产出 | 技术方案 + **建议的 spec 拆分** | 可执行步骤清单 |
| 目的 | 供团队评审，把「大方向」定下来，指导写出更准确的 spec | 指导编码，可暂停、可交接 |
| 产物 | `designs/<VERSION>/<STORYID>-<slug>-design.md` | `plans/<VERSION>/<STORYID>-<slug>-plan.md` |
| 是否必须 | 否，仅大/复杂需求 | 复杂改动必须 |

> 一句话：**Design 决定「用什么方案做、要拆成几个 spec」，Plan 决定「在哪些文件、按什么步骤做」。** Plan 阶段应直接复用 Design 中已沉淀的关键技术决策，不重复讨论。

## 输入参数

| 参数 | 必选 | 说明 |
|------|------|------|
| 原始需求来源 | 是 | `docs/intake/<VERSION>/<STORYID>-<slug>.md` 文件路径 或 自然语言描述 |
| Story ID | 否 | 不指定则从 intake frontmatter 取；都没有则主动询问，暂无用 `0` 占位 |
| Author | 否 | 默认 `[TBD]`，建议指定 |

**触发方式**：

```
请基于 docs/intake/v1.6.0/134389917-dashboard-online-palm-statistics.md 执行 spec-design
```

或：

```
这个需求比较大，先帮我做个技术方案评审，再写 spec
```

## 执行步骤

> ⚠️ 本命令是**交互式两阶段**流程：**先澄清 + 给候选方案（不落盘）→ 用户确认选定后才写最终方案文档**。不允许跳过澄清、不允许只给单一方案、不允许未经用户确认就落盘。

0. **前置校验 — Story ID + 版本目录**
   - 与 `/spec-draft` 一致：Story ID 来源优先级为「用户对话 → intake frontmatter → 主动询问」
   - **从 intake 路径解析 `<VERSION>`（`docs/intake/<VERSION>/…`）；design 写入同名版本目录 `designs/<VERSION>/`，目录不存在则先 `mkdir -p`。如 intake 路径缺少版本目录段，主动询问归属版本（如 `v1.6.0`）**
   - 暂无对应 story 用 `0` 占位
   - design 文件名沿用此 Story ID 与 `<VERSION>`，后续 `/spec-draft` 继续沿用

1. **收集原始需求**
   - 优先读取 `docs/intake/xxx.md`；如用户直接描述，先复述确认理解
   - 明确本次技术方案要回答的核心问题

2. **澄清需求（关键步骤，不可跳过，可多轮）**

   在侦察和出方案**之前**，先向用户澄清以下问题。澄清是**多轮交互**的——用户回答后若仍有歧义或新发现，继续追问，直到方案输入足够清晰再进入下一步。

   | 必问类别 | 问题示例 | 为什么要问 |
   |---------|---------|-----------|
   | **需求性质** | 这是**全新建设**，还是在**已有实现上增量**改造？ | 决定方案是「从零设计」还是「在现有架构上扩展」，影响侦察重点与方案形态 |
   | **涉及仓库 + clone 状态** | 预计涉及哪些仓库？是否**已 clone 到 `src/<repo>/`**？逐一确认 | 必须基于已有代码做方案；未 clone 的仓库**先提示用户 clone**（见 `docs/git-workflow.md`），否则方案只能凭空假设 |
   | **现有实现定位** | 相关的现有功能 / 模块 / 接口在哪？大致怎么工作？ | 增量需求必须先摸清现状，复用现有能力，避免重复造轮子 |
   | **核心逻辑** | 关键业务逻辑、主流程、输入输出、依赖的上下游？ | 方案要覆盖真实主流程，而非想象的流程 |
   | **边界与异常** | 异常分支、并发 / 幂等、数据量级、失败回滚怎么处理？ | 边界往往决定方案选型，需提前暴露 |
   | **非功能约束** | 性能 / 兼容（老版本前端、proto 兼容）/ 安全 / 时效性是否有硬要求？ | 这些约束会直接淘汰部分方案 |
   | **范围边界** | 本期**不做**哪些事？是否分期？ | 框定方案范围，避免过度设计 |

   - 一次性把最关键的 3-6 个问题列给用户，按上表分类
   - 用户回答后**复述确认**理解，有歧义继续追问
   - 涉及仓库逐个确认 clone 状态：**已 clone** → 纳入侦察范围；**未 clone** → 提示用户先 clone 再继续，或在方案中显式标注「该仓库未侦察，相关结论待验证」

3. **现状侦察（基于已确认的仓库范围）**
   - 对**已 clone 到 `src/` 且本需求涉及**的仓库，调用 `skills/codebase-survey`（侧重**架构视角**：模块边界、调用链、跨系统/跨仓库交互，不深入到函数实现细节）
   - 增量需求重点定位 Step 2 中用户指出的现有实现，确认可复用资产与改造点
   - 输出现有架构约束、可复用资产、潜在冲突

4. **提出 2-3 个候选方案（不落盘，等用户选择）**

   - 至少给出 **2-3 个**有实质差异的候选方案（如「最小改动 / 复用现有」vs「重构 / 新建抽象」vs「折中」），而非单一结论
   - 每个候选方案说明：**核心思路、优点、缺点、复杂度 / 工作量、主要风险、对现有代码的影响**
   - 用**对比表**呈现，并给出 AI 的**推荐项 + 理由**
   - 同步给出基于推荐方案的「建议 spec 拆分」初步设想
   - **停下等用户选择**：用户可选定某个、或要求融合 / 调整。未得到用户明确选择前**不写文件**

5. **输出最终方案文档（用户确认后写入文件）**
   - 以用户选定的方案为主线，调用 `skills/technical-design` 技能，按 `designs/templates/design-template.md` 落盘
   - 「方案对比」章节保留被淘汰的候选方案及取舍理由（决策可追溯）
   - **核心产出**：给出「建议的 spec 拆分」——建议拆成几个 spec、各自边界与 slug 建议
   - 不臆造业务目标 / 验收标准（这些仍由 `/spec-draft` 阶段 + 人确定）
   - 路径：`designs/<VERSION>/<STORYID>-<slug>-design.md`
   - frontmatter：`Story ID` / `Author` / `Created` / `Updated` / `Status: draft` / `Reviewers`
   - `Status: draft`（强制，不可直接写 `approved`）

6. **输出方案报告 + 评审清单**
   - 总体方案 2-5 句话概述（含已选定的方案与被淘汰方案）
   - 列出**需要评审拍板的关键技术决策点**（2-5 个）
   - 列出建议的 spec 拆分
   - 列出风险与未决问题

## 输出结果

- **交互阶段**（落盘前）：澄清问答 + 2-3 个候选方案对比表（chat 中输出，等用户选择）
- **落盘产物**（用户选定方案后）：`designs/<VERSION>/<STORYID>-<slug>-design.md`（status: draft）
- 技术方案报告（chat 中输出，含评审清单）

## 后续动作

按顺序：

1. **团队评审技术方案**：架构师 / Tech Lead / 相关方对关键技术决策、方案对比、spec 拆分建议逐条评审
2. **回填评审结论**：把评审意见与结论记录到 design 的「评审记录」章节
3. **Status 改为 `approved`**：方案评审通过后
4. **执行 `/spec-draft`**：基于「intake + 已 approved 的 design」起草 spec（如建议拆多个 spec，逐个起草子 spec）

## 适用时机

- ✅ 需求大、跨多个模块 / 多个仓库，需要先定架构方向
- ✅ 存在多种技术方案需要对比、评审拍板
- ✅ 需求需要拆成多个子 spec，先在方案层确定拆分边界
- ✅ 技术可行性不确定，需要先验证方向再细化需求
- ❌ 小需求 / 改动清晰、单模块 → 直接 `/spec-draft`
- ❌ 纯 bugfix / 配置调整 → 直接 `/spec-draft` 或按流程例外处理

```

  ↓

  ↓
designs/<VERSION>/<STORYID>-<slug>-design.md (status: draft)
  ↓ [团队评审，回填评审记录，改 status: approved]
/spec-draft         ← 基于 intake + 已 approved 的 design 起草
  ↓
specs/<VERSION>/<STORYID>-<slug>.md (status: draft)
  ↓ [人 review，补 TBD，改 status: ready]
/spec-plan
  ↓
... (后续流程)
```
