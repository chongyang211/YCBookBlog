# 嘉年华大赛发榜

## 【榜题名称】

**当‘AI写代码看起来能跑就合并’成为常态：谁来为 AI 写的代码签字担保？谁负责背锅？CR 还能守住质量关吗？**

## 【问题场景】

我们团队 11 人、AI 编码覆盖率已接近 100%，以下场景是每天都在真实发生的困境：

**场景 1 · CR 环节：看不完、看不懂，最后闭眼合并。** AI 一口气吐出横跨十几个文件的千行 diff，评审人要么"能跑就过"，要么让 AI review AI，人只点一下通过。**风险**："AI 审 AI"等于没人审，评审人却要为没看懂的代码签字担责。

**场景 2 · 执行过程：顺手改、静默偏、上下文全丢。** AI 会"好心"重构相邻代码、引入新依赖、动了明确"不要动"的模块且不声明，10 条铁律 + 人抽查仍兜不住。**风险**：改动范围漂移失控，实际改动和需求对不上，事后无人说得清"当初为什么这么改"。

**场景 3 · 出事之后：定位不了，也回滚不掉。** git blame 指向一次大而全的 AI 提交，几十个文件混在一个 commit；回滚只能整包 revert，好的也一起撤掉。**风险**：MTTR 拉长，AI 提效省下的时间，在出事那晚加倍还了回去。

**场景 4 · 同一需求，换个 Agent 就换一套实现。** 不同人/不同 Agent（甚至同人隔天重跑）产出的架构、质量、风格天差地别。**风险**：质量取决于"谁的 prompt 写得好"，工程能力无法沉淀复制——团队从"工程化"退回"看运气"。

**场景 5 · 测试幻觉：自测全绿，只测了 happy path。** AI 自己写测试自己跑，全绿，但 spec 里列的十几条边界情况一条没碰。**风险**：覆盖率报表给人虚假信心，缺陷逃逸到测试/线上才暴露——既当运动员又当裁判。

**场景 6 · 上下文断层：换个人、隔个周末，就接不上了。** 决策上下文只存在于当时的对话窗口里，接手的人要从零理解；文档与代码持续脱节。**风险**：人成了"人肉缓存"，关键人一离开，AI 模块立即变成无人敢动的黑盒。

我们不是要限制 AI 的产出量，而是想让把开发流程切成标准阶段，**每个阶段产出一份磁盘文件**，让需求、方案、计划、执行全程可读、可审、可交接、可追溯。

## 【验收目标】

**实现-Spec 一致性**：AI 实际改动与 spec 声明范围（改哪些、明确不动哪些）可自动核查，越界修改/漏实现检出率 ≥ 80%，误报率 ≤ 15%

**变更粒度**：AI 提交按 spec 的功能需求/任务边界拆分，可独立回滚（不牵连无关改动）的比例 ≥ 80%

**评审有效性**：评审从"通读 diff"变为"对照 spec 验收标准逐条核验"，CR 平均停留时长下降 ≥ 30%，同时 CR 后发现的缺陷数持平或下降（防止"靠不审换速度"）

**可追溯性**：commit/MR 100% 可追溯到 Story ID 与 spec/plan/tasks 三件套，spec 与代码不一致可在 24h 内自动发现

**缺陷逃逸率**：测试/线上阶段发现的缺陷 ÷ 全环节缺陷总量，相对基线下降 ≥ 30%

**可解释性覆盖**：AI 提交自动生成"变更说明 + 影响面 + 回滚方案"的比例 ≥ 90%，且人工重写率 ≤ 10%

## 【影响范围】

**角色**：使用 AI 编码的研发工程师（每天在用）、MR 评审人/CR owner（最直接的"看不懂"受害者）、Tech Lead/架构师（质量与流程责任者）、QA（验收口径被测试幻觉架空）、技术管理者（AI 产出的审计与追责边界）。

**团队**：发榜团队 11 人已全量实践 AI 编码 + Spec 工作流；该痛点在所有规模化使用 AI 编码的团队普遍存在，与语言/技术栈无关（我们覆盖终端 C++ 与后端 Go 双栈）。

**业务**：支付等强合规业务对"实现与需求一致、改动可追溯、事故可回滚"有硬性要求——AI 产出不可证明 = 不可上生产，这直接决定 AI 能力能否进入核心链路。

## 【已知约束】

**数据安全**：代码/文档不允许出内网（不上公网第三方服务），方案需支持私有化部署。

**低误报优先**：误报/噪音过多会被一线直接弃用，宁可漏报也别错杀；指标上是误报率 ≤ 15% 优先于检出率。

**工具链兼容**：需兼容 CodeBuddy 等 IDE Agent + GitLab/工蜂 MR + CI，不强求团队更换现有研发工具。

**Spec 形态**：验收标准以中文自然语言 + 半结构化 Markdown 编写，不能要求全员改用形式化语言；存在天然不可自动化的 AC（视觉/现场演练），方案须显式标注"机器判定边界"而非假装全可自动。

**不增加摩擦**：整条核查链路对单个需求的额外耗时 ≤ 15 分钟，能嵌入现有 IDE/CI 流程；流程可以加卡点，但不能把 AI 的速度优势抵消掉。

## 【可提供资源】

**真实数据集**：1 年+ 的 Spec/Plan/Tasks 三件套与对应 MR 全量真实样本——按迭代版本归档、含 status 全生命周期流转（draft→ready→implemented）、偏离记录与评审记录，可脱敏后直接作为评测集。

**方案基座（整套开源给揭榜方）**：团队自研并已运转 1 年的 Spec 驱动 AI 协作工作空间全套源码——三件套模板 + 10 个 `/spec-*` 工作流命令 + 8 个可复用 SKILL + 10 条铁律规则 + 三段式 MR 模板，可直接集成演进、无需从零搭建。

**核心优势**：基座已从源头缓解上述问题——需求先落 Spec 再动手、改动全程由 Story ID 串联可追溯、变更摘要不可省略、AI 偏离必须显式记录。

**试点环境与人力**：内网 GitLab + CI 测试环境，2~3 个真实迭代需求试点；发榜方 1 名工程师对接数据、需求与联调。
