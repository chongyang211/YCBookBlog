# 03｜原理与思想

> 📖 **本篇定位**：解释 CoSpec 每一条约束**背后的为什么**——每条规则不是拍脑袋定的，是针对"人 + AI 协作"中的具体失败模式量身裁的。

## 一、根本矛盾：AI 能做什么、不能做什么

### 1.1 AI 的三个天然弱点

在与 AI 协作写生产代码时，AI 天然有三个弱点：

**弱点 1：上下文易失**

- AI 对话有 token 窗口限制
- 早期信息会被挤出上下文
- 换会话 = 上下文完全重置
- 结果：**同一个需求今天问和明天问，答案可能不一样**

**弱点 2：擅长"合理化"，不擅长"承认不知道"**

- AI 被训练成"给出看起来合理的答案"
- 面对模糊需求，AI 倾向于**猜测并硬填**，而不是主动问
- 结果：**AI 编造出的"业务目标 / 验收标准"看起来很对，实际上是幻觉**

**弱点 3：容易越界执行**

- AI 常常"顺手"改动周边代码（"看着不顺眼"、"顺便优化一下"）
- AI 常常"扩展"需求（用户说 A，AI 实现 A + B + C）
- 结果：**改动范围失控，一个小需求膨胀成一次重构**

### 1.2 人的三个天然弱点

对应的，人在与 AI 协作时也有三个弱点：

**弱点 1：文档懒惰**

- 人不愿意写需求文档（"就一句话的事"）
- 人不愿意写更新（"改了代码谁还回头改文档"）
- 结果：**需求最终只留在人的脑子里**

**弱点 2：面对 AI 输出会失去审视**

- AI 输出看起来"专业"，人容易直接接受
- Peer review 时对 AI 生成的内容审视会不如人写的严格
- 结果：**AI 幻觉被沉默地合并进代码**

**弱点 3：难以追溯半年前的决策**

- 需求 / 讨论 / 决策散落在 IM / 邮件 / 会议纪要
- 一段代码"为什么这么写"半年后无人记得
- 结果：**代码考古成为高频高痛的工作**

### 1.3 CoSpec 的核心洞察

CoSpec 的核心洞察是：

> **AI 的弱点和人的弱点在协作中会互相放大——必须用"流程约束"把两边的短板都封死。**

- AI 上下文易失 → **强制落盘**（磁盘补 AI 的记忆）
- AI 爱猜测 → **AI 无定义权**（凡是不知道必须问，不能填）
- AI 爱越界 → **Plan 明列改动范围**（超出即偏离，可机器校验）
- 人文档懒 → **命令+模板**（AI 帮起草，人只需审）
- 人对 AI 输出失去审视 → **人工评审卡口 + 来源标注**（明确哪些是 AI 推断的，重点审）
- 决策难追溯 → **Story ID 全程串联**（一个 ID 回溯所有产物）

**每一条铁律都对应一个具体的失败模式**——理解了这一点，你就理解了 CoSpec 的全部设计。

## 二、四条核心理念的原理

### 2.1 理念 1：Spec 是单一事实来源

**背后原理**：**"信息越集中，可追溯性越强"。**

对比：

| 需求存放位置 | 可追溯性                                            |
| ------------ | --------------------------------------------------- |
| IM 消息      | 关闭聊天后基本消失                                  |
| 邮件         | 需要按关键词搜索，容易漏                            |
| 需求管理系统 | 好，但**与代码分离**，需要多平台跳转               |
| **仓库内 markdown** | **最强**——与代码同一 Git 提交树，diff 可比对   |

**推论**：spec 与代码不一致时，改哪个由 spec 状态决定：

- `draft / ready` → 需求还没定稿，改代码方向
- `implemented` → spec 才是权威，代码要么修 bug 要么走"偏离回流"

### 2.2 理念 2：三件套必须落盘

**背后原理**：**"AI 的记忆是易失的，磁盘是持久的"。**

三件套分别对应三个持久化需求：

- **Spec** → 持久化"需求"（跨会话跨人跨时间不变）
- **Plan** → 持久化"设计决策"（怎么做 / 为什么这么做）
- **Tasks** → 持久化"实施进度"（做到哪一步了）

**为什么必须三份**：这三类信息**变化频率完全不同**：

| 类型  | 变化频率        | 更新触发                        |
| ----- | --------------- | ------------------------------- |
| Spec  | 需求评审 / 偏离回流 | 业务需求变化                    |
| Plan  | 技术选型确定后基本稳定 | 架构决策改变                    |
| Tasks | 每 15-60 分钟一次   | 每完成一小步                    |

若混成一份，任何一次更新都要触碰整个文件 → merge 冲突频发。

### 2.3 理念 3：执行权 ≠ 定义权

**背后原理**：**"AI 是承包商，人是甲方——甲方能改需求，承包商只能提建议"。**

**为什么如此严格**：

假设 AI 有权改 spec 会发生什么？

```txt
1. AI 实施时发现"这个需求条款和现有代码冲突"
2. AI 顺手把 spec 里那条改了
3. 代码实施成功，一切"正常"合并
4. 半年后回头看，代码是符合 spec 的
5. 但没人知道 spec 已被 AI 悄悄改过
6. 原始业务意图丢失
```

这就是 **"AI silent drift"**（AI 无声漂移）——比 vibe coding 更危险，因为**看起来符合流程**。

**CoSpec 的解**：AI 遇到 spec 有问题，只能：

1. **停下问**：让人明确决策
2. **写偏离记录**：记录到 tasks 的"偏离记录"章节
3. **走偏离回流**：由人评审后回写到 spec 的"修订记录"

**逐任务职责速查**（✅ 主导 / 🤝 协助把关 / ❌ 无权）：

| 任务 | 人 | AI |
|------|:--:|:--:|
| 业务目标 / 验收标准定义 | ✅ | 🤝 起草建议 |
| 技术方案拍板 | ✅ | ✅ 起草主力 |
| Spec 起草 | 🤝 审 + 补 TBD | ✅ 主力 |
| Plan / Tasks 起草 | 🤝 审 | ✅ 主力 |
| 代码 / 测试实现 | 🤝 监督 | ✅ 主力 |
| Code Review | ✅ | 🤝 lint / 提示 |
| 偏离 Spec 决策 | ✅ | ❌ 只能提建议 |
| 重构 / 引入新依赖 | ✅ 立项 | ❌ |

### 2.4 理念 4：全程用 Story ID 串联

**背后原理**：**"分布式产物需要一把主键把它们连起来"。**

CoSpec 的产物散落在：

```txt
intake/*.md       ← 原始需求
designs/*.md           ← 技术方案
specs/*.md             ← 需求单
plans/*.md             ← 实施计划
tasks/*.md             ← 任务清单
Git 分支                ← 代码变更
Commit 消息            ← 每次提交
MR / PR 描述           ← 合并事件
```

**8 类产物如果没有共同主键，就是 8 个孤岛**。Story ID 作为主键的价值：

- 用一个 ID 一次查询回溯所有产物
- Git hook 可以校验 commit 消息是否带 Story ID
- CI 可以校验 MR 描述是否引用 spec
- 半年后翻代码，`git log --grep '--story=12345'` 一键找回全景

## 三、十铁律的原理

每条铁律对应一个具体的失败模式：

### 3.1 铁律 1：无 Spec 不写代码

**对应失败**：直接开始编码 → 需求隐式化 → 半年后无人知道当初为什么这么做。

**深层逻辑**：**任何代码变更都是需求的映射**——如果连需求都没写，等于凭空发明。哪怕是 5 行的 spec，也强迫开发者先想清楚"要做什么"。

### 3.2 铁律 2：三件套必须落盘

**对应失败**：spec 只在对话里存在 → 关闭会话即消失。

**深层逻辑**：**"落盘"是唯一能抵抗 AI 上下文易失的手段**。

### 3.3 铁律 3：AI 不改 Spec

**对应失败**：AI silent drift（见 §2.3）。

**深层逻辑**：**分权制衡**——定义权和执行权分离，才有相互制约。

### 3.4 铁律 4：MR 带 Story ID

**对应失败**：合并后无法从代码回溯到需求。

**深层逻辑**：**代码是需求的映射，映射必须双向可查**。Git hook 强制校验，成本极低但收益极高。

### 3.5 铁律 5：变更摘要必写

**对应失败**：合并请求描述空洞 → reviewer 无法快速理解改动。

**深层逻辑**：**为 reviewer 而写**——不为自己，也不为 AI。变更摘要的读者是"未来某个不熟悉这块代码的人"。

### 3.6 铁律 6：Tasks 实时勾选

**对应失败**：任务清单只在开头和结尾更新 → 中途无法追踪进度。

**深层逻辑**：**进度可见性**——特别是在跨会话推进时，一进入新会话就能从 tasks 看到"上次做到哪了"。

### 3.7 铁律 7：偏离必记录

**对应失败**：AI 顺手改了 plan 外的东西 → 无人察觉。

**深层逻辑**：**偏离本身不可怕，无声偏离才可怕**。CoSpec 不禁止偏离（现实中偏离常有），但要求"偏离必须显性化"。

### 3.8 铁律 8：分支统一

**对应失败**：跨仓库分支名不一致 → 追踪困难。

**深层逻辑**：**"同一 Story 的所有仓库改动，用同名分支"** → `git branch --list feature/12345-*` 一键找齐。

### 3.9 铁律 9：Push 前 rebase

**对应失败**：merge commit 混乱，历史不线性。

**深层逻辑**：**线性历史 = 可读历史**。`git log` 应该像一本书的目录，而不是一张蜘蛛网。

### 3.10 铁律 10：Commit 规范

**对应失败**：commit 消息随意 → `git log` 不可读。

**深层逻辑**：**Commit 是最小的可追溯单元**——每条 commit 都应该独立可读，配合 Story ID 可回溯完整上下文。

## 四、五个关键设计决策的推理

### 4.1 为什么用磁盘 markdown 而不是 Jira / Trello？

**决策**：需求 / 计划 / 任务全部落成 markdown 文件，与代码同仓库。

**推理**：

| 维度            | Jira / Trello                | 仓库 markdown              |
| --------------- | ---------------------------- | -------------------------- |
| 与代码的关系    | 分离，靠 ID 松散关联         | **同仓库同 commit 树**     |
| Diff 可见性     | 需登录系统                   | **git diff 即可看到**      |
| Review          | 需 Jira 权限                 | **走 Git MR / PR 流程**    |
| 离线可用        | 否                           | **是**                     |
| AI 可读性       | 需 API                        | **原生 markdown，AI 直读**|
| 迁移成本        | 换平台就迁移                 | **永远跟随 Git**           |

**核心理由**：**AI 与磁盘 markdown 的亲和性远高于 Jira**。CoSpec 是为"AI 深度参与"设计的，所以选磁盘。

### 4.2 为什么 spec 必须"其他同事"评审？

**决策**：作者本人不能自审 spec，必须由**其他技术同事**评审。

**推理**：

- 自审的盲区太多——**自己写的 TBD 自己觉得都很清楚**
- 其他同事的价值是"用陌生视角发现歧义"
- 特别是 AI 起草的 spec 中"🤖 AI 推断"的内容，需要人的独立判断

**为什么不能只让 AI review**：AI 复审自己起草的 spec 很难跳出同一个思维路径。

### 4.3 为什么 AI 起草 spec 时必须做代码侦察？

**决策**：`/spec-draft` 前必须调用 `codebase-survey` 做 light 模式侦察。

**推理**：

- AI 不看代码就起草 spec = **另一种 vibe coding**
- 现有代码是"最真实的约束"——不了解现状就起草需求，很容易与既有实现冲突
- Light 模式（架构级）足够起草 spec；Deep 模式（细节）留到 Plan 阶段

### 4.4 为什么用 Story ID 而不是自增序号？

**决策**：文件命名用 `<STORYID>-<slug>.md` 而不是 `NNNN-<slug>.md`（早期废弃）。

**推理**：

- 自增序号在多人并行开发时**易冲突**（张三取了 0007，李四也取了 0007）
- Story ID 来自需求系统，天然全局唯一
- Story ID 让代码可以反向追踪到需求系统的原始 Issue

**保留 `slug`**：一个大需求可能拆多个 spec 共享 Story ID → 靠 slug 区分。

### 4.5 为什么 Design 是可选、Plan 是必须？

**决策**：Design 只在大需求时用，Plan 在复杂改动时必须。

**推理**：

- **Design 的价值**：定"用什么方案、拆几个 spec" → 只在需求大 / 方向不明时有价值
- **Plan 的价值**：定"改哪些文件、按什么顺序" → 任何 ≥ 3 个文件的改动都有价值

**为什么不合并**：Design 是**方案级**（架构决策），Plan 是**执行级**（文件级操作）——两者的读者、颗粒度、更新频率完全不同。

## 五、AI 协作哲学：三层防线

CoSpec 对 AI 的信任设计成"三层防线"，从**结构性防线 → 流程性防线 → 校验性防线**逐层收紧：

### 5.1 第一层：结构性防线（磁盘契约）

**手段**：把关键信息全部落盘。

**防的问题**：AI 上下文易失、跨会话信息丢失。

**具体**：三件套磁盘文件 + 模板 + 目录约定。

### 5.2 第二层：流程性防线（命令 + 卡口）

**手段**：命令链切分阶段，关键节点设人工卡口。

**防的问题**：AI 越界执行、无声偏离、跳过关键步骤。

**具体**：8 阶段命令 + spec 强制人审 + tasks 偏离记录。

### 5.3 第三层：校验性防线（机器可校验的约束）

**手段**：用 Git hook / CI 自动校验规则。

**防的问题**：人的疏忽（忘带 Story ID、忘更新 tasks 等）。

**具体**：

- Pre-commit hook 校验 commit 消息格式
- CI 校验 MR 描述是否引用 spec
- 定期扫描"tasks 未完成但 spec 已 implemented"的不一致

## 六、CoSpec 与传统方法论的对比思想

### 6.1 CoSpec vs 敏捷开发

| 维度        | 敏捷                        | CoSpec                                |
| ----------- | --------------------------- | ------------------------------------- |
| 关注点      | 团队协作 / 迭代节奏         | **人 + AI 的协作契约**                |
| 需求形式    | User Story (Jira)           | **仓库内 markdown spec**              |
| 文档态度    | "工作的软件重于详尽的文档"  | **文档就是工作的一部分（AI 读它）**   |
| 兼容性      | 可以完全兼容                | 补充敏捷缺失的"AI 协作约定"层         |

**CoSpec 不与敏捷冲突**——它填补的是敏捷时代没有考虑的"AI 深度参与"这一层。

### 6.2 CoSpec vs 传统瀑布 / RUP

| 维度        | 瀑布 / RUP              | CoSpec                            |
| ----------- | ----------------------- | --------------------------------- |
| 阶段划分    | 有                      | 有（8 阶段）                     |
| 文档权威    | 极强                    | 强（但可裁剪）                   |
| 迭代性      | 弱                      | **强**（可回退到任一阶段）       |
| AI 视角     | 无                      | **一切为 AI 协作设计**            |

### 6.3 CoSpec 的独特定位

**一句话**：**CoSpec 是"给 AI 协作时代设计的敏捷 + 文档契约"**——保留敏捷的迭代性，补上文档契约让 AI 可读可执行。

## 七、常见质疑与回应

### Q1：这么多流程，效率不会降低吗？

**答**：短期看，中大型需求全流程会多花 15-30 分钟。**长期看效率提升**：

- 换会话 / 换人接手成本大幅降低
- 半年后回溯成本从"几小时读代码"降到"5 分钟读三件套"
- AI 幻觉导致的返工减少 → 每次减少的返工时间就能覆盖 CoSpec 投入

### Q2：AI 现在这么强，还需要这么严格约束吗？

**答**：AI 越强，越需要约束。理由：

- AI 越强 → 人越信任 AI 的输出 → 越容易接受 AI 幻觉
- AI 越强 → 一次能改动的范围越大 → 一次失控代价越大
- **CoSpec 的价值不是"防止 AI 犯错"，是"让错误可追溯、可回滚"**

### Q3：小项目也要用吗？

**答**：小项目可**大幅裁剪**：

- 只用 `/spec-draft` + `/spec-implement` + `/spec-sync`
- 跳过 intake / design / plan / tasks
- 一份 spec 顶所有

**但不能完全跳过 spec** —— 哪怕 5 行的 spec 也胜过 0 行。

### Q4：AI 起草的 spec 质量能保证吗？

**答**：**AI 起草只是初稿，质量靠人审**。CoSpec 的设计假设是：

- AI 起草是**降低门槛**（把"写 spec"从 30 分钟压到 5 分钟）
- 人审是**质量保证**（发现 AI 幻觉、补齐 TBD、拍板决策）

**不允许 AI 自审并直接 `Status: ready`**——这是流程铁律。

### Q5：我们已经在用 Jira / Confluence，能兼容吗？

**答**：能。CoSpec 与需求管理系统**互补而非替代**：

- Jira / Confluence：管理需求生命周期 / Story 关系 / 报表
- CoSpec：管理"从需求到代码"的执行契约

**串联方式**：把 Jira Story ID 用作 CoSpec 的 Story ID → 两个系统天然打通。
