# 项目级 AI 协作原则

本文件定义了 AI 在本仓库中工作时的基础原则。所有其他规则文件都建立在这些原则之上。

## 原则一：Spec 是单一事实来源

- 所有功能实现必须可追溯到 `specs/` 中的具体 spec 文档
- 口头描述或聊天中的指令不能替代 spec；如果指令与 spec 冲突，应先指出冲突
- 没有对应 spec 的修改，应建议先补充 spec

## 原则二：先理解后行动

- 接到任务后，**必须先阅读相关 spec 和涉及的现有代码**，确认理解正确
- 如果上下文不足以理解任务全貌，**主动读取更多文件**，而不是假设
- 在不确定时，先说明自己的理解并请求确认，再动手修改

## 原则三：最小改动

- 每次修改应尽可能小，只改与当前 spec 直接相关的部分
- 不做"顺手"的优化、重构、风格调整
- 如果发现了其他问题，记录下来但不在本次修改中处理

## 原则四：与现有结构保持一致

- 遵循 `src/` 中已有的代码风格、命名约定、目录组织方式
- 不引入新的框架、库或模式，除非 spec 明确要求
- 新代码应该看起来像现有代码的自然延伸

## 原则五：透明可追溯

- 每次修改都应输出清晰的变更摘要
- 说明改了什么、为什么这样改、影响范围
- 如果做了任何假设或取舍，必须明确说明

## 原则六：流程优先于效率

- 即使知道怎么做，也要走完 spec → plan → implement → test → summarize 流程
- 跳过流程看似更快，但会导致遗漏、偏离 spec、缺少测试
- 只有在人明确要求跳过某步骤时，才可以省略

## 原则七：不做无关重构

- 如果 spec 只要求新增一个功能，不要同时重构相邻代码
- 如果发现现有代码有问题但与当前任务无关，记录为建议但不修改
- 重构是一个独立的 spec 主题，需要单独处理
