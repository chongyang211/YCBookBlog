# 编码规则

AI 在修改 `src/` 中的代码时，必须遵循以下规则。

## 最小改动原则

- 只修改与当前任务直接相关的代码
- 不做"顺便"的优化、格式调整、变量重命名
- 如果一个文件只需要改 3 行，不要输出整个文件
- 修改前先读取目标文件，了解当前状态

## 复用优先

- 优先使用项目中已有的工具函数、类型定义、常量
- 新增代码前，先搜索是否已有类似实现可复用
- 不重复造轮子，不引入功能重叠的新依赖

## 避免不必要重构

- 不要因为"看着不顺眼"就重构现有代码
- 不要为了"更优雅"而改变已经能正常工作的逻辑
- 重构是独立的 spec 任务，不应混在功能开发中
- 如果发现需要重构的地方，在变更摘要中记录为建议

## 与现有结构保持一致

- **命名**：遵循现有代码的命名风格（camelCase / snake_case / PascalCase 等）
- **目录**：新文件放在现有目录结构中最合理的位置
- **模式**：如果现有代码用了某种设计模式，新代码应遵循同样的模式
- **缩进**：使用与现有代码一致的缩进（tab/space、宽度）
- **注释**：遵循现有的注释风格和详细程度

## 状态机注释维护

- 修改刷掌状态机（新增/删除/调整状态、转移、事件、Verdict、Action）时，**必须同步更新 `palm_flow_fsm_def.h` 顶部的状态流转图注释**
- 状态图需反映：状态层次（Composite/leaf）、所有转移（含重试循环、超时、abort）、关键 Verdict 分支、事件触发条件
- 新增状态时在图中标明 enter/exit 行为（arm/disarm timer、emit event）与 completion_source 语义
- 注释更新与代码改动同一 commit，不单独拆分

## 模块边界

- 不跨模块修改代码，除非 spec 明确要求
- 新增功能应有清晰的模块边界
- 公共接口（导出的函数/类/类型）的变更需要特别谨慎
- 内部实现的修改不应影响公共接口的行为

## 修改代码前的必做事项

1. 读取要修改的文件，了解当前内容
2. 读取相关的文件（被调用者、调用者），了解上下文
3. 确认修改不会破坏现有调用方
4. 如果涉及接口变更，列出所有受影响的调用方

## 错误处理

- 新增代码必须包含合理的错误处理
- 不吞掉错误（空 catch/except）
- 错误信息应有足够信息帮助定位问题
- 遵循项目已有的错误处理模式

## 依赖管理

- 不引入新的外部依赖，除非 spec 明确要求
- 如果必须引入，说明理由和替代方案
- 优先使用标准库
