# 测试规则

## 为什么需要测试

- 测试是验证实现符合 spec 的唯一客观手段
- 测试防止后续修改引入回归
- 测试是活文档，说明代码应该如何工作

## 什么情况下必须补测试

以下情况**必须**编写或更新测试：

1. 新增功能（对应 spec 中的功能需求和验收标准）
2. 修复 bug（测试应能重现 bug 并验证修复）
3. 修改公共接口的行为
4. 修改核心业务逻辑

以下情况**可以不补**测试：

1. 纯注释/文档修改
2. 不影响行为的代码格式调整
3. 配置项变更（视情况）

## 测试覆盖要求

### 必须覆盖

- **关键路径**：spec 中每个功能需求的正常流程
- **验收标准**：spec 中列出的每个验收标准至少一个测试
- **边界情况**：spec 中列出的所有边界情况
- **错误处理**：非法输入、资源不存在等异常路径

### 建议覆盖

- 状态转换的各种组合
- 空输入、极大输入
- 并发场景（如 spec 涉及）

## 测试命名

测试命名应能直接看出测试内容，推荐格式：

```
Test_[功能]_[场景]_[预期结果]
test_[功能]_[场景]_[预期结果]
```

示例：
- `Test_CreateTodo_ValidInput_ReturnsNewTodo`
- `Test_CreateTodo_EmptyTitle_ReturnsValidationError`
- `test_list_todos_filter_by_status_returns_filtered`

## 测试组织

- 测试文件放在 `tests/` 目录中
- 文件命名与被测模块对应
- 相关测试用 describe/group 组织在一起

## 无法编写自动化测试时

如果因技术限制无法编写自动化测试，应：

1. 明确说明原因
2. 提供手动测试步骤
3. 说明未来何时/如何补上自动化测试
4. 在变更摘要中标注"测试缺口"
