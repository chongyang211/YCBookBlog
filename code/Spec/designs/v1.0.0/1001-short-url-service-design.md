## 1. 需求背景与目标

来自 intake（`intake/v1.0.0/1001-short-url-service.md`）：文章长 URL 分享被截断，
需提供短链生成与跳转，并支持点击统计。运营方明确：活动页过期后短链不报错，跳说明页。

**澄清结论**（已与王敏确认）：

| 澄清点 | 结论 |
|--------|------|
| 保留期 | 默认 90 天，创建时可指定（最长 1 年）；到期后跳"链接已过期"说明页 |
| 自定义后缀 | 本期不做（非目标），预留短码字符集兼容性 |
| 统计维度 | 总量 + 按天 + 按渠道（utm 参数透传）；运营后台报表由 stats 子 spec 承接 |
| 目标 URL 范围 | 仅允许本平台域名（白名单），防钓鱼滥用 |
| 短链域名 | `s.example-content.com`（主域子域，复用证书体系） |
| 防滥用 | 同一创建者 60 次/分钟 频控 + 域名白名单 |
| 端范围 | 本期 Web 端；移动端分享 SDK 接入下期 |

## 2. 现状分析

- `share-service`（Go 1.23 + gRPC）：现有分享渠道适配，无短链逻辑
- 存储统一 MySQL 8.0（主从）；缓存 Redis 3 节点哨兵
- 网关 `api-gateway` 按路径前缀路由；`s.` 子域已有证书与 DNS 控制权
- 平台日均文章 5 万篇，预估短链创建峰值 50 QPS、跳转峰值 5000 QPS

## 3. 总体方案

新建独立 `shorturl-service`（与 share-service 同构部署），职责：生成短码、302 跳转、过期判定。
点击统计由事件异步写入，归 stats 子 spec。

```
用户/编辑器                s.example-content.com/{code}
    │ POST /api/shorturl          │ GET
    ▼                             ▼
api-gateway ──► shorturl-service ──► 302 Location: target
                     │  miss
                     ▼
              Redis(cache) ──► MySQL(short_url 表)
                     │ 命中跳转时
                     ▼
              Redis List / Kafka(点击事件) ──► stats 消费（子 spec）
```

## 4. 方案对比（短码生成算法）

| 维度 | A. 自增 ID + Base62 | **B. MurmurHash + 碰撞重试（选定）** | C. 预生成号段服务 |
|------|--------------------|------------------------------------|------------------|
| 短码长度 | 6 位即可 | 7 位 | 6 位 |
| 实现复杂度 | 低 | 中（需查重） | 高（号段服务、断电恢复） |
| 可预测性 | **差：短码可被枚举遍历，竞品可批量抓取我们的文章映射** | 好：不可预测 | 差（同 A） |
| 碰撞处理 | 无碰撞 | 62^7 ≈ 3.5 万亿空间，亿级数据下碰撞概率可忽略，冲突时加盐重试 | 无碰撞 |
| 运维成本 | 低 | 低 | 高 |
| 适用规模 | 中小 | 中大 | 超大（日均亿级创建） |

**选择 B**。淘汰 A 的决定性理由：短码可枚举 = 平台内容映射可被第三方批量爬取（安全评审一票否决）。
淘汰 C 的理由：我们峰值 50 QPS，上号段服务是过度设计。

## 5. 关键技术决策

| # | 决策 | 选择 | 淘汰 | 理由 |
|---|------|------|------|------|
| D1 | 短码算法 | MurmurHash64 + Base62 截取 7 位 + 冲突加盐重试 | 自增 ID；号段 | 见 §4 |
| D2 | 跳转方式 | 302（临时） | 301 | 301 会被浏览器永久缓存，过期/封禁后无法收回 |
| D3 | 存储 | 复用 MySQL，新表 `short_url`（主键 short_code） | 新库 / MongoDB | 数据量千万级，现有体系足够；避免新增存储组件 |
| D4 | 缓存 | Redis，code→target 热点缓存，TTL = min(剩余有效期, 24h) | 本地缓存 | 多实例部署下本地缓存一致性差 |
| D5 | 过期判定 | 惰性判定（跳转时检查）+ 每日批量清理任务 | 实时状态机 | 短链过期无需精确到秒，惰性判定零额外成本 |
| D6 | 点击采集 | 跳转路径上 Redis List 缓冲，异步落库 | 同步写库 | 跳转 P99 < 50ms 的硬指标不允许同步写统计 |

## 6. 跨系统 / 跨仓库影响

| 系统 | 影响 | 是否本期改动 |
|------|------|--------------|
| api-gateway | 新增 `/api/shorturl` 与 `s.` 域名路由规则 | ✅ 配置变更 |
| share-service | 无改动（编辑器复制链接入口由前端直调 shorturl） | ❌ |
| Web 前端 | 文章页「复制链接」改产出短链 | ✅（前端独立 spec，非本 Story） |
| DNS / 证书 | `s.example-content.com` 解析与证书挂载 | ✅ 运维操作 |
| 移动端分享 SDK | 下期接入 | ❌ 非目标 |

## 7. 数据结构 / 接口影响（高层）

- 新表 `short_url`：short_code(PK)、target_url、creator_id、expire_at、created_at
- 新接口：`POST /api/shorturl`（创建）、`GET s.xxx/{code}`（跳转）
- 点击事件：`shorturl_click`（code、ts、referer、ua 摘要）——结构归 stats 子 spec 定义

## 8. 建议的 spec 拆分 ⭐（本 Design 的核心产出）

需求含两个可独立交付的能力，建议拆为 **2 个子 spec，共享 Story ID 1001**，可并行开发：

| 建议 slug | 边界 | Owner | 依赖 |
|-----------|------|-------|------|
| `1001-short-url-core` | 短码生成、创建 API、302 跳转、过期与频控 | 后端 · 陈晨 | 无（先做，产出点击事件流） |
| `1001-short-url-stats` | 点击事件消费、统计聚合、运营后台报表接口 | 后端 · 刘睿 | 依赖 core 的事件流定义 |

两个 spec 在 frontmatter 互相引用（`Sibling Specs` 字段），MR 均带 `--story=1001`。
